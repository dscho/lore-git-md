Here's a human-readable summary of the thread so far:

Carlos Maiolino reported a concerning behavior where `git tag -s` silently falls back to a different GPG key when the configured smartcard-based signing key is unavailable, rather than failing or warning as expected. This poses security risks for users relying on hardware-backed keys.

Jeff King (Peff) investigated and found the issue appears to be in how Git handles config-specified keys versus CLI-specified keys. His latest analysis clarifies that Git simply passes the configured key string to GPG without checking availability itself, relying on GPG's response. The key question now is whether the substitution happens because Git is incorrectly passing the key (visible in GIT_TRACE) or if GPG is accepting but then substituting the key.

The discussion is narrowing in on diagnostic steps - particularly examining GIT_TRACE outputs to see exactly where in the pipeline the key substitution occurs. Both parties agree that at minimum, Git should warn users when it can't use their specifically requested signing key, especially for security-sensitive operations. The next steps involve determining whether the fix needs to be in Git's GPG plumbing or if GPG itself needs modification to properly report these cases.
