Carlos Maiolino reported a bug in `git tag -s` signing behavior with smartcard-stored GPG keys. When the configured `user.signingKey` (on a smartcard) is unavailable, Git silently falls back to a different key rather than failing or warning, contradicting documented behavior. Jeff King investigated and found that while CLI-specified keys work correctly (`gpg --status-fd=2 -bsau <key>`), config-specified keys exhibit this fallback behavior when inaccessible. The core issue is Git's silent fallback when the primary key cannot be accessed (e.g., smartcard disconnected), which undermines reliability for hardware-backed signing. This appears to be a legitimate bug in Git's key availability handling, distinct from GPG's behavior. The technical focus is on the interaction between `user.signingKey` configuration and GPG invocation when keys are hardware-bound. The thread remains open with the key question being whether Git should fail or warn when the configured signing key is unavailable, particularly for security-sensitive operations.
