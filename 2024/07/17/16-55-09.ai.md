This is a bug report about `git subtree` failing to properly handle merges and hitting recursion limits when splitting subtrees. The reporter, Ian Jackson, provides detailed reproduction steps showing that:

1. In Git 2.45.2, `git subtree split` fails with a "Maximum function recursion depth" error when trying to extract a subtree from a repository with merge-heavy ancestry (the arti.git repository).

2. In Git 2.20.1, the command succeeds but takes an excessively long time and produces an incorrect history that includes commits from the parent repository rather than just the subtree.

The report includes specific commit hashes and merge request references from the Tor Project's arti repository where the issue manifests. Jackson notes that a workaround exists (checking out a specific parent commit before splitting), but this is only viable because the current history is relatively straightforward.

The core issue appears to be that `git subtree`'s merge handling is either inefficient or incorrect when processing repositories where the subtree was added via merge commits. This affects both current and older versions of Git, though the failure modes differ (recursion error vs incorrect output). The report is well-documented with clear reproduction steps and version-specific behavior, making it straightforward to investigate.
