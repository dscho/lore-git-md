This thread concerns a bug report from Ian Jackson about `git subtree split` failing in different ways across Git versions when processing repositories with merge-heavy histories. In Git 2.45.2, the command hits a shell recursion limit (specific to Debian's POSIX implementation), while in Git 2.20.1 it produces incorrect history by including commits from the main repository rather than just the subtree. The test case comes from the Tor Project's arti.git repository.

Colin Stagner has now responded with technical analysis. He identifies that the 2.45.2 recursion issue stems from Debian's shell implementation and has proposed a patch to address that specific limitation. However, he notes that even with this fix, the underlying problem with merge handling persists - the command still produces thousands of commits when only dozens are expected. This appears to trace back to changes in merge base handling from commit e7b07376e5, suggesting the issue may reflect fundamental ambiguities in how subtree operations interact with merge commits rather than being a straightforward bug.

While Colin's patch offers a path forward for the recursion issue, the thread now faces a deeper question about whether `git subtree` can reliably handle complex merge histories at all, or if this represents an inherent limitation of the command's design. No solutions have yet been proposed for the history inclusion problem, which remains open.
