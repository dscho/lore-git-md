This thread examines whether to adopt a clang-format rule (`RemoveBracesLLVM`) that removes braces from single-statement conditional bodies in Git's codebase. The rule was introduced experimentally in CI by Karthik Nayak, but testing revealed problematic cases - notably in `builtin/receive-pack.c` where it removed braces from a multi-line `for` loop that should have kept them for clarity.

Junio Hamano has weighed in with a pragmatic perspective. While not objecting strongly to the specific formatting changes, he notes they don't provide meaningful improvement either. He distinguishes between modifying existing code (where such changes aren't worth the churn) and new code (where the style might be reasonable). His response validates earlier concerns about the rule's limitations in semantic analysis - it can't distinguish between simple one-liners (where brace removal might be acceptable) and more complex cases (where braces aid readability).

The discussion appears to be converging toward either keeping the rule as a non-blocking CI suggestion or abandoning it entirely, given both the demonstrated formatting issues and the fact contributors rarely use `git clang-format` before submission. The original goal of standardizing brace usage through automation seems increasingly unlikely to be realized with this particular rule.
