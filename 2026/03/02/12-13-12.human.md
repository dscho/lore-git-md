Feature: New `git history split` subcommand for interactive commit splitting

This is the final patch in Patrick Steinhardt's 8-part series introducing a new `git history split` command. The command simplifies the common workflow of splitting a single commit into two by interactively selecting which changes should move to a new parent commit. The implementation builds on the refactoring done in earlier patches to decouple the add-patch infrastructure and enable in-memory index operations.

The new subcommand presents changes from the target commit and lets users select which hunks should move to a new commit. It then creates two commits - one with the selected changes (as the new parent) and one with the remaining changes (as the child). The original commit message is reused for both new commits, though users can edit them. The command handles branch updates similarly to `git history reword`, rewriting descendant commits as needed.

The patch includes extensive test suite (755 lines) covering edge cases like empty commits, merge commits, path limiting, and various split scenarios. The implementation appears thorough, with careful handling of tree states, authorship preservation, and integration with the existing history command framework. Given Patrick's track record with architectural changes and the comprehensive test coverage, this looks like a well-considered addition to the experimental `git-history` command family.
