Bugfix for a performance regression in `git-receive-pack`'s hook handling, restoring an optimization lost during the hook API conversion.

Adrian Ratiu submits a small but important fix that prevents `git-receive-pack` from spinning up unnecessary async threads when processing sideband hooks (update, post-update, and receive hooks) that don't exist. The regression was introduced in commit fc148b146ad4 ("receive-pack: convert update hooks to new API") when the code was converted to use the new hook API but lost an optimization that checked for hook existence first.

The patch adds back the early-exit check using the modern `hook_exists()` API, which properly handles both config-defined hooks and traditional hookdir hooks. Patrick Steinhardt originally reported the performance impact, and Jeff King helped analyze the root cause. Benchmark results show measurable overhead from the unnecessary thread creation when processing many refs.

This is a focused fix that touches only `builtin/receive-pack.c`, adding three similar checks in the hook-running functions. The change is straightforward and has already passed CI testing. It's part of the ongoing hook subsystem improvements but stands alone as a clear performance win.
