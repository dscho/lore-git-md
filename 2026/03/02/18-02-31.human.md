This is a follow-up in an ongoing performance regression investigation regarding `receive-pack` operations with the reftable backend. Adrian Ratiu confirms Jeff King's root cause analysis that the slowdown (2.66x in system time when handling 10k refs) stems from unnecessary sideband muxer setup/teardown for each `update` hook invocation, even when no hook exists.

Adrian indicates he has independently identified the same issue and is preparing a more comprehensive fix that will address the problem across three different hook types (not just `update` hooks) that currently spin up and tear down no-op async threads. The fix appears straightforward - skipping hook processing when no hook exists - but needs to be applied consistently across multiple hook types.

The discussion shows good technical alignment between contributors, with Patrick Steinhardt providing initial benchmarking, Jeff King diagnosing the root cause, and Adrian Ratiu now taking the lead on implementing the fix. The regression is specific to the reftable backend and unrelated to other recent changes in the area.
