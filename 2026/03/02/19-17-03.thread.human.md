This thread addresses a performance regression in `git-receive-pack`'s hook handling that was introduced during the recent hook API conversion. The original issue, identified by Patrick Steinhardt and root-caused by Jeff King, involved unnecessary overhead from spinning up async threads for sideband hooks even when no hook existed. Adrian Ratiu's patch (now finalized by Junio) fixed this by restoring the early-exit optimization using the new hook API's `hook_exists()` function, achieving a 2.7x speedup at 10k refs.

In the latest discussion, Jeff King notes that while the current solution works well, there's still some inefficiency in how hooks are looked up twice - once for the existence check and again when running the hook. He suggests a potential reorganization using `HOOK_INIT` and `load_hooks()` to avoid this, but acknowledges the current caching behavior may make this optimization unnecessary. The conversation reveals that while config-based hooks are already cached, filesystem hooks still do fresh `access()` checks on each lookup - a known tradeoff in the current design that hasn't proven problematic in practice.

The immediate fix is settled, with consensus that Ratiu's approach is correct. The discussion leaves the door open for future optimizations if profiling shows the double-lookup becomes a bottleneck, particularly for frequently-run hooks like "update" that execute per-ref. This thread exemplifies Git's careful balance between correctness, performance, and maintainability in its ongoing hook subsystem improvements.
