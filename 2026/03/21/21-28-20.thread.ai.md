Thread identity: Patch series from Lorenzo Pegorari addressing promisor file handling during repacks, part of GSoC work. Current version is v1 (initial submission).

Core problem: When repacking promisor packfiles, Git does not properly preserve the mapping between refs and their corresponding packfiles in `.promisor` files (noted in `NEEDSWORK` comment from commit 5374a290). The work involves both documenting and fixing this behavior.

Current status: Initial submission (v1) consisting of 3 patches now complete. First patch added documentation clarifying `.promisor` file contents. Second patch introduced helper function `copy_all_promisor_files()` to consolidate multiple `.promisor` files during repack, with acknowledged inefficiencies in duplicate checking. Third patch modifies repack logic to use this helper, preserving debug information in the first promisor file while leaving others empty.

Key technical details:
- First patch added documentation to `pack-write.c` explaining `.promisor` file contents are debug-only records of refs/hashes from fetch time
- Second patch adds helper function in `repack-promisor.c` that:
  - Iterates through all packfiles
  - Reads `.promisor` files line-by-line
  - Uses `fseek`-based duplicate checking (acknowledged as inefficient)
  - Writes consolidated output
- Third patch modifies `pack-write.c` and `pack.h` to use this helper:
  - Marks first promisor file as special for debug info
  - Updates `git-repack.adoc` to note promisor files may contain "arbitrary contents"
  - Leaves subsequent promisor files empty
- Implementation questions remain around:
  - More efficient duplicate entry checking
  - Whether to use Git's higher-level I/O abstractions
  - Error handling robustness
  - General design validation

Open questions:
- Is the current consolidation strategy optimal given I/O inefficiency?
- Should duplicate checking use different data structures?
- Are there existing Git utilities that could replace direct file I/O?
- Is single-file consolidation preferable to maintaining per-pack promisor files?
- General design feedback still requested

Participant positions: Only author's position recorded so far - acknowledges implementation inefficiencies in second patch and seeks guidance. This remains Lorenzo Pegorari's first significant contribution in this area.

Related work: Builds on commit 5374a290 which originally noted the issue. Part of GSoC project.
