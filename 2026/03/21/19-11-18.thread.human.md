This thread began with a bug report from Jo Liss about `git-remote-http` segfaulting when parsing refspecs outside a repository context, particularly when running `git ls-remote -h <url>` with global `remote.origin.fetch` set. K Jayatheerth provided an initial fix that addressed the immediate crash by having remote-curl initialize a fallback SHA-1 hash algorithm, along with a test case in t5551.

Jeff King (Peff) has now contributed a deeper analysis, identifying that the root cause traces back to commit c8aed5e8da which changed how SHA1 is set as the default object hash. While the immediate crash occurs when dereferencing `the_hash_algo`, Peff explains the more fundamental issue involves determining which hash algorithm to use when operating outside a repository. He notes that remote-curl normally detects the hash algorithm from the server's response, but this happens after the problematic refspec parsing occurs. 

Peff points out that simply adding a NULL check for `the_hash_algo` would mask rather than solve the underlying architectural question of how hash algorithms should be handled in repository-less remote operations. The discussion has now expanded beyond the immediate crash to consider the `exact_sha1` flag's role and the timing of hash algorithm detection, suggesting the solution may need more careful design consideration. This analysis indicates the fix may need to address when and how the hash algorithm is determined for remote operations outside a repository context.
