This is a review comment from Jeff King on Vaidas Pilkauskas's HTTP 429 rate limit series, specifically addressing patch 3/4 which introduces a helper function for HTTP error handling. Jeff argues against the proposed refactoring, finding it adds complexity without clear benefit.

The patch in question attempts to consolidate repeated patterns of showing HTTP error messages followed by die() calls into a single show_http_message_fatal() helper. Jeff's critique focuses on several technical points: the refactoring doesn't actually reduce line count, it makes the error handling less flexible, and it introduces unnecessary cleanup of strbufs that will be freed anyway when die() is called. He also notes the helper encodes exit() logic into the curl code where it doesn't belong.

Jeff suggests dropping this patch entirely, recommending that the HTTP 429 implementation in patch 4 should stick with the existing pattern of separate show_http_message() and die() calls. His review indicates this is a matter of code organization preference rather than a functional issue with the HTTP 429 feature itself.

This feedback comes from a respected HTTP transport expert (Jeff King) whose opinion carries weight in this area. The author will need to decide whether to revise or drop this patch based on the critique, while the core HTTP 429 functionality in the series remains technically sound and ready for final review.
