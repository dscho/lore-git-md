Lorenzo Pegorari's GSoC proposal to implement configurable fetch ordering for promisor remotes in partial clones has progressed through productive technical review. The proposal addresses a real need for users managing multiple promisor remotes by introducing a `remote.<name>.priority` configuration (simplified from the original `promisorPriority` name) with a fixed 1-100 range. 

Christian Couder provided key technical feedback that helped refine the design. Lorenzo has incorporated this, clarifying that lazy fetches don't use filters (unlike initial partial clones) and that promisor-remote capability is tied to usage rather than server object presence. They've settled on global priorities rather than per-server contexts, as the edge case requiring server-specific priorities is too unusual to justify the complexity.

Lorenzo has demonstrated good understanding of the promisor remote subsystem through this exchange and plans to fix minor formatting issues in the proposal before official GSoC submission. With three prior patches (two merged) showing his partial clone expertise, this well-scoped project appears technically sound and ready for implementation. The remaining open question is whether to document the priority range in the configuration or treat it as an implementation detail.
