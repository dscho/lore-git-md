This is part of Patrick Steinhardt's ongoing performance optimization series targeting lock contention in `git-upload-pack` during high-concurrency scenarios. The current patch introduces an extended version of `hashfd()` that groups optional parameters into a struct, following a common Git pattern.

The change refactors the internal `hashfd_internal()` function into a public `hashfd_ext()` that takes mandatory parameters directly and optional ones via a new `hashfd_options` struct. This provides a forward-compatible interface that can evolve without changing the function prototype. The patch maintains the series' focus on reducing write syscalls while improving code organization.

Junio C Hamano questioned the parameter grouping strategy, and Patrick explains the rationale: mandatory parameters (hash algorithm, file descriptor, name) remain direct arguments while optional ones (progress meter, buffer length) move to the options struct. This follows established patterns in the codebase.

The discussion around this patch intersects with broader architectural questions in the series about whether to use `writev()`-based batching (Patrick's approach) versus alternative buffer management strategies proposed by Jeff King. While this particular patch is uncontroversial, its design reflects the careful interface considerations needed to support the different optimization approaches under debate.
