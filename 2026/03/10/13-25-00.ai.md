This is part 4/10 of Patrick Steinhardt's performance optimization series targeting lock contention in `git-upload-pack` during high-concurrency scenarios. The patch focuses on reducing write syscall frequency by implementing smarter buffering in the packfile data relay path.

The key change introduces a 2/3 buffer fill threshold before flushing data to clients, significantly cutting write syscalls from ~400k to ~130k when cloning the Linux repository. The implementation leverages existing buffering infrastructure while carefully avoiding negative impacts on read operations. The patch maintains compatibility with pack-objects hooks via `uploadpack.packObjectsHook` by handling buffering at the upload-pack level rather than relying on pack-objects changes alone.

Technical details include:
- New buffer management in `relay_pack_data()` with 2/3 fill threshold
- Preserved sideband handling and pktline framing
- Explicit consideration of the tradeoff between write reduction and potential read increase
- Follow-up planned for pack-objects buffer adjustments

The change addresses a real production pain point where upload-pack processes were spending 80% of time in kernel-level pipe write contention. The solution demonstrates measurable improvements while maintaining the existing architecture's safety properties.
