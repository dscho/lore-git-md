This is part 4 of Patrick Steinhardt's performance optimization series targeting lock contention in `git-upload-pack` during high-concurrency scenarios. The patch specifically addresses write syscall overhead by increasing buffering when streaming packfile data to clients.

The change modifies `upload-pack.c` to buffer more data before writing - waiting until the buffer is at least 2/3 full rather than writing immediately. This reduces write syscalls from ~400k to ~130k when cloning the Linux repository. The 2/3 threshold was chosen as a balance between write reduction and avoiding increased read syscalls (going to full buffering would only save ~30k more writes).

The patch notes this could alternatively be fixed in `git-pack-objects`, but that wouldn't help when using `uploadpack.packObjectsHook`. A follow-up will address `pack-objects` separately. The implementation builds on existing buffering infrastructure and maintains the existing flush behavior when pack-objects finishes.

This is a well-motivated change with clear performance measurements showing the 80% reduction in write syscalls. The commit message thoroughly explains the tradeoffs and rationale for the chosen approach. As part of a larger series that's already undergone several iterations, it appears ready for consideration.
