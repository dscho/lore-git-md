This is a follow-up discussion in the merged `git fast-import` signature handling series, focusing on naming and potential future extensions. The core functionality (adding a `re-sign-if-invalid` mode for commit signatures) is already merged, but Junio C Hamano and Justin Tobler are refining the design.

Junio suggests renaming the mode from `re-sign-if-invalid` to `sign-if-invalid`, arguing the "re-" prefix is redundant since "if-invalid" already implies the object was previously signed. He also raises a broader question about whether signature handling should be split into separate concerns: one option for stripping invalid signatures (`strip-if-invalid`) and another for actively signing commits (`--sign-commits`).

Justin agrees the naming change makes sense and may send a follow-up patch. He notes the current implementation intentionally focuses only on re-signing previously-signed-but-now-invalid commits, leaving unsigned commits untouched. While acknowledging Junio's point about projects that might want to sign all commits during history rewriting, Justin suggests that would require a separate option since the current `--signed-commits` parameter is specifically about handling already-signed objects.

The discussion hints at future work directions: supporting tag signatures (not yet implemented) and potentially adding a distinct `--sign-commits` option for signing previously-unsigned objects.
