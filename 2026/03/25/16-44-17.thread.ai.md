[PATCH 0/5] refs: continue removing `the_repository` usage

Series from Shreyansh Paliwal eliminating global state in refs subsystem by converting functions to take explicit `struct repository *` parameters. Builds on jw/object-name-bitset-to-enum. Five mechanical conversions covering branch helpers, file ref lock timeouts, hash algorithm usage, reftable backend, and packed backend. All three ref backends (files, reftable, packed) now free of direct `the_repository` usage except for one remaining `is_bare_repository()` dependency in reftable.

Patrick Steinhardt reviewed the branch helper conversions (patch 1/5), noting the changes look good but suggesting placing `struct *` parameters first in function signatures per codebase convention. For patch 2/5 (ref lock timeouts), Patrick confirms the technical approach using a `create_reflock_cb` struct to pass both lock_file and repository context through to the `create_reflock()` callback is correct. Burak Kaan Karaçay later noted that while the patch correctly adds repository parameter, it retains static variables for caching timeout configuration which could cause issues in multi-repo scenarios, suggesting future move to `repo-settings` mechanism for proper caching.

Regarding patch 4/5 (reftable backend), Patrick acknowledges Shreyansh's removal of two remaining `the_repository` uses in `refs/reftable-backend.c` while noting the persistent `is_bare_repository()` call remains a systemic blocker for complete `USE_THE_REPOSITORY_VARIABLE` removal across Git. This limitation is recognized as requiring broader changes beyond this series.

Changes touch branch.c, ref-filter.c, builtin commands (branch, checkout, worktree), and refs backends, propagating repository parameters where no specific context exists. Series represents significant progress in the long-running `the_repository` removal effort led by René Scharfe, following established patterns without behavior changes. Builds cleanly on previous work. Known limitations remain in reftable backend and ref lock timeout caching requiring future follow-up. Patrick's positive reviews of patches 1/5, 2/5 and 4/5 indicate these parts are technically sound and likely to proceed, with Burak's observation providing useful input for future refinement.
