This is a feature proposal (v5) from Pablo Sabater adding a `--graph-lane-limit` option to constrain the width of `git log --graph` output. The patch addresses terminal readability issues with wide commit graphs by truncating excess lanes while preserving key markers, using '~' to indicate truncated lanes (changed from '.' in v4 to avoid conflict with octopus merge notation).

The implementation introduces a `graph_max_lanes` field in `struct rev_info` (type `int`, where zero/negative means no limit) and modifies the graph rendering logic to cap visible lanes. Commits on the first hidden lane still show their '*' marker, while deeper lanes are fully truncated. The series responds to all prior feedback, including build fixes, style refinements from Johannes Sixt, and error message standardization.

Key improvements in v5 include merged implementation patches (fixing a DEVELOPER=1 build break), added visual examples in the cover letter, and enhanced documentation explaining the horizontal truncation approach (contrasted with gitk's vertical method). The patch touches graph.c, revision.c, and adds tests in t4215-log-skewed-merges.sh.

This appears to be a well-considered solution to a long-standing TODO (from 2008) about column limiting, with thorough test coverage and clear documentation. The author has been responsive to review feedback across multiple iterations, suggesting this is likely to progress toward merging. Future work could refactor lane handling code to make the output more compact when all branches are truncated.
