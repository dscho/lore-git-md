This is a review comment on Luiz Campos's patch adding a 'discard hunk' feature to `git add -p`. D. Ben Knoble raises two thoughtful considerations about the proposed behavior.

First, he notes that the Vim Fugitive client implements hunk discarding with a safety net - it preserves discarded hunks in Git's object database and shows recovery instructions. This suggests the patch might benefit from similar undo protection, since working tree changes not in the index are otherwise unrecoverable after discard.

Second, he asks how this differs from `git restore -p`, implying the functionality may overlap with existing porcelain. This could prompt discussion about whether the feature belongs in `add -p` or should leverage `restore`'s machinery instead. The question touches on Git's command boundary philosophy - whether interactive staging should subsume working tree modification or stay focused on index operations.

The comment doesn't challenge the patch's technical implementation but surfaces important UX and design questions that may influence the feature's final shape. It reflects Git's culture of considering edge cases and user workflows even for seemingly straightforward additions.
