This is a feature proposal for `git add -p` that has drawn significant discussion from the maintainer. Junio C Hamano weighs in against Luiz Campos' RFC to add a 'discard hunk' action, citing fundamental concerns about destructive operations in the staging workflow.

Junio's response is a thoughtful rejection of the core premise, arguing that `git add -p` modifying the working tree would be both conceptually inconsistent and dangerously irreversible. He suggests the current tools (`stash -p` and `restore -p`) already cover the use case, albeit with some workflow friction. His critique centers on data safety - once a hunk is discarded, there's no undo mechanism, which could lead to accidental data loss.

The maintainer instead proposes a more comprehensive vision: a unified interactive command that could navigate between staged, unstaged, and HEAD changes while offering appropriate actions for each context (reset, add, stash, or restore). This would address the workflow pain points while maintaining clear command boundaries and safety.

The email signals this RFC is unlikely to progress in its current form, as Junio's concerns go beyond implementation details to question the fundamental design. However, his alternative suggestion may seed future development - contributors interested in improving interactive workflows now have a maintainer-approved direction to explore. The discussion remains constructive, with Junio acknowledging the real workflow problems while steering toward a solution that fits Git's conceptual model better.
