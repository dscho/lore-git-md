This is Junio C Hamano's review of the final patch in Patrick Steinhardt's reftable portability series, focusing on the header organization. The patch introduced "reftable-system.h" to consolidate system headers, but Junio raises thoughtful questions about the architectural boundaries between platform-specific and platform-neutral code.

Junio notes a conceptual inconsistency in how the series structures the abstraction layers. While reftable/system.c contains platform-specific implementations (like time handling and mmap wrappers), the corresponding reftable/system.h header is meant to be platform-neutral - it defines the abstract interface all platforms must implement. The new reftable-system.h blurs this line by mixing Git-specific includes (compat/posix.h) with what should be generic declarations.

He specifically questions whether REFTABLE_INLINE and zlib-compat.h belong in the platform-neutral system.h or should move to the Git-specific reftable-system.h. This goes to the heart of the series' goal - creating clean separation between reftable's core logic and its system dependencies. Junio's comments suggest the current organization may not fully achieve that separation, as some Git-specific constructs remain in what should be platform-agnostic headers.

The review doesn't block the patch but highlights important design considerations about where to draw boundaries between:
1) The reftable library's portable core
2) Platform abstraction interfaces
3) Git-specific implementations of those interfaces

This feedback will likely lead to a revision that more clearly separates these concerns, possibly by moving more Git-specific details into reftable-system.h while keeping system.h purely abstract. The discussion continues the series' theme of careful system abstraction, now focusing on header organization rather than implementation details.
