Bug report and fix for `git commit -a` crash during unresolved merges with rename detection. Nick Golden originally reported and fixed a reproducible crash occurring when (1) there's an unresolved merge conflict and (2) a tracked file is deleted from working tree, where rename detection would incorrectly pair the deleted file with the unmerged path, causing an "unable to stat" error in `add_files_to_cache()`.

The solution disables rename detection in `add_files_to_cache()` since staging worktree changes doesn't need rename tracking. The v2 patch incorporated review feedback from Junio C Hamano: test improvements replacing Perl with sed, simplifying assertions via `git ls-files` checks, and making output verification more robust against future changes like progress indicators. The regression test reproduces the scenario (creating two identical files, generating merge conflict on one while deleting the other) and verifies correct handling.

In the latest follow-up, Nick Golden confirms all requested test improvements have been implemented and reports having audited similar index refresh paths with no other instances of this issue found. The core solution remains unchanged from v1 - disabling rename detection in `add_files_to_cache()` during unresolved merges. This narrowly targets the crash scenario without broader impacts to merge or rename detection behavior. The test case follows Git's standards and provides clear coverage of the edge case. With Junio's feedback addressed and no further issues identified, this appears to be the final version ready for inclusion.
