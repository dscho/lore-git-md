This is a bugfix patch in the fsmonitor series that completes the Windows pthread emulation layer by implementing `pthread_cond_timedwait()` support. The patch addresses a potential hang scenario where the fsmonitor daemon could block indefinitely waiting for cookie file events on certain container or overlay filesystems where inotify watches succeed but events are never delivered.

The change replaces an infinite `pthread_cond_wait()` with a one-second timeout using `pthread_cond_timedwait()`. If the timeout fires without receiving the expected event, it reports an error and allows the client to proceed with a full scan rather than hanging forever. The implementation includes proper time handling (converting from `timeval` to `timespec`) and error condition checking.

This is part of the mature v12 series that has been production-tested for months. The patch demonstrates careful consideration of edge cases - specifically the scenario where filesystem events might not be delivered despite successful watch setup. The change maintains cross-platform behavior while adding robustness against filesystem quirks.

The implementation uses Git's existing thread utilities and follows the pattern established in earlier patches of the series. The error handling is consistent with the fsmonitor protocol's fallback behavior when events cannot be reliably monitored. This completes the Windows pthread emulation layer that was identified as a remaining technical issue in previous thread summaries.
