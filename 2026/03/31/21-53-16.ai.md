Bugfix for a crash in `git commit -a` during unresolved merges when rename detection is involved.

Nick Golden reports a reproducible crash where `git commit -a` fails with "unable to stat" when two conditions are met: (1) there's an unresolved merge conflict, and (2) a different tracked file has been deleted from the working tree. The issue appears when rename detection pairs the deleted file with the unmerged path, leading to an attempt to stat the deleted path.

The bug manifests in Git 2.53.0 on macOS, and the email includes a detailed reproduction script that creates two identical files, generates a merge conflict on one, deletes the other, then attempts to commit. The expected behavior would be for Git to either stage the deletion while stopping due to the unresolved merge, or refuse the commit entirely - not crash with a stat error.

The patch appears well-motivated and clearly demonstrates a real bug with a minimal test case. The analysis suggests the problem lies in `add_files_to_cache()` during rename detection. This seems like a legitimate edge case that should be fixed, though the patch itself (the actual fix) isn't included in this email - this appears to be just the bug report. The next step would be for someone familiar with the index and merge machinery to propose a solution.
