This is a bugfix for the commit-graph generation number computation, addressing a regression introduced by Patrick Steinhardt's recent commit 024b4c9697. The patch is now in its second version, incorporating feedback from the initial submission.

The core issue involves how commit dates are handled when they exceed 34 bits of precision (dates after year 2514). The commit-graph format stores only 34 bits of commit dates to save space, while the full timestamp_t type has 64 bits. The regression caused generation number calculation errors when commits were parsed both from the commit-graph (with 34-bit dates) and then re-parsed from the object database (with full 64-bit dates).

The v2 patch introduces a new helper function `compute_generation_offset()` that explicitly masks commit dates to 34 bits before calculating generation offsets, ensuring consistent behavior regardless of how the commit was parsed. The patch also adds platform-specific handling for systems where timestamp_t has only 32-bit precision.

A key addition in this version is the test case that verifies the fix works with extremely large dates (year 292,471,210,647) that would trigger the overflow condition. The test uses real-world data from GitLab's test suite, which originally caught this issue. The test demonstrates correct handling when replacing a commit-graph with commits containing these extreme dates.

The patch has already received positive feedback from both Junio C Hamano and Derrick Stolee, indicating it will likely be merged. This is a focused, well-justified fix from a trusted contributor (Patrick Steinhardt) who maintains deep expertise in this area of the codebase. The regression test provides confidence in the solution while maintaining backward compatibility with existing commit-graph files.
