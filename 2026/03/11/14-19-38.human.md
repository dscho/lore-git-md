This is a bugfix for the promisor-remote subsystem that prevents recursive lazy-fetching, which could lead to runaway resource consumption (as evidenced by 276GB of promisor packs being written in 90 minutes in production).

The core issue occurs when `fetch_objects()` spawns a child `git fetch` for lazy fetching, and that child's `index-pack` encounters a REF_DELTA against a missing base object in a blob:none partial clone. This can recursively call back into `fetch_objects()`, creating an unbounded loop. While well-behaved servers shouldn't send such deltas (with negotiationAlgorithm=noop), GitHub's production servers have been observed to do so.

The fix propagates `GIT_NO_LAZY_FETCH=1` into the child fetch's environment, preventing recursion while still allowing the initial lazy fetch. The v3 patch strengthens test coverage by demonstrating the actual failure mode with HTTP-based tests that simulate GitHub's server behavior, rather than just testing environment variable propagation.

The patch has evolved through review, with Patrick Steinhardt initially questioning whether this represented a server protocol violation, but ultimately acknowledging the value of client-side protection regardless. The solution is technically sound and has Junio's approval from earlier versions. The discussion suggests this may warrant follow-up regarding server protocol behavior, but the immediate client fix stands on its own merits.

The patch is well-constructed with a clear commit message explaining both the technical solution and production impact, plus comprehensive tests that verify the fix works against the actual problematic scenario. It's a focused change (just 7 lines of code) that addresses a real-world performance and stability issue in partial clone scenarios.
