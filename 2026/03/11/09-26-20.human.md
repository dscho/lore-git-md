This is a discussion about edge case behavior in the new `git history split` command, part of Patrick Steinhardt's ongoing `git-history` command family effort.

D. Ben Knoble had suggested making the command silently do nothing when users select either all or no hunks (which would result in an empty commit), rather than erroring out. Patrick responds that this might make the interface more confusing, since selecting all or no hunks doesn't actually split the commit - it would just leave you with a single unchanged commit. He suggests that creating an empty commit this way would likely be accidental in most cases, but leaves the door open to adding an `--allow-empty` option later if valid use cases emerge.

The exchange is cordial and constructive, with both contributors considering the user experience implications of different edge case behaviors. This is a typical refinement discussion that often happens after the core functionality of a new feature has been established. The thread shows the project's attention to detail in designing intuitive command behavior, even for cases that might seem obscure at first glance.
