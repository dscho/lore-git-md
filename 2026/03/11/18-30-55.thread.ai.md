Core problem or goal: During a range cherry-pick operation that hits a conflict, users currently must inspect `.git/CHERRY_PICK_HEAD` and run `git show` to see which commit's changes are being applied. The proposal aims to add a dedicated flag for this, but Phillip Wood notes the existing `git show CHERRY_PICK_HEAD` workflow already provides this functionality with more formatting flexibility.

Current status: Discussion stage. Phillip has raised concerns about whether a new flag is necessary given existing capabilities. No implementation or version history yet.

Key technical details: Would modify `builtin/cherry-pick.c` to add `--show-current-patch` flag, similar to rebase's implementation. However, Phillip points out users can already get equivalent information through `git show CHERRY_PICK_HEAD`, which supports all standard diff formatting options. The discussion highlights a design tension between specialized porcelain and composable plumbing.

Open questions and loose ends: Whether the feature justifies a new flag versus improved documentation of existing capabilities. Phillip suggests better documenting `CHERRY_PICK_HEAD`/`REVERT_HEAD`/`REBASE_HEAD` usage might be preferable. No technical implementation concerns raised yet.

Participant positions: Phillip Wood questions the need for a new flag, arguing the existing `CHERRY_PICK_HEAD` mechanism provides equivalent functionality with more flexibility. His position favors improving documentation over adding new porcelain. Florian Best's original motivation (discoverability) remains valid but may be addressable through other means.

Related work: Directly inspired by `git rebase --show-current-patch`, but the discussion reveals this may have been an unnecessary addition given `REBASE_HEAD` already existed.
