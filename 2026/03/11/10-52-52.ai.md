Bugfix for the promisor-remote subsystem addressing a lazy-fetch recursion issue that can cause runaway resource consumption. Patrick Steinhardt is questioning whether the root cause might lie with the server sending invalid packfiles rather than being purely a client-side issue.

The patch from Paul Tarjan aims to prevent recursive lazy-fetching by propagating `GIT_NO_LAZY_FETCH=1` into child fetch processes spawned by `fetch_objects()`. This addresses a production issue where 276GB of promisor packs were written in 90 minutes due to unbounded recursion when resolving REF_DELTA bases against missing objects.

Patrick raises several technical concerns in his response. He questions whether this is a theoretical or practical issue, noting that well-behaved servers shouldn't send REF_DELTA objects to nonexistent objects during backfill fetches. He also asks for clarification about the "depth-2 fetch" comment in the commit message and suggests the test should demonstrate the actual failure mode rather than just checking for the environment variable.

The discussion now centers on whether the client-side protection is addressing a server-side protocol violation. Patrick wants to understand if the server is using standard git-upload-pack or a custom implementation that might be generating invalid packfiles. While not opposed to client-side hardening, he's probing for deeper understanding of the failure scenario before accepting the proposed solution.

This follows up on Paul's v2 patch which had already incorporated Junio's feedback about test organization. The technical solution remains unchanged, but Patrick's questions suggest the justification may need refinement to clearly separate client hardening from potential server bugs.
