This is a clarification request from the maintainer regarding a bugfix targeting zombie process accumulation in containerized Git operations.

Junio C Hamano seeks to reconcile an apparent contradiction in the patch's motivation. The original commit message framed this as Git running as PID 1 in containers, but Andrew Au's follow-up describes a different scenario where a long-running service (not Git itself) runs as PID 1 and spawns Git processes. Junio questions whether the responsibility for child process reaping should lie with Git or with the parent service in this architecture.

The thread has previously covered the technical solution (atexit handlers for transport helpers and connection processes) and received detailed review from Jeff King about deadlock risks and alternative approaches using existing run-command infrastructure. This email shifts focus to the deployment context, suggesting the problem statement may need refinement to match the actual use case.

Key open questions raised:
- Is Git truly PID 1 in the problematic deployments, or is it a child of another service?
- If the latter, should the service (rather than Git) handle orphan cleanup?
- Does this affect the proposed solution's scope or justification?

The exchange highlights Git's role in container ecosystems and the need for precise problem descriptions when fixing edge cases in process lifecycle management. Junio's query suggests the patch may need updates to either the implementation or the commit message to properly address the real-world deployment scenario.
