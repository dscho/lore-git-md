The feature would help users understand which specific commit caused a conflict during range cherry-pick operations. Currently, users must manually inspect `.git/CHERRY_PICK_HEAD` and run `git show`, which is less discoverable than having a dedicated flag.

The proposed behavior would show the patch being applied when conflicts occur, providing immediate visibility into the problematic changes. The flag would error cleanly when no cherry-pick operation is active. The motivation is clear - this would significantly improve the debugging experience for range cherry-picks by showing exactly which commit's changes are conflicting. The implementation appears straightforward since it can leverage existing mechanisms from the rebase command's similar feature.

This seems like a well-justified quality-of-life improvement that would bring cherry-pick's functionality more in line with rebase's existing capabilities. The change would be particularly helpful for users dealing with complex range cherry-picks where conflicts can be difficult to track down.
