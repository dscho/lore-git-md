This is a discussion about refactoring the experimental `git replay` command's interface from mutually-exclusive options to subcommands. Justin Tobler responds to Toon Claes's RFC patch proposing to replace `--onto`, `--advance`, and `--revert` options with `rebase`, `pick`, and `revert` subcommands respectively. The new design introduces a consistent `--ref` option across subcommands to specify which reference to modify, while maintaining backward compatibility with `--onto` for the rebase case.

Justin raises several concerns about the proposal: the rebase subcommand still requiring `--onto` makes it unclear what exactly is being replaced, the subcommand interface feels awkward with required options, and the change breaks backward compatibility (though this may be acceptable for an experimental command). He suggests considering positional arguments instead of required options for a more intuitive interface.

The discussion touches on key files (`builtin/replay.c`, documentation, tests) and the experimental nature of `git replay` as a lower-level alternative to rebase that works with bare repos. The thread shows early design feedback on an interface change that would affect how users interact with this experimental command.
