This is part of the ongoing parallel hook execution feature series (v3 5/9), which introduces configurable parallel execution of Git hooks. The patch specifically marks several hooks as non-parallelizable by default, overriding any parallel execution settings.

Emily Shaffer identifies seven hooks that must always run sequentially due to inherent safety or ordering requirements: `applypatch-msg`, `pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`, `post-checkout`, and `push-to-checkout`. The patch updates each hook's call site to use `RUN_HOOKS_OPT_INIT_FORCE_SERIAL`, which enforces serial execution regardless of global or per-hook parallelization settings.

The changes touch multiple builtin commands (`am`, `checkout`, `clone`, `receive-pack`, `worktree`, and general commit handling) to ensure these critical hooks maintain their existing behavior. Documentation is updated to clarify that these hooks bypass parallel execution controls. A new test case verifies that `hook.jobs=2` is properly ignored for force-serial hooks like `pre-commit`.

This patch represents a key safety mechanism in the parallel hooks infrastructure, ensuring that hooks with strict ordering or side effect requirements cannot be accidentally parallelized. The implementation is thorough, touching all relevant hook call sites while maintaining the existing hook API contract. The test coverage demonstrates the enforcement behavior works as intended.
