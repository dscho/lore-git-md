This is part 4/9 of a feature series introducing parallel hook execution, building on Adrian Ratiu's prior configurable hooks work. The patch implements the core parallel execution capability while maintaining strict opt-in safety.

The key changes:
- Removes the hardcoded `jobs=1` in `run_hooks_parallel()`, allowing hooks to run concurrently when configured
- Introduces `hook.<name>.parallel` config to mark individual hooks as safe for parallel execution
- Adds logic in `get_hook_jobs()` to determine the effective job count based on:
  - Explicit `-j/--jobs` CLI option
  - `hook.jobs` config (with fallback to serial if unset)
  - Whether all hooks in the event are marked parallel
  - Output stream requirements (serial if stdout/stderr separation needed)
- Provides `RUN_HOOKS_OPT_INIT_FORCE_SERIAL` for hooks that must never parallelize
- Includes comprehensive tests verifying serial/parallel behavior under various configs

The implementation carefully maintains backward compatibility - hooks remain serial by default, and any non-parallel hook in an event forces serial execution for all. The tests use a clever sentinel/detector pattern to validate actual parallel vs serial execution timing.

This is a well-structured patch with thorough documentation and testing. It cleanly separates the parallel execution plumbing from the policy decisions (which come in subsequent patches). The opt-in approach addresses safety concerns while providing the infrastructure needed for performance improvements where explicitly configured.
