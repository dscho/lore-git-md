This is a feature proposal for adding an untrusted caching proxy mechanism to Git's remote fetching functionality. The author, Skye Soss, suggests a model where clients would:

1. Connect directly to the real remote for metadata operations
2. Attempt to fetch objects from a read-only cache first
3. Validate all cached objects to prevent spoofing
4. Fall back to the real remote if the cache is unavailable or missing objects

The motivation is to enable network-level caching (similar to apt's DNS-SD caching) without requiring the full trust model of traditional HTTP/SSH proxies that rewrite URLs. This would allow organizations to improve clone performance while maintaining security through cryptographic validation of cached objects.

The proposal acknowledges that Git wasn't designed as a CDN but recognizes the reality that it's often used that way. The key technical question posed is whether Git's internals could support this caching model without major complications.

This appears to be an initial RFC rather than a concrete implementation, as there are no patch files or detailed design attached. The concept touches several core subsystems: remote fetching, object transfer protocols, and object verification. The security implications would need careful consideration, particularly around how to prevent cache poisoning while maintaining the untrusted nature of the cache.
