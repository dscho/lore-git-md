This thread addresses a bug in Git's option parsing behavior where `git rev-parse --parseopt` was incorrectly exiting with status 129 (error) when encountering help flags (`--help`/`-h`), contrary to Git's standard convention of exiting with status 0 for help requests. The issue was identified by brian m. carlson, with Jeff King (Peff) providing historical research showing this behavior was an accidental inheritance from 2007 code rather than an intentional design choice.

After initial implementation caused a regression in `git instaweb -h` (which now exits 0 outside repositories where it previously exited 129), Junio Hamano flagged the issue during integration testing. The discussion has now reached consensus that this should be treated as a bug fix rather than waiting for Git 3.0, as the change aligns with Git's standard help behavior and any scripts depending on the current behavior likely represent poor design. Peff's latest response confirms the technical analysis is complete and the path forward is clear, moving this from discussion to implementation.

The fix will standardize exit codes across all commands using Git's parse-options infrastructure, with updates to `parse-options.c` and appropriate documentation in the release notes. While the change affects many commands, the impact is expected to be positive, as it resolves an inconsistency that has existed since 2007. The regression in `git instaweb` was the most visible symptom of this underlying issue, which the fix will address system-wide.
