This thread began as a bug fix to standardize `--help` exit codes across Git's parse-options API, ensuring they return 0 (Unix convention) instead of 129 (historical accident). The four-patch series, authored by brian m. carlson and reviewed by Jeff King (Peff) and Junio C Hamano, was fully merged as a regular bugfix before Git 3.0. The fix addressed a long-standing inconsistency but introduced two behavioral trade-offs, now documented: scripts using `git rev-parse --parseopt` in shell-eval mode might process nonsense output if `--help` is accidentally passed, and "hacky" scripts that wrap Git commands (e.g., `git log --my-options "$@"`) could feed garbage to downstream logic when passed `--help`, as they now exit 0 instead of failing fast.

Post-merge, three substantive issues were identified. The most significant—a flawed `SVN` test prerequisite logic and shell-quoting bug—was resolved in principle after Junio confirmed the root cause: Perl's `gt` operator treats dotted version strings as ASCII sequences, causing the check to fail silently. brian m. carlson will simplify the prerequisite by removing the version check entirely. A refactoring gap in `usage_with_options_internal()` remains open but is non-urgent, and Peff documented the behavioral trade-offs for the record. Junio's latest follow-up underscores the real-world risk of the wrapped-commands scenario, though he accepts it as a necessary trade-off. The thread is now effectively closed, with the merged series standing as-is.
