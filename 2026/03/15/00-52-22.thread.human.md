This thread is about a long-standing inconsistency in Git's parse-options API, where help flags (`--help`/`-h`) incorrectly exited with status 129 (error) instead of 0 (success). The issue was fully resolved in a four-patch series by brian m. carlson, which standardized help-exit behavior across all Git commands using the parse-options infrastructure. The series was merged as a regular bugfix ahead of Git 3.0, with all identified issues—including a logic flaw in test prerequisites, a shell-quoting bug, and a refactoring gap in `usage_with_options_internal()`—now resolved.

The core fix involved introducing a new return code (`PARSE_OPT_HELP_ERROR`) to distinguish between user-requested help and error-triggered help, updating 37 test files and three built-in commands (`git blame`, `git shortlog`, `git update-index`) to expect exit code 0 for `--help`, and ensuring `git rev-parse --parseopt` in shell-eval mode exits successfully. Junio C Hamano, the maintainer, explicitly approved the refactoring logic and merged the series. Jeff King (Peff) contributed key insights, including identifying the shell-quoting bug and refactoring gap.

The thread also includes a post-merge cleanup patch, now approved by Junio, which tidies up the `SVN` test prerequisite to avoid false negatives. This patch replaces a problematic Perl version check with a minimal script that tests only for module availability, aligning with the project’s test infrastructure. With this final patch, the entire effort is complete, and no further discussion is expected. The regression in `git instaweb -h` is fixed, and all parse-options users now follow the Unix convention of exiting 0 for help requests.
