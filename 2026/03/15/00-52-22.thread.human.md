This thread began as a bug report about `git rev-parse --parseopt` exiting with status 129 (error) for help requests (`-h`/`--help`), which violated Git's standard help-exit convention. brian m. carlson implemented a fix that made shell-eval mode exit 0 for help requests while keeping error exits in direct mode, but this caused a regression in `git instaweb -h` behavior that Junio caught during integration testing.

Jeff King (Peff) has since revealed this is a much broader issue affecting all commands using Git's parse-options machinery. His historical investigation traces the 129 exit code back to 2007, where it was used for both error cases showing help and explicit help requests - suggesting the current behavior may have been an accidental inheritance rather than intentional design. The discussion has now moved beyond the initial `instaweb` regression to consider fundamental questions about Git's option parsing behavior.

The key open questions are whether to:
1) Maintain the historical 129 exit code for help requests (which may have been unintentional)
2) Standardize on exit 0 across all parse-options users
3) Implement a more nuanced approach separating error-triggered help from explicit help requests

brian m. carlson is preparing a revised solution that will need to consider these architectural implications. The thread demonstrates how seemingly simple fixes to core infrastructure can uncover deeper design questions with system-wide impact.
