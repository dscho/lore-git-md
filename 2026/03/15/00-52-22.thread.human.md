This thread examines how Git should handle exit codes when users request help (via `-h` or `--help`). The discussion began when brian m. carlson noticed that `git rev-parse --parseopt` was exiting with status 129 (error) for help requests, contrary to Git's usual convention of exiting 0. His initial fix was merged but caused a regression in `git instaweb`, revealing the issue affects all commands using Git's parse-options infrastructure.

Jeff King (Peff) provided crucial historical context, tracing the 129 exit code to 2007 code where error cases and help requests shared the same status - likely an implementation artifact rather than intentional design. The discussion then broadened to consider whether to maintain this legacy behavior or standardize help exits system-wide.

In the latest development, maintainer Junio C Hamano has weighed in clearly supporting the principle that help requests should exit with status 0, calling this "the general idea". While acknowledging this would be a behavioral change affecting many commands, he suggests implementing it at the Git 3.0 boundary if no compelling historical rationale for the current behavior emerges. This aligns with Peff's technical analysis while providing a path forward that considers compatibility implications.

The thread now awaits brian m. carlson's revised proposal, which will need to address both the technical implementation (possibly separating error-triggered help from explicit requests) and the timing considerations raised by Junio. The consensus appears to be moving toward standardizing on exit 0 for help requests across Git, with details about scope and rollout timing being the remaining open questions.
