Thread identity: Bug report and proposal to change `git rev-parse --parseopt` exit code behavior for help flags (`--help`/`-h`), authored by brian m. carlson, with Jeff King (Peff) now participating in the discussion.

Core problem: `rev-parse --parseopt` currently exits with status 129 (error) when help flags are used, contrary to Git's standard help-exit behavior. The command's shell-eval mode presents additional complexity since it outputs a here-doc with help text rather than directly exiting.

Current status: Consensus forming around changing the behavior to exit successfully for help requests. Peff has proposed a technical solution that would append an `exit 0` to the here-doc output in shell-eval mode, maintaining backward compatibility while fixing the core issue.

Key technical details: Change would modify both `builtin/rev-parse.c` (exit code behavior) and `parse-options.c` (shell-eval output). The shell-eval mode would be enhanced to explicitly exit 0 after displaying help text, while direct invocation would simply return 0. This preserves the existing contract with scripts while fixing the UX inconsistency.

Open questions: Implementation approach now largely resolved (Peff's solution addresses both direct and eval cases). Remaining question is whether to include a compatibility flag for scripts that might depend on status 129 - though this seems unlikely given the nature of help requests.

Participant positions: brian m. carlson identified the issue and proposed initial fix direction. Peff has contributed a more complete technical solution that handles the shell-eval case properly. Both agree on the principle that help should exit successfully. No objections raised yet to the proposed approach.

Related work: Aligns with Git's standard help behavior. Similar to other consistency improvements in option parsing, though the shell-eval aspect makes this case unique. The solution draws on how other Git commands handle help output in shell contexts.
