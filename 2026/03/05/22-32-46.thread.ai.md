RFC series adding remote group support to `git push`, mirroring existing `git fetch` functionality. Authored by Usman Akinyemi. Core idea: enable pushing to all remotes in a configured group (defined via `remotes.<name>` config) with single command like `git push all-remotes`.

Implementation in two parts:
1. [PATCH 1/2] Refactored group-handling code from fetch.c to remote.c for reuse
   - Moved `get_remote_group()`, `add_remote_or_group()`, and `remote_group_data` struct
   - Updated remote.h declarations
   - Purely mechanical code movement with no functional changes
   - Suggested-by: Junio Hamano
   - Maintainer review: Junio confirms naming/scoping appropriate
   - Author removed `UNUSED` macro from headers per feedback

2. [PATCH 2/2] Implements push-to-group functionality
   - Processes each remote in group sequentially
   - Rebuilds refspec lists per-remote to respect `remote.<name>.push`
   - Isolates mirror/force-push flags per remote
   - Accumulates exit codes via bitwise OR (continues after failures)
   - Now unifies single-remote and group handling via remote_group structure
   - Preserves existing single-remote behavior
   - Suggested-by: Junio Hamano
   - Includes test coverage in t5566-push-group.sh (renumbered to t5528 per Junio)

Design decisions resolved by maintainer Junio Hamano:
1. `push.default` behavior: all modes (simple, matching, etc) work with groups, each remote follows its own configuration exactly as if pushed individually. Documentation should not over-specify simple mode.
2. `--force-with-lease` semantics: same commit expectation applies uniformly when specified; when unspecified, each remote uses its own remote-tracking branch state.
3. Core principle established that group push should behave identically to sequential individual pushes (`git push G` == `git push r1; git push r2; ...`).
4. Failure handling: continues pushing to remaining remotes after failure, with final exit code being bitwise OR of individual results.
