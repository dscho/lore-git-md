This is a maintainer comment on the proposed `pre-add` hook feature. Junio C Hamano responds to Phillip Wood's concerns about the hook's limitations, agreeing that the current design has significant usability drawbacks. The key issue is that the hook only sees changes from the current `git add` invocation, not all staged changes since the last commit. This forces users to either run the hook repeatedly or duplicate checks in a `pre-commit` hook. Junio expresses skepticism about the feature's overall value given these constraints.

The exchange reveals fundamental questions about the hook's purpose - while it aims to validate changes during staging, the implementation may not provide enough benefit over existing `pre-commit` hooks to justify its complexity. Junio's closing remark ("I am not sure of the value of the proposed hook") suggests this may be a blocking concern for merging the feature, despite the technical implementation being sound in previous iterations. The thread appears to be at a decision point about whether the concept itself is worth pursuing given the UX tradeoffs.
