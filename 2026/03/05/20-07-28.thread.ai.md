Thread identity: Documentation clarification request about `git stash` pathspec behavior, initiated by Aron Sigfridsson, with follow-up from Junio C Hamano.

Core problem: The gitglossary advises checking individual commands for whether pathspecs are interpreted relative to current directory or toplevel, but `git stash` documentation lacks this specification. Additionally, there are inconsistencies between subcommand help text and actual pathspec support, particularly:
- `git stash push` interprets pathspecs relative to current directory (matching `git status` behavior)
- `push` is the only stash subcommand supporting pathspecs, despite `list` showing pathspec-like syntax in its help text

Current status: Junio C Hamano has weighed in on the broader implications, noting that modern Git with pathspec magics (`:/`, `:(top)`) has reduced the need for top-level-relative pathspec requirements. He suggests this as an opportunity for community documentation standardization work.

Key technical details:
- Confirmed `git stash push` pathspec interpretation is relative to current directory
- Only `push` subcommand accepts pathspecs (help text for `list` is misleading)
- Workaround for pathspec-based stash listing remains `git log stash` with pathspecs
- Modern pathspec magics provide flexible path specification regardless of working directory

Open questions:
- Should `git stash` man page be updated to:
  - Explicitly document pathspec interpretation rules for `push`
  - Correct `list` subcommand help text
  - Clarify which subcommands support pathspecs
- Broader opportunity: Audit commands for remaining top-level-relative pathspec requirements and standardize documentation
