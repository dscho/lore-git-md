This is a bug report about a memory leak in the clone operation. Jacob Keller reports that when cloning a repository, AddressSanitizer detects a 27KB memory leak originating from `git_mmap` in `compat/mmap.c`, which gets called through the chain `check_packed_git_idx` -> `open_pack_index` -> `find_pack_entry_one` during the connectivity check phase of cloning.

The leak appears consistently on the current `next` branch (specifically 7842e34a6654). The stack trace shows the memory was allocated for mmap'ing a pack index but wasn't properly freed. The reporter hasn't yet identified the root cause but has provided a clear reproduction case via the sanitizer output. This looks like a legitimate resource management issue that would affect all users, though the impact is limited to extra memory consumption during clone operations rather than corruption or incorrect behavior.

The leak occurs in core packfile handling code, touching areas that have seen recent activity from contributors like Patrick Steinhardt and Taylor Blau. Given the clear reproduction and narrow scope, this seems like a good candidate for a focused fix - likely needing someone familiar with the pack index mmap lifecycle to audit when and how these mappings should be released. The report doesn't include a proposed fix, so this will need investigation from someone with deeper knowledge of this subsystem.
