This is a documentation review in the ongoing "pre-add hook" feature discussion. Phillip Wood raises several concerns about the design and documentation of the proposed `pre-add` hook mechanism.

Phillip suggests reorganizing the documentation to match `git-commit`'s structure with a dedicated HOOKS section, and clarifies that the hook rejects changes rather than the command itself. He questions the UX implications of bypassing the hook in dry-run mode, arguing this could mislead users when their actual add would be rejected. He also proposes extending the hook to cover `git commit` operations that stage changes, noting the current design requires duplicate validation in both `pre-add` and `pre-commit` hooks.

The review identifies several technical documentation issues: the term "lockfile" is misleading (it's actually a second index file), the read-only nature of the files should be enforced to prevent hook authors from modifying them, and the scope of changes shown in the proposed index state needs clarification. Phillip also notes the documentation should be more precise about which commit operations do and don't invoke the hook.

While this is framed as documentation feedback, Phillip's core concern is the hook's design coherence - particularly around when it runs and how it validates changes. He suggests the current approach may lead to inconsistent user experiences and redundant validation logic. These are substantive design questions that go beyond wording tweaks, indicating the feature may need further refinement before finalization.
