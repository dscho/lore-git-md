Here's the updated human-readable thread summary:

This thread began with a feature request from Norbert Kiesel for `git worktree list --created` to sort worktrees by creation timestamp, particularly useful for users managing 20+ worktrees. The discussion took a turn when Junio Hamano clarified that Git doesn't currently track worktree creation times at all, shifting the conversation from a simple sorting flag to broader questions about worktree metadata storage.

Junio suggested a more general solution modeled after `.git/description` files - where each worktree could have its own metadata file in `.git/worktrees/<id>/description`. This would provide a framework for various metadata needs rather than just timestamps. Filesystem-based timestamp approaches were effectively ruled out as unreliable since they change when worktrees are moved.

Norbert has now shared a Zsh script workaround using filesystem timestamps (with acknowledged limitations) that demonstrates the practical need while reinforcing why a core Git solution would be better. The script parses `git worktree list --porcelain` output and sorts by filesystem creation time, serving as both a temporary solution and proof-of-concept.

The thread now stands at a design crossroads: whether and how to implement persistent worktree metadata in Git's core. Junio's preference for a general metadata file approach seems clear, but the details of implementation - file format, location, and compatibility - remain open questions. The original contributors could potentially take up the challenge of implementing this more general system, which might eventually support creation timestamps as one of many possible fields.
