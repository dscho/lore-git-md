This is version 4 of a feature patch introducing a `pre-add` hook for Git. The hook allows inspecting and potentially rejecting staged changes before they are committed to the index. The implementation is now complete with all technical concerns addressed from previous reviews, focusing on documentation refinements and code cleanup in this iteration.

The hook receives two arguments: the path to the current index file and the path to a lockfile containing the proposed staged changes. It runs after Git computes the new index state but before writing it to disk, allowing validation of the entire staged state (not just the current `git add` operation). The hook can reject changes by exiting non-zero, which leaves the original index unchanged.

Key technical details:
- Uses a new `SKIP_INDEX_CHANGE_HOOK` flag to properly sequence the `post-index-change` hook
- Handles mixed-result adds (tracked changes + ignored files) correctly
- Includes comprehensive test coverage in t/t3706-pre-add-hook.sh with example use cases
- Documents limitations: cannot filter individual paths in multi-file adds, and skips interactive/patch/dry-run modes
- Maintains the original index state on hook failure

The patch has seen significant review engagement, with Junio Hamano confirming the technical implementation is sound in v3. Phillip Wood raised concerns about the argument scope showing all staged changes rather than just the current add operation, and the UX impact of bypassed modes requiring duplicate validation in pre-commit hooks. These concerns remain acknowledged but are not blocking the patch's progress.

The documentation now clearly states the hook's capabilities and limitations, including removed implementation details about stdin handling and improved error messages. Example use cases demonstrate practical applications like blocking `.env` files or secret keys in content.
