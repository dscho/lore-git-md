This thread addressed a report about `git describe --dirty` incorrectly showing a repository as dirty when run from outside the repository with `--git-dir` but without `--work-tree`. Junio C Hamano and Patrick Steinhardt clarified this is expected behavior - when only `--git-dir` is specified, Git assumes the current directory is the working tree root, which leads to incorrect dirty state detection from the wrong location. This matches Git's standard repository discovery behavior for all working-tree-aware commands.

Two correct approaches exist: either specify both `--git-dir` and `--work-tree`, or use the simpler `-C` option to change to the repository directory first. Patrick noted `-C` (added in 2013) is generally preferable to explicit path specifications. The original reporter, Thomas Braun, followed up to confirm he now understands this behavior and that his original 2014 usage of `--git-dir` predated widespread adoption of `-C`. The thread concludes with consensus that the behavior is correct and properly documented, with no code changes needed. It serves as a useful case study in how Git's repository discovery rules interact with working-tree-sensitive operations.
