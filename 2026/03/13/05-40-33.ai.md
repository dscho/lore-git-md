This is a feature addition to the `git replay` command, introducing a `--revert` mode for server-side history rewriting. The patch series is now at v4, with Siddharth Asthana addressing all substantive feedback from previous rounds of review.

The changes enable `git replay` to reverse commits directly on bare repositories, which is particularly useful for GitLab's Gitaly service where server-side operations on bare repos are common. The implementation follows the same approach as `sequencer.c`, treating reverts as merges with swapped arguments (base=commit, ours=current, theirs=parent) to effectively reverse the diff direction.

Key technical aspects of v4 include:
- Complete consolidation of message formatting logic into `sequencer_format_revert_message()` per Phillip Wood's suggestion, moving all formatting (including commit references) into a single helper function
- Updated `refer_to_commit()` to take explicit repository and boolean parameters rather than relying on `replay_opts`
- Reverts now processed in chronological (creation) order (newest-first) to match `git revert` behavior and reduce conflicts
- Empty revert commits are now dropped by default, aligning with `git cherry-pick` behavior
- Improved documentation showing cross-branch revert scenario and restoring the `merge-tree` NOTE
- More precise error messages for incompatible options
- Test coverage expanded to verify newest-first ordering and message formatting

The implementation has been thoroughly reviewed by Phillip Wood, Patrick Steinhardt, and Junio Hamano, with all technical points from prior discussion addressed. The higher-level interface design discussion (flags vs subcommands) continues but is being deferred to avoid scope creep in this series.
