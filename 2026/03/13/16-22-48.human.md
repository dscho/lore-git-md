This is a design discussion about refactoring the experimental `git replay` command's interface. Toon Claes responds to Justin Tobler's feedback on his RFC proposing to replace `git replay`'s mutually-exclusive options (`--onto`, `--advance`, `--revert`) with subcommands (`rebase`, `pick`, `revert`).

Toon provides more detailed examples showing the current asymmetry between how `--onto` (which rebases commits) and `--advance`/`--revert` (which update branches) work. His key motivation is to make the command's behavior more consistent and intuitive, particularly around which refs get updated.

The discussion reveals several open questions about the interface design: whether subcommands should have required options (currently unusual in Git), whether positional arguments might work better, and how to handle backward compatibility for this experimental command. Toon considers alternative designs, including making both `--onto` and `--ref` required or combining `--advance` and `--revert` into a single option.

This is an important design discussion for a low-level plumbing command that may eventually become more widely used. The exchange shows thoughtful consideration of Git's command-line interface conventions while trying to improve consistency. The experimental nature of `git replay` gives some flexibility to make breaking changes, but the discussion suggests the design needs more iteration before settling on an approach.
