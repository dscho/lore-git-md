This is a clarification from the maintainer about the behavior of `git describe --dirty` when used with `--git-dir` outside the repository. Junio C Hamano explains that the reported behavior is actually working as intended - when only `--git-dir` is specified, Git assumes the current directory is the working tree root, which leads to incorrect dirty state detection when run from outside the repository.

The key insight is that `--git-dir` alone implies the current directory should be treated as the working tree, so running from outside the repo while only specifying `--git-dir` will naturally show the repository as dirty (since all files appear modified from that perspective). The correct solution is to also specify `--work-tree` to point to the actual working tree location.

Junio suggests this isn't a bug but rather a documentation issue - the interaction between `--git-dir` and working tree assumptions could be better explained in the man pages. He hints this might be a good area for documentation improvement rather than a code change. The response effectively closes the original bug report by explaining the expected behavior, though leaves the door open for potential documentation patches to make this clearer for future users.
