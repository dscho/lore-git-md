Thread identity: Bug report about `git describe --dirty` behavior when used with `--git-dir` outside repository, reported by Thomas Braun, clarified by Junio C Hamano.

Core problem: Reported behavior where `git describe --dirty` incorrectly reports repository as dirty when run from outside repository with `--git-dir` but without `--work-tree` is actually expected behavior. The command assumes current directory is working tree root when only `--git-dir` is specified, leading to incorrect dirty state detection from wrong location.

Current status: Not a bug - working as designed. The workaround (specifying both `--git-dir` and `--work-tree`) is the correct solution. Original issue stems from commit 2ed5c8e174 ("describe: setup working tree for --dirty", 2019-02-03) which properly implemented this behavior.

Key technical details: When only `--git-dir` is provided, Git's repository discovery defaults current directory as working tree root. This is standard behavior affecting all working-tree-aware commands, not specific to `describe`. The dirty check in `builtin/describe.c` works correctly given this context - the "incorrect" report occurs because it's checking the wrong working tree.

Open questions: Whether documentation about `--git-dir` and `--work-tree` behavior could be improved to make this interaction clearer, particularly for commands like `describe --dirty` that check working tree state.

Participant positions: Thomas Braun initially reported as bug. Junio C Hamano clarified this is expected behavior and closed the issue, suggesting documentation improvements as potential follow-up. Maintainer's position is authoritative here.
