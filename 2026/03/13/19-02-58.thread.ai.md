Thread identity: Bug report and discussion about `git describe --dirty` behavior when used with `--git-dir` outside repository, reported by Thomas Braun, clarified by Junio C Hamano and Patrick Steinhardt.

Core problem: The reported behavior where `git describe --dirty` incorrectly reports repository as dirty when run from outside repository with `--git-dir` but without `--work-tree` is expected behavior. The command assumes current directory is working tree root when only `--git-dir` is specified, leading to incorrect dirty state detection from wrong location. This is standard repository discovery behavior affecting all working-tree-aware commands.

Current status: Not a bug - working as designed since commit 2ed5c8e174 ("describe: setup working tree for --dirty", 2019-02-03). Two correct solutions exist: 1) specifying both `--git-dir` and `--work-tree`, or 2) using `-C` to change to repository directory before operation. Patrick Steinhardt notes `-C` is generally simpler than explicit `--git-dir/--work-tree` specification.

Key technical details: The dirty check in `builtin/describe.c` works correctly given its context - it checks the working tree it believes is correct (current directory when only `--git-dir` specified). This behavior matches Git's standard repository discovery where `--git-dir` alone implies current directory as worktree root. Commands checking working tree state need proper context via either being run from correct directory, using `-C`, or explicit `--git-dir/--work-tree` pair.

Open questions: Whether to improve documentation about `--git-dir`, `--work-tree` and `-C` behavior, particularly for working-tree-sensitive commands like `describe --dirty`. The thread appears to be converging on documentation improvements rather than code changes.

Participant positions: Thomas Braun initially reported as bug. Junio C Hamano authoritatively clarified this is expected behavior and closed the issue.
