This is a feature patch series for a `pre-add` hook mechanism, now faces fundamental questions about its design and value proposition despite being technically complete. 

Phillip Wood raises several key concerns in this response to Chandra's v5 patch. He argues that the current `--dry-run` behavior (skipping hooks) inherited from `pre-commit` is suboptimal, suggesting it should instead follow `pre-push`'s model of running hooks during dry runs. He also questions whether the hook provides enough value in its current limited scope (only seeing changes from the current `git add` rather than all staged changes), suggesting it might need to cover `git commit` staging as well to be truly useful.

The discussion reveals deeper design tensions: whether to enforce read-only access to the index files passed to prevent misuse, how to handle interactive/patch modes (currently excluded), and whether the rapid revision pace (v4 to v5 in minutes) indicates insufficient consideration of these fundamental questions. While the implementation appears technically sound with Windows support, config integration, and comprehensive tests, the maintainer skepticism suggests the series may need significant redesign or reconsideration of whether to proceed at all.

The author remains committed to the change but acknowledges the need for deeper design evaluation. The thread has shifted from implementation details to questioning whether the core concept provides enough value in its current form, with suggestions to instead enhance existing `pre-commit` hooks. This represents a potential pivot point for the feature's direction.
