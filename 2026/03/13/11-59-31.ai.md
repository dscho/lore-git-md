This is a code review response in the ongoing thread about the new `git maintenance list` command. Pablo Sabater suggests a refactoring to reduce code repetition in the config file handling logic.

The review points out that the current implementation has nearly identical branches for handling both custom config files (via `--config-file`) and the default global config case. The key observation is that `global_config_file` can be safely freed in both cases since it's either NULL or allocated by `git_global_config()`. 

Pablo proposes consolidating the common configset initialization and query logic by first normalizing the `config_file` pointer (either using the provided custom file or getting the global one), then handling the config operations in a single shared block. This would eliminate the duplicated code while maintaining the same behavior.

The suggested change is purely a refactoring - it doesn't modify the command's functionality or interface, just makes the implementation more maintainable by removing the redundant code paths. The review is focused and technical, addressing a specific implementation detail rather than the feature's overall design.
