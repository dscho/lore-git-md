This is a feature addition to the `git replay` command, now at v4, introducing a `--revert` mode for server-side history rewriting. The patch series from Siddharth Asthana enables reverting commits directly on bare repositories, which is particularly useful for GitLab's Gitaly service.

The implementation follows the same approach as `sequencer.c`, treating reverts as merges with swapped arguments to reverse the diff direction. Key improvements in v4 include:

1. Fully consolidated revert message formatting into a new `sequencer_format_revert_message()` helper function, addressing Phillip Wood's suggestion to centralize this logic
2. Changed revert commit ordering to newest-first (matching `git revert` behavior) to reduce conflicts
3. Now drops empty revert commits by default (consistent with cherry-pick behavior)
4. Improved documentation with a cross-branch example and restored the `merge-tree` NOTE
5. Cleaned up error message formatting for translation concerns

The technical implementation has been thoroughly reviewed by Phillip Wood, Patrick Steinhardt, and Junio Hamano, with all substantive feedback addressed. While there's ongoing discussion about potentially restructuring the interface into subcommands (e.g., `replay revert`), the consensus is to defer that change to avoid scope creep in this series.

This appears to be a well-considered addition with comprehensive test coverage, building on established patterns in the codebase. The changes maintain consistency with existing `replay` behavior while adding the requested functionality in a way that aligns with Git's conventions for reverts.
