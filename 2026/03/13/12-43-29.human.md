This is a follow-up discussion in the bugfix thread addressing recursive lazy-fetch issues in promisor-remotes. Paul Tarjan clarifies two technical points raised by Patrick Steinhardt's review of the v3 patch.

First, he corrects his earlier description of "GC'd" objects - the issue actually involved stale prefetch refs pointing to commits that were promised but never downloaded in a blob:none partial clone. These refs were created by maintenance prefetch tasks but became invalid when upstream branches were force-pushed. While this explains why the initial fetches got thin packs, Paul notes it's separate from the core recursion issue.

Second, Paul explains an observed behavior where the filter configuration kept being rewritten despite manual unsetting. This occurred because each lazy-fetch child process would reapply the blob:none filter when it found the config set. He identifies this as a potential separate bug where fetch_objects() should use a transient config override rather than persisting the filter.

The discussion shows the patch is technically sound, with Paul offering to send a v4 if wording clarifications are needed. He also surfaces a related configuration persistence issue that could be addressed in a follow-up patch, though it's out of scope for the current fix. The exchange demonstrates careful analysis of edge cases while maintaining focus on the immediate security hardening.
