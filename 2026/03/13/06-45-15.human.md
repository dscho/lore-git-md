This is the fourth patch in Patrick Steinhardt's v4 series addressing lock contention in `git-upload-pack` during high-concurrency scenarios. The series has already been approved by Junio for merging.

The patch specifically targets write contention in `upload-pack` by implementing more aggressive buffering of packfile data before writing to the client. The key change is waiting until the buffer is at least 2/3 full before flushing, which reduces write syscalls from ~400k to ~130k when cloning the Linux repository. The patch includes analysis showing diminishing returns from trying to fill the buffer completely.

The change is particularly impactful for high-concurrency server environments where many `upload-pack` processes contend for kernel locks. The solution is carefully balanced to avoid increasing read syscalls while still providing substantial write reduction. A subsequent patch will address buffering in `pack-objects` as well, though this patch handles the more general case since the pack generator can be replaced via `uploadpack.packObjectsHook`.

The implementation builds on existing buffering in `upload-pack` and maintains all existing protocol semantics while improving performance. The patch has been thoroughly reviewed, with edge cases validated by Johannes Sixt and performance improvements confirmed across all target subsystems.
