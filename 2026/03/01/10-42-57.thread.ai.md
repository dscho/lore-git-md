Subject: [PATCH 0/2] refactor editor.c to remove global state  
Author: Shreyansh Paliwal  
Thread type: refactoring (the_repository removal effort)  

Core problem: Refactoring editor.c to eliminate global state as part of project-wide the_repository removal, specifically addressing editor_program variable and sequence editor dependencies. Debate centers on whether to maintain process-wide behavior (Shreyansh/Phillip) or implement repository-specific lookups (Burak/Tian), with new arguments about configuration model consistency.  

Current status: Initial patches move editor_program to editor.c with controlled access but don't fully eliminate global. Tian Yuchen's arguments for repository-specific configuration and Burak Kaan Karaçay's new response about configuration model challenges Phillip Wood's process-wide position. Burak identifies tension between allowing local core.editor configs while treating editor as process-global.  

Key technical details:  
- Current implementation makes editor_program static in editor.c with set_editor_program()  
- git_sequence_editor() takes explicit struct repository* but doesn't use it for config  
- Tian proposes storing editor_program in repo-settings.c via prepare_repo_settings()  
- Burak notes core.editor can be set locally despite proposed global behavior  
- Existing local config already allows per-repo core.editor settings  
- Use cases presented for different editors in different repos/submodules  
- Changes affect editor.[ch], environment.[ch], builtin/var.c, rebase-interactive.c  
- Part of Google Summer of Code project  

Open questions: Whether to maintain early validation with process-wide behavior (current approach) or fully eliminate global state via repository-specific lookups while preserving validation through repo-settings. Burak raises new concern about configuration model consistency if core.editor remains global while other settings become repository-specific, particularly for libification.  

Participant positions:  
- Shreyansh: defends process-wide behavior as natural for editor settings  
- Burak: advocates repository-specific lookups for config model consistency, notes libification implications  
- Phillip: questioned practicality of per-repo editors, favoring process-wide  
- Tian: strongly supports repository-specific with examples and repo-settings.c solution  

Related work: Part of larger the_repository removal project. Similar architectural tradeoffs have appeared in other subsystems during global state elimination. Burak's arguments about configuration model consistency parallel broader discussions about global vs per-repo settings.
