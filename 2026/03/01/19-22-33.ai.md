This is a performance discussion thread for Justin Tobler's repository statistics feature in `git repo`. The series has already been approved for merging but Lucas Seiki Oshiro raises runtime concerns - the expanded functionality roughly doubles execution time (from 3s to 6s on the Git repository) due to additional object parsing for commit/tree metrics.

Justin acknowledges the performance impact but explains it's inherent to the feature's purpose of providing comprehensive repository structure analysis, inspired by git-sizer. He argues against a key-based selection approach (like git-repo-info) since most metrics share underlying data sources, making selective retrieval ineffective for performance gains. Instead, he suggests a potential future `--[no-]extended` option could separate metrics into cheap/expensive categories if performance tuning becomes necessary.

The exchange highlights a tension between completeness and speed in repository analysis tools. Justin positions the current implementation as prioritizing the command's core purpose (structural overview) over optimization, while leaving room for future filtering options that wouldn't compromise the default comprehensive output. The discussion remains constructive, with both participants recognizing the tradeoffs between functionality and performance in this statistical tool.
