Alan Braithwaite proposed adding a `fetch.blobSizeLimit` config option to make partial clones more discoverable by automatically applying size-based filters during clone and fetch operations. The initial implementation handles configuration precedence and maintains backward compatibility when servers don't support filtering.

Patrick Steinhardt has raised important concerns about the performance implications of defaulting to size-based limits. He points out that size filters require expensive per-blob lookups that can't use existing optimizations like bitmaps, unlike `blob:none` filters which are more efficient server-side. This suggests the current proposal might create performance problems at scale.

The discussion now centers on two key questions: whether a computationally cheaper filter like `blob:none` would be a better default despite potentially requiring more follow-up fetches, and whether a global configuration is appropriate given that filter support varies across repository hosts. These are fundamental design considerations that will need resolution before the feature can move forward. The thread remains open with no clear consensus yet on how to balance discoverability against server performance.
