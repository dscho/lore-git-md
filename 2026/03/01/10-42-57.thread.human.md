Shreyansh Paliwal has submitted a two-patch series refactoring editor.c` to remove global state as part of the ongoing `the_repository` elimination effort. The first patch relocates the `editor_program` variable from `environment.c` to `editor.c` with controlled access, while the second threads a `struct repository` parameter through sequence editor functions to remove `the_repository` usage. The changes follow established patterns for this project-wide refactoring.

Burak Kaan Karaçay has now joined the discussion with a more ambitious proposal: rather than just moving the global state, he suggests eliminating it entirely by looking up the editor program configuration via `repo_config_get*` when needed. This would represent a more thorough removal of global state, though with the tradeoff that configuration errors would be detected later (at editor startup rather than during config loading). Burak argues this is a reasonable compromise since it wouldn't risk data loss.

This marks the first substantive technical discussion on the thread, showing how even mechanical refactorings can prompt deeper architectural conversations about state management in Git's codebase. The core question now is whether to accept Shreyansh's more conservative approach that maintains current behavior exactly, or pursue Burak's more aggressive global state elimination - a decision that may depend on maintainer input about the project's priorities for this refactoring effort.
