This is a performance discussion thread for Justin Tobler's `git repo` statistics series, which has already been approved for merging. The conversation focuses on execution time tradeoffs as the feature expands to include tree entry counting alongside existing object size metrics.

Lucas Seiki Oshiro reports that the expanded functionality roughly doubles execution time (from 3s to 6s when run on the Git repository itself). Justin acknowledges this is expected given the additional parsing required for commit/tree metrics, noting the command's purpose is to provide comprehensive repository overviews akin to git-sizer rather than being optimized for speed.

The discussion explores whether to add selective metric retrieval (similar to `git-repo-info`'s key-based approach) to address performance concerns. Justin argues this may not help much since most metrics share underlying data sources, and suggests any filtering mechanism should wait until after the initial merge. He floats the idea of a `--[no-]extended` option to separate cheap/expensive metrics if performance tuning becomes necessary later.

This is a healthy post-approval discussion about future optimization directions, with both participants recognizing the current implementation's focus on completeness over speed. The exchange maintains the series' original goal of providing structural insights while thoughtfully considering real-world usage patterns.
