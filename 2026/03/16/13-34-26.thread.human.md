Pablo Sabater's RFC series proposes adding a column limit to Git's graph output, now at v3 with refinements addressing earlier feedback. The feature would cap displayed graph columns (showing excess as '.') while preserving commit markers, implementing a 2008 TODO in graph.c. The current iteration proposes `--graph-limit-lanes` as the option name and makes it implicitly enable `--graph`, changes made in response to Junio Hamano's design feedback.

Johannes Sixt (Hannes) has now raised concerns about the implicit `--graph` behavior, arguing it could cause problems if the feature later becomes a config option. As the gitk maintainer, he suggests alternative names like `--edge-limit` or `--lane-limit` and recommends keeping the limit-setting behavior separate from graph display control. This introduces new considerations just as the thread appeared to be converging, with the author now facing competing design inputs from two respected contributors.

The core technical implementation (using `graph_max_columns` in `rev_info`) remains solid, but the user-facing behavior needs resolution. Hannes brings graphical tool expertise and forward-looking config considerations, while Junio previously shaped the current direction with UX-focused feedback. Pablo will need to reconcile these perspectives or seek maintainer guidance on which approach to prioritize.
