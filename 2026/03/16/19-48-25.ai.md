This is a follow-up in the RFC discussion about adding a `--graph-col-limit` option to control Git's graph output width. Pablo Sabater responds to Karthik Nayak's review of the initial patch, addressing several design and implementation points.

The author proposes `--graph-max-cols` as a compromise between clarity and verbosity, though the discussion seems to be converging toward `--graph-col-limit`. He provides a concrete use case for the feature - improving readability of `git log --graph --all` output in repos with many branches (demonstrating 35+ branches in Git's own `next` branch). The response acknowledges the 16-year-old TODO but argues the feature remains useful, particularly when third-party graph viewers aren't available.

Technical adjustments planned for v2 include:
- Explicit error when using the option without `--graph`
- Fixing padding calculations for truncated columns
- Renaming `graphs_needs_truncation()`
- Potentially switching to `unsigned int` for the column count
- Improving commit message clarity about the problem and solution

The email leaves open whether to allow 0 to mean "no limit" (Karthik's preference) versus requiring positive values (Pablo's position, citing other Git options' behavior). The thread remains in design discussion phase, with the author waiting for consensus on whether to proceed before sending v2. Key files involved remain graph.c, revision.h, and t4202-log.sh.
