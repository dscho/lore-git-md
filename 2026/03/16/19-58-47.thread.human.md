This thread introduces a bugfix to improve error reporting in `git apply` when parsing patch headers. The original issue was that error messages only showed line numbers when header parsing failed, making it difficult to identify which input patch caused the problem in batch processing scenarios.

The patch enhances several functions in `apply.c` (`parse_traditional_patch()`, `gitdiff_verify_name()`, and `parse_mode_line()`) to include the patch filename in error messages when available. The implementation adds a `patch_input_file` field to the `gitdiff_data` struct to carry this information through the parsing chain. Test cases in `t/t4100-apply-stat.sh` and `t/t4254-am-corrupt.sh` have been updated to verify the new error message format.

The change is well-contained, maintaining backward compatibility by falling back to line-number-only errors when no filename information is available. This should significantly improve debugging experience for users applying multiple patches at once, while requiring no changes to the core parsing logic. The test coverage appears thorough, checking various malformed patch scenarios to ensure the enhanced error messages work as intended.
