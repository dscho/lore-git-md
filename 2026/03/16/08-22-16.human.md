This is a follow-up discussion about `git describe --dirty` behavior when used with repository discovery options. Patrick Steinhardt adds to Junio C Hamano's earlier clarification about the expected behavior of `--git-dir` and `--work-tree`.

The thread had established that when using `--git-dir` alone, Git assumes the current directory is the working tree root, which can lead to incorrect "dirty" state reports when run from outside the repository. Junio had confirmed this is working as designed and suggested using both `--git-dir` and `--work-tree` as the proper solution.

Patrick now points out that for this common use case, the simpler `-C` option (change directory before running the command) is likely what users actually want, as it handles both repository discovery and working tree context in one go. He notes that `--git-dir` is typically only needed for more specialized cases.

This reinforces that the original behavior isn't a bug but rather a case of using the wrong tool for the job. The exchange serves as a good reminder that `-C` is often the cleaner alternative to manually specifying `--git-dir` and `--work-tree` when operating on repositories from other directories. No further action appears needed beyond this clarification.
