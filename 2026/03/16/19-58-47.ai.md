Bugfix improving error reporting in `git apply`'s patch header parsing. This patch enhances several error messages in `apply.c` to include the input file location when reporting header parsing failures, which is particularly useful when applying multiple patches at once. Currently, these errors only show line numbers, making it hard to identify which input patch caused the problem.

The changes modify error reporting in functions like `parse_traditional_patch()`, `gitdiff_verify_name()`, and `parse_mode_line()` to include the patch filename when available. The patch also updates related test cases in `t/t4100-apply-stat.sh` and `t/t4254-am-corrupt.sh` to verify the new error message format.

The implementation adds a `patch_input_file` field to the `gitdiff_data` struct and threads this information through the parsing call chain. This appears to be a well-contained change focused specifically on improving error reporting without modifying the core parsing logic. The test coverage looks thorough, with new cases added to verify the enhanced error messages for various malformed patch scenarios.

This seems like a straightforward quality-of-life improvement for users who need to debug patch application issues, particularly in batch processing scenarios. The patch is cleanly separated from other functionality and maintains backward compatibility by falling back to line-number-only errors when no input file information is available.
