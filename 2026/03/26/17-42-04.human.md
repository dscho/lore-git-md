This is a technical discussion about const-correctness in Git's revision parsing code, specifically around handling of argv strings. Jeff King (Peff) responds to Michael J Gruber's patch that adds explicit casts to handle ISOC23's stricter const pointer rules.

Peff notes that while mutating argv strings is technically legal (as evidenced by current behavior not segfaulting), the project would prefer to treat them as conceptually const. He points out a potential segfault case with string literals containing range operators ("..") that fortunately doesn't occur in practice.

The key suggestion is to refactor the revision parser to avoid modifying input buffers entirely, using `xmemdupz()` to create copies when needed. Peff mentions having draft patches for this approach but hasn't finalized them yet. This would be a more robust solution than the current casting approach, though with a minor performance tradeoff (additional allocations that should be negligible in practice).

The discussion continues the thread's theme of balancing compiler compliance with clean API design, with Peff advocating for a solution that properly respects const semantics rather than working around them. This touches core revision parsing code in `revision.c` and `builtin/rev-parse.c`, areas where interface clarity is particularly important.
