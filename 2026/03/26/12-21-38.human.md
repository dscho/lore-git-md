This is a feature patch in Christian Couder's series introducing URL-based whitelisting for promisor remotes. Patrick Steinhardt provides feedback on patch 14/16, which implements the core URL matching logic for trusted remote updates.

Patrick raises several thoughtful points about the design and documentation. He questions whether the commit message focuses too much on implementation steps rather than the "why", and suggests including clearer examples of proper URL pattern usage in the documentation. More significantly, he probes the design decision to introduce a new config option (`promisor.acceptFromServerUrl`) rather than extending the existing `promisor.acceptFromServer`, wondering if the concerns could be better separated into distinct configuration variables for accepting new remotes versus updating existing ones.

The discussion reflects careful consideration of both security implications and user experience. While the technical implementation appears sound (as noted in the parent summary), Patrick's comments suggest the interface might benefit from refinement to make the security model more intuitive. This continues the pattern of constructive, security-conscious review seen throughout the thread, now focusing on making the feature's behavior more transparent to end users.
