This is a review response in Christian Couder's series on URL-based whitelisting for promisor remotes. Patrick Steinhardt raises several thoughtful points about patch 14/16, which implements the core URL matching logic for trusted remote updates.

Patrick notes that while the patch focuses on already-configured remotes (with new remote handling coming in the next patch), the commit message leans too much toward implementation steps rather than explaining the design rationale. He suggests the documentation could benefit from concrete examples of proper URL pattern usage.

The key technical questions raised are:
1. Why introduce a new `promisor.acceptFromServerUrl` config rather than extending the existing `promisor.acceptFromRemote` with URL patterns?
2. Whether it would be clearer to separate the concerns of accepting new remotes versus updating existing ones into distinct configuration variables.

Patrick's feedback indicates the security model's interaction between these settings may not be immediately obvious, suggesting the design could benefit from either consolidation or clearer separation of concerns. His questions probe whether the current approach is the most intuitive way to expose these controls to users while maintaining security.

The review maintains the series' constructive tone while identifying potential areas for improved clarity in both implementation documentation and user-facing design. These appear to be genuine design questions rather than blocking concerns, continuing the pattern of iterative refinement seen throughout the thread.
