This is a feature patch (6/12 in v5 of the series) that marks certain Git hooks as non-parallelizable by default. The patch comes from Adrian Ratiu but carries Emily Shaffer's sign-off, indicating she originally worked on this aspect of the parallel hooks feature.

The patch identifies seven hooks that must always run sequentially due to their access to shared resources:
- Message-related hooks (applypatch-msg, prepare-commit-msg, commit-msg) that modify commit messages in-place
- Hooks that interact with working tree/state (pre-commit, post-checkout, push-to-checkout, post-commit)

These hooks are now initialized with RUN_HOOKS_OPT_INIT_FORCE_SERIAL, which overrides any parallel execution settings (hook.jobs config or -j CLI flag). The implementation updates hook calls in builtin commands (am, checkout, clone, receive-pack, worktree) and commit.c to use the force-serial option.

Documentation is added explaining why these hooks can't be parallelized, and a new test verifies that hook.jobs=2 is properly ignored for force-serial hooks (using pre-commit as the test case). The test infrastructure from earlier in the series (sentinel_detector) is reused to verify serial execution ordering.

This patch is part of the larger parallel hooks effort that has been through multiple iterations (now at v5) with maintainer approval on the core approach. It represents a conservative safety measure to prevent parallel execution where it could cause data races or corruption, while still allowing parallelization for other hook types. The implementation appears thorough, touching all relevant hook call sites and adding both documentation and test coverage.
