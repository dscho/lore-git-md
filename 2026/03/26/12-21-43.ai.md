This is a design discussion response in Christian Couder's series on URL-based promisor remote configuration. Patrick Steinhardt suggests splitting the functionality into three distinct concerns: runtime acceptance, initial storage, and ongoing updates of promisor remotes.

Patrick proposes adding a `--accept-promisors` option to `git clone` for one-time configuration, arguing that many users won't want persistent auto-updating behavior. He identifies three separate use cases currently conflated in the implementation:

1. Runtime acceptance of unconfigured promisors (ongoing)
2. Initial storage of promisors (one-time, likely at clone)
3. Automatic updates of stored promisors (ongoing)

The current `promisor.acceptFromServerUrl` combines these behaviors, which Patrick suggests may not match the most common expected workflow - storing promisors at clone time and updating them, but not auto-accepting unconfigured ones. He proposes clearer separation with new config options: `acceptFromServer` for runtime behavior, `storeFromServer` for persistence, and `updateFromServer` for maintenance.

This feedback continues Patrick's pattern of constructive refinement, focusing on improving the design's conceptual clarity and user experience. The suggestion reflects practical deployment considerations and aims to better align the feature with likely administrator workflows. The proposal would require significant restructuring of the series' approach while maintaining its security properties.
