This is a bugfix for the commit-graph generation number computation, addressing a regression introduced by Patrick Steinhardt's recent commit 024b4c9697. The patch is now in its second version, with Karthik Nayak providing review feedback on the implementation.

The core issue involves how commit dates are handled when they exceed 34 bits of precision (dates after year 2514). The commit-graph format stores only 34 bits of commit dates to save space, while the full timestamp_t type has 64 bits. The regression caused generation number calculation errors when commits were parsed both from the commit-graph (with 34-bit dates) and then re-parsed from the object database (with full 64-bit dates).

Karthik's review confirms the technical correctness of Patrick's solution, which introduces a new helper function `compute_generation_offset()` that explicitly masks commit dates to 34 bits before calculating generation offsets. The review specifically validates the commit-graph chunk structure and the test case that verifies the fix works with extremely large dates (year 292,471,210,647). The test demonstrates correct handling when replacing a commit-graph with commits containing these extreme dates.

The review highlights the clear explanation of the problem and solution in the commit message, and confirms the test case properly exercises the code path where the commit-graph is rewritten (which triggers the recomputation of overflow chunks). Karthik's positive review adds to the existing approvals from Junio C Hamano and Derrick Stolee, further solidifying confidence in this fix.
