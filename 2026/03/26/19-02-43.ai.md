This is a follow-up to the const-correctness discussion in Git's revision parsing code. Jeff King (Peff) delivers on his earlier promise to refactor the revision parser to avoid modifying const strings, submitting a 4-patch series that replaces the problematic in-place string modifications with allocation-based solutions.

The series focuses on two key areas where Git previously modified argv strings: handling range operators ("..") in `builtin/rev-parse.c` and `revision.c`, and processing parent shorthand marks ("^@") in the same files. Rather than using explicit casts to work around ISOC23's stricter const handling (as in Michael J Gruber's earlier series), Peff's approach allocates new strings via `xmemdupz()` when temporary modifications are needed. This maintains the same functionality while properly respecting const semantics.

Notable technical changes include simplifying the dotdot parsing interface in patch 1, then applying the allocation pattern to both the range operators (patches 2 and 3) and parent marks (patch 4). The changes touch core revision walking code in `revision.c` and the `git rev-parse` implementation in `builtin/rev-parse.c`, with about 50 lines changed across both files.

This represents the structural solution Peff had hinted at in earlier discussion, moving beyond temporary fixes to properly resolve the underlying const-correctness issues. The series appears well-aligned with maintainer preferences expressed in the thread, particularly Junio Hamano's inclination toward solutions that minimize type system violations. Given Peff's deep knowledge of this code and the prior consensus that allocation was the right long-term direction, this series seems likely to be well-received.
