This is a maintainer response to a test modernization patch, pointing out an issue with how the patch was submitted rather than with the technical content itself. Junio C Hamano notes that the patch appears to be correcting a previous incorrect change (converting `! test -f` to `! test_path_is_file`) rather than directly updating the original code to use `test_path_is_missing`.

The key points are that the patch:
1. Won't apply cleanly to the current tree because it assumes an intermediate state that doesn't exist in the main repository
2. Violates Git's patch submission norms by presenting a fix for a mistake that wasn't merged rather than submitting a clean series
3. Should be resubmitted as a single patch going directly from the original state to the desired final state

Junio provides guidance on proper patch submission workflow, referencing both the SubmittingPatches documentation and a previous email explaining how to structure patch revisions. The technical change itself (using `test_path_is_missing`) remains correct and desirable - the issue is purely with the patch submission process.

This response serves as both a rejection of the current submission and a teaching moment about Git's development norms, particularly the expectation that patch series should present a clean logical progression even if the author's local development involved intermediate missteps.
