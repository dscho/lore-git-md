This is the final patch in Vaidas Pilkauskas's series adding HTTP 429 (Too Many Requests) rate limit handling to Git's HTTP client. The feature enables Git to automatically retry requests when servers respond with rate limits, respecting Retry-After headers in both delay-seconds and HTTP-date formats.

The implementation introduces three new configuration options: `http.maxRetries` (default 0), `http.retryAfter` (default 0), and `http.maxRetryTime` (default 300 seconds). The patch includes comprehensive test coverage verifying retry behavior, header parsing, configuration combinations, and edge cases like past-dated Retry-After values. The code cleanly integrates with Git's existing HTTP transport layer while maintaining the new `HTTP_RATE_LIMITED` result code and Trace2 instrumentation.

The patch has evolved through six iterations with feedback from Jeff King (HTTP transport expert) and Junio Hamano (maintainer). Earlier preparatory strbuf fixes were already merged separately. This final version appears technically complete and well-tested, addressing all prior review feedback about retry logic structure and test timing races. The implementation demonstrates careful attention to both modern libcurl features (CURLINFO_RETRY_AFTER in curl >=7.66.0) and backward compatibility.

For users interacting with rate-limited Git servers, this provides a significant quality-of-life improvement by automating what previously required manual retries. The fail-fast approach when delays exceed `maxRetryTime` gives clear feedback about rate limiting issues rather than silently capping delays.
