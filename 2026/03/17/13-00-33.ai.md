This is a bugfix patch from Vaidas Pilkauskas addressing a memory allocation issue in `strbuf_reencode()`. The patch is part of a larger series implementing HTTP 429 rate limit handling, but this particular change stands alone as a correctness fix.

The issue occurs when reencoding strings - `reencode_string_len()` allocates len+1 bytes (including the NUL terminator) but `strbuf_reencode()` was passing only len bytes to `strbuf_attach()`. This caused unnecessary reallocations since the buffer would always appear too small. The fix simply passes the correct allocation size (len+1) to match what was actually allocated.

This is a straightforward, mechanical change that has already been reviewed and approved by Junio Hamano (as noted in the thread context). It touches only one line in strbuf.c, fixing a subtle memory management issue that could lead to performance overhead from unnecessary reallocations. The change is well-explained in the commit message and has clear test coverage from the existing strbuf tests.
