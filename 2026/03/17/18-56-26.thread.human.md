This thread documents the evolution of `git replay`'s root commit handling, from technical implementation to user experience refinements. The core technical work - enabling `git replay` to handle root commits through refactored logic in `mapped_commit()` with proper NULL pointer safety - has already been merged to `next`. The discussion has shifted to how best to communicate this functionality to users.

Maintainer Junio Hamano has been adamant that clear documentation explaining the behavior (particularly around range syntax like `main..topic` versus `topic`) should ship with the feature itself, rather than being deferred. Christian Couder initially suggested warning about potential pitfalls, but now proposes an alternative approach: improving runtime error messages to explicitly indicate when conflicts occur during replay operations, with special wording for root commit cases. While still advocating for documentation updates, Christian's latest suggestion shows flexibility in considering multiple channels for user education.

The thread exemplifies Git's development process where technical implementation is just the beginning - equal attention goes to ensuring users understand the changes. With the code merged, participants are now exploring complementary ways to improve usability, whether through documentation (Junio's priority) or enhanced error messaging (Christian's new suggestion). The discussion remains productive and focused, with all contributors aligned on the goal of clear communication, just differing on the precise mix of static and dynamic approaches.
