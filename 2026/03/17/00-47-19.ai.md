This is a follow-up to the recently merged `rev-parse --parseopt` help exit code fix, where Junio C Hamano has spotted a regression in `t1517` related to `git instaweb -h` behavior outside a repository. The test expects exit code 129 (error) for help requests in this context, but now gets 0 (success) after the changes.

The issue reveals an unintended consequence of the earlier patch - while the `--parseopt` changes were correct for their specific use case, they've affected the behavior of `git instaweb` which uses the same underlying option parsing machinery. This suggests the fix needs adjustment to maintain the expected behavior for commands that intentionally want error exits for help requests in certain contexts.

Junio's message indicates this was caught during integration testing (queued on top of v2.53.0), showing the value of the project's thorough test suite. The regression appears in test 169 of t1517, which specifically checks that `git instaweb -h` exits with status 129 when run outside a repository, but now exits 0 instead.

This will likely require either:
1. A follow-up patch to make the exit code behavior configurable per-command
2. Special-casing for `instaweb`'s particular needs
3. Revisiting whether `instaweb` should align with the new standard behavior

The thread shows the patch author (brian m. carlson) will need to address this before the change can proceed further in the integration branches.
