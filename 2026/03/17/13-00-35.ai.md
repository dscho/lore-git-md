This is the final patch in Vaidas Pilkauskas's HTTP 429 rate limit retry series, implementing comprehensive rate limit handling in Git's HTTP client. The patch adds support for automatic retries when receiving HTTP 429 (Too Many Requests) responses, respecting server-specified Retry-After headers in both delay-seconds and HTTP-date formats.

The implementation introduces three new configuration options: http.maxRetries (default 0), http.retryAfter (default 0), and http.maxRetryTime (default 300 seconds). These can be overridden by environment variables GIT_HTTP_MAX_RETRIES, GIT_HTTP_RETRY_AFTER, and GIT_HTTP_MAX_RETRY_TIME respectively. The patch includes extensive test coverage in t/t5584-http-429-retry.sh that verifies various scenarios including header parsing, configuration combinations, timing behavior, and edge cases.

Key technical details include:
- New HTTP_RATE_LIMITED (7) result code in http.h
- CURLINFO_RETRY_AFTER support for curl >=7.66.0 with fallback parsing
- Trace2 instrumentation for retry events
- Fail-fast behavior when delays exceed http.maxRetryTime
- Special test endpoint at /http_429/ that simulates rate limiting

The patch builds on previous rounds of review from Jeff King, with v6 addressing architectural feedback by restructuring the retry logic to use http_get_options for parameter passing and fixing retry counter separation between REAUTH/RATE_LIMITED cases. All preparatory strbuf fixes from earlier in the series have already been merged separately by Junio Hamano.

This represents a significant new capability for Git's HTTP client when interacting with rate-limited servers, with careful attention to backward compatibility (supporting older curl versions) and configurable behavior. The implementation appears technically complete and well-tested, with the main HTTP 429 feature now ready for final review.
