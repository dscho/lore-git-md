Thread identity: Bugfix for commit-graph generation number computation regression introduced by Patrick Steinhardt's commit 024b4c9697, affecting dates after year 2514.

Core problem: The commit-graph format stores only 34 bits of commit dates (to save space) while timestamp_t uses 64 bits. When commits were parsed both from commit-graph (34-bit dates) and object database (64-bit dates), generation number calculations could mismatch during commit-graph writes, particularly for dates exceeding 34 bits.

Current status: Patrick Steinhardt's fix introducing compute_generation_offset() helper has been reviewed and approved by Junio C Hamano for inclusion in the integration queue. The helper explicitly masks commit dates to 34 bits before generation number calculations, ensuring consistent behavior regardless of parse path. The patch includes a test case verifying correct handling of extreme dates (year 292,471,210,647).

Key technical details: Fix touches commit-graph.c, adding the new helper function and modifying generation number calculation logic. Maintains backward compatibility with existing commit-graph files. Test case in t5318-commit-graph.sh demonstrates the overflow condition and verifies the fix, using a timestamp of 9223372036854775 (year 292,471,210,647) that clearly exceeds 34 bits.

Participant positions: Patrick Steinhardt (author) identified and fixed his own regression. Junio C Hamano reviewed and approved the fix, noting with interest that GitLab's test suite caught this using unusually large timestamps (year 2600+). As both the primary expert in this area and the maintainer, their combined review carries high confidence in the solution.

Related work: Builds on Patrick's prior work in commit-graph generation number handling (024b4c9697). The fix maintains compatibility with existing commit-graph files while correctly handling edge cases in date parsing. Junio's queueing indicates this will be included in an upcoming release.
