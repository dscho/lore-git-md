Thread identity: Bugfix for commit-graph generation number computation regression introduced by Patrick Steinhardt's commit 024b4c9697, affecting dates after year 2514. Now at v2 with platform-specific handling improvements.

Core problem: The commit-graph format stores only 34 bits of commit dates (to save space) while timestamp_t uses 64 bits. When commits were parsed both from commit-graph (34-bit dates) and object database (64-bit dates), generation number calculations could mismatch during commit-graph writes, particularly for dates exceeding 34 bits. The v2 patch adds explicit handling for 32-bit timestamp_t systems.

Current status: Patrick Steinhardt's fix introducing compute_generation_offset() helper has been reviewed and approved by Junio C Hamano for inclusion in the integration queue, with additional support from Derrick Stolee. The v2 version now properly handles platforms with 32-bit timestamp_t. The helper explicitly masks commit dates to 34 bits before generation number calculations, ensuring consistent behavior regardless of parse path. The patch includes a test case verifying correct handling of extreme dates (year 292,471,210,647) based on real-world data from GitLab's test repositories (year 2600+).

Key technical details: Fix touches commit-graph.c, adding the new helper function and modifying generation number calculation logic. Maintains backward compatibility with existing commit-graph files. Test case in t5318-commit-graph.sh demonstrates the overflow condition and verifies the fix, using a timestamp of 9223372036854775 (year 292,471,210,647) that clearly exceeds 34 bits. The test case's use of real-world data from GitLab's test suite was particularly praised by Stolee. V2 adds explicit handling for 32-bit timestamp_t systems to ensure portability.
