This thread discusses a 2-patch series improving Git's handling of custom bisect terminology. The author has addressed inconsistencies where some bisect-related commands (`bisect status` and `rev-parse --bisect`) were still hardcoding "good"/"bad" terminology even when users configured alternate terms like "old"/"new" via `git bisect start --term-good/--term-bad`.

The first patch fixed `git bisect status` to show the configured terms in its output and error messages. The newly submitted second patch completes the effort by making `git rev-parse --bisect` respect the configured terms when looking up refs. The changes are straightforward - replacing hardcoded strings with dynamically constructed paths using the terms from the bisect state.

The series appears well-tested, with the first patch adding explicit test coverage for the status output case. While the second patch doesn't add new tests (relying on existing bisect test coverage), the commit message notes that explicit tests for custom terms in ref lookup might be worth adding later. Both patches are focused changes touching only their respective builtins (bisect.c and rev-parse.c).

With both patches now submitted, the series provides comprehensive support for custom bisect terminology across Git's commands. The changes look ready for review and should integrate cleanly. No open questions or objections have been raised in the thread so far.
