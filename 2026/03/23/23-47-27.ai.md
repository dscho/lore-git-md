Security-focused review of URL pattern matching rules in promisor remote whitelisting.

Junio Hamano continues the security discussion around Christian Couder's URL-based promisor remote whitelisting feature, focusing on tightening the glob pattern matching rules. While acknowledging the need to maintain backward compatibility with existing `urlmatch` behavior, he proposes more intelligent pattern matching to prevent security pitfalls.

The key concern is how `*` globs interact with slashes in URL patterns. Junio questions whether allowing `*` to match across `/` boundaries (as in `https://*.example.com/*` matching `https://evil-hacker.net/fake.example.com/repo`) has any legitimate use cases. He suggests a compromise where `*` in the domain portion (before the first `/`) would be restricted from matching slashes, while maintaining current behavior elsewhere.

This would prevent dangerous patterns like:
1. `https://*.example.com` matching malicious domains containing the substring
2. `https://example.com*` matching domains with suffix additions

The proposal aims to maintain compatibility with existing configurations like `[http "https://example.com/*"]` while closing security holes in the promisor remote use case. This reflects Junio's typical maintainer approach - balancing security hardening with minimizing disruption to existing workflows. The discussion will likely lead to follow-up patches adjusting the URL matching implementation to incorporate these safer defaults.
