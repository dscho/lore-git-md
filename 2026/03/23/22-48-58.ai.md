This is a cover letter for a 2-patch series addressing inconsistencies in Git's bisect functionality when alternate terms (instead of the default "good"/"bad") are used. The series follows up on an earlier v1 that only addressed part of the problem.

The first patch ensures the `git bisect status` output respects custom bisect terms (like "old"/"new") rather than always showing "good"/"bad". The second patch fixes `git rev-parse --bisect` to also use the configured terms when looking up refs, which was previously hardcoded to "good"/"bad".

The series appears well-motivated, with v2 adding tests and expanding the scope to cover the rev-parse case that was missed in v1. The changes are focused on the bisect and rev-parse builtins, touching their term-handling logic and adding test coverage in t6030. The commit messages clearly explain what behavior changes and why.

This looks like a solid incremental improvement to Git's bisect functionality, particularly for users who prefer alternate terminology. The changes are narrow in scope but address real inconsistencies in how custom terms are handled across different bisect-related commands.
