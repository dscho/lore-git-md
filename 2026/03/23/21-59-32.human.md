This is a feature proposal (v4) from Pablo Sabater introducing a `--graph-lane-limit` option to constrain the width of `git log --graph` output. The patch series addresses terminal readability issues with wide commit graphs by truncating excess lanes while preserving key commit markers.

The v4 iteration responds to Junio Hamano's feedback by improving commit messages to better explain the motivation (wide output from many active branches) and design rationale (minimum limit=1 for consistency). It also standardizes on `int` type for the lane limit parameter, following Git conventions, and accepts zero/negative values as "no limit" similar to `--max-parents`.

The implementation adds a `graph_max_lanes` field to `struct rev_info` and modifies graph.c to replace hidden lanes with '.' characters while showing '*' for commits on the first hidden lane. The series includes thorough test cases demonstrating 2-3 lane limits with merge scenarios.

Key changes in v4:
- Rewritten commit messages focusing on reasoning rather than implementation
- Standardized on `int` type for consistency with other rev_info fields
- Zero/negative values now treated as "no limit"
- Removed MINIMUM_GRAPH_COLUMNS macro
- Fixed documentation formatting

The patch appears well-constructed with good test coverage and addresses a long-standing TODO from 2008 about column limiting. While the technical implementation seems sound, there remain open questions about whether to refactor graph.c's lane handling code and how to best handle collapsing/merge lanes when connection points are obscured. The series is now in good shape for final review.
