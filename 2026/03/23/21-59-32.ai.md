This is a feature proposal (v4) from Pablo Sabater introducing a `--graph-lane-limit` option to constrain the width of `git log --graph` output. The patch series addresses terminal readability issues with wide commit graphs by truncating excess lanes while preserving key commit markers.

The v4 iteration responds to Junio Hamano's feedback by standardizing on `int` type for the lane limit (matching other `rev_info` fields) and improving commit message clarity. The implementation now silently treats zero/negative values as "no limit" (consistent with `--max-parents` behavior) and removes the `MINIMUM_GRAPH_COLUMNS` macro. The series maintains the truncation behavior where excess lanes show as dots while keeping '*' markers for commits on the first hidden lane.

Key technical changes in v4:
- Type standardization: `graph_max_lanes` is now `int` (was `unsigned int`)
- Zero/negative values now mean "no limit" (following `--max-parents` precedent)
- Removed `MINIMUM_GRAPH_COLUMNS` macro
- Improved commit message focus on rationale over implementation
- Fixed documentation formatting (added missing "--" prefix)

The patch touches graph.c, graph.h, revision.c, and adds tests in t4215-log-skewed-merges.sh. It represents a focused solution to a 2008 TODO about column limiting, though it deliberately does not implement gitk-style rearrangement. The author has been responsive to review feedback while maintaining the feature's utility for terminal viewing of complex graphs.

Open technical questions from previous iterations remain about refactoring graph.c's lane handling code and whether to maintain collapsing/merge lanes when connection points are obscured. The design discussion around implicit `--graph` behavior and naming appears resolved in this version. The patch series is now complete with documentation and test coverage, pending final review.
