This is a follow-up to the `STRBUF_INIT_CONST` RFC discussion, where Mateo Patino proposes an alternative approach to handling read-only strings in Git's codebase. The thread has established that directly modifying `strbuf` to support constant strings would violate its API contract of always providing a writable buffer.

Mateo suggests introducing a new `strview` struct as a read-only counterpart to `strbuf`, modeled after C++'s `string_view`. This would be a lightweight structure holding just a pointer and length, with no ownership or allocation semantics. The proposal acknowledges this doesn't solve the original optimization goal (avoiding allocations for constant strings), but positions it as a potentially safer way to handle read-only string data throughout the codebase.

The email shows the author grappling with the architectural constraints raised in earlier reviews, attempting to find a different angle that might satisfy both performance and safety requirements. However, it's unclear whether this alternative would gain traction, as it represents a more fundamental change to Git's string handling infrastructure rather than the original targeted optimization. The proposal would need to demonstrate clear benefits outweighing the cost of introducing and maintaining parallel string-handling APIs.
