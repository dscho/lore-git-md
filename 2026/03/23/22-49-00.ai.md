This is the second patch in a 2-part series improving custom bisect term handling in Git. It fixes `git rev-parse --bisect` to respect configured alternate bisect terms (like "old"/"new") when looking up refs, rather than always using the hardcoded "good"/"bad" paths.

The patch modifies `builtin/rev-parse.c` to read the current bisect terms via `read_bisect_terms()` and uses them to construct the ref paths dynamically. This ensures `rev-parse --bisect` works correctly when users specify custom terms via `git bisect start --term-good/--term-bad`. The change is straightforward - replacing hardcoded strings with dynamically constructed paths using the configured terms.

This completes the series' goal of making Git's bisect functionality consistently respect custom terminology. The first patch handled `git bisect status` output; this one addresses the ref lookup case. Together they eliminate the remaining inconsistencies where some commands still assumed "good"/"bad" terminology. The patch includes no new tests since the existing bisect test suite already verifies the ref lookup behavior, though it might be worth adding explicit coverage for the custom term case in a follow-up.

The changes are focused and well-contained, touching only the rev-parse builtin's bisect handling. The commit message clearly explains the problem and solution. This appears ready for review and should integrate cleanly with the first patch in the series.
