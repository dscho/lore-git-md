Thread identity: 2-patch series on improving custom bisect term handling in response to inconsistencies when alternate terms (e.g. "old"/"new") are used instead of default "good"/"bad". Follow-up to v1 which only partially addressed the issue, now expanded to cover both status output and ref lookup cases.

Core problem: When users configure custom bisect terms via `git bisect start --term-(good|bad)`, various commands were hardcoding "good"/"bad" instead of respecting configured terms. The series makes all bisect-related commands consistently use the configured terminology.

Current status: v2 series with two patches under review:
1. Fixes `git bisect status` to show configured terms
2. Makes `git rev-parse --bisect` respect configured terms

Key technical details:
- Changes in builtin/bisect.c:
  - bisect_print_status() now uses terms->term_good/bad
  - Error messages in bisect_run() use configured terms
  - Phillip Wood suggests wrapping terms in single quotes in output for clarity
- Changes in builtin/rev-parse.c:
  - Reads current bisect terms via read_bisect_terms()
  - Dynamically builds ref paths using configured terms
  - Needs NULL check when no bisect active (read_bisect_terms() returns NULL)
  - Needs memory cleanup for allocated term strings
- Test coverage in t6030-bisect-porcelain.sh:
  - Verifies status output with custom terms
  - Checks bisect run messages
  - Phillip Wood recommends using test_grep instead of grep for better diagnostics
  - Needs additional tests for rev-parse edge cases
  - Tests use example terms "term1"/"term2"

Open questions: Phillip Wood identified two specific improvements needed for the rev-parse patch:
1. Handle case where no bisect is active (NULL terms)
2. Fix memory leak from unfreed term strings
These should be addressed in v3.
