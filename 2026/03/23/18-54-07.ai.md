Junio Hamano raises several important security and documentation concerns about Christian Couder's URL-based promisor remote whitelisting feature. This is a review response in the ongoing series that introduces the `promisor.acceptFromServerUrl` configuration option.

The review focuses on clarifying the security model and tightening URL pattern rules. Key points raised:

1. The documentation needs to explicitly define what "trusted" means in this context - what specific actions are enabled for matching remotes. Junio suggests it likely means treating them as if `promisor.acceptFromServer=all` was set, but this should be made clear.

2. The security advice about URL patterns could be more restrictive by default:
   - The protocol scheme should likely be limited to just `https://` and `ssh://` in code rather than leaving it as documentation advice
   - The glob pattern matching rules should be tightened to prevent `*` from matching across `/` boundaries, as this creates security risks
   - These restrictions could be implemented directly rather than just documented as best practices

3. Terminology note: some may prefer "allowlist" over "whitelist" (though this is a minor stylistic point)

The review doesn't challenge the core functionality but pushes for stronger security defaults and clearer documentation about the trust model. These are reasonable requests that would make the feature safer by default while maintaining its flexibility. The response will likely lead to follow-up patches adjusting the URL matching rules and expanding the security documentation.
