This is a bug report about terminal input handling in Git for Windows when using `git add --patch`. The reporter, Dana Escoli, describes an issue where keyboard input stops being echoed to the terminal after closing the editor during an interactive hunk edit session. The problem manifests when using `bash.exe` from the Git installation on Windows 10, but works correctly with `git-bash.exe`.

Key technical details: The issue occurs after editing a hunk when the editor closes, causing the terminal to stop echoing input. Ctrl+C becomes unresponsive, though Ctrl+Z reveals that inputs are being processed but appear malformed (with unexpected single quotes). The problem reproduces across different editors (Notepad, Notepad++) and terminals (IntelliJ's terminal, cmd.exe), suggesting it's not IDE-specific.

The report indicates this is specific to the Windows port's terminal handling during interactive patch editing. Since the behavior differs between `bash.exe` and `git-bash.exe`, it likely involves how the different shells handle terminal control and input forwarding after editor invocation. This would be of particular interest to the Git for Windows maintainers (Johannes Schindelen) and anyone working on the interactive add/apply machinery (Phillip Wood has historically worked in this area).

The report is clear and provides enough detail to reproduce, though it doesn't include debug traces or bisect information. The workaround (using git-bash.exe) is noted, but the underlying issue remains unaddressed for users who need to use the standard Windows terminal paths.
