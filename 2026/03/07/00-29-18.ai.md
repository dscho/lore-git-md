# Feature patch with use case clarification

This is a follow-up to the proposed `--no-turtle-speed` feature that would abort slow clone operations. The author, Mike Banon, responds to brian m. carlson's review feedback by providing concrete context about their use case - automated builds of a small Linux distribution where slow GitHub server connections (70 KiB/s vs expected multi-MiB/s) cause significant delays. The response clarifies this is not just theoretical but a real pain point in their build system, where they currently work around it with wrapper scripts that retry failed clones.

Key technical points from the response:
- Confirms the feature addresses a genuine problem with GitHub's load balancing occasionally directing connections to slow servers
- Shows their current wrapper script implementation that retries clones until getting a fast connection
- Acknowledges brian m. carlson's suggestions about configurable thresholds and terminology
- Explains the env var approach was chosen for minimal implementation complexity

The email provides important context missing from the original patch - this isn't just a hypothetical feature but solves a concrete problem the author faces regularly. However, it still leaves open the architectural questions raised in review about whether this belongs in core Git versus wrapper scripts, and how best to implement the speed threshold configurability. The response suggests the author may revise the patch to incorporate the feedback but hasn't committed to specific changes yet.
