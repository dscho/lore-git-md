This is a question about partial clone behavior and promisor remote configuration, coming from a Google Summer of Code (GSoC) applicant exploring the "Implement promisor remote fetch ordering" project idea.

Lorenzo Pegorari is investigating how `extensions.partialClone` interacts with multiple promisor remotes. Their experiments suggest that:
1) Multiple promisor remotes can work without `extensions.partialClone` when configured with `remote.<name>.promisor` and `remote.<name>.partialCloneFilter`, trying remotes in config order
2) When `extensions.partialClone` is set, that remote becomes the last one tried

They're seeking confirmation of this behavior and guidance on how a future fetch ordering mechanism should handle the `extensions.partialClone` configuration, since it may become redundant but can't simply be removed.
