This is a feature proposal for per-remote SSH configuration in Git, continuing a discussion that has reached a philosophical impasse. Wesley Schwengle responds to Johannes Sixt's (Hannes) critique by doubling down on the argument that SSH configuration belongs in Git rather than in SSH config files. The core disagreement remains unchanged: Wesley's position is that Git should manage its own SSH settings (identity files, options) through Git's config system, while Hannes and other reviewers maintain that existing SSH host aliases and config files are sufficient.

Wesley provides more concrete examples of his use case - freelancers with multiple clients and developers working across personal/employer projects on the same forge. His key argument is that configuring SSH to work around Git limitations feels backwards when Git could handle these settings directly. He emphasizes version control benefits (configs committed with repos) and workflow simplicity (one Git knob instead of SSH rewrites).

The technical merits of both approaches have been thoroughly aired in the thread, with Jeff King (Peff) and brian m. carlson demonstrating sophisticated solutions using existing Git features (`includeIf`, `url.<URL>.insteadOf`). Wesley acknowledges these work but finds them less elegant than his proposed solution. The discussion has reached a point where further technical debate seems unlikely to shift positions - what's needed is either a clear demonstration of unmet needs in real workflows, or a maintainer decision about whether Git's scope should expand to include this SSH configuration.
