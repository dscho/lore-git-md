This is a feature proposal for per-remote SSH configuration in Git, with Wesley Schwengle responding to Johannes Sixt's critique of the approach. The discussion remains at an impasse between two perspectives: Wesley advocates for version-controllable Git-native SSH configuration while Hannes maintains existing SSH host aliases are sufficient.

Wesley clarifies his position by emphasizing that SSH configuration (even per-user) requires configuring SSH to work around Git's limitations, which he considers architecturally backwards. He provides concrete use cases: freelancers managing multiple client identities and projects like myrepos/metacpan where URL rewriting would be needed. His key argument is that Git should own Git-specific connection configuration rather than delegating to SSH workarounds.

The response introduces new technical context about Wesley's personal workflow - a zsh script that previously implemented similar functionality by parsing Git config to construct `core.sshCommand`. This patch series would eliminate such scripting needs. Wesley frames the feature as particularly valuable for multi-client freelancers who could use `includeIf` namespacing to manage identities without host aliases.

Notable is the philosophical divide in configuration approaches: Hannes/Peff/Junio favor minimalism and existing SSH capabilities, while Wesley prioritizes version control integration and declarative Git-native configuration. The "Why not both?" closing suggests Wesley sees room for coexistence, though previous reviews indicate maintainer resistance to duplicating SSH functionality within Git.

Key technical points remain unresolved: whether concrete examples demonstrate SSH config limitations sufficiently, and if version control benefits outweigh architectural concerns. The patch series' fate likely hinges on whether Wesley can provide compelling cases where current solutions fail in ways that justify expanding Git's configuration surface.
