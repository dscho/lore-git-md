This is a feature proposal (v3) from Pablo Sabater introducing a `--graph-lane-limit` option to constrain the width of `git log --graph` output. The patch series addresses terminal readability issues with wide commit graphs by truncating excess lanes while preserving key commit markers.

The v3 iteration responds to Junio Hamano's feedback by renaming the option from `--max-columns` to `--graph-lane-limit` and making it implicitly enable `--graph`. The implementation adds a `graph_max_columns` field to `struct rev_info` and modifies graph.c to replace hidden lanes with '.' characters while showing '*' for commits on the first hidden lane. The series includes thorough test cases demonstrating 2-3 lane limits with merge scenarios.

Key technical changes in v3:
- New option name: `--graph-lane-limit` (was `--max-columns` in v2)
- Implicit `--graph` enablement (per Junio's suggestion)
- Maintains core truncation behavior from v2
- Documents magic number calculations (2*lanes + 2 padding)
- Acknowledges information loss in truncation

The author raises two open design questions in the cover letter:
1. Whether to refactor graph.c's 17-year-old collapsing/merge lane handling to eliminate redundant lines in limited graphs
2. Whether collapsing/merge lanes to hidden branches remain useful when their connection points are obscured

Johannes Sixt has raised new concerns about the implicit `--graph` behavior potentially complicating future configuration and suggests alternative naming like `--edge-limit`. The patch appears well-constructed but the design discussion remains active regarding the UX implications of implicit behaviors and final naming.

The series touches graph.c, graph.h, revision.c, revision.h while adding tests in t4215-log-skewed-merges.sh. It represents a focused solution to the 2008 TODO about column limiting, though it deliberately does not implement gitk-style rearrangement. The author has been responsive to review feedback while maintaining the feature's utility for terminal viewing of complex graphs.
