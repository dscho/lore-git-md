RFC proposal from Mateo Patino (new contributor) exploring string handling optimizations, originally pitched as `STRBUF_INIT_CONST` macro for constant string initialization but now pivoting to propose a new `strview` struct for read-only string handling. This revives a concept with three prior failed attempts (2019-2021) to optimize strbuf usage, most recently noted by Patrick Steinhardt as #leftoverbit in 2025. 

The core challenge remains strbuf's API guarantee of writable buffers, which `STRBUF_INIT_CONST` would violate by pointing to read-only string literals. Eric Sunshine provided critical historical context that past submissions stalled because authors didn't address Jeff King's (Peff) 2020 architectural objection about this contract violation. 

Mateo's new proposal introduces a parallel `strview` struct (conceptually similar to C++'s `string_view`) to handle read-only strings without allocation, explicitly avoiding modification of strbuf's semantics. This represents a technical pivot from prior attempts by creating new infrastructure rather than modifying existing APIs. The approach would require new helper functions and careful naming to distinguish from strbuf utilities.

Key open questions: whether reviewers will accept this as a viable path forward given its indirect relationship to the original optimization goal, and whether the project wants to maintain two parallel string handling abstractions. The thread demonstrates growing understanding of Git's API design constraints while exploring alternative solutions to a long-standing challenge. Eric Sunshine and Jeff King's prior feedback remains highly relevant to evaluating this new direction.
