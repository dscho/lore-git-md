RFC proposal from Mateo Patino (new contributor) exploring string handling optimizations, originally pitched as `STRBUF_INIT_CONST` macro for constant string initialization but now pivoting to propose a new `strview` struct for read-only string handling. This revives a concept with three prior failed attempts (2019-2021) to optimize strbuf usage, most recently noted by Patrick Steinhardt as #leftoverbit in 2025.

Eric Sunshine responds to the `strview` proposal, arguing it solves a non-existent problem since Git already handles immutable strings via `const char*`. He identifies this as an XY Problem - focusing on `strview` rather than the original goal of safe string initialization with optional heap allocation. Sunshine proposes a simpler `struct str` alternative with explicit ownership tracking via a `free_me` flag, keeping the solution minimal (basic init/assignment functions only) while cleanly handling literal vs heap strings.

The core challenge remains strbuf's API guarantee of writable buffers, which prior attempts (including `STRBUF_INIT_CONST`) violated. Sunshine's counterproposal maintains Git's C idioms while addressing the memory management motivation, though it represents a third distinct approach after the original macro idea and Mateo's `strview` pivot. 

Key open questions now include: whether Sunshine's `struct str` approach will gain traction as a solution to the original optimization goal, and how it compares technically to the `strview` proposal. The thread demonstrates Git's preference for minimal, idiomatic C solutions over introducing new abstractions. Eric Sunshine and Jeff King's historical feedback continues to shape the discussion's trajectory toward solutions that respect existing API contracts.
