Thread identity: Bugfix for `git clone` addressing a segfault when using `--revision` with servers that ignore ref_prefixes filtering.

Core problem: When cloning with `--revision`, some servers (like Azure DevOps) may advertise more refs than requested, including HEAD. This leads to a NULL pointer dereference in `update_remote_refs()` when `remote_head_points_at->peer_ref` is accessed without checking for NULL.

Current status: Single patch version proposed, not yet merged. The fix modifies the guard condition in `update_remote_refs()` (in `builtin/clone.c`) to check both `remote_head_points_at` and `remote_head_points_at->peer_ref` before proceeding.

Key technical details: The bug manifests when:
1. Client requests specific refs via `--revision`
2. Server ignores ref_prefixes filter and advertises HEAD anyway
3. `update_remote_refs()` tries to access `peer_ref` without NULL check
The fix adds the missing NULL check while preserving existing behavior for well-behaved servers.

Open questions: None raised yet - the patch appears complete and well-tested with a reproduction case against Azure DevOps.

Participant positions: Initial patch from the author with no reviews yet. The straightforward nature of the fix (one-line change with clear explanation) suggests it may be picked up quickly.

Related work: This is a corner case in the clone machinery's interaction with non-compliant servers. Similar issues might exist elsewhere in the ref advertisement handling code, but this patch addresses the specific segfault case.
