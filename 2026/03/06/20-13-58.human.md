This is a performance question about `git fetch` behavior on slow network connections. R. Diez reports that `git fetch` takes unexpectedly long (25 seconds even when up-to-date, up to 30 minutes with changes) over a slow SMB/CIFS link to a filesystem-based repository, despite having tried parallel fetch with `--jobs=10`.

The key questions raised are: why does checking for updates take so long (suggesting it may be downloading large files unnecessarily), and whether parallel fetch can improve latency in this single-remote, no-submodules scenario (initial testing suggests not). The email seeks advice on optimizing fetch performance given these constraints.

The scenario touches on known challenges with filesystem-based repositories over high-latency network filesystems, though the specific 25-second baseline for no-op fetches seems unusually high. This may warrant investigation into whether Git is doing full object checks when it could use lighter-weight mechanisms. The parallel fetch question is reasonable but appears to be a dead end for this particular setup.
