This is a follow-up discussion about memory management in Git's mmap emulation layer, specifically regarding the behavior of `NO_MMAP` builds. Ramsay Jones clarifies his earlier comments about a historical bug where double calls to `munmap()` could lead to memory corruption when using the emulation layer (which uses `malloc`/`free` instead of actual mmap).

The key points are:
1. Ramsay explains that his earlier patch was purely illustrative - not meant to be merged - showing how the emulation layer could fail if code incorrectly called `munmap()` twice on the same region.
2. He notes that in normal mmap usage, double `munmap()` calls would return an error (EINVAL) but not crash, while the emulation layer would dangerously double-free the memory.
3. The discussion reveals that most Git code doesn't check `munmap()` return values, so such errors would typically go unnoticed.

This is background context rather than a patch proposal. Ramsay is providing historical perspective about edge cases in the mmap emulation that Jeff King's series (already reviewed and approved) helps address. The thread shows the project's attention to subtle memory management details across different platforms.
