This is a feature addition to the `git replay` command, introducing a `--revert` mode that allows reversing commits directly on bare repositories. The patch is now at v4 in its development cycle.

The implementation handles reverts as a distinct operation mode (mutually exclusive with `--onto` and `--advance`), preserving commit-by-commit reversal with individual messages that follow `git revert` conventions. The technical approach has been refined through discussion with key contributors like Phillip Wood, Patrick Steinhardt, and Junio Hamano.

In this email, Siddharth Asthana responds to Phillip Wood's review feedback on v3. Key changes being incorporated into v4 include:
- Restoring documentation about using `git merge-tree` for bulk reverts
- Changing the revert order to process commits newest-first (like `git revert` does) to reduce conflicts
- Using more realistic examples showing topic branch reverts
- Improving error message formatting for translation
- Clarifying the handling of empty revert commits (currently preserved for consistency with `git revert`)

The discussion also touches on broader interface questions about whether `git replay` should use subcommands (`revert`, `pick`, `rebase`) rather than flags, though there's consensus to defer that restructuring for now. The implementation itself is technically sound with thorough test coverage, and the maintainers appear engaged with both the details and broader design direction.

This patch series is primarily motivated by GitLab's Gitaly service needs, but the functionality is being designed as general-purpose infrastructure. The v4 iteration addresses several polish items while maintaining the core technical approach that has received significant review from domain experts.
