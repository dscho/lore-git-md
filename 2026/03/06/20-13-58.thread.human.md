This thread investigates surprisingly slow `git fetch` performance on SMB/CIFS network shares with asymmetric bandwidth (1 Mbps down/10 Mbps up). The discussion began when R. Diez reported 25-second delays for no-op fetches and up to 30-minute delays for small updates on a bare repository with no submodules.

Technical investigation revealed the bottleneck occurs during reference resolution, with `GIT_TRACE2` showing most time spent in `git-upload-pack` - including 13 seconds waiting on protocol flush packets and 7 seconds on tag peeling. brian m. carlson clarified that Git internally uses the upload-pack protocol even for local filesystem operations, explaining the observed behavior. While reftable was proposed as a solution (storing both peeled/unpeeled refs to avoid computation), R. Diez remains reluctant to adopt it despite brian m. carlson's assurance it will become default in Git 3.0.

The discussion has evolved into examining deeper protocol implementation choices. R. Diez challenges Git's sequential file operations as suboptimal for high-latency networks, contrasting with tools like rsync and GNU make that implement parallel I/O. He also questions whether SSH transport always requires a Git binary on the remote host. With his repository having no branches, previously suggested branch-specific fetch optimizations don't apply, keeping the discussion focused on fundamental protocol behavior and filesystem access patterns.

The thread now highlights a tension between Git's design assumptions (optimized for low-latency local access) and real-world high-latency network scenarios. While reftable remains the comprehensive solution, R. Diez continues exploring optimization possibilities within current constraints, suggesting the project should better document these performance characteristics to help users understand tradeoffs.
