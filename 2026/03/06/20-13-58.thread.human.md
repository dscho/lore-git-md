This thread investigates painfully slow `git fetch` operations over an SMB/CIFS network share with asymmetric bandwidth (1 Mbps down/10 Mbps up). The original report from R. Diez described 25-second delays for no-op fetches, with timing analysis revealing that nearly all the time is spent in reference resolution rather than object transfer. brian m. carlson has been the primary technical responder, identifying the 1Mbps download speed as a fundamental constraint but also pinpointing specific bottlenecks in how Git handles references.

The latest exchange clarifies several key technical points: the mysterious "0000" packet delay (13 seconds) is actually the protocol's flush packet indicating section boundaries, and the 7-second tag resolution overhead comes from runtime "peeling" (resolving tags to their targets). brian m. carlson explains why parallel fetch can't help with single remotes due to protocol design, and strongly recommends adopting the reftable backend - despite its "experimental" label in documentation - as it stores pre-peeled references and will become the default in Git 3.0. He suggests `git pack-refs` as a lighter alternative to full GC and offers to update the documentation about reftable's stability.

While the network speed remains a hard limit, the discussion has moved from diagnosis to actionable optimizations. The focus is now on reducing reference resolution time through backend improvements rather than protocol changes, with reftable adoption emerging as the most promising path forward despite initial reluctance from the original reporter. brian m. carlson's position is that the remaining optimizations are largely constrained by the physical network, but that the reference handling overhead can be substantially reduced with available tools.
