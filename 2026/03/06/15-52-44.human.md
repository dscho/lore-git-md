## Discussion on `git replay --revert` behavior

This is part of an ongoing discussion about the implementation of revert functionality in `git replay`, now at its fourth iteration. Phillip Wood responds to Siddharth Asthana's proposed changes from v3, focusing on two key behavioral aspects of the revert operation.

The first concerns commit ordering - Phillip agrees with Siddharth's solution to process reverts in chronological order (newest-first) rather than reverse chronological, which helps reduce conflicts. The implementation will chain reverts properly by using the last processed commit as a parent rather than falling back to the original branch tip.

The second point discusses empty revert commits. Phillip argues against Siddharth's current approach of preserving empty reverts (for consistency with interactive `git revert`), suggesting instead to drop them silently as `git cherry-pick` does. He notes this would be more practical for a non-interactive command like `replay`, though leaves the final decision to the patch author.

The exchange shows the patch nearing maturity, with Phillip's review focusing on subtle behavioral details after earlier rounds addressed core functionality. The technical approach has consensus from multiple maintainers, with interface design questions about subcommands vs flags being deferred for future work.
