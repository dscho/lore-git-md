This is a documentation clarification from Junio C Hamano regarding pathspec behavior in Git commands, particularly `git stash`. The email builds on earlier discussion about how `git stash push` interprets pathspecs relative to the current directory (matching `git status` behavior), while other stash subcommands like `list` misleadingly show pathspec-like options in their help text despite not actually supporting them.

Junio makes two key points: First, he observes that modern Git with pathspec magics like `:/` and `:(top)` has largely eliminated the need for commands to require top-level-relative pathspecs, except for commands that fundamentally cannot work from subdirectories. He notes that top-level-relative requirements would break shell tab-completion. Second, he suggests this would be a good opportunity for a community member (even a relatively new one) to audit commands for remaining top-level-relative pathspec requirements and propose documentation updates to standardize the wording.

The email also confirms Erik88's workaround for pathspec-based stash listing using `git log stash` with pathspecs, which remains the practical solution since `stash list` itself doesn't support pathspec filtering. This thread continues the project's ongoing effort to clarify and standardize documentation around pathspec behavior across commands.
