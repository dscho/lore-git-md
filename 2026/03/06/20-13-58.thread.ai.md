Thread summary:

Performance investigation into slow `git fetch` operations over SMB/CIFS network share with asymmetric bandwidth (1 Mbps down/10 Mbps up). The repository has a single origin with no submodules. Reported symptoms include 25-second delays for no-op fetches and up to 30-minute delays for small updates. 

Key technical aspects:
- Remote repository confirmed bare, with bottleneck in reference resolution phase
- `GIT_TRACE2=1` output shows 23.7 of 24 seconds spent in `git-upload-pack` child process
- Packet-level breakdown reveals:
  - 13 seconds spent on "0000" flush packet (end-of-section marker in Git protocol)
  - 2 seconds on HEAD/master ref resolution
  - 7 seconds on tag peeling (resolving tag objects to targets)
- Parallel fetch (`--jobs=10`) confirmed ineffective for single-remote scenarios due to protocol design requiring sequential reference negotiation (brian m. carlson)
- Filesystem remote fetch process involves reading remote references followed by history walk
- Technical recommendations now include:
  - `git pack-refs` (lighter alternative to full GC)
  - Reftable backend adoption (stores both peeled/unpeeled refs to avoid runtime computation)
- brian m. carlson clarifies reftable is stable despite "experimental" label in docs, will be default in Git 3.0
- Original poster R. Diez reluctant to use experimental reftable backend despite potential benefits
- brian m. carlson's analysis confirms 1Mbps download as fundamental constraint

Open questions and next steps:
