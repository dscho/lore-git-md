This is a technical review from Jeff King (Peff) on Wesley Schwengle's patch series introducing per-remote SSH configuration options. Peff raises architectural concerns about the current approach of plumbing the remote name down to `git_connect()`, suggesting it may be too low-level and inflexible for future needs like command-line overrides.

Peff proposes an alternative design where higher-level commands would construct an `ssh_options_context` struct containing all SSH-related configuration (from both command line and config), which would then be passed down to the connection layer. This would provide more flexibility than the current patch's approach of just passing the remote name.

The review also notes that much of the functionality being proposed might already be achievable through SSH host aliases in `~/.ssh/config`, which has been discussed elsewhere in the thread. Peff indicates he'll review that discussion before commenting further on the feature itself.

This is a substantive technical review that doesn't reject the feature outright but suggests a more robust architectural approach. The feedback focuses on maintainability and future extensibility rather than immediate functionality. The proposed `ssh_options_context` struct would represent a more comprehensive solution that could accommodate both the current per-remote configuration needs and potential future requirements like command-line overrides.

Key files affected by this discussion would be connect.c, transport.c, and the config parsing infrastructure. The review doesn't address the test changes from the original series but focuses on the core architectural question of how SSH configuration should flow through Git's transport layer.
