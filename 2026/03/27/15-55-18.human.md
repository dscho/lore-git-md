This is a const-correctness follow-up in the ongoing discussion about handling string literals in revision parsing. The email exchange between Jeff King and Junio Hamano confirms their agreement on the technical approach for `handle_dotdot()` in `revision.c`.

The key takeaway is that they've settled on using `xmemdupz()` to create copies of range operator strings (like ".." and "...") rather than modifying them in-place. While Junio initially had reservations about the allocation overhead, he now acknowledges this as the correct solution. Jeff King notes that alternative approaches - either removing `const` from the interface or switching to ptr/len pairs - would create more problems than they solve.

This discussion represents the final alignment between maintainer and contributor on how to properly handle const strings in this part of Git's codebase. The solution maintains functionality while properly respecting const semantics and memory management, setting a pattern for similar cases elsewhere. The changes affect core revision parsing logic but should be transparent to end users.
