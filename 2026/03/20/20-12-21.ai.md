This is a maintainer response in a thread about refactoring branch interpretation flags into an enum type. Junio Hamano clarifies that the bitmask behavior (using `1 << n` values) in Jialong Wang's enum conversion is intentional and necessary, not accidental complexity as Karthik Nayak's review had questioned.

Junio points to the `branch_interpret_allowed()` function's implementation as evidence that the flags are indeed designed to be combinable (non-mutually-exclusive), allowing expressions like `INTERPRET_BRANCH_LOCAL | INTERPRET_BRANCH_HEAD`. He emphasizes that preserving the original bitmask behavior was the correct approach for this refactoring, as changing the values would constitute a separate, more invasive change rather than just a type safety improvement.

The response settles the technical question raised in Karthik's review, confirming that the enum values must maintain their bitmask properties to preserve existing functionality.
