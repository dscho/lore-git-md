This is a maintainer response to a documentation patch that has already been addressed. Junio C Hamano explains that sending a patch to revert a change that was never merged is unnecessary - the preferred workflow is to simply rebase the series to remove the unwanted change rather than adding a revert commit. 

The context is a Google Summer of Code participant's patch series for `git bugreport` documentation. The student had previously sent a version (v2) that added a description to the usage string, which Junio clarified should only contain syntax, not descriptions. The v3 patch properly removed that addition, but Junio notes that sending a standalone revert wasn't needed since the incorrect version was never merged.

Junio takes the opportunity to explain Git's patch submission philosophy: contributors should use interactive rebase to present a clean series that appears to make logical, incremental progress, rather than showing intermediate missteps. If following this approach leads to an empty patch (because all changes were removed), that's acceptable - a simple note retracting the earlier version suffices.

This email serves as both a workflow lesson for this specific case and general guidance for all contributors on maintaining clean patch series. No further action is needed on the technical content, as the documentation convention question was already settled.
