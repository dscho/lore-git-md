This is a maintainer guidance email from Junio Hamano to a GSoC participant about patch submission practices, following up on a documentation patch thread.

Junio explains that sending a patch to revert an unmerged change is unnecessary - the preferred workflow is to use `git rebase -i` to edit the patch series into a clean sequence before sending, even if that means some intermediate versions disappear entirely. He notes that an empty patch (resulting from removing all changes that were rejected) is acceptable, and in such cases a simple note retracting the earlier patch would suffice.

The email serves as a teaching moment about Git's contribution norms, emphasizing the value of presenting a clean history rather than documenting every intermediate step. While the technical content of the original documentation patch was already settled (usage strings should show only syntax, not descriptions), this follow-up addresses the process aspect of how to handle rejected changes in future contributions.

Junio's tone is constructive and explanatory, typical of his maintainer guidance to new contributors. The email closes the thread definitively by establishing that no further action is needed on the reversion patch itself, while providing generally applicable advice about patch submission discipline.
