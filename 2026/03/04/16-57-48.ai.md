This is a bugfix targeting the promisor-remote subsystem, addressing a recursive lazy-fetch issue that can lead to runaway resource consumption. The patch comes with a new test case to verify the fix.

The core problem occurs when `fetch_objects()` spawns a child `git fetch` for lazy fetching, and that child's index-pack` encounters a REF_DELTA against a missing base object. Currently, the child process can recursively trigger another lazy fetch, creating an unbounded chain of fetches. The author reports seeing this in production with severe consequences - 276GB of promisor packs written in 90 minutes due to recursive fetches.

The fix is straightforward: propagate the existing `GIT_NO_LAZY_FETCH=1` environment variable into the child fetch's environment. This prevents the recursion while still allowing the initial lazy fetch to proceed. The commit message provides detailed technical justification, noting that with noop negotiation, servers shouldn't send problematic deltas in the first place, and if they do, recursion wouldn't help anyway.

The patch adds a new test script that verifies two key behaviors: that only one fetch subprocess is spawned during a lazy fetch operation, and that the child process environment contains the expected `GIT_NO_LAZY_FETCH=1` setting. The test uses a reference-transaction hook to inspect the child's environment.

This appears to be a well-crafted fix for a real-world issue, with thorough explanation in the commit message and appropriate test coverage. The change is minimal (a single line addition plus test infrastructure) and the author has cited prior related fixes (e6d5479e7a, 3a1ea94a49) to establish context. The patch follows Git's standard patterns for environment variable handling and process spawning.
