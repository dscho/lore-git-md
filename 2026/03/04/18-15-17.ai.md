This is a bugfix patch in the fsmonitor daemon series, specifically addressing a potential hang condition when waiting for inotify cookie events. The patch introduces a timeout mechanism for the cookie synchronization in the fsmonitor daemon.

The core change replaces an infinite `pthread_cond_wait()` with a 1-second timeout using `pthread_cond_timedwait()`. This prevents indefinite hangs when filesystems (particularly certain container/overlay filesystems) successfully register inotify watches but fail to deliver events. When the timeout occurs, the daemon will report an error and allow the client to proceed with a full scan rather than blocking forever.

The implementation:
- Uses `gettimeofday()` to calculate the timeout timestamp
- Maintains the same locking behavior but with timeout capability
- Preserves all existing error handling paths
- Adds trace logging for timeout events
- Keeps the same memory management and cleanup patterns

This patch is part of the larger fsmonitor Linux inotify support series (v8 04/12) and addresses a specific reliability concern raised during testing. The change is particularly important for containerized environments where filesystem event delivery can be unreliable. The 1-second timeout value appears to be a practical choice, though Patrick Steinhardt has questioned whether this duration is optimal (an open question in the thread).

The patch builds on previous work to make the fsmonitor daemon more robust, including earlier fixes for memory leaks and race conditions. It represents a focused improvement to one component of the larger fsmonitor implementation rather than introducing new functionality.
