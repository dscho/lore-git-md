Thread identity: Bugfix for promisor-remote subsystem addressing recursive lazy-fetch issue that can cause runaway resource consumption (276GB of promisor packs written in 90 minutes in production).

Core problem: When `fetch_objects()` spawns a child `git fetch` for lazy fetching, and that child's `index-pack` encounters a REF_DELTA against a missing base object, it can recursively trigger another lazy fetch, creating an unbounded chain of fetches. Patrick Steinhardt questions whether the root cause might involve servers sending invalid packfiles rather than being purely a client-side issue.

Current status: Patch v2 incorporates Junio's feedback by moving tests into existing infrastructure while maintaining the technical solution - propagating `GIT_NO_LAZY_FETCH=1` into child fetch processes to prevent recursion. Patrick has raised new concerns about whether this addresses a server protocol violation rather than a client bug, asking for clarification of the failure scenario and test coverage.

Key technical details: Single-line change to propagate environment variable in `fetch_objects()`. Tests in `t0411-clone-from-partial.sh` verify: (1) only one fetch subprocess spawned during lazy fetch, (2) child process environment contains `GIT_NO_LAZY_FETCH=1`. Patrick requests the test demonstrate the failure mode rather than just checking the environment variable, and questions whether standard git-upload-pack would ever generate the problematic case. Justification notes that with noop negotiation, servers shouldn't send problematic deltas, but Patrick probes whether this assumes standard server behavior.

Open questions: Patrick has raised whether this is addressing a server protocol violation rather than client bug, and whether the test sufficiently demonstrates the failure mode. Needs clarification on whether servers involved in production incident were using standard git-upload-pack or custom implementations.
