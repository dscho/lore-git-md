This is a bug report thread about `git grep` behavior, where Randy Dunlap confirms the resolution of his issue with helpful explanations from Jeff King and Junio C Hamano. The key takeaway is that Randy's original problem stemmed from using `git apply` (which leaves files untracked) rather than `git am` (which creates commits and tracks changes). 

Randy acknowledges this as user error, noting the important distinction between these two commands. The thread serves as a good reminder that `git grep` by default only searches tracked files, and that patch application method affects file tracking status. While not introducing new technical depth, it reinforces best practices around patch application workflows, with `git am` being the preferred method for applying patches from email while preserving commit metadata. The exchange is a clean resolution to what turned out to be a user education issue rather than a Git bug.
