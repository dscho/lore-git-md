This is a troubleshooting thread about unexpected `git grep` behavior, where Junio C Hamano provides a key insight. The thread started with Randy Dunlap reporting that `git grep` failed to find a string that should have been present after applying a patch to the Linux kernel tree. Jeff King had suggested two possible explanations (failed patch application or subdirectory search scope), which Randy ruled out.

Junio now identifies the likely issue: Randy used `git apply` without `--index`, which leaves the new file in an "untracked" state that `git grep` ignores by default. This explains the discrepancy between Randy's experience and Jeff's successful reproduction - Jeff presumably used `--index` or another method that staged the change. The thread demonstrates Git's sometimes subtle distinctions between working directory state and index state, with Junio's response pinpointing the specific behavioral nuance at play. The solution would be to either use `git apply --index` or explicitly tell `git grep` to search untracked files with `--no-index`.
