This is a technical discussion thread about optimizing `git fetch` performance on slow network links, specifically focusing on reference resolution bottlenecks.

brian m. carlson responds to R. Diez's concerns about slow fetch operations over an SMB/CIFS share with asymmetric bandwidth (1Mbps down/10Mbps up). The key points center around reference handling optimizations. The discussion reveals that 13 seconds of the 24-second fetch time is spent on the initial reference advertisement phase, with 7 seconds specifically on tag resolution.

The email clarifies several technical points: the meaning of "0000" packet in Git's protocol (a flush packet indicating end of section), why parallel fetch doesn't help with single remotes (the protocol design requires sequential reference negotiation), and how tag peeling (resolving tag objects to their targets) contributes to the delay. brian m. carlson strongly advocates for the reftable backend despite its "experimental" label in documentation, noting it's stable and will be default in Git 3.0, and explains how it stores both peeled and unpeeled references to avoid runtime computation.

The technical limitation remains the 1Mbps download speed, but the discussion suggests concrete optimizations: using `git pack-refs` (lighter than full GC) and adopting reftable to reduce filesystem operations. The thread shows a shift from diagnosis to practical solutions, with brian m. carlson offering to update the misleading documentation about reftable stability. The core takeaway is that while protocol-level parallelization isn't feasible, backend optimizations could significantly improve the reference resolution phase that's currently dominating the fetch time.
