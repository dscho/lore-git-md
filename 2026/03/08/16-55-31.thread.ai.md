Git quiltimport shell script bugfix addressing edge cases in patch subject handling. Original patch from Sasha Levin fixed two issues: replacing `echo` with `printf '%s\n'` to prevent backslash interpretation in patch subjects (which could produce invalid NUL bytes rejected by `git commit-tree`), and adding quotes around `$tmp_dir` to properly handle paths. Changes were limited to the script's internal handling with no user-facing behavior changes for normal cases.

Sasha Levin acknowledges Ben Knoble's review feedback and plans to send a v2 incorporating several improvements: splitting the quoting changes into a separate cleanup patch, using POSIX shell parameter expansion (${var%.patch}) instead of `sed` for removing `.patch` suffixes, and adding more detail to the commit message about how `git commit-tree` rejects NUL bytes (with an example from the Linux kernel stable queue where this was hit in practice).

Junio C Hamano raises an important concern about the change from `echo` to `printf` - while it prevents NUL byte issues, it also removes the whitespace normalization that unquoted `echo $patch_name` was unintentionally performing (collapsing multiple spaces into one). Sasha clarifies that `patch_name` comes from a `read` operation that splits on whitespace, so it normally cannot contain internal spaces unless explicitly escaped with backslashes in the input file. This means the whitespace normalization Junio was concerned about would only affect intentionally escaped spaces, not typical cases.

The discussion reveals subtle interactions between shell parsing rules and Git's expectations, with the script needing to handle both intentional escaping (where backslashes should be preserved) and accidental malformed input (where NUL bytes must be prevented). Sasha acknowledges the need to reword the commit message to clarify that echo's backslash interpretation behavior varies by shell implementation (dash does it by default while POSIX leaves it implementation-defined). The changes address real but rare edge cases that could affect users, particularly those importing patches with backslashes in subjects or working in paths with spaces. Open questions remain about how to best balance these requirements while maintaining compatibility with different shell implementations and existing behavior patterns. This exemplifies Git's standards for script robustness and backward compatibility, with careful consideration of subtle behavior changes.
