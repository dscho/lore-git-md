This thread addresses a long-standing const-correctness issue in Git's patch-id subsystem, where the hashmap API's const requirements conflict with the lazy initialization pattern used for patch ID computation. Tian Yuchen initially proposed mechanical const fixes, but maintainer Junio Hamano identified a deeper design tension between type safety and performance optimizations.

After discussion, Yuchen has submitted a v2 patch that takes a pragmatic approach: rather than restructuring the code, it documents why the const-cast in `patch_id_neq()` is necessary to maintain the lazy evaluation optimization. The patch removes an 8-year-old NEEDSWORK comment and replaces it with a clear explanation of the trade-off - preserving performance requires this intentional violation of strict const-correctness, as pre-computing all patch IDs would be too costly.

The solution focuses on `patch-ids.c`, where the `patch_id_neq()` function uses `container_of()` to cast away const when calling the modifying `commit_patch_id()`. The new documentation makes this operation explicit and justified, representing a reasonable compromise that maintains current performance while providing clarity about the design constraints. This approach appears likely to be accepted, as it resolves the issue without requiring invasive changes to either the patch-id or hashmap subsystems.
