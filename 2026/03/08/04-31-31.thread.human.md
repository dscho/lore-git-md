This thread addresses a long-standing const-correctness issue in Git's patch-id subsystem, specifically around the `patch_id_neq()` function which had carried an 8-year-old NEEDSWORK comment. The core tension was between maintaining proper const-correctness in the hashmap API (which requires const parameters for comparison functions) and preserving the lazy evaluation optimization in `commit_patch_id()` (which needs to modify objects).

After initial discussion, Tian Yuchen submitted a v2 patch that replaced the NEEDSWORK comment with detailed documentation explaining the deliberate const-cast as a necessary trade-off between type safety and performance. Junio Hamano reviewed this approach positively but requested more precise wording in the documentation to specifically tie the optimization to rebase operations (referencing commit b3dfeebb from 2016) rather than presenting it as a generic performance benefit.

In the latest email, Yuchen acknowledges Junio's feedback and agrees to incorporate the suggested phrasing in a v3 patch. This will be the final step before the change can be merged, as the technical approach using `container_of()` for an explicit, justified const-cast has already been approved. The solution preserves the existing lazy evaluation optimization that avoids unnecessary patch ID computations during rebase operations while properly documenting the design compromise.

The thread demonstrates how Git handles cases where strict type safety conflicts with performance optimizations, providing a well-documented precedent for similar situations. With only minor documentation polish remaining, this long-standing issue appears ready to be closed after eight years.
