Thread summary:

Bug report from Randy Dunlap about `git grep` failing to find a string ("vma_area_desc") in the Linux kernel repository after applying a patch. Initial hypotheses from Jeff King (Peff) considered patch application issues or incorrect grep invocation, but Randy confirmed clean patch application and root-level execution. Junio C Hamano identified the root cause: Randy used `git apply` without `--index`, leaving the file untracked and thus excluded from `git grep`'s default search scope. Jeff King's follow-up elaborates on the behavioral differences between `git apply` (working tree only) and `git am` (creates commits), recommending `git am` as the preferred workflow since it automatically stages changes while preserving commit metadata. The discussion reveals important nuances in Git's handling of tracked vs untracked files during grep operations, with resolution options being either `git apply --index` to stage changes or `git grep --no-index` to include untracked files. Technical details include the search string typo ("vma_area_desc" vs correct "vm_area_desc"), confirmation of proper grep invocation from repository root, and the critical interaction between patch application mode and grep's default behavior. The thread demonstrates precise troubleshooting of Git's edge cases, with Junio's technical diagnosis and Jeff's workflow advice providing both explanation and practical resolution.
