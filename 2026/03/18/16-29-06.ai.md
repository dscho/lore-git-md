This is a follow-up discussion on Lorenzo Pegorari's GSoC proposal about configurable fetch ordering for promisor remotes in partial clones. Lorenzo responds to Christian Couder's technical review, incorporating feedback and clarifying aspects of the proposal.

Lorenzo acknowledges several technical corrections from Christian regarding how promisor remotes and lazy fetching actually work - notably that lazy fetches don't use filters (unlike initial partial clones/fetches) and that promisor-remote capability is tied to filter usage rather than server object presence. He plans to update the proposal to reflect these distinctions.

The exchange confirms key design decisions: using `remote.<name>.priority` (simpler than original `promisorPriority` name) with a fixed 1-100 range (rather than system-dependent `UCHAR_MAX`), and sticking with global priorities rather than per-server contexts since lazy fetches aren't server-specific. Lorenzo agrees with Christian that the edge case requiring per-server priorities is too unusual to warrant implementation complexity.

Lorenzo also notes he'll fix minor formatting issues (stray LaTeX markup and typos) in the proposal before submitting it officially to GSoC. The discussion shows good technical engagement - Lorenzo demonstrates understanding of Christian's points and the proposal is being refined through this review process. The core approach remains sound, with the implementation details now better specified based on Christian's experience with the promisor remote subsystem.
