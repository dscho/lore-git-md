This thread began with Randy Dunlap reporting that `git grep` failed to find a string in the Linux kernel repository after applying a patch. Jeff King and Junio C Hamano diagnosed the issue: Randy had used `git apply` without `--index`, leaving the file untracked and thus outside `git grep`'s default search scope. The discussion revealed important nuances in how Git handles tracked versus untracked files during grep operations, with solutions being either staging changes via `git apply --index` or using `git grep --no-index` to include untracked files.

Randy has now confirmed the resolution, acknowledging this was user error rather than a Git bug. The thread serves as a clear example of how patch application method affects file tracking - `git am` (which creates commits) would have avoided the issue entirely by automatically tracking changes. While no new technical ground was broken, the exchange provides a concise lesson in Git's patch application workflows and the importance of understanding command defaults. The experts' explanations transformed what initially appeared to be a bug report into a valuable learning opportunity about Git's internals.
