This thread began with Randy Dunlap reporting that `git grep` failed to find a string in the Linux kernel repository after applying a patch containing that string, despite the string being visibly present in the file. Initial troubleshooting by Jeff King (Peff) considered patch application issues and grep invocation location, but Randy confirmed he'd applied the patch cleanly and was running grep from the repository root.

Junio C Hamano identified the root cause: Randy had used `git apply` without `--index`, leaving the patched file in an untracked state that `git grep` ignores by default. Jeff King's follow-up elaborated on this, explaining the behavioral differences between `git apply` (which only modifies working tree files) and `git am` (which stages changes and creates commits). Jeff recommended either staging the file manually with `git add` or - more efficiently - using `git am` directly to handle patching and staging in one step while preserving commit metadata.

The discussion highlights how subtle command variations (`apply` vs `am`) can produce confusing results when combined with grep's default behavior. While the immediate solution is to either use `--index` with `apply` or switch to `am`, the thread also serves as a useful case study in Git's handling of tracked versus untracked files during search operations. The resolution underscores the importance of understanding these workflow nuances and the value of tools like `am` that handle multiple steps correctly by default.
