Jayesh Daga has proposed an RFC to extend `git repo info` with additional path-related metadata, specifically `paths.common_dir` and `paths.toplevel`. The key design question is whether these paths should be output as relative (matching Git's existing conventions in commands like `git rev-parse`) or absolute (which would be more explicit but less portable between systems). Jayesh suggests defaulting to relative paths for consistency, with an optional `--absolute` flag for cases where unambiguous paths are needed.

This is currently in the design discussion phase, with the author explicitly seeking feedback before implementing. The change would affect how tools and scripts consume repository path information, so getting the design right is important for maintaining compatibility. We can expect responses from contributors familiar with Git's path handling in plumbing commands to weigh in on the relative vs. absolute path question. The proposal appears well-considered, balancing existing conventions with practical needs for unambiguous paths when required.
