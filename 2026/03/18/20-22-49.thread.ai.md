Gitweb security fix for hash parameter interpretation, originally reported by Nicolas George. The issue involves gitweb's `hb` parameter potentially being misinterpreted as a command-line option when starting with a dash (e.g. `hb=-c`), causing `git ls-tree` to parse it incorrectly. While not currently exploitable, this could become a security issue if new options are added to `ls-tree`.

The initial proposed fix was to add a double-dash (`--`) before the hash parameter to prevent option parsing. However, Junio C Hamano has raised concerns about this approach, noting that `--` traditionally signals the end of options and start of pathspecs in Git commands, suggesting `--end-of-options` might be more appropriate if forcing tree object parsing is desired. Junio also questions whether the behavior is truly a bug that needs fixing, characterizing invalid hash inputs as "garbage-in garbage-out", though he acknowledges that relaying client-caused errors back to the client rather than logging them server-side would be more appropriate.

The discussion has expanded beyond the immediate gitweb fix to consider deeper design questions about command-line parsing semantics in Git, particularly around how `ls-tree` and other commands should interpret arguments. The thread now appears to be considering both the specific gitweb case and potential broader implications for Git command behavior. The original suggestion to audit gitweb for similar parameter-passing patterns remains relevant, but the solution approach may need to account for these newly raised concerns about proper argument parsing semantics.
