This is a follow-up in the ongoing discussion about standardizing help flag behavior in Git's option parsing. brian m. carlson responds to Jeff King's analysis of potential backward compatibility risks when changing `git rev-parse --parseopt` to exit with status 0 (success) rather than 129 (error) for help requests.

The email provides concrete examples of how scripts might currently use `-h` flags, including an alias that checks for option support by grepping help output. brian m. carlson notes that most such uses would be unaffected by the exit code change, either because they're in pipelines (where only the last command's exit status matters by default) or because they already handle the unexpected 129 status. They argue that any scripts that do depend on the current behavior likely represent poor design that should be fixed regardless.

The response aligns with and reinforces Peff's earlier conclusion that the change carries minimal risk. brian m. carlson explicitly supports treating this as a bug fix that could ship before Git 3.0, noting that users are more likely to welcome the change than be disrupted by it. This moves the discussion toward implementation, with both technical analysis and community sentiment now clearly supporting the standardization effort.
