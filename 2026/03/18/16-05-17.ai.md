This is a review response from Junio C Hamano on Pablo Sabater's v2 patch adding graph column limiting. The maintainer raises several substantive concerns about the design and naming of the `--max-columns` option.

Junio questions whether the option name clearly indicates it affects only the graph portion of the output, suggesting alternatives like `--limit-graph-columns` or `--limit-graph-lanes`. He notes the current name could mislead users into thinking it controls total output width. The implementation's magic numbers in the column calculation also need better explanation.

The review points out that the "no information is lost" claim is overstated since ancestry lines are truncated. Junio also suggests the option could implicitly enable `--graph` rather than erroring when used alone, given its graph-specific nature.

Technical details discussed include:
- The actual column count calculation (2 columns per lane plus 2 padding)
- Whether to keep the 2008 TODO about gitk-style rearrangement
- Error handling when used without `--graph`
- Magic number explanation needs in the code

This moves the discussion forward by:
- Challenging the option naming convention
- Requesting better code documentation
- Questioning the user experience of requiring explicit `--graph`
- Noting the information loss from truncation vs gitk's approach

The patch remains technically sound but now faces higher-level design questions from the maintainer about naming and user expectations. Pablo will need to address these concerns in a v3 iteration.
