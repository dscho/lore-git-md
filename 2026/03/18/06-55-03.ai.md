This is an RFC (Request for Comments) about path representation in a proposed extension to `git repo info`, part of an ongoing effort to expose more repository metadata. The patch comes from Jayesh Daga, who is working on adding path-related information like `paths.common_dir` and `paths.toplevel` to the command's output.

The core question is whether these paths should be shown as relative (matching `git rev-parse`'s behavior) or absolute (more explicit but less portable). The author suggests defaulting to relative paths for consistency with existing Git conventions, with an optional `--absolute` flag for cases where unambiguous paths are needed. This appears to be a thoughtful approach that balances compatibility with flexibility.

The patch is clearly framed as a design discussion rather than a final implementation, and the author is seeking feedback before proceeding. This is exactly how RFCs should work - surfacing architectural questions early. The change would affect how scripts and tools consume repository path information, so getting this right matters for backward compatibility. The thread will likely draw responses from contributors familiar with path handling in Git's plumbing commands.
