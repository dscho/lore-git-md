This is a follow-up discussion about the gitweb security fix for hash parameter interpretation. Junio C Hamano responds to Nicolas George's original report, offering additional technical perspective on the issue.

Junio questions whether the behavior is truly a bug that needs fixing, characterizing it as "garbage-in garbage-out" since invalid hashes already produce error messages. He notes that suppressing these errors might require redirecting stderr, which isn't necessarily the right approach. However, he acknowledges that relaying client-caused errors back to the client rather than logging them server-side would be more appropriate, though harder to implement.

The response introduces a new technical nuance: Junio argues that using `--` to force interpretation as a tree object name might itself be incorrect, since `--` traditionally signals the end of options and start of pathspecs in Git commands. He suggests `--end-of-options` would be a more durable solution if forcing tree object parsing is desired.

This moves the discussion beyond the immediate fix, raising questions about proper command-line parsing semantics in Git. Junio's comments suggest the issue touches on deeper design questions about how Git commands should interpret arguments, making this more than just a simple gitweb bugfix. The thread now appears headed toward considering both the immediate gitweb case and potential ls-tree behavior changes.
