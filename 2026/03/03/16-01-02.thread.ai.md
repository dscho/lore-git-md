Thread identity: Discussion about the deprecated `git whatchanged` command, initiated by Antoine Cousson, with responses from Kristoffer Haugsbakk and Junio C Hamano.

Core problem or goal: Clarifying the deprecation and removal timeline for `git whatchanged` (marked as deprecated) and documenting exact `git log` equivalents for its file modification output format. The thread explores whether the deprecation warning was sufficiently visible and if `git log` defaults could better serve this use case.

Current status: Kristoffer Haugsbakk clarifies the removal will occur in Git 2.52 or later (correcting Junio's earlier mention of Git 3.0), with deprecation warnings already present in Git v2.51.1. Two replacement options remain valid: `git log --stat` for a summary view and `git log --raw --no-merges` for exact output matching whatchanged (including hexadecimal object names). The deprecation was documented in BreakingChanges but may not have been prominent enough.

Key technical details: Both commands use the same diff machinery but with different defaults. `git whatchanged` implicitly shows file modifications per commit without merge commits, while `git log` requires explicit flags. The `--raw` output provides exact compatibility but includes hexadecimal object names that Junio describes as "ugly hexadecimal gibberish." This is part of Git's ongoing interface consolidation where redundant commands are removed in favor of configurable `git log`.

Open questions: Should the deprecation warning have been more visible? Are there plans to make `git log` defaults more aligned with this common use case? The accelerated removal timeline (2.52 vs 3.0) may affect migration planning. Maintainer responses suggest no reconsideration of the deprecation path is planned.

Participant positions: Antoine Cousson initiated with appreciation for whatchanged's behavior. Kristoffer Haugsbakk provided authoritative documentation of the deprecation plan and version specifics, correcting the timeline. Junio C Hamano confirmed the removal direction and offered pragmatic replacement suggestions while expressing personal preference for `--stat` output.
