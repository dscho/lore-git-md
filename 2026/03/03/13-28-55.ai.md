This is a performance optimization discussion in the ongoing hook subsystem improvements, specifically addressing a regression in `git-receive-pack`'s sideband hook handling. Jeff King (Peff) is responding to Adrian Ratiu's patch that restored an optimization where sideband hooks would early-exit if no hook exists, avoiding unnecessary async thread creation.

The key technical point is that while the patch correctly uses `hook_exists()` (which checks both config-defined and traditional hooks), there remains some inefficiency in how hooks are looked up twice - once for the existence check and again when actually running the hook. Peff suggests a potential reorganization using `HOOK_INIT` and `load_hooks()` to avoid this, but acknowledges it may not be worth the complexity given the current caching behavior.

The discussion reveals deeper context about the hook subsystem's evolution - the new API already caches config-based hooks but still does fresh `access()` checks for filesystem hooks on each lookup. While this could theoretically be optimized further (especially for hooks like "update" that run per-ref), Peff notes this isn't new to Ratiu's changes and hasn't been a noticeable performance issue in practice.

This email doesn't introduce new changes but provides valuable technical insight into tradeoffs in the hook subsystem design. It suggests future optimization opportunities while affirming the current patch's approach as reasonable. The thread shows consensus on the immediate fix while leaving door open for deeper refactoring if profiling reveals the double-lookup becomes problematic.
