Patrick Steinhardt responds to Alan Braithwaite's proposed configuration design for partial clone filters, suggesting a narrower scope focused solely on initial clone operations rather than affecting subsequent fetches.

The key technical point is a proposed alternative configuration structure using `clone.<url>.defaultObjectFilter` instead of the more general `fetch.partialCloneFilter` approach. Patrick argues this better matches the intended use case since converting an existing full clone to a partial one requires additional consideration beyond simple configuration.

This represents a significant design divergence from Alan's proposal, which aimed to provide both global defaults and URL-specific overrides while maintaining compatibility with existing fetch operations. Patrick's position reflects concerns about the safety and implications of automatically applying filters to fetches in established repositories.

The exchange highlights an ongoing tension in the thread between configurability flexibility (Alan's approach) and operational safety (Patrick's position). This reply moves the discussion toward defining clearer boundaries for when and how these filters should apply, with Patrick advocating for a more conservative initial implementation focused solely on clone operation configuration.
