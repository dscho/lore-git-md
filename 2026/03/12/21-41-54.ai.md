This is a bug report for the remote-object-info feature in `git cat-file --batch-command`, which is part of a security-focused series enabling remote object metadata queries. Pablo Sabater identifies a critical issue where stale type information from a previous local query persists and corrupts subsequent remote queries, causing incorrect object type reporting without any error indication.

The bug manifests when mixing local info and remote-object-info commands in the same batch session - the `data->type` field retains its value from the local query and incorrectly applies it to remote objects. Sabater provides a concrete reproduction case showing a blob being misreported as a commit after querying a commit locally. This silent data corruption is particularly concerning as it undermines the security benefits of verifying object metadata before download.

The report confirms Jeff King's earlier suggestion about format string behavior - remote-object-info should return empty strings for unsupported fields (like objecttype) rather than propagating stale data. This aligns with ref-filter's handling of inapplicable but known fields. The issue appears specific to Eric's v11 implementation and doesn't affect the main series currently being finalized by Peijian Ju.

This represents a significant correctness issue that would need to be addressed before any version of remote-object-info could be considered production-ready, though it doesn't directly impact the v8 series under final review. The bug demonstrates the importance of proper state clearing between batch commands when mixing local and remote queries.
