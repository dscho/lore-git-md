This is a follow-up discussion in the ongoing thread about a `git clone` segfault when using `--revision` with non-compliant servers. The original patch added NULL checks to prevent crashes when servers ignore ref filtering, but maintainer Junio C Hamano raised concerns about whether this addresses the deeper design issue in `guess_remote_head()`'s contract.

Adrian Friedli responds to Junio's questions by analyzing the three other callers of `guess_remote_head()`, noting that they all safely handle NULL `peer_ref` values. He points out that `get_expanded_map()` explicitly checks for NULL `peer_ref`, suggesting this is an expected case. For the clone path specifically, Adrian explains that without the `REMOTE_GUESS_HEAD_ALL` flag, `guess_remote_head()` returns only the most likely ref, implying the current behavior (returning a ref with NULL `peer_ref`) may be correct for this case.

The discussion is now focused on whether the fix should be the minimal NULL check (as originally submitted) or whether it should involve deeper changes to either make `guess_remote_head()` guarantee non-NULL `peer_ref` or have callers explicitly handle the NULL case. The exchange reveals that this edge case exposes broader questions about how Git should handle servers that don't strictly follow the expected protocol behavior.
