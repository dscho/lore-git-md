This is a performance optimization for `git push` from shallow clones, now expanded into a six-patch series at v3. The core goal remains the same: avoid resending the entire toplevel tree (gigabytes in large repos) when pushing from a shallow clone, but the series has grown to address edge cases and usability concerns raised during review. The new version introduces a tri-state config option, `push.shallowExcludeBoundary` (true/false/abort), improves error messages, and adds advice for recovering from incomplete pushes.

The first three patches are preparatory: they distinguish missing objects from type mismatches in `unpack-objects`, suppress repeated connectivity errors in `receive-pack`, and ensure shallow boundaries are rejected without disconnecting. These changes make the error handling more precise and user-friendly, which was a key concern in Stolee’s review of v2. The fourth patch (carried over from v2) implements the core optimization, now with a tri-state config that defaults to "false" (preserving historical behavior) for backward compatibility. The fifth patch argues for changing the default to "true" (the optimization), and the sixth adds advice for users to retry problematic multi-ref pushes separately.

The series touches `send-pack.c`, `receive-pack.c`, `unpack-objects.c`, `shallow.c`, and several test files, with thorough test coverage for edge cases like over-exclusion (where a rejected ref could incorrectly omit objects needed by an accepted ref) and the interaction with `receive.shallowUpdate`. The implementation is careful to only exclude shallow grafts reachable from the pushed refs, stopping early at commits the server already has to keep the walk short. The tri-state config allows users to opt out entirely ("abort") if they prefer not to choose between performance and correctness.

The discussion from v2 remains unresolved: Stolee’s concern about false-positive failures (rejecting valid refs) is now addressed with improved error messages and recovery advice, but the trade-off between performance and occasional failures is still contentious. The series does not adopt Patrick’s `push.negotiate=shallow` proposal or Stolee’s suggestion to repurpose `push.negotiate` for shallow repos, instead doubling down on the config-based approach with clearer documentation of the trade-offs. The new default ("false") is conservative, but the fifth patch makes a strong case for switching it to "true" in the future. This looks like a well-crafted solution to a real-world pain point, but the default change may still spark debate.
