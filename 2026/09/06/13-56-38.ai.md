This is an RFC proposing a new feature for `git clean`: persistent exclude patterns via configuration.

The patch introduces a new multi-valued configuration key `clean.exclude` that would act as if the patterns were passed via `git clean -e <pattern>` on every invocation. The patterns would persist across runs and continue to protect matching paths even when `git clean -x` is used. The configuration could be set globally or per-repository.

The motivation is to allow users to protect untracked but irreplaceable directories (e.g., local metadata, build artifacts that should not be removed) from accidental deletion during `git clean -fdx`, without having to remember to pass `-e` each time. This differs from `.gitignore` or `core.excludesFile`, which control what Git ignores during normal operations, whereas `clean.exclude` would specifically control what `git clean` should never remove.

The proposed design is a simple extension of the existing `-e` option, avoiding the need for a separate exclude file. The author suggests this aligns well with the current semantics of `git clean` and provides a clear use case for developers who want to safeguard certain untracked paths while still cleaning ignored files aggressively.

No implementation is provided yet—this is purely a design proposal to gauge interest and gather feedback on whether the feature would be welcome and whether the proposed configuration approach is appropriate. The thread is likely to focus on use-case validation and design alternatives before any code is written.
