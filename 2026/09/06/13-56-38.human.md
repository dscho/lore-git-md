This is an RFC proposing a new feature for `git clean`: persistent exclude patterns via Git configuration.

The author, Nicolas Jeanmonod, notes that `git clean` already supports one-off exclude patterns with the `-e`/`--exclude` option, which remain effective even when `-x` (remove ignored files) is used. However, there is no way to make these exclusions persistent across invocations. The proposal is to add a `clean.exclude` configuration key that would behave as if the user had supplied the patterns via `-e` every time.

The use case is protecting untracked but irreplaceable directories (e.g., local metadata) from accidental removal when running `git clean -fdx`. Unlike `.gitignore` or `core.excludesFile`, which control what Git ignores during normal operations, this setting would specifically answer "which untracked paths should `git clean` never remove by default?"

The design is straightforward: a multi-valued `clean.exclude` setting, configurable globally or per-repository, that maps directly to the existing `-e` option. The author suggests this is simpler than introducing a dedicated exclude file (like `clean.excludesFile`).

The proposal is well-motivated and aligns with Git’s existing configuration patterns. It doesn’t appear controversial, though the mailing list may discuss whether the use case is common enough to warrant a new config key or if users should continue managing exclusions manually. Worth watching for feedback on whether this overlaps with other ignore mechanisms.
