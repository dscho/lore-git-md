This is a bugfix patch discussion in the ongoing `rerere` race-condition thread. Thomas Bachem responds to Junio C Hamano’s critique of the v3 patch, which allows a rebase to proceed after a lock timeout without recording the conflict preimage. Thomas argues that the user can recover the skipped recording by running `git rerere` manually at the conflict stop, and that failing the rebase outright is unnecessarily disruptive—especially since the rebase can otherwise complete, and the conflict resolution can still be salvaged. He acknowledges that the current Git behavior (in 2.55) already makes recovery awkward (e.g., `git commit --amend` drops the commit message), but notes this is not introduced by his patch. He proposes keeping the v3 behavior for conflict stops (where the rebase halts anyway) but retaining the failure mode for post-resolution recording and explicit `git rerere` commands. The trade-off is between a loud failure that forces user attention and a warning that allows the rebase to finish while still enabling recovery. The outcome will determine whether the v4 patch fails fast or proceeds with a warning.
