Subject: [RFC] persistent exclude patterns for `git clean` via config
Series version: N/A (design proposal only)
Originating author: Nicolas Jeanmonod
Thread type: RFC / design discussion

Core problem or goal
Allow users to protect specific untracked paths from accidental deletion by `git clean` (including `git clean -x`) via persistent configuration, without requiring manual `-e` arguments on each invocation. The goal is to safeguard irreplaceable untracked directories (e.g., local metadata, build artifacts) that should not be removed even when cleaning ignored files.

Current status
No implementation exists; this is a design proposal to gather feedback on the feature’s desirability and the proposed configuration-based approach (`clean.exclude` multi-valued key).

Key technical details
- New config key: `clean.exclude` (multi-valued)
- Scope: global or per-repository
- Behavior: patterns act as if passed via `git clean -e <pattern>` on every invocation, persisting across runs and protecting paths even when `git clean -x` is used
- Subsystems touched: `git clean` command, config parsing
- No new CLI options or on-disk format changes proposed

Open questions and loose ends
- Is the use case sufficiently common to justify a persistent mechanism?
- Is the proposed `clean.exclude` config key the right design, or would a separate exclude file (analogous to `.gitignore`) be preferable?
- Should the patterns apply only to `git clean -x`, or should they also override `.gitignore` protections in non-`-x` invocations?
- Are there security or usability concerns with persistent patterns (e.g., accidental protection of malicious paths)?

Participant positions
None yet; this is the thread root.

Related work
- `.gitignore` and `core.excludesFile` control what Git ignores during normal operations, but do not affect `git clean` behavior.
- `git clean -e` already supports ephemeral exclude patterns; this proposal extends that mechanism to persistent configuration.
