This is a follow-up in the abandoned `[PATCH 0/3] format-patch: add --[no-]range-diff-notes` thread, focusing on documentation clarity for the proposed (but never merged) feature. Kristoffer Haugsbakk responds to D. Ben Knoble’s surface-level review of a rewritten documentation snippet, elaborating on the intended behavior of the `--range-diff-notes` and `--no-range-diff-notes` options.

The email centers on a niche but technically intricate aspect of the feature: how to revert the "override" behavior (where range-diff notes are controlled independently of patch notes) and restore the default state where both use the same notes. Kristoffer explains that the sequence `--no-range-diff-notes --range-diff-notes` (without arguments) was designed to serve this purpose, acting as a toggle to undo prior overrides and fall back to the notes specified by `--notes`. He provides a concrete example: if `--notes=review --notes=testing --notes=changelog --range-diff-notes=changelog` is used, the patches show all three notes while the range-diff shows only `changelog`; adding `--no-range-diff-notes --range-diff-notes` would restore all three notes to the range-diff. The implementation treats bare `--range-diff-notes` as a special case when the range-diff notes list is empty, avoiding the need for users to repeat all `--notes` arguments.

Kristoffer acknowledges the complexity of the interaction and the verbosity of the documentation, but argues that the feature’s flexibility justifies the added conceptual load. He also notes a tangential concern about `format-patch`’s handling of default notes (suggesting it should respect `format.notes` rather than `notes.displayRef`), though this is unrelated to the current discussion. The email concludes with gratitude for Ben’s feedback and a lighthearted remark about the rarity of Git notes usage among contributors.

The discussion remains purely theoretical, as the feature was abandoned due to Junio C Hamano’s substantive usability concerns about the option semantics. No code changes are proposed here, and the thread is effectively closed. The exchange serves primarily to clarify the intended behavior for posterity, should the feature be revived in the future.
