This is a substantive review comment on the sixth patch in Patrick Steinhardt’s 8-patch series refactoring ODB alternates handling during repository creation. Justin Tobler raises a forward-looking design question about the ODB interface’s exposure of alternates to backends that may not use them.

The comment engages with the patch’s core architectural change: the introduction of `struct odb_create_on_disk_options` and its `alternates` field. Justin observes that while the interface still provides a way to pass alternates to the backend, some backends (e.g., future pluggable ODBs) might not use alternates at all. He asks whether this implies that `git clone --shared` and similar options should be restricted to the "files" backend, or if their behavior should be left to the backend’s discretion.

This is a thoughtful question about the ODB abstraction’s long-term flexibility. It does not challenge the patch’s correctness or immediate implementation (which is sound and addresses the lockfile API adoption from v1), but it probes the interface’s design for future extensibility. The comment is well-placed in the context of the broader ODB abstraction effort, where alternates are intended to become an implementation detail of the backend. Justin’s feedback suggests a potential tension between maintaining a uniform user interface (e.g., `--shared` working the same way across backends) and allowing backends to define their own semantics.

No resolution is proposed in the email, but the question is likely to prompt discussion among ODB-focused contributors (e.g., Patrick Steinhardt, Karthik Nayak) about how to handle backend-specific options in a way that preserves both flexibility and user expectations. The patch itself remains technically ready, but this comment may influence future iterations of the ODB abstraction work.
