This is the fifth patch in Elijah Newren’s six-patch series optimizing `git push` from shallow clones. The patch changes the default value of the `push.shallowExcludeBoundary` config option from `false` to `true`, meaning the optimization (omitting redundant shallow boundary objects) is now enabled by default.

The rationale is straightforward: sending shallow boundaries is almost always wasted work. The server likely already has them, and omitting them avoids transferring and recompressing large trees. The compatibility cost is minimal: seeding a new shallow root already requires `receive.shallowUpdate` on the server, and now also requires `push.shallowExcludeBoundary=false` on the client. The patch updates the documentation to reflect the new default and adjusts the tests to explicitly set the old default (`false`) where the original behavior is required.

The commit message addresses the two edge cases where the new default might reject a push that would have succeeded before: (A) the server has the boundary’s parents but not the boundary itself, and (B) a multi-ref push where one ref’s shallow boundary excludes objects needed by another ref. In both cases, the patch argues that a quick rejection is preferable to a slow, accidental success or a large data transfer. The sixth patch in the series (not shown here) adds advice for users to retry problematic multi-ref pushes separately, mitigating the false-positive failure mode.

This patch is the crux of the series’ trade-off: performance versus occasional false positives. The preparatory patches (1-4) have already improved error handling and robustness, making the failure cases easier to diagnose and recover from. The change looks well-justified for most users, but the default flip may still draw scrutiny from reviewers who prioritize backward compatibility or are wary of the false-positive failure mode. The updated documentation clearly explains the trade-offs, which should help users make an informed choice.
