This is a feature patch introducing the `hooks.allowNoVerify` configuration option. It’s the fourth iteration (v4) of a series that began as a proposal to give administrators control over the `--no-verify` (`-n`) flag in commands like `git commit`, `git push`, `git merge`, `git rebase`, and `git am`.

The patch adds a new config key `hooks.allowNoVerify` that accepts three values: `true` (the default, allowing `--no-verify` as before), `warn` (allowing the bypass but printing a warning), and `false` (disallowing the bypass entirely). When set to `false`, Git aborts with a fatal error and provides actionable advice on how to override the guardrail in emergencies—either via the `GIT_ALLOW_NO_VERIFY=1` environment variable or the `-c hooks.allowNoVerify=true` CLI flag. The implementation centralizes the validation logic in `hook.c` and updates all affected built-in commands (`commit.c`, `push.c`, `merge.c`, `rebase.c`, `am.c`). Documentation is included, and the test suite (`t7599-hooks-allownoverify.sh`) covers every affected command, config precedence, CLI overrides, and edge cases like broken hooks.

The v4 update adds coverage for `git am --no-verify`, which was missing in v3, and keeps the simplified config values and clarified scope from earlier versions. The patch is well-motivated, self-contained, and includes thorough test coverage, making it a strong candidate for environments where accidental hook bypass needs to be prevented without breaking legitimate escape hatches. No open questions or objections have surfaced yet, and the series appears ready for maintainer consideration.
