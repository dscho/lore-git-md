This thread is about a bugfix for a race condition in Git 2.54 where background maintenance (`git rerere gc`)—triggered aggressively by the geometric maintenance strategy—can deadlock or crash an in-progress rebase when both try to acquire the `MERGE_RR.lock`. The fix comes in two parts: a locking patch (now at v2) and a sequencer config-override patch (still pending).

Thomas Bachem’s v2 locking patch refines `rerere_setup()` to propagate errors instead of dying when the lock is held. Non-maintenance callers (like `git commit`) now wait up to 1 second (configurable via `rerere.lockTimeout`), while background maintenance skips the lock entirely (timeout=0). The patch introduces clearer flags (`RERERE_NOWAIT` and `RERERE_LOCK_OR_DIE`) and better error messages, avoiding misleading advice about terminating other Git processes. Phillip Wood and Patrick Steinhardt have both reviewed the approach, with Patrick’s suggestions (like `LOCK_REPORT_ON_ERROR`) now incorporated. The patch is well-tested and aligns with the broader goal of disabling maintenance during rebase, though the sequencer config-override patch is still forthcoming.

Key participants agree on the immediate fix but differ on the root cause. Phillip Wood argues that garbage collection is useless mid-rebase and advocates for disabling maintenance entirely during rebase, while Patrick Steinhardt blames the geometric maintenance strategy’s aggressiveness and plans a separate patch to adjust `maintenance.rerere-gc.auto`. The v2 locking patch is ready for review, but the thread remains open on whether the merge backend should run maintenance at all and how Patrick’s maintenance strategy changes will interact with the rebase-specific overrides. Junio’s input on the locking changes and broader strategy is still pending.
