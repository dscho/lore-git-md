This thread is about fixing a race condition in Git's `rerere` subsystem, where background maintenance (like `git rerere gc`) can interfere with foreground operations such as rebase by pruning conflict-resolution entries while they're still in use. The fix is a two-part series: the first patch (now at v3) improves locking and error handling in `rerere`, while the second will disable background maintenance during rebase via config overrides.

The v3 locking patch, authored by Thomas Bachem, is now ready for final review. It introduces a configurable timeout for `rerere` locks, unified error reporting, and ensures commands like `git rerere clear` fail immediately if the lock is held, avoiding silent corruption. The patch addresses all prior feedback from Junio Hamano, Phillip Wood, and Patrick Steinhardt, who had substantive technical concerns about the locking implementation and usability. Background maintenance is now confirmed to run either daemonized (suppressing output) or synchronously, resolving worries about mixed warnings during rebase.

The only remaining open question is a philosophical one: Junio Hamano argues that rebases should fail immediately if the `rerere` lock is held, rather than proceeding without conflict resolution, to avoid wasting the user's time. The code already aligns with this preference (rebases pause at conflicts), but the commit message wording was misleading. Thomas will clarify this in the final version. The second patch, which will disable maintenance during rebase, is still pending but uncontroversial. The series is under review with no objections to the current approach.
