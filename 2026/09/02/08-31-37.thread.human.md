This thread is about a bugfix for a race condition in Git's `rerere` subsystem that can deadlock or kill an in-progress rebase when background maintenance (`git rerere gc`) and the rebase both try to acquire the `MERGE_RR.lock` simultaneously. The issue was introduced in Git 2.54 with the geometric maintenance strategy.

Thomas Bachem's patch introduces a new `rerere.lockTimeout` configuration option (defaulting to 1000ms) that makes lock acquisition wait instead of failing immediately. When the background `rerere gc` encounters a held lock, it now skips its run and issues a warning, matching the behavior of other maintenance tasks. The fix includes a reproducible test case demonstrating the race condition with a rebase involving two consecutive conflicts.

The implementation touches core `rerere` files, adds documentation, and includes comprehensive test coverage. The solution is backward-compatible (timeout=0 restores old behavior) and follows established Git lock-timeout patterns. No reviews or maintainer decisions have been posted yet, so the patch is still under initial consideration.
