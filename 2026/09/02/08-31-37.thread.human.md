This thread is about fixing a race condition in Git’s `rerere` subsystem, where background maintenance (like `git rerere gc`) can prune conflict entries while a foreground operation (such as a rebase) is recording them, causing failures. The proposed solution is a two-part series: (1) improve error handling in `rerere_setup()` with configurable locking timeouts and unified error reporting, and (2) disable background maintenance during rebase via config overrides. The series is now at v4 of the locking patch, with the sequencer config-override patch still pending.

The key debate revolves around how to handle lock contention. Junio Hamano insists that commands should fail loudly after waiting the full timeout if the lock is still held, arguing that silently proceeding risks losing the user’s conflict resolution work. Thomas Bachem counters that the conflict preimage can always be recovered by manually running `git rerere`, and that failing the rebase outright is overly disruptive given Git’s existing limitations (like lost commit metadata when restarting interrupted rebases). He proposes a compromise: warn and proceed at conflict stops (to preserve rebase continuity) but fail loudly for post-resolution recording, `git rerere` commands, and `git am --continue` (to prevent silent corruption of the `MERGE_RR` file). Phillip Wood has shifted from opposing the timeout fix to accepting it as a pragmatic stopgap, while Patrick Steinhardt’s feedback on locking improvements has been incorporated into v4.

The series remains under review, with no objections to the revised approach. Open questions include whether rebases should run maintenance at all (Phillip Wood argues garbage collection is useless mid-rebase), how Patrick’s planned changes to `maintenance.rerere-gc.auto` will interact with the rebase-specific overrides, and whether the 1-second default timeout is sufficient. The geometric maintenance strategy’s aggressiveness (triggering `rerere gc` after every commit) exacerbates the issue but isn’t the sole cause. Thomas also floated the idea of writing the rebase stop state *before* invoking `rerere` to allow `--continue` even if the lock is held, but this will be explored separately. The error message wording and recovery guidance are still being refined to balance clarity and usability.
