This thread is about a bugfix for a race condition in Git’s `rerere` subsystem that can crash or deadlock rebases when background maintenance runs. The issue surfaced after Git 2.54 introduced the geometric maintenance strategy, which aggressively triggers `git rerere gc` after every commit—even with just one `rr-cache` entry—causing lock contention with in-progress rebases.

Thomas Bachem initially proposed a timeout-based fix but has now settled on a two-part solution shaped by feedback from Phillip Wood and Patrick Steinhardt. The first part, now finalized as v2, improves error handling in `rerere_setup()`: it propagates errors instead of dying, unifies the skip/timeout logic (waiting 1 second for non-maintenance callers like `git commit` while skipping the lock entirely for background maintenance), and uses `LOCK_REPORT_ON_ERROR` for better diagnostics. The second part—disabling maintenance during rebase via config overrides—has been deferred as its benefit is now minimal after the locking changes. The series is ready for review, with Phillip Wood’s feedback still pending.

The root cause remains the geometric maintenance strategy’s aggressiveness, but Patrick Steinhardt plans a separate patch series to adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility rather than just entry counts. Open questions include whether rebases using the merge backend should run maintenance at all, and how Junio might weigh in on the locking changes. The fix is targeted at the `maint` branch and touches `rerere.c`, `sequencer.c`, and test files.
