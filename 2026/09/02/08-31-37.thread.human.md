This thread is about fixing a race condition in Git’s `rerere` subsystem, where background maintenance (like `git rerere gc`) can prune conflict-resolution entries while a foreground operation (such as a rebase) is actively recording them. The issue, exacerbated by the geometric maintenance strategy’s aggressive triggering, risks corrupting or losing conflict resolutions. Thomas Bachem’s two-patch series addresses this with improved locking and config overrides to disable maintenance during rebase.

The latest update simplifies the approach: in the upcoming v4 patch, all foreground commands (including `git rebase`, `git commit`, and `git merge`) will now wait the full configurable timeout (default: 1 second) and fail if the lock remains held, rather than proceeding without `rerere` recording. This aligns with Junio’s preference to avoid silently skipping conflict resolution, which could lose user work. The rebase will stop at the conflict, allowing the user to retry with `git rebase --continue` once the lock is released. The only exception is `git rerere gc`, which still gives up immediately as a best-effort cleanup. The default timeout remains finite to prevent hangs, but users can set `rerere.lockTimeout` to -1 for indefinite waits.

Key participants—Thomas Bachem, Junio Hamano, Phillip Wood, and Patrick Steinhardt—have converged on the locking and error-handling changes, with v3 of the locking patch incorporating all feedback. The sequencer patch (disabling maintenance during rebase) is still pending, but the series is otherwise ready for final review. Open questions include whether rebases should run maintenance at all (Phillip Wood argues it’s useless mid-rebase) and how Patrick’s planned maintenance-strategy changes will interact with the rebase-specific overrides. The geometric maintenance strategy’s defaults remain a contributing factor, though the root issue is broader: any background `rerere gc` can interfere with foreground operations.
