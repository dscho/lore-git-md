This thread is about a bugfix for a race condition in Git’s `rerere` subsystem that can crash or deadlock rebases when background maintenance (`git rerere gc`) runs concurrently. The issue surfaced after Git 2.54 introduced a more aggressive geometric maintenance strategy, which triggers `rerere gc` after every commit—even with just one `rr-cache` entry—leading to lock contention on `MERGE_RR.lock`.

Thomas Bachem initially proposed a timeout-based fix, but after substantive reviews from Phillip Wood and Patrick Steinhardt, the solution has evolved into a two-patch series. The first patch disables background maintenance during rebase via config overrides (`-c gc.auto=false -c maintenance.auto=false`), while the second improves error handling in `rerere_setup()` to propagate errors instead of dying, with better locking logic. The locking changes now include a bounded wait (up to 1 second) for non-maintenance callers like `git commit`, while background maintenance skips the lock entirely. Patrick’s feedback shaped the locking improvements, including unified skip/timeout logic and clearer error reporting with `LOCK_REPORT_ON_ERROR`.

The series is now under review, with implementation details settled and Phillip Wood’s review of the v2 patches pending. Open questions remain about whether to add a maintenance run at the end of rebase (Thomas prefers not to) and whether the fork-based background maintenance design is fundamentally flawed for interactive operations (Phillip’s critique). Patrick plans a separate patch series to adjust the geometric maintenance strategy’s defaults, which may reduce the need for rebase-specific workarounds. Junio’s input on the revised approach is still awaited.
