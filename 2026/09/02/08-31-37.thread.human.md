This thread is about fixing a race condition in Git’s `rerere` subsystem, where background maintenance (like `git rerere gc`) can prune conflict entries while a foreground operation (e.g., rebase) is recording them, causing failures. Thomas Bachem proposed a two-part fix: (1) improve locking in `rerere_setup()` with configurable timeouts and unified error reporting, and (2) disable background maintenance during rebase via config overrides. The series is now at v4 of the locking patch, with the sequencer config-override patch still pending.

Key participants include Thomas (the author), Phillip Wood (who initially opposed the timeout-based fix but now accepts it as a pragmatic stopgap), Patrick Steinhardt (who identified the geometric maintenance strategy’s aggressiveness as a contributing factor), and Junio Hamano (the maintainer). The latest debate centers on error handling: Junio argues that after a lock timeout, the rebase should fail loudly with clear recovery instructions (e.g., running `git rerere` manually) rather than proceeding silently, as the v3 patch allowed. This ensures users don’t lose their conflict resolution work. Thomas is revising v4 to reflect this feedback, ensuring all commands (except `git rerere gc`) wait the full timeout and fail if the lock remains held.

Open questions include whether rebases should run maintenance at all (Phillip argues garbage collection is useless mid-rebase), how Patrick’s planned maintenance strategy changes will interact with the rebase-specific overrides, and whether the 1-second timeout is sufficient. The geometric maintenance strategy’s aggressiveness remains a separate but related issue. The series is under review, with no objections to the revised approach so far.
