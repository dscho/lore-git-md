This is the second patch in Christian Couder’s six-part series introducing `early_scan_options()`, a new sub-API for Git’s `parse-options` infrastructure. The email is a **substantive review** from Junio C Hamano, the maintainer, focusing on the design and implementation of the core `early_scan_options()` function.

Junio’s feedback centers on two main concerns. First, he questions the long-term viability of the new API’s design, which requires commands to maintain a separate `early_scan_option` array alongside their existing `struct option` array. He suggests this duplication could become technical debt if `parse_options()` itself is later refactored to support a "dry-run" prescan mode, and he wonders whether the API could instead accept the full `struct option` array from the start, even if it initially ignores some of its features (like option abbreviations or callbacks). This would reduce programmer burden and make future refactoring easier, though it might complicate the initial implementation.

Second, Junio identifies a **potential bug** in the `find_early_scan_option()` helper: it does not consult the `takes_value` field when handling unstuck option values (e.g., `--option value`), which could lead to misparsing. The function correctly checks `takes_value` for stuck values (`--option=value`) but skips this check for separate values, creating an inconsistency. This is a clear correctness issue that will need to be fixed in the next iteration.

The review also includes minor stylistic feedback, such as naming conventions for array parameters, but the bulk of Junio’s comments are technical and substantive. His skepticism about the API’s design direction—particularly the separate `early_scan_option` array—echoes his earlier concerns about the series as a whole, and his suggestion to use `struct option` directly hints at a preferred long-term solution. The series is **not yet ready for `next`**, and this feedback will likely require a non-trivial revision to the core API.
