This is a follow-up discussion in the ongoing thread about fixing a memory leak in the submodule error path, specifically exploring a deeper refactoring of Git’s `parsed_object_pool` API. The conversation is between Jeff King (Peff) and Patrick Steinhardt, focusing on whether to eliminate the redundant `repo` pointer in the `parsed_object_pool` structure and how to approach such a refactoring.

Peff’s earlier exploration proposed removing the `repo` pointer from `parsed_object_pool`, arguing that it serves no purpose beyond circular access to `repo->parsed_objects` (which is always the pool itself). He suggested introducing pool-based lookup functions (e.g., `lookup_commit_via_pool()`) alongside existing repository-based wrappers to avoid rewriting all callers. However, he concluded the churn (about 60 lines across six files) wasn’t justified for the marginal clarity gained. Patrick agrees with the goal—making the parsed object pool more self-contained—but pushes for a more decisive approach. He argues that retaining both interfaces (repository-based and pool-based) dilutes the benefit, and that the refactoring should either be all-in or abandoned. His perspective aligns with the broader effort to reduce global state in Git, where passing explicit repositories is a first step, but the ultimate goal is to pass only the state each subsystem actually needs.

The discussion remains exploratory and does not propose actionable patches. Patrick’s feedback is supportive of the direction but emphasizes the need for a complete refactoring if the change is to be meaningful. The technical obstacles—circular header dependencies and hidden dependencies in the codebase—remain the primary barriers to progress. No objections or alternative proposals have been raised, and the thread does not affect the original bugfix series, which is still under review. This exchange serves as a technical note for future refactoring efforts, particularly around reducing subsystem coupling in Git’s object management.
