This is a bugfix patch that addresses a race condition between Git's background maintenance tasks and interactive rebase operations. Since Git 2.54, the auto-maintenance feature runs `git rerere gc` in the background after every commit, including those made during `git rebase --continue`. The problem arises when the background gc process and the rebase sequencer both try to lock the `MERGE_RR` file simultaneously—whichever process acquires the lock second dies with an error, breaking the rebase workflow.

The patch introduces a configurable `rerere.lockTimeout` (defaulting to 1000ms) that allows callers to wait for the lock instead of failing immediately. Background gc processes now skip their run if the lock is held, emitting a warning instead of crashing. The fix is well-motivated with a clear reproduction case in the commit message, and the patch includes thorough tests covering both the gc-under-lock scenario and the new timeout behavior. The change is narrowly scoped to the rerere subsystem and should be uncontroversial. If you work with rebases or have rerere enabled, this patch is worth reviewing.
