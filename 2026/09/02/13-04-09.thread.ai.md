Core problem or goal
Fix a long-standing edge case in `common_prefix_len()` where an exclude pathspec (e.g., `:!unrelated/path`) appearing first in the list causes the function to incorrectly return zero as the common prefix length, even when subsequent positive pathspecs (e.g., `foo/bar` and `foo/baz`) share a directory (`foo/`). The bug occurs because the function uses the first pathspec item as the comparison baseline regardless of exclusion status, and skips excluded items only after initializing the comparison. Additionally, the series addresses a memory-safety issue in `match_pathspec_with_flags()` where negative pathspecs shorter than the common prefix derived from positive pathspecs trigger a heap-buffer-overflow when `match_pathspec_item()` reads out-of-bounds memory. Junio C Hamano has now identified a second, independent logical bug: when the common prefix derived from positive pathspecs is incorrectly applied to a negative pathspec of sufficient length, the matching logic produces false positives. For example, `git ls-files a/b ':!x/b' a/c` incorrectly excludes `a/b/m` because the prefix-stripped negative pathspec `b` (from `:!x/b`) incorrectly matches the prefix-stripped path `b/m`.

Key technical details
- Files touched: `dir.c`, `pathspec.c`, `pathspec.h`, `t/t6132-pathspec-exclude.sh`, `t/unit-tests/u-dir.c`
- New symbols: none (output-parameter approach replaces the `pathspec_prefix` struct)
- Subsystem: pathspec handling and directory traversal
- Behavior change: `common_prefix_len()` now correctly returns the common prefix of positive pathspecs even when an exclude pathspec appears first (addressed in patch 3); `match_pathspec_with_flags()` no longer applies the common prefix to negative pathspecs, preventing both out-of-bounds reads and false positives in negative pathspec matching (addressed in patch 2)
- Test coverage: new functional test in `t/t6132-pathspec-exclude.sh` (covering both the memory-safety issue and the common prefix edge case) and unit tests in `t/unit-tests/u-dir.c` (covering the edge case with an unrelated exclude item followed by two non-exclude items sharing a directory, and the heap-buffer-overflow regression). The third patch adds a unit test specifically for the edge case where an exclude pathspec precedes two positive pathspecs sharing a directory. Elijah Newren proposes an additional test case for `t/t6132-pathspec-exclude.sh` that would deterministically expose the heap-buffer-overflow without relying on ASan, using an exclude pathspec whose length exactly matches the common prefix of the positive pathspecs. Junio C Hamano has now provided a deterministic test case (`git ls-files a/b ':!x/b' a/c`) that exposes the false-positive bug in negative pathspec matching, which the fix also resolves.
- Alternative design: Junio's output-parameter approach (`common_prefix_len(pathspec, &matched_prefix)`) is the agreed-upon solution
- Preparatory refactoring: `struct pathspec_item` fields `match` and `original` are now `const char *` to reflect immutability and enable warning-free unit test initialization
- Performance impact: The fix restores an intended optimization where Git avoids traversing from the root when all non-exclude pathspecs share a directory, even if an exclude pathspec appears first. The original behavior forced traversal from the root in such cases, degrading performance.
