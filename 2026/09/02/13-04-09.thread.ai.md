Subject: [PATCH] dir: fix common prefix calculation with leading exclude pathspec
Series version: standalone patch (no series)
Originating author: Yannik Tausch
Thread type: bugfix patch

Core problem or goal
Fix a long-standing edge case in `common_prefix_len()` where an exclude pathspec (e.g., `:!unrelated/path`) appearing first in the list causes the function to incorrectly return zero as the common prefix length, even when subsequent positive pathspecs (e.g., `foo/bar` and `foo/baz`) share a directory (`foo/`). The bug occurs because the function uses the first pathspec item as the comparison baseline regardless of exclusion status, and skips excluded items only after initializing the comparison.

Current status
Under review; no prior versions. Patch introduces a new `pathspec_prefix` struct to track the first *positive* pathspec item and its common prefix length. Junio C Hamano has proposed an alternative implementation: returning the common prefix length directly and passing the match string via an output parameter, which would minimize changes to existing callers. The discussion is now focused on design trade-offs between the struct-based approach and the output-parameter alternative.

Key technical details
- Files touched: `dir.c`, `t/unit-tests/u-dir.c`
- New symbol: `pathspec_prefix` struct (contains match string and common prefix length) -- now under debate
- Subsystem: pathspec handling and directory traversal
- Behavior change: `common_prefix_len()` now correctly returns the common prefix of positive pathspecs even when an exclude pathspec appears first
- Test coverage: new unit test in `t/unit-tests/u-dir.c` covering the edge case
- Alternative design: Junio suggests returning the length directly and using an output parameter for the match string

Open questions and loose ends
- Whether the `pathspec_prefix` struct is justified or if the output-parameter approach is cleaner.
- No other reviewers have weighed in; the patch remains in active discussion.

Participant positions
