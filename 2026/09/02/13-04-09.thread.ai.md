Subject: [PATCH v2 0/2] dir: fix common prefix calculation with leading exclude pathspec
Series version: v2 (two-patch series, with the fix as the second patch; first patch is a memory-safety prerequisite)
Originating author: Yannik Tausch
Thread type: bugfix patch series

Core problem or goal
Fix a long-standing edge case in `common_prefix_len()` where an exclude pathspec (e.g., `:!unrelated/path`) appearing first in the list causes the function to incorrectly return zero as the common prefix length, even when subsequent positive pathspecs (e.g., `foo/bar` and `foo/baz`) share a directory (`foo/`). The bug occurs because the function uses the first pathspec item as the comparison baseline regardless of exclusion status, and skips excluded items only after initializing the comparison. Additionally, the series addresses a memory-safety issue in `match_pathspec_with_flags()` where negative pathspecs shorter than the common prefix derived from positive pathspecs trigger a heap-buffer-overflow when `match_pathspec_item()` reads out-of-bounds memory.

Current status
Under review; v2 adopts Junio C Hamano's output-parameter alternative (`common_prefix_len(pathspec, &matched_prefix)`) to minimize caller churn and avoid a new struct. The series is now split into two patches: the first ensures exclude pathspecs are matched against the full pathname (not the common prefix) to prevent the heap-buffer-overflow, and the second refactors `common_prefix_len()` to derive the common prefix from the first *non-exclude* pathspec item. Discussion has converged on the design approach, with implementation details (e.g., `char **` vs. `const char **` for the output parameter) still being finalized.

Key technical details
- Files touched: `dir.c`, `t/t6132-pathspec-exclude.sh`, `t/unit-tests/u-dir.c`
- New symbols: none (output-parameter approach replaces the `pathspec_prefix` struct)
- Subsystem: pathspec handling and directory traversal
- Behavior change: `common_prefix_len()` now correctly returns the common prefix of positive pathspecs even when an exclude pathspec appears first; `match_pathspec_with_flags()` no longer applies the common prefix to negative pathspecs, preventing out-of-bounds reads
- Test coverage: new functional test in `t/t6132-pathspec-exclude.sh` (covering both the memory-safety issue and the common prefix edge case) and unit test in `t/unit-tests/u-dir.c` (covering the edge case)
- Alternative design: Junio's output-parameter approach (`common_prefix_len(pathspec, &matched_prefix)`) is the agreed-upon solution
