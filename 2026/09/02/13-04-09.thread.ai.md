Subject: [PATCH v2 0/2] dir: fix common prefix calculation with leading exclude pathspec

Thread type: bugfix patch series

Core problem or goal
Fix a long-standing edge case in `common_prefix_len()` where an exclude pathspec (e.g., `:!unrelated/path`) appearing first in the list causes the function to incorrectly return zero as the common prefix length, even when subsequent positive pathspecs (e.g., `foo/bar` and `foo/baz`) share a directory (`foo/`). The bug occurs because the function uses the first pathspec item as the comparison baseline regardless of exclusion status, and skips excluded items only after initializing the comparison. Additionally, the series addresses a memory-safety issue in `match_pathspec_with_flags()` where negative pathspecs shorter than the common prefix derived from positive pathspecs trigger a heap-buffer-overflow when `match_pathspec_item()` reads out-of-bounds memory.

Current status
Under review; v2 adopts Junio C Hamano's output-parameter alternative (`common_prefix_len(pathspec, &matched_prefix)`) to minimize caller churn and avoid a new struct. The series is split into two patches: the first ensures exclude pathspecs are matched against the full pathname (not the common prefix) to prevent the heap-buffer-overflow, and the second refactors `common_prefix_len()` to derive the common prefix from the first *non-exclude* pathspec item. The second patch implements the output-parameter design and adds a unit test in `t/unit-tests/u-dir.c` to verify the fix. Junio has now posted a preparatory refactoring patch that declares `match` and `original` fields in `struct pathspec_item` as `const char *`, resolving the compiler warning in the unit test. This refactoring is uncontroversial, purely mechanical, and enables the unit test to initialize `.match` with a string literal without warnings. The series is now ready for merging once the preparatory patch is integrated; no further technical changes are expected.
