This is a follow-up discussion in the now-graduated `dk/use-nsec-runtime` series, which moved nanosecond timestamp precision from a build-time (`USE_NSEC`) to a runtime (`core.useNanosec`) setting. The series is already in `next` and all prior feedback has been addressed, but this exchange between Jeff King (Peff) and D. Ben Knoble revisits a subtle design choice: whether the `#ifndef NO_NSEC` guard around the `core.usenanosec` config handler is still necessary.

Peff questions the guard’s value, pointing out that platforms without nanosecond support would likely not enable the config, and even if they did, the code would still work by faking nanosecond values as zero. However, he identifies a hypothetical edge case: if a user builds two Git versions (one with `NO_NSEC` and one without) on a system that *does* support nanosecond timestamps, an index generated by the non-`NO_NSEC` build could store real nanosecond values, which the `NO_NSEC` build would misinterpret as zero, potentially leading to false "racy" comparisons. This scenario is admittedly unlikely, and Peff doesn’t propose removing the guard—just noting the trade-off.

Knoble clarifies that the guard prevents reading nanosecond values on unsupported platforms, avoiding false negatives in racy checks, but also restricts users on `NO_NSEC` builds (e.g., from a distro) from enabling `core.useNanosec` without recompiling. The discussion highlights a tension between build-time restrictions and runtime flexibility, but neither participant suggests changing the code. The series remains technically sound and in `next`; this thread is purely a post-graduation clarification of an edge case that might warrant a note in the documentation. No action is needed unless someone later decides to document the mixed-build risk.
