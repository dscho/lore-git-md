This is a substantive discussion about a usability footgun in Git’s branch name validation, specifically whether to tighten the `--branch` mode of `` `git check-ref-format` `` to reject bare `@` as a branch name.

Jeff King (Peff) responds to D. Ben Knoble’s review of Bence Csókás’s bug report. Peff confirms that the current behavior is not a bug in the strict sense—bare `@` is syntactically allowed in ref components due to backwards compatibility—but agrees it is a footgun. He points to the precedent of rejecting `HEAD` as a branch name in `--branch` mode, which already enforces stricter porcelain-specific rules. Peff suggests treating bare `@` the same way, while preserving the ability to use `@` in compound names like `foo@bar`, which are less likely to cause confusion.

The discussion advances the thread by clarifying the design space: the inconsistency is intentional for compatibility, but the porcelain interface can and should be stricter to prevent user mistakes. Peff’s response is substantive, citing specific examples (the `HEAD` restriction) and reasoning about which cases to block. No patch is proposed yet, but the technical direction is now clear: a targeted change to `check-ref-format --branch` to reject bare `@` while allowing other uses of `@`. The subsystem involved is ref name validation in `refs.c` and `check-ref-format.c`.
