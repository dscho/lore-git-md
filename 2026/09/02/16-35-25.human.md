This is a feature patch that introduces a new configuration option `hooks.allowNoVerify` to control whether the `--no-verify` (`-n`) flag can bypass client-side hooks in commands like `git commit`, `git push`, `git merge`, and `git rebase`. This is the second iteration of the patch, expanding the initial proposal with more granular control and better emergency override mechanisms.

The patch now supports three configuration values: `true` (or `always`, the default), `warn` (permits `--no-verify` but prints a warning), and `false` (or `never`, `error`, which disallows `--no-verify` by default). When set to `false`, Git provides actionable advice on how to override the guardrail in emergencies, either via the `GIT_ALLOW_NO_VERIFY=1` environment variable or the `-c hooks.allowNoVerify=true` command-line option. This preserves a "big red button" escape hatch without requiring destructive local workarounds like deleting hooks.

The implementation centralizes the validation logic in `hook.c` via a new `validate_no_verify()` function, reducing code duplication across the affected commands (`builtin/am.c`, `builtin/commit.c`, `builtin/merge.c`, `builtin/push.c`, `builtin/rebase.c`). The patch includes comprehensive documentation in `Documentation/config/hooks.adoc` and a thorough test suite (`t/t7599-hooks-allownoverify.sh`) covering CLI overrides, config precedence, hook failure scenarios, and all supported configuration values.

This is a well-crafted, self-contained patch that addresses a real need in managed environments or CI workflows where accidental hook bypass should be prevented. The expanded configuration options and emergency override mechanisms make it more flexible than the initial version, while the centralized validation logic and thorough test coverage suggest it is ready for serious review. The patch does not alter Git’s server-side security model and maintains backward compatibility by defaulting to `true`.
