This is the **second patch in a six-patch series** introducing a new `parse-options` sub-API for early argument scanning. The series as a whole targets a recurring class of argument-parsing bugs where hand-rolled early scans (looking for `--` or special flags) fail to account for option values that appear as separate arguments.

This patch fixes a specific bug in `git bisect start`: when a term name is `--` (e.g., `git bisect start --term-good --`), the first argument-scanning loop mistakenly treats the term value `--` as the revision/path separator, causing the command to reject subsequent arguments as invalid revisions. The fix replaces the hand-rolled `--` detection with the new `early_scan_options()` API, which correctly skips option values (including `--`) when instructed.

The implementation is clean and minimal. The patch adds a small array of `early_scan_option` entries for the four term-related options (`--term-good`, `--term-old`, `--term-bad`, `--term-new`), each marked with `EARLY_SCAN_SKIP_VALUE` to ensure their values are skipped during the scan. The test coverage is thorough: a new test in `t/t6030-bisect-porcelain.sh` verifies that `git bisect start --term-good -- hello` correctly treats `--` as a term name and `hello` as a path.

The commit message is exemplary: it explains the bug, the root cause, the fix, and the rationale for not tightening term-name validation (a separate UI concern). The patch touches only `builtin/bisect.c` and the test suite, with no on-disk format or behavior changes beyond fixing the misparsing. This is a **well-motivated, well-scoped bugfix** that directly addresses a real user-facing issue. The use of the new `early_scan_options()` API here is a strong signal that the series is on the right track.
