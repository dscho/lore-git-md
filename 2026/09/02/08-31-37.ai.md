This is a bugfix patch targeting the `rerere` subsystem, addressing a race condition introduced in Git 2.54 where background maintenance tasks (specifically `git rerere gc`) can deadlock or kill an in-progress rebase when both try to acquire the `MERGE_RR.lock` simultaneously.

The patch introduces a new `rerere.lockTimeout` configuration option (defaulting to 1000 milliseconds) that allows callers to wait for the lock instead of failing immediately. When the background `rerere gc` task encounters a held lock, it now skips its run and issues a warning, mirroring the behavior of other maintenance tasks. The fix is demonstrated with a reproducible test case showing a rebase with two consecutive conflicts, where the second conflict resolution would previously fail due to the lock contention.

The implementation touches `rerere.c` (adding the timeout logic and new `RERERE_SKIP_LOCKED` flag), updates documentation (`rerere.adoc` and `git-rerere.adoc`), and adds test coverage in `t4200-rerere.sh` and `t7900-maintenance.sh`. The patch is well-motivated with a clear reproduction scenario and includes both positive and negative test cases for the new timeout behavior.

Key technical details:
- Files modified: `rerere.c`, `rerere.h`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`
- New config: `rerere.lockTimeout` (milliseconds, default 1000)
- New flag: `RERERE_SKIP_LOCKED` for `setup_rerere()`
- Lock acquisition now uses `hold_lock_file_for_update_timeout()` instead of `LOCK_DIE_ON_ERROR`
- The test case uses a 20,000-entry `rr-cache` to reliably trigger the race condition

The patch appears to be a clean, targeted fix for a real-world problem that emerged with the geometric maintenance strategy in Git 2.54. The solution preserves backward compatibility (timeout=0 restores old behavior) and follows established patterns from other lock-timeout mechanisms in Git.
