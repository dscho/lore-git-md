Core problem or goal
Introduce a new `parse-options` sub-API (`early_scan_options()`) to fix a class of argument-parsing bugs where hand-rolled early scans (looking for `--` or special flags) fail to account for option values that appear as separate arguments. The new API performs a fast, limited scan of `argv` to locate specific long options, ignoring short options, abbreviations, and edge-case option types like `PARSE_OPT_OPTARG`. The series converts three commands (`git bisect`, `git rev-parse`, and `git fast-import`) to the new API, fixing concrete bugs in each:
- `git bisect start --term-good -- <not-a-rev>` previously mistook the term name `--` for the revision/path separator, rejecting `<not-a-rev>` as an invalid revision.
- `git rev-parse --default -- <not-a-rev>` made the same mistake, producing a confusing "bad revision" error.
- `git fast-import --depth 5 --allow-unsafe-features` silently ignored `--allow-unsafe-features`, refusing unsafe features from the input stream.

Current status
Under review (v1 posted). Junio C Hamano has raised **substantive design concerns** about the long-term viability of the new API, questioning whether it replaces one set of fragile hand-rolled scans with another rather than addressing the root problem: the lack of a unified, reusable early-scan mechanism within `parse_options()` itself. Junio remains skeptical of the `git bisect` and `git rev-parse` fixes, seeing "little practical value" in the `git bisect` scenario (`git bisect start --term-good -- hello`) and questioning whether users are likely to set a bisect term name to `--` in real workflows. He acknowledges the `git fast-import` bug as a real issue but continues to suggest that the series might be more compelling if it focused solely on that bug. He now suggests that even a simplified early scanner could use the real `struct option[]` array, reducing programmer burden and aligning better with the existing `parse_options()` infrastructure. His feedback on the second patch critiques the implementation of `find_early_scan_option()`, noting misleading parameter naming (`options` operates on a single element) and inconsistent logic for handling option values (checks `takes_value` for stuck arguments `--option=value` but not for separate arguments `--option value`). The series is **not yet ready for `next`** and will require at least one more iteration to address Junio’s design and implementation concerns. No merge status reported; CI passed cleanly on v1.

- Refactoring: `parse_options_takes_argument()` helper extracted from `show_gitcomp()` to avoid code duplication and prepare for `early_scan_options()`; `early_scan_options_from_options()` helper bridges the new early-scanning API with existing `struct option` arrays, eliminating the need for commands to maintain separate, hardcoded lists of options for early scanning.
