This is the **fourth patch in a six-patch series** introducing a new `parse-options` sub-API for early argument scanning. The series as a whole fixes a class of argument-parsing bugs where hand-rolled early scans (looking for `--` or special flags) fail to account for option values that appear as separate arguments.

This patch factors out the logic that determines whether a `parse-options` option takes an argument into a new helper function, `parse_options_takes_argument()`. The logic was previously open-coded in `show_gitcomp()`, which uses it to decide whether to append an `=` to the option name during shell completion. The new helper will also be used by the upcoming `early_scan_options()` API (introduced in patch 5) to skip option values during early argument scanning.

The implementation is straightforward: the function returns `1` if the option's type is one that takes a value (`OPTION_STRING`, `OPTION_FILENAME`, `OPTION_INTEGER`, `OPTION_UNSIGNED`, or `OPTION_CALLBACK`) and its flags do not include `PARSE_OPT_NOARG`, `PARSE_OPT_OPTARG`, or `PARSE_OPT_LASTARG_DEFAULT`. The commit message notes that `PARSE_OPT_LASTARG_DEFAULT` is intentionally excluded because it only consumes the next argument when it isn’t the last one, which `show_gitcomp()` already handled correctly.

The patch touches only `parse-options.c` and `parse-options.h`, adding the new function and its documentation. No behavior changes are introduced; this is purely a refactoring to avoid code duplication. The change is **well-motivated and uncontroversial**, as it prepares the ground for the core API addition in the next patch while also improving code clarity in `show_gitcomp()`. The implementation is clean and idiomatic, and the commit message clearly explains the rationale and edge cases.
