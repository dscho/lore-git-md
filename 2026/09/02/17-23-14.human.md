This is a feature patch introducing a new configuration option `hooks.allowNoVerify` to control whether the `--no-verify` (`-n`) flag can bypass client-side hooks in commands like `git commit`, `git push`, `git merge`, `git rebase`, and `git am`. This is the third iteration (v3) of the patch, refining the design based on earlier feedback.

The patch adds a three-tiered control system: `true` (default, allows bypass), `warn` (allows bypass but emits a warning), and `false` (blocks bypass entirely). When set to `false`, Git aborts with a clear error message and provides actionable advice for emergency overrides, including a `GIT_ALLOW_NO_VERIFY=1` environment variable and a `-c hooks.allowNoVerify=true` CLI flag. This prevents users from resorting to destructive workarounds like removing hook files or changing permissions.

The implementation touches multiple built-in commands (`am.c`, `commit.c`, `merge.c`, `push.c`, `rebase.c`), centralizes validation logic in `hook.c`, and includes comprehensive tests in a new file `t/t7599-hooks-allownoverify.sh`. The documentation is thorough, explaining the purpose, values, and emergency overrides, and explicitly notes that this is a workflow guardrail, not a security boundary. The patch is well-structured, with clear commit messages and test coverage for edge cases like config precedence and CLI overrides.

This addresses a real need in managed environments or CI workflows where accidental hook bypass can cause issues. The design is opt-in (backward-compatible) and includes escape hatches for emergencies, making it a pragmatic addition. The patch looks mature and ready for review, with no obvious loose ends.
