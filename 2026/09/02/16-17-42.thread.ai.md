Subject: [PATCH v4] hooks: introduce hooks.allowNoVerify to control --no-verify bypass
Series version: v4 (test coverage extended to `git am`)
Originating author: Alessio Attilio (via GitGitGadget)
Thread type: patch series

Core problem or goal
Introduce a new configuration option `hooks.allowNoVerify` that allows administrators to prevent accidental or intentional bypass of client-side hooks via the `--no-verify` (`-n`) flag in `git commit`, `git push`, `git merge`, `git rebase`, and `git am`. The setting is opt-in (defaults to `allow` for backward compatibility) and is intended for managed environments or CI workflows where hook execution must be enforced. The v4 patch extends test coverage to `git am` without altering the core design: an ergonomic workflow guardrail, not a security boundary.

Current status
Rejected by maintainer (Junio C Hamano). No merge; series will not proceed without a major rethink.

Key technical details
- New config key: `hooks.allowNoVerify` (string, accepts `true`/`warn`/`false`; defaults to `true`)
- Commands affected: `commit`, `push`, `merge`, `rebase`, `am`
- Files touched: `builtin/am.c`, `builtin/commit.c`, `builtin/merge.c`, `builtin/push.c`, `builtin/rebase.c`, `hook.c` (validation logic in `validate_no_verify()`), `hook.h`, `Documentation/config/hooks.adoc`
- New test files: `t/t7599-hooks-allownoverify.sh` (comprehensive coverage of CLI overrides, config precedence, hook failure scenarios, emergency overrides, and all five commands)
- Emergency overrides: `GIT_ALLOW_NO_VERIFY=1` environment variable and `-c hooks.allowNoVerify=true` CLI flag
- No on-disk format changes; purely a client-side workflow guardrail

Open questions and loose ends
Maintainer objection: feature is too narrowly scoped (hooks-only) and risks a "slippery slope" of ever-more-complex configuration layers to prevent CLI overrides. Junio suggests a more general mechanism that could cover built-in verification steps (e.g., pre-commit format validation) as well as hooks, and opposes introducing a new `hooks.` configuration namespace for this purpose. No alternative design proposed; discussion effectively closed unless a fundamentally different approach is presented.

Participant positions
- **Junio C Hamano (maintainer)**: Rejects the feature as currently designed. Concerns: narrow scope (hooks-only), potential for configuration complexity creep, and lack of generality to cover built-in verification steps. Position is final unless a major rethink is offered.
