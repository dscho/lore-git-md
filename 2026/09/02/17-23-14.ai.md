This is a feature patch introducing the `hooks.allowNoVerify` configuration option, now at v3. It is part of a self-contained series that has evolved from v1 and v2 based on feedback, expanding from a binary allow/deny model to a three-tiered control (`true`/`warn`/`false`) and adding emergency override mechanisms.

The patch centralizes validation logic in `hook.c` via a new `validate_no_verify()` function, which is called by all commands that support `--no-verify` (`commit`, `push`, `merge`, `rebase`, `am`). The configuration defaults to `true` (allowing bypass as before) but can be set to `warn` (permit with a warning) or `false` (abort with advice). Emergency overrides are provided via the `GIT_ALLOW_NO_VERIFY=1` environment variable or `-c hooks.allowNoVerify=true` on the command line, preventing destructive workarounds like removing hook files.

Key technical details include the new config key (`hooks.allowNoVerify`), the affected commands and files (`builtin/am.c`, `builtin/commit.c`, `builtin/merge.c`, `builtin/push.c`, `builtin/rebase.c`, `hook.c`, `hook.h`), and a comprehensive test suite (`t/t7599-hooks-allownoverify.sh`) covering CLI overrides, config precedence, hook failure scenarios, and emergency overrides. The v3 changes simplify the configuration values (removing redundant aliases like `always`/`never`/`error`) and clarify the commit message to emphasize that this is an ergonomic workflow guardrail, not a security boundary.
