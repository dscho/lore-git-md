This thread began as a straightforward two-patch series from Jeff King (Peff) fixing a memory leak in Git’s submodule error path. The leak, flagged by Coverity, was plugged by ensuring a URL string is freed when submodule setup fails, and the fix is now under review with no objections. Alongside the bugfix, Peff noted an asymmetry in Git’s `parsed_object_pool` API—where pools are allocated via `new` but never explicitly freed—and explored a deeper cleanup to eliminate a redundant repository pointer in the pool structure.

That exploration has now expanded into a technical discussion about refactoring the object pool API. Peff proposes replacing repository-based lookup functions (e.g., `lookup_commit()`) with pool-based variants, arguing that the pool’s operations don’t actually depend on the repository. His prototype patch touches six files and introduces about 60 lines of churn, but he ultimately concludes the change isn’t worth pursuing yet due to the risk of exposing hidden dependencies and the circular header issues he previously identified. No one has weighed in on this idea, and it remains a solo exploration—interesting as a technical note but not actionable for now.

The original bugfix series is still the focus: patch 1/2 (making `repo_clear()` idempotent) is uncontroversial, and patch 2/2 (the leak fix with a new test) is equally straightforward. The series is under review, with no merge status changes, and the only loose end is Peff’s header dependency discussion, which is purely informational for future work. For now, the thread’s practical outcome is the memory leak fix, while the API cleanup remains a side conversation.
