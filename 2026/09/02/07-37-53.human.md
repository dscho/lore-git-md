This is a discussion about a usability footgun in Git's branch name validation, specifically whether porcelain commands should reject the branch name `@`.

Jeff King (Peff) responds to D. Ben Knoble's review of Bence Csókás's bug report. Peff confirms that the current behavior is technically correct—bare `@` is allowed in ref components for backwards compatibility—but agrees it is a usability trap. He points to an existing precedent: `git check-ref-format --branch` already rejects `HEAD` as a branch name, even though `HEAD` is a valid ref component. This suggests the `--branch` mode is intentionally stricter to prevent confusing or error-prone branch names in porcelain commands.

Peff proposes treating `@` the same way as `HEAD`: allow it in low-level ref operations but reject it in porcelain commands like `git branch` or `git switch -c`. He clarifies that only *bare* `@` should be blocked, not names like `foo@bar`, which are valid and less likely to cause confusion. The discussion is now focused on a targeted fix rather than a broad change to ref validation rules.

The tone is pragmatic and collaborative. Peff does not treat this as a bug but as an opportunity to improve usability by extending an existing pattern. No patch has been sent yet, but the thread has converged on a clear design direction: tighten `--branch` mode to reject bare `@` for consistency with `HEAD`. This looks like a straightforward, uncontroversial improvement that would close a small but real usability gap.
