This is a feature patch introducing a new configuration option, `hooks.allowNoVerify`. The patch adds a boolean setting that, when set to `false`, prevents users from bypassing Git hooks with the `--no-verify` (`-n`) flag in commands like `git commit`, `git push`, `git merge`, `git rebase`, and `git am`. The default remains `true`, preserving existing behavior unless explicitly configured otherwise.

The motivation is to provide an opt-in guardrail for workflows or managed environments (e.g., CI runners) where accidental hook bypasses could be problematic. The commit message and documentation emphasize that this is not a security feature—server-side enforcement remains the authoritative mechanism—but rather a local workflow safeguard. The implementation touches multiple built-in commands, each checking the configuration before allowing `--no-verify`, and includes a thorough test suite covering edge cases like CLI overrides, global vs. local config precedence, and hook execution when `--no-verify` is blocked.

The patch is well-structured: it adds a dedicated documentation file (`Documentation/config/hooks.adoc`), updates the main config index, and includes tests for all affected commands. The code changes are minimal and focused, adding only the necessary checks without altering existing logic. The test coverage is particularly strong, verifying both the blocking behavior and the continued execution of hooks when `--no-verify` is not used.

This looks like a thoughtful, well-executed contribution that addresses a real (if niche) workflow need without overreaching. The default behavior is preserved, so there’s no risk of breaking existing setups, and the implementation is clean enough that it’s unlikely to introduce regressions.
