Subject: Inconsistent newline handling between `git commit` and `git merge`
Series version: N/A (bug report)
Originating author: Simon Cheng
Thread type: bug report

Core problem or goal
Git’s `git commit -m MSG` and `git merge --no-ff -m MSG` handle commit-message newlines differently: `git commit` appends an extra newline before cleanup, while `git merge` does not. Under `commit.cleanup = whitespace` the difference is hidden, but under `commit.cleanup = strip` (which removes comments and trailing whitespace) a `prepare-commit-msg` hook’s output is concatenated with the merge message instead of appearing on a new line, leaving unwanted text in the final commit message.

Current status
Under review; no patch yet proposed. The report demonstrates the issue with reproduction steps (hook setup, `commit.cleanup = strip`, `git merge --no-ff -m "Merge message" BRANCH`) and shows the corrupted output (`"Merge message# My additional comments"`).

Key technical details
- Commands affected: `git merge --no-ff -m MSG` (non-interactive merge commits)
- Configuration involved: `commit.cleanup = strip`
- Hook involved: `prepare-commit-msg`
- On-disk format: commit message object
- Test coverage: none yet; reproduction steps provided in the report
- Git version: reproducible in 2.55.0

Open questions and loose ends
- Should `git merge` append a newline to match `git commit`’s behavior?
- Is this a behavioral inconsistency that warrants a fix, or is it an edge case that users should work around?

Participant positions
- Simon Cheng (author): reports the inconsistency and argues for matching `git commit`’s behavior to avoid user surprises.
