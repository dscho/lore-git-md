This is a maintainer rejection of a feature patch introducing `hooks.allowNoVerify`.

Junio C Hamano declines the patch, calling it the start of a "slippery slope" — if this configuration prevents accidental `--no-verify` bypass, the next step might be another setting to block CLI overrides like `-c hooks.allowNoVerify=true`, and so on. He also questions the design choice of limiting the mechanism to hooks, noting that similar verification steps (like built-in checks) could also be bypassed and might need the same protection. Finally, he expresses concern about introducing a new `hooks.` configuration hierarchy just for this purpose.

The patch itself — which adds an opt-in guardrail for `--no-verify` in `git commit`, `push`, `merge`, `rebase`, and `am` — is well-crafted, with thorough test coverage, clear documentation, and careful attention to backward compatibility. However, Junio’s feedback suggests the conceptual framing (a hooks-specific, opt-in workflow guardrail) does not align with his vision for how such controls should be structured in Git. The rejection is not about the code quality, but about the direction and scope of the feature.
