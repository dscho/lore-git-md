This is a **substantive review** from brian m. carlson that **opposes the `hooks.allowNoVerify` feature** on philosophical and practical grounds, aligning with Junio’s earlier rejection.

The review argues that `--no-verify` is a deliberate user choice and that Git should not introduce configuration layers to restrict it. brian emphasizes that hooks are inherently user-controlled (not security boundaries) and that forcing their use—whether via this feature or by installing hooks by default—is counter to Git’s design principles. They cite the Git FAQ’s stance against forced hooks and note that bypassing hooks entirely (e.g., via `core.hooksPath=/dev/null`) is trivial, undermining any attempt to enforce hook execution.

The tone is firm but not dismissive: brian acknowledges the use case (managed environments) but frames it as a workflow anti-pattern rather than a gap in Git’s functionality. They suggest that repository owners should avoid installing hooks by default instead of adding complexity to Git to accommodate forced hook execution. No technical flaws in the patch itself are raised; the objection is purely conceptual. This reinforces the maintainer’s rejection and further closes the door on the current design.
