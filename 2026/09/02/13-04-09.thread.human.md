This thread is about a bugfix series that addresses a long-standing edge case in Git's pathspec handling, where an exclude pathspec (like `:!unrelated/path`) appearing first in the list could cause `common_prefix_len()` to incorrectly return zero as the common prefix, even when later positive pathspecs (e.g., `foo/bar` and `foo/baz`) share a directory (`foo/`). The series also fixes a memory-safety issue in `match_pathspec_with_flags()` that could trigger a heap-buffer-overflow when negative pathspecs were shorter than the common prefix derived from positive pathspecs.

The series, authored by Yannik Tausch, has evolved into a three-patch sequence in Junio C Hamano's queue: a preparatory refactoring (to declare certain fields as `const`), a memory-safety fix, and the core fix for the common prefix calculation. Junio has confirmed the integration plan, creating a synthetic merge base to apply the patches cleanly, and the series is now queued for merging. Elijah Newren reviewed the patches and identified a gap in the existing regression test, noting that while it reliably triggers the heap-buffer-overflow under AddressSanitizer, it doesn’t deterministically fail without ASan. He proposed an additional test case to address this.

In the latest email, Junio endorses Elijah’s observation and highlights a second, independent bug: when the common prefix derived from positive pathspecs is incorrectly applied to a negative pathspec of sufficient length, the matching logic can produce false positives. He provides a minimal reproduction (`git ls-files a/b ':!x/b' a/c`) showing that the current `master` branch incorrectly excludes `a/b/m` because the prefix-stripped negative pathspec `b` (from `:!x/b`) matches the prefix-stripped path `b/m`. This demonstrates that the fix restores both memory safety and logical correctness. The discussion remains focused on test coverage, and no further changes to the design or implementation are expected. The series is effectively ready for integration.
