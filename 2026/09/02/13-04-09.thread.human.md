This thread is a two-patch bugfix series from Yannik Tausch that fixes a long-standing edge case in Git's pathspec handling. The issue occurs when an exclude pathspec (like `:!unrelated/path`) appears first in the list, causing `common_prefix_len()` to incorrectly return zero as the common prefix length even when later positive pathspecs (such as `foo/bar` and `foo/baz`) share a directory (`foo/`). The series also addresses a related memory-safety issue where negative pathspecs shorter than the common prefix could trigger a heap-buffer-overflow.

The v2 series has converged on Junio C Hamano's suggested output-parameter design (`common_prefix_len(pathspec, &matched_prefix)`), which avoids introducing a new struct and minimizes changes to callers. The series is now split into two patches: the first ensures exclude pathspecs are matched against the full pathname (preventing the buffer overflow), and the second refactors `common_prefix_len()` to derive the common prefix from the first non-exclude pathspec. The implementation is clean, narrowly scoped to `dir.c`, and includes thorough test coverage in both the functional test suite (`t/t6132-pathspec-exclude.sh`) and unit tests (`t/unit-tests/u-dir.c`).

Discussion has settled on the design approach, with only a minor detail (whether the output parameter should use `char **` or `const char **`) still open. No other reviewers have weighed in yet, but the series appears effectively ready for merging. The fix addresses both the memory-safety issue and the common prefix edge case without risking broader regressions.
