Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: two-patch series (v2 posted)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a deadlock or crash in the `rerere` subsystem introduced in Git 2.54 where background maintenance (`git rerere gc`)—triggered by the geometric maintenance strategy after every commit—races with an in-progress rebase to acquire the `MERGE_RR.lock`, causing the rebase to fail when the lock is held. The solution is a two-part series: (1) disable background maintenance during rebase via config overrides (`-c gc.auto=false -c maintenance.auto=false` passed to all `git commit`/`merge` invocations and via `GIT_CONFIG_PARAMETERS` for exec commands), and (2) fix error handling in `rerere_setup()` to propagate errors instead of dying, with improved locking logic. Patrick Steinhardt has identified the geometric maintenance strategy’s aggressiveness (triggering `rerere gc` after every commit with even a single `rr-cache` entry) as the root cause and plans a separate patch series to adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility rather than just counting entries.

Key technical details
- Files touched: `rerere.c` (error propagation, locking logic), `sequencer.c` (config overrides), `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior: `rerere_setup()` returns errors instead of dying, using `LOCK_REPORT_ON_ERROR` for better error reporting. Lock acquisition now waits up to `rerere.lockTimeout` (default: 1 second) for non-maintenance callers (e.g., `git commit`), while background maintenance (`git rerere gc`) passes a timeout of 0 to skip the lock entirely. The `RERERE_SKIP_LOCKED` branch is unified with the timeout logic (timeout=0 for skip). Sequencer disables maintenance via config overrides during rebase.
- Locking changes: No longer uses `hold_lock_file_for_update_timeout()`; error messages are more descriptive, and the code is simplified by merging skip and timeout logic. The 1-second wait is a preexisting behavior (only exposed by the geometric maintenance strategy’s aggressiveness) and is retained to avoid silent failures or crashes.
- Test case: 20,000-entry `rr-cache` to trigger the race; focus on verifying maintenance is disabled during rebase and error reporting is accurate.
- Architectural context: The geometric maintenance strategy’s aggressive triggering of `rerere gc` (after every commit with even a single `rr-cache` entry) is the root cause. Patrick’s planned patch series will address this separately by adjusting `maintenance.rerere-gc.auto` to consider garbage-collection eligibility.
