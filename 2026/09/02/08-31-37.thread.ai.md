Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: two-patch series (v3 locking patch posted; sequencer config-override patch pending)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a race condition in the `rerere` subsystem where background maintenance (`git rerere gc`)—triggered by `git gc`, auto-maintenance, or the geometric maintenance strategy—prunes entries in the shared `rr-cache` directory while a foreground operation (e.g., rebase) is recording conflicts. The race can cause the foreground operation to fail when the lock is held, though the lock itself is per-worktree and does not directly contend between worktrees. The solution remains a two-part series: (1) improve error handling in `rerere_setup()` with configurable locking timeouts and unified error reporting, and (2) disable background maintenance (`gc.auto` and `maintenance.auto`) during rebase via config overrides. The root cause is now framed as any background `rerere gc` interfering with foreground operations, not solely the geometric maintenance strategy’s aggressiveness, though the latter’s defaults remain a contributing factor. Patrick Steinhardt plans a separate patch series to adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility.

Key technical details
- Files touched: `rerere.c` (error propagation, locking logic), `rerere.h` (new flags and config key), `builtin/rerere.c`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior: `rerere_setup()` returns errors instead of dying, using `hold_lock_file_for_update_timeout()` with a configurable timeout (`rerere.lockTimeout`, default: 1000 milliseconds). Non-maintenance callers (e.g., `git commit`, `git merge`, `git rebase`) wait up to the timeout before warning and proceeding without rerere; background maintenance (`git rerere gc`) passes a timeout of 0 to skip the lock entirely (`RERERE_NOWAIT`). Explicit `git rerere`, `git rerere forget`, and `git rerere clear` commands now wait for the full timeout before failing, aligning with other callers. The `RERERE_SKIP_LOCKED` flag is replaced by `RERERE_NOWAIT` (timeout=0) and `RERERE_LOCK_OR_DIE` (fail immediately if lock is held). Error messages are hand-rolled to avoid misleading advice about terminating other Git processes. A `BUG()` assertion checks for incompatible flag combinations (e.g., `RERERE_NOWAIT` with `RERERE_LOCK_OR_DIE`).
- `rerere_clear()` (used by `git rebase --abort` and `--skip`) now fails immediately if the lock is held, matching the behavior of `git rerere clear` and avoiding silent corruption of the `MERGE_RR` file. This removes the need for caller updates in `am.c` and `rebase.c`.
- Config overrides: During rebase, both the merge and apply backends will pass `-c gc.auto=false -c maintenance.auto=false` to `git commit`, `git merge`, and exec commands. The merge backend will also call `run_auto_maintenance()` at the end of the rebase sequence to ensure consistency with the apply backend and avoid leaving maintenance disabled indefinitely.
- Error handling: If `rerere_setup()` fails due to a held lock, the rebase stops at the conflict (without rerere recording or replay) and allows `--continue` to proceed normally. No rescheduling of the pick is required. `git rerere gc` is the only command that silently skips when the lock is held (as it’s a best-effort cleanup); all other commands (`git rerere`, `git rerere forget`, `git rerere clear`) fail after waiting for the timeout.
- Locking changes: The 1-second wait is retained as preexisting behavior to avoid silent failures or crashes. The patch is based on `maint` and resolves a trivial conflict with the recent lockfile helper refactoring (`2e486bfbf7`).
- Test case: 20,000-entry `rr-cache` to trigger the race; focus on verifying error reporting is accurate, the timeout allows rebases to proceed after maintenance completes, and maintenance is disabled during rebase. Tests now also cover the behavior of `git rerere`, `git rerere forget`, and `git rerere clear` under a held lock, and the immediate failure of `rerere_clear()`.
- Architectural context: The geometric maintenance strategy’s aggressive triggering of `rerere gc` (after every commit with even a single `rr-cache` entry) exacerbates the race but is not the sole cause. The root issue is any background `rerere gc` interfering with foreground operations. Patrick’s planned patch series will adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility, reducing the frequency of background maintenance.
- User experience: Background maintenance runs are daemonized, closing standard descriptors and redirecting output to `/dev/null`, so their warnings do not mix with foreground output. On Windows, where daemonization isn’t possible, maintenance runs in the foreground of the triggering commit, avoiding the race entirely. The only warning users see is from the foreground command (e.g., rebase) when it gives up waiting for the lock. Junio’s review clarifies that the rebase should **not** proceed without rerere recording, as silently skipping risks losing the user’s conflict resolution. The commit message will be updated to reflect that the rebase stops at the conflict (without recording or replay) and allows `--continue` to proceed normally, rather than silently skipping rerere.

Open questions and loose ends
1. Should rebases using the merge backend run maintenance at all? (Deferred to future discussion; no new input.)
2. Is the fork-based background maintenance design inherently flawed for interactive operations? (Phillip Wood’s critique remains unresolved; Patrick’s review does not address this; Junio’s review aligns with Phillip’s usability concerns.)
3. How will Patrick’s proposed changes to `maintenance.rerere-gc.auto` interact with the rebase-specific config overrides? (No overlap is expected, but coordination may be needed.)
4. Is the 1-second wait sufficient for all use cases, or should it be configurable? (Configurable via `rerere.lockTimeout`; no new input on default value.)
5. Should there be a single maintenance run at the end of the rebase sequence? (Phillip Wood insists on consistency between backends; this will likely be included in the sequencer patch.)
6. Phillip Wood reiterates that garbage collection is useless mid-rebase—all objects and `rr-cache` entries created during the rebase are too fresh to be collected. This position remains unresolved.
7. Documentation clarity: Junio notes that the current documentation (`git rerere gc does not retry`) is misleading, as all commands respect the timeout but `gc` is the only one that proceeds without error. The commit message will now explicitly state that `gc` "gives up at once" to address this. Junio’s review further clarifies that the commit message must not imply the rebase proceeds without rerere recording; the rebase stops at the conflict and allows `--continue` to proceed normally.

Related work
- The race was introduced by the geometric maintenance strategy in Git 2.54, which triggers `rerere gc` after every commit with even a single `rr-cache` entry.
- Similar lock contention issues have arisen elsewhere due to the fork-based background maintenance design.
- Patrick’s planned patch series will address the geometric maintenance strategy’s defaults, which may reduce the need for rebase-specific workarounds.
