Thread identity
Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: two-patch series (v4 locking patch in progress; sequencer config-override patch pending)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a race condition in the `rerere` subsystem where background maintenance (`git rerere gc`)—triggered by `git gc`, auto-maintenance, or the geometric maintenance strategy—prunes entries in the shared `rr-cache` directory while a foreground operation (e.g., rebase) is recording conflicts. The race can cause the foreground operation to fail when the lock is held. The solution is a two-part series: (1) improve error handling in `rerere_setup()` with configurable locking timeouts and unified error reporting, and (2) disable background maintenance (`gc.auto` and `maintenance.auto`) during rebase via config overrides. The root cause is any background `rerere gc` interfering with foreground operations; the geometric maintenance strategy’s aggressiveness exacerbates the issue but is not the sole cause. Patrick Steinhardt plans a separate patch series to adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility.

Key technical details
- Files touched: `rerere.c` (error propagation, locking logic), `rerere.h` (new flags and config key), `builtin/rerere.c`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior: `rerere_setup()` returns errors instead of dying, using `hold_lock_file_for_update_timeout()` with a configurable timeout (`rerere.lockTimeout`, default: 1000 milliseconds). All non-maintenance callers (e.g., `git commit`, `git merge`, `git rebase`) wait up to the timeout before failing if the lock is still held. Background maintenance (`git rerere gc`) passes a timeout of 0 to skip the lock entirely (`RERERE_NOWAIT`). Explicit `git rerere`, `git rerere forget`, and `git rerere clear` commands now wait for the full timeout before failing, aligning with other callers. The `RERERE_SKIP_LOCKED` flag is replaced by `RERERE_NOWAIT` (timeout=0). Error messages are hand-rolled to avoid misleading advice about terminating other Git processes. A `BUG()` assertion checks for incompatible flag combinations (e.g., `RERERE_NOWAIT` with a non-zero timeout). If `rerere_setup()` fails due to a held lock, the rebase stops at the conflict (without rerere recording or replay) and allows `--continue` to proceed normally. `rerere_clear()` (used by `git rebase --abort` and `--skip`) fails immediately if the lock is held, avoiding silent corruption of the `MERGE_RR` file.
- Config overrides: During rebase, both the merge and apply backends will pass `-c gc.auto=false -c maintenance.auto=false` to `git commit`, `git merge`, and exec commands. The merge backend will also call `run_auto_maintenance()` at the end of the rebase sequence to ensure consistency with the apply backend.
- Locking changes: The 1-second wait is retained as preexisting behavior to avoid silent failures or crashes. The patch is based on `maint` and resolves a trivial conflict with the recent lockfile helper refactoring (`2e486bfbf7`).
- Test case: 20,000-entry `rr-cache` to trigger the race; focus on verifying error reporting is accurate, the timeout allows rebases to proceed after maintenance completes, and maintenance is disabled during rebase. Tests now also cover the behavior of `git rerere`, `git rerere forget`, and `git rerere clear` under a held lock.
- Architectural context: The geometric maintenance strategy’s aggressive triggering of `rerere gc` (after every commit with even a single `rr-cache` entry) exacerbates the race but is not the sole cause. The root issue is any background `rerere gc` interfering with foreground operations. Patrick’s planned patch series will adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility, reducing the frequency of background maintenance.

Current status
v4 of the locking patch is in progress, incorporating Junio’s feedback to remove the special-case behavior that allowed foreground commands to proceed without `rerere` after a timeout. The patch now ensures all commands (except `git rerere gc`) wait the full configurable timeout and then fail if the lock is still held. The `RERERE_LOCK_OR_DIE` flag has been dropped, simplifying the patch. The series is under review, with no objections to the revised approach. The sequencer config-override patch (disabling maintenance during rebase) remains pending.

Open questions and loose ends
1. Should rebases using the merge backend run maintenance at all? (Deferred to future discussion; no new input.)
2. Is the fork-based background maintenance design inherently flawed for interactive operations? (Phillip Wood’s critique remains unresolved; Patrick’s review does not address this.)
3. How will Patrick’s proposed changes to `maintenance.rerere-gc.auto` interact with the rebase-specific config overrides? (No overlap is expected, but coordination may be needed.)
4. Is the 1-second wait sufficient for all use cases, or should it be configurable? (Configurable via `rerere.lockTimeout`; no new input on default value.)
5. Should there be a single maintenance run at the end of the rebase sequence? (Phillip Wood insists on consistency between backends; this will likely be included in the sequencer patch.)
6. Phillip Wood reiterates that garbage collection is useless mid-rebase—all objects and `rr-cache` entries created during the rebase are too fresh to be collected. This position remains unresolved.
7. Thomas Bachem has floated the idea of writing the rebase stop state *before* invoking `rerere` to allow `--continue` even if the lock is held, but this will be explored separately.
