Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: single patch (no series)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a deadlock or crash in the `rerere` subsystem introduced in Git 2.54 where background maintenance (`git rerere gc`)—triggered by the geometric maintenance strategy after every commit—races with an in-progress rebase to acquire the `MERGE_RR.lock`, causing the rebase to fail when the lock is held. The patch proposes a timeout-based mitigation, but the deeper issue is architectural: background maintenance should not run during interactive operations like rebase.

Current status
Under review; no prior versions posted. The patch introduces a `rerere.lockTimeout` configuration (default 1000 ms) and a `RERERE_SKIP_LOCKED` flag to allow callers to wait for the lock or skip maintenance when the lock is held. Phillip Wood’s review argues this approach is insufficient and advocates disabling background maintenance entirely during rebase via `-c gc.auto=false -c maintenance.auto=false` in the sequencer.

Key technical details
- Files touched: `rerere.c`, `rerere.h`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`
- New config key: `rerere.lockTimeout` (milliseconds, default 1000)
- New flag: `RERERE_SKIP_LOCKED` for `setup_rerere()`
- Lock acquisition now uses `hold_lock_file_for_update_timeout()` instead of `LOCK_DIE_ON_ERROR`
- Test case uses a 20,000-entry `rr-cache` to reliably trigger the race
- Additional bugs identified: sequencer’s `rerere_setup()` errors should propagate to the caller (not die), and the background maintenance process’s fork-based design is inherently prone to lock contention

Open questions and loose ends
1. **Architectural direction**: Is the timeout-based fix acceptable, or should background maintenance be disabled during rebase (Phillip’s preferred solution)?
2. **Error handling**: Should the sequencer propagate `rerere_setup()` errors instead of dying?
3. **Maintenance process design**: Is the fork-based background maintenance approach fundamentally flawed for interactive operations?
4. **Commit message**: The current message omits discussion of the timeout solution’s tradeoffs (e.g., forcing the sequencer to block or fail).

Participant positions
- **Phillip Wood**: Substantive review; opposes the timeout-based fix as papering over the root cause. Advocates disabling background maintenance during rebase via config overrides and fixing the sequencer’s error handling. Notes the background maintenance process’s design is inherently problematic.

Related work
- The race was introduced by the geometric maintenance strategy in Git 2.54.
- Similar lock contention issues have arisen elsewhere due to the fork-based background maintenance design.
- The fix’s timeout pattern follows established Git lock-timeout conventions, but Phillip argues this is not the right pattern for this context.
