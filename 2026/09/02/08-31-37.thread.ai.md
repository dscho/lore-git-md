Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: two-patch series (v2 locking patch posted; sequencer config-override patch now scoped and aligned)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a deadlock or crash in the `rerere` subsystem introduced in Git 2.54 where background maintenance (`git rerere gc`)—triggered by the geometric maintenance strategy after every commit—races with an in-progress rebase to acquire the `MERGE_RR.lock`, causing the rebase to fail when the lock is held. The solution is a two-part series: (1) fix error handling in `rerere_setup()` to propagate errors instead of dying, with improved locking logic (timeout=1s for non-maintenance callers, timeout=0 for background maintenance), and (2) disable background maintenance (`gc.auto` and `maintenance.auto`) during rebase by passing `-c gc.auto=false -c maintenance.auto=false` to `git commit`, `git merge`, and exec commands in both the merge and apply backends. Patrick Steinhardt has identified the geometric maintenance strategy’s aggressiveness (triggering `rerere gc` after every commit with even a single `rr-cache` entry) as the root cause and plans a separate patch series to adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility rather than just counting entries.

Key technical details
- Files touched: `rerere.c` (error propagation, locking logic), `sequencer.c` (config overrides for both merge and apply backends), `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior: `rerere_setup()` returns errors instead of dying, using `LOCK_REPORT_ON_ERROR` for better error reporting. Lock acquisition now waits up to `rerere.lockTimeout` (default: 1 second) for non-maintenance callers (e.g., `git commit`), while background maintenance (`git rerere gc`) passes a timeout of 0 to skip the lock entirely. The `RERERE_SKIP_LOCKED` branch is unified with the timeout logic (timeout=0 for skip). The 1-second wait is a preexisting behavior (only exposed by the geometric maintenance strategy’s aggressiveness) and is retained to avoid silent failures or crashes.
- Config overrides: During rebase, both the merge and apply backends now pass `-c gc.auto=false -c maintenance.auto=false` to `git commit`, `git merge`, and exec commands. The merge backend will also call `run_auto_maintenance()` at the end of the rebase sequence to ensure consistency with the apply backend and avoid leaving maintenance disabled indefinitely.
- Error handling: If `rerere_setup()` fails due to a held lock, the rebase stops at the conflict (without rerere recording or replay) and allows `--continue` to proceed normally. No rescheduling of the pick is required.
- Locking changes: No longer uses `hold_lock_file_for_update_timeout()`; error messages are more descriptive, and the code is simplified by merging skip and timeout logic. The patch is based on `maint` and conflicts with a recent lockfile helper refactoring (`d43f701d32`); resolution is straightforward (adopt the repo-scoped helper).
- Test case: 20,000-entry `rr-cache` to trigger the race; focus on verifying error reporting is accurate, the 1-second wait allows rebases to proceed after maintenance completes, and maintenance is disabled during rebase.
- Architectural context: The geometric maintenance strategy’s aggressive triggering of `rerere gc` (after every commit with even a single `rr-cache` entry) is the root cause. Patrick’s planned patch series will address this separately by adjusting `maintenance.rerere-gc.auto` to consider garbage-collection eligibility.
