Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: single patch (no series)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a deadlock or crash in the `rerere` subsystem introduced in Git 2.54 where background maintenance (`git rerere gc`) and an in-progress rebase both attempt to acquire the `MERGE_RR.lock`, causing the rebase to fail when the lock is held.

Current status
Under review; no prior versions posted. The patch is a clean, targeted fix with a new `rerere.lockTimeout` configuration (default 1000 ms) that allows callers to wait for the lock instead of failing immediately. Background `rerere gc` now skips its run and issues a warning when the lock is held, matching the behavior of other maintenance tasks.

Key technical details
- Files touched: `rerere.c`, `rerere.h`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`
- New config key: `rerere.lockTimeout` (milliseconds, default 1000)
- New flag: `RERERE_SKIP_LOCKED` for `setup_rerere()`
- Lock acquisition now uses `hold_lock_file_for_update_timeout()` instead of `LOCK_DIE_ON_ERROR`
- Test case uses a 20,000-entry `rr-cache` to reliably trigger the race

Open questions and loose ends
None raised yet; the patch includes both positive and negative test cases for the new timeout behavior and demonstrates backward compatibility (timeout=0 restores old behavior).

Participant positions
None recorded yet; the patch has just been posted.

Related work
The race was introduced by the geometric maintenance strategy in Git 2.54; the fix follows established lock-timeout patterns used elsewhere in Git.
