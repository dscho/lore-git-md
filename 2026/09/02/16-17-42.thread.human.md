This thread is about a proposed configuration option, `hooks.allowNoVerify`, that would let administrators prevent users from bypassing client-side hooks with the `--no-verify` flag in commands like `git commit`, `git push`, and `git am`. The patch, now in its fourth version, was intended for managed environments or CI workflows where hook execution must be enforced, but it has been firmly rejected by Junio Hamano, the maintainer.

The design is opt-in (defaulting to `allow` for backward compatibility) and includes emergency overrides via an environment variable or CLI flag. The v4 update added test coverage for `git am` but left the core design unchanged. Junio’s objection centers on the feature’s narrow scope—it targets only hooks—and the risk of creating a "slippery slope" of increasingly complex configuration layers to block CLI overrides. He argues that a more general mechanism, covering built-in verification steps as well as hooks, would be preferable, and he opposes introducing a new `hooks.` configuration namespace for this purpose.

The latest email from brian m. carlson reinforces this rejection, framing the feature as philosophically misaligned with Git’s design. Brian argues that `--no-verify` is a deliberate user choice and that Git should not restrict it, citing the Git FAQ’s stance against forced hooks. They note that bypassing hooks entirely (e.g., by setting `core.hooksPath=/dev/null`) is trivial, making any enforcement mechanism ineffective. While they acknowledge the use case for managed environments, they describe it as a workflow anti-pattern rather than a gap in Git’s functionality. No technical flaws in the patch are raised; the opposition is purely conceptual. With both the maintainer and a prominent contributor aligned against the current design, the series is effectively closed unless a fundamentally different approach is proposed.
