This is the fourth patch in Christian Couder’s six-patch series introducing a new `parse-options` sub-API for early argument scanning. The series as a whole fixes a recurring class of argument-parsing bugs where hand-rolled early scans (looking for `--` or special flags) fail to account for option values that appear as separate arguments.

This patch factors out the logic that determines whether a `parse-options` option takes an argument into a new helper function, `parse_options_takes_argument()`. The logic was previously open-coded in `show_gitcomp()`, which uses it to decide whether to append an `=` suffix when completing option names. The new helper will be reused in the next patch to implement the early scan API, which needs the same logic to skip option values correctly.

The implementation is straightforward: the function returns true for option types that take arguments (`OPTION_STRING`, `OPTION_FILENAME`, `OPTION_INTEGER`, `OPTION_UNSIGNED`, and `OPTION_CALLBACK`) unless they are marked with `PARSE_OPT_NOARG`, `PARSE_OPT_OPTARG`, or `PARSE_OPT_LASTARG_DEFAULT`. The patch updates `show_gitcomp()` to use the new helper, replacing its open-coded logic with a single call.

This is a **clean refactoring** that prepares the ground for the early scan API. The change is minimal, well-motivated, and does not alter behavior. The commit message clearly explains why the refactoring is needed and how it will be used. The patch is uncontroversial and should not attract significant discussion.
