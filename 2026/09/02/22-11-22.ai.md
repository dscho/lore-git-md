This is the second patch in Christian Couder’s six-part series introducing `early_scan_options()`, a new sub-API for Git’s `parse-options` infrastructure. The email is a **substantive review** from Junio C Hamano focusing on the core API design and implementation details of the first patch.

Junio’s feedback centers on two main concerns. First, he questions the long-term usability of the new API, noting that users must spell options in full (no abbreviations) and that this restriction may persist even after future improvements. While he acknowledges this is not a regression from the current ad-hoc early scanners, he implies the design could create technical debt if the API later evolves to accept the full `struct option[]` array. Second, he critiques the implementation of `find_early_scan_option()`, pointing out that the function’s parameter naming (`options`) is misleading since it operates on a single element of the array, and that the logic for handling option values is inconsistent—it checks `takes_value` for stuck arguments (`--option=value`) but not for separate arguments (`--option value`). He suggests that even a simplified early scanner could use the real `struct option[]` array, reducing programmer burden and aligning better with the existing `parse_options()` infrastructure.

The review is **technical and forward-looking**, engaging with both the immediate implementation and the API’s future maintainability. Junio does not reject the patch outright but signals that the design may need rethinking before the series can progress. The discussion leaves open whether the current `early_scan_option` structure will remain or be replaced by a more integrated approach. No new tests or behavioral changes are proposed in this reply; the focus is purely on design and code clarity.
