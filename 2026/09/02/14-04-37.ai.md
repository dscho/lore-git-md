This is a bug report about an inconsistency in how Git handles commit message newlines between `git commit` and `git merge`.

The author, Simon Cheng, describes a scenario where `git commit -m MSG` appends an extra newline to the message before cleanup, but `git merge --no-ff -m MSG` does not. Under the default `commit.cleanup = whitespace` setting, this difference is invisible because the extra newline is stripped. However, when using `commit.cleanup = strip` (which removes comments and trailing whitespace) alongside a `prepare-commit-msg` hook that injects comments, the missing newline causes the hook’s output to concatenate with the merge message instead of appearing on a new line. This breaks the cleanup process, leaving unwanted text in the final commit message.

The report includes clear reproduction steps: setting up the hook, configuring `commit.cleanup = strip`, and running `git merge --no-ff -m "Merge message" BRANCH`. The expected behavior is a clean merge message, but the actual result is a corrupted message like `"Merge message# My additional comments"`. The author acknowledges this might not be a "bug" in the strictest sense but argues it’s an inconsistency that creates user surprises.

Key technical details: the issue affects non-interactive merge commits, involves the `prepare-commit-msg` hook and `commit.cleanup` configuration, and is reproducible in Git 2.55.0. The report does not propose a patch but suggests `git merge` should match `git commit`’s behavior by appending a newline. This is likely to resonate with contributors who value consistency in Git’s plumbing commands.
