Subject: [PATCH 0/2] fix memory leak in submodule error path
Series version: v1 (initial submission)
Originating author: Jeff King (Peff)
Thread type: patch series (bugfix)

Core problem or goal
Plug a memory leak in the submodule error path where a URL string allocated during repository setup was not freed when setup failed. The leak was flagged by Coverity after nearby code movement made it newly visible, but likely existed for some time. Additionally, Peff explored a deeper cleanup of the `parsed_object_pool` API asymmetry (allocating via `new` without a corresponding `free`, and a redundant `repo` pointer in the pool structure) but concluded both the asymmetry and the redundancy are too invasive to address in the current series due to circular header dependencies and code churn. The exploratory discussion expanded to include the maintainer’s perspective on the architectural tension between decoupling the parsed object pool from the repository and preserving repository-scoped properties (e.g., hash algorithm), which are currently tied to the pool. Patrick Steinhardt later questioned whether propagating the full repository structure to subsystems is necessary, suggesting that passing only the relevant pieces (e.g., hash algorithm and compatibility hash) might be cleaner, but ultimately abandoned the idea due to complexity.

Current status
Under review. Two-patch series remains unchanged:
1. Make `repo_clear()` idempotent (defensive groundwork, patch 1/2 uncontroversial).
2. Add the missing `free()` call in `submodule--helper` and add a test in `t/t7426-submodule-get-default-remote.sh` (patch 2/2). Patrick Steinhardt’s **substantive but non-blocking** review suggestion (initialize `ret` at declaration) still stands but does not block the series.
No merge status changes; remains in review. The exploratory discussion about the `parsed_object_pool` API remains open but has not produced actionable patches or objections to the bugfix.

Key technical details
Files touched: `builtin/submodule--helper.c`, `repository.c`, `t/t7426-submodule-get-default-remote.sh` (bugfix); `alloc.c`, `alloc.h`, `commit.c`, `commit.h`, `object.c`, `object.h` (exploratory discussion only).
New symbols: none (internal plumbing only).
Behavior change: none (bugfix only).
On-disk format: unchanged.
Test coverage: new test in `t/t7426-submodule-get-default-remote.sh` verifies the leak is plugged by triggering the error path with an uninitialized submodule and checking for the expected error message under `SANITIZE=leak`.
Idempotency note: `repo_clear()` now safely handles double-calls due to a NULL guard on `parsed_objects`.
API asymmetry note: `parsed_object_pool` is allocated via `new` without a corresponding `free`; the pool also holds a redundant `repo` pointer that is only used to access `repo->parsed_objects`, which is always the pool itself. Both issues are noted as potential future cleanups but are left out of scope due to circular dependencies between `repository.h`, `object.h`, and `hash.h` (when `USE_THE_REPOSITORY_VARIABLE` is set) and the risk of exposing hidden dependencies in approximately 9 files.
Architectural tension: The parsed object pool currently depends on the repository’s hash algorithm (SHA-1 or SHA-256), a design choice Junio C Hamano reaffirmed as intentional and not easily decoupled. This dependency complicates efforts to make the pool an implementation detail of the object database rather than tied to the repository. Patrick Steinhardt later suggested that passing only the hash algorithm and compatibility hash—rather than the full repository—might be a cleaner approach, but abandoned the idea due to complexity.
Refactoring proposals:
- Peff suggested introducing pool-based lookup functions (e.g., `lookup_commit_via_pool()`) alongside existing repository-based wrappers to avoid rewriting all callers.
- Patrick Steinhardt initially advocated for a more decisive refactoring (eliminating the redundant `repo` pointer entirely) but later questioned whether propagating the full repository to subsystems is necessary, suggesting a more granular approach (passing only the hash algorithm and compatibility hash) before abandoning the idea.
- Junio’s response highlights the architectural constraint imposed by the hash algorithm dependency, leaving the discussion open but cautioning against assumptions about decoupling feasibility.
Fix mechanics: `get_default_remote_submodule()` now uses a dedicated `out` path with `goto` to ensure `repo_clear(&subrepo)` and `free(url)` are called even when `repo_submodule_init()` fails, preserving the function’s error-reporting behavior. Patrick Steinhardt’s review suggests initializing the `ret` variable to `0` at declaration to make the control flow more explicit and silence compiler warnings.
