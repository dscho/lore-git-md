This is a review reply in the ongoing bugfix series to prevent unsafe commit operations during conflict resolution. Phillip Wood raises a nuanced question about the second patch in Elijah Newren’s v4 series, which removes the restriction on `git commit <paths>` when a rebase pick becomes empty.

The patch itself is small and uncontroversial in its implementation—it simply deletes two lines of code and updates a test—but Phillip’s feedback highlights a subtle inconsistency in Git’s behavior. He notes that when Git stops for a commit that becomes empty, it writes `CHERRY_PICK_HEAD` and `.git/MERGE_MSG`, signaling that the user might want to preserve the commit with `git commit --allow-empty`. This makes him question whether allowing a partial commit in this state is the right call, since `git cherry-pick` still disallows partial commits even when a commit becomes empty. On the other hand, he acknowledges that if the user explicitly asked to edit the commit (e.g., via an interactive rebase `edit` directive), a partial commit might be a reasonable way to modify it.

Phillip’s review is substantive but measured: he doesn’t object to the change, nor does he insist on keeping the restriction. Instead, he flags the inconsistency as something worth considering, though he admits he doesn’t have a strong opinion either way. This leaves the door open for Elijah or Junio to weigh in on whether the inconsistency is worth addressing—or whether the simplicity of removing the restriction (as Junio previously argued) outweighs the edge case.

The patch remains technically sound and ready for integration, but Phillip’s feedback introduces a small wrinkle that might prompt a follow-up discussion or a minor adjustment in a future iteration. For now, the series is still on track for `next`.
