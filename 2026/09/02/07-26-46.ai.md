This is a **substantive follow-up discussion** in the `dk/use-nsec-runtime` series, which graduated to `next` on 2024-07-10. Jeff King (Peff) and D. Ben Knoble revisit the necessity of the `#ifndef NO_NSEC` guard around the `core.usenanosec` config handler, a detail that was previously considered settled. Peff initially questions whether the guard is redundant, arguing that platforms lacking nanosecond support would likely not enable the config, and the code would still work by faking nanosecond values as zero. However, he identifies a subtle edge case: if a user builds two Git versions (one with `NO_NSEC` and one without) on a system that *does* support nanosecond timestamps, an index generated by the non-`NO_NSEC` build could store real nanosecond values, which the `NO_NSEC` build would misinterpret as zero, potentially leading to false "racy" comparisons. This scenario is unlikely in practice but surfaces a correctness risk that was not fully explored in earlier reviews.

Knoble clarifies that the guard prevents reading nanosecond values on unsupported platforms, avoiding false negatives in racy checks, but also restricts users on `NO_NSEC` builds (e.g., from a distro) from enabling `core.useNanosec` without recompiling. Peff acknowledges the guard is reasonable given the complexity of eliminating `NO_NSEC` entirely, but the discussion highlights a trade-off between build-time restrictions and runtime flexibility. The exchange does not propose code changes—Knoble confirms the guard’s practical impact is minimal, and Peff agrees the guard can stay—but it adds nuance to the platform-compatibility discussion. A note in `Documentation/technical/racy-git.adoc` about mixed-build risks might be warranted, though neither participant pushes for it.

The thread is **not a blocker** for the series, which remains in `next` and is technically complete. The discussion is primarily theoretical, focusing on edge cases rather than real-world usage, and both participants treat it as a "don’t do that" footnote rather than a design flaw. The key takeaway is that the guard’s presence is a deliberate choice to prioritize correctness over flexibility, and the trade-off is accepted as part of the series’ final state. Future work to eliminate `NO_NSEC` entirely could revisit this decision, but that is outside the scope of the current effort.
