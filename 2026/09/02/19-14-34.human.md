This is Junio C Hamano’s latest follow-up in the `receive-report` hook thread, drilling into a fundamental consistency concern. The series, now queued in `seen` and ready for `next`, introduces a hook that lets server administrators filter or rewrite the status report sent to clients after ref updates are already committed. Junio’s worry is that the hook’s ability to report a failure when the server actually accepted the update creates a divergence between the client’s remote-tracking branches and the server’s true state.

The scenario he describes is straightforward: a user pushes, the hook reports `ng`, so the client leaves its remote-tracking branches unchanged. But the server *did* commit the update, so a subsequent fetch will show the new state. The user’s local view is now inconsistent with reality, and the server cannot fix it. Karthik Nayak’s earlier reply frames this as intentional and conservative — GitLab’s MVCC system wants the client to behave as if the push failed, even when it succeeded, to avoid racing with other operations. Junio’s message does not reject that rationale outright, but it underscores the inconsistency as a real cost that the commit message should acknowledge more prominently.

The exchange leaves the series’ status unchanged: it is still technically complete, well-tested, and ready for integration. But Junio’s concern is now on the record as a known trade-off, not a hidden side effect. Readers who care about client-server consistency will want to follow how this plays out in `next` and whether any users report confusion from the decoupled state.
