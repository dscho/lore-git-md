This is a feature patch series introducing the new `receive-report` hook for `git-receive-pack`. The v5 iteration is the latest revision of Karthik Nayak’s effort to allow server administrators to intercept and modify the status report sent to clients after ref updates are committed but before the response is finalized. The series is now technically complete and ready for integration into `next`, with all prior feedback addressed.

The series consists of three patches. The first adds missing documentation for the existing `proc-receive` hook in `git-receive-pack.adoc`, clarifying its role in the receive-pack lifecycle. The second refactors the status-report generation logic into a reusable `generate_report()` helper, centralizing the pkt-line formatting code and preparing for the hook’s implementation. The third patch introduces the `receive-report` hook itself, which runs after all ref updates are committed but before the report is sent. The hook receives the pkt-line encoded report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. A non-zero exit status now overwrites all `cmd->error_string` fields to `"receive-report hook failed"`, resolving the earlier precedence ambiguity and aligning with the behavior of the `pre-receive` hook.

Key improvements in v5 include renaming the helper function from `generate_response()` to `generate_report()` for clarity, documenting the hook’s ability to modify the `unpack` status line (e.g., changing `unpack ok` to `unpack push failed due to server error`), and adding a corresponding test case. The documentation has been updated to reflect these changes, including marking the `<reason>` field in `ng <refname>[ <reason>]` as optional and smoothing the phrasing in `git-receive-pack.adoc`. The implementation now uses a new `override_cmds_error()` helper to overwrite all `cmd->error_string` fields when the hook fails, avoiding the awkward output restructuring seen in earlier versions.

The series is well-motivated by GitLab’s need to implement MVCC on the server side, where the status report must reflect the repository state after all ref updates are committed. Test coverage is thorough, with 224 lines in `t/t5412-receive-report-hook.sh` exercising passthrough, failure modes, stdin/stdout handling, sideband relay, and the new unpack-status modification feature. The hook is deliberately not integrated with the config-based hook infrastructure to avoid parallelization complexity, a design choice that has been accepted by reviewers. Junio has already resolved a conflict with Justin Tobler’s concurrent "pluggable writes" series, and Karthik has confirmed the resolution is correct. The series is queued in `seen` and awaits graduation to `next`.
