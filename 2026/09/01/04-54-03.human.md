This is a **substantive review** from Jeff King (Peff) on the final patch in D. Ben Knoble’s `core.useNanosec` series, which has already graduated to `next`. Peff questions whether the build-time `#ifndef NO_NSEC` guard around the new `core.usenanosec` config handler is necessary. His concern is narrow but technical: if a user enables `core.usenanosec` on a platform where `NO_NSEC` is defined (i.e., where nanosecond timestamps are unsupported), the code already handles it gracefully by treating the timestamps as zero, which would always trigger a "racy" tie. The guard, he suggests, might be redundant.

Peff does identify a theoretical edge case: if a user builds two versions of Git (one with `NO_NSEC` and one without) on a system that *does* support nanosecond timestamps, an index generated by the non-`NO_NSEC` build could store real nanosecond values, which the `NO_NSEC` build would then misinterpret as zero, leading to false "racy" comparisons. He acknowledges this scenario is unlikely ("if it hurts, don’t do that") and concedes that removing the guard wouldn’t eliminate `NO_NSEC` as a build knob, so the simplification isn’t worth pursuing. His feedback is exploratory rather than prescriptive—he’s not asking for a change, just raising the question for discussion.

The patch itself remains technically sound and ready for `master`. Peff’s review doesn’t challenge the core design (runtime config, performance fixes, or cross-platform safety) and doesn’t block graduation. The series is still on track, but this exchange highlights a minor design choice that could resurface if users encounter the edge case Peff describes. For now, the guard stays, and the topic is effectively complete.
