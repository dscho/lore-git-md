This is the fourth patch in Elijah Newren's **v4 bugfix series** (5/5 total) that extends Git's existing protection against unsafe commit operations during conflict resolution. This patch specifically **blocks `git commit --amend` during conflict resolution for `git am`, `git revert`, and all forms of `git rebase`**, closing a long-standing gap where these operations were unprotected.

The patch introduces a new helper function, `sequencer_ongoing_operation()`, which consolidates logic for detecting active operations that record their results as new commits on top of HEAD (rather than rewriting HEAD). The function distinguishes between conflict stops (where amending would corrupt state) and clean interactive rebase stops (where amending is expected, e.g., for `squash` or `edit` directives). For the merge backend of rebase, it checks for the presence of `stopped-sha` (indicating a stop) and the absence of `amend` (indicating a conflict rather than a clean stop). The apply backend of rebase is simpler, as it only ever stops for conflicts.

The patch updates `builtin/commit.c` to use the new helper in a `switch` statement, replacing the prior hardcoded checks for merge and cherry-pick with a comprehensive set of cases covering all conflict-prone operations. Error messages are tailored to each operation (e.g., "You are resolving conflicts during a rebase -- cannot amend."). The test coverage is thorough, adding new tests in `t3404-rebase-interactive.sh` (for both merge and apply backends), `t3507-cherry-pick-conflict.sh` (for revert), and `t4151-am-abort.sh` (for `git am`).

This patch is **technically sound and uncontroversial**, with all substantive feedback addressed in earlier iterations. Junio C Hamano explicitly approved the structural improvements, including the deliberate omission of a `default:` case in the `switch` statement. The series is **ready for `next`** and aligns with the project's ongoing efforts to improve user safety during conflict resolution. No further changes are expected.
