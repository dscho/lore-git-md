This is the final patch in Karthik Nayak’s three-part series introducing the `receive-report` hook for `git-receive-pack`. The series is now technically complete and ready for integration into `next`.

The patch implements the core hook functionality: after all ref updates are committed but before the status report is sent to the client, `git-receive-pack` invokes the `receive-report` hook, passing the pkt-line encoded report on stdin. The hook’s stdout replaces the original report, and its stderr is forwarded to the client via the sideband channel. A zero exit code means the hook’s output is used as-is; a non-zero exit rewrites all ref status lines to `"receive-report hook failed"` and discards any existing per-ref errors, ensuring `receive-pack` can exit cleanly. This design aligns with the behavior of the `pre-receive` hook and resolves the earlier precedence issue raised by Patrick Steinhardt.

The implementation is self-contained and does not use the config-based hook infrastructure, avoiding the complexity of coordinating multiple scripts. The hook is documented in both `githooks.adoc` and `git-receive-pack.adoc`, with clear explanations of the three ways it can affect the push outcome: rewriting individual ref status lines, aborting the entire push (non-zero exit), or modifying the initial `unpack` status line. The documentation also marks the `<reason>` field in `ng` lines as optional (`ng <refname>[ <reason>]`), matching the protocol spec.

Test coverage in `t/t5412-receive-report-hook.sh` is thorough, exercising passthrough behavior, failure modes, stdin/stdout handling, sideband relay, and the interaction between exit status and stderr output. The tests confirm the hook can modify the `unpack` status line (e.g., `unpack ok` → `unpack push failed due to server error`) and relay custom failure messages to the client.
