This is a **usability discussion and bug report** about silent binary file corruption in Git, specifically on Windows. Randall S. Becker (the NonStop port maintainer) replies to Skybuck Flying’s report of PNG files being corrupted during checkout due to an overly broad global `.gitattributes` rule (`* text diff=lfclean`). The corruption occurs because Git applies a text filter (CR-stripping) to all files, including binaries, without safeguards.

Becker’s response is **practical advice, not a code fix**. He dismisses the AI-generated suggestions (CoPilot) as unhelpful and offers Windows-specific configuration tips: set `core.autocrlf=input`, `core.ignorecase=true`, and `core.filemode=false` to reduce misclassification of files. He confirms that Git’s binary detection is heuristic (based on early file content) and unreliable, so users must explicitly mark binaries (e.g., `*.png binary`) in `.gitattributes`. He also warns that textconv filters can mishandle binary data, especially if they assume text input (e.g., C’s `fgets()` choking on NUL bytes).

The email advances the thread by clarifying **why Git’s behavior is fragile**—its attribute system lacks safeguards for global rules, and its binary detection is not foolproof. Becker’s advice is actionable for users but sidesteps the broader question Skybuck raised: whether Git should warn about dangerous global `.gitattributes` rules or automatically protect known binary formats. No maintainer has yet weighed in on those proposals, leaving the issue unresolved. The tone is pragmatic but underscores the tension between Git’s flexibility and the risk of silent corruption.
