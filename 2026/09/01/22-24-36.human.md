This is the fourth iteration of a **bugfix series** by Elijah Newren that extends Git's existing protections against unsafe commit operations during conflict resolution. The series now covers `git commit --amend` and `git commit <paths>` for `git am`, `git revert`, and all forms of `git rebase`, preventing users from accidentally corrupting repository state by amending the wrong commit or committing only a subset of paths while resolving conflicts.

The only change since v3 is a **purely mechanical rename** to clarify intent: `FROM_REBASE_EMPTY` becomes `FROM_REBASE_NOW_EMPTY`, `is_from_rebase_empty()` becomes `is_from_rebase_now_empty()`, and `ONGOING_REBASE_EMPTY` becomes `ONGOING_REBASE_NOW_EMPTY`. These names now explicitly convey that the commit *became* empty during rebase, addressing Junio C Hamano's stylistic feedback from v3. The functionality remains identical.

The series is **technically complete and ready for integration**. All substantive feedback from earlier iterations has been resolved, including Junio's approval of the reworded error message ("The now-empty commit has been dropped -- cannot amend.") and Phillip Wood's maintainability concerns about hardcoded paths. The preparatory patches (1-2/5) cleanly separate mechanical changes (renaming and removing an unnecessary restriction on partial commits for empty commits) from the core logic (patches 4-5/5), which extends the protection to additional commands with thorough test coverage.

Key files touched include `builtin/commit.c`, `sequencer.c`, and `sequencer.h`, with new tests in `t3404-rebase-interactive.sh`, `t3507-cherry-pick-conflict.sh`, and `t4151-am-abort.sh`. The series introduces no new CLI options or on-disk format changes, and it aligns with the `the_repository` removal effort where possible. The error messages are now precise and context-aware, distinguishing between conflict stops and clean interactive rebase stops.

This is a well-crafted, uncontroversial fix that addresses a real usability hazard without disrupting legitimate workflows. It has received explicit approval from Junio and looks likely to proceed to `next` soon.
