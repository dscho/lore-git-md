This is the second patch in a two-part CI/build system series that enables Rust compilation in Git’s GitHub Actions Windows CI jobs. The series as a whole removes the `NO_RUST` opt-out for Windows CI, which was previously necessary because the minimal Git for Windows SDK lacks Rust tooling.

This patch adds a new step to the Windows CI workflow that installs the correct Rust target for the MSYS2 subsystem in use. GitHub’s Windows runners ship with Rust pre-installed, but it defaults to the MSVC ABI, which produces `.lib` files incompatible with MinGW’s `ld.exe`. The patch maps the `MSYSTEM` environment variable (exported by the Git for Windows SDK setup) to the corresponding GCC-compatible Rust target triple (`*-pc-windows-gnu` for MinGW, `*-pc-windows-gnullvm` for Clang/LLVM) and runs `rustup target add` to install the precompiled `std` for that target. The mapping is exhaustive, covering all MSYS2 subsystems the CI matrix exercises, even though only `MINGW64` is currently used—this future-proofs the workflow for the imminent switch to `UCRT64` and documents the expected setup for other subsystems.

The patch also ensures `cargo.exe` remains discoverable by adding its directory to `PATH`, working around the minimal SDK’s restricted environment. The `NO_RUST` opt-out in `ci/lib.sh` is removed, allowing the build to proceed with Rust enabled. The changes are narrowly scoped to the CI workflow and have no impact on core Git functionality or on-disk formats.

The patch looks well-crafted and practical, addressing a clear technical hurdle without introducing unnecessary complexity. The exhaustive target mapping and the explicit error handling for unsupported `MSYSTEM` values suggest careful attention to edge cases. The only open question is whether GitLab’s Windows runners (not addressed here) have Rust pre-installed, but that’s a separate concern and doesn’t affect this patch’s correctness for GitHub Actions. If this works as intended, it will unblock the broader Rustification effort in Git’s CI.
