This is the final patch in the v4 series optimizing `git last-modified` performance by reusing Bloom filters for wildcard pathspecs. It addresses a critical edge case: when `prepare_revision_walk()` clears `bloom_filter_settings` for pathspecs that cannot be converted into Bloom keys (like top-level wildcards such as `*.c`), the per-path Bloom filter lookups fail. The patch restores the settings after the walk, ensuring the optimization works for all pathspec types, and adds trace2 instrumentation (`bloom_queries`) to verify the fast-path is correctly triggered.

The change is minimal but essential: a 4-line restoration of `bloom_filter_settings` in `last_modified_run()` and a 3-line trace2 counter increment in `maybe_changed_path()`. The test in `t/t8020-last-modified.sh` exercises the wildcard case, confirming the Bloom filter is queried exactly twice (for `a.c` and `d/b.c`) when the commit-graph is enabled, and zero times when disabled. This instrumentation provides confidence the optimization is working as intended without altering command output.

The patch resolves the last technical blocker for the series: earlier iterations missed this edge case, causing performance regressions for wildcard pathspecs. The fix is pragmatic and aligns with Junio’s feedback to explicitly control the test environment. The trace2 counter is a lightweight addition that doesn’t affect runtime behavior but enables future debugging. No new public APIs are introduced; the patch only touches `builtin/last-modified.c` and the test suite.

This is a well-motivated performance fix for an experimental command. The instrumentation is unobtrusive, the test coverage is thorough, and the change is confined to the `last-modified` builtin. The series is now complete and ready for integration.
