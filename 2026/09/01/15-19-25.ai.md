This is the final patch in a three-patch feature series introducing the `receive-report` hook for `git-receive-pack`. The series is technically complete, well-motivated, and ready for integration into `next`.

This patch implements the core hook functionality. The `receive-report` hook runs after all ref updates are committed but before the status report is sent to the client, allowing server administrators to intercept and modify the report. The hook receives the pkt-line encoded status report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. A zero exit code means the hook’s stdout is used as the report, while a non-zero exit rewrites all ref status lines to `"receive-report hook failed"` and overwrites all `cmd->error_string` fields, discarding existing per-ref errors. This aligns with the behavior of the `pre-receive` hook and resolves the precedence issue raised in earlier iterations.

The implementation is self-contained and does not use the config-based hook infrastructure, avoiding parallelization complexity. The patch touches `builtin/receive-pack.c` to add the hook invocation logic, including the `run_receive_report_hook()` and `override_cmds_error()` helpers, and updates both `report()` and `report_v2()` to call the hook. Documentation is added to `git-receive-pack.adoc` and `githooks.adoc`, explicitly listing the three ways the hook can affect the push outcome: rewriting individual ref status lines, aborting the entire push (by exiting non-zero), and modifying the initial `unpack` status line (e.g., `unpack ok` → `unpack push failed due to server error`).

Test coverage is thorough, with 224 lines added to `t/t5412-receive-report-hook.sh` covering passthrough behavior, failure modes, stdin/stdout handling, sideband relay, and interaction between exit status and stderr output. The tests exercise both success and failure cases, including custom failure messages and the hook’s ability to modify the `unpack` status line.

All prior feedback has been addressed, including the hook naming objection (`report` → `receive-report`), exit status semantics, documentation ambiguities, and the technical design question about overwriting `cmd->error_string` fields. The series is queued in `seen` and awaits graduation to `next`. The implementation is clean, well-documented, and motivated by a concrete use case (GitLab’s MVCC system), making it a strong candidate for merging.
