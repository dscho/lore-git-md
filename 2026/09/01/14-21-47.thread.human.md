This thread is about enabling Rust compilation in Git’s GitHub Actions Windows CI jobs, a necessary step to support the broader Rustification effort in Git. Johannes Schindelin (via GitGitGadget) posted a two-part patch series (v1) to address a blocker introduced in Git 2.55.0, where Rust became a default requirement but Windows CI jobs were still opting out due to compatibility issues with the MSVC ABI.

The series configures the Rust toolchain to target the GCC ABI (used by Git for Windows) instead of the default MSVC ABI, ensuring Cargo produces a static library (`libgit.a`) compatible with MinGW’s `ld.exe`. The first patch laid the groundwork by setting up the toolchain configuration, while this second patch removes the existing opt-out (`NO_RUST=UnfortunatelyYes`) and installs the precompiled Rust `std` library for the GCC-compatible target triple. The changes are narrowly scoped to the CI workflow file (`.github/workflows/main.yml`) and the CI library script (`ci/lib.sh`), with no impact on core Git functionality or user-facing features.

The patch is well-documented and practical, with clear explanations for the target triple mapping and `PATH` adjustments. It directly addresses the CI failure caused by the MSVC-targeted `.lib` file being incompatible with MinGW. While the author couldn’t test on GitLab’s Windows runners, the patch is unlikely to be controversial if those runners behave similarly to GitHub’s. If merged, this will unblock the eventual removal of the Rust opt-out in Git’s CI, a prerequisite for the ongoing Rustification effort. No objections or requests for changes have been raised yet.
