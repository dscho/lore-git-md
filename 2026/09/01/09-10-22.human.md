This is the second patch in the v4 series that speeds up the experimental `git last-modified` command by reusing Git’s Bloom filters. The patch refactors the existing `check_maybe_different_in_bloom_filter()` function in `revision.c` to expose its core logic as a new public helper, `revs_maybe_changed_in_bloom()`, declared in `revision.h`.

The change is straightforward: the new function takes an already-looked-up `struct bloom_filter` and returns a boolean (`true` if the commit *might* have changed any of the paths in the pathspec, `false` if it definitely did not). The original function remains as a thin wrapper that looks up the Bloom filter and delegates to the new helper. This avoids redundant lookups for callers like `git last-modified` that already have the filter in hand.

The patch is cleanly motivated: it reduces code duplication and enables the performance optimization in later patches without altering behavior. The commit message explains the return-value semantics clearly, and the code itself is a textbook refactoring—no functional change, just a better interface. The new helper is well-named and documented, and the diff is minimal and focused.

This is a solid, uncontroversial step in the series. It doesn’t introduce new complexity or edge cases, and it directly supports the performance goal. The only thing worth noting is that the new function’s return value is inverted relative to the original’s tristate (`0`/`1`/`-1`), but the commit message calls this out explicitly, so there’s no risk of confusion.
