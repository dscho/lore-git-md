This is a **follow-up discussion** in the `dk/use-nsec-runtime` series, which graduated to `next` on 2024-07-10. The exchange between D. Ben Knoble and Jeff King (Peff) revisits the necessity of the `#ifndef NO_NSEC` guard around the `core.usenanosec` config handler in `environment.c`. Peff initially questions whether the guard is needed, noting that platforms lacking nanosecond support would likely not enable the config, and the code would still work by faking nanosecond values as zero. However, he identifies a subtle edge case: if a user builds two Git versions (one with `NO_NSEC` and one without) on a system that *does* support nanosecond timestamps, an index generated by the non-`NO_NSEC` build could store real nanosecond values, which the `NO_NSEC` build would misinterpret as zero, leading to false "racy" comparisons. Peff acknowledges this scenario is unlikely and does not propose removing the guard, but the discussion surfaces a correctness risk that may warrant documentation.

Knoble clarifies Peff’s point about faking index entries (not the config value) and agrees the guard prevents reading nanosecond values on unsupported platforms, avoiding false negatives. He also notes the guard’s practical impact: users on `NO_NSEC` builds (e.g., from a distro) cannot enable `core.usenanosec` without recompiling, even if their platform supports it. While Peff confirms the guard is reasonable given the complexity of eliminating `NO_NSEC` entirely, the exchange highlights a trade-off between build-time restrictions and runtime flexibility. No code changes are proposed, but the thread adds nuance to the platform-compatibility discussion, suggesting a potential note in `Documentation/technical/racy-git.adoc` about mixed-build risks.
