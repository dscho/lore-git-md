This is the fourth iteration (v4) of a performance optimization series for the experimental `git last-modified` command. The goal is to reuse Git’s Bloom filter machinery to speed up queries about the last commit that modified files matching a pathspec, including wildcards. The series is now complete and addresses all previously identified issues, including a test environment interaction that blocked v3.

The v4 reroll applies Junio C Hamano’s suggested fix for the test environment issue in `t8020-last-modified.sh`: explicitly overriding `GIT_TEST_COMMIT_GRAPH` when testing the commit-graph-disabled baseline (`GIT_TEST_COMMIT_GRAPH=0`) and the commit-graph-enabled case (`GIT_TEST_COMMIT_GRAPH=1`). This ensures the test behaves as intended regardless of the broader test environment. The fix is minimal and pragmatic, targeting only the two `git` invocations in the test.

The series touches `revision.c`, `revision.h`, `bloom.c`, `bloom.h`, `builtin/last-modified.c`, and the test suite. It introduces two new public helpers in `revision.h`: `revs_maybe_changed_in_bloom()` (for direct pathspec matches) and `revs_maybe_changed_in_bloom_with_parents()` (for `--show-trees`, which checks parent directories). The private helper `bloom_filter_contains_any_vec()` in `bloom.c` underpins the latter. Patch 5/6 adds a pre-filter in `maybe_changed_path()` to discard commits that definitely did not touch any relevant path, while patch 6/6 restores `bloom_filter_settings` after `prepare_revision_walk()` clears it, ensuring Bloom filter lookups succeed for wildcard pathspecs (e.g., `*.c`).

Benchmarks on the ziglang/zig repository show a 3.7× speedup without `--show-trees` (60.7 ms → 16.2 ms) and a 1.95× speedup with `--show-trees` (61.9 ms → 31.8 ms), bringing `git last-modified` nearly to parity with `git log`. The series includes trace2 instrumentation (`bloom_queries`) to verify the Bloom filter fast-path is correctly triggered, and the test suite now exercises the code path for wildcard pathspecs. All technical feedback from earlier iterations is resolved, and the public API is cleanly exposed.

The only remaining discussion point from earlier iterations—the maintainability of restoring `bloom_filter_settings` after `prepare_revision_walk()`—was acknowledged as non-blocking. Jeff King proposed an alternative design but accepted the current approach as sufficient. The series is now ready for integration; the instrumentation is lightweight, the performance gains are well-documented, and the test coverage is thorough. The changes are confined to the experimental `last-modified` command and do not affect the on-disk format or other Git commands.
