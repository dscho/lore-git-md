This is the final review comment in the `receive-report` hook series, now queued in `seen` and ready for `next`. Junio C Hamano raises a conceptual concern about the hook’s design: it allows the server to report a ref update status that differs from what actually happened on disk, creating a potential inconsistency between the client’s remote-tracking branches and the server’s true state.

The hook’s stated purpose is to let GitLab implement MVCC by filtering the status report after all ref updates are committed but before the client receives confirmation. Junio points out that if the hook rewrites an `ok` line to `ng`, the client will mark that ref as `[remote rejected]` and update its remote-tracking branch accordingly — yet the server-side ref was actually updated. This divergence could cause future pushes to behave unexpectedly, since the client’s view of the remote no longer matches reality. He questions whether the reference-transaction hook (which already fires at the commit phase) could be extended to allow optional rejection, making the new hook redundant.

The observation is non-blocking — Junio explicitly says he is not proposing an alternative — but it surfaces a subtle edge case that administrators should be aware of: the hook’s ability to decouple reported status from actual ref state may require additional reconciliation logic on the server side. The series itself remains technically sound and well-motivated; this is a design-level caveat rather than a bug.
