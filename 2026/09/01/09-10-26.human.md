This is the final patch in a six-part performance optimization series for the experimental `git last-modified` command. The series aims to speed up queries about the last commit that modified files matching a pathspec (including wildcards like `*.c`) by reusing Git’s Bloom filter machinery.

This patch ensures that `git last-modified` continues to work efficiently with wildcard pathspecs. The `prepare_revision_walk()` function clears `bloom_filter_settings` when it encounters a pathspec that cannot be turned into a Bloom key (such as a top-level wildcard like `*.c`). The patch restores the settings afterward so that per-path Bloom filter lookups remain functional. While this change does not affect the command’s output, it preserves the performance gains achieved earlier in the series.

The patch also adds a `bloom_queries` trace2 counter to instrument how often the per-path Bloom filter check runs. A new test verifies that the counter increments correctly for wildcard pathspecs, confirming the Bloom filter fast-path is active. The test explicitly controls `GIT_TEST_COMMIT_GRAPH` to ensure consistent behavior regardless of the broader test environment, addressing the issue that blocked the previous iteration.

The implementation is straightforward: a 14-line addition to `builtin/last-modified.c` restores `bloom_filter_settings` and increments the trace2 counter, while the test in `t/t8020-last-modified.sh` exercises the code path for wildcard pathspecs. The patch is well-motivated, with clear performance benefits and thorough test coverage. All technical feedback from earlier iterations has been resolved, and the series is now ready for integration. The changes are confined to the experimental `last-modified` command and do not affect other parts of Git.
