This is the second patch in Patrick Steinhardt’s two-patch series improving the `git maintenance` heuristic for the `rerere gc` task. It updates `builtin/gc.c` and the maintenance configuration documentation to implement the dynamic heuristic introduced in the first patch, replacing the previous hard-coded behavior that triggered the task whenever any `rerere` entry existed.

The patch refines the `rerere_gc_condition()` function to use the new `rerere_gc_needed()` helper (introduced in patch 1) to determine whether the task should run. The `maintenance.rerere-gc.auto` configuration is redefined: negative values force the task to run unconditionally, zero disables it, and positive values specify the minimum estimated stale entries required to trigger the task (default: 512). The documentation is updated to reflect this change, and the test suite (`t/t7900-maintenance.sh`) is expanded to cover the new behavior, including edge cases like threshold crossing and disabled/forced runs.

The implementation is clean and well-tested, with no open questions or loose ends. The patch has received a **tested review** from Thomas Bachem and a **substantive review** from Derrick Stolee, both of whom confirmed the series works as intended and is ready for integration. The heuristic’s sampling strategy (using a "17" prefix and scaling by 256) is consistent with Git’s loose-object estimation and effectively reduces overhead while maintaining accuracy. The patch directly addresses the race condition reported in GitGitGadget PR 2214 by reducing unnecessary `rerere gc` invocations.
