This is the v3 locking patch in Thomas Bachem’s two-part series fixing the `rerere` race condition between rebase and background maintenance. It supersedes v2 and incorporates all review feedback from Junio, Phillip Wood, and Patrick Steinhardt.

The patch keeps the core idea—waiting for `MERGE_RR.lock` instead of dying—but tightens the implementation. It adds a new `rerere.lockTimeout` config (default 1000 ms) that controls how long non-maintenance callers (merge, commit, rebase) wait before warning and proceeding without `rerere`. Background maintenance (`git rerere gc`) still skips the lock entirely (`RERERE_NOWAIT`), while the explicit `git rerere`, `git rerere forget`, and `git rerere clear` commands retry for the full timeout but then fail rather than proceeding. The commit message is now concise, the locking flags are sanity-checked with `BUG()` assertions, and the documentation clarifies the behavior of each command. Tests cover the gc under a held lock, a merge that waits out the timeout, and the fallback behavior when the timeout expires.

The patch is based on `maint` and resolves a trivial conflict with the recent lockfile-helper refactoring (`2e486bfbf7`). It is ready for final review and looks like a clean, well-tested fix for a real-world regression introduced in Git 2.54.
