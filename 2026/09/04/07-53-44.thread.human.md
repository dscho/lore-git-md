This thread is about a small but practical improvement to Git’s auto maintenance behavior during `git rebase`. Thomas Bachem proposed a patch series (v1) that defers auto maintenance until rebase completion, matching the apply backend’s existing behavior and preventing maintenance from running during intermediate steps. The change touches the sequencer code and adds test coverage to verify that `git maintenance run --auto` is called exactly once at the end of a rebase, not during each commit or merge.

Phillip Wood reviewed the series and broadly supports the approach, calling the current patch “reasonable.” His main feedback is about scope: he suggests the same deferral logic should eventually apply to `git cherry-pick` and `git revert`, since both can create loose objects and trigger maintenance mid-operation, potentially causing the same interference issues the rebase patch now avoids. He also noted some minor commit message phrasing and code structure improvements, but nothing that blocks the series. The only open question is whether to expand the series to cover cherry-pick and revert now or in a follow-up.

The series is under active review and looks ready to move forward once the scope question is resolved. No other reviewers have weighed in yet, but the feedback so far is constructive and focused on polish rather than fundamental objections.
