This thread is about a small but practical improvement to Git’s rebase workflow: deferring auto maintenance until the end of a rebase, so that it doesn’t interfere with intermediate steps. Thomas Bachem posted the initial two-patch series (v1) to align the merge backend’s behavior with the apply backend, which already defers maintenance. The change touches the sequencer code and adds test coverage to verify that `git maintenance run --auto` runs exactly once at rebase completion, not during individual commits or merges.

Phillip Wood has reviewed the series and provided substantive feedback. While he agrees with the overall direction—deferring maintenance is the right call—he suggests several refinements. The commit message could be clearer, especially the motivation section, which is currently hard to parse. He also raises a potential edge case: very large rebases might benefit from mid-rebase repacking, though he acknowledges this is hypothetical and not a blocker. On the code side, he proposes factoring out a helper to avoid duplicating config logic and caching the constructed config string to avoid repeated work. The test coverage is praised, and Phillip hints that the same reasoning might eventually apply to `git cherry-pick` and `git revert`, though that’s not part of this series.

The series is still under review, with no objections raised so far. The next step is likely a v2 incorporating Phillip’s suggestions, particularly the code structure improvements and commit message cleanup. No other participants have weighed in yet, but the discussion so far suggests this is a straightforward, uncontroversial change.
