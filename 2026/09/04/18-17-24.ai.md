This is a **bugfix patch** targeting the `rerere` subsystem, addressing a race condition between foreground operations (like rebase) and background maintenance (`git rerere gc`). The email is Thomas Bachem’s reply to Junio C Hamano’s review of the v2 locking patch, detailing adjustments for v3.

Thomas clarifies two key corrections for v3. First, he fixes an oversight in `rerere_clear()` (used by `git rebase --abort` and `--skip`), which previously waited for a lock before proceeding but left the `MERGE_RR` file intact. This could cause subsequent `rerere` operations to misinterpret conflict resolutions. The fix makes `rerere_clear()` fail immediately if the lock is held, matching the behavior of `git rerere clear` and avoiding silent corruption. This change removes the need for caller updates in `am.c` and `rebase.c`, simplifying the patch.

Second, Thomas refines the error-handling logic to align with Junio’s feedback: `git rerere gc` is the only command that silently skips when the lock is held (as it’s a best-effort cleanup), while `git rerere`, `git rerere forget`, and `git rerere clear` fail after waiting for the timeout. Foreground operations like `git commit` or `git merge` warn and proceed without `rerere` support if the lock remains held. The commit message will now explicitly state that `gc` "gives up at once" rather than implying it doesn’t retry, addressing Junio’s concern about misleading documentation.

On the user-experience issue of background-task warnings mixing with foreground output, Thomas confirms this cannot occur: background maintenance runs are daemonized (closing standard descriptors) or, on Windows, run synchronously with the triggering command. The only warning users see comes from the foreground operation after it times out waiting for the lock. This resolves Junio’s and Phillip Wood’s concerns without requiring additional patch changes.

The v3 patch is now focused on locking behavior and error handling, with the sequencer config-override patch (disabling maintenance during rebase) still pending. The locking changes are settled, and Thomas plans to reroll after addressing any remaining v3 feedback. Key files touched remain `rerere.c`, `rerere.h`, and documentation, with tests covering the new error paths. The patch is based on `maint` and resolves a trivial conflict with the lockfile helper refactoring (`2e486bfbf7`).
