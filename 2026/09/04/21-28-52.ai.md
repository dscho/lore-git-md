This is the **core implementation patch** of Karthik Nayak’s four-part series introducing the `receive-report` hook for `git-receive-pack`. It is the final patch (4/4) in the v7 iteration, which is **feature-complete, queued in `seen`, and ready for `next`**. The patch adds the hook itself, its invocation logic, and 224 lines of test coverage in `t/t5412-receive-report-hook.sh`.

The hook addresses a server-side extensibility gap: it allows administrators to intercept and modify the pkt-line encoded status report sent to clients after ref updates are committed but before the response is finalized. This is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the final status must reflect operations that occur *after* `ref_transaction_commit()`. The design intentionally decouples the reported status from the actual repository state—a trade-off explicitly acknowledged in the commit message. A hook can report a push as failed (`ng`) while still committing ref updates, leaving the client’s remote-tracking branches inconsistent with the server. This divergence is justified by GitLab’s use case, where conservative client-side behavior (not updating remote-tracking branches when the hook reports `ng`) is the desired outcome.

The implementation touches `builtin/receive-pack.c`, adding three new helpers: `run_receive_report_hook()`, which invokes the hook and buffers its stdout; `override_cmds_error()`, which rewrites all ref status lines to a generic error on non-zero exit; and the hook’s invocation point in the `report()` function, which runs after `generate_report()` but before the sideband transmission. The hook receives the complete status report on stdin and replaces it with its stdout; stderr is forwarded to the client via sideband. A non-zero exit code discards the hook’s stdout and rewrites all ref status lines to `"receive-report hook failed"`, effectively treating the push as failed (though ref changes are not rolled back).

Test coverage exercises edge cases: passthrough behavior, non-zero exits, stdin/stdout handling, sideband relay, and the hook’s ability to modify both ref status lines and the `unpack` status line. The documentation in `githooks.adoc` and `git-receive-pack.adoc` explains the hook’s three ways of affecting push outcome: rewriting individual ref status lines, aborting the entire push (non-zero exit), and modifying the `unpack` status line. The hook is not integrated with the config-based hook infrastructure, as it acts as a bidirectional filter rather than a parallelizable notification hook.

Junio’s earlier consistency concern—about the hook’s ability to report a state divergent from the actual repository—remains a documented design choice rather than a blocker. The commit message explicitly states that the hook owner is responsible for undoing ref changes if needed and that the hook is only appropriate for servers where rejected updates are not immediately visible to other readers. All prior feedback, including Patrick Steinhardt’s substantive review of the unified `report()` helper and surface-level nits (e.g., curly braces in `override_cmds_error()`), has been addressed in this iteration.
