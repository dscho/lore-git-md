Subject: [PATCH 0/2] sequencer: defer auto maintenance until rebase completion
Series version: v1 (initial)
Originating author: Thomas Bachem (via GitGitGadget)
Thread type: patch series

Core problem or goal
Adjust when auto maintenance runs during a `git rebase` (merge backend) so that it defers until rebase completion, matching the apply backend’s behavior. This isolates the maintenance deferral improvement from the unrelated rerere lock race investigation and prevents maintenance from interfering with intermediate rebase steps.

Current status
Under review; v1 posted. No prior versions.

Key technical details
- Files touched: `sequencer.c`, test file `t/t3418-rebase-continue.sh`
- New behavior: auto maintenance runs once at rebase completion (after autostash is applied) instead of during intermediate commits/merges
- CLI/config impact: disables auto maintenance for individual commands (`git commit`, `git merge`, exec commands) during rebase by passing `maintenance.auto=false` and `gc.auto=0` via `GIT_CONFIG_PARAMETERS`; invokes `git maintenance run --auto` at rebase completion
- Subsystems: sequencer, auto maintenance
- Test coverage: added to `t/t3418-rebase-continue.sh` using `GIT_TRACE2_EVENT` to verify `git maintenance run --auto` is executed exactly once at rebase end and not during intermediate steps
- Unaffected: cherry-pick, revert, and the apply backend’s existing behavior
- Error handling: maintenance errors are ignored to avoid masking user-facing issues
- Code structure: new `disable_auto_maintenance()` helper duplicates logic from `config.c`; Phillip Wood suggests factoring out a reusable helper to append config parameters to an `strbuf` and caching the constructed config string in `replay_ctx` to avoid repeated string construction

Open questions and loose ends
- **Commit message clarity**: Phillip Wood flags a dense paragraph in the second patch’s commit message as hard to parse and suggests breaking it up and tightening phrasing (e.g., “Nothing” → “The objects”).
- **Edge cases**: Hypothetical concern about very large rebases where mid-rebase repacking might improve performance; no concrete issue identified, but Phillip wants to monitor real-world usage for complaints.
