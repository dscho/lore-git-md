This is the v2 locking patch in Thomas Bachem’s two-part bugfix series targeting the `rerere` subsystem, addressing a race condition introduced in Git 2.54 where background maintenance (`git rerere gc`) can deadlock or crash an in-progress rebase when both try to acquire the `MERGE_RR.lock` simultaneously.

The patch refines the locking logic in `rerere_setup()` to avoid dying when the lock is held. Instead, callers now wait up to `rerere.lockTimeout` milliseconds (default: 1000) before warning and proceeding without rerere. The background `rerere gc` task itself never waits (timeout=0) and skips its run if the lock is held, while explicit commands like `git rerere`, `git rerere forget`, and `git rerere clear` continue to fail immediately. The `RERERE_SKIP_LOCKED` flag is renamed to `RERERE_NOWAIT` to better reflect its purpose, and a new `RERERE_LOCK_OR_DIE` flag is introduced to preserve the old behavior for commands that require the lock. Error messages are now hand-rolled to avoid misleading advice about terminating other Git processes.

Key technical details:
- Files modified: `rerere.c`, `rerere.h`, `builtin/rerere.c`, `builtin/am.c`, `builtin/rebase.c`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`
- New config: `rerere.lockTimeout` (milliseconds, default 1000)
- New flags: `RERERE_NOWAIT` (skip lock wait), `RERERE_LOCK_OR_DIE` (fail immediately if lock is held)
- Lock acquisition now uses `hold_lock_file_for_update_timeout()` with configurable timeout
- Test coverage includes scenarios for a held lock during `git rerere gc`, merges, commits, rebases, and explicit commands, with both positive and negative cases for the timeout behavior

The patch is based on `maint` and conflicts with `d43f701d32` (lockfile helper refactoring), but the resolution is straightforward. It is well-motivated, with a clear reproduction scenario and thorough test coverage, and aligns with feedback from Phillip Wood and Patrick Steinhardt. The changes are targeted and preserve backward compatibility while addressing the immediate issue. The deeper root cause—the geometric maintenance strategy’s aggressiveness—will be addressed separately by Patrick Steinhardt.
