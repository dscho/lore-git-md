This is the latest reply in the ongoing feature series adding seven new path-related keys to `git repo info`. The author, K Jayatheerth (a GSoC contributor), responds to Junio C Hamano’s **substantive architectural concern** about code duplication between `git repo info` and `git rev-parse`. Junio had proposed consolidating shared logic (e.g., for `path.cdup`, `path.toplevel`, and `path.superproject-root`) into a new helper library (`repo-info.c`) to avoid long-term maintainability issues.

Jayatheerth acknowledges the feedback and outlines a pragmatic two-phase approach: **merge the current series as-is**, then address the deduplication in a **follow-up refactoring series**. His rationale is that mixing feature additions with legacy refactoring in a single series would complicate review and bisectability. The follow-up would introduce the new library incrementally, porting one command at a time to ensure each change remains self-contained. This plan keeps the current series focused on its original goal while deferring the architectural cleanup to a separate effort.

The proposal is reasonable and aligns with Git’s incremental development practices. Junio’s concern is valid—duplicating logic risks divergence over time—but the current series is already mechanically clean, feature-complete, and addresses all prior feedback. Splitting the work avoids blocking the new functionality on a refactor that could touch multiple built-ins. The follow-up series would also provide a clearer narrative for reviewers, separating the "what" (new keys) from the "how" (code organization). No objections have been raised yet, but the thread’s next step hinges on Junio’s approval of this plan. If accepted, the current series could proceed toward `next`, with the refactoring queued for later.
