This is the second patch in Patrick Steinhardt’s two-part series improving the `git maintenance` heuristic for the `rerere gc` task. It refines the logic in `builtin/gc.c` to use a dynamic heuristic that estimates stale `rerere` entries, triggering the task only when the estimate meets or exceeds a configurable threshold (default: 512). The goal is to reduce unnecessary invocations, lower overhead, and mitigate a long-standing race condition caused by frequent `rerere gc` runs.

The patch replaces the previous hard-coded 60-day cutoff with a sampling-based heuristic that checks the `rr-cache` directory for stale entries (those older than 60 days for resolved conflicts or 15 days for unresolved ones). It uses the same "17" prefix sampling strategy as Git’s loose-object estimation, scaling each sampled stale entry by 256 to estimate the total count. The `maintenance.rerere-gc.auto` configuration is redefined: negative values force the task to run, zero disables it, and positive values set the minimum estimated stale entries required to trigger the task.

The implementation is clean and well-motivated, with thorough test coverage in `t/t7900-maintenance.sh` that verifies edge cases (threshold crossing, disabled/forced runs, and sampling behavior). The patch has received **substantive reviews** from Derrick Stolee and a **tested review** from Thomas Bachem, who confirmed the heuristic works as intended and verified the tests pass. The series is now considered ready for integration, with no open questions or loose ends.

This is a targeted bugfix and performance improvement that addresses a real issue (the race condition reported in GitGitGadget PR 2214) without changing the on-disk format or introducing backward-incompatible behavior. The default threshold (512) is a reasonable starting point, and the sampling heuristic ensures the overhead remains low even with many `rerere` entries. If you care about `git maintenance` or `rerere` performance, this patch is worth reviewing.
