This is the v7 iteration of Karthik Nayak’s four-patch series introducing the `receive-report` hook for `git-receive-pack`. The series is now **feature-complete and ready for `next`**, addressing all prior feedback from Junio C Hamano, Patrick Steinhardt, and others. It targets Git’s server-side extensibility gap, allowing administrators to intercept and modify the status report sent to clients after ref updates are committed but before the response is finalized.

The hook is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the final status reported to the client must reflect server-side operations that occur *after* `ref_transaction_commit()`. The design intentionally decouples the reported status from the actual repository state, a trade-off explicitly acknowledged in the commit message: a hook can report a push as failed (`ng`) while still committing ref updates, leaving the client’s remote-tracking branches inconsistent with the server. This divergence is justified by GitLab’s use case, where conservative client-side behavior (not updating remote-tracking branches when the hook reports `ng`) is the desired outcome.

Key changes in v7:
- **Unified report generation**: The `report()` and `report_v2()` functions are now merged into a single `report()` helper that takes an `enum report_status_version` parameter, eliminating redundancy. This addresses Patrick Steinhardt’s substantive review feedback from v6.
- **Code style improvements**: A `switch` statement replaces the `if/else` chain for handling the `report_status_version` enum, and an unnecessary curly brace in `override_cmds_error()` is removed—both surface-level nits Patrick raised.
- **Rebase**: The series is rebased onto `master` (3cb9185f65, "The 22nd batch, 2026-09-02"), resolving conflicts with Justin Tobler’s concurrent "pluggable writes" series.

The implementation touches `builtin/receive-pack.c`, adds 224 lines of test coverage in `t/t5412-receive-report-hook.sh`, and updates documentation in `githooks.adoc` and `git-receive-pack.adoc`. The hook is invoked after all ref updates are committed, receives the pkt-line encoded status report on stdin, and replaces it with its stdout; stderr is forwarded to the client via sideband. A non-zero exit code rewrites all ref status lines to `"receive-report hook failed"` and overwrites all `cmd->error_string` fields, effectively treating the push as failed (though ref changes are not rolled back).

The series is **queued in `seen`** and has no outstanding technical objections. Junio’s earlier consistency concern—about the hook’s ability to report a state divergent from the actual repository—remains a documented design choice rather than a blocker. The hook is not integrated with the config-based hook infrastructure, as it acts as a bidirectional filter rather than a parallelizable notification hook. Test coverage exercises edge cases like sideband relay, non-zero exits, and the hook’s ability to modify the `unpack` status line.
