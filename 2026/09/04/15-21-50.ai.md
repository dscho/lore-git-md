This is a **tooling follow-up** in the now-closed `git checkout -m` autostash conflict handling series. The series itself is already approved and queued for `next`; this exchange clarifies a minor discrepancy in Git’s style enforcement tooling.

Junio examines Git’s `.clang-format` configuration and confirms that the `RemoveBracesLLVM: true` setting only removes *excess* braces from single-statement `if/else` bodies but does not enforce *consistent* brace usage across an entire `if/else if/else` cascade. Specifically, if one branch in the cascade requires braces (e.g., because it contains multiple statements), `.clang-format` will not automatically add braces to the other branches, even though Git’s coding guidelines prefer consistency. This explains why the GitHub CI workflow (`.github/workflows/check-style.yml`) does not flag the missing braces in `stash.c` that Junio and Phillip Wood noted earlier: the tool simply lacks the capability to enforce this rule. The local `make style` target behaves identically, as it runs the same `git clang-format` command.

The discussion remains purely mechanical and does not affect the integration status of the autostash series. It surfaces a limitation in Git’s current style enforcement tooling: `.clang-format` cannot fully automate compliance with Git’s brace consistency guidelines, leaving some style decisions to manual review. Junio’s example diff illustrates the tool’s behavior, showing how it removes braces from a simple `if/else` block but does not address the broader cascade issue.
