This is Junio C Hamano following up on Patrick Steinhardt’s two-patch series that improves the `git maintenance` heuristic for the `rerere gc` task. The series is already endorsed as ready for integration, but Junio raises a **clarifying question** about the scope of the fix.

The question cuts to the heart of what the series actually solves. The original problem—a race condition between `git maintenance` and `git rebase` caused by lock contention on `MERGE_RR.lock`—is real, but Junio points out that the series does **not** address concurrent `rerere gc` invocations. Even with the new dynamic heuristic, if two `rerere gc` tasks run simultaneously, the second will still fail due to `LOCK_DIE_ON_ERROR`. The series reduces the frequency of `rerere gc` runs (lowering the chance of collision), but it does not eliminate the underlying race. Junio’s tone is neutral, but the implication is clear: the cover letter and commit messages should make this limitation explicit to avoid overpromising.

This is not a request for changes—Junio has already praised the v2 code as "much easier to read"—but it is a **call for clarity** in the project’s collective understanding. If the series lands as-is, future readers (or contributors) might assume the race is fully resolved, when in fact it remains an open issue for a separate patch. The question is a small but important nudge to ensure the documentation (and possibly the RelNotes) accurately reflect what the code does—and what it does not.
