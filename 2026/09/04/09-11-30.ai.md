This is a **substantive review** of the `git var` extension patch (v3), part of the ongoing effort to unify identity and signing configuration under a scriptable interface. Phillip Wood engages deeply with the implementation, identifying several correctness and usability issues that affect both interactive and scripted use. The review is constructive and technical, focusing on edge cases, output format ambiguity, and argument parsing logic.

The most critical issue is **output format ambiguity**: when `-z` is used, the current patch prints `key=value\0`, but keys (especially signing keys) can contain `=` characters, making the output impossible to parse reliably. Phillip suggests adopting the same format as `git config -z` (`key\neolvalue\0`), which avoids this ambiguity. He also flags that multi-valued variables (like paths) may contain newlines, so `-z` should separate values with `\0` rather than `\n` to ensure unambiguous parsing.

On **argument parsing**, Phillip argues that the plumbing command should not support interleaved flags and variable names (e.g., `git var GIT_AUTHOR_NAME -z GIT_AUTHOR_EMAIL`). Instead, flags like `-z` should be processed first, with all remaining arguments treated as variable names. This simplifies the implementation and aligns with the principle that plumbing commands should be predictable and script-friendly.

The **`GIT_SIGNING_KEY` alias** for `GIT_DEFAULT_KEY` is questioned: Phillip notes that `GIT_DEFAULT_KEY` is opaque, while `GIT_SIGNING_KEY` clearly communicates its purpose. He also raises a practical concern: scripts using Git for signing don’t need to query the key (Git handles it automatically), and scripts signing external data would need to know the signing scheme (GPG/SSH/X.509), which isn’t exposed by the variable. This suggests the alias may not pull its weight.

Test coverage is praised ("being able to specify multiple variables that are printed unambiguously is a really useful improvement"), but Phillip doesn’t comment on the existing tests’ adequacy beyond the output format issues. The review implies that the test suite should verify `-z` output matches `git config -z` behavior for edge cases (e.g., no-value variables, multi-valued variables).

The review is **not a blocker**—it’s a refinement request—but the output format and argument parsing issues are serious enough that they’ll likely need to be addressed before merging. The next revision (v4) will probably focus on these points, along with Junio’s earlier feedback on documentation and code structure. The patch remains in `seen` and is still under active review.
