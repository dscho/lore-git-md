This is the v2 cover letter for Patrick Steinhardt’s two-patch series improving the `git maintenance` heuristic for the `rerere gc` task. The series replaces the hard-coded 60-day cutoff with a dynamic heuristic that estimates stale `rerere` entries and triggers the task only when the estimate meets or exceeds a configurable threshold (default: 512). The goal is to reduce unnecessary invocations, lower overhead, and fix a long-standing race condition reported in GitGitGadget PR 2214.

The v2 iteration addresses all prior feedback: the ternary logic in `rerere_gc_condition()` has been rewritten for clarity, `rerere_gc_estimate()` has been renamed to `rerere_gc_needed()`, and the `prune_one()` helper has been restored. The new version also explicitly handles the `maintenance.rerere-gc.auto` configuration values: negative values force the task to run unconditionally, zero disables it, and positive values specify the minimum estimated stale entries required to trigger the task. The core logic and behavior remain unchanged from v1.

The series touches `rerere.c`, `rerere.h`, `builtin/gc.c`, and the maintenance configuration documentation, and updates `t/t7900-maintenance.sh` to cover the new behavior. Both patches have received "LGTM" from Derrick Stolee and a **tested review** from Thomas Bachem, who confirmed the heuristic works as intended and verified the tests pass. The series is now considered ready for integration.

Key technical details for follow-up discussion: the heuristic samples the `rr-cache` directory using a "17" prefix heuristic, scaling each sampled stale entry by 256 to estimate the total count. The new function `rerere_gc_needed()` (formerly `rerere_gc_estimate()`) returns a boolean indicating whether the task should run, and `rerere_entry_is_stale()` encapsulates the logic for determining staleness. The on-disk format remains unchanged.
