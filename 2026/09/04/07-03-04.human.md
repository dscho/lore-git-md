This is the second iteration of Patrick Steinhardt’s two-patch series improving the `git maintenance` heuristic for the `rerere gc` task. The goal remains the same: replace the hard-coded 60-day cutoff with a dynamic heuristic that estimates stale `rerere` entries and triggers the task only when the count meets or exceeds a configurable threshold (default: 512). The changes reduce unnecessary invocations, lower overhead, and fix a long-standing race condition reported in GitGitGadget PR 2214.

In v2, Patrick addresses the stylistic feedback from Derrick Stolee and Thomas Bachem. The ternary logic in `rerere_gc_condition()` is rewritten for clarity, the function `rerere_gc_estimate()` is renamed to `rerere_gc_needed()` to better reflect its boolean nature, and the helper `prune_one()` is restored. The handling of the `maintenance.rerere-gc.auto` configuration is now explicit: negative values force the task to run unconditionally, zero disables it, and positive values set the minimum stale-entry threshold. The core logic and behavior are unchanged from v1.

The series touches `rerere.c`, `rerere.h`, `builtin/gc.c`, and the maintenance configuration documentation, with updated test coverage in `t/t7900-maintenance.sh`. The new heuristic samples the `rr-cache` directory, using a "17" prefix heuristic and scaling each sampled stale entry by 256 to estimate the total count. This avoids the race condition caused by frequent `rerere gc` runs while still pruning older entries when needed.

Both patches received "LGTM" from Derrick Stolee and were tested by Thomas Bachem, who confirmed the heuristic works as intended with synthetic and real-world `rerere` entries. The series is now considered ready for integration, with no open questions or loose ends. If you care about `git maintenance` overhead or `rerere` behavior, this is a straightforward, well-tested improvement worth reviewing.
