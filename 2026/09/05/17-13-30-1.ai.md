This is a documentation and test patch series targeting the sequencer subsystem, specifically clarifying the behavior of `git cherry-pick --no-commit` when conflicts occur. The series is now in its third iteration, addressing feedback from Junio C Hamano and Phillip Wood.

The series consists of two patches: the first reintroduces a minimal test to verify that `CHERRY_PICK_HEAD` is *not* created when a `git cherry-pick --no-commit` operation fails due to conflicts. This test was previously withdrawn in v2 but is now restored as a single-line check (`test_ref_missing CHERRY_PICK_HEAD`) in the existing `t3507-cherry-pick-conflict.sh` test script. The test directly addresses Phillip Wood’s argument that the absence of `CHERRY_PICK_HEAD` in this scenario is not currently covered by the test suite, despite being an intentional and long-standing behavior.

The second patch updates `Documentation/git-cherry-pick.adoc` to document this edge case explicitly. It removes the earlier advice about using `git commit -c <commit>` to preserve authorship (moved to `git-commit` documentation as suggested by Junio) and instead frames the absence of `CHERRY_PICK_HEAD` as a deliberate design choice. The updated phrasing emphasizes that `--no-commit` is intended as a tool for custom work, where users are expected to manually handle the working tree afterward, making the original authorship less relevant. This aligns with Junio’s feedback to better communicate the design intent.

The series touches no code logic, CLI options, or on-disk formats. The test patch is narrowly scoped, adding only a single assertion to an existing test script, while the documentation patch clarifies an asymmetry with `git revert --no-commit` (which *does* write `REVERT_HEAD`). The behavior being documented was introduced in 2011 (commit d7e5c0cbfb) and is confirmed as intentional by Phillip Wood, but it remained undocumented until now.

The unresolved debate over test coverage remains the primary point of contention. Phillip Wood argues that the test is necessary to guard against regressions in the "tricky" logic of `do_pick_commit()`, while Junio and Patrick Steinhardt oppose it on grounds of test suite overhead. The author has revived the test patch in response to Phillip’s latest argument, but the broader policy question—whether the test’s value justifies its maintenance cost—is still open. The documentation patch itself is uncontroversial in substance but may see further editorial tweaks to sharpen its phrasing.

No merge status is reported; the series is still under review. The patches are small, focused, and well-motivated, addressing a real (if niche) user confusion point. The test patch’s fate will likely hinge on whether the author can justify its inclusion beyond "completeness," possibly by tying it to a larger effort (e.g., test modernization) or demonstrating a concrete risk of regression.
