This is a documentation patch for `git cherry-pick`, clarifying a long-standing but undocumented edge case. The patch updates the man page to explain that `CHERRY_PICK_HEAD` is *not* created when `git cherry-pick --no-commit` encounters conflicts, contrasting this with `git revert --no-commit` (which *does* write `REVERT_HEAD`). The change is uncontroversial and directly addresses a gap in the documentation, though Junio C Hamano suggests a small editorial tweak to better emphasize the design intent behind the behavior.

The patch adds two small updates to `Documentation/git-cherry-pick.adoc`: a bullet point in the conflict-handling list noting that `CHERRY_PICK_HEAD` is skipped when `--no-commit` is used, and a new paragraph under the `--no-commit` option explaining the implications for `git commit`. The latter currently advises users to use `git commit -c <commit>` to preserve authorship when picking a single commit, but Junio questions whether this advice fully captures the intended use of `--no-commit`. He suggests rephrasing to clarify that `--no-commit` is designed to let users build their own work from the changes, rather than merely preserving the original commit’s authorship.

The discussion remains focused on wording and intent, not the behavior itself, which was introduced in 2011 and confirmed as intentional by Phillip Wood. No technical objections have been raised, and the patch is likely to be merged once the minor editorial feedback is addressed. The earlier debate over test coverage (whether to add a test for the absence of `CHERRY_PICK_HEAD`) has been set aside, as the author withdrew the test patch in response to review feedback. This documentation update stands alone as a straightforward improvement.
