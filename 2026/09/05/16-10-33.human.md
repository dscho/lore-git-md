This is a follow-up in the ongoing bugfix series to address a race condition between `rerere` background maintenance and foreground operations like rebase. Junio C Hamano pushes back on the idea of silently allowing a rebase to proceed without recording conflict preimages, even after a lock timeout, calling it an unacceptable regression.

The core concern is user experience: if `git rerere` fails to record a preimage due to a held lock, the user’s subsequent conflict resolution could be lost. Junio argues that this is worse than stopping the rebase outright, since the user can always restart from the last successful commit using `git rebase --onto`. He proposes a loud, hard-to-miss warning when `rerere` fails, instructing the user to manually run `git rerere` before proceeding. This would preserve the user’s work while making the failure visible and recoverable.

Thomas Bachem had previously suggested a finite default timeout (1000 ms) to avoid hangs from stale locks, with an option to wait indefinitely (`rerere.lockTimeout=-1`). Junio’s feedback does not challenge the timeout itself but insists that the failure mode must be explicit. The discussion now centers on how to communicate the failure—whether to stop the rebase, warn loudly, or explore Thomas’s separate idea of writing the rebase stop state *before* invoking `rerere` to allow `--continue` even if the lock is held.

The thread remains focused on balancing robustness (avoiding silent data loss) with usability (not forcing users to restart long rebases). No new code has been posted yet, but the direction is clear: v4 of the patch will need to address the visibility of `rerere` failures, likely by adopting Junio’s warning proposal or Thomas’s pre-invocation stop-state idea. The broader series—including the sequencer patch to disable auto-maintenance during rebase—is still pending.
