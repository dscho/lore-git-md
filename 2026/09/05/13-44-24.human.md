This is a CI/build system discussion reply from Jeff King (Peff) in the ongoing thread about bumping the Ubuntu image for Git’s static-analysis CI job. Peff weighs in on the role of Coccinelle in the project, aligning with Patrick Steinhardt’s refined position but offering a more decisive stance: he would prefer to **avoid using Coccinelle for API transitions** altogether.

Peff argues that the most critical aspect of API migrations is simply alerting developers to the change—something the compiler can often handle via deprecation warnings or interface renames. While Coccinelle can automate fixes, he sees this as a marginal benefit compared to the effort of writing and maintaining semantic patches, as well as the operational friction they introduce (e.g., CI performance regressions, false positives). He suggests that Git’s commit messages and tools like `git blame` or `git log -S` should suffice for explaining transitions, and that the project’s contributors can be trusted to adapt without automated patching.

However, Peff still sees value in Coccinelle for **enforcing coding conventions that the compiler can’t catch**, such as style issues (`if (a == NULL)`) or subtle usage guidelines (e.g., preferring `oidclr()` over `hashclr()`). He even floats the idea of simplifying some rules by making deprecated functions private, which would let the compiler handle enforcement instead. This mirrors Junio C Hamano’s earlier defense of Coccinelle’s role in maintaining consistency, but Peff’s tone suggests he’d be happy to phase out transitional rules entirely.

The email doesn’t address the contested performance regression (SZEDER Gábor’s 4.5× slowdown with Coccinelle 1.3.1) or the CI inefficiency Patrick Steinhardt identified, but it narrows the scope of the debate: the image bump’s original rationale (performance improvement) is now moot, but the underlying question—whether Coccinelle’s benefits outweigh its costs—remains open. Peff’s preference for compiler-based enforcement over Coccinelle for transitions could influence future decisions, especially if others share his view that the tool’s complexity isn’t justified for temporary migrations. The thread is still under review, with no clear path forward yet.
