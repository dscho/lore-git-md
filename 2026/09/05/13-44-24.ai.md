This is a CI/build system discussion reply from Jeff King (Peff) that clarifies his stance on Coccinelle's role in Git's development process. Peff agrees with Patrick Steinhardt's refined position: Coccinelle rules for *temporary* API migrations (e.g., helping in-flight patches adapt to interface changes) are not worth the effort and operational overhead. He argues that compiler errors or clear commit messages are sufficient to alert developers to breaking changes, and that the work required to write and maintain Coccinelle rules for transitions outweighs their benefits.

However, Peff still sees value in Coccinelle for enforcing *permanent* coding conventions that are difficult or impossible to catch with the compiler, such as style antipatterns (`if (a == NULL)`) or preferred function usage (e.g., `oidclr()` over `hashclr()`). He suggests that some of these rules might eventually be obsoleted by refactoring (e.g., making `hashclr()` private), but for now, they remain useful. This reply reinforces the emerging consensus in the thread: Coccinelle should focus on long-term enforcement of consistent coding practices rather than temporary API migrations.
