This is the second patch in a two-patch v3 series updating `git-cherry-pick` documentation to clarify an undocumented edge case. The patch adds explicit documentation for the long-standing but previously unmentioned behavior where `git cherry-pick --no-commit` does *not* create `CHERRY_PICK_HEAD` when the operation fails due to conflicts. This contrasts with `git revert --no-commit`, which *does* write `REVERT_HEAD`, and with successful cherry-picks, which always write `CHERRY_PICK_HEAD`.

The update touches `Documentation/git-cherry-pick.adoc`, adding two key clarifications. First, it modifies the bullet-point list describing what happens when a change is hard to apply, adding an exception for `--no-commit` to the statement that `CHERRY_PICK_HEAD` is set. Second, it expands the `--no-commit` option description with a new paragraph explaining that the absence of `CHERRY_PICK_HEAD` means a plain `git commit` afterward will record the user as the author, framing this as a deliberate design choice rather than an oversight. The phrasing emphasizes that `--no-commit` is intended as a tool for building custom work, where users are expected to manually handle the working tree and authorship.

The patch is uncontroversial in substance and directly addresses feedback from Junio C Hamano on earlier versions, particularly his request to better communicate the design intent behind the behavior. The commit message clearly explains the rationale, citing the 2011 commit (d7e5c0cbfb) that introduced the behavior and noting that Phillip Wood has confirmed it as intentional. The documentation now explicitly defends the asymmetry with `git revert` and removes any ambiguity about authorship handling.

This patch complements the first patch in the series, which reintroduces a minimal test to verify the absence of `CHERRY_PICK_HEAD` in the conflict case. While that test remains contentious (with Junio and Patrick Steinhardt opposing it on test-suite overhead grounds), the documentation update here is a clear improvement that resolves a real user confusion point. The changes are narrowly scoped, well-motivated, and unlikely to see further pushback beyond minor editorial tweaks. The series as a whole is a good example of addressing a niche but legitimate documentation gap with minimal risk.
