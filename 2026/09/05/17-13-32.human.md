This is the second patch in a two-part documentation update for `git cherry-pick`. It clarifies a long-standing but undocumented edge case: when `git cherry-pick --no-commit` fails due to conflicts, it does *not* create `CHERRY_PICK_HEAD`, unlike the default behavior. The patch updates the man page to explain this asymmetry, remove outdated advice about `git commit -c <commit>`, and reframe `--no-commit` as a tool for custom work where the user is expected to manually handle authorship.

The change is small (seven lines added, one removed) and uncontroversial in substance. It directly addresses feedback from Junio C Hamano, who suggested the documentation should better communicate the design intent behind `--no-commit`. The updated phrasing emphasizes that the absence of `CHERRY_PICK_HEAD` is intentional, not an oversight, and that `--no-commit` is meant for users who want to build their own work rather than reproduce the original commit. This aligns with the behavior introduced in 2011 (commit d7e5c0cbfb) and confirmed as correct by Phillip Wood.

The patch is part of a series that also includes a revived test (part 1/2), which adds a single-line check to verify the absence of `CHERRY_PICK_HEAD` in the conflict case. While the test patch remains under debate—Junio and Patrick Steinhardt oppose it on grounds of test suite overhead—the documentation patch itself is straightforward and well-motivated. It addresses a real (if niche) point of user confusion and improves the clarity of the man page without changing any behavior.

For a busy reader, this patch is worth noting if you care about sequencer plumbing or documentation hygiene, but it’s not urgent. The test coverage debate in the first patch is the more interesting part of the series, as it touches on broader questions about when to add tests for edge cases. The documentation patch, however, is a clean, incremental improvement that should land without fuss.
