This is a documentation and test-coverage patch for `git cherry-pick`, part of a two-patch series that clarifies a long-standing but undocumented edge case. The series now restores a minimal test (patch 1/2) and updates the man page (patch 2/2) to explain that `git cherry-pick --no-commit` does *not* create `CHERRY_PICK_HEAD` when the operation fails due to conflicts. This behavior, introduced in 2011, contrasts with `git revert --no-commit` (which *does* write `REVERT_HEAD`) and has been confirmed as intentional by Phillip Wood, but it remained undocumented until now.

The test patch (1/2) adds a single check to `t3507-cherry-pick-conflict.sh` to verify that `CHERRY_PICK_HEAD` is absent after a conflicting `--no-commit` cherry-pick. This plugs a gap in the existing test suite, which previously did not guard against regressions in this scenario. The documentation patch (2/2) updates `git-cherry-pick.adoc` to explicitly note the asymmetry with `git revert` and to clarify that the absence of `CHERRY_PICK_HEAD` is a deliberate design choice, not an oversight. The advice about using `git commit -c <commit>` to preserve authorship has been removed, as Junio C Hamano suggested it belongs in the `git-commit` documentation instead.

The series is uncontroversial in substance but has sparked a policy debate about test coverage. Phillip Wood argues that the test is justified because the logic in `do_pick_commit()` is "tricky" and the existing test suite does not verify this edge case. Junio and Patrick Steinhardt oppose the test, framing it as unnecessary overhead for a behavior that has worked "for a long time" without issues. The author has revived the test in this version, but the discussion remains unresolved. The documentation update itself is straightforward and likely to be merged once the phrasing is finalized.

This patch is worth attention for users who rely on `CHERRY_PICK_HEAD` or `REVERT_HEAD` for scripting or tooling, as it clarifies a subtle but important difference between `git cherry-pick` and `git revert`. The test coverage debate may also interest contributors who follow the project’s evolving standards for test suite maintenance. The series is under review and has no merge status yet.
