This is the **test patch** (part 1/2) in Aleksei Sviridkin’s v3 series, which revives the previously withdrawn test coverage for the absence of `CHERRY_PICK_HEAD` in `git cherry-pick --no-commit` conflict cases. The patch adds a single line—`test_ref_missing CHERRY_PICK_HEAD`—to an existing test in `t3507-cherry-pick-conflict.sh`, pinning the long-standing but undocumented behavior that Phillip Wood confirmed as intentional.

The commit message now explicitly justifies the test by calling out the "tricky" logic in `do_pick_commit()`: whether `CHERRY_PICK_HEAD` is written depends on a three-way interaction between the command (`cherry-pick` vs. `revert`), whether the merge started, and the `--no-commit` flag, all gated by a single conditional. The conflicting `--no-commit` case is the only scenario not already covered by the test suite, making this a narrowly scoped safeguard against future regressions. Aleksei’s framing directly addresses Phillip Wood’s argument that the minimal cost (one line) is justified by the complexity of the logic, while sidestepping Junio C Hamano’s and Patrick Steinhardt’s broader concerns about test suite bloat.

The patch itself is uncontroversial in substance—it merely verifies an existing, intentional behavior—but its inclusion remains debated. The revived v3 series now presents the test as a defensive measure rather than a correction, shifting the discussion from *whether the behavior is correct* (settled) to *whether Git should test edge cases in areas where the logic is non-obvious*. The outcome may hinge on whether the mailing list accepts "the logic is tricky" as sufficient justification for adding tests to long-standing code.
