This is a bugfix patch update (v4) targeting the `rerere` subsystem, part of a two-patch series to fix a race condition where background maintenance (`git rerere gc`) can disrupt foreground operations like rebase. The series is now focused on locking improvements and config overrides to disable maintenance during rebase.

Thomas Bachem responds directly to Junio C Hamano’s feedback on v3, clarifying a key behavioral trade-off. The commit message in v3 suggested that when the lock is held, the rebase should proceed without `rerere` recording to avoid failing entirely. Junio objected, arguing that silently skipping `rerere` risks losing the user’s conflict resolution. Thomas now agrees: in v4, **all callers (including rebase) will wait for the configurable timeout (`rerere.lockTimeout`, default 1000ms) and then fail if the lock remains held**, matching the current behavior. The only exception is `git rerere gc`, which will give up immediately (`RERERE_NOWAIT`) since it’s a best-effort cleanup. This removes the `RERERE_LOCK_OR_DIE` flag and simplifies the patch by dropping changes to callers like `git merge` and `git commit`.

The change is narrow but important: it ensures that rebases (and other operations) don’t silently proceed without `rerere` recording, preserving the user’s work. The rebase will still stop at the conflict if the lock is held, but now it fails cleanly after the timeout rather than skipping `rerere`. Thomas notes that a `gc` running longer than the timeout will still block the rebase, but this should be rare with the sequencer patch (disabling maintenance during rebase) and the default finite timeout. Users who prefer to wait indefinitely can set `rerere.lockTimeout` to `-1`, though Thomas recommends keeping the default finite to avoid hangs from stale locks.

The patch is well-motivated and addresses a real usability issue introduced by the geometric maintenance strategy. The locking logic is now consistent and well-documented, and the trade-offs are clearly explained. The series is under active review, with no unresolved objections to the revised approach. The pending sequencer patch (disabling maintenance during rebase) will further reduce the likelihood of contention. This looks like a solid fix that’s ready for final review.
