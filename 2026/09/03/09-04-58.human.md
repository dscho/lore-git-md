This is the second patch in Patrick Steinhardt’s two-part series improving the heuristic for `git maintenance`’s `rerere gc` task. It replaces the current all-or-nothing logic—where `rerere gc` runs unconditionally if there is at least one rerere entry—with a smarter heuristic that estimates how many stale entries exist and only triggers when that estimate exceeds a configurable threshold (default: 512).

The patch touches `builtin/gc.c`, `rerere.c`, `rerere.h`, and the maintenance configuration documentation. It introduces a new function `rerere_gc_estimate()` that samples entries (using the same “17” prefix trick Git uses for loose objects) to avoid scanning every file, then scales the count by 256 to estimate the total. The `maintenance.rerere-gc.auto` setting now means “run only if the estimated number of stale entries is at least this value,” rather than “run if any entry exists.” Tests in `t/t7900-maintenance.sh` verify the new behavior, including edge cases where entry count or age triggers pruning.

The motivation is clear: the old heuristic spawned `git rerere gc` too often, wasting CPU and needlessly blocking concurrent writers with a central lock. The new approach should reduce both overhead and contention. The patch is well-explained, includes thorough test coverage, and looks ready for review.
