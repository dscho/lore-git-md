This is the core implementation patch (4/4) of the `receive-report` hook feature series, now in its sixth iteration. The patch introduces a new server-side hook that allows administrators to intercept and modify the status report sent to clients after ref updates are committed but before the response is finalized. The hook is motivated by GitLab’s MVCC (multi-version concurrency control) system, where the status report must reflect the repository state *after* all server-side operations (including those beyond `ref_transaction_commit()`) are complete.

The hook receives the complete pkt-line encoded status report on stdin and replaces it with its stdout, while stderr is forwarded to the client via the sideband channel. Exit code semantics are strict: a non-zero exit rewrites all ref status lines to `"receive-report hook failed"` and overwrites all `cmd->error_string` fields, while a zero exit uses the hook’s stdout as the report. The hook is intentionally designed as a single-script filter (not integrated with the config-based hook infrastructure) to avoid the complexity of chaining multiple scripts.

Key technical details include the new functions `run_receive_report_hook()` and `override_cmds_error()`, and the hook’s invocation point after `execute_commands()` but before the report is sent. The patch adds 224 lines of test coverage in `t/t5412-receive-report-hook.sh`, exercising edge cases like sideband relay, stdin/stdout handling, and the hook’s ability to modify the `unpack` status line. Documentation is updated in both `githooks.adoc` and `git-receive-pack.adoc`, with the latter now including a dedicated `RECEIVE-REPORT HOOK` section.

The patch explicitly acknowledges a **consistency trade-off**: the hook’s ability to report a state divergent from the actual repository state violates Git’s principle that remote-tracking branches reflect the server’s state. This divergence is justified by GitLab’s use case, where conservative client-side behavior (not updating remote-tracking branches when the hook reports `ng`) is the desired outcome. The commit message clarifies that the hook owner is responsible for undoing ref changes if needed, and that the hook is only appropriate for servers where rejected updates are not immediately visible to other readers. All prior feedback has been addressed, including Junio’s maintainability concerns and Patrick Steinhardt’s technical questions about exit semantics.
