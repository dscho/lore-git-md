This is the second part of a two-patch series improving the heuristic for the `git maintenance` `rerere gc` task. Derrick Stolee provides a **substantive review** of the patch, focusing on code clarity and naming choices but ultimately endorsing the implementation.

The patch replaces the existing hard-coded 60-day cutoff with a dynamic heuristic that estimates stale `rerere` entries by sampling the `rr-cache` directory (using the same "17" prefix heuristic as loose-object sampling) and scaling each sampled entry by 256. The `git maintenance` task now runs only when the estimated number of stale entries meets or exceeds the configurable `maintenance.rerere-gc.auto` threshold (default: 512). Negative values force the task to run unconditionally, while zero disables it.

Stolee’s feedback is stylistic rather than technical. He suggests the ternary logic in `rerere_gc_condition()` could be written more explicitly to match the documentation, and wonders if `rerere_gc_estimate()` should be renamed to `rerere_stale_above_limit()` since the only caller cares only whether the estimate meets the threshold, not the exact count. However, he acknowledges the current implementation is clean and leaves room for future callers that might need the exact count. He concludes by saying both patches look good to him.

The series has already received a **tested review** from Thomas Bachem, who confirmed the heuristic works as intended and verified the tests pass. With Stolee’s approval, this patch looks ready to proceed, addressing the original goal of reducing unnecessary `rerere gc` invocations and mitigating a long-standing race condition.
