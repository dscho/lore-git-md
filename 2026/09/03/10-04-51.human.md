This is the second patch in a two-patch bugfix series targeting Git's pathspec handling. It fixes a long-standing edge case where `common_prefix_len()` incorrectly returns zero as the common prefix length when an exclude pathspec (e.g., `:!unrelated/path`) appears first in the list, even if subsequent positive pathspecs (e.g., `foo/bar` and `foo/baz`) share a directory (`foo/`). The fix refactors `common_prefix_len()` to explicitly track the first *non-exclude* pathspec item and return its match through an output parameter, ensuring the correct string is used for comparison.

The patch touches `dir.c` and adds a unit test in `t/unit-tests/u-dir.c` to verify the edge case. The implementation adopts Junio C Hamano's feedback from v1, replacing the proposed `pathspec_prefix` struct with an output-parameter approach (`common_prefix_len(pathspec, &matched_prefix)`) to minimize caller churn. The changes are narrowly scoped to pathspec handling and directory traversal, with no broader subsystem impact. The commit message clearly explains the bug and the fix, and the test coverage is thorough.

This patch depends on the first patch in the series, which ensures exclude pathspecs are matched against the full pathname (not the common prefix) to prevent a heap-buffer-overflow. The series is converging toward readiness, with only minor implementation details (e.g., `char **` vs. `const char **` for the output parameter) still unresolved. No other reviewers have weighed in yet, but the discussion with Junio suggests the design is settled. The patches are well-motivated and address a real (if niche) bug with minimal risk of regression.
