This is a documentation patch, the second half of a two-patch series by Aleksei Sviridkin. It updates the `git-cherry-pick` man page to clarify that `--no-commit` skips setting `CHERRY_PICK_HEAD`, a detail that was previously undocumented but has user-visible consequences.

The patch adds a small but important qualification to the existing list of what happens during a conflicting cherry-pick: `CHERRY_PICK_HEAD` is *not* set when `--no-commit` is used. It also extends the `--no-commit` option description to explain that a subsequent `git commit` will record the committer as the author, and that `git commit -c <commit>` can restore the original author and message when picking a single commit. The notes in the patch email go further, explaining that this behavior can be particularly confusing when picking multiple commits, as the resulting commit will carry the last picked commit's message but the committer's authorship, with no on-screen indication of the mismatch.

The motivation is clear and practical: the current documentation implies that `CHERRY_PICK_HEAD` is always set during a conflict, which is not true for `--no-commit`. This gap could lead users to assume the wrong behavior, especially since `git commit` reads authorship from `CHERRY_PICK_HEAD`. The patch addresses this by documenting the actual behavior and providing guidance for restoring the original author when appropriate. The commit message and notes are thorough, explaining both the immediate fix and the broader context, including why the asymmetry with `git revert` (which *does* set `REVERT_HEAD` even with `--no-commit`) is not addressed here.

The patch is well-scoped and appears to be a straightforward improvement to the documentation. It doesn’t change any code or behavior, only clarifies what already happens. The notes also suggest a potential follow-up for `Documentation/revisions.adoc`, but that would be a separate effort. For now, this patch plugs a clear documentation gap in a way that should help users avoid confusion.
