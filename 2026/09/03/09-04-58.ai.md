This is the second patch in Patrick Steinhardt’s two-patch series improving the heuristic for the `git maintenance` `rerere gc` task. It replaces the existing hard-coded 60-day cutoff with a dynamic heuristic that estimates how many stale `rerere` entries would be pruned, then only runs the task when that estimate meets or exceeds a configurable threshold (default: 512).

The patch touches `builtin/gc.c`, `rerere.c`, `rerere.h`, and the maintenance configuration documentation. It introduces a new function `rerere_gc_estimate()` that samples the `rr-cache` directory (using the same "17" prefix heuristic as loose-object sampling) to count stale entries, scaling each sampled entry by 256 to produce the estimate. The `maintenance.rerere-gc.auto` setting is redefined: positive values now specify the minimum number of estimated stale entries required to trigger the task, negative values force it to run unconditionally, and zero disables it.

Test coverage in `t/t7900-maintenance.sh` is expanded to verify the new behavior, including edge cases where the number of stale entries crosses the threshold. The motivation is to reduce unnecessary invocations of `git rerere gc`, which currently runs whenever there is at least one `rerere` entry, even if nothing would be pruned. This change should lower overhead and reduce contention for the central lock file, addressing a long-standing race condition reported in GitGitGadget PR 2214.
