This is a **bugfix** for the `git-contacts` contrib script, targeting a long-standing issue in how it interprets `git blame` output. The patch addresses a misclassification of "boundary" commits—commits where `git blame` stops its traversal—as legitimate contributors to the code being analyzed. These boundary commits often did not touch the file at all, leading to false positives in reviewer suggestions and skewing relevance calculations.

The fix modifies `git-contacts` to explicitly ignore boundary commits by tracking them separately during blame parsing and excluding them from the final contact list. It also adds the `--root` flag to `git blame` to ensure the initial commit (or shallow clone cut-off) is not incorrectly marked as a boundary. The commit message provides thorough motivation, including quantitative analysis: over 100 recent commits, 27 lists lost a false contact, 9 became empty (correctly reflecting no recent activity), and 3 gained a previously obscured name due to denominator shrinkage.

The patch is well-crafted, with clear reasoning in both the commit message and accompanying notes. It avoids unrelated cleanups (e.g., SHA-256 support, exit status checks) to focus on the core issue, though the author notes these as follow-up opportunities. The change is minimal and targeted, touching only the blame parsing logic and its documentation. Testing on the patch itself demonstrates the fix: the script now returns an empty list (the correct answer) instead of a misleading boundary commit author.

This is a standalone patch (not part of a series) and applies cleanly to `maint`. The issue has existed since 2013, so the fix is relevant to all supported releases. No controversy is expected, as the behavior change aligns with the script's intended purpose. The patch includes updates to the `git-contacts` man page to document the boundary commit exception.
