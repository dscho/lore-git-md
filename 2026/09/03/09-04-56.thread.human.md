This thread is about Patrick Steinhardt’s patch series improving the `git maintenance` heuristic for `rerere gc`. The goal is to replace the hard-coded 60-day cutoff with a dynamic heuristic that estimates stale `rerere` entries and triggers garbage collection only when the count meets or exceeds a configurable threshold (default: 512). This reduces unnecessary invocations, lowers overhead, and fixes a long-standing race condition reported in GitGitGadget PR 2214.

The series is now ready for integration. Version 2 addressed all prior feedback, including stylistic changes like rewriting ternary logic for clarity, renaming `rerere_gc_estimate()` to `rerere_gc_needed()`, and restoring the `prune_one()` helper. The behavior of `maintenance.rerere-gc.auto` is now well-documented: negative values force the task, zero disables it, and positive values set the threshold. Derrick Stolee and Thomas Bachem have both reviewed the series. Stolee’s latest email reaffirms his "LGTM" after confirming that his feedback was incorporated, while Bachem provided a tested review, verifying the heuristic’s correctness with both synthetic and real-world `rerere` entries. No open questions or loose ends remain.

The patches touch `rerere.c`, `rerere.h`, `builtin/gc.c`, and maintenance configuration documentation. Key changes include new helpers like `rerere_gc_cutoffs()` and `rerere_id_is_stale()`, and the dynamic heuristic now samples the `rr-cache` directory using a "17" prefix heuristic, scaling stale entries by 256 to estimate the count.
