This thread is about Patrick Steinhardt’s two-patch series that overhauls the heuristic for the `git maintenance` task that garbage-collects `rerere` (reuse recorded resolution) entries. The goal is to replace the current hard-coded 60-day cutoff with a smarter, dynamic approach that avoids deleting recently accessed entries even if there are many, while still pruning older entries regardless of count.

The first patch extracted the staleness logic into a helper function, and this second patch implements the core change: instead of running `rerere gc` whenever there’s at least one entry, it now estimates how many stale entries exist (by sampling the `rr-cache` directory) and only triggers the task if that estimate meets or exceeds a configurable threshold (default: 512). The `maintenance.rerere-gc.auto` setting has been redefined to control this threshold, with negative values forcing the task to run unconditionally and zero disabling it entirely. Tests have been updated to cover the new behavior, including edge cases around the threshold.

The series is still under review, with no feedback yet. It touches `rerere.c`, `rerere.h`, `builtin/gc.c`, and the maintenance configuration documentation, and introduces a new function, `rerere_gc_estimate()`. The motivation is to reduce unnecessary invocations of `rerere gc`, lowering overhead and mitigating a long-standing race condition reported in GitGitGadget PR 2214. No open questions or objections have been raised so far.
