This thread is about Patrick Steinhardt’s patch series (v2) that improves the `git maintenance` heuristic for the `rerere gc` task. The goal is to replace the hard-coded 60-day cutoff with a dynamic heuristic that estimates stale `rerere` entries and triggers the task only when the count meets or exceeds a configurable threshold (default: 512). This reduces unnecessary invocations, lowers overhead, and mitigates a long-standing race condition between `git maintenance` and `git rebase` caused by lock contention on `MERGE_RR.lock`. The series does *not* address collisions between multiple concurrent `rerere gc` invocations—only the frequency of runs.

The series is ready for integration. Junio C Hamano has endorsed it, and Derrick Stolee and Thomas Bachem provided substantive reviews and testing. Key changes include new helper functions (`rerere_gc_needed()`, `rerere_gc_cutoffs()`), a dynamic heuristic that samples the `rr-cache` directory, and updated test coverage in `t/t7900-maintenance.sh`. The configuration `maintenance.rerere-gc.auto` now defines the threshold for triggering the task. No on-disk format changes were made, and the locking mechanism remains unchanged.

Thomas Bachem’s latest email clarifies the series’ scope: it reduces the *frequency* of `rerere gc` runs but does not alter the locking behavior, so concurrent invocations (e.g., two `git maintenance` runs) will still collide. A separate effort (pull.2214.v3) is addressing the lock contention problem directly. No further changes to this series are expected or requested.
