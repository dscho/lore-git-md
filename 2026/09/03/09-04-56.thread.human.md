This thread is about Patrick Steinhardt’s two-patch series that replaces the hard-coded 60-day cutoff in `git maintenance`’s `rerere gc` task with a dynamic heuristic. The goal is to reduce unnecessary invocations, lower overhead, and fix a long-standing race condition (reported in GitGitGadget PR 2214). The new approach estimates stale `rerere` entries by sampling the `rr-cache` directory for entries with a "17" prefix and scaling the count by 256, running the task only if the estimate meets or exceeds a configurable threshold (default: 512).

The series is under review, with v1 posted and no prior versions. Key changes include new functions (`rerere_entry_is_stale()`, `rerere_gc_estimate()`), a behavioral shift to a dynamic heuristic, and updated test coverage in `t/t7900-maintenance.sh`. The configuration `maintenance.rerere-gc.auto` now defines the minimum estimated stale entries required to trigger the task, with negative values forcing a run and zero disabling it.

Thomas Bachem’s recent review confirms the series works as intended. He tested it on commit `3cb9185f65`, verified that tests pass, and demonstrated the heuristic’s behavior with both synthetic and real-world `rerere` entries. The review clarifies that the original reproduction case (20,000 fresh entries with counter-based names) no longer triggers the task because the entries are fresh *and* lack the "17" prefix, while a revised case (5,000 stale, hash-named entries) does trigger it. No bugs or design concerns were raised, and the `Tested-by` trailer signals confidence in the implementation. The series appears ready for further review or integration.
