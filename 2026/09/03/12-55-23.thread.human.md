This thread is about a two-patch series from Aleksei Sviridkin that documents and tests a long-standing but undocumented edge case in `git cherry-pick --no-commit`: when the operation fails due to conflicts, `CHERRY_PICK_HEAD` is *not* created, unlike `git revert --no-commit` (which *does* write `REVERT_HEAD`). The series aims to clarify this asymmetry for users and ensure the behavior is explicitly covered by tests.

The first patch added a test case to `t/t3507-cherry-pick-conflict.sh`, but Junio’s reply revealed a misunderstanding—he initially thought the patch was proposing to *change* the behavior to write `CHERRY_PICK_HEAD` on conflict. This elevated the importance of the second patch (the documentation update), which now serves as a defense of the existing design. The documentation explicitly justifies the asymmetry with `git revert` and explains the implications for `git commit` (e.g., the need to use `git commit -c <commit>` to preserve authorship). The patch is small and focused, touching only `Documentation/git-cherry-pick.adoc`, but it may spark broader discussion about sequencer consistency if reviewers find the asymmetry unintuitive.

The series is currently under review, with no prior versions. Aleksei argues the behavior is intentional (dating back to a 2011 commit) and merely undocumented, but Junio’s feedback suggests the thread could expand into a design discussion. A v2 of the test patch is expected to further clarify the intent. The outcome may hinge on whether reviewers accept the asymmetry or push for alignment with `git revert`.
