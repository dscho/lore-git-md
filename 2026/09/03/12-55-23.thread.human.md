This thread is about a small but long-overlooked gap in Git’s documentation: when `git cherry-pick --no-commit` fails due to conflicts, it does *not* create a `CHERRY_PICK_HEAD` file, unlike `git revert --no-commit` (which does write `REVERT_HEAD`). Aleksei Sviridkin’s patch adds a clear explanation of this asymmetry to the `git-cherry-pick` man page, including why it happens and how users should handle it—such as using `git commit -c <commit>` to preserve authorship when picking a single commit.

The documentation patch itself is uncontroversial and ready for merging, but the thread initially included a test patch to verify the behavior, which the author withdrew after reviewers questioned its necessity. Phillip Wood later argued that the existing test suite doesn’t actually check for the absence of `CHERRY_PICK_HEAD` in conflict cases, proposing a minimal test addition. Junio C Hamano and Patrick Steinhardt pushed back, framing this as a broader policy issue: the test suite’s overhead isn’t justified for edge cases that have worked fine for years. Junio’s latest email steps away from the technical debate, instead critiquing the original test patch’s commit message for being unclear—even an AI misread it as proposing a behavior change rather than a test.

The open question remains whether the test suite should be expanded to cover this case. Phillip Wood sees value in verifying the "tricky" logic behind the behavior, while Junio and Patrick Steinhardt argue that without evidence of past regressions, the test isn’t worth the maintenance cost. For now, the focus is on the documentation patch, which directly addresses the user-facing gap. If the test debate resumes, it will likely hinge on whether the author can tie it to a larger effort (like test modernization) or demonstrate a concrete risk.
