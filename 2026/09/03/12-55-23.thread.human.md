This thread is about documenting a long-standing but undocumented edge case in `git cherry-pick --no-commit`: when the operation fails due to conflicts, `CHERRY_PICK_HEAD` is *not* created, unlike `git revert --no-commit` (which *does* write `REVERT_HEAD`). Aleksei Sviridkin authored a two-part series to address this—one patch adding a test, the other updating the documentation—but has now withdrawn the test patch after reviewers agreed it wasn’t necessary.

The core issue is that this asymmetry can trip up users, particularly when trying to preserve authorship with `git commit` after a conflicted cherry-pick. The current behavior, introduced in 2011, is intentional (confirmed by Phillip Wood), but it wasn’t documented until now. The remaining documentation patch clarifies the behavior, explains the implications for `git commit`, and justifies the design choice. Reviewers initially misinterpreted the test patch as proposing a behavioral change, but the discussion clarified that the goal was purely documentation.

Key participants include Phillip Wood, who defended the existing behavior as correct, and Patrick Steinhardt, who questioned the test’s value. Junio Hamano initially misunderstood the intent but the thread has since converged on the documentation patch as the sole focus. The patch itself is uncontroversial and directly addresses the gap, though the asymmetry it describes might still strike some users as unintuitive. No further changes to the code or test suite are expected.
