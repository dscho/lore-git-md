This thread is about a small but long-overlooked documentation gap in `git cherry-pick --no-commit`: when the command fails due to conflicts, it does *not* create a `CHERRY_PICK_HEAD` file, unlike `git revert --no-commit` (which writes `REVERT_HEAD`). Aleksei Sviridkin’s patch adds a clear explanation of this asymmetry to the man page, including why it matters for users who later run `git commit` (they’ll need `git commit -c <commit>` to preserve authorship for single-commit picks). The behavior itself dates back to 2011 and is confirmed as intentional by Phillip Wood, but it was never documented until now.

The documentation patch (the only remaining part of the series) is uncontroversial and directly addresses the gap. The real debate is whether the test suite should explicitly verify the absence of `CHERRY_PICK_HEAD` in conflict cases. Phillip Wood argues it should, pointing to the "tricky" logic in `do_pick_commit()` and the fact that the existing test (`t3507`) doesn’t cover this edge. Patrick Steinhardt and Junio Hamano, however, push back on adding what they see as a low-value test for a stable, long-standing behavior. Junio’s latest reply frames this as a broader policy question: tests for edge cases need strong justification, especially when the behavior has worked "for a long time" without issues. Aleksei has not yet responded to this latest argument, leaving the test coverage question unresolved. For now, the thread is focused on the documentation update, with the test debate simmering in the background.
