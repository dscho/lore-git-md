This thread is about a small but long-standing gap in Git’s documentation: the behavior of `git cherry-pick --no-commit` when conflicts occur. Aleksei Sviridkin noticed that, unlike `git revert --no-commit`, cherry-pick does not create a `CHERRY_PICK_HEAD` file in this case, making it harder for users to preserve the original commit’s authorship when committing the result. His patch adds a clear explanation to the `git-cherry-pick` man page, documenting the asymmetry and advising users to use `git commit -c <commit>` for single-commit picks.

The documentation patch itself has been uncontroversial, with reviewers agreeing the behavior is intentional and the gap worth filling. However, the thread also sparked a side debate about test coverage. Phillip Wood argued that the existing test suite doesn’t verify the absence of `CHERRY_PICK_HEAD` in conflict cases and proposed adding a minimal test. Junio C Hamano and Patrick Steinhardt pushed back, citing the project’s policy against adding tests for long-standing edge cases without strong justification. That debate remains unresolved, though the author withdrew the test patch and is focusing on the documentation update.

Junio’s latest feedback is editorial: he suggests tweaking the phrasing to better explain the design intent—that `--no-commit` is meant as a "better `git show | git apply`" for custom workflows, where users are expected to modify the working tree afterward. He also recommends moving the advice about `git commit -c <commit>` to the `git-commit` documentation, as it applies more broadly. The patch is likely to be merged with these minor adjustments, assuming the author agrees. The only open question is whether the test coverage debate will resurface in a future iteration.
