This thread is about documenting a long-standing but undocumented edge case in `git cherry-pick --no-commit`: when the operation fails due to conflicts, `CHERRY_PICK_HEAD` is *not* created, unlike `git revert --no-commit` (which does write `REVERT_HEAD`). Aleksei Sviridkin’s two-patch series—now at v3—addresses this with a test (part 1/2) and documentation update (part 2/2). The documentation patch is uncontroversial and clarifies the asymmetry, explaining that `--no-commit` is designed as a tool for custom work where users handle the working tree manually. The test, however, remains hotly debated.

The test itself is minimal—a single line in `t3507-cherry-pick-conflict.sh` to verify `CHERRY_PICK_HEAD` is absent after a conflicted `--no-commit`. Phillip Wood supports it as a necessary safeguard against regressions in the "tricky" logic of `do_pick_commit()`, while Junio C Hamano and Patrick Steinhardt oppose it on test-suite overhead grounds. Aleksei initially withdrew the test in v2 but revived it in v3 after realizing existing tests didn’t cover this case. The documentation patch has already addressed Junio’s feedback on phrasing, but the test’s fate is still unresolved. The series is under review, with no merge status reported.
