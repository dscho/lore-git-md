This thread is about documenting a long-standing but undocumented edge case in `git cherry-pick --no-commit`: when the operation fails due to conflicts, `CHERRY_PICK_HEAD` is *not* created, unlike `git revert --no-commit` (which *does* write `REVERT_HEAD`). Aleksei Sviridkin’s patch adds this detail to the documentation, explaining the asymmetry and its implications for users—such as needing `git commit -c <commit>` to preserve authorship for single-commit picks. The behavior, introduced in 2011, is confirmed as intentional by Phillip Wood, but it had never been documented until now.

The patch itself is uncontroversial and under review, though the thread initially included a test patch (now withdrawn) that sparked debate. Junio initially misread the test as proposing a behavioral change, but Phillip clarified that the current behavior is correct. Patrick Steinhardt argued against the test, calling it unnecessary, and the author agreed to drop it. However, Phillip has since revisited the test question, suggesting it could still be worthwhile as a low-cost safeguard against regressions in a subtle part of the sequencer. The discussion now centers on whether the test’s justification ("the logic is tricky") meets the bar for inclusion, though the documentation patch remains the focus.

Key participants include Aleksei (the author), Phillip Wood (who defended the behavior’s intent and now advocates for the test), and Patrick Steinhardt (who pushed back on the test). The patch touches only `Documentation/git-cherry-pick.adoc` and references no new symbols or behaviors. No merge status has been reported, and the thread is now solely about the documentation update.
