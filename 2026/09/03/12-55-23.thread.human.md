This thread is about documenting a long-standing but undocumented edge case in `git cherry-pick --no-commit`: when the operation fails due to conflicts, `CHERRY_PICK_HEAD` is *not* created, unlike `git revert --no-commit` (which writes `REVERT_HEAD`) or successful cherry-picks. Aleksei Sviridkin’s two-patch v3 series addresses this by adding a minimal test (part 1/2) and updating the documentation (part 2/2). The behavior, introduced in 2011 and confirmed as intentional by Phillip Wood, reflects `--no-commit`’s design as a tool for custom work where users manually handle the working tree afterward.

The documentation patch (part 2/2) is now uncontroversial. It clarifies the asymmetry with `git revert`, removes outdated advice about `git commit -c <commit>` (moved to `git-commit` documentation), and frames the absence of `CHERRY_PICK_HEAD` as a deliberate choice. Junio C Hamano’s feedback on earlier versions has been incorporated, sharpening the explanation of the design intent. The test patch (part 1/2), however, remains contentious. Phillip Wood argues it’s necessary to guard against regressions in the "tricky" logic of `do_pick_commit()`, while Junio and Patrick Steinhardt oppose it on grounds of test suite overhead. The author revived the test in v3, but the broader policy question—whether the test’s value justifies its cost—is still unresolved.

Key participants include Aleksei (author), Phillip Wood (advocating for the test), Junio (editorial feedback, test opposition), and Patrick Steinhardt (test opposition). The series touches `Documentation/git-cherry-pick.adoc` and `t/t3507-cherry-pick-conflict.sh`, with no new symbols or on-disk changes. The thread is now focused on the test coverage debate, though the documentation update itself is a clear improvement.
