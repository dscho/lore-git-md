This thread is about documenting a long-standing but undocumented edge case in `git cherry-pick --no-commit`: when the operation fails due to conflicts, `CHERRY_PICK_HEAD` is *not* created, unlike `git revert --no-commit` (which *does* write `REVERT_HEAD`). Aleksei Sviridkin’s patch adds this clarification to the documentation, explaining the asymmetry and its implications for users (e.g., needing `git commit -c <commit>` to preserve authorship for single-commit picks). The behavior, introduced in 2011, is confirmed as intentional by Phillip Wood, but the lack of documentation has left users confused.

The documentation patch itself is uncontroversial and under review, but the thread has focused on whether to add a minimal test to safeguard against regressions. Aleksei initially included a test patch (part 1/2) but withdrew it after Patrick Steinhardt argued it lacked clear justification, as no regressions had been observed and the logic wasn’t fragile. Phillip Wood, however, has now pushed back, arguing that the existing test coverage (`t3507`) doesn’t actually verify the absence of `CHERRY_PICK_HEAD` in the conflict case. He proposes adding a one-line check (`test_ref_missing CHERRY_PICK_HEAD`) to an existing test, calling the logic "tricky" and the cost negligible. This directly contests Patrick’s earlier stance and reopens the debate over whether the test’s value outweighs its inclusion cost. The thread remains split between the straightforward documentation update and this revived discussion about test coverage.
