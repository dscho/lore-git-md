This thread is about a small but important bugfix for the new `git history` command, introduced in Git 2.46. Jinbao Chen identified a NULL-dereference crash that occurs when `git history` tries to process a commit whose parent's tree object is missing—something that can happen in corrupt repositories, after objects are removed by tooling, or during incomplete restores. The fix is minimal: it adds a guard to check the return value of `repo_parse_tree_indirect()` and error out gracefully with a clear message, following Git's established error-handling patterns.

The patch itself touches only `builtin/history.c` and doesn’t change any behavior beyond preventing the segfault. It’s the second version (v2), with no functional changes from v1—just a tweak to the commit message to remove a parenthetical note about UBSan diagnostics, as suggested in review. The fix is well-motivated, addresses a real edge case, and looks ready for integration. There’s no indication of controversy, and the change aligns with Git’s conventions for handling missing objects. If nothing unexpected comes up in review, this should land smoothly.
