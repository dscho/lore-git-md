This is a two-patch bugfix series targeting the `git maintenance` command’s handling of rerere (reuse recorded resolution) garbage collection. The series improves the heuristic that decides when rerere entries are stale and can be pruned.

The problem, as referenced in the linked GitHub pull request, is that the current logic for determining stale rerere entries is too simplistic: it only considers the age of the entry, ignoring whether the conflict is still present in the repository. This can lead to pruning entries that are still relevant, or keeping entries that are no longer needed.

Patch 1 refactors the rerere code to extract the logic that determines whether an entry is stale into a separate function, making it reusable and easier to test. Patch 2 then updates the `git maintenance` command to use a more sophisticated heuristic: it now checks whether the conflicted files still exist in the worktree before deciding to prune the rerere entry. This should make the garbage collection more accurate and less likely to remove useful data.

The changes touch `builtin/gc.c`, `rerere.c`, and `rerere.h`, along with updates to the maintenance configuration documentation and a new test case in `t/t7900-maintenance.sh`. The commit messages are clear, and the test coverage looks thorough. This appears to be a well-motivated fix for a real issue, and the approach seems sensible. If the linked discussion confirms the problem, this series is likely to be uncontroversial.
