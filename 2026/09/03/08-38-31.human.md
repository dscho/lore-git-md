This is a follow-up in the ongoing discussion about whether Git should allow branch names that conflict with the `@` shorthand for `HEAD`. Kristoffer Haugsbakk points to a 2024 thread where Junio C Hamano argued that `@` as a synonym for `HEAD` should be deprecated and removed, rather than tightening branch name validation to reject `@`. The 2024 thread treated `@` as a general refname issue, not specifically a porcelain usability trap.

Haugsbakk’s reply re-surfaces Junio’s position as a counterpoint to the current thread’s direction. The earlier discussion concluded that `@` should remain valid in refnames (including branch names) for compatibility, and that the real fix would be to phase out `@` as a `HEAD` synonym entirely. This directly contradicts the emerging consensus in the current thread, which favors a targeted fix to `check-ref-format --branch` to reject bare `@` while preserving compound names like `foo@bar`.

The email does not propose a patch or new technical direction, but it injects historical context that may force the discussion to revisit the fundamental question: whether the inconsistency is best resolved by tightening validation or by removing `@` as a `HEAD` synonym. No one has yet addressed how the 2024 position interacts with the current usability concerns, so the thread’s next steps are now less clear.
