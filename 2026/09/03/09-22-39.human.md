This is a follow-up in the ongoing discussion about Elijah Newren’s patch to improve `git push` performance from shallow clones. The patch, now at v2, introduces a new config option (`push.shallowExcludeBoundary`) to avoid sending redundant tree objects, but Derrick Stolee’s review identified a potential flaw: the patch could over-exclude objects needed by other refs in a multi-ref push, leading to false-positive failures (rejected pushes) rather than repository corruption.

Elijah’s reply clarifies that Stolee’s concern—while valid—does not risk repository corruption, thanks to `receive-pack`’s connectivity checks (commit `52fed6e1ce07`). Instead, the issue is a usability trade-off: the patch may reject valid pushes in rare cases where the server lacks the shallow graft, but this is recoverable (users can retry pushing individual refs). Elijah acknowledges the error messages in these cases are currently unclear and plans to improve them, along with adding hints for recovery. He also notes that Stolee’s alternative—repurposing `push.negotiate` for shallow repos—fails in several scenarios (e.g., rebased PRs, unrelated repos, or protocol limitations) and introduces a new race condition between client checks and server-side repacking.

The discussion now centers on whether the project prefers Elijah’s approach (with its performance benefits and rare false-positive failures) or Stolee’s simpler alternative (which avoids the false-positive issue but may resend more data). Stolee has not yet responded to Elijah’s refutation of the corruption risk or the race condition in `push.negotiate`, leaving the trade-offs unresolved. The patch touches `send-pack.c` and adds tests in `t5538-push-shallow.sh`, with the key technical detail being the new `append_reachable_shallow_grafts()` function, which walks from pushed tips to their shallow grafts to exclude them from the pack boundary. This is a substantive debate about correctness, safety, and performance trade-offs in a high-impact area.
