Thread identity: Patch series improving `git maintenance` heuristic for `rerere gc`; v1; originating author Patrick Steinhardt; thread type patch series.

Core problem or goal: Replace the hard-coded 60-day cutoff in `git maintenance`'s `rerere gc` task with a dynamic heuristic that estimates stale `rerere` entries and triggers the task only when the estimated count meets or exceeds a configurable threshold (default: 512). The goal is to reduce unnecessary invocations, lower overhead, and mitigate a long-standing race condition (reported in GitGitGadget PR 2214) caused by frequent `rerere gc` runs.

Current status: Under review; v1 posted. No prior versions. Both patches have received substantive reviews from Derrick Stolee, who has indicated "Both patches LGTM" in his latest feedback.

Key technical details:
- Files touched: `rerere.c`, `rerere.h`, `builtin/gc.c`, maintenance configuration documentation.
- New functions: `rerere_entry_is_stale()` (extracted from existing logic in patch 1), `rerere_gc_estimate()` (introduced in patch 2).
- Behavioral change: `rerere gc` task now uses a dynamic heuristic (sampling the `rr-cache` directory with a "17" prefix heuristic, scaling each sampled entry by 256) to estimate stale entries. The task runs only if the estimate meets or exceeds `maintenance.rerere-gc.auto` (default: 512). Negative values force the task to run unconditionally; zero disables it.
- Test coverage: `t/t7900-maintenance.sh` updated to cover new behavior, including edge cases (threshold crossing, disabled/forced runs).
- New/renamed symbols: `rerere_entry_is_stale()`, `rerere_gc_estimate()` (considered for renaming to `rerere_stale_above_limit()` in future iterations, though no change yet).
- On-disk format: No changes.
- Configuration: `maintenance.rerere-gc.auto` redefined to specify the minimum estimated stale entries required to trigger the task.

Open questions and loose ends:

No action required; the suggestion was non-blocking and stylistic.

He also mused about renaming `rerere_gc_estimate()` to `rerere_stale_above_limit()` to reflect its boolean-like usage, though he noted the current name leaves flexibility for future callers. Neither suggestion is blocking; the series is considered ready for integration as-is.
