This is a feature patch series introducing the new `receive-report` hook for `git-receive-pack`. Version 6 of the series (now four patches) addresses Junio C Hamano’s maintainability concern by replacing the `detailed_reports` boolean parameter with an `enum report_status_version`, making the protocol-version switch more explicit and extensible. The series remains well-motivated by GitLab’s need for server-side MVCC, where the status report must reflect the repository state *after* all post-transaction operations (e.g., background maintenance) complete.

The core implementation is unchanged: the hook acts as a bidirectional filter, receiving the pkt-line encoded status report on stdin and replacing it with its stdout, while forwarding stderr to the client via the sideband channel. A non-zero exit status rewrites all ref status lines to `"receive-report hook failed"` and overwrites all `cmd->error_string` fields, causing the client to perceive the push as failed even if ref updates were committed. The series now explicitly documents this divergence in both the commit message and `githooks.adoc`, clarifying that the hook is only appropriate for servers where a rejected update is not immediately visible to other readers (e.g., GitLab’s candidate-state model).

Test coverage remains thorough (224 lines in `t/t5412-receive-report-hook.sh`), exercising passthrough behavior, failure modes, stdin/stdout handling, sideband relay, and the hook’s ability to modify the `unpack` status line. The series is queued in `seen` and ready for `next`; all prior feedback has been addressed, including Patrick Steinhardt’s substantive reviews and Junio’s consistency concerns. The new `enum`-based refactoring is a clear improvement over the boolean parameter, though the hook’s philosophical trade-off (decoupling reported status from actual repository state) remains a documented design choice rather than a bug.
