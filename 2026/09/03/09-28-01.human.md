This is the final patch in a well-crafted four-part series introducing the `receive-report` hook for `git-receive-pack`. The hook lets server administrators intercept and modify the status report sent to clients after ref updates are committed but before the response is finalized. This version addresses all prior feedback, including Junio C Hamano’s maintainability concerns and Patrick Steinhardt’s technical questions, and adds thorough documentation and test coverage.

The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the repository state *after* all server-side operations (including those beyond `ref_transaction_commit()`) are complete. The design intentionally decouples the reported status from the actual repository state, allowing the server to report a push as failed (`ng`) while still committing ref updates. This violates Git’s traditional principle that remote-tracking branches reflect the server’s state, but the commit message explicitly acknowledges and justifies this trade-off with GitLab’s use case, where conservative client-side behavior (not updating remote-tracking branches when the hook reports `ng`) is the desired outcome.

The implementation adds a new `run_receive_report_hook()` function in `builtin/receive-pack.c` that buffers the hook’s stdout and uses it to replace the status report if the hook exits successfully. A non-zero exit discards the hook’s output and rewrites all ref status lines to `"receive-report hook failed"`. The hook receives the complete pkt-line encoded status report on stdin and can modify any part of it, including the initial `unpack` status line. Test coverage in `t/t5412-receive-report-hook.sh` (224 lines) exercises edge cases like sideband relay, stdin/stdout handling, and the hook’s ability to modify individual ref status lines or abort the entire push.

The patch also documents the hook in `githooks.adoc` and `git-receive-pack.adoc`, explaining its purpose, input/output format, exit semantics, and the three ways it can affect the push outcome: rewriting individual ref status lines, aborting the entire push, or modifying the `unpack` status line. The documentation explicitly warns about the consistency trade-off and the responsibility of the hook owner to undo ref changes if needed. The hook is not integrated with the config-based hook infrastructure, aligning with the single-script design of the existing `proc-receive` hook.
