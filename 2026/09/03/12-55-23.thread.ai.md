Originating author: Aleksei Sviridkin
Thread type: documentation patch

Core problem or goal
Document the long-standing but undocumented edge case in `git cherry-pick --no-commit` where `CHERRY_PICK_HEAD` is *not* created when the operation fails due to conflicts, contrasting with `git revert --no-commit` (which *does* write `REVERT_HEAD`). The goal is to clarify this asymmetry for users, explain the implications for `git commit` (e.g., requiring `git commit -c <commit>` to preserve authorship for single-commit picks), and defend the existing design against potential misinterpretation. The behavior was introduced in 2011 (commit d7e5c0cbfb) and is confirmed as intentional by Phillip Wood, but it remained undocumented until now.

Current status
Under review; the documentation patch (part 2/2) remains uncontroversial and directly addresses the identified gap. The test patch (formerly part 1/2) was withdrawn by the author in response to review feedback, but Phillip Wood’s latest reply revives the debate over minimal test coverage, arguing that the existing test suite (`t3507`) does *not* verify the absence of `CHERRY_PICK_HEAD` in the conflict case. Junio C Hamano’s replies endorse Patrick Steinhardt’s earlier pushback on the test patch, reinforcing the project’s broader policy that tests for long-standing edge cases require strong justification due to test suite overhead. No merge status is reported; the series is still under review.

Junio C Hamano and Patrick Steinhardt oppose this, framing the discussion as a broader project policy question: whether the test suite’s overhead (runtime and maintenance) justifies enshrining a behavior that has worked "for a long time" without issues. Junio’s latest reply critiques the withdrawn test patch’s commit message clarity but does not engage with the substantive test coverage debate. The author has not yet responded to Phillip’s latest argument, and any revival of the test patch will likely need to address the "overhead vs. value" tradeoff directly, possibly by demonstrating a concrete risk (e.g., a plausible regression scenario) or tying the test to a larger effort (e.g., test modernization).
