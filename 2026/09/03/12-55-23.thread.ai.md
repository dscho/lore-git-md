Core problem or goal
Document the long-standing but undocumented edge case in `git cherry-pick --no-commit` where `CHERRY_PICK_HEAD` is *not* created when the operation fails due to conflicts, contrasting with `git revert --no-commit` (which *does* write `REVERT_HEAD`). The goal is to clarify this asymmetry for users, explain the design intent behind `--no-commit` as a tool for custom work, and defend the existing behavior against potential misinterpretation. The behavior was introduced in 2011 (commit d7e5c0cbfb) and is confirmed as intentional by Phillip Wood, but it remained undocumented until now.

Current status
Under review; the series is now v3, with the documentation patch (part 2/2) addressing Junio C Hamano's feedback on design intent phrasing. The test patch (part 1/2) remains contentious, with Junio and Patrick Steinhardt opposing its inclusion on test-suite overhead grounds, while Phillip Wood argues it is necessary to guard against regressions in the "tricky" logic of `do_pick_commit()`. The documentation update is uncontroversial and resolves a real user confusion point. No merge status is reported; the series remains under review, with the test coverage debate as the primary unresolved issue.
