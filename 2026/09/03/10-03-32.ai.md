This is the first patch in a two-patch bugfix series targeting a memory-safety issue in Git's pathspec handling. The patch prevents a heap-buffer-overflow when a negative (exclude) pathspec is shorter than the common prefix derived from positive pathspecs. The bug occurs in `match_pathspec_with_flags()`, where the function incorrectly applies the common prefix to negative pathspecs, causing `match_pathspec_item()` to read out-of-bounds memory. The fix is minimal: pass a zero prefix when matching negative pathspecs, ensuring they are matched against the full pathname.

The patch touches `dir.c` and adds a regression test in `t/t6132-pathspec-exclude.sh` that verifies the fix for the edge case (a positive pathspec with a long common prefix and a shorter, unrelated negative pathspec). The test is well-constructed and reproduces the issue reliably under AddressSanitizer. The commit message clearly explains the bug's cause, its consequences (potential out-of-bounds reads), and the reproduction steps, making the motivation unambiguous.

This patch is a prerequisite for the second patch in the series, which refactors `common_prefix_len()` to correctly derive the common prefix from the first *non-exclude* pathspec. The series adopts Junio C Hamano's output-parameter design (`common_prefix_len(pathspec, &matched_prefix)`), and this patch ensures exclude pathspecs are matched against the full pathname rather than the common prefix. The implementation is narrowly scoped and addresses a real, if niche, bug with minimal risk of regression. No other reviewers have weighed in yet, but the patch is well-motivated and aligns with the agreed-upon design.
