This is a follow-up discussion in an ongoing thread about fixing `git clone --revision` behavior with older protocols. The original issue involved a segmentation fault when using shorthand revision names with protocol v0/v1, where `remote_head_points_at->peer_ref` could be NULL during reference updates.

Nitro Cao responds to Junio Hamano's architectural concerns about the initial fix approach (a simple NULL check), agreeing that masking the segfault isn't the right solution. The discussion has shifted to deeper questions about how `--revision` clones should work - particularly whether they should write any refs at all, given that the documented behavior is to detach HEAD at the specified revision.

Junio proposed restructuring the code to separate connectivity checking from ref-writing operations, suggesting `update_remote_refs()` shouldn't be called at all in `--revision` mode. Nitro asks whether an alternative fix could conditionally call `find_ref_by_name()` instead, and commits to adding regression tests once the correct approach is determined.

The thread shows progress toward a more robust solution that would:
1. Properly handle the NULL `peer_ref` case without masking valid errors
2. Reconsider which operations are actually needed for `--revision` clones
3. Add comprehensive tests covering both crash prevention and repository state

This represents a shift from a quick bugfix to addressing underlying design questions about clone behavior across protocol versions. The next steps will need to resolve the architectural approach and implement corresponding tests.
