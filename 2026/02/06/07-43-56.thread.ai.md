Security vulnerability in `git am`'s patch parsing, initially reported by Matthias Beyer via a real-world Debian package incident (i3 window manager) where a `sleep(1)` call was accidentally introduced via a diff in a commit message. The thread has established consensus this is a security risk, not just a nuisance, as malicious changes could be hidden in commit messages.

Core technical problem: `git am` linearly parses email streams but cannot reliably distinguish between intended patch content (after "---\n") and embedded diffs in commit messages. Jeff King (Peff) explains why neither top-down nor bottom-up parsing works - legitimate diffs may contain standalone "---" lines that would be misinterpreted. Cites three prior discussions (2015, 2022, 2024) showing this is a long-standing known issue, previously considered more an annoyance than security risk. Notes irony that `git format-patch --attach` produces unambiguous MIME parts but `git-mailinfo` still combines them into vulnerable streams.

Peff's latest contribution demonstrates `git am`'s historical flexibility in handling both traditional GNU diff output and MIME-attached patches, explaining this was important in Git's early days when patches came from diverse sources. While such formats are rare today, the design accommodates them, which makes fixing the security issue more complex. Concrete examples show the tool accepts both inline GNU diff output (`diff -Nru` style) and MIME attachments, illustrating why simple solutions like always requiring MIME attachments or strict diffstat formatting won't work for all cases.

Florian Weimer adds practical context about `git am`'s real-world usability, reporting frequent failures with patches created by `git format-patch` that force fallback to traditional `patch` command. This reveals tension between `git am`'s design goals (wide format support) and actual behavior (fragile in practice), suggesting any security fix must account for existing usability pain points beyond just the security vulnerability.

Proposed solutions and their challenges:
- Reverse parsing (Weimer): Process from end to find patch delimiter, but fails when diffs contain "---"
- Indentation conventions (Jacob Keller/Kristoffer Haugsbakk): Rely on `git format-patch` magic strings, but not universally followed
- Delimiter position awareness (Beyer): Track "---" position metadata, requires format changes
- Manual attachment handling (Peff): Separate attachments for `git apply` and `git commit -F`, but breaks existing workflows

Historical context includes similar issues in `git rebase` (malformed "From " lines) solved with a `--rebasing` flag, though that approach doesn't work for email patches. The Debian incident provides concrete motivation for a solution that balances security with backward compatibility. Participants: Matthias Beyer (reporter), Jacob Keller, Kristoffer Haugsbakk, Florian Weimer, Jeff King. Open questions remain about implementation details that won't break legitimate uses while closing the security hole, now with added consideration of `git am`'s existing usability limitations in real-world scenarios and its historical support for diverse patch formats.
