Thread identity: `git am` security vulnerability in patch/commit message parsing, originally reported via Debian incident where `sleep(1)` was accidentally introduced from commit message diff. Core problem remains reliably distinguishing intended patches (after "---\n") from embedded diffs in commit messages when processing email streams.

Technical context: `git am` historically supports both traditional diff output and MIME-attached patches, with design accommodating diverse sources (Peff). Current discussion reveals tension between security needs and backward compatibility, exacerbated by `git am`'s existing usability issues (Weimer) and broader Unix toolchain context (Haufe). Prior discussions (2015, 2022, 2024) established this as long-standing issue now recognized as security risk affecting multiple tools (`git am`, `patch(1)`).

Current status: Phillip Wood has implemented a security-focused enhancement to the sample `commit-msg` hook that detects and rejects commit messages containing unindented diffs and separator lines ("---") that could trigger parser confusion. This builds on his earlier infrastructure changes standardizing hook file handling (`.editorconfig` and `.gitattributes` updates) and provides practical mitigation while deeper parser solutions continue being debated. The enhanced hook now handles:
- Diffs only above the scissors line (where commit message cleanup would remove them)
- Configurable comment characters via `core.commentChar`/`core.commentString`
- Both traditional `diff -` and `Index:` diff headers
- Standalone "---" separator lines that would cause `git am` truncation
- Edge cases like custom comment characters ending with "$"
The implementation maintains existing Signed-off-by line checking while adding these security checks, with clear error messages guiding users to indent problematic content.

Key technical details: Vulnerability stems from two sources:
1. Email/diff ambiguities where:
   - `git format-patch --attach` produces unambiguous MIME but `git-mailinfo` combines streams
   - Traditional GNU diff output (`diff -Nru` style) remains supported
   - Tools strip indentation before parsing, undermining indentation-based solutions
2. Commit message patterns that trigger parser confusion:
   - Raw diffs in commit bodies
   - Separator lines ("---") in commit messages
Wood's solution provides:
- Robust diff pattern matching in commit messages
- Scissors line awareness
- Comment character configurability
- Separator line detection
- Backward compatibility (only affects projects adopting the enhanced hook)

Open questions:
- How to modify `git am` without breaking legitimate uses of both inline and MIME-attached patches
- Whether solution requires coordinated changes across Git and `patch(1)`
- Whether to deprecate support for legacy GNU diff formats given security implications
- How widely the enhanced security hook will be adopted
- Whether to expand hook-based prevention to other dangerous patterns
