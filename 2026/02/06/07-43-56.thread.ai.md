Thread identity: `git am` security vulnerability in patch/commit message parsing, originally reported via Debian incident where `sleep(1)` was accidentally introduced from commit message diff. Core problem remains reliably distinguishing intended patches (after "---\n") from embedded diffs in commit messages when processing email streams.

Technical context: `git am` historically supports both traditional diff output and MIME-attached patches, with design accommodating diverse sources (Peff). Current discussion reveals tension between security needs and backward compatibility, exacerbated by `git am`'s existing usability issues (Weimer) and broader Unix toolchain context (Haufe). Prior discussions (2015, 2022, 2024) established this as long-standing issue now recognized as security risk affecting multiple tools (`git am`, `patch(1)`).

Current status: Multiple proposals evaluated but all have limitations:
- Reverse parsing (Weimer) fails when diffs contain "---"
- Indentation conventions (Keller/Haugsbakk) not universally followed, with Haugsbakk now acknowledging indentation stripping makes this insufficient
- Delimiter position tracking (Beyer) requires format changes
- Manual attachment handling (Peff) breaks workflows
Haufe's input confirms even `patch(1)`'s indentation-based solutions don't fully resolve ambiguity, showing problem spans multiple tools.

Key technical details: Vulnerability stems from email/diff ambiguities where:
- `git format-patch --attach` produces unambiguous MIME but `git-mailinfo` combines streams
- Traditional GNU diff output (`diff -Nru` style) remains supported
- `patch(1)` behavior intentionally handles indented diffs, creating parallel issues
- Tools strip indentation before parsing, undermining indentation-based solutions
Historical precedent shows similar `git rebase` "From " line issues were addressed with flag, but email case more complex.

Open questions:
- How to modify `git am` without breaking legitimate uses of both inline and MIME-attached patches
- Whether solution requires coordinated changes across Git and `patch(1)`
- How to address existing usability pain points (frequent `git am` failures) alongside security fix
- Whether to deprecate support for legacy GNU diff formats given security implications
- How to handle indentation stripping that undermines potential solutions

Participant positions:
- Beyer (reporter): Demonstrated real-world impact, proposed delimiter tracking
- Peff: Explained historical design constraints, proposed attachment separation
- Weimer: Highlighted usability issues, suggested reverse parsing
- Haugsbakk: Revised position after Haufe's input, now acknowledges indentation insufficient
- Haufe: Added `patch(1)` context showing broader ecosystem impact and indentation stripping
- Keller: Previously explored indentation conventions

Related work: `git rebase` "From " line fixes (via `--rebasing` flag), prior discussions on patch parsing ambiguities (2015, 2022, 2024), Debian i3 window manager incident as concrete motivation. Emerging consensus that solution must balance security with both Git's backward compatibility and broader Unix toolchain behavior, with new recognition that indentation-based approaches are insufficient due to parsing pipeline behaviors.
