Security fix discussion for `git am`'s handling of embedded diffs in commit messages. Florian Weimer joins the ongoing thread about how `git am` can mistakenly apply diffs that appear in commit messages, a behavior that recently caused a real-world issue in a Debian package.

Weimer suggests the patch format is actually unambiguous if processed correctly - the diff statistics section precedes the actual diffs, with the commit message coming after. The challenge is that this requires looking at the entire email before deciding what to apply, rather than processing it linearly. He also notes that `git rebase` has had similar issues with commit message content being misinterpreted, though in that case it typically led to failures rather than silent application of unintended changes.

This continues the security-focused discussion about how to modify `git am`'s parsing to avoid applying unintended diffs while maintaining compatibility. Weimer's perspective as a Red Hat engineer adds weight to the security concerns, and his observation about the actual structure of patch emails may help guide a solution. The thread remains active with multiple contributors working toward a fix that would prevent this surprising and potentially dangerous behavior.
