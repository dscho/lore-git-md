The thread addresses a long-standing security vulnerability in `git am` where diffs embedded in commit messages can be misinterpreted as patches to apply. This stems from how `git am` parses email streams, particularly around separator lines ("---") and unindented diffs. The issue recently surfaced in a Debian incident where a `sleep(1)` command was accidentally introduced from a commit message.

The discussion has evolved into a multi-pronged solution. Phillip Wood initially proposed a security-focused commit-msg hook to detect problematic patterns, but after feedback from Junio and Jeff King showing legitimate uses of separator lines, he's reconsidering that approach. Meanwhile, Patrick Steinhardt is working on a new `--accept-ambiguous-patch` flag for `git am` that would require explicit confirmation when ambiguous content is detected.

Kristoffer Haugsbakk's documentation patch, which Junio has already queued for merging, adds clear warnings about these hazards in the man pages for `git-am`, `git-format-patch`, and `git-send-email`. Phillip Wood provided some review feedback suggesting minor clarifications, but the core documentation improvements are moving forward. The warnings specifically cover commit message truncation at "---" lines, empty patch errors from "Index:" lines, and unintended application of unindented diffs.

The thread reveals a tension between security needs and backward compatibility, with distribution maintainers (who apply thousands of patches) being particularly vulnerable. While perfect parsing is impossible, the emerging solution combines technical changes (Wood's hook, Steinhardt's flag) with better documentation (Haugsbakk's warnings) to make risks more visible. The discussion continues on how to preserve legitimate workflows while protecting users from this subtle but serious security issue.
