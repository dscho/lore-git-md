This thread addresses a security vulnerability in `git am`'s patch parsing, where diffs embedded in commit messages can be misinterpreted as actual patches - a problem recently demonstrated by a real-world incident in Debian's i3 package. The core challenge is that `git am` cannot reliably distinguish between intended patch content (after the "---" delimiter) and incidental diffs in commit messages, due to fundamental ambiguities in email/diff formats.

Jeff King (Peff) provided key technical background, explaining why neither top-down nor bottom-up parsing works perfectly, and noting this has been a known issue since at least 2015. The discussion has revealed tensions between `git am`'s design goals (supporting diverse historical patch formats) and real-world usability, with Florian Weimer reporting frequent fallbacks to traditional `patch` commands. Proposed solutions face tradeoffs: indentation-based approaches (suggested by Kristoffer Haugsbakk) don't fully solve the problem, as Jakob Haufe notes by referencing `patch(1)`'s behavior, while more comprehensive fixes risk breaking existing workflows.

The thread has established this is a genuine security risk (not just a nuisance) that spans multiple tools in the Unix ecosystem. While participants agree a fix is needed, the solution must carefully balance security against backward compatibility, considering both Git's internal behavior and how patches flow through the broader toolchain. The discussion remains active with open questions about implementation approaches that can address the vulnerability without disrupting legitimate uses.
