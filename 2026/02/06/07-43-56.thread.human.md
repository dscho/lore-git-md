The thread addresses a long-standing security vulnerability in `git am` where patch content can be misinterpreted when commit messages contain diff-like content. This recently caused a real-world incident in Debian when a `sleep(1)` command was accidentally introduced from a commit message. The discussion has evolved through several phases, with key participants including Jeff King (Peff), Patrick Steinhardt, Phillip Wood, and Kristoffer Haugsbakk.

Current solutions in progress include Haugsbakk's documentation warnings (already queued by Junio) and Wood's enhanced commit-msg hook, though the latter is being reconsidered after Peff noted legitimate uses of "---" separators. Steinhardt has proposed an `--accept-ambiguous-patch` flag for `git am`, while Jacob Keller suggested a more radical "unambiguous mode" that would require breaking changes.

Peff's latest contribution analyzes the technical challenges in Steinhardt's proposal, identifying several legitimate cases that might trigger false positives - such as multiple separators in cover letters or explanatory diffs in commit messages. He notes the difficulty in creating heuristics that catch real threats without disrupting valid workflows, especially for non-Git patch formats. The discussion continues to balance security hardening against practical compatibility concerns, with emerging consensus that Git should focus on hardening `git am` while acknowledging that some vulnerabilities in the broader patch toolchain may remain.
