This thread addresses a long-standing security vulnerability in `git am` where it can misinterpret diffs embedded in commit messages as actual patches to apply. The issue recently caused a real-world incident in Debian when a `sleep(1)` command was accidentally executed from a commit message. The discussion has evolved through several phases, with contributors balancing security needs against backward compatibility and workflow requirements.

The current consensus involves a multi-layered approach: Phillip Wood developed an enhanced `commit-msg` hook to detect unindented diffs (though he's reconsidering detection of "---" separator lines after Junio and Jeff King demonstrated legitimate uses), while Kristoffer Haugsbakk added documentation warnings about the risks. Distributions like NixOS - which applies about 2,800 patches - are particularly vulnerable to this issue.

Patrick Steinhardt now proposes a new direction: rather than trying to perfectly parse ambiguous patches (which Jeff King explained is fundamentally impossible), `git am` should detect potential ambiguities and require explicit confirmation via a new `--accept-ambiguous-patch` flag before proceeding. This shifts the model from silent failure to explicit risk acknowledgment, forcing manual review when dangerous ambiguity is detected.

The solution acknowledges that while perfect parsing is unattainable (since legitimate patches can contain separator lines that look like boundaries), we can at least make the risks visible. The discussion continues to weigh security improvements against real-world workflow needs, with distributions remaining particularly concerned due to their high volume of patch applications.
