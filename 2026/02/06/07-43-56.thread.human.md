This thread addresses a security vulnerability in `git am` where commit messages containing separator lines ("---") or unindented diffs can be misinterpreted as patch content when later applied. The issue was highlighted by a real-world incident in Debian where a `sleep(1)` command was accidentally introduced from a commit message diff.

The discussion has evolved through several phases: initial problem identification, technical solutions from Phillip Wood (enhanced commit-msg hook with diff detection), and documentation improvements from Kristoffer Haugsbakk (now queued by Junio). Jeff King (Peff) raises important concerns about the practical effectiveness of hook-based solutions given low adoption rates, suggesting documentation warnings may reach more users. However, he acknowledges these warnings could confuse non-email workflows.

A key tension has emerged between security hardening and preserving legitimate workflows - particularly Junio Hamano's (and Peff's occasional) use of separator lines for developer notes below commit messages. While this usage exists, Peff's latest input suggests it may not be common enough to block security improvements, though any solution must accommodate these edge cases. The emerging approach combines Wood's technical safeguards (with multiple bypass mechanisms), Haugsbakk's educational documentation, and ongoing parser improvement discussions - recognizing that no single solution fully resolves this long-standing email/diff ambiguity issue.
