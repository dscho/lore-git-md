This thread addresses a long-standing security vulnerability in `git am` where commit messages containing certain patterns (like "---" lines or unindented diffs) can be misinterpreted as patch content when roundtripping through `format-patch` and `am`. The issue particularly affects distribution workflows that apply patches in bulk, as demonstrated by a recent Debian incident.

The discussion has produced a multi-layered solution. Kristoffer Haugsbakk's documentation patch - now queued by Junio - clearly warns about three specific parsing hazards in multiple man pages. Phillip Wood has enhanced a sample commit-msg hook to catch dangerous patterns, though he's reconsidering detection of "---" lines after Junio and Jeff King demonstrated legitimate uses in some workflows. Patrick Steinhardt is working on an `--accept-ambiguous-patch` flag to force manual review when ambiguity is detected.

While perfect parsing remains impossible due to email/diff format ambiguities, the combined approach of documentation warnings, optional hooks, and explicit confirmation flags should help mitigate risks. The solution carefully balances security needs with backward compatibility, preserving legitimate uses of separator lines while making the hazards more visible - especially important for distribution maintainers who may not recognize these subtle parsing dangers.
