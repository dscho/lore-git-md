This thread addresses a security vulnerability in `git am` where embedded diffs in commit messages can be accidentally applied as patches, originally discovered when a `sleep(1)` command was unintentionally introduced via a Debian patch. The discussion has evolved to balance security hardening with backward compatibility, particularly for distribution workflows.

Phillip Wood initially proposed a security-enhanced `commit-msg` hook to detect unindented diffs, but after feedback from Junio Hamano and Jeff King demonstrating legitimate uses of separator lines ("---") in maintainer workflows, he's reconsidering that specific check. Kristoffer Haugsbakk's documentation warnings about patch roundtrip hazards have already been queued for merging. The current approach combines these documentation improvements with configurable comment characters and clear error messages, while preserving existing workflows.

Matthias Beyer's latest contribution provides important real-world perspective from NixOS, where distributions apply thousands of upstream patches. He confirms that even experienced users may not recognize this parsing hazard, and agrees that `git commit` warnings would likely be ineffective. The discussion now acknowledges that while the security risk is real—particularly for distribution maintainers who often use `patch` directly—immediate solutions are constrained by practical realities of existing workflows. Documentation improvements are proceeding, while longer-term parser enhancements remain under discussion. The thread reflects a pragmatic consensus that layered, non-disruptive measures are preferable to breaking changes, even if they provide incomplete protection.
