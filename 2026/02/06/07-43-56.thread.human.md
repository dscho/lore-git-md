This thread addresses a security vulnerability in `git am` where commit messages containing unindented diffs or separator lines ("---") can be misinterpreted as patch content, potentially introducing unintended changes. The issue stems from historical design choices that support both traditional diff formats and MIME attachments, creating parsing ambiguities that affect multiple tools in the Unix toolchain.

Phillip Wood has implemented a practical mitigation through an enhanced `commit-msg` hook that detects and rejects dangerous patterns while maintaining backward compatibility. The latest iteration adds detection of unindented "---" lines that would cause `git am` to truncate commit messages, building on earlier work to catch embedded diffs. The hook intelligently handles custom comment characters and provides clear guidance for fixing issues by indenting problematic content.

Junio Hamano has raised an important counterpoint about legitimate workflows where he uses "---" lines in-progress commits as formatting reminders, noting that while the hook can be bypassed with `--no-verify`, the safety check might disrupt valid use cases. This highlights the tension between security hardening and workflow flexibility that remains unresolved.

The discussion reflects broader challenges in modifying `git am`'s behavior without breaking existing uses of both inline and MIME-attached patches. While Wood's hook provides immediate protection, deeper parser ambiguities will require continued discussion, particularly around whether to deprecate legacy GNU diff formats given their security implications. The thread shows emerging consensus on a layered approach combining defensive hooks with potential future parser improvements.
