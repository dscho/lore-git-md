This thread addresses a security vulnerability in `git am` where the tool can mistakenly apply diffs embedded in commit messages as actual changes, demonstrated by a real-world incident in Debian's i3 package. The core issue stems from `git am`'s linear parsing approach, which cannot reliably distinguish between intended patch content (after the "---" delimiter) and embedded diffs in commit messages. Jeff King (Peff) has explained why neither top-down nor bottom-up parsing solves the problem cleanly, as legitimate diffs may contain standalone "---" lines that would be misinterpreted.

The discussion has revealed that `git am` was designed to handle a wide variety of patch formats - including traditional GNU diff output and MIME-attached patches - which was important in Git's early days but now complicates securing the tool. Florian Weimer added practical context about `git am`'s real-world usability issues, noting frequent failures already force users to fall back to the traditional `patch` command. Several solutions have been proposed but each has drawbacks: reverse parsing fails when diffs contain "---" lines, indentation conventions aren't universally followed, and requiring MIME attachments would break existing workflows.

Participants - including Matthias Beyer (who reported the issue), Jacob Keller, Kristoffer Haugsbakk, Florian Weimer, and Jeff King - are grappling with how to preserve `git am`'s flexibility while closing the security hole. The challenge is to find an approach that won't break legitimate uses, especially given the tool's existing usability limitations in real-world scenarios. Historical context shows similar issues were previously considered more an annoyance than a security risk, but the Debian incident has elevated the urgency for a solution.
