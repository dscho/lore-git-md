The thread addresses a long-standing security vulnerability in `git am` where diffs embedded in commit messages can be accidentally applied as patches, stemming from ambiguity in parsing email-formatted patches. This recently caused a real-world incident in Debian where a `sleep(1)` command was unintentionally introduced from a commit message.

The discussion has progressed through several solutions: Kristoffer Haugsbakk's documentation patch warning about the hazard has been finalized and queued by Junio, while Phillip Wood enhanced the sample `commit-msg` hook to catch problematic patterns. Jacob Keller then proposed adding an unambiguous boundary marker (`--- git-patch-boundary ---`) after the traditional `---` separator, maintaining backward compatibility while giving newer clients a definitive patch start point.

Jeff King (Peff) has now weighed in with alternative approaches. He questions whether Keller's marker would need to be so visually intrusive to be unique that it might disrupt email readability. Instead, he suggests two alternatives: having `git format-patch` automatically quote potentially problematic commit message content (similar to how email handles `>From` lines), or adding a `--strict` mode to `git am` that enforces clean `---` separators for Git-generated patches. Peff acknowledges neither solution is perfect but aims to balance security with workflow compatibility.

The thread shows consensus forming around a layered defense - combining documentation warnings, defensive hooks, boundary markers, and strict parsing modes - rather than relying on any single solution. Junio remains skeptical about achieving perfect backward compatibility while solving the security issue, and has floated the idea of signed patches as an alternative security boundary. Technical discussions continue about edge cases and implementation details of the various proposals.
