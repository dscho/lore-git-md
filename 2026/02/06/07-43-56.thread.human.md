This thread addresses a security vulnerability in `git am` where patch/commit message parsing can be confused by embedded diffs, particularly affecting distribution workflows. The issue stems from ambiguity between intended patches (after "---") and diffs in commit messages, with historical examples like a Debian incident where `sleep(1)` was accidentally introduced from a commit message.

Kristoffer Haugsbakk's documentation patch, now queued by Junio after review from Phillip Wood, adds explicit warnings to `format-patch-caveats.adoc` about three key hazards: "---" truncation, "Index:" line issues, and unindented diff application. Wood suggested several improvements to the wording, including removing an unnecessary `git-send-email` reference and clarifying the comparison with `patch(1)`.

The discussion reveals a tension between security needs and backward compatibility, as some legitimate workflows (noted by Peff and Junio) use separator lines in commit messages. Phillip Wood is reconsidering "---" detection in his security-focused commit-msg hook after this feedback, while Patrick Steinhardt proposes a new `--accept-ambiguous-patch` flag to force manual review when ambiguity is detected.

Distribution maintainers like Beyer (NixOS) are particularly vulnerable, applying thousands of patches where this could cause issues. The emerging solution combines documentation warnings, hook-based prevention (though Peff questions effectiveness given low hook usage), and explicit confirmation flags - preserving legitimate uses while addressing the security risk.
