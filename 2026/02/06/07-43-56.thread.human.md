This thread addresses a security vulnerability in `git am` where the tool can misinterpret diffs embedded in commit messages as actual patches to apply, particularly affecting distribution workflows that process patches in bulk. The core issue stems from ambiguity in distinguishing between intended patches (after the "---" separator) and accidental diffs in commit messages.

Kristoffer Haugsbakk's documentation patch has been queued by Junio after incorporating feedback, adding explicit warnings about this hazard in the man pages. The warnings now clearly describe three patterns that can trigger incorrect parsing: three-dash lines, "diff -" lines, and "Index:" lines. Phillip Wood has proposed a security-focused commit-msg hook (though reconsidering some detection logic), while Patrick Steinhardt suggests adding an `--accept-ambiguous-patch` flag to force manual review of ambiguous cases.

Christoph Anton Mitterer's recent email serves as a reminder that while the documentation improvements are valuable, they don't technically fix the underlying vulnerability. The discussion reveals tension between maintaining backward compatibility (as some legitimate workflows use separator lines) and implementing stronger security measures. Junio has demonstrated a workflow dependency on separator lines in email-based development, making complete removal of the ambiguous parsing behavior challenging.

The thread shows consensus that distributions are particularly high-risk users of patch application, with NixOS maintainers confirming they apply around 2800 patches where this could be an issue. While documentation warnings represent progress, some contributors view them as insufficient without accompanying code changes to prevent the vulnerability.
