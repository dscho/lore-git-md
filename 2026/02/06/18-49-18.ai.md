This is a feature proposal for `git log --graph` that aims to simplify complex merge visualization. Toon Claes introduces a new --untangle` option that modifies how merge commits are displayed in the graph output.

The key idea is to stop showing the full ancestry lines for merged branches, which can make complex merge histories (especially octopus merges) appear unnecessarily cluttered. Instead, merged branches are displayed as if they originate from the merge commit itself, skipping the connection back to their original branch point. The patch implements this by calculating merge bases but then suppressing the display of connections to them.

The RFC includes:
1. A new `--untangle` flag (name still under discussion)
2. Core graph drawing logic changes in graph.c
3. New test cases demonstrating the simplified output
4. Acknowledgment of current bugs and memory leaks

The motivation comes from real-world Git repository graphs that become excessively wide and hard to read, particularly with long-running topic branches and frequent merges. The author cites a particularly messy example from git.git's own history.

This appears to be a well-motivated proposal that addresses a genuine usability pain point. The implementation touches core graph drawing logic and would need careful review for edge cases, but the concept seems sound. The RFC nature suggests the author is open to feedback on both the approach and naming (`--untangle` vs alternatives like `--ignore-merge-base`).

Key technical details for future reference:
- New `only_first_merge_base` flag in `struct git_graph`
- Modified column tracking with `ignored_merge_bases` list
- Changes to `graph_insert_into_new_columns()` and merge base calculation
- New test file `t4214-log-graph-octopus.sh` with --untangle cases
- Potential points of discussion: memory management, edge case handling, and whether this belongs in core Git vs a porcelain command
