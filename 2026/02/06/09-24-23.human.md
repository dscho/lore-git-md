Security vulnerability in `git am`'s patch parsing, with historical context from Jeff King (Peff). This thread was sparked by a real-world incident where a Debian package (i3 window manager) accidentally introduced a `sleep(1)` call via a diff embedded in a commit message. Peff explains why neither top-down nor bottom-up parsing can reliably distinguish between intended patch content and embedded diffs, citing three prior discussions (2015, 2022, 2024) where this was recognized as a known issue.

The core problem stems from `git am` linearly parsing email streams that combine both intended patches and commit message content in ways that can't be reliably separated. Peff notes the irony that while `git format-patch --attach` produces unambiguous MIME parts, `git-mailinfo` still combines them into vulnerable streams. He suggests the only robust solution would be manual separation of attachments fed to `git apply` and `git commit -F` directly, though this would break existing workflows.

The discussion has moved from whether this is a problem (consensus is yes) to how to fix it without breaking legitimate uses. Peff provides historical context about similar issues in `git rebase` that were solved with a "--rebasing" flag, though that approach doesn't work for true emailed patches where the receiver doesn't yet have the commit object. This remains an open security issue with no clear backward-compatible solution yet.
