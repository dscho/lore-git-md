Security vulnerability in `git am`'s patch parsing, with historical context from Jeff King (Peff). This is part of an ongoing discussion about how `git am` can mistakenly apply diffs embedded in commit messages, which Matthias Beyer reported could lead to security issues (demonstrated by a real-world Debian package incident).

Peff explains why neither top-down nor bottom-up parsing can reliably distinguish between intended patches and embedded diffs, noting this is a long-standing issue with three previous discussions (2015, 2022, 2024). He points out the irony that while `git format-patch --attach` produces unambiguous MIME parts, `git-mailinfo` still combines them into vulnerable streams. The only robust solution would require manual separation of attachments, but this would break existing workflows.

The thread has established consensus that this is a real security vulnerability, not just a nuisance. Previous solutions like reverse parsing (Weimer), indentation conventions (Keller/Haugsbakk), and delimiter awareness (Beyer) all face backward compatibility challenges. Peff adds historical context about similar issues in `git rebase` that were solved with a gross-but-effective `--rebasing` flag, though that approach doesn't work for true email patches.

Key technical details: the vulnerability stems from linear parsing of email streams that can't reliably distinguish intended patches from embedded diffs. The discussion has moved from whether this is a problem (agreed it is) to how to fix it without breaking legitimate uses. Participants include security-conscious contributors (Beyer, Weimer) and Git experts (Peff, Keller), with the Debian incident providing concrete motivation for a solution.
