This is a follow-up discussion in Adrian Ratiu's ongoing series to make Git hooks configurable via Git configuration. Junio Hamano asks for clearer motivation behind the feature, noting that the current patch series doesn't sufficiently explain why users would want this capability compared to the traditional filesystem hooks.

The exchange highlights a key point in the review process - even for well-constructed technical changes, the maintainer wants explicit justification for new features. Junio's question suggests the series needs to better articulate the use cases, such as:
- Enabling hooks to follow configuration inheritance (global/remote/local)
- Allowing hooks to be version-controlled via included configs
- Supporting multiple hooks per event without symlink chains
- Making hooks portable across repositories via shared configs

The thread remains constructive, with Junio focusing on ensuring the change solves real problems before accepting the infrastructure. Adrian will likely respond with the rationale in a follow-up version. This patch represents infrastructure work (the `list_hooks()` refactoring) that enables the config-based functionality to be built cleanly in subsequent patches.
