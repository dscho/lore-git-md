Security fix discussion for `git am`'s diff parsing behavior. Jeff King (Peff) weighs in on the thread about `git am` applying diffs embedded in commit messages, which recently caused a real-world issue in a Debian package. He confirms the current parsing approach looks for "---\n" from the top of the email, but explains why reversing the search direction (as suggested by Matthias Beyer) wouldn't work - legitimate diffs can contain "---" lines that would be misinterpreted as delimiters.

Peff notes this is a known issue with historical discussions dating back to 2015, but the community has generally treated it as a nuisance rather than a security risk, assuming humans review patches before applying. He points out that while `git format-patch --attach` produces unambiguous output, `git-mailinfo` still combines the parts in a way that could be confused by embedded diffs. The email suggests the problem may require deeper changes than simple parsing tweaks, as existing solutions could break other workflows. This moves the discussion forward by clarifying technical constraints while acknowledging the security implications raised by the Debian incident.
