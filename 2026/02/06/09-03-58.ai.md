This is a security discussion about `git am`'s handling of diffs in commit messages, with Jeff King (Peff) weighing in on the parsing challenges. The thread was sparked by a real-world incident where a `sleep(1)` call was accidentally introduced via a diff in a commit message applied by `git am`.

Peff confirms the current behavior where `git am` looks for the patch delimiter ("---\n") from the top of the email, but explains why parsing from the end wouldn't work either - legitimate diffs may contain standalone "---" lines that would be misinterpreted as delimiters. He cites three prior discussions (2015, 2022, 2024) showing this is a long-standing known issue, though typically considered more of a nuisance than a security risk since humans would presumably notice such diffs when reviewing.

The email notes the irony that `git format-patch --attach` produces unambiguous MIME parts, but `git-mailinfo` still combines them into a single stream vulnerable to the same parsing issues. Peff suggests the only robust solution would be to manually separate attachments and feed them to `git apply` and `git commit -F` directly, though this would break some existing workflows.

Key technical details for future reference: the security issue stems from linear parsing of email streams that can't reliably distinguish between intended patch content and embedded diffs in commit messages. The thread has established this is a real vulnerability with precedent, but solutions face backward compatibility challenges with existing patch application workflows.
