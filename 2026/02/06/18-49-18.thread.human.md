This RFC thread explores a proposed `git log --graph --untangle` option (alternately named `--ignore-merge-base`) to simplify complex history visualization by displaying merged branches as originating from merge commits rather than their original branch points. The discussion has progressed through several technical rounds since Junio C Hamano's initial positive reception of the concept.

Johannes Sixt (Hannes) and Toon Claes have been the primary technical voices, with Hannes raising substantive concerns about edge cases while Toon responds with concrete visualization proposals. The current implementation in graph.c introduces new data structures but still has memory leaks and incomplete handling of criss-cross merges and `--boundary` interactions. 

The latest exchange focuses on visualization challenges for backward merges - cases where the merge base isn't the first parent, like "sync with main" scenarios. Hannes demonstrates how the current approach creates inconsistent subgraph representations depending on viewing context, arguing this could mislead users about actual commit relationships. While Toon had proposed using markers (like '.' or '/') to indicate truncated history, Hannes suggests these may need additional context like commit references to maintain accuracy.

Key open questions remain: finalizing the visual indicators for truncated ancestry, resolving backward merge display logic, and ensuring the visualization accurately represents Git's full complexity. The thread shows steady progress in addressing maintainer concerns through concrete examples, but the feature clearly needs more development around edge cases before it could be considered for merging. Contributors are encouraged to test the proposal on real repositories to further demonstrate its utility.
