Security hardening patch for `.git` validation, v2. This is a follow-up to Tian Yuchen's RFC proposing to make Git fail explicitly when encountering malformed `.git` entries (like FIFOs or sockets) during repository discovery. The current behavior silently ignores such cases, which could potentially lead to unsafe attachment to parent repositories.

The patch implements Junio Hamano's suggestion to optimize the `lstat()` check by moving it after the happy-path directory test, avoiding unnecessary system calls in normal cases. When `.git` exists but isn't a regular file or directory, it now either dies (with `die_on_error=true`) or returns `GIT_DIR_INVALID_GITFILE` (when `die_on_error=false`).

The core debate remains around whether this security hardening is justified given that an attacker who can replace `.git` likely already has broader filesystem access. Junio has questioned the severity while acknowledging the change could help detect filesystem corruption sooner. The patch remains in RFC state while these questions are resolved, with no new participants joining the discussion since Junio's initial review.

This is a small change (15 lines) but touches the sensitive repository setup path in `setup.c`. The technical implementation appears clean, though the security benefits may be limited. Worth watching for maintainer feedback on whether the hardening justifies the change given backward compatibility concerns with systems using non-standard `.git` entries.
