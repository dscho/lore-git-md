This is a feature patch series introducing parallel hook execution, building on Adrian Ratiu's prior work to make hooks configurable. The current discussion focuses on design considerations for parallelization safety and terminal access.

Phillip Wood raises two key points from prior art in hook managers: (1) some hooks like pre-commit often need serial execution when modifying shared state (e.g., the index), and (2) terminal access regressions have occurred historically when changing hook execution. Adrian confirms the current implementation preserves backward compatibility by defaulting to serial execution (jobs=1), which maintains terminal access, while parallel execution (jobs>1) would buffer outputs through pipes. He notes this matches Jeff King's original design intent to avoid regressions.

The thread reveals tension between safety and flexibility in parallelization. While the series provides infrastructure for future fine-grained control (like per-hook parallelization settings), Adrian is taking a conservative approach in this initial version - keeping serial execution as the default and requiring explicit opt-in for parallel behavior. This aligns with the project's typical incremental development style, though it leaves open questions about how to document parallel-safe hooks and manage per-hook configurations in future iterations.

Technical details of note for future reference: the implementation uses `hook.jobs` config for parallelism control, maintains the `hook.forceStdoutToStderr` runtime flag for output handling, and touches multiple builtins (am, checkout, clone) with tests in t/t1800-hook.sh. The discussion suggests the next version may refine job count defaults and precedence rules based on feedback about CPU count assumptions and compile-time overrides.
