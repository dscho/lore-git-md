This is a security-focused patch in RFC state that hardens Git's repository discovery by validating `.git` file types. It's the second iteration of Tian Yuchen's proposal to make Git explicitly fail when encountering malformed `.git` entries (like FIFOs or other non-regular files) rather than silently ignoring them, which could potentially lead to unsafe attachment to parent repositories.

The key technical change moves the `lstat()` check after the happy-path directory test as suggested by Junio Hamano, optimizing the common case where `.git` is a valid directory. When `.git` exists but isn't a regular file or directory, the patch now either dies (when `die_on_error=true`) or returns `GIT_DIR_INVALID_GITFILE` (when false). The implementation remains focused on this specific edge case without expanding scope to other repository discovery scenarios.

The thread's core debate continues around whether this hardening is justified given the limited attack surface (an attacker who can replace `.git` likely already has broader access) and potential backward compatibility concerns for systems using non-standard `.git` entries. Junio has questioned the security severity but acknowledged the change could help detect filesystem corruption sooner. The patch remains in RFC state while these questions are resolved, with no new participants joining the discussion since Junio's initial review. The technical implementation is small (15 lines) but touches the sensitive repository setup path in `setup.c`.
