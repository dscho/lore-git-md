This is the second patch in Patrick Steinhardt's 4-part series improving the `git history` command's user interface. The patch focuses on moving merge commit validation earlier in the execution flow to prevent wasted user input.

The change introduces a new helper function `revwalk_contains_merges()` that checks whether the revision walk contains any merge commits (commits with 2+ parents) before proceeding with user interaction. This validation now happens during the `setup_revwalk()` phase rather than later, ensuring users don't lose work when their input would ultimately be rejected due to unsupported merge commits.

The implementation is clean and well-contained, adding about 40 lines to `builtin/history.c` while touching only one test case to account for the earlier validation. The test change demonstrates the improved behavior - it now fails before editor invocation rather than after, using `-c core.editor=false` to verify the early exit.

This patch follows the series' theme of improving validation timing, building on the first patch's work to move other checks earlier. It maintains the careful separation between validation and action phases while adding another layer of user protection. The change is straightforward but meaningful for usability, characteristic of Patrick's attention to both technical correctness and user experience.
