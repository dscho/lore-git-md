This is a technical clarification in the ongoing LOP (Large Object Promisors) patch series, specifically addressing how Git handles object fetching from multiple promisor remotes. Christian Couder responds to Patrick Steinhardt's concern about object location determination when multiple promisor remotes with different filters are configured.

The key point is that Git currently uses a simple fallback mechanism: when an object is missing, it tries promisor remotes in config file order before falling back to the main remote. This behavior predates the current patch series and is documented in the partial clone documentation. Christian notes there's a planned GSoC 2026 project ("Implement promisor remote fetch ordering") to make this ordering configurable, linking to the project ideas page recently updated by Kaartic Sivaraam.

The exchange highlights an important limitation in the current implementation - the inability to intelligently determine which promisor remote should have a given object based on filter criteria. This remains an area for future improvement, with the current series maintaining the existing fallback behavior while adding new auto-filter capabilities. The discussion shows the careful consideration being given to backward compatibility and the incremental nature of Git's evolution, even as new features are added.
