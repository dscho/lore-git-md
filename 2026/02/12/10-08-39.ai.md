This is part 8/9 of a series implementing promisor remote enhancements, specifically modifying the `promisor_remote_reply()` API to be more flexible. The patch changes the function signature to separate its two responsibilities: processing server advertisements (which always needs to maintain repository state) versus constructing reply strings (which is sometimes unnecessary).

The key change makes `promisor_remote_reply()` take a `char **accepted_out` parameter that can be NULL when the caller only needs the side effects of processing the advertisement. This avoids unnecessary string construction when the reply won't be used, as will be the case in upcoming fetch-pack changes. The implementation carefully maintains all existing behavior when the output parameter is provided.

The patch touches `connect.c`, `promisor-remote.[ch]` with straightforward mechanical changes that:
1. Update the single call site in `connect.c` to use the new API
2. Restructure `promisor_remote_reply()` to conditionally build the reply string
3. Update the function's documentation to reflect the new contract

This appears to be a clean, focused change that improves the API's flexibility while maintaining backward compatibility. It follows the pattern seen elsewhere in the series of making incremental improvements to support the larger LOP (Large Object Promisors) functionality. The change was suggested by Patrick Steinhardt in an earlier review and fits naturally with the series' goal of enhancing promisor remote handling.
