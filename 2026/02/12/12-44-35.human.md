This is the second patch in Patrick Steinhardt's series improving the `git history` command's validation behavior. The patch focuses on detecting merge commits earlier in the execution flow to prevent wasted user input.

The change moves merge commit validation from after user interaction to before it, specifically in the `setup_revwalk()` phase. This ensures users don't lose work when their input contains unsupported merge commits. The implementation adds a new `revwalk_contains_merges()` helper that checks for commits with multiple parents (merges) by adding `--min-parents=2` to the revision walk arguments.

The patch maintains the existing behavior where merge commits still can't be reworded, but now fails fast with a clear error message before any user editing occurs. A test is updated to verify this new timing by using `-c core.editor=false` to simulate the early failure case.

This is a well-motivated UX improvement that follows logically from the first patch's validation restructuring. The implementation is clean and focused, with appropriate test coverage. As part of Patrick's ongoing `git history` work, it demonstrates his characteristic attention to both technical correctness and user experience.
