This is a discussion about improving security around `git am`'s patch parsing behavior, specifically regarding commit messages that could be misinterpreted as patches. Jeff King (Peff) responds to Phillip Wood's proposal to update the sample `commit-msg` hook to reject problematic messages.

Peff expresses skepticism about the effectiveness of modifying the sample hook, noting that few projects use commit-msg hooks and that email-based workflows are now a minority. He suggests documentation updates would reach more users, though acknowledges warnings in `git-commit` might confuse those not using email workflows. He references prior discussions (2015, 2022, 2024) that established this as a long-standing issue.

The email highlights the tension between security improvements and practical adoption - while Phillip's hook-based solution is technically sound, Peff questions whether it will meaningfully address the problem given low hook usage. He points to Matheus Bernardino's earlier work adding format-patch checks as a complementary approach.

Key technical context: the vulnerability stems from ambiguity in parsing email streams where commit message content (like unindented diffs or "---" lines) can be misinterpreted as patch content. The discussion represents ongoing efforts to layer solutions (hooks, documentation, parser improvements) while balancing security with backward compatibility.
