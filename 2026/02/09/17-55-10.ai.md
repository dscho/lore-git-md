This is a test infrastructure patch in response to Patrick Steinhardt's series fixing CI failures on Windows/MSVC related to `iconv(1)` availability. Junio Hamano raises a key architectural question about the approach.

The thread concerns tests that use `iconv(1)` for commit message encoding conversions. Patrick's patch makes these tests skip the `iconv` call when the ICONV prerequisite fails, but still pass the message through Git's commit machinery with the specified encoding. Junio questions whether this is valid - should tests without ICONV support be running these encoding tests at all, given that Git's behavior differ when built without iconv?

The core issue revolves around test expectations: when ICONV is unavailable, should we (a) skip encoding-sensitive tests entirely (Junio's implied position) or (b) run them with modified expectations (Patrick's approach). The patch currently implements (b) by keeping the test structure but avoiding the `iconv` executable call when ICONV isn't available.

This touches on deeper questions about how Git should handle encoding conversions when built without iconv support, and what guarantees (if any) exist about `i18n.commitEncoding` behavior in such configurations. The test changes are straightforward mechanically (wrapping `iconv` calls in ICONV checks), but Junio's comment suggests the solution might need to address the higher-level testing philosophy.
