This is a security-focused discussion about hardening the `commit-msg` sample hook to prevent patch parsing ambiguities in `git am`. The thread revisits a long-standing issue where embedded diffs in commit messages can be misinterpreted when patches are emailed and reapplied, potentially introducing unintended changes (as happened in a Debian incident where `sleep(1)` was accidentally inserted).

Phillip Wood originally proposed adding checks to the sample hook to reject messages containing unindented diffs or separator lines ("---") that could confuse `git am`. After feedback from Jeff King and Junio Hamano demonstrating legitimate uses of separator lines in maintainer workflows, Phillip is now reconsidering that approach - he's leaning toward keeping the diff detection but dropping the "---" line restriction to avoid disrupting valid use cases.

Key points in this email:
- Phillip acknowledges Jeff's concern that few users run commit-msg hooks, but argues having the check in the sample hook does no harm
- He notes the issue affects non-email workflows too, like when patches are downloaded from GitHub
- Kristoffer Haugsbakk has already contributed documentation warnings about the hazard
- Phillip is wary of adding warnings to `git commit` itself as that might confuse users not working with email patches

The discussion shows the project carefully balancing security hardening against backward compatibility, with multiple layers of protection emerging: documentation warnings, optional hook checks, and parser improvements - while preserving legitimate maintainer workflows that depend on the current behavior.
