This is a discussion about Git's branch listing behavior in new repositories, specifically around the inconsistency between `git branch` and `git status` output before the first commit.

Ben Knoble responds to Ryan Johnson's bug report about the confusing behavior where `git status` shows "On branch master" in a new repository while `git branch` shows no output until the first commit is made. Ben notes this is technically an "unborn" or "orphan" branch state (referencing `git switch` documentation) but doesn't directly address the UX inconsistency Ryan highlighted.

The thread reveals a real usability issue - users wanting to rename the default branch from "master" to "main" (as encouraged by modern standards) can't easily see or modify the pending branch name before the first commit. Ben points to `init.defaultBranch` configuration and mentions Git 3.0's planned default branch change to "main" as relevant context, though this doesn't solve the immediate visibility problem.

The discussion touches on core branch plumbing behavior and suggests this could be worth changing to provide more consistent information to users, though no concrete patch proposal has emerged yet. The issue appears straightforward to fix, with clear user benefit, but would require careful consideration of backward compatibility and the technical distinction between promised vs. created branches.
