This is a security-related follow-up in the ongoing discussion about ANSI escape sequence injection in Git's sideband channel (CVE-2024-32002, CVE-2024-52005). Johannes Schindelin strongly disagrees with Junio C Hamano's decision to make the security sanitization opt-in rather than enabled by default.

Schindelin argues that terminal emulators cannot distinguish between legitimate and malicious control sequences, so the responsibility for sanitization must remain with Git. He points out that his proposed default (allowing only color sequences while blocking higher-risk control codes) would not break legitimate use cases like colored pre-receive hooks. The concern about Japanese ISO encodings conflicting with control bytes is dismissed as theoretical given the existing "remote: " prefix.

The core contention is over security philosophy: Schindelin advocates for defense-in-depth with safe defaults, while Junio prioritizes backward compatibility. Schindelin proposes a compromise where sanitization remains off by default in Git 2.x but is documented to change in Git 3.0, allowing time for adaptation while committing to secure-by-default behavior in the next major version.

This email represents a last-ditch effort to shift the maintainer's position before the change is finalized. The technical implementation itself is not in question - the debate centers entirely on policy defaults and security responsibility. Schindelin's arguments reflect his experience maintaining Git for Windows and familiarity with terminal security issues, but Junio's maintainer authority means the opt-in model will likely prevail unless other security experts weigh in strongly.
