This is the second patch in Patrick Steinhardt's v3 series improving the `git history` command's validation and UI. The patch focuses on early detection of merge commits, which the replay infrastructure cannot yet handle.

The change moves merge commit detection before user input is requested, preventing wasted effort when users try to edit merge commits that can't be processed. It introduces a new `revwalk_contains_merges()` function that checks for commits with multiple parents (--min-parents=2) in the revision walk. The test is updated to use `false(1)` as an editor to verify the check happens before editor invocation.

This is a well-contained change that cleanly addresses a specific UX pain point in the new command. The implementation follows established patterns in the codebase and includes appropriate test coverage. As part of the larger series that has already addressed reviewer feedback across multiple iterations, this patch appears ready for inclusion.
