This is a configuration behavior question about submodule recursion settings. D. Ben Knoble notes that the order of `submodule.recurse` and `fetch.recurseSubmodules` in config files affects which setting takes precedence, even though their documentation suggests they should be treated as separate concerns. The same issue appears to affect `push.recurseSubmodules`.

The core of the issue is that both config options write to the same internal variable, with the last one read winning. This creates a potential gotcha where config file ordering affects behavior in ways that aren't obvious from the documentation. Knoble is asking whether this was an intentional design choice (he found no discussion in the original patch series) and whether changing this behavior would be considered too breaking at this point.

The email raises a valid documentation/UX concern but doesn't propose a specific solution - it's more of a "should we do something about this?" probe. Given that this touches submodule behavior and config precedence rules, it's likely to interest contributors who work on submodules and configuration handling. The question about whether this qualifies as a breaking change suggests the author is aware this could be a sensitive area.
