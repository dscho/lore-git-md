This is a configuration behavior question regarding submodule recursion settings. D. Ben Knoble raises an issue where the interaction between `submodule.recurse` and `fetch.recurseSubmodules`/`push.recurseSubmodules` config options produces potentially surprising results due to parse order dependency.

The core observation is that these configs all write to the same internal variable, with later values overriding earlier ones, regardless of which specific option is being set. This means `submodule.recurse=true` followed by `fetch.recurseSubmodules=on-demand` in config files will result in `true` behavior rather than the expected `on-demand`, because the more specific fetch setting gets overwritten by the general submodule setting if it appears later.

The email questions whether this behavior was intentional, noting there wasn't much discussion in the original patch series that introduced `submodule.recurse`. It also asks whether changing this to let more specific options win would be considered a breaking change, and if not, whether the current order-dependent behavior should at least be documented.

This touches on Git's config precedence rules and the tension between backward compatibility and intuitive behavior. The issue affects both fetch and push operations similarly. The thread appears to be starting a fresh discussion about whether the current implementation matches user expectations and whether/how it should be changed.
