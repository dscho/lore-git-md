This thread began as the final review phase for Patrick Steinhardt’s 8-patch series making geometric repacking the default `git maintenance` strategy, which had secured approvals from key reviewers (Derrick Stolee, Justin Tobler, Toon Claes) and addressed all prior feedback. However, the focus has now shifted to two critical bugs reported by Stefan Haller: an overly aggressive `geometric-repack.auto` threshold that triggers background repacks in tiny repositories (e.g., 4-object repos), and a concurrency failure where `prune_packed_objects()` removes fanout directories during concurrent operations, causing "invalid object" errors and commit failures in real-world tooling like lazygit CI.

Patrick Steinhardt has proposed a targeted fix for the auto-condition bug, raising the default `maintenance.geometric-repack.auto` value from 100 to 6700 (matching `gc.auto`) to reduce repack frequency in small repositories. This change, along with documentation updates, is intended to mitigate both the threshold issue and the observed concurrency failures, though the latter stems from a preexisting race condition in the repack/prune machinery that has become more visible since Git 2.54.0. While the threshold adjustment may mask the concurrency issue in practice, the underlying problem remains unaddressed. The series itself is technically ready for merging, but these bugs now take priority, with the concurrency issue posing a data corruption risk during routine operations. The discussion is ongoing to validate whether the threshold change is sufficient or if further hardening of the repack/prune logic is needed.
