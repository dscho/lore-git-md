This thread discusses Tian Yuchen's RFC patch series to harden Git's repository discovery by validating `.git` file types. Currently, Git silently ignores malformed `.git` entries (like FIFOs), which could potentially lead to unsafe attachment to parent repositories. The proposed change would make Git explicitly fail when encountering such cases.

The technical implementation is small (15 lines in `setup.c`) but touches sensitive repository setup code. Version 2 incorporates Junio Hamano's suggestion to optimize the common case by moving the `lstat()` check after verifying the happy path where `.git` is a valid directory. When encountering invalid `.git` files, the patch now either dies (in strict mode) or returns a specific error code.

The main debate centers on whether this hardening is necessary given that an attacker who can replace `.git` files likely already has broader system access. Junio has questioned the security severity but acknowledged the change could help detect filesystem corruption. There are also concerns about backward compatibility for systems using non-standard `.git` entries intentionally.

The patch remains in RFC state while these questions are resolved, with no new participants joining the discussion since Junio's initial review. The scope remains narrowly focused on `.git` validation without expanding to other repository discovery edge cases.
