This thread discusses a security-focused RFC patch from Tian Yuchen that would harden Git's repository discovery by validating `.git` file types. Currently, Git silently ignores malformed `.git` entries (like FIFOs), which could potentially lead to unsafe attachment to parent repositories. The patch proposes explicit validation that would either fail hard (die()) or return an error code when encountering invalid `.git` files.

Junio C Hamano has weighed in with some skepticism about the security impact, noting that if an attacker can replace `.git` with a FIFO, they likely already have broader write access. However, he acknowledges the value in failing explicitly to help users notice filesystem corruption sooner. The main points under discussion are whether to use die() or error returns, how to maintain backward compatibility, and where to optimally place the lstat() check (Junio suggests moving it after the happy-path directory check to avoid unnecessary stats in normal cases).

The thread remains in RFC status while the community debates the security impact and error handling approach. The change is small (12 lines) but touches the sensitive setup.c path, so the discussion is focusing on getting the design right before finalizing.
