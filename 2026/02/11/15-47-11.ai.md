This is a security-focused discussion about hardening `git am` against accidental patch application from commit message diffs. The thread has progressed through multiple technical proposals, with Jeff King (Peff) now proposing a `--strict` mode that would enforce stricter parsing rules for Git-generated patches by requiring a clean `---` separator.

Junio Hamano agrees with the approach, noting that modern Git-generated patches are more predictable than the diverse sources `git am` originally handled. The key insight is that for Git's own output, we can safely ignore traditional patch markers (`Index:`, `diff -`) before the `---` separator, significantly reducing the risk of misinterpreting commit message content as patch content.

The discussion builds on prior work including Kristoffer Haugsbakk's documentation warnings and Patrick Steinhardt's proposed `--accept-ambiguous-patch` flag. Peff's `--strict` mode offers a middle ground between full backwards compatibility and security, leveraging Git's predictable output format to reduce false positives. This aligns with the emerging layered solution combining documentation, parser improvements, and explicit confirmation mechanisms.

Technical details to note for future reference: the proposal assumes Git-generated patches will always include the `---` separator, allowing the parser to safely skip traditional patch markers before that point. The implementation would need to handle both the new strict mode and legacy behavior, likely through a config option alongside the command-line flag. The solution remains focused on the specific case of Git-generated patches rather than attempting to solve the general email/diff ambiguity problem.
