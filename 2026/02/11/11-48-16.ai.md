This is a technical discussion about the implementation of auto-filter resolution in the LOP (Large Object Promisors) patch series. The conversation focuses on how Git should determine which promisor remote to fetch objects from when multiple remotes are configured with different filters.

Patrick Steinhardt raises a key implementation question about the proposed `--filter=auto` behavior: when multiple promisor remotes are configured with different filters, how does Git determine which remote to query for a missing object? He notes that Git cannot always "reverse" the filter logic to determine which remote should have the object, since the filter conditions may not be invertible in all cases.

This discussion occurs in patch 7/9 of the v2 submission, which implements the core auto-filter resolution infrastructure. The thread context shows this is part of a larger effort to enhance promisor remote functionality with configurable filter storage and dynamic filter combination. Christian Couder had previously explained the intention to combine filters from multiple accepted promisor remotes, and Patrick is now probing the edge cases of that approach.

The question touches on fundamental limitations in the promisor remote design - while combining filters allows using multiple remotes, actually locating objects across those remotes may require additional metadata or heuristics beyond what the filters themselves provide. This could impact the reliability of partial clone operations when using auto-filter mode with multiple promisor remotes.
