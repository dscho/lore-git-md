This is a security-focused patch proposal addressing the long-standing issue of `git am` potentially misparsing diffs embedded in commit messages. Jacob Keller builds on prior discussion to suggest a backwards-compatible solution that would introduce an unambiguous boundary marker (e.g., `--- git-patch-boundary ---`) after the traditional `---` separator in patch emails.

The key insight is that older clients would continue treating `---` as the divider (current behavior), while newer clients could recognize the explicit marker as the definitive patch start. This maintains compatibility with existing workflows that tolerate text between `---` and the diff, as the new marker would appear in that traditionally ignored space. The proposal acknowledges some tricky edge cases around ensuring the marker can't be accidentally included in commit messages and handling multiple markers.

This comes after Kristoffer Haugsbakk's documentation warnings about the issue have been queued, and alongside Patrick Steinhardt's proposed `--accept-ambiguous-patch` flag. The thread shows Junio Hamano's openness to solutions that don't break old clients, though he expresses skepticism about whether perfect backwards compatibility is achievable. Keller's approach attempts to thread that needle by leveraging the existing tolerance for text between separators.

The security vulnerability stems from email/diff ambiguities where tools strip indentation before parsing, particularly affecting distribution workflows. The proposal represents one of several layered solutions under discussion, including documentation, hooks, parser improvements, and now this boundary marker concept. Technical questions remain about edge case handling and whether the syntax would work across diverse tooling.
