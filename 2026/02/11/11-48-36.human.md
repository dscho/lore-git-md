This is a technical discussion about naming and behavior in the promisor remote filter implementation, part of the ongoing LOP (Large Object Promisors) effort.

Patrick Steinhardt and Christian Couder are discussing naming choices for variables tracking server-advertised filters in the promisor remote code. The discussion focuses on patch 8/9 in the series, which handles storing and combining filters from multiple promisor remotes. Patrick suggests renaming `captured_filters` to either `remote_filters` or `accepted_filters` to better reflect the variable's purpose. Christian had proposed `server_filters` as an alternative to the original `advertised_filters` name that might cause confusion with an existing variable.

They also briefly touch on whether promisor remotes must always have advertised filters, with Christian explaining there are valid cases where a server might choose not to advertise filters, leaving filter selection to the client. This appears to be a minor refinement discussion in an otherwise settled implementation, with both contributors showing flexibility on naming while maintaining technical precision about the expected behavior.
