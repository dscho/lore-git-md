This is a discussion about configuration handling for the new `--revert` feature in `git replay`. The thread has been focused on implementing revert functionality for server-side use in GitLab's Gitaly service, with recent versions refining the technical details.

Kristoffer Haugsbakk responds to Toon Claes' question about whether `git replay --revert` should respect the `revert.reference` configuration option (which controls whether revert messages include full OIDs or abbreviated hashes). Toon suggests that for consistency, `git replay` should match `git revert`'s behavior when this config is set. Kristoffer raises the broader question about whether plumbing commands like `git replay` should ignore user configurations entirely to ensure predictable behavior, or if callers should explicitly disable configs when they want consistent output.

The exchange highlights an ongoing tension in Git between user-facing porcelain commands (which typically respect configs) and plumbing commands (which often aim for predictable behavior regardless of user settings). This particular case sits at the boundary since `git replay` is gaining both plumbing and porcelain characteristics through the `--revert` feature. The discussion hasn't reached consensus yet, but it's probing an important design question about how this new capability should interact with existing Git configuration patterns.
