This is a security-focused discussion about hardening Git's repository discovery behavior when encountering malformed `.git` entries. The original patch from Tian Yuchen proposed failing explicitly when `.git` is neither a regular file (for submodules/worktrees) nor a directory, rather than silently continuing up the directory tree as the current NEEDSWORK comment suggests.

Junio Hamano, the maintainer, questions whether this scenario is truly "very dangerous" as claimed, noting that if an attacker can replace `.git` with a FIFO or device node, they likely have broader write access to cause more serious harm. However, he acknowledges that failing explicitly could help users notice filesystem corruption or mistakes sooner.

The key open questions are whether failing hard is the right approach (versus continuing discovery) and whether to use `die()` or return an error code for caller handling. Junio also suggests optimizing the patch by moving the new validation after the common case checks to avoid unnecessary `lstat()` calls in normal operation.

This is a focused, security-adjacent change to a sensitive path in `setup.c`, with clear motivation but some debate about the threat model and user impact. The maintainer appears generally receptive to the direction but wants the implementation refined.
