Feature proposal for a new `pre-add` hook, addressing a gap in Git's staging workflow. This is version 2 of the patch, significantly reworked based on maintainer feedback from Junio Hamano.

The patch introduces a hook that runs after `git add` computes the new index state but before committing it to disk. The hook receives two arguments: a temporary copy of the original index and the lockfile containing the proposed changes. This allows hook authors to inspect the computed results directly with standard Git tools, without needing to interpret pathspec or mode flags.

Key technical details:
- Uses tempfile API to create index snapshots
- Implements rollback mechanism via lockfile handling
- Bypassed with `--no-verify` flag
- Not invoked for interactive/patch/dry-run modes or `git commit -a`
- Includes comprehensive test coverage (t/t3706-pre-add-hook.sh)

The implementation follows Junio's suggested architecture from v1 feedback, where the hook receives both original and proposed index states for comparison. The design trades prevention of object database writes for correctness of hook inputs - blobs may already be written when the hook runs, but rejection still leaves the on-disk index unchanged.

The patch includes example use cases for blocking `.env` files and secret keys in content, demonstrating how the hook could enforce policy. Documentation updates cover both the new hook and `--no-verify` option.

This appears to be a well-considered implementation addressing the maintainer's technical concerns from v1, with thorough test coverage and clear documentation. The design provides a clean way to validate staging changes while maintaining Git's core behavior.
