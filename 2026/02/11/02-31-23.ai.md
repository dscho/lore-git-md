This is a technical discussion about improving `git am`'s patch parsing to handle ambiguous diffs in commit messages more safely. Jacob Keller proposes a backwards-compatible approach to mark unambiguous patch boundaries.

The thread has established that `git am` can misinterpret diffs embedded in commit message text as actual patches to apply, creating a security risk. Patrick Steinhardt previously suggested an `--accept-ambiguous-patch` flag, while Junio expressed skepticism about making an "unambiguous mode" work without breaking older clients.

Keller's proposal introduces a new marker after the traditional `---` separator that newer Git versions would recognize as the true patch boundary, while older versions would continue treating `---` as the divider (their current behavior). Since both old and new versions already tolerate extra text between `---` and the diff, this approach would maintain compatibility while allowing newer clients to parse patches more reliably.

The key insight is that the new marker would appear *after* the `---`, so old clients would still stop at `---` (as they do now) and ignore the subsequent marker, while new clients could use the marker to definitively identify the patch start. This builds on the existing behavior where tools accept arbitrary text between the commit message and diff.

This represents a potential path forward for the security hardening effort, complementing the already-queued documentation warnings and sample hook changes. The proposal now awaits technical review to assess whether it truly maintains compatibility in all cases and whether the marker syntax would work across the diverse tooling that processes Git patches.
