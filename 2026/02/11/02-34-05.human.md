This is a security-focused discussion about making `git am` safer when parsing patches with embedded diffs in commit messages. Jacob Keller proposes a backwards-compatible solution to the long-standing issue where `git am` can accidentally apply diffs that were meant to be part of a commit message rather than the patch itself.

Keller suggests adding an unambiguous boundary marker (e.g., `--- git-patch-boundary ---`) after the traditional `---` separator in patches. This would allow older clients to continue working as they do today (treating `---` as the divider), while newer clients could use the explicit marker to definitively identify where the patch starts. The proposal aims to maintain compatibility with existing workflows while providing a clearer security boundary.

The thread shows this is part of a layered approach to the problem, which also includes documentation warnings (already queued by Junio), a proposed `--accept-ambiguous-patch` flag from Patrick Steinhardt, and Phillip Wood's enhancements to the sample `commit-msg` hook. Keller acknowledges there are tricky edge cases to consider, particularly around ensuring the new marker can't be accidentally included in commit messages and handling multiple markers.

This continues a long-running discussion about patch parsing safety, with recent urgency coming from a Debian incident where a `sleep(1)` command was accidentally introduced from a commit message diff. The proposal looks promising for balancing security and compatibility, though implementation details need careful review.
