This is a feature patch adding HTTP 429 (rate limiting) retry support to Git's HTTP client. It's the first part of a two-patch series, with the second patch adding trace2 instrumentation. The implementation has gone through significant revision since v1 based on Taylor Blau's feedback, and now appears technically sound with comprehensive test coverage.

The patch introduces three new options to control retry behavior: `http.maxRetries` (default 0, making this opt-in), `http.retryAfter` (fallback delay when no Retry-After header exists), and `http.maxRetryTime` (300s ceiling for any delay). The implementation handles both RFC-compliant Retry-After header formats (delay-seconds and HTTP-date) and uses slot-specific timers to support concurrent requests.

Taylor's review focuses on several refinements: suggesting the default `http.retryAfter` should be 0 rather than -1 for consistency, noting opportunities to DRY up error handling, questioning some control flow in `run_active_slot()`, and recommending shorter error messages. He also points out some minor style nits around curly braces and comparisons that could be adjusted to better match Git's coding guidelines.

The implementation appears production-ready with thorough test coverage in t5584-http-429-retry.sh (286 lines) and LeakSanitizer verification. The changes touch core HTTP handling in http.c and http.h, with supporting modifications in remote-curl.c and test infrastructure. While Taylor raises some stylistic and organizational points, there are no outstanding technical concerns - this looks like a well-considered feature that's nearing readiness for merging.
