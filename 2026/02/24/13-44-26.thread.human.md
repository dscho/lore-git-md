This thread discusses a proposal by Titania Sugiarto to add selective file/folder merging between branches, responding to user requests for this capability. While the initial suggestion envisioned merging specific portions of files or directories rather than whole files, Thomas Guyot pointed out that existing Git functionality (`git merge --no-commit` plus manual index editing or cherry-picking) might cover some use cases without new features.

Junio C Hamano, the Git maintainer, has now weighed in decisively against implementing this as a core feature. He explains that merge commits represent semantic acceptance of an entire branch's changes, and selectively merging parts while recording it as a full merge would create confusion about what was actually incorporated. While acknowledging the user need, Junio argues this approach would cause more problems than it solves, particularly for later branch operations and historical accuracy. He maintains that the current workflow - while more manual - provides clearer semantics.

The discussion appears effectively closed by Junio's response, which emphasizes Git's design philosophy around merge commits as complete units. Unless significant new technical arguments emerge that address these semantic issues, this proposal is unlikely to progress further in its current form. Those needing this functionality will need to continue using the existing workarounds.
