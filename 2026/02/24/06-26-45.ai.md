This is the final patch in a bugfix series addressing pack validation issues with large objects. The patch specifically fixes an infinite loop in `git fsck` when verifying large objects that exist in multiple packfiles (one corrupt, one valid).

The key insight is that the existing `odb_read_object_stream()` path could trigger an infinite loop due to the MRU (most recently used) pack list behavior when the same object exists in multiple packs. The fix bypasses this by using `packfile_read_object_stream()` directly when we already have the pack/offset information, which provides more reliable verification.

Patrick notes that while brian m. carlson's original test case in t1050 happened to trigger the bug, he added a more targeted test in t1450-fsck.sh that reliably reproduces the scenario with two large blobs in separate packs. The test demonstrates that fsck now correctly identifies which pack contains corruption without getting stuck in a loop.

The series has gone through multiple iterations (v2 and v3) with thorough review from Jeff King and Junio Hamano. All feedback has been addressed, including interface concerns around `packfile_read_object_stream()` and improved error handling. The changes span several object storage subsystems but maintain backward compatibility while fixing this critical verification issue.

This represents a significant improvement in packfile validation reliability, particularly for repositories with large objects stored across multiple packs. The minimal final patch (just 2 lines in pack-check.c) effectively resolves the infinite loop scenario while preserving all existing corruption detection capabilities.
