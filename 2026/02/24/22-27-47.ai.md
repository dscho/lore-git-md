This is a discussion about a proposed feature for selective file/folder merging between branches, with Junio C Hamano weighing in on the implications. The thread began with Titania Sugiarto suggesting a feature to merge specific files/directories from one branch to another, citing user demand for such functionality.

Junio responds by explaining the conceptual problems with partial merges, noting that while technically possible via `git merge --no-commit` and manual editing, such merges create semantic confusion. He emphasizes that merge commits represent an endorsement of the entire branch's changes, and selectively merging parts while recording it as a full merge would misrepresent the branch's state. This could lead to confusion later when others assume all changes from the merged branch are present.

The maintainer's position is clear: this approach would create more problems than it solves, particularly around tracking what was actually merged and maintaining the semantic meaning of merge commits. He doesn't reject the underlying user need but argues strongly against implementing it through partial merges, suggesting the current workflow (cherry-picking or manual editing) is preferable despite being more labor-intensive.

Key technical points include the importance of merge commits as complete semantic units and the problems that would create for later branch operations and bug tracking. The discussion remains at the conceptual level, with no implementation details proposed.
