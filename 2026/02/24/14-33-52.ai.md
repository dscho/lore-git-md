Feature improvement for `git send-email`'s character encoding handling. This patch from Shreyansh Paliwal addresses usability and correctness issues in the command's handling of non-ASCII email subject lines.

The change replaces a length-based charset validation heuristic (which could allow invalid encodings through if they were long enough) with proper semantic validation using Perl's `Encode::find_encoding()`. The new flow warns users about invalid charset names while still allowing them to proceed if they insist. The prompt wording is also updated from "Which 8bit encoding should I declare [UTF-8]?" to "Declare which 8bit encoding to use [default: UTF-8]?" to reduce confusion with yes/no prompts.

The implementation maintains backward compatibility while improving the validation logic. It builds on a 2015 fix that first addressed this issue with a length check, now adding proper charset verification without introducing new dependencies (using core Perl modules). The patch includes test updates to match the new prompt text.

This is the latest iteration in an ongoing discussion that has involved Ben Knoble, Philip Oakley, and Junio Hamano. The current version focuses on code organization refinements while maintaining the semantic validation approach. Key technical points include the relaxed input validation (now accepting any non-blank string rather than requiring 4+ characters) and the preservation of user control through confirmation prompts when invalid charsets are detected.
