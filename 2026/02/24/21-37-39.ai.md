This is a feature patch improving `git send-email`'s handling of character encoding prompts, part of an ongoing thread about making the interface more robust when dealing with non-ASCII content.

The patch replaces `git send-email`'s current length-based validation of charset names (which could allow invalid encodings through if they were long enough) with proper semantic validation using Perl's `Encode::find_encoding()`. It also clarifies the prompt wording from "Which 8bit encoding should I declare [UTF-8]?" to "Declare which 8bit encoding to use [default: UTF-8]?" to prevent users misinterpreting it as a yes/no question.

Key technical changes include adding charset validation while maintaining backward compatibility, relaxing the input rules from requiring 4+ characters to accepting any non-blank string, and improving the warning/confirmation flow when invalid charsets are entered. The implementation uses core Perl modules to avoid new dependencies and updates the test suite to match the new prompt text.

This is the second iteration of the patch, with v2 adding explicit braces in if-else blocks to match Git's coding style as requested by Junio Hamano. The thread shows active collaboration between first-time contributor Shreyansh Paliwal and reviewers Ben Knoble and Philip Oakley, with Junio providing maintainer guidance on style and implementation boundaries. The changes build on a 2015 fix that first addressed this issue with a length check heuristic.
