This is a technical discussion about commit parsing robustness in Git's object database layer, specifically around handling commit objects that were originally parsed from commit-graphs. The conversation follows up on Patrick Steinhardt's patch series optimizing shallow push performance.

Patrick responds to Justin Tobler's review of the second patch in the series, which addressed edge cases where commit-graph-parsed commits could segfault when accessing tree information. Justin had questioned whether the fix should be in `repo_get_commit_tree()` rather than `repo_parse_commit_no_graph()`.

Patrick explains the complexity of making `repo_get_commit_tree()` more robust - it would need to handle partial clones (where objects might be missing) and avoid invalidating parent pointers. He provides a prototype implementation that fails some partial clone tests, demonstrating the challenges. The key technical points are:

1) The issue stems from commit-graph-parsed commits not having their tree information populated in `maybe_tree`
2) Simply making `repo_get_commit_tree()` fetch missing objects could have unintended consequences
3) The current approach of unparsing and re-parsing commits in `repo_parse_commit_no_graph()` may be the most practical solution despite being somewhat indirect

The discussion highlights subtle tradeoffs in Git's object parsing layer between correctness, performance, and partial clone behavior. Patrick's response shows careful consideration of the edge cases while maintaining the optimization goals of his original series.
