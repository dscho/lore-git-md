This is a security-related discussion thread about hardening Git's repository discovery mechanism, specifically around handling `.git` symlinks and directory validation.

Junio Hamano responds to Karthik Nayak's feedback on Tian Yuchen's v4 patch series, clarifying the error handling logic in `read_gitfile_gently()`. The core issue revolves around properly distinguishing between different types of stat() failures - particularly ENOENT (file not found, which should be non-fatal) versus other stat failures (which should trigger errors).

Junio explains that the current patch's approach of adding exclusions in the caller is backwards from the intended design. The proper fix would be to modify `read_gitfile_error_die()` itself to handle these cases consistently, rather than making the caller filter them. He provides a detailed technical rationale for why ERR_STAT_ENOENT and ERR_IS_A_DIR should be handled as "happy cases" within the error die function, while other errors should properly fail.

This is a refinement of the security hardening work that aims to prevent Git from following potentially dangerous repository paths (like FIFOs or sockets) while still allowing legitimate symlinks. The discussion shows the maintainer ensuring the implementation matches the intended security model with clean error handling boundaries.
