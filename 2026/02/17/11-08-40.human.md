Feature: HTTP 429 rate limit retry support in Git's HTTP client. This third patch in the series implements the core retry logic for handling HTTP 429 (Too Many Requests) responses, completing the feature introduced in the previous patches.

The patch adds three new HTTP configuration options to control retry behavior: `http.maxRetries` (default 0), `http.retryAfter` (default 0 seconds), and `http.maxRetryTime` (300 second ceiling). When a server's 429 response includes a Retry-After header, Git will now respect the requested delay before retrying, falling back to the configured `http.retryAfter` value when no header is present. The implementation supports both delay-seconds (numeric) and HTTP-date (RFC 2822) formats for the Retry-After header.

Key technical aspects include:
- Uses curl's CURLINFO_RETRY_AFTER parsing when available (curl >= 7.66.0)
- Implements manual header parsing for older curl versions
- Adds comprehensive test coverage for various Retry-After scenarios
- Includes trace2 instrumentation for monitoring retry behavior
- Follows RFC 9110 semantics for Retry-After handling

The implementation takes a fail-fast approach when delays exceed `http.maxRetryTime`, providing clear error messages rather than silently capping delays. This appears to be a well-considered feature with thorough test coverage, addressing all major feedback points from previous iterations.
