This is a security-related clarification in the ongoing patch series hardening Git's `.git` directory discovery. Junio Hamano responds to Karthik Nayak's feedback about error handling in `read_gitfile_gently()`, explaining the current patch's approach to distinguishing fatal from non-fatal error cases.

The core issue revolves around how different stat() failures should be classified when validating `.git` entries. Junio clarifies that the patch intentionally splits stat() failures into two distinct categories: `ERR_STAT_ENOENT` (non-fatal, continues repository search) and `ERR_STAT_FAILED` (fatal error). This replaces the previous overly broad handling that treated all stat() failures as non-errors.

Junio argues that the current patch's approach is more logical than moving the exclusions into `read_gitfile_error_die()`, as it properly reflects the semantic difference between "this path doesn't exist" (continue searching) versus "this path exists but is invalid" (fail). He notes that if other callers of `read_gitfile_error_die()` need different semantics, that would require a different solution, but the current patch's approach is consistent with making `.git` validation more precise and secure.

The exchange shows the series is in its final polishing stages, with Junio providing authoritative guidance on the error handling strategy. The security model itself (rejecting dangerous `.git` attachments while allowing valid symlinks) remains uncontested, with discussion now focused on implementation clarity.
