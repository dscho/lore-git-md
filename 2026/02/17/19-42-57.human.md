This is a security discussion about push certificate privacy, specifically addressing whether the "pushee" header in push certificates should be allowed to omit or modify the repository path for privacy reasons.

Junio C Hamano responds to Lorenz Leutgeb's concern about local filesystem paths appearing in push certificates during local-to-local repository pushes. The maintainer raises important security considerations about the purpose of push certificates - they exist to bind a signed update to a specific repository, preventing replay attacks where a signed update could be applied to the wrong repository.

Junio questions whether omitting the pushee header entirely would make sense, as it would imply the update should apply to all clones of a project globally - a potentially dangerous proposition. He's more open to allowing the pushee to specify an alternative repository name when pushing through a middleman, as this maintains the security binding while addressing privacy concerns.

The discussion highlights the tension between privacy (not leaking local paths) and security (preventing certificate misuse). Junio's response suggests the solution may need to preserve the ability to verify which repository an update was intended for, while finding a way to avoid exposing sensitive local paths. This appears to be an ongoing discussion rather than a settled matter.
