This is a bugfix patch addressing an off-by-one error in `strbuf_reencode()`. The function was incorrectly passing the string length (excluding null terminator) as the allocation size to `strbuf_attach()`, when it should have passed length + 1 to account for the terminator. While Junio Hamano notes this doesn't cause memory corruption due to `strbuf_grow()`'s internal behavior, it does trigger unnecessary reallocations.

The patch is straightforward and corrects the allocation size parameter. Junio raises an interesting follow-up question about whether `strbuf_attach()` itself should validate that alloc > len to catch similar issues earlier. This suggests the fix might be part of a larger discussion about strbuf API hardening, though the immediate patch stands on its own merits.

The change is minimal (one line) and well-justified, with Junio's analysis confirming the technical basis while expanding the implications. This appears ready for inclusion, though the broader API discussion about parameter validation may spawn follow-up work.
