HTTP 429 rate limit retry support. This is the third version of Vaidas Pilkauskas's series implementing RFC-compliant handling of HTTP 429 (Too Many Requests) responses with Retry-After headers. The patch set introduces configurable retry behavior when Git encounters rate limiting from HTTP servers.

Key changes in v3:
- Simplified the retry mechanism by replacing a complex non-blocking delay system with a straightforward blocking sleep() call
- Added support for curl's native CURLINFO_RETRY_AFTER parsing (curl >= 7.66.0) with fallback to manual header parsing
- Changed the default http.retryAfter from -1 to 0 to allow immediate retries when no Retry-After header is present
- Improved test portability by replacing GNU date commands with test-tool date
- Added comprehensive trace2 instrumentation for monitoring retry behavior
- Fixed handling of Retry-After: 0 to allow immediate retry per RFC 9110

The implementation provides three new HTTP configuration options:
- http.maxRetries (default 0) - maximum number of retry attempts
- http.retryAfter (default 0) - default wait time when no Retry-After header is present
- http.maxRetryTime (default 300) - maximum allowed delay time in seconds

The series has evolved based on feedback from Jeff King and Taylor Blau, with v3 addressing architectural concerns and improving test reliability. The changes touch http.c, remote-curl.c, and add new test scripts in t/t5584-http-429-retry.sh. The implementation looks well-considered, with thorough test coverage and attention to edge cases like invalid Retry-After formats and configuration validation.
