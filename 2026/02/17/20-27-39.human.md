This is a bugfix discussion thread about path handling in `git apply --directory`. The maintainer Junio C Hamano is questioning whether the proposed comprehensive path normalization solution is necessary, given that the original bug report only concerned `./` prefixes.

The thread started with Joaquim Rocha reporting that `git apply --directory=./some/sub` fails while the same path without `./` works. Patrick Steinhardt suggested using `strbuf_normalize_path()` to handle all path normalization cases (including `./`, `../`, and multiple slashes) rather than just stripping `./` prefixes.

Junio now pushes back, asking why we shouldn't just tell users "don't use `./` prefixes" rather than adding complexity to handle them. This suggests he may prefer the minimal fix over Patrick's more general solution. The discussion is currently at a decision point between these two approaches.

The patch would modify `apply.c` to normalize paths passed to `--directory`, affecting how Git processes relative paths in this context. While the change is small (just 1-4 lines), the implications differ between the minimal fix (only handles `./`) and comprehensive normalization (handles all relative path cases).
