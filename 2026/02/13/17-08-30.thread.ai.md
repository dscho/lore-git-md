Git apply --directory path handling fix

Thread identity: Bugfix for `git apply --directory` option when given paths starting with `./`. Originating author Joaquim Rocha. Thread type: bugfix.

Core problem: When `git apply --directory=./some/sub` is used, the `./` prefix causes the command to fail with an invalid path error, despite this being common notation. The behavior differs from non-prefixed paths.

Current status: Initial patch from Joaquim Rocha proposed stripping `./` prefix specifically. Patrick Steinhardt suggests a more comprehensive solution using path normalization.

Key technical details: Original solution modified path handling in `apply.c` (4 lines) with test in `t4128-apply-root.sh`. Patrick's proposal would use `strbuf_normalize_path()` to handle all path normalization (including `././`, `some/./sub`, and `..` paths) with minimal change (1 line in `apply.c`).

Open questions: Whether to adopt the minimal `./`-only fix or comprehensive path normalization. Patrick's approach appears more robust but needs evaluation of edge cases and performance impact.

Participant positions: Joaquim Rocha proposed initial fix. Patrick Steinhardt suggested alternative using existing path normalization infrastructure. No other participants yet.

Related work: Builds on existing `--directory` option behavior and Git's path handling conventions. `strbuf_normalize_path()` is established infrastructure used elsewhere in Git.
