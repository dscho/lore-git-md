Git apply --directory path handling fix

Thread identity: Bugfix for `git apply --directory` option when given paths starting with `./`. Originating author Joaquim Rocha. Thread type: bugfix.

Core problem: When `git apply --directory=./some/sub` is used, the `./` prefix causes the command to fail with an invalid path error, despite this being common notation. The behavior differs from non-prefixed paths.

Current status: Joaquim Rocha's v2 patch implements Patrick Steinhardt's suggestion to use `strbuf_normalize_path()` for comprehensive path normalization rather than just stripping "./" prefixes. This handles multiple edge cases: "./" prefixes, double slashes, "./" in middle of paths, and "../" traversal (while rejecting leading "../"). The change remains minimal (4 lines in `apply.c`) with extensive test coverage in `t4128-apply-root.sh`.

Key technical details: Implementation now uses established `strbuf_normalize_path()` infrastructure to handle all path normalization cases. Tests verify behavior with: `./` prefixes, `././` sequences, `some/./sub` paths, and `../` traversal attempts. Original `./` case remains the primary motivation, but solution generalizes to other path forms users might pass. Junio Hamano's earlier skepticism about need for comprehensive normalization remains an open question - no new response yet to v2.

Open questions: Whether comprehensive normalization is justified versus targeted `./` fix, given Junio's initial preference for simpler solution. Performance impact of `strbuf_normalize_path()` remains unmeasured. Tests suggest real-world cases exist for broader normalization, but decision hinges on whether these justify the generalization.
