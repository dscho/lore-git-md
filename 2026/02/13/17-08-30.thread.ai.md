Git apply --directory path handling fix

Thread identity: Bugfix for `git apply --directory` option when given paths starting with `./`. Originating author Joaquim Rocha. Thread type: bugfix.

Core problem: When `git apply --directory=./some/sub` is used, the `./` prefix causes the command to fail with an invalid path error, despite this being common notation. The behavior differs from non-prefixed paths.

Current status: Initial patch from Joaquim Rocha proposed stripping `./` prefix specifically. Patrick Steinhardt suggests a more comprehensive solution using path normalization. Junio C Hamano has now weighed in with skepticism about the need for comprehensive normalization.

Key technical details: Original solution modified path handling in `apply.c` (4 lines) with test in `t4128-apply-root.sh`. Patrick's proposal would use `strbuf_normalize_path()` to handle all path normalization (including `././`, `some/./sub`, and `..` paths) with minimal change (1 line in `apply.c`). Junio questions whether this generalization is necessary beyond the specific `./` case.

Open questions: Whether to adopt the minimal `./`-only fix or comprehensive path normalization. Junio's initial reaction suggests preference for simpler solution unless compelling real-world cases for broader normalization are presented. Performance impact of `strbuf_normalize_path()` versus targeted fix remains to be evaluated.

Participant positions: Joaquim Rocha proposed initial fix. Patrick Steinhardt suggested alternative using existing path normalization infrastructure. Junio C Hamano expressed skepticism about need for comprehensive solution, favoring simpler approach.

Related work: Builds on existing `--directory` option behavior and Git's path handling conventions. `strbuf_normalize_path()` is established infrastructure used elsewhere in Git. Junio's position suggests weighing whether this is the right place to apply it.
