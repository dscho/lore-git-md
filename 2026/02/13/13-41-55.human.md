This is part of an ongoing effort to add HTTP 429 (rate limiting) retry support to Git's HTTP client. Vaidas Pilkauskas is responding to Jeff King's review feedback on the second version of the patch series.

The key discussion points in this email revolve around implementation details for handling rate limit responses:
1. Jeff suggests using libcurl's built-in `CURLINFO_RETRY_AFTER` functionality (available since curl 7.66.0) rather than manual parsing, which Vaidas agrees to implement conditionally.
2. There's debate about the best layer for retry logic - Jeff proposes simplifying by focusing on `run_one_slot()` for smart-http, while Vaidas suggests `http_request_recoverable()` might be more appropriate.
3. Jeff points out potential portability issues with date handling in tests and recommends using Git's `test-tool date` instead of system `date` commands.

The exchange shows the patch is making progress but still needs architectural decisions resolved, particularly around where to place the retry logic in the HTTP stack. Jeff's feedback indicates this is non-trivial due to the complexity of Git's HTTP layer, especially around active slot handling. The test improvements suggested would make the feature more robust across platforms.
