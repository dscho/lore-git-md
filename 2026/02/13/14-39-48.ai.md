This is a discussion thread about the parallel hook execution feature, specifically addressing safety considerations and backward compatibility.

Phillip Wood raises two key points in response to Adrian Ratiu's parallel hooks patch series. First, he suggests looking to existing hook managers for prior art on parallelization strategies, noting that some serialize pre-commit hooks by default (since they may modify shared state like the index) while allowing parallel execution for other hooks. Second, he flags a historical regression where pre-commit hooks lost terminal access, asking whether this series might reintroduce that issue.

Adrian confirms the implementation preserves backward compatibility by defaulting to serial execution (jobs=1) which maintains terminal access, while parallel execution (jobs>1) buffers outputs through pipes. He emphasizes this follows Jeff King's original design intent to avoid regressions. The discussion reveals tension between safety (conservative defaults) and flexibility (user control), particularly for hooks modifying shared state.

Technical details of interest for future summarization: the `hook.jobs` config controls parallelism, with jobs=1 preserving the original behavior and jobs>1 enabling parallel execution with piped output. Phillip suggests per-hook parallelization control as a potential future direction, which could help address the pre-push hook's special output handling needs while maintaining safety for other hooks. The thread shows consensus forming around keeping serial execution as the safe default while allowing opt-in parallel behavior.
