Parallel hook execution design discussion. Phillip Wood raises important considerations about maintaining backward compatibility with terminal access for hooks, particularly noting a past regression where pre-commit hooks lost terminal access. He suggests a per-hook opt-in model for parallel execution as a safer approach than blanket parallelism.

Adrian Ratiu confirms the current implementation preserves the original serial behavior by default (jobs=1), which maintains terminal access, while parallel execution (jobs>1) buffers outputs through pipes. This follows Jeff King's original design to avoid regressions. The discussion highlights the tension between performance gains from parallelism and the need to maintain existing behavior for hooks that expect direct terminal access or modify state (like pre-commit hooks that update the index).

The exchange suggests future directions could include per-hook configuration of parallel safety, building on the current infrastructure that already supports job count control via `hook.jobs`. Phillip's feedback reinforces the conservative approach taken in the series, prioritizing stability over aggressive parallelization.
