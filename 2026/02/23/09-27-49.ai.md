This is a technical discussion thread about `git fsck` packfile verification, focusing on deeper architectural issues beyond the immediate infinite loop bugfix that was already queued.

Jeff King (Peff) responds to Patrick Steinhardt's analysis of the root causes behind the `git fsck` MRU list traversal issue. Patrick had identified that the problem only manifests when verifying large objects (exceeding `core.bigFileThreshold`), which triggers a different code path that searches by object ID rather than pack offset, inadvertently updating the MRU list during iteration.

Peff agrees with Patrick's assessment and raises a more fundamental concern: the current design may verify the wrong packfile's copy of an object when duplicates exist, since `find_pack_entry()` could return a different pack than the one being verified. This suggests the verification logic itself may be flawed beyond just the iteration safety issue.

The discussion has evolved from the immediate bug (fixed by adding a `skip_mru_updates` flag) to questioning core assumptions about how pack verification should work. There appears to be consensus that the MRU list design creates architectural fragility, but differing views on whether to prioritize fsck-specific fixes versus broader MRU redesign. The thread remains active with Patrick preparing verification correctness patches while Peff advocates for addressing the underlying iteration safety issues more comprehensively.
