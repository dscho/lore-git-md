This is a technical discussion about error handling in the packfile streaming code, part of Patrick Steinhardt's bugfix series addressing fsck` issues with large objects. The exchange focuses on how to properly handle corrupt objects when reading from packfiles.

Jeff King raises concerns about the interface design of `packfile_read_object_stream()`, noting that adding an OID parameter purely for marking corrupt objects feels misleading since the function doesn't use it for lookup. He suggests alternative approaches using detailed error codes or returning the object type directly, which would let callers decide how to handle corruption.

Patrick acknowledges the interface is "a bit ugly" but argues it's acceptable since the function is unlikely to gain many callers. He prefers keeping the explicit OID parameter for marking corrupt objects rather than Jeff's proposed error code approach, as it centralizes the corruption handling and avoids potential future omissions.

The discussion reveals careful consideration of tradeoffs between interface cleanliness and robust error handling. Both demonstrate deep understanding of the packfile internals, with Jeff advocating for either comprehensive error handling or minimal interface changes rather than partial solutions.
