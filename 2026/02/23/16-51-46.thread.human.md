This thread addresses the problem of zombie processes accumulating in containerized Git environments, particularly after network operations fail. The discussion began with an assumption that Git was running as PID 1 in containers, but it's become clear that in the actual deployment, Git runs as a child process under a long-running service.

Andrew Au's v2 patch proposed adding symmetric atexit handlers in transport-helper.c and connect.c to ensure child process cleanup. However, Jeff King (Peff) raised concerns about potential deadlocks and suggested alternative approaches using existing run-command infrastructure. Junio C Hamano then sought clarification about the actual architecture, questioning whether the service spawning Git should handle cleanup instead.

The latest contribution from brian m. carlson provides important context: running Git as PID 1 is unusual in container deployments, where dedicated init systems like tini typically handle process reaping. They argue this remains the preferred solution, as Git likely has other unhandled cleanup cases beyond the specific network operations being patched. This perspective aligns with Junio's request for architectural clarity and suggests the problem might be better solved at the container orchestration level rather than modifying Git's process management.

The thread now faces key questions about responsibility boundaries: should Git be modified to handle these edge cases, or should the solution come from proper container configuration? While the immediate zombie process issue is real (with 6,500+ observed cases), the discussion has shifted toward understanding whether patching Git is the right approach given the actual deployment context.
