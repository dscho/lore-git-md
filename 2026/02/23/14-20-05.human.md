Feature: HTTP 429 rate limit retry support in Git's HTTP client.

This is the final patch in Vaidas Pilkauskas's series adding HTTP 429 (Too Many Requests) response handling to Git's HTTP client. The implementation supports RFC-compliant Retry-After headers in both delay-seconds (integer) and HTTP-date formats, with three new options to control behavior: http.maxRetries (default 0), http.retryAfter (default 0), and http.maxRetryTime (default 300 seconds). The patch includes comprehensive test coverage through a new test script (t/t5584-http-429-retry.sh) that verifies various scenarios including header parsing, configuration combinations, and edge cases. The implementation takes a fail-fast approach when delays exceed maxRetryTime, providing clear error messages rather than silently capping delays. 

The series has gone through multiple iterations incorporating feedback from Jeff King and Taylor Blau, with this version implementing Taylor's suggestion for consistent error handling. The changes affect remote-curl.c and http.c, adding new configuration options and portable test infrastructure. The implementation is thorough, with attention to both modern curl versions (using CURLINFO_RETRY_AFTER when available) and fallback parsing for older versions. 

This appears to be a well-considered addition that will help Git clients better respect server rate limits, particularly useful for services like GitHub and GitLab that implement API rate limiting. The extensive test coverage and clear documentation suggest this is production-ready code.
