This is a documentation/style compliance patch series for `git cat-file` error messages that has uncovered significant ecosystem compatibility concerns. The thread reveals that several major projects (Gitea, Gogs, GitLab Gitaly, IntelliJ) perform case-sensitive string matching on Git's "Not a valid object name" error message, treating it as an undocumented API.

Junio Hamano weighs in decisively, recommending against changing any messages from plumbing commands like `git cat-file`, even for style compliance. His position is that these messages - especially long-standing ones - have effectively become part of Git's external interface, and changing them risks breaking tools that parse Git's output. He extends this caution to all plumbing commands, suggesting a conservative approach even for human-facing messages in porcelain commands.

The exchange highlights a tension between Git's internal style guidelines and real-world usage patterns where tools parse Git's output. Junio's response effectively closes the discussion by establishing a principle: stability of plumbing output takes precedence over style consistency. This suggests similar future efforts to standardize messages will need to either focus exclusively on porcelain commands or accept that some plumbing messages must remain as-is due to their de facto API status.
