Thread addressing zombie process issue when Git runs as PID 1 in containers during abnormal exits from network operations (git-remote-https, ssh). The core problem occurs when transport errors trigger exit(128) before normal cleanup paths (disconnect_helper, finish_connect) can reap child processes, leaving them as zombies when Git is PID 1.

Andrew Au's v2 patch adds symmetric atexit handlers in transport-helper.c and connect.c to ensure child process reaping regardless of exit path, while preserving existing cleanup behavior for normal exits. The solution introduces:
- connect.c: conn_to_reap tracking variable and cleanup_conn_on_exit handler
- transport-helper.c: helper_to_reap and cleanup_helper_on_exit handler
Handlers are registered when child processes start (git_proxy_connect, git_connect, get_helper) and cleared during normal cleanup paths to avoid double-waiting.

Maintainer Junio C Hamano has raised a practical concern about the real-world impact, questioning whether zombie processes persist long enough to matter given containers typically terminate after their main process exits. This shifts focus from implementation (which appears technically complete) to deployment relevance. The response will need to demonstrate concrete scenarios where lingering zombies affect container orchestration systems or monitoring, such as:
- Container platforms that delay teardown while waiting for process reaping
- Resource tracking systems that monitor process tables
- Debugging scenarios where zombie processes complicate post-mortem analysis

The patch has resolved prior technical questions (author attribution in v2) and awaits justification for its practical necessity. The implementation remains unchanged from v1 - atexit handlers provide reliable cleanup while maintaining normal operation behavior, with changes contained in two files and well-commented.
