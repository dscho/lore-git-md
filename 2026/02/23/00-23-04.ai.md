This is a follow-up discussion to a recently merged bugfix series about `.git` directory validation, now examining whether `ENOTDIR` (path component not a directory) should be treated the same as `ENOENT` (file not found) in submodule validation contexts. The original series improved error classification for `.git` file/directory detection while maintaining security boundaries.

Junio Hamano proposes grouping `ENOTDIR` and `ENOENT` into a single `READ_GITFILE_ERR_STAT_MISSING` error code, particularly for cases where a submodule directory is replaced with a regular file. The patch demonstrates this change but notes uncertainty about whether this is universally appropriate - some callers might need to distinguish these cases. The change affects `setup.c`, `setup.h`, and `submodule.c`, with the key modification being in `read_gitfile_gently()` where the error handling now combines both error conditions.

The discussion continues the pattern of rigorous post-merge examination of edge cases from this security-sensitive area. Junio explicitly leaves this as an unsquashed patch to invite further consideration of whether the behavior change is universally desirable or should be caller-specific. This touches on subtle filesystem semantics that could impact submodule handling and other Git operations that validate repository directories.
