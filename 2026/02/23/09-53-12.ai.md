This is a follow-up in the ongoing fsck packfile verification thread, addressing both the immediate infinite loop bug and deeper architectural issues with pack verification. Patrick Steinhardt confirms the root cause analysis from brian m. carlson's original report - that MRU list updates during `git fsck` pack iteration can cause infinite loops when processing large files (those exceeding core.bigFileThreshold) across multiple packs.

Patrick reveals an important technical detail: the issue only manifests when verifying large objects because the verification path for smaller objects bypasses `find_pack_entry()` (and thus MRU updates) by using direct packfile access. He also identifies a more fundamental correctness problem - when duplicate objects exist in multiple packs, the current verification approach may check the wrong instance of an object.

The email references a new patch series Patrick has sent that addresses these issues. While he agrees with the immediate fix (adding a `skip_mru_updates` flag during his investigation he discovered the verification could be checking objects from the wrong pack entirely when duplicates exist. His patches aim to correct both the iteration safety and verification accuracy problems.

This continues the thread's progression from an immediate bugfix toward more comprehensive pack verification correctness, with Patrick connecting it to his broader object database abstraction work that will eventually eliminate `repo_for_each_pack()`. The discussion remains focused on technical solutions while acknowledging the deeper architectural challenges in Git's pack handling.
