This is a design discussion about the interface for `git replay`, specifically around the proposed `--revert` mode and broader command structure. The thread has evolved from technical implementation details to interface philosophy, with Toon Claes and Christian Couder exploring alternative approaches.

Toon responds to Christian's suggestion about making the base branch a positional argument by explaining the different behaviors between modes: `revert` and `pick` operate on a single ref while `replay` (rebasing) can update multiple refs. He proposes a more radical restructuring into subcommands with distinct parameter patterns:

- `revert` and `pick` would use `--ref=<branch>` to specify the target branch
- `rebase` would use `--onto=<branch>` for its target
- Both options could be used together, allowing operation on bare commit IDs
- The interface would make the different operational modes more explicit while solving the bare commit ID limitation

Christian had earlier agreed with the subcommand direction but suggested deferring the change until after merging the current `--revert` implementation. The discussion reveals tension between:
1. The immediate need to support GitLab's use case
2. The desire for a clean, intuitive interface that properly reflects the semantic differences between operations
3. The practical considerations of changing an interface that already has consensus on its technical implementation

The exchange shows the project's careful balancing of immediate needs versus long-term design, with both contributors seeking a solution that serves GitLab's requirements while establishing sustainable patterns for future `git replay` usage. The technical capability to handle bare commit IDs emerges as an additional constraint that the proposed subcommand approach could address more cleanly than the current flag-based design.
