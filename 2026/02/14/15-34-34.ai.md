This is a discussion about the worktree API refactoring effort, specifically addressing the distinction between NULL worktree parameters and explicit primary worktree representation.

Junio C Hamano responds to Phillip Wood's clarification about the historical meaning of NULL worktree parameters in the API. The key points are:

1. The discussion reveals that `wt==NULL` traditionally meant "use current worktree" (resolved to repo->gitdir) while `wt->id==NULL` meant "main worktree" (resolved to repo->commondir), contrary to previous assumptions.

2. Junio strongly endorses Phillip's suggestion to introduce `get_current_worktree()` as a way to gradually clean up NULL usage while maintaining backward compatibility.

3. Concerns are raised about the current implementation's use of `wt->is_current` bit, which requires iterating through a list to find the current worktree. Junio suggests comparing gitdir and commondir might be a more robust approach.

4. The discussion highlights potential issues with the worktree list management, questioning what happens when no worktree or multiple worktrees are marked as current, and whether callers handle these cases properly.

5. Junio agrees that converting from NULL parameters to explicit worktree handling can be done incrementally, with the wt->id==NULL to wt->id=="/" conversion being a separate change.

The email shows the project maintainer validating a significant clarification about API semantics while supporting a measured approach to refactoring. It also surfaces deeper architectural questions about worktree identification that may need addressing in future iterations of the patch series.
