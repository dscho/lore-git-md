This is a discussion about the ongoing security vulnerability in `git am` where it can incorrectly apply diffs embedded in commit messages. The thread explores the interaction between Git's patch parsing and the broader Unix toolchain, particularly `patch(1)`.

Kristoffer Haugsbakk responds to Jakob Haufe's clarification about how `patch(1)` handles indented diffs, acknowledging that his previous assumptions about `git am`'s behavior were incorrect. The key realization is that both `git am` and `patch(1)` will apply all diffs they find, including those in commit messages, unless specific formatting conventions are followed. 

The discussion highlights the complexity of the issue - even if Git were fixed to handle this case, the problem would remain for users piping Git output to `patch(1)`. Haugsbakk notes that while he doesn't typically use `patch(1)` with Git output, he has relied on it for processing email-embedded diffs due to its more forgiving nature compared to `git apply`.

This exchange underscores the tension between security, backward compatibility, and usability in Unix toolchain integration. The thread shows growing recognition that any solution needs to consider both Git's behavior and how it interacts with other tools in the ecosystem.
