This is a discussion about the ongoing security vulnerability in `git am`'s patch parsing, specifically around how it handles diffs embedded in commit messages. Kristoffer Haugsbakk is responding to Jakob Haufe's clarification about how `patch(1)` handles indented diffs, showing that the problem extends beyond just Git's tooling.

The key insight is that both `git am` and Unix's `patch(1)` will apply all diffs they find in a message, even those meant as examples in commit messages, if they're not properly distinguished. Haugsbakk acknowledges their previous assumptions were incorrect - they thought avoiding certain magic strings (`From`, `---`) would prevent misapplication, but the issue is more complex due to how tools strip indentation before parsing.

The discussion reveals this is a systemic issue affecting multiple tools in the Unix ecosystem, not just Git. While Git could potentially be modified to handle indented diffs differently, any solution would need to consider backward compatibility and the broader context of how other tools like `patch(1)` behave. The thread highlights how security vulnerabilities can emerge from the interaction between tools' parsing behaviors and common practices around embedding example diffs in commit messages.
