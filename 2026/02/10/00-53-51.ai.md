This is a security discussion follow-up regarding the `git am` patch parsing vulnerability. Christoph Anton Mitterer raises concerns that while the documentation patch (now queued by Junio) warns about the issue, it doesn't actually fix the underlying security problem where `git am` can misinterpret diffs embedded in commit messages as actual patches to apply.

The core issue stems from ambiguity in distinguishing between intended patches (after the "---" separator) and accidental diffs in commit messages, particularly affecting distribution workflows that apply patches in bulk. The thread has previously established this as a long-standing security risk affecting both Git and Unix `patch(1)`.

Mitterer's email serves as a reminder that documentation alone may not sufficiently address the security implications, suggesting the community should prioritize a technical solution. This comes after multiple proposed approaches have been discussed in the thread: Phillip Wood's security-focused commit-msg hook (now reconsidering "---" detection), Patrick Steinhardt's proposed `--accept-ambiguous-patch` flag, and various parser improvements.

The comment reflects ongoing tension between maintaining backward compatibility (particularly for workflows that legitimately use separator lines) and implementing security hardening. While the documentation warnings represent progress, this email highlights that some contributors view them as insufficient without accompanying code changes to prevent the vulnerability.
