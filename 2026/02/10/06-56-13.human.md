This is a security-focused discussion about `git am`'s patch parsing behavior, continuing the thread about vulnerabilities in applying patches that contain ambiguous diff content. Jeff King (Peff) responds to Patrick Steinhardt's proposal for `git am` to detect and warn about ambiguous patches.

Peff agrees that detecting ambiguous cases is possible but highlights several real-world scenarios that would generate false positives, making the heuristics tricky to implement without being overly noisy. He describes legitimate uses of multiple "---" separators in commit messages and cover letters, as well as cases where diff headers appear before the separator line. These patterns, while valid, would trigger warnings under Steinhardt's proposed detection scheme.

The discussion focuses on balancing security against usability, with Peff suggesting that any warning system would need careful tuning to avoid annoying users with too many false positives. He notes that the "--accept-ambiguous-patch" escape hatch could mitigate this, but only if the warnings don't fire too frequently in normal workflows.

This exchange shows the tension between hardening `git am` against malicious or accidental patch misinterpretation while maintaining compatibility with existing patch formats and common usage patterns. Peff's perspective as a long-time contributor brings practical experience about how these changes would affect real-world workflows.
