This is a discussion about improving `git am`'s handling of ambiguous patch/commit message boundaries, following up on a security vulnerability where diffs in commit messages could be accidentally applied.

Patrick Steinhardt responds to Jacob Keller's suggestion of introducing an "unambiguous mode" for patch generation and application. The key points are:

1. The core challenge remains reliably distinguishing between intended patches (after "---") and embedded diffs in commit messages when processing email streams, which affects distribution workflows.

2. Steinhardt considers whether an unambiguous mode could be introduced in a backwards-compatible way that old Git clients and `patch(1)` would still understand, even if they misinterpret ambiguous parts. This could potentially make the mode defaultable without breaking changes.

3. He acknowledges this is speculative and raises the open question of whether such a backwards-compatible unambiguous mode is technically feasible.

4. Both agree that even with an unambiguous mode, malicious users could still edit patches, but it would prevent accidental cases where diffs are unintentionally included in commit messages.

The discussion builds on prior analysis from Jeff King (Peff) about the fundamental ambiguity in parsing single-stream patch output and the legitimate cases where "---" appears in patches or cover letters. This represents ongoing work to harden `git am` against security risks while balancing backwards compatibility concerns.
