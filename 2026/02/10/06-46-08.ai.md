Security-focused discussion on `git am` patch parsing hazards.

This is a security-related follow-up discussing the ongoing effort to harden `git am` against malicious or accidentally confusing patch content. Jeff King (Peff) responds to Phillip Wood's concerns about the scope of proposed protections, agreeing that while email workflows are less common today, the risk extends to patches downloaded from GitHub and applied with either `git am` or `patch(1)`. 

Peff notes that focusing specifically on `git am`'s behavior is a reasonable boundary, acknowledging that this leaves `patch(1)` users vulnerable to the same class of issues. The discussion reflects the tension between comprehensive security and practical implementation constraints, with Peff suggesting the project must "draw the line somewhere" in terms of what attack vectors it can realistically address.

The exchange occurs in the context of a layered security approach that includes documentation warnings, sample hook improvements, and proposed new flags for `git am`. Peff's input reinforces that while the sample hook can take an opinionated stance (as users can modify it), any solution must account for real-world workflows where separator lines like "---" have legitimate uses, even if rare. This thread continues the project's long-standing effort to balance security hardening against backward compatibility in patch processing.
