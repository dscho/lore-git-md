This RFC thread explores Derrick Stolee's proposed performance optimizations for `git config list --type=<X>`, addressing a bottleneck encountered by git-credential-manager. The five-patch series aims to enable type filtering during initial config parsing rather than after full parsing, with patches 1-4 laying infrastructure groundwork and patch 5 implementing the actual filtering.

The discussion has reached a philosophical crossroads regarding how to handle config values that don't match the requested type. Stolee advocates for silently omitting non-matching values (matching `git config get`'s behavior), while Junio Hamano questions whether this aligns with Git's string-based config model where values have no inherent types. Stolee clarifies that the type parameter represents the caller's expectation rather than an inherent property, arguing against type auto-detection.

On implementation specifics, Stolee has already agreed to Junio's code review suggestions, including renaming a parameter from `die_on_parse` to `gently` and refactoring conditionals into type-specific helper functions. However, these mechanical improvements await resolution of the higher-level design question about whether and how type filtering should work in the `config list` context. The thread remains active with this core conceptual discussion, which will determine the direction of the next version of the series.
