Performance improvement to `git config list --type=<X>` filtering, part of an ongoing RFC series by Derrick Stolee. This email focuses on the core design question around how type filtering should behave when config values don't match the requested type.

The thread has established that config values don't have inherent types - they're just strings that callers may interpret as specific types. Stolee proposes two possible behaviors when filtering: (1) silently skip values that fail to parse as the requested type (current approach), or (2) show all values but let callers handle type mismatches. He argues for option 1 since it matches `git config get --type`'s behavior and gives callers clean results.

Junio C Hamano (the maintainer) had raised concerns about this approach, noting that config system is fundamentally string-based. Stolee's response clarifies that the filtering is meant as a convenience for callers who know what type they want, not as a type assertion about the config itself. The discussion remains open-ended, with Stolee inviting alternative perspectives before proceeding with implementation.

This is patch 3/5 in a series addressing a real-world performance bottleneck in git-credential-manager. The technical groundwork (patches 1-4) has largely been agreed upon, but this design question about type semantics needs resolution before finalizing the user-facing behavior in patch 5. The exchange is constructive, with both participants clearly articulating their perspectives on this subtle interface design question.
