This is a security-focused discussion about `git am`'s patch parsing behavior, building on an ongoing thread about vulnerabilities when applying patches that contain embedded diffs in commit messages. Jacob Keller responds to Patrick Steinhardt's proposal for handling ambiguous patches.

The core issue is that `git am` currently cannot reliably distinguish between intended patch content (after the "---" separator) and accidental diffs embedded in commit message text. This creates security risks where malicious or malformed patches could execute unintended changes. Jeff King (Peff) previously noted this is a long-standing issue with multiple prior discussions (2015, 2022, 2024).

Keller suggests a more radical approach - introducing a breaking change to create an "unambiguous mode" that would fundamentally change how `git format-patch` and `git am` distinguish between commit messages and patch content. While acknowledging this would require coordination between both tools, he notes it could prevent accidental cases even if determined attackers could still bypass it.

The thread shows the project grappling with balancing security against backward compatibility, with multiple proposals on the table:
- Steinhardt's `--accept-ambiguous-patch` flag (force manual review)
- Documentation warnings (already queued)
- Keller's more fundamental "unambiguous mode" redesign
- Improved parser detection of extra separators

This remains an active discussion with no clear resolution yet, but the security implications make it likely some solution will be adopted. The thread reflects Git's challenge in hardening long-standing email-based workflows against modern security concerns.
