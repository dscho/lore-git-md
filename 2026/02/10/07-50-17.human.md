Bugfix discussion regarding `git fetch --dry-run` behavior with shallow clones.

Jeff King (Peff) responds to Tyler Breisacher's report that `git fetch --dry-run --depth=1` creates a `.git/shallow` file in non-shallow clones, contrary to the expectation that dry-run operations should be read-only. Peff explains this is somewhat intentional - while `--dry-run` avoids updating refs, it still performs object transfers and needs to mark shallow objects to prevent them from being seen as corrupted. 

He references a prior discussion about whether a truly read-only dry-run fetch would be useful, but suggests the immediate fix would be to clarify this behavior in the documentation. The issue touches core fetch functionality and the semantics of dry-run operations, though it appears the current behavior is working as designed rather than being an outright bug.

This is a nuanced case where the behavior may surprise users but follows from technical constraints in how shallow clones work. The thread seems headed toward a documentation update rather than a code change.
