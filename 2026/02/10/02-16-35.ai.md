This is a security-focused discussion about `git am`'s patch parsing behavior, continuing from earlier reports of vulnerabilities where commit message diffs could be accidentally applied as patches. Jacob Keller responds to Patrick Steinhardt's proposal for handling ambiguous patches.

The thread has established that `git am` currently cannot reliably distinguish between intended patches (after "---") and embedded diffs in commit messages, creating security risks particularly for distribution workflows. Patrick suggested adding an `--accept-ambiguous-patch` flag to force manual review when ambiguity is detected.

Jacob expands on this by proposing a more fundamental solution - introducing an "unambiguous mode" that would require breaking changes to both `git format-patch` and `git am` to properly distinguish commit messages from patch data. He acknowledges this would still be vulnerable to malicious edits but would prevent accidental cases. He also questions how the receiver could reliably detect ambiguity given that multiple diff hunks are valid in patches.

The discussion highlights the tension between security hardening and backward compatibility, with Jacob leaning toward accepting some breaking changes to improve safety. This follows earlier documentation improvements (queued by Junio) and Phillip Wood's security-focused hook enhancements, showing the community is pursuing multiple approaches to mitigate the issue.
