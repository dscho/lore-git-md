This is a feature proposal for `git send-email`'s handling of non-ASCII character encoding in email subject lines. The thread began with Shreyansh Paliwal reporting confusion around the interactive prompt that appears when 8-bit content is detected, where users might misinterpret "[UTF-8]" as a yes/no question rather than a default value.

In this follow-up, Shreyansh responds to Ben Knoble's suggestion to clarify the prompt by changing "[UTF-8]" to "[default: UTF-8]". The attached patch implements exactly that minimal change to `git-send-email.perl`. Shreyansh also raises the question of whether additional improvements might be warranted, such as warning on invalid charset inputs or falling back to UTF-8 when invalid input is provided.

The change is straightforward and addresses a clear usability issue where users might accidentally enter "y" (thinking they're confirming the default) which then gets incorrectly used as the charset name, producing malformed email headers. The patch follows Git's established pattern for indicating default values in prompts, though the thread notes this convention isn't universally applied across Git's CLI.

This appears to be Shreyansh's first contribution to Git, building on Ben Knoble's suggestion in the thread. The patch is small and focused, touching only the prompt text while leaving open the possibility of more substantial follow-up changes if the discussion identifies further improvements needed in the encoding handling logic.
