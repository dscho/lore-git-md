This thread began as a bug report about `git fsck` entering an infinite loop when verifying packfiles, but has evolved into a deeper discussion about fundamental design issues in Git's packfile handling. The immediate issue - where the Most Recently Used (MRU) list could be modified during iteration - was fixed with a `skip_mru_updates` flag in v1 of the patch, which Junio has already approved for merging.

Jeff King (Peff) raised serious concerns about the underlying architecture, pointing out that the MRU list design is fundamentally fragile and that `git fsck` might actually be verifying the wrong copies of objects when duplicates exist across packs. Patrick Steinhardt has been investigating these issues and preparing follow-up patches to address verification correctness.

In the latest exchange, Patrick acknowledges the architectural problems while proposing two potential solutions: either reverting to a separate iteration list (as existed before the MRU changes) or extending the `repo_for_each_pack()` interface to handle MRU updates safely. He connects this to his ongoing work on object database abstraction, where eliminating `repo_for_each_pack()` entirely would naturally solve the iteration safety issues by containing them within backend implementations.

The immediate fix is on track for merging, but the discussion has revealed deeper questions about how Git should handle packfile verification and MRU list management. Both Peff and Patrick agree the current design needs improvement, though they differ slightly on the best path forward. Patrick's vision ties into his broader refactoring of Git's object storage layer, suggesting this may become part of that larger effort rather than being addressed as an isolated fix.
