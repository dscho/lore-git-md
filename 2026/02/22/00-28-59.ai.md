Feature patch introducing parallel hook execution as part of Adrian Ratiu's configurable hooks series (v2 5/10). This patch removes the hardcoded serial execution of hooks, making parallel execution opt-in via `hook.<name>.parallel` markers and controlled by the `hook.jobs` config introduced in the previous patch.

The core change replaces the fixed `jobs=1` in `run_process_parallel()` with dynamic job count calculation through `get_hook_jobs()`. This function implements a precedence chain: explicit `options->jobs` overrides, then `hook.jobs` config (defaulting to 1), with validation that all hooks for the event are marked parallel-safe. The patch adds a `parallel` flag to the hook config cache and `struct hook`, populated from `hook.<name>.parallel` settings.

New test helpers in t/t1800-hook.sh verify the behavior through sentinel` files that track execution timing. Tests confirm that parallel execution only occurs when both `hook.jobs>1` and all relevant hooks have `parallel=true`. The default remains serial execution for safety, as Git cannot know if arbitrary hook scripts have race conditions.

Key technical details include the new `RUN_HOOKS_OPT_INIT_FORCE_SERIAL` macro for hooks that must never parallelize, and output stream handling that currently restricts parallel hooks to merged stdout/stderr (though a future extension is planned). The implementation builds on the hook config cache from patch 3/10 and unsigned int config parsing from patch 2/10.

This represents the first functional parallel execution capability in the series, though still gated behind explicit opt-in markers that will be added for specific hooks in subsequent patches. The design addresses v1 feedback by making parallel execution strictly opt-in and maintaining backward compatibility with existing hook behavior.
