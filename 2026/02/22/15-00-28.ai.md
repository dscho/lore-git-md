This is a follow-up in the thread about improving `git send-email`'s handling of non-ASCII characters in subject lines. D. Ben Knoble provides technical feedback on Shreyansh Paliwal's proposed changes to add charset validation.

The key points are:
1. The patch changes the validation from requiring 4+ characters (original) to accepting any non-blank input (new), which may weaken the protection against short invalid inputs like "y".
2. It removes the `confirm_only` flag and implements custom confirmation logic, which Knoble suggests might benefit from refactoring to stay closer to the original code structure.
3. The validation uses Perl's `Encode::find_encoding()` to check charset validity, adding a warning for invalid names while still allowing override via confirmation.

Knoble's review focuses on implementation details rather than the overall approach, noting the historical context (the 4-character check was added in 2015 for this same issue) and suggesting potential code organization improvements. The feedback maintains the thread's technical focus on balancing usability improvements with robust input validation in the email-sending workflow.
