This is a technical refinement to Git's Linux fsmonitor daemon implementation, part of the ongoing effort to bring filesystem monitoring support to Linux (matching existing Windows and macOS capabilities). The patch addresses a specific edge case where the daemon could hang indefinitely waiting for filesystem events on certain container/overlay filesystems.

The change replaces an infinite wait in the cookie synchronization mechanism with a one-second timeout using `pthread_cond_timedwait()`. When the timeout triggers, the daemon will now gracefully fall back to a full scan rather than blocking forever. This makes the behavior more robust in environments where inotify watches succeed but events aren't reliably delivered.

Junio Hamano raises a thoughtful question about whether the one-second timeout might be too aggressive, potentially causing unnecessary full scans on working systems. He suggests this might benefit from being configurable or auto-detected, though acknowledges the latter may be complex. The patch author Paul Tarjan doesn't address this in the current version - this seems like the sort of follow-up discussion that might happen on-list.

This is patch 4/10 in the sixth iteration of the Linux fsmonitor series, which has undergone extensive review and testing. The implementation appears solid, with clear error handling and trace logging added for the timeout case. The change is focused and well-contained, touching only the daemon's cookie wait logic while maintaining all other behavior.
