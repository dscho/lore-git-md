This is a technical refinement to Git's filesystem monitoring (fsmonitor) daemon, specifically the cookie wait mechanism used for synchronization between threads. The patch addresses a potential hang scenario where inotify events might not be delivered on certain container/overlay filesystems, even though watch registration succeeds.

The change replaces an infinite `pthread_cond_wait()` with a one-second timeout using `pthread_cond_timedwait()`. If the timeout fires before the expected event arrives, the daemon will report an error and allow the client to proceed with a full scan rather than blocking indefinitely. The implementation includes proper time calculation using `gettimeofday()` and handles the `ETIMEDOUT` case explicitly.

Junio Hamano raises a thoughtful question about whether the one-second timeout might be too aggressive, potentially causing unnecessary polling on systems where inotify works correctly. He suggests this might warrant being configurable or auto-detected, though acknowledges the latter may be difficult. The patch currently hardcodes the timeout as part of the initial implementation.

This change is part of the larger Linux fsmonitor support effort (v6 patch 4/10) and follows from Paul Tarjan's earlier work on Windows pthread compatibility. The technical approach appears sound, though Junio's comment suggests there may be room for refinement in the timeout handling strategy before final merge.
