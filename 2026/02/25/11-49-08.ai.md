This is a reply in an ongoing discussion about a proposed GSoC project to improve disk space recovery in partial clones. Derrick Stolee responds to Amisha Chhajed's application proposal, offering guidance on technical direction and considerations.

Stolee suggests focusing on cleaning up *old* blobs that were needed for previous checkouts but are unlikely to be needed again, rather than just files outside the current sparse-checkout cone. He cautions about potential unintended consequences, noting that some tools (like VS Code's background `git blame`) may automatically repopulate deleted objects, leading to increased network usage. The reply emphasizes the need to carefully consider the tradeoffs between disk space savings and potential performance impacts.

The response builds on the thread's established context about partial clones and sparse-checkout modes, but shifts the focus from spatial considerations (cone vs non-cone) to temporal ones (old vs new objects). Stolee's feedback suggests the project should integrate with existing `git gc`/`git maintenance` infrastructure for object lifecycle management rather than creating new cleanup mechanisms. This positions the work as an extension of Git's existing object storage management rather than a sparse-checkout-specific feature.
