This thread documents and fixes an inconsistency in how `git merge-file` handles the `merge.conflictStyle` configuration. The command previously respected this setting only in repository contexts while accepting command-line flags everywhere, a behavior that had gone undocumented since its 2008 introduction. Yannik Tausch identified the issue and drove the solution through multiple iterations, initially documenting the behavior before implementing a fix that makes the configuration work uniformly in all contexts.

The technical solution settled on using Git's existing `repo_config()` infrastructure to handle both repository and non-repository cases consistently, maintaining the same precedence order (command-line flags override repository config which overrides global config). Junio C Hamano provided the key insight to reuse this existing machinery rather than introducing new code paths. Kristoffer Haugsbakk contributed documentation polish and test style suggestions. The change is now complete with proper documentation and a new test case in `t6407-merge-binary.sh` verifying the behavior outside repositories.

In the latest email, Junio shifted from technical review to process guidance, explaining how to properly format patch submissions in reply emails. While the technical discussion appears resolved, this maintainer feedback ensures future contributions from Yannik and others will follow Git's mailing list conventions - particularly around keeping patches as separate messages rather than embedding them in replies unless absolutely necessary. The thread demonstrates both Git's technical evolution (improving configuration handling) and its social norms (maintainer guidance on contribution practices).
