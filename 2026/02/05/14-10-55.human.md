This is an RFC discussion about optimizing Git config access patterns, particularly for credential managers on Windows where process startup overhead dominates performance. Derrick Stolee responds to Junio C Hamano's initial feedback on the proposed `git config-batch` command.

The conversation explores deeper design questions around config synchronization and process models. Junio suggests considering a long-running config server (similar to fsmonitor) rather than per-client batch processes, which would avoid process startup costs entirely but introduces complexity around config freshness monitoring. Stolee acknowledges the merit but notes the challenges of tracking all config file dependencies (including `includeIf` conditions) that would require proactive refreshing.

The discussion also covers write semantics - whether modifications should be immediately visible to other processes, and if automatic file watching could replace explicit reload commands. Stolee confirms the current implementation handles concurrent writes safely via lockfiles but agrees automatic refresh merits consideration.

The thread is evolving toward evaluating whether simpler solutions (like brian m. carlson's suggestion of `git config -l -z` for reads) could address the immediate performance needs without introducing a new protocol. Stolee indicates he'll explore that path while continuing to consider the more comprehensive server-based approach for future iterations. The exchange highlights the tension between solving the immediate credential-manager bottleneck and designing a general-purpose config access solution.
