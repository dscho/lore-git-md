This is a follow-up discussion in the RFC thread about reorganizing Git's experimental Rust infrastructure, specifically addressing project layout conventions and build system interactions.

Mike Hommey responds to brian m. carlson's suggestion about maintaining standard project layout conventions when moving Rust files to a dedicated `rust/` directory. He questions whether tools actually require the conventional `src/` subdirectory structure, citing Servo as an example of projects that deviate from this pattern. The exchange reveals differing perspectives on how strictly Git should adhere to Rust community norms versus optimizing for its multi-language context.

The thread also surfaces the concrete problem affecting git-cinnabar (Mike's Mercurial-Git bridge project), where Cargo's package behavior skips directories containing `Cargo.toml` files, breaking builds when Git is included as a submodule. While brian suggests modifying Cargo itself as an alternative solution, Mike notes this would go against Cargo's documented design decisions around package exclusion rules.

Key technical points still open:
- Whether to adopt `rust/gitcore/src/` structure versus simpler `rust/` layout
- The feasibility of upstream Cargo changes versus Git-side reorganization
- Long-term implications for Git's Rust integration path

The discussion remains constructive but shows no immediate convergence - Mike maintains his position while acknowledging brian's layout preferences, and neither party has yet addressed the other's core concerns about tool compatibility versus project structure clarity. The git-cinnabar use case remains a concrete motivation that may need resolution regardless of the directory structure debate.
