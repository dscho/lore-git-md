This is a bug discussion thread about `git pull` behavior with rebase configuration, originating from Mark Kharitonov's report against Git 2.51.1.windows.1. The core issue was initially thought to be incorrect rebase initiation during `git pull` when the local branch (`feature/dotnetupgrade`) was 875 commits ahead of upstream with no new upstream changes. Phillip Wood clarified this is actually correct behavior - the rebase occurs because the local commits aren't on top of previously merged upstream changes, regardless of whether new upstream changes exist.

Key technical details include:
- Windows context (paths, credential manager, LFS hooks) though the behavior is platform-independent
- Rebase configuration (`rebase.forkPoint` is false)
- The rebase command `git rebase --autostash --onto <same-sha> <same-sha>`
- Branch topology where local commits exist alongside merged upstream changes

Phillip's response indicates this is working as designed, not a bug. The thread has shifted from bug report to behavior discussion, with potential follow-up on whether this behavior is intuitive or could be improved. The original Windows-specific suspicion has been resolved as the behavior is fundamental to Git's rebase logic. No other participants have joined yet beyond the original reporter and Phillip Wood.
