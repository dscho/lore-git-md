This is a technical review response in the ongoing `git replay --revert` feature discussion. Phillip Wood raises several implementation concerns about Siddharth Asthana's v3 patch series that adds revert capability to `git replay`.

Key points addressed:
1. **Documentation regression** - Notes the loss of an important NOTE in the man page from v2 that suggested using `git merge-tree` for bulk reverts of merge requests rather than commit-by-commit reversal.

2. **Revert order** - Suggests reverting commits in creation order (not reverse order) to reduce conflict likelihood, implying the current implementation may increase unnecessary conflicts.

3. **Example improvement** - Proposes a more realistic example showing reverting commits from a topic branch onto main, rather than the simpler same-branch case shown.

4. **Error message hack** - Criticizes the string manipulation approach for error messages (skipping "--" prefix) as problematic for translation, suggesting a cleaner alternative.

5. **Empty commit handling** - Questions why empty revert commits would be preserved (only dropping empty picks), seeing no advantage to this behavior.

The review focuses on implementation polish rather than fundamental design, indicating the core approach has consensus. Phillip's comments target documentation completeness, user experience edge cases, and code quality - typical areas for late-stage refinement in a feature's development cycle. His engagement suggests this is nearing readiness for merging pending these final tweaks.
