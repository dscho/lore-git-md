This is a bugfix patch for Git's fsmonitor daemon, addressing a memory leak in the client handling code. The patch is part of the larger fsmonitor Linux support effort (v7 series) that was already summarized in the thread context.

The specific issue fixed here involves a khash table (`shown`) that tracks duplicate filesystem events. The table was only being freed in the non-trivial response path, leaking memory when clients received trivial responses. Paul Tarjan's fix:
- Initializes the hash table pointer to NULL upfront
- Moves cleanup to a shared `cleanup` label using `kh_destroy_str()` which safely handles NULL
- Ensures the hash table is freed regardless of which code path executes

The change is small (5 lines modified) but important for correct memory management in the long-running daemon. This appears to be a straightforward fix addressing an oversight in the original implementation, with no visible controversy or complexity beyond the described leak. The patch follows the series' pattern of tightening up resource management in the fsmonitor code.
