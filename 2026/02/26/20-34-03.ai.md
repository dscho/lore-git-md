This is a small refactoring patch in the context of Taylor Blau's larger RFC series on incremental MIDX/bitmap-based repacking. The patch introduces a new `strvec_init_alloc()` function that allows pre-allocating space in a string vector when the caller knows how many elements will be needed upfront.

The change is straightforward - it adds a variant of `strvec_init()` that takes an allocation size parameter and pre-allocates that many slots (plus one for the NULL terminator). Junio notes in his reply that while it would be nice to make `strvec_init()` a thin wrapper around this new function, that's not possible due to an existing optimization where empty strvecs avoid allocation entirely.

This appears to be a clean, focused addition to the strvec API that will be used by Taylor's subsequent patches. The change is small (just 12 lines added across two files) and maintains all existing behavior while adding the new capability. Junio's comment suggests he's generally satisfied with the approach, though he notes the minor inconsistency in initialization patterns.

The patch is part of the infrastructure work needed for Taylor's geometric repacking series, though it stands alone as a general utility improvement. It follows Git's typical style for such utility functions and doesn't appear controversial.
