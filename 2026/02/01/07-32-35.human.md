Bugfix for `git blame` color highlighting when ignoring revisions.

Seth McDonald reports a bug where `git blame --color-lines` fails to properly highlight consecutive lines when used with `--ignore-rev`. The coloring feature (which marks lines cyan when they share blame with the previous line) works correctly without `--ignore-rev`, but when ignoring a revision, it continues to use the original commit assignments for coloring rather than the post-ignored ones.

The report includes a clear reproduction recipe showing how consecutive lines that should be colored (because they now share blame after ignoring a revision) remain uncolored. This affects both the current stable release (2.47.3) and the latest release candidate (2.53.0.rc2). The bug appears to be in the interaction between the coloring logic and revision ignoring - the coloring check isn't accounting for the ignored revision's effect on line attribution.

This is a well-documented bug report with a minimal test case and full environment details. The issue affects a visible user-facing feature but doesn't appear to cause any data corruption or incorrect blame attribution - it's purely a display issue with the coloring logic. The fix would likely involve updating the color calculation to use the post-ignored commit assignments rather than the original ones.
