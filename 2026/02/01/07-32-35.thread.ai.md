Git thread summary:

Subject: git blame --color-lines with --ignore-rev shows incorrect coloring
Author: Seth McDonald
Type: bug report
Status: fixed by René Scharfe, confirmed working by original reporter and acknowledged by Junio C Hamano
Key details: When both --color-lines and --ignore-rev are used together, the coloring of consecutive lines with the same blame (after ignoring a specified revision) incorrectly followed pre-ignored revision history. René Scharfe's patch fixes this by modifying the coloring logic in builtin/blame.c to properly check the previous line's commit when determining repeated-line coloring.

Fix implementation: The solution adds specific handling for the --ignore-rev case while maintaining existing behavior. René explains the technical rationale for not using the existing blame_coalesce() function - ignored entries must remain distinct for blame.markignoredlines to work correctly. This reveals an architectural distinction between merge traversal cases and explicit revision ignoring in the blame machinery.

Junio C Hamano notes this might be addressing a specific case rather than a more general pattern in the blame machinery, suggesting potential future refactoring opportunities for similar situations that occur during merge traversal. However, he confirms the current patch is correct and thanks René for including a test case.

Technical impact: Ensures consistent coloring between cases where --ignore-rev is and isn't used, with consecutive lines from the same commit (after ignoring) now properly colored cyan. The change is minimal and doesn't affect other blame functionality.

Testing: The new test case in t/t8012-blame-colors.sh creates a commit changing whitespace (tabs to spaces) and verifies proper coloring with these options. Seth McDonald confirmed the fix works across Git versions 2.47.3 and 2.53.0.rc2. The thread is fully resolved with maintainer approval and no outstanding issues, though the discussion surfaces implementation insights about the blame subsystem's design.
