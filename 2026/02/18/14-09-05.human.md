This is the second patch in a 5-part series fixing strbuf reencoding issues, following up on the initial off-by-one allocation bug fix in strbuf_reencode().

The patch updates all callers of strbuf_attach() to properly account for NUL termination when passing buffer sizes. The function requires the allocation size to be at least len+1 bytes, but several call sites were incorrectly passing len. The changes fall into two patterns:

1. For buffers that are already NUL-terminated strings (or come from strbuf_detach), the patch updates the alloc parameter to be len+1. This affects mailinfo, am, fast-import, refs/files-backend, and trailer.

2. For cases where the buffer isn't NUL-terminated (specifically ll_merge results in rerere and apply), the patch switches to using strbuf_add() which properly handles allocation, followed by freeing the original buffer.

The changes are mechanical but important for correctness, touching several key subsystems that handle string manipulation. The patch appears well-scoped and the commit message clearly explains the rationale for each type of change. This continues the series' focus on proper memory management in string handling code.
