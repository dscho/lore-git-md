This is a feature patch series adding HTTP 429 rate limit retry support to Git's HTTP transport, along with related strbuf fixes. The series has evolved through four iterations with input from multiple reviewers.

The core feature (patch 5) implements HTTP 429 "Too Many Requests" response handling with Retry-After header support. When Git receives a 429 response, it will now:
- Parse Retry-After headers (both delay-seconds and HTTP-date formats)
- Respect configurable limits (http.maxRetries, http.retryAfter, http.maxRetryTime)
- Fall back to immediate retry when no Retry-After is provided
- Log retry attempts via trace2
- Fail clearly when retry delays exceed maxRetryTime

The series includes preparatory work to fix strbuf memory management:
- Patch 1 fixes strbuf_reencode() to properly account for the null terminator
- Patch 2 audits all strbuf_attach() callers to ensure correct alloc sizes
- Patch 3 hardens strbuf_attach() with a BUG() check for invalid alloc values
- Patch 4 introduces a show_http_message_fatal() helper to reduce code duplication

The implementation includes comprehensive tests in t/t5584-http-429-retry.sh covering various Retry-After scenarios and configuration combinations. The changes touch HTTP plumbing, configuration, and test infrastructure while maintaining backward compatibility.

Review feedback from Jeff King and Taylor Blau led to significant simplifications in v4, including replacing a complex non-blocking delay mechanism with simple blocking sleep() and removing obsolete protocol-specific error handling. The strbuf fixes grew into their own preparatory patches after Junio Hamano identified broader implications in the initial strbuf_reencode() fix.

This appears to be a well-structured series that addresses a real-world need (handling API rate limits) while improving related subsystems. The extensive test coverage and incremental refinement through multiple versions suggest it's production-ready.
