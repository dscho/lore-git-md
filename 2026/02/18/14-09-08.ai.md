Feature patch adding HTTP 429 rate limiting support to Git's HTTP client. This is the final patch in a series (5/5) that introduces retry logic for HTTP 429 (Too Many Requests) responses.

The patch adds three new configuration options to control retry behavior: `http.maxRetries` (default 0), `http.retryAfter` (default 0), and `http.maxRetryTime` (default 300 seconds). The implementation supports RFC-compliant Retry-After headers in both delay-seconds (integer) and HTTP-date (RFC 2822) formats. If the server provides a past date, Git retries immediately without waiting.

Key technical details include:
- New HTTP_RATE_LIMITED return code in http.h
- Retry logic in http.c` that respects both server headers and config values
- Fail-fast behavior when delays exceed `http.maxRetryTime`
- Environment variable overrides for all config options
- Comprehensive test coverage in new test script t/t5584-http-429-retry.sh
- The implementation uses curl's CURLINFO_RETRY_AFTER when available (curl >= 7.66.0) with a manual parser fallback
- Trace2 events for monitoring retry attempts and delays
- The test suite verifies:
  - Basic retry behavior
  - Header format handling
  - Configuration combinations
  - Environment variable overrides
  - Edge cases like past dates and invalid formats

The patch appears well-constructed with thorough test coverage and clear documentation. It follows Git's existing HTTP infrastructure patterns while adding the new rate limiting capability. The implementation is careful about backward compatibility, providing fallbacks for older curl versions.
