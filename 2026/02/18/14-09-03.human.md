This is a feature patch series introducing HTTP 429 rate limit retry support, building on earlier strbuf fixes. The 5-patch series from Vaidas Pilkauskas adds comprehensive handling of rate-limited HTTP responses (status code 429) with configurable retry behavior.

The series has evolved through four iterations with input from Jeff King and Taylor Blau. Key improvements since v3 include:
- Cleaned up all `strbuf_attach()` call sites to properly account for NUL terminators
- Added a BUG() check in `strbuf_attach()` to enforce allocation size contracts
- Simplified the retry mechanism from a complex non-blocking design to straightforward blocking sleeps
- Added support for parsing the Retry-After header in both delay-seconds and HTTP-date formats
- Made the implementation more portable by removing non-POSIX test dependencies

The main feature (patch 5) introduces three new options:
- `http.maxRetries` - controls how many times to retry
- `http.retryAfter` - sets default delay when no Retry-After header exists
- `http.maxRetryTime` - caps total retry delay time

The implementation includes thorough tests in t/t5584-http-429-retry.sh that verify:
- Immediate retry when Retry-After: 0
- Delay-based retry with various wait times
- HTTP-date formatted retry-after headers
- Config option interactions
- Edge cases like maximum retries exceeded

The patches leading up to the main feature are preparatory cleanups that fix subtle strbuf memory management issues and reduce code duplication in the HTTP error handling path. The series shows careful attention to detail and has benefited from thorough review feedback. The HTTP 429 support itself looks well-designed and should help Git better handle rate-limited API responses from services like GitHub.
