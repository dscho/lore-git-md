This is a bugfix patch targeting the `git subtree` contrib command, specifically addressing incorrect commit exclusion during subtree splits. The patch is the third in a series (v2 3/3) and follows up on reports from George and Christian Heusel about split history regressions.

The core issue stems from `should_ignore_subtree_split_commit` logic that was incorrectly filtering out commits from other subtrees during split operations. While this filtering aimed to optimize performance by skipping irrelevant commits, it could actually alter the split history in ways that violate the API contract (commit hashes should remain stable). The patch removes this problematic optimization entirely.

Key points:
1. The removed optimization was particularly problematic for merge commits, where ancestry checks in `copy_or_skip` depend on having the complete split history available.
2. The patch includes an extensive test case that verifies correct behavior with rebased subtree commits, demonstrating the fix handles edge cases where subtree commits have been modified after creation.
3. This follows previous attempts to fix related issues (referenced by commit hashes in the message), showing this is a persistent area needing attention.

The patch appears well-constructed with thorough testing and clear explanation of both the problem and solution. While removing the optimization might impact performance for repositories with many subtrees, correctness is prioritized here. The changes are focused and the test coverage is comprehensive, suggesting this should be a safe fix.
