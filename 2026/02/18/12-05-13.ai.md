Bugfix report for `git rebase` state corruption during interrupted operation.

Cary Reams reports experiencing repository corruption during an interactive rebase that encountered a segmentation fault. The key symptoms were:

1. A rebase of 18 commits failed at commit 7 with a segfault during conflict resolution
2. Subsequent `rebase --continue` and `rebase --abort` commands failed
3. The repository remained stuck in a rebase state across branch checkouts
4. Error messages indicated lockfile issues (`MERGE_RR.lock` exists)
5. Manual lockfile removal led to another segfault
6. The repository eventually self-corrected after transferring files to a fresh clone

The report suggests a potential race condition or incomplete cleanup when `git rebase` fails catastrophically (segfault). The persistence of rebase state across branch operations and the lockfile conflicts point to incomplete state cleanup in the sequencer. While the repository eventually recovered, the experience highlights edge cases in rebase failure handling that could leave users in an unclear state.

The report lacks specific version information and reproduction steps, but documents a real-world failure scenario that could help diagnose sequencer edge cases. The self-healing behavior after repository transfer suggests the corruption was limited to rebase metadata rather than object storage.
