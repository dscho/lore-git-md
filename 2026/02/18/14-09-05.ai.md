Bugfix patch addressing strbuf_attach() buffer size requirements across multiple call sites. This is the second patch in a 5-part series fixing strbuf reencoding issues, following the initial off-by-one allocation fix in strbuf_reencode().

The patch updates seven call sites that were incorrectly passing alloc == len to strbuf_attach(), which violates the function's requirement that alloc must be at least len+1 to accommodate the NUL terminator. The changes fall into two patterns:

1. For cases where the buffer is known to be NUL-terminated (mailinfo, am, fast-import, files-backend, trailer), the patch changes the alloc parameter from len to len+1.

2. For cases dealing with ll_merge results (apply, rerere) which return exactly sized buffers without NUL terminators, the patch switches to using strbuf_add() followed by freeing the original buffer, ensuring proper NUL-termination.

The changes are mechanical but important for correctness, as they may affect memory allocation behavior. The patch maintains the same functionality while properly accounting for NUL terminators, preparing for potential future changes to strbuf_attach()'s internal allocation behavior.

Key files touched include apply.c, rerere.c (for merge handling), and several others dealing with string buffers in mail processing and ref storage. The patch appears well-scoped and follows the established pattern of the series, though we haven't yet seen the remaining patches in the sequence.
