This is a proposal to enhance push certificate privacy by allowing control over the "pushee" header in signed pushes. Lorenz Leutgeb identifies a privacy leak when using Git's push certificates in an unconventional application architecture where pushes occur between local repositories, exposing filesystem paths in the certificate.

The current implementation sanitizes URLs but preserves filesystem paths, which makes sense for most use cases but creates privacy concerns in Leutgeb's scenario. He proposes adding a `--signed-pushee` option to `git send-pack` (and potentially `git push`) to either specify a custom pushee value or suppress the header entirely with `--no-signed-pushee`.

The patch would address a real privacy concern, though one that arises from a somewhat unusual use case. The proposal is well-reasoned, with consideration given to edge cases like empty strings and the relationship to existing `--signed` options. The author demonstrates familiarity with the code history (referencing the 11-year-old commit that introduced the current behavior) and appears prepared to implement a clean solution if the approach is approved.

This seems like a reasonable enhancement that could be accepted if implemented carefully, though reviewers may want to discuss whether the use case is common enough to warrant core Git changes versus handling it in the application layer. The thread is likely to generate discussion about the balance between flexibility and feature creep in Git's push certificate system.
