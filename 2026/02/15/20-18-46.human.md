This is the second patch in a 3-part series fixing issues with `git subtree split`'s handling of commit history. The series addresses problems caused by an optimization that incorrectly excluded commits from split history.

Patch 2/3 focuses on expanding test coverage before the actual fix in patch 3. It adds commit history depth assertions to existing subtree tests, verifying that split operations maintain the expected number of commits. The tests now explicitly check rev-list counts at each step, particularly for:
- Basic subtree splits with --rejoin
- Multiple simultaneous subtree operations
- Nested subtree scenarios

The test additions were originally part of a reverted commit (28a7e27cff), suggesting this validation was previously known to be important. The patch appears well-scoped, touching only the test file with clear, focused assertions. It follows the Git project's preferred approach of adding tests first before behavior changes.

The patch series as a whole looks like a careful, incremental fix for a subtle history-handling bug in the subtree command. This middle patch does the groundwork to ensure the subsequent behavior change can be verified.
