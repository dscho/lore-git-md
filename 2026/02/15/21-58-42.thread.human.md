The thread discusses a privacy concern in Git's push certificate mechanism, where local filesystem paths can unintentionally leak into push certificates during local-to-local repository pushes. Lorenz Leutgeb identified this issue in a Git-based application that uses push certificates as part of its transparency log, where sensitive user-configured paths were being exposed.

The proposed solution would add new `--signed-pushee` and `--no-signed-pushee` options to `git send-pack` (and potentially `git push`) to give users control over the "pushee" header in push certificates. This would allow either specifying an alternative value or omitting the header entirely when privacy is a concern. The current behavior, which dates back to 2013, sanitizes URLs but preserves filesystem paths.

The proposal thoughtfully considers edge cases and implementation details, including empty string handling and the impact on `pre-receive` hooks that might inspect certificates. The change would primarily affect the push certificate generation code in `send-pack.c`. This stems from a real-world use case involving a Git-based application with an unconventional push architecture that splits operations between local and network phases. The author is seeking feedback on the approach before proceeding with implementation.
