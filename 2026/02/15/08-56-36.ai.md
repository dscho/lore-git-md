This is a technical discussion about refactoring Git's worktree API to clarify the distinction between primary and current worktrees. Shreyansh Paliwal responds to Junio Hamano and Phillip Wood's feedback on their RFC patch series that aims to standardize worktree representation by replacing NULL parameters with explicit structs (using wt->id="/" for the primary worktree).

The email clarifies that `wt==NULL` historically meant "use current worktree" (resolving to repo->gitdir) while `wt->id==NULL` meant "main worktree" (resolving to repo->commondir). Shreyansh acknowledges this distinction but raises several open questions about the implementation:

1. The role of `wt->is_current` when NULL already represents current worktree
2. How callers logically differentiate between operating on current vs primary worktree
3. A proposal to include both main and current worktree references directly in `struct repository` (as r->main_wt and r->current_wt) for clarity

The discussion continues to refine the architectural approach to worktree handling, with consensus emerging around Phillip Wood's suggestion to introduce `get_current_worktree()` for gradual NULL cleanup while maintaining backward compatibility. Shreyansh's questions indicate the next iteration will need to address the relationship between NULL parameters, the is_current flag, and repository structure integration.
