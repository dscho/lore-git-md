Thread summary:

Feature proposal addressing privacy leaks in Git's push certificate mechanism, initiated by Lorenz Leutgeb's observation that local filesystem paths appear in push certificates during local-to-local pushes, potentially exposing sensitive paths in logs. The original proposal suggested adding `--signed-pushee` and `--no-signed-pushee` options to control pushee header inclusion in `git send-pack`.

Junio Hamano's response introduces critical security considerations, challenging the proposal's assumptions. He emphasizes push certificates' primary purpose of binding ref updates to specific repositories ("pushee"), identifying two security risks: (1) omitting pushee could enable replay attacks by making certificates repository-agnostic, and (2) allowing pushee substitution might create middleman forwarding scenarios. Junio provides concrete examples where repository context matters (e.g., distinguishing development vs maintenance branches) and acknowledges that while middleman forwarding might be cryptographically verifiable, it still represents a security tradeoff.

The discussion has shifted from pure privacy concerns to deeper design questions about push certificates' security model. Key open questions now include: whether any modification to the pushee field can maintain both privacy and security guarantees, how to handle the replay attack vector, and whether the middleman scenario represents an acceptable tradeoff. The thread awaits responses addressing these security implications, particularly from the original proposer. Technical considerations around `send-pack.c` modifications and hook compatibility remain relevant but are now secondary to the security design discussion.
