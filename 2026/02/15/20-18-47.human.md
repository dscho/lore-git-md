This is the final patch in a 3-part series fixing issues in `git subtree split`'s history handling. The patch removes a problematic optimization (`should_ignore_subtree_split_commit`) that was incorrectly excluding commits from the split history, which violates the API contract that split history commit hashes should remain stable.

The optimization was originally added to speed up splits in repositories with many subtrees by ignoring commits from other subtrees. However, it turns out this can alter merge commit ancestry in ways that break the subsequent `copy_or_skip` logic. The patch demonstrates this can happen when subtrees are rebased or cherry-picked, which changes their commit structure while keeping the same subtree trailers.

The removal is accompanied by expanded test coverage in t7900-subtree.sh that verifies correct behavior with multiple subtrees and rebased commits. The tests now explicitly check commit counts and branch relationships to ensure history integrity. While this may make some splits slower, it guarantees correct behavior.

This completes the series' goal of fixing the regression reported by George and Christian Heusel while maintaining the subtree split's API contract. The patch appears well-justified and thoroughly tested, making it likely to be accepted by the subtree maintainer (D. Ben Knoble).
