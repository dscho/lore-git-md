This is a bug discussion thread about `git pull` behavior with rebase configuration. Phillip Wood responds to Mark Kharitonov's initial report about `git pull` initiating a rebase when no upstream changes exist.

Phillip explains that the behavior Mark observed is actually correct given the branch topology - even though Mark had merged upstream changes into his local branch (`feature/dotnetupgrade`), the local commits are still not on top of those upstream changes. The key technical point is that `git pull --rebase` will rebase local commits that aren't in upstream, regardless of whether the upstream changes were merged in.

The thread shows this isn't Windows-specific (despite the original report coming from Windows) - it's fundamental rebase logic. Phillip's response indicates this is working as designed, not a bug. The discussion centers on understanding Git's rebase behavior when local branches have both direct commits and merged upstream changes.

For future reference, the thread involves:
- The `feature/dotnetupgrade` branch that's 875 commits ahead of upstream
- Rebase configuration (`rebase.forkPoint` is false)
- The specific rebase command that runs: `git rebase --autostash --onto <same-sha> <same-sha>`
- Windows-specific elements like credential manager and LFS hooks in the trace output

The core question appears resolved - this is expected behavior, not a bug - but the discussion may continue around whether this behavior is intuitive or could be improved.
