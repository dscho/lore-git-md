This is a bug report about `git fetch --shallow-since` producing invalid shallow repositories. The issue occurs when fetching into an empty repository with a date-based shallow cutoff, resulting in `.git/shallow` entries that reference commit objects not actually present in the packfile. 

The detailed reproduction shows that under certain merge-heavy histories, the server can mark commits as shallow boundaries (adding them to `.git/shallow`) while failing to include those commits in the transferred pack. This creates a repository that appears healthy for read operations but fails when attempting to deepen the clone later, as the client cannot resolve the promised shallow boundary objects.

The bug manifests when:
1. A merge commit has parents on both sides of the shallow cutoff date
2. The server marks the merge and some parent commits as shallow boundaries
3. The pack generation logic then fails to include all marked boundary commits

The reporter notes this affects both `--shallow-since` and `--shallow-exclude` but not `--depth` fetches. The issue appears to violate an implicit invariant that shallow boundary commits should always be present in the repository. The bug has been reproducible across Git versions (2.51.0 through current `next`).

This is a serious correctness issue in the shallow clone machinery that could affect any user of date-based shallow fetching, particularly those working with repositories containing merge commits that straddle the cutoff date. The bug report is well-constructed with a clear minimal reproduction case and analysis of the failure mode.
