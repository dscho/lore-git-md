Thread identity: Bug report about `git fetch --shallow-since` producing invalid shallow repositories when fetching into empty repos with date-based cutoffs, affecting merge-heavy histories.

Core problem: When fetching with `--shallow-since` or `--shallow-exclude`, the server can mark commits as shallow boundaries (adding to `.git/shallow`) while failing to include those commits in the packfile. This violates the invariant that shallow boundary commits should be present, causing failures when attempting to deepen the clone later.

Current status: Unresolved bug present across Git versions 2.51.0 through current `next`. Affects date-based shallow fetching (`--shallow-since`, `--shallow-exclude`) but not depth-based (`--depth`).

Key technical details: 
- Occurs when merge commits have parents on both sides of shallow date cutoff
- Server marks merge and some parents as shallow boundaries but pack generation fails to include all marked boundaries
- Results in `.git/shallow` entries referencing missing objects
- Repository appears healthy for reads but fails on subsequent deepen operations

Open questions: 
- Exact conditions triggering pack generation to omit boundary commits
- Whether similar issues exist in other shallow fetch scenarios
- Potential fixes that maintain performance while ensuring boundary commit availability

Participant positions: Original reporter provided detailed reproduction case showing the issue spans multiple Git versions. No maintainer response yet.

Severity: Serious correctness issue affecting users of date-based shallow fetching, particularly with merge-heavy histories. Well-constructed report with clear minimal reproduction.
