This is a bug report about `git fetch --shallow-since` producing invalid shallow repositories. The reporter, Nick Gavalas, demonstrates that under certain conditions (particularly with merge commits and branch histories), the shallow fetch operation records commit hashes in `.git/shallow` that don't actually exist in the repository's object database. 

The issue manifests when:
1. Fetching with `--shallow-since` into an empty repository
2. The repository history contains merges where some parents would be excluded by the date cutoff
3. The server marks certain commits as shallow boundaries but fails to include them in the packfile

The immediate symptom is that later attempts to deepen the clone fail with "fatal: error in object" when trying to unshallow missing objects. While read operations work fine, this violates what appears to be an implicit invariant that shallow boundary points should exist in the local repository.

The bug appears to be in how the server computes and transmits shallow boundaries versus what objects it includes in the packfile. The reporter provides a clear minimal test case and suspects the issue may affect the same codepath as `--shallow-exclude`. This looks like a genuine protocol/implementation bug rather than a misunderstanding of expected behavior.
