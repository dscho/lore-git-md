Bug report response about `git pull` rebase behavior. Phillip Wood responds to Mark Kharitonov's report of an unexpected rebase during `git pull` on Windows. Phillip explains this is expected behavior when the local branch (feature/dotnetupgrade) has commits not in upstream (875 commits ahead) and has incorporated upstream changes via merge rather than rebase. The key insight is that while merges bring in the changes, they don't change the branch's base commit, so `git pull --rebase` still sees local commits to rebase. 

This isn't Windows-specific - it's how Git's rebase logic works when dealing with merged upstream changes. The thread shows good technical detail (trace logs, config settings) but reveals a common misunderstanding about how pull/rebase interacts with merge commits. Phillip's response is characteristically knowledgeable about rebase behavior, though it doesn't address why the rebase arguments were identical (--onto X X) which might still indicate a separate issue.
