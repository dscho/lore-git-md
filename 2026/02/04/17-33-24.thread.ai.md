Patch 3/9 implements core parallel execution logic with several key mechanisms: new `hook.<name>.parallel` config option (default false for safety), logic to determine effective job count respecting both global and per-hook settings, special handling for hooks requiring separate output streams (pre-push always runs sequentially), and comprehensive tests in t/t1800-hook.sh verifying serial vs parallel behavior.

The implementation layers controls with clear precedence: CLI `-j/--jobs` override takes highest precedence, followed by per-hook `hook.<name>.parallel` flags (all must be true for parallel execution), then global `hook.jobs` default, with fallback to serial execution if any safety check fails. Core changes enable concurrent execution of hooks for single events with careful output stream handling - when parallel execution is enabled, hook stdout is automatically redirected to stderr to maintain ordering, except for pre-push hook which retains separate streams. Patch 4/9 enables parallel execution for the pre-push hook while maintaining backward compatibility - when no parallelism is requested (jobs=1), pre-push behaves exactly as before. When users explicitly enable parallelism (via hook.jobs > 1 or -j flag), stdout is automatically merged into stderr to allow proper output de-interleaving. The implementation removes the need for any extension infrastructure by having get_hook_jobs() set stdout_to_stderr=1 automatically when jobs > 1. The patch includes clear documentation of this behavior change and adds comprehensive tests verifying both the merged output behavior and actual parallel execution of pre-push hooks. The transport.c changes reflect this new automatic handling while keeping the default serial case unchanged.

Patch 5/9 marks several hooks as non-parallelizable by initializing them with RUN_HOOKS_OPT_INIT_FORCE_SERIAL, which overrides any parallel execution settings. The affected hooks are those that operate on shared state: commit message hooks (applypatch-msg, prepare-commit-msg, commit-msg), working tree/index hooks (pre-commit, post-checkout, push-to-checkout), and post-commit. The changes update hook calls in builtin commands (am, checkout, clone, receive-pack, worktree, commit) to use the force-serial option. Documentation is added explaining why these hooks cannot be parallelized safely. A new test case verifies that hook.jobs settings are ignored for force-serial hooks, demonstrating that pre-commit hooks still run sequentially even when parallel execution is requested.
