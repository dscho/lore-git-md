Junio Hamano raises an important practical concern about the current sideband control character sanitization approach in this reply to Jeff King. While the thread has focused on security risks from ANSI escape sequences, Junio points out a legitimate use case that would be broken by the current implementation - terminal title updates using the ESC ] 0; <string> BEL sequence.

This isn't just theoretical - Junio describes his own workflow where long-running processes update terminal titles to show progress, which he monitors from other terminal tabs. He argues that even if this breaks for users without compatible terminals, that's between the server and client, and the current sanitization would unnecessarily prevent this useful functionality unless users opt into allowing all control characters (which defeats the security purpose).

The comment suggests the security model may need to be more nuanced than a simple whitelist/blacklist dichotomy. Junio's perspective as maintainer carries significant weight here, indicating the patch series may need redesign to accommodate both security and legitimate terminal control needs. His earlier review had already raised concerns about version-dependent defaults and the whitelist approach; this concrete example strengthens that critique by showing a real-world case where the current design falls short.

The test change shown (adding `-c sideband.allowControlCharacters=color`) demonstrates how users would need to explicitly configure around the restrictions, which Junio implies creates unnecessary friction for valid use cases. This feedback suggests the next iteration will need to either find a way to safely allow more control sequences by default or provide more granular control over which sequences are permitted.
