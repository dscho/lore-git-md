This is a follow-up discussion on the `git add -p` navigation feature patch, focusing on the patch application timing behavior (immediate vs transactional). Junio C Hamano clarifies his earlier comments were not meant as implementation suggestions, and now argues strongly for a consistent "all-or-none" approach when in the new navigation mode.

The key point is that allowing partial application (immediate mode) would create an inconsistent user experience: users could revisit and change decisions on some hunks but not others, depending on when they were applied. Junio notes this would undermine the core value proposition of the new navigation feature - the ability to defer decisions and move between files. He explicitly states the transactional model makes more sense for this mode, where all decisions are applied together at the end.

This email resolves the open question about patch application timing by clearly advocating for transactional behavior in the navigation mode, while still allowing the traditional immediate application as a configurable option. The discussion shows the maintainer thinking through the user experience implications and establishing clear design constraints for the next version of the patch.
