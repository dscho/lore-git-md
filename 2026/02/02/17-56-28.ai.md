This is a bugfix for the `git blame` command's coloring behavior when used with both `--color-lines` and `--ignore-rev` options. The patch has already been reviewed and approved by Junio C Hamano, indicating it's ready for merging.

The issue occurs when consecutive lines that should be colored the same (due to coming from the same commit after ignoring a specified revision) were incorrectly showing different colors. René Scharfe's fix addresses this by modifying the coloring logic in `builtin/blame.c` to properly handle the `--ignore-rev` case while maintaining the distinction needed for `blame.markignoredlines` to work correctly.

Junio notes this might represent a special case in the blame machinery rather than a more general solution, suggesting potential future refactoring opportunities. However, he confirms the current patch is correct and thanks René for including a test case. The fix ensures consistent coloring between cases where `--ignore-rev` is and isn't used, with consecutive lines from the same commit (after ignoring) now properly colored cyan.

The technical implementation reveals an architectural distinction in the blame subsystem between merge traversal cases and explicit revision ignoring. While the fix is minimal and doesn't affect other blame functionality, it provides insight into how the `--ignore-rev` feature was integrated with the existing blame machinery. The patch includes a test case in `t/t8012-blame-colors.sh` that verifies the behavior with whitespace-changing commits.
