This is a discussion about potential syntax for referencing a repository's primary branch, specifically considering Phillip Wood's proposal for an `@{local}` modifier as an alternative to Harald Nordgren's `@{default}` proposal.

Junio C Hamano engages with Phillip Wood's suggestion of `@{local}` as a way to reference the local branch that would push to the remote's default branch (as indicated by origin/HEAD). He notes this would be conceptually similar to existing modifiers like `@{push}` but in reverse. The thread has evolved to consider both branch-attached workflows (where explicit branch names are needed) and detached-HEAD workflows (where they aren't), with this email adding consideration of modifier chaining like `feature@{upstream}@{local}`.

Key technical points raised:
- The `@{local}` modifier would resolve to the local branch that pushes to a given tracking branch
- This enables expressions like `feature@{upstream}@{local}` to find the local branch corresponding to a feature branch's upstream default
- Junio questions whether we might need parallel modifiers for other "reverse" operations beyond just push relationships

The discussion continues to weigh syntax options (`@{default}` vs `@{local}`) while the underlying implementation approach (resolving via remote-tracking branches) remains technically sound. Junio's response indicates he's still evaluating whether the demonstrated use cases justify new syntax, with this email focusing more on the conceptual model of modifier chaining than on settling the naming question.
