This is a **substantive review** of the first patch in the **ready-to-merge v6 series** optimizing `paint_down_to_common()` for one-sided histories. The patch adds a **technical document** (`Documentation/technical/paint-down-to-common.adoc`) explaining the algorithm’s core concepts, generation-number regions, and termination conditions.

Elijah Newren’s review **identifies a potential correctness gap** in the document’s explanation of generation-number ordering. The document currently treats the "finite region" (where generation numbers guarantee topological traversal) and the "INFINITY region" (where commit-date ordering can violate it) as distinct, but it does not account for **v1 commit-graphs**, where generation numbers saturate at `GENERATION_NUMBER_V1_MAX`. This saturation can also violate topological ordering, meaning the document’s invariant ("paint on already-visited commits is final") may not hold in all cases. Elijah suggests treating `GENERATION_NUMBER_V1_MAX` similarly to `INFINITY` for consistency.

Additionally, Elijah **questions the wording around the `min_generation` cutoff**, which is used by `remove_redundant()` and `repo_in_merge_bases_many()`. The current phrasing ("No merge base can have a generation below this threshold") could mislead future callers into assuming the cutoff applies to all merge-base queries, when in reality it only works for callers that **do not need deeper merge bases** (e.g., reachability checks among input commits). This is a **clarity and forward-compatibility concern**, not a bug in the current code.

The review is **non-blocking**—the series is procedurally unblocked and queued in Junio’s tree—but it highlights **documentation risks** that could affect future maintainers. The author (Kristofer Karlsson) may want to address these points to ensure the document remains accurate and unambiguous as the algorithm evolves. No code changes are required, but the **technical document’s precision** is at stake.
