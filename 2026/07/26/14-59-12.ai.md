This is a follow-up review comment from Junio C Hamano on the contested second patch of Lucas Zamboni Orioli’s `git mv` bugfix series. The patch adds an early existence check for the destination directory, but Junio now clarifies his objection to the `stat()`-based approach adopted in v3.

Junio reiterates that following symlinks in a Git working tree is unsafe, regardless of whether the symlink points outside the working tree. The core issue is that Git tracks symlinks as first-class objects, so a tracked symlink in the destination path should be treated like any other tracked file: it is "taken" and should block the move. He argues that `git mv x a/b/c` should refuse to operate if any component of `a/b/c` is a tracked symlink, rather than following it to its target. This stance aligns with `git apply`’s behavior and avoids crafting arbitrary rules about link targets.

The email does not propose a specific implementation, but the implication is that the patch should use `lstat()` and reject any symlink in the destination path, even if it points to a directory. This would simplify the logic and avoid the need to reason about link targets. No new edge cases are introduced, but the discussion now explicitly includes multi-level paths (`a/b/c`) where intermediate components may be symlinks. The series remains blocked on resolving this symlink-handling strategy.
