Thread identity: standalone refactoring patch series by Hardik Kumar changing the return type of UTF-8 string-width calculation functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t` in `utf8.c` and `utf8.h`. The series was **withdrawn after three iterations (v1–v3)** following sustained reviewer opposition from Junio C Hamano, Pablo Sabater, and Phillip Wood. The final action is a **follow-up documentation patch** to explain the existing design's rationale, with Hardik Kumar seeking guidance on where to place the documentation (proposed: `Documentation/technical/`).

Core problem or goal: eliminate a type mismatch where functions computing inherently non-negative display widths (UTF-8 string width) return `int` instead of `size_t`. The effort was intended as a purely type-system cleanup but **reviewers unanimously concluded the practical benefits were minimal** for functions measuring display widths of strings that fit on a single line, while risks (regressions, complexity, and pervasive explicit casts) outweighed benefits. The withdrawal resolves the debate in favor of the status quo, with **improved documentation** to clarify the existing design’s rationale.

Current status: **withdrawn**. Hardik Kumar’s final email acknowledges the v3 approach—prioritizing minimal disruption by reintroducing explicit casts to `int` at call sites—failed to deliver meaningful type-system improvements. The patch’s regressions (e.g., underflow risks in `diff.c`, mixed-sign comparisons in `pretty.c`, struct field mismatches in `builtin/repo.c`) and incomplete conversions (e.g., overlooked callers in `builtin/worktree.c`) will **not be addressed**. A **follow-up patch** will:
- Remove the TODO comment in `utf8.c`.
- Document (a) why the functions return `int` (to align with APIs like `printf()` that require `int` for padding calculations) and (b) the necessity of `cast_size_t_to_int()` to prevent overflows.
- The `cast_size_t_to_int()` helper will **remain in place** with its rationale documented.
Hardik Kumar’s latest email asks whether the documentation should live in a new `.adoc` file in `Documentation/technical/`; no technical discussion is expected unless Junio or Phillip reply with placement guidance.
