Thread identity: standalone refactoring patch series by Hardik Kumar changing the return type of UTF-8 string-width calculation functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t` in `utf8.c` and `utf8.h`. The series is now in its third iteration (v3), following two prior versions that introduced regressions and faced strong skepticism from Junio C Hamano about the patch’s practical value. The v3 patch updates function signatures, removes the `cast_size_t_to_int()` helper, and adjusts all callers to use `size_t` for local variables, but **reintroduces explicit casts to `int` at nearly every call site**, effectively preserving the original implicit conversions and undermining the stated goal of type consistency.

Core problem or goal: eliminate a type mismatch where functions computing inherently non-negative display widths (UTF-8 string width) return `int` instead of `size_t`. The change is intended as a purely type-system cleanup with no runtime behavior changes, but **v3 prioritizes minimal disruption over type safety**, reintroducing explicit casts to `int` at call sites and failing to address core issues like mixed-sign comparisons, underflow risks, and struct field mismatches. Junio’s prior skepticism about the patch’s value remains unresolved, as the practical benefit of enforcing `size_t` consistency is minimal for functions measuring display widths of strings that fit on a single line.

Current status: patch posted (v3); under **active review with unresolved blocking issues and ongoing viability concerns**. The v3 patch resolves immediate compilation errors from v2 but **does not address the fundamental regressions** identified by Junio and Pablo Sabater, including:
- Mixed-sign comparisons in `diff.c`, `pretty.c`, `builtin/blame.c`, and `builtin/repo.c`.
- Underflow risks in `diff.c` (`len -= 3` and `padding = len - cast_size_t_to_int(...)`).
- Struct field mismatches in `builtin/repo.c` (`stats_table` fields remain `int`).
- Conditional compilation issues in `gettext.h` (untested `NO_GETTEXT` builds).
- Removal of the overflow check in `cast_size_t_to_int()` without justification.
The patch is **not ready for `next`** and may require either a more comprehensive refactoring (e.g., promoting struct fields to `size_t`, eliminating casts) or withdrawal. Hardik’s latest email reaffirms the v3 approach, which prioritizes minimal disruption by reintroducing explicit casts to `int` at call sites, but does not engage with Junio’s broader skepticism about the patch’s value or Pablo’s concerns about the overflow check and commit message accuracy.

Open questions and loose ends:
- **Overflow check removal**: The patch removes the overflow check in `cast_size_t_to_int()` without justification, despite Pablo Sabater’s prior concern that some callers might rely on it. Hardik’s v3 does not address this.
- **Mixed-sign comparisons**: The patch does not resolve unsafe comparisons between `size_t` and `int` variables (e.g., `padding = len - cast_size_t_to_int(...)` in `diff.c`). These could trigger warnings or subtle bugs.
- **Underflow risks**: `len -= 3` (now `size_t`) in `diff.c` could underflow if `len < 3`, and `padding = len - cast_size_t_to_int(...)` could produce incorrect results if `utf8_strwidth()` returns a value larger than `len`.
- **Struct field mismatches**: In `builtin/repo.c`, `stats_table` struct fields remain `int`, forcing casts that reintroduce implicit conversions. Hardik resists promoting them to `size_t`, prioritizing minimal changes over type consistency.
- **Patch viability**: Junio’s prior email strongly questioned whether the patch is worth pursuing, given the high cost of careful coding and review relative to the minimal practical benefit. Hardik’s v3 does not address this broader concern, leaving the patch’s future uncertain.
- **Explicit casts**: Hardik’s v3 reintroduces explicit casts to `int` at nearly every call site, preserving the original behavior but undermining the patch’s goal of eliminating implicit conversions. The safety of these casts is questionable, especially in `diff.c` where underflow risks persist.
- **Commit message accuracy**: Pablo’s prior critique of the commit message’s technical claims (e.g., "implicit conversion from `size_t` to `int` is not undefined behavior") remains unaddressed.
