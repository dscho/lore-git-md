Thread identity: standalone refactoring patch series by Hardik Kumar changing the return type of UTF-8 string-width calculation functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t` in `utf8.c` and `utf8.h`. The series is now in its third iteration (v3), following two prior versions that introduced regressions and faced strong skepticism from Junio C Hamano and other reviewers about the patch’s practical value. The v3 patch updates function signatures, removes the `cast_size_t_to_int()` helper, and adjusts all callers to use `size_t` for local variables, but **reintroduces explicit casts to `int` at nearly every call site**, effectively preserving the original implicit conversions and undermining the stated goal of type consistency.

Core problem or goal: eliminate a type mismatch where functions computing inherently non-negative display widths (UTF-8 string width) return `int` instead of `size_t`. The change is intended as a purely type-system cleanup with no runtime behavior changes, but **v3 prioritizes minimal disruption over type safety**, reintroducing explicit casts to `int` at call sites and failing to address core issues like mixed-sign comparisons, underflow risks, and struct field mismatches. Reviewers, including Junio C Hamano, Pablo Sabater, and Phillip Wood, have **strongly questioned the patch’s value**, arguing that the practical benefit of enforcing `size_t` consistency is minimal for functions measuring display widths of strings that fit on a single line, while the risks (regressions, increased complexity, and pervasive explicit casts) outweigh the benefits.

Current status: patch posted (v3); under **active review with unresolved blocking issues, ongoing viability concerns, and growing reviewer opposition**. The v3 patch resolves immediate compilation errors from v2 but **does not address the fundamental regressions** identified by reviewers, including:
- Mixed-sign comparisons in `diff.c`, `pretty.c`, `builtin/blame.c`, and `builtin/repo.c`.
- Underflow risks in `diff.c` (`len -= 3` and `padding = len - cast_size_t_to_int(...)`).
- Struct field mismatches in `builtin/repo.c` (`stats_table` fields remain `int`).
- Conditional compilation issues in `gettext.h` (untested `NO_GETTEXT` builds).
- Removal of the overflow check in `cast_size_t_to_int()` without justification.
- **New issue**: Phillip Wood’s review highlights that the patch forces callers to explicitly cast `size_t` results back to `int` for use with `printf()` and other APIs, creating unnecessary complexity and risk. He also notes that the patch may be incomplete, as some callers (e.g., in `builtin/worktree.c`) appear to be incorrectly converted or overlooked.
- **Junio C Hamano’s latest email** endorses Phillip Wood’s position, **reinforcing the blocking nature of the feedback** and emphasizing that the TODO comment in `utf8.c` should be replaced with **documentation explaining (a) why the functions return `int` and (b) why `cast_size_t_to_int()` is necessary to prevent overflows**. This signals that the patch’s approach is flawed and that the status quo (with improved documentation) is preferable.

The patch is **not ready for `next`** and may require either (1) a more comprehensive refactoring (e.g., promoting struct fields to `size_t`, eliminating casts, and addressing all mixed-sign comparisons) or (2) withdrawal in favor of documenting the existing design. Hardik’s latest email reaffirms the v3 approach, which prioritizes minimal disruption by reintroducing explicit casts to `int` at call sites, but does not engage with the broader skepticism about the patch’s value or the technical critiques from Pablo Sabater, Phillip Wood, or Junio C Hamano.

Open questions and loose ends:
- **Overflow check removal**: The patch removes the overflow check in `cast_size_t_to_int()` without justification, despite Pablo Sabater’s prior concern that some callers might rely on it. Junio C Hamano’s latest email **emphasizes the need to document the overflow prevention rationale**, suggesting this is a critical gap in the patch’s design.
- **Mixed-sign comparisons**: The patch does not resolve unsafe comparisons between `size_t` and `int` variables (e.g., `padding = len - cast_size_t_to_int(...)` in `diff.c`). These could trigger warnings or subtle bugs.
- **Underflow risks**: `len -= 3` (now `size_t`) in `diff.c` could underflow if `len < 3`, and `padding = len - cast_size_t_to_int(...)` could produce incorrect results if `utf8_strwidth()` returns a value larger than `len`.
- **Struct field mismatches**: In `builtin/repo.c`, `stats_table` struct fields remain `int`, forcing casts that reintroduce implicit conversions. Hardik resists promoting them to `size_t`, prioritizing minimal changes over type consistency.
- **Patch viability**: Junio C Hamano and Phillip Wood have **strongly questioned whether the patch is worth pursuing**, given the high cost of careful coding and review relative to the minimal practical benefit. Junio’s latest email **aligns with Phillip’s position** that the status quo (with improved documentation) is preferable, increasing the likelihood of withdrawal unless Hardik provides a compelling counterargument.
- **Explicit casts**: Hardik’s v3 reintroduces explicit casts to `int` at nearly every call site, preserving the original behavior but undermining the patch’s goal of eliminating implicit conversions. The safety of these casts is questionable, especially in `diff.c` where underflow risks persist. Phillip Wood argues that this approach is impractical and error-prone, as callers must manage the casts manually.
- **Commit message accuracy**: Pablo’s prior critique of the commit message’s technical claims (e.g., "implicit conversion from `size_t` to `int` is not undefined behavior") remains unaddressed.
- **Incomplete conversion**: Phillip Wood’s review suggests the patch may have missed some callers (e.g., in `builtin/worktree.c`), raising concerns about the patch’s thoroughness.
- **Documentation gap**: Junio C Hamano’s email highlights the need to **document the rationale for the functions returning `int` and the necessity of `cast_size_t_to_int()`**, which the patch currently removes without explanation.
