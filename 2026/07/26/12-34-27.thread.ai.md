Core problem or goal: eliminate a type mismatch where functions computing inherently non-negative display widths (UTF-8 string width) return `int` instead of `size_t`. The change removes the need for a helper function (`cast_size_t_to_int`) and updates all callers to use `size_t` consistently. The patch is intended as a purely type-system cleanup with no runtime behavior changes, but v2 introduces **multiple type-safety regressions** due to unsigned integer underflow, mixed-sign comparisons, and incomplete signature updates in conditional compilation paths. Junio now expresses **strong skepticism about the effort’s overall value**, arguing that the practical benefit is minimal given the functions’ limited use case (measuring display widths of strings that fit on a single line) and that the risk of regressions outweighs the theoretical type-safety improvement. Hardik’s latest email does not address the fundamental tension between type consistency and regression risk, instead reasserting the technical merit of using `size_t` for non-negative values.
