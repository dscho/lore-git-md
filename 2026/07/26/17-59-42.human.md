This is a follow-up in the ongoing `git mv` bugfix series. The author, Lucas Zamboni Orioli, now agrees with Junio C Hamano’s position that **any tracked symlink in the destination path should block the move**, regardless of whether it points to a directory or file. The discovery came from a test case where `git mv` followed a tracked symlink, leaving the index inconsistent with the worktree: the index recorded the literal symlink path (`c/real-dir/a`), while the file landed at the resolved path (`real-dir/a`), confusing `git status`.

Lucas plans to revise the second patch to use `has_symlink_leading_path()` (from `symlinks.c`), matching `git apply`’s behavior and rejecting any symlink in the destination path up front. This will simplify the logic and avoid the need to reason about link targets. The revised patch will fold the symlink check into the existing early directory-existence check, covering both the original misleading-error case and the symlink-traversal issue. New tests will verify that symlinks in both intermediate and final path components are rejected, alongside the existing missing-directory and `--dry-run` cases.

The series remains a two-patch structure: the first patch (already approved) improves error messages, and the second patch (now revised) adds the early existence check. No merge status yet; the series is still under review and blocked on this symlink-handling resolution. The change is a bugfix targeting `builtin/mv.c` and the test suite, with no new user-facing options or on-disk format changes.
