This is the second patch in the v4 series fixing `git mv` error handling for missing or symlinked destination directories. It implements the early existence check that was the core of the series' second commit, now using `has_symlink_leading_path()` to reject any tracked symlink in the destination path—resolving the last technical dispute in the thread.

The patch adds logic in `builtin/mv.c` to check three problematic cases before attempting the `rename()` syscall: missing leading directories, non-directory components, and tracked symlinks anywhere in the destination path. The symlink check uses `has_symlink_leading_path()` (from `symlinks.c`) to avoid following links, ensuring Git never traverses a tracked symlink regardless of its target. This prevents the index corruption bug where moving through a symlink would leave the index recording the literal path while the file was moved to the resolved location. The directory check uses `lstat()` to distinguish between missing directories (ENOENT/ENOTDIR) and non-directory components, with other errors falling through to `rename()` for reporting.

Test coverage in `t/t7001-mv.sh` is comprehensive: 83 new lines cover symlinks as both final and intermediate components, missing directories, non-directory path components, `--dry-run` detection, and force-flag behavior. A regression test verifies that the index remains untouched when a move through a symlink is rejected. The patch introduces one new translatable error message ("destination is beyond a symbolic link") and reuses an existing one for missing directories.

This is a well-scoped, user-facing fix with clear motivation and thorough testing. The symlink-handling approach now aligns with `git apply` precedent and Junio's requirement that Git must not follow tracked symlinks. The only acknowledged loose end is the TOCTOU race (where the destination could disappear between check and `rename()`), which the commit message explicitly calls out as "the best we can do" for now. The series appears ready for integration.
