This is a follow-up from the author (Lucas Zamboni Orioli) in the `git mv` bugfix thread. The patch in question is the second in a two-patch series that fixes a misleading error message and adds an early existence check for the destination directory in `git mv`.

Lucas now acknowledges Junio’s concern about symlink traversal and reports a concrete bug: when `git mv` follows a tracked symlink in the destination path, it leaves the index inconsistent with the worktree. The index records the literal symlink path, while the file is actually moved to the resolved target, causing `git status` to show a staged rename, an unstaged deletion, and an untracked file. This confirms Junio’s position that **any tracked symlink in the destination path should block the move**, regardless of its target.

To address this, Lucas proposes using `has_symlink_leading_path()` (from `symlinks.c`), which is already used by `git apply` to avoid following in-tree symlinks. This would make `git mv`’s behavior consistent with the rest of Git and eliminate the need to reason about link targets. The fix will be folded into the leading-directory check, which will now reject missing directories, non-directory components, and **any symlink** in the destination path. Updated tests will cover symlinks as both final and intermediate components, alongside the existing missing-directory and `--dry-run` cases.

The series remains a bugfix targeting `builtin/mv.c` and `t/t7001-mv.sh`, with no new symbols or on-disk format changes. The l10n impact is unchanged (two new translatable strings). The patch is now aligned with Junio’s feedback and should resolve the last technical blocker, though the TOCTOU race remains acknowledged as "the best we can do." The two-patch structure is preserved.
