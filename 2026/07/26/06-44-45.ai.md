This is the v5 reroll of Ted Nyman’s bugfix series addressing race conditions in Git’s HTTP transport during concurrent packfile URI and dumb HTTP downloads. The series remains a three-patch set, with no changes to the production code since v4—only documentation clarifications and test robustness improvements.

The core issue is unchanged: when multiple Git processes fetch the same packfile into a single object database, they can corrupt the temporary pack file by appending duplicate data. The v5 series continues to use deterministic staging paths opened in read-write mode (without append), ensuring overlapping responses write identical bytes at identical offsets. This preserves resumable downloads for both packfile URIs and dumb HTTP while avoiding cross-process coordination.

Key updates in v5 are minor but address prior feedback. The `--index-pack-arg` documentation now clarifies that the first instance specifies the command and subsequent instances specify its arguments, resolving ambiguity noted in v4 reviews. The overlapping-download test drops assumptions about which concurrent response reaches the staging file first, making the test more robust. The test suite now passes 240 runs with 12 parallel `--stress` jobs, confirming the fix for the intermittent failure in test 34 (the `test -s` check and HTTP 200/206 trace greps were removed in v4).

The patches touch `http.c`, `fetch-pack.c`, and their documentation, with new regression tests in `t/t5550-http-fetch-dumb.sh` and `t/t5702-protocol-v2.sh`. The implementation handles MinGW’s non-append O_RDWR open behavior and Windows sharing semantics, ensuring platform compatibility. The `.keep` file handling in `fetch-pack` is more robust, validating the pack hash and only registering a keep lockfile when the current process created it.

No open technical questions remain, and the series is rebased onto current `master`. The changes are narrowly scoped to the packfile URI and dumb HTTP download paths, with no impact on other HTTP fetch behaviors or on-disk formats. The series is ready for `next` and likely to progress soon.
