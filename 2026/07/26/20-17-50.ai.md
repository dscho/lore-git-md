This is the first patch in a two-patch bugfix series for `git mv`. It addresses a long-standing usability issue where `git mv` emits misleading error messages when the `rename()` syscall fails. Currently, the error message only mentions the source path, even when the actual problem is a missing directory component in the destination path. For example, `git mv a/file b/no-such-dir/file` would blame `a/file` (which exists) rather than indicating that `b/no-such-dir/` is missing.

The fix is simple and non-invasive: the error message now includes both the source and destination paths, making it immediately clear which part of the operation failed. The change is a one-line modification in `builtin/mv.c`, replacing the existing `die_errno()` call with a version that prints both paths. This approach avoids any race conditions (since it doesn’t re-inspect the filesystem after the failure) and requires no new translatable strings beyond the updated error message.

The patch is well-motivated and uncontroversial. It was previously approved by Junio ("Makes sense") and aligns with the broader goal of improving error message clarity in Git. The commit message clearly explains the problem, the solution, and why the chosen approach is safe. No test changes are needed for this patch, as the behavior change is purely in the error message output.

This is a straightforward, user-facing improvement that should have no downsides. The second patch in the series (which adds an early existence check for the destination directory) builds on this clarity by ensuring the error is caught earlier in more cases.
