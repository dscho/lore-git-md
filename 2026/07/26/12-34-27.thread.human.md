This thread is about a refactoring patch series by Hardik Kumar that changes the return type of UTF-8 string-width calculation functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t`. The series is now in its third iteration (v3), but despite addressing compilation warnings from earlier versions, it has faced strong skepticism from Junio C Hamano and other reviewers about its practical value and safety.

The patch aims to eliminate a type mismatch where functions computing inherently non-negative display widths return `int` instead of `size_t`. However, v3 prioritizes minimal disruption over type safety by reintroducing explicit casts to `int` at nearly every call site, effectively preserving the original implicit conversions. This approach undermines the patch’s stated goal of type consistency and fails to address core issues like mixed-sign comparisons, underflow risks, and struct field mismatches. For example, in `diff.c`, `padding = len - cast_size_t_to_int(utf8_strwidth(name))` remains unsafe, and `len -= 3` (now `size_t`) could underflow if `len < 3`. Similarly, struct fields in `builtin/repo.c` remain `int`, forcing casts that reintroduce implicit conversions.

Junio and Pablo Sabater have raised significant concerns about the patch’s regressions and overall value. Junio questioned whether the effort to enforce `size_t` consistency is justified for functions measuring display widths of strings that fit on a single line, while Pablo highlighted unresolved issues like the removal of an overflow check in `cast_size_t_to_int()` without justification. Hardik’s v3 does not engage with these broader concerns, leaving the patch’s future uncertain. The patch is not ready for Junio’s `next` branch and may require either a more comprehensive refactoring or withdrawal. Key questions remain about whether the explicit casts in v3 are safer than the original implicit conversions and whether the patch’s minimal benefits outweigh the risks of introducing subtle bugs.
