This thread is about a refactoring patch by Hardik Kumar that changes the return type of UTF-8 string-width functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t` to better match their inherently non-negative output. The patch, now in its second iteration (v2), was intended as a straightforward type-system cleanup but has run into significant technical issues.

The v1 patch addressed compatibility concerns by updating all callers to use `size_t` explicitly, but Junio C Hamano’s recent review of v2 uncovered multiple bugs introduced by the change. Specifically, the patch causes unsigned integer underflow and incorrect mixed-sign comparisons in `diff.c` and `pretty.c`, breaking existing logic that relied on signed arithmetic. For example, a safeguard in `diff.c` (`if (len < 0)`) becomes ineffective because `len` is now unsigned, and in `pretty.c`, negative padding values (now impossible due to unsigned `occupied`) prevent the intended "steal spaces" logic from working. These issues demonstrate that the change is not as simple as a type-system cleanup and requires careful rework to avoid regressions.

The patch remains under review, with two major unresolved issues: the bugs identified by Junio and the earlier question from Pablo Sabater about whether any callers relied on the overflow check in the removed `cast_size_t_to_int()` helper. Hardik has not yet provided a rationale or verification for removing the overflow check, and the new bugs suggest the patch needs a more thorough audit of caller behavior. René Scharfe and Pablo Sabater previously raised substantive concerns in v1, and while the v2 patch addressed some of them, the core technical challenges remain. The patch is not ready for Junio’s `next` branch and will likely require a v3.
