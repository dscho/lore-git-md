This thread is about a refactoring patch series by Hardik Kumar that changes the return type of UTF-8 string-width calculation functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t`. The series is now in its third iteration (v3), but has faced strong skepticism from maintainers and reviewers about its practical value and implementation approach.

The patch aims to eliminate a type mismatch where functions computing inherently non-negative display widths return `int` instead of `size_t`. However, the v3 patch prioritizes minimal disruption over type safety, reintroducing explicit casts to `int` at nearly every call site. This preserves the original behavior while undermining the stated goal of type consistency. Reviewers, including Junio C Hamano, Pablo Sabater, and Phillip Wood, have questioned whether the patch is worth pursuing, given the high cost of careful coding and review relative to the minimal practical benefit. Key issues remain unresolved, such as mixed-sign comparisons, underflow risks, struct field mismatches, and the removal of an overflow check without justification.

Junio’s latest email endorses Phillip Wood’s review, which strongly opposes the patch on technical and practical grounds. Phillip argues that the patch forces callers to explicitly cast `size_t` results back to `int` for use with `printf()` and other APIs, creating unnecessary complexity and risk. Junio agrees that the existing design should be documented instead, specifically explaining why the functions return `int` and why the `cast_size_t_to_int()` helper is necessary to prevent overflows. This alignment between Junio and Phillip solidifies the reviewer consensus against the patch’s viability, making it likely that the patch will be withdrawn unless Hardik provides a compelling counterargument. The thread’s next steps will likely involve either addressing the overflow check removal and justifying the patch’s value or abandoning the patch in favor of documenting the status quo.
