This thread is about a refactoring patch by Hardik Kumar that changes the return type of Git’s UTF-8 string-width functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t` to address a type-system TODO. The patch, now in its second iteration (v2), aims to eliminate implicit conversions and improve type safety, but it has introduced significant regressions—unsigned integer underflow, mixed-sign comparison bugs, and incomplete conditional compilation updates—across multiple callers, including `diff.c`, `pretty.c`, `blame.c`, and `wt-status.c`.

The discussion has taken a sharp turn with Junio C Hamano’s latest email, which questions the patch’s overall value. Junio acknowledges the theoretical appeal of the cleanup but argues that the practical benefit is minimal, as the functions are only used for measuring display widths of strings that fit on a single line (e.g., for alignment in `git diff --stat` or commit messages). He points out that the effort required to carefully review and fix the regressions is disproportionate to the gain, especially since the existing "safe cast" helper (`cast_size_t_to_int`) already includes an overflow check to prevent undefined behavior. Junio suggests that the project might be better off abandoning the patch entirely rather than risking further regressions.

The thread remains unresolved. Hardik has not yet responded to Junio’s concerns or the blocking feedback from Pablo Sabater and Junio himself, which identified critical bugs in the v2 patch. The unresolved questions include whether the overflow check in the removed helper was necessary, how to fix the new regressions, and whether the patch’s benefits justify the effort. For now, the patch is not ready for integration and will likely require a v3—or a decision to drop it altogether. Key participants include René Scharfe (who raised compatibility concerns in v1), Pablo Sabater (who identified regressions in v2), and Junio (who now questions the patch’s merit).
