This thread is about a refactoring patch by Hardik Kumar that changes the return type of two UTF-8 string-width calculation functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t` in `utf8.c` and `utf8.h`. The goal is to fix a type mismatch where functions computing inherently non-negative display widths return a signed type, addressing a `//TODO` comment and removing a helper function used for conversion. While the patch is a clean, mechanical cleanup, the header-level change affects all callers, not just the updated internal one (`strbuf_utf8_align()`).

The patch is currently under review (v1) with no merge status reported. René Scharfe previously raised a significant compatibility concern: whether all callers of these functions are safe with the new `size_t` return type, given that the header change exposes the type change globally. The patch removes a helper function (`cast_size_t_to_int`) that previously masked the type mismatch, so callers assuming a signed return type could introduce bugs or warnings.

Pablo Sabater’s recent review deepens the discussion by identifying three key issues. First, he suggests improving the commit message for clarity. More substantively, he questions whether any caller relied on the overflow check in the removed helper function, raising the risk of subtle bugs. Finally, he audits the callers (using `git grep`) and finds several outside the patch’s scope, arguing that the patch should either update all callers for consistency or explain why it’s safe to leave them unchanged. His review directly engages with René’s earlier concern, pressing for either a more comprehensive patch or a clear rationale for the current scope. The thread remains open, with the core question unresolved: whether the type change is safe as-is or requires broader updates.
