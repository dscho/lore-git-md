This is a brief but substantive follow-up in the ongoing discussion about the `git receive-pack` connectivity check performance regression introduced by the ODB abstraction rework. Jeff King (Peff) clarifies that the regression is fundamentally about alternates performance, not just the quarantine system where it was first noticed. The issue affects any Git operation that uses alternates—such as `clone -s`, `clone --reference`, or large-scale hosting setups like GitHub and GitLab that share objects between forks—meaning the performance penalty is far broader than initially observed. This reframing underscores the urgency of a near-term fix, as the regression impacts common workflows beyond server-side pushes.

The email is a direct reply to Junio’s observation that the regression manifests even without transaction or temporary directory manipulation, simply by setting up one object store to borrow from another via alternates. Peff confirms this and expands the scope: the problem is not confined to the quarantine area but is inherent to how the ODB rework changed the lookup order across backends. The shift from "pack-first, loose-second" to "pack-loose, pack-loose" causes redundant loose object checks in earlier backends (like alternates) even when objects exist in packs in later backends, a behavior that is now exposed in everyday operations like cloning with shared objects.

This is a high-weight contribution from Peff, whose earlier analysis already identified the root cause and quantified the performance impact. Here, he connects the dots between the specific regression in `git receive-pack` and the broader alternates mechanism, making it clear that the issue is systemic and not an edge case. The implication is that any targeted fix—such as restoring the cross-backend "pack-first, loose-second" lookup order—would benefit a wide range of Git deployments, not just those using quarantine directories.

The email is short but shifts the conversation: it moves the focus from a narrow server-side regression to a general alternates performance problem, raising the stakes for a timely resolution. It also reinforces that the architectural redesign Patrick Steinhardt proposed (transaction-aware ODB writes) is a separate, longer-term effort, while the immediate need is for a targeted fix to the lookup order. No new technical details or proposals are introduced, but the reframing is significant for anyone following the thread.
