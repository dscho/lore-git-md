Subject: [PATCH] clone: fix segfault with --revision on servers advertising more refs than requested
Series version: standalone patch (second submission, now with test coverage; no prior version cited in initial submission)
Originating author: Adrian Friedli
Thread type: bug report / bugfix

Core problem or goal
Fix a segmentation fault in `git clone --revision=<ref>` when the server (e.g., Azure DevOps) advertises more refs than the client requested under protocol v0. The crash occurs in `update_remote_refs()` because `guess_remote_head()` returns a non-NULL `remote_head_points_at` whose `peer_ref` field is NULL; the code then unconditionally dereferences `remote_head_points_at->peer_ref->name`.

Current status
The patch is complete and **merged to `master`**. Junio has explicitly approved the fix and the expanded commit message, which now clarifies the protocol v0-specific nature of the crash and the root cause. No further changes are expected.

Key technical details
- Files touched: `builtin/clone.c` (fix), `t/t5606-clone-options.sh` (test)
- Function modified: `update_remote_refs()` (NULL check on `remote_head_points_at->peer_ref` before dereferencing its `name` field)
- New behavior: NULL check prevents segfault; no change to on-disk format or protocol behavior
- Test coverage: new test case in `t/t5606-clone-options.sh` uses `GIT_TEST_PROTOCOL_VERSION=0` and a custom `upload-pack` hook to simulate the problematic server behavior, verifying the fix works as intended

Open questions and loose ends
None; all feedback has been addressed and the patch is merged.
