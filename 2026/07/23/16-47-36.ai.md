This is a maintainer review of the `http.connectTimeoutMS` feature patch. Junio raises three substantive points that advance the thread beyond the initial submission.

First, he asks for clarification on the use case: when would a user want to fail fast on an unreachable host rather than waiting for the default 300-second timeout? The question is not rhetorical; it probes whether the feature is solving a real problem or merely exposing an implementation detail. The author will need to provide concrete scenarios (e.g., CI pipelines, automated scripts, or flaky networks) to justify the need for millisecond-level control.

Second, Junio identifies a behavioral ambiguity in the patch: the code silently ignores a zero value for `http.connectTimeoutMS`, but libcurl interprets zero as "use the default timeout." He suggests documenting what zero means and adjusting the condition to `0 <= curl_connect_timeout_ms` so that zero explicitly restores the default. This is a clear technical improvement that will prevent user confusion.

Third, he questions the necessity of a dedicated test script (`t5585-http-connect-timeout.sh`). Since the patch does not actually measure real-world timeout behavior (no stopwatch or mock server delays), the tests are effectively just parsing checks. Junio implies these could be folded into an existing HTTP test file, saving a scarce four-digit test number. The author will need to either justify the new script or refactor the tests.

The review also notes a minor procedural nit: the author’s real name should be used in the Signed-off-by trailer, per `Documentation/SubmittingPatches`.

Overall, the patch is well-structured but needs to address these points before it can be considered for merging. The maintainer’s feedback is constructive and focused on usability and resource management rather than implementation details.
