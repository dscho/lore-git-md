This is the fourth patch in Ted Nyman’s six-part v6 series fixing race conditions in Git’s HTTP transport when multiple processes concurrently fetch the same packfile URI or dumb HTTP pack. The series targets a real bug: concurrent downloads can corrupt the packfile by appending duplicate data. This patch implements the core fix.

The solution is simple and robust: instead of opening the staging file in append mode (which forces each write to the current end of the file), the code now opens it read-write without `O_APPEND` and seeks once to its current end. Because the staging key uniquely identifies immutable pack contents, overlapping responses write identical bytes at identical offsets, preserving resumable downloads while avoiding corruption. The patch also duplicates the staging descriptor for `index-pack` so that another downloader cannot unlink the staging path before indexing begins.

The commit message is clear and the code changes are minimal: 34 lines modified in `http.c` and 5 lines in the documentation to clarify the staging-key requirement. The test suite is expanded with a new 164-line test that exercises resumed transfers and overlapping 200/206 responses using a custom Perl server that reliably handles concurrent requests. The test is deterministic and passes 240 runs with 12 parallel stress jobs, giving high confidence the fix works.

This patch is well-crafted, thoroughly tested, and directly addresses the race condition without introducing new complexity. It is part of a larger series that has already addressed all technical feedback from earlier iterations, and it looks ready for `next`. If you care about HTTP transport reliability, this is worth reviewing.
