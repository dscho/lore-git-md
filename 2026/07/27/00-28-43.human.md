This is the sixth and final patch in Ted Nyman’s v6 series fixing race conditions in Git’s HTTP transport when multiple processes fetch the same packfile URI or dumb HTTP pack. The series as a whole is a well-motivated bugfix targeting a real corruption risk in concurrent downloads, and this patch rounds it out by making `fetch-pack` robust against pre-existing `.keep` files.

The patch teaches `fetch-pack` to accept both `"keep<TAB><hash>"` and `"pack<TAB><hash>"` output from `index-pack`. The former is emitted when the current process creates a `.keep` file; the latter when `index-pack` finds an existing one. The code now reads the prefix, validates the reported pack hash against the advertised hash, and only registers a keep lockfile if this fetch created it. A new test in `t/t5702-protocol-v2.sh` exercises the scenario: it pre-seeds a `.keep` file, runs the fetch, and verifies that the `.keep` file is preserved unchanged and the pack is still indexed correctly.

The change is small (33 lines in `fetch-pack.c`, 31 in the test) and surgical: it touches only the packfile-URI code path, leaving dumb HTTP and other fetch behaviors untouched. The commit message is clear and the test coverage is thorough. No new symbols are introduced, and the on-disk format is unchanged. This patch, like the rest of the series, is ready for review and looks uncontroversial.
