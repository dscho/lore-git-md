This is a **substantive review** of Hardik Kumar’s v3 refactoring patch, which changes the return type of UTF-8 string-width functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t`. Phillip Wood’s reply is a sharp critique of the patch’s fundamental approach, arguing that the change creates more problems than it solves.

Phillip’s core objection is that the patch forces callers to manually cast the `size_t` return value back to `int`—the exact type the patch aims to avoid—because nearly all callers (e.g., `printf()` padding calculations) expect `int`. The example from `builtin/blame.c` (`pad = longest_author - cast_size_t_to_int(utf8_strwidth(name))`) illustrates this: the patch replaces one implicit conversion with an explicit one, introducing potential bugs (e.g., underflow, mixed-sign comparisons) while adding no practical safety. Phillip calls this a "bug waiting to happen" and questions whether the conversions are even complete, noting that `builtin/worktree.c` still uses `utf8_strwidth()` with an `int` variable (`display[i].width`).

Beyond the immediate code, Phillip challenges the patch’s motivation. He suggests removing the TODO comment about returning `size_t` (added in a prior commit) and instead documenting why `int` is the correct choice for these functions. His argument hinges on the functions’ purpose: they measure display widths for terminal output, where `int` is sufficient (strings are rarely wider than `INT_MAX`), and the overhead of manual casts outweighs any theoretical type-safety benefit. He also flags the removal of the `cast_size_t_to_int()` overflow check as unjustified, echoing Pablo Sabater’s earlier concern.

The review is **blocking** and aligns with Junio’s prior skepticism about the patch’s value. Phillip’s feedback suggests the patch may need to be withdrawn or rethought entirely—either by abandoning the `size_t` change or by comprehensively refactoring callers to use `size_t` consistently (e.g., promoting struct fields like `stats_table.value_col_width` to `size_t`). For now, the patch remains **not ready for `next`**, with unresolved regressions and no clear path forward.
