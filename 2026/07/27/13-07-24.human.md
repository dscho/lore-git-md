This is the latest installment in the long-running `git replay --linearize` series, now at v7. Toon Claes responds to Elijah Newren’s critique of the current multi-branch behavior with a mix of technical analysis and design philosophy.

Toon acknowledges the core problem—when `--linearize` is used with multiple branches, the current implementation flattens everything into a single linear chain, making commits from one branch reachable from another in ways that weren’t true before. He agrees with Elijah that this violates the principle of least astonishment, especially around command-line order: if the user lists `branchA branchB branchC`, they expect the branches to remain independent, not concatenated. Toon’s example (a merge-heavy topology where `branchC` suddenly contains commits from `branchB`) crystallizes the issue.

The email explores two potential fixes. First, Toon suggests requiring `--ref` when `--linearize` is used, so the user explicitly names the single ref to update (`--ref branchA`). This would make the outcome unambiguous: all commits from the input branches are replayed linearly, but only the named ref is updated. Second, he floats the idea of replaying some commits twice to preserve branch independence, but dismisses it as impractical with the current machinery.

Toon’s tone is pragmatic. He concedes that `--linearize` is a niche feature (mostly for his own use case: server-side non-interactive rebase) and that the multi-branch ambiguity isn’t a showstopper for him personally. But he also accepts Elijah’s argument that erroring out on multiple positive refs is the safer interim step, keeping the door open for a more sophisticated per-branch linearization later. The email ends with a concrete proposal: forbid `--contained` with `--linearize` and require `--ref` to force a single output ref, which would sidestep the ambiguity entirely.

The ball is now back in Elijah’s and Junio’s courts to react to this `--ref`-based escape hatch. If they accept it, the series could graduate to `next` with minimal code changes; if not, the discussion will likely pivot to whether the current behavior is acceptable as-is or needs a deeper redesign.
