This is a **substantive technical discussion** in the ongoing ODB performance regression thread, specifically a reply from Justin Tobler (a key ODB contributor) endorsing and expanding on Patrick Steinhardt’s proposal to move alternates handling into the "files" backend.

Justin strongly supports Patrick’s architectural shift, calling it a "nice property" that the backend would control lookup ordering. He agrees that treating alternates as an implementation detail of the files backend better fits the design of commit graphs and other singletons, which are inherently tied to a single object store rather than spread across multiple sources. His feedback reinforces the proposal’s technical soundness, particularly around simplifying commit-graph and bitmap loading, which currently struggle with the cross-backend abstraction.

The email also introduces a forward-looking refinement: once all temporary object directory users (e.g., quarantine areas) are updated to use ODB transactions, the current practice of reordering the ODB source list during transactions could be eliminated. Instead, transactions would be tracked internally, and reads/writes would directly reference the transaction object without modifying the global source list. Justin plans to tackle this in a future series, suggesting this is a near-term priority rather than a distant goal. This refinement addresses a long-standing pain point in the ODB design—transaction isolation without disrupting the source list—and aligns with Patrick’s broader goal of simplifying alternates handling.

Justin’s only caveat is the loss of flexibility in supporting alternates of different source types (e.g., mixing files and non-files backends). However, he dismisses this as unlikely to be a practical concern, echoing Peff’s earlier assessment. The tone is collaborative and constructive, with Justin positioning his feedback as a natural extension of Patrick’s proposal rather than a critique.

For a busy reader, this email signals that Patrick’s proposal is gaining traction among the ODB subsystem’s core contributors. The discussion is now focused on *how* to implement the redesign, not *whether* it’s the right direction. The planned follow-up work on ODB transactions suggests the architectural changes will be incremental but coordinated, with Justin’s series likely landing soon after Patrick’s initial patches. The regression’s resolution appears to be converging on this broader cleanup, though a near-term fix may still be needed to address immediate performance pain.
