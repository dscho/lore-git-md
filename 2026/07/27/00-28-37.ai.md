This is a v6 reroll of Ted Nyman’s packfile URI race-condition fix series, now expanded to six patches. The core goal remains unchanged—preventing corruption during concurrent HTTP downloads of the same packfile—but the implementation is now split into smaller, more focused commits for clarity. The series is still a bugfix targeting Git’s HTTP transport, specifically the packfile URI and dumb HTTP download paths.

The key technical insight is the same as in v5: deterministic staging paths opened in read-write mode (without append) ensure that overlapping responses write identical bytes at identical offsets, preserving resumable downloads while avoiding corruption. However, v6 breaks the monolithic v5 patch 2 into four separate commits, each addressing one of Peff’s post-acceptance advisory points: a latent double-close bug, HTTP 416 handling for completed partial packs, the generic concurrent-download fix, and the Windows/MINGW sharing requirement. The final two patches (the Windows sharing fix and the `.keep` file race handling) remain unchanged from v5.

The new structure makes the series easier to review and bisect. Patch 2 fixes a double-close in `finish_http_pack_request()` where `start_command()` already takes ownership of the staging-file descriptor. Patch 3 adds HTTP 416 handling for the case where a previous attempt completes the transfer but fails before indexing it. Patch 4 implements the core concurrent-download fix, and Patch 5 handles the Windows-specific sharing semantics. The test suite is expanded with a new standalone test for completed partial packs (replacing the FIFO-based concurrent HTTP 416 test) and retains the overlapping-download test, which still passes 240 runs with 12 parallel stress jobs.

Files touched include `http.c`, `fetch-pack.c`, and their documentation, with new regression tests in `t/t5550-http-fetch-dumb.sh` and `t/t5702-protocol-v2.sh`. The implementation remains platform-compatible, handling MinGW’s non-append O_RDWR open behavior and Windows sharing semantics. The `.keep` file handling in `fetch-pack` is still robust, validating the pack hash and only registering a keep lockfile when the current process created it.

No open technical questions remain, and the series is rebased onto current `master`. The changes are narrowly scoped to the packfile URI and dumb HTTP download paths, with no impact on other HTTP fetch behaviors or on-disk formats. The series is ready for review and likely to progress to `next` soon.
