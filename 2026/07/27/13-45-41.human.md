This is a refactoring patch targeting Git’s revision-walking machinery, specifically the `get_commit_action()` function in `revision.c`. The patch has just been queued by Junio C Hamano after a thorough review and discussion. It addresses a subtle but important impurity in the function: while `get_commit_action()` is nominally a predicate that decides whether a commit should be shown or ignored, it also mutates tracked line ranges when used with `git log -L` (line-level log) without parent rewriting. This side effect violates the function’s intended purity and could cause issues for future callers, such as the in-flight commit graph feature, which assumes the function is side-effect-free.

The patch moves the line-range mutation logic from `get_commit_action()` to `simplify_commit()`, where it runs before the predicate check. A new helper function, `commit_early_ignore()`, is introduced to factor out the cheap checks (e.g., whether the commit is already shown or marked uninteresting) that gate both the mutation and the predicate. This ensures that commits ignored by those checks are not processed unnecessarily, preserving the original behavior while making `get_commit_action()` a pure predicate. The patch also includes a new test subcommand, `line-log-peek`, added to the `test-revision-walking` helper, which verifies that `get_commit_action()` does not mutate commit flags when called out-of-order.

Junio’s review confirms that the patch is well-structured and correctly implements the intended refactoring. He notes that while the `commit_early_ignore()` logic runs twice on the `-L` path, the duplication is harmless because it only reads object flags and pack membership, which are disjoint from the flags modified by the line-range tracking. The patch is framed as a **bugfix refactoring**—defensive programming to preemptively close a correctness risk in core machinery—and Junio has accepted this rationale, resolving the initial question about the patch’s motivation.

The patch touches `revision.c`, `test-revision-walking.c`, and `t4211-line-log.sh`, and while it is over 100 lines long, the changes are mechanical and localized. There are no user-visible behavior changes, but the refactoring makes the code safer for future extensions, such as lookahead optimizations or out-of-order evaluation in the revision walk. The patch is now queued for integration, pending broader consensus on the trade-off between its size and its value as a preemptive fix for a latent bug in core machinery.
