This is a feature patch introducing `git stash reword`, the second iteration of a new subcommand that allows users to edit stash messages after creation. The patch is part of a thread that has already established strong justification for the feature, based on user reports of workflow pain with large numbers of stashes carrying default "WIP on <branch>" messages.

The implementation is now fully transactional: it reads the entire reflog, rewrites it in a single `ref_transaction`, and commits the change atomically. This addresses the two major concerns raised in the first version: the non-atomic drop-and-re-store sequence (which risked data loss on failure) and the quadratic runtime cost for deep stashes (which was especially problematic under the reftable backend). The command rejects time-based selectors (`stash@{yesterday}`) to avoid race conditions and only accepts index-based selectors (`stash@{1}`), which are stable during the rewrite.

Key technical details for follow-up discussion:
- The command uses `ref_transaction_update_reflog` to rewrite the reflog in one step, preserving timestamps, order, and object IDs for all entries except the target.
- It includes a best-effort recovery path: if the transaction fails, it reports the object IDs of any entries it could not re-store, allowing manual recovery with `git stash store`.
- The implementation is backend-agnostic and passes tests with both the files and reftable backends.
- Tests cover edge cases: rewording the deepest entry, empty messages, invalid arguments, and non-stash reflog entries.
- The subcommand integrates with the existing stash infrastructure, supports `--quiet`, and is added to bash completion.

The patch is well-motivated, thoroughly tested, and addresses all substantive review feedback from the first version. The transactional rewrite is a significant improvement over the initial approach and should resolve the performance and atomicity concerns that were raised. The only remaining open question is whether Junio’s broader design suggestion—tying stashes to individual branches—might eventually subsume this feature, but that is a long-term consideration and not a blocker for this patch.
