This is the third patch in Ted Nyman’s six-part v6 series fixing race conditions in Git’s HTTP transport when multiple processes concurrently fetch the same packfile. The series targets a real and subtle bug: concurrent downloads of the same packfile URI or dumb HTTP pack can corrupt the object database unless all processes write identical bytes at identical offsets.

This specific patch addresses a corner case in resumable downloads: when a previous attempt has already completed the transfer but failed before indexing the pack, a subsequent request for the same pack will ask the server for a byte range that is no longer available. The server responds with HTTP 416 (“Requested Range Not Satisfiable”), which Git previously treated as an error. The patch teaches the three HTTP pack-download callers (`http-fetch.c`, `http-push.c`, `http-walker.c`) to accept HTTP 416 as a success signal and let `index-pack` validate the already-complete staging file. A new regression test in `t/t5550-http-fetch-dumb.sh` seeds a complete partial pack and verifies that `http-fetch` indexes it after receiving HTTP 416.

The change is minimal and surgical: three one-line conditionals that add `&& results.http_code != 416` to the existing `CURLE_OK` checks. The commit message clearly explains the scenario (“a previous attempt completed the transfer but failed before indexing it”) and the fix’s effect (“let index-pack validate the completed staging file”). The test is deterministic and uses the existing Perl HTTP server, so it should be reliable in CI.

This patch is part of the series’ overall strategy of preserving resumable downloads while preventing corruption. It was split out from the larger v5 patch 2 after Peff identified HTTP 416 handling as one of four advisory points that deserved its own commit. The split improves bisectability and makes the series easier to review. No open questions remain; the patch is ready for review and looks well-crafted.
