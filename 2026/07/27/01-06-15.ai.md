This is a **substantive review** of Hardik Kumar’s v2 refactoring patch, which changes the return type of UTF-8 string-width functions (`utf8_strwidth()` and `utf8_strnwidth()`) from `int` to `size_t`. Pablo Sabater’s review identifies **multiple new type-safety regressions** introduced by the v2 changes, blocking the patch from proceeding until they are fixed.

The core issue is that while the v2 patch updates all callers to use `size_t` for local variables holding the return value (addressing the v1 compatibility concerns), it **fails to account for mixed-sign comparisons and unsigned underflow** in several key code paths. Pablo’s review highlights three major problem areas:

1. **`builtin/blame.c`**: The `num` variable (now `size_t`) is compared against `int` variables (`longest_file`, `longest_author`, etc.), triggering `-Wsign-compare` errors under `DEVELOPER=1`. Pablo suggests splitting `num` into separate variables to avoid reusing it for incompatible types (e.g., `strlen()` vs. `utf8_strwidth()` vs. line counts).

2. **`diff.c`**: The `len` variable (now `size_t`) is decremented by 3 in a path where it could underflow (e.g., `len -= 3` when `len < 3`), breaking the existing safeguard. Pablo proposes rewriting the logic to avoid unsigned underflow and ensuring consistent types for `name_len` and `len`.

3. **`pretty.c`**: The `occupied` variable (now `size_t`) is compared against `padding` (still `int`), leading to incorrect padding calculations. Pablo recommends keeping `len` and `occupied` as `int` and casting the `utf8_strwidth()` results instead.

Additional issues include:
- **`column.c`**: The `item_length()` function’s return type change is unnecessary, as its sole caller stores the result in an `int*`.
- **`gettext.h`**: The `gettext_width()` signature change is not mirrored in the `#else` branch, breaking the build when `NO_GETTEXT` is defined.
- **`wt-status.c`**: The `maxwidth()` function should also return `size_t` to avoid narrowing conversions, and the `len` calculation should explicitly check for underflow.

Pablo also critiques the commit message’s technical accuracy (e.g., "implicit conversion from `size_t` to `int` is not undefined behavior") and suggests a more concise title. His feedback is **high-weight and blocking**: the patch cannot proceed to `next` until these regressions are fixed. The unresolved overflow check question from v1 (whether any callers relied on `cast_size_t_to_int()`’s overflow check) remains unaddressed, but the immediate focus is on the new type-safety bugs.

Hardik will need to send a v3 to resolve these issues. The review is thorough and constructive, with Pablo providing specific code snippets to guide the fixes.
