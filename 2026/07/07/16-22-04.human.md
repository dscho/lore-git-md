This is the fourth patch in Jeff King’s seven-patch series refactoring the `git_hash_*()` API to make it more robust. Junio C Hamano’s reply is a light but thoughtful review that homes in on a single design question: why only `git_hash_discard()` is made idempotent, while `git_hash_final()` and `git_hash_final_oid()` are not.

Junio’s concern is practical. He notes that the lockfile API (`commit_lock_file()` vs `rollback_lock_file()`) uses distinct names to signal happy-path vs error-path usage, whereas the hash API’s `_final()` and `_discard()` names are less self-documenting. He then asks whether the asymmetry—protecting only `_discard()`—is intentional, or if it simply reflects that `_final()` is already a no-op when called twice. The question is not a blocker, but it does invite the author to clarify the reasoning in the commit message or documentation.

The patch itself remains uncontroversial. It adds a seven-line `active` flag to the `git_hash_ctx` struct, making `_discard()` safe to call multiple times. This is a classic defensive-programming move that will let callers unconditionally discard in error paths without tracking state. No behavior changes are expected for end users, and the patch is small enough that the risk of introducing bugs is minimal. Junio’s feedback is purely about clarity, not correctness.
