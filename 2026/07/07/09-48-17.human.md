This is a **substantive review follow-up** in the `git history squash` series, where Phillip Wood responds to Harald Nordgren’s latest email with detailed technical feedback on three unresolved design questions: default behavior, template formatting, and input validation.

Phillip **reiterates his concern** about making `--reedit-message` the default, noting that the earlier discussion was left unresolved. The series currently treats `--reedit-message` as opt-in, which may conflict with `git rebase -i`’s precedent of defaulting to interactive message editing.

On **template formatting**, Phillip **welcomes Harald’s willingness to explore reordering commits** to place `fixup!`/`squash!`/`amend!` markers after their targets (matching `git rebase -i`’s autosquash behavior). His guidance is pragmatic: if this isn’t addressed in v8, the cover letter should explicitly state it’s deferred. The current implementation’s lack of reordering could make the template confusing when multiple commits target the same base, and Phillip’s examples (e.g., `fixup! fixup! the real target`) highlight the complexity of handling nested markers.

The **input validation gap** receives the most attention. Phillip **expands on Harald’s admission** that `reject_fixupish_oldest()` needs to check all commits in the range (not just the oldest) and verify whether marker targets lie within the range. His proposal is nuanced:
- If the **first commit is a `fixup!`**, allow squashing other fixups with the same target, using the message from the last `amend!` commit if present.
- If the **first commit is not a `fixup!`**, reject any `fixup!` commit whose target hasn’t been seen in the range.
- Support **exact subject matches** and `$objectid` references (e.g., `fixup! abc1234`), with the latter being important for `git-gui` compatibility.
- Handle **nested markers** like `fixup! fixup! the real target`.

This would address edge cases where a `fixup!` commit’s target lies outside the squashed range, but Phillip acknowledges the added complexity. His suggestions are grounded in existing `git rebase -i` logic, making them actionable for v8.
