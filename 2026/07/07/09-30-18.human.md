This is a **substantive review follow-up** in the ongoing `git history squash` series. Phillip Wood responds to Harald Nordgren’s claim that the code already blocks problematic `rev-list` options like `--reverse`. Phillip points out a critical oversight: the command currently **accepts `--reverse` (and other options) when passed after a double-dash (`--`)** because `parse_options()` stops parsing at `--` and forwards everything afterward to `setup_revisions()`. This means a user could write `git history squash -- --reverse HEAD~3..HEAD`, which would silently resolve the range in reverse order, producing an incorrect parent for the squashed commit.

Phillip’s review is **technically precise and actionable**. He references `git replay`’s approach as a model for robust input validation: `git replay` uses `PARSE_OPT_KEEP_ARGV0 | PARSE_OPT_KEEP_UNKNOWN_OPT` to defer option parsing to `setup_revisions()`, then **explicitly checks the resolved `rev_info` structure** to ensure the range meets its requirements. He also criticizes the **cover letter’s lack of clarity** about which prior suggestions were adopted or rejected, making it difficult for readers to track the series’ evolution.

The email does not propose new design changes but **reinforces the need for stricter input validation** in the next iteration. The unresolved question—whether to adopt `git replay`’s full validation approach or a lighter-weight alternative—remains open.
