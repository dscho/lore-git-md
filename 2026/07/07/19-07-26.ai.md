This is the second patch in the v7 series introducing `--linearize` to `git replay`. It refactors the replay base resolution logic, moving it from `pick_regular_commit()` to `replay_revisions()` to improve clarity and reduce the number of parameters passed to `pick_regular_commit()`.

The patch consolidates all base-selection logic in `replay_revisions()`, where it now explicitly determines the replay base for each commit by checking the `replayed_commits` map for the replayed parent or falling back to `onto` (or `last_commit` when reverting). This eliminates the previous split logic, where `pick_regular_commit()` handled part of the decision-making. The change reduces `pick_regular_commit()`'s parameters from five to four, simplifying its interface.

The refactoring is purely internal and introduces no behavior changes. It prepares the ground for the `--linearize` implementation in patch 3/3 by making the base resolution more explicit and easier to modify. The commit message explains the motivation clearly: bundling the base-selection logic in one place improves maintainability and reduces confusion about where the replay base is determined.

This patch has been stable since v5 and has received no substantive objections. It is a clean, well-motivated refactoring that aligns with the series' goal of making the replay machinery more modular. The diff is focused and easy to review, touching only `replay.c` and introducing no new edge cases. The helper functions introduced in patch 1/3 (`put_mapped_commit` and `get_mapped_commit`) are used here to maintain consistency in how replayed commits are tracked.
