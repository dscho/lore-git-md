This is a bug report from SZEDER Gábor describing an unexpected full download during an incremental `git fetch`. The report is substantive: Gábor observed that a routine fetch from GitHub's mirror of `git/git` downloaded over 400,000 objects (~300 MiB) despite the vast majority of those objects already being present locally. He provides detailed reproduction steps (rev-list, verify-pack, diff) showing that only ~1,400 objects were actually new, yet the fetch transferred the entire set. He notes this may be a recurring issue but was unable to reproduce it in a fresh clone, suggesting a state-dependent bug in the object negotiation or packfile generation logic.

Key technical details: the forced updates on `jch`, `next`, and `seen` branches indicate upstream rewinds, but Gábor’s analysis shows the downloaded packfile contained mostly objects already in his local repository. The discrepancy between `existing-objects` and `received-objects` (3615 differing lines) points to a negotiation failure rather than a legitimate need for a full refetch. No custom fetch or transfer configuration was in use, and the issue occurred with a `next`-based build, ruling out local patches as the cause.

The report is credible and well-documented, with clear evidence of a performance regression in incremental fetch behavior. The inability to reproduce in a fresh clone suggests the bug may depend on repository state (e.g., object database layout, ref history) or server-side packfile generation. This is likely to attract attention from maintainers of the fetch/pack subsystem, particularly those working on object negotiation (e.g., Patrick Steinhardt, Jeff King, or Taylor Blau). The forced updates on integration branches (`jch`, `next`, `seen`) may be a contributing factor, but the core issue appears to be a failure to filter already-present objects during packfile construction.
