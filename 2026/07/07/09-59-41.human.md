This is a bugfix for the commit-graph subsystem, part of a two-patch series that addresses a performance regression in incremental commit-graph writes.

The issue stems from a refactoring in commit 199d452758 (April 2025) that introduced a loop variable but failed to use it consistently. The bug causes the `topo_levels` slab to be assigned only to the topmost layer of a split commit-graph chain, rather than to every layer. As a result, when Git reads commits from lower layers during an incremental write, it sees zero generation numbers and re-walks the entire ancestry of those commits—turning what should be an O(new commits) operation into an O(all commits) one.

The cover letter reports a dramatic real-world impact: on a large repository with a four-layer split commit-graph, incremental writes slowed from 233 ms to 4133 ms. This directly affects every `git fetch` when `fetch.writeCommitGraph` is enabled or when `git maintenance` runs afterward. The fix itself is a one-line change in `commit-graph.c` that replaces `g->topo_levels` with `chain->topo_levels` in the loop body.

Patch 1 adds trace2 instrumentation to help diagnose similar issues in the future; patch 2 contains the actual fix. The series includes a new test in `t/t5324-split-commit-graph.sh` that verifies the slab is correctly propagated to all layers. The commit message is clear and thorough, naming the regressing commit, explaining the root cause, and quantifying the performance impact. This looks like a well-motivated, narrowly scoped fix that should be uncontroversial.
