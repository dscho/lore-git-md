This is the v7 iteration of a feature addition that teaches `git replay` a `--linearize` option to flatten merge commits into a linear history. The series is now **technically complete** and addresses all prior feedback, including a key behavioral fix and interface adjustments.

The most significant change in v7 is the **removal of the mutual exclusivity between `--linearize` and `--revert`**, allowing them to be used together. This resolves Junio C Hamano’s earlier documentation concern by eliminating the need to justify or document the incompatibility. The author also updated the commit authorship for the final patch to reflect the extensive changes since Johannes Schindelin’s original contribution, with Schindelin’s blessing.

The series consists of three patches: two refactoring patches (adding a helper function and consolidating base-selection logic) and the core implementation. The `--linearize` option now works predictably when replaying multiple branches or a single branch containing merges, ensuring all commits are flattened into a single linear topology. The commit message and documentation have been expanded to clarify the behavioral difference from `git rebase --no-rebase-merges`, and test coverage is thorough, including scenarios for `--revert`/`--linearize` compatibility and edge cases like replaying to the root commit.

The interface design debate—whether to mirror `git rebase`'s `--rebase-merges=<mode>` syntax—remains unresolved but is no longer blocking. The series continues to use `--linearize` as a standalone flag, with the commit message justifying the divergence as a deliberate choice to avoid repeating past UX mistakes. The series is ready for review, with no unresolved technical objections. Potential trivial conflicts with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series are noted but expected to be minor.
