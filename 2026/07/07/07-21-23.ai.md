This is the fourth patch in Patrick Steinhardt’s 13-patch **refactoring series** to separate repository discovery from setup in Git’s core code. The patch **splits `setup_git_env_internal()` into two distinct functions**, addressing a long-standing design issue where the function conflated two unrelated responsibilities: configuring the repository’s gitdir and propagating environment variables, versus setting global parameters.

The core change moves the global environment setup (e.g., `NO_REPLACE_OBJECTS`, `GIT_REPLACE_REF_BASE`, `NO_LAZY_FETCH`) into a new `setup_environment()` function, which is called once during `init_git()`. This ensures global state is initialized only once, rather than being reapplied unnecessarily during `chdir` notifications. The gitdir-specific logic is retained in `setup.c` as `apply_gitdir_and_environment()`, which now focuses solely on repository-local configuration (e.g., `GIT_COMMON_DIR`, `GRAFT_ENVIRONMENT`, `INDEX_ENVIRONMENT`).

The patch touches `common-init.c` (adding `setup_environment()`) and `setup.c` (renaming `setup_git_env_internal()` to `apply_gitdir_and_environment()` and updating callers). It also introduces a new helper, `apply_and_export_relative_gitdir()`, to consolidate gitdir export logic previously scattered across `set_git_dir()` and `set_git_dir_1()`. The diff is mechanical but extensive, with 45 lines removed and 20 added, reflecting the refactoring’s goal of clearer separation of concerns.

No behavior changes are intended, and the patch preserves existing environment variable precedence (e.g., `GIT_DIR` overrides). However, the split may expose edge cases in callers that relied on the implicit reapplication of global state during `chdir` notifications. The patch does not introduce new tests, relying on existing coverage (e.g., `t1510-repo-setup.sh`) to verify correctness.

This refactoring is a foundational step for later patches in the series, particularly those introducing `struct repo_discovery` (patches 6–10/13). By isolating global state setup, it reduces the risk of unintended side effects when repository configuration is consolidated into `repo_init()`. The patch aligns with the series’ broader architectural goals, though it does not yet enforce single-application semantics for repository configuration (a forward-looking concern raised in patch 5/13).
