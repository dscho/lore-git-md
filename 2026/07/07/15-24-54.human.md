This is the second patch in Patrick Steinhardt’s two-patch series fixing a quadratic performance regression in Git’s reftable backend. The series targets a real, measurable slowdown (15 seconds for 8 000 refs) that occurs when recreating refs after deletion, and this patch removes the root cause: the `suppress_deletions` flag in the merged iterator. By pushing tombstone handling out to the call sites—where prefix and refname bounds are already known—the patch restores O(1) behavior for the two hot paths (`refs_verify_refnames_available` and `reftable_backend_read_ref`) and cuts the runtime to 0.2 seconds in the same scenario.

Patrick’s reply is a substantive review that also surfaces a compatibility concern: the `suppress_deletions` flag is still used by downstream projects like libgit2, so simply deleting it would break them. The patch as written already addresses this by keeping the flag in the API but removing its internal use, so libgit2’s callers continue to work while Git’s own code paths benefit from the performance fix. He also confirms that every ref and log iteration site has been updated to handle tombstones explicitly, ensuring no regressions elsewhere in the backend.

The patch itself is narrowly scoped to the reftable backend and does not attempt broader refactoring. It touches four files (`refs/reftable-backend.c`, `reftable/merged.{c,h}`, and `reftable/stack.c`) and introduces no new symbols or on-disk format changes. Test coverage is already in place via the first patch in the series, which adds both a performance test (`p1401-ref-store-tombstones.sh`) and a correctness test (`t0610-reftable-basics.sh`). The commit message links to prior discussion with Jeff King and a lore thread, providing clear context for the regression’s discovery and the fix’s rationale.

This looks like a well-crafted, focused bugfix that addresses a real performance pain point without risking broader instability. The compatibility concern Patrick raises is already mitigated in the patch, and his review suggests the series is nearly ready to merge. If you care about reftable performance or are tracking the backend’s evolution, this patch is worth a quick look.
