This is the fifth patch in Patrick Steinhardt’s 13-patch refactoring series to separate repository discovery from setup in Git’s core code. The series is part of a larger effort to clean up `setup.c` and consolidate repository configuration into `repo_init()`.

This patch introduces a new `struct repo_discovery` to hold the results of repository discovery (gitdir and worktree paths). It refactors the existing setup logic to populate this structure during the discovery phase, rather than partially configuring the repository object (`struct repository`) as it goes. The goal is to make the discovery phase self-contained, so that repository configuration can later be applied in a single step. Key changes include:
- Renaming `setup_explicit_git_dir()`, `setup_discovered_git_dir()`, and `setup_bare_git_dir()` to `repo_discover_explicit_gitdir()`, `repo_discover_implicit_gitdir()`, and `repo_discover_bare_gitdir()`, respectively, to better reflect their new role.
- Introducing helper functions (`repo_discovery_set_gitdir()`, `repo_discovery_set_worktree()`) to manage the `struct repo_discovery` fields.
- Replacing direct calls to `set_git_work_tree()` and `apply_and_export_relative_gitdir()` with updates to the `repo_discovery` structure.
- Updating `setup_git_directory_gently()` to use the new discovery functions and apply the results to the repository object at the end.

The patch is mechanical and does not change behavior. It lays the groundwork for later patches (e.g., patch 10/13, which introduces `repo_discover()`) to fully separate discovery from setup. Justin Tobler’s substantive review of this patch affirmed the architectural direction but raised a forward-looking question about whether `struct repo_discovery` should enforce single-application semantics (i.e., applying repository configuration more than once should be treated as a bug). Patrick Steinhardt’s reply confirmed this is the intended future direction but noted it is not enforced in this patch.

The patch touches only `setup.c` and is well-explained in the commit message. It is a clear step toward the series’ goal of making repository setup more modular and easier to reason about. If the series lands, this patch will be a key enabler for consolidating setup logic into `repo_init()`. For now, it is a safe refactoring with no user-visible impact.
