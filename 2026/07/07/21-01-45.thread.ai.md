Subject: [PATCH v2] unpack-trees: fix quadratic-time index scan in `next_cache_entry()`
Series version: standalone patch, v2
Originating author: Henrique Ferreiro (via GitGitGadget)
Thread type: performance bugfix

Core problem or goal
Eliminate a quadratic-time index scan in `next_cache_entry()` triggered when `git diff` is run with a pathspec matching a subtree whose entries appear early in the index. The fix introduces a `cache_bottom` field in `o->internal` to track forward-scan progress, allowing subsequent calls to skip already-unpacked entries.

Current status
Under review; v2 posted in response to Junio’s substantive review. The patch remains self-contained (4 lines in `unpack-trees.c`) and includes a perf regression test (`t/perf/p0009-diff-pathspec.sh`). Junio’s primary concern—whether the new `cache_bottom` optimization interacts safely with the existing `.cache_bottom` logic (designed to handle index/tree ordering mismatches)—is now addressed by Henrique’s argument that `find_cache_pos()` already advances `.cache_bottom` past unpacked entries (citing commit `e53e6b4433`). The perf test still needs to scale entry count via the `EXPENSIVE` prerequisite, as suggested by Junio.

Key technical details
- **File modified**: `unpack-trees.c`
- **Function modified**: `next_cache_entry()`
- **New field**: `o->internal.cache_bottom` (tracks forward-scan progress)
- **Existing field**: `o->cache_bottom` (handles backward scans and ordering mismatches)
- **Test added**: `t/perf/p0009-diff-pathspec.sh` (creates 100k-entry index with problematic layout; entry count should be configurable via `EXPENSIVE`)
- **Benchmark**: 100k-entry index, pathspec `aaa/file` as first entry, command `git diff HEAD -- <pathspec>`
- **Performance improvement**: 8 minutes → 0.07 seconds (99.7% speedup) on Chromium-scale repo (~500k index entries)
- **Base commit**: `e90019fcafe0040228b8631c30f97ae1adb61bcd`
- **Core concern**: interaction between forward-scan optimization (`cache_bottom`) and existing backward-scan logic (`.cache_bottom`), now argued to be safe due to `find_cache_pos()` behavior
