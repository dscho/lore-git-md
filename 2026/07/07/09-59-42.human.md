This is the first patch in a two-part bugfix series targeting a performance regression in Git's commit-graph subsystem. The patch adds trace2 instrumentation to `compute_reachable_generation_numbers()` to expose the cost of the generation-number depth-first search (DFS). This diagnostic tool reveals a regression introduced in April 2025 (commit 199d452758) where incremental commit-graph writes unnecessarily re-walk the entire commit ancestry instead of reading topological levels from lower layers in a split commit-graph chain.

The instrumentation itself is straightforward: a step counter tracks how many commits the DFS visits, and a `trace2_data_intmax` call logs the total steps. The accompanying test in `t/t5324-split-commit-graph.sh` demonstrates the problem by creating a two-layer split commit-graph, then writing an incremental layer for a commit whose parent exists in the base layer. The test expects the DFS to take only one step (reading the existing topological level) but currently observes seven steps (walking all the way to the root).

This patch doesn’t fix the bug—it merely makes the regression observable. The fix itself will come in the second patch, which corrects the loop variable in the propagation logic. The instrumentation is well-motivated and narrowly scoped, providing a clear diagnostic hook for future performance investigations. The test is minimal but effective, and the commit message clearly explains the regression’s impact and context. This looks like a thoughtful, uncontroversial contribution that should help reviewers verify the fix in the next patch.
