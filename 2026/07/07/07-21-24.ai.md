This is **patch 5/13 in Patrick Steinhardt’s v2 refactoring series** to split repository discovery from setup in Git’s core code. The patch introduces `struct repo_discovery`, a new data structure that holds the results of repository discovery (gitdir and worktree paths) without partially configuring the repository. This is a foundational step toward consolidating repository setup into `repo_init()`.

The patch mechanically extracts the discovery logic from `setup_explicit_git_dir()`, `setup_discovered_git_dir()`, and `setup_bare_git_dir()` into three new functions: `repo_discover_explicit_gitdir()`, `repo_discover_implicit_gitdir()`, and `repo_discover_bare_gitdir()`. These functions populate a `struct repo_discovery` instead of directly calling `set_git_work_tree()` or `apply_and_export_relative_gitdir()`. The discovery phase is now self-contained, and the results are applied to the repository in a single place (`setup_git_directory_gently()`), eliminating the scattered partial configuration that previously made the code hard to follow.

Key changes:
- **New symbols**: `struct repo_discovery`, `REPO_DISCOVERY_INIT`, `repo_discovery_release()`, `repo_discovery_set_gitdir()`, `repo_discovery_set_worktree()`, and the three `repo_discover_*` functions.
- **Renamed functions**: `setup_git_directory_gently_1()` is renamed to `repo_discovery_find_dir()` to better reflect its role in the discovery phase.
- **Behavioral invariant**: The patch introduces the idea that applying repository configuration more than once (via `struct repo_discovery`) should be treated as a bug, though it does not enforce this yet. This aligns with the series’ goal of consolidating setup into `repo_init()`.
- **Files touched**: Only `setup.c` (155 lines changed, 98 insertions, 57 deletions).

Justin Tobler’s **substantive review** of this patch affirmed the architectural direction and raised a forward-looking question about single-application semantics for `struct repo_discovery`. Patrick Steinhardt’s reply confirmed the invariant is a future goal ("future music") rather than an immediate requirement, implying the current patch is a stepping stone.

The patch is **well-motivated and cleanly executed**, with no intended behavior changes. It lays the groundwork for later patches in the series (e.g., moving the prefix to `struct repository` in patch 7/13) and aligns with ongoing efforts like `the_repository` removal and ODB abstraction. The main risk is whether the new function boundaries handle edge cases like environment variable overrides, gitdir changes during `chdir` notifications, and prefix/worktree path computation (e.g., symlinks, relative paths). The removal of partial configuration may expose lifetime issues in callers that previously relied on implicit state.
