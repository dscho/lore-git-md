This thread is about a performance bugfix for `git diff` that eliminates a quadratic-time index scan in `next_cache_entry()` when using a pathspec matching a subtree with entries early in the index. Henrique Ferreiro proposed a minimal 4-line patch introducing a `cache_bottom` field to track scan progress, achieving a 99.7% speedup (from 8 minutes to 0.07 seconds) on Chromium-scale repositories. The patch includes a thorough performance test but is currently blocked on a critical correctness concern raised by Junio Hamano: whether the new forward-scan optimization interacts safely with the existing `.cache_bottom` logic, which handles index/tree ordering mismatches.

Henrique has responded to Junio’s review, arguing the optimization is safe because the existing logic already advances `.cache_bottom` past unpacked entries. The patch is now in its second iteration, with the core correctness question still unresolved. Junio also suggested a minor test improvement (making the entry count configurable via the `EXPENSIVE` prerequisite), which hasn’t been addressed yet. The fix targets a real-world pain point and is well-motivated, but its readiness depends on confirming the ordering invariants hold. If validated, it’s likely to land quickly.
