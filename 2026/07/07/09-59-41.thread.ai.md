Thread identity: bugfix series for commit-graph regression in split commit-graph chains; 2 patches; originating author Kristofer Karlsson; thread type: patch series (now post-merge discussion on patch presentation style).

Core problem or goal: fix a performance regression in the commit-graph subsystem introduced by commit `199d452758` (September 2025) in the `ps/commit-graph-via-source` series, where the `topo_levels` slab was incorrectly propagated only to the topmost layer of a split commit-graph chain, degrading incremental commit-graph write performance from 233ms to 4133ms on large repositories with deep split graphs.

Current status: merged to `master` as of the v2 series. The v2 reroll addressed Junio C Hamano’s clarification request (correcting the commit-message date from April 2025 to September 2025) and included a cleaner test assertion in `t/t5324-split-commit-graph.sh`. The discussion remains stylistic and non-blocking; no further code changes are required or proposed.

Key technical details:
- Files touched: `commit-graph.c`, `t/t5324-split-commit-graph.sh`.
- Subsystem: commit-graph (split commit-graph chains).
- New symbols: trace2 instrumentation in `compute_reachable_generation_numbers()` (step counter, `trace2_data_intmax` call).
- Old behavior: `topo_levels` slab propagated only to topmost layer of split commit-graph chain; incremental writes re-walk entire commit ancestry via DFS.
- New behavior (after patch 2/2): `topo_levels` slab correctly propagated to all layers; DFS stops early when topological levels are available, restoring original performance.
- On-disk format: no changes.
- Test coverage: updated test in `t/t5324-split-commit-graph.sh` uses `test_expect_failure` in patch 1/2 and flips to `test_expect_success` in patch 2/2 to verify the fix (1 DFS step expected after patch 2/2). - Affected workflows: users with `fetch.writeCommitGraph` enabled or running `git maintenance` after fetch.

Open questions and loose ends: none for the immediate fix.
