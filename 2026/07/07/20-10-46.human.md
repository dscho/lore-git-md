This is the author's reply to Junio's design question about the final patch in Peff's seven-patch series hardening the `git_hash_*()` API. The series aims to make the API more robust by adding runtime checks to catch misuse early, particularly around the idempotency of `git_hash_discard()` and the handling of inactive hash contexts.

Peff clarifies the reasoning behind the asymmetry Junio noted: `git_hash_final()` is disallowed after itself or after `git_hash_discard()` because it attempts to *do* something (compute a hash), whereas `git_hash_discard()` is a no-op cleanup. He argues that calling `git_hash_final()` on an already-discarded or finalized context is almost certainly a bug, and triggering a `BUG()` is the safest response. The alternative—returning a null or empty hash—would silently mask programming errors, which is worse than failing loudly. Peff points to an earlier discussion in the thread for more context but summarizes the key point: loosening the restriction later is always possible, but tightening it after merging would be disruptive.

The reply does not introduce new code or propose changes to the patch; it is purely a design rationale. The series remains ready for integration, with only minor cosmetic nits outstanding from earlier reviews. Junio's question was the last open design point, and Peff's response provides the missing justification—whether Junio finds it convincing will determine if the patch moves forward unchanged or requires a tweak to enforce symmetry.
