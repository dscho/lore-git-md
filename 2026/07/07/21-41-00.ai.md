Carlson provides deep technical context about why hash libraries universally treat multiple calls to the finalization function (`git_hash_final()`) as a bug, contrasting it with the idempotent behavior now being introduced for `git_hash_discard()`.

The email explains the internal mechanics of SHA-256 (and SHA-1) contexts: they contain state words, a bit/byte counter, and a buffer for unprocessed data. Finalization requires padding with `0x80`, zero bytes, and the message length, which updates the state in place. Calling `final()` a second time re-pads the already-finalized context, producing a corrupt hash value—effectively a length-extension attack for SHA-256. This behavior is intrinsic to Merkle-Damgård constructions and is why most hash libraries free memory during finalization and treat subsequent calls as errors.

Brian also highlights how Rust’s ownership model enforces this invariant: the `final()` method consumes `self`, making it impossible to call twice. This reinforces the design choice in Jeff King’s patch to leave `git_hash_final()` unprotected (triggering a `BUG()` on misuse) while making `git_hash_discard()` idempotent for safer cleanup.

The comment does not propose changes to the patch but provides authoritative backing for its asymmetry. It resolves any lingering doubt about whether `git_hash_final()` should also be made idempotent, confirming that the current approach aligns with industry-standard practice.
