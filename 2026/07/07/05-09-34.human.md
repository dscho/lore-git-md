This is a user experience report from Dominique Martinet about the experimental `git history` commands, specifically `reword` and `fixup`. The email highlights a practical problem with the current silent-success behavior when operating on commits that are not ancestors of HEAD or any branch.

Martinet describes a test scenario where both `git history fixup` and `git history reword` appear to succeed (exit code 0) but do not actually modify the visible commit history or unstage changes. In the case of `fixup`, the staged changes remain staged without any feedback; in the case of `reword`, the editor opens but the commit graph remains unchanged afterward. The author suggests that printing the old and new commit hashes on success would provide visual confirmation that the operation took effect, aligning with Pablo Sabater’s earlier proposal.

The email also touches on a potential edge case: if `--update-refs` is not set, the rewritten commit must be an ancestor of HEAD to be reachable. Martinet implies that the command could either enforce this or at least warn when the result would be unreachable.

This is not a code review or a patch—it is a real-world usability observation from someone who tried the new commands and ran into confusion. The report reinforces the ongoing discussion about whether `git history` commands should be silent by default or provide feedback, and it gives concrete examples of where the current design falls short.
