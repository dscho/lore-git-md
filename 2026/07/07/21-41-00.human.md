This is a technical clarification in the ongoing `git_hash_*()` API refactoring thread. Brian M. Carlson chimes in to explain why hash libraries typically treat multiple calls to the finalization function as a bug, backing up Jeff King’s earlier assertion that `git_hash_final()` should *not* be idempotent.

Brian details the internal mechanics of SHA-256 (and SHA-1) contexts: the finalization step pads the message, processes the remaining bytes, and updates the state in-place. Calling `final()` a second time re-pads and re-hashes the already-finalized context, producing a corrupt or attacker-controlled result. He contrasts this with Rust’s ownership model, where the finalization method consumes the context (`self`), making a second call impossible at compile time. The takeaway is that Git’s C API is behaving conventionally by treating repeated `git_hash_final()` calls as a programming error that should trigger a `BUG()`.
