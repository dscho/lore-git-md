This is the second half of a two-patch bugfix series targeting a quadratic performance regression in Git’s reftable backend. The regression surfaces when recreating refs that were previously deleted (tombstoned): the merged iterator’s `suppress_deletions` flag forces a full scan of all tombstone records before higher-level bounds checks can terminate iteration, making operations like `refs_verify_refnames_available()` and `reftable_backend_read_ref()` O(n) per call in tombstone-heavy scenarios.

Kristofer Karlsson’s patch removes the `suppress_deletions` flag from the merged iterator and instead handles tombstone records explicitly at each call site in the reftable backend. This change allows iteration to terminate as soon as a tombstone past the relevant bound is encountered, restoring linear performance. The patch touches `refs/reftable-backend.c` (core logic), `reftable/merged.{c,h}` (removing the flag), and `reftable/stack.c` (minor cleanup). No new symbols are introduced; the behavior change is confined to internal tombstone handling.

Patrick Steinhardt’s review identified a critical downstream compatibility risk: the `suppress_deletions` flag is still used by libgit2, so outright removal would break external consumers. Kristofer’s reply proposes a minimal adjustment—keeping the flag in the API but no longer setting it from `stack.c`—which preserves libgit2 compatibility while still optimizing the internal call sites. This looks like a pragmatic way forward, though it leaves the flag’s long-term fate unresolved.

The patch includes thorough test coverage: a new perf test (`p1401-ref-store-tombstones.sh`) measures both ref recreation and deletion scenarios, and a correctness test (`t0610-reftable-basics.sh`) verifies tombstone edge cases. The performance improvement is dramatic—from ~14s to ~0.2s in the perf test’s 8000-ref scenarios—but the test’s current design (measuring both deletion and recreation in the same run) may distort results due to leftover tombstones. Kristofer acknowledges this and seems open to using `test_when_finished` for cleaner isolation.

This is a well-scoped, high-impact fix for a real performance regression. The libgit2 compatibility issue is the only significant loose end, and Kristofer’s proposed workaround looks viable. If you care about reftable performance or libgit2 interoperability, this thread is worth following—expect a v2 shortly.
