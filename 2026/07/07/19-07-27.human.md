This is the core patch in a feature series that adds a `--linearize` option to `git replay`. The patch implements the new flag, which flattens merge commits into a linear history by dropping merges and replaying all commits in a single sequence, even when multiple branches are involved. The behavior is intentionally distinct from `git rebase --no-rebase-merges`: `git replay --linearize` produces a single linear topology (e.g., `A->X->Y` for a merge of `A->X` and `A->Y`), while `git rebase` rewrites both branches and drops the merge (e.g., `A->X'->Y'` or `A->Y'->X'`). This difference is documented and tested.

The implementation touches `replay.c`, `replay.h`, `builtin/replay.c`, and the man page, with thorough test coverage in `t3650-replay-basics.sh`. The patch is technically complete and addresses all prior feedback, including a regression fix in v6 that ensures correct behavior when replaying a single branch containing merge commits. The mutual exclusivity between `--linearize` and `--revert` has been removed in v7, allowing them to be used together, and authorship of the patch has been updated to Toon Claes to reflect the extensive changes since the original version.

The interface design debate (whether to mirror `git rebase`'s `--rebase-merges=<mode>` syntax) is resolved in favor of a standalone `--linearize` flag, with the commit message justifying the divergence on the grounds that it better describes the predictable, all-or-nothing flattening behavior. The series is ready for review, with no unresolved technical objections. Potential trivial conflicts with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series are noted but expected to be easy to resolve.
