This thread began as a two-patch bugfix series by Kristofer Karlsson to address a performance regression in Git’s commit-graph subsystem, where the `topo_levels` slab was incorrectly propagated only to the topmost layer of split commit-graph chains. The regression, introduced by commit `199d452758` in September 2025, degraded incremental commit-graph write performance from 233ms to 4133ms on large repositories. The fix was merged to `master` in its second iteration, and the immediate issue is resolved.

Post-merge discussion initially expanded to review ergonomics—specifically whether failing tests and their fixes should be split into separate commits—and tooling improvements, such as selective context expansion in patch emails. These debates are now settled: Junio C Hamano demonstrated that reviewer-side tooling (`git show ':!t/' | git apply -R && make test`) is sufficient to isolate failing tests without requiring author-side changes, and Kristofer acknowledged the existing workflow meets his needs. The project will continue grouping tests and fixes in atomic commits, and no tooling changes are planned.

The thread has since shifted to architectural follow-ups, with Taylor Blau and Patrick Steinhardt exploring whether commit graphs belong at the object database (ODB) level or as a backend-specific property. Taylor agrees with Patrick’s skepticism about treating commit graphs as a universal ODB property but argues that generation numbers—unlike optimizations like MIDX or reachability bitmaps—are fundamental commit attributes independent of storage format. This discussion remains exploratory and non-blocking, with no immediate code changes proposed. The broader ODB abstraction effort continues, but the commit-graph’s role within it is still being clarified.
