This is the **v2 cover letter** for Patrick Steinhardt’s 13-patch **refactoring series** that splits repository discovery from setup in Git’s core code. The series is part of the ongoing effort to clean up `setup.c` and consolidate repository configuration into `repo_init()`.

The v2 update addresses feedback from the initial submission:
- **Patch 2/13**: Fixed a typo in the commit message ("exlicitly" → "explicitly") and expanded the explanation of how misconfigurations (both `core.worktree` and `core.bare` set) are handled when `GIT_WORK_TREE` is present.
- **Patch 3/13**: Clarified the precedence order between the `--shallow-file` command-line option and the `GIT_SHALLOW_FILE` environment variable, noting that the command-line option has always taken precedence. The patch also removes an unused parameter in `set_alternate_shallow_file()`.
- No code changes were made to other patches, but the cover letter now explicitly links to the v1 discussion.

The series remains focused on its architectural goal: introducing a new `struct repo_discovery` to hold discovery results (format, paths, prefix) and making the discovery phase self-contained. This separation enables future consolidation of repository setup logic into `repo_init()`, reducing scattered state and improving clarity. Key changes include:
- Renaming `check_repository_format_gently()` to better reflect its role.
- Moving the prefix from `startup_info` to `struct repository` (patch 7/13).
- Dropping redundant global state (e.g., static `cwd` buffer, patch 8/13).
- Propagating the prefix via `struct repo_discovery` (patch 9/13).
- Making `init_db()` accept a worktree parameter (patch 12/13).

The series touches core files (`setup.c`, `repository.h`) and built-ins (`clone`, `init-db`, `rev-parse`), but **no behavior changes are intended**. The refactoring is foundational for ongoing efforts like `the_repository` removal and ODB abstraction. Justin Tobler’s substantive reviews on patches 1–3, 5, and 7/13 have surfaced questions about API design (e.g., single-application semantics for `struct repo_discovery`) and edge cases (e.g., environment variable handling), but Patrick’s replies suggest these are forward-looking concerns rather than blockers.

For follow-up discussion, watch for:
- **API clarity**: Whether `struct repo_discovery` and its methods (`repo_discover()`, `apply_repository_format()`) are sufficiently self-documenting.
- **Edge cases**: Handling of environment variable overrides, shallow file interactions, and prefix/worktree path computation (e.g., symlinks, relative paths).
- **Integration**: Alignment with `the_repository` removal and ODB abstraction goals, particularly ensuring `the_repository` contains no relevant state before `apply_repository_format()` is called.
