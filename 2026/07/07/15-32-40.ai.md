This is patch 8/11 in Patrick Steinhardt’s "Make ODB optimizations pluggable" series, part of the ongoing ODB abstraction effort. It introduces the `odb_optimize_required()` function to centralize the logic that determines whether an ODB optimization (incremental repack, geometric repack, etc.) should run under `--auto`.

The patch extracts the existing auto-condition checks from `need_to_gc()` and `geometric_repack_auto_condition()` into a single, strategy-aware helper. The new function takes an `object_database` pointer and an `odb_optimize_options` struct, then dispatches to the appropriate backend logic based on the requested strategy (`ODB_OPTIMIZE_INCREMENTAL` or `ODB_OPTIMIZE_GEOMETRIC`). All configuration reads, geometry calculations, and loose-object counts are now handled inside this helper, eliminating the scattered logic that previously lived in multiple places.

Files touched: only `builtin/gc.c` (160 lines changed: 92 insertions, 68 deletions). New symbols: `odb_optimize_required()`. Removed symbols: `need_to_gc()` (now inlined into the new helper). Behavior is unchanged; the patch is a pure refactoring that preserves all existing auto-condition semantics, including the split-factor thresholds, loose-object limits, and configuration overrides.

The change is a prerequisite for pluggable ODB backends: once a backend implements its own optimization strategy, it can simply call `odb_optimize_required()` with the appropriate options to decide whether housekeeping is needed. Reviewers may want to verify that the strategy dispatch is exhaustive and that the configuration reads remain consistent with the original code paths, but the patch itself is mechanical and well-scoped.
