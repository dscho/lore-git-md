This is the fifth and final patch in Taylor Blau’s five-part bugfix series hardening Git’s packfile subsystem against duplicate object entries. It addresses a subtle but critical issue in multi-pack index (MIDX) bitmap reuse: when a pack contains duplicate objects (e.g., [A, B, A, C]), the MIDX pseudo-pack assigns one bit position per unique OID, creating a mismatch between bitmap positions and physical pack entries.

The patch makes two key changes. First, it ensures the bitmap count (`bitmap_nr`) is read from the MIDX’s BTMP chunk rather than the pack’s object count, preventing overcounting duplicates. If the BTMP chunk is missing, the patch skips preferred-pack reuse entirely, avoiding the need for a full pseudo-pack scan. Second, it disables verbatim reuse and forces per-object translation when the bitmap and pack positions diverge, ensuring delta bases are resolved correctly even when the MIDX-selected copy differs from the physical pack order.

The test coverage is thorough: a new `t5332-multi-pack-reuse.sh` test verifies reuse works with intra-pack duplicates (A, B, A, C) and confirms the fallback path when BTMP is unavailable. A second test ensures deltas against omitted duplicate bases are handled by normal packing. The changes are narrowly scoped to MIDX reuse paths and leave classic single-pack bitmaps untouched, as those are guaranteed to have one entry per OID.

This patch completes the series by closing the last known gap in duplicate handling. The approach is pragmatic—prioritizing correctness over optimization when edge cases arise—and the commit message clearly explains the trade-offs. No review feedback has appeared yet, but the changes look well-motivated and unlikely to draw objections. The series as a whole now provides a robust foundation for safely using duplicate-containing packs in MIDX and bitmap operations.
