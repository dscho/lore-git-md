Patrick Steinhardt’s five-patch series to make on-disk ODB structures pluggable continues under review, with the latest exchange clarifying the long-term intent behind one of the more subtle refactorings. The series decouples the creation of backend-specific directories (like `objects/pack`) from the generic repository setup code, allowing future ODB backends to define their own on-disk layouts without modifying core logic. The first two patches fix latent bugs in loose-object map loading—one ensuring maps are loaded from the correct ODB source path, the other removing hard-coded assumptions about the "files" backend—which were confirmed to affect repositories with compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility) and alternates. Toon Claes provided a test case that Patrick incorporated, elevating these patches to correctness fixes with regression coverage.

The discussion has focused on three key design questions. Junio C Hamano raised concerns about the robustness of an unconditional downcast in the loop iterating over ODB sources, suggesting a more forward-looking design with a generic `load object map` method; Patrick clarified that the downcast macro will BUG if the source isn’t a "files" backend, making the current loop unsafe for non-files sources, but hasn’t yet addressed the architectural suggestion. Junio also questioned the `create_on_disk` callback’s naming, proposing something more generic like `initialize` for backends that don’t use traditional filesystems; Patrick deferred to consistency with the ref subsystem’s `ref_store_create_on_disk()`, retaining the current name for now. Meanwhile, Justin Tobler challenged the use of the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag in the third patch, asking why an explicit `odb_new()` call wasn’t used instead. Patrick’s latest reply explains that the flag is a pragmatic choice due to the complexity of splitting object directory and alternate logic from `apply_repository_format()`, but notes the design may simplify when environment variable handling moves into the "files" backend—a hint that this is a transitional step rather than a permanent solution.

The series remains under review with no merge status reported. Junio, Justin Tobler, and Toon Claes have all provided substantive feedback, particularly on the first three patches, while the fourth and fifth patches have seen lighter engagement (a spelling nit and a naming discussion, respectively). The only remaining direct caller of `repo_read_loose_object_map()` is in `object-file-convert.c`, and Patrick has suggested this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source, further reducing the object map’s external exposure. The thread is part of Patrick’s broader ODB abstraction effort, which aims to enable alternative backends beyond loose objects and packfiles.
