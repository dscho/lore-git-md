This thread is about Patrick Steinhardt’s six-patch series to make Git’s on-disk object database (ODB) structures pluggable, part of the broader ODB abstraction effort. The goal is to decouple backend-specific directory creation (like `objects/pack` or `objects/info`) from the core repository setup code, enabling future ODB backends with custom layouts. The first patch in the series is already slated for merging to `next` due to its status as a correctness fix—it resolves a latent bug where Git ignored loose-object maps in alternates when using compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility). The fix is now backed by a regression test in `t/t1016-compatObjectFormat.sh`.

The series has evolved significantly through review. The latest update, the fourth patch, abandons an earlier design using a `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag in favor of Toon Claes’s alternative: making ODB creation an explicit step at every call site. This change is purely mechanical, moving `odb_new()` out of `apply_repository_format()` and into `repo_init()`, `enter_repo()`, and other initialization functions. The shift simplifies the path for the final patch, which introduces a `create_on_disk` callback in the ODB backends. Reviewers Justin Tobler and Toon Claes have both given their "looks good to me" (LGTM) for the revised series, with Toon noting he’s "very happy" with the structure. Minor cleanup items—like an outdated docstring and a formatting inconsistency—remain but are non-blocking.

The series is now fully approved and ready for merging, with the first patch already marked for graduation to `next` in Junio’s latest "What’s cooking" report. The remaining patches are uncontroversial and address long-term architectural goals, such as enabling non-filesystem backends. Key technical changes include new symbols like the `create_on_disk` callback and `safe_create_dir()`, as well as the removal of redundant environment variable checks. The only open questions are forward-looking, like whether to generalize the `create_on_disk` callback for non-filesystem backends or replace the remaining direct caller of `repo_read_loose_object_map()` with a `FLUSH_CACHES` operation. These are not blockers but may resurface if new ODB backends emerge. For now, the series is on track for the current development cycle.
