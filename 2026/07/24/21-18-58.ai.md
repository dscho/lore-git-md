This is the second patch in Phillip Wood’s two-patch bugfix series for `rebase -i`, and this email is Junio C Hamano’s review of it. The patch itself is a narrow, surgical fix for a specific edge case: when a `fixup -c` command is followed by a skipped fixup or squash command, the editor is not opened to allow the user to edit the commit message, breaking the expected workflow.

Junio’s review is substantive but light. He notes that the new helper function `seen_fixup_edit_msg()` mirrors the existing `seen_squash()` helper, which is good for consistency, but he questions why the original code did not parse each line carefully to identify commands (instead of using `strstr()` to guess at line boundaries). He also points out that the helpers do not insist on a space after the verb (`squash` or `fixup -c`), which could theoretically match malformed commands. Neither issue is a blocker, and Junio explicitly says the patch “looks good” apart from these minor nits.

The review also reveals that the original code open-coded the squash check in `commit_staged_changes()`, which the patch now replaces with the helper function. Junio’s feedback is actionable but small: consider tightening the string matching to require a space after the verb. No other concerns are raised, and Junio plans to mark the topic for `next` after a few more days if no further review arrives.

Phillip is a seasoned contributor with deep expertise in the sequencer and rebase code, so the patch is likely to be technically sound. The issue is real but niche: users who rely on `fixup -c` to edit messages during an interactive rebase will hit this bug if they skip a subsequent fixup or squash command. The fix is minimal, self-contained, and does not affect other rebase workflows.
