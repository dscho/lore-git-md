This is a design-discussion reply in the ongoing `[PATCH v2]` series adding seven new path-discovery keys to `git repo info`. Junio C Hamano weighs in on the unresolved behavioral question for `path.index`: whether the keys should return an empty string in bare repositories (where no index file is typically used) or the default `<gitdir>/index` path.

Junio’s position is clear and pragmatic: `path.index` should return whatever path Git’s internal `repo->index_file` member holds at the time of the query, regardless of whether the repository is bare or the file exists. This mirrors the behavior of `git rev-parse --git-path index` and aligns with the precedent set by `path.grafts` in the same series. He dismisses the analogy to `path.toplevel` (which returns an empty string when already at the top level) as inapplicable, framing the index path as a configuration detail rather than a contextual absence. The implication is that scripts should treat the returned path as a location to check, not a guarantee of file existence.

No code changes are proposed here; this is purely a design clarification. The outcome resolves the open question for patch 5/7, removing the last behavioral ambiguity before the series can proceed to deeper technical review. Junio’s stance is likely to be decisive, given his role as maintainer and his earlier endorsement of the same principle for `path.grafts`. The discussion now awaits K Jayatheerth’s response or a v3 patch reflecting this consensus.
