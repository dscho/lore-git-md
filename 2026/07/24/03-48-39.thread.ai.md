Thread identity
Subject: [PATCH 0/5] odb: make on-disk ODB structures pluggable
Series version: v1 (initial submission)
Originating author: Patrick Steinhardt
Thread type: patch series (infrastructure, part of ODB abstraction effort)

Core problem or goal
Decouple the creation of backend-specific on-disk object database (ODB) structures (e.g., `objects/info`, `objects/pack`) from the generic repository setup code. The top-level `objects/` directory remains mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback in the ODB source interface. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic. The first two patches fix latent bugs in loose-object map loading: the first ensures the map is loaded from the correct ODB source path (not always the common `objects/` directory), and the second removes hard-coded assumptions that the primary ODB is always the "files" backend and that the ODB must be initialized before the repository’s compatibility hash algorithm is set. **The first patch is confirmed as fixing a latent correctness bug affecting repositories with compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility) and alternates, where loose-object maps were previously loaded from the wrong path. The bug is triggered by an unconditional downcast of the primary ODB to the "files" backend, which would BUG if a different backend type were used with a compatibility hash algorithm. Patrick Steinhardt has incorporated Toon Claes’s test case, which creates two SHA-256 repositories (one acting as an alternate), configures both with SHA-1 compatibility, and verifies `git rev-parse` resolves an object borrowed from the alternate when using the compatibility hash format. This test elevates the patch’s importance to a correctness fix with regression coverage for multi-backend setups.**

Current status
Under review; v1 posted. No prior versions. Based on the "7th batch" integration (commit `9a0c4701dc`), targeting the current development cycle. Junio C Hamano, Justin Tobler, and Toon Claes have provided substantive feedback on multiple patches, particularly the first (loose-object-map path fix) and second (loose-object-map loading refactor). **Patrick Steinhardt has rewritten the second patch’s commit message to clarify the latent correctness issue: the original code unconditionally downcasts the primary ODB to the "files" backend, which would BUG if a different backend type were used with a compatibility hash algorithm. This aligns with Junio’s request for precision and elevates the patch’s status to a correctness fix.** The fourth patch (helper function for ODB source type mapping) received surface-level feedback from Junio (spelling nit: "inmemory" -> "in-memory"), which Patrick has acknowledged and will address. The fifth patch (`create_on_disk` callback design) has received substantive feedback from Junio, who suggested renaming the callback to something more generic (e.g., `initialize`) to better reflect its purpose for backends that do not use traditional filesystems. Patrick Steinhardt deferred to consistency with the existing `ref_store_create_on_disk()` naming in the ref subsystem, opting to retain `create_on_disk` for now. This decision is pragmatic rather than architectural; the callback’s purpose is clear within the current scope, but the naming may need revisiting if non-filesystem backends materialize. **Patrick Steinhardt has also clarified that the downcast macro in the second patch will BUG if the source is not a "files" backend, meaning the current loop cannot safely skip non-files sources. The only remaining direct caller of `repo_read_loose_object_map()` is in `object-file-convert.c`, which reloads the map after potential concurrent updates; Patrick suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source, further reducing external exposure of the object map.**

This aligns with the series’ broader goal of making on-disk ODB structures pluggable and resolves Junio’s question about the patch’s purpose. The reply does not introduce new technical details or reopen design questions but reaffirms the patch’s role as infrastructure for the ODB abstraction effort.**

Key technical details
- Files touched: `loose.c`, `loose.h`, `odb/source-loose.c`, `odb/source-files.c`, `odb/source*.h`, `setup.c`, `setup.h`, `repository.c`.
- New or renamed symbols: `loose_object_map_load()` (public function), backend-specific directory creation helpers, ODB source type mapping functions (`odb_source_type_to_name()`), `get_object_directories()`, `create_object_database()` (renamed from `create_object_directory()`), `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag, `create_on_disk` callback in the ODB source interface.
- Behavior change: ODB creation is deferred until after the ref database is set up; hardcoded assumptions about directory layouts and initialization order are removed. Loose-object maps are now loaded from source-specific paths, and initialization steps in `apply_repository_format()` are reordered. The repository can now be left in a partially-initialized state (ref database created, ODB not yet created) via the new flag. **The first patch fixes a latent bug where loose-object maps were loaded from the wrong path when multiple ODB sources existed (e.g., alternates) and the repository used a non-default hash algorithm (SHA-256 with SHA-1 compatibility). The fix replaces `repo_common_path_replace()` with `xstrfmt()` to construct the correct path from `loose->base.path`. The second patch addresses a latent correctness issue: the original code unconditionally downcasts the primary ODB to the "files" backend, which would BUG if a different backend type were used with a compatibility hash algorithm. The downcast macro will BUG if the source is not a "files" backend, meaning the current loop cannot safely skip non-files sources. The loose object map is being made an internal implementation detail, with the loose backend handling its own loading. The only remaining direct caller of `repo_read_loose_object_map()` is in `object-file-convert.c`, which reloads the map after potential concurrent updates; Patrick suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source.** The third patch defers ODB creation by introducing the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag, allowing the repository to be set up without immediately creating backend-specific directories. **Patrick’s latest reply confirms this refactoring is a prerequisite for the planned `objectStorage` extension, which will enable non-filesystem ODB backends.** The fourth patch adds a helper function to map ODB source types to human-readable strings for improved error messages in downcasting macros. The final patch moves the creation of backend-specific directories (`objects/pack`, `objects/info`) from the generic `create_object_database()` function into the "files" backend’s `create_on_disk` callback. The callback’s name (`create_on_disk`) was retained for consistency with the ref subsystem’s `ref_store_create_on_disk()`, despite Junio’s suggestion to use a more generic term like `initialize`.
- On-disk format: no changes to existing repositories; this is purely internal refactoring.
- Test coverage: Toon Claes provided a concrete test case for the first patch, which Patrick Steinhardt has incorporated. The test verifies the fix for repositories with alternates and compatibility hash algorithms. No additional test cases have been proposed for the architectural questions raised in the second patch.

Open questions and loose ends
1. **Downcast safety and multi-backend consistency**: Junio questions the robustness of the unconditional downcast in the loop iterating over ODB sources, asking whether the downcast macro would return `NULL` for non-files sources (allowing safe skipping) and suggesting a more forward-looking design: adding a generic `load object map` method to the `odb_source` interface to eliminate downcasting entirely. **Patrick Steinhardt has clarified that the downcast macro will BUG if the source is not a "files" backend, meaning the current loop cannot safely skip non-files sources. He notes that the loose object map is being made an internal implementation detail, with the loose backend handling its own loading, but has not addressed Junio’s suggestion of a generic `load object map` method. In the latest follow-up, Patrick confirmed that the `should_use_loose_object_map()` check is now source-local (per-backend), but downplayed the risk of inconsistency across backends. This leaves the broader architectural question unresolved: could multiple backends with divergent answers to `should_use_loose_object_map()` break assumptions?**
2. **Callback naming and extensibility**: Junio suggests renaming the `create_on_disk` callback to something more generic (e.g., `initialize`) to better reflect its purpose for backends that do not use traditional filesystems (e.g., cloud-based object stores). Patrick Steinhardt deferred to consistency with the ref subsystem’s `ref_store_create_on_disk()`, retaining the current name for now. This is not a blocker for the current series but may require revisiting if non-filesystem backends are introduced.
3. **Initialization sequence design**: Justin Tobler questions the use of the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag in the third patch, suggesting that requiring an explicit `odb_new()` call after `apply_repository_format()` might be a cleaner approach. He notes there are few call sites and asks for clarification on why the flag-based approach was chosen. **Patrick’s earlier reply explained that the flag is a pragmatic choice due to the complexity of splitting object directory and alternate logic from `apply_repository_format()`, but acknowledged that the design may simplify when environment variable handling is moved into the "files" backend. This suggests the flag is a transitional step, and the approach may be revisited in the future. The immediate question remains unresolved, but the reply signals openness to refinement. Junio’s latest question about the patch’s purpose was addressed by Patrick, who confirmed it is a prerequisite for the `objectStorage` extension, but this does not resolve Justin’s design preference.**
4. **Callback invocation timing**: Justin Tobler briefly muses in his review of the fifth patch about whether the `create_on_disk` callback should be invoked inside `odb_new()` rather than as a separate step. This is a minor design preference and not a blocker.
5. **Future of `repo_read_loose_object_map()`**: Patrick Steinhardt notes that the only remaining direct caller of `repo_read_loose_object_map()` is in `object-file-convert.c`, which reloads the map after potential concurrent updates. He suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source, further reducing external exposure of the object map. This is a forward-looking design note and not a blocker for the current series.
6. **Eager vs. deferred loading of compatibility maps**: Justin Tobler suggested deferring the loading of compatibility maps to simplify the design, but Patrick retained eager loading for caution. This pragmatic choice does not resolve the underlying question of whether the design could be simplified by deferring map loading entirely.
