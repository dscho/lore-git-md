Thread identity
Subject: [PATCH 0/6] odb: make on-disk ODB structures pluggable
Series version: v3 (updated submission)
Originating author: Patrick Steinhardt
Thread type: patch series (infrastructure, part of ODB abstraction effort)

Core problem or goal
Decouple the creation of backend-specific on-disk object database (ODB) structures (e.g., `objects/info`, `objects/pack`) from the generic repository setup code. The top-level `objects/` directory remains mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback in the ODB source interface. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic. The first patch fixes a latent correctness bug in loose-object map loading: it ensures the map is loaded from the correct ODB source path (not always the common `objects/` directory), addressing a failure mode in repositories with compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility) and alternates. The second patch refactors how Git loads loose object maps to fix two latent issues: an unconditional downcast that would BUG if a non-"files" ODB backend were used with a compatibility hash algorithm, and a tangled initialization sequence that intermixed repository configuration with ODB setup. The patch moves the loose object map loading logic into the "loose" backend itself, making it an internal implementation detail and eliminating the downcast safety issue. The third patch moves handling of the `GIT_OBJECT_DIRECTORY` and `GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables from `apply_repository_format()` into `odb_new()`, making the function self-contained and eliminating the need to duplicate environment variable logic in future call sites. Toon Claes’s test case, which creates two SHA-256 repositories (one acting as an alternate), configures both with SHA-1 compatibility, and verifies `git rev-parse` resolves an object borrowed from the alternate when using the compatibility hash format, elevates the first patch’s importance to a correctness fix with regression coverage for multi-backend setups.

Current status
Under review; v3 posted and now complete. The series consists of six patches. The first patch is explicitly listed in Junio’s "What's cooking" report (2025-06-10) as "will merge to 'next'" due to its status as a correctness fix with dedicated test coverage. The remaining five patches (including the third, which moves environment variable handling into `odb_new()`, and the sixth, which implements the `create_on_disk` callback in the "files" backend) are uncontroversial and ready for merging, with no outstanding technical objections. The third patch is mechanical, touching `odb.c`, `odb.h`, `setup.c`, and a unit test to consolidate environment variable handling. It introduces an `enum odb_new_flags` parameter (`ODB_NEW_HONOR_ENV`) to control whether environment variables are respected, and updates `apply_repository_format()` to pass the flag through. Toon Claes noted a minor cleanup opportunity (removing redundant `xstrdup_or_null()` and `free()` calls for `o->alternate_db`), but this does not affect functionality. The sixth patch replaces generic directory creation logic with the new callback, removes the redundant environment variable check from `create_object_database()` (moved to `odb_new()` in the third patch), and uses `safe_create_dir()` to create `pack/` and `info/` subdirectories in the "files" backend. The top-level `objects/` directory remains hardcoded as a requirement for repository discovery.

Open questions and loose ends
1. **Downcast safety and multi-backend consistency**: Junio’s suggestion to add a generic `load object map` method to the `odb_source` interface remains unresolved. The current patch sidesteps this by making the loose object map an internal detail of the loose backend, which is pragmatic for now but may need revisiting if non-filesystem backends are introduced. Justin Tobler’s broader concern—whether divergent answers to `should_use_loose_object_map()` across backends could break assumptions—also remains open.
2. **Callback naming and extensibility**: Junio suggests renaming the `create_on_disk` callback to something more generic (e.g., `initialize`) to better reflect its purpose for backends that do not use traditional filesystems. Patrick Steinhardt deferred to consistency with the ref subsystem’s `ref_store_create_on_disk()`, retaining the current name for now. This is not a blocker but may require revisiting if non-filesystem backends materialize.
3. **Future of `repo_read_loose_object_map()`**: The only remaining direct caller is in `object-file-convert.c`, which reloads the map after potential concurrent updates. Patrick suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source, but this is forward-looking and not a blocker.
4. **Eager vs. deferred loading of compatibility maps**: Justin Tobler suggested deferring the loading of compatibility maps to simplify the design, but Patrick retained eager loading for caution. This pragmatic choice does not resolve the underlying question.
5. **Minor cleanup in third patch**: Toon Claes identified a redundant `xstrdup_or_null()` and `free()` pair for `o->alternate_db` in the third patch, which could be removed without affecting functionality. This is not a blocker but could be addressed in a future iteration.
