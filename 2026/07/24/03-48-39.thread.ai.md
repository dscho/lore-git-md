Subject: [PATCH 0/5] odb: make on-disk ODB structures pluggable
Series version: v2 (updated submission)
Originating author: Patrick Steinhardt
Thread type: patch series (infrastructure, part of ODB abstraction effort)

Core problem or goal
Decouple the creation of backend-specific on-disk object database (ODB) structures (e.g., `objects/info`, `objects/pack`) from the generic repository setup code. The top-level `objects/` directory remains mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback in the ODB source interface. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic. The first patch fixes a latent correctness bug in loose-object map loading: it ensures the map is loaded from the correct ODB source path (not always the common `objects/` directory), addressing a failure mode in repositories with compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility) and alternates. The bug is triggered by an unconditional downcast of the primary ODB to the "files" backend, which would BUG if a different backend type were used with a compatibility hash algorithm. Patrick Steinhardt has incorporated Toon Claes’s test case, which creates two SHA-256 repositories (one acting as an alternate), configures both with SHA-1 compatibility, and verifies `git rev-parse` resolves an object borrowed from the alternate when using the compatibility hash format. This test elevates the patch’s importance to a correctness fix with regression coverage for multi-backend setups.

Current status
Under review; v2 posted. The series is based on the "7th batch" integration (commit `9a0c4701dc`), targeting the current development cycle. The first patch is now confirmed as a correctness fix with a dedicated test case, making it a candidate for early graduation independent of the rest of the series. The second patch’s refactoring is now better justified: it eliminates a latent BUG by moving loose-object map loading into the "loose" backend, making it an internal implementation detail. The downcast macro in the original code would BUG if the source were not a "files" backend, meaning the loop could not safely skip non-files sources—this is now resolved by making the check source-local. The only remaining direct caller of `repo_read_loose_object_map()` is in `object-file-convert.c`, which reloads the map after potential concurrent updates; Patrick suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source. The third patch defers ODB creation by introducing the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag, allowing the repository to be set up without immediately creating backend-specific directories. The patch consolidates ODB creation logic into a new helper function, `create_object_database()`, replacing the previous `create_object_directory()` function. The fourth patch (helper function for ODB source type mapping) received surface-level feedback from Junio (spelling nit: "inmemory" -> "in-memory"), which Patrick has addressed in v2. The fifth patch (`create_on_disk` callback design) is uncontroversial and ready for merging. It moves the creation of backend-specific directories (`objects/pack`, `objects/info`) into the "files" backend’s `create_on_disk` callback, retaining the callback name for consistency with the ref subsystem’s `ref_store_create_on_disk()`. No merge status reported; the series remains under review.

Open questions and loose ends
1. **Downcast safety and multi-backend consistency**: Junio’s suggestion to add a generic `load object map` method to the `odb_source` interface remains unresolved. The current patch sidesteps this by making the loose object map an internal detail of the loose backend, which is pragmatic for now but may need revisiting if non-filesystem backends are introduced. Justin Tobler’s broader concern—whether divergent answers to `should_use_loose_object_map()` across backends could break assumptions—also remains open.
2. **Callback naming and extensibility**: Junio suggests renaming the `create_on_disk` callback to something more generic (e.g., `initialize`) to better reflect its purpose for backends that do not use traditional filesystems. Patrick Steinhardt deferred to consistency with the ref subsystem’s `ref_store_create_on_disk()`, retaining the current name for now. This is not a blocker but may require revisiting if non-filesystem backends materialize.
3. **Initialization sequence design**: Justin Tobler questioned the use of the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag in the third patch, suggesting an explicit `odb_new()` call might be cleaner. Patrick’s reply explained the flag is a pragmatic, transitional step due to the complexity of splitting object directory and alternate logic from `apply_repository_format()`, but the immediate question remains open. The new email further clarifies that the flag consolidates ODB creation logic into `create_object_database()`.
4. **Callback invocation timing**: Justin Tobler’s minor suggestion to invoke the `create_on_disk` callback inside `odb_new()` rather than as a separate step is not a blocker.
5. **Future of `repo_read_loose_object_map()`**: The only remaining direct caller is in `object-file-convert.c`, which reloads the map after potential concurrent updates. Patrick suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source, but this is forward-looking and not a blocker.
6. **Eager vs. deferred loading of compatibility maps**: Justin Tobler suggested deferring the loading of compatibility maps to simplify the design, but Patrick retained eager loading for caution. This pragmatic choice does not resolve the underlying question.
