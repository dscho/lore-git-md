Thread identity
Subject: [PATCH 0/6] odb: make on-disk ODB structures pluggable
Series version: v5 (final reroll, addressing docstring and formatting nits)
Originating author: Patrick Steinhardt
Thread type: patch series (infrastructure, part of ODB abstraction effort)

Core problem or goal
Decouple the creation of backend-specific on-disk object database (ODB) structures (e.g., `objects/info`, `objects/pack`) from the generic repository setup code. The top-level `objects/` directory remains mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback in the ODB source interface. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic. The first patch fixes a latent correctness bug in loose-object map loading: when iterating through multiple ODB sources (e.g., the main repository and its alternates), Git always loaded the loose-object map from the common `objects/` directory instead of the path specific to each source. This caused alternates’ loose-object maps to be silently ignored, breaking repositories that rely on compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility). The fix is surgical: `load_one_loose_object_map()` now constructs the map path from `loose->base.path` instead of using the repository’s common directory. The patch also adds a regression test in `t/t1016-compatObjectFormat.sh` that verifies `git rev-parse` correctly resolves an object borrowed from an alternate when using a compatibility hash algorithm. The test creates two repositories (one as an alternate, one as the borrower), commits an empty commit in the alternate, and confirms the borrower can resolve the object’s OID in the alternate’s hash format. The second patch further detangles loose object map loading from repository setup by moving the logic into the "loose" backend itself, fixing two latent correctness bugs: (1) the old code unconditionally downcast the primary ODB to the "files" backend when loading loose object maps, which would BUG if a different backend type were ever used with a compatibility hash algorithm, and (2) the intermixing of repository configuration and ODB initialization was awkward and error-prone. The patch moves `repo_read_loose_object_map()` into the loose backend as an internal detail, enforces the `should_use_loose_object_map()` guard at the source level during backend initialization (`odb_source_loose_new()`), and reorders `odb_new()` to happen after `repo_set_compat_hash_algo()` in `setup.c`.

Current status
The entire series (v5) is now fully merged to the `next` branch (2025-06-10, per Junio’s "What's cooking" report). The first patch was previously merged to `next`; the remaining five patches (including this sixth patch) have now graduated as well. All substantive review feedback has been addressed: Justin Tobler and Toon Claes have both given "looks good to me" (LGTM) for the entire series, and Patrick addressed the last two minor issues raised by Toon Claes (the misleading docstring for `apply_repository_format()` and a formatting inconsistency in `init_db()`). The architectural discussion about initialization sequence design is resolved in favor of Toon Claes’s alternative, which abandons the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag and makes ODB creation an explicit step at every call site. The series is based on the recent "7th batch" integration (commit `9a0c4701dc`), targeting the current development cycle.

Key technical details
Files and subsystems touched: `odb.c`, `odb.h`, `setup.c`, `repository.c`, `setup.h`, `object-file-convert.c`, `odb/source-files.c`, `odb/source-loose.c`, `loose.c`, `loose.h`, `t/t0033-safe-directory.sh`, `t/t1016-compatObjectFormat.sh` (regression test for the first patch), `t/unit-tests/u-odb-inmemory.c` (updated to pass `0` instead of empty strings to `odb_new()`), and `odb/source-*.h` (updated in the fifth patch to use `odb_source_type_to_name()` in BUG messages). New or renamed symbols: `enum odb_new_flags` (`ODB_NEW_HONOR_ENV`), `odb_source::create_on_disk` callback, `safe_create_dir()`, `repo_read_loose_object_map()` (now an internal detail of the loose backend), `should_use_loose_object_map()` (moved to loose backend), `odb_source_loose_new()`, downcast macros (`ODB_SOURCE_CAST_TO_FILES`, `odb_source_files_downcast()`), `loose_object_map_load()` (now public), `odb_source_type_to_name()` (new in the fifth patch), and the new helper function `create_object_database()` (replacing `create_object_directory()`). The third patch moves handling of the `GIT_OBJECT_DIRECTORY` and `GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables from `apply_repository_format()` into `odb_new()` itself, eliminating a potential duplication point and preparing for alternates management inside the "files" backend. The change is mechanical: `odb_new()` gains an `enum odb_new_flags` parameter (`ODB_NEW_HONOR_ENV`) that tells it to read the environment variables, and `apply_repository_format()` now passes the flag instead of duplicating the logic. The patch also switches `odb_new()` to use `CALLOC_ARRAY` and removes the redundant `xstrdup_or_null`/`free` dance for `o->alternate_db` (the value is already duplicated or NULL at this point). The fourth patch lifts `odb_new()` out of `apply_repository_format()` and places it at every call site that initializes a repository (`repo_init()`, `enter_repo()`, `setup_git_directory_gently()`, and `init_db()`). This encapsulation keeps ODB initialization and on-disk creation together, simplifying the path for the sixth patch, which moves on-disk structure creation into the `struct odb_source` backends. The patch renames `create_object_directory()` to `create_object_database()` to reflect its expanded role (it now also calls `odb_new()`). The `APPLY_REPOSITORY_FORMAT_HONOR_ENV` flag is passed directly to `odb_new()` at each call site, eliminating the need for an intermediate `odb_new_flags` variable. The fifth patch improves BUG message clarity in downcasting macros by introducing `odb_source_type_to_name()`, a helper function that maps ODB source types (e.g., `ODB_SOURCE_LOOSE`, `ODB_SOURCE_PACKED`) to human-readable strings like `"loose"` or `"packed"`. The function is used in downcasting macros (`odb_source_files_downcast()`, `odb_source_loose_downcast()`, etc.) to replace opaque numeric values with meaningful labels in BUG messages (e.g., `BUG("trying to downcast source of type 'packed' to 'loose'")`). The implementation is defensive: unknown enum values map to `"unknown"`, and the function BUGs if the lookup table is missing an entry. The sixth patch replaces generic directory creation logic with the `create_on_disk` callback, removes the redundant environment variable check from `create_object_database()` (moved to `odb_new()` in the third patch), and uses `safe_create_dir()` to create `pack/` and `info/` subdirectories in the "files" backend. The top-level `objects/` directory remains hardcoded as a requirement for repository discovery. The callback is invoked in `create_object_database()` after ODB initialization, and the "files" backend’s implementation uses `safe_create_dir()` to create `pack/` and `info/` subdirectories.

Open questions and loose ends
1. **Downcast safety and multi-backend consistency**: Junio’s suggestion to add a generic `load object map` method to the `odb_source` interface remains unresolved. The current patch sidesteps this by making the loose object map an internal detail of the loose backend, which is pragmatic for now but may need revisiting if non-filesystem backends are introduced. Justin Tobler’s broader concern—whether divergent answers to `should_use_loose_object_map()` across backends could break assumptions—also remains open.
2. **Callback naming and extensibility**: Junio suggests renaming the `create_on_disk` callback to something more generic (e.g., `initialize`) to better reflect its purpose for backends that do not use traditional filesystems. Patrick Steinhardt deferred to consistency with the ref subsystem’s `ref_store_create_on_disk()`, retaining the current name for now. This is not a blocker but may require revisiting if non-filesystem backends materialize.
3. **Future of `repo_read_loose_object_map()`**: The only remaining direct caller is in `object-file-convert.c`, which reloads the map after potential concurrent updates. Patrick suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source, but this is forward-looking and not a blocker.
4. **Eager vs. deferred loading of compatibility maps**: Justin Tobler suggested deferring the loading of compatibility maps to simplify the design, but Patrick retained eager loading for caution. This pragmatic choice does not resolve the underlying question.
