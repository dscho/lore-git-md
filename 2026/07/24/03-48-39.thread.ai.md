Thread identity
Subject: [PATCH 0/6] odb: make on-disk ODB structures pluggable
Series version: v3 (updated submission)
Originating author: Patrick Steinhardt
Thread type: patch series (infrastructure, part of ODB abstraction effort)

Core problem or goal
Decouple the creation of backend-specific on-disk object database (ODB) structures (e.g., `objects/info`, `objects/pack`) from the generic repository setup code. The top-level `objects/` directory remains mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback in the ODB source interface. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic. The first patch fixes a latent correctness bug in loose-object map loading: it ensures the map is loaded from the correct ODB source path (not always the common `objects/` directory), addressing a failure mode in repositories with compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility) and alternates. The second patch refactors how Git loads loose object maps to fix two latent issues: an unconditional downcast that would BUG if a non-"files" ODB backend were used with a compatibility hash algorithm, and a tangled initialization sequence that intermixed repository configuration with ODB setup. The patch moves the loose object map loading logic into the "loose" backend itself, making it an internal implementation detail and eliminating the downcast safety issue. Toon Claes’s test case, which creates two SHA-256 repositories (one acting as an alternate), configures both with SHA-1 compatibility, and verifies `git rev-parse` resolves an object borrowed from the alternate when using the compatibility hash format, elevates the first patch’s importance to a correctness fix with regression coverage for multi-backend setups.

Current status
Under review; v3 posted. The series consists of six patches. The third patch moves the handling of `GIT_OBJECT_DIRECTORY` and `GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables into `odb_new()`, deduplicating logic and preparing for a future where alternates are managed by the "files" backend. This change simplifies the control flow in `apply_repository_format()` by removing the need to pass environment variables through intermediate variables and aligns with Patrick’s broader goal of moving environment variable handling into the ODB backend itself. The fourth patch (new in v3) splits `create_object_directory()` into two steps: `apply_repository_format()` with `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` to configure the repository without initializing the ODB, followed by `create_object_database()` to initialize the ODB and create its on-disk structures. This ensures both the ODB and its directories are set up in the same function, avoiding an intermediate state where the ODB exists but its directories do not. The change is mechanical, touches only `setup.c` and `setup.h`, and is uncontroversial. The fifth patch (previously the fourth) has been adjusted to reflect the third patch’s changes. Justin Tobler reviewed the entire series in v2 and stated "looks good to me," signaling approval of the changes in that version: the added test case for the loose-object map bug, the "in-memory" backend rename, and the clarified commit messages. The first patch is now confirmed as a correctness fix with a dedicated test case, making it a candidate for early graduation independent of the rest of the series. The second patch is uncontroversial after addressing latent BUG concerns (unconditional downcast to "files" backend) by making the loose object map an internal implementation detail of the loose backend. Junio’s "What's cooking" report (2025-06-10) explicitly lists the first patch as "will merge to 'next'" and the remaining five patches as "under review," confirming the split status.

Open questions and loose ends
1. **Downcast safety and multi-backend consistency**: Junio’s suggestion to add a generic `load object map` method to the `odb_source` interface remains unresolved. The current patch sidesteps this by making the loose object map an internal detail of the loose backend, which is pragmatic for now but may need revisiting if non-filesystem backends are introduced. Justin Tobler’s broader concern—whether divergent answers to `should_use_loose_object_map()` across backends could break assumptions—also remains open.
2. **Callback naming and extensibility**: Junio suggests renaming the `create_on_disk` callback to something more generic (e.g., `initialize`) to better reflect its purpose for backends that do not use traditional filesystems. Patrick Steinhardt deferred to consistency with the ref subsystem’s `ref_store_create_on_disk()`, retaining the current name for now. This is not a blocker but may require revisiting if non-filesystem backends materialize.
3. **Future of `repo_read_loose_object_map()`**: The only remaining direct caller is in `object-file-convert.c`, which reloads the map after potential concurrent updates. Patrick suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source, but this is forward-looking and not a blocker.
4. **Eager vs. deferred loading of compatibility maps**: Justin Tobler suggested deferring the loading of compatibility maps to simplify the design, but Patrick retained eager loading for caution. This pragmatic choice does not resolve the underlying question.
