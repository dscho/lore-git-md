Thread identity
Subject: [PATCH 0/5] odb: make on-disk ODB structures pluggable
Series version: v1 (initial submission)
Originating author: Patrick Steinhardt
Thread type: patch series (infrastructure, part of ODB abstraction effort)

Core problem or goal
Decouple the creation of backend-specific on-disk object database (ODB) structures (e.g., `objects/info`, `objects/pack`) from the generic repository setup code. The top-level `objects/` directory remains mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback in the ODB source interface. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic. The first two patches fix latent bugs in loose-object map loading: the first ensures the map is loaded from the correct ODB source path (not always the common `objects/` directory), and the second removes hard-coded assumptions that the primary ODB is always the "files" backend and that the ODB must be initialized before the repository’s compatibility hash algorithm is set. **The first patch is now recognized as fixing a latent correctness bug affecting repositories with compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility) and alternates, where loose-object maps were previously loaded from the wrong path.**

Key technical details
- Files touched: `loose.c`, `loose.h`, `odb/source-loose.c`, `odb/source-files.c`, `odb/source*.h`, `setup.c`, `setup.h`, `repository.c`.
- New or renamed symbols: `loose_object_map_load()` (public function), backend-specific directory creation helpers, ODB source type mapping functions (`odb_source_type_to_name()`), `get_object_directories()`, `create_object_database()` (renamed from `create_object_directory()`), `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag, `create_on_disk` callback in the ODB source interface.
- Behavior change: ODB creation is deferred until after the ref database is set up; hardcoded assumptions about directory layouts and initialization order are removed. Loose-object maps are now loaded from source-specific paths, and initialization steps in `apply_repository_format()` are reordered. The repository can now be left in a partially-initialized state (ref database created, ODB not yet created) via the new flag. **The first patch fixes a latent bug where loose-object maps were loaded from the wrong path when multiple ODB sources existed (e.g., alternates) and the repository used a non-default hash algorithm (SHA-256 with SHA-1 compatibility). The fix replaces `repo_common_path_replace()` with `xstrfmt()` to construct the correct path from `loose->base.path`.** The second patch moves loose-object-map loading from repository setup into the "loose" backend, introducing lazy loading via `should_use_loose_object_map()` and `loose_object_map_load()`. The third patch defers ODB creation by introducing the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag, allowing the repository to be set up without immediately creating backend-specific directories. The fourth patch adds a helper function to map ODB source types to human-readable strings for improved error messages in downcasting macros. The final patch moves the creation of backend-specific directories (`objects/pack`, `objects/info`) from the generic `create_object_database()` function into the "files" backend’s `create_on_disk` callback.
- On-disk format: no changes to existing repositories; this is purely internal refactoring.
- Test coverage: **Toon Claes provided a concrete test case for the first patch, verifying the fix for repositories with alternates and compatibility hash algorithms. The test creates two SHA-256 repositories (one acting as an alternate), configures both with SHA-1 compatibility, and confirms that `git rev-parse` correctly resolves an object borrowed from the alternate when using the compatibility hash format.**

Open questions and loose ends
1. **Commit message clarity**: Junio requests rewording of the phrase “extract its loose backend” in the second patch’s commit message for precision. **Toon Claes additionally suggests the first patch’s commit message should highlight the severity of the latent bug (affecting repositories with alternates and compatibility hash algorithms) and include the provided test case.**
2. **Downcast safety and multi-backend consistency**: Junio questions the robustness of the unconditional downcast in the loop iterating over ODB sources, asking whether the downcast macro would return `NULL` for non-files sources (allowing safe skipping) and suggesting a more forward-looking design: adding a generic `load object map` method to the `odb_source` interface to eliminate downcasting entirely. Justin Tobler’s review of the second patch raises related concerns about whether `should_use_loose_object_map()` might behave inconsistently across multiple backends and whether the current design could lead to redundant checks in multi-backend scenarios.
3. **Callback naming and extensibility**: Junio suggests renaming the `create_on_disk` callback to something more generic (e.g., `initialize`) to better reflect its purpose for backends that do not use traditional filesystems (e.g., cloud-based object stores). This is not a blocker for the current series but hints at future extensibility needs.
4. **Initialization sequence design**: Justin Tobler questions the use of the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag in the third patch, suggesting that requiring an explicit `odb_new()` call after `apply_repository_format()` might be a cleaner approach. He notes there are few call sites and asks for clarification on why the flag-based approach was chosen.
5. **Callback invocation timing**: Justin Tobler briefly muses in his review of the fifth patch about whether the `create_on_disk` callback should be invoked inside `odb_new()` rather than as a separate step. This is a minor design preference and not a blocker.
