This is the second patch in Phillip Wood’s two-patch bugfix series for `rebase -i`, and this email is Junio C Hamano’s review of it. The patch fixes an edge case where the editor is not opened after a `fixup -c` command if a preceding fixup or squash command was skipped, breaking the expected workflow.

Junio’s review is substantive but narrow. He notes that the new helper function `seen_fixup_edit_msg()` mirrors the existing `seen_squash()` logic, which is a bit loose—it checks for the presence of the string `"squash"` or `"fixup -c"` anywhere in the command chain, rather than parsing each line carefully. This is inherited from the original code, so it’s not a fault of this patch, but Junio wonders aloud whether the detection should be stricter (e.g., insisting on a space after the verb). He also points out that the original code open-coded the squash check in `commit_staged_changes()`, which is now replaced by the helper function—this is a minor cleanup, not a bug.

The review is positive overall: Junio calls the patch “good” and plans to mark the topic for `next` after a few more days if no further feedback arrives. He expresses mild disappointment that no other reviewers have chimed in, but this is a niche edge case in a mature subsystem, and summer is a slow season. The series is likely to proceed with minimal revision—just the robustness tweak Junio already requested in the first patch. Phillip Wood, a seasoned contributor with deep rebase expertise, authored the series, so the fix is almost certainly technically sound.
