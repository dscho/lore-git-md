This is the **sixth patch in the v22 series** implementing `git branch --delete-merged`, introducing the **per-branch opt-out mechanism** via the `branch.<name>.deleteMerged` config key. The patch is **well-crafted, thoroughly tested, and ready for merging** as part of the larger series, which Junio C Hamano has confirmed is unblocked and "pretty much done."

The patch adds a new config key, `branch.<name>.deleteMerged`, which when set to `false` exempts the specified branch from automated cleanup via `git branch --delete-merged`. This addresses a real workflow pain point: developers often want to keep topic branches around for further work after an early round has been merged upstream, but automated cleanup tools (like `--delete-merged`) would otherwise remove them. The opt-out is **non-quiet by default**, printing a skip message (e.g., "Skipping 'kept' (branch.kept.deleteMerged is false)") to inform the user why the branch was preserved. Explicit deletion via `git branch -d` still uses the normal merge check and ignores the opt-out, ensuring manual control remains unaffected.

The implementation is **minimal and targeted**, touching only `builtin/branch.c` to add the config check in `delete_merged_branches()` and updating documentation (`Documentation/config/branch.adoc` and `Documentation/git-branch.adoc`). The config check uses `repo_config_get_bool()` and is performed during candidate filtering, before any deletions occur. The patch also adds **comprehensive test coverage** in `t/t3200-branch.sh`, verifying opt-out behavior, skip messages, explicit deletion via `git branch -d`, and branch state verification via the `check_branches` helper (which uses `git for-each-ref`). Phillip Wood's **surface-level review** of an earlier version suggested the `for-each-ref` verification, which has been applied, and the tests now explicitly confirm the opt-out does not interfere with manual deletion.

The patch is **low-risk** and **well-aligned with Git's config conventions**, using a boolean key with a clear default (`true`). The documentation updates are **clear and concise**, explaining the opt-out's purpose and behavior in both the config reference and the `git-branch` man page. The implementation **avoids side effects** by checking the config early in the deletion pipeline and **preserves existing behavior** for all other commands. The only follow-up work mentioned in the thread is extending stacked-branch protection to `git branch -d` for consistency, but this is **not a blocker** for this patch or the series.
