This is the final patch in the 13-part `git cat-file --batch-command` remote-object-info series, now at **v21** and queued for `next`. The patch makes the client's atom allow-list dynamic, adapting to the server's advertised `object-info` capabilities rather than hardcoding support for only `objectname` and `objectsize`.

The change replaces the static `remote_object_info_atoms[]` array with a `remote_allowed_atoms` string list in `struct expand_data`. The client now queries the server for each requested placeholder (e.g., `%(objectsize)` → `"size"`), filters out unsupported options, and maps the remaining ones back to their placeholders. Unsupported but known atoms (e.g., `%(objecttype)` when the server lacks `"type"` support) expand to empty strings, matching `for-each-ref` behavior. Unknown atoms (e.g., `%(objectcolor)`) still trigger a fatal error.

Key implementation details:
- **Protocol mapping**: A new `protocol_placeholder_entry` array maps server options (`"size"`, `"type"`) to their corresponding atoms (`"objectsize"`, `"objecttype"`). The client uses this to build the allow-list after filtering.
- **Filtering logic**: In `fetch_object_info()`, the client iterates backward through `object_info_options` to avoid skipping elements when removing unsupported options. The list is no longer sorted, so `unsorted_string_list_has_string()` is used for lookups.
- **Output guarantee**: `batch_object_write()` is moved outside the conditional block to ensure output is always produced (a blank line if no attributes are supported).
- **Test coverage**: New tests verify that `%(objectname)`-only requests echo back the OID and that the client correctly reports missing objects.

The patch is mechanical and focused, with no behavior changes for the current scope (size-only queries). It lays the groundwork for future `object-info` extensions (e.g., type support) by ensuring the client gracefully handles servers with varying capabilities. The series remains technically complete and ready for integration.
