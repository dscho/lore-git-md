This is the third patch in Taylor Blau’s five-part bugfix series hardening Git’s packfile subsystem against duplicate object entries. The series targets a long-standing edge case where non-strict pack indexes (which allow duplicate OIDs) can cause MIDX verification to falsely report corruption.

This patch adjusts `verify_midx_file()` to stop treating duplicate OIDs as errors. Instead of comparing the MIDX’s recorded offset against the first match returned by `find_pack_entry_one()`—which may pick a different copy of the same OID—the new logic checks that the exact OID/offset pair exists anywhere in the contiguous duplicate run within the source pack. The change is minimal and surgical: it replaces a single offset comparison with a new helper, `pack_index_has_oid_at_offset()`, that scans the duplicate run in both directions. The test fixture confirms that a MIDX written over a pack with duplicates now passes both `git multi-pack-index verify` and `git fsck --full`.

The patch is clearly motivated and narrowly scoped. It touches only `midx.c`, adds a small test helper flag (`--show-offset`) to `test-find-pack`, and extends the existing `t5308-pack-detect-duplicates.sh` test script. No new symbols are introduced, and the on-disk MIDX format remains unchanged. The commit message explains the invariant being enforced—every physical copy of a duplicate OID is valid—and ties the change back to reader behavior, which already handles unselected duplicates gracefully. This looks like a well-crafted fix that should attract little controversy.
