This is a **substantive review** of the second patch in the v4 Rustification build system series, focusing on macOS Universal Binary support. Patrick Steinhardt raises a **structural design question** about the build artifact layout in the `target/` directory, which could affect maintainability and consistency.

The patch introduces `RUST_TARGETS` to enable multi-architecture Rust builds on macOS, compiling separate static libraries per target triple and combining them into a universal `libgitcore.a` using `lipo`. Patrick’s concern centers on the inconsistent directory structure: the universal library is placed in `target/release/` (or `target/debug/`), while per-architecture artifacts land in `target/<triple>/release/`. This creates two distinct layouts (`target/$BUILD_CONFIG/` vs. `target/$ARCH/$BUILD_CONFIG/`) for what are conceptually similar build outputs.

Patrick proposes unifying the structure by placing all artifacts under `target/$BUILD_CONFIG/`, with per-architecture slices in subdirectories (e.g., `target/release/x86_64-apple-darwin/`). This would align the Rust build layout with Cargo’s default conventions and avoid mixing two different organizational schemes in the same directory. The question is not a surface-level nit—it touches on build system hygiene and could simplify future maintenance or debugging.

The review does not challenge the core functionality (Universal Binary support) or the technical rationale (bridging Cargo’s limitations with Apple’s toolchain). Instead, it targets a **design choice** that, while not breaking the build, could lead to confusion or redundancy. The authors (Shardul Natu and Koji Nakamaru) will need to either justify the current layout or revise the patch to adopt Patrick’s suggestion. No other review feedback is present in this email; the thread remains focused on this single structural point.
