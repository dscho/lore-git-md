This is the final patch in Patrick Steinhardt’s five-part series adding reference-writing subcommands to `` `git refs` ``. The patch introduces the `` `git refs rename` `` subcommand, which renames a reference and its reflog from `<oldref>` to `<newref>`. The implementation is straightforward: it validates the reference names, checks that the old reference exists and the new one does not, then calls the backend’s `` `refs_rename_ref()` `` function. The subcommand supports a `` `--message=<reason>` `` option to record a reflog entry, but unlike `` `update` `` and `` `create` ``, it does not offer `` `--no-deref` `` or `` `--create-reflog` ``.

The test suite (`t/t1467-refs-rename.sh`) is thorough, covering 138 lines of edge cases: successful renames, reflog migration, error conditions (nonexistent source, existing target, invalid names, wrong argument counts), and a new test explicitly documenting that symbolic reference (symref) renaming is unsupported. The symref limitation is a known backend constraint, not a design choice, and Patrick’s earlier response confirms it is unlikely to change soon. The man page update is minimal, adding only a brief synopsis and description without mentioning the symref restriction.

This patch is a clean, well-tested addition that completes the series. The only loose end is the undocumented symref limitation, but the test suite now makes the behavior explicit. No further changes are expected.
