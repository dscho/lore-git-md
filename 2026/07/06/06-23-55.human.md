This is the third iteration of a nine-patch series that makes Git’s `GIT_TEST_LONG` tests reliable and efficient enough to run in CI. The series originated as a small effort to expose GitLab CI status in the README and enable `GIT_TEST_LONG` there, but expanded after Patrick Steinhardt discovered that several `GIT_TEST_LONG` tests were already broken or hanging in both GitHub CI and GitLab CI. The v3 revision fixes only commit message subjects and prerequisite logic in patches 2 and 5, addressing a surface-level nit from Junio C Hamano in v2.

The series is now uncontroversial and appears ready for integration. It splits cleanly into three categories: CI visibility and configuration (patches 1, 8, 9), test correctness fixes (patches 2, 5, 7), and test efficiency improvements (patches 3, 4, 6). Patch 1 adds GitLab CI and GitHub Actions badges to the README, improving pipeline visibility. Patches 2 and 5 skip two tests (`t0021-conversion.sh` and `t7508-status.sh`) on platforms where they are known to be broken due to `size_t` limitations (64-bit for `t0021`, 32-bit for `t7508`). Patch 3 replaces a slow `dd` loop in `t4141-apply-too-large.sh` with a single `genzeros` call, eliminating a 6-minute bottleneck while retaining the `EXPENSIVE` prerequisite due to high memory usage. Patches 4 and 6 reduce peak disk usage in `t5608-clone-2gb.sh` and `t7900-maintenance.sh` by deleting repositories immediately after use. Patch 7 introduces a consistent boolean parser for `GIT_TEST_LONG`, and patches 8 and 9 disable the macOS RAM disk (which was causing out-of-memory issues) and enable `GIT_TEST_LONG` in GitLab CI for integration branches, excluding Windows runners due to hardware limitations.

The changes are mechanical, well-motivated by observed CI failures, and include clear explanations in each commit message. No new user-facing features or behavior changes are introduced. The series is self-contained and does not depend on other in-flight topics. All substantive feedback from v1 and v2 has been addressed, and the remaining nits were trivial. If you care about test suite reliability or CI coverage, this series is worth a quick skim to see how `GIT_TEST_LONG` tests are being made more robust.
