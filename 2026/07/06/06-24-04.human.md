This is the final patch in Patrick Steinhardt’s nine-patch series making `GIT_TEST_LONG` tests reliable and efficient for CI. It enables the long-running test suite for GitLab CI on pushes to integration branches (`next`, `master`, `main`, `maint`), matching the behavior already in place for GitHub Actions since May 2026. The patch explicitly disables `GIT_TEST_LONG` on Windows runners because their 7.5 GB RAM limit is insufficient for some `EXPENSIVE` tests, a pragmatic concession that has not drawn objections.

The change is mechanical and well-motivated: it plugs the test-coverage gap between GitHub and GitLab CI without introducing new user-facing features or on-disk format changes. The patch touches only `.gitlab-ci.yml` and `ci/lib.sh`, adding a `CI_EVENT` variable to map GitLab’s pipeline triggers to GitHub’s event names and setting `GIT_TEST_LONG` to `true` (unless explicitly overridden) for the same branch patterns. The Windows exclusion is implemented via a simple `GIT_TEST_LONG: false` variable in the relevant job definitions.

This patch is uncontroversial and ready for integration. It completes the series, which has already addressed all feedback from earlier revisions and is now focused solely on CI parity between the two platforms. The series as a whole is a clear improvement: it makes expensive tests reliable enough to run in CI without hanging or consuming excessive resources, while ensuring that resource-intensive tests remain appropriately labeled.
