This thread is about a two-patch series from Patrick Steinhardt that fixes a quadratic performance regression in Git’s reftable backend when re-creating refs that were previously deleted. The regression occurs because the merged iterator’s `suppress_deletions` flag forces a full scan of tombstone records before bounds checks can terminate iteration, making operations like `refs_verify_refnames_available()` and `reftable_backend_read_ref()` unnecessarily slow in tombstone-heavy scenarios.

The v1 series moves tombstone handling from the merged iterator to the reftable backend’s call sites, where prefix and refname bounds are available, allowing early termination and improving performance from ~14 seconds to ~0.2 seconds in the perf test’s 8,000-ref scenarios. The fix is narrowly scoped to the reftable backend, avoiding broader refactoring. Key files touched include `refs/reftable-backend.c` and `reftable/merged.{c,h}`, with new tests added to verify correctness and performance.

Patrick’s own review of the series raised concerns about test design, particularly around performance measurement isolation and redundancy in the correctness test. The latest development is a new issue: the `suppress_deletions` flag is still used by libgit2, so outright removal would break downstream compatibility. Patrick acknowledges the patch’s logic but notes this risk, leaving the next step unclear—whether to preserve the flag for external users or introduce a new API. No other reviewers have weighed in yet, so the thread is now focused on resolving this compatibility question before moving forward.
