This thread is about a two-patch series from Patrick Steinhardt that fixes a quadratic performance regression in Git’s reftable backend. The bug surfaces when re-creating refs that were previously deleted (tombstoned): the merged iterator’s `suppress_deletions` flag forces a full scan of all tombstone records before higher-level bounds checks can terminate, making operations like `update-ref` painfully slow in tombstone-heavy scenarios. The fix moves tombstone handling from the merged iterator to the reftable backend’s call sites, where prefix and refname bounds are already known, restoring linear performance.

The series is at v1 and under active review. The key change is surgical: the `suppress_deletions` flag is preserved in the reftable library API for libgit2 compatibility but removed from Git’s internal use, allowing early termination when tombstones exceed the relevant bound. Performance in the perf test improves from ~14 seconds to ~0.2 seconds for 8,000 refs. The correctness test (`t0610-reftable-basics.sh`) was dropped by consensus, as its coverage is already implicit in `t1400-update-ref.sh`.

The only remaining loose end is a tweak to the performance test (`p1401-ref-store-tombstones.sh`) to split benchmarks and use fresh repositories, ensuring clean measurements. Kristofer Karlsson (the patch author) and Patrick Steinhardt have agreed on this change. Brian m. carlson’s recent email confirms the regression is real-world: they’ve observed the same quadratic behavior in production-scale repositories, calling the fix a meaningful improvement. No technical objections have surfaced, and the libgit2 compatibility risk is now resolved. The series looks ready to proceed once the perf test update is posted.
