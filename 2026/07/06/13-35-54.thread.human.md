This thread is about a two-patch series that fixes a quadratic performance regression in Git’s reftable backend when re-creating refs that were previously deleted. The regression, which could slow operations like `refs_verify_refnames_available()` from 0.2 seconds to 14 seconds in repositories with 8,000 tombstoned refs, was caused by the merged iterator’s `suppress_deletions` flag forcing a full scan of tombstone records before bounds checks could terminate iteration.

The series, now at version 3, has been finalized and is ready for integration. It moves the `suppress_deletions` flag from the merged iterator to `struct reftable_stack_options`, allowing downstream users like libgit2 to control tombstone suppression at stack creation time while preserving their current behavior. The fix ensures tombstone handling happens explicitly at call sites, where bounds checks can terminate early, restoring linear performance. All substantive feedback has been addressed, and the series has been acked by Patrick Steinhardt, with only minor cosmetic issues (a commit message typo and a missing comment) remaining—neither of which requires a reroll.

The conversation has now shifted to post-approval cleanup and forward-looking API evolution. Patrick Steinhardt accepted the proposed comment for the new `suppress_deletions` field and confirmed no further changes are needed. Looking ahead, he outlined a migration path: after both this series and the reftable hardening series (`ps/reftable-hardening`) are merged to `master`, he will update libgit2 to use the new `reftable_stack_options` field. Once libgit2 deactivates `suppress_deletions`, Git can drop the flag entirely, though this is not a blocker for the current series.
