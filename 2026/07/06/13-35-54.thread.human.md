This thread is about a two-patch series from Patrick Steinhardt that fixes a quadratic performance regression in Git’s reftable backend when re-creating refs that were previously deleted. The regression occurs because the merged iterator’s `suppress_deletions` flag forces a full scan of tombstone records before bounds checks can terminate iteration, making operations like `refs_verify_refnames_available()` and `reftable_backend_read_ref()` unnecessarily slow in tombstone-heavy scenarios.

The series moves tombstone handling from the merged iterator to the reftable backend’s call sites, where prefix and refname bounds are available, allowing early termination and improving performance from ~14 seconds to ~0.2 seconds in the perf test’s 8000-ref scenarios. However, the initial version faced a downstream compatibility risk: the `suppress_deletions` flag is used by libgit2, so removing it outright would break external consumers. Kristofer Karlsson, the author of the second patch, has now revised the approach to preserve the flag in the reftable library API while removing its use from Git’s internal call sites, ensuring libgit2 compatibility without sacrificing the performance fix. The revised patch is narrower but maintains the original goal.

The series is under review, with Patrick Steinhardt and Kristofer Karlsson as key participants. The next step is likely a v2 incorporating this compatibility-preserving tweak. Open questions include whether the performance test could be improved for better isolation (e.g., using `test_when_finished` to avoid tombstone contamination between scenarios) and whether the correctness test is redundant given Git’s existing ref tests. The fix is narrowly scoped to the reftable backend, with no on-disk format changes or new symbols introduced.
