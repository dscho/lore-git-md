This thread is about a two-patch series from Patrick Steinhardt and Kristofer Karlsson that fixes a quadratic performance regression in Git’s reftable backend. The bug surfaces when re-creating refs that were previously deleted (tombstoned): the merged iterator’s `suppress_deletions` flag forces a full scan of all tombstone records before bounds checks can terminate, making operations like `refs_verify_refnames_available()` and `reftable_backend_read_ref()` painfully slow in tombstone-heavy scenarios. The fix moves tombstone handling from the merged iterator to the reftable backend’s call sites, where prefix and refname bounds are available, cutting performance from ~14 seconds to ~0.2 seconds in the perf test’s 8,000-ref scenarios.

The series is at v1 and under active review. The authors have already addressed the main compatibility concern—preserving the `suppress_deletions` flag in the reftable library API so libgit2 isn’t broken, while Git’s internal callers bypass it. The current discussion centers on test design: Kristofer has agreed to split the performance test into separate benchmarks and use fresh repositories for each scenario to avoid measurement skew from lingering tombstones. He’s also defended the correctness test, arguing that while Git has many ref-creation tests, none cover the delete-then-recreate flow with tombstones present. No substantive objections to the core fix remain, so the next step is likely a revised patch with these test refinements.
