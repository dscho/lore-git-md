This thread is about a two-patch series that fixes a quadratic performance regression in Git’s reftable backend. The issue occurs when re-creating refs that were previously deleted (tombstoned), forcing unnecessary full scans of tombstone records during ref-reading operations. The fix moves tombstone suppression logic from the merged iterator to the reftable backend’s call sites, where bounds checks can terminate early, improving performance from ~14 seconds to ~0.2 seconds in affected scenarios.

The series is now at version 3, incorporating Patrick Steinhardt’s feedback to preserve API compatibility for downstream users like libgit2. The `suppress_deletions` flag has been relocated to `struct reftable_stack_options`, allowing libgit2 to control tombstone suppression at stack creation time while maintaining its current behavior. Kristofer Karlsson, the author, confirms this change is necessary and that libgit2 will need updating due to its use of pre-options-stack code. The fix is narrowly scoped to the reftable backend, with no changes to the on-disk format.

Key participants include Kristofer Karlsson (author), Patrick Steinhardt (who proposed the API refinement), and brian m. carlson (who endorsed the fix based on real-world benchmarks). The series is now ready for review, with no remaining open questions or loose ends. The perf test `p1401-ref-store-tombstones.sh` measures the improvement in two scenarios, ensuring the fix is both correct and effective.
