This is a **follow-up discussion** in the now-merged `git refs` series, specifically addressing usability concerns about the `--no-deref` option in the new `git refs create` subcommand. Patrick confirms that `--no-deref` does **not** enable symref creation but instead controls whether the command fails when the target reference already exists as a symbolic ref. For example, if `refs/heads/symref` is a symref pointing to `refs/heads/target`, `git refs create refs/heads/symref $OID` would create `refs/heads/target` (dereferencing the symref), while `--no-deref` would make the command fail instead. The email also clarifies that the subcommand’s "must not exist" semantics are intentional: `git refs create` rejects attempts to recreate an existing reference, even with the same value. Patrick dismisses Toon’s proposed test for symref creation with `--no-deref`, explaining that the option’s purpose is to enforce atomicity (failing if the reference exists as a symref) rather than enabling symref creation. The discussion highlights a tension between atomicity guarantees and CLI ergonomics, though no code changes are proposed or expected, as the series is already merged.
