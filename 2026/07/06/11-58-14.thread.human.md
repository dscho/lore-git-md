This thread is about a small but important safeguard for `git-subtree` in `contrib/`. Ian Jackson has posted a two-patch series (v1) that adds a check to the existing shell-script version of `git-subtree`. The check detects repositories that have been modified by a forthcoming Rust rewrite of the same command, which will use a config key (`subtree.rust-rewrite`) to store metadata and won’t be backward-compatible. Without this safeguard, mixing the two implementations could create unparseable history.

All review feedback has been addressed or declined with justification, and the series is now effectively ready for v2. Junio C Hamano, the maintainer, reviewed the first patch and confirmed the error message is acceptable. Colin Stagner and Phillip Wood provided surface-level reviews, focusing on test style and idiomatic Git test framework patterns, which Ian incorporated. The last open question—whether the safeguard should check only the top-level repository config or also search inside the subtree directory—was resolved in favor of top-level only, aligning with the Rust rewrite’s design intent. Ian’s recent email clarifies this design choice, emphasizing that the decision to adopt the new implementation belongs to the downstream project, not the upstream.

The series touches `contrib/subtree/git-subtree.sh` and adds a test case to `t/t7900-subtree.sh`. The new logic checks for the presence of the `subtree.rust-rewrite` config key in the top-level repository config and rejects the operation if found. The Rust rewrite will not support unmarked subtree merges (those performed manually with `git merge -X subtree`), but this limitation will be documented rather than enforced at runtime. The thread is now waiting for any final feedback before v2 is posted.
