This thread is about a small but important safeguard for `git-subtree` in `contrib/`. Ian Jackson has proposed a patch series (v1) that adds a check to the existing shell-script version of `git-subtree` to detect and reject repositories that have been modified by a forthcoming Rust rewrite. The Rust version will use a config key (`subtree.rust-rewrite`) to store metadata, making the two implementations incompatible; mixing them could create unparseable history.

The series is under review and nearly ready. The only substantive issue—a scoping bug in the detection helper function—has been resolved in principle, and Junio C Hamano, the maintainer, has confirmed the error message format is acceptable. Ian has now responded to Colin Stagner’s surface-level review: he will adopt Colin’s test-style suggestions (using `test_commit` and orphan branches) to align the new test case with the rest of the subtree test suite, but he declines to remove the existing `local` declarations in the shell script, arguing that the portability risk is negligible. He also confirms that the detection logic should only check for the config key at the top level of the repository, not inside the subtree being split.

The series is uncontroversial and has no outstanding objections. The next revision is expected to incorporate the test-style improvements and the scoping fix, after which it should be ready for Junio to pick up. The only loose end is a design clarification about the Rust rewrite: it will not support unmarked subtree merges (those done manually with `git merge -X subtree`), which Ian considers unreliable. He plans to document this limitation but won’t add runtime detection for it.
