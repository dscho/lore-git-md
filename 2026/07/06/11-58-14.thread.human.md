This thread is about a small but important safeguard for `git-subtree` in `contrib/`, designed to prevent mixing the existing shell-script implementation with a forthcoming Rust rewrite. The Rust version will use a config key (`subtree.rust-rewrite`) to store metadata and won’t be backward-compatible, so the safeguard detects and rejects repositories that have been touched by the new implementation. The series is nearly ready: v1 addressed all substantive feedback, and v2 is pending only test style improvements (using `test_commit` and orphan branches instead of manual repository setup).

The key participants are Ian Jackson (author), Junio Hamano (maintainer), and reviewers Colin Stagner, Phillip Wood, and D. Ben Knoble. Junio and Phillip provided targeted feedback on error messages and test idioms, while Colin engaged in a conceptual discussion about the safeguard’s design, ultimately aligning with Ian on the scope (top-level config only) and terminology ("upstream/downstream" to describe the social relationship between projects). The latest exchange between Colin and Ian was a tangential but useful clarification about documentation conventions: Colin argued that the Rust rewrite’s docs should use file-position-centric terms like "(sub)tree" rather than "upstream/downstream" to avoid confusion in edge cases (e.g., merging unrelated repositories or splitting history for external build systems). Ian’s design remains unchanged, but the discussion highlights a potential pitfall for the Rust rewrite’s documentation.

The series is procedurally ready for inclusion once v2 is posted, with no open technical questions or objections. The only remaining action is Ian’s restyling of the test case, which he confirmed will happen in a few days. The safeguard itself is straightforward: it checks for the `subtree.rust-rewrite` config key in the top-level repository and errors out if found, with a clear message explaining the incompatibility. The Rust rewrite’s limitations—no support for manual `-X subtree` merges, no runtime enforcement of mixing restrictions—are now well-documented in the thread, though they won’t be addressed in this series.
