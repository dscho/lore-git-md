This thread is about a small but important safeguard for `git-subtree` (in `contrib/`), ensuring that repositories modified by a forthcoming Rust rewrite of the same command are detected and rejected to prevent unparseable history. The Rust rewrite will use a config key (`subtree.rust-rewrite`) to store metadata and won’t be backward-compatible with the existing shell-script implementation. Ian Jackson posted the initial patch series (v1), which adds a runtime check in the shell script to error out if the config key is present.

The series has received thorough review, with all substantive feedback addressed or declined with justification. Junio C Hamano, the maintainer, identified a minor scoping bug and provided the fix, while Colin Stagner and Phillip Wood contributed surface-level improvements, particularly around test style. The only remaining action is for Ian to post v2, incorporating the agreed-upon test style changes (using `test_commit` and orphan branches) while leaving the technical design untouched. Junio’s latest email confirms the series remains in "Expecting a reroll" status, with no new concerns or objections. Ian has noted he’ll post v2 shortly, after which the series is procedurally ready for inclusion. The discussion has also clarified the Rust rewrite’s design intent, including its stance on manual `-X subtree` merges (unsupported but not actively prevented) and the use of top-level config to mark adoption.
