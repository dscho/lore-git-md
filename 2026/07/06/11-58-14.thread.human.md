This thread is about a safeguard for `git-subtree` (in `contrib/`) to prevent mixing the existing shell-script implementation with a forthcoming Rust rewrite. The Rust rewrite will store metadata in a top-level config key (`subtree.rust-rewrite`), making it incompatible with the current version. The safeguard, now in its first version (v1), detects this config key and rejects operations to avoid unparseable history. All review feedback has been addressed, and the series is effectively ready for v2.

The key technical details include a new error message triggered by the config key, a test case verifying the detection logic, and a design choice to check only the top-level repository config (not subtree-internal config). The Rust rewrite will not support manual `-X subtree` merges, though it won’t actively block them—interleaving such merges with `git-subtree --squash` could produce unpredictable results. The safeguard itself doesn’t enforce this limitation; it only prevents mixing the two implementations.

The latest email from D. Ben Knoble seeks clarification on whether the Rust rewrite aims to *discourage* manual `-X subtree` merges entirely or just *mixing* them with the new implementation. The thread confirms the latter: the Rust rewrite won’t parse or validate unmarked merges but won’t block them either. Documentation will advise against the practice, but enforcement is limited to the safeguard’s runtime check. No new objections or open questions remain; the thread is poised for v2. Key participants include Ian Jackson (author), Junio C Hamano (maintainer), Colin Stagner, and Phillip Wood, all of whom have reviewed the series without substantive objections.
