This thread is about a small but important safeguard for `git-subtree` in `contrib/`. Ian Jackson’s patch series adds a check to the existing shell-script version of `git-subtree` to detect and reject repositories that have been modified by a forthcoming Rust rewrite of the same command. The Rust rewrite will use a config key (`subtree.rust-rewrite`) to store metadata, and mixing the two implementations could create unparseable history.

The series is now at v1, with only a scoping fix (using `$1` instead of a global variable) and a resolved discussion about error message formatting remaining before the next revision. Junio C Hamano, the maintainer, has reviewed the first patch, identified the scoping bug, and confirmed the error message is acceptable as-is. The second patch, which adds a test case, received a surface-level review from Colin Stagner. He suggested minor test infrastructure improvements—using `test_create_repo` with orphan branches and replacing manual commit creation with the `test_commit` helper—but did not question the test’s correctness or necessity. Ian Jackson has not yet responded to these suggestions.

The implementation touches `contrib/subtree/git-subtree.sh` and adds a test case in `t/t7900-subtree.sh`. The safeguard triggers when the `subtree.rust-rewrite` config key is present, displaying an error message to prevent mixing the two implementations. The only open questions are minor: whether the use of `local` in shell functions (already present elsewhere in the script) is acceptable, and whether the detection logic should also check for the config file inside the subtree being split. Neither has been framed as a blocker, and no substantive changes are expected beyond the scoping fix. The series is under review and appears close to being ready for integration.
