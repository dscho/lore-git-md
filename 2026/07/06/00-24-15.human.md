This is a **substantive review** from Jeff King (Peff) on Trevor Gross’s `git rebase -i -x` patch series. Peff challenges the design premise of the feature, arguing that the problem should be solved by improving `git cherry-pick` rather than extending `git rebase`.

Peff’s core objection is conceptual: `git rebase` and `git cherry-pick` serve fundamentally different workflows. Rebase is about *moving* history (rewriting commits onto a new base and discarding the old ones), while cherry-pick is about *duplicating* history (creating new commits while preserving the originals). Adding a `-x` flag to rebase—whose purpose is to record the origin of a commit—makes little sense when the original commits are discarded. This undermines the flag’s utility and risks confusing users about the distinction between the two commands.

Instead of extending rebase, Peff suggests enhancing `git cherry-pick` to support interactive editing of the commit sequence. He notes that both commands already use the sequencer subsystem under the hood, and the `.git/sequencer/todo` file for a cherry-pick already resembles a rebase todo list. His proposed experiment shows that cherry-pick could plausibly support an `-i` (interactive) flag with minimal additional work, allowing users to edit the todo list before execution. This would address Trevor’s use case (cherry-picking a sequence of commits with `-x`) without blurring the line between rebase and cherry-pick.

Peff also points out a technical inconsistency in Trevor’s patch: `git cherry-pick -x` records the flag as a global option in `.git/sequencer/opts`, while the patch implements `-x` as a per-command flag in the rebase todo list. He suggests that if per-pick flexibility is important, it might make sense to support `-x` in the sequencer commands directly, with `cherry-pick -x` automatically adding it to each line.

The review is thorough and constructive, focusing on the *why* behind the design rather than nitpicking implementation details. Peff’s alternative—interactive cherry-pick—would likely require less code and avoid the semantic tension between the two commands. However, it would also be a larger departure from the current workflow, as users would need to adopt a new command (`git cherry-pick -i`) instead of reusing familiar rebase syntax. The thread’s future hinges on whether Trevor can justify the rebase-based approach or pivot to Peff’s suggestion.
