This is a **UX improvement proposal** targeting the `git show` command, inspired by the ongoing source-tree reorganization debate. Kaartic Sivaraam suggests adding a hint to `git show` when a requested file path does not exist in the specified commit but appears to have been renamed. The hint would suggest the new path (e.g., `lib/wt-status.c` instead of `wt-status.c`) and offer a config knob (`advice.objectNameWarning`) to disable it.

The proposal is a direct response to Patrick Steinhardt’s and Junio C Hamano’s observations that the `lib/` reorganization disrupts workflows by breaking `git show` and `git log --follow` for moved files. Kaartic’s idea aims to mitigate the recurring mental overhead of remembering file moves, which Phillip Wood and Junio highlighted as a major pain point. The suggestion is lightweight—no functional changes to Git’s core, just a user-facing hint—but could reduce friction for contributors navigating the reorganized codebase.

The technical feasibility hinges on whether Git can efficiently detect renames for this purpose. Kaartic acknowledges that "finding rename just to show a hint sounds a bit too much work," implying the current rename-detection machinery (used by `git diff` or `git log --follow`) might be too heavy for a UX hint. The proposal does not include a prototype or performance analysis, so its viability remains an open question. However, the idea aligns with Git’s history of adding advisory messages (e.g., `advice.detachedHead`) to guide users through disruptive changes.

This reply advances the thread by shifting focus from *whether* to reorganize the codebase to *how* to ease the transition. It does not resolve the core debate (structural benefits vs. workflow disruption) but offers a potential compromise: keep the `lib/` move but soften its impact with tooling. The proposal is narrowly scoped—addressing only `git show`—but could inspire broader improvements (e.g., hints for `git log --follow` or IDE integrations).
