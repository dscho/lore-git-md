Thread identity: reftable backend performance regression fix (2-patch series, v1) by Patrick Steinhardt. Thread type: bugfix patch series.

Core problem or goal: fix a quadratic performance regression in the reftable backend when re-creating refs that were previously deleted (tombstoned). The regression occurs in `update-ref` operations where the merged iterator’s `suppress_deletions` flag forces a full scan of all tombstone records before higher-level bounds checks can terminate iteration, making `refs_verify_refnames_available()` and `reftable_backend_read_ref()` O(n) per call in tombstone-heavy scenarios.

Current status: v1 posted; under review. The series moves tombstone handling from the merged iterator to the reftable backend’s call sites, where prefix and refname bounds are available, enabling early termination when tombstones exceed the relevant bound. Performance improves from ~14s to ~0.2s in the perf test’s 8000-ref scenarios. The fix is narrowly scoped to the reftable backend, but now faces a **downstream compatibility risk**: the `suppress_deletions` flag is still used by libgit2, so outright removal would break external consumers. Patrick Steinhardt (author) has not yet proposed an alternative that preserves the flag for external users while allowing internal callers to bypass it.

Key technical details: files touched: `refs/reftable-backend.c` (core logic), `reftable/merged.{c,h}` (removing `suppress_deletions`), `reftable/stack.c` (minor cleanup). New symbols: none introduced; behavior change: tombstone suppression logic removed from merged iterator and handled explicitly at call sites after bounds checks. Test coverage: new perf test `p1401-ref-store-tombstones.sh` and correctness test `t0610-reftable-basics.sh` added, covering tombstone behavior and edge cases for deleted-then-recreated refs. The performance test exercises two scenarios: recreating the same refs after deletion (quadratic behavior) and creating new, differently-named refs after deletion (worst-case tombstone sorting). The correctness test verifies ref visibility after deletion and recreation. On-disk format: unchanged. Related prior discussion: linked lore thread; reviewer engagement: Jeff King (Peff) mentioned in commit context.

Open questions and loose ends:
- **Downstream compatibility**: the `suppress_deletions` flag is used by libgit2; outright removal would break external consumers. A v2 is needed to either (a) preserve the flag for external users while allowing internal callers to opt out, or (b) introduce a new API that avoids breaking libgit2.
- The performance test (`p1401-ref-store-tombstones.sh`) currently measures both ref recreation *and* deletion, which may distort performance data; using `test_when_finished` to queue cleanups would ensure only the intended operation is benchmarked.
- Test isolation: the asymmetric scenario (creating new refs after deleting old ones) runs in the same repository as the previous test, so tombstones from earlier runs may affect later measurements.
- The correctness test (`t0610-reftable-basics.sh`) is questioned for redundancy, as Git already has extensive tests for ref creation and deletion; its necessity hinges on whether it targets tombstone edge cases not covered elsewhere.
