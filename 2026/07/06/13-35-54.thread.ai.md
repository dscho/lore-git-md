Thread identity: reftable backend performance regression fix (2-patch series, v2) by Kristofer Karlsson via GitGitGadget. Thread type: bugfix patch series.

Core problem or goal: fix a quadratic performance regression in the reftable backend when re-creating refs that were previously deleted (tombstoned). The regression occurs in any ref-reading operation where the merged iterator’s `suppress_deletions` flag forces a full scan of all tombstone records before higher-level bounds checks can terminate iteration, making `refs_verify_refnames_available()` and `reftable_backend_read_ref()` O(n) per call in tombstone-heavy scenarios. Auto-compaction does not always mitigate the issue.

Current status: v2 posted; under review. The series moves tombstone handling from the merged iterator to the reftable backend’s call sites, where prefix and refname bounds are available, enabling early termination when tombstones exceed the relevant bound. Performance improves from ~14s to ~0.2s in the perf test’s 8000-ref scenarios. The fix is narrowly scoped to the reftable backend. **Downstream compatibility with libgit2 is preserved**: the `suppress_deletions` flag remains in the reftable library API but is no longer set from `stack.c`, allowing libgit2 to continue using it while Git’s internal callers bypass it. The perf test (`p1401-ref-store-tombstones.sh`) now uses fresh repositories for each scenario to prevent tombstone carryover, and the correctness test (`t0610-reftable-basics.sh`) was dropped by consensus, as its coverage is already implicit in `t1400-update-ref.sh`.

Key technical details: files touched: `refs/reftable-backend.c` (core logic), `reftable/merged.{c,h}` (removing `suppress_deletions` from internal use), `reftable/stack.c` (single-line removal to avoid breaking libgit2). New symbols: none introduced; behavior change: tombstone suppression logic removed from merged iterator and handled explicitly at call sites after bounds checks. Test coverage: perf test `p1401-ref-store-tombstones.sh` measures two scenarios—recreating the same refs after deletion (quadratic behavior) and creating new, differently-named refs after deletion (worst-case tombstone sorting)—using fresh repositories for each to ensure isolation. The test is narrowly scoped to the reftable backend and does not touch other ref backends. On-disk format: unchanged.
