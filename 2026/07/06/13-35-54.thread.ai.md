Thread identity: reftable backend performance regression fix (2-patch series, v2→v3) by Kristofer Karlsson via GitGitGadget. Thread type: bugfix patch series.

Core problem or goal: fix a quadratic performance regression in the reftable backend when re-creating refs that were previously deleted (tombstoned). The regression occurs in ref-reading operations (e.g., `refs_verify_refnames_available()`, `reftable_backend_read_ref()`) where the merged iterator’s `suppress_deletions` flag forces a full scan of all tombstone records before higher-level bounds checks can terminate iteration, making these operations O(n) per call in tombstone-heavy scenarios. Auto-compaction does not always mitigate the issue.

Current status: **v3 finalized and ready for integration**. The series moves the `suppress_deletions` flag from the merged iterator to `struct reftable_stack_options`, enabling downstream users like libgit2 to control tombstone suppression at stack creation time while preserving libgit2’s current behavior. Tombstone handling is now performed explicitly at the reftable backend’s call sites, where prefix and refname bounds are available, allowing early termination when tombstones exceed the relevant bound. Performance improves from ~14s to ~0.2s in the perf test’s 8000-ref scenarios. **Downstream compatibility**: libgit2’s current usage pattern (setting `suppress_deletions` in `stack.c`) remains functional, but libgit2 will need to update to use the new `reftable_stack_options` field in future versions. The break is already inevitable due to libgit2’s use of pre-options-stack code. **Merge status**: under review, with all substantive feedback incorporated. Patrick Steinhardt’s final review acks the series, leaving only Junio’s merge pending.
