This is the third patch in Patrick Steinhardt’s five-part series adding reference-writing subcommands to the `git refs` builtin. The series is already fully merged (v3 was queued for the next release), and this reroll (v4) makes no functional changes to this patch—it remains identical to v3.

The patch adds the `git refs update` subcommand, which mirrors the behavior of `git update-ref <refname> <oldoid> <newoid>`. It supports the same atomic update semantics: if `<old-value>` is provided, the reference is only updated if it currently matches that value; if `<old-value>` is the all-zero OID (`$ZERO_OID`), the reference must not exist (enabling atomic creation); and if `<new-value>` is the all-zero OID, the reference is deleted. The subcommand also supports `--message=<reason>` for reflog entries, `--no-deref` to control symbolic reference (symref) handling, and `--create-reflog` to force reflog creation.

The implementation is straightforward: it parses options, validates arguments, and delegates to `refs_update_ref()` with the appropriate flags. The test suite (`t/t1465-refs-update.sh`) is comprehensive, covering 268 lines of edge cases: creation, modification, deletion, symref handling, reflog behavior, and error conditions (invalid OIDs, mismatched old values, empty messages, and argument counts). The symref test (`update --no-deref rewrites the symref itself`) confirms that `--no-deref` prevents dereferencing, allowing the symref itself to be overwritten rather than its target.

This patch is uncontroversial and well-tested. It introduces no new behavior—only a more discoverable CLI for existing `git update-ref` functionality. The only open question is whether the `--no-deref` option’s behavior (which controls failure when the target exists as a symref) is intuitive, but this is a usability concern rather than a technical flaw. The patch’s design—mirroring `git update-ref` exactly—avoids introducing new edge cases or compatibility risks.
