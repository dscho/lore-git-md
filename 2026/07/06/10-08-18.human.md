This is a **substantive review** from Phillip Wood that aligns with Jeff King’s (Peff) earlier critique of Trevor Gross’s `git rebase -i -x` patch series, while adding new technical and design considerations.

Phillip endorses Peff’s proposal to extend `git cherry-pick` with an interactive mode (`-i`) instead of adding `-x` to `git rebase`. He asks Trevor directly what specific limitations in `git cherry-pick` force users to fall back to `git rebase`, suggesting that addressing those gaps in `cherry-pick` would be a cleaner solution. Phillip also raises practical concerns about how `-x` would behave with other interactive commands like `edit` or `fixup`—for example, whether a "cherry picked from" trailer makes sense if the commit is later amended or squashed. These edge cases highlight potential confusion in the user experience and could complicate implementation.

On the technical side, Phillip agrees with Peff that the sequencer backend (used by both `rebase` and `cherry-pick`) is already close to supporting an interactive cherry-pick mode. He notes that the main obstacle—generalizing the todo-list editing logic—should be straightforward, though it currently handles rebase-specific features like `rebase.missingCommitsCheck`. Phillip also suggests a more elegant way to handle the `-x` flag: instead of mixing global and per-commit logic (as Trevor’s patch does), `cherry-pick -x` could simply add `-x` to each todo line when building the list, avoiding the need for conditional checks later.

Phillip’s review adds weight to the growing consensus that the feature’s current design is misaligned with Git’s workflow semantics. While he doesn’t outright reject Trevor’s approach, his questions and suggestions push the discussion toward Peff’s alternative, which now looks like the more viable path forward.
