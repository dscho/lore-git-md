Core problem or goal
Add a safeguard to the existing shell-script `git-subtree` (in `contrib/`) to detect and reject repositories that have been modified by a forthcoming Rust rewrite of the same command. The Rust rewrite will use a config key (`subtree.rust-rewrite`) to store downstream project metadata and will not be backward-compatible; mixing the two implementations could create unparseable history. The conceptual framework for the safeguard and Rust rewrite is now fully clarified: "upstream" and "downstream" describe the social/logical relationship between projects (code flows from upstream to downstream), not their physical layout in the repository. This distinction underpins the design choice to check only the top-level repository config (`subtree.rust-rewrite`), as the decision to adopt the new implementation belongs to the downstream project. The Rust rewrite will not support unmarked subtree merges (those performed manually with `git merge -X subtree`), and while it will not actively prevent or detect such merges at runtime, interleaving them with `git-subtree --squash` operations could produce unpredictable and incorrect tree states. Documentation will advise against the practice, but enforcement is limited to the safeguard's runtime check. The Rust rewrite will treat manual `-X subtree` merges as pre-existing downstream branches (predating the subtree addition), which may result in missing parent relationships during `split` operations. A future transition path may be explored to help users migrate from manual `-X subtree` workflows to the new implementation, but this is not part of the current series.

- Forthcoming Rust rewrite design: will not support unmarked subtree merges (those performed manually with `git merge -X subtree`); this limitation will be documented and tested but not enforced at runtime. The Rust rewrite will store its metadata in the top-level repository config under `subtree.rust-rewrite`. Unmarked merges (e.g., interleaved squash and non-squash operations) may produce unpredictable results, but this will not be addressed by runtime checks. The rewrite will treat such merges as if they were downstream branches predating the subtree addition, which may result in missing parent relationships during `split` operations. The Rust rewrite will not actively discourage manual `-X subtree` merges in isolation but will document the risks of mixing them with its own operations. A future transition path may be explored to help users migrate from manual `-X subtree` workflows to the new implementation, but this is not part of the current series.
