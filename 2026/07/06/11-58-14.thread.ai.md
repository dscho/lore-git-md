Subject: [PATCH 0/2] git-subtree: safeguard against mixing old and new implementations
Series version: v1 (all review feedback addressed; no substantive changes remain open)
Originating author: Ian Jackson
Thread type: patch series (contributor housekeeping)

Core problem or goal
Add a safeguard to the existing shell-script `git-subtree` (in `contrib/`) to detect and reject repositories that have been modified by a forthcoming Rust rewrite of the same command. The Rust rewrite will use a config key (`subtree.rust-rewrite`) to store downstream project metadata and will not be backward-compatible; mixing the two implementations could create unparseable history. The conceptual framework for the safeguard and Rust rewrite is now clarified: "upstream" and "downstream" describe the social/logical relationship between projects (code flows from upstream to downstream), not their physical layout in the repository. This distinction underpins the design choice to check only the top-level repository config (`subtree.rust-rewrite`), as the decision to adopt the new implementation belongs to the downstream project.

Current status
Under review; v1 posted. All review feedback has been addressed or declined with justification. The thread is effectively ready for v2, pending any further feedback. The final open question—whether detection should check only the top-level repository config or also search inside the subtree directory—was resolved in favor of top-level only, aligning with the Rust rewrite’s design intent. The conceptual discussion with Colin Stagner confirmed this alignment and clarified the terminology ("upstream"/"downstream") to avoid ambiguity in future documentation.

Key technical details
- Files touched: `contrib/subtree/git-subtree.sh` (detection logic), `t/t7900-subtree.sh` (test case).
- New config key: `subtree.rust-rewrite` (presence triggers the error).
- New error message: “This repository appears to have been used with the new git-subtree Rust rewrite.”
- Test coverage: one new test case verifies the error is triggered when the config key exists; uses `test_create_repo` and `test_commit --no-tag` for consistency with other subtree tests and to avoid unwanted tag creation. The test asserts the exact error message using `test_must_fail git subtree ... 2>err && test_grep "expected message" err`.
- Bug fix: `reject_if_v2_config` helper function now uses `$1` to check the intended revision (`HEAD`).
- Shell portability note: the helper uses `local`, which is not POSIX-compliant but is already present elsewhere in the script; the author declines to remove it, citing negligible compatibility risk.
- Detection scope: the logic checks only the top-level repository config (`.git/config` or equivalent), not `.git-subtree/config` inside the subtree being split. This aligns with the Rust rewrite’s design, where the decision to use the new algorithm depends on the downstream’s adoption, not upstream metadata.
- Forthcoming Rust rewrite design: will not support unmarked subtree merges (those performed manually with `git merge -X subtree`); this limitation will be documented and tested but not enforced at runtime. The Rust rewrite will store its metadata in the top-level repository config under `subtree.rust-rewrite`. Unmarked merges (e.g., interleaved squash and non-squash operations) may produce unpredictable results, but this will not be addressed by runtime checks.
