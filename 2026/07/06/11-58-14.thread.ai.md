Subject: [PATCH 0/2] git-subtree: safeguard against mixing old and new implementations
Series version: v1 (initial submission, scoping fix confirmed)
Originating author: Ian Jackson
Thread type: patch series (contributor housekeeping)

Core problem or goal
Add a safeguard to the existing shell-script `git-subtree` (in `contrib/`) to detect and reject repositories that have been modified by a forthcoming Rust rewrite of the same command. The Rust rewrite will use a config key (`subtree.rust-rewrite`) to store downstream project metadata and will not be backward-compatible; mixing the two implementations could create unparseable history.

Current status
Under review; v1 posted. Junio C Hamano identified and Ian Jackson confirmed a **variable scoping bug** in the detection helper function `reject_if_v2_config`: the function must accept the revision as a positional argument (`$1`) instead of relying on the global variable `rev`. The fix is uncontested. The rest of the patch (error message, config key, test) remains unchanged and uncontested. No prior versions exist; the next revision is expected to address only the scoping fix.

Key technical details
- Files touched: `contrib/subtree/git-subtree.sh` (detection logic), `t/t7900-subtree.sh` (test case).
- New config key: `subtree.rust-rewrite` (presence triggers the error).
- New error message: “This repository appears to have been used with the new git-subtree Rust rewrite.”
- Test coverage: one new test case verifies the error is triggered when the config key exists.
- Bug fix: `reject_if_v2_config` helper function now uses `$1` to check the intended revision (`HEAD`).

Open questions and loose ends

- Error message formatting remains open to minor adjustment if Junio prefers a different style, but no substantive changes are expected.
