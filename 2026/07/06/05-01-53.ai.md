This is the **first patch in the v4 series introducing `greplint.pl`**, a test-suite linter that converts bare `grep` assertions to `test_grep`. This specific patch **documents the `test_grep` helper in `t/README`**, addressing a long-standing gap in Git’s test documentation. The commit is part of a larger effort to standardize test assertions, improve debuggability, and eliminate pre-existing bugs masked by automated conversion.

The patch adds a 34-line section to `t/README` explaining `test_grep`’s purpose, usage, and edge cases. It clarifies that `test_grep` is a wrapper around `grep` designed for test assertions, printing file contents on failure to aid debugging—unlike bare `grep`, which fails silently. The documentation emphasizes key distinctions: negation must use `test_grep !` (not `! test_grep`) to preserve diagnostic output, and `test_grep` should only be used where the file is guaranteed to exist (e.g., not for backend-specific paths or platform-dependent files like NTFS 8.3 short names). For such cases, it recommends explicit guards like `test_have_prereq REFFILES` or `test -f <path>`.

This update directly responds to feedback from the maintainer and reviewers, who raised concerns about `# lint-ok` annotations in earlier versions. The new guidance replaces those annotations with explicit guards, ensuring the linter does not preserve or introduce bugs. The patch also notes that bare `grep` remains appropriate for data filters (e.g., `grep | wc -l`) or command substitutions, where the exit code is not the assertion itself.

The commit message is concise but sufficient, noting the helper’s widespread use and the lack of prior documentation. The diff is clean and focused, touching only `t/README`. This patch is **ready for integration** and unlikely to be controversial, as it merely documents existing practice while codifying the rules established by the series. Future patches in the series will rely on this documentation to justify their conversions.
