This is a well-crafted bugfix for a minor but persistent usability issue in `git blame -b`. René Scharfe’s patch refactors the mark-handling logic in `blame.c` to reserve space for boundary/ignored/unblamable commit markers (^, ?, *) only when those markers are actually displayed. The result is that commit hash abbreviations now respect the user’s `core.abbrev` setting exactly, eliminating the one-nibble discrepancy that made copy-pasting hashes into `git rebase -i` awkward.

The patch is minimal, cleanly structured, and directly addresses the core problem reported by Laszlo Ersek, who has already tested and endorsed it. The documentation update clarifies the new behavior, and the test adjustments reflect the corrected output format. No backward-compatibility concerns have been raised, and the fix preserves the fixed-width nature of the blame output, so downstream parsers should not be affected.

The only loose end is test coverage: René notes the patch lacks dedicated tests to verify the dynamic mark-handling logic, particularly edge cases like multiple marks per line. However, the existing test suite has been updated to match the new behavior, and the patch itself is straightforward enough that regressions seem unlikely. This is a low-risk, high-impact fix that should be uncontroversial.
