This is the fifth and final patch in Patrick Steinhardt’s v4 series adding reference-writing subcommands to `git refs`. The patch introduces the `git refs rename` subcommand, which consolidates reference renaming functionality previously scattered across `git branch -m` and low-level plumbing. The implementation is straightforward: it validates the old and new reference names, checks existence/nonexistence, and delegates to `refs_rename_ref()` to perform the rename (including reflog migration). The test suite (`t1467-refs-rename.sh`) covers 144 lines of edge cases, including reflog handling, error conditions, and explicit verification that symbolic reference (symref) renaming is unsupported.

The patch is a post-merge reroll with no functional changes from v3. The only updates are a new test explicitly documenting that symref renaming fails with the error message `is a symbolic ref, renaming is not supported` (addressing Toon Claes’s usability feedback) and a stylistic tweak to use a subshell in one test for consistency. The backend limitation preventing symref renaming is now clearly documented in both the test and error message, though the man page still omits this detail.

Key technical details for future reference:
- Files: `builtin/refs.c`, `Documentation/git-refs.adoc`, new test script `t/t1467-refs-rename.sh`.
- New symbol: `git refs rename` subcommand with `--message=<reason>` option.
- Behavior: Renames references and their reflogs atomically; fails if the old reference doesn’t exist, the new reference exists, or either name is malformed. **Symref renaming is explicitly unsupported** (backend limitation).
- Test coverage: 144 lines validating reflog migration, error conditions (invalid names, missing/duplicate references, empty messages), and symref handling. The symref test confirms the command fails with a clear error message.
