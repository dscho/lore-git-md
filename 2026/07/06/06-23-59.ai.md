This is the fourth patch in a nine-patch series (v3) that makes `GIT_TEST_LONG` tests reliable and efficient for CI. The series is uncontroversial and ready for integration.

This patch reduces the peak disk usage of `t5608-clone-2gb.sh` from 16 GB to 8 GB by deleting repositories immediately after they are no longer needed. The test creates several large repositories (2 GB and 4 GB) to verify Git’s handling of large objects, but previously kept them around until the end of the test. The patch wraps repository creation in `test_when_finished` blocks, ensuring cleanup happens as soon as each repository is no longer used. The change is purely mechanical and does not affect test behavior or coverage.

The patch touches only `t/t5608-clone-2gb.sh`, moving repository setup into a dedicated `2gb-repo` directory and adding `test_when_finished rm -rf` calls for each clone. The 4 GB repository (`4gb-repo`) and its clones are already gated by the `SIZE_T_IS_64BIT` and `EXPENSIVE` prerequisites, so the patch adds cleanup for those as well. The diff is straightforward and well-motivated, with no new prerequisites or user-facing changes.

Jeff King (Peff) reviewed the v1 version of this patch and described it as an "obvious improvement" for disk usage and defensive isolation of expensive test data. No substantive feedback was raised, and the patch has not changed since v1. The change is a clear win for CI environments where disk space is constrained, and it aligns with the series’ broader goal of making `GIT_TEST_LONG` tests more efficient.

The patch is part of a larger effort to fix broken or inefficient `GIT_TEST_LONG` tests, which are now enabled in GitLab CI for integration branches (matching GitHub Actions behavior). The series as a whole is well-tested and addresses all prior feedback, with this patch specifically targeting disk usage without compromising test coverage.
