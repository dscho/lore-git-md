This is a **follow-up discussion** in the `includeIf.worktree` patch series, specifically addressing the symlink-handling inconsistency identified in v6. Chen Linxuan, a new participant in the thread, proposes a technical solution to align the new `worktree` condition's behavior with the existing `gitdir` condition.

The core issue remains: `gitdir` matches both symlinked and real paths, while `worktree` currently resolves symlinks to the real path only. Chen's investigation reveals the root cause: `repo->worktree` is stored as a realpath (via `real_pathdup()`), losing the original symlinked spelling before includeIf conditions are evaluated. His proposed fix involves storing an additional non-realpath worktree path during repository setup, derived from the current working directory and `$PWD`, to preserve the symlinked location for matching.

The solution is **technically plausible** but introduces complexity in the repository setup code (`setup_discovered_git_dir()`). Chen acknowledges this trade-off and seeks feedback on whether this approach is preferable to the current behavior or alternative semantics. His patch is **well-motivated** and **thoroughly explained**, though the added plumbing may require careful review to avoid regressions in other repository-discovery scenarios.

This discussion is **narrowly scoped** to the symlink-handling edge case and does not reopen broader design questions about the feature. If accepted, the fix would resolve the last known blocker for the series, which is otherwise uncontroversial and addresses a clear usability gap in multi-worktree setups. The thread is now awaiting input from Patrick Steinhardt (who identified the issue) and Junio C Hamano (the maintainer) on the proposed approach.
