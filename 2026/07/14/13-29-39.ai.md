This is a follow-up in the `fetch.submoduleErrors` series, specifically addressing Junio C Hamano’s review feedback on the second patch. The author, Paulius Zaleckas, acknowledges the technical concern about CLI override propagation and posts a fix in v4.

The issue was that when a user runs `git fetch --all --submodule-errors=fail`, the per-remote child fetches re-read the repository configuration, potentially overriding the explicit `--submodule-errors=fail` with a configured `fetch.submoduleErrors=warn`. This would silently revert the user’s CLI choice, breaking the expectation that command-line flags take precedence over config. The fix ensures the resolved value (whether `fail` or `warn`) is forwarded to child fetches whenever it was set explicitly, preserving the user’s intent. A new test verifies this behavior.

The change is narrow and targeted: it modifies only the argument propagation logic in `add_options_to_argv()` and adds test coverage. No other parts of the series are affected, and the core functionality (configurable submodule fetch error handling) remains unchanged. This is a correctness fix for a subtle edge case, not a design change. The series as a whole still aims to let users opt into non-fatal submodule fetch errors, with backwards-compatible defaults.
