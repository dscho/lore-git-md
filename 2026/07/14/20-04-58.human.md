This is a workflow proposal from a user seeking ways to optimize Git performance in a large corporate repository with a branch-and-PR workflow.

Richard describes two common pain points: (1) the overhead of carrying individual commits from merged PRs (which squash-merging could address, but at the cost of losing merge-base accuracy and in-branch history), and (2) shallow clones failing to stay shallow when PRs based on old revisions are merged, because Git follows the second parent and pulls in deep history. The latter is particularly problematic because fetches are often triggered by tools or scripts that don’t pass `--shallow-since`.

He proposes two Git enhancements: first, a persistent shallow setting (e.g., `remote.origin.shallowsince`) that would apply to all fetches from that remote, regardless of how they’re triggered. Second, a more ambitious idea: using `.git/shallow` or replace refs to make merge commits on the mainline appear linear (showing only their first parent) until a user explicitly requests the full history for a specific merge. This would let developers keep their repos small by default while still allowing deep dives when needed.

The email is well-motivated and clearly explains the real-world problems behind the proposals. It’s not a patch yet, but the first idea (persistent shallow settings) looks like a straightforward and uncontroversial feature that could benefit many users with similar workflows. The second idea is more speculative and would require deeper design work, but it’s an interesting direction for discussion. Richard signals he’s willing to implement at least the first proposal if there’s interest.
