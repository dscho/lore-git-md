This thread is the root of a 5-patch series (v1) by René Scharfe introducing repository-aware variants of the tempfile and lockfile APIs (`repo_create_tempfile`, `repo_hold_lock_file_for_update`, etc.) as part of the ongoing `the_repository` removal effort. The series touches 38 files across apply, builtins (difftool, gc, history, sparse-checkout), bundle, commit-graph, config, loose object storage, midx, ODB, ref backends (files and packed), repack-midx, repository, and rerere subsystems. The goal is to eliminate implicit reliance on the global `the_repository` by pushing the repository parameter outward through the tempfile/lockfile layer. The changes are mechanical and confined to plumbing, with no expected user-visible behavior changes.

Key technical details:
- New functions (`repo_create_tempfile_mode`, `repo_hold_lock_file_for_update`, `repo_hold_lock_file_for_update_timeout_mode`, etc.) mirror existing non-repo variants and are declared in `lockfile.h` and `tempfile.h`.
- Patch 1/5 adds `repo_create_tempfile_mode()` and `repo_hold_tempfile()` as thin wrappers around `create_tempfile_mode()`, delegating to existing internals while passing the supplied `struct repository *` to `adjust_shared_perm()`. No callers are converted yet; this is API scaffolding only.
- Patch 2/5 converts the first caller (`refs/packed-backend.c`) to use `repo_create_tempfile(refs->base.repo)`, ensuring `core.sharedRepository` is read from the correct repository.
- Patch 3/5 adds `repo_hold_lock_file_for_update()`, `repo_hold_lock_file_for_update_timeout()`, and `repo_hold_lock_file_for_update_mode()`, wiring them into the lockfile internals. The existing non-repo entry points are converted into thin wrappers that call the repo-aware variants with `the_repository`.
- Patch 4/5 removes the now-unused compatibility wrappers `create_tempfile_mode()` and `create_tempfile()` after all callers have been migrated to the new `repo_create_tempfile*` variants. Patrick Steinhardt’s surface-level review of this patch suggested a minor editorial improvement to the preceding commit message: teasing the upcoming removal in patch 4/5 to make the series’ progression clearer. No technical concerns were raised, and the feedback was framed as a nit rather than a blocker.
- Patch 5/5 mechanically replaces direct calls to the old global `hold_lock_file_for_update*` family with the new repository-aware variants across 17 files, passing the appropriate `struct repository *` parameter to ensure correct `core.sharedRepository` resolution. The diff is purely mechanical (46 insertions, 36 deletions) with no new logic or behavior changes. The selection criterion—converting only callers that already hold a `struct repository *` other than `the_repository` (e.g., `commit-graph.c`, `midx-write.c`, ref backends)—is now explicitly documented in the thread and settled.

**Design discussion and resolved questions**:
1. In review of patch 1/5, Patrick Steinhardt raised a substantive technical point questioning whether passing a full `struct repository *` is overkill when only the `core.sharedRepository` setting is needed. He suggested an alternative: letting callers pass the configuration value directly, but acknowledged this could lead to code duplication. He also noted the thin wrapper in `tempfile.c` could have been an inline function in the header, but dismissed it as a minor nit. René responded by acknowledging the conceptual tension—`create_tempfile()` sounds generic but is repository-specific due to shared permissions—and agreed that a repository-less variant could be cleaner in theory. However, he argued that in practice, every caller already has access to at least `the_repository`, making the current design sufficient. The exchange left the door open for future refactoring if a genuine need for a repository-less API emerges, but neither party saw an immediate use case. This discussion did not alter the series’ trajectory; no v2 was expected or produced for this point.
2. In his substantive review of patch 5/5, Patrick requested two clarifications:
   - **Selection rationale**: Addressed in the thread (see above) and now settled.
   - **Safety guard**: He proposed adding a compile-time guard (e.g., `USE_THE_REPOSITORY_VARIABLE`) to the old global functions (`hold_lock_file_for_update*`) to prevent new callers from accidentally reintroducing reliance on `the_repository`. René pushed back, characterizing this as a task for a **separate patch series** and suggesting patch 5/5 could be dropped if the guard requirement complicated the current effort. Junio Hamano later weighed in, stating he is "indifferent" about the immediate decision (whether to keep or drop patch 5/5) but expects the guard to be implemented in the **medium term**. In a follow-up email, Patrick explicitly stated he does not object to merging the series as-is, deferring the guard to a later patch. This removes the last open question from the thread: the series will proceed without the guard, and the medium-term safety measure is acknowledged but decoupled.
