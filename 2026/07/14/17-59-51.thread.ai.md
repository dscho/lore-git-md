This thread is the root of a 5-patch series (v1) by René Scharfe introducing repository-aware variants of the tempfile and lockfile APIs (`repo_create_tempfile`, `repo_hold_lock_file_for_update`, etc.) as part of the ongoing `the_repository` removal effort. The changes are mechanical and confined to plumbing, with no expected user-visible behavior changes.

The existing non-repo entry points are converted into thin wrappers that call the repo-aware variants with `the_repository`.
- Patch 4/5 removes the now-unused compatibility wrappers `create_tempfile_mode()` and `create_tempfile()` after all callers have been migrated to the new `repo_create_tempfile*` variants. **Design discussion and open questions**:
1. In review of patch 1/5, Patrick Steinhardt raised a substantive technical point questioning whether passing a full `struct repository *` is overkill when only the `core.sharedRepository` setting is needed. He suggested an alternative: letting callers pass the configuration value directly, but acknowledged this could lead to code duplication. He also noted the thin wrapper in `tempfile.c` could have been an inline function in the header, but dismissed it as a minor nit. René responded by acknowledging the conceptual tension—`create_tempfile()` sounds generic but is repository-specific due to shared permissions—and agreed that a repository-less variant could be cleaner in theory. However, he argued that in practice, every caller already has access to at least `the_repository`, making the current design sufficient. The exchange leaves the door open for future refactoring if a genuine need for a repository-less API emerges, but neither party sees an immediate use case. This discussion does not alter the series’ trajectory; no v2 is expected for this point.
2. In his substantive review of patch 5/5, Patrick requested two clarifications:
   - **Selection rationale**: The commit message should briefly explain why the converted callers were chosen (e.g., "callers that already accept a `struct repository *`") to make the partial migration explicit and avoid confusion about future work.

This is suggested as a follow-up commit to enforce the migration’s goals and align with the project’s preference for mechanical safety checks.
