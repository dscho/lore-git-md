This thread is about improving the performance of `git last-modified`, a command Toon Claes introduced to quickly find the last commit that modified each file in a directory. The original concern was that `git last-modified -z -t --max-depth=0` was 2.5× slower than a hand-rolled `git log` pipeline when checking a single directory in large repositories like ziglang/zig. Jeff King (Peff) identified the bottleneck—unnecessary Bloom filter checks—and posted a proof-of-concept patch that speeds up the command by 4× (from 64 ms to 16 ms) by reusing Bloom filter logic from `revision.c`. Toon Claes benchmarked the patch on GitLab’s repositories and confirmed consistent speedups without regressions, and the two are now working on a unified patch series.

The discussion has since expanded to include real-world use cases beyond the original benchmark. Gusted, the Forgejo maintainer, chimed in to note that Forgejo’s needs mirror GitLab’s: both projects retrieve the last-modified commit for every file in a directory, not just a single file. Forgejo’s current fallback—repeated `git log` calls for paths not found in the first batch—scales poorly on large repositories, sometimes taking minutes instead of milliseconds. This reinforces the value of the optimization effort, as the patch should improve performance for both single-file and batch use cases. No new technical questions or objections have been raised, and the thread remains focused on refining and integrating Peff’s patch.
