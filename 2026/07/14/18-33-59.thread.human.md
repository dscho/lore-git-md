This thread is about improving the performance of `git last-modified`, a command Toon Claes introduced to efficiently retrieve the last commit that modified each file in a directory. The command was found to be 2.5× slower than a hand-rolled `git log` pipeline when run on the ziglang/zig repository, due to an inefficient design that checked every path in the target directory against every commit’s Bloom filter. Jeff King (Peff) identified the root cause and posted a proof-of-concept patch that reuses Bloom filter logic from `revision.c` to pre-filter commits, achieving a 4× speedup (from 64 ms to 16 ms) in benchmarks.

Peff and Toon have since coordinated on the patch’s implementation, with Peff clarifying how to cleanly expose the internal Bloom filter helper without leaking `rev_info` internals. Toon benchmarked the patch on GitLab’s repositories (`gitlab-org/gitlab` and `gitlab-org/gitaly`), confirming consistent speedups (1.13×–1.56×) with no regressions. Gusted, the Forgejo maintainer, noted that Forgejo’s use case (retrieving last-modified commits for directory entries) aligns with GitLab’s and that its current fallback to repeated `git log` calls scales poorly on large repositories. The patch is now on track for a unified v2 series, with no major open questions remaining. The only unresolved item is whether GitHub’s internal `blame-tree` implementation (the inspiration for `last-modified`) has already solved this problem, but that’s deferred for now. The patch is not yet queued in any integration branch.
