This thread is about improving the performance of `git last-modified`, a command Toon Claes introduced to quickly find the last commit that modified a given file or directory. The initial discussion revealed that `git last-modified` was 2.5× slower than a hand-rolled `git log` pipeline for single-file queries, prompting Jeff King (Peff) to diagnose the issue: `last-modified` was inefficiently checking every path against every commit’s Bloom filter, while the `git log` pipeline used a more scalable single-pass subtree walk. Peff posted a proof-of-concept patch that cut runtime from 64 ms to 16 ms by reusing Bloom filter logic from Git’s revision machinery, and Toon confirmed the patch delivered consistent speedups (1.13×–1.56×) on GitLab’s large repositories without regressions.

The latest update clarifies that Peff’s patch only addresses the single-file case, leaving an earlier batch-performance issue unresolved. Forgejo, a GitLab alternative, currently uses a clever but potentially inefficient `git log` pipeline to fetch last-modified commits for every file in a directory, which scales poorly on large repositories. Toon suggests that `git format-rev` (introduced in Git 2.55) might offer a better solution for batch processing, though he hasn’t tested this yet. The thread remains collaborative, with Toon and Peff aligned on a refactoring strategy for the patch, but no new code has been posted. The open questions now include whether `format-rev` can replace Forgejo’s current approach and whether the patch might regress performance in edge cases, though Peff and Toon agree this is unlikely. No maintainer has queued the patch yet, and GitHub’s internal `blame-tree` implementation—mentioned as a potential reference—hasn’t been discussed further.
