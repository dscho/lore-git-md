The thread is about the performance of `git last-modified`, a command authored by Toon Claes that shows when files in a directory were last modified. A Forgejo contributor noticed it was 2.5× slower than a hand-rolled `git log` pipeline when run on the ziglang/zig repository. Jeff King (Peff) investigated and found the root cause: `last-modified` inefficiently checks every path in the target directory against every commit’s changed-path Bloom filter, while `git log` uses a single Bloom filter key derived from the pathspec to narrow the commit set.

Peff attached a proof-of-concept patch that refactors `last-modified` to reuse the Bloom filter logic from `revision.c`, reducing runtime from 64 ms to 16 ms—faster than the hand-rolled pipeline. The patch touches `builtin/last-modified.c`, `revision.c`, and `revision.h`, exposing an internal helper and adding a new wrapper to check Bloom filter keys. While the patch is functional, Peff raised open questions about edge cases (non-literal pathspecs, potential regressions in frequently modified directories) and whether GitHub’s internal `blame-tree` implementation already addresses this. He cc’d Taylor Blau, suggesting GitHub’s team might have relevant experience, but does not plan to drive the patch further himself. No reviews or decisions have been made yet.
