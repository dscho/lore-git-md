Subject: [PATCH v2] show-branch: use commit-slab for per-commit state instead of object.flags
Series version: v2 (standalone patch, supersedes an earlier RFC by Meet Soni)
Originating author: Gatla Vishweshwar Reddy
Thread type: refactoring patch

Core problem or goal
Refactor `builtin/show-branch.c` to eliminate its reliance on the shared `object.flags` field for per-commit state, replacing it with a dedicated commit-slab (`commit_rev_flags`) that uses `uint64_t` storage. This removes the risk of flag-bit collisions with other subsystems, aligns the code with Git’s canonical pattern for per-commit data storage, and lifts the previous 27-branch limit to 62 branches.

Current status
Under review. This is the second iteration of the patch, addressing Junio C Hamano’s review feedback on the earlier RFC (by Meet Soni) to widen the slab element from 32-bit to 64-bit storage. Junio’s latest review identifies conceptual gaps: the slab’s fixed-width design does not fully exploit its flexibility, and the UNINTERESTING bit (used for revision walking) should remain in `object.flags` rather than being moved to the slab. Jeff King (Peff) endorses Junio’s critique and points to prior art (a 2025 variable-length bitset slab series) as a model for a v3 that could handle an arbitrary number of branches without a hard limit. No merge status reported; the patch remains in the review phase, awaiting a redesign.

Key technical details
- Files touched: `builtin/show-branch.c` only
- New symbols: `commit_rev_flags` slab (now `uint64_t[1]`), `get_rev_flags()`, `or_rev_flags()` helpers
- Old behavior: direct access to `commit->object.flags` for per-commit state, limited to 27 branches due to 32-bit storage
- New behavior: slab-based storage with `uint64_t` elements, lifting the branch limit to 62, but with noted design limitations (fixed-width slab, UNINTERESTING bit placement)
- Test coverage: unchanged (existing tests continue to pass)
- Delta from v1: widened slab element to `uint64_t`, updated bit-shift operations to use `UINT64_C(1)`, adjusted format specifiers for `size_t` results
- Open technical concerns: (1) fixed `uint64_t[1]` slab element vs. variable-length bitset (prior art exists), (2) UNINTERESTING bit should remain in `object.flags`, (3) type mismatch in `omit_in_dense()` where `flag` remains `int` while bit-shifts use `uint64_t`, (4) minor indentation nit
- Prior art: 2025 series introducing a variable-length bitset slab (commit 20250225011757.GA752084), which could be reused or adapted for this patch

Open questions and loose ends

- Is the `omit_in_dense()` type mismatch a blocker for correctness on 32-bit platforms?
