Subject: [PATCH v2] show-branch: use commit-slab for per-commit state instead of object.flags
Series version: v10 (standalone patch, supersedes v9, v8, v7, v6, v5, v4, v3, and v2 by Gatla Vishweshwar Reddy, and an earlier RFC by Meet Soni)
Originating author: Gatla Vishweshwar Reddy
Thread type: refactoring patch

Core problem or goal
Refactor `builtin/show-branch.c` to eliminate its reliance on the shared `object.flags` field for per-commit state, replacing it with a dedicated commit-slab (`commit_rev_flags`) that uses a runtime-computed stride of `uint64_t` words. This removes the risk of flag-bit collisions with other subsystems, aligns the code with Git’s canonical pattern for per-commit data storage, and removes the previous 27-branch limit entirely by dynamically growing arrays and calculating `flags_stride` as `(ref_name_cnt + 63) / 64`. The `UNINTERESTING` bit remains in `object.flags` for revision-walking compatibility.

Key technical details
- Files touched: `builtin/show-branch.c` (primary refactoring), `Documentation/git-show-branch.adoc` (limit removal), `t/t3202-show-branch.sh` (new tests)
- New symbols: `commit_rev_flags` slab (runtime-computed stride of `uint64_t` words), `flags_stride`, `get_rev_flags_ptr()`, `peek_rev_flags_ptr()`, `has_any_rev_flags()`, `or_rev_flag_bit()`, `test_rev_flag_bit()`, `has_only_rev_flag_bit()`, `has_all_rev_flags()`, `has_subset_rev_flags()` helpers
- Old behavior: direct access to `commit->object.flags` for per-commit state, limited to 27 branches due to 32-bit storage; `show_independent()` checks for *exactly* the current branch’s bit set; `join_revs()` propagates `UNINTERESTING` to parents and avoids redundant traversal by skipping parents that have *at least* the flags of the current commit
- New behavior: slab-based storage with runtime-computed stride, removing the branch limit entirely. The `UNINTERESTING` bit remains in `object.flags` for revision-walking compatibility. The regression in `show_independent()` was fixed in v4 via `has_only_rev_flag_bit()`, the regressions in `join_revs()` (propagation of `UNINTERESTING` and redundant traversal avoidance) were fixed in v6, and the performance regression in `join_revs()` (subset checking) was fixed in v7 via `has_subset_rev_flags()`. Documentation no longer mentions any branch limit, and the `%zu` format specifier has been replaced with `%lu` and an explicit `(unsigned long)` cast. Three new tests in `t3202-show-branch.sh` verify correct operation with 30+ branches, including `--independent` and `--merge-base` modes. The v9 regression (division-by-zero crash due to uninitialized `name_slab`) is fixed in v10 by restoring `init_commit_name_slab(&name_slab)` before `repo_config()`. The root cause of the regression is explained: the `name_slab` initialization was accidentally removed during a v7 restructuring that moved the `rev_flags_slab` initialization after ref collection, leaving `slab_size` at 0. The intentional use of a `{}` block in `join_revs()` to scope the `commit_is_merge_base` variable after `mark_seen()` is clarified as required by C99.
- Test coverage: existing tests continue to pass; new tests in `t3202-show-branch.sh` cover 30+ branches, `--independent`, and `--merge-base` modes. Junio notes that the crash revealed a gap in test coverage for the `name_slab` initialization, and Gatla has asked whether a minimal smoke test should be added to address this.
