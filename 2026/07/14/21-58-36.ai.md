This is a **follow-up in the `no-ref-delta` capability thread**, where Taylor Blau responds to Jeff King’s substantive review of the series. The exchange clarifies the motivation behind the feature and addresses Peff’s technical concerns, though some questions remain open.

The core use case is now explicit: the feature supports a **write-through proxy** that spools incoming packs byte-for-byte and replays them upstream before allowing local ref updates. The proxy avoids indexing the pack upfront, instead deriving an object index asynchronously in a single forward pass. `REF_DELTA` entries would complicate this design by requiring an OID lookup or a second pass, so the `no-ref-delta` capability ensures the pack contains only `OFS_DELTA` entries, which can be resolved without an object ID index. This explanation fills the gap Peff identified in the cover letter, though Taylor notes the description is intentionally generic due to constraints on discussing the full system.

On thin packs, Taylor confirms the implementation already advertises `no-thin`, and `send-pack` honoring `no-ref-delta` cannot produce a thin pack (since external bases would require `REF_DELTA`). Older clients ignoring the capability may still send rejected packs, but the receiver’s behavior remains unchanged. If a `REF_DELTA` slips through, the receiver rejects the pack before updating refs. This answers Peff’s interoperability question but leaves the fallback behavior for unexpected deltas as a potential edge case for future discussion.

The response also clarifies the bitmap pack reuse edge case: it’s a correctness safeguard, not part of the motivation. The series ensures `pack-objects --no-ref-delta` behaves consistently even when verbatim reuse occurs. Peff’s concern about pack reuse in client-to-server pushes is acknowledged but deemed non-critical.

Key technical details for follow-ups:
- The **write-through proxy** is the primary use case, though details are limited.
- **Thin packs** are already handled via `no-thin`, and `no-ref-delta` enforces `OFS_DELTA`-only packs.
- **Fallback behavior** for unexpected `REF_DELTA` entries is rejection, but the series doesn’t address how the receiver might recover or retry.
- **Delta reuse** is now explicitly scoped to correctness, not optimization.

The thread is now better grounded in a real-world scenario, but the discussion may continue around safety (e.g., whether rejecting packs is sufficient) and whether the design aligns with Git’s broader protocol principles. The series still feels like a niche optimization, but the motivation is no longer unclear.
