This is a substantive review in the ongoing packfile URI race-condition bugfix series. Jeff King (Peff) engages directly with the design trade-offs in Patch 1, where Ted Nyman proposed using unique temporary files for each packfile URI download to avoid corruption from concurrent processes.

Peff suggests treating the `.pack.temp` file as a lockfile and applying Git’s existing lockfile logic—auto-removing files with ancient modification times or even checking process liveness via PID. He also questions whether the resumption capability (currently preserved for dumb HTTP but broken for packfile URIs in this patch) is worth sacrificing, noting that both transport types face the same concurrency and resumption challenges. His tone is pragmatic: if the project is willing to drop resumption for now, the unique-tempfile approach is a reasonable starting point, with coordination logic deferred to a follow-up if needed.

The review does not propose code changes or reject the patch outright, but it surfaces a key architectural question: should the fix prioritize simplicity and correctness (as Ted argues) or preserve resumption and consistency between dumb HTTP and packfile URIs? The thread remains open on this point, though Peff’s framing suggests he leans toward Ted’s approach as a short-term solution. No new test failures or edge cases are identified; this is purely a design-level discussion.
