This is a substantive review in the ongoing packfile URI race-condition bugfix thread. Jeff King (Peff) engages with the design trade-offs in Patch 1, focusing on the tension between correctness, simplicity, and the ability to resume interrupted downloads.

Peff suggests treating the `.pack.temp` file as a lockfile, borrowing Git’s existing lockfile logic (e.g., auto-removing files with ancient mtimes or checking process liveness via PID). He also questions whether the current design’s abandonment of resumable downloads for packfile URIs is an acceptable trade-off, noting that dumb HTTP and packfile URIs face the same concurrency and resumption problems but are now handled differently. His concern is whether this inconsistency is justified or whether it introduces new edge cases.

The review implicitly endorses Ted Nyman’s argument for deferring coordination logic to a follow-up, provided the project is comfortable sacrificing resumption for packfile URIs. Peff’s tone suggests this is a reasonable short-term fix, but the question of whether resumption should be preserved (and how) remains open. No code-level feedback is provided; this is purely a design discussion. The thread is now aligned on a "fix first, optimize later" approach, pending Junio C Hamano’s final verdict. Key technical details to track: the fate of resumable downloads, potential lockfile-style coordination, and whether dumb HTTP and packfile URIs will eventually share a unified solution.
