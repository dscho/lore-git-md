This is the first patch in Paulius Zaleckas’s two-part series introducing configurable submodule fetch errors, now at v4. The patch fixes a long-standing logic flaw in Git’s submodule fetch error handling that has been documented as `NEEDSWORK` since 2019.

The issue is straightforward: when `git fetch --recurse-submodules` fails to fetch a submodule’s refs (phase 1), it immediately marks the entire operation as failed, even though Git will next attempt an OID-based fetch (phase 2) for any missing commits. If phase 2 succeeds, the overall fetch should succeed, but the premature failure flag makes it appear as an error. The patch restructures the error-handling logic in `fetch_finish()` to defer the decision until after phase 2 has run, ensuring errors are only recorded if both phases fail.

The fix is clean and well-motivated. It extracts the common error-recording logic into a helper (`record_fetch_error()`), updates the existing error paths to use it, and adds clear comments explaining the new control flow. The patch also includes a new test that verifies a failed submodule fetch is still reported even when the gitlinked commits happen to be present locally, closing a subtle edge case.

This is a bugfix with no user-visible behavior change—it preserves the current fatal behavior while enabling the configurable policy introduced in the second patch. The commit message is thorough, the code is well-structured, and the test coverage is solid. No open questions remain, and the patch looks ready for review.
