This is the final patch in Pablo Sabater’s GSoC v17 series implementing `git cat-file --batch-command` support for querying remote object metadata. The patch adds the user-facing `remote-object-info` command, completing a 17-iteration effort to enable secure, batched object metadata queries without full downloads.

Junio Hamano’s review of this patch identified the **only remaining technical issue** in the series: a bounds-checking vulnerability in the response parsing logic. The code currently accesses `object_info_values.items[1 + size_index]` without verifying that the `string_list` contains enough elements, risking an out-of-bounds read if a server returns fewer values than expected. Pablo acknowledges the issue and plans to add a guard to treat responses with only `<oid>` (no trailing space) as corrupted, matching the existing validation for invalid size values. This fix is straightforward and will address the security concern while maintaining compatibility with the protocol’s expected behavior.

The patch is otherwise complete and well-reviewed. It implements the core `remote-object-info` command with:
- **Multi-object batching** (up to 10,000 objects per request)
- **Strict input validation** (8KB URL length limit, OID format checks)
- **Transport support** for `git://`, `file://`, and `http://`
- **Error handling** for unsupported capabilities, missing objects, and malformed responses
- **699 lines of new tests** covering edge cases and error conditions
- **Dynamic placeholder validation** (via capability-based filtering, added in earlier patches)

The series has resolved all prior feedback, including memory leaks, type mismatches, static variable misuse, and segfault risks in format placeholder handling. Junio’s review also suggested minor stylistic improvements (line wrapping in a `for` loop and preferring `size_index + 1` over `1 + size_index`), which Pablo has accepted.

This patch is ready for merging once the bounds-checking fix is applied. The series represents a significant security-hardening effort, with rigorous attention to memory safety, protocol compliance, and edge-case handling. The remaining issue is a targeted fix rather than a design flaw, and the implementation is otherwise robust and well-tested.
