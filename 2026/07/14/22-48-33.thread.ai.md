Subject: [PATCH 0/11] Coverity: unchecked return values
Series version: v2 (second posting, incorporating six fixup patches addressing Junio’s correctness concerns and Patrick Steinhardt’s design suggestions; now with two additional correctness issues identified in the third and eleventh patches)
Originating author: Johannes Schindelin via GitGitGadget
Thread type: patch series

Core problem or goal
Coverity static analysis identified 11 instances where Git code ignores return values from functions that can fail (e.g., `curl_easy_duphandle`, `deflateInit`, `repo_parse_commit`, `lseek`, `dup`, `strbuf_getline_lf`, `launch_editor`, `reftable_table_init_ref_iterator`, and `rename`). The series adds missing error checks to harden these code paths against silent failures, without introducing new behavior or changing on-disk formats.

Current status
Under review; v2 posted incorporating all substantive review feedback. Two patches now have open correctness issues:
- The third patch (`reftable/block.c`: check `deflateInit()` return value) has a memory leak: if `deflateInit()` fails, the `bw->zstream` memory allocated by `REFTABLE_CALLOC_ARRAY` is not freed. Junio C Hamano’s review proposes adding `REFTABLE_FREE_AND_NULL(bw->zstream)` before returning `REFTABLE_ZLIB_ERROR` to ensure cleanup. The broader error-handling issue in the reftable backend—where callers of `block_writer_init()` (e.g., `writer_reinit_block_writer()`) propagate errors, but their callers (e.g., `reftable_writer_new()`) do not always check return values—may require additional scrutiny to prevent inconsistent `block_writer` states.
- The eleventh patch (`bisect.c`: check `dup()` and `dup2()` return values) has a resource leak: if `dup2(temporary_stdout_fd, 1)` fails, the code breaks out of the bisect-run loop without closing the file descriptor stored in `saved_stdout`, which was successfully duplicated by the preceding `dup(1)` call. Jeff King (Peff) identified this issue, confirming it is a real leak introduced by the patch itself. The fix will require an additional `close(saved_stdout)` call in the error path before breaking out of the loop.
All other patches in the series remain technically complete and uncontroversial; no maintainer decision yet, and no integration branch assigned.

Key technical details
Files touched: `http.c`, `builtin/config.c`, `reftable/block.c`, `t/unit-tests/t-reftable-block.c`, `builtin/last-modified.c`, `compat/pread.c`, `transport-helper.c`, `bisect.c`, `builtin/bisect.c`, `t/unit-tests/u-reftable-table.c`.
New symbols: none.
Behavior changes: none; only fatal error paths (`die()`) or propagation to caller added, except in `transport-helper.c` where a non-fatal `warning_errno()` is now emitted for a failed `rename()`. Specific fixes:
- `http.c`: `get_active_slot()` now checks `curl_easy_duphandle()` return value for NULL, calling `die()` on failure to prevent undefined behavior in `curl_easy_setopt()`. This patch (first in v2) is uncontroversial and ready for integration.
- `builtin/config.c`: `show_editor()` now propagates `launch_editor()` failure upward by returning `-1`, ensuring `git config edit` and `git config --edit` exit with an error rather than silently succeeding. Patrick Steinhardt reviewed this patch and confirmed the approach is correct, as `launch_editor()` already emits its own error messages. The change aligns `git config`’s editor-launching behavior with other Git commands like `git commit` and `git rebase --edit-todo`.
- `reftable/block.c`: `block_writer_init()` now checks `deflateInit()` return value and propagates failures via `REFTABLE_ZLIB_ERROR`, preventing silent data corruption or crashes when `deflate()` is later called with an uninitialized `z_stream`. The fix is minimal (two lines added, one removed) but now requires an additional `REFTABLE_FREE_AND_NULL(bw->zstream)` call before returning `REFTABLE_ZLIB_ERROR` to avoid leaking the `zstream` memory allocated by `REFTABLE_CALLOC_ARRAY`. Junio’s review also notes that the broader reftable backend may have unchecked errors in the call graph above `block_writer_init()`, risking inconsistent `block_writer` states if `reftable_writer_new()` or other callers do not check return values.
- `compat/pread.c`: `git_pread()` now checks the return value of the first `lseek(fd, 0, SEEK_CUR)` call; if it fails (e.g., on a non-seekable descriptor like a pipe), the function returns `-1` immediately, preventing a subsequent `lseek(fd, -1, SEEK_SET)` call that would either fail with `EINVAL` or silently corrupt the file position. The indentation inconsistency noted by Patrick Steinhardt (tabs in new code vs. spaces in the rest of the file) does not affect the patch’s technical correctness. The patch is explicitly confirmed as ready for integration.
- `transport-helper.c`: `get_exporter()` now checks the return value of `dup(helper->in)`. If `dup()` fails (e.g., due to file descriptor exhaustion), the error is propagated upward with `error_errno()`, preventing the `child_process` machinery from silently redirecting `fast-export` output to an unread pipe, which would break data flow between the helper and the exporter. Additionally, `push_refs_with_export()` now checks the return value of `rename()` when finalizing the fast-export marks file; if the rename fails, a `warning_errno()` message is emitted naming both the source and destination paths, allowing manual recovery without aborting the push operation. Patrick Steinhardt reviewed the seventh patch and confirmed its correctness, noting that the only caller (`push_refs_with_export()`) already handles non-zero return values by dying.
- `builtin/last-modified.c`: three calls to `repo_parse_commit()` now check return values; on failure, the commit (or parent) is skipped rather than proceeding with uninitialized data, ensuring "last modified" results are not silently incorrect. The error path now uses `goto cleanup` to ensure the `active_paths` slab is released even when the commit is unparsable. The patch directly addresses Junio’s v1 review concern about proceeding with uninitialized commit data and follows the defensive pattern used in other revision walkers like `limit_list()` and `get_revision_internal()`.
- `bisect.c` and `builtin/bisect.c`: `get_terms()` and `read_bisect_terms()` now check the return value of `strbuf_getline_lf()`. In `get_terms()`, a truncated `BISECT_TERMS` file returns `-1`, matching the existing behavior for a missing file. In `read_bisect_terms()`, a truncated file now calls `die()` with a descriptive message, ensuring the user is alerted rather than proceeding with empty or invalid term names. The ninth patch adds error checks at both call sites of `strbuf_getline_lf()` in `get_terms()` and `read_bisect_terms()`; previously, a failed `strbuf_getline_lf()` would leave `term_bad` and `term_good` as `NULL` or empty, leading to confusing downstream behavior (e.g., nonsensical ref names like `refs/bisect/` with no suffix). The new checks ensure a clear error is returned or a descriptive `die()` message is emitted. The `FREE_AND_NULL(terms->term_bad)` addition in `get_terms()` prevents a resource leak if the second `strbuf_getline_lf()` fails. The tenth patch centralizes error handling in `get_terms()` itself by extending its signature to accept a `file_missing_is_ok` flag, so that the function now returns an error if either `term_bad` or `term_good` is `NULL`, deduplicating error messages at the call sites and simplifying the callers. Junio’s review of the tenth patch accepts the boolean-flag design as an acceptable trade-off for an internal function with a single caller requiring distinct behavior, noting that distinct error codes would be preferable only if `get_terms()` were a public API with many callers. The eleventh patch (`bisect.c`) now checks the return values of both `dup(1)` and `dup2(temporary_stdout_fd, 1)`; if either call fails, the code emits an `error_errno()` message, closes the temporary file descriptor, and breaks out of the bisect-run loop. However, if `dup2()` fails, the code does not close the file descriptor stored in `saved_stdout`, which was successfully duplicated by the preceding `dup(1)` call, resulting in a resource leak. This issue was introduced by the patch itself and must be fixed with an additional `close(saved_stdout)` call in the error path.
- `t/unit-tests/u-reftable-table.c`: `test_reftable_table__seek_once()` and `test_reftable_table__reseek()` now check the return value of `reftable_table_init_ref_iterator()`; if initialization fails, the test fails with an assertion error rather than proceeding with an uninitialized iterator. The change is minimal (two lines added) and matches the error-checking pattern used elsewhere in the same test file.
On-disk format changes: none.
Test coverage: unchanged; unit tests in `t-reftable-block.c` and `t-reftable-table.c`, and the existing config, last-modified, transport-helper, and bisect test suites implicitly exercise the new error paths.
