Thread identity: inquiry about performance of the `git last-modified` command (Toon Claes, 2025), comparing its speed to a hand-rolled `git log` pipeline on the ziglang/zig repository.

Core problem or goal: determine why `git last-modified -z -t --max-depth=0` is 2.5× slower (66 ms vs 26 ms) than an equivalent `git log --name-status -c --format=... --parents --no-renames -t -z` pipeline when both are run against the same commit and path filter (`doc/langref/`) in a repository with a precomputed commit-graph and changed-path Bloom filters, and explore optimizations to close the gap.

Current status: under review; Jeff King (Peff) has posted a proof-of-concept patch that reduces runtime from 64 ms to 16 ms by reusing Bloom filter logic from `revision.c` to pre-filter commits. The patch is not yet queued in any integration branch.

Key technical details: command under test is `git last-modified` (authored by Toon Claes); benchmark repository is ziglang/zig; both commands use the same commit and path filter; repository has commit-graph with changed-path Bloom filters. The inefficiency in `last-modified` stems from checking every path in the target directory against every commit’s Bloom filter (290 × 39,000 comparisons in the example), whereas `git log` uses a single Bloom filter key derived from the pathspec. Peff’s patch refactors `last-modified` to reuse the Bloom filter logic from `revision.c`, exposing an internal helper (`prepare_to_use_bloom_filter`) and adding a new wrapper (`filter_contains_keyvec`). The patch touches `builtin/last-modified.c`, `revision.c`, and `revision.h`; introduces no new user-visible options or behavior changes; and relies on existing commit-graph and Bloom filter infrastructure.
