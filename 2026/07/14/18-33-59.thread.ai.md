Thread identity: inquiry about performance of the `git last-modified` command (Toon Claes, 2025), comparing its speed to a hand-rolled `git log` pipeline on the ziglang/zig repository and other large repositories (gitlab-org/gitlab, gitlab-org/gitaly, Forgejo).

Core problem or goal: determine why `git last-modified -z -t --max-depth=0` is 2.5× slower (66 ms vs 26 ms) than an equivalent `git log --name-status -c --format=... --parents --no-renames -t -z` pipeline when run against the same commit and path filter in a repository with a precomputed commit-graph and changed-path Bloom filters. The inefficiency stems from `last-modified` checking every path in the target directory against every commit’s Bloom filter (e.g., 290 × 39,000 comparisons in ziglang/zig), whereas the `git log` pipeline uses a single Bloom filter key derived from the pathspec to pre-filter commits. The discussion now distinguishes two distinct performance issues: (1) the single-file case, where Peff’s patch achieves a 4× speedup by reusing Bloom filter logic from `revision.c`, and (2) the batch-processing case (e.g., retrieving last-modified commits for every entry in a directory), where `last-modified`’s current implementation remains inefficient compared to a hand-rolled `git log` pipeline. Forgejo’s use case (batching directory entries) and GitLab’s identical use case are now central to the discussion, as both tools require scalable batch performance.

Current status: under review; Peff’s proof-of-concept patch for the single-file case reduces runtime from 64 ms to 16 ms (4× speedup) and has been benchmarked by Toon on GitLab’s repositories (`gitlab-org/gitlab` and `gitlab-org/gitaly`), confirming consistent speedups (1.13×–1.56×) with no regressions. Peff and Toon are aligned on a refactoring strategy for the patch: splitting the internal `check_maybe_different_in_bloom_filter()` helper into two parts—one to fetch the Bloom filter and another to check it against the `rev_info`—and exposing only the latter to avoid direct access to `rev_info` internals. The batch-processing case remains unaddressed; Toon has identified `git format-rev` (introduced in Git 2.55) as a potential alternative for batch processing but has not yet tested it. Forgejo’s current implementation (a `git log` pipeline that falls back to inefficient repeated calls for paths not found in the first batch) scales poorly on large repositories (minutes vs milliseconds), and its maintainer (Gusted) has confirmed the need for a more efficient solution. The patch is not yet queued in any integration branch.

Key technical details: command under test is `git last-modified` (authored by Toon Claes); benchmark repositories include ziglang/zig, gitlab-org/gitlab (~530k commits), and gitlab-org/gitaly (~23k commits). The optimization for the single-file case refactors `last-modified` to reuse Bloom filter logic from `revision.c`, exposing an internal helper (`check_maybe_different_in_bloom_filter`) in a cleaner way by splitting it into two functions: one to fetch the Bloom filter and another to check it against the `rev_info`. The patch touches `builtin/last-modified.c`, `revision.c`, and `revision.h`; introduces no new user-visible options or behavior changes; and relies on existing commit-graph and Bloom filter infrastructure. GitLab’s real-world workload batches 25 files at once, where `last-modified` already outperforms the naive loop, but the single-file case remains a regression. Forgejo’s use case is identical to GitLab’s batching scenario, but its current implementation falls back to inefficient `git log` calls for paths not found in the first batch. The `git log` pipeline’s efficiency comes from its single-pass subtree walk, which scales with the number of commits that modified the subtree rather than the total repository size. Toon has suggested `git format-rev` (introduced in Git 2.55) as a potential alternative for batch processing, though this has not yet been tested or benchmarked.
