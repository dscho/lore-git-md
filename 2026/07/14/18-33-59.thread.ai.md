Thread identity: inquiry about performance of the `git last-modified` command (Toon Claes, 2025), comparing its speed to a hand-rolled `git log` pipeline on the ziglang/zig repository.

Core problem or goal: determine why `git last-modified -z -t --max-depth=0` is 2.5× slower (66 ms vs 26 ms) than an equivalent `git log --name-status -c --format=... --parents --no-renames -t -z` pipeline when both are run against the same commit and path filter (`doc/langref/`) in a repository with a precomputed commit-graph and changed-path Bloom filters, and explore optimizations to close the gap. The inefficiency stems from `last-modified` checking every path in the target directory against every commit’s Bloom filter (e.g., 290 × 39,000 comparisons in the ziglang/zig case), whereas `git log` uses a single Bloom filter key derived from the pathspec.

Current status: under review; Jeff King (Peff) posted a proof-of-concept patch that reduces runtime from 64 ms to 16 ms (4× speedup) by reusing Bloom filter logic from `revision.c` to pre-filter commits. Toon Claes, the command’s author, has benchmarked the patch on GitLab’s repositories (`gitlab-org/gitlab` and `gitlab-org/gitaly`), confirming consistent speedups (1.13×–1.56×) with no regressions. Gusted, the Forgejo maintainer, has now confirmed that Forgejo’s use case (retrieving last-modified commits for every entry in a directory) aligns with GitLab’s, and that Forgejo’s current fallback to repeated `git log` calls scales poorly on large repositories (minutes vs milliseconds). Toon and Peff are coordinating on a unified patch series; the patch is not yet queued in any integration branch.

Key technical details: command under test is `git last-modified` (authored by Toon Claes); benchmark repositories include ziglang/zig, gitlab-org/gitlab (~530k commits), and gitlab-org/gitaly (~23k commits). The optimization refactors `last-modified` to reuse Bloom filter logic from `revision.c`, exposing an internal helper (`check_maybe_different_in_bloom_filter`) and adding a new wrapper (`filter_contains_keyvec`). The patch touches `builtin/last-modified.c`, `revision.c`, and `revision.h`; introduces no new user-visible options or behavior changes; and relies on existing commit-graph and Bloom filter infrastructure. GitLab’s real-world workload batches 25 files at once, where `last-modified` already outperforms the naive loop, but the single-file case remains a regression. Forgejo’s use case is identical to GitLab’s batching scenario, but its current implementation falls back to inefficient `git log` calls for paths not found in the first batch.
