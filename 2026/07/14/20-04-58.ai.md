This is an **RFC proposal** from a user seeking workflow optimizations for large repositories with long-running branches and merge-heavy histories. The author, Richard Fine, describes two pain points in their company’s Git usage—**squash-merging resistance** and **shallow clone limitations**—and proposes two Git enhancements to address them:

1. **Persistent shallow fetch options**: A config setting (e.g., `remote.origin.shallowsince`) to enforce `--shallow-since` behavior for all fetches from a remote, regardless of how the fetch is triggered (CLI, UI tools, or automation). This would prevent accidental deep fetches when pulling merge commits with ancient second-parent histories.

2. **Fake-linear mainline**: A mechanism to treat merge commits as linear (ignoring their second parent) until explicitly expanded, using `.git/shallow` or replace refs to mask branch history. The goal is to reduce repository size while preserving the *option* to inspect branch details on demand.

### Context and Motivation
Richard’s team uses a **branch-and-PR model with merge commits**, leading to bloated repositories when long-running branches (based on old revisions) are merged. Shallow clones (`--shallow-since`) help, but merges with old second parents bypass the shallow boundary, forcing users to manually specify `--shallow-since`—a non-starter for non-CLI workflows (e.g., GUI tools, AI agents). The proposals aim to automate this enforcement and reduce history bloat without requiring workflow changes (e.g., rebasing or squash-merging).

### Technical Feasibility
- **Persistent shallow options**: This seems straightforward to implement as a config-driven wrapper around fetch logic. It would require minimal changes to the fetch codepath and could reuse existing shallow machinery.
- **Fake-linear mainline**: More complex. The idea resembles **replace refs** or **partial clones**, but with dynamic toggling. Challenges include:
  - Ensuring `git gc` respects the "masked" state (to avoid pruning still-needed commits).
  - Handling incremental fetches without pulling full history first.
  - Potential edge cases with reachability (e.g., `git log --follow`, bisect).

### Likely Discussion Points
1. **Workarounds vs. New Features**: Reviewers may suggest existing tools (e.g., `--filter=tree:0` for partial clones, `git replace` for masking parents) before endorsing new features.
2. **Performance vs. Correctness**: The fake-linear idea risks breaking Git’s reachability guarantees (e.g., for `git blame`, `git bisect`). The tradeoff between performance and correctness will likely be debated.
3. **Adoption Barriers**: Both proposals require users to opt in, but the fake-linear approach might confuse users if not carefully designed (e.g., clear documentation, tooling support).

### Next Steps
Richard is offering to implement the persistent shallow option if there’s interest. The fake-linear idea is more speculative but could spark discussion about **history pruning** or **merge commit handling**. Expect feedback on:
- Whether the problems are common enough to warrant new features.
- Alternative approaches (e.g., extending `git clone --filter`).
- Edge cases (e.g., how `git fetch --unshallow` interacts with persistent shallow settings).
