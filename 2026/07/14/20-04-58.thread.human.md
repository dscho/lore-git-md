This thread is an RFC from Richard Fine proposing two Git enhancements to optimize workflows in large repositories with long-running branches and merge-heavy histories. The first idea—a config setting like `remote.origin.shallowsince` to enforce `--shallow-since` behavior for all fetches—aims to prevent accidental deep fetches when pulling merge commits with ancient second-parent histories. The second, more ambitious proposal suggests a "fake-linear mainline" mechanism to treat merge commits as linear (ignoring their second parent) until explicitly expanded, reducing repository size while preserving the option to inspect branch details on demand.

Richard’s motivation stems from his team’s branch-and-PR model, where merges of long-running branches (based on old revisions) bloat repositories. While shallow clones help, they require manual intervention, which isn’t feasible for non-CLI workflows like GUI tools or automation. The proposals seek to automate this enforcement without requiring workflow changes like rebasing or squash-merging.

The persistent shallow option appears technically straightforward, leveraging existing shallow machinery, but the fake-linear idea raises questions about reachability, garbage collection, and incremental fetches. Reviewers may push back, suggesting existing tools like `--filter=tree:0` for partial clones or `git replace` for masking parents before endorsing new features. The tradeoff between performance and correctness—especially for tools like `git blame` or `git bisect`—will likely be a key discussion point. Richard has offered to implement the persistent shallow option if there’s interest, while the fake-linear idea remains speculative but could spark broader conversations about history pruning or merge commit handling. So far, no responses from maintainers or other contributors have been posted.
