This is a **follow-up explanation** in the ongoing discussion about the `no-ref-delta` capability series. Taylor Blau responds to Jeff King’s substantive review, clarifying the motivation and addressing technical concerns raised about the feature’s design.

The key revelation here is that the `no-ref-delta` capability is part of a **write-through proxy system**—a custom `receive-pack` implementation that spools incoming packs and replays them byte-for-byte to an upstream Git server. The local repository only updates refs if the upstream accepts the push, preserving the usual connectivity checks. This design treats the received pack as an immutable artifact, with indexing deferred to an asynchronous process optimized for single-pass forward scanning. Avoiding `REF_DELTA` entries simplifies this indexing by eliminating the need for an object ID lookup or multi-pass resolution, which would otherwise complicate or slow down the process.

Taylor acknowledges the cover letter’s lack of clarity on this point and explains that the system’s constraints—particularly the requirement to retain the pack verbatim—make `REF_DELTA` entries impractical. The response also addresses Jeff’s concerns about thin packs: the implementation already advertises `no-thin`, and a sender honoring `no-ref-delta` cannot generate thin packs (since external bases would require `REF_DELTA`). Older clients ignoring the capability may still send invalid packs, but the receiver rejects them before updating refs, maintaining safety.

The explanation leaves some questions open, such as whether the upstream server’s behavior (e.g., thin pack generation) could still introduce edge cases, but it provides a concrete use case that justifies the feature’s existence. The series now appears better motivated, though reviewers may still scrutinize the delta reuse logic and fallback behavior. If the write-through proxy is a real-world system (even if not fully disclosed), this capability could be a targeted optimization rather than a speculative one.
