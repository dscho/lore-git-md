This thread is about a refactoring patch to `git show-branch` that replaces its use of the shared `object.flags` field with a dedicated commit-slab, removing a long-standing 27-branch limit. The patch, now at version 7, was authored by Gatla Vishweshwar Reddy and has been under review since an earlier RFC by Meet Soni. Junio C Hamano provided detailed feedback on prior versions, addressing behavioral regressions, performance issues, and documentation inaccuracies, all of which were resolved in v7.

The patch itself is technically complete: it dynamically grows arrays at runtime, computes the slab stride from the actual number of branches, and removes all hardcoded limits. New tests verify correct operation with 30+ branches, and the code aligns with Git’s canonical pattern for per-commit data storage. However, Junio’s latest reply raises concerns about the patch’s internal consistency and the process behind its submission. He points out that the commit message claims to have removed the branch limit entirely, yet the updated documentation still mentions a 64-branch limit, and a comment about migrating to a shared `UNINTERESTING` definition remains despite the local definition being removed. These inconsistencies suggest the patch may not have been carefully reviewed before submission, casting doubt on its readiness despite the technical fixes.

Patrick Steinhardt had earlier expressed frustration with the author’s communication style, interpreting some replies as likely AI-generated and emphasizing the importance of human, community-oriented tone. Gatla acknowledged this and committed to writing his own responses, but Junio’s critique now shifts focus to the patch’s substance, reopening the review process. The patch remains under review, with no new technical issues raised—only questions about its coherence and the thoroughness of its preparation.
