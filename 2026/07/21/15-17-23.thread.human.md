This thread is about a performance regression in `git receive-pack` connectivity checks introduced by the ODB (object database) abstraction rework, specifically commit `a593373b09`. The regression, reported by Wolfgang Kritzinger (Atlassian), causes a 12% slowdown on fast filesystems and significantly worse performance on NFS-backed deployments due to excessive failing `open()` calls for loose objects across multiple ODB backends. The root cause is a change in object lookup order: the ODB rework shifted from a "pack-first, loose-second" strategy *per backend* to a "pack-loose, pack-loose" strategy *across backends*, leading to redundant loose object checks even when objects exist in packs.

The discussion has evolved from a targeted performance fix to a broader architectural redesign of ODB transactions. Patrick Steinhardt proposed a transaction-aware ODB write mechanism that bypasses the ODB source list for writes during active transactions, routing them directly to the transaction object. This would resolve the regression by avoiding loose-object checks in quarantine directories during connectivity traversals but is tied to a larger refactoring effort delayed until late July or August. Junio C Hamano initially suggested distinguishing "fast" and "slow" lookups within backends or pre-loading loose object names into an in-core table to short-circuit expensive `lstat()` calls. In his latest email, Junio clarifies that while Patrick’s long-term redesign is promising, the immediate regression still requires a targeted fix addressing the lookup order change, as demonstrated by Jeff King’s (Peff) reproduction case using the alternates mechanism.

Key participants include Wolfgang Kritzinger (reporter), Peff (who confirmed the regression and provided a test case), Taylor Blau (who offered a substantive technical analysis and proposed a two-phase lookup fix), Junio (who reframed the issue as an architectural opportunity and emphasized the need for a short-term fix), and Patrick Steinhardt (who proposed the transaction-aware ODB write redesign). The regression remains unresolved pending Patrick’s return, with open questions about how the proposed architectural changes will interact with existing ODB abstraction goals and whether additional optimizations will still be needed. The thread highlights the tension between general-purpose ODB design and specialized use cases like connectivity checks, where performance optimizations may justify application-specific solutions.
