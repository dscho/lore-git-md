This thread is about a performance regression in `git receive-pack` connectivity checks introduced by the ODB (object database) abstraction rework, specifically commit `a593373b09`. The regression, reported by Wolfgang Kritzinger (Atlassian), causes a 12% slowdown on fast filesystems and worse on NFS due to excessive failing `open()` calls for loose objects across multiple ODB backends. The root cause is a shift from a "pack-first, loose-second" lookup strategy per backend to a "pack-loose, pack-loose" strategy across backends, leading to redundant loose object checks.

Patrick Steinhardt, the author of the ODB rework, has proposed a fundamental architectural change: moving alternates handling into the "files" backend itself, treating alternates as an implementation detail rather than a cross-backend concern. This would restore pack-first-loose-second lookups across all alternates while simplifying other subsystems like commit-graph and bitmap loading. Jeff King (Peff) and Justin Tobler have both endorsed this direction, with Peff dismissing concerns about lost flexibility (e.g., combining alternates with non-files backends) as unlikely to be practical issues. Justin’s reply further clarifies that decoupling transaction handling from the ODB source list could eliminate the need to reorder sources during transactions, addressing Peff’s earlier critique about cross-process coordination.

The thread has shifted from discussing a near-term fix (e.g., targeted lookup order adjustment) to focusing on Patrick’s redesign, which is planned for implementation in late July. Key open questions include how the redesign will handle edge cases like nested alternates, submodules, and write isolation, as well as how performance trade-offs will be validated. The regression affects all operations using `GIT_ALTERNATE_OBJECT_DIRECTORIES`, including `clone -s`, `--reference`, and large-scale hosting deployments, making this a high-impact issue for the project.
