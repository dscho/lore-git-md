This thread is about a performance regression in `git receive-pack` connectivity checks introduced by the ODB (object database) abstraction rework, specifically commit `a593373b09`. The regression, reported by Wolfgang Kritzinger (Atlassian), causes a 12% slowdown on fast filesystems and significantly worse performance on NFS-backed deployments due to excessive failing `open()` calls for loose objects across multiple ODB backends. The root cause is a shift in object lookup order from "pack-first, loose-second" per backend to "pack-loose, pack-loose" across backends, leading to redundant loose object checks.

Key participants include Jeff King (Peff), who confirmed the regression and quantified its impact; Taylor Blau, who proposed a two-phase lookup fix that restores performance but violates the ODB abstraction; and Junio C Hamano, who reframed the issue as an opportunity to optimize the ODB abstraction for specialized use cases like connectivity checks. The discussion has now shifted toward broader architectural solutions, with Patrick Steinhardt (the ODB rework author) proposing a transaction-aware ODB write mechanism that would bypass the source list entirely during active transactions. This approach would incidentally resolve the performance issue by avoiding loose object checks in quarantine directories during connectivity traversals but is part of a larger refactoring effort that won’t progress until late July or August.

The thread is still open, with the main unresolved question being how to balance the ODB abstraction’s design goals with performance optimizations for specialized use cases. Patrick’s proposal suggests the regression may persist until the transaction-focused ODB overhaul is implemented, though alternative optimizations (e.g., pre-loading loose object names or distinguishing "fast" and "slow" lookups) remain on the table. The outcome will likely depend on Patrick’s input once he returns from leave.
