Core problem or goal
Add a `--[no-]edit` option to `git rebase --continue` to allow users to skip the editor prompt when continuing a rebase after conflict resolution, controlled by command-line flags (`--no-edit`, `--edit`) and a new configuration option `rebase.noEdit`. The change is motivated by workflow efficiency for users who frequently rebase and want to accept the existing commit message without manual intervention.

Current status
Under review (initial submission). No prior versions or related in-flight topics. The patch is self-contained and touches `builtin/rebase.c`, `sequencer.c`, `Documentation/git-rebase.adoc`, `Documentation/config/rebase.adoc`, and adds tests in `t/t3436-rebase-more-options.sh`.

Key technical details
- **Files touched**: `builtin/rebase.c`, `sequencer.c`, `Documentation/git-rebase.adoc`, `Documentation/config/rebase.adoc`, `t/t3436-rebase-more-options.sh`.
- **New symbols**: CLI options `--no-edit`/`--edit` for `git rebase --continue`, config key `rebase.noEdit`.
- **Behavior**: Flags apply only to the current `--continue` invocation, not subsequent commits in the same rebase. The config option sets the default behavior. The sequencer logic resets the `edit` flag after each `--continue` to prevent unintended persistence.
- **On-disk format**: No changes.
- **Test coverage**: New tests in `t/t3436-rebase-more-options.sh` validate the feature, including edge cases like the interaction between `--edit` and the `rebase.noEdit` config option.

Open questions and loose ends
- Edge cases in the sequencer logic: interaction with `--autosquash`, `--signoff`, or other rebase options.
- Config option naming: whether `rebase.noEdit` (current) or `rebase.continueNoEdit` (more specific) is preferable.
- Potential for user confusion if the flag’s non-persistence across multiple `--continue` invocations in the same rebase is not clearly documented.
