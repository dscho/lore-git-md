Thread identity
Subject: [PATCH] fsmonitor: macOS: flush pending FSEvents before cookie wait
Series version: standalone patch (no series)
Originating author: Tamir Duberstein
Thread type: bugfix

Core problem or goal
Fix a macOS-specific performance regression in Git’s fsmonitor daemon introduced by 56cef9cb1a (April 2026). The regression caused the daemon to time out waiting for filesystem events on loaded macOS systems, triggering excessive lstat() calls and multi-second delays during `git status`. The root cause was initially hypothesized to be non-deterministic drainage of the FSEvents queue within the 1 ms latency interval, but this hypothesis was not empirically validated. The thread explored whether flushing the FSEvents queue could mitigate the issue, but the proposed fix was withdrawn after testing failed to confirm its effectiveness.

Current status
Patch withdrawn by the author after empirical testing did not validate the root cause or the effectiveness of the proposed fix. No code changes were merged. The macOS fsmonitor daemon still exhibits the timeout behavior on loaded systems, but the thread is closed unless Tamir resubmits with new evidence. The discussion now clarifies that the proposed `FSEventStreamFlushAsync()` call was insufficient to guarantee event processing, unlike Watchman’s use of the synchronous `FSEventStreamFlushSync()`, which eliminates the race with the timeout.

Key technical details
- Files touched: `fsmonitor--daemon.c`, `compat/fsmonitor/fsmonitor-fs-listen-macos.c`, `fsmonitor.h` (proposed changes abandoned)
- New symbols: none (proposed macOS-only `FSEventStreamFlushAsync` call was not merged)
- Behavior change: none (proposed asynchronous flush of pending FSEvents notifications was withdrawn)
- On-disk format: unchanged
- Test coverage: performance data provided in the original commit message (M4 Max Mac, 1M-entry index) was not sufficient to validate the fix; no new test files were added. The post-mortem highlights that the asynchronous flush cannot guarantee event processing, unlike the synchronous variant used by Watchman.

Open questions and loose ends
- The macOS fsmonitor daemon’s timeout behavior on loaded systems remains unresolved. If the thread is revived, it will need to re-establish:
  - A performance baseline demonstrating the regression
  - A technical rationale for any proposed fix, grounded in Apple’s documentation and first-hand analysis (as requested by Patrick Steinhardt and endorsed by Junio C Hamano)
  - Benchmark data showing measurable improvement (as requested by Koji Nakamaru and Junio C Hamano)
  - Clarification of whether the synchronous `FSEventStreamFlushSync()` call could address the race, and if so, whether it introduces new risks (Patrick Steinhardt’s concern)
- The original hypothesis about FSEvents queue drainage remains unproven; alternative root causes may need to be explored
