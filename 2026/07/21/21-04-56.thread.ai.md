Subject: [PATCH] fsmonitor: macOS: flush pending FSEvents before cookie wait
Series version: standalone patch (no series)
Originating author: Tamir Duberstein
Thread type: bugfix

Core problem or goal
Fix a macOS-specific performance regression in Git’s fsmonitor daemon introduced by 56cef9cb1a (April 2026). The regression caused the daemon to time out waiting for filesystem events on loaded macOS systems, triggering excessive lstat() calls and multi-second delays during `git status`.

Current status
Under review; no prior versions. Patch is narrowly scoped to the fsmonitor daemon’s cookie wait mechanism and does not affect other backends. Junio forwarded Koji Nakamaru’s tested review, echoing the request for additional benchmark data in the commit message but providing no technical commentary or merge signal. Patrick Steinhardt’s substantive review raises a technical question about the FSEvents queue behavior but does not contest the implementation or block the patch. The patch remains unchanged; the only blocker remains the commit message enhancement with additional benchmark data.

Key technical details
- Files touched: `fsmonitor--daemon.c`, `compat/fsmonitor/fsmonitor-fs-listen-macos.c`, `fsmonitor.h`
- New symbols: none (macOS-only `FSEventStreamFlushAsync` call added)
- Behavior change: asynchronous flush of pending FSEvents notifications immediately after cookie file creation and before the timed wait
- On-disk format: unchanged
- Test coverage: performance data provided in commit message (M4 Max Mac, 1M-entry index); no new test files

Open questions and loose ends
- Commit message must be strengthened with additional benchmark data showing timeout reduction (requested by Koji Nakamaru and echoed by Junio; no response from Tamir yet)
- Clarification needed on macOS FSEvents queue draining guarantees within a single latency interval (raised by Patrick Steinhardt; no response yet)
