This is a **performance regression report** targeting the connectivity check in `git receive-pack`. Wolfgang Kritzinger (Atlassian) identifies a slowdown in server-side Git 2.54 that did not exist in 2.50, specifically during the `rev-list --objects` connectivity check that runs after a push. The regression manifests as repeated failed `open()` calls for loose objects—first in the quarantine directory, then in the main object store—before the object is found in a pack. On NFS-backed repositories (common in Bitbucket deployments), these extra round-trips cause noticeable latency, effectively hanging the push at the "Checking connectivity" step.

Kritzinger bisected the issue to commit `8384cbcb4c`, part of the recent object database rework. He hypothesizes that the lookup order changed: previously, Git checked all packs before any loose objects; now, it checks packs *and* loose objects for each object database in sequence. In well-packed repositories, Git 2.50 often avoided loose object lookups entirely, while 2.54 consistently performs them.

The report is clear and actionable: it names the problematic commit, describes the observed behavior, and explains the real-world impact (NFS latency). No patch is proposed yet, but the diagnosis is thorough enough to guide a fix. This is likely to attract attention from the ODB refactoring crowd (Patrick Steinhardt, Justin Tobler) and anyone concerned with server-side performance. If you run Git on NFS or care about push latency, this thread is worth watching.
