This is a substantive review reply in the `git send-email` completion thread. SZEDER Gábor weighs in on the ongoing discussion about whether the completion script should offer both refs (branches, tags) and filesystem paths (patch files) when they share a common prefix. He argues that the current behavior—offering only refs for commands like `git diff`, `git log`, and `git send-email`—is intentional and justified. His reasoning centers on usability: shorter, focused completion lists make it easier to pick the desired candidate, and users can still trigger filesystem completion explicitly (e.g., via `./<TAB>`, `<ALT-/>`, or `-- <TAB>`). He notes that `git send-email`’s completion function does not support the disambiguating doubledash (`--`), but this does not invalidate the broader design principle.

SZEDER also clarifies that the completion script does not expand abbreviated object names to full hashes, countering a claim in the original commit message. He points out that commands like `git worktree add` and `git bungle create` already handle refs and paths separately based on command-line context, but this approach is not feasible for `git send-email`, `git diff`, or `git log` because they accept arbitrary revision arguments followed by paths. His position suggests skepticism about the patch’s necessity, though he does not explicitly oppose it. The thread remains open, with Junio’s earlier preference for filenames over refs now reinforced by SZEDER’s broader design rationale. The discussion is likely to continue, with Yury Norov’s planned v2 needing to address these usability concerns.
