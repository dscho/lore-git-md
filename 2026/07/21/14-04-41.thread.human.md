This thread is about a proposed `--[no-]edit` option for `git rebase --continue`, allowing users to skip the commit-message editor when continuing a rebase after conflict resolution. The patch, submitted by Hugo Sales, introduces command-line flags (`--no-edit`, `--edit`) and a new configuration option `rebase.noEdit` to control this behavior. Junio C Hamano, the maintainer, has raised significant design concerns, particularly about the configuration option's scope and its potential to silently override user intent during interactive rebase steps like `edit` or `reword`.

Phillip Wood’s recent review reinforces Junio’s skepticism. He corrects a minor technical detail in Junio’s feedback (clarifying that `GIT_EDITOR=:` is the correct workaround, not `GIT_SEQUENCE_EDITOR=:`) but otherwise aligns with the maintainer’s concerns. Phillip references a prior discussion from 2024 where he proposed an alias to suppress the editor only when HEAD hasn’t changed, noting that even that approach doesn’t address the edge cases Junio highlighted. His review makes it clear that the patch, in its current form, is incomplete and unlikely to be accepted without addressing these issues.

The patch remains in its initial version (v1), with no revisions yet posted. Key open questions include whether the feature is justified given existing workarounds, how it behaves during non-conflict rebase stops (e.g., `edit`/`reword` steps), and whether the `rebase.noEdit` configuration option is too broad. The current test coverage is limited to conflict-resolution scenarios, leaving other edge cases unvalidated. Hugo Sales has not yet responded to the feedback.
