This thread is about a proposed `--[no-]edit` option for `git rebase --continue`, allowing users to skip the editor prompt when continuing a rebase after conflict resolution. The patch, submitted by Hugo Sales, introduces command-line flags (`--no-edit`, `--edit`) and a new configuration option `rebase.noEdit` to control this behavior, aiming to improve workflow efficiency.

The discussion has stalled on design concerns raised by Junio C Hamano and Phillip Wood. Both question the feature's necessity, given the existing workaround (`GIT_EDITOR=: git rebase --continue`), and are particularly skeptical of the `rebase.noEdit` configuration option. They argue it could silently override user intent during interactive rebase steps like `edit` or `reword`, and note that the patch does not address edge cases such as non-conflict stops (e.g., `edit`/`reword` steps or merge failures). Phillip Wood also pointed out that the correct environment variable for suppressing the editor is `GIT_EDITOR=:`, not `GIT_SEQUENCE_EDITOR=:`, and referenced prior unresolved discussion from 2024 about these edge cases. Junio’s recent follow-up corrected his earlier mistake on this point but added no new technical feedback.

The patch remains in its initial version (v1) with no revisions yet posted. Key technical details include changes to `builtin/rebase.c`, `sequencer.c`, and documentation, along with new tests in `t/t3436-rebase-more-options.sh` that validate the feature only for conflict-resolution paths. The sequencer logic resets the `edit` flag after each `--continue` to prevent unintended persistence, but the patch does not clarify how the feature interacts with interactive rebase steps or other rebase stop scenarios. No further responses from the author have addressed these concerns, leaving the thread’s open questions unresolved.
