Core problem or goal
A measurable performance regression in server-side Git operations (pushes) was introduced by the ODB abstraction rework, specifically commit `a593373b09` (previously bisected to `8384cbcb4c`). The regression manifests as excessive failing `open()` calls for loose objects across multiple ODB backends (quarantine and main object stores), particularly costly on NFS-backed deployments. The root cause is a change in object lookup order: the ODB rework shifted from a "pack-first, loose-second" strategy *per backend* to a "pack-loose, pack-loose" strategy *across backends*, causing redundant loose object checks even when objects exist in packs. Taylor Blau’s analysis reconciles the two bisect results, showing that both commits contribute to the problem by altering the lookup order in `find_pack_entry()` and `do_oid_object_info_extended()`.

Current status
Regression confirmed and quantified (12% slowdown on fast filesystems; worse on NFS). The problematic commit is now definitively identified as `a593373b09`, with `8384cbcb4c` as an earlier precursor. Taylor Blau has proposed a targeted fix (a two-phase lookup: all packs first, then all loose objects) that restores performance but violates the ODB abstraction’s design goal of treating backends as independent. The thread awaits Patrick Steinhardt’s (ODB rework author) response to evaluate the fix and discuss whether the abstraction can accommodate cross-backend optimizations or requires a broader redesign.

Key technical details
- **Subsystems touched**: ODB (object database), `git receive-pack` (connectivity check), `git rev-list` (used in reproduction), backend iteration logic.
- **Files/symbols**: `find_pack_entry()` (refactored in `a593373b09`), `do_oid_object_info_extended()` (in `odb.c`), `packfile_store_prepare()`.
- **Old behavior**: "Pack-first, loose-second" lookup *per backend* (check all packs before loose objects in a single backend), extended across backends (all packs in all backends before any loose objects).
- **New behavior**: "Pack-loose, pack-loose" lookup *across backends* (check packs *and* loose objects in one backend before moving to the next), causing redundant loose object checks in earlier backends (e.g., quarantine) before finding objects in packs in later backends (e.g., main object store).
- **Performance impact**: 12% slowdown on fast filesystems; significantly worse on NFS due to expensive loose object checks. Measured via `strace` counting failing `open()` calls.
- **On-disk format**: No changes reported.
- **Test coverage**: Reproduction requires `GIT_ALTERNATE_OBJECT_DIRECTORIES` with a packed repository; NFS-specific or large-repository testing may be needed for full validation. Peff’s reproduction recipe uses `strace` and `git rev-list`.
- **Proposed fix**: Two-phase lookup (all packs first, then all loose objects) to restore performance, but this breaks the ODB abstraction by assuming backends can be prioritized.

Open questions and loose ends
- How should the ODB abstraction reconcile its design goals (independent, abstract backends) with the need for cross-backend performance optimizations (e.g., prioritizing "fast" pack lookups over "slow" loose object checks)?
- Is the two-phase lookup proposed by Taylor Blau acceptable, or does it violate the abstraction too severely? Patrick Steinhardt’s response will likely address this.
- Are there alternative fixes (e.g., backend prioritization, caching, or lazy loose object checks) that preserve the abstraction while mitigating the regression?
- Will this require a revert of `a593373b09`, a new optimization layer, or a broader redesign of the ODB lookup strategy?
- What are the performance trade-offs of the ODB rework, and how should they be balanced for different deployment scenarios (e.g., NFS vs. local storage)? Should the abstraction be adjusted to accommodate real-world constraints, or should deployments adapt to the abstraction’s design?
