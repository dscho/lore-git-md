Subject: Performance regression in `git receive-pack` connectivity check after ODB rework (commit 8384cbcb4c)
Series version: N/A (regression report)
Originating author: Wolfgang Kritzinger (Atlassian)
Thread type: bug report / performance regression

Core problem or goal
A measurable performance regression in server-side Git operations (pushes) was introduced by the ODB abstraction rework, specifically commit `a593373b09` (previously bisected to `8384cbcb4c`). The regression manifests as excessive failing `open()` calls for loose objects across multiple ODB backends (quarantine and main object stores), particularly costly on NFS-backed deployments. The root cause is a change in object lookup order: the ODB rework shifted from a "pack-first, loose-second" strategy *per backend* to a "pack-loose, pack-loose" strategy *across backends*, causing redundant loose object checks even when objects exist in packs. The regression is now reframed as an architectural opportunity to optimize the ODB abstraction for specialized use cases like connectivity checks, which prioritize traversal success over general-purpose object lookups, while also addressing a broader goal of making ODB transactions self-contained.

Current status
Regression confirmed and quantified (12% slowdown on fast filesystems; worse on NFS). The problematic commit is definitively identified as `a593373b09`, with `8384cbcb4c` as an earlier precursor. The discussion has shifted from a targeted performance fix to a broader architectural redesign of ODB transactions, though Junio’s latest email clarifies that the architectural and immediate performance goals are separable. Patrick Steinhardt proposes bypassing the ODB source list entirely for writes during active transactions, routing them directly to the transaction object instead of the primary ODB source. This would prevent loose-object checks in the quarantine directory during connectivity traversals, as objects written to the transaction wouldn’t be visible to the ODB layer until commit. Junio now emphasizes that a targeted fix addressing the lookup order change is still needed to restore performance in the short term, while Patrick’s transaction-focused approach remains a forward-looking solution tied to a planned transaction-aware ODB overhaul, with implementation delayed until late July or August due to Patrick’s absence. Junio’s earlier suggestion to distinguish "fast" and "slow" lookups within backends remains unaddressed but may be rendered moot by Patrick’s transaction-focused approach or superseded by a targeted fix.

Key technical details
- **Subsystems touched**: ODB (object database), `git receive-pack` (connectivity check), `git rev-list` (used in reproduction), backend iteration logic, transaction handling.
- **Files/symbols**: `find_pack_entry()` (refactored in `a593373b09`), `do_oid_object_info_extended()` (in `odb.c`), `packfile_store_prepare()`, `git rev-list` connectivity check logic, transaction object routing.
- **Old behavior**: "Pack-first, loose-second" lookup *per backend* (check all packs before loose objects in a single backend), extended across backends (all packs in all backends before any loose objects).
- **New behavior**: "Pack-loose, pack-loose" lookup *across backends* (check packs *and* loose objects in one backend before moving to the next), causing redundant loose object checks in earlier backends (e.g., quarantine) before finding objects in packs in later backends (e.g., main object store).
- **Performance impact**: 12% slowdown on fast filesystems; significantly worse on NFS due to expensive loose object checks. Measured via `strace` counting failing `open()` calls.
- **On-disk format**: No changes reported.
- **Test coverage**: Reproduction requires `GIT_ALTERNATE_OBJECT_DIRECTORIES` with a packed repository; NFS-specific or large-repository testing may be needed for full validation. Peff’s reproduction recipe uses `strace` and `git rev-list`.
- **Proposed optimizations**:
  - **Transaction-aware ODB writes**: Route writes during active transactions directly to the transaction object, bypassing the ODB source list. This would prevent loose-object checks in quarantine directories during connectivity traversals.
  - **Targeted lookup order fix**: Restore the "pack-first, loose-second" strategy *across backends* to eliminate redundant loose object checks, as suggested by Junio’s latest email. This fix is separable from Patrick’s architectural redesign and could address the regression in the short term.
  - **Backend-level "fast" vs. "slow" lookups** (Junio’s proposal): Distinguish between pack and loose object checks within each backend to enable cross-backend optimizations (e.g., all packs before any loose objects) without violating the abstraction. This remains unaddressed but may be superseded by a targeted fix.
  - **Pre-loaded loose object table/Bloom filter** (Junio’s proposal): Short-circuit expensive `lstat()` calls during connectivity checks by caching loose object names in memory, tolerating false positives. Also unaddressed.

Related work
- **ODB abstraction rework**: Ongoing effort led by Patrick Steinhardt to enable pluggable ODB backends. This regression is a side effect of that work, specifically the refactoring of `find_pack_entry()` in `a593373b09` and its interaction with `do_oid_object_info_extended()`.
- **Transaction-aware ODB writes**: Planned refactoring effort by Patrick Steinhardt and Justin Tobler to make ODB transactions self-contained, eliminating the need to modify the ODB source list during transactions. This effort is now the proposed path to resolving the regression, though Junio’s latest email suggests a targeted fix may be needed in the interim.
- **NFS deployments**: The regression is particularly impactful for NFS-backed Git servers (e.g., Atlassian Bitbucket), a common deployment pattern for large-scale hosting. The performance impact is exacerbated by the high cost of loose object checks on NFS.
- **Connectivity checks**: The `git rev-list` connectivity check is a non-standard use of the revision traversal machinery, optimized for a single bit of information (traversal success) rather than the full object list. This use case may justify application-specific optimizations that are not applicable to general-purpose object lookups. Peff’s reproduction case demonstrates the issue without involving transactions or temporary directories, highlighting the need for a targeted fix.
