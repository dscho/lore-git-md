Subject: Performance regression in `git receive-pack` connectivity check after ODB rework (commit 8384cbcb4c)
Series version: N/A (regression report)
Originating author: Wolfgang Kritzinger (Atlassian)
Thread type: bug report / performance regression

Core problem or goal
A measurable performance regression in server-side Git operations (pushes and alternates-based operations) was introduced by the ODB abstraction rework, specifically commit `a593373b09` (previously bisected to `8384cbcb4c`). The regression manifests as excessive failing `open()` calls for loose objects across multiple ODB backends (quarantine and main object stores, alternates), particularly costly on NFS-backed deployments. The root cause is a change in object lookup order: the ODB rework shifted from a "pack-first, loose-second" strategy *per backend* to a "pack-loose, pack-loose" strategy *across backends*, causing redundant loose object checks even when objects exist in packs. The regression is now recognized as a systemic alternates performance issue affecting all operations that use `GIT_ALTERNATE_OBJECT_DIRECTORIES`, including `clone -s`, `--reference`, and large-scale hosting deployments (e.g., GitHub, GitLab). The discussion has coalesced around Patrick’s proposal to **move alternates handling into the "files" backend itself**, treating alternates as an implementation detail rather than a cross-backend concern, which would enable pack-first-loose-second lookups across all alternates while simplifying other subsystems (commit-graph, bitmap, maintenance). A near-term targeted fix to restore the "pack-first, loose-second" lookup order *across backends* remains viable but may be superseded by Patrick’s redesign.

Current status
Regression confirmed and quantified (12% slowdown on fast filesystems; worse on NFS). The problematic commit is definitively identified as `a593373b09`, with `8384cbcb4c` as an earlier precursor. Peff’s analysis broadened the scope to a systemic alternates performance issue, and Patrick’s latest email proposes a **fundamental architectural shift**: moving alternates handling from the ODB layer into the "files" backend. This proposal has gained **explicit endorsement from Peff and Justin Tobler**, who agree that treating alternates as an implementation detail of the files backend is a reasonable course correction for the ODB abstraction, dismissing concerns about lost flexibility (e.g., combining alternates with non-files backends) as unlikely to be a practical issue. Patrick plans to implement this in stages, starting with a patch series to remove `odb_prepare_alternates()` calls (delayed until late July). Justin Tobler has outlined a parallel plan to **decouple transaction handling from the ODB source list**, proposing that once all temporary object directory users (e.g., quarantine areas) are updated to use ODB transactions, the current practice of reordering the source list during transactions could be eliminated. This would simplify the ODB layer by tracking transactions internally and referencing the transaction object directly during reads/writes, addressing Peff’s earlier critique about cross-process coordination. The proposal directly addresses the root cause, resolves secondary issues (e.g., dropping `OBJECT_INFO_SECOND_READ`, unifying commit-graph/bitmap loading), and sidesteps Peff’s earlier critique of transaction-aware ODB writes by treating alternates as a backend-local concern. A near-term fix (e.g., targeted lookup order adjustment) may still be implemented before Patrick’s redesign, but no contributor has volunteered to pursue it yet. Peff’s critique of Patrick’s earlier transaction-aware ODB writes remains unresolved for other use cases, though the new proposal renders it moot for this regression.

Key technical details
- **Subsystems touched**: ODB (object database), `git receive-pack` (connectivity check), `git rev-list` (reproduction), `index-pack` (object writing), backend iteration logic, alternates (`GIT_ALTERNATE_OBJECT_DIRECTORIES`), commit-graph, bitmap, maintenance, object storage extensions, ODB transactions.
- **Files/symbols**: `find_pack_entry()` (refactored in `a593373b09`), `do_oid_object_info_extended()` (in `odb.c`), `packfile_store_prepare()`, `odb_prepare_alternates()`, `OBJECT_INFO_SECOND_READ`, `struct odb_source`, commit-graph/bitmap loading logic, object storage extension design, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, ODB transaction tracking.
- **Old behavior**: "Pack-first, loose-second" lookup *per backend* (check all packs before loose objects in a single backend), extended across backends (all packs in all backends before any loose objects).
- **New behavior**: "Pack-loose, pack-loose" lookup *across backends* (check packs *and* loose objects in one backend before moving to the next), causing redundant loose object checks in earlier backends (e.g., quarantine, alternates) before finding objects in packs in later backends (e.g., main object store).
- **Proposed architectural change**: Move alternates handling into the "files" backend, treating alternates as an implementation detail rather than a cross-backend concern. This would enable pack-first-loose-second lookups across all alternates while simplifying commit-graph/bitmap loading and dropping the `OBJECT_INFO_SECOND_READ` flag. Peff and Justin Tobler endorse this direction, noting that the original motivation for abstracting alternates was to hide implementation details, not to enable arbitrary combinations of sources. Justin’s plan to decouple transaction handling from the ODB source list would further simplify the ODB layer by tracking transactions internally.
- **Performance impact**: 12% slowdown on fast filesystems; significantly worse on NFS due to expensive loose object checks. The regression affects all operations using alternates (`clone -s`, `--reference`, large-scale hosting deployments). Measured via `strace` counting failing `open()` calls.
- **Cross-process constraints**: Peff’s earlier critique highlighted that `index-pack` must write objects to the quarantine area (transaction object), while `rev-list` and user hooks must read from *both* the quarantine area and the original ODB. Patrick’s new proposal sidesteps this by treating alternates as a backend-local concern, while Justin’s transaction handling plan would eliminate the need to reorder the ODB source list during transactions.
- **On-disk format**: No changes reported.
- **Test coverage**: Reproduction requires `GIT_ALTERNATE_OBJECT_DIRECTORIES` with a packed repository; NFS-specific or large-repository testing may be needed for full validation. Peff’s reproduction recipe uses `strace` and `git rev-list`.
- **Proposed optimizations**:
  - **Alternates-in-files-backend**: Move alternates handling into the "files" backend to enable pack-first-loose-second lookups across all alternates and simplify other subsystems. This is now the leading architectural direction, with endorsements from Peff and Justin Tobler, though implementation is delayed until late July.
  - **Decoupled transaction handling**: Justin’s plan to track ODB transactions internally, eliminating the need to reorder the ODB source list during transactions. This would address Peff’s critique of cross-process coordination while preserving write isolation guarantees.
  - **Targeted lookup order fix**: Restore the "pack-first, loose-second" strategy *across backends* to eliminate redundant loose object checks. This remains a viable near-term fix but may be superseded by Patrick’s redesign.
  - **Backend-level "fast" vs. "slow" lookups** (Junio’s proposal): Distinguish between pack and loose object checks within each backend to enable cross-backend optimizations. This remains unaddressed but may be superseded by Patrick’s alternates-in-files-backend proposal.
  - **Pre-loaded loose object table/Bloom filter** (Junio’s proposal): Short-circuit expensive `lstat()` calls during connectivity checks by caching loose object names in memory. This remains unaddressed and may be deprioritized in favor of architectural changes.

Related work
- **ODB abstraction rework**: Ongoing effort led by Patrick Steinhardt to enable pluggable ODB backends. This regression is a side effect of that work, specifically the refactoring of `find_pack_entry()` in `a593373b09` and its interaction with `do_oid_object_info_extended()`.
- **Alternates-in-files-backend redesign**: Patrick’s proposed architectural shift to move alternates handling into the "files" backend, treating alternates as an implementation detail rather than a cross-backend concern. This would enable pack-first-loose-second lookups across all alternates while simplifying other subsystems. Peff and Justin Tobler’s endorsements reinforce the viability of this direction.
- **Decoupled transaction handling**: Justin’s plan to track ODB transactions internally, eliminating the need to reorder the ODB source list during transactions. This would address Peff’s critique of cross-process coordination while preserving write isolation guarantees.
- **Transaction-aware ODB writes**: Planned refactoring effort by Patrick Steinhardt and Justin Tobler to make ODB transactions self-contained, eliminating the need to modify the ODB source list during transactions. Peff’s critique argued this approach cannot fully resolve the regression due to cross-process dependencies, though Justin’s new plan addresses these concerns by decoupling transaction handling from the source list. Patrick’s alternates-in-files-backend proposal sidesteps these concerns for this regression.
- **Alternates deployments**: The regression is particularly impactful for large-scale hosting environments (e.g., GitHub, GitLab) that rely on `GIT_ALTERNATE_OBJECT_DIRECTORIES` for object sharing between forks. The performance impact is exacerbated by the high cost of loose object checks on NFS and other networked filesystems.
- **Connectivity checks**: The `git rev-list` connectivity check is a non-standard use of the revision traversal machinery, optimized for a single bit of information (traversal success) rather than the full object list. This use case may justify application-specific optimizations that are not applicable to general-purpose object lookups.
- **Process coordination**: The need to coordinate object visibility between `index-pack`, `rev-list`, and user hooks spans process boundaries, complicating architectural solutions that assume a single-process context. Patrick’s alternates-in-files-backend proposal and Justin’s decoupled transaction handling plan both sidestep this by treating alternates and transactions as backend-local concerns.
