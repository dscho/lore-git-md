Subject: Performance regression in `git receive-pack` connectivity check after ODB rework (commit 8384cbcb4c)
Series version: N/A (regression report)
Originating author: Wolfgang Kritzinger (Atlassian)
Thread type: bug report / performance regression

Core problem or goal
A measurable performance regression in server-side Git operations (pushes) was introduced by the ODB abstraction rework, specifically commit `a593373b09` (previously bisected to `8384cbcb4c`). The regression manifests as excessive failing `open()` calls for loose objects across multiple ODB backends (quarantine and main object stores), particularly costly on NFS-backed deployments. The root cause is a change in object lookup order: the ODB rework shifted from a "pack-first, loose-second" strategy *per backend* to a "pack-loose, pack-loose" strategy *across backends*, causing redundant loose object checks even when objects exist in packs. The regression is now reframed as an opportunity to optimize the ODB abstraction for specialized use cases like connectivity checks, which prioritize a single bit of information (traversal success) over general-purpose object lookups.

Current status
Regression confirmed and quantified (12% slowdown on fast filesystems; worse on NFS). The problematic commit is definitively identified as `a593373b09`, with `8384cbcb4c` as an earlier precursor. Taylor Blau proposed a two-phase lookup fix (all packs first, then all loose objects) that restores performance but violates the ODB abstraction’s design goal of treating backends as independent. Junio C Hamano has now reframed the discussion, suggesting that the `git rev-list` connectivity check’s unique requirements (tolerating false positives in object existence checks) justify application-specific optimizations. The thread awaits Patrick Steinhardt’s (ODB rework author) response to evaluate whether the abstraction can accommodate cross-backend optimizations (e.g., distinguishing "fast" and "slow" lookups within backends) or requires a broader redesign to support specialized use cases.

Key technical details
- **Subsystems touched**: ODB (object database), `git receive-pack` (connectivity check), `git rev-list` (used in reproduction), backend iteration logic.
- **Files/symbols**: `find_pack_entry()` (refactored in `a593373b09`), `do_oid_object_info_extended()` (in `odb.c`), `packfile_store_prepare()`, `git rev-list` connectivity check logic.
- **Old behavior**: "Pack-first, loose-second" lookup *per backend* (check all packs before loose objects in a single backend), extended across backends (all packs in all backends before any loose objects).
- **New behavior**: "Pack-loose, pack-loose" lookup *across backends* (check packs *and* loose objects in one backend before moving to the next), causing redundant loose object checks in earlier backends (e.g., quarantine) before finding objects in packs in later backends (e.g., main object store).
- **Performance impact**: 12% slowdown on fast filesystems; significantly worse on NFS due to expensive loose object checks. Measured via `strace` counting failing `open()` calls.
- **On-disk format**: No changes reported.
- **Test coverage**: Reproduction requires `GIT_ALTERNATE_OBJECT_DIRECTORIES` with a packed repository; NFS-specific or large-repository testing may be needed for full validation. Peff’s reproduction recipe uses `strace` and `git rev-list`.
- **Proposed optimizations**:
  - **Backend-level "fast" vs. "slow" lookups**: Distinguish between pack and loose object checks within each backend to enable cross-backend optimizations (e.g., all packs before any loose objects) without violating the abstraction.
  - **Pre-loaded loose object table/Bloom filter**: Short-circuit expensive `lstat()` calls during connectivity checks by caching loose object names in memory, tolerating false positives (claiming an object is missing when it isn’t) as long as false negatives are avoided.

Open questions and loose ends
- Can the ODB abstraction accommodate cross-backend optimizations (e.g., prioritizing "fast" pack lookups over "slow" loose object checks) while preserving its design goals of independent, abstract backends? Patrick Steinhardt’s input is critical here.
- Is the two-phase lookup proposed by Taylor Blau acceptable, or does it violate the abstraction too severely? Junio’s reframing suggests it may be palatable if implemented as a backend capability rather than a top-level optimization.
- Are there alternative optimizations (e.g., pre-loading loose object names, lazy loose object checks, or backend prioritization) that preserve the abstraction while mitigating the regression?
- How should the ODB abstraction balance general-purpose lookups with specialized use cases like connectivity checks, where false positives are tolerable? Should such optimizations be exposed as hints or remain internal to the ODB layer?
- Will this require a revert of `a593373b09`, a new optimization layer, or a broader redesign of the ODB lookup strategy?
- What are the performance trade-offs of the ODB rework, and how should they be balanced for different deployment scenarios (e.g., NFS vs. local storage)? Should the abstraction adapt to real-world constraints, or should deployments adjust to the abstraction’s design?

Related work
- **ODB abstraction rework**: Ongoing effort led by Patrick Steinhardt to enable pluggable ODB backends. This regression is a side effect of that work, specifically the refactoring of `find_pack_entry()` in `a593373b09` and its interaction with `do_oid_object_info_extended()`.
- **NFS deployments**: The regression is particularly impactful for NFS-backed Git servers (e.g., Atlassian Bitbucket), a common deployment pattern for large-scale hosting. The performance impact is exacerbated by the high cost of loose object checks on NFS.
- **Connectivity checks**: The `git rev-list` connectivity check is a non-standard use of the revision traversal machinery, optimized for a single bit of information (traversal success) rather than the full object list. This use case may justify application-specific optimizations that are not applicable to general-purpose object lookups.
