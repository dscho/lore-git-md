Subject: Performance regression in `git receive-pack` connectivity check after ODB rework (commit 8384cbcb4c)

Core problem or goal
A measurable performance regression in server-side Git operations (pushes and alternates-based operations) was introduced by the ODB abstraction rework, specifically commit `a593373b09` (previously bisected to `8384cbcb4c`). The regression manifests as excessive failing `open()` calls for loose objects across multiple ODB backends (quarantine and main object stores, alternates), particularly costly on NFS-backed deployments. The root cause is a change in object lookup order: the ODB rework shifted from a "pack-first, loose-second" strategy *per backend* to a "pack-loose, pack-loose" strategy *across backends*, causing redundant loose object checks even when objects exist in packs. The regression is now recognized as a systemic alternates performance issue affecting all operations that use `GIT_ALTERNATE_OBJECT_DIRECTORIES`, including `clone -s`, `--reference`, and large-scale hosting deployments (e.g., GitHub, GitLab). The discussion remains focused on two tracks: (1) a near-term targeted fix to restore the "pack-first, loose-second" lookup order *across backends* and eliminate redundant loose object checks, and (2) a longer-term architectural redesign of ODB transactions to route writes during active transactions directly to the transaction object, bypassing the ODB source list.

Current status
Regression confirmed and quantified (12% slowdown on fast filesystems; worse on NFS). The problematic commit is definitively identified as `a593373b09`, with `8384cbcb4c` as an earlier precursor. Peff’s latest email broadens the scope of the regression beyond the quarantine area, framing it as a systemic alternates performance issue that affects nearly every Git operation in large-scale hosting environments. The discussion continues to split into two tracks: (1) a near-term targeted fix to restore the "pack-first, loose-second" lookup order *across backends*, which remains the most viable path forward, and (2) Patrick’s longer-term architectural redesign of ODB transactions, which is delayed until late July or August. Peff’s critique of Patrick’s transaction-aware approach—arguing that cross-process dependencies (e.g., `index-pack` and `rev-list` coordination) would force the solution to replicate existing "alternates juggling"—remains unresolved. Junio’s and Peff’s prior emails continue to suggest the targeted lookup-order fix is the most actionable near-term solution, but no one has yet volunteered to implement it.

Key technical details
- **Subsystems touched**: ODB (object database), `git receive-pack` (connectivity check), `git rev-list` (used in reproduction), `index-pack` (object writing during pushes), backend iteration logic, transaction handling, quarantine area, alternates (`GIT_ALTERNATE_OBJECT_DIRECTORIES`), process coordination.
- **Files/symbols**: `find_pack_entry()` (refactored in `a593373b09`), `do_oid_object_info_extended()` (in `odb.c`), `packfile_store_prepare()`, `git rev-list` connectivity check logic, transaction object routing, quarantine directory handling, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `index-pack` (object writing).
- **Old behavior**: "Pack-first, loose-second" lookup *per backend* (check all packs before loose objects in a single backend), extended across backends (all packs in all backends before any loose objects).
- **New behavior**: "Pack-loose, pack-loose" lookup *across backends* (check packs *and* loose objects in one backend before moving to the next), causing redundant loose object checks in earlier backends (e.g., quarantine, alternates) before finding objects in packs in later backends (e.g., main object store).
- **Performance impact**: 12% slowdown on fast filesystems; significantly worse on NFS due to expensive loose object checks. The regression now affects all operations using alternates (`clone -s`, `--reference`, large-scale hosting deployments), not just `git receive-pack` connectivity checks. Measured via `strace` counting failing `open()` calls.
- **Cross-process constraints**: Peff’s critique highlights that `index-pack` must explicitly write objects to the quarantine area (transaction object), while `rev-list` and user hooks must transparently read from *both* the quarantine area and the original ODB. This coordination cannot be fully encapsulated within the ODB API, as it spans process boundaries and requires visibility through `GIT_ALTERNATE_OBJECT_DIRECTORIES`.
- **On-disk format**: No changes reported.
- **Test coverage**: Reproduction requires `GIT_ALTERNATE_OBJECT_DIRECTORIES` with a packed repository; NFS-specific or large-repository testing may be needed for full validation. Peff’s reproduction recipe uses `strace` and `git rev-list`.
- **Proposed optimizations**:
  - **Targeted lookup order fix**: Restore the "pack-first, loose-second" strategy *across backends* to eliminate redundant loose object checks. This remains the leading candidate for a near-term fix, separable from Patrick’s architectural redesign.
  - **Transaction-aware ODB writes**: Route writes during active transactions directly to the transaction object, bypassing the ODB source list. Peff’s critique argues this approach cannot fully resolve the regression due to cross-process dependencies, though it may still be pursued as a long-term architectural improvement.
  - **Backend-level "fast" vs. "slow" lookups** (Junio’s proposal): Distinguish between pack and loose object checks within each backend to enable cross-backend optimizations (e.g., all packs before any loose objects). This remains unaddressed but may be superseded by a targeted fix.
  - **Pre-loaded loose object table/Bloom filter** (Junio’s proposal): Short-circuit expensive `lstat()` calls during connectivity checks by caching loose object names in memory, tolerating false positives. Peff’s earlier email clarified this would not resolve the quarantine-specific regression in `git receive-pack` but could optimize other use cases like `git rev-list`.

Related work
- **ODB abstraction rework**: Ongoing effort led by Patrick Steinhardt to enable pluggable ODB backends. This regression is a side effect of that work, specifically the refactoring of `find_pack_entry()` in `a593373b09` and its interaction with `do_oid_object_info_extended()`.
- **Transaction-aware ODB writes**: Planned refactoring effort by Patrick Steinhardt and Justin Tobler to make ODB transactions self-contained, eliminating the need to modify the ODB source list during transactions. Peff’s critique argues this approach cannot fully resolve the regression due to cross-process dependencies, though it may still be pursued as a long-term architectural improvement.
- **Alternates deployments**: The regression is particularly impactful for large-scale hosting environments (e.g., GitHub, GitLab) that rely on `GIT_ALTERNATE_OBJECT_DIRECTORIES` for object sharing between forks. The performance impact is exacerbated by the high cost of loose object checks on NFS and other networked filesystems.
- **Connectivity checks**: The `git rev-list` connectivity check is a non-standard use of the revision traversal machinery, optimized for a single bit of information (traversal success) rather than the full object list. This use case may justify application-specific optimizations that are not applicable to general-purpose object lookups. Peff’s critique distinguishes between the alternates-specific regression (which requires a targeted fix) and broader optimizations for `check_connected()` (which could benefit from Junio’s proposed hints).
- **Process coordination**: The need to coordinate object visibility between `index-pack`, `rev-list`, and user hooks spans process boundaries, complicating architectural solutions that assume a single-process context. This constraint is now central to the feasibility of Patrick’s transaction-aware ODB writes.
