This is a **maintainer's perspective on the ODB performance regression** in the `git receive-pack` connectivity check. Junio C Hamano responds to Jeff King’s analysis with a nuanced take on how to reconcile the ODB abstraction’s design goals with the need for performance optimizations.

Junio proposes a middle-ground solution: **treating ODB backends as opaque but still allowing them to expose "fast" and "slow" lookup phases**. This would let Git check all fast lookups (e.g., packs) across backends before moving to slow ones (e.g., loose objects), preserving the abstraction while restoring the performance lost in the ODB rework. He suggests this could be implemented by passing application-specific hints (like "this is a connectivity check") down to the ODB layer, enabling optimizations tailored to the use case.

He also steps back to question whether the current use of `git rev-list` for connectivity checks is the right tool for the job. Since the caller only cares about whether the traversal succeeds (not the actual list of objects), Junio speculates that alternative approaches—such as preloading loose object names into an in-memory table or Bloom filter—could avoid expensive `lstat()` calls entirely. This hints at a possible longer-term redesign of the connectivity check machinery, though he doesn’t propose a concrete alternative here.

The email **advances the thread** by offering a principled way forward that balances abstraction and performance, but it leaves open questions: Will Patrick Steinhardt (the ODB rework’s author) accept this approach, or will he push back on breaking the abstraction’s opacity? Could the connectivity check be reworked to avoid the problem entirely? For now, this reply shifts the discussion toward practical trade-offs rather than reverting the ODB changes outright.
