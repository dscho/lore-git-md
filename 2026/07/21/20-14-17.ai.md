This is the v3 cover letter for Harald Nordgren’s two-patch series that restores push-tracking display after remote renames when `branch.<name>.pushRemote` is set to a URL. The series is now on its third iteration, with the key change in this revision being the inclusion of `pushurl` and `pushInsteadOf` in the URL-matching logic, addressing Junio C Hamano’s technical gap identified in v2.

The core goal remains unchanged: when a remote is renamed (e.g., from `origin` to `upstream`), Git’s push-tracking logic loses the configured remote name, and `git status` stops displaying the push destination. The solution resolves the URL of the renamed remote to any remaining remote that shares the same URL or `pushurl`, restoring the push-tracking display. The series also extends support to allow a URL as the value for `branch.<name>.pushRemote`, treating it as a lookup key for a uniquely matching configured remote. This extension is motivated by workflows involving GitHub’s `gh` CLI, which renames remotes during forking.

Patch 1/2 is a mechanical refactoring that passes a `struct repository *` parameter to the push-tracking helper function, part of the ongoing `the_repository` removal effort. Patch 2/2 implements the core logic: if the originally configured push remote is missing or is a URL, Git consults the URL-to-remote map to find a fallback remote with the same URL or `pushurl`. If exactly one such remote exists, it is used to resolve `@{push}` and update the remote-tracking branch after a push; if multiple remotes share the URL, the behavior remains unchanged to avoid ambiguity. The commit touches `remote.c`, `transport.c`, and updates `Documentation/config/branch.adoc` and `Documentation/revisions.adoc` to document the new behavior. A new test script (`t/t5505-remote.sh`) adds 124 lines of coverage for rename scenarios, URL resolution, `pushInsteadOf` handling, and edge cases.

The revised commit messages in v3 clarify the motivation and design intent: the URL-based push-remote resolution is an *extension* to support workflows involving renamed remotes, not a fix for an existing capability. The documentation updates explicitly state that `branch.<name>.pushRemote` may now be a URL and describe how `@{push}` behaves in that case. The test coverage now includes `pushInsteadOf` scenarios, addressing Junio’s feedback about the need to consider both `url` and `pushurl` members of a remote. The series appears well-scoped, with thorough test coverage and clear motivation. The files touched are `remote.c`, `remote.h`, `transport.c`, `Documentation/config/branch.adoc`, `Documentation/revisions.adoc`, and the new test script. Key names introduced include `repo_remote_for_push_tracking()` and the updated `tracking_for_push_dest()` function.
