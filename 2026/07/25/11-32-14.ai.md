This is the **core implementation patch** of Harald Nordgren’s `git branch --delete-merged` series, now in its **23rd and final iteration** and **ready for merging**. The patch adds the `--delete-merged` subcommand to `git branch`, enabling safe, automated cleanup of local branches whose work has already landed on their upstream. The command is **feature-complete**, with all safety mechanisms implemented: order-independent stacked-branch protection, per-branch opt-out, `--dry-run` preview, and repeatable upstream selectors.

The patch introduces `delete_merged_branches()`, the central function that filters candidate branches using the `--forked` filter machinery (added in patch 1/7), applies safety checks, and orchestrates the deletion. Key behaviors include:
- **Repeatable upstream selection**: The `--delete-merged` option can be specified multiple times (e.g., `--delete-merged origin/main --delete-merged origin/next`) to widen the upstream match. Optional positional patterns (e.g., `topic-*`) limit the deletion scope.
- **Safety checks**: Branches are preserved if they are checked out, have missing upstreams, or would update their upstream when pushed by name (e.g., `main` tracking `origin/main`). Unmerged branches are silently skipped.
- **Order-independent stacked-branch protection**: A single-pass graph traversal (`collect_stacked_branch_bases()`) ensures branches are never deleted out from under stacked work, regardless of ref iteration order. The command fails to delete a branch if it is used as an upstream for an unmerged branch but clears the upstream config for kept (merged) branches whose own upstream is being deleted.
- **Flags-based API**: The command uses the refactored `delete_branches()` API (patches 2-4/7) with `DELETE_BRANCH_SKIP_UNMERGED` (to skip unmerged branches silently) and `DELETE_BRANCH_NO_HEAD_FALLBACK` (to prevent falling back to `HEAD`).

The implementation touches `builtin/branch.c` and adds 204 lines of integration tests in `t/t3200-branch.sh`, covering edge cases like stacked dependencies, self-referential upstreams, missing upstreams, and the interaction with `remote.pushDefault`. The tests explicitly verify that the stacked-branch protection logic produces consistent results regardless of ref iteration order and that the command respects per-branch opt-out (added in patch 6/7).

This patch is **well-motivated** (addressing a real workflow pain point), **thoroughly tested**, and **aligned with Git’s API consistency expectations**. The only agreed follow-up work is extending stacked-branch protection to `git branch -d` for consistency, which will be implemented after the series lands. The series is **unblocked** and should appear in an upcoming "What's cooking" report.
