This is the second patch in a two-patch bugfix series targeting a critical memory-safety issue in `git worktree add`. The patch adds explicit validation to reject empty strings as worktree paths before they reach the problematic `worktree_basename()` function, which was shown in the first patch to perform an out-of-bounds read when given such input. The change is minimal—just two lines in `builtin/worktree.c`—and directly addresses the edge case that can lead to data loss (recursive deletion of the current working directory, including `.git`).

The patch is well-motivated: the commit message clarifies that the existing BUG message (`How come '' becomes empty after sanitization?`) is a symptom of the underlying issue, not a bug in the sanitization code itself. By rejecting empty strings outright, the patch closes the door on the memory-unsafe behavior while providing a clear error message to users. The fix is narrowly scoped and does not introduce new CLI options, on-disk format changes, or dependencies.

This patch complements the first patch, which prevents the out-of-bounds read in `worktree_basename()`. Together, they form a complete fix for the issue, though neither patch includes test coverage or reproduction steps. The series is likely to attract attention from maintainers of the worktree subsystem, as the bug was discovered in the wild (Git for Windows #6346) and involves a real risk of data corruption. Reviewers may request tests or additional validation for other edge cases (e.g., strings consisting solely of directory separators), but the current patch is a necessary and correct step toward resolving the issue.
