Subject: [PATCH 0/2] checkout -m: refine autostash conflict handling
Series version: v5 (posted, queued for merging to `next`)
Originating author: Harald Nordgren
Thread type: patch series (closed; spin-off tooling discussion)

Core problem or goal
Refine `git checkout -m` behavior when autostash is involved by visually separating autostash conflict advice from the branch-switch confirmation message, eliminating visual clutter without altering the underlying conflict resolution logic. The series also correctly distinguishes between true conflicts and other failures during stash application, and aligns exit codes with Git’s established conventions (exit code 1 for conflicts, other non-zero values for errors). A spin-off discussion about Git’s style enforcement in CI is ongoing: the project’s `.clang-format` configuration (`RemoveBracesLLVM: true`) removes excess braces from single-statement `if/else` bodies but does not enforce consistent brace usage across `if/else if/else` cascades, leaving some style decisions to manual review. The tooling discussion now explores whether Git should adopt stricter, fully automated style enforcement to eliminate manual style debates, weighing the one-time disruption of a global reformat against long-term consistency gains.

Current status
v5 posted, reviewed, and accepted. Junio has explicitly stated both patches are "good to me" and will queue the series for merging to `next` in the upcoming integration cycle. The series is scheduled for integration; no further iterations or technical changes are expected. The spin-off discussion about style enforcement in CI remains open but is purely exploratory: no policy changes or code changes are proposed. The GitHub CI workflow (`.github/workflows/check-style.yml`) and local `make style` target continue to run `git clang-format` in an advisory capacity, as the tool cannot enforce consistent brace usage in `if/else if/else` cascades.

Key technical details
- Files touched: `sequencer.c`/`sequencer.h` (return-value semantics, conflict detection logic, and the new `do_stash_apply` helper), `builtin/checkout.c` (advice formatting and error messages), `builtin/stash.c` (exit code handling and brace style consistency), `stash.h` (new `enum stash_apply_result` definition: `STASH_APPLY_CLEAN`, `STASH_APPLY_CONFLICT`, `STASH_APPLY_ERROR`), `Documentation/git-stash.adoc` (exit code documentation), and tests (`t/t3903-stash.sh`, `t/t7201-co.sh`).
- New behavior: `apply_save_autostash_oid()` and `apply_save_autostash_ref()` return `enum stash_apply_result` instead of `int`. Callers in `checkout.c` print a blank line to stderr when the return value is `STASH_APPLY_CONFLICT`, and a new error message (e.g., "could not apply autostash") for `STASH_APPLY_ERROR`. The conflict detection logic distinguishes between `ret == 1` (conflict, exit code 1), `ret > 1` or negative (error, exit code 128 or other non-zero), and `ret == 0` (success, exit code 0). Exit code documentation in `git-stash.adoc` is updated to reflect this convention.
- Symbols: `apply_save_autostash_oid()`, `apply_save_autostash_ref()` (return type changed to `enum stash_apply_result`), `do_stash_apply()` (new helper function for `run_command()` enum handling), `enum stash_apply_result` (`STASH_APPLY_CLEAN`, `STASH_APPLY_CONFLICT`, `STASH_APPLY_ERROR`).
- Test coverage: updated tests in `t/t3903-stash.sh` and `t/t7201-co.sh` use `test_cmp` to validate the full screen output, including the new blank line for conflicts and the new error message for non-conflict failures. Tests cover all three return states and now include `stash branch` coverage. The unnecessary commit in `t3903-stash.sh` has been removed.
- Code clarity: the nested ternary operator in `do_apply_stash()` and odd indentation in function signatures have been addressed. The redundant `STASH_APPLY_ERROR` assignment in one error path has been removed. Junio’s review suggested two minor mechanical refinements: consistent brace usage in conditionals and a helper function for `run_command()` enum handling; these are implemented in v5. The series does not address a surface-level style nit about missing braces in an `else if` branch in `stash.c` (noted by Phillip Wood and Junio), but this does not affect functionality or integration readiness. Git’s `.clang-format` configuration (`RemoveBracesLLVM: true`) removes excess braces from single-statement `if/else` bodies but does not enforce consistent brace usage across `if/else if/else` cascades, as confirmed by Junio’s examination. The GitHub CI job (`.github/workflows/check-style.yml`) and local `make style` target run `git clang-format` but are advisory only; the tool’s output can vary across versions and does not perfectly match Git’s style guide.

Open questions and loose ends
None for the patch series itself. The spin-off discussion about style enforcement in CI remains open but is purely exploratory: Harald Nordgren and Phillip Wood are weighing the trade-offs of adopting stricter, fully automated style enforcement (e.g., via `clang-format` or `checkpatch.pl`) to eliminate manual style debates. Harald argues that a linter-enforced, auto-fixable style would eliminate an entire class of code-review discussions, even if the specific rules are arbitrary, and sees the one-time disruption of a global reformat as a worthwhile cost. Phillip’s earlier point—that the current CI job is advisory because `clang-format` does not perfectly match Git’s style guide and its output varies across versions—remains the crux of the trade-off: either accept the tool’s deviations and stop debating style, or continue handling style manually. No decisions or action items have emerged; the thread documents the tension between automation and manual review, leaving the status quo intact for now.
