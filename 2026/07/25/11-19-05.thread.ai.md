Subject: [PATCH 0/2] Fix out-of-bounds read in `git worktree add` leading to data loss
Series version: v1 (initial submission; v2 pending review feedback, now with René Scharfe as sole author for the first patch)
Originating author: Matthias Aßhauer (series), René Scharfe (first patch)
Thread type: bugfix patch series

Core problem or goal
Fix a critical memory-safety bug in `worktree_basename()` (`builtin/worktree.c`) that causes `git worktree add` to perform an out-of-bounds read when given an empty string *with an explicit branch or commit reference* (e.g., `git worktree add "" HEAD` or `git worktree add "//" HEAD`). The bug can lead to silent data corruption (recursive deletion of the working directory, including `.git`) or trigger a BUG message (`How come '' becomes empty after sanitization?`). The root cause is a design flaw in `worktree_basename()`: the function returns a pointer to the basename but requires callers to compute the length via fragile pointer arithmetic (`path + len - name`), which underflows when `len` is zero.

Current status
Under active review; no prior versions. The first patch is now **ready for `next`** with René Scharfe as the sole author. Junio C Hamano explicitly endorses the approach ("obvious and clear") and suggests it is ready for integration, pending any further review comments. The patch replaces the original pointer-decrement loop with an integer-index loop that stops at the string boundary, eliminating the underflow risk entirely. It preserves the function’s interface while fixing the memory-safety flaw and is simpler and more robust than Matthias Aßhauer’s original proposal.

The second patch (explicit validation to reject empty strings) remains **needs adjustment**. René Scharfe’s latest review clarifies that the validation is *not* redundant—it catches the edge case where an empty string is passed *with* a reference (e.g., `HEAD`), which bypasses earlier branch-name validation (`git branch "" HEAD`) and exposes the memory-safety flaw. However, the patch’s current placement (in `add_worktree()`) may be suboptimal; validation could be moved to `add()` or `dwim_branch()` to fail faster. The commit message should also be updated to reflect this nuance (e.g., "reject empty worktree paths when a reference is provided").

Key technical details
- **Files touched**: `builtin/worktree.c`
- **Root cause**: `worktree_basename()` decrements the `name` pointer below the start of the input string when the input is empty or contains only separators, leading to undefined behavior. The function’s interface is error-prone because it relies on callers to compute the length via pointer arithmetic (`path + len - name`).
- **Callers affected**: `add_worktree()`, `dwim_branch()`, and `add()` in `builtin/worktree.c`. Two callers (`dwim_branch()` and `add()`) avoid immediate issues only because `xstrndup()` with a length of zero does not dereference the pointer, but this is an implementation detail rather than a safe design.
- **New behavior**: The first patch ensures `worktree_basename()` no longer underflows, but the second patch is still required to make `git worktree add "" HEAD` and `git worktree add "//" HEAD` fail with an error instead of corrupting the working directory. The second patch’s validation is confirmed as necessary for the `"" HEAD` case.
- **No new symbols, CLI options, or on-disk format changes**.
- **No test coverage included** in the series; reviewers have requested reproduction steps or test cases to verify the fix (especially for the `"" HEAD` case) and prevent regressions. The bug’s manifestation is call-path-dependent, with some edge cases (e.g., `git worktree add ""`) already handled by earlier validation.
- **Bug context**: Discovered via Git for Windows issue #6346; likely triggered by unset environment variables in scripts or strings that become empty after sanitization.
