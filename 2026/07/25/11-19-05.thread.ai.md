Subject: [PATCH 0/2] Fix out-of-bounds read in `git worktree add` leading to data loss
Series version: v1 (initial submission; v2 likely after review feedback)
Originating author: Matthias Aßhauer
Thread type: bugfix patch series

Core problem or goal
Fix a critical memory-safety bug in `worktree_basename()` (`builtin/worktree.c`) that causes `git worktree add` to perform an out-of-bounds read when given an empty string or a string consisting solely of directory separators (e.g., `""` or `"//"`). The bug can lead to silent data corruption (recursive deletion of the working directory, including `.git`) or trigger a BUG message (`How come '' becomes empty after sanitization?`). The issue was discovered in the wild (Git for Windows #6346), likely via an unset environment variable (e.g., `git worktree add "$UNSET_VAR"`). The root cause is a design flaw in `worktree_basename()`: the function returns a pointer to the basename but requires callers to compute the length via fragile pointer arithmetic (`path + len - name`), which underflows when `len` is zero.

Current status
Under active review; no prior versions. Two patches:
1. **Needs rework**: The first patch attempts to prevent the out-of-bounds read by tracking the original string length but introduces a new risk: when `path` is a string like `"///"`, the proposed fix can still underflow the pointer, leading to `strbuf_add()` allocating an enormous buffer (due to negative length wrapping to `SIZE_MAX`). Junio C Hamano and René Scharfe both identify flaws in the current approach. Junio suggests avoiding pointer arithmetic entirely when `len` is zero or using an integer index loop to eliminate underflow risk. René proposes a more fundamental refactoring: have `worktree_basename()` return the *length* of the basename directly, making the function harder to misuse and addressing the root cause.
2. **Pending**: The second patch adds explicit validation to reject empty strings outright, providing a clear error message. This patch may require adjustment if the first patch's logic changes, but its core goal (rejecting empty inputs) is uncontested.

Key technical details
- **Files touched**: `builtin/worktree.c`
- **Root cause**: `worktree_basename()` decrements the `name` pointer below the start of the input string when the input is empty or contains only separators, leading to undefined behavior. The function's interface is error-prone because it relies on callers to compute the length via pointer arithmetic (`path + len - name`).
- **Callers affected**: `add_worktree()`, `dwim_branch()`, and `add()` in `builtin/worktree.c`. Two callers (`dwim_branch()` and `add()`) avoid immediate issues only because `xstrndup()` with a length of zero does not dereference the pointer, but this is an implementation detail rather than a safe design.
- **New behavior**: The series aims to make `git worktree add ""` and `git worktree add "//"` fail with an error instead of corrupting the working directory.
- **No new symbols, CLI options, or on-disk format changes**.
- **No test coverage included** in the series; reviewers may request reproduction steps or test cases to verify the fix and prevent regressions.
- **Bug context**: Discovered via Git for Windows issue #6346; likely triggered by unset environment variables in scripts.
