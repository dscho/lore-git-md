Subject: [PATCH 0/2] Fix out-of-bounds read in `git worktree add` leading to data loss
Series version: v1 (initial submission)
Originating author: Matthias Aßhauer
Thread type: bugfix patch series

Core problem or goal
Fix an out-of-bounds memory read in `worktree_basename()` (in `builtin/worktree.c`) that can cause `git worktree add` to recursively delete the current working directory (including `.git`) when an empty string or a string consisting solely of directory separators is passed as the worktree path. The bug manifests inconsistently—sometimes triggering a BUG message (`How come '' becomes empty after sanitization?`), sometimes allowing silent corruption.

Current status
Under review; no prior versions. Two patches:
1. Prevents the out-of-bounds read by ensuring the function does not access memory before the start of the input path string.
2. Adds explicit validation to reject empty strings outright, closing the edge case where malformed input could bypass safety checks. The second patch is now described in detail: it adds a two-line guard in `builtin/worktree.c` to reject empty strings before they reach `worktree_basename()`, providing a clear error message to users.

Key technical details
- Files touched: `builtin/worktree.c`
- New behavior: `git worktree add ""` and `git worktree add "//"` now fail with an error instead of corrupting the working directory.
- Root cause: `worktree_basename()` decrements the `name` pointer below the start of the input string when the input is empty or contains only separators.
- No new symbols, CLI options, or on-disk format changes.
- No test coverage included in the series.
- Bug discovered in the wild (Git for Windows #6346), likely via an unset environment variable (e.g., `git worktree add "$UNSET_VAR"`).
