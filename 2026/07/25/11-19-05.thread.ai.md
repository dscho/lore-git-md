Subject: [PATCH 0/2] Fix out-of-bounds read in `git worktree add` leading to data loss
Series version: v1 (initial submission; v2 pending review feedback)
Originating author: Matthias Aßhauer
Thread type: bugfix patch series

Core problem or goal
Fix a critical memory-safety bug in `worktree_basename()` (`builtin/worktree.c`) that causes `git worktree add` to perform an out-of-bounds read when given an empty string *with an explicit branch or commit reference* (e.g., `git worktree add "" HEAD` or `git worktree add "//" HEAD`). The bug can lead to silent data corruption (recursive deletion of the working directory, including `.git`) or trigger a BUG message (`How come '' becomes empty after sanitization?`). The issue was discovered in the wild (Git for Windows #6346), likely via unset environment variables (e.g., `git worktree add "$UNSET_VAR" HEAD`). The root cause is a design flaw in `worktree_basename()`: the function returns a pointer to the basename but requires callers to compute the length via fragile pointer arithmetic (`path + len - name`), which underflows when `len` is zero.

Current status
Under active review; no prior versions. The series now has two competing proposals for the first patch:
1. **Needs rework**: Matthias Aßhauer’s original patch attempts to prevent the out-of-bounds read by tracking the original string length but introduces a new risk: when `path` is a string like `"///"`, the proposed fix can still underflow the pointer, leading to `strbuf_add()` allocating an enormous buffer (due to negative length wrapping to `SIZE_MAX`). Junio C Hamano and René Scharfe both identify flaws in this approach.
2. **Ready for review**: René Scharfe’s alternative patch replaces the original loop with a safer integer-index loop that stops at the string boundary, eliminating the underflow risk entirely. This patch is a drop-in replacement for the first patch in the series and addresses the root cause without changing the function’s interface. It is simpler, more robust, and avoids the negative-length edge case flagged by Junio.

The second patch (explicit validation to reject empty strings) remains **needs adjustment**. René Scharfe’s latest review clarifies that the validation is *not* redundant—it catches the edge case where an empty string is passed *with* a reference (e.g., `HEAD`), which bypasses earlier branch-name validation (`git branch "" HEAD`) and exposes the memory-safety flaw. However, the patch’s current placement (in `add_worktree()`) may be suboptimal; validation could be moved to `add()` or `dwim_branch()` to fail faster. The commit message should also be updated to reflect this nuance (e.g., "reject empty worktree paths when a reference is provided").

Key technical details
- **Files touched**: `builtin/worktree.c`
- **Root cause**: `worktree_basename()` decrements the `name` pointer below the start of the input string when the input is empty or contains only separators, leading to undefined behavior. The function’s interface is error-prone because it relies on callers to compute the length via pointer arithmetic (`path + len - name`).
- **Callers affected**: `add_worktree()`, `dwim_branch()`, and `add()` in `builtin/worktree.c`. Two callers (`dwim_branch()` and `add()`) avoid immediate issues only because `xstrndup()` with a length of zero does not dereference the pointer, but this is an implementation detail rather than a safe design.
- **New behavior**: The series aims to make `git worktree add "" HEAD` and `git worktree add "//" HEAD` fail with an error instead of corrupting the working directory. The second patch’s validation is confirmed as necessary for the `"" HEAD` case.
- **No new symbols, CLI options, or on-disk format changes**.
- **No test coverage included** in the series; reviewers have requested reproduction steps or test cases to verify the fix (especially for the `"" HEAD` case) and prevent regressions. The bug’s manifestation is call-path-dependent, with some edge cases (e.g., `git worktree add ""`) already handled by earlier validation.
- **Bug context**: Discovered via Git for Windows issue #6346; likely triggered by unset environment variables in scripts or strings that become empty after sanitization.
