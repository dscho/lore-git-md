Thread identity: `[PATCH 0/3] v1` series migrating four global configuration variables (`minimum_abbrev`, `default_abbrev`, `pack_size_limit_cfg`, `assume_unchanged`) into `repo_config_values` as part of the ongoing `the_repository` removal effort. Originating author: Tian Yuchen. Thread type: patch series (infrastructure refactoring).

Core problem or goal: Eliminate four more process-global configuration variables by making them repository-scoped, enabling code paths that explicitly avoid `the_repository` (e.g., `merge-ort`) to access them safely. The series is a direct continuation of prior `repo_config_values` work and is motivated by the broader goal of removing implicit reliance on the global `the_repository`.

Current status: Under review (v1 posted). Series consists of three patches:
- Patch 1/3: Migrates `minimum_abbrev` and `default_abbrev`; introduces repository-aware getters (`repo_minimum_abbrev()`, `repo_default_abbrev()`) and moves the variables into `repo_config_values`. The `MINIMUM_ABBREV` and `DEFAULT_ABBREV` macros are redefined to call these getters for backward compatibility. **Controversial**: Junio objects to the unconditional fallback to `the_repository` when `repo != the_repository`, arguing it papers over an API limitation rather than addressing it. He proposes `BUG()` in such cases to force proper API extension.
- Patch 2/3: Migrates `pack_size_limit_cfg` from a standalone global in `environment.c` into the `repo_config_values` struct. All direct references are updated to use the repository-specific instance. No getter function is introduced due to limited call sites (only two). In `object-file.c`, a local `cfg` pointer ensures the value is accessed via `the_repository`'s config for backward compatibility.
- Patch 3/3: Migrates `assume_unchanged` from `environment.h` into the `repo_config_values` struct. The global variable is removed, and all direct references are updated to use the repository-specific instance. No getter function is introduced due to limited call sites and no hardcoded fallback values. Backward compatibility is maintained by accessing the value via `the_repository`'s config in affected code paths.

Key technical details:
- Files touched: `environment.c`/`environment.h` (central location for the variables), with callers updated in `builtin/pack-objects.c`, `builtin/update-index.c`, `merge-ort.c`, `object-file.c`, `object-name.h`, `read-cache.c`, `replay.c`, and `sequencer.c`.
- New or renamed symbols: Repository-aware getters for `minimum_abbrev` and `default_abbrev` (`repo_minimum_abbrev()`, `repo_default_abbrev()`). No getters for `pack_size_limit_cfg` or `assume_unchanged` due to limited call sites. Implementation includes explicit checks for `repo != the_repository` where applicable.
- Subsystems affected: Configuration handling, object abbreviation, pack-objects, index updates, merge machinery (`merge-ort`), replay, sequencer, and ODB transaction logic.
- No behavior change intended; the series is purely infrastructure for future libification.
- Test coverage: Not explicitly mentioned, but the mechanical nature of the changes suggests existing tests should suffice. The ODB transaction logic in `object-file.c` (touched in patch 2/3) and the `core.ignorestat` behavior in `read-cache.c` (touched in patch 3/3) are noted as potential edge cases for testing.

Open questions and loose ends:
- **Architectural direction**: Junio’s objection to patch 1/3’s fallback to `the_repository` raises a fundamental question: should repository-scoped getters unconditionally delegate to `the_repository` when `repo != the_repository`, or should they `BUG()` to force proper API extension? The former approach risks accumulating technical debt; the latter may block progress until dependent APIs are updated.
- **Scope of v2**: Whether patches 2/3 and 3/3 will need revision depends on the resolution of patch 1/3’s design. If the fallback is removed, callers in `merge-ort.c` and other subsystems may need to be updated to handle the `BUG()` case or provide their own repository-aware APIs.
