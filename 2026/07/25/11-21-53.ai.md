This is a **substantive review follow-up** in the ongoing thread fixing `git rebase --update-refs` edge cases with symbolic references. Erik Cervin-Edin reports a regression he encountered in v2 of Son Luong Ngoc’s series and explains why it was resolved in v3, while also surfacing a latent bug in the current `master` branch.

The regression in v2 occurred because the logic for skipping the current branch (the one being rebased) relied on `branch_checked_out()` returning `NULL` for the checked-out branch, which it does not—it returns the worktree path regardless of whether the branch is checked out in the current worktree or another one. This caused the current branch to incorrectly appear in the `git-rebase-todo` file as an `--update-refs` entry, even though it is updated automatically by the rebase itself. The v3 series fixed this by removing the `!path` gate and reordering the checks, ensuring the current branch is always skipped.

Erik also identifies a **pre-existing bug in `master`**: the `head_ref` buffer used to compare against decoration names is clobbered by the call to `branch_checked_out()`, which internally calls `refs_resolve_ref_unsafe()`. This can cause branches that should be skipped (because they match HEAD) to incorrectly appear in the todo list. The bug surfaces when multiple branches are checked out across worktrees, and the order of resolution causes `head_ref` to be overwritten before comparison. This is not a regression introduced by the series—it exists in the current codebase—but it explains why some users might see unexpected entries in their rebase todo files even on `master`.

The discussion reinforces Phillip Wood’s earlier feedback about the fragility of the HEAD comparison logic and the need for careful handling of resolved references. While the v3 series resolves the immediate regression, Erik’s observation highlights that the underlying issue in `master` remains unaddressed. This is likely to become a follow-up topic once the current series lands.
