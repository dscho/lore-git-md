This thread is fixing a critical memory-safety bug in `git worktree add` that can lead to silent data corruption—specifically, recursive deletion of the working directory including `.git`—when given an empty string or a string consisting solely of directory separators (e.g., `""` or `"//"`). The bug was discovered in the wild via Git for Windows issue #6346, likely triggered by unset environment variables in scripts. Matthias Aßhauer’s initial two-patch series addresses the issue in `worktree_basename()` (`builtin/worktree.c`), but both patches are now under active rework after substantive technical reviews.

The first patch, which attempts to prevent the out-of-bounds read by tracking the original string length, was found to introduce a new risk: pointer underflow when the input is a string like `"///"`, potentially causing `strbuf_add()` to allocate an enormous buffer. Junio C Hamano and René Scharfe both identified flaws in this approach, with Junio suggesting safer alternatives (e.g., integer index loops) and René proposing a more fundamental refactoring—having `worktree_basename()` return the basename length directly—to eliminate the error-prone pointer arithmetic at the root of the problem. The second patch, which adds explicit validation to reject empty strings, was revealed by René to be redundant: the empty-string case is already caught earlier in the call chain by `git branch "" HEAD`, which rejects invalid branch names. This makes the patch ineffective, though the core goal of rejecting empty inputs remains uncontested.

Key participants—Junio, René, and Matthias—have all engaged substantively. Junio and René’s reviews highlight that the series needs significant revision before it can be accepted. The first patch’s design is still contested, with René advocating for a broader refactoring, while the second patch’s necessity is now in question.
