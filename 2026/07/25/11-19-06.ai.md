This is the first patch in a two-part bugfix series addressing a critical memory-safety issue in `git worktree add`. The patch prevents an out-of-bounds read in `worktree_basename()` when an empty string (or a string consisting solely of directory separators) is passed as the worktree path. Without this fix, the function accesses memory before the start of the input string, leading to undefined behavior—most alarmingly, the recursive deletion of the current working directory (including `.git`) in some cases.

The change is confined to `builtin/worktree.c` and modifies the logic in `worktree_basename()` to avoid decrementing the `name` pointer below the start of the input string. When the input is empty, the function now returns the original pointer (adjusted for trailing separators) instead of attempting to traverse backward. This eliminates the out-of-bounds access but leaves the function returning an empty string, which triggers a BUG message (`How come '' becomes empty after sanitization?`) in later validation. The second patch in the series will address this by explicitly rejecting empty strings.

The commit message clearly explains the consequences (data loss) and the root cause (memory unsafety), though it does not include test cases or reproduction steps. The fix is narrowly scoped and appears technically sound, though reviewers may request additional validation (e.g., tests for edge cases like strings with only separators). The GitHub issue link (Git for Windows #6346) suggests this was discovered in the wild, likely via an unset environment variable (e.g., `git worktree add "$UNSET_VAR"`).
