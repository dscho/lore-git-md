This GSoC feature series from Pablo Sabater extends `git cat-file --batch-command` to support the `%(objecttype)` placeholder, allowing clients to request object type metadata from servers alongside size. The series is now at v3, feature-complete, and under final review.

The architectural refactoring is settled: the legacy `struct object_info` has been replaced with a dedicated `struct fetch_object_info_results` that holds only the fields the caller requests (currently size and type). This design, proposed by Junio and Peff, avoids sentinel values and boolean flags, using a single array of lightweight structs where the caller controls which fields are populated. The server now advertises a "type" capability, transmits type data as strings (e.g., `"blob"`), and the client maps these to Git’s internal `enum object_type`.

All prior review feedback has been addressed, including test robustness improvements and protocol hygiene fixes. Junio raised two forward-compatibility concerns: the client now detects under-length responses (fewer objects than requested) but should also reject over-length responses (more objects than requested) by checking for an immediate flush packet after reading the expected count. Pablo plans to add this defensive check. The second concern—a premature `ask_type` flag introduced before the client can parse type responses—will be fixed by moving the flag to a later patch, eliminating a potential `BUG()` scenario.

The series touches core files (`fetch-object-info.c`, `builtin/cat-file.c`, `protocol-caps.c`) and test suites (`t5701`, `t1017`), expanding coverage for the new placeholder. The default format for all queries is now unified to `%(objectname) %(objecttype) %(objectsize)`, ensuring consistent output across transport protocols. No on-disk format changes are involved.

With the GSoC deadline passed, the series is merge-ready. The remaining loose ends are minor protocol hygiene issues that will be resolved in the next iteration or as follow-ups. Reviewers have focused on the robustness of the protocol handling, but no substantive objections remain.
