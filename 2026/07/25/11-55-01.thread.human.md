This GSoC thread is extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder for remote-object-info queries, completing the metadata that can be reliably fetched from a server. The series is now at v2, with Pablo Sabater having addressed all prior feedback, but the architectural refactoring of how batch results are stored remains the central discussion point.

Two competing designs for the refactoring have emerged: Pablo’s `object_info_results` (a struct of arrays with boolean flags to control which metadata fields are populated) and Junio’s simpler array of lightweight structs (e.g., `struct { struct oid *oid; enum object_type type; size_t size; }`). Jeff King (Peff) has now weighed in, refining the trade-offs between memory efficiency and code clarity. He notes that Junio’s design, while viable, wastes memory when only a subset of fields is requested and complicates signaling which fields are valid. The discussion has converged on a hybrid approach: a single array of lightweight structs where the caller decides which fields to populate, avoiding sentinels entirely. This aligns with the protocol’s transmission of raw strings (e.g., `"blob"`, `"1234"`) that the client parses directly, bypassing `struct object_info` and simplifying the implementation.

The series is still under review, with no maintainer decision yet. The key files affected are `fetch-object-info.c` and `builtin/cat-file.c`, and the next revision will need to incorporate this hybrid design. The only remaining loose end is a minor shell quoting fix in the tests, which Pablo has already acknowledged. The GSoC deadline is approaching, and this refactoring is confirmed as part of the series.
