Thread identity
Subject: [PATCH 0/4] last-modified: reuse Bloom filters for speed
Series version: v1 (initial submission)
Originating author: Toon Claes
Thread type: patch series (performance optimization)

Core problem or goal
Make the experimental `git last-modified` command as fast as `git log` when querying the last commit that modified files matching a pathspec (including wildcards like `*.c`), by reusing Git’s Bloom filter machinery more effectively. The current implementation is ~3.7× slower (52 ms vs 14 ms) on the ziglang/zig repository.

Current status
Under review; v1 posted. No prior versions. Author acknowledges an oversight in commit trailers (missing `Helped-by`/`Based-on-patches-by` for Jeff King) and intends to add them in a reroll. Junio C Hamano's review of patch 2/4 identifies two unintended behavioral changes in Bloom filter statistics reporting: (1) the new code increments `count_bloom_filter_not_present` even when no key vectors exist, whereas the original code returns early without incrementing; (2) the new code returns immediately on `bloom_filter_contains_vec()` errors, skipping counter updates that the original code performed. Junio suggests these should either be documented as intentional fixes or corrected. Taylor Blau now agrees with Junio that the first change is unintentional and should be reverted to preserve the original guard (`revs->bloom_keyvecs_nr != 0`) before generation and filter lookups. Junio also proposes a stylistic improvement to the loop in `revs_maybe_changed_in_bloom()` to return immediately on a positive result. Jeff King's review of patch 1/4 raises a design concern about the tristate return semantics of `check_maybe_different_in_bloom_filter` (returning `0`, `1`, or `-1`), arguing that exposing this subtlety in the public API (`revision.h`) is error-prone and suggesting a boolean return (`false` = definitely unchanged, `true` = possibly changed) for clarity. Taylor Blau's review of patch 3/4 identifies a correctness bug in the Bloom-filter pre-filtering logic when `--show-trees` is used: the pathspec does not cover all entries in `lm->paths` (which includes ancestor tree entries added by `populate_paths_from_revs()`), so a Bloom filter that says "no changes" for the pathspec may still miss changes to those ancestor trees. Jeff King's latest review of patch 3/4 endorses Taylor's correctness concern and proposes an alternative design: rather than disabling the Bloom-filter optimization when `--show-trees` is used, remove ancestor tree entries from the output when they are not covered by the original pathspec. This would preserve the performance benefit while avoiding misleading results. He argues this is an acceptable trade-off for an experimental command, as it simplifies the output and aligns with the likely intent of most callers. The proposal involves double-checking pathspecs in `add_path_from_diff()` to filter out such entries. Jeff King also notes a documentation inconsistency: the man page claims `-t` has no effect without `-r`, but the test case shows it does. The broader design question of whether `--show-trees` should behave this way at all remains open, given that `git log` does not include ancestor trees in its output for similar queries. Jeff King's review of patch 4/4 raises a maintainability concern about the current approach of restoring `bloom_filter_settings` after `prepare_revision_walk()` clears it, arguing that `rev_info.bloom_filter_settings` is an internal implementation detail of `revision.c` and suggesting a cleaner design where `last-modified` manages its own settings pointer instead of relying on the revision machinery. He provides a diff illustrating this alternative, which moves the settings into the `last_modified` struct to avoid conflicts with `revision.c`'s use of the same field. The review also raises a broader design question about whether `bloom_filter_settings` should be a repository-level property accessible via a helper like `repo_bloom_filter_contains()`, rather than requiring callers to manage the settings pointer themselves. The cover-letter benchmarks, which use `--show-trees`, may therefore be misleading until the correctness bug is fixed.

Key technical details
- Files touched: `revision.c`, `revision.h`, `builtin/last-modified.c`
- New symbols: `repo_may_have_commit_with_changes` (exposed in `revision.h`), `revs_maybe_changed_in_bloom` (new public function in `revision.h`)
- Behavior change: `git last-modified` reuses Bloom filters instead of re-fetching them, reducing runtime from 52 ms to 14 ms on the ziglang/zig repository (matching `git log` speed). The optimization now covers all pathspec types, including wildcards (e.g., `*.c`), which require per-path Bloom-filter lookups.
- On-disk format: unchanged
- Test coverage: benchmarks included in cover letter; no new test files added. Taylor Blau's review includes a minimal reproduction case in `t8020` demonstrating the `--show-trees` correctness bug and identifies a gap in test coverage for the Bloom filter code path in patch 4/4 (the existing test suite does not exercise the Bloom filter code path because it never writes a commit-graph with `--changed-paths`, and test cases use unquoted wildcards that bypass per-path Bloom filter logic). Jeff King's review of patch 3/4 highlights a documentation inconsistency: the man page claims `-t` has no effect without `-r`, but the test case shows it does.
- Refactoring detail: Patch 1/4 moves a precondition check (`revs->bloom_keyvecs_nr != 0`) into `check_maybe_different_in_bloom_filter`, eliminating duplicate checks at callsites and returning `-1` when no Bloom key vectors are present (unobservable to callers, as Bloom statistics are only reported when key vectors exist). Jeff King's review argues that the tristate return (`0`, `1`, `-1`) is subtle and error-prone for a public API, suggesting a boolean return (`false` = definitely unchanged, `true` = possibly changed) instead. Patch 2/4 extracts the core Bloom-filter-checking logic from `check_maybe_different_in_bloom_filter` into `revs_maybe_changed_in_bloom`, which takes an already-looked-up `struct bloom_filter` instead of a commit, avoiding redundant filter lookups for callers that have already fetched the filter. The original function becomes a thin wrapper around the new one. Junio's review and Taylor Blau's endorsement highlight that this refactoring unintentionally changes observable behavior in two ways: (1) `count_bloom_filter_not_present` is incremented even when `revs->bloom_keyvecs_nr` is zero, and (2) errors from `bloom_filter_contains_vec()` now skip counter updates that the original code performed. The first change is now agreed to be unintentional and should be reverted. Patch 4/4 addresses wildcard pathspecs by restoring `bloom_filter_settings` after `prepare_revision_walk()` clears it, but Jeff King's review argues this approach is fragile and suggests managing the settings pointer in the `last_modified` struct instead.
