Subject: [PATCH 0/4] last-modified: reuse Bloom filters for speed
Series version: v3 (complete; final patch adds trace2 instrumentation for wildcard pathspec verification)
Originating author: Toon Claes
Thread type: patch series (performance optimization)

Core problem or goal
Make the experimental `git last-modified` command as fast as `git log` when querying the last commit that modified files matching a pathspec (including wildcards like `*.c`), by reusing Git’s Bloom filter machinery more effectively. The v3 series achieves a 3.7× speedup without `--show-trees` (60.7 ms → 16.2 ms) and a 1.95× speedup with `--show-trees` (61.9 ms → 31.8 ms) on the ziglang/zig repository, bringing performance nearly to parity with `git log`. The series now fully supports wildcard pathspecs (e.g., `*.c`) without performance regressions, includes trace2 instrumentation to verify the Bloom filter fast-path is correctly triggered, and completes the optimization.

Current status
Under review; v3 posted and complete but blocked by a test environment interaction in `t8020-last-modified.sh`. The test exports `GIT_TEST_COMMIT_GRAPH=1` globally, overriding the `-c core.commitGraph=false` setting intended to establish a baseline, causing the test to fail under standard Git test environment variables. The failure is reproducible locally with `make T='t8020*' test` and the same CI settings. Junio C Hamano identified the issue and provided a one-line fix for each of the two `git` invocations in the test: explicitly unset `GIT_TEST_COMMIT_GRAPH` (to `0`) when testing the commit-graph-disabled baseline, and explicitly set it (to `1`) when testing the commit-graph-enabled case. The series is otherwise ready for integration; all previously identified technical feedback is resolved, including the `--show-trees` correctness fix, wildcard pathspec support, and trace2 instrumentation. The base commit remains 41365c2a9b ("The 4th batch for Git 2.56").

Key technical details
- Files touched: `revision.c`, `revision.h`, `bloom.c`, `bloom.h`, `builtin/last-modified.c`, test suite (`t/t8020-last-modified.sh`)
- New symbols: `revs_maybe_changed_in_bloom` (public, boolean return), `revs_maybe_changed_in_bloom_with_parents` (public, boolean return), `bloom_filter_contains_path` (private helper in `bloom.c`), `bloom_filter_contains_any_vec` (private helper in `bloom.c`)
- Behavior change: `git last-modified` reuses Bloom filters instead of re-fetching them, reducing runtime by up to 3.7×. The optimization now covers all pathspec types, including wildcards (e.g., `*.c`), with per-path Bloom-filter lookups. The `--show-trees` correctness bug is fixed by filtering out ancestor tree entries not covered by the original pathspec in `add_path_from_diff()` using `match_pathspec()`, preserving performance while avoiding misleading results. The fix handles the minor edge case of directory queries (e.g., `Documentation/technical/`) by retaining the queried directory while removing its parent (`Documentation/`), which is considered non-critical given the command's experimental status. The new `revs_maybe_changed_in_bloom_with_parents()` function enables `--show-trees` to report changes to parent directories by checking all keys in the path’s key vector (e.g., for `a/b/c/`, it checks `a/`, `a/b/`, and `a/b/c/`). Patch 3/6 adds `bloom_filter_contains_any_vec()` to answer whether *any* key in a vector is present in the Bloom filter (proving the path *or any of its parent directories* might have changed), which is exactly what `--show-trees` needs to avoid false negatives for directory queries. Patch 4/6 introduces `revs_maybe_changed_in_bloom_with_parents()`, a 15-line helper that loops over the key vectors and calls `bloom_filter_contains_any_vec()` to determine if any key in the vector is present, returning `true` if the Bloom filter indicates a possible change to the path or any of its parent directories. Patch 5/6 adds a 12-line pre-filter in `maybe_changed_path()` that calls the appropriate Bloom filter helper before starting the per-path diff machinery, discarding commits that definitely did not touch any relevant path early. Patch 6/6 restores `bloom_filter_settings` after `prepare_revision_walk()` clears it, ensuring Bloom filter lookups succeed for wildcard pathspecs (e.g., `*.c`), and adds a trace2 counter (`bloom_queries`) to instrument per-path Bloom filter invocations. The v3 reroll adds a 10-line test in `t/t8020-last-modified.sh` to verify that the per-path Bloom filter logic is invoked exactly twice for a top-level wildcard query (e.g., `*.c`), confirming the fix for the edge case where `prepare_revision_walk()` clears `bloom_filter_settings`. The test writes a commit-graph with `--changed-paths`, disables the commit-graph to establish a baseline, then re-enables it and checks that the Bloom filter fast-path is triggered (counter = 2) while preserving the correct output. The test now requires explicit control of `GIT_TEST_COMMIT_GRAPH` to avoid environment inheritance issues: unset it (to `0`) when testing the commit-graph-disabled baseline, and set it (to `1`) when testing the commit-graph-enabled case.
- On-disk format: unchanged
- Test coverage: benchmarks included in cover letter; new tests in `t/t8020-last-modified.sh` verify Bloom filter behavior with `--show-trees` and wildcard pathspecs, and trace2 instrumentation confirms the Bloom filter fast-path is correctly triggered. The test suite now exercises the Bloom filter code path by writing a commit-graph with `--changed-paths` and using quoted wildcards to trigger per-path Bloom filter logic.

Jeff King proposed an alternative design where `last-modified` manages its own settings pointer, but accepted the current approach as sufficient. The documentation inconsistency for `--show-trees` (man page vs. observed behavior) is noted but unresolved. The pre-existing discrepancy between `match_pathspec()` and `tree-walk.c:do_match()` is noted but not considered a blocker for this series. The naming of `revs_maybe_changed_in_bloom_with_parents()` (which refers to parent directories, not commit parents) may require clarification in documentation or comments, but this is a minor issue. The test environment interaction in `t8020-last-modified.sh` is now resolved by Junio’s suggested fix; the series is otherwise ready for integration.
