Subject: [PATCH 0/4] last-modified: reuse Bloom filters for speed
Series version: v1 (initial submission)
Originating author: Toon Claes
Thread type: patch series (performance optimization)

Core problem or goal
Make the experimental `git last-modified` command as fast as `git log` when querying the last commit that modified files matching a pathspec (including wildcards like `*.c`), by reusing Git’s Bloom filter machinery more effectively. The current implementation is ~3.7× slower (52 ms vs 14 ms) on the ziglang/zig repository.

Current status
Under review; v1 posted. No prior versions.

Key technical details
- Files touched: `revision.c`, `revision.h`, `builtin/last-modified.c`
- New symbols: `repo_may_have_commit_with_changes` (exposed in `revision.h`), `revs_maybe_changed_in_bloom` (new public function in `revision.h`)
- Behavior change: `git last-modified` reuses Bloom filters instead of re-fetching them, reducing runtime from 52 ms to 14 ms on the ziglang/zig repository (matching `git log` speed). The optimization now also covers wildcard pathspecs (e.g., `*.c`), which the Bloom-filter machinery cannot directly convert into a single key.
- On-disk format: unchanged
- Test coverage: benchmarks included in cover letter; no new test files added
- Refactoring detail: Patch 1/4 moves a precondition check (`revs->bloom_keyvecs_nr != 0`) into `check_maybe_different_in_bloom_filter`, eliminating duplicate checks at callsites and returning `-1` when no Bloom key vectors are present (unobservable to callers, as Bloom statistics are only reported when key vectors exist). Patch 2/4 extracts the core Bloom-filter-checking logic from `check_maybe_different_in_bloom_filter` into `revs_maybe_changed_in_bloom`, which takes an already-looked-up `struct bloom_filter` instead of a commit, avoiding redundant filter lookups for callers that have already fetched the filter. The original function becomes a thin wrapper around the new one. Patch 3/4 wires the Bloom-filter helper (`revs_maybe_changed_in_bloom`) into the command’s main revision walk in `builtin/last-modified.c` with a three-line change, eliminating the need to diff trees for commits whose Bloom filters definitively say “no changes” to the entire pathspec. Patch 4/4 restores the `bloom_filter_settings` field after `prepare_revision_walk()` clears it, ensuring per-path Bloom-filter lookups continue working for wildcard pathspecs.
