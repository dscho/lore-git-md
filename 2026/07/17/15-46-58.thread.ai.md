Thread identity
Subject: [PATCH 0/4] last-modified: reuse Bloom filters for speed
Series version: v2 (reroll addressing all v1 feedback)
Originating author: Toon Claes
Thread type: patch series (performance optimization)

Core problem or goal
Make the experimental `git last-modified` command as fast as `git log` when querying the last commit that modified files matching a pathspec (including wildcards like `*.c`), by reusing Git’s Bloom filter machinery more effectively. The v2 reroll achieves a 3.7× speedup without `--show-trees` (60.7 ms → 16.2 ms) and a 1.95× speedup with `--show-trees` (61.9 ms → 31.8 ms) on the ziglang/zig repository, bringing performance nearly to parity with `git log`.

Current status
Under review; v2 posted. All previously identified technical blockers resolved: (1) public API (`repo_may_have_commit_with_changes`) refactored to return boolean (`false` = definitely unchanged, `true` = possibly changed) for clarity, while retaining tristate logic in a private wrapper; (2) unintended behavioral changes in Bloom filter statistics reporting reverted (restoring the original guard `revs->bloom_keyvecs_nr != 0` before generation and filter lookups, and preserving counter updates on `bloom_filter_contains_vec()` errors); (3) `--show-trees` correctness bug fixed by filtering ancestor tree entries not covered by the original pathspec in `add_path_from_diff()` using `match_pathspec()`; (4) missing `Helped-by`/`Based-on-patches-by` trailers for Jeff King added. Junio C Hamano's follow-up email in v1 reaffirmed that the `--show-trees` correctness fix was the sole remaining technical blocker; this is now implemented. The series now consists of six patches, adding two new commits: one introducing helpers for `--show-trees` filtering, and one adding a test to verify Bloom filter behavior with `--show-trees`. The first patch in v2 refactors the internal Bloom filter helper `check_maybe_different_in_bloom_filter()` to centralize the precondition check (`revs->bloom_keyvecs_nr != 0`), simplifying callsites in `rev_compare_tree()` and `rev_same_tree_as_empty()`. The second patch extracts the core filter-consulting logic into a new public function `revs_maybe_changed_in_bloom()` that takes an already-looked-up `struct bloom_filter` and returns a boolean, while the original function remains as a thin wrapper for internal statistics tracking. The third patch introduces `bloom_filter_contains_any_vec()`, a helper that answers “did this commit possibly change the queried path or any of its parent directories?” by returning true if any key in the supplied vector is present in the Bloom filter, supporting wildcard pathspec queries in `git last-modified`. The fourth patch adds `revs_maybe_changed_in_bloom_with_parents()`, which extends the Bloom filter check to include parent directories of the queried paths, enabling `--show-trees` to report changes to ancestor directories (e.g., a pathspec like `a/b/c/` will now consider changes to `a/` or `a/b/`). No further rerolls are expected unless new substantive feedback emerges.

Key technical details
- Files touched: `revision.c`, `revision.h`, `bloom.c`, `bloom.h`, `builtin/last-modified.c`, test suite (`t/t8020-last-modified.sh`)
- New symbols: `revs_maybe_changed_in_bloom` (public, boolean return), `revs_maybe_changed_in_bloom_with_parents` (public, boolean return), `bloom_filter_contains_path` (private helper in `bloom.c`), `bloom_filter_contains_any_vec` (private helper in `bloom.c`)
- Behavior change: `git last-modified` reuses Bloom filters instead of re-fetching them, reducing runtime by up to 3.7×. The optimization now covers all pathspec types, including wildcards (e.g., `*.c`), with per-path Bloom-filter lookups. The `--show-trees` correctness bug is fixed by filtering out ancestor tree entries not covered by the original pathspec in `add_path_from_diff()` using `match_pathspec()`, preserving performance while avoiding misleading results. The fix handles the minor edge case of directory queries (e.g., `Documentation/technical/`) by retaining the queried directory while removing its parent (`Documentation/`), which is considered non-critical given the command's experimental status. The new `revs_maybe_changed_in_bloom_with_parents()` function enables `--show-trees` to report changes to parent directories by checking all keys in the path’s key vector (e.g., for `a/b/c/`, it checks `a/`, `a/b/`, and `a/b/c/`).
- On-disk format: unchanged
- Test coverage: benchmarks included in cover letter; new test in `t8020-last-modified.sh` verifies Bloom filter behavior with `--show-trees`. The test suite now exercises the Bloom filter code path by writing a commit-graph with `--changed-paths` and using quoted wildcards to trigger per-path Bloom filter logic. Patch 1/6 centralizes the precondition check (`revs->bloom_keyvecs_nr != 0`) in the internal helper `check_maybe_different_in_bloom_filter()`, simplifying callsites in `rev_compare_tree()` and `rev_same_tree_as_empty()` without altering behavior. Patch 2/6 refactors the public API to expose `revs_maybe_changed_in_bloom()`, which takes an already-looked-up `struct bloom_filter` and returns a boolean, eliminating redundant filter lookups for callers like `git last-modified` that already have the filter in hand. Patch 3/6 introduces `bloom_filter_contains_any_vec()` to support wildcard pathspec queries by checking if any key in the supplied vector is present in the Bloom filter. Patch 4/6 adds `revs_maybe_changed_in_bloom_with_parents()` to extend the Bloom filter check to parent directories. Patch 5/6 implements the `--show-trees` correctness fix. Patch 6/6 is a minor cleanup to the loop in `revs_maybe_changed_in_bloom()` as suggested by Junio.

Open questions and loose ends
The maintainability concern about patch 4/6's approach of restoring `bloom_filter_settings` after `prepare_revision_walk()` clears it remains acknowledged but non-blocking. Jeff King proposed an alternative design where `last-modified` manages its own settings pointer, but accepted the current approach as sufficient. The documentation inconsistency for `--show-trees` (man page vs. observed behavior) is noted but unresolved. The pre-existing discrepancy between `match_pathspec()` and `tree-walk.c:do_match()` is noted but not considered a blocker for this series. The naming of `revs_maybe_changed_in_bloom_with_parents()` (which refers to parent directories, not commit parents) may require clarification in documentation or comments, but this is a minor issue.
