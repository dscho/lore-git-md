Subject: [PATCH 0/4] last-modified: reuse Bloom filters for speed
Series version: v3 (reroll adding trace2 instrumentation for wildcard pathspec verification)
Originating author: Toon Claes
Thread type: patch series (performance optimization)

Core problem or goal
Make the experimental `git last-modified` command as fast as `git log` when querying the last commit that modified files matching a pathspec (including wildcards like `*.c`), by reusing Git’s Bloom filter machinery more effectively. The v3 reroll achieves a 3.7× speedup without `--show-trees` (60.7 ms → 16.2 ms) and a 1.95× speedup with `--show-trees` (61.9 ms → 31.8 ms) on the ziglang/zig repository, bringing performance nearly to parity with `git log`. The series now fully supports wildcard pathspecs (e.g., `*.c`) without performance regressions, includes trace2 instrumentation to verify the Bloom filter fast-path is correctly triggered, and completes the optimization.

Current status
Under review; v3 posted and complete. All previously identified technical feedback resolved: (1) public API (`repo_may_have_commit_with_changes`) refactored to return boolean (`false` = definitely unchanged, `true` = possibly changed) for clarity, while retaining tristate logic in a private wrapper; (2) unintended behavioral changes in Bloom filter statistics reporting reverted (restoring the original guard `revs->bloom_keyvecs_nr != 0` before generation and filter lookups, and preserving counter updates on `bloom_filter_contains_vec()` errors); (3) `--show-trees` correctness bug fixed by filtering ancestor tree entries not covered by the original pathspec in `add_path_from_diff()` using `match_pathspec()`; (4) missing `Helped-by`/`Based-on-patches-by` trailers for Jeff King added; (5) wildcard pathspec support ensured by restoring `bloom_filter_settings` after `prepare_revision_walk()` clears it, preventing Bloom filter lookup failures for wildcards (e.g., `*.c`); (6) trace2 instrumentation added to verify the Bloom filter fast-path is correctly triggered for top-level wildcard pathspecs (e.g., `*.c`), addressing the test gap identified in v2. Junio C Hamano's follow-up email in v1 reaffirmed that the `--show-trees` correctness fix was the sole remaining technical blocker; this is now implemented. The series consists of six patches, with the final patch in v2 addressing the wildcard pathspec edge case and the new instrumentation in v3 closing the test coverage gap. The series is now ready for integration.

Key technical details
- Files touched: `revision.c`, `revision.h`, `bloom.c`, `bloom.h`, `builtin/last-modified.c`, test suite (`t/t8020-last-modified.sh`)
- New symbols: `revs_maybe_changed_in_bloom` (public, boolean return), `revs_maybe_changed_in_bloom_with_parents` (public, boolean return), `bloom_filter_contains_path` (private helper in `bloom.c`), `bloom_filter_contains_any_vec` (private helper in `bloom.c`)
- Behavior change: `git last-modified` reuses Bloom filters instead of re-fetching them, reducing runtime by up to 3.7×. The optimization now covers all pathspec types, including wildcards (e.g., `*.c`), with per-path Bloom-filter lookups. The `--show-trees` correctness bug is fixed by filtering out ancestor tree entries not covered by the original pathspec in `add_path_from_diff()` using `match_pathspec()`, preserving performance while avoiding misleading results. The fix handles the minor edge case of directory queries (e.g., `Documentation/technical/`) by retaining the queried directory while removing its parent (`Documentation/`), which is considered non-critical given the command's experimental status. The new `revs_maybe_changed_in_bloom_with_parents()` function enables `--show-trees` to report changes to parent directories by checking all keys in the path’s key vector (e.g., for `a/b/c/`, it checks `a/`, `a/b/`, and `a/b/c/`). Patch 5/6 adds a 12-line pre-filter in `maybe_changed_path()` that calls the appropriate Bloom filter helper before starting the per-path diff machinery, discarding commits that definitely did not touch any relevant path early. Patch 6/6 restores `bloom_filter_settings` after `prepare_revision_walk()` clears it, ensuring Bloom filter lookups succeed for wildcard pathspecs (e.g., `*.c`). The v3 reroll adds trace2 instrumentation (a new counter `bloom_queries`) and a 10-line test in `t8020-last-modified.sh` to verify that the per-path Bloom filter logic is invoked exactly twice for a top-level wildcard query (e.g., `*.c`), confirming the fix for the edge case where `prepare_revision_walk()` clears `bloom_filter_settings`.
- On-disk format: unchanged
- Test coverage: benchmarks included in cover letter; new test in `t8020-last-modified.sh` verifies Bloom filter behavior with `--show-trees` and wildcard pathspecs, and trace2 instrumentation confirms the Bloom filter fast-path is correctly triggered. The test suite now exercises the Bloom filter code path by writing a commit-graph with `--changed-paths` and using quoted wildcards to trigger per-path Bloom filter logic. Patch 1/6 centralizes the precondition check (`revs->bloom_keyvecs_nr != 0`) in the internal helper `check_maybe_different_in_bloom_filter()`, simplifying callsites in `rev_compare_tree()` and `rev_same_tree_as_empty()` without altering behavior. Patch 2/6 refactors the public API to expose `revs_maybe_changed_in_bloom()`, which takes an already-looked-up `struct bloom_filter` and returns a boolean, eliminating redundant filter lookups for callers like `git last-modified` that already have the filter in hand. Patch 3/6 introduces `bloom_filter_contains_any_vec()` to support wildcard pathspec queries by checking if any key in the supplied vector is present in the Bloom filter. Patch 4/6 adds `revs_maybe_changed_in_bloom_with_parents()` to extend the Bloom filter check to parent directories. Patch 5/6 implements the Bloom filter pre-filter in `maybe_changed_path()`.
