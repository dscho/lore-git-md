Subject: [PATCH 0/4] last-modified: reuse Bloom filters for speed
Series version: v4 (complete; final patch adds pre-filter and trace2 instrumentation for wildcard pathspec verification)
Originating author: Toon Claes
Thread type: patch series (performance optimization)

Core problem or goal
Make the experimental `git last-modified` command as fast as `git log` when querying the last commit that modified files matching a pathspec (including wildcards like `*.c`), by reusing Git’s Bloom filter machinery more effectively. The v4 series achieves a 3.7× speedup without `--show-trees` (60.7 ms → 16.2 ms) and a 1.95× speedup with `--show-trees` (61.9 ms → 31.8 ms) on the ziglang/zig repository, bringing performance nearly to parity with `git log`. The series now fully supports wildcard pathspecs (e.g., `*.c`) without performance regressions, includes trace2 instrumentation to verify the Bloom filter fast-path is correctly triggered, and resolves the test environment interaction that blocked v3.

Current status
Under review; v4 posted and complete. The series is ready for integration. All previously identified technical feedback is resolved, including the `--show-trees` correctness fix, wildcard pathspec support, trace2 instrumentation, the test environment interaction in `t8020-last-modified.sh`, and the pre-filter optimization in patch 5/4. The base commit remains 41365c2a9b ("The 4th batch for Git 2.56"). Junio C Hamano’s suggested fix for the test environment issue is incorporated: the test now explicitly unsets `GIT_TEST_COMMIT_GRAPH` (to `0`) when testing the commit-graph-disabled baseline and explicitly sets it (to `1`) when testing the commit-graph-enabled case, ensuring the test behaves as intended regardless of the broader test environment. Patch 2/4 in v4 refactors the Bloom filter precondition check in `revision.c` to expose a new public helper, `revs_maybe_changed_in_bloom()`, via `revision.h`. The new function returns a boolean (`false` if the commit definitely did not change any paths, `true` otherwise) and cleanly separates the concerns of filtering and statistics tracking, enabling the performance optimizations in later patches.

Key technical details
- Files touched: `revision.c`, `revision.h`, `bloom.c`, `bloom.h`, `builtin/last-modified.c`, test suite (`t/t8020-last-modified.sh`)
- New symbols: `revs_maybe_changed_in_bloom` (public, boolean return), `revs_maybe_changed_in_bloom_with_parents` (public, boolean return), `bloom_filter_contains_path` (private helper in `bloom.c`), `bloom_filter_contains_any_vec` (private helper in `bloom.c`)
- Behavior change: `git last-modified` reuses Bloom filters instead of re-fetching them, reducing runtime by up to 3.7×. The optimization now covers all pathspec types, including wildcards (e.g., `*.c`), with per-path Bloom-filter lookups. The `--show-trees` correctness bug is fixed by filtering out ancestor tree entries not covered by the original pathspec in `add_path_from_diff()` using `match_pathspec()`, preserving performance while avoiding misleading results. The fix handles the minor edge case of directory queries (e.g., `Documentation/technical/`) by retaining the queried directory while removing its parent (`Documentation/`), which is considered non-critical given the command's experimental status. The new `revs_maybe_changed_in_bloom_with_parents()` function enables `--show-trees` to report changes to parent directories by checking all keys in the path’s key vector (e.g., for `a/b/c/`, it checks `a/`, `a/b/`, and `a/b/c/`). Patch 3/4 adds `bloom_filter_contains_any_vec()` to answer whether *any* key in a vector is present in the Bloom filter (proving the path *or any of its parent directories* might have changed), which is exactly what `--show-trees` needs to avoid false negatives for directory queries. The helper is a 12-line loop over the key vector that returns `1` as soon as any key is found in the filter, and `0` only if none are present. Patch 4/4 introduces `revs_maybe_changed_in_bloom_with_parents()`, a 15-line helper that loops over the key vectors and calls `bloom_filter_contains_any_vec()` to determine if any key in the vector is present, returning `true` if the Bloom filter indicates a possible change to the path or any of its parent directories. Patch 5/4 adds a 12-line pre-filter in `maybe_changed_path()` that calls the appropriate Bloom filter helper before starting the per-path diff machinery, discarding commits that definitely did not touch any relevant path early. The pre-filter uses `revs_maybe_changed_in_bloom()` for the default case and `revs_maybe_changed_in_bloom_with_parents()` for `--show-trees`, ensuring correctness for directory queries. Patch 6/4 restores `bloom_filter_settings` after `prepare_revision_walk()` clears it, ensuring Bloom filter lookups succeed for wildcard pathspecs (e.g., `*.c`), and adds a trace2 counter (`bloom_queries`) to instrument per-path Bloom filter invocations. The v4 reroll incorporates Junio’s fix for the test environment interaction in `t8020-last-modified.sh`: the test now explicitly controls `GIT_TEST_COMMIT_GRAPH` for both the commit-graph-disabled baseline (`GIT_TEST_COMMIT_GRAPH=0`) and the commit-graph-enabled case (`GIT_TEST_COMMIT_GRAPH=1`). Patch 1/4 in v4 refactors `revision.c` to move the `revs->bloom_keyvecs_nr` check into `check_maybe_different_in_bloom_filter`, making `bloom_ret` return `-1` when no Bloom key vectors are present, which prevents `count_bloom_filter_false_positive` from being incremented in that case. Patch 2/4 exposes `revs_maybe_changed_in_bloom()` as a public helper, preserving the original function’s tristate return for statistics while providing a boolean API for filtering.
- On-disk format: unchanged
- Test coverage: benchmarks included in cover letter; new tests in `t/t8020-last-modified.sh` verify Bloom filter behavior with `--show-trees` and wildcard pathspecs, and trace2 instrumentation confirms the Bloom filter fast-path is correctly triggered. The test suite now exercises the Bloom filter code path by writing a commit-graph with `--changed-paths` and using quoted wildcards to trigger per-path Bloom filter logic. The test also verifies that the pre-filter in `maybe_changed_path()` correctly discards commits that do not match the pathspec, including edge cases for `--show-trees` (e.g., sibling files in the same directory).

Open questions and loose ends
The maintainability concern about patch 6/4's approach of restoring `bloom_filter_settings` after `prepare_revision_walk()` clears it remains acknowledged but non-blocking. Jeff King proposed an alternative design where `last-modified` manages its own settings pointer, but accepted the current approach as sufficient. The documentation inconsistency for `--show-trees` (man page vs. observed behavior) is noted but unresolved. The pre-existing discrepancy between `match_pathspec()` and `tree-walk.c:do_match()` is noted but not considered a blocker for this series. The naming of `revs_maybe_changed_in_bloom_with_parents()` (which refers to parent directories, not commit parents) may require clarification in documentation or comments, but this is a minor issue.
