This is the second patch in Toon Claes's four-patch series optimizing the experimental `git last-modified` command by reusing Git's Bloom filter machinery. The patch extracts the core Bloom-filter-checking logic from `check_maybe_different_in_bloom_filter` into a new public function, `revs_maybe_changed_in_bloom`, exposed in `revision.h`. The new function takes an already-looked-up `struct bloom_filter` instead of a commit, avoiding redundant filter lookups for callers that have already fetched the filter. The original function becomes a thin wrapper around the new one.

The change is a straightforward refactoring that prepares for patch 3, where `git last-modified` will reuse this logic to avoid fetching the same Bloom filter twice. The commit message clearly explains the motivation and the interface contract, including the return value semantics (-1 for missing preconditions, 0 for no changes, 1 for possible changes). The patch touches only `revision.c` and `revision.h`, and the code is clean and well-structured. This looks like a sensible, low-risk step toward the series' performance goal.
