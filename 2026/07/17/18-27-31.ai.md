This is a **feature** patch series (v2) implementing the `--auto-reset[=<where>]` option for `git bisect`. The series is now complete and ready for review, following the design agreement reached in the v1 discussion.

The new option allows users to automatically reset the bisect session after the first bad commit is found, with two possible behaviors: `original` (return to the pre-bisect commit, the default) or `found` (leave the working tree on the first bad commit). This addresses both automated workflows (scripts, CI pipelines) and interactive debugging by eliminating the need for an explicit `git bisect reset`. The implementation touches `bisect.c`, `builtin/bisect.c`, `Documentation/git-bisect.adoc`, and adds comprehensive test coverage in `t/t6030-bisect-porcelain.sh`.

Key changes in v2 include the parameterized option (`--auto-reset=<where>`), replacing the original boolean flag, and the addition of the `found` target to support leaving the first bad commit checked out. The state file `BISECT_AUTO_RESET` now stores the target commit (`original` or `found`) instead of a boolean, and the reset behavior is wired into both `git bisect start` and `git bisect run`. The series also enforces a constraint that `--auto-reset` cannot be used with `--no-checkout`, as that mode prevents checking out either target.

The preparatory patches (1 and 2) remain unchanged: patch 1 refactors `print_file_to_stdout()` to `print_fd_to_stdout()` to avoid reopening files, and patch 2 adds a `quiet` parameter to `bisect_reset()` to suppress checkout output during auto-reset. The test suite now includes four new tests validating both `original` and `found` behaviors, state cleanup, and edge cases like invalid targets and `--no-checkout` conflicts.

The series is well-structured and addresses the feedback from v1, particularly Junio’s suggestion to parameterize the option. The implementation is clean, with no on-disk format changes or new symbols introduced beyond the state file updates. The only practical limitation noted is that users cannot conditionally choose the reset target based on the bisect outcome, as the target must be specified upfront. This is a reasonable trade-off for the simplicity of the feature. The series looks ready for review, with no obvious gaps in functionality or test coverage.
