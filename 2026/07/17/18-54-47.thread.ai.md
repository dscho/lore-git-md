Subject: `git history fixup` corrupts index in other worktrees
Series version: N/A (bug report, not a patch series)
Originating author: Toon Claes
Thread type: bug report

Core problem or goal
The `git history fixup` command (introduced in Git 2.46, 2026) does not properly isolate index modifications to the current worktree. When run in one worktree, it leaves spurious staged changes in other worktrees that share the same repository, corrupting their index state without any user action in those worktrees. The root cause is that `git history fixup` rewrites commits pointed to by branches checked out in other worktrees without updating their index or working copy, leaving them in a dirty state.

Current status
Design decision settled: `git history fixup` will refuse to rewrite branches checked out in other worktrees, mirroring `git rebase --update-refs` behavior (option 1 from prior discussion). This conservative approach avoids the complexity and edge cases of "best-effort" index updates in other worktrees. No patch posted yet; implementation work remains to add the safety check (reusing logic from `git rebase`) and regression tests for both the `git history` and worktree test suites. The issue is tracked in GitLab issue #772 for the next release cycle but is open to community contribution. Root cause analysis and minimal reproduction case remain unchanged.

Key technical details
- Command: `git history fixup`
- Subsystems: worktree handling, index management, commit rewriting
- Files likely involved: `builtin/history.c`, `worktree.c`, `read-cache.c`
- Behavior: staged changes leak across worktrees after `fixup`; commit history remains correct; concurrent rewrites of the same branch are not prevented
- On-disk format: no changes
- Safety mechanism: will adopt `git rebase`'s protection against rewriting branches checked out in other worktrees
- Test coverage: none yet; reproduction case provided in report; regression tests planned for both `git history` and worktree test suites

Open questions and loose ends
- Implementation: exact reuse of `git rebase` safety-check logic vs. adaptation for `git history` context
- Test requirements: whether to test concurrent rewrite scenarios (beyond basic regression)
- Backward compatibility: whether the new safety check will require changes to user workflows (e.g., forcing users to check out branches in the current worktree before rewriting)
