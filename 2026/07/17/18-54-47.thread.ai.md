Subject: `git history fixup` corrupts index in other worktrees
Series version: N/A (bug report, not a patch series)
Originating author: Toon Claes
Thread type: bug report

Core problem or goal
The `git history fixup` command (introduced in Git 2.46, 2026) does not properly isolate index modifications to the current worktree. When run in one worktree, it leaves spurious staged changes in other worktrees that share the same repository, corrupting their index state without any user action in those worktrees. The root cause is now identified: `git history fixup` rewrites commits pointed to by branches checked out in other worktrees without updating their index or working copy, leaving them in a dirty state.

Current status
Reported and confirmed; root cause analysis provided by Phillip Wood. No patch posted yet. The issue is reproducible with the minimal test case from Toon Claes. Two distinct problems are now recognized: (1) immediate index corruption in other worktrees, and (2) lack of safety mechanisms to prevent concurrent rewrites of the same branch.

Key technical details
- Command: `git history fixup`
- Subsystems: worktree handling, index management, commit rewriting
- Files likely involved: `builtin/history.c`, `worktree.c`, `read-cache.c`
- Behavior: staged changes leak across worktrees after `fixup`; commit history remains correct; concurrent rewrites of the same branch are not prevented
- On-disk format: no changes
- Proposed solution: adopt `git rebase --update-refs` behavior (refuse to rewrite branches checked out in other worktrees, or update their index and working copy if clean)
- Test coverage: none yet; reproduction case provided in report

Open questions and loose ends
- Fix scope: whether to refuse rewriting branches checked out in other worktrees (safer) or attempt to update their index/working copy (more complex, requires cleanliness check)
- Safety mechanism: how to implement protection against concurrent rewrites of the same branch (analogous to `git rebase`'s safety check)
- Test requirements: whether to add regression tests to the `git history` test suite, the worktree test suite, or both; whether to test concurrent rewrite scenarios
- Backward compatibility: whether the fix will require changes to user workflows (e.g., forcing users to check out branches in the current worktree before rewriting)
