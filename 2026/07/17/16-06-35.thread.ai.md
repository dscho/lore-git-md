Core problem or goal
Fix two edge-case bugs in the interactive rebase (`rebase -i`) subsystem:
1. The commit count in the template message for squash/fixup is incorrect when a preceding fixup/squash command is skipped.
2. The editor is not opened after a `fixup -c` command if a preceding fixup/squash command was skipped, breaking the expected workflow.

Current status
Under review. Two-patch series posted as v1; no prior versions. No maintainer decision or merge status recorded.

Key technical details
Files touched: `sequencer.c` (core rebase logic)
New/renamed symbols: helper function `seen_fixup_edit_msg()` added to check for `fixup -c` commands in the current chain
Behavior changes: corrects commit count in template message by fixing newline-handling in the sequencer’s internal command list file; ensures editor is launched after `fixup -c` following a skip by tracking the presence of any `fixup -c` command in the chain, not just squash commands. The command list file uses a newline-before-each-command convention (except the first), and skipping a command previously left an orphaned newline, causing the count to be off by one. The fix removes the newline when popping a skipped command and makes the reading logic skip blank lines for version compatibility.
On-disk format: unchanged
Test coverage: adds 36 lines to `t/t3418-rebase-continue.sh` (covering skipped fixup/squash commands and commit count accuracy) and 47 lines to `t/t3437-rebase-fixup-options.sh` (covering the `fixup -c` edge case, including scenarios where the final or a later fixup command in the chain is skipped)
