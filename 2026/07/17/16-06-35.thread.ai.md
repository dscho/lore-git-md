Subject: [PATCH 0/2] rebase -i: fix edge cases with skipped fixup/squash commands

Originating author: Phillip Wood
Thread type: patch series (bugfix)

Core problem or goal
Fix two edge-case bugs in the interactive rebase (`rebase -i`) subsystem:
1. The commit count in the template message for squash/fixup is incorrect when a preceding fixup/squash command is skipped.
2. The editor is not opened after a `fixup -c` command if a preceding fixup/squash command was skipped, breaking the expected workflow.

Current status
Under review. Two-patch series posted as v1; no prior versions. Junio C Hamano provided substantive reviews of both patches. The first patch received feedback on robustness against older Git versions (trailing newlines in legacy command-list files), and the second patch received minor nits about string-matching consistency. No maintainer decision or merge status recorded; no response from Phillip Wood yet. The series is likely to proceed to `next` once the feedback is addressed.

Key technical details
Files touched: `sequencer.c` (core rebase logic)
New/renamed symbols: helper function `seen_fixup_edit_msg()` added to check for `fixup -c` commands in the current chain; mirrors existing `seen_squash()` helper
Behavior changes:
- Corrects commit count in template message by fixing newline-handling in the sequencer’s internal command list file. The command list file uses a newline-before-each-command convention (except the first), and skipping a command previously left an orphaned newline, causing the count to be off by one. The fix removes the newline when popping a skipped command and makes the reading logic skip blank lines for version compatibility. Junio’s review highlights that the reading logic must also guard against trailing newlines (e.g., `p[1] != '\0'`) to avoid miscounting in legacy files.
- Ensures editor is launched after `fixup -c` following a skip by tracking the presence of any `fixup -c` command in the chain, not just squash commands. The patch replaces open-coded squash checks in `commit_staged_changes()` with the new helper for consistency.
String matching: Junio’s review notes that the helpers (`seen_squash()`, `seen_fixup_edit_msg()`) do not require a space after the verb (`squash` or `fixup -c`), which could theoretically match malformed commands. This is not a blocker but may be tightened in a follow-up.
On-disk format: unchanged
Test coverage: adds 36 lines to `t/t3418-rebase-continue.sh` (covering skipped fixup/squash commands and commit count accuracy) and 47 lines to `t/t3437-rebase-fixup-options.sh` (covering the `fixup -c` edge case, including scenarios where the final or a later fixup command in the chain is skipped)

Open questions and loose ends
- First patch: Junio’s review raises a specific robustness concern: the reading logic must handle trailing newlines in legacy command-list files to avoid an off-by-one error. This requires a follow-up from Phillip Wood to adjust the condition from `p[1] != '\n'` to `p[1] != '\n' && p[1] != '\0'`.
- Second patch: Junio suggests tightening the string matching in the helpers to require a space after the verb (`squash ` or `fixup -c `) to avoid matching malformed commands. This is a minor nit and not a blocker.
