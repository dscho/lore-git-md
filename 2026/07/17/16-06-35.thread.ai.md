Subject: [PATCH 0/2] rebase -i: fix edge cases with skipped fixup/squash commands
Series version: v2 (v1 previously posted)
Originating author: Phillip Wood
Thread type: patch series (bugfix)

Core problem or goal
Fix two edge-case bugs in the interactive rebase (`rebase -i`) subsystem:
1. The commit count in the template message for squash/fixup is incorrect when a preceding fixup/squash command is skipped.
2. The editor is not opened after a `fixup -c` command if a preceding fixup/squash command was skipped, breaking the expected workflow.

Current status
Under review. Two-patch series posted as v2; v1 received substantive review from Junio C Hamano. The v2 addresses Junio’s robustness concern in the first patch (trailing NUL bytes in legacy command-list files) by tightening the condition from `p[1] != '\n'` to `p[1] && p[1] != '\n'`. The second patch, which ensures the editor is launched after `fixup -c` following a skip, remains unchanged from v1. Junio’s feedback on string-matching consistency (requiring a space after `squash`/`fixup -c` in the helpers) was acknowledged by Phillip but deemed unnecessary because the command-list file is internally generated and only contains lines starting with those verbs. Junio has indicated he plans to mark the series for `next` after a few more days; no maintainer decision or merge status recorded yet.

Key technical details
Files touched: `sequencer.c` (core rebase logic)
New/renamed symbols: helper function `seen_fixup_edit_msg()` added to check for `fixup -c` commands in the current chain; mirrors existing `seen_squash()` helper
Behavior changes:
- Corrects commit count in template message by fixing newline-handling in the sequencer’s internal command list file. The command list file uses a newline-before-each-command convention (except the first), and skipping a command previously left an orphaned newline, causing the count to be off by one. The fix removes the newline when popping a skipped command and makes the reading logic skip blank lines for version compatibility. The v2 tightens the reading logic to guard against trailing NUL bytes (e.g., `p[1] && p[1] != '\n'`).
- Ensures editor is launched after `fixup -c` following a skip by tracking the presence of any `fixup -c` command in the chain, not just squash commands. The patch replaces open-coded squash checks in `commit_staged_changes()` with the new helper for consistency.
String matching: Junio’s review suggested tightening the helpers (`seen_squash()`, `seen_fixup_edit_msg()`) to require a space after the verb (`squash` or `fixup -c`) to avoid matching malformed commands. Phillip argued this is unnecessary because the file being read is internally generated and only contains lines starting with those verbs. This nit remains open but is not a blocker.
On-disk format: unchanged
Test coverage: adds 36 lines to `t/t3418-rebase-continue.sh` (covering skipped fixup/squash commands and commit count accuracy) and 47 lines to `t/t3437-rebase-fixup-options.sh` (covering the `fixup -c` edge case, including scenarios where the final or a later fixup command in the chain is skipped). The test additions verify the commit message reflects expected content after editing.

Open questions and loose ends
- Junio’s string-matching nit remains open but is not a blocker. The helpers will not be tightened to require a space after `squash`/`fixup -c` in this series.
- The series awaits Junio’s confirmation of the robustness fix in v2; he has indicated he plans to mark it for `next` after a few more days.
