This is Junio C Hamano’s review of the v6 patch that converts `git show-branch` to use a commit-slab for per-commit state. The patch itself is a well-executed refactoring that lifts the 27-branch limit to 64 and is technically ready for merging, but Junio identifies two remaining issues that prevent immediate sign-off.

First, he points out a **performance regression** in the `join_revs()` traversal logic. The original code avoided parsing and re-queueing a parent commit if it already had all the flags being propagated. The slab-based version, however, only skips the parent if it has *all* possible flags (up to `num_rev`), missing the opportunity to prune early when the parent already has a *subset* of the current commit’s flags. This could lead to redundant work and queue thrashing in densely merged histories. Junio suggests introducing a helper function (`has_subset_rev_flags`) to restore the original pruning behavior.

Second, he questions the **continued use of a hardcoded `MAX_REVS` limit** (now 64). The patch already includes infrastructure for dynamic stride via `init_commit_rev_flags_with_stride`, and Junio argues that the remaining obstacles — the static `ref_name[]` array and stack-allocated `rev[]`/`reflog_msg[]` arrays in `cmd_show_branch()` — could be overcome with modest additional work. By dynamically growing these arrays and calculating `flags_stride` at runtime, the patch could eliminate `MAX_REVS` entirely, allowing `git show-branch` to handle an arbitrary number of branches. Junio frames this as a missed opportunity, given that the patch already does 90% of the work needed for dynamic stride.

The review is substantive and constructive, focusing on correctness, performance, and long-term maintainability. No further feedback has been posted since this reply, so the ball is now in the author’s court to address these points in a v7. The patch remains part of the ongoing effort to eliminate misuse of `object.flags` in Git’s codebase.
