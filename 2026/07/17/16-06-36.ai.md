This is the first patch in Phillip Wood’s two-patch bugfix series for interactive rebase (`rebase -i`). It fixes an incorrect commit count in the template message that appears when a "fixup" or "squash" command is skipped during a rebase.

The bug occurs because the sequencer’s internal list of executed fixup/squash commands is stored in a file with a slightly unusual newline-handling convention: newlines are inserted *before* each new command (except the first). When a command is skipped, the code removes the command but leaves the preceding newline, which later causes the count to be off by one. The patch corrects this by removing the newline when popping a skipped command and also makes the reading logic skip blank lines, ensuring compatibility between different Git versions.

The patch touches `sequencer.c` (the core rebase logic) and extends an existing test in `t/t3418-rebase-continue.sh` with 36 new lines. The test now covers a scenario where two fixup/squash commands are skipped before the final command, verifying that the commit count in the template message is accurate. The consequence of the bug is minor—just a misleading count in the template—but the fix is thorough and includes both the writing and reading sides of the problem.

Phillip is a well-known contributor with deep expertise in the rebase and sequencer code, so the patch is likely to be technically sound. The issue is niche (requires skipping two fixup/squash commands in a row), but the fix is self-contained and well-tested. This patch sets the stage for the second patch in the series, which addresses a related edge case involving `fixup -c` and skipped commands.
