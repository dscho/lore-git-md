This is Junio C Hamano's review of Gatla Vishweshwar Reddy's `[PATCH v6]` refactoring of `git show-branch` to use a commit-slab for per-commit state. The patch is now under deeper scrutiny for performance and design completeness.

Junio acknowledges the correctness fixes in v6 (restored `UNINTERESTING` propagation and redundant traversal avoidance in `join_revs()`) but raises two new concerns. First, a potential performance regression: the current slab-based logic in `join_revs()` skips parents only if they already have *all* possible revision flags (`num_rev`), whereas the original code skipped if the parent had *at least* the flags of the current commit. This could cause redundant queueing and parsing in merge-heavy histories. Junio suggests adding a `has_subset_rev_flags()` helper to restore the original pruning behavior.

Second, and more fundamentally, Junio questions why the patch retains a hardcoded 64-branch limit (`MAX_REVS`) when the infrastructure (`flags_stride` and `init_commit_rev_flags_with_stride`) already supports dynamic stride. The remaining blockers are the static `ref_name[]` array and stack-allocated `rev[]`/`reflog_msg[]` arrays in `cmd_show_branch()`. Junio proposes dynamically growing these arrays at runtime, calculating `flags_stride` as `(ref_name_cnt + 63) / 64`, and eliminating `MAX_REVS` entirely. This would align the implementation with the variable-length bitset slab pattern established in 2025 and remove the last artificial limit.

The review is substantive: it identifies a concrete performance risk and a design gap that, if addressed, would make the patch more future-proof. No new tests or documentation changes are requested yet, but the feedback implies a v7 will be needed. The thread remains uncontested; no other reviewers have weighed in on these points.
