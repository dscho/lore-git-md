This is a **performance optimization follow-up** for the `git last-modified` command, part of an ongoing effort to close the speed gap between it and a hand-rolled `git log` pipeline. Jeff King (Peff) and Toon Claes are coordinating on a patch to reuse Git’s Bloom filter logic, which has already demonstrated a 4× speedup in benchmarks.

Peff responds to Toon’s latest benchmarks and design notes with a brief but substantive technical clarification. He confirms that the optimization—pre-filtering commits using a Bloom filter key derived from the pathspec—is unlikely to regress performance, even in edge cases where the target directory is modified by nearly every commit. The cost of checking a single Bloom key is low enough that the optimization should remain a net win unless the subtree is touched by *almost all* commits, a scenario Peff considers impractical.

The key technical discussion centers on how to expose the Bloom filter logic from `revision.c`. Peff suggests refactoring the internal helper `check_maybe_different_in_bloom_filter` into two parts: one to retrieve the filter, and another to check it against a `rev_info` structure. This would avoid exposing `revision.c` internals while still making the logic reusable. Toon had initially planned to make the helper public but now agrees to adopt Peff’s cleaner approach.

This exchange resolves the last major design question before a v2 patch series. The optimization is well-motivated, thoroughly benchmarked, and now has a clear implementation path. The only remaining work is the refactoring itself, which Peff and Toon are coordinating. The patch is likely to land smoothly, with no user-visible changes but measurable real-world impact for GitLab and Forgejo’s use cases.
