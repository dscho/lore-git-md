This is the fourth and final patch in Toon Claes’s four-part series to speed up the experimental `git last-modified` command by reusing Git’s Bloom filters. The patch ensures wildcard pathspecs (like `*.c`) continue to benefit from the Bloom-filter optimization introduced earlier in the series. Without this fix, `prepare_revision_walk()` would clear the `bloom_filter_settings` field, breaking per-path Bloom-filter lookups for wildcards.

Taylor Blau’s review is surface-level but practical: he points out that the existing test suite (`t8020`) never actually exercises the Bloom-filter code path because it doesn’t generate a commit-graph with changed-path Bloom filters. The current test cases either don’t use wildcards or let the shell expand them before Git sees them, so the new logic remains untested. He suggests adding a test that writes a commit-graph with `--changed-paths` and uses a genuinely quoted wildcard (e.g., `git last-modified -r "*"`) to verify the fix works as intended. The review is not questioning correctness—just flagging a gap in test coverage.

The patch itself is a small, targeted fix: eight lines in `builtin/last-modified.c` that restore the `bloom_filter_settings` field after `prepare_revision_walk()` clears it. It doesn’t expose new symbols or change the on-disk format, and the series as a whole already benchmarks well (cutting runtime from 52 ms to 14 ms on the ziglang/zig repo). The missing test is the only loose end here, and it’s a straightforward addition that wouldn’t require reworking the patch. If the author adds it, this patch should be ready to merge.
