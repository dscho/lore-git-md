This is a **bug report** about `git history fixup` interacting poorly with worktrees. Toon Claes demonstrates a clear reproduction case: after running `git history fixup HEAD` in one worktree, a second worktree (created via `git worktree add`) shows spurious staged changes that were never made in that worktree. The commit history itself is correct, but the index in the second worktree is corrupted, leaving it in a dirty state.

The issue appears to be that `git history fixup` (a command introduced in the `git history` series) does not properly account for multiple worktrees sharing the same repository. The command likely modifies the index in a way that is not isolated to the current worktree, causing the staged changes to leak into other worktrees. The reproduction steps are minimal and reproducible: a fresh repository, one commit, a worktree, and a single `git history fixup` invocation.

This is a **serious correctness bug** for users of `git history` in multi-worktree setups. The `git history` command is still relatively new (landed in Git 2.46, 2026), so edge cases like this are expected, but this one is particularly disruptive because it silently corrupts the index of unrelated worktrees. The report does not include a proposed fix, but the reproduction case is clear enough that a patch should be straightforward to develop.
