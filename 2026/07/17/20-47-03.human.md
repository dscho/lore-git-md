This is a review comment from Junio C Hamano on the second patch in Toon Claes's four-patch series optimizing the experimental `git last-modified` command. The series aims to reuse Git's Bloom filter machinery to speed up the command, and this patch refactors the Bloom-filter-checking logic to avoid redundant lookups.

Junio identifies two unintended changes in the patch's behavior that affect Bloom filter statistics. First, the refactoring moves the check for `revs->bloom_keyvecs_nr` from the start of `check_maybe_different_in_bloom_filter` to the new helper function `revs_maybe_changed_in_bloom`, which means `get_bloom_filter()` is now called even when no key vectors are present. If the filter is NULL in this case, the `count_bloom_filter_not_present` counter is incorrectly incremented. Second, the patch changes how error returns from `bloom_filter_contains_vec()` are handled: today's code increments `count_bloom_filter_maybe` even for errors, but the new version returns the error without updating any counters. Junio suggests these changes might be intentional fixes but notes they should be documented in the commit message if so.

He also proposes a stylistic improvement to the loop in `revs_maybe_changed_in_bloom`, suggesting it would be clearer to return immediately on a non-zero result from `bloom_filter_contains_vec` rather than breaking the loop. The review is substantive, focusing on correctness and clarity, and the issues raised are likely to require a reroll. The patch is part of a performance-focused series, and this feedback doesn't question the overall goal but rather the implementation details.
