This is a performance optimization for the experimental `git last-modified` command, part of a four-patch series from Toon Claes. The goal is to make `git last-modified` as fast as `git log` when querying the last commit that modified files in a directory, which currently isn’t the case—`last-modified` is about 2.5× slower in the reported benchmark.

The series reuses Git’s existing Bloom filter machinery (the same code that powers `git log`) to pre-filter commits before walking them. Patch 1 tidies up a condition in `revision.c` to avoid duplication, patch 2 exposes a helper function so `last-modified` can check a pathspec against the Bloom filter without redundant lookups, and patch 3 wires that helper into `last-modified`. Patch 4 is a bonus: it caches Bloom filters per-path when wildcards are used, squeezing out a little more speed.

Benchmarks on the ziglang/zig repository show the optimized version running in 14 ms instead of 53 ms, making it slightly faster than the equivalent `git log` pipeline. The same improvement is seen on GitLab’s monorepo. The patches touch only three files (`builtin/last-modified.c`, `revision.c`, and `revision.h`) and look clean: no new dependencies, no behavior changes, just plumbing reuse. If you care about `git last-modified` performance, this series is worth watching.
