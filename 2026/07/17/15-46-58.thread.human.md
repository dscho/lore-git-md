This thread is about Toon Claes’s four-patch series to speed up the experimental `git last-modified` command by reusing Git’s Bloom filters, aiming to match the performance of `git log` (14 ms vs the current 52 ms on the ziglang/zig repository). The series is under active review, with v1 posted and no prior versions.

The key technical change is reusing Bloom filters to avoid re-fetching them, which now covers all pathspec types, including wildcards like `*.c`. The patches touch `revision.c`, `revision.h`, and `builtin/last-modified.c`, introducing new public functions like `revs_maybe_changed_in_bloom` and exposing `repo_may_have_commit_with_changes`. Junio C Hamano’s review of patch 2/4 flagged two unintended behavioral changes in Bloom filter statistics reporting, which Toon has yet to address. Additionally, Toon acknowledged missing trailers for Jeff King’s contributions and plans to add them in a reroll.

The latest development is Taylor Blau’s substantive review of patch 3/4, which uncovered a correctness bug in the Bloom-filter pre-filtering logic when `--show-trees` is used. The issue arises because the pathspec doesn’t cover all entries in `lm->paths` (which includes ancestor trees), so a Bloom filter indicating “no changes” for the pathspec may miss changes to those trees. Taylor provided a minimal reproduction case and suggested guarding the pre-filter with a check for `!lm->show_trees`. This bug means the cover-letter benchmarks, which use `--show-trees`, may be misleading until fixed. The series is now blocked on addressing this issue, along with Junio’s earlier feedback and the missing trailers.
