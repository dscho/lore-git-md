This thread is about Toon Claes’s four-patch series that speeds up the experimental `git last-modified` command by reusing Git’s Bloom filters. The goal is to match the speed of `git log` when querying the last commit that modified files matching a pathspec (including wildcards like `*.c`). The current implementation is about 3.7 times slower (52 ms vs 14 ms) on the ziglang/zig repository.

The series is under review, with v1 posted and no prior versions. Toon has acknowledged a minor oversight—missing `Helped-by`/`Based-on-patches-by` trailers for Jeff King—and plans to address it in a reroll. The series is functionally complete, with the final patch ensuring the Bloom-filter optimization works for wildcard pathspecs. Key changes include new functions (`repo_may_have_commit_with_changes` and `revs_maybe_changed_in_bloom`) and a refactoring that eliminates redundant Bloom-filter lookups.

Junio C Hamano’s recent review of the second patch raised two unintended behavioral changes that affect Bloom filter statistics. First, the refactored code increments the "not present" counter even when no key vectors exist, unlike the original code. Second, it no longer increments the "maybe" counter when `bloom_filter_contains_vec()` returns an error. Junio suggests either documenting these as intentional fixes or correcting them. He also proposed a stylistic improvement to the loop in `revs_maybe_changed_in_bloom()` to clarify control flow. The review is substantive, focusing on observable behavior rather than just code structure, and highlights a potential regression in monitoring data. No other reviews or objections have been raised yet.
