This thread is about Toon Claes’s four-patch series that speeds up the experimental `git last-modified` command by reusing Git’s Bloom filters, aiming to match the speed of `git log` (14 ms vs. the current 52 ms on the ziglang/zig repository). The series is under review, with no prior versions posted.

The key technical change is reusing Bloom filters to avoid redundant fetches, extending the optimization to wildcard pathspecs like `*.c`. However, reviews have surfaced several issues. Junio C Hamano flagged two unintended behavioral changes in patch 2/4: the new code increments a Bloom filter counter even when no key vectors exist, and it skips counter updates on errors—both deviations from the original behavior. Taylor Blau, who also reviewed patches 3/4 and 4/4, identified a correctness bug in patch 3/4 when `--show-trees` is used, as the pathspec doesn’t cover all entries in the revision walk, potentially missing changes to ancestor trees. He also noted that the test suite doesn’t exercise the Bloom filter code path, as it lacks a commit-graph with changed-path Bloom filters and uses unquoted wildcards that bypass the optimization.

Toon has acknowledged missing trailers for Jeff King’s contributions and intends to address them in a reroll. The open questions are whether the counter behavior changes in patch 2/4 are intentional (and should be documented) or accidental (and should be fixed), and how to resolve the `--show-trees` bug and test coverage gaps. Taylor Blau’s latest reply reinforces Junio’s concern about the counter regression, calling it a bug and suggesting the guard for key vectors should be restored. The series remains in flux, with no merge decisions yet.
