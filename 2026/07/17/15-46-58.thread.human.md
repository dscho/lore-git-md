This thread is about Toon Claes's patch series (`v1`) to speed up the experimental `git last-modified` command by reusing Git's Bloom filters, aiming to match the performance of `git log` (14 ms vs. the current 52 ms) when querying the last commit that modified files matching a pathspec (including wildcards like `*.c`). The series is under active review, with key participants including the author, Junio C Hamano (maintainer), Jeff King (Peff), and Taylor Blau.

The main technical focus has been on correctness and design trade-offs. Junio and Taylor identified unintended behavioral changes in Bloom filter statistics reporting in patch 2/4, with agreement that one change (incrementing `count_bloom_filter_not_present` even when no key vectors exist) should be reverted. Jeff raised concerns about the public API's tristate return semantics in patch 1/4, suggesting a boolean return for clarity. The most contentious issue has been patch 3/4, where Taylor discovered a correctness bug in the Bloom-filter pre-filtering logic when `--show-trees` is used: the pathspec doesn't cover all entries in `lm->paths`, leading to potential false negatives. Jeff proposed an alternative design—removing ancestor tree entries not covered by the original pathspec—which Taylor endorsed as a reasonable trade-off for an experimental command. Taylor provided two tested implementations: one that removes uncovered paths entirely (simpler and faster) and another that retains them while optimizing Bloom-filter checks (more complex but preserves output). The simpler approach is favored for now.

Other open questions include a maintainability concern in patch 4/4 (restoring `bloom_filter_settings` after `prepare_revision_walk()` clears it) and a documentation inconsistency for `--show-trees`. The author has acknowledged missing trailers for Jeff King's contributions and plans to address them in a reroll. The series touches `revision.c`, `revision.h`, and `builtin/last-modified.c`, introducing new symbols like `repo_may_have_commit_with_changes` and `revs_maybe_changed_in_bloom`. No new test files were added, but Taylor identified gaps in test coverage for Bloom filter code paths. The next steps are likely a reroll incorporating the agreed-upon fixes, particularly for patch 3/4.
