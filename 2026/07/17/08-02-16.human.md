This is a performance discussion about the `git last-modified` command, part of an ongoing thread comparing its speed to a hand-rolled `git log` pipeline. Jeff King (Peff) clarifies a key misunderstanding: while GitLab’s real-world use case batches multiple files (where `git last-modified` already outperforms naive loops), the benchmark Gusted reported focuses on a single-file case where `git last-modified` is 2.5× slower. Peff explains that the `git log` pipeline in Gusted’s example processes the entire subtree in one walk, then requires post-processing to extract individual files—an overhead that scales with the number of *touched* commits, not the total repository size. In contrast, `git last-modified`’s inefficiency scales with the total number of commits, which is why it lags in large repositories even when the target directory is small. Peff reaffirms his earlier analysis: the command can be optimized to match `git log`’s top-level commit filtering, and his proof-of-concept patch already demonstrates a 4× speedup. The discussion remains technical and collaborative, with no new edge cases or objections raised.
