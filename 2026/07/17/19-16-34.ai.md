This is the final patch in Toon Claes’s four-part series optimizing the experimental `git last-modified` command by reusing Bloom filters. The patch ensures wildcard pathspecs (e.g., `*.c`) continue to benefit from the Bloom-filter acceleration introduced earlier in the series. Without this fix, `prepare_revision_walk()` would clear `bloom_filter_settings` for pathspecs that cannot be converted into a single Bloom key, breaking the per-path filter lookups added in patch 3. The fix is a straightforward eight-line addition in `builtin/last-modified.c` that restores the settings after the revision walk is prepared.

The patch is narrowly scoped and directly addresses the regression it describes. The commit message clearly explains why the settings are cleared and why restoring them is necessary, and the code change is minimal and self-contained. No new symbols are introduced, and the on-disk format remains unchanged. The series as a whole already demonstrates a 3.7× speedup (from 52 ms to 14 ms) on the ziglang/zig repository; this patch ensures those gains extend to wildcard pathspecs, which are a common use case.

Toon’s follow-up clarifies that the fix is simpler than an earlier approach suggested by Jeff King (Peff), which would have re-invoked `prepare_to_use_bloom_filter()`. The current solution avoids redundant work by restoring only the settings, not the entire filter preparation. The thread context confirms this is the last piece needed to make the Bloom-filter optimization work for all pathspec types, completing the series’ goal of matching `git log`’s performance for last-modified queries.
