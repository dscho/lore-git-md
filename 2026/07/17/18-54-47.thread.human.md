The `git history fixup` command, introduced in Git 2.46 (2026), has a bug where it corrupts the index in other worktrees sharing the same repository. When run in one worktree, it leaves spurious staged changes in others, even though those worktrees were untouched by the user. The root cause was identified by Phillip Wood: the command rewrites commits pointed to by branches checked out in other worktrees without updating their index or working copy, leaving them in a dirty state.

The discussion has now settled on a fix. Patrick Steinhardt, the original author of `git history`, has endorsed the safer approach—refusing to rewrite branches checked out in other worktrees, similar to `git rebase --update-refs`. This avoids the complexity of attempting "best-effort" updates in other worktrees, which could introduce new edge cases. A GitLab issue (#772) has been opened to track this for the next release cycle, but the community is welcome to submit a patch in the meantime. The remaining work involves implementing the safety check (likely reusing logic from `git rebase`) and adding regression tests to both the `git history` and worktree test suites.

The bug remains reproducible with the minimal test case provided by Toon Claes, who initially reported the issue. The fix will target the worktree subsystem, primarily touching `builtin/history.c` and `worktree.c`. While the design decision is now clear, no patch has been posted yet.
