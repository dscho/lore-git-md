The `git history fixup` command, introduced in Git 2.46 (2026), has a bug where running it in one worktree corrupts the index in other worktrees sharing the same repository. Toon Claes reported this with a clear reproduction case: after creating a fresh repository, adding a worktree, and running `git history fixup`, the other worktree shows spurious staged changes it never made.

Phillip Wood analyzed the issue and traced it to `git history fixup` rewriting commits without updating the index or working copy in other worktrees where those commits are checked out. This mirrors a problem `git rebase --update-refs` already handles—it refuses to update branches checked out elsewhere by default. Phillip suggests `git history fixup` adopt the same approach: either refuse to rewrite such branches or update their indexes if they’re clean. He also flagged a missing safety check: `git history fixup` lacks the rebase subsystem’s protection against concurrent rewrites of the same branch, risking race conditions.

No patch has been posted yet, but the root cause and solution path are now clear. The fix will likely touch `builtin/history.c` and worktree infrastructure, with no on-disk format changes expected. The discussion is still early, but Phillip’s review provides a solid foundation for the next steps.
