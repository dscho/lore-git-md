This thread is a **bug report** about a serious correctness issue in `git history fixup` when used with multiple worktrees. Toon Claes discovered that running `git history fixup HEAD` in one worktree silently corrupts the index of other worktrees in the same repository, leaving them in a dirty state with spurious staged changes—even though no actual modifications were made in those worktrees. The commit history itself remains correct, but the index corruption is disruptive and could lead to accidental commits or confusion.

The bug affects users of the relatively new `git history` command (introduced in Git 2.46, 2026) who work with multiple worktrees. The reproduction case is minimal and reproducible: a fresh repository, one commit, a second worktree created via `git worktree add`, and a single `git history fixup` invocation. The issue likely stems from `git history fixup` modifying the index in a way that isn’t properly isolated to the current worktree, causing changes to leak across worktrees. The report doesn’t propose a fix, but the clear reproduction steps should make it straightforward to debug and patch.

Key participants so far are just Toon Claes, who provided the detailed report. The subsystems involved are worktree handling and index management, with likely culprits in `builtin/history.c`, `worktree.c`, or `read-cache.c`. No prior discussion of this issue is referenced, so this appears to be a newly discovered bug. The thread is still open, with no responses or proposed fixes yet.
