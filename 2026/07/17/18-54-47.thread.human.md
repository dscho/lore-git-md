The `git history fixup` command, introduced in Git 2.46, has a bug where running it in one worktree corrupts the index of other worktrees sharing the same repository. The issue is confirmed, and Phillip Wood identified the root cause: the command rewrites commits pointed to by branches checked out in other worktrees without updating their index or working copy, leaving them in a dirty state. No patch has been posted yet, but the discussion is now focused on how to fix it.

The main debate is whether `git history fixup` should refuse to rewrite branches checked out in other worktrees (a safer default, similar to `git rebase --update-refs`) or attempt to update their index and working copy if they are clean (a more user-friendly approach). Toon Claes, the reporter, prefers the latter, calling it the "friendlier" option. Additionally, the command lacks a safety mechanism to prevent concurrent rewrites of the same branch, which `git rebase` already has. Toon suggests building on an existing patch that enumerates all ways a branch can be checked out to implement this protection.

The fix will likely involve changes to `builtin/history.c`, `worktree.c`, and `read-cache.c`, and may require new regression tests for both the `git history` and worktree test suites. The thread remains in the design phase, with no code changes yet.
