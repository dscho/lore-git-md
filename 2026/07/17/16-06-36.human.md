This is the first patch in a two-part bugfix series from Phillip Wood targeting edge cases in `git rebase -i`. It fixes an incorrect commit count in the squash/fixup template message that occurs when a preceding fixup or squash command is skipped during an interactive rebase.

The bug arises from how the sequencer tracks executed fixup/squash commands. When a command is skipped (via `git rebase --skip`), the code removes the command from the tracking list but fails to remove the preceding newline, leaving a blank line that later causes the count to be off by one. The patch corrects this by ensuring the newline is removed when a command is skipped, and also makes the code that reads the list skip blank lines to maintain compatibility between different Git versions.

The fix touches `sequencer.c` and extends an existing test in `t/t3418-rebase-continue.sh` with 36 new lines to cover the regression. The test now verifies that skipping multiple fixup/squash commands before the final one produces the correct commit count in the template message. Phillip is a well-regarded contributor with deep expertise in the rebase code, so the fix is likely technically sound. The issue is user-facing but niche—it only affects workflows where multiple fixup/squash commands are skipped before the final one in a chain. The consequence is minor (a misleading count in the template header), but the fix is clean and well-tested.
