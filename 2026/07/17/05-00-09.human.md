This is a **feature addition** to `git bisect` that is now at a design crossroads. Junio C Hamano, the maintainer, responds to Harald Nordgren’s clarification about the `--auto-reset` option’s current behavior (which resets to the original pre-bisect commit) by proposing a more flexible design: `--auto-reset=<where>`, where `<where>` can be either `original` or `found` (the first bad commit). The default, if omitted, would remain `original`.

The key shift here is from a binary flag to a parameterized option, which better accommodates both automated workflows (where resetting to the original commit is useful) and interactive debugging (where staying on the bad commit is preferred). Junio’s suggestion is pragmatic: it avoids forcing a one-size-fits-all behavior and instead lets users choose based on their context. The proposal also sidesteps the earlier naming debate—`--auto-reset` remains appropriate even if the default behavior stays the same, and the parameter makes the intent explicit.

This change would require updates to the implementation (parsing the parameter, persisting the choice in the state file), documentation (describing the two modes), and tests (validating both behaviors). The preparatory refactoring in patches 1 and 2 (file descriptor handling and quiet checkout) are unaffected and likely to remain as-is. No other reviewers have weighed in yet, so the discussion is still between the author and maintainer. If Harald accepts this direction, the series will need a v2 with the new design.
