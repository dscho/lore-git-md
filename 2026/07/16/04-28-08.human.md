This is a performance analysis and optimization proposal for the `git last-modified` command. Jeff King (Peff) investigates why `git last-modified` is 2.5× slower than a hand-rolled `git log` pipeline when both use the same commit and path filter on a repository with commit-graph and changed-path Bloom filters.

Peff identifies the root cause: `git last-modified` checks every path in the input set against every commit’s Bloom filter, leading to O(paths × commits) filter checks. In contrast, `git log` pre-filters commits using a single Bloom key derived from the pathspec, reducing the number of checks to O(commits). He demonstrates this by benchmarking three scenarios: no commit-graph (where `last-modified` wins), commit-graph without changed-paths (where they tie), and commit-graph with changed-paths (where `last-modified` loses).

The proposed fix is a hacky patch that reuses the Bloom filter logic from `revision.c` to pre-filter commits, bringing `last-modified`’s runtime down from 64 ms to 16 ms—faster than the `git log` pipeline. The patch is not production-ready but serves as a proof of concept. Peff outlines next steps: refactoring `revision.c` to expose the Bloom filter logic, adding tests (none currently cover `last-modified` with changed-paths), and exploring edge cases like high-touch paths or non-literal pathspecs.

This is a well-motivated optimization with clear benchmarks and a concrete path forward. The patch itself is small and focused, though it highlights the need for broader refactoring in `revision.c`. If Toon Claes (the command’s author) or others pick this up, it could significantly improve `last-modified`’s performance in repositories with many paths and sparse changes. The discussion is early-stage but already substantive.
