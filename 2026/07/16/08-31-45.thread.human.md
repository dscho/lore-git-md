This thread introduces `git stash reword`, a new subcommand that lets users edit stash messages after creation—a feature long requested by users who end up with hundreds of stashes carrying unhelpful default messages like "WIP on main". The justification for the feature is now firmly established, with reports from brian m. carlson (211 stashes in `git.git`) and erik88 (100+ stashes) making a clear case for its practical value. Junio C Hamano, initially skeptical, has accepted the need for the feature, though he’s also floated a broader idea of tying stashes to branches in the future, which could eventually replace or conflict with this implementation.

The second version of the patch (`v2`) addresses all the major concerns raised during review. The most significant change is a fully transactional reflog rewrite, replacing the earlier non-atomic drop-and-re-store approach that risked data loss and suffered from quadratic runtime, especially under the reftable backend. The new implementation reads the entire reflog, rewrites it in a single transaction, and commits the change atomically, preserving timestamps and order for all entries except the one being reworded. It also includes a recovery path for failed transactions, reporting object IDs of any entries that couldn’t be re-stored so users can manually recover with `git stash store`. The command now only accepts index-based selectors (`stash@{1}`) to avoid race conditions and rejects time-based ones (`stash@{yesterday}`). Tests cover edge cases like rewording the deepest entry, empty messages, and invalid arguments, and the patch works with both the files and reftable backends.

The patch is now technically sound and ready for further review. The only lingering question is whether Junio’s suggestion of branch-tied stashes might eventually make this feature redundant, but that’s a long-term consideration and not a blocker for merging. The author, Emin Özata, has addressed all substantive feedback, and the implementation is now both atomic and performant. The next step is likely a final round of review from Junio or other maintainers before it’s queued for integration.
