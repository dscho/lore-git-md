This thread introduces `git repack --drop-filtered`, a new option that lets partial clones reclaim disk space by safely removing locally cached promisor blobs above a size threshold. The feature is now technically complete in its fifth iteration (v5), with all prior feedback addressed—including a blocking type-mismatch bug, documentation improvements, and mechanical cleanups. Christian Couder has declared the series "good to go," and the author has proposed it for Junio’s `next` integration branch, signaling readiness for broader testing.

The core design targets only promisor objects (ensuring they remain recoverable from the remote), avoids locally created objects, and includes UX optimizations like merge/rebase checks and index validation to prevent immediate re-fetching. However, a new substantive review from Samuel Bronson—based on real-world testing with a large `llvm-project` clone—highlights a usability pain point: the current implementation fails hard if any blob in the drop set is referenced by the index, forcing users to restart the slow enumeration process. Bronson proposes a softer approach—skipping such blobs with a warning—arguing it preserves safety while improving usability. This feedback may require a v6 before the series graduates to `next`, as it touches a key safety guard and could influence how users interact with the feature.

Key participants include the author (Siddharth Shrimali), Junio (who raised procedural questions about integration), and Christian Couder (who reviewed the mechanical readiness). The series builds on existing partial-clone and repack infrastructure, with follow-up work deferred for remote verification, time-based culling, and a drop log. The open question now is whether to adopt Bronson’s proposed behavioral change or retain the current fail-fast behavior.
