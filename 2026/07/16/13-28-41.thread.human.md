Here’s the human-mode catch-up summary for the thread:

This thread is an RFC patch series from first-time contributor Siddharth Shrimali proposing `git repack --drop-filtered`, a new option to safely reclaim disk space in partial clones by removing locally cached promisor blobs above a size threshold (e.g., `--filter=blob:limit=10M`). The feature is designed to target only objects marked as promisor (ensuring they can be re-fetched from the remote), avoid locally created objects, and include safety guards to prevent drops during merges, rebases, or cherry-picks, or of blobs referenced by the current index.

The series is now at RFC v1 (7/7 patches posted), with a v2 planned to address key feedback. The most critical issue—a logical flaw in the `--drop-filtered` vs `--write-bitmap-index` validation—was identified by Junio and will be fixed in v2 by restructuring the validation to distinguish between command-line and configuration-driven bitmap settings. Safety guards (merge/rebase/cherry-pick checks and index validation) are now confirmed as non-negotiable for v2, per feedback from Siddharth Asthana. The drop log (`$GIT_DIR/objects/info/promisor-dropped`), which records removed objects, is deferred to a follow-up, though Shrimali has agreed to document its path in `gitrepository-layout` and add test coverage when finalized. A notable clarification for v2: a real `--drop-filtered` run will now imply `-d` (removing old promisor packs containing the dropped blobs), ensuring actual disk space reclamation.

The series touches several subsystems, including `repack-filtered.c` (core logic), `repack-promisor.c` (promisor pack rebuilding), and `list-objects-filter.c` (new APIs for filtering OID sets). While the CLI design (`--drop-filtered` + `--dry-run`) is settled, internal API reorganization and test placement remain priorities for v2. No maintainer decision on integration has been made yet, and the series is still under active design iteration. The current focus is on addressing the blocking issues before posting v2.
