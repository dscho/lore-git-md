This thread is an RFC patch series from first-time contributor Siddharth Shrimali proposing `git repack --drop-filtered`, a new option to safely reclaim disk space in partial clones by removing locally cached promisor blobs exceeding a user-specified size threshold. The series is now complete at RFC v1 (7/7 patches), with the final patch implementing a drop log to record removed objects for improved error messages during future lazy-fetch failures.

The core functionality is implemented, but a blocking logical flaw in patch 1/7—identified by Junio—renders the safety mechanism ineffective: the validation of `--drop-filtered` against `--write-bitmap-index` occurs too late in the control flow, after bitmaps may have been enabled by repository configuration, preventing proper error handling. Siddharth has acknowledged this issue and plans to restructure the validation in v2 to explicitly track whether `--write-bitmap-index` was set on the command line (erroring out if so) versus via configuration (silently disabling it). Other safety guards, such as checks for merges, rebases, or index references, remain deferred to follow-ups. The series also introduces a drop log (`$GIT_DIR/objects/info/promisor-dropped`) to record removed objects, though it currently lists all configured promisor remotes rather than the specific one each object is recoverable from, pending the `remote-object-info` protocol command.

The discussion has so far involved Junio’s substantive review of the blocking flaw and Christian Couder’s surface-level feedback on the CLI design, which Siddharth addressed by reaffirming his preference for separating `--drop-filtered` and `--dry-run` while committing to document the rationale. No maintainer decision on integration has been made yet, and the series remains in flux with a v2 expected to reorganize APIs and fix the validation issue. The broader architectural questions, such as remote verification and filter scope, are still open.
