This thread is about an RFC patch series from first-time contributor Siddharth Shrimali that adds a `--drop-filtered` option to `git repack` for partial clones. The feature lets users reclaim disk space by removing locally cached promisor blobs above a specified size threshold, with safety guarantees to avoid dropping objects that can't be recovered from the promisor remote or are currently in use.

The series is now complete at RFC v2 (7/7 patches), addressing all blocking issues from the first version. Key improvements include a fix for a subtle validation bug around bitmap handling, full implementation of safety guards to prevent drops during merges or rebases and of blobs referenced by the current index, and comprehensive documentation. The core logic enumerates promisor blobs exceeding the threshold and rebuilds promisor packs while excluding them, with crash safety ensured by Git's existing repack machinery. A new test script verifies the behavior, including the safety guards.

The main open question is whether to keep the current safety guards or replace them with a time-based heuristic proposed by Junio, which would avoid culling recently fetched objects to reduce redundant network operations. Siddharth Shrimali now endorses this approach, noting that promisor objects are always stored in packs, so per-object timestamps would require new metadata similar to cruft pack `.mtimes` files. The guards are now seen as optional optimizations rather than correctness measures. Other loose ends include the deferred drop log (which would record removed objects) and remote verification, both dependent on the pending `remote-object-info` protocol command. No maintainer decision has been made yet on whether or when to merge the series.
