This thread is an RFC patch series from first-time contributor Siddharth Shrimali proposing `git repack --drop-filtered`, a new option to safely reclaim disk space in partial clones by removing locally cached promisor blobs above a size threshold. The series is now complete at seven patches, with the final patch implementing a drop log to record removed objects for better error messages during future lazy-fetch failures.

The feature is designed to work only on objects marked as promisor (ensuring they can be refetched from the remote), avoids locally created objects, and introduces a new log file (`$GIT_DIR/objects/info/promisor-dropped`) to track removals. However, Junio C Hamano’s recent review of the first patch identified a critical flaw: the validation logic for `--drop-filtered`’s incompatibility with `--write-bitmap-index` runs too late, after repository configuration may have already enabled bitmaps by default. This means the check cannot distinguish between user-requested bitmaps (which should be rejected) and config-driven ones (which should be silently disabled), undermining the safety mechanism meant to prevent bitmap corruption.

The series remains in early RFC stage with no maintainer decision or integration branch assignment. Key open questions include deferred safety checks (e.g., preventing drops during merges or when blobs are referenced by the index), remote verification (the drop log currently records all promisor remotes rather than the specific one each object is recoverable from), and API reorganization. The author plans a v2 addressing these issues, but Junio’s feedback now blocks progress until the bitmap validation logic is fixed. No other substantive reviews have been recorded yet.
