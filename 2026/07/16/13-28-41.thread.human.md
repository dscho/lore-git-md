This thread is an RFC patch series from first-time contributor Siddharth Shrimali, proposing a `--drop-filtered` option for `git repack` to safely reclaim disk space in partial clones by removing locally cached promisor blobs exceeding a size threshold. The series is now at RFC v2 (7/7 patches), with the core functionality finalized and all blocking issues from v1 addressed.

The key idea is to let users specify a size limit (e.g., `--filter=blob:limit=10M`) so that `git repack --drop-filtered` can safely remove promisor blobs larger than that threshold, knowing they can be re-fetched from the promisor remote if needed. Safety is enforced through multiple guards: only promisor objects are targeted, locally created objects are untouched, and drops are blocked during merges, rebases, or cherry-picks to avoid immediate re-fetching. The series also implements index validation to prevent dropping blobs referenced by the current index. A real `--drop-filtered` run now implies `-d`, ensuring old promisor packs containing the dropped blobs are removed and disk space is actually reclaimed.

Patch 4/7, just posted, implements the core enumeration logic that identifies which promisor blobs exceed the threshold. It introduces `enumerate_promisor_blobs()` to walk promisor objects, apply the filter, and collect candidates for dropping. The patch is well-tested and integrates cleanly with the existing repack machinery. Earlier patches in the series laid the groundwork: patch 1/7 added the CLI options and validation logic (fixing a critical flaw in the `--write-bitmap-index` interaction), patch 2/7 introduced a helper to apply filters to existing oidsets, and patch 3/7 extended the promisor repack machinery to exclude specified objects.

The series has drawn substantive review from Junio Hamano (who identified the blocking validation flaw in v1) and Siddharth Asthana (who raised critical safety concerns now addressed in v2). Christian Couder provided surface-level feedback on the CLI design, which has been incorporated. The drop log and remote verification remain deferred to follow-ups, but the core functionality is complete. No maintainer decision has been made yet, and the integration branch is still unknown. The series is a promising addition to partial clone tooling, offering a safe way to manage disk space without risking data loss.
