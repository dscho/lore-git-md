This is a **feature addition** to `git bisect` that introduces a `--auto-reset` option, but the design is now in flux due to maintainer feedback.

The author, Harald Nordgren, clarifies that the current implementation of `--auto-reset` returns the working tree to the original pre-bisect commit, not the first bad commit (the culprit). Junio C Hamano, the maintainer, expresses a strong preference for the opposite behavior: leaving the working tree on the first bad commit after bisect completes. This is a fundamental design disagreement that will likely require a rework of the feature’s core logic, documentation, and tests.

The thread is now at a decision point: the author acknowledges the misalignment and is open to changing the behavior, but notes that the option name (`--auto-reset`) may no longer fit if the working tree stays on the bad commit. No alternative names or behaviors have been proposed yet, and no other reviewers have weighed in. The outcome will determine whether the feature serves automated workflows (original intent) or interactive debugging (Junio’s use case).

Key technical details to track in follow-up discussion: the commit to which the working tree resets, the option name, and whether the `BISECT_AUTO_RESET` state file remains necessary if the behavior changes.
