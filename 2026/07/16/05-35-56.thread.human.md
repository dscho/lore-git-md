This thread introduces a new `--reset-when-found[=<where>]` option for `git bisect`, allowing users to automatically reset the working tree to either the pre-bisect state (`original`, the default) or the first bad commit (`found`) after the bisect completes. The feature is designed for automated workflows and interactive debugging, eliminating the need for an explicit `git bisect reset`.

The series has evolved through three versions, with the current v3 addressing all prior feedback. The design settled on a parameterized option (`--reset-when-found[=<where>]`) instead of the earlier boolean `--auto-reset`, making the behavior more explicit. The implementation includes a preparatory plumbing change (adding a `quiet` parameter to `bisect_reset()`), the core auto-reset logic, and deferred reset handling for `git bisect run` to avoid platform-specific issues with open file descriptors. The series touches `bisect.c`, `builtin/bisect.c`, documentation, and tests, with no on-disk format changes.

All key participants—Harald Nordgren (author), Junio C Hamano (maintainer), and Johannes Sixt (reviewer)—have signed off on the design and implementation. Junio’s latest email confirms the series is uncontroversial and ready for integration, with no outstanding objections. He plans to mark it for the `next` branch shortly, indicating it will likely graduate to `master` in the current cycle. The only practical limitation noted is that users cannot conditionally choose the reset target based on the bisect outcome, as the target must be specified upfront.
