The `git bisect --auto-reset` feature is moving toward a more flexible design after the author, Harald Nordgren, agreed to Junio C Hamano’s proposal to make the option parameterized. Originally pitched as a simple boolean flag that would reset the working tree to its pre-bisect state, the feature will now accept `--auto-reset=<where>` with two values: `original` (the default, resetting to the pre-bisect commit) or `found` (leaving the working tree on the first bad commit). This change accommodates both automated workflows—where resetting to the original state is desirable—and interactive debugging, where users may want to inspect the culprit commit directly.

The first version of the series included a preparatory refactoring and a quiet-checkout addition, both of which remain uncontroversial and will carry forward unchanged. The next iteration, v2, will focus on implementing the parameterized behavior, updating the `BISECT_AUTO_RESET` state file to store the target commit instead of a boolean, and revising tests to cover both reset modes. No other reviewers have weighed in, so the design discussion appears settled for now. The thread is now waiting on the revised patch series, which should address the remaining technical details and edge cases.
