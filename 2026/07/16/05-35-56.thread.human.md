This thread is about adding a `--auto-reset=<where>` option to `git bisect` that automatically returns the working tree to a specified commit after identifying the first bad commit. The feature is designed to simplify both automated workflows and interactive debugging by eliminating the need for an explicit `git bisect reset`.

The design is now settled, with the author, Harald Nordgren, preparing a v2 patch series that implements Junio C Hamano’s proposal to make the option parameterized, accepting either `original` (reset to the pre-bisect commit, the default) or `found` (leave the working tree on the first bad commit). The preparatory refactoring and quiet-checkout additions remain uncontroversial. Junio’s latest email clarifies a minor limitation: because the reset target depends on the bisect outcome, users who need conditional behavior may still need to manually reset afterward. This isn’t a blocker—just a note on the feature’s scope.

The series touches `bisect.c`, `builtin/bisect.c`, documentation, and tests, introducing no new on-disk formats or symbols beyond updates to the `BISECT_AUTO_RESET` state file. Open questions are now limited to implementation details like the state file format and edge-case handling (interruptions, errors). No further review comments have been raised, and the thread is on track for the next iteration.
