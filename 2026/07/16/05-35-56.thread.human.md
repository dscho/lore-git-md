This thread introduces a new `--reset-when-found[=<where>]` option for `git bisect`, allowing users to automatically reset the working tree after identifying the first bad commit. The feature is designed for automated workflows and interactive debugging, eliminating the need for an explicit `git bisect reset`.

The v3 patch series, posted by Harald Nordgren, is now complete and uncontroversial. It consists of three patches: a preparatory plumbing change, a quiet-checkout implementation, and the core feature. The option accepts `original` (reset to the pre-bisect commit, the default) or `found` (leave the working tree on the first bad commit). The series retains the settled design from v2, including the rename from `--auto-reset` to `--reset-when-found` and deferred reset behavior for `git bisect run` to address platform-compatibility concerns.

Key participants include Junio C Hamano, who proposed the parameterized design, and Johannes Sixt, who suggested the option rename and raised a platform-compatibility concern that was resolved in v3. The implementation touches `bisect.c`, `builtin/bisect.c`, and related documentation and tests, with no on-disk format changes beyond a new state file. The series is ready for integration, with no open questions or loose ends. The only noted limitation is that users cannot conditionally choose the reset target based on the bisect outcome, as the target must be specified upfront.
