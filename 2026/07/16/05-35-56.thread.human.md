The `git bisect --reset-when-found` feature is nearly ready for integration. Harald Nordgren’s v3 patch series, which adds an option to automatically reset the working tree after a bisect completes, has been marked for `next` by Junio Hamano. The series introduces `--reset-when-found[=<where>]`, where `<where>` can be `original` (the default, resetting to the pre-bisect commit) or `found` (leaving the working tree on the first bad commit). This targets automated workflows and interactive debugging by eliminating manual reset steps.

The design is settled, with all prior feedback addressed. Junio noted a minor practical limitation: users who want to conditionally choose the reset target based on the bisect outcome (e.g., `original` or `found`) must still reset manually, as the target must be specified upfront. Johannes Sixt’s review of v2 led to the option being renamed from `--auto-reset` to `--reset-when-found` for clarity, and a platform-compatibility concern about file descriptor handling was resolved by reverting to filename-based output in v3.

The latest review from Sixt is surface-level, focusing on coding style and test hygiene rather than core functionality. He flagged minor issues—standardizing error message templates, improving shell safety in tests, and cleaning up test chaining—but none affect the feature’s logic or integration. The series remains uncontroversial and is expected to graduate to `master` in the current cycle.
