This thread introduces a new `--reset-when-found[=<where>]` option for `git bisect`, allowing users to automatically reset the working tree after identifying the first bad commit—either to the original pre-bisect state (`original`, the default) or to the found commit itself (`found`). The feature is designed for automated workflows and interactive debugging, eliminating the need for an explicit `git bisect reset`.

The v5 patch series, authored by Harald Nordgren, is technically complete and has addressed all substantive and surface-level feedback, including a maintainer-proposed refactoring that centralized the auto-reset logic in the top-level `cmd_bisect()` function. The series is marked for integration into Junio C Hamano’s `next` branch, indicating it is ready for broader testing. While the implementation is sound, Junio has since suggested two minor internal clean-ups—reading `refs/bisect/bad` directly instead of propagating the first bad commit OID via a static variable, and simplifying the state tracking for the reset target—that could further streamline the code. These are optional and would not change the user-facing behavior.

Key participants include Harald Nordgren, who implemented the feature and incorporated all prior feedback; Junio C Hamano, who proposed the refactoring and later suggested the additional clean-ups; and Johannes Sixt, who provided surface-level review comments that were addressed in earlier versions. The series touches `bisect.c`, `builtin/bisect.c`, and related documentation and tests, with no on-disk format changes or new public symbols. All open questions have been resolved, and the feature is now awaiting integration.
