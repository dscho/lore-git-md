The `git bisect --auto-reset` feature is nearing readiness, with only a final naming tweak standing between the current v2 patch series and integration. Harald Nordgren introduced the option to automatically reset the working tree after a bisect completes, either back to the original pre-bisect commit or to the first bad commit (the culprit). This targets both scripted workflows and interactive debugging by eliminating the need for an explicit `git bisect reset`.

The design settled early on a parameterized `--auto-reset=<where>` (with values `original` or `found`), replacing the original boolean flag. Junio C Hamano, the maintainer, endorsed this approach, noting that the default (`original`) aligns with the author’s use case while still accommodating users who prefer to leave the working tree on the first bad commit. The implementation is split across three uncontroversial patches: a preparatory refactoring of file handling, plumbing to suppress checkout noise, and the core feature with thorough test coverage. The only constraint is that `--auto-reset` cannot be used with `--no-checkout`, as that mode prevents checking out either target.

Two loose ends from the v2 review have now been resolved. Johannes Sixt suggested renaming the option to `--reset-when-found` to make the timing explicit, and Junio agreed, leaving the author to update the patches. Sixt also raised a technical question about the refactoring in patch 1—whether the commit message’s claim about avoiding file reopens was accurate on Windows—but this was a minor clarification rather than a blocker. With the naming settled, the series is effectively ready for a v3 update and subsequent integration. The feature’s practical limitation—that users cannot conditionally choose the reset target based on the bisect outcome—remains, but this was acknowledged upfront and doesn’t affect the core functionality.
