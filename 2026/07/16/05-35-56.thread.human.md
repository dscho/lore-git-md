This thread is about a small but useful quality-of-life improvement for `git bisect`: a new `--auto-reset=<where>` option that automatically returns the working tree to either the original pre-bisect commit (`original`, the default) or the first bad commit (`found`) after the bisect completes. The feature is aimed at both scripted workflows and interactive debugging, eliminating the need for an explicit `git bisect reset`.

The v2 patch series, posted by Harald Nordgren, is now under review and remains uncontroversial. The design settled after Junio C Hamano suggested making the option parameterized (`--auto-reset=<where>`) rather than a simple boolean flag, accommodating both automated and interactive use cases. The series consists of three patches: a preparatory refactoring of `print_file_to_stdout` to avoid reopening files by name, plumbing to support quiet checkouts in `bisect_reset`, and the core implementation of `--auto-reset`. All three patches are technically sound, with thorough test coverage and no outstanding technical objections.

The only open question is a minor naming suggestion from Johannes Sixt, who proposed `--reset-when-found` to make the timing clearer, though this doesn’t affect the implementation. A new review comment from Sixt now raises a platform-specific concern about the refactoring in the first patch: the commit message implies that the change avoids issues with files being deleted while open, but on Windows, deleting an open file is normally impossible. Sixt asks whether the Windows port has evolved to allow this, or if the commit message is overstating the risk. This is a technical clarification request rather than a design objection, and the author may adjust the commit message to avoid implying a cross-platform issue where none exists. The series is otherwise ready for integration.
