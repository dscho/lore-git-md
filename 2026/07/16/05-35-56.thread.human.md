This thread is about a small but useful enhancement to `git bisect`: a new `--auto-reset=<where>` option that automatically returns the working tree to a specified commit after the bisect identifies the first bad commit. The feature is aimed at both scripted workflows (like CI pipelines) and interactive debugging, eliminating the need for an explicit `git bisect reset`.

The author, Harald Nordgren, has posted a second version of the three-patch series, incorporating feedback from Junio C Hamano to make the option parameterized (`original` or `found`) rather than a simple boolean flag. The first two patches—preparatory refactoring and plumbing for quiet checkouts—are uncontroversial and ready for integration. The third patch, which implements the core functionality, has just been posted and is now under review. It handles state persistence, enforces constraints (like the incompatibility with `--no-checkout`), and performs the quiet reset when the bisect completes. The test coverage is thorough, covering both happy paths and edge cases.

Junio has already settled the design, and the implementation aligns with the agreed approach. The only practical limitation noted is that users who want to conditionally reset based on the bisect outcome (e.g., choosing between `original` and `found` after seeing the result) will still need to handle the reset manually, as the option requires the target to be specified upfront. No other open questions or objections have surfaced, and the series appears to be on track for merging once the final patch receives a clean review.
