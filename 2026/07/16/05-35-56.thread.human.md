This thread introduces a new `--reset-when-found[=<where>]` option for `git bisect`, allowing users to automatically reset the working tree after identifying the first bad commit. The feature is designed for automated workflows and interactive debugging, with the reset target configurable as either the original pre-bisect commit (`original`, the default) or the first bad commit itself (`found`). The v4 patch series, authored by Harald Nordgren, has been marked for integration into Junio C Hamano’s `next` branch and is uncontroversial, with all substantive feedback addressed.

The series consists of two patches: a preparatory plumbing change adding a `quiet` parameter to `bisect_reset()`, and the core implementation wiring the new option into the bisect state machine and CLI. Johannes Sixt’s review raised minor issues around error message boilerplate, shell safety in tests, and test cleanup chaining, all of which have been resolved in this version. Junio noted a practical limitation—the reset target must be specified upfront, preventing conditional choices based on the bisect outcome—but this does not affect the feature’s readiness.

Junio’s latest review suggests a targeted refactoring to improve the internal code structure by centralizing the auto-reset logic and decoupling `bisect_clean_state()` from `bisect_reset()`. While this would enhance maintainability, it is not a blocker for integration, and the series remains on track for `next`. The only remaining loose end is whether the author or another contributor will implement this refactoring in a follow-up patch.
