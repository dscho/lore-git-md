This thread is about a small but useful addition to `git bisect`: a `--reset-when-found` option that automatically resets the working tree after the bisect identifies the first bad commit. The feature is aimed at automated workflows and interactive debugging, letting users specify whether to reset to the original pre-bisect state or leave the working tree on the bad commit.

The series is now at version 4, with the design settled and all substantive feedback addressed. Junio C Hamano has marked it for integration into `next`, meaning it’s considered technically sound and ready for wider testing. The series consists of two patches: the first refactors `bisect_reset()` to accept a `quiet` parameter (a preparatory change), and the second implements the core feature, including CLI wiring, state persistence, and the auto-reset logic. Johannes Sixt’s review raised minor issues—error message boilerplate, shell safety in tests, and test cleanup chaining—which the author has now fully addressed in this version.

The only remaining loose end is a trivial suggestion from Junio to change the `quiet` parameter’s type from `int` to `bool` for consistency with the next patch. This is purely stylistic and doesn’t affect the feature’s readiness. The series is uncontroversial and should land in `next` soon.
