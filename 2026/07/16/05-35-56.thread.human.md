This thread introduces a new `--reset-when-found[=<where>]` option for `git bisect`, which automatically resets the working tree after identifying the first bad commit—either to the original pre-bisect state (`original`, the default) or to the found commit itself (`found`). The feature is designed for automated workflows and interactive debugging, eliminating the need for an explicit `git bisect reset`. The v4 patch series, authored by Harald Nordgren, has been marked for integration into Junio C Hamano’s `next` branch and is uncontroversial, with all substantive feedback addressed.

The series consists of two patches: a preparatory plumbing change to `bisect_reset()` and the core implementation. Junio and reviewer Johannes Sixt settled on the parameterized design (`--reset-when-found[=<where>]`) early in the discussion, and the author has since addressed all remaining feedback, including shell safety fixes in tests and error message standardization. Junio noted a practical limitation: users cannot conditionally choose the reset target based on the bisect outcome, as the target must be specified upfront. He also suggested two surface-level improvements—changing a parameter type from `int` to `bool` and refactoring the internal state machine—but neither blocks integration.

In the latest email, Junio proposes a more significant refactoring to simplify the state machine by centralizing the auto-reset logic in the top-level `cmd_bisect()` function. This would eliminate the `defer_reset` parameter and repeated filesystem checks, making the code easier to maintain. The proposal is framed as a question and does not challenge the feature’s readiness; the series remains on track for `next`. If the author or another contributor agrees, this could become a follow-up patch. The discussion is now focused on implementation trade-offs rather than the feature’s design.
