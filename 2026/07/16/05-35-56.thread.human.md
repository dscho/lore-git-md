This thread introduces a new `--reset-when-found[=<where>]` option for `git bisect`, designed to automate the reset step after identifying the first bad commit. The feature is now complete in its sixth iteration, refined into a clean two-patch series that addresses all maintainer feedback. Harald Nordgren authored the series, with Junio C Hamano providing the final review and internal clean-ups.

The option allows users to specify whether the working tree should reset to the original pre-bisect commit (`original`, the default) or remain on the first bad commit (`found`). This targets automated workflows like CI pipelines and interactive debugging sessions, eliminating the need for an explicit `git bisect reset`. The implementation is centralized in `cmd_bisect()`, which now reads `refs/bisect/bad` directly to avoid relying on a static variable, and uses a sentinel value to track the reset target. The preparatory patch refactors `bisect_reset()` to accept a `quiet` parameter, suppressing progress output during automated resets.

Junio’s final review confirmed the patch is technically sound, with only minor stylistic suggestions—such as splitting style clean-ups into a separate patch—that don’t block integration. The series is ready for `next`, with no open questions or conflicts with other in-flight work. Test coverage validates edge cases, including invalid targets and conflicts with `--no-checkout`. The feature is now poised for graduation to `master` in the current cycle.
