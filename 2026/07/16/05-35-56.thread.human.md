This thread introduces a new `--reset-when-found[=<where>]` option for `git bisect`, allowing users to automatically reset the working tree after a bisect completes. The feature is now in its third iteration (v3), posted by Harald Nordgren via GitGitGadget, and is ready for final review.

The option lets users specify whether to reset to the original pre-bisect commit (`original`, the default) or leave the working tree on the first bad commit (`found`). This eliminates the need for a manual `git bisect reset`, making it useful for both automated workflows and interactive debugging. The implementation is straightforward: the chosen target is stored in a state file, and the reset is deferred until after `git bisect run` finishes to avoid platform-specific issues with open files. The series enforces that `--reset-when-found` cannot be used with `--no-checkout`, as that mode prevents checking out either target.

The design has settled after feedback from Junio C Hamano and Johannes Sixt, who helped refine the option name and behavior. The v3 series drops an earlier preparatory refactor and focuses on the core feature, addressing platform-compatibility concerns by reverting to filename-based output handling. All design decisions are now final, and the series includes thorough test coverage for both targets, edge cases, and constraints. The only remaining limitation is that users cannot conditionally choose the reset target based on the bisect outcome, but this is a reasonable trade-off for simplicity. The patches are uncontroversial and ready for integration.
