This thread is about adding an `--auto-reset` option to `git bisect` to automate the reset step after identifying the first bad commit, primarily for use in scripts and CI pipelines. The series, posted by Harald Nordgren as v1, initially implemented the option as a boolean flag that resets the working tree to the original pre-bisect commit. However, Junio C Hamano, the maintainer, has raised a fundamental design concern: he expects the option to leave the working tree on the first bad commit (the culprit) instead, as this would better serve interactive debugging workflows.

The discussion has now evolved into a proposed redesign. Junio suggests making `--auto-reset` a parameterized option (`--auto-reset=<where>`) with values `original` (reset to the pre-bisect commit) or `found` (stay on the first bad commit), defaulting to `original` if no value is specified. This would make the feature flexible enough for both automated and interactive use cases. The preparatory refactoring (patch 1) and the quiet-checkout addition (patch 2) are uncontroversial and would remain unchanged, but the core logic, documentation, and tests for the `--auto-reset` option would need to be revised. The thread is currently waiting for Harald’s response to this proposal, and no other reviewers have weighed in on the parameterized design. The outcome will determine whether the feature becomes a versatile tool or remains narrowly focused on automated workflows.
