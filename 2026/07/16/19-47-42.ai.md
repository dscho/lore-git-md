This is a **bug report and feature request** about `git submodule` behavior with sparse-checkout.

Brad Larson reports that when using `git sparse-checkout` to limit the working tree to a subset of files (e.g., only `src/doc` in the Rust repository), `git submodule update --init` still initializes *all* submodules, not just those within the sparse-checkout cone. This defeats the purpose of sparse-checkout for repositories with many submodules, as the user ends up with a full checkout of submodules they don’t need.

The reproduction steps are clear: clone a large repository (Rust) with `--filter=blob:none --no-checkout`, set a sparse-checkout pattern, check out the branch, and then run `git submodule update --init`. The result is that submodules outside the sparse-checkout cone are still initialized, which Brad argues is counterintuitive.

Brad asks whether the maintainers would be open to a patch that makes `git submodule` respect the sparse-checkout configuration, so it only interacts with submodules whose paths fall within the sparse-checkout cone. No patch is provided yet—this is an RFC-style inquiry about whether the idea is welcome in principle. The tone is polite and constructive, framing the issue as a usability gap rather than a bug in the strict sense.
