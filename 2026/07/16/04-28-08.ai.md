This is a **performance analysis and optimization proposal** for the `git last-modified` command, authored by Jeff King (Peff) in response to a performance inquiry from a Forgejo contributor.

Peff reproduces the reported 2.5× slowdown (66 ms vs 26 ms) and identifies the root cause: `git last-modified` inefficiently checks every path in the target directory against every commit’s changed-path Bloom filter, resulting in 290 × 39,000 filter comparisons for the `doc/langref/` example. In contrast, `git log` uses a single Bloom filter key derived from the pathspec, narrowing the commit set to only those that likely touch the directory.

Peff attaches a **proof-of-concept patch** that refactors `last-modified` to reuse the Bloom filter logic from `revision.c`, pre-filtering commits with the original pathspec. The patch reduces runtime from 64 ms to 16 ms on his machine, making `last-modified` slightly faster than the hand-rolled `git log` pipeline. The patch exposes an internal `revision.c` helper (`prepare_to_use_bloom_filter`) and adds a new wrapper (`filter_contains_keyvec`) to check whether a commit’s Bloom filter contains any of the pathspec-derived keys.

Key technical details: the patch touches `builtin/last-modified.c`, `revision.c`, and `revision.h`; it introduces no new user-visible options or behavior changes; it relies on the existing commit-graph and changed-path Bloom filter infrastructure. Peff notes several open questions—edge cases with non-literal pathspecs, potential regressions in repositories where the target directory is frequently modified, and whether GitHub’s internal `blame-tree` implementation already solved this problem—but does not plan to drive the patch further himself. He cc’s Taylor Blau, suggesting GitHub’s team may have relevant experience.
