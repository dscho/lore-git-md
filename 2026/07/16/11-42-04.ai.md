This is a **performance optimization follow-up** for the `git last-modified` command, part of the ongoing thread comparing its speed to a hand-rolled `git log` pipeline. Toon Claes, the command’s author, responds to Jeff King’s (Peff) proof-of-concept patch that demonstrated a 4× speedup by reusing Bloom filter logic from `revision.c`.

Toon confirms the performance gap Peff identified and reports additional benchmarking on GitLab’s repositories. On `gitlab-org/gitlab` (a Rails monorepo with ~530k commits), the patch reduces runtime for the `app/` directory (touched in ~35% of commits) from 435 ms to 278 ms (1.56× faster). On `gitlab-org/gitaly` (~23k commits), it improves performance for `internal/` (touched in ~58% of commits) from 13.2 ms to 9.9 ms (1.33× faster), and recursive queries also see a 1.13× speedup. These results suggest the optimization is robust across different repository shapes and commit patterns, with no observed regressions.

Technically, Toon acknowledges Peff’s analysis of the inefficiency—checking every path in the target directory against every commit’s Bloom filter—and agrees with the proposed solution: pre-filtering commits using the original pathspec. He notes that his own experiments with an AI assistant arrived at a similar approach but plans to adopt Peff’s cleaner refactoring, which exposes an internal `revision.c` helper (`check_maybe_different_in_bloom_filter`). Toon explicitly commits to coordinating with Peff on a unified patch series, resolving the earlier uncertainty about who would drive the effort.

The email leaves two open technical questions: (1) whether the patch handles non-literal pathspecs (e.g., `*.c`)—Toon defers this as out of scope—and (2) whether GitHub’s internal `blame-tree` implementation (the inspiration for `last-modified`) already solved this problem, which remains unanswered. The patch itself touches `builtin/last-modified.c`, `revision.c`, and `revision.h`, introducing no user-visible changes but relying on existing commit-graph and Bloom filter infrastructure.

This is a **substantive, well-motivated optimization** with clear real-world impact, particularly for GitLab’s use case (batching 25 files at once). The coordination between Toon and Peff, combined with the demonstrated speedups, suggests the patch is likely to land smoothly. The only potential friction could come from exposing internal `revision.c` helpers, but Toon’s willingness to refactor suggests this will be addressed. The thread is now poised for a v2 patch series.
