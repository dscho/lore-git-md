Thread identity: `[PATCH v3]` series adding seven new path-related keys (`path.toplevel`, `path.superproject-working-tree`, `path.objects`, `path.hooks`, `path.index`, `path.grafts`, `path.git-prefix`) to the `git repo info` command. Originating author: K Jayatheerth (GSoC contributor). Thread type: feature patch series. Current version: 4 (in preparation; v3 complete but blocked on forward-compatibility, mechanical nits, and substantive design questions about ODB abstraction and `/dev/null` handling).

Core problem or goal: Expose filesystem locations of repository components (e.g., hooks directory, index file, grafts file, superproject working tree, object database, and the relative path from the top-level working tree to the current directory) in a user-facing, scriptable format via `git repo info`. The new keys mirror existing internal Git struct fields but avoid requiring direct access to Git’s internals. Each key supports suffix-based formatting (e.g., absolute vs. relative paths) where applicable.

Current status: Third submission (version 3) complete but blocked by multiple issues: a forward-compatibility issue in patch 1/7 (use of `startup_info->prefix`, removed from `master`), minor mechanical nits across patches 1/7–4/7, and two substantive design questions: (1) the long-term viability of exposing the object database directory in light of pluggable ODB backends, and (2) how the `path.hooks` keys should handle the special `/dev/null` value for `core.hooksPath`. Junio C Hamano has acknowledged the series as mechanically clean and free of glaring design issues, explicitly inviting substantive technical review from the broader community. The v3 iteration is functionally identical to v2 but adds documentation clarifications for `path.index` and `path.grafts` to explicitly state their behavior in edge cases (bare repositories and non-existent files). The behavioral design for `path.hooks`, `path.index`, and `path.grafts` is settled: all three keys return paths unconditionally, even when the file or directory does not exist or the repository is bare, aligning with `git rev-parse --git-path` precedent. The series remains under active review; no merge status is reported. **New developments**:
- The forward-compatibility issue in patch 1/7 (use of `startup_info->prefix`) will be resolved in v4 by rebasing onto `master` and replacing the deprecated field with the new `repo` struct prefix field (introduced by Patrick Steinhardt).
- All mechanical nits raised by Justin Tobler (redundant `strbuf_addstr(buf, "")` calls, incomplete test coverage for `path.toplevel.relative` in bare repositories, and the `format_path()` call in `path.objects.absolute`) have been accepted and will be addressed in v4.
- The commit messages for patches 3/7 and 4/7 have been revised to use broader phrasing ("Scripts operating on a repository" instead of "Tools and deployment hooks") and to clarify "legacy parsing methods" as manual parsing of `git rev-parse --git-dir` or `.git/config`.
- The `/dev/null` handling question for `path.hooks` is now partially resolved: Jayatheerth argues against special-casing `/dev/null` to return an empty string, citing consistency with `git rev-parse --git-path hooks`, the series’ design principle of using empty strings only for inapplicable contexts, and the need for scripts to handle `/dev/null` literally. He proposes documenting the behavior and adding a test to lock it in. This aligns with the series’ broader goal of mirroring `git rev-parse` behavior where possible.
- The naming question for `path.superproject-working-tree` remains open, though Jayatheerth now leans toward Justin’s suggestion of `superproject-root` for brevity and clarity, while deferring to consistency with `git rev-parse --show-superproject-working-tree`.

Key technical details:
- Files touched: `builtin/repo.c` (implementation), `Documentation/git-repo.adoc` (documentation), `t/t1900-repo-info.sh` (tests).
- New symbols: Twenty-one new keys with suffix-based formatting support: `path.toplevel.absolute`, `path.toplevel.relative`, `path.superproject-working-tree.absolute`, `path.superproject-working-tree.relative`, `path.objects.absolute`, `path.objects.relative`, `path.hooks.absolute`, `path.hooks.relative`, `path.index.absolute`, `path.index.relative`, `path.grafts.absolute`, `path.grafts.relative`, and `path.git-prefix`. The first three patches (1/7–3/7) implement `path.toplevel`, `path.superproject-working-tree`, and `path.objects` using `repo_get_work_tree()`, `get_superproject_working_tree()`, `repo_get_object_directory()`, and `format_path()`. Patch 4/7 implements `path.hooks.absolute` and `path.hooks.relative` using `repo_git_path_replace()` and `format_path()`, respecting the `core.hooksPath` environment/config override. Patches 5/7 and 6/7 implement `path.index` and `path.grafts` using `repo_get_index_file()`, `repo_get_graft_file()`, and `format_path()`. Patch 7/7 adds `path.git-prefix` via the deprecated `startup_info->prefix` (to be replaced with the new `repo` struct field in v4).
- Behavior: Keys return filesystem paths (absolute or relative) for repository components, matching internal Git struct fields. In bare repositories or when not inside a submodule, the respective keys return an empty string, except for `path.index`, `path.grafts`, and `path.hooks`, which return paths unconditionally (even when the file or directory does not exist or the repository is bare). The `path.objects`, `path.index`, `path.grafts`, and `path.hooks` keys respect the `GIT_OBJECT_DIRECTORY`, `GIT_INDEX_FILE`, `GIT_GRAFT_FILE`, and `core.hooksPath` environment/config overrides, respectively. The `path.git-prefix` key returns the relative path from the top-level working tree to the current directory, including a trailing slash (empty string at the root). The `path.hooks` keys now explicitly document that they return `/dev/null` verbatim when `core.hooksPath` is set to that value, matching `git rev-parse --git-path hooks` behavior.

Open questions and loose ends:
- **Substantive design question about ODB abstraction**: Justin Tobler raises a forward-looking concern about the `path.objects` keys: they assume a filesystem-backed object database, which may not hold true if pluggable ODB backends (e.g., non-filesystem stores) are introduced. He suggests that the keys could return an empty string in such cases, but also questions whether exposing the object directory location is appropriate at all if it becomes an internal detail of a specific ODB backend. Patrick Steinhardt (ODB abstraction effort lead) has been CC’d for input. This remains an open question.
- **Key naming and suffix semantics**: Reviewers may suggest adjustments for consistency with existing Git terminology (e.g., `path.objectdir` instead of `path.objects`, `path.hookdir` instead of `path.hooks`, `path.index-file` instead of `path.index`, `path.graft-file` instead of `path.grafts`, `superproject.root` instead of `superproject-working-tree`, or alignment of `path.git-prefix` with `gitdir`/`commondir` terminology). The specific question of whether to rename `path.superproject-working-tree` to `superproject-root` remains open, though Jayatheerth now leans toward the latter for brevity and clarity while deferring to consistency with `git rev-parse --show-superproject-working-tree`.
- **Substantive technical review**: The series remains open for in-depth review by the broader community, following Junio’s invitation. Junio’s recent meta-review comment encourages reviewers to provide more detailed positive feedback, noting that "Acked-by" carries more weight when accompanied by evidence of substantive engagement (e.g., tracing the patch’s logic or explaining the reviewer’s reasoning).
