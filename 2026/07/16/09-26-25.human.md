This is a performance discussion about the `git last-modified` command, with a focus on closing the speed gap compared to a hand-rolled `git log` pipeline. Toon Claes, the command's author, acknowledges the performance issue Gusted reported—where `git last-modified` is 2.5× slower (66 ms vs 26 ms) on a single directory in the ziglang/zig repository—and explains why GitLab hasn't prioritized optimizing this case: their typical use involves batching many files at once, where `last-modified` already outperforms the alternative.

Toon notes he was already working on improvements (with AI assistance) when Jeff King (Peff) sent a proof-of-concept patch that addresses the root cause—inefficient Bloom filter usage in `last-modified`—and achieves a 4× speedup (64 ms → 16 ms). He plans to coordinate with Peff to combine their efforts into a patch series. The thread remains under active review, with no integration branch yet, but the technical path forward is clear: reuse the Bloom filter logic from `revision.c` to pre-filter commits, avoiding the current brute-force approach.
