This thread is about a Google Summer of Code contributor’s patch series, now at version 4, that adds six new path-related keys to the `git repo info` command. The keys expose filesystem locations of repository components—such as the hooks directory, index file, grafts file, superproject root, and the relative path from the top-level working tree to the current directory—in a scriptable format. The series has been mechanically cleaned up and is ready for substantive technical review, but one design question remained unresolved: whether `path.git-prefix` belongs in the command at all.

Junio C Hamano has now weighed in, siding with the author and rejecting the objection that `path.git-prefix` represents "current directory information" rather than "repository information." He analogizes it to existing keys like `path.commondir.relative` and `git rev-parse --show-cdup`, arguing that both are inherently about the repository’s structure, just expressed relative to the current working directory. To complete the symmetry, Junio proposes adding a new `path.cdup` key that would return the relative path *to* the working tree root from the current directory, mirroring `path.git-prefix`’s role as the path *from* the root. This effectively resolves the primary blocker, shifting the discussion toward implementing the new key rather than debating its inclusion.

The series is otherwise uncontroversial. All mechanical issues have been addressed, and the author has incorporated feedback on naming, test coverage, and edge cases like `/dev/null` handling for hooks. The only remaining open questions are minor: whether to adjust key names for consistency with existing Git terminology (e.g., `path.hookdir` instead of `path.hooks`) and how to implement `path.cdup`. The author has already signaled willingness to drop `path.git-prefix` if reviewers objected, but Junio’s intervention makes that unlikely. The next steps will likely involve a v5 series adding `path.cdup` and any final naming tweaks.
