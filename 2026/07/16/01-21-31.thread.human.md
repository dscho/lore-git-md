This thread is about a Google Summer of Code contributor’s patch series adding seven new path-related keys to `git repo info`, exposing filesystem locations of repository components like the hooks directory, index file, and object database. The series is now at version 3, with a fourth version in preparation to address a forward-compatibility issue and minor mechanical nits.

The core goal is to make these paths available in a scriptable format, mirroring internal Git struct fields without requiring direct access to Git’s internals. The design for most keys is settled—returning paths unconditionally, even in bare repositories or when files don’t exist—but a new substantive question has emerged about the `path.objects` keys in light of pluggable ODB backends. Justin Tobler raised this concern, questioning whether exposing the object directory location is future-proof if Git moves to non-filesystem backends. Patrick Steinhardt, the ODB abstraction effort lead, has been looped in but hasn’t yet responded.

The latest review from Justin focuses on the `path.hooks` keys, specifically how they should handle the special `/dev/null` value for `core.hooksPath`. Currently, the patch returns `/dev/null` verbatim (matching `git rev-parse --git-path hooks`), but Justin suggests returning an empty string for the relative-path variant to avoid confusion. This is a nuanced edge-case discussion rather than a blocker, but it highlights the need for consistency with existing Git behavior. The author, K Jayatheerth, has confirmed plans to address the forward-compatibility issue in patch 1/7 and other minor nits in a v4 update, but the ODB abstraction question and the `/dev/null` handling remain open for discussion. Junio has invited broader technical review, emphasizing the importance of substantive engagement.
