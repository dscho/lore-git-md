This thread is about a Google Summer of Code contributor’s patch series, `[PATCH v3]`, that adds seven new path-related keys to the `git repo info` command. These keys expose filesystem locations of repository components—such as the hooks directory, index file, grafts file, and object database—in a scriptable format, mirroring internal Git struct fields without requiring direct access to Git’s internals. The series is now in its third version, functionally identical to v2 but with added documentation clarifications for edge cases like bare repositories.

Junio C Hamano, the maintainer, has acknowledged the v3 series, confirming that his earlier design concerns are resolved and the patches are mechanically clean. He has explicitly invited broader technical review from the community, signaling that the series is ready for deeper scrutiny but not yet merged. The behavioral design for `path.hooks`, `path.index`, and `path.grafts` is settled: all return paths unconditionally, even when the file or directory doesn’t exist or the repository is bare, aligning with `git rev-parse --git-path` precedent. The series touches `builtin/repo.c`, the documentation, and adds comprehensive tests.

The main open question remains whether the key naming and suffix semantics (e.g., `path.objects` vs. `path.objectdir`, `path.hooks` vs. `path.hookdir`) are sufficiently consistent with existing Git terminology. While Junio is supportive of the current design for the three settled keys, Lucas Seiki Oshiro had previously suggested returning empty strings in bare repositories for `path.index`, though this was resolved in favor of the unconditional behavior. The series is now awaiting substantive technical feedback from other contributors.
