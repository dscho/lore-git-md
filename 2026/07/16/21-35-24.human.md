This is the final exchange in Christian Couder’s seven-patch series refactoring `git fast-import`’s usage string and laying groundwork for libification. Junio’s reply is a substantive review of the last patch (7/7), which replaces the hand-written usage string with a `struct option` array.

The core issue Junio raises is the awkwardness of the current implementation: the patch defines a full `struct option` array for help-text generation but leaves the actual option parsing to the existing `parse_one_option()` and `parse_one_feature()` functions. This results in a long list of unused, uninitialized local variables (like `pack_size_limit`, `date_format`, etc.) that serve only as placeholders for the help system. Junio acknowledges the series’ stated scope—improving `-h` output—but suggests the patch stops just short of a more natural endpoint: having `fast_import_state_init()` (or a similar helper) use the new `struct option` array to parse arguments, eliminating the need for throwaway locals.

He proposes a small but meaningful extension: instead of creating temporary variables, the options array should reference the existing global variables (e.g., `max_packsize` instead of `pack_size_limit`). This would avoid the "sour taste" of unused locals while keeping the patch aligned with the series’ goals. The suggestion is pragmatic rather than a demand for a full rewrite—Junio frames it as bending the scope slightly to reach a cleaner stopping point.

No objections to the technical approach are raised; the feedback is about polish and future-proofing.
