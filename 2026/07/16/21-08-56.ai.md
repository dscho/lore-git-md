This is a maintainer review of the first patch in Siddharth Shrimali’s RFC series introducing `git repack --drop-filtered`. Junio’s feedback is **substantive** and identifies a **logical flaw** in the option validation logic.

The core issue: the patch checks for `--drop-filtered`’s incompatibility with `--write-bitmap-index` (`-b`) *after* `write_bitmaps` may have already been set by repository configuration (e.g., `repack.writeBitmaps=true`). This means the check cannot distinguish between a user explicitly requesting bitmaps on the command line (which should be rejected) and bitmaps being enabled by default (which should be silently disabled). Junio points out that the validation happens too late in the control flow—after `parse_options()` and `repo_config()` have already set `write_bitmaps`—so the patch cannot enforce the intended safety constraint.

The review is concise but precise: it names the specific variable (`write_bitmaps`), traces the execution path (lines 245–247 in `builtin/repack.c`), and explains why the current placement of the check is ineffective. No alternative implementation is suggested, but the implication is clear: the validation must move earlier, before configuration is read, or the logic must be restructured to distinguish between command-line and config-driven bitmap settings.

This is a **blocking issue** for the series: the safety mechanism designed to prevent bitmap corruption is itself broken. The author will need to address it before the feature can be considered for integration. The rest of the patch (precondition checks for `--filter`, `-a`, promisor remote, and `--dry-run`) is not commented on, suggesting it is uncontroversial or will be revisited once the bitmap issue is fixed.
