Subject: [PATCH 0/3] bisect: add --reset-when-found option
Series version: v4
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series (feature addition)

Core problem or goal
Introduce a `--reset-when-found[=<where>]` option to `git bisect` that automatically resets the working tree to a user-specified commit after the bisect identifies the first bad commit. The parameter `<where>` accepts `original` (reset to the pre-bisect commit, the default) or `found` (leave the working tree on the first bad commit). The feature targets automated workflows (scripts, CI pipelines) and interactive debugging by eliminating the need for an explicit `git bisect reset`.

Current status
The v4 patch series has been marked for integration into `next` by Junio C Hamano. The series consists of two patches: (1) a preparatory plumbing change adding a `quiet` parameter to `bisect_reset()`, and (2) the core feature implementation (auto-reset logic, state persistence, and CLI wiring). The design is settled, with the rename from `--auto-reset` to `--reset-when-found` and the deferred reset behavior for `git bisect run` retained. Junio noted a practical limitation: users whose desired reset target depends on the bisect outcome (e.g., conditionally choosing between `original` and `found`) may need to forgo the option and manually reset afterward, as the target must be specified upfront. The series is uncontroversial, with all substantive and surface-level feedback addressed. Johannes Sixt’s review raised minor issues (error message boilerplate, shell safety in tests, test cleanup chaining) that the author has now fully addressed in this version. Junio has since proposed a significant internal refactoring to simplify the state machine by centralizing the auto-reset logic in the top-level `cmd_bisect()` function, eliminating the `defer_reset` parameter, and decoupling `bisect_clean_state()` from `bisect_reset()`. The refactoring would involve: (1) stopping calls to `bisect_clean_state()` from `bisect_reset()`, (2) making all `cmd_bisect__<subcommand>` functions return their result codes instead of calling `exit()`, (3) having `bisect_next_all()` report the found commit via a file-scope static variable, and (4) handling the auto-reset in `cmd_bisect()` when it receives `BISECT_INTERNAL_SUCCESS_1ST_BAD_FOUND`. The proposal is framed as a question and does not challenge the feature’s readiness for `next`; the series remains marked for integration pending a decision on whether to adopt the refactoring before merging.

Key technical details
- Files touched: `bisect.c`, `builtin/bisect.c`, `Documentation/git-bisect.adoc`, `t/t6030-bisect-porcelain.sh`.
- New CLI option: `--reset-when-found[=<where>]` (parameterized; values `original` or `found`; default `original`). The boolean form (`--auto-reset`) is deprecated.
- Behavior: After `git bisect` identifies the first bad commit, the working tree is automatically reset to the commit specified by `<where>`. The default (`original`) preserves the original pre-bisect state; `found` leaves the working tree on the first bad commit (the culprit). For `git bisect run`, the reset is deferred until after the captured output is printed and the `BISECT_RUN` file is closed, addressing platform-compatibility concerns about unlinking open files.
- Internal changes: `bisect_reset()` now accepts a `quiet` parameter (added in patch 1/2) to suppress checkout output, with all callers updated to pass `0` (false) to maintain current behavior. Junio suggested changing the type of `quiet` from `int` to `bool` for consistency with the `defer_reset` parameter introduced in patch 2/2. The `BISECT_RESET_WHEN_FOUND` state file stores the target commit (`original` or `found`). If `<where>` is `found`, the reset step is omitted entirely. The option is wired into both `git bisect start` and `git bisect run`. Junio’s refactoring proposal would: (1) stop calling `bisect_clean_state()` from `bisect_reset()`, (2) move that cleanup to the callers that need it, (3) store the parsed auto-reset mode in a variable (like `struct bisect_terms`) to centralize the logic and eliminate repeated filesystem checks, and (4) restructure the top-level `cmd_bisect()` function to handle the auto-reset after receiving `BISECT_INTERNAL_SUCCESS_1ST_BAD_FOUND` from `bisect_next_all()` via a file-scope static variable. The `defer_reset` parameter would be eliminated under this design.
- Constraints: `--reset-when-found` cannot be used with `--no-checkout`, as that mode prevents checking out either target. The error message for this conflict uses Git’s standard dual-option template (`"options '%s' and '%s' cannot be used together"`), reducing translation overhead.
- Test coverage: Four new tests in `t/t6030-bisect-porcelain.sh` validate auto-reset behavior for both `original` and `found`, state cleanup, and edge cases (invalid targets, `--no-checkout` conflicts, interrupted bisects, quiet parameter handling in error paths). Shell safety issues in the test helpers (`test_bisect_state_file` and `test_bisect_state_missing`) have been fixed by assigning `git rev-parse` output to a variable before passing it to `test_path_is_file`/`test_path_is_missing`, avoiding potential silent failures.
- No on-disk format changes or new symbols introduced beyond the state file updates.

Open questions and loose ends
Junio’s refactoring proposal to simplify the internal state machine by centralizing the auto-reset logic in the top-level `cmd_bisect()` function, eliminating the `defer_reset` parameter, and decoupling `bisect_clean_state()` from `bisect_reset()` remains open. The proposal is framed as a question and does not block integration, but it may prompt a follow-up patch if the author or another contributor agrees the change would improve maintainability. The only unaddressed item from prior reviews—joining `test_when_finished` commands with `&&`—is mechanical and does not affect the feature’s core logic or integration status.
