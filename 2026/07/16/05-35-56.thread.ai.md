Subject: [PATCH 0/3] bisect: add --reset-when-found option
Series version: v3 (pending author update)
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series (feature addition)

Core problem or goal
Introduce a `--reset-when-found=<where>` option to `git bisect` that automatically returns the working tree to a user-specified commit after the bisect identifies the first bad commit. The parameter `<where>` accepts `original` (reset to the pre-bisect commit, the default) or `found` (leave the working tree on the first bad commit). The feature targets both automated workflows (scripts, CI pipelines) and interactive debugging by eliminating the need for an explicit `git bisect reset`.

Current status
v2 patch series posted and under review; v3 pending to incorporate the agreed rename from `--auto-reset` to `--reset-when-found`. The design is settled, including Junio C Hamano’s proposal to convert the original boolean flag into a parameterized option. All three patches remain uncontroversial and ready for integration: patch 1 (preparatory refactoring of `print_file_to_stdout`) refactors `print_file_to_stdout()` to `print_fd_to_stdout()` by reading from an already open file descriptor instead of reopening the `BISECT_RUN` file by name, avoiding potential file accessibility issues and enabling the feature; patch 2 (quiet-checkout plumbing in `bisect_reset`) extends the function signature and updates callers without altering existing behavior; patch 3 (implementation of `--reset-when-found`) delivers the core functionality, enforces the `--no-checkout` constraint, and includes thorough test coverage. The series enforces that `--reset-when-found` cannot be used with `--no-checkout`, as that mode prevents checking out either target. Junio has noted a practical limitation: users whose desired reset target depends on the bisect outcome (e.g., conditionally choosing between `original` and `found`) may need to forgo the option and manually reset afterward, as the target must be specified upfront. Johannes Sixt’s platform-compatibility concern about the refactoring in patch 1 remains unresolved; the author may need to clarify the motivation or adjust the commit message to avoid implying a cross-platform issue where none exists.

Key technical details
- Files touched: `bisect.c`, `builtin/bisect.c`, `Documentation/git-bisect.adoc`, `t/t6030-bisect-porcelain.sh`.
- New CLI option: `--reset-when-found=<where>` (parameterized; values `original` or `found`; default `original`). The boolean form (`--auto-reset`) is deprecated.
- Behavior: After `git bisect` identifies the first bad commit, the working tree is automatically reset to the commit specified by `<where>`. The default (`original`) preserves the original pre-bisect state; `found` leaves the working tree on the first bad commit (the culprit).
- Internal changes: `print_file_to_stdout()` refactored to `print_fd_to_stdout()` (opened with `O_RDWR`, seek to start before copying to stdout); `bisect_reset()` now accepts a `quiet` parameter to suppress checkout output, with all callers updated to pass `0` (false) to maintain current behavior. The `BISECT_AUTO_RESET` state file stores the target commit (`original` or `found`) rather than a boolean flag. If `<where>` is `found`, the reset step is omitted entirely. The option is wired into both `git bisect start` and `git bisect run`.
- Constraints: `--reset-when-found` cannot be used with `--no-checkout`, as that mode prevents checking out either target.
- Test coverage: Four new tests in `t/t6030-bisect-porcelain.sh` validate auto-reset behavior for both `original` and `found`, state cleanup, and edge cases (invalid targets, `--no-checkout` conflicts, interrupted bisects, descriptor errors, seek failures, quiet parameter handling in error paths).
- No on-disk format changes or new symbols introduced beyond the state file updates.

Open questions and loose ends
One unresolved item remains: Johannes Sixt’s platform-compatibility concern about the refactoring in patch 1, questioning whether the commit message’s claim that the change avoids needing the file to be "reachable by name" is accurate on Windows, where deleting an open file is normally impossible. The author may need to clarify the motivation or adjust the commit message to avoid implying a cross-platform issue where none exists.

Participant positions
- Harald Nordgren (author): Implemented the parameterized design (`--reset-when-found=<where>`) as agreed in the v1 discussion. The refactoring in patches 1 and 2 (preparatory changes and quiet-checkout plumbing) are motivated by technical needs (avoiding file reopens, reducing output noise) and remain uncontroversial. Patch 3 delivers the core functionality with thorough test coverage and is ready for review.
- Junio C Hamano (maintainer): Proposed and settled the parameterized design (`--reset-when-found=<where>` with values `original` or `found`), accommodating both automated workflows (reset to original) and interactive debugging (leave on first bad commit). The default (`original`) aligns with the author’s original use case. Junio has noted the refactoring in patch 1 is clean and necessary, using `O_RDWR` to allow seeking, and considers the theoretical seek failure edge case unlikely to be a practical regression. He has also noted that the feature’s flexibility comes with a practical limitation: users cannot rely on the option alone if their desired reset target depends on the bisect outcome, as the target must be specified upfront. Junio agreed with Johannes Sixt that `--reset-when-found` is an improvement over `--auto-reset` because it makes the timing explicit in the option name.
- Johannes Sixt (reviewer): Suggested renaming the option to `--reset-when-found` to make the timing explicit in the option name. The feedback was accepted by Junio and is now settled. Additionally, raised a platform-compatibility concern about the refactoring in patch 1, questioning whether the commit message’s claim about avoiding file reopens is accurate on Windows, where deleting an open file is normally impossible. The concern targets the rationale for the refactoring rather than its implementation.
