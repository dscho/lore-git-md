Subject: [PATCH 0/3] bisect: add --auto-reset option
Series version: v1
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series (feature addition)

Core problem or goal
Introduce a `--auto-reset` option to `git bisect` that automatically returns the working tree to a specified commit after the bisect identifies the first bad commit, eliminating the need for an explicit `git bisect reset`. The feature targets automated workflows (scripts, CI pipelines) where manual intervention is impractical, but its exact behavior—whether it resets to the original pre-bisect commit or stays on the first bad commit—is now under discussion.

Current status
Under review (v1 posted). No prior versions or related in-flight topics mentioned. The series consists of three patches:
1. Preparatory refactoring to read `bisect run` output from an open descriptor (replaces `print_file_to_stdout()` with `print_fd_to_stdout()`, updates file open flags to include read access, avoids reopening the file by name, and seeks to start before copying to stdout).
2. Add quiet-checkout capability to `bisect_reset()` (new `quiet` parameter suppresses progress and branch-status output during checkout; no callers set the flag yet, so behavior is unchanged in this patch).
3. Introduce `--auto-reset` and wire it into `git bisect start` and `git bisect run` (adds the CLI option, updates documentation, persists the flag in a new `BISECT_AUTO_RESET` state file, and triggers a quiet reset after successful bisect completion; the state file is unlinked during `bisect_clean_state()` to avoid persistence across sessions).

Key technical details
- Files touched: `bisect.c`, `builtin/bisect.c`, `Documentation/git-bisect.adoc`, `t/t6030-bisect-porcelain.sh`.
- New CLI option: `--auto-reset` (no short form).
- Behavior: After `git bisect` identifies the first bad commit, the working tree is automatically reset to a commit determined by the option’s design. The current implementation resets to the original pre-bisect commit, but Junio’s review suggests this may not be the desired behavior.
- Internal changes: `print_file_to_stdout()` -> `print_fd_to_stdout()` (opened with `O_RDWR`, seek to start before copying to stdout); `bisect_reset()` now accepts a `quiet` parameter to suppress checkout output; new `BISECT_AUTO_RESET` state file tracks the auto-reset flag and is unlinked during `bisect_clean_state()`.
- Test coverage: Four new tests in `t/t6030-bisect-porcelain.sh` validate auto-reset behavior, state cleanup, and non-persistence across sessions. These tests currently assume a reset to the original commit.
- No on-disk format changes or new symbols introduced.

Open questions and loose ends
- **Design behavior**: Junio C Hamano has raised a high-weight question about whether `--auto-reset` should reset to the original pre-bisect commit (current implementation) or leave the working tree on the first bad commit (his expectation). This is a fundamental design decision that will affect the feature’s utility and may require changes to the implementation, documentation, and tests.
- Edge cases: Reviewers may still scrutinize behavior if the bisect is interrupted, fails, or encounters errors (e.g., `bisect run` exits non-zero, descriptor errors, seek failures, or quiet parameter handling in error paths).
- No other review comments have been received yet; this is the first substantive feedback on the series.

Participant positions

The refactoring in patch 1 and the quiet-checkout addition in patch 2 are motivated by the need to avoid reopening files by name and to reduce output noise in automated workflows, respectively.

His feedback is framed as a clarification request but signals a potential misalignment with the maintainer’s workflow and expectations.
