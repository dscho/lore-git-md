Subject: [PATCH 0/3] bisect: add --reset-when-found option
Series version: v5
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series (feature addition)

Core problem or goal
Introduce a `--reset-when-found[=<where>]` option to `git bisect` that automatically resets the working tree to a user-specified commit after the bisect identifies the first bad commit. The parameter `<where>` accepts `original` (reset to the pre-bisect commit, the default) or `found` (leave the working tree on the first bad commit). The feature targets automated workflows (scripts, CI pipelines) and interactive debugging by eliminating the need for an explicit `git bisect reset`.

Current status
The v5 patch series is technically complete, with all substantive and surface-level feedback addressed. Junio C Hamano’s proposed internal simplification—centralizing the auto-reset logic in the top-level `cmd_bisect()` function—has been fully implemented. This refactoring eliminates the `defer_reset` parameter, decouples `bisect_clean_state()` from `bisect_reset()`, and propagates the first bad commit OID via a file-scope static variable (`first_bad_oid`). The series remains marked for integration into `next`. The practical limitation noted by Junio—users cannot conditionally choose the reset target based on the bisect outcome—remains unchanged, as the target must still be specified upfront.

Key technical details
- Files touched: `bisect.c`, `builtin/bisect.c`, `bisect.h`, `Documentation/git-bisect.adoc`, `t/t6030-bisect-porcelain.sh`.
- New CLI option: `--reset-when-found[=<where>]` (parameterized; values `original` or `found`; default `original`). The boolean form (`--auto-reset`) is deprecated.
- Behavior: After `git bisect` identifies the first bad commit, the working tree is automatically reset to the commit specified by `<where>`. The default (`original`) preserves the original pre-bisect state; `found` leaves the working tree on the first bad commit. For `git bisect run`, the reset is deferred until after the captured output is printed and the `BISECT_RUN` file is closed, addressing platform-compatibility concerns about unlinking open files.
- Internal changes: The auto-reset logic is centralized in `cmd_bisect()`, which handles the reset after receiving `BISECT_INTERNAL_SUCCESS_1ST_BAD_FOUND` from `bisect_next_all()` via the file-scope static variable `first_bad_oid`. The preparatory patch (1/3) adds a `quiet` parameter to `bisect_reset()`, allowing the checkout step to suppress progress and branch-status output. The parameter is a `bool`, and existing callers (`bisect_replay()` and `cmd_bisect__reset()`) are updated to pass `false` to preserve current behavior. `bisect_reset()` no longer calls `bisect_clean_state()`, and the `defer_reset` parameter has been eliminated. The `quiet` parameter in `bisect_reset()` remains an `int` (not converted to `bool`), as the suggested type change was not adopted. The `BISECT_RESET_WHEN_FOUND` state file stores the target commit (`original` or `found`). If `<where>` is `found`, the reset step is omitted entirely. The option is wired into both `git bisect start` and `git bisect run`.
- Constraints: `--reset-when-found` cannot be used with `--no-checkout`, as that mode prevents checking out either target. The error message for this conflict uses Git’s standard dual-option template.
- Test coverage: Four new tests in `t/t6030-bisect-porcelain.sh` validate auto-reset behavior for both `original` and `found`, state cleanup, and edge cases (invalid targets, `--no-checkout` conflicts, interrupted bisects). Shell safety issues in test helpers have been fixed by assigning `git rev-parse` output to variables before passing them to `test_path_is_file`/`test_path_is_missing`.
- No on-disk format changes or new symbols introduced beyond the state file updates.
