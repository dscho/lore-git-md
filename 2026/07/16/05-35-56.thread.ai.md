Subject: [PATCH 0/3] bisect: add --auto-reset option

Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series (feature addition)

Core problem or goal
Introduce a `--auto-reset` option to `git bisect` that automatically returns the working tree to a user-specified commit after the bisect identifies the first bad commit, eliminating the need for an explicit `git bisect reset`. The feature targets both automated workflows (scripts, CI pipelines) and interactive debugging, but the exact behavior—whether it resets to the original pre-bisect commit or stays on the first bad commit—has evolved into a parameterized design proposed by the maintainer.

Current status
Under review (v1 posted). Junio C Hamano has proposed a redesign of the option from a boolean flag (`--auto-reset`) to a parameterized form (`--auto-reset=<where>`) accepting `original` (reset to the pre-bisect commit) or `found` (leave the working tree on the first bad commit), with `original` as the default. The author has not yet responded to this proposal, so the thread is awaiting either a revised patch series or further discussion. The preparatory refactoring (patch 1) and quiet-checkout addition (patch 2) remain uncontroversial and are unaffected by the design change.

Key technical details
- Files touched: `bisect.c`, `builtin/bisect.c`, `Documentation/git-bisect.adoc`, `t/t6030-bisect-porcelain.sh`.
- New CLI option: `--auto-reset=<where>` (parameterized; values `original` or `found`; default `original`). The boolean form (`--auto-reset`) is deprecated in the proposed design.
- Behavior: After `git bisect` identifies the first bad commit, the working tree is automatically reset to the commit specified by the parameter (`original` or `found`). The default (`original`) preserves the original pre-bisect state, while `found` leaves the working tree on the first bad commit (the culprit).
- Internal changes: `print_file_to_stdout()` -> `print_fd_to_stdout()` (opened with `O_RDWR`, seek to start before copying to stdout); `bisect_reset()` now accepts a `quiet` parameter to suppress checkout output. The `BISECT_AUTO_RESET` state file may need to store the target commit (`original` or `found`) rather than a boolean flag, or it may be eliminated if the reset step is omitted for `found`.
- Test coverage: Four new tests in `t/t6030-bisect-porcelain.sh` validate auto-reset behavior, state cleanup, and non-persistence across sessions. These tests currently assume a reset to the original commit and will need revision to cover both `original` and `found` behaviors.
- No on-disk format changes or new symbols introduced beyond the proposed state file updates.

Open questions and loose ends
- **Parameterized design adoption**: The author has not yet responded to Junio’s proposal. The outcome will determine whether the feature proceeds as a flexible tool (supporting both automated and interactive use cases) or remains narrowly targeted.
- **Option name and syntax**: The proposed `--auto-reset=<where>` syntax is clear but may be revisited if the author or other reviewers suggest alternatives (e.g., `--auto-checkout=<where>`).
- **State file necessity**: If the behavior includes `found` (no reset), the `BISECT_AUTO_RESET` state file may need to store the target commit or be eliminated entirely. The current implementation assumes a boolean flag and will require updates.
- **Edge cases**: Reviewers may still scrutinize behavior if the bisect is interrupted, fails, or encounters errors (e.g., `bisect run` exits non-zero, descriptor errors, seek failures, or quiet parameter handling in error paths).
- **Documentation and tests**: Both will need updates to reflect the parameterized behavior, including examples for `original` and `found` use cases.
- No other review comments have been received; the maintainer’s proposal is the only substantive feedback on the series.

Participant positions
- Harald Nordgren (author): Proposed the feature as a workflow improvement for automated environments, with the initial implementation resetting to the original pre-bisect commit. Acknowledged the maintainer’s preference for leaving the working tree on the first bad commit and is open to revising the behavior. The refactoring in patch 1 and the quiet-checkout addition in patch 2 are uncontroversial and motivated by technical needs (avoiding file reopens, reducing output noise).
- Junio C Hamano (maintainer): Proposed a parameterized design (`--auto-reset=<where>` with values `original` or `found`) to accommodate both automated workflows (reset to original) and interactive debugging (leave on first bad commit). The default (`original`) aligns with the author’s original use case. This proposal resolves the earlier design disagreement and provides flexibility for future users.
