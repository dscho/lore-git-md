Subject: [PATCH 0/3] bisect: add --reset-when-found option
Series version: v3
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series (feature addition)

Core problem or goal
Introduce a `--reset-when-found[=<where>]` option to `git bisect` that automatically resets the working tree to a user-specified commit after the bisect identifies the first bad commit. The parameter `<where>` accepts `original` (reset to the pre-bisect commit, the default) or `found` (leave the working tree on the first bad commit). The feature targets automated workflows (scripts, CI pipelines) and interactive debugging by eliminating the need for an explicit `git bisect reset`.

Current status
The v3 patch series has been marked for integration into `next` by Junio C Hamano. The series consists of three patches: (1) a preparatory plumbing change adding a `quiet` parameter to `bisect_reset()`, (2) the core feature implementation (auto-reset logic, state persistence, and CLI wiring), and (3) the quiet-checkout plumbing retained from v2. The design is settled, with the rename from `--auto-reset` to `--reset-when-found` and the deferred reset behavior for `git bisect run` retained. Junio noted a practical limitation: users whose desired reset target depends on the bisect outcome (e.g., conditionally choosing between `original` and `found`) may need to forgo the option and manually reset afterward, as the target must be specified upfront. The series is uncontroversial, with all substantive feedback addressed. Johannes Sixt’s recent review raised minor surface-level issues (error message boilerplate, shell safety in tests, test cleanup chaining) that are mechanical and do not affect the feature’s core logic or integration status.

Key technical details
- Files touched: `bisect.c`, `builtin/bisect.c`, `Documentation/git-bisect.adoc`, `t/t6030-bisect-porcelain.sh`.
- New CLI option: `--reset-when-found[=<where>]` (parameterized; values `original` or `found`; default `original`). The boolean form (`--auto-reset`) is deprecated.
- Behavior: After `git bisect` identifies the first bad commit, the working tree is automatically reset to the commit specified by `<where>`. The default (`original`) preserves the original pre-bisect state; `found` leaves the working tree on the first bad commit (the culprit). For `git bisect run`, the reset is deferred until after the captured output is printed and the `BISECT_RUN` file is closed, addressing platform-compatibility concerns about unlinking open files.
- Internal changes: `bisect_reset()` now accepts a `quiet` parameter (added in patch 1/3) to suppress checkout output, with all callers updated to pass `0` (false) to maintain current behavior. The `BISECT_RESET_WHEN_FOUND` state file stores the target commit (`original` or `found`). If `<where>` is `found`, the reset step is omitted entirely. The option is wired into both `git bisect start` and `git bisect run`.
- Constraints: `--reset-when-found` cannot be used with `--no-checkout`, as that mode prevents checking out either target.
- Test coverage: Four new tests in `t/t6030-bisect-porcelain.sh` validate auto-reset behavior for both `original` and `found`, state cleanup, and edge cases (invalid targets, `--no-checkout` conflicts, interrupted bisects, quiet parameter handling in error paths). Johannes Sixt’s review flagged shell safety issues in these tests (e.g., unchecked `git rev-parse` calls in subshells) and suggested using Git’s standard dual-option error template for the `--reset-when-found`/`--no-checkout` conflict.
- No on-disk format changes or new symbols introduced beyond the state file updates.

Open questions and loose ends
None. The platform-compatibility concern raised by Johannes Sixt in v2 about the descriptor refactor has been addressed by reverting to filename-based output handling. The remaining issues from Sixt’s recent review are mechanical (error message boilerplate, shell safety in tests, test cleanup chaining) and do not affect the feature’s design or integration status.
