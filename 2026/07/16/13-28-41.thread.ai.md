Subject: [RFC PATCH 0/N] repack: introduce --drop-filtered for partial clones
Series version: RFC v1 (patches 1/7–7/7 complete; v2 planned with bitmap validation fix, safety guards, API reorganization, drop-log documentation/test additions, and merge/rebase/cherry-pick checks)
Originating author: Siddharth Shrimali (first-time contributor)
Thread type: RFC patch series

Core problem or goal
Extend `git repack` with a `--drop-filtered` option that safely reclaims disk space in partial clones by removing locally cached promisor blobs exceeding a user-specified size threshold (e.g., `--filter=blob:limit=10M`). The feature must guarantee safety by (1) only targeting objects marked as promisor (ensuring they are recoverable from the promisor remote), (2) avoiding locally created objects, and (3) introducing a drop log (`$GIT_DIR/objects/info/promisor-dropped`) to record removed objects for improved error messages during future lazy-fetch failures.

Current status
RFC v1 is complete (7/7 patches posted). The series remains in active design iteration with no integration branch assignment. The **blocking logical flaw** in the `--drop-filtered` vs `--write-bitmap-index` validation (Junio’s feedback) is now **confirmed and settled**: the validation must be restructured in v2 to explicitly track whether `--write-bitmap-index` was set on the command line (erroring out if so) versus via configuration (silently disabling it). **Safety guards** (merge/rebase/cherry-pick checks and index validation) and **function signature reorganization** (internal APIs such as `enumerate_promisor_blobs()`) are now implemented in v1 but still require refinement in v2. The drop log (`$GIT_DIR/objects/info/promisor-dropped`) is implemented and now **supports real drops** (not just dry runs) but still **lacks documentation in `gitrepository-layout`** and **test coverage for real drops** (both deferred to v2). Remote verification logic remains deferred pending the `remote-object-info` protocol command. The CLI design (`--drop-filtered` + `--dry-run`) is settled, with rationale to be documented in the commit message.

Key technical details
- **New CLI options**: `git repack --drop-filtered` (supports real runs) and `--dry-run` (no longer mandatory)
- **New files**: `repack-filtered.c` (core logic), `t/t7706-repack-drop-filtered.sh` (test script)
- **Modified files**: `builtin/repack.c` (option parsing, validation, conditional bypass of `write_filtered_pack()`, drop log wiring, and now **real object removal** via `repack_promisor_objects()` with `drop_oids`), `list-objects-filter.{c,h}` (new `list_objects_filter__filter_oidset()` API), `repack-promisor.c` (promisor pack rebuilding with object exclusion via `to_drop` parameter, `append_drop_log()`), `repack.h` (function signature changes)
- **New data structures**: drop log (`$GIT_DIR/objects/info/promisor-dropped`) recording removed OIDs with timestamp, filter spec, and promisor remote(s); `collect_cb_data` struct; `all_promisor_blobs` and `to_drop` oidsets
- **New helper functions**: `list_objects_filter__filter_oidset()` (applies filter to an existing oidset without object traversal), `enumerate_promisor_blobs()` (walks promisor objects via `odb_for_each_object()` with `ODB_FOR_EACH_OBJECT_PROMISOR_ONLY`, returns drop set via output parameter `oidset *to_drop`), `append_drop_log()` (formats and appends drop entries to the log file)
- **Behavior**: `--drop-filtered` + `--filter=<spec>` (currently limited to `blob:limit=<n>`) removes promisor blobs exceeding the threshold; locally created objects are untouched. Bitmaps are silently disabled to avoid breaking pack closure. The `to_drop` set’s contents are passed to `repack_promisor_objects()` to rebuild promisor packs while excluding the dropped blobs, implying `-d` to remove old promisor packs containing the dropped objects. The repack machinery’s existing write-before-delete and fsync guarantees ensure crash safety. The drop log is written only on real runs (not dry runs), with minimal error handling (warnings on I/O failures). Test coverage validates CLI preconditions (e.g., `--filter` and `-a` are required, `--filter-to` is rejected, promisor remote must be configured), promisor blob filtering (only blobs exceeding the threshold are listed as drop candidates), dry-run safety (no objects are removed), and **actual object removal** (preserving smaller blobs).
- **Safety**: objects are only enumerated if marked as promisor (via `ODB_FOR_EACH_OBJECT_PROMISOR_ONLY`); lazy fetches are avoided during enumeration by passing `OBJECT_INFO_SKIP_FETCH_OBJECT` to every object info query. Preconditions enforced: `--filter` must be `blob:limit`, `-a` is required, a promisor remote must be configured, and `--filter-to` is rejected. **Safety guards for v2**: merge/rebase/cherry-pick checks and index validation (preventing drops of blobs referenced by the current index) will be implemented to avoid immediate re-fetching of just-dropped blobs. The drop log enables future error-message improvements but does not yet validate that dropped objects are not referenced by the index or that the promisor remote still has them (deferred to follow-ups).

Open questions and loose ends
1. **Bitmap validation**: the blocking flaw in patch 1/7 is now confirmed and must be fixed in v2 by restructuring the validation to distinguish command-line vs configuration-driven bitmap settings.
2. **Safety guards**: merge/rebase/cherry-pick checks and index validation are now implemented in v1 but require refinement in v2 (Siddharth Asthana’s feedback).
3. **Function signature churn**: internal APIs (`list_objects_filter__filter_oidset()`, `repack_promisor_objects()`, `enumerate_promisor_blobs()`) and test placement will be reorganized in v2.
4. **Drop log documentation and testing**: the log path (`$GIT_DIR/objects/info/promisor-dropped`) must be documented in `gitrepository-layout` and tested for real drops (Siddharth Asthana’s feedback).
5. **Remote verification**: the drop log currently records all configured promisor remotes rather than the specific one each object is recoverable from; this depends on the `remote-object-info` protocol command (not yet implemented).
6. **Client-side remote object availability**: no way to query whether a promisor remote still has an object; this is a known limitation.
7. **Merge status**: no maintainer decision yet; integration branch unknown.
8. **Filter scope**: currently limited to `blob:limit`; future extensions may include other filter types (e.g., `tree:0`).
9. **Drop log enhancements**: recording the exact promisor remote per object and validating remote object availability are deferred pending the `remote-object-info` protocol command.

Participant positions
- **Siddharth Shrimali (author)**: RFC v1 now complete (7/7 patches). Plans v2 to address the **blocking logical flaw** in the `--drop-filtered` vs `--write-bitmap-index` validation by restructuring the validation to explicitly track whether `--write-bitmap-index` was set on the command line (erroring out if so) versus via configuration (silently disabling it). **Safety guards** (merge/rebase/cherry-pick checks and index validation) are now implemented in v1 but require refinement in v2. Commits to documenting the rationale for the `--drop-filtered` + `--dry-run` CLI design in the commit message and adding **drop log documentation in `gitrepository-layout`** and **test coverage for real drops** (both deferred from v1). The **drop log** and **remote verification** enhancements remain deferred.
- **Junio C Hamano (maintainer)**: **Substantive review of patch 1/7** identifies and now **confirms the blocking logical flaw** in the `--drop-filtered` vs `--write-bitmap-index` validation. The check occurs too late in the control flow (after `write_bitmaps` may have been set by config), so it cannot distinguish between user-requested bitmaps (which should be rejected) and config-driven bitmaps (which should be silently disabled). This renders the safety mechanism ineffective and must be fixed before the series can proceed.
- **Christian Couder**: **Surface-level review of patch 1/7** focuses on CLI design. Suggests an alternative syntax (`--drop-filtered[=dry-run]`) but ultimately endorses the current separation of `--drop-filtered` and `--dry-run`, noting that `--dry-run` is already a common pattern in other Git commands. Requests only that the commit message explain the rationale for the two-option design.
- **Siddharth Asthana (reviewer)**: **Substantive review** endorses the core approach (using the promisor repack path rather than `write_filtered_pack()`) as the right technical direction. Raises two **critical safety concerns** that are now implemented in v1 but require refinement in v2: (1) **safety guards preventing drops during merges, rebases, or cherry-picks**, and (2) **index validation** (preventing drops of blobs referenced by the current index to avoid immediate re-fetching). Aligns with Christian Couder on the CLI design (`--drop-filtered` + `--dry-run`), leaving the door open for a unified `--drop-filtered=<mode>` syntax if more drop-specific options emerge later. **Endorses the drop log implementation** but insists on **documentation in `gitrepository-layout`** and **test coverage for real drops** in v2. Pragmatically defers the drop log and remote-object-info protocol improvements but insists the safety guards are non-negotiable for the next RFC round.
