This thread is about a usability gap in Git’s sparse-checkout feature when used with submodules. Brad Larson reports that `git submodule update --init` currently initializes *all* submodules in a repository, even those outside the sparse-checkout cone, which undermines the purpose of sparse-checkout for large repositories with many submodules. He provides a clear reproduction case using the Rust repository and asks whether the maintainers would accept a patch to make `git submodule` respect sparse-checkout boundaries—initializing only submodules whose paths fall within the cone.

The thread is at the RFC stage: no patch has been posted yet, and Brad is gauging interest in the idea. So far, there are no replies, so the discussion is still open. If you’re working with sparse-checkout or submodules, this is a thread to watch—it could lead to a significant behavior change in how Git handles submodules in sparse worktrees.
