Subject: [PATCH 0/6] Reintroduce writev(3p) wrapper for performance
Series version: v1 (initial revival)
Originating author: Patrick Steinhardt
Thread type: patch series

Core problem or goal
Reintroduce a `writev(3p)`-like wrapper to reduce system call overhead in low-level I/O operations, specifically targeting pktline transmission in `sideband.c` and cat-blob responses in `fast-import.c`. The wrapper was originally merged in Git 2.54 but reverted due to platform compatibility issues (NonStop, CMake); this series incorporates fixes for those issues and demonstrates broader applicability. The goal is performance improvement, with the API design, naming, and broader I/O abstraction strategy now fully resolved.

Current status
Under review; v1 posted. No prior versions in this thread. The series is self-contained, with no unresolved external dependencies. All technical design and correctness issues have been resolved: the integer-overflow concern raised by Simon Richter was addressed by Junio C Hamano’s confirmation of existing bounds-checking safety and Patrick Steinhardt’s explicit overflow check using `unsigned_add_overflows()`; API naming is resolved in favor of `git_write_gather()` to avoid implying POSIX semantics; and the architectural question about I/O abstraction is resolved by Johannes Sixt and Junio C Hamano’s confirmation that Git’s pktline and cat-blob use cases do not require atomicity, allowing the API to be implemented as a simple loop of `write(2)` calls. Junio C Hamano has now decisively resolved the last remaining design question—the forward-compatibility of the API name—by reaffirming that explicit documentation of non-atomic emulation is sufficient, and that competing writes to the same destination would be a bug regardless of atomicity. The series is now technically complete; the only open questions are maintainer appetite (whether the performance gains justify the complexity) and the absence of a range-diff to the reverted version for self-documentation. No maintainer decision on merge status; the series remains in review pending Junio C Hamano’s assessment of appetite and Patrick Steinhardt’s respin, which is not expected immediately due to his offsite attendance.

Key technical details
- Files touched: `Makefile`, `compat/posix.h`, `compat/writev.c`, `wrapper.{c,h}`, `write-or-die.{c,h}`, `sideband.c`, `builtin/fast-import.c`, plus build system files (`config.mak.uname`, `CMakeLists.txt`, `meson.build`).
- New symbols: `git_write_gather()` and `git_write_gather_or_die()` wrappers (naming resolved); platform-specific implementations in `compat/writev.c`. The API is a two-level abstraction: a Git-specific API that platforms can implement either via `writev(2)` or as a series of `write(2)` calls, with explicit documentation that emulation may be non-atomic.
- Behavior change: replaces multiple `write()` calls with batched `writev()`-like operations in pktline transmission and cat-blob responses; explicit `MAX_IO_SIZE` handling to avoid partial writes.
- On-disk format: no changes.
- Test coverage: none mentioned; benchmarks referenced but not provided in the email.
- Safety concerns: The integer-overflow issue in the `iov_len` accumulation logic (`iov[i].iov_len + sum > SSIZE_MAX`) has been resolved. Junio C Hamano confirmed the existing bounds-checking logic is safe because both `sum` and `iov[i].iov_len` are individually constrained to ≤ `SSIZE_MAX`, preventing wrap-around in `size_t`. Patrick Steinhardt added an explicit overflow check using `unsigned_add_overflows()` for clarity, with negligible performance cost.
- Architectural resolution: Johannes Sixt and Junio C Hamano confirmed that Git’s pktline and cat-blob use cases do not require atomicity, and both are inherently single-writer scenarios. The `git_write_gather()` API is therefore implemented as a simple loop of `write(2)` calls without violating necessary semantics, and competing writes to the same destination would be a bug regardless of atomicity.
