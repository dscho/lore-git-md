Subject: [PATCH 0/6] Reintroduce writev(3p) wrapper for performance
Series version: v2 (revival with compatibility wrapper simplification)
Originating author: Patrick Steinhardt
Thread type: patch series

Core problem or goal
Reintroduce a `writev(3p)`-like wrapper to reduce system call overhead in low-level I/O operations, specifically targeting pktline transmission in `sideband.c` and cat-blob responses in `fast-import.c`. The wrapper was originally merged in Git 2.54 but reverted due to platform compatibility issues (NonStop, CMake); this series incorporates fixes for those issues, resolves all prior technical objections, and demonstrates broader applicability. The goal is performance improvement through batched writes, with the API design, naming, and architectural questions now fully resolved.

Current status
Under review; v2 posted. The series is self-contained with no unresolved external dependencies. All technical design and correctness issues from v1 have been resolved: the integer-overflow concern raised by Simon Richter was addressed by Junio C Hamano’s confirmation of existing bounds-checking safety and the compatibility wrapper’s simplification; API naming is resolved in favor of `git_write_gather()` to avoid implying POSIX semantics; the architectural question about atomicity is resolved by Johannes Sixt and Junio C Hamano’s confirmation that Git’s pktline and cat-blob use cases do not require atomicity and are inherently single-writer scenarios. Junio C Hamano accepted Patrick Steinhardt’s proposed one-line tweak to the compatibility wrapper, which writes only the first `iovec` in the loop to restore the non-interleaving property of `write(3p)` and avoid interleaving even on platforms without `writev(2)`. This change simplifies the wrapper by removing overflow checks and most loop logic, making the code both safer and cleaner. Patch 3/6 (new in this update) adds `xwritev()` to handle `MAX_IO_SIZE` limitations on platforms like NonStop, ensuring the wrapper remains robust across all supported systems. The series is now technically complete and awaits Junio C Hamano’s final assessment of merge appetite.

Key technical details
- Files touched: `Makefile`, `compat/posix.h`, `compat/writev.c` (new), `wrapper.{c,h}`, `write-or-die.{c,h}`, `sideband.c`, `builtin/fast-import.c`, plus build system files (`config.mak.uname`, `CMakeLists.txt`, `meson.build`).
- New symbols: `git_write_gather()` and `git_write_gather_or_die()` wrappers (naming resolved); `writev_in_full()` and `writev_or_die()` plumbing functions (added in patch 2/6); `xwritev()` (added in patch 3/6) for `MAX_IO_SIZE` handling; platform-specific implementations in `compat/writev.c`. The API is a two-level abstraction: a Git-specific API that platforms can implement either via `writev(2)` or as a series of `write(2)` calls, with explicit documentation that emulation may be non-atomic.
- Behavior change: replaces multiple `write()` calls with batched `writev()`-like operations in pktline transmission and cat-blob responses; explicit `MAX_IO_SIZE` handling to avoid partial writes. The compatibility wrapper now writes only the first `iovec` in the loop, restoring the non-interleaving property of `write(3p)` and matching `write(2)` behavior to avoid interleaving even on platforms without `writev(2)`.
- On-disk format: no changes.
- Test coverage: none mentioned; benchmarks referenced but not provided in the email.
- Safety concerns: The integer-overflow issue in the `iov_len` accumulation logic is resolved. Junio C Hamano confirmed the existing bounds-checking logic is safe because both `sum` and `iov[i].iov_len` are individually constrained to ≤ `SSIZE_MAX`, preventing wrap-around in `size_t`. The compatibility wrapper’s simplification (writing only the first `iovec`) removes the need for overflow checks entirely. The new `writev_in_full()` function handles partial writes by adjusting the `iovec` array in-place, discarding fully written segments and shrinking the current segment for the next attempt, matching the semantics of `write_in_full()`. Patch 3/6 introduces `xwritev()` to handle `MAX_IO_SIZE` limitations, splitting large `iovec` entries into smaller chunks to avoid `EINVAL` on platforms like NonStop, while preserving the retry logic for `EINTR` and `EAGAIN`.
- Architectural resolution: Johannes Sixt and Junio C Hamano confirmed that Git’s pktline and cat-blob use cases do not require atomicity, and both are inherently single-writer scenarios. The `git_write_gather()` API is therefore implemented as a simple loop of `write(2)` calls without violating necessary semantics, and competing writes to the same destination would be a bug regardless of atomicity.
