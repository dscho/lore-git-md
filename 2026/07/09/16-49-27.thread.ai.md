Thread identity
Subject: [PATCH 0/12] Widen size fields in delta/pack machinery for 64-bit Windows
Series version: v1
Originating author: Johannes Schindelin (via GitGitGadget)
Thread type: patch series (platform-compatibility fix)

Core problem or goal
Widen size-related fields, parameters, and local variables in Git’s delta-compression and pack-objects code from `unsigned long` or `int` to `size_t` to prevent integer truncation on 64-bit Windows (where `unsigned long` is 32-bit) and other platforms where `unsigned long` does not match the pointer width. This is part of the ongoing effort to eliminate incorrect `unsigned long` usage in favor of `size_t`.

Current status
Under review; v1 posted. No prior versions. The series remains mechanical and confined to type widening; no behavior or on-disk format changes. All patches now include the final piece (widening `git_deflate_bound()`), completing the series' stated goal. Patrick Steinhardt identified three issues in earlier patches: (1) a type mismatch in Patch 1 where `sizeof_delta_index()` returns `index->memsize` (widened to `size_t`) but its return type and callers remain `unsigned long`, risking truncation; (2) a latent configuration-parsing bug in Patch 3 where `max_delta_cache_size` (widened to `size_t`) is set via `git_config_int()`, which accepts negative values, potentially leading to nonsensical cache limits; (3) a type mismatch in Patch 4 where `free_unpacked()` computes a `size_t` value (`freed_mem`) but returns it as `unsigned long`, reintroducing truncation risk on platforms where `unsigned long` is narrower than `size_t`. All three issues are expected to be fixed in the next iteration. Patrick Steinhardt also questioned the necessity of the twelve-patch split, suggesting the changes could be squashed into a single patch due to their trivial nature, and requested clarification on the fallback formula used in Patch 12 for inputs above zlib’s `uLong` range (>4 GiB on 64-bit Windows), noting unfamiliarity with zlib’s stored-block mechanism and asking whether the formula is an upper-bound estimate. Johannes Schindelin’s explanation in Patch 6 about initializing `deltalen` to 0 to work around a GCC warning was acknowledged by Patrick Steinhardt; the initialization is temporary and will be removed in a later series when `deltalen` is widened to `size_t`.

Key technical details
- Files touched: 21, primarily in the delta (`diff-delta.c`, `delta.h`), pack-objects (`pack-objects.c`, `pack-objects.h`), zlib (`git-zlib.c`, `git-zlib.h`), packfile (`packfile.c`, `packfile.h`), and diff (`diff.c`) subsystems; also `http-push.c`, `archive-zip.c`, `builtin/fast-import.c`, `builtin/pack-objects.c`, `pack-check.c`, and test helpers (`t/helper/test-delta.c`, `t/helper/test-pack-deltas.c`).
- New/renamed symbols: `struct delta_index` size fields (`src_size`, `trg_size`, `max_size`), `create_delta_index()` and `create_delta()` parameters (including `bufsize` in `create_delta_index()` and all size parameters in `create_delta()` and `diff_delta()`), delta-cache accounting variables (`delta_cache_size`, `max_delta_cache_size`, `delta_cacheable()`) in `pack-objects.c`, zlib stream fields (`avail_in`, `avail_out`) in `struct git_zstream` (widened from `unsigned long` to `size_t`), the `*left` output parameter of `use_pack()` (widened from `unsigned long` to `size_t`), the `mem_usage` counter in `find_deltas()` and corresponding output parameter in `try_delta()` (widened from `unsigned long` to `size_t`), the `maxsize` local variable in `zlib_deflate_raw()` (widened from `unsigned long` to `size_t` in `archive-zip.c`), the `bound` local variable in `deflate_it()` (widened from `int` to `size_t` in `diff.c`), the `size` local variable in `start_put()` (widened from `ssize_t` to `size_t` in `http-push.c`), the `maxsize` local variable in `do_compress()` (widened from `unsigned long` to `size_t` in `t/helper/test-pack-deltas.c`), and the `git_deflate_bound()` function (widened from `unsigned long` to `size_t` in both parameter and return type in `git-zlib.h` and `git-zlib.c`).
- Internal preparatory work: Patch 1 widened `src_size` and `memsize` in the private `struct delta_index` (defined in `diff-delta.c`) from `unsigned long` to `size_t`; Patch 2 widens the `bufsize` parameter of `create_delta_index()` from `unsigned long` to `size_t` in both declaration (`delta.h`) and definition (`diff-delta.c`). Patch 3 widens the global counters `delta_cache_size` and `max_delta_cache_size`, and the helper function `delta_cacheable()` in `builtin/pack-objects.c` from `unsigned long` to `size_t`, matching the `size_t` return type of `DELTA_SIZE()` that feeds into these counters. The sole caller (`try_delta()`) still passes `unsigned long` parameters, which safely promote to `size_t`. Patch 4 widens the `freed_mem` local variable in `free_unpacked()` from `unsigned long` to `size_t` but leaves the function’s return type as `unsigned long`, creating a type mismatch that could reintroduce truncation. Patch 5 widens the `mem_usage` counter in `find_deltas()` and the corresponding output parameter in `try_delta()` from `unsigned long` to `size_t`, ensuring type consistency in the delta-window memory accounting chain. The `window_memory_limit` configuration value remains `unsigned long` but safely promotes when compared against `mem_usage`. Patch 6 widens all size parameters and output variables in `create_delta()` and `diff_delta()` from `unsigned long` to `size_t` in both declaration (`delta.h`) and definition (`diff-delta.c`), then updates callers. Most callers still use `unsigned long` downstream (e.g., zlib’s `avail_in` or test helpers), so the patch introduces temporary `size_t` variables and `cast_size_t_to_ulong()` shims to bridge the gap; these shims are noted as temporary and will be removed in later topics that widen the downstream consumers. The only caller widened outright is `t/helper/test-delta.c`, which has no downstream constraints. Patch 7 widens the `avail_in`/`avail_out` fields in `struct git_zstream` and the `*left` output parameter of `use_pack()` from `unsigned long` to `size_t` to maintain type consistency at the four call sites in `builtin/pack-objects.c` and `pack-check.c` that pass `&stream.avail_in` directly to `use_pack()`. The widened locals (`avail`, `remaining`, `left`) are bounded by `core.packedGitWindowSize`, and `git_zstream.avail_in`/`avail_out` are already capped by `zlib_buf_cap()` at 1 GiB, so the wrapper effectively already accepted `size_t`-shaped inputs. Patch 8 widens the `maxsize` local variable in `zlib_deflate_raw()` (in `archive-zip.c`) from `unsigned long` to `size_t` to align with the upcoming `git_deflate_bound()` return type change. Patch 9 widens the `bound` local variable in `deflate_it()` (in `diff.c`) from `int` to `size_t` to eliminate a silent integer narrowing when `git_deflate_bound()` returns values above 2 GiB, which would wrap negative in `int` and then be sign-extended back to `size_t` in the subsequent `xmalloc()`. Patch 10 widens the `size` local variable in `start_put()` (in `http-push.c`) from `ssize_t` to `size_t` to fix a latent type mismatch: the variable is initialized from `git_deflate_bound()` (an unsigned upper bound) and passed only to `strbuf_grow()` and `stream.avail_out`, both of which already expect `size_t`. The original `ssize_t` was technically incorrect—values above `SSIZE_MAX` would wrap negative on assignment and then implicitly re-extend to a huge `size_t` at the call sites, risking absurd allocation requests. Patch 11 widens the `maxsize` local variable in `do_compress()` (in `t/helper/test-pack-deltas.c`) from `unsigned long` to `size_t` to align with the `git_deflate_bound()` return type, eliminating a similar truncation risk on 64-bit Windows. Patch 12 widens `git_deflate_bound()` from `unsigned long` to `size_t` in both its parameter and return type, introducing a compile-time guard (`#if SIZE_MAX > ULONG_MAX`) that detects platforms where `uLong` (zlib’s input type) is narrower than `size_t`. On those platforms, inputs above `uLong`’s range (>4 GiB on 64-bit Windows) fall back to zlib’s stored-block formula plus worst-case overhead, while smaller inputs continue to use the existing `deflateBound()` path.

Open questions and loose ends
- Patch 1: `sizeof_delta_index()` return type and callers remain `unsigned long` despite returning `index->memsize` (widened to `size_t`), creating a type mismatch that could reintroduce truncation. This is expected to be fixed in the next iteration.
- Patch 3: `max_delta_cache_size` is set via `git_config_int()`, which accepts negative values, potentially leading to nonsensical cache limits. The documentation only mentions positive values, but the current code does not enforce this. Patrick Steinhardt suggests either introducing a `git_config_size_t()` helper or switching to `git_config_uint()` to reject negative values outright, though the latter could break users who mistakenly rely on negative values as "infinite" cache.
- Patch 4: `free_unpacked()` computes a `size_t` value (`freed_mem`) but returns it as `unsigned long`, reintroducing truncation risk on platforms where `unsigned long` is narrower than `size_t`. The fix is to widen the return type to `size_t`.
- Patch 6: Johannes Schindelin’s commit message notes that `deltalen` is initialized to 0 to work around a GCC warning, and that this initialization is temporary and will be removed in a later series when `deltalen` is widened to `size_t`.
- Patch 12: Patrick Steinhardt requested clarification on the fallback formula used for inputs above zlib’s `uLong` range (>4 GiB on 64-bit Windows), asking whether it is an upper-bound estimate and noting unfamiliarity with zlib’s stored-block mechanism. The formula’s correctness and whether it is a strict upper bound remain open for confirmation.
- Series structure: Patrick Steinhardt questioned the necessity of the twelve-patch split, suggesting the changes could be squashed into a single patch due to their trivial nature. The rationale for the split (e.g., bisectability, review granularity) remains unaddressed.
