Subject: [PATCH 0/13] Widen size fields in delta/pack machinery for 64-bit Windows
Series version: v3 (final; fully type-consistent, addresses all prior review feedback)
Originating author: Johannes Schindelin (via GitGitGadget)
Thread type: patch series (platform-compatibility fix)

Core problem or goal
Widen size-related fields, parameters, and local variables in Git’s delta-compression and pack-objects code from `unsigned long` or `int` to `size_t` to prevent integer truncation on 64-bit Windows (where `unsigned long` is 32-bit) and other platforms where `unsigned long` does not match the pointer width. This completes the ongoing effort to eliminate incorrect `unsigned long` usage in favor of `size_t` in the delta/pack subsystems.

Current status
Merged to `master` (date unknown). The series is now fully type-consistent across all affected code paths, addressing all prior review feedback, including the final two truncation risks in the delta-window memory accounting chain (`mem_usage` in `find_deltas()` and the corresponding output parameter in `try_delta()`), the delta-encoding API (`create_delta()`, `diff_delta()`, and their `delta_size` output parameters), the zlib stream interfaces (`avail_in`, `avail_out`, and `use_pack()`'s `left` output parameter), the `maxsize` local variables in `archive-zip.c` and `t/helper/test-pack-deltas.c`, the narrowing bug in `diff.c`’s `deflate_it()` function, the `size` local variable in `http-push.c`’s `start_put()` function (widened from `ssize_t` to `size_t`), the `git_deflate_bound()` helper (widened to `size_t` for both parameter and return type in Patch 12), and the `unpack_object_header_buffer()` function in `packfile.c` (widened to `size_t` for its `len` parameter and return type in Patch 13). The 13-patch split is final; no further changes are expected.

Patch 13 widens `unpack_object_header_buffer()`’s `len` parameter and return type to `size_t`, addressing the last remaining `unsigned long` interface in the affected code paths. The fallback formula for inputs exceeding zlib’s `uLong` range (>4 GiB on 64-bit Windows) mirrors zlib’s stored-block logic plus worst-case wrapper overhead and is guarded by `#if SIZE_MAX > ULONG_MAX` to avoid overhead on platforms where `unsigned long` is already 64-bit. The original `ssize_t` in `http-push.c` was incorrect because it risked negative wrap on large inputs, though this was not a practical concern for current object sizes.
