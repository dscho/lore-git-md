Subject: [PATCH 0/12] Widen size fields in delta/pack machinery for 64-bit Windows
Series version: v2 (all review feedback addressed; ready for integration)
Originating author: Johannes Schindelin (via GitGitGadget)
Thread type: patch series (platform-compatibility fix)

Core problem or goal
Widen size-related fields, parameters, and local variables in Git’s delta-compression and pack-objects code from `unsigned long` or `int` to `size_t` to prevent integer truncation on 64-bit Windows (where `unsigned long` is 32-bit) and other platforms where `unsigned long` does not match the pointer width. This is part of the ongoing effort to eliminate incorrect `unsigned long` usage in favor of `size_t`.

Current status
Queued in `next` for integration testing. The series remains uncontroversial and mechanically correct, but Junio C Hamano’s latest review raises two narrowly scoped technical questions about potential truncation risks in patch 07/12 that may require follow-up patches to fully align the type system. All prior review feedback from v1 and v2 has been addressed, and the 12-patch split is unchanged.

Key technical details
- Files touched: 24, spanning `diff-delta.c`, `pack-objects.c`, `git-zlib.c`, `http-push.c`, `archive-zip.c`, `remote-curl.c`, `builtin/fast-import.c`, and test helpers.
- New/renamed symbols: `git_deflate_bound()` parameter and return type widened to `size_t` (Patch 12), completing the type chain. All prior widenings remain unchanged: `sizeof_delta_index()` return type, `git_config_size_t()` and `git_parse_size_t()` helpers, `free_unpacked()` return type, `bufsize` parameter of `create_delta_index()`, `struct delta_index` size fields, `create_delta()` and `diff_delta()` parameters, delta-cache accounting variables, zlib stream fields (`avail_in`, `avail_out`), `*left` output parameter of `use_pack()`, `mem_usage` counter in `find_deltas()` and `try_delta()`, and local variables in `archive-zip.c`, `diff.c`, `http-push.c`, and test helpers.
- Internal preparatory work: Patch 12 finalizes the type chain by widening `git_deflate_bound()` and updating all callers, removing the last `cast_size_t_to_ulong()` shim in `write_no_reuse_object()`. The fallback formula for inputs exceeding zlib’s `uLong` range (>4 GiB on 64-bit Windows) mirrors zlib’s stored-block logic plus worst-case wrapper overhead, ensuring correctness without behavior change for inputs within `uLong`. The code is guarded by `#if SIZE_MAX > ULONG_MAX` to avoid overhead on platforms where `unsigned long` is already 64-bit.
- Behavior change: none; this is a pure type-widening correctness fix.
- On-disk format change: none.
- Test coverage: unchanged; no new tests added.
- Base commit: `f85a7e662054a7b0d9070e32508231afa214b47`.

Open questions and loose ends
- Junio C Hamano’s review of patch 07/12 raises two potential truncation risks:
  1. `zlib_buf_cap()` remains `unsigned long`, and `zlib_pre_call()` passes the now-wider `avail_in`/`avail_out` values to it. Could this trigger truncation before comparison with `ZLIB_BUF_MAX`?
  2. `unpack_object_header_buffer()` still takes an `unsigned long` length parameter, and `oe_get_size_slow()` in `builtin/pack-objects.c` passes a `size_t` value to it. Could this cause truncation that a static checker might flag?
  Junio acknowledges these are likely harmless in practice but flags them as type-consistency issues that may require follow-up patches to fully align the type system. Resolution of these questions is now the only remaining technical loose end before the series can graduate to `master`.
