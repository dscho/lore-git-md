Subject: [PATCH 0/9] Introduce object filters to odb_for_each_object()
Series version: v3 (v1 was 7 patches; v2 was 8 patches; v3 adds Jeff King’s cleanup patch as 3/9 and Patrick Steinhardt’s `const` filter parameter patch as 2/9, plus this mechanical rename patch as 6/9, making 9 patches total)

Thread type: patch series

Core problem or goal
Enable `git cat-file --batch-all-objects` to work with pluggable object databases by removing its dependency on internal details of the "packed" backend, specifically for efficient handling of bitmapped objects. This is a step in the ongoing ODB abstraction effort to restructure Git’s object storage layer to support alternative backends. The series also addresses an inefficiency in `odb_for_each_object()` where object lookups during enumeration redundantly traverse indices, risking incorrect pack selection and degrading performance.

Peff’s latest email responds to Taylor’s observation about the incomplete refactoring in patch 4/9, noting that the non-bitmap traversal function `traverse_commit_list()` also ignores callback return values (its callbacks return `void`, not `int`). He suggests that the two traversal functions should remain consistent: either both should allow early termination via non-zero returns, or both should ignore callback return values. **Patrick Steinhardt has responded to this design question**, proposing to leave both functions unchanged—`traverse_bitmap_commit_list()` continuing to ignore callback return values despite its callbacks returning `int`, and `traverse_commit_list()` retaining its `void`-returning callbacks. This approach avoids a large-scale refactoring but leaves the "foot-gun" in patch 4/9 unresolved. All other review feedback from v1 and v2 has been resolved: (1) Patch 1/9’s two open questions about object lookup behavior and the `if (opts->flags || data->request)` condition were clarified, confirming that reading from a different packfile is semantically incorrect but not harmful, and that `data->request` ensures the pack is populated for `packed_object_info()`. (2) Patch 2/9 marks the object filter parameter in `for_each_bitmapped_object()` and its helper functions as `const`, reflecting that the filter is never modified during traversal. This is a mechanical, uncontroversial change that aligns the API with Git’s broader practice of marking read-only parameters as `const`. (3) Patch 3/9 (Peff’s cleanup) resolves the return-value inconsistency by removing the unused `int` return from `add_object_entry()`. (4) Patch 4/9’s return-value changes were confirmed as safe due to dead code elimination. (5) Patch 5/9’s style suggestions were incorporated, including the restructuring of `open_bitmap()` to iterate over object sources first, then attempt to load a bitmap for each source. This change reverses the loop order, introduces a subtle change in bitmap precedence (local packfile bitmaps now take precedence over MIDX bitmaps in alternates), and simplifies the logic by using a boolean instead of an integer return value. The patch also improves trace2 reporting and is a prerequisite for the ODB filtering mechanism introduced later in the series. (6) Patch 6/9 (the new email) is a mechanical refactoring that drops the `_1` suffix from `open_pack_bitmap_1()` and `open_midx_bitmap_1()`, renaming them to `open_pack_bitmap()` and `open_midx_bitmap()` respectively. The change follows patch 5/9’s consolidation of the original functions into `open_bitmap_for_source()`, leaving the `_1`-suffixed variants as the only remaining callers. The patch touches only `pack-bitmap.c` and makes no functional changes—it is purely a rename to improve clarity and consistency. (7) Patch 7/9’s design question—whether backends should be required to support a subset of object filters—was resolved in favor of the current design, which allows backends to ignore filters, consistent with Git’s existing patterns (e.g., reference backend exclude patterns). The v2 update added one new patch (5/8, now 6/9) to drop unnecessary `_1()` suffixes from bitmap-opening functions, simplifies the logic in `open_bitmap_for_source()` by using a boolean instead of an integer, and improves commit message explanations. Patch 8/9 adds a `filter` field to the `odb_for_each_object_options` struct, allowing callers to pass object filters to backends for optimization. Backends may use these filters to skip excluded objects (e.g., via bitmaps) but are not required to, so callers must still re-apply the filter to yielded objects if strict filtering is needed. The "packed" backend implementation introduces a new `bitmapped_for_each_object` callback that uses `prepare_bitmap_git_for_source()` to open bitmaps exclusively for the current object source, ensuring objects are correctly attributed to their source and avoiding redundant enumeration. The backend skips packs already covered by a bitmap during iteration, improving efficiency. The patch also exposes `can_filter_bitmap()` (previously static) to allow backends to check if a filter can be optimized via bitmaps. Taylor Blau’s latest review of patch 8/9 confirms it "looks plausibly correct" but notes limited familiarity with the pluggable ODB subsystem; the feedback is surface-level and does not engage with technical details or raise new considerations. The final patch (9/9) replaces the direct, backend-specific bitmap handling in `git cat-file --batch-all-objects` with the new ODB-mediated filtering mechanism, eliminating tight coupling between the command and the "packed" backend internals. The change removes 69 lines of intricate, backend-aware logic and replaces them with 7 lines that delegate filtering to the ODB layer via `odb_for_each_object_ext()`. The patch also removes the now-unused `pack-bitmap.h` include and drops three helper functions (`batch_one_object_packed`, `batch_one_object_bitmapped`, and the old bitmap-handling branch in `batch_each_object`). **Patrick’s latest email (v3 cover letter) confirms that all substantive review feedback has been addressed**, including the integration of Peff’s cleanup patch, the new `const` filter parameter patch, and the mechanical rename patch. The series is now ready for integration, pending Junio’s final review. The tone remains collaborative, with no unresolved objections or signs of contention.

Open questions and loose ends
The **performance inefficiency in patch 1/9** identified by Taylor Blau remains unresolved but clarified: the current implementation aborts iteration on the first non-match, mitigating the inefficiency, but the loop’s scope (full MIDX chain vs. primary MIDX) is ambiguous. Patrick has deferred Taylor’s proposed optimization (using the OID fanout chunk to narrow the iteration range) to a separate series, leaving the current implementation as "not incorrect, merely suboptimal." The surface-level nit about mixing unrelated changes (the `store` → `source` rename) in the same patch as the object lookup logic in patch 1/9 remains open but is minor and does not block progress. **The design question about consistency between `traverse_bitmap_commit_list()` and `traverse_commit_list()` has been addressed by Patrick Steinhardt’s proposal to leave both functions unchanged**, avoiding a large-scale refactoring but leaving the "foot-gun" in patch 4/9 unresolved. This decision defers the broader API consistency question and may influence whether future callers can rely on early termination during object enumeration. All other review feedback has been resolved, including the integration of Peff’s cleanup patch, the new `const` filter parameter patch, the mechanical rename patch, and the restructuring in patch 5/9. No new open questions or loose ends were introduced in the latest email or patches.
