Subject: [PATCH 0/8] Introduce object filters to odb_for_each_object()

Core problem or goal
Enable `git cat-file --batch-all-objects` to work with pluggable object databases by removing its dependency on internal details of the "packed" backend, specifically for efficient handling of bitmapped objects. This is a step in the ongoing ODB abstraction effort to restructure Git’s object storage layer to support alternative backends. The series also addresses an inefficiency in `odb_for_each_object()` where object lookups during enumeration redundantly traverse indices, risking incorrect pack selection and degrading performance.

The cleanup is ready to proceed and touches `builtin/pack-objects.c` to remove the unused `int` return from `add_object_entry()`. Peff’s latest email responds to Taylor’s observation about the incomplete refactoring in patch 3/8, noting that the non-bitmap traversal function `traverse_commit_list()` also ignores callback return values (its callbacks return `void`, not `int`). He suggests that the two traversal functions should remain consistent: either both should allow early termination via non-zero returns, or both should ignore callback return values. **Patrick Steinhardt has now responded to this design question**, proposing to leave both functions unchanged—`traverse_bitmap_commit_list()` continuing to ignore callback return values despite its callbacks returning `int`, and `traverse_commit_list()` retaining its `void`-returning callbacks. This approach avoids a large-scale refactoring but leaves the "foot-gun" in patch 3/8 unresolved. All other review feedback from v1 has been resolved: (1) Patch 1/8’s two open questions about object lookup behavior and the `if (opts->flags || data->request)` condition were clarified, confirming that reading from a different packfile is semantically incorrect but not harmful, and that `data->request` ensures the pack is populated for `packed_object_info()`. (2) Patch 3/8’s return-value changes were confirmed as safe due to dead code elimination. (3) Patch 4/8’s style suggestions were incorporated. (4) Patch 6/8’s design question—whether backends should be required to support a subset of object filters—was resolved in favor of the current design, which allows backends to ignore filters, consistent with Git’s existing patterns (e.g., reference backend exclude patterns). The v2 update adds one new patch (5/8) to drop unnecessary `_1()` suffixes from bitmap-opening functions, simplifies the logic in `open_bitmap_for_source()` by using a boolean instead of an integer, and improves commit message explanations. Patch 7/8 adds a `filter` field to the `odb_for_each_object_options` struct, allowing callers to pass object filters to backends for optimization. Backends may use these filters to skip excluded objects (e.g., via bitmaps) but are not required to, so callers must still re-apply the filter to yielded objects if strict filtering is needed. The "packed" backend implementation introduces a new `bitmapped_for_each_object()` callback that uses `prepare_bitmap_git_for_source()` to open bitmaps exclusively for the current object source, ensuring objects are correctly attributed to their source and avoiding redundant enumeration. The backend skips packs already covered by a bitmap during iteration, improving efficiency. The patch also exposes `can_filter_bitmap()` (previously static) to allow backends to check if a filter can be optimized via bitmaps. Taylor Blau’s latest review of patch 7/8 confirms it "looks plausibly correct" but notes limited familiarity with the pluggable ODB subsystem; the feedback is surface-level and does not engage with technical details or raise new considerations. The final patch (8/8) replaces the direct, backend-specific bitmap handling in `git cat-file --batch-all-objects` with the new ODB-mediated filtering mechanism, eliminating tight coupling between the command and the "packed" backend internals. The change removes 69 lines of intricate, backend-aware logic and replaces them with 7 lines that delegate filtering to the ODB layer via `odb_for_each_object_ext()`. The patch also removes the now-unused `pack-bitmap.h` include and drops three helper functions (`batch_one_object_packed`, `batch_one_object_bitmapped`, and the old bitmap-handling branch in `batch_each_object`).

**Patrick’s latest email addresses Taylor Blau’s performance concern in patch 1/8**, clarifying that the current implementation aborts iteration as soon as `match_hash()` reports a non-match, mitigating the inefficiency. However, he acknowledges uncertainty about whether the loop should iterate over the full MIDX chain (`m->num_objects + num_objects_in_base`) or just the primary MIDX (`m->num_objects`), highlighting a long-standing ambiguity in chained MIDX handling. He notes that the optimization proposed by Taylor (using the OID fanout chunk to narrow the iteration range) is worth pursuing but suggests deferring it to a separate series to avoid scope creep. This leaves the performance question unresolved but clarifies its boundaries: the current implementation is not incorrect, merely suboptimal. The tone remains collaborative, with no signs of contention.
