This is a feature patch introducing a new `post-worktree-remove` hook. It is the second patch in a three-patch series (v1) by Domen Kožar, with co-authorship attributed to an AI assistant.

The patch adds a hook that runs after `git worktree remove` deletes a worktree, providing external tools with a way to learn that a worktree has been removed. The hook receives two arguments: the absolute path of the removed worktree and its identifier (the name of its administrative directory under `$GIT_DIR/worktrees/`). The hook runs even if the worktree directory itself is already gone, as long as the administrative entry is being deleted. It does not run if the removal is refused (e.g., due to a locked or dirty worktree), and it cannot affect the outcome of the command—only its exit status is reflected in the overall exit status of `git worktree remove`.

The implementation touches `builtin/worktree.c` to invoke the hook, updates `Documentation/githooks.adoc` to document it, and adds four new tests in `t/t2403-worktree-move.sh` covering: basic invocation, removal of a missing worktree, refusal cases, and hook failure scenarios. The tests verify that the hook runs with the correct arguments and that its behavior aligns with the stated guarantees.

The motivation is clear: external tooling currently has no way to detect when a worktree is removed, which this hook addresses. The patch is narrowly scoped, well-tested, and follows the established pattern of Git’s post-command hooks. No prior discussion of this specific hook is referenced in the commit message, but the design aligns with existing hooks like `post-checkout` and `post-worktree-add`.
