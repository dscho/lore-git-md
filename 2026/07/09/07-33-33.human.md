This is a bug report (with a possible documentation improvement request) about confusing behavior in `git fetch`'s automatic tag fetching.

Ondřej Medek reports that `git fetch`'s automatic tag fetching behaves inconsistently depending on the refspec format. When fetching a branch like `master` without a destination ref (`:dst` part), tags are *not* fetched automatically, but when a destination ref is specified (e.g., `refs/heads/master:refs/remotes/origin/master`), tags *are* fetched. Even more puzzling, adding a dummy refspec with a destination (e.g., `refs/none/*:refs/none/*`) causes tags to be fetched for unrelated refspecs like `master`.

The current documentation states that tags pointing to fetched histories are fetched by default, but it doesn’t explain this refspec-dependent behavior. Ondřej tested this with a fresh tag (`tagTest`) pushed to the remote and confirmed the inconsistency across multiple refspec variations. The report suggests either documenting the current behavior (if intentional) or fixing it (if it’s a bug).

This looks like a genuine edge case that could trip up users, especially those scripting `git fetch` operations. The report is clear and includes reproducible examples, making it easy for a maintainer to investigate. If this is indeed unintended, it might require a small fix in the fetch logic; if intentional, the documentation should be updated to clarify the rules. Either way, it’s worth attention.
