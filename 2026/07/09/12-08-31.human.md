This is the second patch in Kristofer Karlsson’s v2 series fixing a quadratic performance regression in Git’s reftable backend when tombstones (deleted refs) are present. The patch removes the `suppress_deletions` flag from the reftable stack’s merged table and instead handles tombstone records explicitly at each call site in the reftable backend, where prefix and refname bounds are available. This allows iteration to terminate early when tombstones exceed the relevant bound, restoring linear performance.

The change is narrowly targeted: it touches only `refs/reftable-backend.c` (adding tombstone checks to ref and log iteration paths) and `reftable/stack.c` (removing the single line that set `suppress_deletions`). The `suppress_deletions` flag is retained in the reftable library API for downstream users like libgit2, preserving compatibility. Performance in the perf test (`p1401-ref-store-tombstones.sh`) improves from ~14 seconds to ~0.2 seconds in the worst-case scenarios.

The patch is well-motivated and addresses the root cause identified in the cover letter: the merged iterator’s `suppress_deletions` flag forced a full scan of all tombstones before higher-level bounds checks could terminate iteration. By moving tombstone handling to the call sites, the fix enables early termination and restores expected performance. The commit message clearly explains the affected code paths (`refs_verify_refnames_available()` and `reftable_backend_read_ref()`) and the mechanism of the fix.

This is a clean, focused bugfix with no controversial design choices. The v2 revision incorporates prior feedback about compatibility and test isolation, and the series appears ready for review. If you work with large repositories using the reftable backend, this patch is worth your attention.
