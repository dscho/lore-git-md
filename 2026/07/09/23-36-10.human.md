This is a feature patch introducing a new `post-worktree-remove` hook. It is the second patch in a three-patch series (v1) by Domen Kožar.

The patch adds a hook that runs after `git worktree remove` deletes a worktree, giving external tools a way to learn that a worktree is gone. The hook receives the former absolute path of the worktree and its identifier as arguments. It runs even if the worktree directory itself is already missing, but not if the removal is refused (e.g., because the worktree is locked or dirty). The hook cannot affect the outcome of the command, but its exit status is reflected in the exit status of `git worktree remove`.

The implementation is straightforward: a new `run_post_worktree_remove_hook` function is added to `builtin/worktree.c`, and it is called at the end of the `remove_worktree` function. The documentation (`githooks.adoc`) and tests (`t/t2403-worktree-move.sh`) are updated to describe and verify the new hook. The tests cover the happy path, the case where the worktree directory is already missing, and the case where the hook fails.

The patch looks well-crafted: the commit message is clear, the implementation is minimal, and the tests are thorough. There is no obvious controversy here; this is a sensible extension to Git's hook system that addresses a real gap. If you care about worktree lifecycle events, this patch is worth watching.
