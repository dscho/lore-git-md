This is a feature patch that extends Git's hook system to run the `post-worktree-remove` hook when worktrees are pruned, not just when they are explicitly removed with `git worktree remove`. Domen Kožar (with co-authorship from an AI assistant) adds support for triggering the hook during `git worktree prune`, which cleans up administrative entries after a worktree directory is deleted manually. The patch also ensures the hook receives the correct worktree path even when the directory is already gone, and propagates hook failures to the command's exit status.

The change is motivated by tooling that needs to observe all worktree deletions, not just explicit ones. The implementation modifies `should_prune_worktree()` to return the worktree path even for pruned entries, adjusts the pruning logic to invoke the hook for each removed entry (including duplicates), and updates the documentation to clarify the hook's behavior in prune scenarios. Eight new tests cover edge cases like dry runs, unknown paths, hook failures, and relative worktrees.

The patch is well-structured and thoroughly tested, addressing a clear gap in the hook's coverage. It should be uncontroversial since it extends existing functionality without changing behavior for users who don't use the hook. The only minor quirk is that the hook may receive an empty string for worktrees whose paths cannot be determined, but this is documented and seems reasonable.
