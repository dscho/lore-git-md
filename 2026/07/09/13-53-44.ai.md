This is a substantive review comment on the second patch of Kristofer Karlsson’s v2 two-patch series fixing a quadratic performance regression in the reftable backend. Patrick Steinhardt, the reftable backend maintainer, points out that while the patch removes Git’s internal use of the `suppress_deletions` flag from the merged iterator, it does not provide a clear mechanism for downstream users like libgit2 to set the flag. He proposes extending `struct reftable_stack_options` to allow callers to control suppression at stack creation time, ensuring compatibility without requiring libgit2 to modify its usage pattern.

The comment is narrowly scoped to the API surface: it does not question the core logic of the patch (moving tombstone handling to call sites) but instead addresses a downstream compatibility detail that was not fully resolved in v2. The proposed change would be mechanical—adding a field to `reftable_stack_options` and plumbing it through to the merged table—but it ensures that libgit2 can continue using the suppression feature without relying on internal implementation details. This is a forward-looking concern: the patch as written preserves libgit2’s current behavior, but Patrick’s suggestion future-proofs the API against changes in how the reftable library evolves.

The review is substantive (engaging with API design and compatibility) but not deeply technical: it does not identify a bug or edge case in the existing code, nor does it require rethinking the patch’s approach. It is a refinement rather than a blocker, and the author is likely to address it in a v3. The thread remains under active review, with no open technical questions beyond this compatibility detail.
