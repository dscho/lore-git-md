This is the second patch in Kristofer Karlsson’s two-patch series fixing a quadratic performance regression in Git’s reftable backend. The series targets a real-world slowdown: when Git re-creates refs that were previously deleted (leaving tombstones in the reftable stack), operations like `refs_verify_refnames_available()` and `reftable_backend_read_ref()` scan all tombstones before higher-level bounds checks can terminate, making them O(n) per call in tombstone-heavy scenarios.

The patch itself removes Git’s internal use of the `suppress_deletions` flag from the merged iterator, moving tombstone handling to the reftable backend’s call sites where prefix and refname bounds are available. This change restores early termination and cuts performance from ~14 seconds to ~0.2 seconds in the perf test’s 8000-ref scenarios. The fix is narrowly scoped to the reftable backend and does not affect other ref backends or the on-disk format.

In this reply, Kristofer acknowledges Patrick Steinhardt’s feedback on downstream compatibility. While the patch as written preserves libgit2’s current behavior, Patrick pointed out that libgit2 would lose the ability to set `suppress_deletions` once Git stops using it internally. Kristofer agrees to extend `struct reftable_stack_options` to expose the flag at stack creation time, ensuring libgit2 can continue using the feature without relying on internal implementation details. This is a mechanical refinement—adding a field and plumbing it through—but it future-proofs the API.

The patch is well-motivated, thoroughly tested (including a dedicated perf test), and addresses a real performance regression observed in production-scale repositories. The upcoming v3 will likely be the final version, incorporating this compatibility refinement. If you care about reftable performance or downstream compatibility with libgit2, this is worth tracking.
