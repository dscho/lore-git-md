This is a feature patch introducing a new `post-worktree-add` hook. Domen Kožar proposes adding a hook that fires after `git worktree add` completes, addressing a gap where tools managing per-worktree state (like IDEs or development environment managers) currently lack a reliable way to react to new worktrees. The existing `post-checkout` hook is insufficient because it’s skipped with `--no-checkout` or `--orphan` and can’t distinguish worktree creation from regular checkouts.

The hook runs inside the new worktree with `GIT_DIR` and `GIT_WORK_TREE` cleared, receiving the worktree’s absolute path and identifier as arguments. It executes *after* `post-checkout` (if that hook runs) and is skipped if `post-checkout` fails. A failing `post-worktree-add` hook doesn’t roll back the worktree but propagates its exit status to `git worktree add`. The implementation touches `builtin/worktree.c`, updates `githooks.adoc`, and includes thorough tests covering normal cases, `--no-checkout`, `--orphan`, bare repos, and relative paths.

The patch is well-motivated and clearly written, with a detailed commit message and comprehensive test coverage. It fits naturally into Git’s hook system and addresses a real workflow pain point. No controversy is evident, and the design aligns with existing hook conventions. This looks like a solid, uncontroversial addition that tools can immediately adopt.
