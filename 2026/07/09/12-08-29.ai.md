This is the v2 revision of a two-patch bugfix series targeting a quadratic performance regression in the reftable backend when tombstones (deleted refs) are present. The series is now narrowly scoped to address the root cause while preserving downstream compatibility with libgit2.

The core issue remains unchanged: the merged iterator’s `suppress_deletions` flag forces a full scan of all tombstones before higher-level bounds checks can terminate iteration, making operations like `refs_verify_refnames_available()` and `reftable_backend_read_ref()` O(n) per call in tombstone-heavy scenarios. The fix moves tombstone handling from the merged iterator to the reftable backend’s call sites, where prefix and refname bounds are available, enabling early termination when tombstones exceed the relevant bound.

Key changes since v1: the `suppress_deletions` flag is retained in the reftable library API for downstream users (e.g., libgit2) but is no longer set in `stack.c`, avoiding the regression while maintaining compatibility. The perf test (`p1401-ref-store-tombstones.sh`) now uses separate repositories for each scenario to prevent tombstone carryover, and the correctness test (`t0610-reftable-basics.sh`) was dropped as its coverage is already implicit in `t1400-update-ref.sh`. The commit message and scope description were broadened to clarify that the regression affects all readers (not just ref creation) and that auto-compaction does not always mitigate the issue.

Files touched: `refs/reftable-backend.c` (core logic), `reftable/stack.c` (single-line removal), and the new perf test. The performance improvement is dramatic: both test scenarios now run in ~0.2s (down from ~13s). The fix is well-motivated, narrowly targeted, and addresses prior feedback about compatibility and test isolation. No controversial design choices are evident, and the series appears ready for review.
