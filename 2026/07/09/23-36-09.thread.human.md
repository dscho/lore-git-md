This thread introduces a new `post-worktree-add` hook, proposed by Domen Kožar in a three-patch series (v1). The hook fills a gap in Git's current hook system by providing a reliable way for tools like IDEs or development environment managers to detect when a new worktree is created—something the existing `post-checkout` hook cannot do, as it is skipped when `--no-checkout` or `--orphan` is used and doesn’t distinguish between worktree additions and regular checkouts.

The implementation is straightforward and aligns with Git’s existing hook conventions. The hook runs unconditionally after `git worktree add` completes, regardless of checkout status, and receives the new worktree’s absolute path and identifier as arguments. It executes in the new worktree’s directory with `GIT_DIR` and `GIT_WORK_TREE` cleared, matching the environment of `post-checkout`. The hook runs *after* `post-checkout` and is skipped if that hook fails; its own failure does not delete the worktree but propagates its exit status to the `git worktree add` command. The patch updates `builtin/worktree.c`, documents the hook in `githooks(5)`, and includes thorough tests in `t/t2400-worktree-add.sh` covering normal cases, `--no-checkout`, `--orphan`, bare repositories, relative paths, and hook failure scenarios.

So far, the patch appears uncontroversial. The motivation is clear, the implementation is clean, and the test coverage is extensive. No objections or alternative approaches have been raised in this initial submission. The next steps will likely involve review feedback on the implementation details or documentation, but the design itself seems sound and well-justified.
