Thread identity: eleven-patch bugfix series (`js/coverity-fixes-v2`) by Johannes Schindelin (Dscho) via GitGitGadget, targeting NULL-dereference issues identified by Coverity. Thread type: patch series (bugfix).

Core problem or goal: eliminate NULL-dereference vulnerabilities in eleven files across diff, remote, reftable, mailsplit, bisect, replay, revision, pack-bitmap, shallow, and diffcore-break subsystems. Each patch adds a guard or early check to prevent dereferencing NULL pointers or using invalid file descriptors, addressing edge cases such as commits with unset `maybe_tree`, non-obvious NULL `remote` in `remote_tracking()`, partial initialization failures in reftable stack creation, `fopen()` failures in `mailsplit`, NULL commits in bisect functions due to concurrent gc or repository corruption, NULL returns from `peel_committish()` in `git replay --onto`, NULL returns from `get_reference()` in `revision.c`, missing base MIDX bitmaps in incremental MIDX chains, and shallow graft entries referencing missing commit objects. The final patch in the series (shallow.c) also addresses a latent bug in the same code path: the use of `oid_to_hex()`’s rotating static buffer in `write_one_shallow()` risks clobbering the `hex` variable before it is used in verbose logging, which Junio C Hamano proposes fixing by replacing it with a stack-allocated buffer and `oid_to_hex_r()`.

Current status: queued as GitGitGadget pull request `pr-2174`; under review. The series remains uncontroversial and well-motivated. The first five patches (diffcore-break.c, diff.c, reftable/stack.c, remote.c, and mailsplit.c) and the seventh patch (pack-bitmap.c) have received approval from Junio C Hamano, who confirmed the fixes as correct and ready for integration. The sixth patch (bisect.c, `bisect_successful()`) now requires a v3 update to address Junio’s feedback about using the `BISECT_FAILED` symbolic constant instead of the raw `-1` return value. The eighth patch (revision.c) now requires a test to prevent future regressions, as requested by Junio in his latest review. The ninth patch (bisect.c, `bisect_start()`) now requires either a test demonstrating the edge case or a clarification of its plausibility, as Junio’s review expresses skepticism about the real-world occurrence of `refs_resolve_ref_unsafe()` returning NULL while `repo_get_oid("HEAD")` succeeds. The fourth patch (remote.c) has a design disagreement between Dscho and Junio C Hamano regarding error-handling philosophy. The final patch (shallow.c) will require a v3 update to incorporate Junio’s suggested fix for the latent `oid_to_hex()` bug.

Key technical details:
- Files touched: diff.c, remote.c, reftable/merged.c, reftable/stack.c, mailsplit.c, bisect.c (two patches), replay.c, revision.c, pack-bitmap.c, shallow.c, diffcore-break.c.
- Symbols: guards added in functions already named in commit messages; no new public symbols. Specific guards:
  - In `diffcore_merge_broken()` (`diffcore-break.c`), `if (!pp) continue` mirrors existing pattern in outer loop. Junio C Hamano reviewed this patch and confirmed the fix as correct, noting it addresses a latent bug that has existed for over two decades.
  - In `cmd_diff()` (`diff.c`), `repo_get_commit_tree()` return value checked for NULL before dereferencing; if NULL, `die()` is called with a descriptive error message including the commit name. Junio C Hamano reviewed this patch and confirmed it as "obviously correct".
  - In `stack_destroy()` (`reftable/stack.c`), NULL check added before calling `read_lines()` to prevent passing NULL filename to `open()` when `reftable_new_stack()` fails partway through initialization. Junio C Hamano reviewed this patch and confirmed the fix as correct, calling it "Nice spotting and recovery. Well done."
  - In `remote_tracking()` (`remote.c`), the current patch returns `-1` if `remote` is NULL, treating it as "no tracking ref available". Junio C Hamano disagrees with this approach, arguing that the function is *designed* not to be called with a NULL `remote` and that silently returning `-1` obscures a programming error. He proposes using `BUG()` to explicitly fail when `remote` is NULL, making future regressions immediately visible. The disagreement is purely about error-handling philosophy, not the technical correctness of the guard itself.
  - In `split_mbox()` (`mailsplit.c`), NULL check for file handle `f` (returned by `fopen()`) moved before the `fileno(f)` call to prevent undefined behavior when `fopen()` fails. Junio C Hamano reviewed this patch and confirmed it as "obviously correct", noting the bug has existed since the code was introduced in 2022 (commit `7b20af6a06`).
  - In `bisect_successful()` (`bisect.c`), NULL check added for the commit returned by `lookup_commit_reference_by_name()`; if NULL, the function returns an error rather than dereferencing the pointer. Junio’s review identifies a maintainability issue: the patch returns the raw `-1` from `error()` instead of the symbolic `BISECT_FAILED` constant defined in `bisect.h`. The fix is a one-line adjustment (`return BISECT_FAILED` instead of `return res`) and does not alter the patch’s defensive intent or behavior.
  - In `bisect_start()` (`bisect.c`), NULL check added after `refs_resolve_ref_unsafe()` returns NULL but `repo_get_oid("HEAD")` succeeds, using `"HEAD"` as a fallback to prevent dereferencing NULL. Junio’s review questions the real-world plausibility of this edge case, specifically whether `refs_resolve_ref_unsafe()` can return NULL while `repo_get_oid("HEAD")` succeeds (e.g., in a detached bare OID scenario with reftable backend). The fix itself is uncontroversial, but Junio requests a test to demonstrate the bug or clarify why it cannot be triggered.
  - In `replay.c`, NULL check added after `peel_committish()` call in the `--onto` code path; if the object does not peel to a commit, `die()` is called with a clear error message.
  - In `add_parents_only()` (`revision.c`), explicit handling added for all three NULL-return scenarios from `get_reference()`: returning `0` for `ignore_missing` and `do_not_die_on_missing_objects`, and `-1` for `exclude_promisor_objects`. Junio’s review requests a test to prevent future regressions, noting the fix is "Nicely spotted" but that the edge case is subtle enough to warrant regression coverage.
  - In `load_midx_bitmap()` (`pack-bitmap.c`), NULL check added after `prepare_midx_bitmap_git()` call when loading the base MIDX bitmap in an incremental MIDX chain; if the base MIDX lacks a bitmap, the code jumps to cleanup and returns `-1`. Junio C Hamano reviewed this patch and endorsed the reasoning and fix, calling it "Nicely reasoned." The fix addresses a real-world edge case where a base MIDX is written without `--write-bitmap-index` or its bitmap is pruned by `gc`, while the incremental layer’s bitmap still references it.
  - In `write_one_shallow()` (`shallow.c`), the verbose logging code now uses `graft->oid` instead of `c->object.oid` when `lookup_commit()` returns NULL for a shallow graft entry’s commit object. Additionally, Junio’s review identifies a latent bug in the same function: the use of `oid_to_hex()`’s rotating static buffer risks clobbering the `hex` variable before it is used in verbose logging. The proposed fix replaces the static buffer with a stack-allocated buffer (`hex[GIT_MAX_HEXSZ + 1]`) and uses `oid_to_hex_r()` to ensure the string remains valid throughout the function.
- Behavior: purely defensive; no new user-visible behavior beyond error messages for edge cases; rare edge cases addressed without altering normal operation.
- On-disk format: unchanged.
- Test coverage: none added yet; Junio’s reviews of the eighth (revision.c) and ninth (bisect.c, `bisect_start()`) patches request tests to prevent future regressions. Existing tests expected to verify guards do not break normal operation.
