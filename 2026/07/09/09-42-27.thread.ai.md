Thread identity: eleven-patch bugfix series (`js/coverity-fixes-v2`) by Johannes Schindelin (Dscho) via GitGitGadget, targeting NULL-dereference issues identified by Coverity. Thread type: patch series (bugfix).

Core problem or goal: eliminate NULL-dereference vulnerabilities in eleven files across diff, remote, reftable, mailsplit, bisect, replay, revision, pack-bitmap, shallow, and diffcore-break subsystems. Each patch adds a guard or early check to prevent dereferencing NULL pointers or using invalid file descriptors, addressing edge cases such as commits with unset `maybe_tree` (not in commit-graph), non-obvious NULL `remote` in `remote_tracking()`, partial initialization failures in reftable stack creation, `fopen()` failures in `mailsplit`, NULL commits in `bisect_successful()` and `bisect_start()` due to concurrent gc or repository corruption, NULL returns from `peel_committish()` when given non-commit objects in `git replay --onto`, NULL returns from `get_reference()` in `revision.c` when `exclude_promisor_objects` or `do_not_die_on_missing_objects` is set, missing base MIDX bitmaps in incremental MIDX chains, and shallow graft entries referencing missing commit objects.

Current status: queued as GitGitGadget pull request `pr-2174`; no prior version recorded. Under review; no maintainer decision yet.

Key technical details:
- Files touched: diff.c, remote.c, reftable/merged.c, reftable/stack.c, mailsplit.c, bisect.c (two patches), replay.c, revision.c, pack-bitmap.c, shallow.c, diffcore-break.c.
- Symbols: guards added in functions already named in commit messages; no new public symbols. Specific guards:
  - In `diffcore_merge_broken()` (`diffcore-break.c`), `if (!pp) continue` mirrors existing pattern in outer loop.
  - In `cmd_diff()` (`diff.c`), `repo_get_commit_tree()` return value checked for NULL before dereferencing; if NULL, `die()` is called with a descriptive error message including the commit name.
  - In `remote_tracking()` (`remote.c`), NULL check for `remote` added, returning `-1` if NULL to treat it as "no tracking ref available" rather than risking a crash.
  - In `stack_destroy()` (`reftable/stack.c`), NULL check added before calling `read_lines()` to prevent passing NULL filename to `open()` when `reftable_new_stack()` fails partway through initialization (e.g., out-of-memory before `reftable_buf_detach` assigns `p->list_file`).
  - In `split_mbox()` (`mailsplit.c`), NULL check for file handle `f` (returned by `fopen()`) moved before the `fileno(f)` call to prevent undefined behavior when `fopen()` fails. The fix is three lines moved; no new logic introduced.
  - In `bisect_successful()` (`bisect.c`), NULL check added for the commit returned by `lookup_commit_reference_by_name()`; if NULL, the function returns an error rather than dereferencing the pointer in `repo_format_commit_message()`.
  - In `bisect_start()` (`bisect.c`), NULL check added after `refs_resolve_ref_unsafe()` returns NULL but `repo_get_oid("HEAD")` succeeds. The variable `head` is set to the string literal `"HEAD"` as a fallback to prevent dereferencing NULL in subsequent `repo_get_oid()` and `starts_with()` calls. This edge case is rare but plausible, particularly with the reftable backend where symbolic ref resolution might fail even when the OID is valid.
  - In `replay.c`, NULL check added after `peel_committish()` call in the `--onto` code path; if the object does not peel to a commit, `die()` is called with a clear error message instead of dereferencing the NULL pointer.
  - In `add_parents_only()` (`revision.c`), explicit handling added for all three NULL-return scenarios from `get_reference()`: returning `0` for `ignore_missing` and `do_not_die_on_missing_objects` (consistent with existing patterns in `handle_revision_arg()` and `process_parents()`), and `-1` for the `exclude_promisor_objects` case. The caller’s return-value handling treats `-1` as success for `commit^@`/`commit^!` pseudo-options, so the fix aligns with existing behavior.
  - In `load_midx_bitmap()` (`pack-bitmap.c`), NULL check added after `prepare_midx_bitmap_git()` call when loading the base MIDX bitmap in an incremental MIDX chain. If the base MIDX lacks a bitmap, the code jumps to the existing cleanup label that unmaps the current bitmap and returns `-1`, forcing the caller to fall back to non-bitmap object enumeration. The fix is four lines added and matches the error-handling pattern already used elsewhere in the same function.
  - In `write_one_shallow()` (`shallow.c`), the verbose logging code now uses `graft->oid` instead of `c->object.oid` when `lookup_commit()` returns NULL for a shallow graft entry’s commit object. This prevents a crash while preserving the intended verbose output.
