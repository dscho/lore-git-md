This is the final patch in Justin Tobler’s ODB transaction series, and Junio C Hamano’s reply raises a process-lifecycle question about the new transaction object. The patch itself is a clean conversion: it replaces the global `tmp_objdir` with a local `struct odb_transaction *` that is created at the start of the unpack phase and committed just before reference updates. The quarantine semantics are preserved—objects land in an “incoming” directory and are migrated to the main object store only after pre-receive hooks and connectivity checks pass.

Junio’s concern is narrow but important: if `unpack_with_sideband()` fails, `execute_commands()` returns early without committing the transaction, and the transaction object is simply left to be cleaned up at process exit. For file-based backends the tempfile/lockfile API will handle it, but Junio wonders whether there are other resources (e.g., in-memory state, backend-specific locks, or future pluggable backends) that might need explicit cleanup. He suggests adding an `odb_transaction_abort()` call in the error path to make the lifecycle symmetric and future-proof.

The question is purely defensive; there is no known leak or misbehavior today. It is a surface-level review observation rather than a substantive design critique, and the fix—if needed—would be a one-line addition in the error path. The series as a whole remains ready for `next`; this is a minor hygiene point that can be addressed in a follow-up or even in-tree.
