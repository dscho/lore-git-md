This is a **contributor housekeeping** patch for `git-subtree` in `contrib/`, part of a two-patch series that adds a safeguard against mixing the existing shell-script implementation with a forthcoming Rust rewrite. The series is now in its final form after addressing all review feedback, and this email is a minor follow-up in the discussion.

Colin Stagner’s reply confirms the design choice to check only the top-level repository (the "downstream" project) for the `subtree.rust-rewrite` config key, not the subtree’s internal `.git-subtree/config`. He also asks whether the Rust rewrite will honor config files in other locations (working tree, `HEAD:.git-subtree/config`, etc.), but Ian Jackson has already clarified that the Rust version will only read `.git-subtree/config` at the root of the revision being manipulated, so the current detection logic is correct.

The only other point raised is a reminder that the Rust rewrite will not support "unmarked subtree merges" (those performed manually with `git merge -X subtree`). Colin notes that such merges would likely fail with "unrelated history" warnings if `--squash` is in use, but the Rust version will not attempt to detect or prevent them at runtime. This limitation will be documented and tested separately.

The series itself is ready: the scoping bug in the detection helper is fixed, the error message is settled, and the test case now uses idiomatic Git test framework patterns (`test_create_repo`, `test_commit --no-tag`, and `test_must_fail git ... 2>err && test_grep`). No further changes are expected. If you care about `git-subtree` or the upcoming Rust rewrite, this is a small but important safeguard worth reviewing.
