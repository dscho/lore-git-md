This is the fourth patch in Johannes Schindelin’s eleven-patch bugfix series addressing NULL-dereference issues identified by Coverity. This patch targets the reftable backend, specifically the `stack_destroy` function in `reftable/stack.c`.

The problem is straightforward: when `reftable_new_stack()` fails partway through initialization (for example, due to an out-of-memory error), it jumps to an error path that calls `reftable_stack_destroy()`. At this point, `st->list_file` may still be NULL because the initialization step that assigns it (`reftable_buf_detach`) never completed. The current `reftable_stack_destroy()` unconditionally passes `st->list_file` to `read_lines()`, which expects a valid filename and will crash if given NULL. The fix adds a simple NULL check before calling `read_lines()`, which is safe because if `list_file` is NULL, there are no table files to clean up anyway.

The change is minimal—just two lines added—and mirrors defensive patterns already used elsewhere in the codebase. The commit message clearly explains the failure scenario and why the fix is correct. This is a classic defensive-programming bugfix: no new behavior is introduced, and the patch is unlikely to be controversial. Given the reftable backend’s role in ref storage, this fix is important for stability, especially in error paths that might otherwise go unnoticed.
