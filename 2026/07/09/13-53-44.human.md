This is the second patch in Kristofer Karlsson’s two-patch series fixing a quadratic performance regression in Git’s reftable backend. The thread is focused on a narrow but important compatibility detail: how downstream users like libgit2 can continue to suppress tombstone (deleted ref) records after the patch removes Git’s internal use of the `suppress_deletions` flag.

Patrick Steinhardt’s reply is a substantive review comment. He acknowledges that the `suppress_deletions` field remains in the reftable library API but points out that libgit2 currently sets it via `stack.c`, which this patch removes. His suggestion is to expose the flag through `struct reftable_stack_options` instead, giving callers explicit control at stack creation time. This is a small but meaningful improvement to the patch’s compatibility story—it preserves libgit2’s ability to suppress tombstones without requiring them to fork the reftable library or rely on internal implementation details.

The rest of the series remains uncontroversial and well-motivated. The performance fix itself (moving tombstone handling to call sites where bounds checks enable early termination) is not in question; this is purely about the API surface. Kristofer’s v2 already addressed prior feedback on test isolation and correctness coverage, and brian m. carlson’s real-world validation confirms the regression is not theoretical. If this compatibility tweak is incorporated, the series looks ready to land.
