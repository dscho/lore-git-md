This is the fourth patch in Harald Nordgren’s **v20 `git branch --delete-merged` series**, which is now unblocked and ready for merging. This patch prepares the `delete_branches()` function for the upcoming `--delete-merged` subcommand by adding a new flag, `DELETE_BRANCH_NO_HEAD_FALLBACK`, to prevent falling back to `HEAD` when no upstream is configured. This ensures the `--delete-merged` command only deletes branches that are merged into their upstream, without silently defaulting to `HEAD` as a reference point.

The change is minimal and targeted: it modifies `delete_branches()` to skip the `HEAD` fallback when the new flag is set, and updates the `branch_merged()` helper to avoid printing a "gentle reminder" about `HEAD` fallback when the caller explicitly opts out. The patch preserves existing behavior for all current callers (e.g., `git branch -d`), which continue to use the `HEAD` fallback as before. The new flag will be used by the `--delete-merged` subcommand (introduced in patch 5/7) to enforce stricter upstream-based deletion criteria.

This is a **refactoring patch** that introduces no new user-visible behavior but enables the core functionality of the series. The change is well-motivated and aligns with the series’ goal of providing precise, upstream-based branch cleanup. The commit message clearly explains the purpose of the flag and its intended use case. No test coverage is added here, as the flag’s behavior will be exercised by the `--delete-merged` tests in later patches.

The patch touches only `builtin/branch.c` and is part of the **flags-based API refactoring** (patches 2-4/7) that replaces boolean arguments with an `unsigned int flags` parameter. Earlier versions of this refactoring had a maintenance risk due to local boolean caching, but that issue has been resolved in v20 by eliminating cached values and ensuring flags remain the single source of truth. This patch specifically adds the `DELETE_BRANCH_NO_HEAD_FALLBACK` flag, which is tested directly at its use site to avoid stale state.

The series as a whole is **implementation-complete**, with all safety mechanisms (per-branch opt-out, `--dry-run`, order-independent stacked-branch protection) and filtering capabilities (repeatable `--delete-merged` arguments, positional branch patterns) now in place. The stacked-branch protection logic has been structurally refactored in v20 to resolve the order dependency that previously blocked the series, addressing Junio C Hamano’s correctness concerns. The only agreed follow-up work is extending stacked-branch protection to `git branch -d` for consistency, which will be implemented after the series lands.
