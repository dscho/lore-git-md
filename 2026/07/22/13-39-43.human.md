The key change in v20 is a **structural rewrite of the stacked-branch protection logic** to make it independent of ref iteration order. Instead of mutating the deletion set (`deletable`) during the ref iteration (which could produce inconsistent results depending on the order branches were visited), the new implementation:

1. **Collects all protected branches in a single pass** using a new `collect_stacked_branch_bases()` function that walks upstream chains from each surviving branch, marking every branch in the chain as protected.
2. **Defers mutation of the deletion set** until after the ref iteration completes, ensuring the result is deterministic regardless of iteration order.
3. **Uses three strsets** to track state:
   - `deletable_branch_names`: branches initially marked for deletion.
   - `protected_branch_names`: branches that must be kept because they are upstreams of unmerged branches.
   - `visited_branch_names`: branches already processed to avoid infinite loops in self-referential upstream chains.

The old approach (v19) removed branches from `deletable` during the ref iteration, which could miss some dependencies if the iteration order didn’t visit upstream branches before their dependents. The new approach guarantees all dependencies are discovered before any deletions are finalized.

The v20 refactor eliminates this edge case by decoupling discovery from mutation.
