Subject: [PATCH v2] compat/regex: work around macOS TRE regexec() memory leak
Series version: standalone patch, v2
Originating author: Chungmin Lee
Thread type: platform-specific bugfix

Core problem or goal
Fix a memory leak in Git’s macOS builds when the system regex engine (TRE) processes invalid UTF-8 sequences. A single `git grep` over binary files (e.g., PDFs) can leak gigabytes, risking kernel watchdog panics. The patch adds a Darwin-specific workaround in dedicated platform files (`compat/darwin.h` and `compat/darwin/regexec.c`) that splits input buffers at invalid multibyte boundaries and searches each valid segment separately, avoiding the leaking code path while preserving all genuine matches.

Current status
Ready for merging; v2 addressed Junio C Hamano’s structural concerns about long-term maintainability and platform-specific override organization. Junio’s latest feedback proposes a trivial `Makefile` comment addition (provided as a ready-to-squash patch) to document the `DARWIN_REGEXEC` flag alongside other platform-specific symbols. Patrick Steinhardt has raised a **new design-level question**: whether the fix should be temporary (falling back to Git’s built-in regex via `NO_REGEX` for affected macOS versions) or permanent (the current Darwin-specific override). The patch remains narrowly scoped to macOS builds using the system regex engine (skipped when `NO_REGEX` is set). All build systems (Makefile, Meson, CMake) are updated using the `DARWIN_REGEXEC` flag. Regression tests in `t7810-grep.sh` verify matches around invalid bytes, correct anchoring of `^`/`$`, and edge cases like incomplete trailing sequences.

Key technical details
Files touched: `compat/darwin.h`, `compat/darwin/regexec.c`, `t7810-grep.sh`, `Makefile` (comment only)
New symbols: none (internal-only logic)
Behavior change: none for valid UTF-8; invalid sequences are split at the exact bytes rejected by `mbrtowc()`, ensuring consistency with TRE’s decoder
On-disk format: unchanged
Test coverage: new tests in `t7810-grep.sh` for invalid UTF-8 handling (macOS-specific) and `^`/`$` anchoring (runs on all `MB_REGEX` platforms). Tests use POSIX regex patterns to avoid the fixed-string optimization, ensuring they exercise the patched code path.

Open questions and loose ends
1. **Design direction**: Patrick Steinhardt’s review proposes detecting affected macOS versions and falling back to Git’s built-in regex (`NO_REGEX`) instead of maintaining a Darwin-specific workaround. Key unknowns:
   - Whether Git’s built-in regex avoids the leak (and if so, why it wasn’t chosen initially).
   - Performance and feature parity of the built-in regex on macOS.
   - How version detection would work (e.g., macOS SDK versions or runtime behavior).
   - Maintainability burden of the current workaround versus a detection-based fallback.
   No counterarguments or data have been presented yet; the question is unresolved.
2. Test scope: The anchor-related tests run on all `MB_REGEX` platforms, but the invalid-UTF-8 matching tests remain macOS-specific. No objections raised.
3. Upstream macOS fixes: The commit message and code comments treat the workaround as indefinite, acknowledging that Git will need to support affected macOS releases even after upstream fixes. No speculation on timeline.
4. `Makefile` documentation: Junio proposed adding a comment to document when users should define `DARWIN_REGEXEC`; this is pending but trivial to implement.
