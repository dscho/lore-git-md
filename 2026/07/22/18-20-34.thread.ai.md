Subject: [RFC] Re-enable symlinks in submodule paths via config
Series version: none (user request, no patch)
Originating author: Kyle Marek
Thread type: user request / RFC

Core problem or goal
Kyle Marek requests a configuration knob (`safe.submodule.path`) to opt out of the security-motivated restriction introduced in commit e8d060894448 ("submodule--helper: reject symlinks in submodule paths", 2024-05-15). The restriction broke workflows that share a single submodule checkout across multiple worktrees via symlinks.

Current status
No patch exists; the request is for project feedback on whether such a knob would be accepted. The restriction remains in place.

Key technical details
- Files touched: `builtin/submodule--helper.c` (contains the TODO comment proposing the config variable)
- Subsystem: submodule path validation
- New config key: `safe.submodule.path` (proposed, not yet implemented)
- Behavior change: when set, symlinks in submodule paths would be allowed again
- On-disk format: unchanged
- Test coverage: none yet

Open questions and loose ends
- Would the project accept a patch implementing the config knob?
- If accepted, what should the default value be (safe-by-default vs. opt-in)?
- Should the config be a boolean or an enum allowing finer-grained control?
- Are there additional security considerations beyond the original commit’s rationale?

Participant positions
- Kyle Marek (author): argues the blanket prohibition is overly paternalistic and requests an opt-out mechanism. Position is substantive (engages with the security-vs-usability trade-off).
