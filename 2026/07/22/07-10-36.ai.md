This is the core implementation patch of Harald Nordgren’s `git branch --delete-merged` series, now **unblocked and ready for merging** after resolving the last correctness issue (order dependency in stacked-branch protection). The patch adds the `--delete-merged` subcommand to `git branch`, which safely deletes local branches whose work has already landed on their upstream while preserving branches used as upstreams for unmerged work.

The command supports **repeatable `--delete-merged` arguments** (e.g., `--delete-merged origin/main --delete-merged origin/next`) to widen the upstream match and **optional positional patterns** (e.g., `topic-*`) to limit deletion scope. It skips checked-out branches, branches with missing upstreams, and branches that push to their upstream (e.g., `main` tracking `origin/main`), ensuring no false positives. A branch is only deleted if its tip is reachable from its upstream and it is not used as an upstream for an unmerged branch.

The **stacked-branch protection logic** has been refactored to be **order-independent**, addressing Junio C Hamano’s blocking concern. The new implementation collects all protected branches in a single pass before mutating the deletion set, ensuring consistent results regardless of ref iteration order. The `deletable` and `spared` strsets are indexed by **branch names** (e.g., `main`) rather than full refnames, aligning with `branch_get()` and `branch_get_upstream()` behavior.

The patch includes **comprehensive test coverage** verifying all safety checks, edge cases (e.g., self-referential upstreams, missing upstreams), and the order-independent stacked-branch protection behavior. The tests also confirm the command respects per-branch opt-out (via `branch.<name>.deleteMerged=false`) and `--dry-run` functionality, both implemented in later patches.

Key files touched: `builtin/branch.c` (core logic), `Documentation/git-branch.adoc` (man page updates), and `t/t3200-branch.sh` (integration tests). The implementation is **well-motivated** (addressing a real workflow pain point) and **thoroughly tested**, with clear documentation and a flags-based API designed for future extensibility.
