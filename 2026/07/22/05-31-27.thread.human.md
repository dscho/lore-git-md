This thread is about a memory leak in Git’s macOS builds when the system regex engine (TRE) processes invalid UTF-8 sequences. The issue can cause `git grep` over binary files (like PDFs) to leak gigabytes of memory, risking kernel watchdog panics. Chungmin Lee’s patch adds a Darwin-specific workaround in `compat/regexec.c` that splits input buffers at invalid multibyte boundaries, avoiding the leaking code path while preserving all genuine matches.

The patch is now in its second version, which adopts Junio C Hamano’s suggestion to organize the Darwin-specific override in a dedicated platform header (`compat/darwin.h`) and implementation file (`compat/darwin/regexec.c`). This makes the codebase more modular and maintainable. The core logic remains unchanged—splitting buffers at invalid sequences using `mbrtowc()` and searching each segment separately—but the patch now includes clearer documentation and treats the workaround as indefinite, acknowledging that Git will need to support affected macOS releases even after upstream fixes. Build system integration is consistent across Makefile, Meson, and CMake, using a single `DARWIN_REGEXEC` flag.

Test coverage has expanded to verify matches around invalid bytes, correct anchoring, and edge cases like incomplete trailing sequences. While the invalid-UTF-8 matching tests remain macOS-specific, the anchor-related tests now run on all `MB_REGEX` platforms, improving broader regression detection. Junio’s earlier concerns about structural maintainability and test scope have been addressed, and the patch is ready for further review from macOS users and reviewers familiar with regex internals or platform-specific workarounds. No technical objections remain, and the modular approach sets a good precedent for future platform overrides.
