This thread is about a memory leak in Git’s macOS builds when the system regex engine (TRE) processes invalid UTF-8 sequences, such as those found in binary files. The leak can be severe enough to trigger kernel watchdog panics during operations like `git grep`. Chungmin Lee’s v2 patch adds a Darwin-specific workaround that splits input buffers at invalid multibyte boundaries, avoiding the leaking code path while preserving all genuine matches. The fix is narrowly scoped to macOS builds using the system regex engine and includes regression tests for edge cases like invalid UTF-8 handling and anchor behavior.

The patch is ready for merging, having addressed Junio C Hamano’s earlier concerns about maintainability and platform-specific override organization. Junio’s latest feedback proposes only a trivial `Makefile` comment addition to document the `DARWIN_REGEXEC` flag. However, Patrick Steinhardt has raised a new question about the long-term maintainability of the current approach. He suggests detecting affected macOS versions and falling back to Git’s built-in regex implementation (`NO_REGEX`) instead of maintaining a custom workaround, arguing that this might be cleaner given that Apple is expected to fix the underlying issue eventually. This discussion is still open, and no counterarguments or data about the built-in regex’s performance or memory behavior have been presented yet.

The thread remains focused on whether the current workaround or a version-detection-based fallback is the better long-term solution. The patch itself is technically sound and ready for merging unless the discussion converges on the `NO_REGEX` alternative.
