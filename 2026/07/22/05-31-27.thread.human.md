This thread is about a **platform-specific bugfix for macOS** that plugs a memory leak in Git’s system regex engine (TRE) when processing invalid UTF-8 sequences. The issue is severe: a single `git grep` over binary files (like PDFs) can leak gigabytes of memory, risking kernel watchdog panics. Chungmin Lee’s patch adds a Darwin-specific workaround in `compat/regexec.c` that splits input buffers at invalid multibyte boundaries, avoiding the leaking code path while preserving all genuine matches. The fix is narrowly scoped to macOS builds using the system regex engine (skipped when `NO_REGEX` is set, e.g., in ASAN builds) and includes regression tests in `t7810-grep.sh` to verify matches around invalid bytes and correct anchoring of `^`/`$`.

Junio C Hamano’s review raises two structural concerns without challenging the patch’s correctness. First, he questions how long the workaround will need to be maintained—whether it’s a temporary fix or a permanent fixture—since the commit message doesn’t speculate on upstream macOS fixes. Second, he suggests a more modular approach for future platform-specific overrides, proposing that each override live in its own platform header and be conditionally included in `git-compat-util.h` to avoid cluttering the main header with nested `#ifdef` chains. He also notes that the test coverage, while thorough, is currently restricted to macOS builds using multibyte regex, which may limit broader regression detection.

The patch itself is ready for deeper technical review, particularly from macOS users and regex subsystem experts. No substantive objections or requests for changes have been raised yet, and the fix integrates cleanly across all build systems (Makefile, Meson, CMake). The discussion now centers on long-term maintainability rather than immediate correctness.
