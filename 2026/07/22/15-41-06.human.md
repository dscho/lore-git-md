This is the final reply in the long-running `git branch --delete-merged` series, now **implementation-complete and unblocked for merging**. Harald Nordgren responds to Phillip Wood’s request for clarification about the **order-independent stacked-branch protection** refactor in v20.

The core change in v20 is a **structural refactor** of the stacked-branch protection logic to eliminate an **order dependency** that could produce inconsistent results. The new implementation (`protect_stacked_branch_bases()`) collects all protected branches in a single pass before mutating the deletion set, ensuring consistent behavior regardless of ref iteration order. This directly addresses Junio C Hamano’s blocking correctness concern from earlier versions.

Harald explains that the previous approach (removing spared branches from the deletion set *during* ref iteration) was insufficient because it could produce different results depending on the order in which branches were processed. For example, if `b1` was processed before `b2` (where `b2→b1`), `b1` would be spared, but if `b2` was processed first, `b1` might be incorrectly deleted. The new implementation avoids this by deferring all mutations until after the full set of protected branches is collected.

The refactor introduces:
- `collect_stacked_branch_bases()`: A new helper function that traverses upstream chains from each branch, marking all transitively required branches as "protected" before any deletions occur.
- `visited_branch_names` strset: Avoids infinite loops in self-referential upstream chains (e.g., `b3→b3`).
- `protected_branch_names` strset: Replaces the previous `spared` set with clearer semantics.
- `refs_for_each_ref_ext()` with `prefix` option: Limits iteration to local branches, avoiding unnecessary work.
