This is Patrick Steinhardt’s response to the ongoing discussion about the `git receive-pack` performance regression introduced by the ODB abstraction rework. The email is a **design-level reply** from the author of the ODB rework, addressing Junio’s proposal to distinguish "fast" and "slow" lookups within ODB backends and offering an alternative architectural direction.

Patrick acknowledges the regression’s root cause (the `tmp_objdir` case modifying the list of ODB sources during transactions) and agrees that the current approach feels "gross." He proposes a longer-term solution: **eliminating the need to modify the ODB source list during transactions entirely**. Instead of redirecting writes to a temporary object directory by swapping sources, he suggests embedding transaction-awareness directly into functions like `odb_write()`. If an active transaction exists, writes would go into the transaction rather than the primary ODB source, removing the need to alter the source list. This would prevent the problematic loose-object checks in the quarantine directory during connectivity checks, as objects written to the transaction wouldn’t be visible for reading until the transaction commits.

The proposal is framed as a cleanup that aligns with his and Justin Tobler’s existing plans, rather than a targeted fix for the regression. Patrick notes that this change shouldn’t disrupt current behavior, since Git doesn’t typically read objects immediately after writing them to a transaction. He also hints that this could pave the way for further refactoring, such as moving all object writes exclusively into transactions. However, he’s currently out of office and won’t be able to explore this further for at least two weeks.

This email shifts the thread’s focus from a narrow performance fix to a broader architectural question: **how should the ODB abstraction handle transactions and source lists?** While Patrick’s proposal doesn’t directly address Junio’s "fast" vs. "slow" lookup idea, it offers a more principled alternative that could resolve the regression as a side effect. The response is measured and forward-looking, but the timeline suggests the regression may not be fixed immediately.
