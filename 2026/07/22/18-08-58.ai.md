This is the second patch in Harald Nordgren’s v4 series fixing push-tracking after remote renames when `branch.<name>.pushRemote` is set to a URL. The patch implements the core logic to resolve a URL-valued push destination to a configured remote for tracking purposes, ensuring `git status` and `@{push}` work correctly even after remotes are renamed or rearranged.

The patch introduces `repo_remote_for_push_tracking()`, a new helper in `remote.h` that consults Git’s URL-to-remote map to find a fallback remote when the originally configured push remote is missing or is a URL. The helper prefers the *effective push URL* (using `pushurl` over `url` when both are present) and handles `pushInsteadOf` rewrites, ensuring the fallback logic aligns with where the push would actually go. If exactly one configured remote matches the URL, it is used for push tracking; if multiple remotes share the URL, the behavior remains unchanged to avoid ambiguity. The test suite in `t/t5505-remote.sh` has been extended to cover rename scenarios, URL resolution, `pushInsteadOf` handling, up-to-date pushes, duplicate URL edge cases, and the `pushurl` path (144 new lines).

Key technical details include the new `remote_has_push_url()` helper, the explicit preference for `pushurl` over `url` in the resolution logic, and the unchanged on-disk format. The documentation in `Documentation/config/branch.adoc` and `Documentation/revisions.adoc` has been updated to clarify that `branch.<name>.pushRemote` may now be a URL and how `@{push}` behaves in that case. The patch touches `remote.c`, `remote.h`, `transport.c`, and the test script, and is motivated by workflows involving GitHub’s `gh` CLI, which renames remotes during forking.

The series is technically complete, with thorough test coverage and clear documentation.
