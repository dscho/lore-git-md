This is a bugfix series targeting the `rev-parse --parseopt` help flag behavior. The four-patch series from brian m. carlson implements the final agreed solution to make Git's help flag exit codes consistent with Unix conventions—exiting 0 when help is explicitly requested (`--help` or `-h`) rather than the current error code 129.

The series addresses a long-standing inconsistency in how `git rev-parse --parseopt` handles help requests, which has been present since 2007. The change ensures that scripts using this command (and the parse-options infrastructure more broadly) exit cleanly when help is requested, aligning with the standard Unix practice where help output is considered successful user-requested output. The implementation distinguishes between help explicitly requested by the user (exit 0) and help triggered by invalid options (exit 129), preserving useful debugging information for the latter case.

The patches touch a wide range of files—40 in total—but the changes are mostly mechanical. The core logic is in `parse-options.c`, where the help output handling is adjusted, while the bulk of the changes update test expectations to reflect the new exit code behavior. One patch also fixes a minor unrelated issue (skipping svn tests when svn is not installed), which was likely included to avoid test failures in environments without svn.

The series is well-motivated and has already received thorough discussion and approval from key maintainers, including Junio C Hamano and Jeff King. The regression in `git instaweb` (where `-h` previously exited 129 but now exits 0) was identified and resolved as part of this effort, and the solution has been confirmed to not require a major version bump. This looks like a clean, uncontroversial fix that improves Git's consistency without significant compatibility risks.
