Subject: [PATCH] ci: adjust PID limits in Dockerized jobs on private GitHub repositories
Series version: standalone patch
Originating author: Johannes Schindelin (Dscho)
Thread type: bug fix / CI configuration

Core problem or goal
GitHub Actions workflows for Git’s CI fail consistently in private repositories due to Dockerized jobs hitting default PID limits on hosted runners. The error “cannot create async thread: Resource temporarily unavailable” surfaces in the t5xxx-t6xxx test range, blocking private-repository testing of Microsoft Git changes.

Current status
Patch submitted; no prior iterations. Junio C Hamano reviewed the commit message, noting the subject line (“limit PIDs”) inaccurately describes raising the limit to 16,384. The technical approach—conditional container options (`--pids-limit=16384`, `--ulimit=nproc=16384`, `--ulimit=nofile=32768`) applied only when `github.repository_visibility` is private—remains uncontested. No review trailers or testing feedback yet.

Key technical details
- File touched: `.github/workflows/main.yml`
- New container options: `--pids-limit=16384`, `--ulimit=nproc=16384`, `--ulimit=nofile=32768`
- Conditional: only applied when `github.repository` is private
- Benchmarking data in commit message shows 16 k is the optimal trade-off (64 k caused 2–2.5× longer runtimes)
- No on-disk format, CLI, or public-repository changes; purely CI runtime behavior

Open questions and loose ends
- Commit message framing: subject line and description should clarify the limit is being *raised* to resolve failures, not reduced.
