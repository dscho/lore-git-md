This is the final patch in the GSoC v15 series implementing `git cat-file --batch-command`'s `remote-object-info` feature. It replaces the static allow-list for format placeholders with a dynamic system that adapts to what the server actually advertises, addressing the forward-compatibility concern raised in earlier reviews.

The patch makes the client fully protocol-aware: it now maps requested atoms (like `%(objectsize)`) to protocol options (like "size"), asks the server which options it supports, filters out unsupported ones, and populates `remote_allowed_atoms` with only the placeholders that correspond to supported options. This ensures the client never requests data the server cannot provide, preventing crashes or information leaks.

Key changes include:
- Moving `object_info_options` out of `get_remote_info()` so callers can specify which metadata they want
- Adding a mapping table (`remote_atom_map`) that connects protocol options ("size", "type") to atoms ("objectsize", "objecttype")
- Modifying `expand_atom()` to check the dynamic `remote_allowed_atoms` list instead of the static `remote_object_info_atoms`
- Ensuring `batch_object_write()` always produces output, even when all placeholders are unsupported (returning empty lines)
- Adding backward iteration when filtering the options list to avoid skipping elements during removal
- Including "type" in the mapping table for future extensibility

The implementation is careful about memory management (clearing string lists, freeing object info contents) and maintains the established behavior of returning empty strings for unsupported atoms rather than failing. The patch also updates `EXPAND_DATA_INIT` to initialize the new `remote_allowed_atoms` field.

This completes the security-hardened design: the client now dynamically validates all format placeholders against server capabilities at runtime, closing the last major gap in the protocol's extensibility story. The series is now fully ready for merging.
