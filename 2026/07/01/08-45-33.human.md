This is a **bugfix patch** for `git blame -b` that resolves a long-standing usability annoyance. The issue: when using `git blame -b` (show boundary commits as blank), the command unnecessarily reserves an extra hex digit in commit hash abbreviations for a caret marker that never appears, causing hashes to exceed the user’s `core.abbrev` setting by one character. This creates friction in manual workflows—like copying hashes from `git blame -b` into `git rebase -i`—where users must manually truncate the extra digit.

René Scharfe’s patch implements Junio C Hamano’s proposed solution by refactoring the mark-handling logic in `blame.c`. The key change is dynamic column reservation: the code now counts and prints boundary/ignored/unblamable marks (like `^`, `*`, or `?`) only when they’re actually displayed, ensuring abbreviated hashes respect `core.abbrev`. The patch introduces two helper functions, `print_marks()` and `count_marks()`, to centralize this logic, and updates `find_alignment()` to calculate the maximum marks needed per line. The result is a cleaner, more predictable output format without breaking fixed-width alignment.

Laszlo Ersek, the original reporter, confirms the fix works as intended and eliminates the manual truncation step in his workflow. The patch is minimal, well-structured, and directly addresses the core problem. However, René notes it lacks test coverage, and neither he nor Laszlo have exhaustively tested edge cases (e.g., multiple marks per line), though the dynamic logic should handle them if they exist.

No backward-compatibility concerns have been raised, and the change is narrowly scoped to `git blame -b`. The discussion has converged on this solution, with no objections or requests for additional configuration (like a `blame.abbrev` setting). The patch is now awaiting final validation, likely focusing on testing and edge-case verification. For users who rely on `git blame -b` in interactive workflows, this is a small but meaningful quality-of-life improvement.
