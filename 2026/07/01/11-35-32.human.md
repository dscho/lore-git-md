This is part five of Patrick Steinhardt’s eleven-patch series adding the `git history drop` subcommand. The patch introduces a dry-run mode to `reset_working_tree()`—a preparatory step for the upcoming drop command, which will use this mode to verify whether replaying descendants after dropping a commit would succeed without actually updating the index or working tree.

The change is clean and focused: it adds a new `RESET_WORKING_TREE_DRY_RUN` flag to the reset API’s enum, skips all file-system updates when the flag is set, and uses a scratch index to simulate the operation. The implementation avoids duplicating logic by reusing the existing unpack-trees machinery, setting `unpack_tree_opts.dry_run` and `unpack_tree_opts.update = 0` to suppress side effects. A new `scratch_index` is allocated for dry runs, read from the repository’s index file, and released at the end.

This is a well-motivated refactoring that directly supports the series’ goal. The commit message clearly explains why the dry-run mode is needed, and the code itself is straightforward, with no obvious edge cases or regressions. The patch is part of the larger reset-API modernization effort that began in earlier patches (renaming `reset_head()` to `reset_working_tree()` and converting flags to an enum), and it paves the way for the actual drop implementation in patch eleven. No controversy or open questions are evident here—this looks like a routine, uncontroversial step in a mature series.
