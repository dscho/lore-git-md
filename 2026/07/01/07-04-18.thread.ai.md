Core problem or goal
Coverity Scan recently resumed after an outage; this 13-patch series addresses the first batch of real (non-false-positive) resource leaks and error-path bugs it flagged in core Git. The goal is to plug memory, file-descriptor, process-handle, and other resource leaks, and to ensure proper cleanup when functions return early due to errors. No user-visible behavior changes; purely internal correctness.

Test coverage: none added; fixes are mechanical and covered by existing tests. Jeff King (Peff) independently reproduced the leak fixed in patch 6/13 under `GIT_TEST_COMMIT_GRAPH_CHANGED_PATHS=1`, confirming the fix’s correctness and the leak’s real-world impact.
**Patch 1/13 (critical correctness concern)**: consolidates error-path cleanup in `load_one_loose_object_map` by introducing a `ret` variable to ensure `fclose(fp)` is always called before return. Junio C Hamano identified a latent bug: the patch checks `errno` to detect file-reading errors, but `errno` may have been clobbered by intervening function calls (`strbuf_release`, `insert_loose_map`). He recommends replacing the `errno` check with an explicit `ferror(fp)` call to reliably detect errors. The fix is small but essential for correctness.
Patch 2/13 adds a `fd >= 0` guard in `write_one_object` to prevent undefined behavior from `close(-1)` on open failure; confirmed by Patrick Steinhardt to be the only `close(fd)` call in the function, eliminating double-close risk.
Patch 3/13 reorders `fclose(child_out)` in `download_https_uri_to_file()` to execute unconditionally before returning on error.
Patch 4/13 replaces `if (cmd->in)` and `if (cmd->out)` with `if (cmd->in > 0)` and `if (cmd->out > 0)` in `start_command()` to avoid closing the `-1` sentinel value (CID 1049722). Patrick Steinhardt confirmed the fix is consistent with an existing guard (`close(cmd->out)`) elsewhere in the same function.
**Patch 5/13 (contested)**: purports to plug a memory leak in `run_diff_files()` by freeing the `combine_diff_path` structure (`dpath`) when `changed < 0` triggers an early `continue` after allocation but before the normal cleanup block. The fix initializes `dpath` to `NULL` and adds an explicit `free(dpath)` on the error path, but `dpath` is never assigned a non-NULL value before the `free` call, so the fix is ineffective. The leak remains unplugged.
Patch 6/13 removes a redundant copy in `line_log_process_ranges_arbitrary_commit()`: when `bloom_filter_check()` determines a commit does not touch any tracked paths, the function previously made an intermediate copy of the `range` structure (`line_log_data_copy(range)`) and passed it to `add_line_range()`, but `add_line_range()` always makes its own internal copy, so the caller’s copy was never freed and leaked. The fix deletes the redundant copy and passes the original `range` directly to `add_line_range()`. Jeff King (Peff) independently reproduced the leak under `GIT_TEST_COMMIT_GRAPH_CHANGED_PATHS=1` and confirmed the fix’s correctness.
**Patch 7/13 (resolved completeness concern)**: plugs two memory leaks in `read_one_dir()` (dir.c) that occur when parsing the untracked-cache data fails: `ud.untracked` (allocated at line 3846) and `ud.dirs` (allocated at line 3851) are now freed before the function returns -1 on either of the two error paths that lie between those allocations and the point where ownership is transferred to the final `xmalloc`’d struct at line 3857. Johannes Schindelin clarified that the two later early returns occur *after* ownership transfer, so no leak occurs. The fix is complete as written.
**Patch 8/13 (maintainability caveat)**: plugs a memory leak in `get_superproject_working_tree()` (submodule.c) by ensuring the `cwd` buffer allocated via `xgetcwd()` is freed on the two early-return paths that previously bypassed cleanup. The fix redirects the early returns through a new `out` label that calls `free(cwd)` before returning 0. Patrick Steinhardt confirmed correctness but flagged a fragility risk: the function already has an earlier `free(cwd)` call, and if a future contributor adds a `goto out` after that first `free`, it would trigger a double-free. He recommends consolidating all cleanup into a single exit path to eliminate the risk.
Patch 9/13 plugs resource leaks in `builtin/worktree.c:add()` when `run_command()` fails while creating a new branch. The fix redirects the error return through the existing cleanup block, ensuring four allocations (`path`, `opt_track`, `branch_to_free`, and `new_branch_to_free`) are freed.
Patch 10/13 plugs a memory leak in `imap-send.c` where the `msgbuf.buf` strbuf, used to accumulate messages during IMAP uploads via libcurl, was never released before the function returned. The fix adds a single line (`strbuf_release(&msgbuf.buf)`) alongside the existing libcurl cleanup calls in `curl_append_msgs_to_imap()`.
Patch 11/13 plugs a resource leak in the reftable backend’s `reftable_table_refs_for_unindexed()` function: when `reftable_buf_add()` fails, the `filter` allocation and any memory it may have grown for its `oid` buffer are left unreleased. The fix adds four lines to the existing `out` label to call `reftable_buf_release(&filter->oid)` and `reftable_free(filter)` alongside the table-iterator cleanup.
Patch 12/13 plugs a memory leak in the fsmonitor daemon’s startup sequence: when `fsmonitor_run_daemon()` fails early (e.g., during alias resolution, listener construction, or IPC server initialization), the `state.current_token_data` allocation—created before any of those steps—was never freed. The fix adds two lines at the top of the `done:` cleanup block to call `fsmonitor_free_token_data()` and clear the pointer, ensuring the leak is plugged on all error paths while remaining a no-op on the success path.
Patch 13/13 fixes a Windows-specific process-handle leak and double-close bug in `compat/mingw.c` and `compat/win32/exit-process.h`. The patch establishes a clear ownership invariant: both `exit_process()` and `terminate_process_tree()` now own the process handle from the call onward and close it on every return path. The fix removes the redundant `CloseHandle(h)` in `mingw_kill()` and adds a single `CloseHandle(process)` call in `exit_process()` before returning on error.

Open questions and loose ends
**Patch 1/13**: Junio C Hamano’s review raises a critical correctness issue -- the patch’s reliance on `errno` to detect file-reading errors is unsafe because `errno` may have been clobbered by intervening function calls (`strbuf_release`, `insert_loose_map`). The author must revise the patch to use `ferror(fp)` instead of `errno` to reliably detect errors. Until resolved, this patch remains a blocker for the series’ progress.
**Patch 5/13**: Patrick Steinhardt’s review raises a critical correctness issue -- the fix as written does not plug the leak it claims to address. The author must either clarify the intended logic (e.g., whether `dpath` is assigned elsewhere in the function or whether the Coverity report was misinterpreted) or revise the patch to correctly free the leaked memory. Until resolved, this patch remains a blocker.
**Patch 8/13**: Patrick Steinhardt’s review raises a maintainability concern -- the function has two separate `free(cwd)` calls, one inline and one via the new `out` label. If a future contributor adds a `goto out` after the first `free`, it would trigger a double-free. He recommends consolidating all cleanup into a single exit path to eliminate the risk. The observation is forward-looking and not a blocker, but it may prompt a follow-up patch to improve robustness.
