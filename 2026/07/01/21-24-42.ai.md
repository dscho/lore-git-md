This is the final patch in a four-part bugfix series standardizing help-flag exit codes across Git's parse-options infrastructure. The patch updates all built-in commands using the parse-options API to exit with status 0 (success) when `-h` or `--help` is specified, aligning with Unix conventions where help output is considered a successful operation. Previously, these commands exited with 129, which was an accidental holdover from 2007 code rather than an intentional design choice.

The change touches 37 files, primarily test scripts in `t/` that previously expected exit code 129 for help scenarios. The patch updates these tests to expect exit 0 instead, with a few exceptions (e.g., `git diff`) where commands handle their own option parsing and still exit 129. The implementation preserves backward compatibility for `git rev-parse --parseopt`'s direct invocation mode (which still exits 129 on help as a debugging aid) while ensuring the documented shell-eval mode exits 0. Three built-in commands (`git blame`, `git shortlog`, and `git update-index`) are updated to explicitly call `exit(0)` when `PARSE_OPT_HELP` is returned.

The patch is well-motivated, with a clear technical rationale: help output is user-requested information, not an error condition, and scripts depending on help-exit behavior would be poorly designed. The maintainer has already endorsed this as a regular bugfix, not requiring a major version bump. Test coverage is thorough, updating expectations across the test suite to match the new behavior while handling edge cases like commands with different behavior for `-h` vs `--help-all`. The implementation is minimal and focused, introducing no new options or config keys.
