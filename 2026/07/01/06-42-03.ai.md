This is the third and final patch in Jeff King’s three-patch bugfix series targeting memory leaks in Git’s commit-graph Bloom filter code. It fixes a leak in `line-log.c` where `line_log_process_ranges_arbitrary_commit()` unnecessarily copies a range before passing it to `add_line_range()`, which already makes its own copy. The extra copy is leaked. The fix is a one-line change that passes the original range directly, eliminating the redundant copy.

The leak has been present since the Bloom filter integration for line-log in f32dde8c12 (2020-05-11) but only surfaces when running the test suite with `GIT_TEST_COMMIT_GRAPH_CHANGED_PATHS=1` and leak sanitizers enabled. Jeff provides a reproduction recipe using `t4211-line-log.sh` with additional test flags. He notes that while more targeted test coverage for the interaction between line-log and Bloom filters would be useful, this fix can rely on the existing leak-checking recipe for validation.

The patch touches only `line-log.c`, changes no behavior or on-disk format, and is part of a broader effort to eliminate leaks in the `linux-TEST-vars` CI jobs when leak-checking is enabled. The series, combined with two other recent fixes (one from Peff, one from Kaartic Sivaraam), will address most of these leaks; OpenSSL SHA-1–related leaks remain deferred. The fix is minimal, well-motivated, and directly addresses the stated issue without introducing new complexity.
