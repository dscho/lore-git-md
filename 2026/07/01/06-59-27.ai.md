This is the second patch in Patrick Steinhardt's RFC v3 series to reorganize Git's source tree by moving all `libgit.a` components into a new `lib/` directory. The patch is a **pure refactoring** with no functional changes, focusing on the mechanical relocation of approximately 700 files (including core subsystems like object handling, refs, diff, merge, and platform compatibility shims) into the `lib/` directory while preserving their internal structure.

Key technical details:
- **Files moved**: Core Git subsystems (e.g., `object.c`, `refs.c`, `diff.c`, `merge.c`, `compat/`, `reftable/`, `xdiff/`) and utility files (e.g., `strbuf.c`, `hashmap.c`).
- **Build system updates**: Paths in `Makefile`, `meson.build`, `CMakeLists.txt`, and `config.mak.uname` are updated to reference the new `lib/` directory. This includes adjustments to include paths, object file lists (`LIB_OBJS`), and third-party source definitions (`THIRD_PARTY_SOURCES`).
- **CI and tooling**: The patch incorporates Johannes Schindelin's fix for Windows CI (adjusting `.github/workflows/main.yml` to reference `lib/compat`) and updates `.gitmodules` to point to the new location of the `sha1collisiondetection` submodule.
- **Documentation**: A minor update to `Documentation/Makefile` ensures `fsck.h` is referenced from its new location.
- **No symbol changes**: The patch does not introduce or modify any symbols, APIs, or on-disk formats.

The commit message explicitly acknowledges the trade-offs of this mass rename, including:
1. **Disrupted history tracking**: Tools like `git log --follow` will no longer track file history across the rename by default, creating a "cutoff point" in the history of every moved file.
2. **Rebasing/backporting challenges**: In-flight or not-yet-submitted topics touching moved files will require rebasing, and backporting fixes across the rename boundary will be more cumbersome.
3. **Downstream disruption**: Long-lived forks (e.g., GitHub, Microsoft Git) may face merge conflicts and rebase challenges.

Patrick argues these are one-time costs justified by permanent improvements in code discoverability and onboarding, and suggests the change could incentivize tooling improvements (e.g., better rename tracking in `git log`). The patch has been validated via GitLab and GitHub CI pipelines, with the Windows regression from v2 now resolved.
