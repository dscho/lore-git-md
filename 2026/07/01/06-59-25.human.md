This is the third iteration of Patrick Steinhardt's ambitious refactoring to reorganize Git's source tree by moving all `libgit.a` components into a new `lib/` directory. The patch remains a two-part series: the first patch prepares a test helper, while the second performs the mass relocation of nearly 700 files—including core subsystems like object handling, refs, diff, merge, and platform compatibility shims—into the new directory. The changes are primarily mechanical, updating build system files (Makefile, meson.build, CMakeLists.txt) and CI configurations to reflect the new paths.

Version 3 explicitly acknowledges the downsides of this reorganization in the commit message, framing them as one-time costs that are outweighed by permanent improvements in code discoverability. The key trade-offs Patrick highlights are: (1) the mass rename creates a historical cutoff point, as `git log` and similar tools don’t follow renames by default, and (2) in-flight patches or backports will require rebasing. His argument leans on the idea that these limitations are deficiencies in Git’s tooling that the project should address, and that subjecting Git itself to this pain could incentivize improvements to rename-following functionality.

The series has already addressed prior technical feedback, including a Windows CI regression fix from Johannes Schindelin (applied as a fixup patch). Testing has been validated against GitLab and GitHub’s build systems, and the timing—sent close to the upcoming release—suggests Patrick aims to land this early in the next cycle if the community agrees. The thread context reveals ongoing debate about whether the structural benefits justify the logistical disruption, with SZEDER Gábor raising concerns about `git log --follow` usability and Junio C Hamano expressing skepticism about the practical value. Patrick’s response positions the reorganization as a necessary step for long-term maintainability, even if it temporarily complicates development workflows.
