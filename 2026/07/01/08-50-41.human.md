This is the third patch in the `git replay --linearize` series, now at v5. It introduces a `--linearize` option to `git replay` that flattens merge commits into a linear history, similar to `git rebase --no-rebase-merges`. The patch is part of a three-patch series that has been under review for several iterations, with all prior feedback incorporated except for two blocking issues: a regression in `--linearize` behavior when replaying a single branch containing merge commits, and an unresolved design debate about the command-line interface for handling merge commits.

The current patch implements the core logic for `--linearize`, which skips merge commits during replay and maps them to the last non-merge commit, effectively dropping them from the resulting history. The implementation touches `replay.c`, `replay.h`, `builtin/replay.c`, and adds test coverage in `t3650-replay-basics.sh`. The patch also documents the new option in `git-replay.adoc` and enforces mutual exclusivity with `--revert`.

Junio’s review highlights a behavioral difference between `git replay --linearize` and `git rebase --no-rebase-merges`: while rebase rewrites both branches of a divergent merge and drops the merge commit (e.g., `A->X'->Y'`), replay drops the merge and keeps only one branch (e.g., `A->X'` or `A->Y'`), leaving the other dangling. This is not a bug but a potential user-expectation mismatch, and Junio suggests documenting the behavior and adding a test to lock in the current semantics. Toon acknowledges the issue and agrees that the behavior should be predictable, leaning toward restoring the v1-v4 behavior where `--linearize` flattens all replayed commits into a single linear topology, even when multiple branches are involved. This would address the regression but may not always match user expectations, especially when replaying multiple branches at once.

The unresolved interface design debate remains a sticking point. Johannes Schindelin opposes mirroring `git rebase`'s `--rebase-merges=<mode>` syntax, arguing that `--linearize` better describes the flattening behavior and avoids repeating past UX mistakes. Patrick Steinhardt, however, insists that any divergence from `git rebase`'s syntax must be explicitly justified in the commit message. Toon now aligns with Schindelin’s position but must still address Steinhardt’s requirement for justification. The patch also needs to restore the `replayed_base` parameter (removed in v5) to fix the regression and add test coverage for the behavioral difference Junio identified.

The patch is well-crafted and addresses a real need, but the regression and interface debate must be resolved before it can merge. The discussion is technical and collaborative, with all participants engaged in finding a solution. If the regression is fixed and the interface debate settled, this patch could be a solid addition to `git replay`. For now, it remains under active review.
