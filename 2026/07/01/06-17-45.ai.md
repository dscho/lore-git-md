This is a **performance analysis follow-up** in the reftable backend, responding to Jeff King’s discovery of quadratic-time behavior during bulk ref deletion and re-creation. Patrick Steinhardt confirms the issue is a known limitation tied to reftable’s tombstone handling: when refs are deleted, they are not immediately purged but instead marked as tombstones, forcing subsequent operations to iterate through all tombstones to determine if a ref exists. This design choice—intended to avoid expensive compaction—creates a performance cliff for workflows like `git for-each-ref | git update-ref --stdin` followed by re-creation, where runtime scales quadratically with the number of deleted refs.

The root cause lies in `refs_verify_refname_available()`, which must scan all tombstones to confirm a refname is available. While Patrick previously optimized this function, he acknowledges further gains are possible, such as early termination in the merged iterator when the tombstone name sorts after the target ref. However, he notes the issue is currently deprioritized because it primarily affects artificial benchmarks rather than real-world usage. The discussion frames this as a trade-off: tombstoning avoids costly compaction but introduces scalability bottlenecks for bulk operations.

Key technical details for future reference:
- **Subsystem**: reftable backend (`refs_verify_refname_available()`, `merged_iter_next_entry()`).
- **Trigger**: Bulk ref deletion followed by re-creation (e.g., `git for-each-ref | git update-ref --stdin`).
- **Symptom**: Quadratic runtime growth (4x for 2x input size) due to tombstone iteration.
- **Files touched**: None in this email, but future work would target `reftable/refs.c` and `reftable/merged.c`.
