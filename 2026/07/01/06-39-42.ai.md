This is the first patch in a three-part bugfix series targeting memory leaks in Git’s commit-graph Bloom filter code. The patch makes the Bloom-filter slab initialization (`init_bloom_filters()`) idempotent by introducing a static flag (`bloom_filter_slab_initialized`) that prevents re-initialization without an intervening `deinit_bloom_filters()` call. The leak occurs when `init_bloom_filters()` is called multiple times—such as during split commit-graph parsing or in the `test-tool bloom` helper—overwriting the existing slab pointers and leaking previously allocated memory. The fix is minimal (5 lines added to `bloom.c`) and does not change behavior or on-disk format, only ensuring that repeated initialization does not corrupt the slab state.

The commit message provides a detailed analysis of three scenarios where the leak could surface, including a concrete reproduction case using `GIT_TEST_COMMIT_GRAPH_CHANGED_PATHS=1` and leak sanitizers. The solution is intentionally conservative, avoiding deeper refactoring of the slab initialization logic, which the author notes could introduce subtle dependencies on when the slab is populated. The patch pairs the initialization flag with the existing `deinit_bloom_filters()` function to maintain explicit state management, though the author acknowledges that the slab-clearing function already leaves the slab in a usable state.

Key symbols introduced: `bloom_filter_slab_initialized` (static flag in `bloom.c`). The patch is part of a broader effort (alongside two other recent fixes) to eliminate leaks in the `linux-TEST-vars` CI jobs when leak-checking is enabled, with remaining OpenSSL SHA-1–related leaks deferred. No test failures or edge cases are expected, as the fix only prevents redundant initialization. The series is authored by Jeff King (Peff), a long-time contributor with deep expertise in low-level Git internals, and the patch reflects his typical precision in addressing memory management issues.
