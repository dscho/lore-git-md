This is the third patch in the `git replay --linearize` feature series (v5), focusing on the core implementation of the `--linearize` option. The patch introduces a new flag that flattens merge commits during replay, producing a linear history. The current implementation drops merge commits and keeps only one branch of the original topology, which differs from `git rebase --no-rebase-merges` (which rewrites both branches and drops the merge).

This email is a reply to Junio C Hamano’s observation about the behavioral difference between `git replay --linearize` and `git rebase --no-rebase-merges`. Junio notes that when replaying a divergent merge (e.g., `A->X` and `A->Y` merging at `Z`), `git replay --linearize` drops the merge and keeps only one branch (e.g., `A->X'` or `A->Y'`), leaving the other branch dangling. In contrast, `git rebase --no-rebase-merges` rewrites both branches and drops the merge, producing a linear history like `A->X'->Y'` or `A->Y'->X'`. Junio suggests documenting this behavior and adding a test to lock in the current semantics.

Toon Claes acknowledges the issue and agrees that the current behavior may not be intuitive, especially when replaying multiple branches. He proposes restoring the v1-v4 behavior, where `--linearize` flattens *all* replayed commits into a single linear history, even when multiple branches are involved. This would ensure predictability and avoid dangling commits. For example, replaying branches `Z` and `C` onto `X` with `--linearize` would produce `A->X->Y->Z->B->C`, where all commits are linearized into a single topology. Toon also suggests two workarounds for users who want to replay multiple branches without rewriting all of them: (1) using `--ref` to limit which refs are updated, or (2) peeling commits to avoid treating them as refs.

The email includes a proposed test case from Junio to verify the behavior when replaying a divergent merge. The test ensures that only one of the two branches (`X` or `Y`) survives after `--linearize`, reflecting the current implementation. Toon accepts the test case, indicating it will be included in the next version.

The discussion highlights two unresolved issues: (1) the regression in `--linearize` behavior when replaying a single branch with merges (fixed by restoring the `replayed_base` parameter, as noted in the thread summary), and (2) the interface design debate between `--linearize` and `git rebase`'s `--rebase-merges=<mode>` syntax. Toon now aligns with Johannes Schindelin’s position that `--linearize` should remain a standalone flag, arguing it better describes the all-or-nothing flattening behavior. However, Patrick Steinhardt’s requirement for explicit justification of any divergence from `git rebase`’s syntax still applies. The next version will need to address both the regression fix and the interface design rationale in the commit message. Test coverage for the behavioral difference between `git replay --linearize` and `git rebase --no-rebase-merges` will also be added.
