This is a follow-up in the `git replay --linearize` thread, focusing on the merge-commit divergence edge case identified by Junio Hamano. The email is part of the post-merge discussion about the newly merged `--linearize` feature, which is already in `master` but has known behavioral quirks and regressions.

Toon Claes responds to Junio’s review, which pointed out that `git replay --linearize` silently drops one side of a divergent merge (e.g., when replaying a merge commit Z that merges branches X and Y, only one of X or Y survives in the output). Toon acknowledges the issue and clarifies the intended design: `--linearize` should produce a *single linear sequence* regardless of input branches, meaning all commits are replayed in a straight line, even if this means duplicating shared history. This design choice is deliberate and aligns with Johannes Schindelin’s earlier feedback, but it differs from the behavior of `git rebase --no-rebase-merges`, which replays both branches separately.

Toon proposes two potential solutions for users who want to preserve branch independence: (1) use `--ref` to limit which refs are updated, or (2) peel commits to avoid treating them as refs. However, he also notes that these workarounds may not fully address the core issue and that the current behavior could still surprise users. He plans to document the behavior more clearly and add test cases in a follow-up patch.

The email includes a detailed walkthrough of the code’s logic, confirming Junio’s analysis: when replaying a merge commit, the code drops the merge and grafts its descendants onto the surviving parent, which can orphan one branch entirely. Toon agrees this is a limitation but argues it’s inherent to the feature’s design. He also references Johannes Schindelin’s earlier critique, which similarly flagged the need for predictable behavior.

Key technical details:
- The issue stems from the `put_mapped_commit()` logic in `replay.c`, which maps the dropped merge commit to its surviving parent.
- The proposed test case (included in Junio’s review) would expose the behavior by verifying that only one of the two divergent branches (X or Y) appears in the replayed history.
- The discussion touches on CLI design (e.g., `--ref` and peeling commits) but ultimately defers to the core design principle: `--linearize` produces a single linear sequence.
