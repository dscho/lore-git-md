This is the author's reply to Junio C Hamano's **substantive review** of the final patch in Patrick Steinhardt's `git history drop` series. The series implements a new `` `git history drop` `` subcommand to remove commits from history and replay their descendants, and is now at v7 (11/11 patches).

Patrick **acknowledges the redundancy** in the `find_head_tree_change()` helper: when HEAD is detached, `refs_resolve_ref_unsafe()` already returns `"HEAD"`, so the manual overwrite is unnecessary. However, he **disputes the core flaw** Junio identified. Junio argued that when `` `--update-refs=head` `` is used, `compute_pending_ref_updates()` filters the `result->updates[]` array to contain only `HEAD` (not the symbolic branch name, e.g., `refs/heads/master`), causing `find_head_tree_change()` to miss HEAD movements. Patrick counters that `replay_revisions()` populates the result with the **resolved branch name**, and `find_head_tree_change()` searches for the same name, so the mismatch Junio described should not occur.

The exchange leaves the **critical issue unresolved**: whether the ref resolution logic in `` `--update-refs=head` `` mode is correct. Junio's analysis suggests a high-impact bug that could skip index/worktree updates, while Patrick's reply implies the code path works as intended. The next step is likely a v8 patch addressing the redundant `head_target` overwrite and providing clearer evidence (e.g., test cases or debug output) to resolve the disagreement. Until then, the series remains blocked. All other prior feedback—including reset API modernization, dry-run support, and code deduplication—has been addressed.
