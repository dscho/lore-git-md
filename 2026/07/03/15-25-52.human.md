This is a clarification in an ongoing discussion about `git rm`’s recursive behavior with glob patterns. Mikael Magnusson weighs in to explain why the reported behavior—`git rm -n *.json` recursing into subdirectories—is actually correct and expected, not a bug.

The key point Mikael makes is that the `git-rm` man page never explicitly promises non-recursive behavior for glob patterns. Instead, the recursion stems from Git’s pathspec rules, which are documented in `gitglossary(7)`. There, it states that `*` and `?` in pathspecs can match directory separators (`/`), meaning they inherently allow recursion unless constrained. Mikael quotes the relevant glossary text to underscore this.

He also suggests a shell-level workaround: enabling `failglob` in Bash. This would cause the shell to reject unmatched globs like `*.json` (when no `.json` files exist in the current directory) rather than passing the literal `*.json` to Git. This prevents Git from interpreting the glob recursively, but it’s a shell-specific fix, not a Git change.

The email doesn’t propose any code or documentation changes—it’s purely explanatory. Mikael’s tone is matter-of-fact, treating the behavior as a known quirk of Git’s pathspec design rather than a defect. This aligns with the thread’s shift from bug report to documentation discussion, though it doesn’t directly address the open question of whether `git-rm(1)` should clarify pathspec behavior or cross-reference the glossary. For a busy reader, this email confirms the behavior is intentional and points to the glossary for the technical rationale.
