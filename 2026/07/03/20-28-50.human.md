This is a bugfix targeting the revision traversal subsystem. Junio C Hamano responds to Michael Hore’s report about `` `git rev-list --exclude-first-parent-only` `` misbehaving when extra commits are explicitly given on the command line.

The patch adds two early-exit conditions inside the parent-processing loop in `revision.c`: if `revs->exclude_first_parent_only` is set, the loop breaks as soon as it hits a parent that is either unparseable or already marked `SEEN`. This prevents the rest of the parents from being marked uninteresting, so commits reachable only through later parents (like `F` in the reproduction case) are still emitted. A new test in `t/t6012-rev-list-simplify.sh` verifies that both `git rev-list --exclude-first-parent-only F ^R2` and `git rev-list --exclude-first-parent-only F R1 ^R2` now return `F`.

Junio notes that he has never used the feature himself and cc’s the original author for input, but the patch is small, well-contained, and comes with a test. The change looks like a straightforward fix for the reported symptom without obvious side effects.
