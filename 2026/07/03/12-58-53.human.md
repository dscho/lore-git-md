This is the tenth patch in Patrick Steinhardt’s twelve-patch security-hardening series for Git’s reftable backend, now at v3. The patch fixes an out-of-bounds read vulnerability triggered when a maliciously corrupted reftable file contains a bogus restart offset.

Restart points in reftable blocks are records that do not use prefix compression, allowing direct seeking. These offsets are stored in a restart table, but Git did not previously validate that each offset points to a valid record within the block. A corrupted restart offset could therefore cause the parser to read memory outside the block, as demonstrated by the AddressSanitizer backtrace in the commit message. The fix adds a bounds check in `restart_needle_less()` to ensure the restart offset points to a record stored before the restart table; if not, the function signals an error via `args.error` and returns `REFTABLE_FORMAT_ERROR`.

The patch includes a new unit test (`test_reftable_block__corrupt_restart_offset`) that reproduces the issue by writing a valid ref record into a block, then corrupting the first restart offset to `0xffffff` (the maximum 24-bit value). The test verifies that `block_iter_seek_key()` now fails gracefully with `REFTABLE_FORMAT_ERROR` instead of crashing. The test uses the `cl_reftable_write_block` helper introduced earlier in the series to reduce boilerplate.

This is a well-crafted security fix: the commit message clearly explains the vulnerability, the fix is minimal and targeted, and the test covers the edge case. The patch touches only `reftable/block.c` and the corresponding unit test file, with no changes to public APIs or on-disk format. Junio C Hamano has already approved three earlier patches in the series (6/12, 7/12, and 8/12) as "obviously correct," and this patch follows the same pattern of hardening against corrupted input. With all feedback addressed and no open questions, this series appears ready for merging.
