This is a platform-compatibility bugfix targeting macOS, addressing a crash in Git’s Unicode normalization layer (`precompose_utf8`) when handling long UTF-8 filenames. The patch itself is not being resubmitted here; instead, Ihar Hrachyshka responds to Patrick Steinhardt’s review questions, clarifying macOS’s filename length limits and explaining the patch’s memory management approach.

Ihar confirms that macOS allows filenames to exceed the traditional `NAME_MAX` (255 bytes) because the system’s `dirent` structure uses `__DARWIN_MAXPATHLEN` (1024 bytes) as its in-memory limit. While HFS+ and APFS enforce a 255-character limit (not bytes), the kernel’s API can still return filenames longer than `NAME_MAX` in practice. This aligns with Linux’s behavior, where `readdir()` also doesn’t guarantee `NAME_MAX` compliance. The discussion highlights that neither platform strictly adheres to POSIX’s `NAME_MAX` requirement for `d_name`, making Git’s current assumption (that filenames fit in `NAME_MAX + 1` bytes) unsafe.

On the implementation side, Ihar acknowledges Patrick’s suggestion to use `FLEX_ALLOC_MEM()` for the initial allocation but notes that reallocation is still necessary for filenames exceeding the initial buffer size. The patch’s current approach—using a helper function (`dirent_prec_psx_size()`) to calculate dynamic sizes—remains justified because the buffer is reused across directory entries and must grow as needed. While this may over-allocate for shorter filenames, it avoids repeated reallocations for directories with mixed-length entries.

The patch is well-motivated and addresses a real crash, with reviewers (Junio C Hamano, Torsten Bögershausen, and Patrick Steinhardt) generally supportive. The only remaining blockers are Junio’s request to rewrite the test without Perl and Patrick’s memory-management suggestions, both of which appear straightforward to address. The discussion also surfaces broader platform-specific quirks that could inform future macOS compatibility work.
