This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s v3 series addressing vulnerabilities in corrupted reftable files. This specific patch (6/12) fixes a heap-buffer-overflow in the log block parser when the inflated block size is smaller than the header size, leading to an out-of-bounds write during zlib decompression.

The vulnerability occurs in `reftable/block.c` when parsing log blocks, which store compressed reflog data. The block header includes an inflated size field, but the code fails to validate that this size is at least as large as the header itself. When the size is too small, zlib writes beyond the allocated buffer, as demonstrated by the AddressSanitizer output in the commit message. The fix adds a sanity check to reject blocks where the size is insufficient to cover the header, returning `REFTABLE_FORMAT_ERROR` instead of crashing.

The patch includes a new unit test (`test_reftable_block__corrupt_log_block_size`) in `t/unit-tests/u-reftable-block.c` that reproduces the issue by corrupting the block size field to a value smaller than the header. The test uses the `cl_reftable_write_block` helper introduced earlier in the series to reduce boilerplate. Patrick explicitly rejected Toon Claes’s proposed test improvements from v2, arguing that the current approach (writing a size of 1) is the most direct way to trigger the bug, as the vulnerability requires the block size to be smaller than the header size (1–3 bytes).

This is a well-motivated bugfix with clear security implications, though exploitation requires local disk access. The fix is minimal and targeted, addressing only the specific underflow condition without changing public APIs or on-disk formats. The accompanying test ensures the vulnerability is caught in CI, and the ASan output provides concrete evidence of the issue. The patch is part of the broader reftable hardening effort and integrates with the new fuzzing infrastructure introduced in earlier patches.
