This is the eighth patch in Patrick Steinhardt’s twelve-part security-hardening series for Git’s reftable backend, now at v3. It fixes an out-of-bounds read vulnerability triggered by a maliciously corrupted restart count in a reftable block.

The restart count is stored in the last two bytes of each block and is used to compute the offset of the restart table. If the count is bogus (e.g., 0xffff), the offset calculation underflows, causing subsequent reads via the restart table to access out-of-bounds memory. The fix adds a bounds check in `reftable_block_init()` to verify that the computed restart offset lies within the block’s valid range; if not, it returns `REFTABLE_FORMAT_ERROR` instead of proceeding. The accompanying unit test (`test_reftable_block__corrupt_restart_count`) uses the `cl_reftable_write_block` helper (introduced earlier in the series) to create a minimal ref block, corrupts the restart count to 0xffff, and confirms that the parser rejects the block with the expected error code.

This patch is part of the “fixes” segment of the series (patches 3–4 and 6–12), each of which addresses a distinct vulnerability discovered by fuzzing. All prior feedback has been resolved, and the series is technically complete. Junio C Hamano has already approved two of the fixes (patches 6 and 7), signaling confidence in the approach. The hardening is comprehensive, replacing crashes or undefined behavior with graceful error returns, and the new fuzzing infrastructure (patches 1–2) ensures these issues won’t regress. No user-visible changes or on-disk format modifications are introduced.
