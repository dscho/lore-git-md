This is a **surface-level review** of the `git refs create` subcommand, part of Patrick Steinhardt’s now-merged five-patch series consolidating reference manipulation under `git refs`. Toon Claes raises usability concerns about the `--no-deref` option in the context of symbolic reference (symref) creation, questioning whether the current design is intuitive or well-documented.

The review focuses on two main points:
1. **Symref creation with `--no-deref`**: Toon asks whether `git refs create --no-deref` can be used to create symrefs and whether this behavior should be tested. He argues the option name is obscure for this use case, as `--no-deref` implies operating on the reference itself (not its target), which is counterintuitive when creating a symref. He outlines two confusing scenarios: (a) the symref doesn’t exist (where `--no-deref` forces symref creation), and (b) the symref exists (where the user must know it exists to use `--no-deref` effectively). His proposed test (creating a symref with `--no-deref`) would fail under the current implementation, highlighting the ambiguity.
2. **Test coverage**: Toon notes that a test for "create succeeds when the reference exists with the same value" fails intentionally (the subcommand rejects duplicate creations), but this isn’t explicitly documented in the test script. He also suggests adding a test for symref creation with `--no-deref` to clarify the behavior.

The review is **purely stylistic and ergonomic**—it does not dispute the patch’s correctness or challenge the atomic "must not exist" semantics of `git refs create`. Instead, it questions whether the CLI design aligns with user expectations, particularly around symref handling. The concerns are framed as usability observations rather than technical flaws, and Toon does not propose a specific alternative (e.g., a dedicated `--symref` flag). Given the series is already merged, these points are likely deferred for future discussion or follow-up patches. The thread context confirms the series is technically complete, so this feedback may inform future refinements to the `git refs` interface.
