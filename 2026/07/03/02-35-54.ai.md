This is a platform-compatibility bugfix targeting macOS. The patch addresses a crash in `git status` when reading directory entries with UTF-8 filenames longer than `NAME_MAX` bytes (255 on macOS). The crash occurs in the `precompose_utf8` compatibility layer, which handles Unicode normalization for macOS filesystem paths.

The root cause is a mismatch between the fixed-size `d_name` array in `dirent_prec_psx` and the dynamic reallocation logic in `precompose_utf8_readdir`. While the code already attempts to grow the buffer for long filenames, fortified libc functions still enforce the original declared size of `d_name[NAME_MAX + 1]`, causing an overflow check failure. The fix converts `d_name` to a flexible array member and adjusts allocation calculations to match the actual memory layout.

The patch includes a regression test that creates a 261-byte non-ASCII filename (249 'a' characters + 3 UTF-8 em-dashes + ".md") and verifies `git status` works with `core.precomposeunicode` enabled. The test uses Perl to generate the filename and checks the byte count explicitly.

The change is confined to `compat/precompose_utf8.c` and its header, with no impact on other platforms. The implementation uses `FLEX_ARRAY` (Git's compatibility macro for flexible array members) and `st_add`/`offsetof` for safe size calculations. The commit message clearly explains the crash scenario and the fortified libc interaction.

This appears to be a well-scoped fix for a real-world macOS issue, with appropriate test coverage and clean implementation. The patch is from a first-time contributor to this subsystem but follows Git's coding conventions.
