This is a security hardening patch for the reftable backend, part of Patrick Steinhardt’s v3 series addressing vulnerabilities in Git’s reftable parser. This is patch 7/12, fixing an out-of-bounds read triggered by a maliciously corrupted block size in the reftable block header.

The vulnerability occurs when the block size, read from untrusted data, exceeds the actual data available. This leads to an out-of-bounds read when accessing the restart count or computing the restart table offset. The fix adds a bounds check in `reftable_block_init()` to verify the claimed block size fits within the available data, returning `REFTABLE_FORMAT_ERROR` if not. The accompanying unit test (`test_reftable_block__corrupt_block_size`) dynamically calculates the corruption value—reading the actual block size, verifying it (47 bytes), and then corrupting it by adding 1—ensuring the test always targets the minimal invalid size (one byte beyond the buffer). This addresses Toon Claes’s feedback from v2, making the test more robust than the original hardcoded value (`0xffffff`).

The patch touches `reftable/block.c` and adds a new test case to `t/unit-tests/u-reftable-block.c`. No public APIs or on-disk formats are changed; the behavior is strictly safer, replacing undefined behavior with a graceful error return. The fix is minimal and targeted, with a clear commit message and ASan output demonstrating the vulnerability. Junio C Hamano has already approved patch 6/12 in the series, and this patch follows the same pattern of hardening against corrupted input. The test helper `cl_reftable_write_block` (introduced in patch 5/12) is used here to reduce boilerplate, and both Junio and Christian Couder have acknowledged its effectiveness.

This is a well-crafted security fix with thorough test coverage, part of a larger effort to harden the reftable backend. The series is technically complete, with all feedback addressed, and this patch specifically resolves a heap-buffer-overflow identified by fuzzing. The dynamic corruption value in the test case ensures the fix is exercised correctly, and the bounds check is straightforward and correct. No controversy or open questions remain.
