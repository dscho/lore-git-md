This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s ongoing series to harden the code against maliciously corrupted files. This is patch 11/12 in the v3 series, which is now technically complete and ready for merging.

The patch fixes a NULL pointer dereference in `reftable/table.c` when seeking to a bogus offset. When an iterator is seeked to an offset that points beyond the block, the code currently treats it as a normal end-of-iteration, leaving a partially-initialized block. This can later cause a NULL pointer exception in `reftable_block_type()`, as demonstrated by the included ASan backtrace. The fix is simple: return `REFTABLE_FORMAT_ERROR` when the offset is out of bounds, ensuring the corruption is surfaced rather than silently ignored.

The unit test (`test_reftable_table__seek_invalid_log_offset`) reproduces the issue by corrupting the log section offset in the footer to `UINT64_MAX`, then verifying that seeking the log iterator returns the expected error code instead of crashing. The test is thorough, dynamically corrupting the footer and recomputing the CRC to ensure the corruption is valid. It uses the `cl_reftable_write_to_buf` helper introduced earlier in the series to reduce boilerplate.

This patch is part of the larger reftable hardening effort, which has already seen approval from Junio C Hamano for several earlier fixes in the series. The quality is high: the commit message clearly explains the vulnerability, the fix is minimal and targeted, and the test is robust. No user-visible behavior changes; the patch strictly improves safety by replacing a crash with an error return. The series as a whole is well-motivated and addresses a real security concern, even if exploitation requires local disk access.
