This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s v3 series addressing vulnerabilities in corrupted reftable files. This is the sixth patch in the twelve-patch series, which is now technically complete and ready for merging.

The patch fixes a heap-buffer-overflow in the log block parser (`reftable/block.c`). Log blocks store compressed reflog data, and the inflated size is stored in the block header. The bug occurs when the untrusted block size (from the header) is smaller than the trusted header size, causing an underflow that leads zlib to write beyond the allocated buffer. The fix adds a sanity check to ensure the block size covers at least the header, block header, and restart counter, returning `REFTABLE_FORMAT_ERROR` instead of crashing. The commit message includes a detailed ASan trace showing the out-of-bounds write, making the vulnerability and fix clear.

The patch includes a unit test (`test_reftable_block__corrupt_log_block_size`) that corrupts the block size field to trigger the bug. The test uses the `cl_reftable_write_block` helper introduced earlier in the series to reduce boilerplate, and the corruption is minimal (setting the size to 1) to directly trigger the underflow. Patrick explicitly rejected earlier feedback from Toon Claes to add a sanity check or use a different corruption value, arguing that the current approach is the most direct way to expose the bug. The test verifies the fix by confirming the function returns the expected error code.

This is a well-crafted patch: the commit message is thorough, the fix is minimal and targeted, and the test is clear. The vulnerability is real (exploitable with local disk access) and the hardening is appropriate. The patch is part of a larger security effort, but it stands alone as a complete fix for this specific issue. No user-visible behavior changes; the fix strictly improves safety.
