This is the **maintainer's review of the final patch in v6** of the `git replay --linearize` series. Junio C Hamano raises two process-level questions and one technical concern about the documentation.

First, Junio asks whether **Toon Claes should take full responsibility** for latent bugs in this round, given the extensive changes to behavior and documentation. The patch still carries Johannes Schindelin as a co-author, but the bulk of the work in v6 (regression fixes, expanded test coverage, and design clarification) was done by Toon. This is a **process signal**: Junio is checking whether the co-authorship is still appropriate or if Toon should be the sole author going forward.

Second, Junio **accepts the `--linearize` design** as described in the documentation. The explanation—that the option flattens all revision ranges into a single linear history, updates refs accordingly, and drops merge commits while preserving both sides of divergent merges—is clear and sufficient. No objections are raised to the core functionality.

Third, Junio questions the **blanket incompatibility between `--linearize` and `--revert`**. He suggests that reverting a closed set of commits containing merges *could* work if the inverse commits are applied linearly. The current documentation states the incompatibility without justification; Junio proposes either adding a rationale ("because ...") or moving the limitation to a BUGS/LIMITATIONS section. This is a **documentation nit**, not a functional objection, but it highlights an edge case that may need clarification before merging.

The review is **substantive but narrow**: it focuses on process (authorship) and documentation (incompatibility rationale), not on the correctness of the regression fix or the design choices already documented. The series remains **ready for re-merge** once these points are addressed. No new design changes are requested.
