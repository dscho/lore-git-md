This is the eleventh patch in Patrick Steinhardt’s twelve-patch security-hardening series for Git’s reftable backend, now at v3. It fixes a NULL pointer dereference that occurs when seeking to a bogus section or index offset in a corrupted reftable file.

The vulnerability arises in `table_iter_seek_to()` when an out-of-bounds offset is treated as a normal end-of-iteration condition. Instead of surfacing the corruption, Git silently reports an empty section and leaves the block partially initialized. Later, when `reftable_block_type()` is called on the uninitialized block, it dereferences a NULL pointer, causing a segmentation fault. The fix is minimal: `table_iter_seek_to()` now returns `REFTABLE_FORMAT_ERROR` when the offset exceeds the block size, ensuring the corruption is detected early.

The patch includes a new unit test (`test_reftable_table__seek_invalid_log_offset`) that reproduces the issue by corrupting the log section offset in the footer to `UINT64_MAX`, then verifies that seeking the log iterator returns the expected error code instead of crashing. The test uses the `cl_reftable_write_block` helper introduced earlier in the series to reduce boilerplate.

This fix touches only `reftable/table.c` and adds the corresponding test to `t/unit-tests/u-reftable-table.c`. No public APIs or on-disk formats are changed; the behavior is strictly safer, replacing a crash with an error return. The patch is part of the ongoing reftable backend effort and complements the fuzzing infrastructure and other hardening fixes already merged in the series. With Junio C Hamano’s approval of earlier patches in the series and no open feedback, this patch appears ready for inclusion.
