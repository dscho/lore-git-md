This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s ongoing series to harden the code against maliciously corrupted files. This is patch 8/12 in the v3 series, which is now technically complete and has addressed all prior feedback.

The patch fixes an out-of-bounds read vulnerability in `reftable/block.c`. The issue occurs when a reftable block contains a bogus restart count: the code uses this untrusted value to compute the offset of the restart table without validation, leading to an underflow and subsequent out-of-bounds memory access. The fix adds a bounds check in `reftable_block_init()` to verify that the computed restart offset (`restart_off`) is within the valid range (`header_size + 4` to `block_size - 2`). If not, the function returns `REFTABLE_FORMAT_ERROR` instead of proceeding with the invalid offset.

The commit message includes a detailed ASan backtrace showing the crash, which occurs when `reftable_get_be24()` attempts to read from an invalid memory address during block parsing. The new unit test (`test_reftable_block__corrupt_restart_count`) reproduces the issue by writing a valid ref record into a block, then corrupting the restart count to `0xffff` (the maximum 16-bit value). The test uses the `cl_reftable_write_block` helper introduced earlier in the series to reduce boilerplate, and verifies that the function now returns `REFTABLE_FORMAT_ERROR` as expected.

This patch touches `reftable/block.c` and adds a new test to `t/unit-tests/u-reftable-block.c`. No public APIs or on-disk formats are changed; the behavior is strictly safer, replacing a crash with an error return. The fix is minimal and targeted, addressing a specific edge case in block parsing. The series as a whole is part of the reftable backend effort, and this patch continues the pattern of hardening the code against corrupted input while maintaining backward compatibility.
