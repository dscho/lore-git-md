This is a platform-compatibility bugfix targeting macOS, continuing the discussion of Ihar Hrachyshka's patch to fix a crash in Git's `precompose_utf8` layer when handling UTF-8 filenames longer than `NAME_MAX` (255 bytes). Ihar clarifies that macOS allows filenames to exceed `NAME_MAX` bytes because the system's `dirent` structure uses `__DARWIN_MAXPATHLEN` (1024 bytes) as its limit, not `NAME_MAX`. The effective constraint is 255 Unicode characters (not bytes), which can translate to more than 255 bytes in UTF-8 encoding. This behavior is not unique to macOS—Linux also permits filenames longer than `NAME_MAX` in some filesystems, though POSIX technically requires `d_name` to be limited to `NAME_MAX` bytes. The explanation suggests the patch's approach is justified by real-world platform behavior rather than a macOS quirk.

The current implementation starts with a `NAME_MAX + 1` buffer and reallocates only when encountering longer filenames, which avoids over-allocation for most directory entries. This design choice balances memory efficiency with the need to handle edge cases, though Patrick's feedback implies there may still be room for optimization.
