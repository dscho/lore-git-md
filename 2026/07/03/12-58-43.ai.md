This is a security-hardening patch series for Git’s reftable backend, now at v3. The series systematically fixes a range of vulnerabilities—out-of-bounds reads/writes, NULL pointer dereferences, uninitialized memory usage, and `abort()` calls—triggered by maliciously corrupted reftable files. While exploitation requires local disk access (reftables are not transferred over the network), the hardening is comprehensive and includes new fuzzing infrastructure to prevent regressions.

The v3 update is minimal: a single test in patch 7/12 is made stricter by dynamically calculating the corruption value instead of hardcoding it. This addresses Toon Claes’s feedback from v2, ensuring the test always targets the minimal invalid block size (one byte beyond the buffer) and includes a sanity check to verify the expected block size before corruption. All other patches remain unchanged from v2, and all prior feedback—including Junio C Hamano’s and Christian Couder’s approval of the test helper in patch 5/12—has been resolved.

The series is split into three parts: fuzzing infrastructure (patches 1–2), a test helper to reduce boilerplate (patch 5), and the security fixes themselves (patches 3–4, 6–12). The fuzzer, now integrated into Git’s CI via `ci/run-build-and-minimal-fuzzers.sh`, exercises the three main entry points into the reftable parser and has run for 2+ hours without surfacing new issues. The fixes touch `reftable/basics.c`, `reftable/block.c`, `reftable/record.c`, and `reftable/table.c`, with corresponding unit tests added to `t/unit-tests/`. No public APIs or on-disk formats are changed; the behavior is strictly safer, replacing crashes or undefined behavior with error returns.

Patrick Steinhardt is the sole author, and the series is part of the ongoing reftable backend effort. The technical quality is high: each fix is accompanied by a clear commit message, a unit test, and ASan output demonstrating the vulnerability. The fuzzing infrastructure is a notable addition, providing a reusable framework for future hardening work. With all feedback addressed and no open questions, this series appears ready for merging.
