This is a test and CI infrastructure patch series, now in its second version. The goal is to make Git’s `GIT_TEST_LONG` tests reliable and efficient enough to run in CI without hanging or consuming excessive resources. The series fixes broken tests, reduces disk and memory usage, and enables `GIT_TEST_LONG` in GitLab CI for the first time.

The key change in v2 is the reinstatement of the `EXPENSIVE` prerequisite in `t4141-apply-too-large.sh`, which was dropped in v1. While the test now runs in under a second (down from several minutes), it still consumes over 1 GiB of memory, justifying the label. This resolves the only substantive disagreement from v1, where SZEDER Gábor argued that memory usage, not just runtime, should determine whether a test is considered expensive. The rest of the series remains unchanged: it skips broken tests on incompatible platforms, reduces disk usage in long-running tests, and improves CI configuration.

The patches are well-motivated by real CI failures—some tests hang or fail in GitHub and GitLab CI, and GitLab previously didn’t run `GIT_TEST_LONG` tests at all. The changes are mechanical and focused: no new user-facing behavior, just fixes to test scripts, CI configuration, and the project README. The series is uncontroversial except for the resolved debate over `t4141`, and the improvements to test isolation (e.g., cleaning up large repositories immediately) are endorsed by Jeff King and Patrick Steinhardt as "obvious improvements."

If you care about test reliability or CI coverage, this series is worth a quick skim. The most interesting part is the implicit policy question it raises: should "expensive" tests be defined by runtime, memory usage, or both? The resolution here (memory matters) may set a precedent for future test suite changes. Otherwise, this is a straightforward cleanup that makes CI more robust.
