This is a security hardening patch for the reftable backend, part of Patrick Steinhardt’s ongoing series (v3, patch 9/12). It fixes a use of uninitialized memory in `block_iter_seek_key()` when the binary search fails during record decoding.

The bug occurs when `restart_needle_less()` encounters an error while decoding a record at a restart offset. Although the function correctly detects the error and exits, it later calls `reftable_record_release()` on a record that was never initialized. The fix moves the `reftable_record_init()` call to the start of the function, ensuring the record is always initialized before any potential error path. The change is minimal (four lines moved up) and touches only `reftable/block.c`.

This is a clear-cut memory safety issue with no user-visible behavior change—just a crash or undefined behavior replaced with proper cleanup. The patch follows the series’ pattern: a targeted fix with a straightforward rationale. No test is included here, but the series’ fuzzing infrastructure (introduced in patches 1–2) and prior unit tests for other fixes provide confidence in the hardening effort. Junio C Hamano has already approved earlier patches in the series, and this one looks equally uncontroversial.
