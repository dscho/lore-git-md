This is a security-hardening patch series for Git’s reftable backend, now in its third iteration. The series systematically fixes a range of vulnerabilities—out-of-bounds reads and writes, NULL pointer dereferences, uninitialized memory usage, and calls to `abort()`—that can be triggered by maliciously corrupted reftable files. While exploitation requires local disk access (reftables are never transferred over the network), the hardening is thorough and includes new fuzzing infrastructure to prevent regressions.

The v3 update is minimal: it tightens one unit test in patch 7/12 by dynamically calculating the corruption value instead of hardcoding it, ensuring the test always targets the minimal invalid block size. This change addresses feedback from Toon Claes, who had suggested the test could be more robust. All other patches remain unchanged from v2, which already incorporated a new test helper (`cl_reftable_write_block`) to reduce boilerplate in unit tests, a change that both Junio C Hamano and Christian Couder acknowledged as an improvement.

The series is split into three logical parts: fuzzing infrastructure (patches 1–2), the test helper (patch 5), and the security fixes themselves (patches 3–4 and 6–12). Each fix is accompanied by a unit test in `t/unit-tests/`, and the fuzzer (`oss-fuzz/fuzz-reftable.c`) now runs for 2+ hours without surfacing new issues. The fixes touch core reftable internals (`reftable/basics.c`, `reftable/block.c`, `reftable/record.c`, `reftable/table.c`) but introduce no user-visible changes or API modifications—only safer error handling.

Patrick Steinhardt, the primary author of the reftable backend, is driving this effort. All feedback from v2 has been addressed, and the series appears technically complete. Junio has not yet signaled readiness to merge, but there are no remaining technical blockers. This is a well-scoped, well-tested security effort that looks ready for integration.
