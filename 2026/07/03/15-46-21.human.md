This is a **build system and platform compatibility** follow-up in the ongoing discussion about `USE_NSEC`, the build-time knob that enables Git to track sub-second file timestamps. D. Ben Knoble responds to Jeff King’s feedback on Patrick Steinhardt’s proposal to convert `USE_NSEC` from a build-time option to a runtime-configurable setting (like `core.ignoreCase`).

Knoble acknowledges the appeal of runtime configuration but notes it would require "more surgery" than his original patch, which simply added a `nanosec` Meson option to mirror the existing Autotools/Makefile knob. He doesn’t push back against the idea but points out the added complexity, particularly around testing behavior across filesystems with varying timestamp granularity. His email doesn’t propose a concrete implementation for runtime configuration, leaving that as future work.

The thread remains focused on whether the original patch (adding the Meson option) should proceed or be shelved in favor of a runtime knob. Knoble’s position is that the patch is justified for build system parity, especially for source distributions like Gentoo that want to expose the knob to users who know their filesystem supports nanosecond timestamps. He doesn’t engage with the interoperability risks (e.g., mixing `USE_NSEC` and non-`USE_NSEC` implementations like Git and JGit) or the default behavior debate, but his earlier confirmation that XFS preserves nanosecond timestamps bolsters the case for enabling the feature by default on modern Linux.

The discussion is now at a crossroads: the original patch is queued for merging, but the broader debate about `USE_NSEC`’s viability—build-time vs. runtime, default behavior, and deprecation—remains unresolved. If you care about filesystem timestamp handling or build system parity, this thread is worth following, but the immediate next steps are unclear. No new patches have been submitted yet for runtime configuration, and Knoble’s email doesn’t resolve the open questions about auto-detection or interoperability.
