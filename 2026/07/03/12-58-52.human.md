This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s ongoing series to harden the code against maliciously corrupted files. This is patch 9/12 in the v3 series, which is now technically complete and has addressed all prior feedback.

The patch fixes a use of uninitialized memory in `block_iter_seek_key()` in `reftable/block.c`. When the binary search through restart offsets fails—specifically, when `restart_needle_less()` fails to decode a record at a given offset—the code correctly detects the error but then calls `reftable_record_release()` on a record that was never initialized. The fix is simple: move the `reftable_record_init()` call earlier in the function so the record is always initialized before any error path can attempt to release it.

The change is minimal (four lines moved, no new logic) and the commit message is clear. This is a classic "uninitialized variable" bug that could lead to undefined behavior or crashes when parsing corrupted reftable files. The fix is obviously correct and aligns with the series’ overall goal of making the reftable backend more robust against malformed input.

This patch, like the rest of the series, is part of the reftable backend effort and benefits from the new fuzzing infrastructure introduced earlier in the series. No new test is added here, but the existing fuzzer and unit tests for the reftable subsystem would catch regressions. The series has already received approval from Junio C Hamano for several of its patches, and this one looks equally uncontroversial.
