This is a security-hardening patch for the reftable backend, part of Patrick Steinhardt’s v3 series (patch 4/12). It fixes a call to `abort()` in `reftable_ref_record_decode()` when encountering an invalid ref value type, replacing it with a graceful `REFTABLE_FORMAT_ERROR` return. The fix is minimal: the invalid type is now validated before being stored in the record, and the function exits early with an error instead of crashing. A new unit test (`test_reftable_record__ref_record_decode_invalid_value_type`) verifies the behavior by feeding an out-of-range value type (`REFTABLE_NR_REF_VALUETYPES`) and confirming the function returns the expected error code.

The patch touches `reftable/record.c` and adds a test to `t/unit-tests/u-reftable-record.c`. No public APIs or on-disk formats are changed; the behavior is strictly safer, replacing a crash with an error return. The commit message clearly explains the rationale: untrusted data should not trigger `abort()`, and the fix ensures the record’s `value_type` is only set after validation. The test is straightforward, using `cl_must_pass` and `cl_assert_equal_i` to verify the error code, and follows the pattern established in earlier patches in the series.

This is one of the smaller fixes in the series, but it is well-motivated and uncontroversial. The unit test is thorough and aligns with the series’ focus on hardening against corrupted files. No feedback was raised on this patch in v2, and it remains unchanged in v3. The patch is ready for merging as part of the broader reftable security-hardening effort.
