This is the fourth patch in Jeff King’s nine-patch **bugfix series** addressing memory leaks in Git’s hash implementations when non-default backends (OpenSSL, libgcrypt) are used. The series targets low-level plumbing code and was discovered via `SANITIZE=leak` testing.

Patrick Steinhardt’s reply engages with the naming and semantics of the new `git_hash_discard()` function introduced in patch 2. He acknowledges Jeff’s rationale for using "release" in `hashfile_checkpoint_release()` (to indicate cleanup for *every* checkpoint, regardless of whether it was used) but questions whether `git_hash_discard()` could be made idempotent. If it were safe to call on an already-discarded hash, the code could avoid tracking whether `git_hash_final()` was called, simplifying error paths. This is a **substantive review** comment—it probes the design of the cleanup API rather than surface-level details.

The question is narrowly scoped to the hash API’s behavior and does not challenge the patch’s correctness or the broader series goal. No alternative implementation is proposed yet, but the suggestion could influence future revisions if Jeff or others agree that idempotency is desirable. The thread’s prior discussion (including Patrick’s earlier suggestion to rename `git_hash_discard()` to `git_hash_release()`) frames this as part of an ongoing conversation about naming and API ergonomics, not a blocker for the current series.
