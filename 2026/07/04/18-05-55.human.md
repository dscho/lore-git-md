This is the second patch in the finalized v4 series that adds macOS Universal Binary support to Git’s Rust components. It introduces the `RUST_TARGETS` environment variable, allowing users to specify multiple target triples (e.g., `aarch64-apple-darwin x86_64-apple-darwin`) for cross-compilation. The build system then compiles each target separately via Cargo and combines the resulting static libraries into a single Universal Binary using `lipo`, Apple’s tool for creating multi-architecture binaries.

The patch is a clean, well-motivated build system enhancement that addresses a practical need: distributing Git with Rust components (like `git-credential-osxkeychain`) as a single Universal Binary for macOS. This is standard practice for macOS packaging and CI, eliminating the need for separate builds or Rosetta emulation. The implementation is careful to maintain backward compatibility—if `RUST_TARGETS` is unset, the build behaves exactly as before—and includes sensible error handling for non-macOS platforms.

Technically, the patch bridges a gap between Apple’s C toolchain (which natively supports multi-architecture builds via `-arch` flags) and Cargo (which requires separate invocations per target triple). The solution is minimal: it introduces declarative pattern rules to compile each target-specific library slice, then combines them into a universal archive. The commit message clearly explains the rationale and design, and the code itself is straightforward, with no on-disk format changes or user-facing behavior changes beyond the new environment variable.

All feedback from earlier iterations has been addressed, including Junio’s style tweaks (removing `@` from `mkdir` and replacing `[` with `test`) and Patrick Steinhardt’s concerns about Universal Binary completeness. While Patrick noted that the C build could theoretically also support multi-architecture, the authors clarified that this patch’s scope is sufficient for practical use cases like macOS distribution and CI. The series is now converged and ready for integration, with no outstanding objections. The changes are implicitly covered by existing build tests, and the patch is a logical follow-up to the first patch in the series, which fixed a parallel build race condition in the credential helper.
