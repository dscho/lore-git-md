This is a build system patch series for the Rustification effort, specifically targeting the macOS credential helper (`git-credential-osxkeychain`). The v4 iteration finalizes the two-patch series that was previously discussed, addressing both a parallel build race condition and macOS Universal Binary support for Rust components.

The first patch ensures the credential helper links against Rust libraries when Rust is enabled by adding `$(RUST_LIB)` as a prerequisite to the build rule. This fixes a race condition where `make -j` could attempt to link the helper before Cargo finishes compiling `libgitcore.a`. The change is wrapped in `ifndef NO_RUST` blocks for backward compatibility, making it a clean, low-risk fix.

The second patch introduces Universal Binary support via the `RUST_TARGETS` environment variable. This allows users to specify multiple target triples (e.g., `aarch64-apple-darwin x86_64-apple-darwin`), compiling separate static libraries per target and combining them into a single Universal Binary using `lipo`. The commit message now clearly explains the technical rationale: Apple’s C toolchain natively supports multi-architecture builds via `-arch` flags, while Cargo requires separate invocations per target triple. The patch bridges this gap by combining target-specific Rust static libraries into a universal archive, enabling Universal Binary support for Rust components even if the C build is not explicitly configured for it. Junio’s requested style tweaks (removing a redundant `@` prefix and replacing `if [` with `if test`) have been incorporated.

The series is now converged, with all substantive feedback addressed. Patrick Steinhardt’s earlier concerns about the completeness of Universal Binary support (specifically, whether the C build should also be modified to use `-arch` flags) remain unresolved in principle, but the current design is accepted as sufficient for practical use cases like macOS distribution and CI packaging. The patch maintains backward compatibility and introduces no on-disk format changes—it’s purely a build-time improvement.

No new test coverage was introduced, but the changes are implicitly covered by existing build tests. The series is ready for integration into Junio’s branches, marking a small but meaningful step forward for Rust support in Git’s build system.
