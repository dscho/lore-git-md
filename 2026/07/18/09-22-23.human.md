This is a **bugfix follow-up** in the ongoing sequencer rebase-dropped-commit audit. Phillip Wood acknowledges a **regression in interactive rebase** (`-i`) that Uwe Kleine-König reported: notes from commits dropped via `git rebase --skip` are still incorrectly copied to neighboring commits, despite the recently approved 9-patch series that fixed the issue for non-interactive rebase and `--empty=drop`.

The root cause is a **design gap** in the series: it only addressed commits dropped automatically by `--empty=drop`, not those dropped manually by the user (e.g., via `--skip` or `--continue` after a conflict). Interactive rebase (`-i`) defaults to `--empty=ask`, which prompts the user to decide whether to keep or drop empty commits—this path was not covered by the original fix. Phillip is now considering how to handle user-dropped commits, noting that the current behavior (dropping on `--continue`, keeping on `--skip`) is counterintuitive and dates back to Git’s early days.

No patches have been proposed yet, but the discussion clarifies that the fix will require extending the `PICK_RESULT_DROPPED` logic to cover manual skips. The regression is **specific to interactive rebase** and does not affect the apply backend or non-interactive rebase. This is a **high-priority follow-up** for the series, as it undermines the core behavioral fix for a common workflow. Test coverage for interactive rebase (`t3404-rebase-interactive.sh`) will need to be expanded to catch this edge case.
