This is a **bug report** from Uwe Kleine-König about Phillip Wood’s recently approved 9-patch sequencer series. The series was intended to fix the issue where `git rebase` incorrectly copies notes from dropped commits, but Uwe has discovered that the problem persists in **interactive rebase** (`-i`) while disappearing in non-interactive mode.

Key details:
- **Reproduction**: Uwe rebases a large branch (`device_id`) onto `next-20260717` using `git rebase --onto=next-20260717 next-20260716 -r -i device_id^{}`. During the rebase, he manually skips commits that become empty (`git rebase --skip`).
- **Symptom**: After the rebase, the notes from a dropped commit (`69be5d4f9f13`) are incorrectly copied into the commit message of the neighboring commit (`9f3e8813f6b4`). This is visible in the `git range-diff` output, where the dropped commit’s note (`Forwarded: id:...`) appears in the rewritten commit.
- **Workaround**: When Uwe rebases **without `-i`**, the rebase completes without manual intervention, and the notes are **not** copied. This suggests the bug is specific to the interactive backend.
- **Scope**: The issue affects **only interactive rebase**, not the apply backend or non-interactive rebase. This contradicts the series’ test coverage, which included both backends (`t3400-rebase.sh` for apply, `t3404-rebase-interactive.sh` for merge).

The report is **substantive and tested**: Uwe provides exact commands, commit hashes, and output snippets, making it easy to reproduce. The discrepancy between interactive and non-interactive behavior is a critical clue for debugging. No new patches or fixes are proposed yet; this is a regression report against a series that was considered complete and ready for `next`.

**Files/subsystems implicated**:
- `sequencer.c` (core logic for interactive rebase)
- Interactive rebase backend (vs. apply backend, which works correctly)
- `record_in_rewritten()` (the function responsible for tracking rewritten commits, modified in patch 9/9 of Phillip’s series)

**Likely next steps**:
- Phillip or another contributor will need to investigate why the interactive backend still copies notes from dropped commits, despite the fix in patch 9/9.
- The fix may involve adjusting how `record_in_rewritten()` is called in the interactive code path, or addressing a subtle difference in how dropped commits are handled between backends.
- Test coverage for interactive rebase (`t3404-rebase-interactive.sh`) may need to be expanded to catch this edge case.

This is a **high-priority follow-up** for the series, as it undermines the core behavioral fix. The fact that the bug is backend-specific suggests a localized issue rather than a systemic flaw in the series’ design.
