This is the final patch in the twentieth iteration of the `git cat-file --batch-command` remote-object-info series, now queued for `next`. It implements dynamic adaptation of the client's allow-list to the server's advertised `object-info` capabilities, replacing the previous hardcoded allow-list with a runtime-negotiated one.

The patch enables the client to request only the metadata fields (`size`, `type`) that the server advertises support for, ensuring forward compatibility as the `object-info` protocol gains new capabilities. When the server does not advertise a requested field, the client silently omits it (e.g., `%(objecttype)` expands to an empty string), matching `for-each-ref`'s behavior for known-but-inapplicable atoms. The implementation introduces a new `remote_allowed_atoms` string list in `struct expand_data` to track server-supported placeholders, and maps protocol options (`size`, `type`) to their corresponding atoms (`objectsize`, `objecttype`) via a new `protocol_placeholder_entry` struct.

Key changes include moving `object_info_options` out of `get_remote_info()` to allow the caller to control which options are requested, and ensuring output is always produced—even if no attributes are supported, resulting in a blank line. The patch also drops the pre-sort in `fetch_object_info_via_pack()` since the list is now unsorted (due to filtering via `unsorted_string_list_delete_item`), though this has no performance impact given the small size of the list. Test coverage in `t/t1017-cat-file-remote-object-info.sh` verifies that unsupported placeholders expand to empty strings and that `%(objectname)`-only requests trigger existence checks.

The patch is technically complete and uncontroversial, resolving the last major design issue in the series by enabling dynamic capability negotiation. The changes are mechanical and well-tested, with no known edge cases or regressions. The series is now ready for final polish before merging to `master`.
