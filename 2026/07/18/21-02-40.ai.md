This is a **follow-up discussion** in the ongoing `no-ref-delta` capability thread, focusing on the technical trade-offs between Taylor Blau’s proposed design and Jeff King’s suggested alternative.

Taylor clarifies the core motivation: the write-through proxy’s asynchronous indexer is designed to process packs in a single forward pass, with random access to already-resolved objects stored on disk. By restricting packs to `OFS_DELTA` entries, the indexer can guarantee that base objects are always processed before their deltas, avoiding the need to buffer unresolved deltas or build an OID-to-pack-position map. This simplifies the indexer’s memory management and eliminates worst-case pipeline stalls caused by long `REF_DELTA` chains with late bases.

Jeff King’s alternative—a narrower “bases-before-deltas” capability—would enforce Git’s default pack ordering (bases before deltas) without banning `REF_DELTA` outright. Taylor acknowledges this would address the ordering problem but argues it’s weaker than the current design: even a backward `REF_DELTA` requires an OID lookup, complicating the proxy’s offset-based reconstruction metadata. The discussion leaves open whether the stricter `no-ref-delta` approach is justified by the proxy’s specific needs or if a more permissive capability could achieve the same performance goals with broader protocol compatibility.

The thread remains in the design phase, with no clear consensus yet on the optimal solution. Key technical details include the proxy’s reliance on offset-based addressing, the memory overhead of `REF_DELTA` resolution, and the trade-off between strict enforcement and protocol flexibility.
