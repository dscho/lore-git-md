This is a **substantive review** of Toon Claes's bug report about `git history fixup` corrupting the index in other worktrees. Phillip Wood confirms the issue and traces its root cause: `git history fixup` rewrites the commit pointed to by the `feature` branch but does not update the index or working copy in the `feature` worktree, leaving it in a dirty state. He compares this to `git rebase --update-refs`, which refuses to update branches checked out in other worktrees by default to avoid exactly this problem.

Phillip suggests that `git history fixup` should adopt a friendlier approach, similar to the discussion in the linked thread about `rebase --update-refs`: if the worktree is clean, the command could update the index and working copy to preserve the relationship between branches and avoid materializing spurious changes. He also notes that `git rebase` refuses to rewrite a branch already being rewritten by another rebase in a different worktree, a safety measure that `git history` currently lacks.

The review is **well-informed and actionable**, drawing on prior work in the rebase subsystem to propose a clear path forward. It elevates the bug report from a mere reproduction case to a discussion about design choices and safety guarantees. The missing safety check (preventing concurrent rewrites) is a particularly important point, as it could lead to data corruption if two `git history` commands run simultaneously on the same branch. This is now a **serious correctness issue** that will likely require both a fix for the immediate index corruption and a broader safety mechanism to prevent concurrent rewrites.
