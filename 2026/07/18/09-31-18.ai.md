This is a **substantive review** of Toon Claes's bug report about `git history fixup` corrupting the index in other worktrees. Phillip Wood identifies the root cause and proposes a solution path.

The issue stems from `git history fixup` rewriting the commit pointed to by the `feature` branch (created via `git worktree add`) without updating the index or working copy in the `feature` worktree. This leaves the worktree in a dirty state with staged changes that were never made there. Phillip compares this to `git rebase --update-refs`, which refuses to update branches checked out in other worktrees by default to avoid this exact problem. He suggests adopting a similar approach for `git history fixup`: either refuse to rewrite branches checked out in other worktrees, or update the index and working copy in those worktrees if they are clean.

Phillip also notes that `git rebase` includes a safety mechanism to prevent rewriting a branch that is already being rewritten by another rebase in a different worktree. He flags this as a missing safety measure in `git history fixup`, which could lead to race conditions or data corruption if multiple instances of the command run concurrently on the same branch.

The review is well-informed and actionable, drawing on prior work in the rebase subsystem to propose a solution. It highlights two distinct problems: the immediate index corruption issue and the broader lack of safety mechanisms for concurrent rewrites. The reference to the `--update-refs` discussion provides useful context for how similar problems have been handled in the past.

Key technical details for follow-up:
- **Command**: `git history fixup`
- **Subsystems**: worktree handling, index management, commit rewriting
- **Files likely involved**: `builtin/history.c`, `worktree.c`, `read-cache.c`
