Subject: [PATCH v2] branch: clarify error message when deleting a branch used by bisect
Series version: v2 (standalone patch, follow-up work anticipated)
Originating author: René Scharfe
Thread type: user-facing error message improvement with emerging design implications for a broader branch-safety API

Core problem or goal
The error message from `git branch -d` when attempting to delete a branch currently in use by `git bisect` is generic ("used by worktree at ..."), obscuring the actual reason. The v2 patch narrows scope to address only the bisect case, replacing the generic message with a specific one ("for bisect"). Junio’s earlier feedback framed this as a foundation for a broader, consistent API to check branch usage across all commands that repoint branch tips (e.g., `git history`), but this version defers other checkout kinds (rebase, worktree) to future work.

Current status
Under review; v2 posted. Junio’s feedback from v1 suggested refining error messages and test coverage, with potential follow-up work to unify branch-safety checks. The v2 patch resolves the `int` vs. `enum` debate in favor of `enum branch_checkout_kind` for debuggability and focuses solely on the bisect case. Open questions remain: (1) how to handle the `BRANCH_CHECKOUT_KIND_UPDATE_REF` case (used during rebase with merges) in error messages, (2) whether to change the `BRANCH_CHECKOUT_KIND_CHECKOUT` message to "checked out at '%s'" (Junio and Phillip Wood’s preference), (3) extending test coverage to all checkout kinds (`WORKTREE` and `UPDATE_REF` cases are still missing), and (4) Phillip Wood’s usability concern about confusion when `git status` shows a different branch than the error message.

Key technical details
- Files touched: `branch.c`, `branch.h`, `builtin/branch.c`, `t/t3200-branch.sh`
- New data structure: `checked_out_branches` array in `branch.c` tracking checkout reasons (`BRANCH_CHECKOUT_KIND_*`) and worktree paths
- New symbols: `branch_bisecting()` helper function (internal-only)
- On-disk format: unchanged
- Test coverage: extended in `t/t3200-branch.sh` to verify the bisect-specific error message; coverage for `BRANCH_CHECKOUT_KIND_WORKTREE` and `BRANCH_CHECKOUT_KIND_UPDATE_REF` is still missing
- Error message logic: The v2 patch only addresses the bisect case, leaving the `UPDATE_REF` case (rebase with merges) and `WORKTREE` case unmodified. The `BRANCH_CHECKOUT_KIND_CHECKOUT` message remains "used by worktree at '%s'", though Junio and Phillip Wood prefer "checked out at '%s'".
- Implementation detail: The `enum branch_checkout_kind` is now used for the `kind` variable, improving debuggability without affecting error messages.

Open questions and loose ends
1. **Error message design for `BRANCH_CHECKOUT_KIND_UPDATE_REF`**: Should it be merged into the "rebase" category (René’s initial proposal), kept distinct with a technical message ("for rebase with merges", Junio’s preference), or replaced with a more detailed message to address usability concerns (Phillip Wood’s proposal)?
2. **Error message wording for `BRANCH_CHECKOUT_KIND_CHECKOUT`**: Should it remain "used by worktree at '%s'" or be changed to "checked out at '%s'" (Junio and Phillip Wood’s preference)?
3. **Test coverage**: Need to extend tests to cover the remaining checkout kinds (`BRANCH_CHECKOUT_KIND_WORKTREE` and `BRANCH_CHECKOUT_KIND_UPDATE_REF`).
4. **Usability concern**: Phillip Wood raised a concrete issue about potential confusion when `git status` shows a different branch than the error message, suggesting either enhancing `git status` to show all branches being rewritten or crafting a distinct, detailed error message for the `UPDATE_REF` case. This remains unresolved.
5. **Broader API design**: Junio’s earlier feedback hinted at unifying branch-safety checks across commands (e.g., `git history`). This remains unresolved, with no concrete follow-up patches yet, but the `checked_out_branches` array introduced in v2 could serve as a foundation for future work.
