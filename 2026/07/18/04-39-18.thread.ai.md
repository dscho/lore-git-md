Thread identity
Subject: [PATCH] branch: clarify error message when deleting the current branch
Series version: standalone patch (potential follow-up work anticipated)
Originating author: René Scharfe
Thread type: user-facing error message improvement with emerging design implications for a broader branch-safety API

Core problem or goal
The error message from `git branch -d` when attempting to delete the currently checked-out branch is generic ("used by worktree at ..."), obscuring the actual reason (regular worktree, `git bisect`, `git rebase`, or other internal operations). The patch replaces the generic message with a specific one that names the reason (e.g., "for bisect" or "for rebase"). Junio’s feedback expands the scope, framing this as a foundation for a broader, consistent API to check branch usage across all commands that repoint branch tips (e.g., `git history`, which recently missed this safety check).

Current status
Under review; no prior versions. Junio’s feedback suggests refining error messages and test coverage, with potential follow-up work to unify branch-safety checks across Git commands. The latest exchange resolves the `int` vs. `enum` debate in favor of `enum branch_checkout_kind` for debuggability. The remaining open questions are: (1) how to handle the `BRANCH_CHECKOUT_KIND_UPDATE_REF` case (used during rebase with merges) in error messages, and (2) extending test coverage to all checkout kinds (`WORKTREE` and `UPDATE_REF` cases are still missing). No consensus yet on error message design; René proposes merging the `UPDATE_REF` case into the "rebase" category for simplicity, Junio prefers a distinct message for clarity ("for rebase with merges"), and Phillip Wood now raises a usability concern about confusion when `git status` shows a different branch than the error message.

Key technical details
- Files touched: `branch.c`, `branch.h`, `builtin/branch.c`, `t/t3200-branch.sh`
- New data structure: a `strintmap` in `branch.c` mapping checkout reasons (`BRANCH_CHECKOUT_KIND_*`) to descriptive strings
- New symbols: none (internal-only change)
- On-disk format: unchanged
- Test coverage: extended in `t/t3200-branch.sh` to verify error messages during `bisect` and `rebase`; coverage for `BRANCH_CHECKOUT_KIND_WORKTREE` and `BRANCH_CHECKOUT_KIND_UPDATE_REF` is still missing. Junio’s feedback highlights the need for full coverage.
- Error message logic: The `BRANCH_CHECKOUT_KIND_UPDATE_REF` case (used during rebase with merges) is now the focal point of debate. Junio proposes a distinct message ("for rebase with merges"), René proposes merging it into the "rebase" category for simplicity, and Phillip Wood proposes a more detailed message ("because it is being updated by a rebase running in '../feature' which is updating multiple branches") to address potential user confusion when `git status` shows a different branch. The `BRANCH_CHECKOUT_KIND_CHECKOUT` message ("used by worktree at '%s'") is also under discussion, with Junio and Phillip preferring "checked out at '%s'" for clarity.
- Implementation detail: The `int` vs. `enum` debate is resolved in favor of `enum branch_checkout_kind` for the `kind` variable, as enums improve debuggability (e.g., symbolic output in GDB) without sacrificing ease of printing. This change is internal and does not affect error messages.

Open questions and loose ends
1. **Error message design for `BRANCH_CHECKOUT_KIND_UPDATE_REF`**: Should it be merged into the "rebase" category (René), kept distinct with a technical message ("for rebase with merges", Junio), or replaced with a more detailed message to address usability concerns (Phillip Wood)?
2. **Error message wording for `BRANCH_CHECKOUT_KIND_CHECKOUT`**: Should it remain "used by worktree at '%s'" or be changed to "checked out at '%s'" (Junio and Phillip Wood)?
3. **Test coverage**: Need to extend tests to cover the remaining checkout kinds (`BRANCH_CHECKOUT_KIND_WORKTREE` and `BRANCH_CHECKOUT_KIND_UPDATE_REF`).
4. **Broader API design**: Junio’s earlier feedback hinted at unifying branch-safety checks across commands (e.g., `git history`). This remains unresolved, with no concrete follow-up patches yet, but the thread could seed the effort.
