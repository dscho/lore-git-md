Thread identity
Subject: [PATCH] branch: clarify error message when deleting the current branch
Series version: standalone patch (potential follow-up work anticipated)
Originating author: René Scharfe
Thread type: user-facing error message improvement with emerging design implications for a broader branch-safety API

Core problem or goal
The error message from `git branch -d` when attempting to delete the currently checked-out branch is generic ("used by worktree at ..."), obscuring the actual reason (regular worktree, `git bisect`, `git rebase`, or other internal operations). The patch replaces the generic message with a specific one that names the reason (e.g., "for bisect" or "for rebase"). Junio’s feedback expands the scope, framing this as a foundation for a broader, consistent API to check branch usage across all commands that repoint branch tips (e.g., `git history`, which recently missed this safety check).

Current status
Under review; no prior versions. Junio’s feedback suggests refining error messages and test coverage, with potential follow-up work to unify branch-safety checks across Git commands. The latest exchange between Junio and René focuses on two technical details: (1) the use of `int` versus `enum` for the checkout kind, and (2) whether to simplify error messages by merging the `BRANCH_CHECKOUT_KIND_UPDATE_REF` case (used during rebase with merges) into the "rebase" category. No consensus yet; René proposes simplification, while Junio leans toward more descriptive messages. Test coverage remains incomplete (only 2 of 4 checkout kinds tested).

Key technical details
- Files touched: `branch.c`, `branch.h`, `builtin/branch.c`, `t/t3200-branch.sh`
- New data structure: a `strintmap` in `branch.c` mapping checkout reasons (`BRANCH_CHECKOUT_KIND_*`) to descriptive strings
- New symbols: none (internal-only change)
- On-disk format: unchanged
- Test coverage: extended in `t/t3200-branch.sh` to verify error messages during `bisect` and `rebase`; coverage for `BRANCH_CHECKOUT_KIND_WORKTREE` and `BRANCH_CHECKOUT_KIND_UPDATE_REF` is still missing. Junio’s feedback highlights the need for full coverage.
- Error message logic: Junio criticizes the current `UPDATE_REF` message ("used by worktree at '%s' for update-ref") as too technical, proposing a more descriptive alternative (e.g., "for rebase with merges"). René now proposes merging this case into the "rebase" category to simplify the user-facing output, pending Junio’s agreement.
- Implementation detail: Junio questions René’s use of `int` instead of `enum branch_checkout_kind` for the `kind` variable, noting that enums improve debuggability (e.g., symbolic output in GDB). René’s response suggests he prioritized ease of printing, but Junio demonstrates that enums can be printed just as easily.

Open questions and loose ends
1. **Error message design**: Should `BRANCH_CHECKOUT_KIND_UPDATE_REF` retain a distinct message (e.g., "for rebase with merges") for precision, or be merged into the "rebase" category for simplicity? Junio prefers clarity; René prefers simplicity.
2. **Test coverage**: Need to extend tests to cover the remaining checkout kinds (`BRANCH_CHECKOUT_KIND_WORKTREE` and `BRANCH_CHECKOUT_KIND_UPDATE_REF`).
3. **Type choice**: Should the `kind` variable use `enum branch_checkout_kind` instead of `int` for better debuggability? Junio argues for enums; René’s patch currently uses `int`.
4. **Broader API design**: Junio’s earlier feedback hinted at unifying branch-safety checks across commands (e.g., `git history`). This remains unresolved, with no concrete follow-up patches yet, but the thread could seed the effort.
