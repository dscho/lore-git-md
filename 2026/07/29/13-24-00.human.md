This is a **substantive review** of the `hn/history-squash` topic, which was recently merged to `next` and marked for `master`. Phillip Wood raises serious concerns about the correctness, edge-case handling, and user experience of the new `git history squash` subcommand.

The patch introduces a `squash` subcommand to the experimental `git history` command, allowing users to fold a range of commits into a single commit while replaying descendants on top. Phillip’s review identifies multiple **functional flaws** in the implementation:

- **Incorrect assumptions about commit reachability**: The code assumes that an `UNINTERESTING` commit implies a `BOTTOM` commit and that such a commit cannot reach any root commits. Phillip argues both assumptions are false, which could lead to incorrect squashing behavior.
- **Multiple-tip handling**: The command accepts ranges like `^A C D` (where `A`, `C`, and `D` are commits in a diverged history) but fails to squash them correctly. It also inconsistently refuses to squash `^A C` if a branch points to `B` (the merge base) but not if a branch points only to `D` (a descendant), leaving the branch unreachable after squashing.
- **Overly restrictive ref checks**: The command refuses to squash if a tag or remote-tracking ref points to any commit in the range, a behavior Phillip calls "strange" since other `git history` commands do not enforce this restriction.
- **Message handling issues**: Without `--reedit-message`, the command discards `amend!` and `squash!` commit messages, ignoring user intent. The `--reedit-message` flag is also criticized as poorly named (since the command creates a new message, not re-edits an existing one) and as an awkward reuse of rebase’s squash template, which is ill-suited for folding multiple commits into multiple targets.

Phillip plans to submit fixup patches but notes this may take until next week. His review suggests the topic may need significant revision before graduating to `master`, despite Junio’s earlier intent to merge it. The concerns are **technical and correctness-focused**, not surface-level, and could affect users relying on the feature for complex histories.
