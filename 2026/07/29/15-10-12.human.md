This is the **core implementation patch** of Harald Nordgren’s `git branch --delete-merged` series, now in its 23rd iteration and **ready for merging**. The patch adds the `--delete-merged` subcommand, which safely deletes local branches whose work has already landed on their upstream while preserving stacked work and respecting safety checks.

Phillip Wood’s review focuses on **clarity and correctness** in the stacked-branch protection logic and the `branch_pushes_to_upstream()` helper. His feedback is **substantive but non-blocking**: he identifies a **logical gap** in `branch_pushes_to_upstream()` (it checks fetch refspecs but ignores push refspecs, which could misclassify branches) and suggests **test improvements** (simpler config setup, consistent option ordering, and line-wrapping). He also questions the **behavior of stacked-branch protection** in one edge case (why `lower` is kept when `mid`’s upstream is deleted) but acknowledges the overall design is sound.

The patch itself is **feature-complete and well-tested**, with 204 lines of new tests covering stacked dependencies, missing upstreams, and ref iteration order independence. The stacked-branch protection logic—implemented via a single-pass graph traversal—ensures consistent results regardless of ref iteration order, addressing Junio C Hamano’s earlier correctness concerns. The command respects per-branch opt-out (via `branch.<name>.deleteMerged=false`), checked-out branches, and push divergence, and it supports `--dry-run` preview.

The **only unresolved technical issue** is the `branch_pushes_to_upstream()` helper, which Phillip notes does not account for push refspecs. This could cause the command to misclassify branches where pushing by name would update their upstream (e.g., `main` tracking `origin/main`). However, this is **not a regression**—the current behavior is already more conservative than necessary—and Phillip’s suggested fix (applying push refspecs in reverse) is a **forward-looking improvement** rather than a blocker. The series remains **ready for merging**, with this issue noted for follow-up.

Phillip’s review also highlights **minor test cleanups** (simpler config setup, consistent option ordering, and line-wrapping), which are **surface-level** and could be addressed in a follow-up patch if desired. The stacked-branch protection behavior he questions (`lower` being kept when `mid`’s upstream is deleted) is **intentional**—the command preserves the entire upstream chain of unmerged branches to avoid breaking stacked work—but the documentation could clarify this.

Overall, this is a **high-quality patch** that addresses a real workflow pain point with thorough safety checks and test coverage. The series is **unblocked** and should appear in an upcoming "What’s cooking" report. The only agreed follow-up work is extending stacked-branch protection to `git branch -d` for consistency, which Harald has committed to implementing after the series lands.
