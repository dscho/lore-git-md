This is a **performance discussion** about `fetch.bundleURI`, continuing the thread where Ryszard Knop reported unexpectedly slow clone times when using Git bundles for the Linux kernel repository.

Brian M. Carlson responds with a key insight: the performance comparison is flawed because a bundle containing multiple refs forces Git to process *all* objects in the bundle's pack, not just those reachable from the requested ref. This explains why a bundle-based clone might be slower than fetching a single branch directly. He suggests that a fair comparison would require a bundle containing only the desired ref, or comparing a full bundle to a full clone.

On the `index-pack` bottleneck, Brian notes that the code should respect `pack.threads` and automatically scale to half the available CPU cores (capped at 20 threads). The single-threaded behavior Ryszard observed could stem from Git being compiled without pthreads, running on a low-core machine, or being explicitly configured for single-threaded operation. Enabling threading might improve performance, though Brian hasn’t tested this with bundle URIs specifically.

Finally, Brian raises a security concern: distributing bare repositories (Ryszard’s alternative approach) is discouraged because it encourages unsafe usage patterns. Even in trusted environments, this practice could normalize anti-patterns that pose risks in broader contexts. The implication is that bundles remain the preferred solution, but their performance limitations need addressing. No patches or concrete fixes are proposed yet—this is still an exploratory discussion.
