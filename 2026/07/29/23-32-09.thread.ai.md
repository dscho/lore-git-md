Thread identity: RFC patch series proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. Originating author: brian m. carlson. Thread type: design discussion / RFC.

Core problem or goal: Git currently emits lowercase hex object IDs but accepts both uppercase and lowercase in parsing, creating potential compatibility and security issues for external tools that assume hex uniqueness. The series aims to enforce lowercase-only parsing in Git 3.0 to make the behavior consistent and predictable, addressing real-world security vulnerabilities where external tools failed to properly sanitize or filter object IDs due to case insensitivity. The first five patches introduce infrastructure (new `hex_kind` enum, `hexval_lc_table`, updated `hexval()`, `hex2chr()`, and `hex_to_bytes()` functions, and `HEX_KIND_OID` constant) and refactor existing hex-parsing code to use these helpers without altering runtime behavior yet. The final patch activates enforcement by defining `HEX_KIND_OID` as `HEX_KIND_LOWER` when `WITH_BREAKING_CHANGES` is enabled, documents the change in `Documentation/BreakingChanges.adoc`, and adds test coverage to verify rejection of uppercase object IDs.

Current status: RFC stage; no prior versions. The series is complete in implementation but explicitly seeks feedback on whether the project wants this breaking change. Junio C Hamano initially pushed back on the motivation, but brian m. carlson has since provided concrete evidence of real-world security vulnerabilities caused by Git's current case-insensitive parsing, citing personal observation of multiple security issues in external tools and ecosystem inconsistency (e.g., Gitolite and GitHub-hosted tools rejecting or mishandling uppercase hex). Junio has now engaged with both the rationale and the implementation details: he approved the use of `HEX_KIND_OID` in the fourth patch, raised a technical question about whether the constant should also cover derived hashes (e.g., packfile names, rerere database keys), and in his most recent reviews, questioned the fundamental premise of the series by invoking the Robustness Principle, arguing that Git should remain liberal in what it accepts even in a breaking-change release. He further distinguished between internal enforcement (where Git could enforce lowercase) and external inputs (where Git should continue accepting uppercase), suggesting a potential compromise. In his latest email, Junio expands on this distinction with a concrete example: Git’s dumb HTTP transport encountering a loose object directory named in uppercase (e.g., `objects/AB/`). He argues that a robust implementation would accept such directories, normalize them to lowercase internally, and avoid storing duplicates—rather than rejecting them outright. Jeff King (Peff) has weighed in on Junio’s micro-optimization suggestion for the third patch, confirming that gcc-15 does not hoist the `hexval` table selection out of the loop in `hex_to_bytes()`, but noting that branch prediction may mitigate the performance cost, making manual hoisting less critical. Peff has now identified a new edge case: uppercase hex within object payloads (specifically commit and tag objects) can create parallel histories of otherwise identical commits, since Git does not normalize case when hashing object contents. This adds a new dimension to the discussion, as the proposed breaking change (rejecting uppercase hex in parsing) would not address this case, because the uppercase hex here is part of the object content, not an external input. The thread remains focused on both the justification and the design philosophy, with no maintainer decisions or merge status yet. The first five patches remain preparatory and do not change behavior; the sixth patch introduces the breaking change but remains gated behind `WITH_BREAKING_CHANGES`.

Key technical details:
- New files: `hex-ll.c`/`hex-ll.h` (lower-level hex parsing utilities).
- New symbols: `hex_kind` enum (`HEX_KIND_MIXED`, `HEX_KIND_LOWER`, `HEX_KIND_OID`), `hexval_lc_table`, updated `hexval()`, `hex2chr()`, and `hex_to_bytes()` functions (all take `enum hex_kind` parameter).
- Modified subsystems: `hex.c`, `pkt-line.c`, `color.c`, `mailinfo.c`, `ref-filter.c`, `strbuf.c`, `url.c`, `urlmatch.c`, `index-pack.c`, `diagnose.c`, `http-push.c`, `notes.c`, `object-file.c`, `object-name.c` (hex parsing in packet-length parsing, quoted-printable decoding, percent-encoding, ref formatting, URL handling, object ID parsing from disk/network/diagnostics, and object name resolution), plus `Documentation/BreakingChanges.adoc` (documentation).
- On-disk format: no changes; this is a parser behavior change only.
- Test coverage: new test in `t1503-rev-parse-verify.sh` verifies rejection of uppercase object IDs; existing test in `t5324-split-commit-graph.sh` adjusted to avoid false positives in SHA-256 mode.
- Breaking change gated behind "breaking changes mode" (target: Git 3.0).
- First five patches are mechanical and do not introduce test failures or behavioral changes; the sixth patch introduces the breaking behavior but only when `WITH_BREAKING_CHANGES` is enabled.
- Junio’s review of the third patch suggested a micro-optimization: hoisting the `hexval` table selection outside the loop in `hex_to_bytes()` to avoid repeated conditional checks, proposing a revised API where `hexval()` would take a precomputed `void *hextable` instead of an `enum hex_kind`. Jeff King’s review confirms that gcc-15 does not perform this hoisting automatically, but notes that branch prediction may reduce the performance impact, making the optimization less urgent.
- Jeff King’s latest observation: uppercase hex within object payloads (commit and tag objects) can create parallel histories, as Git does not normalize case when hashing object contents. This affects only commits and tags (trees use binary hashes, so case is irrelevant) and is unlikely to occur accidentally with most Git commands, but demonstrates that the problem of case sensitivity extends into the object model itself. The example uses `git hash-object` to write a commit with an uppercase parent hash, producing a distinct object ID.

Open questions and loose ends:
- Whether the project wants this breaking change at all (primary open question). Junio’s initial objection to the motivation has been partially addressed by brian’s evidence of real-world security vulnerabilities, but Junio’s later reviews raised a philosophical objection based on the Robustness Principle, arguing that Git should remain liberal in what it accepts even in a breaking-change release. He further distinguished between internal enforcement (where Git could enforce lowercase) and external inputs (where Git should continue accepting uppercase), suggesting a potential compromise that would preserve case-insensitive parsing for network-facing operations while enforcing lowercase internally. In his latest email, Junio expands on this distinction with a concrete example (dumb HTTP transport encountering uppercase loose object directories) and proposes that Git should accept but normalize such inputs rather than reject them. It remains unclear whether the project will accept the disruption in light of the security rationale or whether a compromise will emerge.
- Whether `HEX_KIND_OID` should also cover derived hashes (e.g., packfile names, rerere database keys) that are not object IDs themselves but are computed from the same hash function. This question, raised by Junio, could affect the scope of the breaking change and the complexity of the implementation.
- Potential controversy due to the breaking nature of the change and the need to balance security benefits against ecosystem disruption.
- Junio’s micro-optimization suggestion for the third patch remains unresolved. Jeff King’s review confirms the compiler does not hoist the table selection, but notes that branch prediction may mitigate the cost, leaving the optimization’s necessity ambiguous. It is unclear whether brian will adopt the change or whether it will affect the series’ progression.
- Jeff King’s observation about uppercase hex in object payloads adds a new dimension to the discussion: the proposed breaking change (rejecting uppercase hex in parsing) would not address this case, because the uppercase hex here is part of the object content, not an external input. This complicates the narrative by showing that the problem of case sensitivity is more pervasive than just external tooling. Whether this weakens the justification for the breaking change (by showing it doesn’t solve the full problem) or strengthens it (by demonstrating another way case sensitivity can cause issues) remains to be debated.
