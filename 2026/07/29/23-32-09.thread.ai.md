Thread identity: RFC patch series proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. Originating author: brian m. carlson. Thread type: design discussion / RFC.

Core problem or goal: Git currently emits lowercase hex object IDs but accepts both uppercase and lowercase in parsing, creating potential compatibility and security issues for external tools that assume hex uniqueness. The series aims to enforce lowercase-only parsing in Git 3.0 to make the behavior consistent and predictable, addressing real-world security vulnerabilities where external tools failed to properly sanitize or filter object IDs due to case insensitivity. The first five patches introduce infrastructure (new `hex_kind` enum, `hexval_lc_table`, updated `hexval()`, `hex2chr()`, and `hex_to_bytes()` functions, and `HEX_KIND_OID` constant) and refactor existing hex-parsing code to use these helpers without altering runtime behavior yet. The final patch activates enforcement by defining `HEX_KIND_OID` as `HEX_KIND_LOWER` when `WITH_BREAKING_CHANGES` is enabled, documents the change in `Documentation/BreakingChanges.adoc`, and adds test coverage to verify rejection of uppercase object IDs.

Current status: RFC stage; no prior versions. The series is complete in implementation but explicitly seeks feedback on whether the project wants this breaking change. Junio C Hamano initially pushed back on the motivation, but brian m. carlson has since provided concrete evidence of real-world security vulnerabilities caused by Git's current case-insensitive parsing, citing personal observation of multiple security issues in external tools and ecosystem inconsistency (e.g., Gitolite and GitHub-hosted tools rejecting or mishandling uppercase hex). Junio has now engaged with both the rationale and the implementation details: he approved the use of `HEX_KIND_OID` in the fourth patch, raised a technical question about whether the constant should also cover derived hashes (e.g., packfile names, rerere database keys), and in a later review, questioned the fundamental premise of the series by invoking the Robustness Principle, arguing that Git should remain liberal in what it accepts even in a breaking-change release. The most recent email adds a micro-optimization suggestion for the third patch, proposing to hoist the `hexval` table selection outside the loop in `hex_to_bytes()` to avoid repeated conditional checks. The discussion remains focused on both the justification and the design philosophy, with no maintainer decisions or merge status yet. The first five patches remain preparatory and do not change behavior; the sixth patch introduces the breaking change but remains gated behind `WITH_BREAKING_CHANGES`.

Key technical details:
- New files: `hex-ll.c`/`hex-ll.h` (lower-level hex parsing utilities).
- New symbols: `hex_kind` enum (`HEX_KIND_MIXED`, `HEX_KIND_LOWER`, `HEX_KIND_OID`), `hexval_lc_table`, updated `hexval()`, `hex2chr()`, and `hex_to_bytes()` functions (all take `enum hex_kind` parameter).
- Modified subsystems: `hex.c`, `pkt-line.c`, `color.c`, `mailinfo.c`, `ref-filter.c`, `strbuf.c`, `url.c`, `urlmatch.c`, `index-pack.c`, `diagnose.c`, `http-push.c`, `notes.c`, `object-file.c`, `object-name.c` (hex parsing in packet-length parsing, quoted-printable decoding, percent-encoding, ref formatting, URL handling, object ID parsing from disk/network/diagnostics, and object name resolution), plus `Documentation/BreakingChanges.adoc` (documentation).
- On-disk format: no changes; this is a parser behavior change only.
- Test coverage: new test in `t1503-rev-parse-verify.sh` verifies rejection of uppercase object IDs; existing test in `t5324-split-commit-graph.sh` adjusted to avoid false positives in SHA-256 mode.
- Breaking change gated behind "breaking changes mode" (target: Git 3.0).
- First five patches are mechanical and do not introduce test failures or behavioral changes; the sixth patch introduces the breaking behavior but only when `WITH_BREAKING_CHANGES` is enabled.
- Junio’s review of the third patch suggests a micro-optimization: hoisting the `hexval` table selection outside the loop in `hex_to_bytes()` to avoid repeated conditional checks, proposing a revised API where `hexval()` would take a precomputed `void *hextable` instead of an `enum hex_kind`. The suggestion is not framed as a blocker and remains open-ended.

Open questions and loose ends:
- Whether the project wants this breaking change at all (primary open question). Junio’s initial objection to the motivation has been partially addressed by brian’s evidence of real-world security vulnerabilities, but Junio’s later review raised a philosophical objection based on the Robustness Principle, arguing that Git should remain liberal in what it accepts even in a breaking-change release. It remains unclear whether the project will accept the disruption in light of the security rationale.
- Whether `HEX_KIND_OID` should also cover derived hashes (e.g., packfile names, rerere database keys) that are not object IDs themselves but are computed from the same hash function. This question, raised by Junio, could affect the scope of the breaking change and the complexity of the implementation.
- Potential controversy due to the breaking nature of the change and the need to balance security benefits against ecosystem disruption.
- Junio’s micro-optimization suggestion for the third patch remains unresolved; it is not clear whether brian will adopt it or whether it will affect the series’ progression.
- No substantive technical review yet beyond Junio’s engagement with the fourth patch, his philosophical objection to the series premise, and his micro-optimization suggestion for the third patch; the discussion is still focused on both the rationale and the design philosophy.
- The series is complete and ready for review, but further progress depends on resolving the justification debate, the derived-hash labeling question, and the micro-optimization suggestion.
