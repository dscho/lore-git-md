This is the second patch in brian m. carlson’s six-part RFC series proposing a Git 3.0 breaking change: restricting hex object IDs to lowercase only. The series aims to make Git’s hex parsing consistent (emitting and accepting only lowercase) to avoid compatibility and security issues with external tools that assume hex uniqueness.

This patch is a mechanical refactoring that prepares the infrastructure for the breaking change. It modifies the `hex2chr()` helper function to accept an `enum hexkind` parameter, allowing callers to specify whether they want to parse lowercase-only hex (`HEX_KIND_LOWER`) or mixed-case hex (`HEX_KIND_MIXED`). For now, all existing callers are updated to pass `HEX_KIND_MIXED`, so the runtime behavior remains unchanged. The patch touches seven files (`hex-ll.h`, `hex.c`, `mailinfo.c`, `ref-filter.c`, `strbuf.c`, `url.c`, and `urlmatch.c`), all of which use `hex2chr()` for tasks like percent-encoding, quoted-printable decoding, or object ID parsing.

The change is straightforward and well-scoped, but it’s a necessary stepping stone for later patches that will enforce lowercase-only parsing in specific contexts (e.g., object names). The commit message clearly explains the motivation (future-proofing for the breaking change) and the mechanical nature of the update. No test failures are introduced, and the patch doesn’t yet alter Git’s behavior—it just lays the groundwork.

This patch is unlikely to be controversial on its own, but it’s part of a larger discussion about whether the project wants this breaking change at all. The series is still in the RFC stage, and no substantive technical review has been posted yet. If the series moves forward, this patch will be a key enabler for the stricter parsing rules in later patches.
