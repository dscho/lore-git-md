This is a **substantive review** of the core implementation patch in Harald Nordgren’s `git branch --delete-merged` series, now in its 23rd iteration and ready for merging. Phillip Wood’s review focuses on the **stacked-branch protection logic** and **upstream push detection**, raising two key technical concerns:

1. **Stacked-branch protection behavior**: The review questions whether the current implementation (which keeps *all* branches in a chain if any are unmerged) is too conservative. Phillip notes that the documentation should clarify this behavior, and the test for "keeps the upstream chain of a surviving branch" appears to show the opposite of what was intended—`lower` (the merged base of the chain) is preserved, but the test expects its upstream config to remain intact, which contradicts the design goal of clearing stale configs for kept (merged) branches. This suggests either a **logic error in the stacked-branch traversal** or a **test expectation mismatch**.

2. **`branch_pushes_to_upstream()` correctness**: The review identifies a **critical flaw** in the push-detection logic. The current implementation checks whether the branch’s *fetch* refspec maps to its upstream, but it should instead:
   - Apply the *push* refspec to the local branch.
   - Apply the *fetch* refspec in reverse to the result.
   - Compare that to the upstream branch.
   This ensures the check accurately reflects whether pushing the branch would update its upstream, regardless of `remote.pushDefault`. The current implementation risks **false negatives** (deleting branches that should be preserved) or **false positives** (keeping branches that should be deleted).

The review also includes **surface-level feedback** on test style (e.g., avoiding mixed option/positional arguments in `git checkout`, simplifying test setup) and documentation clarity (e.g., wrapping long command lines, clarifying stacked-branch behavior in the man page). These are minor and easily addressed.

**Impact**: The push-detection issue is a **blocker**—it undermines the safety guarantee that branches like `main` (tracking `origin/main`) are preserved. The stacked-branch test discrepancy warrants investigation, though it may be a test expectation error rather than a code bug. The series remains **ready for merging** once these issues are resolved, as the core design (order-independent protection, per-branch opt-out, `--dry-run`) is sound and well-tested.

**Key files touched**: `builtin/branch.c` (core logic), `t/t3200-branch.sh` (tests), and `Documentation/git-branch.adoc` (man page). The review does not question the flags-based API (patches 2–4/7) or the `--forked` filter foundation (patch 1/7), which are already settled.
