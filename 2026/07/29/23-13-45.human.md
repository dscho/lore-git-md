This is the fifth patch in Harald Nordgren’s 7-patch series adding `git branch --delete-merged`, now in its 23rd iteration. The series is **implementation-complete and ready for merging**, but **blocked on two correctness issues** identified by Phillip Wood in this review. This patch introduces the core `--delete-merged` subcommand, which safely deletes local branches merged into their upstream while preserving branches used as upstreams for unmerged work.

The patch is **well-structured and thoroughly tested**, with all prior feedback addressed. It implements **order-independent stacked-branch protection** via a single-pass graph traversal, ensuring consistent results regardless of ref iteration order. The command supports **repeatable `--delete-merged` arguments** (e.g., `--delete-merged origin/main --delete-merged origin/next`) to widen the upstream match and **optional positional patterns** (e.g., `topic-*`) to limit deletion scope. Safety checks include preserving checked-out branches, branches with missing upstreams, and branches where pushing by name would update their upstream (e.g., `main` tracking `origin/main`).

Phillip Wood’s review raises two **blocking technical concerns**:
1. **Stacked-branch protection test discrepancy**: The test for "keeps the upstream chain of a surviving branch" expects the upstream config of `lower` (a kept merged branch) to remain intact, but the design goal is to **clear stale configs for kept (merged) branches whose own upstream is being deleted**. This suggests either a **logic error in the stacked-branch traversal** or a **test expectation mismatch**.
2. **`branch_pushes_to_upstream()` correctness**: The current implementation checks whether the branch’s *fetch* refspec maps to its upstream, but it should instead apply the *push* refspec to the local branch, apply the *fetch* refspec in reverse to the result, and compare that to the upstream branch. The current implementation risks **false negatives** (deleting branches that should be preserved) or **false positives** (keeping branches that should be deleted).

The review also includes **surface-level feedback** on documentation clarity (e.g., wrapping long command lines, clarifying stacked-branch behavior) and test style (e.g., avoiding mixed option/positional arguments in `git checkout`, simplifying test setup). These are minor and easily addressed.

**Key files touched**: `builtin/branch.c` (core logic), `Documentation/git-branch.adoc` (man page), and `t/t3200-branch.sh` (tests). The patch is **ready for merging once the two correctness issues are resolved**. The series as a whole is **low-risk**—it introduces no behavioral changes for existing `git branch` usage and adds a well-scoped, safety-focused feature with comprehensive test coverage. The stacked-branch protection and per-branch opt-out mechanisms address real-world workflow pain points, making this a valuable addition for users managing topic branches.
