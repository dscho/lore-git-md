This is the fifth patch in Harald Nordgren’s **v23 `git branch --delete-merged` series**, which is now **blocked on two correctness issues** identified by Phillip Wood. The patch implements the core `--delete-merged` subcommand, enabling safe automated cleanup of local branches merged into their upstream while preserving branches used as upstreams for unmerged work. The series is **ready for merging** pending resolution of the blocking issues, and this patch is the centerpiece of the effort.

The email is a **reply to Phillip Wood’s substantive review** of the core logic. Harald acknowledges all of Phillip’s feedback—**clarifying documentation, fixing test style, and addressing the push-detection flaw**—but the **two blocking technical concerns remain unresolved**:
1. **`branch_pushes_to_upstream()` correctness**: The current implementation checks whether the branch’s *fetch* refspec maps to its upstream, but it should instead apply the *push* refspec to the local branch, apply the *fetch* refspec in reverse to the result, and compare that to the upstream branch. The current logic risks **false negatives** (deleting branches that should be preserved, e.g., `main` tracking `origin/main`) or **false positives** (keeping branches that should be deleted). Harald notes this will require re-adding some of the push logic removed earlier for simplicity, but the fix is necessary for safety.
2. **Stacked-branch protection test discrepancy**: The test for "keeps the upstream chain of a surviving branch" expects the upstream config of `lower` (a kept merged branch) to remain intact, but the design goal is to **clear stale configs for kept (merged) branches whose own upstream is being deleted**. Harald’s reply confirms the intent is to preserve the upstream chain of surviving *tips*, but the test expectation contradicts this. Resolution requires either fixing the logic to match the test or updating the test to match the design.

The email also addresses **surface-level feedback** from Phillip:
- **Documentation**: Harald agrees to add "it is the upstream of an unmerged branch" to the list of reasons a branch is not deleted, clarifying the stacked-branch protection behavior. He also proposes a clearer synopsis for the `--delete-merged` usage.
- **Test style**: Harald will avoid mixing options/positional arguments in `git checkout` (e.g., `git checkout --track -b unmerged origin/next`), simplify the "upstream gone" setup by directly setting config, and unwrap short command lines.
- **Test logic**: Harald notes that `main` in the "keeps cloned main without a default push remote" test has no upstream, so it should never be deleted regardless of push remote. This suggests the test may be redundant or mislabeled.

**Key files touched**: `builtin/branch.c` (core logic), `Documentation/git-branch.adoc` (man page), and `t/t3200-branch.sh` (tests). The patch introduces:
- **Order-independent stacked-branch protection** via `collect_stacked_branch_bases()` and `protect_stacked_branch_bases()`, which traverse upstream chains to mark all transitively required branches as "protected" before any deletions occur.
- **Safety checks** for checked-out branches, missing upstreams, and push divergence (though the push-detection logic is flawed).
- **Support for repeatable `--delete-merged` arguments** (e.g., `--delete-merged origin/main --delete-merged origin/next`) and optional positional patterns (e.g., `topic-*`) to limit deletion scope.

**Next steps**: Harald must resolve the two blocking issues—**rewriting `branch_pushes_to_upstream()` and reconciling the stacked-branch test discrepancy**—before the series can proceed.
