This is a **design discussion reply** in the ongoing `git rebase --update-refs` symref bugfix thread. Phillip Wood responds to Junio C Hamano’s skepticism about whether `git rebase` should handle HEAD symrefs pointing outside `refs/heads/` by providing concrete evidence that the configuration is not merely a "broken state" but an actively used pattern.

Phillip clarifies that the permissiveness introduced in commit e9cc02f0e4 (2009) was not about repair tools but about allowing `git symbolic-ref` to set HEAD to any ref under `refs/`, a capability still relied on by external tools like TopGit. He points to TopGit’s current codebase, which by default sets HEAD to `refs/top-bases/...` (outside `refs/heads/`) and uses `git rebase` as part of its workflow. This demonstrates that the edge case is not hypothetical: real-world tools depend on Git’s low-level flexibility, and `git rebase` must therefore handle symrefs robustly rather than assuming HEAD always points to a branch.

The exchange does not resolve the design tension but shifts the framing. Junio’s earlier position—that high-level commands should not cater to states Git discourages—is now countered by a concrete use case showing that the state is not only allowed but actively used. This strengthens the argument for the current patch’s approach (using `resolved_ref` for HEAD comparison) and suggests that v4 of the series will likely retain the robustness improvements rather than narrowing the scope. The latent `head_ref` buffer clobbering bug remains unaddressed and is still a candidate for a follow-up patch.
