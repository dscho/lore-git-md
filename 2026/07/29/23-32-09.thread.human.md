This thread is an RFC discussion about a proposed breaking change for Git 3.0: restricting hex object IDs to lowercase only. The series, authored by brian m. carlson, aims to address security vulnerabilities and ecosystem inconsistencies caused by Git's current case-insensitive parsing of object IDs. While Git emits lowercase hex, it accepts both cases, which has led to real-world issues in external tools that assume hex uniqueness.

The series introduces infrastructure changes (new `hex_kind` enum, updated parsing functions) in its first five patches, with the sixth patch activating enforcement—gated behind `WITH_BREAKING_CHANGES`. Junio C Hamano, the maintainer, initially questioned the motivation but has since engaged deeply with the rationale and design. He raised a philosophical objection based on the Robustness Principle, arguing that Git should remain liberal in what it accepts, even in a breaking-change release. In his latest email, Junio expanded on this, suggesting that Git could normalize uppercase inputs to lowercase internally rather than rejecting them outright, particularly for external inputs like dumb HTTP transport directories.

The discussion remains open, with no maintainer decision yet. Key unresolved questions include whether the project will accept the breaking change, whether enforcement should distinguish between internal and external inputs, and whether derived hashes (e.g., packfile names) should also be covered. The series is technically complete but awaits further feedback on its justification and potential compromises. No other contributors have weighed in substantively so far.
