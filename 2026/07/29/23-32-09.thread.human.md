This thread is an RFC discussion about a proposed breaking change for Git 3.0: restricting hex object IDs to lowercase only. The series, authored by brian m. carlson, aims to address security vulnerabilities in external tools caused by Git's current case-insensitive parsing of object IDs. The first five patches introduce infrastructure changes without altering runtime behavior, while the sixth patch activates enforcement, gated behind the `WITH_BREAKING_CHANGES` flag.

The core debate revolves around whether this change is justified. Brian argues for consistency and security, citing real-world issues in tools like Gitolite and GitHub-hosted services that reject or mishandle uppercase hex. Junio C Hamano, the maintainer, initially questioned the motivation but has since engaged more deeply, raising a philosophical objection based on the Robustness Principle. He suggests Git should remain liberal in what it accepts, even in a breaking-change release, and proposes distinguishing between internal enforcement and external compatibility. His latest reply reopens the fundamental question of whether the project should proceed with this disruption, leaving the series' future uncertain.

The discussion remains focused on the justification and design philosophy rather than implementation details. Key unresolved questions include whether `HEX_KIND_OID` should cover derived hashes (e.g., packfile names) and whether a compromise—enforcing lowercase internally while preserving case-insensitive parsing for external inputs—could satisfy both security and compatibility concerns. No maintainer decisions have been made, and the thread is still in the RFC stage.
