This thread is an RFC patch series from brian m. carlson proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. Git currently emits lowercase hex IDs but accepts both cases in parsing, which has led to security issues in external tools that assume hex uniqueness. The series introduces infrastructure for stricter hex parsing (new `hex_kind` enum, updated helper functions) and, in its final patch, enforces lowercase-only parsing when `WITH_BREAKING_CHANGES` is enabled.

Junio C Hamano, the maintainer, has engaged deeply with the proposal, initially questioning its motivation but later signaling tentative acceptance ("Will queue"). He’s expressed discomfort with the philosophical implications—particularly the idea of rejecting uppercase hex even in a breaking-change release—and suggested a compromise: normalizing mixed-case inputs to lowercase internally while accepting them from external sources. Brian has pushed back on this as impractical, arguing it would require extensive auditing for only a partial fix. Jeff King’s reviews focused on technical details, including a micro-optimization suggestion and an edge case where uppercase hex in object payloads could create parallel histories, complicating hash-algorithm compatibility.

The series is now in a holding pattern. Junio’s "Will queue" suggests movement toward integration, but the core question—whether Git 3.0 should enforce lowercase-only object IDs—remains unresolved. The thread’s tone has shifted from technical debate to procedural acknowledgment, with Brian emphasizing the project’s consensus will decide the outcome. Key loose ends include Junio’s normalization compromise, the unresolved micro-optimization, and the edge case of uppercase hex in object payloads. The discussion is effectively paused, awaiting broader community feedback or a final maintainer decision.
