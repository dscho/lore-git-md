This thread is an RFC patch series from **brian m. carlson** proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. Git currently emits lowercase IDs but accepts both cases in parsing, which has led to security vulnerabilities in external tools that assume hex uniqueness. The series introduces infrastructure (new `hex_kind` enum, `hexval_lc_table`, and updated hex-parsing helpers) in its first five patches, then activates enforcement in the sixth patch, gated behind `WITH_BREAKING_CHANGES`.

The discussion remains in the RFC stage, with **Junio C Hamano** signaling tentative acceptance ("Will queue") but expressing ambivalence about the philosophical trade-offs. Key objections have centered on whether the security rationale justifies a breaking change, with **Phillip Wood** questioning why uppercase IDs (`ABCDEF`) pose a risk when their lowercase equivalents (`abcdef`) do not. Brian addressed this by providing concrete scenarios where case-insensitive parsing enables security bypasses (e.g., tools checking only lowercase forms or regex misclassification), which may tip the balance toward acceptance. **Junio** also revived a potential compromise—normalizing mixed-case inputs to lowercase internally while accepting them externally—but Brian previously rejected this as impractical.

Recent activity has focused on technical refinements. **Elijah Newren** flagged two issues in the fifth patch: a behavioral change (preserving original case where the old code lower-cased it) and a correctness risk (storing `hexval()`’s `unsigned int` result in an `int`). Brian’s latest reply commits to documenting the behavioral change and adopting a defensive pattern (`val & ~0xf`) to address the fragility. **Junio**’s latest reviews also identified omissions in the fourth patch (`builtin/index-pack.c` and `notes.c` should use `HEX_KIND_OID` instead of `HEX_KIND_MIXED`) and requested clarification for test adjustments in the sixth patch. **Michael Montalbo** contributed a script demonstrating how mixed-case IDs can create ambiguous commit objects, further strengthening the security argument.

The series is technically complete but awaits broader consensus. The infrastructure patches (1–5) are uncontroversial, while the sixth patch’s enforcement remains the sticking point. If the security rationale holds, the series will likely advance to `next` after addressing the remaining technical feedback. The next steps are a `v2` revision incorporating Elijah’s and Junio’s suggestions, followed by renewed discussion on the breaking change’s merits.
