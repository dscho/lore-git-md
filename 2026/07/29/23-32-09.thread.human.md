This thread is a design discussion about a proposed breaking change for Git 3.0: restricting hex object IDs to lowercase only. The series, authored by brian m. carlson, aims to address security vulnerabilities and ecosystem inconsistencies caused by Git's current case-insensitive parsing of object IDs. While Git emits lowercase hex, it accepts both cases, which has led to real-world issues in external tools that assume hex uniqueness.

The series introduces infrastructure changes (new `hex_kind` enum, updated hex-parsing functions) in its first five patches, with the sixth patch activating enforcement—gated behind `WITH_BREAKING_CHANGES`. Junio C Hamano, the maintainer, initially questioned the motivation but later engaged with the rationale, citing concrete security vulnerabilities. However, he has since invoked the Robustness Principle, arguing that Git should remain liberal in what it accepts, even in a breaking-change release. Junio proposed a compromise: enforcing lowercase internally while accepting uppercase from external sources (e.g., network inputs), but brian rejects this as impractical, noting it would require auditing every `oid_to_hex` call for only a partial fix.

Jeff King (Peff) contributed technical reviews, confirming a micro-optimization suggestion from Junio (though its necessity remains ambiguous) and identifying an edge case: uppercase hex in object payloads (commits/tags) can create parallel histories, complicating hash-algorithm compatibility. This edge case remains unaddressed and may weaken the series' justification.

The thread is now sharply divided between brian's insistence on strict enforcement for security and consistency and Junio's preference for preserving backward compatibility. No decision has been made, and the series remains in RFC limbo. The outcome hinges on whether the project prioritizes security strictness over the Robustness Principle—or whether a feasible compromise emerges.
