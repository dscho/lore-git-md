This thread is about an RFC patch series from **brian m. carlson** proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. The goal is to address security vulnerabilities and ecosystem inconsistencies caused by Git’s current case-insensitive parsing of object IDs, which has led to real-world issues in external tools like Gitolite and GitHub-hosted services. The series introduces infrastructure (new `hex_kind` enum, updated parsing functions) in the first five patches—mechanical changes that don’t alter behavior—while the sixth patch activates the enforcement, gated behind `WITH_BREAKING_CHANGES`.

The discussion remains focused on two fronts: **justification** and **implementation**. Junio C Hamano initially questioned the motivation but has since engaged with both the security rationale and the technical details. His latest review, on the third patch, suggests a micro-optimization for `hex_to_bytes()` (hoisting the `hexval` table selection outside the loop) but doesn’t challenge the patch’s intent. Earlier, he raised a philosophical objection based on the Robustness Principle, arguing Git should remain liberal in what it accepts even in a breaking-change release. A separate technical question—whether `HEX_KIND_OID` should cover derived hashes like packfile names—also remains unresolved.

The series is complete and ready for review, but progress hinges on resolving the justification debate and Junio’s derived-hash labeling question. No other contributors have weighed in yet, leaving the discussion between the author and maintainer. The first five patches are uncontroversial infrastructure; the sixth, which introduces the breaking change, is the crux of the debate. For now, the series remains in RFC limbo, with no maintainer decision or merge status.
