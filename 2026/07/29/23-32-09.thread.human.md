This thread is an RFC discussion about whether Git 3.0 should enforce lowercase-only parsing of hex object IDs, proposed by brian m. carlson. The series aims to address security and compatibility issues caused by Git’s current acceptance of both uppercase and lowercase hex digits, which has led to real-world vulnerabilities in external tools that assume case uniqueness. The first five patches introduce infrastructure (new hex-parsing helpers and refactoring) without changing behavior, while the sixth patch activates the breaking change—rejecting uppercase object IDs—gated behind Git 3.0’s "breaking changes mode."

The discussion has centered on whether the project should adopt this change, with Junio C Hamano signaling tentative acceptance ("Will queue") but remaining ambivalent. He has distinguished between *storing* mixed-case inputs (e.g., loose object filenames) and *normalizing* them internally, suggesting the latter could be a compromise. brian m. carlson has argued for the change on security and consistency grounds, citing ecosystem tools that reject or mishandle uppercase hex, but acknowledges an edge case where uppercase hex in object payloads (e.g., commits) creates parallel histories, complicating hash-algorithm compatibility.

A new reply from Michael Montalbo demonstrates how Git’s current behavior allows commits to reference the same parent object using different case spellings, producing distinct commit objects that differ only in the case of the parent OID. This inconsistency—where raw output preserves mixed-case but formatted output normalizes to lowercase—could confuse downstream tools, reinforcing the argument for stricter parsing. The thread remains unresolved, with the core question—whether Git 3.0 should enforce lowercase-only object IDs—still open. Junio’s proposed compromise (normalizing inputs internally) has not been ruled out, but no consensus has emerged.
