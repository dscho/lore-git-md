This thread is an RFC discussion about a proposed breaking change for Git 3.0: restricting hex object IDs to lowercase only. The series, authored by brian m. carlson, aims to address security vulnerabilities and ecosystem inconsistencies caused by Git's current case-insensitive parsing of object IDs. While Git emits lowercase hex, it accepts both cases, which has led to real-world issues in external tools that assume hex uniqueness.

The series introduces infrastructure changes (new `hex_kind` enum, updated parsing functions) in its first five patches, with the sixth patch activating enforcement under a `WITH_BREAKING_CHANGES` flag. Junio C Hamano, the maintainer, initially questioned the motivation but has since engaged deeply with both the rationale and implementation. He raised philosophical objections based on the Robustness Principle, arguing that Git should remain liberal in what it accepts even in a breaking-change release, and suggested a potential compromise: enforcing lowercase internally while preserving case-insensitive parsing for external inputs. Jeff King (Peff) contributed technical reviews, confirming performance implications of a micro-optimization and identifying an edge case where uppercase hex in object payloads (commits/tags) could create parallel histories—though Junio downplayed this as harmless, noting Git already tolerates similar duplicates.

The discussion remains open, with no maintainer decision yet. Key unresolved questions include whether the project will accept the breaking change, whether `HEX_KIND_OID` should cover derived hashes, and whether a compromise (e.g., case normalization instead of rejection) might emerge. The thread is still in the design phase, with participants weighing security benefits against ecosystem disruption.
