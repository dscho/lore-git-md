This thread is about an RFC patch series from brian m. carlson proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. The goal is to address security vulnerabilities and ecosystem inconsistencies caused by Git's current case-insensitive parsing of object IDs, which has led to real-world issues in external tools. The series introduces infrastructure for enforcing lowercase parsing (without changing behavior yet) and activates the enforcement in the final patch, gated behind Git 3.0's "breaking changes mode."

The discussion has centered on a philosophical divide between security strictness and the Robustness Principle. Brian argues that lenient parsing is a security anti-pattern, citing modern practices in TLS and HTTP, while Junio C Hamano has pushed back, questioning whether Git should reject uppercase hex even in a breaking-change release. Junio initially suggested a compromise—enforcing lowercase internally while accepting and normalizing uppercase from external sources—but Brian rejected this as impractical. In his latest reply, Junio acknowledges the security rationale but remains uncomfortable with the idea of offloading compatibility fallout onto reimplementations like libgit2 or JGit. He signals a tentative willingness to queue the series ("Will queue") but leaves the core question unresolved, pending further community input.

Key technical details include new hex-parsing utilities (`hex-ll.c`/`hex-ll.h`), refactored subsystems (packet-length parsing, object ID resolution, URL handling), and a breaking change gated behind `WITH_BREAKING_CHANGES`. The series has also surfaced edge cases, such as uppercase hex in object payloads creating parallel histories, which complicates hash-algorithm compatibility. While the first five patches are mechanical and uncontroversial, the sixth patch—enforcing lowercase-only parsing—remains contentious. The thread is still in RFC limbo, with no maintainer decision or merge status yet.
