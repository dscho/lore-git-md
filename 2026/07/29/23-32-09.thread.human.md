This thread is about an RFC patch series from brian m. carlson proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. The goal is to address security and compatibility issues caused by Git's current case-insensitive parsing, which can confuse external tools that assume hex uniqueness. The series is complete but explicitly seeks community feedback before moving forward.

The first five patches are preparatory, introducing infrastructure like a new `hex_kind` enum and updated hex-parsing functions without changing runtime behavior. The sixth patch, gated behind `WITH_BREAKING_CHANGES`, would enforce lowercase-only parsing. Junio C Hamano has signaled tentative acceptance ("Will queue") but remains ambivalent, suggesting a potential compromise: normalizing mixed-case inputs to lowercase internally while still accepting them externally. Phillip Wood’s review of the sixth patch raises a key question about the security rationale—why `ABCDEF` is a risk when `abcdef^0` (the same object) is not—which could determine whether the series advances.

The latest email is Junio’s surface-level review of the first patch, catching a trivial typo but not engaging with the series’ broader motivation or open questions. The patch itself is mechanical and uncontroversial, touching `hex-ll.c`, `hex-ll.h`, `color.c`, and `pkt-line.c` to lay groundwork for later enforcement. No new behaviors or test failures are introduced. The thread remains in RFC limbo, with the core debate unresolved: whether the project will accept the breaking change, whether the security justification holds, and whether Junio’s compromise is feasible. Brian has left the door open to dropping the series if the community disagrees.
