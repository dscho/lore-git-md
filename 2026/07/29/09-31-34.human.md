This is a **design discussion reply** in the ongoing `git rebase --update-refs` symref bugfix thread. Phillip Wood responds to Junio C Hamano’s skepticism about whether `git rebase` should handle HEAD symrefs pointing outside `refs/heads/` by providing concrete evidence that the configuration is not just a theoretical edge case but a real-world requirement.

Phillip clarifies that Git’s low-level plumbing (`git symbolic-ref`) has *always* allowed HEAD to point to any ref under `refs/` (citing commit e9cc02f0e4 from 2009), and that this permissiveness was not just for repair tools but to accommodate tools like TopGit, which still actively uses this feature to set HEAD to `refs/top-bases/...`. While user-facing commands like `git checkout` detach HEAD when given a non-branch ref, external tools can bypass this restriction using `git symbolic-ref`, and TopGit’s rebase workflow explicitly relies on `git rebase` working in this state. The exchange reinforces that the current patch’s approach—robustly handling symrefs to non-branch refs—is not over-engineering but a necessary compatibility measure for existing workflows.

The discussion remains unresolved but now has a clear real-world anchor: TopGit’s continued use of non-branch HEAD symrefs means `git rebase` cannot assume HEAD always points to a branch without breaking external tools. This may help the author (Son Luong Ngoc) frame the v4 revision as a compatibility fix rather than a robustness improvement, though the latent `head_ref` buffer clobbering bug (unrelated to this design question) still awaits a follow-up patch.
