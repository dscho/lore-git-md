The core issue is that `fetch.bundleURI`-based clones are unexpectedly slow (4–5 minutes) compared to standard single-branch clones (~3–4 minutes). Brian explains that the comparison is misleading: a bundle containing multiple refs forces Git to process *all* objects in the bundle's pack, not just those reachable from the requested ref. A fair comparison would require a bundle containing only the target ref, or comparing a full-repository bundle to a full-repository clone. This distinction is critical for understanding whether the observed slowness is inherent to the bundle mechanism or a mismatch in the test setup.

On the `index-pack` bottleneck, Brian notes that the unbundling code simply invokes `index-pack`, which should respect `pack.threads`. He cites the logic in Git's source that caps the thread count at 20 (or half the available cores, with a minimum of 3), suggesting that the single-threaded behavior Ryszard observed is abnormal unless Git was compiled without pthreads, run on a low-core machine, or explicitly configured for single-threaded operation. Enabling threading could significantly improve performance, though Brian cautions that he lacks direct experience with `fetch.bundleURI`.

Finally, Brian raises a security concern: distributing bare repositories (Ryszard's alternative approach) is insecure because it encourages users to work directly with untrusted repos, which can lead to vulnerabilities. Bundles, by contrast, are safer because they are only used during clone/fetch operations. This framing reinforces the motivation to optimize the bundle workflow rather than abandon it.
