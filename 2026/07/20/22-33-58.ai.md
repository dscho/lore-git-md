This is a rerolled bugfix series targeting race conditions in Git's HTTP transport when multiple processes concurrently fetch the same packfile URI or dumb HTTP pack. The series now preserves resumable downloads while preventing corruption, addressing feedback from the v1 discussion that abandoning resumability was premature.

The core change in patch 1 replaces the v1 approach (unique tempfiles for packfile URIs) with a deterministic staging path opened in read-write mode without append. Each downloader maintains its own file offset, allowing overlapping responses to write identical bytes at identical offsets. This preserves resumable downloads for both packfile URIs and dumb HTTP, fixes the EOF-range/416 case, and handles concurrent unlink scenarios (including Windows sharing behavior). The patch also corrects documentation typos and clarifies staging-key semantics.

Patch 2 makes `fetch-pack` accept both `"keep<TAB><hash>"` and `"pack<TAB><hash>"` output from `index-pack`, addressing the race where a concurrent process may have already created the `.keep` file. The implementation now reads only the prefix and hash, leaving any subsequent fsck output available to `fetch-pack`. The patch validates the reported pack hash against the advertised hash and only registers a keep lockfile when the current process created it.

The test coverage is thorough, exercising resumed transfers, EOF ranges, overlapping 200/206 responses, and pre-existing `.keep` files. A new deterministic overlapping-download regression test uses a custom Perl server to simulate concurrent partial responses, verifying that the pack remains uncorrupted.

This reroll directly addresses all open questions from v1: it preserves resumability, handles handoffs and stale-file cleanup, and unifies the solution for both packfile URIs and dumb HTTP. The design avoids cross-process coordination while maintaining correctness, and the implementation is clean and well-motivated. The series looks ready for serious review and is likely to be uncontroversial.
