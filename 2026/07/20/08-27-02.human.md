This is the core implementation patch of Harald Nordgren’s `git history squash` series, now in its tenth iteration. The patch adds the new subcommand that folds a commit range into its oldest commit while preserving descendant history, addressing all feedback from earlier versions.

The command resolves a long-standing workflow gap: collapsing a linear or merge-heavy range into a single commit without the repeated conflict stops of an interactive rebase. It accepts multiple revision arguments (e.g., `HEAD~3..HEAD ^topic`) and sanitizes `rev-list` options to ensure the walk order remains predictable. A merge inside the range is folded as long as the range has a single base; otherwise, the command rejects the operation. By default, it refuses to proceed if any ref points to a commit inside the squashed range, offering `--update-refs=head` to rewrite only the current branch.

The implementation is careful about `fixup!`, `squash!`, and `amend!` commits: it refuses markers whose target lies outside the range but folds markers whose target is inside, grouping them under their targets in the `--reedit-message` template. A range made entirely of markers for one target is combined into a single commit, taking its message from the last `amend!` if present. The reflog message now records the full revision expression (e.g., `squash: updating start..HEAD ^keep`) instead of truncating to the first argument, preserving the user’s intent.

The patch is well-tested, with a 569-line test script covering range parsing, merge handling, ref safety, fixup/squash/amend edge cases, and CLI compliance. The code is cleanly structured, introducing focused helpers like `resolve_squash_range`, `reject_dangling_fixups`, and `find_interior_ref`. Junio’s “Will replace” sign-off on v7 and the resolution of all technical feedback in v9 and v10 signal that this series is ready for the next release. The only open question—whether `--reedit-message` should be the default—is a minor usability tweak and does not block merging.
