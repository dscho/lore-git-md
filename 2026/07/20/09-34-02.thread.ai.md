Subject: `git config --global` does not respect `include.*` directives by default
Series version: N/A (bug report)
Originating author: Hendrik Jaeger
Thread type: bug report

Core problem or goal
The thread reports an unintuitive interaction between `git config --global` and `include.*` directives. When a configuration value is moved to a file included via `include.*`, `git config --global` (without `--includes`) fails to find it, while `git config` (repository-level) finds it automatically. The man page phrasing suggests `--global` should behave like other "specific file" cases, but it does not. The discrepancy affects real-world usage (e.g., the `lbmk` project's config checks).

Current status
Under discussion; no patch proposed yet. The author confirms `--includes` resolves their immediate issue but questions whether the current behavior is intentional.

Key technical details
- **Command**: `git config --global <key>` vs. `git config <key>`
- **Config files**: Global Git config (`~/.gitconfig`) with `include.*` directives
- **Behavior**: Repository-level `git config` respects includes by default; `--global` does not
- **Man page claim**: `--global` is listed as an example of "giving a specific file" (implying includes should be respected)
- **Workaround**: Explicit `--includes` flag

Open questions and loose ends
1. Is the current behavior intentional, or is it a bug?
2. If intentional, what is the rationale for the inconsistency between `--global` and repository-level `git config`?
3. Should the man page be clarified, or should the behavior be changed to match user expectations?
