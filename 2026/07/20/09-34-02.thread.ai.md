Subject: `git config --global` does not respect `include.*` directives by default

Core problem or goal
The thread investigates an unintuitive interaction between `git config --global` and `include.*` directives: `git config --global <key>` (without `--includes`) fails to find values moved to files included via `include.*`, while repository-level `git config <key>` respects includes by default. The discrepancy affects real-world usage (e.g., the `lbmk` project’s config checks) and raises questions about design intent and user expectations.

Current status
The "is this a bug?" question is resolved: the current behavior is intentional, rooted in backwards compatibility and a design choice to avoid surprising users who explicitly request a specific file. Discussion has shifted to broader design implications, including whether `lbmk`’s use of `--global` is appropriate and what alternatives might better serve its goals. No patch has been proposed yet.

Key technical details
- **Command**: `git config --global <key>` vs. `git config <key>`
- **Config files**: Global Git config (`~/.gitconfig`) with `include.*` directives
- **Behavior**: Repository-level `git config` respects includes by default; `--global` does not, treating `--global` as `--file=$HOME/.gitconfig` to avoid reading outside the explicitly named file
- **Man page claim**: `--global` is listed as an example of "giving a specific file" (implying includes should be respected, but the implementation does not match this expectation)
- **Workaround**: Explicit `--includes` flag or omitting `--global` entirely
- **Alternatives**:
  - `git config <key>` (no scope) to resolve values as Git would internally
  - `git var GIT_AUTHOR_IDENT` for identity checks, which accounts for environment variables and derived values
  - `git config user.name` (without scope) to check explicitly configured values
- **Design rationale**: `--include` was implemented to avoid surprising users who request a specific file, and `--global` was treated as a synonym for `--file=$HOME/.gitconfig`

Open questions and loose ends
1. Should the man page be clarified to reflect the actual behavior of `--global` (i.e., that it does not respect `include.*` by default)?
2. Is `lbmk`’s use of `--global` overly restrictive, and should it adopt alternatives (e.g., omitting scope or using `git var`)?
3. What is the best way to check whether a user has explicitly configured Git (e.g., `git config user.name` without scope) versus whether Git can derive an ident at all (e.g., `git var GIT_AUTHOR_IDENT`)?
