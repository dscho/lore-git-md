Core problem or goal
When a remote is renamed (e.g., from `origin` to `upstream`), Git’s push tracking logic loses the configured remote name and `git status` stops displaying the push destination, even though the actual push still works. The goal is to restore the push-tracking display by resolving the URL of the renamed remote to any remaining remote that shares the same URL. The series also extends support to allow a URL (rather than just a remote name) as the value for `branch.<name>.pushRemote`, treating it as a lookup key for a uniquely matching configured remote. The extension is motivated by workflows involving GitHub’s `gh` CLI, which renames remotes during forking.

Key technical details
- Files touched: `remote.c`, `remote.h`, `transport.c`, `Documentation/revisions.adoc`, new test script `t/t5505-remote.sh` (104 lines).
- Subsystem: remote tracking, specifically the push branch display logic.
- New behavior: if the originally configured push remote is missing (due to rename) or is a URL, Git consults the URL-to-remote map to find a fallback remote that shares the same URL or pushurl. If exactly one such remote exists, it is used to resolve `@{push}` and update the remote-tracking branch after a push; if multiple remotes share the URL, the behavior remains unchanged (no tracking) to avoid ambiguity.
- New symbols: `repo_remote_for_push_tracking()` in `remote.h` (consults the URL-to-remote map), `tracking_for_push_dest()` now takes an explicit `struct repository *` parameter (currently marked `UNUSED`).
- On-disk format: unchanged.
- Test coverage: 104-line test script in `t/t5505-remote.sh` exercises rename scenarios, URL resolution, up-to-date pushes, and the edge case of duplicate URLs.
