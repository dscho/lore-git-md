This is a discussion about a reported inconsistency in `git config` behavior, specifically how `--global` interacts with `include.*` directives. Jeff King (Peff) clarifies that the current behavior—where `git config --global` does *not* respect includes by default—is intentional, rooted in backwards compatibility and a design choice to avoid surprising users who explicitly request a specific file. He traces this behavior to the original implementation of the `--include` flag, where `--global` was treated as synonymous with `--file=$HOME/.gitconfig`, meaning it should not automatically follow includes unless explicitly told to do so.

Peff also weighs in on the practical use case that prompted the report: the `lbmk` project’s script, which checks for user identity configuration using `git config --global`. He argues that the script is misusing `--global`, since it should not care *where* the user configured their identity—only whether Git can resolve it. He suggests two alternatives: either use `git config user.name` (without `--global`) to let Git resolve the value naturally, or use `git var GIT_AUTHOR_IDENT` for a more accurate check that accounts for environment variables and other Git internals. The latter would be especially useful if the script’s goal is to verify that Git can produce a valid ident, rather than just checking for explicit configuration.
