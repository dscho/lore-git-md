This is the first patch in a rerolled bugfix series (v2) targeting race conditions in Git's HTTP transport when multiple processes concurrently fetch the same packfile URI or dumb HTTP pack. The patch preserves resumable downloads while preventing corruption by switching from append mode to read-write mode with per-descriptor offsets.

The core change is in `http.c`: instead of opening partial pack files in append mode (which allows concurrent processes to interleave writes), the code now opens them read-write, seeks to the current end, and tracks the offset for incoming data. This ensures that overlapping responses write identical bytes at identical offsets, preventing corruption while maintaining resumability. The patch also handles edge cases like concurrent unlinks (including Windows-specific sharing behavior) and HTTP 416 responses when a partial pack is already complete.

Documentation updates clarify the staging-key semantics and fix a long-standing typo in the `--index-pack-args` option (now corrected to `--index-pack-arg`). The test coverage is thorough, with new regression tests in `t/t5550-http-fetch-dumb.sh` that exercise resumed transfers, EOF ranges, overlapping 200/206 responses, and pre-existing `.keep` files. A particularly notable test uses a custom Perl server to simulate concurrent partial responses, verifying that the pack remains uncorrupted even when downloads overlap.

The patch directly addresses feedback from the v1 discussion, where reviewers (notably Junio and Peff) expressed concern about abandoning resumable downloads for packfile URIs. The v2 design unifies the solution for both packfile URIs and dumb HTTP, avoiding cross-process coordination while maintaining correctness. The implementation is clean and well-motivated, with no new symbols introduced and no changes to the on-disk format.

This patch looks ready for serious review. The design is sound, the test coverage is comprehensive, and the commit message clearly explains the motivation and trade-offs. The only remaining loose end is a minor mechanical cleanup in `release_http_pack_request()`, but that’s a nit and doesn’t affect functionality. The series as a whole is likely to be uncontroversial.
