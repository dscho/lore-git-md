This thread began as a bug report about an inconsistency in how `git config --global` handles `include.*` directives compared to repository-level `git config`. The core issue—whether this behavior is a bug—has been definitively resolved: it’s intentional, rooted in backwards compatibility and a design choice to avoid surprising users who explicitly request a specific config file. Junio C Hamano and Jeff King (Peff) have closed the design discussion, confirming that the current behavior will not change.

The thread has since shifted to educating downstream projects (like `lbmk`) about better alternatives for their use cases. Peff and Junio recommend avoiding `--global` entirely when checking config values, instead using `git config <key>` (without scope) or `git var GIT_AUTHOR_IDENT`—both of which respect includes by default and align with how Git resolves values internally. Hendrik Jaeger’s recent follow-up underscores a lingering usability concern: while the behavior may be "least-surprise" for experienced users, it’s counterintuitive for newcomers, echoing the XKCD "Workflow" comic. This tension hasn’t led to a proposed patch, but it keeps open the question of whether the man page should clarify the actual behavior of `--global`.

No code changes are expected, but the thread remains active on two fronts: documenting the behavior more clearly and guiding downstream projects toward more robust alternatives. The unresolved loose ends are purely about communication, not implementation.
