This thread is about a surprising behavior in `git config --global`: it doesn’t respect `include.*` directives by default, even though the man page suggests it should behave like other "specific file" cases. Hendrik Jaeger reported the issue after noticing that `git config --global` fails to find values moved to included files, while repository-level `git config` finds them automatically. This affects real-world usage, such as the `lbmk` project’s config checks.

The discussion has clarified that the current behavior is intentional, not a bug. Jeff King (Peff) explained that `--global` was designed to avoid reading outside the explicitly named `~/.gitconfig` file, prioritizing backwards compatibility and avoiding surprises for users who request a specific file. He also questioned whether `lbmk`’s use of `--global` is the right tool for the job, suggesting alternatives like omitting `--global` entirely (letting Git resolve the value as it would internally) or using `git var GIT_AUTHOR_IDENT` for identity checks, which accounts for environment variables and derived values.

The thread is now focused on the broader design implications: whether the man page should be clarified to reflect the current behavior, and whether `lbmk` (or similar tools) should adjust their usage. Ben Knoble had earlier raised similar concerns about `--global`’s necessity, proposing alternatives that respect includes by default. No patch has been proposed yet, but the discussion has narrowed the open questions to practical next steps.
