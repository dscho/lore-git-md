This thread is about a two-patch series from Harald Nordgren that fixes Git’s push tracking display after a remote is renamed. When a remote like `origin` is renamed to `upstream`, Git currently loses track of the push destination in `git status`, even though pushes still work. The series restores the display by letting Git fall back to any remaining remote that shares the same URL, and it also extends `branch.<name>.pushRemote` to accept a URL as a lookup key for a uniquely matching remote.

The series is under review, with v1 posted. Junio C Hamano, the maintainer, has requested a revised commit message for the first patch to clarify that the URL-based lookup is an *extension* of the existing system, not a fix for something that was previously broken. Harald has acknowledged the request and will update the commit message to better explain the motivation—specifically, smoothing out workflows when remotes are renamed (a common scenario with GitHub’s `gh` CLI). No code changes are needed, and the technical details remain the same: the series touches `remote.c`, `remote.h`, and `transport.c`, adds a new test script, and introduces a helper function to resolve remotes by URL while handling edge cases like duplicate URLs.

The only open item is the commit message update, after which a v2 will be posted. Junio has already reviewed the core logic and agrees with the approach, so the series is likely to proceed once the documentation is clarified.
