This thread is about a two-patch series (v4) by Harald Nordgren that fixes Git’s push-tracking display after a remote is renamed. The issue arises when `branch.<name>.pushRemote` is set to a URL (or when the configured remote name is renamed), causing `git status` to stop showing the push destination even though pushes still work. The series restores the display by resolving the URL to any remaining remote that shares the same *effective push URL*—after applying `pushInsteadOf` rewrites—and extends support to allow URLs as `pushRemote` values, which is useful for workflows involving GitHub’s `gh` CLI.

The first patch is a mechanical cleanup removing reliance on the `the_repository` global variable, and it’s already been reviewed by Junio C Hamano without further feedback. The second patch, now posted as part of v4, implements the core logic via a new helper, `repo_remote_for_push_tracking()`, which consults Git’s URL-to-remote map to find a fallback remote when the originally configured one is missing or is a URL. The helper prefers `pushurl` over `url` when both are present and handles `pushInsteadOf` rewrites to ensure the fallback aligns with where the push would actually go. If exactly one remote matches the URL, it’s used for tracking; if multiple remotes share the URL, the behavior remains unchanged to avoid ambiguity. The test suite has been expanded to cover rename scenarios, URL resolution, `pushInsteadOf` handling, and edge cases like duplicate URLs and `pushurl` paths.

Junio’s review of v3 identified a documentation inconsistency—the commit message and man pages claimed the fallback logic used only `remote.<name>.url`, but the code actually considered both `url` and `pushurl`—and this has been fully addressed in v4. The documentation and test coverage now correctly reflect the behavior, and all prior feedback has been incorporated. The series is technically complete, with no open questions or objections, and is ready for integration. The only remaining step is Junio’s final review and queuing.
