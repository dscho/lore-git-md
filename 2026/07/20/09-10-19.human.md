This is the **core feature patch** in the v3 series adding `--reset-when-found[=<where>]` to `git bisect`. It implements the user-facing option that automatically resets the working tree once the first bad commit is identified, eliminating the need for a manual `git bisect reset`.

The patch wires the new option into both `git bisect start` and `git bisect run`, accepting either `--reset-when-found` (defaults to `original`) or `--reset-when-found=<where>` with values `original` or `found`. The chosen target is persisted in a `BISECT_RESET_WHEN_FOUND` state file, and the reset is performed quietly using the plumbing change introduced in patch 1. For `git bisect run`, the reset is deferred until after the captured output is printed and the `BISECT_RUN` file is closed, addressing platform-compatibility concerns about unlinking open files.

The implementation enforces the constraint that `--reset-when-found` cannot be used with `--no-checkout`, as that mode prevents checking out either target. The test suite has been expanded with four new tests validating both `original` and `found` targets, state cleanup, and edge cases like invalid targets and `--no-checkout` conflicts. The documentation is updated to reflect the new option and its behavior.

This patch is technically solid, with no on-disk format changes or new symbols beyond the state file updates. The design has settled after two iterations, and the implementation is uncontroversial. The feature is ready for integration and will be particularly useful for automated workflows and interactive debugging.
