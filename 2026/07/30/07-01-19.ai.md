This is a feature patch introducing a new `--date=elapsed` (and `--date=elapsed-pad`) date format to Git, along with corresponding `%aX` and `%cX` pretty-format placeholders. The feature addresses a gap in Git's date formatting: while `--date=human` provides a readable but imprecise phrase like "2 days ago," the new format offers a precise, script-friendly breakdown of elapsed time (e.g., "1y 11M 5d 13h 5m 13s") modeled after `uptime(1)`.

The patch is well-structured and thorough. It adds the new date mode to the `date_mode_type` enum, implements the formatting logic in `date.c` (with a helper function `show_date_elapsed()`), wires it through `show_date()` and `parse_date_format()`, and exposes the placeholders in `pretty.c`. The implementation handles edge cases like future timestamps (clamped to "0s") and includes both compact and zero-padded variants. Documentation updates cover the new options and placeholders, and tests verify the behavior for both the date helper and pretty-format equivalence.

The motivation is clearly articulated: the existing `--date=human` format obscures precise time differences, while raw timestamps (`%ct`) require manual calculation. The author also notes prior art (`git-log-compact`) and explains why it wasn’t merged, positioning this as a lighter-weight alternative. Four open questions are flagged for discussion (placeholder letter choice, format naming, future timestamp behavior, and symmetry of padded placeholders), but none appear to block the patch’s core functionality.

The patch passes all tests, including new ones for the elapsed format, and the code is clean and idiomatic. The use of `uptime(1)` conventions (30-day months, 365-day years) aligns with Git’s existing `show_date_relative()` approximations, ensuring consistency. The choice of `X` as the placeholder letter (due to `E` being reserved for mailmap variants) is pragmatic, though the author invites alternatives.

This is a user-facing feature with clear utility for scripting and readability. The implementation is self-contained and unlikely to introduce regressions, making it a strong candidate for merging. The open questions are minor and can be resolved during review.
