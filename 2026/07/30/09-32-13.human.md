Phillip’s review confirms the original synopsis for `--delete-merged` is fine (the `(--delete-merged <branch>)...` notation is idiomatic for “give this option at least once”), but he **sharpens the two technical objections** that Harald must address:

1. **`branch_pushes_to_upstream()` is still broken**. The current implementation checks whether the branch’s *fetch* refspec maps to its upstream, but it should instead:
   - Apply the *push* refspec to the local branch (e.g., `refs/heads/main` → `refs/heads/master`).
   - Apply the *fetch* refspec to the result (e.g., `refs/heads/master` → `refs/remotes/origin/main`).
   - Compare that to the upstream branch.
   Phillip corrects his earlier suggestion: the fetch refspec should be applied **forward**, not in reverse. The fix is **not independent** of the stacked-branch logic—Harald removed much of the push machinery when refactoring for stacked branches, and now must **reintroduce it carefully** to avoid regressing the safety check that prevents deleting branches like `main` tracking `origin/main`.

2. **Stacked-branch protection test expectation is still misaligned with the design goal**. The test expects the upstream config of `lower` (a kept merged branch) to remain intact, but the **design intent** is to **clear stale configs for kept (merged) branches whose own upstream is being deleted**. Phillip presses for a clear rationale: why preserve the whole upstream chain rather than just the upstream of the unmerged branch? Harald’s reply (“to preserve the upstream chain of surviving tip”) is **not yet persuasive**—the test and the code are still at odds, and the cover letter never flagged this as a deliberate behavior change.

**Next steps**: Harald must **rewrite `branch_pushes_to_upstream()`** to correctly simulate push/fetch refspecs and **reconcile the stacked-branch test**—either by updating the test to match the design goal (clearing stale configs) or by updating the code to match the test (preserving the whole chain).
