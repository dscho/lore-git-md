Thread identity
Subject: `git config --global` reads only one file despite docs claiming it reads both
Series version: standalone bug report (no patch series)
Originating author: Nils Fahldieck
Thread type: bug report

Core problem or goal
The `--global` flag in `git config` is documented to read both `~/.gitconfig` and the XDG config file (`~/.config/git/config`), but the implementation reads only one file (prioritizing `~/.gitconfig` if readable, even if empty). This creates a discrepancy between documented and actual behavior, leading to user confusion and practical failures in tools relying on `--global`. The issue is now framed as a systemic inconsistency: `git config --get` reads both files, while `git config --global` does not, violating user expectations of uniform behavior across commands.

Current status
Under review. The maintainer (Junio C Hamano) and Ben Knoble agree the documentation is incorrect, but no consensus has emerged on the fix direction. The maintainer implicitly prefers aligning the docs with the code (Option B: document single-file behavior), while Nils Fahldieck and Ben Knoble’s observations about unintuitive behavior with `--global --no-includes` and cross-command inconsistency strengthen the case for aligning the code with the docs (Option A: make `--global` read both files). Nils has signaled willingness to contribute a patch but is uncertain about the process for updating documentation (man pages and git-scm.com).

Key technical details
- **Subsystem**: configuration handling (`config.c`)
- **Functions**: `git_global_config()` (single-file logic), `do_git_config_sequence()` (multi-file logic)
- **Files touched**: `~/.gitconfig`, `~/.config/git/config`
- **Behavioral change**: If both files exist, `--global` currently reads only `~/.gitconfig` (even if empty), while `--get` reads both. Option A would make `--global` read both files, matching the documentation and `--get` behavior. The issue also affects `--global --no-includes`, which may behave unintuitively due to the single-file limitation.
- **Backward compatibility**: Option A preserves compatibility (no existing configurations would break; users relying on the undocumented single-file behavior would gain access to settings in the XDG file). Option B would require users to manually migrate settings to a single file.

Open questions and loose ends
- **Fix direction**: Should the code be updated to match the docs (Option A) or the docs updated to match the code (Option B)? The maintainer’s preference for Option B remains unchallenged, but Nils’s emphasis on cross-command inconsistency (`--get` vs. `--global`) and Ben’s reference to `--global --no-includes` issues may shift the balance toward Option A.
- **Implementation process**: Nils is willing to contribute a patch but is uncertain about the process for updating documentation (man pages, git-scm.com, and translations). This may delay progress until clarified.
- **Backporting**: Should the fix (whichever is chosen) be backported to maintenance releases, given the long-standing nature of the issue?
- **User impact**: Is the current behavior (reading only one file) intentional or an oversight? The lack of historical context persists, but the systemic nature of the issue (affecting `--global --no-includes` and cross-command consistency) suggests it is likely an oversight.
