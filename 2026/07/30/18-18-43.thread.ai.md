Subject: `git config --global` reads only one file despite docs claiming it reads both
Series version: standalone bug report (no patch series)
Originating author: Nils Fahldieck
Thread type: bug report

Core problem or goal
The `--global` flag in `git config` is documented to read both `~/.gitconfig` and the XDG config file (`~/.config/git/config`), but the implementation only reads one file (prioritizing `~/.gitconfig` if readable, even if empty). This creates a discrepancy between documented and actual behavior, potentially leading to user confusion or misconfiguration. The issue is now understood to have broader implications, as it also affects the interaction between `--global` and include directives, suggesting a systemic problem in how global configuration is handled.

Current status
Under review. The maintainer (Junio C Hamano) and Ben Knoble agree the documentation is incorrect and needs correction, but no consensus has emerged on whether to align code with docs (Option A: read both files) or docs with code (Option B: document single-file behavior). The thread remains unresolved on the fix direction.

Key technical details
- **Subsystem**: configuration handling (`config.c`)
- **Functions**: `git_global_config()` (single-file logic), `do_git_config_sequence()` (multi-file logic)
- **Files touched**: `~/.gitconfig`, `~/.config/git/config`
- **Behavioral change**: If both files exist, `--global` currently reads only `~/.gitconfig` (even if empty), while default `--get` reads both. Option A would make `--global` read both files, matching the documentation. The issue also affects `--global --no-includes`, which may behave unintuitively due to the single-file limitation.
- **Backward compatibility**: Option A preserves compatibility (no existing configurations would break; users relying on the undocumented single-file behavior would gain access to settings in the XDG file).

Open questions and loose ends
- **Fix direction**: Should the code be updated to match the docs (Option A) or the docs updated to match the code (Option B)? The maintainer and Ben Knoble agree the documentation is wrong, but neither has explicitly endorsed a fix. The maintainer’s framing suggests a preference for Option B, while Ben’s reference to broader unintuitive behavior with `--global --no-includes` may strengthen the case for Option A.
- **Backporting**: Should the fix (whichever is chosen) be backported to maintenance releases, given the long-standing nature of the issue?
- **User impact**: Is the current behavior (reading only one file) intentional or an oversight? The lack of historical context persists, but the new reference to `--global --no-includes` suggests the issue may be systemic rather than isolated.
