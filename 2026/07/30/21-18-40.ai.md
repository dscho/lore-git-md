This is a follow-up in the RFC thread proposing to restrict Git 3.0's hex object ID parsing to lowercase only. The author, brian m. carlson, responds to Junio C Hamano's request for a stronger justification by providing concrete evidence of real-world security vulnerabilities caused by Git's current case-insensitive parsing.

The email shifts the discussion from theoretical consistency to practical security impact. brian reports having personally observed multiple security issues where external tools failed to properly sanitize or filter object IDs because they assumed hex uniqueness, leading to vulnerabilities. This is the first time the thread has cited specific harm rather than potential risk. Additionally, brian points to widespread Git-adjacent software (including Gitolite and GitHub-hosted tools) that either rejects uppercase hex or handles it incorrectly, creating ecosystem inconsistency. The email also notes that Git's own hook examples use lowercase-only patterns, reinforcing the expectation that object IDs are lowercase.

The argument now rests on three pillars: security vulnerabilities in the wild, ecosystem incompatibility, and user expectations set by Git's own documentation. This response does not address the implementation details (which remain unchanged from the original series) but aims to overcome Junio's objection that the motivation was insufficient. Whether this will be enough to justify a breaking change in Git 3.0 remains to be seen; the thread is now squarely focused on the trade-off between disruption and security benefit. No new patches or technical feedback have been introduced.
