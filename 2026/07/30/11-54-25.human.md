This is a **build system** follow-up in the `WITH_BREAKING_CHANGES` test-failure thread. Jeff King (Peff) replies to brian m. carlson’s patch that moves the inclusion of `config.mak` earlier in the Makefile to ensure the `WITH_BREAKING_CHANGES=1` flag is respected when generating the list of binaries to build.

Peff confirms the underlying issue—`WITH_BREAKING_CHANGES` is ignored during the initial build target generation—but raises a serious concern: moving the `config.mak` inclusion too early would break the Makefile’s last-one-wins behavior for variables like `CFLAGS`. He demonstrates this with a concrete example: a user’s `CFLAGS` override in `config.mak` would be silently ignored, leading to build failures or unintended compiler flags. Instead, Peff suggests a targeted fix: extract the `git-whatchanged` line from the main `BUILT_INS` setup and handle it conditionally later, mirroring the existing pattern for `http-fetch` and `http-push`.

The discussion is technical but narrow, focusing on the mechanics of Makefile variable precedence. Peff’s feedback is substantive and tested (he includes a reproduction case), making it a clear blocker for the current patch. The thread is now waiting on brian to revise the approach; until then, the build system issue remains unresolved, and users building with `WITH_BREAKING_CHANGES=1` may still encounter test failures due to stale artifacts. This is a pragmatic, low-risk fix that matters primarily to contributors preparing for Git 3.0.
