This is a follow-up in the ongoing RFC discussion about restricting Git 3.0 to lowercase-only hex object IDs. The author, brian m. carlson, responds to Junio C Hamano’s request for a stronger justification by providing concrete examples of real-world security vulnerabilities caused by Git’s current case-insensitive parsing.

brian elaborates that the core issue is not just theoretical inconsistency but actual security incidents where external tools (and even Git’s own hook examples) assume hex object IDs are always lowercase, leading to ineffective filtering or sanitization. They cite Gitolite and other Git-adjacent software that fails to handle uppercase IDs correctly, as well as GitHub code searches revealing widespread use of `[0-9a-f]{40}` patterns that silently exclude uppercase variants. The argument is that Git’s current behavior—accepting formats that most of the ecosystem rejects—creates a mismatch that only ever causes problems, never interoperability.

The thread remains in the design phase, with no technical review of the implementation yet. Junio’s earlier pushback focused on the lack of a compelling long-term benefit, and brian’s response now centers on security and ecosystem consistency as the primary motivations. Whether this will be enough to overcome the project’s inherent conservatism around breaking changes remains an open question. The discussion is still about *whether* to do this, not *how*.
