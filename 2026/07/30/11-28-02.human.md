This is the fifth iteration of a two-patch bugfix series for `git mv` that fixes misleading error messages and unsafe behavior when the destination path contains missing directories or tracked symlinks. The series is now complete and ready for integration.

The first patch improves error messages by including both source and destination paths when `rename()` fails, making it clear which part of the operation caused the problem. The second patch adds an early check for three problematic destination path cases: missing leading directories, non-directory components, and any tracked symlink in the path. This prevents both misleading error messages and a subtle index corruption bug where moving through a symlink would leave the index recording the literal symlink path while the file was moved to the resolved target.

In this version, the author has extracted a small shared condition into a new helper function `needs_worktree_rename()` to ensure the early check and the actual rename operation stay in sync, addressing Junio’s request for deduplication. The commit message has also been reworded for clarity. Two new tests cover edge cases: moving into an existing directory (where the destination is normalized to a full path) and moving to a bare filename in the current working directory (where no leading directory check is needed).

The series has been thoroughly reviewed and approved by Junio, with all technical concerns resolved. The only remaining loose end is a TOCTOU race (where the destination directory could disappear between the check and the `rename()` call), which is acknowledged as "the best we can do" for now. The implementation now rejects all tracked symlinks in the destination path, aligning with `git apply` precedent and Junio’s requirement that Git must not follow tracked symlinks. Test coverage is comprehensive, including regression tests for the index corruption scenario. This is a well-crafted, user-facing fix that addresses a real problem.
