This is the second patch in a two-patch bugfix series for `git mv`, now in its fifth iteration (v5). The patch addresses a long-standing correctness and usability issue: `git mv` previously failed to detect missing destination directories, non-directory path components, or tracked symlinks in the destination path until the `rename(2)` syscall, leading to misleading error messages and potential index corruption.

The patch adds an early check in `builtin/mv.c` that rejects three problematic cases before attempting the move: missing leading directories (ENOENT/ENOTDIR), non-directory components, and *any* tracked symlink in the destination path (regardless of target type). The symlink check uses `has_symlink_leading_path()`, borrowed from `git apply`, to avoid following symlinks and align with Git's policy of not traversing tracked symlinks. The check is guarded by the new `needs_worktree_rename()` helper, which ensures it only runs when the move would actually touch the worktree (skipping index-only, sparse, or out-of-cone operations). This helper also deduplicates logic previously repeated in two places, optimizing memory allocation by deferring the `dirname` copy until needed.

Test coverage in `t/t7001-mv.sh` is comprehensive, adding 102 new lines that verify the new behavior for symlinks (as both final and intermediate components), missing directories, non-directory components, `--dry-run` detection, and force-flag behavior. A regression test confirms the index is not corrupted when a move through a symlink is rejected. The patch introduces two new translatable error messages but does not change existing ones or the on-disk format.

The series is technically complete, with Junio explicitly approving the approach and no outstanding objections. The only unresolved issue is a TOCTOU race (the destination could disappear between check and `rename()`), which the commit message acknowledges as "the best we can do" for now. The helper function name (`needs_worktree_rename()`) may still be bikeshedded during integration, but this is purely cosmetic. The patch is ready for `next`.
