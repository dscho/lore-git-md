This is the latest update in Harald Nordgren’s long-running series to add `git branch --delete-merged`, a safe automated cleanup command for local branches. The series is **implementation-complete and ready for merging**, but **blocked on two unresolved correctness issues** identified by Phillip Wood in this email exchange. Both issues are in patch 5/7, which implements the core `--delete-merged` subcommand.

The first issue is **`branch_pushes_to_upstream()` correctness**. The current implementation checks whether the branch’s *fetch* refspec maps to its upstream, but it should instead **apply the *push* refspec to the local branch, then apply the *fetch* refspec to the result, and compare that to the upstream branch**. Phillip clarifies the correct sequence with a concrete example: if `origin` uses `main` locally but `master` remotely, the push refspec `refs/heads/main:refs/heads/master` and fetch refspec `refs/heads/master:refs/remotes/origin/main` must both be applied to determine whether pushing the branch would update its upstream. The current logic risks **false negatives** (deleting branches like `main` that track `origin/main`) or **false positives** (keeping branches that should be deleted). Harald acknowledges this will require re-adding some of the push logic removed earlier for simplicity.

The second issue is a **test discrepancy in the stacked-branch protection logic**. The test for "keeps the upstream chain of a surviving branch" expects the upstream config of `lower` (a kept merged branch) to remain intact, but the design goal is to **clear stale configs for kept (merged) branches whose own upstream is being deleted**. Phillip questions why the whole chain is preserved rather than just the upstream of the unmerged branch, noting this is a **behavior change from earlier versions** that wasn’t clearly justified. Harald confirms the intent is to preserve the upstream chain of surviving *tips*, but the test expectation contradicts this. Resolution requires either **fixing the logic to match the test** (preserving upstream configs for kept merged branches) or **updating the test to match the design** (clearing stale configs).

Harald is actively working on fixes for both issues. He has already addressed Phillip’s **surface-level feedback** (usage syntax clarification, test style improvements) and is now focused on the **substantive correctness concerns**. The rest of the series—including the **per-branch opt-out (`branch.<name>.deleteMerged=false`)**, **order-independent stacked-branch protection**, **`--dry-run` preview**, and **flags-based API refactoring**—is **unchanged and ready for merging**. Junio C Hamano has explicitly confirmed the series is ready pending resolution of these two issues.

This is a **well-crafted, thoroughly reviewed feature** that addresses a real workflow pain point: safe automated cleanup of local branches. The unresolved issues are **narrow and technical**, not design-level problems, and the fixes are straightforward. Once resolved, the series should merge quickly. If you care about branch management or have been following the thread, now is the time to review the **push-detection logic** and **stacked-branch test expectations** in patch 5/7.
