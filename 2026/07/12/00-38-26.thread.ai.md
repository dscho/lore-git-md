Thread type: bugfix patch

Core problem or goal
Fix inconsistent handling of empty commits in `git rebase --autosquash`: when a `fixup!` or `squash!` operation cancels out its target commit, the resulting empty commit is currently *always* stopped at, ignoring the `--empty` option (drop/keep/stop). The patch aims to make autosquash respect `--empty` for these emptied commits, enabling workflows like reverting a commit via `fixup!` and having `--empty=drop` remove both the original and its revert. The goal now includes distinguishing between commits that *become* empty during rebase (which should respect `--empty`) and commits that *were already empty* (which should not be dropped), and handling edge cases around conflict resolution, multiple fixups, and missing pick commands.

Key technical details
- Files touched: `sequencer.c` (core logic), `git-rebase.adoc` (documentation), `t/t3415-rebase-autosquash.sh` (tests).
- New behavior: `do_pick_commit()` must now track the original emptiness state of the target commit and distinguish it from emptiness induced by autosquash. It must also handle conflict resolution paths (e.g., `git reset HEAD^` vs. `git checkout HEAD^ :/`), multiple fixups targeting the same commit, and missing pick commands (e.g., after `reset`, `exec`, or `break`).
- Implementation refinements: Phillip suggests extending the return enum from `pw/rebase-drop-notes-with-commit` to include a "dropped HEAD" state instead of adding a `dropped` output parameter. Documentation wording ("melded" → "squashed") and test cases must be updated to avoid applying `--empty` to commits that were already empty.
- On-disk format: unchanged.
- Symbols: no new CLI options or config keys; leverages existing `--empty` option.
- Test coverage: must be expanded to cover edge cases, including commits that were already empty, conflict resolution paths, multiple fixups, and missing pick commands.
