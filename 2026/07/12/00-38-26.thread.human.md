This thread is about a bugfix patch (v3) by Farid Zakaria that makes `git rebase --autosquash` respect the `--empty` option for commits that become empty after a `fixup!` or `squash!` operation. The goal is to allow workflows like reverting a commit via `fixup!` and having `--empty=drop` remove both the original and its revert, while distinguishing between commits that *become* empty during rebase (which should respect `--empty`) and those that *were already empty* (which should not be dropped).

The patch is currently under review and blocked on a sequencing dependency (`pw/rebase-drop-notes-with-commit`), which Phillip Wood expects to graduate to `next` shortly. Phillip’s substantive review of v3 identified several edge cases (original commit emptiness, conflict resolution, multiple fixups, missing pick commands) and implementation refinements (e.g., extending a return enum instead of adding an output parameter) that Farid will address in v4. No technical objections to the core idea have been raised, but the patch is not yet ready for integration.

In the latest email, Phillip clarifies logistical details for Farid: how to track the dependency’s graduation (via Junio’s "What's cooking" reports) and which commit to use as the rebase base (the tip of the dependency’s branch, not `next`). The thread remains blocked on the dependency’s graduation, but Farid now has clear guidance on how to proceed once that happens. Key participants are Farid (author), Phillip (reviewer), and Junio (maintainer).
