This thread is about a bugfix patch by Farid Zakaria that makes `git rebase --autosquash` respect the `--empty` option for commits that become empty during fixup or squash operations. The issue is that when a `fixup!` or `squash!` cancels out its target commit, the resulting empty commit is currently always stopped at, ignoring `--empty=drop` (or `keep`/`stop`). The goal is to enable workflows like reverting a commit via `fixup!` and having `--empty=drop` remove both the original and its revert.

The patch is now at v4, which addresses the edge cases raised in Phillip Wood’s substantive review of v3: distinguishing originally empty commits from autosquash-induced emptiness, handling conflict resolution paths, multiple fixups, missing pick commands, and rewritten commit tracking. The dependency (`pw/rebase-drop-notes-with-commit`) is now in `next`, so the patch can be cleanly rebased. Junio C Hamano’s recent coordination ping and Farid’s logistical update confirm the patch is unblocked and ready for re-review. Phillip Wood’s feedback remains the primary technical hurdle, but v4 should resolve his concerns about correctness and consistency with Git’s existing behavior. No objections to the core idea have been raised, and the patch is now poised for integration once v4’s edge cases are validated.
