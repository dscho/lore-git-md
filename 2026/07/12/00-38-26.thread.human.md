This thread is about a bugfix patch from Farid Zakaria that aims to make `git rebase --autosquash` respect the `--empty` option when a `fixup!` or `squash!` operation cancels out its target commit, producing an empty commit. Currently, these emptied commits are always stopped at, ignoring `--empty`. The patch is in its third version but remains under review, with no maintainer decision yet.

The key technical challenge is distinguishing between commits that *become* empty during rebase (which should respect `--empty`) and those that *were already empty* (which should not be dropped). Phillip Wood’s review of v3 identified several edge cases—conflict resolution, multiple fixups, missing pick commands—and suggested implementation refinements, including extending a return enum rather than adding an output parameter. The patch also depends on Phillip’s `pw/rebase-drop-notes-with-commit` topic, which is expected to graduate to `next` soon.

Farid recently confirmed he’s paused work until the dependency lands to avoid rebasing on a moving target, but hasn’t shared a timeline for v4. Junio’s recent ping and Farid’s response signal the patch is still active but stalled pending updates. No technical objections to the core idea have been raised, but the unresolved edge cases and dependency mean it’s not yet ready for integration. The next steps will likely focus on addressing Phillip’s feedback and expanding test coverage for the edge cases.
