Thread identity: RFC proposal for a standardized debug-commit mechanism in Git. Series version: none (initial proposal). Originating author: Simon Richter. Thread type: feature request / RFC.

Core problem or goal: Provide a standardized way for developers to mark debug commits (e.g., temporary `printf` statements) so that Git's autosquash feature can automatically drop them during interactive rebase (`git rebase -i`). The goal is to streamline history cleanup before submission and prevent accidental inclusion of debug code in shared branches via push hooks or CI checks. The proposal targets only interactive rebase and client-side hooks without altering core Git behavior or on-disk formats.

Current status: Conceptual discussion stage; no implementation or patches yet. Junio C Hamano has responded with technical feedback on feasibility, suggesting the use of a `drop!` prefix (instead of `discard!`) to align with existing sequencer conventions (e.g., `fixup!`). No agreement or decisions on implementation; the thread remains exploratory. The proposal is still lightweight, with no changes to Git's core logic or on-disk formats.

Key technical details: Proposed mechanism would use a commit message prefix (e.g., `drop!`) to signal debug commits for automatic removal during interactive rebase. Junio notes that the sequencer machinery already supports similar patterns (e.g., `fixup!`), and the feature could leverage this by converting `pick` instructions to `drop` for commits with the prefix. No new symbols, files, or subsystems identified yet. No changes to on-disk formats or test coverage discussed. Junio clarified that no changes to `git commit` are needed—users could manually use `git commit -m 'drop!'`—and that a custom `GIT_SEQUENCE_EDITOR` script could achieve the same result today without modifying Git.

Open questions and loose ends:
- The exact commit message convention (e.g., `drop!` vs. `discard!` or another prefix).
- How autosquash would recognize and handle these commits (e.g., via a new `--autosquash-drop` flag or integrated into existing autosquash logic).
- Whether this would be opt-in or opt-out (e.g., via configuration).
- How push hooks or CI checks would enforce this (e.g., rejecting commits with the debug prefix).
- Potential edge cases (e.g., conflicts during rebase, interaction with other autosquash patterns like `fixup!` or `squash!`).
- Backwards compatibility concerns (e.g., existing workflows that might conflict with the proposed prefix).
- Whether the feature should be built into Git or remain a client-side script (Junio’s response suggests the latter is feasible today).
