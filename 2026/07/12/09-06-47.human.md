This is a security-focused reply in the ongoing discussion about the `GIT_NO_LAZY_FETCH=fromAccepted` feature series. Christian Couder responds to brian m. carlson’s high-weight objection that the series expands the attack surface by allowing more network-facing C code to run in the context of an untrusted repository.

Christian argues that the series does not substantially increase risk because it does not change any defaults—`GIT_NO_LAZY_FETCH` remains enabled by default for `git upload-pack`—and the new `fromAccepted` mode is more restrictive than the existing `GIT_NO_LAZY_FETCH=0` (which allows all lazy fetching). He acknowledges the security concern but frames it as a separate issue: while client acceptance of a promisor remote signals trust in that remote, the served repository itself may still be untrusted. He suggests that server operators, not clients, should control which repositories are marked as trusted, and proposes future work to address this, such as operator-defined allow/deny rules, repo-scanning tools, or mechanisms to limit lazy fetching to safe operations (e.g., avoiding config file reads or hook execution).

The reply is conciliatory but firm: Christian agrees the series doesn’t solve all security problems but maintains its value as a pragmatic middle ground. He commits to improving documentation in the next version to clarify these risks. The thread remains unresolved, with brian’s objection still unaddressed in substance—no counterproposal or compromise has emerged, and the series’ fate likely hinges on whether the security concerns can be mitigated or whether the project accepts the trade-off.
