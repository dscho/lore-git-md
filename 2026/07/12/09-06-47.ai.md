This is a security-focused reply in the ongoing thread about the `GIT_NO_LAZY_FETCH=fromAccepted` feature series. Christian Couder responds to brian m. carlson’s high-weight objection, which argued that the series expands the attack surface by allowing more network-facing C code to execute in the context of an untrusted repository.

Christian pushes back on the characterization that the series *substantially* increases risk, noting that the new `fromAccepted` mode is more restrictive than the existing `GIT_NO_LAZY_FETCH=0` (which disables all lazy-fetch protections) and does not change any defaults. He acknowledges the core security concern—that the served repository itself may still be untrusted even if the promisor remote is mutually accepted—but argues that the operator of the server (not the client) should be responsible for marking repositories as trusted. He suggests several potential future improvements to address this, including server-side configuration to explicitly mark trusted repositories, operator-defined allow/deny rules, and tools to scan repositories for sensitive configuration.

The reply also commits to improving documentation in the next revision (v2) to clarify these security considerations. While Christian does not propose immediate changes to the implementation, his framing positions the series as a pragmatic step forward rather than a final solution, inviting further discussion on how to balance usability and security in lazy-fetching scenarios. The thread remains unresolved, with brian’s objection still unaddressed in substance.
