This is a brief follow-up in the `git-subtree` safeguard thread, clarifying the Rust rewrite's stance on manual `-X subtree` merges. Ian Jackson confirms that the Rust rewrite will not support such merges but will not actively discourage or prevent users from performing them independently. The key point is that the rewrite is not designed to handle unmarked subtree merges (those done manually with `git merge -X subtree`), and mixing them with the new implementation could lead to unpredictable results—though the rewrite itself won’t block or detect these merges at runtime.

The exchange with D. Ben Knoble resolves the last ambiguity around the rewrite’s design intent: users who rely on `-X subtree` merges for workflows outside `git-subtree` can continue doing so, but they should avoid interleaving them with the new `git-subtree` commands. Jackson hints that the Rust rewrite may eventually offer a smoother transition path for users currently using `-X subtree`, though this is still a TODO. The safeguard patch series (already under review) remains focused solely on preventing mixing of the old and new implementations via the `subtree.rust-rewrite` config key, not on policing manual merge strategies. The discussion is now purely informational, with no new review points or design changes introduced.
