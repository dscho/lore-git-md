This is a **contributor housekeeping** follow-up in the `git-subtree` safeguard thread, clarifying the Rust rewrite’s stance on manual `-X subtree` merges. Ian Jackson confirms that the Rust rewrite will not actively discourage users from performing manual `-X subtree` merges in isolation, but it will not support them either. The rewrite’s ergonomics are expected to be superior to manual merges, and Jackson plans to explore a transition path (likely treating such merges as "unmarked subtree merges") to help users migrate from manual `-X subtree` workflows to the new implementation. This response resolves the last open question from D. Ben Knoble’s follow-up, leaving no remaining ambiguities about the Rust rewrite’s design intent or the safeguard’s scope.

The clarification underscores that the safeguard (introduced in the patch series) remains narrowly focused: it prevents mixing the old shell-script implementation with the Rust rewrite by detecting the `subtree.rust-rewrite` config key, but does not police manual merge strategies. The Rust rewrite will document the risks of interleaving manual `-X subtree` merges with its own operations, but runtime enforcement is limited to the safeguard’s config check. Jackson’s TODO note about transition support suggests future work may address migration from manual merges, but this is not part of the current series.

Key technical details reiterated:
- The Rust rewrite will not parse or validate manual `-X subtree` merges, treating them as pre-existing downstream branches.
- The safeguard’s detection logic checks only the top-level repository config (`subtree.rust-rewrite`), not subtree-internal metadata.
- No runtime enforcement of manual merge restrictions is planned; documentation will advise against mixing strategies.
