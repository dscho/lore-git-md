This is a **contributor housekeeping** follow-up in the `git-subtree` safeguard thread. D. Ben Knoble chimes in to clarify a key point about the forthcoming Rust rewrite of `git-subtree`: whether it will actively discourage *all* manual `-X subtree` merges, or only mixing them with the new implementation.

Ian Jackson’s reply in the quoted text makes it clear that the Rust rewrite will **not support** manual `-X subtree` merges (what he calls "unmarked subtree merges"), but he does not intend to prevent or discourage users from continuing to use them *outside* the new implementation. The concern is interoperability: mixing the two approaches (e.g., using `-X subtree` on a repository that has already been modified by the Rust rewrite) could produce confusing or incorrect results, especially when combined with `--squash`. Ian plans to document this limitation and add a test case, but he does not propose runtime enforcement. The safeguard in the current patch series is narrowly focused on detecting the *config key* (`subtree.rust-rewrite`) that the Rust rewrite will use, not on policing merge strategies.

This exchange is a minor but useful clarification for users who rely on `-X subtree` today. It does not alter the design or scope of the current patch series, which remains ready for a v2 posting.
