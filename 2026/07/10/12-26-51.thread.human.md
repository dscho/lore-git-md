This thread is about allowing users to configure whether `git fetch --recurse-submodules` should fail hard or just warn when a submodule’s gitlink points to an unreachable commit. The series, now at version 3, is authored by Paulius Zaleckas and introduces a new configuration option (`fetch.submoduleErrors`) and CLI flag (`--submodule-errors`) to control this behavior. The default remains `fail` to preserve backwards compatibility, but users can now opt for `warn` mode to avoid disruptive fetch failures in workflows where upstream topic branches are still evolving.

The first patch in the series fixed a correctness issue in submodule fetch error handling, ensuring transient failures don’t prematurely abort the fetch. The second patch, just summarized, adds the user-facing controls, propagates the setting to child fetches (including `--all` and nested recursion), and updates documentation and tests. Feedback from earlier versions was substantive and has been addressed in this iteration. The implementation touches `submodule.c`, `builtin/fetch.c`, and related documentation and test files, with thorough test coverage for the new behavior.

No open questions remain, and the series is now under review. If merged, this would resolve a long-standing pain point for users working with submodules in active development.
