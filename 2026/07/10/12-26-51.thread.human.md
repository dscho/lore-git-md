This thread is about a patch series that adds a configuration option (`fetch.submoduleErrors`) and corresponding command-line flag (`--submodule-errors`) to control whether `git fetch --recurse-submodules` fails hard or merely warns when a submodule’s gitlink points to an unreachable commit. The default behavior (`fail`) is preserved for backwards compatibility, while the new `warn` mode enables workflows where upstream topic branches are still in flux.

The series is now at version 4, with the latest update addressing a technical concern raised by Junio C Hamano. The issue was that an explicit `--submodule-errors=fail` flag could be silently overridden by a `fetch.submoduleErrors=warn` configuration in child fetches (e.g., when using `--all`). The fix ensures the resolved value (whether from CLI or config) is always propagated to child processes, preserving the user’s intent. This was a correctness fix for a subtle edge case, not a design change.

The series touches `submodule.c`, `builtin/fetch.c`, and related documentation and tests. It introduces a new config key (`fetch.submoduleErrors`) and CLI option (`--submodule-errors=(fail|warn)`), along with tests to verify the new behavior and edge cases. The first patch in the series (a correctness fix for submodule fetch error handling) remains unchanged, while the second patch (user-facing controls) now includes the propagation fix.

Junio’s feedback was substantive, engaging with the behavior and edge cases, and the author has addressed it in this update. The series is still under review, with no merge status change. The only remaining open question is whether the fix fully resolves the propagation concern to Junio’s satisfaction.
