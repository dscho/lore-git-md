This thread is about a patch series (v3) by Paulius Zaleckas that makes submodule fetch errors configurable. The goal is to let users choose whether `git fetch --recurse-submodules` should fail hard or just warn when a submodule’s gitlink points to an unreachable commit. The default (`fail`) keeps existing behavior, while the new `warn` mode helps workflows where upstream topic branches are still changing.

The series is under review. The first patch fixes a logic flaw in submodule fetch error handling, ensuring errors are recorded only after both fetch phases complete. The second patch adds the user-facing controls: a `fetch.submoduleErrors` config key and a `--submodule-errors` CLI option. These settings are propagated to child fetches (e.g., with `--all` or `--multiple`), and errors are routed through a new helper to respect the chosen policy.

Junio’s recent review highlights a subtle issue in the second patch: the logic for propagating the `--submodule-errors` setting to child fetches doesn’t handle the `fail` case correctly. If a user overrides the config with `--submodule-errors=fail` on the command line, child fetches might silently revert to the config default instead of respecting the override. This could lead to inconsistent behavior, especially with `--all` or `--multiple`. The fix would be to ensure the explicit CLI setting is always propagated to child processes. No other open questions remain, and feedback from earlier versions has been addressed.
