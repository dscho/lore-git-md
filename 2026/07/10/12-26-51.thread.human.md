This thread is about a patch series (v6) by Paulius Zaleckas that adds configurable error handling for `git fetch --recurse-submodules`. The goal is to let users choose whether fetch should fail hard or just warn when a submodule’s gitlink points to an unreachable commit, with the default (`fail`) preserving backwards compatibility. The series also fixes a pre-existing logic flaw where submodule fetch errors were recorded prematurely, before all retry attempts were exhausted.

The series is now technically complete, with all review feedback addressed, including Junio Hamano’s latest mechanical requests (changing array indexing from `size_t` to `unsigned` and renaming the array to singular form). The first patch refactors the error-handling logic, while the second adds the user-facing controls—a new config key (`fetch.submoduleErrors`) and CLI option (`--submodule-errors`)—and wires them into the fetch machinery. The implementation is clean, using a shared name array for parsing and formatting, and the setting is properly forwarded to child fetches (including `--all` and nested recursion).

Key participants include Paulius (the author), Junio (who reviewed earlier versions and requested the latest mechanical improvements), Ramsay Jones (who noted a test portability issue now fixed), and Jean-Noël Avila (who contributed documentation fixes). The series is under review and awaiting maintainer action, with no open questions or loose ends. The changes are narrowly scoped, well-tested, and solve a real workflow pain point without introducing broader risks.
