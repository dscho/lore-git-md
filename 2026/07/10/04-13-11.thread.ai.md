Thread identity: Patch series (single patch) introducing a bugfix for `--autosquash` behavior in `git rebase` when `fixup!`/`squash!` commits cancel out their target, resulting in empty commits. Originating author: Farid Zakaria. Thread type: bug report and fix.

Core problem or goal: Fix a long-standing edge case in the sequencer subsystem where `fixup!` or `squash!` commits that cancel out all changes in their target commit are not handled according to the `--empty` option (`drop`, `keep`, or `stop`). Currently, Git halts the rebase with an error instead of respecting the user's `--empty` configuration.

Current status: Under review. The initial version (`v1`) of the patch has received substantive feedback from Phillip Wood, and Farid Zakaria has announced a forthcoming `v2` that will address the review concerns. The `v2` will adopt Phillip's proposed alternative: adding a new check to detect when applying a `fixup!` makes the target empty (rather than modifying the existing emptiness check), preserving existing behavior for `fixup!` commits that become empty. It will also fix correctness issues, such as removing the `rewritten-pending` file when dropping a commit. No merge event to `master` or other integration branches has been reported.

Key technical details:
- **Files touched**: `sequencer.c` (core logic), `Documentation/git-rebase.adoc` (user-facing documentation), `t/t3415-rebase-autosquash.sh` (test coverage).
- **Subsystems**: Sequencer (`--autosquash` logic), rebase.
- **New/renamed symbols**: None explicitly introduced; the `v2` will modify the logic to add a new check for emptiness after applying a `fixup!` (rather than changing `is_index_unchanged()` and `allow_empty()` as in `v1`).
- **Behavior changes**:
  - The new check will detect when applying a `fixup!` makes the target commit empty, classifying such commits as "became empty" (subject to `--empty` handling) while preserving existing behavior for `fixup!` commits that become empty.
  - When `--empty=drop` applies, the patch will ensure the emptied commit is dropped by removing the `rewritten-pending` file and moving `HEAD` back to its parent before flushing the rewritten-commit list, preserving mappings for `--update-refs` and other consumers.
- **On-disk format changes**: None.
- **Test coverage**: New tests in `t/t3415-rebase-autosquash.sh` cover all three `--empty` modes (`drop`, `keep`, `stop`) for both `fixup!` and `squash!` scenarios, including edge cases like root commits and already-empty targets.
- **Open design questions**:
  - Correctness of dropping commits: The `v2` will address Phillip's concerns about the `rewritten-pending` file and ensure labels/`--update-refs` commands after the dropped commit see `HEAD` pointing to the dropped commit's parent.
  - **New autosquash directive**: The thread has expanded to discuss a potential `revert!` (or `drop!`) autosquash directive. Three competing designs are now proposed:
    - **Phillip Wood (original)**: Use an empty marker commit to represent the `revert!` directive, avoiding conflicts during rebase.
    - **Yuxuan Chen**: Use an inverse patch (like `git revert`) to represent the `revert!` directive, prioritizing semantic clarity and consistency with existing Git commands. Conflicts during rebase would signal real difficulties in undoing the change, mirroring `git revert` behavior.
    - **Phillip Wood (new)**: A middle-ground proposal: a new `git revert --drop` option (or similar) that creates a commit containing the inverse patch *and* a `drop!` message. During `git rebase --autosquash`, the sequencer would replace the target commit’s `pick` with `drop` and discard the `drop!` commit itself. This avoids conflicts during rebase while reflecting the intended removal in the repository state before the rebase runs. Cites an open GitGitGadget issue as prior art for this idea.
