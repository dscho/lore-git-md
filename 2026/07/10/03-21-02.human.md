This is a review exchange on the third patch in Johannes Schindelin’s eleven-patch bugfix series (`js/coverity-fixes-v2`), which adds a NULL guard in `remote_tracking()` in `remote.c`. The patch itself is small and uncontroversial in intent—preventing a NULL-dereference crash—but Junio C Hamano’s review raises a design question: whether the function should silently return an error (`-1`) or explicitly fail with `BUG()` when given a NULL `remote`.

Dscho’s original patch treats a NULL `remote` as "no tracking ref available" and returns `-1`, mirroring the existing behavior for other error cases in the same function. Junio argues that since the function is *not* designed to be called with NULL, silently returning `-1` obscures a programming error and makes the reasoning behind the guard fragile. He prefers `BUG()` to ensure future changes to the caller do not reintroduce the issue unnoticed.

The disagreement is narrow but meaningful: it’s about whether defensive programming should prioritize robustness (silent error handling) or correctness (loud failure). Neither approach changes the patch’s core goal—preventing a crash—but the choice affects how future regressions would surface. The discussion is still open; no updated patch has been sent yet. For now, the series remains uncontroversial, but this patch may see a v3 to address Junio’s feedback.
