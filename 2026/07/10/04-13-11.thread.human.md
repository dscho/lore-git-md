This thread is about a bugfix for `git rebase --autosquash` when `fixup!` or `squash!` commits cancel out their target, leaving an empty commit. The issue has been a long-standing edge case where Git halts with an error instead of respecting the user's `--empty` option (`drop`, `keep`, or `stop`). Farid Zakaria, the author, posted an initial patch (`v1`) that modifies the sequencer logic to treat such commits as empty only if the target was already empty, enabling automatic dropping when `--empty=drop` is set.

Phillip Wood provided a substantive review, disagreeing with the implementation approach. He argued that the patch breaks his workflow, where empty commits are used as placeholders and later `fixup!` commits may become empty. He proposed an alternative: add a new check to detect when applying a `fixup!` makes the target empty, preserving existing behavior for `fixup!` commits that become empty. He also raised correctness concerns about how the patch handles dropping commits, particularly around the `rewritten-pending` file.

Farid has now agreed to address Phillip's feedback in a forthcoming `v2`. The next version will add a new check to detect when a `fixup!` makes the target empty, rather than modifying the existing emptiness check, and will remove the `rewritten-pending` file when dropping commits. The patch is motivated by a real-world workflow at Meta, where internal LLVM patches are managed as single commits using `fixup!` autosquash, and the fix enables automatic dropping of both a commit and its revert. The discussion is now focused on refining the implementation to balance the new use case with existing workflows. No merge decisions have been made yet, and the series remains under active review.
