This thread is about a bugfix patch from Farid Zakaria that addresses a long-standing edge case in `git rebase --autosquash`. When a `fixup!` or `squash!` commit cancels out all changes in its target (e.g., a revert of a previous commit), Git currently fails to respect the `--empty` option, halting the rebase with an error instead of dropping, keeping, or stopping at the empty commit as configured. The patch fixes this by adjusting how emptiness is determined during amending operations, ensuring the correct parent commit is used for comparison.

The fix is motivated by a practical workflow at Meta, where internal LLVM patches are managed as single commits using `fixup!` autosquash. The patch enables automatic dropping of both the original commit and its revert when `--empty=drop` is used, eliminating manual rebase steps. The implementation touches `sequencer.c`, updates the `git-rebase` documentation, and adds comprehensive tests covering all `--empty` modes for both `fixup!` and `squash!`. The author also raises the possibility of a `revert!` autosquash directive in a follow-up, hinting at broader improvements to rebase ergonomics.

So far, the patch appears uncontroversial, with a clear problem statement, thorough test coverage, and narrowly scoped changes. No reviews or objections have been posted yet, but the follow-up discussion about `revert!` could spark debate about autosquash semantics. The series is at its first version (`v1`), and the patch is under review.
