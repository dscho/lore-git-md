This thread began with Farid Zakaria’s patch to fix a long-standing edge case in `git rebase --autosquash`, where `fixup!` or `squash!` commits that cancel out their target would halt the rebase with an error instead of respecting the `--empty` option. The patch is now under review, with a second version (`v2`) in the works to address substantive feedback from Phillip Wood. That version will add a new check to detect when applying a `fixup!` makes the target empty, preserving existing behavior for other cases, and will fix correctness issues around dropping commits.

The discussion has since expanded to explore a potential `revert!` (or `drop!`) autosquash directive, which would allow users to mark commits for removal during rebase. Phillip Wood and Yuxuan Chen have proposed competing designs: Yuxuan favors an inverse-patch approach (like `git revert`) for semantic clarity, while Phillip advocates for an empty marker commit to avoid conflicts during rebase. In this latest exchange, Phillip suggests a middle ground—a `git revert --drop` option that would create a commit with an inverse patch *and* a `drop!` message, which the sequencer would then use to replace the target commit’s `pick` with `drop` during rebase. This would sidestep conflicts while still reflecting the intended removal in the repository state. No consensus has been reached, and the original bugfix patch remains unaffected by this design debate. The thread is still in the design phase for the `revert!` directive, with no code yet proposed.
