This thread is about a bugfix patch from Farid Zakaria that addresses a long-standing edge case in `git rebase --autosquash`: when a `fixup!` or `squash!` commit cancels out all changes in its target commit, Git currently halts with an error instead of respecting the user's `--empty` option (`drop`, `keep`, or `stop`). The patch modifies the sequencer logic to correctly identify these cases as "became empty" and apply the `--empty` handling, enabling workflows like automatically dropping both a commit and its revert.

Phillip Wood has reviewed the patch and raised substantive concerns. While he agrees with the problem and use case, he disagrees with the implementation. The patch changes the behavior of `fixup!` commits that become empty to only treat them as empty if the target commit was itself empty, which breaks his workflow where he uses empty commits as placeholders. He proposes an alternative: add a new check to detect when applying a `fixup!` makes the target empty, preserving the current behavior for `fixup!` commits that become empty while also handling the cancellation case. He also notes a correctness issue: when dropping a commit, the patch should remove the `rewritten-pending` file to avoid recording the commit as rewritten.

The discussion is now open on whether to adjust the patch to Phillip's alternative or proceed with the current approach. The patch is still under review, with no other positions recorded yet. The series is at version 1, and the author has hinted at a broader effort to improve rebase ergonomics, including a potential `revert!` autosquash directive.
