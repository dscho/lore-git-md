This is the maintainer's review of the second patch in Paulius Zaleckas' v3 series introducing configurable submodule fetch error handling. The patch adds the user-facing controls (`fetch.submoduleErrors` config and `--submodule-errors` CLI option) that let users opt into non-fatal behavior when `git fetch --recurse-submodules` encounters a submodule whose gitlink points to an unreachable commit.

Junio's review focuses on a single technical point: the logic in `add_options_to_argv()` that propagates the `--submodule-errors` setting to child fetches. Currently, the code only pushes `--submodule-errors=warn` to the child's argument vector when the config value is `SUBMODULE_ERRORS_WARN`, but does nothing when the value is `SUBMODULE_ERRORS_FAIL`. Junio questions whether this is correct when the user explicitly overrides the config with `--submodule-errors=fail` on the command line. He suggests that the child fetch should receive the explicit `--submodule-errors=fail` argument rather than silently defaulting to `fail`.

The concern is subtle but valid: if the parent fetch's behavior is controlled by an explicit CLI override, that override should be propagated to child fetches to ensure consistent behavior across the entire operation (especially with `--all` or `--multiple`). The current implementation risks silently reverting to the config default in child processes, which could surprise users who expect the CLI setting to take precedence everywhere. The fix would be to push `--submodule-errors=fail` to the child's argv when the CLI override is `fail`, not just when it is `warn`.
