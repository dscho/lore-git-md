This is a security-related objection to Christian Couder’s three-patch series that introduces a `fromAccepted` option to `GIT_NO_LAZY_FETCH`.

The series proposes a middle-ground security setting: instead of disabling lazy fetching entirely (the current default), it would allow lazy fetching only from promisor remotes that both the server advertises and the client accepts via the "promisor-remote" capability in protocol v2. The goal is to reduce the attack surface while still permitting some lazy fetching for performance.

brian m. carlson’s reply is a strong, principled rejection. They argue that the change expands the security threat model by exposing more code—particularly network-facing C code—to untrusted repositories. Their concern centers on the fetch code’s default behavior of reading repository configuration, including remote settings, which they believe should never run in the context of an untrusted repository. The objection is not about the implementation quality or design details, but about the fundamental security implications of relaxing the current strict default.

No technical counter-arguments or alternative proposals are offered in this email; it is a clear, high-level security stance. The thread is now at a conceptual impasse: the series’ goal of a pragmatic security-performance trade-off is directly at odds with brian’s position that no such relaxation should be permitted while Git’s network code remains in C. Future discussion will likely need to address whether the threat model can be narrowed or whether the feature’s benefits outweigh the risks.
