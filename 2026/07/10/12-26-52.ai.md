This is the first patch in Paulius Zaleckas’s v3 series introducing configurable submodule fetch errors. It targets the submodule subsystem and fixes a long-standing logic flaw in how recursive submodule fetches report failures.

The patch restructures the error-handling flow in `submodule.c` so that a phase-1 fetch failure (fetching refs) does not immediately mark the overall operation as failed. Instead, the decision is deferred until after the phase-2 OID-based retry: if phase 2 succeeds, no error is recorded; if phase 2 also fails, the error is recorded then. This ensures that transient or recoverable failures do not abort the entire fetch prematurely. The patch also extracts the common error-recording logic into a helper (`record_fetch_error`) and uses it consistently for all submodule fetch errors, including the “Could not access submodule” case.

The test coverage is thorough: a new test verifies that a failed submodule fetch is still reported even when the gitlinked commits happen to be present locally, addressing a subtle edge case that the old logic missed. The patch touches only `submodule.c` and the test suite (`t/t5526-fetch-submodules.sh`), with no changes to user-facing behavior—this is purely a correctness fix that paves the way for the configurable error policy introduced in patch 2.
