This is a two-patch series from Paulius Zaleckas that makes submodule fetch errors configurable. It targets the submodule and fetch subsystems.

The series addresses a long-standing pain point: when `git fetch --recurse-submodules` encounters a submodule whose gitlink points to an OID not reachable from the submodule’s remote, Git currently fails hard. This is disruptive in workflows where upstream topic branches are still in flux—even if the local branch doesn’t depend on the missing commit, the entire fetch aborts.

Patch 1 fixes a pre-existing NEEDSWORK in `submodule.c` where a phase-1 fetch failure was recorded immediately, before the phase-2 OID-based retry could run. After the fix, errors are only recorded if the phase-2 retry also fails or if no retry is scheduled. The existing fatal behavior is preserved, but the logic is now structured so that later patches can safely change the error-handling policy.

Patch 2 introduces `fetch.submoduleErrors` (config) and `--submodule-errors=(fail|warn)` (command-line) to let users opt into non-fatal behavior. The default remains `fail` for full backwards compatibility. The implementation routes all submodule fetch errors through `record_fetch_error()` so they honor the new warn mode, forwards the setting to child fetches (so it works with `--all`/`--multiple` and nested recursion), and adds comprehensive tests covering the new modes, error reporting, and edge cases.

v3 addresses feedback from the list: phase-1 failures are now reported even when the gitlink commits are already present locally, “Could not access submodule” errors are routed through the new error-handling machinery, the option is forwarded to child fetches, and the documentation no longer implies that `git pull` accepts `--submodule-errors`. The series touches `submodule.c`, `builtin/fetch.c`, the fetch config and options documentation, and the test suite (`t/t5526-fetch-submodules.sh`).
