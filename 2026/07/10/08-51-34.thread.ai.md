Thread identity: Patch series replacing the `GIT_NO_LAZY_FETCH=fromAccepted` proposal with `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable to mark repositories as trusted for lazy fetching. Series version: v2. Originating author: Christian Couder.

Core problem or goal: Provide a server-side mechanism for operators to explicitly declare which repositories are safe to lazy-fetch from, addressing the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration. The new approach shifts trust decisions entirely to the server operator, modeled after Git’s `safe.directory` configuration, and is intended as a replacement for the earlier client-side `fromAccepted` proposal.

- New or modified symbols: `path_allowlist_apply()` now takes an `allow_dot` argument to control whether single-dot paths (`.`) are accepted; the existing `safe_directory_cb` caller passes `true` for backward compatibility.
- New behavior: `uploadpack.lazyFetchTrusted` (protected configuration variable) will allow server operators to mark repositories as trusted for lazy fetching. Lazy fetching is permitted only for repositories explicitly listed in this variable, sidestepping client-side negotiation of promisor remotes. The configuration is read from protected files only, and relative paths (including single-dot paths) are rejected. When the served repository is trusted, `GIT_NO_LAZY_FETCH=0` is set in the environment.
