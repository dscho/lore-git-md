Thread identity: Patch series replacing the `GIT_NO_LAZY_FETCH=fromAccepted` proposal with `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable to mark repositories as trusted for lazy fetching. Series version: initial (v1). Originating author: Christian Couder.

Core problem or goal: Provide a server-side mechanism for operators to explicitly declare which repositories are safe to lazy-fetch from, addressing the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration. The new approach shifts trust decisions entirely to the server operator, modeled after Git’s `safe.directory` configuration, and is intended as a replacement for the earlier client-side `fromAccepted` proposal.

Key technical details:
- Files touched: `promisor-remote.c` (refactoring), `promisor-remote.h` (header updates), `setup.c` (allowlist refactoring), `setup.h` (documentation), `git-upload-pack.adoc`, `git.adoc` (documentation), `upload-pack.c` (configuration reading and integration), `upload-pack.h` (export), new test script (`t/t5710-promisor-remote-capability.sh`).
- New behavior: `uploadpack.lazyFetchTrusted` (protected configuration variable) allows server operators to mark repositories as trusted for lazy fetching. Lazy fetching is permitted only for repositories explicitly listed in this variable, sidestepping client-side negotiation of promisor remotes. The configuration is read from protected files only, and relative paths (including single-dot paths) are rejected. When the served repository is trusted, `GIT_NO_LAZY_FETCH=0` is set in the environment, permitting `upload-pack` and its `pack-objects` child to lazily fetch objects as needed.
- Refactoring specifics:
  - Patch 1/5: `lazy_fetch_objects()` helper introduced; `promisor_remote_get_direct()` split into remote-selection and object-validation logic; `try_promisor_remotes()` now returns `bool`; `GIT_NO_LAZY_FETCH` check runs once up front; `promisor_remote_init()` skipped when lazy fetching is disabled. The patch is uncontroversial, with no behavioral changes and minor optimizations (e.g., skipping initialization when lazy fetching is disabled). A minor sign-off email address issue was noted and will be corrected in the next iteration.
  - Patch 2/5: `path_allowlist_apply()` helper extracted from `safe_directory_cb()` to generalize allowlist-checking logic. Handles wildcard (`*`), dot (`.`), absolute paths, `real_pathdup()` normalization, and directory-globbing (`/*`). `safe_directory_cb()` reduced to a thin wrapper delegating to the new helper.
  - Patch 3/5: `path_allowlist_apply()` extended with a `bool allow_dot` argument to reject non-absolute paths (including single-dot paths) when needed. The helper is exported and documented in `setup.h` for use in `promisor-remote.c`. The existing `safe_directory_cb()` call site updated to pass `true` for backward compatibility.
  - Patch 4/5: `upload_pack_lazy_fetch_trusted()` function added to `upload-pack.c`, reading the `uploadpack.lazyFetchTrusted` configuration from protected files only (using `git_protected_config()`), normalizing the repository path with `real_pathdup()`, and delegating the allowlist check to `path_allowlist_apply()` with `allow_dot=false`. The function is exported in `upload-pack.h`.
  - Patch 5/5: Integration in `builtin/upload-pack.c` checks whether the environment variable was already set, and if not, relaxes the default `GIT_NO_LAZY_FETCH=1` to `0` when the repository is trusted. No new helper functions or on-disk format changes.
- New symbols: `lazy_fetch_objects()` (refactoring), `path_allowlist_apply()` (generalized allowlist helper, now with `allow_dot` argument), `upload_pack_lazy_fetch_trusted()` (configuration check), `uploadpack.lazyFetchTrusted` configuration variable.
- On-disk format: No changes.
- Test coverage: New test script (`t/t5710-promisor-remote-capability.sh`) validates the configuration and trust mechanism across four scenarios: (1) lazy fetching succeeds when the repository is trusted, (2) it fails when the repository is not trusted, (3) the configuration is ignored if set in the repository’s own config (not protected), and (4) an explicit `GIT_NO_LAZY_FETCH=1` overrides the trusted setting.
- Protocol support: Targets both protocol v0/v1 and v2.
- Backward compatibility: Default behavior unchanged (lazy fetching disabled by default); new configuration is opt-in.
