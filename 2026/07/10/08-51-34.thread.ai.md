Thread identity: Patch series introducing a `fromAccepted` option to `GIT_NO_LAZY_FETCH` to allow lazy fetching only from mutually agreed promisor remotes. Series version: initial (v1, with v2 promised). Originating author: Christian Couder.

Core problem or goal: Extend `GIT_NO_LAZY_FETCH` from a boolean (disable all lazy fetching) to support a `fromAccepted` mode, enabling lazy fetching only from promisor remotes that both the server advertises and the client accepts via the "promisor-remote" capability in protocol v2. This provides a security middle ground between full disablement and unrestricted lazy fetching, while acknowledging that the served repository itself may still be untrusted.

Current status: Under review (initial v1 posted; v2 promised). All three patches (1/3 refactoring, 2/3 enum conversion, 3/3 core functionality) available. No merge status reported; series is not in `seen`, `next`, or `master`. The series now faces a high-weight security objection from brian m. carlson that remains unresolved in substance, though Christian has responded with a security-focused rationale and committed to documentation improvements.

Key technical details:
- Files touched: promisor-remote subsystem (`promisor-remote.c`, `promisor-remote.h`), `setup.c`, documentation (`git-upload-pack.adoc`, `git.adoc`), new test script (`t/t5710-promisor-remote-capability.sh`).
- New behavior: `GIT_NO_LAZY_FETCH=fromAccepted` permits lazy fetching only from promisor remotes negotiated via the "promisor-remote" capability.
- On-disk format: No changes.
- New symbols: `LAZY_FETCH_FROM_ACCEPTED` enum value (added to `allow_lazy_fetch` in patch 3), `parse_allow_lazy_fetch_env()` function (replaces `git_env_bool()`), `lazy_fetch_objects()` helper (refactoring), one-time warning emitted when `fromAccepted` mode is active. `try_promisor_remotes()` returns `bool` (previously `int`).
- Test coverage: New test script (`t/t5710-promisor-remote-capability.sh`) validates `fromAccepted` behavior, promisor-remote capability negotiation, and rejection of invalid values.

Open questions and loose ends:
- Usability concern: Using an environment variable is acknowledged as suboptimal; a configuration variable (e.g., `upload-pack.allowLazyFetch`) is proposed for future work but deferred due to backward compatibility constraints.
- **Security objection (high weight)**: brian m. carlson argues that the series expands the attack surface by allowing more network-facing C code to execute in the context of an untrusted repository, weakening security guarantees for tooling outside Git's formal threat model. This objection is categorical and remains unresolved. Christian counters that `fromAccepted` is more restrictive than the existing `GIT_NO_LAZY_FETCH=0` (which disables all lazy-fetch protections) and does not change defaults, but acknowledges that the served repository itself may still be untrusted. He proposes future improvements (server-side trusted repository marking, operator-defined allow/deny rules, repository scanning tools) to address this, positioning the series as a pragmatic step forward rather than a final solution.
- Documentation: Christian commits to improving documentation in v2 to clarify security considerations.
- No substantive technical review feedback yet beyond the security objection.

Participant positions:
