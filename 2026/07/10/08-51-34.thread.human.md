This thread is about a five-patch series from Christian Couder that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side configuration variable, `uploadpack.lazyFetchTrusted`, to control lazy fetching securely. The goal is to let server operators explicitly mark repositories as trusted for lazy fetching, addressing security concerns about untrusted repositories triggering arbitrary code execution via hooks or configuration.

The series is now at version 2, with the first two patches (1/5 and 2/5) being uncontroversial refactorings—consolidating lazy-fetch logic and generalizing allowlist-checking code. The third patch (just summarized) continues this refactoring by adding an `allow_dot` parameter to `path_allowlist_apply()` to reject relative paths (like `.`) in the upcoming `uploadpack.lazyFetchTrusted` implementation. This change is mechanical and backward-compatible, preparing the ground for the core functionality without altering existing behavior.

The series remains under review, with no merge status reported. The main security objection from brian m. carlson is addressed by the server-side trust model, but the broader discussion is still open. The first three patches are positioned as ready for integration once the rest of the series is reviewed, but the series as a whole hasn’t yet reached a decision point. Key files touched include `promisor-remote.c`, `setup.c`, and documentation, with new behavior centered around the `uploadpack.lazyFetchTrusted` configuration.
