This thread is about a patch series from Christian Couder that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side configuration variable, `uploadpack.lazyFetchTrusted`, to let operators explicitly mark repositories as trusted for lazy fetching. The goal is to address security concerns about untrusted repositories triggering arbitrary code execution via lazy-fetch hooks or configuration, shifting trust decisions entirely to the server operator.

The series is now at its third patch (v1), with the first two patches refactoring lazy-fetching logic and generalizing Git’s `safe.directory` allowlist machinery into a reusable helper. Patch 3/5 prepares that helper for use in the promisor-remote subsystem by adding a `bool allow_dot` argument to reject non-absolute paths (like `.`), which would be ambiguous or unsafe in the context of promisor remotes. This is a small, uncontroversial refactoring that directly supports the series’ goal, though its value depends on the overall series being accepted.

The central discussion point remains brian m. carlson’s security objection to expanding lazy-fetching flexibility, which the series addresses by shifting trust decisions to the server operator. No substantive technical review has yet emerged beyond this objection, and the series remains under review, not yet queued in Junio’s integration branches. Christian positions the series as a pragmatic security improvement for corporate environments, deferring usability refinements to future work. The next patches will integrate the configuration variable and add test coverage.
