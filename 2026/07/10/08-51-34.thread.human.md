This thread is about a patch series from Christian Couder that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side configuration variable, `uploadpack.lazyFetchTrusted`. The goal is to let server operators explicitly mark repositories as trusted for lazy fetching, addressing security concerns about untrusted repositories triggering arbitrary code execution. The series is in its initial version (v1) and consists of six patches, with the first being a refactoring of the promisor-remote subsystem to prepare for the new feature.

The refactoring patch (1/5) introduces a `lazy_fetch_objects()` helper to streamline lazy-fetching logic, eliminating redundant checks and improving clarity. It’s a clean, behavior-preserving change that sets the stage for the rest of the series. The core of the series (patches 2–5) generalizes Git’s `safe.directory` allowlist machinery, implements the new configuration variable, and integrates it into `upload-pack.c`. When a repository is trusted, the server sets `GIT_NO_LAZY_FETCH=0` in the environment, permitting lazy fetching. The configuration is opt-in and read only from protected files, rejecting relative paths for security.

The main open question is whether the series satisfies brian m. carlson’s earlier security objection, which argued against expanding lazy-fetching flexibility while Git’s network code remains in C. Christian positions the series as a pragmatic improvement for corporate environments, shifting trust decisions to server operators, but the objection’s substance—expanded attack surface—may still apply. No substantive technical reviews have appeared yet beyond the security concern, though the refactoring patch is uncontroversial and ready for integration if the rest of the series holds up. The series remains under review, with no merge status reported.
