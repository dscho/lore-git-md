This thread is about a patch series that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side configuration variable, `uploadpack.lazyFetchTrusted`, to let operators mark repositories as safe for lazy fetching. The goal is to address security concerns about untrusted repositories triggering arbitrary code execution via lazy-fetch hooks or configuration.

The series is now at version 2, but the patches were misthreaded: each patch incorrectly replies to the v1 cover letter instead of the v2 cover letter. Junio C Hamano has confirmed the cause—using `--in-reply-to` with `git format-patch` instead of `git send-email`—and reiterated his request for a resend with correct threading (using `--no-chain-reply-to`). Christian Couder has acknowledged the issue and agreed to the resend, but it hasn’t happened yet. Until then, substantive review is on hold.

The technical approach mirrors Git’s `safe.directory` mechanism: `uploadpack.lazyFetchTrusted` is a protected configuration variable read only from server-side files, and relative paths (including `.`) are rejected. When the served repository is trusted, `upload-pack` sets `GIT_NO_LAZY_FETCH=0` in its environment, enabling lazy fetching. The series touches promisor-remote, setup, and upload-pack code, adds a new test script, and updates documentation. While brian m. carlson’s earlier security objection remains unresolved, the server-side trust model directly addresses it. No substantive reviews have been posted yet, but the refactoring and configuration changes appear uncontroversial.
