This is the second patch in a two-patch bugfix series (v3) targeting a quadratic performance regression in Git’s reftable backend. The patch removes the `suppress_deletions` flag from the merged iterator and makes it configurable via `struct reftable_stack_options`, allowing callers to control tombstone suppression at stack creation time. The core logic is in `refs/reftable-backend.c`, where tombstone handling is now performed explicitly at each call site after bounds checks, enabling early termination when tombstones exceed the relevant prefix or refname range. This change eliminates the O(n) per-call behavior in tombstone-heavy scenarios, reducing runtime from ~14s to ~0.2s in the perf test’s 8000-ref scenarios.

The patch touches three files: `refs/reftable-backend.c` (adding deletion checks to ref and log iteration paths), `reftable/reftable-stack.h` (adding the `suppress_deletions` field to `struct reftable_stack_options`), and `reftable/stack.c` (removing Git’s internal use of the flag while preserving libgit2’s current behavior). The on-disk format remains unchanged, and the fix is narrowly scoped to the reftable backend. All prior feedback from Patrick Steinhardt and others has been incorporated, including the API-compatibility refinement to support libgit2’s existing usage pattern.

Key symbols introduced or modified include the `suppress_deletions` field in `struct reftable_stack_options` and the explicit deletion checks in functions like `reftable_ref_iterator_advance()`, `reftable_be_for_each_reflog_ent()`, and `reftable_be_reflog_exists()`. The patch also updates log iteration paths to handle tombstones, which were previously suppressed by the merged iterator. The perf test (`p1401-ref-store-tombstones.sh`) introduced in the first patch measures the regression and fix, using separate repositories for each scenario to ensure isolation.

The series is well-motivated, addressing a real-world performance issue observed by brian m. carlson, and the design choices appear uncontroversial. The patch is ready for review and integration, with no open questions or loose ends remaining. Downstream users like libgit2 will need to update to use the new `reftable_stack_options` field in future versions, but the break is already inevitable due to libgit2’s use of pre-options-stack code.
