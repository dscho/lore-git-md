This is a three-patch feature series introducing a new `fromAccepted` option to the `GIT_NO_LAZY_FETCH` environment variable, allowing lazy fetching only from promisor remotes that are both advertised by the server and accepted by the client.

The series builds on recent work that added the "promisor-remote" capability to Git's protocol v2, enabling servers and clients to negotiate which promisor remotes can be safely used. Currently, `GIT_NO_LAZY_FETCH` is a boolean that disables lazy fetching entirely by default for security reasons. This series introduces a middle ground: when set to `fromAccepted`, lazy fetching is permitted only from mutually agreed-upon promisor remotes.

Patch 1 refactors the promisor-remote code to separate fetching logic from error handling and validation, which may also improve performance when multiple promisor remotes exist. Patch 2 transitions `GIT_NO_LAZY_FETCH` from a boolean to an enum, preparing the codebase for the new option. Patch 3 implements the `fromAccepted` option itself, leveraging the preparatory work in the previous patches.

The commit message acknowledges that using an environment variable for this feature is not ideal from a usability perspective and suggests that a configuration variable like `upload-pack.allowLazyFetch` would be preferable. However, the current approach is constrained by backward compatibility requirements, leaving the transition to a configuration variable for future work.

The series touches the promisor-remote subsystem, documentation (`git-upload-pack.adoc` and `git.adoc`), and adds a new test script (`t/t5710-promisor-remote-capability.sh`). CI tests have passed, indicating the changes integrate cleanly with the existing codebase. The implementation appears well-structured, with clear separation of concerns and thorough test coverage.
