This is the third patch in the `git replay --linearize` series, now in its seventh iteration and queued in `next`. Elijah Newren’s review raises a **substantive design concern** about how `--linearize` handles multiple branches.

The current implementation flattens all commits from every branch into a single linear history, regardless of whether merges are present. Elijah argues this violates the principle of least astonishment: if no merges exist, `--linearize` should behave identically to the default mode (replaying branches independently) or explicitly reject multiple positive refs, just as `--advance` and `--revert` do. The current behavior also introduces an arbitrary ordering between branches, determined by the revision walk rather than user input, which Elijah finds unpredictable and inconsistent with the rest of the `replay` command.

The review suggests two alternatives: either disallow multiple positive refs under `--linearize` (requiring users to invoke `git replay` separately for each branch), or implement a more complex branch-aware tracking system to maintain separate linearized histories for each branch. The simpler option—rejecting multiple refs—would preserve the fix for the single-branch merge-flattening regression while avoiding the ordering ambiguity.

The series remains technically complete and addresses all prior feedback, but this new objection challenges a core design choice. The ball is now in Toon Claes’s court to either defend the current behavior, adopt one of Elijah’s alternatives, or propose another solution. Until resolved, the objection could delay graduation from `next` to `master`.
