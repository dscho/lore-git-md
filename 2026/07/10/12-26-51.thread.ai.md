Subject: [PATCH v3 0/2] fetch: configurable submodule fetch errors
Series version: v3
Originating author: Paulius Zaleckas
Thread type: patch series

Core problem or goal
Allow users to configure whether `git fetch --recurse-submodules` should fail hard or merely warn when a submodule’s gitlink points to an OID that is not reachable from the submodule’s remote. The default (`fail`) preserves backwards compatibility; the new `warn` mode enables workflows where upstream topic branches are still in flux without disrupting the entire fetch.

Current status
Under review; v3 posted addressing feedback from the list. Junio C Hamano has raised a technical concern about the propagation of the `--submodule-errors` CLI override to child fetches, suggesting that the current implementation may silently revert to the config default in child processes when the CLI override is `fail`. This issue is specific to the second patch (user-facing controls) and does not affect the correctness fix in the first patch (submodule fetch error handling logic). No merge status change; the series remains under review.

Key technical details
- Files touched: `submodule.c`, `builtin/fetch.c`, `Documentation/config/fetch.txt`, `Documentation/fetch-options.txt`, `t/t5526-fetch-submodules.sh`
- New config key: `fetch.submoduleErrors` (values: `fail`, `warn`)
- New CLI option: `--submodule-errors=(fail|warn)`
- New behavior: when set to `warn`, submodule fetch errors are reported but do not abort the parent fetch
- Forwarding: the setting is propagated to child fetches (`--all`, `--multiple`, nested recursion), but the current implementation only pushes `--submodule-errors=warn` to the child’s argv when the config value is `SUBMODULE_ERRORS_WARN`, omitting the explicit `--submodule-errors=fail` when the CLI override is `fail`
- Error routing: all submodule fetch errors now flow through `record_fetch_error()` so they honor the new policy. The helper ensures errors are recorded only after both fetch phases (refs and OID-based retry) have failed, fixing a logic flaw where phase-1 failures could abort the fetch prematurely.
- Test coverage: new tests for warn mode, error reporting, and edge cases, including tests verifying that a failed submodule fetch is still reported even when the gitlinked commits are present locally, and that the setting is forwarded correctly with `--all`.

Open questions and loose ends
- **CLI override propagation**: Junio’s review identifies a potential inconsistency in how the `--submodule-errors=fail` CLI override is propagated to child fetches. The current implementation may silently revert to the config default in child processes, which could surprise users who expect the CLI setting to take precedence everywhere. This requires a fix to ensure the explicit CLI override is always propagated.
