Subject: [PATCH v3 0/2] fetch: configurable submodule fetch errors
Series version: v3
Originating author: Paulius Zaleckas
Thread type: patch series

Core problem or goal
Allow users to configure whether `git fetch --recurse-submodules` should fail hard or merely warn when a submodule’s gitlink points to an OID that is not reachable from the submodule’s remote. The default (`fail`) preserves backwards compatibility; the new `warn` mode enables workflows where upstream topic branches are still in flux without disrupting the entire fetch.

Current status
Under review; v3 posted addressing feedback from the list. Prior versions (v1–v2) were discussed but not merged. Patch 1/2 is a correctness fix that restructures submodule fetch error handling to defer error recording until after both fetch phases (refs and OID-based retry) complete, ensuring transient failures do not prematurely abort the fetch.

Key technical details
- Files touched: `submodule.c`, `builtin/fetch.c`, `Documentation/config/fetch.txt`, `Documentation/fetch-options.txt`, `t/t5526-fetch-submodules.sh`
- New config key: `fetch.submoduleErrors` (values: `fail`, `warn`)
- New CLI option: `--submodule-errors=(fail|warn)`
- New behavior: when set to `warn`, submodule fetch errors are reported but do not abort the parent fetch
- Forwarding: the setting is propagated to child fetches (`--all`, `--multiple`, nested recursion)
- Error routing: all submodule fetch errors now flow through `record_fetch_error()` so they honor the new policy. The helper ensures errors are recorded only after both fetch phases (refs and OID-based retry) have failed, fixing a logic flaw where phase-1 failures could abort the fetch prematurely.
- Test coverage: new tests for warn mode, error reporting, and edge cases, including a test verifying that a failed submodule fetch is still reported even when the gitlinked commits are present locally.
