Originating author: Paulius Zaleckas
Thread type: patch series

Core problem or goal
Allow users to configure whether `git fetch --recurse-submodules` should fail hard or merely warn when a submodule’s gitlink points to an OID that is not reachable from the submodule’s remote. The default (`fail`) preserves backwards compatibility; the new `warn` mode enables workflows where upstream topic branches are still in flux without disrupting the entire fetch.

Current status
Under review; v4 posted addressing Junio C Hamano’s technical concern about CLI override propagation. The fix ensures that an explicit `--submodule-errors=fail` CLI override is always propagated to child fetches, preventing silent reversion to the config default. No merge status change; the series remains under review.

Key technical details
- Files touched: `submodule.c`, `builtin/fetch.c`, `Documentation/config/fetch.txt`, `Documentation/fetch-options.txt`, `t/t5526-fetch-submodules.sh`
- New config key: `fetch.submoduleErrors` (values: `fail`, `warn`)
- New CLI option: `--submodule-errors=(fail|warn)`
- New behavior: when set to `warn`, submodule fetch errors are reported but do not abort the parent fetch
- Forwarding: the resolved value (whether from CLI or config) is now always propagated to child fetches (`--all`, `--multiple`, nested recursion) when it was set explicitly, preserving the user’s intent
- Error routing: all submodule fetch errors flow through `record_fetch_error()` so they honor the new policy; the helper ensures errors are recorded only after both fetch phases (refs and OID-based retry) have failed, fixing a logic flaw where phase-1 failures could abort the fetch prematurely
- Test coverage: new tests for warn mode, error reporting, CLI override propagation, and edge cases, including tests verifying that a failed submodule fetch is still reported even when the gitlinked commits are present locally, and that the setting is forwarded correctly with `--all`
