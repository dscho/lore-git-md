This is a **substantive review** of the `--linearize` feature in `git replay`, focusing on a **principle-of-least-astonishment violation** when multiple branches are replayed with `--linearize`. The review comes from Elijah Newren, a domain expert in Git's merge machinery, and targets the third patch in the v7 series (`[PATCH v7 3/3] replay: offer an option to linearize the commit topology`).

Elijah argues that the current implementation of `--linearize` behaves inconsistently and unpredictably when multiple positive refs (e.g., `topic1 topic2`) are provided. Specifically:
- Without `--linearize`, `git replay --onto main topic1 topic2` replays each branch independently, updating both refs to their respective replayed tips.
- With `--linearize`, the same command flattens all commits into a single linear history, concatenating the branches in an order determined by the revision walk (not the user's command-line order). This means both refs end up pointing to different commits along the *same* linear chain, which Elijah describes as surprising and inconsistent with the behavior of other `git replay` modes (`--advance` and `--revert`), which explicitly reject multiple positive refs to avoid this ambiguity.

The review challenges two claims in the commit message:
1. **"Only way to ensure predictable results"**: Elijah proposes two alternatives: (a) disallow multiple positive refs with `--linearize` (aligning with `--advance`/`--revert`), or (b) track a `last_commit` per branch to preserve branch independence during linearization.
2. **"Predictable"**: The current behavior fails both user expectations (order of branches is opaque) and consistency with other `git replay` commands (which avoid concatenation).

Elijah traces the root of the issue to the `base = last_commit` rule introduced in v5 to fix a regression where only one side of a linearized merge survived. While this rule works for single-branch cases, it unconditionally applies to multi-branch scenarios, reintroducing the "which branch first?" problem that `--advance` and `--revert` deliberately avoid. He suggests that disallowing multiple positive refs under `--linearize` would preserve the merge-flattening fix while sidestepping the ambiguity.

The review is **not a rejection** of the feature but a call to address the inconsistency. It does not propose a specific implementation change, instead outlining trade-offs (e.g., disallowing multiple refs vs. tracking per-branch state). The ball is now in Toon Claes's court to either:
- Justify the current behavior as intentional (e.g., by documenting the concatenation order explicitly),
- Restrict `--linearize` to single positive refs, or
- Implement a more complex solution (e.g., per-branch `last_commit` tracking).
