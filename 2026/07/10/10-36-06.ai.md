This is the first patch in the v3 series fixing a reftable backend performance regression. It adds a new perf test (`t/perf/p1401-ref-store-tombstones.sh`) to measure the quadratic slowdown in ref operations when many tombstones (deleted refs) are present.

The test covers two scenarios: first, recreating the same 8,000 refs after deleting them (which triggers the regression), and second, creating 8,000 *new* refs after deleting 8,000 differently-named ones (a worst-case scenario where tombstones sort after the new refs, forcing every creation to scan all tombstones). Each scenario runs in a fresh repository to ensure isolation. The test is narrowly scoped to the reftable backend and does not interact with other ref backends.

The test setup is straightforward: create 8,000 tags, delete them all (creating tombstones), then measure the time to recreate them. The asymmetric variant uses `old-` and `new-` prefixes to force tombstones to sort after the new refs, exposing the worst-case behavior. This patch is purely infrastructure for the series; the actual fix is in patch 2/2. The test is well-motivated and directly tied to the regression being addressed. No controversial design choices are evident, and the test appears ready for integration. The perf numbers it produces will be critical for validating the fix in the next patch.
