This is a **bugfix** targeting the sequencer and rebase machinery. It addresses a long-standing edge case in `git rebase --autosquash`: when a `fixup!` or `squash!` commit cancels out all changes in its target (e.g., reverting a previous commit), the resulting empty commit is not handled according to the `--empty` option. Instead, the rebase halts with an error, forcing users to manually drop the commit or adjust their workflow.

The patch teaches `is_index_unchanged()` and `allow_empty()` to recognize when an amended commit (like a `fixup!`) becomes empty relative to its *parent* (not HEAD), and to apply `--empty=drop`, `--empty=keep`, or `--empty=stop` as specified. When dropping, it moves HEAD back to the parent of the now-empty commit, ensuring the rewritten-commit list remains consistent for `--update-refs` and other consumers.

The motivation is practical: at Meta, the author maintains a fork of LLVM where internal patches are kept as single commits via `fixup!` autosquash. Retiring a patch currently requires manual interactive rebase surgery, but with this change, a revert-as-`fixup!` followed by `--autosquash --empty=drop` would cleanly remove both the original commit and its revert. The included tests cover all three `--empty` modes and both `fixup!` and `squash!` directives.

The patch is well-explained, with a clear commit message, thorough test coverage, and a conservative approach (it does not introduce a new `revert!` autosquash directive, leaving that for potential follow-up discussion). The code changes are focused and appear to handle edge cases (e.g., root commits) correctly. This looks like a solid fix for a real pain point in rebase workflows.
