Key points from the review:
1. **Design suggestion**: Phillip wonders if `--delete-merged` should accept a `<branch>` argument (like `--forked`) to limit deletion candidates, rather than relying solely on the `branch.<name>.deleteMerged` config opt-out. This is a **non-blocking enhancement idea**—the current implementation is functional and well-motivated, but the suggestion could improve usability for users who prefer not to configure per-branch opt-outs. Harald may choose to defer this to a follow-up patch.

2. **Test improvements**:
   - **Clarity**: Phillip suggests adding comments to explain helper functions (e.g., `merged_branch`) and renaming them for better readability (e.g., `create_merged_branch`). He also recommends documenting the expected outcomes in complex tests (e.g., the "keeps a chain of upstreams" test).
   - **Conciseness**: Several test patterns could be simplified:
     - Using `git checkout -b --track` to avoid manual `git branch --set-upstream-to` calls.
     - Replacing manual config checks with `git config --get-regexp` for upstream/remote settings.
     - Introducing a helper function (e.g., `check_branches`) to standardize `for-each-ref` comparisons.
   - **Redundancy**: A few unnecessary commands (e.g., `git fetch` after a push, `test_when_finished` alongside `setup_repo_for_delete_merged`) could be removed.
   - **Dry-run test**: A `--dry-run` test case appears prematurely in this patch (it belongs to patch 7/7), suggesting the series wasn’t tested incrementally. Phillip notes this but doesn’t treat it as a blocker.

3. **Implementation notes**:
   - **Config clearing**: Phillip confirms that ignoring errors when clearing upstream configs (a convenience feature) is acceptable.
   - **Merge-base checks**: The double-check of branch merges (once in `delete_merged_branches`, again in `delete_branches`) is noted as potentially expensive but necessary for now. A future flag could optimize this.
   - **Test numbering**: Phillip finds the reverse-numbered branch chain (`b3→b2→b1`) confusing and suggests numbering from the base (`b1→b2→b3`).

4. **No functional concerns**: The review **does not challenge** the core logic of the patch:
   - Stacked-branch protection (abort-and-clear) is **explicitly endorsed** as the correct design.
   - Safety checks (checked-out branches, missing upstreams, push divergence) are **uncontroversial**.
   - The `--forked` filter integration is **confirmed as sound**.
