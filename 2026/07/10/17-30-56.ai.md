This is the second patch in the v2 series fixing race conditions in Git's HTTP daemon test helpers. It targets `t/lib-httpd/http-429.sh`, a CGI script that rate-limits HTTP requests by returning 429 (Too Many Requests) to the first request and forwarding subsequent ones to `git-http-backend`. The original implementation used a non-atomic check-then-act pattern (`test -f` followed by `touch`) to manage state, creating a latent race condition where concurrent requests could both pass the check and incorrectly forward instead of rate-limiting. This patch replaces the pattern with an atomic `mkdir` operation, ensuring exactly one request is elected as the first and rate-limited.

The commit message and code comments now explicitly address Junio C Hamano's feedback from v1, clarifying that skipping state for the `"permanent"` case (which must return 429 to every request) is required for correctness, not just an optimization. The original implementation's create-then-remove pattern (`touch` followed by `rm -f`) left a race window where a concurrent `"permanent"` request could see the marker and be forwarded, defeating the requirement that every such request rate-limits. The new version avoids this by guarding the `mkdir` with a `!= permanent` check, ensuring no marker is ever created for `"permanent"` requests.

The patch is minimal and targeted, changing only the state management logic in `http-429.sh` without altering its external behavior or introducing new dependencies. There is no accompanying regression test because the race cannot be forced deterministically (the check and set are adjacent commands with no external synchronization point), making this a preventive fix. The atomic `mkdir` idiom is consistent with the series' broader approach and is documented in the third patch (`t/README`), which generalizes the pattern for other test helpers. This patch looks well-crafted and uncontroversial, addressing a real (if latent) issue with a clean, atomic solution.
