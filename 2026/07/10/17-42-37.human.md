This is a bugfix patch for `git rebase --autosquash` that addresses a long-standing edge case: when a `fixup!` or `squash!` commit cancels out all changes in its target (e.g., reverting a commit), the resulting empty commit is not handled according to the `--empty` option. Instead, the rebase halts with an error, forcing manual intervention. The patch makes `--empty=drop` (or `keep`/`stop`) work as expected in this scenario, allowing users to automate workflows like backing out a commit by reverting it as a `fixup!`.

The commit message is exceptionally clear, walking through the problem, the root cause (emptiness is checked against the wrong parent), and the solution (a new `amended_commit_is_empty()` helper that compares against the parent of HEAD). The real-world motivation—maintaining a fork of LLVM at Meta—is concrete and persuasive. The v2 changes, guided by Phillip Wood’s review, tighten the logic (e.g., no longer treating an already-empty target as a special case) and add thorough test coverage for edge cases like empty-placeholder commits.

The patch touches `sequencer.c` (the core rebase logic), updates the `git-rebase` man page to document the new behavior, and adds comprehensive tests to `t3415-rebase-autosquash.sh`. The implementation is careful: when `--empty=drop` applies, it moves HEAD back to the parent without recording the commit as rewritten, ensuring the post-rewrite machinery doesn’t see spurious entries.

This is a well-crafted, user-facing improvement that closes a gap in `--autosquash`’s handling of empty commits. The patch is self-contained, the tests are exhaustive, and the commit message leaves no ambiguity about what problem is being solved or why. For teams that rely on `fixup!`/`squash!` to manage patch series, this will eliminate a frustrating manual step. The change is unlikely to be controversial—it aligns existing `--empty` behavior with a natural extension of autosquash.
