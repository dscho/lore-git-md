Subject: Why does Git default to showing author date instead of committer date?
Series version: N/A (discussion thread, not a patch series)
Originating author: Omri Sarig
Thread type: design discussion / workflow question

Core problem or goal
The thread explores why Git’s porcelain commands (e.g., `git log`) default to displaying the *author date* rather than the *committer date*, and whether this choice is driven by specific workflows, historical artifact, or usability. Omri Sarig initiated the discussion, noting that in rebase-heavy workflows the committer date often reflects when a commit was introduced into the main branch, while the author date remains static. The goal is to evaluate whether the current default remains justified or should be adjusted to better serve modern workflows.

Current status
No decisions or agreements yet; the thread remains in open discussion. Jeff King (Peff) and Junio C Hamano have defended the current default, framing it as intentional and tied to Git’s mailing-list-based workflow, where the author date reflects when the patch was *sent* (not written), serving as a proxy for when the work became visible to others. Oswald Buddenhagen has proposed an alternative: defaulting to the *committer date* while retaining the *author name*, arguing this better reflects when a commit "started to matter to users." No consensus has emerged on whether to change the default, introduce a configuration option, or leave the behavior unchanged.

Key technical details
- Commands affected: `git log`, `git show`, and other porcelain displaying commit metadata.
- Symbols: `GIT_AUTHOR_DATE` vs. `GIT_COMMITTER_DATE` environment variables; `--pretty=format:` placeholders `%ad` (author date) and `%cd` (committer date).
- No on-disk format changes, new CLI options, or file modifications are proposed.
- The author date’s role in Git’s workflow: it reflects when the patch was shared (e.g., sent to the mailing list), not necessarily when the work was created.
- Buddenhagen’s proposal: introduce a new default format (e.g., "compact") that shows *author name* alongside *committer date*, possibly renaming the field label (e.g., `Stamp:` instead of `Date:`) to avoid confusion.

Open questions and loose ends
- Are there workflows (e.g., rebase-heavy, CI-driven, or monorepo) where the committer date is more useful than the author date, and would changing the default serve them better?
- Would changing the default break existing scripts, user expectations, or tooling (e.g., `git blame`, `git bisect`, `git rebase --committer-date-is-author-date`)?
- Is the current default sufficient for most users, or should Git provide a configuration option (e.g., `log.defaultDate=committer`) to allow users to choose?
- How do other VCS tools (e.g., Mercurial, Jujutsu) handle this distinction, and could Git learn from their approaches?
- Would Buddenhagen’s proposed "compact" format (author name + committer date) address usability concerns without introducing backward compatibility issues?
- What are the implications for porcelain output parsing if the default format changes (e.g., field renaming, date field interpretation)?

Participant positions
- **Jeff King (Peff)**: Argues the current default (author date) is intentional and aligns with Git’s mailing-list-based workflow, where the author date reflects when the work was originally done (or sent). No position on changing the default; focuses on explaining the rationale.
- **Junio C Hamano**: Reinforces Peff’s rationale, adding that the author date is typically set to when the patch was *sent* to the mailing list (not when it was written), making it a meaningful proxy for when the work became visible to others. No position on changing the default; provides historical context.
- **Oswald Buddenhagen**: Challenges the current rationale, arguing the committer date is more useful for most users exploring branch histories, as it reflects when the commit "started to matter to users." Proposes a compromise: defaulting to *author name* alongside *committer date*, possibly renaming the field label (e.g., `Stamp:`) to avoid confusion. Dismisses backward compatibility concerns for users parsing porcelain output without specifying a format, framing it as a self-inflicted issue.
