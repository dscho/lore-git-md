Thread identity
Subject: Why does Git default to showing author date instead of committer date?
Series version: N/A (discussion thread, not a patch series)
Originating author: Omri Sarig
Thread type: design discussion / workflow question

Core problem or goal
The thread explores why Git’s porcelain commands (e.g., `git log`) default to displaying the *author date* rather than the *committer date*, and whether this choice is driven by specific workflows or is a historical artifact. Omri notes that in rebase-heavy workflows, the committer date often reflects when a commit was introduced into the main branch, while the author date remains static.

Current status
No decisions or agreements yet; the thread remains in open discussion. Jeff King (Peff) and Junio C Hamano have provided rationale for the current default, framing it as intentional and tied to Git’s mailing-list-based workflow. Peff emphasized that the author date reflects when the work was originally done, while Junio clarified that in practice, the author date is typically set to when the patch was *sent* to the mailing list (not when it was written), making it a proxy for when the work became visible to others. No consensus has emerged on whether the default should change or how other workflows might be affected.

Key technical details
- Commands affected: `git log`, `git show`, and other porcelain displaying commit metadata.
- Symbols: `GIT_AUTHOR_DATE` vs. `GIT_COMMITTER_DATE` environment variables; `--pretty=format:` placeholders `%ad` (author date) and `%cd` (committer date).
- No on-disk format changes, new CLI options, or file modifications are proposed.
- The author date’s role in Git’s workflow: it reflects when the patch was shared (e.g., sent to the mailing list), not necessarily when the work was created.

Open questions and loose ends
- Are there workflows (e.g., rebase-heavy or CI-driven) where the committer date is more useful than the author date?
- Would changing the default break existing scripts, user expectations, or tooling (e.g., `git blame`, `git bisect`)?
- Is the current default sufficient for most users, or should Git provide a configuration option (e.g., `log.defaultDate=committer`) to allow users to choose?
- How do other VCS tools (e.g., Mercurial, Jujutsu) handle this distinction, and could Git learn from their approaches?

Participant positions
- **Jeff King (Peff)**: Argues the current default (author date) is intentional and aligns with Git’s mailing-list-based workflow, where the author date reflects when the work was originally done. No position on changing the default; focuses on explaining the rationale.
- **Junio C Hamano**: Reinforces Peff’s rationale, adding that the author date is typically set to when the patch was *sent* to the mailing list (not when it was written), making it a meaningful proxy for when the work became visible to others. No position on changing the default; provides historical context.
