This is the v3 cover letter for a two-patch bugfix series targeting a quadratic performance regression in the reftable backend. The series is now finalized and ready for review, addressing all prior feedback from Patrick Steinhardt and others.

The core issue remains a performance regression in ref-reading operations (e.g., `refs_verify_refnames_available()`, `reftable_backend_read_ref()`) when tombstones (deleted refs) are present. The merged iterator’s `suppress_deletions` flag forces a full scan of all tombstones before bounds checks can terminate iteration, making these operations O(n) per call in tombstone-heavy scenarios. The fix moves tombstone suppression logic from the merged iterator to the reftable backend’s call sites, where prefix and refname bounds are available, enabling early termination when tombstones exceed the relevant bound.

Key changes since v2: the `suppress_deletions` flag is now configurable via `struct reftable_stack_options` (defaulting to off), preserving libgit2’s current behavior while future-proofing the API. This addresses Patrick Steinhardt’s concern about downstream compatibility, as libgit2 can now control tombstone suppression at stack creation time. The perf test (`p1401-ref-store-tombstones.sh`) remains narrowly scoped to the reftable backend, using separate repositories for each scenario to ensure isolation. Performance improves dramatically: both test scenarios now run in ~0.2s (down from ~13s).

The series touches `refs/reftable-backend.c` (core logic), `reftable/stack.c` (removal of Git’s internal use of `suppress_deletions`), and `reftable/reftable-stack.h` (new `suppress_deletions` field in `struct reftable_stack_options`). The on-disk format is unchanged, and the fix is well-motivated, narrowly targeted, and addresses real-world performance issues observed by brian m. carlson. No controversial design choices are evident, and the series appears ready for integration.
