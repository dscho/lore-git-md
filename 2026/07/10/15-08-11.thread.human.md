This thread is a design discussion about why Git’s porcelain commands (like `git log`) default to showing the *author date* instead of the *committer date*. Omri Sarig started the conversation, noting that in rebase-heavy workflows, the committer date often better reflects when a commit was introduced into the main branch, while the author date remains static.

Jeff King (Peff) and Junio C Hamano have both weighed in to explain the rationale behind the current default. Peff framed it as intentional, tied to Git’s mailing-list-based workflow, where the author date represents when the work was originally done. Junio added nuance, clarifying that in Git’s workflow, the author date is typically set to when the patch was *sent* to the mailing list (not when it was written), making it a more meaningful proxy for when the work became visible to others. Neither has proposed changing the default, and the discussion remains open-ended.

Key questions still unanswered include whether rebase-heavy or CI-driven workflows would benefit from a different default, whether changing it would break existing scripts or tooling (like `git blame` or `git bisect`), and whether Git should introduce a configuration option (e.g., `log.defaultDate=committer`) to let users choose. The thread hasn’t yet explored how other version control systems handle this distinction or whether Git could learn from their approaches. For now, the focus is on understanding the historical and practical reasons for the current behavior.
