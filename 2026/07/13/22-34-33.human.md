This is a bugfix patch for the HTTP transport layer, specifically addressing a race condition in packfile URI downloads.

Since 2020, Git has supported fetching packfiles directly by URL, but the implementation reused the same temporary file path (`objects/pack/pack-<hash>.pack.temp`) for all downloads of the same pack. When two processes fetch the same pack into a shared object database, their concurrent writes can corrupt the temporary file. The patch switches packfile URI downloads to use the tempfile API, giving each download a unique temporary file (e.g., `objects/pack/tmp_pack_XXXXXX`). Ordinary dumb HTTP pack requests keep the deterministic path so they can resume partial downloads.

The change is motivated by real-world corruption observed when multiple Git processes fetch the same pack simultaneously. The trade-off is that packfile URI downloads can no longer be resumed by a later invocation, but the commit message argues this is acceptable since retries start fresh. The patch includes a new test that pauses one download mid-flight, starts a second download, and verifies both complete without corrupting the object database.

The implementation is clean: it adds a `tempfile` field to the `http_pack_request` struct, refactors the request-creation logic into a helper that takes a `resumable` flag, and updates the cleanup paths to handle both tempfile-backed and direct-file cases. The documentation is updated to remove misleading claims about the hash determining the temporary file name.
