This is a follow-up in the `post-worktree-add` / `post-worktree-remove` hook series. Domen Kožar and Phillip Wood clarify two key design points that were left open in the initial review.

First, they agree that `post-worktree-add` should run even if the earlier `post-checkout` hook fails. The worktree still exists, so tooling that tracks worktrees (e.g., AI-driven development environments) would otherwise miss it. The current implementation skips the hook when `post-checkout` fails, but both authors now prefer running it unconditionally.

Second, they discuss whether the hook should receive the worktree’s absolute directory and ID as arguments. Domen initially included them for symmetry with `post-worktree-remove` (which needs them because the worktree is gone), but Phillip questions their utility for `post-worktree-add` since the hook already runs inside the worktree. Domen counters that a shared hook script could use the same signature for both hooks, and Phillip concedes that differing argument counts might help the script distinguish which hook invoked it. The worktree ID is also useful for accessing a worktree’s local refs from another worktree, though this is a niche use case.

Phillip also raises a new idea: whether to add a `post-worktree-rename` hook so external tools can update their mappings. Domen does not respond to this in the email, leaving it as an open question for future discussion. The thread remains focused on refining the current series rather than expanding its scope.
