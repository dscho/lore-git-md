This thread is about a patch series from Taylor Blau introducing a `no-ref-delta` capability to Git’s pack protocol. The feature lets a receiver (`receive-pack`) instruct the sender (`send-pack`) to omit `REF_DELTA` entries from generated packs, which simplifies processing for systems that don’t want to build an object ID index upfront. The initial submission left the motivation unclear, but Taylor’s follow-up clarifies that this supports a write-through proxy that spools packs byte-for-byte and replays them upstream before allowing local ref updates. The proxy avoids indexing the pack upfront, relying instead on a single forward pass, and `REF_DELTA` entries would complicate this design.

Jeff King (Peff) raised fundamental concerns in his review, questioning the practical value of the feature and highlighting potential issues with thin packs and safety. Taylor’s response addresses these points: the implementation already advertises `no-thin`, ensuring `send-pack` can’t produce a thin pack when `no-ref-delta` is active, and any unexpected `REF_DELTA` entries would cause the receiver to reject the pack before updating refs. The series also ensures consistent behavior for bitmap pack reuse, though this was a correctness safeguard rather than part of the core motivation.

The thread is now better grounded in a real-world use case, but some questions remain open. The fallback behavior for unexpected `REF_DELTA` entries is rejection, but it’s unclear how the receiver might recover or retry. There’s also ongoing discussion about whether the design aligns with Git’s broader protocol principles and whether rejecting packs is a sufficient safeguard. The series is still under review, with no substantive changes yet, but the motivation is no longer in doubt.
