This thread is about Taylor Blau’s patch series introducing a `no-ref-delta` capability to Git’s pack protocol, which would allow receivers (like a write-through proxy) to request packs containing only `OFS_DELTA` entries. The goal is to simplify asynchronous pack processing by avoiding the need for object ID lookups, which complicate memory management and risk pipeline stalls in the proxy’s offset-based reconstruction design.

The series is still under review, with v1 posted but no consensus yet on the optimal design. Jeff King (Peff) has been the primary reviewer, initially raising fundamental concerns about the motivation and safety of the feature. While Taylor’s responses addressed some of these, Peff’s latest follow-up reveals a deeper engagement with the technical trade-offs. He now acknowledges that `OFS_DELTA`-only packs could enable meaningful optimizations for the proxy’s asynchronous delta resolution, particularly around worker coordination and cache locality. However, he remains hesitant about merging a protocol capability that Git itself doesn’t use, citing long-term maintainability risks and the potential for the feature to become a mismatch for future optimizations. Peff’s earlier suggestion of a narrower “bases-before-deltas” capability—enforcing Git’s default ordering to prevent worst-case stalls while preserving broader compatibility—remains on the table as a potential middle ground.

The key technical details include a new `--no-ref-delta` option in `git pack-objects`, modifications to delta reuse logic, and test coverage verifying `OFS_DELTA`-only packs. The series touches the pack-objects subsystem and protocol capabilities but makes no on-disk format changes. Open questions revolve around whether `no-ref-delta` is the right solution or if a more permissive alternative would suffice, how to handle unexpected `REF_DELTA` entries, and whether the feature’s narrow applicability justifies its inclusion. Taylor argues the stricter design is necessary for the proxy’s use case, while Peff leans toward a more general solution. No other participants have weighed in yet, and the discussion remains focused on these design trade-offs.
