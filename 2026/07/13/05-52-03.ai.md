This is the v2 cover letter for Patrick Steinhardt’s 12-patch series **"Make ODB optimizations pluggable"**, part of the ongoing ODB abstraction effort. The series refactors Git’s object housekeeping (repacking, geometric repacking, auto-gc) into a modular system, allowing different ODB backends to implement their own optimization strategies. This v2 addresses feedback from Junio C Hamano on the v1 series, primarily by making the test suite more robust.

Key changes in v2:
- **Test robustness**: The tests in `t/t7900-maintenance.sh` now avoid checking for exact command invocations (e.g., `git repack --geometric=2`) and instead verify that the expected maintenance *tasks* (e.g., `geometric-repack`) were executed. This replaces the brittle `GIT_TRACE2_EVENT`-based checks from v1 with a new helper, `test_maintenance_tasks`, which parses trace2 output for task names rather than command-line arguments. The change is purely internal to the test suite and does not affect functionality.
- **Patch count**: The series grew from 11 to 12 patches, with the new first patch (`t7900: simplify how we check for maintenance tasks`) introducing the `test_maintenance_tasks` helper and updating all existing tests to use it. The remaining patches are mechanically identical to v1, with only minor adjustments to test assertions.

The series continues to target the same goal: extracting ODB optimization logic from `builtin/gc.c` into a pluggable interface. The final patch relocates the `odb_optimize()` and `odb_optimize_required()` functions into `odb/source-files.c`, exposing them via vtable callbacks in the ODB source interface. The net effect is a 466-line reduction in `builtin/gc.c` and a 470-line addition to `odb/source-files.c`, with no behavioral changes.

The design remains uncontroversial, with Junio’s v1 feedback on patches 1–3 already addressed. The only open point from v1 (replacing `GIT_TRACE2_EVENT` with trace2 regions) was resolved by this v2’s test refactoring. The series is now focused on mechanical correctness and test reliability, with no known objections to the core design. It is a prerequisite for future ODB backends (e.g., reftable) to implement their own housekeeping logic.
