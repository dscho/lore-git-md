This is a **substantive discussion** about the `--linearize` option in `git replay`, specifically whether it should allow multiple positive refs (branches) or reject them to avoid ambiguity. The email is a reply from Junio C Hamano to Elijah Newren’s critique of the current behavior, which flattens multiple branches into a single linear history with an opaque order.

Junio pushes back on Elijah’s proposal to disallow multiple positive refs with `--linearize`. He argues that the unpredictability of branch ordering is inherent to linearization itself, even for single-branch cases containing merges. For example, if a branch merges two independent lines of development, linearizing it will still require choosing an arbitrary order for those lines. Junio suggests that this ambiguity is not a bug but a feature in cases where the merge order is inconsequential (e.g., octopus merges of independent branches). He interprets the current behavior as an "escape hatch" for users who want to avoid manual ordering decisions, rather than a design flaw.

The email does not resolve the debate but reframes it: Junio sees the current behavior as a reasonable default for cases where order doesn’t matter, while Elijah views it as a violation of user expectations and consistency with other `git replay` modes. The discussion now hinges on whether the ambiguity is acceptable or whether `--linearize` should enforce stricter constraints (like `--advance` and `--revert` do). No code changes are proposed here—this is purely a design philosophy exchange.
