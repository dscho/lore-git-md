Subject: [PATCH 0/4] pack-objects: introduce `no-ref-delta` capability
Series version: v1
Originating author: Taylor Blau

Core problem or goal
Add a `no-ref-delta` capability to Git’s pack protocol. The sender (`send-pack`) can be instructed by the receiver (`receive-pack`) to omit `REF_DELTA` entries from the generated pack, simplifying pack processing for receivers that do not want to build an object ID index upfront. The motivation and practical use case for this optimization remain unclear; Jeff King’s review questions whether avoiding an object ID index is a realistic or safe goal.

Key technical details
- New `--no-ref-delta` option in `git pack-objects`.
- New protocol capability `no-ref-delta` wired into `send-pack` and `receive-pack`.
- Test helper `test-tool pack-deltas` added to inspect delta representations.
- Subsystems touched: pack-objects, protocol capabilities, test infrastructure.
- Delta reuse logic modified to avoid copying `REF_DELTA` entries when the capability is active; bitmap pack reuse is re-enabled only when safe.
- No on-disk format changes; behavior is opt-in via protocol negotiation.
- Thin packs may introduce `REF_DELTA` entries on the server side after pack completion, creating a potential interoperability issue if the receiver requests `no-ref-delta` but receives a thin pack anyway.
- Git’s `receive-pack` does not currently support the `no-thin` capability, and even if it did, not all clients might respect it.

Open questions and loose ends
- **Motivation and use case**: Why would a receiver want to avoid building an object ID index upfront? Is this part of a larger system (e.g., a custom `receive-pack` implementation) or an optimization for a specific workflow? The cover letter and commit messages do not provide sufficient context.
- **Thin packs and interoperability**: What should the server do if it requests `no-ref-delta` but receives a thin pack containing `REF_DELTA` entries? Should `no-thin` be enforced alongside `no-ref-delta`?
- **Safety**: Updating refs without indexing the pack’s contents could allow a malicious client to corrupt the repository. Is the `no-ref-delta` capability safe in its current form, or does it require additional safeguards?
- **Fallback behavior**: How should the receiver handle unexpected `REF_DELTA` entries when the capability is active?
- **Delta reuse edge cases**: Reviewers may still scrutinize the logic around bitmap pack reuse and other edge cases.
