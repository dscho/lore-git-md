Subject: [PATCH 0/4] pack-objects: introduce `no-ref-delta` capability
Series version: v1
Originating author: Taylor Blau
Thread type: patch series

Core problem or goal
Add a `no-ref-delta` capability to Git’s pack protocol, enabling receivers (e.g., a write-through proxy) to request packs containing only `OFS_DELTA` entries. This allows the receiver to avoid building an object ID index upfront, simplifying asynchronous pack processing. The use case is a write-through proxy that spools incoming packs byte-for-byte and replays them upstream before allowing local ref updates; `REF_DELTA` entries would complicate this design by requiring an OID lookup or a second pass, and their worst-case resolution order (a long delta chain depending on a late base) risks pipeline stalls.

Key technical details
- New `--no-ref-delta` option in `git pack-objects` and corresponding protocol capability.
- Subsystems touched: pack-objects, protocol capabilities, test infrastructure (`test-tool pack-deltas`).
- Delta reuse logic modified to avoid copying `REF_DELTA` entries when the capability is active; bitmap pack reuse is re-enabled only when safe.
- Thin packs are already handled via `no-thin` advertisement; `send-pack` honoring `no-ref-delta` cannot produce a thin pack (external bases would require `REF_DELTA`).
- No on-disk format changes; behavior is opt-in via protocol negotiation.
- Test coverage includes a helper to inspect delta representations and verify `OFS_DELTA`-only packs.
- The write-through proxy’s asynchronous indexer relies on offset-based addressing and processes packs in a single forward pass; `REF_DELTA` entries would require random access or buffering, complicating memory management.
- **New detail**: `OFS_DELTA` enables simpler worker coordination and cache locality in the proxy’s asynchronous delta resolution pipeline by allowing upfront base offset determination. However, even `OFS_DELTA` does not fully solve the problem of predicting intermediate object reuse, as delta families may not be grouped contiguously in the pack.

Open questions and loose ends
- **Design optimality**: Is `no-ref-delta` the right solution, or would a narrower “bases-before-deltas” capability (enforcing Git’s default ordering) suffice to prevent worst-case pipeline stalls while preserving broader protocol compatibility? Taylor argues the stricter design is justified by the proxy’s offset-based reconstruction needs, while Peff suggests the more permissive approach could achieve similar performance goals with less disruption.
- **Fallback behavior**: How should the receiver handle unexpected `REF_DELTA` entries when the capability is active? The current implementation rejects the pack, but is this sufficient, or should there be a retry mechanism or more graceful degradation?
- **Safety and protocol alignment**: Does rejecting packs with unexpected `REF_DELTA` entries align with Git’s broader protocol principles (e.g., resilience to malformed input), or should the design prioritize robustness over strict enforcement?
- **Niche optimization**: The feature is grounded in a real-world use case (write-through proxy), but its applicability remains narrow. Peff questions whether this justifies inclusion, given the risk of long-term maintainability issues and the feature becoming a mismatch for future optimizations. He suggests the proxy’s optimizations might be more compelling if they were also applicable to Git’s native receiving code, but no concrete path for that integration has been proposed.
- **Parallel delta resolution**: Even with `OFS_DELTA`, the proxy cannot fully predict which intermediate objects will be reused later in the pack, as delta families may not be grouped contiguously. This limits the effectiveness of some optimizations.
