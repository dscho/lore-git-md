This is a **design discussion** in the final stages of Harald Nordgren’s `--delete-merged` series, focusing on a refinement to the `--forked` filter’s logic. Harald acknowledges Phillip Wood’s proposal to improve how the filter distinguishes true "forked" branches from long-lived branches like `main`, `next`, or `seen` when `remote.pushDefault` is set. The current implementation misclassifies branches lacking an explicit `branch.<name>.pushRemote` as forked if `remote.pushDefault` points elsewhere, which is unintuitive for users.

Phillip’s alternative would simulate a push operation: apply the push refspec to the branch name, then the fetch refspec to the result, and only treat the branch as forked if the final ref does *not* match its upstream. This would protect branches that, when pushed, would update their own upstream (e.g., `main` pushing to `origin/main`), while still catching true forks. Harald agrees the idea is sound and plans to implement it, but asks whether Phillip’s review of the rest of the series is complete so he can prepare a final version.
