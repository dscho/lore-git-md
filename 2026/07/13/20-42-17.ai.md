This is a **post-merge discussion** continuing the thread on patch presentation style and review ergonomics. Junio C Hamano responds to Kristofer Karlsson’s proposal for tooling improvements to selectively expand context in patch emails.

Junio pushes back on the need for new tooling, demonstrating that the existing workflow already supports the desired outcome: a reviewer can easily see both the code fix and its corresponding test in a single atomic commit, and can also verify the pre-fix behavior by temporarily reverting the code changes while keeping the test. He provides a concrete command (`git show ':!t/' | git apply -R && make test`) to show how reviewers can isolate the test and observe the bug without requiring the author to split the test and fix into separate commits. His concern is that artificially expanding context (or splitting commits) increases the risk of merge conflicts and complicates the review process without adding value.

The discussion remains exploratory and non-technical; no code changes or project guidance are proposed. Junio’s response reinforces his earlier stance that the project’s existing tooling is sufficient, and that the trade-off between atomic commits and reviewer clarity is best addressed by reviewer-side tooling rather than author-side changes.
