This is a **substantive design discussion** in the final v18 thread of Harald Nordgren’s `--delete-merged` series, focusing on a subtle edge case in the `--forked` filter’s behavior. Phillip Wood proposes a refined heuristic to better distinguish "forked" branches from long-lived branches like `main`, `next`, and `seen` when `remote.pushDefault` is set.

The current implementation treats any branch whose upstream is not its push target as "forked" (and thus eligible for deletion). This misclassifies branches that lack an explicit `branch.<name>.pushRemote` when `remote.pushDefault` points elsewhere—common in test environments and some workflows. Phillip’s alternative would simulate a push operation: apply the push refspec to the branch name, then the fetch refspec to the result, and only treat the branch as forked if the final ref does *not* match its upstream. This would protect branches that, when pushed, would update their own upstream (e.g., `main` pushing to `origin/main`), while still catching true forks.

The proposal is **technical and forward-looking**, not a blocker for v18. It targets a known limitation (documented in the thread summary) and could be implemented later as a follow-up. No code changes are requested here; this is purely conceptual.
