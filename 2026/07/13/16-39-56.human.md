This is a **design discussion** in the final stages of Harald Nordgren’s `git branch --delete-merged` series (v18, patch 5/7). Phillip Wood proposes a refined approach to the edge case where branches without an explicit `branch.<name>.pushRemote` may be misclassified as "forked" when `remote.pushDefault` is set (e.g., in the test environment). Currently, the feature protects branches where `branch@{push} == branch@{upstream}`, but this misses cases like `next` or `seen` that are not the default branch but are still long-lived and pushed to a different remote.

Phillip’s suggestion: instead of comparing push and upstream refs directly, apply the push refspec to the branch name, then apply the fetch refspec to the result, and check if this matches the upstream branch name. This would protect any branch that, when pushed, would update its own upstream — a more robust heuristic for identifying "primary" branches that should not be auto-deleted. The idea is technically sound but not yet implemented; it’s a **forward-looking refinement** rather than a blocker for the current series, which remains ready for merging once the agreed mechanical fixes (flags cleanup and `--dry-run --quiet` rejection) are applied.

The discussion is narrow and targeted: it addresses a known limitation (documented in the thread summary) without challenging the core logic or safety checks. If adopted in a future iteration, this change would further reduce false positives in forked-branch detection, but for now, the series is complete and the edge case is acknowledged as a trade-off.
