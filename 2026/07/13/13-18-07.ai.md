This is a **design-level reply in the ongoing `--autosquash` bugfix thread**, continuing the discussion about how a future `revert!` (or `drop!`) autosquash directive should be implemented. Phillip Wood responds to Yuxuan Chen’s argument that a `revert!` commit should carry the inverse patch (like `git revert`) rather than being an empty marker.

Phillip acknowledges Yuxuan’s point about semantic clarity but proposes a middle ground: a new `git revert --drop` option (or similar) that would create a commit containing the inverse patch *and* a `drop!` message. During `git rebase --autosquash`, the sequencer would then replace the target commit’s `pick` with `drop` and discard the `drop!` commit itself. This approach avoids conflicts during the rebase (since the inverse patch is never applied) while still reflecting the intended removal in the repository state before the rebase runs. He cites an open GitGitGadget issue as prior art for this idea.

The trade-off remains unresolved: Yuxuan prioritizes consistency with `git revert` (and accepts conflicts as meaningful), while Phillip prioritizes conflict avoidance. The discussion now has a concrete proposal on the table (`git revert --drop`), but no consensus has emerged. The thread is still focused on design rather than code; the original `--autosquash` bugfix patch (addressing `fixup!`/`squash!` emptiness) is unaffected by this exchange.
