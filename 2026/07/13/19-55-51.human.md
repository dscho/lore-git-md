This is a post-merge discussion about **review ergonomics** in the Git project, specifically how to balance atomic commits (demonstrating a bug before fixing it) with the practical challenges of reviewing patches on the mailing list.

Kristofer Karlsson weighs in on the ongoing debate between Junio C Hamano and Taylor Blau about whether to split failing tests and their fixes into separate commits. He acknowledges the value of atomic commits—showing the bug exists before fixing it—but also recognizes Junio’s concern that reviewers on the mailing list may lack sufficient context when reading patch emails, especially for complex test setups. Kristofer suggests a middle ground: **tooling improvements** that would allow authors to selectively expand context in patch emails for critical sections (like test bodies) while preserving atomic commits in the repository. He notes that `git apply` already handles extra context lines, so the missing piece is either a more granular `-W` option in `git format-patch` or a post-processing tool to expand context before sending. While he doesn’t propose an immediate solution, he hints at future experimentation if he encounters similar scenarios.

The discussion remains exploratory and non-blocking, with no code changes or policy proposals on the table. It reflects broader tensions in the project between ideal patch structure and the realities of a high-volume mailing list workflow.
