This thread is a bugfix series from Ted Nyman addressing race conditions in Git's HTTP transport when multiple processes concurrently fetch the same packfile URI or dumb HTTP pack. The v2 series, now under review, fixes these races while preserving resumable downloads—a key improvement over v1, which had abandoned resumability for packfile URIs.

The first patch (previously summarized) introduced deterministic staging paths and read-write mode without append to handle concurrent downloads safely. The second patch, just posted, focuses on `fetch-pack` and its interaction with `index-pack`. It ensures `fetch-pack` correctly handles both `"keep<TAB><hash>"` and `"pack<TAB><hash>"` output from `http-fetch`, validates the pack hash against the advertised hash, and only registers a keep lockfile when the current process created it. The patch includes a regression test for pre-existing `.keep` files and adopts Jeff King’s suggested `strbuf` refactor for clarity.

Key participants include Junio C Hamano, who was skeptical of v1’s trade-offs but should find v2’s resumability preservation more palatable; Taylor Blau, who reviewed v1 and suggested minor improvements; and Jeff King, whose feedback directly shaped v2’s design. The series touches `http.c`, `fetch-pack.c`, and documentation, with new tests in `t/t5550-http-fetch-dumb.sh` and `t/t5702-protocol-v2.sh`. The only remaining loose end is a minor mechanical cleanup in `release_http_pack_request()`.

The v2 series appears ready for serious review, with no major objections or open design questions. If the current momentum holds, it should land smoothly.
