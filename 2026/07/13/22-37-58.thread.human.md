This thread is a bugfix series from Ted Nyman addressing race conditions in Git's HTTP transport when multiple processes concurrently fetch the same packfile URI. The races can corrupt temporary pack files or cause resume requests to fail. The series consists of two patches: the first modifies the HTTP layer to use unique temporary files for each packfile URI download, while the second makes `fetch-pack` accept both `"keep<TAB><hash>"` and `"pack<TAB><hash>"` output from `index-pack` to handle concurrent `.keep` file creation.

The initial design prioritized correctness and simplicity by avoiding cross-process coordination, but this approach abandons resumable downloads for packfile URIs, creating an inconsistency with dumb HTTP. Junio C Hamano has now weighed in, expressing skepticism about this trade-off, as resumability is a key goal of the packfile URI feature. While he doesn’t insist on coordination logic for this series, his feedback questions whether the current approach is acceptable. Jeff King (Peff) had earlier proposed alternatives to preserve resumption, such as using write-only file descriptors or piping downloads directly to `index-pack --stdin`, and raised concerns about the inconsistency between dumb HTTP and packfile URIs. Taylor Blau and Ted Nyman have defended the current design as the simplest fix for the immediate issue, deferring efficiency improvements to a follow-up.

The series is under active review, with most technical feedback focused on Patch 1. Mechanical cleanups, such as removing a redundant `NULL` assignment in `release_http_pack_request()` and adopting Peff’s `strbuf` refactor for Patch 2, are non-blocking but would improve maintainability. The key open question is whether the series will proceed as-is or require a revised design to preserve resumable downloads. No merge status has been indicated yet.
