This is a bugfix series targeting the packfile URI download mechanism in Git’s HTTP transport. The two patches address race conditions that can corrupt temporary packfiles or cause spurious failures when multiple Git processes fetch the same packfile URI into a shared object database.

The first patch changes how direct packfile URI downloads stage their temporary files. Instead of using a fixed path (`objects/pack/pack-<hash>.pack.temp`), each download now writes to a unique temporary file, preventing concurrent appends from corrupting the pack. The commit message clarifies that this change applies only to packfile URI downloads; ordinary dumb HTTP pack requests retain their existing resumable staging behavior, so a retry of a failed packfile URI download starts fresh rather than attempting to resume.

The second patch handles a related race around `.keep` files. When one process has already created the `.keep` file for a pack, `index-pack` reports success with the line `pack<TAB><hash>` instead of `keep<TAB><hash>`. The patch updates `fetch-pack` to accept either form as valid and ensures that only `.keep` files created by the current process are removed, avoiding interference with concurrent fetches.

Both patches include regression tests: the first adds a test to `t5550-http-fetch-dumb.sh` that verifies concurrent downloads do not corrupt the temporary pack, and the second adds a test to `t5702-protocol-v2.sh` that checks the `.keep` race is handled correctly.

The series touches the HTTP transport layer (`http.c`, `http.h`), the fetch-pack plumbing (`fetch-pack.c`), and the `git-http-fetch` documentation. The changes are narrowly scoped to the packfile URI code path and do not affect other HTTP fetch modes or the on-disk format. The commit messages are clear and the test coverage is thorough, suggesting the patches are well-prepared and address real, observed issues.
