Thread identity: Bugfix series for packfile URI download race conditions in Git's HTTP transport. Series version: initial (reroll planned). Originating author: Ted Nyman. Thread type: patch series (bugfix).

Core problem or goal: Fix race conditions in Git's HTTP transport when multiple processes concurrently fetch the same packfile URI into a single object database. The races can corrupt temporary pack files or cause resume requests to fail at EOF. The series targets the packfile URI feature and now also acknowledges a similar concurrency vulnerability in dumb HTTP, with a planned unified solution for both.

Current status: Initial submission under review; reroll planned. No prior versions. No merge status indicated. Changes in initial version:
- Patch 1: Modified HTTP layer to use unique temporary files for each direct packfile URI download, preserving resumable staging for ordinary dumb HTTP pack requests. The design prioritized correctness and simplicity by avoiding cross-process coordination, but this abandoned resumable downloads for packfile URIs, creating an inconsistency with dumb HTTP.
- Patch 2: Made `fetch-pack` accept both `"keep<TAB><hash>"` and `"pack<TAB><hash>"` output from `index-pack` when processing packfile URIs, addressing a race where a concurrent fetch may have already created the `.keep` file. The planned reroll will adopt Peff’s suggested `strbuf` refactor (using `strbuf_getwholeline_fd()` or equivalent) to improve clarity and maintainability when handling extra lines emitted by `index-pack` under `transfer.fsckObjects`, and will correct the `--index-pack-args` documentation typo.

Key technical details:
- Files touched: `http.c`, `fetch-pack.c`, documentation.
- New symbols: None (behavioral changes only).
- Test coverage: New regression tests in `t/t5550-http-fetch-dumb.sh` and `t/t5702-protocol-v2.sh`, explicitly addressing the tempfile and `.keep` file races.
- Subsystem: HTTP transport, packfile URI feature, dumb HTTP.
- On-disk format: No changes.
- Old vs. new behavior: The initial design used unique tempfiles for packfile URIs, preventing corruption but abandoning resumable downloads; `.keep` file handling was made more tolerant of concurrent processes. The planned reroll will preserve predictable partial-pack paths while preventing concurrent corruption, address handoff scenarios and stale-file cleanup for both packfile URIs and dumb HTTP, and include mechanical improvements to `fetch-pack` parsing logic.
- Design rationale: The initial design avoided cross-process coordination to prioritize correctness and simplicity, but this trade-off is now recognized as premature. The reroll will aim to balance correctness, coordination complexity, and resumability, with a unified solution for both packfile URIs and dumb HTTP.

Open questions and loose ends:
- How handoffs (one process taking over a stalled download) and stale-file cleanup (leftover `.pack.temp` files from crashed processes) will be handled in the reroll.
- What coordination mechanism (e.g., lockfiles, Peff’s write-only file descriptor approach, or piping to `index-pack --stdin`) will be used for the unified solution covering both packfile URIs and dumb HTTP.
- Mechanical cleanup in `release_http_pack_request()`: whether to drop the redundant `preq->packfile = NULL` assignment or restructure the conditional with a comment to clarify ownership semantics.
