Thread identity: Bugfix series for packfile URI download race conditions in Git's HTTP transport. Series version: initial (no prior versions mentioned). Originating author: Ted Nyman. Thread type: patch series (bugfix).

Core problem or goal: Fix race conditions in Git's HTTP transport when multiple processes concurrently fetch the same packfile URI into a single object database. The races can corrupt temporary pack files or cause resume requests to fail at EOF. The series targets the packfile URI feature, which allows servers to offload large packfiles to external storage.

Current status: Initial submission under review. No prior versions. No merge status indicated. Changes:
- Patch 1: Modifies HTTP layer to use unique temporary files for each direct packfile URI download, preserving resumable staging for ordinary dumb HTTP pack requests. The design prioritizes correctness and simplicity by avoiding cross-process coordination, though Junio C Hamano has raised concerns about redundant downloads when multiple processes fetch the same packfile concurrently.
- Patch 2: Handles a race condition with `.keep` files by making `fetch-pack` accept both success message forms from `index-pack` and only remove keep files created by the current process.

Key technical details:
- Files touched: `http.c`, `fetch-pack.c`, documentation.
- New symbols: None (behavioral changes only).
- Test coverage: New regression tests in `t/t5550-http-fetch-dumb.sh` and `t/t5702-protocol-v2.sh`, explicitly addressing the tempfile and `.keep` file races.
- Subsystem: HTTP transport, packfile URI feature.
- On-disk format: No changes.
- Old vs. new behavior: Concurrent packfile URI downloads now use unique tempfiles, preventing corruption; `.keep` file handling is more tolerant of concurrent processes.
- Design rationale: Ted Nyman argues that unique tempfiles avoid the complexity of cross-process coordination (e.g., detecting in-progress downloads, handling handoffs, or implementing timeouts), which would be required for a coordination-based approach. The current design preserves the existing "download, index, then install" workflow for each process.

Open questions and loose ends:
- Whether the simplicity of unique tempfiles is preferable to the efficiency of coordinated downloads. Ted suggests deferring the coordination logic to a follow-up unless Junio insists it is necessary for the fix.
- The feasibility of reliably distinguishing between an in-progress download and a leftover `.pack.temp` file from a crashed process, which would be required for a coordination mechanism.
