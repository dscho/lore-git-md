Thread identity: Bugfix series for packfile URI download race conditions in Git's HTTP transport. Series version: initial (no prior versions mentioned). Originating author: Ted Nyman. Thread type: patch series (bugfix).

Core problem or goal: Fix race conditions in Git's HTTP transport when multiple processes concurrently fetch the same packfile URI into a single object database. The races can corrupt temporary pack files or cause resume requests to fail at EOF. The series targets the packfile URI feature, which allows servers to offload large packfiles to external storage.

Current status: Initial submission under review. No prior versions. No merge status indicated. Changes:
- Patch 1: Modifies HTTP layer to use unique temporary files for each direct packfile URI download, preserving resumable staging for ordinary dumb HTTP pack requests. The design prioritizes correctness and simplicity by avoiding cross-process coordination. Junio C Hamano and Jeff King (Peff) have both expressed concerns about the abandonment of resumable downloads for packfile URIs, with Junio emphasizing that resumability is a major goal of the feature and Peff suggesting alternatives to preserve it (e.g., lockfile-style coordination, write-only file descriptors without O_APPEND, or piping to `index-pack --stdin`). Ted Nyman and Taylor Blau argue that the current approach is the correct trade-off for the immediate bugfix, deferring coordination logic to a follow-up. Peff’s latest review proposes an alternative: keep the deterministic path but open the file in write-only mode (without O_APPEND) using low-level file descriptors, avoiding corruption from concurrent appends. He provides a minimal diff demonstrating this approach and confirms it passes the existing test, though he notes potential portability concerns and the risk of silent corruption if conflicting data is written. Peff also raises the question of whether resumption should be preserved, suggesting two potential improvements if it is abandoned: allowing users to opt into resumable behavior via configuration, and piping the download directly to `index-pack --stdin` to reduce disk I/O and enable pipelining (which would inherently fix the concurrency issue). Peff’s review clarifies a subtle ownership issue in `release_http_pack_request()`: the `preq->packfile = NULL` assignment after `delete_tempfile()` is redundant because `delete_tempfile()` already closes the FILE handle, and the struct is about to be freed. He recommends either dropping the assignment or restructuring the conditional with a comment to clarify ownership semantics. Taylor Blau's review suggests the same mechanical improvement and otherwise approves the patch's logic, documentation, and regression test. The test for concurrent downloads, which pauses one process mid-download to simulate a race, is noted as "plausibly correct" but not deeply scrutinized.
- Patch 2: Makes `fetch-pack` accept both `"keep<TAB><hash>"` and `"pack<TAB><hash>"` output from `index-pack` when processing packfile URIs, addressing a race where a concurrent fetch may have already created the `.keep` file. Jeff King (Peff) reviewed the patch and suggested a mechanical refactor using `strbuf` to eliminate magic numbers and improve readability, replacing the fixed-size buffer (`packname[GIT_MAX_HEXSZ + 6]`) with a dynamically resized `strbuf`. In a follow-up email, Peff provides the missing cleanup code for the `strbuf` approach: a `strbuf_release(&cmd_output)` call after the packhash is extracted, preventing a memory leak. The fix is trivial and does not affect the patch’s core logic or correctness. Peff’s feedback remains focused on code hygiene, reinforcing that the refactor is a non-blocking, maintainability-focused improvement. The patch remains a clean, well-motivated fix for the `.keep` file race. Peff also noted two unrelated quirks in the surrounding code: (1) a discrepancy between the documented (`--index-pack-args`) and actual (`--index-pack-arg`) option name in `git-http-fetch`, and (2) the implicit reliance on `get_pack()` to pass `--keep` to `index-pack`, which makes the requirement to read `"keep"` output subtle. Neither issue is new or introduced by this patch, and Peff explicitly stated they are not the patch’s fault.

Key technical details:
- Files touched: `http.c`, `fetch-pack.c`, documentation.
- New symbols: None (behavioral changes only).
- Test coverage: New regression tests in `t/t5550-http-fetch-dumb.sh` and `t/t5702-protocol-v2.sh`, explicitly addressing the tempfile and `.keep` file races.
- Subsystem: HTTP transport, packfile URI feature.
- On-disk format: No changes.
- Old vs. new behavior: Concurrent packfile URI downloads now use unique tempfiles (or could use deterministic paths with write-only file descriptors), preventing corruption; `.keep` file handling is more tolerant of concurrent processes. Resumable downloads for packfile URIs are abandoned in the current design, creating an inconsistency with dumb HTTP. The design rationale remains that unique tempfiles avoid the complexity of cross-process coordination, but the abandonment of resumption is now a contested trade-off.
- Design rationale: Ted Nyman argues that unique tempfiles avoid the complexity of cross-process coordination (e.g., detecting in-progress downloads, handling handoffs, or implementing timeouts), which would be required for a coordination-based approach. The current design preserves the existing "download, index, then install" workflow for each process. Taylor Blau endorses this rationale, emphasizing that reliably distinguishing between an in-progress download and a leftover `.pack.temp` file from a crashed process is not feasible with existing mechanisms. Jeff King and Junio C Hamano now challenge this rationale, arguing that resumability is a major goal of the packfile URI feature and that the current approach deliberately sacrifices it. Peff’s alternative (write-only file descriptors without O_APPEND) is proposed as a way to preserve resumption while avoiding corruption.

Open questions and loose ends:

Junio C Hamano’s feedback signals skepticism, and the thread’s consensus on a “fix first, optimize later” approach is now in question. A revised design that preserves resumption (e.g., lockfile-style coordination, Peff’s write-only file descriptor approach, or piping to `index-pack --stdin`) may be required.
- Whether the inconsistency between dumb HTTP (resumable) and packfile URIs (non-resumable in the current design) is justified or introduces new edge cases. Peff’s review suggests this is a meaningful drawback worth reconsidering.
