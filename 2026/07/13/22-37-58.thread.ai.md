Thread identity: Bugfix series for packfile URI download race conditions in Git's HTTP transport. Series version: initial (no prior versions mentioned). Originating author: Ted Nyman. Thread type: patch series (bugfix).

Core problem or goal: Fix race conditions in Git's HTTP transport when multiple processes concurrently fetch the same packfile URI into a single object database. The races can corrupt temporary pack files or cause resume requests to fail at EOF. The series targets the packfile URI feature, which allows servers to offload large packfiles to external storage.

Current status: Initial submission under review. No prior versions. No merge status indicated. Changes:
- Patch 1: Modifies HTTP layer to use unique temporary files for each direct packfile URI download, preserving resumable staging for ordinary dumb HTTP pack requests. The design prioritizes correctness and simplicity by avoiding cross-process coordination. Junio C Hamano raised concerns about redundant downloads when multiple processes fetch the same packfile concurrently, but Taylor Blau and Ted Nyman now agree that the current approach is the correct trade-off for the immediate bugfix. Jeff King (Peff) suggests treating the `.pack.temp` file as a lockfile (using Git’s existing lockfile logic, e.g., auto-removing ancient mtime files or checking PID liveness) and questions whether abandoning resumable downloads for packfile URIs is justified, given that dumb HTTP and packfile URIs face the same concurrency/resumption problems but are now handled differently. Peff’s latest review clarifies a subtle ownership issue in `release_http_pack_request()`: the `preq->packfile = NULL` assignment after `delete_tempfile()` is redundant because `delete_tempfile()` already closes the FILE handle, and the struct is about to be freed. He recommends either dropping the assignment or restructuring the conditional with a comment to clarify ownership semantics. Taylor Blau's review suggests the same mechanical improvement and otherwise approves the patch's logic, documentation, and regression test. The test for concurrent downloads, which pauses one process mid-download to simulate a race, is noted as "plausibly correct" but not deeply scrutinized.
- Patch 2: Handles a race condition with `.keep` files by making `fetch-pack` accept both success message forms from `index-pack` and only remove keep files created by the current process.

Key technical details:
- Files touched: `http.c`, `fetch-pack.c`, documentation.
- New symbols: None (behavioral changes only).
- Test coverage: New regression tests in `t/t5550-http-fetch-dumb.sh` and `t/t5702-protocol-v2.sh`, explicitly addressing the tempfile and `.keep` file races.
- Subsystem: HTTP transport, packfile URI feature.
- On-disk format: No changes.
- Old vs. new behavior: Concurrent packfile URI downloads now use unique tempfiles, preventing corruption; `.keep` file handling is more tolerant of concurrent processes. Resumable downloads for packfile URIs are abandoned in favor of correctness, creating an inconsistency with dumb HTTP.
- Design rationale: Ted Nyman argues that unique tempfiles avoid the complexity of cross-process coordination (e.g., detecting in-progress downloads, handling handoffs, or implementing timeouts), which would be required for a coordination-based approach. The current design preserves the existing "download, index, then install" workflow for each process. Taylor Blau endorses this rationale, emphasizing that reliably distinguishing between an in-progress download and a leftover `.pack.temp` file from a crashed process is not feasible with existing mechanisms. Jeff King implicitly endorses the "fix first, optimize later" approach but raises the question of whether resumption should be preserved (and how) and whether dumb HTTP and packfile URIs should eventually share a unified solution.
