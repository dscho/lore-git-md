Thread identity: Bugfix series for packfile URI download race conditions in Git's HTTP transport. Series version: v2 (reroll). Originating author: Ted Nyman. Thread type: patch series (bugfix).

Core problem or goal: Fix race conditions in Git's HTTP transport when multiple processes concurrently fetch the same packfile URI or dumb HTTP pack into a single object database. The races can corrupt temporary pack files or cause resume requests to fail at EOF. The series provides a unified solution for both packfile URIs and dumb HTTP, preserving resumable downloads while preventing corruption.

Current status: Rerolled (v2) under review. The v2 series replaces the v1 approach (unique tempfiles for packfile URIs) with deterministic staging paths opened in read-write mode without append, allowing overlapping responses to write identical bytes at identical offsets. Changes in v2:
- Patch 1: Uses deterministic staging paths for both packfile URIs and dumb HTTP, preserving resumable downloads. Handles concurrent unlink scenarios (including Windows sharing behavior) and fixes the EOF-range/416 case. Corrects documentation typos (e.g., `--index-pack-args` → `--index-pack-arg`) and clarifies staging-key semantics. The core change in `http.c` switches from append mode to read-write mode with per-descriptor offsets, ensuring overlapping responses write identical bytes at identical offsets. Test coverage includes new regression tests in `t/t5550-http-fetch-dumb.sh` and a deterministic overlapping-download test using a custom Perl server. Junio C Hamano reviewed the patch and suggested splitting the `--index-pack-args` typo fix into a separate preliminary patch to keep the functional change clean, but did not object to the core design. He expressed unease about the `pwrite(2)` approach ("somehow makes me feel dirty") but accepted the Windows/MINGW workaround allowing one process to finalize the file while others hold open descriptors.
- Patch 2: Makes `fetch-pack` accept both `"keep<TAB><hash>"` and `"pack<TAB><hash>"` output from `index-pack`, validating the reported pack hash against the advertised hash and only registering a keep lockfile when the current process created it (`created_keep` flag). The implementation reads only the prefix and hash, leaving any subsequent fsck output available to `fetch-pack`. Test coverage adds a regression test exercising a packfile URI fetch with a pre-existing `.keep` file, verifying the pack and index are correctly installed and the `.keep` file remains untouched.

Key technical details:
- Files touched: `http.c`, `fetch-pack.c`, documentation.
- New symbols: None (behavioral changes only).
- Test coverage: New regression tests in `t/t5550-http-fetch-dumb.sh` and `t/t5702-protocol-v2.sh`, exercising resumed transfers, EOF ranges, overlapping 200/206 responses, pre-existing `.keep` files, and packfile URI fetches with concurrent `.keep` files. A deterministic overlapping-download regression test uses a custom Perl server to simulate concurrent partial responses, verifying pack integrity.
- Subsystem: HTTP transport, packfile URI feature, dumb HTTP.
- On-disk format: No changes.
- Old vs. new behavior: The v2 design preserves resumable downloads for both packfile URIs and dumb HTTP by using deterministic staging paths and read-write mode without append. Concurrent processes write identical bytes at identical offsets, preventing corruption while maintaining resumability. The `.keep` file handling is more robust, with `fetch-pack` validating the pack hash and only registering a keep lockfile when the current process created it.
- Design rationale: The v2 design avoids cross-process coordination while preserving resumability and correctness. It unifies the solution for both packfile URIs and dumb HTTP, addressing handoffs, stale-file cleanup, and the EOF-range/416 case.

Open questions and loose ends:
