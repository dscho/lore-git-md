This thread introduces a `-x` flag for `git rebase -i`'s `pick`, `reword`, and `edit` commands, mirroring `git cherry-pick -x` by appending "(cherry picked from commit ...)" to commit messages. The feature aims to streamline cherry-picking during interactive rebases, avoiding the need for `exec git cherry-pick -x`. Version 1 of the series was posted by Trevor Gross and has drawn substantive feedback, most critically from Junio C Hamano.

Junio’s latest review challenges the feature’s very premise, arguing that `git rebase` and `git cherry-pick` serve fundamentally different purposes: rebase *moves* history (abandoning original commits), while cherry-pick *duplicates* it (preserving originals). The `-x` flag makes sense for cherry-pick because the original commit remains accessible, but in a rebase, the original commits are discarded, rendering the "cherry picked from" line potentially misleading. Junio also notes that rebase copies notes from original commits (since they’re replaced), while cherry-pick does not (since originals are preserved), further underscoring the workflow mismatch. This is now the central open question: whether the feature aligns with rebase’s design or risks encouraging a workflow that contradicts its semantics.

Earlier feedback from Junio also raised technical concerns, including the need to clarify the fast-forward behavior (no message appended), stricter error handling for malformed todo lines, and documentation improvements. The series touches `rebase-interactive.c`, `sequencer.c`, and test files, and reuses existing `TODO_RECORD_ORIGIN` logic. The ball is in Trevor’s court to address Junio’s design critique—either by justifying the feature’s place in rebase, proposing an alternative, or revisiting the approach. Until this is resolved, the series remains under active discussion with no merge in sight.
