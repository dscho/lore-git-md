Trevor Gross’s `git rebase -i -x` patch series (v1) introduces a `-x` flag for `pick`, `reword`, and `edit` commands to append "(cherry picked from commit ...)" trailers, mirroring `git cherry-pick -x`. The series remains under active review, with **high-weight substantive objections** from Junio C Hamano, Jeff King (Peff), and Phillip Wood challenging the feature’s conceptual alignment with `git rebase` (moving vs. duplicating history). Junio’s latest reply explicitly endorses Peff’s and Phillip’s critiques, reinforcing that the "cherry picked from" annotation loses meaning in a rebase workflow where original commits are discarded. The thread’s future now centers on Peff’s proposed `cherry-pick -i` mode as the likely path forward, with Junio’s and Phillip’s support.

**Core problem or goal**: Users performing cherry-picks during interactive rebases lack a native way to record commit origin, forcing them to use `exec git cherry-pick -x`, which disrupts the rebase flow. The patch integrates this functionality directly into rebase todo commands, reusing `TODO_RECORD_ORIGIN` logic from `git cherry-pick`. However, the fundamental tension between `rebase` (moving history) and `cherry-pick` (duplicating history) remains unresolved. Peff’s and Phillip’s proposal to extend `cherry-pick` with an interactive mode (`-i`) is now the most viable alternative, as it leverages the existing sequencer backend and avoids semantic inconsistencies. Phillip’s question—why `rebase` is the right tool for this workflow rather than extending `cherry-pick`—remains unanswered and is central to the thread.

**Current status**: v1 posted; under review. The series faces three major design objections:
1. **Junio’s objection**: The `-x` flag’s purpose is undermined in a rebase workflow where original commits are discarded, making the annotation’s utility questionable. Junio now explicitly agrees with Peff and Phillip that the feature misaligns with `rebase`’s core semantics and endorses the `cherry-pick -i` alternative.
2. **Peff’s objection**: The feature could be better addressed by extending `cherry-pick` with an interactive mode (`-i`), leveraging its existing sequencer backend. Peff’s experiment confirms that `cherry-pick` already generates a todo file (`.git/sequencer/todo`), suggesting minimal work to add interactivity. In his latest reply, Peff tempers expectations about edge cases (e.g., `edit -x` followed by `fixup`) but reinforces the practicality of `cherry-pick -i`, noting that `rebase.missingCommitsCheck` is the primary rebase-specific hurdle. He adopts a permissive stance on user behavior, assuming users will document edits in commit messages rather than enforcing strict validation.
3. **Phillip’s objection**: Endorses Peff’s critique and presses Trevor to justify the rebase-centric approach, noting that `cherry-pick -i` would avoid inconsistencies between per-commit `-x` flags (Trevor’s patch) and the global `record-origin` option (used by `cherry-pick -x`). Phillip also highlights edge cases (e.g., `edit -x` followed by `fixup`) where the "cherry picked from" trailer’s meaning becomes ambiguous, and suggests harmonizing global and per-commit `-x` flags by having `cherry-pick -x` automatically add `-x` to each todo line. Peff’s reply largely agrees with Phillip’s assessment but leaves edge-case handling to user discretion.

**Key technical details**:
- Files touched: `rebase-interactive.c`, `sequencer.c`, `t/t3404-rebase-interactive.sh`.
- New flag: `-x` for `pick`, `reword`, and `edit` commands in rebase todo list, parsed as an argument (e.g., `pick 123456 -x`).
- Behavior: Appends "(cherry picked from commit ...)" to commit messages, reusing `TODO_RECORD_ORIGIN` logic. Fast-forwards skip the message (documented difference from `git cherry-pick -x`).
- Edge cases: Struct initialization (`struct todo_item item = { 0 }`) fixes a latent bug in `do_pick_commit()`; error handling for malformed todo lines (e.g., `pick -xabcdef 123456`) remains unresolved; parsing ambiguity between `-x` as a flag vs. argument persists. Phillip notes that the per-commit `-x` flag approach would require awkward conditional logic (`if (opt->record_origin || (item->flags & TODO_RECORD_ORIGIN))`) to check for trailers. Peff’s latest reply leaves edge cases like `edit -x` or `pick -x` followed by `fixup` to user discretion, with no explicit validation proposed.
- Test coverage: Verifies flag works with all three commands and checks output format.
- **New insight**: Peff’s review confirms that `cherry-pick` already uses the sequencer backend and generates a todo file, implying an interactive mode could be implemented with minimal changes. The primary rebase-specific hurdle is `rebase.missingCommitsCheck`, which would need to be generalized or bypassed for `cherry-pick -i`. Phillip’s suggestion to harmonize global and per-commit `-x` flags (by having `cherry-pick -x` automatically add `-x` to each todo line) remains unresolved. Behavioral inconsistency noted: `cherry-pick -x` applies globally via `record-origin = true`, while Trevor’s patch allows per-command `-x` flags.
- **Fast-forward behavior**: Absence of a message is intentional but must be documented. Phillip notes this stems from unchanged conditions in `do_pick_commit()` and `skip_unnecessary_picks()`.
- **Error handling**: Stricter validation needed for malformed todo lines (e.g., `pick -xabcdef 123456`).
- **Code style**: Nested conditionals in `todo_list_to_strbuf` could be flattened for clarity.
- **Latent bug**: The `struct todo_item` initialization fix may need to be split into a separate patch to avoid conflating it with the feature work. Matt Hunter’s review advocates for this.
