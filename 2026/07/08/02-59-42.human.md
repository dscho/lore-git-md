This is the second patch in a three-patch bugfix series targeting race conditions in Git’s HTTP daemon test helpers. The series addresses a real, observed flake in the test suite (`t5616.47`) where concurrent Apache requests to the same CGI script caused HTTP 500 errors due to non-atomic state management.

This patch fixes `t/lib-httpd/http-429.sh`, which uses a `test -f` check followed by a `touch` to track whether it has already returned a 429 (Too Many Requests) response. Because Apache serves requests concurrently, two requests can both pass the `test -f` check before either writes the state file, causing both to treat themselves as the first request. The fix replaces the non-atomic check with an atomic `mkdir`, which fails if the directory already exists, ensuring exactly one request is rate-limited while the rest are forwarded to `git-http-backend`.

The change is minimal and targeted: it removes the `touch` and `rm -f` operations, replaces the state file with a directory, and adjusts the logic to handle the `permanent` retry-after case without state cleanup. The commit message explains the race clearly and notes that the fix is preventive, as the race is latent and has not yet been observed in practice. There is no accompanying regression test because the race cannot be forced deterministically—only reproduced probabilistically—but the atomic `mkdir` idiom is well-established in Git’s own lockfile machinery.

This patch is part of a well-crafted series that addresses a narrow but real problem in the test infrastructure. The fixes are mechanical and unlikely to be controversial, as they do not change the scripts’ behavior under sequential execution. The series as a whole is motivated by a concrete CI flake and includes a new test (in patch 1) that verifies the fix for the other affected script. If you care about test reliability, this patch is worth a quick look.
