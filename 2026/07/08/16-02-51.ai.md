This is a refactoring series (v8, 9 patches) that continues the libification effort by migrating more global configuration variables into `struct repo_config_values`. The series is a direct follow-up to the recently merged `excludes_file` migration and addresses the memory leak Junio C Hamano identified in v7.

The core change since v7 is a fix for the memory leak in `pager_program` (and by extension, other heap-allocated string fields in `repo_config_values`). The leak occurred when these fields were re-assigned without freeing the old value; the fix ensures proper cleanup during re-assignment. This resolves the primary technical blocker from the previous iteration.

The series remains structured in two parts: infrastructure and strings (patches 1-6) and enums (patches 7-9). The infrastructure work introduces `repo_config_values_clear()` to manage heap-allocated strings, while the enum migrations handle `push_default`, `autorebase`, and `object_creation_mode`. The RFC questions from v7—whether migrating program paths (editor, pager, askpass) is worthwhile, and how this work relates to prior discussions about `git_branch_track`—remain open but do not block progress.

Key technical details for follow-up discussion:
- The memory leak fix affects all string-valued fields in `repo_config_values` (`pager_program`, `editor_program`, `askpass_program`, `excludes_file`, `attributes_file`, `apply_default_whitespace`, `apply_default_ignorewhitespace`).
- The series touches `environment.c`/`environment.h` heavily, along with smaller changes in `apply.c`, `branch.c`, `builtin/push.c`, and other files.
- New symbols: `repo_config_values_clear()` (destructor), getters like `repo_askpass_program()`, and direct field access for migrated variables.
- The `NEEDSWORK` comments from v7 (submodule support, enum placements) remain unresolved but are not blockers.

The series is now technically complete and CI-clean, with the memory leak fixed. The remaining open questions are about design choices (RFCs) and follow-up cleanup (comments, variable classification), not correctness. This looks ready for `next` once the memory leak fix is confirmed.
