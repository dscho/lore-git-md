This is a follow-up in the RFC thread proposing `--only`/`--except` options for `git clone` to specify sparse-checkout paths upfront. The author, Pushkar Singh, responds to Jeff King’s feedback, clarifying his design intent and acknowledging the alternative approach Peff suggested (providing a patterns file at clone time).

Pushkar explains that his proposal was motivated by the existing `git sparse-checkout set` workflow, which he uses regularly, rather than direct manipulation of the patterns file. He sees the feature as a convenience layer over that workflow, not as a way to expose the patterns file itself. This distinction is important: the proposal targets users who prefer CLI commands over manual file editing, even if the underlying mechanism remains the same.

On the performance question Peff raised, Pushkar confirms that his focus was purely ergonomic—simplifying the workflow by eliminating the separate `sparse-checkout set` step after clone. He acknowledges that any performance benefits (e.g., using the selected paths earlier in the clone process) would be a bonus but notes he hasn’t explored whether that’s feasible. This reinforces that the feature’s primary value is workflow simplification, not performance optimization.

The email also includes a practical step: Pushkar cc’s Derrick Stolee, a sparse-checkout domain expert, following Peff’s suggestion. This increases the chances of getting substantive feedback from someone with deep knowledge of the subsystem, though no response from Stolee is included here.

The tone remains collaborative and open-ended. Pushkar doesn’t push back on Peff’s alternative design; instead, he frames his proposal as one possible approach and welcomes further input. The thread is still in the exploratory phase, with no clear consensus on the best path forward. For now, the feature’s prospects depend on whether other contributors (especially Stolee or Elijah Newren) see enough value in the ergonomic improvement to justify the added complexity.
