This is a bugfix patch discussion about the ongoing `core.configLockTimeout` feature. Johannes Schindelin steps into the thread to break the deadlock between Junio C Hamano and Patrick Steinhardt over whether to cache the timeout value or not.

Schindelin bluntly calls the caching debate a distraction that has delayed the patch for over a month. The patch itself adds a configurable timeout (default 1000 ms) for acquiring `config.lock`, modeled after the existing `core.packedRefsTimeout`. It is motivated by real-world failures in concurrent operations like `git worktree add -b` that write branch tracking information. The v2 iteration includes thorough test coverage and clear documentation of read-after-lock semantics.

This email does not resolve the technical question—Junio still prefers an explicitly process-wide timeout, Patrick still prefers removing the cache—but it removes the procedural blocker. The patch is now effectively unblocked unless someone objects to Schindelin’s call to merge.
