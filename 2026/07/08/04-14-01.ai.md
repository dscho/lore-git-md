This is the v2 submission of a refactoring series that replaces `tmp_objdir` usage in `git-receive-pack` with the ODB transaction subsystem, advancing the ODB abstraction effort. The series now consists of 11 patches (up from 6 in v1), incorporating all feedback from the v1 review cycle and splitting some patches for clarity.

The core goal remains unchanged: to make `git-receive-pack` ODB-backend-agnostic by staging incoming objects via transactions rather than temporary object directories. The v2 series addresses all blocking feedback from v1, including:
- Renaming transaction functions for consistency (`odb_transaction_files_flush`, `odb_transaction_files_prepare`)
- Propagating error codes through the transaction lifecycle (begin, commit, and environment interfaces)
- Introducing `ODB_TRANSACTION_RECEIVE` flags to preserve `receive-pack`'s eager directory creation and "incoming" prefix naming
- Redesigning the `odb_transaction_env` interface to use `struct strvec` for error propagation
- Splitting the final patch into two (flag introduction and application in `receive-pack`)
- Adding a file-local global variable in `builtin/receive-pack.c` to avoid churn in transaction parameter passing

The series touches 14 files, with the heaviest changes in `object-file.c` (159 lines) and `builtin/receive-pack.c` (69 lines). Key interfaces modified include `odb_transaction_begin()`, `odb_transaction_commit()`, and `odb_transaction_env()`, all of which now return `int` for error propagation. The `ODB_TRANSACTION_RECEIVE` flag is documented in `odb/transaction.h` and used to configure the "files" backend for `receive-pack`'s specific needs.

Notable deferred work includes:
- Error-handling improvements (e.g., making `odb_transaction_files_prepare()` failures fatal)
- Lazy directory creation investigation
- Explicit `odb_transaction_abort()` interface
- Detangling object-write paths to remove the "files" transaction functions from `object-file.c`

The series is queued for `next` pending v2 integration. No objections remain to the approach or goals, and the architectural limitation (one ODB transaction per ODB) is explicitly documented for future refactoring. The changes are mechanical but non-trivial, with thorough error propagation and interface updates. Test coverage remains unchanged, relying on the existing test suite to exercise `receive-pack` and its child processes.
