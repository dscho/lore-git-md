This is a review of the first patch in Michael Montalbo’s three-patch series fixing race conditions in Git’s HTTP daemon test helpers. Junio C Hamano’s feedback is substantive but narrowly focused on a single edge case in the atomicity logic.

The patch replaces a non-atomic shell sequence (`test -f` followed by `rm`) in `t/lib-httpd/apply-one-time-script.sh` with an atomic `mv` operation, eliminating a race that could cause HTTP 500 errors when concurrent requests (e.g., a partial fetch lazily retrieving a promisor object) hit the same CGI script. The fix is minimal: it claims the marker atomically only after the one-time script succeeds and actually modifies the response, and it uses per-request scratch files (`out.$$`, `out-modified.$$`) to prevent clobbering.

Junio’s review identifies a subtle remaining race window: if two requests run the one-time script concurrently, the second request might still execute the script before the first request’s `mv` completes, potentially running the script twice. However, he acknowledges that this is harmless because the script’s output is discarded if the `mv` fails, ensuring only one request emits the modified response. His concern is purely about clarity—future readers might misinterpret the atomicity guarantee—rather than correctness. He suggests adding a note to the commit message explaining that running the script multiple times is acceptable, as long as only one request’s output is used.

The rest of the patch (the new test in `t5567-one-time-script.sh`, the atomic idiom, and the per-request scratch files) passes without comment, implying no objections. The series remains a well-motivated, self-contained bugfix targeting test infrastructure, with no user-visible behavior changes. The fix is already in use to address a real, observed flake in `t5616.47` on macOS CI, and the atomic patterns align with Git’s existing lockfile machinery. Reviewers can expect a v2 addressing Junio’s documentation nit, but the core logic is unlikely to change.
