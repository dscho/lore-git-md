This is the second patch in the now-merged four-patch series that standardizes help-flag exit codes across Git’s parse-options infrastructure. It introduces a new return code, `PARSE_OPT_HELP_ERROR`, to distinguish between user-requested help (which will soon exit 0) and help output triggered by invalid input (which should continue to exit 129). The patch updates `parse-options.c`, `usage.c`, and three built-in commands (`git blame`, `git shortlog`, `git update-index`) to handle the new return code, ensuring that all help-related exits are routed through the same logic.

The core change is in `usage_with_options_internal()`, which now returns `PARSE_OPT_HELP_ERROR` when `err` is set, closing the refactoring gap identified by Peff in the previous iteration. This ensures that help output triggered by errors (e.g., ambiguous options) is treated consistently across all parse-options users. The patch also shifts `PARSE_OPT_COMPLETE` to `-4` to make room for the new `-3` value, a mechanical adjustment that doesn’t affect behavior.

The three built-in commands are updated to include `PARSE_OPT_HELP_ERROR` in their exit-129 cases, preserving the existing error-handling flow while preparing for the upcoming exit-code change. The patch is a targeted refactoring with no immediate behavioral impact—it lays the groundwork for the next patch in the series, which will flip the exit code for user-requested help to 0. The changes are minimal and focused, touching only the parse-options infrastructure and its direct consumers.
