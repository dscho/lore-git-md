This is the first patch in a v2 two-patch bugfix series addressing the bundle-URI protocol's handling of invalid server configurations. The patch modifies the client-side `get_remote_bundle_uri()` function in `connect.c` to drain the protocol stream after encountering invalid bundle-URI lines (such as empty URIs), preventing stale data from remaining in the read buffer and causing the misleading "expected 'packfile'" error during clone operations.

The change is straightforward: the function now continues reading packets even after an error occurs, though it skips processing them. This ensures the protocol exchange can proceed cleanly, allowing the clone to complete successfully despite the server's misconfiguration. The patch includes two new test cases in `t/t5558-clone-bundle-uri.sh` that verify the client handles both missing and empty URIs gracefully, with appropriate error messages and no "expected packfile" noise.

The implementation aligns with the series' agreed-upon approach of combining client-side resilience with server-side validation (handled in patch 2). The commit message clearly explains the problem, the fix, and the rationale for allowing clones to continue, referencing the historical behavior of `transport_get_remote_bundle_uri()`. The patch looks well-crafted, with thorough test coverage and no obvious oversights. It should be uncontroversial as it doesn't change fundamental behavior but makes error handling more robust.
