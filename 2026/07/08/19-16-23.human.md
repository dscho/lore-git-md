This is a **performance bugfix** for `unpack-trees.c` that resolves a quadratic-time index scan in `next_cache_entry()`. The patch is now in its second iteration, with Junio confirming that Henrique’s argument about the safety of the new `cache_bottom` optimization—specifically, that `find_cache_pos()` already advances `.cache_bottom` past unpacked entries—addresses his earlier correctness concern. The fix remains minimal (4 lines) and targets a real-world performance regression: on a Chromium-scale repository, `git diff HEAD -- <pathspec>` drops from 8 minutes to 0.07 seconds when the pathspec matches a subtree whose entries appear early in the index.

The only remaining loose end is a **surface-level improvement** to the perf test (`t/perf/p0009-diff-pathspec.sh`). Junio suggested making the entry count (`100000`) configurable via the `EXPENSIVE` prerequisite, a tweak Henrique has not yet incorporated. This is not a blocker for correctness or performance but would make the test more flexible for contributors running it locally. The patch is otherwise ready for further review or integration, assuming no new concerns emerge about the interaction between the forward-scan optimization and the existing `.cache_bottom` logic for handling index/tree ordering mismatches.

Key technical details: the fix adds a `cache_bottom` field to `o->internal` to track forward-scan progress, complementing the existing `.cache_bottom` field (which handles backward scans). The perf test creates a 100k-entry index with a problematic layout to trigger the regression, though the entry count should ideally scale with `EXPENSIVE`. The patch is well-motivated, thoroughly tested, and addresses a clear pain point for large repositories. If the correctness argument holds under further scrutiny, this is likely to land soon.
