This is the third patch in a now-merged four-patch bugfix series that standardizes help-flag exit codes across Git’s parse-options infrastructure. The series addresses a long-standing inconsistency where `--help`/`-h` exited 129 (error) instead of 0 (success), violating Unix conventions. This patch specifically targets `git rev-parse --parseopt`’s shell-eval mode, ensuring it exits 0 when help is requested, while preserving the 129 exit code for direct invocation (a debugging aid).

The implementation appends `exit 0` to the heredoc output generated by `usage_with_options_internal()` in `parse-options.c`, a solution Junio Hamano accepted despite calling it "yuck." This change ensures scripts evaluating `--parseopt`’s output (the recommended usage) exit successfully on `--help`. The patch also updates test expectations in `t/t1502-rev-parse-parseopt.sh` and `t/t1517-outside-repo.sh`, adding `exit 0` to help-spec files and adjusting sed commands to account for the new heredoc line. Three shell scripts (`instaweb`, `quiltimport`, `request-pull`) are temporarily marked as failing in `t1517` pending a follow-up patch that updates their expected exit codes.

Key technical details: the patch modifies `parse-options.c` (adding `exit 0` to the heredoc), updates 37 test files (including help-spec files and test scripts), and touches `t1502`/`t1517` to reflect the new behavior. The change is backward-compatible for scripts using the standard `eval "$(git rev-parse --parseopt ...)"` pattern, as the `exit 0` in the heredoc overrides any subsequent `exit 129` from the `echo exit $?` fallback. The patch is part of a fully merged series, with all post-merge issues (prerequisite logic, refactoring gaps) resolved in this v3 revision. No further discussion is expected.
