Subject: [PATCH] merge --abort: preserve autostash on reset failure
Series version: standalone patch (no series)
Originating author: Kris Point
Thread type: bug report / bugfix patch

Core problem or goal
When `git merge --abort` fails (e.g., due to a locked index), the autostash created by `merge --autostash` is permanently lost because the `MERGE_AUTOSTASH` ref is deleted before `git reset --merge` is attempted. The goal is to prevent this data loss by ensuring the autostash is preserved if the reset fails, and only saved if conflicts arise during application.

Current status
Under review. The original patch is blocked pending redesign. Junio C Hamano and Phillip Wood have endorsed an alternative approach: decoupling reset logic from `cmd_reset()` and introducing a new flag (`RESET_WORKING_TREE_MERGE`) to `reset_working_tree()` or `reset_head()`. This aligns with ongoing refactoring in the `ps/history-drop` branch in `seen`. No revised patch has been posted yet.

Key technical details
- File touched: `builtin/merge.c`
- Original behavior (current): `MERGE_AUTOSTASH` ref is deleted upfront; `cmd_reset()` handles merge state cleanup, risking autostash loss if reset fails.
- Flaw in original patch: Unconditionally saves the autostash even if it applies cleanly, and persists it even if reset fails.
- Correct behavior (per Phillip Wood and Junio): Autostash should only be saved if conflicts arise during application, and merge state should persist if reset fails.
- Proposed solution: Avoid calling `cmd_reset()`; instead, directly invoke `reset_working_tree()` or `reset_head()` with a new flag (`RESET_WORKING_TREE_MERGE`) to control autostash behavior. Target branch: `ps/history-drop` in `seen`.
- No new symbols, CLI options, or on-disk format changes introduced by the redesign.
- Test coverage: Original patch lacked test coverage for edge cases (e.g., autostash application conflicts, reset failures). The redesign may require additional tests.
