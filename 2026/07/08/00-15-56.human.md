This is the third patch in a now-merged four-patch bugfix series that standardizes how Git’s parse-options infrastructure handles `--help`/`-h` flags. The series addresses a long-standing inconsistency where `git rev-parse --parseopt` (and all commands using parse-options) exited with status 129 for help requests instead of the Unix-standard exit 0.

This patch specifically targets the shell-eval mode of `git rev-parse --parseopt`, which is designed to be evaluated by scripts. When help output is requested, the command prints a `cat` heredoc to standard output; the patch appends `exit 0` to that heredoc so the invoking script exits successfully. The change is minimal but effective: it modifies `usage_with_options_internal()` in `parse-options.c` to print `EOF\nexit 0\n` instead of just `EOF\n`, and updates the test suite to expect the new behavior. Three test files (`t/t1502-rev-parse-parseopt.sh`, `t/t1502/optionspec-neg.help`, and `t/t1502/optionspec.help`) are adjusted to reflect the added `exit 0` line, and `t/t1517-outside-repo.sh` adds three shell scripts (`instaweb`, `quiltimport`, and `request-pull`) to its failure list because they no longer return 129 as expected—these will be updated in the next patch.

The implementation is pragmatic: Junio called the heredoc `exit 0` approach “yuck” but accepted it as functionally correct. The patch preserves backward compatibility for direct invocations of `--parseopt` (which still exit 129 for debugging purposes) while ensuring shell-eval mode follows Unix conventions. The trade-off—scripts delegating option parsing to Git may now feed garbage to downstream logic if `--help` is accidentally passed—was acknowledged and accepted as a side effect of the broader fix. This patch is part of a fully merged series, so no further discussion is expected.
