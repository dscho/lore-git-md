This is a documentation patch, part of Junio C Hamano's ongoing effort to clarify contributor workflows in `Documentation/SubmittingPatches`. The patch adds explicit guidance on how to handle abandoning or retracting a patch series, addressing a real friction point in the review process where topics left in limbo create unnecessary work for the maintainer and community.

The update introduces a new bulleted section that acknowledges the reality that not all patch series succeed. It encourages contributors to explicitly retract a topic if it becomes clear the changes aren't ideal, if they can no longer work on it, or if it stalls for four weeks with unaddressed review comments. The text emphasizes that retraction is not permanent—topics can be resurrected later—and frames it as a courtesy to the community rather than a failure.

This is the second iteration of the patch (v2), though the changes from v1 are not shown in the diff. The update is concise, well-motivated, and aligns with the project's culture of clear communication. No controversy is expected, as the guidance reflects existing informal practices rather than introducing new policy. The patch touches only `Documentation/SubmittingPatches` and makes no code or behavioral changes.

Key details for follow-up discussion: the new section uses the term "retract" (not "abandon"), specifies a four-week inactivity threshold for maintainer discard, and explicitly allows for resurrection. These are the likely points any light feedback might address, though substantive objections are unlikely. The patch is self-contained and ready for merging.
