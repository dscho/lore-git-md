This is the final patch in the nine-part `diff.<driver>.process` RFC series, now in its fifth revision. It wires `git log -L` (line-log) range tracking to consult the external diff process, closing the last major gap in the feature's integration with Git's diff and blame pipelines.

The patch ensures that the commit selection logic in `collect_diff()` uses the same diff hunks as the display pass (`builtin_diff()`), preventing a mismatch where a reformat-only commit would be selected by the built-in algorithm but then rendered with an empty diff because the external tool reported the files as equivalent. When the tool declares a commit equivalent, the range tracking now collects no diff ranges, causing the tracked range to map across unchanged and the commit to drop out of the log entirely. This matches the behavior already implemented for `git blame` and the summary formats (`--stat`, `--numstat`, `--shortstat`).

The implementation reuses the `xdi_diff_process()` helper introduced in an earlier patch, passing the raw file contents to the tool (mirroring the summary-format integration) and omitting blob object names for now, with a comment noting that a future change could supply them to enable caching across the range-tracking and display passes. The driver selection logic matches `builtin_diff()` by using the old (parent) path, ensuring renamed files resolve to the same driver for both tracking and display.

Test coverage (33 lines in `t/t4080-diff-process.sh`) verifies that the tool can selectively drop commits from the log while preserving others, and that the protocol is invoked with the expected parameters. The documentation update clarifies that `git log -L` now consults the process for both range tracking and display, completing the "Which features consult the diff process" matrix in `gitattributes(5)`.

With this patch, the series is now technically complete: all major diff and blame features either consult the external process or explicitly bypass it, and the protocol carries enough information (including blob object names) to support future optimizations like caching.
