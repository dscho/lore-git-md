This is the first patch in the v5 series introducing configurable submodule fetch errors, targeting the submodule subsystem. It fixes a long-standing logic flaw in `submodule.c` where phase-1 fetch failures (e.g., ref fetch errors) were recorded as errors immediately, even when a subsequent phase-2 OID-based fetch could still succeed. The fix defers error recording until all retry attempts fail, ensuring the overall fetch result accurately reflects whether the required commits were ultimately obtained.

The patch restructures `fetch_finish()` to handle four distinct scenarios: phase-2 retry succeeds (no error), phase-2 retry fails (error recorded), unconditional fetch with no retry (error recorded immediately), and phase-1 failure with all commits already present locally (error recorded despite availability). A new helper function `record_fetch_error()` centralizes error recording, ensuring consistent behavior and proper submodule name inclusion in the final error summary. The changes also fix a pre-existing issue where phase-1 failures were not reported when the gitlinked commits were already present locally, which is now covered by a new test.

Key technical details include the extraction of error recording logic into `record_fetch_error()`, the use of `task->commits` to distinguish between phase-1 and phase-2 failures, and the introduction of a test environment helper (`create_err_env`) to isolate submodule fetch error scenarios. The test suite adds a comprehensive case verifying that fetch failures are reported even when the required commits exist locally but are unreachable from the submodule’s remote.

The patch is a prerequisite for the configurable error policy introduced in patch 2/2, as it ensures errors are only recorded when truly unrecoverable. The implementation is narrowly scoped to the submodule fetch error-handling path, with no behavior changes outside this context. The commit message clearly explains the problem, the solution, and the edge cases addressed, making the rationale easy to follow.

This patch is uncontroversial and appears technically sound. It addresses a NEEDSWORK comment from 2019 and lays the groundwork for the user-facing controls in the next patch. The changes are well-tested and align with the series’ goal of making submodule fetch errors more flexible without breaking existing workflows.
