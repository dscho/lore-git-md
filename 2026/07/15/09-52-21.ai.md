This is the final patch in the GSoC v18 series implementing `git cat-file --batch-command`'s `remote-object-info` feature. It replaces the hardcoded allow-list for format placeholders (`%(objectname)` and `%(objectsize)`) with a dynamic system that adapts to what the server actually advertises, paving the way for future expansion (notably `objecttype` support).

The patch restructures `expand_data` to include a `remote_allowed_atoms` string list that is populated at runtime based on the server's advertised capabilities. The client now maps requested placeholders (e.g., `%(objectsize)`) to protocol options (e.g., `"size"`), filters out any options the server does not support, and only allows placeholders corresponding to successfully fetched options. This ensures clients never request metadata the server cannot provide, eliminating segfault risks and aligning behavior with `for-each-ref`'s handling of inapplicable atoms (returning empty strings rather than errors).

Key changes include:
- A new `remote_atom_map` array that associates protocol options (`"size"`, `"type"`) with their corresponding placeholders (`"objectsize"`, `"objecttype"`).
- Dynamic population of `remote_allowed_atoms` in `parse_cmd_remote_object_info()` after fetching object info, using the filtered `object_info_options` list.
- Removal of the static `remote_object_info_atoms` array and its replacement with runtime checks against `data->remote_allowed_atoms`.
- Logic to skip output entirely if no supported options remain after filtering, while still producing output (empty lines) for unsupported placeholders when at least one option is supported.
- Memory management updates to initialize and clear the new `remote_allowed_atoms` string list in `EXPAND_DATA_INIT` and `batch_objects()`.

The patch also moves `object_info_options` out of `get_remote_info()` to allow callers to specify which options to request, and relocates `batch_object_write()` to ensure output is generated even when all placeholders are unsupported. The implementation is future-proof: new protocol options can be added to `remote_atom_map` without modifying the core logic.

The dynamic allow-list system is a necessary foundation for extensibility, and the patch demonstrates careful attention to edge cases (e.g., backward compatibility, memory safety, and graceful degradation).
