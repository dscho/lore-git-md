This thread is about a patch series from Tian Yuchen that moves the global `fetch_if_missing` variable into `struct repository` as part of Git’s ongoing libification and `the_repository` removal efforts. The goal is to make the flag repository-specific, preserving existing behavior while eliminating global state. The v2 patch addressed prior feedback but introduced new issues, including a null pointer dereference risk in `builtin/index-pack.c` and a fundamental design question: whether `fetch_if_missing` should be tied to a repository at all, given that commands like `git index-pack` can run outside one.

The latest exchange between Tian and Junio C Hamano narrows the focus to two key problems. First, Tian agrees to adopt Junio’s suggestion to require `git index-pack` to always run inside a repository, removing the problematic `if (repo)` check and eliminating the crash risk. This change restricts `index-pack`’s flexibility but aligns with the libification goal of removing global state. Second, the thread surfaces a deeper tension: `fetch_if_missing` serves both as a repository-specific flag (controlling lazy fetches) and a global setting (controlling network behavior), making its placement in `struct repository` conceptually awkward. Tian proposes deferring a more comprehensive solution—such as Junio’s idea of a global "basic settings" structure—until subsystems are fully prepared to handle `repo` instead of `the_repository`.

The patch is not yet ready for pickup. A v3 is planned to address the immediate crash risk, but the broader design question remains unresolved. Patrick Steinhardt’s earlier feedback (identifying the null pointer risk) and Junio’s architectural concerns highlight that the patch may need further revision before it can be merged. Testing will need to verify that `index-pack` fails gracefully outside a repository and that per-repository behavior remains consistent. The thread is now at a crossroads: whether to proceed with the minimal change or pursue a more ambitious refactoring.
