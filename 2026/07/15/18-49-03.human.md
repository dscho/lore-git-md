This is a **design discussion** about the `--linearize` option in `git replay`, focusing on how it should handle multiple branches. Junio C Hamano responds to Elijah Newren’s concerns about the current behavior, which concatenates all branches into a single linear chain when `--linearize` is used.

Junio argues that the current behavior is **intentional and predictable**: if a user supplies multiple branches to `--linearize`, the command does exactly what it’s asked to do—flatten all commits into one chain. He suggests that users who want finer control (e.g., linearizing only one branch while keeping others independent) can achieve this by running `git replay` multiple times, once per branch. This, he claims, is a **feature**, not a bug, because it gives users flexibility without imposing arbitrary restrictions.

Elijah’s counterargument is that the current behavior **violates the principle of least astonishment** and is **inconsistent with other `git replay` modes** (`--advance` and `--revert`), which reject multiple positive refs to avoid ambiguity. He provides a concrete example where a user might want to linearize *one* branch (flattening its merges) while rebasing others normally—but the current implementation silently concatenates all branches, making the result difficult to untangle. Junio dismisses this as a user error ("why would they feed all three branches to a single invocation?"), but Elijah’s point is that the command’s behavior is **surprising and hard to recover from** when it happens unintentionally.

Junio also raises a **technical concern**: if the user wants to linearize branches in a specific order (e.g., `B` then `A` then `C`), the current implementation doesn’t guarantee that order because it relies on the revision walk’s traversal. He suggests that the command-line syntax might need to be **restricted** (e.g., one negative ref plus one or more positive refs) to make the behavior more predictable, though he acknowledges this would limit flexibility.

The discussion is now at an impasse: Junio sees the current behavior as **acceptable for most use cases** (especially where order doesn’t matter, like octopus merges), while Elijah argues it **prioritizes a rare use case (concatenating branches) over a common one (linearizing a single branch)**.
