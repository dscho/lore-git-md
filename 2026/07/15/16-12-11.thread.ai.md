Thread identity: Bugfix and hardening patch series targeting the trace2 subsystem to prevent crashes caused by `die()`-triggering helpers (e.g., `xsnprintf()`, `xstrdup()`, `ALLOC_ARRAY()`, `xstrfmt()`, `ALLOC_GROW()`, `xcalloc()`) under memory pressure or system call failures. Originating author: Derrick Stolee. Thread type: patch series (bugfix/hardening).

Core problem or goal: Eliminate all `die()`-triggering helpers from the trace2 API to prevent Git crashes during telemetry operations. The original crash (a "recursion detected in die handler" error) was caused by `xsnprintf()` failures in trace2 timestamp formatting, specifically due to `libintl_vsnprintf()` memory allocations on Git for Windows. The expanded goal is to harden trace2 against all allocation or system call failures by replacing banned functions with defensive fallbacks that prioritize process stability over telemetry completeness. The series introduces `banned-die.h` as a general-purpose enforcement mechanism to systematically block `die()`-prone functions in trace2 and potentially other low-level subsystems, with Junio C Hamano clarifying that the banned functions are prohibited due to their potential to trigger `die()` in unsafe contexts (e.g., `atexit()` handlers).

Current status: Under review. Derrick has posted a complete seven-part series (v2) that supersedes the earlier standalone patch (v1) and implements the agreed two-part solution: (1) his hardening patch series, which replaces all `die()`-triggering helpers in trace2 with defensive fallbacks, and (2) a planned MinGW-specific follow-up (Taylor Blau’s alternative) to disable `libintl_vsnprintf()` redirection for `xsnprintf()` in a platform-isolated file. The series touches 17 files within the trace2 subsystem and introduces `banned-die.h` as a new architectural enforcement mechanism. Junio’s feedback from the prior thread remains aligned with this approach, and his latest reply reinforces the header’s broader applicability while raising no objections or technical concerns. Elijah Newren’s reviews of the first, third, fifth, and sixth patches raise architectural, correctness, and splitting concerns: a naming inconsistency (`banned(die)` vs. `BANNED(die)`) and include-ordering risk in `banned-die.h`, an incomplete hardening in the config parsing path (where the error path still triggers a `die()` via `xstrfmt()`), a one-byte off-by-one error in the fifth patch’s manual string concatenation for redaction (omitting the trailing `>` in `:<REDACTED>`), and a regression in the sixth patch when applied in isolation (triggering a `BUG()` due to region stack underflow). The seventh patch resolves the sixth patch’s regression, indicating a splitting error in the series. Junio’s latest reply confirms the off-by-one error in the fifth patch and clarifies the fix: the `memcpy()` call for the redacted placeholder should copy `redact_len` bytes (not `redact_len - 1`) to include the trailing `>`.

Key technical details:
- **Files touched**: `banned-die.h` (new header to block `die()`-triggering functions), all trace2 `.c` files (`trace2/tr2_ctr.c`, `trace2/tr2_tls.c`, `trace2/tr2_tmr.c`), and `trace2/tr2_tls.h`. The changes are self-contained to the trace2 subsystem, though the header’s placement at the root of the tree signals intent for future reuse in other subsystems.
- **Subsystem**: trace2 (telemetry), memory allocation, MinGW compatibility, and architectural enforcement mechanisms.
- **Behavior change**:
  - The first patch introduces `banned-die.h` to enforce the prohibition of `die()`-triggering functions (e.g., `xsnprintf()`, `xstrdup()`, `ALLOC_ARRAY()`, `xstrfmt()`, `ALLOC_GROW()`, `xcalloc()`) in trace2. The header is designed to be extensible for other banned functions or traits (e.g., `the_repository`, `the_hash_algo`) in future hardening efforts.
  - Subsequent patches replace banned functions with defensive fallbacks:
    - `xsnprintf()` in timestamp formatting is replaced with `snprintf()` and hardcoded fallbacks (e.g., `"1900-00-00T00:00:00.000000Z"`).
    - `xstrdup()` in `tr2_sysenv.c` is replaced with `strdup()`, with `tr2_sysenv_cb()` halting config parsing on failure and `tr2_sysenv_get()` returning `NULL`. However, Elijah Newren’s review of the third patch reveals that the error path still triggers a `die()` in `git_parse_source()` via `xstrfmt()`, meaning the hardening is incomplete for this code path. The commit message’s claim of "full defense in depth" is misleading for this specific case.
    - `ALLOC_ARRAY()` in `redact_argv()` is replaced with `calloc()`, with callers degrading gracefully by dropping telemetry on `NULL`.
    - `xstrfmt()` in `redact_arg()` (fifth patch) is replaced with manual string concatenation and overflow checks, returning `NULL` on failure. Elijah Newren’s review identifies a one-byte off-by-one error in the manual string construction: the patch copies `redact_len - 1` bytes of the `:<REDACTED>` placeholder, omitting the trailing `>` and producing `:<REDACTED` instead of `:<REDACTED>`. Junio’s latest reply confirms this error and clarifies that the fix requires copying `redact_len` bytes to include the trailing `>`. This could corrupt trace2 logs or expose sensitive data if the suffix contains unredacted content.
    - `ALLOC_GROW()` in `tr2_tls.c` (sixth patch) is replaced with manual reallocation and a `nr_skipped_regions` counter to skip stack growth on failure. However, when applied in isolation, this patch breaks the invariant that the region stack cannot underflow, triggering a `BUG()` in `tr2tls_pop_unwind_self()` with the message `"no open regions in thread 'main'"`. The regression is resolved by the seventh patch, which replaces `xcalloc()` and ensures the fallback context is properly initialized.
    - `xcalloc()` in `tr2tls_create_self()` (seventh patch) is replaced with `calloc()` and a **statically allocated fallback context** (`tr2tls_thread_fallback`) that uses the thread name `"unknown"` to signal failure. The new `tr2tls_is_fallback()` helper allows callers to detect and handle the fallback state, and trace2 counter/timer functions short-circuit when operating on a fallback context.
  - Trace2 will tolerate allocation or system call failures by falling back to degraded operation (e.g., truncated messages, hardcoded timestamps, dropped events, `NULL` returns, unrecorded regions, or a static fallback context) instead of crashing. This is a breaking change for trace consumers, who may see malformed or missing data under failure conditions, but the trade-off is intentional and documented.
- **On-disk format**: No changes.
- **Test coverage**: None, as the issue depends on transient allocation or system call failures that are hard to reproduce. The series acknowledges this limitation.
- **Platform focus**: Primarily Git for Windows, where `libintl_vsnprintf()`’s allocation behavior differs from POSIX, but the hardening applies to all platforms.
- **Architectural concerns raised by Elijah Newren**:
  - **Naming inconsistency**: The patch uses `banned(die)` instead of `BANNED(die)`, deviating from Git’s existing convention (e.g., `NO_THE_REPOSITORY_H`). This could produce a confusing compiler error ("implicit declaration of function 'banned'") instead of the intended clear message ("sorry_die_is_a_banned_function").
  - **Include-ordering risk**: `banned-die.h` is included in the middle of the include list in `trace2.c`. If future includes are added *after* it, functions from those headers that later get banned would be silently ignored, creating a false sense of security. The fix is to move `banned-die.h` to the end of the include list.
  - **Incomplete hardening in config parsing path**: The third patch’s replacement of `xstrdup()` with `strdup()` does not fully eliminate the risk of crashing in trace2’s config parsing path, as the error path still triggers a `die()` in `git_parse_source()` via `xstrfmt()`.
  - **Off-by-one error in redaction**: The fifth patch’s manual string concatenation for `:<REDACTED>` omits the trailing `>`, corrupting the output and potentially exposing sensitive data. Junio’s latest reply confirms this error and clarifies the fix.
  - **Splitting error in the sixth patch**: The sixth patch introduces a regression (region stack underflow) when applied in isolation, which is only resolved by the seventh patch. This suggests the series was incorrectly split—either the sixth patch should not be standalone, or the seventh patch should have been folded into it.
