This is a **substantive discussion** in the `git replay --linearize` thread, where Junio C Hamano responds to Elijah Newren’s critique of the current `--linearize` behavior with multiple branches. The email clarifies Junio’s position on two key points: **user intent** and **command-line syntax limitations**.

Junio argues that the current behavior is **not a bug but a feature**—users who want to avoid concatenating branches can simply invoke `git replay` multiple times, one branch at a time. He dismisses Elijah’s concern about silent concatenation by framing it as the user’s responsibility to know what they’re asking for: if the outcome isn’t desired, the user shouldn’t provide all branches in a single command. This aligns with his earlier defense of the status quo, but here he explicitly rejects the idea that the command should "solve" the problem of unintended concatenation by restricting input.

The email then shifts to **syntax design**, where Junio explores whether the command-line interface should be more restrictive to prevent ambiguity. He suggests two alternatives:
1. **Track replayed commits across invocations** (so `branchC` can be replayed on top of `branchA` even if `branchA` was handled in a previous command). This would require persistent state, which `git replay` currently lacks.
2. **Limit the syntax to a single negative ref plus one or more positive refs**, ensuring a predictable order (e.g., `git replay --onto master branchB branchA branchC` would produce `master..B1'..B3'..A1'..A4'..C1'..C2'`). This would sacrifice flexibility (e.g., arbitrary rev-list ranges) but reduce user error.

Junio leans toward the second option, calling it "much less error prone for casual users," but stops short of endorsing it outright. His tone suggests skepticism about over-engineering the solution—he seems content with the current behavior, provided users understand its limitations.

The email leaves the **multi-branch ambiguity** unresolved but reframes it as a **syntax design question** rather than a correctness issue. The ball is back in Toon Claes’s court to either:
- Accept the current behavior (with improved documentation/warnings),
- Restrict `--linearize` to a single positive ref (Elijah’s minimal fix), or
- Implement one of Junio’s proposed syntax changes.

Notably, Junio does not address Elijah’s **recoverability asymmetry** argument (that untangling concatenated branches is harder than concatenating independent ones), which remains a key point in favor of restricting the interface. The discussion is now squarely about **trade-offs between flexibility and usability**.
