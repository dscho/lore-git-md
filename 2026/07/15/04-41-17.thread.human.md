This thread is about a small but thoughtful refactoring in Git’s HTTP transport code. René Scharfe proposed a patch to simplify how push specifications are passed to the `remote-curl` protocol handlers by removing redundant tracking of the array count (`nr_spec`). Since the array is already NULL-terminated (as all `strvec` arrays are), the count is unnecessary and requires error-prone conversions between `size_t` and `int`.

The discussion has since expanded into a design-level conversation about whether to pass a `const struct strvec *` instead of a raw `const char **` to the handlers. Patrick Steinhardt suggested this change to make the interface more self-documenting and future-proof, arguing that it would explicitly guarantee NULL-termination and align better with the caller’s context. René acknowledged the benefits but prefers the current simplicity of `strvec_pushv()`, which operates on NULL-terminated arrays. He also noted that introducing a `strvec_pushvec()` function (which would operate on length-limited vectors) could encourage safer usage, though he doubts the performance impact would be measurable.

No consensus has been reached yet, but the conversation remains constructive. Patrick has made it clear he won’t block the current patch, so it could proceed as-is, though a v2 incorporating his suggestion is still possible. The patch itself is confined to `remote-curl.c` and has no observable impact on Git’s behavior—it’s purely an internal cleanup. The thread is now focused on weighing the trade-offs between interface clarity and simplicity, with no other open questions or edge cases identified.
