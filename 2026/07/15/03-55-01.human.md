This is the final patch in a four-part refactoring series (v5) that migrates the `has_symlinks` configuration flag into repository-scoped storage as part of the ongoing `the_repository` removal effort. The patch completes the work begun in the now-merged v4 series by reintroducing the previously deferred `has_symlinks` migration, establishing a unified getter pattern alongside the already-migrated `trust_executable_bit`.

The patch moves the global `has_symlinks` variable into `struct repo_config_values` and introduces a new getter function, `repo_has_symlinks()`, which callers use with an explicit repository pointer (falling back to `the_repository` where necessary). To accommodate early platform-specific overrides on MinGW before repository initialization, a fallback global variable `default_has_symlinks` is introduced, though only the MinGW compatibility layer (`compat/mingw.c`) writes to it. The patch touches seven files, updating call sites in `apply.c`, `combine-diff.c`, `entry.c`, and `read-cache.c` to use the new getter, while adjusting the MinGW layer to respect the repository-scoped configuration.

This is a mechanical migration with no behavioral changes, preserving existing functionality while eliminating global state. The author acknowledges the MinGW compatibility layer as a potential area for future improvement but notes that the current approach ensures correctness. The patch appears well-scoped and ready for review, with the migration pattern established here likely to serve as a template for similar configuration refactoring efforts. The inclusion of `has_symlinks`—previously deferred due to complexity—suggests growing confidence in the approach, though the MinGW adjustments may attract further discussion.
