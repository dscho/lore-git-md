This is the fifth patch in Patrick Steinhardt’s nine-patch v4 series introducing object filters to `odb_for_each_object()`, part of the ongoing ODB abstraction effort. The patch restructures how bitmaps are opened in `pack-bitmap.c` by reversing the loop order: instead of iterating over all object sources to find multi-pack index bitmaps and then iterating again to find packfile bitmaps, it now iterates over each source once and attempts to load either type of bitmap for that source.

The change is mechanical but introduces a subtle behavioral difference: when multiple sources have bitmaps, the new code prefers the first source’s bitmap (typically the local repository) over any later source’s bitmap, even if the later source has a multi-pack index bitmap. Previously, multi-pack index bitmaps from any source took precedence over packfile bitmaps. The commit message argues this is an improvement because it prioritizes local bitmaps, and notes that repositories with multiple bitmaps are already considered broken (Git warns about them).

The patch renames `open_pack_bitmap()` and `open_midx_bitmap()` to `open_bitmap_for_source()`, which now takes an `odb_source_packed *` parameter instead of a repository. The new function encapsulates the logic for opening either a multi-pack index or packfile bitmap for a single source, simplifying the outer loop in `open_bitmap()`. The diffstat shows 31 insertions and 38 deletions, reflecting the consolidation of duplicate iteration logic.

This is a refactoring patch that prepares for the next commit (6/9), which will introduce the ability to open a bitmap for a specific object source. The change is well-motivated and aligns with the series’ goal of making the packed backend’s bitmap handling more modular. No new symbols are exposed, and the behavior change is confined to an edge case that was already problematic. The patch is uncontroversial and has not drawn substantive review feedback beyond the initial discussion in earlier versions.
