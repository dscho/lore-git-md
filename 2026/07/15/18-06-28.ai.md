This is a **bugfix follow-up** to the GSoC v18 `remote-object-info` series, addressing the last unresolved robustness issue before the series graduates to `next`. The patch in question (11/13) introduces a silent failure mode in `parse_cmd_remote_object_info()`: if `get_remote_info()` fails, the function returns without notifying the caller or user, leaving the output buffer in an undefined state. This could mislead callers (e.g., `batch_command()`) into treating stale or partial data as valid.

The author (Pablo Sabater) confirms the issue stems from an earlier design choice to mimic `git cat-file --batch`'s behavior for missing objects, but acknowledges this is incorrect for remote queries. The agreed fix is to replace the silent `goto cleanup` with `die()`, aligning with other `parse_cmd_*` functions in `cat-file.c`. This change ensures failures are loud and unambiguous, preventing subtle bugs in downstream consumers. The fix is trivial (a one-line change) but critical for correctness, as the series is otherwise ready for integration.

This resolves the final technical blocker identified by Junio in the v18 review. The thread context confirms all other feedback—including security hardening, edge-case handling, and protocol design—has been addressed. The series implements a security-hardened `remote-object-info` command for querying object metadata (currently size only) from remotes without full downloads, with dynamic allow-lists, strict input validation, and comprehensive test coverage. The fix here ensures the command fails fast rather than silently producing misleading output.
