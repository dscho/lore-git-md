This is the ninth and final iteration of Harald Nordgren’s `git history squash` feature, a new subcommand that folds a commit range into its oldest commit while preserving descendant history. The series is now functionally complete, addresses all prior feedback, and is ready for integration.

The headline improvement in v9 is the resolution of the `amend!` message handling edge case raised by Matt Hunter. The command now uses the body of the last `amend!` commit targeting the oldest folded commit as the default squashed message, ignoring any `amend!` markers targeting later commits. This ensures internal consistency and improves commit hygiene by incorporating the most recent amendment intent. The implementation is clean: the `reject_dangling_fixups()` helper now also identifies the relevant `amend!` source, and the message is constructed before the commit tree is written.

The series remains well-structured, with each patch serving a clear purpose. Patch 1/5 refactors a helper for resolving a commit’s first-parent tree, patch 2/5 extends `commit_tree_ext()` to support a message template, patch 3/5 implements the core squash logic (including range validation, merge handling, and rev-list option sanitization), patch 4/5 refactors sequencer helpers for reuse, and patch 5/5 adds the `--reedit-message` feature. The test suite is thorough, covering range parsing, merge commit handling, descendant replay, authorship preservation, `--reedit-message` template construction (including autosquash grouping), ref-handling behavior, `--dry-run` prediction accuracy, interior ref detection, input validation, and fixup/squash/amend edge cases. The tests now include helpers for improved readability, following the pattern established in the `delete-merged` topic.

Junio’s "Will replace" sign-off on v7 indicates intent to queue the series, and v9 resolves the last technical concern. The only remaining discussion point is whether `--reedit-message` should be the default, but this is a minor usability tweak that does not block merging. The series is technically sound, well-documented, and aligns with the project’s architectural goals, particularly the vision of using `git history squash` and `git replay` as a faster, non-interactive backend for `git rebase --autosquash`.
