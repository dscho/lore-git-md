Thread identity: Refactoring of `remote-curl` transport code to simplify push specification handling. Series version: standalone patch (potential v2 pending). Originating author: René Scharfe.

Core problem or goal: Eliminate redundant tracking of the push specification array count (`nr_spec`) in the HTTP transport handlers (`push_dav` and `push_git`). The array is already NULL-terminated (as all `strvec` arrays are), so the count is unnecessary and requires error-prone conversions between `size_t` and `int`. The discussion has expanded to consider whether to pass a `const struct strvec *` instead of a raw `const char **` to make the NULL-termination guarantee explicit, improve interface clarity, align with caller context, and enable future optimizations like `strvec_pushvec()`. The broader API design question now includes whether to introduce a `strvec_pushvec()` helper to encourage safer, length-limited vector usage over NULL-terminated arrays.

Current status: Under review. No prior versions. The patch is a standalone refactoring with no behavior change. The thread remains focused on design-level trade-offs between interface clarity and simplicity, with Patrick Steinhardt and Junio C Hamano advocating for the `strvec *` approach and a potential `strvec_pushvec()` helper, while René Scharfe prefers the current simplicity of `strvec_pushv()`. Patrick has explicitly stated he will not insist on a reroll, so the current patch could proceed as-is, but a v2 incorporating the `strvec *` interface or future work on `strvec_pushvec()` remains possible. No merge status has been reported; the series is still under review.

Key technical details:
- Files touched: `remote-curl.c` only.
- Functions modified: `push_dav`, `push_git`, and `push`.
- New behavior: Callers now pass only the NULL-terminated `strvec` array to protocol handlers; handlers iterate until NULL terminator instead of relying on a count. The discussion now centers on whether to pass the entire `strvec` struct to make the interface more self-documenting and future-proof, and whether to introduce a `strvec_pushvec()` helper to encourage safer usage patterns.
- Old behavior: Handlers received both the array and its item count (`nr_spec`), requiring conversions between `size_t` and `int`.
- No new symbols, CLI options, config keys, or on-disk format changes.
- Test coverage: None added; the change is internal to the transport layer and does not affect observable behavior. No test failures or performance regressions reported.

Open questions and loose ends:
- Whether to adopt Patrick’s suggestion to pass a `const struct strvec *` instead of a raw `const char **`. This remains unresolved, with René acknowledging the safety and clarity benefits but preferring the simplicity of the current approach.
- Whether to introduce a `strvec_pushvec()` helper as a future optimization and API improvement. Junio suggests this could be a worthwhile independent effort, separate from René’s current patch, and notes that identifying conversion candidates would be straightforward using `git grep` or Coccinelle. The performance impact of such a helper is debated, but its potential to encourage safer usage patterns is acknowledged.
- No other open questions or edge cases identified.
