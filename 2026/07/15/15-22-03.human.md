This is the final patch in Phillip Wood’s nine-part series fixing how Git’s sequencer handles dropped commits during rebase. The patch directly addresses the original bug: when `git rebase` drops a commit (e.g., because its changes are already upstream), the sequencer incorrectly copies that commit’s notes to the current HEAD and confuses post-rewrite hooks by recording the dropped commit as "rewritten."

The fix is surgical. It adds a new `PICK_RESULT_DROPPED` value to the `enum pick_result` introduced earlier in the series, then modifies `pick_one_commit()` to skip calling `record_in_rewritten()` for dropped commits. The patch also ensures that if the dropped commit is the final one in a chain of fixups, the list of rewritten commits is flushed. Test coverage is expanded in both `t3400-rebase.sh` (notes from dropped commits) and `t5407-post-rewrite-hook.sh` (post-rewrite hook accuracy for fixups and commits that become empty).

One known limitation remains: the "edit" command still erroneously records dropped commits as rewritten when `rebase --continue` is run. The commit message documents this and flags it for a separate fix, making the limitation explicit rather than hidden.

This is a well-crafted, minimal change that completes a thoroughly reviewed and tested series. The patch itself is small (24 lines added, 5 removed in `sequencer.c`), and the accompanying tests are clear and targeted. Junio has already approved the series for `next` after minor typofixes are squashed, so this patch is effectively ready to land in the next Git release. If you care about rebase correctness or use post-rewrite hooks, this is worth noting.
