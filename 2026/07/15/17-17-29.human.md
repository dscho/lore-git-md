This is a refactoring patch that converts `git show-branch` to use a commit-slab for per-commit state instead of the shared `object.flags` field, lifting the long-standing 27-branch limit to 64 branches. Junio C Hamano’s reply to the v5 patch identifies two behavioral regressions in the slab-based implementation that break the revision-walking logic in `join_revs()`: the code now incorrectly marks merge-base commits as `UNINTERESTING` and fails to propagate that bit to parents, which would prevent those commits from being shown. He also notes that the documentation still claims a 26-branch limit and that the test suite may lack coverage for the expanded limits, suggesting new tests to verify the change. Finally, he points out a minor portability issue with the use of `%zu` in a warning message, recommending `unsigned long` instead.

The patch is technically sound in its slab conversion and branch-limit expansion, but Junio’s feedback reveals that the author missed subtle but critical differences in how the original code handled `UNINTERESTING` propagation. The regressions are not cosmetic: they would alter the output of `git show-branch` in ways that users would notice. The author will need to revise the patch to restore the original behavior while keeping the slab infrastructure. The discussion is now focused on correctness rather than style or design, and the patch is not yet ready for merging.
