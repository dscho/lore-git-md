This is the final patch in the nine-part `diff.<driver>.process` RFC series, now at v5. It wires `git log -L` range tracking to consult the external diff process, ensuring that the commits selected for display match what the user actually sees in the diff output. Previously, `git log -L` used Git's builtin diff algorithm for commit selection while the displayed diff consulted the external tool, creating a mismatch where a reformat-only commit could be selected but then rendered with an empty diff because the tool reported the files as equivalent.

The patch modifies `collect_diff()` in `line-log.c` to call `xdi_diff_process()` before falling back to the builtin diff. When the tool reports the files as equivalent (`DIFF_PROCESS_EQUIVALENT`), no ranges are collected, causing the tracked range to map across the commit unchanged and the commit to drop out of the log. This matches the behavior already implemented for `git blame` and the summary formats (`--stat`, `--numstat`, `--shortstat`). The patch also updates the documentation in `gitattributes.adoc` to reflect that `git log -L` now consults the tool for both range tracking and display, removing it from the "not yet wired" list.

The implementation is careful to preserve existing behavior: the driver is selected by the old (parent) path, matching how `builtin_diff()` resolves the driver, and blob object names are omitted in the protocol for this path (though the infrastructure is in place for a future optimization to thread them through). The test coverage (33 lines in `t/t4080-diff-process.sh`) exercises the key scenario: a commit that the tool reports as equivalent is dropped from the log, while the creating commit still appears, confirming that the change is selectively skipped rather than the entire log going empty.

This patch completes the series' goal of making every "which lines changed" operation consult the external tool. The only remaining cases that still use the builtin algorithm are combined diffs (`--cc` and merge diffs), whose protocol would need to be extended to handle multiple parent comparisons. The series is now technically complete, with all substantive review feedback addressed and comprehensive integration across Git's diff and blame pipelines. The path to merging depends on final documentation refinements and maintainer sign-off on the overall justification.
