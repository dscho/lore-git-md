This is the second patch in a two-part series (v5) that adds configurable error handling for submodule fetches. It introduces `fetch.submoduleErrors` (config) and `--submodule-errors=(fail|warn)` (CLI) to let users choose whether `git fetch --recurse-submodules` should fail hard or merely warn when a submodule’s gitlink points to an unreachable OID. The default remains `fail` for backwards compatibility, preserving existing behavior.

The patch wires up the new controls in `builtin/fetch.c`, forwarding the resolved setting (whether from CLI or config) to child fetches (`--all`, `--multiple`, nested recursion) when explicitly set. This ensures the user’s intent is preserved across all fetch phases, including per-remote child processes that handle submodule recursion themselves. The implementation is clean: config value parsing and option formatting are centralized in a shared name array (`submodule_error_names`), eliminating redundant conditional branches and aligning CLI/config logic. Case sensitivity is enforced with `strcmp` as requested in prior review.

Test coverage is thorough, verifying warn mode, error reporting, CLI override propagation, and edge cases like inaccessible submodules. The tests also confirm that the setting is forwarded correctly with `--all` and that a failed submodule fetch is still reported even when the gitlinked commits are present locally. The patch touches `submodule.c`, `submodule.h`, documentation files, and adds new tests to `t/t5526-fetch-submodules.sh`.

This patch depends on the first one in the series, which fixes a pre-existing logic flaw in submodule fetch error handling. Together, they solve a real workflow pain point—upstream topic branches that are still in flux—without introducing broader risks. The implementation appears robust, the rationale is well-explained, and the changes are narrowly scoped to the submodule fetch error-handling path.
