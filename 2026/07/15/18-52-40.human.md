This is the final patch in the GSoC v18 series that implements `git cat-file --batch-command`'s `remote-object-info` feature, now with a dynamic allow-list for server-advertised metadata fields. The series is queued for `next` and functionally complete, addressing all prior feedback except for one robustness issue in this patch.

Pablo Sabater responds to Junio’s review with clarifications and fixes. The key change is making the allow-list dynamic: instead of hardcoding support for only `objectname` and `objectsize`, the client now maps format placeholders (e.g., `%(objectsize)`) to protocol options (e.g., `"size"`) based on what the server advertises. Unsupported placeholders (like `%(objectcolor)`) return empty strings, matching `for-each-ref` behavior. Pablo confirms this with an example: if the server supports only `size`, `%(objectsize) %(objectcolor)` outputs `42 ` (not `42 %(objectcolor)`).

Junio’s concern about silent failures when no object-info options are requested (e.g., only `%(objectname)`) is addressed by an early return that skips the remote query entirely, returning the OID directly. While this avoids unnecessary connections, it means the client cannot verify object existence on the remote—a limitation Pablo acknowledges as future work. The patch also fixes a silent failure in `parse_cmd_remote_object_info()` by ensuring it `die()`s on errors, aligning with other `parse_cmd_*` functions.

A minor style nit about the `EXPAND_DATA_INIT` macro is resolved by reformatting it for readability. The patch is well-motivated and technically sound, with clear test coverage and security considerations (e.g., batch limits, input validation). The dynamic allow-list design ensures future extensibility (e.g., adding `objecttype` support) without breaking compatibility. This is a polished, production-ready contribution that resolves the last open issue in the series.
