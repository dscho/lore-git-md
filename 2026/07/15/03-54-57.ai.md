This is a refactoring patch series (v5, 4 patches) that migrates both `trust_executable_bit` and `has_symlinks` configuration flags into `struct repo_config_values`, completing the work begun in the now-merged v4 series. The series is part of the ongoing `the_repository` removal effort and targets core index handling and configuration plumbing.

The key change since v4 is the reintroduction of the `has_symlinks` migration (as patch 4/4), which was previously deferred due to implementation complexity. The series now moves both flags into repository-scoped storage while maintaining eager parsing for performance in hot paths. A new getter pattern (`repo_trust_executable_bit()` and `repo_has_symlinks()`) is established, and all call sites are updated to use repository-scoped access. The author notes that `repo_config_values()` still does not support non-`the_repository` instances due to deep integration of these flags, but this work lays groundwork for future elimination of the global.

Files touched include `read-cache.c`, `environment.c/h`, `apply.c`, `compat/mingw.c`, and related headers. The series removes redundant extern declarations, relocates `ce_mode_from_stat()` implementation, and migrates both flags into `repo_config_values` with proper initialization and safety checks. The mingw compatibility layer is adjusted, though the author questions whether a cleaner approach might exist. Review feedback from v4 has been incorporated, including dropping a redundant comment and preferring the `repo` parameter over `the_repository` where possible.

The series builds on prior attempts (some unsuccessful) to refactor these flags, with the author explicitly noting that `struct repo_settings` was deemed suboptimal for this migration. The work demonstrates incremental progress in eliminating global state while establishing patterns for future configuration migrations. The inclusion of `has_symlinks`—previously deferred—suggests growing confidence in the approach, though the mingw compatibility question may attract further discussion.

This is a well-scoped refactoring with clear technical goals, touching core Git internals but preserving existing behavior.
