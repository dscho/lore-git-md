This is a **substantive discussion** in the ongoing `git replay --linearize` thread, where Elijah Newren elaborates on his objections to the current implementation’s handling of multiple positive refs. The email is a detailed rebuttal to Junio C Hamano’s earlier defense of the status quo, and it reframes the debate around **usability, consistency, and recoverability** rather than just predictability.

Elijah’s core argument is that the current `--linearize` behavior **makes the rare use case easy while ignoring the common one**. Specifically:
- **Rare case**: Users who want to flatten multiple independent branches into a single linear chain (e.g., for an octopus merge) can do so with one command.
- **Common case**: Users who want to linearize *one* branch (e.g., to flatten a merge) while rebasing others independently are forced into a confusing, concatenated topology where all branches are merged into one chain. Recovering from this is **asymmetrically difficult**—undoing an unwanted concatenation requires meticulous manual work, while the reverse (splitting a concatenated chain) is trivial.

The email includes **concrete examples** contrasting the current behavior with what Elijah considers the intuitive outcome. For instance, replaying three branches (`branchA`, `branchB`, `branchC`) with `--linearize` currently produces a single linear chain where all branches are flattened into one, with the original branches pointing to arbitrary commits along that chain. Elijah argues this is **rarely useful** and **violates the principle of least astonishment**, as it:
1. Ignores the user’s command-line order of branches.
2. Turns multiple branches into one while still updating all of them (a logical inconsistency).
3. Behaves differently on already-linear history when `--linearize` is added (e.g., `git replay --linearize --onto main topic` does something unexpected even if `topic` has no merges).

Elijah also highlights an **inconsistency within `git replay` itself**: `--advance` and `--revert` reject multiple positive refs to avoid ambiguity, but `--linearize` silently accepts them, leading to divergent behavior for similar operations.

His proposed solutions are:
1. **Minimal fix**: Make `--linearize` reject multiple positive refs (aligning with `--advance`/`--revert`), unblocking the series for merging while leaving per-branch linearization as future work.
2. **Complete fix**: Track a `last_commit` per branch to linearize each independently, preserving the original branch structure.

Elijah strongly prefers the minimal fix for this series, arguing that **erroring out now preserves flexibility**—turning an error into working behavior later is safe, but allowing the current concatenation semantics to reach `master` risks users depending on them, making future changes a compatibility break. He notes that `git replay` is still **EXPERIMENTAL**, so this isn’t a hard blocker, but the current behavior risks painting the project into a corner.
