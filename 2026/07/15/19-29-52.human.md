This is a refactoring patch targeting the revision-walking machinery, specifically the `get_commit_action()` function in `revision.c`. The patch addresses a long-standing impurity in the function: while it reads like a predicate that decides whether a commit should be shown or ignored, it also has a hidden side effect—it mutates tracked line ranges when used with `git log -L` (line-level log) without parent rewriting. This side effect makes it unsafe to call the function out of order, such as in a lookahead scenario.

The patch splits the early, cheap checks (e.g., whether the commit is already shown or marked uninteresting) into a new helper, `commit_early_ignore()`, and moves the line-range mutation logic into `simplify_commit()`, where it runs before `get_commit_action()` is called. This ensures `get_commit_action()` becomes a pure predicate, as its name suggests. The change is motivated by historical context: `get_commit_action()` was originally split out of `simplify_commit()` to avoid parent rewriting for the commit-graph renderer, but the line-log code later routed its filtering through it, introducing the side effect.

The patch includes a new test helper, `line-log-peek`, which verifies that `get_commit_action()` does not mutate a commit’s flags when called out of order. The test is added to `t4211-line-log.sh` and checks that the function leaves a not-yet-walked commit untouched. The commit message is thorough, explaining the history, the problem, and the solution clearly, and the code changes are well-scoped and justified.

This looks like a clean, well-motivated refactor that addresses a real technical debt issue. The test coverage is appropriate, and the patch should be uncontroversial. It’s a standalone change, not part of a larger series.
