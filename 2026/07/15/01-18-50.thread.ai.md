Thread identity
Subject: [PATCH v2] repository: move `fetch_if_missing` into `struct repository`
Series version: v2 (standalone patch, part of libification and `the_repository` removal efforts)
Originating author: Tian Yuchen <cat@malon.dev>
Thread type: patch submission

Core problem or goal
Move the global `fetch_if_missing` variable into `struct repository` to make it a per-repository flag controlling whether missing objects should trigger lazy fetches from promisor remotes. This continues the project-wide effort to eliminate global state in favor of repository-specific configuration, preserving existing behavior (default value remains `1`, enabled).

Current status
Under review; v2 posted addressing prior feedback, but new architectural concerns and a null pointer dereference risk have surfaced. Junio C Hamano’s review questions the fundamental design, arguing that `fetch_if_missing` may not belong in `struct repository` at all, given that commands like `git index-pack` can run outside a repository. The author has agreed to adopt Junio’s first proposed approach—requiring `git index-pack` to always run inside a repository—eliminating the null pointer dereference risk in `builtin/index-pack.c` by removing the conditional check for `repo`. This resolves the immediate crash risk but restricts `index-pack`’s flexibility. The patch is not yet ready for pickup and will require a v3 to address these issues and the broader design question.

Key technical details
- **Files touched**: 15 files, including `odb.c`, `repository.c`, `fetch-pack.c`, `fsck.c`, `index-pack.c`, `revision.c`, `setup.c`, and partial clone documentation.
- **New symbols**: `struct repository->fetch_if_missing` (replaces global `fetch_if_missing`).
- **Behavior**: Default value remains `1` (enabled); initialization occurs in `initialize_repository()`. Special handling in `fsck.c` and `index-pack.c` avoids null pointer dereferences during early option parsing. `revision.c` adds a `BUG()` check to enforce that `--exclude-promisor-objects` can only be used when `fetch_if_missing` is disabled. The patch retains `the_repository` in `builtin/index-pack.c` and `revision.c` to preserve existing behavior when these commands run without an explicit repository or when the passed repository differs from `the_repository`.
- **Edge cases**:
  - The `setup.c` fix (`repo->fetch_if_missing = 0`) is mechanical and uncontroversial.
  - The decision to retain `the_repository` in specific subsystems is a pragmatic compromise to avoid regressions, but Junio’s review reveals a deeper issue: in repository-less invocations (where `repo` is NULL), the flag remains at its default value (enabled), whereas the current code unconditionally disables it, creating a behavior change. The author has agreed to resolve this by requiring `index-pack` to always run inside a repository, making `repo` non-NULL and eliminating the need for the conditional check in `builtin/index-pack.c`.
  - Patrick Steinhardt’s review identified a **null pointer dereference risk** in `builtin/index-pack.c`: the code checks for `repo` but then unconditionally sets `the_repository->fetch_if_missing`, which could crash if `repo` is NULL. This will be fixed in v3 by removing the conditional check entirely, as the reordering of `show_usage_if_asked()` in v2 is no longer necessary.
  - Junio’s latest review outlines three possible approaches to resolve the repository-less invocation issue:
    1. Require `index-pack` to always run inside a repository, making `repo` non-NULL (adopted by the author for v3).
    2. Use `the_repository` as a fallback when `repo` is NULL, but ensure all code paths that reference `fetch_if_missing` pass `the_repository` in repository-less contexts.
    3. Introduce a new global "basic settings" structure to hold flags like `fetch_if_missing` that apply even outside a repository, with per-repository settings overriding them.
- **On-disk format**: No changes.
- **Test coverage**: No new tests; existing behavior is preserved. The correctness issues in `setup.c` and Patrick’s concerns about multi-repository scenarios have been addressed, but explicit testing of per-repository behavior (especially in `index-pack` and `revision`) and repository-less invocations remains unconfirmed. The null pointer risk in `index-pack.c` and the architectural concerns further underscore the need for additional testing. The v3 patch will need verification that `index-pack` fails gracefully when invoked outside a repository, and that per-repository `fetch_if_missing` behavior remains consistent.

Open questions and loose ends
- **Repository-less invocations**: Junio’s review questions whether `fetch_if_missing` should be tied to `struct repository` at all, given its dual role as both a repository-specific flag ("allow lazy fetching?") and a global setting ("allow network behavior?"). The author has adopted Junio’s first approach (restricting `index-pack` to repository-bound operation) for v3, but the broader design question remains unresolved. The author suggests deferring a more comprehensive solution (e.g., Junio’s third approach: a global "basic settings" structure) until subsystems are fully prepared to handle `repo` instead of `the_repository`.
- **Testing**: The author has not provided explicit confirmation that the patch was tested with repositories other than `the_repository` or in repository-less contexts. While the fixes address the raised concerns, the absence of new test coverage or multi-repository verification leaves a risk of undetected regressions. The v3 patch will need to include tests for the new repository-bound behavior of `index-pack` and per-repository `fetch_if_missing` consistency.
- **Design preference**: Patrick Steinhardt previously suggested moving the flag into the object database rather than `struct repository`, but acknowledged the current approach aligns with libification goals. Junio’s review now challenges whether the flag belongs in `struct repository` at all, making this a more fundamental point of discussion. The author’s v3 will address the immediate crash risk and repository-less behavior change, but the long-term architectural direction remains open.
