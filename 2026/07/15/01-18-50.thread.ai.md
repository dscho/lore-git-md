Thread identity
Subject: [PATCH v3] repository: move `fetch_if_missing` into `struct repository`
Series version: v3 (standalone patch, part of libification and `the_repository` removal efforts)
Originating author: Tian Yuchen <cat@malon.dev>
Thread type: patch submission

Core problem or goal
Move the global `fetch_if_missing` variable into `struct repository` to make it a per-repository flag controlling whether missing objects should trigger lazy fetches from promisor remotes. This continues the project-wide effort to eliminate global state in favor of repository-specific configuration, preserving existing behavior (default value remains `1`, enabled).

Current status
Under review; v3 posted addressing feedback from Junio C Hamano and Patrick Steinhardt. The patch resolves the null pointer dereference risk in `builtin/index-pack.c` by removing the conditional check for `repo` and instead using `(repo ? repo : the_repository)->fetch_if_missing = 0` to handle both repository-bound and repository-less invocations. The author has adopted Junio’s first proposed approach—requiring `index-pack` to always run inside a repository—eliminating the immediate crash risk and the behavior change in repository-less contexts. However, the patch is not yet ready for pickup: it conflicts with `cf1687a41c` (split of `setup_git_env_internal()`), now in `seen`, and the author must address an inconsistency in `setup.c` where `the_repository` is still used despite the function receiving a `repo` parameter. The author proposes to wait for `cf1687a41c` to settle before rerolling, but Junio’s feedback indicates the `setup.c` issue is the more immediate blocker. The broader architectural question of whether `fetch_if_missing` belongs in `struct repository` remains unresolved.

Key technical details
- **Files touched**: 15 files, including `odb.c`, `repository.c`, `fetch-pack.c`, `fsck.c`, `index-pack.c`, `revision.c`, `setup.c`, and partial clone documentation.
- **New symbols**: `struct repository->fetch_if_missing` (replaces global `fetch_if_missing`).
- **Behavior**: Default value remains `1` (enabled); initialization occurs in `initialize_repository()`. Special handling in `fsck.c` and `index-pack.c` defers operations on the repository until after parameter parsing to avoid null pointer dereferences. `revision.c` retains a `BUG()` check to enforce that `--exclude-promisor-objects` can only be used when `fetch_if_missing` is disabled. The patch now uses `(repo ? repo : the_repository)->fetch_if_missing` in `builtin/index-pack.c` to handle both repository-bound and repository-less invocations, preserving existing behavior while eliminating the null pointer risk.
- **Edge cases**:
  - The `setup.c` fix (`the_repository->fetch_if_missing = 0` when `NO_LAZY_FETCH_ENVIRONMENT` is set) remains unchanged and is uncontroversial, but Junio has asked why the function still uses `the_repository` when it already receives a `repo` parameter. The author’s response misinterprets Patrick Steinhardt’s unrelated `setup_environment()` patch as justification, missing the point that the inconsistency is internal to the function’s own signature.
  - The v3 patch resolves the null pointer dereference risk in `builtin/index-pack.c` by replacing the conditional check for `repo` with `(repo ? repo : the_repository)->fetch_if_missing = 0`. This preserves the existing behavior for repository-less invocations while ensuring safety.
  - Junio’s review in v2 outlined three possible approaches to resolve the repository-less invocation issue:
    1. Require `index-pack` to always run inside a repository (adopted in v3 for the immediate fix).
    2. Use `the_repository` as a fallback when `repo` is NULL (partially adopted in v3 via the ternary operator).
    3. Introduce a new global "basic settings" structure to hold flags like `fetch_if_missing` that apply even outside a repository, with per-repository settings overriding them.
  - The broader design question of whether `fetch_if_missing` belongs in `struct repository` remains open. The author has deferred a more comprehensive solution (e.g., Junio’s third approach) until subsystems are fully prepared to handle `repo` instead of `the_repository`.
  - The patch conflicts with `cf1687a41c` (split of `setup_git_env_internal()`), which is now in `seen`. The author must rebase the patch to resolve this conflict before it can be queued.
- **On-disk format**: No changes.
- **Test coverage**: No new tests; existing behavior is preserved. The patch addresses the immediate correctness issues, but explicit testing of per-repository behavior (especially in `index-pack` and `revision`) and repository-less invocations remains unconfirmed. Junio has requested confirmation that the patch has been tested against the current `seen` and `next` branches to check for conflicts. The v3 patch will need verification that `index-pack` behaves correctly in both repository-bound and repository-less contexts, and that per-repository `fetch_if_missing` behavior remains consistent.

Open questions and loose ends

Junio’s review in v2 outlined three approaches, and the author has adopted the first (restricting `index-pack` to repository-bound operation) as a pragmatic solution. The other two approaches—a fallback to `the_repository` or a new global "basic settings" structure—remain on the table for future discussion.
- **Testing**: The author has not provided explicit confirmation that the patch was tested with repositories other than `the_repository` or in repository-less contexts. While the fixes address the raised concerns, the absence of new test coverage or multi-repository verification leaves a risk of undetected regressions. Junio has explicitly requested confirmation that the patch has been tested against the current `seen` and `next` branches to check for conflicts. The next iteration will need to include tests for the new repository-bound behavior of `index-pack` and per-repository `fetch_if_missing` consistency.

Junio’s review now challenges whether the flag belongs in `struct repository` at all, making this a more fundamental point of discussion. The v3 patch resolves the immediate crash risk and repository-less behavior change, but the long-term architectural direction remains open.

The author must rebase the patch to resolve this conflict before it can be queued. The author proposes to wait for `cf1687a41c` to settle, but Junio’s feedback indicates the `setup.c` inconsistency is the more immediate blocker.
