This is the v5 iteration of a two-patch series that makes submodule fetch errors configurable, targeting the fetch and submodule subsystems. The series introduces `fetch.submoduleErrors` (config) and `--submodule-errors=(fail|warn)` (CLI) to let users choose whether `git fetch --recurse-submodules` should fail hard or merely warn when a submodule’s gitlink points to an unreachable OID. The default remains `fail` for backwards compatibility.

v5 addresses all remaining feedback from Junio C Hamano and Ramsay Jones: config values are now case-sensitive (using `strcmp` instead of `strcasecmp`), the parsing and formatting logic is centralized in a shared name array, and the test suite replaces raw `grep` with `test_grep` for portability. The series also credits Jean-Noël Avila for documentation fixes in v2. No new design objections have been raised, and the implementation is now mechanically cleaner while preserving the behavior introduced in earlier versions.

Patch 1 fixes a pre-existing logic flaw in `submodule.c` where phase-1 fetch failures were recorded prematurely, before phase-2 OID-based retries could run. This refactoring ensures errors are only recorded after all retry attempts fail, which is necessary for the configurable policy in Patch 2 to work correctly. The fix also ensures that phase-1 failures are reported even when the gitlinked commits are already present locally, and routes all submodule fetch errors through `record_fetch_error()` for consistent reporting and policy enforcement.

Patch 2 adds the user-facing controls, including forwarding the resolved setting (whether from CLI or config) to child fetches (`--all`, `--multiple`, nested recursion) when explicitly set. The implementation touches `submodule.c`, `builtin/fetch.c`, documentation files, and adds comprehensive test coverage in `t/t5526-fetch-submodules.sh`. The commit messages are clear, the rationale is well-explained, and the changes are narrowly scoped to the submodule fetch error-handling path.

The series is now technically complete and addresses all prior review feedback. It solves a real workflow pain point—upstream topic branches that are still in flux—without introducing broader risks. The implementation appears robust, the test coverage is thorough, and the changes are uncontroversial. This looks ready for `next` once Junio queues it.
