This is the **final patch (11/13)** in the **GSoC v18 series** that implements the `remote-object-info` command for `git cat-file --batch-command`. The series is now **queued for merging to `next`** after resolving all prior technical and security concerns.

This patch adds the **client-side integration** of the `remote-object-info` command, allowing users to query object metadata (currently only size) from remote repositories without downloading the full objects. The implementation supports multiple object IDs per request to minimize network overhead, and works with all smart transports (`git://`, `file://`, `http://`). Key technical details include:

- **Command syntax**: `remote-object-info <remote> <oid>...` (supports multiple OIDs per line)
- **Protocol**: Requires protocol v2 and the `object-info` server capability (advertised when `transfer.advertiseobjectinfo` is enabled)
- **Security**: Enforces a 10,000-object batch limit, 8KB URL length limit, and strict input validation (e.g., rejects short OIDs)
- **Format support**: Currently limited to `%(objectname)` and `%(objectsize)` placeholders; other format atoms (e.g., `%(objecttype)`, `%(objectsize:disk)`) are explicitly rejected
- **Buffer mode**: Works with `--buffer` and `-Z` (null-delimited output) options
- **Edge cases**: Handles missing objects gracefully (returns "missing" status) and rejects unsupported protocol versions or malformed OIDs

The patch includes **680 lines of new tests** in `t/t1017-cat-file-remote-object-info.sh`, covering all supported transports, error conditions, and edge cases. The tests verify that objects are *not* downloaded from the remote, and that the command behaves consistently with `info` for local objects where applicable.

This is the **core user-facing feature** of the series, building on the protocol and transport-layer work in earlier patches. The implementation is **functionally complete** for the initial scope (size-only queries), with future expansion (e.g., object type support) explicitly designed for. The patch demonstrates careful attention to security (bounds-checking, dynamic capability validation) and robustness (memory management via `free_object_info_contents()`, stateless RPC design).
