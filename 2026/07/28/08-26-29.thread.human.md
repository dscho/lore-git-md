This thread is about a bug in Git’s rebase cleanup logic: after a successful rebase, the `.git/REBASE_HEAD` file and `REBASE_HEAD` ref are sometimes left behind, which can mislead scripts or commands that check for `REBASE_HEAD` and cause unnecessary force-push warnings. The issue was reported by Long 76, who encountered it during conflict resolution, and later confirmed by Matt Hunter, who found it also occurs after `squash` or `edit` actions in the rebase todo list.

Phillip Wood, a sequencer and rebase expert, has now weighed in, confirming that the leftover `REBASE_HEAD` is indeed a bug. He explains that `REBASE_HEAD` should only exist during active rebase operations—such as when there are conflicts or the editor is open for rewording—and should always be cleaned up after the rebase finishes. The root cause is that the sequencer deletes `REBASE_HEAD` *before* processing each rebase command but fails to remove it after the final command completes. Phillip also clarified why `REBASE_HEAD` is missing when a rebase stops on a `break` command: those states are not considered "conflict" scenarios, so the file is intentionally absent.

The discussion is now focused on fixing the sequencer’s cleanup logic in `sequencer.c` to ensure `REBASE_HEAD` is removed after the final rebase command, regardless of the command type. Matt Hunter’s workaround—checking for `rebase-merge` or `rebase-apply` directories instead of `REBASE_HEAD`—is endorsed as the correct way to detect an in-progress rebase. No patch has been proposed yet, but the problem and expected fix are now well-defined. The thread remains open, awaiting a patch to address the cleanup oversight.
