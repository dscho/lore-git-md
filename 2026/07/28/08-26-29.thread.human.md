This thread is about a bug in Git’s rebase cleanup logic that leaves behind a `.git/REBASE_HEAD` file and ref after a successful rebase, which can mislead scripts and cause unnecessary force-push requirements. The issue was first reported by Long 76, who encountered it during conflict resolution, and later confirmed by Matt Hunter, who noticed it also occurs after `squash`, `edit`, or `reword` commands as the final rebase action. Phillip Wood, a rebase/sequencer expert, identified the root cause: the sequencer removes `REBASE_HEAD` before processing each rebase command but fails to clean it up after the final command completes, regardless of the command type.

The expected behavior is that `REBASE_HEAD` should exist only during active rebase operations (e.g., conflicts or editor open for rewording) and must not persist after rebase completion. The workaround—checking for `rebase-merge` or `rebase-apply` directories instead of `REBASE_HEAD`—has been endorsed by Wood as the correct way to detect an in-progress rebase. No patch has been proposed yet, and the discussion remains focused on confirming the bug and its scope. Long 76’s latest reply clarifies that the issue is unrelated to push semantics or conflict resolution side effects, reinforcing that the leftover file is a distinct bug in the sequencer’s cleanup logic. The thread is now waiting for a fix.
