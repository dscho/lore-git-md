This is a **design discussion follow-up** in the `git rebase --update-refs` symref bugfix thread. Junio C Hamano pushes back on Phillip Wood’s earlier clarification about Git’s permissiveness with HEAD symrefs, questioning whether the low-level flexibility cited (commit e9cc02f0e4) should extend to end-user commands like `git rebase`.

Junio argues that while plumbing commands like `git symbolic-ref` may need to handle broken or edge-case states (e.g., HEAD pointing outside `refs/heads/`), user-facing commands like `git checkout` have long been tightened to prevent such configurations in the first place. He implies that `git rebase`—as a high-level command—should not be burdened with handling these edge cases, and that the current patch’s approach (using `resolved_ref` for HEAD comparison) might be over-engineering for a state Git actively discourages.

The exchange leaves the design question unresolved but sharpens the tension: should the rebase logic assume HEAD always points to a branch (simplifying the code) or robustly handle symrefs to tags/other namespaces (aligning with Git’s low-level flexibility)? This is not a blocker for the v3 series, but it may influence how the author frames the v4 revision—either as a strict bugfix (if the edge case is deemed invalid) or as a robustness improvement (if the permissive behavior is retained). The latent `head_ref` buffer clobbering bug remains unaddressed and is orthogonal to this discussion.
