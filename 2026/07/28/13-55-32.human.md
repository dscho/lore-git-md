This is a follow-up in the ongoing discussion about test failures when `WITH_BREAKING_CHANGES=1` is enabled. Jeff King (Peff) provides a clear explanation for both sets of failures reported earlier: the `t0014-alias.sh` and `t1517-outside-repo.sh` test failures are caused by stale build artifacts left over from previous builds.

Peff explains that the alias-related failures occur because the tests assume certain Git commands (`whatchanged` and `pack-redundant`) are deprecated built-ins, which allows aliasing over them. However, when `WITH_BREAKING_CHANGES=1` is enabled, these commands are no longer treated as special built-ins, and any leftover executables (like `git-whatchanged`) from prior builds are treated as external commands, which Git does not allow to be aliased. This creates a mismatch between the test's expectations and the actual behavior.

For the `t1517-outside-repo.sh` failures, Peff confirms Phillip Wood's hypothesis: stale executables from previous builds interfere with the test, as those executables are no longer built when `WITH_BREAKING_CHANGES=1` is enabled. This explains why the failures are environment-specific and do not reproduce in clean builds.

Peff suggests two potential fixes: either remove the problematic test in `t0014-alias.sh` after the breaking changes are fully integrated (since the test will no longer be relevant), or use a test prereq to skip the test when `WITH_BREAKING_CHANGES=1` is detected via `GIT-BUILD-OPTIONS`. The thread remains in the diagnostic phase, but Peff's explanation provides a clear path forward for resolving the issue. The failures appear to be a side effect of the build system rather than a regression in Git's logic, so the fix should be straightforward once the right approach is agreed upon.
