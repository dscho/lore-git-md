This is a follow-up from Junio C Hamano in the `git stash reword` thread, expanding on his earlier proposal to extend the reflog API. The patch itself remains blocked on the data-loss risk he identified in the current implementation, but this email focuses on the design details of the new API he suggested.

Junio sketches a more complete picture of `refs_reflog_edit_in_bulk()`, a proposed reflog API extension that would allow atomic batch edits to reflog entries. The function would take an array of edit operations (replace, delete, insert) and apply them in a single transaction, eliminating the data-loss window in the current patch. He outlines several edge cases the API must handle: index drift when inserting or deleting entries, multiple edits targeting the same entry, and invalid sequences like deleting an entry before replacing it. These details suggest he has thought through the design carefully and expects the API to be general enough to consolidate other reflog operations (e.g., `reflog delete`, `stash drop`, `stash pop`) in the future.

The email is not a review of the patch itself but a design discussion about the infrastructure needed to implement it safely. Junio’s tone is constructive and forward-looking, treating the API extension as the natural path forward rather than a detour. He also clarifies that multi-line messages should be squashed to single lines, matching the behavior of `git stash push -m`. This is a minor but important UX consistency point.

For a busy reader, the takeaway is that the `git stash reword` feature is not dead — the justification still stands — but it now depends on a non-trivial API extension that will require backend-specific work (files and reftable). The discussion has shifted from "should we do this?" to "how do we do this right?", and Junio’s email provides a clear roadmap for the next steps. If someone picks up this work, the patch is likely to return in a future iteration with a safer implementation.
