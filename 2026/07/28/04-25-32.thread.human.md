This thread is an RFC patch proposing `pack.allowDuplicateObjects`, a configuration and command-line flag to allow Git to accept packfiles containing duplicate objects during `git index-pack`. The feature is opt-in (defaulting to `false`) and targets performance bottlenecks for servers streaming objects from overlapping existing packs. The originating author, friel@openai.com, has received substantive feedback, particularly from Taylor Blau and Junio C Hamano, but the discussion remains unresolved.

Taylor Blau has argued that Git’s internals are already hardened against duplicates via his `tb/pack-with-duplicates` series and proposed a narrower design where `--allow-duplicate-objects` would only relax the duplicate-OID check in `--strict` mode while preserving other validation. However, Junio has consistently pushed back on philosophical grounds, framing the feature as a slippery slope that could undermine repository integrity. In his latest reply, Junio acknowledges the performance benefits of concatenating packs but insists that any duplicates must be deduplicated *during* `index-pack` rather than stored on disk. He suggests that Git’s longer-term direction should be to reject duplicates in all `index-pack` modes, including shallow and filtered clones, while providing tools to deduplicate packs at the receiving end.

The thread is now at an impasse, with Junio’s suggestion of deduplicating during indexing offering a potential path forward if the author can demonstrate its feasibility. The patch touches `builtin/index-pack.c`, adds a new configuration knob and command-line flag, and includes extensive test coverage, but the design may need refinement to address Junio’s concerns. No prior versions exist, and the series remains under review as an RFC. The key open questions are whether deduplication during indexing is viable, whether the performance benefits justify storing duplicates, and whether Git should eventually reject duplicates in all modes.
