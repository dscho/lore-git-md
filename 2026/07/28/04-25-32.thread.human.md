This thread introduces an RFC patch to add a configuration option (`pack.allowDuplicateObjects`) and command-line flag (`--[no-]allow-duplicate-objects`) to `git index-pack`, allowing Git to accept packfiles containing duplicate objects when explicitly enabled. The feature is motivated by performance optimizations for servers streaming objects from overlapping existing packs, and it defaults to disabled (`false`) while preserving all other validation checks.

The patch has received substantive technical feedback from Taylor Blau, who raised a key design question about whether `--allow-duplicate-objects` should be a strict override of `--strict`/`--verify` or a selective carve-out that disables *only* the duplicate-object check. Taylor also suggested minor refinements to the documentation and tests. The patch is self-contained, touching `builtin/index-pack.c`, documentation, and adding a new test file, with no changes to the on-disk format.

However, Junio C Hamano, the project maintainer, has expressed strong philosophical reservations about the feature. In his reply, Junio frames the patch as a slippery slope that could complicate Git’s internals and undermine repository integrity, citing a past discussion with Shawn Pearce to argue that Git should prioritize early detection and rejection of malformed packfiles. His feedback does not engage with the technical implementation or the specific use case but instead focuses on the broader principle that Git should not accommodate "broken" packfiles, even as an opt-in exception. This suggests the patch faces a high bar for justification, and its future direction is now uncertain. The author will need to address Junio’s philosophical concerns or explore alternative solutions that align with his preference for strict validation.
