This is a follow-up in the ongoing bug report about `git history fixup` corrupting the index in other worktrees. The thread remains focused on diagnosing the problem and exploring potential fixes, with no patch yet proposed.

Toon Claes acknowledges Phillip Wood’s root cause analysis and agrees that the fix will be non-trivial. The discussion centers on two possible approaches: (1) refusing to rewrite branches checked out in other worktrees (the current behavior of `git rebase --update-refs`), or (2) attempting a "best-effort" update of the index and working copy in those worktrees if they are clean. Toon leans toward the latter, calling it a more user-friendly solution that preserves branch relationships.

Phillip also flagged a missing safety mechanism in `git history fixup`: unlike `git rebase`, it lacks protection against concurrent rewrites of the same branch from different worktrees. Toon notes that implementing this will require accounting for all ways a branch can be checked out, referencing a prior patch that could serve as a foundation.

The conversation is constructive and pragmatic, with both participants drawing on prior work in the rebase subsystem. The next step is likely a patch series that addresses both the immediate index corruption and the concurrent rewrite safety gap. Until then, users should avoid running `git history fixup` in repositories with multiple worktrees.
