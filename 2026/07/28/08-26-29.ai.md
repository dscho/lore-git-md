This is a bug report about a leftover `REBASE_HEAD` file after a successful rebase.

The reporter describes a specific scenario: after rebasing a feature branch onto `master` (where the feature branch has modified files that require conflict resolution), the `.git/REBASE_HEAD` file and the `REBASE_HEAD` ref persist even after the rebase completes successfully. Normally, these should be cleaned up once the rebase finishes. The reporter notes that this causes issues when pushing, as a force push (`git push --force`) is required, implying the lingering ref might be interfering with Git's state tracking.

The reproduction steps are detailed: initialize a repo, create a feature branch with conflicting changes, rebase onto `master`, resolve conflicts using `git mergetool`, continue the rebase, and then observe that `git rev-parse REBASE_HEAD` still returns a value. The reporter uses Git 2.54.0 on Kubuntu 24.04 and provides their `.gitconfig` (though it’s unlikely to be directly relevant to the issue).

No prior discussion or patches are referenced, and this appears to be a standalone report rather than part of an ongoing thread. The issue touches the rebase/sequencer subsystem, specifically how Git cleans up temporary state files after a rebase completes. If confirmed, this would be a correctness bug, as lingering state files could mislead other Git commands or scripts that check for `REBASE_HEAD`.
