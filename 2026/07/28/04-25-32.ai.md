This is an RFC patch introducing a new configuration option `pack.allowDuplicateObjects` and a corresponding command-line flag `--[no-]allow-duplicate-objects` for `git index-pack`. The patch targets the packfile handling subsystem and is motivated by a practical problem: servers that stream objects from overlapping existing packs may produce packs containing duplicate objects, which Git currently rejects during strict validation (e.g., in full clones). The patch allows clients to opt into accepting such packs while preserving all other validation checks.

The patch is well-structured and thoroughly tested. It adds a new configuration knob (`pack.allowDuplicateObjects`, defaulting to `false`), a command-line override (`--[no-]allow-duplicate-objects`), and updates the documentation for both `git-index-pack` and `config/pack`. The implementation preserves backward compatibility: explicit `--strict` or `--verify` flags continue to reject duplicates regardless of configuration, and the default behavior remains unchanged. The test suite (`t5308-pack-detect-duplicates.sh`) is extensive, covering edge cases like configuration overrides, connectivity checks, object validation, and integration with `git clone`.

The patch builds on an existing topic (`tb/pack-with-duplicates`) and is clearly motivated by real-world use cases where streaming packs from overlapping sources is more efficient than deduplicating at request time. The commit message is detailed and explains the trade-offs (memory/latency vs. correctness) and the rationale for making this opt-in. The code itself is clean, with clear separation between the new flag handling and existing strictness logic.

This is a niche but well-justified feature that addresses a specific performance bottleneck for servers that stream packs. The implementation is conservative (opt-in, preserves all other checks) and unlikely to be controversial. The patch is ready for substantive review, though the RFC tag suggests the author is still seeking feedback on the approach. Key technical details for follow-up discussion:
