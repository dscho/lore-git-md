This is a **substantive review** of the RFC patch introducing `pack.allowDuplicateObjects` and `--[no-]allow-duplicate-objects` for `git index-pack`. The review comes from Taylor Blau, a key contributor with deep expertise in the pack subsystem, and it engages directly with the patch’s design and implementation.

The core discussion revolves around **whether the new flag should be a strict override (current design) or a carve-out from `--strict`**. Taylor questions the current approach, where `--allow-duplicate-objects` is incompatible with `--strict`/`--verify`, and suggests an alternative: allowing the flag to selectively disable *only* the duplicate-object check while preserving all other strict validation (e.g., connectivity, object integrity). This would better serve use cases like `git clone`, where users might want to accept duplicates but still enforce other safety checks. The review includes specific code suggestions (e.g., using `die_for_incompatible_opt2`) and notes that the current tri-state enum (`DUPLICATE_OBJECTS_REJECT`, `DUPLICATE_OBJECTS_ALLOW_CONFIG`, `DUPLICATE_OBJECTS_ALLOW_OPTION`) exists primarily to handle this incompatibility.

Taylor also raises **minor documentation and test concerns**:
- The phrase *"while checking that the pack is self-contained and connected"* in the config documentation may be misleading, as these checks are only performed when `--check-self-contained-and-connected` is explicitly passed.
- The example in the config docs (`git clone -c pack.allowDuplicateObjects`) might be better suited for the `git-clone` man page.
- The test suite (`t5308-pack-detect-duplicates.sh`) is thorough but could potentially be streamlined to reduce redundancy while maintaining coverage.

The review is **constructive and forward-looking**, noting that while the patch is motivated by out-of-tree optimizations (e.g., concatenating packs), similar optimizations could eventually be adopted in Git’s own `upload-pack`. No fundamental objections are raised, but the design question about `--strict` interaction is a key point for the author to address in a v2. The patch remains **well-motivated and technically sound**, with the review focusing on refining its interface rather than questioning its necessity.
