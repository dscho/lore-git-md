This thread introduces `git add --resolved`, a new option that stages only files whose conflict markers have been removed, helping users resolve merge conflicts without accidentally staging unrelated local changes. The series, now at version 3, is authored by Junio C Hamano and is under active review. It consolidates duplicate conflict-marker detection logic, adds helper functions for index manipulation, and includes a performance tweak for binary files.

The core design of `--resolved` has sparked debate. Junio defends it as a monolithic, workflow-oriented operation consistent with existing Git commands like `git am --resolved`, while Michael Montalbo proposes a more flexible `--unmerged` selector with explicit policy flags for conflict markers. This discussion remains unresolved but is not blocking progress. The series has addressed all prior technical feedback, including a logic error in option incompatibility handling, a missing test script entry, and portability fixes. Jeff King (Peff) raised a usability concern that `--resolved` might create a false sense of completeness by staging only conflict-resolved files while ignoring related changes (e.g., updates to callers of a modified function). Junio has clarified that Git’s merge machinery already enforces constraints to mitigate this risk, citing a test case (`t6423`) as evidence, though the concern remains unaddressed in documentation or command output.

The series touches several subsystems, including `merge-ll.c` (conflict-marker helpers), `read-cache.c` (index manipulation), and `builtin/add.c` (option implementation). It introduces no on-disk format changes but adds a new test script (`t/t2207-add-resolved.sh`) and updates `t/meson.build`. The implementation handles edge cases like binary files and deletions by staging them without marker checks, while partially resolved conflicts trigger an error listing unresolved paths. The series is technically complete and ready for integration, pending minor documentation tweaks to clarify the feature’s limitations.
