This thread introduces `git add --resolved`, a new option to stage only files whose conflict markers have been removed after a merge conflict. The feature is now in its third iteration (v3), with Junio C Hamano as the author. The series consolidates duplicate conflict-marker detection logic, adds helper functions for index manipulation, and includes a performance tweak for binary files.

The core design of `--resolved` has sparked debate. Junio defends it as a monolithic, workflow-oriented command aligned with Git’s existing conventions (e.g., `git am --resolved`), while Michael Montalbo argues for a more flexible `--unmerged` selector with explicit policy flags for conflict markers. This discussion remains unresolved but is not blocking progress. Jeff King (Peff) raised a usability concern: `--resolved` might create a false sense of completeness by staging only files with resolved conflict markers while ignoring related changes (e.g., updates to callers of a modified function). Junio responded that Git’s merge machinery already prevents this scenario by refusing to operate on paths with local modifications, though he acknowledges this relies on newer merge code paths. The risk is now framed as a documentation or warning opportunity rather than a design flaw.

Technically, the series is complete and addresses all prior feedback. It introduces helpers like `is_conflict_marker_line()` and `remove_file_from_index_with_flags()`, touches multiple subsystems (merge logic, index handling, documentation), and includes a new test script (`t/t2207-add-resolved.sh`). The v3 update fixed a test-script portability issue and added a performance optimization for binary files. No major technical objections remain, and the series appears ready for merging pending minor documentation tweaks to clarify the feature’s limitations. Key participants include Junio (author), Michael Montalbo (reviewer), and Peff (reviewer), with no other substantive feedback since v2.
