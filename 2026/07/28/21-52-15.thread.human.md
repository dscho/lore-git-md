This thread introduces `git add --resolved`, a new option proposed by Junio C Hamano that stages only paths where conflict markers have been removed, helping users avoid accidentally staging unrelated local changes during merge conflict resolution. The series is currently under review in its first version (v1), consisting of four patches: two preparatory refactorings, the core feature implementation, and a minor whitespace cleanup.

The first patch, now posted, consolidates duplicate conflict-marker detection logic from `diff.c` and `rerere.c` into a single helper function in `merge-ll.c`. This refactoring enforces a stricter rule requiring a space after conflict markers (e.g., `<<<<<<< `), aligning with Git's conflict output format. While this change isn't user-visible, it establishes the foundation for the `--resolved` option by centralizing the logic that identifies resolved conflicts. The patch reduces code duplication while maintaining existing behavior for all callers.

No substantive reviews have been posted yet, leaving several open questions about edge cases: how the feature handles partially resolved conflicts, its interaction with `--patch` mode, and its behavior when no conflicts exist. The series touches several core files (`merge-ll.c`, `read-cache.c`, `builtin/add.c`) and introduces a new test script (`t/t2207-add-resolved.sh`), but makes no on-disk format changes. The implementation appears technically sound but awaits community feedback on both the refactoring and the proposed user interface.
