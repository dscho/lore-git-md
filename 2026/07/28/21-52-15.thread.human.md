This thread introduces `git add --resolved`, a new option to stage only files whose conflict markers have been removed after a merge. Junio Hamano posted the third version of the four-patch series, which consolidates duplicate conflict-marker detection logic, adds helper functions for index manipulation, and includes a performance tweak for binary files. The series is technically complete and addresses all prior feedback, including a portability fix for the test script and a logic correction in option incompatibility handling.

The core debate centers on the design of `--resolved`: Junio defends it as a monolithic operation that stages only when *all* conflict markers are removed, while Michael Montalbo argues for incremental staging via a `--skip-conflict-markers` flag. Jeff King raised a usability concern about the command potentially creating a false sense of completeness by ignoring related changes outside conflicted files, though Junio countered that Git’s existing merge behavior mitigates this risk. A correctness issue in the binary-file check was also discussed, with Junio opting to retain the current logic despite Montalbo’s proposed fix, prioritizing early failure over false negatives. Junio additionally flagged a broader architectural question—whether Git’s attribute system should influence conflict-marker detection—but left it unresolved for future discussion.

The series is now ready for integration pending minor clarifications, though the design debate and usability concerns remain open. Key technical details include new helpers like `is_conflict_marker_line()` and `remove_file_from_index_with_flags()`, and a new test script (`t/t2207-add-resolved.sh`) covering edge cases like deletions and pathspecs. No on-disk format changes are introduced.
