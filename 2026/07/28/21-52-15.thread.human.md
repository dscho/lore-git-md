The `git add --resolved` feature is taking shape in its second iteration, posted by Junio C Hamano. The goal is simple: let users stage only those files whose conflict markers have been fully removed after a merge, avoiding accidental staging of unrelated local changes. The series is now complete, with four patches covering refactoring, new helpers, and the core feature.

The first patch is a quiet but necessary cleanup—realigning the indentation of `skip_submodule()` in `read-cache.c`, which had been misaligned since a February 2026 commit. It’s purely mechanical, no logic changes, and sets the stage for the rest of the series. Michael Montalbo’s earlier review caught two real issues in the v1 series: a logic error in option incompatibility handling and a missing test script entry in the build system. Both are now fixed in v2, along with a small performance tweak that skips binary files early when scanning for conflict markers.

The core of the feature is the new `--resolved` option, which scans the index for unmerged paths, checks each for remaining conflict markers, and stages only those that are fully resolved. Binary files and deletions are staged without marker checks. The implementation consolidates duplicate conflict-marker detection logic into a single helper, adds a new index-removal function with support for `--dry-run` and `--verbose`, and includes a new test script covering edge cases like partially resolved conflicts and option incompatibility. So far, only Michael has weighed in with substantive feedback, and his concerns are now addressed. The series is under active review, with no objections or conditional approvals recorded yet.
