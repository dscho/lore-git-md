This thread introduces `git add --resolved`, a new option that stages only paths whose conflict markers have been removed, allowing users to resolve merge conflicts without accidentally staging unrelated local changes. The series, now at version 3, is authored by Junio C Hamano and is under active review.

The implementation consolidates duplicate conflict-marker detection logic into a new helper, `is_conflict_marker_line()`, and introduces `remove_file_from_index_with_flags()` to support dry-run and verbose modes for index removals. The `--resolved` option itself scans the index for unmerged paths, checks for remaining conflict markers (with an early exit for binary files), and stages resolved paths or aborts with an error listing unresolved ones. The series also includes a targeted performance optimization for binary files and a portability fix for the test script.

All prior technical feedback from Michael Montalbo—including a logic error in option incompatibility handling and a missing test script entry—has been addressed. The remaining discussion centers on a conceptual disagreement over the user-facing interface: Junio defends `--resolved` as a monolithic, workflow-oriented operation consistent with Git’s existing conventions (e.g., `git am --resolved`), while Montalbo proposes a more flexible `--unmerged` selector with explicit policy flags for conflict markers. No consensus has been reached, but the series is technically complete and ready for further review. The final patch in v3 implements the core logic and adds comprehensive test coverage.
