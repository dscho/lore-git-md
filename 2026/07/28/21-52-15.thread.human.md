The `git add --resolved` feature, introduced by Junio C Hamano, aims to streamline conflict resolution by staging only paths where conflict markers have been removed. The initial v1 series—four patches covering refactoring, infrastructure, the core feature, and a whitespace cleanup—is now under review after Michael Montalbo raised two targeted but important issues.

Montalbo’s review highlights a logic error in the option-compatibility check: the new `die_for_incompatible_opt3()` function incorrectly flags `--resolved` as incompatible with `--no-all` or `--ignore-removal`, even though these combinations were valid before. The fix is straightforward—adjust the condition to check for explicit `--all` activation rather than treating its absence as a conflict. He also caught a build-system oversight: the new test script `t/t2207-add-resolved.sh` is missing from `t/meson.build`, which would prevent it from running in CI. Both issues are actionable and likely to be addressed in a v2.

The feature itself remains well-structured, with clear separation between refactoring (consolidating conflict-marker detection logic) and the new functionality. The `--resolved` option scans the index for unmerged paths, stages those without conflict markers, and errors out if any remain unresolved—handling edge cases like binary files and deletions gracefully. No substantive reviews beyond Montalbo’s have appeared yet, so the series is still in early technical scrutiny. The next steps will likely focus on fixing the option-parsing bug and ensuring the test suite is properly integrated.
