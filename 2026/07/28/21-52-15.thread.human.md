This thread introduces `git add --resolved`, a new option that stages only files whose conflict markers have been fully removed, helping users resolve merge conflicts without accidentally staging unrelated changes. The series, now at v3, consolidates conflict-marker detection logic, adds index-removal helpers, and includes a performance tweak for binary files. Junio C Hamano is the author, and the feature is under active review.

The core debate centers on whether `--resolved` should remain a monolithic operation (staging only when *all* conflict markers are gone, as Junio prefers) or allow incremental staging of resolved files via a `--skip-conflict-markers` flag (proposed by Michael Montalbo). Junio argues the current design aligns with Git’s conventions and user intent, while Montalbo emphasizes flexibility for complex merges. A usability concern from Jeff King (Peff) highlights a potential "false sense of completeness" risk—staging resolved files while ignoring related changes—but Junio counters that Git’s existing merge constraints mitigate this. The series is technically complete, with all prior feedback addressed, though the binary-file handling in `has_conflict_markers()` remains contentious. Junio rejected Montalbo’s earlier fix to prioritize the binary check, favoring false positives over false negatives, but Montalbo now proposes a more deterministic alternative: skipping conflict-marker detection for files handled by merge drivers (e.g., `binary`, `union`) that cannot emit markers. This could replace the current heuristic but introduces new complexity.

Open questions include whether Git’s attribute system should influence conflict-marker detection (e.g., marking files as "never conflicted") and how to document the edge case Peff raised. The series is otherwise ready for integration, pending minor clarifications.
