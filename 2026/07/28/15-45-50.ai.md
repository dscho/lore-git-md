This is the v8 iteration of the patch series introducing a `--linearize` option to `git replay`, which flattens merge commits into a linear history. The series is now **technically complete** and addresses the last major design question from v7: **disallowing `--linearize` with multiple revision ranges or `--contained`**, resolving the "multi-branch ambiguity" that had blocked the series in `next`.

The core change in v8 is a **restriction on `--linearize` usage**: it can no longer be combined with multiple positive revisions (e.g., `topic2 topic3 topic4`) or with `--contained`. This aligns with Elijah Newren’s "minimal fix" proposal from v7, eliminating emergent reachability issues while preserving the option’s core functionality. The restriction is implemented via a new check in `replay_revisions()` that errors out if `--linearize` is used with more than one ref to update. The commit message and documentation have been updated to reflect this change, and tests verify the new behavior.

The series remains a **three-patch refactoring + feature addition**:
1. **Patch 1/3**: Introduces `put_mapped_commit()` to encapsulate logic for tracking replayed commits (pure refactoring).
2. **Patch 2/3**: Moves replay base resolution out of `pick_regular_commit()` (pure refactoring).
3. **Patch 3/3**: Implements `--linearize`, now with the multi-range restriction and updated documentation.

**Key technical details**:
- **New restrictions**: `--linearize` cannot be used with multiple revision ranges or `--contained` (error messages added).
- **Behavior**: Merge commits are dropped, and subsequent commits are reparented onto the last non-merge commit, ensuring a single linear history.
- **Compatibility**: `--linearize` can still be combined with `--revert` (mutual exclusivity removed in v7).
- **Files touched**: `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, and `t/t3650-replay-basics.sh`.
- **Test coverage**: New tests verify the multi-range and `--contained` restrictions, alongside existing coverage for edge cases (e.g., replaying to root, `--advance` compatibility).

**Design rationale**:
The series diverges from `git rebase --no-rebase-merges` by design, as `--linearize` offers a predictable, all-or-nothing flattening behavior. The commit message justifies this divergence, arguing that mirroring `git rebase`'s `--rebase-merges=<mode>` syntax would repeat past UX mistakes. The restriction to single branches in v8 addresses Elijah’s recoverability concerns while preserving flexibility for future per-branch linearization.

**Status**:
The series is **ready for review** and should unblock the hold in `next`. The only remaining open question is whether `--linearize` should eventually support per-branch linearization (e.g., via `--ref` syntax), but this is now deferred. Potential trivial conflicts with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series are noted.
