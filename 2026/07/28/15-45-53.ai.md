This is the third and final patch in the v8 series introducing the `--linearize` option to `git replay`. The patch implements the core functionality: when `--linearize` is active, merge commits are dropped and all replayed commits are flattened into a single linear history. The patch also enforces the new restriction (introduced in v8) that `--linearize` cannot be used with multiple revision ranges or `--contained`, addressing the "multi-branch ambiguity" that had blocked the series in `next`.

The implementation touches `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, and `t/t3650-replay-basics.sh`. The key changes are:
- A new `linearize` boolean field in `struct replay_revisions_options` (in `replay.h`).
- A check in `replay_revisions()` that errors out if `--linearize` is used with more than one ref to update.
- Logic in the main replay loop (`replay.c`) that skips merge commits when `--linearize` is active, leaving `last_commit` unchanged so that subsequent commits are reparented onto the last non-merge commit.
- Updated documentation and tests covering the new behavior, including the multi-range and `--contained` restrictions, edge cases (replaying to root, `--advance` compatibility), and the behavioral difference from `git rebase --no-rebase-merges`.

The commit message justifies the design choice to diverge from `git rebase`'s `--rebase-merges=<mode>` syntax, arguing that `--linearize` better describes the predictable, all-or-nothing flattening behavior. The restriction to single branches in v8 resolves Elijah Newren’s recoverability concerns while preserving flexibility for future per-branch linearization.

The patch is technically complete and addresses all prior feedback. The only remaining open question is whether `--linearize` should eventually support per-branch linearization (e.g., via `--ref` syntax), but this is now deferred. The series is ready for review and should unblock the hold in `next`. Potential trivial conflicts with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series are noted.
