This is a surface-level review of the second patch in K Jayatheerth’s v3 series adding path-related keys to `git repo info`. The patch introduces `path.superproject-working-tree.absolute` and `path.superproject-working-tree.relative` to expose the superproject’s working tree path when the current repository is a submodule.

Justin Tobler’s review focuses on two minor mechanical issues already noted in patch 1/7: the redundant `strbuf_addstr(buf, "")` calls in the getter functions, and the same pattern in the test helper. These are cleanliness nits and do not affect functionality. He also raises a naming question—whether "superproject-working-tree" is too verbose and suggests "superproject-root" as an alternative—but defers to consistency with `git rev-parse --show-superproject-working-tree`.

The patch itself is mechanically clean and aligns with the series’ design: it uses `get_superproject_working_tree()` and `format_path()` with `PATH_FORMAT_CANONICAL` or `PATH_FORMAT_RELATIVE`, returning an empty string when not inside a submodule. Test coverage is thorough, verifying both absolute and relative paths in submodule and non-submodule contexts. The only open question is the key naming, but the current choice is consistent with existing Git terminology. No substantive technical concerns are raised; the patch is ready for broader review. For future reference, note the new keys (`path.superproject-working-tree.absolute`, `path.superproject-working-tree.relative`) and their reliance on `get_superproject_working_tree()`.
