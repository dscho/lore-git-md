This is a **build system / test infrastructure** follow-up in the `WITH_BREAKING_CHANGES` thread. Jeff King (Peff) provides a substantive explanation for both sets of test failures reported by brian m. carlson: stale build artifacts (`git-whatchanged` and `git-pack-redundant` executables) left over from prior builds. These executables are no longer built when `WITH_BREAKING_CHANGES=1` is enabled, but if they remain in the build directory, the test suite treats them as external commands, triggering alias-loop detection logic that causes `t0014-alias.sh` to fail. The same stale artifacts also explain the `t1517-outside-repo.sh` failures, as the tests expect those commands to be unavailable.

Peff’s analysis is thorough and actionable. He identifies the exact mechanism (stale `git-whatchanged` and `git-pack-redundant` binaries) and the behavioral change (`WITH_BREAKING_CHANGES` removes special handling for deprecated builtins, making them subject to normal alias rules). He also notes that the `t0014` test covering this edge case should eventually be removed once the breaking changes land, but in the interim, the test could be skipped via a prereq tied to the `GIT-BUILD-OPTIONS` environment. This shifts the discussion from "why is this failing?" to "how should we handle the limbo state before Git 3.0?"

The thread is now in a solution-oriented phase. The next steps are likely to be: (1) confirming that a clean build (`make clean` or `git clean -xdf`) resolves the failures, (2) deciding whether to add a prereq to skip the affected tests when `WITH_BREAKING_CHANGES=1`, and (3) ensuring the CI job for this configuration includes a clean build step. The explanation also clarifies that the failures are not regressions in Git’s logic but artifacts of the build system’s dependency tracking, which is a low-risk issue for the upcoming Git 3.0 release.
