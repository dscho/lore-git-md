This is the second patch in Jeff King’s two-patch series fixing the `t0014-alias.sh` test failures that appear when `WITH_BREAKING_CHANGES=1` is enabled. The patch replaces the hard-coded list of deprecated commands (`whatchanged` and `pack-redundant`) with a dynamic list generated by `git --list-cmds=deprecated`. If no deprecated commands are available, the tests that rely on them are skipped via a new `HAVE_DEPRECATED` prereq. This makes the test resilient to both future removals of deprecated commands (e.g., in Git 3.0) and to stale build artifacts that can trigger false positives in CI or local testing environments.

The change is confined to `t/t0014-alias.sh` and does not touch core Git logic or the build system. It directly addresses the root cause identified in the thread: stale `git-whatchanged` and `git-pack-redundant` executables left over from prior builds, which the test suite treats as external commands, triggering alias-loop detection logic. By generating the list dynamically, the patch ensures the test remains accurate and maintainable as the set of deprecated commands evolves. The prereq-based skipping is a pragmatic solution for the "limbo state" of `WITH_BREAKING_CHANGES`, where deprecated commands are no longer built but may still linger in the build directory.

The patch is well-scoped and unlikely to be controversial. It complements the first patch (which refactored the test to use variables for deprecated command names) and completes the fix for the `t0014` failures. The `t1517-outside-repo.sh` failures, also caused by stale build artifacts, remain unaddressed but are acknowledged as a separate issue. Peff suggests generating that test’s command list from the Makefile as a potential follow-up, but this patch does not attempt to solve it. The series as a whole is motivated by the need to prevent false positives in environments where `WITH_BREAKING_CHANGES` is used, a configuration expected to see increased adoption as contributors prepare for Git 3.0.
