Subject: [PATCH 0/4] git add --resolved
Series version: v3 (refactoring, feature addition, bugfix, performance tweak)
Originating author: Junio C Hamano
Thread type: patch series (feature addition)

Core problem or goal
Introduce a `git add --resolved` option that stages only paths whose conflict markers have been removed, allowing users to resolve merge conflicts without accidentally staging unrelated local changes. The series consolidates duplicate conflict-marker detection logic, adds helpers for index removal with flags, and includes a targeted performance optimization for binary files. The conceptual design of the option remains contested: Junio defends `--resolved` as a monolithic, workflow-oriented operation that stages only when *all* conflict markers are removed, while Michael Montalbo proposes allowing incremental staging of resolved files (those without conflict markers) via a `--skip-conflict-markers` flag, enabling users to stage a partial set of resolved files without waiting for all conflicts to be addressed. Junio has rejected a correctness fix for the binary-file check in `has_conflict_markers()`, arguing that false positives (incorrectly identifying a binary file as conflicted) are preferable to false negatives (missing actual conflict markers) in this context, and that failing early is better than failing late. A new architectural question has been raised: whether Git’s attribute system should influence the conflict-marker detection logic, allowing users to override the default behavior (e.g., marking certain files as "never conflicted" or "always binary") via `.gitattributes`. This possibility remains open for discussion and could affect the entire series and other conflict-marker consumers (`diff.c`, `rerere.c`). Michael Montalbo has now proposed an alternative approach to the binary-file issue: inspecting the *merge driver* used for the file (e.g., `binary`, `union`) to determine whether conflict-marker detection should be skipped, as these drivers cannot emit conflict markers. This would replace the current `buffer_is_binary()` heuristic with a more deterministic check, though the proposal’s feasibility and implementation details remain open.

Current status
Under review; v3 posted with a test-script portability fix (replacing `git checkout master` with `git checkout @{-1}`). The series is technically complete and addresses all prior review feedback from Michael Montalbo (logic error in option incompatibility handling, missing test script entry in `t/meson.build`, and portability fixes for the test script). The v2 update also added a performance optimization for binary files. The final patch (4/4) implements the user-facing `--resolved` option, completing the feature. Junio has clarified the correct logic for option incompatibility checks in `die_for_incompatible_opt3()` (retaining `0 < addremove_explicit`, not `addremove`), resolving a potential bug in the v2 implementation. He has also identified a broader architectural issue in Git’s option-parsing logic for `git add`, where the presence of command-line flags (e.g., `-A`) is conflated with the behaviors they trigger (e.g., `addremove`), making the logic unnecessarily confusing. This observation is not a blocker for the current series but signals a potential future refactoring to improve maintainability. Jeff King (Peff) raised a usability concern about `--resolved` potentially creating a false sense of completeness by staging only files with resolved conflict markers while ignoring related changes (e.g., updates to callers of a modified function) that are logically part of the merge resolution. Junio has responded that this risk is mitigated by Git’s existing merge behavior, which refuses to operate on paths with local modifications, and cites a test case (`t6423`, "Testcase 11b") that explicitly validates this constraint. The concern remains unresolved in terms of documentation or command output, but the series is otherwise ready for integration pending minor clarifications.

Open questions and loose ends
- Design decision: whether `--resolved` should remain a monolithic operation (staging only when *all* conflict markers are removed, Junio’s position) or support incremental staging of resolved files (those without conflict markers) via a `--skip-conflict-markers` flag (Montalbo’s proposal). Junio argues that the monolithic design aligns with Git’s existing conventions (e.g., `git am --resolved`) and reflects user intent, while Montalbo’s proposal prioritizes flexibility for users who want to stage resolved files incrementally without waiting for all conflicts to be addressed. The discussion remains open, with Montalbo’s clarification shifting the focus from naming to functionality.
- Usability risk: Jeff King (Peff) identified a potential footgun where `--resolved` could create a false sense of completeness by staging only files with resolved conflict markers while ignoring related changes (e.g., updates to callers of a modified function) that are logically part of the merge resolution. Junio has responded that this risk is mitigated by Git’s existing merge behavior (merges refuse to operate on paths with local modifications), and cites test case `t6423` ("Testcase 11b") as validation. The mitigation relies on the merge machinery’s constraint enforcement, which is now supported by concrete evidence (the test case). The concern remains unresolved in terms of documentation or command output; reviewers should verify whether `git-add.txt` or the command’s output adequately addresses this edge case. The test suite (`t/t2207-add-resolved.sh`) does not currently cover scenarios where related changes exist outside conflicted files.
- Edge cases: partially resolved conflicts (some markers remain), interaction with `--patch` mode, behavior when no conflicts exist. The implementation handles partially resolved conflicts by aborting with an error listing unresolved paths, and `--patch` mode is explicitly incompatible (enforced by `die_for_incompatible_opt3()`). Behavior when no conflicts exist is to do nothing (no error, no staging), which is documented in `git-add.txt`.
- Correctness of binary-file handling: Junio has rejected Michael Montalbo’s proposed fix to move the `buffer_is_binary()` check *before* the conflict-marker detection loop in `has_conflict_markers()`, arguing that false positives (incorrectly identifying a binary file as conflicted) are preferable to false negatives (missing actual conflict markers) in this context. The binary check remains *after* the marker check, which could cause false positives in binary files whose first line coincidentally matches a conflict-marker pattern. Junio considers this acceptable and notes that the practical impact is negligible. Montalbo has now proposed an alternative approach: inspecting the *merge driver* used for the file (e.g., `binary`, `union`) to determine whether conflict-marker detection should be skipped, as these drivers cannot emit conflict markers. This would replace the current `buffer_is_binary()` heuristic with a more deterministic check, though the proposal’s feasibility and implementation details remain open. Montalbo acknowledges the potential fragility of this approach if new merge drivers are added in the future.
- Architectural question: whether Git’s attribute system should influence the conflict-marker detection logic, allowing users to override the default behavior (e.g., marking certain files as "never conflicted" or "always binary") via `.gitattributes`. Junio is ambivalent about this possibility, which could affect the entire series and other conflict-marker consumers (`diff.c`, `rerere.c`). No decision has been made; the question is left open for further discussion. This idea is independent of Montalbo’s merge-driver proposal but could interact with it if both were implemented.
- Architectural refactoring opportunity: Git’s option-parsing logic in `git add` conflates the detection of incompatible options with the determination of the program’s operating mode, making the logic unnecessarily confusing. A future refactoring could separate these concerns to improve maintainability and prevent similar bugs. This is not a blocker for the current series but is noted as a potential follow-up effort.

  - Consolidation of conflict-marker logic is complete (no remaining duplicates in the codebase)
  - `remove_file_from_index_with_flags()` behaves correctly with edge-case flag combinations (e.g., both `--dry-run` and `--verbose` set, or path not in index)
  - `--resolved` logic handles deletions and binary files as expected (staged without marker checks, despite the binary-check placement)
  - The two issues raised by Michael Montalbo in v1 are resolved: (1) option incompatibility logic is fixed, and (2) test script is discoverable via Meson
  - The performance tweak in `has_conflict_markers()` does not alter behavior and correctly identifies binary files (with the binary check remaining after the marker check)
  - The test script portability fix (`git checkout @{-1}`) works in all environments (repositories using `main` or other default branch names)
  - Whether incremental staging (via `--skip-conflict-markers`) would better align the interface with user workflows in complex merge scenarios
