Subject: [PATCH 0/4] git add --resolved
Series version: v3 (refactoring, feature addition, bugfix, performance tweak)
Originating author: Junio C Hamano
Thread type: patch series (feature addition)

Core problem or goal
Introduce a `git add --resolved` option that stages only paths whose conflict markers have been removed, allowing users to resolve merge conflicts without accidentally staging unrelated local changes. The series consolidates duplicate conflict-marker detection logic, adds helpers for index removal with flags, and includes a targeted performance optimization for binary files. The conceptual design of the option remains contested: Junio defends `--resolved` as a monolithic, workflow-oriented operation that stages only when *all* conflict markers are removed, while Michael Montalbo proposes allowing incremental staging of resolved files (those without conflict markers) via a `--skip-conflict-markers` flag, enabling users to stage a partial set of resolved files without waiting for all conflicts to be addressed.

Current status
Under review; v3 posted with a test-script portability fix (replacing `git checkout master` with `git checkout @{-1}`). The series is technically complete and addresses all prior review feedback from Michael Montalbo (logic error in option incompatibility handling, missing test script entry in `t/meson.build`, and portability fixes for the test script). The v2 update also added a performance optimization for binary files. The final patch (4/4) implements the user-facing `--resolved` option, completing the feature. Junio has clarified the correct logic for option incompatibility checks in `die_for_incompatible_opt3()` (retaining `0 < addremove_explicit`, not `addremove`), resolving a potential bug in the v2 implementation. He has also identified a broader architectural issue in Git’s option-parsing logic for `git add`, where the presence of command-line flags (e.g., `-A`) is conflated with the behaviors they trigger (e.g., `addremove`), making the logic unnecessarily confusing. This observation is not a blocker for the current series but signals a potential future refactoring to improve maintainability. Jeff King (Peff) raised a usability concern about `--resolved` potentially creating a false sense of completeness by staging only files with resolved conflict markers while ignoring related changes (e.g., updates to callers of a modified function) that are logically part of the merge resolution. Junio has responded that this risk is mitigated by Git’s existing merge behavior, which refuses to operate on paths with local modifications, and cites a test case (`t6423`, "Testcase 11b") that explicitly validates this constraint. The concern remains unresolved in terms of documentation or command output, but the series is otherwise ready for integration pending minor clarifications and a correctness fix to the binary-file check in `has_conflict_markers()`.

Key technical details
- New command-line option: `git add --resolved` (design contested; incremental staging proposed)
- New helpers:
  - `is_conflict_marker_line()` in `merge-ll.c` (header `merge-ll.h`), replacing duplicate implementations in `diff.c` and `rerere.c`; stricter rule requires space after `<<<<<<<` and `>>>>>>>` markers; returns marker character (`<`, `=`, `>`, or `|`) to distinguish marker types
  - `remove_file_from_index_with_flags()` in `read-cache.c` (header `read-cache-ll.h`), supporting `--dry-run` (`ADD_CACHE_PRETEND`) and `--verbose` (`ADD_CACHE_VERBOSE`) flags for index removals. The helper checks flags, prints a removal message if `ADD_CACHE_VERBOSE` is set (regardless of `ADD_CACHE_PRETEND`), and skips the actual index update if `ADD_CACHE_PRETEND` is set. The only caller updated in this patch is `update_callback()`, which previously handled these flags manually.
  - `has_conflict_markers()` in `merge-ll.c`, used by `--resolved` to scan file content for remaining conflict markers; includes an early-exit check for binary files using `buffer_is_binary()`. **Correctness issue**: the current placement of the binary check *after* the conflict-marker detection could cause the function to incorrectly return `has_markers = 1` if the first line of a binary file happens to match the pattern for a conflict marker (e.g., starts with `<<<<<<<`). The fix requires moving the binary check *before* the marker check in the loop.
- Files touched: `merge-ll.c`, `merge-ll.h`, `read-cache.c`, `read-cache-ll.h`, `builtin/add.c`, `diff.c`, `rerere.c`, `Documentation/git-add.txt`, `t/t2207-add-resolved.sh`, `t/meson.build`
- New test script: `t/t2207-add-resolved.sh` covers refusal to stage files with markers, success when all markers are removed, ignoring unconflicted modified files, handling deletions, pathspecs, and option incompatibility with `-u` and `-A`; updated in v3 to use `git checkout @{-1}` instead of `git checkout master` for portability
- Whitespace patch (1/4) reindents `skip_submodule()` in `read-cache.c` to match surrounding style; the misindented block was introduced in commit a16c4a245a (February 2026) when `--force` support for `ignore=all` submodules was added. The patch is purely mechanical (36 lines reindented with hard tabs) and alters no logic or behavior.
- No on-disk format changes; no new config keys or environment variables
- Conflict-marker helper returns marker character to distinguish marker types
- `--resolved` scans the index for unmerged paths, checks each for remaining conflict markers, stages resolved paths, or aborts with an error listing unresolved ones; binary files and deletions are staged as resolved without marker checks
- Bugfix in v2: `die_for_incompatible_opt3()` in `builtin/add.c` now uses `0 < addremove_explicit` (not `0 <= addremove_explicit`); `t/meson.build` updated to include `t/t2207-add-resolved.sh`
- Performance tweak in v2: `has_conflict_markers()` in `merge-ll.c` exits early if `buffer_is_binary()` detects binary content, avoiding unnecessary I/O and processing. **Note**: the binary check must be moved *before* the marker check to avoid false positives.
- Junio’s architectural observation: Git’s option-parsing logic in `git add` conflates the presence of command-line flags (e.g., `-A`) with the behaviors they trigger (e.g., `addremove`), making the logic unnecessarily confusing. A future refactoring could separate the detection of incompatible options (done upfront) from the determination of the program’s operating mode (decided afterward), reducing complexity and preventing similar bugs.

Open questions and loose ends
- Design decision: whether `--resolved` should remain a monolithic operation (staging only when *all* conflict markers are removed, Junio’s position) or support incremental staging of resolved files (those without conflict markers) via a `--skip-conflict-markers` flag (Montalbo’s proposal). Junio argues that the monolithic design aligns with Git’s existing conventions (e.g., `git am --resolved`) and reflects user intent, while Montalbo’s proposal prioritizes flexibility for users who want to stage resolved files incrementally without waiting for all conflicts to be addressed. The discussion remains open, with Montalbo’s clarification shifting the focus from naming to functionality.
- Usability risk: Jeff King (Peff) identified a potential footgun where `--resolved` could create a false sense of completeness by staging only files with resolved conflict markers while ignoring related changes (e.g., updates to callers of a modified function) that are logically part of the merge resolution. Junio has responded that this risk is mitigated by Git’s existing merge behavior (merges refuse to operate on paths with local modifications), and cites test case `t6423` ("Testcase 11b") as validation. The mitigation relies on the merge machinery’s constraint enforcement, which is now supported by concrete evidence (the test case). The concern remains unresolved in terms of documentation or command output; reviewers should verify whether `git-add.txt` or the command’s output adequately addresses this edge case. The test suite (`t/t2207-add-resolved.sh`) does not currently cover scenarios where related changes exist outside conflicted files.
- Edge cases: partially resolved conflicts (some markers remain), interaction with `--patch` mode, behavior when no conflicts exist. The implementation handles partially resolved conflicts by aborting with an error listing unresolved paths, and `--patch` mode is explicitly incompatible (enforced by `die_for_incompatible_opt3()`). Behavior when no conflicts exist is to do nothing (no error, no staging), which is documented in `git-add.txt`.
- Correctness fix required: the `has_conflict_markers()` helper in `merge-ll.c` must move the `buffer_is_binary()` check *before* the conflict-marker detection loop to avoid false positives in binary files whose first line coincidentally matches a conflict-marker pattern. This is a one-line reordering with no performance impact.
- Architectural refactoring opportunity: Git’s option-parsing logic in `git add` conflates the detection of incompatible options with the determination of the program’s operating mode, making the logic unnecessarily confusing. A future refactoring could separate these concerns to improve maintainability and prevent similar bugs. This is not a blocker for the current series but is noted as a potential follow-up effort.
- Reviewers should verify:
  - Stricter conflict-marker rule is correct for all callers (`diff.c`, `rerere.c`, and any future consumers like `diff --check`)
  - Consolidation of conflict-marker logic is complete (no remaining duplicates in the codebase)
  - `remove_file_from_index_with_flags()` behaves correctly with edge-case flag combinations (e.g., both `--dry-run` and `--verbose` set, or path not in index)
  - `--resolved` logic handles deletions and binary files as expected (staged without marker checks)
  - The two issues raised by Michael Montalbo in v1 are resolved: (1) option incompatibility logic is fixed, and (2) test script is discoverable via Meson
  - The performance tweak in `has_conflict_markers()` does not alter behavior and correctly identifies binary files (after the reordering fix)
  - The test script portability fix (`git checkout @{-1}`) works in all environments (repositories using `main` or other default branch names)
  - Whether incremental staging (via `--skip-conflict-markers`) would better align the interface with user workflows in complex merge scenarios
