This is an RFC patch introducing a new configuration option, `pack.allowDuplicateObjects`, that lets Git clients accept packs containing duplicate objects during initial fetch. The patch is motivated by a performance trade-off: streaming existing packs without deduplication avoids the latency and memory overhead of rewriting them at request time, but Git currently rejects such packs in full clones because they violate strict index validation.

The patch adds the config knob and a corresponding `--[no-]allow-duplicate-objects` command-line flag to `git index-pack`. It preserves the default behavior (rejecting duplicates) introduced by commit 68be2fea50 (2011), so existing workflows remain unchanged unless explicitly configured. Strict modes (`--strict` or `--verify`) still reject duplicates regardless of configuration, and the patch includes mutual-exclusion checks to prevent contradictory options.

The implementation touches `builtin/index-pack.c` and adds extensive test coverage in `t/t5308-pack-detect-duplicates.sh`, including scenarios for configuration overrides, connectivity checks, object validation, and integration with `git clone`. The tests demonstrate that allowing duplicates does not relax other safety checks—connectivity and object integrity remain enforced.

This is a well-crafted patch that addresses a real performance bottleneck for servers that stream pre-existing packs. The motivation is clearly explained, the implementation is careful (e.g., preserving strict modes), and the test coverage is thorough. The RFC tag suggests the author is seeking feedback on the approach rather than aiming for immediate merge, but the patch looks production-ready. It’s part of a broader effort (see `tb/pack-with-duplicates`) to optimize pack generation, and the mailing list discussion will likely focus on whether this is the right trade-off for the project.
