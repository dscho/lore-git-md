This is a review reply in the ongoing RFC thread about `pack.allowDuplicateObjects`, a proposed configuration and command-line option to let `git index-pack` accept packs containing duplicate objects. The patch is part of a performance optimization for servers that stream objects from overlapping existing packs.

Taylor Blau’s review is substantive. He raises two main technical points. First, he questions whether the new `--allow-duplicate-objects` flag should be incompatible with `--strict` and `--verify`. Currently the patch makes them mutually exclusive, but Taylor suggests that a more useful design would be to let `--allow-duplicate-objects` carve out only the duplicate-object check from `--strict`, preserving all other strictness behaviors (broken links, missing objects, etc.). This would allow `git clone` to accept packs with duplicates while still enforcing connectivity and object validity. Second, he notes that the documentation could be tightened: the phrase “while checking that the pack is self-contained and connected” is not always true (those checks are only performed when the corresponding flags are given), and the example in the config documentation feels overly specific to `git clone`.

Taylor also offers small mechanical improvements: using the existing `die_for_incompatible_opt2` helper to simplify the option-conflict checks, and suggesting that the test suite could be made more concise while still covering all edge cases. His tone is constructive and he explicitly states that he has not yet studied the tests in detail, leaving room for the author to adjust the implementation before finalizing them.

The review does not object to the overall goal or approach, but it does propose a significant design refinement that would change how the feature interacts with existing strictness flags. If adopted, this change would make the feature more useful in real-world scenarios like `git clone` without sacrificing safety. The patch remains an RFC, so the author is still seeking feedback on the approach.
