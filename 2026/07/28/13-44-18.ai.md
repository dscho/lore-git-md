This is a follow-up in the `git history fixup` worktree corruption bug report. Toon Claes acknowledges Phillip Wood’s root-cause analysis and proposed solution path, agreeing that the issue is well-understood but non-trivial to fix.

The discussion now centers on two implementation choices: whether `git history fixup` should (1) refuse to rewrite branches checked out in other worktrees (the safer default, analogous to `git rebase --update-refs`), or (2) attempt a “best-effort” update of the index and working copy in those worktrees if they are clean (a more user-friendly approach that preserves branch relationships). Toon leans toward the latter, calling it the “friendlier” option.

Toon also flags a missing safety mechanism: `git rebase` prevents concurrent rewrites of the same branch across worktrees, and `git history fixup` lacks this protection. He points to a prior patch ([2]) that enumerates all ways a branch can be checked out, suggesting it could serve as a foundation for implementing both the safety check and the index-update logic.

Key technical details carried forward: the bug affects `git history fixup` (Git 2.46), involves `builtin/history.c`, `worktree.c`, and `read-cache.c`, and requires coordination with the rebase subsystem’s `--update-refs` behavior. No patch has been posted yet; the thread remains in the design-discussion phase.
