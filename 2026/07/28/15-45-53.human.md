This is the final patch in the v8 series introducing the `--linearize` option to `git replay`. The feature flattens merge commits into a linear history, matching the behavior of `git rebase --no-rebase-merges`. The patch is now technically complete and addresses the last major design issue from earlier iterations: it disallows `--linearize` with multiple revision ranges or `--contained`, resolving the "multi-branch ambiguity" that had blocked the series in `next`.

The core change is a new restriction in `replay_revisions()` that errors out if `--linearize` is used with more than one ref to update. This ensures the option only operates on single branches, avoiding emergent reachability issues while preserving its core functionality. The implementation drops merge commits and reparents subsequent commits onto the last non-merge commit, producing a predictable linear history. The patch also updates documentation and adds thorough test coverage, including cases for replaying to the root commit, merge commit rejection, and the new multi-range restriction.

The series diverges from `git rebase`'s `--rebase-merges=<mode>` syntax by design, with the commit message justifying this as a deliberate UX improvement. The restriction to single branches in v8 aligns with Elijah Newren’s "minimal fix" proposal and should unblock the series for graduation to `next`. The only remaining open question is whether `--linearize` should eventually support per-branch linearization (e.g., via `--ref` syntax), but this is deferred. The patch looks well-crafted, with clear documentation and robust test coverage, and appears ready for review.
