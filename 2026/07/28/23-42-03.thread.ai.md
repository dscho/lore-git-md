Thread identity: Performance inquiry regarding `fetch.bundleURI` slowness when cloning the Linux kernel repository. Originating author: Ryszard Knop. Thread type: bug report / performance investigation (no patch series).

Core problem or goal: Determine why `fetch.bundleURI`-based clones of the Linux kernel repository are unexpectedly slow—comparable to or slower than standard full clones—despite the intended performance benefit of using pre-generated bundles. The inquiry now confirms that the primary bottleneck (single-threaded `git index-pack`) was due to misconfiguration, and seeks to explore further optimizations or best practices for bundle-based workflows in CI environments.

Current status: The immediate performance issue is resolved: enabling threaded `index-pack` via `pack.threads=0` halved the clone time (from 4–5 minutes to ~2 minutes). The discussion has shifted from diagnosing the bottleneck to identifying next steps, such as incremental processing, bundle generation parameters (e.g., single-ref bundles, compression levels), or addressing remaining single-threaded sections during packing. No decisions or patch versions yet; the thread remains an open inquiry.

Key technical details:
- **Feature in question**: `fetch.bundleURI`, a Git configuration option enabling pre-generated bundles as a source for clone/fetch operations.
- **Repository**: Linux kernel (large, monolithic repository).
- **Workflow**: Initialize a new repository, configure `fetch.bundleURI` to point to a bundle, then fetch a specific reference (branch, tag, or commit).
- **Resolved bottleneck**: `git index-pack` was running single-threaded due to misconfiguration; enabling `pack.threads=0` (auto-detect cores) restored threaded operation, significantly improving performance.
- **Remaining behavior**: Bundles containing multiple refs force Git to process *all* objects in the pack, not just those reachable from the requested ref. Threading mitigates this impact but does not eliminate it.
- **Configuration**: `pack.threads=0` is now confirmed as critical for performance. The `nr_threads` logic in `index-pack.c` caps threads at 20 (or half the available cores, with a minimum of 3).
- **Symbols**: `nr_threads` in `index-pack.c`, `pack.threads` configuration key.
- **Security consideration**: Bare repositories (a faster but less secure alternative) are discouraged; bundles are the safer solution for distributing pre-generated data.
- **Files/subsystems touched**: `fetch.bundleURI` implementation, `index-pack.c`, packfile handling.

Open questions and loose ends:
- What causes the remaining single-threaded sections during packing, and can they be parallelized?
- Could bundle generation parameters (e.g., single-ref bundles, compression levels) further improve performance for this use case?
- Could the bundle-fetching logic be modified to skip unreachable objects during `index-pack` processing, or is this inherently limited by the packfile format?
- Are there optimizations (e.g., incremental processing) that could address the `index-pack` bottleneck for large bundles?
