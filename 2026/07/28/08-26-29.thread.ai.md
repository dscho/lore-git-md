Thread identity
Subject: Leftover REBASE_HEAD file after successful rebase
Series version: standalone bug report (no patch series)
Originating author: Long 76
Thread type: bug report

Core problem or goal
Git fails to clean up the `.git/REBASE_HEAD` file and the `REBASE_HEAD` ref after a successful rebase in certain scenarios, leaving behind state that can cause spurious force-push requirements and mislead scripts or commands checking for `REBASE_HEAD`. The issue appears tied to specific rebase actions (e.g., `squash`, `edit`, or conflict resolution) rather than all rebases.

Current status
Reported; two data points (Long 76, Matt Hunter) with distinct reproduction scenarios. No patches or maintainer response yet. Subsystem: sequencer (rebase cleanup). The issue is now understood to affect multiple rebase workflows, not just conflict resolution.

Key technical details
- Files touched: `.git/REBASE_HEAD` (leftover), `REBASE_HEAD` ref (leftover)
- Subsystem: sequencer (rebase cleanup logic)
- Old behavior: `REBASE_HEAD` is removed after rebase completes (expected)
- New behavior: `REBASE_HEAD` persists in specific cases:
  - After conflict resolution (Long 76)
  - After `squash` or `edit` as the final todo action (Matt Hunter)
  - Inconsistently missing when rebase stops on a `break` command (Hunter)
- Test coverage: none yet; reproduction steps provided by both reporters
- Workaround: Check for `rebase-merge`/`rebase-apply` directories instead of `REBASE_HEAD` (Hunter)

Open questions and loose ends
- Is this a regression, a design oversight, or intentional (undocumented) behavior?
- Does the issue affect *all* rebase actions, or only specific ones (`squash`, `edit`, conflict resolution)?
- Why is `REBASE_HEAD` missing when rebase stops on a `break` command, despite the rebase still being in progress?
- Are there other sequencer state files (e.g., `rebase-merge/`, `rebase-apply/`) that might also be inconsistently cleaned up?
- Does the reporter’s `.gitconfig` or Git version play a role? (Long 76 claims unlikely; Hunter does not mention config.)
- Has the sequencer’s cleanup logic changed recently, or has this always been the behavior?
