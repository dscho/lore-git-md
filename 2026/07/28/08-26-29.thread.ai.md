Thread identity
Subject: Leftover REBASE_HEAD file after successful rebase
Series version: standalone bug report (no patch series)
Originating author: Long 76
Thread type: bug report

Core problem or goal
Git fails to clean up the `.git/REBASE_HEAD` file and the `REBASE_HEAD` ref after a successful rebase in certain scenarios, leaving behind state that can cause spurious force-push requirements and mislead scripts or commands checking for `REBASE_HEAD`. The issue is confirmed as a bug in the sequencer’s cleanup logic: `REBASE_HEAD` is deleted before processing each rebase command but not after the final command completes, regardless of the command type (squash, edit, reword, etc.). The expected behavior, as clarified by Phillip Wood, is that `REBASE_HEAD` should exist only during active rebase operations (conflicts, editor open for rewording) and must not persist after rebase completion.

Key technical details
- Files touched: `.git/REBASE_HEAD` (leftover), `REBASE_HEAD` ref (leftover)
- Subsystem: sequencer (rebase cleanup logic in `sequencer.c`)
- Old behavior: `REBASE_HEAD` is removed after rebase completes (expected)
- New behavior: `REBASE_HEAD` persists after successful rebase in specific cases:
  - After conflict resolution (Long 76)
  - After `squash`, `edit`, or `reword` as the final todo action (Matt Hunter)
  - The inconsistency around the `break` command (noted by Hunter) remains: `REBASE_HEAD` is intentionally absent when rebase stops on a `break` or failed `exec` command, as these are not considered "conflict" scenarios
- Test coverage: none yet; reproduction steps provided by both reporters
- Workaround: Check for `rebase-merge`/`rebase-apply` directories instead of `REBASE_HEAD` (Hunter, endorsed by Wood)
- Precedent: Other temporary HEAD files (e.g., for `merge` or `cherry-pick`) are reliably cleaned up after operation completion, and `REBASE_HEAD` should behave identically (Long 76, reinforced in this update)
- Documentation reference: `--show-current-patch` implies `REBASE_HEAD` should exist only when a rebase is actively in progress (Long 76)

Open questions and loose ends

- Does the reporter’s `.gitconfig` or Git version play a role? (Long 76 claims unlikely; Hunter does not mention config; no evidence of version-specific behavior yet)

Participant positions
