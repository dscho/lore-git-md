Thread identity
Subject: Leftover REBASE_HEAD file after successful rebase
Series version: standalone bug report (no patch series)
Originating author: Long 76
Thread type: bug report

Core problem or goal
Git fails to clean up the `.git/REBASE_HEAD` file and the `REBASE_HEAD` ref after a successful rebase in certain scenarios, leaving behind state that can cause spurious force-push requirements and mislead scripts or commands checking for `REBASE_HEAD`. The issue is now confirmed as a bug in the sequencer’s cleanup logic: `REBASE_HEAD` is deleted before processing each rebase command but not after the final command completes, regardless of the command type (squash, edit, reword, etc.).

Current status
Reported and diagnosed; two distinct reproduction scenarios (Long 76: conflict resolution; Matt Hunter: squash/edit as final todo action). Phillip Wood (sequencer/rebase domain expert) has weighed in, confirming the bug and clarifying the expected behavior: `REBASE_HEAD` should exist only during active rebase operations (conflicts, editor open for rewording) and must not persist after rebase completion. No patches posted yet; subsystem is the sequencer’s state management in `sequencer.c`.

Key technical details
- Files touched: `.git/REBASE_HEAD` (leftover), `REBASE_HEAD` ref (leftover)
- Subsystem: sequencer (rebase cleanup logic in `sequencer.c`)
- Old behavior: `REBASE_HEAD` is removed after rebase completes (expected)
- New behavior: `REBASE_HEAD` persists after successful rebase in specific cases:
  - After conflict resolution (Long 76)
  - After `squash`, `edit`, or `reword` as the final todo action (Matt Hunter)
- Inconsistency explained: `REBASE_HEAD` is intentionally absent when rebase stops on a `break` or failed `exec` command, as these are not considered "conflict" scenarios
- Test coverage: none yet; reproduction steps provided by both reporters
- Workaround: Check for `rebase-merge`/`rebase-apply` directories instead of `REBASE_HEAD` (Hunter, endorsed by Wood)
