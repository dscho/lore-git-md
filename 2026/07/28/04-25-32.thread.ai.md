Thread identity: RFC patch introducing `pack.allowDuplicateObjects` configuration and `git index-pack --[no-]allow-duplicate-objects` flag, targeting the packfile handling subsystem. Series version: RFC (single patch). Originating author: friel@openai.com. Thread type: RFC patch series.

Core problem or goal: Allow Git to accept packfiles containing duplicate objects during `git index-pack` when explicitly configured, addressing a performance bottleneck for servers streaming objects from overlapping existing packs. The feature is opt-in (default `false`) and preserves all other validation checks, including strict mode rejection of duplicates. The discussion has converged on implementing deduplication *during* `index-pack` (as suggested by Junio C Hamano and endorsed by the author) to prevent duplicates from being stored on disk, rather than allowing them as an opt-in exception. The philosophical debate persists: Junio views duplicate objects as a violation of Git’s integrity guarantees, while Taylor Blau argues they are merely unsupported by current client-side logic and cites existing Git behavior (non-strict `index-pack`, shallow clones, filtered clones) as precedent for accepting them defensively.

Current status: Under review as an RFC with no prior versions or integration status. The patch has received substantive technical feedback and philosophical pushback, with consensus emerging on the technical direction (deduplication during indexing) but no resolution on the philosophical question of whether Git should ever tolerate duplicates. The discussion now centers on implementation details: how to deduplicate objects efficiently during `index-pack`, whether the feature should remain opt-in or become automatic, and how to handle edge cases (e.g., delta resolution, connectivity checks). Taylor Blau’s proposal to relax only the duplicate-OID check in `--strict` mode remains unresolved but may inform the deduplication design.

This would require modifying `index-pack` to deduplicate objects before writing them, potentially making the feature automatic or opt-in via a new flag (e.g., `--deduplicate`). The proposed deduplication approach would address Junio’s philosophical objection but may require significant changes to the patch’s interface and test suite.
- **On-disk format**: No changes; the proposed deduplication approach would ensure no duplicates are written to disk, preserving repository integrity.

Junio’s longer-term direction (rejecting duplicates in *all* `index-pack` modes and providing tools to deduplicate packs at the receiving end) remains unaddressed by the author and Taylor.

Open questions and loose ends:
- **Implementation of deduplication during indexing**: The author has agreed to explore deduplication during `index-pack`, but no concrete mechanism has been proposed. Key questions include:
  - Should deduplication be automatic or opt-in (e.g., via `--deduplicate`)?
  - How to handle edge cases (e.g., delta resolution, connectivity checks, performance overhead)?
  - Whether to preserve the existing configuration knob (`pack.allowDuplicateObjects`) or replace it with a new interface.
- **Design question**: Should the feature remain opt-in (e.g., via `--deduplicate` or a configuration knob) or become automatic during `index-pack`? The latter would align with Junio’s philosophical objection but may require significant changes to the patch’s interface.
- **Longer-term direction**: Junio suggests that Git should eventually reject duplicates in *all* `index-pack` modes and provide tools to deduplicate packs at the receiving end. This would represent a significant shift in Git’s handling of packfiles and may require additional work to diagnose existing duplicates in `fsck`. Neither the author nor Taylor Blau has engaged with this broader direction.
- **Documentation clarifications**: Taylor Blau previously noted that the phrase *"while checking that the pack is self-contained and connected"* in the config documentation may be misleading, as these checks are only performed when `--check-self-contained-and-connected` is explicitly passed. The example in the config docs (`git clone -c pack.allowDuplicateObjects`) might be better suited for the `git-clone` man page. These concerns remain unaddressed.
- **Test refinement**: The test suite is thorough but may need updates to reflect the proposed deduplication behavior, particularly around `--strict` mode and edge cases. No new edge cases are introduced, but redundancy could be streamlined.
- **Server-side optimizations**: The author mentions that duplicates would only occur as a side effect of server-side optimizations (e.g., concatenating packs to avoid deduplication overhead during `upload-pack`). It remains unclear whether such optimizations could eventually be adopted in Git’s own `upload-pack` or whether they would remain out-of-tree. Taylor Blau’s latest reply does not address this.
- **Performance trade-offs**: Taylor Blau suggests that repacking the entire pack (as Friel proposed) might be overkill if only a few duplicates are present, and floats the idea of efficiently removing duplicates during the fetch/clone stream. This aligns with Junio’s preference for deduplication during indexing but leaves the implementation details open.
