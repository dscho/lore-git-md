Thread identity: RFC patch introducing `pack.allowDuplicateObjects` configuration and `--[no-]allow-duplicate-objects` flag for `git index-pack`, targeting the packfile handling subsystem. Series version: RFC (single patch). Originating author: friel@openai.com. Thread type: RFC patch series.

Core problem or goal: Allow Git to accept packfiles containing duplicate objects during `git index-pack` when explicitly configured to do so, addressing a performance bottleneck for servers that stream objects from overlapping existing packs. The feature is opt-in (default `false`) and preserves all other validation checks, including strict mode rejection of duplicates.

Current status: Under review as an RFC. No prior versions or integration status (not in `pu`, `seen`, `next`, or `master`). The patch is self-contained and has received substantive technical feedback from Taylor Blau, focusing on the interaction between `--allow-duplicate-objects` and `--strict`/`--verify`.

Key technical details:
- **Files touched**: `builtin/index-pack.c`, `Documentation/git-index-pack.txt`, `Documentation/config/pack.txt`, `t/t5308-pack-detect-duplicates.sh` (new test file).
- **New symbols**: Configuration knob `pack.allowDuplicateObjects` (boolean, default `false`), command-line flag `--[no-]allow-duplicate-objects` for `git index-pack`.
- **Behavior**: When enabled, `git index-pack` accepts packs with duplicate objects during validation, but the current design makes `--allow-duplicate-objects` incompatible with `--strict`/`--verify`. Connectivity checks and object validation (e.g., `fsck-objects`) remain unchanged. Taylor Blau has suggested revisiting this design to allow the flag to selectively disable *only* the duplicate-object check while preserving other strict validation.
- **On-disk format**: No changes; duplicates are only allowed during pack validation and do not affect delta resolution or storage.
- **Test coverage**: Extensive, including configuration overrides, integration with `git clone` (full, shallow, and partial clones), and edge cases like connectivity checks. Minor suggestions from Taylor Blau include streamlining test redundancy.

Open questions and loose ends:
- **Design question**: Should `--allow-duplicate-objects` be a strict override (current design) or a carve-out from `--strict`? Taylor Blau argues for the latter, proposing that the flag should disable *only* the duplicate-object check while preserving all other strict validation (e.g., connectivity, object integrity). This would better serve use cases like `git clone` where users might want to accept duplicates but still enforce safety checks. The current implementation uses a tri-state enum (`DUPLICATE_OBJECTS_REJECT`, `DUPLICATE_OBJECTS_ALLOW_CONFIG`, `DUPLICATE_OBJECTS_ALLOW_OPTION`) primarily to handle this incompatibility.
- **Documentation clarifications**: Taylor Blau notes that the phrase *"while checking that the pack is self-contained and connected"* in the config documentation may be misleading, as these checks are only performed when `--check-self-contained-and-connected` is explicitly passed. The example in the config docs (`git clone -c pack.allowDuplicateObjects`) might be better suited for the `git-clone` man page.
- **Test refinement**: The test suite is thorough but could be streamlined to reduce redundancy while maintaining coverage.
