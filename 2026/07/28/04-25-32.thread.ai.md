Thread identity: RFC patch introducing `pack.allowDuplicateObjects` configuration and `git index-pack --[no-]allow-duplicate-objects` flag, targeting the packfile handling subsystem. Series version: RFC (single patch). Originating author: friel@openai.com. Thread type: RFC patch series.

Core problem or goal: Allow Git to accept packfiles containing duplicate objects during `git index-pack` when explicitly configured, addressing a performance bottleneck for servers streaming objects from overlapping existing packs. The feature is opt-in (default `false`) and preserves all other validation checks, including strict mode rejection of duplicates. The discussion has evolved to focus on whether Git should ever allow invalid packfiles (even as an opt-in exception), how to design the feature to minimize risks, and whether deduplication should occur during indexing rather than storing duplicates.

Current status: Under review as an RFC with no prior versions or integration status. The patch has received substantive technical feedback and philosophical pushback. The discussion is now centered on Junio C Hamano’s suggestion that duplicates should be deduplicated *during* `index-pack` rather than stored on disk, which would address his philosophical objection but may require a redesign of the feature. Taylor Blau’s proposed narrower design (where `--allow-duplicate-objects` would only relax the duplicate-OID check in `--strict` mode) remains unresolved, as does Junio’s broader concern about allowing "broken" packs to persist.

Key technical details:
- **Files touched**: `builtin/index-pack.c`, `Documentation/git-index-pack.txt`, `Documentation/config/pack.txt`, `t/t5308-pack-detect-duplicates.sh` (new test file).

Taylor Blau proposes replacing this with a more granular override that only disables the duplicate-OID check in `--strict` mode, preserving all other validation. Junio’s latest reply suggests an alternative approach: deduplicating objects during `index-pack` rather than storing them, which would eliminate the need for an opt-in exception entirely.
- **On-disk format**: No changes in the current design; duplicates are only allowed during pack validation and do not affect delta resolution or storage. Junio’s suggestion would require modifying `index-pack` to deduplicate objects before writing them to disk, ensuring no duplicates are stored.
- **Test coverage**: Extensive, including configuration overrides, integration with `git clone` (full, shallow, and partial clones), and edge cases like connectivity checks. The proposed design refinement (deduplication during indexing) may require updates to reflect the new behavior, particularly around how duplicates are handled in `--strict` mode.

Junio’s reply does not reference this work but implies that the longer-term direction should be to reject duplicates in *all* `index-pack` modes (including shallow and filtered clones) while providing tools to deduplicate packs at the receiving end.

Open questions and loose ends:
- **Philosophical objection**: Junio’s feedback remains firm: Git should not allow "broken" packs to persist, even as an opt-in feature. He suggests that the feature should deduplicate objects during `index-pack` rather than storing them, which would address his concerns but may require a redesign. The author must now either propose a deduplication mechanism or justify why storing duplicates is unavoidable for the performance use case.
- **Design question**: Should `--allow-duplicate-objects` be a strict override (current design), a carve-out from `--strict` (Taylor Blau’s proposal), or replaced entirely by a deduplication mechanism during indexing (Junio’s suggestion)? The latter would eliminate the need for an opt-in exception but may complicate the implementation.
- **Longer-term direction**: Junio suggests that Git should eventually reject duplicates in *all* `index-pack` modes (including shallow and filtered clones) and provide tools to deduplicate packs at the receiving end. This would represent a significant shift in Git’s handling of packfiles and may require additional work to diagnose existing duplicates in `fsck`.
