This thread began when brian m. carlson reported test failures in `t0014-alias.sh` and `t1517-outside-repo.sh` when building Git with `WITH_BREAKING_CHANGES=1`, a configuration flag expected to see more use as contributors prepare for Git 3.0. The root cause turned out to be stale build artifacts—`git-whatchanged` and `git-pack-redundant` executables left over from prior builds—which are no longer built when `WITH_BREAKING_CHANGES=1` is enabled but still interfered with test expectations.

Jeff King (Peff) quickly submitted a two-patch series that fixed the `t0014-alias.sh` failures by making the test dynamically generate its list of deprecated commands from `git --list-cmds=deprecated` and skip if fewer than two are available, ensuring resilience against future changes and stale artifacts. Junio C Hamano accepted the approach, and the series is now settled. The `t1517-outside-repo.sh` failures were confirmed to be caused solely by stale build artifacts; a clean build resolves them, and no test changes were needed.

The thread has now concluded with brian’s follow-up patch, which addresses the underlying build system issue: the Makefile was reading `config.mak` too late, so `WITH_BREAKING_CHANGES` had no effect on the initial list of binaries to build. By moving the inclusion of `config.mak` earlier, the patch ensures the configuration flag is respected at the right time, preventing the build system from creating the stale artifacts that triggered the test failures. This is a minimal, targeted fix that fully resolves the issue, leaving no loose ends. CI jobs using this configuration should now pass reliably as long as they include a clean build step.
