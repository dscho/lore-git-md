This thread is about test failures that appear when building Git with `WITH_BREAKING_CHANGES=1`, a configuration flag expected to see more use as the project prepares for Git 3.0. Brian m. carlson reported that two test scripts—`t0014-alias.sh` (tests 4 and 8) and `t1517-outside-repo.sh` (tests 248 and 249)—fail only when this flag is enabled, and only in his specific build environment (which also includes `DEVELOPER=1`, `WITH_RUST=1`, and `CC=clang`). Junio C Hamano confirmed the failures don’t reproduce in his local builds across all integration branches, suggesting the issue might be tied to Brian’s environment rather than the breaking-changes code itself.

Phillip Wood has now proposed a plausible explanation for at least some of the failures: stale build artifacts from a previous build (on a different branch) that are no longer compiled when `WITH_BREAKING_CHANGES=1` is enabled. These leftover binaries could interfere with the `t1517-outside-repo.sh` tests, which would explain why the failures are environment-specific and don’t appear in Junio’s clean builds. This shifts the focus from the breaking-changes logic to the build system’s handling of conditional compilation. If confirmed, the fix might be as simple as ensuring the CI job for this configuration includes a `make clean` step. The alias-related failures in `t0014-alias.sh` remain unexplained, and the thread is still in the diagnostic phase—no patches or test changes have been proposed yet. The next step is likely to test whether cleaning the build directory resolves the issue in Brian’s environment.
