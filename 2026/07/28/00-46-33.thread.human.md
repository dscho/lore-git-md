This thread began when brian m. carlson reported test failures in `t0014-alias.sh` and `t1517-outside-repo.sh` when building Git with `WITH_BREAKING_CHANGES=1`, a configuration flag expected to see more use as the project prepares for Git 3.0. The failures were traced to stale build artifacts—`git-whatchanged` and `git-pack-redundant` executables left over from prior builds—which the flag is meant to exclude. These artifacts triggered alias-loop detection logic in the tests, causing false positives.

Jeff King (Peff) quickly provided a fix for the alias-related failures with a two-patch series that made `t0014-alias.sh` resilient to future changes in the set of deprecated commands. The test now dynamically generates its list of deprecated commands from `git --list-cmds=deprecated` and skips itself if fewer than two are available, avoiding hardcoded assumptions. Meanwhile, the root cause of the stale artifacts—a build system issue where `WITH_BREAKING_CHANGES` was read too late to affect the list of binaries to build—was addressed by brian’s patch, which Junio C Hamano has now merged to `master`. The patch moves the inclusion of `config.mak` earlier in the Makefile, ensuring the flag takes effect before build targets are generated. Junio noted potential fragility in exposing more Makefile symbols to `config.mak` but deemed the change safe enough for integration.

With both fixes in place, the thread is fully resolved. The alias test is now future-proof, and the build system no longer produces stale artifacts when `WITH_BREAKING_CHANGES=1` is enabled. No further changes are expected unless platform-specific regressions emerge. The discussion was technical but collaborative, with Phillip Wood and Junio providing diagnostic input and Peff and brian delivering targeted solutions. The outcome aligns with the project’s goal of supporting the `WITH_BREAKING_CHANGES` configuration as contributors prepare for Git 3.0.
