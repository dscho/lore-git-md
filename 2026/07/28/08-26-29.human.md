This is a bug report about a leftover `REBASE_HEAD` file after a successful rebase.

The author, Long76, describes a scenario where after completing a rebase (including resolving conflicts with `git mergetool` and continuing with `git rebase --continue`), the `.git/REBASE_HEAD` file persists and `git rev-parse REBASE_HEAD` still returns a value. This should not happen — the file should be cleaned up once the rebase is successfully finished.

The report includes detailed reproduction steps: setting up a repository with a `master` branch and a `feature_branch`, making conflicting changes, rebasing, resolving conflicts, and then observing that `REBASE_HEAD` still exists. The author notes this is problematic because it can mislead tools or scripts that check for ongoing operations, and it requires a force push (`git push --force`) to update the branch on the server.

The configuration and environment are clearly stated (Kubuntu 24.04, Git 2.54.0 from the official PPA), and the steps are reproducible. The report is well-structured and includes all necessary details to investigate the issue. This looks like a legitimate bug in the rebase cleanup logic.
