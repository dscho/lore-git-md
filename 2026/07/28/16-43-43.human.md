This is the second patch in the v3 series adding path-related keys to `git repo info`. It introduces `path.superproject-working-tree.absolute` and `path.superproject-working-tree.relative` to expose the superproject’s working tree path when the current repository is a submodule. The patch is mechanically clean and aligns with the series’ established design: it uses `get_superproject_working_tree()` and `format_path()` to return either an absolute or relative path, or an empty string when not inside a submodule.

Justin Tobler’s review here is surface-level, focusing on a minor naming preference. He suggests `superproject-root` as a shorter alternative to `superproject-working-tree` but acknowledges the value of consistency with `git rev-parse --show-superproject-working-tree`. This is a cosmetic concern rather than a technical one; the current name is defensible and matches existing Git terminology. The patch itself is uncontroversial and ready for broader review.

The implementation touches `builtin/repo.c` (adding two getter functions and registering the keys), `Documentation/git-repo.adoc` (documenting the new keys), and `t/t1900-repo-info.sh` (adding thorough tests for both absolute and relative paths, including edge cases). The test coverage is complete, verifying behavior both inside and outside a submodule. No substantive issues have been raised, and the patch follows the same pattern as the rest of the series.

This patch is part of a larger effort to make repository component paths scriptable via `git repo info`. The series as a whole is under active review, with a v4 update planned to address a forward-compatibility issue in the first patch. For now, this patch looks solid and unlikely to generate significant debate.
