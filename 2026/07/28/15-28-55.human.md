This is a follow-up in the ongoing bug report about leftover `REBASE_HEAD` files after a successful rebase. The original reporter, Long 76, reinforces that the behavior is clearly a bug, not an edge case or intentional design. He points out that Git reliably cleans up similar temporary HEAD files for `merge` and `cherry-pick` operations, so `REBASE_HEAD` should behave the same way. He also cites the `--show-current-patch` documentation, which implies `REBASE_HEAD` should exist only when a rebase is actively in progress (e.g., stopped due to conflicts), not after completion.

The email doesn’t introduce new technical details or propose a fix, but it strengthens the case for treating this as a sequencer cleanup bug. Long 76 acknowledges Matt Hunter’s workaround—checking for `rebase-merge` or `rebase-apply` directories instead of `REBASE_HEAD`—but doesn’t engage with the earlier observation that the issue is tied to specific rebase actions like `squash` or `edit`. The thread remains in the exploratory phase, with no patch yet proposed. Phillip Wood, the sequencer expert, has already confirmed the bug, so the next step is likely a fix targeting `sequencer.c`. If you’ve encountered spurious force-push warnings or scripts misled by leftover `REBASE_HEAD` state, this is worth tracking.
