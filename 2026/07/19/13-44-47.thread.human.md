This thread is about a small but long-standing usability gap in Git’s bash completion: when typing `git send-email` followed by a prefix that could match either a revision (like a commit hash) or a patch file (like `0001-fix.patch`), the completion script only offered revisions, not patch files. Yury Norov from NVIDIA proposed a one-patch fix that extends the completion logic to include filesystem paths for patch files alongside the existing revision candidates.

The patch is under review and has drawn feedback from two people so far. Junio C Hamano, the maintainer, acknowledged the bug as a real annoyance and praised the fix, but gave surface-level feedback on test robustness (suggesting the `test_when_finished` block be moved earlier in the test setup) and mildly criticized the use of a purely hexadecimal tag name as ambiguous. D. Ben Knoble, a contributor with expertise in build and completion scripts, provided a substantive review confirming the new helper function follows established patterns, the file-candidate generation is correct, and the Bash 3 compatibility hack remains valid. He also suggested a wording tweak in the commit message for consistency with Git’s documentation style. Knoble’s review ended with a `Reviewed-by`, indicating he considers the patch technically sound.

The patch touches only the bash completion script and its test file, and the change is narrow: it adds a new helper function that appends filesystem candidates to the completion list without disrupting existing revision completion. There are no open technical objections to the core logic, but the patch is still awaiting input from other completion-script experts before it can be queued. The only loose ends are the test robustness tweak Junio requested and the minor commit-message wording suggestion from Knoble.
