This thread is about a small but long-standing annoyance in Git’s bash completion for `git send-email`: when a user types a prefix that could match both a revision (like a branch or tag) and a patch file, only the revision is offered as a completion candidate. Yury Norov, from NVIDIA, proposed a patch to fix this by extending completion to include filesystem paths for patch files. The patch itself is technically straightforward—it adds a helper function, `__gitcomp_file_append()`, to append filesystem candidates to the completion list without disrupting existing revision completion—and has received a `Reviewed-by` from D. Ben Knoble, who confirmed it follows established patterns and works as intended.

The discussion has centered not on the code but on whether the problem is real and widespread enough to justify the change. Junio Hamano, the maintainer, initially questioned the necessity, calling the test case (a long hexadecimal tag) artificial. Yury argued that the underlying logic flaw is real, demonstrated by a 14-year-old Git tag with a purely hexadecimal name that can’t be deleted without disrupting history. Junio has since softened his stance, proposing a revised commit message that frames the problem more clearly: when branches, tags, and patch files share a prefix (like `0-branch`, `0-tag`, and `0001.patch`), all three should be offered as completion candidates. He’s now encouraging Yury to post a v2 with updated messaging and more realistic test cases, which should address the remaining concerns. The core implementation remains uncontested, and the thread is now poised for a final version.
