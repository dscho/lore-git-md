This thread is about a patch from Yury Norov that extends bash completion for `git send-email` to include filesystem paths for patch files, not just revision identifiers. The patch itself is technically sound—it adds a helper function (`__gitcomp_file_append()`) to append file candidates to the completion list without disrupting existing revision completion, and it includes a test to verify the behavior. D. Ben Knoble reviewed the implementation and signed off with a `Reviewed-by`, confirming it follows established patterns.

However, Junio C Hamano has raised doubts about whether the patch solves a real problem. His concern was that the original test case—a purely hexadecimal tag name—felt artificial. Yury has now clarified that the issue is real: a 14-year-old Git tag with a hexadecimal name (`05c69d298c96...`) creates a conflict where patch files sharing its prefix (e.g., `0001-*.patch`) are excluded from completion. This tag can’t be deleted without rewriting history, so the problem is persistent. Yury also proposed expanding the test to cover more realistic cases (e.g., `0001.patch`, `0-tag`, and `0-branch`) to better demonstrate the fix.

The discussion is now at a stalemate. The patch’s implementation is uncontested, but its necessity is still debated. Junio hasn’t objected to the feature itself—only whether it’s worth adding—and the thread awaits input from other completion-script experts or contributors to break the deadlock. If no further objections arise, Yury plans to post a v2 with the expanded test coverage.
