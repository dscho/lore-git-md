This is a substantive review comment in the ongoing discussion about the correctness of the stacked-branch protection logic in Harald Nordgren’s `git branch --delete-merged` series (v19, patch 5/7). The series remains blocked by Junio C Hamano’s concerns about order dependency in the current implementation.

Phillip Wood proposes a structural change to the stacked-branch protection logic: instead of mutating the `deletable` set during the traversal in `spare_stacked_base()`, he suggests deferring the removal of spared branches until after the entire dependency graph has been analyzed. This would replace the current sequential, order-dependent approach with a two-phase process: first identify all branches that must be spared (those used as upstreams for unmerged branches), then remove them from the `deletable` set in a single batch operation. The change would make the logic easier to reason about and eliminate the order dependency that Junio highlighted.

Phillip’s suggestion is not a full multi-pass algorithm (as Junio speculated might be needed), but it is a step in that direction. It preserves the existing abort-and-clear design while addressing the immediate correctness concern. He plans to review the current iteration more thoroughly in the coming week, but this email already signals a concrete, implementable path forward that could unblock the series if Junio finds it sufficient. The tone is constructive and focused on correctness, not style or API design.
