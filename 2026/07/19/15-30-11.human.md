This is the latest update in the long-running `git branch --delete-merged` series, now at v19. Harald Nordgren proposes a one-line fix to address the correctness issue Junio C Hamano identified in the stacked-branch protection logic: the algorithm currently only checks whether a branch is marked for deletion (`deletable`), but should also check whether it is already marked as spared (`spared`) to avoid redundant or inconsistent processing. The fix ensures that branches already spared (because they are upstreams of unmerged branches) are not reconsidered for deletion, which should make the behavior order-independent.

The patch is small and targeted, but the underlying issue is significant: the original implementation’s behavior depended on the alphabetical order of branch names, which violates the principle that identical branch relationships should produce identical results. Harald also mentions adding a test for this case, which is critical for verifying the fix. This is the last known blocker for the series, which otherwise implements a well-designed, safety-focused branch cleanup feature with per-branch opt-out, `--dry-run` preview, and refined stacked-branch protection.

If this fix works, the series should be ready for final review and merging. The feature is valuable for users who want safe, automated local branch cleanup with precise control over which branches are deleted. The implementation is thorough, with good test coverage and attention to edge cases, though the stacked-branch protection logic has been a persistent challenge. Junio’s concern was well-founded, and this fix looks like the right direction.
