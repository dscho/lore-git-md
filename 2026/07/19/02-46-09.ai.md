This is a feature proposal for a "linked files" mechanism in Git, allowing multiple paths in a repository to always mirror the same source file byte-for-byte.

The author, sporteka, identifies a common pain point: projects often need the same file available at multiple locations (e.g., shared libraries, documentation snippets, or headers), but existing solutions—manual copies, symlinks, hardlinks, or commit hooks—either drift over time or don’t work reliably across all workflows (e.g., archives, cross-filesystem operations). The proposal introduces a declarative `.gitlinks` file to define source-target relationships, with Git enforcing identity at commit/checkout/archive time and auto-syncing edits.

The pitch argues this belongs in Git’s tooling because it leverages Git’s existing content-addressed storage (identical files already share a blob) but lacks a working-tree guarantee. As a minimal first step, the author suggests teaching `git archive` to preserve hardlinks between identical files, which would address a subset of the problem without requiring full linked-file support.

Alternatives like submodules, symlinks, and hooks are dismissed as either too heavy or unreliable. The proposal is well-motivated and scoped, though it’s early-stage and lacks implementation details. The key technical questions likely to arise in discussion include how to handle edge cases (e.g., concurrent edits, merge conflicts, or filesystem limitations) and whether the `.gitlinks` format should support patterns or just explicit path mappings. The idea is novel for Git and could spark debate about whether such guarantees belong in the core tooling or remain workflow-specific.
