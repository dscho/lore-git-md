Subject: [PATCH] send-email: add filesystem path completion for patch files

Originating author: Yury Norov (NVIDIA) <yury.norov@gmail.com>
Thread type: patch series (single-patch)

Core problem or goal
Extend bash completion for `git send-email` to include filesystem paths for patch files when the user’s prefix could match both a revision identifier (commit hash, branch, tag) and a patch file (e.g., `0` in a directory containing `0001-*.patch`). The problem is now precisely framed: when branches, tags, and patch files share a common prefix, `git send-email <TAB>` should offer all three as completion candidates, but currently only offers refs (branches and tags). The real-world trigger is a 14-year-old Git tag (`05c69d298c96...`) with a purely hexadecimal name that cannot be deleted without history disruption, but the discussion has shifted to simpler, more realistic examples (`0-branch`, `0-tag`, `0001.patch`) to demonstrate the underlying logic flaw.

Key technical details
- Files touched: `contrib/completion/git-completion.bash`, `t/t9902-completion.sh`
- New helper: `__gitcomp_file_append()` appends filesystem candidates to the existing completion list without disrupting revision completion; uses `compgen -f` and follows the established pattern of `__gitcompadd`/`__gitcompappend`
- Behavior change: `git send-email <TAB>` now offers both patch files and refs (branches, tags) when they share a prefix
- Test coverage: regression test in `t/t9902-completion.sh` verifies that both patch files and refs are offered; Junio proposes expanding the test to include more realistic cases (`0001.patch`, `0-tag`, `0-branch`) to address artificial-test-case concerns.
