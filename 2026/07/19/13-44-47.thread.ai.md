Thread identity
Subject: [PATCH] send-email: add filesystem path completion for patch files
Series version: standalone patch (v1, v2 anticipated)
Originating author: Yury Norov (NVIDIA) <yury.norov@gmail.com>
Thread type: patch series (single-patch)

Core problem or goal
Extend bash completion for `git send-email` to include filesystem paths for patch files when the user’s prefix could match both a revision identifier (commit hash, branch, tag) and a patch file (e.g., `0` in a directory containing `0001-*.patch`). The original motivation framed this as a fix for a long-standing annoyance where patch files were omitted from completion candidates. The real-world trigger is now clarified: a 14-year-old, purely hexadecimal Git tag (`05c69d298c96...`) that cannot be deleted without history disruption, which currently suppresses completion of any patch file sharing its prefix.

Current status
Under review; v1 posted, v2 anticipated. The core logic (`__gitcomp_file_append()` helper) remains uncontested. The discussion has shifted from technical correctness to problem validity: Junio questions whether the scenario is sufficiently common to justify the change, while Yury argues the underlying logic flaw—completion stopping after finding a matching ref, even when matching files exist—is real and demonstrated by the existing tag. No new version has been posted; Yury proposes expanding the test to cover more realistic cases (patch file `0001.patch`, tag `0-tag`, branch `0-branch`) to address Junio’s artificial-test-case concern.

Key technical details
- Files touched: `contrib/completion/git-completion.bash`, `t/t9902-completion.sh`
- New helper: `__gitcomp_file_append()` appends filesystem candidates to the existing completion list without disrupting revision completion; uses `compgen -f` and follows the established pattern of `__gitcompadd`/`__gitcompappend`
- Behavior change: `git send-email <TAB>` now offers both patch files and 40-hex refs when they share a prefix
- Test coverage: regression test in `t/t9902-completion.sh` verifies that both patch files and 40-hex refs are offered; Junio identified a test-script robustness issue (the `test_when_finished` block should be registered *before* creating the tag and files to ensure cleanup happens even if setup fails); Yury proposes expanding the test to include more realistic cases (`0001.patch`, `0-tag`, `0-branch`)
- Implementation details: the Bash 3 file-mode hack (from 2013) remains applicable; the helper does not expand abbreviated object names to full hashes, contrary to the commit message’s implication
- Real-world trigger: a 14-year-old Git tag (`05c69d298c96...`) with a purely hexadecimal name that cannot be deleted without history disruption

Open questions and loose ends
- **Problem validity**: Junio questions whether the patch addresses a real, widespread issue, given that purely hexadecimal tag names are rare in practice. Yury argues the underlying logic flaw—completion stopping after finding a matching ref, even when matching files exist—is real and demonstrated by the existing tag.
- **Test robustness**: Junio’s feedback about moving the `test_when_finished` block remains unresolved; Yury’s proposed expanded test coverage may address this.
- **Test realism**: Junio’s criticism of the original test case (a long hex string) persists; Yury proposes expanding the test to include more realistic cases (`0001.patch`, `0-tag`, `0-branch`).
- **Commit message wording**: D. Ben Knoble’s suggestion to replace “hashtag” with “hash” or “object name” remains open.
- **Prioritization**: Junio expresses a personal preference for prioritizing filenames over refs in completion, but this is not a blocker.
- **Broader input**: The thread awaits input from completion-script experts or other contributors to assess the patch’s necessity and design.
