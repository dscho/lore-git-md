Thread identity: Feature proposal for a "linked files" mechanism in Git, allowing multiple repository paths to mirror the same source file byte-for-byte. Originating author: sporteka (sporteka2@disroot.org). Thread type: RFC (Request for Comments), design discussion.

Core problem or goal: Address the pain point of maintaining identical copies of files across multiple repository locations (e.g., shared libraries, documentation snippets, headers). Existing solutions—manual copies, symlinks, hardlinks, or commit hooks—either drift over time or fail in cross-platform/cross-filesystem workflows (e.g., archives, clones). The proposal introduces a declarative `.gitlinks` file to define source-target relationships, with Git enforcing byte-for-byte identity at commit/checkout/archive time and auto-syncing edits. As a minimal first step, the author suggests teaching `git archive` to preserve hardlinks between identical files, leveraging Git’s content-addressed storage (identical files already share a blob) but lacking a working-tree guarantee.

Current status: Early-stage proposal; no implementation or patch series yet. The thread is in the initial discussion phase, with the author seeking feedback on the concept and design direction. No decisions or agreements have been made. No versioned series exists.

Key technical details:
- **Proposed mechanism**: Declarative `.gitlinks` file to define source-target path mappings (format details unspecified; may support patterns or explicit paths).
- **Subsystems touched**: Working tree management, commit/checkout logic, archive generation, and potentially merge/rebase conflict resolution.
- **Edge cases raised**: Concurrent edits, merge conflicts, filesystem limitations (e.g., hardlink support), and cross-platform compatibility.
- **Minimal first step**: Teach `git archive` to preserve hardlinks between identical files, addressing a subset of the problem without full linked-file support.
- **Alternatives dismissed**: Submodules (too heavy), symlinks (unreliable across workflows), hooks (prone to drift), and manual copies (error-prone).

Open questions and loose ends:
- Should `.gitlinks` support patterns (e.g., globs) or only explicit path mappings?
- How should Git handle concurrent edits to linked files (e.g., merge conflicts, race conditions)?
- What are the implications for merge/rebase operations when linked files diverge?
- Should this be a core Git feature or remain workflow-specific (e.g., hooks or external tools)?
- What are the performance implications for large repositories with many linked files?
- How would this interact with Git’s existing content-addressed storage (e.g., blob deduplication)?
