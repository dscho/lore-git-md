This thread introduces a feature proposal for Git to support "linked files"—a mechanism ensuring that multiple paths in a repository always mirror the same source file byte-for-byte. The author, sporteka, frames this as a solution to a common pain point: projects needing identical files in multiple locations (e.g., shared libraries or headers) often resort to manual copies, symlinks, or hooks, which either drift over time or fail in certain workflows (like archives or cross-filesystem operations).

The proposal suggests a declarative `.gitlinks` file to define source-target relationships, with Git enforcing identity at commit, checkout, or archive time. As a minimal first step, the author proposes teaching `git archive` to preserve hardlinks between identical files, addressing a subset of the problem without requiring full linked-file support. The idea is well-motivated but early-stage, lacking implementation details. Key questions likely to emerge include how to handle edge cases (concurrent edits, merge conflicts, or filesystem limitations) and whether the `.gitlinks` format should support patterns or only explicit path mappings.

So far, the thread is just the initial proposal—no responses or reviews have been posted yet. The discussion could pivot on whether such guarantees belong in Git’s core tooling or should remain workflow-specific.
