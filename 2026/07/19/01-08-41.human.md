This is the first patch in a two-part Rustification cleanup series from brian m. carlson, fixing a memory-safety issue in Git’s Rust hash bindings. The patch ensures the C hash context is properly initialized before cloning, preventing a crash when non-default hash backends (like OpenSSL) are used.

The problem is straightforward: the Rust `Clone` implementation for `CryptoHasher` calls a C helper (`git_hash_clone`) that expects the destination context to be initialized, but the Rust code wasn’t doing that. The fix adds a single line to initialize the context before cloning, matching the C-side contract. This is a small but critical correction—without it, the code risks using uninitialized memory, which could lead to crashes or undefined behavior.

The change is confined to `src/hash.rs` and is purely mechanical: four lines added, one removed. No new APIs or behavior changes are introduced, and the fix aligns with Jeff King’s recent C-side leak fixes in the same area. Given the author’s track record and the narrow scope, this looks like a clear, uncontroversial fix that should merge smoothly after review.

This patch is part of the broader Rustification effort but doesn’t depend on any other ongoing work. It’s a targeted follow-up to Peff’s earlier C-side improvements, addressing a Rust-specific gap in the same subsystem. If you’re tracking Rust in Git or care about memory safety at the FFI boundary, this is worth a quick look.
