This is a feature proposal for a "linked files" mechanism in Git. The author, sporteka, suggests adding a declarative way to ensure that multiple files in a repository remain byte-identical at all times, enforced by Git itself rather than relying on manual copies, symlinks, or commit hooks.

The motivation centers on common use cases where the same file needs to appear in multiple locations—such as shared libraries, headers, or documentation snippets—without drifting out of sync. The proposal introduces a `.gitlinks` file (modeled after `.gitignore`) to map linked paths to their source, with Git enforcing identity during commits, checkouts, and archives. The author also suggests a smaller first step: making `git archive` preserve hardlinks between identical files, which would already address some of the pain points.

The idea is well-motivated and clearly articulated, but it’s ambitious and likely to be controversial. Git’s working-tree model is built around individual files, and introducing automatic synchronization between paths could create edge cases around permissions, conflicts, or performance. The proposal doesn’t yet address how this would interact with merges, rebases, or partial checkouts, which might be sticking points. That said, the smaller scope of improving `git archive` to handle hardlinks seems like a reasonable and uncontroversial first step.

This is early-stage discussion material—worth following for anyone interested in Git’s file-handling capabilities, but not yet a patch or even an RFC with code. The thread is just getting started, so feedback is likely to focus on feasibility and design trade-offs rather than implementation details.
