This is the second patch in Jeff King’s 9-patch **bugfix series** addressing memory leaks in Git’s hash implementations when using non-default backends like OpenSSL SHA-256 or libgcrypt. The series targets low-level plumbing code where hash contexts (`git_hash_ctx`) are abandoned without cleanup, leaking resources allocated by these backends.

This patch introduces `git_hash_discard()`, a new primitive to explicitly free resources held by a hash context. The implementation is intentionally simple: it calls `git_hash_final()` into a dummy buffer, relying on the side effect of freeing resources. The commit message acknowledges this is inefficient but notes it’s a pragmatic first step, with a more optimized approach deferred to patch 9 (which widens the platform-specific interface). The patch touches only `hash.c` and `hash.h`, adding the new function without changing behavior.

The rationale is clear: non-default hash backends (e.g., OpenSSL ≥ 3.0) allocate heap memory during initialization, and without explicit cleanup, these leaks surface under `SANITIZE=leak`. The patch is narrowly scoped and uncontroversial, as it addresses a correctness issue without affecting default configurations. The commit message’s candid note about inefficiency ("a little wasteful") and the deferred optimization in patch 9 suggest careful staging of the fix.

Key technical details for follow-up discussion:
- **New function**: `git_hash_discard(struct git_hash_ctx *)`
- **Implementation**: Calls `git_hash_final()` into a dummy buffer; platform-specific optimizations deferred to patch 9
- **Files modified**: `hash.c`, `hash.h`
- **Test flags**: Leaks verified with `SANITIZE=leak` and `OPENSSL_SHA256=1`
- **Related patches**: Patch 9 (platform-specific discard functions), patches 3–8 (consumers of `git_hash_discard()`)
- **Impact**: No user-visible changes; fixes leaks in non-default hash backends only.
