This is a follow-up from Jeff King (Peff) in the thread that standardized `--help`/`-h` exit codes across Git's parse-options API. The series itself has already been merged as a bugfix, but Peff raises a practical concern about a subtle edge case in script compatibility.

The merged patches ensure that `git cmd --help` exits with status 0 (Unix convention) instead of 129 (the previous, inconsistent behavior). Peff acknowledges the change is unlikely to break most scripts, since `--help` is rarely scripted. However, he points out a specific scenario where a wrapper script that blindly passes arguments to a Git command (like `git log`) and then processes its output could now behave incorrectly: if the script is invoked with `--help`, the Git command will exit successfully, dump its help text to stdout, and the wrapper will proceed to process that help text as if it were valid output. Previously, the wrapper would have aborted due to the non-zero exit code.

Peff describes this as a potential issue for "hacky little scripts" that don't parse their own options, but notes he isn't convinced the fallout will be significant. The message is a heads-up rather than a call for reversion — the change is already merged, and the concern is framed as a minor, unlikely edge case. No action is requested; this is an observation for future reference if users report unexpected behavior.
