This thread is a bug report from Michael Hore about unexpected behavior in `git rev-list --exclude-first-parent-only`. The issue arises when additional commits are explicitly given on the command line: in a simple merge scenario, `git rev-list --exclude-first-parent-only F ^R2` correctly outputs `F`, but `git rev-list --exclude-first-parent-only F R1 ^R2` unexpectedly returns nothing. Michael traces the problem to `process_parents()` in `revision.c`, where the presence of `R1` on the command line causes it to be marked as `SEEN` before the exclusion of `R2` is processed, leading to `F` being incorrectly filtered out.

The report is clear, includes a minimal reproduction case, and points to a specific function in Git’s revision-walking machinery. It affects Git for Windows 2.54.0, but the issue appears to be a logic flaw rather than a platform-specific quirk. No patch has been posted yet, so the thread is likely to attract attention from reviewers familiar with the revision traversal subsystem—particularly those who have worked on `revision.c` or similar walk logic. If you’ve been following Git’s revision-walking internals, this is a straightforward bug with a well-defined scope.
