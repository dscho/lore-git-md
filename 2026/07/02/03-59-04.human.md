This is a bug report about `git rev-list --exclude-first-parent-only`.

Michael Hore from the Australian Securities & Investments Commission reports what looks like a real bug in the `--exclude-first-parent-only` traversal logic. He describes a simple merge topology (a diamond: R1 → F → R2 and R1 → R2) and shows that `git rev-list --exclude-first-parent-only F ^R2` correctly returns `F`, but `git rev-list --exclude-first-parent-only F R1 ^R2` unexpectedly returns nothing. He traces the problem to `process_parents()` in `revision.c`, where an explicitly listed commit (`R1`) is marked `SEEN` before the uninteresting flag (`^R2`) is processed, causing the second parent (`F`) to be incorrectly marked uninteresting.

The report includes system info (Git for Windows 2.54.0, SHA-1, no Rust) and a clear reproduction recipe. No patch is offered, but the diagnosis is plausible and the scenario is easy to set up. If this is indeed a bug, it affects a rarely used but documented option, so the impact is probably low but real for anyone relying on the flag. Worth a quick look from someone familiar with the revision-walking internals.
