This is the sixth patch in Jeff King’s nine-patch **bugfix series** plugging memory leaks in Git’s hash implementations when non-default backends (OpenSSL SHA-256, libgcrypt) are used. The series was previously summarized in the thread context.

This patch fixes a leak in `check_stream_oid()` (in `object-file.c`), which is called when Git reads loose objects. The function initializes a hash context, feeds the zlib stream into it, and expects to finalize the hash on success. However, if the stream is corrupted or contains extra cruft, the function bails early with an error—without calling `git_hash_final()`—leaking any resources allocated by the hash backend. The fix adds `git_hash_discard()` calls in both error paths, ensuring the hash context is cleaned up even when the function returns early. The change is minimal (two lines added) and narrowly scoped to the leaky error paths.

The patch is well-motivated: the commit message explains the leak’s cause, the conditions under which it manifests (`SANITIZE=leak OPENSSL_SHA256=1`), and the specific test (`t1450`) that fails without the fix. The reasoning for not using a common "out:" label (to avoid double-discarding a hash that was already finalized) is clear and pragmatic. This aligns with the series’ overall approach of introducing `git_hash_discard()` as a safe cleanup primitive.

No new symbols or subsystems are introduced; the patch only uses the `git_hash_discard()` function added in patch 2. The leak is specific to non-default hash backends, so the impact is limited to users who explicitly configure Git to use OpenSSL or libgcrypt. The fix is uncontroversial and unlikely to interact with other in-flight topics. The only potential follow-up discussion might involve CI coverage gaps (e.g., the linux-sha256 job lacks leak checking), but this is not addressed here.
