This is a reply in the ongoing debate about Patrick Steinhardt’s RFC patch series to reorganize Git’s source tree by moving `libgit.a` components into a new `lib/` directory. The discussion remains focused on the trade-offs between structural benefits and logistical disruption.

Patrick pushes back on Junio C Hamano’s and Phillip Wood’s critique of the "discoverability" argument, clarifying that the goal isn’t to make library files easier to find but to reduce clutter in the root directory, making *non-library* files more discoverable. He acknowledges that the sheer number of files remains the same, just nested under `lib/`, but argues the reorganization creates clearer boundaries for what constitutes library code. This, he suggests, would make it easier to enforce coding conventions (e.g., avoiding `the_repository` or `die()` in library code) by providing a visual indicator of a file’s role.

He also concedes that the recurring pain of remembering file moves (e.g., `wt-status.c` → `lib/wt-status.c`) is a real and unresolved downside, with no immediate solution beyond hoping developers adapt over time. The exchange underscores that while the structural argument for `lib/` has some merit, the practical friction—especially for maintainers working across branches like `seen`—remains a significant hurdle. The debate is now less about whether the change improves discoverability and more about whether the benefits of clearer code organization outweigh the ongoing workflow disruptions.
