This is a bug report about `git rev-list --exclude-first-parent-only`. The author, Michael Hore, describes a scenario where the command behaves unexpectedly when additional commits are explicitly specified on the command line.

The report centers on a repository with a merge commit `R2` (parents `R1` and `F`) and `F` whose parent is `R1`. When running `git rev-list --exclude-first-parent-only F ^R2`, the output is `F` as expected. However, when running `git rev-list --exclude-first-parent-only F R1 ^R2`, the output is empty, which contradicts the expected result (`F`). The author suspects the issue lies in `process_parents()` in `revision.c`, where the presence of `R1` on the command line causes it to be marked as `SEEN` before `^R2` is processed, leading to `F` being incorrectly marked as uninteresting.

The report includes system information (Git for Windows 2.54.0) and a clear reproduction case. The issue appears to be a logic flaw in how `--exclude-first-parent-only` interacts with explicitly specified commits, rather than a platform-specific or edge-case problem. No patch is provided, but the diagnosis points to a specific function in the revision-walking machinery. This is likely to attract attention from reviewers familiar with the revision traversal subsystem.
