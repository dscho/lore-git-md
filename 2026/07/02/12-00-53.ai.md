This is a nine-patch series targeting the test suite and CI infrastructure, specifically around the `GIT_TEST_LONG` environment variable used to gate expensive or long-running tests. The series originated as a small effort to expose GitLab CI status in the README and enable `GIT_TEST_LONG` there, but expanded after Patrick Steinhardt discovered that several `GIT_TEST_LONG` tests were already broken on both GitHub CI and GitLab CI, with some causing pipeline hangs.

The series makes three kinds of changes:

1. **CI visibility and configuration** (patches 1, 8, 9): adds a GitLab CI badge to the README, disables the RAM disk on macOS jobs (which was causing out-of-memory issues), and enables `GIT_TEST_LONG` in GitLab CI so that expensive tests run there.
2. **Test correctness fixes** (patches 2, 5, 7): two tests (`t0021-conversion.sh` and `t7508-status.sh`) are marked as broken when `SIZE_T_IS_32BIT` is not set (i.e., on 64-bit systems) and are now skipped in those cases. A helper function `test_bool_env` is introduced to consistently parse `GIT_TEST_LONG` as a boolean.
3. **Test efficiency improvements** (patches 3, 4, 6): three tests (`t4141-apply-too-large.sh`, `t5608-clone-2gb.sh`, `t7900-maintenance.sh`) are refactored to use less disk space or CPU time. For example, `t4141` replaces a slow `dd` loop with a single `fallocate` call, and `t5608` reduces the maximum file size it creates from 2 GiB to 1 GiB.

The patches touch the test scripts themselves, the CI configuration (`.gitlab-ci.yml` and `ci/lib.sh`), and the project README. The changes are mechanical and focused on making `GIT_TEST_LONG` tests reliable and efficient enough to run in CI without hanging or consuming excessive resources. The series is well-motivated by the observed CI failures and includes clear explanations in each commit message. No new user-facing features or behavior changes are introduced.
