Subject: `git rm -n *.json` unexpectedly recurses into subdirectories

Core problem or goal
The thread investigates why `git rm -n *.json` recursively matches JSON files in subdirectories, contrary to the user’s expectation of non-recursive behavior. The root cause is Git’s pathspec logic: `*` matches directory separators by default, documented in `gitglossary(7)`. The discussion has shifted from treating this as a bug to addressing a documentation gap, specifically whether `git-rm(1)` sufficiently explains pathspec semantics and their interaction with shell globbing (e.g., the edge case where no `.json` files exist in the current directory, causing the shell to pass `*.json` literally to Git).

Current status
The issue is confirmed as expected behavior, not a code defect. The pathspec machinery already supports the desired non-recursive matching via the `:(glob)` modifier (e.g., `git rm -n ':(glob)*.json'`), but this is not prominently documented in `git-rm(1)`. The thread now focuses on whether the man page should cross-reference `gitglossary(7)` or explicitly mention pathspec modifiers to prevent similar confusion.

Key technical details
- Command: `git rm -n *.json`
- Subsystem: pathspec handling (`pathspec.c`, shared across Git; `builtin/rm.c` for the command)
- Behavior: `*` in pathspecs matches `/` by default (documented in `gitglossary(7)`). Recursion depends on shell globbing:
  - If no `.json` files exist in the current directory, the shell passes `*.json` literally to Git, which treats it as a recursive pathspec.
  - If `.json` files exist, the shell expands the glob, and Git receives explicit non-recursive paths.
  - The `:(glob)` pathspec modifier restricts matching to the current directory (e.g., `:(glob)*.json`), overriding the default recursive behavior.
- No new symbols, no on-disk format changes, no test coverage yet.
- Platform: originally reported on Git for Windows 2.55.0.windows.1; core Git behavior, not platform-specific.
