This is the v6 iteration of a feature patch series adding a `--linearize` option to `git replay`. The series teaches `git replay` to flatten merge commits into a linear history, mimicking `git rebase --no-rebase-merges`. It is now technically complete, addressing all prior feedback including a regression fix and extensive test coverage.

The core change is in patch 3, which implements `--linearize` by skipping merge commits and reparenting subsequent commits onto the last non-merge commit. This ensures all replayed commits are flattened into a single linear topology, even when multiple branches are involved. The commit message and documentation now explicitly clarify how this differs from `git rebase --no-rebase-merges`: `git replay --linearize` drops merges and keeps only one branch (e.g., `A->X'` for a merge of `A->X` and `A->Y`), while `git rebase --no-rebase-merges` rewrites both branches and drops the merge (e.g., `A->X'->Y'` or `A->Y'->X'`). This difference is intentional and reflects the distinct goals of the two commands.

The series also includes two preparatory refactoring patches. Patch 1 introduces a helper function to put entries into `replayed_commits`, and patch 2 moves the logic for selecting the replay base outside `pick_regular_commit()`, improving code clarity. The regression fix (restoring the `replayed_base` parameter) is now incorporated, ensuring proper reparenting when replaying multiple divergent branches with `--onto`.

Test coverage is thorough, with new cases verifying `--linearize` behavior in various scenarios: replaying to the root commit, handling multiple divergent branches, incompatibility with `--revert`, and the behavioral difference from `git rebase --no-rebase-merges`. The documentation has been extended to explain how multiple revision ranges are flattened into a single linear history and how this differs from `git rebase`.

The only remaining open question is the interface design: whether to adopt `git rebase`'s `--rebase-merges=<mode>` syntax or keep `--linearize` as a standalone flag. The author and Johannes Schindelin argue that `--linearize` better describes the predictable, all-or-nothing flattening behavior, while Patrick Steinhardt prefers consistency with `git rebase`. This debate does not block merging, but the commit message must explicitly justify any divergence from `git rebase`'s syntax. The series is otherwise ready for review and looks well-crafted, with clear commit messages and robust test coverage.
