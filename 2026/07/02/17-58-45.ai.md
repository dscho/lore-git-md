This is the third and final patch in the v6 series introducing the `--linearize` option to `git replay`. It implements the core functionality: when `--linearize` is active, merge commits are dropped, and all replayed commits are flattened into a single linear history, even when multiple revision ranges are provided. The patch touches `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, and `t3650-replay-basics.sh`.

The implementation skips merge commits entirely when `--linearize` is active, reparenting subsequent commits onto the last replayed non-merge commit. This ensures a single linear topology, avoiding dangling commits and ensuring predictability. The patch also enforces mutual exclusivity with `--revert` and documents the behavioral difference from `git rebase --no-rebase-merges`: `git replay --linearize` drops merges and keeps only one branch, while `git rebase --no-rebase-merges` rewrites both branches and drops the merge. This difference is intentional, documented, and tested.

Test coverage is thorough, including scenarios for replaying multiple divergent branches, handling merge commits, replaying to the root commit, and verifying the behavioral difference from `git rebase`. The patch also includes a regression fix from earlier versions, ensuring all replayed commits are linearized into a single topology even when replaying a single branch containing merge commits. The commit message and documentation have been extended to explain the behavior, edge cases, and differences from `git rebase`.

The interface design debate remains unresolved but is no longer blocking. The series uses `--linearize` as a standalone flag, diverging from `git rebase`'s `--rebase-merges=<mode>` syntax, with an explicit justification in the commit message. The patch is technically complete, addresses all prior feedback, and is ready for review. No unresolved technical objections remain.
