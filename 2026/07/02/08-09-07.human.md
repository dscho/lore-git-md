This is the eighth patch in Jeff King’s nine-patch **bugfix series** plugging memory leaks in Git’s non-default hash implementations. It targets a **libgcrypt-specific leak** that occurs when cloning a SHA-256 hash context.

The issue stems from a mismatch between Git’s abstracted hash API and libgcrypt’s behavior. Git’s API assumes cloning works like OpenSSL—initializing the destination context first, then copying into it. But libgcrypt’s `gcry_md_copy()` *reinitializes* the destination, leaking the memory allocated during the prior `gcry_md_open()`. The leak surfaces when running the test suite with `SANITIZE=leak` and `GCRYPT_SHA256=1`, where many tests fail due to unreleased memory.

The fix is minimal: add a `gcry_md_close(*dst)` call in libgcrypt’s clone function to release the pre-allocated context before overwriting it. While this introduces a small inefficiency (the initial `gcry_md_open()` becomes redundant), it’s a pragmatic solution that avoids rewriting Git’s hash API or its callers. The patch touches only one line in `sha256/gcrypt.h` and is clearly motivated by the commit message’s detailed explanation of the API mismatch.

This is a **well-scoped, low-risk fix** for a correctness issue that only affects users explicitly configuring Git to use libgcrypt’s SHA-256 backend. The series as a whole is uncontroversial, and this patch fits neatly into its systematic approach to leak cleanup. No prior discussion or objections have been raised, and the fix aligns with the series’ earlier patches (e.g., introducing `git_hash_discard()`) without introducing new complexity.
