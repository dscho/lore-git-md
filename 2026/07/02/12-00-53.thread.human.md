This thread is about a nine-patch series (v3) that makes Git’s `GIT_TEST_LONG` tests reliable and efficient enough to run in CI. Originally submitted by Toon Claes and now in its final form by Patrick Steinhardt, the series fixes broken or hanging tests, reduces resource usage, and ensures GitLab CI runs these expensive tests—matching GitHub Actions’ behavior.

The fourth patch in the series cuts the peak disk usage of `t5608-clone-2gb.sh` in half, from 16 GB to 8 GB, by deleting repositories as soon as they’re no longer needed. This is a straightforward improvement that doesn’t change test behavior but makes the test more CI-friendly. Jeff King reviewed the patch in its first version and called it an “obvious improvement” for disk efficiency and defensive test isolation. No further changes were needed.

The series as a whole is uncontroversial and ready for integration. All feedback from earlier versions has been addressed, including restoring the `EXPENSIVE` label for a memory-hungry test and correcting commit subjects to accurately describe prerequisite logic. The only remaining open question—how Git should define “expensive” tests—is a policy matter that doesn’t block this work. The patches are split into three groups: CI visibility (badges, configuration), test correctness (skipping broken tests), and efficiency (reducing runtime and disk usage). GitLab CI now runs `GIT_TEST_LONG` tests on pushes to integration branches, excluding Windows runners due to hardware limits.
