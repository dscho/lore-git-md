Thread identity
Subject: `git rev-list --exclude-first-parent-only` misbehavior with explicit commits
Series version: none (standalone bug report)
Originating author: Michael Hore
Thread type: bug report

Core problem or goal
The `--exclude-first-parent-only` option in `git rev-list` incorrectly excludes commits when additional commits are explicitly specified on the command line, even if those commits are not part of the first-parent ancestry path being excluded. The issue manifests as an empty output when the expected output should include commits reachable from the explicitly specified commits but not from the excluded merge commit.

Current status
No patches or fixes proposed yet. The report includes a minimal reproduction case and a diagnosis pointing to `process_parents()` in `revision.c` as the likely source of the bug. The issue is confirmed on Git for Windows 2.54.0 but is not platform-specific.

Key technical details
- **Subsystem**: revision traversal (`revision.c`)
- **Function implicated**: `process_parents()`
- **Behavior**: `--exclude-first-parent-only` works correctly when only one positive ref is given (`git rev-list --exclude-first-parent-only F ^R2` → `F`), but fails when an additional commit is explicitly specified (`git rev-list --exclude-first-parent-only F R1 ^R2` → empty, expected `F`).
- **Root cause hypothesis**: Explicitly specified commits (e.g., `R1`) are marked as `SEEN` before the exclusion logic processes `^R2`, causing `F` to be incorrectly marked as uninteresting.
- **Test coverage**: None yet; the report provides a manual reproduction case.

Open questions and loose ends
- Is the diagnosis in `process_parents()` correct, or is the issue elsewhere in the revision-walking machinery?
- How should `--exclude-first-parent-only` interact with explicitly specified commits that are not part of the first-parent ancestry path?
- Are there other edge cases (e.g., multiple merge commits, octopus merges) where this logic might fail?
- Should the fix preserve backward compatibility for scripts relying on the current (buggy) behavior?

Related work
- The `--exclude-first-parent-only` option was introduced in Git 2.30.0 (commit `a12c1ff` in 2020) to support `git log --first-parent` use cases. This is the first reported bug specific to its interaction with explicit commits.
- The revision traversal subsystem (`revision.c`) has seen recent refactoring (e.g., `the_repository` removal, ODB abstraction), but this issue appears to be isolated to the exclusion logic.
