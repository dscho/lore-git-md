Thread identity
Subject: `git rev-list --exclude-first-parent-only` misbehavior with explicit commits
Series version: none (standalone bug report and fix)
Originating author: Michael Hore
Thread type: bug report and fix

Core problem or goal
The `--exclude-first-parent-only` option in `git rev-list` incorrectly excludes commits when additional commits are explicitly specified on the command line, even if those commits are not part of the first-parent ancestry path being excluded. The issue manifests as an empty output when the expected output should include commits reachable from the explicitly specified commits but not from the excluded merge commit.

Current status
A fix has been proposed by Junio C Hamano in the form of a standalone patch. The patch modifies `process_parents()` in `revision.c` to break out of the parent-processing loop early when `--exclude-first-parent-only` is active and a parent has already been marked as `SEEN`, preventing the exclusion logic from incorrectly marking commits as uninteresting. The patch includes a new test case in `t/t6012-rev-list-simplify.sh` that reproduces the reported scenario and verifies the fix. The fix has received a **Reviewed-by** from Jerry Zhang, the original author of the `--exclude-first-parent-only` option, confirming the patch aligns with the intended behavior. The patch is now effectively "ready to cook" unless other reviewers identify issues; no merge status has been reported yet.

Key technical details
- **Subsystem**: revision traversal (`revision.c`)
- **Function modified**: `process_parents()`
- **Files touched**: `revision.c`, `t/t6012-rev-list-simplify.sh` (new test case)
- **Behavior**: The fix ensures that `--exclude-first-parent-only` correctly handles explicitly specified commits that are not part of the first-parent ancestry path (e.g., `git rev-list --exclude-first-parent-only F R1 ^R2` now correctly outputs `F`).
- **Root cause**: Explicitly specified commits (e.g., `R1`) were marked as `SEEN` before the exclusion logic processed `^R2`, causing `F` to be incorrectly marked as uninteresting.
- **Test coverage**: A new test case in `t/t6012-rev-list-simplify.sh` verifies the fix for the reported edge case. No broader test coverage for other edge cases (e.g., multiple merge commits, octopus merges) has been added yet.
- **Intended behavior**: As clarified by Jerry Zhang, `--exclude-first-parent-only` is designed to exclude only the first-parent ancestry path from a merge commit while preserving commits reachable from explicitly specified commits, even if they are not part of that excluded path. This distinguishes it from tools like `git when-merged`, as it answers the question "when did a branch first split off from the baseline" rather than "when was a branch merged into the baseline."

Open questions and loose ends
- Are there other edge cases (e.g., multiple merge commits, octopus merges) where the exclusion logic might still fail?
- Should the fix preserve backward compatibility for scripts relying on the current (buggy) behavior? Jerry Zhang’s review suggests the fix restores the intended behavior, but the possibility of scripts depending on the buggy behavior remains.
- Is additional test coverage needed to verify the fix does not introduce regressions in other scenarios?
