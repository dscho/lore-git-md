This is the first patch in Jeff King’s nine-patch **bugfix series** addressing memory leaks in Git’s hash implementations when using non-default backends like OpenSSL or libgcrypt. The series was introduced earlier in the thread to plug leaks in error paths where `git_hash_final()` is not called, but this patch is a **refactoring cleanup** that precedes the main fixes.

The patch removes `discard_hashfile()`, a function introduced in 2024 to clean up hashfile structs by closing their file descriptors before freeing them. After a merge conflict resolution, Git now has two nearly identical functions—`discard_hashfile()` and `free_hashfile()`—with the only difference being that the former closes descriptors. Jeff argues that `free_hashfile()` is the better choice because the hashfile struct doesn’t always own the descriptors it holds. For example, in `do_write_index()`, the descriptor comes from a tempfile struct that will close it later, and closing it prematurely could lead to subtle bugs like double-closes or accidentally closing unrelated files.

The change is small (10 lines removed) and uncontroversial, as it simplifies the API by eliminating redundancy. It’s included in the series because later patches will modify the remaining `free_hashfile()` function, and Jeff wanted to clarify the interface first. The commit message is thorough, explaining the history, the trade-offs, and why the simpler function is preferable. No user-visible behavior changes are expected, and the patch is unlikely to draw objections.
