This is a **substantive review** from Jeff King (Peff) in the thread standardizing `--help`/`-h` exit codes across Git's parse-options API. The series itself has already been merged, but Peff raises two **post-merge concerns** about unintended consequences of the behavioral change.

First, he acknowledges the maintainer’s rationale for merging the series (the inconsistency was long-standing, `--help` is rarely scripted, and the change moves from error to success exit codes). However, he flags a **potential edge case** in scripts that use `git rev-parse --parseopt` in shell-eval mode: if a script accidentally passes `--help` and blindly continues execution, it might now process nonsense output instead of failing. While he considers this unlikely (the eval magic in patch 3 already made such callers fragile), he notes it as a theoretical risk.

Second, he describes a **concrete regression scenario** for scripts that wrap Git commands without parsing their own options. For example, a script that runs `git log --my-options "$@" >output || exit 1` and then processes `output` would previously fail on `--help` (exit 129), but now succeeds (exit 0), potentially feeding garbage to downstream logic. This affects "hacky" scripts that delegate option parsing to Git, and while Peff doubts widespread fallout, he flags it as a possible source of breakage.

The review is **not a call to revert**—the series is already merged—but it **identifies a behavioral trade-off** that future contributors or users might encounter. No follow-up patches are proposed here; Peff is documenting the risk for the record. The tone is measured, focusing on edge cases rather than fundamental flaws.
