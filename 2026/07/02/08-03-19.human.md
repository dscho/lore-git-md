This is the fourth patch in Jeff King’s nine-patch **bugfix series** plugging memory leaks in Git’s hash implementations when non-default backends (OpenSSL, libgcrypt) are used. The series is well-motivated and narrowly scoped, addressing a correctness issue without changing user-visible behavior.

This patch introduces `hashfile_checkpoint_release()`, a function to clean up the hash context stored in a `hashfile_checkpoint` struct. The checkpoint is essentially a snapshot of the hash state at a given point in a file, and its internal `git_hash_ctx` may need explicit cleanup depending on the hash implementation. The new function ensures this cleanup happens, fixing leaks in two callers: `builtin/fast-import.c` and `object-file.c`. With this patch applied, two more test scripts (`t1050` and `t9300`) become leak-free when run with `SANITIZE=leak` and `OPENSSL_SHA1_UNSAFE=1`.

The change is minimal and mechanical, adding just nine lines across four files. The commit message clearly explains the rationale and impact, and the patch itself is straightforward—no refactoring or API changes beyond the new function. The leaks it fixes are specific to non-default hash backends, so the patch is unlikely to affect most users, but it’s a necessary correctness fix for those who do use OpenSSL or libgcrypt.

No review feedback has been posted yet, but the patch looks solid and uncontroversial. It’s part of a larger, well-structured series that has so far addressed leaks in `csum-file`, and the remaining patches will tackle similar issues in other subsystems.
