This is a **substantive review** from Jeff King (Peff) on the second patch of brian m. carlson’s four-patch series standardizing help-flag exit codes in Git’s parse-options API. The series is already merged, but Peff’s feedback identifies a **logical gap** in the refactoring that could lead to inconsistent behavior.

Peff agrees with the patch’s goal—distinguishing between help output triggered by user request (`--help`/`-h`) and help output triggered by invalid input (e.g., ambiguous options). The patch introduces `PARSE_OPT_HELP_ERROR` for the latter case and reserves `PARSE_OPT_HELP` for the former. However, Peff points out that the patch only updates *one* of the two places in `parse-options.c` that generate `PARSE_OPT_HELP`. The other site, `usage_with_options_internal()`, still returns `PARSE_OPT_HELP` for *all* help output, regardless of whether it was triggered by a user request or an error. This undermines the patch’s intent to separate the two cases cleanly.

Peff suggests moving the fix for `usage_with_options_internal()` into this patch (rather than deferring it to patch 4) to maintain consistency. He also proposes a code snippet that would make the function return `PARSE_OPT_HELP_ERROR` when help output is triggered by an error (`err` is set) and `PARSE_OPT_HELP` otherwise. While he notes that the `usagestr` check might never be false in practice, he argues that the logic should still be consistent for clarity and future-proofing.

The review is **technically precise**: it identifies the exact function and line numbers involved, explains the behavioral implications, and provides a concrete fix. Peff’s feedback does not question the series’ overall direction but highlights a **subtle correctness issue** that could cause confusion later. Since the series is already merged, this will likely require a follow-up patch from brian m. carlson to address the inconsistency. The fix is straightforward and should not disrupt the broader exit-code standardization effort.
