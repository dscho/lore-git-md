This is the eighth patch in Jeff King’s nine-patch **bugfix series** plugging memory leaks in Git’s non-default hash implementations. It addresses a **libgcrypt-specific leak** that occurs when cloning a SHA-256 hash context.

The issue stems from a mismatch between Git’s abstracted hash API and libgcrypt’s behavior. Git’s API assumes cloning works like OpenSSL: the destination context is initialized first (allocating resources), then overwritten by the clone operation. However, libgcrypt’s `gcry_md_copy()` allocates a new context *and* copies data, leaking the previously allocated one. The fix is simple: close the destination context (`gcry_md_close(*dst)`) before copying, accepting a minor inefficiency (a redundant allocation in the init step) to maintain API consistency.

The patch touches only `sha256/gcrypt.h` and adds a single line. Leaks are reproducible by running the test suite with `SANITIZE=leak GCRYPT_SHA256=1 GIT_TEST_DEFAULT_SHA=256`, which previously failed many tests. This fix is narrowly scoped to libgcrypt and doesn’t affect other hash backends. The commit message justifies the pragmatic approach (keeping the existing API) over a more invasive refactor to optimize away the redundant allocation. No review feedback has been posted yet.
