This is the second patch in the v6 series introducing `--linearize` to `git replay`. It refactors the replay machinery to resolve the replay base outside `pick_regular_commit()`, improving clarity and maintainability.

The patch moves the logic for deciding the base commit (where the next commit will be replayed) from inside `pick_regular_commit()` to its caller, `replay_revisions()`. Previously, `pick_regular_commit()` would try to find the replayed result of the parent commit in the `replayed_commits` map, falling back to `onto` or `last_commit` depending on the replay mode. This split responsibility made the code harder to follow. Now, `replay_revisions()` handles the base selection entirely, passing the resolved base directly to `pick_regular_commit()`. The refactoring reduces the number of parameters to `pick_regular_commit()` and bundles all base-selection logic in one place.

The change is purely internal and does not alter behavior. The commit message explains the motivation clearly: consolidating the base-selection logic improves readability and reduces confusion about where the base is decided. The diff is clean and focused, touching only `replay.c`. This refactoring was uncontested in prior rounds and is now part of a series that is technically complete and ready for review. If the series lands, this patch will be a small but meaningful cleanup of the replay internals.
