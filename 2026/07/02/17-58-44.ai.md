This is the second patch in the v6 series introducing `--linearize` to `git replay`. It refactors the replay machinery to resolve the replay base outside `pick_regular_commit()`, improving clarity and maintainability.

The patch moves the logic for determining the base commit (the commit onto which the current commit is replayed) from `pick_regular_commit()` to its caller, `replay_revisions()`. Previously, `pick_regular_commit()` would decide the base by checking if the parent commit had already been replayed (using the `replayed_commits` map) and falling back to `onto` or `last_commit` depending on the replay mode. This split responsibility made the code harder to follow. Now, `replay_revisions()` resolves the base upfront and passes it directly to `pick_regular_commit()`, reducing the latter's parameters from five to four and bundling all base-selection logic in one place.

The refactoring is purely internal and introduces no behavior changes. It prepares the ground for the `--linearize` feature in patch 3/3 by making the base resolution more explicit and easier to modify. The commit message explains the motivation clearly: consolidating the base-selection logic improves readability and reduces confusion about where the base is decided. The diff shows the mechanical changes: `pick_regular_commit()` no longer handles the fallback logic, and `replay_revisions()` now computes the base before calling it.

This patch is uncontested and aligns with the series' goal of making the replay machinery more modular. It touches only `replay.c` and is a straightforward refactoring with no edge cases or new functionality. The change is well-motivated and should be non-controversial.
