This is the **second patch in the v6 series** for the `git replay --linearize` feature, now urgently focused on fixing the **silent commit-dropping regression** introduced in v5. The patch **refactors the base-selection logic** in `replay.c` to restore the `replayed_base` mechanism that was inadvertently broken, ensuring all commits in the input range are replayed rather than just the tip.

The core change moves the logic for determining the replay base **entirely outside `pick_regular_commit()`** and into the caller (`replay_revisions()`). This fixes the regression by ensuring the base is resolved consistently, regardless of whether the parent commit has already been replayed. The refactoring also **cleans up the interface** of `pick_regular_commit()` by reducing its parameters and bundling all base-selection logic in one place. The commit message explicitly states this is a **pure refactoring with no behavior changes**, but the structural fix is critical for restoring the intended functionality of `--linearize`.

Key technical details:
- **Functions modified**: `pick_regular_commit()` (simplified interface) and `replay_revisions()` (now handles base resolution).
- **Data structures**: Uses the `replayed_commits` khash map to track replayed commits and their new bases.
- **Files touched**: Only `replay.c` (21 insertions, 13 deletions).
- **Regression root cause**: The v5 series removed the `replayed_base` logic from `pick_regular_commit()`, causing commits to be silently dropped when their parents weren’t found in `replayed_commits`.

This patch is **mechanically straightforward** but **functionally essential**—it directly addresses the highest-priority issue in the series (silent commit dropping) and paves the way for the expanded documentation and test coverage in patch 3/3. The refactoring is well-motivated and aligns with the series’ goal of improving code clarity while fixing the regression. No controversy or edge cases are introduced here; the focus is purely on restoring the correct behavior.
