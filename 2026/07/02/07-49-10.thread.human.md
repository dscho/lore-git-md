The thread began when Евгений Плискин reported that `git rm -n *.json` unexpectedly recurses into subdirectories, treating the behavior as a bug. The discussion quickly clarified that this is not a defect but a consequence of Git’s pathspec logic: `*` matches directory separators by default, and when no `.json` files exist in the current directory, the shell passes `*.json` literally to Git, triggering recursive matching. The focus has since shifted to improving `git-rm(1)`’s documentation to clarify pathspec semantics and the interaction with shell globbing.

Key participants have weighed in with substantive technical insights. Patrick Steinhardt reclassified the behavior as correct but under-documented, provided the `:(glob)` modifier as a workaround, and asked the reporter to identify confusing parts of the man page. Phillip Wood highlighted how the behavior depends on shell globbing (empty vs. non-empty directory), while Mikael Magnusson quoted `gitglossary(7)` to explain why `*` matches `/` by default and noted that `git-rm(1)` makes no promise of non-recursive behavior. Junio C Hamano recently endorsed Mikael’s suggestion to use `failglob` in bash as a user-side mitigation, though this does not address the core documentation gap.

The thread is now centered on whether `git-rm(1)` should cross-reference `gitglossary(7)`, summarize pathspec behavior, or explicitly mention the `:(glob)` modifier to prevent confusion. No code changes are planned, and the behavior is confirmed as expected. The remaining open question is what specific wording in the man page led to the original misunderstanding.
