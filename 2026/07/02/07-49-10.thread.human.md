This thread began when Евгений Плискин reported that `git rm -n *.json` unexpectedly recurses into subdirectories, framing it as a violation of `git rm`’s non-recursive contract. The discussion quickly clarified that the behavior stems from Git’s pathspec logic—where `*` matches directory separators by default—and its interaction with shell globbing. Phillip Wood added a key insight: if no `.json` files exist in the current directory, the shell passes `*.json` literally to Git, triggering recursive matching; if files exist, the shell expands the glob, and Git receives explicit non-recursive paths.

The issue is now recharacterized as a documentation gap, not a bug. Patrick Steinhardt confirmed the behavior is correct but under-documented, and Евгений Плискин later acknowledged this. The thread has since focused on how to improve `git-rm(1)` to prevent similar confusion. A concrete solution emerged: using the `:(glob)` pathspec modifier (e.g., `git rm -n ':(glob)*.json'`) restricts matching to the current directory, aligning with the user’s original expectation. This modifier is documented in `gitglossary(7)` but not prominently referenced in `git-rm(1)`, leaving users unaware of the option.

The discussion leaves two open questions: whether `git-rm(1)` should cross-reference `gitglossary(7)` or summarize pathspec behavior, and how to clarify the shell-Git interaction edge case (empty vs. non-empty directory). No patches have been proposed yet, but the thread provides a clear workaround and identifies specific pain points for future documentation improvements. The core pathspec machinery remains unchanged, and the behavior is consistent across platforms.
