This is a **substantive review** of patch 3/9 in Toon Claes’s series to make `GIT_TEST_LONG` tests reliable and efficient in CI. The patch, originally authored by Patrick Steinhardt, refactors `t4141-apply-too-large.sh` to replace a byte-by-byte `dd` copy with direct `genzeros` generation, reducing runtime from minutes to under a second.

SZEDER Gábor’s review identifies a key oversight: while the patch dramatically improves execution time, it does not address the high memory usage of `git apply` when processing a 1 GiB patch. The process’s resident set size (RSS) still exceeds 1 GiB, which qualifies as "expensive" in terms of resource consumption, not just runtime. Gábor argues that the `EXPENSIVE` prerequisite should be retained to signal this cost, even though the test now runs quickly. The review is concise but substantive, focusing on a behavioral aspect (memory usage) that the original patch did not consider. It does not propose a code change but instead flags a policy question: whether the `EXPENSIVE` label should be tied to runtime, resource usage, or both.

The review is well-targeted and raises a valid concern about the patch’s framing. It does not challenge the technical correctness of the change (the test still verifies the same behavior) but questions whether the removal of `EXPENSIVE` is justified. This could spark discussion about how Git defines "expensive" tests and whether memory usage should be a factor in CI gating. No other issues are raised, and the review does not suggest alternative approaches or request further changes. The ball is now in the author’s court to either justify removing `EXPENSIVE` or restore it.
