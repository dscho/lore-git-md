This is the seventh patch in Jeff King’s nine-patch **bugfix series** plugging memory leaks in Git’s hash implementations when using non-default backends like OpenSSL SHA-256. The series targets leaks that only surface under `SANITIZE=leak` with `OPENSSL_SHA256=1` and don’t affect Git’s default hash behavior.

This patch fixes a leak in the HTTP object-request subsystem (`http.c`). When Git fetches objects over dumb HTTP, it creates an `http_object_request` struct that holds a `git_hash_ctx` for verifying the object’s integrity. Normally, `finish_http_object_request()` calls `git_hash_final_oid()` to clean up the hash context, but if an error occurs (e.g., network failure or corrupted data), the code bails early and frees the request without cleaning up the hash. For backends like OpenSSL 3.0, which allocate memory in their context, this causes a leak.

The fix adds a `hash_ctx_valid` flag to the `http_object_request` struct. The flag starts as true when the request is created and flips to false after `git_hash_final_oid()` is called. The `release_http_object_request()` function now checks this flag and calls `git_hash_discard()` only if the hash context is still valid, avoiding a double-free. This approach is pragmatic: it sidesteps the need for idempotent discard functions (which would require platform-specific changes) while ensuring cleanup happens exactly once.

The patch is small (5 lines added) and touches only `http.c` and `http.h`. It fixes leak-sanitizer failures in tests `t5550` and `t5619` when run with `OPENSSL_SHA256=1` and `GIT_TEST_DEFAULT_HASH=sha256`. The commit message clearly explains the edge cases (e.g., errors after finalization) and justifies the flag-based approach over more invasive changes.

This looks like a well-crafted, low-risk fix. The series as a whole is narrowly scoped to a correctness issue (memory leaks) in non-default configurations, and this patch fits neatly into that goal. No controversy is expected, but reviewers may discuss whether the flag-based approach is the cleanest long-term solution or if platform-specific idempotent discard functions (mentioned in the commit message) would be preferable. For now, the patch is ready for review.
