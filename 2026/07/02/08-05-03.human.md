This is the sixth patch in Jeff King’s nine-patch series fixing memory leaks in Git’s hash implementations when using non-default backends like OpenSSL SHA-256. The patch plugs a leak in `check_stream_oid()`—a helper that verifies loose objects by streaming their zlib-compressed contents into a hash context. If the stream is corrupted or contains trailing garbage, the function bails early without calling `git_hash_final()`, leaking any resources allocated by the hash backend. The fix adds `git_hash_discard()` calls to the two error-return paths, ensuring the hash context is cleaned up even when the object is invalid.

The change is minimal (two lines added to `object-file.c`) and well-targeted. The commit message clearly explains why a shared cleanup label isn’t feasible—`git_hash_discard()` must not be called after `git_hash_final()`—and the patch itself is straightforward. Like the rest of the series, this addresses a correctness issue that only surfaces under `SANITIZE=leak` with non-default hash backends, so it won’t affect most users. The leak was discovered in test `t1450` (which feeds corrupted objects), and the fix eliminates it without altering behavior.

This patch looks uncontroversial and follows the same pattern as earlier ones in the series. It’s part of a systematic sweep of leaky code paths, and the solution—using the new `git_hash_discard()` primitive—is consistent with the rest of the series. No review feedback has appeared yet, but the patch is narrow enough that objections seem unlikely. If you’re tracking the series, this is another incremental step toward plugging leaks in Git’s object-handling plumbing.
