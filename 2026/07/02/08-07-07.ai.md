This is **patch 7/9** in Jeff King’s **bugfix series** addressing memory leaks in Git’s hash implementations when using non-default backends like OpenSSL SHA-256. The patch targets the HTTP object request subsystem (`http.c`), where leaks occur if an object request fails before the hash context is finalized.

The fix introduces a `hash_ctx_valid` flag to track whether the hash context (`git_hash_ctx`) in an `http_object_request` struct is still active. The flag is set to `1` when the context is initialized and cleared after `git_hash_final_oid()` is called. This ensures `git_hash_discard()` is only called in `release_http_object_request()` if the context was never finalized, avoiding double-free errors. The approach is pragmatic, accounting for edge cases where requests might skip the abort function or encounter errors after finalization.

The patch resolves leak-related test failures in `t5550` and `t5619` when run with `SANITIZE=leak` and `OPENSSL_SHA256=1`. The commit message notes that a more elegant solution (e.g., making `git_hash_discard()` idempotent by nulling the context pointer) would require platform-specific changes and offers limited benefit, so the flag-based approach is preferred for now. The change is minimal (5 lines added) and touches only `http.c` and `http.h`.

This patch is part of a well-structured series that systematically plugs leaks in subsystems like `csum-file`, `patch-id`, and now HTTP. The fixes are narrowly scoped and unlikely to be controversial, as they address correctness issues without altering behavior. The series remains unreviewed at this stage, but the HTTP-specific fix aligns with the established pattern of tracking hash context validity to avoid leaks. Key symbols introduced: `hash_ctx_valid` (struct field), and the logic depends on `git_hash_discard()` (added in patch 2).
