This thread is a bugfix series from Jeff King (Peff) that plugs memory leaks in Git’s non-default hash implementations (OpenSSL SHA-256, libgcrypt). The leaks occur because the hash context (`git_hash_ctx`) requires explicit cleanup via `git_hash_final()` in error paths, but the codebase often fails to call it, causing leaks detectable under `SANITIZE=leak` with `OPENSSL_SHA256=1` or `GCRYPT_SHA256=1`. The series introduces `git_hash_discard()` (proposed as `git_hash_release()`) and systematically applies it to leaky subsystems like `csum-file`, `patch-id`, stream OID checking, HTTP object requests, and libgcrypt-specific handle copying.

The series is at v1, with patch 1 (removing a redundant `discard_hashfile()` function) already approved by Junio. Jeff proposed a follow-up cleanup to rename `free_hashfile()` for consistency, but Patrick Steinhardt opposed disrupting the series for naming tweaks. The main open discussion revolves around API design: Patrick suggested renaming `git_hash_discard()` to `git_hash_release()` for idiomatic consistency and questioned whether the function could be made idempotent to simplify error paths. Jeff’s current approach uses a flag-based system to track whether `git_hash_final()` was called, avoiding idempotency due to platform-specific complexities. Patrick’s latest reply re-emphasizes his preference for idempotency, citing past pain with non-idempotent APIs like reference transactions. The rest of the series (patches 2–9) remains unreviewed, and no merge decisions have been made. The fixes are invisible to users but critical for correctness in non-default configurations.
