This thread is a nine-patch series from Jeff King (Peff) fixing memory leaks in Git’s hash implementations when non-default backends like OpenSSL or libgcrypt are used. The leaks only surface under `SANITIZE=leak` with these backends enabled, so they’re correctness issues rather than user-facing bugs. The series introduces a new `git_hash_discard()` function in patch 2 and systematically applies it to leaky subsystems, starting with `csum-file` in this third patch.

Peff’s approach is pragmatic: the new `git_hash_discard()` calls `git_hash_final()` into a dummy buffer (a minor inefficiency deferred to patch 9), and the fixes are narrowly scoped to avoid disrupting existing APIs. This patch ensures every `hashfile` struct either finalizes or discards its hash context, plugging leaks in error paths and cases where the `skip_hash` flag is set. The fix splits `free_hashfile()` into a public version (now calling `git_hash_discard()`) and an internal helper, preserving the API while ensuring cleanup. Tests confirm the leaks are gone in six scripts when run with `SANITIZE=leak` and OpenSSL.

No reviews or objections have appeared yet, and the series hasn’t been queued for merging. The main loose ends are CI coverage gaps—neither the linux-sha256 job nor libgcrypt backend are tested with leak sanitizers—and a minor API discussion about renaming `free_hashfile()` to better reflect its role. For now, the series is a straightforward bugfix with no user-visible changes, targeting a niche but important correctness issue.
