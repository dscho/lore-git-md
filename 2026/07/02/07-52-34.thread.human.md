This thread is a bugfix series from Jeff King addressing memory leaks in Git's hash implementations when using non-default backends like OpenSSL SHA-256 or libgcrypt. The leaks occur because the hash context (`git_hash_ctx`) requires explicit cleanup via `git_hash_final()`, but error paths often skip this call. Peff introduces a new `git_hash_discard()` function (later proposed as `git_hash_release()` for naming consistency) and systematically applies it across subsystems like `csum-file`, `patch-id`, and HTTP object requests.

The series is in its initial v1 submission. Patch 1, which removes a redundant `discard_hashfile()` function, has been approved by Junio Hamano. Naming discussions are ongoing: Patrick Steinhardt suggested renaming `git_hash_discard()` to `git_hash_release()` to align with Git's idiomatic cleanup functions, and Peff proposed a follow-up patch to rename `free_hashfile()` to `hashfile_free()`. A larger debate centers on whether `git_hash_discard()` should be made idempotent—Patrick and Brian m. carlson endorsed this for maintainability and Rust integration, and Peff has proposed a concrete design using an `active` flag in `struct git_hash_ctx`. The latest email clarifies that direct calls to backend `init_fn()` functions would need to be updated to use `git_hash_init()` for the idempotency design to work fully, though this can be addressed in a follow-up.

Patches 2–9 remain unreviewed, and the series is not yet queued for merging. Open questions include the final naming of the discard function, whether to implement idempotency now or later, and how to address CI gaps (e.g., leak sanitizer not running in the linux-sha256 job). No objections to the technical approach have been raised, and the discussion remains focused on implementation details rather than the series' overall direction.
