Jeff King’s nine-patch series fixes memory leaks in Git’s hash implementations when using non-default backends like OpenSSL or libgcrypt. The leaks, which only surface under `SANITIZE=leak` with these backends enabled, stem from missing cleanup calls in error paths across several subsystems, including `csum-file`, `patch-id`, stream OID checking, and HTTP object requests. The series introduces a new `git_hash_discard()` primitive and systematically applies it to ensure proper resource cleanup, while also addressing platform-specific leaks in libgcrypt’s SHA-256 handle copying.

The first eight patches lay the groundwork: patch 1 removes a redundant function to simplify the API, patches 2–6 introduce and apply `git_hash_discard()` to the affected subsystems, patch 7 adds a flag to track hash context state in HTTP requests, and patch 8 fixes a libgcrypt-specific leak. The final patch, just posted, replaces the initial "hacky" `git_hash_discard()` implementation with platform-specific discard functions, eliminating the inefficiency of computing a final hash just to free resources. This completes the series, which is well-scoped and uncontroversial, with no objections raised so far. The fixes are narrowly targeted at correctness and performance in non-default configurations, with no user-visible changes.

The series is now fully posted and awaiting review. While the leaks are limited to users who explicitly configure Git to use OpenSSL or libgcrypt, the fixes are thorough and the commit messages clearly justify each change. The series is likely to be merged as-is, though future discussions might revisit API naming or further optimize the discard paths. CI coverage gaps—such as the lack of leak sanitizer in the linux-sha256 job and no CI testing for libgcrypt—have not yet been addressed but may surface during review.
