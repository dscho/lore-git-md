Subject: [PATCH 0/9] hash: plug memory leaks in non-default hash implementations
Series version: v1 (initial submission)
Originating author: Jeff King
Thread type: bugfix series

Core problem or goal
Git's hash context (`git_hash_ctx`) requires explicit cleanup via `git_hash_final()` when using non-default hash implementations (OpenSSL SHA-256, libgcrypt), but the codebase fails to call this function in error paths, causing memory leaks. These leaks are invisible with Git's default hash backends (which treat the context as a simple byte array) but become apparent under `SANITIZE=leak` with `OPENSSL_SHA256=1` or `GCRYPT_SHA256=1`. The series introduces a new `git_hash_discard()` primitive and systematically applies it to leaky subsystems: `csum-file`, `patch-id`, stream OID checking, HTTP object requests, and libgcrypt-specific leaks in SHA-256 handle copying. Patch 1 additionally removes a redundant `discard_hashfile()` function introduced in a prior commit, simplifying the `csum-file` API. Patch 9 replaces the initial "hacky" `git_hash_discard()` implementation (which called `git_hash_final()` into a dummy buffer) with platform-specific discard functions, eliminating inefficiency while maintaining correctness.

Current status
Initial submission (v1). Patch 1 received **maintainer approval** from Junio C Hamano, who endorsed the removal of `discard_hashfile()` in favor of `free_hashfile()` and playfully deferred to Eric Sunshine for naming feedback. Key technical details
- New symbols: `git_hash_discard()`, `hashfile_release_checkpoint()`, `free_hashfile_memory()`, `hashfile_checkpoint_release()`, `hash_ctx_valid` (struct field in `http_object_request`), `git_hash_discard_fn` (vtable callback), `platform_SHA1_Discard`, `platform_SHA256_Discard`
- Modified subsystems: `csum-file` (patches 1, 3, 4), `patch-id` (patch 5), stream OID checking (patch 6), HTTP object requests (patch 7), libgcrypt SHA-256 handle copying (patch 8), platform-specific discard functions (patch 9)
- Files touched: `hash.h`, `hash.c`, `csum-file.h`, `csum-file.c`, `patch-id.c`, `diff.c`, `http.c`, `http.h`, `object-file.c`, `builtin/fast-import.c`, `sha1/openssl.h`, `sha256/gcrypt.h`, `sha256/openssl.h`
- Functions removed: `discard_hashfile()` (patch 1)
- Related symbols: `free_hashfile()`, `finalize_hashfile()`, `hashfd_check()`, `git_hash_final()`, `skip_hash`, `hashfile_checkpoint`, `odb_transaction_files_write_object_stream`, `stream_blob`, `flush_one_hunk()`, `get_one_patchid()`, `diff_get_patch_id()`, `check_stream_oid()`, `release_http_object_request()`, `abort_http_object_request()`, `git_hash_final_oid()`, `gcry_md_copy()`, `gcry_md_close()`, `CLONE_HELPER`
- Implementation detail: Patch 1 removes the redundant `discard_hashfile()` function, simplifying the `csum-file` API by ensuring `free_hashfile()` is the sole cleanup function. Patch 2 initially implemented `git_hash_discard()` by calling `git_hash_final()` into a dummy buffer (inefficient but pragmatic); patch 9 replaces this with platform-specific discard callbacks in the hash algorithm vtable, eliminating the inefficiency. Patch 3 splits `free_hashfile()` into a public wrapper (calling `git_hash_discard()`) and an internal `free_hashfile_memory()` (used by `finalize_hashfile()` to avoid double-discarding). Patch 4 introduces `hashfile_checkpoint_release()` to clean up `hashfile_checkpoint` structs, called unconditionally for every checkpoint. Patch 5 adds `git_hash_discard()` to `patch-id` computation paths to free the hash context after the last hunk. Patch 6 adds `git_hash_discard()` to `check_stream_oid()`'s error paths to ensure cleanup even when the function bails early due to stream corruption or extra cruft. Patch 7 uses a `hash_ctx_valid` flag in `http_object_request` to track whether the hash context was finalized, ensuring `git_hash_discard()` is only called in `release_http_object_request()` if the context was never finalized. Patch 8 closes the destination context (`gcry_md_close(*dst)`) before calling `gcry_md_copy()` to avoid leaking the previously allocated context in libgcrypt's SHA-256 backend, accepting a minor inefficiency to maintain API consistency. Patch 9 adds `discard_fn` callbacks to `struct git_hash_algo`, requiring boilerplate wrappers for each algorithm (SHA-1, SHA-256, and their unsafe variants) and platform (OpenSSL, libgcrypt), with fallback no-op functions for platforms that don’t need special cleanup.
- Test coverage: Leaks discovered via `SANITIZE=leak` and `OPENSSL_SHA256=1` or `GCRYPT_SHA256=1`; patches 3-9 eliminate leaks in 68 test scripts (`t1450`, `t1600`, `t1601`, `t2107`, `t5550`, `t5619`, `t7008`, `t9210`, `t9211`, `t1050`, `t9300`, and 57 others) when run with `OPENSSL_SHA1_UNSAFE=1`, `OPENSSL_SHA256=1`, or `GCRYPT_SHA256=1`. CI gaps noted: linux-sha256 job lacks leak checking, libgcrypt not tested in CI.
- On-disk format: No changes
- Behavior: No user-visible changes; fixes correctness issue (memory leaks) in non-default configurations.

Open questions and loose ends
- **Patch 1**: Junio approved the removal of `discard_hashfile()`, but naming feedback is pending. Jeff King proposed renaming `free_hashfile()` to `hashfile_free()` (or `hashfile_discard()`) in a follow-up patch to align with Git's naming conventions. No technical objections raised.
- **Patches 2-9**: Unreviewed. No objections or requests for changes raised yet.
- CI coverage gaps: linux-sha256 job does not run leak sanitizer; libgcrypt backend not tested in CI. No discussion yet on whether these gaps should be addressed.
- Patch 3's split of `free_hashfile()` into public/private variants may prompt future API simplification discussions, though no such feedback has been raised yet.
- Patch 4's naming choice ("release" instead of "discard") for `hashfile_checkpoint_release()` is deliberate: the function is meant to be called unconditionally for every checkpoint, whereas `git_hash_discard()` is only needed if `git_hash_final()` wasn’t called.
- Patch 6's commit message justifies not using a common "out:" label to avoid double-discarding a hash that was already finalized, aligning with the series’ pragmatic approach.
- Patch 7's flag-based approach (tracking `hash_ctx_valid`) is preferred over making `git_hash_discard()` idempotent (e.g., by nulling the context pointer), as the latter would require platform-specific changes and offers limited benefit.
- Patch 8's commit message justifies the pragmatic approach (closing the destination context before cloning) over a more invasive refactor to optimize away the redundant allocation in libgcrypt's backend.
- Patch 9's boilerplate wrappers for platform-specific discard functions are verbose but pragmatic, reusing the existing `CLONE_HELPER` flag to determine whether a platform needs smart copying/discarding.
