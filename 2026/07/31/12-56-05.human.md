This is the final patch in Junio C Hamano’s four-part series introducing `git add --resolved`, a new workflow-oriented option for staging only conflict-resolved paths during merges, rebases, or cherry-picks. The patch implements the core logic: scanning the index for unmerged paths, checking each for remaining conflict markers (with an early exit for binary files), and staging only those that are fully resolved. If any path still contains conflict markers, the command aborts with an error listing the unresolved files.

The implementation is technically solid and addresses all prior review feedback. It uses the new `has_conflict_markers()` helper (introduced in an earlier patch) to scan file content, and the `remove_file_from_index_with_flags()` helper to support `--dry-run` and `--verbose` modes. The test script `t/t2207-add-resolved.sh` covers edge cases like partially resolved conflicts, pathspecs, deletions, and option incompatibility with `-u` and `-A`. The v3 update fixed a portability issue in the test script by replacing `git checkout master` with `git checkout @{-1}`.

The remaining open question is purely about interface design: whether `--resolved` should remain a monolithic, workflow-oriented operation (Junio’s position) or be split into a more general `--unmerged` selector with explicit policy flags (Michael Montalbo’s proposal). This debate does not affect the correctness of the implementation, which is well-tested and ready for review. The patch is a clean, focused addition that solves a real workflow pain point for maintainers who resolve conflicts while carrying unrelated local changes. Reviewers should verify the edge cases and the robustness of the new helpers, but the series is likely to land in some form.
