This is the v3 iteration of Junio C Hamano’s `git add --resolved` feature series, a targeted workflow improvement for maintainers who resolve conflicts while carrying unrelated local changes. The series remains structurally unchanged from v2: two preliminary refactorings (conflict-marker logic consolidation and a new index-removal helper), the core `--resolved` implementation, and a whitespace-only reindentation. The sole update in v3 is a test-script portability fix—replacing the hard-coded `git checkout master` with `git checkout @{-1}`—to accommodate repositories that use `main` or other default branch names, addressing the BREAKING_CHANGES test environment.

The feature itself is now technically complete and addresses all prior review feedback from Michael Montalbo: the option-incompatibility logic is fixed, the test script is discoverable via Meson, and the portability issue is resolved. The implementation scans the index for unmerged paths, checks each for remaining conflict markers (with an early exit for binary files), and stages only those that are fully resolved. The new `remove_file_from_index_with_flags()` helper in `read-cache.c` supports `--dry-run` and `--verbose` modes, and the conflict-marker detection logic in `merge-ll.c` is now shared across `diff.c`, `rerere.c`, and the new `--resolved` code path.

The conceptual debate over the user-facing interface remains unresolved. Junio’s `--resolved` option is a monolithic, workflow-oriented operation that stages only paths whose conflict markers have been removed, aligning with Git’s existing conventions (e.g., `git am --resolved`). Michael Montalbo’s alternative proposal—a more general `--unmerged` selector with explicit policy flags like `--allow-conflict-markers`—prioritizes flexibility and decouples selection from policy. Neither side has conceded, and the discussion may continue with further arguments or counter-proposals. For now, the series is ready for review on its technical merits, with the interface design as the primary open question.
