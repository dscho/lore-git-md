This is the latest reply in the ongoing RFC discussion about restricting Git 3.0 to accept only lowercase hex object IDs. Junio C Hamano responds to brian m. carlson’s justification for the breaking change by invoking the **Robustness Principle** (Postel’s Law): "Be liberal in what you accept, and conservative in what you send." Junio argues that Git’s current behavior—accepting both uppercase and lowercase while emitting only lowercase—already adheres to this principle, and that the real issue lies with external tools violating it by failing to handle uppercase input. He suggests that Git need not change its own behavior to accommodate others’ mistakes.

Junio proposes an alternative: Git could maintain its current strict output (lowercase only) while continuing to accept uppercase from third-party implementations, treating object IDs used *locally* (e.g., in the object database) and those exchanged *over the network* as separate categories. This would preserve compatibility with tools that emit uppercase without requiring a breaking change. His position reflects skepticism about the necessity of the proposed change, framing it as a philosophical rather than purely technical debate.

The reply does not address the implementation details of the patch itself (which Junio had previously reviewed in earlier parts of the series) but instead challenges the series’ foundational premise. This keeps the discussion open but shifts focus from *how* to enforce lowercase to *whether* it should be enforced at all. The thread remains in the RFC stage, with no clear consensus yet on whether the project will adopt this breaking change for Git 3.0.
