This is a **bug report** about a regression in `git rebase` when submodules are involved. The issue surfaced between Git v2.53 and v2.55 and is tied to commit-graph usage.

Florian Schmidt reports that rebasing a branch with submodule pointer changes fails with the error *"commit graph is likely corrupt"* and an invalid commit OID (`157b7492624beac3ac667dd3a84de9969377866b`). The rebase succeeds when commit-graphs are disabled (`core.commitGraph=false`), suggesting the problem lies in how the commit-graph interacts with submodules. The OID in question exists as a commit in one of the submodules (`rpmsrc/qemu-kvm`) but is not found in the main repository, hinting at possible confusion between the two object stores.

A bisect identified the culprit as commit `bb5da75d61` ("commit: use commit graph in `lookup_commit_reference_gently()`"), which introduced commit-graph lookups in a function that may now incorrectly handle submodule commits. While Git v2.53 also logs errors for the same OID, it continues the rebase, whereas v2.54+ fails fatally. The report includes detailed reproduction steps, object checks, and a clear link to the problematic commit, making it actionable for maintainers.

This looks like a real regression with a well-defined scope (submodules + commit-graph). The fact that it works with commit-graphs disabled narrows the issue to a specific code path. No patches or fixes are proposed yet, but the report is thorough enough to guide debugging. If you work with submodules or commit-graphs, this is worth tracking.
