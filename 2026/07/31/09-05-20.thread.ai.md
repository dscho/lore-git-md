Subject: `git rebase` regression with commit graphs and submodules (bisected to `bb5da75d61`)
Series version: N/A (bug report)
Originating author: Florian Schmidt <flosch@nutanix.com>
Thread type: bug report

Core problem or goal
A regression in `git rebase` causes fatal errors (`invalid commit position. commit-graph is likely corrupt`) when commit graphs are enabled and the rebase involves submodule pointer changes. The error occurs because `lookup_commit_reference_gently()` now consults the commit graph but appears to resolve object references across repository boundaries, treating a submodule commit OID as if it belonged to the main repository.

Current status
Under investigation; no patches posted yet. The regression was introduced between Git v2.53 and v2.54 by commit `bb5da75d61` ("commit: use commit graph in `lookup_commit_reference_gently()`"). Workaround: disable commit graphs (`core.commitGraph=false`).

Key technical details
- **Subsystems**: commit graph, submodule handling, rebase machinery
- **Files touched by regression commit**: `commit.c` (function `lookup_commit_reference_gently()`)
- **Error message**: `error: Could not read 157b7492624beac3ac667dd3a84de9969377866b` followed by `fatal: invalid commit position. commit-graph is likely corrupt`
- **Object OID**: `157b7492624beac3ac667dd3a84de9969377866b` (exists in submodule `rpmsrc/qemu-kvm`, not in main repository)
- **Test case**: rebase a branch containing a single commit that updates two submodule pointers
- **Behavior change**: Git v2.53 emits the same error but continues the rebase; Git v2.54 fails fatally

Open questions and loose ends
- Why does `lookup_commit_reference_gently()` resolve a submodule OID against the main repository’s commit graph?
- Is the commit graph being built or queried without considering submodule boundaries?
- Should the function fall back to loose-object lookup when the OID is not found in the commit graph, or should it avoid querying the commit graph altogether for submodule OIDs?
- Are there other code paths that might trigger the same cross-repository confusion?
