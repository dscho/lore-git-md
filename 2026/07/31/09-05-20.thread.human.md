This thread is a **bug report** about a regression in `git rebase` introduced between Git v2.53 and v2.54, specifically when commit graphs are enabled in repositories with submodules. The issue was bisected to commit `bb5da75d61` ("commit: use commit graph in `lookup_commit_reference_gently()`"), which began using commit graphs in a function that resolves object references.

Florian Schmidt, the reporter, describes a scenario where rebasing a branch with submodule pointer changes fails with the error `error: Could not read 157b7492624beac3ac667dd3a84de9969377866b` and `fatal: invalid commit position. commit-graph is likely corrupt`. The problematic commit OID exists in a submodule (`rpmsrc/qemu-kvm`) but not in the main repository, suggesting Git is incorrectly resolving object references across repository boundaries. Disabling commit graphs (`core.commitGraph=false`) allows the rebase to proceed, though submodule conflicts may still occur. Notably, Git v2.53 emits similar errors but continues the rebase, while v2.54 fails fatally.

The report is thorough, including a clear reproduction case, a bisect result, and a workaround. The regression appears to stem from how commit graphs interact with submodule object resolution, making this a potentially widespread issue for users with submodules. No responses or reviews have been posted yet, so the thread is currently focused on diagnosing the problem. The next steps will likely involve reviewers or maintainers investigating the bisect result and the interaction between commit graphs and submodule handling.
