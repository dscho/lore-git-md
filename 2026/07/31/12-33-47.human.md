This is Junio C Hamano’s latest reply in the ongoing RFC thread about restricting Git 3.0 to lowercase-only hex object IDs. He expands on his earlier invocation of the Robustness Principle with a concrete hypothetical: Git’s dumb HTTP transport encountering a remote repository that uses uppercase hex in loose object filenames. Junio argues that a truly robust system would accept such filenames (treating them as equivalent to their lowercase counterparts) rather than rejecting them outright, even if Git itself never produces uppercase hex. His example illustrates how the proposed breaking change could disrupt interoperability with other tools or reimplementations, even when those tools are technically violating Git’s documented conventions.

The message does not engage with the patch’s implementation or test coverage but instead reaffirms Junio’s philosophical objection to tightening the rules after two decades. He acknowledges that rejecting uppercase hex would prevent certain edge-case bugs (like the hypothetical duplicate loose objects) but insists that the correct solution is to handle such cases gracefully—accepting the input while normalizing it internally—rather than rejecting it. This position directly challenges brian m. carlson’s security-focused rationale, which cites real-world vulnerabilities in external tools caused by Git’s current case-insensitive parsing.

The thread remains at an impasse: Junio’s argument prioritizes backward compatibility and interoperability, while brian’s emphasizes security and consistency. No compromise or alternative design has been proposed yet, and the discussion is now squarely focused on whether the project is willing to accept a breaking change of this magnitude. The infrastructure patches (1–5) may still proceed independently, but the final enforcement patch (6/6) is unlikely to move forward without resolving this fundamental disagreement.
