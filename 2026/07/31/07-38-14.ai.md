This is a review reply in the ongoing RFC thread about restricting hex object IDs to lowercase in Git 3.0. The author, brian m. carlson, proposes a breaking change to enforce lowercase-only parsing of object IDs, citing security and consistency motivations. Junio C Hamano, the maintainer, engages with the first patch in the series, which introduces infrastructure for the change without altering behavior yet.

Junio’s review is substantive but narrowly focused on the design philosophy behind the proposed `HEX_KIND_LOWER` mode. He questions whether Git should ever reject uppercase hex digits, invoking the Robustness Principle ("be conservative in what you produce, be liberal in what you accept"). His concern is not with the implementation itself—he does not critique the code or suggest alternatives—but with the fundamental premise of the series: whether Git should ever enforce lowercase-only parsing, even in a future breaking-change release. He does not address the security rationale or the real-world evidence brian has provided in later replies, nor does he engage with the rest of the series (patches 2-6), which build on this infrastructure to implement the actual enforcement.

The review does not resolve the central question of whether the project wants this breaking change at all. Junio’s objection is philosophical rather than technical, and it remains unclear whether his position will shift in light of brian’s evidence of security vulnerabilities caused by Git’s current case-insensitive parsing. The thread is still in the RFC stage, with no maintainer decision or merge status, and the discussion is likely to continue focusing on the justification for the change rather than the implementation details. For now, this reply signals that the maintainer is not yet convinced of the need for the change, but it does not close the door on further discussion.
