This is a review reply in the ongoing RFC thread about restricting Git 3.0 to lowercase-only hex object IDs. Junio C Hamano, the maintainer, engages with the first patch in brian m. carlson’s six-patch series, which introduces infrastructure for enforcing lowercase hex parsing without yet changing behavior.

Junio’s review is substantive but narrowly focused. He questions the scope of the proposed change, asking what cases *must* continue accepting uppercase hex—network protocols with other Git implementations are the obvious example. His tone suggests skepticism about the need for *any* breaking change here, invoking the Robustness Principle ("be conservative in what you produce, liberal in what you accept") to argue that rejecting uppercase hex violates a long-standing design guideline. The review does not address the security rationale brian has since provided (real-world vulnerabilities in external tools caused by Git’s case-insensitive parsing), nor does it engage with the later patches that actually implement the enforcement. Instead, it stays tightly on the mechanics of the first patch: the new `hex_kind` enum and `hexval_lc_table` are technically sound, but their purpose is still under debate.

This reply does not resolve the thread’s central question—whether Git 3.0 should make this breaking change—but it does clarify that Junio’s initial pushback is rooted in principle rather than implementation. The discussion remains open, with the security evidence still unaddressed and the derived-hash labeling question (raised in the fourth patch) still unresolved. For now, the first patch is a mechanical refactoring that prepares the ground; the real controversy lies ahead.
