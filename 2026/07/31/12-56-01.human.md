This is the third iteration of Junio C Hamano’s `git add --resolved` feature series, a new workflow-oriented option for staging only paths whose conflict markers have been removed. The series remains technically complete, addressing all prior review feedback and now passing tests even under the `BREAKING_CHANGES` regime (which assumes a default branch name of `main` instead of `master`). The only change since v2 is a one-line test portability fix: replacing `git checkout master` with `git checkout @{-1}` to return to the previous branch regardless of its name.

The core design debate—whether `--resolved` should remain a monolithic operation or be split into a more general `--unmerged` selector with policy flags—is still unresolved, but this update does not revisit that discussion. Instead, it focuses on mechanical readiness: the code is clean, the test coverage is thorough, and the commit messages clearly explain the motivation and implementation. The series touches conflict-marker detection logic, index manipulation helpers, and the `git add` command itself, with no on-disk format changes or new configuration knobs.

For maintainers juggling frequent merges alongside unrelated local changes, this feature looks like a practical improvement. The implementation is careful about edge cases (binary files, deletions, and partially resolved conflicts) and includes a small performance tweak to skip unnecessary I/O for binary content. If the conceptual debate doesn’t derail it, this is likely to land soon.
