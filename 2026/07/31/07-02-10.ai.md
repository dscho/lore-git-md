This is a **reviewer reflection and design discussion** in the `hn/history-squash` thread, focusing on the `--reedit-message` option and message-handling behavior.

Matt Hunter weighs in on the ongoing debate about whether `--reedit-message` should be removed and re-editing made the default. He acknowledges Phillip Wood’s earlier concerns about preserving `amend!`/`squash!` messages but notes that some of those issues were addressed in recent updates (citing two prior emails). He suggests that if the default behavior is to squash all changes while discarding context beyond the first commit, accepting `amend!` messages for that commit would align better with user intent.

In response to Harald Nordgren’s proposal to remove `--reedit-message` and always open the editor, Matt raises a practical concern: scripts relying on non-interactive operation would break, though he concedes a workaround exists (`git -c core.editor=/bin/true`). He then proposes a more conventional approach—offering both `--edit` and `--no-edit` options—arguing this would be consistent with other Git commands and allow future configuration (e.g., `history.editSquashMsg`). He also notes the tension between this and the existing `--reedit-message` precedent in `git history`.

The email advances the discussion by introducing a middle-ground proposal (`--edit`/`--no-edit`) but does not resolve the core design questions. It highlights the trade-offs between scriptability, user experience, and consistency with other Git commands, while leaving the broader correctness issues (e.g., reachability logic) untouched. The tone is collaborative but tentative, reflecting the unresolved state of the topic.
