Subject: [PATCH v2] ci: cancel stale workflow runs for pull requests
Series version: standalone patch, v2
Originating author: Harald Nordgren
Thread type: CI/build system improvement

Core problem or goal
Reduce wasted GitHub Actions CI runner capacity by ensuring only the latest workflow run for a pull request remains active, canceling any stale in-progress runs when a new push occurs. The current configuration groups workflow runs by commit hash, which prevents cancellation of stale runs for pull requests.

Current status
Under review; v2 posted addressing Junio C Hamano’s review of v1. Patch modifies `.github/workflows/main.yml` to make the `concurrency.group` expression both pull-request-aware and workflow-specific, grouping by workflow name plus pull request number for pull request events and by workflow name plus commit hash for regular pushes. Sets `cancel-in-progress: true` for pull request events only. Junio’s edge case regarding simultaneous workflows sharing the concurrency group is addressed by including the workflow name in the group key. Junio tested v2 and identified a potential regression: the same commit pushed to a repository and later submitted as a pull request could trigger two parallel workflow runs (one per event type), wasting CI resources. Harald Nordgren confirmed this scenario is unavoidable under GitHub Actions’ concurrency model, as groups are scoped to individual repositories. The trade-off between pull-request cancellation and potential duplicate runs is now explicitly acknowledged; no technical fix is proposed.

Key technical details
- File touched: `.github/workflows/main.yml`
- New behavior: stale workflow runs for the same pull request and same workflow are canceled on new pushes; non-pull-request events remain commit-based and run to completion; simultaneous workflows for the same commit no longer interfere
- Old behavior: all workflow runs for a commit hash ran to completion, regardless of pull request state
- Confirmed limitation: same commit could trigger duplicate workflow runs if pushed directly and later submitted as a pull request, due to separate concurrency groups for `push` and `pull_request` events; this is inherent to GitHub Actions’ design and cannot be mitigated within the current patch scope
- No new symbols, CLI options, or on-disk format changes
- Test coverage: none (CI configuration change only)

Open questions and loose ends
- Is the risk of duplicate workflow runs for the same commit (pushed directly and later submitted as a PR) acceptable, given its rarity in practice and the absence of a technical workaround?
- Should the `skip-if-redundant` optimization for non-PR pushes be revisited, or is the current v2 behavior sufficient for the project’s needs?
