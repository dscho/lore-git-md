Thread identity
Subject: [PATCH] ci: cancel stale workflow runs for pull requests
Series version: standalone patch (no series)
Originating author: Harald Nordgren
Thread type: CI/build system improvement

Core problem or goal
Reduce wasted GitHub Actions CI runner capacity by ensuring only the latest workflow run for a pull request remains active, canceling any stale in-progress runs when a new push occurs. The current configuration groups workflow runs by commit hash, which prevents cancellation of stale runs for pull requests.

Current status
Under review; no prior versions. Patch modifies `.github/workflows/main.yml` to make the `concurrency.group` expression pull-request-aware, grouping by pull request number for pull request events and by commit hash for regular pushes. Sets `cancel-in-progress: true` for pull request events only. Junio C Hamano has reviewed the patch, raised a potential edge case regarding simultaneous workflows sharing the concurrency group, and requested clarification or commit message adjustment. No evidence of integration into Junio’s branches; remains in review state.

Key technical details
- File touched: `.github/workflows/main.yml`
- New behavior: stale workflow runs for the same pull request are canceled on new pushes; non-pull-request events remain commit-based and run to completion
- Old behavior: all workflow runs for a commit hash run to completion, regardless of pull request state
- No new symbols, CLI options, or on-disk format changes
- Test coverage: none (CI configuration change only)

Open questions and loose ends
- **Edge case**: if multiple workflows sharing the same concurrency group are triggered simultaneously for the same commit, the new grouping might cause some workflows to be skipped entirely. Junio requests this be either verified or explicitly addressed in the commit message.
