This is a bugfix patch in the ongoing `git-history` command series, addressing an edge case in the replay subsystem's handling of empty commit ranges. The patch comes from Elijah Newren in response to Patrick Steinhardt's v10 series.

The issue occurs when `replay_revisions()` is called with an empty range of commits (which will be valid for the upcoming `git-history` command). Currently, the function incorrectly reports a merge conflict in this case because the `clean` flag in the `merge_result` struct remains zero-initialized rather than being explicitly set to indicate success.

Newren suggests a wording improvement to the commit message to clarify that the empty range case can occur with any branch tip, not just HEAD. The actual code change is straightforward - initializing the `clean` flag to 1 rather than zeroing the struct. This matches the expected behavior since no actual merge occurs with an empty range.

This appears to be a minor but necessary fix in the final polishing stages of the `git-history` series. Newren's review indicates the technical approach is sound, with only the commit message clarification suggested. The change maintains consistency of the replay infrastructure as it prepares to support the new `git-history` command's use cases.
