Thread identity: Bugfix discussion addressing multiple issues in Git's hook subsystem - stdout/stderr separation in pre-push hooks, stdin feeding performance in `feed_pipe`, and potential deadlocks in hook execution. Authored by Chris Darroch with participation from brian m. carlson, Patrick Steinhardt, Adrian Ratiu, Junio C Hamano, Jeff King (Peff), and Kristoffer Haugsbakk.

Core problem: Three interrelated issues in hook execution:
1. Stdout/stderr separation regression causing pre-push hooks to lose separate stream capability
2. Stdin feeding performance issues in `feed_pipe` when not using `ungroup=1`
3. Newly identified deadlock scenario when feeding stdin while reading stderr

Current status: The fixes are being split into three distinct commits for v3:
1. Stdout/stderr separation (validated and ready)
2. Stdin feeding improvements (now addressing deadlock risk and performance impact)
3. Proper `ungroup` flag initialization (newly identified issue)

Technical details:
- Stdout/stderr solution (ready):
  * New `stdout_to_stderr` flag in `run_hooks_opt` (defaults to 1)
  * Explicit handling for pre-push hooks in transport.c
  * Comprehensive test coverage in `t/t1800-hook.sh`
- Stdin feeding solution (updated with Jeff King's findings):
  * Demonstrated deadlock scenario when pipe buffer fills up
  * Measured 100ms performance penalty when exceeding 500-line batch size
  * Two concrete solutions under consideration:
    1. Require `ungroup=1` (simplest, avoids polling)
    2. Implement proper poll() handling for simultaneous stdin/stderr
  * Performance impact now quantifiable via pre-receive hook test case
- Ungroup flag fix (new):
  * Correct initialization based on historical behavior from commit 857f047e40
  * Will ensure backward compatibility

Open questions: 
1. Final decision between `ungroup=1` requirement vs poll() implementation
2. Whether stderr buffering (to prevent interleaving) is worth losing real-time updates
3. Final verification of `ungroup` flag initialization against historical behavior
4. Performance impact assessment for large ref sets (501+ refs)
