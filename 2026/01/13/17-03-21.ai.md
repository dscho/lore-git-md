This is a follow-up discussion about the recently merged push-tracking feature in `git status`. Jeff King (Peff) raises a practical concern about the new push branch divergence output being too verbose for certain workflows.

Peff notes that in his triangular workflow (where he works on 'jch' branch and treats the remote as a simple mirror), the push branch status is just noise. While the output can be disabled globally via `status.aheadbehind`, this would also hide the useful upstream branch information he wants to keep. He also points out that `git checkout` shows this information without any configuration to suppress it.

The core issue is that the new feature, while well-implemented and thoroughly tested, doesn't account for all workflow variations. Peff's comment suggests the need for more granular control - perhaps a separate configuration to disable just the push branch status while keeping upstream branch information visible. This is the first post-release feedback on a feature that went through 25 iterations of review before merging, showing how real-world usage can surface new considerations even after extensive pre-merge testing.

The thread context shows this is building on Harald Nordgren's work that added push tracking to status output, with careful handling of edge cases and advice messages. Peff's comment focuses on a specific but valid workflow where the new output creates clutter rather than value. This may prompt discussion about adding configuration knobs or making the push status display conditional on workflow patterns.
