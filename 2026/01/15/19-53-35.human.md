This is a discussion about refining the configuration options for `git status`'s branch comparison output, building on Harald Nordgren's merged series that added push tracking branch information.

Jeff King and Phillip Wood are discussing their shared preference for simpler status output in triangular workflows (where fetch and push remotes differ). Both find the exact ahead/behind counts less useful than a binary "needs push" or "needs rebase" indicator. King notes the counts are only helpful when they reveal something wildly wrong (like a 1500-commit divergence suggesting misconfigured tracking).

The exchange suggests two potential configuration axes emerging from the thread: whether to show push comparisons at all, and whether to display detailed counts versus simplified status. Wood proposes designing the configuration system to accommodate both choices from the start, even if the simplified output comes later. This aligns with Junio Hamano's earlier suggestion for an extensible framework.

The discussion reinforces that `push.default=current` is a common setting for triangular workflow users (as both King and D. Ben Knoble use it), though the default `simple` mode doesn't work well in such setups. The thread continues to balance immediate workflow needs with long-term configuration design, now with clearer input from experienced contributors about what information they actually use day-to-day.
