Git thread summary:

Bug report from Jon Forrest about inconsistent behavior in `git add` when handling invalid paths, with current behavior differing between:
- Non-existent files (`git add x bogus_file`): entire command fails, nothing added to index (confirmed by Jeff King)
- Ignored files (`git add file1 jon` where file1 is ignored): warns about ignored file but still adds non-ignored file (jon)

Junio C Hamano provides maintainer perspective on the ignored file case, arguing the current behavior makes practical sense for common workflows like `git add .` or `git add *` where some files may be ignored. He notes technical challenges in distinguishing explicitly typed filenames from shell-expanded ones, and suggests changing this would constitute a new design rather than a bugfix.

Jon Forrest follows up acknowledging Junio's perspective, reframing his original concern about `git add` behaving like a database transaction (all-or-nothing) while recognizing the practical workflow benefits of the current behavior. He concedes this is a minor issue now that he understands the rationale, though the distinction between error types (invalid vs ignored files) remains noteworthy for user awareness.

The discussion highlights key technical constraints: the distinction matters for scripting use cases, and the current implementation treats shell-expanded paths the same as explicitly named ones once they reach `git add`. The thread appears to be winding down with consensus for keeping current behavior, though it surfaces useful context about edge cases in path handling and the tradeoffs between strict consistency and practical workflow needs. No patches are proposed - this remains a documentation/design discussion rather than a code change proposal.
