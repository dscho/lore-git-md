This is a performance analysis email in an ongoing thread about `git pack-refs --all` slowness on large repositories with millions of refs stored on NFS. Jeff King (Peff) responds to Martin Fick's flame graph analysis that showed significant time spent in memcmp, object header parsing, and page faults.

Peff identifies that much of the overhead comes from Git repeatedly verifying the sortedness of packed-refs files written by JGit (which doesn't mark them as sorted). He explains Git's three-step process when reading packed-refs without the "sorted" marker: checking for the tag, verifying sortedness, and potentially re-sorting. This creates unnecessary work compared to JGit's simpler approach.

The email suggests testing whether manually adding the "sorted" marker to packed-refs improves performance, and recommends JGit should properly mark sorted files to enable Git's optimized binary search. Peff also notes JGit should support the "fully-peeled" marker for additional performance gains.

This advances the thread by providing a concrete, testable hypothesis for part of the performance gap while maintaining technical neutrality about the broader reftable vs packed-refs debate. The analysis focuses on an interoperability issue between Git and JGit's packed-refs implementations rather than the NFS/mmap interactions that dominated earlier discussion.
