Patrick Steinhardt's ODB abstraction series (v3 14/14) restructures Git's object storage layer to support pluggable backends, with most technical work complete. The series systematically converted six major components to use core iteration APIs while standardizing flags/path handling. Key discussions included path-based object access (patch 03/14), naming conventions (04/14), and the layered iteration API design (07/14), with Taylor Blau providing extensive review feedback that shaped the final approach.

Technical review has converged on most aspects, with Taylor approving conversions in `fsck.c` (08/14), promisor object handling (09/14), and `commit-graph.c` (10/14). The latest exchange addresses patch 10/14 (`builtin/cat-file.c` conversion), where Patrick includes a temporary workaround for full filter support (like "--filter=blobs:none") that will be implemented in a follow-up series via a new `struct odb_for_each_object_options`. He agrees to add a TODO comment marking this as temporary. The discussion also clarifies the planned filtering API direction, which will support object ID prefixes, object filters, and potentially other iteration parameters, moving filtering logic into the backend for optimizations like bitmap-based filtering.

The mtime handling discussion in patch 12/14 remains the primary open architectural question. Taylor Blau questions whether exposing mtime at the ODB layer is the right abstraction, particularly for GC-specific semantics around cruft packs. He proposes an alternative approach using a generic `statp` field in `struct object_info` with GC-specific logic moved to a helper function (`object_info_gc_mtime()`), arguing this better separates concerns. Patrick counters that this would break pluggability by putting backend-specific logic outside the backends, maintaining his approach keeps the logic fully contained within each backend implementation. The technical disagreement centers on whether cruft pack mtimes should be handled internally within the packfile store backend (Patrick's current implementation) or at a higher level via a more general stat structure (Taylor's proposal). Patrick agrees to keep passing the `ODB_FOR_EACH_OBJECT_LOCAL_ONLY` flag for safety but maintains his design better serves the pluggable backend goal.

In the latest exchange, Taylor Blau responds to Patrick's position on deferring a larger refactor of the object_info struct by proposing an interim solution that would have callers pass two separate structs - one for request fields and another (via pointer) for response fields. While acknowledging this approach is "kind of ugly", Taylor expresses concern about the risk of uninitialized response fields in the current design, particularly for future contributors who might add new fields without proper initialization. This represents a compromise position that would mitigate immediate safety concerns without requiring the full struct split that he had previously proposed.

Earlier in the thread, Patrick addressed Taylor's feedback on patch 08/14 (`builtin/fsck.c` conversion), accepting a variable name change (`io` -> `oi`) and agreeing to document how `mark_unreachable_referents()` safely handles duplicate object visits. Another open discussion concerns `struct object_info` reuse in `packfile_store_for_each_object()` (06/14). Taylor had proposed an alternative mtime design for patch 12/14 that would keep GC-specific logic out of the core ODB layer via a generic `statp` field in `struct object_info`, providing a `object_info_gc_mtime()` helper as proof of concept.
