This is a bug report for the `git subtree` command, specifically about its `split` subcommand's path validation behavior. The reporter found that when splitting a subdirectory from a non-checked-out branch (due to Windows-incompatible paths elsewhere in that branch), `git subtree -P path split [rev]` incorrectly checks for the path's existence in the working directory rather than in the specified revision.

The current behavior forces users to create the directory locally as a workaround, even when the path exists in the target revision. The reporter argues this is misleading (the error suggests the path doesn't exist at all) and proposes changing the validation to check the specified revision rather than the working tree. The issue was encountered on Git for Windows 2.52.0, but the problem appears to be in the core `git subtree` logic.

The report is well-constructed - it clearly describes the unexpected behavior, provides reproduction steps, shows understanding of the underlying code issue, and offers a specific improvement direction. This looks like a legitimate bug that could affect users trying to extract subtrees from branches they can't check out fully, particularly on Windows where path limitations are more common. The suggested fix seems reasonable and focused, though it would need implementation and testing.
