This is part 9/12 of Adrian Ratiu's hook subsystem refactoring series, introducing a `jobs` option to control parallel hook execution. The patch allows API callers to specify how many jobs a hook can be parallelized across, though it defaults to 1 (sequential execution) for now. The change enables future parallel execution while maintaining current behavior.

The key addition is a `jobs` field in `struct run_hooks_opt` that determines whether output is buffered (for parallel jobs) or real-time (for sequential). The patch includes ASCII diagrams showing how output handling differs between the two modes, with parallel execution using run-command's buffering to avoid interleaving.

This continues the series' pattern of cleanly converting existing hook behavior to the new API while preserving functionality. The change is well-contained, touching only hook.c and hook.h, and builds on Jeff King's earlier suggestion about sideband handling. With maintainer approval already indicated for the series, this patch appears to be a straightforward step toward the goal of a unified hook API.
