This is a discussion about extending Git's ignore mechanism to support multiple named ignore files (like `editor.gitignore`, `build.gitignore`) alongside the standard `.gitignore`. The thread is in early exploratory stages, with no patches yet.

brian m. carlson responds to ZH L's RFC with several concerns. They note that editor-specific ignore rules should remain in per-user global ignore files rather than being project-specific, since different contributors use different editors. They also point out that adding new ignore file patterns would break backward compatibility for users on older Git versions that wouldn't recognize the new files.

The response suggests that most projects don't actually need this feature, citing examples where language ecosystems already consolidate build artifacts in single directories, keeping `.gitignore` files manageable. As an alternative, they reference a different proposal (linked in the email) for an explicit include syntax in ignore files, which they find more flexible but still challenging to implement without breaking changes.

The discussion remains open-ended, with brian m. carlson inviting other perspectives while making clear their own reservations about both the need for and feasibility of the proposed change. The tone is constructive but skeptical, emphasizing practical considerations around compatibility and questioning whether the problem is severe enough to warrant the solution.
