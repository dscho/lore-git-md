This is a discussion thread about extending Git's ignore file mechanism, specifically regarding a proposal to support multiple named ignore files (like `*.gitignore`) alongside the standard `.gitignore`. The original proposal from ZH L suggested this could help organize rules in large repositories by separating editor, build, and other rules into distinct files while maintaining backward compatibility.

brian m. carlson raised several objections, noting that editor-specific rules should be personal rather than project-wide, and pointing out that automatic loading of new ignore file patterns wouldn't truly be backward compatible since older Git versions would not recognize them. They suggested that if such a feature were to be implemented, an explicit include syntax or pragma might be preferable.

In this follow-up email, ZH L acknowledges these concerns, agreeing that editor-specific rules should remain personal and recognizing the backward compatibility risks. They clarify that their intent was not to push for implementation but to understand whether the idea had been considered and what objections might exist. The thread remains open with no clear consensus yet on whether to pursue the approach or stick with existing ignore file patterns. The discussion touches on practical considerations like version compatibility and the potential need for such a feature given current alternatives.
