This is patch 9/12 in Adrian Ratiu's hook subsystem refactoring series, introducing parallel execution capability to the hook API. The patch adds a `jobs` option that allows callers to specify how many hook processes can run in parallel, though all current hooks still default to sequential execution (jobs=1).

The key technical addition is the integration with `run-command`'s existing parallel execution infrastructure. When jobs=1 (the default), hooks maintain their current real-time output behavior via direct stderr writes. For jobs>1, output is buffered and de-interleaved using `run-command`'s ungroup=0 mode, with stderr routed through the sideband async thread that was introduced earlier in the series. The patch includes an ASCII diagram showing both execution modes and their output paths.

The implementation preserves backward compatibility while laying groundwork for future parallel hook execution. Jeff King suggested this approach to leverage existing `run-command` capabilities rather than reimplementing parallel output handling. The change is well-contained, touching only hook.c and hook.h to add the jobs parameter and adjust the parallel execution plumbing.

This continues the series' pattern of methodically converting hook types to the new API while maintaining existing behavior. With this patch, the infrastructure for both sequential and parallel execution is now in place, though no hooks actually use parallel mode yet. The remaining patches in the series will presumably build on this to enable parallel execution for appropriate hooks.
