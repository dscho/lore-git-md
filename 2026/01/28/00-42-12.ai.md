This is a feature proposal for multiple named ignore files in Git, building on the existing `.gitignore` mechanism. The author (ZH L) suggests allowing additional files like `editor.gitignore` and `build.gitignore` to be automatically merged with `.gitignore`, maintaining backward compatibility while providing better organization of ignore rules in large repositories.

The proposal is at an early stage - the author is primarily asking whether this idea has been considered before and whether there are fundamental design concerns. They note that some projects currently use external scripts to generate `.gitignore` files, which this feature could potentially replace.

The email doesn't propose specific implementation details or precedence rules, focusing instead on gauging initial interest and potential objections. This appears to be an RFC-style exploration of whether the concept would be welcome before investing time in a full implementation.

Key technical points that would need to be addressed in any follow-up include:
- The exact naming pattern for additional ignore files (`.gitignore` vs `*.gitignore`)
- Precedence order between multiple ignore files
- Interaction with existing ignore mechanisms (global, info/exclude)
- Performance implications of scanning for/processing multiple files

The proposal touches on a real pain point (managing large, mixed-purpose ignore files) but would need to demonstrate clear benefits over the current workarounds to gain traction.
