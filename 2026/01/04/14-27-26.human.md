This is a bugfix submission for a regression in `git subtree` functionality. The patch provides a minimal reproduction case demonstrating how commit 83f9dad7d6 ("subtree: fix split after annotated tag was squashed merged") broke subtree operations when dealing with squashed commits in certain repository topologies.

The issue occurs when a subtree's squash commit appears as a linear commit (rather than a merge commit) in the history, particularly when that commit is the parent of another subtree's changes. The new behavior fails to properly traverse ancestry when identifying subtree splits, resulting in broken history reconstruction during subtree operations.

The reporter has done thorough investigation, showing:
- The regression appears between Git 2.51.1 (working) and 2.52.0 (broken)
- The issue stems from a change in how subtree split markers are detected
- A complete reproduction script that creates a minimal test case
- Performance impact measurements showing the regression also affects operation speed

The test case demonstrates the core problem: when using the new code, a subtree split operation fails to include all expected commits in the resulting history because it only examines immediate parent commits rather than traversing ancestry to find relevant subtree markers. This matches the behavior observed in the larger Athena Framework monorepo that originally surfaced the issue.

The patch appears well-constructed and clearly demonstrates the regression. The reproduction script is particularly valuable as it isolates the issue from the complexity of the original monorepo where it was discovered. This should make it easier to verify any proposed fix.
