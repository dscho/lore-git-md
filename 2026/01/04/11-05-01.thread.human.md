This thread discusses a reported issue with `git stash` where untracked directories that conflict with previously tracked files are silently overwritten during a reset --hard operation. The original contributor, Tsahi Elkayam, proposed changing this to use reset --merge to prevent data loss, noting there was already a known-but-unfixed test case for this behavior.

Git maintainer Junio Hamano has now clarified that this behavior is intentional for the default `git stash` (without -u), as stashing is designed as a "panic button" operation that must succeed when invoked. The current behavior of removing conflicting untracked files is correct in this case, though Junio notes there may be edge cases worth examining when using `stash -u` (which saves untracked files) where the current implementation could prevent proper saving of untracked content.

The discussion reveals that what initially appeared to be a clear bug is actually intentional behavior in most cases, though there may still be room for improvement in the `-u` scenario. Junio's response provides important context about the design philosophy behind `git stash` prioritizing reliability over preserving untracked content in the default case.
