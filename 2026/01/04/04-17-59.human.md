This is a discussion about Git workflow philosophy, unrelated to the ongoing `git status` tracking branch feature development.

Junio C Hamano responds to Nico Williams' advocacy of a strictly linear rebase-based workflow (citing Sun Microsystems' historical practice) by clarifying that his own preference isn't about avoiding merges per se. He distinguishes between two types of linear histories: a clean "logical progression" focused on a single theme versus a messy "drunken-man's walk" of development iterations. Junio argues that a history with topic branches merged sequentially is clearer than forcing all topics into a single linear sequence, as it preserves the natural boundaries between different development efforts.

The exchange is purely theoretical - no changes to Git functionality are proposed. This side discussion emerged alongside but separate from the main thread about displaying push tracking information in `git status`. Junio's comments here reflect his long-standing views on version control history organization, previously expressed in other contexts.
