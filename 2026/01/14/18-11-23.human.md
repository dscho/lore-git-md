This is a bugfix for gitk's color configuration system, addressing inconsistencies in how ref and tag colors are rendered. The original patch from Shannon Barber fixed two issues where gitk was ignoring color settings: `tagfgcolor` was unused (all labels used `headfgcolor`), and head outlines were hardcoded black instead of respecting `headoutlinecolor`.

Johannes Sixt (Hannes), the gitk maintainer, acknowledges the technical correctness of the patch but provides constructive feedback on improving the commit message. He suggests a clearer structure that would explain: (1) the current behavior of gitk's four ref-drawing styles, (2) which parts are configurable versus hardcoded, and (3) the user-visible impact of the change. Hannes also notes a minor issue with the author/signer identity mismatch and some odd indentation in the commit message.

The patch itself appears to be a straightforward improvement that makes gitk respect its existing color configuration options more consistently, while maintaining backward compatibility for cases where colors remain hardcoded (non-head ref outlines and fills). This should give users more control over gitk's appearance through config files, though as Hannes points out, these settings aren't exposed in the UI which may limit their discoverability.
