This is a bugfix discussion in the hook subsystem, specifically addressing performance and deadlock issues in hook execution. Jeff King (Peff) provides a concrete demonstration of two problems in the current `feed_receive_hook_cb` implementation when handling stdin feeding for hooks.

The first issue shows how the current 500-line batching can deadlock when the pipe buffer fills up, blocking both stdin writing and stderr reading. The second issue demonstrates a performance penalty - when sending 501 refs (just over the 500-line batch size), there's an unnecessary 100ms delay as the code waits for stderr output that never comes.

Peff suggests two potential solutions: either require `ungroup=1` (which would simplify the code by avoiding the polling entirely) or implement proper poll() handling to manage both stdin writing and stderr reading simultaneously. The example uses a pre-receive hook test case that clearly shows the 100ms delay when exceeding the batch size.

This email advances the thread by providing measurable evidence of the performance impact and deadlock scenarios, helping inform the decision between the simpler `ungroup=1` approach versus a more complex poll()-based solution.
