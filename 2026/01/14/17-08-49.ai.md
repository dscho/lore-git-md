This is a technical discussion about hook execution internals, specifically addressing potential deadlocks in the stdin/stderr handling between Git and hooks. Jeff King (Peff) responds to Adrian Ratiu's proposed fixes by identifying a serious deadlock scenario in the current approach to feeding stdin to hooks while simultaneously reading their stderr output.

The core issue stems from how `feed_receive_hook_cb()` currently batches 500 lines of input before yielding to poll for stderr output. Peff demonstrates this can deadlock when:
1. Git writes 500 lines to hook stdin (filling pipe buffer)
2. Hook writes to stderr (blocking when pipe fills)
3. Git reads some stderr but hook immediately writes more
4. Git tries to write more stdin while hook is still blocked on stderr

Two solutions are proposed:
1. Require `ungroup=1` when using `feed_pipe` (simplest but loses stderr buffering)
2. Implement proper poll() handling for both stdin writing and stderr reading (more complex)

Peff also raises an important design question about whether buffering hook stderr (to prevent interleaving from parallel hooks) is worth losing real-time progress updates from individual hooks. The discussion reveals deeper architectural considerations about hook execution should balance between correctness, performance, and user experience.
