Here's a human-readable summary of the thread so far:

The thread began with Rajiv Sharma reporting unexpected behavior when pushing a new branch that points to an existing commit (HEAD~1). Instead of just creating the lightweight branch, Git was transferring large amounts of commit history unnecessarily, causing significant network overhead. This happens even when the target commit already exists on the remote.

Karthik Nayak has now responded, confirming this is the expected behavior but acknowledging it could be improved. He explains that the client lacks enough information about the remote's state to optimize the push - since the server only advertises ref tips (not all reachable commits), Git conservatively sends all objects needed to reconstruct the new branch's history. In his test case, this meant sending 4 objects when only creating a new ref was needed.

The discussion has identified this as a limitation in Git's push negotiation protocol rather than a bug. Karthik suggests potential solutions might involve having servers advertise more commit information, but notes this would require careful design decisions about what and how much to share. The thread remains open with no concrete proposals yet, but the discussion has clarified the technical constraints and opened the door for future optimizations to this common workflow.
