This is a discussion about push negotiation behavior when creating new branches pointing to existing commits. Karthik Nayak responds to Rajiv Sharma's bug report about excessive data transfer during such pushes.

Karthik confirms the observed behavior but argues it's not strictly a bug - rather a limitation in how Git's push negotiation works. When creating a new branch at an existing commit (HEAD~1 in the example), Git currently sends all objects needed to reconstruct that commit's history, even if the remote already has them. This happens because the client lacks information about commits not referenced by any branch on the remote.

The discussion highlights a real performance pain point, particularly for repositories with long histories, where this can result in GBs of unnecessary data transfer. Karthik suggests potential optimizations, such as having the server advertise more commit information during negotiation, but notes this would require careful design around what exactly to advertise and how much overhead it would add.

While there's a simple workaround (doing a `git pull` first to sync refs), the thread opens an interesting discussion about potential optimizations to Git's push negotiation logic, particularly around the refs/remote.c and builtin/send-pack.c areas. The exchange is technical but constructive, with both participants clearly demonstrating the issue and its implications.
