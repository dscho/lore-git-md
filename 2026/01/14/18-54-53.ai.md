This is a follow-up discussion about the recently merged `git status` push tracking feature, focusing on configuration ergonomics.

Junio Hamano weighs in on the ongoing debate about whether push tracking information should be shown by default in `git status` output. He proposes making the feature optional via a new `status.compareBranches` configuration that would allow users to specify which branches to compare against (e.g. `@{upstream}`, `@{push}`, or both). This would preserve backward compatibility while giving users who want the additional information a way to opt in.

The key technical points raised:
- Junio acknowledges Jeff King's concern that the push tracking output can create noise and potential confusion in some workflows
- Suggests a flexible configuration approach that could support future extensions beyond just `@{push}` comparisons
- Proposes keeping the traditional upstream-only behavior as the default to avoid regressing existing users
- The configuration syntax would use branch tracking notation familiar from other contexts

This moves the discussion from debating the merits of `@{push}` versus push tracking (which was settled in the merged implementation) to considering how to make the feature more configurable without disrupting existing workflows. Junio's proposal suggests a middle path that could satisfy both users who want richer status information and those who prefer minimal output.

The thread continues to focus on UI/UX considerations rather than implementation details, with the core technical work already merged. Junio's involvement as maintainer signals this is likely the direction the feature will take in a future iteration.
