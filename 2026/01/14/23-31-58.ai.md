This is a discussion about configuring branch comparison behavior in `git status`, specifically around the philosophical question of whether push/pull relationships should have special status compared to arbitrary branch comparisons.

Junio Hamano responds to Harald Nordgren's argument that push/pull relationships should be treated specially in `git status` output. While acknowledging the technical feasibility of Harald's position, Junio argues against artificially limiting comparisons to just push/pull relationships. He draws a parallel to the original ahead/behind implementation that only considered @{upstream}, which proved insufficient when push tracking was later added. Junio suggests there may be value in comparing against other references like release tags, particularly for maintainer workflows.

The exchange highlights an ongoing tension in the design:
- Harald's view that push/pull are fundamental Git operations deserving special treatment
- Junio's preference for a more flexible, extensible configuration that isn't limited by current workflow assumptions

This continues the thread's exploration of how configurable the branch comparison feature should be, with Junio advocating for keeping options open for future use cases beyond just push/pull relationships. The discussion remains philosophical rather than technical at this point, focusing on Git's conceptual model rather than implementation details.
