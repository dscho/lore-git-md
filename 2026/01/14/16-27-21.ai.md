This is a discussion about push negotiation behavior when creating new branches pointing to existing commits. Karthik Nayak responds to Rajiv Sharma's bug report about excessive data transfer during such pushes, explaining the current behavior is expected but potentially improvable.

Karthik confirms Rajiv's observation that pushing a new branch at an existing commit (HEAD~1) sends more objects than expected - in his test case, 4 objects (C1, C2, C3 and a tree) when only creating a new ref was needed. He explains this happens because the client (base2 in his example) lacks knowledge about the remote's newest commit (C4), preventing it from finding the common ancestor (C3) efficiently. Without this context, Git conservatively sends all objects needed to reconstruct the new ref's history.

The discussion identifies this as a negotiation protocol limitation rather than a bug - the server only advertises ref tips, not all reachable commits. Karthik suggests potential optimizations like having servers advertise additional commit information beyond ref tips, but notes this would require careful design around what and how much to advertise. The thread remains open-ended, presenting an opportunity to improve push efficiency for this common workflow without yet proposing concrete changes.
