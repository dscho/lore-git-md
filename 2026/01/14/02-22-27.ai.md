This is a follow-up discussion about the recently merged `git status` push-tracking feature, focusing on triangular workflow ergonomics. D. Ben Knoble chimes in to share their own workflow experience, which aligns with Jeff King's earlier example of using a mirror remote for pushing while tracking a different branch.

Knoble responds to Harald Nordgren's suggestion about using `push.default=upstream` in scripts, noting that their own workflow (like Peff's) relies on pushing to a mirror remote without specifying the branch each time. The key point is that some established workflows depend on the convenience of argument-less `git push` to a predefined destination, even when the tracking branch points elsewhere - a pattern that the new push-tracking status display might not serve optimally.

The exchange continues to surface real-world usage patterns that may inform future configuration refinements, though no concrete changes are proposed here. Knoble's contribution reinforces that the feature's assumptions about push destinations don't universally match all workflows, particularly those involving mirror remotes where push destination is stable but tracking branch differs.
