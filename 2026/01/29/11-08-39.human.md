This is a technical discussion about interface design for Git's object database (ODB) abstraction effort, specifically around how to handle backend-specific metadata like modification times (mtimes) and object paths.

Jeff King (Peff) responds to Patrick Steinhardt's earlier message about the ODB abstraction series, focusing on two key design questions for the API:

1. Whether the ODB interface should provide opaque context handles (cleaner API but more restrictive) versus exposing optional backend-specific information (more flexible but pushes complexity to callers)

2. Where domain-specific logic like mtime interpretation should live - centralized in the ODB layer versus distributed to callers like fsck and repack

Peff leans toward the second approach, arguing it keeps specialized logic together in the subsystems that need it rather than forcing the ODB layer to accommodate every possible need. He notes this mirrors how fsck currently handles paths via `for_each_loose_file_in_source()` rather than through the new ODB interface.

The discussion doesn't propose concrete changes to the current patch series but provides architectural guidance that may influence future iterations of the ODB work. It reflects careful consideration of how to balance abstraction with practical needs of different subsystems.
