This thread explores adding a shorthand syntax for referencing a repository's primary branch, with Harald Nordgren driving the effort through multiple iterations. The discussion has evolved from an initial `@{default}` proposal to the current `@{primary}` syntax, with the implementation approach shifting from using `init.defaultBranch` configuration to relying on upstream tracking (typically `origin/HEAD`) after Junio Hamano raised concerns about config reliability.

The technical work introduces `branch_get_primary_ref()` and supporting infrastructure, with tests showing the shorthand works in commands like rev-parse, checkout, and status. However, fundamental questions remain about whether this approach adequately captures the "primary branch" concept across all workflows - particularly for repositories without clear remote tracking or with diverging local/remote branch names. Kristoffer Haugsbakk's earlier observation about `git var GIT_DEFAULT_BRANCH` providing similar functionality without new syntax remains an open consideration.

The thread reflects a tension between the convenience of a shorthand reference and Git's emphasis on semantic precision in branch naming. While the technical implementation appears sound, the discussion now centers on higher-level design questions about the feature's purpose and whether remote-HEAD-based resolution aligns with user mental models across diverse workflows. Junio has previously suggested alternative syntax like `@{dumbo}` modeled after `@{push}`, indicating the naming and exact semantics may still in flux.
