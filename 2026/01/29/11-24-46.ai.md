This is a technical discussion about case sensitivity in `git config --get-regexp` matching. Jeff King (Peff) responds to Pushkar Singh's RFC about using `REG_ICASE` for case-insensitive matching, explaining why the current implementation's selective lowercasing is necessary due to Git's config key semantics.

Peff clarifies that config subsections (middle parts of dotted keys) must remain case-sensitive, while only the section and key parts should be case-insensitive. He provides concrete examples showing current behavior where `foo.Bar.baz` and `foo.bar.baz` are intentionally treated as distinct. The discussion reveals undocumented but expected behavior where common camelCase config names (like `fetch.unpackLimit`) work in queries due to the current implementation.

Rather than adopting `REG_ICASE`, Peff suggests the status quo may be preferable, though he acknowledges potential edge cases where the current regex rewriting could produce incorrect matches. He notes the lowercasing behavior, while imperfect, provides useful ergonomics by matching how Git internally canonicalizes config keys. The thread leaves open whether to document current behavior more thoroughly or consider deprecating the automatic lowercasing feature.
