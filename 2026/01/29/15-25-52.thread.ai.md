Thread introduces shorthand syntax to reference a repository's primary branch, evolving from `@{default}` to `@{primary}` in v3 after design discussions. Harald Nordgren's latest work-in-progress implementation abandons the initial `init.defaultBranch`-based approach in favor of resolving via upstream tracking infrastructure (typically `origin/HEAD`), directly addressing Junio Hamano's concerns about config reliability and better matching real-world usage patterns where remote tracking branches are primary indicators.

Technical implementation adds `branch_get_primary_ref()` and supporting infrastructure, reusing existing branch tracking machinery with new `primary_mark` parser in object-name.c. Tests verify resolution in rev-parse, checkout, and status contexts, showing the shorthand works as expected when pointing to the branch tracking remote/HEAD. Documentation describes this as resolving to "the primary branch via upstream tracking."

Key open questions remain about whether this sufficiently captures the "primary branch" concept across all workflows, particularly in repositories without clear remote tracking or with multiple primary branches. The discussion has shifted from implementation details to semantic questions about what "primary branch" should mean in Git's reference system, with Junio previously suggesting alternative syntax like `@{dumbo}` modeled after `@{push}`. Kristoffer Haugsbakk's earlier observation about `git var GIT_DEFAULT_BRANCH` providing similar functionality without new syntax remains an unresolved counterpoint.

The thread reflects ongoing tension between Harald's goal of convenient shorthand and the project's emphasis on semantic precision when branch naming diverges between local and remote repositories. Testing continues to validate the technical soundness of the upstream-tracking approach while leaving higher-level design questions about the feature's purpose and naming. Future discussion may focus on whether the current implementation's remote-HEAD-based resolution matches user expectations for a "primary branch" reference across diverse workflows, and how this relates to existing functionality like `git var GIT_DEFAULT_BRANCH`.
