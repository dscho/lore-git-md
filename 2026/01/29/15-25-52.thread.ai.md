Thread introduces shorthand syntax to reference a repository's primary branch, evolving from `@{default}` to `@{primary}` in v3 after design discussions. Harald Nordgren's latest work-in-progress implementation resolves via upstream tracking infrastructure (typically `origin/HEAD`), addressing Junio Hamano's concerns about config reliability while diverging from the `init.defaultBranch`-based approach originally proposed.

Technical implementation adds `branch_get_primary_ref()` and supporting infrastructure, reusing existing branch tracking machinery with new `primary_mark` parser in object-name.c. Tests verify resolution in rev-parse, checkout, and status contexts. Documentation describes this as resolving to "the primary branch via upstream tracking."

Junio Hamano questions the terminology shift from "default" to "primary", noting `init.defaultBranch` already has an established meaning. He observes the current remote-tracking approach solves a different problem than Harald's original use case, creating tension between:
1. Convenient shorthand needs
2. Semantic precision in branch naming
3. Alignment with user expectations
4. Relationship to existing mechanisms like `git var GIT_DEFAULT_BRANCH`

Key open questions:
- Whether remote-HEAD-based resolution sufficiently captures "primary branch" across all workflows
- How this relates to repositories without clear remote tracking
- If the implementation matches the originally stated problem (now diverged from `init.defaultBranch`)
- Kristoffer Haugsbakk's earlier observation about `git var GIT_DEFAULT_BRANCH` providing similar functionality

The discussion has shifted from implementation details to fundamental design questions about the feature's purpose and naming. Junio suggests the current approach may need clearer distinction from default branch concept if it represents a new primitive. Testing continues to validate technical soundness while higher-level semantics remain unresolved. Future discussion will likely focus on reconciling the implementation's remote-tracking behavior with the original problem statement and user expectations.
