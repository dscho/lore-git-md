This is a technical review response in the ongoing promisor remote enhancement series (patch 8/9). Patrick Steinhardt provides feedback on Christian Couder's implementation of server-advertised filter storage.

Patrick suggests two improvements to the patch that adds in-memory storage of server-advertised filters for promisor remotes. First, he finds the variable name `captured_filters` unclear and proposes renaming it to `advertised_filters` to better reflect its purpose. Second, he questions whether a promisor remote could ever be accepted without an advertised filter, suggesting this might warrant a `BUG()` check for robustness.

The discussion continues the thread's focus on careful memory management and clear naming conventions, with Patrick noting his initial confusion about the lifetime of filter strings before seeing how they're properly handled. This patch builds on previous work to enable dynamic filter combination from multiple promisor remotes, with the current implementation storing these server-provided filters in the promisor remote configuration.
