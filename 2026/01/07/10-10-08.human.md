This is the eighth iteration of Patrick Steinhardt's patch series introducing a new `git history` command, focused on the `reword` subcommand for rewriting commit messages. The series builds on Git's replay machinery to provide a faster, in-memory alternative to interactive rebase for simple history editing operations.

Key changes in v8:
- The series has been rebased on recent changes to the replay infrastructure
- The implementation now fully leverages the replay subsystem instead of custom commit-walking logic
- The `split` subcommand has been split out to a future series to focus attention on core mechanics
- Added support for updating all descendant branches by default (addressing stacked branch workflows)
- Introduced `--ref-action` option to control which refs get updated (branches, HEAD, or just show updates)
- Improved documentation of limitations and differences from rebase

The patch looks well-structured with thorough test coverage. It addresses previous feedback by:
- Limiting scope to local branches only (per Newren's immutability arguments)
- Using direct branch commit checks for performance (Wood's suggestion)
- Cleaning up configuration documentation (Haugsbakk's note)

Remaining open questions noted in the thread:
- Handling of stacked branch workflows (Knoble's concern)
- Justification for three operation modes
- Final documentation updates for new behavior

This appears to be a high-quality contribution that provides a useful new tool for history editing while carefully considering performance and workflow implications. The separation of concerns (splitting out the `split` subcommand) and thorough test coverage suggest it's ready for serious review.
