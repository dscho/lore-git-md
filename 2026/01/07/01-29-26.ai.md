Bugfix patch addressing race conditions in `git fsck` when run on live repositories, part of an ongoing collaboration between Elijah Newren and Jeff King (Peff) under Junio Hamano's guidance. This v2 iteration incorporates feedback from the previous round.

The core issue is that `git fsck` can report false positives when run concurrently with repository modifications, as it reads refs at operation start/end. This is particularly problematic for automated maintenance and forge operations. The solution now takes a snapshot of refs at program start, checks connectivity, then verifies against the snapshotted refs.

Key technical changes in v2:
- Adopts Junio's suggested `struct ref_snapshot` design instead of parallel arrays
- Handles both forward (new objects) and reverse (GC deletion) race cases
- Extends to command-line specified refs (addressing Peff's edge case)
- Includes `odb_reprepare()` for fresh object DB state
- Retains timestamp-based reflog filtering with TODO markers for improvement
- Documents worktree/index limitations explicitly

The patch modifies `builtin/fsck.c` (~90 lines) to implement this snapshot approach while preserving existing behavior for non-concurrent cases. It demonstrates good responsiveness to review feedback while maintaining clear technical boundaries around the solution scope.

Open questions remain around reflog marker approaches (timestamps vs `refs_for_each_reflog_ent_reverse()`) and network filesystem clock skew edge cases. The implementation favors availability over strict consistency, making it particularly suitable for production environments like forges.
