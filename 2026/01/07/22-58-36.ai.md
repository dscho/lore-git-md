This is a performance investigation thread about `git pack-refs --all` slowness on large repositories with millions of refs stored on NFS. Martin Fick provides `perf(1)` profiling data that confirms the mmap/NFS interaction is the primary bottleneck, with roughly two-thirds of the time spent in memory operations (memcmp, page faults) and object header parsing.

The flame graph shows three main hotspots: SSE-optimized memcmp operations (29.8%), object header unpacking (30%), and packed-refs storage creation (8.7%). The high percentage of page faults (totaling ~42% across all sections) strongly supports Patrick Steinhardt's earlier hypothesis about mmap being the root cause. While the data doesn't reveal new technical insights beyond what was already suspected, it provides concrete measurements validating the theory.

The thread remains at an impasse between short-term mitigation options (NO_MMAP builds, lock reordering) and Patrick's advocated long-term solution of migrating to the reftable backend. Martin's inability to extract clear action items from the perf data suggests the next steps may require deeper analysis from someone more familiar with Git's mmap internals, though production environment limitations continue to constrain diagnostic options.
