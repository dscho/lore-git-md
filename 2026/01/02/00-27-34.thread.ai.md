Performance optimization and modernization of Git's byte-swapping functions in `compat/bswap.h` (initial patch from Rostislav Krasny). The series replaces manual bit-twiddling implementations with `memcpy`-based type punning for better maintainability and consistent behavior while avoiding undefined behavior. Key technical scope: complete network byte order API including new 16-bit variants (`bswap16`, `ntohs`, `htons`, `put_be16`), renamed functions for consistency (`default_swab32` -> `default_bswap32`), and optimized implementations of `get_be32/64`/`put_be32/64` using compiler intrinsics (GCC/Clang `__builtin_bswap*`, MSVC `_byteswap_*`) with portable fallbacks.

Jeff King (Peff) conducted detailed benchmark analysis showing: (1) -O0 results are not meaningful for real use, (2) -O3 speedups appear to be loop optimization artifacts, (3) Clang -O2 shows 1.8x speedup but may be test-case specific, (4) aligned 8-byte reads show no performance difference. Peff concludes the changes improve readability/maintainability but questions real-world performance benefits.

Rostislav Krasny clarifies the primary motivation is code simplicity and API consistency rather than performance gains, noting the inconsistency between optimized `ntoh*` macros and complex pointer-handling in `get_be*` functions. He acknowledges -O0/-O1 benchmarks are less meaningful for production but maintains the changes show no regression. The discussion reveals differing perspectives: Peff focuses on measurable performance impact while Krasny emphasizes code quality improvements.

Current status: initial submission awaiting broader review. Open questions: portability verification across additional architectures (ARM, PPC, RISC-V) and compilers, type-punning safety in edge cases, and whether code quality improvements alone justify changes to these critical-path functions. The implementation remains carefully crafted but needs scrutiny from multiple reviewers, particularly on platforms beyond x86-64. Peff's analysis provides methodology for evaluating real-world impact while Krasny's response reframes the justification around maintainability benefits.
