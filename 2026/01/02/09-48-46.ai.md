This is a discussion about commit organization in the final stages of a feature enhancement for `git status` that shows divergence from push/tracking branches. Kristoffer Haugsbakk responds to Harald Nordgren's concerns about restructuring commit history mid-development, advocating for Git's conventional approach of presenting a clean, logical progression of changes rather than preserving the actual development history.

Haugsbakk acknowledges Nordgren's preference for squashing changes into one or two commits (a common GitHub workflow) but argues this loses valuable context about the logical separation of concerns. He contrasts this with Git's preferred approach where each commit in a series should represent a self-contained, logical step toward the final goal, even if that requires rewriting history to present a cleaner evolution than what actually occurred during development.

The email highlights a cultural difference between GitHub's squash-and-merge workflow (where developers treat branches as workspaces) and Git's mailing-list workflow (where each patch series should tell a coherent story). Haugsbakk notes that while squashing can produce a "clean" history by removing back-and-forth changes, it can also create bloated, lossy commits that obscure the reasoning behind individual changes. He suggests that Git's approach, while requiring more effort to restructure commits, produces a more maintainable history.

This discussion occurs after the technical aspects of the feature have been resolved (the implementation now uses Git's existing branch tracking mechanisms following Junio Hamano's feedback) and focuses solely on the presentation of the changes for merging. The thread demonstrates how Git's development culture values not just the final code but also the clarity of its evolution in the project history.
