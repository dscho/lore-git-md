This is part of the ongoing `the_repository` removal effort, specifically addressing how to handle configuration values that are currently stored globally. The patch series (from an Outreachy intern mentored by Christian Couder) introduces a per-repository approach for storing values like `core.attributesFile`, `core.sparseCheckout`, and `branch.autoSetupMerge`.

In this email, the author responds to feedback from Phillip Wood, who suggested architectural improvements to the approach. The key points are:

1. Phillip emphasizes that the critical invariant is preserving when the config is parsed (eager loading), not necessarily keeping the exact implementation of `git_default_core_config()`.

2. He recommends embedding the configuration struct directly in `struct repository` (like `repo_settings`) rather than heap-allocating it, which would simplify memory management.

3. Naming is discussed - Phillip prefers `repo_config` over the current `config_values`, though the author points out there's already a struct with that name.

4. The file location (`config.[ch]` vs `environment.[ch]`) is still under consideration, with Phillip suggesting `environment.[ch]` as a temporary home.

The exchange shows the author incorporating feedback while noting some naming constraints. The thread demonstrates the careful balancing act in this refactoring work - eliminating globals while maintaining existing behavior and finding the right places for new structures in Git's architecture.
