RFC patch series by Olamide Caleb Bello (Outreachy intern mentored by Christian Couder) introducing `struct repo_config_values` to eliminate global configuration variables as part of `the_repository` removal effort. Series demonstrates approach across three config value types: string (`core.attributesFile` in part 1), boolean (`core.sparseCheckout` in part 2), and enum (`branch.autoSetupMerge` in part 3), affecting 30+ files across branch, checkout, push, submodule, sparse-checkout, clone, grep, mv, and worktree commands.

Part 1 moved `core.attributesFile` from global `git_attributes_file` to `attributes_file_path` in new `struct repo_config_values` embedded in `struct repository`. Part 2 followed same pattern for `core.sparseCheckout` boolean, replacing global `core_apply_sparse_checkout` with `sparse_checkout` field. Part 3 (current patch) completes the series by moving enum `branch.autoSetupMerge` from global `git_branch_track` to `git_branch_track` field in `repo_config_values`, initialized to `BRANCH_TRACK_REMOTE`. Updates access points across branch, checkout, push, and submodule commands to read from repository's config struct.

Junio C Hamano raises key architectural questions in two areas: (1) whether all config values should be repository-scoped (pointing to other nearby globals like whitespace handling and compression levels that may need different treatment), and (2) specific concerns about the `core.sparseCheckout` transition where he notes the `USE_THE_REPOSITORY_VARIABLE` macro removal in `builtin/backfill.c` may be premature since repository access is still needed. He observes that while variable names change (e.g., `core_apply_sparse_checkout` to `the_repository->config_values.sparse_checkout`), the fundamental access patterns remain similar, suggesting the architectural changes should do more than just mechanical renames.

In follow-up discussion, Junio identifies two additional technical concerns: (1) a bootstrapping problem where `git_config(git_default_config)` cannot safely initialize a second repository's config struct if some values remain global, and (2) an implementation gap where `repo_config_values_init()` initializes `git_branch_track` but not the other config values (`attributes_file_path` and `sparse_checkout`) moved in the series. He suggests this function should handle both default initialization and repository-specific config loading.

Core design consistently embeds config storage directly in `struct repository` (avoiding allocation, matching `repo_settings` pattern). Phillip Wood's v1 feedback incorporated throughout: struct renamed from `config_values` to `repo_config_values`, embedded directly in repository. Technical changes include new fields in config struct (`attributes_file_path`, `sparse_checkout`, `git_branch_track`), updates to access patterns (all affected commands becoming repository-aware), and removal of global declarations.

Open questions now include: final struct location (`config.[ch]` vs `environment.[ch]`), naming (`repo_config_values` vs `repo_config`), scope determination (which configs should remain global vs become repository-specific), initialization strategy (handling both defaults and repo-specific values in `repo_config_values_init`), and whether access pattern changes should be more substantial than just routing through repository struct. As an Outreachy intern project under Christian Couder's mentorship, this series demonstrates complete pattern for config handling while making progress on `the_repository` removal, but Junio's feedback indicates need for deeper consideration of both architectural principles (scoping, initialization) and specific implementation choices.
