This is a user help request about `git rebase` behavior in the Linux kernel repository context. Alan Mackenzie is trying to move his local patches from the linux-6.13.y stable branch to master, initially encountering confusing conflicts in files he never modified. The thread reveals this was due to attempting to rebase across a large divergence between branches (2012 commits), where intermediate kernel releases had modified files that now conflicted during rebase.

A private correspondent helped diagnose the issue by identifying the actual commit where Alan's changes began (733381204a86 "Linux 6.13.3-rc1"), allowing a targeted rebase that only includes his eight commits. While this solves the immediate problem, Alan now faces the expected but still painful task of resolving conflicts in his actual changes (a 3400-line diff). The email highlights a common pain point - the lack of a `--dry-run` option for `git rebase` to preview conflicts - and demonstrates how kernel maintainers often need to be precise about commit ranges when working across stable branches. The solution involves careful commit range specification rather than branch names when the branches have significantly diverged.
