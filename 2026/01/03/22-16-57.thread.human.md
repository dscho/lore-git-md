This thread discusses how Git should handle `.gitignore` files (called "exclude files" in Git's code) that aren't UTF-8 encoded, particularly focusing on UTF-16LE files with BOM markers that Windows PowerShell creates by default. The original patch by Matthieu Beauchamp-Boulay proposed comprehensive Unicode handling with BOM detection and conversion to UTF-8, but reviewers have raised concerns about this approach.

Junio Hamano initially questioned whether Git should assume UTF-8 for these files at all, while Torsten Bögershausen suggested simpler technical solutions like detecting UTF-16 via null bytes rather than full conversion. Now brian m. carlson has entered the discussion with a strong counterargument - they demonstrate that Git has historically allowed arbitrary byte sequences in exclude files to match Unix filename conventions, and that enforcing UTF-8 would break this behavior. They point out inconsistencies with how Git handles BOM-marked files in other contexts like config files.

The core tension is between Windows usability (where UTF-16LE files are common) and Git's cross-platform design principles. While the original proposal aimed to solve a real pain point for Windows users, reviewers are concerned it might introduce new problems elsewhere. brian m. carlson suggests the issue might be better addressed by educating Windows users about PowerShell's encoding behavior rather than changing Git's core behavior, though this leaves the usability issue unresolved. The thread is at an impasse awaiting either a revised technical proposal or consensus on whether to treat this as a Windows-specific edge case.
