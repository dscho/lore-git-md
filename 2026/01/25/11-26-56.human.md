This is a documentation discussion thread about terminology in Git's error messages, specifically around the term "revision" versus "commit" in the context of the `git last-modified` command.

Kristoffer Haugsbakk and Patrick Steinhardt are debating the precise meaning of "revision" in Git's documentation. The thread stems from earlier work on hardening `git last-modified`'s error messages, where Toon Claes had to choose between using "revision" or "commit-ish" in user-facing output.

Patrick notes that while gitglossary(7) defines "revision" as a synonym for "commit", he finds this definition too narrow - in practice, revisions can name any object type (like trees via `HEAD^{tree}`) and are more about the naming syntax than the underlying object type. Kristoffer responds that he's always understood "revision" as a generic term similar to "commit", separate from the technical definition in gitrevisions(7).

This is a subtle but important distinction for error messages and documentation clarity. The discussion shows how even seemingly simple terminology choices can have implications for user understanding and technical accuracy. The thread doesn't propose any immediate changes but contributes to an ongoing conversation about how Git's concepts should be named and explained to users.
