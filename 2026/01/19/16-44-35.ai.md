This is a feature patch adding a new `--maximal` option to `git rev-list`, currently in active discussion about naming and interface design. The patch implements functionality to filter commit output to only those that are maximal in the reachability order - essentially the "frontier" commits not reachable from others in the input set. This has applications for bundle URIs and other cases where you want to identify key reference points.

The technical implementation adds a `CHILD_VISITED` flag (bit 28) to track reachability during the walk, extending Git's object flag space usage to 29/32 bits. The core logic lives in revision.c and commit.c, with thorough test coverage including interaction with `--first-parent`.

The current debate centers on naming and documentation clarity. Author Derrick Stolee defends the mathematically precise `--maximal` terminology from order theory, while Johannes Sixt proposes alternatives like `--only-maximal`, `--hide-reachable`, or `--topmost-only`, arguing Git traditionally avoids mathematical terms in favor of intuitive names. There's also discussion about making `--maximal` and `--boundary` mutually exclusive due to potentially confusing interaction.

The patch appears technically sound with complete test coverage, but the interface design questions suggest this may need another revision before consensus is reached. The flag bit usage (now at 28/32 bits) may also warrant broader discussion about long-term implications for Git's object flag space.
