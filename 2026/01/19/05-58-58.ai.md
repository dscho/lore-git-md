This is a tangential discussion in the ongoing thread about configurable branch comparison in `git status`. Chris Torek weighs in on Ben Knoble's suggestion to include `@{push}` by default in the new `status.compareBranches` configuration.

Torek supports the idea of defaulting to both `@{upstream}` and `@{push}` comparisons, noting this would particularly benefit triangular workflows common on GitHub (where users fork a repo, clone their fork locally, and need to track both the original upstream and their fork). He acknowledges the complexity when additional remotes are involved (like corporate backups), but sees value in having the comparison capability even in those cases.

The email doesn't propose any code changes, but reinforces the usability perspective that informed the original feature design. It's worth noting this comes after Jeff King identified and is addressing memory management issues in the implementation, suggesting the high-level design questions are still being refined even as the technical foundations are being solidified.
