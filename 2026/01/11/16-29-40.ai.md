This is a user support thread about rebase difficulties when working with the Linux kernel stable repository. Pushkar Singh responds to Alan Mackenzie's query about unexpected conflicts during rebase, explaining that the issue stems from rebasing against a moving target branch (linux-6.13.y) rather than a fixed base commit.

Pushkar provides a detailed technical explanation of why Alan is seeing conflicts in files he never touched - because Git is attempting to replay not just Alan's local commits but also all the upstream commits that have accumulated on linux-6.13.y since Alan first branched. The key insight is that `git status` showing "ahead by 2012 commits" indicates these are upstream changes, not Alan's work.

The response includes concrete solutions:
1. Finding the original fork point using `git merge-base`
2. Rebasing only the local commits using `--onto` with the correct base
3. Using `git range-diff` to preview what would be rebased

The thread is still early in the discussion, with this being the first substantive technical response to Alan's initial query about rebase problems with an older Git version (2.52.0 from 2021). The advice appears technically sound and directly addresses the symptoms described, though we don't yet see Alan's confirmation that it resolved his issue.
