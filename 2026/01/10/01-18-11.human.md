This is a bugfix for the `git subtree` contrib command, specifically addressing issues with detecting rewritten subtree commits during split operations. The patch comes from Colin Stagner and targets the `maint` branch.

The core issue is that `git subtree split --prefix` fails to properly handle rebased or cherry-picked subtree commits, potentially producing incomplete history. The current logic only checks for `git-subtree-*` trailers without validating whether the commit has been rewritten, which can lead to incorrect pruning of history when splitting different paths.

The fix introduces a new `find_other_splits()` function that performs more thorough validation of subtree merge commits by:
1. Checking that the first parent matches the `git-subtree-mainline` trailer
2. Verifying the commit still has multiple parents
3. Ensuring the subtree directory is outside the current prefix

The patch also improves performance by:
- Caching ignored subtrees in a `notree` file
- Using `rev-list --stdin` to avoid repeated history traversals
- Eliminating redundant `git show` calls that were previously made for every commit

The changes come with extensive test coverage that verifies correct behavior with:
- Multiple subtrees
- Nested subtrees
- Rebases/cherry-picks of subtree commits
- Various split/rejoin scenarios

This appears to be a well-considered fix for a subtle edge case in subtree operations, with careful attention to both correctness and performance. The commit message clearly explains the problem and solution, and the test additions provide good coverage of the affected scenarios.
