This is a discussion about adding Bazel build support to Git, following up on earlier technical objections. The author, Son Luong Ngoc, acknowledges brian m. carlson's concerns about the current implementation's limitations - particularly around hardcoded paths (SHELL_PATH, PERL_PATH, PYTHON_PATH) and platform assumptions that don't match Git's existing build system flexibility. 

The email clarifies that in Bazel's ecosystem, these paths would normally be handled through toolchain definitions rather than hardcoding, pointing to existing Bazel rules for shell, Python and Perl that include such toolchain support. However, the author concedes their current work is tailored to a specific use case (building libgit for Go integration) rather than being a general-purpose solution.

Facing the maintenance burden concerns raised earlier, the author now plans to pursue an out-of-tree approach via the Bazel Central Registry, with clear labeling as an unofficial, community-maintained option. This represents a scaling back from the earlier proposal for in-tree Bazel support, though the door remains open for future contributions to address the configurability gaps. The technical discussion remains focused on how Bazel's toolchain system could theoretically meet Git's build requirements, though no concrete implementation of this is yet proposed.
