Phillip Wood responds to Esteban Küber's proposal for improving merge conflict metadata during rebase operations. This is part of an ongoing discussion about making Git's conflict information more accessible to tools like rustc without requiring Git command invocations.

Wood provides detailed feedback on the current state of Git's rebase metadata files and their limitations. He notes that while some information can be gleaned from files like .git/rebase-merge/head-name, there are edge cases where this approach fails (like when other commands are run during a rebase). He also cautions against relying too heavily on parsing MERGE_MSG due to potential format changes.

The key technical contribution is Wood's proposal to have Git write an "onto-desc" file during rebase that would explicitly describe the target commit in a structured way. This would help both tools and Git's own status output understand the rebase context better. He outlines several common cases this would handle, though notes some limitations when dealing with object IDs rather than refnames.

Regarding the conflict marker enhancements, Wood expresses skepticism about injecting branch names directly into conflict markers, particularly for rebases where the relationship between HEAD and branch names isn't always straightforward. He suggests alternative phrasing like "[from 'main']" might be clearer than implying HEAD is exactly the branch.

The discussion continues to explore the tension between making metadata accessible to tools while maintaining Git's internal architecture constraints. Wood's response adds important implementation considerations to the thread, particularly around edge cases and the semantic meaning of branch names during complex operations.
