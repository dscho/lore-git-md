This is a performance investigation thread about `git pack-refs --all` slowness on large repositories with high ref counts (~3M refs). The discussion has evolved from initial I/O concerns to focus on mmap/NFS interaction and lock duration optimization.

Martin Fick provides new test results showing that pre-reading the pack file (by dropping caches and `cat`-ing it to `/dev/null`) reduces `pack-refs` runtime from 5+ minutes to under 20 seconds, while pre-reading the packed-refs file has no effect. This confirms Jeff King's hypothesis that the bottleneck is in mmap'd packfile access rather than packed-refs handling. The tests were conducted on a Gerrit server environment with ~90M objects, 50GB data, and NFS storage.

The email also clarifies that Git uses sequential access (not binary search) for packed-refs during write-out, and that the observed delays occur between write operations rather than during the writes themselves. Martin notes that while JGit's performance (20s) suggests mmap may be the culprit, NFS remains a hard requirement for Gerrit's multi-mirror replication needs. He expresses interest in Jeff's suggestion to try a NO_MMAP build but notes it would be more useful as a runtime configuration.

This continues the thread's progression toward understanding the tension between Git's implementation and large-scale deployment constraints, with the latest findings pointing squarely at mmap/NFS interaction as the primary performance bottleneck. The discussion remains technically focused on diagnosing the exact nature of the slowdown rather than proposing solutions.
