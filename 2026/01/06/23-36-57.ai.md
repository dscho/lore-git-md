Bugfix patch addressing race conditions in `git fsck` when run on live repositories, with refinements based on Jeff King's review. This is part of an ongoing collaboration between Elijah Newren and Jeff King to make `git fsck` more robust during concurrent repository operations.

The core issue involves `git fsck`'s vulnerability to races when refs are modified while it's running. The current implementation can produce false positives about missing objects when new objects are added after `fsck` starts scanning the object database but before it checks refs. The patch introduces a snapshot mechanism to lock in ref states at the object scan start.

Key technical changes in this iteration:
- Adds `struct ref_snapshot` to capture ref states atomically
- Extends snapshotting to command-line specified refs (addressing a gap Jeff identified)
- Calls `odb_reprepare()` to ensure fresh object database state
- Documents remaining limitations regarding worktree/index races
- Adds TODO markers for future improvements to reflog handling

The solution now handles both directions of races - not just new objects being added (original case) but also objects being deleted during GC (Jeff's reverse case). The implementation favors allowing concurrent operations over strict consistency, prioritizing availability for busy servers.

This version shows good responsiveness to review feedback, with Elijah systematically addressing Jeff's technical concerns about edge cases and implementation details. The discussion remains focused on practical solutions for production environments, particularly relevant for GitHub/GitLab-scale operations where this race was originally observed.
