This is a technical discussion about the ODB abstraction series, specifically addressing how to handle mtime information for objects in cruft packs. The exchange between Patrick Steinhardt and Taylor Blau focuses on whether mtime handling should be implemented within the object storage backend (Patrick's approach) or at a higher level via a generic stat structure (Taylor's proposal).

Taylor argues that adding a `statp` field to `struct object_info` would provide a more general solution that keeps GC-specific mtime logic out of the core ODB layer. He demonstrates how this could work with a helper function `object_info_gc_mtime()` that handles the cruft pack special case. Taylor notes that the current `object_info` struct already leaks some backend-specific details (like `disk_sizep` and `delta_base_oid`), so adding `statp` wouldn't introduce new abstraction leakage.

Patrick maintains that his approach - where each backend handles mtime internally - better serves the pluggable backend goal by keeping all backend-specific logic contained within the backend implementations. He sees Taylor's proposal as moving cruft pack logic outside the backend where it doesn't belong.

The discussion reveals a fundamental difference in perspective: Taylor wants to avoid baking GC-specific semantics into the ODB layer, while Patrick prioritizes keeping backend behavior fully encapsulated. This is the last major architectural question blocking the ODB abstraction series from being merged. Both agree the end result would function the same, but differ on where the abstraction boundary should be drawn.
