This thread explores improvements to `git add -p`'s interactive workflow, allowing users to revisit and modify hunk decisions after completing a file. The original RFC patch, inspired by Junio C Hamano's UI suggestions, introduced a "what_now" prompt post-hunk selection with navigation controls (J/K for hunk movement, 'q' to quit). It maintained file state while enabling hunk rework, though Junio raised concerns about architectural complexity—particularly the `skip_what_now` flag—and proposed a more flexible file-switching model using '>' and '<' at any point.

In the latest exchange, the author acknowledges Junio's feedback, agreeing to split variable declarations and reconsider the navigation approach. The discussion now favors a design where file-switching commands behave like hunk-level controls, reducing state-tracking overhead while offering mid-file navigation—potentially allowing users to jump between files without completing all hunks first. Both parties align on the feature's value, focusing on implementation refinements rather than fundamental disagreements. The author plans to restructure the patch accordingly, building on their prior work to enhance `git add -p`'s usability. This iteration reflects Git's collaborative review culture, where maintainer feedback steers implementations toward simpler, more flexible solutions.
