This thread discusses an RFC proposal to enhance `git add -p`'s interactive workflow by allowing users to revisit and modify hunk decisions after completing a file. The proposal originates from Junio C Hamano's prior suggestions for UI improvements to interactive add.

The current patch introduces a "what_now" prompt that appears after all file hunks are decided, providing navigation controls (J/K to move between hunks, 'q' to quit, '>' to advance). The implementation modifies `add-patch.c` with about 65 lines of changes, carefully preserving decided-file state while enabling hunk rework. It addresses two of Junio's three suggested enhancements, leaving file-switching between decided files for future work.

The author has built this on their prior work showing previous hunk decisions and is specifically seeking feedback on the interaction design and implementation approach. The changes are focused on the necessary parts of `add-patch.c`, introducing a new interaction mode that maintains backward compatibility while adding navigation capabilities. Key technical details include handling of the new prompt state via a `skip_what_now` flag and careful management of hunk navigation.

Junio C Hamano, as the originator of the enhancement suggestions, is the key participant whose feedback will likely shape the direction of this work. The proposal appears to be a thoughtful, incremental improvement to the interactive add interface, with clear room for further refinement based on list feedback before final implementation.
