This is a continuation of the CI optimization discussion about skipping certain tests in leak-checking jobs. Junio C Hamano responds to Phillip Wood's point about the rationale for test exclusions, arguing that the key factor is whether the code being tested is under Git's control rather than whether it's written in C.

Junio makes a nuanced distinction: even if `git svn` were rewritten in C, its dependencies on external libraries (like libsvn) would still make leak testing impractical since Git doesn't control those dependencies. He extends this reasoning to Perl interpreter leaks, noting Git can't fix Perl's memory issues across all user systems.

The discussion remains focused on the underlying principle for test exclusions - not just the presence of foreign code, but whether the project can reasonably act on any leaks. This suggests the eventual solution (whether NO_FOREIGN_CODE_TESTS or another name) should be framed around testability rather than implementation language. The thread shows careful consideration of edge cases while maintaining the practical goal of CI speed improvements.
