Thread summary:

Johannes Schindelin (Dscho) initiated a CI optimization to skip git-svn tests during leak-checking jobs via NO_SVN_TESTS in ci/lib.sh, saving ~42 minutes of runtime from Perl-based tests irrelevant to C memory leak detection. Junio C Hamano approved this approach and extended it to CVS/Perforce tests (24-minute savings) by introducing NO_CVS_TESTS and NO_P4_TESTS variables with early-exit checks in t/lib-cvs.sh and t/lib-git-p4.sh, following the established pattern for linux-leaks and linux-reftable-leaks jobs. Phillip Wood confirmed the technical approach and raised whether these exclusions should also apply to ASan (AddressSanitizer) jobs. Junio agreed with Phillip's ASan suggestion and proposed considering a more general NO_FOREIGN_CODE_TESTS variable instead of individual SCM-specific flags.

In follow-up discussion, Phillip Wood responded to Junio's generalization suggestion, agreeing with the technical approach but highlighting the naming challenge - the tests are skipped because they're scripted and exercise minimal C code (where leaks would occur), not primarily because they interface with foreign SCMs. Junio further clarifies the underlying principle, arguing the key factor is whether the code being tested is under Git's control rather than implementation language. He notes that even if `git svn` were rewritten in C, its dependencies on external libraries (like libsvn) would still make leak testing impractical since Git doesn't control those dependencies, extending this reasoning to Perl interpreter leaks as well.

Phillip adds technical refinement regarding leak detection in linked libraries like libsvn - they wouldn't be caught unless specifically built with leak sanitizers. He also considers a hypothetical scenario where a C-based `git svn` called libgit directly (rather than forking), suggesting there might be value in leak-checking Git's own code paths in such cases, though acknowledges this is academic since no such rewrite is planned. The discussion maintains focus on practical CI configuration (ci/lib.sh and related test libs) while carefully distinguishing between what Git can reasonably test (its own controlled code) versus external dependencies, with both participants demonstrating thoughtful consideration of the boundaries between practical CI improvements and theoretical purity in leak detection. The thread shows consensus on the optimization approach while continuing to refine the conceptual framing around test exclusion criteria based on controllability rather than language or SCM interaction characteristics.
