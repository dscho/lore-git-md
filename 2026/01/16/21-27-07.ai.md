This is part 2/7 of a bugfix series addressing regression in error message reporting for batched reference updates. The patch focuses on fixing incorrect control flow when handling refname conflicts during batched updates.

The core issue is that when `refs_verify_refnames_available()` detects a filesystem conflict, the current code uses `continue` which only skips to the next iteration of the inner loop, causing the outer loop to reprocess the same rejected reference. The fix replaces this with a `goto next_ref` to properly skip to the next reference in the outer loop.

Key technical changes:
- Adds `rejection_details` field to `struct ref_update` to store error messages
- Modifies `ref_transaction_maybe_set_rejected()` to accept a `strbuf` for error details
- Updates all three ref backends (files, packed, reftable) to pass error details
- Simplifies control flow by removing redundant error message construction
- Maintains backward compatibility with existing error reporting behavior

The patch is part of a larger effort to restore detailed error messages that were lost when batched reference updates were introduced. It builds on the foundation established in the first patch (already merged) and prepares for subsequent patches that will reconstruct status tables in `fetch` and `receive-pack`.

The changes are well-contained and focused, with thorough updates to all ref backends. The use of `goto` for control flow is justified here as it provides clearer behavior than nested loops with `continue`. The patch maintains the existing error reporting behavior while fixing the regression.
