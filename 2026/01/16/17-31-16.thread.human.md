This thread discusses optimizing Git's CI pipeline by skipping certain tests in memory leak-checking jobs. Johannes Schindelin (Dscho) originally proposed excluding git-svn tests from leak-check runs, saving significant time since these Perl-based tests don't exercise the C code being checked. Junio C Hamano expanded this to CVS and Perforce tests and suggested a broader principle: tests should be excluded when they involve code outside Git's control (like external SCM dependencies), regardless of implementation language.

Phillip Wood engaged in thoughtful discussion about the boundaries of this approach. While agreeing with the practical benefits, he noted technical nuances - like how leaks in linked libraries wouldn't be detected without specific instrumentation. The conversation evolved to consider whether a hypothetical C-based git-svn that called libgit directly (rather than forking) might warrant inclusion in leak checks, though this remains theoretical. 

The thread demonstrates the project's careful balance between CI efficiency and thorough testing. Participants are converging on configuring exclusions based on controllability (can Git reasonably fix any leaks found) rather than implementation details. Changes so far affect ci/lib.sh and related test libraries, with potential future extensions to ASan jobs. The discussion remains focused on practical CI improvements while thoughtfully considering the underlying principles of what constitutes meaningful leak testing.
