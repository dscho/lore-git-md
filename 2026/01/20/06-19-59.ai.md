This is a bug report about a regression in `git fetch`'s error reporting behavior after the batched reference updates change in Git 2.51. The reporter, Stepan Tsymbal from Atlassian, explains that while the new batched updates are generally an improvement, they've lost the ability to see which specific refs failed to update due to directory/file conflicts.

Previously (pre-2.51), when a ref update failed due to a conflict (like trying to create `refs/remotes/origin/branch` when `refs/remotes/origin/branch/conflict` exists), Git would clearly show both the error and which ref failed. Now it only shows a generic "some local refs could not be updated" message without indicating which ones. This is problematic for automation (like Bitbucket's mirror synchronization) that needs to know exactly which ref updates failed.

The reporter provides a reproducible test case and asks whether this is the expected new behavior or if there are workarounds to identify failed refs. The issue appears specific to directory/file conflicts - other error types still show per-ref messages. The `reference-transaction` hook also doesn't help here as it shows all refs as committed.

This looks like an unintended side effect of the batched ref updates optimization that needs addressing, particularly for automation use cases that parse `git fetch` output. The reporter is seeking guidance on whether this behavior is permanent and if there are alternative ways to get the failure information their automation requires.
