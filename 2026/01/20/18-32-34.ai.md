This is the final version of a feature adding PID file debugging for Git locks, now ready for merging. Paulo Casaretto has implemented a system where each lock file can have an accompanying PID file (named with a `~pid` infix) that records the process holding the lock. The feature is controlled by the new `core.lockfilePid` config setting (defaulting to false).

When enabled, Git creates PID files alongside locks, containing the process ID in a standardized format. During lock conflicts, Git checks these PID files to provide more informative error messages - distinguishing between currently running processes and stale locks from terminated processes. The implementation handles edge cases like PID file parsing failures and maintains cross-platform compatibility (including Windows via mingw_kill() updates).

The v5 iteration addresses feedback from Junio Hamano and D. Ben Knoble about PID reuse concerns by making error messages more cautious about process identity certainty. The 139-line test suite (t0031) verifies all major scenarios: stale lock detection, running process identification, config-controlled behavior, and cleanup. The solution is now been through multiple rounds of review with contributions from Jeff King (configuration), Patrick Steinhardt (files backend), Taylor Blau (naming), and Ben Knoble (edge cases).

Key technical details for future reference: PID files use `~pid.lock` suffix to avoid refname collisions, contain `pid <value>` format, are registered as tempfiles for cleanup, and are read even when the feature is disabled (to help diagnose existing stale locks). The implementation touches lockfile.c/h, adds mingw_kill() support for PID checking, and introduces the new config option. Error messages carefully avoid implying certainty about process identity due to PID reuse possibilities.
