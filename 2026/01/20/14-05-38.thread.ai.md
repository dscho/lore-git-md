RFC patch series modernizing `git show-index` from Shreyansh Paliwal, addressing three modernization aspects: hash algorithm identification when run outside repositories (SHA-1 vs SHA-256), i18n support via `_()` wrappers, and removing `the_repository`/`the_hash_algo` globals in favor of explicit `repo` parameters. The technical implementation in `builtin/show-index.c` is mechanically sound but has sparked debate about hash detection reliability.

Junio C Hamano initially suggested structural improvements to the size-based hash detection: extracting logic into `auto_detect_hash_function()` helper, handling non-regular files gracefully, converting fatal errors to warnings, and letting callers handle SHA-1 fallback. Shreyansh incorporated these suggestions while maintaining the core approach.

Patrick Steinhardt raised deeper concerns about the fragility of size-based guessing, noting pack index formats lack explicit hash algorithm metadata. He questioned whether introducing index v5 with proper headers would be justified for this debugging tool, suggesting the existing `--object-format` option might suffice when operating outside repositories.

Shreyansh now considers two paths: either require explicit `--object-format` specification (dropping auto-detection) or pursue format changes with index v5. The discussion reveals architectural tensions between backward compatibility and correctness, with both maintainers acknowledging the command's limited use may not warrant complex format changes. While the i18n and global-state removal patches are uncontroversial, the hash detection approach remains unresolved - highlighting a fundamental limitation in Git's pack index format that affects other commands but is most visible in this plumbing tool. The series demonstrates proper modernization techniques but operates in a context where perfect solutions may be impractical.
