This is a follow-up discussion about a bugfix patch for gitk's color configuration system. The original patch addressed two issues: unused `tagfgcolor` settings and hardcoded black outlines for head refs that should have respected `headoutlinecolor`. 

Johannes Sixt (Hannes) responds to the author's characterization of the change as purely cosmetic with no functional impact. He argues that since users may have previously modified these color settings (despite them being ignored), the change could unexpectedly alter gitk's appearance for those users. He requests that the commit message explicitly document this potential impact and the expected behavior in such edge cases.

The discussion remains focused on commit message quality rather than technical implementation - Hannes confirms the code changes themselves are sound but wants better documentation of the behavioral implications. This is typical of Git's review culture where even small changes receive thorough scrutiny of their documentation and edge cases. The patch appears ready to merge once the commit message is updated to address these considerations.
