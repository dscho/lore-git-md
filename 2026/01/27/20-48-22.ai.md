Feature patch enhancing `git add -p` navigation, now addressing maintainer feedback.

This is the second version of Abraham Samuel Adekunle's patch to improve file navigation in `git add -p`. The core change adds context-sensitive '<' and '>' options that appear only when movement between files is possible (hidden for single file, only '<' at first file, both in middle files), while preserving the existing 'q' submission behavior. The navigation options only appear after all hunks in the current file are decided.

Junio C Hamano's review raises several technical concerns. He questions the need for the new `get_file_diff_index()` helper function, suggesting the interface could be simplified by passing file indices directly. He also expresses skepticism about moving the patch application logic from `patch_update_file()` to its caller `run_add_p()`, noting this changes the transactional behavior (from per-file to all-or-nothing application) without clear justification. The maintainer suggests the navigation might need to be optional via configuration to avoid surprising existing users.

The patch modifies `add-patch.c` to track file positions and navigation state through new `ALLOW_GOTO_PREVIOUS_FILE` and `ALLOW_GOTO_NEXT_FILE` flags. It introduces a new prompt ("All hunks decided. What now?") when navigation options become available. The implementation uses magic numbers (0/1/2) for navigation state that Junio suggests should be replaced with an enum for clarity.

While the core navigation concept has maintainer approval, several open questions remain: whether to make the feature configurable, how to handle the patch application timing change, and potential UI refinements. Test updates in t/3701-interactive.sh are still pending finalization of the UI behavior. The patch represents a quality-of-life improvement for interactive staging, but needs to address the architectural concerns raised before being ready for inclusion.
