This thread discusses a proposal to introduce 'ls` as an alias for 'list` subcommands across Git, such as making `git stash ls` work alongside `git stash list`. The suggestion comes from observing that many CLI tools accept 'ls` as shorthand while Git remains inconsistent - some commands like `git-ls-files` use it, but others like stash and worktree don't.

Daniel Tang points to `git remote rm`/`remove` as existing precedent for such aliases within Git, while the author notes this is widespread in tools like npm and Docker. The core argument is that programmers frequently reach for 'ls` by muscle memory, creating friction when Git rejects it. Junio Hamano has expressed initial reservations, questioning whether Git needs this change given limited internal precedent. The discussion now hinges on whether this would meaningfully improve UX for a common pattern or unnecessarily expand Git's command surface. No implementation has been proposed yet.
