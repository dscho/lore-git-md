This is a follow-up in the RFC series introducing `string_list_sort_u()`, addressing edge cases in fetch.c and help.c that Junio identified as potentially problematic for the new combined sort+deduplicate operation.

The author demonstrates two key findings:

1. For fetch.c's remote consultation order: A test case shows that the current unsorted deduplication in `cmd_fetch()` leads to duplicate fetches when remotes appear non-adjacent in config. The proposed `string_list_sort_u()` would change the consultation order, potentially breaking user expectations. The author suggests an alternative approach that would preserve first-occurrence order while still deduplicating, though notes this isn't currently implemented in the string-list API.

2. For help.c's key processing: The analysis reveals that while the current code technically works (because duplicates happen to be adjacent), the key munging could theoretically produce unsorted output. The author proposes moving the sort operation after deduplication as a more robust solution, noting this appears safe since the processing doesn't depend on order.

The email shows the author has done thorough investigation of both edge cases, including writing test cases to verify behavior. The findings suggest the original RFC may need adjustments to handle these real-world usage patterns where order matters or where processing breaks the sort invariant. The thread remains in RFC state while these design questions are worked through.
