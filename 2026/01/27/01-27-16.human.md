This is a follow-up in the RFC series introducing `string_list_sort_u()`, addressing edge cases in `fetch.c` and `help.c` that Junio identified as problematic for the combined sort+deduplicate operation.

Amisha Chhajed reports test results showing that `fetch.c`'s remote consultation order would change if sorted before deduplication, potentially breaking user expectations about remote priority. The current behavior preserves configuration file order when removing remotes, which may be intentional. They suggest an alternative implementation that would preserve first-seen order while still deduplicating, similar to Python's set insertion behavior.

For `help.c`, they analyze a case where key processing could theoretically produce unsorted output, though the current implementation happens to work because duplicates remain adjacent. They propose moving the sort operation after processing to make the behavior more robust.

The email demonstrates careful analysis of both edge cases but leaves open whether to modify these callers to accommodate the new API or keep them as special cases using the separate operations. The thread remains in RFC state while these design questions are resolved.
