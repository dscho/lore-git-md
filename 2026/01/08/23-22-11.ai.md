This is a response in an ongoing thread about adding `--config` support to `git init`. brian m. carlson explains the current behavior and suggests workarounds rather than endorsing the feature request.

The response clarifies that `git -c` (preceding the subcommand) only affects the current command's behavior without persisting the config, unlike `git clone --config` which writes to the new repository's config. They note that most repository initialization doesn't need early config settings since operations like index creation happen later.

Three alternative approaches are suggested: 1) A shell alias that runs `git init` followed by `git config`, 2) A custom shell script using `git rev-parse --parseopt` for more sophisticated argument handling, and 3) Using Git's `includeIf` functionality to automatically load different configs based on repository location. The latter is presented as particularly clean since it handles the email distinction without per-repository commands.

The tone is informative rather than dismissive, but the response implicitly questions the need for the feature by showing multiple existing solutions. The technical details about when config needs to be set (before vs after operations) help explain why `git clone --config` exists while `git init --config` might be less critical.
