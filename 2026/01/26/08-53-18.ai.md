This is a technical discussion in Patrick Steinhardt's ODB abstraction series (v3 12/14), focusing on how to handle object mtimes in the context of cruft packs and pluggable backends. The exchange centers on whether GC-specific mtime logic should live in the ODB layer (Patrick's position) or be handled at a higher level via a generic stat structure (Taylor Blau's proposal).

Patrick argues his approach keeps backend-specific logic fully contained within backend implementations, maintaining pluggability. He notes the current design already works sensibly for `odb_for_each_object()` callers, with no ambiguity in practice. Taylor counters that adding a `statp` field would be no more leaky than existing fields like `disk_sizep`, and would better separate concerns by keeping GC-specific logic out of the core ODB layer.

The discussion reveals deeper architectural questions about what constitutes an object property versus a storage implementation detail. Patrick acknowledges Taylor's point about mtime ambiguity in some cases but maintains the current approach is sufficiently documented and functional. He agrees to expand documentation to cover these nuances while keeping the implementation as-is for now.

This represents one of the last open questions in the otherwise largely settled ODB abstraction series, with both sides agreeing the end behavior would be identical but differing on where to draw abstraction boundaries.
