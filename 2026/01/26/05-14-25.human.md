This is a follow-up in the `git subtree` regression thread, where Colin Stagner provides additional technical analysis of the issue. The regression, introduced in Git 2.53.0-rc1, causes `git subtree push` to incorrectly fail with "non-fast-forward" errors in cases that previously worked, particularly affecting Arch Linux AUR package workflows.

Colin confirms he won't have a fix ready by the upcoming rc2 deadline and supports Junio's plan to revert the problematic commit. He digs deeper into the technical roots, tracing the issue back to an earlier optimization (98ba49ccc2) that was meant to speed up subtree processing but inadvertently changes split commit hashes in some cases. 

The core tension is between the optimization's benefits and Git's documented guarantee that repeated splits of identical history should produce identical results. Colin suggests a potential compromise: making the optimization opt-in via a new flag like `--fast-exclude` rather than having it on by default. He also shares specific test results using Christian Heusel's Arch Linux monorepo, showing how the pre-patch behavior correctly generates expected commit hashes.

This email advances the discussion by moving from problem identification to solution exploration, though the immediate path forward remains a revert. The technical details provided will be valuable when designing a proper fix that maintains both correctness and performance.
