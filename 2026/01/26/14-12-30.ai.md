This is a bugfix discussion for a regression in `git subtree push` functionality. The thread involves Christian Heusel reporting a problem where subtree pushes started failing with "non-fast-forward" errors after Git 2.53.0-rc1, specifically affecting Arch Linux AUR package repository synchronization.

Colin Stagner has confirmed the bisect points to commit 28a7e27cff ("contrib/subtree: detect rewritten subtree commits") as the regression source. The issue manifests when pushing subtrees to the Arch Linux AUR, with the google-chrome subtree serving as a concrete test case. The problematic change interacts badly with an earlier optimization (98ba49ccc2) that modified subtree split behavior in subtle ways.

Christian verifies that the pre-patch behavior (commit e6f461379) produces the expected subtree commit hash that matches the remote repository's state. Colin acknowledges the regression and is working on a more permanent solution, but suggests reverting the problematic commit in 2.53.0-rc2 as an immediate fix. Christian expresses appreciation for the investigation but cautions against rushing a complex fix for what is fundamentally an optimization.

The discussion highlights tension between performance improvements and maintaining stable behavior guarantees in the subtree command. The immediate path forward is clear (reverting the regression-causing commit), but the underlying issue of how to reconcile optimizations with behavioral consistency remains open for future work.
