Bugfix discussion for git-gui's tab display issues, now with maintainer pushback on proposed solution. Johannes Sixt (Git GUI maintainer) confirms that the tab alignment problem occurs across all tab widths, not just width 4 as initially reported. More critically, he reiterates that the current approach of converting tabs to spaces breaks the core staging functionality - the "Stage Line/Hunk for Commit" commands fail because they operate on the original file contents, not the space-converted display text.

Sixt expresses strong reservations about modifying the displayed text at all, noting that decades of patch-reading experience have trained developers to expect certain tab alignment patterns. He suggests that the visual misalignment might actually serve as a useful indicator of whitespace errors. The thread remains at an impasse: the Windows Tk rendering issue needs addressing, but the maintainer has vetoed solutions that alter the text content in ways that disrupt staging operations or deviate from established patch display conventions.

Key technical constraints now clear: any solution must (1) fix the visual tab alignment without modifying the underlying text, or (2) find a way to make the staging commands work with transformed text while maintaining patch accuracy. Neither path has yet been demonstrated as feasible. The discussion appears to have reached a stalemate between fixing the display issue and preserving existing functionality.
