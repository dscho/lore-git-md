This is a technical discussion in Patrick Steinhardt's ongoing ODB abstraction series (v3 12/14), focusing on how to handle object mtimes in the context of cruft packs and GC operations. The exchange between Patrick and Taylor Blau centers on whether mtime handling should be implemented within each backend (Patrick's preference) or via a more generic stat structure at a higher level (Taylor's proposal).

Patrick argues that keeping mtime logic within backends better serves the goal of pluggable backends, as it allows each storage implementation to define its own mtime semantics. He notes this approach already works for the two callers (reachable.c and pack-objects.c) and maintains clear disambiguation when objects exist in multiple forms. Taylor counters that adding a generic stat structure would avoid baking GC-specific semantics into the ODB layer while providing more generally useful metadata.

The discussion reveals deeper architectural tensions around the object_info struct - while both agree it already leaks some backend details (like disk_sizep and delta_base_oid), they differ on whether to minimize further leakage (Patrick) or embrace a pragmatic approach (Taylor). Patrick acknowledges the ambiguity concerns but believes better documentation can address them without restructuring.

This represents one of the final open questions in the otherwise largely settled ODB abstraction series. The exchange is technical but collegial, with both sides working toward a solution that maintains the series' goals while addressing safety and clarity concerns. The patch itself converts pack-objects.c to use the new packfile_store_for_each_object() API, with the mtime handling discussion being the primary blocker before integration.
