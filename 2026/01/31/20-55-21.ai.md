This is a follow-up in the ongoing discussion about adding a shorthand for referencing a repository's primary branch, now considering Junio's suggestion to use `repo_default_branch_name()` instead of the remote-tracking approach.

Harald Nordgren examines the suggested alternative and finds it problematic because `repo_default_branch_name()` hardcodes the fallback to "main" or "master" rather than reflecting what's actually used in each repository. This would make the shorthand less useful in practice since it wouldn't adapt to repositories using different primary branch names (like "trunk" or other variants).

The email highlights a key tension in the design: Junio prefers a conceptually clean solution tied to Git's configuration system, while Harald's implementation aims for practical utility by following what's actually used in the repository (via origin/HEAD). The hardcoded fallback in `repo_default_branch_name()` would make the shorthand less flexible than the current remote-tracking approach.

This exchange moves the discussion toward the core question of whether the shorthand should represent:
1. The configured default (via init.defaultBranch)
2. The actual primary branch used (via origin/HEAD)
3. Some combination with fallback logic

The implementation choice here will determine whether the shorthand works reliably across diverse repositories or remains limited to those using standard branch names. Harald's response suggests the current remote-tracking approach better serves the original goal of simplifying workflows in environments with varying branch naming conventions.
