This is a feature patch introducing a new shorthand `@{primary}` to reference a repository's primary branch (typically "main" or "master"). The v4 iteration resolves the primary branch via upstream tracking infrastructure (usually `origin/HEAD`) rather than directly using `init.defaultBranch`, addressing concerns from Junio Hamano about config reliability.

The implementation adds `branch_get_primary_mark()` and supporting infrastructure, reusing existing branch tracking machinery with a new `primary_mark` parser in object-name.c. Tests verify the shorthand works in `rev-parse`, `checkout`, and `status` contexts. Documentation describes this as resolving to "the primary branch via upstream tracking."

The patch appears technically sound with thorough test coverage, though the design discussion has shifted from implementation details to fundamental questions about the feature's purpose and naming. Junio has questioned whether the remote-tracking approach sufficiently captures "primary branch" across all workflows and how it relates to repositories without clear remote tracking. The terminology shift from "default" to "primary" also remains a point of discussion, as it diverges from the established `init.defaultBranch` concept.

This represents a useful quality-of-life improvement for users who frequently switch between repositories with different primary branch names, though the semantic distinction between "default" and "primary" branches may need clearer documentation if this approach is adopted. The patch is ready for review but may see further discussion about its conceptual alignment with Git's existing branch naming conventions.
