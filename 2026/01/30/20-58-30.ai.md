This is a follow-up in the ongoing discussion about adding a shorthand for referencing a repository's primary branch. Harald Nordgren shares a work-in-progress implementation, marking it explicitly as non-final and continuing the conversation from previous iterations that evolved from `@{default}` to `@{primary}` syntax.

The technical approach has shifted from relying on `init.defaultBranch` configuration to using upstream tracking infrastructure (typically `origin/HEAD`) as the resolution mechanism, addressing Junio Hamano's earlier concerns about config reliability. The current implementation introduces `branch_get_primary_ref()` and supporting code to handle the new shorthand.

Key unresolved questions remain about whether this sufficiently captures the "primary branch" concept across all Git workflows, particularly in repositories without clear remote tracking or with multiple primary branches. The thread reflects tension between the convenience goal of a shorthand reference and Git's emphasis on semantic precision when branch naming diverges between local and remote repositories.

Testing continues to validate the technical soundness while leaving open higher-level design questions about the feature's purpose and naming. The discussion may need to address whether remote-HEAD-based resolution matches user expectations for a "primary branch" reference across diverse workflows, and how this relates to existing functionality like `git var GIT_DEFAULT_BRANCH`.
