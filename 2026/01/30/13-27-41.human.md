This is a bugfix series addressing issues with `refs_for_each_ref_in()` usage in bitmap and bisect functionality. The series consolidates bitmap tip iteration logic and fixes cases where exact ref matches would trigger a BUG() condition.

Patrick Steinhardt's v2 series builds on previous discussion and incorporates Jeff King's cleanup patch for bisect string handling. The key changes are:

1. A new `for_each_preferred_bitmap_tip()` helper consolidates duplicate bitmap tip iteration code from pack-objects and midx, removing the last external caller of `bitmap_preferred_tips()`.

2. The bitmap case now uses `refs_for_each_fullref_in()` to properly handle exact ref matches in "pack.preferBitmapTips" configuration, avoiding the BUG() while maintaining existing matching semantics where "refs/heads/base" matches both itself and "refs/heads/base-something".

3. The bisect case similarly replaces `refs_for_each_ref_in()` with `refs_for_each_fullref_in()` and adds proper trailing slash handling for "refs/bisect/" prefix.

Jeff King's cleanup simplifies bisect string_list memory management by switching to DUP mode, removing manual string duplication. The series includes comprehensive tests in t5310 and t5319 demonstrating the fixes.

The remaining open question is whether to maintain the current prefix-matching behavior (where "refs/heads/foo" matches both "foo" and "foobar") or require explicit trailing slashes for strict hierarchy matching. Patrick leans toward keeping current behavior for backward compatibility but remains open to change if consensus favors stricter matching. Documentation updates will clarify the chosen semantics.

The technical changes have received approvals from Karthik Nayak and Junio Hamano, with only the matching semantics decision and final documentation wording remaining. The series appears well-tested and addresses a real bug while cleaning up related code.
