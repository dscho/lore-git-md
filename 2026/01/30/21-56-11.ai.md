This is a design discussion email in the ongoing thread about adding a shorthand for referencing a repository's primary branch. Junio Hamano responds to Harald Nordgren's work-in-progress implementation that has evolved from using `@{default}` to `@{primary}` syntax.

Junio expresses concern about the terminology shift from "default" to "primary", noting that `init.defaultBranch` already has an established meaning as the "default" branch. He suggests that if the implementation is now tracking something different - specifically the remote's HEAD via upstream tracking - then "primary" might be appropriate for this new concept, but it should be clearly distinguished from the default branch concept.

The email reveals a disconnect between what Harald originally proposed (a shorthand for `init.defaultBranch`) and what his current WIP implements (resolving via remote tracking branches). Junio seems puzzled by this shift, noting that the remote-tracking approach doesn't match Harald's originally stated use case. He implies the implementation may be solving a different problem than originally described.

This exchange highlights the ongoing tension in the thread between:
1. The desire for a convenient shorthand
2. Precise semantics around branch naming
3. Whether remote-tracking behavior matches user expectations
4. How this feature relates to existing mechanisms like `git var GIT_DEFAULT_BRANCH`

The technical implementation appears sound (as seen in previous emails), but Junio is focusing on the higher-level design questions about what exactly this shorthand should represent in Git's reference system. His comments suggest the discussion needs to revisit the fundamental purpose of the feature before finalizing the implementation.
