This is a feature proposal for a new branch shorthand `@{default}` that continues to face design challenges. Kristoffer Haugsbakk weighs in on the ongoing discussion, offering practical perspective from their workflow.

The thread has evolved from initial implementation details to fundamental questions about what "default branch" should mean in Git. While Harald Nordgren's patch implements `@{default}` to resolve via `init.defaultBranch` config (with fallbacks), Junio Hamano has raised concerns about this approach's reliability given real-world branch naming mismatches. Kristoffer shares their personal workflow, noting they typically interact with the default branch via remote-tracking references (`origin` or their shorthand `o`) rather than needing a local branch.

Kristoffer points out that `git var GIT_DEFAULT_BRANCH` already provides similar functionality without new syntax, though it requires more typing. Their comment suggests the proposed shorthand may not address their actual needs, as they find remote-tracking branches more directly useful than local default branch references. This reinforces Junio's concern that the config-based approach may not match how users actually work with default branches in practice.

The discussion now faces key design questions: whether to track remote HEAD instead of local config, whether to rename the feature to better reflect its behavior, and whether the problem might be solved through better branch hygiene rather than new syntax. Testing has revealed widespread mismatches between configured default names and actual branches, casting doubt on the current implementation's reliability.
