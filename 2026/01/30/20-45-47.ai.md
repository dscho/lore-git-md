This is a feature patch introducing a new `@{primary}` shorthand for referring to a repository's primary branch, part of an ongoing discussion about default branch naming and access patterns.

Harald Nordgren's v3 patch renames the proposed shorthand from `@{default}` to `@{primary}` and significantly changes the implementation approach. Instead of resolving via `init.defaultBranch` configuration as in previous versions, it now piggybacks on the upstream tracking infrastructure, effectively making `@{primary}` resolve to the local branch that tracks the remote/HEAD reference (typically `origin/HEAD`). This aligns with Junio Hamano's earlier feedback that remote tracking branches are a more reliable indicator of primary branch usage than local configuration.

The implementation adds new functions `branch_get_primary_ref()` and supporting infrastructure while reusing much of the existing branch tracking machinery. Documentation and tests are updated to reflect the new behavior, showing `@{primary}` resolving to the expected branch name and working with commands like `git checkout` and `git status`. The test suite verifies both the reference resolution and the expected status output when on the primary branch.

Key technical details for future reference:
- New `primary_mark` parser in object-name.c handles the `@{primary}` syntax
- `branch_get_primary_ref()` internally uses modified `branch_get_upstream_options()` with `omit_remote=1`
- Tests confirm resolution works in rev-parse, checkout, and status contexts
- Documentation describes it as resolving to the primary branch via upstream tracking

The change addresses core concerns from earlier rounds about reliability when local and remote branch names diverge, though some design questions remain about whether this sufficiently captures the "primary branch" concept across all workflows. The implementation appears technically sound but may still face discussion about whether this is the right semantic for the feature.
