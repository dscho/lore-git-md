This is a reply in the ongoing discussion about the `git history reword` subcommand, part of Patrick Steinhardt's RFC series to introduce flexible history editing operations. The email comes from Elijah Newren responding to SZEDER Gábor's concerns about the command's default behavior and documentation.

The core disagreement centers on whether `git history reword` should rewrite all local branches containing the modified commit by default (current implementation) or only the current branch (SZEDER's preference). Newren argues strongly for the all-branches approach, citing:
- The pain of rebasing multiple interdependent branches with traditional tools
- Easier recovery from unwanted branch updates (via reflog) compared to fixing missed updates
- Precedent from other tools like Jujutsu and GitButler that rewrite all descendant branches
- The original design goal of moving away from HEAD-centric assumptions in `git replay`

Newren acknowledges SZEDER's point about Git's porcelain commands typically defaulting to current-branch operation, but counters that the "view" and "edit" command categories have different precedents. He also proposes a compromise: adding a `history.scope` config variable to let users choose between "descendant-branches", "current-branch", or "error-if-multiple-branches" behaviors.

The exchange highlights a tension between Git's traditional single-branch porcelain conventions and the more repository-wide approach of newer history editing tools. While the technical implementation has received sign-off, this discussion shows there are still open questions about the command's safest and most intuitive defaults before this feature ships.
