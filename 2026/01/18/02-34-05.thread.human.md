This thread centers on Derrick Stolee's proposal to add a `--maximal` option to `git rev-list` that would filter output to show only commits not reachable from others in the input range - essentially finding the "frontier" commits. The implementation is complete with thorough test coverage, but the discussion has shifted to interface design concerns.

Johannes Sixt has raised significant concerns about the `--maximal` name being too mathematical and potentially confusing alongside `git-log`'s existing `--minimal` option (despite their different semantics). He's proposed several alternatives like `--only-maximal`, `--hide-reachable`, and `--range-head-only` that might better convey the functionality to users. Junio Hamano has now entered the discussion, agreeing that `--maximal` and `--boundary` should likely be mutually exclusive options, framing this mathematically as requesting both minimal and maximal elements simultaneously.

The debate reflects Git's historical tension between mathematical precision and user-friendly terminology in command-line interfaces. While the implementation is sound and the feature is clearly useful for cases like bundle URIs, the naming discussion appears to be the final hurdle before merging. Junio's participation suggests this is nearing decision time, with the community working to find a name that both accurately describes the functionality and aligns with Git's interface conventions. The discussion remains constructive, with Johannes providing concrete alternatives rather than blocking the feature outright.
