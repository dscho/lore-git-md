This is a follow-up in a thread discussing inconsistent behavior in `git add` when handling invalid paths. Jon Forrest originally reported that `git add` behaves differently for non-existent files (fails entirely) versus ignored files (warns but continues). 

Junio C Hamano previously clarified that the current behavior for ignored files makes practical sense for common workflows like `git add .`, where some files may be ignored. He noted that treating explicitly named files differently would require a new design rather than being a simple bugfix.

In this email, Jon acknowledges Junio's perspective and agrees the issue is minor. He frames it as a difference in mental models - he initially thought of `git add` as an atomic transaction, but now sees that ignored files are treated as a different class of error. The warning about ignored files helps make the behavior more transparent to users.

The thread appears to be winding down with consensus that while the behavior could theoretically be made more consistent, the current approach serves common use cases well and any change would need to be considered a new feature rather than a bugfix.
