Bugfix targeting ref resolution behavior in branch comparisons. Jeff King continues his technical deep dive into implementing DWIM-based branch name expansion for `git status`'s new `compareBranches` configuration. This email focuses on two specific edge cases in the ref resolution machinery that would need to be addressed for proper DWIM behavior.

The first issue involves `repo_dwim_ref()` not properly handling missing upstream refs - currently it returns nothing when a configured upstream branch is missing, while the tracking-info code expects to be able to report this case. King proposes modifying `repo_dwim_ref()` to return the ref name (with a null OID) when `nonfatal_dangling_mark` is set, similar to how `branch_get_upstream()` behaves.

The second issue stems from how `substitute_branch_name()` shortens unambiguous refs during @-mark expansion, which could lose information needed by the tracking-info code. King suggests adding a `do_not_shorten` option to `interpret_branch_name()` to preserve the full refname when needed.

King provides concrete patches for both issues and notes they allow the test suite to pass, though he expresses some concern about the complexity being introduced. These changes would support his proposed DWIM-based approach using pattern expansion ("%s@{upstream}") rather than the current hardcoded remote-tracking branch resolution. The email continues the thread's progression toward a technically sound implementation that maintains consistency with Git's existing ref resolution behavior.
