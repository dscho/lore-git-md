This is a feature patch from Derrick Stolee adding the `--maximal-only` option to `git rev-list`, now in its second iteration. The patch has evolved from the initial proposal with naming consensus reached (`--maximal-only` instead of `--maximal`) and comprehensive test coverage added.

The option identifies "frontier" commits - those not reachable from others in the input set, which is useful for bundle URIs and bitmap optimization. The current email specifically addresses Junio's question about how this relates to `git merge-base --independent`. Stolee clarifies that while both find maximal elements, they operate on different sets: `--maximal-only` works on the union of histories (for rev-list input), while `--independent` works on the intersection (for merge bases). He also notes the documentation discrepancy where `--independent` describes itself as finding a "minimal subset" when it actually finds maximal elements.

The implementation uses bit 28 (`CHILD_VISITED`) in revision.c/commit.c and explicitly documents incompatibility with `--boundary`. The patch appears ready for merging with all feedback addressed, including thorough test coverage of edge cases and interactions with other options like `--first-parent`. The discussion suggests potential future optimizations for the bundle URI use case and notes the ongoing bit allocation considerations (28 of 32 bits now used).
