This is a follow-up discussion about the recently merged `status.compareBranches` feature, focusing on refname resolution behavior. Jeff King (Peff) responds to Junio Hamano's concerns about the current hardcoded remote-tracking branch prefixing by proposing two alternative approaches for more flexible branch name resolution.

The first suggestion involves modifying `repo_interpret_branch_name()` to accept a default branch parameter through its options struct, which would allow proper interpretation of `@{upstream}` and `@{push}` syntax relative to the comparison branch rather than always using HEAD. This would eliminate the need for special casing these markers in the current implementation.

The second, more ambitious proposal considers supporting dynamic branch name patterns (like "origin/%s") that could expand based on the current branch name, potentially unifying the handling of upstream/push syntax with other refspec-like patterns. This would provide greater flexibility for users wanting to compare against derived branch names.

Jeff agrees with Junio's concern that the current hardcoded `refs/remotes/` prefixing is too limiting, as it prevents comparisons against tags, local branches, or other refs outside the remote-tracking namespace. He suggests using Git's standard DWIM rules (via `ref_rev_parse_rules[]` or `repo_dwim_ref()`) to maintain consistency with how refs are resolved elsewhere in Git.

The discussion highlights a key design decision point for the feature: whether to maintain the current restricted behavior or adopt more flexible resolution rules that would enable comparisons against any ref type while preserving Git's standard ref lookup semantics. Jeff's technical suggestions provide concrete paths forward for implementing the more flexible approach.
