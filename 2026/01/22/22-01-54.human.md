This is a follow-up discussion about the recently merged `status.compareBranches` feature, focusing on refname resolution behavior. Jeff King (Peff) responds to Junio Hamano's concerns about the current implementation's hardcoded `refs/remotes/` prefixing for branch comparisons.

Jeff acknowledges the special-casing of `@{upstream}` and `@{push}` is unfortunate but necessary given the current design. He proposes two alternative approaches that could make the resolution more flexible:

1. Extending `repo_interpret_branch_name()` to accept a default branch parameter, allowing it to properly resolve `@{upstream}` against non-HEAD branches.

2. Supporting format strings like `origin/%s` or `%s@{upstream}` that would expand based on the current branch name, providing more dynamic comparison targets.

Jeff agrees with Junio that the current hardcoded remote-tracking branch resolution is too limiting, preventing comparisons against tags or local branches. He suggests using Git's standard DWIM (Do What I Mean) resolution rules through `repo_dwim_ref()` instead, which would maintain consistency with how refs are resolved elsewhere in Git.

The discussion represents a post-merge design critique of an already functional feature, with both contributors exploring ways to make the branch comparison mechanism more flexible while maintaining Git's established ref resolution semantics. The suggestions indicate this feature may see further refinement in future iterations.
