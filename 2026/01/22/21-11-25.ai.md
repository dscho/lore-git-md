This is a follow-up discussion about the recently merged `status.compareBranches` feature, focusing on potential future expansion of branch name resolution rules. The thread involves Harald Nordgren (the feature author) and Junio Hamano (the maintainer) debating whether to implement broader refname disambiguation now or defer it.

Junio argues against deferring the DWIM (Do What I Mean) expansion of branch names, noting that the current implementation hardcodes `refs/remotes/` prefixing which would create backward compatibility issues if more flexible resolution were added later. He points out that Git's standard refname resolution (via `ref_rev_parse_rules[]`) handles multiple ref types with precedence rules, while the current implementation would force remote-tracking branch resolution even when local branches or tags exist with the same name.

The discussion reveals a tension between the feature's current focus on remote-tracking branches and the potential for more flexible comparisons. Junio's position is that either the full DWIM rules should be implemented now, or the project should explicitly decide to never support non-remote comparisons through this interface. This would avoid future behavior changes that users might perceive as regressions.

Key technical details at stake:
- Current implementation uses hardcoded `refs/remotes/` prefixing
- Standard Git ref resolution uses `ref_rev_parse_rules[]` with ordered precedence
- Local branches (`refs/heads/`) normally take precedence over remote-tracking branches
- Tags and other ref types could theoretically be supported through DWIM rules

The exchange suggests the merged code may need follow-up work to align with Git's standard ref resolution behavior, despite having passed all CI checks and review cycles. This is a nuanced post-merge discussion about long-term interface design rather than any immediate functional issue with the current remote-tracking branch comparison capability.
