This is a response from the maintainer (Junio C Hamano) to a proposed bugfix for `git reset`'s reflog behavior. The original patch aimed to skip writing reflog entries when `git reset` is a no-op (target commit matches HEAD), but Junio expresses concern that this could break existing scripts relying on the current behavior.

Junio provides a concrete example where a script uses `git reset --hard` followed by `git diff --stat @{1}` to compare against the pre-reset state. If the reset is a no-op and skips the reflog entry, `@{1}` would refer to an older state rather than the intended pre-reset position, breaking the script's logic. This suggests the proposed change, while well-intentioned to reduce reflog pollution, might have unintended consequences for existing workflows.

The response indicates this is likely to be a contentious change that would need broader discussion about backwards compatibility versus optimization. Junio's "mildly negative" stance suggests the patch in its current form is unlikely to be accepted without addressing these script compatibility concerns.
