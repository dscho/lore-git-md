This is a bugfix patch addressing submodule fetching behavior when submodules use non-"origin" remote names. The patch completes a 7-year-old NEEDSWORK item from commit be76c21282 that hardcoded "origin" as the remote name for fetching missing submodule objects.

The key changes in v3:
- Adds a new `get-default-remote` subcommand to `submodule--helper` to properly detect a submodule's default remote
- Modifies the submodule fetch logic to use this helper instead of assuming "origin"
- Falls back to "origin" if default remote detection fails (maintaining backward compatibility)
- Includes comprehensive test coverage across multiple scenarios (custom remote names, nested submodules, error cases)

The patch has been through several iterations with review feedback addressed, including:
- Fixing test syntax issues caught post-v2
- Renaming a test file to avoid conflicts
- Properly including Jacob Keller's Reviewed-by that was missed in v2

This is a well-tested solution to a real limitation in submodule handling, particularly affecting workflows that use the "repo" tool or other systems that configure non-standard remote names. The implementation is technically sound and ready for inclusion after the minor test adjustments in this v3.
