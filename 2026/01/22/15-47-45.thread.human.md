This thread examines a proposed change to `git reset`'s behavior regarding reflog entries during no-op resets (where HEAD doesn't actually move). The original patch sought to optimize reflog storage by skipping entries when `git reset` doesn't change the commit position, but it has run into significant pushback from maintainers.

Junio Hamano first raised compatibility concerns, pointing out that existing scripts might break if `@{1}` no longer refers to the immediate pre-reset state after a no-op operation. Jeff King (Peff) has now reinforced these objections, adding that the reflog messages (which record the target commit name) provide valuable human-readable context even for no-op resets. Both maintainers view the current behavior as intentionally useful rather than merely redundant.

The discussion has reached a stalemate between the optimization benefits and maintaining backward compatibility. Unless the patch can address these concerns - either by preserving the existing scripts rely on or making a compelling case that the change is worth the breakage - it seems unlikely to move forward in its current form. The key files involved remain `builtin/reset.c` for the implementation and `t/t1410-reflog.sh` for testing the behavior.
