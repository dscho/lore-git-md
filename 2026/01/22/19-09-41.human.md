This is a discussion about a proposed bugfix for `git reset`'s reflog behavior. Jeff King (Peff) is responding to Junio C Hamano's concerns about the patch, which aimed to skip reflog updates for no-op resets (where HEAD doesn't change).

Peff agrees with Junio's assessment that the change could break existing scripts that rely on `@{1}` referencing the pre-reset state, even for no-op resets. He adds another perspective - that the reflog message provides useful human-readable context about what reset operation was attempted, even when no actual change occurred.

The thread shows consensus forming against the original patch due to backward compatibility concerns. Both maintainers highlight how this seemingly small optimization could negatively impact both scripts and human users examining the reflog history. The discussion suggests this change would need a stronger justification to overcome these compatibility tradeoffs.
