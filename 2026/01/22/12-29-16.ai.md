[Security] Sideband control character sanitization defaults debate

This email from Johannes Schindelin continues the discussion about default security settings for Git's sideband channel sanitization. The thread concerns CVE-2024-32002 and CVE-2024-52005/GHSA-7jjc-gg6m-3329, which address ANSI escape sequence injection vulnerabilities.

Schindelin strongly opposes making sanitization opt-in or weakening it based on trust heuristics, arguing that safe-by-default should be the baseline for security-sensitive features. He challenges Junio Hamano's suggestion of tiered defaults based on remote trust levels, pointing out that even trusted remotes can be compromised. The current implementation already allows color sequences by default while requiring explicit opt-in for higher-risk sequences like cursor movement and erase commands.

Key technical points include the existing `sideband.allowControlCharacters` configuration (which supports granular levels from `false` to `true` with intermediate values like `color` and `cursor`), and the availability of per-URL overrides via `sideband.<url>.allowControlCharacters`. Schindelin requests concrete examples of workflows that would break under stricter defaults, noting that color sequences are already permitted without configuration.

The email highlights a fundamental disagreement between security-conscious defaults (advocated by Schindelin, Patrick Steinhardt, and D. Ben Knoble) and backward-compatibility concerns (raised by brian m. carlson). Schindelin's position reflects the implementation's production validation in Git for Windows and Red Hat environments over extended periods. The discussion has narrowed to whether the default should remain at "color-only" filtering) or revert to historical unfiltered behavior, with Schindelin firmly opposing the latter as leaving users vulnerable by default.
