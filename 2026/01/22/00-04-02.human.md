This is a discussion about object storage abstraction in the ongoing ODB refactoring series. Taylor Blau raises a concern about interface design in patch 3/14, which extracts a function to read object info from a filesystem path. 

Taylor questions whether the path-based approach is too tied to Git's current filesystem storage model, potentially making it a poor fit for future database-backed storage implementations. This is a key architectural consideration for the ODB abstraction effort, as the series aims to enable pluggable backends while maintaining clean separation between storage mechanisms and their callers.

The exchange occurs early in the series (patch 3/14) and doesn't block progress - the technical work proceeds to completion in later patches with positive reviews from Justin Tobler and Karthik Nayak. However, Taylor's point about avoiding filesystem assumptions in the core interface touches on an important design principle that may influence future API evolution, even if it doesn't require changes to this particular series.
