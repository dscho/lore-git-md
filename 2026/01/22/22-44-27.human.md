This is a technical follow-up in the ongoing discussion about branch comparison behavior in `git status`. Jeff King (Peff) presents a concrete implementation approach for making the `status.compareBranches` feature more flexible by using Git's standard DWIM (Do What I Mean) rules rather than hardcoding remote-tracking branch resolution.

The key proposal is to allow dynamic branch name patterns (like "origin/%s") that can expand the comparison branch name, similar to how `@{upstream}` and `@{push}` work. This would unify the syntax with other refspec-like patterns in Git. Peff provides a prototype implementation showing how this could work by modifying the branch resolution code in `remote.c`.

The email also surfaces two technical complications that would need to be addressed:
1. A race condition in branch configuration during `git checkout -b` that would require clearing cached remote state
2. Handling of missing upstream refs, which currently behaves differently between the direct branch_get_upstream() approach and the proposed DWIM-based resolution

This builds on Junio Hamano's earlier concerns about the current implementation's non-standard resolution behavior. Peff's proposal offers a path to align with Git's existing ref resolution patterns while maintaining the feature's core functionality. The discussion appears to be converging toward adopting this more flexible approach, though some implementation details remain to be worked out.
