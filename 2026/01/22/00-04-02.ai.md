This is a discussion about the ODB abstraction series, specifically addressing whether path-based object access is an appropriate interface for pluggable backends. Taylor Blau raises a concern about patch 03/14, which introduces a function to read object info via path, questioning whether this design assumes too much about the storage implementation (filesystem paths) when future backends might use databases or blob storage without such concepts.

The exchange highlights an architectural tension in the ODB abstraction effort - how to transition from filesystem-centric APIs to truly backend-agnostic ones. Taylor's comment suggests the path-based approach might be premature optimization for the current loose-object implementation at the cost of future flexibility. This comes early in the series (part 3 of 14), indicating the discussion could influence subsequent API design before the abstraction is fully locked in.

The thread context shows this series is otherwise technically complete and ready for Junio's review, with this being one of the few remaining design questions. The concern touches on a core goal of the ODB effort - creating interfaces that genuinely enable diverse storage backends rather than just abstracting the existing filesystem model.
