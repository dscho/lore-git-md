This is a follow-up discussion about the recently merged `status.compareBranches` configuration feature, focusing on refname resolution behavior. Junio Hamano is pushing back against the idea of deferring full DWIM (Do What I Mean) resolution rules to a future patch, arguing that the current hardcoded `refs/remotes/` prefixing creates an implicit interface constraint that should be addressed now rather than later.

The core issue is that the merged implementation automatically prepends `refs/remotes/` to branch names (unless they use `@{upstream}` or `@{push}` syntax), which differs from Git's standard ref resolution behavior where local branches (`refs/heads/`) normally take precedence. Junio notes this prevents natural use cases like comparing against tags or local branches, and suggests either:

1. Implementing the full `ref_rev_parse_rules[]` DWIM resolution now, or
2. Explicitly deciding to permanently restrict comparisons to remote-tracking branches

While the feature works as implemented (with thorough test coverage and optimizations like Jeff King's `strset` already incorporated), this post-merge discussion reveals a design tension about future flexibility. Junio's position is that deferring the decision effectively locks in the current behavior, making it harder to extend later without breaking existing configurations. The thread shows the maintainer's typical focus on long-term interface stability, even for freshly merged features.
