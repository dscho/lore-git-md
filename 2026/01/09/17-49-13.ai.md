Bugfix patch addressing race conditions in `git fsck` when run on live repositories, now in its third iteration with significant refinements from community feedback. This version represents a collaborative effort between Elijah Newren, Jeff King (Peff), and Junio Hamano, though it has diverged substantially from Matthew John Cheetham's original approach (who has requested removal of attribution).

The core issue involves `git fsck` reading refs at operation start/end, making it vulnerable to races during concurrent repository modifications - particularly problematic for automated maintenance and forge operations. The solution has evolved through review to handle both forward (new objects) and reverse (GC deletion) race cases while maintaining clear technical boundaries.

Key technical elements in this version:
- Introduces `struct ref_snapshot` to replace parallel arrays for refnames/OIDs
- Handles command-line specified refs as well as default ones
- Uses timestamp-based reflog filtering (marked as TODO for potential improvement)
- Explicitly documents worktree/index limitations
- Preserves existing fsck behavior for non-concurrent cases
- Adds `odb_reprepare()` for fresh object DB state

The implementation favors availability over strict consistency, particularly important forges where locking during object addition would be problematic. While most focused on ref handling, the patch leaves clear markers for future improvements to index and reflog handling, particularly around network filesystem clock skew.
