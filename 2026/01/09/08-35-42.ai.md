Feature implementation in the ongoing git-history series. This patch adds the "reword" subcommand to the experimental `git-history` command, providing a faster alternative to interactive rebase for changing commit messages.

The implementation builds on Git's replay machinery to perform the operation in-memory without checking out the commit, allowing it to work even with uncommitted changes. Key characteristics include:
- Operates on a single commit at a time (unlike rebase which handles ranges)
- Supports three reference update modes via `--ref-action`: update all branches containing the commit (`branches`), only update HEAD (`head`), or print updates without applying them (`print`)
- Preserves original authorship and tree while only modifying the commit message
- Currently skips hook execution (though the implementation leaves room for future hook support)
- Includes comprehensive tests covering basic usage, edge cases, and integration with the replay infrastructure

The patch touches several subsystems:
- Adds new files: `builtin/history.c` and `t/t3451-history-reword.sh`
- Modifies existing replay infrastructure in `replay.c`
- Updates documentation in `Documentation/git-history.adoc`
- Integrates with build systems via `t/meson.build`

Notable technical details:
- Uses `wt_status_collect_changes_trees()` to show changes in the editor
- Implements custom reference update logic via `handle_reference_updates()`
- Maintains the experimental status marker in documentation
- Adds 344 lines of test coverage across various scenarios

This represents the first concrete subcommand in the git-history series, establishing patterns likely to be followed by future subcommands. The implementation carefully avoids some of rebase's limitations (like requiring a clean working tree) while maintaining clear boundaries around what it can and cannot do (like replaying merge commits).
