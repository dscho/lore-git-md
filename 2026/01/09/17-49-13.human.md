This is the third version of a bugfix patch addressing race conditions in `git fsck` when run on live repositories. The patch comes from Elijah Newren with input from Junio Hamano and Jeff King, and represents a significant evolution from the original approach by Matthew John Cheetham (who has requested removal of attribution due to the extensive changes).

The core issue is that `git fsck` currently reads refs at operation start/end, making it vulnerable to races during concurrent repository modifications - particularly problematic for automated maintenance and forge operations. The solution now takes a snapshot of refs at program start, performs the connectivity check, then verifies against the snapshotted refs. This handles forward races (new objects being added) while still leaving GC-related reverse races as a known limitation.

Key technical changes include:
- Introducing a `struct ref_snapshot` to replace parallel arrays
- Snapshotting both default refs and command-line specified refs
- Using timestamp-based filtering for reflogs (with TODO for improvement)
- Adding `odb_reprepare()` for fresh object DB state
- Explicitly documenting worktree/index limitations

The patch shows careful attention to real-world use cases while maintaining clear technical boundaries. It's particularly relevant for forge operators but also benefits automated jobs and casual users. The implementation has been refined through community collaboration, with maintainer feedback directly incorporated into the design. While some edge cases remain (network filesystem clock skew, GC races), this represents a substantial improvement in fsck's robustness.
