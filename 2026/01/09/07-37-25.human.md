This is a refactoring patch in the ongoing `git history` series, specifically addressing the replay infrastructure that the new command will build upon. Patrick Steinhardt responds to D. Ben Knoble's observation about potentially flipped return codes in the replay logic.

The core issue involves error handling semantics in `cmd_replay()` - the function appears to have inconsistent return value conventions between error cases (merge conflicts vs other errors). Knoble noted that while the current fix seems correct, the original behavior from commit 81613be31e used different truthy/falsy meanings that made the logic hard to follow at a glance.

Steinhardt confirms the intent is to maintain three distinct exit states:
- 128 for generic errors
- 1 for merge conflicts
- 0 for success

He acknowledges the current implementation doesn't properly preserve this and commits to refactoring the code to make these cases more explicit. This is part of the broader effort to extract and clean up replay logic that will be shared between the existing `replay` command and the new `history` functionality.
