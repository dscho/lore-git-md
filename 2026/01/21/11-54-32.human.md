This is a feature proposal from Simon Richter about handling repositories with intentionally omitted objects, motivated by Debian's desire to move to Git-based source package storage while excluding certain non-redistributable or vendored files.

The core idea is to enable verification of unmodified files while explicitly tracking which paths were removed, allowing continued work on such repositories as long as excluded paths aren't modified. The proposal would extend Git's capabilities beyond what `git archive` provides, adding the ability to:
- Store a commit and its tree with some objects intentionally missing
- Preserve tag signatures when present
- Maintain a record of removed paths
- Allow safe cloning and further development (with constraints)

Simon acknowledges this may challenge Git's design principles and is seeking feedback on feasibility. The use case is practical - Debian wants Git-based source management but needs to handle cases where they must exclude certain files from upstream repositories while maintaining verifiability for the remaining content.

The proposal could also incidentally help with recovery of repositories missing objects. This looks like a thoughtful exploration of Git's boundaries for a real-world packaging workflow need, though it's unclear how it would interact with Git's object model fundamentals. The tone is appropriately exploratory, recognizing this may not fit Git's design.
