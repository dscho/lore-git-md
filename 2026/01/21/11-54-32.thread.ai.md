Git thread summary:

Feature proposal for Git to support repositories with intentionally missing objects, targeting Debian's use case of storing source packages while excluding non-redistributable files or vendored dependencies. Simon Richter's original proposal outlined requirements: verifying unmodified files in received bundles, listing removed paths, allowing work on clones that avoid omitted paths, and maintaining minimal archive contents (commit, tree, dependencies, optionally signed tag). Philip Oakley continues the discussion by referencing prior unsuccessful attempts at object redaction from Git Merge 2020 and proposing speculative technical approaches.

Philip explores two potential solutions: 1) specially-formatted replacement objects that preserve commit graph structure while marking omitted content, and 2) creating separate commits with deletions to leverage Git's content deduplication. He emphasizes the distinction between metadata (which must remain intact for graph integrity) and content (where exceptions might be possible), while acknowledging these ideas remain unproven.

Key technical constraints under discussion include maintaining Git's hash-based integrity model while creating exceptions for omitted content. The conversation remains at conceptual stage, focused on finding a minimal viable feature that could work within Git's design principles. Open questions persist about verification mechanisms for partial repositories and whether any solution could provide sufficient integrity guarantees for distributed workflows, particularly regarding how to handle missing objects during fetches and clones while still allowing useful work on the remaining content. The thread represents an ongoing challenge in balancing Git's strict object model with practical use cases requiring selective content exclusion.
