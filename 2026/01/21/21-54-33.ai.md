This is part of a larger hook subsystem refactoring series (v7, patch 9/12) that introduces parallel execution capabilities for Git hooks. The patch adds a `jobs` option to the hook API, allowing callers to specify how many hook processes can run in parallel while maintaining output stream integrity.

The change defaults to sequential execution (jobs=1) to maintain current behavior, but lays groundwork for future parallel execution by:
1. Adding a `jobs` field to `struct run_hooks_opt` with documentation
2. Setting `ungroup=0` when jobs>1 to buffer output de-interleaving
3. Adding BUG checks for invalid job counts
4. Preserving the existing sideband output mechanism for sequential case

The patch includes detailed ASCII diagrams showing how output handling differs between sequential and parallel modes, with the parallel case routing through run-command's buffering to prevent interleaving. This implements Jeff King's suggested design for maintaining output integrity while enabling future parallelization.

As part of the ongoing hook API conversion effort, this change is well-integrated with previous work (stdin streaming, pre-push hook support) and has sign-offs from key contributors. It represents a stepping stone toward the series' eventual goal of configurable parallel hook execution while maintaining all current functionality.
