Maintainer response on `git stash` behavior with untracked files. Junio C Hamano clarifies that the current behavior of `git stash` using `reset --hard` is intentional - it's designed to quickly clean the working tree (a "panic button" scenario) and that untracked files getting removed is expected when they conflict with restoring the tracked state. 

He notes the distinction between `stash push` (which shouldn't fail) and `stash pop` (which can fail for conflict resolution). The maintainer questions whether the "BUG" comment in the code might relate to the `-u` (untracked files) mode, but confirms that without `-u`, removing conflicting untracked files is correct behavior.

This response effectively closes the RFC by explaining the design rationale behind the current implementation. The thread shows a good example of a beginner contributor identifying what appears to be a bug, only to learn it's actually intentional behavior with sound reasoning behind it.
