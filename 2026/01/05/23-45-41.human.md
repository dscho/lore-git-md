This is a performance investigation email in an ongoing thread about `git pack-refs --all` slowness on large repositories with millions of refs. Martin Fick follows up on Jeff King's analysis with new findings from strace timing data.

Martin reports that after properly accounting for filesystem caching, he's confirmed that object repacking doesn't actually speed up `pack-refs`, contrary to earlier observations. The slowness persists even with a minimal pack setup (one used pack and one cruft pack). 

Using strace timing flags, Martin discovered that while the actual write operations (at 8KB chunks) are fast, nearly all the runtime (4 out of 4.15 minutes) occurs in the gaps between system calls. He hypothesizes this could be due to slow mmap access patterns over NFS when reading the packed-refs file, or possibly some inefficient in-memory ref lookup mechanism.

This email advances the investigation by ruling out several potential bottlenecks (loose objects, pack count, write buffering) and pointing toward memory access patterns as the likely culprit. The thread remains focused on understanding why Git's files backend performs worse than JGit in high-refcount scenarios despite similar verification and I/O patterns.
