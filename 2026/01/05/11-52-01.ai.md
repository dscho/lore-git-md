This is a follow-up in an ongoing discussion about the `git last-modified` command's behavior and performance characteristics. Gusted@Codeberg.org reports three issues they encountered while testing the command on a Forgejo repository with Git v2.52.0. Command author Toon Claes responds to each case:

1. **Performance characteristics** - Confirms the single-file case is slower than `git log --max-count=1` (151ms vs 87ms) but defends the design choice, showing a 6x speedup for bulk operations (141ms vs 852ms for multiple files). The optimization purpose remains valid for its intended multi-file use case.

2. **Directory handling behavior** - Acknowledges the current behavior (returning identical commits for parent/child directories) is confusing. Proposes changing the default to match `-r --max-depth=0` behavior (different commits for different levels) and seeks feedback on this change. Gusted agrees this would be more intuitive, comparing it to `git-diff-tree`'s defaults.

3. **Crash condition** - Confirms the BUG() assertion when passing a tree commit ID directly is unintended and requires proper error handling instead of crashing. Gusted's report is validated as a legitimate bug discovery.

The thread shows active maintenance of this relatively new command, with the author receptive to real-world feedback. Key technical details include the command's optimization tradeoffs (prioritizing bulk operations) and directory traversal semantics. Open questions remain about the proposed directory behavior change and crash fix implementation.
