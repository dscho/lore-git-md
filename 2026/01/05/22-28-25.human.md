This is a continuation of the discussion about moving "core.attributesFile" configuration into `struct repo_settings` as part of the `the_repository` removal effort. Junio C Hamano weighs in on Phillip Wood's concern about lazy vs eager config parsing regressions that can occur when moving settings to the repository-scoped structure.

Junio acknowledges the behavior change (where invalid attribute paths now fail during operations rather than at startup) but questions whether early failure is always desirable. He gives the example of `git cat-file` which shouldn't fail on invalid attribute paths it doesn't use. Junio suggests commands should declare which settings they use to skip irrelevant validation, cautioning against "overusing repo_settings" as a "disease" - while moving globals to per-repo storage is good, parsing behavior changes need careful consideration.

The exchange highlights the tension between architectural improvements (removing globals) and maintaining predictable user experience. Junio's input as maintainer adds weight to the discussion, suggesting the team needs to resolve this parsing behavior question before proceeding with more settings migrations. The technical discussion shows careful review from experienced contributors, with test coverage remaining solid but behavioral implications needing resolution.
