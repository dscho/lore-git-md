This is a response in the ongoing discussion about adding Bazel build support to Git. brian m. carlson expresses strong reservations about introducing a fourth build system (alongside Make, Meson, and contrib/CMake), citing the existing maintenance burden. They specifically object to the current Bazel implementation's hardcoding of configurable paths (SHELL_PATH, PERL_PATH, PYTHON_PATH) and platform-specific defines, arguing this would break functionality on many systems where these values need to be customized. The response suggests that any Bazel support would need to match the flexibility of Git's existing build system before being suitable for either upstream inclusion or publication in the Bazel Central Registry.

Key technical concerns raised: the loss of configurability for critical paths and incorrect assumptions about platform capabilities (like strlcpy availability). The reply positions this as a regression from Git's current build system capabilities rather than an improvement. The tone is firm but grounded in specific technical objections rather than blanket opposition to Bazel itself. This response will likely require the original proposer to either demonstrate how these concerns can be addressed or reconsider their distribution approach.
