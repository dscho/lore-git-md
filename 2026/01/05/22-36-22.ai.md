This is a follow-up email in the thread about configuring Git for triangular workflows (pull from one remote, push to another). D. Ben Knoble provides a detailed description of his personal workflow configuration, building on his earlier response to Harald Nordgren's query.

The email outlines a comprehensive setup using two remotes (typically "origin" for pulling and a personal remote like "benknoble" for pushing). Key configuration includes global settings like `push.default=current` to enable the `@{push}` ref, `pull.rebase=true`, and `branch.autoSetupRebase=always`. Per-repository, he sets `remote.pushDefault` to the push remote. The workflow automatically sets up both `@{upstream}` (pull remote) and `@{push}` (push remote) tracking when creating branches with `git switch -c`.

Knoble describes his daily workflow commands including aliases for common operations: `git pull` for rebasing, `pf` for force-pushing with lease, `rdup` for range-diffs between upstream and push refs, and custom commands `git sbup` and `git div` for visualizing branch relationships. He notes this setup works well for PR-style review workflows but mentions limitations when dealing with Git's own repository structure where topic branch merges can complicate divergence visualization.

The email provides concrete examples and links to Knoble's dotfiles for reference, offering a practical implementation of the triangular workflow concept discussed earlier in the thread. The approach assumes comfort with rebase-based workflows and some familiarity with Git's refspec syntax.
