This is the second version of a feature patch series introducing a `--reverse=before` option for revision walks, allowing reversal to happen before commit limiting rather than after. The series now consists of two patches: the core implementation and a memory optimization for the new behavior.

Key changes from v1:
1. Simplified the interface by removing the non-stuck form of `--reverse`
2. Made bare `--reverse` toggle between states: no-reverse → reverse-after → no-reverse → reverse-before → no-reverse
3. Added a memory optimization window when using `--reverse=before` with `--max-count`
4. Updated documentation to clarify the toggle behavior

The first patch implements the core functionality, modifying the revision walking machinery in `revision.c` to handle the new state transitions and ordering. The second patch optimizes memory usage by implementing a sliding window approach when combining `--reverse=before` with commit limits.

The thread has evolved from initial implementation discussions to refining edge case behavior, with Jeff King having proposed enhanced state machine handling in response to the v1 submission. This version appears to address those concerns while adding practical optimizations for real-world usage. The patch touches key files in the revision walking subsystem (`revision.[ch]`) and includes thorough test coverage in `t4202-log.sh`.

The series remains focused on its original goal of enabling use cases like `git log --reverse --max-count=3` to show the first commits rather than the last, but now with more robust handling of multiple `--reverse` specifications and better memory characteristics. Documentation has been expanded to clarify the toggle behavior's nuances.
