This is a v2 bugfix patch from Karthik Nayak addressing lock file handling in the files ref backend's consistency checks. The patch moves the lock file skipping logic from individual validation functions to the directory iteration level, ensuring all checks consistently ignore lock files.

The key changes in v2 are:
1. A clarified commit message explaining the two-phase checking process
2. More accurate code comments about lock file handling
3. Additional test cases verifying behavior with bare lock files

The patch now properly handles three scenarios:
- Skipping valid-looking lock files (e.g. "refs/heads/branch.lock")
- Rejecting invalid refnames that happen to end in ".lock" (e.g. ".branch.lock")
- Continuing to validate actual ref contents when they're not lock files

The implementation follows Junio Hamano's earlier suggestion to centralize the lock file check rather than having each validation function handle it separately. The test coverage appears thorough, verifying both the skipping of valid lock files and the continued validation of malformed refs.

This version addresses Christian Couder's feedback from v1 about comment accuracy and hidden file handling. The core approach remains the same - unconditionally skipping ".lock" files during directory iteration - which Karthik argues is the simplest solution, though he acknowledges more sophisticated validation could be added later if needed.

The patch touches refs/files-backend.c and adds test cases to t/t0602-reffiles-fsck.sh. It's a focused, well-tested fix for a clear inconsistency in the refs files backend's validation behavior.
