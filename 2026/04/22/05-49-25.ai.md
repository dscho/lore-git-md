This is a follow-up in the security discussion about `git-credential-libsecret` leaking credentials during store operations. Mantas Mikulėnas clarifies several key aspects of the interface contract:

1. The credential helper protocol's specification that stdout is ignored during store/erase operations doesn't technically prohibit output - it just means the output will be discarded when used through the proper Git interface. The current behavior, while odd, doesn't violate the contract.

2. The direct invocation pattern that exposes the leak is not the documented user interface - `git credential approve` is the intended way to store credentials, and it properly discards helper output. The widespread use of direct helper invocation in documentation and scripts represents a community misunderstanding rather than a protocol flaw.

3. While agreeing the helper should be fixed to avoid unnecessary output (and inviting a patch), Mikulėnas argues this doesn't rise to CVE-worthy severity since the vulnerable pattern involves bypassing Git's intended interface. The risk is somewhat self-inflicted by those using internal implementation details as public API.

The exchange highlights an important distinction between Git's public credential storage interface (`git credential approve`) and internal helper protocol details that happen to work when invoked directly. This clarification helps frame both the severity assessment and solution approach - fixing the helper's output while also potentially documenting the proper usage patterns to prevent similar misuse.
