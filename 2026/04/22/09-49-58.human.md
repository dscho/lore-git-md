This is a bugfix patch from Karthik Nayak addressing how lock files are handled during ref consistency checks in the files backend. It's the second version of a patch that has already received substantive review from both Junio Hamano and Christian Couder.

The core issue is that while some ref validation checks were skipping lock files (temporary files ending in ".lock"), others were processing them. The patch moves the lock file skipping logic higher up in the call stack to `files_fsck_refs_dir()`, ensuring all validation checks consistently ignore lock files. This is a cleaner architectural solution than having each check implement its own skipping logic.

The v2 iteration incorporates feedback from the reviews:
- The commit message is clarified
- The code comment about bare ".lock" files is made more accurate
- Additional test cases are added to verify behavior with bare lock files and hidden lock files (like ".branch-1.lock")

The patch appears well-constructed with thorough test coverage. The discussion has converged on the technical approach, with only minor open question about whether the lock file check might better belong in `files_fsck_ref()` itself (Junio's suggestion). This seems ready for merging once that last architectural point is addressed.
