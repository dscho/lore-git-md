This is a technical discussion about the ongoing alias regression fix, where Jeff King (Peff) weighs in on the design tradeoffs for Git's alias system. The thread began with a regression in Git 2.54.0 that broke hierarchical aliases (like `pull.sub`), and has evolved into a broader conversation about how to balance backward compatibility with future extensibility.

Peff suggests an alternative approach where Git could interpret `alias.foo.bar` both as a single alias "foo.bar" and as the "bar" key of alias "foo", without special-casing any key names. This would maximize backward compatibility but could create some edge cases, like accidentally creating aliases ending in ".command" or future metadata keys. He acknowledges this might be overkill, as reserving specific keys like "command" and future attributes would likely have minimal impact on users.

The discussion highlights the tension between maintaining compatibility (especially for configs that need to work across Git versions) and keeping the system clean for future extensions. Peff notes that while a separate namespace (like `nalias`) would technically solve the problem, it might not provide the best user experience. The core fix for the regression remains sound, but this exchange surfaces important considerations about how the alias system should evolve.
