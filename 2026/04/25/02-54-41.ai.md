Maintainer follow-up on the `--fetch` checkout/switch proposal.

Junio C Hamano continues to push back against the proposed `--fetch` option, now suggesting it may be better integrated with the existing `--track` functionality rather than being a standalone flag. He expresses fundamental concerns about automatically fetching remote refs, noting that many Git operations rely on the stability of remote-tracking branches. The maintainer proposes that if such behavior were to be implemented, it should be tied more closely to branch tracking setup rather than being a general checkout feature.

The feedback raises several key points:
1. The current proposal's scope (just checkout/switch) may be too narrow given how widely remote-tracking refs are used across Git
2. Automatic fetching behavior could introduce usability issues when working with multiple branches from the same remote
3. The maintainer personally prefers not to see this change implemented at all, citing unaddressed edge cases

This response effectively puts the proposal on hold, as the maintainer's position makes clear the feature would need significant redesign to be considered. The ball is now in the author's court to either:
- Substantially rework the approach to address these concerns
- Make a case for why checkout/switch should be special cases
- Withdraw the proposal

The thread has moved from implementation details to fundamental design questions about Git's behavior with remote refs, suggesting this may not land without broader consensus on how automatic fetching should work across commands.
