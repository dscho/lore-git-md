This is a brief reply in the ongoing discussion about adding a `--set-head` option to `git remote add`. The author, Harald Nordgren, acknowledges D. Ben Knoble's suggestion that the GitHub `gh` tool could instead run `git remote set-head` as a separate command after adding the remote.

The key point here is a symmetry argument: since `git clone` automatically sets the remote's HEAD reference, having `git remote add --set-head` would provide consistent behavior when adding secondary remotes (like forks). The tone is conciliatory ("maybe we should" go with the client-side approach) while still presenting the design rationale for the Git-side change.

This moves the discussion toward weighing consistency with clone behavior against the simplicity of keeping the change client-side. The technical merits remain sound, but the thread now hinges on whether this behavioral symmetry justifies a new Git option.
