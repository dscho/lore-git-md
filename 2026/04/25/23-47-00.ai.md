This is a technical discussion about the alias system design, where Jeff King proposes an alternative implementation approach for the hierarchical alias fix. The thread began with a regression in Git 2.54.0 that broke dotted aliases (like `pull.sub`) and has evolved into a design discussion about namespace handling.

King suggests modifying the alias lookup to consider `alias.foo.bar` as both:
1. A single alias "foo.bar" (for backward compatibility)
2. The "bar" key of alias "foo" (for future extensibility)

This dual interpretation would avoid special-casing any key names (like "command") and maximize backward compatibility, though it could create some edge cases. The proposed code shows how this would work in `alias.c`, with comments explaining the behavior for both historical aliases and potential metadata attributes.

The discussion highlights the tradeoff between maintaining compatibility (especially for configs that need to work across Git versions) and keeping the system clean for future extensions. While this approach is more complex than the original fix, it would provide smoother transitions when new alias attributes are added. The core issue remains the same - how to handle dotted aliases while preserving future extensibility - but this email surfaces a new technical approach to consider alongside the existing proposals.
