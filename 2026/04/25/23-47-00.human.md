King suggests modifying the alias lookup to interpret `alias.foo.bar` in two ways simultaneously: both as a single alias "foo.bar" (for backward compatibility) and as the "bar" key of alias "foo" (for future extensibility). This differs from the current patch's approach of special-casing the "command" key. The proposal would handle future metadata keys more gracefully but could create some edge cases, like duplicate entries in alias listings.

The discussion highlights the tension between maintaining compatibility (especially for configs that need to work across Git versions) and keeping the system clean for future extensions. King acknowledges this approach is more complex than simply reserving certain key names, but argues it provides better backward compatibility. He includes a concrete diff showing how the implementation would look in alias.c.
