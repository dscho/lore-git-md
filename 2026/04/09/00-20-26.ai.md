This is a platform compatibility discussion about `writev()` optimizations in Git's network code, continuing from test failures in Git 2.54.0-rc1 on NonStop systems. brian m. carlson weighs in on Jeff King's analysis of the `writev()` optimization tradeoffs.

brian m. carlson examines the POSIX specifications and finds no constraints on vector sizes beyond the SSIZE_MAX limit, noting that 64KiB seems like a reasonable minimum expectation for network operations. They observe that major platforms like Linux and BSDs set much higher SSIZE_MAX values (INT_MAX or LONG_MAX), making NonStop's 52KB limit for 32-bit systems unusually restrictive. Their position is that platforms with such small SSIZE_MAX values should simply use NO_WRITEV rather than complicating the code with runtime fallbacks.

The email raises an important forward-looking concern about Rust integration - the `write_vectored` API in Rust would likely inherit the same platform limitations, potentially recreating this issue when Rust code uses network operations. While brian m. carlson states they don't strongly oppose Jeff King's proposed runtime solution, their analysis clearly favors the simpler NO_WRITEV approach for constrained platforms.

This contribution reinforces the technical basis for Junio Hamano's skepticism about the optimization's value while acknowledging the architectural tension between performance gains and broad platform compatibility. The Rust compatibility note adds a new dimension to consider for future development.
