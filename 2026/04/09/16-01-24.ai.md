This is a discussion about the `git repo info` feature's path handling design and GSoC participation norms. Karthik Nayak responds to Junio C Hamano's questions about how to handle path normalization in the new `paths.toplevel` output, suggesting two possible approaches: either making it configurable via a boolean flag, or outputting both relative and absolute paths as separate fields. He emphasizes the need to finalize this design before implementing more path-valued options.

The second part of the email addresses Junio's question about GSoC candidates working on projects before selection. Karthik clarifies that while GSoC rules don't prohibit pre-selection contributions, the project recommends against it to avoid creating confusion for other applicants working on the same topic. He notes the tension between open source's inclusive nature and maintaining fairness in the selection process.

The discussion shows the patch is currently blocked on two fronts: technically, the path handling design needs consensus, and process-wise, there are open questions about GSoC candidate participation timing. Karthik's response provides useful context for both issues while maintaining the project's collaborative tone. The path design question in particular need resolution before the `repo info` feature can move forward, as it will affect all future path-valued outputs.
