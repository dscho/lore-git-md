This is a platform compatibility discussion about `writev()` optimizations in Git's network code, continuing from test failures in Git 2.54.0-rc1 on NonStop systems. brian m. carlson weighs in on Jeff King's earlier analysis of potential solutions.

brian m. carlson examines the POSIX specifications and finds no constraints on individual write sizes beyond the SSIZE_MAX limit, noting that 64KB seems like a reasonable minimum expectation for modern systems. They observe that major platforms like Linux and BSDs set much higher limits (INT_MAX or LONG_MAX), making NonStop's 52KB limit for 32-bit systems unusually restrictive. Their position aligns with Jeff King's first proposed solution: systems with overly restrictive limits should simply disable `writev()` via NO_WRITEV rather than complicating the code with runtime fallbacks.

The email raises an interesting forward-looking concern about Rust integration, noting that future use of Rust's `write_vectored` would inherit the same platform limitations. While brian m. carlson expresses no strong objection to implementing runtime fallback logic, their analysis clearly favors the simpler NO_WRITEV approach for constrained platforms. The technical assessment reinforces Junio Hamano's earlier skepticism about the optimization's value versus its complexity.
