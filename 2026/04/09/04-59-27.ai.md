This is a feature patch in the fsmonitor series, specifically addressing a potential hang condition in the cookie wait mechanism. The change replaces an infinite `pthread_cond_wait()` with a one-second timeout using `pthread_cond_timedwait()`, preventing indefinite blocking when filesystem events fail to arrive.

The patch solves a real problem where certain container/overlay filesystems may successfully register inotify watches but never deliver events, which could cause the daemon and client to hang forever waiting for a cookie event. The solution introduces proper timeout handling - if the wait times out after one second, it logs the event and returns an error, allowing the client to proceed with a full scan rather than blocking indefinitely.

Key technical aspects:
- Uses `gettimeofday()` to calculate the timeout timestamp
- Converts microseconds to nanoseconds for the timespec
- Handles `ETIMEDOUT` by setting the cookie result to `FCIR_ERROR`
- Maintains the existing locking and condition variable signaling pattern
- Adds trace logging for timeout events

This change completes the Windows compatibility work in the fsmonitor series by ensuring the daemon can properly handle timeout scenarios across all platforms. The implementation is clean and follows the established patterns in the codebase, with careful attention to thread safety and error handling. The one-second timeout seems reasonable given the context - long enough to avoid false positives from normal filesystem delays but short enough to prevent noticeable hangs.
