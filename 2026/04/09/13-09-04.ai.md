This is a technical follow-up in the bugfix thread addressing a `git clone` segfault with `--revision` when servers ignore ref filtering. Adrian Friedli provides a detailed analysis of all four callers of `guess_remote_head()` in response to Junio C Hamano's review questions, showing that three already safely handle NULL `peer_ref` values.

The analysis reveals that `get_expanded_map()` explicitly checks for NULL `peer_ref`, suggesting this is an expected case in the API contract. For the problematic clone path, Adrian notes that without the `REMOTE_GUESS_HEAD_ALL` flag, `guess_remote_head()` returns only the most likely ref, implying the current behavior (returning a ref with NULL `peer_ref`) may be correct for this case. The segfault occurs specifically in `update_remote_refs()`, which is the only caller that doesn't properly handle the NULL case.

This response strengthens the case for the original patch's approach of adding a NULL check in `update_remote_refs()`, as it demonstrates that other callers already account for this possibility. The discussion now hinges on whether this localized fix is sufficient or if a broader change to `guess_remote_head()`'s contract is warranted. The analysis provides concrete evidence that NULL `peer_ref` values are already part of the expected behavior in most calling contexts.
