This is a technical discussion about improving `git subtree split`'s handling of merge-heavy histories, continuing from an earlier bug report. Colin Stagner responds to Ian Jackson's proposed algorithm for making subtree splits more deterministic.

Colin confirms that the current `subtree split` implementation is deterministic but inefficient, needing to reconstruct the complete split history each time. He highlights a key issue with the documented guarantee that identical splits produce identical commit IDs - this hasn't held up due to behavior-changing fixes over time. He suggests a config file approach to record both current split preferences and historical split methods to enable improvements without breakage.

On Ian's proposed algorithm, Colin notes that cases 0 and 1 (single-parent changes) match current behavior, while the merge handling (cases 2 and 3) is where most history-breaking changes have occurred. He cautions about edge cases in merge processing and recommends visual diagramming. Colin also clarifies that `subtree split` isn't particularly aware of `subtree merge` operations, and that merge trailers don't be relied upon due to potential rebasing.

Colin shares his personal workflow preferences, favoring plain `git merge` with an upwards workflow for most cases, using `subtree merge` only for dependencies, and `format-patch` for submitting changes rather than `split`. He uses `split` primarily for creating read-only views of subdirectories. His response provides practical context about real-world usage patterns while acknowledging others may have different needs.

The discussion remains technical and solution-focused, with Colin offering implementation insights and workflow context while neither endorsing nor rejecting Ian's proposal outright.
