This thread explores a proposal from new contributor JAM to add `--recurse-submodules` support to `git worktree add`, aiming to improve submodule handling in multi-worktree development scenarios. The initial RFC suggested sharing submodule data via hardlinks while adjusting config paths, but Phillip Wood—a worktree and submodule expert—identified a critical limitation: shared submodule directories would prevent different worktrees from having independent submodule checkouts, since HEAD state cannot be shared. 

Junio Hamano, while not a submodule user himself, has now weighed in to reinforce Phillip's technical assessment. The maintainer agrees that any viable solution must provide proper isolation of submodule working state across worktrees, mirroring Git's existing worktree model where repository data is shared but per-worktree state (like HEAD) remains independent. This feedback from both a domain expert and the maintainer establishes a clear technical hurdle for the proposal: it cannot sidestep the need for worktree-specific submodule configuration. The discussion now turns to whether and how this fundamental design challenge can be resolved while preserving the object-sharing benefits that motivated the original approach.
