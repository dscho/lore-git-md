This thread explores a proposal to add `--recurse-submodules` support to `git worktree add`, addressing a long-standing gap in functionality. The original RFC from JAM suggested a pragmatic approach using hardlinks to share submodule object data while adjusting config paths, deliberately sidestepping deeper questions about per-worktree submodule configuration that had stalled prior discussions.

Phillip Wood, a recognized expert in worktree behavior, has raised a key technical concern: while the proposal efficiently shares object storage, it would force all worktrees to share the same submodule checkouts since HEAD state cannot be shared. This limitation undermines the core use case of concurrent development across worktrees with different submodule states. The discussion has surfaced a fundamental tension between sharing object data and maintaining worktree isolation for submodules.

The proposal now faces a clear design challenge that must be resolved - how to properly isolate submodule working state across worktrees while still benefiting from shared storage. Phillip's critique suggests the solution may require revisiting those previously avoided questions about per-worktree submodule configuration. The thread awaits either a revised approach from the original author or further discussion about whether this limitation is acceptable given the feature's target use cases.
