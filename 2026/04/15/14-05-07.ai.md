Feature proposal for submodule support in worktrees, with technical concerns raised. Phillip Wood responds to JAM's RFC for adding `--recurse-submodules` to `git worktree add`, questioning the design's handling of per-worktree submodule state. While the original proposal focused on sharing submodule object data via hardlinks to avoid configuration complexity, Phillip points out a key limitation: shared modules directories would prevent different worktrees from having different submodule checkouts (different HEADs in submodules), since HEAD is per-worktree state that cannot be shared.

The exchange highlights a tension in the design - the desire to leverage existing object sharing while needing to maintain worktree-specific state for submodules. Phillip's response suggests the current approach may not fully solve the use case of concurrent worktree development with submodules, as it would force all worktrees to share submodule checkouts. This technical objection may require revisiting the earlier avoided questions about per-worktree submodule configuration.

The thread now has a clear technical sticking point to resolve before the feature can move forward: how to properly isolate submodule working state across worktrees while still benefiting from shared object storage. Phillip's expertise in worktree and submodule behavior makes this a substantive critique that the proposal will need to address in any revision.
