This is an RFC proposal to add `--recurse-submodules` support to `git worktree add`, addressing a long-standing gap in worktree functionality. The patch comes from a new contributor and takes a pragmatic approach to a problem that has previously stalled on deeper design questions about submodule configuration.

The core idea is to leverage the existing object store sharing that worktrees already use, extending it to submodules by hardlinking the modules directory and adjusting configuration paths. This avoids the thornier questions about per-worktree submodule configuration that derailed earlier discussions in 2015-2016. The immediate motivation comes from multi-agent development workflows where submodule support is currently a pain point.

The proposed implementation would:
1. Hardlink submodule data from the main repo to avoid duplication
2. Update submodule config paths to point to the new worktree
3. Initialize submodule working trees locally
4. Handle both regular and worktreeConfig extension cases

The attached prototype shell script demonstrates the approach. Open questions remain about how to handle uninitialized submodules and whether the community would want this as a proper feature. The patch references prior discussions with Glen Choo and others, showing awareness of the historical context.

This looks like a well-motivated proposal that tackles a real pain point while sidestepping the more controversial aspects of submodule configuration. The implementation approach seems sound based on the description, though the actual C implementation would need review. The use case for multi-agent workflows gives this particular relevance as development practices evolve.
