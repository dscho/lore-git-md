This is a technical discussion thread about adding `--recurse-submodules` support to `git worktree add`, building on an earlier RFC proposal from a new contributor. Phillip Wood, a contributor with expertise in worktree handling and the sequencer, raises an important technical concern about the proposed approach.

The core issue Phillip identifies is that while sharing the submodule object store via hardlinks makes sense (mirroring how worktrees already share the main object store), the current proposal would also share the submodule's gitdir (containing HEAD and other per-worktree refs). This would prevent different worktrees from having different submodule checkouts - a key use case the feature aims to support.

Phillip's question highlights a gap in the original proposal's design: it correctly handles object store sharing but doesn't properly account for the need to maintain separate submodule worktree states. His comment suggests the solution may need to involve creating per-worktree submodule gitdirs (similar to how main worktrees work) while still sharing the underlying object store.

This is a substantive technical critique from someone familiar with worktree internals, and it points to an area the proposal will need to address in any revised version. The thread shows healthy technical discussion - identifying a real limitation while acknowledging the value of the overall goal.
