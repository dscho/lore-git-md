This is a maintainer review response in Lorenzo Pegorari's GSoC patch series about promisor file handling during repacks. Junio Hamano provides clarification on the timestamp rationale in the proposed `copy_promisor_content()` helper function.

Junio corrects the commit message's explanation about using modification time instead of creation time - the key point isn't about ease of access (since UNIX filesystems don't reliably track creation time anyway), but rather that the modification time serves as a useful proxy for when the remote refs were fetched. This timestamp allows debuggers to understand the temporal relationship between entries, especially when the same ref appears multiple times across different `.promisor` files.

The response doesn't request any code changes to patch 2/5, but does improve the conceptual framing of why timestamps matter in this context. This clarification will help future maintainers understand the design decisions when working with the promisor file handling code.
