This is a technical follow-up in the `contrib/subtree` discussion, where Ian Jackson identifies a significant limitation in their proposed Rust/libgit2 implementation for `git subtree split`. 

Ian discovers that their initial assumption about detecting subtree merges through commit message metadata doesn't hold - only `git-subtree add` includes the necessary markers, while `git-subtree merge` does not. This makes it impossible to reliably distinguish between genuine subtree merges and regular branch merges in existing histories without breaking compatibility.

The email raises two key points:
1. The Rust implementation would require fundamental changes to the data model to work correctly, potentially breaking existing workflows
2. Ian proposes either maintaining compatibility (which seems difficult) or creating a "version 2" of the command with different behavior

This development complicates the already-contentious discussion about the future of this component, as it now appears the Rust approach may require more invasive changes than originally thought. The email seeks Colin Stagner's input on whether to proceed with these breaking changes under the same command name or create a new tool.

Given Junio Hamano's earlier position against including Rust/libgit2 dependencies in the main tree, this technical hurdle may further strengthen the case for Colin's shell-based solution as the simpler in-tree option.
