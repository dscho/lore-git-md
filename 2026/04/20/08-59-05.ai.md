This is a bug report identifying a regression in Git's commit signing behavior for non-UTF-8 messages since v2.45.0. The issue causes signatures to become invalid when commit messages contain non-UTF-8 bytes and no explicit `i18n.commitEncoding` is set.

The key problem is that commit 6206089cbd changed the order of operations in `commit_tree_extended`: signature generation now happens *before* UTF-8 validation/transcoding, whereas previously it happened after. This means:
1. The signer hashes the raw (non-UTF-8) message bytes
2. Git then transcodes the message to UTF-8 before storing in the ODB
3. Verification fails because the stored UTF-8 message doesn't match what was signed

The reporter provides a detailed reproduction script showing:
- Case A (default config): signature verification fails (BAD)
- Case B (with `i18n.commitEncoding=iso-8859-1`): verification succeeds (GOOD)

The bug affects all signers (both GnuPG and non-GnuPG) and is reproducible across multiple Git versions (2.45.0 through at least 2.53.0). The workaround is to set `i18n.commitEncoding` explicitly.

This appears to be a legitimate regression introduced by the signature handling changes in 6206089cbd. The reporter has done thorough analysis including:
- Identifying the problematic commit
- Providing a containerized reproduction script
- Testing across multiple Git versions and platforms
- Verifying the workaround

The bug affects the integrity of signed commits when non-UTF-8 messages are used, which could impact users relying on commit signatures for verification. The clear reproduction steps and analysis make this a high-quality bug report that should be straightforward to address.
