This thread reports a significant regression in Git's commit signing behavior that affects users working with non-UTF-8 commit messages. Since Git v2.45.0, signatures become invalid when commit messages contain non-UTF-8 bytes unless users explicitly set `i18n.commitEncoding`. The root cause was traced to commit 6206089cbd, which changed the order of operations in signature generation - now happening before UTF-8 validation rather than after. This causes a mismatch between what gets signed (raw bytes) and what gets stored (transcoded UTF-8).

The reporter provided a thorough analysis including a containerized test case demonstrating the failure across multiple Git versions (2.45.0 through 2.53.0) and confirmed the workaround of setting `i18n.commitEncoding` resolves the issue. This affects all signing methods (both GnuPG and others) and impacts the integrity verification of signed commits, making it a potentially serious regression for users relying on commit signatures with non-ASCII messages. The clear reproduction steps and technical analysis make this a high-quality bug report that should be prioritized for fixing.
