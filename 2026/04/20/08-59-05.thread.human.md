This thread addressed a regression in commit signing for non-UTF-8 messages introduced in Git 2.45.0, where signatures would become invalid due to UTF-8 processing happening after signing rather than before. brian m. carlson fixed the issue by reordering operations in `commit_tree_extended()` and renaming a key function to better reflect its behavior (from `verify_utf8()` to `ensure_utf8()`). The solution has been confirmed to work in real-world cases by Kushal Das.

While the technical fix is complete, there was some discussion about expanding test coverage to other signing backends beyond GnuPG. brian m. carlson clarified that since the signing code is abstract at the point of the fix, the behavior should be consistent across all signing methods (SSH, X.509, etc.), making additional tests unnecessary. The thread appears to be concluding now that the core issue is resolved and the remaining questions about testing have been addressed. Users encountering this issue can expect the fix in an upcoming release, after which the workaround of setting `i18n.commitEncoding` won't be needed.
