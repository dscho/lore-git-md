This thread addresses a high-impact regression in Git versions 2.45.0 through 2.53.0 where commit signatures would become invalid for messages containing non-ASCII characters when no explicit encoding was configured. The issue stemmed from a change in operation order that caused signatures to be generated before UTF-8 validation/transcoding.

brian m. carlson submitted a two-patch series that fixes the regression by restoring the pre-2.45.0 where UTF-8 handling occurs before signing. The solution is backend-agnostic, working for all signature types (GnuPG/SSH/X.509), and includes test coverage using invalid UTF-8 bytes (0xfe and 0xff) to prevent future regressions.

Elijah Newren provided substantive review, identifying two edge cases: potential duplicate warning messages when both main and compatibility buffers contain invalid UTF-8, and a logical short-circuiting issue in the original code. brian has acknowledged these points and committed to addressing them in v2 of the patch, particularly the duplicate warnings. The core fix remains sound, with these being refinements to edge case handling.

D. Ben Knoble contributed historical context by pinpointing the exact commit (6206089cbd) that introduced the regression. The broader question about supporting unconfigured non-UTF-8 messages remains open but is now decoupled from this immediate fix. With the author actively incorporating review feedback, this regression appears on track to be fully resolved in the next patch iteration.
