The thread addresses a regression in Git's commit signing behavior for non-UTF-8 messages, introduced in v2.45.0 and affecting versions through at least 2.53.0. The issue caused signatures to become invalid when commit messages contained non-ASCII characters, as signing was happening before UTF-8 validation and transcoding. brian m. carlson has led the fix with a two-patch series.

The first patch, already merged, renamed `verify_utf8()` to `ensure_utf8()` to better reflect its behavior - this was a preparatory change that didn't alter functionality. The just-arrived second patch completes the fix by moving the UTF-8 processing before signing operations in `commit_tree_extended()`, ensuring the signed content matches what gets stored. The patch includes a test case using invalid UTF-8 bytes (0xfe and 0xff) to verify the fix and prevent future regressions.

This appears to resolve the core issue while maintaining backward compatibility. The solution restores the pre-2.45.0 where signatures remained valid for non-UTF-8 messages, though the thread had previously raised questions about whether supporting unconfigured non-UTF-8 messages should be Git's long-term position. With this fix, users can continue relying on commit signing regardless of their message encoding.
