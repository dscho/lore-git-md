This thread addressed a significant regression in Git's commit signing functionality that affected all signature types (GnuPG, SSH, X.509) when dealing with non-UTF-8 commit messages. The bug, introduced in Git 2.45.0, caused signatures to be generated before UTF-8 validation/transcoding, leading to mismatches between signed and stored content. brian m. carlson provided a two-patch fix that restores the pre-2.45.0 behavior by moving UTF-8 handling before signing operations in `commit_tree_extended()`.

Elijah Newren contributed substantive review, identifying potential edge cases around duplicate warning messages and buffer handling, though he approved the overall approach. The fix is now in place, making the previous workaround (setting `i18n.commitEncoding`) unnecessary. D. Ben Knoble's follow-up helpfully pinpointed the exact commit (6206089cbd) that introduced the regression, though this doesn't change the already-landed solution. The broader question about supporting unconfigured non-UTF-8 messages remains open but is now decoupled from this immediate fix.
