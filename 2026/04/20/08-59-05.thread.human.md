This thread addresses a significant regression in Git's commit signing functionality that affected versions 2.45.0 through 2.53.0. The core issue was that signatures were being generated before UTF-8 validation/transcoding of commit messages, causing mismatches between the signed content (raw bytes) and stored content (UTF-8 transcoded). This broke signatures for commits with non-ASCII messages when no explicit encoding was configured.

brian m. carlson has led the fix with a two-patch series. The first patch renamed `verify_utf8()` to `ensure_utf8()` to better reflect its behavior, while the second patch - now in its second version - moves the UTF-8 validation before signing operations. The latest version incorporates Elijah Newren's thorough review feedback, addressing edge cases around warning messages and buffer processing. Specifically, it now avoids duplicate warnings when both main and compatibility buffers contain invalid UTF-8 and fixes the original code's short-circuiting behavior.

The fix is backend-agnostic, working for all signature types (GnuPG/SSH/X.509), and includes a robust test case using invalid UTF-8 bytes (0xfe and 0xff) to prevent future regressions. D. Ben Knoble helped identify the exact commit (6206089cbd) that introduced the regression. With these changes, the series appears ready for merging, restoring the pre-2.45.0 behavior where signatures remain valid for non-UTF-8 messages. The broader question about supporting unconfigured non-UTF-8 messages remains open but is now been decoupled from this critical bugfix.
