Bugfix targeting commit signature validation for non-UTF-8 messages.

Kushal Das reports a regression in Git 2.45+ where commit signatures become invalid when the commit message contains non-UTF-8 bytes and no explicit `i18n.commitEncoding` is set. The issue stems from commit 6206089cbd which changed the order of operations - now the signature is computed on the raw bytes before UTF-8 validation/transcoding occurs, but the transcoded UTF-8 bytes are what get stored in the object database. This mismatch causes signature verification to fail.

The report includes a detailed reproduction script that:
1. Creates a test commit with a Latin-1 section symbol (0xA7)
2. Shows the signature is computed on the raw bytes
3. Demonstrates the stored commit contains UTF-8-transcoded bytes (0xC2 0xA7)
4. Confirms verification fails due to the byte mismatch

A workaround exists - setting `i18n.commitEncoding=iso-8859-1` prevents the UTF-8 transcoding and keeps signatures valid. The bug affects all signers (both GnuPG and non-GnuPG) and has been reproducible across multiple Git versions and platforms since 2.45.0.

This appears to be a clear regression with a well-identified root cause and thorough reproduction steps. The impact is limited to users signing non-UTF-8 commit messages without explicit encoding set, but for those cases it's a complete breakage of signature verification. The report is high quality with all the technical details needed to understand and fix the issue.
