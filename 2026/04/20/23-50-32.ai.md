This is a conceptual follow-up in the ongoing discussion about the `--reverse=before` feature for Git's revision walk. Mirko Faina responds to Junio Hamano's concerns about whether the feature should be framed as a `--reverse` variant versus a change to when count limits are applied.

Mirko argues that the current implementation approach - presenting this as an extension of `--reverse` behavior - is conceptually sound and more intuitive for users than reframing it around count limit timing. He points to existing documentation that already describes commit limiting options as being applied before ordering/formatting options like `--reverse`, suggesting the new behavior fits naturally within this mental model.

The response maintains that implementation details (how max_count interacts with reversal) should remain opaque to users, and that "choose when reversal happens relative to limiting" is clearer than trying to explain special timing rules for `--max-count` versus other limiting options. This addresses Junio's concern about conceptual coherence while defending the current design direction.

The exchange shows the discussion moving from technical implementation (settled in earlier emails) to UX design questions about how best to document and explain the feature's behavior to end users. Mirko's position suggests the v2 submission will likely retain the `--reverse=before/after` framing unless stronger arguments emerge.
