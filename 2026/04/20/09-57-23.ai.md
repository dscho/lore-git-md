This is a technical follow-up in the `contrib/subtree` discussion, where Ian Jackson identifies a significant limitation in his proposed Rust/libgit2 implementation approach. The email reveals that the metadata-based detection strategy for subtree merges (a key optimization in his prototype) cannot work as originally described because only `git-subtree add` operations leave detectable markers - `git-subtree merge` does not.

Ian acknowledges this forces a choice between:
1. Making incompatible changes to the data model (requiring migration for existing histories)
2. Creating a separate "git-subtree v2" tool with different behavior
3. Abandoning the optimization approach entirely

The email directly engages Colin Stagner (author of the competing shell-based patches) about naming and compatibility strategy, suggesting Ian is now considering his Rust version as a potential successor rather than a drop-in replacement. This moves the discussion beyond technical implementation into versioning and transition planning.

The revelation about missing merge metadata undercuts one of the Rust prototype's key advantages (efficient history traversal) and may strengthen the case for Colin's more conservative shell fixes. However, Ian's willingness to treat this as a version 2 tool rather than a strict replacement shows flexibility in finding a path forward that doesn't block improvements due to legacy constraints.

This email doesn't change Junio's earlier ruling against including the Rust version in git.git, but does surface important technical constraints that will inform whether the shell patches proceed as the only viable in-tree solution. The metadata handling issue now appears more fundamental than previously understood, affecting both implementation approaches.
