This is a follow-up in the ongoing discussion about adding a `--reverse=before` option to Git's revision walk machinery. The patch, originally proposed by Mirko Faina, would allow reversing the commit order before applying limiting options like `-n` or `--author`, rather than after as `--reverse` currently does.

In this email, Mirko responds to Junio Hamano's conceptual concerns about whether framing this as a `--reverse` variant might confuse users. Junio had suggested the behavior might be better understood as "applying count limits later" rather than a reversal timing change. Mirko argues that the current documentation already describes commit limiting as happening before ordering options, so extending `--reverse`'s behavior is conceptually consistent and more intuitive than introducing a separate mechanism for delayed limiting.

The technical implementation details were previously settled, with Jeff King providing the authoritative solution for handling multiple `--reverse` flags via an enum-based state machine. The discussion has now shifted to higher-level UX questions about how users will understand and apply the feature. Mirko maintains that the `--reverse=before/after` model aligns well with Git's existing documentation and mental model, though Junio's intervention suggests the maintainer sees potential for confusion that may need addressing before merging.
