This is the second patch in brian m. carlson's series fixing a commit signing regression for non-UTF-8 messages introduced in Git 2.45.0. The patch addresses the core issue where signatures were being created before UTF-8 validation/transcoding, causing verification failures when messages contained non-UTF-8 bytes.

The fix moves the `ensure_utf8()` call before signing operations in `commit_tree_extended()`, ensuring the signed content matches what gets stored in the commit object. The patch adds a test case using invalid UTF-8 bytes (0xfe and 0xff) to verify the fix works for problematic encodings. This completes the solution started in the first patch (which renamed the function for clarity).

The change is straightforward but important - it restores the pre-2.45.0 behavior where signatures remain valid even when commit messages contain non-UTF-8 characters. The test case provides regression protection against similar issues in the future. This appears to be the final piece needed to resolve the reported regression, following the preparatory API clarification in the first patch.
