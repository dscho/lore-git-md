Thread identity: Commit signing regression for non-UTF-8 messages since v2.45.0, caused by operation order change in `commit_tree_extended`. Originating author brian m. carlson, patch series addressing a high-impact bug affecting all signature types across Git 2.45.0 through at least 2.53.0.

Core problem: Signatures were generated before UTF-8 validation/transcoding, causing mismatch between signed content (raw bytes) and stored content (UTF-8 transcoded). Affects signed commits with non-ASCII messages when no explicit encoding is configured.

Current status: brian m. carlson's two-patch series has landed with the regression fixed by moving `ensure_utf8()` before signing operations in `commit_tree_extended()`. The v2 patch incorporates Elijah Newren's review feedback by: 1) eliminating duplicate UTF-8 warning messages when both main and compatibility buffers contain invalid UTF-8, 2) fixing the original code's logical short-circuiting that caused only the first invalid buffer to be processed. The test case using invalid UTF-8 bytes (0xfe and 0xff) provides regression protection. The fix is backend-agnostic (GnuPG/SSH/X.509) and restores pre-2.45.0 behavior where signatures remain valid for non-UTF-8 messages.

Key technical details: First patch renamed `verify_utf8()` to `ensure_utf8()` in `commit.c` to better reflect behavior (validation plus transcoding). Second patch reorders operations in `commit_tree_extended()` to ensure UTF-8 validation happens before signing. Files affected: `commit.c` (signing and UTF-8 handling), `gpg-interface.c` (signature verification). Test coverage verifies handling of invalid UTF-8 bytes (0xfe and 0xff).
