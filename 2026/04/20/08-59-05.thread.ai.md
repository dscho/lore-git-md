Thread identity: Two-patch bugfix series by brian m. carlson fixing a commit-signing regression introduced in Git v2.45.0 and present through at least v2.53.0. The regression caused signatures to be computed over pre-UTF-8-transcoding content, rendering signed commits with non-ASCII messages unverifiable if no `i18n.commitEncoding` was configured.

Current status: Junio C Hamano acknowledged the final (v2) round and has queued the series for `next` integration branch. All review feedback from the previous round has been incorporated and no further changes are expected. The fix covers all signing backends (GnuPG, SSH, X.509).

Key technical details:
- `commit.c`: Function `verify_utf8()` renamed to `ensure_utf8()` (first patch) to more accurately describe its effect (validation plus transcoding to UTF-8).
- `commit.c`: In `commit_tree_extended()`, operation order changed so that `ensure_utf8()` runs before `sign_commit_and_label()` (second patch). This ensures the content that gets signed is the same content that gets stored.
- `gpg-interface.c`: Signature verification code touched by the broader change area.
- Also fixed: a latent logical short-circuit bug in the original code (`&&` evaluation) that caused only the main buffer's UTF-8 validity to be checked; the compatibility buffer check was skipped if the main buffer was invalid. The fix ensures both buffers are independently validated.
- Test: Adds regression protection using bytes 0xfe and 0xff, which are never valid as UTF-8 bytes even in multi-byte sequences.

Open questions: None remaining. The previously open question about supporting unconfigured non-UTF-8 commit messages in general is explicitly decoupled from this fix and remains an open topic for separate future work, unrelated to the signing regression.
