Commit signing regression for non-UTF-8 messages since v2.45.0, caused by commit 6206089cbd changing operation order in `commit_tree_extended`. Signatures were generated before UTF-8 validation/transcoding, causing mismatch between signed content (raw bytes) and stored content (UTF-8 transcoded). Affects all signature types across Git 2.45.0 through at least 2.53.0. High impact on signed commits with non-ASCII messages.

brian m. carlson addressed the issue with a two-patch series. First patch renamed `verify_utf8()` to `ensure_utf8()` to accurately reflect its behavior (validation plus possible transcoding), touching only the function name and call sites in `commit.c`. Second patch (now landed) fixes the core issue by moving `ensure_utf8()` before signing operations in `commit_tree_extended()`, ensuring signed content matches stored content. Added test case using invalid UTF-8 bytes (0xfe and 0xff) provides regression protection.

The solution restores pre-2.45.0 behavior where signatures remain valid for non-UTF-8 messages. While the technical fix is complete, open questions remain about whether unconfigured non-UTF-8 messages should be supported at all. Current workaround (setting `i18n.commitEncoding`) is no longer needed once this fix lands in a release.

Key technical details: Issue manifested when commit messages contained non-UTF-8 bytes without explicit encoding configuration. Signature was generated on raw bytes before UTF-8 processing but verified after transcoding. Affected files: `commit.c` (signing and UTF-8 handling), `gpg-interface.c` (signature verification). Test coverage now includes invalid UTF-8 byte sequences.
