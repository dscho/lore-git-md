Commit signing regression for non-UTF-8 messages since v2.45.0. The bug causes invalid signatures when commit messages contain non-UTF-8 bytes without explicit `i18n.commitEncoding` configuration. Root cause is commit 6206089cbd changing the operation order in `commit_tree_extended`: signatures are now generated before UTF-8 validation/transcoding, causing a mismatch between signed content (raw bytes) and stored content (UTF-8 transcoded). Affects all signature types (GnuPG and others) across Git 2.45.0 through at least 2.53.0. Current workaround is setting `i18n.commitEncoding`. High impact on users relying on signed commits with non-ASCII messages. Reporter provided detailed reproduction showing failure case (default config) and working case (with explicit encoding). Analysis identifies the exact regression point and demonstrates cross-version reproducibility. This is a clear regression in signature integrity that needs fixing.
