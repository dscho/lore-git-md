Thread identity: Commit signing regression for non-UTF-8 messages since v2.45.0, caused by operation order change in `commit_tree_extended`. Originating author brian m. carlson, patch series addressing a high-impact bug affecting all signature types across Git 2.45.0 through at least 2.53.0.

Core problem: Signatures were generated before UTF-8 validation/transcoding, causing mismatch between signed content (raw bytes) and stored content (UTF-8 transcoded). Affects signed commits with non-ASCII messages when no explicit encoding is configured.

Current status: brian m. carlson's two-patch series has landed, with the second patch moving `ensure_utf8()` before signing operations in `commit_tree_extended()`. Fix is backend-agnostic (GnuPG/SSH/X.509). Test case using invalid UTF-8 bytes (0xfe and 0xff) provides regression protection.

Key technical details: First patch renamed `verify_utf8()` to `ensure_utf8()` in `commit.c` to better reflect behavior (validation plus transcoding). Second patch restores pre-2.45.0 behavior where signatures remain valid for non-UTF-8 messages. Elijah Newren identified two potential issues in implementation: possible duplicate UTF-8 warning messages when both main and compatibility buffers contain invalid UTF-8, and notes the original code had logical short-circuiting behavior that the patch fixes by handling buffers separately. Files affected: `commit.c` (signing and UTF-8 handling), `gpg-interface.c` (signature verification).

Open questions: Whether to refine warning message behavior to avoid duplicates (Elijah's observation). Broader question about supporting unconfigured non-UTF-8 messages remains unresolved but is now separate from the immediate fix. Kushal Das's suggestion for expanded test coverage for non-GnuPG tools was considered but deemed unnecessary due to the fix's abstraction.

Participant positions: brian m. carlson implemented the fix and maintains the solution is complete.
