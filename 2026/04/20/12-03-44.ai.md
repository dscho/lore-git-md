This is a follow-up discussion in the ongoing thread about Patrick Steinhardt's proposal to reorganize Git source code by moving libgit.a components into a "lib/" directory. Derrick Stolee raises several practical considerations about the impact of such a large-scale refactoring.

Stolee acknowledges the benefits of reducing the root directory clutter but highlights two major disruption vectors: (1) potential conflicts with in-flight patch series that would need special handling during merge, and (2) challenges for long-lived forks like GitHub's, Git for Windows, and Microsoft's Git forks when rebasing onto the new structure. He suggests timing the change immediately after a major release (like v2.54.0) to minimize merge pain for downstreams.

The email also explores whether the reorganization could go further by moving root-level command implementations (git.c, git-*.c) into a dedicated directory like "cmd/". Stolee suggests considering such a move now if deemed valuable, to avoid needing multiple disruptive reorgs. His tone is constructive but cautious, emphasizing the need to carefully manage the transition for both core contributors and downstream consumers.

The discussion moves the thread from design consensus (already established) into practical execution planning, with Stolee's comments reflecting his experience maintaining large forks and considering the broader ecosystem impact. No new technical objections are raised to the core proposal, but the email surfaces important logistical considerations that would need addressing before merging.
