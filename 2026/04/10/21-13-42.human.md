This is a maintainer process discussion sparked by the Rust-by-default build system changes. Junio C Hamano reflects on Git's development cycle in light of the timing debate around enabling Rust support by default.

The email questions whether the current release process adequately handles high-impact changes like the Rust integration. Junio notes that the current model - where all topics merge to 'next' at roughly the same pace regardless of impact - may not provide enough time for community testing of architectural changes. He suggests potentially restructuring the cycle to identify high-impact changes earlier and give them more bake time before release.

The proposal would split the cycle into two tracks: high-impact changes would need to land by an early '-rc0' (around week 3-4), while smaller changes could continue until the traditional '-rc1' cutoff. This would give the community more time to test disruptive changes while maintaining the current flow for routine patches.

This is not a concrete plan but rather a thought experiment from the maintainer about how to better handle major transitions like Rust integration. The discussion remains open-ended, with Junio explicitly stating uncertainty about whether this would actually improve the process. The email serves more to surface the tension between rapid iteration and stability than to propose a specific solution.
