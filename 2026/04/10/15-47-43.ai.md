This is a clarification from Junio Hamano about header inclusion policy in Git's C code, specifically addressing Lorenzo Pegorari's question about whether to explicitly include headers like `strmap.h` and `strbuf.h` in the promisor file repack series.

Junio confirms that the CodingGuidelines do indeed require direct inclusion of headers for any types or functions used, even if they might be transitively included through other headers. He explains that while some files (like `strbuf.h`) are so commonly included that builds may work without explicit inclusion, this is an implementation detail that shouldn't be relied upon. The guideline exists because future changes to header dependencies could break code that doesn't directly include its dependencies.

The response provides important context about Git's header inclusion philosophy - it's better to be explicit even when things appear to work implicitly. This helps future-proof the code against changes in header relationships. Junio's explanation makes clear this isn't just about current functionality but about maintaining long-term build stability.
