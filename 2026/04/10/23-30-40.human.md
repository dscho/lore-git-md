This is a bugfix targeting promisor packfile handling during repacks, part of Lorenzo Pegorari's GSoC work. Junio C Hamano has identified a memory leak in the `copy_promisor_content()` helper function introduced in patch 2/6 of the series.

The issue stems from using `parse_pack_index()` to read packfiles without properly handling its return value or cleaning up the allocated `packed_git` struct. While `close_pack_index()` unmaps the index data, it doesn't free the struct itself, leading to a 285-byte leak per invocation. Junio questions whether this low-level API is even the right approach, noting the function's warning that callers likely want `add_packed_git()` instead.

The discussion reveals deeper questions about packfile handling - the code needs to verify object presence in specific packfiles rather than just checking the object store generally. Patrick Steinhardt is CC'd as the recent refactoring of this area makes him the expert on current best practices.

This represents the last remaining issue in an otherwise polished series that has addressed all previous feedback around timestamp handling, header includes, and test coverage. The fix will likely involve either proper cleanup of the `packed_git` struct or switching to a more appropriate API for packfile inspection.
