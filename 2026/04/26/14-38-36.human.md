Security hardening patch changing default bare repository behavior when built with breaking changes. This is the final patch in Johannes Schindelin's 8-part series that makes `safe.bareRepository` default to "explicit" (rather than "all") when Git is compiled with `WITH_BREAKING_CHANGES`. The change prevents Git from automatically discovering bare repositories when walking directory trees, requiring explicit `--git-dir` or `GIT_DIR` specification instead.

The patch implements the core behavior change after the previous 7 patches prepared the test infrastructure. It includes:
- Documentation updates explaining the security rationale and migration path
- Code change to make "explicit" the default when `WITH_BREAKING_CHANGES` is set
- Test updates to verify the new default behavior

The security motivation is clear: this prevents attacks where malicious bare repositories with hooks could be triggered simply by entering a directory, even without running Git commands directly (since some shells run `git status` automatically). The change is carefully staged behind the breaking changes flag to avoid disrupting existing workflows in standard builds.

Users who rely on implicit bare repo discovery can maintain the old behavior by setting `safe.bareRepository=all` in their config. The patch shows thoughtful attention to edge cases, including a test fix that avoids repository discovery during cleanup by using direct config file access.

This completes a well-structured series that balances security hardening with backwards compatibility, positioning the change for Git 3.0 while maintaining current behavior in 2.x releases. The thorough test preparation in earlier patches suggests this is ready for consideration, though integration testing with other in-flight topics may still be needed.
