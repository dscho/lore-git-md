Feature patch discussion about preserving change-id headers during commit rewriting operations, with Junio Hamano weighing in on the philosophical divide.

This thread continues the debate about whether Git should preserve 'change-id' headers (used by tools like Gerrit) during operations like rebase and cherry-pick. Nico Williams has proposed making the behavior configurable, suggesting upstream repositories could define default rules that most contributors would follow. Junio Hamano responds that while Nico's approach is sensible for project-specific validation, he maintains that this metadata belongs in commit trailers (like Signed-off-by) rather than commit headers.

Junio makes two key points: first, that project validation of commit metadata (whether change-ids or Signed-off-by) can and should happen regardless of where the information is stored, and second, that trailers are preferable to headers because they're more visible in `git log` output. The discussion remains at a philosophical level about Git's role in supporting external tools' metadata needs, with no resolution yet on the concrete scenarios Phillip Wood raised earlier about how different operations (cherry-picks, splitting, squashing) should handle these headers.

The exchange highlights the tension between Nico's tool-friendly configuration approach and Junio's preference for keeping Git's core simple while pushing tool-specific needs to established extension points like trailers. While both positions have merit, the lack of progress on Phillip's test cases suggests the discussion needs more concrete examples of how these approaches would handle real-world rewriting scenarios before consensus can emerge.
