This thread explores how Git should handle 'change-id' headers during commit rewriting operations like rebase, cherry-pick, and amend. These headers are used by external tools like Gerrit, GitButler, and Jujutsu to track changes across operations where Git would normally drop them. Nico Williams has proposed a configurable approach with operation-specific defaults and hooks for custom header transformation, but maintainer Junio Hamano and contributor Phillip Wood have raised fundamental concerns about the semantic consistency of such an approach.

Phillip Wood's latest intervention shifts the discussion from implementation details to core behavioral questions. He identifies three critical scenarios that need clear contracts: cherry-picks (whether to copy headers), commit splitting (handling headers when one commit becomes multiple), and squashing (consolidating headers when multiple commits become one). For splitting, he outlines options ranging from generating all new IDs to letting users specify inheritance. For squashing, he questions whether to preserve original IDs or generate new ones. These concerns reinforce Junio's earlier skepticism about whether configurable solutions can provide the consistency external tools would need.

The discussion remains in design phase, with technical implementation taking a backseat to more fundamental questions about Git's role in supporting external workflows. While Nico's proposal represents progress in accommodating diverse tooling needs, Phillip and Junio's interventions suggest the community may need to reach consensus on behavioral expectations before any implementation can move forward. The thread highlights that what initially appeared as a technical challenge may actually be a design philosophy question about how tightly Git should couple itself to external tools' metadata needs.
