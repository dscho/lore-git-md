This thread explores how Git should handle change-id headers during commit rewriting (rebase, cherry-pick, amend) - metadata that tools like Gerrit, GitButler and Jujutsu rely on but which Git currently drops. The discussion has evolved from a technical debate into a philosophical one about Git's boundaries with external tools.

Nico Williams advocates for configurable core handling with project-defined policies, proposing a concrete design where hooks would transform change-ids during operations. Junio Hamano prefers keeping metadata in commit message trailers rather than headers, citing better log visibility, but acknowledges the need for configuration. While their approaches differ, both now seem aligned on some form of policy-based solution, with Nico's latest email offering a potential middle ground through standardized hooks.

Phillip Wood's three key scenarios (cherry-picks, splitting, squashing) remain the technical framework neither approach has yet fully addressed. The discussion now hinges on whether the community will accept Nico's policy/hook approach as sufficiently lightweight, or if Junio's trailer-based solution can meet tooling requirements. While consensus appears closer, the fundamental question of how deeply Git should integrate with external workflows remains unresolved.
