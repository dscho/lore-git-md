This thread explores how Git should handle 'change-id' headers during commit rewriting operations like rebase, cherry-pick, and amend. These headers are used by tools like Gerrit, GitButler, and Jujutsu to track commits across modifications, but Git currently drops them. The original patch proposed simply preserving any existing change-id header regardless of format, prompting concerns from maintainer Junio Hamano about whether this approach considers all semantic implications and edge cases.

Nico Williams has now responded with a more nuanced proposal that addresses some of Junio's concerns. Rather than blanket preservation, Nico suggests configurable options to control when headers are preserved or dropped, plus a new `original-change-id` header to track commit lineage when the main ID might legitimately change. This acknowledges that different tools and workflows may need different behaviors, and that some operations might warrant generating new IDs while preserving the original for reference.

The discussion has shifted from implementation details to broader design questions about Git's role in change-id handling. Junio remains skeptical about whether there's real consensus on the value of this feature, while contributors are trying to find solutions that meet tooling needs without baking in assumptions. Key unresolved questions include how to handle complex cases like commit operations that split changes, and whether Git should establish standards around change-id formats rather than being completely agnostic. The thread remains active with no clear resolution yet.
