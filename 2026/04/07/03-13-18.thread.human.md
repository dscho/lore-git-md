This thread continues the debate about how Git should handle 'change-id' headers during commit rewriting operations like rebase and cherry-pick - metadata that tools like Gerrit, GitButler, and Jujutsu rely on. The discussion has crystallized into two competing visions: Nico Williams advocates for configurable core handling where upstream projects could define default rules, while Junio Hamano prefers keeping such metadata in commit message trailers rather than commit headers, maintaining Git's traditional workflow neutrality.

In the latest exchange, Junio acknowledges Nico's upstream-defaults proposal as sensible (comparing it to Signed-off-by enforcement) but reiterates his trailer-based alternative. He raises a practical concern that headers like 'encoding' aren't visible in normal `git log` output, making validation harder. Phillip Wood's three key test scenarios (covering cherry-picks, commit splitting, and squashing) remain the unresolved technical crux that neither approach has yet addressed in detail.

The philosophical divide persists: should Git adapt to support external tools' needs through core changes, or maintain its neutral stance by keeping tool-specific metadata separate? Junio's repeated emphasis on trailers suggests this may become the preferred direction unless stronger use cases emerge for integrated header handling. The discussion now awaits either concrete analysis of how each approach would handle Phillip's scenarios or broader community input on Git's appropriate integration boundaries.
