Thread identity: Feature patch to preserve 'change-id' header during rebase, cherry-pick, and amend operations, with Nico Williams, Junio Hamano, and Phillip Wood as key participants in design discussion. Thread connects to needs of Gerrit, GitButler and Jujutsu.

Core problem: Git currently drops change-id headers used by external tools during commit rewriting operations. Discussion has evolved from implementation details to fundamental questions about header semantics and Git's role in supporting external workflows. Phillip Wood's latest intervention crystallizes three critical behavioral scenarios needing clear contracts: cherry-picks (header copying), commit splitting (header inheritance), and squashing (header consolidation).

Current status: Design phase focused on semantic contracts before implementation. Nico Williams' configurable approach (operation-specific defaults and hooks) remains on table but faces reinforced skepticism from both Phillip Wood and Junio Hamano about whether configuration solves the underlying semantic consistency problems.

Key technical details:
- Proposal includes per-operation configuration for header handling (copy/drop)
- Introduces hooks for custom header transformation during complex operations
- Adds `original-change-id` header concept for lineage tracking
- Phillip Wood identifies three key scenarios needing behavioral contracts:
  1. Cherry-picks: whether/when to copy headers between repositories
  2. Commit splitting: handling when one commit becomes multiple (options: new IDs for all, original ID plus new ones, user-specified inheritance)
  3. Squashing: handling when multiple commits become one (preserve all original IDs vs generate new one)
- Default behaviors would differ by operation type (e.g. preserve in rebase but not cherry-pick)
- Current implementation doesn't fully handle edited commit scenarios

Open questions:
- Whether configurable approach resolves semantic consistency concerns (Phillip Wood and Junio Hamano remain skeptical)
- How to establish clear contracts for the three critical scenarios Phillip identified
- If hook-based customization introduces more complexity than value given core semantic uncertainties
- Git's philosophical stance toward external tool integration remains contested
- Whether operation-specific defaults can satisfy diverse tooling needs without causing workflow divergence
- How `original-change-id` interacts with existing change-id headers in edge cases

Participant positions:
- Nico Williams continues advocating for configurable approach as middle ground
- Junio Hamano maintains skepticism about design foundations
- Phillip Wood shifts focus to semantic contracts, arguing implementation is secondary to defining expected behaviors
- Thread shows technical progress in identifying key scenarios but core philosophical disagreement persists
