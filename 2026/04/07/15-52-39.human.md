This is a continuation of the discussion about preserving 'change-id' headers during commit rewriting operations like rebase and cherry-pick. Nico Williams responds to Phillip Wood's concerns about configurable header preservation semantics by clarifying his vision for site-wide defaults that could be enforced by upstream repositories.

Nico suggests that while individual users could override the default configuration, upstream projects could establish and verify compliance with their preferred change-id handling rules. This addresses Phillip's concern about inconsistent semantics by proposing a model where projects define the expected behavior rather than leaving it to individual user preferences.

The exchange highlights the ongoing tension between flexibility and consistency in this feature design. Nico maintains that configurable behavior with project-level defaults is viable, while Phillip (and earlier Junio) have expressed skepticism about whether this approach can provide the semantic stability that tools like Gerrit and Jujutsu require. The discussion remains at an impasse regarding whether Git's core should handle this metadata or whether an alternative like notes/trailers would be more appropriate.
