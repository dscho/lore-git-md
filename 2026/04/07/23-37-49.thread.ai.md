Thread identity: Test failure report for t5401.13 ("pre-receive hook that forgets to read its input") in Git 2.54.0-rc0, reported by Randall Becker (NonStop port maintainer) with technical analysis from Jeff King (Peff).

Core problem: A regression in pre-receive hook behavior where hooks that exit successfully (status 0) without reading their input incorrectly reject all pushed references. The test creates 900 branches and pushes them to a repository with such a hook, expecting the push to succeed but instead seeing all branches rejected with "remote rejected" messages.

Current status: Jeff King identified the root cause as a race condition in signal handling during parallel process execution, specifically in SIGPIPE handling within `run_processes_parallel()`. He has now demonstrated the issue also affects parallel hook execution scenarios, though this feature isn't in 2.54.0. The proposed fix reorders signal handler installation to ensure SIG_IGN takes precedence over child cleanup handlers, which addresses both the original NonStop case and parallel execution scenarios.

Key technical details: The bug occurs in run-command.c's `run_processes_parallel()` where:
1. Initial SIGPIPE handling (SIG_IGN) gets overridden by child cleanup handlers
2. This creates a race condition in signal propagation to child processes
3. The issue manifests differently across platforms - NonStop shows it readily while Linux only shows it in parallel execution
4. New test case demonstrates the race can incorrectly terminate slow hooks when fast hooks exit without reading input
The fix ensures consistent SIGPIPE handling regardless of execution mode or platform.

Open questions: Whether the fix resolves Randall's original test case on NonStop systems (Peff is awaiting confirmation). The analysis suggests no additional edge cases remain beyond what the current fix addresses.

Participant positions: 
- Randall Becker originally reported the issue during rc testing
- Jeff King diagnosed the root cause, proposed the fix, and has now extended the analysis to parallel execution scenarios
- The issue is confirmed as general hook execution infrastructure bug rather than platform-specific

Related work: While this touches the hook subsystem (which Adrian Ratiu is working on for configurable hooks), the issue appears unrelated to those changes and stems from deeper process handling logic. The fix would affect all platforms' hook execution behavior.
