This is a follow-up discussion about the ongoing proposal to preserve 'change-id' headers during commit rewriting operations. Junio C Hamano, the Git maintainer, expresses skepticism about the claimed consensus around change IDs, noting that while multiple people want them, they may have different semantic expectations.

Junio raises important questions that weren't addressed in the initial patch - particularly around the meaning and inheritance rules for change IDs during operations like commit splitting. He points out that different operations (rebase vs cherry-pick) currently handle note propagation differently, suggesting similar inconsistencies could arise with change IDs.

The exchange highlights that while the technical implementation of header preservation may be sound, there are unresolved design questions about the feature's behavior in edge cases. Junio's response indicates this may need more discussion before being ready for inclusion, particularly around establishing clear semantics rather than just preserving the header mechanically.

This moves the thread from a straightforward feature proposal into more fundamental design discussion territory. The patch author will likely need to address these semantic questions in a revised submission.
