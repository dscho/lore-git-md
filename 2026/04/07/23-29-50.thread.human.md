This thread addresses a regression in Git 2.54.0-rc1 where `writev()` optimizations in network operations fail on NonStop platforms due to hardware-imposed limits on vectorized writes. The core issue stems from NonStop's SSIZE_MAX being smaller than Git's 64k packet-line maximum, causing EINVAL errors. Initial discussion established that while the `NO_WRITEV=Nope` workaround works, a more robust solution was needed.

Patrick Steinhardt proposed an `xwritev()` implementation that splits large writes while preserving optimization benefits, which gained support after technical validation. However, Randall Becker (NonStop maintainer) has now raised a critical constraint: Patrick's solution must not modify `MAX_IO_SIZE` in `git-compat-util.h`, as this would break existing `xwrite()` functionality that NonStop relies on. Randall isn't rejecting the approach but emphasizes preserving this long-verified platform mechanism.

The thread shows consensus forming around Patrick's runtime fallback solution, now with clearer implementation boundaries. Key participants include Jeff King (who confirmed the root cause), Junio Hamano (questioning optimization value), and brian m. carlson (noting Rust would inherit similar limits). With Randall's latest input, the path forward appears to be adapting Patrick's `xwritev()` to work within existing platform constants while still solving the regression.
