This thread addresses a regression in Git 2.54.0-rc1 affecting NonStop systems, where `writev()` optimizations in network operations fail due to platform-specific limitations (SSIZE_MAX being smaller than Git's 64k packet-line maximum). The issue was first reported by Randall S. Becker, with key technical analysis from Jeff King, Junio Hamano, and others.

The current state shows convergence around two solution paths: Patrick Steinhardt's proposed `xwritev()` implementation that splits large writes while preserving optimization benefits, and a `NO_WRITEV` workaround that's already been successfully tested in production. A critical constraint emerged that `MAX_IO_SIZE` must remain unchanged to preserve existing functionality on NonStop systems.

Jeff King's latest contribution suggests a more comprehensive approach: auto-detecting SSIZE_MAX limitations at compile time by moving MAX_IO_SIZE definition to compat/posix.h and automatically disabling writev() when platform constraints would prevent it from working with Git's packet-line protocol. While architecturally cleaner, Jeff acknowledges this solution may be too involved for the current release cycle, alternatively proposing a temporary `NO_WRITEV` flag for NonStop in config.mak.uname.

Key participants remain engaged: Patrick favors his runtime solution, Randall has validated the workaround, Junio leans toward reliability over optimization, and brian m. carlson has provided POSIX context. The discussion now balances the need for a proper architectural fix against release timeline pressures, with Jeff offering both short-term and long-term paths forward.
