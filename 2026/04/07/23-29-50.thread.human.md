The thread began with Randall S. Becker reporting test failures in Git 2.54.0-rc1 on NonStop systems, tracing them to limitations in the `writev()` system call. Jeff King confirmed the root cause: NonStop's 32-bit environment has an SSIZE_MAX limit of 52KB, which conflicts with Git's packet-line protocol assuming 64KB maximums. A workaround (`NO_WRITEV=Nope`) was quickly validated in production CI environments.

Junio Hamano has since deepened the technical analysis, recognizing this as more than just a NonStop issue. While the code handles short writes through `writev_in_full()`, it can't solve the fundamental SSIZE_MAX limitation. Junio notes a key architectural tension: Git's protocol design assumes certain buffer sizes that some platforms can't support, and while `write_in_full()` can split large writes, doing so for vectorized writes would defeat the optimization's purpose.

The discussion has evolved from an immediate compatibility fix to questioning the value of the `writev()` optimization itself. Jeff King and Junio both express skepticism about whether the performance gains justify the complexity and platform constraints. The workaround provides a short-term solution, but the thread now grapples with whether to keep the optimization at all or revert to simpler `write()` calls, trading some performance for broader compatibility. This decision will affect not just NonStop but any platform with similar size limitations.
