This is a feature proposal for configurable change-id header preservation during commit rewriting operations, continuing a discussion about how Git should handle these headers used by tools like Gerrit and Jujutsu.

Nico Williams responds to Junio Hamano's skepticism about the claimed consensus around change-id headers by proposing a middle ground. Rather than hardcoding behavior, he suggests making header preservation configurable per operation (rebase, cherry-pick, etc.) with different defaults for each, and introducing hooks to allow custom transformation logic when commits are split or modified. The approach would treat the header values as opaque strings while still providing the basic functionality external tools need.

The proposal attempts to address Junio's concerns about semantic ambiguity by pushing interpretation to site-specific configuration rather than baking it into Git. However, it introduces new complexity with the hooks system and doesn't fully resolve the fundamental questions about how change-ids should behave across operations like commit splitting. The thread shows movement toward compromise but the core tension between Git's design principles and external tooling needs remains unresolved.
