This is a bugfix follow-up in Lorenzo Pegorari's series on promisor file handling during repacks, addressing portability and implementation issues. Junio Hamano points out two specific problems with the current approach to timestamp handling in patch 2/5:

1. The use of `localtime_r()` with a comma operator is not just a typo but actually breaks the macOS build, as shown in the CI failure. This needs to be fixed for cross-platform compatibility.

2. More fundamentally, Junio questions the design choice of storing timestamps in human-readable format ("%Y/MM/DD-HH:MM:SS") rather than simply recording the Unix epoch time as an integer. He suggests this would be both simpler and less prone to errors, especially since the current approach doesn't record timezone information.

This feedback builds on earlier reviews from Tian Yuchen that identified a memory leak and syntax error in the same code section. While those were straightforward fixes, Junio's comments go deeper into the architectural decision about how to represent time information in the promisor files. The thread shows the patch progressing through increasingly detailed review stages, from basic correctness to design-level evaluation.

The exchange highlights Git's cross-platform requirements (the macOS build breakage) and the maintainer's preference for simple, robust solutions over potentially fragile text formatting. This suggests the next version will need to reconsider the timestamp storage approach while maintaining the core functionality of tracking packfile relationships during repacks.
