This is a continuation of the design discussion about preserving 'change-id' headers during commit rewriting operations, with Junio Hamano responding to Nico Williams' proposal for configurable header preservation behavior. The thread remains focused on how Git should handle metadata used by external tools like Gerrit and Jujutsu.

Junio reinforces his position that Git should not special-case change-id headers in core operations, suggesting instead that Git's existing notes/trailers mechanism could be extended to meet the same needs. He draws a key distinction between rebase (a rewriting operation where the old history is discarded) and cherry-pick (a duplication operation where both old and new commits remain), arguing this justifies allowing them to behave differently with respect to metadata propagation.

The email highlights two competing approaches: Nico's preference for configurable core handling versus Junio's advocacy for keeping metadata separate via notes/trailers. Junio suggests the trailers mechanism, while currently limited, provides a more Git-native framework that could be extended without special-casing specific headers. This maintains Git's traditional neutrality toward workflow tools while still allowing projects to define their own metadata semantics.

The discussion remains at a philosophical level about Git's appropriate role in supporting external workflows, with Junio's position representing a more conservative approach that would require tooling changes rather than core Git modifications. The three key scenarios identified earlier by Phillip Wood (cherry-picks, commit splitting, and squashing) remain the technical framework any solution must address, though this email does not delve into those specifics.
