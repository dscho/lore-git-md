This is a follow-up discussion in the ongoing thread about preserving 'change-id' headers during commit rewriting operations like rebase and cherry-pick. The original patch proposed preserving these headers as-is, but maintainer Junio C Hamano raised concerns about the semantic implications and whether there was sufficient consensus on the approach.

Nico Williams now suggests two additional ideas in response to Junio's concerns: (1) making the header preservation behavior configurable per-operation (e.g. different rules for rebase vs cherry-pick), and (2) introducing an `original-change-id` header that could track relationships between commits even when their change-ids diverge. 

The discussion appears to be shifting from a simple implementation question to a broader design exploration of how Git should handle these metadata fields. Nico's suggestions indicate they're thinking about more flexible solutions that could accommodate different workflows while maintaining traceability. However, the thread still lacks clear consensus on whether this functionality belongs in core Git at all, or if it should be handled by external tools. 

The exchange remains productive but unresolved, with Junio's earlier skepticism suggesting this may need more design discussion before proceeding with any implementation. The new proposals attempt to address the maintainer's concerns about semantic consistency across operations, but it's unclear if they'll satisfy the deeper questions about whether this belongs in Git's core functionality.
