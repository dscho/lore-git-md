This is a technical discussion about header organization in the reftable portability series, specifically addressing the platform-specific and project-specific abstraction layers. Junio C Hamano responds to Patrick Steinhardt's explanation of the current header structure, which splits reftable interfaces into internal ("reftable/foo.h") and external ("reftable/reftable-foo.h") API surfaces.

Junio clarifies his position on the architectural division of labor, proposing three clear layers: 1) a platform/project-specific implementation file (reftable/system.c), 2) a neutral interface declaration (reftable/system.h), and 3) a platform-specific shim header (reftable-system.h) to provide common definitions. While initially finding the naming confusing, he now sees this as a sound structure.

However, Junio notes the current code doesn't fully honor this division - platform-specific elements like MINGW support and project-specific items like `inline` definitions and zlib compatibility still appear in the wrong layers. His feedback maintains the thread's focus on architectural purity while acknowledging the practical challenges of clean abstraction boundaries. The exchange shows progress toward consensus on the header organization approach, with Junio now providing more concrete guidance about where various components should live in the layered design.
