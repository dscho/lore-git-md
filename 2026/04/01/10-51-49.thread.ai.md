Thread identity: Bug report about hash algorithm mismatch when cloning empty repositories, originally reported by Miljan Mitrovic, with follow-up from Patrick Steinhardt.

Core problem: When cloning an empty SHA256 remote repository, Git would incorrectly create a local SHA1 repository, silently creating an incompatible local/remote pair. This became problematic when pushing commits back to the remote. The root cause was missing hash algorithm propagation during empty repository cloning, despite it being a fundamental repository property that cannot be changed after creation.

Current status: Patrick Steinhardt confirms this was a known bug fixed in Git v2.41 through the introduction of an "object-format" capability. The fix requires both client and server to run Git v2.41 or later for proper capability negotiation during clone operations.

Key technical details: The solution involved protocol-level changes - the new "object-format" capability allows the server to announce its object format during the clone handshake, preventing the client from defaulting to SHA1 when the remote is SHA256. This specifically addresses the empty repository case where the hash algorithm wasn't properly propagated before.

Open questions: None remaining - the issue has been resolved through proper protocol support. The response serves as documentation for others encountering similar behavior, with the clear solution being to upgrade to Git v2.41+.

Participant positions: Miljan Mitrovic originally reported the issue with clear reproduction steps. Patrick Steinhardt provided the authoritative response confirming the fix, explaining the technical solution (protocol capability), and noting the version requirements for the fix to take effect.

Related work: This connects to broader SHA-256 support and repository initialization work, with the specific empty-repo case now properly handled through protocol capabilities introduced in Git v2.41. The fix represents a deliberate protocol enhancement rather than a quick workaround.
