This is a follow-up in the fsmonitor series addressing Junio's concerns about the split-index interaction fixes. Paul Tarjan provides detailed technical context about why the current approach is safe, while remaining open to alternative solutions.

Paul explains that the callback's purpose is to clear CE_FSMONITOR_VALID on entries, and that the guard condition (positions beyond cache_nr) should only trigger if entries were removed between write and read. He notes the call sequence in read_index_from() ensures cache_nr represents the full merged size by the time tweak_fsmonitor() runs. Even if marking were missed, refresh_fsmonitor() provides a fallback path by re-querying the daemon.

The response clarifies two key points: first, that the bitmap positions are written against the full merged index but read before merge, making out-of-bounds positions legitimate during the read phase. Second, that the existing !istate->split_index guard in the write path already acknowledges this split-index behavior.

Paul remains flexible, offering to revert to Derrick Stolee's original test-side approach if Junio prefers keeping the BUG() assertion. He also agrees with deferring tighter split-index invariants to a future focused series, and notes he's moved this commit to 1/13 for better bisectability as previously suggested.
