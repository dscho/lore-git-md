This is a technical discussion about header organization in the reftable portability series, specifically addressing Junio C Hamano's concerns about architectural boundaries between platform-specific and Git-specific code.

Patrick Steinhardt responds to Junio's review of patch 6/6, which introduced "reftable-system.h" to consolidate system headers. He acknowledges the current split between internal ("reftable/foo.h") and external ("reftable/reftable-foo.h") API surfaces is somewhat confusing, particularly where "reftable/system.h" sits between platform-specific and project-specific concerns.

The key points are:
1) The current design aims to make public headers self-contained while minimizing required includes, but the boundary between what belongs in platform-neutral vs Git-specific headers remains unclear.
2) Patrick suggests an alternative approach where callers would be responsible for satisfying basic dependencies like <stdint.h> themselves, potentially simplifying the header structure.
3) He remains open to alternative suggestions for better organizing these abstraction layers while maintaining the goal of clean separation between reftable's core and its system dependencies.

This email continues the thread's careful attention to architectural purity in system abstractions, with both parties recognizing the current solution isn't ideal but differing slightly on how to improve it. The discussion remains technical and constructive, focused on finding the right balance between abstraction cleanliness and practical implementation needs.
