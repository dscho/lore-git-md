This is a reply in an ongoing discussion about improving Git's content search capabilities, specifically around tracking string presence across file versions. Mirko Faina responds to Junio C Hamano's RFC about the limitations of `git log -S` and `git grep` for this use case.

Mirko proposes a shell script workaround that combines `git log -S` with revision range specification to precisely identify when a string first appeared and when it last appeared in a file. The solution involves finding the first and last commits where the string appears (using `--reverse` and `--max-count` with `-S`), then using those commit ranges to show the full history where the string was present. 

The reply notes an apparent bug in how `--reverse`, `-S` and `--max-count` interact, suggesting this might be worth fixing separately. While the solution works, it's admittedly verbose and would need to be scripted, confirming Junio's original point that this is a gap in Git's built-in capabilities.

This continues the thread's exploration of content search limitations, offering a practical (if imperfect) solution while highlighting areas where the tooling could be improved. The discussion remains technical and focused on the revision walking/search subsystems.
