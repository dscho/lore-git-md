Junio C Hamano has raised an RFC about a gap in Git's content search capabilities, specifically the inability to track when a string first appeared in a file's history (rather than just when it changed). This is particularly relevant for his "what's cooking" reports, where he needs to follow topic names across versions. Current tools like `git log -S` only show transitions (when a string appears or disappears), while `git grep` requires manual revision ranges.

Mirko Faina has responded with a workaround using existing `git log -S` functionality combined with revision range specification. His approach involves first identifying introduction and removal commits of a string, then using those ranges to show the relevant history. He notes an apparent bug in how `--reverse` interacts with `-S` and `--max-count`, where the combination doesn't behave as expected. While this provides a practical solution, it remains somewhat verbose and highlights the underlying tooling gap Junio identified. The discussion is now moving from problem identification to potential solutions, with Mirko's reply offering concrete implementation experience.
