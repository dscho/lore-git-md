This is a technical reply in the thread about improving Git's content search capabilities, specifically addressing Junio C Hamano's RFC about tracking string presence across file versions. Mirko Faina proposes a workaround using existing `git log -S` functionality combined with revision range specification to avoid guessing ranges.

The response suggests a scriptable approach that first identifies the introduction and removal commits of a string (using `git log -S` with `--reverse` and `--max-count`), then uses those commit ranges to show the relevant history. Mirko notes an apparent bug in how `--reverse` interacts with `-S` and `--max-count`, where the combination doesn't behave as intuitively expected.

The email demonstrates a practical solution to Junio's use case of tracking topic names in "what's cooking" reports, though it acknowledges the solution is somewhat verbose. The technical details about commit range specification and the observed bug in flag interactions would be relevant to anyone working on Git's revision walking or content search features. As a reply to the maintainer's RFC, this contributes concrete implementation experience to the discussion of the tooling gap.
