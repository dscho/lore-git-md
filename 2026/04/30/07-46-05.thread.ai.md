Thread summary:

Subject: Bug report - `git rebase -i` on Windows processes rewording commits sequentially instead of batched

Core problem: Regression in interactive rebase behavior on Windows when rewording multiple commits. Previously, editing the todo list to mark several commits as "reword" would process all changes at once; now it processes them one commit at a time, requiring repeated editor invocations.

Current status: Reported by David Jordanes as occurring in Git 2.53.0 on Windows 11. No maintainer response or analysis yet. The issue appears specific to Windows platform behavior in the interactive rebase machinery, though the exact version introducing the regression is unknown.

Key technical details: Affects the `sequencer.c` and `rebase-interactive.c` interaction when processing multiple "reword" operations. The reporter's reproduction case shows the changed behavior clearly but lacks bisection to pinpoint when it regressed.

Open questions: Is this intentional? Does it affect other platforms? What change caused the different behavior? The workflow impact is significant when rewording many commits.

Participant positions: Only David Jordanes so far, reporting the issue with clear reproduction steps but no technical analysis of root cause. The report suggests this may be related to editor handling changes on Windows.
