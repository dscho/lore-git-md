This is a bugfix patch that addresses concurrent config file locking issues. The patch makes Git retry acquiring the config file lock for 100ms when there's contention, similar to how reference locks already work.

The problem occurs when multiple processes try to write to `.git/config` simultaneously - currently they fail immediately if they can't get the lock, even when writing unrelated configuration keys. This particularly affects `git worktree add -b` operations run in parallel, where the worktree gets created but branch tracking configuration may be silently lost.

The solution introduces a 100ms timeout for config lock acquisition, matching the behavior Git already uses for reference locks. This should handle normal contention cases while still failing quickly for stale locks from crashed processes. The change is small and focused, touching only two call sites in `config.c` that acquire the lock.

The patch appears well-motivated and addresses a real pain point in parallel workflows. The implementation follows an established pattern from the reference locking code, which gives confidence in the approach. The commit message clearly explains both the problem and solution, including the connection to existing reference lock behavior.
