This thread explored adding a timeout to config file locking to prevent concurrent Git operations from failing due to immediate lock contention, particularly affecting `git worktree add -b` operations. The original patch by Jörg Thalheim proposed a 100ms timeout but was abandoned after maintainers Junio Hamano and Patrick Steinhardt raised fundamental design concerns about configurable timeouts and unresolved race conditions in concurrent writes.

In a follow-up, Johannes Schindelin (Dscho) provided valuable technical context from Microsoft's Git fork, showing that configurable timeouts are technically feasible (as demonstrated in Scalar's test suite) and that optimal timeout values vary by filesystem (NTFS requiring longer delays than Unix filesystems). While confirming the maintainers' concerns about deeper race conditions, Dscho's contribution serves as useful documentation of alternative approaches that work in controlled environments. The thread now stands as a case study in Git's design tradeoffs - while the core issue remains unaddressed in mainline Git, the discussion has produced practical knowledge and working implementations for those needing similar solutions in forks.
