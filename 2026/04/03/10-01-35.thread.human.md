This thread addresses a locking issue where concurrent Git operations fail when writing to config files, particularly affecting `git worktree add -b` operations. Jörg Thalheim's v2 patch proposes a configurable timeout (`core.configLockTimeout`) modeled after the packed-refs timeout, with thorough test coverage. The maintainer, Junio C Hamano, identified that the current implementation makes the timeout effectively process-wide due to caching behavior, despite taking a repository parameter.

In the latest discussion, Patrick Steinhardt engages with Junio's review, agreeing that per-repository timeout values are likely unnecessary but questioning whether the caching layer should be kept. While Junio prefers simplifying to an explicitly process-wide timeout using `the_repository`, Patrick suggests removing caching entirely to maintain the per-repository parameter while accepting that timeouts would still typically be uniform in practice. The exchange reflects substantive technical discussion about implementation tradeoffs, with both contributors focusing on practical considerations around lock contention and configuration overhead. The patch appears headed toward acceptance, pending resolution of this final design question about whether to optimize for simplicity (Junio's approach) or conceptual clarity (Patrick's suggestion).
