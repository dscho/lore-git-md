This thread is about a bugfix patch that adds a configurable timeout (`core.configLockTimeout`, defaulting to 1000ms) for acquiring locks on Git config files. The patch, now at version 2, addresses a real-world issue where concurrent Git operations (like `git worktree add -b`) fail due to immediate lock contention, especially on slower filesystems such as NTFS. The problem and solution have been thoroughly reviewed, with key participants including Jörg Thalheim (the author), Junio C Hamano (the maintainer), Patrick Steinhardt, and Johannes Schindelin.

The patch is now explicitly cleared for merging to `next` and subsequently `master`. All technical concerns have been resolved, including a debate about whether the timeout should be process-wide or per-repository—this was deferred to a follow-up patch, with Junio preferring a simpler process-wide approach and Patrick advocating for the current implementation. Johannes Schindelin’s endorsement and Junio’s confirmation that the patch is otherwise ready for integration signal broad acceptance. The only remaining step is Junio’s merge queue management, as the patch has temporarily slipped through the cracks but is now back on track.

The implementation follows the precedent set by `core.packedRefsTimeout` and includes comprehensive test coverage for both immediate failure and retry scenarios. The timeout is implemented with a process-wide cache, making it effectively global despite being passed as a repository parameter. Documentation covers read-after-lock semantics and last-writer-wins behavior, addressing earlier reviewer questions. No further changes to the patch are expected, and the deferred caching tradeoff discussion will be handled separately. The patch is procedurally ready for integration.
