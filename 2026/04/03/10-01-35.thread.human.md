This thread is about a bugfix patch that adds a configurable timeout (`core.configLockTimeout`, default 1000ms) to Git's config file locking mechanism, addressing failures in concurrent operations like `git worktree add -b`. The patch is now at v2, with the author Jörg Thalheim driving the implementation and maintainers Junio C Hamano and Patrick Steinhardt actively reviewing the technical details.

The core debate centers on whether the timeout should be process-wide (Junio's preference, simplifying caching behavior) or per-repository (Patrick's counterproposal, removing caching to allow per-repo values). Johannes Schindelin has weighed in to clarify that his earlier comment about the unit-less timeout naming convention was supportive, not an objection, and that he’s satisfied with the current approach and will handle any Windows-specific adjustments. He now urges the patch to move forward to `next` and then `master`, though the deeper technical discussion between Junio and Patrick remains unresolved. The patch is otherwise ready, with tests, documentation, and precedent (e.g., `core.packedRefsTimeout`) in place.
