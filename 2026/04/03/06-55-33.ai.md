This is the first patch in a two-part series that makes submodule fetch errors configurable. It fixes a pre-existing issue where submodule fetch failures were being recorded too early in the process, before the retry mechanism had completed. The patch restructures the error handling in `submodule.c` to defer recording failures until after the OID-based retry phase (phase 2) has completed, unless the submodule was fetched unconditionally (where no retry occurs).

The changes extract common error recording logic into a new `record_fetch_error()` helper and carefully document the different cases where errors should or shouldn't be recorded. This resolves a NEEDSWORK comment from 2019 about unclear failure handling. The patch touches only the submodule fetch implementation, with no user-visible behavior changes yet - those come in the second patch which introduces configurable error handling.

The implementation looks clean and well-documented, with clear commit message explaining the motivation and approach. This appears to be a solid refactoring that sets up for the new functionality in the next patch while fixing an edge case in the current behavior.
