Chen Linxuan's v3 series adding `includeIf worktree` and `worktree/i` config conditions has picked up a new question. After Patrick Steinhardt gave the implementation a thorough review and called it "sensible" -- endorsing patch 1/2 as a good preparatory step and offering three modest action items (documentation dedup, two missing test cases) -- Phillip Wood has now raised a more fundamental question about the feature's motivation.

Phillip points out that Git already supports per-worktree config through `extensions.worktreeConfig` and `git config --worktree`. He asks why matching on a worktree's checkout path is more convenient than that existing mechanism, giving the concrete example of whether the author has multiple repositories with worktrees under a common prefix. This is the first challenge to the design premise itself rather than the implementation, and could become a sticking point unless Chen Linxuan can articulate a clear scenario where `worktree:` patterns solve something the existing mechanism does not.

The series otherwise stands at v3 with Patrick's three requests expected in a v4: share a common documentation section for pattern-matching rules (avoiding verbatim copies from the `gitdir` condition), add a test for the condition during early config parsing, and add a test for behavior outside a repository entirely. No technical objections to the implementation have been raised; the open question is now whether the feature justifies itself.
