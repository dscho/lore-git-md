This is a review response to Patrick Steinhardt's RFC proposal to reorganize Git's source tree by moving libgit.a components into a new "lib/" directory. Phillip Wood offers a substantive review that engages with the technical merits while questioning some of the claimed benefits.

Phillip agrees with the general direction, seeing value in having library code clearly separated to enforce coding conventions like avoiding `the_repository` and preferring `error()` over `die()`. However, he pushes back on the discoverability argument, noting that moving files into a subdirectory doesn't actually reduce the number of files to search through - it just adds another directory level. He suggests tools like `git grep` and ctags are the real solution for code navigation.

The review acknowledges the practical timing of the proposal (targeting the start of a new release cycle) and finds no technical faults with the implementation. While supportive of the change, Phillip's feedback provides a useful reality check on some of the claimed motivations, distinguishing between the organizational benefits (which he accepts) and discoverability improvements (which he questions).

This continues the generally positive reception the RFC has received from other key contributors like Elijah Newren, brian m. carlson, and Junio Hamano, though with a more nuanced take on the benefits. The thread appears to be converging toward acceptance with minor adjustments.
