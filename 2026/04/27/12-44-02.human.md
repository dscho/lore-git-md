This is a discussion thread in Christian Couder's series on URL-based promisor remote configuration, specifically addressing patch 15/16 which proposes auto-configuring unknown remotes that match whitelisted URL patterns.

Christian pushes back on Patrick Steinhardt's earlier suggestion to split the functionality into separate concerns (runtime acceptance, initial configuration, and updates) and to add a `--accept-promisors` clone option. He argues that his current approach with `promisor.acceptFromServerUrl` provides a simpler one-time configuration that's more secure than requiring repeated manual flags.

Key points in Christian's response:
- The current design already minimizes user effort through global configuration
- Manual flags could lead to more errors than a single configuration
- He questions Patrick's assumption that most users won't want ongoing updates
- Notes that `git -c` can already provide per-clone behavior similar to the proposed flag

The exchange reveals a philosophical difference in approach: Patrick favors explicit, granular control while Christian prioritizes convenience and reduced configuration burden. Christian maintains that his solution adequately covers the use cases while being more user-friendly.

This is a substantive design discussion touching on security tradeoffs and workflow preferences. The thread shows Christian defending his architectural choices while remaining open to Patrick's feedback about separating concerns. The disagreement appears to be about the right level of control rather than technical correctness.
