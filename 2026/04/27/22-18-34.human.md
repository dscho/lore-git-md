This is the second patch in a bugfix series addressing a regression in commit signing for non-UTF-8 messages. The regression, introduced in Git 2.45.0, caused signatures to become invalid when commit messages contained non-UTF-8 text without an explicit encoding configuration.

The patch fixes the core issue by reordering operations in `commit_tree_extended()` to perform UTF-8 validation and transcoding *before* generating signatures. This ensures the signed content matches what gets stored in the commit. The fix handles both the main commit buffer and a compatibility buffer used for SHA-1/SHA-256 interoperability.

Key technical changes:
- Moves UTF-8 validation (`ensure_utf8()`) before signing operations
- Adds logic to avoid duplicate warning messages when both buffers contain invalid UTF-8
- Includes a test case using invalid UTF-8 bytes (0xfe and 0xff) to verify the fix

The patch builds on the first in the series (which renamed `verify_utf8()` to `ensure_utf8()`) and addresses edge cases identified in review, particularly around warning message behavior. The solution is backend-agnostic, working for all signature types (GPG, SSH, X.509).

This appears to be a well-constructed fix for a significant regression affecting all Git versions from 2.45.0 through at least 2.53.0. The test coverage provides confidence in the solution, and the changes align with the pre-2.45.0 behavior that worked correctly.
