This is the second patch in a two-part bugfix series addressing a regression in commit signing for non-UTF-8 messages. The patch fixes the core issue by reordering operations in `commit_tree_extended()` to ensure UTF-8 validation/transcoding happens before signing, restoring pre-2.45.0 behavior where signatures remain valid for non-UTF-8 messages.

The key changes are:
1. Moving the UTF-8 validation (`ensure_utf8()`) before signing operations
2. Adding logic to avoid duplicate warning messages when both main and compatibility buffers contain invalid UTF-8
3. Fixing the original code's logical short-circuiting that caused only the first invalid buffer to be processed
4. Adding a test case using invalid UTF-8 bytes (0xfe and 0xff) to verify the fix

The patch addresses Elijah Newren's review feedback from v1 about warning message behavior while maintaining the core fix. The regression affected all signature types (GnuPG/SSH/X.509) when commit messages contained non-ASCII characters without explicit encoding configuration. The test case provides regression protection going forward.

This completes the fix for the high-impact bug that affected Git versions 2.45.0 through at least 2.53.0. The series has received substantive review and appears ready for merging once the warning message refinements are confirmed in v2.
