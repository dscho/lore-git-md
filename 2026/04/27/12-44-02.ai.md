This is a design discussion response in Christian Couder's ongoing series on URL-based promisor remote configuration. Christian pushes back on Patrick Steinhardt's suggestion to split the functionality into separate concerns (runtime acceptance, initial storage, and ongoing updates) and add a `--accept-promisors` clone option.

Christian argues that the current approach with `promisor.acceptFromServerUrl` provides sufficient flexibility while being more user-friendly than requiring manual options for each clone. He makes several key points:

1. The global config approach requires less user effort than repeated command-line flags, as admins can set it once for all users
2. The `-c` option can provide per-clone behavior similar to Patrick's proposed flag
3. Automatic updates are valuable since server-side URLs/fields may change
4. Manual options increase typo/misconfiguration risks compared to centralized config

The exchange reveals differing assumptions about the most common workflow - Patrick assumes users will want explicit control at clone time, while Christian believes automatic acceptance of trusted domains will be the dominant case. Christian maintains that the current design already supports both approaches through different configuration methods.

This continues the pattern of substantive technical discussion in this series, with both contributors engaging on the actual security and usability tradeoffs rather than surface-level concerns. The thread remains focused on refining the feature's design before implementation.
