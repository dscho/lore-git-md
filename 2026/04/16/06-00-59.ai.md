This is a follow-up discussion on Patrick Steinhardt's completed series to enable `set -e` in Git's test suite. Jeff King (Peff) raises practical verification concerns now that the change is implemented.

Peff acknowledges the series has successfully made the test suite abort on unexpected failures outside test cases, but questions how to verify this protection actually catches real bugs. He demonstrates with a test modification that intentionally introducing an error (`test_expect_foobar`) only fails when explicitly using Bash (not the default `/bin/sh` on Debian). This leads to his core question: do the CI systems (GitHub and GitLab) reliably use a Bash version that would catch such errors?

The email highlights an important gap between the theoretical protection and practical verification. While the series carefully restricted `set -e` to Bash 5+ for reliability, Peff notes we lack visibility into whether CI environments will use the right shell by default. He suggests explicitly setting `TEST_SHELL_PATH` in at least one Linux CI job to ensure error detection works as intended in automated testing.

This continues the thread's theme of balancing robust error checking with practical constraints. Peff's concern isn't about the technical implementation (which Junio has already approved) but about operational verification - making sure the safety net actually catches falls in real-world use. The question about Windows shell versions also hints at remaining platform-specific considerations, though the series deliberately avoided tackling those by limiting scope to known-good Bash versions.
