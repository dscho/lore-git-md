This thread explores optimizing submodule performance in linked worktrees by reusing objects from the main worktree. The original patch series proposed using `git clone --local` to create hardlinks to existing submodule objects, saving bandwidth and disk space while keeping worktree metadata separate. The approach was well-contained and addressed real performance pain points.

Maintainer Junio Hamano has now weighed in with a significant design consideration. He suggests that rather than creating independent submodule repositories via `clone --local`, a better approach might be to use `git worktree add` to maintain proper synchronization between submodule instances across worktrees. This would share object storage while keeping worktree-specific metadata separate, avoiding potential inconsistencies that could arise if commits are added to one submodule instance but not automatically visible in others.

The core question now is whether submodule state should be completely independent between worktrees (as in the current patch) or share object storage while maintaining separate working trees (as Junio suggests). This touches on fundamental questions about how submodule state should propagate across linked worktrees. The patch author will need to consider this feedback and either adjust their approach or justify why independent repositories are preferable in this case.
