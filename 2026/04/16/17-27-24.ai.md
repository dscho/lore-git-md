This is a review response from Junio C Hamano regarding the submodule clone optimization patch. The maintainer suggests reconsidering the implementation approach - instead of using `git clone --local` to create hardlinks to the main worktree's submodule objects, he proposes using `git worktree add` which would better maintain the relationship between the submodule instances across worktrees.

Junio points out that the current approach creates two logically separate repositories for the submodule, which could lead to inconsistencies if commits are added to one but not automatically visible in the other. The `worktree add` approach would keep them properly synchronized through the shared object store while still maintaining separate worktree metadata.

The technical discussion focuses on the implementation in `clone_submodule()` where the patch adds about 50 lines to handle the local clone case. Junio doesn't reject the optimization itself but questions whether the chosen mechanism (`clone --local`) is the right primitive for this use case given the desired behavior of shared submodule state across worktrees.

For future reference: The key consideration here is whether submodule state should be completely independent between worktrees (current patch approach) or share object storage while maintaining separate working trees (`worktree add` approach). The discussion touches on Git's object model and how submodule state should propagate across linked worktrees.
