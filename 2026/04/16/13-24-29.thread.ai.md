Patrick Steinhardt's RFC patch series (v2) to reorganize Git's source tree by moving all `libgit.a` components into a new `lib/` directory remains under discussion. The series aims to reduce root directory clutter (from ~550 to ~80 files) to improve shell tab completion and establish a clear boundary for `libgit.a`. Version 2 addresses all prior technical feedback, including Meson build logic, ODB source handling, fsmonitor backend paths, Rust build requirements, and submodule complications, with no outstanding objections from reviewers.

The series consists of two patches: the first (1/2) adjusts `t/helper/test-example-tap.c` to ensure build integrity post-relocation, while the second (2/2) relocates ~700 files—including core subsystems (object handling, refs, diff, merge) and platform compatibility shims—into `lib/` while preserving internal structure. Changes are dominated by path updates in build system files (`Makefile`, `meson.build`, `CMakeLists.txt`, `config.mak.uname`), CI workflows (GitHub Actions), and platform-specific logic. No functional changes or new symbols are introduced; this is purely a structural reorganization.

Johannes Schindelin (Git for Windows) has given preliminary approval for the transition, and earlier concerns from Derrick Stolee about merge conflicts and rebase challenges for long-lived forks (e.g., GitHub, Microsoft Git) are being mitigated through incrementalism and Patrick's willingness to assist. However, Junio C Hamano has expressed skepticism about the reorganization's practical benefits, framing it as a cosmetic change that may not justify the disruption to in-flight and upcoming patches, particularly during the prerelease freeze period. Junio's concerns focus on the logistical burden of updating topics and complicating backporting fixes to older versions, though he has not outright rejected the idea.

In response, Patrick argues that Git's resistance to handling file moves gracefully is itself a usability issue the project should address. He contends that experiencing the pain of reorganization firsthand—akin to other projects—would incentivize improvements to Git's tooling (e.g., `git diff`, `git rebase`) to better handle such changes. This reframes the reorganization as a catalyst for tooling improvements rather than just a cosmetic cleanup. While Patrick remains open to the community rejecting the idea, his response advocates for the broader value of the change, shifting the discussion toward tooling gaps rather than addressing Junio's timing or backporting concerns directly. The tone suggests a willingness to accept a "no" but underscores the potential long-term benefits.

Key technical details remain the `lib/` directory structure and the build system updates from the original patch. The discussion now centers on whether the structural improvement and tooling incentives outweigh the maintenance overhead, with no technical objections raised but timing and coordination emerging as unresolved concerns. Downstream consumers should monitor whether Patrick's tooling argument gains traction or if the focus remains on disruption to ongoing work.
