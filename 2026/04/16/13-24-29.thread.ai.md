Patrick Steinhardt's RFC patch series (v3) to reorganize Git's source tree by moving all `libgit.a` components into a new `lib/` directory remains a **refactoring-only** effort aimed at reducing root-directory clutter (from ~550 to ~80 files) and establishing a clearer boundary for Git's core library code. The series explicitly acknowledges the downsides of the mass rename—disrupted `git log --follow` history, rebasing/backporting challenges for in-flight topics, and merge conflicts for downstream forks (e.g., GitHub, Microsoft Git)—but frames these as one-time costs justified by permanent improvements in code discoverability and onboarding. The v3 iteration incorporates Johannes Schindelin's Windows CI fix (adjusting `.github/workflows/main.yml` to reference `lib/compat`) and reiterates the trade-off rationale in the commit message, addressing SZEDER Gábor's earlier objection about historical tracking by positioning it as a tooling deficiency the project should address.

The series consists of two patches: (1) a preparatory change to `t/helper/test-example-tap.c` to ensure build integrity, and (2) the main patch moving ~700 files (core subsystems like object handling, refs, diff, merge, and platform compatibility shims) into `lib/` while preserving internal structure. The relocation is a **pure mechanical move** with no functional changes, updating build system files (`Makefile`, `meson.build`, `CMakeLists.txt`, `config.mak.uname`), CI workflows, and `.gitmodules` to reference the new `lib/` paths. No symbols, APIs, or on-disk formats are modified.

**Core debate status**: The discussion continues to weigh structural benefits against logistical disruption. Proponents (Patrick Steinhardt, Oswald Buddenhagen, Johannes Schindelin) argue the reorganization improves discoverability and could incentivize tooling improvements (e.g., better rename tracking in `git log`). Opponents (Junio C Hamano, SZEDER Gábor, Derrick Stolee) emphasize the disruption to ongoing work, backporting, and historical tracking, viewing the change as cosmetic and risky during the prerelease freeze. Phillip Wood's **substantive review** introduces a new critique: the discoverability argument is weak because the number of files remains the same, just nested under an extra directory. He suggests tools like `git grep` or `ctags` are better solutions and instead endorses the `lib/` directory as a way to enforce coding conventions (e.g., avoiding `the_repository` or `die()` in library code). However, he also highlights a practical friction point—recurring mental overhead from remembering file moves (e.g., `wt-status.c` -> `lib/wt-status.c`)—framing it as an ongoing annoyance rather than a one-time cost.

**Key technical details**:
- **Files moved**: Core subsystems (`object.c`, `refs.c`, `diff.c`, `merge.c`, `compat/`, `reftable/`, `xdiff/`, `wt-status.c`) and utility files (`strbuf.c`, `hashmap.c`).
- **Build system updates**: Paths in `Makefile`, `meson.build`, `CMakeLists.txt`, `config.mak.uname`, and `.gitmodules` are updated to reference `lib/`.
- **CI/tooling**: Windows CI regression fixed; GitLab/GitHub CI pipelines validate the change.
- **No symbol/API changes**: Pure path reorganization; no functional or on-disk format changes.

**Open questions**:
- Whether the tooling-incentive argument (that this change will drive improvements to `git log --follow`) gains traction among maintainers.
- How to mitigate rebasing/backporting pain for downstream consumers (e.g., incrementalism, assistance offers).
- Whether the structural benefits (e.g., enforcing library conventions) justify the ongoing friction, particularly during the prerelease freeze.
- Whether Phillip Wood's coding-convention argument (avoiding `the_repository`/`die()` in library code) is compelling enough to shift the debate.
