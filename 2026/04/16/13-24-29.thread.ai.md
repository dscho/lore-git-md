Patrick Steinhardt's RFC patch series (v4) to reorganize Git's source tree by moving all `libgit.a` components into a new `lib/` directory remains a **refactoring-only** effort aimed at reducing root-directory clutter (from ~550 to ~80 files) and establishing a clearer boundary for Git's core library code. The series explicitly acknowledges the downsides of the mass rename—disrupted `git log --follow` history, rebasing/backporting challenges for in-flight topics, and merge conflicts for downstream forks—but frames these as one-time costs justified by permanent improvements in code organization and enforcement of coding conventions (e.g., avoiding `the_repository` or `die()` in library code). **SZEDER Gábor's latest reply directly challenges this framing**, arguing that the disruption is **not one-time** but an ongoing burden that will persist indefinitely, particularly for `git log --follow` and rebasing workflows. Gábor dismisses Patrick's suggestion that the pain could incentivize tooling improvements (e.g., better rename detection) as unrealistic, questioning who would implement such changes and whether they are even feasible. His position remains unchanged: the reorganization trades one annoyance (root-directory clutter) for another (ongoing workflow friction) and is "not worth it."

The series consists of two patches: (1) the preparatory change to `t/helper/test-example-tap.c` to fix the include path, and (2) the main patch moving ~700 files (core subsystems like object handling, refs, diff, merge, platform compatibility shims, and utility files such as `strbuf.c` and `hashmap.c`) into `lib/` while preserving internal structure. The relocation is a **pure mechanical move** with no functional changes, updating build system files (`Makefile`, `meson.build`, `CMakeLists.txt`, `config.mak.uname`), CI workflows (GitHub Actions, GitLab CI), and `.gitmodules` to reference the new `lib/` paths. No symbols, APIs, or on-disk formats are modified.

**Core debate status**: The discussion continues to focus on whether the reorganization's benefits justify its workflow disruptions, with Patrick Steinhardt refining the goal to emphasize root-directory decluttering (rather than library file discoverability) and enforcing coding conventions. Critics like Junio C Hamano, Phillip Wood, and **SZEDER Gábor** highlight the **ongoing mental overhead** of remembering file moves (e.g., `wt-status.c` → `lib/wt-status.c`) and the **persistent disruption** to tools like `git log --follow`. Gábor's latest reply reinforces the stalemate, as he sees no realistic path to mitigating the ongoing costs and questions the tradeoff's value. Kaartic Sivaraam's proposal to add a hint to `git show` when a file appears renamed (e.g., suggesting `lib/wt-status.c` instead of `wt-status.c`), controlled by a config knob (`advice.objectNameWarning`), remains a potential middle ground, though its feasibility hinges on efficient rename detection and performance implications.

**Key technical details**:
- **Files moved**: Core subsystems (`object.c`, `refs.c`, `diff.c`, `merge.c`, `compat/`, `reftable/`, `xdiff/`, `wt-status.c`) and utility files (`strbuf.c`, `hashmap.c`).
- **Build system updates**: Paths in `Makefile`, `meson.build`, `CMakeLists.txt`, `config.mak.uname`, and `.gitmodules` are updated to reference `lib/`.
- **CI/tooling**: Windows CI regression fixed; GitLab/GitHub CI pipelines validate the change. The preparatory patch ensures include resolution works post-move.
- **No symbol/API changes**: Pure path reorganization; no functional or on-disk format changes.
- **Proposed UX improvement**: A hint in `git show` to suggest renamed file paths (e.g., `lib/wt-status.c` instead of `wt-status.c`), controlled by a config knob (`advice.objectNameWarning`). Feasibility depends on efficient rename detection.

**Open questions**:
- Whether the refined rationale (reducing root-directory clutter to improve non-library file discoverability) gains sufficient traction among maintainers, given **SZEDER Gábor's latest objection** that the costs are ongoing, not one-time.
- How to mitigate the **persistent mental overhead** of file moves (e.g., `wt-status.c` → `lib/wt-status.c`) for contributors, including the viability of Kaartic Sivaraam's `git show` hint proposal and its performance implications.
- Whether the structural benefits (e.g., enforcing coding conventions like avoiding `the_repository`/`die()` in library code) justify the **ongoing friction**, particularly during the prerelease freeze.
- Whether non-structural solutions (e.g., documentation, tooling improvements, or Junio's "map" proposal) could address discoverability without disrupting file locations, and who would implement them.
