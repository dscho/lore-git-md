Patrick Steinhardt's RFC patch series (v2) to reorganize Git's source tree by moving all `libgit.a` components into a new `lib/` directory continues, with the goal of reducing root directory clutter (from ~550 to ~80 files) and establishing a clear boundary for `libgit.a`. Version 2 addresses all prior technical feedback, including Meson build logic, ODB source handling, fsmonitor backend paths, Rust build requirements, submodule complications, and a Windows CI regression fix. Junio C Hamano has queued Johannes Schindelin's one-line fix (`path: lib/compat` in `.github/workflows/main.yml`) to resolve a Visual Studio build regression in the Git for Windows CI pipeline, confirming it will be squashed into the original patch (2/2) in the next iteration.

The series consists of two patches: the first (1/2) adjusts `t/helper/test-example-tap.c` to ensure build integrity post-relocation, while the second (2/2) relocates ~700 files—including core subsystems (object handling, refs, diff, merge) and platform compatibility shims—into `lib/` while preserving internal structure. Changes are dominated by path updates in build system files (`Makefile`, `meson.build`, `CMakeLists.txt`, `config.mak.uname`), CI workflows (GitHub Actions), and platform-specific logic. Johannes Schindelin (Git for Windows) has given preliminary approval for the transition, and the Windows CI regression fix further solidifies platform compatibility.

The discussion now centers on whether the structural improvement and tooling incentives outweigh the maintenance overhead, with **new substantive pushback** from SZEDER Gábor. SZEDER raises a **user-facing technical concern**: the reorganization disrupts `git log --follow` and exacerbates the "rename barrier" problem, making it harder to trace file history across the move. This objection challenges the series' core premise by framing the change as a zero-sum trade-off—replacing root directory clutter with historical tracking difficulties. The feedback is **not surface-level** and engages directly with the patch's motivation, shifting the debate from implementation details to whether the benefits (e.g., onboarding, structural clarity) justify the costs. This is the first substantive critique of the series' fundamental value, despite prior technical feedback being addressed.

Earlier concerns from Derrick Stolee about merge conflicts and rebase challenges for long-lived forks (e.g., GitHub, Microsoft Git) persist, though Patrick has offered to mitigate these through incrementalism and assistance. Junio remains skeptical about the reorganization's practical benefits, viewing it as a cosmetic change that may not justify the disruption to in-flight and upcoming patches, particularly during the prerelease freeze period. Junio's concerns focus on the logistical burden of updating topics and complicating backporting fixes to older versions, though he has not outright rejected the idea. Patrick argues that Git's resistance to handling file moves gracefully is itself a usability issue the project should address, contending that experiencing the pain of reorganization firsthand would incentivize improvements to Git's tooling (e.g., `git diff`, `git rebase`, `git log --follow`).

Oswald Buddenhagen supports the reorganization and suggests applying it *before* the upcoming release (Git 2.55), arguing that the change affects only the build system (thoroughly validated by CI) and poses minimal risk of regressions late in the cycle. Oswald acknowledges that this timing won't resolve backporting or rebasing challenges but defers to Patrick's earlier response, explicitly endorsing the change as a cleanup for the "messy and confusing" current source tree. The unresolved questions now include:
- Whether the tooling argument (that this change will incentivize improvements to `git log --follow` and other move-handling tools) gains traction.
- How to address SZEDER's objection about historical tracking, which may require either a stronger defense of the trade-offs or a proposal to mitigate the pain (e.g., improved tooling).
- Whether the logistical disruption to downstream consumers and ongoing work outweighs the structural benefits.
