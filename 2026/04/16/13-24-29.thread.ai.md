Patrick Steinhardt's RFC patch series (v3) to reorganize Git's source tree by moving all `libgit.a` components into a new `lib/` directory remains a **refactoring-only** effort aimed at reducing root-directory clutter and establishing a clearer boundary for Git's core library code. The series explicitly acknowledges the downsides of the mass rename—disrupted `git log --follow` history, rebasing/backporting challenges for in-flight topics, and merge conflicts for downstream forks—but frames these as one-time costs justified by permanent improvements in code organization. The v3 iteration incorporates Johannes Schindelin's Windows CI fix and reiterates the trade-off rationale, though the core debate has shifted from historical tracking to the practicality of the reorganization's goals.

The series consists of two patches: (1) a preparatory change to `t/helper/test-example-tap.c` to ensure build integrity, and (2) the main patch moving ~700 files (core subsystems like object handling, refs, diff, merge, and platform compatibility shims) into `lib/` while preserving internal structure. The relocation is a **pure mechanical move** with no functional changes, updating build system files (`Makefile`, `meson.build`, `CMakeLists.txt`, `config.mak.uname`), CI workflows, and `.gitmodules` to reference the new `lib/` paths. No symbols, APIs, or on-disk formats are modified.

**Core debate status**: The discussion has evolved to focus on whether the reorganization's benefits outweigh its ongoing friction. Patrick Steinhardt now clarifies that the primary goal is **not** to improve discoverability of library files (contrary to earlier framing) but to reduce clutter in the root directory, making non-library files easier to locate. He concedes Phillip Wood's critique that the change does not help find library files themselves but argues that grouping library code enforces clearer coding conventions (e.g., avoiding `the_repository` or `die()` in library code). However, he offers no concrete mitigation for the recurring mental overhead of remembering file moves (e.g., `wt-status.c` → `lib/wt-status.c`), leaving the debate unresolved. Junio C Hamano and Phillip Wood remain skeptical, emphasizing workflow disruption and suggesting non-structural alternatives (e.g., documentation or tooling improvements). Junio's proposal of a high-level "map" of the codebase (possibly leveraging LLMs) remains unaddressed.

**Key technical details**:
- **Files moved**: Core subsystems (`object.c`, `refs.c`, `diff.c`, `merge.c`, `compat/`, `reftable/`, `xdiff/`, `wt-status.c`) and utility files (`strbuf.c`, `hashmap.c`).
- **Build system updates**: Paths in `Makefile`, `meson.build`, `CMakeLists.txt`, `config.mak.uname`, and `.gitmodules` are updated to reference `lib/`.
- **CI/tooling**: Windows CI regression fixed; GitLab/GitHub CI pipelines validate the change.
- **No symbol/API changes**: Pure path reorganization; no functional or on-disk format changes.

**Open questions**:
- Whether the refined rationale (reducing root-directory clutter to improve non-library file discoverability) gains traction among maintainers.
- How to mitigate the recurring mental overhead of file moves (e.g., `wt-status.c` → `lib/wt-status.c`) for contributors.
- Whether the structural benefits (e.g., enforcing coding conventions like avoiding `the_repository`/`die()` in library code) justify the ongoing friction, particularly during the prerelease freeze.
- Whether non-structural solutions (e.g., documentation, tooling improvements, or Junio's "map" proposal) could address discoverability without disrupting file locations.
