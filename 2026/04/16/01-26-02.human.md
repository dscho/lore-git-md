This is a follow-up in the ongoing `git subtree` bug thread, where Colin Stagner responds to Ian Jackson's original report about `git subtree split` failing with merge-heavy histories. 

Colin identifies that the recursion depth issue in Git 2.45.2 stems from Debian's POSIX shell implementation artificially limiting recursion to 1000 calls, which is not typical behavior in other distributions. He has proposed a fix for this specific issue in a separate patch series and requests testing/review.

For the older Git 2.20.1 behavior (where the command runs slowly and produces incorrect history), Colin notes that even with his fixes, the command still produces a much larger history (12,307 commits) than the expected "few dozen". He attributes this to fundamental challenges in determining which parts of merge-heavy histories should be considered "important" for subtree operations, referencing a 2018 change (e7b07376e5) that adjusted merge-base ancestry checks.

The response is helpful in explaining the technical context behind both failure modes, though it makes clear that the underlying merge-handling challenges in `git subtree` remain unresolved. The proposed fix addresses only the immediate recursion issue on Debian systems, not the broader merge-handling problems.
