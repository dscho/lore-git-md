This is a technical discussion about improving `git subtree split`'s handling of merge-heavy histories, building on an earlier bug report. Ian Jackson responds to Colin Stagner's analysis with a proposed algorithm refinement.

Ian starts by acknowledging Colin's patch series addressing the shell recursion limit issue, then focuses on the deeper problem of incorrect history inclusion when splitting subtrees with complex merge ancestry. He observes that the current implementation (even with fixes) produces ~12,000 commits when only dozens are expected, tracing this to changes in merge base handling from commit e7b07376e5.

The core contribution is Ian's detailed proposal for a deterministic split algorithm that would treat merge commits more carefully. His approach would: (1) make splits a pure function of downstream commits, (2) avoid duplicate work by reusing identical splits, and (3) handle merge parents by discarding redundant ancestry. The algorithm is specified through four cases covering single-parent changes, no-changes, multi-parent merges, and explicit subtree merges.

Ian asks whether prototyping this approach would be worthwhile, suggesting it might significantly reduce the commit count in his test case (the Tor Project's arti.git). The email advances the technical discussion by moving from problem diagnosis to solution design, though the complexity of merge handling in subtree operations means any implementation would need careful validation.
