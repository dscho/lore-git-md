[PATCH v2 2/3] submodule: optimize clone in linked worktrees by reusing objects

This series improves submodule clone performance in linked worktrees by avoiding redundant fetches when the same submodule exists in the main worktree. The current patch modifies clone_submodule() to detect existing submodules via the_repository->commondir and use git clone --local with hardlinks instead of remote fetching.

Junio C Hamano has raised a design consideration in review: he suggests using `git worktree add` rather than `git clone --local` to maintain proper synchronization between submodule instances across worktrees. The key distinction is that `clone --local` creates independent repositories that could diverge, while `worktree add` would share object storage while keeping worktree metadata separate. This would better preserve the relationship between submodule states in different worktrees.

Technical implementation currently adds ~50 lines to handle the local clone path in builtin/submodule--helper.c. The open question is whether to:
1) Keep the current approach (independent clones with hardlinks)
2) Switch to worktree-add model (shared object store)
3) Find a hybrid solution

The optimization goal remains valid - reducing bandwidth/disk usage when the same submodule appears in multiple worktrees. The discussion now centers on which Git primitive best achieves this while maintaining correct submodule behavior across worktrees. No other reviewers have weighed in yet on Junio's suggestion. The patch is at v2 in a 3-part series.
