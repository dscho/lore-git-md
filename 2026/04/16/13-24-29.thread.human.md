Patrick Steinhardt’s RFC patch series (v2) to reorganize Git’s source tree by moving `libgit.a` components into a new `lib/` directory continues to draw discussion, with the debate now centering on timing and practical trade-offs. The series, which aims to reduce root directory clutter and establish a clearer boundary for `libgit.a`, has no outstanding technical objections—version 2 addresses all prior feedback, including build system adjustments, ODB handling, and platform-specific concerns.

Johannes Schindelin has given preliminary approval, while Junio C Hamano remains skeptical, questioning whether the cosmetic benefits justify the disruption to in-flight patches and backporting efforts, particularly during the prerelease freeze. Patrick has countered that the reorganization could serve as a catalyst for improving Git’s tooling (e.g., `git diff`, `git rebase`) to better handle file moves, framing the change as a long-term usability win rather than just a cleanup.

The latest reply comes from Oswald Buddenhagen, who supports the reorganization but suggests merging it *before* the upcoming Git 2.55 release, arguing that the build system changes are low-risk and well-validated by CI. While this doesn’t resolve Junio’s concerns about backporting or rebasing, it adds weight to the case for moving forward sooner rather than later. Oswald’s endorsement—calling the current source tree "messy and confusing"—reinforces Patrick’s goal of improving navigability, though the broader question of whether the benefits outweigh the disruption remains unresolved. The discussion now hinges on whether the community prioritizes structural improvements or stability during the freeze.
