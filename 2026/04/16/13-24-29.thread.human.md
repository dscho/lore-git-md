Patrick Steinhardt’s RFC patch series (v2) to reorganize Git’s source tree by moving `libgit.a` components into a new `lib/` directory has sparked renewed debate about its practical trade-offs. The series, now technically sound after addressing feedback on build systems, CI regressions, and platform compatibility, aims to reduce root directory clutter and establish a clearer boundary for `libgit.a`. However, SZEDER Gábor’s substantive review has shifted the discussion from *how* to implement the move to *whether* it’s worth the disruption.

SZEDER highlights a key drawback: the reorganization would break `git log --follow`’s ability to track file history across the move, creating a "rename barrier" that complicates debugging and maintenance. This objection challenges the series’ core premise—that improved structural clarity justifies the change—by framing it as a zero-sum trade-off between root directory clutter and historical traceability. The feedback resonates with contributors who rely on `git log` for debugging, adding weight to Junio C Hamano’s earlier skepticism about the disruption to in-flight patches and backporting. While Patrick argues that the pain of such moves could incentivize improvements to Git’s tooling (e.g., `git log --follow`), SZEDER’s review suggests the immediate costs may outweigh the long-term benefits.

The series itself consists of two patches: one adjusting a test helper to ensure build integrity, and another relocating ~700 files into `lib/` while preserving internal structure. Johannes Schindelin (Git for Windows) has given preliminary approval, and a Windows CI regression fix has been queued by Junio, but the debate now centers on whether the structural improvements justify the logistical overhead. Derrick Stolee’s earlier concerns about merge conflicts for long-lived forks (e.g., GitHub, Microsoft Git) remain unresolved, though Patrick has offered to assist with incremental adoption. Oswald Buddenhagen supports merging the change before Git 2.55’s release, arguing it poses minimal regression risk, but the discussion’s focus has shifted to whether the tooling argument holds water or if the project should prioritize stability over structural cleanup. Downstream consumers should monitor whether Patrick or others propose mitigations for the `git log --follow` issue or if the series stalls on logistical concerns.
