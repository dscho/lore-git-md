Patrick Steinhardt’s RFC patch series (v2) to reorganize Git’s source tree by moving all `libgit.a` components into a new `lib/` directory is nearing readiness, with only a minor Windows-specific fixup remaining. The series aims to reduce root directory clutter and establish a clearer boundary for `libgit.a`, and version 2 has addressed all prior technical feedback, including build system adjustments, ODB source handling, and submodule complications. The two-patch series relocates ~700 files into `lib/` while preserving internal structure, with changes primarily affecting build system files and CI workflows—no functional changes or new symbols are introduced.

Johannes Schindelin (Git for Windows) has provided a fixup patch to address a missed path adjustment in the GitHub Actions workflow, ensuring the Windows CI job can locate relocated compatibility files. This one-line change, validated by a successful CI run, resolves a build regression specific to the Visual Studio toolchain and should be squashed into the original patch before final submission. Johannes’s earlier preliminary approval for the reorganization remains intact, and the fix reinforces the series’ compatibility with downstream platforms.

The discussion continues to center on whether the structural benefits outweigh the logistical overhead, particularly during the prerelease freeze period. Junio C Hamano remains skeptical, emphasizing the disruption to in-flight patches and backporting efforts, while Patrick Steinhardt argues that the reorganization will incentivize improvements to Git’s tooling for handling file moves. Oswald Buddenhagen supports merging the change before Git 2.55, framing it as a low-risk cleanup that primarily affects the build system. No technical objections remain, but the debate over timing and coordination persists. Downstream consumers should watch whether the tooling argument gains traction or if the focus stays on logistical trade-offs.
