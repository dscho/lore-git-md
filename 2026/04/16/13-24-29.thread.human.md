Patrick Steinhardt's RFC patch series to reorganize Git's source tree by moving core library files into a new `lib/` directory continues to spark debate, with the latest discussion shifting toward practical ways to ease the transition. The series, now in its third iteration, remains a refactoring-only effort aimed at reducing root-directory clutter and enforcing clearer boundaries for Git's core library code. While the v3 update addressed Windows CI issues and refined the rationale—emphasizing that the goal is to make *non-library* files easier to locate rather than improving library file discoverability—the core concerns about workflow disruption persist.

The most notable development is Kaartic Sivaraam's proposal to add a user-facing hint to `git show` when a requested file path doesn't exist in the specified commit but appears to have been renamed. For example, if a user runs `git show HEAD:wt-status.c` after the reorganization, Git would suggest the new path (`lib/wt-status.c`) and offer a config knob (`advice.objectNameWarning`) to disable the hint. This idea directly addresses the recurring mental overhead of file moves, a pain point highlighted by Junio C Hamano and Phillip Wood. While lightweight and non-disruptive to Git's core functionality, the proposal raises questions about performance, as rename detection for hints might be too resource-intensive for a UX feature. No prototype or analysis has been shared yet, leaving its feasibility unresolved.

The debate over the reorganization itself remains polarized. Patrick Steinhardt has doubled down on the structural benefits, arguing that grouping library code enforces better coding conventions (e.g., avoiding `the_repository` or `die()` in library code). However, Junio and Phillip Wood remain skeptical, questioning whether the benefits justify the ongoing friction, especially during the prerelease freeze. Junio has suggested non-structural alternatives, such as a high-level "map" of the codebase (possibly leveraging LLMs), while Phillip Wood has endorsed the `lib/` directory in principle but doubts its practical value. Meanwhile, Johannes Schindelin and Oswald Buddenhagen support the change, prioritizing long-term code organization over short-term disruption.

The thread is now at a crossroads: the core reorganization debate is unresolved, but Kaartic's proposal offers a potential middle ground. If implemented, it could soften the impact of the `lib/` move without requiring a reversal. For now, the discussion hinges on whether such tooling improvements can address the workflow concerns raised by maintainers—or if the structural benefits of the reorganization will ultimately prevail.
