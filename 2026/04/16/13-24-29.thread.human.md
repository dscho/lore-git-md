Patrick Steinhardt’s RFC patch series (v4) to reorganize Git’s source tree by moving all `libgit.a` components into a new `lib/` directory continues to spark debate. The effort aims to reduce root-directory clutter—shrinking the number of files from ~550 to ~80—and establish a clearer boundary for Git’s core library code, but critics argue the disruption to workflows like `git log --follow` and rebasing outweighs the benefits. Johannes Schindelin has joined the discussion in strong support, framing the current disorganized state as an "ongoing burden" that justifies the one-time cost of reorganization, while dismissing concerns about persistent friction as short-sighted. However, SZEDER Gábor remains unconvinced, arguing the disruption is not one-time but a recurring mental overhead for contributors, and questioning whether the tradeoff is worthwhile without concrete tooling improvements.

The series itself is a mechanical refactoring, moving ~700 files (including core subsystems like object handling, refs, diff, and utility files like `strbuf.c`) into `lib/` while updating build systems, CI workflows, and `.gitmodules`. No functional changes or API modifications are involved. The debate hinges on whether the structural benefits—such as enforcing coding conventions like avoiding `the_repository` or `die()` in library code—justify the ongoing friction. Kaartic Sivaraam’s proposal to add a hint in `git show` suggesting renamed file paths (e.g., `lib/wt-status.c` instead of `wt-status.c`) remains a potential middle ground, though its feasibility is still under discussion.

The discussion remains polarized, with proponents (Patrick Steinhardt, Johannes Schindelin, Oswald Buddenhagen, and now brian m. carlson) emphasizing long-term codebase hygiene, while critics (SZEDER Gábor, Junio C Hamano, Phillip Wood) highlight the persistent mental overhead and lack of realistic tooling improvements. brian’s recent endorsement, while surface-level, adds weight to the pro-reorganization camp by framing the change as a necessary cleanup for contributor experience. However, the core concerns about workflow disruption and the viability of tooling fixes remain unresolved. The series is likely to remain under active debate as the next development cycle begins.
