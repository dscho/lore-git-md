Patrick Steinhardt’s RFC patch series to reorganize Git’s source tree by moving core `libgit.a` components into a new `lib/` directory continues to spark debate. The series aims to reduce root-directory clutter—shrinking the number of files from ~550 to ~80—and enforce clearer boundaries for Git’s core library code, but it comes with acknowledged downsides: disrupted `git log --follow` history, rebasing challenges for in-flight topics, and merge conflicts for downstream forks. While Patrick frames these as one-time costs, **SZEDER Gábor remains unconvinced**, arguing that the disruption is an ongoing burden that outweighs the benefits. Gábor dismisses the idea that the pain could spur tooling improvements (e.g., better rename detection) as unrealistic, questioning both the feasibility and the willingness of contributors to implement such changes.

Johannes Schindelin (Dscho) has now weighed in strongly in favor of the reorganization, countering Gábor’s objections by framing the current disorganized source tree as an *ongoing* burden that the patch would resolve. His reply draws a parallel between resistance to this change and historical skepticism toward Git itself, implying that the objections are short-sighted. While Dscho’s endorsement reinforces Patrick’s position, it does little to address the practical concerns raised by Gábor and others—such as the mental overhead of remembering file moves (e.g., `wt-status.c` → `lib/wt-status.c`) or the persistent friction in rebasing and history tracking. The debate remains polarized: proponents (Dscho, Patrick, Oswald Buddenhagen) see the reorganization as a necessary cleanup, while critics (Gábor, Junio C Hamano, Phillip Wood) prioritize minimizing workflow disruption.

The series itself is a **pure mechanical move**, relocating ~700 files (including core subsystems like object handling, refs, diff, and merge, as well as utility files like `strbuf.c` and `hashmap.c`) into `lib/` without altering symbols, APIs, or on-disk formats. Build system files (`Makefile`, `meson.build`, `CMakeLists.txt`), CI workflows, and `.gitmodules` have been updated to reflect the new paths, and a preparatory patch ensures include resolution works post-move. **Kaartic Sivaraam’s proposal**—adding a hint to `git show` to suggest renamed file paths—remains a potential middle ground, though its feasibility depends on efficient rename detection. For now, the thread remains at an impasse, with no clear consensus on whether the benefits justify the costs. The timing of the series (sent close to the upcoming release) suggests Patrick aims to land it early in the next cycle if accepted.
