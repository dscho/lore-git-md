This is a bugfix for gitk, the Git repository browser GUI. The patch addresses a race condition that occurs when changing views while gitk is still processing diffs for a large commit. The error manifests as "can't read 'treediffs(...)': no such variable" when switching views too quickly after loading a commit with many files.

The root cause is that gitk's background task queue (runq) may still be processing diff operations when a view change clears the treediffs data structure those operations depend on. The fix introduces a new runq_active counter and wait_runq_empty procedure to ensure view changes wait for pending operations to complete before proceeding.

The patch is straightforward but comes with a performance tradeoff - it makes view changes wait for all pending operations, even those that may no longer be needed after the view change. The author acknowledges this is suboptimal but couldn't find a cleaner way to selectively cancel pending diff operations. The issue has been reported before (referencing a 2013 StackOverflow post) but wasn't previously fixed in gitk.

The fix touches gitk's core task scheduling machinery, modifying how background operations are tracked and waited upon. Key changes include:
- Adding runq_active counter to track in-progress operations
- New wait_runq_empty procedure to block until queue drains
- Calls to wait_runq_empty before view changes and other operations that clear treediffs

While functional, the solution may warrant future optimization to avoid waiting for unnecessary operations during view changes. The patch demonstrates a clear understanding of gitk's Tcl/Tk codebase and provides a reproducible test case involving a repository with many files.
