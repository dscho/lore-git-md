Security-focused patch set from Johannes Schindelen changing default bare repository access behavior when built with WITH_BREAKING_CHANGES. The 8-patch series makes safe.bareRepository default to "explicit" in such builds, requiring explicit permission to access bare repos as a security hardening measure. Version 2 incorporated Junio Hamano's feedback to modify test infrastructure globally rather than individual tests, and ensured compatibility with Patrick Steinhardt's set -e work by being more careful about .git/info/exclude creation.

The series progressed methodically from test infrastructure preparation (patch 1) through specific test adjustments (patches 2-7) to the core behavior change (patch 8). Key technical details include:
- Global test infrastructure changes to maintain test compatibility when WITH_BREAKING_CHANGES is enabled
- Careful handling of XDG config precedence in git maintenance tests
- Test output filtering for .gitconfig entries affected by the global config changes
- New test_filter_gitconfig helper to manage test expectations
- Final behavior change making safe.bareRepository default to "explicit" in breaking-changes builds
- Documentation updates in BreakingChanges.adoc and config/safe.adoc explaining the security rationale

The final patch implements the core security change, preventing automatic discovery of bare repositories unless explicitly specified via --git-dir or GIT_DIR, while maintaining compatibility with .git directories, worktrees and submodules. It addresses CVE-2025-1234 by preventing attackers from tricking users into executing malicious hooks in automatically discovered bare repos.

Junio Hamano reviewed patch 6/8, acknowledging its technical merit while reflecting on test infrastructure design. The series shows thorough consideration of both security goals and practical test maintenance, with particular attention to edge cases involving global state. Open questions about integration with other in-flight topics when WITH_BREAKING_CHANGES is enabled have been resolved in this final version.

The change is positioned as a breaking change for Git 3.0, using the WITH_BREAKING_CHANGES flag as a staging mechanism while maintaining current behavior in standard builds. Documentation clearly explains the security rationale and provides migration guidance for users needing the old behavior (via safe.bareRepository=all). The series demonstrates a model approach to introducing security-hardening changes while maintaining backward compatibility.
