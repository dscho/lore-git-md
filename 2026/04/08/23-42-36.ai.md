This is a technical discussion about Git's signal handling architecture, following up on the recently merged SIGPIPE fix for parallel process execution. Jeff King (Peff) responds to Junio Hamano's observation about similar signal handler patterns in `upload-pack.c` and `fetch-pack.c` with a deeper analysis of the underlying design issues.

Peff identifies that the current sigchain_push_common() mechanism doesn't properly express the desired behavior for SIGPIPE handling, where the signal's treatment depends on whether it's being ignored. He proposes a potential solution involving a new sigchain_push_1() helper that preserves SIG_IGN states, but notes this doesn't fully address the deeper issue with start_command()'s cleanup handlers.

The core problem is that Git's signal handler push/pop paradigm breaks down when cleanup handlers are installed permanently (as with child process cleanup) while other handlers are pushed/popped temporarily. Peff sketches a more comprehensive redesign where cleanup handlers would be registered once and managed through a central dispatcher, with separate ignore-state tracking.

While acknowledging this would be a significant architectural change, Peff suggests a stop-gap approach of registering permanent cleanup handlers during program initialization to avoid the push/pop interleaving problem. He clearly marks this as future work rather than something for immediate implementation in the current release cycle.

The discussion reveals fundamental tensions in Git's signal handling design that go beyond the specific SIGPIPE case, touching on how cleanup handlers interact with temporary signal state changes across the codebase. Peff's analysis provides valuable context for future work in this area while recognizing the complexity of any comprehensive solution.
