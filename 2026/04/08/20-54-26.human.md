This is a follow-up discussion about the recently merged SIGPIPE handling fix in `run-command.c`. Junio Hamano notes that while Jeff King's patch correctly addressed the immediate issue with parallel process execution, there are two other similar patterns in the codebase (`upload-pack.c` and `fetch-pack.c`) where SIGPIPE is ignored before spawning subprocesses.

Junio raises a thoughtful question about whether these other cases should also be updated to match the new signal-handler-ordering approach, even though they currently don't use the cleanup mechanism that caused problems in the parallel case. He's weighing the tradeoff between future-proofing the code against hypothetical changes versus potentially making the code less clear for scenarios that currently work fine.

The email doesn't propose any concrete changes - it's more of a design consideration now that the core fix is merged. This shows Junio thinking ahead about consistency and maintainability, even after the immediate bug is resolved. The discussion may lead to follow-up patches if others agree the pattern should be standardized, but for now it remains an open question.
