**Thread identity**: "negotiator: implement new negotiation and restrict options" series (v3-v4), by Derrick Stolee. Type: patch series (7 patches).

**Core problem/goal**: Provide fetch/push negotiation controls for monorepo scenarios: (1) `--negotiation-include` guarantees that specified refs are always advertised even when not part of the common-object search, and (2) `--negotiation-restrict` limits negotiation to a subset of remote refs. Replaces the existing single-valued `--negotiation-tip` with a more general two-direction mechanism.

Stolee has acknowledged all issues identified by Cheetham and will produce v4 with fixes. The key open items are: (1) two bugs in patch 4/7 (documentation inaccuracy about push support at this point in the series, and a boolean-logic defect in `--negotiate-only` error handling using `||` instead of `&&`), (2) minor fixups including documentation references to old option names, a `transport-helper.c` warning string that should be made translatable, a commit-message typo (`s/tips/tip/`), and an old option reference in `send-pack.c`'s shell command, and (3) converting `builtin/pull.c` to use `OPT_ALIAS` instead of a separate `OPT_PASSTHRU_ARGV`. Stolee has confirmed a complete inventory of remaining cleanup items and will include all fixes in v4.

**Key technical details**:
- Files touched: `builtin/fetch.c`, `fetch-pack.c`, `transport.c`, `transport-helper.c`, `remote.c`, `send-pack.c`, `builtin/pull.c`, plus documentation (`Documentation/fetch-options.adoc`, `Documentation/config/fetch.adoc`, `Documentation/config/remote.adoc`).
- New/renamed symbols: internal rename of `negotiation_tips` field to `negotiation_restrict_tips` (transport layer). New `negotiation_include` and `negotiation_restrict` fields in `git_transport_options` and `send_pack_args`. Config keys `remote.<name>.negotiationInclude` and `remote.<name>.negotiationRestrict` (multi-valued, glob patterns). Backward-compatible `--negotiation-tip` retained via `OPT_ALIAS`.
- Behavior: `--negotiation-include` causes included commits to be unconditionally advertised as COMMON. `--negotiation-restrict` narrows the set of refs considered during negotiation to those matching given patterns. When no restrict patterns are given, falls back to all remote refs. Push negotiation works by `send-pack.c` shelling out to `git fetch --negotiate-only` with explicit `--negotiation-restrict=<oid>` args. Missing refs are silently ignored (best-effort); missing objects are fatal.
- Edge cases: early server stop, duplicate OID prevention, protocol capability warnings for negotiation restrictions, empty-value reset behavior for config, CLI-priority-over-config, non-smart-transport handling.

**Open questions and loose ends**:
1. **Patch 4/7 (config support) -- two bugs found by Matthew Cheetham**:
   - (a) Documentation incorrectly claims `remote.<name>.negotiationRestrict` works for "`git fetch` and `git push`" at this point in the series, but the push path in `prepare_transport()` is unreachable until patch 7 because `send-pack.c` shells out with explicit `--negotiation-tip` args, making the new `else if` branch never taken. Fix: either drop "and `git push`" from this patch's docs, or add a note that `push.negotiate` must be set for push to honor this config.
   - (b) Logic error in `--negotiate-only` error handling: the new die-check (moved from before `prepare_transport()` to after it) fires whenever `gtransport->smart_options` is NULL, even if the user did supply restrict options, because it uses `||` instead of `&&`. This gives a confusing "needs one or more --negotiation-restrict=*" message against non-smart transports. Fix: change `||` to `&&` to preserve the existing non-smart-transport error path.
2. **Patch 4/7 (consistency question)**: The `remote.<name>.negotiationRestrict` config handler treats NULL value as a reset, which is consistent with other `parse_transport_option()`-based handlers but differs from some other handlers that treat NULL as an error. Minor, possibly worth aligning.
