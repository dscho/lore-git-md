This is a follow-up in an ongoing thread about SIGPIPE handling in Git hooks, where Randall Becker reports test behavior with Jeff King's proposed fix. The thread has revealed that while the fix resolves the original pre-receive hook issue (where hooks exiting without reading input could incorrectly reject pushed references), it introduces a regression in pre-push hook execution causing apparent hangs.

Randall initially observed an indefinite hang in t5571.11 ("sigpipe does not cause pre-push hook failure") when testing the fix, but later notes the test does eventually complete successfully after a delay. This suggests the fix may introduce performance degradation rather than a true deadlock in pre-push scenarios, though the exact timing implications remain unclear.

The email confirms Jeff King's SIGPIPE handling changes work as intended for the parallel pre-receive case while revealing new edge cases in pre-push execution. The test eventually passing indicates the fundamental behavior is correct, but the delay suggests the signal handling changes may need optimization or additional safeguards for non-parallel hook contexts. This moves the discussion toward understanding the performance impact rather than correctness, with Randall's NonStop platform continuing to serve as an important test case.
