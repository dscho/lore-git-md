This is a platform compatibility discussion about the `writev()` optimization in Git's network operations, continuing from test failures in Git 2.54.0-rc1 on NonStop systems. Junio C Hamano follows up on his earlier skepticism about the optimization, now examining the implementation details more closely.

Junio realizes the code already handles short writes via `writev_in_full()`, but notes this doesn't solve the fundamental problem for platforms like NonStop where the total size of vectorized writes must be below SSIZE_MAX (52KB for 32-bit). He observes that while `write_in_full()` can transparently split large writes into smaller chunks, `writev_in_full()` lacks an equivalent mechanism to split vectorized writes without defeating the optimization's purpose of reducing allocations and calls.

The discussion highlights a deeper architectural issue: Git's packet-line protocol assumes 64KB maximums, but this conflicts with platforms having smaller SSIZE_MAX values. Junio's uncertainty suggests the project may need to choose between maintaining the `writev()` optimization (with its platform compatibility challenges) or reverting to simpler `write()` calls (with potential performance costs). His technical analysis confirms this isn't just a NonStop-specific issue but rather exposes a tension between protocol design and platform constraints that affects any system with small SSIZE_MAX values.
