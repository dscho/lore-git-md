This is a follow-up from Randall Becker reporting that Jeff King's SIGPIPE handling fix for pre-receive hooks (which successfully resolved the original NonStop case and parallel execution scenarios) introduces a new regression in t5571.11 ("sigpipe does not cause pre-push hook failure"). The test now hangs indefinitely during a pre-push hook execution, suggesting the fix may have unintended consequences in other hook contexts.

The issue appears when pushing with a simple pre-push hook that exits successfully without reading input - a similar pattern to the originally reported pre-receive case but in a different hook type. This indicates the signal handling changes may need broader validation across all hook types rather than just focusing on pre-receive scenarios.

Randall's report provides a minimal reproduction case showing the test hangs after applying the fix, with no output beyond the pack-reused line. This suggests either a deadlock in hook process management or an infinite loop in the push/hook interaction when SIGPIPE occurs in this context. The regression affects core push functionality, making it a blocker for inclusion in 2.54.0-rc2 unless resolved.

This development means the previously agreed-upon integration path (standalone patch for rc2) may need reconsideration until the pre-push interaction is fully understood. The thread now requires input from Jeff King and Adrian Ratiu to analyze whether this is a fundamental limitation of the approach or an additional edge case that can be handled within the same fix framework.
