Thread summary:

Bugfix for bundle-URI protocol implementation addressing misconfigured servers advertising invalid bundle-URI data (empty URIs). The issue caused stale packet data to remain in the read buffer during clone operations, leading to confusing "expected 'packfile'" errors. The fix modifies `get_remote_bundle_uri()` to properly drain the protocol stream by continuing to read (but not process) remaining packets after encountering an error, while maintaining error reporting.

Patrick Steinhardt provided follow-up suggestions to strengthen the patch: (1) clarify and test the distinction between explicitly requested bundle URIs (via `--bundle-uri` flag) which should fail hard versus optional URIs (via config) which should continue gracefully, and (2) verify test cases confirm expected error messages are shown for misconfigurations while still allowing operations to complete. These additions would improve documentation and test coverage around the explicit/optional behavior boundary.

Justin Tobler has now entered the discussion with a counterproposal, arguing the root issue is servers sending invalid empty bundle-URI values and suggesting a server-side fix that would prevent such malformed configurations from being advertised. He provides a concrete diff showing server-side filtering of empty bundle URIs during configuration-to-packet conversion. While acknowledging client-side resilience is valuable for backward compatibility, Justin maintains the primary fix belongs on the server. This introduces an architectural tension between client-side robustness (Toon's approach) versus server-side validation (Justin's preference).

Key technical points under discussion:
1. Server-side validation could prevent empty URIs via config filtering
2. Client error handling could better distinguish recoverable vs fatal errors
3. Current test coverage demonstrates missing/empty URI cases, though only empty URIs trigger the original bug

The thread now presents two distinct approaches to solving the misconfiguration issue, with implications for both server administrators and client behavior. The discussion remains unresolved, awaiting either Toon Claes' response to Justin's proposal or further input from other contributors. Prior feedback from Junio Hamano about handling misconfigurations has been incorporated in the current version, but the new server-side proposal may require reevaluation of the solution approach. The changes under discussion aim to improve error handling robustness while preserving bundle-URI's optional nature.
