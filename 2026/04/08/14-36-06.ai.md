This is a feature proposal for Git's fetch negotiation system, introducing a new `--must-have` option and corresponding `remote.*.mustHave` config setting. The patch series comes from Derrick Stolee, a well-known contributor with expertise in large-repository performance.

The core problem being addressed involves fetch negotiation failing in monorepos with many branches, particularly when important long-lived branches (like 'main' and 'release') get truncated from the haves list due to protocol limits. The current `--negotiation-tip` option isn't quite right for this case since it completely excludes other branches rather than prioritizing certain ones.

The proposed solution adds `--must-have` to guarantee certain refs are always included in negotiation while still allowing other refs to participate opportunistically. The series includes:
1. A test fix (likely preparatory)
2. The core `--must-have` implementation with tests
3. Config support via `remote.*.mustHave`
4. Push negotiation integration

The implementation follows the pattern of `--negotiation-tip` while solving a complementary problem. Stolee raises good design questions about naming, interaction with existing features, and whether `--negotiation-tip` should get similar config support.

This appears to be a well-motivated change targeting a real pain point in large repositories. The implementation looks thorough, with extensive test coverage and documentation updates. The proposal is particularly relevant for monorepo workflows where certain branches are more important than others but shouldn't completely dominate negotiation.
