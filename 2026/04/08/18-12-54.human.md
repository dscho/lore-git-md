This is a maintainer response in an ongoing thread about `writev()` system call compatibility issues affecting Git 2.54.0-rc1 on the NonStop platform. Junio C Hamano acknowledges Jeff King's analysis that the problem isn't related to `MAX_IO_SIZE` limitations (since packet-line operations stay within 64k bounds) but rather stems from NonStop's fundamental rejection of vectorized writes on certain descriptor types.

Junio notes that the previous implementation using `write_or_die()` with its write-looping behavior would have handled platform-specific I/O size limitations automatically. He also points out that POSIX allows `writev()` to transfer fewer bytes than requested, suggesting the current implementation may need to be more defensive in its handling of partial writes.

The email reinforces that this is a release-blocking issue affecting multiple test suites (t5310, t5326, t5327, t5608, t7700) and network operations like cloning and push/pull. While the `NO_WRITEV=Nope` workaround remains available, Junio's comments hint that a more robust solution may be needed - either making the `writev()` usage handle partial writes properly or reconsidering the optimization's tradeoffs between performance and platform compatibility.
