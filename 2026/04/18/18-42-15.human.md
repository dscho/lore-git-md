This is a technical discussion about the proposed `--reverse=before` feature for revision walks, following up on Tian Yuchen's review. The author, Mirko Faina, responds to two key points from the review.

On naming, Faina acknowledges the potential confusion with "before/after" terminology and is open to suggestions for more intuitive phrasing that better matches user expectations of getting "oldest commits" rather than thinking about internal ordering mechanics. They note the existing flags already handle ordering during traversal.

Regarding memory efficiency concerns, Faina explains the technical constraints that make it difficult to avoid loading the full reversed history - Git's commit traversal works through parent pointers in a linked-list fashion, making it impossible to efficiently get the tail commits without processing the entire history first. They suggest significant architectural changes would be needed to support bidirectional traversal.

The exchange remains constructive, with Faina receptive to improving the UX while explaining the technical tradeoffs of the current implementation. The discussion points suggest this feature may need more design iteration before finalizing, particularly around naming and whether the memory usage tradeoff is acceptable for the use case.
