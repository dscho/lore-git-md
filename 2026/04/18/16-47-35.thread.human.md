This thread continues the discussion of Mirko Faina's proposal to add a `--reverse=before` option to Git's revision walk machinery, which would reverse commits before applying limiting operations (like `-n`) rather than after. The current implementation has been technically finalized with input from Jeff King (Peff), who provided the authoritative solution for handling multiple `--reverse` flags using an enum-based state machine.

The latest exchange shows Peff considering an even more nuanced approach to the state machine that would preserve the `reverse_when` setting when toggling with bare `--reverse` flags. This would allow sequences like `--reverse=before --reverse --reverse` to return to the original `before` state rather than defaulting back to `after`. While this makes the implementation more internally consistent, Peff acknowledges it might not necessarily be clearer to users, emphasizing the need for thorough documentation of these subtle behaviors.

Meanwhile, Junio Hamano has raised conceptual questions about whether framing this as a `--reverse` variant is the most intuitive approach, suggesting it might be better understood as "applying count limits later." Mirko has defended the current design as being consistent with Git's existing documentation about commit ordering. The discussion has now shifted from implementation details to these higher-level UX considerations, with the technical consensus solid but the conceptual framing still under review. The next version of the patch will need to address both the edge case behaviors and Junio's concerns about how users will understand the feature.
