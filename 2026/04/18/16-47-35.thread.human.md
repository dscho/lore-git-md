This thread discusses Mirko Faina's proposal to add a `--reverse=before` option to Git's revision walk, which would reverse commits before applying other limiting options (as opposed to the current `--reverse` behavior that reverses after limiting). The technical implementation has been worked out through collaborative review, with Jeff King (Peff) providing key insights on option parsing and backward compatibility, and Ben Knoble contributing implementation refinements. The code changes to `revision.c` and related files are ready for submission in a v2 patch.

However, Junio Hamano has now raised deeper questions about the feature's conceptual model. While the implementation correctly handles the mechanics of when to reverse commits, Junio suggests the `--reverse=before/after` framing might not best convey the behavior to users. He probes whether describing it as "applying limits later" would be more intuitive, and examines how the feature interacts with edge cases like using `--reverse=before` without any limit. This late-stage maintainer feedback indicates that while the code is technically sound, the user-facing design may need refinement to ensure the feature fits coherently into Git's revision walk UX. The thread now awaits Mirko's response addressing these higher-level UX considerations.
