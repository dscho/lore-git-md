This is a feature patch that enhances the `--reverse` option in Git's revision walking logic. The current behavior applies reversal only after commit limiting options (like `--max-count`), which can be counterintuitive when users want to get the earliest commits first.

The patch introduces a new `--reverse=(before|after)` syntax that lets users control when the reversal happens relative to commit limiting. The key changes are:
1. Extending the `--reverse` option to accept an optional timing parameter
2. Modifying the revision walk logic to handle reversal before commit limiting when `--reverse=before` is specified
3. Adding comprehensive tests showing the new behaviors

The implementation is clean and well-tested, with clear documentation updates. The motivation is solid - the current behavior of `git log --reverse --max-count=3` returning the last 3 commits in reverse order rather than the first 3 commits is indeed unintuitive. This change makes Git's behavior match what many users would naturally expect.

The patch touches core revision walking code but the changes are focused and well-contained. The test coverage is thorough, verifying both the new `before` mode and ensuring backward compatibility with the default `after` behavior. This looks like a well-considered improvement to Git's commit traversal options.
