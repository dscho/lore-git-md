This is a test infrastructure discussion about error handling in Git's test suite. Jeff King (Peff) responds to Junio Hamano's request for a way to catch unexpected test failures without strictly enforcing `set -e` across the entire suite.

Peff explores two technical approaches to selectively monitor stderr output from test scripts. His first attempt - a separate "lint" mode that runs tests as no-ops while capturing stderr - proved too slow and incompatible with the test suite's flexible structure. His second approach redirects stderr to a file during normal test execution while preserving the original stderr (via fd7) for intentional error output. This catches typos like `test_expect_foobar` while allowing expected stderr output through the original descriptor.

The solution requires careful handling of edge cases:
- Preserving verbose/debug output to the terminal
- Ensuring test framework error messages still reach users
- Maintaining compatibility with existing test patterns
- Handling early exits via `die()`

Peff's prototype works for basic cases but reveals deeper integration challenges, particularly around test framework diagnostics that intentionally write to stderr. He proposes a compromise where fatal errors dump the accumulated stderr log before exiting, though acknowledges this creates a slight delay in error visibility.

The discussion continues the thread's theme of balancing strict error checking against test suite usability, with Peff now focusing on implementation tradeoffs rather than the original philosophical debate. His technical exploration suggests the `set -e` approach may not be the only path to catching silent test failures, offering Junio an alternative that could address his concerns about maintainer friction.
