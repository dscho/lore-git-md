This is a technical discussion about a bugfix in the fsmonitor implementation, specifically addressing an interaction between split-index and index.skipHash that causes index corruption. Johannes Schindelin provides a deep analysis of the root cause, arguing that Paul Tarjan's patch addresses a symptom rather than the underlying issue.

The core problem occurs when:
1. Scalar sets index.skipHash=true (leaving shared index OID as null)
2. A later index read skips loading the shared index due to the null OID
3. This leaves cache_nr=0 while fsmonitor_dirty bitmap references entries from the unloaded shared index

Schindelin identifies three potential fixes:
1. Make write_shared_index() generate a real OID even with skipHash
2. Fix the unconditional index reload in hn/git-checkout-m-with-stash
3. Keep the current test workaround (disabling split-index)

He strongly recommends against Paul's approach of silently skipping bitmap entries, as this could mask real filesystem changes. The discussion reveals this isn't actually an fsmonitor bug but rather an index.skipHash limitation that happens to surface through fsmonitor assertions.

This email advances the thread by shifting focus from fsmonitor-specific fixes to the broader index.skipHash/split-index incompatibility. Schindelin's analysis suggests the fsmonitor series should drop this patch and address the issue either through core index changes or by maintaining the test workaround. The technical depth and production validation of the fsmonitor implementation remain intact, with this being an orthogonal concern.
