This thread explores the challenges of generating reproducible tarballs with `git archive`, particularly for Debian packaging workflows. Simon Richter from Debian kicked off the discussion by explaining their need for verifiable tarballs, highlighting issues with commit objects, submodules, and especially the problematic `export-subst` feature that embeds non-deterministic short object IDs. brian m. carlson provided historical context about Git's previous consideration of reproducible formats, suggesting Rust might now make this work feasible.

The discussion has since narrowed to specific technical hurdles. Theodore Tso recently joined with practical insights from maintaining e2fsprogs, sharing his workarounds using explicit gzip parameters (`-9n`) to handle compression inconsistencies. He also noted timestamp variations when using tree-IDs versus commit-IDs, and platform differences in archive prefixes between GitHub and GitLab. While Tso's use of pristine-tar provides a temporary solution, it underscores the need for native Git improvements.

The core challenges are now clearly defined: making `export-subst` deterministic (Simon's primary concern), standardizing compression and timestamp handling (Tso's focus), and deciding whether to modify `git archive` or external tooling. The thread shows growing consensus that Git should provide stronger reproducibility guarantees, with Rust implementation potentially offering a path forward, though no concrete solutions have been proposed yet.
