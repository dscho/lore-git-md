Subject: git grep --only-matching shows incorrect column numbers for multiple matches on same line

Brandon Chinn reported a bug where `git grep --only-matching --column` produces incorrect column positions for multiple matches on a single line, showing positions 1, 2, 6 for "x   x   x" instead of the expected 1, 4, 8 (matching GNU grep). The issue affects Git 2.51.1 and stems from Taylor Blau's 2018 implementation calculating positions relative to previous match ends rather than line start.

René Scharfe confirmed the bug and proposed a fix modifying `grep.c` to track line start positions (`bol` pointer), with test updates in `t7810-grep.sh`. Phillip Wood validated the technical approach, confirming the fix properly calculates absolute column numbers using `cno = bol - start + match.rm_so + 1` to match GNU grep's behavior. Wood explicitly approved the fix with "That looks good, thanks for fixing it," indicating no further changes needed.

The patch includes test updates verifying correct behavior, particularly for the "mmap" test case where the second match should start at column 14. There is clear consensus from multiple reviewers (Scharfe and Wood) that matching GNU grep's output is the right approach, as the current behavior was likely an oversight in the original implementation. The change affects tools parsing `git grep --column` output for precise match locations but carries minimal risk, touching only column calculation logic while preserving other grep functionality. With Wood's approval, the fix appears ready for merging with no outstanding objections.
