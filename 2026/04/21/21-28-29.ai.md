Performance optimization follow-up regarding cherry-pick prefetch generalization.

Elijah Newren responds to Phillip Wood's review about sharing the `prefetch_cherry_blobs()` logic with `revision.c` for use in `git rebase` and other cherry-pick detection contexts. While acknowledging the technical validity of Phillip's suggestion, Elijah expresses reservations about expanding partial clone support further into this area.

The key points:
1. The prefetch logic could indeed be generalized to `revision.c` to benefit `git rebase` and `git log --cherry-pick`
2. This would involve moving helper functions from `builtin/log.c` to `patch-ids.c`
3. However, Elijah questions whether cherry-pick detection is worth optimizing in large repositories that need partial clones
4. He suggests users in such repositories might be better served by avoiding cherry-pick detection entirely (e.g., using `--reapply-cherry-picks` with rebase)
5. The current `git cherry` optimization was implemented for a specific customer use case, not as part of a broader initiative

Elijah indicates he would help review such a generalization if someone else wanted to implement it, but doesn't plan to pursue it himself. The response maintains the technical completeness of the current series while providing context about the broader design considerations.
