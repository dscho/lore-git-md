This thread addresses a bug in `git-gui` where it fails with cryptic errors when launched from bare repositories or locations without accessible worktrees. The discussion has evolved through several technical solutions, with a key safety concern emerging: allowing `git-gui` to operate in gitdirs (like `.git` directories) could lead to data corruption when `core.bare=false` but no valid worktree exists.

Shroom Moo initially proposed a strict approach (v4 patch) that blocks all gitdir launches, while Johannes Sixt (Hannes) advocated preserving compatibility with historical `.git` directory usage. Mark Levedahl then demonstrated concrete data corruption risks in Hannes' approach, strengthening the case for strict correctness.

In the latest analysis, Mark identifies deeper architectural issues in `git-gui`'s startup logic, including broken `git gui blame` functionality in gitdirs and incorrect `is_bare` checks. He proposes a comprehensive solution that would:
1. Strictly separate read-only operations (safe in gitdirs) from write operations (requiring a worktree)
2. Explicitly handle error cases rather than silently falling back
3. Restore read-only functionality while preventing dangerous write operations

The proposal would require significant refactoring but would provide clear safety guarantees. The thread now awaits maintainer input (from Junio or git-gui maintainer Johannes Schindelin) to decide between this thorough correctness-focused approach and simpler compatibility-focused alternatives. The discussion highlights the tension between maintaining legacy behavior and preventing data corruption in edge cases.
