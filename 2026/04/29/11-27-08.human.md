Bugfix for `fetch --deepen` regression in v2.54.0. Owen Stephens reports that when repeatedly running `git fetch --deepen 2` in a shallow clone, the command unexpectedly truncates history and re-shallows the repository after all commits have been fetched. This behavior is new in v2.54.0 and does not occur in v2.53.0.

The issue manifests when fetching from a local file:// repository with 4 commits, cloned initially with `--depth 2`. After two `fetch --deepen` operations successfully retrieve all commits (making the repo non-shallow), a third fetch incorrectly reverts the repository to a shallow state with only the two most recent commits. The commit suggests 3ef68ff (a commit from the v2.54.0 cycle) may be related.

The report includes a clear reproduction script demonstrating the regression between versions. This appears to be an unintended side effect of recent changes to the shallow clone machinery, where the code path for deepening fetches isn't properly detecting when the repository should remain non-shallow. The bug affects the core functionality of incremental history fetching in shallow clones.
