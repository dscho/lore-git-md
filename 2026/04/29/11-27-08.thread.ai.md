Thread summary:

Bug report and fix for `git fetch --deepen` regression in Git 2.54.0 causing history truncation in shallow clones. Owen Stephens originally reported that repeated `fetch --deepen 2` commands on a shallow clone (depth=2) would incorrectly revert the repository to shallow state after full fetch, losing previously visible commits. The regression was introduced in commit 3ef68ff (part of 2.54.0) and does not occur in 2.53.0, manifesting on ARM64 Darwin systems via incorrect toggling of `is-shallow-repository`.

René Scharfe has now confirmed the regression by reproducing it with Owen's test script and verifying that reverting 3ef68ff fixes the problem. His patch adds a regression test to t5537-fetch-shallow.sh that verifies `fetch --deepen` doesn't modify a non-shallow repository's history or shallow status, checking both the shallow status (via `rev-parse --is-shallow-repository`) and commit history (via `log --oneline`).

Earlier discussion established consensus that: (1) the 2.54.0 behavior is a regression causing data loss and must be fixed, (2) the 2.53.0 behavior (no-op in non-shallow repos) is the only logical interpretation of `--deepen`. D. Ben Knoble initially raised documentation ambiguity while Mikael Magnusson provided strong technical arguments for why `--deepen` must be a no-op in non-shallow repos. The current patch focuses on the immediate bugfix rather than documentation updates, though that remains an open secondary question. The regression test will prevent future occurrences of this issue. No maintainer response to the patch yet.
