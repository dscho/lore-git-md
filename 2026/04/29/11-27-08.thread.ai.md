Thread summary:

Bug report: `git fetch --deepen` regression in Git 2.54.0 causing history truncation in shallow clones. Reporter Owen Stephens demonstrates that after fully fetching a shallow clone (depth=2) via repeated `fetch --deepen 2` commands, an additional `fetch --deepen 2` incorrectly reverts the repository to shallow state, losing previously visible commits. The regression was introduced in commit 3ef68ff (part of 2.54.0) as it does not occur in 2.53.0. The bug manifests on ARM64 Darwin (macOS) systems and involves incorrect toggling of the repository's shallow status via `is-shallow-repository`. The report includes version bisection results and a self-contained test case showing actual data loss via `git log` output changes.

D. Ben Knoble has responded by examining the documentation, noting ambiguity in whether `--deepen` should be a no-op in non-shallow repositories. While the man page doesn't explicitly forbid the behavior, the unconditional wording about `--depth` could imply `--deepen` should have some effect regardless of shallow state. This highlights a documentation ambiguity that may need clarification independent of the regression. The behavior change between 2.53 and 2.54 remains concerning, though Knoble has not yet attempted reproduction. The discussion is now at a technical crossroads between fixing the regression versus potentially redefining expected behavior, with the data loss aspect suggesting the former is more urgent. No maintainer response or proposed fix has appeared yet.
