Thread summary:

Bug report: `git fetch --deepen` regression in Git 2.54.0 causing history truncation in shallow clones. Reporter Owen Stephens demonstrates that after fully fetching a shallow clone (depth=2) via repeated `fetch --deepen 2` commands, an additional `fetch --deepen 2` incorrectly reverts the repository to shallow state, losing previously visible commits. The regression was introduced in commit 3ef68ff (part of 2.54.0) as it does not occur in 2.53.0, with the bug manifesting on ARM64 Darwin systems via incorrect toggling of `is-shallow-repository`.

D. Ben Knoble initially raised documentation ambiguity around whether `--deepen` should be a no-op in non-shallow repositories, noting the man page doesn't explicitly forbid the behavior. Mikael Magnusson has since countered this with a strong technical argument that `--deepen` must be a no-op in non-shallow repos to prevent nonsensical behavior where a fully unshallow repository could revert to being shallow. He emphasizes the practical consequences (data loss) outweigh documentation interpretation, pointing to the original bisection showing the 2.53.0 behavior (no-op) as correct.

The discussion has now converged on two key points: (1) the 2.54.0 behavior is clearly a regression that causes data loss and must be fixed, regardless of documentation wording, and (2) the 2.53.0 behavior (no-op in non-shallow repos) is the only logical interpretation of `--deepen`'s. The remaining open question is whether the documentation should be updated to explicitly state this expectation, though this is secondary to fixing the regression. No maintainer response or proposed fix has appeared yet.
