Bug report and fix for `git fetch --deepen` regression in Git 2.54.0 causing history truncation in shallow clones. Owen Stephens originally reported that repeated `fetch --deepen 2` commands on a shallow clone (depth=2) would incorrectly revert the repository to shallow state after full fetch, losing previously visible commits. The regression was introduced in commit 3ef68ff40e (part of 2.54.0) and does not occur in 2.53.0, manifesting on ARM64 Darwin systems via incorrect toggling of `is-shallow-repository`.

Samo Pogačnik implemented the technical solution in `shallow.c`, making `get_shallow_commits()` return NULL for non-shallow cases to prevent `--deepen` from incorrectly converting full clones to shallow ones while maintaining expected behavior for shallow repositories. The implementation includes test coverage.

Junio C Hamano reviewed the final patch, requesting:
1. Use of `git show` format for patch references
2. Consideration of whether to warn when `--deepen` is used on non-shallow repos

Junio and René Scharfe subsequently agreed that:
- `--deepen` has silently been a no-op on non-shallow repos since its 2016 introduction (commit cccf74e2da)
- Any warning implementation should be in `fetch` rather than shallow-handling code
- Warnings would require a separate patch
- The core technical fix in `shallow.c` is settled

The thread has progressed from bug report through technical solution to final presentation details, with the remaining discussion focused on whether to maintain historical silent operation or add warnings for non-shallow `--deepen` usage. No new technical concerns have been raised about the core fix. Key files remain `shallow.c` (core fix) and the test file.
