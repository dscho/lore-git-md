Thread summary:

Bug report and fix for `git fetch --deepen` regression in Git 2.54.0 causing history truncation in shallow clones. Owen Stephens originally reported that repeated `fetch --deepen 2` commands on a shallow clone (depth=2) would incorrectly revert the repository to shallow state after full fetch, losing previously visible commits. The regression was introduced in commit 3ef68ff40e (part of 2.54.0) and does not occur in 2.53.0, manifesting on ARM64 Darwin systems via incorrect toggling of `is-shallow-repository`.

René Scharfe has now proposed a fix that modifies `builtin/fetch.c` to only apply `--deepen` when the repository is actually shallow (`is_repository_shallow(the_repository)`). This minimal change prevents the data loss while maintaining the established behavior that `--deepen` should be a no-op in non-shallow repositories. René notes this feels "like cheating" and suggests a more thorough fix might belong in `shallow.c`, but this solution addresses the immediate regression.

Earlier discussion established consensus that: (1) the 2.54.0 behavior is a regression causing data loss and must be fixed, (2) the 2.53.0 behavior (no-op in non-shallow repos) is the only logical interpretation of `--deepen`. D. Ben Knoble initially raised documentation ambiguity while Mikael Magnusson provided strong technical arguments for why `--deepen` must be a no-op in non-shallow repos. The current patch focuses on the immediate bugfix while leaving open the question of documentation updates and potential more architectural fix in `shallow.c`. The regression test added earlier in t5537-fetch-shallow.sh will prevent future occurrences of this issue. No maintainer response to the patch yet.
