This thread concerns a regression in `git fetch --deepen` introduced in Git 2.54.0, where repeated deepening operations on a shallow clone can incorrectly revert the repository to a shallow state, causing visible commits to disappear. Owen Stephens reported the issue with a reproducible test case showing actual data loss, particularly affecting ARM64 Darwin systems.

D. Ben Knoble initially raised questions about whether the documentation implies `--deepen` should have some effect in non-shallow repositories, suggesting potential ambiguity. However, Mikael Magnusson has since countered this view, arguing forcefully that `--deepen` must be a no-op in non-shallow repos to prevent nonsensical behavior where a fully fetched repository could revert to being shallow. Magnusson's practical example highlights how the current 2.54.0 behavior violates user expectations, while the 2.53.0 behavior (where deepening stops once unshallow) aligns with how the feature is actually used.

The discussion is converging toward treating this as a clear regression that needs fixing, with the data loss aspect taking priority over documentation debates. While the man page wording may need clarification, the consensus forming is that the 2.53.0 was correct in behavior. No patch has been proposed yet, but the technical direction is now clearer.
