This thread addresses a regression in `git fetch --deepen` introduced in Git 2.54.0, where the command would incorrectly truncate history in shallow clones by reverting the repository to a shallow state after a full fetch. Owen Stephens originally reported the issue, which was confirmed by René Scharfe using a test script. The regression stems from commit 3ef68ff40e and affects ARM64 Darwin systems, causing previously visible commits to be lost.

René has now proposed a fix that modifies `builtin/fetch.c` to only apply the `--deepen` operation when the repository is actually shallow. This simple change prevents the problematic behavior in non-shallow repositories while maintaining the established understanding that `--deepen` should be a no-op in such cases. René acknowledges that this feels like a quick fix and suggests a more thorough solution might belong in `shallow.c`, but this patch serves as an immediate remedy for the data loss issue.

The thread has already established consensus that the 2.54.0 behavior is a clear regression and that the pre-2.53.0 behavior (where `--deepen` was a no-op in non-shallow repos) is correct. While the current patch focuses on the immediate bugfix, the question of whether to update the documentation to clarify this behavior remains open. René's earlier regression test addition to t5537-fetch-shallow.sh will help prevent similar issues in the future. The patch is now awaiting maintainer review.
