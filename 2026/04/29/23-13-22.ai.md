This is a bug report about `git maintenance`'s error handling when dealing with unavailable remotes. The issue occurs when running maintenance tasks on repositories where one or more remotes are no longer accessible - the prefetch task fails with a generic error message that doesn't identify which remote caused the problem, and the operation aborts entirely rather than continuing with other remotes.

The reporter, Anselm Schüler, suggests two improvements:
1. Make the error message identify which remote failed
2. Continue processing other remotes even if one fails

They also note that when using `git-for-each-repo` (as in systemd timer setups), it would be helpful to identify which repository encountered the error, though they're unsure if this is an upstream behavior or specific to their Nix/home-manager setup.

The bug appears well-motivated - the current behavior makes troubleshooting difficult, especially in setups with multiple repositories under maintenance. The reporter indicates willingness to contribute a patch but makes no firm commitment. This seems like a straightforward usability improvement that would help users diagnose maintenance failures more easily.
