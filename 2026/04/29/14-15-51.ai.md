Bugfix for the `git subtree` command, addressing an edge case when re-adding a previously removed subtree.

The patch fixes a scenario where `git subtree split` would fail with "fatal: cache for <hash> already exists!" when a subtree is added, removed, and then re-added at the same path. The issue occurs because the split cache mechanism was treating duplicate cache entries as errors even when they contained the same value.

The fix modifies `cache_set()` in `contrib/subtree/git-subtree.sh` to silently succeed when the existing cache entry already contains the same value being written. This matches the intuitive expectation that re-adding the same subtree commit should work smoothly.

The change is well-validated with a new test case that exercises the add-remove-readd scenario, verifying that `git subtree split` now works correctly in this case. The test creates a repository with a subtree, removes it, re-adds it at the same path, and confirms the split operation succeeds.

This appears to be a straightforward and correct fix for a real edge case in the subtree command's caching mechanism. The patch follows Git's standard practices with a clear commit message explaining both the problem and solution, and includes a regression test.
