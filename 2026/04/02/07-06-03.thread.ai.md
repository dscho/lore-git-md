Christian Couder's 10-patch series refactors promisor-remote handling to enable future auto-configuration of advertised promisor remotes via URL allowlist. The first patch modified `promisor_remote_get_direct()` to prioritize server-advertised remotes over configured ones, extracting logic into `try_promisor_remotes()`. The current patch (part of the refactoring phase) optimizes the `all_fields_match()` function in `promisor-remote.c` by replacing its `in_list` boolean parameter with a direct `config_entry` pointer, eliminating redundant lookups when checking remote configurations. The function now either checks all remotes (when passed NULL) or a specific remote (when given a config_entry), improving efficiency. Clarifying comments are added to both `all_fields_match()` and `match_field_against_config()` to document behavior and prevent misuse, particularly important for upcoming auto-configuration features where remote names may differ between server ads and local config.

The series also improves warning messages when Git ignores advertised promisor remotes due to configuration mismatches or missing fields. The changes make it explicit in the warning text that the remote is being ignored, not just why. Previously, messages like "no or empty URL advertised" or "known remote but with different URL" didn't state the consequence (ignoring the remote). Now each warning clearly indicates the remote will be ignored, helping users understand the actual system behavior rather than just seeing a diagnostic. The patch touches three warning cases in `promisor-remote.c`: when a remote has no URL or an empty URL, when a remote's URL doesn't match the locally configured one, and when a server-advertised remote lacks either a name or URL.

The series maintains backward compatibility while cleaning up the subsystem, with patches 1-4 being fixes and 5-10 refactorings/cleanups. These changes are mechanical but important groundwork for planned remote configuration enhancements, following the pattern of preparing the codebase before introducing new functionality. Core promisor-remote functionality is touched without new user-facing behavior, just internal optimizations to existing configuration matching logic and improved warning messages. Subsequent patches will continue refactoring control flow and data structures (5-9) and rejecting empty names/URLs in advertised remotes (4).
