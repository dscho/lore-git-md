Here's the updated human-readable thread summary:

This thread discusses a bug where `git fetch` operations in container environments (where Git runs as PID 1) accumulate zombie processes from terminated subprocesses like `git-remote-https` and `git-index-pack`. SURA originally reported the issue, noting it appeared in Git 2.53.0. While a workaround exists using the `tini` init process, there's debate about whether Git should adapt its behavior.

Jeff King (Peff) provided a detailed technical analysis showing how Git's process handling evolved across versions: pre-2.29 used synchronous `git gc --auto` checks, 2.29-2.47 used attached `git maintenance`, and post-2.47 uses immediately-detached maintenance processes. This means modern Git versions spawn more short-lived processes that require proper reaping. Peff agrees with brian m. carlson's earlier position that using an init process is the correct solution, though he notes the current behavior represents a minor performance regression in fork frequency compared to older versions.

The core disagreement remains unresolved - whether this is purely a container configuration issue (as Peff and brian m. carlson argue) or whether Git should modify its process handling for this edge case. No patches have been proposed yet, and the exact commit introducing the regression still needs bisecting.
