RFC proposal for a **diff provider interface** (`diff-provider.h`) that establishes a unified abstraction layer for consulting alternate sources of diff hunks before falling back to Git's builtin xdiff computation. The series (11 patches, v7) introduces a repository-owned chain of providers, each queried in turn until one answers or fails, with the builtin xdiff as the terminal provider. This framework enables future extensions (e.g., content-carrying requests, additional backends) without requiring consumers to know provider implementations. The series ships two example providers: an **in-process cache** (`diff-hunks` store) and an **external process driver** (`diff.<driver>.process`), both answering by object identity alone. The goal is to unify diff/blame integration under a single interface while preserving downstream features (word-diff, color-moved, function context, `--stat`, `git blame`, `git log -L`). The RFC explicitly seeks design feedback on the framework direction, not a merge of the 11 patches as one.

**Core problem and motivation:**
The series aims to address two primary needs:
1. **Performance:** The `diff-hunks` store delivers 1.26–1.9× speedups for warmed caches (e.g., `git blame` and `log --stat` on `git.git`), reducing redundant diff computations for frequently compared blob pairs.
2. **Extensibility:** The provider interface enables future integrations with external tools (e.g., language servers, AI-assisted diffing) without requiring consumers to hardcode provider-specific logic. The current scope focuses on hunk headers (coordinates), but the framework is designed to support content-carrying requests (e.g., for patch output) in later work.

Phillip Wood’s review highlights that the RFC’s **motivation and strategic value** are not yet clearly articulated. The documentation explains the mechanics but does not answer: *What new capabilities or integrations does this unlock that aren’t possible today?* For example:
- Could this enable `git blame` to use a language-aware diff tool (e.g., one that understands syntax boundaries)?
- Does it pave the way for tighter integration with external tools (e.g., IDEs, AI-assisted code review)?
- Is the primary goal performance, extensibility, or both? If both, which is prioritized?

The review suggests that the RFC should explicitly state its long-term vision (e.g., "this enables future content-carrying requests for patch output") and provide concrete use cases to justify the complexity.

**Core infrastructure (Patches 1-2):**
- **Interface design (Patch 2):** Introduces `diff-provider.h` with two core functions:
  - `diff_provider_consult_fn`: Queries a provider for hunks given a `diff_request` struct (old/new blobs, xdiff options, flags).
  - `diff_provider_emit_fn`: Optional callback for providers to emit hunks directly (e.g., for caching).
  Providers are registered in a repository-owned chain (`repo->diff_providers`) and consulted in order until one answers or fails. The chain is built on first consultation and released in `repo_clear()`, ensuring provider state (e.g., a running process) never outlives its repository. Consumers express requests via a single `diff_request` struct and read outcomes (answered, unanswered, or failed) without naming providers, enabling transparent integration of new backends. The interface enforces hunk validation via `diff_provider_check_hunk()`: coordinates must fit `int32`, hunks must be ordered/non-overlapping, and unchanged runs between hunks must align on both sides. The first wired consumer is `git blame`'s `pass_blame_to_parent()`, whose content loads move into a fill callback that runs only when ranges are computed.
- **Internal contract:** Adds `diff-provider-internal.h` (modeled after `refs/refs-internal.h`) to define the implementor contract, including provider dispositions (answer, pass, fail, refuse) and chain composition rules. The walk in `diff-provider.c` maps these dispositions onto the public outcome set (`answered`, `unanswered`, `failed`, `refused`) and uses `BUG()` to enforce that only the computing provider fails and that it passes on a consult-only walk. Chain order carries **authority resolution**: earlier providers override later ones. Phillip Wood’s review questions the clarity of "authoritative" providers, noting that the implications of chain order are not intuitive. For example:
  - If an external process claims two blobs are identical (zero hunks), does Git trust it blindly, or does it validate the claim?
  - How does this interact with tools like `git patch-id`, which assume deterministic diff output?
  The RFC should explicitly document these trade-offs and provide examples of authoritative vs. non-authoritative use cases.
- **Documentation (Patch 1):** Adds `git-diff-provider(7)` and `gitformat-diff-provider(5)` to explain the interface, provider chain, and example backends. Clarifies that providers may be authoritative (e.g., external process) or non-authoritative (e.g., cache), and that failures degrade to the builtin diff. Documents the `diff_request` struct fields and expected behavior for providers. Phillip Wood’s review requests clearer definitions for jargon like "coordinates" (hunk offsets/lengths) and "trim-stable pairs" (blob pairs whose trimmed/untrimmed diffs match), which are not defined in existing Git documentation.

**In-process cache (`diff-hunks` store, Patches 3-6):**
- **Store design (Patch 3):** A non-authoritative cache at `$GIT_DIR/objects/info/diff-hunks` that may only reproduce the builtin diff. Keyed by `(old_blob, new_blob, xdl_opts)` and recorded only when the pair's trimmed and untrimmed diffs agree, ensuring one entry serves both blame (zero context) and stat formats (any context). The file uses a chunked binary format with a sorted index (DHIX) and hunk data segment (DHDT), plus a trailing checksum. Entries are deduplicated (identical hunk blocks share storage) and flushed atomically, merging with the existing store rather than replacing it. The reader is loaded once and cached on the object database; writing is opt-in (`GIT_DIFF_HUNKS_WRITE=1` or `diffHunks.write`), so ordinary commands read without modifying the store.
- **Warming mechanism (Patch 4):** Teaches stat output (`--stat`, `--numstat`, `--shortstat`) to record precomputed hunks into the store when writing is enabled. A warming run collects hunk coordinates in a single xdiff pass, sums counts from those hunks, and records the pair into the store. The store records only "trim-stable" pairs—those whose zero-context trimmed diff (blame) and untrimmed diff (stat) are identical—so one entry serves both formats. The warming run displays trimmed counts (matching a store-less run), while untrimmed counts are used only for stability comparison. Exclusions: `--ignore-blank-lines` (coalesces hunks differently between text-emitting and coordinate-callback paths), `-I` patterns, `--anchored`, and `-B` (shape the diff outside the key). Recording requires both sides to be valid regular files with named blobs, so working-tree sides, textconv output, and gitlinks are skipped.
- **Cache keying concern:** Phillip Wood’s review flags that the store keys entries by `(old_blob, new_blob, xdl_opts)`, storing `xdl_opts` directly. This could break the cache if Git’s internal representation of diff options changes (e.g., adding a new field). The review asks if there are plans to version the cache or garbage-collect stale entries. The RFC should address this in the documentation or implementation.
- **Stat integration (Patch 5):** Wires stat output (`--stat`, `--numstat`, `--shortstat`) to consult the provider chain before falling back to the builtin xdiff. The core change is in `builtin_diffstat()`, which calls `diff_provider_consult()` with a summing callback (`diffstat_sum_hunk_cb()`) that accumulates provided hunk counts into the diffstat entry. On an answer, the blobs were already loaded for the binary check, so the only cost saved is the diff computation itself. On an unanswered outcome, the code computes as before and, if writing is enabled, records what it computed. The request carries the pair’s object IDs and the diff options read by the exclusions; sides that are not stored blobs (working-tree files, gitlinks) have NULL IDs, so the store passes them by and the terminal provider computes them. Exclusions are handled as follows:
  - `-I` patterns, `--anchored` anchors, and break detection (`-B`) map to `DIFF_PROVIDER_DISP_STOP_NO_RECORD`, ensuring such requests are neither served nor recorded for any consumer.
  - `--ignore-blank-lines` is excluded before consulting because it coalesces hunks differently between text-emitting and coordinate-callback paths, so a served answer would not match a store-less run’s output.
  - A `log -L` range-scoped stat neither reads nor records, as the line-range filter computes it as before.
- **Blame integration (Patch 6):** Wires `git blame` to consult the provider chain via `pass_blame_to_parent()`. The store is consulted only for plain blob-pair diffs (no reverse blame, ignored revisions, textconv, or working-tree/`--contents` pseudo-commits). Requests with `-I` patterns or anchors bypass the store entirely. Blame’s default `xdl_opts` now derive from `DIFF_HUNKS_DEFAULT_XDL_OPTS`, ensuring key alignment with stat warming runs. `--show-stats` reports store hits/misses via consultation counters. Test coverage (355 new lines in `t4220-diff-hunks.sh`) verifies:
  - Output parity for plain, `--porcelain`, and `--incremental` blame.
  - Hit/miss accounting across warming runs.
  - Bypass conditions: `-w`, indent heuristics, `--reverse`, textconv, `-M`/`-C`, `--ignore-rev`, `--contents`, and rename/merge handling.
  - Corruption recovery (truncated store, corrupt signature, over-claimed chunk count, zero-hunk record).
  Performance tests (`t/perf/p4218-diff-hunks.sh`) show a ~1.26× speedup for blame on `git.git` with a warmed store.
- **Format and recovery:** On-disk format documented in `gitformat-diff-hunks(5)`. Lacks fsck integration or expiry; recovery relies on `git diff-hunks clear` and re-warming. Corruption (e.g., checksum mismatch, malformed chunks) is detected on read and handled gracefully (fallback to builtin diff). The `git diff-hunks verify` command checks the checksum, chunk table, sort order, and every entry's hunk sequence; `git diff-hunks clear` removes the file.
- **Performance:** On `git.git`, a warmed store speeds up `log --stat -5000` by ~1.9x and `git blame` by ~1.26x, with hit rates of 54-74% depending on the file. The store serves blame at zero context and stat formats at any `-U`.

**External process provider (`diff.<driver>.process`, Patches 7-11):**
- **Plumbing (Patch 7):** Adds the `process` field to `struct userdiff_driver` and teaches the config parser to populate it from `diff.<driver>.process`. This field names the long-running hunk provider process for a given diff driver but is not yet used by the consult logic. The change is mechanical: two lines in `userdiff.h` to declare the field and its owned string, and seven lines in `userdiff.c` to parse the config key and manage ownership. This plumbing enables the external process provider introduced in later patches.
- **Protocol (Patch 11):** A long-running pkt-line protocol (version=1, capability=hunks) over stdin/stdout. The handshake negotiates version/capability, then per-file requests send object names (`old-oid`/`new-oid`) and xdiff options. The tool responds with hunk lines (`hunk <old_start> <old_count> <new_start> <new_count>`) and a status packet (success/error/abort). Git validates hunks for bounds, overlap, and per-gap alignment before feeding them into xdiff. On error/abort, Git falls back to the builtin diff for that file or the entire session, respectively. The protocol is **identity-only**: only object names are sent, enabling providers to answer before any blob is read (e.g., for caching or fetching blobs themselves). The process is **authoritative**: its answers may differ from the builtin diff and override the `diff-hunks` store. A pair the process answers is never recorded into the store, ensuring the store holds only builtin results.
- **Portability fix (Patch 10 + Junio's fix):** Corrects a type mismatch in `blob_line_cap()` (`diff-process.c`) where an `unsigned long` was used to store a blob size, breaking the build on platforms where `size_t` differs from `unsigned long` (e.g., 32-bit systems and 64-bit Windows). The fix replaces `unsigned long size` with `size_t size`, aligning the variable with the type expected by `odb_read_object_info_extended()`’s `sizep` field. Junio applied this patch on top of the series in his `seen` branch, resolving the `-Wincompatible-pointer-types` warning and ensuring the external process provider works across all supported platforms. The change is purely mechanical and does not affect functionality, as the subsequent bounds check (`size > INT32_MAX`) remains valid.
- **Key refinements from v6:**
  - **Identity-only requests:** The protocol sends only object names (no file content), enabling providers to answer before any blob is read. This suits caches or processes that fetch blobs themselves (e.g., via `git cat-file --batch`).
  - **Per-command opt-in:** Consulting is opt-in per command (like `textconv`), with failures degrading to the builtin diff. Porcelain commands (`git diff`, `git log`, `git blame`) allow it by default; plumbing commands (e.g., `diff-tree`) forbid it unless explicitly enabled.
  - **Gating:** Options the process is never told about (e.g., whitespace-ignoring flags, `--ignore-matching-lines`, `--anchored`, or a forced diff algorithm) bypass the process entirely. `--diff-process`/`--no-diff-process` control it independently of `--ext-diff`.
  - **Forward-compatible design:** Tools ignore unknown request keys; Git ignores unknown trailing fields on hunk lines.
  - **Subprocess lifecycle:** Managed via the provider chain, ensuring the process is launched on first use and terminated with the repository. A failed process is retained in the pool to avoid retries.
  - **Error handling:** Protocol errors (malformed packets, unrecognized status, or process crashes) disable the process for the remainder of the command, falling back to the builtin diff. Semantically invalid coordinates (e.g., overlapping hunks) skip only the affected pair while keeping the process alive.
- **Subprocess API refinements (Patches 10-11):**
  - **Patch 10:** Adds `subprocess_read_status_gently()` to `sub-process.c` and `sub-process.h`, a gentle variant of `subprocess_read_status()` that returns -1 instead of dying on protocol errors (malformed length headers, truncated packets, or empty packets where a status line or flush is expected). This is essential for the diff process provider, which treats its external process as optional: any protocol error must degrade to the builtin diff rather than abort the command. The existing `subprocess_read_status()` and its callers are unchanged, preserving fatal behavior for required subprocesses like filters.
  - **Patch 11:** Extracts process lifecycle management from hashmap management in `sub-process.c`, introducing `subprocess_start_command()` and `subprocess_stop_command()` as lower-level primitives. This decouples the subprocess API from the global hashmap, allowing the diff process provider to manage its own process pool with custom membership rules (e.g., retaining failed commands to avoid retries). The change is mechanical: `subprocess_start()` and `subprocess_stop()` become thin wrappers around the new `_command` variants. No behavior changes; this is purely about decoupling concerns.
- **Integration (Patch 11):** Wires `git blame` and the summary formats (`--stat`, `--numstat`, `--shortstat`) to consult the external process via the provider interface. The external process is consulted after the `diff-hunks` store but before the builtin xdiff, enabling authoritative answers to override the cache. A `status=success` response with zero hunks asserts the blobs equivalent, omitting the pair from the stat or passing the whole commit through in blame. Patch output and `git log -L` range tracking remain builtin, as the protocol currently lacks content-carrying requests.

**Documentation clarification:**
- **Scope of external diff drivers:** A documentation patch updates `gitattributes(5)` to explicitly state the limitations of traditional external diff drivers (pre-`diff-provider` interface). These drivers *only* replace textual patch output and do not integrate with Git's builtin features like word diff, function context (`-W`), `--color-moved`, or syntax coloring. Summary formats (`--stat`, `--numstat`, `--shortstat`, `--dirstat`), `git blame`, and `git log -L` do not invoke external drivers at all and continue using the builtin diff. This clarification underscores the motivation for the `diff-provider` interface, which aims to unify and extend how external diff sources interact with Git's full feature set.
