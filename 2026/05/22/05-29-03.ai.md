This is a review response from the Git maintainer on the RFC proposal for `diff.<driver>.process`, a mechanism to let external tools inject diff hunks into Git's diff/blame pipelines.

Junio Hamano raises several key points about the proposal. He notes that for simple content normalization (like whitespace ignoring), the existing `textconv` mechanism would suffice, suggesting the real value lies in enabling structural/ast-based diffs while preserving original content display - a distinction that should be clearer in the documentation.

The maintainer expresses concern about the implementation complexity and performance impact, particularly for `git blame` which would require a subprocess roundtrip per commit. While acknowledging the potential value for AST-aware diff tools, he seems hesitant about the tradeoffs, ending with an ambivalent "I dunno" that suggests the series may need more justification or optimization before he'd be comfortable merging it.

This feedback indicates the proposal, while technically sound, needs to better articulate its unique value beyond existing mechanisms and address performance implications for intensive operations like blame. The maintainer's neutral-to-skeptical tone suggests the series may require revisions or stronger motivating use cases to progress.
