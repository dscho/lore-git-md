Bugfix discussion for `git log --follow` behavior with merges. Jeff King (Peff) weighs in on Miklos Vajna's patch to improve rename detection across merge parents, particularly for subtree merges.

Peff agrees with Junio's earlier assessment that `--follow` is fundamentally limited when dealing with merges, since it can only follow one path at a time. While the patch makes the behavior more consistent with `git blame --follow`, Peff questions whether this actually improves things - when a file has different names on different sides of a merge, choosing any single path means potentially missing history from the other side.

The review suggests exploring whether Git's existing history simplification flags (which use TREESAME to prune uninteresting parents) could provide a better solution, though Peff notes uncertainty about how this interacts with `--follow`. The core concern is that the patch might make some cases worse by changing which path gets followed, rather than solving the underlying limitation.

This is a substantive review that engages with the technical tradeoffs, though Peff doesn't reach a firm conclusion about whether to accept the patch. The discussion now awaits input from Elijah Newren (merge expertise) to help evaluate the change's impact on merge semantics.
