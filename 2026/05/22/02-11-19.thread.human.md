This thread is an RFC proposing a **diff provider interface** that lets Git consult alternate sources for diff hunks before falling back to its built-in xdiff engine. The series (11 patches, now v7) introduces a repository-owned chain of providers, with two examples: an in-process cache (`diff-hunks` store) and an external process driver. The goal is to unify diff and blame integration under a single interface while preserving features like word-diff, color-moved, and function context. The RFC explicitly seeks design feedback on the framework, not a merge of the patches as-is.

The core motivation is twofold: **performance** (the `diff-hunks` cache delivers 1.26–1.9× speedups for warmed runs) and **extensibility** (enabling future integrations with external tools like language servers or AI-assisted diffing). Phillip Wood’s review highlighted that the RFC’s long-term vision isn’t clearly articulated—what new capabilities does this unlock that aren’t possible today? For example, could it enable `git blame` to use a language-aware diff tool, or pave the way for tighter IDE integration? The series currently focuses on hunk headers (coordinates), deferring content-carrying requests (e.g., for patch output) to later work.

The infrastructure is technically complete. The interface (`diff-provider.h`) defines a unified `diff_request` struct and provider chain, with robust validation for hunk ordering and alignment. The `diff-hunks` store (Patches 3–6) uses a chunked binary format at `$GIT_DIR/objects/info/diff-hunks`, warmed during stat output (`--stat`, `--numstat`) and consulted by `git blame`. The external process provider (Patches 7–11) adds a long-running pkt-line protocol for authoritative answers, with opt-in per command and graceful fallback on errors. Junio Hamano recently fixed a **platform compatibility bug** in the external process provider, replacing an `unsigned long` with `size_t` to align with Git’s updated `object_info` API, ensuring the code builds on 32-bit systems and 64-bit Windows.

Key open questions revolve around Phillip Wood’s feedback: How should the RFC clarify its strategic goals (performance vs. extensibility)? What are the implications of "authoritative" providers (e.g., can an external tool override Git’s diff output)? And how will the cache handle future changes to `xdl_opts`? The series is ready for design feedback, after which it will split into separate topics for the interface, `diff-hunks` store, and external process provider. No merge decisions have been made yet.
