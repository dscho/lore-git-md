Bugfix and performance discussion around ALLOC_GROW overflow safety.

Jeff King (Peff) responds to René Scharfe's concern about missing overflow checking in alloc_nr(), the helper used by ALLOC_GROW. While acknowledging the theoretical risk, Peff argues the current implementation is practically safe due to two factors: the growth factor (3/2) makes overflows implausible on both 64-bit and 32-bit systems, and the fallback to the requested size when growth would be smaller prevents buffer overflows even if arithmetic overflow occurred.

The response reveals an important design consideration in Git's memory allocation patterns - the tradeoff between theoretical correctness and practical safety. Peff notes that while adding overflow checking would be ideal, he had previously avoided it due to performance concerns. With René's work showing compiler optimizations can maintain speed while adding safety, this may be the right time to implement more rigorous checking.

This exchange highlights the careful balance Git maintainers strike between robustness and performance. The discussion now centers on whether to:
1. Accept the current "good enough" state given real-world constraints
2. Add overflow checking to alloc_nr() as part of René's broader refactoring
3. Consider deeper changes to the ALLOC_GROW interface to bake in safety

The thread continues to evolve from a specific optimization into a fundamental discussion about memory safety patterns in Git's core.
