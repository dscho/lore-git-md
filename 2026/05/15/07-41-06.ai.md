This is a technical discussion thread about HTTP protocol handling in Git, specifically around the security and efficiency of dumb HTTP clones versus smart protocols.

Patrick Steinhardt chimes in on Jeff King and Junio Hamano's exchange about the dumb HTTP walker's vulnerabilities and potential deprecation. He suggests that packfile URIs could offer a middle ground - allowing efficient static file serving while using the smart protocol. The key insight is that packfile URIs could theoretically match dumb HTTP's server-side efficiency by letting clients fetch pre-generated packfiles directly.

However, Patrick notes the current security implications: `fetch.uriProtocols` defaults to empty for good reason, as unrestricted packfile URIs could enable server-side redirect attacks. He floats the idea of a more secure default that would only allow same-host packfile URIs, which could make this approach viable for broader use.

This is not a patch submission but rather a speculative design discussion. The conversation builds on the context of the recently accepted `http-walker.c` bugfix while exploring longer-term protocol evolution. The technical tradeoffs mentioned (server efficiency vs security) are relevant to any future work in this area, though no concrete proposals are made here.
