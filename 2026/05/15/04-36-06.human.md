Performance optimization and safety discussion for Git's memory allocation patterns.

Jeff King (Peff) weighs in on René Scharfe's proposal to add overflow checking to `alloc_nr()`, the helper function used by `ALLOC_GROW` for memory allocation growth calculations. While acknowledging the theoretical risk, Peff provides practical perspective on why the current unchecked implementation has been acceptable:

1. The 3/2 growth factor means overflows would only occur with impractically large buffers (approaching 1/3 of address space on 64-bit systems)
2. Even if overflow occurred, the fallback to using `nr` directly would result in slower allocation rather than buffer overflow
3. Most callers compute `nr` with simple increments unlikely to overflow

Peff sees René's work on compiler intrinsics for overflow checking as an opportunity to properly harden this code while maintaining performance benefits. The discussion remains focused on balancing theoretical safety with real-world constraints, with both contributors bringing complementary perspectives - René's thoroughness in addressing edge cases and Peff's pragmatic understanding of Git's actual allocation patterns. This exchange helps ground the broader infrastructure changes in concrete performance and safety tradeoffs.
