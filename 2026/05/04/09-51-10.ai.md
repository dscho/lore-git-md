This is a bugfix for `git clone --dissociate` that addresses a race condition with commit-graph handling during the checkout phase. Jeff King (Peff) identifies the root-causes the issue reported earlier where checkout fails with "unable to parse commit" errors when using a reference repository with `--dissociate`.

The problem occurs due to premature invalidation of commit-graph data during the clone sequence:
1. Commit objects are initially loaded from the reference repo's commit-graph with lazy-loaded tree pointers
2. The `--dissociate` step closes the reference repo's object database, discarding the commit-graph cache
3. When checkout later requests the tree, the cached position is gone but the tree wasn't fully loaded

The fix modifies `repo_get_commit_tree()` to fall back to parsing the raw commit object when graph data is missing, rather than failing. This matches the behavior theorized in an earlier discussion but now confirmed by the reproducible case. The patch includes both the technical explanation and a workaround (`-c core.commitGraph=false`) for users awaiting the fix.

This is a subtle interaction between the commit-graph optimization and the object store lifecycle during clone operations. The fix preserves the performance benefits of commit-graph while handling the dissociation case correctly. The change is contained to the commit object handling layer and doesn't affect other parts of the clone machinery.
