AI thread summary (updated):

Thread identity: Bug report about repository corruption from concurrent `git maintenance run --detach` operations due to broken lock handling in daemonized mode (regression in v2.54 via commits a6affd3343 and 452b12c2e0). Continued architectural debate between comprehensive tempfile-ownership fix and targeted lockfile-only fix. Jacob Keller concurs with Jeff King's latest refinement.

Core problem: When `git maintenance run --detach` forks, the parent process's atexit handlers (including tempfile cleanup) run in the parent, while the child continues maintenance work still holding references to those tempfiles. This can cause repository corruption when the parent exits and releases locks that the child still needs, particularly with geometric repacking introduced in v2.54.

Current status: Jeff King (Peff) has clearly endorsed Taylor Blau's comprehensive approach (transferring *all* tempfile ownership from parent to child during daemonization) over Patrick Steinhardt's narrower proposal (transferring only lockfiles via a new `lock_file_reassign_owner()` function). Peff's latest review argues the fix should be baked into `daemonize()` itself as an automatic mechanism, not left as a per-caller responsibility. Peff has now offered a concrete refinement for Taylor's implementation: have the parent reassign ownership to "0" (no owner) before `fork()`, then reclaim ownership if the fork fails. This eliminates the risk of double-delete while keeping the only bad case as nobody cleaning up if the child dies before claiming ownership -- an unlikely and minimally harmful outcome. Jacob Keller has offered lightweight concurrence with this refinement, noting that the worst-case outcome (a stale lock file left behind) is already an existing risk regardless.

Key technical details: Peff makes two architectural arguments for the broader scope:
1. The problem is general -- any cleanup handler running in the parent after fork() while the child still holds references is a lurking risk; lockfiles are just the form the bug currently takes.
2. The existing workaround in `git gc --detach` (manually dropping and reacquiring locks across the fork boundary) confirms this is a missing infrastructure layer.
3. Baking tempfile handling into `daemonize()` is future-proof and naturally handles Windows (where `daemonize()` is a no-op and never switches PIDs).
4. Peff's "assign to 0 before fork" refinement makes the ownership handoff atomicity race harmless: the worst case is a stale lock that goes uncleaned, never a double-delete.
