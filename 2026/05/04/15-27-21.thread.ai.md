Thread identity: Bug report about Git's resource usage exceeding configured limits during `git add` and `git commit` operations, now understood to involve the maintenance subsystem.

Core problem: Git's newer `git-maintenance` subsystem operates independently of traditional `gc.auto` settings, leading to uncontrolled resource consumption (CPU threads, disk space) and potential repository corruption from concurrent repacks. Jeff King (Peff) has identified the root cause in maintenance behavior rather than pack-objects configuration.

Key technical details:
- Maintenance operations use `maintenance.auto` rather than `gc.auto`
- Each maintenance-invoked `pack-objects` gets its own thread allocation
- No locking prevents concurrent maintenance runs
- Reproduction case demonstrates this can corrupt repositories
- Affects Git 2.51.0 on Linux 6.17 with glibc 2.42

Current status:
- Issue confirmed as maintenance subsystem behavior rather than configuration parsing bug
- Two specific design issues identified:
  1. Should `maintenance.auto` respect `gc.auto` for backward compatibility?
  2. Should background maintenance implement locking to prevent concurrent runs?
