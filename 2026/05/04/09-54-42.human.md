This is a follow-up to Jeff King's earlier bugfix for `git clone --dissociate` failures. He notes an ironic workaround - moving the dissociation step to the very end of the clone process would avoid the commit-graph race condition, since no further object access would occur after the reference repository is closed. 

However, he points out this is merely masking the underlying issue rather than fixing it, as the bug could still affect other code paths that call `odb_close()`. The proposed solution from his previous email (making `repo_get_commit_tree()` more resilient when commit-graph data disappears) remains the proper fix, while this observation about timing highlights how subtle the interaction is between object store lifecycle and commit-graph optimizations.

The email reinforces that this is a real bug with a clear reproduction case, and that while there are multiple ways to avoid it, the core issue needs addressing at the commit-graph access layer. This follow-up helps frame the discussion for reviewers considering whether the fix should be backported to maintenance releases.
