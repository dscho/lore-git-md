This thread has uncovered serious issues with Git's maintenance operations, particularly around resource usage and repository corruption risks in `git maintenance run --detach`. Jeff King (Peff) identified the root cause: a regression in v2.54 where geometric repacks run without proper locking in auto mode, combined with broken locking patterns during daemonization that can lead to concurrent repacks corrupting repositories. The discussion has expanded from technical analysis to include UX concerns about misleading documentation that claims maintenance is "safe" while the implementation allows corruption in auto mode.

Taylor Blau has now moved the conversation forward with a concrete solution proposal. His patch introduces a new `reassign_tempfile_ownership()` function to properly handle lock file ownership during daemonization, preventing the parent process from prematurely unlocking resources the child still needs. While more complex than simply reverting the problematic commit, Taylor argues this properly fixes the underlying issue rather than just making corruption less likely. The patch is contained to tempfile handling code, touching only a few files.

Key questions remain about whether this solution is appropriate for the upcoming v2.54.1 stable release or if it should wait for a later version.
