Maintainer response rejecting the `--track=fetch` feature on philosophical grounds.

Junio C Hamano reiterates his fundamental objection to automating remote ref updates during branch creation, arguing that the proposed convenience feature conflicts with Git's workflow principles. While acknowledging the technical improvements in v5 (which folded the functionality into `--track` rather than adding a separate flag), he maintains that:

1. Calling a non-fetched commit "wrong" is misleading - distributed workflows inherently involve working with potentially stale references
2. The commit message's workflow description remains unclear, and he suggests a complete rewrite to better explain the feature
3. The core philosophical disagreement persists: Git expects users to verify remote state explicitly before creating branches

The response indicates the technical refinements in v5 don't address the maintainer's higher-level concerns about workflow design. Junio's suggested rewrite of the commit message shows how he believes the feature should be framed, but notably doesn't withdraw his objection to the concept itself.

This appears to be the thread's likely conclusion point unless the author can present new arguments about why this automation belongs in Git's core workflow model despite the maintainer's stated principles. The exchange highlights how Git project sometimes prioritizes workflow philosophy over user convenience, even for well-implemented features.
