This thread explores how Git handles fetches when a commit that was previously tagged gets replaced by a different commit under the same tag. Jens Tröger initially observed that fetching an old commit (dda8db1) that was once tagged 1.20.0 resulted in FETCH_HEAD showing the original SHA while the working tree contained a different commit (fda7769) now bearing that tag.

Chris Torek provided a detailed technical explanation of Git's immutable object model, clarifying that "rewriting" history actually creates new commits while leaving old ones intact. He emphasized that tags are meant to be stable references, unlike branches, and that the observed behavior stems from fundamental Git design rather than being fetch-specific. While this explains the general principles at play, the exact mechanism connecting the old and new commits during fetch operations remains an open question. The discussion highlights that tag rewriting after publication is generally discouraged, as it can lead to this kind of confusion. The thread currently stands with a solid technical foundation but without resolution of the specific fetch behavior that prompted the original question.
