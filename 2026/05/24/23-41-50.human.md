This is a question about Git's behavior when fetching objects that have been force-pushed (history rewritten) in the remote repository.

Jens Tröger observes that when fetching a specific commit by SHA (dda8db1) that was previously tagged as 1.20.0 but has since been force-pushed to a new SHA (fda7769), Git somehow resolves the fetch to the new commit despite explicitly requesting the old one. The key observations are:
- The fetch operation reports success with the old SHA in FETCH_HEAD
- But checking out FETCH_HEAD lands at the new SHA
- The HEAD file shows the new SHA while FETCH_HEAD still references the old one

This appears to be Git's mechanism for handling rewritten history - when it detects that a requested object has been replaced (likely through the advertised refs showing the tag now points elsewhere), it transparently provides the replacement. The exact mechanics of how this resolution happens aren't clear from the email, and Jens is asking for clarification on both the behavior and how to manually trace this connection.

The question touches on deep Git internals around object transfer protocols and history rewriting detection. A response would likely need to cover how the protocol v2 fetch negotiates objects and how Git handles the case where a requested object is known to have been replaced on the server.
