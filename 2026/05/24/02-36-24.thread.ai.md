Thread identity: Shell completion patch series (v3) modifying path completion behavior for dotfiles across all Git commands, authored by Zakariyah Ali.

Core problem: Git’s path completion currently shows dotfiles (e.g., `.gitignore`) by default, deviating from standard shell completion behavior. The series aligns Git’s completion with shell conventions by hiding dotfiles unless explicitly requested with a leading dot (e.g., `git rm .`), while preserving explicit dotfile access.

Current status: Series is at v3 but requires restructuring. The original v3 proposed a two-patch series: the first patch implemented dotfile hiding for `git rm`, `git mv`, and `git ls-files` by introducing a `hide-dotfiles` parameter in `__git_index_files`; the second patch extended this behavior to all path completion contexts by making dotfile hiding the default in `__git_index_files` and removing the `hide-dotfiles` parameter. Junio C Hamano has now rejected this structure, requesting a cleaner two-patch progression: (1) refactor the AWK script for readability without changing behavior, and (2) implement dotfile hiding on top of that refactored base. The series is now blocked on addressing these structural and clarity concerns.

Key technical details:
- `__git_index_files` helper is the focal point for dotfile filtering logic.
- AWK processing filters dotfiles after path dequoting; the current implementation duplicates logic across callers.
- All invocations of `__git_complete_index_file` must be updated to match the new API (no `hide-dotfiles` flag).
- Test suite (`t/9902-completion.sh`) verifies default hiding and explicit dot completion for all commands; resolves 2013 TODO comments.
- Files touched: `contrib/completion/git-completion.bash`, `t/9902-completion.sh`.
- New/renamed symbols: `__git_index_files` (signature to be simplified), `__git_complete_index_file` (callers to be updated).

Open questions:

- **Clarity**: How to make it obvious which callers should hide dotfiles and which should not, and document this design decision in the cover letter.
- **Documentation**: Whether the behavior change requires explicit documentation (minor concern; the change is self-documenting via shell conventions).
