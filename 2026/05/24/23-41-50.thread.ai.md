Subject: Git fetch behavior with rewritten commits under same tag

Core problem: Understanding how Git resolves fetches when a commit SHA (dda8db1) that was previously tagged (1.20.0) gets replaced by a different commit (fda7769) under the same tag, yet Git still associates them during fetch operations.

Current status: Chris Torek explained Git's immutable object model and tag semantics. Junio C Hamano has now identified grafts as a potential explanation for the observed behavior, suggesting this may be a local configuration artifact rather than core Git behavior.

Key technical details:
- Original commit dda8db1 was tagged 1.20.0
- Remote repository rewrote history, now has fda7769 as 1.20.0
- Fetching dda8db1 results in FETCH_HEAD showing original SHA but working tree containing fda7769
- Git objects are immutable - rewrites create new objects while old ones remain
- Tags are meant to be stable references (unlike branches)
- FETCH_HEAD is temporary and gets overwritten
- GC keeps old objects around temporarily after rewrites
- Legacy .git/info/grafts mechanism could explain commit substitution behavior
- Grafts were superseded by replace-refs but may still be in use

Open questions:

- Practical implications of tag rewriting after publication
- Whether this is intended behavior or potentially problematic
