This is a technical discussion about improving the safety of Git's ALLOC_GROW macro, continuing from earlier exchanges between René Scharfe, Jeff King (Peff), and Johannes Sixt (Hannes). Peff responds to Hannes' suggestion of modifying ALLOC_GROW to take a pointer to the allocation counter, which would enforce size_t usage.

Peff acknowledges the theoretical benefits of Hannes' approach for type safety but identifies practical challenges: converting ~200 call sites would be invasive, and some cases rely on negative values that size_t can't represent. He also notes a subtle risk where fixing allocation overflow could mask overflow issues in the "nr" (element count) parameter, potentially leading to buffer underflows.

The discussion remains focused on balancing safety improvements against the real-world impact of changes to this core memory allocation primitive. Peff's analysis suggests that while Hannes' pointer-based approach has merit, it would require careful auditing of each caller to avoid introducing new edge cases. This continues the thread's substantive technical debate about how to best harden Git's infrastructure while maintaining compatibility with existing usage patterns.
