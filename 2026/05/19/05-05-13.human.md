This is a bugfix addressing an edge case in Git's commit-graph handling. Jeff King (Peff) identifies a rare but problematic scenario where a commit loaded from the commit-graph fails to find its associated tree after the graph file is closed, particularly affecting `git clone --dissociate`.

The issue stems from lazy-loading of tree objects introduced in 2018 (commit 7b8a21dba1). When commits are loaded from the graph, their trees aren't immediately instantiated, creating a dependency on the graph file remaining open. The patch makes `repo_get_commit_tree()` more robust by falling back to reading the full commit object when the graph data is unavailable, similar to what would happen without the graph optimization.

The fix includes a new test case that reproduces the failure by:
1. Creating a repo with a commit-graph
2. Cloning with `--dissociate` (which closes the graph)
3. Verifying the checkout succeeds despite the graph being unavailable

The solution adds some overhead for corrupted commits (which would need repeated disk reads), but this is deemed acceptable given corruption should be rare. Peff considered but rejected an alternative approach of pre-loading all trees at graph-close time, as it would do unnecessary work in most cases.

This fixes real-world cases reported by users where `git clone --dissociate` would fail with "unable to parse commit" errors after successfully completing the clone. The bug had existed since 2018 but became more noticeable as commit-graph usage increased.
