This is a bugfix addressing an edge case in Git's commit-graph handling. Jeff King (Peff) identifies a rare but problematic interaction between lazy-loading of tree objects from commit-graphs and the `--dissociate` option in `git clone`.

The issue occurs when:
1. A commit is loaded from a commit-graph (lazily, without its tree)
2. The graph file is closed (as happens during `--dissociate`)
3. Later code tries to access the commit's tree via `repo_get_commit_tree()`

The patch adds a fallback path that reads the commit object directly from disk when the graph-based lookup fails, parsing just enough to find the tree OID. This matches what would happen if we hadn't used the graph at all. The solution is robust against various failure modes and doesn't require complex coordination between subsystems.

The fix comes with a new test case that reproduces the failure by:
1. Creating a repo with a commit-graph
2. Cloning it with `--reference` and `--dissociate`
3. Verifying the checkout succeeds

This is a well-crafted fix from a trusted contributor, addressing a real (if rare) issue with clear reproduction steps and test coverage. The commit message thoroughly explains the problem space and rationale for the chosen solution over alternatives.
