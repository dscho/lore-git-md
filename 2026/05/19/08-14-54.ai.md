This is a follow-up from Junio Hamano on Miklos Vajna's `git log --follow` bugfix patch. Junio provides deeper technical context about why the `--follow` feature has inherent limitations when dealing with merge commits, explaining that it was fundamentally designed for linear history traversal.

The core issue is that `--follow` tracks a single pathname at a single point in history, which breaks down at merges where a file may have different names in different branches. Junio illustrates this with a diagram showing how the traversal can lose track of a file if it switches to following a different pathname in one branch while ignoring the same file under its original name in another branch.

Junio makes clear that while Miklos's patch may improve the specific subtree merge case, it doesn't address the fundamental design limitation of `--follow`. He indicates this is why he hasn't prioritized reviewing the patch - not because it's wrong, but because it's solving a narrow case of a feature that has known, broader limitations.

This response shifts the conversation from "does this patch work?" to "is this the right direction given `--follow`'s inherent constraints?" It suggests reviewers should consider whether piecemeal fixes to `--follow` are worthwhile or if a more fundamental redesign would be needed to properly handle merge cases. The ball is back in Miklos's court to either find reviewers who see value in the incremental improvement or to reconsider the approach.
