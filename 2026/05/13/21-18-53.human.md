This is patch 11/13 in Derrick Stolee and Taylor Blau's v4 series to make `--path-walk` work with `--filter`. It adds support for the `tree:0` filter, and it is the most important patch in the series from a correctness standpoint -- it fixes the bug that the cover letter says Taylor Blau "correctly smelled" in v3.

The `tree:0` filter tells Git to emit only commits and tags, skipping all trees and blobs. The integration with path-walk is conceptually simple: when the filter requests `tree:0`, set `info->trees = 0` and `info->blobs = 0`. The existing path-walk machinery already checks those flags in several places to decide whether to enumerate tree objects, fetch root trees, or expand tree entries, so the walk effectively skips all tree and blob work entirely. This means the path-walk is also quite efficient under `tree:0` -- it never allocates or expands tree structures.

However, a real bug in v3 meant this did not work correctly for trees that are reachable only through lightweight tags. Those trees were silently dropped when the walk visited "directly-requested" objects under `tree:0`, because the code treated them as root trees but the expansion logic did the wrong thing with the pseudo-path `/tagged-trees`. The fix is a careful restructuring of `setup_pending_objects()` and `walk_path()`. Trees that come in via lightweight tags (where `pending->path` is NULL) now get routed into a proper `/tagged-trees` list. The expansion logic in `walk_path()` is also corrected: when expanding a tree from the `/tagged-trees` path, it uses the root path as the expansion base rather than the pseudo-path itself, so child entries get correct path prefixes.

A separate change that non-zero tree-depth filters (`tree:1`, `tree:2`, etc.) are explicitly rejected with an error message, prompting fallback to the standard revision walk. This is because depth-sensitive filtering does not mesh with how path-walk visits trees -- depth is not currently shared between the filter machinery and the path-walk API.

The test updates are substantial. The existing `t6601-path-walk.sh` test expectations are all re-indented in their object indices because the tagged trees now appear under `/tagged-trees` rather than at the root path. Two new test cases verify that `tree:0` with `--all` produces only commits, tags, and the handful of tagged trees and tagged blobs (no regular trees or blobs), and that a single-branch `tree:0` walk produces commits only (no tags, no trees, no blobs). A third test confirms the expected error for `tree:1`.

This is a well-constructed patch. The commit message is clear about what the filter does, which flags are checked, and why the restructuring was needed. The fix to the tagged-tree bug appears thorough. The decision to reject non-zero depths rather than silently accepting wrong behavior is the right call. The test coverage is solid, though it is worth noting that this correctness-critical patch (and the test infrastructure patch that precedes it) has received no reviewer engagement on the mailing list. If you care about the `--path-walk` series landing correctly, this is the patch that deserves the most careful look.
