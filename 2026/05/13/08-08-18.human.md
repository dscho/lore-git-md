This is a feature patch -- the second and final patch of a small series adding `worktree:<pattern>` and `worktree/i:<pattern>` conditions to Git's `includeIf` configuration mechanism.

This is the patch that actually delivers the feature. The first patch, already seen in this thread, was a mechanical refactoring that renamed `include_by_gitdir()` to `include_by_path()` and changed its signature so that the caller passes in whichever path should be used for matching. This second patch adds two new conditional-include keywords on top of that infrastructure.

When you write `[includeIf "worktree:/home/user/work/"]` in your global gitconfig, Git will now match the realpath of the current worktree's working directory -- the path returned by `git rev-parse --show-toplevel` -- against that glob pattern, using the same syntax as the existing `gitdir:` patterns. The condition never fires in bare repositories (which have no worktree) or during early config reading (when the repository object is not yet initialized). The case-insensitive variant `worktree/i:` works the same way but compares case-insensitively.

The commit message does a nice job explaining the motivation: the existing `gitdir:` condition matches against the `.git` directory path, but in multi-worktree setups all linked worktrees point into the same `.git/worktrees/<id>/` area, making `gitdir:` useless for distinguishing worktrees by checkout path. The author also provides a concrete comparison with `extensions.worktreeConfig`, which is the existing per-worktree alternative -- that mechanism stores config inside each repository's `.git/config.worktree` and requires per-worktree `git config --worktree` commands, whereas this new mechanism can be set once in a global config file and applies to all repositories based on worktree location.

The diff touches three files. The `config.c` changes are minimal -- just four lines adding the two new condition keywords, passing `repo_get_work_tree()` through `include_by_path()`. The documentation update adds a detailed description of the new conditions, a worked example of using them for different `user.name`/`user.email` per project, and a comparison with `extensions.worktreeConfig`. The test file adds 113 lines covering bare repos, multiple worktrees, symlink resolution, case-insensitive matching, early config, and non-repository scenarios -- this is thorough coverage for a small feature.

This is a clean, well-understood patch. The refactoring in the previous patch was minimal and obviously correct; the new code here reads like the natural extension of that pattern. The test coverage is comprehensive for the scope of the change. The documentation explicitly addresses the one question a reader would likely have -- "why not just use `extensions.worktreeConfig`?" -- with a clear answer. This looks ready to be picked up.
