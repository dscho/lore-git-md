This is patch 12/13 of the ongoing series adding `--path-walk`/`--filter` integration, posted by Taylor Blau (co-author with Derrick Stolee), and implements the `object:type` filter.

The patch wires `object:type=commit|tag|tree|blob` into the path-walk machinery by reusing the existing per-type flags (`info->commits`, `info->trees`, etc.) that path-walk already uses to control which object types it descends into. In `prepare_filters()`, a new `LOFC_OBJECT_TYPE` handler ANDs each flag against the requested type, so `object:type=blob` leaves only `info->blobs=1` and sets the others to zero. A new `strict_types` flag is introduced to handle a subtlety: by default, when a user directly requests objects by tip (e.g. `--all`), the path-walk machinery would previously treat those direct-object requests as overriding the type restrictions -- meaning a `tag` object requested directly would still be reported even under `object:type=blob`. With `strict_types=1`, this override no longer happens, so the path-walk follows the type filter faithfully for direct object requests too.

There are two more involved fixes. First, `setup_pending_objects()` previously skipped pending trees as soon as `info->trees` was zero, but that breaks `object:type=blob` when an otherwise-unreachable blob is only reachable through a tag pointing to a tree. The fix loosens the gate to only skip when both `!info->trees && !info->blobs`. Second, the revision machinery (revision.c) drops pending trees during `prepare_revision_walk()` when `revs->tree_objects` is zero; the patch sets `revs->tree_objects = info->trees || info->blobs` so those trees survive the revision walk and stay available for path-walk's own descent, then resets it back to zero afterwards.

Test coverage in `t6601-path-walk.sh` adds four new tests, one for each `object:type` value. The `object:type=blob` test is especially interesting: it explicitly checks that `file2` and `child/file` (blobs reachable only through `tag-pointed trees`, not from any commit root tree) show up in the output, exercising the pending-tree fix described above.

This looks like the last substantive code patch in the series, with only patch 13/13 yet to be posted. The approach is clean and the two incidental fixes for the `!info->trees && info->blobs` corner case are exactly the kind of second-order interactions that get missed when adapting existing machinery for a new filter type. The test coverage is thorough and specifically targets the edge case that makes the fix non-trivial. This patch should land without controversy as long as the `strict_types` semantics are uncontroversial -- the commit message explains the design decision clearly, which should head off most questions.
