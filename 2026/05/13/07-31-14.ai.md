This is patch 2/2 of Patrick Steinhardt's v3 bugfix series for the maintenance subsystem, and it is substantively unchanged from v2. The patch fixes a user-reported regression where setting `gc.auto=0` no longer disables automatic maintenance, which was a silent behavioral change introduced when the default maintenance strategy stopped shelling out internally to `git gc`.

The root cause is a subtle historical path-dependency. When Git switched from `git gc` to `git maintenance` as the default auto-maintenance mechanism (a95ce12430, 2020), the code still shelled out to `git gc` internally, so `gc.auto=0` was still honored because the subprocess checked it. That internal shell-out was recently removed, and `gc.auto` was never wired into the new `prepare_auto_maintenance()` path -- only `maintenance.auto` was checked. The result: users who had `gc.auto=0` to suppress maintenance found that it no longer worked.

The fix in `run-command.c` is small and follows the same pattern already used for the `autoDetach` config keys: check `maintenance.auto` first (via `repo_config_get_bool`), and if it is unset, fall back to `gc.auto` (read as an integer). If `gc.auto` is zero or negative, maintenance is disabled. The test coverage in `t/t7900-maintenance.sh` is thorough -- three cases covering the default behavior (maintenance runs), `gc.auto=1` (maintenance still runs), and `gc.auto=0` (maintenance suppressed), plus two override tests showing that `maintenance.auto` takes precedence over `gc.auto` in both directions.

This patch is well-written and uncontentious. The regression it fixes was user-reported, and the config fallback pattern is consistent with existing precedent in the same function. Both Peff and Junio confirmed the correctness of the approach in earlier iterations, and no outstanding review concerns remain. The series as a whole signals readiness for merge.
