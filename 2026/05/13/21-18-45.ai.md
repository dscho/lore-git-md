Patch 03/13 of the v4 `--path-walk`/`--filter` series is a performance benchmarking script, `p5315-pack-objects-filter.sh`. It measures `git pack-objects --revs --all` with and without `--path-walk`, under three filter scenarios: no filter (baseline), `blob:none`, and `sparse:oid`. The output already included in the commit message shows that at this point in the series there is no meaningful difference between path-walk and the standard walk for any filter -- which is expected, because the actual filter integration into the `path-walk.c` API only comes later in the series. In effect, this patch lands the measurement tool now so that later patches can show before-and-after results directly in their own commit messages.

The setup logic is interesting: it builds a cone-mode sparse-checkout pattern file dynamically by sampling depth-2 directories from the test repository, hashing it into the object store, and recording the OID. This makes the test portable across any repo passed via `GIT_PERF_LARGE_REPO`. It handles the edge case of repos with only top-level directories by falling back to a simpler pattern, or if the repo has no directories at all (flat), the sparse tests are skipped via a prerequisite. The script measures both wall-clock time and packfile size for each combination, and uses `--no-reuse-delta` to force fresh delta computation.

Technically, this is a test-only patch -- it touches no production code and introduces no new symbols. The script is well-structured (clean shell style, sensible fallback logic, good use of `test_size` to record packfile sizes alongside timing). The commit message is clear about what is being benchmarked and why the numbers are all identical here. One small thing: the `sed` on line 30 that appends `$tdir/` to `depth2-dirs.raw` references `$tdir` from a `while read` loop on line 26, which already terminated -- the `$tdir` variable will hold the *last* value from that loop, so if there are multiple top-level directories, most of them will get the wrong prefix. This looks like a latent bug, though it may not matter in practice if the performance test is typically run against repos with only one or two top-level directories.
