ai brief: sideband.c patch accepting colons in ANSI SGR parameters

**Classification:** bugfix (terminal compatibility)

This is a single-patch bugfix for Git's sideband protocol handling. The sideband code includes a function `handle_ansi_sequence()` that parses ANSI escape codes in progress messages (e.g. from `git push`) and strips or passes through Select Graphic Rendition (SGR) sequences like `\e[31m`. The parser currently accepts only semicolons (`;`) as separators between numeric parameters inside an SGR sequence.

The problem is that the official ECMA-48 specification for SGR uses colons (`:`) as sub-parameter separators within a single numeric parameter. This is relevant for 256-color (`\e[38:5:NNm`) and true-color (`\e[38:2:R:G:Bm`) escape codes, which use a colon-separated subfield encoding. Many real-world terminals emit these sequences, and some terminals interpret the more common semicolon-separated form (`\e[38;5;NNm`) differently or incorrectly. Git's current parser rejects the colon-containing forms entirely when they appear in sideband output, causing the escape sequence to be left in the progress message as raw garbage.

The fix is a one-character change in `sideband.c` line 217: adding `src[i] != ':'` to the character-class check in the SGR parsing loop. The patch also updates the block comment to document the new accepted syntax.

The patch is small, well-scoped, and clearly motivated. The commit message cites the upstream xterm source code to support the claim about the standard encoding. The change is mechanically correct: it only relaxes an existing parser to accept an additional character that is valid in the ANSI/ISO standard but was previously rejected. No tests are added, but the existing sideband tests should still pass -- the change is additive (accepting more input) and does not alter how previously accepted sequences are handled. This is a plausible oversight-fix: the original author of the SGR parsing code (added in some earlier sideband change) appears to have been unaware of the colon-subparameter form, which is a common mistake.

If a follow-up summary is needed, future readers should note that this affects how `git push` and similar commands display colored progress output when the remote side emits 256-color or true-color escape codes. The only likely point of contention is whether the patch should also add a test for the new codepath, but given the triviality of the change and the fact that the sideband test infrastructure is somewhat specialized, many contributors would consider it fine as-is.
