This is patch 04/13 in Derrick Stolee's v4 series to make `--path-walk` interoperable with `--filter`, and it is the first patch that changes production logic rather than establishing test infrastructure.

The problem is subtle: when `--path-walk` is combined with a `--filter` that suppresses certain object types (e.g., a filter that discards blobs), the path-walk API was applying those type filters to *everything* it emitted -- including objects that the user explicitly asked for via the revision machinery (tag targets, ref tips, etc.). This meant that directly-requested objects could be silently dropped. The root cause is that the `setup_pending_objects()` function in `path-walk.c` consulted `info->blobs` and `info->trees` before deciding whether to add pending blobs and trees to the walk lists, and `walk_path()` also checked those flags before calling `path_fn`.

The fix has several parts. First, a new helper `path_is_for_direct_objects()` identifies objects whose path starts with `'/'` -- these are pseudo-paths like `/tagged-blobs` that were assigned to directly-requested objects rather than discovered via tree traversal. Second, the logic in `walk_path()` is changed so that directly-requested objects bypass the type filter: if the path starts with `/`, the object is always emitted to `path_fn` regardless of `info->blobs` or `info->trees`. Third, in `setup_pending_objects()`, the guard clauses that skipped trees and blobs based on `info->trees` and `info->blobs` are simply removed -- every pending object is now added to a list regardless of type. Fourth, around the `prepare_revision_walk()` call, the code temporarily sets both `blob_objects` and `tree_objects` to 1 on the revs struct to prevent the revision machinery from discarding those object types during the walk setup, then restores the caller's desired values afterward. The documentation in both `api-path-walk.adoc` and the `path_walk_info` struct comment in `path-walk.h` is updated to spell out this new behavior.

This is a preparatory patch that changes no observable behavior on its own -- the filter integration that would cause objects to be skipped has not been wired in yet. It just makes the path-walk API safe against that future change. The implementation is clean and well-motivated; the `ASSERT(path)` in the new helper and the careful temporary override of revision flags suggest the author is being thorough about edge cases. The convention of using leading `/` to distinguish directly-requested objects from tree-discovered ones is already established in the path-walk codebase, so this patch extends an existing pattern rather than inventing something new.
