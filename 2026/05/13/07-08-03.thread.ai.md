- Thread by Jeff King on `sideband.c` handling of ANSI SGR sequences. The sideband code in `handle_ansi_sequence()` parses SGR escape codes (e.g., `\e[31m`) in progress messages (e.g., from `git push`), but only accepts semicolons (`;`) as separators between numeric parameters. The ECMA-48 specification allows colons (`:`) as sub-parameter separators within a single numeric parameter, which are required for 256-color (`\e[38:5:NNm`) and true-color (`\e[38:2:R:G:Bm`) escape codes. Many terminals emit these colon-containing sequences, and Git's current parser leaves them as raw garbage in the output.

- Jeff King's patch (originally authored by Mantas Mikulėnas) makes a one-character change in `sideband.c` line 217: adding `src[i] != ':'` to the character-class check in the SGR parsing loop. The commit message cites the upstream xterm source code to support the standard encoding. The change is additive (accepting more input) and does not alter handling of previously accepted sequences. No tests are included.

- **Current status**: The patch is effectively approved for merging. Johannes Schindelin provided an **Acked-by**, calling it "well-motivated and well-executed." Junio C Hamano has not objected but mildly questioned the project's long-standing whitelist-based design philosophy (accepting only known-good patterns) rather than blacklisting known-bad ones. The patch remains in "under review" state pending Junio's integration (likely `pu` or `next` in the next "What's cooking" report).

- **Open questions**:

He advocates for *strict whitelisting* of all escape sequences in sideband output, proposing exclusions for cursor-movement sequences (lacking terminal-dimension context), hyperlink sequences (`OSC 8;...ST`, due to security risks like `file://` URLs), and progress-bar sequences (`OSC 9;4;nST`), favoring a protocol extension for server-side percentage reporting instead. This debate is tangential to the patch and not actionable.
