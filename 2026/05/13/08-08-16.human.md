This is a feature patch (two patches, actually) extending the `includeIf` configuration mechanism with a new `worktree:` condition keyword. The cover letter and patch series are by Chen Linxuan.

Currently, `includeIf` can conditionally include a config file based on either the `.git` directory path (`gitdir:`) or the current branch (`onbranch:`). This series adds `worktree:<pattern>` and `worktree/i:<pattern>`, which match on the real path of the working tree's working directory. This addresses a real pain point in multi-worktree setups: because linked worktrees share the main repository's `.git` directory (via `.git/worktrees/`), using `gitdir:` patterns to target a specific worktree is awkward and fragile. Being able to match on the checkout path itself is much more natural.

The series is small and well-structured. Patch 1 is a refactoring: it renames and repurposes the internal `include_by_gitdir()` function into a more general `include_by_path()` so that the worktree condition can reuse the same pattern-matching logic. Patch 2 adds the actual feature: the new condition keywords, documentation, and tests.

This is the fourth version of the series (v4), and the changelog shows careful engagement with reviewer feedback from Patrick Steinhardt, Phillip Wood, and Junio. Patrick suggested deduplicating the pattern documentation (done), adding a test for early config reading (done), and adding a test for the non-repository case (done). Phillip and Junio suggested adding a documentation comparison with `extensions.worktreeConfig` (done, with an example). These are the right kinds of concerns to address — correctness at the boundaries — and the author has been responsive. The tests have grown to 113 lines, which is a healthy amount for a feature this size.

The documentation in `Documentation/config.adoc` now explains the new condition, notes that it never matches in a bare repository, and explicitly contrasts it with `extensions.worktreeConfig`, which is the existing (but heavier) way to have per-worktree config. That is a nice touch — it helps users decide which mechanism to reach for.

Overall, this is a well-executed, clearly motivated feature from a contributor who is listening to feedback. It touches only `config.c` (the include-by-path logic), documentation, and tests — no risky subsystems. It looks ready for `next`.
