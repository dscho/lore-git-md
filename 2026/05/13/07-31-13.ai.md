This is a bugfix, the first of two patches in a v3 series from Patrick Steinhardt targeting the maintenance subsystem.

The problem is straightforward: when a user runs `git maintenance run --detach`, the parent process creates a lockfile to prevent concurrent maintenance runs, but the parent exits immediately after forking, releasing the lock before the child has finished its work. This means the lock only covers a tiny fraction of the maintenance window, defeating its purpose entirely and leaving the actual background work unprotected.

The fix is clean and systematic. Rather than handling the ownership transfer at the single problematic call site in `builtin/gc.c`, Patrick has adopted the approach Taylor Blau championed in the v2 discussion: `daemonize()` itself now automatically reassigns all open tempfiles and lockfiles from the parent PID to the child PID after forking. The parent drops ownership (so its atexit handler does not unlink them on exit), and the child claims ownership (so it cleans them up when it eventually exits). This is the right level -- future callers of `daemonize()` get the correct behavior for free, and there is no need for a special `daemonize_without_transfer()` function unless a caller actively wants the old behavior.

The patch touches five files. In `setup.c`, the `daemonize()` function itself is modified to call the new `reassign_tempfile_ownership()` helper in both the parent and child paths. In `tempfile.c` and `tempfile.h`, the helper walks the linked list of active tempfiles and updates the owner PID for any that match. In `setup.h`, the doc comment for `daemonize()` is updated to promise the reassignment as part of the contract. The test in `t/t7900-maintenance.sh` is an elaborate FIFO-based integration test that verifies the lock is held by the parent until the child exits, and then is released. Taylor praised this test as "much more robust" than the alternatives.

Taylor Blau's Co-authored-by and Signed-off-by appear on the commit, reflecting that this v3 incorporates his alternative design. The only caller besides maintenance is `daemon.c`, which creates no tempfiles before calling `daemonize()`, so this change is a no-op there. The `#ifdef NO_POSIX_GOODIES` duplication visible in `setup.c` is acknowledged as messy but deferred to a follow-up, unchanged from earlier versions.

This patch looks ready for merge. The design was debated in v2, the disagreement was resolved by adopting the cleaner approach, and the implementation is careful and well-tested.
