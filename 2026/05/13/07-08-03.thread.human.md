This is a small, clean bugfix for how Git's sideband protocol handles ANSI escape codes. The sideband code parses SGR (Select Graphic Rendition) sequences like `\e[31m` to manage colored progress messages during push and similar operations.

The issue is that Git's parser currently only accepts semicolons as separators inside SGR parameters, but the ECMA-48 standard also defines colons as valid sub-parameter separators. This is particularly relevant for 256-color and true-color escape codes (`\e[38:5:NNm`, `\e[38:2:R:G:Bm`), which many terminals emit. Git's parser rejects these, leaving raw escape garbage in the user's progress display.

The fix is a one-character addition on line 217 of `sideband.c`: adding `src[i] != ':'` to the parser's character-class check. The change is mechanically trivial -- it only relaxes an existing parser to accept an additional valid character.

No tests are added, but the change is purely additive (it accepts more input without altering how previously accepted sequences are handled), so existing tests should pass. Some might argue for a test, though given the triviality and the specialized sideband test infrastructure, this is likely fine as-is. The only practical impact is on users whose remote side emits 256-color or true-color escape codes during push.
