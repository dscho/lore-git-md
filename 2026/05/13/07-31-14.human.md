This is a bugfix patch, the second in a two-patch series, making `gc.auto=0` actually suppress automatic maintenance again.

When Git's maintenance subsystem stopped shelling out to `git gc`, users who had `gc.auto=0` in their config found that automatic maintenance still ran. The old code path worked because `git gc` checked the threshold itself; after the internal switch, `gc.auto` was simply never read. Patrick fixes this by having `run_auto_maintenance()` check `maintenance.auto` first (it takes precedence), then fall back to reading `gc.auto` as an integer -- if the value is zero or negative, maintenance is disabled. This is the same pattern already used for the `autoDetach` config keys, so it is a well-precedented approach.

The tests are thorough and easy to follow: three cases in a row (default, `gc.auto=1`, `gc.auto=0`) plus a pair that confirm `maintenance.auto` overrides `gc.auto` in both directions. The commit message narrates the chain of events clearly and credits the reporter (`Jean-Christophe Manciot`). None of this is new in v3 -- the patch is unchanged from v2 and was already settled. Anyone who was bitten by the regression and set `gc.auto=0` expecting it to work will be glad to see this.
