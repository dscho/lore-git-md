This is patch 11 of 13 in the v4 `--path-walk` / `--filter` integration series from Derrick Stolee and Taylor Blau. This is the fix for the `tree:0` bug that was the main correctness issue from v3 — it addresses what Blau "correctly smelled" as a problem with how tagged trees were handled.

The core change is straightforward in principle but required significant supporting work in the path-walk API. The `tree:0` filter should omit all trees and blobs, emitting only commits and tags. The mapping onto path-walk is simple: set `info->trees = 0` and `info->blobs = 0` in `prepare_filters()`, and the existing plumbing already checks these flags before allocating or expanding any tree structures. The commit message walks through the three places where these flags short-circuit work: the revision walk parameters, the root-tree fetch, and the pending-objects setup. Under `tree:0`, the path-walk never touches tree objects at all.

The complication is that directly-requested trees (from command-line arguments or lightweight tags) interact badly with the `/tagged-trees` path that the series introduced in an earlier patch. The fix has two parts. First, in `walk_path()`, tree expansion is now gated by `path_is_for_direct_objects()`: if the current path is a "direct objects" path and `info->trees` is false, the code skips tree expansion entirely. When it does expand (because `info->trees` is true), it uses the root path rather than the `/tagged-trees` path itself, so that content from tagged trees appears under correct path names. Second, `setup_pending_objects()` is substantially rewritten for the OBJ_TREE case: trees without a path are now collected into a separate `tagged_trees` list (replacing what was previously an informal assumption that they were root trees), and registered under `/tagged-trees` in the path map. The old code's comment "assume a root tree, such as a lightweight tag" was silently wrong for trees reached through tags — they ended up at root instead of under `/tagged-trees`, causing the v3 bug.

The diff touches only three files but the test changes are extensive: every test in `t6601-path-walk.sh` that previously listed tagged trees under the root path now lists them under `/tagged-trees`, with a corresponding renumbering of all line indices. Six existing tests are affected (`all`, `blob:none`, `blob:limit=0`, `blob:limit=3`, `sparse:oid`). Three new tests are added at the end: a `tree:0` with `--all` (which should show only commits, tags, tagged-blobs, and tagged-trees, with no trees from the commit ancestry), a `tree:0` with a single-branch (`topic` only, which has no tags so the output is just three commits), and a negative test confirming that `tree:1` is rejected with a clear error message. Non-zero tree-depth is explicitly unsupported because the depth at which a tree is visited is path-walk API state that the filter machinery doesn't share.

Technically, this patch looks correct and well-motivated. The commit message is unusually good — it pre-explains why tree expansion doesn't happen, then walks through the three code paths that enforce it, and only then describes the tagged-trees fix. The test coverage is thorough: the `--all` test exercises the tagged tree and blob paths, the single-branch test exercises the pure path (no tags at all), and the rejection test clarifies the API boundary. The renumbering of the existing tests is mechanical and correctly done — this is exactly the kind of test update that a reviewer would want to confirm visually rather than re-run everything, and the diff makes it easy to do that.

For a reader catching up: this is the substantive fix that the series was waiting for. If it passes review, the remaining two patches (12/13 and 13/13) should be straightforward. No reviewer has engaged with any patch in the series yet, which is concerning for a patch of this complexity touching core path-walk data structures — the tagged-trees rewrite in `setup_pending_objects()` in particular would benefit from a second pair of eyes.
