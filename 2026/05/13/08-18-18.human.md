**Bug report: lowercase `head` resolves to wrong worktree HEAD on case-insensitive filesystems.**

Alexander Sandström reports a correctness bug that appears when using
linked worktrees on a case-insensitive filesystem like macOS APFS.  The
core issue is that `HEAD` (uppercase) is resolved through a
per-worktree path (`.git/worktrees/<id>/HEAD`), but `head` (lowercase)
falls through to general ref resolution, where Git tries to open a file
named `head`.  On a case-insensitive filesystem that file lookup matches
`.git/HEAD` -- the main worktree's HEAD -- instead of the linked
worktree's HEAD.  The result is that `git rev-parse head` returns the
main worktree's HEAD commit, and `git reset --soft head~1` silently
resets the linked worktree to the wrong parent, staging changes from the
wrong history.  The bug is latent without worktrees because
`.git/HEAD` is the only HEAD file, but it becomes an observable
correctness problem as soon as the main and linked worktree heads
diverge.

The reporter provides a clear reproduction script and correctly
identifies the mechanism (case-insensitive filesystem matching the wrong
file), but does not submit a patch, citing lack of C programming
experience.  This is a genuine bug, not a style question -- it causes
silent data corruption in a common workflow (`git reset` in a linked
worktree), and it is likely to become more common as worktrees grow in
popularity.  The fix should be fairly localized: during ref resolution,
either reject a case-insensitive match to `HEAD` that is not exactly
`HEAD`, or normalize it and route through the per-worktree codepath.
Either approach is mechanical and should not require deep refactoring.
This is worth a look from someone familiar with the ref resolution code.
