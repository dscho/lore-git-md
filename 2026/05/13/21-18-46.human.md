This is patch 04/13 of the `--path-walk`/`--filter` integration series, a refactoring that ensures the path-walk API never silently drops objects that were directly requested by the user (e.g., tagged trees or blobs in a partial clone), even when an object-type filter would otherwise suppress them. It's a preparatory patch -- no behavior change yet, but it fixes a latent bug that would surface once filters are wired into the API later in the series.

The fix is conceptually straightforward. The path-walk API has a notion of "paths" that it walks. Until now, when a type filter like `info->blobs = 0` was set, a directly-requested blob (for example, the target of a lightweight tag) could be skipped because the filter check did not distinguish between "a blob I found by walking a tree" and "a blob the user explicitly asked for." Stolee solves this by introducing the convention that paths starting with `'/'` (e.g., `/tagged-blobs`) represent directly-requested objects, while paths without that prefix were discovered during tree traversal. A new helper, `path_is_for_direct_objects()`, is used at two points in the walk logic to exempt directly-requested objects from the type-filter checks. The patch also tweaks how the revision walk is configured: it temporarily enables both `blob_objects` and `tree_objects` before `prepare_revision_walk()`, then restores the user's original settings afterward, because the revision machinery itself can drop pending objects when it sees matching type flags disabled.

The commit message explains the motivation cleanly and is well-justified: the bug was only latent because the filter integration hasn't landed yet, but it would have been caught by the `GIT_TEST_PACK_PATH_WALK=1` test-mode once that integration arrives. The change touches three files -- the implementation in `path-walk.c`, the API header `path-walk.h`, and the technical documentation in `api-path-walk.adoc` -- and the documentation update is clear about the new guarantee.

This is a solid, well-scoped preparatory patch from an author who clearly understands the edge cases in their own API. The `ASSERT(path)` in the new helper is a nice belt-and-suspenders touch. No controversial design decisions here. Worth a quick read for anyone following the series closely, but probably not something that needs a deep review -- the logic is compact and the impact is entirely internal to the path-walk machinery.
