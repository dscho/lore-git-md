**Thread identity** -- bug report from Alexander Sandström. Subject: linked worktrees produce wrong commit for lowercase `head` on case-insensitive filesystems. Not a patch series.

**Core problem** -- On case-insensitive filesystems (macOS APFS/HFS+), `git rev-parse head` in a linked worktree resolves to the *main* worktree's HEAD instead of the linked worktree's HEAD. `git rev-parse HEAD` (uppercase) correctly goes through the per-worktree ref at `.git/worktrees/<name>/HEAD`. Lowercase `head` falls through to general ref resolution, which does a file lookup; on case-insensitive fs, this accidentally matches `.git/HEAD` (the main worktree's HEAD). Without linked worktrees both codepaths produce the same result, so the bug is latent. With linked worktrees the two HEADs diverge and the behavior silently changes. Practical impact: `git reset --soft head~1` in a linked worktree operates on the wrong commit.

**Current status** -- Initial report from Alexander Sandström, plus one reply from D. Ben Knoble. No patch submitted. Knoble links two prior discussions from 2024 that identified the same underlying problem and states that the filesystem-backed ref store is fundamentally incapable of fixing this -- the problem is effectively blocked on the reftable transition, which should eliminate these paper cuts by not delegating name lookup to the filesystem.

**Key technical details** -- File: `refs/files-backend.c` or similar ref resolution path. No new symbols. Two fix options proposed by reporter: (a) reject lowercase `head` with an error (matching behavior on case-sensitive filesystems where it already fails with "unknown revision"); or (b) normalize to `HEAD` and route through the per-worktree codepath. Knoble's reply does not evaluate these options; the implication of his reference is that neither fix in the files backend is worth pursuing.

**Open questions and loose ends** -- No discussion of the design question of whether lowercase `HEAD` should be treated as valid at all. The bug only manifests on case-insensitive filesystems with linked worktrees -- two conditions that together are relatively uncommon, which combined with Knoble's "blocked on reftable" framing may affect prioritization. The reporter is not a C programmer and no patch is expected from them. Knoble's reply appears closed to further discussion in the files backend.
