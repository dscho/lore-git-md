**Thread identity** -- bug report from Alexander Sandström. Subject: linked worktrees produce wrong commit for lowercase `head` on case-insensitive filesystems. Not a patch series.

**Core problem** -- On case-insensitive filesystems (macOS APFS/HFS+), `git rev-parse head` in a linked worktree resolves to the *main* worktree's HEAD instead of the linked worktree's HEAD. `git rev-parse HEAD` (uppercase) correctly goes through the per-worktree ref at `.git/worktrees/<name>/HEAD`. Lowercase `head` falls through to general ref resolution, which does a file lookup; on case-insensitive fs, this accidentally matches `.git/HEAD` (the main worktree's HEAD). Without linked worktrees both codepaths produce the same result, so the bug is latent. With linked worktrees the two HEADs diverge and the behavior silently changes. Practical impact: `git reset --soft head~1` in a linked worktree operates on the wrong commit.

**Current status** -- Initial report from Alexander Sandström, plus replies from D. Ben Knoble and Torsten Bögershausen. No patch submitted. Knoble links prior discussions and states the issue is blocked on reftable transition. Torsten takes a firm stance that lowercase "head" is invalid regardless of filesystem behavior, effectively closing the discussion as "not a bug."

**Key technical details** -- File: `refs/files-backend.c` or similar ref resolution path. No new symbols. Two theoretical fix options from reporter: (a) reject lowercase `head` with an error; or (b) normalize to `HEAD`. Torsten's position makes clear neither will be pursued - the project considers lowercase HEAD invalid by design. Documentation could be updated to clarify this expectation.
