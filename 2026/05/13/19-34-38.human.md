This is v9 of Harald Nordgren's five-patch series adding safe automated local branch cleanup to `git branch`, and it looks like the series is effectively done. The sole remaining design objection from Junio C Hamano in v8 — that `--force` should not bypass the mergedness check for `--prune-merged` — has been addressed cleanly.

The core architecture carries forward from v8: `git branch --prune-merged <remote>` deletes local branches whose tip is reachable from their configured upstream remote-tracking branch. This upstream-reachability model was the v8 redesign that Junio called "a lot better" than the earlier approach. It means that a local branch is only deleted when its work has demonstrably been integrated into its upstream — a much more intuitive safety check than the previous series' push-ref-existence logic. Branches whose upstream ref no longer resolves locally are silently skipped rather than deleted.

The change in v9 is exactly what Junio asked for and Harald agreed to: `--force` no longer has any special interaction with `--prune-merged`. The `[-f]` is gone from the synopsis, the `--force` parameter has been removed from `prune_merged_branches()`, and the associated tests have been dropped. Instead of suggesting `--force` to delete unmerged branches, the error message now points users at `git branch -D`. The per-branch opt-out config `branch.<name>.pruneMerged` is also simpler now — since `--force` no longer skips the reachability check, the note that it did not override the config opt-out is unnecessary and has been removed.

The supporting infrastructure is the same: patch 1 adds `--forked <remote>` to list branches tracking a remote, patch 2 refactors `delete_branches()` to warn instead of error on bulk refusal, patch 3 is the core `--prune-merged` logic, patch 4 adds the per-branch opt-out config, and patch 5 adds `--all-remotes` as a convenience flag for enumerating all remotes.

Test coverage remains thorough, and with Junio's objection resolved there are no apparent remaining blockers. This series is a candidate for `next`.
