**Patches 12/13 of the `--path-walk`/`--filter` integration series (Stolee/Blau).**

This patch adds `object:type=<type>` filter support to the path-walk machinery, completing the "object-info-only" filter family alongside `blob:none` and `tree:0`. The mapping is straightforward in `prepare_filters()`: each of the four `info->{commits,tags,trees,blobs}` flags is AND-ed against whether the requested type matches, so a single filter like `object:type=blob` leaves only `info->blobs = 1` and everything else zero. This AND-based approach is explicitly designed to be composable with future combined-filter support.

The tricky part, and the real contribution of this patch, is handling the "trees off, blobs on" case. Previously, `setup_pending_objects()` skipped pending trees as soon as `info->trees` was zero, but `object:type=blob` needs those trees because a lightweight or annotated tag pointing to a tree can reach blobs that are otherwise unreachable from any commit's root tree. The fix loosens the gate to "skip only when both `info->trees` and `info->blobs` are zero". A second subtlety involves the revision machinery: by default, `handle_commit()` drops pending tree objects when `revs->tree_objects` is zero, so the patch sets `revs->tree_objects = info->trees || info->blobs` before `prepare_revision_walk()` to ensure those pending trees survive, then immediately resets it to zero afterwards so the revision walk does not redundantly enumerate trees alongside path-walk's own descent.

A new `strict_types` field is introduced in `struct path_walk_info` and set to 1 for `object:type` filters. This flag is checked in `walk_path()` to override the normal behavior where directly-requested objects bypass type-based filtering -- without it, a pending tree would always be emitted under its path regardless of the filter. The flag appears designed for this filter, though the commit message hints it may serve combined-filter cases later.

Four new tests in `t6601-path-walk.sh` cover each of `object:type=commit`, `object:type=tag`, `object:type=tree`, and `object:type=blob`. The `object:type=blob` test is the important one: it explicitly asserts that `file2` and `child/file` (both reachable only through tag-pointed trees) appear in the output, exercising the pending-tree fix in `setup_pending_objects()`.

This is the second-to-last patch in the 13-patch series. Like nearly all patches before it, it has received no independent review. The pending-tree gate fix and the `strict_types` override are the kinds of edge cases where a second pair of eyes would be valuable -- they interact with the tagged-trees rewrite from patch 11/13 and with the revision machinery's object-type flags, which is a subtle interface.
