Patches 1-2 unchanged, patch 3 drops `--force override`,
and now patch 4 adds the per-branch opt-out config.

This is the fourth patch in Harald Nordgren's v9 five-patch series adding
`git branch --prune-merged`. It adds a `branch.<name>.pruneMerged` config
option (default true) that, when set to `false`, exempts an individual
branch from the `--prune-merged` operation -- even when `--force` is used
in its now merely stylistic role. Explicit `git branch -d` deletion is
unaffected, so the user can still remove the branch directly even while
keeping it safe from bulk cleanup.

The implementation in `builtin/branch.c` is straightforward: inside the
candidate-loop in `prune_merged_branches()`, after the existing checks
(not checked out, resolvable upstream, not the default branch), it reads
`branch.<name>.pruneMerged` via `repo_config_get_bool`. If the config key
exists and is `false`, the branch is skipped with a warning message like
"Skipping 'one' (branch.one.pruneMerged is false)". The diff is 23 lines
in `builtin/branch.c`, plus documentation and two new tests in
`t/t3200-branch.sh`. One test confirms the opt-out works (it preserves
'one' while deleting 'two'); the other confirms that `git branch -d`
bypasses the opt-out and deletes the branch normally.

The commit message frames the feature around the use case of keeping a
topic branch around between review rounds after its upstream has been
merged. This is a clean, well-scoped patch: it extends the safety model
with a per-branch escape hatch without complicating the core logic.
`branch.<name>.pruneMerged` follows the existing `branch.<name>.`
config convention, which should feel natural to users. No controversy
expected; this is the last substantive piece of the series before the
final `--all-remotes` convenience flag in patch 5.
