This is a bug report from Alexander Sandström about a subtle issue on case-insensitive filesystems (macOS APFS/HFS+) that affects linked worktrees. The user is a reporter, not a patch submitter, and explicitly states they are not C programmers.

The core problem is a discrepancy between what `git rev-parse HEAD` and `git rev-parse head` return in a linked worktree on a case-insensitive filesystem. `HEAD` (uppercase) correctly resolves to the linked worktree's HEAD via the per-worktree ref at `.git/worktrees/<name>/HEAD`. But lowercase `head` falls through to general ref resolution, which looks for a file called `head` on disk. On a case-insensitive filesystem, this accidentally matches `.git/HEAD`, which is the *main* worktree's HEAD, not the linked one's. Without worktrees this doesn't matter -- there is only one HEAD file -- so the wrong codepath happens to produce the right result. With linked worktrees, the two HEADs diverge and the bug becomes visible.

The impact is practical: `git reset --soft head~1` in a linked worktree silently operates on the wrong commit, staging unexpected changes with no error or warning. The author suggests one of two possible fixes: reject lowercase `head` with an error (matching the behavior on Linux, where it already fails with "unknown revision") or normalize it to `HEAD` and route through the per-worktree codepath. The author notes that an argument could be made that "lowercase head isn't a thing" and that the bug may be considered outside the project's scope.
