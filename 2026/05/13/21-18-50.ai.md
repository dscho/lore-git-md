PATCH v4 08/13 -- `path-walk: add pl_sparse_trees to control tree pruning`

This is the eighth patch in Derrick Stolee's series to make `--path-walk` work with `--filter` options. It sets up infrastructure for the upcoming `sparse:oid` filter integration (patches 09/13 and 10/13, which follow in the series).

The patch adds a `pl_sparse_trees` flag to `path_walk_info`. When the flag is set (as it is for `git backfill --sparse` and the test helper's `--stdin-pl` mode), sparse-checkout patterns prune both trees and blobs -- the existing behavior. When the flag is unset, only blobs are filtered by the sparse patterns and all trees are walked and emitted. This distinction matters because the `sparse:oid` filter in `pack-objects` needs to retain all trees while hiding blobs outside the sparse cone.

Along the way, Stolee fixes a subtle SEEN-flag ordering bug in `add_tree_entries()`. Previously, the SEEN flag was set on an object immediately after checking whether it had already been visited, before checking path-sparseness. If the same object ID appeared at multiple paths (which can happen when sibling directories have identical contents), the first encounter at an out-of-cone path would mark it SEEN and prevent it from being discovered later at an in-cone path. By deferring the SEEN flag to after all sparse and pathspec checks pass, objects remain "findable" from any path regardless of where they were first seen.

The test coverage is clean: a new test in `t6601-path-walk.sh` exercises the `--no-pl-sparse-trees` mode on the familiar base-and-topic test scenario, confirming that all trees are walked (including those in the `right/` directory, which would be pruned by the sparse cone) but only in-cone blobs (`a`, `left/b`) are emitted.

This is a well-scoped, well-motivated patch. The SEEN-flag fix is the kind of subtle correctness issue that would be easy to miss and hard to debug later, and the commit message explains it clearly. The architecture is clean and the new flag integrates naturally into the existing pattern-matching logic. This is solid preparatory work for the meatier filter patches that follow.
