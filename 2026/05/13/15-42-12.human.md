This is a follow-up response to a bug report, not a patch.

Alexander Sandström reported that on case-insensitive filesystems, `git rev-parse head` in a linked worktree silently resolves to the *main* worktree's HEAD, causing commands like `git reset --soft head~1` to operate on the wrong commit. The root cause is that lowercase `head` bypasses the per-worktree ref resolution and instead does a filesystem file lookup that accidentally matches `.git/HEAD` (the main worktree's HEAD) on case-insensitive systems.

D. Ben Knoble replies with two links to prior mailing list discussions showing this is a known issue. The short version: Git's on-disk ref storage treats refs as filenames, so "HEAD" and "head" are distinct names but on case-insensitive filesystems they collide. The project does not appear inclined to fix this in the traditional filesystem ref backend because the mismatch is inherent to the design. The thread links suggest the long-term answer is moving to the reftable backend, where ref names are stored in a binary format that is not subject to filesystem case folding.

This is a brief, informative pointer from someone familiar with the problem history. It does not propose a fix, endorse one, or add new analysis. It effectively tells the reporter that this is a known papercut without a near-term fix in the files backend, and points to reftables as the eventual solution.
