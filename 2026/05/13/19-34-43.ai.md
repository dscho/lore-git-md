**Patch 5/5 of the `--prune-merged` series.** Adds the `--all-remotes` convenience flag, which makes `--forked` or `--prune-merged` operate on every configured remote rather than requiring each one as an explicit argument. This is the final patch in a now-complete v9 series that has already addressed Junio C Hamano's sole remaining objection (that `--force` should not bypass the mergedness check).

The implementation is straightforward wiring. `--all-remotes` is a `NONEG` boolean option registered alongside `--forked` and `--prune-merged`. If neither `--forked` nor `--prune-merged` is present, using `--all-remotes` alone dies with `"requires --forked or --prune-merged"`. When active, it calls `for_each_remote(collect_remote_name)` to populate a `string_list` of remote names, which is then merged with any explicit `<remote>` arguments before filtering into `collect_forked_set()`. The `parse_forked_args()` function that validates explicit arguments is unchanged -- so a misspelled explicit name alongside `--all-remotes` is still rejected, which the tests confirm.

The synopsis in the documentation is updated to `(--forked|--prune-merged) (<remote>... | --all-remotes)`, and four new tests cover the flag: one confirming `--forked --all-remotes` produces the expected list of branches across multiple remotes, one verifying that an invalid explicit remote is still caught even with `--all-remotes`, one rejecting `--all-remotes` alone, and a substantial `--prune-merged --all-remotes` integration test that sets up two remotes, creates branches tracking each, and confirms both are deleted.

This is a clean, well-motivated convenience feature that follows established patterns (e.g., `for_each_remote()` is used the same way elsewhere for "all remotes" flags). At 81 lines of diff across three files, it is modest in scope. Given that the safety model was approved by Junio in v8 and the only objection was resolved in the v9 patches 3 and 4, this series should be ready for `next`.
