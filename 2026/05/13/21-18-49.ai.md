Patch 07/13 in the `--path-walk`/`--filter` integration series, adding native support for `blob:limit=<n>` to the path-walk API. This is the fourth filter type to be handled directly in `path-walk.c`, following `blob:none`, `sparse:oid`, and `tree:0` in earlier patches.

The implementation is straightforward. `prepare_filters()` stores the size limit in a new `blob_limit` field on `path_walk_info` and clears the filter from `revs`. During `walk_path()`, blob batches are individually filtered: each blob's size is read via `odb_read_object_info()`, and only blobs strictly smaller than the limit survive. A limit of zero degenerates to `blob:none` (all blobs suppressed). Batches that become empty after filtering are skipped rather than delivering an empty batch to the callback.

The commit message is transparent about the tradeoff this creates for `git backfill` -- calling `odb_read_object_info()` on each blob will trigger on-demand downloads from a partial clone, which is the opposite of what backfill wants to do. The patch handles this by adding a second-level check in `backfill.c` that explicitly rejects `blob:limit` before falling through to the general incompatibility error. The existing test in `t5620-backfill.sh` is updated so the error message matches, and a new `blob:limit=3` test exercises the partial-filtering case within a single path batch (some blobs kept, others excluded) while `blob:limit=0` verifies the degenerate-to-none path.

This is a mechanical extension of the architecture established in patches 04/13 through 06/13. No surprises, no design questions raised, and the backfill-incompatibility concern is addressed upfront rather than left for later discovery. The test coverage looks adequate for a feature of this scope. As with every patch in this series so far, no independent review has appeared on-list.
