This is patch 07/13 of the `--path-walk` / `--filter` series from Derrick Stolee and Taylor Blau, adding support for the `blob:limit=<n>` filter to the path-walk API.

The patch extends `prepare_filters()` in `path-walk.c` to recognize `LOFC_BLOB_LIMIT` and store the limit in a new `blob_limit` field on the `path_walk_info` struct. A limit of zero is treated as equivalent to `blob:none` (all blobs excluded). During the actual walk, blobs are now checked individually: `odb_read_object_info()` is called for each blob in a batch, and only those smaller than the limit are passed to the callback. The commit message notes that this means `blob:limit` is not compatible with the batch-download model used by `git backfill` -- it would fetch blobs one-by-one, defeating the purpose -- so `backfill` gets its own explicit rejection of the size-limit filter with a specific error message.

The documentation update is mechanical, just extending the list of supported filter forms in `git-pack-objects.adoc`. The test additions in `t6601-path-walk.sh` are thorough: one test for `blob:limit=0` (which should produce the same output as `blob:none`, confirmed by the expected output matching) and one for `blob:limit=3` that exercises partial filtering where some blobs in a path batch are kept and others are dropped.

This is a straightforward extension of the pattern established in earlier patches -- the filter is consumed by `prepare_filters()`, removed from the `revs` structure, and handled directly by the path-walk infrastructure. The only noteworthy design decision is the `||` short-circuit for non-blob types from `odb_read_object_info()`, which is a defensive guard: in theory every call here should return `OBJ_BLOB`, but if it does not, the blob is conservatively included. The commit message is upfront about the performance cost (the per-blob `odb_read_object_info()` call) and the resulting incompatibility with `backfill`.
