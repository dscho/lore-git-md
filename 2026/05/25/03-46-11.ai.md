This is a technical explanation of Git's object model and fetch behavior in the context of rewritten history. Chris Torek provides a detailed response to Jens Tröger's question about how Git handles fetches when commits are rewritten under the same tag.

The key points are:
1. Git objects (including commits) are immutable once created - their SHA hashes never change
2. History "rewrites" actually create new commits while leaving old ones in place
3. Human-readable names (tags/branches) are how we typically reference commits, not raw hashes
4. Tag names are meant to be stable (unlike branch names which move forward)
5. FETCH_HEAD acts as a temporary reference to fetched objects, but gets overwritten on next fetch
6. The observed behavior where a fetch of an old SHA checks out a new commit suggests the remote has rewritten history while keeping the same tag name

Torek emphasizes this isn't fetch-specific behavior but rather fundamental to Git's object model. He notes tag rewriting is generally discouraged once tags are published, and explains how Git's garbage collection interacts with this (keeping old objects around for a while even after rewrites). The response provides the technical grounding needed to understand why the original observation occurred, though it doesn't address the specific mechanism connecting the old and new commits during fetch.
