This is a follow-up in the thread about Git's behavior with rewritten commits under the same tag. Junio C Hamano (the Git maintainer) responds to Jens Tröger's question about how Git connects a rewritten commit (fda7769) to its predecessor (dda8db1) during fetch operations.

Junio focuses on a specific detail from Jens' GitHub discussion that wasn't included in the mailing list post - the "(grafted, HEAD)" annotation seen in the commit reference. He asks whether Jens might be using the legacy `.git/info/grafts` mechanism, which was Git's original way to handle history rewriting before the introduction of replace-refs.

The key technical point is that grafts (now largely superseded by replace-refs) could explain the observed behavior where Git appears to substitute one commit for another during fetch operations. Junio's question suggests this might not be core Git behavior but rather a local configuration artifact.

This moves the discussion forward by:
1. Identifying a potential local configuration factor (grafts) that could explain the behavior
2. Narrowing the investigation from general fetch mechanics to specific history-rewriting mechanisms
3. Highlighting the importance of including all relevant context when reporting behavior

The response doesn't yet resolve the original question but provides a concrete direction - checking for graft files - that could explain the observed commit substitution.
