This is a technical explanation of Git's object model and fetch behavior when dealing with rewritten commits. Chris Torek provides a detailed response to Jens Tröger's question about how Git handles fetches when a commit SHA that was previously tagged gets replaced by a different commit under the same tag.

The key points clarified:
1. Git objects (including commits) are immutable once created - their hash IDs permanently identify them
2. History "rewrites" actually create new commits while leaving old ones in the repository
3. Tag names normally shouldn't change, unlike branch names which are expected to move
4. FETCH_HEAD records the hash ID from the fetch operation, but this is temporary and will be overwritten by the next fetch
5. The apparent contradiction between immutable objects and rewritten history comes from how humans use names (tags/branches) rather than raw hash IDs

The explanation digs into Git's underlying mechanisms while cautioning against tag rewrites in shared repositories. It provides useful context about how Git maintains object permanence while still allowing history modification through creation of new objects rather than changing existing ones. The response is thorough and authoritative, coming from a long-time Git contributor.
