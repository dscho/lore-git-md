This is a follow-up in a thread about Git's behavior when fetching rewritten commits under the same tag. Junio C Hamano responds to Jens Tröger's question about why fetching a specific SHA (dda8db1) that was previously tagged as 1.20.0 results in checking out a different commit (fda7769) that now carries that same tag.

Junio zeroes in on a key detail from Jens' GitHub discussion (not included in the mailing list post) that shows the replacement commit is marked as "grafted". He asks whether Jens might be using the legacy `.git/info/grafts` mechanism, which was Git's original way to handle history rewriting before the introduction of replace-refs.

The response suggests that the observed behavior could be explained by either:
1. An active grafts file manually connecting the commits
2. Or some other local mechanism that's effectively creating a graft-like relationship between the commits

This moves the discussion forward by identifying grafts as a potential explanation, while leaving open whether this is the actual cause or if there's another mechanism at work. The question remains relevant to understanding how Git handles rewritten history during fetch operations, particularly when tags are involved.
