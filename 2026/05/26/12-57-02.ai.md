Feature proposal for `git mv` to support post-move index updates.

Frieder Hannenheim proposes adding a new option to `git mv` that would update Git's index to reflect a file move/rename without actually moving the file on disk. This would be useful when:
1. A file has already been moved manually or by an external tool
2. The user wants Git to recognize the move after the fact

The proposal is minimal at this stage - just the core idea without implementation details or discussion of edge cases. It appears motivated by practical workflow needs where files get renamed outside Git's control, but the commit message doesn't provide concrete examples of such scenarios.

This would be a new user-facing feature requiring careful design around:
- Naming the flag (e.g. `--index-only` vs `--no-move`)
- Handling cases where the source file still exists
- Interaction with other `git mv` options like `--force`
- Whether to support directory moves

The change would touch the builtin/mv.c implementation and require updates to documentation. No patch is attached yet - this appears to be an RFC to gauge interest before implementation work begins.
