This is a follow-up in the thread about adding an index-only move option to `git mv`. Frieder Hannenheim provides additional context about their specific use case where they manually modified a patch's filename and commit message, making the move undetectable by Git's automatic rename detection. They speculate that staging the files might have helped Git recognize the rename.

The email is responding to Chris Torek's earlier technical assessment that the same effect can be achieved through existing `git add`/`git rm` commands, with the proposed feature mainly offering convenience. Frieder's reply suggests their motivation comes from a real workflow pain point where Git's rename detection failed, though they acknowledge user error (not staging files) may have contributed.

This exchange highlights the tension between Git's automatic rename detection capabilities and cases where users need explicit control over recording moves. The thread continues to explore whether the convenience and explicit nature of a dedicated `git mv --index-only` would justify adding a new flag versus relying on existing commands and Git's rename detection heuristics.
