Thread summary:

Frieder Hannenheim proposes a new `git mv` feature to update Git's index for file moves without performing the actual filesystem move, with use cases involving external file renaming operations. The RFC-level proposal would modify builtin/mv.c and requires design decisions on flag naming, source file existence cases, and directory move support.

Chris Torek provides substantive technical review, noting the same index changes can be achieved through existing `git add`/`git rm` commands, with the main differences being ergonomics and minor CPU overhead reduction from avoiding redundant object lookups. He confirms Git's rename detection would behave identically regardless of implementation path. This positions the proposed feature as a convenience wrapper rather than fundamentally new functionality.

Key open questions remain:
- Whether the convenience justifies a new flag given existing alternatives
- Flag naming (`--index-only` vs `--no-move`)
- Edge case handling when source file persists
- Directory move support scope
- Interaction with `--force` and other existing flags

The thread now includes both the original use case motivation and a technical assessment of alternative implementations. No maintainer or additional reviewer feedback yet on whether the feature would be accepted if implemented. The next steps likely depend on whether Frieder revises the proposal to address the ergonomic vs fundamental value proposition raised in the review.
