Thread summary:

Frieder Hannenheim proposes a new `git mv --index-only` feature to explicitly record file moves in Git's index without performing filesystem operations, motivated by a workflow where Git's automatic rename detection failed after manual file renaming. The RFC-level proposal would modify builtin/mv.c to provide explicit move recording.

Chris Torek's substantive technical review notes the same index state can be achieved through `git add`/`git rm` sequences, positioning the feature as a convenience wrapper rather than fundamental new functionality. Frieder's follow-up provides concrete context where automatic detection failed due to unstaged changes, highlighting a tension between implicit rename heuristics and explicit move recording.

D. Ben Knoble reinforces Torek's technical assessment, confirming that `git add old new` produces equivalent index state to the proposed `--index-only` flag. His build system expertise lends weight to the position that existing commands already cover this functionality.

Key technical details:
- Would modify builtin/mv.c to skip filesystem operations
- Existing alternatives: `git add`/`git rm` pairs or `git add old new`
- Rename detection behaves identically in both approaches
- No new technical arguments introduced in latest email

Open questions:
- Whether convenience justifies new flag given multiple existing alternatives
- Flag naming (`--index-only` vs `--no-move`)
- Edge cases (source file persistence, directory moves)
- Interaction with `--force` and other flags
- How often automatic detection fails in practice

Participant positions:
- Frieder advocates for explicit move recording based on workflow pain points
- Chris and D. Ben acknowledge use case but question necessity given existing commands
- Technical consensus forming that functionality exists via other means

The thread now shows growing technical agreement that while the use case is valid, the proposed feature may not be necessary given current Git capabilities. The discussion awaits either new technical arguments for the flag or maintainer input on whether convenience merits inclusion despite functional overlap.
