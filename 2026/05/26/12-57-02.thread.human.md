This thread explores a proposal to add an `--index-only` flag to `git mv` that would update Git's index to record a file rename without performing the actual filesystem move. Frieder Hannenheim originally proposed the feature to handle cases where external tools rename files, making the changes undetectable by Git's automatic rename detection. In a follow-up, Frieder shared a concrete example where manually editing a patch's filename and commit message led Git to miss a rename, suggesting that staging the changes might have helped.

Chris Torek provided substantive technical review, noting that the same index updates can already be achieved with `git add` and `git rm`, making the new flag primarily a convenience feature. He confirmed that Git's rename detection would work the same either way. The discussion now centers on whether the convenience justifies a new flag, with open questions around naming (`--index-only` vs `--no-move`), edge cases, and interaction with existing flags like `--force`. Frieder's real-world example adds weight to the ergonomic argument, but the thread awaits maintainer feedback on whether such a feature would be accepted. The core tension is between relying on Git's rename heuristics versus giving users explicit control when needed.
