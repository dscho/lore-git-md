This is a substantive review from Junio Hamano on the `diff.<driver>.process` feature implementation, focusing on error handling and global state management in the diff subprocess protocol.

Junio raises several technical concerns about the current implementation:

1. **Global variables**: Questions whether the subprocess_map and its initialization flag need to be global, suggesting they could be attached to existing structures like `userdiff_driver` or `diff_options` instead.

2. **Error handling**: Identifies multiple cases where error conditions are either:
   - Not properly validated (like negative size parameter in send_file_content)
   - Silently falling back when they should report errors (like process startup failures)
   - Treating non-errors as errors (like when a driver lacks process configuration)

3. **Protocol behavior**: Suggests the implementation should more clearly distinguish between:
   - Normal non-error cases (no process configured)
   - Capability mismatches (not an error)
   - Actual failures that should be reported to users

The review indicates the technical approach is sound but needs refinement in how it communicates failures to users and manages process state. Junio emphasizes that some failures should not be silently fallback-able, as they indicate configuration problems users need to address.

This continues the thread's pattern of Junio engaging deeply with implementation details while maintaining skepticism about the feature's readiness until performance and documentation concerns are addressed. The review doesn't reject the approach but pushes for clearer error handling semantics before considering merge.
