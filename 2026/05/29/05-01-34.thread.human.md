This thread began with Wesley Schwengle reporting unexpected argument passing behavior in gitconfig-configured pre-push hooks, particularly when used with npm commands. The immediate issue was resolved with proper shell quoting (`command = "npm run test #"`), and the documentation in `githooks(5)` was updated to clarify the argument passing behavior. Jeff King (Peff) confirmed this behavior is intentional for backward compatibility, noting that pre-push hooks receive data through both arguments and stdin, which can cause issues for commands that read stdin.

The discussion has now shifted to documentation clarity. Peff points out that while the `git-hook(1)` manual shows an example with a custom wrapper hook (where the contract is tool-defined), it doesn't sufficiently distinguish this from native Git hooks like `pre-push` that have well-defined contracts. The current example using `pre-commit` with a linter is somewhat misleading when applied to `pre-push`, as it doesn't address how the script should handle the hook's expected inputs. Peff suggests expanding the documentation to better explain these nuances and has CC'd Adrian Ratiu, the original author of these docs, for awareness.

While the immediate technical issue is resolved, the thread has surfaced broader questions about hook architecture and documentation. The key remaining work is improving the documentation to clearly differentiate between native Git hooks (with fixed contracts) and custom wrapper hooks (with tool-defined contracts), particularly around argument handling expectations. This would help prevent similar confusion in the future while maintaining backward compatibility with existing hook scripts.
