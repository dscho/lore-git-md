This is a follow-up in the thread about config-based pre-push hook argument handling, where Wesley Schwengle reports that the suggested workarounds from Jeff King (Peff) don't work as expected in their environment.

Wesley demonstrates that both proposed solutions - using a comment character (#) to discard arguments and wrapping in a shell function - fail when tested. The comment approach still passes arguments to npm, while the shell function fails with a syntax error. This leaves wrapper scripts as the only viable solution, which Wesley finds suboptimal as it requires creating additional infrastructure for each test command.

The email raises a design question about whether config-based commands should receive hook arguments via stdin (like traditional hooks) rather than as command-line arguments, which would provide more consistent behavior between manual `git hook run` invocations and automatic execution during `git push`. This suggestion would represent a more fundamental change to how config-based hooks handle input compared to the current implementation.

The thread continues to explore the tension between the hook subsystem's general-purpose scripting design and the specific needs of hook implementers who expect traditional hook argument patterns. Wesley's testing reveals practical limitations in the current workarounds while proposing an alternative approach that could better align with existing hook conventions.
