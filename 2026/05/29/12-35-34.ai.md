This is a reply in the ongoing `git son` discussion thread, where Claus Schneider suggests an alternative approach to addressing the use case by improving submodules rather than introducing a new command.

Claus proposes modifying `git submodule` behavior to better support "loose" submodule relationships where the submodule is tracked by branch rather than pinned to a SHA. He references his own pull request (#1987) that makes submodules with `ignore=all` truly ignored in both `git status` and `git add` (requiring `--force` to stage them). This aims to reduce friction when developers want branch-tracked submodules without constant staging conflicts.

The email positions this as a potential solution to the original motivation for `git son` - creating repositories with looser coupling than traditional submodules. Claus invites the thread participants to try his submodule changes and identify any remaining gaps that would still necessitate a new `git son` command.

This represents a substantive counter-proposal to the original RFC, suggesting that the desired functionality might be better achieved by evolving existing submodule capabilities rather than adding new porcelain. The response continues the thread's focus on whether the use case merits a new command versus leveraging/extending current mechanisms.
