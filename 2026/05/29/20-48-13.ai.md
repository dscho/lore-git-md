This is the third revision of an RFC series introducing a new `diff.<driver>.process` configuration that allows external tools to inject diff hunks into Git's diff and blame pipelines. The key changes since v2 include:

1. **Subprocess management refactoring** (new patch 3) - Separated process lifecycle from hashmap management to allow storing the subprocess on the userdiff_driver struct rather than in a global hashmap.

2. **Improved error handling** - Differentiated between tool failures (warn and fall back), "not configured" (silent fallback), and voluntary abort (silent fallback with no further requests).

3. **Single public API** - Consolidated the interface into `diff_process_fill_hunks()` which handles driver lookup, flag checks, subprocess management, and error reporting for both diff.c and blame.c.

4. **Protocol documentation** - Rewrote the gitattributes documentation section with packet diagrams and fully specified hunk format.

5. **Bypass knobs** (new patch 5) - Added support for `--no-ext-diff` and format-patch to skip the diff process.

6. **Robustness improvements** - Added SIGPIPE protection, stricter input validation, and const correctness.

The core functionality remains allowing specialized tools (like AST-based diff tools) to participate in Git's diff processing while preserving downstream features like word-diff and color-moved. The protocol follows Git's established long-running process pattern from the filter subsystem.

Key technical points:
- Uses pkt-line protocol for communication with external tools
- Tools can mark files as unchanged (no hunks) which affects both diff output and blame attribution
- Falls back gracefully to builtin diff on errors
- Includes thorough test coverage (660 lines) of success/error paths

The blame integration shows how this could be used to skip reformat-only commits in history analysis. Performance remains a consideration - the current implementation adds ~17% overhead to blame operations due to per-commit roundtrips, though an OID-based optimization is noted as future work.

The series appears technically sound with comprehensive test coverage. The main open questions are around performance optimization and final documentation refinements before potential acceptance.
