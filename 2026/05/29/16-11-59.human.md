This is a follow-up in the thread about config-based pre-push hook argument handling. Wesley Schwengle reports that Jeff King's suggested workarounds (using a comment character or shell function to discard arguments) don't work as expected in their testing. The `npm run test` command still receives the unwanted remote/URL arguments when triggered by `git push`.

The email reveals two key findings:
1. The `#` comment approach fails because the shell still includes the arguments before processing the comment
2. The shell function approach fails with a syntax error, likely due to how Git's shell invocation processes the command

Wesley expresses frustration that this forces every hook command to implement argument-handling wrappers, diverging from the simpler behavior of traditional hooks that receive data via stdin. They suggest that having config-based hooks follow the stdin pattern would provide more consistent behavior between manual and automatic hook invocations.

The response maintains the technical focus while highlighting the practical usability concerns that remain unresolved by the current workarounds. The core tension is between the hook subsystem's design philosophy (where callers control arguments) and user expectations shaped by traditional hook behavior.
