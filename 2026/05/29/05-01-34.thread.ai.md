Thread summary:

Subject: Question about argument handling in config-based pre-push hooks

Core issue: Wesley Schwengle reports unexpected argument passing behavior when using gitconfig-configured pre-push hooks. While manual `git hook run pre-push` works as expected, automatic execution during `git push` passes remote name/URL arguments that interfere with their `npm run test` command. This reveals a documentation gap in `git-hook` man pages regarding argument control for config-based hooks.

Current status: Jeff King (Peff) confirms the current argument passing behavior is expected, as the `git hook` command doesn't enforce hook-specific argument conventions. He provides two shell-based workarounds for discarding unwanted arguments (#` comment character or shell function). The thread remains open for discussion about documentation improvements or potential configuration knobs.

Technical details: The setup uses `hook.pre-push.event` and `hook.pre-push.command` gitconfig directives. Automatic push passes remote info arguments while manual runs pass none, differing from traditional hook scripts which consistently pass ref/object pairs. Peff explains this stems from config-based hooks being a general scripting interface where the caller controls argument passing.

Key participant positions:
- Jeff King (Peff): Confirms current behavior is by design, provides practical workarounds, suggests documentation clarification. Views this as consistent with hook subsystem philosophy.

Open questions: Should documentation be updated to clarify argument passing behavior? Are additional configuration knobs needed for argument control in config-based hooks? The original issue has workarounds but the design/documentation questions remain.
