This is a follow-up discussion in an ongoing thread about improving `git log --follow`'s with merge commits, particularly for subtree use cases.

The patch author Miklos Vajna is responding to Jeff King's earlier suggestion about how to handle rename detection in merge commits. Miklos proposes a tweak to Jeff's original idea - rather than requiring all but one parent to be TREESAME (unchanged), he suggests also treating file additions as uninteresting changes since they imply no prior history to follow.

The key technical point is that this approach would:
1. Still work for Miklos's subtree use case
2. Avoid changing behavior when files have history on multiple parents
3. Handle the case where a file appears as an addition in one parent (common in subtree workflow)

Miklos acknowledges this isn't a complete solution for all `--follow` edge cases with merges, but suggests it's a reasonable incremental improvement while larger rework would be needed for more comprehensive fixes. He's specifically seeking Jeff's feedback on whether this adjusted approach seems sound before proceeding.
