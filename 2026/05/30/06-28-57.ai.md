This is a follow-up discussion in an ongoing thread about improving `git log --follow`'s with merge commits, particularly for subtree merges. The patch aims to better handle rename detection in merge scenarios where files are added in one parent but renamed in another.

Miklos Vajna responds to Jeff King's earlier suggestion about choosing which merge parent to follow based on path changes. He proposes a tweaked rule: when a path is either untouched *or just added* in all parents except one, follow the parent where it was meaningfully changed. This refinement addresses Jeff's concern about being too strict with the TREESAME requirement while still handling Miklos's subtree use case.

The key technical distinction here is between "added vs parent" (which Miklos argues should count as uninteresting for following purposes) versus actual content changes. Miklos acknowledges this is a narrower fix than a potential rework of `--follow`'s merge commit handling, but suggests it's a practical first step.

The discussion remains open-ended, with Miklos seeking Jeff's feedback on whether this adjusted approach seems reasonable before proceeding. The exchange demonstrates careful consideration of edge cases (subtree merges) while trying to avoid regressing other scenarios.
