**Patch 5/5 of the `branch --prune-merged` series -- adds the `--all-remotes` flag.**

This is the final piece of Harald Nordgren's v7 series. The patch adds an `--all-remotes` option that, when combined with `--forked` or `--prune-merged`, operates on every configured remote rather than requiring explicit `<remote>` arguments. Used alone, it dies with an error.

The implementation is clean and proportional. A new `OPT_BOOL_F` with `PARSE_OPT_NONEG` is added in `cmd_branch()`. A `collect_remote_name()` callback feeds into `for_each_remote()`, and the existing `collect_forked_set()` and the two callers (`list_forked_branches()` and `prune_merged_branches()`) gain an `all_remotes` parameter. The error messages adjust slightly: the commands now require "at least one <remote> or --all-remotes" rather than just "at least one <remote>", and a standalone `--all-remotes` is rejected explicitly.

The documentation updates the synopsis lines in `git-branch.adoc` from `--forked <remote>...` to `--forked (<remote>... | --all-remotes)` (and similarly for `--prune-merged`), plus a short description entry explaining the flag's semantics.

The test suite adds four test cases in `t/t3200-branch.sh`. Two exercise `--forked --all-remotes`: one verifies the output list covers branches tracking multiple remotes, and one confirms that an explicit invalid remote name still triggers the proper error (the `--all-remotes` flag does not swallow validation). A third test confirms that `--all-remotes` alone is rejected. A fourth, more involved test sets up two remotes (`origin` and `other`), deletes both tracking refs, and verifies that `--prune-merged --all-remotes` cleans up both branches tracked to different remotes.

In the context of the full thread, this is the capstone patch. Patches 1-4 have already established the `--forked` listing mode, the warning infrastructure, the core `--prune-merged` logic with its upstream-fallback semantics, and the per-branch opt-out configuration knob. This patch simply makes those modes operate across all remotes at once, which is the natural convenience feature. The test coverage looks thorough: both modes are vetted, error paths are exercised, and the multi-remote scenario is explicitly tested.
