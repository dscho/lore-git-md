This thread is about a single-patch bugfix from Miklos Vajna for `git log --follow` when used with subtree merges. When a file comes into a repository through a subtree merge (where another repository's history is merged into a subdirectory), `git blame --follow` already handles this correctly by checking each parent of a merge commit for renames. However, `git log --follow` does not -- it returns early from merge commits without attempting per-parent rename detection, so it loses the pre-merge history of the file from the inner repository.

The fix is a small, roughly 20-line addition to `log-tree.c`. In the merge-commit branch of `log_tree_diff()`, it adds a loop that checks each parent with `diff_tree_oid()` and, if a follow is found, breaks out of the parent loop rather than returning, mirroring the logic already present in `blame.c`. The included test sets up two repositories where an inner repo's `inner.txt` is subtree-merged into an outer repo as `inner/inner.txt`, then asserts that `git log --follow inner/inner.txt` shows the "inner init" commit.

Vajna noted this is a resend after the initial submission received no replies and is sending it directly to Junio for review. There is no visible discussion yet and no known objections. The patch is self-contained, well-structured, and its approach is validated by existing precedent in `blame`. It looks ready for review and likely merge.
