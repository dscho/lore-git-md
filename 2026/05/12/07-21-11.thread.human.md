This thread discusses a bugfix patch from Miklos Vajna addressing `git log --follow`'s failure to track file history across subtree merges, where files first appear via a subtree merge. While `git blame --follow` already handles this case correctly, `git log --follow` shows only post-merge commits, missing pre-merge history. The patch modifies `log-tree.c` to check merge parents similarly to `blame.c`.

Junio Hamano initially responded that while the patch isn't technically wrong, it may not be the right direction given `--follow`'s inherent limitations with merge commits. He suggested seeking input from domain experts, leading the author to explicitly request reviews from Elijah Newren (merge expertise) and Jeff King (diff/performance).

Jeff King has now weighed in with a substantive technical analysis. He agrees with Junio's assessment, noting that even with the patch, `--follow` would still have fundamental limitations with merge commits. Peff questions whether making the current behavior slightly more useful is actually an improvement, as it would still arbitrarily choose one parent's path over others. He suggests exploring whether existing history-simplification flags could help, but remains unconvinced the current patch is the right approach.

The thread now awaits further input from Elijah Newren and potentially others, while the core question remains whether to accept this incremental improvement or hold out for a more comprehensive solution to `--follow`'s merge handling limitations.
