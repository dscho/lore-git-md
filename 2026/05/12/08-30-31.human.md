This is **Patch 2 of a two-patch bugfix series from Patrick Steinhardt**, fixing a regression in how Git's auto-maintenance honors the `gc.auto` config key.

The problem is a clear user-facing regression. Historically, setting `gc.auto=0` was the standard way to disable automatic `git gc` (for example, when using a separate cron job for garbage collection). When Git transitioned from `git gc` to `git maintenance` as the default auto-maintenance strategy, `gc.auto` still worked because the new code shelled out to `gc` internally, which honored the key itself. But a more recent change removed that internal `gc` call, meaning `gc.auto=0` quietly stopped having any effect.

The fix is straightforward: `prepare_auto_maintenance()` now checks `gc.auto` when `maintenance.auto` is not explicitly set, using `repo_config_get_int()` (correctly -- this was fixed from v1 which used `repo_config_get_bool()` by mistake). The precedence logic is that `maintenance.auto` (the newer config key) takes priority when present, but `gc.auto` is used as a fallback for backward compatibility.

This is the patch that drew the substantive review in v1 from both Jeff King and Junio C Hamano, who independently caught the `repo_config_get_bool()` type error. V2 incorporates that fix and is otherwise clean.

The commit message is well-structured, clearly explaining the chain of events that led to the regression (with specific commits cited), and the test coverage is good -- both the basic `gc.auto` behavior and the `maintenance.auto`-overrides-`gc.auto` precedence are tested. The series is ready for merging; with both the lockfile fix (patch 1) and this config fix, the maintenance subsystem regressions introduced during the `gc`-to-`maintenance` transition should be fully resolved.
