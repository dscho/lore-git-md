**Classification:** Bugfix, part 2 of a 3-patch series (v2) targeting Git's approxidate date parser. This is the core fix patch.

**Summary:** This is the second patch in Tuomas Ahola's three-patch series fixing long-standing bugs in Git's fuzzy date parser, and it directly tackles the main user-visible problem that the series was written for.

The "special" time keywords in Git's approxidate parser -- "noon" and "tea" (5 PM) -- have a built-in rule: they always refer to the *most recent* occurrence of that time in the past. So if it is currently 11 AM, "noon" wraps back to yesterday. This rule fires even when an explicit day has been provided. That means "10 May at tea" and "last Friday at noon" can produce a day that is obviously wrong, contradicting the explicit date the user gave. The commit message helpfully illustrates this with a concrete example: given a "now" of 2026-05-12 11:00, the input "10 May at tea" yields 2026-05-09 instead of 2026-05-10. The author also references a two-decade-old bug report from Linus Torvalds complaining about exactly this behavior.

The fix is remarkably simple: in the `date_time()` function, check whether `tm_mday` has already been set to a non-negative value (meaning a specific day was provided), and if so, skip the rollback logic entirely. This is a three-line change to `date.c`. The patch also adds `"today"` as an alias for `"now"` in the specials table, so that inputs like "today at noon" parse correctly (the existing alias infrastructure makes this a one-liner).

The test additions are sensible: new cases for "today at noon", "last Friday at noon" (twice, once at offset 0 and once at -12 hours to cover the morning-vs-afternoon edge case that patch 1/3 enabled), and "January 5th noon pm" at the -12 offset. These demonstrate that the fix works regardless of the current time of day.

This is a clean, well-motivated patch with a very narrow scope and minimal code change. The commit message is clear, includes a concrete motivating example, and responsibly cites the 2006 bug report. The fix is straightforward enough that it seems unlikely to be controversial, though the earlier v1 received active review from Jeff King, so it is worth watching for his reaction to this revised approach. The test infrastructure from patch 1/3 is put to good use here, covering both sides of the day-rollover boundary.
