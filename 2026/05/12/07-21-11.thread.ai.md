**Thread identity**: Subject: `git log --follow` fails to follow files across subtree merges. Single-patch bugfix, v2 (resend of earlier version). Author: Miklos Vajna. Thread type: bugfix patch.

**Core problem or goal**: Fixes inconsistency where `git log --follow` fails to track file history across subtree merges (when a file first appears via a subtree merge), while `git blame --follow` already handles this case correctly. The issue occurs when a file exists only in a subtree-merged inner repository - `git log --follow` shows only post-merge commits, missing pre-merge history.

**Current status**: Patch v2 sent after v1 received no replies. Junio Hamano responded to author's ping with technical context about `--follow`'s inherent limitations with merge commits, shifting the discussion from implementation correctness to design philosophy. No technical objections raised, but maintainer indicates patch addresses only a narrow case of a feature with known broader limitations.

**Key technical details**: Modifies `log-tree.c` to add parent-checking loop in `log_tree_diff()` for merge commits, mirroring `blame.c`'s existing logic. Before early return, iterates over parents with `diff_tree_oid()` to find file under different path/name. Sets `found_follow` if found, allowing parent walk. Test case constructs two-repo scenario with subtree merge (inner.txt -> inner/inner.txt) and verifies `git log --follow` shows inner repo's initial commit. Junio's follow-up explains `--follow` was designed for linear history and fundamentally struggles with merges where files have different names in different branches.
