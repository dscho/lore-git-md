**Core problem or goal**: `git log --follow` fails to follow a file across merge commits when that file first appeared via a subtree merge. Specifically, when a file lives only in a subtree-merged inner repository, `git log --follow <path>` shows only the post-merge outer-repo commits, missing the pre-merge history from the merged-in project. `git blame --follow` already handles this case correctly by checking each parent of a merge with `diff_tree_oid()` and `try_to_follow_renames()`.

**Current status**: Patch has been re-sent (no replies to v1). No objections or concerns raised. Appears ready for review and likely merge.

**Key technical details**: One file touched: `log-tree.c`. Adds a loop in `log_tree_diff()` in the merge-commit branch, before its early return, that iterates over each parent using `diff_tree_oid()` and checks whether the file can be found under a different path/name. If found, sets `found_follow` and breaks out of the parent loop (instead of returning immediately) so that the parent containing the file's earlier name can be walked. The logic mirrors the existing handling in `blame.c`. Test added: constructs a two-repo scenario with a subtree merge of an inner repo (containing `inner.txt`) into an outer repo (as `inner/inner.txt`), then asserts `git log --follow inner/inner.txt` shows the inner repo's initial commit. The test is registered in the Meson build file.
