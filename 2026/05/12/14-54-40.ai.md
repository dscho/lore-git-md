This is a review reply from Matthew Cheetham to patch 6/7 of Derrick Stolee's negotiation-control series, which adds the `remote.<name>.negotiationInclude` config option. This review is essentially two quick observations on top of the same reviewer's earlier thorough review of the series' analogous patch 4/7 (which added `remote.<name>.negotiationRestrict`).

Cheetham makes two points. First, the documentation cross-reference for value types says "same as for `--negotiation-restrict`" but should say "same as for `--negotiation-include`" to point each config option at its corresponding CLI flag. Second, one of the new tests checks that the empty-value reset works, but the test's assertions only verify that both `alpha_1` and `beta_1` appear in the trace -- and `alpha_1` is sent via a `--negotiation-restrict` CLI option, not via the config include list. So if the reset were broken and `alpha_1` were still being sent through the include list too, the test would still pass. It's a test-robustness issue, not a code bug.

This is a surface-level review -- two straightforward observations about documentation wording and test coverage, both of which are correct and easy to fix. Cheetham flags that the same points apply from his earlier review of patch 4/7 (the `parse_transport_option()` reuse and the fact that values can be commit SHAs as well as refs and globs), but does not re-litigate those issues here. No structural concerns about the patch itself.
