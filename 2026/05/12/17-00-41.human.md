This is a new standalone patch (not part of Harald's `--prune-merged` series) that introduces a `fetch.pruneLocalBranches` configuration option for `git fetch`. The idea is simple: when `git fetch --prune` removes a remote-tracking branch because the upstream branch was deleted, also delete the corresponding local branch that was tracking it.

The patch is a one-off reply in a thread about Harald's `--prune-merged` series -- specifically, it is responding to Junio questioning whether the core safety assumptions of the `--prune-merged` feature make sense. Harald's covering note frames this as a "nuclear option" -- a more aggressive automated cleanup than `--prune-merged` -- which he offers up almost as a thought experiment in response to Junio's skepticism.

This is clearly RFC-quality, not submission-ready. The patch content gives the game away: it reuses `collect_forked_set()` from Harald's own `--prune-merged` series, a function that has not been accepted yet. The commit message is thin -- just a few lines saying "this is what the patch does" with no discussion of safety, edge cases, or the potential for data loss. There are no tests. The implementation appears to hook into the prune callback and call `delete_branches()` with `warn_only`, but the logic for deciding which local branch to delete is not explained in the commit message and the code is not shown in the quoted patch.

This patch is unlikely to be picked up as-is. It depends on unreviewed infrastructure from the `--prune-merged` series, it lacks a safety story, and it was apparently written as a rough sketch to stimulate discussion rather than as a serious candidate for inclusion. The reply from Junio or others will likely point out that deleting a local branch whose remote-tracking ref was pruned is different from the `--prune-merged` scenario -- here there is no merged-ness check at all, so you could lose work. The interesting engineering question is whether this *should* have some merged-ness safety built in, or whether it is deliberately bare-bones as the "nuclear" option its author describes it as. But for now, this is a discussion piece, not a patch anyone should spend time reviewing in depth.
