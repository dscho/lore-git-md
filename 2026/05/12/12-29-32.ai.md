**Classification:** Bugfix integration review (review of patch 4/7 in Derrick Stolee's negotiation control series)

Matthew Cheetham provides a substantive review of patch 4/7, which adds `remote.<name>.negotiationRestrict` config support. The review catches two real issues and raises one consistency question.

The first issue is a documentation claim: the commit message and the new config documentation say the option works for "`git fetch` and `git push`", but at this point in the series the push path has not been wired up yet. Cheetham points out that the `prepare_transport()` arm added in this patch for reading the config is unreachable on the `push.negotiate=true` path because `send-pack.c` shells out to `git fetch --negotiate-only` with explicit `--negotiation-tip=<oid>` args, meaning the CLI restrict list is always non-empty and the new config-reading `else if` is never taken. Patch 7 will wire up push support, so Cheetham suggests either dropping "and `git push`" from this patch's documentation or adding a clarifying note that `push.negotiate` must be set for the config to be honored during push.

The second issue is a logic error in the `--negotiate-only` error handling. The patch moves the existing "needs one or more" die-check from before `prepare_transport()` to after it, but the new condition fires whenever `gtransport->smart_options` is NULL -- which previously would have been handled by a separate warning-and-cleanup path a few lines later. This means a user running `--negotiate-only` against a non-smart transport gets a confusing "needs one or more --negotiation-restrict=*" message even if they did specify restrict options. Cheetham correctly identifies that the condition should use `&&` instead of `||` to preserve the existing non-smart-transport handling.

Cheetham also raises a consistency question: the `remote.<name>.negotiationRestrict` config handler treats NULL value as a reset (like the other `parse_transport_option()`-based handlers do), but unlike those handlers it *also* treats NULL as a reset rather than as an error. This is a minor observation rather than a bug, since NULL values from the config layer are unlikely in practice, but it points to a possible inconsistency worth aligning.

The review is well-grounded, identifying concrete code paths and behavioral corner cases rather than offering stylistic opinions. The issues are real but small -- mostly documentation precision and a boolean logic fix -- and should be straightforward for the author to address in the next iteration. No fundamental problems with the design are raised and the reviewer signals that, aside from these points, the shape of the patch is good.
