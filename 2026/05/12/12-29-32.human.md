This is a substantive review of patch 4/7 in Derrick Stolee's
negotiation control series. The reviewer, Matthew Cheetham, has been
working through the whole series and clearly understands both the code
and the upcoming patches -- he explicitly reads ahead to patch 7 before
filing his observations.

The patch adds `remote.<name>.negotiationRestrict` as a multi-valued
config option that serves as the default for `git fetch
--negotiation-restrict` when fetching from a specific remote. The
reviewer raises one concrete correctness issue and two documentation
suggestions.

**A logic bug in the `--negotiate-only` path.** The reviewer spots that
a new `die()` condition in `cmd_fetch` fires whenever
`gtransport->smart_options` is NULL -- but that case was previously
handled further down by a `protocol does not support --negotiate-only`
warning. A user who runs `git fetch --negotiate-only` against a
non-smart transport will now see `"fatal: --negotiate-only needs one or
more --negotiation-restrict=*"` even if they provided
`--negotiation-restrict` options. The reviewer suggests the condition
should use `&&` instead of `||` so the die only triggers when the
transport *does* support smart options but no restriction tips were
configured. This looks like a genuine bug that would cause a confusing
error message.

**A documentation claim about push support.** The commit message says
the config applies "during `git fetch` and `git push`", but push
negotiation is only wired up in patch 7. Between patches 4 and 7, the
`else if (remote->negotiation_restrict.nr)` branch in
`prepare_transport()` is never taken on the push path because
`send-pack` shells out to `git fetch --negotiate-only` with explicit
`--negotiation-tip` arguments, making the restrict list non-empty and
bypassing the config fallback. The reviewer suggests either dropping the
push mention from this patch's documentation, or adding a note that
`push.negotiate` must be enabled for the config to take effect during
pushes.

**An inconsistency in empty-value handling.** The new
`remote.negotiationRestrict` config treats both NULL and empty string as
"reset the list", while `parse_transport_option()` (used by
`serveroption` in the same file) treats NULL as an error
(`config_error_nonbool`) and only the empty string as a reset. Minor
consistency nit, but worth noting since it is in the same code area.

Overall the review is thorough and well-informed -- the reviewer caught
a plausible runtime bug, the doc claim issue that would confuse readers,
and a consistency quirk, all while clearly understanding how this patch
interacts with the rest of the series. No fundamental objections to the
approach. The `--negotiate-only` logic bug is the one item that probably
warrants a reroll.
