This is a review from Junio C Hamano on patch 3/5 of Harald Nordgren's v7 series, and it raises fundamental design questions that the earlier thread summaries did not flag as still open. This is not a minor nit -- Junio is questioning whether the whole safety-check rationale makes sense.

Junio's core objection is that the patch's logic conflates two different scenarios. The patch assumes the remote-tracking branch has been *pruned* (deleted by the remote owner), and then falls back to the remote's default branch as a merged-ness anchor. Junio argues this is nonsense: a remote's default branch is not something you expect to disappear, and if it *did* disappear, falling back to some other arbitrary branch cannot provide safety. He rephrases the scenario to make his point explicit -- the feature is designed for the case where you forked from `origin/next`, pushed, and `next` later got pruned at the remote. But why, Junio asks, would a branch that others fork from be pruned? And if it *were* pruned, how would you know whether the topic branch's commits were safely integrated elsewhere?

He also questions the `no_head_fallback` parameter introduced in patch 2 as a new knob threaded through `branch_merged()`. He suggests the same effect could be achieved more simply by just passing NULL for `head_rev` from `check_branch_commit()` when doing `--prune-merged`, without adding a new parameter.

This is substantive review from the project maintainer, and the concerns go to the heart of whether the feature's safety model is sound. The earlier thread summary described this as "awaits Junio's review" with "no outstanding issues" -- that characterization should be revised. Junio is not asking for small wording changes; he is asking Harald to rethink whether the upstream-fallback logic is defensible at all, and whether the parameterization of `branch_merged()` is clean. The series is not as close to integration as the thread summary implied.
