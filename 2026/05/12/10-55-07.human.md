## `--track=fetch` feature, v9

This is the ninth iteration of Harald Nordgren's patch to let `git checkout` and `git switch` accept `--track=fetch`, which fetches the remote ref before creating the local tracking branch -- collapsing the usual two-step `git fetch && git checkout -b` into a single command.

The headline change in v9 directly addresses what the maintainer flagged in v8: the ambiguity when a remote name itself contains a slash (e.g. `nested/remote`). The previous logic naively split on the first `/`, so a start-point like `nested/remote/branch` would have been misparsed as remote `nested` / branch `remote/branch`. The new `resolve_fetch_target()` now tries the *longest* prefix first, walking backward through the string to find a configured remote match. This is a principled fix: it matches how Git already resolves ambiguous hierarchical remote names elsewhere. A test case confirms the new behavior works.

The other open item from Junio's v8 review -- folding the pre-fetch existence check into `resolve_fetch_target()` so that it returns the existing ref directly rather than having the caller reconstruct it -- has also been cleaned up. The function now populates an `existing_ref_out` parameter, and `fetch_remote_for_start_point()` uses that instead of doing its own second lookup. This simplifies the caller and removes a minor code smell from the previous round.

The feature itself is unchanged in terms of user experience: `git checkout -b new_branch --track=fetch origin/some-branch` fetches `some-branch` from origin, sets up tracking, and checks out the new branch. Bare remote names like `origin` still fetch only the default branch. An offline failure that has an existing ref becomes a warning rather than a fatal error. The `fetch` flag can be combined with `direct` or `inherit` (e.g. `--track=fetch,inherit`), and invalid combinations like `inherit,direct` are rejected.

This feels like the most polished round yet. The author has methodically addressed every piece of technical feedback as it came in, and this version's approach to the slash-in-remote-name problem is both correct and consistent with existing Git conventions. The 12 test cases cover the obvious happy paths and failure modes. The main remaining question is not technical but social: the maintainer's earlier objection was about the feature's place in the workflow rather than its implementation, and he did not revisit that in his v8 review. Whether his detailed code engagement in v8 -- now fully addressed -- signals acceptance or simply due diligence is uncertain, but there is not much left for a reviewer to ask for technically.
