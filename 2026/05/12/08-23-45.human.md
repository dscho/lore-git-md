This is feature patch 1/5 in the v7 series from Harald Nordgren, adding `git branch --forked <remote>` to list local branches whose configured upstream lives on a given remote. The design point that held up v6 -- how merged-ness is determined -- has been resolved in the cover letter's description, but this patch itself doesn't touch that logic; it's a pure listing command.

The patch introduces two new mechanisms. First, `parse_forked_args()` accepts either a configured remote name (`origin`, matching any `refs/remotes/origin/*` tracking ref) or a specific remote-tracking branch (`origin/master`), and dies with a clear error if neither matches. Second, `branch_is_forked()` checks each local branch against the union of the given remote names and tracking refs by inspecting the branch's upstream configuration. The implementation is straightforward -- `refs_for_each_branch_ref()` collects matching branches, sorts them, and prints.

There is one thing worth flagging. This patch uses `the_repository` directly in `repo_dwim_ref()` and `get_main_ref_store()` rather than threading a repository pointer through. That is fine for now -- `cmd_branch` always operates on the main repository -- but if the series eventually wants to handle worktrees or submodules it would need to be cleaned up. It is not a blocker for this patch.

The test suite is thorough: setup creates two upstream repos and a clone with mixed tracking branches (`origin/one`, `origin/two`, `other/foreign`, and a detached branch), then covers remote-name mode, specific-tracking-ref mode, union across multiple arguments, and both error cases (unknown remote, missing argument). This is solid coverage for a listing command.

This patch looks clean and ready. The real discussion for this round will be on patches 3-5 where the deletion logic and the fallback behavior are implemented.
