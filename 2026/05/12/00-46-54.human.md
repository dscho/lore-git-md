**Bugfix patch, part of Taylor Blau's nine-patch series fixing pseudo-merge bitmap bugs.**

This is patch 3 of 9, fixing a sorting bug in the pseudo-merge commit lookup table. The pseudo-merge code maintains a lookup table that maps commits to their position in pack order so the reader can binary-search to find which pseudo-merge(s) a commit belongs to. The bug was that the table was being sorted lexicographically by OID (via `oid_array_sort()`) instead of by bit position (pack order), which made the binary search fail entirely.

The patch has two parts. First, it replaces `oid_array_sort()` with `QSORT_S()` using a new comparator `pseudo_merge_commit_pos_cmp()` that sorts by `find_object_pos()` -- pack order. This makes the writer produce what the reader already expects. The commit message is candid about the practical impact: pseudo-merge application during the initial phases of bitmap traversal (`cascade_pseudo_merges_1()`) worked correctly because it uses a different code path. The broken part was the fill-in traversal, which relies on the binary search. Importantly, the bug did not produce *wrong* bitmaps -- it just silently fell back to the non-pseudo-merge fill-in routines, meaning pseudo-merges were effectively useless for this second code path but the results were still correct, just slower.

Second, the test `t/t5333-pseudo-merge-bitmaps.sh` changes one expectation from `test_expect_failure` to `test_expect_success` for the test that exercises applying pseudo-merges during fill-in traversal. The `test_when_finished` ordering fix that Elijah Newren noted (moving it above `git init`) is also included in this patch.

This is a clean, well-motivated fix. The commit message does a good job of explaining why the bug was not catastrophic and why the on-disk-format change is safe (the documented format was correct; only the writer was wrong). This is a straightforward candidate for merging, and with Junio having already signaled readiness for the series, this patch in particular should be uncontroversial.
