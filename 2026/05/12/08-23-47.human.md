This is patch 3 of 5 in the v7 series by Harald Nordgren, which is where the main functional logic lives: adding `--prune-merged <remote>` as a deletion command that pairs with the `--forked` listing command from patch 1.

The semantics are carefully designed in response to Junio C Hamano's concern from the v6 review. `--prune-merged` works by first collecting the same candidates that `--forked <remote>` would list, then filtering further: it only deletes a branch if the remote-tracking branch it would push to (the "push destination" per `branch_get_push()`) no longer exists locally. This means the branch was pushed upstream under some name, and that upstream tracking branch has since been pruned. As a safety check, before deleting, the code verifies that the branch is fully merged into its own upstream remote-tracking branch -- and if that upstream is itself gone, it falls back to the remote's default branch (`refs/remotes/<remote>/HEAD`). If neither exists, the branch is refused. The `--force` flag overrides the merged-ness check and deletes unconditionally, but the checked-out branch in any worktree is always preserved regardless.

A subtlety worth noting: the patch also wires the `no_head_fallback` parameter -- threaded through `branch_merged()`, `check_branch_commit()`, and `delete_branches()` in patch 2 -- into the pruney deletion path. This means `--prune-merged` does not compare candidate branches against the local `HEAD` as a merged-ness baseline at all; it only consults the upstream or the remote default branch. That is correct behavior for a remote-prune command, where you care about integration with the remote, not with your local checkout.

The test coverage is thorough -- fourteen new test cases covering the fallback scenario, the both-gone scenario, checked-out branch protection, the interaction with branches whose push destination is the remote default branch, and the full set of edge cases around `--force` behavior.

This is the heart of the series. Patches 1 and 2 were mechanical setup; patch 3 is where the actual design decisions land. If the merged-ness logic holds up under review, the remaining two patches (the `branch.<name>.pruneMerged` config opt-out and the `--all-remotes` convenience flag) are straightforward extensions. This looks ready for close attention.
