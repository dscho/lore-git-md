**Key technical details** -- New function in `strbuf.h` and `strbuf.c`: `void strbuf_add_uint(struct strbuf *sb, unsigned int value)`. Formats via `x / 10` and `x % 10` into an on-stack buffer, then appends with `memcpy()`. Call-sites converted: `builtin/cat-file.c`, `builtin/ls-files.c`, `builtin/ls-tree.c` (patches 2-4). Overall delta: 38 insertions, 14 deletions. Benchmark on `git cat-file --batch-all-objects --batch-check='%(objectsize)'` from 751.7ms to 720.4ms (approx. 4% speedup). Patch 3 (ls-tree.c) handles field-width padding via `strbuf_insert()` with `memmove()` -- marginal gain. No test changes, no new config keys, no on-disk format changes, no CLI options.

Rene later sent a follow-up email (after the review cycle had closed) reporting an empirical experiment: he tested whether `__builtin_add_overflow()` could be faster than the existing `unsigned_add_overflows()` pattern in `strbuf_grow()`. Using godbolt, he found Clang and GCC on x86-64 emit identical instructions for both, but Clang on ARM64 fails to optimize away a redundant comparison when using `unsigned_add_overflows()`. He then patched `strbuf_grow()` to use `__builtin_add_overflow()` and benchmarked on his Apple M1 (Apple's Clang), getting a 2% speedup on `git cat-file --batch-all-objects --batch-check='%(objectname)'`. The same patch had no effect with GCC 15.2. This was a casual, collegial aside -- not a patch submission or a request for inclusion. The diff was provided only for illustration. Rene gave no indication he intends to send this as a separate patch.
