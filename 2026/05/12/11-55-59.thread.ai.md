Core problem or goal: Replace four existing uses of `strbuf_addf(sb, "%"PRIuMAX, (uintmax_t)value)` with a specialized function `strbuf_add_uint()` that formats an unsigned integer directly via a simple division loop, avoiding the overhead of the full printf machinery. This is a performance optimization for high-volume output commands.

Current status: v1 submitted and reviewed. The series has received all the review it needs; it is ready to be picked up by the maintainer. No further iteration is expected. Jeff King confirmed the change is both a performance win and a readability improvement.

Key technical details:
- Files touched: `strbuf.h`, `strbuf.c`, `builtin/cat-file.c`, `builtin/ls-files.c`, `builtin/ls-tree.c`
- New function: `void strbuf_add_uint(struct strbuf *sb, unsigned int value)` added to strbuf interface. Formats the integer as a decimal string using a loop of `x / 10` and `x % 10` operations, writing digits to a small on-stack temporary buffer in reverse then appending to the strbuf with `memcpy()`. Located in `strbuf.c` with declaration in `strbuf.h`.
- Call sites converted (patches 2-4): `cat-file.c`, `ls-files.c`, `ls-tree.c` -- all replace `strbuf_addf(... PRIuMAX ...)` with `strbuf_add_uint()`.
- Overall delta: 38 insertions, 14 deletions across 5 files.
- Benchmark (from patch 2, reviewed by Peff): `cat-file --batch-all-objects --batch-check='%(objectsize)'` went from 751.7 ms to 720.4 ms, a 4% speedup.
- No test changes needed (behavior is identical).
- No new symbols, config keys, CLI options, or on-disk format changes.
- Patch 3 (ls-tree.c conversion) additionally handles field-width padding by formatting the number into the strbuf, then using `strbuf_insert()` to shift content right if padding is required. Peff noted this involves a `memmove()` that could diminish the performance gains in that specific caller.

Open questions and loose ends:
- None resolved yet, and none are expected. The one design question -- why not format directly into a pre-grown strbuf? -- was raised and resolved by Jeff King in the earlier review: formatting right-to-left is simpler, computing the digit count up front would require a log-10 calculation with off-by-one pitfalls, and the extra `memcpy()` from the temporary buffer is acceptable overhead. No changes requested.

These were musings, not demands for a v2. No changes requested, and no action required.
