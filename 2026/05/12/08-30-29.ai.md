This is a **v2 cover letter** for a two-patch bugfix series from Patrick Steinhardt, correcting two issues in Git's maintenance subsystem that were flagged in the v1 review.

The series addresses two distinct problems. The first patch fixes a lockfile leak when running `git maintenance run --detach`. In detached mode, the parent process exits without releasing the lockfile it holds, leaving a stale lock that blocks subsequent maintenance runs. The v1 fix used this approach; v2 clarifies a comment (per Junio's feedback during the v1 discussion) to say "we drop ownership of the lockfile to prevent us from removing it upon exit" rather than the misleading original phrase about "assigning ownership to the child." This is the only substantive change in patch 1 going from v1 to v2.

The second patch restores the correct `gc.auto` threshold behavior. When Git's auto-maintenance was transitioned from `git gc` to `git maintenance`, the new code in `prepare_auto_maintenance()` began reading `gc.auto` with `repo_config_get_bool()`. But `gc.auto` is an integer config key -- it stores a loose-object count threshold, not a boolean. This broke the expected behavior for users who set `gc.auto` to a non-boolean value. The bug was independently flagged by both Jeff King and Junio C Hamano in the v1 thread; Patrick has accepted the finding and switched to `repo_config_get_int()` in v2. This was the only substantive change in patch 2.

The range-diff confirms minimal changes from v1: the comment rewording in patch 1, and the config-reading fix in patch 2. The series touches `builtin/gc.c`, `lockfile.c`, `lockfile.h`, `run-command.c`, and `setup.h`, plus new tests in `t/t7900-maintenance.sh`.
