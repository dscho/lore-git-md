This is a small, targeted bugfix for `git log --follow` that extends rename-following to work through merge commits, specifically addressing the common case of subtree merges.

Today, `git log --follow file.c` on a subtree-merged repository only shows commits from the "outer" repo, not the commits that happened before the subtree merge into the subdirectory. This is inconsistent with `git blame -- file.c`, which does find the pre-merge commits. The fix is straightforward: when `log_tree_diff()` encounters a merge commit and would normally return early, it now checks each parent using `diff_tree_oid()` in the `follow_renames` case, just as `git blame` does. If a rename is detected across one of the parents, it stops on that parent and proceeds to follow history into it.

The patch is small -- twenty lines in `log-tree.c` -- plus a new test and a meson build registration. The test sets up a textbook subtree-merge scenario (two unrelated repos, an `-s ours` merge with `read-tree --prefix`) and checks that `--follow` finds the pre-merge commit.

The motivation is clearly stated and the problem is easy to reproduce. The approach is conservative: reusing the existing `try_to_follow_renames` infrastructure rather than designing new machinery. A closer look might want to understand whether there are edge cases where `follow_renames` interacts poorly with other merge-reduction logic, but on its face this looks like a safe and welcome improvement.
