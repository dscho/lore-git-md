This is a **bugfix** patch (the second of two) by **Patrick Steinhardt**, fixing a regression where setting `gc.auto=0` no longer suppresses automatic maintenance runs. The context provided confirms it is the v2 version; the only substantive change from v1 is the switch from `repo_config_get_bool()` to `repo_config_get_int()` for reading the integer-valued `gc.auto` key, correcting a type error that both Jeff King and Junio C Hamano flagged in the v1 review.

The root cause is a chain of internal changes over the past several years. Originally, `git gc` respected `gc.auto` directly. When the project transitioned to `git maintenance run --auto`, the new code still shelled out to `git gc` internally for most work, so `gc.auto=0` continued to work as before because `git gc` itself still honored it. That indirect dependency broke when the default maintenance strategy stopped calling `git gc` -- code path that previously hit `git gc`'s own config check no longer did, and the newer `maintenance.auto` config key that replaced it was the only one checked. Users who relied on `gc.auto=0` to prevent background maintenance from running silently lost that ability.

The fix is in `prepare_auto_maintenance()` in `run-command.c`. The logic now reads `maintenance.auto` first; if that config key is unset (which is the common case), it falls back to checking `gc.auto` as an integer. If `gc.auto` is set to 0 or a negative value, maintenance is disabled. If `maintenance.auto` is explicitly set, it takes precedence over `gc.auto`. This matches the pattern already used elsewhere in the same function for the `autoDetach` keys, where both `maintenance.autoDetach` and `gc.autoDetach` are read.

The commit message is well-written and clearly explains both the regression and why the fix is correct rather than a hack. The tests in `t/t7900-maintenance.sh` cover three cases: that `gc.auto=1` still allows maintenance, that `gc.auto=0` suppresses it, and that `maintenance.auto` correctly overrides `gc.auto` in both directions. This is a clean, well-motivated fix for a user-reported regression that the thread summary reports was independently confirmed by core reviewers. Barring unexpected new concerns, this patch is in good shape for `next`.
