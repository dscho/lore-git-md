This is a bugfix / user experience improvement that qualifies Git's status hints. When `git status` shows that a local branch is behind or has diverged from a push branch (as opposed to the upstream branch), the advice previously suggested `git pull` with no arguments, which would follow the upstream -- potentially a different remote entirely. This patch changes the advice to say `git pull <remote> <branch>`, making the suggestion actually useful for push-branch users. It also enables the pull and divergence advice hints for push-branch comparisons; previously, both were only enabled for the upstream comparison.

The change touches `remote.c`, adding two new parameters to the internal `format_branch_comparison()` function, and extends `format_tracking_info()` to extract the push remote and branch name when processing a push-branch comparison. The caller-side plumbing is straightforward: when iterating over branches to compare, both `is_upstream` and `is_push` comparisons now set the advice flags (formerly only upstream did). The new test cases in `t/t6040-tracking-info.sh` cover the "behind" and "diverged" cases, including a remapped push refspec to ensure the extracted branch name matches what the user would type.

The patch is small and well-scoped, with a clear motivation and tests that directly validate the output. It addresses a genuine usability shortcoming for anyone who uses `status.compareBranches` or `push.default = current` and gets a `git pull` hint that leads to the wrong branch. No controversial design decisions here -- it is a simple matter of quoting the right remote and branch in the hint text. The only subtlety is the extraction logic for `push_branch_name` from the refspec, which strips the `refs/remotes/<remote>/` prefix; the skip_prefix dance handles the common case but could theoretically fail for unusual refspecs (e.g., with no `refs/remotes/` prefix), in which case the code degrades gracefully to the unqualified `git pull`.
