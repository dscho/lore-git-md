This is a review of patch 5/7 in Derrick Stolee's v3 negotiation-control series. The patch implements the new `--negotiation-include` option for `git fetch`, which guarantees that specified ref tips are always sent as "have" lines during negotiation -- a complement to the restricting `--negotiation-restrict` introduced earlier in the series.

The reviewer is Matthew Cheetham, and this is a **substantive review** that engages with the code's actual behavior rather than surface-level issues. Cheetham identifies a potential correctness concern about how the COMMON flag is being used to suppress duplicate "have" lines from the negotiator, and raises a design consistency question about where refs-to-OIDs resolution happens for the two complementary options.

The review makes several key observations. The most technically significant is about the COMMON flag. In `find_common()`, the patch marks OIDs from `--negotiation-include` as COMMON (bit 6, `fetch-pack.c`'s version) to prevent the negotiator from also outputting them. But Cheetham correctly notes that there are two independent COMMON bits defined in the codebase: bit 6 in `fetch-pack.c` (set after server confirms a common object) and bit 2 in `negotiator/default.c` (used internally by the negotiator's `get_rev()` to decide whether to emit a commit as a "have"). The patch is setting bit 6, but the negotiator only checks bit 2. This means the deduplication logic works correctly on protocol v2 (which uses an `oidset_contains()` check that is independent of flags) but may produce duplicate "have" lines on protocol v0/v1 -- a real bug if Cheetham's understanding is correct. The reviewer qualifies this with appropriate humility ("if my assessment is correct, then we'd see a duplicate I think?") but the analysis of the two distinct COMMON bits is precise and well-grounded in the code.

Cheetham also raises a design consistency question: `--negotiation-restrict` resolves its refs to OIDs in the builtin layer (`add_negotiation_restrict_tips()` in `builtin/fetch.c`), but `--negotiation-include` passes the raw `string_list` to the transport layer and resolves it there in `fetch-pack.c`. The reviewer observes that these are doing essentially the same work (resolving ref names and globs to object IDs), just outputting to different data structures (`oid_array` vs `oidset`), and asks whether future readers would benefit from resolving at the same layer. This is presented as a design-preference question, not a bug.

There are smaller observations too: the documentation for `--negotiation-include` uses `<revision>` as a placeholder but the description talks about ref names and globs, whereas `--negotiation-restrict`'s docs use `(<commit>|<glob>)` -- and since the implementation calls `repo_get_oid()`, bare OIDs and abbreviated SHAs work, so the syntax descriptions should align across the two options. Cheetham also notes a minor typo (`s/brances/branches/`).

Cheetham questions whether the silent-ignore behavior for missing refs (changed in this patch for both options) warrants an additional test case: the existing `--negotiation-tip rejects missing OIDs` test passes because it uses an all-zero OID which parses as valid hex, meaning the "object does not exist" path fires. A non-parseable name like `--negotiation-restrict=notreal` that previously died would now be silently ignored -- a behavioral change that probably deserves test coverage.

The tone is collegial and technically precise. Cheetham clearly read the code carefully, including the constants for the two COMMON flags (a detail easy to miss), and presents the potential v0/v1 duplicate-haves issue as an open question rather than a confirmed defect, inviting the author to clarify. This is a solid review that the author should engage with seriously.
