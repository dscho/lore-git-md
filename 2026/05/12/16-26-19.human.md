This is a bugfix from Jeff King (Peff) targeting the dumb HTTP transport, specifically how Git handles alternates advertised by an HTTP server that uses an absolute path.

The problem is a long-standing bug in `http-walker.c`, present since the very first alternate-support commit in 2005. When a dumb HTTP server reports an alternate as an absolute path like `/parent.git`, Git tries to combine it with the repository's own URL. It does this by finding the first slash after the `://` in the base URL and using that position to compute the "host portion" -- the part it keeps when pasting on the alternate path. But when the URL has no path component at all (e.g., `http://example.com` with no trailing slash), `strchr()` returns NULL, and the resulting calculation produces garbage. The analysis in the commit message is unusually thorough: Peff works through exactly what can happen with the resulting nonsense length (crash, silent misbehavior, or a very unlikely truncation attack) and concludes it is just a regular bug, not a security vulnerability.

The fix is trivial -- replacing `strchr(...)` with `strchrnul(...)` so that reaching the end of the string (NULL byte) is treated as a valid endpoint rather than an error. The accompanying test is honest about being "a little gross": it sets up a repository directly in the HTTP document root so that the fetch URL has no path component, then verifies that an absolute-path alternate actually works. The test requires `http.followRedirects` to be on, implying that the alternate-allowed check is involved.

This is a classic Peff patch: a narrow, well-analyzed bug that nobody has noticed for twenty years, fixed with a one-character change in the C code and a thorough but slightly awkward test. The commit message walks through all the failure modes in detail, which is worth reading for the analysis alone. The fix is obviously correct and will be low-controversy. Hardly urgent -- nobody is likely hitting this in practice -- but it is clean and complete.
