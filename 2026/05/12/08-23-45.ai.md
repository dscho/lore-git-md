This is **patch 1/5** in v7 of Harald Nordgren's branch-pruning series, adding the `--forked <remote>` flag to `git branch`. This is a building-block patch for the `--prune-merged` option in a later patch.

`git branch --forked <remote>` lists local branches whose configured upstream (their `branch.<name>.merge` setting) falls within the given remote. The remote argument can be either a configured remote name (e.g. `origin`, matching all its refs) or a specific remote-tracking branch (e.g. `origin/master`). Multiple remote arguments are unioned. The implementation parses arguments into two lists — configured remote names and specific remote-tracking refs — then iterates over all branch refs via `refs_for_each_branch_ref()`, checking each branch's upstream with `branch_is_forked()`.

This is a well-structured patch. The code introduces three new functions — `parse_forked_args()`, `branch_is_forked()`, and `list_forked_branches()` — plus a callback struct and `collect_forked_branch()`. The argument parsing handles both remotes and tracking refs, dying with a clear message if an argument matches neither. The logic correctly handles branches not configured with an upstream (they are rejected), branches tracking the named remote (accepted), and branches tracking a specific upstream ref (accepted). Tests cover the basic cases: listing by remote name, by specific tracking ref, unioning multiple arguments, rejecting unknown arguments, and requiring at least one argument. The `--forked` flag is wired into the action-disambiguation logic alongside the other non-list actions.

The motivation is clear and the implementation is straightforward. This patch does not introduce the deletion machinery — it is purely a listing mode. One observation: `branch_is_forked()` uses the string-comparison approach from v6, which is fine for this listing patch since it is only matching against live upstreams; the downstream `--prune-merged` patch will add the more complex merged-ness checking logic that required the fallback-to-remote-default-branch refactoring described in the cover letter.

The tests are thorough and follow existing conventions in `t3200-branch.sh`. The code integrates cleanly into `cmd_branch()` and respects the existing action-mutual-exclusion guard.

This patch looks ready. It is well-scoped, well-tested, and the only thing it does is provide the listing mechanism. The interesting design complexity lives in the later patches in the series.
