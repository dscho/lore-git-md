This is a bug report from Daniel Mach at SUSE, describing a crash when `git clone --dissociate` is used with a reference repository that has a commit-graph. The reproducer is attached as a shell script.

**Bugfix** targeting the clone + commit-graph interaction. Not part of a larger series; a standalone report with a reproducer.

The user found that `git clone --dissociate --reference <old-repo>` fails during checkout with `fatal: unable to parse commit <SHA>`, leaving the clone in an incomplete state where `git status` works but the initial checkout did not complete. Omitting `--dissociate` avoids the problem, as does passing the `-c core.commitGraph=false` workaround.

The report includes a plausible root cause analysis: during dissociation, Git repacks objects from the alternate and removes the `objects/info/alternates` file, but the clone process has already opened the alternate's commit-graph. After the alternate is no longer valid, the clone does not invalidate or reload the object store, so it tries to parse commits using a commit-graph that references the now-unlinked alternate, causing the parse failure. This diagnosis is attributed to an AI assistant and the author flags it as such, which is an honest caveat. The key piece of supporting evidence is that a manual `git checkout` immediately after the failure succeeds, confirming the repository is sound and the corruption is in the in-memory state of the clone process.

The report is well-structured: clear symptoms, a reproducer (verified by the author), a plausible explanation, and a workaround. The commit message does not overclaim -- the root cause is stated as AI-generated and caveated. This looks like a real bug rather than a user error, and the provided reproducer should make it straightforward for a maintainer or contributor to confirm and fix. The fix will likely involve invalidating the commit-graph or reloading the object store after the dissociate operation completes.
