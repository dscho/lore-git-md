This is a **review of patch 1 in a two-patch bugfix series**, from Taylor Blau.

The patch addresses a lockfile leak when `git maintenance run --detach` runs: the parent process exits without releasing the lock, leaving a stale lock that blocks future maintenance. Patrick's v2 fix introduces a new helper function `daemonize_without_exit()` and adjusts the one call-site in `builtin/gc.c` to manually reassign lockfile ownership to the child process before the parent exits.

Taylor Blau is **not a surface-level reviewer here** -- this is a substantive engagement. He has been working on essentially the same problem (he previously shared his own sketch of the fix, linked in the message) and is advocating for a different design approach. He argues that lockfile ownership transfer should happen **automatically inside `daemonize()` itself**, not manually at each call-site. His reasoning is that every future caller that daemonizes is going to want this behavior, and making it automatic prevents it from being forgotten. He acknowledges that if an exception ever arises, a `daemonize_without_transfer()` could be added then.

This is not a blocking objection -- Taylor frames it as a design preference, not a correctness issue, and offers to co-author and sign off if Patrick adopts the automatic approach. He also praises the test for the `--detach` locking behavior, calling the FIFO-based approach used in the test "much more robust" than his own sketch.

Bottom line: the review is a substantive design discussion, not a rejection. Nothing wrong with the patch as sent, but the reviewer feels strongly that the fix should live in `daemonize()` rather than at the call-site. Whether this gets resolved in this series or deferred is up to the author. The patch was previously considered ready for `next`; this is a new wrinkle to watch.
