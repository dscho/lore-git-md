This is patch 4 of 5 in Harald Nordgren's v8 series adding `git branch --prune-merged`, implementing a per-branch opt-out mechanism via a new config option.

The patch introduces `branch.<name>.pruneMerged` (defaulting to true), which when set to `false` exempts that specific branch from `--prune-merged` operations. This is designed for topic branches that the author wants to keep around between development rounds after an initial version has been merged upstream. Notably, `--force` does not override the opt-out -- the commit message explicitly states this. Explicit deletion via `git branch -d` remains unaffected, as the third test confirms. When a branch is skipped due to the config, a warning message is printed (unless `--quiet` is in effect).

The implementation in `builtin/branch.c` is straightforward -- roughly 25 lines of new code in the `prune_merged_branches()` loop. After the existing checks (checked-out branch, resolvable upstream, default-branch-name protection), it reads `branch.<name>.pruneMerged` from the config and skips the branch if the value is false. The documentation changes update both the config documentation and the `--prune-merged` description in `git-branch.adoc` to mention the new option.

The test coverage is thorough and well-designed: three tests covering the basic opt-out scenario (one branch protected by config is kept while a sister branch without the config is deleted), confirmation that `--force` still respects the config, and confirmation that `branch -d` bypasses the restriction entirely.

This represents strong, complete feature design: when the upstream-reachability safety check (patch 3) already protects branches that are not integrated, a config-based opt-out addresses the user's actual need -- "keep this branch around even though it *is* integrated and would otherwise be pruned". The decision to make it stick past `--force` is deliberate and correct for the use case: if a developer explicitly marks a branch as "do not prune me", force should not override that intent. All three tests pass cleanly. The implementation is minimal and clean, the commit message explains the motivation and the `--force` behavior, and the tests cover all stated edge cases.
