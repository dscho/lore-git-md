This is a bugfix patch targeting `git log --follow` behavior in merge commits, specifically the case where a file appears in the repository only through a subtree merge. The author, Miklos Vajna, is following up on a previous send that received no replies, submitting directly to Junio for review.

The problem is a real inconsistency: `git blame --follow` already handles renames across merge commits (including subtree merges) by checking each parent of a merge, using `diff_tree_oid()` and the `try_to_follow_renames()` machinery. But `git log --follow` does not, because its merge-handling code returns early without attempting the same per-parent rename detection. The result is that a user who has a subtree merge (e.g., an inner repository merged into a subdirectory of an outer repository) sees only the post-merge "outer repo" history when running `git log --follow path`, missing the earlier commits from the merged-in project.

The patch is a small, targeted addition of roughly 20 lines to `log-tree.c`. In the merge-commit branch of `log_tree_diff()`, right before the early return, it adds a loop that checks each parent with `diff_tree_oid()` and sets `found_follow`. If found, it breaks out of the parent loop rather than returning, allowing subsequent parents (the one that contains the file under a different name or path) to be walked. The logic mirrors how `blame.c` already handles this -- the author explicitly notes this relationship in the commit message.

The test is straightforward: it builds a two-repo setup where an inner repository with one commit containing `inner.txt` is subtree-merged into an outer repository as `inner/inner.txt`. Then it asserts that `git log --follow inner/inner.txt` shows the "inner init" commit, which would not have appeared before the fix. The test is registered in the Meson build file, which is the current build system being adopted alongside the traditional Makefile.
