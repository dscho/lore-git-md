This is a **bugfix** patch for `git maintenance --detach`, part 1 of a 2-patch series. The author is Patrick Steinhardt.

The problem is straightforward: `git maintenance run --detach` creates a lockfile to prevent concurrent maintenance processes, but the lock's lifetime is broken. The parent process creates the lock, then forks and exits immediately (the standard daemonize pattern). Since the parent's exit triggers cleanup of the lockfile, the lock only covers the brief interval before the child takes over, not the full duration of maintenance work. A second maintenance invocation can run concurrently, defeating the purpose of the lock.

The fix introduces two new primitives. `daemonize_without_exit()` is a variant of the existing `daemonize()` that returns the child PID to the parent instead of calling `exit(0)` in the parent. `lock_file_reassign_owner()` allows transferring ownership of a lockfile's tempfiles from one PID to another, so the atexit handler of the old owner won't unlink them. The maintenance code then uses these together: after forking, both the parent and child reassign the lockfile's ownership to the child PID; the parent exits without cleaning up the lock, and the child now owns it and will clean it up when *it* exits.

The existing `daemonize()` is reimplemented as a wrapper around `daemonize_without_exit()` for backward compatibility -- there is no behavior change for existing callers.

The patch includes a new test in `t7900-maintenance.sh` that uses FIFOs to precisely sequence the parent exit, verify that the lock file is held by the parent's PID while the child runs, and then confirm the lock is released when the child finally exits. This is a thorough, well-constructed test that validates the specific failure mode.
