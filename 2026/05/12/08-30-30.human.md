This is a **bugfix** from Patrick Steinhardt addressing a specific problem in `git maintenance --detach`.

When `git maintenance` is run with `--detach`, the parent process forks and exits immediately, but the lockfile that prevents concurrent maintenance processes is created and owned by the parent. Because the parent cleans up its tempfiles on exit (and the child doesn't inherit the lockfile's ownership), the lock only covers the startup phase, not the actual background tasks—opening a window for concurrent maintenance runs to interfere with each other.

The fix introduces two new internal functions: `daemonize_without_exit()`, which forks but lets the parent keep running rather than calling `exit(0)`, and `lock_file_reassign_owner()`, which transfers the tempfile lock ownership to the child process after fork. The parent then exits after the handoff, and the child holds the lock for the full duration of its work.

This is a clean, well-supported patch. It has been seen by Peff, Taylor Blau, and Derrick Stolee (all thanked in the commit message), and it includes a thorough FIFO-based test that verifies the lock exists while the child runs and disappears after the child exits. The test also confirms the lock's PID matches the parent process, not the child.

This is part of a small series (patch 1/2), so it's worth watching the companion patch to see the full picture. The change itself is well-scoped and clearly motivated; the only thing to note is that the lockfile API is getting a new public function (`lock_file_reassign_owner`) which other potential forking callers might want to use, so there may be some discussion about generalizing the approach further.
