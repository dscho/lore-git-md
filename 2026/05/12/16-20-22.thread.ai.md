**Thread identity:** "pretty: remove possible overflow in rfc2047 encoder" -- single-patch cleanup, Jeff King (Peff). Standalone patch; no series version.

**Core problem or goal:** Remove a single `strbuf_grow(sb, len * 3 + strlen(encoding) + 100)` call from `pretty.c`'s RFC 2047 email header encoding path. On 32-bit systems, `len * 3` can overflow `SIZE_MAX` with extremely large inputs (~1.4GB author names), triggering undefined behavior. The line was originally a direct buffer sizing from 2007 that became pure dead optimization when the code was converted to use strbufs later that same year.

**Current status:** Patch is correct and accepted. Junio C Hamano replied with approval ("Very nice.") and suggested a broader cleanup -- systematically removing all ineffective `strbuf_grow()` calls that are immediately followed by a `strbuf_addX()` call that will grow the buffer on its own. Peff agreed with the idea, characterizing it as a `#leftoverbits` item (acknowledged but not prioritized), and added a practical caution: anyone picking this up needs to read the full function context, not just the immediate line, because there might be a subtle dependency on the grown buffer that is not obvious from the two-line pattern. He then sketched a concrete example from `builtin/fast-import.c`'s `mktree()` where removing the `strbuf_grow()` call would also allow deleting the entire pre-computation loop that calculates `maxlen` (a net reduction of about a dozen lines). The thread is concluded. No further action required for Peff's patch.
