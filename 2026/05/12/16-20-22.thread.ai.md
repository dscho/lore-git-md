**Thread identity:** "pretty: remove possible overflow in rfc2047 encoder" -- single-patch cleanup, Jeff King (Peff). Standalone patch; no series version.

**Core problem or goal:** Remove a single `strbuf_grow(sb, len * 3 + strlen(encoding) + 100)` call from `pretty.c`'s RFC 2047 email header encoding path. On 32-bit systems, `len * 3` can overflow `SIZE_MAX` with extremely large inputs (~1.4GB author names), triggering undefined behavior. The line was originally a direct buffer sizing from 2007 that became pure dead optimization when the code was converted to use strbufs later that same year.

**Current status:** Patch is correct and accepted. Junio C Hamano replied with approval ("Very nice.") and suggested a broader cleanup -- systematically removing all ineffective `strbuf_grow()` calls that are immediately followed by a `strbuf_addX()` call that will grow the buffer on its own. He cited examples from `apply.c` and `archive.c`. This is not a request to change Peff's patch; it is a "yes, and" suggestion for future work. The thread is effectively concluded.

**Key technical details:**
- File touched: `pretty.c`
- Symbol removed: one `strbuf_grow()` call, the only line changed
- Behavior change: none -- strbuf's built-in amortized growth handles all real-world inputs without measurable slowdown
- No test changes; the patch removes dead optimization code, not observable behavior
- Commit message addresses the obvious alternative (checked arithmetic) and explains why deletion is the correct approach
