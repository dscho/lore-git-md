This thread introduces a fix for a real bug in `git maintenance --detach`. The problem is that when running maintenance in detached mode, the parent process acquires a lockfile to prevent concurrent maintenance runs, but then forks and exits immediately as part of the standard daemonize pattern. The parent's exit triggers cleanup of the lockfile, so the lock only covers the brief interval before the child takes over — a second maintenance invocation can run concurrently, which defeats the purpose of locking.

Patrick Steinhardt's two-patch series addresses this with two new primitives: `daemonize_without_exit()`, which returns the child PID to the parent instead of calling `exit(0)`, and `lock_file_reassign_owner()`, which transfers lockfile ownership so the parent's atexit handler won't unlink it. The maintenance code then has the parent transfer lock ownership to the child before exiting without cleanup. The existing `daemonize()` is reimplemented as a wrapper for backward compatibility. A new test using FIFOs to precisely sequence the parent exit and verify lock lifetime rounds out the series. Multiple Helped-by credits (from Peff, Taylor Blau, and Derrick Stolee) suggest the approach went through some prior discussion.

This is part 1 of a 2-patch series; the second patch presumably uses these primitives in the maintenance code. No objections or open issues have been raised so far.
