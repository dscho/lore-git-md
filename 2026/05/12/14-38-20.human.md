This is a substantive review by Matthew John Cheetham of patch 5/7 in Derrick Stolee's negotiation-control series. The patch adds `--negotiation-include` to `git fetch`, guaranteeing that specified refs are always sent as "have" lines during negotiation -- a complement to the previously-reviewed `--negotiation-restrict` option for monorepo scenarios where a release branch might otherwise be skipped.

Cheetham's review engages at a deeper level than the earlier patches in this series. He raises a genuine correctness concern about how the COMMON flag is used, and several thoughtful design questions about documentation and code organization.

The core technical issue is about duplicate "have" lines in protocol v0/v1. Cheetham correctly identifies that `find_common()` in `fetch-pack.c` marks the included OIDs with COMMON (bit 6), but the default negotiator's deduplication logic checks a *different* COMMON flag (bit 2) defined in `negotiator/default.c`. This means the pre-marking will not actually suppress the negotiator from re-emitting those same OIDs as "have" lines in protocol v0/v1. The protocol v2 path handles this correctly via an `oidset_contains()` check, but the v0/v1 path may produce duplicates. Cheetham frames this tentatively ("if my assessment is correct"), but the analysis looks sound -- this is a real bug that Stolee will need to address for v4.

Beyond the flag issue, Cheetham flags several smaller items: a documentation inconsistency where the `--negotiation-include` synopsis uses `<revision>` while the body describes it as a ref name or glob (the underlying code also accepts bare OIDs via `repo_get_oid()`); a missing test for the new silent-ignore behavior for missing refs (previously a fatal error, now silently skipped); and the fact that `resolve_negotiation_include()` duplicates the same ref-resolution logic as `add_negotiation_restrict_tips()` but outputs to a different data structure, which could be confusing for future readers.

The review is well-grounded and specific -- it names the exact functions, files, and flags involved, and includes a reproduction scenario for the potential bug. This is the most technically substantive review this series has received so far, and the COMMON-flag issue in particular is something Stolee should definitely look into before sending v4.
