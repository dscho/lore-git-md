This is a bugfix: the seventh patch in Taylor Blau's nine-part series fixing bugs in Git's pseudo-merge bitmap implementation. The series is effectively ready for merge -- Junio Hamano has signaled in his draft "What's cooking" that he considers it "so close to the finish line" and is awaiting this final update.

Patch 7 prevents a division-by-zero crash when the `bitmapPseudoMerge.*.sampleRate` configuration option is set to exactly 0. The validation previously accepted any value in the inclusive range `[0, 1]`, and a value of zero hit a code path in `select_pseudo_merges_1()` that divides by the sample rate. In C, dividing `1.0 / 0.0` yields infinity; casting infinity to `uint32_t` is undefined behavior, and on most platforms produces 0, making the subsequent `j % 0` a fatal arithmetic trap.

This path was unreachable until patch 6 fixed the date-classification bug that had been silently classifying all commits as "stable" (where the sampling rate is not used). With the unstable path now live, the division by zero is exploitable. The fix is straightforward: the config validation is tightened from `0 <= rate <= 1` to `0 < rate <= 1`, and the config documentation is updated accordingly to say "greater than 0" rather than "between 0 and 1 (inclusive)". A previously-marked `test_expect_failure` in `t5333` is promoted to `test_expect_success`.

Three files are touched: `Documentation/config/bitmap-pseudo-merge.adoc` (the doc change), `pseudo-merge.c` (the bound check), and `t/t5333-pseudo-merge-bitmaps.sh` (the test promotion). This is a small, well-explained fix with no loose ends -- the kind of patch that should merge without further discussion now that the preceding patch has exposed the underlying issue.
