This is a bug report from Daniel Mach about `git clone` failing when the `--dissociate` option is used together with a reference repository that has a commit-graph.

The problem: `git clone <url> <dir> --reference <old-dir> --dissociate` dies with `fatal: unable to parse commit <SHA>` and a failed checkout, even though the resulting repository is structurally sound (a manual `git checkout` immediately after the failure succeeds). Omitting `--dissociate` avoids the problem entirely, which is a strong signal that the dissociation logic is at fault.

The root cause is well-summarized in Daniel's writeup (with an admitted AI assist). During a clone with `--reference`, Git's object store reads the alternate's commit-graph. When `--dissociate` later runs, Git repacks the objects and removes the alternates file but does not "forget" or reload the commit-graph it already loaded. That stale commit-graph still points into the now-disconnected alternate, so when the checkout tries to look up commits via the graph, Git can't find them.

The report includes a workable reproducer script and notes that `-c core.commitGraph=false` sidesteps the crash. This looks like a legitimate bug with a clear mechanism, not a configuration error. The fix likely lives in the clone/dissociate code path, where the in-memory commit-graph should be invalidated or the object store reinitialized after dissociation. A patch from someone familiar with the object-store initialization flow should be straightforward.
