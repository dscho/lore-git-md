This is a revised version of the previously abandoned config file locking timeout patch, now incorporating feedback from the earlier discussion. The patch adds configurable retry behavior when acquiring locks for config file writes, addressing race conditions in concurrent operations like `git worktree add -b`.

Key changes in v2:
- Introduces `core.configLockTimeout` config option (default 1000ms) following the same pattern as `core.packedRefsTimeout`
- Explicitly documents the read-after-lock semantics and last-writer-wins behavior
- Adds test coverage for both immediate failure (timeout=0) and successful retry scenarios
- Maintains backward compatibility with existing tests by forcing timeout=0 in test cases

The implementation builds on Microsoft's Scalar-specific solution while adapting it for core Git, using the same timeout mechanism as the packed-refs lock handling. The commit message thoroughly explains the tradeoffs and edge cases, acknowledging that while this doesn't solve all race conditions (same-key writes still race), it eliminates the common case of spurious failures from transient lock contention.

The patch appears well-considered and addresses the maintainers' earlier concerns about configurability and semantics. The test coverage is particularly thorough, validating both the happy path and edge cases. This represents a mature iteration of the concept that could potentially be reconsidered despite the earlier rejection.
