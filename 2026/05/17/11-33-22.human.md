This is a follow-up discussion in the ongoing RFC series adding merge commit support to `git history`. The thread focuses on error handling edge cases that surfaced during the implementation.

Johannes Schindelin (Dscho) responds to D. Ben Knoble's earlier query about error message improvements for cases where conflicts occur during `git history reword` operations. The core issue involves silent-success scenarios where merge conflicts should theoretically never happen but could occur due to edge cases or bugs. Dscho explains that while the original implementation treated these cases as successes, the increased complexity of merge handling makes explicit error messages necessary now.

The key technical point is that the error reporting occurs too late in the control flow - by the time the error is detected, the specific unrewritten descendants can't be identified, only the conflict state. Dscho acknowledges Knoble's suggestion for more detailed error messages but notes the current implementation only has access to a simple `int ret` status code at that point.

This exchange continues the thread's careful attention to edge case handling while maintaining the collaborative tone seen throughout. The discussion doesn't introduce new concerns but reinforces the thoroughness of the review process for this feature. The RFC status remains appropriate as these implementation details get ironed out.
