This is a technical discussion in response to Phillip Wood's substantive review of Johannes Schindelin's RFC patch series adding merge commit support to `git history`. The thread focuses on an edge case in the merge replay logic where new conflicts could be silently introduced.

Schindelin acknowledges Wood's discovery of a scenario where:
1. A merge commit O has parents B and D
2. B is rewritten onto E (creating E')
3. If E' and D conflict in ways that don't overlap with O's original conflicts, the current implementation would silently accept these new conflicts

The author confirms this is a real issue that needs addressing, particularly since the upcoming `fixup` subcommand would be affected. Schindelin is already working on a solution following Elijah Newren's design notes, though he expresses uncertainty about whether the conflict output will be sufficiently clear for interactive use cases.

The discussion remains technical and constructive, with Schindelin clearly receptive to the feedback. The thread shows active development work in progress to improve the merge replay functionality, with particular attention to edge cases in conflict resolution preservation. This exchange demonstrates the careful consideration being given to making `git history` robust for real-world merge scenarios.
