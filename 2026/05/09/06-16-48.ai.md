This is a follow-up in the ongoing discussion about `git diff --word-diff`'s whitespace handling. Johannes Sixt responds to Vincent Lefevre's demonstration that piping regular `git diff` output to GNU wdiff produces different results than Git's built-in word-diff for whitespace-only changes.

Johannes maintains that Git's current behavior is intentional and correct, noting there's no documentation requiring `--word-diff` to match GNU wdiff's output exactly. He challenges Vincent's implicit assumption that external tool behavior defines what Git "should" do, pointing out the lack of any documented requirement for parity with wdiff.

The exchange highlights a documentation gap - while Johannes is technically correct that Git's behavior is consistent with its own diff machinery, Vincent's point about user expectations shaped by other tools remains unaddressed. The thread remains at an impasse between "works as designed" and "doesn't meet some users' needs based on other tools they use."

Key technical details reinforced:
- Git's word-diff inherits the core diff engine's whitespace sensitivity
- The `-w` flag exists for whitespace-agnostic comparison
- No documented promise of GNU wdiff compatibility

The discussion now centers on whether this behavior/expectation mismatch warrants documentation clarification, behavior changes, or neither. Johannes' response suggests he sees no technical need for change, while Vincent's examples indicate some users may find the current behavior surprising.
