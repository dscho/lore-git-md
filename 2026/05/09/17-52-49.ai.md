This is a bugfix addressing a serious regression in Git's maintenance subsystem that can lead to repository corruption. Jeff King (Peff) identifies a critical locking issue in `git maintenance run --detach` that was introduced in v2.54.

The problem stems from how maintenance handles daemonization and locking:
1. The code takes a lock before daemonizing (forking)
2. The parent process exits after forking, triggering atexit handlers that release the lock
3. The child process continues running maintenance tasks (including repacks) without holding the lock
4. Multiple concurrent repacks can then corrupt the repository

Peff traces this to two commits:
- a6affd3343 (2024) introduced the broken locking pattern
- 452b12c2e0 (2026) made it dangerous by changing how repacks are run

The issue is particularly severe in v2.54 because the new geometric repack strategy runs without the additional locking that `git gc` previously provided. Peff suggests two potential fixes:
1. Properly transfer lock files during daemonization
2. As a short-term measure, revert 452b12c2e0 for v2.54.1

This builds on the ongoing thread about maintenance resource usage, now revealing a concrete corruption vector. The analysis provides technical details needed to understand the locking subsystem's interaction with daemonization, while also considering the practical implications for current users. The mention of a potential revert indicates this is being treated as a serious regression requiring prompt attention.
