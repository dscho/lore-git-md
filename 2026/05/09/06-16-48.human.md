This is a follow-up in the ongoing discussion about `git diff --word-diff`'s whitespace handling. Johannes Sixt responds to Vincent Lefevre's demonstration that piping regular `git diff` output to GNU `wdiff` produces different results than Git's built-in word-diff for whitespace changes.

Johannes maintains that Git's current behavior is intentional and correct, pointing out that the documentation doesn't promise compatibility with GNU wdiff's output format. He challenges Vincent to identify where the documentation this expectation is set, noting that the absence of such a promise means the current behavior isn't a bug.

The exchange highlights a documentation gap rather than a technical flaw - Git's word-diff inherits the core diff engine's whitespace sensitivity by design, but this design choice isn't clearly explained to users who might expect behavior matching external tools like wdiff. Johannes' response suggests the project's position is that the current behavior is correct unless proven otherwise by documentation, putting the onus on Vincent to identify specific documentation that sets different expectations.

This moves the discussion toward whether the documentation should be clarified to better set expectations about whitespace sensitivity in word-diff mode, rather than changing the implementation to match external tools. The thread remains unresolved but is narrowing to a documentation question.
