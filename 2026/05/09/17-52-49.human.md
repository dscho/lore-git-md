This is a bugfix discussion thread about a serious locking issue in Git's maintenance subsystem that can lead to repository corruption.

Jeff King (Peff) has uncovered a critical flaw in how `git maintenance run --detach` handles locking, particularly when running background tasks like repacking. The issue stems from the daemonization process incorrectly releasing locks that should remain held, allowing multiple concurrent repacks to run simultaneously - a known unsafe operation that can corrupt repositories.

The problem became much worse in Git 2.54 due to commit 452b12c2e0, which changed the default repack strategy to "geometric" while bypassing Git's normal locking mechanisms. Peff provides a detailed technical analysis showing how the lock is lost during daemonization and suggests two potential fixes: either reacquiring the lock after daemonizing or modifying the tempfile subsystem to properly transfer lock ownership.

Given the severity of the issue (demonstrable repository corruption) and its recent regression in 2.54, Peff suggests considering reverting 452b12c2e0 for an upcoming 2.54.1 maintenance release if the proper fix proves too complex to implement quickly. This builds on earlier discussion in the thread about unexpected resource usage, but now focuses squarely on a concrete, serious bug with clear reproduction steps and potential solutions.

The email highlights how what initially appeared as a resource management issue has uncovered deeper locking problem in the maintenance subsystem, with implications for both current users and the design of background operations. Peff's analysis provides clear technical direction for fixing the immediate issue while raising important questions about the subsystem's long-term robustness.
