This is a review of patch 3/5 in Harald Nordgren's v9 series adding `git branch --prune-merged` functionality. The review comes from Phillip Wood, who raises a design concern about the command's interface.

Phillip suggests the `--prune-merged` option should accept upstream branch arguments rather than remote names, making it more flexible for local workflows. He notes that the current remote-focused design creates an inconsistency where `git branch --prune-merged origin` would prune all branches tracking any remote branch from origin, rather than just those tracking origin's default branch (as one might expect from the analogy with `git checkout -b topic origin`).

The review proposes allowing glob patterns like `origin/*` to specify which upstream branches to consider, and suggests supporting local branches as upstreams (e.g., `git branch --prune-merged master` for topic branches tracking a local master). This would make the feature more versatile for both remote-tracking and local-only workflows.

Phillip's feedback doesn't challenge the technical implementation or safety model (which was already approved in v8), but questions whether the user interface aligns with common workflows. The review is substantive, engaging with the command's actual usage patterns rather than surface-level concerns.

This feedback introduces a new design consideration late in the series' review cycle, though the core functionality remains technically sound. The series had previously addressed all outstanding technical concerns, with Junio Hamano's only remaining objection (about `--force`) resolved in v9 by removing that option entirely.
