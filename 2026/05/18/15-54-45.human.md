This is a follow-up to Junio's "What's cooking" report regarding a proposed `--max-count-oldest` option for `git rev-list`. The author, Mirko Faina, acknowledges a bug when the option is used with `--boundary` and indicates an eighth version (v8) of the patch will be coming to address this.

The patch series (previously at v7) aims to add functionality to select the oldest N commits in a range rather than the default newest N. This appears to be a feature enhancement to the revision traversal machinery. The author's note suggests the implementation needs more work to properly handle boundary commits, which are special markers in Git's revision walk that indicate the edge of the commit graph being traversed.

No technical details about the specific bug are provided in this brief response, but the mention of `--boundary` suggests the issue relates to how the oldest-N selection interacts with these graph boundary markers. Given that this will be the eighth iteration, the patch appears to be receiving careful scrutiny and refinement.
