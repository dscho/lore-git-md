This is a technical response in the ongoing discussion about timeout handling for external Git notes helpers. Siddh Raman Pant defends the design of patch 4/9 in their series, which adds timeout support to `run-command.c` for managing misbehaving child processes.

The author makes several key arguments against Johannes Sixt's suggestion to use wrapper processes instead:
1. The normal protocol flow (Git sends OID, helper responds) doesn't require killing - timeouts are only for failure cases where the helper stops cooperating
2. Wrapper processes would need the same timeout logic, just pushed outside core Git
3. The current design allows graceful degradation (warn and disable misbehaving helpers) rather than hanging the main Git process

This response establishes a clear technical rationale for keeping timeout handling in core Git, framing it as necessary infrastructure rather than a band-aid. The exchange now presents two competing architectural visions:
- Sixt's position: Timeout handling indicates protocol flaws and belongs in wrapper processes
- Pant's position: Timeouts are essential for robustness and belong in core Git

The response doesn't address Sixt's concern about signal handling rationale, but does clarify that the primary use case is recovery from helper failures rather than normal operation. As this is part of a larger series, the timeout discussion may influence whether the feature lands in its current form or requires redesign.
