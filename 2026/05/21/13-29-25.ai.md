This is a design discussion in the final stages of Harald Nordgren's series adding `git branch --prune-merged` functionality. Junio C Hamano weighs in on Phillip Wood's earlier review about the command's interface.

Junio strongly endorses Phillip's suggestion to make `--prune-merged` work with local upstream branches (like `master`) rather than being restricted to remote-tracking branches. He demonstrates how this could be implemented by combining existing commands (`--forked` and `--merged`) with shell pipelines, showing the conceptual simplicity of the feature when generalized beyond remotes.

The discussion reveals an inconsistency in Git's existing behavior: while `git checkout -b topic origin` creates a branch tracking the remote's default branch (origin/HEAD), the current `--prune-merged` design would interpret `origin` as matching all branches under that remote (origin/*). Junio acknowledges this as his own oversight in the initial design review.

This email signals the maintainer's clear preference for a more flexible interface that supports both remote-tracking and local-only workflows. The technical implementation remains sound, but the series may need another revision to adjust the argument handling semantics before final acceptance. Junio's endorsement of Phillip's position makes this interface change likely to be implemented in the next version.
