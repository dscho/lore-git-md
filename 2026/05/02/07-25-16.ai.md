This is a technical follow-up in the thread about Git's rename detection behavior with Ruby files moved between namespaces. Johannes Sixt (Hannes) responds to Phillip Wood's earlier explanation and suggested workaround.

Hannes agrees with Phillip's technical assessment that indentation changes make the files appear too dissimilar for Git's rename detection, but points out a limitation in the proposed workaround. While splitting the change into two commits (move-then-modify) would help Git detect the rename when comparing adjacent commits (like in `git log`), it wouldn't solve the case when comparing commits across the entire change (before-move vs after-modify).

The exchange highlights an inherent limitation in Git's current rename detection approach for this Ruby-specific case - the similarity-based algorithm fundamentally struggles when structural changes (like namespace moves) affect every line of a file. Hannes doesn't propose an alternative solution but clarifies the scope of the workaround's effectiveness.

This continues the substantive technical discussion about Git's rename detection heuristics, specifically addressing when and why the proposed mitigation would or wouldn't work. The core issue remains open - whether Git should/could be enhanced to better handle such cases in Ruby or other languages with significant indentation changes during refactoring.
