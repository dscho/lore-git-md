**Key technical details:**

Core architecture moves filter logic into path-walk API (`path-walk.c`). Key implementation patterns:
- `blob:limit` checks each blob's size via `odb_read_object_info()` before emission.
- `sparse:oid` validates entire path groups against sparse-checkout patterns at once (biggest speedup: git/git sparse repack 77.91s to 31.41s).
- `object:type` adds `strict_types` flag to prevent direct object requests from bypassing type restrictions.
- `combine` filters use recursive `prepare_filters_one()` helper.

Patch details:
- **Patch 03/12:** New performance benchmark script `p5315-pack-objects-filter.sh`.
- **Patch 04/12 (always emit directly-requested objects):** Introduces `path_is_for_direct_objects()` heuristic checking if a path starts with `/`. Blau flags this as brittle but offers no alternative; admits limited familiarity with path-walk internals. Also suggests an `ASSERT()` to guard against a NULL path pointer. Neither concern is blocking.
- **Patch 06/12:** Replaces blanket rejection of `--filter` in `git backfill` with a call to `path_walk_filter_compatible()`. Blau engaged with the question of whether error messages should name which child filter is incompatible within a `combine` filter, then self-resolved that suggestion as impractical. No change requested.
- **Patch 07/12 (`blob:limit=<size>`):** Uses `odb_read_object_info()` during the path walk to check blob sizes. Blau asks whether this should use `odb_read_object_info_extended()` with `OBJECT_INFO_SKIP_FETCH_OBJECT` to avoid downloading blobs just to check their size in a partial clone, or temporarily disable `fetch_if_missing`. Blau admits he does not know enough about `git backfill` to judge which behavior is more appropriate. The parent summary confirms that `builtin/backfill.c` already has its own extra `blob:limit` guard for exactly this reason (backfill's batch-download strategy would be defeated by on-demand fetch); that guard may need updating if Blau's suggestion is adopted. Blau signed off with "The rest looks good to me." No change requested; question left for Stolee to answer.
- **Patch 10/12 (`tree:0` filter):** Suppresses all trees and blobs, keeping only commits and tags. Tagged trees collected into `/tagged-trees` pseudo-path. Non-zero tree-depths trigger fallback to standard revision walk.
- **Patch 11/12 (`object:type=<type>` filter):** Maps `LOFC_OBJECT_TYPE` onto per-type flags via bitwise AND. Fix: `handle_commit()` drops pending trees when `revs->tree_objects` is zero before path-walk sees them; fix sets `revs->tree_objects` during setup, resets to zero after `prepare_revision_walk()`. New `strict_types` flag gates direct-object-request bypass.
- **Patch 12/12 (`combine` filter):** Every supported child filter is a monotonic restriction, intersected via `path_walk_info`. `blob:limit` takes minimum; `sparse:oid` allowed once, refuses overwriting. `prepare_filters()` split into recursive helper.
