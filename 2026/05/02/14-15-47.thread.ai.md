The `git pack-objects --path-walk --filter` integration series (Derrick Stolee and Taylor Blau) is now at v3, a 12-patch series currently posted as a single submission batch. The series makes `--path-walk` work with `blob:none`, `blob:limit=<size>`, `sparse:<oid>`, `tree:0`, `object:type=<type>`, and `combine` filters. Derrick Stolee submitted the cover letter and changelog; Junio C Hamano's prior "What's cooking" check-in confirmed the topic is in final refinement.

The core technical decision in v3 is moving filter logic *into* the path-walk API (`path-walk.c`) rather than keeping it in `builtin/pack-objects.c`. Each filter type is handled in `walk_path()` and `prepare_filters()` dispatch. Key implementations: `blob:limit` checks each blob's size via `odb_read_object_info()` before emission; `sparse:oid` validates entire path groups against sparse-checkout patterns at once (producing the biggest speedups: e.g., git/git sparse repack from 72.53s to 29.00s); `object:type` adds a `strict_types` flag to prevent "direct object requests" from bypassing type restrictions; `combine` filters use a recursive `prepare_filters()` helper that walks child filters without releasing prematurely; `tree:0` gives tagged trees their own `/tagged-trees` pseudo-path so they are emitted when normal trees are suppressed.

The v3 changeset is substantial. Taylor Blau's three patches (for `tree:0`, `object:type`, and `combine`) are commits 10-12; Stolee has posted three additional bitmap-related patches on top.

Patch 04/12 is now posted. It fixes a correctness bug where the path-walk API would silently drop directly-requested objects (such as blobs needed for a partial-clone fetch) when a filter was active. The problem: the path-walk API classifies pending objects (targets of lightweight tags, ref tips, other explicitly-requested objects) using paths starting with `'/'` (e.g., `/tags`, `/tagged-blobs`). Prior to this patch, `walk_path()` applied the same blob/tree type filters to these as to tree-discovered objects, causing directly-requested objects to be skipped under filters. The fix: a new helper `path_is_for_direct_objects()` checks whether a path starts with `'/'`, and the type-filter logic in `walk_path()` now exempts those paths from the filter. The guards in `setup_pending_objects()` that skipped trees/blobs when their type flags were disabled are removed entirely. In `walk_objects_by_path()`, `blob_objects` and `tree_objects` are temporarily forced to `1` before `prepare_revision_walk()`, then restored to the correct filter values afterward. Documentation in `path-walk.h` and the AsciiDoc technical docs is updated to clarify that type filters only apply to tree-discovered objects, not pending ones. The commit message frames this as a prerequisite for the filter integration patches that follow, noting the bug was uncovered by `GIT_TEST_PACK_PATH_WALK=1`.
