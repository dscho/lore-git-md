The `git pack-objects --path-walk --filter` integration series (Derrick Stolee and Taylor Blau) is at v3, a 12-patch series currently posted as a single submission batch with an additional linked patch-set enabling `--filter` support for `git backfill`. The series makes `--path-walk` work with `blob:none`, `blob:limit=<size>`, `sparse:<oid>`, `tree:0`, `object:type=<type>`, and `combine` filters. Derrick Stolee submitted the cover letter and changelog; Junio C Hamano's prior "What's cooking" check-in confirmed the topic is in final refinement.

The core technical decision in v3 is moving filter logic *into* the path-walk API (`path-walk.c`) rather than keeping it in `builtin/pack-objects.c`. Each filter type is handled in `walk_path()` and `prepare_filters()` dispatch. Key implementations: `blob:limit` checks each blob's size via `odb_read_object_info()` before emission; `sparse:oid` validates entire path groups against sparse-checkout patterns at once (producing the biggest speedups: e.g., git/git sparse repack from 72.53s to 29.00s); `object:type` adds a `strict_types` flag to prevent "direct object requests" from bypassing type restrictions; `combine` filters use a recursive `prepare_filters()` helper that walks child filters without releasing prematurely; `tree:0` gives tagged trees their own `/tagged-trees` pseudo-path so they are emitted when normal trees are suppressed.

The v3 changeset is substantial. A key motivation was passing all tests with `GIT_TEST_PACK_PATH_WALK=1` -- which uncovered test failures in `t5620-backfill.sh` (fixed with a preliminary patch that disables the test variable for the three failing tests by setting `GIT_TEST_PACK_PATH_WALK=0` locally), required moving "directly requested objects" emission earlier in the walk, and prompted extensive test updates in `t6601-path-walk.sh`. Taylor Blau's three patches (for `tree:0`, `object:type`, and `combine`) are commits 10-12; Stolee has posted three additional bitmap-related patches on top.

Performance data across git/git, nodejs/node, microsoft/fluentui, and microsoftdocs/azure-devops-docs is included. The most striking results are for `sparse:oid` filters (often 2-3x faster). `blob:none` and `blob:limit` show modest speedups; the docs repo shows near-identical times. Space savings vary by repo. For `blob:none` specifically, the path-walk path is 73% slower on the test repo (23.43s vs 13.51s) but produces a 16% smaller packfile (115.2M vs 137.7M). Stolee frames this as a meaningful space benefit at the cost of two compression passes, an honest tradeoff for users deciding whether to enable this. Patch 05/12 adds `blob:none` filter support to the path-walk API. The approach: a new `prepare_filters()` function in `path-walk.c` checks the filter type; for `LOFC_BLOB_NONE` it sets `info->blobs = 0` (skipping all blob objects) and releases the filter options so `prepare_revision_walk()` does not reject the configuration. The same function is exposed as `path_walk_filter_compatible()` so `builtin/pack-objects.c` can check compatibility before the walk starts. Unsupported filter types produce an error and return 0. The three `t5620-backfill.sh` workarounds that disabled `GIT_TEST_PACK_PATH_WALK` are reverted, confirming the incompatibility is resolved. New tests in `t6601-path-walk.sh` verify the walk emits no blobs (only commits, tags, and trees) for `blob:none --all` and for a single-branch walk. A minor fix in the test helper replaces `REV_INFO_INIT` with `repo_init_revisions()` to properly initialize the filter strbuf needed for parsing. Documentation in `git-pack-objects.adoc` is updated to remove `--filter` from the list of incompatible options (though notably it still says "Whe" instead of "When" -- a typo). No review comments, objections, or discussion have been raised on this patch.

Patch 06/12 is a tiny but consequential correctness patch: it replaces a blanket check in `cmd_backfill()` that rejected *any* filter with a call to the newly introduced `path_walk_filter_compatible()` function. The cover letter from the same thread explains that `git backfill` uses the path-walk API as its core mechanism, with no fallback, so incompatible filters must be rejected early during argument validation rather than at walk time. The compatible filters for backfill are the same set as for pack-objects: `blob:none`, `blob:limit=<size>`, `sparse:<oid>`, `tree:0`, `object:type=<type>`, and `combine`. The new error message is `"cannot backfill with these filter options"` -- deliberately less specific than the old `"--filter"` rejection, telling the user *that* their filter is not supported but not *which* filters are viable. Two new tests in `t5620-backfill.sh` confirm that `--filter=tree:1` and `--filter=blob:limit=10m` are rejected with the expected message. The change is mechanically straightforward and well-tested; the only notable design point is the small UX regression from the generic error message, which may need updating if the compatible filter set grows.

Patch 07/12 adds `blob:limit=<size>` support to the path-walk API. In `prepare_filters()`, the limit value is stored in a new `info->blob_limit` field and the filter is cleared from `revs` so that `prepare_revision_walk()` does not reject the configuration. A limit of zero degenerates to `blob:none`, so `info->blobs` is set to 0 in that case. During `walk_path()`, blob batches are filtered per-object: each blob's size is checked via `odb_read_object_info()`, and only blobs strictly smaller than the limit are included in the batch delivered to the callback. Blobs whose size cannot be determined (e.g. missing in a partial clone) are conservatively included, matching the existing list-objects-filter behavior. Empty batches after filtering are skipped. A specific interaction with `git backfill` is noted: `odb_read_object_info()` will download a missing blob on-demand, which defeats the purpose of backfill's batch-download strategy. So `builtin/backfill.c` adds its own extra check to reject `blob:limit` explicitly with a new error message. The existing rejection test is updated to expect this new message. Test additions are thorough: a `blob:limit=0` test confirming equivalence to `blob:none` (emitting no blobs at all), and a `blob:limit=3` test that exercises partial filtering within a batch where some blobs are kept (`left/b`, `right/c`, `right/d`) and others are excluded -- notably blobs in the `a/` subtree are kept, but the `a` blob at the root-level tree is not, confirming the filter works correctly. The documentation in `git-pack-objects.adoc` is updated to list `blob:limit=<n>` alongside `blob:none` as a supported filter form (though the pre-existing typo "Whe" remains). No review comments, objections, or discussion have been raised on this patch.

Patch 08/12 adds a `pl_sparse_trees` flag to the `path_walk_info` struct, separating two related but distinct behaviors for how sparse-checkout patterns interact with trees. The `git backfill --sparse` command wants sparse patterns to prune *both* trees and blobs -- it only needs objects within the sparse cone. But the `sparse:<oid>` filter (added in patch 09/12) wants the opposite: prune *only* blobs while walking all reachable trees. Before this patch, `backfill`'s tree-pruning behavior was hardcoded into the path-walk API. Now, `pl_sparse_trees` controls which mode is active. When set (as `backfill` does), behavior is unchanged. When unset, all trees are walked and only blobs are filtered by the sparse patterns. The patch also fixes a subtle SEEN-flag ordering bug that this change exposed: previously, the SEEN flag was set on an object immediately when discovered in a tree entry, before the sparse-pattern check. When the same object ID appeared at multiple paths (e.g. sibling directories with identical contents), the first path visited would mark the object as SEEN, and if that path was outside the sparse cone, the object was skipped there and never re-discovered at its in-cone path. The fix moves SEEN flag assignment to *after* the sparse-pattern and pathspec checks, so objects remain discoverable at other paths when filtered out at the first one. A new test in `t6601-path-walk.sh` exercises `--no-pl-sparse-trees` on a four-commit branch structure with sparse patterns that exclude most paths except `/left/`, and confirms all 10 trees are emitted (one for each commit's tree and each commit's subtrees) while blobs at allowed paths are preserved. The test helper adds a `--pl-sparse-trees` option defaulting to the previous behavior (on), so existing tests are unaffected. This is infrastructure preparation for the `sparse:<oid>` filter patch; the SEEN-flag fix is a genuine correctness win that would matter even without the new flag. No review comments have been raised.

Patch 09/12 (Derrick Stolee, co-authored-by Taylor Blau) adds `sparse:<oid>` filter support to the path-walk API. The performance motivation is clear: constructing packs with `--filter=sparse:<oid>` has historically been expensive because the revision walk checks every object individually against sparse-checkout patterns. With path-walk, objects are grouped by path and entire groups are checked at once. Benchmarks in the commit message show repack time dropping from 77.91s to 31.41s (60% faster) and packfile size shrinking from 187.5M to 161.1M (14% smaller) on the Git repository itself. A notable design detail around error handling: because `sparse:<oid>` requires parsing a blob from the repository to load cone-mode patterns, it can fail in ways that are not the path-walk's fault (the blob might be missing or the patterns might not be cone-mode). The patch makes `get_object_list_path_walk()` return an error code instead of dying, and the caller in `builtin/pack-objects.c` falls back to the standard revision-walk path with a warning. This means users get correct behavior even when the path-walk approach cannot be used. The SEEN-flag ordering fix from patch 08/12 is exercised here in a concrete edge case. The patch adds tests in both `t5317-pack-objects-filter-objects.sh` (end-to-end pack-objects comparison between standard traversal and path-walk) and `t6601-path-walk.sh` (the test-tool path-walk directly). The shared-tree-OID tests are well-designed: they create a repository with two sibling directories that share identical content (and thus the same tree OID), where one directory is inside the sparse cone and the other is not. The test confirms that the blob inside the in-cone directory is included even though its out-of-cone sibling was visited first -- the deferred SEEN flag from patch 08 makes this work. Test coverage is thorough: a `sparse:oid` test that verifies blobs and commits match exactly between standard and path-walk packfiles, another test confirming all trees are preserved (since `sparse:<oid>` only restricts blobs), and the shared-tree-OID regression test. The documentation updates list `sparse:<oid>` as a supported filter form in both `git-pack-objects.adoc` and `git-backfill.adoc`. The pre-existing typo "Whe" in `git-pack-objects.adoc` remains. This is a well-motivated, well-tested patch that delivers on the performance promise the series has been building toward. The fallback mechanism is a pragmatic touch.
