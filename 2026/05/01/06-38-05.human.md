This is a discussion about test suite ergonomics in response to Johannes Schindelin's series fixing Windows platform issues with large (>4GB) objects. Jeff King (Peff) weighs in on Derrick Stolee's earlier review about the new regression test's execution time.

The test in question verifies correct handling of large objects during cloning, which requires generating a 4GB+ test repository. Peff confirms Stolee's concern about runtime impact, noting the test alone nearly doubles his local test suite duration (from 90s to 160s). He raises additional concerns about disk space requirements, especially for developers using RAM disks.

Peff points out the test is already gated behind GIT_TEST_CLONE_2GB, suggesting this ad-hoc flag should be replaced with Git's standard EXPENSIVE test label for consistency. The discussion broadens to question how the project handles expensive tests generally, with Peff noting there's no systematic process for running them during release validation. This reflects a recurring theme in Git's testing infrastructure - balancing thoroughness against practical constraints, particularly for platform-specific edge cases.

The exchange remains focused on test suite maintenance rather than the technical content of the Windows fixes themselves, which appear uncontroversial. Both reviewers agree the test is valuable but needs proper labeling to avoid undue CI and developer overhead.
