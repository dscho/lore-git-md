This thread proposes a new `fetch.pruneBranches` configuration option to automatically clean up local branches when their upstream counterparts are pruned. Harald Nordgren's initial implementation offers three modes (disabled/safe/force) with protections against data loss, including preserving the current branch and unpushed work by default.

Git maintainer Junio Hamano has responded with conceptual support for the feature's goal but suggests restructuring the implementation. Rather than baking the logic directly into fetch's configuration, he proposes decomposing it into standalone branch operations (`git branch --forked` and `git branch --prune-merged`) that fetch could compose. This would make the functionality more flexible while maintaining the original safety distinctions. Junio also notes that some development workflows may need to preserve branches even after upstream merging, hinting at potential future work for branch-level opt-out markers.

The discussion is now at an architectural crossroads - whether to proceed with the integrated config-based approach or pivot to Junio's suggested plumbing commands. Either path would address the core use case of automatic branch cleanup, but the latter would offer more flexibility for scripting and edge cases. Harald will likely respond with either a revised implementation or rationale for keeping the current structure.
