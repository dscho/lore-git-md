# Git Branch --prune-merged v7: Junio Questions Safety Model

Harald Nordgren's v7 series for `git branch --prune-merged` has received substantive review from Junio C Hamano on patch 3/5, and the concerns go to the core of the feature's design.

## Junio's Objection: Fallback Logic Unsound

Junio argues the patch's merged-ness checking logic conflates two different scenarios. The feature is designed for the case where you forked from a topic branch like `origin/next`, pushed your work, and `next` later got pruned at the remote. The patch's fallback strategy -- when a branch's upstream is gone, check against the remote's default branch instead -- is what Junio objects to. He asks: if a branch that others fork from (like `next`) has been pruned, how can you know whether your topic branch's commits have been safely integrated elsewhere? Falling back to an arbitrary different branch cannot provide safety.

Junio is not asking for minor changes. This is a fundamental question about whether the safety-check rationale makes sense. The series is not as close to integration as was previously implied -- the maintainer has a genuine design concern that may require significant rethinking of the upstream-fallback behavior.

## Secondary Concern: Parameter Cleanliness

Junio also questioned the `no_head_fallback` parameter introduced in patch 2, suggesting the same effect could be achieved more simply by passing NULL for `head_rev` from `check_branch_commit()` when doing `--prune-merged`, without adding a new parameter.

## What Remains

The other four patches (collect_forked_set, branch.<name>.pruneMerged config, --all-remotes flag) received less scrutiny in this review -- Junio's attention was focused on the design question raised by the core merge-checking logic in patch 3. No other reviewers have weighed in on v7. Harald Nordgren has not yet responded. The series awaits his reply addressing Junio's objections before it can progress.
