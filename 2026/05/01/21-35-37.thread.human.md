This thread is about Harald Nordgren’s `git branch --delete-merged` series, now at its 15th iteration, which introduces a safe, automated way to clean up local branches that have been merged. The command includes filtering options (`--forked`), safety checks (e.g., preserving checked-out branches and those with push divergence), per-branch opt-out via config, and a `--dry-run` preview mode. After extensive review, the series is nearly complete, but two key issues remain unresolved: an API consistency problem in the deletion logic and a new question about whether to protect branches that serve as upstreams for other unmerged branches ("stacked-branch safety").

Phillip Wood, the primary reviewer, has flagged both issues as potentially blocking. The API problem—replacing a boolean `dry_run` parameter with a flags-based API—is straightforward but must be fixed before testing can proceed. The stacked-branch safety question is more nuanced: should the command avoid deleting branches that are upstreams of other branches not slated for deletion? Junio C Hamano has weighed in, expressing skepticism about the need for this protection, arguing that in typical rebase workflows, deleting a merged branch (e.g., Topic A) wouldn’t break dependent branches (e.g., Topic B), since Topic B’s base would already be part of `main`. His response leaves room for further discussion but suggests the added complexity may not be justified.

Harald has agreed to address both issues before sending a v16. The series is otherwise mature, with all prior test failures resolved and safety mechanisms in place. The next steps hinge on whether the stacked-branch protection is deemed necessary—if not, the implementation could be simplified, but if retained, it would require additional logic to filter out upstream branches. Either way, the thread is now in a holding pattern until Harald posts the next version.
