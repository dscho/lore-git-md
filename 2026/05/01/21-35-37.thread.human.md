Harald Nordgren's `git branch --delete-merged` series is now effectively complete, with all planned features implemented and only one remaining blocker: a correctness issue in the stacked-branch protection logic. The series introduces a safe, automated way to clean up local branches that have been merged into specified upstreams, with multiple safety mechanisms and precise control over which branches are deleted.

The core command, `--delete-merged`, supports repeatable upstream arguments (e.g., `--delete-merged origin/main --delete-merged origin/next`) and optional branch patterns to limit deletion scope. Safety features include protection for checked-out branches, branches with missing upstreams, and branches where pushing by name would update their upstream. The stacked-branch protection ensures that branches used as upstreams for unmerged branches are preserved, while stale upstream configurations for kept branches are cleaned up. Additional safeguards include per-branch opt-out via `branch.<name>.deleteMerged=false` and a `--dry-run` preview mode that avoids modifying refs or config.

Junio C Hamano recently confirmed that the implementation's use of branch names (rather than full refnames) in the stacked-branch protection logic is correct, resolving a potential confusion point. The series remains blocked only by the order dependency in the stacked-branch protection logic, which Phillip Wood has proposed a structural refactor to address. Once this is resolved, the series is ready to merge, with a follow-up planned to extend the protection to `git branch -d` for consistency.
