Harald Nordgren’s `git branch --delete-merged` series, now in its sixteenth iteration, introduces a safe, automated way to clean up local branches that have been merged into their upstream. The command combines filtering options (`--forked`), multiple safety checks (checked-out branches, missing upstreams, push divergence, and per-branch opt-out via `branch.<name>.deleteMerged`), and a `--dry-run` preview mode. After extensive refinement, the series is technically complete and feature-complete, with all prior blocking issues resolved—except one lingering design question.

The remaining debate centers on **stacked-branch safety**: should the command preserve branches that serve as upstreams for unmerged stacked branches? Junio C Hamano has argued that such protection is unnecessary, suggesting users can manually update the upstream of stacked branches after the base branch is merged. Phillip Wood, however, has pushed back with a practical concern: deleting a merged branch like `feature1` (the upstream for `feature2`) would break common workflows like `git log @{u}..` and `git rebase` (without an explicit upstream), which rely on the upstream relationship. This isn’t just a theoretical edge case—it’s a real disruption to iterative development patterns. The discussion remains open, and its resolution will determine whether the final implementation prioritizes safety or simplicity.

Beyond this, the series is ready for final review. Harald has addressed all other feedback, including API consistency (a unified flags-based approach), the `--forked` filter (with remote shorthand/glob support), and comprehensive test coverage. The `--dry-run` mode is fully implemented, mirroring the actual deletion logic without modifying refs. Phillip Wood and Johannes Sixt have already signed off on the core design, leaving this one question as the last hurdle before the series can be queued for merging.
