Harald Nordgren’s `git branch --delete-merged` series, now at v16, is nearly ready for final review after resolving its last major design hurdle: how to handle branches used as upstreams for other unmerged branches (e.g., `feature2` stacked on `feature1`). Earlier versions proposed automatically retargeting dependent branches (updating `feature2@{u}` to `origin/master` when `feature1` is deleted), but this introduced edge cases like recursive chains (`b1→b2→b3`) and self-referential upstreams (`b3→b3`). Harald has now simplified the approach, opting to **abort deletion entirely** if a branch is used as an upstream, with a clear error message (e.g., "Cannot delete branch 'feature1' because 'feature2' depends on it"). This aligns with Junio C Hamano’s preference for a conservative default and avoids the complexity of retargeting in the initial implementation.

The series is otherwise feature-complete, with robust safety mechanisms already in place: per-branch opt-out via `branch.<name>.deleteMerged`, protection for checked-out branches, push divergence checks, and a `--dry-run` preview mode. The stacked-branch protection will be the final piece in v17, and retargeting can be added later as an optional flag (e.g., `--retarget-upstreams`) without breaking existing behavior. Phillip Wood and Junio have both endorsed the abort-on-dependency approach, clearing the way for final review. The next steps are implementation and testing of the stacked-branch check, with no further design objections expected.
