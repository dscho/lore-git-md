This thread proposes a new `fetch.pruneBranches` feature to automatically clean up local branches when their upstream counterparts are deleted, while preserving any unpushed work. The v3 series, authored by Harald Nordgren with input from Junio Hamano, takes a decomposed approach - first adding standalone `git branch` plumbing commands (`--forked` to list branches and `--prune-merged` to delete them) before introducing the high-level `fetch --prune-merged` integration.

The latest patch (4/6) adds the `fetch --prune-merged` option, which automatically runs the branch pruning after successful fetches. It includes robust safety checks: reachability verification prevents data loss, checked-out branches are protected across all worktrees, and the operation fails entirely if pruning encounters errors. The implementation builds on the earlier plumbing commands while maintaining their safety mechanisms and adding comprehensive test coverage.

While the technical implementation appears solid, Johannes Sixt has raised an outstanding concern about the `--prune-merged` naming potentially misleading users, as the behavior depends on upstream tracking rather than commit reachability. This semantic question remains unresolved as the series focuses on adding non-controversial improvements like bulk deletion warnings, consistent "remote-tracking branches" terminology, and a new `--all-remotes` convenience flag. The core functionality is now complete through both low-level plumbing and high-level fetch integration, pending resolution of the naming issue.
