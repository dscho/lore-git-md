Core problem or goal: Provide safe, automated local branch cleanup through explicit `git branch` commands. Components: `--prune-merged`, per-branch opt-out via `branch.<name>.pruneMerged`, multi-remote support via `--all-remotes`, and refined merged-ness checking with upstream-fallback logic.

Key technical details:
- Files and subsystems: `builtin/branch.c`, branch utilities header/implementation, `t/t3200-branch.sh`, `Documentation/git-branch.txt`, `Documentation/config/branch.txt`.
- Patch 1: `collect_forked_set()` for enumerating branches by remote, reusable infrastructure.
- Patch 2: `no_head_fallback` parameter for `branch_merged()`.
- Patch 3: `prune_merged_branches()` -- core prune logic. Reuses `collect_forked_set()`. Semantics: skip if push-destination ref still exists on remote; protect remote's default-branch local counterpart; merged-ness check via `branch_merged()` with `no_head_fallback` (try own upstream first, fall back to remote default if upstream gone, refuse if neither available); exclude worktree-checked-out branches via `branch_checked_out()`; delete via `delete_branches()` with `warn_only` flag. Push-destination semantics use `branch_get_push()`, correct when branch is pushed under a different name. Bulk-deletion uses single `warning()` plus summary count. Test suite: 14 cases covering mainline, in-flight, unpushed (with/without `--force`), upstream-gone fallback, both-upstream-and-HEAD-gone, worktree protection, push-ref-differs-from-upstream semantics, default-branch protection, custom `remote.origin.push` config. Documentation had minor nit of referencing `branch_get_push` directly.
- Patch 4: `branch.<name>.pruneMerged` config for per-branch opt-out. Config check in `prune_merged_branches()` loop; if false, branch is skipped even with `--force`. `--force` does not override opt-out, tested explicitly. Normal `-d` unaffected, tested. Three test cases. Documentation: config entry in `Documentation/config/branch.txt`; patch also revises synopsis in `git-branch.adoc`, replacing the `branch_get_push` code reference from patch 3 with plain English.
- Patch 5 (new): `--all-remotes` flag. `OPT_BOOL_F` with `PARSE_OPT_NONEG`. `collect_remote_name()` callback for `for_each_remote()`. Existing `collect_forked_set()` and its callers gain `all_remotes` parameter. Error messages adjusted: "at least one <remote> or --all-remotes". Standalone `--all-remotes` rejected. Documentation synopses updated: `--forked (<remote>... | --all-remotes)` and similarly for `--prune-merged`. Four test cases: `--forked --all-remotes` verifies output covering multiple remotes; confirms explicit invalid remote name still errors; standalone `--all-remotes` rejected; multi-remote setup with both tracking refs deleted verifies `--prune-merged --all-remotes` cleans both.

Open questions and loose ends:
- Junio has raised a fundamental design question about patch 3's safety model. He argues that the fallback-to-remote-default logic is unsound: a remote's default branch is not expected to disappear, so designing fallback behavior for that case is misguided. He also questions why a branch that others fork from would be pruned. These concerns go to the core of whether the feature's merged-ness checking is defensible.
- Junio also questions the `no_head_fallback` parameter introduced in patch 2, suggesting the same effect could be achieved more simply by just passing NULL for `head_rev` from `check_branch_commit()` when doing `--prune-merged`, without adding a new parameter.
- Harald needs to either defend the upstream-fallback logic with a stronger justification, or redesign the merged-ness checking to avoid the questionable fallback scenario.
- If Junio's concern is resolved, the remaining patches (4 and 5) appeared uncontroversial in v6 review and have no new objections.
