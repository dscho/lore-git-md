This is the fourth iteration of a bugfix for git-gui's handling of bare repositories and missing worktrees. The patch significantly changes direction from v3 by adopting Mark Levedahl's suggestion to use `--is-inside-git-dir` as the primary detection mechanism, rather than the previous multi-stage filesystem checks.

The key change is that git-gui now explicitly blocks launching from inside any Git directory (including .git subdirectories), with a clear error message directing users to start from a worktree instead. This simplifies the logic by treating all gitdir launches uniformly rather than trying to distinguish between valid and invalid cases. The implementation:

1. Maintains the existing bare repository handling (showing "Cannot use bare repository")
2. Adds a new check for `--is-inside-git-dir` that blocks all gitdir launches with a clear error
3. Falls back to empty `_gitworktree` for other error cases

The commit message explains the rationale for dropping support for launching from .git subdirectories - this behavior was unreliable and problematic in multi-worktree scenarios. The 12-line diff shows a clean implementation that addresses the core issue while removing complex edge case handling.

This version represents a substantive response to Mark's review feedback, choosing simplicity and safety over backward compatibility with the .git subdirectory case. The change appears well-considered, though it may impact some existing workflows that relied on the old behavior. The patch maintains git-gui's existing error paths while adding clear guidance for users when they encounter the new restriction.
