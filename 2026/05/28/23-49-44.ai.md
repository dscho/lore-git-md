Bugfix addressing both the memory leak and tempfile cleanup in HTTP pack index handling.

This v2 patch from Lorenzo Pegorari builds on the initial memory leak correction by also removing an unnecessary `unlink()` call that became redundant after commit 63aca3f7f1 introduced tempfile registration. The changes maintain the core fix - ensuring proper cleanup of pack index resources when verification fails - while simplifying the error path by relying on the tempfile subsystem's process-exit cleanup.

The patch now clearly separates three cleanup operations: closing the pack index (which unmaps any mmap'd regions), freeing the temporary index filename, and freeing the pack structure itself. These happen in all error paths, with the success case remaining unchanged. The removal of `unlink()` follows Jeff King's observation about inconsistent tempfile handling, though the thread suggests there may be more to discuss about proper tempfile API usage.

This appears to be a well-considered iteration that addresses both the original memory leak and a related cleanup issue while maintaining the existing error handling flow. The changes are focused specifically on the HTTP transport layer's pack index handling, touching only the error paths in `fetch_and_setup_pack_index()`. The discussion thread indicates this may not be the final word on tempfile management in this area, but the current changes represent a clear improvement over the previous behavior.
