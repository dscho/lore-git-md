This is a follow-up in a thread about Git's unexpected resource usage during routine operations. Jeff King (Peff) identifies that the reported behavior - where Git spawns multiple pack-objects processes despite `gc.auto=0` and `pack.threads=1` settings - is likely due to the newer `git-maintenance` system running independently of the traditional `gc.auto` configuration.

Key points:
- The issue stems from `git-maintenance` running background tasks that aren't controlled by `gc.auto`, explaining why packing operations still occur
- While `pack.threads=1` works per process, multiple maintenance processes can still spawn concurrently
- Peff demonstrates this can lead to repository corruption when multiple pack operations run simultaneously
- He raises two important questions about the design:
  1. Should `maintenance.auto` respect `gc.auto` for backward compatibility?
  2. Should background maintenance operations use locking to prevent concurrent runs?

The email includes a clear reproduction case showing how concurrent packing can corrupt repositories. This moves the discussion from "is this a bug?" to "how should we fix the maintenance system's behavior?" Peff also involves Derrick Stolee (a maintenance subsystem expert) for input.

This is a substantive technical response that identifies the root cause and raises important design questions about Git's maintenance behavior. The potential for repository corruption makes this more than just a performance issue.
