This is patch 4/11 in Johannes Schindelin's series addressing Windows platform issues with large objects (>4GB) during cloning. The focus here is on delta header handling, where 32-bit `unsigned long` types can cause truncation.

The patch introduces `size_t` variants of delta header parsing functions (`get_delta_hdr_size_sz()` and `get_size_from_delta_sz()`) to properly handle large objects, while maintaining the existing `unsigned long` versions for compatibility. The key changes are:

1. New `_sz` variants that preserve full 64-bit sizes throughout delta processing
2. Explicit truncation points marked with `cast_size_t_to_ulong()` where needed
3. Updates to `packed_object_info()` to use the new functions while maintaining the existing interface

The changes respond directly to Torsten Bögershausen's review feedback from v2 about type safety. The patch acknowledges that some truncation remains unavoidable at API boundaries (like `oi->sizep` being `unsigned long*`), but makes these points explicit rather than silent.

This is part of the broader effort to make Git's object handling work correctly with >4GB objects on Windows, building on the zlib wrapper changes in patch 2/11 and the packfile streaming updates in patch 3/11. The implementation appears careful and well-considered, with clear attention to maintaining both correctness and backwards compatibility.
