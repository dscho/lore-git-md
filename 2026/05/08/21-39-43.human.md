This is a follow-up discussion about `git diff --word-diff`'s whitespace handling behavior. Vincent Lefevre pushes back on Johannes Sixt's explanation that the current behavior is expected, arguing the documentation doesn't match the implementation.

The key point of contention is whether `--word-diff` should be whitespace-agnostic by default (like GNU wdiff) or inherit Git's standard whitespace sensitivity. Vincent demonstrates that piping regular `git diff` output to GNU wdiff produces the whitespace-agnostic behavior he expects, suggesting Git's built-in word-diff could follow this model.

The exchange highlights a documentation vs. behavior mismatch - Vincent believes the current implementation doesn't align with what users would reasonably expect from a word-diff feature, especially those familiar with GNU wdiff's approach. This appears to be more about user expectations and interface design than a technical bug, with Johannes maintaining the current behavior is intentional while Vincent argues for a more intuitive default.
