This is a follow-up in the thread about Git's unexpected resource usage during routine operations. Jeff King (Peff) provides technical analysis of why the reported configuration (`gc.auto=0`, `pack.threads=1`) isn't preventing excessive resource consumption.

Key insights:
- The issue stems from Git's newer `git-maintenance` subsystem running independently of `gc.auto` settings, controlled instead by `maintenance.auto`
- Multiple concurrent `pack-objects` processes can occur because each gets its own thread allocation, and maintenance lacks locking to prevent redundant work
- Peff demonstrates this can lead to repository corruption through a simple reproduction case with concurrent repacks

The email raises two important questions for the maintenance subsystem:
1. Should `maintenance.auto` respect `gc.auto` for backward compatibility?
2. Should background maintenance implement locking to prevent concurrent runs?

Peff also CCs Derrick Stolee (the maintenance subsystem expert) for input. The corruption risk from concurrent repacks is noted as a known issue that this case highlights needs addressing.

This moves the discussion from "why is this happening?" to specific technical questions about maintenance behavior and thread safety. The reproduction case provides clear evidence that current behavior can lead to data corruption, elevating the issue's severity.
