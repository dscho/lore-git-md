This is the third patch in Jonas Rebmann’s v4 series to make `git bisect` respect user-configured alternate bisect terms. The series is complete and ready for merge; this patch addresses the `git rev-parse --bisect` plumbing command.

The problem is straightforward: when a user runs `git bisect start --term-old=known --term-new=curious`, Git creates refs like `refs/bisect/known` and `refs/bisect/curious` instead of `refs/bisect/good` and `refs/bisect/bad`. But `git rev-parse --bisect` was hardcoding the old ref names, so it would silently find nothing in a bisect session using alternate terms. The fix reads the actual terms from `BISECT_TERMS` via `read_bisect_terms()`, builds the ref prefixes dynamically with `xstrfmt()`, and frees them afterwards. The code is clean and follows the pattern established by the earlier patches in the series.

The test is well-constructed: it creates a bisect session with `--term-old=known --term-new=curious`, then deliberately creates both the custom-termed refs (`refs/bisect/curious-*`, `refs/bisect/known-*`) and the standard ones (`refs/bisect/bad`, `refs/bisect/good`). The test verifies that only the former are listed, confirming the hardcoded ref fallback is correctly bypassed. The explicit comment in the test about why `refs/bisect/bad` and `refs/bisect/good` should be ignored is good practice for future readers.

This is a correct, minimal fix to an actual bug. The patch touches only `builtin/rev-parse.c` and adds one test case. No design questions remain; this is the final polish on a v4 series that has already had memory leaks and quoting conventions addressed in earlier rounds. Anyone reviewing does not need to rehash the approach -- just check for any leftover hardcoded ref lookups that might have been missed, and verify the memory management is sound (it is: every `xstrfmt` has a matching `free`).
