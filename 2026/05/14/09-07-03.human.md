This is a cover letter for a three-patch series that fixes a long-standing edge case in `git bisect`: when users set custom bisect terms (e.g., `git bisect term old new` instead of `good`/`bad`), several output messages and internal references still hardcode the words "good" and "bad".

The series addresses two places where this happens. Patch 1 fixes the status output that `git bisect` prints during its search, making it use whatever terms the user has configured. Patch 3 fixes a subtler issue in `git rev-parse --bisect`, which is used by the `git bisect run` helper internally -- if you run custom-term bisects programmatically, `rev-parse` was looking up the wrong refs. Patch 2 is a small formatting cleanup that prints terms in single quotes.

The series is now on its fourth iteration and has been through significant polishing. The change log shows careful attention to previous review feedback from Junio and Phillip Wood, including memory leak fixes, test improvements, and commit message wording. The tests are substantial -- the series touches five files and adds 25 new test lines alongside adjusting 124 existing ones.

This is a focused, well-scoped fix to a real usability gap. Custom bisect terms are not widely used, but when they are used the existing behavior is silently wrong, which makes this a legitimate bugfix rather than a cosmetic improvement. The fact that the author found the `rev-parse` issue only while testing the status output (as the cover letter mentions) suggests the fix is more thorough than it initially set out to be. The series looks ready for a close look and likely inclusion.
