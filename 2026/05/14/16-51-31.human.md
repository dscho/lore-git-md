Performance optimization for revision traversal in merge-heavy histories.

Kristofer Karlsson from Spotify proposes replacing the O(n) insertion sorted linked list in `limit_list()` with an O(log n) priority queue (binary heap). This affects commands like `--left-right`, `--cherry-mark`, bisect, and rebase's fork-point computation when operating on repositories with many merge commits.

The patch shows significant speedups (2.5-3x) in benchmarks on a 2.3M-commit monorepo when the symmetric difference contains thousands of commits. Small traversals see no change. The implementation is clean, leveraging existing `prio_queue` infrastructure and requiring only 21 lines added vs 17 removed in `revision.c`.

The change is well-motivated with profiling data showing commit list insertion consuming 59% of CPU time in some cases. The commit message clearly explains the algorithmic improvement and includes concrete benchmark numbers. This appears to be a straightforward performance win for a common pain point in large repositories.
