This is patch 6 of 8 in Derrick Stolee's v4 series adding negotiation controls, and it delivers the marquee feature: `--negotiation-include` for `git fetch` (and passthrough for `git pull`).

The problem is real and clearly explained: in monorepos with long parallel histories, if a critical ref like "release" isn't selected for negotiation, the server may assume the client has no shared history with that branch, triggering a full download -- Stolee gives a real example of 60+ GB fetches. `--negotiation-restrict` (patch 2 in this series) solves this by narrowing the ref set, but at the cost of excluding anything opportunistic. `--negotiation-include` takes the complementary approach: it guarantees specific refs are always sent as haves while still letting the negotiator pick others. The two can be combined, giving users fine-grained control.

The implementation is clean. The include tips are resolved from ref names or patterns (in `builtin/fetch.c`) into an `oid_array` that gets threaded down to `fetch-pack.c`, where they're fed to the wire before the negotiator's `next()` iterator kicks in. Crucially, the call uses the `have_sent()` interface established in patch 5 to let the negotiator know about these pre-sent commits, preventing it from re-emitting them as duplicates. Tests verify this deduplication works for both protocol v0 and v2.

A smart detail: missing refs are silently ignored rather than dying. This matches real-world usage where an include pattern might match nothing without the user wanting an error. The documentation carefully describes the interaction with `--negotiation-restrict` (restrict first, then include on top).

Patch quality is high -- clear commit message, sensible code organization, thorough test coverage across glob patterns, additive behavior, and duplicate prevention. `builtin/pull.c` wires it through correctly. The `the_repository` usage is present in the new `add_oids_to_set()` helper, consistent with existing negotiator conventions and not a defect.

Bottom line: this is the heart of the series, well-designed and well-executed. It solves a concrete, painful problem for large-repo users and the abstraction feels right. Ready for `next`.
