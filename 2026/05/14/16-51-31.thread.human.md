This thread continues the discussion of performance optimizations for Git's revision walking code, building on the recently merged changes that replaced linked lists with priority queues in `limit_list()` for significant speedups in merge-heavy repositories. The current debate centers on how to extend these optimizations further.

Kristofer Karlsson and Jeff King (Peff) have proposed two different approaches - Kristofer's hybrid method maintains linked lists during setup but introduces priority queues for walking (fewer file changes, slightly faster in some cases), while Jeff's approach converts all commit list usage to priority queues (more comprehensive but touches more code). Both show 3-5x speedups in large monorepo benchmarks.

In the latest email, Jeff provides a detailed technical analysis of Kristofer's approach, raising concerns about state management complexity and potential ordering issues in functions like `cherry_pick_list()`. While acknowledging both approaches achieve similar performance gains, Jeff leans toward his more comprehensive conversion but stops short of rejecting Kristofer's method, instead highlighting areas needing further thought. The discussion remains open, with no clear consensus yet on which path to take for the next phase of optimizations.
