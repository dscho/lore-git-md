This is patch 5/8 of Derrick Stolee's v4 series adding two-directional fetch negotiation controls for monorepo scenarios, and it is the most structurally significant new patch in this iteration -- introduced solely to address the key abstraction concern raised in Matthew Cheetham's v3 review.

The patch adds a `have_sent()` callback to the `fetch_negotiator` interface, declared in `fetch-negotiator.h` and implemented in all three negotiator backends. The purpose is to allow the fetch-pack machinery to tell the negotiator "I have already sent this commit as a 'have' line outside your control" -- so that the negotiator can avoid emitting it again from its `next()` iterator, and can further optimize by treating it (and its ancestors) as common for the purposes of its traversal logic.

For the default and skipping negotiators, the implementation is straightforward: parse the commit and call `mark_common()` with the appropriate arguments. For the noop negotiator, `have_sent()` is a no-op, which is consistent with how that negotiator works in general. The actual caller of this interface comes in the next patch (6/8), which introduces `--negotiation-include` -- the main new abstraction concern is set up here first as a clean, self-contained step.

This is the patch that makes the entire series work correctly: without it, the earlier v3 approach used the COMMON flag for a dual purpose, conflating "the server told us this is common" with "we decided to include this commit regardless of server feedback." By introducing `have_sent()` as a separate signal, the series avoids that semantic muddle. The commit message is clear about what problem this solves and why the interface is needed.

One small note: both the default and skipping implementations call `repo_parse_commit(the_repository, c)`. The use of `the_repository` here is consistent with the rest of the negotiator code (which has not yet been converted to the ongoing `the_repository` removal effort), but it is worth noting for anyone tracking that cross-cutting cleanup. This is not a criticism of the patch -- it would be inappropriate to introduce a `struct repository *` parameter here as part of a separate effort.

The patch is small (32 insertions across 4 files), well-documented with a clear doc comment on the new function pointer, and structurally sound. It is a textbook example of introducing an abstraction in a separate, reviewable step before the code that exercises it.
