Performance optimization patch series (v2) for revision walking's `limit_list()`, replacing a linked list with a priority queue to achieve O(log n) insertion cost in merge-heavy repositories. Shows 1.6-4.3x speedups in benchmarks, with largest gains for ancestry-path queries (4.3x) and commit-graph-enabled cases (2.5x). Affects commands using symmetric difference: `--left-right`, `--cherry-mark`, bisect, rebase fork-point, and `git status --ahead-behind`. The original optimization has been reviewed and approved by Derrick Stolee, Jeff King, and Junio C Hamano, with all technical concerns addressed.

Kristofer Karlsson reports the priority queue approach could also benefit `get_revision_1()`, yielding a 3.3x speedup for `git rev-list HEAD` in a monorepo while making `commit_list_insert_by_date` obsolete, though this extension would complicate `get_revision_1()` by requiring both a priority queue and a linked list in the `rev_info` struct. Kristofer seeks guidance on whether to pursue this as a separate thread.

René Scharfe provides benchmark data showing consistent 1.16-1.28x speedups across Git's own version ranges (v2.0.1 to v2.10.1 through v2.50.1) when using `git rev-list --bisect`, validating Derrick Stolee's suggestion to test against Git's history. While more modest than the 4.3x speedups in synthetic merge-heavy cases, these results demonstrate the optimization provides meaningful improvements even in relatively linear histories, strengthening the case for merging while setting realistic expectations for typical repositories. The data suggests the largest gains appear in repositories with complex merge histories.
