This is **patch 4/8** of Derrick Stolee's v4 series adding negotiation controls for Git fetch. It's a **feature/config patch** that adds `remote.<name>.negotiationRestrict` as a new multi-valued config option.

The patch adds a configuration counterpart to the `--negotiation-restrict` command-line option introduced in patch 2 of this series. When a remote is configured with this option, `git fetch <name>` will automatically restrict the set of "have" lines sent during negotiation to only commits reachable from the specified ref patterns. The familiar patterns apply here: if the user provides even one `--negotiation-restrict` argument on the command line, the config values are ignored entirely, and an empty config value resets the list (allowing override of system or global config).

The implementation is straightforward and follows the pattern already established by `remote.<name>.serverOption`: it uses `parse_transport_option()` for parsing, stores the result in a new `struct string_list negotiation_restrict` field on `struct remote`, and reads it in `prepare_transport()` to populate the already-existing `negotiation_restrict_tips` field on the transport options. The only notable structural change is that the patch also moves the `--negotiate-only` guard -- the check that at least one negotiation-restrict tip is provided -- from the top of `cmd_fetch()` to *after* `prepare_transport()`, so that config values are considered before deciding the user has made an error. This is a correct adjustment.

Three new tests in `t5510-fetch.sh` cover the config defaults (with a blank-value reset to verify that mid-list resets work), and a CLI-overrides-config test that checks the packet trace for presence of only the explicitly requested ref.

This is clean, well-motivated plumbing, following the established patterns for transport config options. No surprises, no controversy.
