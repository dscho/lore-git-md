This is patch 7 of 8 in Derrick Stolee's negotiation-control series, adding a `remote.<name>.negotiationInclude` config option. It mirrors the `remote.<name>.negotiationRestrict` config added in patch 4/8, providing a way for users to persistently configure which refs should always be sent as haves during fetch negotiation, without needing to pass `--negotiation-include` on every command line.

The implementation is straightforward and follows the same pattern as the restrict config: a multi-valued string list on the `struct remote`, parsed via `parse_transport_option()` (which also supports blank-value reset), and wired into `builtin/fetch.c`'s `prepare_transport()` as a fallback when no `--negotiation-include` CLI option is given. If the CLI option is specified, the config is ignored entirely -- no additive merging. The documentation is thorough, with a cross-reference to push negotiation behavior when `push.negotiate` is enabled.

The three tests in t5510 cover the expected scenarios: blank-value list reset, glob patterns, and CLI-overrides-config behavior. All are clean and self-contained.

This is a mechanical config hookup patch. The conceptual groundwork was laid in patches 5/6 (the `have_sent()` interface and the CLI `--negotiation-include` implementation), so this patch has no new design decisions or surprises. It is exactly what you would expect from a well-structured series: complete the feature by adding the persistent configuration counterpart. No controversy, no open questions.
