This thread discusses whether `git diff --word-diff` should handle whitespace changes differently to better match user expectations set by tools like GNU wdiff. Vincent Lefevre reported that Git highlights entire lines when only whitespace differs, unlike wdiff which shows more granular changes. Johannes Sixt explains this is intentional - Git's word-diff inherits the standard diff engine's whitespace sensitivity, and the `-w` flag exists for whitespace-agnostic comparison.

Vincent followed up with a concrete example showing different results between piping `git diff` to wdiff versus using Git's built-in word-diff, arguing the behavior should align with external tools. Johannes maintains there's no requirement for Git to match wdiff's output, and that the current behavior is correct by Git's own design standards. While technically accurate, this leaves a gap between Git's implementation and what some users expect based on other diff tools they use.

The discussion has reached an impasse: Johannes sees no technical reason to change the behavior, while Vincent's examples demonstrate real cases where users might find Git's output surprising. The open question is whether this warrants documentation clarification about whitespace sensitivity in word-diff, or if the behavior itself should be reconsidered to better match common workflows. For now, users needing wdiff-like behavior must remember to use the `-w` flag explicitly.
