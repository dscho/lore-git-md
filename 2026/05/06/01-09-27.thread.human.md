This thread examines how `git diff --word-diff` handles whitespace changes, revealing a gap between technical implementation and user expectations. Vincent Lefevre originally reported that the command highlights entire lines when only whitespace differs, unlike GNU wdiff which shows no difference in such cases. Johannes Sixt clarified this is intentional - Git's word-diff inherits the whitespace sensitivity of its underlying line-diff engine, and the `-w` flag exists specifically for whitespace-agnostic comparisons.

The discussion has evolved from technical implementation to documentation clarity. Vincent now argues the man page doesn't adequately explain that `--word-diff` builds on line-diff behavior, only describing it in terms of "changed words." While Johannes maintains the current behavior is technically correct, Vincent highlights how the undocumented relationship to line-diff creates surprising results for users familiar with tools like wdiff. The core disagreement now centers on whether to adjust the documentation to better set expectations or reconsider the default behavior to match common external tools. Neither side has conceded ground, leaving the thread at an impasse between technical purity and user experience considerations.
