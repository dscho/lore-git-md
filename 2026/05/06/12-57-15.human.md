This is a technical discussion continuing the thread about git-gui's handling of bare repositories and missing worktrees. Johannes Sixt responds to Mark Levedahl's analysis of git's worktree detection primitives.

The discussion centers on whether `git rev-parse --is-inside-work-tree` or `--is-bare-repository` provides better information for git-gui's startup decisions. Johannes questions whether Mark's proposed approach would properly handle the case where git-gui is launched from a ".git" directory (where the parent directory should be treated as the worktree) and raises concerns about the `git gui blame` command in bare repositories.

Johannes also clarifies that the root issue with empty GIT_WORK_TREE exports likely stems from Git commands trying to resolve empty paths, not specifically from git-gui's 2014 changes. He expresses a preference for not setting GIT_WORK_TREE at all when GIT_DIR is set, provided this is a supported Git use case.

The exchange reveals the complexity of reconciling git-gui's historical behaviors (like special .git directory handling) with Git's current worktree detection primitives. While technical solutions are emerging, there remain open questions about edge cases and backward compatibility that need resolution before the patch can be finalized.
