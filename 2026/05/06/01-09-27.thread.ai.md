Bug report and discussion regarding `git diff --word-diff` whitespace handling. Vincent Lefevre initially reported incorrect highlighting of entire lines when only leading/trailing whitespace differs, comparing behavior unfavorably to GNU wdiff. Johannes Sixt clarified this is expected behavior: `--word-diff` inherits Git's standard whitespace sensitivity by default, matching the underlying line-diff behavior. The correct approach for whitespace-agnostic comparison is to use `-w` flag to suppress whitespace differences.

Vincent Lefevre demonstrated that piping regular `git diff` output to GNU wdiff produces different results for whitespace-only changes, highlighting a divergence between Git's word-diff and external tools' behavior. In follow-up, Vincent argues the documentation is unclear, failing to mention `--word-diff`'s dependence on line-diff behavior while describing it in terms of "changed words." He maintains the behavior differs unexpectedly from GNU wdiff, which shows no differences for whitespace-only changes.

Key technical details:
- Current behavior intentionally matches Git's line-diff whitespace rules
- `-w` flag provides whitespace-agnostic mode
- GNU wdiff handles same input differently, creating user expectations
- Documentation describes word-diff in terms of "changed words" without mentioning line-diff inheritance

Open questions:
- Whether documentation should be clarified about whitespace sensitivity
- Whether to add explicit mention of line-diff behavior relationship
- If keeping current behavior, how to better set user expectations about GNU wdiff differences

Participant positions:
- Johannes Sixt: current behavior is correct and intentional, no technical need for change
- Vincent Lefevre: documentation is unclear and should be updated to explain behavior, current output is surprising compared to other tools

The discussion has shifted from implementation correctness to documentation clarity, with Vincent now focusing on the gap between the documented description and actual behavior. The core disagreement remains between technical correctness (Git's behavior matches its design) and user experience (documentation doesn't set accurate expectations). Resolution may require either documentation updates or a clearer explanation of why the current behavior is preferable to matching GNU wdiff.
