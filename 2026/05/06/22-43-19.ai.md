This is a feature proposal to add merge commit support to `git history`, the new history-rewriting command introduced in Git 2.54. The series comes from Johannes Schindelin (Git for Windows maintainer) as an RFC (Request for Comments).

The core problem being addressed is that `git history` currently fails when encountering merge commits, making it unusable for workflows that rely on feature branch merges. The patch series implements support for replaying 2-parent merges (the most common case) while explicitly deferring octopus merges and merge reverts as future work.

The implementation builds on Elijah Newren's earlier design notes and prototype, with three key improvements:
1. Consistent conflict marker labels for inner merges
2. Handling non-clean merge results
3. Proper boundary commit mapping when both parents need replaying

The series includes both the core functionality (in `replay.c`) and extensive testing infrastructure:
- A new `test-historian` helper for creating merge test scenarios
- A dedicated test file (`t3454-history-merges.sh`) with 300+ lines of test cases
- Documentation updates explaining the merge replay limitations

The changes touch multiple areas:
- The replay engine's merge handling
- `git history` command's return code validation
- Test infrastructure additions
- Documentation updates

This appears to be a well-considered proposal with thorough test coverage. The RFC status suggests the author is seeking feedback on the implementation approach before finalizing it. Given the complexity of merge handling and the command's relatively recent introduction (v2.54), this seems prudent. The patch builds on established design work while addressing practical edge cases the original prototype didn't handle.
