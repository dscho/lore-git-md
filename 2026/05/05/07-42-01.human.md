This is a bugfix patch addressing an inconsistency in `git log --follow` behavior with subtree merges. Currently, when examining history with `--follow`, Git fails to track file renames that occur during subtree merges, while `git blame` correctly follows such renames.

The patch modifies `log-tree.c` to check each parent of a merge commit for potential renames when `--follow` is active, similar to how `blame.c` handles this case. This ensures `log --follow` will show the complete history of a file across subtree merges, rather than stopping at the merge point.

The change comes with a new test case that:
1. Creates two repos (inner and outer)
2. Merges inner into outer as a subtree
3. Verifies `log --follow` can trace the file's history back through the merge

The patch appears well-constructed with:
- Clear commit message explaining the problem and solution
- Minimal code changes focused on the specific issue
- New test that demonstrates and verifies the fix
- Proper sign-off and formatting

This fixes a real inconsistency in Git's behavior that would affect users working with repositories that use subtree merges. The solution follows established patterns from the blame machinery.
