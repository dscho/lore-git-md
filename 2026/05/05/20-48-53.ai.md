Feature: Discussion on `fetch --prune-merged` local branch modification concerns.

Johannes Sixt raises a fundamental design concern about the proposed `fetch --prune-merged` functionality in Harald Nordgren's v4 series. While acknowledging the motivation for automated branch cleanup, Sixt objects to the core concept of `git fetch` modifying local branches, even as an opt-in feature. His position is that local branch management should remain exclusively within `git branch`'s domain at the porcelain level.

This feedback represents a significant architectural concern that wasn't fully addressed in previous iterations. The series had focused on implementation details and safety mechanisms (including the newly added `--all-remotes` flag and default branch protection), but Sixt's comment challenges the basic premise of coupling fetch operations with branch deletion.

The critique comes from a respected contributor with deep experience in Git's user-facing behavior (as maintainer of `gitk` and Git GUI), suggesting the concern may resonate with others who prioritize command separation of concerns. This could require rethinking the high-level design rather than just adjusting implementation details.

The thread now faces a key decision point: whether to proceed with the current integration approach (despite the conceptual objection) or to reconsider how to expose the branch pruning functionality while maintaining clearer command boundaries. Junio Hamano's earlier preference for decomposed architecture may factor into this discussion, as the current series already provides the low-level `git branch --prune-merged` plumbing that could potentially stand alone without fetch integration.
