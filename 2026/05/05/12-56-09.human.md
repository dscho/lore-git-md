This is a maintainer workflow discussion emerging from Johannes Schindelin's series fixing Windows handling of large (>4GB) objects. The thread has reached the final patch (11/11) which gates expensive tests to run only on push builds to integration branches.

Junio Hamano responds to Derrick Stolee's question about CI failure monitoring with a characteristically pragmatic perspective. He emphasizes that catching issues early in contributors' own CI is far more effective than detecting problems after integration branches are updated. Junio notes he does monitor 'seen' branch failures but has limited bandwidth to diagnose all issues, and suggests the ideal workflow would have contributors catching problems in their own forks before sending patches.

The exchange reveals Git's CI philosophy: integration branch testing should primarily catch interaction issues between topics, not basic functionality problems that authors should have caught locally. Junio gently pushes back on Stolee's suggestion of automated issue creation for CI failures, preferring instead to encourage contributors to run comprehensive tests before submitting patches.

This discussion, while prompted by the Windows large-object series, touches on broader project norms about responsibility for test coverage and failure triage. Junio's response reinforces that contributors bear primary responsibility for their patches' correctness, with integration testing serving as a final safety net rather than the first line of defense.
