2. **Semantic ambiguity**: He questions what "merged into what?" would determine which branches get pruned, noting the current description doesn't specify the merge target criteria that would make a branch eligible for pruning.

The review is substantive - it engages with the actual behavior being proposed rather than surface-level issues. Hannes is flagging a potential UX pitfall where the command name doesn't match its behavior, which could lead to accidental data loss if users assume it has the same safety semantics as `--merged`.

This feedback would need to be addressed either by:
- Renaming the option to better reflect its behavior (e.g., `--prune-tracked`), or
- Actually implementing merged-ness checking to match the `--prune-merged` name

The thread context shows the v2 series has since implemented this functionality with additional safety checks, but Hannes' point about command naming clarity remains relevant to how users will understand and trust the feature.
