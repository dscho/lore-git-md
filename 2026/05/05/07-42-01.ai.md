This is a bugfix patch addressing an inconsistency in `git log --follow` behavior when dealing with subtree merges. Currently, `git log --follow` fails to track file history across subtree merges, while `git blame` correctly follows renames. The patch modifies `log-tree.c` to check each parent of a merge commit for potential renames when `--follow` is enabled, similar to how `blame.c` handles this case.

The change is well-motivated by the real-world use case of importing one repository into another via subtree merge. The commit message clearly explains the current behavior, the inconsistency with `git blame`, and the solution approach. The patch includes a new test case that verifies the fixed behavior by creating a test repository with a subtree merge and checking that `git log --follow` can now trace the file history across the merge.

The implementation appears straightforward - it extends the existing rename-following logic to handle merge commits by iterating through parents. The test coverage looks appropriate for the change. This seems like a solid improvement that makes `--follow` behavior more consistent and useful in repositories using subtree merges.
