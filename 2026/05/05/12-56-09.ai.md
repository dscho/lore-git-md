This is a maintainer response in the ongoing thread about Windows platform support for large objects (>4GB), specifically addressing CI testing strategy for expensive tests. Junio Hamano replies to Derrick Stolee's question about monitoring CI failures on integration branches.

Junio makes several key points about the project's CI philosophy:
1. Breakages should ideally be caught before patches reach integration branches, at the contributor's fork level, where problems are easier to isolate and fix.
2. Integration branch CI primarily serves to catch inter-topic interactions that can't be tested in isolation, not to find basic faults that should have been caught earlier.
3. The current workflow already surfaces many problems at the 'seen' branch stage, where Junio does actively monitor and report failures.
4. Automated issue creation for CI failures might help, but Junio suggests an even earlier intervention point - better tooling for contributors to test their own forks before sending patches.

The response reflects Git's maintainer-driven culture, where Junio emphasizes individual contributor responsibility for pre-submission testing while acknowledging the practical challenges of platform-specific issues. He notes he'll be intermittently available, managing expectations about response times.

This exchange highlights the tension between thorough CI coverage and maintainer bandwidth, with Junio advocating for moving quality gates earlier in the process rather than adding more integration-time checks. The discussion remains relevant to the series' test strategy but has broad implications for the project's development workflow.
