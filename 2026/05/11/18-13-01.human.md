This is an architectural fix inside the path-walk API, patch 04/12 in the ongoing `--path-walk --filter` integration series from Derrick Stolee and Taylor Blau.

The problem it solves is subtle but important. When a filter is active (say, `blob:none`), the path-walk API was silently dropping directly-requested objects -- things like the blobs needed to fulfill a partial-clone fetch. The root cause is that the path-walk code was checking its type-filter flags (`info->blobs`, `info->trees`) uniformly for every object, including those that were specifically requested as pending objects in the revision walk. Those directly-requested objects should always be emitted regardless of the filter, because the caller explicitly asked for them.

Stolee's fix works by introducing a `path_is_for_direct_objects()` helper that checks whether the path starts with `/` -- a convention that distinguishes directly-requested objects (stored under pseudo-paths like `/tagged-blobs`) from objects discovered during normal tree traversal. The patch then adjusts three points in `path-walk.c`: the emission logic in `walk_path()` now skips type-filter checks for these paths; the `setup_pending_objects()` function no longer skips tree and blob pending objects when their type flags are disabled; and `walk_objects_by_path()` temporarily overrides the revision machinery's own type flags to `1` before `prepare_revision_walk()`, ensuring pending objects survive the initial revision walk setup, then restores them afterward.

This is solid, careful work. The commit message clearly explains both the symptom (test failures under `GIT_TEST_PACK_PATH_WALK=1`) and the root cause, and the fix is self-contained and straightforward. The documentation and header comments are updated in tandem, which is a good sign. No controversy here -- this is a prerequisite correctness fix that makes the rest of the series possible, and it looks ready to go.
