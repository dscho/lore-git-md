This is **patch 05/12** of the `--path-walk --filter` integration series from Derrick Stolee and Taylor Blau, and it adds support for the `blob:none` filter.

Up until now, using `--path-walk` with any filter at all was forbidden — the code would emit a warning and silently disable path-walk. This patch makes `blob:none` the first filter that works natively within the path-walk API. The implementation is straightforward: when the filter is `blob:none`, the walk simply sets its internal blob-processing flag to zero, then releases the filter from the revision machinery so that `prepare_revision_walk()` doesn't reject it. The logic lives in a new `prepare_filters()` function, which will be extended by later patches to handle other filter types.

The patch also introduces a public `path_walk_filter_compatible()` function that `builtin/pack-objects.c` can call during setup to decide whether the combination is valid. This replaces the old hardcoded "any filter is incompatible" check with a proper per-filter query. Correspondingly, the documentation for `--path-walk` in `git-pack-objects.adoc` is updated to reflect that `blob:none` is now supported.

On the testing side, this patch removes the `GIT_TEST_PACK_PATH_WALK=0` overrides that were sprinkled through `t5620-backfill.sh` as stopgaps in earlier patches, and adds new tests in `t6601-path-walk.sh` that exercise `blob:none` with `--all` and with a single branch. The test helper (`test-path-walk`) gains a `--filter` option and is switched from `REV_INFO_INIT` to `repo_init_revisions()` to properly support filter parsing.

The performance numbers are included in the commit message and are interesting: on the Git repository itself, using `blob:none` with `--path-walk` takes about 73% longer (23.43s vs 13.51s without) but produces a pack that is 16% smaller (115MB vs 138MB). The size savings come from the fresh delta compression that `--path-walk` triggers. The author frames this as a meaningful trade-off for users who want smaller blobless packs.

This is a clean, well-scoped patch. The `prepare_filters()` dispatch pattern is sensible — it both serves as a compatibility check (called with a NULL info pointer from `path_walk_filter_compatible()`) and as an actual setup step (called with a real info pointer from `walk_objects_by_path()`). The tests are thorough and the documentation change is correctly scoped. This looks ready for `next`.
