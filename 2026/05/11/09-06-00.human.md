This is a follow-up in the abandoned config file locking timeout thread. The original author, Jörg Thalheim, responds to Junio Hamano's consideration of dropping the patch by noting they've worked around the issue in their own project (workmux) by implementing file locking at a higher level.

The response highlights the practical resolution path many users take when Git's core behavior doesn't meet their needs - working around it in their own tooling rather than pushing for upstream changes. Thalheim also expresses uncertainty about how a configurable timeout could work given the chicken-and-egg problem of needing to read configuration to know the timeout value.

This effectively closes the thread with no resolution in Git itself. The underlying issue of unreliable concurrent config updates remains, but the discussion shows both the challenges of solving it properly (as Patrick Steinhardt noted) and the reality that many users will find their own solutions rather than wait for core fixes. The exchange reinforces how even well-intentioned patches can stall when they raise complex questions that the original author isn't positioned to address.
