This is patch 11/12 in the `--path-walk` / `--filter` integration series from Taylor Blau and Derrick Stolee, implementing support for the `object:type=<type>` filter. It's a feature patch, the second of three from Taylor Blau at the end of the series (following `tree:0` and preceding `combine` filters).

The approach is clean and leverages what path-walk already does. The `object:type` filter is one of the "object-info-only" family (like `blob:none` and `tree:0`) requiring only type information. The implementation maps `LOFC_OBJECT_TYPE` onto the existing per-type flags (`info->{commits,tags,trees,blobs}`) using a bitwise AND, so setting `object:type=blob` leaves only `info->blobs=1` and zeroes everything else. The commit message explains the AND approach is intentionally preparing for the `combine` filter in the next patch.

The substantive fix is handling the "trees off, blobs on" case -- specifically when `object:type=blob` is used. Two issues arise: 1) `setup_pending_objects()` was skipping pending trees as soon as `info->trees` was zero, but tags pointing to trees can reach blobs that are otherwise unreachable from any commit's root tree; and 2) the revision machinery's `handle_commit()` drops pending trees when `revs->tree_objects` is zero before path-walk ever sees them. The fix sets `revs->tree_objects` to `info->trees || info->blobs` during setup (so pending trees survive `prepare_revision_walk()`), then resets it to zero immediately after so the revision walk doesn't redundantly enumerate trees. A new `strict_types` flag on the `path_walk_info` struct gates the "direct object requests" bypass -- when set, direct requests no longer override type restrictions.

The test coverage in `t6601-path-walk.sh` is thorough, with separate tests for each of the four `object:type` values. The `object:type=blob` test specifically verifies that file2 and child/file -- reachable only through tag-pointed trees that would otherwise be dropped -- are correctly emitted. The documentation update adds `object:type` to the list of supported filter forms.

This looks like a well-considered patch. The two interaction bugs it fixes (pending trees being dropped by the revision machinery, and `setup_pending_objects()` over-skipping) are the kind of subtle cross-subsystem issues that are easy to miss in initial design. The commit message is clear about both the fix and why it's correct. The `strict_types` flag feels like a prudent addition -- it's unclear from the commit message alone whether there are real-world filter combinations where bypassing type restrictions on direct requests is desirable, but making it opt-in is the safer default.
