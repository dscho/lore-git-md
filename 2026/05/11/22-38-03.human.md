This is a reply in the feature-request thread about allowing users to configure which shell Git uses for aliases. The original request asked for a `core.shell` config option so that e.g. mksh could be used instead of `/bin/sh`.

brian m. carlson gives a thorough, technically grounded explanation of why this is unlikely to happen. The use of `/bin/sh` is intentional for consistency across platforms, and allowing arbitrary shells would cause real portability problems: system-level aliases shipped to developer VMs would break on machines without the configured shell, Windows has multiple incompatible shells (CMD, PowerShell, bash), and shells like zsh can become non-POSIXy depending on their config files. The deeper problem is that Git's "with-shell" mode formats commands as `%s "$@"`, which is fundamentally a POSIX-sh idiom, and quoting for arbitrary shells would be both impractical and a security risk.

The author does offer a practical workaround: the `SHELL_PATH` build-time knob, already available for systems where `/bin/sh` is not POSIXy, can be set to `/bin/mksh` at compile time. This is not the same as a per-user config option, but it covers the case of replacing the shell for the entire Git installation.

The review depth here is substantive: the author engages with the original proposal on technical grounds, identifies specific failure modes (Windows, zsh `.zshenv`, quoting for non-POSIX shells), references the existing build infrastructure (`SHELL_PATH`), and links to prior discussion about PowerShell. There is nothing shallow about this response -- it is a clear, well-reasoned no with supporting evidence and a workable alternative. A busy reader can take away that this feature request is essentially dead-on-arrival at the config level, but the build-time knob solves the core use case for power users on homogeneous systems.
