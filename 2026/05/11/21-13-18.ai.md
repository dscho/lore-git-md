This is a feature request (proposal, not a patch) asking Git to allow users to configure which shell is used to run alias commands, rather than hard-coding `/bin/sh`.

The author, Thorsten Glaser, points out that Git always invokes alias commands via `/bin/sh`. This means aliases that rely on shell features not available in POSIX `sh` -- or that are tested against a specific shell like `mksh` -- can break, and there is currently no configuration option to point Git at a different shell. The concrete ask is for a config key like `core.shell` (the author suggests `core.sh = /bin/mksh` as an example) that would override the hard-coded path.

The commit message (this is a single-email thread root with no prior discussion) does not provide reproduction steps, a patch, or any analysis of where in Git's source this path is used. It is a straightforward feature request, stated clearly but without implementation detail.

This seems like a reasonable quality-of-life request -- there are real use cases where people rely on shell-specific syntax in aliases -- but it is unlikely to be straightforward to implement or accept. Changing the shell involves not just `run_command()` plumbing but also how Git spawns shell commands across platforms, and there would be portability concerns (not every platform has or wants an alternative to `/bin/sh`). The email does not address any of those trade-offs. A busy reader might glance at this and decide it is worth tracking for discussion but not urgent -- the right response is probably for interested parties to chime in with use cases and constraints before anyone writes code.
