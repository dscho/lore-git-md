This is **patch 6 of 12** in Derrick Stolee and Taylor Blau's v3 series integrating `--path-walk` with `--filter` in `git pack-objects`, preceded by a cover letter and a preparatory patch-set for `git backfill`. The cover letter from the same thread explains that `git backfill` uses the path-walk API as its core mechanism, with no fallback, so incompatible filters must be rejected early during argument validation rather than at walk time.

The patch is tiny but consequential for correctness: it replaces a blanket check that rejected *any* filter in `cmd_backfill()` with a call to the newly introduced `path_walk_filter_compatible()` function. That function determines which filters the path-walk API actually handles for the purposes of backfill (the cover letter confirms these are `blob:none`, `blob:limit=<size>`, `sparse:<oid>`, `tree:0`, `object:type=<type>`, and `combine`), and produces a specific error message—`"cannot backfill with these filter options"`—rather than the generic `"--filter"` rejection. Two new tests in `t5620-backfill.sh` confirm that `--filter=tree:1` and `--filter=blob:limit=10m` are rejected with the expected message.

The change is mechanically straightforward, consistent with the architecture being set up in patches 05/12 (which introduced `path_walk_filter_compatible()`), and well-tested. The only notable design point is that the error message is deliberately less specific than the old one: it tells the user *that* their filter is not supported for backfill, but not *which* filters are viable. That is a small UX regression from the old `"--filter"` message, but probably fine given that the backfill use case is narrow (local server-assisted partial-clone fetching, not general purpose). The patch looks clean and ready to go; the only thing worth flagging is that if the set of compatible filters grows later, the error message may need updating.
