This is a follow-up to the ongoing discussion about local branch pruning functionality, specifically addressing the architectural question of whether `git fetch` should be able to modify local branches. The patch removes the previously proposed `fetch.pruneLocalBranches` config option that would have allowed `git fetch` to automatically prune local branches when their upstream counterparts are deleted.

The change comes after Johannes Sixt's strong stance that branch modification should remain exclusively within `git branch`'s domain, and Junio Hamano's observation that the v4 series still included fetch integration despite the author's tentative agreement with Sixt's position. Harald Nordgren now confirms the removal of this functionality, settling the architectural debate in favor of keeping branch management separate from fetch operations.

The core branch-pruning functionality remains available through the standalone `git branch --forked` and `--prune-merged` commands, which include all the safety mechanisms (reachability checks, default branch protection, and per-branch configuration). This resolution maintains clearer command boundaries while preserving the practical utility of the feature through explicit branch operations rather than fetch integration.

The patch represents a significant design decision in this long-running thread, choosing architectural purity over convenience automation. With this change, any automation of branch pruning would need to be implemented through separate tooling or periodic execution of the branch commands, rather than being triggered by fetch operations.
