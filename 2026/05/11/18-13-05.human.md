This is a preparatory refactoring patch in Derrick Stolee’s `pack-objects --path-walk --filter` series, laying groundwork for the upcoming `sparse:<oid>` filter support.

The patch introduces a `pl_sparse_trees` flag to the path-walk API. When the path-walk engine is given sparse-checkout patterns, it currently prunes both trees and blobs for paths outside the sparse cone. That is correct for `git backfill --sparse` but wrong for the `sparse:<oid>` filter, which should restrict only blobs while still walking all reachable trees. This flag lets each caller choose: backfill sets it to 1 (prune trees), while the `sparse:<oid>` filter (coming in a later patch) will leave it at 0 (keep all trees).

The patch also fixes a subtle correctness bug in `add_tree_entries()`. Previously, the SEEN flag was set on an object immediately upon discovery, *before* checking whether its path matched the sparse patterns. If the same object ID appeared at multiple paths (e.g., sibling directories with identical contents), the first path visited would mark it SEEN. If that path happened to be outside the sparse cone, the object would be skipped there but also never discovered again at its in-cone path — effectively dropping objects from the walk. Moving the SEEN flag assignment to *after* the sparse-pattern check fixes this.

The rest of the diff is plumbing: a new `--pl-sparse-trees` option for the `test-path-walk` helper, and a test that confirms that with `--no-pl-sparse-trees`, the walk emits all trees (including those outside the sparse cone) while filtering only blobs.

This is a clean, well-explained structural change from an experienced contributor. The bug fix is independently worthwhile and the new flag makes the API’s behavior explicit per caller. The test covers the new option thoroughly. There are no apparent points of contention — this seems like unproblematic groundwork for the `sparse:<oid>` filter to come in the next patch.
