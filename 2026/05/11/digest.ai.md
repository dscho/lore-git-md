# Git Mailing List Daily Digest — 2026/05/11 (Monday)

**The day in brief.** A heavy-traffic Monday with 114 emails across 31 active threads. The day's dominant story is the v3 submission of Derrick Stolee and Taylor Blau's 12-patch series integrating `--path-walk` with `--filter` in `git pack-objects` — a substantial architectural change that has received no substantive review beyond a single typo correction. Also notable: the tempfile-ownership race in daemonized `git maintenance` reached a clearer resolution path, with Jeff King endorsing Taylor Blau's comprehensive fix and proposing a refinement to eliminate the double-delete risk.

## Notable threads

**`--path-walk` meets `--filter`: v3 lands, still unreviewed.** Derrick Stolee and Taylor Blau posted the third iteration of their series making `git pack-objects --path-walk` work with `blob:none`, `blob:limit`, `sparse:oid`, `tree:0`, `object:type`, and `combine` filters. The core architectural decision in v3 moves filter logic into the path-walk API itself rather than keeping it in `builtin/pack-objects.c`. Performance data is striking: `sparse:oid` repack on git/git drops from 77.91s to 31.41s. The series includes careful handling of edge cases — tagged trees under `tree:0`, a `strict_types` flag for `object:type`, and a recursive `prepare_filters_one()` helper for `combine`. The sole review of the entire 12-patch series remains Taylor Blau's catch of a one-character typo ("Whe" -> "The") in the documentation. Stolee confirmed the typo will be fixed in v4. The series has been in development since early May and is based on `en/backfill-fixes-and-edges`.

**Tempfile ownership race: Peff endorses comprehensive fix, proposes refinement.** The thread about repository corruption from `git maintenance run --detach` reached a clearer resolution point. Jeff King argued that the fix should live in `daemonize()` itself, transferring *all* tempfile ownership from parent to child automatically, rather than Patrick Steinhardt's narrower proposal of a lockfile-only `lock_file_reassign_owner()`. Peff then proposed a concrete refinement: have the parent reassign ownership to "0" (no owner) before `fork()`, then reclaim ownership if the fork fails. This eliminates the double-delete risk entirely — the worst case is a stale lock if the child dies before claiming ownership, which is already possible with `kill -9`. Jacob Keller signaled acceptance of the race as tolerable. Derrick Stolee's position on the fix-forward direction remains the key open question; Junio has not yet weighed in on the v2.54.1 release strategy.

**Branch pruning reaches v6 with refined merged-ness checking.** Harald Nordgren's series implementing `git branch --forked` and `git branch --prune-merged` reached its sixth iteration. The v6 refinement changes how merged-ness is determined: `--prune-merged` now compares against the remote's default branch (`refs/remotes/<remote>/HEAD`) rather than the candidate's specific upstream. Junio pushed back on this design choice, arguing that a local branch tracking `origin/todo` may have nothing in common with `origin/HEAD`, and that the existing `branch_merged()` function already does the right thing by checking the branch's specific upstream. The series otherwise appears technically complete with all safety mechanisms (default branch protection, per-branch opt-out via `branch.<name>.pruneMerged`, unpushed work protection) and multi-remote support via `--all-remotes`. Junio's feedback suggests the merged-ness logic needs to be reverted to checking the branch's specific upstream before the series can proceed.

**Merge-base optimization: 100x speedup, split into two patches.** Kristofer Karlsson's performance optimization for single merge-base calculations reached v4, now split into two commits per Patrick Steinhardt's suggestion: a pure refactoring introducing `enum merge_base_flags`, followed by the optimization that exits early from `paint_down_to_common()` when generation numbers are available. The speedup is dramatic — 5,229ms to 24ms in a 2.2M-commit monorepo. Junio's v2 review feedback (simplifying the generation number check, fixing comment formatting) has been incorporated. The series appears merge-ready with all substantive feedback addressed.

**`git format-rev` v5 posted, documentation hold requested.** Kristoffer Haugsbakk posted the fifth iteration of the `git format-rev` series, introducing a new command for on-demand pretty formatting of revisions from stdin. The v5 changes are all documentation-related: fixing AsciiDoc formatting for nested definition lists, clarifying NUL-handling in text mode, and simplifying example object names. The series has undergone thorough review from Phillip Wood (stream safety, NUL-handling design) and René Scharfe (code style). Junio had marked the topic ready for `next` in his "What's cooking" report, but Haugsbakk requested a brief delay to fix a remaining AsciiDoc formatting issue before it progresses.

**What's cooking: sideband sanitization held for Git 3.0, `format-rev` delayed.** Junio's biweekly status report tracks the state of Git development topics. Notable moves: the sideband control character sanitization series (from Johannes Schindelin) is ready to graduate from `next` to `master`, but the final patch loosening restrictions will be held until Git 3.0 to gather real-world feedback on the stricter defaults. New topics proposed for `next` include Windows nedmalloc removal, submodule.fetchJobs fix, proxy URL validation, merged branch pruning, and a new `git url-parse` command. The `kh/name-rev-custom-format` topic (`git format-rev`) was marked ready for `next` but is temporarily delayed at the author's request.
