This is a reply in the feature-request thread about allowing Git to configure which shell is used for aliases. The original proposal asked for a `core.shell` config key. Brian m. carlson pushes back firmly, explaining why the hard-coded `/bin/sh` is intentional and why the proposal is unlikely to be accepted as-is.

Brian's response is a substantive review of the proposal, not of any patch. He makes several technical arguments: the current behavior is deliberate because it guarantees consistent alias behavior across platforms; a per-user config option would break system-level aliases that ship with a specific shell in mind; Windows, zsh, and other non-POSIX shells would introduce quoting and security problems that Git cannot reasonably handle; and the "with-shell" mode that aliases use has a specific POSIX quoting format (`%s "$@"`) that would need to be reworked for arbitrary shells. He also points out that mksh is POSIX-compatible, so the closest existing workaround is the build-time `SHELL_PATH` variable, which was designed for systems with non-POSIX `/bin/sh` and would already work for this user. He references a prior discussion about PowerShell that covers similar ground.

A reader should note that Brian's position -- while technically well-grounded -- represents one well-known perspective on the list. His arguments about security and portability are mainstream concerns that any proposal would need to address, and his refusal to engage with the possibility of narrowing the scope (e.g., only allowing a configurable shell for user-level aliases, or only for POSIX shells) reflects his characteristic principled stance rather than necessarily the only viable design path. The proposal is now in a position where the original author would need to either refine the ask to address these objections or let the thread die.
