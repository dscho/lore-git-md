This is a regression bugfix for `git fetch --deepen`, and the second iteration of a patch that was already reviewed and largely agreed upon in the thread.

The bug was introduced in Git 2.54.0 by commit 3ef68ff40e. Running `fetch --deepen=<n>` on a non-shallow repository was incorrectly treating the relative deepen value as an absolute depth, causing the repository to become shallow and its history to be truncated. The fix is a tidy three-line change in `shallow.c`: in `get_shallow_commits()`, the code checks whether there is actually an existing shallow depth before adding the deepen amount. If the repository is not shallow (cur_shallow_depth returns zero), the function returns NULL, leaving the repository alone.

The patch also adds a test in `t/t5537-fetch-shallow.sh` that clones a repository fully, records its shallow status and commit list, runs `fetch --deepen=1`, and verifies that nothing changed. The test is straightforward and covers the regression properly.

The thread context shows that the earlier discussion had already settled the technical fix. The remaining open question was whether to add a warning when `--deepen` is used on a non-shallow repo (it has been a silent no-op since 2016), but Junio and René Scharfe agreed that is a separate concern for a separate patch. This v2 only fixes a commit-message formatting issue from v1 (the commit reference was wrong), so there is nothing new to discuss here technically.

This is a small, well-scoped, and uncontroversial fix. It has been adequately reviewed, tests the regression, and the broader discussion has already converged. It looks ready for picking into `next`.
