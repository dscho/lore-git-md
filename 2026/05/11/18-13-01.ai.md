This is patch 04/12 in the v3 `pack-objects --path-walk --filter` integration series from Derrick Stolee. It fixes a correctness bug where the path-walk API would silently drop directly-requested objects (such as blobs needed for a partial-clone fetch) when a filter was active.

The problem is subtle: the path-walk API classifies pending objects -- targets of lightweight tags, ref tips, and other explicitly-requested objects -- using paths that start with `'/'` (e.g., `/tags`, `/tagged-blobs`). Prior to this patch, the `walk_path()` function applied the same blob/tree type filters to these objects as to objects discovered during the tree walk. When a filter was active, this meant directly-requested blobs or trees could be skipped, which would break partial-clone fetches.

The fix works at a few levels. A new helper `path_is_for_direct_objects()` checks whether a path starts with `'/'`, and the type-filter logic in `walk_path()` now exempts direct-object paths from the filter. In `setup_pending_objects()`, the guards that skipped trees and blobs when their type flags were disabled are removed entirely -- all pending objects are now collected regardless. The most visible change is in `walk_objects_by_path()`, where `blob_objects` and `tree_objects` are temporarily forced to `1` before `prepare_revision_walk()` (so pending objects are preserved through that pass), then restored to the correct filter values immediately afterward. The documentation in both `path-walk.h` and the AsciiDoc technical docs is updated to clarify that type filters only apply to tree-discovered objects, not to pending ones.

The commit message frames this as a prerequisite for the filter integration patches that follow (04/12 through 12/12), and notes that the bug was uncovered by running the test suite with `GIT_TEST_PACK_PATH_WALK=1`. The patch is clearly motivated, the mechanism is well-explained, and the changes are self-contained within the path-walk subsystem. No tests are added in this patch itself, which is typical for a preparatory fix that will be exercised by the later patches in the series. This looks like a straightforward, correct patch that addresses a real correctness issue.
