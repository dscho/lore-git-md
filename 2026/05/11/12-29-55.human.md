This is a bugfix patch addressing an issue with `git maintenance`'s locking behavior when run with `--detach`. The patch comes from Patrick Steinhardt with help from several experienced contributors (Jeff King, Taylor Blau, and Derrick Stolee).

The core problem is that when `git maintenance --detach` runs, the lockfile meant to prevent concurrent maintenance operations gets cleaned up too early. This happens because the parent process creates the lock but exits after forking, while the child process continues running maintenance tasks. The lockfile cleanup occurs when the parent exits, leaving the child unprotected.

The solution introduces two new functions:
1. `daemonize_without_exit()` - a variant of `daemonize()` that doesn't exit the parent process
2. `lock_file_reassign_owner()` - transfers lockfile ownership between processes

The patch includes a thorough test case that verifies the lockfile remains in place until the background maintenance completes. The changes touch core functionality (lockfile handling and process management) but appear carefully implemented with clear commit messages and test coverage.

This looks like a well-constructed fix for a real race condition, addressing a subtle edge case in the maintenance command's background operation. The involvement of multiple experienced reviewers suggests the approach has been vetted.
