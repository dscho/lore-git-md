This is the seventh patch in Derrick Stolee and Taylor Blau’s 12-patch series adding `--filter` support to the path-walk API. Specifically, it adds `blob:limit=<size>` support: blobs whose size is equal to or greater than the limit are omitted.

The implementation lives in `path-walk.c`. During `prepare_filters()`, if the filter choice is `LOFC_BLOB_LIMIT`, the limit value is stored in a new `blob_limit` field on `path_walk_info`; if the limit is zero it degenerates to `blob:none` (all blobs excluded). During `walk_path()`, each blob batch is filtered individually — every blob in the batch gets an `odb_read_object_info()` call to check its size, and only blobs smaller than the limit are included. Blobs whose size cannot be determined (e.g., missing in a partial clone) are conservatively kept, matching the existing filter semantics.

A subtle but important design note is flagged explicitly in the commit message: `odb_read_object_info()` can trigger an on-demand download of missing blobs. This means `blob:limit` is not suitable for use with `git backfill`, whose whole purpose is to download missing blobs in batches — downloading them one-by-one defeats the point. So the patch adds a second rejection check in `builtin/backfill.c` that exits with `"cannot backfill with blob size limits"` rather than the generic `"cannot backfill with these filter options"` message. The existing test in `t5620-backfill.sh` is updated to expect the new message.

Two new tests in `t6601-path-walk.sh` exercise `blob:limit=0` (equivalent to `blob:none`, producing zero blobs) and `blob:limit=3` (partial filtering where some blobs in a batch are kept and others dropped). Both tests produce lengthy expected output listing every path with its type and OID.

This is a straightforward, well-documented patch in the series. The commit message explains the design thinking clearly, including the on-disk download tradeoff and why `git backfill` needs a separate rejection. The one quibble is the continuing "Whe" typo in `git-pack-objects.adoc` that was present in earlier patches — it's still there. Otherwise, the patch looks correct and uncontroversial within the larger series. The `odb_read_object_info()` call inside the walk is potentially expensive (one object-info lookup per blob in each batch), but the author is aware of this and the discussion so far has accepted the tradeoff as worth making for correctness.
