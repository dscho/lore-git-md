This is a maintainer checkpoint sent by Junio C Hamano in response to Harald Nordgren's just-posted v6 series for the `git branch --prune-merged` feature. This is **not** a patch -- it is a brief reply flagging a potential design problem.

The surface-level concern is about the description of the merged-ness check. In the v6 cover letter, Harald described it as "measuring merged-ness against the remote's default branch." Junio thinks this is likely a misunderstanding: the existing `branch_merged()` function already correctly checks against `branch_get_upstream()`, and it is that upstream tracking relationship that matters, not the remote's HEAD. The fallback to `head_rev` (the remote's HEAD) only happens when the upstream is not set, and that fallback is what was being questioned in earlier rounds. Junio is not sure whether it should even be kept optional.

This is a meaningful objection. If the patch series really does replace the upstream-based check with a remote-HEAD-based check, that would be wrong: a branch might track `refs/remotes/origin/todo` and not share any commits with `refs/remotes/origin/master` (the remote's default branch). Junio is asking for clarification before proceeding further.

**Bottom line:** The v6 series may have introduced a behavioral regression in its merged-ness logic. Unless Harald can clarify that he kept the upstream-based check and only touched the fallback path, this topic is likely heading back for another round of revision. A quick read of the actual code change would settle it.
