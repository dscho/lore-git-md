Patrick Steinhardt sent a two-patch v3 bugfix series addressing two issues in Git's maintenance subsystem. The first patch fixes a lockfile problem: when `git maintenance run --detach` forks, the parent process releases the lockfile immediately, allowing a second invocation to race with the still-running child. The fix, implemented inside `daemonize()`, reassigns ownership of all open tempfiles and lockfiles to the child process after forking, so the child cleans them up on exit and the parent does not release them early. The second patch restores the `gc.auto` integer-threshold behavior that broke when the default maintenance strategy stopped shelling out to `git gc`; now `maintenance.auto` takes precedence, with `gc.auto` as a fallback.

Taylor Blau pushed back on the v2 design and offered an alternative -- transferring ownership automatically inside `daemonize()` rather than at the call site -- which Patrick adopted for v3. Taylor praised the FIFO-based integration test as "much more robust" and appears as Co-authored-by and Signed-off-by on the v3 lockfile patch. Jeff King and Junio C Hamano each independently caught the `gc.auto` type error in earlier rounds. Junio then reviewed the v3 lockfile patch and endorsed the design direction, calling the framing -- that a daemonized child is logically a continuation of the original process -- natural and sound. The reply is a brief concurrence with no requests for change, effectively a maintainer sign-off.

The thread is fully settled: both patches are ready for merge with no outstanding change requests. No further revisions are needed.
