This is the 10th patch of a 12-patch v3 series by Derrick Stolee and Taylor Blau integrating `--filter` support into `git pack-objects --path-walk`. This specific patch (authored by Taylor Blau) adds `tree:0` filter support.

The `tree:0` filter suppresses all trees and blobs from output, keeping only commits and tags. The mapping onto the path-walk infrastructure is straightforward because the decision depends only on object type, not on any path-dependent state. The patch sets `info->trees = 0` and `info->blobs = 0` in `prepare_filters()` when the `LOFC_TREE_DEPTH` filter is requested with depth zero, and the existing path-walk plumbing -- which skips the root-tree fetch, suppresses pending trees and blobs, and stops the revision walk from enumerating them -- handles the rest with no extra work.

A subtle correctness detail: tagged trees (trees pointed to by annotated tag objects) need special treatment. When trees are disabled, pending trees that come in via tags are collected into a special `/tagged-trees` pseudo-path list, which bypasses the type filter so they are still emitted. This is the same pattern the code already uses for `/tagged-blobs` when blobs are disabled. Without this, a `git rev-list --objects`-style walk under `tree:0` would silently drop tagged-tree objects that the caller might legitimately expect.

Non-zero tree-depth filters (`tree:1`, `tree:2`, etc.) are rejected with a specific error message, causing pack-objects to fall back to the standard revision walk -- the same mechanism used for other unsupported filters. The commit message explains that these depend on the depth at which a tree is visited, a concept the path-walk API does not currently expose to the filter machinery.

Test coverage in `t6601-path-walk.sh` is clean: one test checks `--all` output (confirming commits, tags, tagged blobs, and tagged trees are all emitted but normal trees and blobs are not), one checks a single-branch walk with `topic` (no tags at all, so only three commits), and one confirms that `tree:1` produces the expected rejection message. The tests are placed before the sparse-filter setup to avoid interference from the orphan branch that later tests create.

This is a clean, well-motivated patch from a contributor with deep pack-format expertise. The special handling of tagged trees is the kind of edge case that would be easy to miss and is correctly caught here. The decision to reject non-zero tree depths rather than silently do the wrong thing is the right call. Like the other patches in this series, it has not attracted any review discussion yet.
