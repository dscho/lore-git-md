This is a thread-root email from Junio C Hamano, the maintainer, reviewing the v6 series. It is a substantive review.

Junio pushes back on the v6 refinement that `--prune-merged` now checks against the remote's default branch (`refs/remotes/<remote>/HEAD`). He argues that the change from checking against a branch's specific upstream to checking against the remote's HEAD is misguided: a local branch that tracks `refs/remotes/origin/todo` may have nothing in common with `refs/remotes/origin/HEAD` (which typically points to `origin/master`), so using the remote HEAD as the merged-ness base would produce incorrect results -- it would not reflect what the branch was actually built on top of.

Junio points out that the existing function `branch_merged()` already does the right thing: it calls `branch_get_upstream()` to find the branch's specific upstream remote-tracking branch and compares against that. Only when no upstream is found does it fall back to `head_rev` (which is the remote's HEAD). He notes that the code is already prepared to handle a NULL `head_rev` gracefully, and suggests that the fallback behavior may want to be optional rather than changed.

The implication is that the v6 refinement likely introduces a regression for branches that track a non-HEAD remote branch. Junio is not rejecting the series outright but is asking for clarification and reconsideration of this design choice. The core feature direction remains viable, but this particular detail -- what to compare against when checking merged-ness -- needs to be reverted back to checking the branch's specific upstream before the series can proceed.
