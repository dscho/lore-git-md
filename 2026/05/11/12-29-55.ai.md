This is a bugfix patch for `git maintenance`'s locking behavior when run with `--detach`. The issue affects the maintenance lockfile's persistence when the process daemonizes.

The patch addresses a race condition where the maintenance lockfile (which prevents concurrent maintenance runs) could be prematurely removed when using `--detach`. Currently, the parent process creates the lock but exits after forking, causing the lock to be released before the background maintenance completes. 

Patrick Steinhardt's solution introduces two new functions:
1. `daemonize_without_exit()` - A variant of `daemonize()` that doesn't exit the parent process
2. `lock_file_reassign_owner()` - Transfers lockfile ownership between processes

The fix ensures the lock persists through the entire maintenance operation by:
- Having the parent process transfer lock ownership to the child before exiting
- Having the child process take ownership of the lock after daemonizing

The patch includes extensive test coverage that verifies the lockfile remains in place until the background maintenance fully completes. It was developed with input from several core contributors (Jeff King, Taylor Blau, Derrick Stolee) and addresses a real-world issue reported by a user.

This is a focused, well-tested fix that touches the maintenance subsystem's process management and locking behavior. The changes are contained to `builtin/gc.c`, `lockfile.c/h`, and `setup.c/h`, with a comprehensive new test case added to verify the behavior.
