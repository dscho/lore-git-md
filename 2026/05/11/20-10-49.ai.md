This is a reply from Jeff King (Peff) to Derrick Stolee's review in the ongoing thread about fixing the maintenance daemonization locking issue. The thread has been debating whether to fix forward with Taylor Blau's `reassign_tempfile_ownership()` approach or revert the geometric repack default for the v2.54.1 stable release. Peff addresses two specific technical points Stolee raised.

First, Peff confirms that Windows platform concerns are not a blocker: the `daemonize()` function is already a no-op on Windows, so the proposed tempfile ownership fix would never be invoked there. This removes one of Stolee's concerns about cross-platform compatibility.

Second, Peff addresses Stolee's request for a test that proves the detached process cleans up locks on both normal exit and early exit. For the normal-exit case, Peff acknowledges this is straightforward but notes that the existing test already covers it indirectly (the child process calls `rollback_lock_file()` on normal exit and never checks the owner field). For the early-exit case, Peff explains that triggering an early exit is actually hard in practice: the only thing the process does while holding the maintenance lock is run subprocesses via `run-command`, and there is no obvious path that leads to a `die()`. However, signals can cause an early exit, and Peff describes a concrete test approach: use a long-running maintenance operation (`git gc` on the linux.git repository), verify the lock exists, kill the detached process with SIGTERM, and confirm the lock was cleaned up. He notes that Taylor has already found a way to make an arbitrarily slow task using the prefetch process, so the test could be modified to issue a kill at the right moment and verify cleanup.

This is a substantive review from Peff -- he engages directly with Stolee's technical concerns, provides platform-specific analysis, and proposes a concrete test strategy. It is not a full re-review of Taylor's patch; rather, it is a targeted rebuttal of remaining objections, clearing the way for the fix-forward approach. Peff's word carries significant weight on technical correctness, and his implicit endorsement of the proposed direction here (by helping address Stolee's concerns rather than raising new ones) should help move the discussion toward resolution.
