This thread addresses a bug in `git log --follow` where it fails to track file renames across subtree merges, showing only the outer repository's history. Miklos Vajna has proposed a solution that carefully extends the rename-following logic to handle this case while preserving existing behavior for ambiguous scenarios.

The patch modifies `log_tree_diff()` to detect when a path is unchanged in all parents except one - treating file additions as "unchanged" for this purpose. This allows it to follow renames from the single changed parent, which covers the common subtree merge case where a file is added in one parent and renamed in another. Jeff King had previously raised concerns about ambiguity when multiple parents have independent rename histories, and this implementation addresses that by only following renames when there's a clear single parent with changes.

The change comes with thorough test coverage in a new test file (`t4218-log-follow-subtree-merge.sh`) that verifies both the fixed subtree merge case and the unchanged behavior for multiple rename sources. The solution appears well-considered, making a pragmatic improvement to rename following while acknowledging the fundamental limitations of Git's single-path-following model.
