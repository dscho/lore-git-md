This is a bugfix patch addressing `git log --follow` behavior with subtree merges. Currently, when following a file's history across a subtree merge (where one repo is merged into a subdirectory of another), `--follow` fails to show commits from the merged repository. The patch improves this by making `--follow` track the file's history through the parent where it was changed, while maintaining existing behavior for cases where a file has rename history on multiple parents.

The change is motivated by the observation that `git blame` can find these pre-merge commits, so `git log --follow` should be able to as well. The implementation adds logic to detect when a path is unchanged in all parents but one (treating file additions as "unchanged" for this purpose), and follows the rename in that parent. The patch includes tests demonstrating both the fixed subtree case and the unchanged behavior for multi-parent rename scenarios.

Jeff King (Peff) raised concerns in the thread about whether this makes the already-imperfect `--follow` behavior more useful or just differently broken. The current patch represents a compromise that handles the subtree case while not changing behavior for other merge scenarios. The implementation appears careful, with new test coverage for both the target case and edge cases.
