This is a bugfix patch addressing a limitation in `git log --follow` when dealing with subtree merges. The current implementation fails to follow renames across subtree merges, only showing history from the outer repository. Miklos Vajna proposes a solution that improves rename following in merge commits while maintaining existing behavior for other cases.

The patch changes `log_tree_diff()` to detect when a path is unchanged in all parents except one (treating file additions as "unchanged"), and in that case follows the rename from the changed parent. This handles the common subtree merge case where a file is added in one parent and renamed in another, while not changing behavior when multiple parents have independent rename histories for the file.

The implementation includes tests demonstrating both the fixed subtree merge case and the unchanged behavior for multiple rename sources. Jeff King had raised concerns about the ambiguity when multiple parents have rename sources, and this patch addresses that by only following renames when there's a clear single parent with changes.

Key technical details:
- Modifies the rename-following logic in `log-tree.c`
- Adds a new test file `t4218-log-follow-subtree-merge.sh`
- Handles the "addition vs rename" case common in subtree merges
- Preserves existing behavior for ambiguous rename cases

The patch appears well-considered, with clear test coverage for both the target case and edge cases. It represents a pragmatic improvement to rename following while acknowledging the fundamental limitations of the single-path-following model.
