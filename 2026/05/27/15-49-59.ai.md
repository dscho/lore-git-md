Performance optimization for revision walking using priority queues.

This 3-patch series from Kristofer Karlsson follows up on a previous optimization that replaced O(N) linked-list insertion in `limit_list()` with a priority queue. The current work targets the streaming (non-limited) walk in `get_revision_1()`, which similarly suffers from O(w) insertion costs where w is the walk frontier width.

The series takes a conservative approach by:
1. First fixing a memory leak in pack-objects that becomes visible with the new queue implementation
2. Introducing a `rev_walk_mode` enum to clean up dispatch logic in `get_revision_1()`
3. Converting the streaming walk to use a priority queue while maintaining compatibility with existing callers

Benchmarks show dramatic improvements for merge-heavy repositories (5.3x faster for a 2.4M commit monorepo), while having no measurable impact on repositories with narrow walk frontiers (like linux.git). The optimization removes what was previously the dominant bottleneck - queue maintenance now accounts for just 16% of runtime versus 79% before.

The changes touch core revision walking logic but appear carefully scoped, with clear performance data showing the benefits. The cover letter thoughtfully addresses potential concerns about broader impacts by including regression checks across different repository types and walk modes. This looks like a well-motivated optimization that follows the pattern of an earlier successful change while minimizing disruption to other code paths.
