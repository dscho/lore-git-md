This is a technical discussion about the proposed `git mv --index-only` feature, continuing from earlier exchanges.

Chris Torek follows up on Junio Hamano's response about the efficiency aspects of the proposed `git mv --index-only` flag. He clarifies that the efficiency gain comes from avoiding content hashing of large files when recording moves in the index, similar to how regular `git mv` operates. The proposed flag would skip working tree operations while maintaining the same index update behavior.

Torek provides a practical example - when dealing with a 3TB file, the flag would prevent Git from unnecessarily reading and hashing the file contents when only the index needs updating. He draws a parallel to `git rm --cached` as Junio did, agreeing it could serve as a useful "morning-after" correction tool but expressing skepticism about whether the convenience justifies implementing it as a core feature.

Notably, Torek shares that he's already implemented this functionality as a shell script in his personal scripts repository, suggesting the feature might be better suited as an external helper rather than a built-in command flag. The thread appears to be winding down with general agreement about the technical merits but no clear consensus on whether to proceed with the implementation.
