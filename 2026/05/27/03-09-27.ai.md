Maintainer commentary on the `git mv --index-only` proposal.

Junio C Hamano weighs in on the discussion about adding an index-only` mode to `git mv`, agreeing with Chris Torek's technical assessment that the same effect can be achieved through existing `git add`/`git rm` commands. However, he provides additional context about the efficiency implications and clarifies some potentially confusing aspects of Torek's explanation regarding rename detection.

The maintainer draws a useful parallel between the proposed feature and the existing `git rm --cached` functionality, positioning it as a similar "morning-after" correction tool for cases where files were moved without informing Git. This framing suggests the feature could have merit as a convenience wrapper, though Junio stops short of explicitly endorsing its implementation.

Key technical clarifications:
- Confirms index operations would be identical between the proposed flag and manual `add`/`rm`
- Notes the CPU efficiency difference comes from avoiding redundant object lookups
- Explains how rename detection works independently of how the index state was achieved
- Draws analogy to `git rm --cached` as precedent for corrective operations

The response maintains a neutral stance while providing important technical context that could help shape the proposal's next iteration. Junio's comparison to existing corrective mechanisms suggests the concept isn't fundamentally problematic, leaving the door open for Frieder to refine the use case justification or implementation details in a follow-up.
