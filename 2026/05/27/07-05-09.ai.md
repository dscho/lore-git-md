This is a performance optimization proposal for `git branch --contains` and related ref listing operations, building on Jeff King's earlier analysis in the thread. Kristofer Karlsson from Spotify revives the discussion with concrete benchmark data showing significant speedups from enabling the cached DFS algorithm (`contains_tag_algo`) for branch operations when generation numbers are available via commit-graph.

The key findings show dramatic improvements in large repositories:
- 15-16x speedup for deep history queries in a monorepo (4.14s -> 272ms)
- 3.7x speedup for deep tags in git.git (1.08s -> 292ms)
- The optimization is strictly better when generation numbers exist, with crossover point around 3-6 refs where both algorithms perform similarly

Kristofer makes a strong case that the change is safe when commit-graph is present, though notes the theoretical analysis is less clear without generation numbers. The benchmarks demonstrate real-world impact at Spotify's scale (millions of commits, thousands of refs), validating the optimization's value for large repository workflows. The patch appears to be a straightforward application of existing infrastructure (`contains_tag_algo`) to a new use case, with no apparent downsides when generation numbers are available. This moves the thread forward from analysis to implementation, providing the performance data needed to evaluate the change.
