This is the second patch in Kristofer Karlsson's 3-part series optimizing revision walking with priority queues. It introduces a `rev_walk_mode` enum to clarify the dispatch logic in `get_revision_1()`.

The patch refactors how `get_revision_1()` selects between different walk strategies (reflog, topological, limited, and streaming). Previously, these were determined by checking `rev_info` flags in multiple places within the function, creating potential for logic drift between the selection and parent expansion steps. The new version:
- Defines an explicit `rev_walk_mode` enum
- Centralizes mode selection in a `get_walk_mode()` helper
- Uses a single switch statement for both commit selection and parent expansion

This is a pure refactoring with no behavior change, preparing for the priority queue conversion in the next patch. The enum makes the code more maintainable by:
- Documenting the possible walk modes
- Ensuring consistent mode handling between selection and expansion
- Making it easier to verify all modes are handled correctly

The change touches core revision walking logic but is carefully scoped to just the dispatch mechanism. It follows the pattern of the series' first patch (a memory leak fix) in being a prerequisite cleanup that reduces risk for the subsequent optimization. The patch appears well-structured with clear commit message explaining the motivation and implementation.
