This is the sixth patch in the `git history squash` series (v14, 8 patches total), implementing the ref-protection logic that prevents the command from leaving local branches dangling. The patch is part of a feature that folds a commit range into its oldest ancestor in a single operation, avoiding the repeated conflict resolution of a rebase-based approach.

The patch adds a new `advice.historyUpdateRefs` configuration knob and uses Git’s existing `ref-filter` machinery to detect local branches that descend from the selected range but do not contain its tip. If any such branches exist, the command refuses the operation unless `--update-refs=head` is specified, which restricts updates to the current branch. The blocking branches are sorted and printed in short form (e.g., `topic-1`, `topic-2`) so the user can decide whether to move them or leave them behind. The implementation is careful to limit protection to local branches, matching the refs that the default rewrite mode updates; tags and remote-tracking refs are untouched.

The patch is well-motivated and technically sound. It addresses a real usability concern—preventing accidental history divergence—without overreaching into unrelated ref classes. The use of `ref-filter` keeps the code idiomatic and maintainable, and the sorted, formatted output is a thoughtful touch. The test coverage is thorough, verifying both the error message and the advice-suppression behavior. This is a substantive, uncontroversial piece of the series that looks ready for integration.
