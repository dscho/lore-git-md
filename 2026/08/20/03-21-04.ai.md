This is a **bugfix** targeting Git's HTTP authentication layer. The patch addresses a regression where `WWW-Authenticate` headers from an HTTP redirect response are lost when Git updates the credential struct for the new URL. This breaks authentication when the redirect target requires a credential helper (e.g., OAuth2 Bearer tokens) rather than URL-embedded credentials.

The fix introduces `credential_update_url()`, a new helper in `credential.c` that wraps `credential_from_url()` but preserves the `wwwauth_headers` field across URL updates. The implementation uses `SWAP()` to avoid copying the entire `strvec`, making it efficient. The patch updates `http.c` to use this helper when recovering from redirects, ensuring the authentication challenge from the server survives the URL transition.

The commit message clearly explains the problem: the `WWW-Authenticate` challenge is derived from the server's response, not the URL, and must persist so credential helpers can determine which authentication methods are valid for the redirect target. The v2 iteration moves the preservation logic into `credential.c`, making it reusable for future credential fields that might need similar treatment.

Test coverage is thorough: a new test in `t/t5563-simple-http-auth.sh` verifies that `wwwauth_headers` are preserved after a redirect, using a custom Apache rewrite rule (`/custom_auth_redir/`) that redirects to a bearer-auth-protected endpoint. The test checks both the credential query (with preserved headers) and the subsequent credential storage.

The patch is well-motivated, with a link to a prior report of the same bug and a reference to Junio's earlier suggestion to centralize the preservation logic. The changes are minimal and focused, touching only the HTTP and credential subsystems.
