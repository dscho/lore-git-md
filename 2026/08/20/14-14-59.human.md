This is a review reply from Karthik Nayak on Patrick Steinhardt’s v2 patch series refactoring how the object database (ODB) handles corrupt objects with the `OBJECT_INFO_DIE_IF_CORRUPT` flag. The series is part of the ongoing ODB abstraction effort and is now in its second iteration, addressing Junio C Hamano’s feedback on return conventions and error propagation.

Karthik’s review is substantive but narrowly focused on code hygiene and error-propagation semantics rather than design or correctness. He raises two specific points: first, in patch 2/7, he notes that while the return type of several functions is updated to `enum odb_read_status`, the functions still return raw integers (`0` or `-1`) instead of the named enum constants (`ODB_READ_OK`, `ODB_READ_ERROR`). This could reduce code clarity and increase the risk of misuse as the enum expands. Second, in patch 3/7, he questions the error-propagation logic in the files backend, which implicitly prioritizes certain error codes over others—specifically, it filters out `ODB_READ_NOT_FOUND` from the packed backend, effectively preferring `ODB_READ_ERROR` from the packed backend over any error from the loose backend, and `ODB_READ_NOT_FOUND` from the loose backend over `ODB_READ_ERROR` from the packed backend. Karthik asks whether this behavior is intentional, noting that the commit message does not explain the error-propagation policy.

The review is polite and constructive, framing the issues as small questions rather than objections. It does not challenge the overall design or correctness of the series, and Patrick has not yet responded to these points. The series itself is well-structured, with clear commit messages and thorough test coverage, and addresses all of Junio’s design-level feedback from v1. The remaining open question about the granularity of the `bad_pack` logic—specifically, whether the error-reporting mechanism can handle duplicate objects in corrupt packs—remains unresolved but is not directly addressed in this review.
