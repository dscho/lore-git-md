This is a **substantive review** of patch 3/7 in Patrick Steinhardt’s ODB refactoring series, focusing on the new `ODB_READ_NOT_FOUND` error code. Karthik Nayak’s feedback targets a specific logic branch in `odb/source-files.c` where the files backend decides which error to propagate when both the packed and loose backends fail.

The review raises two points. First, a **surface-level nit**: Karthik suggests replacing the implicit boolean check `if (!ret_packed)` with the explicit `if (ret_packed == ODB_READ_OK)` for clarity, mirroring his earlier feedback on patch 2/7 about using named enum constants instead of raw integers. Second, and more substantively, he questions the logic that filters out `ODB_READ_NOT_FOUND` for the packed backend: the current code returns `ret_packed` only if it is not `ODB_READ_NOT_FOUND`, otherwise it returns `ret_loose`. Karthik’s analysis shows this effectively prioritizes `ODB_READ_ERROR` from the packed backend over any error from the loose backend, and `ODB_READ_NOT_FOUND` from the loose backend over `ODB_READ_ERROR` from the packed backend. He asks whether this is the intended behavior, noting that the commit message does not explain the error-propagation policy.

The review is narrowly scoped to this one function and does not challenge the overall design or correctness of the patch. No test failures or edge cases are identified; the concern is purely about code clarity and whether the current logic matches the intended semantics. Patrick Steinhardt has not yet responded.
