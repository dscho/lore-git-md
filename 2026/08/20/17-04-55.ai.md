This is a substantive review comment on the first patch of Patrick Steinhardt’s six-part v3 series introducing a pluggable ODB interface for packfile generation. Junio C Hamano raises a specific technical question about the lifecycle of the `pack_fd` file descriptor in the new `odb_generate_pack()` interface.

The question targets the contract around `pack_fd` in `struct odb_generate_pack_options`: when the caller provides a file descriptor (not `-1` or `0`), the documentation states it "is consumed by the generator". Junio asks whether this means the generator is responsible for closing the descriptor after writing the pack, and crucially, what happens if the primary ODB source does not support packfile generation at all. In that error case, the function returns an error code without touching the descriptor, leaving it open and potentially leaked if the caller assumes the generator will close it.

The review is narrowly scoped to this one edge case in the interface contract. Junio’s concern is that the current implementation does not address descriptor cleanup in the error path, which could lead to resource leaks if the caller does not explicitly close `pack_fd` after an error return. The question is mechanical and precise: should the interface guarantee that `pack_fd` is always consumed (and thus closed) by the generator, even on error, or should the caller retain responsibility for cleanup in all cases?

This is a substantive issue because it affects the interface’s safety and usability. The review does not engage with the broader design or the rest of the patch, but the question is well-placed: the interface’s documentation implies a contract that the implementation does not fully uphold. The answer will determine whether callers must handle descriptor cleanup themselves or can rely on the generator to manage it.
