This is the second patch in Patrick Steinhardt’s five-patch v3 series refactoring the object database (ODB) subsystem to remove lazy-loading of alternates. The email is a review from Junio C Hamano focusing on the deduplication logic for alternate object database sources, specifically the use of `core.ignoreCase` for case-insensitive path comparisons.

Junio’s review engages substantively with the patch’s design, questioning whether `core.ignoreCase` should even be part of the repository configuration. He raises a fundamental issue: if a repository spans filesystems with different case sensitivities, the current approach could lead to inconsistent behavior in the equality function (`eq()`). Junio suggests that each object database source should report its own case-sensitivity rather than relying on a global repository setting, though he acknowledges this would require a more complex design. He also explores simpler alternatives, such as documenting that users must spell paths consistently (as `readdir()` would report) or declaring that repositories cannot span filesystems with different case sensitivities.

Junio’s feedback on the implementation is technical and precise. He questions whether `o->repo->initialized` is guaranteed to be true when `odb_source_paths_cmp()` is called, noting that while `o->repo` is set early in `odb_new()`, the repository’s configuration might not yet be fully loaded. He suggests that the function should default to case-sensitive comparison if the repository isn’t initialized, rather than risking an unsafe call to `repo_config_get_bool()`. This is a correctness concern that could lead to flaky behavior if not addressed.

The review also touches on the `NEEDSWORK` note in the patch, which flags the case-insensitive deduplication mechanism as potentially unnecessary. Junio does not explicitly endorse or reject the note, but his questions about the complexity and edge cases align with the broader consensus that the mechanism may not be worth retaining. His alternative proposals (e.g., user education or filesystem homogeneity) suggest a preference for simplicity over the current approach.

No resolution or follow-up is proposed in this email; the discussion remains open. The patch’s fate hinges on whether Patrick can address Junio’s concerns about case-sensitivity handling and repository initialization timing, or whether the project will opt to remove the case-insensitive logic entirely. The review is substantive and raises non-trivial design questions that may require broader discussion.
