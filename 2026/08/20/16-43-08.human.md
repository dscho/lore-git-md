This is a **feature proposal follow-up** in the ongoing `git pull --hard` / `--reset` discussion. Artur Bieniek, the original author, now endorses Phillip Wood’s proposed redesign (`git pull --reset`) and offers a concrete use case that Junio’s `git pull --ff-only` alternative does not address: tracking an upstream branch that is frequently rewritten (e.g., rebased or force-pushed).

Artur argues that `--ff-only` fails when upstream history diverges, leaving users with no built-in way to sync a clean working tree to the latest upstream state. He sees `--reset` as a natural fit for this scenario, framing it as a safer, more explicit alternative to the existing `git fetch && git reset --hard @{u}` workflow. The key distinction from his original `--hard` proposal is that `--reset` would error out by default if uncommitted changes exist, requiring an explicit `--discard-changes` or `--autostash` to proceed. This aligns with Phillip’s safety-focused redesign and directly targets Junio’s concerns about implicit destructive behavior.

The email does not include a revised patch or implementation details, but it signals the author’s willingness to adopt the `--reset` design. The thread remains at a conceptual impasse: Junio has rejected the feature’s underlying motivation, not just its implementation, and no other participants have weighed in on this latest exchange. Whether this use case will sway Junio’s position—or whether the discussion will stall here—is still unclear. For now, this is a well-motivated counterpoint to Junio’s stance, but the feature’s future remains uncertain.
