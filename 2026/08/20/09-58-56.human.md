This is a review reply in the `git pull --hard` thread. Phillip Wood proposes a design pivot that could salvage the feature by making it safer and more aligned with Git’s philosophy.

Phillip suggests replacing the current `--hard` option with a new `--reset` mode that, by default, refuses to run if there are uncommitted changes. This would prevent accidental data loss for users who have local changes they care about. The mode would offer two sub-options: `--discard-changes` (the current destructive behavior) and `--autostash` (which stashes uncommitted changes before resetting and reapplies them afterward). This design keeps the convenience of a single command while making the destructive operation explicit and opt-in.

The proposal directly addresses Junio’s core objection: that `git pull` is about history integration, not destructive resets. By making the reset behavior conditional on explicit flags and protecting uncommitted changes by default, Phillip reframes the feature as a safer "working copy update" rather than a history-destroying shortcut. He also notes that unreachable commits remain recoverable via the reflog, further mitigating the risk of accidental data loss.

This is a substantive review contribution that shifts the discussion from "should this exist?" to "how could this exist safely?".
