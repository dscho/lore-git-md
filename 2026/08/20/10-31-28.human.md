This is a bugfix patch for `git worktree add`, now at version 4, that restores the intended behavior where explicit `-b` or `-B` options take precedence over DWIM (Do What I Mean) branch resolution. The patch addresses a regression introduced in Git 2.42.0 (commit `128e5496b3`) where providing `-b <new-branch>` with a branch name that could be DWIMmed to a remote-tracking branch would incorrectly ignore the `-b` option and create a worktree for the DWIMmed branch instead.

The change is minimal and surgical: in `builtin/worktree.c`, the DWIM logic is now guarded by a check for `!new_branch`, ensuring it only runs when no explicit branch creation option (`-b` or `-B`) is given. The test in `t/t2400-worktree-add.sh` verifies that `git worktree add -b branch ../wt foo` fails with the expected error message (`fatal: invalid reference: foo`) rather than silently DWIMming `foo` to a remote-tracking branch. The commit message has been refined to cite the regression commit in the preferred `log -1 --pretty=reference` format, and the test uses `setup_remote_repo` for precision.

This version (v4) is a final polish after thorough review; all prior feedback has been addressed, including preserving warning behavior for edge cases (e.g., `-b` with `HEAD`) and ensuring the test is robust. The patch is now merged to `master` and resolves the regression cleanly without side effects. If you use `git worktree add` with `-b` or `-B`, this fix ensures your explicit branch name is respected.
