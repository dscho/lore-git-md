This is the final version of D. Ben Knoble’s three-patch series converting the build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`). The series is now ready to graduate from the `dk/use-nsec-runtime` topic to `next` and, eventually, `master`.

The core change allows users to enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The v6 update is purely cosmetic: it incorporates Patrick Steinhardt’s requested change to replace "defined" with "enabled" in a comment in `builtin/update-index.c`, better reflecting the runtime nature of the new config option. All prior technical feedback—including performance regression fixes, cross-platform correctness concerns, and architectural constraints—has been addressed in earlier iterations.

The first patch fixes a Meson build-system issue (`MAN_BASE_URL` configuration), and the second is a no-op refactor of `repo_config_values_init` to group assignments by config section. Both are uncontroversial and ready to advance independently. The third patch introduces `core.useNanosec` (defaulting to false) and updates the relevant code paths (`is_racy_stat`, `statinfo`, etc.) to use the runtime value. The series preserves backward compatibility on platforms lacking nanosecond support by treating the `use_nanosec` field as false when `NO_NSEC` is defined, and the documentation now explicitly warns about platform/filesystem limitations.

A minor textual conflict exists with `ty/repo-config-cleanups` in `seen` (which removes comments in `struct repo_config_values`), but resolution will be routine if both topics advance. The series is well-tested, with performance benchmarks confirming the v1 regression (~41× slowdown) has been resolved by caching the config value in `repo_config_values`. The only lingering architectural constraint—the new dependency on `repo_config_values()` in `is_racy_stat()`—is acknowledged but not blocking, as it merely makes an existing limitation (restriction to `the_repository`) more visible. Patrick Steinhardt suggests refactoring to `struct repo_settings` as a potential future mitigation if edge cases arise.

This is a clean, well-motivated change that addresses a long-standing usability pain point. The author has been responsive to feedback, and the series has received thorough review from Junio and Patrick Steinhardt. If you care about "racy Git" issues or runtime configurability, this is worth tracking as it moves toward `master`.
