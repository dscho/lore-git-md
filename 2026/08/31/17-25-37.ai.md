This is the **first patch in a seven-part bugfix/hardening series** targeting the trace2 subsystem. It introduces `banned-die.h`, a new header that enforces compile-time bans on functions that can trigger `die()`—such as `die()` itself—in low-level APIs. The immediate goal is to prevent trace2 from crashing Git during telemetry operations, particularly in `atexit()` handlers where `die()` recursion can occur.

The patch creates `banned-die.h` at the root of the tree, signaling intent for broader reuse beyond trace2. The header currently bans only `die()`, though the commit message hints at future expansion to include other `die()`-triggering helpers (e.g., `xsnprintf()`, `xstrdup()`). All trace2 implementation files now include this header, with a comment emphasizing it must be the last include to avoid silent bypasses. This addresses Elijah Newren’s prior concern about include-ordering risks.

**Key details:**
- **Files touched:** 14 files, including all trace2 `.c` files and the new `banned-die.h`.
- **Mechanism:** The header uses `BANNED(die)` (uppercase, per v3 feedback) to block `die()` at compile time. This is a defensive measure to prevent regressions, though Jeff King’s review highlights it does not address indirect `die()` calls via helpers like `strbuf`.
- **Scope:** The patch is narrowly focused on trace2, but the header’s placement and Junio’s earlier feedback suggest it could be reused for other subsystems (e.g., to ban `the_repository` or `the_hash_algo`). Patrick Steinhardt’s follow-up reinforces this potential, noting Git already uses similar patterns for `the_repository`.

**Assessment:** This is a **well-crafted, incremental step** toward hardening trace2. The mechanism is simple but effective for its limited scope, and the patch addresses prior feedback thoroughly (e.g., macro naming, include-ordering documentation). While Jeff King’s critique about indirect `die()` calls remains unresolved, the series frames this as a pragmatic first step rather than a complete solution. The patch is **worth attention** for its architectural implications—`banned-die.h` could become a template for future hardening efforts—but its immediate impact is confined to trace2. No behavioral changes are introduced yet; the ban is currently a safeguard against future misuse.
