This is the fifth patch in a six-patch performance series (v3) for the experimental `git last-modified` command. It introduces a Bloom-filter-based pre-filter to avoid unnecessary tree diffs when checking whether a commit modified any path matching the user’s pathspec.

The patch adds a 12-line block in `builtin/last-modified.c` that calls either `revs_maybe_changed_in_bloom()` (for the simple case) or `revs_maybe_changed_in_bloom_with_parents()` (when `--show-trees` is given) before iterating over individual paths. The helper functions were introduced in earlier patches: the former checks the pathspec itself, while the latter checks every parent directory up to the root, ensuring that changes to parent directories are not missed when `--show-trees` is active. A new 21-line test in `t/t8020-last-modified.sh` verifies that the Bloom filter fast-path works correctly with `--show-trees` by comparing the output of `git last-modified -t HEAD -- d/a` with and without the commit-graph enabled.

The change is purely internal and does not alter user-visible behavior; it simply avoids expensive diff operations when the Bloom filter can prove that no relevant path was modified. The commit message explains the rationale clearly and ties the patch back to the series’ overall goal of matching `git log`’s performance. The test coverage is thorough, exercising both the happy path and the `--show-trees` edge case. No open questions remain; this patch is ready for integration.
