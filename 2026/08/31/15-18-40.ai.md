This is a performance optimization for the experimental `git last-modified` command, now in its third iteration (v3). The series reuses Git’s Bloom filter machinery to speed up queries about the last commit that modified files matching a pathspec, including wildcards. The v3 reroll adds trace2 instrumentation to verify that the Bloom filter fast-path is correctly triggered for top-level wildcard pathspecs (e.g., `*.c`), addressing the last remaining test gap identified in v2.

The benchmarks in the cover letter show a 3.7× speedup without `--show-trees` (from 60.7 ms to 16.2 ms) and a 1.95× speedup with `--show-trees` (from 61.9 ms to 31.8 ms) on the ziglang/zig repository, bringing `git last-modified` nearly to parity with `git log`. The changes touch `revision.c`, `revision.h`, `bloom.c`, `bloom.h`, `builtin/last-modified.c`, and the test suite. The new trace2 counter (`bloom_queries`) and accompanying test in `t/t8020-last-modified.sh` verify that the per-path Bloom filter logic is invoked exactly twice for a top-level wildcard query, confirming the fix for the edge case where `prepare_revision_walk()` clears `bloom_filter_settings`.

The series is now complete: all technical feedback from v1 and v2 has been addressed, the public API is cleanly exposed, and the test coverage is thorough. The only remaining discussion point from v2—whether to add a test for wildcard pathspecs—is now resolved by the new trace2-based test. The patch looks ready for integration; the instrumentation is lightweight and non-intrusive, and the performance gains are well-documented.
