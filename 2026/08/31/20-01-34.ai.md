This is the final version (v6) of D. Ben Knoble’s three-patch series converting the build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`). The series is now technically complete and ready to graduate from the `dk/use-nsec-runtime` topic to `next`. The only change since v5 is a trivial cosmetic tweak requested by Patrick Steinhardt: replacing "defined" with "enabled" in a comment in `builtin/update-index.c` to better reflect the runtime nature of the new config key.

The core goal—allowing users to enable nanosecond precision on supported filesystems without recompiling Git—remains unchanged. The series addresses all prior technical concerns: the performance regression from v1 (~41× slowdown in `git diff` benchmarks) is resolved by caching the config value in `struct repo_config_values`, and the cross-platform correctness blocker (silent corruption risk when `core.useNanosec=true` is set on a `NO_NSEC` platform) is mitigated by unconditionally including the `use_nanosec` field but treating it as false when `NO_NSEC` is defined. The documentation now explicitly warns users about platform/filesystem limitations, and the architectural constraint introduced by the new call to `repo_config_values()` in `is_racy_stat()`—which limits future in-process submodule operations—is acknowledged but not blocking.

The first two patches are uncontroversial: the first fixes a Meson build-system issue (`MAN_BASE_URL` configuration), and the second refactors `repo_config_values_init()` for maintainability. The series touches 12 files, including `Documentation/config/core.adoc`, `environment.c`, and `read-cache.c`, and introduces the new `core.useNanosec` config key (defaults to false). A routine textual conflict exists with `ty/repo-config-cleanups` in `seen` (removes comments in `struct repo_config_values`), but resolution will be straightforward if both topics advance.

The author confirms the series is ready for `next`, and both Junio and Patrick Steinhardt have signed off on the technical approach. The only loose ends are platform-dependent test coverage (not blocking) and the forward-looking constraint on submodule support, which Patrick suggests could be addressed later by refactoring to `struct repo_settings` if needed. The series is based on master (2c78326f81) and carries forward the performance fix from v2 (21 ms vs 20 ms in benchmarks). No runtime warning will be emitted for `NO_NSEC` platforms, aligning with the project’s preference for shared-configuration compatibility.
