This is the final patch in the v9 series introducing the `--linearize` option to `git replay`. It implements the core feature: flattening merge commits into a linear history by dropping merges and replaying their commits sequentially.

The patch adds the `--linearize` flag to `git replay`, which ensures all replayed commits form a single linear chain. When a merge commit is encountered, its parents are replayed in order, but the merge itself is dropped. Refs pointing to merge commits are updated to the last replayed ancestor. The implementation enforces the v8 restriction that `--linearize` cannot be used with multiple branches or `--contained`, with updated error messages now using "branches" instead of "revision ranges" for clarity.

Key changes in this patch:
- The `replay_revisions()` function now skips merge commits when `--linearize` is active, leaving `last_commit` unchanged so subsequent commits are reparented onto the last non-merge commit.
- The commit base selection logic is updated to use `last_commit` when `--linearize` is active, ensuring a single linear history.
- Documentation and tests are expanded to cover the new behavior, including edge cases like replaying to the root commit, combining `--linearize` with `--revert`, and verifying the behavioral difference from `git rebase --no-rebase-merges`.
- Error messages and documentation now use "multiple branches" terminology, addressing feedback from Justin Tobler and Elijah Newren.

The patch touches `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, and `t/t3650-replay-basics.sh`.
