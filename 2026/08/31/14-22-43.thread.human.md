This thread reports a usability trap in Git’s branch name validation: porcelain commands (`checkout -b`, `switch -c`, `branch`) allow creating a branch named `@`, but this branch cannot later be checked out via the same commands because `@` is interpreted as `HEAD`. The inconsistency arises from `git check-ref-format --branch` accepting `@` as valid, while the general ref validation rejects it.

Bence Csókás identified the issue and provided clear reproduction steps. D. Ben Knoble confirmed the problem and framed it as a design question: should `--branch` mode enforce stricter validation to align with general ref rules? Jeff King (Peff) weighed in, clarifying that the current behavior is intentional for compatibility but agrees it’s a footgun. He suggests tightening `--branch` mode to reject bare `@` (following the precedent of blocking `HEAD` as a branch name) while allowing compound names like `foo@bar`. The discussion is now focused on a targeted fix to `check-ref-format --branch` in the ref validation logic.

No patch has been posted yet, but the technical direction is settled. The thread remains under review, with no objections to Peff’s proposed approach.
