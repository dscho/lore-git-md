This thread is about an inconsistency in Git’s branch name validation: porcelain commands like `git checkout -b` and `git switch -c` allow creating a branch named `@`, but this branch cannot later be checked out because `@` is interpreted as `HEAD`. The root cause is that `git check-ref-format --branch` incorrectly accepts `@` as a valid branch name, even though `git check-ref-format` (without `--branch`) rejects it.

The discussion has clarified that the current behavior is intentional for compatibility but creates a usability trap. The technical direction now favored by most participants is to tighten `--branch` validation to reject bare `@` while allowing compound names like `foo@bar`. This aligns with Junio C Hamano’s 2024 stance advocating deprecation of bare `@` as a synonym for `HEAD`. However, Bence Csókás has pushed back, arguing that `@` is a useful shorthand in complex expressions (e.g., `git range-diff long-branch-name{^..otherbranch,..@}`) and that removing it would harm usability. The thread is now split between stricter validation (to prevent user mistakes) and preserving `@` for convenience.

Key participants include Bence Csókás (who reported the issue and now advocates for preserving `@`), Jeff King (Peff) (who supports stricter validation while preserving compound names), D. Ben Knoble (who confirmed the inconsistency and highlighted the usability trap), and Kristoffer Haugsbakk (who cited Junio’s 2024 stance). No patch has been proposed yet, and the next step will likely be a patch addressing both the usability trap and the convenience argument. The discussion remains civil and focused, with no signs of escalation.
