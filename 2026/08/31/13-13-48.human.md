This is the second patch in the v9 series introducing `--linearize` to `git replay`. It refactors the replay machinery to resolve the replay base outside `pick_regular_commit()`, consolidating base-selection logic in one place for clarity and maintainability.

The patch moves the logic that determines where a commit should be replayed from `pick_regular_commit()` to its caller, `replay_revisions()`. Previously, `pick_regular_commit()` would decide the base by checking if the parent commit had already been replayed (using the `replayed_commits` map) or falling back to `onto` (or `last_commit` for `--revert`). Now, `replay_revisions()` handles this upfront, reducing `pick_regular_commit()`'s parameters from five to four and making the code easier to follow. The change is purely internal and introduces no behavior changes.

The commit message explains the motivation well: bundling base-selection logic in one place reduces confusion about where the replay base is determined. The helper functions `get_mapped_commit()` (introduced in patch 1/3) and `put_mapped_commit()` are used to maintain consistency in how replayed commits are tracked. The patch also clarifies the distinction between regular replay (where the base is either the replayed parent or `onto`) and revert replay (where the base is always `last_commit`).

This refactoring is a necessary preparatory step for the `--linearize` feature in patch 3/3, as it simplifies the logic for handling commit parents during replay. The patch is uncontroversial and has been stable since v5, with no substantive feedback in later iterations. It’s a clean, well-motivated change that improves the codebase’s structure without altering functionality.
