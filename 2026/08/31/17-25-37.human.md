This is the first patch in a seven-part bugfix/hardening series targeting the trace2 subsystem. It introduces `banned-die.h`, a new header that enforces compile-time bans on functions that can trigger `die()`—such as `die()` itself—in low-level APIs. The immediate goal is to prevent Git crashes caused by `die()`-handler recursion in trace2, which runs during `atexit()` and is particularly sensitive to abrupt termination.

The patch creates `banned-die.h` at the root of the tree, signaling intent for broader reuse beyond trace2, though its current scope is limited to the trace2 implementation files. Each trace2 `.c` file now includes this header last, ensuring it overrides any prior definitions of banned functions. The mechanism is simple: it undefines `die` and redefines it as `BANNED(die)`, which will trigger a compile error if used. While the commit message notes that `die()` was already unused in trace2, this patch lays the groundwork for banning other `die()`-triggering helpers (e.g., `xsnprintf()`, `xstrdup()`) in subsequent patches.

The motivation is clear: trace2 must not crash Git, even under memory pressure or system call failures. The series’ broader context (as noted in the thread summary) confirms this patch is part of a deliberate, incremental hardening effort. Jeff King’s earlier critique about the limitations of compile-time bans—particularly their inability to catch indirect `die()` calls via helpers like `strbuf`—remains unresolved, but this patch is framed as a necessary first step. The trade-off is pragmatic: it prevents regressions and provides a template for future hardening, even if it doesn’t fully solve the problem.

The patch itself is mechanical and well-scoped, touching only the trace2 subsystem and adding a single header. The include-ordering requirement (placing `banned-die.h` last) is documented in a local comment, addressing Elijah Newren’s prior concern about maintainability. No behavior changes are introduced yet, but the infrastructure is now in place for the rest of the series to replace banned functions with defensive fallbacks.

For a busy reader, this patch is worth noting as the foundation of a stability-focused effort. It’s uncontroversial on its own but sets the stage for more substantive changes in later patches. If you care about Git’s resilience or telemetry subsystems, this series is worth tracking.
