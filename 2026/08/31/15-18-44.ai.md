This is the fourth patch in Toon Claes’s v3 series optimizing `git last-modified` by reusing Bloom filters. It introduces `revs_maybe_changed_in_bloom_with_parents()`, a new public API in `revision.h` that checks whether *any* key in a path’s key vector (the path itself or any of its parent directories) is present in the Bloom filter. This is the missing piece that enables `--show-trees` to report changes to parent directories (e.g., for the pathspec `a/b/c/`, it checks `a/`, `a/b/`, and `a/b/c/`), avoiding false negatives when a commit only touched a file in a parent directory (e.g., `a/top`).

The implementation is straightforward: a 15-line helper in `revision.c` that loops over the key vectors and calls `bloom_filter_contains_any_vec()` (introduced in patch 3/6) to answer whether *any* key in the vector is present. The function returns `true` if the Bloom filter indicates a possible change to the path or any of its parent directories, and `false` only if the filter definitively rules out changes to all of them. The commit message explains the motivation clearly: `--show-trees` needs this logic to avoid missing commits that modified parent directories, and the new function is exactly what the subsequent patch (5/6) will use to pre-filter commits before running the per-path diff machinery.

The patch is well-motivated and technically sound. The new API is cleanly exposed, the implementation is minimal, and the commit message provides the necessary context about why this is needed for `--show-trees`. There are no callers yet, but the next patch will add one, completing the optimization. The naming (`with_parents`) is slightly misleading—it refers to parent directories, not commit parents—but this is a minor documentation issue that does not affect correctness. The patch is ready for integration.
