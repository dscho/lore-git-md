This is the third patch in Toon Claes’s six-patch series (v3) that speeds up the experimental `git last-modified` command by reusing Git’s Bloom filters. The patch adds a new helper, `bloom_filter_contains_any_vec()`, to the Bloom filter API. This helper answers a slightly different question than the existing `bloom_filter_contains_vec()`: instead of checking whether *every* key in a vector is present (meaning the path *might* have changed), it checks whether *any* key is present (meaning the path *or any of its parent directories* might have changed). The implementation is a simple loop over the key vector, returning as soon as any key hits.

The motivation is straightforward: when `git last-modified` queries a pathspec like `a/b/c`, the Bloom filter machinery already builds a key vector for `a/b/c`, `a/b`, and `a`. If the commit only touched `a/b/d`, the existing helper would report “no change” for `a/b/c` because not all keys are present, even though the parent directory `a/b` *did* change. The new helper lets callers detect that case, which is essential for correctness when `--show-trees` is used.

The patch is clean and minimal—twelve lines of code plus documentation. It has no callers yet; the next patch in the series will wire it up inside `git last-modified`. The commit message clearly explains the semantic difference and gives a concrete example, making the purpose obvious even without reading the rest of the series. There are no open questions or loose ends here; this is a well-motivated, uncontroversial plumbing addition.
