This is a CI/build system patch, part of an ongoing thread about canceling stale GitHub Actions workflow runs for pull requests. The author, Harald Nordgren, replies to Junio C Hamano’s tested review of v2, which identified a potential regression: the same commit pushed to a repository and later submitted as a pull request could now trigger two parallel workflow runs (one per event type), wasting CI resources.

Harald’s response is brief and technical: he clarifies that concurrency groups in GitHub Actions are scoped to individual repositories, so there is no way for the CI configuration to prevent duplicate runs when the same commit appears in both a user’s repository (triggering a `push` event) and a pull request (triggering a `pull_request` event). This confirms Junio’s suspicion that the scenario is unavoidable under the current design. The reply does not propose a workaround or suggest revisiting the patch, leaving the trade-off between pull-request cancellation and potential duplicate runs unresolved.

The thread now hinges on whether the project considers the risk of duplicate runs acceptable. Junio’s earlier review framed it as a low-probability edge case, and Harald’s reply reinforces that no technical fix exists without broader changes to GitHub Actions’ concurrency model. No other participants have weighed in on this specific point, so the decision likely rests with Junio or other maintainers assessing the practical impact. The patch itself remains well-motivated and narrowly scoped, but this final detail may delay merging until the project decides how much weight to give to a rare but real inefficiency.
