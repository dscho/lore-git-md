Subject: Inconsistent branch name validation in porcelain commands

Originating author: Bence Csókás

Core problem or goal
Git’s porcelain commands (`checkout -b`, `switch -c`, `branch`) allow creating a branch named `@`, even though `@` is rejected by `git check-ref-format` as an invalid ref name. The inconsistency stems from `git check-ref-format --branch` incorrectly accepting `@` as valid, creating a usability trap: the branch cannot be checked out afterward (due to `@` being interpreted as `HEAD`) but can be deleted. The discussion centers on whether the convenience of `@` as a shorthand for `HEAD` outweighs the risk of accidental branch creation.

Current status
Under review. No patch proposed yet. The thread remains split on the design trade-off: stricter validation (to prevent user mistakes) versus preserving `@` as a shorthand (for usability). The 2024 citation by Junio C Hamano advocating deprecation of bare `@` as a synonym for `HEAD` remains a key reference point, but Bence Csókás’s pushback introduces a countervailing argument grounded in real-world usage.

Key technical details
- Commands affected: `git checkout -b @`, `git switch -c @`, `git branch @`
- Validation discrepancy: `git check-ref-format` (without `--branch`) rejects `@`; `git check-ref-format --branch` accepts it
- On-disk consequence: branch ref `refs/heads/@` is created but cannot be checked out via porcelain commands (e.g., `git switch @` fails, interpreting `@` as `HEAD`)
- Subsystem: ref name validation logic in `refs.c` and `check-ref-format.c`
- Usability impact: manual manipulation of `.git/HEAD` is required to check out the branch; `@` remains useful as a shorthand in complex expressions (e.g., `git range-diff long-branch-name{^..otherbranch,..@}`)
- Design precedent: `--branch` mode already rejects `HEAD` as a branch name for porcelain safety; bare `@` could be treated similarly while preserving compound names like `foo@bar`
- Historical context: Junio C Hamano has previously argued (2024) for deprecating bare `@` as a synonym for `HEAD`, except in compound names

Open questions and loose ends
- Implementation: exact patch to tighten `--branch` validation for bare `@` (no patch proposed yet)
- Backwards compatibility: no known breakage expected if the change targets porcelain safety, but the convenience argument may delay or block the fix
- Design resolution: whether to prioritize safety (reject bare `@`) or convenience (preserve `@` as a shorthand)
