Subject: Inconsistent branch name validation in porcelain commands
Series version: N/A (bug report)
Originating author: Bence Csókás
Thread type: bug report / design discussion

Core problem or goal
Git’s porcelain commands (`checkout -b`, `switch -c`, `branch`) allow creating a branch named `@`, even though `@` is rejected by `git check-ref-format` as an invalid ref name. The inconsistency stems from `git check-ref-format --branch` incorrectly accepting `@` as valid, creating a usability trap: the branch cannot be checked out afterward (due to `@` being interpreted as `HEAD`) but can be deleted.

Current status
Under review. No prior versions or related patch series. The discussion has clarified that the current behavior is intentional for compatibility but should be tightened in the porcelain interface to prevent user mistakes. The technical direction is now clear: a targeted change to `check-ref-format --branch` to reject bare `@` while allowing other uses of `@` (e.g., `foo@bar`).

Key technical details
- Commands affected: `git checkout -b @`, `git switch -c @`, `git branch @`
- Validation discrepancy: `git check-ref-format` (without `--branch`) rejects `@`; `git check-ref-format --branch` accepts it
- On-disk consequence: branch ref `refs/heads/@` is created but cannot be checked out via porcelain commands (e.g., `git switch @` fails, interpreting `@` as `HEAD`)
- Subsystem: ref name validation logic in `refs.c` and `check-ref-format.c`
- Usability impact: manual manipulation of `.git/HEAD` is required to check out the branch
- Design precedent: `--branch` mode already rejects `HEAD` as a branch name for porcelain safety; bare `@` should be treated similarly
- Allowed cases: compound names like `foo@bar` should remain valid

Open questions and loose ends
- Implementation: exact patch to tighten `--branch` validation for bare `@` (no patch proposed yet)
- Backwards compatibility: no known breakage expected, as the change targets porcelain safety
