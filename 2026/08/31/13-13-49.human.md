This is the third and final patch in the v9 series introducing the `--linearize` option to `git replay`. The feature flattens merge commits into a linear history, matching the behavior of `git rebase --no-rebase-merges`. The patch is now **technically complete** and addresses all prior feedback, including the multi-branch ambiguity resolved in v8 and UX terminology refinements in v9.

The implementation adds the `--linearize` flag, which drops merge commits and replays their ancestors into a single linear chain. When a merge is encountered, the commit is skipped, and subsequent commits are reparented onto the last non-merge commit. The patch enforces a **single-branch restriction**: `--linearize` cannot be used with multiple revision ranges or `--contained`, as the current implementation cannot safely concatenate unrelated histories. Error messages and documentation now use "multiple branches" instead of "multiple revision ranges" for clarity, addressing feedback from Justin Tobler and Elijah Newren.

The patch touches `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, and `t/t3650-replay-basics.sh`. Key changes include:
- A new `linearize` field in `struct replay_revisions_options`.
- Logic in `replay_revisions()` to skip merge commits when `--linearize` is active and enforce the single-branch restriction.
- Updated documentation explaining the behavior and restrictions, including the intentional divergence from `git rebase --rebase-merges=<mode>`.
- Comprehensive test coverage for edge cases (e.g., replaying to the root commit, `--linearize` with `--revert`, and the multi-branch restriction).

The series is **ready for integration**, with Junio having removed the previous version from `next` and queuing v9 for review. The only remaining open question is whether `--linearize` should eventually support per-branch linearization (e.g., via `--ref` syntax), but this is deferred. The patch is well-motivated, thoroughly tested, and aligns with the project's goal of providing server-side rebase functionality. Potential trivial conflicts with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series are noted but unlikely to block progress.
