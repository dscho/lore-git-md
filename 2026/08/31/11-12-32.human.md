This is a CI/build system patch, part of an ongoing discussion about optimizing GitHub Actions workflows for pull requests. The author, Harald Nordgren, replies to Junio C Hamano’s tested review of v2, which raised a potential regression: the same commit pushed directly to a repository and later submitted as a pull request could now trigger duplicate workflow runs because the concurrency groups for `push` and `pull_request` events are now separate.

Harald’s response is brief and technical: concurrency groups in GitHub Actions are scoped to individual repositories, so there is no way to unify the groups across a user’s fork and the upstream repository. This means the duplicate-run scenario Junio described is indeed possible, but only if the user has CI enabled on their own fork *and* submits a pull request from the same branch. The commit message in v2 already noted this limitation, and Harald’s reply confirms it is a fundamental constraint of GitHub’s design, not something the patch can address.

The patch itself remains a clear improvement for the common case—canceling stale pull request workflows—while accepting a minor edge-case inefficiency. Junio’s review was substantive and tested, but his concern was framed as a low-risk trade-off rather than a blocker. With Harald’s clarification, the discussion now hinges on whether the project is comfortable merging a change that slightly increases CI resource usage in rare scenarios in exchange for a more responsive pull request workflow. No further technical objections are on the table.
