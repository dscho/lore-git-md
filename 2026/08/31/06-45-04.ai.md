This is the core implementation patch of Karthik Nayak’s `receive-report` hook series, now in its fourth iteration and queued in `seen`. Patrick Steinhardt’s review here is substantive, focusing on two documentation ambiguities and one technical design question in the hook’s failure-handling logic.

The first documentation nit is a grammatical fix in `git-receive-pack.adoc`: the phrase “Allowing the hook to rewrite” becomes “, which allows the hook to rewrite” for smoother flow. The second is a missing optional marker in `githooks.adoc`: `ng <refname> <reason>` should read `ng <refname>[ <reason>]` to match the protocol spec.

The substantive point is whether the hook can also update the “unpack” status line. The current text lists only two ways the hook can affect the push outcome (rewrite individual refs or abort the entire push), but the protocol allows a third: the hook can change the initial `unpack ok` or `unpack <error>` line. Patrick asks whether this should be documented as a third option.

The technical question concerns the new `ref_error` parameter in `generate_response()`. When the hook exits non-zero, the code currently adds a new `ng` line for every ref, but it leaves any existing `cmd->error_string` untouched. Patrick notes that this creates odd precedence: an explicit per-ref error is preserved even when the hook wants to signal a global failure. He wonders whether it would be cleaner to overwrite all `cmd->error_string` fields instead of introducing a separate parameter. The question is left open; no code change is suggested yet.
