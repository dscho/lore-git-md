This is the fourth patch in Toon Claes’s six-patch v3 series that speeds up the experimental `git last-modified` command by reusing Git’s Bloom filters. The patch introduces `revs_maybe_changed_in_bloom_with_parents()`, a new public helper in `revision.h` that answers a slightly different question than the existing `revs_maybe_changed_in_bloom()`: instead of asking “did this commit touch any of the exact paths in the pathspec?” it asks “did this commit touch any of the paths *or any of their parent directories*?”  The difference is exactly what `--show-trees` needs to avoid false negatives when a commit only modified a file inside a directory that was itself unchanged.

The implementation is straightforward: the new function loops over the same key vectors that the old one did, but it calls `bloom_filter_contains_any_vec()` instead of `bloom_filter_contains_vec()`.  That helper (added in patch 3/6) returns true if *any* key in the vector is present in the Bloom filter, so it catches changes to parent directories as well as to the path itself.  The patch is purely additive—no existing code is touched—and the commit message clearly explains the motivation and the intended caller (`git last-modified --show-trees`).  The function is already documented in the header with a concise comment that spells out the difference from the existing API.

This is a clean, well-motivated refactoring that plugs the last technical gap identified in the v1 review.  The only thing left is the actual wiring-up in `builtin/last-modified.c`, which comes in patch 5/6.
