This is the final patch (5/5) in Patrick Steinhardt’s v2 series refactoring how the object database (ODB) subsystem handles corrupt objects when `OBJECT_INFO_DIE_IF_CORRUPT` is used. The patch makes the error-handling fully generic and backend-agnostic by removing the last abstraction-breaking code (`has_packed_and_bad()`) and teaching `do_oid_object_info_extended()` to track corruption status and accumulate error messages from all ODB backends.

Key changes in this patch:
- **Removes `has_packed_and_bad()`** (and its declaration in `packfile.h`), eliminating the direct dependency on the "files" backend’s internals. This function previously checked whether an object was known to be corrupt in any packfile, but its implementation assumed the ODB used the "files" backend, breaking abstraction.
- **Makes `OBJECT_INFO_DIE_IF_CORRUPT` generic**: `do_oid_object_info_extended()` now tracks corruption status (`corrupt` boolean) and accumulates error messages from all backends via the `errmsg` parameter introduced in earlier patches. When the flag is set, it dies with the first available error message (or a generic one if no backend provided a message).
- **Removes the loose backend’s direct `die()` call**: The loose backend’s `read_object_info_from_path()` no longer dies unconditionally on corruption, allowing other backends (e.g., alternates) to provide a good copy. Instead, it populates the `errmsg` parameter, and the ODB layer decides whether to die.
- **Updates test coverage**: Adds a test case (`t1060-object-corruption.sh`) verifying that a corrupted loose commit can still be read from an alternate repository, demonstrating the new backend-agnostic behavior.

The patch is a clean culmination of the series’ goals: consistent error reporting, backend-agnostic handling of corrupt objects, and removal of abstraction leaks. The changes are internal to the ODB subsystem and do not affect user-facing behavior or on-disk formats. The series as a whole is now ready for integration, pending any further discussion on the `bad_pack` granularity question noted in earlier patches. The refactoring is well-motivated, thoroughly tested, and addresses all prior feedback.
