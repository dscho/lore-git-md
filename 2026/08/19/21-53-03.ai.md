This is the first patch in Justin Tobler’s v4 series completing the ODB abstraction for `git receive-pack`. It fixes a regression introduced in bdee7b3013 (July 2026) where `.keep` files—used to prevent incoming packfiles from being pruned before refs are updated—were not being properly cleaned up after the ODB transaction committed. The root cause was that `index_pack_lockfile()` derived the `.keep` file path from the repository’s primary object directory, but the ODB transaction reordered the sources list so that the quarantine directory became the primary source. As a result, the `.keep` file was written to the quarantine directory and then migrated to the main ODB, but the cleanup path still pointed to the quarantine directory, leaving the `.keep` file orphaned.

The patch updates `index_pack_lockfile()` to accept an explicit `struct odb_source *` parameter instead of a `struct repository *`, allowing callers to specify which ODB source should be used to derive the `.keep` file path. In `builtin/receive-pack.c`, the transaction’s source (the quarantine directory) is passed to `index_pack_lockfile()`, but the returned path is the *final* location in the main ODB, ensuring the `.keep` file can be found and removed after the transaction commits. The `fetch-pack.c` call site is updated to use the repository’s primary source list (not the quarantine directory) for consistency. A new test in `t/t5547-push-quarantine.sh` verifies that the `.keep` file is generated in the quarantine directory during the transaction and removed from the main ODB after the push completes.

The change is minimal and targeted: it preserves the existing `.keep` file semantics while fixing the cleanup regression. The new test provides clear coverage for the race-avoidance property that `.keep` files are meant to enforce. This patch is a prerequisite for the rest of the series, which replaces `git receive-pack`’s hardcoded use of `git index-pack` with a backend-agnostic ODB transaction interface. The fix aligns with the broader ODB abstraction effort led by Patrick Steinhardt and addresses the lockfile lifecycle flaw identified in earlier reviews. No user-visible behavior changes are introduced.
