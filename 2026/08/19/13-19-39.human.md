This is the final patch in Karthik Nayak's three-part series optimizing stack reloads in the reftable backend. It delivers the core performance improvement by avoiding redundant stack reloads when the stack is already locked during transactions.

The patch modifies `reftable/stack.c` to add a `skip_if_locked` parameter to `stack_uptodate()`, allowing the function to skip reloads when the stack's list lock is held. This change reduces `newfstatat()` syscalls from linear growth (one per ref) to a constant ~55 calls regardless of ref count, while maintaining safety by always reloading immediately after acquiring the lock. Benchmarks show consistent 1-2% clock time improvements in `git update-ref` operations across ref counts from 2,000 to 100,000.

The implementation is clean and targeted, building directly on the lock state relocation introduced in patch 2. The commit message clearly explains the trade-off between performance and safety, and the benchmark data (originally from Jeff King's profiling) provides solid motivation. This looks like a well-crafted optimization that addresses a real bottleneck without introducing complexity or risk.
