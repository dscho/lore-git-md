This is the **author's response** to Patrick Steinhardt's **substantive review** of the final patch in the `dk/use-nsec-runtime` series (v3 3/3). The series replaces the build-time `USE_NSEC` macro with the runtime `core.useNanosec` config option and is cooking in `next` under the topic `dk/use-nsec-runtime`.

D. Ben Knoble **accepts all of Patrick's suggestions** and confirms they will be incorporated into the next revision. Specifically:
- The documentation for `core.useNanosec` will include a warning about platform/filesystem limitations (e.g., "may not be safe on all platforms").
- The `use_nanosec` field in `struct repo_config_values` will be unconditionally initialized to `0` in `repo_config_values_init()`, resolving the uninitialized-read concern.
- The `#ifndef NO_NSEC` guards in `is_racy_stat()` will be simplified to a single ternary expression for readability, as previously agreed with Junio.
- The missed reference to `USE_NSEC` in `builtin/update-index.c` will be updated (though the author notes they only found a comment referencing `USE_NSEC` in that file, not executable code).

The response also clarifies the **documentation linking convention**: Git's man pages frequently link to HTML documentation (e.g., `technical/racy-git.html`) because not all technical documents have man-page equivalents. The author argues this is the established style, citing examples from other config keys and noting that tools like `git --html-path` provide a way to access these documents. No changes to the linking approach are planned.

The author **declines to add a runtime warning** for `NO_NSEC` builds where `core.useNanosec=true` is set, reasoning that such a warning could be obnoxious and that better documentation is sufficient for now. This aligns with the series' design, which already `#ifdef`s out the `use_nanosec` field and related code paths in `NO_NSEC` builds to prevent silent corruption.

The response does not revisit the **architectural question** of where to cache `core.useNanosec` (`repo_config_values`, `repo_settings`, or a global variable), as this was not part of Patrick's review. The series remains on track for graduation to `master` once the agreed-upon polish items are addressed. The **textual conflict** with `ty/repo-config-cleanups` in `seen` will need resolution if both topics advance.
