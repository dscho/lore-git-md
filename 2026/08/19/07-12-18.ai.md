This is a Google Summer of Code (GSoC) progress update from Siddharth Shrimali on his project to improve disk space recovery for partial clones. The email links to his week 11 and 12 blog posts, continuing the work on the `gc-promisor` maintenance task introduced earlier in the summer.

The latest updates refine the design and implementation of the `gc-promisor` task, which aims to safely prune unneeded promisor objects in partial clones without breaking future fetches. Key advancements include finalizing the per-remote `.keep`-file safety mechanism, which now includes timestamps to enforce the grace period (default 30 days) and remote-specific markers to prevent cross-remote data loss. The task’s integration with the `git maintenance` scheduler is now stable, with `gc-promisor` running *after* `gc` to avoid interfering with pack consolidation. Performance testing has expanded to include repositories with up to 15 remotes and promisor packs exceeding 1 GB, with results showing fetch latency increases of less than 5% post-prune. Edge-case evaluation has progressed, though shallow clones, grafted history, and alternate object directories remain under scrutiny.

New technical details include the addition of a `--dry-run` flag to `git maintenance run --task=gc-promisor`, allowing users to preview which objects would be pruned without actually removing them. The grace period is now fully configurable via both CLI (`--grace-period=<days>`) and config (`maintenance.gcPromisor.gracePeriod`), with the CLI flag taking precedence over config settings. The test suite (`t/t5329-partial-clone-prune.sh`) has grown to cover dry-run functionality, multi-remote scenarios, and performance benchmarks. The on-disk format remains backward-compatible, with `.keep` files now storing remote-specific metadata and timestamps to support grace-period enforcement.

Open questions remain around the sufficiency of the `.keep`-file mechanism for recovery in all scenarios (e.g., whether a dedicated recovery log is needed) and whether additional configurability (e.g., per-remote grace periods or prune aggressiveness) should be exposed. The author also notes that performance testing for repositories with more than 15 remotes is still pending. Feedback is explicitly invited on these points, as well as on the overall safety and usability of the design.

No formal patch series has been posted yet, but the work continues to touch `promisor-remote.c`, `builtin/gc.c`, `builtin/maintenance.c`, and `packfile.c`, with new symbols like `cmd_maintenance__gc_promisor()` and the `--dry-run` flag. The project builds on prior GSoC efforts and the existing `git maintenance` machinery, targeting improved usability for partial clones. The thread remains an invitation for wider review, with Christian Couder (the GSoC mentor) and other Git contributors yet to weigh in.
