This is a bugfix patch updating the exit code behavior of `git config -e` when the editor fails. This is the second iteration of a standalone patch that surfaced in an RFC thread earlier this month.

The patch itself is unchanged: it still modifies `show_editor()` in `builtin/config.c` to return the error code from `launch_editor()` instead of always returning 0, so that `git config -e` now exits non-zero if the editor fails. What has changed are the tests—Kenneth has simplified them by replacing manual `GIT_EDITOR` export/unset with `test_env`, and renamed the test cases from `--edit` to `-e` to match the actual command being tested. The test logic remains the same: one test verifies exit code 0 when the editor succeeds (`GIT_EDITOR=true`), and the other verifies exit code 1 when the editor fails (`GIT_EDITOR=false`).

The patch is small, well-tested, and addresses a real inconsistency: other Git commands like `git commit` already propagate editor failures, so this change brings `git config -e` into alignment. The risk of breaking scripts is low—the feature was only introduced mid-2024, so few scripts are likely to rely on the current behavior. The thread’s core question—whether the benefit of consistency outweighs the risk of breakage—remains unresolved, but the patch itself is ready for review. If you care about error handling in Git’s interactive commands, this is worth a look.
