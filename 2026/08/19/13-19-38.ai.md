This is the second patch in Karthik Nayak's three-part series optimizing reftable stack reloads during transactions. It moves the list lock from `struct reftable_addition` into `struct reftable_stack`, enabling future optimizations (realized in patch 3) that avoid redundant stack reloads when the stack is already locked.

The change is mechanical: the `reftable_flock` field is relocated from `reftable_addition` to `reftable_stack`, and all references in `reftable/stack.c` are updated to point to the new location. The patch also removes an unused `#include "reftable-writer.h"` from `reftable/stack.h`. The lock state is now initialized in `reftable_new_stack()` and released in `reftable_addition_close()`, mirroring the previous behavior but making the lock state accessible to the stack itself.

This refactoring is a prerequisite for patch 3, which will use the lock state to skip unnecessary stack reloads during transactions. The commit message explains that while the write path could previously access the lock state, read paths operating on `struct reftable_stack` could not, limiting optimization opportunities. No behavior changes are introduced yet; the patch is purely preparatory.

Files modified: `reftable/stack.c` and `reftable/stack.h`. The diff is straightforward, with no new symbols introduced. The series remains focused on the reftable backend's transaction performance, building on Jeff King's profiling data showing excessive `fstat()` calls during bulk ref operations.
