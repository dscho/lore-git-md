Subject: `git stash` non-atomic failure and unhelpful error messages
Series version: N/A (bug report, not a patch series)
Originating author: Yuri <yuri@rawbw.com>
Thread type: bug report

Core problem or goal
`git stash push` fails non-atomically when handling large (2 GB) untracked files, leaving behind invalid stash entries and the original file changes. Two distinct failure modes are reported: (1) "unable to generate diff" during the initial attempt, and (2) "patch too large" on subsequent attempts, both with uninformative error messages that do not specify the actual size limit (1 GB). The goal is to prompt discussion or future fixes to make `git stash` operations atomic (no partial state on failure) and to improve error messages with actionable details (e.g., stating the 1 GB limit).

Current status
Under discussion; no patches or decisions yet. The report includes concrete reproduction steps and highlights that the leftover stash entry is invalid due to missing files.

Key technical details
- **Command**: `git stash push`
- **Failure modes**:
  - Diff generation failure for large untracked files ("unable to generate diff").
  - Patch size limit exceeded ("patch too large"), with an implicit 1 GB limit.
- **Subsystems touched**: stash internals, diff generation, patch application.
- **Behavioral issue**: Non-atomic failure leaves partial state (invalid stash entry + original changes).
- **Error message issue**: Lacks specific limits (e.g., "1 GB") or guidance.
- **Test coverage**: None mentioned; reproduction steps provided in the report.

Open questions and loose ends
1. Should `git stash` operations be made atomic (rollback on failure)?
2. Should error messages explicitly state size limits (e.g., "patch too large (limit: 1 GB)")?
3. Are there other edge cases where `git stash` fails non-atomically?
4. Is the 1 GB limit documented elsewhere, and if not, should it be?
