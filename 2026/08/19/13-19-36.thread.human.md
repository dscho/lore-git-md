This thread is about a three-patch series from Karthik Nayak that optimizes the reftable backend by eliminating redundant stack reloads during reference transactions. The series targets a performance bottleneck where excessive `fstat()` calls were slowing down bulk ref creation, with independent benchmarks showing a consistent 25% speedup.

The first patch simplifies the API by removing a redundant flag and making stack reloading the default behavior, while the third patch implements the core optimization by reducing `newfstatat()` syscalls from linear to constant time. Both are uncontroversial and ready to proceed. The second patch, which relocates a lock from `reftable_addition` to `reftable_stack`, was the sticking point—Junio C Hamano raised a safety concern about premature lock release when multiple `reftable_addition` instances operate on the same stack. Karthik has now proposed a fix that tracks lock ownership per instance, resolving the issue in principle, though the implementation details remain open for discussion. Justin Tobler and Jeff King have reviewed the series favorably, with Justin offering an alternative design suggestion for patch 3 that avoids changing a function signature. Patrick Steinhardt’s feedback was limited to a cosmetic naming suggestion for patch 1.

The series is now effectively unblocked, pending finalization of the lock-tracking mechanism in patch 2. Once that’s settled, the path to merging looks clear. Karthik has also offered to update libgit2 for compatibility once the changes land in Git.
