This thread is about Karthik Nayak’s three-patch series optimizing reftable stack reloads during reference transactions, aiming to eliminate redundant `fstat()` calls that scale poorly with ref count. The series is under active review, with v1 posted and no prior versions.

The first two patches have seen substantive feedback. Justin Tobler reviewed all three patches, confirming the mechanical correctness of patch 1 (which removes a redundant reload flag) and endorsing patch 2’s lock relocation as conceptually sound. However, Junio C Hamano’s recent review of patch 2 raises a safety concern: moving the list lock from `reftable_addition` to `reftable_stack` could allow a caller to prematurely release the lock if multiple `reftable_addition` instances operate on the same stack concurrently. This might leave other operations in an inconsistent state, a regression from the current per-addition lock design. The question is whether the API needs additional safeguards, such as reference counting or explicit error handling for nested additions.

Patch 3, the core optimization, is ready for iteration based on Justin’s feedback, which suggests an alternative approach to avoid changing the `stack_uptodate()` function signature. The series touches `refs/reftable-backend.c` and the reftable library, with no on-disk format changes, and includes updated unit tests. Performance benchmarks show a 1-2% clock time improvement in `git-update-ref` operations. Key participants include Karthik (author), Jeff King (who identified the bottleneck), Justin Tobler (substantive reviewer), and now Junio (maintainer). The open question is whether patch 2’s lock relocation introduces a safety risk that needs mitigation.
