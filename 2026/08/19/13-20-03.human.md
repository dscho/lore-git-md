This is a **feature patch** introducing the `report` hook for `git-receive-pack`, allowing server administrators to intercept and modify the status report sent to clients after ref updates. The patch remains under active review, with the latest exchange between Karthik Nayak and Patrick Steinhardt clarifying design intent but leaving a key ambiguity unresolved.

The hook fills a timing gap in Git’s existing hook infrastructure: it runs *after* all ref updates are committed but *before* the status report is sent to the client, enabling use cases like GitLab’s MVCC (multi-version concurrency control) system. The hook receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status currently causes `receive-pack` to die, discarding the hook’s stdout—a behavior both Junio C Hamano and Patrick Steinhardt find surprising and potentially problematic.

Patrick’s latest reply reaffirms his position that the hook should *always* return zero to ensure the client receives a well-formed status report, even when rejecting ref updates. He acknowledges the non-zero exit code could serve as a "nuclear option" for catastrophic failures but does not endorse it as a normal rejection mechanism. Karthik has previously indicated openness to revising the implementation to ignore the exit code entirely, but no concrete change has been posted yet. This design ambiguity remains the primary obstacle to merging.

The patch is well-motivated and addresses a real need, with clear test coverage for passthrough behavior, failure modes, and sideband relay. Documentation improvements (e.g., clarifying stderr forwarding behavior, dropping the word "remote" from the hook description) are planned but not yet implemented. The unresolved exit status question is the most likely source of further discussion—administrators may expect the hook’s output to be honored regardless of exit status, and the current behavior could lead to unexpected client-side failures. If this is resolved, the patch looks ready for `next`.
