This is the final patch in Karthik Nayak's three-part series optimizing reftable stack reloads during transactions. It implements the core optimization: skipping redundant stack reloads when the stack is already locked.

The patch modifies `reftable/stack.c` to add a `skip_if_locked` parameter to `stack_uptodate()`, allowing the function to return early (indicating the stack is up-to-date) if the stack is locked and reloads should be skipped. The key change is in `reftable_stack_reload()`, which now passes `1` to skip reloads when the stack is locked, while other callers (like `reftable_stack_init_addition()` and `stack_compact_range()`) pass `0` to ensure reloads happen immediately after acquiring the lock.

This is a targeted performance optimization that reduces `newfstatat()` syscalls from linear growth (O(n) with ref count) to a constant ~55 calls, regardless of ref count. The clock-time improvement is modest (~1-2% in `git-update-ref` benchmarks) but consistent across ref counts from 2,000 to 100,000. The patch builds on the earlier refactoring in patches 1 and 2, which removed a redundant flag and relocated the lock state to the `reftable_stack` structure.

The implementation is mechanical and well-scoped, focusing on eliminating redundant operations without changing the reftable on-disk format or introducing new behavior. The commit message clearly explains the motivation (preventing data loss from concurrent writes while avoiding unnecessary reloads) and provides concrete benchmark data. The test coverage in `t/unit-tests/u-reftable-stack.c` (updated in earlier patches) suggests the new locking logic is thoroughly validated.

This patch completes the series and appears ready for review. The optimization is motivated by Jeff King's profiling data and addresses a real bottleneck in the reftable backend's handling of reference transactions. The changes are confined to the reftable subsystem and do not affect other parts of Git.
