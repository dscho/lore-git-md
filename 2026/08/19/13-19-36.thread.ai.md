Subject: [PATCH 0/3] reftable: optimize stack reloads during transactions
Series version: v1 (initial submission)
Originating author: Karthik Nayak
Thread type: patch series

Core problem or goal
Eliminate redundant stack reloads in the reftable backend during reference transactions, addressing a performance bottleneck where excessive `fstat()` calls (scaling linearly with ref count) were consuming significant time during bulk ref creation.

Current status
Under review; v1 posted. No prior versions. No merge status reported.

Key technical details
- Files touched: `refs/reftable-backend.c`, `reftable/stack.h`, `reftable/stack.c`, `t/unit-tests/u-reftable-stack.c`
- New symbols: none; refactoring of existing `reftable_stack` and `reftable_addition` structures to include lock state in the stack (patch 2) and optimize reload logic (patch 3)
- Behavior change: stack reloads now default in `reftable_stack_init_addition()` (patch 1); patch 2 relocates the list lock from `reftable_addition` to `reftable_stack` to enable future optimizations; patch 3 (not yet summarized) will use the lock state to skip reloads when the stack is already locked during a transaction
- Performance impact: 1-2% clock time improvement in `git-update-ref` benchmarks; `newfstatat()` syscalls reduced from linear growth to constant ~55 calls regardless of ref count (demonstrated in cover letter)
- On-disk format: unchanged

Open questions and loose ends
None raised yet; series appears self-contained and ready for review.

Participant positions
- Karthik Nayak (author): presents the series as a targeted, mechanical optimization motivated by Jeff King's profiling data. Patch 1 removes the `REFTABLE_STACK_NEW_ADDITION_RELOAD` flag (redundant since 16684b6fae, 2025-08-12) and simplifies the API by making stack reloading the default behavior. Patch 2 relocates the list lock from `reftable_addition` to `reftable_stack` to enable future optimizations (patch 3), with no behavior changes introduced yet. All callers already ensured reloading when needed, so the flag's removal is a cleanup with no functional regression.
- Jeff King (Peff): identified the bottleneck (excessive `fstat()` calls during bulk ref creation) that motivates this series; no review comments yet.
