Thread identity
Subject: [PATCH 0/3] reftable: optimize stack reloads during transactions
Series version: v2 (expands v1 to four patches)
Originating author: Karthik Nayak
Thread type: patch series

Core problem or goal
Eliminate redundant stack reloads in the reftable backend during reference transactions, addressing a performance bottleneck where excessive `fstat()` calls (scaling linearly with ref count) were consuming significant time during bulk ref creation.

Current status
Under review; v2 posted. Changes from v1: added a `locked` bit field to `struct reftable_addition` to track lock acquisition per instance, preventing premature lock release when multiple additions operate on the same stack (resolving Junio C Hamano's safety concern); renamed `reftable_stack_new_addition()` to `reftable_stack_addition_new()` for naming consistency (addressing Patrick Steinhardt's cosmetic feedback); updated commit messages to reflect benchmark results showing a consistent 15-20% performance improvement (up from the 1-2% reported in v1), with the discrepancy attributed to test methodology differences (`refs/tags/*` vs `refs/heads/*`).

Key technical details
- Files touched: `refs/reftable-backend.c`, `reftable/stack.h`, `reftable/stack.c`, `t/unit-tests/u-reftable-stack.c`
- New symbols: `locked` bit field in `struct reftable_addition`
- Behavior change: stack reloads now default in `reftable_stack_addition_new()` (formerly `reftable_stack_new_addition()`); patch 2 (new in v2) adds per-addition lock tracking to prevent premature lock release when multiple `reftable_addition` instances operate on the same stack; patch 3 (formerly patch 2 in v1) relocates the list lock from `reftable_addition` to `reftable_stack` to enable future optimizations; patch 4 (formerly patch 3 in v1) reduces `newfstatat()` syscalls from O(n) to ~55 constant calls regardless of ref count by skipping redundant reloads when the stack is locked during a transaction, with the lock-checking logic embedded in `stack_uptodate()` to enforce consistent application and prevent caller error
- Performance impact: independent measurements by Jeff King show a consistent 25% speedup across ref counts from 10,000 to 50,000; v2 benchmarks report a 15-20% improvement, with the discrepancy from the original 1-2% definitively attributed to test methodology (`refs/tags/*` triggers an extra stack reload due to reflog creation, whereas `refs/heads/*` shortcuts it)
- On-disk format: unchanged
- Test coverage: updated unit tests in `t/unit-tests/u-reftable-stack.c` validate the new locking logic, per-addition lock tracking, and performance optimization
- External compatibility: libgit2 (separate project) uses the `REFTABLE_STACK_NEW_ADDITION_RELOAD` flag removed in patch 1, but all libgit2 call sites already pass it, so the change is compatible with minimal adaptation. Karthik Nayak has offered to send a pull request to libgit2 once the patch lands in Git.

Open questions and loose ends
Patch 1 (flag removal and API simplification) and patch 2 (cosmetic rename) are fully resolved. Patch 3 (lock relocation and per-addition lock tracking) resolves Junio C Hamano's safety concern in principle, but the implementation detail of whether to embed the lock-checking logic in `stack_uptodate()` or expose it to callers remains open; Karthik's argument for encapsulation (reducing caller error risk) is persuasive, but Justin Tobler's alternative (preserving the existing signature) is technically viable and has not been formally withdrawn. No new objections or requests for changes have been raised in v2.
