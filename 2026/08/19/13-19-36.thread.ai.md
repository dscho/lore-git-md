Thread identity
Subject: [PATCH 0/3] reftable: optimize stack reloads during transactions
Series version: v1 (initial submission)
Originating author: Karthik Nayak
Thread type: patch series

Core problem or goal
Eliminate redundant stack reloads in the reftable backend during reference transactions, addressing a performance bottleneck where excessive `fstat()` calls (scaling linearly with ref count) were consuming significant time during bulk ref creation.

Current status
Under review; v1 posted. No prior versions. No merge status reported.

Key technical details
- Files touched: `refs/reftable-backend.c`, `reftable/stack.h`, `reftable/stack.c`, `t/unit-tests/u-reftable-stack.c`
- New symbols: none (alternative approach avoids the previously proposed `skip_if_locked` parameter for `stack_uptodate()`)
- Behavior change: stack reloads now default in `reftable_stack_init_addition()` (patch 1); patch 2 relocates the list lock from `reftable_addition` to `reftable_stack` to enable future optimizations, with each `reftable_addition` now tracking whether it acquired the lock to prevent premature release; patch 3 reduces `newfstatat()` syscalls from O(n) to ~55 constant calls regardless of ref count by skipping redundant reloads when the stack is locked during a transaction
- Performance impact: originally reported as 1-2% clock time improvement in `git-update-ref` benchmarks; Jeff King's independent measurements show a consistent 25% speedup across ref counts from 10,000 to 50,000, with the discrepancy attributed to differences in test methodology (Peff used `hyperfine` on fresh repository copies for each run)
- On-disk format: unchanged
- Test coverage: updated unit tests in `t/unit-tests/u-reftable-stack.c` validate the new locking logic and per-addition lock tracking
- External compatibility: libgit2 (separate project) uses the `REFTABLE_STACK_NEW_ADDITION_RELOAD` flag being removed in patch 1, but all libgit2 call sites already pass it, so the change is compatible with minimal adaptation. Karthik Nayak has offered to send a pull request to libgit2 once the patch lands in Git.

Open questions and loose ends
Patch 1 is fully resolved on substance; the only remaining feedback is Patrick Steinhardt’s cosmetic suggestion to rename `reftable_stack_new_addition()` to `reftable_stack_addition_new()` for naming consistency, which Karthik has agreed to address in a separate commit if desired. Patch 2’s safety concern about premature lock release when multiple `reftable_addition` instances operate on the same stack is now resolved in principle by per-addition lock tracking, but the implementation detail (adding a tracking bit to `struct reftable_addition`) remains open for discussion. Patch 3’s design is uncontroversial, but Justin Tobler’s alternative proposal to avoid changing the `stack_uptodate()` function signature remains unaddressed; this is a design preference rather than a correctness issue.

Participant positions
- Karthik Nayak (author): presents the series as a targeted, mechanical optimization motivated by Jeff King's profiling data. Patch 1 removes the `REFTABLE_STACK_NEW_ADDITION_RELOAD` flag (redundant since 16684b6fae, 2025-08-12) and simplifies the API by making stack reloading the default behavior. The manual reload in `reftable_stack_clean_locked()` is confirmed as an artifact of incremental flag adoption, not a functional requirement. Patch 2 relocates the list lock from `reftable_addition` to `reftable_stack` to enable the optimization in patch 3, with each `reftable_addition` now tracking whether it acquired the lock to prevent premature release. All callers already ensured reloading when needed, so the flag's removal is a cleanup with no functional regression. The final patch completes the series by implementing the core optimization, with benchmark data showing consistent performance gains across ref counts from 2,000 to 100,000. Karthik has agreed to address Patrick Steinhardt’s cosmetic naming suggestion with a separate commit and has offered to send a pull request to libgit2 for compatibility.
- Jeff King (Peff): identified the bottleneck (excessive `fstat()` calls during bulk ref creation) that motivates this series; provides independent benchmark results showing a 25% speedup across ref counts from 10,000 to 50,000, reinforcing the optimization’s effectiveness and robustness across workloads. No review comments on design or implementation; feedback is purely empirical and supportive.
- Justin Tobler: substantive reviews of all three patches, engaging with the patches’ logic and edge cases. Confirms the mechanical correctness of the unconditional reload flow in patch 1, verifies that `REFTABLE_OUTDATED_ERROR` checks are redundant, and resolves his initial question about `reftable_stack_clean_locked()` as a non-issue. For patch 2, he endorses the lock relocation as conceptually sound, noting that the lock is inherently singular for a reftable stack and that `struct reftable_stack` is the more logical home for the field. For patch 3, he proposes an alternative approach to avoid changing the `stack_uptodate()` function signature by skipping the call entirely when the stack is locked. No objections to the series’ goals or design; feedback is focused on implementation details.
- Junio C Hamano: substantive review of patch 2, raising a safety concern about the lock relocation’s implications for concurrent or nested `reftable_addition` instances on the same stack. The shared lock could be prematurely released when a second instance closes, potentially disrupting other operations. The concern is now resolved in principle by Karthik’s proposal to track lock acquisition per `reftable_addition`; Junio has not yet responded to this resolution.
- Patrick Steinhardt: surface-level review of patch 1, noting that libgit2 (a separate project) uses the flag being removed but confirming that all libgit2 call sites already pass it, so the change is compatible. Suggests a cosmetic function rename from `reftable_stack_new_addition()` to `reftable_stack_addition_new()` for naming consistency. No objection to the patch’s substance; feedback is narrowly scoped to API aesthetics and external compatibility. Karthik has agreed to handle the rename in a separate commit if desired.
