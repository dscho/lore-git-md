Thread identity
Subject: [PATCH 0/3] reftable: optimize stack reloads during transactions
Series version: v1 (initial submission)
Originating author: Karthik Nayak
Thread type: patch series

Core problem or goal
Eliminate redundant stack reloads in the reftable backend during reference transactions, addressing a performance bottleneck where excessive `fstat()` calls (scaling linearly with ref count) were consuming significant time during bulk ref creation.

Current status
Under review; v1 posted. No prior versions. No merge status reported.

Key technical details
- Files touched: `refs/reftable-backend.c`, `reftable/stack.h`, `reftable/stack.c`, `t/unit-tests/u-reftable-stack.c`
- New symbols: `skip_if_locked` parameter proposed for `stack_uptodate()` in `reftable/stack.c` (alternative approach suggested by Justin Tobler avoids this change)
- Behavior change: stack reloads now default in `reftable_stack_init_addition()` (patch 1); patch 2 relocates the list lock from `reftable_addition` to `reftable_stack` to enable future optimizations, but Junio C Hamano raises a safety concern about premature lock release if multiple `reftable_addition` instances operate on the same stack; patch 3 reduces `newfstatat()` syscalls from O(n) to ~55 constant calls regardless of ref count by skipping redundant reloads when the stack is locked during a transaction
- Performance impact: 1-2% clock time improvement in `git-update-ref` benchmarks
- On-disk format: unchanged
- Test coverage: updated unit tests in `t/unit-tests/u-reftable-stack.c` validate the new locking logic
- External compatibility: libgit2 (separate project) uses the `REFTABLE_STACK_NEW_ADDITION_RELOAD` flag being removed in patch 1, but all libgit2 call sites already pass it, so the change is compatible with minimal adaptation

Open questions and loose ends
Justin Tobler’s review of patch 1 raised targeted questions about the removal of the `REFTABLE_STACK_NEW_ADDITION_RELOAD` flag: he confirmed the mechanical correctness of the unconditional reload flow, probed the historical need for a manual reload in `reftable_stack_clean_locked()` (resolved as a non-issue), and verified that `REFTABLE_OUTDATED_ERROR` checks are now redundant. His review of patch 2 endorses the lock relocation as conceptually sound and unblocking for the optimization in patch 3, but Junio C Hamano now highlights a potential regression in API safety: if a caller opens a second `reftable_addition` on a stack already locked by another instance, the shared lock could be prematurely released when the second instance closes, disrupting concurrent operations. This issue was not previously discussed in the thread and requires resolution before the patch can proceed. For patch 3, Justin proposes an alternative approach to avoid changing the `stack_uptodate()` function signature by skipping the call entirely when the stack is locked, rather than adding a `skip_if_locked` parameter. Patrick Steinhardt’s feedback on patch 1 is cosmetic (function renaming for consistency) and does not block progress. No unresolved concerns remain for patch 1; patches 2 and 3 are now contingent on addressing Junio’s feedback and Justin’s suggestion, respectively.

Participant positions
- Karthik Nayak (author): presents the series as a targeted, mechanical optimization motivated by Jeff King's profiling data. Patch 1 removes the `REFTABLE_STACK_NEW_ADDITION_RELOAD` flag (redundant since 16684b6fae, 2025-08-12) and simplifies the API by making stack reloading the default behavior. Patch 2 relocates the list lock from `reftable_addition` to `reftable_stack` to enable the optimization in patch 3, which skips reloads when the stack is locked. All callers already ensured reloading when needed, so the flag's removal is a cleanup with no functional regression. The final patch completes the series by implementing the core optimization, with benchmark data showing consistent performance gains across ref counts from 2,000 to 100,000.
- Jeff King (Peff): identified the bottleneck (excessive `fstat()` calls during bulk ref creation) that motivates this series; no review comments yet.
- Justin Tobler: substantive reviews of all three patches, engaging with the patches’ logic and edge cases. Confirms the mechanical correctness of the unconditional reload flow in patch 1, verifies that `REFTABLE_OUTDATED_ERROR` checks are redundant, and resolves his initial question about `reftable_stack_clean_locked()` as a non-issue. For patch 2, he endorses the lock relocation as conceptually sound, noting that the lock is inherently singular for a reftable stack and that `struct reftable_stack` is the more logical home for the field. For patch 3, he proposes an alternative approach to avoid changing the `stack_uptodate()` function signature by skipping the call entirely when the stack is locked. No objections to the series’ goals or design; feedback is focused on implementation details.
- Junio C Hamano: substantive review of patch 2, raising a safety concern about the lock relocation’s implications for concurrent or nested `reftable_addition` instances on the same stack. The shared lock could be prematurely released when a second instance closes, potentially disrupting other operations. The concern is narrowly scoped to API safety and does not challenge the optimization goal, but it introduces a new open question that must be resolved before the patch can proceed.
- Patrick Steinhardt: surface-level review of patch 1, noting that libgit2 (a separate project) uses the flag being removed but confirming that all libgit2 call sites already pass it, so the change is compatible. Suggests a cosmetic function rename from `reftable_stack_new_addition()` to `reftable_stack_addition_new()` for naming consistency. No objection to the patch’s substance; feedback is narrowly scoped to API aesthetics and external compatibility.
