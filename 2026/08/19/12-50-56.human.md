This is the fifth iteration of a two-patch series improving user-facing error messages for `git worktree add` and `git checkout`/`git switch` when an ambiguous remote branch name is provided. The series now incorporates Junio’s refactoring, which extends `unique_tracking_name()` to optionally return the list of conflicting remotes, enabling a static list in the advice message. This unifies the logic across all three commands via a new shared helper (`be_explicit()`) and replaces the earlier command-based advice with a more immediately actionable format.

The core change is a usability improvement: when a user runs `git worktree add ../foo-dir bar-topic` and `bar-topic` exists on multiple remotes (e.g., `origin` and `upstream`), Git now fails with a clear, actionable message listing the conflicting remotes and suggesting concrete next steps—either specify the fully qualified branch name (`origin/bar-topic`) or set `checkout.defaultRemote` in the config. The advice is gated behind the new `advice.checkoutAmbiguousRemoteBranchName` config key (enabled by default) and is tailored to the command being used. The patch also moves an existing `die()` call earlier in the code path to replace a generic "invalid reference" error with a more specific diagnostic, improving clarity without altering `dwim_branch()`’s return behavior.

The implementation touches `builtin/checkout.c`, `builtin/worktree.c`, `checkout.c`, `checkout.h`, and the test script `t/t2400-worktree-add.sh`. The changes are well-motivated, with thorough test coverage including a new test for `--guess-remote` with ambiguous branches. The series addresses all substantive feedback from prior iterations, and the remaining open questions—minor code nits like unnecessary braces—are not blockers. The design debate over static vs. command-based advice is now settled in favor of Junio’s refactoring, which prioritizes immediate usability.

This looks like a straightforward win for users encountering ambiguous branch names, with no obvious downsides. The patch is functionally complete, backward-compatible, and ready for final review. If you care about Git’s error messages or worktree usability, this is worth a look.
