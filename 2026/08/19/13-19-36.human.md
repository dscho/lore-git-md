This is a performance-focused bugfix for the reftable backend, part of the ongoing reftable effort. Karthik Nayak addresses a specific inefficiency Jeff King identified: when creating many refs in a single transaction, the reftable stack repeatedly reloads itself via `fstat()` calls, even though the stack is already locked and no concurrent updates are possible.

The series consists of three patches. The first removes an unnecessary flag (`REFTABLE_STACK_NEW_ADDITION_RELOAD`) that was complicating the reload logic. The second moves the lock state into the `reftable_stack` struct itself, and the third uses that state to skip reloading when the stack is already locked. Benchmarks show a modest 1-2% improvement in clock time for `git update-ref`, but more importantly, the number of `newfstatat()` syscalls stays constant (around 55) regardless of how many refs are created, instead of growing linearly.

The patches touch only the reftable library (`reftable/stack.c`, `reftable/stack.h`) and its backend glue (`refs/reftable-backend.c`), plus unit tests. The motivation is clear, the fix is targeted, and the commit messages explain both the problem and the solution well. This looks like a clean, uncontroversial improvement that should be worth reviewing for anyone following the reftable backend.
