This is the final patch in Patrick Steinhardt’s five-patch series refactoring how the object database (ODB) handles corrupt objects when `OBJECT_INFO_DIE_IF_CORRUPT` is used. The series is part of the ongoing ODB abstraction effort and is now in its second iteration (v2), addressing all design-level feedback from Junio C Hamano.

The patch removes the last abstraction-breaking code by eliminating the `has_packed_and_bad()` function, which previously reached into the internals of the packed backend to check for corrupt objects. Instead, `do_oid_object_info_extended()` now tracks corruption status generically by accumulating error messages from all ODB backends and dying with the first available message when `OBJECT_INFO_DIE_IF_CORRUPT` is set. This makes the mechanism fully backend-agnostic and consistent: the loose backend no longer dies unconditionally on corruption, allowing other backends (e.g., an alternate repository) to provide a good copy of the object.

Key changes include:
- **Files touched**: `odb.c` (core logic), `odb/source-loose.c` (removes direct `die()` call), `packfile.c`/`packfile.h` (removes `has_packed_and_bad()`), and `t/t1060-object-corruption.sh` (adds a test for reading corrupted loose objects from alternates).
- **Behavior change**: The loose backend’s direct `die()` call is removed, and `OBJECT_INFO_DIE_IF_CORRUPT` is now handled generically in the ODB layer. The patch also ensures that backend-specific error messages (e.g., "packed object X (stored in Y) is corrupt") are preserved and surfaced to the user.
- **Test coverage**: A new test verifies that a corrupted loose commit can still be read from an alternate repository, demonstrating the improved consistency.

The series is well-structured, with clear commit messages and thorough test updates. The refactoring is mechanical but impactful, eliminating backend-specific assumptions and paving the way for future ODB backends. The patches are under review but appear ready for merging, assuming no further objections to the `bad_pack` granularity discussion (which remains unresolved but is not blocking).
