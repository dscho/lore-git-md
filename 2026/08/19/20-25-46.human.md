This is a follow-up in the **performance bug report** about Git's bash completion being slow in large repositories. The author, Matthew Hughes, revisits his earlier workaround and proposes a refined version that avoids the need for an environment variable.

Instead of disabling index-based completion entirely, Hughes now suggests a more targeted approach: redefining the `__git_complete_index_file` function in the user's shell to skip completion when certain slow options (`--others`, `--modified`, `--deleted`, `--ignored`, or `--killed`) are present. This preserves completion for faster cases while avoiding the expensive filesystem scans that cause the 1–2 second hangs in large repositories. The patch is still a workaround — it doesn’t fix the root cause — but it’s more surgical than the earlier `GIT_COMPLETION_NO_COMPLETE_INDEX` proposal, which disabled all index-based completion.

The refinement is pragmatic and addresses a key concern from the original report: whether the trade-off between speed and accuracy is justified. By only skipping completion for the slowest cases, this version maintains accuracy for most use cases while still mitigating the performance issue. It’s also easier to deploy, as it doesn’t require modifying the upstream completion script — users can add the redefinition to their shell profile.

This is still not a true fix, but it’s a step forward in usability. The discussion is likely to continue around deeper solutions, such as optimizing `git ls-files` for wildcard patterns or making the completion script smarter about when to scan the filesystem. For now, this workaround offers a practical way for users to avoid the worst slowdowns without sacrificing too much functionality.
