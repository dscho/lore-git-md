This is the third and final patch in a three-patch series improving error messages for ambiguous remote branch names in `git worktree add`. The series, now in its seventh iteration (v7), is ready for merging and addresses a long-standing usability issue where Git fails silently or with unhelpful errors when multiple remotes contain a branch with the same name.

This patch applies the same user-friendly advice mechanism introduced in the earlier patches to `git worktree add`. When the command encounters an ambiguous branch name (e.g., `bar-topic` existing in both `origin` and `upstream`), it now dies immediately with a clear error message listing the conflicting remotes and actionable advice. The message suggests either specifying the remote explicitly (`git worktree add -b bar-topic ../foo-dir origin/bar-topic`) or configuring a default remote (`checkout.defaultRemote=origin`). The advice is controlled by the new `advice.checkoutAmbiguousRemoteBranchName` config key, which defaults to true.

The implementation reuses the `advise_disambiguating_remotes()` helper introduced in patch 1/3 and extends `unique_tracking_name()` to collect remote names via a new `struct string_list` parameter. The patch also narrows the scope of the `oid` variable and updates the test suite to verify the new error message format. The one-argument `git worktree add` edge case (e.g., `git worktree add ../foo-dir`) is intentionally excluded from disambiguation logic, as the command succeeds in this scenario due to `--guess-remote` or `worktree.guessremote=true`.

Junio C Hamano and D. Ben Knoble have reviewed the series, and all structural adjustments (including fixing a grammatical error in the advice message) are complete. The only remaining suggestion is a non-blocking code comment near the `dwim_branch()` call in the one-argument path. The patch is well-tested, localized, and follows Git’s advice-message conventions. It looks ready for `next`.
