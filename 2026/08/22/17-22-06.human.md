This is the final exchange in the v7 patch series improving error messages for ambiguous remote branch names in `git worktree add`, `git checkout`, and `git switch`. Junio C Hamano steps back from the immediate patch to reflect on a deeper design issue in `git worktree add`.

The thread confirms that the current behavior of the one-argument form (`git worktree add ../topic-branch`) is intentional: it succeeds regardless of whether `dwim_branch()` finds zero, one, or multiple matches, creating either a tracking branch or a local branch from HEAD. Yoichi Nakayama had already concluded that no disambiguation logic is needed here, and Junio now agrees that this is a reasonable boundary for the current series.

However, Junio identifies a latent bug: the code path treats zero matches and multiple matches identically, which he argues is incorrect. He traces the history back to Thomas Gummerer’s 2017 work that introduced DWIM behavior, noting that the original design did not anticipate multiple matches. Even after Ævar Arnfjörð Bjarmason’s 2018 patch allowed callers to distinguish between zero and multiple matches, the `git worktree` side was left incomplete. Junio’s position is that the command should eventually error out on multiple matches rather than silently creating a local branch from HEAD.

The message is explicitly framed as `#leftoverbits` — a note for future work, not a blocker for the current series. The v7 patches are otherwise ready for merging; this is a forward-looking observation about how the command *should* behave, not a request for immediate change.
