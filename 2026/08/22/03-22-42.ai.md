This is the third and final patch in Yoichi NAKAYAMA’s v7 series improving error messages for ambiguous remote branch names in `git worktree add`. It extends the advice mechanism introduced in patch 1/3 and applied to `git checkout`/`git switch` in patch 2/3 to the worktree command, completing the series.

The patch teaches `git worktree add` to detect when a branch name (e.g., `bar-topic`) matches multiple remote tracking branches (e.g., `origin/bar-topic` and `upstream/bar-topic`) and, instead of silently giving up and later failing with a generic “invalid reference” error, immediately die with a clear diagnostic. The new message lists the conflicting remotes and suggests concrete next steps: either specify the remote explicitly (`git worktree add -b bar-topic ../foo-dir origin/bar-topic`) or set `checkout.defaultRemote` to prefer one remote in future. The advice is controlled by the same `advice.checkoutAmbiguousRemoteBranchName` config key (default: true) introduced earlier, ensuring consistency across all three commands.

Code changes are confined to `builtin/worktree.c` and the test script. The patch extends `unique_tracking_name()`’s existing `num_matches` parameter with a new `struct string_list *matched_remote_names` to collect the names of all matching remotes, then passes them to the shared `advise_disambiguating_remotes()` helper. The `die()` call is moved earlier in the code path, replacing the generic “invalid reference” message with one that explicitly states the ambiguity and the number of matches (e.g., “matched multiple (2) remote tracking branches”). The `oid` variable’s scope is narrowed, and the test script is updated to verify the new error message format.

The implementation handles the one-argument edge case (`git worktree add ../foo-dir`) correctly: no disambiguation logic is added here because the command succeeds even when multiple remotes match (due to `--guess-remote` or `worktree.guessremote=true`). Junio’s suggestion to add a code comment near the `dwim_branch()` call in this path remains the only open item, but it is non-blocking.

This patch is a clean, localized usability improvement with thorough test coverage. The series as a whole is now functionally complete, reviewed by Junio C Hamano and D. Ben Knoble, and ready for `next`.
