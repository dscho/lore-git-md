This is a new participant joining the RFC thread about restricting Git object IDs to lowercase in Git 3.0. Michael Montalbo demonstrates a concrete way to exploit Git's current case-insensitive hex parsing: by crafting a commit whose parent field contains a mixed-case object ID, you create two distinct commit objects that refer to the same underlying parent but are treated as separate commits by Git. This produces parallel histories that differ only in case, with Git normalizing the parent ID in some outputs (e.g., `git log --format='%P'`) but preserving the raw mixed-case form in others (e.g., `git log --pretty=raw`).

The example is simple to reproduce and shows how Git's current behavior can lead to confusion or even security issues for tools that consume Git output. While Montalbo doesn't propose a specific attack vector, the ambiguity itself is problematic: downstream tools might parse the same object ID differently depending on the output format, leading to inconsistent behavior. This strengthens brian m. carlson's argument that Git's lenient parsing creates real-world compatibility and security risks, and it directly counters Junio C Hamano's earlier suggestion that normalizing inputs internally could address the problem without outright rejection. The example shows that normalization alone isn't sufficient—Git's own output paths already produce inconsistent representations of the same object ID, which is exactly the kind of ambiguity the series aims to eliminate.
