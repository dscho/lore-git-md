This is a **substantive review** of the third patch in Johannes Schindelin’s 12-patch series widening size fields in Git’s delta and pack machinery to `size_t` for 64-bit Windows correctness. The series is part of the broader effort to eliminate unsafe `unsigned long` usage in favor of `size_t`.

Patrick Steinhardt identifies a latent configuration-parsing bug in `builtin/pack-objects.c`: the `max_delta_cache_size` variable is currently set via `git_config_int()`, which accepts negative values. While the patch widens the variable from `unsigned long` to `size_t`, it does not address the fact that negative inputs (e.g., `pack.deltacachesize = -1`) are still accepted, leading to nonsensical cache limits. The documentation only mentions positive values, so this is technically a pre-existing bug, but the patch’s type change makes it more visible. Patrick suggests either introducing a `git_config_size_t()` helper or switching to `git_config_uint()` to reject negative values outright, though he notes the latter could break users who mistakenly rely on negative values as "infinite" cache.

The review is narrowly scoped to this one variable and its configuration parsing, but it surfaces a real edge case that could affect user expectations. The fix is straightforward and uncontroversial, aligning with the series’ goal of type correctness. No other issues are raised in this reply.
