This is a new participant reply in the RFC thread about restricting hex object IDs to lowercase in Git 3.0. Michael Montalbo contributes a concrete demonstration of how mixed-case object IDs can create ambiguity and potential security issues. His script shows that Git currently allows commits to reference the same parent object using different case spellings, producing distinct commit objects that differ only in the case of the parent OID field. While both spellings resolve to the same underlying object, Git's output paths handle them inconsistently: raw output preserves the mixed-case form, while formatted output (e.g., `%P`) normalizes to lowercase. This inconsistency could confuse downstream tools that parse Git output, creating opportunities for malicious manipulation or unintended behavior. The example strengthens brian m. carlson's argument that Git's current case-insensitive parsing is problematic, though it does not directly address Junio C Hamano's proposed compromise of normalizing inputs internally. The demonstration is narrowly scoped to the existing behavior and does not propose or modify the patch series itself.
