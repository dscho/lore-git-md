This is a brief follow-up in the `git last-modified` Bloom-filter optimization thread, specifically about patch 1/4. Jeff King (Peff) acknowledges a correction from Toon Claes: the distinction between the tristate return values (`0`, `1`, `-1`) in `check_maybe_different_in_bloom_filter` is not purely academic, as the `count_bloom_filter_false_positive` counter depends on knowing whether the filter returned "maybe" (`1`) or no filter was used at all (`-1`). Peff accepts Toon’s plan to refactor the public API (`repo_may_have_commit_with_changes`) to use a boolean return while retaining the tristate logic in a private wrapper, calling this a reasonable compromise. He also suggests that symbolic constants (e.g., `BLOOM_FILTER_MAYBE`, `BLOOM_FILTER_NONE`) could further clarify the interface, but considers this a non-blocking cleanup that could be deferred. The exchange resolves the open design question from Peff’s earlier review, leaving no remaining objections to the patch’s approach.
