This is a follow-up in the ongoing bug report about `git rebase -x` losing notes when combined with `git commit --amend`. The thread remains focused on the rebase and notes subsystems.

Phillip Wood, who previously diagnosed the root cause, now proposes an alternative fix strategy. Instead of updating the rebase’s internal `rewritten` file after `git commit --amend` (the approach in his stalled `wip/rebase-update-rewritten` branch), he suggests copying notes *before* stopping for an `exec` or `edit` command. This would let `git commit --amend` handle the notes rewrite itself, avoiding the need to track amended OIDs in the rebase machinery. He acknowledges that `edit` commands complicate this approach due to potential conflicts, and notes that in-process note copying would be more efficient than forking `git notes copy` before each `exec`.

The proposal is still conceptual—no new patches or test cases are attached—but it shifts the discussion toward a potentially simpler design. The thread remains open, with no consensus yet on which approach to pursue. If you care about rebase edge cases or notes behavior, this is worth monitoring.
