This is the fourth patch in Patrick Steinhardt’s six-patch series making on-disk object database (ODB) structures pluggable, part of the ongoing ODB abstraction effort. The patch itself is a straightforward refactoring that defers ODB creation until after the reference database is initialized, preparing for the next patch’s pluggable on-disk structure mechanism. It is uncontroversial and ready for merging, with no open technical objections.

Toon Claes’s reply, however, shifts the discussion to a broader design question: whether the current two-step initialization (first `apply_repository_format()`, then `odb_new()`) should be simplified by always requiring an explicit `odb_new()` call after `apply_repository_format()`. His proposed diff removes the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag entirely, making `apply_repository_format()` never create the ODB, and instead adds explicit `odb_new()` calls at each callsite. This would eliminate the intermediate state where the repository is partially configured, aligning with Justin Tobler’s earlier suggestion.

The trade-off is clear: Toon’s approach simplifies the API by removing a flag and making ODB creation always explicit, but it requires updating every callsite of `apply_repository_format()`. The current patch’s approach is more incremental, preserving backward compatibility while enabling the pluggable ODB structure work. Neither approach is obviously superior, but Toon’s proposal is a serious alternative that could reduce long-term complexity if adopted. The thread context suggests this is the first time the idea has been fleshed out with a concrete diff, so it may prompt further discussion about the right balance between simplicity and incrementalism.
