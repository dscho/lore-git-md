This is the third iteration of Patrick Steinhardt’s six-patch series making the creation of on-disk object database (ODB) structures pluggable. The series is part of the ongoing ODB abstraction effort and remains under active review.

The core goal is unchanged: decouple the creation of backend-specific directories (like `objects/info` and `objects/pack`) from the generic repository setup code. The top-level `objects/` directory is still mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic.

The v3 update addresses the main point of contention from v2: environment variable handling. Patrick has moved the handling of `GIT_OBJECT_DIRECTORY` and `GIT_ALTERNATE_OBJECT_DIRECTORIES` directly into `odb_new()`, eliminating the awkward double-pointer passing and deduplicating logic. This change also prepares for a future where alternates are handled within the "files" backend itself. The new third patch (`setup: handle ODB-related environment variables in `odb_new()``) implements this refactoring, replacing the previous environment variable helper function.

The series still starts with the same correctness fix for loose-object map loading (patch 1), followed by the detangling of loose object map loading from repository setup (patch 2). The fourth patch (`setup: defer object database creation`) has been updated to reflect the new environment variable handling, simplifying the control flow. The fifth patch introduces a helper function to map ODB source types to their names, and the sixth patch implements the pluggable directory creation mechanism.

The changes look well-motivated and the v3 update addresses the main implementation concern from the previous round. The series is now more streamlined, with clearer separation of concerns and better alignment with future work. The first patch remains a strong candidate for early graduation due to its status as a correctness fix with regression coverage. The rest of the series is infrastructure work with no immediate user-visible impact, but it’s a prerequisite for any future ODB backend that doesn’t follow the traditional loose/pack layout.
