This is the second patch in a two-patch bugfix series for `git maintenance`'s geometric repack task, addressing a regression where the `--auto` trigger failed to account for promisor packs after they gained independent geometric progression support. The patch updates the auto-condition logic in `builtin/gc.c` to check `geometry.promisor_split` alongside `geometry.split`, ensuring the task runs when promisor packs are ready for rollup even if ordinary packs or loose objects don't require maintenance.

The change is minimal but critical: a single-line modification to the condition in `geometric_repack_auto_condition()` that determines whether a repack is needed. The test coverage in `t/t7900-maintenance.sh` demonstrates the fix by creating three promisor packs (two small, one large) and verifying that `--auto` triggers the task when the two smaller packs should roll up. A minor adjustment in `t/t5331-pack-objects-stdin.sh` disables auto-maintenance in a filtered clone fixture to avoid interfering with its existing test logic.

This patch completes the series' goal of making promisor pack handling consistent across both the repack decision logic (fixed in patch 1) and the auto-trigger mechanism. The regression it addresses is well-documented (introduced by dcc9c7ef47 in January 2026), and the solution aligns with the existing code's structure. The test case is thorough, using `GIT_TRACE2_EVENT` validation in the first patch and now explicitly testing the auto-trigger behavior for promisor packs. This looks like a clean, targeted fix for a real-world issue in partial clone repositories.
