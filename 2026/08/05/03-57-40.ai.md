This is the first patch in a two-patch bugfix series for `git maintenance`'s geometric repack task, addressing a regression in how promisor packs are handled. The patch modifies the maintenance task to evaluate both ordinary and promisor pack geometric progressions before deciding whether to fall back to an all-into-one repack.

The regression was introduced by dcc9c7ef47 (2026-01-05), which added geometric progression support for promisor packs but did not update the maintenance task to account for them. Previously, the task only considered the non-promisor pack progression, leading to unnecessary rewrites when promisor packs would have been left intact. The fix ensures the task checks both progressions and only falls back to all-into-one when neither progression would keep a pack above its split threshold.

The change touches `builtin/gc.c` to update the repack mode decision logic, adding a condition to check `geometry.promisor_split` alongside `geometry.split`. The patch also adds a new test in `t/t7900-maintenance.sh` that verifies the fix by creating three promisor packs (two small, one large) and confirming that the two smaller ones roll up while the large one remains untouched. The test uses `GIT_TRACE2_EVENT` to validate the correct `git repack` command is invoked.

This is a well-motivated, targeted fix with clear test coverage. The commit message explains the problem, the regression's origin, and the rationale for the solution. The patch looks ready for review and should resolve a real-world issue in partial clone repositories.
