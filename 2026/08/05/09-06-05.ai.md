This is a bug report about credential helper behavior during HTTP redirects. The issue is that when `git push` follows a 301 redirect, the `wwwauth[]` attribute (containing the WWW-Authenticate header from the server) is stripped from the credential helper input, preventing helpers like `git-credential-oauth` from detecting the required authentication scheme. The reporter expects the header to be preserved across redirects, as it is when no redirect occurs.

The report provides clear reproduction steps: pushing to a remote that 301-redirects before responding with a 401 and WWW-Authenticate header. The affected credential helper is `git-credential-oauth`, and the server is a self-hosted Forgejo instance. The reporter notes this is a regression in behavior compared to direct (non-redirect) requests.

Key technical details include the credential helper protocol attribute `wwwauth[]`, the HTTP 301/401 redirect flow, and the interaction with libcurl (version 8.15.0). The report does not include a patch or proposed fix, only the observed misbehavior. This appears to be a thread root, with no prior discussion context provided. The issue is likely in the credential helper protocol implementation or how Git processes HTTP responses during redirects.
