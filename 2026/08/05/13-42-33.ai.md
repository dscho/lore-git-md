This is a substantive review of a bug report in the rebase and notes subsystems.

Phillip Wood responds to D. Ben Knoble’s report about `git rebase -x` losing notes when combined with `git commit --amend`. He identifies the root cause: the rebase machinery records the new commit OID *before* the external command runs, so when `git commit --amend` creates a new OID, the notes-rewriting step (which happens after the rebase finishes) still maps the old OID to the pre-amend OID, not the post-amend one. The notes are therefore copied to the wrong commit and appear lost.

Phillip notes he has an old, unfinished branch (`wip/rebase-update-rewritten`) that attempts to fix this by having `git commit --amend` update the rebase’s internal rewritten-commits file. The branch is pushed to his GitHub fork, though he warns the commit messages are poor. He confirms the approach worked for simple `exec` amend cases but stalled when trying to handle interactive editing more robustly.

The review is substantive: it traces the bug to a specific code path (the `rewritten` file in the rebase state directory), explains why the current design fails, and points to prior work that tried to address it. No test results or CI feedback are mentioned, so the depth is diagnostic rather than tested. The key technical detail for follow-up is the `rewritten` file and the timing of when OIDs are recorded.
