This is the second patch in Patrick Steinhardt’s six-patch series (v3) making on-disk ODB structures pluggable, part of the ongoing ODB abstraction effort. It refactors how Git loads loose object maps—used when a repository is configured with a compatibility hash algorithm—to fix two latent issues: an unconditional downcast that would BUG if a non-"files" ODB backend were used with a compatibility hash, and a tangled initialization sequence that intermixes repository configuration with ODB setup.

The patch moves the loose object map loading logic into the "loose" backend itself, making it an internal implementation detail. The `loose_object_map_load()` function is now called directly from `odb_source_loose_new()`, ensuring the map is loaded only when the backend is initialized and only if the repository is configured to use loose object maps. This eliminates the need for `repo_set_compat_hash_algo()` to assume the primary ODB is a "files" backend, resolving the downcast safety issue. The change also reorders the initialization sequence in `apply_repository_format()` to set the compatibility hash algorithm *before* creating the ODB, simplifying control flow.

Files touched include `loose.c` and `loose.h` (where the loading logic is moved), `odb/source-loose.c` (where the new call site is added), and `repository.c` and `setup.c` (where the initialization sequence is adjusted). The diff is small and mechanical, introducing no new behavior but laying groundwork for future ODB backends. The patch is now uncontroversial; earlier concerns about downcast safety and initialization sequence design were addressed in v2 by making the loose object map an internal detail of the loose backend. Junio’s "What’s cooking" report (2025-06-10) lists this patch as "under review" alongside the rest of the series, while the first patch (a correctness fix) is marked for early graduation to `next`.
