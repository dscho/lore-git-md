This is a follow-up discussion in the ongoing bug report about `git rebase -x` losing notes when combined with `git commit --amend`. The thread remains focused on the rebase and notes subsystems, specifically the edge case where an external command amends a commit during rebase.

Phillip Wood proposes an alternative approach to the fix he previously outlined. Instead of updating the rebase’s internal `rewritten` file after `git commit --amend` (as in his stalled `wip/rebase-update-rewritten` branch), he suggests copying notes *before* stopping for an `exec` or `edit` command. This would allow `git commit --amend` to handle note copying directly to the amended commit, avoiding the need to track OIDs post-amend. He acknowledges that `edit` commands complicate this approach due to potential conflicts, and notes that in-process note copying would be preferable to forking `git notes copy` before each `exec` command.

The proposal is a shift in strategy rather than a concrete patch, but it introduces a new technical consideration: preemptive note copying as a way to sidestep the OID-mapping issue entirely. This could simplify the fix but may require careful handling of conflict cases during interactive editing. No test results or implementation details are provided yet, so the idea remains conceptual. The key detail for future discussion is the timing of note copying—whether it happens before or after the external command runs.
