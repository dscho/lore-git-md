This is a **platform compatibility bugfix** for macOS, specifically addressing a memory leak in the system regex engine (TRE) when processing invalid UTF-8 sequences. The patch itself is ready for merging, but Patrick Steinhardt raises a thoughtful question about whether the workaround is the best long-term solution.

The current patch (v2) adds a Darwin-specific `regexec_buf()` implementation that splits input buffers at invalid multibyte boundaries and searches each valid segment separately, avoiding the leaking code path. This approach is narrowly scoped to macOS builds using the system regex engine and preserves all behavioral guarantees of the original implementation. Junio C Hamano’s feedback on v2 was positive, focusing only on minor structural improvements (now addressed) and a trivial `Makefile` comment addition.

Patrick’s question cuts to the heart of the trade-off: the patch adds ~100 lines of platform-specific logic to work around an upstream bug that may eventually be fixed. He suggests an alternative—detecting affected macOS versions and falling back to Git’s built-in regex implementation (`NO_REGEX`)—which would avoid maintaining a custom workaround. The commit message and code comments treat the current fix as indefinite, but Patrick’s proposal could simplify the codebase if viable.

The patch is well-motivated and thoroughly tested, with new regression tests in `t7810-grep.sh` verifying matches around invalid bytes and correct anchoring. The modular approach (dedicated `compat/darwin/` files) sets a clean precedent for future platform overrides. However, Patrick’s alternative deserves consideration, especially if the upstream fix timeline is uncertain or if Git’s built-in regex implementation is already robust enough for macOS users. **Worth attention from macOS users and reviewers familiar with regex internals or platform-specific workarounds.** The discussion now hinges on whether the workaround’s complexity is justified or if a simpler fallback would suffice.
