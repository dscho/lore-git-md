This is a macOS-specific bugfix for the fsmonitor daemon, part of the ongoing effort to stabilize filesystem monitoring performance. Patrick Steinhardt’s reply to Tamir Duberstein’s patch raises a pointed technical question: why does flushing FSEvents help when the daemon already waits up to a full second—far longer than the 1 ms batching latency configured for the event stream?

The patch itself remains uncontested: it adds a single asynchronous flush call (`fsm_listen__flush_async`) immediately after cookie creation and before the timed wait, with no-op stubs for Linux and Windows. The change is minimal, well-scoped, and backed by Tamir’s performance data showing timeout rates dropping from ~89% to zero on a loaded M4 Max Mac. Koji Nakamaru’s tested review confirmed the fix is low-risk, and Junio has already forwarded that feedback, leaving only the commit message’s benchmark detail as a loose end.

Patrick’s question cuts to the heart of the macOS FSEvents behavior. He notes that the 1 ms latency should be negligible compared to the 1-second timeout, yet Tamir’s measurements show otherwise. The implication is that FSEvents’ batching may not respect the configured latency under load, or that the kernel’s flushing mechanism provides stronger guarantees than mere latency hints. The commit message hints at this (“does not guarantee that its queue is drained in one latency interval”), but Patrick is asking for authoritative documentation or deeper explanation—something Tamir has not yet provided.

For a busy reader, this patch looks like a safe, targeted fix for a real regression. The only open question is why the flush works, not whether it does. If Tamir can clarify the FSEvents guarantees, the patch is likely to proceed; if not, the lack of explanation may not block it, but it could leave reviewers uneasy about future macOS-specific optimizations. Either way, the fix itself is narrow and unlikely to cause collateral damage.
