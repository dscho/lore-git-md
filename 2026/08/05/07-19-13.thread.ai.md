Thread identity: Bug report about inconsistent `--porcelain` output in `git push --delete` when deleting non-existent refs. Originating author: Xavier Morel. Thread type: bug report (RFC-style).

Core problem or goal: The `git push --delete --porcelain` command outputs human-readable error messages (e.g., "remote ref does not exist") instead of the documented machine-readable porcelain format when attempting to delete a ref that no longer exists on the remote. This breaks the expected output consistency for `--porcelain`, which is intended for script consumption, and prevents reliable error detection in automation tools.

Current status: The issue is acknowledged by the maintainer (Junio C Hamano) as an unintended oversight. The technical direction is settled: use `!` as an error prefix for machine-readable output in failure cases (e.g., non-existent refs). Xavier Morel has proposed a concrete implementation strategy targeting `match_explicit`, `set_ref_status_for_push`, and reporting logic in `push.c`. The plan avoids disrupting valid pushes unless `--atomic` is set, and the choice between introducing a new status code (`REF_STATUS_REJECT_NODELETE`) or extending an existing one remains open but is considered a minor detail. No patch has been submitted yet, but the maintainer's prior invitation signals that a clean implementation following this plan would likely be accepted.

Key technical details:
- **Subsystems/files**: `push.c` (primary), specifically `match_explicit`, `set_ref_status_for_push`, and `push_refs_with_push`.
- **CLI flag**: `--porcelain` (documented to use `:` for successful deletions and `!` for errors).
- **Error case**: Concurrent deletion of a ref (e.g., by another user) causes the command to fall back to unstructured error messages.
- **Expected behavior**: Use `!` prefix for remote failures (e.g., non-existent refs) to maintain machine-readability.
- **Implementation plan**: (1) Modify `match_explicit` to create a dummy destination ref with a failure status instead of aborting, (2) ensure `set_ref_status_for_push` skips refs that already have a status set, and (3) adapt reporting logic to handle the new failure case.
- **Status code question**: Whether to introduce a new status code (`REF_STATUS_REJECT_NODELETE`) or extend an existing one; either is acceptable if it achieves the desired output format.
- **Impact**: Scripts/tools parsing `--porcelain` output cannot reliably detect deletion failures for non-existent refs.
- **Maintainer stance**: The behavior is unintended; a patch to fix it would be welcome.
