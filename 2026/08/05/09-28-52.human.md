This is the second patch in Patrick Steinhardt’s six-patch series making on-disk ODB structures pluggable, part of the ongoing ODB abstraction effort. It addresses a latent correctness bug in how Git loads loose object maps when using compatibility hash algorithms (e.g., SHA-256 repositories with SHA-1 compatibility).

The patch detangles loose object map loading from repository setup by moving it into the "loose" ODB backend. Previously, `repo_set_compat_hash_algo()` unconditionally downcast the primary ODB to a "files" backend, which would BUG if a different backend type were used with a compatibility hash. The fix makes the loose object map an internal implementation detail of the loose backend, eliminating the unsafe downcast and allowing the ODB to be fully initialized before loading the map. The change is small (11 insertions, 10 deletions) but important: it removes a hardcoded assumption that could break future ODB backends.

The patch looks well-crafted and addresses a real issue. The commit message clearly explains the problem, the fix, and the benefits, and the code changes are focused and mechanical. This is a refactoring that improves safety without changing behavior, making it a strong candidate for merging. The only remaining caller of `repo_read_loose_object_map()` is in `object-file-convert.c`, which reloads the map after potential concurrent updates; Patrick notes this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source.

This patch is now uncontroversial and ready for merging. It was previously reviewed by Junio and Justin Tobler, who identified the latent BUG and approved the fix. The series as a whole is under review, but this patch stands on its own as a correctness improvement.
