This thread is about a bug in `git rebase -x` where notes attached to commits are lost when the external command amends the commit with `git commit --amend`. The issue was diagnosed by Phillip Wood: the rebase machinery records the new commit OID *before* the external command runs, so when `--amend` creates a new OID, the notes-rewriting step fails to map it correctly, making the notes appear lost.

Two fix strategies were previously proposed: updating the rebase’s internal `rewritten` file after `--amend` (Phillip’s stalled approach) or copying notes *before* the external command runs (a newer idea). D. Ben Knoble has now suggested two alternative workarounds: exposing rebase’s internal OID mapping to `exec` commands so they can handle note copying directly, or providing a post-rebase mechanism to feed the OID mapping to `git notes copy`. These ideas avoid modifying rebase’s internal state but would require new plumbing to expose the mapping safely.

The discussion remains conceptual, with no implementation or test results yet. The root cause is confirmed, but the best fix is still unresolved—whether to modify rebase internals, preemptively copy notes, or expose the OID mapping for external use. Phillip Wood and D. Ben Knoble are the key participants, but no consensus has emerged on the path forward.
