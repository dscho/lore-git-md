This thread is a bug report about `git rebase -x` losing notes when combined with `git commit --amend`. The issue was reported by D. Ben Knoble, who observed that notes attached to commits are lost only when both `-x` (execute an external command) and `--amend` are used together during a rebase, despite `notes.rewriteref` being configured to preserve them.

Phillip Wood has diagnosed the root cause: the rebase machinery records the new commit OID *before* the external command runs, so when `git commit --amend` creates a new OID, the notes-rewriting step (which occurs after the rebase finishes) still maps the old OID to the pre-amend OID. This causes the notes to be copied to the wrong commit, making them appear lost. Phillip also mentions an old, unfinished branch (`wip/rebase-update-rewritten`) that attempts to fix this by having `git commit --amend` update the rebase’s internal `rewritten` file, though he notes the branch is not fully robust for interactive editing.

No patch has been proposed yet, and the issue remains under investigation. The key technical detail for any future fix is the timing of when OIDs are recorded in the rebase state directory’s `rewritten` file. The thread is still open, with no test case or formal reproduction steps beyond the reporter’s initial sketch.
