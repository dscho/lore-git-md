This is the first patch in a two-patch bugfix series targeting `git maintenance`'s geometric repack task when promisor packs are present. The patch addresses a regression introduced by dcc9c7ef47 (2026-01-05), which added geometric progression support for promisor packs but did not update the maintenance task to account for them.

Previously, the geometric-repack maintenance task only considered the non-promisor pack progression when deciding whether to perform a geometric repack or fall back to an all-into-one repack. This could lead to unnecessary rewrites when promisor packs would have been left intact. The patch fixes this by checking both the ordinary and promisor pack progressions before choosing the repack mode. The fallback to all-into-one now only occurs when neither progression leaves a pack above its split threshold, preserving the original intent of avoiding rewrites when geometric repacking would not reduce the number of packs.

The change is minimal and focused: it modifies a single condition in `builtin/gc.c` to include promisor pack geometry in the decision logic. The accompanying test in `t/t7900-maintenance.sh` verifies the fix by creating three promisor packs (two small, one large) and confirming that the maintenance task rolls up only the smaller ones while leaving the large one untouched. The test is thorough and clearly demonstrates the expected behavior.

This patch is well-motivated and addresses a real-world issue in partial clone repositories. The commit message explains the problem and solution clearly, and the test coverage ensures the fix works as intended. The change is unlikely to be controversial, as it aligns the maintenance task's behavior with the existing geometric repacking logic for promisor packs.
