This is a brief follow-up in the `git-replay`/`git-history` notes-loss thread. Elijah Newren clarifies his earlier remark about `git filter-repo` lacking built-in support for preserving notes during history rewriting. He acknowledges the existence of documented workarounds (which he previously labeled in the GitHub issue) but emphasizes that these are not ideal, as they require changes to `git fast-export` and `git fast-import` to properly handle notes as a special case. His comment reinforces the architectural challenge: notes are stored as ordinary commits, so filtering operations detach or discard them unless explicitly preserved. This adds context to the broader discussion about whether `git-replay` and `git-history` should implement note preservation by default or via an opt-in flag, but does not propose a specific design direction. The thread’s core questions—such as plumbing vs. user-facing command behavior and the default state of any new `--copy-notes` flag—remain unresolved.
