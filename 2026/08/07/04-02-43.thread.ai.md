Thread identity: Feature request for unified interactive patch selection in Git (`git add -p`/`git checkout -p` workflow enhancement). Originating author: Junio C Hamano. Thread type: design discussion (RFC).

Core problem or goal: Address the lack of a built-in workflow for efficiently triaging hunks into three categories (stage, keep in working tree, or discard) during interactive patch selection. The immediate goal is to unify triage actions (stage/discard/defer) into a single session, with the underlying mechanism (a single command set for all three actions) prioritized over UI style. The discussion distinguishes between workflow unification (core friction) and UI improvements (longer-term concern), with consensus that the *workflow* (not the UI) is the key value of existing tools like Fugitive.

Current status: Conceptual discussion in early design phase; no patches or implementation sketches have been posted. The thread has converged on the immediate priority: unifying triage actions (stage/discard/defer) into a single session by extending `git add -p` (or a similar command) to support a "discard" action alongside "stage" and "defer," eliminating the need for a separate `git checkout -p` step. Junio C Hamano’s latest reply reinforces this consensus, signaling that the mechanism (single command set) is the focus, while UI design (e.g., prompt-loop vs. TUI-like interfaces) remains a separate, longer-term concern.

Key technical details:
- Subsystems involved: `add--interactive` (Perl script or C rewrite in `add-interactive.c`), `apply` machinery (used by `checkout -p`), index manipulation logic (used by `add -p`), and potentially `git history` (for rewriting commits) or branch creation logic.
- New behavior: Unified interactive session supporting at least three actions per hunk (stage, discard, defer), with the mechanism (single command set) decoupled from UI style. The "discard" action would operate on the working tree, while "stage" and "defer" would manipulate the index and working tree, respectively.
- Open questions: How to represent deferred hunks (persist in working tree, stash temporarily, or ignore until next session); whether this functionality belongs in `git add -p` (as Junio proposes), a new command (e.g., `git triage -p`), or modular intent-based commands (e.g., inspired by GitButler); how the "discard" action would interact with the existing `apply` and index manipulation logic; and whether to prioritize simplicity (stage/discard/defer only) or flexibility (e.g., supporting advanced workflows like amending arbitrary commits).

Open questions and loose ends:
- How should deferred hunks be handled? Persist in working tree, stash, or ignore?
- Should the "discard" action be added to `git add -p` (as Junio proposes), or should this functionality be introduced via a new command or intent-based commands?
- How would a "discard" action interact with the underlying `apply` machinery and index manipulation logic in `add--interactive` or `add-interactive.c`?
- Can `git history` or similar tools be leveraged to support squashing hunks into older commits or moving them to new branches, or is this a separate concern?
