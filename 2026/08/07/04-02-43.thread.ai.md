Thread identity: Feature request for unified interactive patch selection in Git (`git add -p`/`git checkout -p` workflow enhancement). Originating author: Junio C Hamano. Thread type: design discussion (RFC).

Core problem or goal: Address the lack of a built-in workflow for efficiently triaging hunks into three categories (stage, keep in working tree, or discard) during interactive patch selection. The discussion centers on three competing visions: (1) Junio C Hamano’s near-term goal of unifying triage actions (stage/discard/defer) into a single session while preserving Git’s existing prompt-loop UI, (2) Patrick Steinhardt’s proposal to adopt a hierarchical TUI (text-based user interface) inspired by Jujutsu (JJ) for non-linear selection, with a pragmatic middle ground of addressing core workflow gaps (e.g., navigable hunk selection) while deferring full UI modernization, and (3) Stefan Haller’s suggestion to avoid internal UI modernization entirely and rely on external tools (e.g., lazygit) for enhanced interfaces, with Git focusing on improving core APIs. Junio’s latest reply clarifies the project’s philosophical boundary: Git should provide minimal, "usable but not pretty" interactive features that serve as a reference implementation without competing with external tools, ruling out larger UI efforts (e.g., a full TUI) but leaving room for incremental workflow fixes (e.g., unified hunk triage).

Current status: Conceptual discussion in early design phase; no patches or implementation sketches have been posted. The thread has converged on the immediate priority of unifying triage actions (stage/discard/defer) into a single session, but the scope of the solution remains contested. Junio’s latest reply reinforces that Git’s built-in workflows should avoid duplicating functionality already provided by external tools, implying that incremental improvements (e.g., extending `git add -p` to support "discard") are acceptable, while larger UI modernization efforts (e.g., a TUI) are not. Patrick’s proposal for basic UI improvements (e.g., navigable hunk selection) remains a middle ground, but Junio’s position suggests it may be deemed too ambitious if it risks competing with external tools. Stefan’s external-tool proposal remains unchanged, with Junio’s reply aligning philosophically but not addressing the technical specifics of API improvements.

- New behavior:
  - **Junio’s proposal**: Unified interactive session supporting at least three actions per hunk (stage, discard, defer) within the existing prompt-loop UI. The "discard" action would operate on the working tree, while "stage" and "defer" would manipulate the index and working tree, respectively. Junio’s latest reply clarifies that this should be implemented as a minimal, reference-like feature, not a polished UI.
  - **Patrick’s proposal**: Hierarchical, navigable TUI for selecting changes (files → hunks → lines), replacing the linear prompt-loop. His latest reply refines this to focus on *basic* UI improvements (e.g., navigable hunk selection) to address core workflow gaps without requiring a full TUI rewrite. However, Junio’s position suggests that even basic TUI-like features may be deemed too competitive with external tools.
  - **Stefan’s proposal**: No internal UI changes; instead, improve Git’s core APIs (e.g., `add--interactive`, `git history`) to make them more consumable by external tools like lazygit.
