Thread identity: Feature request for unified interactive patch selection in Git (`git add -p`/`git checkout -p` workflow enhancement). Originating author: Junio C Hamano. Thread type: design discussion (RFC).

Core problem or goal: Address the lack of a built-in workflow for efficiently triaging hunks into three (or four, if stash is included) categories (stage, keep in working tree, discard, or stash) during interactive patch selection. The discussion has converged on the immediate priority of unifying triage actions into a single session, but the scope, implementation path, and inclusion of stash as a deferral mechanism remain contested. Junio C Hamano’s latest reply refines the goal to a *minimal, reference-like* solution that avoids overloading existing commands (`git add -p`, `git checkout -p`) and explicitly includes stash as a viable deferral mechanism, provided it is housed in a command whose scope encompasses working-tree modifications.

Key technical details:
- Subsystems involved: `add--interactive` (Perl script or C rewrite in `add-interactive.c`), `apply` machinery (used by `checkout -p`), index manipulation logic (used by `add -p`), `git stash`, and potentially a new command or mode (e.g., `git triage -p` or `git add --triage`).
- New behavior:
  - **Unified triage workflow**: A single interactive session supporting at least three actions per hunk (stage, discard, keep) with the option to include stash as a fourth action (stage/stash/keep/discard). The workflow would avoid the need to switch between `git add -p` and `git checkout -p`.
  - **Command scope**: The solution should be implemented as a *new* command (e.g., `git triage -p`) or a new mode for an existing command (e.g., `git add --triage`), rather than extending `git add -p` or `git checkout -p`. This avoids overloading commands with working-tree-munging features and addresses Junio’s philosophical objection to extending `git add -p`. Peff’s suggestion of `git triage -p` as a separate command is now the most viable path forward, aligning with Junio’s latest stance.
  - **Stash as deferral mechanism**: Deferred hunks would be stashed (as in Dscho’s stash-mode proposal) rather than persisted in the working tree or ignored. Junio’s latest reply confirms that the "weirdness" of stash-mode (modifying the working tree via stash) is a design concern rather than a fundamental flaw, and the feature remains worth pursuing. The interaction with existing stash workflows (e.g., stash list management) remains an open question.
  - **UI considerations**: The solution should prioritize a minimal, prompt-loop interface (e.g., extending the existing `add--interactive` machinery) rather than a polished TUI. Basic UI improvements (e.g., navigable hunk selection) may still be relevant if the new command adopts a prompt-loop interface, but Junio’s latest reply suggests that UI polish is not a priority.
- Open questions:
  - **Implementation path**: Should the solution be a standalone command (e.g., `git triage -p`) or a mode for an existing command (e.g., `git add --triage`)? Peff’s suggestion of a standalone command (`git triage -p`) is now the most viable path, but the trade-offs (e.g., modularity vs. integration) remain unresolved.
  - **Stash integration**: How would stash-mode interact with existing stash workflows? Would it clutter the stash or interfere with other stash-based operations? What was the rationale for rejecting the March 2026 stash-mode patch, and do those concerns still apply?
  - **Command interface**: What would the new command’s interface look like (e.g., `git triage -p` vs. `git add --triage`)? How would it avoid the pitfalls of overloading existing commands while remaining intuitive?
  - **UI scope**: If the new command adopts a prompt-loop interface, would *basic* UI improvements (e.g., navigable hunk selection) be acceptable, or would they violate Junio’s "no competition" principle?
  - **Backwards compatibility**: Would the new command or mode introduce breaking changes or require users to adopt new workflows? How would it interact with existing commands (`git add -p`, `git checkout -p`, `git stash`)?
  - **External tool integration**: How would the new command interact with external tools like lazygit? Would it make Git’s interactive machinery more or less consumable?
  - **Advanced workflows**: Should the solution support advanced use cases (e.g., squashing hunks into older commits), or should these be deferred to external tools or future enhancements?
