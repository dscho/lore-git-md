Thread identity: Feature request for unified interactive patch selection in Git (`git add -p`/`git checkout -p` workflow enhancement). Originating author: Junio C Hamano. Thread type: design discussion (RFC).

Core problem or goal: Address the lack of a built-in workflow for handling "good but not yet ready" hunks (category 2) during interactive patch selection, while exploring broader use cases such as squashing hunks into arbitrary commits, moving them to new branches, or adopting more intuitive interfaces. The goal is to unify interactive patch selection workflows into a flexible session supporting staging, discarding, deferring, and potentially advanced operations (e.g., amending older commits, creating new branches, or visual/hunk-browsing interfaces), without overcomplicating the existing UI.

Current status: Conceptual discussion in early design phase; no patches or implementation sketches have been posted. The thread has expanded from Junio’s original proposal (stage/discard/defer) to include broader workflow possibilities (e.g., leveraging `git history`, intent-based commands, or TUI-like interfaces inspired by Fugitive/Magit). No decisions or agreements have been reached.

Key technical details:
- Subsystems involved: `add--interactive` (Perl script or C rewrite in `add-interactive.c`), `apply` machinery (used by `checkout -p`), index manipulation logic (used by `add -p`), and potentially `git history` (for rewriting commits), branch creation logic, or terminal UI frameworks.
- New behavior: Unified interactive session supporting at least three actions per hunk (stage, discard, defer), with potential extensions for squashing into older commits, moving hunks to new branches, or adopting a visual/hunk-browsing interface (e.g., inspired by Fugitive).
- Open questions: How to represent deferred hunks (persist in working tree, stash temporarily, or ignore until next session); whether this belongs in `add -p`, a new command (e.g., `git triage -p`), or modular intent-based commands (e.g., `git butler commit amend`); how to integrate with `git history` or other rewrite tools; how to design the UI (prompt-loop vs. TUI-like interface); and how to avoid complicating the existing patch-selection workflow.

Open questions and loose ends:
- How should deferred hunks be handled? Persist in working tree, stash, or ignore?
- Should this functionality be added to `add -p`, introduced as a new command (e.g., `git triage -p`), or split into modular intent-based commands (e.g., inspired by GitButler)?
- How to design the UI to balance flexibility and simplicity? Should Git adopt a TUI-like interface (e.g., inspired by Fugitive/Magit) or stick to its current lightweight prompt-loop design?
- What are the implications for the underlying `apply` and index manipulation logic?
- Can `git history` or similar tools be leveraged to support squashing hunks into older commits or moving them to new branches?
- Should the solution prioritize simplicity (e.g., stage/discard/defer only) or flexibility (e.g., supporting advanced workflows like amending arbitrary commits or visual interfaces)?

Knoble suggests Git could learn from this design but notes that emulating it might require a heavier interface (e.g., a full terminal UI). No specific implementation proposal for Git, but highlights the potential benefits of a more interactive, visual workflow over the current prompt-loop approach.

Related work:

- GitButler’s `but rub` command: Recently refactored into intent-based commands (e.g., `git butler branch create`, `git butler commit amend`), serving as a real-world example of modular workflow tooling.
- Fugitive (Vim plugin): Provides a visual, interactive interface for hunk selection, inspired by Magit (Emacs). Offers a concrete example of how a unified hunk-selection workflow might look and feel.
