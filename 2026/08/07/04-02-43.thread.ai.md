Thread identity: Feature request for unified interactive patch selection in Git (`git add -p`/`git checkout -p` workflow enhancement). Originating author: Junio C Hamano. Thread type: design discussion (RFC).

Core problem or goal: Address the lack of a built-in workflow for efficiently triaging hunks into three categories (stage, keep in working tree, or discard) during interactive patch selection. The discussion centers on three competing visions: (1) Junio C Hamano’s near-term goal of unifying triage actions (stage/discard/defer) into a single session while preserving Git’s existing prompt-loop UI and avoiding competition with external tools, (2) Patrick Steinhardt’s refined proposal to adopt *targeted* UI improvements (e.g., hierarchical, navigable hunk selection) to address core workflow gaps without building a "full UI" that competes with external tools like lazygit, and (3) Stefan Haller’s suggestion to avoid internal UI modernization entirely and rely on external tools for enhanced interfaces, with Git focusing on improving core APIs.

Current status: Conceptual discussion in early design phase; no patches or implementation sketches have been posted. The thread has converged on the immediate priority of unifying triage actions (stage/discard/defer) into a single session, but the scope of the solution remains contested. Junio’s latest reply reinforces that Git’s built-in workflows should be minimal, "usable but not pretty" features that serve as a reference implementation, ruling out larger UI efforts (e.g., a full TUI) but leaving room for incremental workflow fixes (e.g., extending `git add -p` to support "discard"). Patrick’s latest reply refines his earlier TUI proposal to focus on *basic* UI improvements (e.g., navigable hunk selection) as a middle ground, arguing that such changes would not significantly overlap with external tools. However, Junio’s position suggests that even these modest UI enhancements may be deemed too ambitious if they risk competing with external tools. Stefan’s external-tool proposal remains unchanged, with Junio’s reply aligning philosophically but not addressing the technical specifics of API improvements.

Key technical details:
- Subsystems involved: `add--interactive` (Perl script or C rewrite in `add-interactive.c`), `apply` machinery (used by `checkout -p`), index manipulation logic (used by `add -p`), `git history` (for rewriting commits), and potentially new lightweight dependencies for basic UI features (e.g., ncurses or alternatives for navigable hunk selection).
- New behavior:
  - **Junio’s proposal**: Unified interactive session supporting at least three actions per hunk (stage, discard, defer) within the existing prompt-loop UI. The "discard" action would operate on the working tree, while "stage" and "defer" would manipulate the index and working tree, respectively. Junio’s latest reply clarifies that this should be implemented as a minimal, reference-like feature, not a polished UI.
  - **Patrick’s refined proposal**: *Targeted* UI improvements to address core workflow gaps, such as hierarchical, navigable hunk selection (e.g., allowing users to move between hunks without restarting the prompt-loop). This would not constitute a "full UI" but would make `git add -p` more functional without overlapping significantly with external tools. The proposal avoids specifying implementation details (e.g., ncurses vs. lighter alternatives) but implies that even minimal UI enhancements could meaningfully improve usability.
  - **Stefan’s proposal**: No internal UI changes; instead, improve Git’s core APIs (e.g., `add--interactive`, `git history`) to make them more consumable by external tools like lazygit.
