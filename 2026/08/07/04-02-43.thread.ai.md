Thread identity: Feature request for unified interactive patch selection in Git (`git add -p`/`git checkout -p` workflow enhancement). Originating author: Junio C Hamano. Thread type: design discussion (RFC).

Core problem or goal: Address the lack of a built-in workflow for efficiently triaging hunks into three categories (stage, keep in working tree, or discard) during interactive patch selection, while exploring broader use cases such as squashing hunks into arbitrary commits, moving them to new branches, or adopting more intuitive interfaces. The goal is to unify interactive patch selection workflows into a flexible session supporting at least these three actions, with potential extensions for advanced operations (e.g., amending older commits, creating new branches, or visual/hunk-browsing interfaces), without overcomplicating the existing UI.

Current status: Conceptual discussion in early design phase; no patches or implementation sketches have been posted. The thread has narrowed its focus to a concrete, implementable goal: unifying triage actions (stage/discard/defer) into a single session, as proposed by Junio. The discussion now distinguishes between two orthogonal concerns: (1) the core workflow friction (two-step triage via `git add -p` and `git checkout -p`) and (2) UI limitations (linear prompt-loop vs. TUI-like interfaces). No decisions or agreements have been reached, but the scope of the immediate problem is now clearer.

Key technical details:
- Subsystems involved: `add--interactive` (Perl script or C rewrite in `add-interactive.c`), `apply` machinery (used by `checkout -p`), index manipulation logic (used by `add -p`), and potentially `git history` (for rewriting commits), branch creation logic, or terminal UI frameworks.
- New behavior: Unified interactive session supporting at least three actions per hunk (stage, discard, defer), with potential extensions for squashing into older commits, moving hunks to new branches, or adopting a visual/hunk-browsing interface (e.g., inspired by Fugitive). Junio proposes extending `git add -p` to support a "discard" action alongside "stage" and "defer," eliminating the need for a separate `git checkout -p` step.
- Open questions: How to represent deferred hunks (persist in working tree, stash temporarily, or ignore until next session); whether this functionality belongs in `add -p` (as Junio proposes), a new command (e.g., `git triage -p`), or modular intent-based commands (e.g., inspired by GitButler); how to integrate with `git history` or other rewrite tools; how to design the UI (incremental extension of the prompt-loop vs. TUI-like interface); and how to avoid complicating the existing patch-selection workflow.
