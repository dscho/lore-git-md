Thread identity: Feature request for unified interactive patch selection in Git (`git add -p`/`git checkout -p` workflow enhancement). Originating author: Junio C Hamano. Thread type: design discussion (RFC).

Core problem or goal: Address the lack of a built-in workflow for efficiently triaging hunks into three categories (stage, keep in working tree, or discard) during interactive patch selection. The discussion now centers on three competing visions: (1) Junio C Hamano’s near-term goal of unifying triage actions (stage/discard/defer) into a single session while preserving Git’s existing prompt-loop UI, (2) Patrick Steinhardt’s proposal to adopt a hierarchical TUI (text-based user interface) inspired by Jujutsu (JJ) for non-linear selection, and (3) Stefan Haller’s suggestion to avoid internal UI modernization entirely and rely on external tools (e.g., lazygit) for enhanced interfaces, with Git focusing on improving core APIs. The core friction—eliminating the need for separate `git add -p` and `git checkout -p` steps—remains, but the scope and locus of the solution are contested, with Patrick’s latest reply reframing the discussion around *where to draw the line* between Git’s built-in workflows and external tooling.

Current status: Conceptual discussion in early design phase; no patches or implementation sketches have been posted. The thread has converged on the immediate priority of unifying triage actions (stage/discard/defer) into a single session, but Patrick Steinhardt’s latest reply introduces nuance by distinguishing between *core workflow improvements* (e.g., navigable hunk selection) and *full UI modernization* (e.g., a TUI for history editing). Junio’s position reinforces the consensus on the *mechanism* (single command set for all three actions) as the focus, while Patrick argues that even basic UI enhancements (e.g., hierarchical navigation) are necessary to solve the workflow problem. Stefan’s reply continues to challenge the necessity of either approach, advocating for external tools. No resolution has been reached on which path to prioritize, but Patrick’s framing suggests a middle ground: Git should address clear gaps in its core workflows (e.g., unified hunk triage) while deferring larger UI efforts (e.g., a TUI for `git history`) to external tools or future discussions.

Key technical details:
- Subsystems involved: `add--interactive` (Perl script or C rewrite in `add-interactive.c`), `apply` machinery (used by `checkout -p`), index manipulation logic (used by `add -p`), `git history` (for rewriting commits), and potentially new dependencies (ncurses or similar for TUI support).
- New behavior:
  - **Junio’s proposal**: Unified interactive session supporting at least three actions per hunk (stage, discard, defer) within the existing prompt-loop UI. The "discard" action would operate on the working tree, while "stage" and "defer" would manipulate the index and working tree, respectively.
  - **Patrick’s proposal**: Hierarchical, navigable TUI for selecting changes (files → hunks → lines), replacing the linear prompt-loop. This would enable non-linear workflows (e.g., jumping between hunks, toggling selections out of order) and could extend to other interactive commands (e.g., `git history` for reordering commits). Patrick’s latest reply clarifies that this is not an all-or-nothing proposition; even basic UI improvements (e.g., navigable hunk selection) could address core workflow gaps without requiring a full TUI rewrite.
  - **Stefan’s proposal**: No internal UI changes; instead, improve Git’s core APIs (e.g., `add--interactive`, `git history`) to make them more consumable by external tools like lazygit, which would handle the presentation layer.
- Open questions:

  - Whether to prioritize simplicity (stage/discard/defer only) or flexibility (e.g., supporting advanced workflows like amending arbitrary commits or visual interfaces).

    - How to maintain backward compatibility with the existing prompt-loop UI if a TUI is introduced?

    - Where should the line be drawn between Git’s built-in workflows and external tooling? Patrick’s latest reply suggests that *basic* UI improvements (e.g., navigable hunk selection) are within scope, while *full* UI modernization (e.g., a TUI for history editing) is not.

- **Patrick Steinhardt**: Proposes a pragmatic middle ground: Git should address *core workflow gaps* (e.g., unified hunk triage) with *basic* UI improvements (e.g., hierarchical, navigable hunk selection) but avoid building a "full UI" (e.g., a TUI for history editing). - **Stefan Haller**: Questions whether Git should build any interactive UI at all, instead advocating for external tools (e.g., lazygit) to handle presentation. Argues that Git should focus on core functionality and improve its APIs to better support external tooling, rather than duplicating the work of specialized tools. His position remains unchanged: Git’s role is to provide robust plumbing, not polished UIs.
