Thread identity: Feature request for unified interactive patch selection in Git (`git add -p`/`git checkout -p` workflow enhancement). Originating author: Junio C Hamano. Thread type: design discussion (RFC).

Core problem or goal: Address the lack of a built-in workflow for efficiently triaging hunks into three categories (stage, keep in working tree, or discard) during interactive patch selection. The discussion centers on three competing visions: (1) Junio C Hamano’s near-term goal of unifying triage actions (stage/discard/defer) into a single session while preserving Git’s existing prompt-loop UI and avoiding competition with external tools, (2) Patrick Steinhardt’s refined proposal to adopt *targeted* UI improvements (e.g., hierarchical, navigable hunk selection) to address core workflow gaps without building a "full UI" that competes with external tools, and (3) Stefan Haller’s suggestion to avoid internal UI modernization entirely and rely on external tools for enhanced interfaces, with Git focusing on improving core APIs. Johannes Schindelin has revived a previously rejected patch series (`[PATCH] add -p: introduce stash mode`, March 2026) that proposes a `--stash` option for `git add -p` to defer hunks via the stash, offering a concrete implementation path that aligns with Junio’s core goal of unified triage but uses the stash as the deferral mechanism. Jeff King (Peff) has now weighed in, suggesting that the stash-mode functionality could be implemented more cleanly under a separate command (e.g., `git triage -p`) to avoid overloading `git add -p` and address concerns about unintuitive working tree modifications.

Current status: Conceptual discussion in early design phase; no patches or implementation sketches have been posted for the current thread, but Dscho’s revival of the stash-mode patch provides a concrete starting point. The thread has converged on the immediate priority of unifying triage actions (stage/discard/defer) into a single session, but the scope and implementation path remain contested. Junio’s latest reply reinforces that Git’s built-in workflows should be minimal, "usable but not pretty" features that serve as a reference implementation, ruling out larger UI efforts (e.g., a full TUI) but leaving room for incremental workflow fixes (e.g., extending `git add -p` to support "discard"). Patrick’s latest reply refines his earlier TUI proposal to focus on *basic* UI improvements (e.g., navigable hunk selection) as a middle ground, arguing that such changes would not significantly overlap with external tools. Peff’s reply introduces a new dimension: the stash-mode functionality could be housed under a separate command (e.g., `git triage -p`) to avoid overloading `git add -p` and address concerns about unintuitive working tree modifications. This suggestion may bridge the gap between Junio’s minimalism and Dscho’s stash-mode proposal, offering a cleaner implementation path that avoids philosophical concerns about command scope. Stefan’s external-tool proposal remains unchanged, with Junio’s reply aligning philosophically but not addressing the technical specifics of API improvements.

Key technical details:
- Subsystems involved: `add--interactive` (Perl script or C rewrite in `add-interactive.c`), `apply` machinery (used by `checkout -p`), index manipulation logic (used by `add -p`), `git stash` (for Dscho’s stash-mode proposal), `git history` (for rewriting commits), and potentially new lightweight dependencies for basic UI features (e.g., ncurses or alternatives for navigable hunk selection).
- New behavior:
  - **Junio’s proposal**: Unified interactive session supporting at least three actions per hunk (stage, discard, defer) within the existing prompt-loop UI. The "discard" action would operate on the working tree, while "stage" and "defer" would manipulate the index and working tree, respectively. Junio’s latest reply clarifies that this should be implemented as a minimal, reference-like feature, not a polished UI.
  - **Patrick’s refined proposal**: *Targeted* UI improvements to address core workflow gaps, such as hierarchical, navigable hunk selection (e.g., allowing users to move between hunks without restarting the prompt-loop). This would not constitute a "full UI" but would make `git add -p` more functional without overlapping significantly with external tools. The proposal avoids specifying implementation details (e.g., ncurses vs. lighter alternatives) but implies that even minimal UI enhancements could meaningfully improve usability.
  - **Dscho’s stash-mode proposal**: Extend `git add -p` with a `--stash` option to defer hunks by stashing them, unifying triage actions (stage/stash/discard) in a single session. Deferred hunks would persist in the stash, not the working tree, sidestepping the open question of how to represent them (persist vs. stash vs. ignore). The approach is a lightweight extension of the existing `add--interactive` machinery, requiring no new UI or dependencies.
  - **Peff’s suggestion**: Implement the stash-mode functionality under a separate command (e.g., `git triage -p`) to avoid overloading `git add -p` and address concerns about unintuitive working tree modifications. This would preserve the unified triage workflow while keeping the implementation clean and modular.
  - **Stefan’s proposal**: No internal UI changes; instead, improve Git’s core APIs (e.g., `add--interactive`, `git history`) to make them more consumable by external tools like lazygit.
