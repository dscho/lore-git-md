Thread identity: Feature request for unified interactive patch selection in Git (`git add -p`/`git checkout -p` workflow enhancement). Originating author: Junio C Hamano. Thread type: design discussion (RFC).

Core problem or goal: Address the lack of a built-in workflow for efficiently triaging hunks into three categories (stage, keep in working tree, or discard) during interactive patch selection. The discussion now spans two competing visions: (1) Junio C Hamano’s near-term goal of unifying triage actions (stage/discard/defer) into a single session while preserving Git’s existing prompt-loop UI, and (2) Patrick Steinhardt’s proposal to adopt a full TUI (text-based user interface) inspired by Jujutsu (JJ), enabling hierarchical navigation of changes (files → hunks → lines) and non-linear selection. The core friction remains the same—eliminating the need for separate `git add -p` and `git checkout -p` steps—but the scope of the solution is now contested.

Current status: Conceptual discussion in early design phase; no patches or implementation sketches have been posted. The thread has converged on the immediate priority of unifying triage actions (stage/discard/defer) into a single session, but Patrick Steinhardt’s proposal introduces a significant divergence: whether to extend the existing prompt-loop (Junio’s approach) or replace it with a TUI (Patrick’s approach). Junio’s latest reply reinforces the consensus on the *mechanism* (single command set for all three actions) as the focus, while Patrick’s email reframes the discussion around UI modernization as the prerequisite for solving the workflow problem. No resolution has been reached on which path to prioritize.

Key technical details:
- Subsystems involved: `add--interactive` (Perl script or C rewrite in `add-interactive.c`), `apply` machinery (used by `checkout -p`), index manipulation logic (used by `add -p`), `git history` (for rewriting commits), and potentially new dependencies (ncurses or similar for TUI support).
- New behavior:
  - **Junio’s proposal**: Unified interactive session supporting at least three actions per hunk (stage, discard, defer) within the existing prompt-loop UI. The "discard" action would operate on the working tree, while "stage" and "defer" would manipulate the index and working tree, respectively.
  - **Patrick’s proposal**: Hierarchical, navigable TUI for selecting changes (files → hunks → lines), replacing the linear prompt-loop. This would enable non-linear workflows (e.g., jumping between hunks, toggling selections out of order) and could extend to other interactive commands (e.g., `git history` for reordering commits).
- Open questions:
  - How to represent deferred hunks (persist in working tree, stash temporarily, or ignore until next session).
  - Whether the "discard" action belongs in `git add -p` (Junio’s preference), a new command (e.g., `git triage -p`), or modular intent-based commands (e.g., inspired by GitButler).
  - How a "discard" action would interact with the underlying `apply` and index manipulation logic.
  - Whether to prioritize simplicity (stage/discard/defer only) or flexibility (e.g., supporting advanced workflows like amending arbitrary commits or visual interfaces).
  - **New questions from Patrick’s proposal**:
    - Should Git adopt ncurses or a similar library as a dependency for TUI support?
    - How to maintain backward compatibility with the existing prompt-loop UI if a TUI is introduced?
    - Should the TUI redesign be a standalone effort or part of a broader modernization of Git’s interactive commands (e.g., `git rebase -i`, `git history`)?

Open questions and loose ends:
- How should deferred hunks be handled? Persist in working tree, stash, or ignore?
- Should the solution extend `git add -p` (Junio’s preference), introduce a new command, or adopt intent-based commands (e.g., GitButler’s `but rub` refactor)?
- Can `git history` or similar tools be leveraged to support squashing hunks into older commits or moving them to new branches, or is this a separate concern?
- Should the project prioritize incremental workflow fixes (Junio’s approach) or invest in a larger UI modernization effort (Patrick’s proposal)?
- What are the trade-offs of introducing ncurses as a dependency, and is the project willing to accept it?
- How would a TUI-based redesign interact with Git’s existing interactive machinery (e.g., `add--interactive`, `add-interactive.c`)?

Participant positions:
- **Junio C Hamano (author)**: Proposed the enhancement, motivated by a real workflow friction (stage/discard/defer). Narrowed the focus to unifying triage actions into a single session (e.g., extending `git add -p` to support "discard"), framing UI improvements (e.g., TUI-like interfaces) as a separate, longer-term concern. His latest reply reinforces consensus on the *mechanism* (single command set) as the immediate priority, not the UI.
- **Christian Couder**: Expanded the scope to include advanced use cases (squashing hunks into older commits, moving hunks to new branches) and suggested leveraging `git history` or adopting intent-based commands (e.g., GitButler’s `but rub` refactor). Advocates for flexibility but acknowledges the need to balance power with usability. No specific UI or implementation proposal yet.
- **D. Ben Knoble**: Clarified that the key takeaway from Fugitive (a Vim plugin) is its *unified workflow* (single command set for stage/unstage/revert), not its visual or TUI-like interface. This aligns with Junio’s core goal of enabling triage in a single session, regardless of UI style. Knoble’s framing emphasizes that the underlying mechanism (a single command set for all three actions) is more important than the specific UI (prompt-loop vs. TUI).
- **Patrick Steinhardt**: Proposes a more ambitious UI redesign, advocating for a full TUI (ncurses-based) to replace Git’s linear prompt-loop model. Cites Jujutsu’s `jj split --interactive` as a superior model, where users can navigate a hierarchical view of changes (files → hunks → lines) and toggle selections non-linearly. Argues that this approach would address both workflow limitations (stage/discard/defer) and UI frustrations (linear prompts) in one stroke. His position introduces a potential tension between incremental workflow fixes and a broader UI modernization effort.

Related work:
- `git history`: Experimental command for rewriting history, potentially relevant for squashing hunks into older commits.
- GitButler’s `but rub` command: Recently refactored into intent-based commands (e.g., `git butler branch create`, `git butler commit amend`), serving as a real-world example of modular workflow tooling.
- Fugitive (Vim plugin): Provides a unified set of commands for moving hunks between staged, unstaged, and reverted states, offering a concrete example of how a triage workflow might be implemented. The value lies in its *mechanism* (single command set), not its interface.
- Jujutsu (JJ): Patrick Steinhardt’s primary inspiration for the TUI proposal. JJ’s `jj split --interactive` command allows hierarchical navigation of changes (files → hunks → lines) and non-linear selection, which he argues is superior to Git’s linear prompt-loop model.
