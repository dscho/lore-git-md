This is the second patch in Christian Couder’s five-patch series introducing `uploadpack.lazyFetchTrusted`, a server-side configuration variable that lets operators mark repositories as trusted for lazy fetching. The series replaces the earlier `GIT_NO_LAZY_FETCH=fromAccepted` proposal and is a direct response to the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration.

This patch extracts and generalizes the allowlist-checking logic from Git’s existing `safe.directory` machinery into a new `path_allowlist_apply()` helper in `setup.c`. The helper is designed to be reusable: it takes a configuration key, value, target path, and an output pointer, and sets the output to 1 if the target path matches the allowlist pattern. The patch also adds an `allow_dot` argument (though not yet used) to handle repository paths that start with `.`, making the helper more flexible than the original `safe.directory` code.

The refactoring is clean and well-motivated. The commit message explains the purpose clearly, and the code changes are straightforward: the existing logic is lifted verbatim from `safe_directory_cb()` into the new helper, with minor adjustments for genericity. No behavior changes are introduced; this is purely preparatory work for the next patch, which will use the helper to implement the `uploadpack.lazyFetchTrusted` configuration.

The patch touches only `setup.c` and is small (59 insertions, 48 deletions). It passes CI, indicating no integration issues. The helper’s design—taking an output pointer rather than returning a value—matches the pattern used elsewhere in Git for configuration callbacks, making it a natural fit for the codebase.

This is a solid, uncontroversial refactoring that sets up the core trust mechanism for the series. It doesn’t address the security objection directly but provides the infrastructure needed to do so in the next patch. If the series as a whole gains traction, this patch is likely to be merged as-is.
