This is the fourth patch in Pablo Sabater’s ten-patch GSoC series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The series is now at v5, feature-complete, and ready for merging.

This patch replaces the `struct object_info` array used to store remote-object-info results with a dedicated `struct fetch_object_info_results`. The old design allocated one `object_info` per object per attribute, even though `fetch_object_info()` never calls `read_object_info()` and thus has no need for the extended parameter pointers that `object_info` provides. The new struct holds only the fields the caller actually wants (currently just `size`, with `type` coming in a later patch), using a single array per attribute and a bitmask to indicate which fields are requested. The caller releases the arrays with `free_fetch_object_info_results()`.

The patch also drops the `object_info_options` string list and `remote_atom_map[]`, which existed only to map protocol option strings back into atom names. Instead, the client now builds the list of allowed atoms directly from the result arrays, simplifying the code and removing about 30 lines. The final `else` in `fetch_object_info()`—previously unreachable—is converted from a `BUG()` to a `die()`, since an unknown attribute is now a protocol violation rather than an internal error.

The change is purely internal and has no user-visible behavior changes. It touches seven files (`builtin/cat-file.c`, `fetch-object-info.c`, `fetch-object-info.h`, `object-file.c`, `odb.h`, `transport.c`, and `transport.h`), updating function signatures and call sites to use the new struct. The patch is mechanical, well-motivated, and uncontroversial; Junio has already noted that the removal of `remote_atom_map[]` aligns with the new design and does not require changes. All tests pass, and the series remains on track for integration.
