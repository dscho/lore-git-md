This is a five-patch feature series introducing `uploadpack.lazyFetchTrusted`, a new protected configuration variable that allows server operators to explicitly mark repositories as trusted for lazy fetching. The series is a direct response to the unresolved security objections raised against Christian Couder’s earlier `GIT_NO_LAZY_FETCH=fromAccepted` proposal, replacing it with a server-side control mechanism modeled after Git’s `safe.directory` configuration.

The core idea is to let operators declare which repositories are safe to lazy-fetch from by setting `uploadpack.lazyFetchTrusted` in global or system scope. This sidesteps the earlier debate about client-side negotiation of promisor remotes by shifting trust decisions entirely to the server operator. The served repository itself cannot influence the setting, addressing the primary security concern that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration.

Patch 1 is a refactoring carried over from the previous series, extracting `lazy_fetch_objects()` from the promisor-remote code. Patches 2 and 3 generalize the `safe.directory` allowlist machinery into a reusable `path_allowlist_apply()` helper, adding an `allow_dot` argument to handle repository paths. Patch 4 reads the new configuration variable, and patch 5 wires it into `upload-pack` to disable `GIT_NO_LAZY_FETCH` (i.e., permit lazy fetching) only for trusted repositories. The implementation touches the promisor-remote subsystem, `setup.c`, documentation, and adds a new test script (`t/t5710-promisor-remote-capability.sh`).

The series explicitly targets both protocol v0/v1 and v2, unlike the earlier `fromAccepted` proposal which was v2-only. It also introduces no on-disk format changes and maintains backward compatibility: the default behavior remains unchanged (lazy fetching disabled by default), and the new configuration is opt-in. CI tests have passed, indicating clean integration with the existing codebase.

This is a deliberate pivot from the earlier approach, positioning the feature as a pragmatic security improvement for corporate environments where server operators need fine-grained control over lazy fetching. The unresolved security objection from brian m. carlson—who argued that any expansion of lazy-fetching flexibility increases exposure to untrusted repositories—remains relevant but is now addressed by the server-side trust model. Whether this satisfies the objection will likely be the central point of discussion. The series also defers usability improvements (e.g., a configuration variable instead of an environment variable) to future work, focusing first on establishing the trust mechanism.
