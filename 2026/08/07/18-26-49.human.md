This is a refactoring patch in the Bloom filter subsystem, part of Toon Claes’s v2 series to speed up the experimental `git last-modified` command. The patch adds a new helper function, `bloom_filter_contains_any_vec()`, which checks whether *any* key in a given vector is present in a Bloom filter, rather than requiring *all* keys to be present (the behavior of the existing `bloom_filter_contains_vec()`).

The motivation is straightforward: when querying whether a path or any of its parent directories might have changed in a commit, the caller needs to know if *any* of the corresponding Bloom filter keys are present, not just the key for the path itself. For example, if a commit changed `a/b/d`, the Bloom filter will contain keys for `a/b/d`, `a/b`, and `a`. A query for `a/b/c` should return "possibly changed" because `a/b` and `a` are present, even though `a/b/c` is not. The new helper provides this logic, returning `1` if any key in the vector is present and `0` only if none are.

The implementation is simple: it iterates through the key vector and returns as soon as it finds a key that is present in the filter. The function is exposed in `bloom.h` with a clear docstring, and there are no callers yet—those will be added in a later patch in the series. The patch is clean, well-explained, and directly addresses a gap in the Bloom filter API that the `git last-modified` optimization needs. No behavioral changes are introduced, and the new helper is purely additive. This looks like a sensible, low-risk refactoring that enables the performance gains in the rest of the series.
