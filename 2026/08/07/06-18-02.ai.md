This is a performance patch series reintroducing a `writev(3p)`-like wrapper for Git, now in its second iteration (v2). The series aims to reduce system call overhead by batching writes in low-level I/O operations, specifically targeting pktline transmission in `sideband.c` and cat-blob responses in `fast-import.c`. The wrapper was originally merged in Git 2.54 but reverted due to platform compatibility issues (NonStop, CMake); this version incorporates fixes for those issues and demonstrates broader applicability.

The key change in v2 is a simplification of the compatibility wrapper: instead of attempting to write all `iovec` entries in a loop (which could lead to torn writes on platforms without `writev(2)`), it now writes only the first non-empty `iovec`. This restores the non-interleaving property of `write(3p)` and avoids interleaving even on platforms without `writev(2)`, addressing a forward-compatibility concern raised by Johannes Sixt. The change also removes the need for overflow checks in the wrapper, making the code cleaner and safer. Junio C Hamano accepted this tweak, describing it as "clever" and noting it simplifies the wrapper significantly.

The series touches 12 files, including `compat/writev.c` (new), `wrapper.{c,h}`, `sideband.c`, `builtin/fast-import.c`, and build system files (`config.mak.uname`, `CMakeLists.txt`, `meson.build`). It introduces two new functions: `git_write_gather()` and `git_write_gather_or_die()` (the name `git_writev()` was dropped to avoid implying POSIX semantics). The API is designed as a two-level abstraction: a Git-specific wrapper that platforms can implement either via `writev(2)` or as a series of `write(2)` calls, with explicit documentation that emulation may be non-atomic. The compatibility wrapper’s behavior now matches `write(2)` by writing only the first `iovec`, ensuring no interleaving occurs.

All technical design and correctness issues from v1 have been resolved. The integer-overflow concern raised by Simon Richter was addressed by Junio C Hamano’s confirmation of existing bounds-checking safety and the wrapper’s simplification. The API naming and architectural questions (e.g., whether atomicity is required) were resolved by Johannes Sixt and Junio C Hamano, who confirmed that Git’s pktline and cat-blob use cases do not require atomicity and are inherently single-writer scenarios. The series is now technically complete and awaits Junio C Hamano’s final assessment of whether the performance gains justify the complexity.
