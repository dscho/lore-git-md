This is a **feature request** from Junio C Hamano proposing an enhancement to the interactive patch selection workflow in Git.

The email describes a common pain point when using `git add -p` (interactive staging) and `git checkout -p` (interactive discarding of changes). Currently, these commands operate in isolation: `add -p` lets users stage hunks (category 1: "good"), while `checkout -p` lets users discard hunks (category 3: "bogus"). However, there’s no built-in way to handle hunks that are "good but not yet ready" (category 2) in a single session. Junio’s workaround—editing hunks into no-ops during `add -p`—is clunky and lacks a proofreading step before application.

The proposal is to unify these workflows into a single interactive session where users can choose, for each hunk, whether to stage it, discard it, or defer it (e.g., by marking it as "not ready"). This would address the gap for category 2 hunks and streamline the process of triaging working tree changes. The email doesn’t include a patch or implementation sketch, so this is purely a conceptual discussion at this stage.

Key technical context for follow-up discussion:
- The underlying machinery is the `add--interactive` Perl script (or its C rewrite in `add-interactive.c`), which powers both `add -p` and `checkout -p`.
- The `apply` machinery (used by `checkout -p`) and the index manipulation logic (used by `add -p`) would need to be coordinated to support deferred hunks.
- A likely point of contention is how to represent deferred hunks—whether they should persist in the working tree, be stashed temporarily, or simply ignored until the next session.

Junio’s request is well-motivated and reflects a real workflow friction, but the implementation would require careful design to avoid complicating the existing patch-selection UI. The thread may attract proposals for alternative approaches (e.g., a new `git triage -p` command) or debates about whether this belongs in `add -p` at all.
