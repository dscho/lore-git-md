This is a **design discussion reply** in the ongoing thread about enhancing Git’s interactive patch selection workflow. Christian Couder responds to Junio’s proposal by expanding the scope of the problem and suggesting additional use cases that a unified interactive session could support.

Christian raises a key question: what if a user wants to *squash* a hunk into an earlier commit (e.g., `HEAD~2`) or move it to a new commit on a separate branch? This extends Junio’s original three categories (stage, discard, defer) to include more advanced workflows, such as amending arbitrary commits or creating new branches mid-session. He suggests leveraging recent work on `git history` (the experimental command for rewriting history) to implement these cases, implying that the underlying machinery for moving hunks across commits or branches might already exist or could be adapted.

He also references GitButler’s `but rub` command, which was recently refactored into more explicit, intent-based commands (e.g., `git butler branch create`, `git butler commit amend`). This serves as a real-world example of a tool that already addresses some of these workflows, albeit in a different form. Christian’s point is that Git’s solution should aim for flexibility without becoming overly complex—balancing power with usability.

The reply does not propose a specific implementation or UI design, but it broadens the discussion by highlighting that the original proposal (stage/discard/defer) might be too narrow. Future replies may debate whether these advanced cases belong in the same interactive session or should be handled by separate commands (e.g., `git history edit` for squashing into older commits). This could also spark discussion about whether Git should adopt a more modular approach, similar to GitButler’s intent-based commands, rather than overloading `add -p` with additional functionality.
