This is the fourth patch in Christian Couder’s six-patch series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators mark repositories as trusted for lazy fetching. The series is a deliberate pivot from the earlier `GIT_NO_LAZY_FETCH=fromAccepted` proposal, shifting trust decisions from the client to the server to address security objections.

This patch wires up the configuration machinery. It adds a new `upload_pack_lazy_fetch_trusted()` function that reads the `uploadpack.lazyFetchTrusted` variable from protected configuration files (global or system scope), checks whether the current repository’s path is in the allowlist using the reusable `path_allowlist_apply()` helper introduced in earlier patches, and returns a boolean result. The function is exported in `upload-pack.h` for use in the next patch, which will integrate it into the `upload-pack` process to disable `GIT_NO_LAZY_FETCH` (i.e., permit lazy fetching) only for trusted repositories.

The implementation is straightforward: it normalizes the repository path with `real_pathdup()`, delegates the allowlist check to the existing helper (passing `false` for `allow_dot` to reject non-absolute paths), and frees the allocated path. The configuration callback is registered via `git_protected_config()`, ensuring the variable is read only from protected files. No behavior changes are introduced yet; this patch only provides the plumbing.

The patch is clean and well-scoped, touching only `upload-pack.c` and `upload-pack.h`. It builds directly on the refactoring in patches 1–3, which extracted and generalized the allowlist logic. The commit message clearly states the purpose and defers integration to the next patch, making the progression easy to follow. No substantive review feedback has appeared yet, but the patch looks technically sound and aligns with the series’ goal of establishing a server-side trust mechanism. The unresolved security objection from brian m. carlson remains the main open question, but this patch does not engage with it directly—it simply implements the agreed-upon design.
