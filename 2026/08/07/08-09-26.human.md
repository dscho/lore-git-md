This is the fourth and final patch in Vincent Mailhol’s v2 series adding Bash completion for the new `git history` command. The thread has already converged on a technical compromise, and this email is a focused discussion about a lingering maintainability concern in the completion logic.

The patch itself is uncontroversial: it wires up completion for `git history` subcommands (`--empty`, `--update-refs`, and `split` pathspecs) using Git’s existing parse-options infrastructure. The core logic—requiring exactly one revision argument before any options or pathspecs—is now well-tested and aligns with the command’s design. The series is effectively ready to merge once the last loose end is tied off.

That loose end is the `__git_history_has_revision` helper, which scans the command line to determine whether a revision has been provided. The helper hardcodes options like `--empty` and `--update-refs` that take arguments, and Patrick Steinhardt has repeatedly flagged this as fragile. Vincent acknowledges the risk but argues that the alternative—ignoring the `--option <value>` syntax entirely—would be even more user-hostile, since it would break completion for any new option that doesn’t use the `--option=<value>` form. His preference is to keep the current implementation, which works today and can be extended later via a `case` block for edge cases, but he is open to a v3 that drops support for `--option <value>` if that’s the project’s preference.

The trade-off is now clearly framed: short-term correctness versus long-term maintainability. Neither side is digging in; this is a pragmatic discussion about which compromise is least bad. The series will likely land in its current form, with the understanding that the helper may need revisiting as `git history` gains new options (e.g., for commit signing or notes handling). For now, the patch is a clean, well-tested addition that fills a real gap in the user experience.
