This is a follow-up in the ongoing discussion about decoupling explicit branch fetches from the default fetch refspec in `git fetch`. Junio C Hamano expands on his earlier suggestion to use the existing `--refmap` option as a foundation, sketching a possible workflow where `git fetch` could operate in a "matching" mode similar to `git push`.

Junio clarifies that `--refmap` was designed to separate two concerns: (A) the mapping between remote and local ref names, and (B) which refs are actually transferred. He proposes that `git fetch` could learn a "matching" mode (analogous to `push.default = matching`) where it would fetch only the refs that correspond to existing remote-tracking branches, using the fetch refmap to determine the mapping. This would allow users to maintain a restricted default fetch set while still automatically mapping explicitly fetched branches to their remote-tracking refs. For example, fetching a new branch (`git fetch origin a-new-topic`) would create the corresponding remote-tracking ref, and subsequent fetches would include it in the default set.

The proposal remains conceptual, with no implementation details or patches yet. Junio acknowledges uncertainty about the final design but suggests this direction as a plausible way to address the original problem without breaking backward compatibility. The discussion is still focused on exploring options rather than settling on a specific solution. No new objections or endorsements from other reviewers have appeared in this reply.
