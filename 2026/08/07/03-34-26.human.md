This is the second patch in Patrick Steinhardt’s six-patch series making Git’s on-disk object database (ODB) structures pluggable. The series is part of the ongoing ODB abstraction effort and is now in its final form, with all substantive feedback addressed.

This patch detangles the loading of loose object maps from repository setup. Loose object maps are used when a repository is configured with a compatibility hash algorithm (e.g., SHA-256 repositories that also support SHA-1). Previously, the code unconditionally downcast the primary ODB to the "files" backend when loading these maps, which would trigger a BUG if a different backend type were ever used with a compatibility hash. The patch moves the logic into the loose backend itself, making the loose object map an internal implementation detail. This fixes the latent correctness bug and removes the awkward intermixing of repository configuration and ODB initialization.

The change is small but important: it moves the `should_use_loose_object_map()` guard into the loose backend’s initialization (`odb_source_loose_new()`), exposes `loose_object_map_load()` as a public function, and removes the now-redundant call to `repo_read_loose_object_map()` from `repo_set_compat_hash_algo()`. The patch touches five files (`loose.c`, `loose.h`, `odb/source-loose.c`, `repository.c`, and `setup.c`) and is uncontroversial. Both Justin Tobler and Toon Claes have reviewed and approved the series, and Junio’s "What’s cooking" report lists it as ready for `next`.

This is a well-motivated refactoring that cleans up a latent bug without changing user-visible behavior. The commit message clearly explains the problem and the fix, and the patch itself is surgical. If you care about ODB internals or the ongoing abstraction effort, this is worth a quick skim; otherwise, it’s safe to assume it’s in good shape and moving forward.
