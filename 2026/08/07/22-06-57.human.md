This is a bugfix patch in Pablo Sabater’s GSoC series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder. The patch targets the `fetch-object-info` subsystem, which handles remote object metadata queries.

The change addresses a protocol robustness issue: the current implementation does not validate whether the server sends exactly the number of object-info responses the client requested. A server that sends too few responses leaves the end of the result array uninitialized, while one that sends too many leaves extra packets unread. On stateless transports, `check_stateless_delimiter()` catches the latter case, but stateful transports (e.g., git://) silently ignore the extra data. The patch adds explicit checks for both conditions, calling `die()` if the server violates the protocol invariants.

The fix is straightforward: the loop now reads each packet explicitly (rather than relying on the loop condition) and fails immediately if it encounters anything other than `PACKET_READ_NORMAL` before reading all expected objects. After the loop, it verifies that the next packet is a flush, ensuring no extra data remains. The commit message clearly explains the motivation and the defensive programming rationale.

This patch is part of a larger, now feature-complete series that has addressed all prior review feedback. Junio C Hamano explicitly endorsed this patch as ready to merge in his latest reply, noting it is mechanical and uncontroversial. The change is isolated to `fetch-object-info.c` and does not affect other subsystems. Test coverage for the new checks is not added here, but the series expands test coverage elsewhere. The patch aligns with Git’s defensive programming practices and is a necessary robustness improvement for the remote-object-info feature.
