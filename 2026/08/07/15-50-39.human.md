This is a **design discussion contribution** in the ongoing thread about improving Git’s interactive patch selection workflow. Junio C Hamano responds to D. Ben Knoble’s suggestion of adopting a more visual, TUI-like interface (inspired by Fugitive) by clarifying that the core issue he wants to address is *not* the linear, one-hunk-at-a-time prompt-loop itself, but rather the *directional limitation* of how modifications flow between the working tree, index, and discard pile.

Junio acknowledges that the current `git add -p`/`git checkout -p` workflow forces users into an awkward two-pass process: first staging or deferring hunks, then later discarding the unwanted ones in a separate step. This is error-prone and inefficient, especially for hunks that are clearly unwanted (the "third kind") but must be deferred during the first pass. He argues that even within the existing prompt-loop model, Git could support a triage workflow where users label hunks as *stage*, *keep*, or *discard* in a single pass, eliminating the need for a follow-up `git checkout -p` step.

The email keeps the discussion grounded in the original problem—workflow friction—while gently pushing back on the idea that a heavier interface (like a TUI) is the only solution. Junio’s focus remains on simplicity and incremental improvement, suggesting that a better workflow could emerge without abandoning Git’s lightweight, scriptable design. This sets up a natural tension in the thread: should Git prioritize a minimalist, prompt-based solution, or is this an opportunity to explore richer interfaces? The answer will likely shape how ambitious any eventual implementation becomes.
