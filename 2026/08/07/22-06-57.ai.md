This is a bugfix patch in Pablo Sabater’s GSoC series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder. It targets the `fetch-object-info` subsystem and addresses a latent protocol robustness issue.

The patch hardens the client against malformed server responses by explicitly checking both under-length (fewer objects than requested) and over-length (more objects than requested) cases. Previously, the loop in `fetch_object_info()` stopped either when the reader returned something other than `PACKET_READ_NORMAL` or when it had read as many lines as requested, but neither boundary was validated. A server sending too few objects left the end of the result arrays uninitialized, while a server sending too many left extra packets unread—only caught on stateless transports by `check_stateless_delimiter()`.

The fix extracts `packet_reader_read()` from the loop condition, so the loop no longer consumes the final packet. Inside the loop, if the read is not `PACKET_READ_NORMAL`, the client now `die()`s with a clear message indicating how many objects were expected versus received. After the loop, the client expects a flush packet; if anything else arrives, it `die()`s to fail fast. This aligns with Git’s defensive programming practices and addresses Junio’s protocol hygiene concern from the thread.

The change is purely mechanical (10 insertions, 4 deletions) and touches only `fetch-object-info.c`. It introduces no new symbols or behavior changes beyond the robustness checks. Junio has explicitly endorsed this patch as ready to merge, noting it is uncontroversial and addresses a preexisting latent bug. The commit message clearly explains the motivation and the fix, and the patch is well-tested as part of the broader series. No further changes are expected.
