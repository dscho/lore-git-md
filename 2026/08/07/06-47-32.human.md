This is a sparse-checkout/sparse-index performance patch that addresses a specific edge case in `repo_index_has_changes()`. The patch itself is well-crafted—it includes a clear commit message, a test helper, and a new test case—but Elijah Newren raises a fundamental question about its motivation.

The patch fixes an unnecessary index expansion when `repo_index_has_changes()` is called on an unborn branch (e.g., a newly created orphan branch). Currently, the function falls back to walking the index directly when HEAD doesn’t exist, which forces a full expansion of sparse directory entries. The fix replaces this fallback with a comparison against the empty tree, avoiding the expansion while still reporting paths inside sparse directories. The change is technically sound: it consolidates the unborn-branch case with the normal tree-comparison path, reduces code complexity (a net 28-line reduction in `read-cache.c`), and adds test coverage.

However, Elijah’s review questions whether this scenario is realistic. He asks why someone with an unborn HEAD would even *have* a sparse index—how would tree entries for millions of files exist in the index if nothing has been committed? His skepticism isn’t about the code’s correctness but about whether this is a problem worth solving. The commit message explains *what* the patch does but doesn’t justify *why* this edge case matters in practice. Without a compelling use case, the patch risks being seen as a solution in search of a problem.

The test helper (`test-tool read-cache --index-has-changes`) and the new test in `t1092` are thorough, but Elijah also points out a minor issue in the test output: the helper assumes a single dirty file, which could lead to odd formatting if multiple files are changed. This is a surface-level nit, though, and doesn’t undermine the patch’s core value.

For now, the patch is under review, and its fate hinges on whether Sahitya can articulate a real-world scenario where this optimization matters. If such a use case exists—perhaps in tooling that operates on unborn branches with sparse checkouts—it would strengthen the patch’s rationale. Otherwise, this may end up as a "nice-to-have" cleanup rather than a must-fix regression.
