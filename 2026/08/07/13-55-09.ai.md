This is the third patch in Christian Couder’s five-patch series introducing `uploadpack.lazyFetchTrusted`, a server-side configuration variable that lets operators mark repositories as trusted for lazy fetching. The series is a deliberate pivot from the earlier `GIT_NO_LAZY_FETCH=fromAccepted` proposal, shifting trust decisions entirely to the server operator to address the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration.

Patch 3/5 prepares the reusable `path_allowlist_apply()` helper—introduced in patch 2/5 by generalizing the `safe.directory` allowlist machinery—for its upcoming use in the promisor-remote subsystem. The patch adds a `bool allow_dot` argument to the helper, allowing it to reject non-absolute paths (including single-dot paths) when needed. This is necessary because the promisor-remote code will use the helper to validate repository paths, where a single dot (`.`)—currently accepted by `safe.directory` to mean "the top level of the current repository"—would be ambiguous or unsafe. The patch also exports the function and documents it in `setup.h`, making it available for use in `promisor-remote.c` in a later patch.

The change is small and focused: it modifies only `setup.c` and `setup.h`, adding the new argument, updating the single existing call site (`safe_directory_cb()`) to pass `true` for backward compatibility, and documenting the function’s behavior and constraints. The commit message clearly explains the motivation—preparing for reuse in promisor-remote—and the technical rationale for rejecting non-absolute paths. No test coverage is added here, as the existing `safe.directory` tests continue to validate the helper’s behavior.

This patch is a well-motivated refactoring that directly supports the series’ goal of establishing a server-side trust mechanism for lazy fetching. It is uncontroversial in isolation, but its value depends on the overall series being accepted. The unresolved security objection from brian m. carlson—whether any expansion of lazy-fetching flexibility increases exposure to untrusted repositories—remains the central point of discussion for the series as a whole. This patch itself is unlikely to attract substantive review feedback, as it is a straightforward preparatory step.
