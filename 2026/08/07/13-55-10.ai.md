This is the fourth patch in Christian Couder’s six-patch series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators mark repositories as trusted for lazy fetching. The patch implements the configuration-reading logic, building on the reusable `path_allowlist_apply()` helper introduced in earlier patches.

The patch adds a new `upload_pack_lazy_fetch_trusted()` function that checks whether the current repository’s path is listed in the `uploadpack.lazyFetchTrusted` configuration variable. The function reads the configuration from protected files only (using `git_protected_config()`), normalizes the repository path with `real_pathdup()`, and delegates the allowlist check to `path_allowlist_apply()` with `allow_dot=false` to reject non-absolute paths. The result is a boolean indicating whether lazy fetching should be permitted for this repository.

The implementation is straightforward and follows the pattern established by Git’s `safe.directory` configuration. It touches `upload-pack.c` (adding the new function and a protected-config callback) and `upload-pack.h` (exporting the function). No behavior changes are introduced yet; the new function will be wired into the lazy-fetch logic in the next patch.

This patch is a key step in the series’ security model: by restricting the configuration to protected files and rejecting relative paths, it ensures that the trust decision cannot be influenced by the served repository itself. The patch looks clean and well-motivated, with no obvious gaps or oversights. The only open question is whether the server-side trust model will satisfy brian m. carlson’s earlier security objection, but that discussion belongs to the series as a whole rather than this specific patch.
