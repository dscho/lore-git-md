This is a **completion infrastructure patch discussion** in the ongoing `git history` Bash completion series. The email captures Vincent Mailhol’s response to Patrick Steinhardt’s maintainability concerns about the `__git_history_has_revision` helper, which hardcodes options like `--empty` and `--update-refs` that take arguments.

Vincent acknowledges the fragility of the current approach but argues that the practical impact is limited. He notes that the `--option=<value>` syntax (e.g., `--empty=drop`) is already handled correctly by the existing logic, and most users are unlikely to use the `--option <value>` form (e.g., `--empty drop`) without an equals sign. For options like `--gpg-sign` (which may be added in the future), the helper’s behavior is mostly correct because the value is optional and defaults to the committer identity. The only problematic case is when a user explicitly provides a value for an option *without* an equals sign (e.g., `--new-option value`), which would incorrectly trigger reference completion. Vincent suggests this edge case is rare enough to tolerate, especially since the `--option <value>` syntax isn’t documented in the man pages.

He proposes two options for moving forward: (1) retain the current helper (which works well today but will require manual updates for future options), or (2) simplify the logic by ignoring the `--option <value>` syntax entirely, accepting that it will produce incorrect completions in some cases. Vincent slightly prefers the first option but is open to the second if reviewers prefer it. No new implementation is provided in this email, but a v3 iteration is implied to address the feedback. The discussion remains focused on balancing short-term correctness with long-term maintainability, with no clear resolution yet. Key references include the `__git_history_has_revision` helper, the `--option=<value>` vs. `--option <value>` syntax distinction, and the hypothetical `--gpg-sign` option.
