Subject: [PATCH 0/3] convert USE_NSEC to runtime config
Series version: v5 (applied under topic `dk/use-nsec-runtime`; ready to graduate to `master`)
Originating author: D. Ben Knoble
Thread type: patch series

Core problem or goal
Replace the build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`) to allow users to enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The series also includes a Meson build-system fix (`MAN_BASE_URL` configuration) and a no-op refactor of `repo_config_values_init`.

Current status
Applied under the topic `dk/use-nsec-runtime`; v5 is effectively complete and ready to graduate to `master`. The cross-platform correctness blocker (silent corruption risk when `core.useNanosec=true` is set on a `NO_NSEC` platform) is resolved by unconditionally including the `use_nanosec` field in `struct repo_config_values` but treating it as false when `NO_NSEC` is defined, ensuring backward compatibility and eliminating any risk of uninitialized reads. The performance regression identified in v1 (~41× slowdown in `git diff` benchmarks) is fixed by caching the value in the repository’s `repo_config_values` struct; benchmark results confirm performance is restored to baseline (21 ms vs 20 ms). Junio’s and Patrick Steinhardt’s reviews of v3 and v4 identified final polish items, all of which are now addressed in v5: (1) the `use_nanosec` field in `struct repo_config_values` is unconditionally initialized to `0` in `repo_config_values_init()`, (2) the `#ifndef NO_NSEC` guards in `is_racy_stat()` are simplified to a single ternary expression for readability, (3) the documentation for `core.useNanosec` includes a direct warning about platform/filesystem limitations, and (4) the commit message of the second patch (no-op refactor) incorporates Junio’s suggested wording tweak ("definition of 'struct repo_config_values'" instead of "struct definition"). Junio’s latest reply rejects the idea of a runtime warning when `core.useNanosec=true` is set on a `NO_NSEC` platform, and Patrick Steinhardt explicitly agrees, closing the last open design question: no runtime warning will be added. The author acknowledges this reasoning and notes that users with shared `.gitconfig` files can work around the limitation by using a site-local configuration path to set the option only on supported platforms. Patrick Steinhardt’s final review confirms that the only remaining `USE_NSEC` reference (a comment in `builtin/update-index.c`) was already updated by the patch, and endorses the plan to eliminate preprocessor directives in `is_racy_stat()` by unconditionally initializing `use_nanosec`. The Meson build-system fix (first patch) is confirmed correct, uncontroversial, and ready to advance independently after Patrick Steinhardt’s review; it exposes a configurable knob (`man_base_url`) for Meson builds, mirroring the `MAN_BASE_URL` option in the Makefile, and changes the default to `file://$(htmldir)/` (with a trailing slash) to match the Makefile’s behavior. The no-op refactor in the second patch is purely mechanical, introduces no behavioral changes, and is ready to advance. The core change introducing `core.useNanosec` (third patch) is now explicitly described as "well-crafted, uncontroversial, and ready to advance to `master`" in the author’s latest email. Junio’s latest reply raises a forward-looking architectural concern: the new call to `repo_config_values()` in `is_racy_stat()` introduces an ordering constraint for future work, as any effort to support in-process submodule operations (e.g., `git diff --recurse-submodules`) will now require `repo_config_values()` to work on arbitrary repositories, not just `the_repository`. This is not a regression—`repo_config_values` was already limited to `the_repository`—but the new call site makes the limitation more visible. The concern does not block graduation to `master`. Patrick Steinhardt’s latest reply confirms that while the constraint is not a regression, it may complicate future work on sub-repository support. He notes that an upcoming patch series (motivated by removing submodule ODB registration) will rely more on sub-repositories, but the `core.useNanosec` change does not break it. Steinhardt expresses dissatisfaction with the current state of `repo_config_values()` but acknowledges that refactoring it away from `the_repository` is non-trivial due to its initialization via `repo_config(git_default_config)`. He suggests that if future edge cases reveal problems, the series could be refactored to move the `use_nanosec` value into `struct repo_settings` instead, which already supports multiple repositories. **Patrick Steinhardt’s final review feedback on the third patch requests a trivial cosmetic change to a comment in `builtin/update-index.c`**: replacing "defined" with "enabled" to better reflect the runtime nature of `core.useNanosec`. This is the only remaining action before Junio can merge the topic.** The series is based on master (2c78326f81) and consists of three patches: (1) the Meson build-system fix, (2) the no-op refactor of `repo_config_values_init`, and (3) the core change introducing `core.useNanosec` and removing `USE_NSEC`. A textual and semantic conflict exists with `ty/repo-config-cleanups` in `seen` (removes comments in `struct repo_config_values` that this series adds).

Key technical details
Files touched: `Documentation/config/core.adoc`, `Documentation/meson.build`, `meson_options.txt`, `environment.c`, `environment.h`, `read-cache.c`, `statinfo.c`, `Documentation/technical/racy-git.adoc`, `compat/posix.h`, `Makefile`, `configure.ac`, `builtin/update-index.c`.
New config key: `core.useNanosec` (defaults to false).
Behavior change: nanosecond precision becomes configurable at runtime rather than compile time; performance impact documented for `git diff` in new worktrees. The patch preserves existing behavior on platforms lacking nanosecond support by treating the `use_nanosec` field as false when `NO_NSEC` is defined, preventing silent corruption when `core.useNanosec=true` is set on a platform where `NO_NSEC` is defined. **No runtime warning will be emitted** when `core.useNanosec=true` is set on a `NO_NSEC` platform; users must rely on documentation to understand the risks and can use per-machine overrides (e.g., `includeIf`) to avoid setting the option on unsupported platforms.
On-disk format: unchanged.
Test coverage: not yet updated; platform-dependent nature complicates testing. The author notes that existing tests (including `t4060`) pass when `core.useNanosec=true` is set, but systematic testing across the entire test suite is complicated by platform-dependent behavior. The Meson build-system fix and the no-op refactor are self-contained and unlikely to require additional testing. Documentation now lists filesystems known to support nanosecond precision (ext2, ext4, XFS, CEPH, CIFS, NTFS, UFS, FUSE, FAT) and includes a direct warning about platform/filesystem limitations.
Performance regression: the v1 implementation introduced a hot-path cost by parsing the config key on every `is_racy_stat()` call; caching in `repo_config_values` is confirmed as the fix. Junio’s and Patrick’s reviews do not affect performance but address initialization correctness and code clarity.
Code structure: the nested `#ifndef NO_NSEC` guards in `is_racy_stat()` are replaced with a single ternary expression, since `use_nanosec` is now unconditionally initialized to `0` in `repo_config_values_init()`. The `use_nanosec` field is unconditionally present in `struct repo_config_values` but ignored (treated as false) when `NO_NSEC` is defined. The Meson build-system fix adds a new option (`man_base_url`) to `meson_options.txt` and updates `Documentation/meson.build` to use it, defaulting to `file://$(htmldir)/` (with a trailing slash) to match the Makefile’s behavior. The fix resolves broken relative links in generated man pages (e.g., `/usr/share/manuser-manual.html` becomes `file:///usr/share/doc/git/html/user-manual.html`). The author’s audit (limited to Gentoo and a web search) found no evidence that any distribution currently uses `MAN_BASE_URL`, but the option is provided for consistency and future-proofing. The no-op refactor in the second patch reorders the assignments in `repo_config_values_init()` to group them by config section ("core", "sparse", "branch") and match the struct declaration, making future additions easier to validate; the reordering is purely mechanical, introduces no new fields, and aligns with Junio’s suggested commit message wording tweak ("definition of 'struct repo_config_values'"). The diff for the second patch shows 12 lines added and 7 removed, all within `environment.c`, with assignments now grouped by config section to improve readability and maintainability. The third patch removes all remaining `USE_NSEC` preprocessor directives, replacing them with a runtime check of the `core.useNanosec` config key (cached in `repo_config_values`). The commit message for the third patch notes that `--ignore-space-change` may be helpful when viewing the diff due to the conversion from `#ifdef` to runtime checks. **Architectural constraint**: the new call to `repo_config_values()` in `is_racy_stat()` introduces an ordering dependency for future work, as any effort to support in-process submodule operations (e.g., `git diff --recurse-submodules`) will now require `repo_config_values()` to work on arbitrary repositories, not just `the_repository`. This is not a regression but makes the existing limitation more visible. The author confirms that a partial control-flow analysis of 214 call paths leading to `repo_config_values()` shows every analyzed path currently terminates at `the_repository`, even though some intermediate nodes are exposed via public `libgit.a` interfaces, meaning the `the_repository`-only limitation is not a new constraint. Patrick Steinhardt suggests that if future edge cases reveal problems, the series could be refactored to move the `use_nanosec` value into `struct repo_settings` instead, which already supports multiple repositories. **Cosmetic comment fix requested**: in `builtin/update-index.c`, change "defined" to "enabled" in a comment to better reflect the runtime nature of `core.useNanosec`.
