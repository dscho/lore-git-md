Core problem or goal
Replace the build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`) to allow users to enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The series also includes a Meson build-system fix (`MAN_BASE_URL` configuration) and a no-op refactor of `repo_config_values_init`.

Current status
Cooking in `next` under the topic `dk/use-nsec-runtime`; v4 is effectively complete and ready to graduate to `master` pending only the agreed final polish. The cross-platform correctness blocker (silent corruption risk when `core.useNanosec=true` is set on a `NO_NSEC` platform) is resolved by unconditionally including the `use_nanosec` field in `struct repo_config_values` but treating it as false when `NO_NSEC` is defined, ensuring backward compatibility and eliminating any risk of uninitialized reads. The performance regression identified in v1 (~41× slowdown in `git diff` benchmarks) is fixed by caching the value in the repository’s `repo_config_values` struct; benchmark results confirm performance is restored to baseline (21 ms vs 20 ms). Junio’s and Patrick Steinhardt’s reviews of v3 identified final polish items, all of which are now addressed in v4: (1) the `use_nanosec` field in `struct repo_config_values` is unconditionally initialized to `0` in `repo_config_values_init()`, (2) the `#ifndef NO_NSEC` guards in `is_racy_stat()` are simplified to a single ternary expression for readability, (3) the documentation for `core.useNanosec` includes a direct warning about platform/filesystem limitations. Junio’s latest reply rejects the idea of a runtime warning when `core.useNanosec=true` is set on a `NO_NSEC` platform, and Patrick Steinhardt explicitly agrees, closing the last open design question: no runtime warning will be added. The author acknowledges this reasoning and notes that users with shared `.gitconfig` files can work around the limitation by using a site-local configuration path to set the option only on supported platforms. Patrick Steinhardt’s final review confirms that the only remaining `USE_NSEC` reference (a comment in `builtin/update-index.c`) was already updated by the patch, and endorses the plan to eliminate preprocessor directives in `is_racy_stat()` by unconditionally initializing `use_nanosec`. The Meson build-system fix (first patch) is now confirmed correct, uncontroversial, and ready to advance independently after Patrick Steinhardt’s review; it exposes a configurable knob (`man_base_url`) for Meson builds, mirroring the `MAN_BASE_URL` option in the Makefile, and changes the default to `file://$(htmldir)/` (with a trailing slash) to match the Makefile’s behavior. Junio C Hamano’s review of the second patch (no-op refactor) is purely surface-level, suggesting a minor wording tweak to the commit message ("definition of 'struct repo_config_values'" instead of "struct definition") but otherwise endorsing the improvement. The patch remains uncontroversial, introduces no behavioral changes, and is ready to advance. The core change introducing `core.useNanosec` (third patch) remains uncontroversial and ready to advance. The series is based on master (2c78326f81) and consists of three patches: (1) the Meson build-system fix, (2) the no-op refactor of `repo_config_values_init`, and (3) the core change introducing `core.useNanosec` and removing `USE_NSEC`. A textual and semantic conflict exists with `ty/repo-config-cleanups` in `seen` (removes comments in `struct repo_config_values` that this series adds).

Key technical details
Files touched: `Documentation/config/core.adoc`, `Documentation/meson.build`, `meson_options.txt`, `environment.c`, `environment.h`, `read-cache.c`, `statinfo.c`, `Documentation/technical/racy-git.adoc`, `compat/posix.h`, `Makefile`, `configure.ac`, `builtin/update-index.c`.
New config key: `core.useNanosec` (defaults to false).
Behavior change: nanosecond precision becomes configurable at runtime rather than compile time; performance impact documented for `git diff` in new worktrees. The patch preserves existing behavior on platforms lacking nanosecond support by treating the `use_nanosec` field as false when `NO_NSEC` is defined, preventing silent corruption when `core.useNanosec=true` is set on a platform where `NO_NSEC` is defined. **No runtime warning will be emitted** when `core.useNanosec=true` is set on a `NO_NSEC` platform; users must rely on documentation to understand the risks and can use per-machine overrides (e.g., `includeIf`) to avoid setting the option on unsupported platforms.
On-disk format: unchanged.
Test coverage: not yet updated; platform-dependent nature complicates testing. The Meson build-system fix and the no-op refactor are self-contained and unlikely to require additional testing. Documentation now lists filesystems known to support nanosecond precision (ext2, ext4, XFS, CEPH, CIFS, NTFS, UFS, FUSE, FAT) and includes a direct warning about platform/filesystem limitations.
Performance regression: the v1 implementation introduced a hot-path cost by parsing the config key on every `is_racy_stat()` call; caching in `repo_config_values` is confirmed as the fix. Junio’s and Patrick’s reviews do not affect performance but address initialization correctness and code clarity.
Code structure: the nested `#ifndef NO_NSEC` guards in `is_racy_stat()` are replaced with a single ternary expression, since `use_nanosec` is now unconditionally initialized to `0` in `repo_config_values_init()`. The `use_nanosec` field is unconditionally present in `struct repo_config_values` but ignored (treated as false) when `NO_NSEC` is defined. The Meson build-system fix adds a new option (`man_base_url`) to `meson_options.txt` and updates `Documentation/meson.build` to use it, defaulting to `file://$(htmldir)/` (with a trailing slash) to match the Makefile’s behavior. The no-op refactor in the second patch reorders the assignments in `repo_config_values_init()` to group them by config section ("core", "sparse", "branch") and match the struct declaration, making future additions easier to validate; the reordering is purely mechanical, introduces no new fields, and aligns with Junio’s suggested commit message wording tweak ("definition of 'struct repo_config_values'").
