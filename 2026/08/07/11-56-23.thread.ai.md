Core problem or goal
Replace the build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`) to allow users to enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The series also includes a Meson build-system fix (`MAN_BASE_URL` configuration) and a no-op refactor of `repo_config_values_init`.

Current status
Applied under the topic `dk/use-nsec-runtime`; v6 is complete and ready to graduate to `next`. The only change from v5 is the trivial cosmetic fix requested by Patrick Steinhardt: replacing "defined" with "enabled" in a comment in `builtin/update-index.c` to better reflect the runtime nature of `core.useNanosec`. Junio’s and Patrick Steinhardt’s reviews confirm the series is technically sound, with all prior feedback addressed. The cross-platform correctness blocker (silent corruption risk when `core.useNanosec=true` is set on a `NO_NSEC` platform) is resolved by unconditionally including the `use_nanosec` field in `struct repo_config_values` but treating it as false when `NO_NSEC` is defined, ensuring backward compatibility. The performance regression identified in v1 (~41× slowdown in `git diff` benchmarks) is fixed by caching the value in the repository’s `repo_config_values` struct; benchmark results confirm performance is restored to baseline (21 ms vs 20 ms). The architectural constraint introduced by the new call to `repo_config_values()` in `is_racy_stat()`—limiting future in-process submodule operations—is acknowledged but not blocking, as `repo_config_values()` was already restricted to `the_repository`. Patrick Steinhardt suggests that if future edge cases reveal problems, the series could be refactored to move the `use_nanosec` value into `struct repo_settings` instead. The Meson build-system fix (first patch) and the no-op refactor (second patch) are uncontroversial and ready to advance independently. A textual and semantic conflict exists with `ty/repo-config-cleanups` in `seen` (removes comments in `struct repo_config_values` that this series adds), requiring routine resolution if both topics advance.

Key technical details
Files touched: `Documentation/config/core.adoc`, `Documentation/meson.build`, `meson_options.txt`, `environment.c`, `environment.h`, `read-cache.c`, `statinfo.c`, `Documentation/technical/racy-git.adoc`, `compat/posix.h`, `Makefile`, `configure.ac`, `builtin/update-index.c`.
New config key: `core.useNanosec` (defaults to false).
Behavior change: nanosecond precision becomes configurable at runtime rather than compile time; performance impact documented for `git diff` in new worktrees. The patch preserves existing behavior on platforms lacking nanosecond support by treating the `use_nanosec` field as false when `NO_NSEC` is defined, preventing silent corruption. **No runtime warning will be emitted** when `core.useNanosec=true` is set on a `NO_NSEC` platform; users must rely on documentation to understand the risks.
On-disk format: unchanged.
Test coverage: platform-dependent; existing tests (e.g., `t4060`) pass when `core.useNanosec=true` is set, but systematic testing is complicated by platform variability. The Meson build-system fix and no-op refactor are self-contained and unlikely to require additional testing.
Performance: the v1 performance regression (~41× slowdown) is resolved by caching the config value in `repo_config_values`. The nested `#ifndef NO_NSEC` guards in `is_racy_stat()` are replaced with a single ternary expression for clarity.
Code structure: the `use_nanosec` field is unconditionally present in `struct repo_config_values` but ignored (treated as false) when `NO_NSEC` is defined. The Meson build-system fix adds a configurable `man_base_url` option to `meson_options.txt`, defaulting to `file://$(htmldir)/` (with a trailing slash) to match the Makefile’s behavior. The no-op refactor in the second patch reorders assignments in `repo_config_values_init()` to group them by config section ("core", "sparse", "branch") for maintainability.
**Architectural constraint**: the new call to `repo_config_values()` in `is_racy_stat()` introduces an ordering dependency for future work, as any effort to support in-process submodule operations (e.g., `git diff --recurse-submodules`) will require `repo_config_values()` to work on arbitrary repositories, not just `the_repository`. This is not a regression but makes the existing limitation more visible. Patrick Steinhardt suggests refactoring to `struct repo_settings` as a potential mitigation if future edge cases arise.
