Thread identity
Subject: [PATCH 0/3] convert USE_NSEC to runtime config
Series version: v2
Originating author: D. Ben Knoble
Thread type: patch series

Core problem or goal
Replace the build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`) to allow users to enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The series also includes a Meson build-system fix (`MAN_BASE_URL` configuration) and a no-op refactor of `repo_config_values_init`.

Current status
Under review; v2 posted. The performance regression identified in v1 (a ~41× slowdown in `git diff` benchmarks due to calling `repo_config_get_bool()` on every `is_racy_stat()` invocation) is fixed by caching the value in the repository’s `repo_config_values` struct. Benchmark results confirm the fix restores performance to baseline (21 ms vs 20 ms). The architectural question of where to cache `core.useNanosec`—`repo_config_values` (modern but currently limited to `the_repository`), `repo_settings` (supports per-repository variation, e.g., for submodules), or a global variable—remains open. The author’s partial control-flow analysis of 214 call paths leading to `repo_config_values()` shows every analyzed path currently terminates at `the_repository`, even though some intermediate nodes are exposed via public `libgit.a` interfaces, meaning the `the_repository`-only limitation is already exposed and may grow with this change. Patrick Steinhardt suggests that requiring `the_repository`-cleanliness could block the series indefinitely and offers a global variable as a fallback if the project is unwilling to accept the current limitation of `repo_config_values`. The Meson build-system fix (first patch) is confirmed correct and uncontroversial after Patrick Steinhardt’s review; it aligns Meson’s `man.base.url.for.relative.links` default with the Makefile’s behavior and adds a configurable `man_base_url` option for downstream flexibility. The no-op refactor (second patch) is purely mechanical, uncontested, and ready to advance independently. The core change (third patch) remains the focus of the architectural discussion. The series is based on master (2c78326f81) and consists of three patches: (1) the Meson build-system fix, (2) the no-op refactor of `repo_config_values_init`, and (3) the core change introducing `core.useNanosec` and removing `USE_NSEC`. A textual and semantic conflict exists with `ty/repo-config-cleanups` in `seen` (removes comments in `struct repo_config_values` that this series adds). Benchmark results show a ~57× performance improvement for `git diff` in new worktrees when `core.useNanosec` is enabled (from ~217 ms to ~3.8 ms) in the original v1 implementation, but this is now overshadowed by the hot-path regression fix. The `Best-viewed-with: --ignore-space-change` hint has been moved into the commit message body as requested by SZEDER Gábor.

Key technical details
Files touched: `Documentation/config/core.adoc`, `Documentation/meson.build`, `meson_options.txt`, `environment.c`, `environment.h`, `read-cache.c`, `statinfo.c`, `Documentation/technical/racy-git.adoc`, `compat/posix.h`, `Makefile`, `configure.ac`, `builtin/update-index.c`.
New config key: `core.useNanosec` (defaults to false).
Behavior change: nanosecond precision becomes configurable at runtime rather than compile time; performance impact documented for `git diff` in new worktrees. The patch preserves existing behavior on platforms lacking nanosecond support by retaining the `NO_NSEC` conditional in `compat/posix.h`.
On-disk format: unchanged.
Test coverage: not yet updated; platform-dependent nature complicates testing. The Meson build-system fix and the no-op refactor are self-contained and unlikely to require additional testing. Documentation now lists filesystems known to support nanosecond precision (ext2, ext4, XFS, CEPH, CIFS, NTFS, UFS, FUSE, FAT).
Performance regression: the v1 implementation introduced a hot-path cost by parsing the config key on every `is_racy_stat()` call; caching in `repo_config_values` is confirmed as the fix. The choice of cache location (`repo_config_values`, `repo_settings`, or a global variable) now hinges on whether the project is willing to accept the current `the_repository`-only limitation of `repo_config_values` or prefers a stopgap (global variable or `repo_settings`) until the broader `the_repository` issue is resolved. The first patch (Meson build-system fix) is confirmed correct and ready to advance independently; it touches only `Documentation/meson.build` and `meson_options.txt`, aligns the default `man.base.url.for.relative.links` with the Makefile’s behavior (`file://$(htmldir)/` with a trailing slash), and adds a configurable `man_base_url` option for downstream packagers.

Open questions and loose ends
- Cache location: whether to use `repo_config_values` (modern but limited to `the_repository`), `repo_settings` (supports per-repository variation, e.g., for submodules), or a global variable as a temporary measure for caching `core.useNanosec`. The author’s partial control-flow analysis shows that all 214 call paths to `repo_config_values()` currently terminate at `the_repository`, even though some intermediate nodes are exposed via public `libgit.a` interfaces, meaning the `the_repository`-only limitation is already exposed and may grow with this change. Patrick Steinhardt suggests that requiring `the_repository`-cleanliness could block the series indefinitely and offers a global variable as a fallback if the project is unwilling to accept the current limitation of `repo_config_values`.
- Naming: `core.useNanosec` may be too specific if platforms offer extended precision beyond nanoseconds (e.g., picoseconds).
- Testing: how to handle platform-dependent behavior in the test suite for the nanosecond-precision change.
- Coordination: conflict with `ty/repo-config-cleanups` in `seen` will require resolution if both topics advance.
- Performance: broader implications (e.g., for `git status` or `git add`) remain unmeasured.
