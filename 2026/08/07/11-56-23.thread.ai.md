Core problem or goal
Replace the build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`) to allow users to enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The series also includes a Meson build-system fix (`MAN_BASE_URL` configuration) and a no-op refactor of `repo_config_values_init`.

Current status
**Graduated to `next`** (integration testing branch) as of 2024-07-10. The series is complete and all prior feedback has been addressed. The only change from v5 was the trivial cosmetic fix requested by Patrick Steinhardt: replacing "defined" with "enabled" in a comment in `builtin/update-index.c` to better reflect the runtime nature of `core.useNanosec`. Junio’s latest comment requests a single documentation typo fix ("comparisions" → "comparisons" in `Documentation/config/core.adoc`). This is purely editorial and does not affect the patch’s technical readiness. Junio’s and Patrick Steinhardt’s reviews confirm the series is technically sound, with all performance, correctness, and architectural concerns resolved. Jeff King (Peff) raises a subtle correctness risk in the final patch: if a user builds two versions of Git (one with `NO_NSEC` and one without) on a system that supports nanosecond timestamps, an index generated by the non-`NO_NSEC` build could store real nanosecond values, which the `NO_NSEC` build would misinterpret as zero, leading to false "racy" comparisons. Peff acknowledges this scenario is unlikely and does not block graduation, but it adds a new dimension to the platform-compatibility discussion. The cross-platform correctness blocker (silent corruption risk when `core.useNanosec=true` is set on a `NO_NSEC` platform) is resolved by unconditionally including the `use_nanosec` field in `struct repo_config_values` but treating it as false when `NO_NSEC` is defined, ensuring backward compatibility. The performance regression identified in v1 (~41× slowdown in `git diff` benchmarks) is fixed by caching the value in the repository’s `repo_config_values` struct; benchmark results confirm performance is restored to baseline (21 ms vs 20 ms). The architectural constraint introduced by the new call to `repo_config_values()` in `is_racy_stat()`—limiting future in-process submodule operations—is acknowledged but not blocking, as `repo_config_values()` was already restricted to `the_repository`. Patrick Steinhardt suggests that if future edge cases reveal problems, the series could be refactored to move the `use_nanosec` value into `struct repo_settings` instead. The Meson build-system fix (first patch) and the no-op refactor (second patch) are uncontroversial and ready to advance independently. A textual and semantic conflict exists with `ty/repo-config-cleanups` in `seen` (removes comments in `struct repo_config_values` that this series adds), requiring routine resolution if both topics advance.

Key technical details
Files touched: `Documentation/config/core.adoc`, `Documentation/meson.build`, `meson_options.txt`, `environment.c`, `environment.h`, `read-cache.c`, `statinfo.c`, `Documentation/technical/racy-git.adoc`, `compat/posix.h`, `Makefile`, `configure.ac`, `builtin/update-index.c`.
New config key: `core.useNanosec` (defaults to false).
Behavior change: nanosecond precision becomes configurable at runtime rather than compile time; performance impact documented for `git diff` in new worktrees. The patch preserves existing behavior on platforms lacking nanosecond support by treating the `use_nanosec` field as false when `NO_NSEC` is defined, preventing silent corruption. **No runtime warning will be emitted** when `core.useNanosec=true` is set on a `NO_NSEC` platform; users must rely on documentation to understand the risks. The `#ifndef NO_NSEC` guard around the `core.usenanosec` config handler in `environment.c` is retained, but Jeff King (Peff) questions its necessity, noting it does not eliminate the `NO_NSEC` build knob and introduces a subtle correctness risk: an index generated by a non-`NO_NSEC` build could store real nanosecond values, which a `NO_NSEC` build would misinterpret as zero, leading to false "racy" comparisons. This edge case is unlikely in practice but may warrant documentation.
On-disk format: unchanged.
Test coverage: platform-dependent; existing tests (e.g., `t4060`) pass when `core.useNanosec=true` is set, but systematic testing is complicated by platform variability. The Meson build-system fix (first patch) addresses a long-standing inconsistency between Makefile and Meson builds by exposing a configurable `man_base_url` option in `meson_options.txt`, defaulting to `file://$(htmldir)/` (with a trailing slash) to match the Makefile’s behavior. The fix resolves broken links in manual pages (e.g., `/usr/share/manuser-manual.html` → `/usr/share/man/user-manual.html`) and is motivated by the need to ensure correct rendering of links added in later patches (e.g., to `racy-git.adoc`). The no-op refactor in the second patch reorders assignments in `repo_config_values_init()` to group them by config section ("core", "sparse", "branch") for maintainability.
Performance: the v1 performance regression (~41× slowdown) is resolved by caching the config value in `repo_config_values`. The nested `#ifndef NO_NSEC` guards in `is_racy_stat()` are replaced with a single ternary expression for clarity.
Code structure: the `use_nanosec` field is unconditionally present in `struct repo_config_values` but ignored (treated as false) when `NO_NSEC` is defined. The Meson build-system fix adds a configurable `man_base_url` option to `meson_options.txt`, defaulting to `file://$(htmldir)/` (with a trailing slash) to match the Makefile’s behavior. The no-op refactor in the second patch reorders assignments in `repo_config_values_init()` to group them by config section ("core", "sparse", "branch") for maintainability, improving code readability and easing future maintenance as new fields are added.
**Architectural constraint**: the new call to `repo_config_values()` in `is_racy_stat()` introduces an ordering dependency for future work, as any effort to support in-process submodule operations (e.g., `git diff --recurse-submodules`) will require `repo_config_values()` to work on arbitrary repositories, not just `the_repository`. This is not a regression but makes the existing limitation more visible. Patrick Steinhardt suggests refactoring to `struct repo_settings` as a potential mitigation if future edge cases arise.
