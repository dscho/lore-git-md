Thread identity
Subject: [PATCH 0/3] convert USE_NSEC to runtime config
Series version: v1 (v2 expected)
Originating author: D. Ben Knoble
Thread type: patch series

Core problem or goal
Replace the build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`) to allow users to enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The series also includes a Meson build-system fix (`MAN_BASE_URL` configuration) and a no-op refactor of `repo_config_values_init`.

Current status
Under review; v1 posted, v2 planned. Junio C Hamano identified a performance-critical flaw in the core patch: the implementation called `repo_config_get_bool()` on every `is_racy_stat()` invocation, creating a ~41× slowdown in `git diff` benchmarks (854 ms vs 20 ms). The author has benchmarked a fix that caches the value in the repository’s `repo_settings` struct, restoring performance to baseline (21 ms vs 20 ms). Patrick Steinhardt now raises an architectural question: whether `core.useNanosec` should be cached in `repo_config_values` (modern but currently limited to `the_repository`) or in `repo_settings` (supports per-repository variation, e.g., for submodules). The rest of the series (build-system cleanup, no-op refactor, documentation) remains uncontested. The series is based on master (2c78326f81) and consists of three patches: (1) a Meson build-system fix for `MAN_BASE_URL`, (2) a no-op refactor of `repo_config_values_init` that reorders assignments and adds section comments, and (3) the core change introducing `core.useNanosec` and removing `USE_NSEC`. A textual and semantic conflict exists with `ty/repo-config-cleanups` in `seen` (removes comments in `struct repo_config_values` that this series adds). Benchmark results show a ~57× performance improvement for `git diff` in new worktrees when `core.useNanosec` is enabled (from ~217 ms to ~3.8 ms) in the original v1 implementation, but this is overshadowed by the hot-path regression. The next iteration will include the performance fix, a cosmetic commit-message adjustment (moving the `Best-viewed-with: --ignore-space-change` hint into the body), and the cache location decision.

Key technical details
Files touched: `Documentation/config/core.adoc`, `Documentation/meson.build`, `meson_options.txt`, `environment.c`, `environment.h`, `read-cache.c`, `statinfo.c`, `Documentation/technical/racy-git.adoc`, and related build files (Makefile, configure.ac).
New config key: `core.useNanosec` (defaults to false).
Behavior change: nanosecond precision becomes configurable at runtime rather than compile time; performance impact documented for `git diff` in new worktrees.
On-disk format: unchanged.
Test coverage: not yet updated; platform-dependent nature complicates testing. The Meson build-system fix and the no-op refactor are self-contained and unlikely to require additional testing. Documentation now lists filesystems known to support nanosecond precision.
Performance regression: the v1 implementation introduced a hot-path cost by parsing the config key on every `is_racy_stat()` call; caching in `repo_settings` is confirmed as the fix. The choice of cache location (`repo_config_values` vs `repo_settings`) now hinges on whether per-repository variation is needed.

Open questions and loose ends
- Cache location: whether to use `repo_config_values` (modern but limited to `the_repository`) or `repo_settings` (supports per-repository variation, e.g., for submodules) for caching `core.useNanosec`.
- Naming: `core.useNanosec` may be too specific if platforms offer extended precision beyond nanoseconds (e.g., picoseconds).
- Testing: how to handle platform-dependent behavior in the test suite for the nanosecond-precision change.
- Coordination: conflict with `ty/repo-config-cleanups` in `seen` will require resolution if both topics advance.
- Performance: broader implications (e.g., for `git status` or `git add`) remain unmeasured.
- Commit message formatting: resolved in principle; the `Best-viewed-with: --ignore-space-change` hint will be moved into the commit message body in v2.
