This is a feature patch series introducing `uploadpack.lazyFetchTrusted`, a new protected configuration variable that allows server operators to explicitly mark repositories as trusted for lazy fetching. It directly addresses the unresolved security concerns raised during the earlier `GIT_NO_LAZY_FETCH=fromAccepted` series by shifting control from client-side environment variables to server-side configuration.

The series abandons the previous "fromAccepted" approach in favor of a model inspired by Git's `safe.directory` mechanism. Like `safe.directory`, `uploadpack.lazyFetchTrusted` is a protected config variable that only takes effect when set in global or system scope, ensuring only server operators—not clients or served repositories—can enable lazy fetching. This design explicitly acknowledges the security risk of executing arbitrary commands from repository configuration and hooks during lazy fetching, placing responsibility for trust decisions squarely on the server operator.

Five patches implement the feature. The first is a refactoring carried over from the earlier series, extracting lazy-fetch logic into a reusable `lazy_fetch_objects()` helper. Patches 2 and 3 generalize the `safe.directory` code into a reusable `path_allowlist_apply()` function, which patch 4 then uses to process the new `uploadpack.lazyFetchTrusted` config. The final patch wires this up in `builtin/upload-pack.c`, setting `GIT_NO_LAZY_FETCH=0` (enabling lazy fetching) only when the served repository is listed in the trusted allowlist. The series touches the promisor-remote subsystem, `setup.c`, documentation, and adds a new test script (`t/t5710-promisor-remote-capability.sh`).

The motivation is clear: server operators need finer control over lazy fetching, especially in corporate environments where large-object promisors are used. The current `GIT_NO_LAZY_FETCH` boolean is too blunt, and the earlier "fromAccepted" approach was rejected on security grounds. This series offers a pragmatic alternative that maintains security by requiring explicit operator action. The implementation is clean, reusing existing patterns and adding thorough test coverage. CI tests have passed, indicating the changes integrate well with the existing codebase.

The unresolved security objection from the previous series is addressed head-on, though it remains to be seen whether this new approach will satisfy critics. The series positions itself as a step toward a more comprehensive solution, with future work suggested for server-side configuration, allow/deny rules, and repository scanning tools. For now, it provides a workable mechanism for operators who need lazy fetching in trusted environments.
