This thread is about a patch series from D. Ben Knoble that replaces Git’s build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`), allowing users to enable nanosecond precision on supported filesystems without recompiling Git. The goal is to reduce "racy Git" problems, where timestamp resolution can cause false conflicts.

The series is currently under review, with a second version expected soon. The first version introduced a significant performance regression—about 41× slower in `git diff` benchmarks—because it called `repo_config_get_bool()` on every `is_racy_stat()` invocation. The author has since benchmarked a fix that caches the value in the repository’s `repo_settings` struct, restoring performance to baseline. The main open question is where to cache the value: `repo_config_values` (modern but currently limited to `the_repository`) or `repo_settings` (supports per-repository variation, such as for submodules). The author’s investigation found that `repo_config_values` is already exposed via public `libgit.a` interfaces, meaning the `the_repository`-only limitation is not new but could grow with this change. The author suggests that requiring `the_repository`-cleanliness could block the series indefinitely and proposes `repo_settings` as a stopgap if the project isn’t ready to accept the current limitation.

Junio C Hamano identified the performance flaw, and Patrick Steinhardt reviewed the Meson build-system fix (the first patch), confirming it aligns with the Makefile’s behavior. Steinhardt also framed the architectural trade-off, noting that while `repo_config_values` is the modern target for config-driven settings, its limitation to `the_repository` is a blocker for further expansion until the project resolves how to support other repositories. In the latest email, Steinhardt takes a pragmatic stance: he doesn’t oppose landing the series with `repo_config_values` if the CI run and control-flow analysis suggest it’s safe, but he also offers a fallback—using a global variable as a temporary measure—if the project prefers to avoid expanding the `the_repository`-only surface area. The series also includes a no-op refactor of `repo_config_values_init` and a Meson build-system fix, both of which are uncontroversial. A minor conflict exists with `ty/repo-config-cleanups` in Junio’s `seen` branch, but this is expected to be resolved if both topics advance. The next version will include the performance fix, a cosmetic commit-message adjustment, and the final cache location decision.
