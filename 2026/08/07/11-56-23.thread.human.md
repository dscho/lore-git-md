This thread is about D. Ben Knoble’s patch series (v2) converting Git’s build-time `USE_NSEC` macro into a runtime configuration option, `core.useNanosec`, to allow users to enable nanosecond precision without recompiling Git. The goal is to reduce "racy Git" problems on filesystems that support nanosecond timestamps.

The series has three patches: a Meson build-system fix (uncontroversial and ready to advance), a no-op refactor of `repo_config_values_init` (also uncontroversial), and the core change introducing `core.useNanosec`. The v1 implementation introduced a performance regression (~41× slowdown in `git diff` benchmarks) due to calling `repo_config_get_bool()` on every `is_racy_stat()` invocation, but this was fixed in v2 by caching the value in the repository’s `repo_config_values` struct. Benchmarks confirm the fix restores performance to baseline.

The main remaining blocker was a cross-platform correctness issue flagged by Junio C Hamano: if `core.useNanosec=true` is set in a shared configuration (e.g., a network-mounted `.gitconfig`) and Git is used on a platform where `NO_NSEC` is defined, the code could compare garbage or zeroed nanosecond fields, risking silent corruption. The author has now proposed a fix to force-disable `cfg->use_nanosec` in `NO_NSEC` builds, mirroring the existing behavior where nanosecond paths are skipped entirely. This resolves the correctness blocker, though the architectural debate over where to cache `core.useNanosec` (`repo_config_values`, `repo_settings`, or a global variable) remains open. Patrick Steinhardt has suggested a global variable as a fallback if the project is unwilling to accept the current `the_repository`-only limitation of `repo_config_values`.

The series is under active review, with the Meson fix and refactor ready to advance independently. A textual conflict with `ty/repo-config-cleanups` in `seen` will need resolution if both topics progress. Testing for the nanosecond-precision change is complicated by platform dependencies, and broader performance implications (e.g., for `git status` or `git add`) remain unmeasured. The author’s partial control-flow analysis shows that all current call paths to `repo_config_values()` terminate at `the_repository`, but some intermediate nodes are exposed via public `libgit.a` interfaces, meaning the limitation is already exposed.
