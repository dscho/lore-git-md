This thread is about a patch series from D. Ben Knoble that replaces Git’s build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`), allowing users to enable nanosecond precision on supported filesystems without recompiling Git. The goal is to reduce "racy Git" problems, where file timestamps lack sufficient precision to determine modification order.

The series is now at version 1, with version 2 imminent. The core patch initially introduced a severe performance regression—calling `repo_config_get_bool()` on every `is_racy_stat()` invocation slowed `git diff` by ~41× (854 ms vs. 20 ms). The author has since benchmarked a fix that caches the value in the repository’s `repo_settings` struct, restoring performance to baseline (21 ms vs. 20 ms). The remaining open question is where to cache the value: `repo_config_values` (modern but currently limited to `the_repository`), `repo_settings` (supports per-repository variation, e.g., for submodules), or a global variable as a temporary measure. The author’s analysis shows that `repo_config_values` is already exposed via public `libgit.a` interfaces, meaning the `the_repository`-only limitation is not a new constraint. Patrick Steinhardt has suggested that requiring `the_repository`-cleanliness could block the series indefinitely and offers a global variable as a fallback if the project prefers to avoid expanding the `the_repository`-only surface area. The Meson build-system fix (first patch) is uncontroversial, and the no-op refactor remains unchallenged.

The series is under active review, with no architectural decision yet reached. The author is ready to send v2 within 24 hours if the project accepts the current `repo_config_values()` approach but is also open to a global variable as a stopgap. A textual conflict exists with `ty/repo-config-cleanups` in Junio’s `seen` branch, which will need resolution if both topics advance. The broader performance implications for commands like `git status` or `git add` remain unmeasured.
