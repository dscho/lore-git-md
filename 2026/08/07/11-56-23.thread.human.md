This thread is about a patch series from D. Ben Knoble that replaces Git’s build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`), allowing users to enable nanosecond precision on supported filesystems without recompiling Git. The goal is to reduce "racy Git" problems, where timestamps lack sufficient precision to reliably detect file changes.

The first version of the series introduced a significant performance regression—about a 41× slowdown in `git diff`—because it called `repo_config_get_bool()` on every `is_racy_stat()` invocation. The author has since benchmarked a fix that caches the value in the repository’s `repo_settings` struct, restoring performance to baseline. However, Patrick Steinhardt raised an architectural question: whether `core.useNanosec` should be cached in `repo_config_values` (a modern but currently limited-to-`the_repository` approach) or in `repo_settings` (which supports per-repository variation, useful for submodules). The author is now investigating which repository values populate `repo_config_values` to inform this decision. The first patch—a Meson build-system fix—is uncontroversial and confirmed correct, while the rest of the series (a no-op refactor and the core change) awaits resolution of the cache location question. A conflict with `ty/repo-config-cleanups` in Junio’s `seen` branch will need to be addressed if both topics advance.

The series is still under review, with v2 expected to include the performance fix, a cosmetic commit-message adjustment, and a decision on where to cache the config value. No objections have been raised to the core idea, but the architectural trade-off remains the key open question. Junio and Patrick have both weighed in on the performance and design implications, while SZEDER Gábor provided a surface-level review on commit-message formatting. The author is actively working toward a resolution before posting the next iteration.
