This is a follow-up discussion in the ongoing feature request for decoupling explicit branch fetches from the default fetch refspec in `git fetch`. Phillip Wood chimes in to endorse the problem described by Douglas Puchalski, noting that he has encountered the same annoyance and pointing out a parallel issue with the push refspec.

Phillip reacts positively to Junio C Hamano’s suggestion of using the existing `--refmap` option as a starting point, proposing that it could be extended via configuration variables like `remote.<remote>.fetchMap` and `remote.<remote>.pushMap`. These would map refnames without altering the default fetch or push sets, preserving backward compatibility. His comment is brief but constructive, focusing on the potential usefulness of the approach rather than diving into implementation details.

The email also surfaces a secondary pain point: the current refspec matching logic, where the first matching refspec wins rather than the longest (most specific) match. This forces users to manually edit the config file to add branch-specific refspecs, as `git config` appends new entries to the end. Phillip’s observation suggests that any solution to the primary problem might also need to address this quirk to be truly ergonomic.

No patches or concrete design proposals are attached; this remains a conceptual discussion. The thread is now at the stage where the original author (Douglas Puchalski) or another contributor might propose an implementation based on the `--refmap` + configuration idea, or explore whether the approach fully addresses the original workflow limitation. Phillip’s feedback adds weight to the idea that the problem is real and shared by others, but the technical details and edge cases (e.g., interaction with existing `remote.<remote>.fetch` settings, precedence rules) are still open.
