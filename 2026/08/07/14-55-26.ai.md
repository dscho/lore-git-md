This is a follow-up in the ongoing `git fetch` refspec-mapping discussion, clarifying Junio C Hamano’s proposed design direction. The email elaborates on how the existing `--refmap` mechanism could be extended to address the original feature request—decoupling explicit branch fetches from the default fetch refspec—without requiring new configuration knobs like `remote.<remote>.fetchMap`.

Junio reaffirms that `--refmap` was originally designed to separate *name mapping* (how remote refs map to local remote-tracking refs) from *selection* (which refs are fetched). He sketches a workflow where `git fetch` could gain a `matching`-like mode (analogous to `git push`’s `push.default=matching`), allowing everyday fetches to automatically update all remote-tracking refs that match the configured `refmap`. For example, a user’s default `git fetch` would reverse-map existing remote-tracking refs to decide which remote branches to fetch, then update those refs accordingly. Explicitly fetching a new branch (e.g., `git fetch origin a-new-topic`) would automatically create the corresponding remote-tracking ref (`refs/remotes/origin/a-new-topic`), extending the set of refs managed by future fetches.

The proposal avoids introducing new configuration variables (like Phillip Wood’s `remote.<remote>.fetchMap`), instead building on `--refmap` and potentially making it configurable per-remote (e.g., `remote.<name>.refmap`). This approach preserves backward compatibility while enabling the desired opt-in behavior. Key technical details include the need for two separate maps (fetch and push) and the interaction between the proposed `matching` mode and existing refspec logic. No implementation or patch is provided; this remains a conceptual outline. The email does not address edge cases (e.g., overlapping branch names, `--prune` interactions) or test coverage, but it solidifies Junio’s preference for leveraging existing mechanisms over new configuration layers.
