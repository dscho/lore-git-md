This is a performance optimization for the experimental `git last-modified` command, now in its second iteration (v2). The series reuses Git’s Bloom filter machinery to speed up queries about the last commit that modified files matching a pathspec, including wildcards. The v2 reroll addresses all previously identified technical blockers: it refactors the public API to use a boolean return for clarity, restores the original Bloom filter statistics behavior, and fixes the `--show-trees` correctness bug by filtering ancestor tree entries not covered by the original pathspec. The series now consists of six patches, adding two new commits that introduce helpers for `--show-trees` and a test to verify Bloom filter behavior with that option.

The benchmarks in the cover letter show a 3.7× speedup without `--show-trees` (from 60.7 ms to 16.2 ms) and a 1.95× speedup with `--show-trees` (from 61.9 ms to 31.8 ms) on the ziglang/zig repository, bringing `git last-modified` nearly to parity with `git log`. The changes are confined to `revision.c`, `revision.h`, `bloom.c`, `bloom.h`, `builtin/last-modified.c`, and the test suite. The new public functions—`revs_maybe_changed_in_bloom` and `revs_maybe_changed_in_bloom_with_parents`—are now cleanly exposed in `revision.h` and return boolean values, while the internal tristate logic is kept private. The series looks well-motivated, thoroughly tested, and ready for further review; the remaining discussion points from v1 have all been resolved.
