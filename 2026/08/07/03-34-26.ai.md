This is the second patch in Patrick Steinhardt’s six-patch series (v5) making Git’s on-disk object database (ODB) structures pluggable. The patch detangles loose object map loading from repository setup, fixing two latent correctness issues: an unconditional downcast that would BUG if a non-files ODB backend were ever used with a compatibility hash algorithm, and awkward intermixing of repository configuration and ODB initialization.

The change moves loose object map loading into the "loose" backend itself. The `repo_read_loose_object_map()` function is now an internal detail of the loose backend, and the `should_use_loose_object_map()` guard is enforced at the source level during backend initialization (`odb_source_loose_new()`). The patch touches five files: `loose.c` (where `loose_object_map_load()` is made public and the guard is moved), `loose.h` (new function declaration), `odb/source-loose.c` (calls `loose_object_map_load()` during initialization), `repository.c` (removes the call to `repo_read_loose_object_map()`), and `setup.c` (reorders `odb_new()` to happen after `repo_set_compat_hash_algo()`).

The commit message clearly explains the motivation and the two downsides being fixed. The diff is minimal and focused, with no behavior change for existing users. The patch is uncontroversial and fully approved; it is part of a series that Junio’s "What’s cooking" report (2025-06-10) lists as "will merge to 'next'." The only remaining direct caller of `repo_read_loose_object_map()` is in `object-file-convert.c`, which reloads the map after potential concurrent updates; Patrick has suggested this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source.
