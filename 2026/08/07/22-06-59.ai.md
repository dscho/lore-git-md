This is patch 4/10 in Pablo Sabater’s GSoC series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The patch replaces the `object_info` struct with a dedicated `struct fetch_object_info_results` for storing object metadata retrieved from the server.

The change is a mechanical refactoring that eliminates the mismatch between `object_info` (designed for `read_object_info()`’s single-object, pointer-based API) and `fetch_object_info()`’s multi-object, array-based needs. The new struct uses caller-controlled flags (`wants_size`, later `wants_type`) to indicate which attributes are requested, and dynamically allocates arrays only for the attributes the server actually provides. This avoids allocating unused scalars per object per attribute and simplifies memory management, which is now handled by `free_fetch_object_info_results()`.

The patch also removes the `object_info_options` string list and `remote_atom_map[]`, replacing them with direct flag-based logic in `send_object_info_request()` and `fetch_object_info()`. The server’s advertised capabilities are now checked against the caller’s `wants_*` flags, and the protocol option strings are built from those flags rather than a string list. This eliminates the need for the `remote_atom_map[]` array, which previously mapped protocol strings back to atom names. The "type" entry in that array (added in anticipation of future support) is dropped here and reimplemented in later patches where it belongs.

Key files touched are `fetch-object-info.c`, `fetch-object-info.h`, `builtin/cat-file.c`, and `transport.c`. The patch introduces `struct fetch_object_info_results` and its initializer `FETCH_OBJECT_INFO_RESULTS_INIT`, the `free_fetch_object_info_results()` function, and updates function signatures to use the new struct. It also converts the final `else` in `fetch_object_info()` to `die()` for protocol violations (unknown attributes), replacing a `BUG()` and aligning with Git’s defensive programming practices.

The patch is uncontroversial and ready for integration. Junio previously noted that it removes about 30 lines of code by eliminating `remote_atom_map[]` and its associated logic, and Pablo clarified that the "type" entry in that array was included to test the client’s handling of known-but-unsupported placeholders. The new design avoids carrying unused arrays, so the entry is dropped here and reimplemented in the later patches that add type support. No behavior changes are introduced.
