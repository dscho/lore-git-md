This thread is about Patrick Steinhardt’s six-patch series (v3) to make Git’s packfile generation pluggable, a key step in his larger effort to abstract the object database (ODB) so alternative backends can be supported. The series decouples the transport layer (fetch, push, bundle) from the "files" ODB backend by introducing a new interface, `odb_generate_pack()`, which delegates to the existing `git pack-objects` command. The latest patch, just posted, migrates `git bundle` to this interface, completing the transport-layer refactoring for all pack-based operations.

The series is now in its third iteration, with v3 addressing prior feedback: a use-after-scope bug in the files-backend implementation (fixed by moving a `child_process` struct to the heap) and Junio C Hamano’s objection to lingering `the_repository` usage. The latter is mostly resolved—patch 5/6 refactored `bundle.c` to eliminate most `the_repository` references, replacing them with an explicit `struct repository *` parameter—but a workaround for `get_log_output_encoding()` (an `extern` declaration) remains contentious. Junio argued this undermines the compile-time guard against reintroducing `the_repository`, and no resolution has been reached. The new patch (6/6) simplifies `write_pack_data()` by replacing manual `child_process` construction with a declarative ODB setup, preserving all existing functionality (thin packs, delta policies, progress meters) while consolidating progress-meter option handling.

The series is queued in `seen` and under active review, with no prior versions merged to `next` or `master`. Key participants include Junio (who raised the `the_repository` concern), Elijah Newren (who identified the use-after-scope bug), and Justin Tobler (who clarified the long-term intent for `git bundle`). Open questions include the unresolved `get_log_output_encoding()` dependency and whether the ODB interface will need to evolve once the future `git-objects` command is introduced. The series is part of Patrick’s broader ODB abstraction effort, which aims to support alternative backends beyond loose objects and packfiles.
