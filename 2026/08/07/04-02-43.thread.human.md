This thread is a design discussion about improving Git’s interactive patch selection workflow, specifically how to efficiently triage hunks into staged, kept, or discarded states during commands like `git add -p`. The conversation has narrowed to a philosophical and practical debate over Git’s role in providing interactive features.

Junio C Hamano initiated the discussion, proposing a near-term solution: unify triage actions (stage/discard/defer) into a single session while preserving Git’s existing minimalist prompt-loop UI. His latest reply reinforced Git’s boundary—interactive features should be "usable but not pretty," serving as a reference implementation rather than competing with polished external tools like lazygit. This rules out larger UI efforts (e.g., a full TUI) but leaves room for incremental workflow fixes, such as extending `git add -p` to support "discard."

Patrick Steinhardt has refined his earlier proposal for a hierarchical TUI, now advocating for a pragmatic middle ground: Git should address core workflow gaps (e.g., navigable hunk selection) with *basic* UI improvements, but avoid building a "full UI." He argues that even small changes—like allowing users to move between hunks without restarting the prompt-loop—could meaningfully improve usability without overlapping with external tools. However, Junio’s stance suggests that even these modest UI enhancements may be deemed too competitive. The discussion now centers on where to draw the line: what constitutes a "minimal" improvement versus an unacceptable UI modernization.

Stefan Haller remains opposed to any internal UI changes, arguing that Git should focus on core APIs and leave presentation to external tools like lazygit. His position aligns philosophically with Junio’s but hasn’t gained traction on the technical specifics of API improvements. Christian Couder and D. Ben Knoble have contributed broader perspectives, such as leveraging `git history` for advanced use cases or adopting intent-based commands, but no consensus has emerged on these ideas.

The thread is still in the design phase, with no patches or implementation details proposed. Key open questions include how to handle deferred hunks, whether to extend `git add -p` or introduce a new command, and whether the project would accept even a minimal dependency like ncurses for basic UI improvements. The next steps will likely involve clarifying what "basic UI improvements" would entail and whether they can be implemented without violating Junio’s "do not compete" principle. For now, the most plausible path forward appears to be Junio’s incremental approach—unifying triage actions within the existing UI—while larger UI changes remain off the table.
