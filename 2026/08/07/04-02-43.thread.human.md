This thread is about improving Git’s interactive patch selection workflow—specifically, how to efficiently triage hunks into staged, kept, or discarded states during commands like `git add -p` or `git checkout -p`. The discussion has coalesced around three competing visions: Junio C Hamano’s minimalist approach (unify triage actions in a single session without a polished UI), Patrick Steinhardt’s refined proposal for *basic* UI improvements (e.g., navigable hunk selection), and Stefan Haller’s argument to defer all UI enhancements to external tools like lazygit. Johannes Schindelin recently revived a previously rejected patch series (`git add -p --stash`) that offers a concrete implementation path for Junio’s core goal, using the stash to defer hunks.

The thread has now entered a pragmatic phase, with Jeff King (Peff) weighing in on Dscho’s stash-mode proposal. This aligns with Junio’s preference for minimal, reference-like features but leaves room for a cleaner design. Peff’s feedback also highlights the long history of this discussion, noting that the stash-mode idea has been proposed—and rejected—multiple times since 2016, underscoring the project’s struggle to balance usability with its minimalist philosophy.

Key open questions remain: Should deferred hunks be stashed (Dscho’s proposal), persisted in the working tree, or ignored? Peff’s suggestion to explore a separate command could sidestep this concern but might fragment the workflow. Meanwhile, Patrick’s call for *basic* UI improvements (e.g., navigable hunks) and Stefan’s insistence on external tools continue to test the boundaries of Git’s built-in capabilities.
