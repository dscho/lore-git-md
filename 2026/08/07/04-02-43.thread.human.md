This thread is about improving Git’s interactive patch selection workflow, specifically the friction of needing separate commands (`git add -p` and `git checkout -p`) to stage, discard, or defer hunks during triage. Junio C Hamano kicked off the discussion with a proposal to unify these actions into a single session, preserving Git’s existing prompt-loop UI while adding a "discard" option to `git add -p`. The conversation has since expanded into three competing visions: Junio’s incremental approach, Patrick Steinhardt’s call for a hierarchical TUI (inspired by Jujutsu), and Stefan Haller’s argument that Git should avoid interactive UIs entirely and rely on external tools like lazygit.

The latest reply from Junio clarifies the project’s philosophical boundary: Git should provide core functionality without duplicating the work of external tools. This means small, targeted improvements (like unifying stage/discard/defer in a single session) are still on the table, but larger UI efforts (such as a full ncurses-based TUI) are unlikely to gain traction. Patrick’s recent framing bridges this gap, suggesting Git could adopt *basic* UI improvements (e.g., navigable hunk selection) to address core workflow gaps while deferring full UI modernization to external tools. Stefan’s position remains unchanged—Git should focus on improving its APIs to better support tools like lazygit rather than building interactive interfaces itself.

No patches or implementation sketches have been posted yet, and the discussion remains in the design phase. The key open questions revolve around where to draw the line between Git’s built-in workflows and external tooling, how to handle deferred hunks, and whether the solution should extend `git add -p` or introduce a new command. For now, the thread has converged on the immediate priority of unifying triage actions, but the scope and locus of the solution are still contested.
