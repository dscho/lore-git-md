This thread is exploring how to improve Git’s interactive patch selection workflow, specifically the friction of handling hunks that are "good but not yet ready" during staging. Junio C Hamano kicked off the discussion by proposing a way to unify the current two-step process—where users first stage or defer hunks with `git add -p`, then manually discard unwanted ones with `git checkout -p`—into a single session supporting three actions: stage, discard, or defer. The goal is to make triage more efficient without overcomplicating the existing lightweight UI.

The conversation has since expanded to include broader possibilities, such as squashing hunks into older commits, moving them to new branches, or adopting more visual interfaces inspired by tools like Fugitive (a Vim plugin) or GitButler’s intent-based commands. Christian Couder suggested leveraging `git history` or modular commands for advanced workflows, while D. Ben Knoble highlighted Fugitive’s visual, interactive approach as a potential model for Git. However, Junio’s latest email refocuses the discussion on the core issue: the *directional limitation* of the current workflow, not the UI itself. He argues that the triage problem could be solved incrementally—by adding a "discard" action to `git add -p`—without abandoning the linear prompt-loop model. This leaves the thread at a crossroads: whether to pursue a simple extension of the existing tool or a more ambitious redesign. No implementation sketches or decisions have been made yet, but the narrowed scope suggests a practical path forward.
