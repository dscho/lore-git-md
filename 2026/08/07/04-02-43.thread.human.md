This thread is exploring how to improve Git’s interactive patch selection workflow, specifically to address the common frustration of handling "good but not yet ready" hunks during `git add -p` or `git checkout -p` sessions. Junio Hamano kicked off the discussion by proposing a simple "stage/discard/defer" triage system, while Christian Couder expanded the scope to include more advanced use cases like squashing hunks into older commits or moving them to new branches. The conversation remains in the early design phase, with no concrete implementation yet.

D. Ben Knoble recently contributed a fresh perspective by pointing to Fugitive, a Vim plugin that offers a more flexible and intuitive interface for hunk management. Fugitive’s approach—letting users browse all hunks at once and apply actions like staging or reverting directly—contrasts with Git’s current linear prompt-loop, which forces users to cycle through hunks one by one. Knoble suggests Git could learn from this design, though he acknowledges that adopting a similar interface might require a heavier terminal UI. His input shifts the discussion toward user experience, raising questions about whether Git should evolve toward a more interactive, visual workflow or stick to its current lightweight model.

So far, the thread has surfaced several open questions: how to handle deferred hunks (persist them, stash them, or ignore them?), whether to extend `add -p`, create a new command, or adopt modular intent-based tools like GitButler’s, and how to balance simplicity with flexibility. The mention of Fugitive adds a concrete example of how other tools have tackled similar problems, which could help shape future proposals. For now, the discussion remains conceptual, with no decisions or agreements on the table.
