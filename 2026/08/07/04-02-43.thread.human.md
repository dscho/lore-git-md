This thread is about modernizing Git’s interactive patch selection workflow to eliminate the need for separate `git add -p` and `git checkout -p` commands, enabling users to stage, discard, or defer hunks in a single session. The discussion has evolved into a debate over three competing visions: Junio C Hamano’s incremental approach (extending `git add -p` to support discard/defer actions within Git’s existing prompt-loop UI), Patrick Steinhardt’s proposal to adopt a hierarchical TUI (text-based user interface) inspired by Jujutsu for non-linear hunk selection, and Stefan Haller’s suggestion to avoid internal UI changes entirely and instead improve Git’s APIs for external tools like lazygit.

The thread remains in the early design phase, with no patches or implementation sketches posted. The immediate consensus is on unifying triage actions (stage/discard/defer) into a single session, but the scope of the solution is contested. Junio’s latest reply reinforces the focus on the *mechanism* (a single command set) as the priority, while Patrick’s recent email reframes the discussion around *how much* UI modernization is necessary to solve the workflow problem. Patrick argues that Git should address clear gaps in its core workflows—such as the cumbersome need for separate commands—without overcommitting to a full UI rewrite. He draws a line between "core functionality" (e.g., hunk selection) and "full UI" (e.g., a TUI for history editing), suggesting that incremental improvements (like a navigable interface for hunks) are within scope.
