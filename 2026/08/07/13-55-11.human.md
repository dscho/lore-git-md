This is the final patch in Christian Couder’s five-patch series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators mark repositories as trusted for lazy fetching. The patch wires the new configuration into `upload-pack` by setting `GIT_NO_LAZY_FETCH=0` when the served repository is listed in the allowlist, effectively permitting lazy fetching for those repositories.

The implementation is straightforward: `upload-pack` checks the repository path against the `uploadpack.lazyFetchTrusted` allowlist (using the reusable `path_allowlist_apply()` helper introduced earlier in the series) and, if the repository is trusted and `GIT_NO_LAZY_FETCH` was not explicitly set, overrides the default `GIT_NO_LAZY_FETCH=1` to `0`. This environment variable is automatically inherited by the `pack-objects` child process, so no additional plumbing is needed. The patch also adds comprehensive documentation for the new configuration variable, including its security implications, syntax, and interaction with `GIT_NO_LAZY_FETCH`, and updates cross-references in the `git-upload-pack` and `git` man pages.

The new test script (`t/t5710-promisor-remote-capability.sh`) validates the end-to-end behavior: lazy fetching is permitted when the repository is listed in the protected allowlist, rejected when it is not, ignored when the configuration is set in the repository itself (rather than in protected scope), and overridden by an explicit `GIT_NO_LAZY_FETCH=1`. The tests confirm that the security model works as intended: only server operators can enable lazy fetching, and untrusted repositories cannot tamper with the setting.

This patch completes the series’ pivot from the earlier client-side `fromAccepted` proposal to a server-side trust model, addressing the core security objection by shifting control to the server operator. The series is well-structured, with each patch building on the previous ones to refactor, generalize, and integrate the new functionality. The implementation is clean, the documentation is thorough, and the test coverage is robust. Whether the security objection is fully satisfied will likely be the main point of discussion, but the series itself is technically sound and ready for review.
