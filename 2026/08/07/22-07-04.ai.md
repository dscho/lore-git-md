This is the ninth patch in Pablo Sabater’s ten-patch GSoC series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The patch is a small, targeted change that enables the server to advertise the "type" capability, completing the end-to-end chain for object type metadata.

The patch modifies `serve.c` to append "type" to the advertised capabilities string in `object_info_advertise()`, changing the comment from "Currently only size is supported" to "Currently only size and type are supported". This signals to the client that the server can handle type requests, allowing the client to include the "type" keyword in its protocol requests (as implemented in earlier patches). The change is minimal—just four lines, including the comment update—and touches only one line of code in `serve.c`.

The test suite in `t/t1017-cat-file-remote-object-info.sh` is updated to reflect the new functionality. The patch replaces the now-obsolete test for unsupported placeholders with two new tests: one verifying that `%(objecttype)` returns the actual type ("blob") for a known object, and another confirming that truly unsupported placeholders (e.g., `%(objectmode)`, `%(objectsize:disk)`) still return empty strings. The new tests use the same helper functions and setup as the rest of the test file, ensuring consistency. The patch also adds type variables (`hello_type`, `tree_type`, `commit_type`, `tag_type`) to the test preamble, mirroring the existing size and OID variables.

This patch is the penultimate step in the series, following the server-side parsing logic (patch 7/10) and client-side parsing logic (patch 8/10). With this change, the server now advertises, parses, and transmits object type data, and the client can request and display it. The final patch (10/10) will unify the default format string for all `cat-file` batch commands, removing the temporary exception for `remote-object-info` commands. The patch is uncontroversial, well-tested, and ready for integration. It has no dependencies beyond the earlier patches in the series and no open technical concerns. The commit message clearly explains the motivation and scope, and the code changes are mechanical and follow the established pattern from the predecessor series.
