This is a **design discussion contribution** in the ongoing thread about unifying Git’s interactive patch selection workflow. Junio C Hamano responds to D. Ben Knoble’s suggestion of adopting a more visual, TUI-like interface (inspired by Fugitive) by clarifying that the core issue he wants to address is *not* the linear prompt-loop UI, but rather the *directional limitation* of how modifications flow between the working tree, index, and discard state.

Junio acknowledges that the current "one hunk at a time" model is simple but restrictive—users cannot easily jump between hunks or revisit earlier decisions. However, he argues that this UI limitation is *orthogonal* to the real friction: the inability to triage hunks into three categories (stage, keep in working tree, or discard) in a single session. Today, users must first run `git add -p` to stage or defer hunks, then manually sift through the remaining hunks and run `git checkout -p` to discard unwanted ones. This two-step process is error-prone and cumbersome, even if the UI were more flexible.

His key point is that the workflow could be improved *without* abandoning the linear prompt-loop model. For example, `git add -p` could be extended to support a third action ("discard") alongside "stage" and "defer," eliminating the need for a separate `git checkout -p` step. This would address the core problem—triage efficiency—while keeping the UI lightweight. The discussion about TUI-like interfaces (e.g., Fugitive) remains relevant but is framed as a separate, longer-term consideration.

This email narrows the thread’s focus to a concrete, implementable goal: unifying the triage actions into a single session, regardless of UI style. It also sets up a potential tension between incremental improvement (extending `add -p`) and more ambitious redesigns (adopting a TUI or intent-based commands). The next steps may involve sketching out how the "discard" action could be integrated into the existing machinery (e.g., `add--interactive` or `add-interactive.c`).
