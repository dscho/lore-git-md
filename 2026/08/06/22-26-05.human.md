This is a feature request for `git fetch` that proposes separating the mapping of explicitly requested branches from the default fetch refspecs.

The author, Douglas Puchalski, describes a common workflow frustration: when a remote is configured to fetch only a limited set of branches by default (e.g., `main` and `team/*`), explicitly fetching an additional branch (e.g., `git fetch origin topic/example`) does not create or update the corresponding remote-tracking ref (`refs/remotes/origin/topic/example`). Instead, the branch is only available in `FETCH_HEAD`, which is ephemeral and can be overwritten by subsequent fetches. This breaks the natural `git checkout -b topic/example origin/topic/example` workflow, forcing users to either fetch all remote branches, manually specify a two-sided refspec, or rely on the fragile `FETCH_HEAD`.

The request is for a configuration or default behavior that automatically maps explicitly requested branches to their corresponding remote-tracking refs, while preserving the restricted default fetch set. The author suggests this could be opt-in to avoid breaking existing scripts that depend on the current behavior. The proposal is well-motivated and addresses a real pain point for users who work with large repositories but occasionally need to fetch and track additional branches.

No patch is provided—this is purely a request for discussion. The idea seems reasonable and aligns with Git’s general philosophy of making common workflows more ergonomic. Whether it gains traction will likely depend on how invasive the implementation would be and whether the backward-compatibility concerns can be addressed cleanly. For now, this is worth watching for users who share the same frustration.
