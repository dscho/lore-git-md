This is the second patch in Patrick Steinhardt’s v4 series making on-disk ODB structures pluggable, and it fixes a latent correctness bug in how Git loads loose object maps for repositories using compatibility hash algorithms.

The patch detangles the loading of loose object maps from repository setup by moving the logic into the "loose" ODB backend. Previously, `repo_set_compat_hash_algo()` unconditionally downcast the primary ODB to the "files" backend, which would BUG if a different backend type were used with a compatibility hash algorithm. The fix is straightforward: the loose object map is now loaded directly in `odb_source_loose_new()`, ensuring the check happens at the right layer and only for the relevant backend. The `should_use_loose_object_map()` guard is also moved to the backend level, making the logic source-local and avoiding assumptions about the ODB type.

The commit message clearly explains the problem (unconditional downcast, intermixed setup/configuration) and the solution (backend-local loading). The diff is small and focused, touching only the loose backend and repository setup code. This patch is uncontroversial and ready for merging; it was already acknowledged in Junio’s "What's cooking" report as part of the series that is under review. The regression test added in the first patch (for SHA-256 repositories with SHA-1 compatibility) ensures the fix works as intended.
