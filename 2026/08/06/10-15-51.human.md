This is the second patch in the v4 series adding new path-related keys to `git repo info`. It introduces `path.superproject-root.absolute` and `path.superproject-root.relative` to expose the top-level working tree of a superproject when the current repository is a submodule.

The patch is clean and well-structured: it adds the new keys to `builtin/repo.c`, documents them in `Documentation/git-repo.adoc`, and includes thorough tests in `t/t1900-repo-info.sh`. The implementation uses `get_superproject_working_tree()` and `format_path()` to return absolute or relative paths, matching the behavior of `git rev-parse --show-superproject-working-tree`. When not inside a submodule, both keys return an empty string, which aligns with the series' design principle of using empty strings for inapplicable contexts.

The naming (`superproject-root`) is now uncontroversial after feedback in earlier versions, and the commit message clearly explains the motivation: scripts in multi-repository setups need a scriptable way to identify the superproject's root. The tests cover both submodule and non-submodule cases, including edge cases like relative paths.

This patch is part of a larger GSoC effort to make repository component paths more accessible via `git repo info`. It looks ready for substantive review, though reviewers may still suggest minor adjustments to key naming or documentation phrasing for consistency with existing Git terminology. The series as a whole is mechanically clean and addresses all prior feedback.
