This is the sixth patch in the v3 series introducing `git repack --drop-filtered`, a feature for partial clones to reclaim disk space by dropping large promisor blobs. This patch adds two safety guards to prevent poor user experience: it refuses to run during ongoing operations (merge, rebase, cherry-pick, etc.) and refuses to drop blobs currently referenced by the index.

The guards are implemented in `builtin/repack.c` using `wt_status_get_state()` to detect in-progress operations and `repo_read_index()` to check for index references. Both checks are skipped for bare repositories. The error messages are specific and actionable: "cannot be used while another operation is in progress" and "cannot drop '<path>' (<oid>): it is referenced by the current index". The accompanying test script (`t/t7706-repack-drop-filtered.sh`) adds two new cases: one for merge conflicts and one for index-referenced blobs.

The commit message now frames these guards as UX optimizations rather than correctness measures, reflecting the discussion in earlier rounds where Junio proposed replacing them with a time-based heuristic. The implementation remains unchanged, but the rationale is softer: the guards avoid redundant lazy-fetches rather than being strictly necessary for safety. This patch is well-tested and production-ready, though the broader debate about the best way to avoid redundant network operations is still open.
