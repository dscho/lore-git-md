Thread identity: Feature request for `git fetch` to decouple default fetch refspec from explicit branch mapping. Originating author: Douglas Puchalski (dpuchals). Thread type: RFC (no patch provided).

Core problem or goal: Enable `git fetch` to automatically map explicitly named branches (e.g., `git fetch origin topic/example`) to their corresponding remote-tracking refs (`refs/remotes/origin/topic/example`) even when the remote’s default fetch refspec is restricted (e.g., only `main` and `team/*`), without requiring opt-out workarounds or fetching all remote branches. The goal is to preserve the restricted default fetch set while allowing automatic remote-tracking ref updates for explicitly fetched branches.

Current status: Design discussion stage with maintainer feedback shaping the approach. Junio C Hamano has proposed a design direction leveraging the existing `--refmap` mechanism, extended to support a `matching`-like mode (analogous to `git push`’s `push.default=matching`). This would allow everyday fetches to automatically update all remote-tracking refs that match the configured `refmap`, while explicitly fetching a new branch would extend the set of refs managed by future fetches. No new configuration knobs (e.g., `remote.<remote>.fetchMap`) are proposed; instead, the solution would build on `--refmap` and potentially make it configurable per-remote (e.g., `remote.<name>.refmap`). Phillip Wood’s earlier proposal for a dedicated mapping layer remains an alternative but is not the current focus. No implementation or patch exists yet; backward compatibility is preserved, and the solution would be opt-in.

Key technical details:
- Subsystems/files likely affected: `builtin/fetch.c`, `remote.c`/`remote.h` (fetch refspec logic), and configuration handling (e.g., potential new `remote.<name>.refmap` configuration).
- Current behavior: Explicitly named branches are fetched into `FETCH_HEAD` but not mapped to remote-tracking refs unless they match the default fetch refspec. Refpec matching follows a "first match wins" rule, not longest match.
- Proposed behavior: Extend `--refmap` to support a `matching`-like mode where `git fetch` automatically updates all remote-tracking refs that match the configured `refmap`. Explicitly fetching a branch (e.g., `git fetch origin a-new-topic`) would create the corresponding remote-tracking ref (`refs/remotes/origin/a-new-topic`), extending the set of refs managed by future fetches. The default fetch refspec remains restricted, but the `refmap` configuration (or `--refmap` flag) defines which remote-tracking refs are updated.
- On-disk format: No changes anticipated; this remains a behavioral/configuration change.
- Test coverage: Not yet discussed, but would likely involve tests for `git fetch` with restricted refspecs, explicit branch names, `--refmap`/`remote.<name>.refmap` interactions, the proposed `matching` mode, and `git push` equivalents, verifying remote-tracking ref updates, `FETCH_HEAD` behavior, and refspec precedence.

Open questions and loose ends:
- Whether the `--refmap` + `matching`-like mode fully addresses the original problem (e.g., does it preserve the restricted default fetch set while allowing explicit branch mapping?).
- How the proposed `matching` mode would interact with existing refspec logic, including the "first match wins" rule and edge cases like overlapping branch names or multiple remotes.
- Whether the `refmap` configuration (e.g., `remote.<name>.refmap`) would apply globally to all fetches from the remote or only to explicitly named branches.
- Interaction with other fetch features (e.g., `--prune`, `--all`, `--tags`).
- No feedback or positions from other reviewers beyond Junio and Phillip Wood; no implementation details or patches yet.
