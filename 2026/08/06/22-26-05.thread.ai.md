Thread identity: Feature request for `git fetch` to decouple default fetch refspec from explicit branch mapping. Originating author: Douglas Puchalski (dpuchals). Thread type: RFC (no patch provided).

Core problem or goal: Address the workflow limitation where explicitly fetching a branch (e.g., `git fetch origin topic/example`) does not create or update the corresponding remote-tracking ref (`refs/remotes/origin/topic/example`) when the remote’s default fetch refspec is restricted (e.g., only `main` and `team/*`). The goal is to enable automatic mapping of explicitly named branches to their remote-tracking refs while preserving the restricted default fetch set, without requiring opt-out workarounds or fetching all remote branches.

Current status: Proposal stage with maintainer feedback. Junio C Hamano has suggested an alternative approach using the existing `--refmap` option, possibly extended via configuration (e.g., `remote.<name>.refmap`). No design or implementation details yet. Backward compatibility remains a constraint, and the solution would likely remain opt-in.

Key technical details:
- Subsystems/files likely affected: `builtin/fetch.c`, `remote.c`/`remote.h` (fetch refspec logic), and configuration handling (e.g., potential new `remote.<name>.refmap` knob).
- Current behavior: Explicitly named branches are fetched into `FETCH_HEAD` but not mapped to remote-tracking refs unless they match the default fetch refspec.
- Proposed behavior: Junio suggests leveraging `--refmap` (e.g., `git fetch --refmap="refs/heads/*:refs/remotes/origin/*" origin topic/example`) and making it configurable per-remote to avoid manual repetition.
- On-disk format: No changes anticipated; this remains a behavioral/configuration change.
- Test coverage: Not yet discussed, but would likely involve tests for `git fetch` with restricted refspecs, explicit branch names, and `--refmap`/`remote.<name>.refmap` interactions, verifying remote-tracking ref updates and `FETCH_HEAD` behavior.

- How the proposed configuration would interact with existing `remote.<name>.fetch` settings (e.g., precedence, merging, or overriding).
- Whether the configuration would apply globally to all fetches from the remote or only to explicitly named branches.
- Edge cases: branch names conflicting with default refspec patterns, multiple remotes with overlapping branch names, and interaction with other fetch features (e.g., `--prune`, `--all`, `--tags`).
