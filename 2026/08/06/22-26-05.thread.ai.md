Thread identity: Feature request for `git fetch` to decouple default fetch refspec from explicit branch mapping. Originating author: Douglas Puchalski (dpuchals). Thread type: RFC (no patch provided).

Core problem or goal: Address the workflow limitation where explicitly fetching a branch (e.g., `git fetch origin topic/example`) does not create or update the corresponding remote-tracking ref (`refs/remotes/origin/topic/example`) when the remote’s default fetch refspec is restricted (e.g., only `main` and `team/*`). The goal is to enable automatic mapping of explicitly named branches to their remote-tracking refs while preserving the restricted default fetch set, without requiring opt-out workarounds or fetching all remote branches.

Current status: Proposal stage with maintainer and reviewer feedback. Junio C Hamano suggested leveraging the existing `--refmap` option, possibly extended via configuration (e.g., `remote.<name>.refmap`). Phillip Wood endorsed the goal and proposed a new configuration variable (`remote.<remote>.fetchMap`) acting as a pure mapping layer, while also suggesting extending the idea to `git push`. No design or implementation details yet; backward compatibility remains a constraint, and any solution would likely remain opt-in.

Key technical details:
- Subsystems/files likely affected: `builtin/fetch.c`, `remote.c`/`remote.h` (fetch refspec logic), and configuration handling (e.g., potential new `remote.<name>.refmap` or `remote.<remote>.fetchMap` knobs).
- Current behavior: Explicitly named branches are fetched into `FETCH_HEAD` but not mapped to remote-tracking refs unless they match the default fetch refspec. Refpec matching follows a "first match wins" rule, not longest match, complicating branch-specific mappings.
- Proposed behavior: Junio suggests leveraging `--refmap` (e.g., `git fetch --refmap="refs/heads/*:refs/remotes/origin/*" origin topic/example`) and making it configurable per-remote. Phillip Wood proposes a dedicated mapping layer (`remote.<remote>.fetchMap`) that leaves default fetch/push sets untouched.
- On-disk format: No changes anticipated; this remains a behavioral/configuration change.
- Test coverage: Not yet discussed, but would likely involve tests for `git fetch` with restricted refspecs, explicit branch names, `--refmap`/`remote.<name>.refmap`/`remote.<remote>.fetchMap` interactions, and `git push` equivalents, verifying remote-tracking ref updates, `FETCH_HEAD` behavior, and refspec precedence.

Open questions and loose ends:
- Whether the `--refmap` approach fully addresses the original problem (e.g., does it preserve the restricted default fetch set while allowing explicit branch mapping?).
- How to implement the opt-in mechanism (configuration knob like `remote.<name>.refmap` or `remote.<remote>.fetchMap`, command-line flag, or other).
- How the proposed configuration would interact with existing `remote.<name>.fetch` settings (e.g., precedence, merging, or overriding).
- Whether the configuration would apply globally to all fetches from the remote or only to explicitly named branches.
- Edge cases: branch names conflicting with default refspec patterns, multiple remotes with overlapping branch names, interaction with other fetch features (e.g., `--prune`, `--all`, `--tags`), and the "first match wins" refspec rule.
- No feedback or positions from other reviewers yet beyond Junio and Phillip Wood.
