This thread is about a feature request from Douglas Puchalski to change how `git fetch` handles explicitly named branches when the remote’s default fetch refspec is restricted. Currently, fetching a branch like `git fetch origin topic/example` doesn’t update the corresponding remote-tracking ref (`refs/remotes/origin/topic/example`) unless the branch matches the default fetch refspec (e.g., `main` or `team/*`). This breaks workflows that rely on `git checkout -b <branch> origin/<branch>`, forcing users to use `FETCH_HEAD` or manually specify a refspec.

Junio C Hamano, the maintainer, responded with an alternative approach: instead of modifying the default fetch behavior, he suggested making the existing `--refmap` option more accessible via configuration. The `--refmap` flag currently allows users to override the default refspec mapping for a single fetch (e.g., `git fetch --refmap="refs/heads/*:refs/remotes/origin/*" origin topic/example`). Junio proposed introducing a configuration variable like `remote.<name>.refmap` to apply a custom refmap automatically for all fetches from a remote. This would preserve backward compatibility while enabling the desired workflow without requiring users to repeat the refmap on every command. The response is exploratory, leaving the next steps to the author to either propose a patch based on this suggestion or explain why `--refmap` (even with configuration support) doesn’t fully address the problem.

No other participants have weighed in yet, and the discussion is still in the early stages. Key open questions include how the proposed configuration would interact with existing `remote.<name>.fetch` settings and whether it would apply globally or only to explicitly named branches. The thread remains at the proposal stage, with no design or implementation details yet.
