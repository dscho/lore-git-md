This thread is about a feature request from Douglas Puchalski to improve `git fetch` so that explicitly fetching a branch (like `git fetch origin topic/example`) automatically creates or updates the corresponding remote-tracking ref (`refs/remotes/origin/topic/example`), even when the remote’s default fetch refspec is restricted (e.g., only `main` and `team/*`). Currently, such branches are fetched into `FETCH_HEAD` but not mapped to remote-tracking refs unless they match the default refspec.

Junio C Hamano suggested an alternative approach using Git’s existing `--refmap` option, possibly extended via configuration (e.g., `remote.<name>.refmap`), to avoid manual repetition while preserving backward compatibility. Phillip Wood has now weighed in, endorsing the goal and proposing a new configuration variable (e.g., `remote.<remote>.fetchMap`) that would act as a pure mapping layer, leaving the default fetch and push sets untouched. He also noted a quirk in Git’s refspec matching—where the first match wins, not the longest—which complicates adding branch-specific mappings via configuration.

The discussion remains in the proposal stage, with no implementation details or patches yet. Key open questions include whether the `--refmap` approach fully addresses the original problem, how the proposed configuration would interact with existing settings, and whether it would apply globally or only to explicitly named branches. The thread has yet to attract broader review, but the maintainer’s and Phillip Wood’s feedback suggests the feature is seen as worthwhile if implemented carefully.
