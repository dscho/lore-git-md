This thread is about a feature request from Douglas Puchalski to improve `git fetch` so that explicitly fetching a branch (like `git fetch origin topic/example`) automatically creates or updates the corresponding remote-tracking ref (`refs/remotes/origin/topic/example`), even when the remote’s default fetch refspec is restricted (e.g., only fetching `main` and `team/*`). Currently, such branches are fetched into `FETCH_HEAD` but not mapped to remote-tracking refs unless they match the default refspec.

Junio C Hamano and Phillip Wood have weighed in on the design. Junio now proposes extending the existing `--refmap` mechanism to achieve this, avoiding new configuration knobs like Phillip’s suggested `remote.<remote>.fetchMap`. His idea is to introduce a `matching`-like mode for `git fetch` that automatically updates all remote-tracking refs matching the configured `refmap`, allowing everyday fetches to reverse-map existing refs to decide which remote branches to fetch. Explicitly fetching a new branch would then automatically create its remote-tracking ref, extending the set managed by future fetches. This approach keeps the change opt-in and backward-compatible, though it doesn’t yet address edge cases like overlapping branch names or `--prune` interactions.

Phillip Wood had previously endorsed the goal and suggested a dedicated mapping layer (`remote.<remote>.fetchMap`) that wouldn’t interfere with default fetch/push sets, also proposing extending the idea to `git push`. Junio’s latest email solidifies his preference for building on `--refmap` instead. The thread remains in the design phase, with no implementation or patches yet, and no feedback from other reviewers beyond Junio and Phillip. The key open questions are whether Junio’s `--refmap` approach fully addresses the original problem and how it would interact with existing refspec logic.
