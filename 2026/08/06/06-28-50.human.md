This is a performance-focused refactoring patch series that revives a previously reverted `writev(3p)`-like wrapper to reduce system call overhead in Git’s low-level I/O operations. The series, authored by Patrick Steinhardt, reintroduces the wrapper (now named `git_write_gather()`) with fixes for earlier platform compatibility issues (NonStop, CMake) and applies it to pktline transmission in `sideband.c` and cat-blob responses in `fast-import.c`. All technical design and correctness concerns—including integer-overflow safety, API naming, and atomicity requirements—have been resolved through discussion with Junio C Hamano, Johannes Sixt, and Simon Richter. The series is now technically complete, with no unresolved issues, but awaits Junio’s assessment of whether the performance gains justify the added complexity.

The patch touches build system files (`Makefile`, `CMakeLists.txt`, `meson.build`), compatibility layers (`compat/posix.h`, `compat/writev.c`), and core I/O wrappers (`wrapper.{c,h}`, `write-or-die.{c,h}`), along with the two targeted call sites. The new `git_write_gather()` API is explicitly documented as non-atomic, addressing concerns about future misuse, and is implemented as a loop of `write(2)` calls where `writev(2)` is unavailable. While benchmarks are referenced, their results aren’t included in the email, leaving the magnitude of the performance improvement unclear.

Patrick’s latest reply suggests a minor optimization to restore non-interleaving behavior in the compatibility wrapper by writing only the first iovec, which wouldn’t sacrifice efficiency. This is a small refinement rather than a fundamental change, and the series appears ready for a reroll once Patrick returns from his offsite. The main open question is Junio’s appetite for merging it, given the prior revert and the trade-off between performance and code complexity. The discussion has been thorough and collaborative, with no signs of controversy—just a final maintainer decision pending.
