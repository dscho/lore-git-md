This is a follow-up in the ongoing discussion about a bug in `git rebase -x` where notes are lost when combined with `git commit --amend`. The thread remains focused on diagnosing and proposing fixes for the issue in the rebase and notes subsystems.

D. Ben Knoble acknowledges Phillip Wood’s explanation of the root cause: during a rebase with an external command (`-x`), the notes are incorrectly mapped to the pre-amend commit OID rather than the post-amend one. This happens because the rebase machinery records the new OID *before* the external command runs, so `git commit --amend` creates a new OID that the notes-rewriting step doesn’t account for.

Knoble explores two potential workarounds. First, he suggests exposing the rebase’s internal OID mapping (old-to-new commits) to external commands, allowing them to handle note copying or other rewrites directly. Second, he proposes a post-rebase mechanism to feed the OID mapping to `git notes copy` or similar commands, though he notes this would require parsing or manual intervention, which feels brittle. Neither idea is fleshed out as a concrete patch, but they reflect practical user-level concerns about how to recover from or avoid the bug in the short term.

The discussion reinforces the two fix strategies already on the table: Phillip’s prior approach (updating the rebase’s `rewritten` file after `--amend`) and his newer proposal (copying notes *before* stopping for `exec` or `edit`). Knoble’s questions don’t resolve the trade-offs between these approaches but highlight the need for a solution that is both robust and user-friendly. The thread remains conceptual, with no test cases or implementation details yet, so the bug is still open and unpatched. For now, users should avoid combining `git rebase -x` with `git commit --amend` if they rely on notes.
