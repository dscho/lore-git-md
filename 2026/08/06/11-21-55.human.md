This is the v3 patch series for `git repack --drop-filtered`, a new feature that lets partial clone users safely reclaim disk space by dropping locally cached promisor blobs over a size threshold. The series is now ready for final review after addressing feedback from v2: it fixes a subtle bitmap validation bug (explicit `-b` is now always rejected, even when `repack.writeBitmaps` is set in config), softens the documentation language to acknowledge remote availability risks, and reframes the safety guards as convenience measures rather than correctness requirements.

The implementation is unchanged from v2 in its core mechanics: it enumerates promisor blobs via `ODB_FOR_EACH_OBJECT_PROMISOR_ONLY`, filters them by size, and rebuilds the promisor pack while excluding the selected blobs. The repack machinery’s existing crash-safety guarantees (write, fsync, install, then delete) ensure the operation is safe. The `--dry-run` option lists candidates without making changes. The two safety guards—refusing to run during merges/rebase/cherry-pick and refusing to drop blobs referenced by the current index—are now explicitly documented as optimizations to avoid immediate re-fetching, not as correctness measures. Both are skipped for bare repositories.

The series is well-structured, with tests distributed across the relevant commits and clear commit messages. The deferred work (remote verification, a "don’t cull recently-fetched objects" heuristic, and a drop log) is explicitly scoped and does not block the core functionality. This looks like a production-ready feature that addresses a real pain point for partial clone users. The author has responded thoughtfully to feedback, and the series now reflects a mature understanding of the trade-offs involved. Worth attention from anyone interested in partial clones or repack optimizations.
