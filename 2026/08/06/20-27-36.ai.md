This is the first patch in a four-part series adding Bash completion for the `git history` command. It introduces the core completion logic for subcommands and their options, focusing on the common pattern where every `git history` subcommand starts with a revision argument.

The patch adds a new helper function `__git_history_has_revision` that scans the command line to determine whether a revision has already been provided. The main `_git_history` completion function uses this to decide whether to complete a revision (using `__git_complete_refs`) or delegate to subcommand-specific logic. The implementation correctly handles `--` termination by suppressing option completion after it, and avoids completing options when the cursor is on a revision argument.

Tests in `t/t9902-completion.sh` verify that subcommands are completed, options are suggested before and after revisions (but not after `--`), and revision completion works as expected. The v2 revision addresses feedback from v1 by tightening revision handling (exactly one required revision) and expanding test coverage.

This patch is narrowly scoped to the completion infrastructure and does not modify the `git history` command itself. The code is clean, the commit message is clear, and the test cases cover the main scenarios. The series appears uncontroversial and ready for integration.
