This is the v4 cover letter for Patrick Steinhardt’s six-patch series that makes the creation of on-disk object database (ODB) structures pluggable. The series is part of the ongoing ODB abstraction effort and is now split into two distinct tracks: the first patch (a correctness fix for loose-object map loading) is slated for early graduation to `next`, while the remaining five patches await a revised fourth patch before merging.

The core goal remains unchanged: decouple the creation of backend-specific on-disk structures (e.g., `objects/info`, `objects/pack`) from the generic repository setup code. The top-level `objects/` directory is still mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback in the ODB source interface. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic.

Key changes in v4 reflect concessions to Toon Claes’s alternative design proposal. The `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag introduced in v3 is now dropped entirely, and `odb_new()` is moved out of `apply_repository_format()` to make ODB creation an explicit step at every call site. This change is mechanical and affects only the initialization sequence, but it directly reverts the refactoring introduced in the original fourth patch. The concession does not block Patrick’s longer-term goal of moving `apply_repository_format()` into `repo_init()`. Other minor cleanups include removing a redundant `xstrdup()` call and marking a new `die()` message as translatable.

Files touched span `odb.c`, `odb.h`, `setup.c`, `repository.c`, and backend-specific source files (`odb/source-files.c`, `odb/source-loose.c`). New or renamed symbols include the `create_on_disk` callback, `safe_create_dir()`, and `odb_source_type_to_name()`. The series is based on the recent "7th batch" integration (commit `9a0c4701dc`), indicating it targets the current development cycle.

The first patch’s status as a correctness fix with dedicated test coverage (Toon Claes’s test case for SHA-256 repositories with SHA-1 compatibility) is now explicitly recognized in Junio’s "What's cooking" report (2025-06-10), which lists it as "will merge to 'next'." The remaining patches are uncontroversial but blocked pending the revised fourth patch. The architectural discussion about initialization sequence design is now resolved in favor of the simpler, unified approach.
