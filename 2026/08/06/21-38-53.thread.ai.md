Subject: [PATCH 0/6] receive-pack: use ODB transaction for pluggable packfile writes
Series version: v2 (with follow-up fix for critical lockfile lifecycle flaw; v3 will incorporate mechanical refinements to `unpack_limit` resolution, address Junio’s feedback on transaction lifecycle, lockfile migration, backend design flaws, per-repository unpack limit storage, new `*_or_die()` helpers, and resolve the "files" backend’s misuse of `repo->objects->sources[0]`)
Originating author: Justin Tobler
Thread type: patch series

Core problem or goal
Extend the ODB transaction system to make `git receive-pack` fully backend-agnostic by replacing its hardcoded use of `git index-pack` and `git unpack-objects` (which assume the "files" backend) with a new generic transaction interface, `odb_transaction_write_pack()`. The goal is to enable alternative ODB backends (e.g., reftable, cloud storage) to handle incoming packfiles without being tied to the traditional files backend.

Current status
Under active review; series updated to v2 with a follow-up fix for a **critical design flaw** in the "files" backend’s lockfile lifecycle. Still cooking in `seen`; no merge status change. The next iteration (v3) will focus on: (1) mechanical refinements to `unpack_limit` resolution (adopting Patrick Steinhardt’s proposed non-caching, `unsigned int` version and directly reading the configuration via `repo_config_get_uint()` with a default of 100), (2) evaluating Junio’s suggestion to store the unpack limit as a per-repository setting in `repo->settings` or `repo->config_values` (this remains an open design decision for v3), (3) ensuring `odb_transaction_finalize()` is invoked on all code paths, including non-local exits, (4) fixing the lockfile migration issue in the "files" backend (where tempfile structures reference pre-migration paths, causing `finalize()` to fail silently), (5) adding `odb_transaction_finalize_or_die()` and `odb_transaction_commit_or_die()` helpers to allow callers to opt into stricter error handling while preserving backward compatibility, (6) evaluating whether the base `finalize()` and `commit()` functions should return `void` (since no callers check their return values, but the new `*_or_die()` helpers would provide an alternative for stricter contexts), (7) correcting the "files" backend’s misuse of `repo->objects->sources[0]` instead of `base->source` in `odb_transaction_files_write_pack()`, and (8) addressing the future source-tracking design debt identified in Junio’s review of patch 7/7, where the transaction’s source (`base->source`) is ignored in favor of the first source in `repo->objects->sources`. The author has now fixed the immediate lockfile lifecycle flaw by passing the correct ODB source (`base->source`) to `index_pack_lockfile()`, ensuring lockfile paths remain valid post-commit.

Open questions and loose ends
- **Unpack limit storage**: Junio Hamano’s review of patch 3/7 suggests storing the unpack limit as a per-repository setting in `repo->settings` or `repo->config_values` rather than using a `static int` inside `get_unpack_limit()`. Justin Tobler has agreed to adopt a non-caching, `unsigned int` version that directly reads the configuration via `repo_config_get_uint()` and defaults to 100, but the per-repository storage suggestion remains an open design decision for v3. This would align with Git’s broader pattern of avoiding static variables in favor of explicit repository state, especially as the ODB abstraction effort progresses toward supporting multiple backends and repositories.
- **Transaction lifecycle design**: Junio Hamano’s review highlights three issues: (1) `finalize()` is bypassed on non-local exits (e.g., `exit(128)` after `report_path_error()` in `cmd_add()`), undermining deferred cleanup, (2) the **critical design flaw** in the "files" backend’s lockfile migration, where tempfile structures reference pre-migration paths but the lockfiles themselves are moved during `odb_transaction_files_commit()`, causing `finalize()` to fail silently (now fixed in the follow-up by passing `base->source` to `index_pack_lockfile()`), and (3) no callers check the return values of `finalize()` or `commit()`, raising the question of whether these functions should return `void`. The author has agreed to restructure the code to ensure `finalize()` is invoked on all code paths and will add `*_or_die()` helpers to allow callers to opt into stricter error handling. The follow-up fix clarifies that `.keep` files are tied to the `finalize` callback (not `release`), and callers must ensure reference updates are complete before invoking `finalize()`.
- **Error reporting ergonomics**: the shift to `strbuf` output parameters is complete, with const-correctness refinements incorporated. The `unpack_status` buffer is initialized once per invocation of `cmd_receive_pack()`, so reuse is unnecessary. The author proposes adding `odb_transaction_finalize_or_die()` and `odb_transaction_commit_or_die()` helpers to mirror the existing `odb_transaction_begin_or_die()` pattern, allowing callers to opt into stricter error handling where appropriate. The existing `receive-pack` caller already checks `commit()` errors, so the interface’s flexibility is not purely theoretical.
- **File descriptor passing**: the explicit file descriptor passing for the incoming packfile in `unpack()` is now part of the interface; reviewers may evaluate whether this abstraction is ergonomic and whether it interacts cleanly with the new `odb_transaction_write_pack()` interface.
- **Struct initialization and mutation patterns**: the ternary initialization of `fsck_objects` and the late assignment of `err_fd` in `unpack_with_sideband()` remain as trade-offs for the larger goal of removing global state. Patrick Steinhardt accepted these as necessary but invited future scrutiny when the function moves to a different file.
- **Design flaw in "files" backend**: Junio Hamano identified a bug in `odb_transaction_files_write_pack()` where the transaction’s source (`base->source`) is ignored in favor of `repo->objects->sources[0]`. This could lead to subtle bugs if multiple ODB backends are in use. The fix is straightforward (replace `repo->objects->sources` with `base->source`), but the issue highlights the importance of respecting the transaction’s source context as the ODB abstraction effort matures. The author acknowledges the fragility of this approach and plans to address it in a follow-up by stopping the reordering of the source list during transaction startup and tracking the source separately, treating this as technical debt rather than a blocker for the current series.
