Subject: [PATCH 0/6] receive-pack: use ODB transaction for pluggable packfile writes
Series version: v1 (initial)
Originating author: Justin Tobler
Thread type: patch series

Core problem or goal
Extend the ODB transaction system to make `git receive-pack` fully backend-agnostic by replacing its hardcoded use of `git index-pack` and `git unpack-objects` (which assume the "files" backend) with a new generic transaction interface, `odb_transaction_write_pack()`. The goal is to enable alternative ODB backends (e.g., reftable, cloud storage) to handle incoming packfiles without being tied to the traditional files backend.

Current status
Under active review; not yet merged. Series remains at v1, posted by Justin Tobler as part of the ongoing ODB abstraction effort led by Patrick Steinhardt. No merge status change; still cooking in `seen` or under review.

Key technical details
- New symbols: `odb_transaction_release()` (decouples transaction cleanup from commit, enabling backend-specific deferred cleanup such as removing ".keep" lockfiles), `odb_transaction_write_pack()` (generic interface for packfile writes, introduced in patch 6/6), `struct odb_transaction_write_pack_opts` (bundles previously global unpack options: shallow file, fsck settings, max input size, etc.), and `struct unpack_opts` (bundles previously global variables in `builtin/receive-pack.c` to eliminate reliance on globals). The `write_pack` callback is added to `struct odb_transaction`.
- Files touched: `builtin/receive-pack.c` (main refactoring target: explicit shallow-file path passing through the call chain, introduction of `struct unpack_opts`, conversion of error reporting from direct string returns to `strbuf` output parameters in `unpack()` and `unpack_with_sideband()`, explicit file descriptor passing for the incoming packfile in `unpack()`, and replacement of `unpack()` with calls to `odb_transaction_write_pack()`), `odb/transaction.c` (new API and core transaction logic), `object-file.c` (implementation of the "files" backend for `odb_transaction_write_pack()`), related headers, plus mechanical updates in `builtin/add.c`, `builtin/unpack-objects.c`, `builtin/update-index.c`, `cache-tree.c`, and `object-file.c` to adopt the new `release` callback.
- Behavior change: `receive-pack` no longer directly invokes `git index-pack` or `git unpack-objects`; instead, it delegates packfile processing to the ODB backend via the transaction system. The first five patches are plumbing-only and do not change observable behavior. The sixth patch completes the switch to backend-agnostic packfile processing by introducing `odb_transaction_write_pack()` and moving the packfile ingestion logic into `object-file.c`, where it becomes the "files" backend implementation.
- On-disk format: no changes; the series remains plumbing-only.
- Test coverage: relies on existing `receive-pack` and transaction tests. No test failures or edge cases introduced by the series.

Open questions and loose ends
- Transaction lifecycle design: the author and Patrick Steinhardt now both question whether `odb_transaction_release()` is the best place for post-commit cleanup of ".keep" lockfiles (owned by the transaction and removed in the backend’s `release` callback). Patrick suggests renaming the function to `odb_transaction_finalize()` and making it capable of reporting errors, as failures in cleaning up ".keep" files (which can occur in the "files" backend) should not be silently ignored. The commit message should also highlight that `builtin/receive-pack.c` is the only caller where the transaction is not released immediately after commit, because it needs to retain ".keep" files until references are updated.
- Abstraction robustness: reviewers will likely focus on whether the new `odb_transaction_write_pack()` interface is sufficiently generic and whether error handling remains robust across the split between `commit` and `release`.
- Global state removal: the second and third patches explicitly address the removal of global variables (`alt_shallow_file` and others bundled in `struct unpack_opts`). Patrick Steinhardt’s review of patch 2/6 confirmed the mechanical soundness of the approach, and his review of patch 3/6 is similarly positive but flags ergonomic concerns: (1) the diff is hard to audit for completeness due to scattered global references, (2) the ternary initialization of `fsck_objects` inside the struct initializer is visually awkward, and (3) the late assignment of `err_fd` in `unpack_with_sideband()` forces mutation of the passed-in struct, which feels unergonomic. Steinhardt accepts these trade-offs as necessary for the larger goal but invites future scrutiny when the function moves to a different file in a later patch.
- Error reporting ergonomics: the fourth patch shifts error reporting from direct string returns to `strbuf` output parameters. Patrick Steinhardt’s review of this patch finds the new calling convention clearer than the previous opaque string return but suggests two refinements: (1) marking the `strbuf` parameters in `report()` and `report_v2()` as `const` for const-correctness, and (2) reusing the `unpack_status` buffer across multiple runs to reduce memory allocations. No objections to the patch’s core goal or approach are raised.
- File descriptor passing: the fifth patch introduces explicit file descriptor passing for the incoming packfile in `unpack()`; reviewers may evaluate whether this abstraction is ergonomic and whether it interacts cleanly with the new `odb_transaction_write_pack()` interface.
- Backend-specific optimizations: Patrick Steinhardt raises two questions about the final patch: (1) whether `odb_reprepare()` (which refreshes the entire object database after packfile ingestion) is overly broad now that the logic is part of an ODB transaction, suggesting it might suffice to reprepare only the transaction’s source ODB, and (2) whether `unpack_limit` (a threshold for storing objects in loose vs. packed format) belongs in the generic `odb_transaction_write_pack_opts` struct, given that it is irrelevant to backends that do not use loose/packed storage, proposing instead to handle it internally in the backend.

Participant positions
- Justin Tobler (author): proposed the series, acknowledged design uncertainty around the transaction lifecycle (specifically whether `release` is the right place for post-commit cleanup), and seeks reviewer feedback. The series demonstrates mechanical refactoring to remove global state, prepare for explicit file descriptor passing, and lay the groundwork for the ODB transaction interface. The author presents these changes as uncontroversial but subject to reviewer scrutiny on ergonomics, scalability, and robustness.
- Patrick Steinhardt (ODB abstraction lead): reviewed patch 1/6, patch 2/6, patch 3/6, patch 4/6, and patch 6/6 substantively. Engages with the design of `odb_transaction_release()`, suggesting renaming it to `odb_transaction_finalize()` and making it capable of reporting errors. Notes that `builtin/receive-pack.c` is the only caller where the transaction is not released immediately after commit, due to the need to retain ".keep" files until references are updated. Raises concerns about silently ignoring cleanup failures (e.g., ".keep" file removal) and invites further discussion on the interface’s ergonomics and robustness. No objections to the series’ direction, but flags the transaction lifecycle, struct ergonomics, error reporting, and backend-specific optimizations as open design questions. Confirms the mechanical soundness of the global state removal in patches 2/6 and 3/6, calling the refactoring clean and aligned with the series’ goals, though he notes ergonomic friction in the struct initialization and mutation patterns. In his review of patch 4/6, he accepts the shift to `strbuf` output parameters as an improvement but suggests const-correctness refinements and a potential optimization to reuse the `unpack_status` buffer. In his review of patch 6/6, he calls the patch "nicely done" and notes that most of the code was simply moved from `builtin/receive-pack.c` to `object-file.c` with minimal changes, successfully shifting ownership of `.keep` lockfiles from a global `pack_lockfile` tempfile to the transaction itself. He raises two substantive questions about backend-specific optimizations (`odb_reprepare()` and `unpack_limit`) but frames them as forward-looking design considerations rather than blockers.
