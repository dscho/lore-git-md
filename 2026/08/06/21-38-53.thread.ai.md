Subject: [PATCH 0/6] receive-pack: use ODB transaction for pluggable packfile writes
Series version: v2 (addresses all feedback from v1: interface naming, error reporting ergonomics, const-correctness, backend-specific optimizations, struct initialization refinements, buffer reuse clarification, shallow-file path plumbing, explicit file descriptor passing, and removal of `unpack_limit` global state)
Originating author: Justin Tobler
Thread type: patch series

Core problem or goal
Extend the ODB transaction system to make `git receive-pack` fully backend-agnostic by replacing its hardcoded use of `git index-pack` and `git unpack-objects` (which assume the "files" backend) with a new generic transaction interface, `odb_transaction_write_pack()`. The goal is to enable alternative ODB backends (e.g., reftable, cloud storage) to handle incoming packfiles without being tied to the traditional files backend.

Current status
Under active review; series updated to v2. Still cooking in `seen`; no merge status change. The next iteration, if any, will likely focus on reviewer feedback about the ergonomics of the new `odb_transaction_write_pack()` interface, the robustness of the transaction lifecycle (particularly deferred cleanup of ".keep" lockfiles), the mechanical soundness of the global state removal, the design flaw in the "files" backend implementation identified by Junio Hamano in patch 7/7 (incorrect use of `repo->objects->sources[0]` instead of `base->source`), and two new concerns raised by Junio in patch 1/7: ensuring `odb_transaction_finalize()` is invoked on all code paths (including non-local exits) and whether the function should return `void` given that no callers check its return value. Junio’s latest review of patch 7/7 reveals a **critical design flaw** in the "files" backend’s handling of `.keep` lockfiles: the tempfile structures registered during packfile ingestion point to pre-migration paths, but the lockfiles themselves are moved during `odb_transaction_files_commit()`, causing `odb_transaction_files_finalize()` to fail silently when attempting to delete them. This undermines the deferred cleanup pattern and could leave lockfiles stranded.

Open questions and loose ends
- Transaction lifecycle design: the interface now supports error reporting in `odb_transaction_finalize()`, which is critical for the "files" backend’s deferred cleanup of ".keep" lockfiles. The commit message clarifies that `builtin/receive-pack.c` is the only caller where the transaction is not finalized immediately after commit, because it needs to retain ".keep" files until references are updated. Reviewers may evaluate whether this deferred cleanup pattern is robust and ergonomic, particularly in light of Junio’s observation that `finalize()` is bypassed on non-local exits and his latest review identifying the lockfile migration issue.
- Error reporting ergonomics: the shift to `strbuf` output parameters is complete, with const-correctness refinements incorporated. The `unpack_status` buffer is initialized once per invocation of `cmd_receive_pack()`, so reuse is unnecessary. However, the return value of `odb_transaction_finalize()` (and `odb_transaction_commit()`) is unchecked by all callers, raising the question of whether these functions should return `void`.
- File descriptor passing: the explicit file descriptor passing for the incoming packfile in `unpack()` is now part of the interface; reviewers may evaluate whether this abstraction is ergonomic and whether it interacts cleanly with the new `odb_transaction_write_pack()` interface.
- Struct initialization and mutation patterns: the ternary initialization of `fsck_objects` and the late assignment of `err_fd` in `unpack_with_sideband()` remain as trade-offs for the larger goal of removing global state. Patrick Steinhardt accepted these as necessary but invited future scrutiny when the function moves to a different file.
- Design flaw in "files" backend: Junio Hamano identified a bug in `odb_transaction_files_write_pack()` where the transaction’s source (`base->source`) is ignored in favor of `repo->objects->sources[0]`. This could lead to subtle bugs if multiple ODB backends are in use. The fix is straightforward (replace `repo->objects->sources` with `base->source`), but the issue highlights the importance of respecting the transaction’s source context as the ODB abstraction effort matures.
- Non-local exits and deferred cleanup: Junio Hamano’s review of patch 1/7 highlights that `odb_transaction_finalize()` is bypassed on non-local exits (e.g., `exit(128)` after `report_path_error()` in `cmd_add()`). This undermines the deferred cleanup pattern and could leave ".keep" lockfiles stranded. The author will need to restructure the code to ensure `finalize()` is invoked on all code paths, even on error.
- Lockfile migration issue: Junio’s latest review of patch 7/7 reveals a **critical design flaw** in the "files" backend’s handling of `.keep` lockfiles. The tempfile structures registered during packfile ingestion point to pre-migration paths, but the lockfiles themselves are moved during `odb_transaction_files_commit()` via `tmp_objdir_migrate()`. This causes `odb_transaction_files_finalize()` to fail silently when attempting to delete them, as the tempfile structures still reference the original (now nonexistent) paths. The fix will require either (1) skipping migration of `.keep` lockfiles during commit and letting the finalize step handle their deletion, or (2) updating the tempfile structures during commit to reflect the post-migration paths.
