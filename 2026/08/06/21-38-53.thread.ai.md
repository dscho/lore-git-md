Subject: [PATCH 0/6] receive-pack: use ODB transaction for pluggable packfile writes
Series version: v2 (addresses all feedback from v1: interface naming, error reporting ergonomics, const-correctness, backend-specific optimizations, struct initialization refinements, buffer reuse clarification, shallow-file path plumbing, explicit file descriptor passing, and removal of `unpack_limit` global state; v3 will incorporate mechanical refinements to `unpack_limit` resolution, address Junio’s feedback on transaction lifecycle, lockfile migration, backend design flaws, and now the per-repository unpack limit storage suggestion)
Originating author: Justin Tobler
Thread type: patch series

Core problem or goal
Extend the ODB transaction system to make `git receive-pack` fully backend-agnostic by replacing its hardcoded use of `git index-pack` and `git unpack-objects` (which assume the "files" backend) with a new generic transaction interface, `odb_transaction_write_pack()`. The goal is to enable alternative ODB backends (e.g., reftable, cloud storage) to handle incoming packfiles without being tied to the traditional files backend.

Current status
Under active review; series updated to v2. Still cooking in `seen`; no merge status change. The next iteration (v3) will focus on: (1) mechanical refinements to `unpack_limit` resolution (adopting Patrick Steinhardt’s proposed non-caching, `unsigned int` version and now Junio Hamano’s suggestion to store the unpack limit as a per-repository setting in `repo->settings` or `repo->config_values`), (2) addressing Junio Hamano’s feedback on the transaction lifecycle (ensuring `odb_transaction_finalize()` is invoked on all code paths, including non-local exits), (3) fixing the critical design flaw in the "files" backend’s handling of `.keep` lockfiles (where tempfile structures reference pre-migration paths, causing `finalize()` to fail silently), (4) evaluating whether `odb_transaction_finalize()` and `odb_transaction_commit()` should return `void` (since no callers check their return values), and (5) correcting the "files" backend’s misuse of `repo->objects->sources[0]` instead of `base->source` in `odb_transaction_files_write_pack()`.

Open questions and loose ends
- **Unpack limit storage**: Junio Hamano’s latest review of patch 3/7 suggests storing the unpack limit as a per-repository setting in `repo->settings` or `repo->config_values` rather than using a `static int` inside `get_unpack_limit()`. This would align with Git’s broader pattern of avoiding static variables in favor of explicit repository state, especially as the ODB abstraction effort progresses toward supporting multiple backends and repositories. The current design, while simpler, may complicate future work if the unpack limit needs to vary across repositories or backends. The author will need to evaluate whether to adopt this suggestion in v3.
- Transaction lifecycle design: the interface now supports error reporting in `odb_transaction_finalize()`, which is critical for the "files" backend’s deferred cleanup of ".keep" lockfiles. The commit message clarifies that `builtin/receive-pack.c` is the only caller where the transaction is not finalized immediately after commit, because it needs to retain ".keep" files until references are updated. Junio Hamano’s review highlights two issues: (1) `finalize()` is bypassed on non-local exits (e.g., `exit(128)` after `report_path_error()` in `cmd_add()`), undermining deferred cleanup, and (2) the **critical design flaw** in the "files" backend’s lockfile migration, where tempfile structures reference pre-migration paths but the lockfiles themselves are moved during `odb_transaction_files_commit()`, causing `finalize()` to fail silently. The author will need to restructure the code to ensure `finalize()` is invoked on all code paths and resolve the lockfile migration issue (either by skipping migration of `.keep` lockfiles during commit or updating tempfile structures to reflect post-migration paths).
- Error reporting ergonomics: the shift to `strbuf` output parameters is complete, with const-correctness refinements incorporated. The `unpack_status` buffer is initialized once per invocation of `cmd_receive_pack()`, so reuse is unnecessary. However, the return values of `odb_transaction_finalize()` and `odb_transaction_commit()` are unchecked by all callers, raising the question of whether these functions should return `void`.
- File descriptor passing: the explicit file descriptor passing for the incoming packfile in `unpack()` is now part of the interface; reviewers may evaluate whether this abstraction is ergonomic and whether it interacts cleanly with the new `odb_transaction_write_pack()` interface.
- Struct initialization and mutation patterns: the ternary initialization of `fsck_objects` and the late assignment of `err_fd` in `unpack_with_sideband()` remain as trade-offs for the larger goal of removing global state. Patrick Steinhardt accepted these as necessary but invited future scrutiny when the function moves to a different file.
- `unpack_limit` resolution: Patrick Steinhardt’s review of patch 3/7 identified two mechanical issues: (1) the function’s return type should be `unsigned int` (not `int`) because the unpack limit is always non-negative, and (2) the static variable caching the limit is unnecessary because `unpack()` is only called once per `receive-pack` invocation. The next iteration will adopt a simpler, non-caching version that directly reads the configuration via `repo_config_get_uint()` and defaults to 100, overwriting the default if either `transfer.unpacklimit` or `receive.unpacklimit` is set. Junio Hamano’s feedback now adds a third consideration: whether the unpack limit should be stored as a per-repository setting rather than using a static variable.
- Design flaw in "files" backend: Junio Hamano identified a bug in `odb_transaction_files_write_pack()` where the transaction’s source (`base->source`) is ignored in favor of `repo->objects->sources[0]`. This could lead to subtle bugs if multiple ODB backends are in use. The fix is straightforward (replace `repo->objects->sources` with `base->source`), but the issue highlights the importance of respecting the transaction’s source context as the ODB abstraction effort matures.
