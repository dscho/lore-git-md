Subject: [PATCH 0/6] receive-pack: use ODB transaction for pluggable packfile writes
Series version: v5 (nine-patch series; addresses all v4 feedback, including test coverage for ".keep" file migration, commit message rewording, lockfile lifecycle regression fix, unpack limit global state removal, unpack options struct introduction, strbuf-based error reporting in the unpack path, explicit packfile file descriptor passing, explicit ODB source tracking, and the generic `odb_transaction_write_pack()` interface)
Originating author: Justin Tobler
Thread type: patch series

Core problem or goal
Extend the ODB transaction system to make `git receive-pack` fully backend-agnostic by replacing its hardcoded use of `git index-pack` and `git unpack-objects` (which assume the "files" backend) with a new generic transaction interface, `odb_transaction_write_pack()`. The goal is to enable alternative ODB backends (e.g., reftable, cloud storage) to handle incoming packfiles without being tied to the traditional files backend.

Current status
Under active review; series updated to v5 (nine patches) with all remaining feedback from v4 addressed. Still cooking in `seen`; no merge status change. Key improvements since v4:
- **Test coverage for ".keep" file migration**: Added a new test step in `t/t5547-push-quarantine.sh` that uses a `reference-transaction` hook to verify the `.keep` file is correctly migrated to the main ODB during the reference update phase and removed afterward. This addresses Patrick Steinhardt’s v4 feedback and ensures the packfile is protected from pruning while refs are being updated.
- **Commit message rewording**: Incorporated Patrick Steinhardt’s suggested rewording for patch 2/9 to improve clarity around the motivation for `odb_transaction_commit_and_finalize_or_die()`. The change is purely stylistic and does not affect the patch’s technical content.
- **Lockfile lifecycle regression fix (patch 1/9)**: Fixed a regression introduced in bdee7b3013 (July 2026) where `.keep` files were not being properly cleaned up after ODB transaction commits. The root cause was `index_pack_lockfile()` hardcoding the `.keep` file path to the repository’s primary object directory, while the ODB transaction system reorders the sources list to make the quarantine directory the primary source during the transaction. The patch updates `index_pack_lockfile()` to take an explicit `struct odb_source *` parameter, ensuring the `.keep` file is written to and removed from the correct location. The new test in `t/t5547-push-quarantine.sh` verifies the fix.
- **Transaction lifecycle split (patch 2/9)**: Introduced `odb_transaction_finalize()` to enable post-commit cleanup (e.g., removing ".keep" files after reference updates). The existing `odb_transaction_commit()` is now split into `commit()` (staging objects) and `finalize()` (deferred cleanup), with a new helper `odb_transaction_commit_and_finalize_or_die()` for callers that do not need intermediate work. This change directly addresses the lockfile lifecycle regression by ensuring ".keep" files are removed only after reference updates complete.
- **Global state removal (patches 3/9, 4/9, and 5/9)**: Eliminated the global `alt_shallow_file` variable (patch 3/9), the global `receive_unpack_limit`, `transfer_unpack_limit`, and `unpack_limit` variables (patch 4/9), and the global unpack options (`receive_fsck_objects`, `transfer_fsck_objects`, `fsck_msg_types`, `max_input_size`, `reject_thin`, and `quiet`) (patch 5/9). The temporary shallow file is now created in `cmd_receive_pack()` and passed explicitly through the call chain, unpack limit resolution is now handled lazily via `get_unpack_limit()`, and unpack options are bundled into a new `struct unpack_opts` passed explicitly. These changes remove key blockers for the ODB abstraction identified in Junio’s v2 review.
- **Strbuf-based error reporting (patch 6/9)**: Converted the `unpack()` and `unpack_with_sideband()` functions from returning static error strings to writing error messages into a caller-provided `strbuf` and returning a negative value on failure. The call sites in `builtin/receive-pack.c` are updated to match: `execute_commands()` now takes an `int unpacker_error` flag instead of a string, and the `report()` and `report_v2()` functions now accept a `struct strbuf *` for the unpack status. This change removes the last use of static error strings in the unpack path, aligning it with the ODB transaction system’s `strbuf`-based error reporting introduced in earlier patches. The motivation is to allow the unpack logic to move behind the generic `odb_transaction_write_pack()` interface in a later patch, which will need to propagate errors through the transaction system rather than returning them directly.
- **Explicit packfile file descriptor passing (patch 7/9)**: Replaced the hardcoded stdin (`fd 0`) assumption in `unpack()` and `parse_pack_header()` with an explicit `int pack_fd` parameter passed through the call chain. The call sites in `builtin/receive-pack.c` are updated to pass `0` (stdin) where the packfile is read, and the sideband multiplexer (`unpack_with_sideband()`) passes `0` to `unpack()`. This change removes the last hardcoded assumption about where the packfile is read from, aligning with the series' goal of making `git receive-pack` fully ODB-agnostic. The patch is mechanical and introduces no new symbols or behavior changes.
- **Explicit ODB source tracking (patch 8/9)**: Removed the fragile assumption that the temporary quarantine directory is always the first entry in the ODB source list by returning the newly installed source directly from `odb_set_temporary_primary_source()` and propagating it through the call chain. The "files" ODB transaction now stores the quarantine source explicitly in `struct odb_transaction_files`, eliminating the need to rely on source list ordering during commit and finalize. The change is mechanical: `odb_set_temporary_primary_source()` gains a `prev_source` out-parameter, `tmp_objdir_replace_primary_odb()` now returns the new source, and `struct odb_transaction_files` adds a `quarantine` field. No behavior change; the patch is a pure refactoring that tightens the interface for future ODB backends.
- **Generic `odb_transaction_write_pack()` interface (patch 9/9)**: Introduced the backend-agnostic `odb_transaction_write_pack()` interface, replacing the hardcoded `unpack()` logic in `builtin/receive-pack.c` with a call to the new interface. The unpack logic is moved into the "files" ODB backend (`odb_transaction_files_write_pack()`), making it reusable for alternative backends. The patch deletes 157 lines from `builtin/receive-pack.c` and adds equivalent logic in `object-file.c`, preserving all existing behavior. The `unpack_opts` struct is renamed to `odb_transaction_write_pack_opts` and passed through the new interface. The ".keep" lockfile management is moved into the "files" backend, with lockfiles now tracked in `struct odb_transaction_files` and removed during transaction finalization. The unpack limit resolution now uses the transaction’s `flags` field to determine whether to read `transfer.unpackLimit` or `receive.unpackLimit`. The `unpack_with_sideband()` function is updated to call `odb_transaction_write_pack()` instead of `unpack()`. The patch is mechanical and introduces no new symbols beyond the interface itself and the renamed `odb_transaction_write_pack_opts` struct.

- New or renamed symbols: `enum odb_transaction_flags` (`ODB_TRANSACTION_RECEIVE`, `ODB_TRANSACTION_FETCH`), `get_unpack_limit()` (signature change: now takes `enum odb_transaction_flags` and `struct repository *`), `odb_transaction_write_pack()` (new interface), `odb_transaction_files_write_pack()` (new function), `index_pack_lockfile()` (signature change: now takes `struct odb_source *` instead of `struct repository *`), `odb_transaction_finalize()` (new function), `odb_transaction_commit_and_finalize_or_die()` (new helper), `struct odb_transaction_files` (new fields: `flags`, `quarantine`, `pack_lockfiles`, `pack_lockfiles_nr`, `pack_lockfiles_alloc`), `struct unpack_opts` (renamed to `struct odb_transaction_write_pack_opts` in patch 9/9, bundling `receive_fsck_objects`, `transfer_fsck_objects`, `fsck_msg_types`, `max_input_size`, `reject_thin`, `quiet`, and `err_fd`), `odb_set_temporary_primary_source()` (signature change: now takes a `struct odb_source **prev_source` out-parameter and returns the new source), `tmp_objdir_replace_primary_odb()` (signature change: now returns `struct odb_source *`), `unpack()` (signature changes: now takes `int pack_fd`, `const char *shallow_file`, `const struct unpack_opts *`, and `struct strbuf *err_msg`), `unpack_with_sideband()` (signature changes: now takes `const char *shallow_file`, `const struct unpack_opts *`, and `struct strbuf *err_msg`), `parse_pack_header()` (signature change: now takes `int pack_fd`), `execute_commands()` (signature change: now takes `int unpacker_error` instead of `const char *unpack_status`), `report()` and `report_v2()` (signature change: now take `const struct strbuf *unpack_status`).
- Old-vs-new behavior: No user-visible behavior change; the series is a refactor to enable pluggable ODB backends. The unpack limit is now resolved lazily in the backend via `get_unpack_limit()`, which reads `transfer.unpackLimit` and `receive.unpackLimit` (with the latter taking precedence) for `git receive-pack` and will use `fetch.unpackLimit` for `git fetch-pack` in the future. The ".keep" file placement now correctly preserves race-avoidance properties by writing the file to the quarantine directory during the transaction and migrating it to the main ODB at commit time, then removing it during finalization. The global `alt_shallow_file` variable, static unpack limit caching, and unpack-related globals are removed, with configuration resolved lazily or passed explicitly. Error reporting now uses a `strbuf` instead of static strings, and the packfile file descriptor, shallow file path, and unpack options are passed explicitly through the call chain, aligning with the ODB transaction system. The explicit ODB source tracking (patch 8/9) eliminates the fragile reliance on `repo->objects->sources[0]` by storing the quarantine source explicitly in `struct odb_transaction_files`. The generic `odb_transaction_write_pack()` interface (patch 9/9) replaces the hardcoded unpack logic with a backend-agnostic call, enabling alternative ODB backends to handle incoming packfiles.
- On-disk format changes: None.
- Test coverage: Enhanced test in `t/t5547-push-quarantine.sh` now verifies the ".keep" file is generated in the quarantine directory, migrated to the main ODB during the reference update phase (using a `reference-transaction` hook), and removed afterward. Existing tests cover the refactored shallow file handling, unpack limit resolution, `unpack_opts` struct usage, `strbuf`-based error reporting, explicit file descriptor and shallow file passing, explicit ODB source tracking, and the new `odb_transaction_write_pack()` interface.

Open questions and loose ends
- **Struct initialization and mutation patterns**: The ternary initialization of `fsck_objects` and late assignment of `err_fd` in `unpack_with_sideband()` are preserved as trade-offs for removing global state. The `odb_transaction_write_pack_opts` struct initialization (patch 9/9) follows this pattern, which remains a minor ergonomic trade-off for clarity and testability.
- **Future source-tracking design debt**: The explicit ODB source tracking (patch 8/9) addresses the immediate fragility of relying on `repo->objects->sources[0]`, but the broader design of how transactions interact with multiple ODB backends may require further refinement as the ODB abstraction effort matures.
- **No remaining substantive feedback**: All critical design flaws and reviewer feedback from v4 have been addressed, including the lockfile lifecycle regression fix, test coverage enhancement, transaction lifecycle split, global state removal, unpack options struct introduction, strbuf-based error reporting in the unpack path, explicit packfile file descriptor passing, explicit ODB source tracking, and the generic `odb_transaction_write_pack()` interface. The series is technically sound and ready for merging, pending Junio’s final review.
