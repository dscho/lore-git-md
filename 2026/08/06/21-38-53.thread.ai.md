Subject: [PATCH 0/6] receive-pack: use ODB transaction for pluggable packfile writes
Series version: v3 (nine-patch series; addresses all v2 feedback, including critical lockfile lifecycle flaw, unpack limit resolution, transaction lifecycle, backend design flaws, per-repository unpack limit storage, new `*_or_die()` helpers, and explicit ODB source tracking)
Originating author: Justin Tobler
Thread type: patch series

Core problem or goal
Extend the ODB transaction system to make `git receive-pack` fully backend-agnostic by replacing its hardcoded use of `git index-pack` and `git unpack-objects` (which assume the "files" backend) with a new generic transaction interface, `odb_transaction_write_pack()`. The goal is to enable alternative ODB backends (e.g., reftable, cloud storage) to handle incoming packfiles without being tied to the traditional files backend.

Current status
Under active review; series updated to v3 (nine patches) with all critical design flaws addressed. Still cooking in `seen`; no merge status change. Key improvements since v2:
- Fixed the **critical lockfile lifecycle flaw** in the "files" backend (patch 1/9) by ensuring lockfile paths remain valid post-commit via explicit `struct odb_source *` tracking in `index_pack_lockfile()`. The fix is verified by a new test in `t/t5547-push-quarantine.sh`.
- Introduced `odb_transaction_finalize()` and `odb_transaction_commit_and_finalize_or_die()` to enforce proper transaction lifecycle management (patch 2/9).
- Removed static caching of the unpack limit, adopting a non-caching `unsigned int` version that reads the configuration directly via `repo_config_get_uint()` with a default of 100 (patch 4/9).
- Added explicit ODB source tracking to avoid fragile reliance on source list ordering (patch 8/9).
- The "files" backend now properly manages ".keep" lockfiles, removing them post-commit via the finalize callback.
- All callers now use `odb_transaction_commit_and_finalize_or_die()` to ensure cleanup on error paths.
- The unpack limit is resolved lazily in the backend rather than being wired through the interface.

Open questions and loose ends
- **Transaction lifecycle design**: While `finalize()` is now invoked on all code paths (including non-local exits), the question of whether `finalize()` and `commit()` should return `void` remains open. The new `*_or_die()` helpers provide an alternative for stricter contexts, but the base functions still return `int` for backward compatibility.
- **Error reporting ergonomics**: The `*_or_die()` helpers are now available for callers that prefer stricter error handling, but the base interface remains flexible. The `unpack_status` buffer is initialized once per invocation, so reuse is unnecessary.
- **File descriptor passing**: The explicit file descriptor passing for the incoming packfile in `unpack()` remains part of the interface; reviewers may still evaluate its ergonomics.
- **Struct initialization and mutation patterns**: The ternary initialization of `fsck_objects` and late assignment of `err_fd` in `unpack_with_sideband()` are preserved as trade-offs for removing global state.
- **Future source-tracking design debt**: The explicit ODB source tracking (patch 8/9) addresses the immediate fragility of relying on `repo->objects->sources[0]`, but the broader design of how transactions interact with multiple ODB backends may require further refinement as the ODB abstraction effort matures.
