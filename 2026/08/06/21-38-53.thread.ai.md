Subject: [PATCH 0/6] receive-pack: use ODB transaction for pluggable packfile writes
Series version: v3 (nine-patch series; addresses all v2 feedback, including critical lockfile lifecycle flaw, unpack limit resolution, transaction lifecycle, backend design flaws, per-repository unpack limit storage, new `*_or_die()` helpers, explicit ODB source tracking, shallow file global state removal, error-reporting refactor for backend-agnostic use, explicit file descriptor passing for incoming packfiles, explicit temporary ODB source tracking to eliminate reliance on source list ordering, and the new `odb_transaction_write_pack()` interface completing the ODB abstraction)
Originating author: Justin Tobler
Thread type: patch series

Core problem or goal
Extend the ODB transaction system to make `git receive-pack` fully backend-agnostic by replacing its hardcoded use of `git index-pack` and `git unpack-objects` (which assume the "files" backend) with a new generic transaction interface, `odb_transaction_write_pack()`. The goal is to enable alternative ODB backends (e.g., reftable, cloud storage) to handle incoming packfiles without being tied to the traditional files backend.

Current status
Under active review; series updated to v3 (nine patches) with all critical design flaws addressed. Still cooking in `seen`; no merge status change. Key improvements since v2:
- Fixed the **critical lockfile lifecycle flaw** in the "files" backend (patch 1/9) by ensuring lockfile paths remain valid post-commit via explicit `struct odb_source *` tracking in `index_pack_lockfile()`. The fix is verified by a new test in `t/t5547-push-quarantine.sh`. **Design discussion ongoing**: Patrick Steinhardt proposed an alternative ".keep" file placement strategy (write packfile to temporary directory without ".keep", write ".keep" to main ODB at commit time, remove during finalization) to preserve race-avoidance properties. Justin Tobler argues the current approach is functionally equivalent but agrees to clarify the commit message and add a test hook to verify ".keep" file location pre-commit.
- Introduced `odb_transaction_finalize()` and `odb_transaction_commit_and_finalize_or_die()` (patch 2/9) to enforce proper transaction lifecycle management. The split decouples object visibility (`commit()`) from deferred cleanup (`finalize()`), enabling backend-specific post-commit operations (e.g., lockfile removal). Callers now use `*_or_die()` for strict error handling or explicitly invoke `finalize()` after reference updates. **Patrick Steinhardt approved the design and implementation of this patch in v3**, noting only a minor typo in the commit message ("step fail" → "fail").
- Removed static caching of the unpack limit (patch 4/9), adopting a non-caching `unsigned int` version that reads the configuration directly via `repo_config_get_uint()` with a default of 100. The helper `get_unpack_limit()` resolves both `transfer.unpackLimit` and `receive.unpackLimit` (with the latter taking precedence) lazily inside `unpack()`.
- Added explicit ODB source tracking (patch 8/9) to avoid fragile reliance on source list ordering. `odb_set_temporary_primary_source()` now returns the newly installed source directly and reports the previous primary source via an optional out-parameter (`prev_source`). The return value is propagated through `tmp_objdir_replace_primary_odb()` and stored in the "files" ODB transaction struct (`quarantine` field), ensuring the temporary source remains accessible post-commit without depending on the ODB source list order. **Patrick Steinhardt approved this patch in v3** ("Makes sense"), signaling alignment with the broader ODB abstraction goals.
- Removed reliance on the global `alt_shallow_file` variable (patch 3/9) by lifting temporary shallow file setup out of `unpack()` and wiring it through explicitly to call sites. The shallow file path is now passed as a parameter to `unpack()`, `unpack_with_sideband()`, `prepare_shallow_update()`, and `update_shallow_info()`, and the temporary file is created at the call site in `cmd_receive_pack()`.
- The "files" backend now properly manages ".keep" lockfiles, removing them post-commit via the finalize callback.
- All callers updated to use `odb_transaction_commit_and_finalize_or_die()` or explicitly invoke `finalize()` after reference updates.
- The unpack limit is resolved lazily in the backend rather than being wired through the interface.
- **Patch 5/9**: Refactored `unpack()` to eliminate reliance on global variables by introducing a `struct unpack_opts` that explicitly passes all previously implicit state (fsck settings, shallow file path, input size limits, error file descriptor, quiet flag, and thin-pack rejection). This mechanical change lifts global state into an explicit options struct, making the logic reusable behind the new `odb_transaction_write_pack()` interface.
- **Patch 6/9**: Refactored error reporting in `unpack()` and `unpack_with_sideband()` to use a caller-provided `strbuf` for error messages instead of returning a static string. The change is purely internal and prepares the code for the upcoming `odb_transaction_write_pack()` interface, enabling backend-agnostic error handling. The `strbuf` is initialized once in `cmd_receive_pack()` and released at the end of the function, avoiding dynamic allocation overhead during unpack.
- **Patch 7/9**: Replaced the implicit stdin assumption in `unpack()` with an explicit file descriptor parameter (`int pack_fd`) for the incoming packfile. The change is mechanical: `unpack()` and `parse_pack_header()` now take the new parameter, and callers pass `0` (stdin) to preserve existing behavior. The child-process setup in `unpack()` is updated to wire the new `pack_fd` to the spawned `git index-pack` or `git unpack-objects` command. No user-visible behavior changes; the goal is to lift the hardcoded stdin assumption so the logic can later be moved behind the new `odb_transaction_write_pack()` interface.
- **Patch 9/9**: Introduced `odb_transaction_write_pack()`, the generic interface completing the ODB abstraction for `git receive-pack`. The patch moves the packfile ingestion logic from `builtin/receive-pack.c` into the "files" ODB backend (`object-file.c`), replacing the hardcoded `unpack()` function with the new callback. The "files" backend now manages ".keep" lockfiles explicitly, storing them in a dynamically grown array (`pack_lockfiles`) and removing them during transaction finalization. Call sites in `receive-pack` are updated to use the new interface, and the old `unpack()` implementation is removed. The `odb_transaction_write_pack_opts` struct mirrors the old `unpack_opts` but is now part of the public ODB transaction interface, enabling backend-agnostic packfile ingestion. The transaction’s `finalize` callback iterates over the `pack_lockfiles` array to clean up ".keep" files, ensuring they are removed even if the transaction is finalized after reference updates. The patch removes the global `pack_lockfile` variable and the last direct dependency on `lockfile.h` in `receive-pack.c`.

Open questions and loose ends
- **".keep" file design**: **Substantive design discussion ongoing**. Patrick Steinhardt raised a **fundamental design question** about the placement of ".keep" files under the new transaction system. The current approach writes the ".keep" file to the temporary transaction directory and migrates it alongside the packfile, but Patrick argues this does not preserve the race-avoidance properties the ".keep" file is meant to provide. He proposed an alternative design: write the packfile to the temporary directory without a ".keep" file, then at commit time write a ".keep" file to the *main* object directory before migrating the packfile, and finally remove the ".keep" file during finalization. This would restore the original race-avoidance properties by ensuring the ".keep" file is always in the main ODB when the packfile is migrated. Justin Tobler contends the current approach is functionally equivalent but agrees to clarify the commit message and add a test hook to verify the ".keep" file is in the correct location before commit. **Resolution of this design question is pending**; the author must either justify the current approach or revise the design to align with Patrick’s suggestion.
- **Transaction lifecycle design**: The question of whether `finalize()` and `commit()` should return `void` remains open. The new `*_or_die()` helpers provide an alternative for stricter contexts, but the base functions retain `int` returns for backward compatibility. **Patrick Steinhardt’s approval of patch 2/9 in v3 suggests this design is now settled for the purposes of this series.**
- **Error reporting ergonomics**: The `*_or_die()` helpers are available for callers preferring strict error handling, but the base interface remains flexible. The `strbuf`-based error reporting (patch 6/9) is a step toward backend-agnostic use, but reviewers may still evaluate its ergonomics.
- **File descriptor passing**: The explicit file descriptor passing for the incoming packfile in `unpack()` (patch 7/9) remains part of the interface; reviewers may still evaluate its ergonomics, though the change itself is uncontroversial.
- **Struct initialization and mutation patterns**: The ternary initialization of `fsck_objects` and late assignment of `err_fd` in `unpack_with_sideband()` are preserved as trade-offs for removing global state. The `unpack_opts` struct initialization (patch 5/9) follows this pattern, which remains a minor ergonomic trade-off for clarity and testability.
- **Future source-tracking design debt**: The explicit ODB source tracking (patch 8/9) addresses the immediate fragility of relying on `repo->objects->sources[0]`, but the broader design of how transactions interact with multiple ODB backends may require further refinement as the ODB abstraction effort matures.
