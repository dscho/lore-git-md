Subject: `git rebase` regression with commit-graph and submodule pointer changes
Series version: N/A (bug report)
Originating author: Philippe Blain
Thread type: bug report

Core problem or goal
A fatal error occurs during `git rebase` when commit-graph is enabled and a submodule pointer is updated to a commit that exists only in the submodule, not in the main repository. The error message (`invalid commit position. commit-graph is likely corrupt`) is misleading; `git fsck` reports no corruption. Disabling commit-graph (`-c core.commitGraph=false`) bypasses the error, though submodule conflicts remain.

Current status
Under review. The regression was bisected to commit `bb5da75d61` ("commit: use commit graph in `lookup_commit_reference_gently()`") by Florian Schmidt. No patch has been posted yet; the next step is to write a minimal reproducer.

Key technical details
- Files/subsytems: `commit.c`, commit-graph subsystem, submodule handling in `git rebase`
- New/renamed symbols: none
- Behavior: `lookup_commit_reference_gently()` now consults the commit-graph, which fails when the OID exists only in a submodule, not in the main repo
- On-disk format: unchanged
- Test coverage: none yet; a minimal reproducer is planned

Open questions and loose ends
- Is the commit-graph lookup logic correct when the OID is not present in the main repo’s object store?
- Should `lookup_commit_reference_gently()` fall back to the object store when the commit-graph lookup fails, or is the caller responsible for handling this case?
- What is the minimal reproducer that triggers the error?
