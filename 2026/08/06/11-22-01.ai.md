This is the sixth patch in the v3 series introducing `git repack --drop-filtered`, focusing on the safety guards that prevent the command from running during ongoing operations or dropping blobs referenced by the current index. The patch adds two checks, both skipped for bare repositories: (1) it refuses to run if a merge, rebase, am, cherry-pick, revert, or bisect is in progress, and (2) it refuses to drop any blob referenced by the current index. These guards are now explicitly framed as UX optimizations rather than correctness measures, since lazy-fetching would transparently restore dropped objects.

The implementation uses `wt_status_get_state()` to detect ongoing operations and `repo_read_index()` to validate the index, with clear error messages ("cannot be used while another operation is in progress" and "cannot drop '<path>' (<oid>): it is referenced by the current index"). The test coverage is thorough, including a merge conflict scenario and an index-referenced blob case. The patch is well-motivated and addresses a real concern: without these guards, users would experience redundant network fetches during half-finished operations or immediately after dropping blobs still in use.

This patch is part of the larger `--drop-filtered` effort, which aims to safely reclaim disk space in partial clones by removing locally cached promisor blobs exceeding a size threshold. The guards here are uncontroversial in principle but their necessity is debated: Junio has proposed replacing them with a time-based heuristic (avoiding culling recently fetched objects) to reduce redundant network operations. The current implementation remains unchanged from v2, but the commit message now clarifies that these checks are optional optimizations. The patch is production-ready and integrates cleanly with the rest of the series.
