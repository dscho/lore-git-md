This is a feature request for `git fetch` that proposes decoupling the default fetch refspec from the mapping used for explicitly named branches.

The author, Douglas Puchalski, describes a common workflow frustration: when a remote is configured to fetch only a limited set of branches by default (e.g., `main` and `team/*`), explicitly fetching an additional branch (e.g., `git fetch origin topic/example`) does not create or update the corresponding remote-tracking ref (`refs/remotes/origin/topic/example`). Instead, the branch is only available in `FETCH_HEAD`, which is ephemeral and shared state. This breaks the natural `git checkout -b topic/example origin/topic/example` workflow unless the user manually specifies a refspec or uses workarounds like `--refmap`.

The request is for a configuration or default behavior that would automatically map explicitly named branches to their remote-tracking refs while preserving the restricted default fetch set. The author emphasizes that this should not require fetching all remote branches, repeating the branch name in a refspec, or relying on `FETCH_HEAD`. Backward compatibility is a key constraint, so the solution would need to be opt-in.
