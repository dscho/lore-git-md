This thread is about adding Bash completion for the new `git history` command, now in its second version. Vincent Mailhol is the author, and Patrick Steinhardt has been the primary reviewer. The series provides completion for subcommands like `--empty` and `--update-refs`, and for pathspecs in the `split` subcommand, using Git’s existing parse-options infrastructure.

The main point of contention is the `__git_history_has_revision` helper, which scans the command line to determine if a revision has been provided. Patrick critiqued it as fragile because it hardcodes options that take arguments, requiring manual updates when new options are added. Vincent has now responded, acknowledging the fragility but arguing that the practical impact is limited. Most users will use the `--option=<value>` form (e.g., `--empty=drop`), which the helper handles correctly, and the `--option <value>` form (e.g., `--empty drop`) is rare and undocumented. For future options like `--gpg-sign`, the helper’s behavior is mostly correct because the value is optional. The only edge case is when a user explicitly provides a value without an equals sign, which would incorrectly trigger reference completion.

Vincent proposes two paths forward: keep the current helper (which works well today but will need manual updates for future options) or simplify the logic by ignoring the `--option <value>` syntax entirely, accepting some incorrect completions. He slightly prefers the first option but is open to the second. The series is under review, and a third version is likely to incorporate this feedback. The maintainability concern remains unresolved but is now better understood.
