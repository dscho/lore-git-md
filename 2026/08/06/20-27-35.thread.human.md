This thread is about adding Bash completion for the new `git history` command. Vincent Mailhol posted a second version of the patch series (4 patches) to implement completion for the command's subcommands (`--empty`, `--update-refs`, and `split` pathspecs) using Git's existing parse-options infrastructure.

The series is under review and has evolved to address feedback, particularly around how to handle the requirement that every subcommand must start with exactly one revision argument. Patrick Steinhardt reviewed the latest version and, while accepting a compromise for now, has again raised concerns about the maintainability of the helper function `__git_history_has_revision`. This function hardcodes options that take arguments, which Patrick warns will become fragile as new parameters (like those for commit signing or notes) are added. The discussion highlights a tension between the current pragmatic solution and the risk of future maintenance issues, but no immediate changes are required—the series can proceed to a third version with the existing logic.

The technical details include a new helper to check for revisions, completion logic for option values (like `--empty=drop`), and tests covering subcommands, options, and pathspecs. The only open question is the long-term maintainability of the revision-checking logic, which may need revisiting as the `git history` command grows. So far, only Patrick and Vincent have weighed in, with no other reviews or maintainer decisions reported.
