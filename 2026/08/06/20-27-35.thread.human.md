This thread is about adding Bash completion for the new `git history` command, now in its second version. Vincent Mailhol is the author, and the series provides shell completion for `git history` subcommands like `--empty`, `--update-refs`, and `split` pathspecs, using Git’s existing parse-options infrastructure. The key constraint is that every subcommand requires exactly one revision argument before any options or pathspecs.

The v2 patch addressed earlier feedback on revision handling, `--` termination, and test coverage, but Patrick Steinhardt raised a maintainability concern: the helper function `__git_history_has_revision` hardcodes options that take arguments (e.g., `--empty`), which would require manual updates if new such options are added. Vincent proposed a compromise—keeping the current logic but adding a `case` statement to handle future exceptions (like subcommands that don’t follow the "revision-first" pattern) before the revision check. Patrick accepted this as a pragmatic trade-off, and the series is now closer to being ready for a v3 iteration.

The patch itself is uncontroversial, but the discussion clarifies how future edge cases will be handled. No maintainer decision has been made yet, and the series remains under review. The completion logic is confined to `contrib/completion/git-completion.bash` and the test suite, with no changes to core Git behavior or on-disk formats.
