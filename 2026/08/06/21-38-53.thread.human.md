This thread is about Justin Tobler’s six-patch series making `git receive-pack` backend-agnostic by replacing its hardcoded use of `git index-pack` and `git unpack-objects` with a new ODB transaction interface, `odb_transaction_write_pack()`. The goal is to let alternative ODB backends (like reftable or cloud storage) handle incoming packfiles without being tied to the traditional files backend. The series is now at v2, addressing all feedback from v1—interface naming, error reporting, const-correctness, backend optimizations, and global state removal.

The series is under active review, still cooking in Junio’s `seen` branch. The latest iteration focuses on refining the transaction lifecycle, particularly deferred cleanup of ".keep" lockfiles, and addressing a critical design flaw in the "files" backend’s lockfile handling identified by Junio Hamano. The third patch in the series, which removes the global `unpack_limit` variable, was recently refined in response to Patrick Steinhardt’s review. Patrick pointed out that the function’s return type should be `unsigned int` (since the limit is non-negative) and that caching the limit in a static variable was unnecessary, as `unpack()` is only called once per `receive-pack` invocation. Justin agreed and proposed a simpler, non-caching version that directly reads the configuration, which will likely be adopted in the next iteration.

Key open questions include whether the deferred cleanup pattern is robust enough, especially on non-local exits, and whether `odb_transaction_finalize()` should return `void` given that no callers check its return value. Junio also identified a critical bug in the "files" backend where lockfiles are moved during commit but the tempfile structures still reference their original paths, causing cleanup to fail silently. The author is expected to address these issues in the next version. The series remains part of the broader ODB abstraction effort led by Patrick Steinhardt, with no objections to its direction but ongoing scrutiny of its ergonomics and robustness.
