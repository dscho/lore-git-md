This thread is about a six-patch series from Justin Tobler that extends Git’s ODB (object database) transaction system to make `git receive-pack` fully backend-agnostic. The goal is to replace its hardcoded use of `git index-pack` and `git unpack-objects`—which assume the traditional "files" backend—with a new generic transaction interface, `odb_transaction_write_pack()`. This change is part of the broader ODB abstraction effort led by Patrick Steinhardt, which aims to enable alternative backends (like reftable or cloud storage) to handle incoming packfiles without being tied to the files backend.

The series is still under active review at version 1, with no merge status change. The first five patches are plumbing-only and focus on removing global state, preparing for explicit file descriptor passing, and improving error reporting ergonomics. The sixth patch introduces `odb_transaction_write_pack()` and moves the packfile ingestion logic into `object-file.c`, completing the switch to backend-agnostic processing. Key technical details include new symbols like `odb_transaction_finalize()` (renamed from `release` to better reflect its role in error reporting), `struct odb_transaction_write_pack_opts`, and `struct unpack_opts`, as well as changes to `builtin/receive-pack.c` and `odb/transaction.c`.

The discussion has converged on a few open design questions, particularly around the transaction lifecycle. Justin and Patrick agree that `odb_transaction_finalize()` should be able to report errors, as failures in cleaning up ".keep" lockfiles (used by the "files" backend) should not be silently ignored. Patrick also raised questions about backend-specific optimizations, such as whether `odb_reprepare()` is overly broad and whether `unpack_limit` belongs in the generic options struct. These are forward-looking considerations rather than blockers. The next version of the series is expected to address these points, including clarifying in the commit message that `git receive-pack` is the only caller where the transaction isn’t released immediately after commit, due to its need to retain ".keep" files until references are updated. No substantive objections to the series’ direction have been raised.
