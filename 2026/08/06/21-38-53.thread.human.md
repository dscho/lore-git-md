This thread is about a patch series from Justin Tobler that extends Git's object database (ODB) transaction system to make `git receive-pack` work with pluggable backends, like reftable or cloud storage, instead of being hardcoded to the traditional "files" backend. The series is now at version 2, addressing all feedback from the first round—renaming interfaces, improving error handling, cleaning up struct initialization, and removing global state like `unpack_limit`.

The core change replaces calls to `git index-pack` and `git unpack-objects` with a new generic interface, `odb_transaction_write_pack()`, allowing alternative backends to handle incoming packfiles. The series is under active review, still in Junio Hamano's `seen` branch, with no merge decisions yet. The next version (v3) will focus on mechanical refinements to `unpack_limit` resolution, fixing transaction lifecycle issues (ensuring cleanup happens on all code paths), and addressing a critical bug in the "files" backend where lockfile migration during commit causes silent failures in cleanup.

Key participants include Justin Tobler (the author), Patrick Steinhardt (leading the ODB abstraction effort), and Junio Hamano (the maintainer). Patrick reviewed the first version, accepting the direction but flagging areas like transaction lifecycle and error reporting for further attention. Junio's latest feedback highlights two major issues: the transaction cleanup is bypassed on non-local exits (like fatal errors), and the "files" backend has a design flaw where lockfile paths become stale after migration, causing cleanup to fail. He also questioned whether the transaction interface's return values are even checked, suggesting they might as well return `void`.

The latest email adds another design consideration: Junio suggests storing the `unpack_limit` setting in the repository struct (`repo->settings` or `repo->config_values`) instead of using a static variable, making it truly per-repository and aligning with Git's broader architecture. This isn't a blocking issue but could simplify future work as the ODB abstraction matures. The series remains under review, with these design questions still open.
