This thread is about Justin Tobler’s nine-patch v3 series that refactors `git receive-pack` to use the ODB transaction system, enabling pluggable backends for incoming packfiles. The series has addressed all critical feedback from v2, including a lockfile lifecycle flaw, unpack limit resolution, and global state removal. It’s currently under active review in Junio’s `seen` branch, with no merge status change yet.

The key technical achievement is the new `odb_transaction_write_pack()` interface, which replaces hardcoded calls to `git index-pack` and `git unpack-objects` with a generic mechanism. This allows alternative ODB backends (like reftable or cloud storage) to handle incoming packfiles without being tied to the traditional files backend. The series also introduces proper transaction lifecycle management, explicit ODB source tracking, and removes reliance on global variables like `alt_shallow_file`.

Patrick Steinhardt’s recent review of the first patch raises a fundamental design question about the ".keep" file mechanism. He argues that the current approach—writing the ".keep" file to the main object directory while the packfile resides in a temporary transaction directory—doesn’t actually prevent the race it’s meant to address. He proposes an alternative design where the ".keep" file is written to the main directory only at commit time, then removed during finalization. This would require significant changes to the transaction lifecycle and isn’t addressed in the current series. The author will need to either justify the existing approach or revise the design to align with Patrick’s suggestion.

The series is otherwise technically sound, with all critical flaws from v2 resolved. The remaining open questions are primarily about ergonomics (e.g., transaction lifecycle design, error reporting) and the broader ODB abstraction effort. Junio and Patrick have both engaged substantively with the series, and the next steps will likely involve addressing Patrick’s design concerns before the series can graduate to `next`.
