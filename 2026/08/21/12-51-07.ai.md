This is a **feature patch** introducing the `report` hook for `git-receive-pack`, part of an ongoing discussion about hook design in Git. Karthik Nayak responds to Phillip Wood’s **substantive review** questioning whether the hook’s single-script design (modeled after `proc-receive`) remains appropriate now that Git supports config-based hooks, which allow multiple scripts per event.

Karthik acknowledges the design challenge and explains that he attempted to adapt the config-based infrastructure for bidirectional I/O but found it messy. He now argues the single-script approach is justified not by the server/client distinction (as Junio C Hamano noted) but by the nature of bidirectional communication: piping output from one hook to another would not work for `proc-receive`, and parallel execution is inherently unsafe for this use case. The commit message will be updated to clarify this reasoning, addressing the **central unresolved design question** in the thread.

The patch itself remains unchanged in implementation. It adds a `report` hook that acts as a bidirectional filter for the status report sent to clients after ref updates, motivated by GitLab’s need to implement MVCC (multi-version concurrency control). The hook receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. A non-zero exit status causes `receive-pack` to die, treating the push as failed (ref changes are not rolled back). Test coverage verifies passthrough behavior, failure modes, stdin/stdout handling, and sideband relay, though the interaction between exit status and stdout is not yet explicitly tested.

Key files touched include `builtin/receive-pack.c` (hook implementation), `Documentation/githooks.adoc` (hook documentation), and a new test script `t/t5412-report-hook.sh`. The unresolved documentation question about where to document the `pkt-line` format persists, and minor test adjustments (e.g., verifying the "remote:" prefix on stderr) are planned. The patch is **not integrated with the config-based hook infrastructure**, a deliberate choice to avoid parallelization and coordination complexity.
