This is the first patch in a two-patch bugfix series targeting the submodule subsystem. It prevents a crash (BUG) in the experimental `submodule.propagateBranches` feature when `git branch --recurse-submodules` is used with a start point that is not a ref name (e.g., a raw object ID).

The bug occurs because `create_branches_recursively()` passes a NULL `tracking_name` to `setup_tracking()`, which then triggers an assertion in `refspec_find_match()` when a remote is configured. The fix aligns the recursive path with the non-recursive `create_branch()` logic by adding a guard to check `tracking_name` before calling `setup_tracking()`. This ensures the command fails cleanly rather than aborting after partially completing the operation.

The patch includes a new test in `t/t3207-branch-submodule.sh` that reproduces the issue in a repository without submodules, confirming the fix works even when `propagateBranches` has nothing to propagate. The test requires all four conditions that trigger the bug: `submodule.recurse=true`, `submodule.propagateBranches=true`, a configured remote, and a non-ref start point.

The commit message is thorough, explaining the root cause, the fix, and why the decision belongs in the caller rather than `setup_tracking()`. The author notes the bug was introduced in two stages (commits 961b130d20 and 75388bf5b4) and that the current behavior leaves callers with misleading exit statuses. The patch looks well-motivated and narrowly scoped, addressing only the crash without changing behavior for valid ref names.
