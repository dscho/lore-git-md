This is the second patch in a two-patch bugfix series targeting the submodule subsystem, specifically the experimental `submodule.propagateBranches` feature. It addresses a crash in `git branch --recurse-submodules` when the start point is not a ref name (e.g., a raw object ID) in repositories *with* submodules.

The patch makes the tracking name argument optional in the `submodule--helper create-branch` command, allowing recursion to proceed even when no tracking name exists. The fix is minimal: it modifies `submodule_create_branch()` in `branch.c` to push the tracking name separately (rather than relying on `strvec_pushl()` to stop at NULL) and updates the helper's usage text and argument parsing in `builtin/submodule--helper.c` to accept two or three arguments. A new test in `t/t3207-branch-submodule.sh` verifies the fix by creating a branch from a raw object ID in a repository with submodules and confirming the branch exists in all submodules.

The commit message is thorough, explaining the root cause (a truncated argument list due to `strvec_pushl()` stopping at NULL), the fix, and the reasoning behind the approach. The author notes that this is the same NULL tracking name issue as in the first patch, but reached earlier in the code path when submodules are present. The patch is well-scoped, touching only the necessary code to fix the crash without changing behavior for start points that *are* ref names.

This patch, combined with the first, completes the fix for the crash and error handling issues in the `submodule.propagateBranches` feature. The series is under review and has no prior versions; it is based on `maint` and merges cleanly into `next` and `seen`. The exposure is limited to the experimental feature, but within those bounds, the bug is reproducible and problematic for scripting use cases.
