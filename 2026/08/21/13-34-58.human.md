This is a feature patch introducing a new `report` hook for `git-receive-pack`. It is the second iteration of a standalone patch by Karthik Nayak, addressing feedback from the first version while keeping the core design intact.

The hook allows server administrators to intercept and modify the status report sent to the client after all ref updates are committed but before the response is finalized. This is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the final status depends on post-push operations. The hook receives the pkt-line encoded status report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. A non-zero exit status causes `receive-pack` to die, treating the entire push as failed (though ref changes are not rolled back).

The patch touches `builtin/receive-pack.c`, adds documentation in `githooks.adoc` and `git-receive-pack.adoc`, and includes a new test script (`t/t5412-report-hook.sh`) with seven test cases covering passthrough, failure modes, stdin/stdout handling, and sideband relay. The hook is intentionally not integrated with the config-based hook infrastructure, as that system is designed for parallelizable notification hooks, whereas this hook is a bidirectional filter requiring a single script.

Changes in this version include more verbose documentation and commit message, a link to the hook in `git-receive-pack.adoc`, renaming the return code variable from `code` to `ret`, and adjusting the test to verify the "remote:" prefix on stderr. The core implementation remains unchanged, and the central design question—whether to use a single-script or config-based hook—has been resolved in favor of the single-script approach, justified by the need for bidirectional communication and consistency with `proc-receive`.

This is a well-crafted patch addressing a real gap in Git’s server-side extensibility. The use case is clearly documented, the implementation is clean, and the test coverage is thorough. The design avoids config-based hooks for sound technical reasons, and the feedback from the first version has been incorporated without compromising the original goals. The patch is ready for further review but is unlikely to require major changes.
