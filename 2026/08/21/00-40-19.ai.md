This is a **substantive technical discussion** in the ongoing `git pack-objects` Trace2 instrumentation thread, focusing on a performance curiosity that emerged during review of the byte-counting patch. Jeff King (Peff) and Patrick Steinhardt explore the implications of Git’s current triple-hash verification in `write_pack_file()`—a design they both describe as "absurdly pessimal" and "awful"—and weigh the trade-offs of relaxing it.

The core observation is that when `git pack-objects` splits output into multiple packs (triggered by `--max-pack-size`), the code recomputes the packfile’s hash three times: once during writing (via `struct hashfile`), once during read-back verification, and once during `fixup_pack_header_footer()`. Peff notes this is unique to the split-pack path; the common case (single pack) only hashes once. Both reviewers agree the read-back verification (step b) is redundant and could be dropped without sacrificing safety, as Git does not re-verify other on-disk data like loose objects or refs. The discussion is purely exploratory—neither proposes a patch—but Peff outlines the technical constraints: dropping the initial hash (step a) would require pessimistically assuming a split pack, forcing a full re-read of the data in the common case, which is worse for performance.

The thread also clarifies that the unsafe hash variants (introduced for performance) are not currently used in this code path, despite being a prime candidate for optimization. Peff speculates this was an oversight, but notes the split-pack case is rarely exercised, so the performance impact went unnoticed. Patrick agrees switching to the unsafe variant for `fixup_pack_header_footer()` is sensible, though neither treats it as urgent.

Peff’s closing remark contextualizes the triple-hash as a relic of Git’s early "paranoid" era, where checksums were aggressively verified. He contrasts this with modern practices like `PARSE_OBJECT_SKIP_HASH_CHECK` and the commit-graph, which prioritize performance over exhaustive validation. The pack checksum, he argues, is less critical than object hashes, making this a viable candidate for relaxation. No decisions are made, but the exchange lays groundwork for a future patch if someone chooses to pursue it. The Trace2 byte-counting patch itself remains unaffected; this is a tangential performance discussion.
