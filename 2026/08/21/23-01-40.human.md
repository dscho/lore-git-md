This is a bugfix series targeting the `git branch` command when used with submodule recursion and a nameless start point (like a raw object ID). The issue surfaces when `submodule.propagateBranches` is enabled, causing either a BUG abort (in repositories without submodules) or an early failure (with submodules) due to a missing tracking name. The problem is reproducible across recent Git versions (2.54.0, 2.55.0, and `master`), so the patches are based on `maint`.

The series consists of two patches: the first prevents tracking a start point that lacks a ref, while the second allows recursion to proceed even when no tracking name is available. The changes are minimal and focused, guarding at the call site rather than modifying the callee (`setup_tracking()`), which aligns with existing conventions in `create_branch()`. The author notes that the exposure is limited to specific configurations (experimental `submodule.propagateBranches`, `submodule.recurse`, a configured remote, and a non-ref start point), but within those bounds, the bug is easy to trigger—especially in scripts that move branches to commits not yet referenced by a ref.

The commit messages are clear and well-motivated, explaining both the bug’s impact (e.g., a misleading abort after a successful branch update) and the rationale for the fix. The author also flags two open questions: whether to address a similar unguarded call in `dwim_and_setup_tracking()` (which currently avoids the bug by coincidence) and whether to relocate the first test from `t3207` to `t3200`. The series builds cleanly and passes relevant tests, including the full suite on the topic branch.

This looks like a solid, well-scoped fix for a real (if niche) issue. The patches are small, the tests are thorough, and the author’s transparency about LLM assistance (and their own validation) adds credibility. The only minor quibble is the test placement, but that’s a bikeshed discussion. Worth attention from anyone using submodule recursion.
