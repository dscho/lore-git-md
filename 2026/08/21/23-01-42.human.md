This is the second patch in a two-patch bugfix series for the submodule subsystem, targeting the experimental `submodule.propagateBranches` feature. It addresses a crash in `git branch --recurse-submodules` when the start point is not a ref name (e.g., a raw object ID) in repositories *with* submodules.

The issue occurs because `submodule_create_branch()` passes three arguments to the helper (`name`, `start-oid`, and `tracking_name`), but when the start point is not a ref, `tracking_name` is NULL. The helper (`git submodule--helper create-branch`) expects exactly three arguments and prints its usage text as an error when it receives fewer, causing the command to fail. The fix makes the `tracking_name` argument optional in both the helper and the caller, allowing recursion to proceed even when there is no tracking name. The patch also improves clarity by pushing the optional argument separately rather than relying on `strvec_pushl()` to stop at the first NULL, which could obscure the intent.

The commit message is thorough, explaining the problem, the root cause, and the solution. It notes that this is the same NULL tracking name issue as the first patch, but reached earlier in the code path when submodules are present. The patch includes a new test in `t/t3207-branch-submodule.sh` to verify that recursion works correctly with a non-ref start point.

The fix is minimal and targeted, touching only the necessary code in `branch.c` and `builtin/submodule--helper.c`. It does not change behavior for start points that *are* ref names, and the new test ensures the crash is resolved. The series as a whole is well-motivated and addresses a real problem in an experimental but increasingly used feature. The patches are under review and look ready for serious consideration.
