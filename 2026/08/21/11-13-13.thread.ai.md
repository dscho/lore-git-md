Core problem or goal
Anselm Schüler asks why Git provides the `--ext-diff` option and why custom diff filters (configured via `diff.<driver>.command` or `diff.external`) are not executed by default in all commands that show diffs (e.g., `git show` vs. `git diff`). The inquiry seeks the design intent behind this behavior, particularly whether it stems from security concerns, performance trade-offs, or historical oversight.

Current status
No decisions or agreements; the thread remains at the inquiry stage. Jeff King (Peff) has provided the first substantive reply, explaining the rationale but not proposing any changes.

Key technical details
- `--ext-diff`: a command-line flag that forces Git to use external diff drivers even when they would not normally be invoked.
- Commands that *do* invoke external diffs by default when configured: `git diff`, `git log -p`, `git format-patch`.
- Commands that *do not* invoke external diffs by default: `git show`, `git stash show -p`, `git cherry-pick -n` (when showing the diff).
- External diff drivers are arbitrary executables; Git passes filenames and labels to them, so they can read/write the working tree, spawn GUI windows, or perform other side effects.
- `textconv`: a Git mechanism for converting binary files to text for diffing, designed to be more constrained and safer than external diff drivers. Peff notes it integrates more smoothly with Git’s commands and is often a better fit for most use cases.

Open questions and loose ends
- Is the distinction between `git diff` (allows external diffs by default) and `git show` (does not) an oversight or a deliberate design choice?
- Are there scenarios where a user would want external diffs in `git diff` but not in `git show`, or vice versa?
- Could the current behavior be rationalized (e.g., via documentation or a config option) without code changes, or would it require a breaking change to existing workflows?

Participant positions
- **Jeff King (Peff)**: Explains that external diff drivers are suppressed in some commands (e.g., `git show`) to avoid disruptive side effects (e.g., spawning GUI windows during `git log`). Suggests the distinction between `git diff` and `git show` may be an oversight rather than intentional. Recommends `textconv` as a safer, more integrated alternative for most use cases, though acknowledges his bias as its author. No objection to the current behavior, but implies it could be revisited if there is demand. Position is substantive (engages with design trade-offs and edge cases).
