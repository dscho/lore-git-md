Core problem or goal
Anselm Schüler asks why Git provides the `--ext-diff` option and why custom diff filters (configured via `diff.<driver>.command` or `diff.external`) are not executed by default in all commands that show diffs (e.g., `git show` vs. `git diff`). The inquiry seeks the design intent behind this behavior, particularly whether it stems from security concerns, performance trade-offs, or historical oversight.

Current status
No decisions or agreements; the thread remains at the inquiry stage. The maintainer and a key contributor have both weighed in to explain the rationale, but no changes to behavior or documentation have been proposed or ruled out. The discussion has clarified that the distinction between commands that allow external diffs by default (`git diff`) and those that do not (`git show`) is intentional, though the reasoning may not be widely documented.

Key technical details
- `--ext-diff`: a command-line flag that forces Git to use external diff drivers even when they would not normally be invoked.
- Commands that *do* invoke external diffs by default when configured: `git diff`, `git log -p`, `git format-patch`.
- Commands that *do not* invoke external diffs by default: `git show`, `git stash show -p`, `git cherry-pick -n` (when showing the diff).
- External diff drivers are arbitrary executables; Git passes filenames and labels to them, so they can read/write the working tree, spawn GUI windows, or perform other side effects. This makes them potentially disruptive in commands where diffs are incidental (e.g., `git show` during a rebase).
- `textconv`: a Git mechanism for converting binary files to text for diffing, designed to be more constrained and safer than external diff drivers. Both Jeff King and Junio C Hamano recommend it as a better fit for most use cases, as it integrates more smoothly with Git’s commands and avoids side effects.
- Junio’s sole remaining use for `--ext-diff` is maintaining "What's cooking" report drafts, which could likely be replaced with a combination of `textconv`, diff hunk header patterns, and the `-W` (function-context) option.

Open questions and loose ends
- Is there a compelling use case for enabling external diffs by default in commands like `git show`, or is the current suppression sufficient for most workflows?
- Could the current behavior be rationalized (e.g., via improved documentation or a config option) without code changes, or would it require a breaking change to existing workflows?
- Should the distinction between commands that allow external diffs and those that do not be documented more explicitly, given that it is intentional but not widely understood?

Participant positions
- **Jeff King (Peff)**: Explains that external diff drivers are suppressed in some commands (e.g., `git show`) to avoid disruptive side effects (e.g., spawning GUI windows during `git log`). Suggests the distinction between `git diff` and `git show` may be an oversight rather than intentional, but defers to Junio’s clarification. Recommends `textconv` as a safer, more integrated alternative for most use cases, though acknowledges his bias as its author. Position is substantive (engages with design trade-offs and edge cases).
- **Junio C Hamano**: Endorses Peff’s explanation and clarifies that the distinction between commands that allow external diffs and those that do not is intentional. Notes that his own use of `--ext-diff` is niche (maintaining "What's cooking" reports) and could likely be replaced with `textconv` and other built-in options. Implies that the current behavior is sufficient for most users and that any changes would need a compelling use case to justify breaking existing workflows. Position is substantive (provides historical context and design intent).

Related work
