This thread tackles a long-standing inefficiency in `git push` from shallow clones, where even tiny changes trigger the resending of entire toplevel trees—gigabytes of redundant data in large repositories. Elijah Newren’s v2 patch introduces `push.shallowExcludeBoundary` (default: `true`) to treat shallow grafts as uninteresting tips during pack generation, slashing unnecessary transfers. The series has sparked a lively debate over correctness and trade-offs, with three competing approaches now on the table.

Elijah’s patch is the most aggressive in optimizing performance but introduces a rare false-positive failure mode: if the server lacks the shallow graft, the push is rejected (though safely, thanks to `receive-pack`’s connectivity checks). He argues this is preferable to the status quo—resending massive trees—and that the edge case is recoverable (users can retry with the config disabled or push refs individually). Derrick Stolee initially framed this as a corruption risk but has since been corrected; his alternative, repurposing `push.negotiate` for shallow repos, avoids the false-positive issue but resends more data and fails in several scenarios Elijah outlined (e.g., rebased PRs, protocol limitations). Patrick Steinhardt’s proposal (`push.negotiate=shallow`) splits the difference, enabling negotiation only for shallow clones, but Elijah counters that it still suffers from a race condition and doesn’t address all failure modes.

The discussion now hinges on whether the project is comfortable trading occasional false-positive failures for significant bandwidth savings. Elijah has clarified the trade-offs, rebutted the corruption concern, and proposed follow-up patches to improve error messages. Stolee’s silence leaves the false-positive issue unresolved, while Patrick’s constructive engagement suggests his negotiation-based approach remains a contender. The series is under active review, with no blocking objections but no clear consensus yet on the best path forward.
