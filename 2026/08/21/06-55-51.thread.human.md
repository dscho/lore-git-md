This thread is about a performance fix for `git push` from shallow clones, authored by Elijah Newren. The problem is that even tiny changes in a shallow clone trigger resending the entire toplevel tree—gigabytes of data in large repos—because Git assumes the server lacks the shallow grafts. Elijah’s patch introduces a new config option, `push.shallowExcludeBoundary` (defaulting to `true`), which treats shallow grafts as uninteresting tips during pack generation, avoiding the redundant transfer.

The series is now at v2, incorporating minor code cleanups suggested by Patrick Steinhardt (e.g., `const` parameters, loop efficiency) and clarifying why `push.negotiate=true` alone isn’t a complete solution. The patch adds a helper function, `append_reachable_shallow_grafts()`, to walk from pushed tips to their grafts and mark them as negative tips, stopping early at commits the server already has. Tests in `t5538-push-shallow.sh` cover edge cases, including rejected refs and interactions with `receive.shallowUpdate`. The config defaults to `true` for optimization, but users can opt out for workflows like seeding new shallow roots.

The main open question is whether to adopt Elijah’s config-based approach or Patrick’s proposed `push.negotiate=shallow` mode, which would enable negotiation for shallow clones. Elijah argues his patch is necessary for edge cases where negotiation fails (e.g., rebased PRs, unrelated repos, or protocol limitations). The discussion remains constructive, with no blocking objections, but the choice between the two approaches is still unresolved. The patch itself is well-scoped and ready for further review.
