This is a short follow-up in the ongoing ODB refactoring series, specifically about **patch 3/7** ("odb/source: let callers discern missing and corrupt objects"). The exchange between Patrick Steinhardt and Karthik Nayak clarifies a subtle but important point in the commit message’s wording.

Karthik points out that the current commit message claims the code "prefers the error of the packed source in case both reads have failed," but the actual logic — as shown in his table — returns the loose backend’s error whenever the packed backend reports `ODB_READ_NOT_FOUND`, even if the loose backend reports a corruption error (`ODB_READ_ERROR`). In other words, the design **prioritizes any error (including corruption) over "not found" errors**, and only prefers the packed backend’s error when both backends report non-"not found" failures.

Patrick acknowledges the distinction but argues the phrasing is still accurate because, in the cases where both backends fail with non-"not found" errors, the packed backend’s error is indeed preferred. The disagreement is purely about documentation clarity, not the logic itself. Karthik suggests rewording the commit message to say something like "prefer other errors over not found errors," which would more precisely reflect the behavior.

This is a **surface-level review** comment — no code changes are proposed or needed — but it highlights how easily error-handling policies can be miscommunicated. The patch remains under review, and the series as a whole is part of Patrick’s larger ODB abstraction effort to make corrupt-object handling consistent and backend-agnostic.
