This is a **bugfix follow-up** in the ongoing ODB transaction series, specifically addressing a **critical design flaw** in the "files" backend’s handling of `.keep` lockfiles identified by Junio Hamano in patch 7/7 of v2. The flaw stems from a lifecycle mismatch: the `.keep` lockfiles are registered as tempfiles during packfile ingestion but are *moved* during transaction commit (`odb_transaction_files_commit()`), leaving the tempfile structures pointing to pre-migration paths. The finalize step (`odb_transaction_files_finalize()`) then fails silently when attempting to delete them, as the files no longer exist at the recorded paths.

Justin Tobler acknowledges the bug and traces its root cause to `index_pack_lockfile()` using the wrong ODB source path. The function currently generates lockfile paths based on the *real* ODB source (e.g., `repo->objects->sources[0]`), but `git-receive-pack` reorders the ODB source list during transaction startup, causing the lockfile paths to become invalid after migration. The fix is straightforward: pass the correct ODB source (`base->source`) to `index_pack_lockfile()` so it generates paths that remain valid post-commit. Justin plans to send a patch later today to correct this.

This is a **substantive correction** that directly impacts the robustness of the transaction system. The flaw undermines the deferred cleanup pattern introduced in the series, risking stranded `.keep` lockfiles if the finalize step fails. The fix is narrowly scoped (a single function call change) but critical for ensuring the "files" backend’s lockfile management works as intended. The discussion also clarifies the transaction lifecycle: `.keep` files are now explicitly tied to the `finalize` callback (not `release`), and callers must ensure reference updates are complete before invoking `odb_transaction_finalize()`. This aligns with the series’ goal of making `receive-pack` backend-agnostic while preserving the "files" backend’s need to defer lockfile cleanup until after references are updated.

The patch will touch `odb/transaction-files.c`, specifically the `odb_transaction_files_write_pack()` function, where `index_pack_lockfile()` is called. Key names involved include `base->source` (the transaction’s ODB source), `transaction->pack_lockfiles` (the list of registered lockfiles), and `tmp_objdir_migrate()` (the function that moves files during commit). The fix does not address the broader design debt around source list reordering (which Justin plans to tackle in a follow-up), but it resolves the immediate correctness issue. No new configuration options or user-visible behavior changes are introduced; this is purely an internal plumbing fix. The series remains cooking in `seen` with no merge status change.
