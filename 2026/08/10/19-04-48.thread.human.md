This thread is about a Windows-specific bugfix for a deadlock in Git’s sequencer during interactive rebase, where the sequencer holds the object database (ODB) lock while spawning `git commit`, causing child processes that trigger auto-maintenance (like repacking) to fail. The fix, authored by Johannes Schindelin (Dscho), releases the ODB lock before spawning `git commit`, following an established pattern, and was recently marked for inclusion in Junio C Hamano’s `next` branch after addressing a commit message clarification.

The patch itself is uncontroversial and considered correct—it touches only `sequencer.c`, adds a Windows-specific regression test, and makes no changes to on-disk formats. Junio accepted the updated commit message, which now explicitly states the ODB will be reacquired in a "refreshed state" after auto-maintenance, resolving his initial safety concern. However, Phillip Wood’s recent review raises two forward-looking questions about broader implications. He suggests two alternative approaches: disabling auto-maintenance during rebase via `-c gc.auto=false` (since `run_auto_maintenance()` is called at the end anyway) or automatically closing the ODB whenever any Git command is spawned, noting that reopening the ODB is likely cheap. Neither suggestion is framed as a blocker, but they reframe the patch as a potential pattern for all Git command spawns rather than just a Windows-specific fix. For now, the patch remains on track for integration, but these ideas may influence future work.
