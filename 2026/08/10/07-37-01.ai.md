This is a follow-up in the geometric repacking series, specifically a reply from Stefan Haller that sharpens the concurrency concern raised earlier. The email is short and substantive, pushing back on Patrick Steinhardt’s framing of the auto-detach mechanism as purely a test-suite issue.

Stefan reiterates that the race condition he observed in lazygit’s test suite—where simple Git commands like `git add` and `git commit` fail with "invalid object" errors—occurs *without* any special repository inspection. Lazygit’s tests are not reaching into Git internals; they are just running ordinary Git operations, yet they still hit the same race. This suggests the problem is not confined to test environments but affects real-world usage when background maintenance runs concurrently with normal Git commands.

The implication is that Git’s current concurrency handling may not be as transparent as intended. Stefan’s position is that tools like lazygit should not have to disable maintenance to avoid errors, and the fact that they do indicates a gap in Git’s robustness. This reply does not propose a solution but elevates the issue from a test-suite quirk to a potential real-world usability problem, making it more likely to attract attention from other reviewers. The thread’s focus has now shifted: while the series itself remains ready for merging, this exchange has opened a small but meaningful question about Git’s background maintenance reliability.
