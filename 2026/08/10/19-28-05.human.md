This is a **security-focused follow-up** in the `gitk` custom commands thread. The author, Tim Wiederhake, acknowledges Junio C Hamano’s critical security concern: the current implementation is vulnerable to arbitrary command injection via unquoted shell substitution of commit metadata (titles, messages, etc.). Tim confirms the flaw is real and traces its origin to a late design change—adding `sh -c` to support process forking and exit-code manipulation—without updating the placeholder interpolation logic to account for shell metacharacters.

Tim frames the fix as a choice between two approaches: (1) revert to direct command execution (no shell), requiring users to write wrapper scripts for complex logic, or (2) implement proper shell escaping for all interpolated values while retaining the convenience of `sh -c`. He invites community input on which path to take, but does not propose a concrete fix or patch in this email. The maintainer (Johannes Sixt) has not yet weighed in on this specific question, though he previously endorsed Junio’s security critique as a blocker.

The thread remains stalled on three fronts: the security flaw, the AI-assisted code ownership policy, and the maintainer’s request for an incremental patch series. This email advances only the security discussion, leaving the other two issues unaddressed. The author’s response is factual and direct, but the lack of a proposed solution suggests the feature is unlikely to progress until the security question is resolved. For readers tracking `gitk` development, this is a clear signal that the patch is not ready for review beyond its security implications.
