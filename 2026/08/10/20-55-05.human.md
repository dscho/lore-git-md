This is a usability-focused bugfix for `git worktree add`. The patch improves error messages when a user tries to create a worktree from a branch name that exists on multiple remotes (e.g., `git worktree add ../foo bar` when both `origin/bar` and `upstream/bar` exist). Previously, Git would fail with a generic "invalid reference" error after silently giving up on resolving the ambiguity. Now, it detects the ambiguity early, explains the problem, and provides actionable advice.

The key change is in `builtin/worktree.c`, where the patch adds a new advice message (`WORKTREE_ADD_AMBIGUOUS_REMOTE_BRANCH_NAME_HINT_TEXT`) that suggests two workarounds: either specify the fully qualified remote branch name (e.g., `origin/bar`) or set `checkout.defaultRemote` in the Git config. The advice is gated behind the new `advice.checkoutAmbiguousRemoteBranchName` setting (enabled by default). The patch also moves an existing `die()` call earlier in the code path to fail fast with a clearer error message, replacing the misleading "invalid reference" diagnostic.

The commit message now thoroughly explains the problematic flow: when multiple remotes match the branch name, Git silently leaves the branch variable unset, which later causes `lookup_commit_reference_by_name()` to fail with a generic error. The new behavior catches this ambiguity immediately and provides a more helpful message. This justification addresses Junio C Hamano’s feedback from v2, which requested a clearer explanation of the error-handling change.

The patch includes updated tests in `t/t2400-worktree-add.sh` to verify the new error message and advice. The implementation is localized and follows Git’s advice-message conventions. The only remaining open question is whether the command-based advice (`git branch -r --list "*/<name>"`) is the best way to help users discover conflicting remotes, but this is a minor usability trade-off rather than a technical blocker.
