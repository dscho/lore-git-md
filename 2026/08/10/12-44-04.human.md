This is the third patch in D. Ben Knoble’s three-part series converting Git’s build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`). The patch itself is not controversial—its goal of making nanosecond precision configurable without recompiling is widely supported—but the implementation has sparked a performance debate that is now largely resolved.

Patrick Steinhardt’s reply here is a brief but substantive technical comment. He clarifies that `repo_config_values()` is the modern, preferred structure for repository-specific configuration, but notes it is currently tied to `the_repository`. This raises the question of whether `core.useNanosec` might eventually be needed for submodules or other repositories. His hunch is that it will, suggesting the setting should be stored in a way that supports multiple repositories rather than being hardcoded to the global one. This nudges the author toward using `repo_settings` (which already handles per-repository configuration) rather than `repo_config_values`, aligning with the project’s broader architectural direction.

The performance regression identified in v1—caused by calling `repo_config_get_bool()` on every `is_racy_stat()` invocation—has already been benchmarked and fixed by caching the value in `repo_settings`. The next iteration (v2) will include this fix, restoring baseline performance. The remaining open question is purely structural: where to store the cached value. Patrick’s input here helps steer the author toward a solution that scales beyond the main repository, avoiding future refactoring. The rest of the series (a Meson build-system fix and a no-op refactor) remains uncontested.
