This is the v4 patch series introducing `git repack --drop-filtered` for partial clones, a feature that allows users to reclaim disk space by safely removing locally cached promisor blobs exceeding a specified size threshold. The series is now complete (7/7 patches) and addresses all feedback from v3, including Junio’s mechanical fixes (usage string formatting, test script style, and documentation SYNOPSIS cleanup). The core functionality remains unchanged: promisor objects are enumerated via `ODB_FOR_EACH_OBJECT_PROMISOR_ONLY`, filtered by size using the new `list_objects_filter__filter_oidset()` helper, and dropped by rebuilding the promisor pack while excluding them, with crash safety guaranteed by the existing repack machinery.

The series introduces two new CLI options (`--drop-filtered` and `--dry-run`), a new helper function (`list_objects_filter__filter_oidset()`), and a new file (`repack-filtered.c`). The implementation is well-scoped: it enforces preconditions (`-a` required, promisor remote required, `--filter` limited to `blob:limit`), avoids lazy fetches during enumeration, and silently disables bitmaps to prevent pack closure issues. The safety guards (merge/rebase/cherry-pick checks and index validation) are now explicitly framed as UX optimizations rather than correctness measures, since lazy-fetching would transparently restore dropped objects. Documentation is thorough, covering preconditions, incompatibilities, implied `-d`, and `--dry-run` preview functionality.

Key technical details for follow-up discussion include the `list_objects_filter__filter_oidset()` helper (which duplicates `blob:limit` logic and is flagged for future refactoring), the two separate promisor-object walks (one for enumeration, one for repacking), and the deferred work (drop log, remote verification via `remote-object-info`, and Junio’s proposed time-based heuristic for avoiding recently fetched objects). The series is production-ready, with no known blocking issues, and the author has confirmed intent to perform full test suite runs and trial merges into `next` and `seen` before posting the next revision.
