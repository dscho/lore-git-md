This is the sixth patch in the v4 series introducing `git repack --drop-filtered` for partial clones. It adds two safety guards to prevent `--drop-filtered` from running during ongoing operations (merge, rebase, cherry-pick, etc.) or dropping blobs referenced by the current index. Both guards are skipped for bare repositories, which lack a worktree or index.

The first guard uses `wt_status_get_state()` to detect in-progress operations and aborts with a clear error message ("cannot be used while another operation is in progress"). The second guard reads the index with `repo_read_index()` and checks each cache entry against the `drop_oids` set, aborting if a referenced blob would be dropped ("cannot drop '<path>': it is referenced by the current index"). The commit message and code comments explicitly frame these as UX optimizations rather than correctness measures, since lazy-fetching would transparently restore dropped objects.

The patch adds 49 lines to `builtin/repack.c` and 36 lines to the test script (`t/t7706-repack-drop-filtered.sh`). The tests cover both guards: one creates a merge conflict and verifies the command refuses to run, while the other adds a large blob to the index and confirms the command refuses to drop it. The implementation is clean and well-scoped, with no new dependencies beyond the existing `wt-status` and `read-cache-ll` APIs.

This patch is production-ready and integrates smoothly with the rest of the series. The safety guards address Junio’s earlier concern about redundant network operations by preventing immediate re-fetching, though his proposed time-based heuristic (avoiding recently fetched objects) remains deferred to a follow-up. The current design is simpler and avoids the need for timestamp tracking, which would require extending the promisor object log or introducing a separate mechanism.
