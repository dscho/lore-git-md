This is a **design discussion contribution** in the ongoing thread about modernizing Git’s interactive patch selection workflow. Patrick Steinhardt responds to Stefan Haller’s suggestion that Git should avoid building interactive UIs and instead rely on external tools like lazygit. Patrick acknowledges the Unix philosophy of specialization but argues that Git’s core workflows—such as staging, discarding, or deferring hunks—are currently too cumbersome for users who rely solely on Git’s built-in commands. He frames these workflows as *core functionality* that Git should improve, rather than delegating to external tools.

Patrick’s position is pragmatic: while he agrees that Git should not build a "full UI" (e.g., a comprehensive TUI for history editing), he believes that *basic* interactive improvements—such as a navigable interface for hunk selection—are within scope. He cites Jujutsu (JJ) as an example of how small, targeted UI enhancements can significantly improve usability without requiring a full-blown interface. His reply reframes the discussion around *where to draw the line*: Git should address clear gaps in its core workflows (e.g., the need for separate `git add -p` and `git checkout -p` commands) but avoid duplicating the work of specialized tools like lazygit.

The email does not propose a specific implementation (e.g., ncurses dependencies or changes to `add--interactive`) but instead focuses on *motivation*. Patrick’s argument hinges on the distinction between "core functionality" (e.g., hunk selection) and "full UI" (e.g., a TUI for history editing). This leaves room for incremental improvements—such as a hierarchical, navigable interface for hunks—while deferring larger UI modernization efforts (e.g., a TUI for `git history`) to external tools or future discussions.

For readers tracking this thread, Patrick’s reply clarifies that the immediate priority is *unifying triage actions* (stage/discard/defer) into a single session, with UI improvements serving as a means to that end. His position bridges the gap between Junio C Hamano’s incremental approach (extending `git add -p`) and Stefan Haller’s external-tool proposal, suggesting that Git can—and should—improve its built-in workflows without overcommitting to a full UI rewrite. The discussion now centers on *how much* UI modernization is necessary to solve the workflow problem, rather than whether it belongs in Git at all.
