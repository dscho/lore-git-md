This is a **design discussion contribution** in the ongoing thread about unifying Git’s interactive patch selection workflow. Patrick Steinhardt responds to Junio C Hamano’s focus on workflow unification (stage/discard/defer in a single session) by proposing a more ambitious UI redesign inspired by Jujutsu (JJ) and other modern tools. He suggests adopting a full **TUI (text-based user interface)**—specifically an ncurses-based interface—that would allow users to interactively select files, hunks, and even individual lines, rather than Git’s current linear prompt-loop model.

Patrick’s proposal shifts the discussion from incremental improvements (e.g., adding a "discard" action to `git add -p`) to a broader rethinking of Git’s interactive interfaces. He cites JJ’s `jj split --interactive` as a superior model, where users can navigate a hierarchical view of changes (files → hunks → lines) and toggle selections without being constrained by a one-hunk-at-a-time workflow. This aligns with earlier suggestions (e.g., Fugitive) for a more visual interface but goes further by explicitly advocating for ncurses-based TUIs across Git, including for commands like `git history` (e.g., for reordering or squashing commits).

The email introduces a potential tension between two approaches: Junio’s narrow, near-term goal (unifying triage actions in a single session while preserving the existing prompt-loop UI) and Patrick’s vision of a more radical UI overhaul. Patrick’s proposal is technically ambitious—it would require significant changes to Git’s interactive machinery (e.g., `add--interactive` or `add-interactive.c`) and introduce new dependencies (ncurses)—but he frames it as a way to make Git more "visual and easier to use." The discussion now hinges on whether the project should prioritize incremental workflow fixes or invest in a larger UI modernization effort.

Key technical details introduced:
- **Subsystems**: The proposal would likely touch `add--interactive` (or its C rewrite), `git history`, and potentially other interactive commands (e.g., `git rebase -i`). It would also require integrating ncurses or a similar library.
- **New behavior**: A hierarchical, navigable TUI for selecting changes (files → hunks → lines), replacing the linear prompt-loop. This would enable non-linear workflows (e.g., jumping between hunks, toggling selections out of order).
- **Open questions**: Whether the project is willing to adopt ncurses as a dependency, how to maintain backward compatibility with the existing prompt-loop UI, and whether this should be a standalone effort or part of a broader modernization of Git’s interactive commands.

Patrick’s position is clear: he favors a TUI-based redesign as the path forward, arguing that it would address both the workflow limitations (stage/discard/defer) and the UI frustrations (linear prompts) in one stroke. This sets up a potential debate about scope—whether to tackle the problem incrementally or holistically—and about the trade-offs of introducing new dependencies. The thread’s next steps may involve weighing these options or exploring hybrid approaches (e.g., a TUI as an optional mode alongside the existing prompt-loop).
