This is a follow-up discussion in the ongoing refactoring thread about Git’s repository configuration handling. The series itself—three patches from Tian Yuchen cleaning up documentation and structure in `environment.c` and `environment.h`—is technically complete and ready for final review, with all maintainer feedback addressed in v3. What’s new here is Patrick Steinhardt’s deeper exploration of a long-term architectural question: how to lift the current restriction that `repo_config_values()` can only operate on `the_repository`, and whether the split between `repo_settings` and `repo_config_values` is still justified.

Patrick proposes merging the two structures into a single `git_config_values` (or `git_settings`) that would exist at two levels: a truly global instance for system- and user-wide settings, and a per-repository instance for overrides. The function `repo_config_values()` would then return a constant pointer to the appropriate structure based on whether a repository is passed in, with callers forbidden from modifying it directly. He acknowledges that this could require significant caller-side changes—passing a `struct git_config_values` down the stack instead of a `struct repository`—but argues that this is the right direction for subsystems that are inherently repository-agnostic.

The discussion remains exploratory and does not block the current series, but it signals that the `the_repository` removal effort is now colliding with configuration handling in a way that may require broader redesign. For now, the v3 patches are still the focus; this email is a heads-up that the next phase of that effort could be more invasive.
