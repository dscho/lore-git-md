Subject: [PATCH 0/4] odb: remove lazy-loading of alternates
Series version: v3 (current)
Originating author: Patrick Steinhardt
Thread type: patch series

Core problem or goal
Refactor the object database (ODB) subsystem to remove lazy-loading of alternate object databases. The current implementation defers loading alternates until they are needed, but many code paths already parse alternates eagerly (e.g., during object lookups), making the lazy-loading optimization ineffective. The goal is to simplify the code by initializing all alternate ODBs upfront during primary ODB setup, reducing scattered calls to `odb_prepare_alternates()` and enabling future work to move alternates into the "files" backend. The series consists of five patches, with the first patch reordering repository initialization to ensure the object database is created *after* the full repository configuration is written, fixing a correctness issue with `core.ignoreCase` lookups. The design discussion has converged on retaining case-insensitive deduplication for now but documenting it as `NEEDSWORK` and acknowledging the consensus that it may be removed in the future for simplicity. However, the first patch’s approach to the `core.ignoreCase` timing issue is now blocked by two technical constraints: (1) `repo_ignore_case()` cannot be used because it relies on `repo_config_values()`, which is hardcoded to `the_repository` and would break submodule support, and (2) Junio’s latest review of patch 2/5 questions whether `core.ignoreCase` should be part of the repository configuration at all, given that repositories spanning filesystems with different case sensitivities could lead to inconsistent behavior in the equality function. The latest discussion between Patrick and Junio clarifies that the case-insensitive deduplication mechanism, while imperfect, has worked reliably for two decades without reported issues and is retained to avoid regressing edge cases (e.g., repositories with thousands of alternates). Patrick argues that retroactively imposing limitations (e.g., declaring repositories cannot span filesystems with mixed case sensitivity) could break existing setups, and the mechanism’s practical reliability outweighs its theoretical flaws.

Key technical details
- **Subsystems/files touched**: Primarily `odb/` (`odb.c`, `odb.h`, `odb/source.h`), with changes in `builtin/fsck.c`, `builtin/pack-objects.c`, `commit-graph.c`, `pack-bitmap.c`, `setup.c` (new in v3), and others (14 files total). The first patch (1/5) touches `setup.c` to reorder repository initialization, while patch 2/5 migrates from `khash` to `hashmap` to support dynamic comparison functions. Patch 3/5 removes calls to `odb_prepare_alternates()` from 11 files, centralizing alternate initialization in `odb.c`. Patch 4/5 removes the `loaded_alternates` field from `odb.h` and simplifies `odb_add_to_alternates_file()`. Patch 5/5 removes the `alternates_db` field from `odb.h` and updates `odb_new()` and `odb_prepare()` to pass the environment variable directly.
- **Symbols changed/removed**: `loaded_alternates` (field, removed in patch 4/5), `alternates_db` (field, removed in patch 5/5), `odb_prepare_alternates()` (usage removed; made static in patch 3/5). Patch 2/5 introduces `source_paths_icase` (field in `struct object_database`) and the case-insensitive comparison functions (`odb_source_paths_cmp()`, `odb_source_by_path_cmp()`) but documents them as `NEEDSWORK`. The first patch’s approach to `core.ignoreCase` is now blocked by (1) `repo_config_values()` (hardcoded to `the_repository`), which prevents the use of `repo_ignore_case()` in submodule contexts, and (2) Junio’s design concerns about whether `core.ignoreCase` should be used for alternate path comparisons at all. The latest discussion confirms that patch 1/5 resolves the timing issue in `odb_source_paths_cmp()` by ensuring the repository is fully initialized before ODB creation, as verified by a `BUG()` check.
- **Behavioral changes**: No intended user-visible changes, but the series removes lazy-loading, which may affect performance or error handling in edge cases (e.g., repositories with thousands of alternates, corrupt alternates, or commands that previously avoided loading alternates entirely). Patch 2/5 retains case-insensitive deduplication but documents it as a candidate for future removal, though the latest discussion reaffirms its practical reliability and backward-compatibility value. The first patch’s correctness fix for `core.ignoreCase` lookups is now verified to work as intended, addressing Junio’s concern about `o->repo->initialized` in `odb_source_paths_cmp()`. Patch 3/5 centralizes alternate initialization, which may slightly increase startup time for commands that previously avoided loading alternates when none were present (e.g., `git fsck`). Patches 4/5 and 5/5 are mechanical cleanups with no behavioral impact.
- **Code delta**: Net reduction of 16 lines across the series (98 insertions, 114 deletions). The first patch adds 6 lines, patch 3/5 removes 42 lines (46 deletions, 4 insertions), patch 4/5 removes 9 lines (1 insertion, 10 deletions), and patch 5/5 removes 6 lines (9 insertions, 15 deletions). Patch 2/5 migrates from `khash` to `hashmap` without changing the line count.
- **Dependencies**: Builds on Patrick’s prior ODB refactoring series (`ps/odb-make-creation-pluggable`). The first patch’s timing fix is now verified to work, but the `repo_config_values()` limitation and Junio’s broader design concerns about case-sensitivity remain unresolved and may require a new approach or a separate fix to `repo_ignore_case()`.
- **Related work**: Part of the broader ODB abstraction effort led by Patrick Steinhardt.

The latest discussion clarifies that the case-insensitive deduplication mechanism, while imperfect, has worked reliably for two decades and is retained to avoid regressing edge cases. However, no resolution has been proposed for the `repo_config_values()` limitation or Junio’s broader design concerns. Patrick may need to (1) implement a submodule-compatible version of `repo_ignore_case()`, (2) adopt one of Junio’s proposed alternatives (e.g., requiring users to spell paths consistently, declaring repositories cannot span mixed-case filesystems, or having each ODB source report its own case-sensitivity), or (3) proceed with the current approach and document the limitations.
- **Future of case-insensitive deduplication**: Patch 2/5 retains case-insensitive deduplication but documents it as `NEEDSWORK`, reflecting the consensus that it may be removed in the future. The latest discussion reaffirms its practical reliability and backward-compatibility value, but Junio’s preference for simplicity (dropping the mechanism entirely) remains unaddressed. No reviewer has engaged with the `NEEDSWORK` note beyond Junio’s critique, and the mechanism’s future is still uncertain.
- **Performance implications of eager alternate loading**: The commit message acknowledges this as a low-risk trade-off, but no reviewer has engaged with the concern, particularly for commands like `git fsck` that previously avoided loading alternates when none were present. Edge-case handling (e.g., repositories with thousands of alternates or corrupt alternates) also remains untested.
