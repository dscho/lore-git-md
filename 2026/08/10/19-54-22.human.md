This is a **bugfix follow-up** in the ongoing ODB transaction series from Justin Tobler. The patch series (v2 of 6) aims to make `git receive-pack` backend-agnostic by replacing hardcoded packfile writes with a new ODB transaction interface, `odb_transaction_write_pack()`. The current email is a reply to Junio Hamano’s review of the final patch (7/7), which uncovered a **critical design flaw** in the "files" backend’s handling of `.keep` lockfiles.

The issue is straightforward: during packfile ingestion, `.keep` lockfiles are registered as tempfiles with paths pointing to the quarantine directory. However, when the transaction is committed, the quarantine directory is migrated to the main object store, moving the lockfiles to new locations. The finalize step then fails to delete them because the tempfile structures still reference the *pre-migration* paths. Justin acknowledges this as a bug and proposes a simple fix: pass the correct ODB source to `index_pack_lockfile()` so it generates the final (post-migration) path for the lockfile. The root cause is deeper, though—`git receive-pack` reorders the ODB source list when applying the transaction, breaking the assumption that the first source (`repo->objects->sources[0]`) is the correct one. This misuse of `repo->objects->sources[0]` instead of the transaction’s `base->source` was already flagged in Junio’s review, and Justin plans to address it in a follow-up by tracking the source separately.

The fix itself is small and targeted, but it highlights a broader fragility in the transaction system’s design. The deferred cleanup pattern (where `.keep` lockfiles are deleted during finalize) is undermined by the lifecycle mismatch between commit and finalize. Junio’s review questioned whether this pattern is sustainable, and Justin’s response suggests it will remain for now, with the understanding that callers must ensure reference updates are complete before invoking `odb_transaction_finalize()`. The next version (v3) will clarify this requirement in the commit message and documentation.

This is a **well-motivated bugfix** with clear stakes: without it, `.keep` lockfiles could be stranded, potentially causing future packfile corruption or unnecessary disk usage. The fix is narrowly scoped to the "files" backend, but it’s a blocker for the series’ correctness. Justin’s response is direct and actionable, and the proposed solution aligns with the series’ goal of making the ODB abstraction robust. The patch is part of a larger, actively reviewed effort (the ODB abstraction work led by Patrick Steinhardt) and is cooking in `seen`. If the fix lands cleanly, it should unblock the series for further integration.
