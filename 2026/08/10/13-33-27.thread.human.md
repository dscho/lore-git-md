This thread is about Patrick Steinhardt’s patch series to refactor Git’s object database (ODB) subsystem by removing lazy-loading of alternate object databases. The goal is to simplify the code by initializing all alternate ODBs upfront during primary ODB setup, reducing scattered calls to `odb_prepare_alternates()` and enabling future work on the ODB backend. The series is currently at version 2, with a v3 anticipated to address design feedback.

The key technical change is the removal of lazy-loading, which may affect performance or error handling in edge cases, though no user-visible changes are intended. The series touches 12 files, primarily in the `odb/` subsystem, and removes or modifies several symbols, including `loaded_alternates` and `alternates_db`. A major design discussion has centered on patch 1, which originally retained case-insensitive deduplication for alternate paths. After feedback from Jeff King and Junio Hamano, the consensus is now to switch to case-sensitive comparisons only, simplifying the code and eliminating complexity. However, Peff’s latest review raises a correctness concern: the current implementation caches the case-sensitivity flag during ODB initialization, which could be incorrect if the repository’s configuration isn’t fully loaded at that time. He suggests using `repo_ignore_case()` instead, which centralizes config handling.

The series is queued in Junio’s `seen` branch as of July 10, but its integration status remains pending a v3 revision. Patrick has agreed to simplify patch 1 by removing case-insensitive handling, but Peff’s new concern may require additional changes. Other reviewers, including Justin Tobler and Karthik Nayak, have provided feedback, but their engagement has been mostly surface-level or stylistic. Open questions include the exact implementation of patch 1’s simplification and the performance implications of eager alternate loading, particularly for commands like `git fsck` that previously avoided loading alternates when none were present. A procedural question about Junio’s merge strategy remains unaddressed but does not affect the series’ content.
