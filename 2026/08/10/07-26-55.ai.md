This is a **design discussion contribution** in the ongoing thread about unifying Git’s interactive patch selection workflow. Stefan Haller responds to Patrick Steinhardt’s proposal for ncurses-based TUIs in Git by questioning whether such functionality belongs in core Git at all. He draws a parallel to **lazygit**, a popular third-party TUI tool, and suggests that Git should focus on providing core functionality while leaving UI enhancements to specialized external tools.

Stefan’s email introduces a pragmatic counterpoint to Patrick’s vision: rather than reinventing a TUI within Git, the project could rely on existing tools like lazygit, which already implement intuitive interfaces for staging, discarding, and navigating changes. He frames this as a separation of concerns—core Git handles the plumbing, while external tools handle the presentation. This aligns with the broader Unix philosophy but contrasts with Patrick’s argument that Git should modernize its own interactive interfaces to improve usability.

The email does not engage with the technical details of Patrick’s proposal (e.g., ncurses dependencies or changes to `add--interactive`) but instead challenges the *motivation* behind it. Stefan’s position is clear: if the goal is to provide a better user experience, Git should not duplicate the work of tools like lazygit, which already do this well. This adds a new dimension to the thread’s debate—whether the solution should be internal (Patrick’s TUI) or external (Stefan’s tooling ecosystem).

For readers tracking this thread, Stefan’s reply highlights a potential alternative path: instead of building a TUI into Git, the project could focus on improving the underlying APIs (e.g., `add--interactive`, `git history`) to make them more consumable by external tools. This could address the workflow problem (stage/discard/defer) without requiring Git to adopt new dependencies or UI paradigms. The discussion now hinges on whether the project should prioritize internal modernization or external integration.
