This is a **design discussion contribution** in the ongoing thread about improving Git’s interactive patch selection workflow. Stefan Haller responds to Patrick Steinhardt’s proposal for a TUI (text-based user interface) by questioning whether such functionality belongs in Git’s core at all. He draws a parallel to **lazygit**, a popular third-party tool that already provides an intuitive, ncurses-based interface for staging, discarding, and managing changes, and suggests that Git should focus on its core functionality while leaving UI enhancements to external tools.

Stefan’s email introduces a pragmatic counterpoint to Patrick’s vision of modernizing Git’s interactive interfaces. While Patrick argues for integrating a TUI into Git to make it more "visual and easier to use," Stefan frames this as a matter of **separation of concerns**: Git should provide the plumbing (e.g., APIs for staging, discarding, and applying hunks), while external tools like lazygit should handle the presentation layer. This aligns with Git’s historical design philosophy, where the core project prioritizes scriptability and composability over built-in visual interfaces. Stefan’s position implies that adding ncurses-based TUIs to Git would duplicate functionality already well-handled by tools like lazygit, without necessarily improving the core workflow.

The email also subtly reinforces Junio C Hamano’s original focus on **workflow unification** (stage/discard/defer in a single session) rather than UI modernization. By citing lazygit’s ability to handle Junio’s use case (selecting hunks for staging or discarding), Stefan suggests that the problem is already solved—just not within Git itself. This raises a broader question for the thread: *Is the goal to improve Git’s built-in tools, or to ensure that Git’s plumbing is robust enough to enable better third-party tools?* Stefan’s perspective leans toward the latter, which could shift the discussion away from implementation details (e.g., ncurses dependencies) and toward API design (e.g., making it easier for tools like lazygit to interact with Git’s internals).

The tone is measured and inquisitive rather than dismissive. Stefan doesn’t outright reject Patrick’s proposal but instead asks whether the effort is justified given the existence of tools like lazygit. This invites further discussion about the trade-offs between built-in functionality and ecosystem diversity. For example, a built-in TUI might lower the barrier to entry for new users, while relying on external tools could encourage innovation and specialization. The thread’s next steps may involve weighing these trade-offs or exploring whether Git’s existing APIs are sufficient to support tools like lazygit without requiring core changes.

For readers following the thread, Stefan’s email is a reminder that **not all problems require built-in solutions**. It’s a useful counterbalance to Patrick’s ambitious proposal, grounding the discussion in Git’s long-standing emphasis on modularity and scriptability. Whether this perspective gains traction will depend on how other participants view the balance between core functionality and external tooling.
