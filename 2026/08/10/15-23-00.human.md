This is a **philosophical reply** in the ongoing design discussion about improving Git’s interactive patch selection workflow. Junio C Hamano responds to Stefan Haller’s suggestion that Git should avoid building interactive UIs and instead rely on external tools like lazygit. Junio broadly agrees with Stefan’s position, framing it as a matter of not competing with downstream tools that build on Git’s core functionality.

Junio’s email reinforces the project’s long-standing philosophy: Git should avoid bundling features that directly compete with external tools, even if those tools provide a better user experience. He argues that if Git were to include an officially sanctioned TUI (like the one Patrick Steinhardt proposed), it would unfairly disadvantage third-party tools that offer similar functionality—not because Git’s implementation would be superior, but simply because it is bundled with Git. The only exception he allows is when Git’s built-in version serves as a "usable but perhaps not pretty" demonstration of what could be done better by external tools.

This reply shifts the thread’s focus from *how* to improve interactive workflows to *whether* Git should even attempt to do so internally. Junio’s stance aligns with Stefan’s pragmatic view: Git’s role is to provide robust plumbing, while presentation-layer improvements (like TUIs) belong in external tools. The implication is that the project should prioritize making Git’s core APIs more consumable by tools like lazygit, rather than duplicating their functionality.

For readers following this thread, Junio’s reply suggests that the path forward is unlikely to involve a TUI or other UI modernization within Git itself. Instead, the discussion may pivot toward identifying specific API improvements (e.g., to `add--interactive` or `git history`) that would enable external tools to better support triage workflows like stage/discard/defer. The thread’s earlier proposals—Junio’s unified triage actions, Patrick’s hierarchical TUI, and Christian Couder’s advanced use cases—now face a higher bar: they must justify why they belong in Git’s core rather than in external tooling.
