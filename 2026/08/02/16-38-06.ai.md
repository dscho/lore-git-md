This is a substantive review reply in the ongoing GSoC series adding `%(objecttype)` support to `git cat-file --batch-command` for remote-object-info queries. Jeff King (Peff) engages directly with Junio C Hamano’s proposed design for the batch result storage in `fetch-object-info.c`, refining the trade-offs between memory efficiency and code clarity.

Peff acknowledges that Junio’s array-of-structs design (a single array of `struct { struct oid *oid; enum object_type type; size_t size; }`) is viable but flags two practical concerns. First, it wastes memory when only a subset of fields (e.g., just `type`) is requested, since every array element reserves space for all fields. This matters because batch queries are explicitly designed to handle many objects at once, unlike the single-object `struct object_info` used elsewhere. Second, signaling which fields are valid becomes awkward: while `OBJ_NONE` can serve as a sentinel for `type`, there is no natural sentinel for `size`, and a per-object flag would duplicate information that is constant across the entire query.

The discussion converges on a hybrid approach: use a single array of lightweight structs, but let the caller decide which fields to populate, avoiding sentinels entirely. Peff emphasizes that the remote-object-info protocol itself does not require `struct object_info` at all, since the server transmits raw strings (e.g., `"blob"`, `"1234"`) that the client parses directly. This means the entire refactoring can bypass `read_object_info()` and its parameter-passing conventions, simplifying the implementation. The key files remain `fetch-object-info.c` and `builtin/cat-file.c`; no new subsystems are involved.
