Thread identity
Subject: [PATCH] read-cache: avoid index expansion in repo_index_has_changes() on unborn HEAD
Series version: standalone patch (v2 anticipated)
Originating author: Sahitya Chandra
Thread type: bug fix (performance regression in sparse-checkout/sparse-index)

Core problem or goal
When `repo_index_has_changes()` is called without an explicit tree and HEAD is unborn (e.g., on a newly created orphan branch), the function falls back to walking the index directly, which forces a full expansion of any sparse directory entries. This expansion is unnecessary because an unborn HEAD is logically equivalent to the empty tree, so every index entry is new. The patch replaces the fallback with a comparison against the empty tree, keeping the unborn-branch case on the same diff code path as normal tree comparisons and avoiding the expansion.

Open questions and loose ends
- **Motivation**: The patch originated from a TODO comment rather than a user-reported issue. Sahitya concedes no realistic use case exists where a user with an unborn HEAD would simultaneously be using a sparse index containing millions of uncommitted files, but argues the patch still has value: it removes a TODO, unifies the code path, and eliminates an `ensure_full_index()` call that future readers would otherwise need to reason about.
- **Test helper flaw**: The output format (`dirty=%s`) is ambiguous if multiple files are dirty; Sahitya plans to fix this in v2.
