Junio responds to Michael Montalbo’s correctness concern about the placement of the `buffer_is_binary()` check in `has_conflict_markers()`. Montalbo pointed out that the current implementation could misclassify a binary file as conflicted if its first line coincidentally matches a conflict-marker pattern (e.g., starts with `<<<<<<<`), and suggested moving the binary check *before* the marker check to avoid false positives.

Junio disagrees, arguing that false positives are preferable to false negatives in this context. He views early detection of a potential conflict marker—even if it’s a false positive—as a feature, not a bug, because it forces the user to inspect the file more closely rather than silently proceeding. His position is that the current placement is correct and that the trade-off (failing early on a false positive) is acceptable. He also briefly raises a tangential question about whether Git’s attribute system should influence this logic, though he doesn’t propose a change here.

The exchange is substantive but narrow: it’s about a single line of code and its implications for edge cases. Junio’s response suggests the patch will likely proceed as-is, but the discussion leaves open whether the attribute system could play a role in future iterations.
