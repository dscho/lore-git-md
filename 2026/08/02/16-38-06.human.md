This is a substantive technical discussion in the ongoing GSoC series to extend `git cat-file --batch-command` with `%(objecttype)` support for remote-object-info queries. Jeff King (Peff) and Junio C Hamano are refining the architectural design for storing batch query results in `fetch-object-info.c`.

Peff responds to Junio’s proposed array-of-structs design with two practical concerns. First, allocating a full struct for every object wastes memory if only one field (e.g., type) is requested, since unused fields like `size` still consume space. This matters because batch queries are meant to handle many objects at once, unlike single-object queries where memory overhead is negligible. Second, signaling which fields are valid is awkward: while `OBJ_NONE` can mark an unknown object type, there is no natural sentinel for missing size or other future metadata. Peff suggests that a per-query flag (rather than per-object flags) would be cleaner, though he acknowledges Junio’s point that the caller knows upfront which fields are requested.

The discussion remains focused on `fetch-object-info.c` and does not revisit the protocol or user-facing behavior. Both participants agree that the remote-object-info protocol avoids the need for `struct object_info` entirely, but they are still weighing trade-offs between Junio’s array-of-structs and Pablo’s earlier `object_info_results` with separate arrays and boolean flags. Peff’s feedback is advisory and does not block the series, but it highlights memory efficiency and clarity as key considerations for the final design. The series remains under review with no merge status implied.
