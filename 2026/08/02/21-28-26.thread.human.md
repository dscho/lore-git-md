This thread is about a small but targeted performance optimization in Git's sparse-index handling. Sahitya Chandra posted a patch that avoids unnecessary index expansion when `repo_index_has_changes()` is called on an unborn HEAD (like a newly created orphan branch). Instead of walking the index directly—which forces a full expansion of sparse directory entries—the patch compares against the empty tree, keeping the unborn-branch case on the same code path as normal tree comparisons.

The patch originated from a TODO comment rather than a user-reported issue, and while Sahitya concedes there’s no realistic scenario where a user with an unborn HEAD would have millions of uncommitted files in a sparse index, both he and Elijah Newren agree the change is still worthwhile. It removes a TODO, unifies the code path, and eliminates an `ensure_full_index()` call that future readers would otherwise need to reason about. Elijah’s review was substantive, focusing on design and correctness rather than surface-level issues, and he suggested the commit message should be upfront about the lack of a concrete use case, framing the patch as a code hygiene improvement.

The only remaining loose end is a minor flaw in the test helper (`test-tool read-cache --index-has-changes`), where the output format (`dirty=%s`) is ambiguous if multiple files are dirty. Sahitya plans to fix this in a v2 patch, which should be the final version before the patch is ready for merging. The patch touches only `read-cache.c` and adds a test case in `t1092-sparse-checkout-compatibility.sh`, with no changes to the on-disk format. It’s part of the broader sparse-checkout/sparse-index performance effort led by contributors like Derrick Stolee and Elijah Newren.
