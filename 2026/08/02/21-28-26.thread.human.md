This thread is about a small but important performance fix for Git’s sparse-checkout/sparse-index feature. Sahitya Chandra posted a patch on August 2nd that prevents an unnecessary index expansion when `repo_index_has_changes()` is called on an unborn HEAD (like a newly created orphan branch). Instead of walking the index directly—which forces a full expansion of sparse directory entries—the patch compares the index against the empty tree, keeping the logic consistent with normal tree comparisons and avoiding the performance hit.

The patch is clean and well-contained: it modifies `read-cache.c`, adds a test helper (`test-tool read-cache --index-has-changes`), and includes a new test case in `t1092-sparse-checkout-compatibility.sh` to verify the fix. The implementation actually reduces the code size by 28 lines, and the test confirms that paths inside sparse directories are correctly reported without expanding the index. So far, there’s been no feedback—positive or negative—on the patch, which suggests it might be ready for integration once someone reviews it.

This fix is part of the broader sparse-checkout/sparse-index performance work led by Derrick Stolee and Elijah Newren. The ping from Sahitya is just a routine nudge to keep the patch from slipping through the cracks, not a sign of any urgency or concern. If you’re following the sparse-index effort, this is a low-risk, high-impact improvement worth watching.
