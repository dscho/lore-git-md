This is a reply in the ongoing RFC thread about restricting Git 3.0's hex object ID parsing to lowercase only. The email responds to Jeff King's observation that uppercase hex within object payloads (commits and tags) can create parallel histories, a case the proposed breaking change does not address.

Brian acknowledges the issue and agrees that multiple representations of the same logical data are problematic, even if the example is unlikely to occur accidentally. He adds a new technical detail: objects containing uppercase hex cannot be round-tripped through Git's interoperability code (which only emits lowercase object IDs), effectively making them SHA-1-only. This further complicates the case-sensitivity problem by tying it to hash-algorithm compatibility, not just external tooling or security.

The response does not propose a solution or alter the patch series; it simply accepts the edge case as a real (if niche) problem that the current proposal does not solve. This may strengthen the argument for the breaking change by showing that case sensitivity creates broader consistency issues, or it may weaken it by demonstrating that the proposed fix is incomplete. The thread remains focused on design discussion, with no implementation changes or maintainer decisions yet. Key context: the interoperability code Brian references is part of Git's SHA-256 support, where object IDs are always emitted in lowercase to ensure compatibility across tools.
