This is a follow-up in the GSoC thread extending `git cat-file --batch-command` to support `%(objecttype)` for remote-object-info queries. Junio C Hamano responds to Jeff King’s architectural feedback, clarifying the historical design intent of `struct object_info` and reinforcing Peff’s recommendation to avoid reusing it for batch queries.

Junio explains that `struct object_info` was originally introduced in 2011 as a container for *extended parameters* to `sha1_object_info_extended()`, allowing the function to accept new query fields without changing its signature. The pointers in the struct (e.g., `size_p`, `type_p`) were meant to point to caller-provided variables or struct members—*not* to serve as storage for the results themselves. For batch queries (N objects), this design breaks down: you’d either loop over objects, calling the function once per object and consuming the results immediately, or pre-allocate storage for all results and point the struct’s pointers at the appropriate slots. What you *shouldn’t* do, Junio emphasizes, is create an array of `object_info` structs—this misuses the pattern and was never the intended use case.

The email reinforces Peff’s earlier recommendation: the remote-object-info path should bypass `object_info` entirely and define its own lightweight query structure. Instead of reusing `object_info`’s pointer-based model, the remote path should use simple boolean flags (e.g., `want_type`, `want_size`) to declare what metadata it needs, then parse the server’s response directly into `expand_data`, the cat-file-specific struct. This avoids the conceptual awkwardness of repurposing a single-object query mechanism for batch operations. The thread remains under review, with no merge status implied, but the architectural direction is now clear: Pablo Sabater will need to refactor the client-side parsing logic in `fetch-object-info.c` to avoid `object_info` and map server responses directly to `expand_data`.
