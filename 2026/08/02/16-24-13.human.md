This is a brief but substantive architectural follow-up in the GSoC series adding `%(objecttype)` support to `git cat-file --batch-command` for remote-object-info queries. Junio C Hamano responds to Pablo Sabater’s proposed `struct object_info_results` with a simpler alternative: an array of lightweight structs, each holding an OID, type, and size, rather than separate arrays for each field. Junio suggests two patterns: either a dynamically resized array (with `result_nr` and `result_alloc`) if the number of objects is unknown upfront, or a fixed-size array if the caller knows the count in advance. He also clarifies that boolean flags like `wants_type` may not be needed if the caller consistently requests the same metadata for all objects—`type==OBJ_NONE` can signal missing data instead.

The key insight is that the new structure should mirror the batch nature of the query: one entry per object, with all requested metadata stored contiguously. Junio’s example shows how the existing `struct object_info` can still be used as a temporary interface to `sha1_object_info_extended()`, pointing its `type_p` and `size_p` fields at the appropriate slots in the result array. This avoids the conceptual mismatch of reusing `object_info` for batch storage while preserving its role as a query interface. The proposal is a direct refinement of Pablo’s plan and aligns with Jeff King’s earlier feedback to bypass `object_info` for batch queries. No merge status is implied, but the architectural direction is now clearer.
