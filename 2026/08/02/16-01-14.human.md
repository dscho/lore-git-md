This is the maintainer’s final review of the **v5 `--reset-when-found` feature series** for `git bisect`. The series is nearly ready for `next`, but Junio spots two small internal simplifications that could further clean up the implementation.

The first point is about **how the first bad commit OID is propagated**. The current v5 patch uses a file-scope static variable (`first_bad_oid`) to pass the OID from `bisect_next_all()` to the top-level `cmd_bisect()` function, where the auto-reset logic now lives. Junio suggests this is unnecessary: the OID is already recorded in `refs/bisect/bad`, and the existing mechanism that reads this ref could be reused instead of introducing a new static variable. This would shrink the patch series slightly without changing behavior.

The second point concerns **redundant state tracking**. The code currently maintains two variables: `reset_when_found` (the enum value, `original` or `found`) and `reset_when_found_arg_seen` (a boolean flag indicating whether the option was provided). Junio proposes initializing `reset_when_found` to a sentinel value (e.g., `RESET_WHEN_FOUND_UNSET`) that no command-line argument or state file could ever set. This would eliminate the need for the separate boolean flag, simplifying the state machine.

Neither suggestion affects the user-facing behavior or CLI. Both are internal cleanups that would make the code slightly more concise. The series remains well-motivated, thoroughly tested, and uncontroversial; these are just final polish before integration.
