This is the **v5 feature patch series** for `git bisect`, adding the `--reset-when-found[=<where>]` option. The series is now down to two patches and implements Junio’s proposed refactoring to simplify the internal state machine.

The core feature remains unchanged: after `git bisect` identifies the first bad commit, the working tree is automatically reset to either the pre-bisect commit (`original`, the default) or the first bad commit itself (`found`). The deferred reset behavior for `git bisect run` is preserved, ensuring captured output is printed before cleanup. The option still cannot be used with `--no-checkout`.

The key change in v5 is the internal refactoring. The auto-reset logic is now centralized in the top-level `cmd_bisect()` function, eliminating the `defer_reset` plumbing and decoupling `bisect_clean_state()` from `bisect_reset()`. The first bad commit OID is propagated from `bisect_next_all()` via a file-scope static variable, and the reset is performed after the subcommand returns. This design addresses Junio’s concern about maintainability and reduces the complexity of the state machine.

The preparatory patch (1/2) now uses `bool` for the `quiet` parameter in `bisect_reset()` and separates checkout from state cleanup, returning early if the checkout fails. The core feature patch (2/2) introduces the static `first_bad_oid` variable, updates `bisect_next_all()` to populate it, and moves the auto-reset logic to `cmd_bisect()`. The `read_reset_when_found()` helper reads the persisted mode from the `BISECT_RESET_WHEN_FOUND` state file, and `bisect_reset_when_found()` performs the reset and state cleanup.

Test coverage remains thorough, validating both reset targets, state cleanup, and edge cases. The series is uncontroversial and ready for integration into `next`. All substantive feedback has been addressed, and the refactoring improves the code’s clarity without changing the user-facing behavior.
