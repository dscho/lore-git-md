This is a follow-up in the ongoing discussion about how to handle object metadata queries in the GSoC series extending `git cat-file --batch-command` to support `%(objecttype)` for remote-object-info. Junio C Hamano responds to Jeff King’s earlier architectural feedback, agreeing that the current use of `struct object_info` for batch queries is conceptually awkward.

Junio clarifies the original design intent of `struct object_info`: it was meant as a container for *extended parameters* to `sha1_object_info_extended()`, not as a structure for storing results. The pointers in the struct (`size_p`, `type_p`, etc.) were intended to point to caller-provided variables where the function would write its results, not to heap-allocated memory. He illustrates two correct usage patterns—either reusing a single `object_info` struct across multiple calls (with pointers updated to point to different variables each time) or using an array of result structs (with `object_info` pointing to the appropriate slot in each iteration). The current series’ approach—allocating an array of `object_info` structs, each with its own heap-allocated pointers—deviates from this design and feels unnatural.

The discussion remains advisory and does not block the series, but it reinforces Peff’s earlier recommendation to bypass `object_info` entirely for the remote-object-info path. The thread is still under review, with no merge status implied. Pablo Sabater will likely need to refactor the client-side parsing logic in `fetch-object-info.c` to use a lightweight query structure and map server responses directly to `expand_data`, avoiding the current inefficiency and conceptual mismatch.
