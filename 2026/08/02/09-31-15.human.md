This is the **v5 feature patch** (2/2) for `git bisect`, adding the `--reset-when-found[=<where>]` option. The patch is now technically complete and ready for integration into `next`.

The core change implements the auto-reset logic in the top-level `cmd_bisect()` function, as proposed by Junio C Hamano. After `bisect_next_all()` identifies the first bad commit, `cmd_bisect()` reads the `BISECT_RESET_WHEN_FOUND` state file to determine whether to reset to the original pre-bisect commit (`original`, the default) or leave the working tree on the first bad commit (`found`). The reset is performed quietly, and the bisection state is cleaned up immediately afterward. For `git bisect run`, the reset is deferred until after the captured output is printed and the `BISECT_RUN` file is closed, ensuring compatibility with platforms that cannot unlink open files.

The patch rejects `--reset-when-found` when used with `--no-checkout`, since that mode prevents checking out either target. The option is wired into both `git bisect start` and `git bisect run`, and the selected target is persisted in the `BISECT_RESET_WHEN_FOUND` state file. The internal plumbing is now centralized in `cmd_bisect()`, eliminating the `defer_reset` parameter and decoupling `bisect_clean_state()` from `bisect_reset()`.

Test coverage is thorough, validating both reset targets, state cleanup, and edge cases (invalid targets, `--no-checkout` conflicts, interrupted bisects). The patch is well-crafted, with a clear commit message and no loose ends. It addresses all prior feedback, including Junio’s refactoring proposal and Johannes Sixt’s surface-level suggestions. The series is uncontroversial and appears ready for integration.
