This is a **substantive technical follow-up** in the ongoing packfile performance regression thread. Jeff King (Peff) pushes back on Patrick Steinhardt’s suggestion to refactor the existing packfile hashmap by moving it from `packfile_store` into `packfile_list`. Peff argues that the hashmap’s current placement is deliberate: it prevents redundant work in `add_packed_git()`—such as memory allocation and filesystem `stat()` calls—*before* the packfile is even added to the list. Moving the hashmap into `packfile_list` would require callers to perform an existence check *prior* to calling `packfile_list_append()`, complicating the API without a clear benefit, since `packfile_list_append()` currently has only one caller (`packfile_store_add_pack()`).

The exchange clarifies a key design constraint: the hashmap’s role extends beyond duplicate detection in the list—it also avoids expensive setup work for packfiles that are already known. This makes Patrick’s proposed refactoring less straightforward than it initially appeared. Peff’s comment suggests that any generalized solution would need to demonstrate broader utility (e.g., multiple callers of `packfile_list_append()`) to justify the added complexity. For now, the discussion reinforces the status quo: Johannes Schindelin’s fast-path patch (v2) remains the leading fix for the regression, while the hashmap refactoring is deferred pending further evidence of need. The thread’s unresolved questions—Junio’s maintainability concerns and the unexplained persistence of the O(N) scan—remain untouched by this exchange.
