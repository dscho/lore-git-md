This thread is about a **performance bug in Git's bash completion** that makes it unusably slow in large repositories. Matthew Hughes reports that completing paths for commands like `git add` can take 1–2 seconds in a repository with ~368,000 tracked files across ~58,000 directories. The issue stems from the completion script running `git ls-files --others --modified --directory` with a wildcard pattern (e.g., `di*`), which forces Git to scan every directory in the repository, generating hundreds of thousands of system calls.

Hughes provides a **reproducible test case** (a repository with 25,000 directories, each containing 12 files) and a **workaround**: an environment variable `GIT_COMPLETION_NO_COMPLETE_INDEX` that disables index-based completion entirely, falling back to default bash file completion. The patch is small (5 lines) and targets `contrib/completion/git-completion.bash`. While the workaround is pragmatic, it sacrifices completeness for speed, which may not be ideal for all users.

The report is thorough, including exact command invocations, system call counts from `strace`, and a clear explanation of the code path. So far, there’s been no discussion of prior art or deeper solutions (e.g., optimizing `git ls-files` for wildcard patterns, caching directory listings, or making the completion script smarter). The issue is credible and well-motivated, so it’s likely to spark debate about how to balance performance and functionality in Git’s completion system. No responses or reviews have been posted yet.
