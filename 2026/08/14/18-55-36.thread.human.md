This thread is about a performance regression in Git’s bash completion script, which becomes unusably slow (1–2 second hangs) when completing paths in large repositories with hundreds of thousands of tracked files. The issue was reported by Matthew Hughes, who identified that the completion logic invokes `git ls-files` with wildcard patterns, triggering excessive system calls (`getdents64`, `openat`, `fstat`). Hughes provided a minimal reproduction case (25,000 directories × 12 files) and a workaround patch that disables index-based completion via the environment variable `GIT_COMPLETION_NO_COMPLETE_INDEX`, trading accuracy for speed.

D. Ben Knoble has suggested enabling Git’s `feature.manyFiles` configuration as a potential mitigation. This setting activates optimizations like the fsmonitor daemon, which maintains an inotify-based cache of file changes, potentially reducing the latency of the filesystem scans caused by the completion script. While this doesn’t fix the root cause—the wildcard-driven `git ls-files` invocations—it could improve performance in practice for users with large repositories. The suggestion is actionable and leverages existing Git infrastructure, though its effectiveness hasn’t been benchmarked yet.

The thread is still in the early stages, with no patches or deeper fixes proposed beyond the workaround. Open questions remain: whether the workaround should become the default, whether `git ls-files` can be optimized to avoid full directory scans with wildcards, and whether caching or smarter heuristics could limit filesystem scans. There’s also potential overlap with other large-repository optimizations like sparse-index or partial-clone, but no related efforts have been mentioned yet. So far, only Hughes and Knoble have weighed in, with no maintainer or broader community feedback.
