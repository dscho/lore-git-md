This thread is about a performance regression in Git’s bash completion script, where completing paths for commands like `git add` becomes painfully slow (1–2 second hangs) in repositories with hundreds of thousands of tracked files. The issue was reported by Matthew Hughes, who provided a minimal reproduction case and a workaround patch that disables index-based completion via the `GIT_COMPLETION_NO_COMPLETE_INDEX` environment variable, trading accuracy for speed.

The root cause is that the completion script invokes `git ls-files --others --modified --directory` with wildcard patterns, forcing Git to scan every directory in the repository and generate hundreds of thousands of system calls. D. Ben Knoble initially suggested enabling `feature.manyFiles` (which activates fsmonitor) as a potential mitigation, but Matthew later clarified that this doesn’t help: his test repository already uses `git-scalar`, which disables `feature.manyFiles`, and even in a fresh repository, the setting had no measurable impact on completion performance. He also questioned whether `git ls-files` is even aware of fsmonitor or the untracked cache, suggesting the optimizations might not apply to completion-related filesystem scans.

The discussion has narrowed to whether the workaround (disabling index-based completion) is acceptable as a default or if a deeper fix is needed, such as optimizing `git ls-files` to avoid full directory scans or making the completion script smarter about large repositories. No patches or alternative solutions have been proposed yet, and the thread remains focused on diagnosing the problem and evaluating existing mitigations.
