Matthew Hughes reported a performance regression in Git’s bash completion script, where completing paths for commands like `git add` becomes painfully slow (1–2 second hangs) in repositories with hundreds of thousands of files. The issue stems from the script’s use of `git ls-files --others --modified --directory` with wildcard patterns, forcing Git to scan every directory and generate excessive system calls. Hughes initially proposed a blunt workaround—disabling index-based completion entirely via the `GIT_COMPLETION_NO_COMPLETE_INDEX` environment variable—but has now refined it.

His follow-up offers a more targeted fix: a shell function override that disables index-based completion *only* when the command line includes "slow" options like `--others` or `--modified`, preserving it for simpler cases. This balances speed and accuracy better than the original workaround, though it’s still a local hack rather than a true fix. The core problem—whether `git ls-files` can avoid full directory scans for wildcards—remains unresolved, and suggestions like enabling `feature.manyFiles` (fsmonitor) have proven ineffective for this specific issue. D. Ben Knoble previously engaged with the problem, but no deeper solutions have emerged yet. The thread is still open, with the refined workaround serving as a pragmatic stopgap while the community decides whether to pursue optimizations in the completion script or Git’s wildcard handling.
