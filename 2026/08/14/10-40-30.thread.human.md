This thread is an RFC by Peter Morris proposing that `git worktree add` use filesystem-level copy-on-write (CoW) or block cloning to avoid physically duplicating files until they are modified, reducing storage overhead and speeding up worktree creation—especially useful for large repositories or scenarios like concurrent AI coding agents. The discussion has stalled due to two major blockers: (1) Git’s checkout machinery lacks visibility into sibling worktrees, requiring a complex refactoring of `checkout_entry()`, and (2) a platform-specific correctness issue on Windows (ReFS), where block cloning can corrupt data if writes aren’t flushed to disk.

Peter’s latest email clarifies that the Windows `CopyFile` API—already used in `git clone --block-clone`—mitigates the ReFS corruption risk by locking the source file during copying, preventing concurrent writes. He argues this makes the optimization safe for Windows and Linux (which uses `FICLONE`), but not macOS, which lacks equivalent protections. However, this doesn’t fully resolve brian m. carlson’s objection, which stems from an underlying ReFS bug (unflushed writes causing corruption) that `CopyFile`’s locking may not address. The broader architectural challenges (checkout refactoring, TOCTOU races) remain unaddressed, and no one has stepped up to implement the changes. The thread is effectively paused, with the proposal’s future hinging on whether the benefits justify the effort and whether the ReFS issue can be resolved. Key participants include Junio (who sees the idea as feasible but high-effort), brian m. carlson (who opposes ReFS support until the bug is fixed), and Peter (who remains optimistic but unable to drive the work forward).
