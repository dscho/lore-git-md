The thread is an RFC proposing filesystem-level copy-on-write (CoW) or block cloning optimizations for `git worktree add` to reduce storage overhead and improve performance when creating multiple worktrees. Peter Morris kicked off the discussion, aiming to leverage CoW features like ReFS on Windows, Btrfs on Linux, and APFS on macOS to avoid duplicating data until files are modified. The idea is to intercept Git’s checkout machinery to perform CoW based on a mapping of blob objects to cleanly checked-out files across worktrees, building on prior work like `git clone --block-clone`.

Junio C Hamano provided substantive feedback, outlining the architectural challenge: Git’s checkout machinery (`checkout_entry()`) operates in isolation and lacks visibility into sibling worktrees, making cross-worktree CoW complex but feasible. He flagged potential issues like TOCTOU races and side effects on other commands but didn’t reject the proposal outright, calling it high-effort with broad implications. The discussion seemed to be moving toward a design phase until brian m. carlson raised a critical correctness issue: ReFS’s block cloning is unreliable, producing corrupt copies if data hasn’t been flushed to disk. This was demonstrated in a recent Git LFS bug and directly undermines the Windows support Peter Morris had proposed. Carlson’s position is firm—ReFS support should be excluded until the issue is fixed in Windows.

The thread is now at a crossroads. The architectural questions Junio raised remain open, but the ReFS bug introduces a concrete, platform-specific blocker that could derail the optimization entirely unless mitigated. No implementation exists yet, and the discussion has shifted from "how to design this" to "is this even safe to pursue on Windows?" The niche use case (e.g., AI coding agents) and the effort required may make this a non-starter unless the ReFS issue is resolved or the scope is narrowed to exclude Windows. For now, the proposal is stalled on this correctness concern.
