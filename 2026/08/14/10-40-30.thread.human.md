This thread is an RFC by Peter Morris proposing filesystem-level copy-on-write (CoW) or block cloning optimizations for `git worktree add` to reduce storage overhead and improve performance when creating multiple worktrees. The idea targets scenarios like concurrent AI coding agents, where physically copying all files to each new worktree is inefficient. The optimization would leverage existing filesystem features (e.g., ReFS on Windows, Btrfs on Linux, APFS on macOS) to defer duplication until files are modified, saving disk space and speeding up worktree creation for large repositories.

The discussion remains conceptual, with no implementation or patch yet. Peter Morris recently clarified that Windows (ReFS) support could be achieved "for free" using Git’s existing `CopyFile` API integration (from the 2024 `git clone --block-clone` series), removing a potential portability obstacle. This builds on prior art showing Git can abstract filesystem-specific cloning, but key questions remain unanswered: whether Git’s architecture can support this for `worktree add`, how it would interact with existing worktree features (e.g., `lock`, `prune`), and whether the complexity is justified for the niche use case. Edge cases like hardlinks, symlinks, and cross-platform consistency also need resolution. So far, the only feedback has been a low-weight clarification about Windows support, leaving the broader technical and roadmap alignment questions open.
