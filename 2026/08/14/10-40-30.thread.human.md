This thread explores whether Git could optimize `git worktree add` by using filesystem-level copy-on-write (CoW) or block cloning to avoid physically duplicating files until they are modified. The goal is to reduce storage overhead and speed up worktree creation, particularly for large repositories or scenarios like concurrent AI coding agents. The proposal is still conceptual, with no implementation yet.

The discussion has advanced slightly with confirmation that Windows (ReFS) support is technically viable via the `CopyFile` API, which Git already uses for `git clone --block-clone`. However, Junio C Hamano’s recent review highlights a significant architectural hurdle: the checkout machinery lacks visibility into what files other worktrees have already checked out. The `checkout_entry()` helper, which materializes files from the object database, operates in isolation and would need to be refactored to track cleanly checked-out files across all worktrees. This would introduce complexity, including time-of-check-to-time-of-use (TOCTOU) races and potential side effects for other commands like `git checkout` or `git reset`.

Junio’s feedback suggests the proposal is feasible but would require careful design and justification. The benefits—reduced storage use and faster worktree creation—must be weighed against the risks of added complexity and edge cases, particularly for niche use cases. No fundamental objections have been raised, but the discussion is still in the early stages, with key questions about alignment with Git’s roadmap and handling of cross-platform consistency unresolved.
