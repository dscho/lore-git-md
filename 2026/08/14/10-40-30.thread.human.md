This thread is an RFC by Peter Morris proposing that `git worktree add` use filesystem-level copy-on-write (CoW) or block cloning to avoid physically duplicating files until they are modified. The goal is to reduce storage overhead and improve performance for scenarios like concurrent AI coding agents, where multiple worktrees for the same repository are common. The proposal is conceptual, with no implementation or patch provided, and seeks feedback on whether Git’s architecture can support a platform-agnostic abstraction for this optimization, building on the existing `git clone --block-clone` infrastructure introduced in 2024.

So far, the discussion has been light. The only follow-up is a minor correction from Kristoffer Haugsbakk, a documentation contributor, who noted that Peter’s observation about `git clone --block-clone` being limited to Linux and macOS overlooked Windows support: ReFS (a Windows filesystem) also supports block cloning, and the Windows `CopyFile` API can leverage it automatically when source and destination are on the same ReFS volume. This means the proposed optimization could work "for free" on Windows Dev Drives if Git used `CopyFile` instead of manual copying. Haugsbakk’s reply is a narrow clarification and does not engage with the broader questions about Git’s architecture, edge cases, or roadmap alignment.

The thread remains in the conceptual phase, with key open questions still unaddressed: whether Git’s architecture can support a platform-agnostic abstraction for this feature, how it would interact with existing worktree features (e.g., `git worktree lock`), and whether the complexity is justified by the benefits. The Windows angle adds a potential implementation detail but does not change the thread’s direction. No substantive technical feedback has been provided yet, and the discussion has not progressed beyond the initial RFC and Haugsbakk’s correction.
