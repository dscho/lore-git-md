This is the third patch in D. Ben Knoble’s three-part series converting Git’s build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`). The series as a whole is under active review, with a second version imminent. This specific email is a reply in the ongoing discussion about where to cache the `core.useNanosec` value to avoid the ~41× performance regression Junio C Hamano identified in the first iteration.

The author reports two new pieces of evidence: a CI run that confirms the test suite passes when using `repo_config_values()` (the modern config-driven settings mechanism), and a partial control-flow analysis showing that 214 call paths leading to `repo_config_values()` all terminate in `the_repository`—though some intermediate nodes are exposed via public `libgit.a` interfaces. This means the `the_repository`-only limitation of `repo_config_values()` is already part of Git’s public API surface, and this patch would not introduce a new constraint. The author expresses concern that requiring the patch to be "clean" with respect to `the_repository` could block it indefinitely unless the project accepts a stopgap solution like caching in `repo_settings` or a global variable.

Patrick Steinhardt responds pragmatically, reiterating that while `repo_config_values()` is the modern target for config-driven settings, its current limitation to `the_repository` is a blocker for further expansion until the project resolves how to support other repositories (e.g., submodules). He does not oppose landing the series with `repo_config_values()` if the CI and analysis suggest it is safe, but he also offers a global variable as a fallback if the project prefers to avoid expanding the `the_repository`-only surface area. The tone is conciliatory, and the decision now hinges on whether the project is willing to accept the current limitation of `repo_config_values()` or prefers a temporary measure until the broader `the_repository` issue is resolved.

The patch itself is well-motivated: it addresses a real problem ("racy Git" issues on filesystems that support nanosecond precision) and the performance regression has a confirmed fix. The architectural question about cache location is the only remaining open issue, and the new evidence from the CI run and control-flow analysis gives the project concrete data to weigh the trade-offs. If the series lands as-is, it will be a small but meaningful improvement for users who need nanosecond precision without recompiling Git.
