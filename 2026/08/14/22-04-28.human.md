This is a review comment from Junio C Hamano on a GSoC microproject patch that aims to warn users about valueless `submodule.active` configuration entries. The patch, now in its second version, addresses a NEEDSWORK comment in `submodule.c` by replacing `repo_config_get_string_multi()` with `repo_config_get_value_multi()` and emitting a warning via `config_error_nonbool()` when a valueless key is encountered.

Junio’s feedback focuses on two key points. First, he questions whether the current behavior—emitting a warning but continuing execution—is correct. He argues that since the configuration is broken, the command should fail outright (exit with a non-zero status) rather than just warning the user. This would align with Git’s general approach to invalid configuration, where malformed entries typically cause commands to abort rather than proceed with a warning. Second, he suggests updating the test case to use `test_must_fail` to verify that the command fails, rather than just checking for the warning message.

The review also includes a minor style nit about the commit message (preferring "valueless true" over "valueless keys") and notes that the test portion of the patch is still whitespace-damaged, though the C code itself is clean. This iteration of the patch is now technically sound and aligns with Git’s error-handling patterns, but Junio’s feedback raises a fundamental question about whether the patch’s current approach is the right one. The author will need to decide whether to treat valueless entries as fatal errors or stick with the warning-based approach—and justify that choice in the commit message. The patch is well-scoped and addresses a documented TODO, but this feedback suggests it may need another revision before it’s ready for merging.
