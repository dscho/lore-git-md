This is a **performance bug report** about Git's bash completion being extremely slow in large repositories, specifically when completing paths for commands like `git add` that invoke `git ls-files` to scan the filesystem.

The author, Matthew Hughes, describes a real-world scenario where a repository contains ~368,000 tracked files across ~58,000 directories. In this environment, bash completion for `git add ./<tab>` hangs for 1–2 seconds. The root cause is that the completion script runs `git ls-files --others --modified --directory` with a wildcard pattern (e.g., `di*`), which forces Git to scan every directory in the repository, generating hundreds of thousands of system calls (`getdents64`, `openat`, `fstat`).

Hughes provides a minimal reproduction: create a repository with 25,000 directories, each containing 12 files, then attempt completion. He also proposes a workaround — an environment variable `GIT_COMPLETION_NO_COMPLETE_INDEX` that skips index-based completion entirely, falling back to default bash file completion. The patch is small (5 lines) and targeted at `contrib/completion/git-completion.bash`.

The report is thorough: it includes exact command invocations, system call counts from `strace`, and a clear explanation of the code path (`_git_add` → `__git_complete_index_file` → `__git_index_files`). There is no existing discussion of prior art or related efforts, but the problem is clearly motivated and reproducible. The proposed workaround is pragmatic but not a true fix — it trades completeness for speed, which may not be acceptable for all users.

This is likely to generate discussion about deeper solutions: optimizing `git ls-files` for wildcard patterns, caching directory listings, or making the completion script smarter about when to scan the filesystem. The report itself is well-structured and credible; the slowdown is real and measurable.
