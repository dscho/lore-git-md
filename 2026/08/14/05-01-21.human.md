This is a **refactoring proposal** that advances the long-running debate over Git’s source tree reorganization. Michael Montalbo, a newer contributor, responds to Junio C Hamano’s skepticism about Patrick Steinhardt’s `lib/` directory RFC by offering a **data-driven alternative** that identifies cohesive subsystems using Git’s own history and call graphs. The email presents a Python script that analyzes commit message prefixes ("area labels") and function call relationships to group ~160 of Git’s 231 `libgit.a` source files into 14 directories (e.g., `transport/`, `revision/`, `index/`), leaving 68 files ungrouped. The approach aims to avoid the arbitrariness of a monolithic `lib/` directory while still enabling incremental progress—addressing Junio’s core critique that the original RFC lacked clear semantic boundaries.

The script’s methodology is pragmatic: it weights commit labels by focus (smaller commits count more), maps them to directories via a 14-line "charter" table, and cross-checks groupings against call graphs generated by `cscope`. The results align surprisingly well with existing carved-out directories like `refs/` and `odb/`, while also surfacing new candidates like `transport/` (cohesion score 6.9) and `index/` (6.8). Boundary cases—where call graphs span multiple directories—are explicitly flagged for review (e.g., `shallow.c` grouped with `transport/` despite its `revision:` commit label). This transparency contrasts with the original RFC’s mechanical move, offering a principled way to debate specific groupings rather than the entire reorganization.

Montalbo’s proposal reframes the discussion around **how** to reorganize, not **whether**, by providing a repeatable, objective signal for subsystem cohesion. The email sidesteps the original RFC’s "newcomer discoverability" framing, instead appealing to **project consistency**: if the script’s methodology would have flagged `odb/` before it was carved out, why not apply it systematically? This argument could resonate with Junio’s preference for incremental, motivated changes, though the proposal’s novelty (and reliance on a script) may limit immediate traction. The 68 ungrouped files—including core utilities like `strbuf.c` and `hashmap.c`—highlight the approach’s limitations, but also suggest a path forward: start with the highest-cohesion groups, then refine.

The email does not engage with the **disruption tradeoffs** (e.g., `git log --follow`, rebasing) that dominated earlier threads, focusing instead on structural flaws. This narrow scope may help isolate the debate, but risks overlooking practical concerns raised by SZEDER Gábor and others. The call graph analysis is a strength, but its reliance on `cscope` (which excludes macros and comments) could miss important relationships. Still, the proposal’s hybrid approach—balancing Junio’s incrementalism with Patrick’s "start somewhere" pragmatism—offers a plausible middle ground if the community accepts header-sharing and call graphs as proxies for conceptual cohesion.

For a busy reader, this is a **substantive contribution** to a deadlocked debate. The script’s output is compelling enough to warrant closer scrutiny, but the proposal’s success hinges on whether the community views its methodology as a valid foundation for reorganization. If accepted, it could break the impasse by providing a roadmap for incremental, data-driven moves—without the disruption of a sweeping `lib/` rename. If rejected, the thread may revert to stalemate, with Junio’s subsystem-by-subsystem alternative remaining the default. Either way, Montalbo’s work elevates the discussion beyond subjective preferences, offering a concrete tool for evaluating structural changes.
