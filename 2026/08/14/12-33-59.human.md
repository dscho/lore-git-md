This is the second iteration of a three-patch series that converts Git’s build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`). The goal is to let users enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The series is now cooking under the topic name `dk/use-nsec-runtime`.

Version 2 addresses the performance regression Junio identified in v1: instead of calling `repo_config_get_bool()` on every `is_racy_stat()` invocation (which caused a ~41× slowdown in `git diff` benchmarks), the value is now cached in the repository’s `repo_config_values` struct. A CI run confirms the test suite still passes, and the author reports that a partial control-flow analysis of 214 call paths leading to `repo_config_values()` shows every analyzed path currently terminates at `the_repository`, even though some intermediate nodes are exposed via public `libgit.a` interfaces. This means the `the_repository`-only limitation is already exposed and may grow with this change. The author also moved the `Best-viewed-with: --ignore-space-change` hint into the commit message body as a descriptive note, resolving SZEDER Gábor’s surface-level review comment.

The first patch remains a small, uncontroversial Meson build-system fix that aligns the default `man.base.url.for.relative.links` behavior with the Makefile and adds a configurable `man_base_url` option for downstream flexibility. The second patch is still a no-op refactor of `repo_config_values_init` that prepares the struct for the new field. The third patch is the core change, introducing `core.useNanosec` (defaulting to false) and removing the `USE_NSEC` macro from the build system. The on-disk format is unchanged, and the patch preserves existing behavior on platforms lacking nanosecond support by retaining the `NO_NSEC` conditional in `compat/posix.h`.

The architectural question of where to cache `core.useNanosec`—`repo_config_values`, `repo_settings`, or a global variable—has been narrowed by new evidence. Patrick Steinhardt noted that while `repo_config_values` is the modern target for config-driven settings, its current limitation to `the_repository` is a blocker for further expansion until the project resolves how to support other repositories (e.g., submodules). The author’s analysis suggests this limitation is already exposed, and the series could proceed with `repo_config_values` if the project accepts the current constraint. If not, a global variable or `repo_settings` could serve as a temporary measure. The author is ready to send a follow-up if the project prefers a different cache location, but for now, the series is technically sound and addresses the performance regression.

The series touches `Documentation/config/core.adoc`, `environment.c`, `read-cache.c`, and several other files, but the author hasn’t updated the test suite yet, as it’s unclear how to handle the platform-dependent nature of the change. The naming question (`core.useNanosec` vs something more abstract like `core.useExtendedPrecision`) remains open, though it’s a minor point compared to the performance and caching decisions. There’s also a small textual and semantic conflict with `ty/repo-config-cleanups` in `seen`, which removes comments in `struct repo_config_values` that this series adds. If both topics advance, coordination will be needed.

Overall, this is a well-motivated and technically solid series that addresses a real usability issue. The performance fix in v2 resolves the most critical flaw, and the caching decision is now informed by concrete evidence. The series looks ready to cook in `next` unless the project prefers a different cache location.
