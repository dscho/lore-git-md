This is the third patch in a three-patch series that converts Git’s build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`). The goal is to let users enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems that degrade performance in commands like `git diff` in new worktrees.

The patch removes the `USE_NSEC` macro from the build system (Makefile and configure.ac), adds a new `core.useNanosec` config key (defaulting to false), and updates the codebase to check this setting at runtime instead of relying on a compile-time `#ifdef`. It also updates documentation to reflect the change, including `Documentation/technical/racy-git.adoc`, which now lists filesystems known to support nanosecond precision (ext2, ext4, XFS, CEPH, CIFS, NTFS, UFS, FUSE, and FAT).

The performance regression identified in v1—where calling `repo_config_get_bool()` on every `is_racy_stat()` invocation caused a ~41× slowdown in `git diff` benchmarks—is fixed in this version by caching the value in the repository’s `repo_config_values` struct. The commit message notes that the `Best-viewed-with: --ignore-space-change` hint has been moved into the body as requested by SZEDER Gábor.

The patch is well-motivated and addresses a real problem, but the architectural question of where to cache `core.useNanosec` remains open. The current approach uses `repo_config_values`, which is modern but limited to `the_repository` (a limitation already exposed by public `libgit.a` interfaces). Alternatives like `repo_settings` (which supports per-repository variation) or a global variable have been discussed, but the author and Patrick Steinhardt have framed this as a pragmatic choice: land now and revisit the broader `the_repository` issue later, or use a global variable as a temporary measure. The patch is ready to advance, but the cache location decision may still evolve based on feedback.
