This is an RFC proposing a performance and storage optimization for `git worktree`.

The author, Peter Morris, observes that `git worktree add` currently copies all files from the source working tree to the new worktree, which can be wasteful when multiple worktrees are created for the same repository—especially in scenarios like AI coding agents running concurrently. He suggests leveraging filesystem-level copy-on-write (CoW) or block cloning features (e.g., ReFS on Windows Dev Drives) to avoid physically duplicating data until a file is modified. This would reduce SSD wear, save disk space, and speed up worktree creation for large repositories.

The proposal is framed as an optional optimization: default behavior would remain unchanged on filesystems without CoW support or when files differ from the checked-out version. Morris asks whether Git’s architecture could accommodate a platform-agnostic abstraction for such filesystem-specific cloning, and whether this aligns with Git’s future roadmap.

Key technical details include the focus on worktree creation (not runtime behavior), the potential for cross-platform support (e.g., Btrfs on Linux, APFS on macOS), and the explicit non-goal of making Git dependent on any specific filesystem. The RFC does not include a patch or implementation sketch, so the discussion is currently conceptual.

This touches on Git’s platform compatibility and performance subsystems, and could intersect with ongoing work on repository scalability (e.g., sparse-checkout, ODB backends). The idea is likely to appeal to users managing large repositories or high-frequency worktree operations, but may face questions about portability, edge-case correctness (e.g., hardlinks, symlinks), and whether the complexity justifies the benefit.
