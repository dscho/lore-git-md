Thread identity: RFC proposing filesystem-level copy-on-write (CoW) or block cloning optimizations for `git worktree add` to reduce storage overhead and improve performance when creating multiple worktrees for the same repository. Series version: RFC (no patch version). Originating author: Peter Morris. Thread type: RFC / design discussion.

Core problem or goal: Address the inefficiency of `git worktree add` physically copying all files from the source working tree to the new worktree, which is wasteful for scenarios like concurrent AI coding agents. The goal is to leverage filesystem-level CoW or block cloning (e.g., ReFS on Windows, Btrfs on Linux, APFS on macOS) to avoid duplicating data until a file is modified, reducing SSD wear, saving disk space, and speeding up worktree creation for large repositories. The optimization would be optional and default behavior would remain unchanged on unsupported filesystems or when files differ from the checked-out version.

Current status: Conceptual discussion with substantive technical feedback from Junio C Hamano and brian m. carlson. The RFC has advanced by confirming Windows (ReFS) support via `CopyFile` (already used in `git clone --block-clone`), but this is now challenged by a critical correctness issue: ReFS's block cloning implementation is unreliable when data has been written but not flushed to disk, leading to potential corruption. This issue, demonstrated in a recent Git LFS bug, directly undermines the technical viability of the proposed optimization on Windows. The architectural challenge identified by Junio -- the checkout machinery's lack of visibility into sibling worktrees -- remains unresolved, and the proposal is now additionally blocked by a platform-specific correctness concern. No implementation or patch exists yet.

Key technical details:
- Subsystems touched: `git worktree`, checkout machinery (`checkout_entry()`), platform compatibility layer, potentially repository scalability (intersection with sparse-checkout, ODB backends).
- New behavior: Filesystem-level CoW or block cloning during `git worktree add` to defer physical duplication until modification, contingent on a platform-agnostic abstraction that intercepts `checkout_entry()`.
- Old behavior: Always physically copy all files to the new worktree.
- No new CLI options, config keys, or on-disk format changes proposed yet.
- Test coverage: Not discussed; likely to require platform-specific test cases for CoW/block cloning behavior, TOCTOU race conditions, cross-worktree consistency, and now *correctness* of block cloning on supported filesystems (e.g., ReFS).
- Edge cases noted: Hardlinks, symlinks, correctness on filesystems without CoW support, Windows-specific behavior (ReFS, `CopyFile` API), TOCTOU races between mapping source files and performing CoW, side effects on other commands that use `checkout_entry()` (e.g., `git checkout`, `git reset`, `git restore`), and now *data corruption risk on ReFS* due to unflushed writes.
- Related prior work: `git clone --block-clone` (pull.2317, 2024) demonstrates Git’s existing ability to abstract filesystem-specific cloning, including Windows (ReFS) support via `CopyFile`. This precedent is now called into question by the ReFS correctness issue.

Open questions and loose ends:
- Can Git’s checkout machinery be refactored to support cross-worktree visibility without breaking existing assumptions about isolation or performance?
- How would the proposed abstraction handle TOCTOU races, where the source file might be modified between mapping and CoW? Junio suggests verifying the CoW result by hashing the copied file against the index, but this adds complexity.
- What are the performance implications of intercepting `checkout_entry()` for all working tree updates, not just `git worktree add`?
- Does this align with Git’s future roadmap and priorities, particularly given the niche use case (e.g., AI coding agents) and the effort required?
- How would this interact with existing worktree features (e.g., `git worktree lock`, `git worktree prune`)?
- Are there edge cases (e.g., hardlinks, symlinks, partial checkouts) that would break or complicate the optimization?
- Is the complexity justified by the performance and storage benefits, especially for large repositories?
- Would this require changes to Git’s assumptions about working tree isolation or file ownership?
- How would the abstraction handle platform-specific APIs (e.g., `CopyFile` on Windows, `ioctl_ficlone` on Linux) while maintaining cross-platform consistency?
- **New**: Can the ReFS block cloning corruption issue be mitigated, or must Windows support be excluded from the optimization entirely? If excluded, does the remaining use case (Btrfs, APFS) justify the effort?
- **New**: Are there alternative approaches to achieve the same storage and performance benefits without relying on filesystem-specific CoW or block cloning?

Participant positions:
- **Junio C Hamano (maintainer)**: Substantive technical review. Identifies the core challenge as the checkout machinery’s lack of visibility into sibling worktrees and outlines a feasible but complex path forward (intercepting `checkout_entry()`). Flags TOCTOU races and side effects on other commands as significant pain points. Expresses personal disinterest in implementing the change due to its complexity but does not reject the proposal outright. Position: architecturally feasible but high-effort; benefits must justify the cost.
- **Peter Morris (originating author)**: Proposed the RFC and confirmed Windows (ReFS) support via `CopyFile` (already used in `git clone --block-clone`). Position: optimistic about technical viability but has not addressed architectural challenges raised by Junio or the ReFS correctness issue raised by brian m. carlson.
- **brian m. carlson**: Substantive technical objection. Reports that ReFS's block cloning implementation is unreliable when data has been written but not flushed to disk, leading to potential corruption. Cites a recent Git LFS issue as evidence. Position: Git should not add ReFS support until only fixed versions of Windows are publicly available; this is a critical blocker for the proposed optimization on Windows.
- **Kristoffer Haugsbakk (documentation contributor)**: Low-weight follow-up linking to the 2024 `git clone --block-clone` series as prior art and clarifying Windows (ReFS) support via `CopyFile`. Position: neutral; no substantive technical engagement.
