Thread identity: RFC proposing filesystem-level copy-on-write (CoW) or block cloning optimizations for `git worktree add` to reduce storage overhead and improve performance when creating multiple worktrees for the same repository. Series version: RFC (no patch version). Originating author: Peter Morris. Thread type: RFC / design discussion.

Core problem or goal: Address the inefficiency of `git worktree add` physically copying all files from the source working tree to the new worktree, which is wasteful for scenarios like concurrent AI coding agents or large repositories with static assets (e.g., 80GB of images). The goal is to leverage filesystem-level CoW or block cloning (e.g., ReFS on Windows, Btrfs on Linux, APFS on macOS) to avoid duplicating data until a file is modified, reducing SSD wear, saving disk space, and speeding up worktree creation. The optimization would be optional and default behavior would remain unchanged on unsupported filesystems or when files differ from the checked-out version.

Current status: Conceptual discussion stalled. The RFC has received substantive technical feedback from Junio C Hamano and brian m. carlson, identifying two critical blockers: (1) the checkout machinery’s lack of visibility into sibling worktrees, requiring a complex refactoring of `checkout_entry()`, and (2) a platform-specific correctness issue on Windows (ReFS), where block cloning is unreliable when data has been written but not flushed to disk, risking corruption. Peter Morris acknowledges these challenges as beyond his current expertise and expresses hope that another contributor might implement the changes. His latest reply clarifies that the Windows `CopyFile` API’s locking behavior (shared-read, deny-write) prevents the race condition described by Carlson, but this does not address the underlying ReFS bug or the broader architectural challenges. The proposal remains paused pending a new champion or further technical resolution. No implementation or patch exists.

Key technical details:
- Subsystems touched: `git worktree`, checkout machinery (`checkout_entry()`), platform compatibility layer, potentially repository scalability (intersection with sparse-checkout, ODB backends).
- New behavior: Filesystem-level CoW or block cloning during `git worktree add` to defer physical duplication until modification, contingent on a platform-agnostic abstraction that intercepts `checkout_entry()`. Windows support would rely on `CopyFile`’s locking semantics to mitigate TOCTOU races, while Linux (`FICLONE`) and macOS lack equivalent protections.
- Old behavior: Always physically copy all files to the new worktree.
- No new CLI options, config keys, or on-disk format changes proposed.
- Test coverage: Not discussed; likely to require platform-specific test cases for CoW/block cloning behavior, TOCTOU race conditions, cross-worktree consistency, and correctness of block cloning on supported filesystems (e.g., ReFS, Btrfs). The Windows `CopyFile` locking behavior would need explicit validation.
- Edge cases noted: Hardlinks, symlinks, correctness on filesystems without CoW support, Windows-specific behavior (ReFS, `CopyFile` API), TOCTOU races between mapping source files and performing CoW, side effects on other commands that use `checkout_entry()` (e.g., `git checkout`, `git reset`, `git restore`), and *data corruption risk on ReFS* due to unflushed writes. The `CopyFile` API’s locking mitigates concurrent writes but does not resolve the ReFS bug itself.
- Related prior work: `git clone --block-clone` (pull.2317, 2024) demonstrates Git’s existing ability to abstract filesystem-specific cloning, including Windows (ReFS) support via `CopyFile`. This precedent remains undermined by the ReFS correctness issue, though Morris’s reply argues the `CopyFile` locking behavior addresses the race condition.

Open questions and loose ends:
- Can Git’s checkout machinery be refactored to support cross-worktree visibility without breaking existing assumptions about isolation or performance? This remains the primary architectural blocker.
- Does the Windows `CopyFile` API’s locking behavior fully mitigate the ReFS corruption risk described by Carlson, or does the underlying bug (unflushed writes causing corruption) persist? If the latter, is Windows support still viable?
- How would the proposed abstraction handle TOCTOU races on Linux and macOS, where no equivalent locking mechanism exists?
- What are the performance implications of intercepting `checkout_entry()` for all working tree updates, not just `git worktree add`?
- Does this align with Git’s future roadmap and priorities, particularly given the niche use case (e.g., AI coding agents, large media repositories) and the effort required?
- How would this interact with existing worktree features (e.g., `git worktree lock`, `git worktree prune`)?
- Are there edge cases (e.g., hardlinks, symlinks, partial checkouts) that would break or complicate the optimization?
- Is the complexity justified by the performance and storage benefits, especially for large repositories?
- Would this require changes to Git’s assumptions about working tree isolation or file ownership?
- How would the abstraction handle platform-specific APIs (e.g., `CopyFile` on Windows, `ioctl_ficlone` on Linux) while maintaining cross-platform consistency?
- If macOS is excluded due to lack of locking, does the remaining use case (Windows, Linux) justify the effort?

Participant positions:
- **Junio C Hamano (maintainer)**: Substantive technical review. Identifies the core challenge as the checkout machinery’s lack of visibility into sibling worktrees and outlines a feasible but complex path forward (intercepting `checkout_entry()`). Flags TOCTOU races and side effects on other commands as significant pain points. Expresses personal disinterest in implementing the change due to its complexity but does not reject the proposal outright. Position: architecturally feasible but high-effort; benefits must justify the cost.
- **Peter Morris (originating author)**: Proposed the RFC and confirmed Windows (ReFS) support via `CopyFile` (already used in `git clone --block-clone`). Acknowledges the architectural and platform-specific challenges as beyond his current expertise. In his latest reply, argues that `CopyFile`’s locking behavior (shared-read, deny-write) prevents the race condition described by Carlson, but does not address the underlying ReFS bug or broader architectural blockers. Position: optimistic about the concept but unable to address the blockers; effectively cedes further development to the community.
- **brian m. carlson**: Substantive technical objection. Reports that ReFS's block cloning implementation is unreliable when data has been written but not flushed to disk, leading to potential corruption. Cites a recent Git LFS issue as evidence. Position: Git should not add ReFS support until only fixed versions of Windows are publicly available; this is a critical blocker for the proposed optimization on Windows. Has not responded to Morris’s clarification about `CopyFile` locking.
- **Kristoffer Haugsbakk (documentation contributor)**: Low-weight follow-up linking to the 2024 `git clone --block-clone` series as prior art and clarifying Windows (ReFS) support via `CopyFile`. Position: neutral; no substantive technical engagement.
