This is a bug report about performance degradation in Git's bash completion for `git add` (and similar commands) in repositories with a very large number of directories.

Matthew Hughes describes a frustrating slowdown when using tab completion for `git add` in a repository with hundreds of thousands of files and tens of thousands of directories. The delay—one to two seconds per tab press—stems from the completion script calling `git ls-files` to scan the entire working tree for untracked or modified files, which triggers hundreds of thousands of system calls (`getdents64`, `openat`, `fstat`) per completion attempt.

He provides a minimal reproduction: a synthetic repository with 25,000 top-level directories, each containing a handful of files. The slowdown is visible even when completing a partial directory name (e.g., `git add ./di<TAB>`). As a temporary workaround, he suggests an environment variable (`GIT_COMPLETION_NO_COMPLETE_INDEX`) that would skip the index-aware completion and fall back to plain Bash file completion, though he acknowledges this is not a real fix.

The report is clear, includes concrete numbers, and offers both a reproduction recipe and a diagnostic trace via `strace`. It looks like a real, reproducible performance bug that would affect any user in a large monorepo. No prior discussion or existing solution is mentioned, so this appears to be the first time the issue has been raised on the list.
