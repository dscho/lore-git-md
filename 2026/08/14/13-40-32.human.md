This is the final patch in Justin Tobler’s nine-patch v3 series making `git receive-pack` fully backend-agnostic by introducing `odb_transaction_write_pack()`. The series is part of Patrick Steinhardt’s ongoing ODB abstraction effort, which aims to enable alternative object storage backends (e.g., reftable, cloud storage) without hardcoding the traditional "files" backend.

The patch moves packfile ingestion logic from `builtin/receive-pack.c` into the "files" ODB backend, replacing the hardcoded `unpack()` function with the new `odb_transaction_write_pack()` interface. The transaction now manages ".keep" lockfiles explicitly, storing them in a dynamically grown array and removing them during finalization. The patch also removes the last direct dependency on `lockfile.h` in `receive-pack.c` and completes the refactoring of global state into explicit parameters (e.g., `unpack_opts`, `strbuf`-based error reporting, and explicit file descriptor passing).

Patrick Steinhardt’s review identified a substantive design gap: the `get_unpack_limit()` helper assumes a `git receive-pack` context, but the new interface is intended to be generic and reusable for other commands like `git fetch-pack`. The current design does not provide a way to pass context-specific configuration keys (e.g., `fetch.unpackLimit` vs. `receive.unpackLimit`). Justin Tobler’s reply clarifies that transaction flags (e.g., `ODB_TRANSACTION_RECEIVE`, `ODB_TRANSACTION_FETCH`) already exist and can be used to differentiate callers. He plans to update the patch in the next version to use these flags, ensuring the backend resolves the correct configuration keys based on the caller’s context.

The series is technically sound, with all critical design flaws from v2 resolved (lockfile lifecycle, transaction lifecycle, unpack limit resolution, shallow file handling, and error reporting). The remaining loose ends are interface-level refinements rather than implementation bugs. The patch is well-motivated and aligns with Git’s broader pattern of eliminating global state in favor of explicit repository parameters. The upcoming v4 will likely address the unpack limit context issue without disrupting the series’ core goals. The series remains cooking in `seen` and is a key step toward pluggable ODB backends.
