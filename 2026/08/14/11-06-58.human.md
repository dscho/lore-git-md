This is the latest exchange in the `core.useNanosec` series, a feature that replaces the build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`). The goal is to let users enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems.

The series has been under active review, with the main sticking point being where to cache the `core.useNanosec` value to avoid a severe performance regression. The author, D. Ben Knoble, has confirmed through CI testing and partial control-flow analysis that using `repo_config_values()` (the modern config storage) works with the test suite, but notes that some call paths touch public `libgit.a` interfaces, meaning the "must only use `the_repository`" limitation is already exposed and may grow with this change. Knoble expresses concern that requiring full `the_repository`-cleanliness could indefinitely block the series unless the project accepts `repo_settings` (which supports per-repository variation) as a stopgap.

In this email, Patrick Steinhardt responds with a pragmatic stance: he suggests that if the CI results and analysis indicate the change is safe, the project should proceed with `repo_config_values()`, or alternatively use a global variable as a temporary measure. Steinhardt does not want the series held hostage to the broader `repo_config_values()` cleanup effort, which is still unresolved. His tone is collaborative and solution-oriented, leaving the final call to the author while making it clear the project is open to landing the feature without full architectural purity.

The next iteration (v2) is expected within 24 hours, and the decision on cache location will likely be settled in that version. The series remains uncontroversial in its other aspects: the Meson build-system fix and the no-op refactor are already confirmed correct. If the performance fix holds, this looks like a well-motivated and thoroughly tested feature that addresses a real user pain point.
