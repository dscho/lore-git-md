This is the third and final patch in D. Ben Knoble’s v2 series converting Git’s build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`). The patch removes the `#ifdef USE_NSEC` guards and replaces them with a cached boolean value read from the repository’s `repo_config_values` struct, eliminating the ~41× performance regression identified in v1. It updates the Racy Git documentation to reflect the new runtime setting, removes the `USE_NSEC` build knobs from `Makefile` and `configure.ac`, and adds the new `core.useNanosec` key to `Documentation/config/core.adoc`.

The patch touches ten files: `Documentation/config/core.adoc`, `Documentation/technical/racy-git.adoc`, `Makefile`, `configure.ac`, `builtin/update-index.c`, `compat/posix.h`, `environment.c`, `environment.h`, `read-cache.c`, and `statinfo.c`. The core logic change is in `read-cache.c` and `statinfo.c`, where the `#ifdef` blocks are replaced with a runtime check on `repo_config_values(istate->repo)->use_nanosec`. The documentation now lists filesystems known to support nanosecond precision (ext2, ext4, XFS, CEPH, CIFS, NTFS, UFS, FUSE, FAT) and clarifies that the setting defaults to false.

The architectural trade-off—whether to cache the value in `repo_config_values` (modern but limited to `the_repository`), `repo_settings` (supports per-repository variation), or a global variable—remains unresolved, but the author’s partial control-flow analysis shows that all 214 call paths to `repo_config_values()` currently terminate at `the_repository`, meaning the limitation is already exposed. The patch is ready for review, with the performance fix confirmed and the cache location decision still pending. The conflict with `ty/repo-config-cleanups` in `seen` persists, as both series touch `struct repo_config_values`.
