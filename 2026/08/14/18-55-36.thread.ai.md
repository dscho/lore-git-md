Subject: Performance regression in bash completion for large repositories
Series version: N/A (bug report, not a patch series)
Originating author: Matthew Hughes <matthewhughes934@gmail.com>
Thread type: bug report

Core problem or goal
Git’s bash completion script (`contrib/completion/git-completion.bash`) becomes unusably slow (1–2 s hang) when completing paths for commands like `git add` in repositories with hundreds of thousands of tracked files. The root cause is that the completion logic invokes `git ls-files --others --modified --directory` with a wildcard pattern (e.g., `di*`), forcing Git to scan every directory in the repository and generate hundreds of thousands of system calls (`getdents64`, `openat`, `fstat`).

Current status
Reported; no prior discussion or patch versions. The author provides a minimal reproduction (25 000 directories × 12 files) and a 5-line workaround patch that disables index-based completion via the environment variable `GIT_COMPLETION_NO_COMPLETE_INDEX`, falling back to default bash file completion. The workaround is pragmatic but sacrifices completion accuracy for speed. D. Ben Knoble’s suggestion to enable `feature.manyFiles` (fsmonitor) as a mitigation has been tested and found ineffective for this specific use case; the issue remains unresolved.

Key technical details
- Files touched: `contrib/completion/git-completion.bash`
- Completion functions involved: `_git_add` → `__git_complete_index_file` → `__git_index_files`
- System calls observed: `getdents64`, `openat`, `fstat`
- Workaround variable: `GIT_COMPLETION_NO_COMPLETE_INDEX`
- Mitigation suggestion: `feature.manyFiles` (fsmonitor) — now ruled out as ineffective
- Test case: 25 000 directories, 12 files each (~300 000 files total)
- Commands under scrutiny: `git ls-files --exclude-standard --others --directory` (invoked by completion script)
- Optimizations not engaged: fsmonitor, untracked cache (completion script’s use of `git ls-files` bypasses these)

Open questions and loose ends
- Is the workaround (disabling index-based completion) acceptable as a default, or should a deeper fix be pursued?
- Can `git ls-files` be optimized to avoid full directory scans when given wildcard patterns, or is the completion script’s invocation inherently expensive?
- Should the completion script cache directory listings, use smarter heuristics (e.g., limiting depth or breadth of filesystem scans), or integrate with Git’s performance features (fsmonitor, untracked cache)?
- Are there existing efforts (e.g., sparse-index, partial-clone) that could mitigate this issue, or is this a completion-specific problem?
- What is the performance impact of the workaround on smaller repositories, and is the trade-off between speed and accuracy justified?
