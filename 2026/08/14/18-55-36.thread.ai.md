Subject: Performance regression in bash completion for large repositories
Series version: N/A (bug report, not a patch series)
Originating author: Matthew Hughes <matthewhughes934@gmail.com>
Thread type: bug report

Core problem or goal
Git’s bash completion script (`contrib/completion/git-completion.bash`) becomes unusably slow (1–2 s hang) when completing paths for commands like `git add` in repositories with hundreds of thousands of tracked files. The root cause is that the completion logic invokes `git ls-files --others --modified --directory` with a wildcard pattern (e.g., `di*`), forcing Git to scan every directory in the repository and generate hundreds of thousands of system calls (`getdents64`, `openat`, `fstat`).

Current status
Reported; no prior patch versions. The author initially provided a minimal workaround patch (5 lines) that disabled index-based completion via the environment variable `GIT_COMPLETION_NO_COMPLETE_INDEX`, falling back to default bash file completion. This workaround was pragmatic but sacrificed completion accuracy for speed. In the latest email, Hughes refines the approach by overriding the `__git_complete_index_file` function to skip index-based completion *only* when the command line includes "slow" options (`--others`, `--modified`, `--deleted`, `--ignored`, or `--killed`). This preserves completion for simpler cases (e.g., `git add <tab>` without flags) while avoiding the expensive scans. The refined workaround is still a local hack, not a project-wide solution, and does not address the root cause (optimizing `git ls-files` or integrating with Git’s performance features). D. Ben Knoble’s earlier suggestion to enable `feature.manyFiles` (fsmonitor) was tested and ruled out as ineffective for this use case.

Key technical details
- Files touched: `contrib/completion/git-completion.bash` (indirectly via function override)
- Completion functions involved: `_git_add` → `__git_complete_index_file` → `__git_index_files`
- System calls observed: `getdents64`, `openat`, `fstat`
- Workaround mechanism: Shell function override of `__git_complete_index_file` to conditionally skip index-based completion when "slow" options are present
- Mitigation suggestion: `feature.manyFiles` (fsmonitor) — ruled out as ineffective
- Test case: 25 000 directories, 12 files each (~300 000 files total)
- Commands under scrutiny: `git ls-files --exclude-standard --others --directory` (invoked by completion script)
- Optimizations not engaged: fsmonitor, untracked cache (completion script’s use of `git ls-files` bypasses these)

Open questions and loose ends
- Is the refined workaround (selective disabling of index-based completion) acceptable as a default, or should a deeper fix be pursued?
- Can `git ls-files` be optimized to avoid full directory scans when given wildcard patterns, or is the completion script’s invocation inherently expensive?
- Should the completion script cache directory listings, use smarter heuristics (e.g., limiting depth or breadth of filesystem scans), or integrate with Git’s performance features (fsmonitor, untracked cache)?
- Are there existing efforts (e.g., sparse-index, partial-clone) that could mitigate this issue, or is this a completion-specific problem?
- What is the performance impact of the refined workaround on smaller repositories, and is the trade-off between speed and accuracy justified?
- Could the completion script’s use of `git ls-files` be replaced with a more targeted Git command or API (e.g., leveraging the index or untracked cache directly)?
