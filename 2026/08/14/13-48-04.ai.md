This patch is a **feature** that extends `git rev-parse` to compute object names in a different hash algorithm on demand, addressing a long-standing gap in Git's object-format interoperability. The work is motivated by the need to reference objects in repositories using different hash algorithms (e.g., SHA-1 vs. SHA-256) without requiring a full repository conversion.

The core change teaches `repo_oid_to_algop()` to compute the name of an object in another algorithm when the `extensions.compatObjectFormat` mapping is missing. This is done by recursively converting the object's contents (trees, tags, blobs) and hashing the result. The implementation caches computed names in-memory during the process to avoid redundant work, though it does not persist them. Commits and trees containing submodules are explicitly rejected, as converting them would require traversing unbounded history or external repositories.

The patch touches several key files:
- `builtin/rev-parse.c`: Accepts any known algorithm (not just the configured compatibility one) and checks for conversion errors.
- `object-file-convert.c`: Adds the `compute_oid_to_algop()` function and a per-repository cache for computed names. It also improves error messages for submodules.
- `repository.{c,h}`: Adds the `compat_oid_cache` field and cleanup logic.
- `t/t1018-output-object-format.sh`: A new test script covering edge cases (empty trees, submodules, unknown algorithms) and verifying correctness against `fast-export`/`fast-import`.

Performance is reasonable: on the Linux kernel tree (1.6 GiB), computing the SHA-256 name takes 8 seconds, close to the theoretical minimum for reading and hashing the content. The commit message notes that a prior `contrib/` script using `fast-export` was slower due to unnecessary work.

The patch is well-motivated, with clear documentation updates and thorough test coverage. It avoids controversial design choices (e.g., no persistent cache, no commit conversion) and focuses on a narrow, practical use case. The author acknowledges prior art and alternative approaches, suggesting confidence in the solution. This looks like a solid contribution to Git's object-format interoperability story.
