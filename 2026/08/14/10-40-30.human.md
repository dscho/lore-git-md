This is an RFC proposal for a **feature** targeting `git worktree` to reduce disk writes and improve performance when creating multiple worktrees, particularly in AI-driven workflows.

Peter Morris suggests leveraging filesystem-level copy-on-write (CoW) or block cloning—where supported—to avoid physically duplicating file data when creating new worktrees. The idea is to let the filesystem share underlying storage blocks until a file is modified, which could significantly reduce SSD wear, disk space usage, and checkout time for large repositories. The proposal is motivated by the growing use of AI coding agents that create many concurrent worktrees, each potentially duplicating the same files.

The email does not include a patch or implementation details, but it floats a high-level design: an abstraction layer for filesystem cloning, with platform-specific backends (e.g., ReFS on Windows, Btrfs on Linux). The fallback would be the current behavior on unsupported filesystems or when files differ from the source. Peter asks whether this aligns with Git’s roadmap and whether there are technical blockers, particularly around worktree safety or correctness.

This is a well-motivated idea with clear real-world use cases, but it is early-stage and likely to require careful design to avoid introducing subtle bugs in worktree isolation or filesystem edge cases. The proposal is platform-agnostic in spirit, though the immediate benefit would be most visible on Windows (ReFS) and Linux (Btrfs, XFS). If the Git community is receptive, this could evolve into a substantial performance and efficiency win for users managing many worktrees.
