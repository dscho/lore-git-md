Thread identity
Subject: [PATCH] gitk: add user-configurable custom commands to context menus
Series version: standalone patch (now contested as monolithic vs. incremental)
Originating author: Tim Wiederhake
Thread type: feature patch

Core problem or goal
Enable users to define their own workflows in `gitk` by adding user-configurable custom commands to right-click context menus (commit list and diff display). The feature is designed as a **generic extension system** with placeholder substitution (file, line, commit ID, title, author, blame origin, etc.) and shell execution, allowing commands like "edit this line at that point in history" without hardcoding niche functionality. Configuration is exposed via a new "Commands" tab in the preferences dialog.

Current status
Under review; no prior versions on-list. The patch remains self-contained to `gitk` (Tcl/Tk frontend), touching only the `gitk` script. **Blocked on four fronts**:
1. **Design scope**: The author (Tim) and maintainer (Hannes) disagree on whether the feature should be implemented as a **single, complete mechanism** (Tim’s position: substitutions are parameters of a unified system, not independent features) or as an **incremental patch series** (Hannes’ position: start with a minimal use case, e.g., "open an editor at this line in the diff," and defer less essential functionality). Tim acknowledges splitting the patch for review is possible but insists the goal is the full mechanism, not a series of standalone features.
2. **Process**: Hannes has rejected the monolithic implementation and now expects an incremental approach, while Tim argues that splitting the feature would result in a half-usable system that fails to meet the core goal.
3. **AI assistance policy**: Hannes remains uncertain whether Tim’s iterative reworking of Claude-generated code meets the project’s requirement that the author "review and understand every line," and has explicitly asked for community input. Tim has clarified his process (designed the feature in English, used Claude to translate to Tcl, iteratively reworked the code to match his intent) and argues this is a valid use of AI, as the algorithm and design are his. The policy question remains unanswered by the community.
4. **Security**: The critical security concern about unquoted shell command substitution (enabling arbitrary command injection via malicious commit titles/messages) is **confirmed by Hannes** as a blocker. Junio provided a concrete exploit example (`title?'; echo no'`); Tim has acknowledged the flaw and is evaluating two approaches: (a) revert to direct command execution (without `sh -c`) and require users to write wrapper scripts for advanced use cases, or (b) implement proper escaping for all interpolated values while retaining shell features. No concrete fix has been proposed yet.

Key technical details
- Files touched: `gitk` (Tcl script)
- New global variables: command templates for commit-list and diff-display menus
- New procedures: dynamic menu population, preferences-page UI
- Execution: commands run via `sh -c`; exit code 42 displays command output
- Symbols: none in C; Tcl variables and procedures internal to `gitk`
- On-disk format: none; configuration stored in `~/.gitk` (existing file)
- Test coverage: none in this patch
- **Security vulnerability**: Placeholder substitution in shell commands is unquoted, allowing injection of arbitrary shell metacharacters (e.g., `title?'; echo no'` in a commit title would execute both the intended command and the injected payload). The flaw is recognized as a blocker by both Junio and Hannes.

Tim has provided a detailed account of his process, but the maintainer’s request for community input remains unanswered.
3. **Security flaw**: The command substitution mechanism remains unresolved. Tim is evaluating two approaches (direct execution vs. proper escaping) but has not yet proposed a concrete fix.
