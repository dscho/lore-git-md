This is the second patch in Domen Kožar’s four-part series introducing `post-worktree-add`, `post-worktree-remove`, and `post-worktree-move` hooks. It adds the `post-worktree-remove` hook, which fires after a worktree is deleted by `git worktree remove` or pruned after manual deletion. The hook receives the absolute path of the removed worktree and its identifier (the name of its former administrative directory in `.git/worktrees/`), allowing external tools to clean up per-worktree state or deregister the worktree from monitoring systems.

The implementation is straightforward: the hook is called from `builtin/worktree.c` after the worktree’s administrative directory is deleted, and it runs even if the worktree directory itself is already gone. The hook cannot prevent the removal, but its exit status is reflected in the exit status of `git worktree remove`. Test coverage in `t/t2403-worktree-move.sh` verifies that the hook runs in all removal scenarios (normal, missing worktree, and pruning) and does not run when removal is refused (e.g., due to a locked worktree). The documentation in `Documentation/githooks.adoc` clearly explains the hook’s purpose, arguments, and limitations.

This patch is well-motivated and addresses a real gap for tooling that manages ephemeral worktrees. The design is consistent with Git’s existing hook semantics, and the implementation is clean and thoroughly tested. The only open question from the thread—whether the hook should run if `post-checkout` fails—does not apply here, as this hook is purely about removal. The series as a whole is shaping up to be a useful addition for high-velocity workflows, particularly in AI-driven development environments.
