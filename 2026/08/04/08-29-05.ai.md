This is the v2 cover letter for Patrick Steinhardt’s five-patch series making the creation of on-disk object database (ODB) structures pluggable. The series is part of the ongoing ODB abstraction effort and targets the current development cycle (based on the 7th batch, commit `9a0c4701dc`).

The core goal remains unchanged: decouple the creation of backend-specific directories (e.g., `objects/info`, `objects/pack`) from the generic repository setup code. The top-level `objects/` directory is still mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback in the ODB source interface. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic.

Key updates in v2:
- **Added a test case** (provided by Toon Claes) that demonstrates the latent bug fixed in the first patch. The test creates two SHA-256 repositories (one acting as an alternate), configures both with SHA-1 compatibility, and verifies `git rev-parse` resolves an object borrowed from the alternate when using the compatibility hash format. This elevates the first patch’s status to a correctness fix with regression coverage for multi-backend setups.
- **Clarified commit messages**, particularly for the second patch, which now explicitly states the latent correctness issue: the original code unconditionally downcasts the primary ODB to the "files" backend, which would BUG if a different backend type were used with a compatibility hash algorithm.
- **Renamed the "inmemory" backend to "in-memory"** (a surface-level nit from Junio in v1).

The series touches 14 files, introducing new functions (e.g., `odb_source_type_to_name()`, `loose_object_map_load()`), backend-specific directory creation helpers, and the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag. The changes are mechanical but foundational, removing hardcoded assumptions about directory layouts and initialization order. The third patch defers ODB creation until after the ref database is set up, a prerequisite for the planned `objectStorage` extension (which will enable non-filesystem ODB backends).

Open architectural questions from v1 remain unresolved:
1. **Downcast safety**: Junio’s suggestion to add a generic `load object map` method to the `odb_source` interface (to eliminate downcasting entirely) was not addressed. Patrick clarified that the downcast macro will BUG if the source is not a "files" backend, but the broader design question lingers.
2. **Callback naming**: Junio’s preference for a more generic term like `initialize` (instead of `create_on_disk`) was deferred in favor of consistency with the ref subsystem’s `ref_store_create_on_disk()`.
3. **Initialization sequence**: Justin Tobler’s question about the `APPLY_REPOSITORY_FORMAT_SKIP_ODB_CREATION` flag (vs. an explicit `odb_new()` call) was acknowledged as a pragmatic choice but not resolved.

The series is under active review, with substantive feedback from Junio, Justin Tobler, and Toon Claes. The added test case and clarified commit messages strengthen the case for merging, particularly for the first two patches, which now address confirmed correctness issues. The remaining patches are infrastructure work with no immediate user-visible impact but are critical for future ODB backends.
