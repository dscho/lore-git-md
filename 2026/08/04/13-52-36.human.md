This is a **substantive design review** of Michael Montalbo’s RFC for a diff provider interface, focusing on the framework’s motivation, terminology, and technical trade-offs. Phillip Wood, a seasoned reviewer, presses for clarity on what the interface enables beyond caching and how its authority model works.

The review homes in on three core questions. First, **motivation**: Wood asks what the interface unlocks beyond a unified cache, noting that the commit message and cover letter describe mechanics but not the broader vision. The answer lies in the two example providers: the `diff-hunks` store (a non-authoritative cache) and `diff.<driver>.process` (an authoritative external process). The interface is designed to let Git consult alternate hunk sources—whether a cache, an external tool, or future backends—without consumers needing to know their implementation. This abstraction is the key to extending Git’s diff machinery beyond xdiff, enabling features like content-carrying requests (for patch output) or custom diff drivers that integrate with Git’s full feature set (e.g., `--color-moved`, `-W` function context).

Second, **authority**: Wood questions what "authoritative" means and why xdiff isn’t the sole authority. The distinction is about trust: an authoritative provider (like an external process) may supply hunks that differ from xdiff’s output, while a non-authoritative one (like the `diff-hunks` store) must reproduce xdiff exactly. Chain order determines authority: earlier providers override later ones, with xdiff as the terminal fallback. This lets Git prioritize external tools or caches while ensuring a safe fallback.

Third, **technical details**: Wood probes the `diff-hunks` store’s design, asking whether its direct storage of `xdl_opts` locks in the in-memory representation and whether there are plans for garbage collection. The store keys entries by `(old_blob, new_blob, xdl_opts)`, so changes to `xdl_opts` would indeed break compatibility. There’s no garbage collection yet; the store is designed to be derivable at any time, with recovery via `git diff-hunks clear` and re-warming. Wood also clarifies "coordinates" as the hunk offsets and lengths in the diff header, a term not used in the existing codebase.

The review is **constructive but skeptical**, seeking to ensure the framework’s complexity is justified by tangible benefits. Wood’s questions highlight areas where the documentation and commit messages could better articulate the long-term vision—particularly how the interface enables future extensions like content-carrying requests or integration with Git’s formatting features. The discussion is still in the design phase; no code changes are suggested yet, but the feedback underscores the need for clearer motivation and terminology in the next iteration.
