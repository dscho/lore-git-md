Patrick Steinhardt’s eight-patch series to unify Git’s object database (ODB) streaming API is now complete in its second version and under final review. The goal is to eliminate redundancy between the read and write stream interfaces (`odb_read_stream` and `odb_write_stream`) by merging them into a single `odb_stream` structure, a purely structural change that paves the way for pluggable ODB backends. All feedback from the first iteration has been addressed, including a critical bug in the in-memory backend where object types weren’t propagated correctly, risking silent corruption.

The series builds incrementally: earlier patches align the two stream designs by embedding the expected size in the write stream (Patch 1) and removing a now-redundant `is_finished` flag (Patch 2), while Patch 3 fixes the in-memory backend bug and extends write streams to support arbitrary object types. The centerpiece, Patch 5, merges the two structures into one and introduces wrapper types for the two sites that need special handling (`builtin/unpack-objects.c` and `odb/streaming.c`). Later patches rename supporting structures (`fd_stream`, `zlib_stream`) and standardize function names (`odb_stream_from_object()`, `odb_stream_from_fd()`), with Patch 8 documenting file descriptor ownership to prevent leaks.

Justin Tobler and Junio C Hamano provided the most substantive feedback on the first version. Junio caught the in-memory backend bug, which Patrick fixed by propagating the stream’s object type to `hash_object_file()`. Justin’s detailed reviews confirmed the loop restructuring in `feed_input_zstream()` and the wrapper allocation logic, though he initially questioned the naming of the wrapper structures; those names are now cleaned up in Patches 6 and 7. Karthik Nayak’s recent reviews of Patches 1, 2, and 5 are positive but surface-level, focusing on structural intent rather than edge cases. The series touches 38 files and introduces no behavior changes or new CLI options, so the remaining open questions center on whether the wrapper allocation logic is leak-free and whether the unified API’s indirection might regress performance in stream-heavy code paths like `pack-objects`. With all feedback incorporated, the series is ready for Junio to queue in `next`.
