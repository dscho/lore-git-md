This is the second patch in Patrick Steinhardt’s five-part series making on-disk ODB structures pluggable, part of the ongoing ODB abstraction effort. It addresses a latent correctness issue in how loose object maps are loaded when a repository uses a compatibility hash algorithm (e.g., SHA-256 with SHA-1 compatibility).

The patch refactors the loading of loose object maps to avoid two problems in the current code: (1) an unconditional downcast of the primary ODB to the "files" backend, which would BUG if a different backend type were used with a compatibility hash algorithm, and (2) a tangled initialization sequence that requires the ODB to be set up before configuring the repository’s hash algorithm. The fix moves the map-loading logic into the "loose" backend itself, making it an internal implementation detail rather than a cross-cutting concern. The `loose_object_map_load()` function is now called during backend initialization (`odb_source_loose_new()`), and the global `repo_read_loose_object_map()` function is simplified to iterate over ODB sources and delegate to the backend-specific loader.

The change is mechanical but important: it eliminates a BUG waiting to happen while also cleaning up the initialization sequence. The patch touches five files (`loose.c`, `loose.h`, `odb/source-loose.c`, `repository.c`, and `setup.c`), introducing a new public function (`loose_object_map_load()`) and reordering the ODB initialization in `apply_repository_format()` to ensure the repository’s hash algorithm is configured before the ODB is created. The downcast macro in the original code would BUG if the source were not a "files" backend, meaning the loop could not safely skip non-files sources—this is now resolved by making the check source-local.

Junio and Justin Tobler raised substantive concerns about the original design in v1, particularly the unconditional downcast and the potential for inconsistent `should_use_loose_object_map()` results across backends. Patrick’s follow-up clarified that the downcast macro would BUG on non-files backends, but the broader architectural question—whether a generic `load object map` method should be added to the `odb_source` interface—remains unresolved. The current patch sidesteps this by making the loose object map an internal detail of the loose backend, which is a pragmatic solution for now but may need revisiting if non-filesystem backends are introduced.

The patch is well-motivated and addresses a real (if latent) correctness issue. The commit message clearly explains the problem and the fix, and the code changes are minimal and focused. The only remaining direct caller of `repo_read_loose_object_map()` is in `object-file-convert.c`, which reloads the map after potential concurrent updates; Patrick suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source, further reducing external exposure of the object map. This patch is a strong candidate for merging, especially given the added test coverage in the first patch of the series.
