This is the fourth patch in Pablo Sabater’s nine-patch GSoC series (v4), which refactors the remote-object-info subsystem to use a dedicated `struct fetch_object_info_results` instead of the generic `struct object_info`. The patch is a mechanical cleanup that removes about 30 lines of code by eliminating the intermediate `struct protocol_placeholder_entry` and its associated `remote_atom_map[]`, aligning with the new design that avoids string-based lookups in favor of explicit flags and dedicated arrays for each attribute.

Junio’s feedback was surface-level and curiosity-driven, asking why the `remote_atom_map[]` already included the "type" entry despite `%(objecttype)` support not being introduced until later in the series. Pablo clarifies that the list was designed to be idempotent—new placeholders could be added without changing behavior until the server advertised support. The "type" entry was included to test the client’s handling of known-but-unsupported placeholders (e.g., new client vs. old server), leveraging the fact that `struct object_info` already had a type field. With the new design requiring a dedicated array per attribute, carrying an unused `types` array would be wasteful, so the "type" entry is dropped here and reintroduced in the later patch (7/9) where it is fully implemented. The explanation is pragmatic and does not affect the patch’s readiness.

The patch remains uncontroversial and ready for integration. It is part of a feature-complete, merge-ready series that extends `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. All prior review feedback has been addressed, and the architectural refactoring is finalized. The remaining patches in the series (5/9 through 9/9) are similarly uncontroversial and focus on completing the end-to-end implementation for object type metadata.
