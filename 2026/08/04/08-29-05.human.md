This is the v2 cover letter for Patrick Steinhardt’s five-patch series making the creation of on-disk object database (ODB) structures pluggable. The series is part of the ongoing ODB abstraction effort and targets the current development cycle.

The goal remains unchanged: decouple backend-specific directory creation (e.g., `objects/info`, `objects/pack`) from the generic repository setup code. The top-level `objects/` directory is still mandatory for repository recognition, but individual backends now handle their own subdirectory creation via a new `create_on_disk` callback. This enables future ODB backends to implement custom on-disk layouts without modifying core setup logic.

Key improvements in v2 include:
- A new test case (by Toon Claes) demonstrating the bug fixed in the first patch, which ensures loose object maps are loaded from the correct source path in repositories with alternates and compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility). This elevates the patch from a refactoring to a correctness fix with regression coverage.
- A spelling fix in the fourth patch, renaming the "inmemory" backend to "in-memory".
- Clarified commit messages, particularly in the second patch, which now explicitly states that the original code unconditionally downcasts the primary ODB to the "files" backend, risking a BUG if a different backend type were used with a compatibility hash algorithm.

The series touches the loose-object handling (`loose.c`, `loose.h`), ODB source management (`odb/source*.c`, `odb/source*.h`), and repository setup (`setup.c`, `repository.c`). The changes introduce new functions (e.g., `odb_source_type_to_name()`) and structures while removing hardcoded assumptions about directory layouts and initialization order. The `create_on_disk` callback in the ODB source interface is retained for consistency with the ref subsystem’s `ref_store_create_on_disk()`, despite Junio’s suggestion to use a more generic term like `initialize`.

This is infrastructure work with no immediate user-visible impact, but it’s a prerequisite for future ODB backends that don’t follow the traditional loose/pack layout. The series is well-motivated, addresses real correctness issues, and includes thorough test coverage for the edge cases it fixes. The feedback from v1 has been incorporated, and the patches look ready for serious review. If you care about Git’s storage layer or the ODB abstraction effort, this series is worth your time.
