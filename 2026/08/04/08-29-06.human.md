This is the first patch in Patrick Steinhardt’s v2 series making on-disk object database (ODB) structures pluggable. It fixes a latent correctness bug in how Git loads loose object maps when repositories use alternates and compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility).

The bug: `load_one_loose_object_map()` ignored the passed-in ODB source and always loaded the map from the repository’s common `objects/` directory. This meant loose object maps in alternates were silently ignored, breaking object resolution when using compatibility hash formats. The fix replaces `repo_common_path_replace()` with `xstrfmt()` to construct the correct path from the loose source’s `base.path`.

The patch is now a confirmed correctness fix, not just refactoring. Toon Claes provided a test case (included here) that creates two SHA-256 repositories (one as an alternate), configures both with SHA-1 compatibility, and verifies `git rev-parse` resolves an object borrowed from the alternate. This test elevates the patch’s importance and provides regression coverage for multi-backend setups.

Review feedback from v1 was incorporated: the commit message now clearly states the bug’s impact, and the test case demonstrates the real-world scenario where the original logic failed. Junio and Justin Tobler previously confirmed the issue affects repositories with compatibility hash algorithms and alternates, and the fix is correct.

This patch is well-motivated, thoroughly tested, and addresses a real bug. It’s a clear candidate for merging, especially given its role in the broader ODB abstraction effort. The only remaining architectural question—whether to eliminate downcasting entirely via a generic `load object map` method—is deferred to future work and doesn’t block this fix.
