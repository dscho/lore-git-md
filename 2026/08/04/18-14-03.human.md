This is the third patch in Domen Kožar's v2 series introducing `post-worktree-add`, `post-worktree-remove`, and `post-worktree-move` hooks. This patch specifically enables the `post-worktree-remove` hook to run when worktrees are pruned via `git worktree prune`, not just when explicitly removed with `git worktree remove`.

The patch addresses a key gap in the series' original scope: tooling that relies on these hooks to clean up per-worktree state needs to observe *all* worktree deletions, including those that happen when users manually delete a worktree directory and later run `git worktree prune`. The implementation is careful to handle edge cases like duplicate entries (the hook runs once per pruned worktree) and missing or corrupt gitdir files (the hook receives an empty string for the path in such cases).

The changes are confined to `builtin/worktree.c` and the hook documentation, with thorough test coverage added to `t/t2401-worktree-prune.sh`. The tests verify that the hook runs once per pruned worktree, respects `--dry-run`, propagates failure exit status, and handles relative worktree paths correctly. The patch is well-motivated and aligns with the series' goal of providing reliable automation triggers for worktree lifecycle events.

This patch is unlikely to be controversial. The only open question from the v1 discussion -- whether the hook should run even when the worktree path cannot be determined -- is resolved here by passing an empty string, which seems reasonable. The series as a whole looks like a clean, useful addition for tooling that manages ephemeral worktrees.
