This thread is about a bug in Git’s history-rewriting commands: `git replay --onto` and `git history fixup` silently drop Git notes when rewriting commits, losing notes on all but the tip commit. D. Ben Knoble reported the issue, and Patrick Steinhardt acknowledged it as an unimplemented feature rather than a deliberate design choice, opening a GitLab issue to track the work.

Phillip Wood has now joined the discussion, confirming a recent bug in `git rebase`’s handling of notes that both Knoble and Steinhardt had vaguely recalled. He proposes a design direction: `git replay` (a plumbing command) should include a command-line option to enable note copying, while `git history` (user-facing) should handle notes automatically. This suggests the underlying implementation would be shared, allowing both commands to reuse the same logic once the plumbing flag is exposed. The thread now has a clearer design path—plumbing gets opt-in behavior, user-facing gets automatic—but no timeline or assignee has been set. The issue remains open for contributions.
