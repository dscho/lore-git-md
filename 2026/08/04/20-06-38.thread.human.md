This thread is about a bug in Git’s history-rewriting tools—specifically `git replay --onto` and `git history fixup`—that silently drops notes attached to commits. D. Ben Knoble reported the issue, noting that only the tip commit’s notes can be manually recovered, while notes on intermediate commits are permanently lost. The discussion has since expanded to include `git filter-repo` and `git fast-export`/`fast-import`, which share the same problem due to architectural constraints: notes are stored as ordinary commits, so filtering operations detach or discard them unless explicitly handled.

Key participants have weighed in on the design. Patrick Steinhardt acknowledged the issue as an unimplemented feature for `git history` (user-facing) and a likely gap for `git replay` (plumbing). Phillip Wood proposed a command-line option (`--[no-]copy-notes`) for `git replay` to enable note copying, while `git history` should handle notes automatically. Junio C Hamano provided historical context about how `git rebase` and `git cherry-pick` treat notes differently, which may influence the design. Elijah Newren highlighted the broader architectural challenge, noting that `git filter-repo` and related tools also drop notes by default. A GitLab issue tracks the work, but there’s no assignee or timeline yet.

The latest email from erik88 points to workarounds for preserving notes in `git filter-repo`, though these are described as "okay" rather than ideal. This doesn’t resolve the core questions—whether note preservation should be opt-in or automatic, how to handle plumbing vs. user-facing commands, or what architectural changes might be needed—but it provides a data point for future implementation. The thread remains open, with no patches or concrete design proposals yet. Community contributions are invited.
