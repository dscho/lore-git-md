This thread is about a bug report from D. Ben Knoble: `git-replay` and `git-history` silently drop Git notes when rewriting commits, losing notes on all but the tip commit. The discussion has clarified that this is an unimplemented feature rather than an intentional design choice, especially for the user-facing `git history` command, while `git replay` (as plumbing) may need a flag to control note copying.

Key participants include Patrick Steinhardt, who acknowledged the gap and opened a GitLab issue to track the work, and Phillip Wood, who proposed a design direction: a `--[no-]copy-notes` command-line option for `git replay` (not config-based) and automatic note handling in `git history`. Junio C Hamano provided historical context about how `git rebase` and `git cherry-pick` handle notes differently, which may influence the design. Elijah Newren added that `git filter-repo` (and `git fast-export`/`fast-import`) also silently drop notes due to architectural limitations—notes are stored as ordinary commits, so filtering operations detach them unless explicitly handled. This reinforces the broader pattern that notes are often overlooked in history-rewriting tools.

The discussion is still open, with no patches or concrete implementation plan yet. The main questions are whether the proposed `--copy-notes` flag for `git replay` should default to on or off, and how the existing design precedent for `git rebase` and `git cherry-pick` should shape the solution. The shared implementation would likely reside in the history-rewriting codebase, allowing both commands to reuse it. Community contributions are invited, but there’s no assignee or timeline for the work.
