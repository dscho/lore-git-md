This thread is about a bug report where `git-replay` and `git-history` silently drop Git notes when rewriting commits, with only the tip commit’s notes recoverable manually. D. Ben Knoble initially reported the issue, questioning whether notes are intentionally out of scope or an unimplemented feature. The discussion expanded to include `git filter-repo` and `git fast-export`/`fast-import`, which also drop notes due to architectural constraints—notes are stored as ordinary commits, so filtering operations detach or discard them unless explicitly handled.

Key participants include Patrick Steinhardt, who acknowledged the issue as an unimplemented feature for `git history` (user-facing) and a likely gap for `git replay` (plumbing), and Phillip Wood, who proposed a `--[no-]copy-notes` flag for `git replay` (opt-in by default) while suggesting `git history` should handle notes automatically. Junio C Hamano provided historical context about `git rebase` and `git cherry-pick`’s differing note-handling designs, which may inform the current discussion. Elijah Newren reinforced the architectural challenges, noting that `git filter-repo`’s workarounds for note preservation are imperfect and require changes to `git fast-export`/`fast-import`.

The thread remains under review with no patches or concrete design yet. Open questions include whether note preservation should be opt-in or automatic, how to handle plumbing vs. user-facing commands, and whether architectural changes are needed for broader tooling like `git filter-repo`. A GitLab issue tracks the work, but there’s no assignee or timeline. Community contributions are invited, and the discussion is still active.
