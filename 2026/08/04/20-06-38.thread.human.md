This thread is about a bug report from D. Ben Knoble: `git-replay` and `git-history` silently drop Git notes when rewriting commits, losing notes on all but the tip commit. The issue is under review, with no patches yet, but there’s growing consensus that this is an unimplemented feature rather than an intentional design choice.

Key participants include Junio C Hamano, who provided historical context about how `git rebase` and `git cherry-pick` handle notes differently, and Patrick Steinhardt, who acknowledged the gap for both commands and opened a GitLab issue to track the work. Phillip Wood proposed a design direction: a `--[no-]copy-notes` command-line option for `git replay` (not config-based) and automatic note handling in `git history`, with shared implementation in the history-rewriting codebase. D. Ben Knoble’s latest reply agrees with Phillip’s proposal but briefly explored (and then dismissed) the idea of reusing the existing `notes.rewrite.<command>` config pattern, reinforcing that config is unsuitable for plumbing commands.

The main open questions remain: whether note preservation should be opt-in or opt-out, what technical constraints might exist, and how the historical precedent of `git rebase` and `git cherry-pick` should influence the design. The GitLab issue is the only tracking mechanism, with no assignee or timeline yet, and the community is invited to contribute.
