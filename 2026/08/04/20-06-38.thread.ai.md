Thread identity
Subject: `git-replay` and `git-history` silently drop notes during history rewriting
Series version: none (standalone bug report)
Originating author: D. Ben Knoble
Thread type: bug report

Core problem or goal
`git-replay` (specifically `git replay --onto=...`) and `git-history` (specifically `git history fixup`) silently drop Git notes when rewriting commits. The reporter observes that only the tip commit’s notes can be manually recovered (`git notes copy @{1}`), while notes on intermediate commits are permanently lost. The thread seeks to clarify whether notes are intentionally out of scope for these commands or if this is an unimplemented feature. Elijah Newren has expanded the scope by noting that `git filter-repo` (and by extension `git fast-export`/`fast-import`) also silently drops notes due to architectural constraints: notes are stored as ordinary commits, so filtering operations that modify the commit graph detach or discard them unless explicitly handled as a special case. erik88 adds that `git filter-repo` has documented workarounds for preserving notes, though these are described as "okay" rather than ideal, and do not address the underlying architectural issue.

Current status
Under review; no patches or detailed design discussion yet. Junio C Hamano has provided historical context regarding the intentional design distinction between `git rebase` and `git cherry-pick` in their handling of notes, which should inform the current design discussion. Patrick Steinhardt has acknowledged the issue as an unimplemented feature for `git history` (user-facing) and a likely gap for `git replay` (plumbing). Phillip Wood has proposed a design direction: a command-line option (`--[no-]copy-notes`) for `git replay` to enable note copying (not config-based), while `git history` should handle notes automatically. D. Ben Knoble has acknowledged Phillip’s proposal and agreed that config-based control is inappropriate for plumbing commands, briefly considering but ultimately rejecting the idea of reusing the `notes.rewrite.<command>` configuration pattern for `git replay`. Elijah Newren’s contribution reinforces the architectural challenge of preserving notes across history-rewriting tools, highlighting that the issue is not isolated to `git-replay` and `git-history` but affects the broader ecosystem. erik88’s follow-up notes that `git filter-repo` has workarounds for note preservation, though these are not ideal and do not resolve the architectural root cause. The shared implementation would reside in the history-rewriting codebase, allowing both commands to reuse it once the plumbing flag is exposed. A GitLab issue tracks the work for the next release cycle, but no assignee, timeline, or concrete implementation plan exists. Community contributions are invited.

Key technical details
- Commands affected: `git replay --onto=...`, `git history fixup`, `git filter-repo`, `git fast-export`/`fast-import`
- Subsystems touched: notes, history rewriting (replay/history/filter-repo)
- Behavior: notes on rewritten commits are silently dropped; no warning or error is emitted
- Root cause for `filter-repo`/`fast-export`/`fast-import`: notes are stored as ordinary commits, so filtering operations that modify the commit graph detach or discard them unless explicitly handled as a special case
- Workaround: manual `git notes copy @{1}` recovers only the tip commit’s notes; `git filter-repo` has documented workarounds for note preservation, though these are not ideal
- Distinction between user-facing (`git history`) and plumbing (`git replay`) commands noted; intent to address differs accordingly
- New symbols: proposed `--[no-]copy-notes` command-line option for `git replay` (not config-based)
- Implementation plan: shared note-copying logic in the history-rewriting codebase, reused by both commands
- Historical context: `git rebase` and `git cherry-pick` intentionally treat notes differently, which may serve as precedent for the current design discussion. The `notes.rewrite.<command>` configuration pattern governs note copying for these commands but is considered unsuitable for plumbing commands like `git replay`.
