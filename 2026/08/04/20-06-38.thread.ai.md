Thread identity
Subject: `git-replay` and `git-history` silently drop notes during history rewriting
Series version: none (standalone bug report)
Originating author: D. Ben Knoble
Thread type: bug report

Core problem or goal
`git-replay` (specifically `git replay --onto=...`) and `git-history` (specifically `git history fixup`) silently drop Git notes when rewriting commits. The reporter observes that only the tip commit’s notes can be manually recovered (`git notes copy @{1}`), while notes on intermediate commits are lost. The question is whether notes are intentionally out of scope for these commands or if this is an unimplemented feature.

Current status
Under review; Patrick Steinhardt has acknowledged the issue as an unimplemented feature for `git history` (user-facing) and a likely gap for `git replay` (plumbing). A GitLab issue has been opened to track the work for the next release cycle, but no patch or detailed design discussion has emerged yet.

Key technical details
- Commands affected: `git replay --onto=...`, `git history fixup` (and likely other `git-history` modes)
- Subsystems touched: notes, history rewriting (replay/history)
- Behavior: notes on rewritten commits are silently dropped; no warning or error is emitted
- Workaround: manual `git notes copy @{1}` recovers only the tip commit’s notes
- Distinction between user-facing (`git history`) and plumbing (`git replay`) commands noted; intent to address differs accordingly

Open questions and loose ends
- What is the expected scope of note preservation (all rewritten commits, only the tip commit, or none)?
- Should `git replay` and `git history` follow the behavior of other history-rewriting commands (`git rebase`, `git cherry-pick`) that already handle notes, or is a different approach warranted?
- Are there technical constraints (e.g., transactional safety, performance) that would make full note preservation difficult?
- No timeline or assignee for implementation; community contributions are invited.

Participant positions
- D. Ben Knoble (reporter): observes the behavior, considers it unexpected, and seeks clarification on intent vs. implementation gap. Framing suggests the omission is a gap rather than a deliberate design choice.
- Patrick Steinhardt: confirms that for `git history` (user-facing), the silent dropping of notes is an unimplemented feature, not a design decision. For `git replay` (plumbing), he considers the behavior a likely gap that should eventually be addressed. Opens a GitLab issue to track the work but does not commit to implementing it himself.

Related work
None mentioned in the thread. Potential comparison points: `git rebase` and `git cherry-pick` behavior with notes (if known or documented elsewhere). No prior versions or external dependencies referenced.
