Subject: `git-replay` and `git-history` silently drop notes during history rewriting
Series version: none (standalone bug report)
Originating author: D. Ben Knoble
Thread type: bug report

Core problem or goal
`git-replay` (specifically `git replay --onto=...`) and `git-history` (specifically `git history fixup`) silently drop Git notes when rewriting commits. The reporter observes that only the tip commit’s notes can be manually recovered (`git notes copy @{1}`), while notes on intermediate commits are lost. The question is whether notes are intentionally out of scope for these commands or if this is an unimplemented feature.

Current status
Under review; no prior discussion or patch referenced. The report is a new observation, not a response to an existing thread.

Key technical details
- Commands affected: `git replay --onto=...`, `git history fixup` (and likely other `git-history` modes)
- Subsystems touched: notes, history rewriting (replay/history)
- Behavior: notes on rewritten commits are silently dropped; no warning or error is emitted
- Workaround: manual `git notes copy @{1}` recovers only the tip commit’s notes

Open questions and loose ends
- Is the silent dropping of notes intentional (design choice) or an unimplemented feature?
- If unimplemented, what is the expected scope of note preservation (all commits, only tip, none)?
- Are there other history-rewriting commands in the same family (`git rebase`, `git cherry-pick`, etc.) that already handle notes correctly, and if so, should `git-replay` and `git-history` follow the same pattern?

Participant positions
- D. Ben Knoble (reporter): observes the behavior, considers it unexpected, and seeks clarification on intent vs. implementation gap. No explicit position on whether it should be fixed, but the framing suggests it is a gap rather than a deliberate omission.
