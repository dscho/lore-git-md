This is the sixth patch in the RFC v2 series introducing `--drop-filtered` to `git repack` for partial clones. The patch implements the two critical safety guards that were blocking concerns from the v1 review: it prevents `--drop-filtered` from running during ongoing operations (merge, rebase, cherry-pick, etc.) and refuses to drop blobs referenced by the current index. Both checks are skipped for bare repositories, and the error messages are specific and actionable.

The implementation is clean and well-tested. It adds 47 lines to `builtin/repack.c`, using `wt_status_get_state()` to detect in-progress operations and `repo_read_index()` to scan the index for any blob in the `drop_oids` set. The test script (`t/t7706-repack-drop-filtered.sh`) verifies both guards: one test creates a conflicting merge and confirms the command fails, while another stages a large blob, marks it as promisor, and verifies the drop is refused. The commit message clearly explains the rationale, and the code is ready for review.

However, the necessity of these guards is now contested. Junio has proposed replacing them with a time-based heuristic (avoid culling recently fetched objects), and Siddharth Shrimali has endorsed this direction. The current guards are now viewed as optional optimizations rather than correctness measures, so this patch may need to be revisited or removed in the next revision. The review from Siddharth Asthana is brief but positive, endorsing the index guard as a UX optimization to avoid immediate re-fetching.
