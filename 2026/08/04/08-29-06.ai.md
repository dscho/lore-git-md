This is the first patch in Patrick Steinhardt’s v2 series making on-disk ODB structures pluggable, and it **fixes a latent correctness bug** in how loose object maps are loaded. The patch ensures that loose object maps are loaded from the correct ODB source path (e.g., an alternate repository’s `objects/` directory) rather than always defaulting to the common directory. This is critical for repositories using compatibility hash algorithms (e.g., SHA-256 with SHA-1 compatibility) and alternates, where the original logic would silently ignore maps from alternate sources.

The bug is demonstrated by the new test case (provided by Toon Claes), which creates two SHA-256 repositories—one acting as an alternate—and verifies that `git rev-parse` correctly resolves an object borrowed from the alternate when using the compatibility hash format. The test elevates the patch’s importance: without this fix, repositories with alternates and non-default hash algorithms could fail to resolve objects or produce incorrect results. The commit message now clearly states the bug’s impact, and the test provides regression coverage.

The fix itself is straightforward: it replaces `repo_common_path_replace()` with `xstrfmt()` to construct the correct path from the loose source’s `base.path`. The change is minimal but touches a core part of the object database infrastructure (`loose.c`), where incorrect behavior could have subtle, far-reaching consequences. The patch also updates the function signature of `load_one_loose_object_map()` to take only the `odb_source_loose` parameter, removing the redundant `repository` argument.

Review feedback from v1 (including from Junio and Justin Tobler) confirmed the bug’s real-world relevance and the fix’s correctness. The added test case addresses Toon Claes’s suggestion to highlight the severity of the issue, making the patch’s motivation unambiguous. This is **not just refactoring**—it’s a targeted fix for a confirmed correctness issue, and the test ensures it won’t regress.

The patch is part of the broader ODB abstraction effort, but its immediate impact is narrow: it resolves a specific bug without changing behavior for repositories without alternates or compatibility hashes. The series’ later patches build on this foundation, but this one stands alone as a bugfix with clear value. **For anyone using alternates or SHA-256 repositories, this patch is worth attention.** The rest of the series is infrastructure work, but this fix is ready to merge.
