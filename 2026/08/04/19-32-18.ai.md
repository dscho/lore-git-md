This is Junio C Hamano’s latest reply in the ongoing RFC thread about restricting hex object IDs to lowercase in Git 3.0. He acknowledges brian m. carlson’s argument that modern security practices favor strict input validation over Postel’s Law (the Robustness Principle), but pushes back, calling the premise "debatable." Junio distinguishes between *careless* leniency (e.g., storing mixed-case loose object filenames verbatim on case-sensitive filesystems) and *deliberate* leniency (e.g., normalizing inputs to avoid compatibility issues). He suggests that the project could, with sufficient care, accept mixed-case inputs while enforcing lowercase internally—addressing both security and compatibility concerns—rather than rejecting them outright. His tone is ambivalent: while he plans to queue the series for integration ("Will queue"), he expresses discomfort ("my more principled side feels dirty") at the idea of offloading compatibility fallout onto reimplementations like libgit2 or JGit. This reply does not resolve the philosophical divide but signals that Junio is leaning toward accepting the series as-is, pending further community input. The thread remains in RFC limbo, with the core question—whether Git 3.0 should enforce lowercase-only object IDs—still open. Key technical context for follow-ups: the distinction between *storing* and *normalizing* mixed-case inputs, and whether the project is willing to invest in the latter.
