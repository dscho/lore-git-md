This is a bugfix patch (part 2/9 of the GSoC `objecttype` support series) that hardens the `fetch_object_info()` function against malformed server responses. The patch addresses a latent protocol robustness issue: the client previously trusted the server to send exactly the number of object-info lines requested, leaving the end of the result arrays uninitialized if the server sent too few, and silently ignoring extra packets if the server sent too many. The fix extracts the packet-reading logic from the loop condition, checks for under-length responses (too few objects) and over-length responses (too many objects), and `die()`s in either case to fail fast. This aligns with Git’s defensive programming practices and Junio’s protocol hygiene concerns from earlier review.

The change is minimal and focused: it adds two explicit checks (one inside the loop for under-length responses, one after the loop for over-length responses) and updates the error messages to include the expected and actual object counts. The patch touches only `fetch-object-info.c` and does not affect any other part of the series’ functionality. It is a direct response to Junio’s feedback on v3, which noted that while the code was safe against buffer overflow, it should detect and reject protocol violations rather than silently tolerating them. The fix is uncontroversial and ready to merge.
