This is Junio C Hamano's reply to the `post-worktree-*` hook series (v2), raising a fundamental design question: whether these hooks are necessary at all. Junio argues that most of the proposed functionality—running custom logic before or after `git worktree add`/`remove`/`move`—can already be achieved by wrapping the commands in a shell script (e.g., `git-wt`), which users would have to write anyway. He lists five valid use cases for hooks (countermands, post-data generation, remote access, mutual exclusion, and outcome-dependent execution) and contends that none apply here, since the worktree lifecycle events are locally observable and do not require Git's internal state or locks.

Junio acknowledges that a hook *might* be justified if the use case were so common that everyone would end up writing the same wrapper, but he does not see that as true for these hooks. The email is a substantive review that challenges the series' premise rather than its implementation, and it sets a high bar for justifying new hooks. Domen Kožar's v2 patches (which added `post-worktree-move` and extended `post-worktree-remove` to cover pruning) are not addressed directly; the critique applies equally to all three hooks. This reply is likely to shift the thread toward a meta-discussion about whether the feature belongs in Git at all.
