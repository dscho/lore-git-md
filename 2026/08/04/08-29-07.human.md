This is the second patch in Patrick Steinhardt’s five-part series refactoring how Git loads loose object maps for repositories using compatibility hash algorithms. The patch addresses a latent correctness issue in the current initialization sequence: the code unconditionally downcasts the primary object database (ODB) to the "files" backend when loading loose object maps, which would trigger a BUG if a different backend type were used with a compatibility hash algorithm. By moving the map-loading logic into the "loose" backend itself, the patch eliminates the unsafe downcast and decouples repository configuration from ODB initialization.

The change is small (11 insertions, 10 deletions) but significant. It introduces a new public function, `loose_object_map_load()`, which the "loose" backend now calls during its own initialization (`odb_source_loose_new()`). This ensures the map is loaded from the correct ODB source path, fixing a bug that could occur in repositories with alternates and non-default hash algorithms (e.g., SHA-256 with SHA-1 compatibility). The patch also reorders the initialization steps in `apply_repository_format()` to set the compatibility hash algorithm *before* creating the ODB, avoiding a circular dependency where the ODB had to exist before its configuration was complete.

The commit message is clear and direct, explaining both the problem (unsafe downcast, intermixed configuration/initialization) and the solution (backend-local map loading). The added test case in the first patch (not part of this diff) strengthens the case for merging, as it demonstrates the bug in a real-world scenario. Reviewers—particularly Junio and Justin Tobler—have raised architectural questions about the downcast’s safety and whether a more generic `load object map` method should be added to the ODB source interface, but Patrick has clarified that the current approach is correct for now, as the loose object map is being treated as an internal implementation detail of the "loose" backend.

This patch is a well-motivated refactoring with a concrete correctness benefit. It’s part of the broader ODB abstraction effort, but the fix stands on its own and could graduate early if the rest of the series is delayed. The changes are mechanical and focused, touching only the loose-object map loading logic without altering on-disk formats or user-visible behavior. If you care about repository initialization robustness or the ODB abstraction work, this patch is worth reviewing.
