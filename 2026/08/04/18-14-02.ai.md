This is the second patch in Domen Kožar’s v2 series introducing `post-worktree-add`, `post-worktree-remove`, and `post-worktree-move` hooks. It implements the `post-worktree-remove` hook, which fires after a worktree is deleted by `git worktree remove` (or pruned after manual deletion). The hook receives two arguments: the absolute path of the removed worktree and its identifier (the name of its former administrative directory under `$GIT_DIR/worktrees/`). The hook runs unconditionally once deletion is underway, even if parts of the deletion fail, but it does not run if the removal is refused (e.g., due to a locked or dirty worktree). The hook’s exit status is propagated to `git worktree remove`, though it cannot prevent the worktree from being deleted.

The patch touches `builtin/worktree.c` to add the hook invocation, updates `Documentation/config/hook.adoc` and `Documentation/githooks.adoc` to document the new hook, and extends `t/t2403-worktree-move.sh` with four new tests covering normal removal, removal of a missing worktree, refused removal, and a failing hook. The implementation is straightforward and consistent with the design choices established in the series: hooks run after the fact, cannot affect the outcome, and are given minimal but sufficient arguments for tooling to identify the affected worktree.

This patch directly addresses the core problem outlined in the series: external tooling (particularly AI-driven development environments) needs a reliable way to learn when a worktree is gone so it can tear down associated resources. The hook’s behavior—running after deletion, with no special environment, and receiving the worktree’s former path and ID—matches the pattern set by `post-worktree-add` and aligns with the needs of high-velocity tooling. The test coverage is thorough, handling edge cases like missing worktrees and refused removals, and the documentation is clear and complete.

No open questions or loose ends are introduced by this patch; it implements the design as agreed in the thread (unchanged from v1). The only remaining discussion point from the series—whether to document the relative order of `post-worktree-add` and `post-checkout`—is unrelated to this patch and was not addressed in v2. The patch is technically sound, well-tested, and ready for review.
