Thread identity: user support question regarding a regression in Git’s textconv feature introduced in Git 2.50; originating author Randall S. Becker (NonStop port maintainer). The regression is confirmed to be **platform-specific to NonStop**, affecting only files beginning with a null byte, and is now further isolated to NonStop’s I/O stack behavior during tempfile creation. Randall has proposed a new feature (`%f` placeholder in textconv filters) to mitigate the workflow breakage caused by the regression.

Core problem or goal: since Git 2.50, external textconv filters receive an empty temporary file when processing *binary* files (those beginning with a null byte) **only on NonStop**, breaking workflows that depend on the original file path to locate repository files. The regression is now attributed to platform-specific I/O behavior (e.g., early truncation or failure to write during tempfile creation). The thread has shifted from diagnosing the regression to proposing a workaround: extending the textconv filter interface to accept a `%f` placeholder that expands to the original working-tree file path, addressing the symptom (path ambiguity) but not the root cause (empty temp files).

Current status: reported as a breaking change with a confirmed scope—empty temp files occur **only for binary files (null-byte-prefixed) on NonStop**, and the regression is attributed to platform-specific I/O behavior. Jeff King (Peff) and D. Ben Knoble have confirmed they **cannot reproduce the issue** on non-NonStop platforms, even with files containing NUL bytes. No patch, root-cause analysis, or maintainer response addressing the regression itself has emerged. Randall’s `%f` proposal is the first concrete suggestion to mitigate the workflow impact, but it remains untested and unendorsed by other participants. The issue remains unresolved and user-facing.

Key technical details: textconv filters now receive empty `/tmp/git-blob-*/<name>` files **only for binary files (null-byte-prefixed) on NonStop**; prior behavior passed the actual working-tree file content. The regression appears tied to null-byte handling during tempfile creation, likely involving NonStop-specific I/O behavior (e.g., early truncation or failure to write). Peff’s explanation of tempfile reuse (working-tree file passed for clean files in `git diff HEAD^` or `git diff --cached HEAD^`, tempfiles always used for `git show HEAD`) accounts for earlier inconsistencies but does not resolve the regression. The `%f` proposal would introduce a new placeholder in the textconv filter interface, expanding to the original file path in the working tree, but would not fix the underlying regression (empty temp files).
