Thread identity: user support question regarding a regression in Git’s textconv feature introduced in Git 2.50; originating author Randall S. Becker (NonStop port maintainer). The regression is confirmed to be binary-file-specific on the NonStop platform, affecting only files beginning with a null byte.

Core problem or goal: since Git 2.50, external textconv filters receive an empty temporary file when processing *binary* files (those beginning with a null byte) on NonStop, breaking workflows that depend on the original file path to locate repository files. Text files and ELF binaries (which do not begin with null bytes) work as expected. The question remains whether this change was deliberate or a bug, and how to restore the previous behavior.

Current status: reported as a breaking change with a confirmed scope—empty temp files occur only for binary files (null-byte-prefixed) on NonStop. Jeff King (Peff) has clarified that Git’s tempfile reuse optimization (passing the working-tree file instead of a tempfile) is not new and is not the root cause of the regression. However, he cannot reproduce the issue even with files containing NUL bytes, leaving the root cause unresolved. No patch, root-cause analysis, or maintainer response addressing the regression itself. The issue remains unresolved and user-facing.

Key technical details: textconv filters now receive empty `/tmp/git-blob-*/<name>` files *only for binary files* (null-byte-prefixed) on NonStop; prior behavior passed the actual working-tree file content. The regression appears tied to null-byte handling during temp file creation, possibly involving platform-specific I/O behavior (e.g., early truncation or failure to write). Peff’s explanation of tempfile reuse (working-tree file passed for clean files in `git diff HEAD^` or `git diff --cached HEAD^`, tempfiles always used for `git show HEAD`) accounts for earlier inconsistencies but does not resolve the regression. The discrepancy between Randall’s and D. Ben Knoble’s observations is now fully explained by file content type (binary vs. text) and command context (diff vs. show).

Open questions and loose ends:
- Root cause: is this a platform-specific I/O issue (e.g., NonStop’s handling of null bytes), a Git version regression, or a combination of both?
- Why Peff cannot reproduce the issue even with NUL-prefixed files: is there a NonStop-specific factor (e.g., I/O stack behavior) or a missing test case?
- How to restore the old behavior for binary files on NonStop.
- Whether other users have encountered this, particularly on other platforms with binary files.
- Whether the regression affects all textconv filters or only those relying on file paths for binary content.

Participant positions:
