This is a follow-up in the ODB abstraction series, specifically addressing Justin Tobler’s review of the second patch, which refactors how loose object maps are loaded. The patch is part of Patrick Steinhardt’s effort to make on-disk ODB structures pluggable, and this exchange clarifies two key points about the design.

Patrick acknowledges Justin’s observation that `repo_set_compat_hash_algo()` currently reaches directly into the loose ODB backend to load compatibility object maps. While Patrick agrees this responsibility should shift to the backend itself (a goal of the series), he defers changing the eager-loading behavior for now, citing caution about the compatibility mapping logic. This leaves the initialization sequence intact but paves the way for future backend-specific handling.

The second clarification addresses Justin’s question about whether multiple ODB sources might answer `should_use_loose_object_map()` differently. Patrick confirms they should not, but explains the guard was moved into `loose_object_map_load()` to let each source validate its own state—a necessary step as the loose backend now manages its own map loading. This doesn’t resolve the broader architectural question (raised earlier by Junio) about downcast safety in multi-backend setups, but it tightens the patch’s internal logic.

The tone is pragmatic: Patrick prioritizes incremental progress over speculative changes, and the exchange doesn’t introduce new objections. For readers tracking the ODB abstraction effort, this follow-up underscores that the patch is a correctness fix (removing hardcoded assumptions about the "files" backend) while leaving room for future refinements. The loose object map remains an internal detail, and the only remaining external caller is in `object-file-convert.c`. No merge status is reported; the series is still under review.
