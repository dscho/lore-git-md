This is a follow-up in the ODB abstraction series, specifically addressing Junio C Hamano’s review of the second patch. Patrick Steinhardt clarifies two points from the original review.

First, he rewrites the commit message to replace the ambiguous phrase “extract its loose backend” with a precise explanation: the code unconditionally downcasts the primary ODB to the “files” backend, which will trigger a BUG if a different backend type is used with a compatibility hash algorithm. This is a latent correctness issue that the patch fixes.

Second, he confirms that the downcast macro will BUG if the source is not a “files” backend, meaning the current loop cannot safely skip non-files sources. He then explains the series’ broader direction: the loose object map is being made an internal implementation detail, with the loose backend handling its own loading. The only remaining direct caller of `repo_read_loose_object_map()` is in `object-file-convert.c`, which reloads the map after potential concurrent updates; Patrick suggests this could eventually be replaced by a `FLUSH_CACHES` operation on the ODB source, further reducing external exposure of the object map. He does not address Junio’s suggestion of a generic `load object map` method, implying the current design (with its downcast) is acceptable for now as part of the incremental refactoring.
