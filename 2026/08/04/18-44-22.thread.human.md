This thread began when Randall S. Becker reported a regression in Git 2.50’s textconv feature that affects only the NonStop platform: when processing binary files (those beginning with a null byte), textconv filters receive empty temporary files instead of the actual file content. The issue is now confirmed to be tied to NonStop’s I/O stack behavior during tempfile creation, and neither Jeff King (Peff) nor D. Ben Knoble could reproduce it on other platforms, even with identical file content.

Randall proposed a workaround—adding a `%f` placeholder to textconv filters that would expand to the original working-tree file path—hoping to restore workflows that depend on the file’s location. Peff’s latest reply, however, raises significant technical hurdles: Git caches textconv output using only the blob ID as a key, so introducing path-dependent output would break cache consistency. He also questions whether `%f` is the right solution, arguing it masks the underlying regression (empty temp files) and could introduce new correctness issues, such as when diffing historical trees. While Peff doesn’t reject the idea outright, his feedback suggests the proposal would need substantial redesign to be viable.

The thread remains unresolved. The regression itself—empty temp files for binary content on NonStop—has no root-cause fix or maintainer response, and the `%f` proposal, while technically possible, now faces serious implementation challenges. No other participants have weighed in on the proposal, leaving Randall’s suggestion as the only concrete mitigation on the table. The core questions persist: whether to address the regression directly, pursue the `%f` workaround, or explore a platform-specific fix for NonStop’s I/O behavior. For now, NonStop users relying on textconv for binary files continue to face a broken workflow.
