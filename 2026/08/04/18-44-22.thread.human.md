This thread is about a regression in Git 2.50’s textconv feature that affects the NonStop platform. Randall S. Becker, the NonStop port maintainer, reported that since Git 2.50, external textconv filters receive empty temporary files when processing *binary* files (those beginning with a null byte) on NonStop. This breaks workflows that rely on the original file path to locate repository files, though text files and ELF binaries (which don’t begin with null bytes) work as expected.

The issue has been confirmed to be binary-file-specific and platform-specific, occurring only on NonStop. Jeff King (Peff) clarified that Git’s tempfile reuse optimization—where the working-tree file is passed to the filter instead of a tempfile in certain contexts—is not new and isn’t the root cause. However, he couldn’t reproduce the issue even with NUL-prefixed files, leaving the root cause unresolved. D. Ben Knoble’s follow-up testing, using a file filled with zeros, also failed to reproduce the issue, reinforcing that the regression is tied to NonStop’s I/O behavior rather than Git’s general handling of binary files.

The thread remains open, with no patch or root-cause analysis yet. The key questions are why this happens only on NonStop (possibly due to platform-specific I/O quirks) and how to restore the old behavior for binary files. No other users have reported similar issues, and it’s unclear whether this affects all textconv filters or only those relying on file paths for binary content. The discussion is now focused on debugging the tempfile creation logic on NonStop or finding a platform-specific workaround.
