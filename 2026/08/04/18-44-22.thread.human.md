This thread began when Randall S. Becker, the NonStop port maintainer, reported a regression in Git 2.50’s textconv feature that affects only NonStop systems: when processing binary files (those beginning with a null byte), textconv filters receive empty temporary files instead of the actual file content. The issue is now confirmed to be platform-specific, tied to NonStop’s I/O stack behavior during tempfile creation, and cannot be reproduced on other platforms even with identical file content.

The discussion has clarified that the regression breaks workflows that rely on the original file path to locate repository files, as the tempfile paths provide no useful context. Jeff King and D. Ben Knoble have both confirmed they cannot reproduce the issue, reinforcing its NonStop-specific nature. In the latest email, Randall proposes a new feature to mitigate the problem: extending the textconv filter interface to support a `%f` placeholder that would expand to the original working-tree file path. This would address the symptom—path ambiguity—without fixing the underlying regression (empty temp files). The proposal is novel and has not yet been reviewed by other participants, so its feasibility or acceptance remains uncertain.

No root-cause analysis or maintainer response has emerged, and the regression itself remains unresolved. The open questions center on whether the fix should target Git’s tempfile logic, NonStop’s I/O stack, or Randall’s proposed `%f` workaround, and whether other NonStop users are affected. The thread is still seeking input on how to proceed.
