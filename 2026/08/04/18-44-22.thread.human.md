This thread is a user support discussion about a potential regression in Git’s textconv feature introduced in Git 2.50. Randall S. Becker, the NonStop port maintainer, reported that external textconv filters now receive empty temporary files instead of the actual working-tree content, breaking workflows that rely on the original file path to locate repository files. The issue affects users who depend on the file path to disambiguate content, particularly when multiple files share the same name.

D. Ben Knoble replied, noting that on his system (Git 2.53.0), the temporary files *do* contain the expected content, even with `binary = true` set in the diff driver. This discrepancy suggests the regression may be environment-specific—possibly tied to platform, Git version, or configuration—rather than a universal issue. Ben recommended debugging with `GIT_TRACE2=1` or a shell-based textconv filter to inspect the invocation, but no root cause or fix has been identified yet.

The thread remains open-ended, with no confirmation on whether the change was intentional or how to restore the previous behavior. No other participants have weighed in, and the discussion is still focused on diagnosing the behavior rather than resolving the regression. If you rely on textconv filters that use file paths, this is worth monitoring for updates.
