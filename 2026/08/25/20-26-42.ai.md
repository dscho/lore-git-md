This is a follow-up in the `git am --3way` bugfix thread. Nikita Leshenko responds to Junio C Hamano’s performance critique and counterproposal with a simpler, less optimized alternative. The core idea is to avoid the per-patch overhead Junio objected to while still fixing the edge case where a later patch in a series fails because its preimage (the postimage of an earlier patch) was never recorded.

Nikita acknowledges the complexity of Junio’s suggested lazy reconstruction—tracking which blobs are missing, identifying which prior patches affect them, and surgically applying only the necessary ones in-core. Instead, he proposes a coarser approach: when `build_fake_ancestor()` fails due to missing SHA-1 information, apply *all* prior patches (1..N-1) on their fake ancestors, generating the missing blobs as a side effect. This ensures the preimage for patch N exists, allowing the 3-way fallback to proceed. To avoid repeating this expensive operation for every subsequent patch, Nikita suggests recording in the `am_state` (`.git/rebase-apply/`) a "postimage-attempted" marker indicating how far the full reconstruction has progressed. If patch M later fails, only patches (N+1)..(M-1) need to be reapplied.

The trade-off is clear: Nikita’s approach prioritizes simplicity and correctness over performance, accepting that the worst-case overhead (applying all prior patches) is still better than failing entirely. It preserves the clean-path performance (no overhead when patches apply cleanly or blobs already exist) and only kicks in when the original bug would have surfaced. The proposal is pragmatic but introduces a new state variable (`postimage-attempted`) and relies on the assumption that the overhead of reapplying patches is tolerable in practice. Junio’s likely concern will be whether this still feels too heavy for large series, but Nikita’s framing—this is a niche issue, and the logic only runs when failure is imminent—may address that. The ball is back in Junio’s court to weigh the trade-offs.
