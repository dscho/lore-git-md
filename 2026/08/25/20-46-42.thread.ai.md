Thread identity: patch series extending `git var` to provide unified identity and signing configuration, replacing the earlier `git ident` proposal. Originating author: Andrew Pleeter (via GitGitGadget). Thread type: patch series (implementation of design consensus).

Core problem or goal: provide a unified, scriptable interface to Git’s identity (author/committer names/emails/dates) and signing configuration (GPG/SSH/X.509 keys, `commit.gpgsign` status) by extending the existing `git var` plumbing command. The solution must support both interactive use and scripting, with composable arguments and machine-readable output.

Current status: **design consensus reached and implementation under active review**. The patch remains **not yet merged** and is still in `seen`. Junio C Hamano and Phillip Wood have posted **substantive, high-weight reviews** of the v3 patch, focusing on documentation clarity, code structure, usability edge cases, output format ambiguity, and argument parsing logic. A v4 revision is expected to address these points, including the newly surfaced issues around `-z` output format and flag handling, before integration. The next step is code-level refinement and resubmission.

Key technical details:
- **Files touched**: `builtin/var.c`, `Documentation/git-var.adoc`, `t/t0007-git-var.sh`.
- **New variables**: `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `GIT_COMMITTER_DATE`, `GIT_DEFAULT_KEY` (with `GIT_SIGNING_KEY` alias).
- **Behavior**: supports multiple variable arguments in a single invocation, `-z` for NUL-terminated output, and resolves signing keys (GPG/SSH/X.509) via `GIT_DEFAULT_KEY`. Maintains backwards compatibility with existing `git var` usage, though new features (e.g., NUL-terminated output) may affect scripts expecting the current format.
- **Code structure feedback**: Junio requests an `enum` for `ident_part()`, table-driven alias handling, and consideration of `parse_options()` for argument parsing. Phillip Wood adds that flags like `-z` should be processed before variable names to avoid interleaving (e.g., `git var GIT_AUTHOR_NAME -z GIT_AUTHOR_EMAIL` should be rejected).
- **Output format**: Phillip Wood flags a critical ambiguity in `-z` mode: the current `key=value\0` format fails when keys (e.g., signing keys) contain `=` characters. He proposes adopting the same format as `git config -z` (`key\neolvalue\0`), which avoids this ambiguity. Multi-valued variables (e.g., paths) may also contain newlines, so `-z` should separate values with `\0` rather than `\n`.
- **Edge cases**: Junio flags usability concerns (e.g., erroring on empty variable lists, special `--` handling) and signing key resolution logic (e.g., resolving keys regardless of `commit.gpgsign` status). Ben Knoble’s **surface-level review** notes that the current behavior (exiting with code 129 and printing usage on empty arguments) may mask logic errors in scripts, though lifting this restriction could improve scripting ergonomics. Phillip Wood’s review implies that the `GIT_SIGNING_KEY` alias may not be necessary, as scripts signing external data would need to know the signing scheme (GPG/SSH/X.509), which isn’t exposed by the variable.
- **Test coverage**: comprehensive, including signing key resolution, environment variable overrides, and multi-argument invocations. Phillip Wood implies that tests should verify `-z` output matches `git config -z` behavior for edge cases (e.g., no-value variables, multi-valued variables).
- **No on-disk format changes or new configuration options**; the patch extends an existing plumbing command predictably.

Open questions and loose ends:
- **Documentation**: Junio requests rewording of variable descriptions to clarify their relationship to commit objects (e.g., "the name that would be recorded in a commit object" instead of "of a piece of code").
- **Code structure**: mechanical improvements (e.g., `enum` for `ident_part()`, table-driven aliases, shorter lines) and argument parsing (e.g., `parse_options()` vs. hand-rolled, flag processing order).
- **Usability**: whether to allow empty variable lists (e.g., `git var` with no args) and whether `--` handling is necessary. Ben Knoble’s feedback suggests deferring this decision to Junio’s broader usability argument.
- **Signing key resolution**: whether `default_key()` should resolve keys even when `commit.gpgsign` is false (Junio argues yes).
- **Output format**: whether `-z` should use `key\neolvalue\0` (like `git config -z`) to avoid ambiguity with `=` in keys, and whether multi-valued variables should be separated by `\0` instead of `\n`.
- **Backwards compatibility**: the patch’s handling of `user.signingkey` (empty string as "not set") is intentional but requires a clarifying comment. The `-z` format change may affect scripts expecting the current format.
- **`GIT_SIGNING_KEY` alias**: whether it is necessary or useful, given that scripts signing external data would need to know the signing scheme (GPG/SSH/X.509), which isn’t exposed by the variable.
