This is the fourth patch in brian m. carlson’s RFC series proposing a Git 3.0 breaking change: restricting hex object IDs to lowercase only. The series remains in the RFC stage, awaiting broader feedback on whether the project wants this change at all. This patch is purely preparatory, introducing a new `HEX_KIND_OID` constant (currently aliased to `HEX_KIND_MIXED`) and updating several core files to use it when parsing object IDs. The change is mechanical and does not alter runtime behavior, but Junio’s review identifies two overlooked spots in `builtin/index-pack.c` and `notes.c` where `HEX_KIND_MIXED` should also be replaced with `HEX_KIND_OID`.

Junio’s feedback is substantive but narrowly scoped. He manually audited the codebase after applying the patch and found that `load_subtree()` in `notes.c` updates only one of its two `hex_to_bytes()` calls to `HEX_KIND_OID`, leaving the other as `HEX_KIND_MIXED`. Similarly, `repack_local_links()` in `builtin/index-pack.c` still uses `HEX_KIND_MIXED` when reading object IDs from `pack-objects` output, which Junio argues could safely use `HEX_KIND_OID` since the sender is a known version of Git. The rest of the remaining `HEX_KIND_MIXED` usages are in subsystems like URL decoding, quoted-printable mail parsing, and color codes, where uppercase hex is either unavoidable or not relevant to object IDs.

The review does not engage with the series’ broader motivation or design, focusing instead on mechanical completeness. Junio’s observations are actionable and suggest the patch needs a small update before it can be considered ready, but they do not address whether the breaking change itself is desirable. The thread’s core question—whether Git should enforce lowercase-only object IDs in 3.0—remains unresolved, with Junio’s earlier ambivalence ("my more principled side feels dirty") still hanging over the discussion. Phillip Wood’s recent question about the security rationale may yet shift the focus back to the bigger picture.
