This is a **substantive review** of the fourth patch in brian m. carlson’s RFC series proposing a Git 3.0 breaking change: restricting hex object IDs to lowercase. The patch itself is preparatory, introducing a `HEX_KIND_OID` constant to label hex-parsing code paths that handle object IDs, with no functional change yet. Junio C Hamano’s review identifies two omissions where `HEX_KIND_OID` should have been used instead of the generic `HEX_KIND_MIXED`: in `builtin/index-pack.c` (reading pack-objects output) and in `notes.c` (reading paths in a notes tree, where one of two calls was missed). The review also confirms that the remaining uses of `HEX_KIND_MIXED`—in color decoding, quoted-printable email parsing, packet-length parsing, ref formatting, percent-encoding, and URL handling—are correctly left unchanged, as they serve purposes unrelated to object IDs. Junio’s feedback is narrowly technical, focusing on completeness rather than the series’ broader motivation or design. The omissions he flags are straightforward and unlikely to be controversial, but they underscore the importance of thorough auditing in a series that touches many low-level parsing paths. The review does not engage with the RFC’s core question—whether the project wants this breaking change at all—but it does signal that the preparatory work is being scrutinized for correctness. Future discussion may still pivot on Phillip Wood’s open question about the security rationale, but for now, this review advances the series by identifying concrete, fixable gaps in the implementation.
