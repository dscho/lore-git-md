Thread identity
Subject: [PATCH 0/2] branch: protect local upstreams from `git branch -d`
Series version: v1 (initial submission)
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series (feature addition)

Core problem or goal
Prevent accidental deletion of a local branch via `git branch -d` when that branch is the upstream of another local branch, thereby breaking the dependency chain. The change alters the semantics of the `-d` flag to refuse deletion unless `-D` (force) is used, unless an alternative behavior (retargeting dependent branches) is implemented.

Current status
Under review (no prior versions, no merge status reported). The series consists of two patches: (1) a pure refactoring of helper functions in `builtin/branch.c` (preparatory, no behavioral change), and (2) the core logic implementing the protection (contested). Junio C Hamano has raised a **substantive backward-compatibility objection** to patch 2/2, and Tuomas Ahola has now clarified that Junio’s earlier feedback was a brainstorm of *possible* directions (blocking deletion *or* retargeting dependent branches) rather than an endorsement of the current approach. The author has acknowledged the compatibility concern but not yet proposed a resolution or new version.

Key technical details
- Files touched: `builtin/branch.c`, `Documentation/git-branch.adoc`
- Tests updated: `t3200-branch.sh` (two new test cases), `t1507-rev-parse-upstream.sh`, `t6040-tracking-info.sh` (both updated to use `-D` where the new logic would block `-d`)
- New behavior: `git branch -d <branch>` refuses to delete `<branch>` if it is the upstream of any other local branch; `-D` overrides. Alternative behavior (retargeting dependent branches to a fallback upstream) has been proposed but is not implemented.
- Scope: local branches only; remote-tracking branches are ignored
- New internal symbols: `deletable_branch_names` and `protected_branch_names` (`strset` variables) track which branches are safe to delete
- Refactoring details: `collect_stacked_branch_base` and `protect_stacked_branch_bases` helpers (with their `stacked_branch_data` struct) were relocated earlier in `builtin/branch.c` in patch 1/2 to allow `delete_branches()` to call them without forward declarations
- Implementation: after collecting candidate branches, `protect_stacked_branch_bases` marks any branch that is an upstream of another local branch as protected; deletion fails with an error message and advice to use `-D` if a protected branch is encountered
- Multi-branch deletions are order-independent: a branch that fails its safety check remains available to protect its upstream, even if the upstream was listed later in the command line

Open questions and loose ends
**Backward-compatibility and design direction (Junio C Hamano, Tuomas Ahola)**: The patch changes the long-established semantics of the `-d` flag, which could break existing user workflows. Tuomas Ahola’s email clarifies that Junio’s earlier feedback was not a blanket endorsement of the current approach but a brainstorm of two possible behaviors: (1) blocking deletion (as implemented), or (2) retargeting dependent branches to a fallback upstream (e.g., `origin/master`). The latter option is more complex but user-friendly, while the former is simpler but disruptive. Junio explicitly rejects introducing a configuration variable to toggle this behavior, arguing it would complicate predictability. The core tension remains unresolved: whether the simpler "block deletion" approach is sufficient or whether the patch must implement retargeting to be acceptable. **Author’s reply** notes that Junio previously requested extended protections and that Phillip Wood recently raised the idea, but does not clarify whether those discussions align with the retargeting alternative.
