This is the first patch in brian m. carlson’s RFC series proposing a Git 3.0 breaking change to restrict hex object IDs to lowercase only. The thread remains in RFC limbo, with Junio C Hamano signaling tentative acceptance but no final decision made. This patch is purely preparatory: it introduces a new `hex_kind` enum and a lowercase-only hex lookup table (`hexval_lc_table`), updates the `hexval()` function to accept an `enum hex_kind` parameter, and refactors existing call sites to use the new infrastructure—all without altering runtime behavior yet.

Junio’s review is surface-level, catching only a trivial typo in the comment (68-67 → 68-6f) and noting the lateness of his feedback. The review does not engage with the patch’s substance or the series’ broader motivation, so it does not advance the thread’s core questions: whether the project will accept the breaking change, whether the security rationale holds, or whether Junio’s proposed compromise (normalizing inputs internally while accepting mixed-case externally) is feasible. The typo fix is uncontroversial and will likely be adopted in a future reroll, but the patch itself remains unchanged in this iteration.

The patch touches four files: `hex-ll.c` (new table and updated `hex_to_bytes`), `hex-ll.h` (enum and function signature), `color.c` (one call site), and `pkt-line.c` (packet-length parsing). The diff is mechanical and does not introduce new test failures. No new symbols or behaviors are exposed to users or other subsystems at this stage—this is infrastructure-only work for the later patches that will enforce lowercase-only parsing in specific contexts (e.g., object IDs). The thread’s open questions—particularly Phillip Wood’s challenge to the security rationale and Junio’s ambivalence about the breaking change—remain unresolved.
