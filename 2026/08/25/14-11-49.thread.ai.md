Thread identity: Refactoring ODB alternates handling during repository creation. 8-patch series (`[PATCH 0/8]`) by Patrick Steinhardt, part of the ongoing ODB abstraction effort. Thread type: patch series.

Core problem or goal: Remove the ability to write ODB alternates after repository creation, simplifying the ODB interface. Currently, alternates can be added at any time via `odb_source_write_alternate()`, but Git only uses this during initial setup (e.g., `git clone --reference`). The series introduces a new option in `odb_source_create_on_disk()` to handle alternates at creation time, eliminating the need for a separate `write_alternates()` callback. This change prepares for alternates to become an implementation detail of the ODB backend, giving backends more control over their configuration.

Current status: Under review. The series is built on `ps/odb-eagerly-load-alternates` and remains in the review phase. All 8 patches have been posted and reviewed, with substantive feedback now focused on the locking strategy for alternates file updates. Patches 1-5 refactored reference handling in `git clone`, deferring ODB setup and consolidating alternates logic into `collect_alternates()`. Patch 5 addressed a latent bug in worktree alternates handling (fixing unresolved common directory paths) and added test coverage for worktree clones and relative path resolution. Patch 6 implemented the core design change, introducing `odb_create_on_disk_options` to write alternates during ODB creation, but Junio C Hamano has raised a security and correctness concern about the patch’s use of append mode (`"a"`) instead of Git’s standard lockfile API for writing the `info/alternates` file. This could introduce TOCTOU (time-of-check-to-time-of-use) races or partial writes, even during repository creation. Patch 7 wired up the new mechanism in `cmd_clone()`, removing the last direct use of `odb_add_to_alternates_file()`. Patch 8 removes the now-unused `odb_source_write_alternates()` function and its supporting infrastructure across all ODB backends, but Toon Claes previously flagged the removal of the lockfile mechanism as potentially unsafe under concurrent access.

Key technical details:
- Files touched: `builtin/clone.c` (patches 1-5 refactored reference handling, deferring ODB setup and consolidating alternates logic into `collect_alternates()`; patch 7 removed manual alternates writing), `setup.c`/`setup.h` (added `INIT_DB_SKIP_ODB` flag, exposed `create_object_database()`, and updated it to accept a `strvec` of alternates paths), `odb/source-files.c` (patch 6 added support for writing alternates during creation via `odb_source_files_create_on_disk()` with `odb_create_on_disk_options`; patch 8 removed the `write_alternate` callback and its lockfile mechanism), `odb/source-inmemory.c`, `odb/source-loose.c`, `odb/source-packed.c` (patch 8 removed backend-specific `write_alternate` implementations), `odb/source.h` (patch 6 added `#include "strvec.h"` and `odb_create_on_disk_options`), and `t/t5604-clone-reference.sh` (updated tests for worktree alternates handling and relative path resolution).
- New or renamed symbols: `INIT_DB_SKIP_ODB` flag added to `init_db()`; `create_object_database()` made public and updated to accept a `strvec` of alternates paths; `collect_alternates()` (renamed from `setup_reference()`, now with `src_repo` and `is_local` parameters), `add_one_alternate()` (replaces `add_one_reference()`), `struct add_one_alternate_data` (tracks whether an alternate is required/optional and holds the `strvec` of paths), `read_alternates()` (renamed from `copy_alternates()`), and `odb_create_on_disk_options` (new struct carrying alternates `strvec` for ODB creation). The `write_alternates()` callback, `odb_add_to_alternates_file()` helper, and lockfile mechanism have been removed. `odb_source_write_alternates()` is now unused and deleted.
- Subsystems: ODB (object database), alternates handling, repository creation, worktree handling.
- Old-vs-new behavior: No user-visible changes. The series defers ODB creation in `git clone` until after the clone source URI is resolved, ensuring alternates are written with full context. Patches 1-5 addressed a latent bug in worktree alternates handling (fixing unresolved common directory paths) and consolidated alternates logic into a single code path. Patch 6 implemented the core design change: alternates are now written during ODB creation via `odb_create_on_disk_options`, but the use of append mode (`"a"`) for writing the `info/alternates` file introduces a potential TOCTOU race or partial write risk, as noted by Junio. Patch 7 removed the last manual alternates writing step in `cmd_clone()`, consolidating alternates setup into `create_object_database()`. Patch 8 removed the unused `write_alternates()` infrastructure, including the lockfile mechanism, but this removal is now under scrutiny due to the locking concerns raised by both Junio and Toon Claes.
- Test coverage: Updated in `t/t5604-clone-reference.sh` to verify new behavior, including edge cases for cloning from worktrees and resolving relative alternates paths. No regressions expected in clone or alternates handling, but the locking issue in patch 6 may require additional test coverage for concurrent repository creation scenarios.

Open questions and loose ends: The primary open question is the locking strategy for writing the `info/alternates` file. Junio C Hamano has raised a substantive concern about patch 6’s use of append mode (`"a"`) instead of Git’s standard lockfile API, which could introduce TOCTOU races or partial writes. While the operation happens only once during repository creation, Junio implies that the lockfile API would still be the safer and more conventional choice. Toon Claes previously raised a related concern in patch 8 about the removal of the lockfile mechanism, questioning whether the new implementation (writing alternates during ODB creation via `odb_create_on_disk_options`) is safe under concurrent access. The series does not currently address locking in the new flow, and this issue may require a rethink of the locking strategy or a justification for why it is no longer needed. Minor code hygiene suggestions from Toon Claes (e.g., `fclose(in)` placement in `read_alternates()`, header include order in `odb/source.h`) remain unresolved but do not affect functionality or design.
