This is a follow-up in the RFC thread about making Git's stash stack branch-aware or worktree-aware to prevent silent interference between worktrees. The author, Vladimir Sitnikov, responds to feedback from Kristoffer Haugsbakk, Phillip Wood, and Junio C Hamano, refining the problem and evaluating the proposed branch-aware design.

Vladimir clarifies that the original problem—silent interference between worktrees—cannot be fully addressed by banning `git stash` or using wrappers, because commands like `git rebase --autostash` implicitly create stash entries in the global `refs/stash` without ever invoking the `stash` subcommand. This makes the issue unavoidable for automated agents, as `rebase.autoStash` is a shared configuration that affects all worktrees. He acknowledges Junio’s point about the high bar for new configuration but argues that the problem is severe enough to justify a solution, especially given the rise of automated tooling.

On the branch-aware design proposed by Phillip Wood, Vladimir notes that it covers most of his use case, since Git prevents checking out the same branch in multiple worktrees. However, he identifies a gap: detached HEAD worktrees (common in automated workflows) all record stashes with the same "(no branch)" label, which would group them together rather than separating them. In his environment, 23 out of 436 worktrees are in a detached HEAD state, making this a non-trivial edge case. He suggests that a configurable scope (shared ref, per-branch, or per-worktree) could unify the two approaches, allowing detached worktrees to opt into per-worktree isolation while others use branch-aware filtering.

Vladimir also reiterates that the current workaround—using `git stash create` and manually managing refs under `refs/worktree/`—is cumbersome and requires every tool to reimplement it, which is why the problem persists in practice. He expresses willingness to implement whichever direction the maintainers prefer, signaling that the discussion is now focused on design trade-offs rather than feasibility. The thread remains in the RFC stage, with no clear consensus yet on whether the solution should prioritize branch-awareness, worktree-awareness, or a hybrid approach.
