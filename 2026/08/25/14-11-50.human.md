This is the first patch in Patrick Steinhardt’s 8-patch series refactoring how Git handles object database (ODB) alternates during repository creation. The patch defers initialization of the object database in `git clone` to a later point, after the repository’s URI has been fully resolved.

The motivation is twofold. First, some ODB backends (particularly alternate backends) may need to know the object hash format upfront, which isn’t available during early repository setup. Second, and more immediately, the patch prepares for a later change in the series where alternates will be written as part of repository creation rather than as a separate step. Currently, `git clone --reference` writes alternates after the ODB is initialized, but this requires resolving the repository’s URI twice—once before and once after repository initialization—because the URI might be rewritten by configuration in the cloned repository. Deferring ODB initialization until after URI resolution avoids this awkwardness.

The patch introduces a new flag, `INIT_DB_SKIP_ODB`, which makes `init_db()` skip ODB initialization. It also exposes `create_object_database()` as a public function so it can be called later. In `builtin/clone.c`, the ODB is now created after URI resolution and before setting up references, ensuring alternates can be written at the right time.

This is a clean, mechanical refactoring with no user-visible behavior changes. The commit message clearly explains the rationale and ties the change to the broader ODB abstraction effort. Reviewers will likely focus on whether the deferred initialization introduces any edge cases or regressions in clone behavior, particularly around URI resolution and alternate handling. The patch is well-structured and appears uncontroversial.
