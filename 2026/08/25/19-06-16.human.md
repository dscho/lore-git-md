This is a performance optimization for `git push` from shallow clones, updating the v1 patch Elijah Newren sent earlier in the thread. The core problem remains: when pushing from a shallow repository, Git often resends the entire toplevel tree (gigabytes in large repos) even for tiny changes, because it walks back to shallow grafts and assumes the server lacks them. The v2 patch introduces a new config option, `push.shallowExcludeBoundary`, defaulting to `true`, which tells `send-pack` to treat shallow grafts as uninteresting tips during pack generation, avoiding the redundant transfer.

The implementation is largely unchanged from v1, but Elijah has incorporated minor feedback from Patrick Steinhardt: marking input-only parameters as `const` and combining loops over `refs` for efficiency. The patch still adds a helper function, `append_reachable_shallow_grafts()`, that walks from pushed tips to their shallow grafts, adding those grafts to the pack boundary as negative tips. It stops early at any commit the server already has, keeping the walk short for deeper clones. The rare case where a server is being seeded with new shallow roots (requiring the full tree) can opt out by setting the config to `false`.

The test coverage in `t5538-push-shallow.sh` has expanded significantly, now including edge cases like a rejected ref not over-excluding objects needed by an accepted ref, and the interaction with `receive.shallowUpdate`. The commit message is thorough, explaining the motivation, the tradeoffs, and the backward-compatibility story, and now explicitly addresses why `push.negotiate=true` is not a complete solution. This looks like a well-crafted fix for a real-world performance pain point, with the v2 patch addressing the minor implementation feedback while maintaining the original design.
