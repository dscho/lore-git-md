This is a follow-up in the ongoing discussion about Elijah Newren’s patch to improve `git push` performance from shallow clones. Elijah responds to Patrick Steinhardt’s proposal to enable `push.negotiate` by default (or conditionally for shallow clones) with a detailed rebuttal, arguing that while `push.negotiate` helps in some cases, it does not fully solve the problem.

Elijah outlines four scenarios where `push.negotiate` falls short: (a) shallow clones of rebased pull requests where the shallow graft is no longer common, (b) pushing from one shallow clone to a different repository where the graft isn’t shared, (c) users who explicitly disable `push.negotiate`, and (d) setups where `push.negotiate` silently fails due to protocol limitations (e.g., SSH environments that don’t support Git protocol v2, or corporate policies blocking environment variables). He also notes that `push.negotiate` is not universally supported—BitBucket and some GitLab installations default to protocol v0 over SSH, and Windows tools like PuTTY may not allow sending the required environment variables.

While Elijah acknowledges the benefits of `push.negotiate` and even suggests making it the default for large repositories, he maintains that his patch is still necessary to fully address the redundant tree-transfer problem. He also mentions plans to split his follow-up work on shallow graft handling into two series: one for `rebase`/`revert`/`am` and another for broader shallow graft improvements.

The discussion remains constructive, with both contributors exploring trade-offs between latency (Patrick’s proposal) and bandwidth savings (Elijah’s patch).
