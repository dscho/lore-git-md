Patrick Steinhardt’s eight-patch series refactoring ODB alternates handling during repository creation is now technically complete and under review, with the lockfile API adoption in the sixth patch resolving the primary blocker raised by Junio C Hamano in the first version. The series removes the ability to write ODB alternates after repository creation, simplifying the ODB interface by consolidating alternates setup into a single step during ODB creation. This change is part of the ongoing ODB abstraction effort, preparing for alternates to become an implementation detail of the ODB backend.

The refactoring defers ODB creation in `git clone` until after the clone source URI is resolved, ensuring alternates are written with full context, including any URI rewrites from template `.git/config` files. Patches 1-5 consolidated alternates logic into a new `collect_alternates()` function, fixed a latent bug in worktree alternates handling, and removed manual alternates updates in `clone_local()`. Patch 6 introduced `odb_create_on_disk_options` to write alternates during ODB creation using Git’s standard lockfile API, resolving TOCTOU race and concurrent access concerns. Patch 7 wired up the new mechanism in `cmd_clone()`, and patch 8 removed the now-unused `write_alternates()` infrastructure. The series touches `builtin/clone.c`, `setup.c`, ODB backend files, and test coverage in `t/t5604-clone-reference.sh`, with no user-visible behavior changes.

Justin Tobler’s recent review of the sixth patch raises a forward-looking design question about the ODB interface’s exposure of alternates to backends that may not use them. He asks whether `git clone --shared` and similar options should be restricted to the "files" backend or left to the backend’s discretion, probing the interface’s long-term flexibility. This is a thoughtful architectural question that does not challenge the patch’s correctness but may influence future iterations of the ODB abstraction work. The series itself remains technically ready, with all substantive feedback addressed, and is expected to proceed to integration once the remaining ODB-focused contributors (e.g., Karthik Nayak) have reviewed patches 6-8.
