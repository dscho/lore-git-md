Patrick Steinhardt’s eight-patch series to refactor how Git handles ODB alternates during repository creation is nearing completion after addressing a key correctness issue. The goal is to simplify the ODB interface by removing the ability to write alternates after repository creation, consolidating the logic into a single step during ODB setup. This prepares the ground for alternates to become an implementation detail of the ODB backend, giving backends more control over their configuration.

The series has been under review, with patches 1–5 refactoring reference handling in `git clone` and fixing a latent bug in worktree alternates handling. Patch 6 introduced the core change—writing alternates during ODB creation via a new `odb_create_on_disk_options` struct—while patch 7 removed the last manual alternates writing step in `cmd_clone()`. The final patch, 8/8, proposed removing the now-unused `write_alternates()` infrastructure, but this sparked a discussion about locking. Toon Claes pointed out that the new implementation lacked lockfile protection, risking corruption if multiple processes (e.g., concurrent `git clone` operations) wrote to the same `info/alternates` file. Patrick acknowledged the oversight and agreed to adopt Git’s standard lockfile API in the next iteration, resolving Junio C Hamano’s earlier concern about TOCTOU races. This fix will likely appear in `v3` of the series, with no major delays expected.

The series is part of Patrick’s broader ODB abstraction effort and builds on earlier work like `ps/odb-eagerly-load-alternates`. While the refactoring is largely mechanical, the locking issue highlights a subtle but critical safety requirement. The resolution ensures the new design is robust, and the series is now poised to land once the lockfile integration is finalized. No other open questions remain, and the changes should be transparent to users, with no visible behavior changes.
