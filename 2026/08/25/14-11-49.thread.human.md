This thread is Patrick Steinhardt’s 8-patch series refactoring how Git handles ODB alternates during repository creation, part of the broader ODB abstraction effort. The goal is to simplify the ODB interface by removing the ability to write alternates after repository creation, consolidating alternates setup into a single step during ODB creation. The series has been under review, with all patches now posted, and the first five focused on refactoring reference handling in `git clone` and fixing a latent bug in worktree alternates handling.

The core change arrived in patch 6, which introduced `odb_create_on_disk_options` to write alternates during ODB creation, eliminating the need for a separate `write_alternates()` callback. Patch 7 wired this up in `cmd_clone()`, and patch 8 removed the now-unused `write_alternates()` infrastructure. Toon Claes provided surface-level reviews on earlier patches but raised a substantive concern in the final patch: the new implementation omits the lockfile mechanism that previously protected alternates file updates, potentially introducing race conditions during concurrent repository creation. This question directly challenges the correctness of the refactoring and may prompt a rethink of the locking strategy or a justification for why it’s no longer needed.

The series touches several subsystems—ODB, alternates handling, repository creation, and worktree handling—and introduces new symbols like `INIT_DB_SKIP_ODB`, `create_object_database()` (now public), and `odb_create_on_disk_options`. Tests in `t/t5604-clone-reference.sh` verify the fix for worktree clones and relative path resolution, but the locking concern remains unresolved. The series is built on `ps/odb-eagerly-load-alternates` and is foundational for making alternates an ODB backend implementation detail. Further review from ODB-focused contributors (e.g., Justin Tobler, Karthik Nayak) is likely, particularly around the implications of removing the lockfile and whether the new design is safe under concurrent access.
