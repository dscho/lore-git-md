This is the sixth and final patch in brian m. carlson’s RFC series proposing a Git 3.0 breaking change: restricting hex object IDs to lowercase only. The patch itself is minimal—it flips the enforcement switch by defining `HEX_KIND_OID` as `HEX_KIND_LOWER` when `WITH_BREAKING_CHANGES` is enabled, documents the change in `Documentation/BreakingChanges.adoc`, and adds test coverage to verify rejection of uppercase object IDs.

The email is a review reply from Phillip Wood, who asks for clarification on the security implications of allowing uppercase hex object IDs. Specifically, he wants to know why `ABCDEF` is a security risk when `abcdef^0` (the same object) is not. This is a substantive question that cuts to the heart of the series’ motivation. The answer will likely shape whether the project accepts the breaking change: if the security rationale is weak or speculative, the case for disrupting existing workflows weakens; if the risks are concrete and well-documented, the argument for enforcement strengthens.

Phillip’s question is narrow but pivotal. It does not engage with the implementation (which is already complete and uncontroversial) but challenges the core justification. The thread remains in RFC limbo, with Junio’s tentative “Will queue” signaling movement toward integration, but no final decision. This reply is the first substantive pushback on the motivation itself, and brian’s response will be critical in determining whether the series advances or stalls. The patch is otherwise ready—clean, well-tested, and gated behind the breaking-changes flag—but the security rationale is the last open question.
