This is the first patch in brian m. carlson’s RFC series proposing a Git 3.0 breaking change to enforce lowercase-only hex object IDs. The series aims to address security and compatibility issues caused by Git’s current case-insensitive parsing, and this patch lays the groundwork without altering runtime behavior.

The patch introduces a new `hex_kind` enum and a lowercase-only hex lookup table (`hexval_lc_table`), then updates the `hexval()` function to accept an `enum hex_kind` parameter. Existing call sites in `color.c` and `pkt-line.c` are refactored to use the new infrastructure, but the patch deliberately preserves the current behavior by defaulting to the mixed-case variant. The change is mechanical and preparatory, touching only internal APIs (`hex-ll.c`, `hex-ll.h`) and two call sites, with no user-visible impact.

Junio’s review was surface-level, catching only a trivial typo in the comment (68-67 → 68-6f) and noting the lateness of his feedback. The typo is uncontroversial and will be fixed in a reroll, but the review did not engage with the patch’s substance or the series’ broader questions—whether the project will accept the breaking change, or whether the security rationale holds. Those discussions remain unresolved in the thread.

This patch is well-crafted and clearly motivated, but its significance lies entirely in what comes next: the later patches that will enforce lowercase-only parsing for object IDs. For now, it’s infrastructure-only, and the thread’s open questions—particularly Phillip Wood’s challenge to the security justification and Junio’s ambivalence about the breaking change—will determine whether the series advances. If you’re tracking Git 3.0 planning or security-related changes, this is worth monitoring, but the patch itself doesn’t yet change anything.
