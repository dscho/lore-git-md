This is a follow-up in the ongoing RFC thread about making Git's stash stack branch-aware or worktree-aware to prevent silent interference between worktrees. The author, Vladimir Sitnikov, responds to feedback from Kristoffer Haugsbakk, Phillip Wood, and Junio C Hamano, refining the problem and evaluating the proposed branch-aware design.

Vladimir clarifies that the issue isn't just about explicit `git stash` commands but also about operations like `git rebase --autostash`, which create stash entries without the user invoking `git stash` directly. Since `rebase.autoStash` is stored in the shared `.git/config`, one worktree can enable it for all, making it impossible to ban stash usage via a wrapper script. This reinforces the original motivation: the problem isn't just theoretical but affects real workflows, including automated agents.

He then engages with Phillip Wood's branch-aware proposal, which would associate stashes with the branch they were created on. Vladimir notes this works well for worktrees on branches (since Git prevents checking out the same branch in multiple worktrees) but falls short for detached HEAD states, where all stashes are recorded as `"On (no branch):"`. In his environment, 23 out of 436 worktrees are detached, making this a non-trivial edge case. He suggests a configurable scope (shared ref, current branch, or per-worktree ref) as a unifying solution, allowing users to choose the behavior that fits their workflow.

The email also acknowledges Junio's suggestion of using `git stash create` and storing the OID under `refs/worktree/` as a workaround, but Vladimir points out this requires every tool to reimplement the logic, which isn't practical. The tone is collaborative, offering to write or test patches for whichever direction the maintainers prefer. The discussion remains at the design stage, with no clear consensus yet on the best approach.
