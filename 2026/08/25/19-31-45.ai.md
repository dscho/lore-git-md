This is the seventh and final patch in the **`[PATCH v5]` series** adding seven new path-related keys to `git repo info`. The patch implements `path.cdup`, the inverse of `path.git-prefix`, completing the relative-path key set and resolving the last open design question from earlier iterations. Junio C Hamano’s reply raises a **substantive architectural concern**: the duplication of logic between `git repo info` and `git rev-parse`, specifically for `path.cdup` and other keys that mirror existing `rev-parse` functionality.

Junio suggests consolidating the shared logic into a new helper library (e.g., `repo-info.c` at the top level) to avoid maintaining parallel implementations of features like `cdup`. This critique applies broadly to the series, as several of the new `path.*` keys (`path.toplevel`, `path.superproject-root`, `path.git-prefix`, and now `path.cdup`) replicate functionality already present in `git rev-parse` or other built-ins. The concern is not about the correctness of the implementation but about long-term maintainability and code hygiene. While the current patch is mechanically sound and the tests are thorough, addressing this feedback would require a non-trivial refactor of the series, potentially splitting the shared logic into a new file and updating both `builtin/repo.c` and `builtin/rev-parse.c` to use it.

The patch itself remains uncontroversial in its design and behavior: `path.cdup` returns the relative path from the current directory to the top-level working tree (e.g., `../../` in a subdirectory, empty string at the root), matching `git rev-parse --show-cdup`. The implementation is self-contained, and the tests cover both root and subdirectory cases. However, Junio’s feedback shifts the focus from the patch’s immediate functionality to its place in the broader codebase, raising a question about whether the series should have been structured differently from the outset. This is a **substantive review** that could lead to a v6 or a follow-up series to address the duplication.
