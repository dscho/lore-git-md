This is a maintainer review of Nikita Leshenko's bugfix for `git am --3way`. Junio C Hamano identifies a significant performance problem with the proposed solution: if a 50-patch series applies cleanly, the patch would spawn 49 extra `git apply --build-fake-ancestor` processes, write and unlink 49 temporary index files, perform 49 in-core patch applications, and generate unneeded loose objects in the object database. He calls this overhead "simply unacceptable" and suggests a lazy reconstruction approach instead.

Junio outlines an alternative design: when `fall_back_threeway()` fails to find a preimage blob, it should inspect the already-applied patches in `.git/rebase-apply/` to reconstruct the necessary preimage blob in-core, applying only the relevant patches from the chain. This would avoid the per-patch overhead while still enabling 3-way merges for subsequent patches. The approach would incur no additional overhead when patches apply cleanly or when the necessary blobs already exist.

The review is substantive and technical, focusing on algorithmic efficiency and resource usage. Junio's suggestion is a clear counterproposal that addresses the same edge case without the performance penalty. The ball is now in Nikita's court to either revise the patch or argue why the lazy approach is infeasible. No merge status or maintainer decision has been made yet. Key technical details to track in follow-up discussion: the `.git/rebase-apply/` directory, in-core patch application, and blob reconstruction logic.
