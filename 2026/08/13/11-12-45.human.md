This is a **packfile performance bugfix** targeting a severe regression in `git rev-parse --short HEAD` when repositories accumulate tens of thousands of packfiles. The thread has reached a key milestone: Patrick Steinhardt, who previously proposed a more ambitious hashmap-based refactoring, now explicitly endorses Johannes Schindelin’s fast-path optimization as the immediate solution. The patch is poised to advance, with no remaining technical objections and a clear path forward.

The core issue—a quadratic-time performance regression introduced in Git v2.53 (commit `589127caa730`)—manifests in Microsoft Git Scalar’s shared cache repositories, where scheduled fetches outpace maintenance, leaving repositories with 38,000+ packfiles. Johannes’s patch adds a `skip_dup_check` parameter to `packfile_list_append()`, allowing callers to bypass duplicate checks when they can guarantee the packfile is new. This eliminates the O(N²) scan for those cases, restoring linear-time behavior. The parameter was renamed from `is_new` to better reflect its purpose, addressing Patrick’s earlier critique about ambiguity.

Patrick’s hashmap counterproposal, while more comprehensive, is now acknowledged as a longer-term effort. He concedes that skipping the search entirely (Johannes’s approach) is faster than even an O(1) hashmap lookup, and agrees the fast-path patch should land first. His intent to pursue the hashmap refactoring independently remains, but it no longer blocks this fix.
