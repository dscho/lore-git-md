This is the final patch in Christian Couder’s five-part series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators mark repositories as trusted for lazy fetching. The patch wires up the logic: when the served repository is listed in the allowlist, `upload-pack` sets `GIT_NO_LAZY_FETCH=0` in its environment, enabling lazy fetching for itself and its `pack-objects` child process.

The implementation is straightforward. The patch checks whether `GIT_NO_LAZY_FETCH` was already set; if not and the repository is trusted, it flips the variable to `0`. This happens early in `cmd_upload_pack()`, after the repository is opened but before protocol negotiation, so the setting applies to the entire session. The patch also adds comprehensive documentation in `git-upload-pack.adoc`, `git.adoc`, and a new section in `uploadpack.adoc` that explains the security model, syntax, and scope rules. Four new tests in `t/t5710-promisor-remote-capability.sh` verify that lazy fetching works when the repository is trusted, fails when it is not, ignores unprotected configuration, and respects an explicit `GIT_NO_LAZY_FETCH=1` override.

The patch completes the series’ pivot from the earlier client-side `fromAccepted` proposal to a server-side trust model. It directly addresses the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration by ensuring that only repositories explicitly listed in protected configuration can enable lazy fetching. The design is opt-in, backward-compatible, and modeled after Git’s existing `safe.directory` mechanism. No on-disk format changes are introduced, and the feature works across all protocol versions. The series is now functionally complete and ready for review; the unresolved objection from brian m. carlson remains the main open question, but the server-side trust model should satisfy it.
