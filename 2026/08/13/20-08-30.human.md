This is the final patch in the v5 series introducing `git repack --drop-filtered` for partial clones. It adds two safety guards to prevent the command from running in unsafe or counterproductive scenarios, both skipped for bare repositories.

The patch implements checks to block `--drop-filtered` during ongoing operations (merge, rebase, am, cherry-pick, revert, or bisect) and when the current index references any blob slated for removal. The first guard avoids surprising network fetches mid-operation, while the second prevents immediate re-fetching of blobs needed by the working tree. Both are framed as UX optimizations rather than correctness measures, since lazy-fetching would transparently restore dropped objects.

The implementation uses `wt_status_get_state()` to detect ongoing operations and `repo_read_index()` to validate the index, with clear error messages listing all blocked operations explicitly. The documentation update explains these guards and their rationale, noting they are skipped in bare repositories. The test script (`t/t7706-repack-drop-filtered.sh`) covers both scenarios: a merge-in-progress and an index-referenced blob, verifying the command fails with the expected error messages.

This patch completes the series, which is now technically sound and ready for maintainer review. The safety guards address feedback from earlier iterations and align with the series' goal of providing a safe, user-friendly way to reclaim disk space in partial clones. No further changes are expected unless reviewers identify new issues.
