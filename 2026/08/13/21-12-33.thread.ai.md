Subject: [PATCH] t1401: add tests for `git symbolic-ref` exit codes and output with non-symbolic refs
Series version: standalone patch (v2)
Originating author: Nikolaus Schuetz
Thread type: patch (test coverage addition)

Core problem or goal
Add systematic test coverage for `git symbolic-ref`'s exit codes and output behavior when querying a non-symbolic ref, both with and without the `--quiet` (`-q`) flag. The patch documents the current behavior—exit code 128 without `--quiet`, exit code 1 with `--quiet`, and empty stdout in both cases—but the thread has evolved to question whether this design is intentional or a quirk worth revising. The motivation remains to fill a gap in test coverage for edge cases relied upon by existing tests (e.g., `t2020`, `t5621`).

Current status
Under review; second iteration (v2). Changes since v1: added a test to verify stdout is empty in both cases (addressing Patrick Steinhardt's review suggestion) and expanded the commit message to clarify the motivation and technical rationale. The patch touches only `t/t1401-symbolic-ref.sh`, adds three new tests, and introduces no new functionality or on-disk format changes. The technical explanation for the exit code behavior (consistency with `die()` and other Git commands) has been provided, but Patrick Steinhardt has now explicitly challenged the intentionality of the design, proposing either to avoid testing the exit codes or to align them (preferring the latter).

Key technical details
- Files touched: `t/t1401-symbolic-ref.sh` (test script)
- New test names: (implicit in script) `git symbolic-ref exits with 128 and error on non-symbolic ref`, `git symbolic-ref --quiet exits with 1 and no error on non-symbolic ref`, and a new test verifying stdout is empty in both cases
- Subsystem: refs (symbolic-ref plumbing)
- New symbols: none
- On-disk format changes: none
- Test coverage: edge-case behavior of `git symbolic-ref` with non-symbolic refs, including exit codes, error output, and stdout emptiness. The tests explicitly verify behavior that existing tests (e.g., `t2020`, `t5621`) rely on but do not test directly. The current implementation uses `die()` (exit 128) for the non-quiet path and `exit(1)` for the quiet path.

Open questions and loose ends
1. **Design consensus**: Is the differing exit code behavior (128 vs. 1 with `--quiet`) intentional or an oversight? Patrick Steinhardt argues it likely reflects an oversight, as the non-quiet path uses `die()` (returning 128) while the quiet path uses `exit(1)`, and suggests aligning the exit codes to 128 in both cases by changing the quiet path to use `die(NULL)`. Nikolaus Schuetz had previously defended the behavior as consistent with `die()` and other Git commands, but no consensus has emerged.
2. **Follow-up work**: If the current behavior is deemed unintentional, a follow-up patch may be proposed to align the exit codes (e.g., by changing the quiet path to use `die(NULL)`). If the behavior is preserved, the tests will codify it as-is.
3. **Test scope**: Whether to test the exact exit codes at all, given Patrick's alternative proposal to rely on existing implicit coverage.
