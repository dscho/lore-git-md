Subject: [PATCH] t1401: add tests for `git symbolic-ref` exit codes and output with non-symbolic refs
Series version: standalone patch (v2)
Originating author: Nikolaus Schuetz
Thread type: patch (test coverage addition)

Core problem or goal
Add systematic test coverage for `git symbolic-ref`'s exit codes and output behavior when querying a non-symbolic ref, both with and without the `--quiet` (`-q`) flag. The patch documents the current behavior—exit code 128 without `--quiet`, exit code 1 with `--quiet`, and empty stdout in both cases—but the thread has converged on treating this design as likely unintentional rather than intentional. The motivation remains to fill a gap in test coverage for edge cases relied upon by existing tests (e.g., `t2020`, `t5621`). Phillip Wood has now introduced a new perspective, suggesting the exit code discrepancy may have been intentional to allow scripts to distinguish between invalid options (exit 128) and non-existent refs (exit 1), drawing a parallel with `git rev-parse --quiet --verify` and `git show-ref --quiet --verify`.

Current status
Under review; second iteration (v2). Changes since v1: added a test to verify stdout is empty in both cases (addressing Patrick Steinhardt's review suggestion) and expanded the commit message to clarify the motivation and technical rationale. Junio C Hamano and Patrick Steinhardt have both weighed in, agreeing the differing exit codes likely reflect an oversight and endorsing either avoiding testing the exact exit codes or aligning them (Junio prefers the former, Patrick the latter). Phillip Wood's reply challenges this consensus, arguing the behavior may serve a useful purpose for script-level error differentiation. The patch touches only `t/t1401-symbolic-ref.sh`, adds three new tests, and introduces no new functionality or on-disk format changes. The technical explanation for the exit code behavior (consistency with `die()` and other Git commands) has been provided but is no longer the sole consideration.

Open questions and loose ends
1. **Design resolution**: The thread now has three distinct viewpoints:
   - Junio and Patrick favor treating the differing exit codes as an oversight and either avoiding testing them or aligning them (Junio prefers avoiding tests, Patrick prefers alignment).
   - Nikolaus documents the status quo but is open to revisiting it.
   - Phillip Wood suggests the behavior may be intentional and useful for script-level error differentiation, challenging the consensus.
   The question remains whether to (a) preserve the current behavior (and test it), (b) align the exit codes (and update tests accordingly), or (c) avoid testing the exit codes to prevent overspecification. No resolution or follow-up patch has been proposed yet.
2. **Test scope**: If the exit code tests are preserved, the patch may proceed as-is. If the exit codes are aligned, the tests may be updated to reflect the new behavior. If the exit codes are avoided, the patch may be revised to test only stdout emptiness.
3. **Follow-up work**: If the exit codes are aligned, a follow-up patch will be needed to change the quiet path to use `die(NULL)` instead of `exit(1)`. If the behavior is preserved, no follow-up is required beyond the current patch.
