This is a v2 feature series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The series is a direct response to the security objections raised against the earlier `GIT_NO_LAZY_FETCH=fromAccepted` proposal, replacing it with a server-controlled trust model modeled after Git’s `safe.directory` configuration.

The core idea is to shift trust decisions entirely to the server operator. By setting `uploadpack.lazyFetchTrusted` in global or system scope, operators can declare which repositories are safe to lazy-fetch from, addressing the primary security concern that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration. The served repository itself cannot influence the setting, and relative paths (including single-dot paths) are rejected. When the served repository is trusted, `GIT_NO_LAZY_FETCH=0` is set in the environment, permitting `upload-pack` and its `pack-objects` child to lazily fetch objects as needed.

The series consists of five patches. Patch 1 is a refactoring carried over from the previous series, extracting `lazy_fetch_objects()` from the promisor-remote code to improve clarity and efficiency. Patches 2 and 3 generalize the `safe.directory` allowlist machinery into a reusable `path_allowlist_apply()` helper, adding an `allow_dot` argument to handle repository paths. Patch 4 reads the new configuration variable from protected files only, and patch 5 wires it into `upload-pack` to disable `GIT_NO_LAZY_FETCH` (i.e., permit lazy fetching) only for trusted repositories. The implementation touches the promisor-remote subsystem, `setup.c`, documentation, and adds a new test script (`t/t5710-promisor-remote-capability.sh`) covering four scenarios: trusted repository, untrusted repository, configuration ignored if set in the repository’s own config, and explicit `GIT_NO_LAZY_FETCH=1` overriding the trusted setting.

The v2 iteration resolves the mechanical submission blocker from v1 by re-sending the series with correct threading and version numbering, and fixes the Signed-off-by email address to match the primary address in `.mailmap`. The series maintains backward compatibility: the default behavior remains unchanged (lazy fetching disabled by default), and the new configuration is opt-in. It targets both protocol v0/v1 and v2, unlike the earlier `fromAccepted` proposal which was v2-only, and introduces no on-disk format changes.

The unresolved security objection from brian m. carlson—who argued that any expansion of lazy-fetching flexibility increases exposure to untrusted repositories—remains relevant but is now addressed by the server-side trust model. Whether this satisfies the objection will likely be the central point of discussion. The series also defers usability improvements (e.g., a configuration variable instead of an environment variable) to future work, focusing first on establishing the trust mechanism. No substantive technical review feedback has been received yet beyond the security objection.
