This is a bug report about mtime handling during `--autostash` operations.

The author, Jos van den Oever, reports that when `git pull`, `git merge`, or `git rebase` are used with `--autostash`, the mtime (modification time) of files restored via `stash apply` is incorrectly set to the current time, even if the file content was unchanged. Normally, Git preserves the original mtime of files when writing them, which is important for build systems that rely on mtime to determine whether to rebuild. The `--autostash` workflow presents an opportunity to restore the original mtime of dirty files, but currently fails to do so.

The report highlights two practical consequences: (1) unnecessary rebuilds triggered by build systems, and (2) disruption to automated systems that use mtime as a proxy for commit author dates. The author suggests that Git should track and restore the original mtime of dirty files during `--autostash` operations.

No patch is provided; this is a feature request or bug report framed as a behavioral inconsistency. The affected commands are `git pull`, `git merge`, and `git rebase` when combined with `--autostash`. The key technical detail is the interaction between `stash apply` and filesystem mtime attributes. The report does not reference prior discussion or related work, so this appears to be a new observation.
