This is the first patch in a six-part series introducing `git repack --drop-filtered`, a new feature for partial clones that allows users to reclaim disk space by safely removing locally cached promisor blobs exceeding a specified size threshold. This patch adds the `--drop-filtered` and `--dry-run` command-line options to `git repack`, along with all the necessary validation logic, but does not yet implement the actual object enumeration or deletion.

The patch enforces several preconditions: `--drop-filtered` requires `--filter` (currently limited to `blob:limit`), `-a`, and a configured promisor remote, and is incompatible with `--filter-to` and explicit `-b`/`--write-bitmap-index`. The bitmap incompatibility is handled carefully: an explicit `-b` on the command line is rejected as a conflict, while a config-driven `repack.writeBitmaps` setting is silently disabled for the duration of the command. The `--dry-run` option is only meaningful when used with `--drop-filtered` and is kept separate to maintain consistency with other Git commands and allow future expansion.

The implementation touches `builtin/repack.c` and introduces a new test script (`t/t7706-repack-drop-filtered.sh`) that covers all validation scenarios, including the bitmap-handling edge case. The patch is well-scoped and addresses the feedback from earlier revisions, particularly the bitmap validation fix that distinguishes command-line vs config-driven settings. The commit message clearly states that the actual deletion logic will follow in later patches, making this a clean, atomic addition.

This is a feature patch targeting the repack machinery and partial clone subsystem, and it looks technically sound. The validation logic is thorough, the test coverage is comprehensive, and the patch aligns with the series' overall goal of providing a safe, user-controlled way to reclaim disk space in partial clones.
