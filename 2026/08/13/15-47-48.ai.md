This is the final patch (5/5) in Christian Couder’s `uploadpack.lazyFetchTrusted` series, which implements the core behavior: when the served repository is listed in the protected `uploadpack.lazyFetchTrusted` configuration, `upload-pack` sets `GIT_NO_LAZY_FETCH=0` in its environment, enabling lazy fetching for itself and its `pack-objects` child process.

The patch wires the trust check (introduced in patch 4) into `cmd_upload_pack()`. It first saves the current value of `GIT_NO_LAZY_FETCH`, then unconditionally sets it to `1` (the default). If the repository is trusted *and* the variable was not explicitly set by the caller, it relaxes the restriction by setting it back to `0`. This ensures that an explicit `GIT_NO_LAZY_FETCH=1` from the environment always wins, preserving the security boundary.

Documentation is updated in three places: `git-upload-pack.adoc` gains a cross-reference to the new configuration, `git.adoc` adds a brief mention of the server-side control, and `Documentation/config/uploadpack.adoc` receives a detailed 42-line entry explaining the purpose, security implications, syntax, and scope of `uploadpack.lazyFetchTrusted`. The documentation emphasizes that the server operator—not the client—is responsible for ensuring that the promisor remotes of a trusted repository are themselves trustworthy.

The patch also adds a new test script (`t/t5710-promisor-remote-capability.sh`) with four test cases: (1) a successful clone when the repository is trusted, (2) a failure when it is not, (3) a demonstration that the configuration is ignored if set in the repository config (not protected), and (4) a check that an explicit `GIT_NO_LAZY_FETCH=1` overrides the trust setting. These tests verify the security model and the precedence rules.

The implementation is minimal and focused: no new plumbing is needed because `GIT_NO_LAZY_FETCH` is already passed through the environment to child processes. The patch completes the series by making the configuration actually do something, and the thorough documentation and tests suggest a well-considered design. Whether the server-side trust model satisfies the earlier security objection from brian m. carlson remains the open question, but this patch provides the mechanism for operators to make that call.
