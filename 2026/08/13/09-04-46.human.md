This is a **bugfix targeting the packfile subsystem**, specifically addressing a performance regression in `git rev-parse --short HEAD` (commonly used in shell prompts) when dealing with repositories containing thousands of packfiles. The patch itself was previously summarized, but this reply from Johannes Schindelin clarifies a key real-world deployment detail that affects whether the proposed code fix is the only viable solution.

Johannes explains that the reported slowdown occurs in *Microsoft Git Scalar* clones, a downstream fork with features not yet upstreamed to core Git. One such feature is the "shared cache repository" — a bare repository used as an alternate object store for fetches, which can accumulate a very high number of packfiles (sometimes in the tens of thousands). While `git maintenance` *does* run on these shared cache repos, it often fails to complete before the machine is shut down, leaving many packfiles in place. This context makes the code fix — which reduces the time complexity of packfile insertion from O(N²) to O(N) for new packfiles — more urgent and practical than relying solely on maintenance.

The reply also implicitly narrows the scope of the patch: it is not a general solution for all many-pack scenarios, but a targeted fix for a specific, high-impact use case in Microsoft’s environment. This clarification helps readers assess the patch’s relevance to their own workflows. If you’re not using Scalar or a similar setup with thousands of packfiles, the regression may not affect you — but the fix is still a clean, low-risk optimization that Junio has already endorsed as "clever and clean."

The discussion about maintenance as an alternative is now resolved: while repacking *could* help in theory, in practice it doesn’t run to completion often enough to prevent the problem. This leaves the code fix as the only reliable mitigation for the reported slowdown. The thread’s remaining open question is Patrick Steinhardt’s hashmap-based counterproposal, which would eliminate quadratic-time behavior entirely but at the cost of added complexity. Johannes hasn’t yet responded to that, so the design direction is still fluid. For now, the patch looks like a well-motivated, narrowly scoped fix that addresses a real pain point.
