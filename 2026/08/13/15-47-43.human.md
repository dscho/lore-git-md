This is a five-patch feature series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The series is a direct response to the security objections raised against an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`), replacing it with a model that shifts trust decisions entirely to the server operator.

The core idea is simple: operators set `uploadpack.lazyFetchTrusted` in global or system scope to declare which repositories are safe to lazy-fetch from. This sidesteps the earlier debate about client-side negotiation of promisor remotes by ensuring the served repository itself cannot influence the setting. The implementation reuses Git’s existing `safe.directory` machinery, generalizing it into a reusable `path_allowlist_apply()` helper that now supports rejecting relative paths (including single-dot paths). The new configuration is read only from protected files, and when the served repository is trusted, `GIT_NO_LAZY_FETCH=0` is set in the environment, permitting `upload-pack` and its `pack-objects` child to lazily fetch objects as needed.

Patch 1 is a carry-over from the earlier series, refactoring the promisor-remote code to extract a `lazy_fetch_objects()` helper. Patches 2 and 3 generalize the `safe.directory` allowlist logic into the new helper, adding an `allow_dot` argument to handle repository paths. Patch 4 reads the new configuration variable, and patch 5 wires it into `upload-pack` to disable `GIT_NO_LAZY_FETCH` (i.e., permit lazy fetching) only for trusted repositories. The series touches the promisor-remote subsystem, `setup.c`, documentation, and adds a new test script (`t/t5710-promisor-remote-capability.sh`) that validates the configuration and trust mechanism across four scenarios.

The series is well-motivated and addresses a real operational need in corporate environments where fine-grained control over lazy fetching is desirable. The implementation is clean, reusing existing patterns and avoiding on-disk format changes. Backward compatibility is maintained: the default behavior remains unchanged (lazy fetching disabled by default), and the new configuration is opt-in. The unresolved security objection from brian m. carlson—who argued that any expansion of lazy-fetching flexibility increases exposure to untrusted repositories—remains relevant but is now addressed by the server-side trust model. Whether this satisfies the objection will likely be the central point of discussion.
