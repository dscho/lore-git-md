This is the fourth patch in Christian Couder’s five-patch series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The patch wires up the configuration reading logic, completing the groundwork for the final patch (5/5) that will actually enable lazy fetching for trusted repositories.

The patch adds a new `upload_pack_lazy_fetch_trusted()` function that checks whether the repository being served is listed in the `uploadpack.lazyFetchTrusted` allowlist. It reuses the `path_allowlist_apply()` helper introduced in earlier patches, ensuring the configuration is read only from protected files (system or global scope) and rejecting relative paths (including single-dot paths) for security. The function returns a boolean indicating whether lazy fetching should be permitted for the current repository.

The implementation is straightforward and well-scoped: it touches only `upload-pack.c` and `upload-pack.h`, adding the new function and its internal plumbing. The commit message clearly explains the purpose and ties it to the series’ overall goal of shifting trust decisions to the server operator. No behavioral changes are introduced yet—this patch only exposes the configuration check for use in the next patch.

The patch looks clean and uncontroversial, assuming the earlier refactoring patches (1/5–3/5) are accepted. It directly addresses the security objection raised against the earlier client-side `GIT_NO_LAZY_FETCH=fromAccepted` proposal by ensuring the served repository cannot influence the setting. The only open question is whether the server-side trust model will satisfy brian m. carlson’s security concerns, but that discussion belongs to the series as a whole rather than this mechanical patch.
