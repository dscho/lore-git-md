This is a **bugfix reply** in the ongoing packfile performance regression thread, clarifying the real-world context of the reported slowdown and addressing Ben Knoble’s question about whether `git maintenance` could mitigate the issue.

Johannes Schindelin explains that the performance regression was observed in a *Microsoft Git Scalar* clone, a downstream fork with features not yet upstreamed to core Git. Specifically, Scalar uses a "shared cache repository" (a bare repository acting as an alternate for the actual clone) where scheduled fetches deposit packfiles. While maintenance *does* run on this shared cache, it often fails to complete before the machine is shut down, leaving repositories with tens of thousands of packfiles. This confirms that maintenance is not a reliable workaround for the regression in this environment, and the code fix remains necessary to handle such edge cases gracefully.

The reply also narrows the scope of the problem: the regression is tied to Scalar’s architecture, not a general Git issue. This does not diminish the patch’s value—Scalar is widely used at Microsoft—but it contextualizes why maintenance alone cannot solve the problem. Johannes’s tone suggests frustration with the downstream/upstream divergence but focuses on the technical justification for the fix. The thread’s open questions (Patrick Steinhardt’s hashmap counterproposal and test-coverage debates) remain unresolved, but this reply removes the maintenance workaround as a viable alternative for the reported scenario.
