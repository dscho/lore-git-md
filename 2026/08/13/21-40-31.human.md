This is the third patch in D. Ben Knoble’s three-part series converting Git’s build-time `USE_NSEC` macro into a runtime `core.useNanosec` configuration option. The series is under active review and a second version is imminent.

The core issue is architectural: where to cache the `core.useNanosec` setting so that the hot-path `is_racy_stat()` function does not repeatedly call `repo_config_get_bool()`. The author has already benchmarked a fix that restores performance to baseline (21 ms vs 20 ms) by caching the value, but the question remains whether to store it in `repo_config_values` (modern but currently limited to `the_repository`) or `repo_settings` (supports per-repository variation, e.g., for submodules). The author’s control-flow analysis and CI run show that the test suite does not exercise any code path that would populate `repo_config_values` with a repository other than `the_repository`. However, some public `libgit.a` interfaces appear in the call graph, suggesting that the limitation to `the_repository` is already a broader issue.

The email signals that the author is ready to post v2 shortly, using `repo_config_values` unless there is a strong objection. The tone is pragmatic: the CI results are good enough for now, and the author would prefer to land the change rather than wait for a full `the_repository` cleanup. The patch itself is small and focused, touching only the nanosecond-precision logic in `read-cache.c` and `statinfo.c`, with no on-disk format changes. The performance regression identified in v1 is resolved, and the remaining open question is purely about code organization. If you care about the `the_repository` removal effort or about racy-Git performance, this is worth watching.
