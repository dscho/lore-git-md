This is the second patch in Junio C Hamano’s three-patch v3 series fixing Bash completion for `git checkout`. It implements the core behavior change: when completing paths for `git checkout` (with or without `-C <dir>`), the completion now prioritizes **tracked paths** (files in the index) over untracked ones, addressing a long-standing usability gap where untracked files were inconsistently suggested.

The patch modifies `_git_checkout()` in `contrib/completion/git-completion.bash` to call `__git_complete_index_file ""` when revision reference completion (`__git_complete_refs()`) yields no matches or when `--` is present. This ensures only tracked paths are offered as completion candidates, aligning with `git checkout`'s purpose of operating on repository files. The change is minimal—just four lines added to the function—but it fixes a real-world annoyance: previously, if no revision matched the input (e.g., `git checkout f`), Bash would fall back to completing untracked files in `$PWD`, which was especially problematic when using `git -C <path>` (where `$PWD` is not the target repository).

Test coverage is thorough. The patch adds two new tests to `t/t9902-completion.sh`:
1. Verifies that `git checkout f` (and `git checkout -- f`) completes only tracked paths (`file1`, `file2`) when no refs match "f", ignoring untracked files.
2. Confirms that `git -C <path> checkout o` completes tracked paths in the specified repository (e.g., `otherfile`), not the current directory, and handles edge cases like missing files (`lostfile`).

The patch is uncontroversial and technically sound. It builds on the refactoring in patch 1/3 (which prepared the control flow) and sets the stage for patch 3/3’s fallback to untracked paths when no tracked paths match. The series as a whole is ready for integration, with no open questions or objections. The only prior feedback—Elijah Newren’s suggestion to include `--directory` in the fallback logic—was addressed in patch 3/3, not this one.
