This is the third patch in Elijah Newren’s four-patch v3 series fixing a race condition in Git’s geometric repacking mechanism. It removes the `OBJECT_INFO_QUICK` flag from `git mktree --batch` to prevent it from incorrectly reporting objects as missing when they have been repacked into a new packfile by a concurrent process.

The issue arises because `OBJECT_INFO_QUICK` skips the "reprepare-and-retry" step that reloads the on-disk pack set, leaving a long-running `git mktree --batch` process with a stale view of available packs. When a concurrent repack moves an object into a new pack, the resident `mktree` process fails to find it and rejects the entry. The patch replaces `OBJECT_INFO_QUICK` with `OBJECT_INFO_SKIP_FETCH_OBJECT` (which already avoids promisor fetches) so that `mktree` can recover from repacks by reloading the pack set.

The patch is small and focused: it removes a single flag from `builtin/mktree.c` and adds a 48-line regression test in `t/t1010-mktree.sh`. The test simulates a resident `mktree --batch` process reading trees over a FIFO while a concurrent repack removes a pack’s `.idx` file, verifying that the process can still resolve objects after the repack. The test is well-constructed and covers the exact scenario that motivated the fix.

This patch directly addresses feedback from Jeff King (Peff), who argued that `OBJECT_INFO_QUICK` was being misused in `git mktree --batch` and that the correct fix was to remove it rather than adding recovery logic for `QUICK` readers. The change is minimal, uncontroversial, and aligns with the broader goal of the series: ensuring that object lookups remain correct even when the on-disk pack set changes mid-operation. The test coverage is thorough and should prevent regressions.

The patch is part of a well-motivated series that fixes a real production issue affecting server-side operations like `git replay`. It is ready for integration and should not require further changes.
