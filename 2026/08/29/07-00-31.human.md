This is the final patch in a well-crafted four-part bugfix series addressing a race condition in Git's geometric repacking mechanism. The issue causes objects to be incorrectly reported as missing when a multi-pack-index (MIDX) references a packfile that has been removed by a concurrent repack, leading to crashes in `git replay` and missing-object errors in other operations like `git merge-tree`, `git diff`, and `git rev-list`.

This patch implements the core recovery mechanism. When a MIDX lookup fails because the pack it references is gone, the code now scans all packs covered by the MIDX to find a surviving copy of the object. The fix is carefully optimized: the rescan only happens on the second read (triggered by `OBJECT_INFO_SECOND_READ`), ensuring that objects merely relocated to a new pack are found by the cheaper on-disk reload, while only genuine hidden duplicates trigger the more expensive MIDX scan. The function `fill_midx_entry()` has been renamed to `midx_fill_entry()` and now returns a tri-state enum (`MIDX_FILL_MISS`, `MIDX_FILL_HIT`, `MIDX_FILL_OWNER_UNAVAILABLE`) to clearly distinguish between different failure modes.

The patch touches the packed-object backend (`odb/source-packed.c`), MIDX internals (`midx.c` and `midx.h`), and adds thorough test coverage in `t/t5319-multi-pack-index.sh`. It is the culmination of several rounds of substantive review, particularly from Jeff King (Peff), who helped refine the tri-state design and the `SECOND_READ`-gated fallback. The series is now merge-ready, with all prior feedback addressed and no unresolved technical disagreements. The only minor loose ends are cosmetic (error message clarity and a potential follow-up to reduce the race condition's frequency by deferring pack deletion), neither of which are blockers. This is a high-quality fix for a real production issue, and it should be uncontroversial.
