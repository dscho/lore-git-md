This is a follow-up in the ongoing discussion about adding a `--hard` or `--reset` mode to `git pull`. Junio C Hamano, the maintainer, responds to Artur Bieniek’s proposal of an alternative design (`git reset --pull --hard`) by suggesting that the desired functionality—fetching the upstream branch and resetting the working tree to it—might be better implemented as a **user-defined Git alias** rather than a built-in command.

Junio’s reply sidesteps the technical merits of the proposed designs and instead frames the issue as one of **scope and philosophy**: Git’s core commands should remain focused on their primary responsibilities (`pull` for integrating history, `reset` for local state management, `fetch` for network operations), and convenience features that combine these operations should live in user configuration. This aligns with his earlier objections, where he argued that `git pull`’s purpose is history integration, not working-copy management, and that force-pushed or rebased upstream branches should require explicit user intervention rather than being automated.

The suggestion to use an alias (e.g., `git config --global alias.sync '!git fetch && git reset --hard @{u}'`) is a pragmatic workaround, but it leaves the core debate unresolved: whether the force-push/rebase use case is common enough to justify a built-in solution, and whether Git’s design should prioritize convenience for this workflow over the clarity of keeping commands narrowly focused. Junio’s position remains firm—this feature does not belong in Git’s core—and his reply does not engage with the safety improvements in the `--reset` redesign or the `reset --pull` alternative. The thread is now at an impasse unless Artur or another contributor can demonstrate a compelling reason why an alias is insufficient.
