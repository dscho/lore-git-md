This is a follow-up in the ongoing debate about whether to add a `--hard` (or `--reset`) mode to `git pull`. Artur Bieniek responds to Kristoffer Haugsbakk’s suggestion to work directly with remote-tracking branches like `origin/main` instead of local branches. Artur clarifies that the goal is not just to update the remote-tracking branch (which `git fetch` already does) but to also update the *checked-out working tree* to match it. He then floats an alternative design: `git reset --pull --hard`, which would fetch the configured upstream and reset the working tree to it in one command. This inverts the original proposal, moving the network I/O from `pull` to `reset`, but leaves open whether such a change would be any more acceptable to Junio, who has already rejected the idea of adding destructive operations to `git pull`.

The email does not advance the technical implementation or post a revised patch, but it does shift the framing of the problem. The core question remains whether the force-push/rebase use case justifies any convenience feature at all, and if so, where that feature should live in Git’s command set. No other participants have yet weighed in on this specific alternative.
