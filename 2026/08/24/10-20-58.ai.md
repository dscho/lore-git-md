This is a feature patch series (3 patches) introducing the `report` hook for `git-receive-pack`. The series is now in its third iteration, addressing the last major design question—exit status semantics—by adopting Junio C Hamano and Patrick Steinhardt’s proposal: a non-zero exit no longer causes `receive-pack` to die but instead rewrites all ref status lines to `"report hook failed"`, allowing the push to complete with a clear error message. The series also splits out two preparatory commits: one to document the existing `proc-receive` hook in `git-receive-pack.adoc`, and another to refactor the status-report generation into a reusable function.

The core implementation (patch 3/3) remains unchanged in its architecture: the hook is invoked after all ref updates are committed but before the status report is sent, receives the pkt-line encoded report on stdin, and replaces it with its stdout. Stderr is still forwarded to the client via the sideband channel. The documentation (`githooks.adoc` and `git-receive-pack.adoc`) now links to `gitprotocol-pack[5]` for protocol details, resolving the earlier ambiguity about where to document the pkt-line format. Test coverage (`t/t5412-report-hook.sh`) has been updated to reflect the new exit semantics, verifying that a non-zero exit rewrites all refs rather than causing a disconnect.

The series is now effectively complete: all prior feedback has been addressed, the exit status semantics have been resolved in line with maintainer and reviewer consensus, and the documentation is thorough. The only remaining loose end is the unresolved question of whether to link to `gitprotocol-common.adoc` or `gitprotocol-pack[5]` for pkt-line format documentation, but this is a minor documentation nit and does not affect functionality. The patch is well-motivated (GitLab’s MVCC use case is documented in the commit message), thoroughly tested, and ready for integration. Expect it to land in `next` shortly unless a new substantive concern emerges.
