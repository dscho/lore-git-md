This is a review reply in the ongoing test-coverage thread for `git symbolic-ref`. Patrick Steinhardt responds to Nikolaus Schuetz’s v2 patch, which adds tests to document the command’s exit codes and `--quiet` behavior when querying non-symbolic refs.

The patch itself is uncontroversial—it simply adds three new tests to `t/t1401-symbolic-ref.sh` to verify that `git symbolic-ref` exits with 128 and prints an error when given a non-symbolic ref, while `--quiet` exits with 1 and produces no output. Nikolaus’s v2 incorporated Patrick’s earlier suggestion to also test that stdout is empty in both cases, and the commit message now clearly explains the motivation: existing tests (like `t2020` and `t5621`) already rely on this behavior, but none explicitly pins down the exit codes or confirms that `--quiet` suppresses diagnostics.

Patrick’s reply, however, shifts the focus from the patch to the design itself. He remains unconvinced that the differing exit codes (128 vs. 1) are intentional, calling the inconsistency “weird” and suggesting it may simply be an oversight—one code path uses `exit(1)` while the other uses `die()`, which returns 128. His concern is that the new tests would “cast this behavior into stone,” making it harder to change later. He proposes two alternatives: either drop the exact exit-code checks from the tests, or align the code paths by changing `exit(1)` to `die(NULL)` so both cases return 128.

The thread is now at a crossroads. The patch is technically sound and fills a clear gap in test coverage, but Patrick’s feedback raises a legitimate design question. Nikolaus has already stated that the current behavior is consistent with other Git commands (like `git rev-parse --verify --quiet`), but Patrick’s skepticism suggests the discussion isn’t over. If the exit-code difference is deemed unintentional, a follow-up patch to unify them would likely be needed. For now, the patch remains under review, with the design question still open.
