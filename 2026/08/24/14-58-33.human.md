This is a brief but substantive follow-up in the ongoing `stash.ref` RFC thread. Junio C Hamano responds to Phillip Wood’s alternative design (associating stashes with branches rather than introducing a new `stash.ref` config knob) with cautious interest. He acknowledges that per-branch and per-worktree stashes have been discussed before but raises a practical concern: relying on the stash message to encode branch information could conflict with user-provided messages, especially if the format becomes more structured (e.g., appending `: target-branch` to the message).

Junio’s comment is not a rejection but a technical caveat. He suggests that if Git were to officially support per-branch stashes, the stash message format might need to evolve to avoid ambiguity — for example, by reserving a suffix for branch metadata. This would require changes to how the `-m` option works, ensuring user messages don’t accidentally collide with the branch-tracking mechanism. The observation is a small but important detail that could shape the eventual implementation if the thread converges on Phillip’s approach.

The discussion remains open-ended. No new patches have been proposed yet, and the thread is still exploring design options rather than reviewing code. Junio’s input adds a layer of realism to the branch-aware stash idea but doesn’t tip the scales toward or against it. For now, the debate is still about *how* to solve the cross-worktree stash interference problem, not *whether* to solve it.
