This is a **follow-up in the `git pull --hard`/`--reset` thread**, advancing the design discussion. Artur Bieniek responds to Kristoffer Haugsbakk’s workflow suggestion by clarifying the core use case: the goal is not merely to update a local branch pointer, but to update the *working tree* to match a force-pushed or rebased upstream branch. While `git fetch` updates the remote-tracking branch (e.g., `origin/main`), it does not update the checked-out working tree, leaving the user at the old commit. Artur then floats an alternative design: `git reset --pull --hard`, which would fetch the configured upstream and reset the working tree to it. This inverts the original proposal, moving the destructive operation to `git reset` while adding network I/O. The question is whether this design would be more acceptable to Junio, or whether introducing network operations into `git reset` would be equally objectionable. No updated patch has been posted; the discussion remains conceptual.
