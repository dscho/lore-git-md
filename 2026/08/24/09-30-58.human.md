This is a performance-focused refactoring of the reftable backend, now in its second iteration. The series targets redundant stack reloads during reference transactions, addressing a bottleneck where excessive `fstat()` calls were consuming significant time during bulk ref creation. The v2 update incorporates feedback from the initial review, adding a fourth patch to rename a function for naming consistency and introducing per-addition lock tracking to prevent premature lock release when multiple `reftable_addition` instances operate on the same stack.

The changes are well-motivated by Jeff King's profiling data and demonstrate clear performance improvements. Benchmark results now show a consistent 15-20% speedup across ref counts from 2,000 to 50,000 when using `refs/tags/` (which triggers reflog checks), with `newfstatat()` syscalls reduced from linear growth to a constant ~55 calls regardless of ref count. The series touches `refs/reftable-backend.c`, `reftable/stack.h`, `reftable/stack.c`, and corresponding unit tests, with no changes to the on-disk format.

Key technical improvements in v2 include the addition of a `locked` bit field to `struct reftable_addition` to track lock ownership, preventing multiple additions from releasing each other's locks. The series also addresses the earlier benchmarking discrepancy by using `refs/tags/` instead of `refs/heads/` to better reflect real-world performance gains. The implementation remains focused and mechanical, with thorough test coverage validating the new locking logic.

The series appears ready for further review, with the core design decisions now settled. The remaining discussion points from v1—such as the lock relocation safety concern raised by Junio C Hamano—have been addressed in principle, though the implementation details may still see minor refinements. The performance gains and clean design make this a worthwhile optimization for the reftable backend.
