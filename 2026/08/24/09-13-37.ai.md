This is a substantive review in the ongoing `stash.ref` RFC thread. Phillip Wood engages directly with the core problem — silent stash interference between worktrees — and proposes an alternative design: instead of introducing a new `stash.ref` configuration knob, he suggests extending the existing stash machinery to associate stashes with the branch they were created on, then adding an option to `git stash pop` to only apply stashes created on the current branch.

The review is well-informed and constructive. Phillip acknowledges the real-world pain point (AI agents stashing in parallel worktrees) but questions whether a new config knob is the right solution. His alternative leverages existing Git concepts (branch names, `refs/worktree/`) and avoids inventing new configuration. He also hints at future work — an option to specify the branch name when creating a stash — that would further refine the design.

This is not a surface-level nitpick; it challenges the RFC’s premise and offers a concrete, backward-compatible alternative. The discussion is now squarely about *how* to solve the problem, not *whether* it exists. If the thread converges on Phillip’s approach, the eventual patch will likely be smaller and more aligned with Git’s existing patterns.
