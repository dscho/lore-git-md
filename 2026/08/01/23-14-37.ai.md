This is a substantive review in the GSoC series extending `git cat-file --batch-command` to support `%(objecttype)` in remote-object-info queries. Jeff King (Peff) replies to Pablo Sabater’s explanation of the `struct object_info` design, clarifying the historical rationale for using pointer indirection and offering a nuanced perspective on its trade-offs.

Peff confirms the pointer system was introduced in 2011 to mirror direct function arguments, allowing callers to pass only the fields they care about (e.g., `read_object_info(oid, &size)`) without requiring a struct. He notes the compiler’s ability to catch uninitialized variables when pointers are forgotten is a minor but real benefit, though he doubts the memory overhead (~24 bytes per struct) is significant in practice, since callers typically reuse a single struct. He also observes that the `type_valid` bitfield Junio suggested is unnecessary in the current codebase, as the query either succeeds or returns an error.

The discussion then turns to Pablo’s example of a recent bugfix where `typep` was used to restore state between commands. Peff points out that bitfields would require the same save/restore logic, so the complexity is inherent to the design, not the implementation. He also clarifies that `expand_atom()`’s dual role (marking requested atoms and expanding them) would still need to set flags, regardless of whether pointers or bitfields are used.

Most critically, Peff identifies a conceptual mismatch: `struct object_info` is meant for *local* object queries, while remote-object-info should bypass it entirely. The remote data should flow directly into `expand_data`, the cat-file-specific struct. This suggests the current series might be overloading `object_info` for a use case it wasn’t designed for, though Peff doesn’t explicitly call for a redesign—only that the remote path shouldn’t rely on `object_info` internals.

The review is technical and advisory, not a blocker. It reinforces Junio’s earlier feedback about the oddness of the `object_info` design but shifts focus to the broader architectural question of whether remote-object-info should avoid `object_info` altogether. Pablo’s next steps will likely involve either justifying the current approach or adjusting the series to align with Peff’s observation. The thread remains under review, with no merge status implied.
