This is a **maintainer response** in the ongoing RFC thread about restricting Git 3.0's hex object ID parsing to lowercase only. Junio C Hamano engages with Jeff King's observation about uppercase hex in object payloads (commits and tags) creating parallel histories, but downplays its significance.

Junio acknowledges the edge case but frames it as a non-issue: Git already tolerates parallel histories (e.g., empty rebases that delay the clock by one second), and the same logic applies to uppercase-induced duplicates. He notes that tree objects are unaffected because they use binary hashes, limiting the problem to the top-level object names in commits and tags. He also points out that `git diff` would correctly identify identical trees even if referenced by commits with different (uppercase vs. lowercase) object IDs, because the diff layer operates on binary representations.

Junio references brian m. carlson's earlier observation that Git normalizes case by converting to binary in many places, though he concedes this happens opportunistically rather than systematically. He agrees with Peff that accidental creation of uppercase objects is unlikely with most Git commands, since most code paths round-trip through binary hashes (e.g., `git commit-tree 1234ABCD` would normalize the case).

This response does not directly address the core question of whether Git 3.0 should enforce lowercase-only parsing, but it reinforces Junio's broader skepticism about the need for a breaking change. By framing the parallel-history edge case as harmless and already accommodated by Git's design, he weakens the argument that uppercase hex in object payloads creates meaningful problems. The discussion remains focused on design philosophy rather than implementation, with no new technical objections or compromises proposed. The thread is still in RFC stage, and no maintainer decision has been made.
