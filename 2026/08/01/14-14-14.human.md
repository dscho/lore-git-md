This is a substantive review from Jeff King (Peff) on Junio C Hamano’s `git add --resolved` series. Peff engages directly with the workflow the feature aims to improve, raising two potential corner cases to assess whether the new option might inadvertently create footguns for users. His analysis is technical and scenario-driven, focusing on how the feature interacts with Git’s existing merge machinery and working-tree state.

Peff’s first concern—whether unrelated local changes in a conflicted file could be accidentally staged—turns out to be a non-issue: he confirms that most merge strategies (except "ours") refuse to operate on dirty files, so the scenario is impossible in practice. The second concern is more nuanced: if a conflict resolution requires changes to additional files (e.g., updating callers of a modified function), `git add --resolved` will ignore those files because Git cannot infer their relevance to the merge. Peff notes that this limitation already exists in manual workflows, but warns that `--resolved` might create a false sense of completeness by staging only the conflicted paths.

The review is measured and constructive. Peff does not oppose the feature, but his questions highlight a subtle usability risk: users might assume `--resolved` stages *all* necessary changes, when in fact it only stages files that were conflicted. This could lead to incomplete resolutions if users overlook related changes in other files. The discussion is now open for Junio or others to address whether the documentation, error messages, or even the feature’s behavior should be adjusted to mitigate this risk. The series remains technically sound, but Peff’s feedback suggests the user experience may need refinement.
