This is the fourth patch in Pablo Sabater’s GSoC v2 series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The patch teaches the client to parse the "type" field from the server’s response, completing the end-to-end chain for object type metadata.

Junio’s earlier review identified two inefficiencies in the patch’s memory management: (1) the current implementation allocates `xcalloc` once per object ID for `object_info_data[j].typep`, which is correct but inefficient; and (2) the broader design of `odb.h:struct object_info` stores scalar values like `enum object_type` as pointers to heap-allocated memory, adding ~24 bytes of overhead per object for a single byte of data. Junio suggested replacing the pointer indirection with bitfields (`unsigned type_asked:1, type_valid:1`) to track request status and validity, eliminating heap allocation overhead entirely. This feedback was advisory and not a blocker for the series.

In this reply, Pablo acknowledges the design oddity and provides context from a recent bugfix (`contents` commands) that illustrates how the current pointer-based design is used to track whether an atom was requested. He notes that `expand_atom()`—which maps requested atoms and later expands them—relies on `typep` being non-NULL to signal whether the caller asked for `%(objecttype)`. While the current design works, it does force extra work: for `info` commands, it triggers a type lookup, and for `remote-object-info`, it directly determines whether the client requested the placeholder. Pablo agrees the design feels strange but defers any cleanup to a future effort, keeping the focus on landing the GSoC work.

The patch itself remains ready for integration; the memory management feedback is now understood and can be addressed in a follow-up. The series is otherwise complete and uncontroversial, with all other review feedback incorporated in v2.
