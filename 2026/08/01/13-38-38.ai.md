This is a substantive review comment on the fourth patch in Pablo Sabater’s GSoC v2 series, which extends `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. Junio identifies a design inefficiency in the `odb.h:struct object_info` structure, which currently stores scalar values like `enum object_type` and `size_t` as pointers to heap-allocated memory rather than directly in the struct. This forces callers to allocate separate memory for each object, adding ~24 bytes of overhead per object (8-byte pointer + malloc overhead) to store a single byte of data.

Junio suggests replacing the pointer indirection with two bitfields (`unsigned type_asked:1, type_valid:1`) to track whether the caller requested the information and whether the object layer provided it. This would eliminate the heap allocation overhead entirely while preserving the same semantics. He acknowledges this is not a blocker for the current series but flags it as a potential cleanup for later, noting the design feels "iffy" and could be revisited after the GSoC work lands.

The feedback is narrowly scoped to the memory management pattern and does not question the patch’s core functionality. Pablo’s current implementation (allocating `xcalloc` once per object ID) is correct but inefficient; Junio’s alternative (contiguous allocation or bitfields) would improve code hygiene without changing behavior. The patch remains ready for integration once this feedback is addressed, though the change is advisory rather than mandatory. The thread context confirms this is the only outstanding feedback on the patch, which is otherwise uncontroversial and part of a well-reviewed series.
