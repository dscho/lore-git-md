This is a technical discussion in the ongoing GSoC series that extends `git cat-file --batch-command` to support `%(objecttype)` in remote-object-info queries. The thread zooms in on a design detail: whether `odb.h:struct object_info` should continue using pointer indirection for scalar values like `enum object_type` or switch to bitfields (`unsigned type_asked:1, type_valid:1`) to eliminate heap allocation overhead.

Jeff King (Peff) provides historical context, explaining that the pointer system dates back to 2011 and was originally designed to mirror direct function arguments, allowing callers to pass only the fields they cared about. He notes that while bitfields would be more memory-efficient, the current design offers a minor benefit: the compiler can detect if a caller forgets to set a pointer (e.g., `oi.typep = &type`), whereas a forgotten bitfield assignment would silently produce garbage values. Peff also clarifies that the `type_valid` bitfield Junio suggested isn’t strictly necessary, as the current code either satisfies a query or returns an error.

The discussion then turns to a recent bugfix where the pointer system was used to restore state between commands, but Peff points out that bitfields would require the same save/restore logic. He emphasizes that `object_info` should not be used at all for remote data—remote queries should populate `expand_data` directly, avoiding the overhead entirely. This suggests the current series might be mixing local and remote data paths in a way that could be streamlined.

The exchange is substantive but advisory: Peff’s feedback doesn’t block the series, but it highlights a design tension between the current pointer-based approach and a potential bitfield refactor. The series remains ready for maintainer consideration, with Pablo’s earlier acknowledgment that the broader cleanup is out of scope.
