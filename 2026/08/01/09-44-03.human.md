This is the **v4 feature patch series** for `git bisect`, adding the `--reset-when-found[=<where>]` option. The series is now in its final form, addressing all remaining feedback from Johannes Sixt’s review of v3.

The feature automates the post-bisect cleanup step: once `git bisect` identifies the first bad commit, it resets the working tree to either the pre-bisect commit (`original`, the default) or the first bad commit itself (`found`). This eliminates the need for an explicit `git bisect reset`, making it especially useful for automated workflows (CI, scripts) and interactive debugging. The implementation persists the chosen target in a `BISECT_RESET_WHEN_FOUND` state file and enforces a constraint that `--reset-when-found` cannot be used with `--no-checkout`, since that mode prevents checking out either target.

Key improvements in v4 include simplifying translation calls (using Git’s standard dual-option error template) and fixing shell safety issues in tests by avoiding unchecked `git rev-parse` calls in subshells. The test suite now assigns `git rev-parse` output to variables before passing them to `test_path_is_file` or `test_path_is_missing`, ensuring errors are not silently buried. The series also chains `test_when_finished` commands with `&&` for better cleanup reliability, though this is a minor mechanical detail.

The series is technically sound and uncontroversial. It touches only the bisect subsystem (`bisect.c`, `builtin/bisect.c`, and tests), with no on-disk format changes or new symbols beyond the state file updates. Junio has already marked it for integration into `next`, and all substantive feedback has been addressed. The only practical limitation—users cannot conditionally choose the reset target based on the bisect outcome—is a reasonable trade-off for the feature’s simplicity.

This is a well-crafted addition that solves a real workflow friction. The implementation is clean, the test coverage is thorough, and the commit messages clearly explain the design choices. If you use `git bisect` in scripts or CI, this patch is worth your attention.
