This is Junio C Hamano following up on his earlier review of the `--reset-when-found` feature in the `git bisect` command. The patch in question is the second in a two-patch series that adds the new option, and Junio is now proposing a more ambitious refactoring of the bisect state machine to simplify the implementation.

Junio steps back from the current patch and sketches a cleaner design: instead of scattering auto-reset logic throughout the codebase, he suggests making all bisect subcommands return their result codes rather than calling `exit()`, then handling the auto-reset in the top-level `cmd_bisect()` function. This would centralize the logic, eliminate the need for the `defer_reset` parameter introduced in the current patch, and avoid the platform-specific file-descriptor issues that motivated it. The proposal is still framed as a question ("Hmm?") rather than a demand, but it is clearly a more invasive change than his earlier suggestion to decouple `bisect_clean_state()` from `bisect_reset()`.

The refactoring would require significant changes to the patch series, including converting all bisect subcommands to return codes and introducing a file-scope static variable to pass the found commit from `bisect_next_all()` up to `cmd_bisect()`. While this would simplify the internal structure, it would also delay integration of the feature, which is otherwise ready for `next`. The current patch is uncontroversial and addresses all prior feedback, so this proposal is likely to prompt discussion about whether the improved design is worth the additional churn. For now, the series remains marked for `next`, but this review may shift the focus from integration to a potential v5.
