This is a major RFC proposal that restructures how Git computes and consumes diff hunks, introducing a new **hunk provider interface** that lets external tools or internal caches supply diff hunks instead of Git’s built-in xdiff computation. The series is split into three conceptual pieces: the interface itself (patch 2), an in-process cache called the **diff-hunks store** (patches 3–6), and an external process driver (patches 7–10) that builds on the earlier `diff.<driver>.process` RFC but now integrates via the new interface.

The core idea is to abstract the question "which lines changed?" behind a provider chain owned by the repository. Every diff consumer—blame, stat formats, patch output, or `git log -L`—asks the same interface, which may consult one or more providers before falling back to the built-in xdiff. The interface is designed to be extensible: providers can be added later without changing consumer code, and the chain order reflects authority (external processes outrank caches, which outrank the built-in diff). Performance measurements show the overhead of walking the chain is negligible, while the diff-hunks store delivers measurable speedups (1.4–1.9x for `git log --stat`, 1.2–1.4x for blame) when warmed.

The diff-hunks store is an in-process cache that records precomputed hunks at `$GIT_DIR/objects/info/diff-hunks`. It only stores hunks that match the built-in diff (to guarantee output stability) and is opt-in for writing (`GIT_DIFF_HUNKS_WRITE=1`). The store is keyed by blob pairs and diff options, and its format is documented in new man pages (`git-diff-hunks(1)`, `gitformat-diff-hunks(5)`). It handles corruption gracefully (treating unreadable files as absent) and has no background maintenance—recovery is simply `git diff-hunks clear` followed by a re-warm. The store is deliberately limited to identity-keyed requests (blob pairs only) and does not serve divergent hunks (0.4–0.5% of a warm store), which always fall back to xdiff.

The external process driver (`diff.<driver>.process`) is now implemented as a provider that sits at the head of the chain. It uses the same pkt-line protocol as the earlier RFC but is reduced to identity-only requests (sending only blob object IDs, not file content). The driver is opt-in per command (like textconv) and degrades gracefully to the built-in diff on failure. The protocol is versioned and forward-compatible, with room to extend to content-carrying requests later. The series includes a gentle status read for subprocesses (patch 8), so a protocol error in an optional process does not die but falls back to the built-in diff.

The series is **not intended to merge as-is**—it is an RFC to validate the direction. If accepted, the work will return as separate reviewable series: first the interface and store (patches 1–6), then the process driver (patches 7–10), and finally content enrichment (patch output, `git log -L`, etc.). The current series applies on the `mm/line-log-limited-ops` topic (rebased onto master) and replaces the earlier `mm/diff-process-hunks` RFC. It includes comprehensive test coverage (1,400+ lines across `t/t4080-diff-process.sh` and `t/t4220-diff-hunks.sh`) and performance benchmarks (`t/perf/p4218-diff-hunks.sh`).

The proposal is ambitious but well-motivated: it unifies how diff consumers ask for hunks, enables external tools to inject semantic diffs, and provides a cache that speeds up common operations without changing output. The interface design is clean, with clear separation between providers and consumers, and the store’s limitations (no divergent hunks, no background maintenance) keep it simple and safe. If the direction holds, this could be a foundational change for Git’s diff infrastructure.
