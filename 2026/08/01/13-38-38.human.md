This is a follow-up review comment from Junio on the fourth patch in Pablo Sabater’s GSoC v2 series, which teaches `git cat-file --batch-command` to parse object type metadata from remote-object-info responses. The patch itself is uncontroversial and ready for integration, but Junio takes the opportunity to critique the broader design of `struct object_info` in `odb.h`, which the patch interacts with.

Junio’s concern is architectural: the struct currently stores scalar values like `enum object_type` and `size_t` as pointers to heap-allocated memory, rather than embedding the values directly. This forces callers to allocate separate memory for each object, adding ~24 bytes of overhead per object (8-byte pointer plus malloc overhead) to store a single byte of data. He suggests replacing the pointer indirection with two bitfields (`type_asked` and `type_valid`) to track whether the caller requested the information and whether the engine provided it, eliminating the need for heap allocation entirely.

The critique is purely advisory and does not block the current patch. Junio explicitly notes that this is not something to change mid-series, but he leaves the comment to "stir the pot" for future cleanup. The observation is sharp and well-founded: the current design is indeed wasteful, and the suggested bitfield approach would be more efficient. However, addressing it would require a broader refactoring of the ODB layer, which is beyond the scope of Pablo’s GSoC work.

For now, the patch remains ready for merging as-is. The only actionable feedback from Junio’s earlier review (on memory allocation for `object_info_data[j].typep`) is still pending, but this new comment is a side note rather than a blocker. The series as a whole is complete, addresses all prior review feedback, and is awaiting Junio’s merge decision.
