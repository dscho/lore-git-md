This is Junio C Hamano’s reply to Jeff King’s observation about uppercase hex in object payloads creating parallel commit histories. Junio acknowledges the edge case but downplays its severity, comparing it to the existing practice of empty rebases that create near-identical commits with slightly different timestamps. He notes that Git’s object model already handles such parallel histories gracefully: tree objects use binary hashes, so case variations in commit or tag payloads do not propagate into the tree hierarchy, and `git diff` will correctly identify identical trees even if referenced by commits with different parent hashes (e.g., one lowercase, one uppercase). Junio also points out that Git already normalizes hex case in many places by converting to binary, which incidentally resolves the issue for most code paths—though he concedes this normalization is opportunistic rather than systematic.

The reply reinforces Junio’s broader skepticism about the RFC series’ premise: he treats the parallel-history edge case as a minor curiosity rather than a compelling reason to enforce lowercase-only parsing. His tone suggests he sees the existing normalization behavior as sufficient, and he implies that the proposed breaking change might be overkill for a problem that Git already mitigates in practice. The discussion remains philosophical, with no new technical objections or implementation feedback; Junio’s stance continues to favor the Robustness Principle (accepting both cases) over strict enforcement, even for Git 3.0. The thread is still in RFC stage, with no maintainer decision yet.
