This is a substantive review in the GSoC series adding `%(objecttype)` support to `git cat-file --batch-command` for remote-object-info queries. Jeff King (Peff) follows up on his earlier feedback about the `struct object_info` design, now making a clear architectural recommendation: **the remote-object-info path should not use `object_info` at all**.

Peff explains that `object_info` is designed for single-object queries, where the caller provides pointers to store results (e.g., `query.sizep = &size`). For batch queries (N objects), this model breaks down—you’d need an array of `object_info` structs, one per object, which is inefficient and conceptually awkward. Instead, the remote path should define its own query structure using simple boolean flags (e.g., `want_type`, `want_size`) to declare what metadata it needs, then parse the server’s response directly into `expand_data`, the cat-file-specific struct.

The review is technical and actionable, though not a blocker. It suggests a cleaner separation between local and remote object queries, avoiding the current series’ reuse of `object_info` internals. Pablo Sabater will likely need to refactor the client-side parsing logic in `fetch-object-info.c` to bypass `object_info` entirely, using a lightweight query struct and mapping server responses directly to `expand_data`.
