This is a follow-up in the GSoC series extending `git cat-file --batch-command` to support `%(objecttype)` in remote-object-info queries. Pablo Sabater acknowledges Junio’s feedback about the inefficiency in `odb.h:struct object_info`—where scalar values like `enum object_type` are stored as pointers rather than directly in the struct—and confirms the design does indeed feel odd. He notes the pointer indirection is currently used to track whether the caller requested the information (non-NULL `typep`) and whether the object layer provided it (non-NULL value), but agrees bitfields (`unsigned type_asked:1, type_valid:1`) would be a cleaner, allocation-free alternative.

Pablo adds context from a recent bugfix (Peff’s patch) where the pointer was used to restore state between commands, showing the current design’s dual role: `typep` signals both “was this asked?” and “is this valid?”. He suggests the broader cleanup is out of scope for this series but could be revisited later. The thread remains focused on the v2 series’ readiness; Junio’s feedback was advisory, and Pablo’s response doesn’t introduce new blockers. The series is otherwise complete, with only minor nits (e.g., shell quoting in patch 5) left to address before maintainer consideration. Key technical detail: the `struct object_info` design affects multiple commands (`info`, `remote-object-info`), so any cleanup would need to preserve their shared behavior.
