This is the maintainer’s final review of the second patch in the `--reset-when-found` series, now cooking in `next`. Junio’s message is a detailed technical critique of the internal structure, not a rejection but a suggestion for a cleaner design before the patch graduates to `master`.

The core issue is the `defer_reset` mechanism introduced to work around platform limitations (unlinking open files). Junio finds this “somewhat ugly” and proposes an alternative: stop calling `bisect_clean_state()` from `bisect_reset()` altogether. Instead, callers that need cleanup would invoke `bisect_clean_state()` explicitly after `bisect_reset()` returns. He sketches how this would simplify the call graph: `bisect_run()` could close its files, then call `bisect_reset()`, then call `bisect_clean_state()`, eliminating the need for the `defer_reset` boolean and the conditional logic that checks for the `BISECT_RESET_WHEN_FOUND` state file in multiple places.

Junio also points out that the current code checks for the state file in several ad-hoc spots (`is_empty_or_missing_file(...)`), which he compares unfavorably to how the code already handles `struct bisect_terms`—parsed once and stored in a variable. He suggests parsing the reset target upfront and storing it in the same structure, so that later code can simply check a field rather than probing the filesystem repeatedly.

The review is substantive but constructive; Junio is not blocking the patch, merely asking for a refactor that would make the code easier to reason about. The series remains in `next`, and the author will likely send a v5 addressing these points before the topic graduates to `master`.
