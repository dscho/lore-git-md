This is a **substantive review** in the ongoing RFC thread about restricting Git 3.0's hex object ID parsing to lowercase only. Jeff King (Peff) identifies a **new edge case**: uppercase hex within object payloads (specifically commit and tag objects) can create parallel histories of otherwise identical commits, since Git does not normalize case when hashing object contents. He demonstrates this with a concrete example: a commit with an uppercase parent hash produces a different object ID than the same commit with a lowercase parent hash, even though the logical content is identical.

The observation is narrowly scoped to object *contents* (not refs, command-line arguments, or network inputs) and affects only commits and tags (trees use binary hashes, so case is irrelevant). Peff notes that accidental creation of such objects is unlikely with most Git commands, since most code paths round-trip through binary hashes (e.g., `git commit-tree 1234ABCD` would normalize the case). However, the example shows that it *is* possible to create these objects intentionally, and they persist as distinct objects in the repository.

This adds a new dimension to the discussion: the proposed breaking change (rejecting uppercase hex in *parsing*) would not address this case, because the uppercase hex here is part of the object *content*, not an external input. The thread has so far focused on external inputs (command-line arguments, refs, network protocols), but Peff's example shows that the problem of case sensitivity extends into the object model itself. Whether this weakens the justification for the breaking change (by showing it doesn't solve the full problem) or strengthens it (by demonstrating another way case sensitivity can cause issues) is likely to be debated. The example does not directly contradict brian m. carlson's security rationale, but it complicates the narrative by showing that the problem is more pervasive than just external tooling.

No new patches or implementation feedback are provided; this is purely a design-level observation. The thread remains in RFC stage, with no maintainer decision yet. Key technical detail: the example uses `git hash-object` to write a commit with an uppercase parent hash, producing a distinct object ID.
