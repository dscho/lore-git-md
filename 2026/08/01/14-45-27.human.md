This is a substantive review comment in the ongoing RFC thread about restricting Git 3.0's hex object ID parsing to lowercase only. Jeff King (Peff) identifies a previously unconsidered edge case: uppercase hex object IDs *within* commit objects (specifically, in parent references) can create parallel histories of otherwise identical commits. He demonstrates this with a concrete example where manually uppercasing a parent reference in a commit object produces a different object ID, effectively creating a fork in the commit graph from what should be the same commit.

Peff notes this is mostly a "don't do that" scenario but points out Git generally avoids multiple representations of the same data within its object model. He observes that only commits and tags are vulnerable to this (since tree hashes are binary), and that most Git commands would likely normalize such cases incidentally when round-tripping through binary hashes. This suggests the problem is more theoretical than practical for most workflows, but it does reveal a subtle inconsistency in Git's object model that the proposed breaking change would address.

The comment doesn't take a position on whether the breaking change is justified, but it adds a new technical dimension to the discussion: the proposed restriction would eliminate this parallel-history edge case, further strengthening the case for consistency in Git's object representation. This is particularly relevant to Junio's earlier philosophical objection about the Robustness Principle, as it shows there are internal consistency benefits beyond just external tool compatibility.
