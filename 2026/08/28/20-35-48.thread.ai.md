Subject: [PATCH] dir: avoid prefix-stripping negative pathspecs
Series version: standalone patch (no series)
Originating author: Diogo Castro
Thread type: bugfix patch

Core problem or goal
`git ls-files` and `git add` incorrectly strip the common prefix of positive pathspecs from *all* pathspecs, including negative (exclusion) pathspecs. This can cause negative pathspecs to degenerate into empty strings (matching everything) or trigger out-of-bounds reads when the negative pathspec is shorter than the prefix. The patch adds a guard in `do_match_pathspec()` to skip prefix-stripping for negative pathspecs.

Current status
Under review; no prior versions. The patch is minimal (11 lines in `dir.c`), includes three new tests in `t/t6132-pathspec-exclude.sh`, and traces the bug to its introduction in 2013 (ef79b1f870). The discussion is now at an impasse: Junio C Hamano has suggested recalculating the common prefix to include negative pathspecs (changing negative pathspec semantics to be relative to the full tree), while Diogo Castro argues that the optimization is a performance feature for positive pathspecs only and should not be extended to negative pathspecs (preserving current semantics and performance).

Key technical details
- Files touched: `dir.c` (function `do_match_pathspec()`)
- New behavior: negative pathspecs are no longer affected by positive-path prefix optimizations
- Test coverage: three new tests in `t/t6132-pathspec-exclude.sh` covering edge cases (negative pathspecs matching prefix length, shorter than prefix, and interaction with `git add` trailing-slash handling)
- On-disk format: no changes
- Symbols: no new or renamed symbols
- Design trade-off: the current patch preserves performance by limiting the working-directory walk to the common prefix of positive pathspecs, while Junio's alternative would require a full walk when negative pathspecs share no common prefix with positives (e.g., `git add -- a/b/c a/b/d ':!*.md'`)

Open questions and loose ends
- **Design direction**: Is the current fix (skipping prefix-stripping for negative pathspecs) the correct approach, or should the common prefix be recalculated to include negative pathspecs? The discussion is unresolved; no alternative implementation has been proposed.
- **Semantics**: Junio's suggestion would make negative pathspecs relative to the full tree, while the current patch treats them as absolute. The choice affects both correctness (e.g., whether `!a/b/` excludes `a/b/c` when the common prefix is `a/`) and performance (full vs. limited working-directory walks).

Participant positions
- Diogo Castro (author): defends the current patch, arguing that the prefix-stripping optimization is a performance feature for positive pathspecs only and should not be extended to negatives. Provides the example `git add -- a/b/c a/b/d ':!*.md'` to illustrate the performance trade-off.
- Thomas Haller (reporter): prior report of the bug (referenced in commit message).
- Junio C Hamano (maintainer): raised a substantive design question, suggesting the common prefix should include negative pathspecs to make their semantics more intuitive (e.g., `git ls-files -- a/b/c a/b/d !a/b/`). This remains an open objection.
