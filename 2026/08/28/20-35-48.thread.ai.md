Subject: [PATCH] dir: avoid prefix-stripping negative pathspecs
Series version: standalone patch (no series)
Originating author: Diogo Castro
Thread type: bugfix patch

Core problem or goal
`git ls-files` and `git add` incorrectly strip the common prefix of positive pathspecs from *all* pathspecs, including negative (exclusion) pathspecs. This can cause negative pathspecs to degenerate into empty strings (matching everything) or trigger out-of-bounds reads when the negative pathspec is shorter than the prefix. The patch adds a guard in `do_match_pathspec()` to skip prefix-stripping for negative pathspecs.

Current status
Under review; no prior versions. The patch is minimal (11 lines in `dir.c`), includes three new tests in `t/t6132-pathspec-exclude.sh`, and traces the bug to its introduction in 2013 (ef79b1f870). Junio C Hamano has raised a substantive design question: whether the current fix (skipping prefix-stripping for negative pathspecs entirely) is correct, or if the common prefix should instead be calculated across *both* positive and negative pathspecs. The discussion is ongoing.

Key technical details
- Files touched: `dir.c` (function `do_match_pathspec()`)
- New behavior: negative pathspecs are no longer affected by positive-path prefix optimizations
- Test coverage: three new tests in `t/t6132-pathspec-exclude.sh` covering edge cases (negative pathspecs matching prefix length, shorter than prefix, and interaction with `git add` trailing-slash handling)
- On-disk format: no changes
- Symbols: no new or renamed symbols
- Design alternative: Junio suggests recalculating the common prefix to include negative pathspecs, which would change the semantics of negative pathspecs to be relative to the full tree rather than absolute

Open questions and loose ends
- **Design direction**: Is the current fix (skipping prefix-stripping for negative pathspecs) the correct approach, or should the common prefix be recalculated to include negative pathspecs? Junio's example (`git ls-files -- a/b/c a/b/d !a/b/`) suggests the latter might be more intuitive.
- No alternative implementation has been proposed yet; the author (Diogo Castro) will need to respond to this question.
