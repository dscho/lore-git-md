Subject: [PATCH] dir: avoid prefix-stripping negative pathspecs
Series version: standalone patch (no series)
Originating author: Diogo Castro
Thread type: bugfix patch

Core problem or goal
`git ls-files` and `git add` incorrectly strip the common prefix of positive pathspecs from *all* pathspecs, including negative (exclusion) pathspecs. This can cause negative pathspecs to degenerate into empty strings (matching everything) or trigger out-of-bounds reads when the negative pathspec is shorter than the prefix. The patch aims to fix this by ensuring negative pathspecs are not affected by the positive-path prefix optimization.

Current status
Under review; no prior versions. The patch is minimal (11 lines in `dir.c`), includes three new tests in `t/t6132-pathspec-exclude.sh`, and traces the bug to its introduction in 2013 (ef79b1f870). The discussion has evolved: Junio C Hamano initially suggested recalculating the common prefix to include negative pathspecs (changing negative pathspec semantics to be relative to the full tree), but has since refined his position. He now agrees that the current behavior (stripping the positive-only prefix from negatives) is incorrect and proposes recalculating the common prefix to include *both* positive and negative pathspecs *only when the negatives share a meaningful prefix with the positives*. The design direction remains unresolved, with no alternative implementation proposed yet.

Key technical details
- Files touched: `dir.c` (function `do_match_pathspec()`)
- New behavior: negative pathspecs are no longer affected by positive-path prefix optimizations (current patch); Junio's alternative would recalculate the common prefix to include negatives when they share a prefix with positives
- Test coverage: three new tests in `t/t6132-pathspec-exclude.sh` covering edge cases (negative pathspecs matching prefix length, shorter than prefix, and interaction with `git add` trailing-slash handling)
- On-disk format: no changes
- Symbols: no new or renamed symbols
- Design trade-off: the current patch preserves performance by limiting the working-directory walk to the common prefix of positive pathspecs, while Junio's alternative would require a full walk when negative pathspecs share no common prefix with positives (e.g., `git add -- a/b/c a/b/d ':!*.md'`). Junio's approach prioritizes intuitive semantics (negative pathspecs relative to the full tree) over performance in such cases.

Open questions and loose ends
- **Design direction**: Should the common prefix be recalculated to include negative pathspecs when they share a prefix with positives (Junio's refined proposal), or should negative pathspecs remain unaffected by prefix-stripping (Diogo's current patch)? The discussion is unresolved; no alternative implementation has been proposed.
- **Semantics**: Junio's proposal would make negative pathspecs relative to the full tree when they share a prefix with positives (e.g., `git add -- a/b/c a/b/d ':!a/b/x'` would exclude `a/b/x` but not `a/b/c/x` or `a/y`), while Diogo's patch treats them as absolute. The choice affects both correctness (e.g., whether `!a/b/` excludes `a/b/c` when the common prefix is `a/`) and performance (full vs. limited working-directory walks).
- **Implementation**: No alternative patch has been posted to implement Junio's proposal, leaving the thread at the design stage.
