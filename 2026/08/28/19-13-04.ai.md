This is a substantive review comment on the sixth patch in Patrick Steinhardt’s 8-patch series refactoring ODB alternates handling. Junio C Hamano raises a security and correctness concern about the patch’s approach to writing the `info/alternates` file: it opens the file in append mode (`"a"`) rather than using Git’s standard lockfile API, which would provide atomicity and prevent partial writes or TOCTOU (time-of-check-to-time-of-use) races.

The question is whether this matters in practice. Junio notes that the operation happens only once, during repository creation, when no other process should be accessing the repository. However, he implies that even in this context, using the lockfile API would be the safer and more conventional choice. The patch’s current implementation reads any preexisting alternates (e.g., from template directories), deduplicates them against the new entries, and appends the new ones — but this sequence is not atomic, leaving a window where the file could be corrupted or partially written if another process interferes.

This comment directly engages with the patch’s technical design and has implications for the broader series. If the lockfile API is deemed necessary, the patch will need to be revised, and the removal of the lockfile mechanism in patch 8 (which Toon Claes already flagged as potentially unsafe) may need to be rethought. The discussion is likely to attract attention from ODB-focused contributors (e.g., Justin Tobler, Karthik Nayak) and could delay the series until the locking strategy is resolved. The patch is otherwise well-scoped and uncontroversial, but this issue is now its primary open question.
