This is a short follow-up in the ongoing architectural discussion about Git's built-in command interfaces. Junio clarifies a nuance in his earlier response to D. Ben Knoble about how to properly refactor and reuse logic from built-in commands like `git checkout`. While his initial reply suggested factoring out reusable parts from `cmd_checkout()` into libified routines, he now notes that the current design—where `git switch` and `git restore` share a monolithic `checkout_main()`—is an "ugly" but serviceable shortcut that wouldn’t have arisen if the commands had been designed independently from the start.

The key takeaway is a stronger articulation of the anti-pattern: calling `cmd_foo()` directly from another command (e.g., `cmd_bar()`) is akin to calling `main()` in a C program, as it risks repeating one-time initialization (like `git_config()`) and finalization steps. Instead, Junio reinforces that built-in commands should be slim orchestrators, delegating reusable logic to helper functions. This approach would put external consumers (like a hypothetical library user) on equal footing with Git’s own commands, aligning with the broader "libification" goal of reducing global dependencies and enabling code reuse. The message doesn’t introduce new objections or alter the thread’s direction but sharpens the rationale for the architectural shift already underway.
