This is a reply in the ongoing bugfix series by Elijah Newren that extends Git's protection against unsafe commit operations during conflict resolution. The series targets the merge machinery, blocking both `git commit --amend` and `git commit <paths>` during conflict resolution for `git am`, `git revert`, and all forms of `git rebase`, except for interactive rebase directives like `squash` or `edit`.

In this email, Elijah responds to Junio C Hamano’s follow-up review of the first patch (1/3), which rewords error messages to clarify that restrictions apply specifically when resolving a commit that became empty. Junio had confirmed that the core logic (`whence == FROM_REBASE_PICK`) is technically sound—`sequencer_determine_whence()` only sets this value when the rebase-head and cherry-pick-head are identical, indicating an empty-pick situation—but found the enum name (`FROM_REBASE_PICK`) misleading and proposed mechanical improvements: replacing direct enum checks with calls to `is_from_rebase(whence)` (except in the function itself) and renaming the enum and helper function to include "empty" (e.g., `FROM_REBASE_EMPTY_PICK` and `is_from_rebase_empty()`).

Elijah agrees that the current naming is confusing and will add a preparatory patch in v3 to address Junio’s proposed changes. This is a surface-level refactoring that improves code clarity but does not alter the series’ behavior or logic. The unresolved technical question—whether blocking `git commit <paths>` during conflict resolution for empty commits is necessary—remains open, but this email does not engage with it. The focus here is purely on mechanical cleanup to prevent future confusion. The series is otherwise technically sound, with Junio’s earlier substantive objection resolved and Phillip Wood’s maintainability concerns already addressed in the upcoming v3.
