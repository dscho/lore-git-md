This thread is about a bug in `git ls-files` and `git add` where negative (exclusion) pathspecs are incorrectly affected by the common-prefix optimization meant only for positive pathspecs. The bug can cause negative pathspecs to degenerate into empty strings or trigger out-of-bounds reads. Diogo Castro proposed a minimal fix (11 lines in `dir.c`) that skips prefix-stripping for negative pathspecs, preserving their absolute interpretation and the performance optimization for positive pathspecs.

The discussion has reached an impasse over design direction. Junio C Hamano initially suggested recalculating the common prefix to include negative pathspecs, which would make negatives relative to the full tree but could degrade performance in some cases (e.g., `git add -- a/b/c a/b/d ':!*.md'`). In the latest email, Junio clarifies his position: the common prefix should include both positive and negative pathspecs *only when they share a meaningful prefix*, aligning negative pathspec semantics with the full tree. This narrows the disagreement—both agree the current behavior is wrong, but differ on whether to preserve the performance optimization (Diogo) or prioritize intuitive semantics (Junio). No alternative implementation has been proposed yet, so the thread remains at the design stage. The key unresolved question is whether the common prefix calculation will be extended to include negative pathspecs, affecting both correctness and performance.
