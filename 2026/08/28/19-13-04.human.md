This is a review comment from Junio C Hamano on the sixth patch in Patrick Steinhardt’s eight-patch series refactoring how Git handles ODB alternates during repository creation. The series is part of the ongoing ODB abstraction effort and aims to simplify the ODB interface by removing the ability to write alternates after repository creation.

Junio’s comment focuses on a potential TOCTOU (time-of-check-to-time-of-use) race in the new alternates-writing logic. The patch adds support for writing alternates at ODB creation time via a new `odb_create_on_disk_options` struct, which carries a `strvec` of alternate paths. The code opens the `info/alternates` file in append mode (`"a"`) to avoid overwriting any preexisting entries (e.g., from template directories), reads existing entries to avoid duplicates, and then appends the new ones. Junio questions whether this approach is safe under concurrent access, noting that using the standard lockfile API would provide atomicity and prevent partial writes. He also asks whether the race is actually a concern, given that alternates are typically written only once during repository creation when no other processes should be accessing the repository.

This is a **substantive review** that directly challenges the correctness of the implementation. The concern is not about the patch’s immediate functionality but about its robustness in edge cases, particularly concurrent repository creation. Junio’s question suggests he expects either a justification for why the race is harmless or a revised implementation using the lockfile API. The comment is likely to prompt further discussion and may require a follow-up patch to address the issue before the series can proceed. The broader thread context indicates that Toon Claes previously raised a similar concern about the removal of the lockfile mechanism in patch 8, so this issue is now attracting attention from multiple reviewers.
