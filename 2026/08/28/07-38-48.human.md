This is the first patch in Elijah Newren’s three-part bugfix series, now in its second iteration. The patch rewords error messages to clarify that restrictions on `git commit --amend` and `git commit <paths>` apply specifically when resolving a commit that became empty during a rebase, rather than during any rebase conflict. Junio C Hamano has confirmed that the underlying logic (`whence == FROM_REBASE_PICK`) is technically sound—it reliably identifies rebase stops caused by empty commits—but the enum name (`FROM_REBASE_PICK`) and helper function (`is_from_rebase()`) are misleading and should be renamed to include the word "empty" for clarity.

Elijah agrees with Junio’s proposed mechanical changes: replacing direct enum checks with calls to `is_from_rebase(whence)` (except in the helper itself) and renaming the enum and helper to `FROM_REBASE_EMPTY_PICK` and `is_from_rebase_empty()`. He will add a preparatory patch in v3 to address this. The error message phrasing ("while resolving a commit that became empty") remains awkward, but Junio has not yet proposed a better alternative, and this is unlikely to block progress.

The patch is part of a well-motivated bugfix targeting the merge machinery, addressing a real user-facing issue: preventing accidental corruption of repository state during conflict resolution. The series has already addressed Phillip Wood’s substantive maintainability concerns from v1, and Junio’s remaining feedback is now limited to surface-level improvements. Unless Junio’s new question about the necessity of blocking partial commits for empty commits leads to a significant revision, this patch looks ready for integration once the mechanical changes are made.
