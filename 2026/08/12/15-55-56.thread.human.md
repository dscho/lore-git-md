This thread is about a security fix for CVE-2026-62960 in Git's `bundle-uri` subsystem. Johannes Schindelin (Dscho) posted a patch that prevents Git from automatically fetching bundle URIs advertised by servers unless their protocol is explicitly allowed by Git's `protocol.*.allow` configuration. The fix specifically blocks "file" URIs (including Windows UNC paths) by default, as these could be exploited to leak NTLM credentials via outbound SMB connections. The patch is narrowly scoped to the clone/fetch code path and does not affect `ls-remote` or user-supplied `--bundle-uri` arguments.

The implementation is clean, leveraging Git's existing `is_transport_allowed()` logic and adding a `sanitize_bundle_list()` helper to filter out disallowed URIs. The patch includes a new test file (`t/lib-bundle-uri-protocol.sh`) to verify that non-HTTP(S) URIs are ignored unless explicitly re-enabled (e.g., via `protocol.file.allow=always`). The commit message notes this fix was already released in Git for Windows v2.55.0(4) and underwent private review in a GitHub security advisory, suggesting it has been vetted for correctness.

Key technical details include the new functions `bundle_uri_protocol()` (to extract the protocol from a URI) and `sanitize_bundle_list()` (to filter disallowed URIs), as well as a behavior change where advertised bundle URIs are now subject to `protocol.*.allow` restrictions. The patch is likely to be uncontroversial, as it aligns with Git's existing security mechanisms and addresses a clear risk. The only potential discussion point might be whether the warning message for skipped URIs is sufficiently actionable for users. No responses or reviews have been posted yet.
