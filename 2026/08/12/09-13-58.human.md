This is the second patch in Patrick Steinhardt’s four-part series refactoring the object database (ODB) subsystem to eagerly load alternate object databases. The series is part of the broader ODB abstraction effort and builds on Patrick’s prior work to make Git’s object storage layer more modular.

The patch removes lazy-loading of alternates, which has become ineffective due to scattered eager parsing throughout the codebase. Instead of deferring alternate initialization until first use, it centralizes the process in `odb_new()` and `odb_prepare()`, eliminating 13 calls to `odb_prepare_alternates()` across 10 files. The change simplifies the codebase by reducing redundancy and potential sources of bugs (e.g., callsites forgetting to prepare alternates before iterating through sources). The commit message explains that most Git commands access the object database anyway, making the lazy-loading optimization largely moot. It also notes that the preceding patch resolved a long-standing issue with case-sensitivity handling for alternate paths, enabling this refactoring.

The patch touches 11 files, primarily in the `odb/` directory but also affecting higher-level code like `builtin/fsck.c` and `commit-graph.c`. The diff is mechanical: it removes redundant calls to `odb_prepare_alternates()` and makes the function static, as it is now only used internally. No behavioral changes are intended, but the removal of lazy-loading could have subtle performance implications for commands like `git fsck` that previously avoided loading alternates when none were present. The v1 review by Justin Tobler was surface-level, focusing on a minor commit message typo (now fixed in v2), and did not engage with deeper technical trade-offs.

This is a well-motivated refactoring that aligns with the ODB abstraction goals. The patch is clean, with a clear rationale and no obvious downsides beyond the acknowledged performance trade-off, which appears low-risk. It looks ready for further review or integration, though reviewers may want to validate edge-case handling (e.g., repositories with many alternates or corrupt alternates). The series as a whole is progressing smoothly, with v2 addressing all feedback from v1.
