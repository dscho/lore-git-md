This thread addresses a severe performance regression in Git v2.53 that causes quadratic-time behavior when loading many packfiles, particularly impacting shell prompts (`git rev-parse --short HEAD`) in Microsoft Git Scalar environments. The regression, introduced in October 2025, was traced to `packfile_store_add_pack()`'s linear scan for duplicates before each insertion, undoing a prior 2019 fix. Johannes Schindelin's v2 patch introduces a fast-path optimization via a `skip_dup_check` parameter in `packfile_list_append()`, allowing callers to bypass duplicate checks when packfiles are guaranteed new.

The patch has gained momentum, with Patrick Steinhardt now explicitly approving the v2 iteration, signaling it’s ready to land despite lingering design discussions. Junio C Hamano’s earlier maintainability concerns—about the fast-path’s reliance on caller discipline and potential performance trade-offs—remain unresolved but are no longer blocking. Jeff King clarified that Git already maintains a hashmap for packfile tracking (from the 2019 fix), which prevents duplicates during "reprepare" operations, reframing the fast-path as a targeted optimization. Patrick’s proposed hashmap refactoring (moving it to `packfile_list`) is deferred as a longer-term cleanup, contingent on the patch’s acceptance.

The regression is confirmed to affect Scalar’s "shared cache repository" architecture, where scheduled fetches outpace maintenance, leaving repositories with tens of thousands of packfiles. While the patch resolves the immediate slowdown, an unrelated CI clone-time regression (from under 2 minutes to over 30) remains unresolved. The thread’s focus has narrowed to the fast-path as a tactical fix, with broader architectural improvements left for future work.
