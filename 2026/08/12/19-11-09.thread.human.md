This thread is about a critical performance regression in Git’s packfile subsystem that caused quadratic-time behavior when loading many packfiles, severely slowing down operations like `git rev-parse --short HEAD` in Microsoft Git Scalar environments. The regression, introduced in Git v2.53 (commit `589127caa730`, October 2025), undid a prior fix (`ec48540fe8`, 2019) and was traced to `packfile_store_add_pack()`’s linear scan of the packfile list before each insertion.

The author, Johannes Schindelin, proposed a v2 patch that adds a fast-path optimization to `packfile_list_append()` via a `skip_dup_check` parameter, allowing callers to skip duplicate checks for packfiles they guarantee are new. This approach was approved by Patrick Steinhardt, who initially suggested a broader hashmap-based refactoring but deferred it as a longer-term cleanup. Jeff King (Peff) later clarified that Git already maintains a hashmap for packfile tracking (introduced in `ec48540fe8`), reframing the fast-path as a targeted optimization to avoid O(N) scans even when uniqueness is already guaranteed.

Junio C Hamano, the maintainer, had raised **substantive maintainability concerns** about the `skip_dup_check` parameter relaxing the uniqueness invariant of `packfile_list`, but these were deferred for post-merge follow-up. In the latest email, Junio explicitly queued the patch for the `next` branch, signaling its readiness for integration. The patch is now locked in, with unresolved questions—such as the long-term viability of the fast-path and the unrelated CI clone regression—left for future work. The regression’s real-world impact was confirmed in Scalar’s "shared cache repository" architecture, where scheduled fetches outpace maintenance, leaving repositories with tens of thousands of packfiles.
