This thread is about a performance regression in Git’s packfile handling that causes quadratic-time slowdowns when many packfiles are present. The issue was introduced in Git v2.53 and affects operations like `git rev-parse --short HEAD` (used in shell prompts), which slowed from 0.4s to 4.5s in real-world cases. Johannes Schindelin initially proposed a fix that also claimed to address a separate `git clone` slowdown (from under 2 minutes to over 30 minutes), but he later corrected this: the clone regression is still unresolved, and the patch only fixes the `rev-parse` issue.

The patch itself adds a fast-path optimization to `packfile_store_add_pack()` to skip duplicate checks for new packfiles, eliminating the O(N²) scan in that case. Junio Hamano reviewed it favorably, calling the design "clever and clean," and it remains under review. However, Patrick Steinhardt proposed a more ambitious alternative: replacing the linked-list implementation with a hashmap to make all duplicate checks O(1). This counterproposal is now the main open question, though its urgency may have lessened now that the patch’s scope is narrower. Meanwhile, D. Ben Knoble raised whether `git maintenance` (repacking) could mitigate the remaining clone regression, adding a strategic dimension to the discussion.

The patch includes a new performance test (`t/perf/p5303-many-packs.sh`) to catch regressions in `rev-parse --short HEAD`, which Johannes clarified exercises a distinct code path not covered by existing tests. The fix is uncontroversial for its stated scope, but the unresolved clone regression and Patrick’s hashmap proposal keep the thread active. No merge has occurred yet, and the patch is still queued for review.
