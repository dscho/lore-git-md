Here’s the human-mode summary for a developer catching up on the thread:

This thread tackles a severe performance regression in Git v2.53 that caused quadratic-time slowdowns when loading many packfiles—most visibly in `git rev-parse --short HEAD` (used in shell prompts), where execution time ballooned from 0.4s to 4.5s in Microsoft Git Scalar’s shared-cache repositories. The root cause was a linear scan for duplicates in `packfile_store_add_pack()`, reintroducing an issue fixed in 2019. Johannes Schindelin’s v2 patch, now merged to `next`, adds a fast-path optimization to skip duplicate checks when the caller guarantees the packfile is new, restoring linear-time performance. The fix is narrowly scoped to the immediate regression, though Junio raised unresolved maintainability concerns about relying on caller discipline for correctness.

The discussion has since shifted to longer-term architectural questions. Jeff King (Peff) revealed that Git already uses a hashmap to track packfiles (for both duplicate detection and avoiding expensive `add_packed_git()` calls), but its placement in `packfile_store` limits its utility. Patrick Steinhardt proposed refactoring this hashmap into `packfile_list` to optimize other operations like `prepend()`, but Peff cautioned that decoupling it from `add_packed_git()` would be non-trivial. Patrick’s latest follow-up highlights that `prepend()` suffers the same quadratic inefficiency as `append()`, strengthening the case for a broader fix—though no concrete design has emerged. For now, the fast-path patch is the accepted solution, with hashmap refactoring deferred as a potential follow-up. The unrelated CI clone-time regression (30+ minutes) remains unresolved.
