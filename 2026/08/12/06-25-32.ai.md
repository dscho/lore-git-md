This is a **substantive review** of the `http.sslVerifyStatus` security feature patch (v2). Patrick Steinhardt raises fundamental questions about the patch's purpose and practical impact, challenging its value despite its technical correctness.

The review questions why Git should add OCSP staple validation at all, given that the feature is disabled by default and does not resolve the behavioral difference between OpenSSL and GnuTLS backends. With the option set to `false` (the default), OpenSSL continues to ignore staples while GnuTLS still validates them; with it set to `true`, OpenSSL fails closed but GnuTLS remains unchanged. The patch thus does not unify behavior across backends, and its security benefit is limited because users must manually enable it per-host—a step Patrick doubts anyone will take in practice.

Patrick also notes the broader context: OCSP stapling is being phased out (e.g., Let’s Encrypt dropping support), which weakens the long-term case for this feature. He asks for a concrete use case or audience that would benefit from the option, implying the patch may not justify its complexity. The review is not a rejection but a request for clearer motivation—why this change matters if it neither fixes a cross-backend inconsistency nor provides meaningful security gains out of the box.

The author’s response will likely need to address these points directly to move the patch forward. The discussion now hinges on whether the feature’s niche utility (fail-closed validation for users who opt in) outweighs its maintenance cost and the potential confusion from backend differences.
