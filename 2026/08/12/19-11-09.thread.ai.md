Subject: [PATCH] packfile: fix quadratic-time performance regression in packfile_store_add_pack()
Series version: standalone patch (no series)
Originating author: Johannes Schindelin
Thread type: bugfix (packfile subsystem)

Core problem or goal
A severe performance regression was introduced in Git v2.53 (commit 589127caa730, October 2025) that causes O(N²) behavior when loading many packfiles. The regression manifests in `git rev-parse --short HEAD` (used in shell prompts), with real-world slowdowns from 0.4s to 4.5s in Microsoft Git Scalar environments. The root cause is `packfile_store_add_pack()`’s linear scan of the packfile list before each insertion to check for duplicates. The regression undoes a prior fix (`ec48540fe8`, 2019) that had addressed the same issue. The patch does not fix a previously claimed CI clone-time regression (from under 2 minutes to over 30 minutes); that regression remains unresolved and is unrelated to this fix. The regression is now confirmed to be tied to Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles.

Current status
Under review, with maintainer approval but facing a **high-weight** design debate between the fast-path optimization and Patrick Steinhardt’s hashmap counterproposal. Junio C Hamano reviewed the patch and endorsed its design ("clever and clean"), explicitly approving the fast-path optimization. The patch remains queued for review (GitGitGadget PR #2202) and has not been merged to any integration branch. No prior versions exist. The maintenance workaround proposed by Ben Knoble is ruled out as unreliable for the reported scenario, as Scalar’s maintenance often fails to complete before machines are shut down.

Key technical details
- **Files touched**: `packfile.c` (core logic), `t/perf/p5303-many-packs.sh` (new perf test)
- **Subsystem**: packfile list management
- **New/renamed symbols**:
  - `packfile_list_append()` extended with `is_new` parameter (backward-compatible signature change; Patrick suggests renaming to `accept_duplicates`, but Johannes clarifies the parameter does not accept duplicates—it skips the duplicate check for packfiles known to be new)
  - Patrick’s counterproposal introduces `packfile_list_init()`, `packfile_list_clear()`, and a hybrid hashmap+linked-list structure for `packfile_list`
- **Behavior change**:
  - Johannes’s patch adds a fast path to skip duplicate checks when the packfile is known to be new, eliminating the O(N²) scan for that case.
  - Patrick’s counterproposal eliminates the O(N) duplicate check entirely by using a hashmap, making both `append()` and `prepend()` O(1) for duplicate checks. It also enables O(log N) reordering if the list were doubly-linked.
- **Test coverage**: New perf test `p5303-many-packs.sh` measures `git rev-parse --short HEAD` performance with 10,000 packs; Peff’s review confirms a 246% slowdown in the existing `p5303.21` test due to the regression. Johannes clarifies that the new test exercises a distinct code path (finding a unique abbreviation) not covered by the existing `load 10,000 packs` test, justifying its inclusion. GitLab’s Bencher-based CI benchmarking system failed to catch this regression due to flakiness (inconsistent runner specs) and lack of coverage for many-pack scenarios.
- **On-disk format**: No changes
- **Regression history**: The quadratic-time issue was previously fixed in `ec48540fe8` (2019) and regressed in `589127caa730` (October 2025)
- **Real-world context**: The regression is observed in Microsoft Git Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles. Maintenance is not a reliable workaround in this environment.

Open questions and loose ends
- **Design direction**: The **high-weight** debate between Johannes’s fast-path optimization and Patrick’s hashmap counterproposal remains unresolved. Johannes argues the fast-path fix is sufficient and simpler, while Patrick’s approach offers a more comprehensive solution with O(1) duplicate checks. Resolution will require further input from Junio, Johannes, and other packfile subsystem experts. The narrowed scope of the patch (addressing only the `rev-parse --short HEAD` slowdown in Scalar environments) may reduce the urgency of a more complex fix.
- **Test-coverage debate**: Peff’s question about the new perf test’s redundancy is resolved: Johannes clarified the distinct code paths exercised by `git rev-parse --short HEAD`. The broader perf-suite gaps (flakiness, lack of many-pack coverage in GitLab CI) remain unaddressed.
- **Maintenance as mitigation**: Ben Knoble’s question about whether `git maintenance` could mitigate the slowdowns is resolved: maintenance is not a reliable workaround for Scalar’s shared cache repositories, as it often fails to complete before machines are shut down. The unresolved CI clone regression (confirmed as unrelated to this patch) may still benefit from maintenance, but that is outside the scope of this thread.
