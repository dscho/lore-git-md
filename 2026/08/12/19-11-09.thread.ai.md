Subject: [PATCH] packfile: fix quadratic-time performance regression in packfile_store_add_pack()
Series version: standalone patch (no series)
Originating author: Johannes Schindelin
Thread type: bugfix (packfile subsystem)

Core problem or goal
A severe performance regression was introduced in Git v2.53 (commit 589127caa730, October 2025) that causes O(N²) behavior when loading many packfiles. The regression manifests in `git rev-parse --short HEAD` (used in shell prompts), with real-world slowdowns from 0.4s to 4.5s in Microsoft Git Scalar environments. The root cause is `packfile_store_add_pack()`’s linear scan of the packfile list before each insertion to check for duplicates. The regression undoes a prior fix (`ec48540fe8`, 2019) that had addressed the same issue. The patch does not fix a previously claimed CI clone-time regression (from under 2 minutes to over 30 minutes); that regression remains unresolved and is unrelated to this fix. The regression is now confirmed to be tied to Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles.

Current status
**Resolved for merging to 'next'**. The last open design question—whether to land Johannes Schindelin’s fast-path optimization or Patrick Steinhardt’s hashmap counterproposal—is now settled in favor of the fast-path. Junio C Hamano previously endorsed the patch as "clever and clean," and Patrick Steinhardt has conceded that the fast-path is the correct immediate fix, while his hashmap refactoring is deferred to a future series. The patch is unblocked and ready for integration. No prior versions exist.

Key technical details
- **Files touched**: `packfile.c` (core logic), `t/perf/p5303-many-packs.sh` (new perf test)
- **Subsystem**: packfile list management
- **New/renamed symbols**:
  - `packfile_list_append()` extended with `skip_dup_check` parameter (renamed from `is_new`; backward-compatible signature change). The parameter skips duplicate checks for packfiles the *caller* guarantees are new, making it clear that the caller bears responsibility for correctness.
  - Patrick’s hashmap counterproposal (`packfile_list_init()`, `packfile_list_clear()`, hybrid hashmap+linked-list structure) is deferred and will not be part of this patch.
- **Behavior change**:
  - The fast-path optimization adds a targeted fix for the quadratic-time regression by skipping duplicate checks when the packfile is known to be new. This eliminates the O(N²) scan for that case and is explicitly faster than an O(1) hashmap lookup, as it avoids the lookup entirely.
- **Test coverage**: New perf test `p5303-many-packs.sh` measures `git rev-parse --short HEAD` performance with 10,000 packs, exercising a distinct code path (finding a unique abbreviation) not covered by the existing `p5303.21` test. Peff’s review confirmed a 246% slowdown in `p5303.21` due to the regression, and Johannes clarified the new test’s necessity.
- **On-disk format**: No changes
- **Regression history**: The quadratic-time issue was previously fixed in `ec48540fe8` (2019) and regressed in `589127caa730` (October 2025)
- **Real-world context**: The regression is observed in Microsoft Git Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles.

Open questions and loose ends
- **Deferred work**: Patrick Steinhardt’s hashmap refactoring is acknowledged as a valid longer-term improvement but will be pursued independently. It could complement or eventually replace the fast-path, but no timeline or scope is set.
- **Perf-suite gaps**: GitLab’s Bencher-based CI benchmarking system still lacks coverage for many-pack scenarios and suffers from flakiness. The regression was not caught due to these gaps, but addressing them is outside the scope of this thread.
- **CI clone regression**: The unrelated regression (clone times increasing from under 2 minutes to over 30 minutes) remains unresolved.
