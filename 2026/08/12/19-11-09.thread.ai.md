Subject: [PATCH v2] packfile: fix quadratic-time performance regression in packfile_store_add_pack()
Series version: standalone patch (v2)
Originating author: Johannes Schindelin
Thread type: bugfix (packfile subsystem)

Core problem or goal
A severe performance regression was introduced in Git v2.53 (commit 589127caa730, October 2025) that causes O(N²) behavior when loading many packfiles. The regression manifests in `git rev-parse --short HEAD` (used in shell prompts), with real-world slowdowns from 0.4s to 4.5s in Microsoft Git Scalar environments. The root cause is `packfile_store_add_pack()`’s linear scan of the packfile list before each insertion to check for duplicates. The regression undoes a prior fix (`ec48540fe8`, 2019) that had addressed the same issue. The patch does not fix a previously claimed CI clone-time regression (from under 2 minutes to over 30 minutes); that regression remains unresolved and is unrelated to this fix. The regression is now confirmed to be tied to Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles. Jeff King’s latest review reveals that Git already maintains a hashmap for tracking packfiles (introduced in `ec48540fe8`), which is used to determine the `is_new`/`skip_dup_check` flag in Johannes’s patch. This existing hashmap prevents duplicates during "reprepare" operations (e.g., after `git fetch`), raising the question of why the O(N) scan persists despite this mechanism.

Current status
**Under review (design discussion reopened with new technical context)**. The v2 patch refines the fast-path optimization by renaming the `is_new` parameter to `skip_dup_check` to better reflect its behavior and clarify caller responsibility. Junio C Hamano’s latest review reopens the design discussion with **substantive maintainability concerns** about the fast-path’s reliance on caller discipline, questioning whether the consequences of duplicates (faster existence checks but slower non-existence checks) are fully understood. Jeff King’s new comment adds critical context: the existing hashmap in `packfile_store_add_pack()` already prevents duplicates during "reprepare" operations, suggesting the fast-path optimization is not a workaround for a missing hashmap but a targeted optimization to avoid the O(N) scan *even when uniqueness is already guaranteed*. This may prompt further iteration or accelerate Patrick Steinhardt’s deferred hashmap refactoring, though the latter now appears redundant unless it addresses gaps in the existing hashmap (e.g., `prepend()` operations or O(log N) reordering). No prior versions exist beyond v2.

Key technical details
- **Files touched**: `packfile-list.c`, `packfile-list.h`, `packfile.c` (core logic), `t/perf/p5303-many-packs.sh` (new perf test)
- **Subsystem**: packfile list management
- **New/renamed symbols**:
  - `packfile_list_append()` extended with `skip_dup_check` parameter (renamed from `is_new`; backward-compatible signature change). The parameter skips duplicate checks for packfiles the *caller* guarantees are new, making it clear that the caller bears responsibility for correctness.
  - Patrick’s hashmap counterproposal (`packfile_list_init()`, `packfile_list_clear()`, hybrid hashmap+linked-list structure) is deferred and now appears redundant due to the existing hashmap in `packfile_store_add_pack()`.
- **Behavior change**:
  - The fast-path optimization adds a targeted fix for the quadratic-time regression by skipping duplicate checks when the packfile is known to be new. This eliminates the O(N²) scan for that case and is explicitly faster than an O(1) hashmap lookup, as it avoids the lookup entirely.
  - Junio’s review highlights a **risk**: duplicates could make existence checks faster (if early in the list) but non-existence checks slower (requiring full scans), introducing subtle performance or correctness issues.
  - The regression occurs during *initial pack list creation* (`packfile_store_add_pack()`), affecting all operations that load packfiles, not just those that open individual packs or search for object IDs.
  - The existing hashmap (introduced in `ec48540fe8`) already prevents duplicates during "reprepare" operations, raising the question of why the O(N) scan persists. This suggests the fast-path optimization is not a workaround for a missing hashmap but a targeted optimization to avoid the scan *even when uniqueness is already guaranteed*.
- **Test coverage**: New perf test `p5303-many-packs.sh` measures `git rev-parse --short HEAD` performance with 10,000 packs, exercising a distinct code path (finding a unique abbreviation) not covered by the existing `p5303.21` test. Peff’s review confirmed a 246% slowdown in `p5303.21` due to the regression, and the necessity of the new test is now clarified: it targets the 10,000-pack case where quadratic-time behavior is most pronounced, justifying its inclusion despite some overlap with existing tests.
- **On-disk format**: No changes
- **Regression history**: The quadratic-time issue was previously fixed in `ec48540fe8` (2019) and regressed in `589127caa730` (October 2025). The existing hashmap (introduced in `ec48540fe8`) is now revealed as a key part of the historical context.
- **Real-world context**: The regression is observed in Microsoft Git Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles.

Open questions and loose ends
- **Design robustness**: Junio’s review raises **substantive concerns** about the fast-path’s long-term maintainability. The `skip_dup_check` parameter relaxes the uniqueness invariant of `packfile_list`, relying on caller discipline. Future changes could break this assumption, leading to duplicates with unclear consequences (faster existence checks but slower non-existence checks). Jeff King’s new comment adds critical context: the existing hashmap already prevents duplicates during "reprepare" operations, suggesting the fast-path is not a workaround for a missing hashmap but a targeted optimization. This may prompt further iteration or accelerate Patrick’s deferred hashmap refactoring, though the latter now appears redundant unless it addresses gaps in the existing hashmap (e.g., `prepend()` operations or O(log N) reordering).
- **Deferred work**: Patrick Steinhardt’s hashmap refactoring is acknowledged as a valid longer-term improvement but will be pursued independently. It could complement or eventually replace the fast-path, but its necessity is now in question due to the existing hashmap. No timeline or scope is set.
- **Perf-suite gaps**: GitLab’s Bencher-based CI benchmarking system still lacks coverage for many-pack scenarios and suffers from flakiness. The regression was not caught due to these gaps, but addressing them is outside the scope of this thread.
- **CI clone regression**: The unrelated regression (clone times increasing from under 2 minutes to over 30 minutes) remains unresolved.
- **Existing hashmap limitations**: Jeff King’s comment raises the question of why the existing hashmap (introduced in `ec48540fe8`) does not eliminate the O(N) scan. Possible explanations include:
  - The hashmap is not used in all code paths (e.g., `prepend()` operations).
  - The hashmap is not maintained during certain operations (e.g., manual packfile list modifications).
  - The hashmap is not sufficient for the fast-path’s optimization (e.g., it does not enable O(log N) reordering as claimed in Patrick’s counterproposal).
