Subject: [PATCH v2] packfile: fix quadratic-time performance regression in packfile_store_add_pack()
Series version: standalone patch (v2)
Originating author: Johannes Schindelin
Thread type: bugfix (packfile subsystem)

Core problem or goal
A severe performance regression was introduced in Git v2.53 (commit 589127caa730, October 2025) that causes O(N²) behavior when loading many packfiles. The regression manifests in `git rev-parse --short HEAD` (used in shell prompts), with real-world slowdowns from 0.4s to 4.5s in Microsoft Git Scalar environments. The root cause is `packfile_store_add_pack()`’s linear scan of the packfile list before each insertion to check for duplicates. The regression undoes a prior fix (`ec48540fe8`, 2019) that had addressed the same issue. The patch does not fix a previously claimed CI clone-time regression (from under 2 minutes to over 30 minutes); that regression remains unresolved and is unrelated to this fix. The regression is now confirmed to be tied to Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles. Jeff King’s review reveals that Git already maintains a hashmap for tracking packfiles (introduced in `ec48540fe8`), which is used to determine the `is_new`/`skip_dup_check` flag in Johannes’s patch. This existing hashmap prevents duplicates during "reprepare" operations (e.g., after `git fetch`), but its placement in `packfile_store` limits its utility for other operations (e.g., `prepend()` or reordering). Patrick Steinhardt now proposes refactoring the existing hashmap by moving it into `packfile_list` to make it more broadly usable, addressing the redundancy while pursuing a narrower hashmap-based solution.

Key technical details
- **Files touched**: `packfile-list.c`, `packfile-list.h`, `packfile.c` (core logic), `t/perf/p5303-many-packs.sh` (new perf test)
- **Subsystem**: packfile list management
- **New/renamed symbols**:
  - `packfile_list_append()` extended with `skip_dup_check` parameter (renamed from `is_new`; backward-compatible signature change). The parameter skips duplicate checks for packfiles the *caller* guarantees are new, making it clear that the caller bears responsibility for correctness.
  - Patrick’s proposed hashmap refactoring would move the existing hashmap from `packfile_store` to `packfile_list`, exposing it for broader use (e.g., `prepend()` operations or O(log N) reordering).
- **Behavior change**:
  - The fast-path optimization adds a targeted fix for the quadratic-time regression by skipping duplicate checks when the packfile is known to be new. This eliminates the O(N²) scan for that case and is explicitly faster than an O(1) hashmap lookup, as it avoids the lookup entirely.
  - Junio’s review highlights a **risk**: duplicates could make existence checks faster (if early in the list) but non-existence checks slower (requiring full scans), introducing subtle performance or correctness issues.
  - The regression occurs during *initial pack list creation* (`packfile_store_add_pack()`), affecting all operations that load packfiles, not just those that open individual packs or search for object IDs.
  - The existing hashmap (introduced in `ec48540fe8`) prevents duplicates during "reprepare" operations, but its placement in `packfile_store` limits its utility for other operations. Patrick’s refactoring proposal aims to address this.
- **Test coverage**: New perf test `p5303-many-packs.sh` measures `git rev-parse --short HEAD` performance with 10,000 packs, exercising a distinct code path (finding a unique abbreviation) not covered by the existing `p5303.21` test. Peff’s review confirmed a 246% slowdown in `p5303.21` due to the regression, and the necessity of the new test is now clarified: it targets the 10,000-pack case where quadratic-time behavior is most pronounced.
- **On-disk format**: No changes
- **Regression history**: The quadratic-time issue was previously fixed in `ec48540fe8` (2019) and regressed in `589127caa730` (October 2025). The existing hashmap (introduced in `ec48540fe8`) is now revealed as a key part of the historical context.
- **Real-world context**: The regression is observed in Microsoft Git Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles.

Open questions and loose ends
- **Design robustness**: Junio’s **substantive maintainability concerns** about the fast-path’s long-term viability remain unresolved but are now deferred. The `skip_dup_check` parameter relaxes the uniqueness invariant of `packfile_list`, relying on caller discipline. Future changes could break this assumption, leading to duplicates with unclear consequences (faster existence checks but slower non-existence checks). Jeff King’s comment confirms the existing hashmap prevents duplicates during "reprepare" operations, but the fast-path’s necessity for other code paths remains unresolved.
- **Existing hashmap limitations**: Why the O(N) scan persists despite the hashmap is still unexplained. Possible explanations include:
  - The hashmap is not used in all code paths (e.g., `prepend()` operations).
  - The hashmap is not maintained during certain operations (e.g., manual packfile list modifications).
  - The hashmap’s placement in `packfile_store` limits its utility for broader use.
  Patrick’s refactoring proposal (moving the hashmap to `packfile_list`) could address these gaps but is not yet implemented and is now decoupled from the immediate fix.
- **Deferred work**: Patrick Steinhardt’s hashmap refactoring is now explicitly deferred as a longer-term cleanup, contingent on the fast-path’s acceptance. No timeline or scope is set.
- **Perf-suite gaps**: GitLab’s Bencher-based CI benchmarking system still lacks coverage for many-pack scenarios and suffers from flakiness. The regression was not caught due to these gaps, but addressing them is outside the scope of this thread.
- **CI clone regression**: The unrelated regression (clone times increasing from under 2 minutes to over 30 minutes) remains unresolved.
