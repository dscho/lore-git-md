Subject: [PATCH] packfile: fix quadratic-time performance regression in packfile_store_add_pack()
Series version: standalone patch (no series)
Originating author: Johannes Schindelin
Thread type: bugfix (packfile subsystem)

Core problem or goal
A severe performance regression was introduced in Git v2.53 (commit 589127caa730, October 2025) that causes O(N²) behavior when loading many packfiles. The regression manifests in common operations like `git rev-parse --short HEAD` (used in shell prompts) and `git clone`, with real-world slowdowns from 0.4s to 4.5s and from under 2 minutes to over 30 minutes, respectively. The root cause is `packfile_store_add_pack()`’s linear scan of the packfile list before each insertion to check for duplicates. The regression undoes a prior fix (`ec48540fe8`, 2019) that had addressed the same issue.

Current status
Under review, with maintainer approval but now facing a **high-weight** design alternative and **medium-weight** test-coverage debate. Junio C Hamano reviewed the patch and endorsed its design ("clever and clean"), explicitly approving the fast-path optimization. The patch remains queued for review (GitGitGadget PR #2202) and has not been merged to any integration branch. No prior versions exist.

Key technical details
- **Files touched**: `packfile.c` (core logic), `t/perf/p5303-many-packs.sh` (new perf test)
- **Subsystem**: packfile list management
- **New/renamed symbols**:
  - `packfile_list_append()` extended with `is_new` parameter (backward-compatible signature change; Patrick suggests renaming to `accept_duplicates`)
  - Patrick’s counterproposal introduces `packfile_list_init()`, `packfile_list_clear()`, and a hybrid hashmap+linked-list structure for `packfile_list`
- **Behavior change**:
  - Johannes’s patch adds a fast path to skip duplicate checks when the packfile is known to be new, eliminating the O(N²) scan for that case.
  - Patrick’s counterproposal eliminates the O(N) duplicate check entirely by using a hashmap, making both `append()` and `prepend()` O(1) for duplicate checks. It also enables O(log N) reordering if the list were doubly-linked.
- **Test coverage**: New perf test `p5303-many-packs.sh` measures `git rev-parse --short HEAD` performance with 10,000 packs; Peff’s review confirms a 246% slowdown in the existing `p5303.21` test due to the regression. GitLab’s Bencher-based CI benchmarking system failed to catch this regression due to flakiness (inconsistent runner specs) and lack of coverage for many-pack scenarios.
- **On-disk format**: No changes
- **Regression history**: The quadratic-time issue was previously fixed in `ec48540fe8` (2019) and regressed in `589127caa730` (October 2025)

Open questions and loose ends
- **Design direction**: Patrick’s hashmap counterproposal introduces a **new high-weight open question**: whether the added complexity of a hashmap is justified to eliminate quadratic-time behavior entirely, or whether Johannes’s fast-path optimization is sufficient. Resolution will require input from Johannes, Junio, and other packfile subsystem experts.
- **Test redundancy**: Peff questions whether the new `abbreviate with 10,000 packs` test adds value beyond the existing `load 10,000 packs` test (`p5303.21`). Patrick’s follow-up highlights systemic perf-suite gaps (flakiness, human judgment barriers) and GitLab CI’s lack of coverage for many-pack scenarios, but does not resolve the redundancy question.
- **Maintenance as mitigation**: Ben Knoble asks whether `git maintenance` (repacking) could address the reported slowdowns in monorepo checkouts and CI clones, either as a substitute for or complement to the code fix. This introduces a **strategic dimension**: whether the problem should be solved at the infrastructure level (via maintenance) or the code level. Resolution will require input from Johannes or another domain expert on whether maintenance is a viable workaround for the reported scenarios.
