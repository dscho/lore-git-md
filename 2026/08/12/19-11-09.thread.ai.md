Subject: [PATCH v2] packfile: fix quadratic-time performance regression in packfile_store_add_pack()
Series version: standalone patch (v2)
Originating author: Johannes Schindelin
Thread type: bugfix (packfile subsystem)

Core problem or goal
A severe performance regression was introduced in Git v2.53 (commit 589127caa730, October 2025) that causes O(N²) behavior when loading many packfiles. The regression manifests in `git rev-parse --short HEAD` (used in shell prompts), with real-world slowdowns from 0.4s to 4.5s in Microsoft Git Scalar environments. The root cause is `packfile_store_add_pack()`’s linear scan of the packfile list before each insertion to check for duplicates. The regression undoes a prior fix (`ec48540fe8`, 2019) that had addressed the same issue. The patch does not fix a previously claimed CI clone-time regression (from under 2 minutes to over 30 minutes); that regression remains unresolved and is unrelated to this fix. The regression is now confirmed to be tied to Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles. Jeff King’s review reveals that Git already maintains a hashmap for tracking packfiles (introduced in `ec48540fe8`), which is used to determine the `skip_dup_check` flag in Johannes’s patch. This existing hashmap prevents duplicates during "reprepare" operations (e.g., after `git fetch`), but its placement in `packfile_store` limits its utility for other operations (e.g., `prepend()` or reordering). Patrick Steinhardt’s latest follow-up highlights that the `prepend()` operation suffers from the same quadratic-time inefficiency as `append()`, strengthening the case for a broader refactoring, though Peff’s skepticism about decoupling the hashmap from `add_packed_git()` remains unresolved.

Key technical details
- **Files touched**: `packfile-list.c`, `packfile-list.h`, `packfile.c` (core logic), `t/perf/p5303-many-packs.sh` (new perf test)
- **Subsystem**: packfile list management
- **New/renamed symbols**:
  - `packfile_list_append()` extended with `skip_dup_check` parameter (renamed from `is_new`; backward-compatible signature change). The parameter skips duplicate checks for packfiles the *caller* guarantees are new, making it clear that the caller bears responsibility for correctness.
  - The existing hashmap in `packfile_store` (introduced in `ec48540fe8`) is now confirmed to serve a dual role: preventing duplicates during "reprepare" operations *and* avoiding expensive `add_packed_git()` calls (allocations, `stat()`). This dual role complicates Patrick’s proposed refactoring (moving the hashmap to `packfile_list`).
  - `packfile_list_prepend()` is now identified as suffering from the same quadratic-time inefficiency as `append()`, due to its lack of a fast-path or hashmap-based duplicate check.
- **Behavior change**:
  - The fast-path optimization adds a targeted fix for the quadratic-time regression by skipping duplicate checks when the packfile is known to be new. This eliminates the O(N²) scan for that case and is explicitly faster than an O(1) hashmap lookup, as it avoids the lookup entirely.
  - Junio’s review highlights a **risk**: duplicates could make existence checks faster (if early in the list) but non-existence checks slower (requiring full scans), introducing subtle performance or correctness issues.
  - The regression occurs during *initial pack list creation* (`packfile_store_add_pack()`), affecting all operations that load packfiles, not just those that open individual packs or search for object IDs.
  - The existing hashmap prevents duplicates during "reprepare" operations, but its placement in `packfile_store` limits its utility for other operations. Peff’s latest comment reveals that the hashmap also avoids expensive `add_packed_git()` calls, complicating any refactoring.
  - Both `append()` and `prepend()` operations are now confirmed to suffer from quadratic-time inefficiency in the absence of a hashmap-based duplicate check.
- **Test coverage**: New perf test `p5303-many-packs.sh` measures `git rev-parse --short HEAD` performance with 10,000 packs, exercising a distinct code path (finding a unique abbreviation) not covered by the existing `p5303.21` test. Peff’s review confirmed a 246% slowdown in `p5303.21` due to the regression, and the necessity of the new test is now clarified: it targets the 10,000-pack case where quadratic-time behavior is most pronounced.
- **On-disk format**: No changes
- **Regression history**: The quadratic-time issue was previously fixed in `ec48540fe8` (2019) and regressed in `589127caa730` (October 2025). The existing hashmap (introduced in `ec48540fe8`) is now revealed as a key part of the historical context, with its dual role in duplicate detection and performance.
- **Real-world context**: The regression is observed in Microsoft Git Scalar’s "shared cache repository" architecture, where scheduled fetches deposit packfiles faster than maintenance can repack them, leaving repositories with tens of thousands of packfiles.

Open questions and loose ends
- **Design robustness**: Junio’s **substantive maintainability concerns** about the fast-path’s long-term viability remain unresolved but are deferred. The `skip_dup_check` parameter relaxes the uniqueness invariant of `packfile_list`, relying on caller discipline. Future changes could break this assumption, leading to duplicates with unclear consequences (faster existence checks but slower non-existence checks). Jeff King’s comment confirms the existing hashmap prevents duplicates during "reprepare" operations, but the fast-path’s necessity for other code paths remains unresolved.
- **Hashmap refactoring feasibility**: Peff’s latest reply **casts doubt** on Patrick’s proposal to move the hashmap into `packfile_list`, noting that the hashmap’s current role—avoiding `add_packed_git()` overhead—makes it non-trivial to relocate without broader architectural changes. The newly highlighted symmetry between `append()` and `prepend()` inefficiencies adds weight to the refactoring case, but no concrete design or timeline exists. The refactoring is now **premature** given the single-caller context (`packfile_store_add_pack()`), but Peff leaves the door open for future work if more use cases emerge or the architectural challenges are addressed.
- **Deferred work**: Patrick’s hashmap refactoring is now explicitly deferred as a longer-term cleanup, contingent on the fast-path’s acceptance *and* the emergence of additional callers or clearer performance trade-offs. No timeline or scope is set.
- **Perf-suite gaps**: GitLab’s Bencher-based CI benchmarking system still lacks coverage for many-pack scenarios and suffers from flakiness. The regression was not caught due to these gaps, but addressing them is outside the scope of this thread.
- **CI clone regression**: The unrelated regression (clone times increasing from under 2 minutes to over 30 minutes) remains unresolved.
