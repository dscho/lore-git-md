This is a **design discussion follow-up** in the ongoing thread about unified interactive patch selection in Git. Junio C Hamano responds to Johannes Schindelin’s revival of the stash-mode patch, clarifying his vision for a minimal, reference-like solution that unifies triage actions (stage/discard/defer) into a single session without overloading `git add -p`.

Junio agrees that the core functionality—classifying changes into three (or four, if stash is included) categories—is valuable but reiterates his long-standing objection to extending `git add -p` with working-tree-munging features. His concern is not the stash-mode idea itself but the command scope: `git add -p` should focus on staging, not modifying the working tree. Instead, he suggests that the solution should be a *new* command (or a new mode for an existing command) that handles all three (or four) actions in one session, avoiding the need to switch between `git add -p` and `git checkout -p`.

The email introduces a new dimension: whether to include stash as a fourth category ("stash away") alongside stage, keep, and discard. This would allow users to defer hunks by stashing them, aligning with Dscho’s stash-mode proposal but implemented in a way that avoids overloading `git add -p`. Junio’s framing suggests that stash could be a natural fit for a unified triage workflow, provided it is housed in a command whose scope includes working-tree modifications.

Key technical details for follow-up:
- **Command scope**: Junio’s objection to extending `git add -p` is philosophical (it should not munge the working tree) and practical (what about `git checkout -p`?). His preference is for a new command or mode that explicitly handles all triage actions.
- **Stash as a fourth category**: Junio is open to including stash as a deferral mechanism, which would make the workflow more flexible (stage/stash/keep/discard) but also more complex. This tests whether the project is willing to embrace stash as a core triage tool.
- **Implementation path**: The email does not specify whether the new command should be a standalone tool (e.g., `git triage -p`, as Peff suggested) or a mode for an existing command (e.g., `git add --triage`). The latter might feel more integrated but risks overloading an existing command.
- **Backwards compatibility**: Junio does not address whether stash-mode would clutter the stash or interfere with existing workflows, leaving that as an open question for follow-up.

Junio’s reply refines the thread’s focus:
- The priority is a *single-session workflow* for triage, not a polished UI.
- The solution should avoid overloading `git add -p` or `git checkout -p`.
- Stash is a viable deferral mechanism, but its inclusion depends on whether the project is willing to embrace it as a core triage tool.
- The discussion is now centered on *where* to implement the functionality (new command vs. mode) rather than *whether* to implement it.

This email narrows the design space but leaves key questions unanswered:
- Would a new command (e.g., `git triage -p`) fragment the workflow or provide a cleaner implementation path?
- How would stash-mode interact with external tools like lazygit? Would it make Git’s interactive machinery more or less consumable?
- What would the new command’s interface look like, and how would it avoid the pitfalls of overloading existing commands?

The thread is now at a crossroads: Junio’s reply provides a clear direction (new command, stash as an option) but leaves the details to be hashed out. Dscho’s stash-mode patch could serve as a starting point, but it would need to be reworked to fit Junio’s vision of a separate command. Patrick Steinhardt’s refined proposal for *basic* UI improvements (e.g., navigable hunk selection) may still be relevant if the new command adopts a prompt-loop interface, but Junio’s latest reply suggests that UI polish is not a priority. Stefan Haller’s external-tool proposal remains on the table, but Junio’s focus on a built-in solution implies that API improvements are not the immediate goal. Peff’s suggestion of a separate command (`git triage -p`) now looks like the most viable path forward.
