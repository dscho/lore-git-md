This is a brief follow-up in the long-running design discussion about unified interactive patch selection in Git. Junio C Hamano responds to Jeff King’s (Peff) email, clarifying his own stance on the proposed stash-mode enhancement for `git add -p`.

Junio acknowledges Peff’s point about the "weirdness" of `git add -p` modifying the working tree (via stash) but aligns with Peff’s broader view: the feature itself is valuable, and the design quirks are not insurmountable. His reply is short and conciliatory, emphasizing agreement on the *goal*—a unified triage workflow—rather than dwelling on implementation details. This suggests the discussion is moving toward practical next steps, though no concrete proposal or patch has emerged yet.

The thread remains focused on the core problem: how to efficiently triage hunks into staged, kept, discarded, or stashed states in a single session. Junio’s earlier emails ruled out overloading `git add -p` or `git checkout -p`, so the likely path forward is a new command (e.g., `git triage -p`) or a new mode for an existing command (e.g., `git add --triage`). This email doesn’t advance the design further, but it reinforces that the project’s leadership sees value in solving this workflow gap.

For readers tracking this thread, the key takeaway is that the philosophical objections to the stash-mode approach have softened. The remaining questions are technical: where to implement the feature (new command vs. mode), how to integrate stash cleanly, and how to avoid unintuitive side effects. The discussion is still in the design phase, but the tone is now collaborative rather than contentious. If you care about interactive staging workflows, this is a thread to watch—though don’t expect patches immediately.
