This is a **substantive review** from Junio C Hamano on Yoichi Nakayama’s patch series improving error messages for ambiguous remote branch names in `git worktree add`. The review advances the discussion by proposing an alternative implementation that extends `unique_tracking_name()` to optionally return the list of conflicting remotes, rather than relying on a command-based advice message. Junio’s patch demonstrates how this could work for the `git checkout`/`git switch` commands, refactoring the advice logic into a shared helper (`be_explicit()`) and showing how the new optional feature could be added without disrupting existing callers.

The key technical change is the addition of a `struct string_list *dwim_remote_names` parameter to `unique_tracking_name()`, allowing the function to return the names of all remotes that contain the ambiguous branch. This enables the advice message to list the conflicting remotes statically (e.g., "the branch exists on `origin`, `upstream`") rather than requiring users to run a separate command. Junio argues this approach is more user-friendly because it provides immediate clarity without requiring additional steps, and it avoids the need for users to parse or execute shell commands. The patch also refactors the advice logic in `parse_remote_branch()` to use the new helper, improving code readability and reducing duplication.

Junio’s patch touches four files: `builtin/checkout.c` (refactoring and new helper), `builtin/worktree.c` (updating calls to `unique_tracking_name()`), `checkout.c` (extending `unique_tracking_name()` to collect remote names), and `checkout.h` (updating the function signature). The implementation is backward-compatible: existing callers (like `worktree add`) can pass `NULL` for the new parameter and continue to work unchanged. The advice message in `be_explicit()` is tailored to the command (`checkout` or `switch`) and includes both a static list of remotes and a suggestion to use `--track` or set `checkout.defaultRemote` for future disambiguation.

The review does not reject Yoichi’s command-based approach outright but presents a compelling alternative that prioritizes immediate usability. The unresolved question is whether the static list of remotes (Junio’s preference) or the command-based discovery (Yoichi’s current implementation) is more effective for user discovery. Junio’s patch also addresses the misindentation in `parse_remote_branch()` and clarifies the edge case around detached HEAD workflows, noting that users specifying ambiguous branch names are likely making a mistake rather than intentionally targeting a detached HEAD. The patch is well-structured, with clear commit boundaries and no workflow disruptions, and it provides a concrete path forward for unifying the advice messages across `checkout`, `switch`, and `worktree add`.
