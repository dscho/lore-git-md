This is a **security feature patch** that adds `http.sslVerifyStatus` to enable OCSP staple validation in Git’s HTTPS certificate verification. It is the third iteration of a standalone patch, addressing Junio C Hamano’s procedural feedback (test script numbering conflict) while leaving the core functionality unchanged.

The patch introduces a new boolean configuration option, `http.sslVerifyStatus`, which defaults to `false` but can be set to `true` to enforce OCSP staple validation via libcurl’s `CURLOPT_SSL_VERIFYSTATUS`. This closes a security gap where Git (when linked against OpenSSL) silently ignores stapled OCSP responses, potentially accepting revoked certificates. The design is fail-closed: if the server does not provide a staple, the connection fails. Per-URL overrides (e.g., `http.https://example.com/.sslVerifyStatus`) are supported without additional plumbing.

Key technical details include the option’s behavior across TLS backends: OpenSSL-linked builds ignore staples unless explicitly enabled, while GnuTLS-linked builds already enforce staple validation under `http.sslVerify`. The patch fails loudly if the backend cannot support the feature, avoiding silent fallbacks. The test suite (`t/t5568-http-verify-status.sh`) verifies the fail-closed path and per-URL configuration, using a server that staples nothing to ensure the option’s effect is observable.

The motivation remains centered on government and government-adjacent users (e.g., US Department of Defense PKI) who mandate OCSP stapling. The author’s earlier response to Patrick Steinhardt’s challenge framed the threat model as a low-to-medium severity CVE risk (stolen private key impersonation enabling data exfiltration), providing concrete evidence for the feature’s necessity. The default remains `false` to avoid breaking remotes that do not support stapling, but the long-term question of whether to flip the default or warn users about ignored staples remains open.

This version resolves the only outstanding procedural issue (test numbering) and is ready for substantive review. The patch is well-documented, thoroughly tested, and addresses a real-world security concern, though its maintenance burden (given OCSP stapling’s declining relevance) may still be debated. The implementation is minimal and focused, touching only `http.c` and `Documentation/config/http.adoc`.
