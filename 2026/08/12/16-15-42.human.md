This is a follow-up in the ongoing discussion about a bugfix patch that prevents a segmentation fault when `git --shallow-file` is called without a required argument. The patch itself is a straightforward, low-risk fix for a real crash, but the thread has shifted to procedural and test-coverage questions.

Christian Couder responds to Junio C Hamano’s review by defending the patch’s current form. He clarifies that the "while at it" reordering of the `--shallow-file` logic was intentional, aiming to align it with the established pattern used by other similar options (`--git-dir`, `--namespace`, `--work-tree`, etc.). This consistency argument is now explicit: the patch follows the two-line error-reporting convention (`fprintf` + `usage`) seen elsewhere in `git.c`, and Christian rejects the idea of splitting the patch or adopting a different style.

On test coverage, Christian notes that `--shallow-file` is an undocumented, internal-only option with no existing direct tests—its behavior is only verified indirectly in shallow-clone and fetch/push test scripts. He points out that `--config-env` (in `t/t1300-config.sh`) is the only similar option with explicit coverage for missing values, but argues that `--shallow-file` doesn’t belong in that test file. While he’s open to expanding test coverage (Junio’s option 3), he doesn’t see it as a clear improvement over the current patch’s single test case.

The discussion remains focused on process rather than correctness. Junio’s concerns about patch scope and test completeness are still unresolved, but neither blocks merging. The patch is ready to land as-is, though a future follow-up to add broader test coverage for similar options might be warranted. For now, the fix addresses a real crash with no known downsides, and the stylistic choices are defended as consistent with the codebase.
