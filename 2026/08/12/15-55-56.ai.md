This is a security bugfix targeting the `bundle-uri` subsystem, specifically addressing CVE-2026-62960. The patch prevents Git from automatically fetching bundle URIs advertised by servers unless their protocol is explicitly allowed by Git's `protocol.*.allow` configuration. By default, this blocks "file" URIs (including UNC paths on Windows), which could otherwise be exploited to leak NTLM credentials via outbound SMB connections. The fix is narrowly scoped to the clone/fetch code path (`fetch_bundle_list()`), leaving `ls-remote` and user-supplied `--bundle-uri` arguments unaffected. A new test file (`t/lib-bundle-uri-protocol.sh`) verifies that non-HTTP(S) URIs are ignored unless explicitly re-enabled (e.g., via `protocol.file.allow=always`), including UNC paths on Windows.

The patch is well-motivated and clearly explains the attack vector: servers advertising malicious bundle URIs could trick Git into opening arbitrary local/UNC paths, which on Windows would trigger transparent NTLM authentication. The implementation is clean, leveraging existing `is_transport_allowed()` logic and adding a `sanitize_bundle_list()` helper to filter out disallowed URIs before fetching. The commit message notes this was already released in Git for Windows v2.55.0(4) and underwent private review in a GitHub security advisory, suggesting it has been vetted for correctness.

Key technical details for follow-up discussion:
- **Files touched**: `bundle-uri.c` (core logic) and `t/lib-bundle-uri-protocol.sh` (tests).
- **New functions**: `bundle_uri_protocol()` (extracts protocol from URI) and `sanitize_bundle_list()` (filters disallowed URIs).
- **Behavior change**: Advertised bundle URIs are now subject to `protocol.*.allow` restrictions; skipped URIs trigger a warning.
- **Test coverage**: Includes cases for local paths, `file://` URIs, and UNC paths (on Windows), with and without `protocol.file.allow=always`.
- **Backwards compatibility**: User-supplied `--bundle-uri` arguments bypass the check, preserving existing workflows.

The patch is likely to be uncontroversial, as it aligns with Git's existing protocol allow-list mechanism and addresses a clear security risk. The only potential discussion point might be whether the warning message for skipped URIs is sufficiently actionable for users.
