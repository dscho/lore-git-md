Thread identity
Subject: Unexpected pseudo-commits in custom `git lg` alias output
Series version: N/A (bug report)
Originating author: Marcel Svitalský
Thread type: bug report

Core problem or goal
A user observed four spurious pseudo-commits—three labeled “Notes added by 'git notes append' - rewrite-analytics” and one “chatter: initialize notes ref - chatter”—appearing at the top of the graph produced by a custom `git lg` alias (`git log --graph --all --oneline --decorate`). These commits were invisible in Sublime Merge and IntelliJ IDEA, appeared inconsistently after resets or new commits, and were believed to originate from Git’s notes or hook machinery despite the user’s enabled hooks list being empty. The goal was to understand why these commits surfaced only in the CLI alias and how to suppress them while retaining the alias’s intended project-commit output.

Current status
Resolved. The root cause was identified as the `--all` flag in the alias, which includes all refs (including Git notes `refs/notes/rewrite-analytics` and `refs/notes/chatter`), forming a disconnected graph. This is not a bug but an expected consequence of `--all`. Marcel Svitalský confirmed that workarounds—replacing `--all` with `--branches --tags --remotes` or using `--exclude='refs/notes/*' --all`—successfully suppress the spurious notes refs. Junio C Hamano later added that `--branches`, `--tags`, and `--remotes` are the standard narrower alternatives to `--all` for excluding notes. The user’s final preference was for `--exclude='refs/notes/*' --all` to retain stashes in the log output while filtering notes. The notes’ appearance was attributed to background tooling (e.g., lazygit or IntelliJ IDEA) and deemed environment-specific rather than a Git regression. Junio reflected on the unintuitive nature of `--all`’s behavior for end-user-facing `git log`, noting that while it may make sense for plumbing commands like `git rev-list`, altering this behavior at this stage would be impractical. Kristoffer Haugsbakk’s follow-up speculated that `--all` may have been designed before Git notes existed, with the intent to include custom refs users were expected to be aware of, and noted that Git notes require explicit refspecs to push or fetch, making them less likely to propagate unintentionally. The discussion underscored the tension between plumbing-level flexibility and porcelain-level usability but did not propose changes or reopen the thread.

Key technical details
- Command: `git log --graph --all --oneline --decorate` (custom alias `git lg`)
- Spurious refs: `refs/notes/rewrite-analytics` and `refs/notes/chatter` (legitimate Git notes, likely generated by background tooling such as `rewrite-analytics`, `chatter`, or IDE integrations)
- Environment: tmux + mate-terminal, Git 2.55.0 (with Rust support and fsmonitor--daemon)
- Discrepancy: CLI showed pseudo-commits due to `--all`; GUI tools (Sublime Merge, IntelliJ IDEA) likely filter refs by default (e.g., omitting `--all` or applying implicit exclusions)
- Hooks: user’s enabled hooks list was empty; notes were appended by Git components, not user-configured hooks
- On-disk: no format changes; issue was purely cosmetic in log output
- Workarounds: `--branches --tags --remotes` (narrower scope) or `--exclude='refs/notes/*' --all` (preserves `--all` coverage while filtering notes; preferred by the user to retain stashes)
- Junio’s observation: `--all`’s inclusion of notes and stash refs feels unintuitive for `git log`, though it may be justified for plumbing commands like `git rev-list`. No changes were proposed due to the impracticality of altering this behavior late in Git’s lifecycle.
- Kristoffer’s observation: `--all` may predate Git notes and was designed to include custom refs users were expected to manage. Git notes require explicit refspecs to push or fetch, limiting unintended propagation, but third-party tools may use them for metadata, exposing implementation details when `--all` is used.
