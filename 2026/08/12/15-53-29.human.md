This is a **security feature patch** that adds `http.sslVerifyStatus` to enable OCSP staple validation in Git's HTTPS connections. The author, Grayson Gordon, responds to Patrick Steinhardt's substantive review by providing a clear, real-world use case: government and defense-sector customers who rely on OCSP-stapled certificates issued by US Department of Defense PKI CAs. These users—particularly those using OpenSSL-linked Git binaries—currently face a security gap where revoked certificates are accepted, creating a low-to-medium severity risk of data exfiltration via impersonated Git servers.

The patch remains well-motivated and technically sound. Grayson’s response addresses Patrick’s concerns head-on: the feature is not about unifying backend behavior (OpenSSL vs. GnuTLS) but about giving users who *need* staple validation a way to enforce it. The default (`false`) is a pragmatic choice to avoid breaking existing setups, but the per-URL override (`http.https://example.com/.sslVerifyStatus`) allows targeted enforcement where it matters. The author’s firsthand experience with affected GitLab customers (especially those requiring FIPS compliance) lends credibility to the argument that this is not a theoretical edge case but a practical requirement for certain environments.

The threat model is concrete: an attacker with a stolen private key could impersonate a revoked Git server, and OpenSSL-linked clients would accept it unless staple validation is explicitly enabled. While OCSP stapling is declining in some contexts (e.g., Let’s Encrypt), it remains critical for DoD and other government PKI systems, which are unlikely to abandon it soon. The patch’s fail-closed design (connections fail if staples are missing) aligns with security best practices, and the author’s comparison to libcurl CVEs (e.g., CVE-2024-0853) underscores the real-world risks of ignoring staples.
