This is a reply in an ongoing feature discussion about adding a `git squash` command.

Matej Dujava responds to the original RFC by pointing out that Git already supports a workflow for squashing commits using `fixup!` or `squash!` commits combined with `git rebase --autosquash`. This is a more flexible approach than the proposed `git squash <n>`, as it allows selective squashing of commits based on their content rather than just the last *n* commits. Matej also links to a long-running patch series (v13) that proposed a `git history squash` command, which would preserve the message of the first commit in the squashed range. The linked series suggests that this idea has been discussed before, though the proposed implementation and scope differ from the original RFC.

The reply does not engage with the technical feasibility or edge cases of the proposed `git squash` command but instead highlights existing functionality that achieves a similar goal. This shifts the discussion toward whether a new command is necessary or if the existing tools (`rebase --autosquash` and `git history squash`) already address the use case. The thread now has two distinct directions: the original proposal for a simple `git squash <n>` and the more nuanced `git history squash` from the linked series. No maintainer or core contributor has weighed in yet, so the discussion remains open-ended.
