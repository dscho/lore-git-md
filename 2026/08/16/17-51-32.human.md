This is a **bugfix** patch targeting a critical memory-safety flaw in `git worktree add` that can cause data loss. René Scharfe has taken sole authorship of this patch at Junio C Hamano’s suggestion to simplify DCO compliance, though he acknowledges Matthias Aßhauer’s original discovery of the bug. The patch itself is now **ready for `next`**—Junio explicitly calls it "obvious and clear" and endorses the approach.

The fix addresses an out-of-bounds read in `worktree_basename()` (`builtin/worktree.c`) that occurs when the input path is empty or contains only directory separators. The original code used pointer arithmetic to compute the basename length, which underflows when the input is empty, leading to undefined behavior. René’s patch replaces the problematic pointer-decrement loop with an integer-index loop that safely stops at the string boundary, eliminating the underflow risk while preserving the function’s interface. The change is minimal (3 insertions, 5 deletions) and confined to a single file.

This patch does not introduce new validation or error handling—it only fixes the memory-safety flaw. The second patch in the series (which rejects empty worktree paths when a reference is provided, e.g., `git worktree add "" HEAD`) remains necessary but is not part of this submission. The thread context confirms that this patch is the agreed-upon solution for the first half of the problem, and Junio’s feedback suggests it will be merged as-is.

The bug was discovered via Git for Windows issue #6346 and can trigger silent data corruption (recursive deletion of the working directory, including `.git`) or a BUG message. The fix is straightforward and well-motivated, with no test coverage included yet—reviewers may still request reproduction steps or test cases for the `"" HEAD` edge case in future revisions. For now, this patch is a clean, targeted fix that addresses the immediate risk.
