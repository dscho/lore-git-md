This is a **design discussion** in the ongoing RFC thread for a diff provider interface. The author, Michael Montalbo, responds to Phillip Wood’s substantive review of v7 by proposing a major pivot: abandoning the "diff provider" abstraction introduced in v7 and reverting to the v6 framing of a "cousin" interface to `xdiff-interface.h`. The goal remains the same—enabling external diff tools to integrate with Git’s diff/blame machinery—but the architectural approach is now simpler and more tightly scoped.

Key points in this reply:
1. **Conceptual retreat**: The "diff provider" abstraction (a unified chain of authoritative/non-authoritative providers) is dropped as overly complex and unclear. The new direction focuses on a direct "cousin" to `xdiff-interface.h`, which would let users plug in external diff tools via pkt-line while still relying on xdiff for content rendering. This sidesteps the thorny "authority" question (e.g., whether Git trusts an external tool’s hunks) by making the external tool’s output advisory rather than authoritative.

2. **Terminology cleanup**: The invented term "coordinates" (for hunk offsets/lengths) will be replaced with established Git terminology. Similarly, "trim-stable pairs" (blob pairs whose trimmed/untrimmed diffs match) will be explained in plain language.

3. **Scope reduction**: The `diff-hunks` store (an in-process cache) is ejected from the RFC for now. While it demonstrated a non-pkt-line use case, it complicated the design and raised cache-keying concerns (e.g., storing `xdl_opts` directly). The author now plans to focus on the pkt-line external process provider (`diff.<driver>.process`), which aligns better with the "cousin" interface framing.

4. **Motivation reframed**: The reply clarifies the goals more concretely:
   - Enable users to configure external diff tools that integrate with Git’s existing diff features (e.g., word diff, `--color-moved`, function context).
   - Allow xdiff-interface callers (e.g., `git blame`, `--stat`) to operate on OIDs alone when only hunk headers are needed, avoiding blob loads.
   - Provide a consistent pkt-line interface for external tools, building on the existing `diff.<driver>.process` plumbing.

5. **Technical implications**:
   - The external process provider will no longer be "authoritative"; its hunks will be advisory, with xdiff remaining the final arbiter for content rendering. This resolves Phillip’s concern about non-deterministic behavior (e.g., external tools differing from xdiff).
   - The interface will be simpler, with no provider chain or "authority" resolution. Consumers will explicitly opt into external tools (like `textconv`), and failures will degrade to xdiff.
   - The `diff-hunks` store’s cache-keying issue (storing `xdl_opts` directly) is deferred, as the store is now out of scope.

6. **Next steps**: The author plans to re-roll the series based on v6, focusing on the pkt-line external process provider. The `diff-hunks` store may return as a separate effort if the interface stabilizes.

**Why this matters**: This pivot addresses Phillip’s core feedback—clarifying motivation, reducing jargon, and simplifying the design—while preserving the RFC’s long-term vision (enabling external diff tools). The new framing is more aligned with Git’s existing patterns (e.g., `textconv`, `diff.<driver>.command`) and avoids over-engineering. The discussion now shifts to whether the "cousin" interface is the right abstraction for integrating external diff tools without disrupting Git’s built-in features.
