This is the sixth patch in Michael Montalbo’s **14-patch RFC series** introducing `git organize`, a tool designed to restructure Git’s source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`, `pack/`) based on recorded placement rules in a `.gitorganize` file. This patch **records a label for every source file in scope**, populating the `[labels]` section of `.gitorganize` with metadata derived by the reference labeler.

The patch adds **475 lines** to `.gitorganize`, assigning each `.c` and `.h` file at the root a *component* (e.g., `odb`, `refs`, `pack`), *role* (`lib`, `public`, `program`), and advisory signals like *prefix* (from commit messages), *#include coupling*, and *co-change* profiles. The labeler uses Git’s commit history (mining "area:" prefixes) and static analysis to infer component membership, with fallbacks for files that don’t fit neatly into a single subsystem (marked `component=?`). Standalone programs and public headers remain at the root, while the 79 files labeled `component=?` form a "backlog" left for future refinement.

The patch is **purely declarative**: it records labels but does not move files or update references. The labels serve as input for later patches in the series, where `git organize apply` will use them to generate and execute moves. The commit message reports that 303 files are now marked for relocation across 13 components, with the rest either already in place or part of the backlog. This is a foundational step for the series, as the labels define the semantic structure that the organizer will later enforce.

The patch looks **well-structured and intentional**, with clear documentation of the labeling heuristics and their limitations. The backlog (`component=?`) is explicitly acknowledged, leaving room for future refinement without blocking the initial carve-outs. However, the **labeling logic’s reliance on Git-specific conventions** (e.g., "area:" prefixes in commit messages) may raise questions about its generality for other projects. Reviewers might also scrutinize the **completeness of the reference organizer** (handling `#include` paths, build system entries, etc.) in later patches, as this patch only sets up the metadata.

No new code or symbols are introduced here—just the `.gitorganize` file—so the patch is **low-risk** but critical for the series’ workflow. The test coverage in earlier patches (e.g., `t/t0096-organize.sh`) should validate the labeler’s output, though this patch itself does not add new tests.
