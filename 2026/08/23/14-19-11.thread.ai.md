Thread identity: RFC proposing a branch-aware or worktree-aware stash design to address silent interference between worktrees' stash operations. Originating author: Vladimir Sitnikov. Thread type: RFC design discussion (no patch series currently in flight).

Core problem or goal: Prevent data loss or unintended cross-worktree changes caused by Git's global stash stack when multiple worktrees (or automated agents) operate on the same repository. The discussion has converged on a branch-aware design that associates stashes with the branch or commit they were created on, resolving the detached HEAD edge case via reflog and commit parent analysis. The goal is to finalize a design that avoids new configuration, maintains backward compatibility, and handles all worktree states (branch-attached and detached HEAD).

Current status: RFC stage; no prior versions. The original `stash.ref` config knob proposal is superseded by the branch/commit-aware design, which leverages existing Git machinery (structured stash message metadata, reflogs, and commit parent pointers) to avoid new configuration or ref namespaces. Phillip Wood's reflog-based solution resolves the detached HEAD gap by associating stashes with the commit (not branch) they were created on, enabling per-worktree isolation without synthetic branch names or configuration knobs. The design is now technically feasible for all worktree states, with remaining questions focused on user interface (e.g., default behavior of `git stash pop`) and whether to expose both branch-aware and worktree-aware filtering.

Key technical details:
- **Branch/commit-aware design**: Stashes are associated with the branch *or commit* they were created on by encoding the branch name in the stash message (existing `"On $branch: "` prefix) and using HEAD's reflog + stash commit first parents to identify the most recent stash for a given commit (detached HEAD case). This avoids parsing ambiguity and enables scoped operations without breaking backward compatibility.
- **Detached HEAD handling**: Phillip's solution uses the reflog of HEAD and the first parent of stash commits to associate stashes with the specific commit (not branch) they were created on. This achieves per-worktree isolation for detached HEAD worktrees without synthetic branch names or configuration.
- **Subsystems touched**: stash subcommands (`push`, `pop`, `list`), reflog parsing, and potentially `gc`/`fsck` for reachability. The design may require extending `git stash pop` with `--current-branch` and `--current-worktree` flags to filter stashes by scope. No new CLI options, configuration keys, or on-disk format changes required.
- **Edge cases**: Detached HEAD (resolved via reflog/commit parent analysis), branch renames (handled via commit OIDs), and backward compatibility (older Git versions will see all stashes in `refs/stash` but ignore scope filtering).
- **User interface**: Proposed `--current-branch` and `--current-worktree` flags for `git stash pop`; `git stash list` may gain filtering options in the future. Default behavior of `git stash pop` (branch-aware vs. global) remains unresolved.

Open questions and loose ends:
1. **Default behavior of `git stash pop`**: Should it default to applying stashes from the current branch/commit (branch-aware), the current worktree (worktree-aware), or the global stash stack? Should an explicit flag (e.g., `--current-branch` or `--current-worktree`) be required to avoid surprises?
2. **User interface for filtering**: Should `git stash list` gain `--branch=<name>` and `--worktree=<path>` flags to filter stashes by scope, or is this unnecessary complexity?
3. **Backward compatibility**: How will older Git versions handle stash entries with branch metadata? Will the branch prefix (e.g., `"On $branch: "`) be stripped from `git stash list` output for consistency?
4. **Necessity and scope**: Is the problem severe enough to justify the change, given Git’s design philosophy? Will users who rely on the global stash stack (e.g., moving changes between worktrees) be disrupted?
5. **Future extensions**: Could the reflog/commit parent mechanism be extended to support per-worktree refs (e.g., `refs/worktree/stash`) if needed, or is this unnecessary complexity?

Participant positions:

Initially proposed a configurable scope (shared ref, per-branch, or per-worktree) but now appears satisfied with Phillip's reflog-based solution, which resolves the detached HEAD gap without configuration. Willing to implement whichever direction the maintainers prefer.

Agrees that opting into a per-worktree ref (e.g., `refs/worktree/stash`) is technically sound but dismisses reachability concerns for `gc`/`fsck`.
