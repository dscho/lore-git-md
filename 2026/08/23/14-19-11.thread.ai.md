Thread identity: RFC proposing a new `stash.ref` configuration knob to make Git's stash stack per-worktree rather than global. Originating author: Vladimir Sitnikov. Thread type: RFC patch series (single patch).

Core problem or goal: Address the pain point where multiple worktrees (or AI coding agents) sharing a repository experience silent interference in stash operations, leading to data loss or unintended cross-worktree changes. The discussion has shifted from a config-based solution to a branch-aware stash design, which associates stashes with the branch they were created on and enables branch-filtered operations (e.g., `git stash pop --current-branch`).

Current status: RFC stage; no prior versions. The original `stash.ref` config knob proposal is effectively superseded by the branch-aware design, which avoids new configuration and leverages existing Git concepts. The discussion is now focused on implementation details for encoding and using branch information in stash entries, with no major technical blockers identified.

Key technical details:
- Original proposal: New config key `stash.ref`, defaulting to `refs/stash` but configurable to per-worktree refs (e.g., `refs/worktree/stash`).
- Branch-aware design: Associate stashes with the branch they were created on by encoding the branch name in the stash message. Git already prepends `"On $branch: "` or `"WIP on $branch ..."` to stash messages, making the branch name machine-readable at the start of the message. This avoids parsing ambiguity (e.g., colons in user messages) and enables branch-filtered operations without breaking backward compatibility.
- Subsystems touched: stash subcommands (`push`, `pop`, `list`, etc.), refs backend, and potentially `gc`/`fsck` for reachability. The branch-aware design may require extending `git stash pop` with a `--current-branch` flag (or similar) to filter stashes by branch.
- No new CLI options or on-disk format changes in the original proposal. The branch-aware design would require minimal changes to stash message parsing and display logic, leveraging existing metadata.
- Leverages existing Git machinery: `refs/worktree/*`, `extensions.worktreeConfig`, and structured stash message metadata. The branch-aware design does not require new configuration or ref namespaces.

Open questions and loose ends:
1. **User interface for branch-aware operations**: What would the CLI for branch-aware stash operations look like? For example, would `git stash pop` default to applying stashes from the current branch, or would it require an explicit flag (e.g., `--current-branch`)? Should `git stash list` gain a `--all` flag to show stashes from all branches/worktrees?
2. **Interaction with detached HEAD**: How would the branch-aware design handle stashes created in a detached HEAD state? Would they be associated with a synthetic branch name (e.g., `HEAD@{1}`) or excluded from branch-aware operations?
3. **Branch renames**: How would the branch-aware design handle stashes created on a branch that is later renamed? Would the stash remain associated with the original branch name, or would it be updated to reflect the new name?
4. **Backward compatibility**: Would the branch-aware design require changes to how stash messages are displayed (e.g., stripping the branch prefix in `git stash list` output)? How would older Git versions handle stash entries with branch metadata?
5. **Necessity of the change**: While the branch-aware design avoids a new config knob, the underlying problem (silent interference between worktrees) remains. Is the branch-aware approach sufficient to address the pain point, or would it still require users to opt into per-worktree behavior (e.g., via a config knob or CLI flag)?
6. Should `git stash list` gain a `--branch=<name>` flag to filter stashes by branch, or is `--current-branch` sufficient?

Participant positions:
- **Vladimir Sitnikov (author)**: Proposes the `stash.ref` config knob as a solution to silent interference between worktrees' stash operations, particularly for automated agents. Argues the change is necessary to prevent data loss and unintended cross-worktree changes. No explicit response to the branch-aware alternative yet.
- **Kristoffer Haugsbakk**: Skeptical of the proposal's necessity. Argues the current behavior is occasionally useful for humans (e.g., moving changes between worktrees) and that the problem for automated agents can be addressed by avoiding the stash or blocking `git stash` commands. Questions whether the harm justifies a new config knob, given Git’s design philosophy of reserving such changes for cases where manual user confusion is the primary concern. Agrees that opting into a per-worktree ref (e.g., `refs/worktree/stash`) is technically sound but dismisses reachability concerns for `gc`/`fsck`.
- **Phillip Wood**: Substantive review challenging the RFC’s premise. Proposes the branch-aware design as an alternative, leveraging existing stash message metadata to associate stashes with branches. Clarifies that Git already encodes branch information in stash messages (`"On $branch: "` or `"WIP on $branch ..."`), removing a technical obstacle to Junio’s proposed design. Argues this approach avoids new configuration and aligns better with Git’s existing patterns. No objections to the branch-aware design’s feasibility.
- **Junio C Hamano (maintainer)**: Refines the branch-aware design by suggesting encoding branch information in stash messages (e.g., appending the branch name after a colon). Raises the technical concern that relying on the stash message for branch tracking would restrict user flexibility (e.g., parsing `-m` messages). Phillip’s follow-up resolves this concern by pointing out the existing metadata structure.

Related work: None mentioned in the thread. The branch-aware design suggests potential future work, such as extending `git stash` with options to filter or specify branch names during stash creation or application.
