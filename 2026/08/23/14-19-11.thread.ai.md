Thread identity: RFC proposing a branch-aware or worktree-aware stash design to address silent interference between worktrees' stash operations. Originating author: Vladimir Sitnikov. Thread type: RFC design discussion (no patch series currently in flight).

Core problem or goal: Prevent data loss or unintended cross-worktree changes caused by Git's global stash stack when multiple worktrees (or automated agents) operate on the same repository. The discussion has converged on a branch-aware design that associates stashes with the branch they were created on, but a key gap remains for detached HEAD worktrees, which all record stashes with the same "(no branch)" label. The goal is now to refine the design to handle this edge case while avoiding new configuration or breaking backward compatibility.

Current status: RFC stage; no prior versions. The original `stash.ref` config knob proposal is superseded by the branch-aware design, which leverages existing Git machinery (structured stash message metadata) to avoid new configuration. The branch-aware design is technically feasible for branch-attached worktrees but does not address detached HEAD worktrees. Focus has shifted to evaluating whether the branch-aware approach is sufficient or if a hybrid (configurable scope) is needed. No major technical blockers identified, but the design is not yet finalized.

Key technical details:
- Branch-aware design: Stashes are associated with the branch they were created on by encoding the branch name in the stash message. Git already prepends `"On $branch: "` or `"WIP on $branch ..."` to stash messages, making the branch name machine-readable at the start of the message. This avoids parsing ambiguity and enables branch-filtered operations without breaking backward compatibility.
- Detached HEAD gap: Stashes created in detached HEAD worktrees all record the same "(no branch)" label, which would group them together under the branch-aware design rather than separating them by worktree. This is a non-trivial edge case, as detached HEAD worktrees are common in automated workflows (e.g., 23 out of 436 worktrees in Vladimir's environment).
- Subsystems touched: stash subcommands (`push`, `pop`, `list`, etc.), refs backend, and potentially `gc`/`fsck` for reachability. The branch-aware design may require extending `git stash pop` with a `--current-branch` flag (or similar) to filter stashes by branch. No new CLI options, configuration keys, or on-disk format changes required.
- Edge cases: Detached HEAD (how to associate stashes), branch renames (whether to update stash metadata), and backward compatibility (how older Git versions handle stash entries with branch metadata). The detached HEAD case is now the primary unresolved technical challenge.
- Configurable scope: Vladimir suggests a hybrid approach where users could configure the scope of stash isolation (shared ref, per-branch, or per-worktree), allowing detached worktrees to opt into per-worktree isolation while others use branch-aware filtering.

Open questions and loose ends:
1. **Detached HEAD handling**: How should stashes created in detached HEAD worktrees be handled? Options include:
   - Associating them with a synthetic branch name (e.g., `HEAD@{1}` or the worktree's directory name).
   - Excluding them from branch-aware operations (defaulting to the global stash stack).
   - Allowing per-worktree isolation for detached HEAD worktrees via configuration.
2. **User interface for branch-aware operations**: Should `git stash pop` default to applying stashes from the current branch, or require an explicit flag (e.g., `--current-branch`)? Should `git stash list` gain a `--all` flag to show stashes from all branches/worktrees, or a `--branch=<name>` flag to filter by branch?
3. **Branch renames**: Should stashes remain associated with the original branch name, or be updated to reflect the new name?
4. **Backward compatibility**: Will the branch-aware design require changes to how stash messages are displayed (e.g., stripping the branch prefix in `git stash list` output)? How will older Git versions handle stash entries with branch metadata?
5. **Necessity and scope**: Is the branch-aware approach sufficient to address the original pain point (silent interference between worktrees), or would it still require users to opt into per-worktree behavior (e.g., via a config knob or CLI flag)? Is the problem severe enough to justify the change, given Git’s design philosophy?
6. **Hybrid approach**: Would a configurable scope (shared ref, per-branch, or per-worktree) unify the branch-aware and worktree-aware designs, or would it introduce unnecessary complexity?

Participant positions:
- **Vladimir Sitnikov (author)**: Argues the problem is severe enough to justify a solution, especially for automated agents where `rebase.autoStash` creates implicit stash entries in the global `refs/stash`. Acknowledges the branch-aware design covers most of his use case but identifies the detached HEAD gap as a critical limitation. Proposes a configurable scope (shared ref, per-branch, or per-worktree) to unify the approaches, allowing detached worktrees to opt into per-worktree isolation. Willing to implement whichever direction the maintainers prefer.
- **Kristoffer Haugsbakk**: Skeptical of the proposal's necessity. Argues the current behavior is occasionally useful for humans (e.g., moving changes between worktrees) and that automated agents can avoid the stash or block `git stash` commands. Questions whether the harm justifies a new config knob, given Git’s design philosophy. Agrees that opting into a per-worktree ref (e.g., `refs/worktree/stash`) is technically sound but dismisses reachability concerns for `gc`/`fsck`.
- **Phillip Wood**: Proposes the branch-aware design as an alternative to the original `stash.ref` config knob, leveraging existing stash message metadata to associate stashes with branches. Clarifies that Git already encodes branch information in stash messages (`"On $branch: "` or `"WIP on $branch ..."`), resolving Junio’s parsing concern. No objections to the branch-aware design’s feasibility but has not yet addressed the detached HEAD gap.
- **Junio C Hamano (maintainer)**: Refines the branch-aware design by suggesting encoding branch information in stash messages. Initially raised a technical concern about parsing `-m` messages, but Phillip’s clarification resolved this. Acknowledges the branch-aware design is technically feasible without new configuration or ref namespaces. Has not yet commented on the detached HEAD gap or the hybrid approach.

Related work: None mentioned in the thread. The branch-aware design suggests potential future work, such as extending `git stash` with options to filter or specify branch names during stash creation or application. The configurable scope proposal may require new configuration keys (e.g., `stash.scope`).
