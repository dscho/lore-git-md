Thread identity: RFC proposing a branch-aware stash design to address silent interference between worktrees' stash operations. Originating author: Vladimir Sitnikov. Thread type: RFC patch series (single patch, now superseded by design discussion).

Core problem or goal: Prevent data loss or unintended cross-worktree changes caused by Git's global stash stack when multiple worktrees (or automated agents) operate on the same repository. The discussion has converged on a branch-aware design that associates stashes with the branch they were created on, enabling branch-filtered operations without new configuration or ref namespaces.

Current status: RFC stage; no prior versions. The original `stash.ref` config knob proposal is superseded by the branch-aware design, which leverages existing Git machinery (structured stash message metadata) to avoid new configuration. The design is now technically feasible, with no major blockers identified. Focus has shifted to refining the user interface for branch-aware operations and addressing edge cases.

Key technical details:
- Branch-aware design: Stashes are associated with the branch they were created on by encoding the branch name in the stash message. Git already prepends `"On $branch: "` or `"WIP on $branch ..."` to stash messages, making the branch name machine-readable at the start of the message. This avoids parsing ambiguity (e.g., colons in user messages) and enables branch-filtered operations without breaking backward compatibility.
- Subsystems touched: stash subcommands (`push`, `pop`, `list`, etc.), refs backend, and potentially `gc`/`fsck` for reachability. The branch-aware design may require extending `git stash pop` with a `--current-branch` flag (or similar) to filter stashes by branch.
- No new CLI options, configuration keys, or on-disk format changes required. The design leverages existing Git concepts: `refs/worktree/*`, `extensions.worktreeConfig`, and structured stash message metadata.
- Edge cases: Detached HEAD (how to associate stashes), branch renames (whether to update stash metadata), and backward compatibility (how older Git versions handle stash entries with branch metadata).

Open questions and loose ends:
1. **User interface for branch-aware operations**: Should `git stash pop` default to applying stashes from the current branch, or require an explicit flag (e.g., `--current-branch`)? Should `git stash list` gain a `--all` flag to show stashes from all branches/worktrees, or a `--branch=<name>` flag to filter by branch?
2. **Detached HEAD**: How should stashes created in a detached HEAD state be handled? Associate them with a synthetic branch name (e.g., `HEAD@{1}`) or exclude them from branch-aware operations?
3. **Branch renames**: Should stashes remain associated with the original branch name, or be updated to reflect the new name?
4. **Backward compatibility**: Will the branch-aware design require changes to how stash messages are displayed (e.g., stripping the branch prefix in `git stash list` output)? How will older Git versions handle stash entries with branch metadata?
5. **Necessity and scope**: Is the branch-aware approach sufficient to address the original pain point (silent interference between worktrees), or would it still require users to opt into per-worktree behavior (e.g., via a config knob or CLI flag)? Is the problem severe enough to justify the change, given Git’s design philosophy?

Participant positions:
- **Vladimir Sitnikov (author)**: Proposes the original `stash.ref` config knob to solve silent interference between worktrees' stash operations, particularly for automated agents. Argues the change is necessary to prevent data loss. No explicit response to the branch-aware alternative yet.
- **Kristoffer Haugsbakk**: Skeptical of the proposal's necessity. Argues the current behavior is occasionally useful for humans (e.g., moving changes between worktrees) and that automated agents can avoid the stash or block `git stash` commands. Questions whether the harm justifies a new config knob, given Git’s design philosophy. Agrees that opting into a per-worktree ref (e.g., `refs/worktree/stash`) is technically sound but dismisses reachability concerns for `gc`/`fsck`.
- **Phillip Wood**: Substantive review challenging the RFC’s premise. Proposes the branch-aware design as an alternative, leveraging existing stash message metadata to associate stashes with branches. Clarifies that Git already encodes branch information in stash messages (`"On $branch: "` or `"WIP on $branch ..."`), resolving Junio’s parsing concern. Argues this approach avoids new configuration and aligns better with Git’s existing patterns. No objections to the branch-aware design’s feasibility.
- **Junio C Hamano (maintainer)**: Refines the branch-aware design by suggesting encoding branch information in stash messages. Initially raises a technical concern about parsing `-m` messages, but Phillip’s clarification resolves this by confirming the existing metadata structure. Acknowledges the branch-aware design is now technically feasible without new configuration or ref namespaces.

Related work: None mentioned in the thread. The branch-aware design suggests potential future work, such as extending `git stash` with options to filter or specify branch names during stash creation or application.
