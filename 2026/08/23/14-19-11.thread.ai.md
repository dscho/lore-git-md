Thread identity: RFC proposing a new `stash.ref` configuration knob to make Git's stash stack per-worktree rather than global. Originating author: Vladimir Sitnikov. Thread type: RFC patch series (single patch).

Core problem or goal: Address the pain point where multiple worktrees (or AI coding agents) sharing a repository experience silent interference in stash operations, leading to data loss or unintended cross-worktree changes. The proposal aims to introduce a configurable per-worktree stash ref while preserving backward compatibility, but the discussion has shifted to evaluating whether the problem justifies a new config knob and exploring alternative designs, particularly a branch-aware stash system.

Current status: RFC stage; no prior versions. The original `stash.ref` config knob proposal is effectively sidelined in favor of a branch-aware stash design, as proposed by Phillip Wood and refined by Junio C Hamano. The discussion is now focused on implementation details for encoding branch information in stash entries without disrupting existing workflows.

Key technical details:
- Original proposal: New config key `stash.ref`, defaulting to `refs/stash` but configurable to per-worktree refs (e.g., `refs/worktree/stash`).
- Phillip Wood’s alternative: Associate stashes with the branch they were created on and add an option to `git stash pop` to only apply stashes from the current branch. This avoids new configuration and leverages existing Git concepts (`refs/worktree/`, branch names).
- Junio’s refinement: Encode branch information in the stash message by appending the target branch name after a colon at the end of the message (e.g., `stash message:branch-name`). This requires a small tweak to the `-m` option to ensure the branch name is always appended, preserving backward compatibility while enabling machine-readable metadata.
- Subsystems touched: stash subcommands (`push`, `pop`, `list`, etc.), refs backend, and potentially `gc`/`fsck` for reachability. The branch-aware design may also require changes to how stash messages are parsed and displayed.
- No new CLI options or on-disk format changes in the original proposal, but the branch-aware design would require extending `git stash pop` with a branch-aware option (e.g., `--current-branch` or similar).
- Leverages existing Git machinery: `refs/worktree/*`, `extensions.worktreeConfig`, and `git config --worktree`. The branch-aware design additionally relies on structured stash message metadata.
- Reachability of stash entries under `refs/worktree/*` is not a technical blocker, per `gitdatamodel(7)`; no ref namespace is inherently special.

Open questions and loose ends:
1. **Implementation of branch-aware stashes**: How to encode branch information in stash messages without breaking existing workflows (e.g., user-provided `-m` messages, scripts that parse stash output). Junio’s suggestion to append the branch name after a colon is a starting point, but details need to be worked out (e.g., handling colons in user messages, backward compatibility with older Git versions).
2. **Interaction with detached HEAD**: How would the branch-aware design handle stashes created in a detached HEAD state? Would they be associated with a synthetic branch name (e.g., `HEAD@{1}`) or excluded from branch-aware operations?
3. **Branch renames**: How would the branch-aware design handle stashes created on a branch that is later renamed? Would the stash remain associated with the original branch name, or would it be updated to reflect the new name?
4. **User interface for branch-aware operations**: What would the CLI for branch-aware stash operations look like? For example, would `git stash pop` default to applying stashes from the current branch, or would it require an explicit flag (e.g., `--current-branch`)?
5. **Backward compatibility**: Would the branch-aware design require changes to how stash messages are displayed (e.g., stripping the branch suffix in `git stash list` output)? How would older Git versions handle stash entries with branch metadata?
6. **Necessity of the change**: While the branch-aware design avoids a new config knob, the underlying problem (silent interference between worktrees) remains. Is the branch-aware approach sufficient to address the pain point, or would it still require users to opt into per-worktree behavior (e.g., via a config knob or CLI flag)?
7. Should `git stash list` gain a `--all` flag to show stashes from all branches/worktrees, or would this be redundant with branch-aware filtering?

Participant positions:
- **Vladimir Sitnikov (author)**: Proposes the `stash.ref` config knob as a solution to silent interference between worktrees' stash operations, particularly for automated agents. Argues the change is necessary to prevent data loss and unintended cross-worktree changes. No explicit response to the branch-aware alternative yet.
- **Kristoffer Haugsbakk**: Skeptical of the proposal's necessity. Argues the current behavior is occasionally useful for humans (e.g., moving changes between worktrees) and that the problem for automated agents can be addressed by avoiding the stash or blocking `git stash` commands. Questions whether the harm justifies a new config knob, given Git’s design philosophy of reserving such changes for cases where manual user confusion is the primary concern. Agrees that opting into a per-worktree ref (e.g., `refs/worktree/stash`) is technically sound but dismisses reachability concerns for `gc`/`fsck`.
- **Phillip Wood**: Substantive review challenging the RFC’s premise. Proposes an alternative design: associate stashes with the branch they were created on and add an option to `git stash pop` to only apply stashes from the current branch. Argues this avoids new configuration and aligns better with Git’s existing patterns. Acknowledges the real-world pain point but questions whether a config knob is the right solution.
- **Junio C Hamano (maintainer)**: Weighs in on Phillip’s alternative, refining the design to encode branch information in stash messages by appending the branch name after a colon. This preserves backward compatibility while enabling machine-readable metadata. Raises the technical concern that relying on the stash message for branch tracking would restrict user flexibility (e.g., parsing `-m` messages). No explicit stance on the necessity of the change, but his feedback shifts the discussion toward implementation details for the branch-aware design.

Related work: None mentioned in the thread. The branch-aware design suggests potential future work, such as extending `git stash` with options to filter or specify branch names during stash creation or application.
