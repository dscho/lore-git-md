Thread identity: RFC proposing a new `stash.ref` configuration knob to make Git's stash stack per-worktree rather than global. Originating author: Vladimir Sitnikov. Thread type: RFC patch series (single patch).

Core problem or goal: Address the pain point where multiple worktrees (or AI coding agents) sharing a repository experience silent interference in stash operations, leading to data loss or unintended cross-worktree changes. The proposal aims to introduce a configurable per-worktree stash ref while preserving backward compatibility, but the necessity and design of the change are now contested.

Current status: RFC stage; no prior versions. The discussion has shifted from *how* to implement the change to *whether* and *how* it should be implemented, with Phillip Wood proposing an alternative design that avoids a new config knob.

Key technical details:
- New config key proposed: `stash.ref`, defaulting to `refs/stash` but configurable to per-worktree refs (e.g., `refs/worktree/stash`).
- Phillip Wood’s alternative: Associate stashes with the branch they were created on and add an option to `git stash pop` to only apply stashes created on the current branch. This leverages existing Git concepts (`refs/worktree/`, branch names) and avoids new configuration.
- Subsystems touched: stash subcommands (`push`, `pop`, `list`, etc.), refs backend, and potentially `gc`/`fsck` for reachability.
- No new CLI options or on-disk format changes in the original proposal, but a potential `--all` flag for `git stash list` was discussed. Phillip’s alternative would require extending `git stash pop` with a branch-aware option.
- Leverages existing Git machinery: `refs/worktree/*`, `extensions.worktreeConfig`, and `git config --worktree`.
- Reachability of stash entries under `refs/worktree/*` is not a technical blocker, per `gitdatamodel(7)`; no ref namespace is inherently special.

Open questions and loose ends:
1. **Necessity of the change**: Is the problem severe enough to warrant a new config knob, or can automated agents (e.g., AI tools) mitigate it by avoiding the stash or blocking `git stash` commands? Phillip Wood’s alternative suggests the problem can be solved without new configuration.
2. Should `stash.ref` config values be restricted to valid ref names?
3. Should `git stash list` gain a `--all` flag to show stashes from all worktrees?
4. How would Phillip’s branch-aware stash design interact with detached HEAD states or branch renames?
5. No substantive reviews or objections yet beyond Phillip’s alternative; discussion is ongoing, with conceptual pushback on the proposal’s justification and design.

Participant positions:
- **Vladimir Sitnikov (author)**: Proposes the `stash.ref` config knob as a solution to silent interference between worktrees' stash operations, particularly for automated agents. Argues the change is necessary to prevent data loss and unintended cross-worktree changes.
- **Kristoffer Haugsbakk**: Skeptical of the proposal's necessity. Argues the current behavior is occasionally useful for humans (e.g., moving changes between worktrees) and that the problem for automated agents can be addressed by avoiding the stash or blocking `git stash` commands. Questions whether the harm justifies a new config knob, given Git’s design philosophy of reserving such changes for cases where manual user confusion is the primary concern. Agrees that opting into a per-worktree ref (e.g., `refs/worktree/stash`) is technically sound but dismisses reachability concerns for `gc`/`fsck`.
- **Phillip Wood**: Substantive review challenging the RFC’s premise. Proposes an alternative design: associate stashes with the branch they were created on and add an option to `git stash pop` to only apply stashes from the current branch. Argues this avoids new configuration and aligns better with Git’s existing patterns. Acknowledges the real-world pain point but questions whether a config knob is the right solution.

Related work: None mentioned in the thread. The proposal remains self-contained, though Phillip’s alternative suggests potential future work (e.g., an option to specify the branch name when creating a stash).
