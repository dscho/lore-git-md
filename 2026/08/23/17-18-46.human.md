This is the second patch in Michael Montalbo’s **14-patch RFC series** introducing `git organize`, a new command designed to restructure Git’s source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`) based on rules recorded in a `.gitorganize` file. This patch adds the **labeler** and **organizer** scripts—two key components that supply the project-specific logic for determining where files belong and how to update references when files move.

### What this patch does
The patch implements the **labeling** and **reference-updating** workflows that make `git organize` functional. The core command (introduced in the first patch) reconciles the tree against a hand-written `[labels]` section in `.gitorganize`, but it cannot populate that section or handle the fallout of moves (e.g., broken `#include` paths). This patch fills those gaps:

1. **Labeler** (`contrib/organize/labeler`):
   - A Perl script that assigns **component** and **role** labels to each file in scope (root `*.c` and `*.h` files).
   - Labels are derived from:
     - The most frequent "area:" prefix in the file’s commit history (mined via `git log --follow`).
     - A static `git-layout.map` that groups fine-grained prefix tokens into components (e.g., "object", "object-file" → `odb/`).
     - Fallback to filename tokens (e.g., `object-file.c` → `odb/`) if the prefix is ambiguous or missing.
     - Co-change analysis for files with no clear prefix (e.g., `alloc.c` and `cbtree.c` are promoted to `odb/` due to frequent co-changes with ODB files).
   - Outputs one record per file: `path \0 component=<dir> role=<role> prefix=<token> includes=<c>:<n>,... cochange=<c>:<n>,...\0`.
   - The labeler is **parallelized** (via `ORGANIZE_JOBS`) to handle Git’s large history efficiently.

2. **Organizer** (`contrib/organize/organizer`):
   - A Perl script that generates a **patch** to update references broken by moves (e.g., `#include` paths, `Makefile`/`meson.build` entries).
   - Handles:
     - `#include` rewrites (e.g., `#include "fsck.h"` → `#include "odb/fsck.h"`), with logic to avoid shadowing local headers.
     - Build system updates (e.g., `Makefile` object lists, `meson.build` source paths).
     - Documentation examples (e.g., `#include` lines in `.adoc` files).
   - **Declines moves** it cannot handle (e.g., if a build file still references the old path after edits), returning a `reject <src> <reason>` line.
   - The patch is **validated** to ensure it only edits or renames files involved in the planned moves.

3. **Protocol and plumbing**:
   - Adds `organize.labeler` and `organize.organizer` config settings to point to the scripts.
   - Implements a **line protocol** for communication between `git organize` and the scripts:
     - `git organize` sends `move <src> <dst> <rule_value>` lines to the organizer.
     - The organizer replies with `reject` lines for declined moves and a `patch` section for edits.
   - Adds `--labels-only` and `--reseed` options to `git organize apply` to control label recording.

4. **Test coverage**:
   - Extends `t/t0096-organize.sh` to verify:
     - Label recording (`--labels-only` preserves hand-made decisions; `--reseed` re-derives all labels).
     - Organizer behavior (declining moves, patching references, handling edge cases like duplicate basenames).
     - Validation (rejects malformed patches, edits to unmoved files, or renames that don’t match the plan).

### Key technical details
- **Atomicity**: Moves and the organizer’s patch apply as a single `git apply --index` transaction. A failure leaves the tree untouched.
- **Reference updates**: The organizer’s patch is **validated** to ensure it only touches files involved in the moves (e.g., no edits to unrelated files).
- **Label persistence**: Recorded labels survive `--labels-only` runs unless `--reseed` is used, allowing manual overrides.
- **Performance**: The labeler parallelizes history mining across CPU cores.

### Why this matters
This patch is the **engine** of the series. The first patch laid the foundation, but this one provides the **project-specific logic** that makes `git organize` usable for Git’s own codebase. The labeler and organizer scripts are **demonstrations**—real projects would customize them (e.g., different `git-layout.map` rules or build system handling). The patch also addresses critical edge cases:
- **Shadowing**: `#include` paths are resolved correctly to avoid local header collisions.
- **Backward compatibility**: The tool is opt-in and incremental (e.g., a project could merge the `odb/` move without adopting the tool).
- **Safety**: Validation ensures the organizer cannot corrupt the tree.

### What’s next
The remaining 12 patches in the series will:
1. Demonstrate the tool’s use to **carve out 8 subsystems** (e.g., `odb/`, `refs/`) from Git’s codebase.
2. Add supporting scripts (e.g., `contrib/organize/labeler` refinements).
3. Show how the tool could later align with Patrick Steinhardt’s `libgit.a` series (e.g., moving subsystems to `lib/odb/`).

### Assessment
This is a **well-crafted, ambitious patch** that tackles a long-standing challenge: making large-scale source tree reorganizations **auditable, reversible, and repeatable**. The design is thoughtful (e.g., parallelized labeler, atomic transactions, validation), and the test coverage is thorough. The biggest open questions are:
- **Generality**: Can the `.gitorganize` format and scripts handle other projects’ needs (e.g., nested directories like `lib/odb/`)?
- **Adoption path**: Should the tool or the demonstrated carve-outs (e.g., `odb/`) be merged first? The author frames them as separable, but the series presents them together.
- **Controversy**: The proposed subsystem directories (e.g., `odb/`) are likely to spark debate—this patch focuses on the **mechanism**, not the layout, but the two are intertwined in the series.

For now, this patch is **worth close attention** from maintainers interested in Git’s long-term code organization. The labeler/organizer design is flexible enough to accommodate alternative layouts, but the series’ success hinges on whether the community embraces the tool *and* the proposed structure.
