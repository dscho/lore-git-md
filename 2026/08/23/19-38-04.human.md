This is a **design discussion** in the ongoing RFC thread for a diff provider interface. The author, Michael Montalbo, responds to Phillip Wood’s substantive review with a significant pivot: he proposes abandoning the "diff provider" abstraction introduced in v7 and returning to the v6 approach, which framed the work as a "cousin" interface to `xdiff-interface` rather than a unified provider chain.

The key points in this email are:

1. **Abandoning the "diff provider" abstraction**: Michael acknowledges that the abstraction introduced in v7 (a repository-owned chain of providers with authority determined by chain order) is confusing and unhelpful. The concept of "authority" (whether a provider’s answer overrides xdiff or merely supplements it) was poorly defined, and the abstraction shoehorned together distinct use cases (caching vs. external tools) that should be addressed separately. He now plans to drop this framework and revert to the v6 approach, which treated the work as a direct extension of `xdiff-interface` rather than a standalone provider system.

2. **Clarifying goals**: Michael distills his objectives into four concrete goals:
   - Add a "cousin" interface to `xdiff-interface` that allows users to configure their own alternatives to xdiff (e.g., language-aware diff tools, AI-assisted diffing).
   - Preserve xdiff’s content-rendering features (e.g., word diff, color-moved, function context) so that alternative diff providers can compose with Git’s existing diff functionality rather than replacing it wholesale.
   - Enable `xdiff-interface` callers (e.g., `git blame`, `git log --stat`) to operate with OIDs alone, avoiding blob loading when only hunk headers are needed (a performance optimization).
   - Provide a consistent interface (pkt-line) for users to plug in their own xdiff alternatives.

3. **Dropping the `diff-hunks` store**: Michael plans to eject the `diff-hunks` store (an in-process cache for hunk headers) from the RFC, as it no longer fits the revised framing. The store was intended to demonstrate an in-process alternative to xdiff, but without the "diff provider" abstraction, it becomes a distraction. He may revisit it later as a separate effort.

4. **Focusing on pkt-line xdiff alternatives**: The revised focus will be on the external process provider (`diff.<driver>.process`), which communicates with Git via pkt-line. This aligns with the v6 approach and avoids the complexity of the provider chain. The external process provider will remain authoritative (its answers may differ from xdiff) and opt-in per command, following the `allow_textconv` precedent.

5. **Terminology cleanup**: Michael agrees to replace jargon like "coordinates" (hunk offsets/lengths) with established Git terminology (e.g., "hunk headers") to improve clarity.

6. **Next steps**: The RFC will return to the v6 line, with future re-rolls focusing on the pkt-line xdiff-interface extension. The external process provider will be the primary example, and the `diff-hunks` store will be deferred.

**Why this matters**: This email marks a major shift in the RFC’s direction, addressing Phillip Wood’s core concerns about motivation and clarity. By dropping the "diff provider" abstraction and focusing on a simpler extension to `xdiff-interface`, the proposal becomes more targeted and easier to evaluate. The revised framing also makes it clearer how the work fits into Git’s existing architecture (e.g., as a complement to `xdiff-interface` rather than a replacement).

### What’s still open

- How will the pkt-line interface handle content-carrying requests (e.g., for patch output)? This was deferred in v6 but remains a long-term goal.
- Will the external process provider support non-authoritative use cases (e.g., caching), or will it remain strictly authoritative?
- How will the interface ensure backward compatibility with tools like `git patch-id`, which assume deterministic diff output?

This pivot makes the RFC more focused and practical, but it also narrows the scope. The discussion now centers on whether the pkt-line xdiff-interface extension is the right way to enable external diff tools, and whether the trade-offs (e.g., opt-in per command, authoritative answers) are acceptable.
