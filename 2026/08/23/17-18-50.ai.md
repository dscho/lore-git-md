This is the sixth patch in Michael Montalbo’s **14-patch RFC series** introducing `git organize`, a tool for restructuring Git’s source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`, `pack/`) based on recorded placement rules. This patch **records a label for every source file in scope** by running the reference labeler over Git’s tree and populating the `[labels]` section of the `.gitorganize` file.

The patch adds **475 lines** to `.gitorganize`, assigning each `.c` and `.h` file at the root a `component` (e.g., `odb`, `refs`, `pack`) and a `role` (e.g., `lib`, `public`, `program`). The labeler derives components from commit message prefixes (`area:`), filename patterns, and co-change analysis (e.g., files frequently modified together). Files that cannot be confidently assigned to a component are labeled `component=?` and left at the root as a "backlog" (79 files in this case). Public headers and standalone programs are also kept at the root by their role, even if their component is ambiguous.

Key technical details:
- **Files/subsystems**: Only `.gitorganize` is modified. The patch does not move files or update references; it solely records metadata for later use by `git organize apply`.
- **New symbols**: None. The patch populates the `[labels]` section of `.gitorganize`, which was introduced in earlier patches.
- **Behavior**: The labeler’s heuristics (commit prefixes, `#include` coupling, co-change profiles) are Git-specific and may not generalize to other projects. The patch includes advisory signals (e.g., `prefix=`, `includes=`, `cochange=`) to help users audit or override labels.
- **On-disk changes**: The `.gitorganize` file now contains a line for every source file in scope, with fields like `component=odb role=lib prefix=alloc cochange=odb:54,revision:8`.
- **Test coverage**: No new tests are added, but the existing test suite (`t/t0096-organize.sh`) validates the configuration file’s syntax and semantics.

The patch advances the series’ goal of making structural changes auditable and reversible. It provides a concrete snapshot of how Git’s codebase could be reorganized, though the labels themselves are open to debate. Reviewers may focus on the labeler’s heuristics (e.g., whether commit prefixes are a reliable signal) or the backlog of unassigned files (e.g., whether `component=?` is a useful category or a sign of incomplete analysis). The patch is a prerequisite for later patches that use these labels to move files and update references.
