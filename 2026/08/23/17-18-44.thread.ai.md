Thread identity: RFC feature proposal introducing `git organize`, a new command to restructure Git's source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`, `pack/`, `diff/`, `revision/`, `index/`, `setup/`) based on recorded placement rules in a `.gitorganize` file. Series is 14 patches long (v1), authored by Michael Montalbo.

Core problem or goal: Externalize file placement decisions into a tracked configuration file (`.gitorganize`) to enable systematic, repeatable reorganization of Git's source tree. The tool aims to make structural changes (e.g., moving files to subsystem directories) auditable, reversible, and project-specific, while ensuring the tree remains buildable after each move. The series establishes a two-phase workflow: (1) a **labeler** assigns semantic labels (e.g., `component=setup`) to files using project-specific heuristics, and (2) an **organizer** updates references (e.g., `#include` paths, build system entries) after moves. The first patch implemented the core command; the second patch added the labeler/organizer infrastructure and reference implementations for Git's own codebase. The third patch added `--exit-code` to `git organize status` to enable CI/gating by returning a non-zero exit code when the tree is out of sync with the declared layout. The fourth patch adds `--label` selectors to `git organize status` and `git organize apply`, enabling incremental reconciliation of specific components or label groups. The fifth patch introduces the `.gitorganize` configuration file, which defines the scope (all `.c` and `.h` files at the root) and layout (mapping components like `odb`, `refs`, `pack`, `diff`, `revision`, `index`, and `setup` to their own directories, while keeping `public` headers and `program` executables at the root). The sixth patch populates the `[labels]` section of `.gitorganize` with a label for every source file in scope, derived from Git-specific heuristics (commit prefixes, filename patterns, and co-change analysis). The seventh through thirteenth patches demonstrate the tool's practical application by mechanically moving the ODB, refs, pack, diff, revision, index, and setup subsystems to their own directories, updating all references (build system, `#include` directives, documentation) to maintain build integrity.

Current status: Proposed as an RFC (v1); no prior versions. The series is under initial review. Open questions and loose ends:
- **Labeler heuristics**: The reference labeler’s reliance on Git-specific heuristics (commit prefixes, `#include` coupling, co-change analysis) may not generalize to other projects. The backlog of 70 files labeled `component=?` may prompt discussion about whether this category is useful or a sign of incomplete analysis.
- **Organizer completeness**: The reference organizer handles Git’s build systems and `#include` paths, but reviewers may question its scalability for more complex reference graphs (e.g., documentation cross-references, test fixtures, or nested subsystems like `lib/odb/`). The thirteenth patch’s handling of cross-subsystem dependencies (e.g., `index/`, `odb/`, `transport/`) may be scrutinized for completeness, particularly given the setup subsystem’s foundational role.
- **Performance**: The labeler’s use of `git log --follow` (fanned out to worker processes) could be slow for large repositories. Reviewers may request benchmarks or optimizations (e.g., caching or parallelization). The thirteenth patch’s update of 347 files may also prompt performance concerns.
- **Integration with other efforts**: Alignment with Patrick Steinhardt’s `libgit.a` series (e.g., moving subsystems to `lib/odb/`) remains unclear. The author notes this as a future possibility, but reviewers may want a clearer roadmap or proof-of-concept. The choice of flat directories (e.g., `setup/`, `diff/`, `revision/`) rather than nested (e.g., `lib/setup/`, `lib/diff/`) may spark discussion about consistency with other ongoing efforts.
- **Adoption path**: Whether the tool or the demonstrated carve-outs (e.g., `odb/`, `refs/`, `pack/`, `diff/`, `revision/`, `index/`, `setup/` moves) should be merged first, or if they are inseparable. The atomicity guarantees (via `git apply --index`) may not cover all failure modes (e.g., partial reference updates by external scripts).
- **Tool generality**: Whether the `.gitorganize` format and workflow are sufficiently flexible for other projects or future reorganizations (e.g., nesting subsystems under `lib/` or handling non-C codebases). The Git-specific layout (e.g., keeping `public` headers at the root) may not suit all projects.
- **Subsystem move specifics**: Reviewers may debate whether `odb/`, `refs/`, `pack/`, `diff/`, `revision/`, `index/`, and `setup/` are the right names/locations for these subsystems or whether the reference updates are complete (e.g., no missing `#include` fixes or documentation updates). The thirteenth patch’s handling of setup-specific edge cases (e.g., interactions with platform-specific shims in `compat/` or external tools like Git for Windows) may be scrutinized.
- **Completeness of reference updates**: Whether all references were caught (e.g., documentation, test fixtures, scripts, or external tools like Git for Windows or libgit2). The thirteenth patch’s broad impact (347 files updated) may amplify these concerns.
- **Backward compatibility**: Whether the moves break external tools or forks (e.g., Git for Windows, libgit2) that rely on the old paths. The setup subsystem’s centrality to Git’s operation may make these concerns more acute.
- **Performance impact**: The setup subsystem is foundational to Git’s operation; reviewers may request benchmarks to ensure the move doesn’t introduce overhead.
