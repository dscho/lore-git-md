Thread identity: RFC feature proposal introducing `git organize`, a new command to restructure Git's source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`, `pack/`) based on recorded placement rules in a `.gitorganize` file. Series is 14 patches long (v1), authored by Michael Montalbo.

Core problem or goal: Externalize file placement decisions into a tracked configuration file (`.gitorganize`) to enable systematic, repeatable reorganization of Git's source tree. The tool aims to make structural changes (e.g., moving files to subsystem directories) auditable, reversible, and project-specific, while ensuring the tree remains buildable after each move. The series establishes a two-phase workflow: (1) a **labeler** assigns semantic labels (e.g., `component=odb`) to files using project-specific heuristics, and (2) an **organizer** updates references (e.g., `#include` paths, build system entries) after moves. The first patch implemented the core command; the second patch added the labeler/organizer infrastructure and reference implementations for Git's own codebase. The third patch added `--exit-code` to `git organize status` to enable CI/gating by returning a non-zero exit code when the tree is out of sync with the declared layout. The fourth patch adds `--label` selectors to `git organize status` and `git organize apply`, enabling incremental reconciliation of specific components or label groups. The fifth patch introduces the `.gitorganize` configuration file, which defines the scope (all `.c` and `.h` files at the root) and layout (mapping components like `odb`, `refs`, and `pack` to their own directories, while keeping `public` headers and `program` executables at the root). The sixth patch populates the `[labels]` section of `.gitorganize` with a label for every source file in scope, derived from Git-specific heuristics (commit prefixes, filename patterns, and co-change analysis). The seventh patch demonstrates the tool's practical application by mechanically moving all 23 ODB C sources and 26 headers from the root into a new `odb/` subdirectory, updating all references (build system, `#include` directives, documentation) to maintain build integrity. The eighth patch extends this demonstration by mechanically moving all refs-related C sources and headers (8 C files and 8 headers) from the root into a new `refs/` subdirectory, updating 347 files to reflect the new paths, and updating `.gitorganize` to record the new layout.

Current status: Proposed as an RFC (v1); no prior versions. The series is under initial review. The first six patches establish the tool's infrastructure and configuration, while the seventh and eighth patches provide concrete examples of its use by moving the ODB and refs subsystems to their own directories. No merge status has been reported; the series remains under review.

Key technical details:
- **Files/subsystems**: Extends `builtin/organize.c`, `organize/organize.c`, `Documentation/git-organize.adoc`, and `t/t0096-organize.sh`. The fifth patch adds `.gitorganize` to the root, the sixth patch populates its `[labels]` section, the seventh patch moves ODB files to `odb/`, and the eighth patch moves refs files to `refs/`. Both moves update the build system (Makefile, meson.build), documentation, and tutorial examples to reflect the new paths.
- **New symbols**: Command `git organize status` and `git organize apply` support `--label=<selector>` (added in the fourth patch). The `organize_plan_build()` function filters moves by label selectors. The seventh and eighth patches do not introduce new symbols but demonstrate the tool's output.
- **Behavior**: The `--label` option enables incremental reconciliation of specific components (e.g., `--label=component=odb` or `--label=component=refs`). The `.gitorganize` file defines scope (`.c` and `.h` files at the root) and layout (components like `odb`, `refs`, and `pack` move to their own directories; `public` headers and `program` executables remain at the root). The seventh patch mechanically moves ODB files to `odb/`, and the eighth patch mechanically moves refs files to `refs/`, updating all references in both cases. Files labeled `component=?` (79 files) remain at the root as a "backlog."
- **On-disk changes**: The sixth patch adds 475 lines to `.gitorganize` to record labels. The seventh patch moves 23 C sources and 26 headers to `odb/` (updating 347 files), and the eighth patch moves 8 C sources and 8 headers to `refs/` (updating 347 files). Both patches result in net-zero line churn, confirming the mechanical nature of the changes.
- **Test coverage**: `t/t0096-organize.sh` covers `--label` selectors, edge cases (shared basenames, quoted paths, malformed reject lines), and selector matching logic. The seventh and eighth patches rely on the existing test suite to validate build integrity and functionality.

Open questions and loose ends:
- **Labeler heuristics**: The reference labeler’s reliance on Git-specific heuristics (commit prefixes, `#include` coupling, co-change analysis) may not generalize to other projects. The backlog of 79 files labeled `component=?` may prompt discussion about whether this category is useful or a sign of incomplete analysis.
- **Organizer completeness**: The reference organizer handles Git’s build systems and `#include` paths, but reviewers may question its scalability for more complex reference graphs (e.g., documentation cross-references, test fixtures, or nested subsystems like `lib/odb/`).
- **Performance**: The labeler’s use of `git log --follow` (fanned out to worker processes) could be slow for large repositories. Reviewers may request benchmarks or optimizations (e.g., caching or parallelization).
- **Integration with other efforts**: Alignment with Patrick Steinhardt’s `libgit.a` series (e.g., moving subsystems to `lib/odb/`) remains unclear. The author notes this as a future possibility, but reviewers may want a clearer roadmap or proof-of-concept.
- **Adoption path**: Whether the tool or the demonstrated carve-outs (e.g., `odb/` and `refs/` moves) should be merged first, or if they are inseparable. The atomicity guarantees (via `git apply --index`) may not cover all failure modes (e.g., partial reference updates by external scripts).
- **Tool generality**: Whether the `.gitorganize` format and workflow are sufficiently flexible for other projects or future reorganizations (e.g., nesting subsystems under `lib/` or handling non-C codebases). The Git-specific layout (e.g., keeping `public` headers at the root) may not suit all projects.
- **Subsystem move specifics**: Reviewers may debate whether `odb/` and `refs/` are the right names/locations for these subsystems or whether the reference updates are complete (e.g., no missing `#include` fixes or documentation updates). The eighth patch’s handling of refs-specific edge cases (e.g., interactions with the reftable backend or ref-filter) may also be scrutinized.
