Thread identity: RFC feature proposal introducing `git organize`, a new command to restructure Git's source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`, `pack/`) based on recorded placement rules in a `.gitorganize` file. Series is 14 patches long (v1), authored by Michael Montalbo.

Core problem or goal: Externalize file placement decisions into a tracked configuration file (`.gitorganize`) to enable systematic, repeatable reorganization of Git's source tree. The tool aims to make structural changes (e.g., moving files to subsystem directories) auditable, reversible, and project-specific, while ensuring the tree remains buildable after each move. The series establishes a two-phase workflow: (1) a **labeler** assigns semantic labels (e.g., `component=odb`) to files using project-specific heuristics, and (2) an **organizer** updates references (e.g., `#include` paths, build system entries) after moves. The first patch implemented the core command; the second patch added the labeler/organizer infrastructure and reference implementations for Git's own codebase. The third patch adds `--exit-code` to `git organize status` to enable CI/gating by returning a non-zero exit code when the tree is out of sync with the declared layout.

Current status: Proposed as an RFC (v1); no prior versions. The series is under initial review. The first patch added the `git-organize` builtin and `.gitorganize` parser. The second patch introduced the labeler and organizer scripts, their communication protocols, and `--labels-only`/`--reseed` CLI options. The third patch adds `--exit-code` to `git organize status` to distinguish between *backlog* (files with labels but no matching rule) and *drift* (misplaced, unrecorded, or missing files), ensuring only the latter triggers a failure. Later patches will demonstrate the tool's use to reorganize Git's codebase (carving out 8 subsystems) and introduce supporting scripts. The tool remains opt-in and designed for incremental adoption.

Key technical details:
- **Files/subsystems**: New functionality added to `builtin/organize.c`, `organize/organize.c`, `Documentation/git-organize.adoc`, and `t/t0096-organize.sh`. The third patch does not introduce new files or symbols but extends existing ones.
- **New symbols**: Command `git organize status` gains the `--exit-code` option. The `organize_status()` function now takes an `exit_code` flag and returns `1` if drift is detected.
- **Behavior**: The `--exit-code` option enables programmatic detection of layout drift (e.g., via CI or pre-commit hooks). It distinguishes between *backlog* (non-failing) and *drift* (failing), ensuring only actionable inconsistencies trigger a failure. The command's output remains unchanged.
- **On-disk changes**: No changes to file placement or reference updates; this patch only affects the exit code behavior of `git organize status`.
- **Test coverage**: `t/t0096-organize.sh` expands to cover `--exit-code`, including edge cases like shared basenames, missing files, and the distinction between backlog and drift.

Open questions and loose ends:
- **Labeler heuristics**: The reference labeler’s reliance on commit prefixes (`area:`) and `#include` coupling may not generalize to other projects. Reviewers may question whether the format is flexible enough for different workflows or if it locks projects into Git-specific conventions.
- **Organizer completeness**: The reference organizer handles Git’s build systems (Makefile, meson.build) and `#include` paths, but reviewers may ask whether it can scale to more complex reference graphs (e.g., documentation cross-references, test fixtures, or nested subsystems like `lib/odb/`).
- **Performance**: The labeler’s use of `git log --follow` (fanned out to worker processes) could be slow for large repositories. Reviewers may request benchmarks or optimizations (e.g., caching or parallelization).
- **Integration with other efforts**: How this tool interacts with Patrick Steinhardt’s `libgit.a` series (e.g., moving subsystems to `lib/odb/`) remains unclear. The author notes this as a future possibility, but reviewers may want a clearer roadmap or proof-of-concept alignment.
- **Adoption path**: Whether the tool or the demonstrated carve-outs (e.g., `odb/` move) should be merged first, or if they are inseparable. The atomicity guarantees (via `git apply --index`) may not cover all failure modes (e.g., partial reference updates by external scripts).
- **Tool generality**: Whether the `.gitorganize` format and workflow are sufficiently flexible for other projects or future reorganizations (e.g., nesting subsystems under `lib/` or handling non-C codebases).
