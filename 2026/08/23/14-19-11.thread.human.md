This thread is an RFC discussion about redesigning Git’s stash mechanism to prevent silent interference when multiple worktrees operate on the same repository. Vladimir Sitnikov kicked off the conversation, highlighting that the global stash stack can cause data loss or unintended changes when automated agents (or users) use `git stash` across worktrees. The discussion has since converged on a branch-aware design, where stashes are associated with the branch they were created on, leveraging existing stash message metadata to avoid new configuration or breaking changes.

The main technical hurdle has been handling detached HEAD worktrees, which all record stashes with the same "(no branch)" label, making them indistinguishable under the branch-aware approach. Phillip Wood has now proposed a solution: associate stashes with the specific commit they were created on (not the branch) by using HEAD’s reflog and the first parent of stash commits. This elegantly resolves the detached HEAD gap without synthetic branch names, new ref namespaces, or configuration knobs. The proposal extends `git stash pop` with `--current-branch` and `--current-worktree` flags, allowing users to choose the scope of stash isolation at operation time while preserving the global stash stack for backward compatibility.

Key participants include Vladimir (the RFC author), who argues the problem is severe enough to justify a solution and prefers a configurable scope; Kristoffer Haugsbakk, who is skeptical of the necessity and questions whether the harm outweighs the complexity; and Phillip Wood, who has advanced the design with his reflog-based solution. Junio Hamano, the maintainer, has refined the branch-aware approach but has not yet weighed in on the detached HEAD solution or the hybrid design. The discussion has shifted from *whether* to implement stash isolation to *how* to do it, with Phillip’s proposal offering a technically feasible path forward that aligns with Git’s design philosophy. The remaining open questions are primarily about user interface defaults (e.g., whether `git stash pop` should default to branch-aware behavior) and whether `git stash list` should gain filtering options. No major technical blockers remain, and the proposal is likely to gain traction if it avoids new configuration and maintains backward compatibility.
