This thread began as an RFC by Vladimir Sitnikov proposing a new `stash.ref` configuration knob to make Git’s stash stack per-worktree, addressing silent interference between worktrees (or AI agents) that can lead to data loss. The discussion has since pivoted to whether the change is necessary at all, with Phillip Wood suggesting an alternative: associate stashes with the branch they were created on and add a branch-aware option to `git stash pop`. This avoids a new config knob and leverages existing Git concepts like `refs/worktree/` and branch names.

Junio C Hamano has now weighed in, refining Phillip’s alternative. He acknowledges the long-standing interest in per-branch/per-worktree stashes but raises a technical concern: encoding branch information in the stash message (as Phillip suggested) would restrict how users format their `-m` messages. Junio proposes a more structured approach—appending the branch name after a colon at the end of the message—to formalize the metadata without breaking existing workflows. This shifts the discussion toward implementation details, focusing on how to make branch-aware stashes both machine-readable and user-friendly. The original `stash.ref` proposal is now effectively sidelined unless the branch-based approach hits roadblocks.
