This thread began as an RFC by Vladimir Sitnikov proposing a new `stash.ref` configuration knob to make Git's stash stack per-worktree, addressing the pain point where multiple worktrees (or AI agents) sharing a repository can silently interfere with each other's stash operations. The discussion quickly pivoted away from the config knob idea after Phillip Wood suggested an alternative: making stashes branch-aware by associating them with the branch they were created on, and adding an option to `git stash pop` to only apply stashes from the current branch. Junio C Hamano refined this idea by proposing to encode branch information in stash messages, but Phillip's latest email clarifies that Git already does this—prepending `"On $branch: "` or `"WIP on $branch ..."` to stash messages—making the branch name machine-readable without any new encoding scheme.

The thread is now focused on ironing out the details of the branch-aware design. Key questions remain, such as how to handle stashes created in detached HEAD states, how branch renames would affect stash associations, and what the user interface for branch-aware operations should look like (e.g., whether `git stash pop` should default to the current branch or require an explicit flag). Vladimir hasn't yet responded to the branch-aware alternative, while Kristoffer Haugsbakk remains skeptical of the need for any change, arguing that the current behavior can be useful and that automated agents should avoid using `git stash`. The original `stash.ref` config knob proposal is effectively sidelined unless the branch-aware design encounters unforeseen issues. No decisions have been made, but the discussion is now centered on implementation rather than necessity.
