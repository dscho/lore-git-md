## Notable threads

### Global config listing inconsistency fix resubmitted
Delilah Ashley Wu resubmitted her three-patch v2 series to fix Git’s inconsistent `--global` config listing behavior, where `git config list --global` only showed `$HOME/.gitconfig` despite Git reading both that and `$XDG_CONFIG_HOME/git/config`. The v2 addresses all prior feedback by reordering patches to avoid temporary regressions, narrowing Windows path normalization scope, and squashing test-only changes.

The series modifies `config_sequence()` in `config.c` to handle the global scope by reading both config files through `do_git_config_sequence()`, using new flags (`ignore_system`, `ignore_repo`, `ignore_worktree`, `ignore_cmdline`) and counters (`global_config_success_count`) to track reads and enforce error handling. Johannes Schindelin’s Reviewed-by tags from v1 remain applicable to the technical aspects. The series is now technically complete and ready for maintainer integration, with no new CLI options or on-disk format changes introduced.

### Diff provider RFC pivots to simpler "cousin" interface
Michael Montalbo proposed a major pivot in the diff provider RFC, abandoning the "diff provider" abstraction introduced in v7 in favor of a simpler "cousin" interface to `xdiff-interface.h`. The new approach models the interface after the existing `diff.<driver>.process` plumbing, letting users plug in external diff tools via pkt-line while preserving xdiff as the final arbiter for content rendering.

The pivot responds to Phillip Wood’s review by dropping the "authority" question entirely—external tools are now advisory, not authoritative, resolving concerns about non-deterministic behavior. The RFC also replaces invented terminology ("coordinates", "trim-stable pairs") with established Git terms and ejects the `diff-hunks` store (an in-process cache) to avoid cache-keying concerns. Montalbo plans to re-roll the series based on v6, focusing on the pkt-line external process provider. The discussion now centers on whether this simpler interface is the right abstraction for integrating external diff tools without disrupting Git’s built-in features.

### `git organize` RFC proposes source tree restructuring
Michael Montalbo introduced `git organize`, a new command designed to restructure Git’s source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`, `pack/`) based on recorded placement rules in a `.gitorganize` file. The 14-patch RFC includes both the tool itself and a demonstration of its use to reorganize Git’s own codebase, carving out eight subsystems (`odb`, `refs`, `pack`, `diff`, `revision`, `index`, `setup`, `transport`) in separate commits.

The tool externalizes file placement decisions into a tracked `.gitorganize` file, which defines *scope* (which files are governed), *layout* (rules mapping labels to directories), and *labels* (metadata about each file). The workflow has two phases: a **labeler** assigns semantic labels (e.g., `component=odb`) using project-specific heuristics, and an **organizer** updates references (e.g., `#include` paths, build system entries) after moves. The series demonstrates the tool’s practical application by mechanically moving each subsystem to its own directory, updating all references to maintain build integrity.

Key technical details include the `.gitorganize` file format (INI-style with `[scope]`, `[layout]`, and `[labels]` sections), the `organize.labeler` and `organize.organizer` config settings, and the `--label` selector for incremental reconciliation. The tool is designed to be opt-in and project-specific, with the Git-specific layout open to debate. Reviewers may focus on the labeler’s heuristics (e.g., reliance on commit prefixes), the organizer’s completeness (e.g., handling documentation cross-references), and the tool’s alignment with ongoing efforts like Patrick Steinhardt’s `libgit.a` series.

### Policy debate on AI-generated contributions
The mailing list saw heated policy discussions around AI-generated contributions, with Junio C Hamano questioning the strictness of Git’s current policy and highlighting precedents for AI-assisted work. The debate was sparked by two threads: one proposing a documentation patch for `gitk` to discourage AI-generated contributions, and another discussing Alexey Samsonov’s `utimensat()` series, which was generated by an AI tool and manually verified.

Weijie Yuan twice highlighted that Johannes Schindelin has landed commits in `master` with an `Assisted-by` trailer, suggesting prior acceptance of AI-assisted contributions. Junio’s replies framed the issue as one of **contributor trust** rather than a blanket policy, implying that the project might tolerate AI-assisted contributions from trusted contributors who disclose their use of tools. He used analogies to prior art exposure (e.g., GPL/BSD contamination) to argue for a more practical balance between legal risk and community trust.

The discussion remains unresolved, with no explicit path forward proposed. Key questions include whether Git should adopt a disclosure-based policy (like Linux’s `Assisted-by: LLM [TOOL1] [TOOL2]` guidance), whether the distinction between "generated" and "assisted" can be meaningfully enforced, and how to reconcile the precedent of `Assisted-by` trailers with the current policy’s blanket discouragement of AI contributions. The Project Leadership Committee (PLC) or broader community may need to clarify or amend `SubmittingPatches` to address these questions.

### Reftable backend optimizations advance
Karthik Nayak’s three-patch v1 series to optimize stack reloads in the reftable backend saw substantive progress, with replies addressing reviewer concerns about locking semantics and performance benchmarks. The series eliminates redundant `fstat()` calls during reference transactions, addressing a performance bottleneck where excessive syscalls (scaling linearly with ref count) were consuming significant time during bulk ref creation.

Patch 1 removes the `REFTABLE_STACK_NEW_ADDITION_RELOAD` flag, making stack reloading the default behavior. Patch 2 relocates the list lock from `reftable_addition` to `reftable_stack` to enable future optimizations, with each `reftable_addition` now tracking whether it acquired the lock to prevent premature release. Patch 3 reduces `newfstatat()` syscalls from O(n) to ~55 constant calls by skipping redundant reloads when the stack is locked during a transaction.

Today’s deltas included Karthik’s proposal to add a tracking bit to `struct reftable_addition` to record lock acquisition, preventing premature release when multiple instances operate on the same stack. He also argued that lock-checking logic belongs in `stack_uptodate()` to enforce consistent application and reduce caller error risk. Jeff King’s independent benchmarks showed a consistent 25% speedup across ref counts from 10,000 to 50,000, reinforcing the optimization’s effectiveness. The series is now converging on a resolution for the remaining design questions.
