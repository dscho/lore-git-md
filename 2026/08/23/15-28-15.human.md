This is the second patch in Karthik Nayak’s three-patch series optimizing reftable stack reloads during transactions. The patch moves the list lock from `struct reftable_addition` to `struct reftable_stack` to enable future optimizations, but Junio C Hamano’s review identified a safety issue: if multiple `reftable_addition` instances operate on the same stack, the shared lock could be prematurely released when the second instance closes, disrupting other operations.

Karthik acknowledges the problem and proposes a fix: each `reftable_addition` would track whether it acquired the lock and only release it if it did. He plans to add a unit test to validate this behavior but is open to alternative designs. The patch is not yet ready to merge; the lock relocation’s safety for concurrent access must be resolved first.

The series as a whole targets a real performance bottleneck—excessive `fstat()` calls during bulk ref creation—and has shown consistent speedups in benchmarks. This patch is a prerequisite for the final optimization (patch 3), which reduces syscalls from O(n) to a constant ~55. The discussion is substantive, focusing on API safety rather than the optimization’s merit. If the locking issue is addressed cleanly, the series looks likely to land.
