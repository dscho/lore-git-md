This is the second patch in Michael Montalbo's **14-patch RFC series** introducing `git organize`, a new command for restructuring Git's source tree. This patch adds the **labeler** and **organizer** scripts—two external commands that supply the project-specific logic for deciding where files belong and how to update references after moves. It also implements the `--labels-only` mode for `git organize apply`, which records labels without moving files.

The patch introduces:
- **`organize.labeler`** (a config setting): a command that assigns labels (e.g., `component=odb`, `role=lib`) to each file in scope, based on project-specific heuristics. The reference implementation mines commit prefixes (`area:odb`) and `#include` coupling to group files into subsystems like `odb/`, `refs/`, and `pack/`. The labeler runs only during `git organize apply --labels-only` and preserves existing labels unless `--reseed` is used.
- **`organize.organizer`** (another config setting): a command that returns edits (as a patch) to update references (e.g., `#include` paths, build system entries) after moves. The reference organizer handles Makefile, meson.build, and C `#include` updates, and can decline moves it cannot handle (e.g., if a build file still references the old path). The organizer’s patch is validated to ensure it only edits or renames files involved in the planned moves.
- **Protocol layers** (`labeler-protocol.c`, `organizer-protocol.c`): these files define the line-based protocols for communicating with the labeler and organizer, including validation of their output.
- **Reference implementations** in `contrib/organize/`: the `labeler` (Perl) and `organizer` (Perl) scripts demonstrate how to implement these commands for Git’s own codebase. The labeler uses `git log --follow` to mine commit prefixes and a static `git-layout.map` to group them into components. The organizer updates `#include` paths, build system entries, and documentation examples.
- **New CLI options**: `--labels-only` (record labels without moving files) and `--reseed` (discard existing labels and re-run the labeler).

Key technical details for follow-up discussion:
- **Files touched**: `builtin/organize.c`, `organize/organize.c`, `organize/gitorganize-format.c`, plus new files `organize/labeler-protocol.{c,h}`, `organize/organizer-protocol.{c,h}`, `contrib/organize/{labeler,organizer,git-layout.map}`, and updates to `Documentation/git-organize.adoc`, `Makefile`, and `meson.build`.
- **New symbols**: `organize_run_labeler()`, `run_labeler()`, `run_organizer()`, and the `organize.labeler`/`organize.organizer` config keys.
- **Behavior**: The labeler and organizer are trusted commands (like filters or hooks) and must be set in user/system config (not repository config). The organizer’s patch is validated to ensure it only edits or renames files involved in the planned moves, and the entire operation (moves + edits) is atomic via `git apply --index`.
- **Test coverage**: `t/t0096-organize.sh` expands to cover `--labels-only`, `--reseed`, organizer rejects, and edge cases like duplicate basenames and in-place edits of moved files.

The patch is **well-structured** and **thoroughly tested**, with clear separation between the generic engine (`organize/`) and project-specific logic (`contrib/organize/`). The reference implementations are detailed and demonstrate real-world use cases (e.g., mining commit prefixes, updating `#include` paths). The atomicity guarantees and validation of the organizer’s patch are particularly strong points.

Open questions likely to surface in review:
- **Labeler heuristics**: The reference labeler’s reliance on commit prefixes (`area:`) and `#include` coupling may not generalize to other projects. Reviewers may ask whether the format is flexible enough for different workflows.
- **Organizer completeness**: The reference organizer handles Git’s build systems and `#include` paths, but reviewers may question whether it can scale to more complex reference graphs (e.g., documentation cross-references, test fixtures).
- **Performance**: The labeler’s use of `git log --follow` (fanned out to worker processes) could be slow for large repositories. Reviewers may ask for benchmarks or optimizations.
- **Integration with other efforts**: How this tool interacts with Patrick Steinhardt’s `libgit.a` series (e.g., moving subsystems to `lib/odb/`) is still unclear. The author notes this as a future possibility, but reviewers may want a clearer roadmap.
