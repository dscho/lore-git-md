This is a discussion reply in the ongoing RFC thread about making Git's stash stack per-worktree via a new `stash.ref` configuration knob. The email is from Kristoffer Haugsbakk, who engages with Vladimir Sitnikov's proposal but raises conceptual and practical concerns about the necessity and design of the change.

Kristoffer acknowledges the problem Vladimir describes—silent interference between worktrees' stash operations—but questions whether it justifies a new configuration option. He argues that the current behavior, while not elegant, is occasionally useful for humans (e.g., moving changes between worktrees) and that the real pain point—automated agents like AI coding tools—could be addressed by simply avoiding the stash altogether. He suggests that agents could be instructed not to use the stash or wrapped in scripts that block `git stash` commands, making the proposed config knob unnecessary for the stated use case.

The reply also touches on Git's design philosophy, noting that the stash has always been optional (achievable via other porcelain commands) and that introducing new configuration for porcelain commands is typically reserved for cases where manual user confusion is the primary concern. Kristoffer implies that the bar for such changes is high and that the current proposal may not meet it, given that the harm is primarily to automated workflows rather than human users.

Technically, Kristoffer agrees that opting into a per-worktree ref (e.g., `refs/worktree/stash`) makes sense but dismisses Vladimir's concern about reachability for `gc` and `fsck`, pointing to `gitdatamodel(7)` to argue that no ref namespace is inherently special—stash entries under `refs/worktree/*` would be treated the same as those under `refs/stash`.

The tone is skeptical but not dismissive. Kristoffer does not outright reject the proposal but frames it as a solution in search of a problem, particularly for the AI agent use case. His feedback suggests the discussion may pivot toward whether the problem is severe enough to warrant a new config knob or if alternative mitigations (e.g., agent-side restrictions) would suffice. No new technical objections are raised, but the email shifts the focus from *how* to implement the change to *whether* it should be implemented at all.
