This is the first patch in a 14-part RFC series introducing `git organize`, a new command designed to restructure Git's source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`) based on rules defined in a `.gitorganize` configuration file. The patch implements the core command and its two subcommands: `status` (which reports misplaced files) and `apply` (which moves them into place).

The patch adds the new builtin (`builtin/organize.c`), the `.gitorganize` file parser (`organize/gitorganize-format.c`), and the engine that plans and executes moves (`organize/organize.c`). The `.gitorganize` file is structured like an INI file with three sections: `[scope]` (which files are governed), `[layout]` (rules mapping labels to directories), and `[labels]` (metadata about each file). The `apply` subcommand moves files as content-identical renames (preserving `git log --follow` and `git blame` history) and updates the `.gitorganize` file to reflect the new paths.

The patch includes a test script (`t/t0096-organize.sh`) that verifies basic functionality: reporting misplaced files, applying moves, handling dirty worktrees, and detecting malformed `.gitorganize` files. The implementation is careful to stage changes atomically (using `git apply --index`) and requires a clean worktree to avoid data loss.

This is a well-structured, self-contained patch that lays the groundwork for the rest of the series. The commit message is clear, the code is modular, and the test coverage is thorough for the core functionality. The patch does not yet include the labeler or organizer scripts (which will handle reference updates like `#include` rewrites) — those appear in later patches. The series as a whole is ambitious and addresses a long-standing pain point in Git's codebase organization, but this patch focuses narrowly on the tool's plumbing.
