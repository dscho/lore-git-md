This is the **eleventh patch in the 14-patch RFC series introducing `git organize`**, a tool designed to restructure Git's source tree by moving files into subsystem-specific directories. This patch mechanically moves the **revision subsystem** (14 C sources and 15 headers) into a new `revision/` directory, updating all references to their old paths—including `#include` directives, build system entries (Makefile and meson.build), and tutorial examples in the documentation.

The patch is **pure refactoring**: it changes file locations and updates references without altering behavior. The net line churn is zero, confirming the mechanical nature of the changes. The `.gitorganize` file is updated to reflect the new paths, and the build remains intact. This patch demonstrates the `git organize` tool's ability to handle complex, widely-used subsystems like `revision/`, which is deeply embedded in Git's codebase (referenced by 347 files in this patch alone).

Key technical details:
- **Files moved**: 29 files (14 `.c`, 15 `.h`) from the root to `revision/`.
- **References updated**: `#include` directives, Makefile, meson.build, and documentation (`Documentation/MyFirstContribution.adoc`, `Documentation/MyFirstObjectWalk.adoc`).
- **Subsystem scope**: The revision subsystem includes core revision-walking logic (`revision.c`, `revision.h`), commit reachability (`commit-reach.c`), blame (`blame.c`), bisect (`bisect.c`), and related utilities like `log-tree.c` and `pretty.c`.
- **Labeling**: The `.gitorganize` file now records the moved files under `component=revision`, preserving their semantic labels (e.g., `role=lib` or `role=header`).

This patch is part of the series' **demonstration phase**, showing how `git organize` can incrementally carve out subsystems. The revision subsystem is a logical candidate for isolation due to its clear boundaries and heavy cross-subsystem usage (e.g., by `diff/`, `pack/`, and built-ins). Reviewers may focus on:
1. **Completeness**: Whether all references were caught (e.g., test fixtures, scripts, or documentation not covered by the organizer script).
2. **Naming/structure**: Whether `revision/` is the right name/location (e.g., alignment with Patrick Steinhardt’s `libgit.a` series, which might prefer `lib/revision/`).
3. **Performance**: The tool’s scalability for large-scale moves (this patch updates 347 files, the largest move in the series so far).
4. **Backward compatibility**: Potential breakage for external tools or forks (e.g., Git for Windows, libgit2) that might rely on the old paths.

The patch is **well-structured** and **builds cleanly**, but its value depends on the broader discussion about the `git organize` tool and the proposed layout. It is unlikely to be merged independently of the tool itself.
