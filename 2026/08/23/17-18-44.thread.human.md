This thread proposes `git organize`, a new command to systematically restructure Git's source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`, `pack/`, `diff/`, `revision/`, `index/`, `setup/`, and now `transport/`). The series, now complete at 14 patches, externalizes file placement decisions into a tracked `.gitorganize` configuration file, enabling auditable, reversible reorganizations while keeping the tree buildable. The first six patches established the tool's infrastructure—core command, labeler/organizer workflow, and Git-specific heuristics—while the remaining eight demonstrated its use by mechanically moving Git's major subsystems to their own directories, updating all references (build system, `#include` paths, documentation) in the process.

The latest patch moves the transport subsystem (22 C sources and 21 headers) to `transport/`, completing the series' demonstration. This was the largest move by file count, touching 347 files and underscoring the tool's ability to handle complex cross-subsystem dependencies. The patch is purely mechanical, with zero net line churn, but its thoroughness may prompt scrutiny of edge cases, such as interactions with platform-specific shims or external tools like Git for Windows. The transport subsystem's foundational role in Git's network operations makes this a critical test of the organizer's scalability.

No substantive reviews have appeared yet, but the series remains under active discussion. Key open questions include the labeler's reliance on Git-specific heuristics (leaving 70 files labeled `component=?`), the organizer's completeness for complex reference graphs (e.g., documentation cross-references), and alignment with other efforts like Patrick Steinhardt's `libgit.a` series. The demonstrated carve-outs—now covering eight subsystems—raise questions about whether the tool or the moves should be merged first, and whether the flat directory structure (e.g., `transport/`) is consistent with future plans. Performance concerns, particularly around the labeler's use of `git log --follow`, may also surface as reviewers dig deeper.
