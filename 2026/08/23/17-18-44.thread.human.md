This thread is an RFC proposing `git organize`, a new command to systematically restructure Git’s source tree by moving files into subsystem-specific directories (e.g., `odb/`, `refs/`, `pack/`) based on rules in a `.gitorganize` configuration file. The 14-patch series, authored by Michael Montalbo, introduces a two-phase workflow: a *labeler* assigns semantic labels to files (e.g., `component=odb`), and an *organizer* updates references (e.g., `#include` paths, build system entries) after moves. The first six patches establish the tool’s infrastructure and configuration, while the remaining eight demonstrate its use by mechanically moving the ODB, refs, pack, diff, revision, index, setup, and transport subsystems to their own directories, updating hundreds of files to maintain build integrity.

The discussion has focused on two key design decisions. Oswald Buddenhagen argues for nesting subsystems under `lib/` (e.g., `lib/odb/`) to align with Patrick Steinhardt’s `libgit.a` effort, while the series currently uses flat directories (e.g., `odb/`). Oswald also critiques the include style in the ODB move patch, advocating for angle brackets (`#include <odb/object-file.h>`) over double quotes to match Git’s `-I<path>` convention. Junio C Hamano has pushed back, requesting explicit clarification on the "right" include style, but no consensus has emerged. Other open questions include the labeler’s Git-specific heuristics (e.g., 70 files labeled `component=?` remain unresolved), the organizer’s scalability for complex reference graphs, and the tool’s performance for large repositories.

The series remains under initial review, with no merge status reported. The demonstrated moves (e.g., ODB, refs, transport) are mechanical but raise concerns about backward compatibility with external tools (e.g., Git for Windows, libgit2) and alignment with other refactoring efforts. Reviewers have not yet weighed in on whether the tool or the carve-outs should be merged first, or how the `.gitorganize` format’s Git-specific layout (e.g., keeping `public` headers at the root) might generalize to other projects. The thread’s trajectory will likely hinge on whether the maintainers prioritize include style standardization or directory layout consistency as prerequisites for further progress.
