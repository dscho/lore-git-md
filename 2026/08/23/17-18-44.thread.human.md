This thread is an RFC proposal for `git organize`, a new command designed to systematically restructure Git’s source tree by moving files into subsystem-specific directories (like `odb/` or `refs/`) based on rules in a `.gitorganize` file. The tool aims to make large-scale reorganizations auditable, reversible, and project-specific, using a two-phase workflow: a *labeler* assigns semantic labels to files (e.g., `component=odb`), and an *organizer* updates references (like `#include` paths or build system entries) after moves.

The series is now at its third patch, which adds a `--exit-code` option to `git organize status`. This allows the command to return a non-zero exit code when the tree is out of sync with the declared layout—useful for CI or pre-commit hooks to enforce consistency. The change is small and focused, distinguishing between *backlog* (files with labels but no rules) and *drift* (misplaced or missing files), with only the latter triggering a failure. The implementation is straightforward, with tests covering edge cases like shared basenames and missing files.

So far, the series has seen no substantive review, but this patch is unlikely to spark controversy. It’s a practical addition that doesn’t complicate the core workflow, and the design choices (e.g., not failing for backlog) are well-justified. The next patches will demonstrate the tool’s use to reorganize Git’s own codebase, but the atomicity guarantees (via `git apply --index`) and opt-in nature of the tool should keep concerns about disruption minimal. Key open questions remain, though: whether the labeler’s heuristics (relying on commit prefixes and `#include` coupling) are flexible enough for other projects, and how this effort might align with Patrick Steinhardt’s `libgit.a` series. For now, the series is still in the early review phase, with no decisions or objections yet recorded.
