This thread is an RFC proposal for `git organize`, a new command designed to systematically restructure Git’s source tree by moving files into subsystem-specific directories based on rules defined in a `.gitorganize` configuration file. The series, now 14 patches long, is authored by Michael Montalbo and aims to make structural changes auditable, reversible, and repeatable while keeping the tree buildable after each move.

The tool operates in two phases: a **labeler** assigns semantic labels (e.g., `component=setup`) to files using project-specific heuristics, and an **organizer** updates references (like `#include` paths and build system entries) after moves. The first six patches establish the tool’s infrastructure and configuration, including the `.gitorganize` file and label assignments for all source files. The seventh through thirteenth patches demonstrate the tool’s practical application by mechanically moving the ODB, refs, pack, diff, revision, index, and now **setup** subsystems into their own directories (`odb/`, `refs/`, `pack/`, `diff/`, `revision/`, `index/`, and `setup/`). Each move updates hundreds of files to reflect new paths, with net-zero line churn confirming the mechanical nature of the changes.

The setup subsystem, moved in the thirteenth patch, is foundational—its files (`config.c`, `environment.c`, `repository.c`, `setup.c`, etc.) are included by nearly every other subsystem, making this patch a critical test of the organizer’s ability to handle cross-subsystem dependencies. While the existing test suite continues to pass, reviewers may question whether all edge cases (e.g., platform-specific shims, external tools like Git for Windows, or nested `#include` chains) were addressed. The series remains under initial review, with no merge status reported, and key open questions include the tool’s generality for other projects, its performance on large repositories, and its alignment with ongoing efforts like Patrick Steinhardt’s `libgit.a` series.
