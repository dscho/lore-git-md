This is an RFC proposing a new configuration knob to make Git's stash stack per-worktree rather than global. The patch targets a real and increasingly common pain point: when multiple worktrees (or AI coding agents) share a repository, their stash operations silently interfere with each other, leading to data loss or unintended cross-worktree changes. The author demonstrates the problem with a clear reproduction case and cites real-world bug reports from tools like GitHub Copilot CLI and StablyAI Orca.

The proposal is pragmatic: introduce a `stash.ref` configuration key that defaults to `refs/stash` but can be set to a per-worktree ref (e.g., `refs/worktree/stash`). This leverages existing Git machinery (`refs/worktree/*`, `extensions.worktreeConfig`, and `git config --worktree`) and avoids inventing new concepts. The author explicitly rejects more disruptive alternatives like making the stash per-worktree by default or introducing named stashes, noting that the current approach preserves backward compatibility while solving the immediate problem.

Key technical details for follow-up discussion:
- The proposed config key is `stash.ref`, which would be honored by all stash subcommands (`push`, `pop`, `list`, etc.).
- The author seeks guidance on whether the config value should be restricted to valid ref names and whether `git stash list` should gain a `--all` flag to show stashes from all worktrees.
- Reachability of stash entries under `refs/worktree/*` is flagged as a potential concern for `gc` and `fsck`.

The patch is well-motivated and addresses a growing use case (AI agents working in parallel worktrees). The design is conservative, avoiding breaking changes, and the author is upfront about open questions. This looks like a strong candidate for eventual inclusion, pending discussion of the edge cases.
