This is a follow-up in the ongoing `the_repository` removal effort, specifically Junio C Hamano’s response to Hardik Kumar’s defense of a patch that partially converts built-in commands to use an explicit `struct repository *` parameter instead of the global `the_repository`. The patch targets `is_bare_repository()` call sites in five built-in commands (`blame`, `gc`, `repo`, `reset`) and `transport.c`.

Junio’s email rejects the patch’s approach outright, arguing that the inconsistent state it creates—mixing `the_repository` and the passed `repo` parameter in the same function—is not an improvement and risks introducing behavioral drift or segfaults. He clarifies that built-in commands like `cmd_blame()` are inherently tied to `the_repository` and cannot be reused with arbitrary repositories, making partial conversions strategically misguided. His critique extends beyond this patch: he calls the original design of passing a `struct repository *` to built-in commands "misguided," as the parameter is either `NULL` or `the_repository` and never any other value. He proposes a better path forward: changing the function signature of built-in commands to accept a `bool` indicating whether the command was run inside a repository, which would prevent confusion and eliminate the need for NULL checks.

The email also underscores a broader principle: while utility functions outside `builtin/` are being "libified" to reduce dependence on `the_repository`, the built-in command implementations themselves should not be updated to take arbitrary repository pointers. Junio’s position is clear: the patch’s partial conversion is not worth the effort or review time, and future work should focus on either full conversions (if the function is truly repository-agnostic) or abandoning the idea for built-in commands altogether. This sets a high bar for any follow-up patches in this area.
