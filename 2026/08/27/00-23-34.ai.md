This is a **bugfix** targeting the merge machinery, part of the ongoing effort to prevent unsafe commit operations during conflict resolution. Elijah Newren responds to Junio C Hamano’s feedback by posting a **v2 patch** that introduces a new helper function, `ongoing_operation()`, in `builtin/commit.c`. The helper consolidates logic for detecting active operations (merge, am, apply-based rebase, and sequencer-based rebase/revert) and is used to block both `git commit --amend` and `git commit <paths>` during conflict resolution.

The v2 patch addresses Junio’s suggestion to extend protection to `git commit <paths>` by reusing the same detection logic already in place for `--amend`. It also incorporates Junio’s minor cleanup request—replacing `the_repository` with `s->repo`—to align with the ongoing `the_repository` removal effort. The structural refactor avoids moving conflict-resolution checks into `sequencer_determine_whence()` (as Phillip Wood proposed) but achieves similar maintainability goals by centralizing the detection logic in a single helper.

Key technical details:
- Files touched: `builtin/commit.c` (new `ongoing_operation()` helper), with test coverage in `t3404-rebase-interactive.sh`, `t3507-cherry-pick-conflict.sh`, and `t4151-am-abort.sh`.
- New behavior: blocks both `git commit --amend` and `git commit <paths>` during conflict resolution for `git am`, `git revert`, and all `git rebase` variants, except for interactive rebase directives (`squash`, `reword`, `edit`, `break`, `fixup`) that explicitly require `--amend`.
- No on-disk format changes or new CLI options.
- The patch remains uncontroversial in its goal and approach, with Junio’s feedback now fully addressed. The only remaining loose end is whether the `#leftoverbits` marker for future work will be retained in the commit message.
