This is a follow-up discussion in the `the_repository` removal thread, specifically a reply from D. Ben Knoble to Junio C Hamano’s architectural objection. Ben raises a design question about libification: whether Git should explicitly support replicating built-in command behavior via libgit, or whether the current stance—where built-ins are not libified—is intentional and sufficient.

Ben’s concern is practical: if a program wants to replicate the behavior of `git switch` (or any other built-in) without shelling out to Git, the current code organization makes this difficult. Built-in implementations are complex and not structured as reusable libraries, so reimplementing their logic using existing libgit helpers would be a maintenance burden. He suggests that the project’s position—that it’s not worth libifying built-ins—only makes sense if Git also explicitly states that it does not support precisely replicating built-in behavior via libgit. Ben is seeking clarification on whether this stance is intentional and documented, or whether there has been prior discussion or consensus on the topic.

The email does not propose a patch or technical solution, but it introduces a new dimension to the architectural debate: the trade-off between code reusability and the effort required to libify built-ins. Ben’s perspective is exploratory rather than prescriptive, and he acknowledges that he lacks a concrete use case. His question is whether the project has considered organizing built-in code in a way that would make it feasible to replicate their behavior with a small sequence of libgit calls, even if full libification is not the goal. This could inform future decisions about how to structure built-in commands, particularly in the context of the `the_repository` removal effort. The thread remains open-ended, with no resolution or follow-up yet.
