This is a **substantive review** from Jeff King (Peff) on the third patch of Elijah Newren’s four-patch bugfix series (v2), which addresses a race condition in Git’s geometric repacking mechanism. The patch introduces a `stale_packs_detected` flag to force a rescan of the object database when a packfile vanishes mid-lookup, ensuring `OBJECT_INFO_QUICK` callers (like `git mktree --batch`) recover correctly instead of reporting false negatives.

Peff’s review challenges the patch’s core premise: he argues that `OBJECT_INFO_QUICK` is *supposed* to accept false negatives, and that the real issue lies in `git mktree --batch` using `QUICK` inappropriately. He suggests `mktree` should use `SKIP_FETCH_OBJECT` (or neither flag) instead of `QUICK`, as the latter is designed for scenarios like `git upload-pack` where speed on genuine misses outweighs occasional false negatives. Peff also questions whether the "error: packfile ... index unavailable" message is unnecessarily alarming, given that non-`QUICK` lookups already recover silently.

On the patch itself, Peff calls the `stale_packs_detected` flag a "hacky" way to trigger `SECOND_READ` for `QUICK` queries, noting that it subverts `QUICK`’s intended behavior. He further points out a race in the implementation: the flag is set when the `.idx` file is missing, but if the `.pack` file vanishes later, the flag won’t be set, leaving the lookup unrecovered. This could lead to inconsistent behavior depending on the timing of the repack.

The review is **technically sharp** and **controversial**: it reframes the problem as a misuse of `QUICK` rather than a bug in the repacking race logic. Peff’s alternative—fixing `mktree`’s flag usage—would be simpler but might not address the broader correctness issue for other `QUICK` callers (e.g., `git upload-pack`). The thread is now at a crossroads: Elijah’s patch prioritizes robustness for all `QUICK` users, while Peff’s critique suggests a narrower, more targeted fix. The outcome will likely hinge on whether the project views `QUICK`’s false negatives as acceptable trade-offs or as bugs to be mitigated. No other reviewers have weighed in on this specific point yet.
