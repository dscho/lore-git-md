This is a **bugfix series** (three patches) from Elijah Newren that tightens Git's safety net during conflict resolution. The goal is to prevent users from accidentally corrupting repository state by running `git commit --amend` or `git commit <paths>` while resolving conflicts in `git am`, `git revert`, or any form of `git rebase`.

The series is a direct follow-up to the v1 patch discussed earlier in the thread. Patch 1 rewords two existing rebase error messages to be more precise. Patch 2 blocks `git commit --amend` during conflict resolution for the newly covered operations, while Patch 3 extends the same protection to partial commits (`git commit <paths>`). The logic carefully distinguishes between genuine conflict stops and the internal use of `--amend` by interactive rebase directives like `squash` or `reword`, which remain allowed.

The implementation introduces a new helper function, `sequencer_ongoing_operation()`, in `sequencer.c` to consolidate the detection of in-progress operations. This improves maintainability by separating the merge and sequencer logic while avoiding the deeper refactor Phillip Wood suggested in his v1 review. The patch also aligns with the `the_repository` removal effort by replacing `the_repository` with `s->repo` where possible, though the partial commit callsite retains the global due to lack of a readily available repository instance.

Test coverage is thorough, with new tests in `t3404-rebase-interactive.sh`, `t3507-cherry-pick-conflict.sh`, and `t4151-am-abort.sh` verifying the behavior across all affected commands. The commit messages are detailed and explain both the motivation and the technical approach clearly. Junio C Hamano and Phillip Wood have already endorsed the v2 changes, and the series looks ready for integration. This is a well-crafted, uncontroversial fix that addresses a real foot-gun without disrupting legitimate workflows.
