This is a **bugfix** patch targeting the sequencer subsystem, specifically the `--autosquash` behavior in `git rebase`. The patch resolves a long-standing edge case where a `fixup!` or `squash!` commit cancels out all changes in its target commit, resulting in an empty commit. Previously, Git would halt the rebase with an error instead of respecting the user's `--empty` configuration (`drop`, `keep`, or `stop`). The fix is now in its fourth iteration (`v4`), incorporating substantive feedback from Phillip Wood, and is ready for final review.

The core issue is that `is_index_unchanged()` and `allow_empty()` compare the index against `HEAD` rather than `HEAD`'s parent when amending (as happens with `fixup!`/`squash!`), causing them to miss cases where the melded commit cancels out its target. The patch introduces a new check, `is_amended_head_empty()`, to detect when applying a `fixup!` or `squash!` empties the target commit. This check is integrated into the sequencer logic, ensuring that `--empty` is honored for such commits. The patch also tracks whether the target commit was originally picked with changes (via a new `enum fixup_target` and on-disk state in `$GIT_DIR/rebase-merge/fixup-target`), so only commits that *become* empty are subject to `--empty` handling. Commits picked empty to begin with are left untouched, preserving existing behavior for workflows that rely on empty commits as placeholders.

The implementation is careful to handle edge cases. For example, only the final `fixup!` in a chain may drop the target commit, as dropping it earlier would cause subsequent fixups to be squashed into the wrong commit. The patch also ensures that dropping a commit (when `--empty=drop` applies) correctly updates `HEAD` and cleans up the `rewritten-pending` file, preserving mappings for `--update-refs` and other consumers. Conflict resolution is supported: if a user resolves a conflicted `fixup!` by undoing its target, the patch honors `--empty` for the resulting empty commit. The on-disk state (`fixup-target`) survives stops for conflict resolution, ensuring consistency across rebase restarts.

The motivation is practical: the author maintains a fork of LLVM at Meta where internal patches are kept as single commits using `fixup!` autosquash. Retiring a patch currently requires manual todo-list surgery, but with this patch, a revert committed as a `fixup!` will automatically drop both the original and its revert when `--empty=drop` is used. The commit message includes a clear before/after example demonstrating the fix, and the patch adds thorough test coverage in `t/t3415-rebase-autosquash.sh` for all three `--empty` modes (`drop`, `keep`, `stop`) and edge cases like mid-chain fixups, root commits, and conflict resolution.

The patch touches `sequencer.c` (core logic), `Documentation/git-rebase.adoc` (user-facing documentation), and adds tests in `t/t3415-rebase-autosquash.sh` and `t/t5407-post-rewrite-hook.sh`. The changes are narrowly scoped to the identified problem and do not introduce new symbols or on-disk format changes. The `v4` iteration addresses all of Phillip Wood's review concerns, including correctness issues around dropping commits and preserving existing behavior for empty commits. The patch looks well-crafted, with a thorough commit message, complete test coverage, and careful handling of edge cases. It should be uncontroversial and ready for merging.
