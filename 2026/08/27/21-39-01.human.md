This is Junio C Hamano’s direct response to D. Ben Knoble’s question about libification in the ongoing `the_repository` removal thread. The email clarifies the project’s stance on libifying built-in commands and provides concrete guidance on how to structure reusable code.

Junio rejects the idea of treating built-in command implementations (`cmd_foo()`) as reusable library code. Instead, he advocates for a principled approach: if a program wants to replicate the behavior of a built-in command (e.g., `git switch`), the correct path is to factor out the reusable logic from the command implementation into separate, properly libified routines. These routines should then be called by both the original command and any other code that needs the same functionality. This approach avoids the pitfalls of "cheating" (e.g., calling `main()` or treating `cmd_foo()` as a library) and ensures that the reusable code is designed for modularity from the start.

The response is substantive and aligns with the architectural direction Junio proposed earlier in the thread. It reaffirms that built-in commands are not intended for libification and redirects the focus toward extracting reusable logic into utility functions outside the `builtin/` directory. This stance has implications for the `the_repository` removal effort: rather than incrementally converting built-in commands to use an explicit `struct repository *` parameter, the project will prioritize refactoring utility code to reduce dependence on globals. The email does not address Ben’s question about whether this stance is explicitly documented, but it provides a clear technical rationale for the approach.
