Subject: [PATCH] builtin/*: stop passing the_repository to is_bare_repository()
Series version: standalone patch (no cover letter), now superseded by Junio’s architectural proposal
Originating author: Hardik Kumar (initial patch), Junio C Hamano (architectural counter-proposal)
Thread type: refactoring patch (part of the ongoing `the_repository` removal effort), now expanded to architectural redesign of built-in command interfaces

Core problem or goal
The thread began as a small refactoring to remove implicit use of the global `the_repository` variable in five built-in commands by switching to an already-passed-but-unused `struct repository *` parameter. Junio’s review rejected this approach outright, arguing that the `repo` parameter in built-in command implementations (`cmd_foo()`) is a misguided design that should be removed entirely, not propagated. He now proposes a sweeping architectural change: replacing the `struct repository *` parameter in *all* built-in commands with a simple `bool has_repo` flag indicating whether the command was run inside a repository. This eliminates segfault risks (e.g., `cd / && git foo -h`), removes the false promise of libification for built-ins, and redirects the `the_repository` removal effort toward utility code outside `builtin/`. The broader goal has shifted from incremental conversion to architectural cleanup of built-in command interfaces, with implications for how Git’s internals are structured and documented. Junio’s subsequent clarification to D. Ben Knoble reaffirms that built-in commands are not intended for direct reuse via libgit; instead, reusable logic should be factored out into utility functions that both built-ins and other consumers (e.g., new commands) can call.

Current status
Junio’s architectural proposal is now the active direction, with Hardik Kumar’s explicit acceptance of the shift. The original patch by Hardik Kumar is definitively superseded. Junio’s patch applies cleanly to `master`, passes the test suite, and remains explicitly marked as a request for opinions rather than a final decision. Three substantive concerns remain: (1) **segfault risk**, where the `bool has_repo` flag prevents crashes in edge cases by making repository presence explicit, (2) **design clarity**, where the new interface removes the misleading `repo` parameter and reaffirms that built-in commands are not libified, and (3) **strategic redirection**, where the proposal halts further incremental `the_repository` conversions in built-in commands and focuses effort on utility code. Junio’s clarification to Ben Knoble resolves the libification question by redirecting reuse efforts toward factoring out shared logic. Hardik Kumar’s follow-up email poses a speculative question about whether the `bool has_repo` approach is a stepping stone toward a more efficient future design, but does not introduce new objections or propose alternatives. The question remains open-ended, inviting further clarification from Junio or other maintainers about the long-term vision for built-in command interfaces.
