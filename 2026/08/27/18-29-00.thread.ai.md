Thread type: architectural redesign of built-in command interfaces, part of the broader `the_repository` removal effort

Core problem or goal
The thread began as a small refactoring to remove implicit use of the global `the_repository` variable in five built-in commands by switching to an explicit `struct repository *` parameter. Junio’s review rejected this approach outright, arguing that the `repo` parameter in built-in command implementations (`cmd_foo()`) is a misguided design that should be eliminated entirely, not propagated. The goal has since expanded to a sweeping architectural change: replacing the `struct repository *` parameter in *all* built-in commands with a simple `bool has_repo` flag indicating whether the command was run inside a repository. This eliminates segfault risks (e.g., `cd / && git foo -h`), removes the false promise of libification for built-ins, and redirects the `the_repository` removal effort toward utility code outside `builtin/`. Junio’s subsequent clarifications reaffirm that built-in commands are not intended for direct reuse via libgit; instead, reusable logic should be factored out into utility functions that both built-ins and other consumers (e.g., new commands) can call. The latest clarification sharpens the distinction between two design flaws: (1) the "cheating" pattern where new commands like `git switch` and `git restore` were bolted onto `git checkout` via a monolithic `checkout_main()` helper, and (2) the deeper anti-pattern of treating `cmd_foo()` functions as reusable entry points when they are actually one-time orchestrators (like `main()`) that perform initialization and finalization unsuitable for repeated calls. The libification goal is now precisely defined as refactoring reusable logic out of built-in commands into standalone helper functions that accept a `struct repository *` parameter, placing all callers (built-ins and external programs) on equal footing.

Current status

Junio’s patch applies cleanly to `master`, passes the test suite, and remains explicitly marked as a request for opinions rather than a final decision. Three substantive concerns remain resolved: (1) **segfault risk**, where the `bool has_repo` flag prevents crashes in edge cases by making repository presence explicit, (2) **design clarity**, where the new interface removes the misleading `repo` parameter and reaffirms that built-in commands are not libified, and (3) **strategic redirection**, where the proposal halts further incremental `the_repository` conversions in built-in commands and focuses effort on utility code. Junio’s clarification to D. Ben Knoble resolved the libification question by redirecting reuse efforts toward factoring out shared logic, and Ben’s follow-up accepted this approach as sensible. Junio’s latest response to Hardik Kumar closed the speculative question about the `bool has_repo` approach being a stepping stone, framing it as a final state for built-in command interfaces. The latest clarification further refines the rationale for the `bool has_repo` design and the redirection of the `the_repository` removal effort, explicitly defining the libification path as extracting reusable logic into standalone helpers. No new objections or alternatives have been raised, but the patch remains open for community feedback.
