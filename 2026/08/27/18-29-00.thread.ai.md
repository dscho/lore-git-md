Core problem or goal
The thread implements the libification path clarified in the parent thread: reusable logic is factored out of the `git checkout`, `git switch`, and `git restore` built-in commands into standalone utility functions that accept a `struct repository *` parameter. The immediate goal is to eliminate the monolithic `checkout_main()` choke point, which was identified as a "cheating" pattern where `git switch` and `git restore` were bolted onto `git checkout` via a shared helper. The broader goal is to place all callers (built-in commands and external programs) on equal footing by extracting reusable logic into top-level files (`checkout.c`, `checkout.h`) that can be called directly. This aligns with the architectural direction established in the parent thread: built-in commands are not libified, but their reusable internals are. Junio now expresses skepticism about the refactoring's utility, noting that the series "scratches the surface" of what would be needed for true programmatic reuse (e.g., finer-grained control than entire commands like `git restore`).
