This thread began as a small refactoring to remove implicit use of Git’s global `the_repository` variable in a handful of built-in commands, but Junio C Hamano’s review transformed it into a sweeping architectural proposal. The core issue is now whether built-in commands should continue accepting a `struct repository *` parameter—a design Junio argues is misleading and unsafe—or switch to a simpler `bool has_repo` flag that makes repository presence explicit. His patch, which applies cleanly to `master` and touches 135 files, removes the `repo` parameter entirely, eliminating segfault risks (e.g., running `git foo -h` outside a repository) and reaffirming that built-in commands are not intended for libification. The change also redirects the ongoing `the_repository` removal effort away from built-in commands and toward utility code, where the work is more meaningful.

Junio’s latest email clarifies the project’s stance on libification: rather than exposing `cmd_foo()` functions as reusable entry points, the correct approach is to factor out shared logic into utility functions that both built-ins and other consumers can call. This resolves an open question from D. Ben Knoble and strengthens the case for the architectural shift. The remaining hurdles are community consensus—will contributors like René Scharfe or Patrick Steinhardt accept this change?—and coordination with others working on `the_repository` removal to avoid duplicative efforts. Hardik Kumar’s original patch is now superseded, and no further incremental conversions in built-in commands are expected unless Junio’s proposal is rejected. The patch itself is mechanical and passes tests, but its implications for Git’s internals are far-reaching.
