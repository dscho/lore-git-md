This is a **bugfix patch update** (v2) from Elijah Newren, addressing Junio C Hamano’s feedback on a patch that extends Git’s protection against unsafe commit operations during conflict resolution. The patch now blocks both `git commit --amend` and `git commit <paths>` during conflict stops for `git am`, `git revert`, and all forms of `git rebase`, preventing users from accidentally corrupting repository state by amending the wrong commit or updating individual paths.

Elijah incorporated Junio’s suggestion to replace `the_repository` with `s->repo` in the new conflict-resolution checks, aligning with the ongoing `the_repository` removal effort. The only exception is the `git commit <paths>` case, where no repository instance was readily available, so `the_repository` is still used there. The patch introduces a new helper function, `ongoing_operation()`, in `builtin/commit.c` to consolidate logic for detecting active operations (merge, am, apply-based rebase, and sequencer-based rebase/revert) while keeping merge and sequencer logic separate.

The patch touches `builtin/commit.c` and adds test coverage in `t3404-rebase-interactive.sh`, `t3507-cherry-pick-conflict.sh`, and `t4151-am-abort.sh`. It does not change on-disk formats or introduce new CLI options. The commit message retains a `#leftoverbits` marker for future work, though it’s unclear whether this will be addressed in follow-up patches.

This update follows Junio’s endorsement of the patch’s correctness and Phillip Wood’s earlier suggestion to refactor conflict-resolution checks into `sequencer_determine_whence()` for better maintainability. Elijah opted for a middle-ground approach, consolidating logic without fully adopting Phillip’s proposed refactor. The patch is now well-motivated, thoroughly tested, and addresses all feedback from the maintainer and reviewers. It looks ready for `next` unless new concerns arise.
