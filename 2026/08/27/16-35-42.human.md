This is a **bugfix documentation patch** — the first in Elijah Newren’s three-part series to prevent unsafe commit operations during conflict resolution. Junio C Hamano raises a **substantive technical question** about the patch’s logic: whether the code can reliably distinguish between a rebase that stopped because a commit became empty (the hazard this series targets) and a rebase that stopped for other reasons (e.g., a normal conflict during a `pick` step).

The patch rewords two error messages in `builtin/commit.c` to clarify that restrictions on `git commit --amend` and `git commit <paths>` apply specifically when resolving a commit that became empty, not during rebase in general. Junio’s concern is that the current implementation uses `is_from_rebase(whence)` and `whence == FROM_REBASE_PICK` as proxies for "a commit became empty," but these flags do not actually indicate whether the rebase stopped due to an empty commit — only that a rebase is in progress. If a user resolves a normal conflict (not an empty commit) and then tries to amend or commit a subset of paths, the new error messages would misleadingly claim the commit became empty, which could confuse users and obscure the real reason for the restriction.

The patch is otherwise uncontroversial: it improves clarity, aligns with the series’ goal, and has no behavioral impact. However, Junio’s question suggests the underlying logic may need revisiting before the series can proceed. The thread’s prior context confirms the series is otherwise ready for integration, with Phillip Wood calling it "pretty sound" and Junio previously endorsing its direction. This specific patch, though small, now hinges on whether the detection logic can be made more precise.
