This is the ninth patch in Kristoffer Haugsbakk’s now-merged 11-patch documentation series (`kh/doc-trailers`) that overhauls the `git-interpret-trailers` man page. The patch commits the documentation to the term “trailer block” (already introduced in earlier patches) by systematically replacing looser phrasing with the new terminology throughout the DESCRIPTION section.

The change is purely editorial: it replaces three paragraphs that previously talked about “existing trailers” and “blank lines” with a single coherent narrative centered on the “trailer block” concept. The old text said “a blank line will be added before the new trailer if there isn’t one already,” which was ambiguous—does “one” refer to a blank line or to an existing trailer? The new version removes the ambiguity by stating that a blank line is inserted only when a new trailer block must be created. It also clarifies that the trailer block is always at the end of the commit message, either at the very end of the input or immediately before a `---` line, eliminating the need to repeat the “preceded by one or more empty lines” rule.

The commit message explains the motivation in detail: the “trailer block” term simplifies the text by unifying the two contexts (adding to an existing block vs. creating a new one) and removes redundancy. A footnote even walks through a concrete example—adding a `Reviewed-by` after a `(cherry picked from commit <commit>)` line—to show why inserting a blank line would be wrong. The patch is uncontroversial and part of a series that has already been merged to `master`; this v5 iteration is unchanged from v4 except for a trivial commit-message tweak in patch 11/11.
