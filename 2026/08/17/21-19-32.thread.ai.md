Thread identity
Subject: [RFC PATCH v2] config: propagate editor failure exit code
Series version: v2 (standalone patch)
Originating author: Kenneth Lorber
Thread type: bug report / bugfix patch

Core problem or goal
`git config -e` currently exits with status 0 even when the configured editor fails (crashes or returns non-zero). The patch changes `show_editor()` in `builtin/config.c` to return the error code from `launch_editor()` instead of unconditionally returning 0, thereby surfacing the editor failure to the caller.

Current status
Under review (RFC). This is the second version of the patch. Changes from v1: incorporated Karthik Nayak's surface-level test-script cleanups—replaced manual `GIT_EDITOR` export/unset with `test_env` and simplified test names from `--edit` to `-e` to match the actual command. The patch's substance (one-line code change and two new tests) remains unchanged. The feature being modified was introduced mid-2024, limiting the scope of potential breakage. No maintainer decision yet; Junio's latest response frames the decision as a trade-off between conceptual correctness (aligning with commands like `git commit`) and script breakage but does not resolve it.

Key technical details
Files touched: `builtin/config.c` (function `show_editor()`), `t/t1300-config.sh` (updated tests)
New symbols: none
Behavior change: `git config -e` now exits non-zero if the editor fails, rather than always exiting 0
On-disk format: unchanged
Test coverage: two tests covering editor success (exit 0) and failure (exit 1), using `test_env` for `GIT_EDITOR` setup; no change to test logic or coverage

Open questions and loose ends
- Is the current behavior (ignoring editor failure) intentional or a bug?
- Could this break existing scripts that rely on `git config -e` always succeeding? The limited age of the feature (introduced mid-2024) reduces but does not eliminate this risk.
- No clear maintainer direction yet; Junio's latest response frames the decision as a trade-off between conceptual correctness (aligning with commands like `git commit`) and script breakage but does not resolve it.
- The thread's core tension—whether the benefit of consistency (with commands like `git commit`) outweighs the risk of breaking scripts—remains unresolved.

Participant positions
Kenneth Lorber (author): argues the current behavior may not have been intentional and proposes the change as a bugfix. Acknowledges potential script breakage and seeks community input on the trade-off. Implementation is clean and test coverage is appropriate. Has accepted Karthik Nayak's surface-level test-script cleanups without altering the patch's substance.
Junio C Hamano (maintainer): notes the inconsistency with commands like `git commit` but questions the value of changing the behavior now, given that the config file is already modified by the time the editor exits. Latest response acknowledges the trade-off between conceptual correctness and script breakage but remains neutral-to-skeptical; no technical objections to the patch itself. Emphasizes the feature's recent introduction (mid-2024) as a mitigating factor for breakage risk.
Karthik Nayak: supports the change, arguing that surfacing the error to the user (via non-zero exit code) is more intuitive and aligns with user expectations, even if the config file has already been modified. Engages directly with Junio's skepticism, framing the change as a user experience improvement.
brian m. carlson: supports propagating the editor's exit code, emphasizing that nonzero exit codes from editors are meaningful and that scripts relying on `set -e` may be silently broken by the current behavior. Engages directly with Junio's trade-off framing, arguing that the risk of masking errors outweighs the benefit of backward compatibility in this case. Contribution is substantive but does not introduce new technical details or alternatives.
