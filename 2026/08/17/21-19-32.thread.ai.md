Thread identity
Subject: [RFC PATCH] config: propagate editor failure exit code
Series version: none (standalone patch)
Originating author: Kenneth Lorber
Thread type: bug report / bugfix patch

Core problem or goal
`git config -e` currently exits with status 0 even when the configured editor fails (crashes or returns non-zero). The patch changes `show_editor()` in `builtin/config.c` to return the error code from `launch_editor()` instead of unconditionally returning 0, thereby surfacing the editor failure to the caller.

Current status
Under review (RFC). No prior versions. Patch is minimal: one-line code change plus two new tests in `t/t1300-config.sh` that verify exit codes when `GIT_EDITOR` is set to `true` (exit 0) and `false` (exit 1). Junio C Hamano has responded twice, first questioning the value of altering long-standing behavior given that the config file has already been modified by the time the editor exits, and second acknowledging the trade-off between conceptual correctness and potential script breakage but remaining noncommittal. The patch was introduced only two years ago (mid-2024), limiting the scope of potential breakage. Karthik Nayak has weighed in twice: first explicitly supporting the change as more intuitive and aligned with user expectations, and second providing a surface-level review suggesting minor test-script cleanups (using `test_env` for `GIT_EDITOR` setup).

Key technical details
Files touched: `builtin/config.c` (function `show_editor()`), `t/t1300-config.sh` (new tests)
New symbols: none
Behavior change: `git config -e` now exits non-zero if the editor fails, rather than always exiting 0
On-disk format: unchanged
Test coverage: added two tests covering editor success (exit 0) and failure (exit 1); Karthik Nayak's review suggests stylistic improvements to test setup but does not alter test logic or coverage

Open questions and loose ends
- Is the current behavior (ignoring editor failure) intentional or a bug?
- Could this break existing scripts that rely on `git config -e` always succeeding? The limited age of the feature (introduced mid-2024) reduces but does not eliminate this risk.
- No clear maintainer direction yet; Junio's latest response frames the decision as a trade-off but does not resolve it. Karthik Nayak's support may influence further discussion, but no other substantive reviews have been provided.
- The thread's core tension—whether the benefit of consistency (with commands like `git commit`) outweighs the risk of breaking scripts—remains unresolved.

Participant positions
Kenneth Lorber (author): argues the current behavior may not have been intentional and proposes the change as a bugfix. Acknowledges potential script breakage and seeks community input on the trade-off. Implementation is clean and test coverage is appropriate.
Junio C Hamano (maintainer): notes the inconsistency with commands like `git commit` but questions the value of changing the behavior now, given that the config file is already modified by the time the editor exits. Latest response acknowledges the trade-off between conceptual correctness and script breakage but remains neutral-to-skeptical; no technical objections to the patch itself. Emphasizes the feature's recent introduction (mid-2024) as a mitigating factor for breakage risk.
Karthik Nayak: supports the change, arguing that surfacing the error to the user (via non-zero exit code) is more intuitive and aligns with user expectations, even if the config file has already been modified. Engages directly with Junio's skepticism, framing the change as a user experience improvement. Also provided a surface-level review suggesting minor test-script cleanups (using `test_env` for `GIT_EDITOR` setup), which does not affect the patch's substance.
