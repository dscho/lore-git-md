This is the **v4 iteration of a security feature patch** that adds `http.sslVerifyStatus`, a boolean config option (default `false`) to enable OCSP staple validation in Git’s HTTPS transport. The patch is now **technically complete** and addresses all procedural feedback from previous rounds.

The core change remains unchanged: when `http.sslVerifyStatus` is set to `true`, Git instructs libcurl to validate the stapled OCSP response during the TLS handshake, causing the connection to fail if the server does not provide a staple or if the staple indicates a revoked certificate. This closes a security gap where OpenSSL-linked Git binaries (common in FIPS-compliant deployments) silently ignore staples and accept revoked certificates. The design is fail-closed (no staple → failure) but defaults to `false` to avoid breaking remotes that do not support stapling.

Key adjustments in v4:
- **Test integration**: The four new tests have been moved from the abandoned `t5568` script into `t5551-http-fetch-smart.sh`, where they run only in the HTTPS pass (via `t5559`). This eliminates the need for a new test script and resolves the earlier numbering conflict.
- **Prerequisite robustness**: The `SSL_VERIFYSTATUS` lazy prerequisite now uses `test_might_fail` to properly handle the expected failure of `git ls-remote` when stapling is enabled but unavailable, avoiding silent skips.
- **Documentation**: The commit message now includes the rationale that was previously in an in-code comment, explaining why the default cannot be left to libcurl (which intentionally ignores staples) and why the feature is fail-closed.

The patch touches `http.c` (adding the config option and libcurl setup), `Documentation/config/http.adoc` (documenting the new key and backend differences), and `t/t5551-http-fetch-smart.sh` (adding tests for the fail-closed path and per-URL overrides). No symbols are renamed, and the libcurl requirement (`CURLOPT_SSL_VERIFYSTATUS` since 7.41.0) is already below Git’s minimum version.

The open question from earlier rounds—whether the feature’s maintenance burden is justified by its use case—remains unresolved, but the author has provided concrete evidence: government and FIPS-compliant deployments (e.g., US DoD PKI) mandate OCSP stapling, and OpenSSL-linked Git binaries (common in these environments) currently ignore staples, creating a security gap. The threat model (stolen private key impersonation enabling data exfiltration) is framed as a low-to-medium severity CVE risk. The patch is now ready for final review, with no outstanding technical or procedural issues.
