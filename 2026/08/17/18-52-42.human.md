This is a **security feature patch** that adds `http.sslVerifyStatus`, a new boolean configuration option (default `false`) to enable OCSP staple validation in Git’s HTTPS certificate verification. The patch is now in its fourth iteration and addresses all prior procedural feedback.

The core issue is that Git’s OpenSSL-linked builds silently ignore stapled OCSP responses, leaving users vulnerable to accepting revoked certificates. This creates a security gap for government and FIPS-compliant deployments (e.g., US Department of Defense PKI) where OCSP stapling is mandated. The patch closes this gap by setting libcurl’s `CURLOPT_SSL_VERIFYSTATUS`, which causes connections to fail if the server does not provide a staple. The design is fail-closed for security but defaults to `false` to avoid breaking remotes that do not support stapling.

This version (v4) simplifies the test approach by integrating the four new tests into the existing `t5551-http-fetch-smart.sh` script, keyed to run only in the HTTPS pass (via `t5559`). This avoids the need for a new test script and resolves the earlier numbering conflict. The tests verify the fail-closed behavior (connections fail when staples are missing) and per-URL configuration overrides. The patch also fixes the `SSL_VERIFYSTATUS` lazy prerequisite to use `test_might_fail` instead of a bare `&&`, ensuring the test fails loudly if the server does not support stapling.

The patch is technically complete and ready for final review. The remaining open question is whether the feature’s maintenance burden (given OCSP stapling’s declining relevance) is justified by its use case. The author has provided concrete evidence of real-world demand, framing the threat model as a low-to-medium severity CVE risk (stolen private key impersonation enabling data exfiltration).
