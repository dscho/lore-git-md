This thread is about a proposed change to `git config -e` to make it exit with a non-zero status if the configured editor fails, rather than always returning success. The patch, submitted by Kenneth Lorber in mid-2024, fixes what the author argues may have been an unintended behavior: the config file is modified even if the editor crashes or exits with an error, but Git still reports success.

The discussion has centered on whether this change is worth making, given the trade-off between conceptual correctness and potential breakage of existing scripts. Junio C Hamano, the maintainer, has expressed skepticism about the value of altering long-standing behavior, noting that the config file is already modified by the time the editor exits. However, he acknowledges the feature's recent introduction (mid-2024) limits the scope of potential breakage. Karthik Nayak supports the change, arguing it aligns with user expectations and improves consistency with commands like `git commit`. Brian M. Carlson has now also weighed in, emphasizing that the current behavior risks masking meaningful errors, particularly for scripts using `set -e`.

The patch itself is minimal: a one-line code change in `builtin/config.c` and two new tests in `t/t1300-config.sh` to verify the exit codes. No maintainer decision has been made yet, and the thread remains unresolved. The key question—whether the benefit of surfacing editor failures outweighs the risk of breaking scripts—is still open.
