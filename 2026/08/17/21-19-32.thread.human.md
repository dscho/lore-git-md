This thread is about a proposed change to make `git config -e` exit with a non-zero status when the configured editor fails, rather than always succeeding. The patch, submitted by Kenneth Lorber as an RFC, fixes what the author suggests may be an unintended inconsistency: while commands like `git commit` propagate editor failures, `git config -e` does not. The change is minimal—just one line of code plus two new tests—but the RFC status reflects uncertainty about whether the current behavior is intentional and whether changing it could break existing scripts.

Junio C Hamano, the maintainer, has weighed in with a measured response. He acknowledges the inconsistency but questions the practical benefit of the change. Unlike `git commit`, where an editor failure can prevent an unintended commit, `git config -e` has already modified the config file by the time the editor exits, so surfacing the failure doesn’t enable meaningful recovery. His reply neither endorses nor rejects the patch, but it suggests the bar for altering long-standing behavior is high. No technical objections to the implementation itself were raised, leaving the RFC’s future open-ended while the community considers the trade-offs. So far, no other reviewers have chimed in.
