This thread is about a small but potentially disruptive change to `git config -e`: making it exit with a non-zero status if the configured editor fails, rather than always succeeding. The patch itself is simple—a one-line code change plus two new tests—but the discussion centers on whether the current behavior (ignoring editor failures) is a bug or an intentional design choice, and whether fixing it now is worth the risk of breaking scripts that might rely on the current behavior.

Kenneth Lorber, the author, argues the change is a bugfix and aligns `git config -e` with commands like `git commit`, which already propagate editor failures. Junio Hamano, the maintainer, acknowledges the inconsistency but remains skeptical, framing the decision as a trade-off between conceptual correctness and script breakage. Karthik Nayak and brian m. carlson support the change, emphasizing that surfacing editor failures is more intuitive and safer for scripts using `set -e`. The feature being modified was introduced only in mid-2024, which limits the scope of potential breakage but doesn’t eliminate it.

The latest update is minor: Kenneth has incorporated Karthik’s suggested test-script cleanups (using `test_env` for `GIT_EDITOR` setup), but the patch’s substance and the thread’s core tension remain unchanged. No maintainer decision has been made yet, and the discussion is still open.
