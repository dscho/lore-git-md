Core problem or goal
Add a Trace2 event to `git pack-objects` that records the cumulative size (in bytes) of all pack files generated during a single invocation, including headers and checksums. This fills an observability gap: Trace2 already records object counts but not byte counts, which are needed to measure how compression settings affect push performance.

Key technical details
- New Trace2 event: `write_pack_file/wrote_bytes`
- Symbol: `bytes_written` (accumulator variable, simplified in v2)
- Files: `builtin/pack-objects.c`, `t/t5300-pack-object.sh`
- Behavior: reports cumulative bytes written across all packs in a single `git pack-objects` run, including headers and checksums
- On-disk format: no changes
- Test coverage: single pack, split packs (via `pack.packSizeLimit`), and edge cases (empty packs)
- Hash size handling: v3 will use `f->algop->rawsz` (the hashfile’s algorithm) instead of `the_repository->hash_algo->rawsz` for consistency, as confirmed functionally equivalent by Jeff King and endorsed by Patrick Steinhardt and Junio C Hamano.

Open questions and loose ends
1. **Event naming clarity**: Patrick Steinhardt noted that the existing Trace2 event `"write_pack_file/wrote"` is ambiguously named (it counts objects, not bytes) and suggested `"wrote_objects"` would be clearer. This remains an optional improvement; no consensus has been reached on whether to rename it.
2. **Triple-hash recomputation**: Jeff King and Patrick Steinhardt conducted a **substantive technical discussion** on the current triple-hash recomputation in `write_pack_file()` when packs are split (triggered by `--max-pack-size`). The code recomputes the packfile’s hash three times: once during writing (via `struct hashfile`), once during read-back verification, and once during `fixup_pack_header_footer()`. Both reviewers agree this is "absurdly pessimal" and that the read-back verification (second pass) is redundant and could be dropped without sacrificing safety, as Git does not re-verify other on-disk data like loose objects or refs. Junio C Hamano has now endorsed this proposal in a **surface-level reply**, agreeing that dropping the read-back step is a reasonable optimization. The unsafe hash variants (introduced for performance) are not currently used in this code path, despite being a prime candidate for optimization. Jeff King speculates this was an oversight, but notes the split-pack case is rarely exercised, so the performance impact went unnoticed. The discussion is exploratory and does not propose a patch, but lays groundwork for a future optimization. The Trace2 byte-counting patch itself remains unaffected; this is a tangential performance discussion.
