This is the eighth patch in Pablo Sabater’s ten-patch GSoC series, now at v6, which extends `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The series is feature-complete, addresses all prior review feedback, and is explicitly endorsed by Junio as ready to merge.

This patch prepares the client to parse object type data from the server response, though the server does not yet advertise the "type" capability (that comes in patch 9). The changes mirror the existing pattern for size metadata: a `wants_type` flag and `types` array are added to `struct fetch_object_info_results`, and the client-side parsing logic maps the server’s type string (e.g., `"blob"`) to an internal `enum object_type` using `type_from_string_gently()`. If the server sends an unrecognized type string, the client `die()`s with a clear error message.

The patch touches three files. In `fetch-object-info.c`, it extends `send_object_info_request()` to include the "type" keyword in the protocol request when the caller sets `wants_type`, updates the response parsing loop to handle the "type" attribute, and adds validation to ensure the server does not send duplicate or unrequested type data. The parsing logic uses `type_from_string_gently()` to convert the server’s type string to an `enum object_type`, with a `die()` if the string is invalid. In `builtin/cat-file.c`, the patch updates the caller to set `wants_type` when the user requests `%(objecttype)` and appends "objecttype" to the allowed-atoms list if the server provides type data. In `fetch-object-info.h`, it adds the `wants_type` flag and `types` array to `struct fetch_object_info_results` and updates `free_fetch_object_info_results()` to free the new array.

The patch is mechanical and uncontroversial, following the established pattern for size metadata. It does not alter behavior yet—object type support remains disabled until the server advertises the capability—but it completes the client-side plumbing needed to handle type data once the server is ready. The design avoids sentinel values and boolean flags, using a dedicated array and flag for each attribute, and the validation logic ensures the client fails fast if the server violates protocol invariants.
