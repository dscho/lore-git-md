Thread identity: Patch series improving user-facing error messages for `git worktree add`, `git checkout`, and `git switch` when an ambiguous remote branch name is provided (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). Seventh iteration (v7) of a three-patch series originating from Yoichi NAKAYAMA. Thread type: patch series.

Core problem or goal: Replace the terse "matched multiple remote tracking branches" warning with a detailed, actionable advice message to help users resolve ambiguity. The advice is gated behind `advice.checkoutAmbiguousRemoteBranchName` (enabled by default) and provides a static list of conflicting remotes (e.g., "Branch name '%s' appears in multiple remotes:") for immediate usability. The series also refines error handling by moving an existing `die()` call earlier in the code path, replacing a generic "invalid reference" message with a more specific diagnostic that explains the ambiguity. This is a usability improvement, not a regression, as the command was already failing — just with less clarity. The problematic flow (silent failure to resolve ambiguity -> `NULL` remote -> misleading "invalid reference" error) is explicitly traced in the commit message to justify the early `die()` as intentional. The implementation avoids altering `dwim_branch()`'s return behavior, addressing concerns about workflow disruption. Junio C Hamano has identified a latent bug in `git worktree add`'s one-argument form (e.g., `git worktree add ../topic-branch`): the command should error out when ambiguity exists, rather than silently creating a local branch from HEAD. This issue stems from an incomplete refactoring in 2018 (Ævar Arnfjörð Bjarmason’s `unique_tracking_name()` update), which improved `git checkout` but left `git worktree add` unable to distinguish between zero matches and multiple matches. The current series fixes one of the two affected code paths; the other (the one-argument `worktree add` case) is left for a follow-up effort.

Current status: Ready for merging.
