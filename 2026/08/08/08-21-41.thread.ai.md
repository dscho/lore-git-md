Thread identity: Patch series improving user-facing error messages for `git worktree add` (and potentially `git checkout`/`git switch`) when an ambiguous remote branch name is provided (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). Single-patch series originating from Yoichi NAKAYAMA, now in its fifth iteration (v5 implied by Junio’s proposed refactoring). Thread type: patch series.

Core problem or goal: Replace the terse "matched multiple remote tracking branches" warning with a detailed, actionable advice message to help users resolve ambiguity. The advice is gated behind `advice.checkoutAmbiguousRemoteBranchName` (enabled by default) and focuses on *immediate usability* by providing a static list of conflicting remotes (e.g., "the branch exists on `origin`, `upstream`") rather than requiring users to run a separate command. The patch also refines error handling by moving an existing `die()` call earlier in the code path, replacing a generic "invalid reference" message with a more specific diagnostic that explains the ambiguity. This is a usability improvement, not a regression, as the command was already failing — just with less clarity. The problematic flow (silent failure to resolve ambiguity -> `NULL` remote -> misleading "invalid reference" error) is explicitly traced in the commit message to justify the early `die()` as intentional. The implementation avoids altering `dwim_branch()`'s return behavior, addressing concerns about workflow disruption.

Current status: Under active review. The series is functionally complete, with all substantive feedback addressed in prior iterations. The latest discussion centers on the *mechanism* for surfacing ambiguity: Junio’s proposed refactoring extends `unique_tracking_name()` to optionally return the list of conflicting remotes, enabling a static list in the advice message. This replaces Yoichi’s command-based approach (`git branch -r --list '*/<name>'`) and unifies the advice logic across `checkout`, `switch`, and `worktree add` via a new shared helper (`be_explicit()`). The refactoring is backward-compatible and does not disrupt existing callers. Minor code nits (unnecessary newline, braces) remain unaddressed but are secondary to the core design. The unresolved question is whether the static list (Junio’s preference) or command-based discovery (Yoichi’s prior implementation) is more effective for user discovery, though the refactoring provides a clear path forward.
