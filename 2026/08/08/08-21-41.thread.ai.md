Thread identity: Patch series improving user-facing error messages for `git worktree add` (and potentially `git checkout`/`git switch`) when an ambiguous remote branch name is provided (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). Fifth iteration (v5) of a single-patch series originating from Yoichi NAKAYAMA. Thread type: patch series.

Core problem or goal: Replace the terse "matched multiple remote tracking branches" warning with a detailed, actionable advice message to help users resolve ambiguity. The advice is gated behind `advice.checkoutAmbiguousRemoteBranchName` (enabled by default) and provides a static list of conflicting remotes (e.g., "the branch exists on `origin`, `upstream`") for immediate usability. The patch also refines error handling by moving an existing `die()` call earlier in the code path, replacing a generic "invalid reference" message with a more specific diagnostic that explains the ambiguity. This is a usability improvement, not a regression, as the command was already failing — just with less clarity. The problematic flow (silent failure to resolve ambiguity -> `NULL` remote -> misleading "invalid reference" error) is explicitly traced in the commit message to justify the early `die()` as intentional. The implementation avoids altering `dwim_branch()`'s return behavior, addressing concerns about workflow disruption.

Current status: Under active review, functionally complete. All substantive feedback has been addressed, and the core design debate (static list vs. command-based advice) is settled in favor of Junio’s refactoring. The refactoring extends `unique_tracking_name()` to optionally return the list of conflicting remotes, enabling a static list in the advice message and unifying the logic across `checkout`, `switch`, and `worktree add` via a new shared helper (`be_explicit()`). The patch is backward-compatible and does not disrupt existing callers. Minor code nits (unnecessary newline, braces) remain unaddressed but are secondary to the core design. The next steps are likely to focus on these nits before merging.

Key technical details:
- Files: `builtin/worktree.c`, `builtin/checkout.c`, `checkout.c`, `checkout.h`, `t/t2400-worktree-add.sh`
- New/updated functions: `unique_tracking_name()` (extended to optionally collect remote names via `struct string_list *dwim_remote_names`), `be_explicit()` (new shared helper for advice messages)
- New config key: `advice.checkoutAmbiguousRemoteBranchName` (default: true)
- Advice message: Proposes a static list of conflicting remotes (e.g., "the branch exists on `origin`, `upstream`") and suggests using `--track` or setting `checkout.defaultRemote` for future disambiguation. The message is tailored to the command (`checkout`/`switch` vs. `worktree add`).
- Behavior change: Moves an existing `die()` call earlier in the code path, replacing a generic "invalid reference" message with a more specific diagnostic that explains the ambiguity. The diagnostic logic is relocated to avoid altering `dwim_branch()`'s return behavior, addressing workflow concerns. The commit message justifies this change by tracing the problematic flow (silent failure to resolve ambiguity -> `NULL` remote -> misleading error).
- Test coverage: Updated existing tests + new test for `--guess-remote` with ambiguous branch; coverage verifies the new advice format and error-handling behavior. The `--guess-remote` case is explicitly excluded from emitting warnings/advice.
- Edge cases: The ambiguous branch warning does not trigger for fully qualified branch names (e.g., `origin/bar-topic`), as these are resolved earlier in the code path. The detached HEAD scenario is dismissed as unlikely and irrelevant. A minor edge case involving typos in fully qualified branch names (e.g., `origin/bar-topik` matching multiple remotes due to partial matches) is noted but considered too rare to address.

Open questions and loose ends:
