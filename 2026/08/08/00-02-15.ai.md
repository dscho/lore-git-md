This is the v6 iteration of Pablo Sabater’s GSoC feature series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The series is now ten patches, feature-complete, and addresses a static-analysis warning that surfaced in CI for v5.

The core goal remains unchanged: object type is the last piece of metadata guaranteed to be identical on client and server after a fetch, so the series adds end-to-end support—server capability advertisement, client request logic, protocol extension, and client-side parsing/display. The scope is deliberately narrow; other metadata (disk size, delta base, object mode) are explicitly ruled out as unreliable or context-dependent.

Patches 1–6 are preparatory. Patch 1 is a test cleanup in `t5701-git-serve.sh`, replacing `wc -c | xargs` with `test_file_size()` and caching `git rev-parse` output for robustness. Patch 2 hardens the client against malformed server responses by explicitly checking both under-length (fewer objects than requested) and over-length (more objects than requested) cases; the fix extracts `packet_reader_read()` from the loop condition so the loop no longer consumes the final packet, and the client now `die()`s if anything other than a flush packet arrives after the expected number of objects. Patches 3 and 4 refactor how object data is stored and handled, replacing `struct object_info_args` and `struct object_info` with a dedicated `struct fetch_object_info_results` that avoids sentinel values and boolean flags. Patch 5 converts the last error path in `fetch_object_info()` to `die()`, making the function `void` and removing the final `return 0`. Patch 6 is Jeff King’s mechanical refactoring that removes object-info fields from `git_transport_options` and passes them as explicit parameters to `transport_fetch_object_info()`, clarifying ownership semantics and eliminating a latent bug where dangling pointers could persist if the transport were reused.

Patches 7–10 implement object type support. Patch 7 teaches the server to parse and transmit type data as a string (e.g., `"blob"`), adding a `type` bit field to `struct requested_info` and updating the server-side handler. Patch 8 teaches the client to request and parse type data, adding a `wants_type` flag and `types` array to `struct fetch_object_info_results` and mapping the server’s type string to an internal `enum object_type` using `type_from_string_gently()`. Patch 9 appends "type" to the advertised capabilities string in `serve.c` and updates the test suite to expect the actual type ("blob") for `%(objecttype)` and confirm that unsupported placeholders (e.g., `%(objectmode)`) still return empty strings. Patch 10 unifies the default format for all `cat-file` batch commands, removing the temporary workaround that used a different default format for remote queries and ensuring consistent output across all transport protocols (git://, file://, http://).

The v6 changes are minimal: two forward declarations to fix a static-analysis warning and a whitespace fix (`%"PRIuMAX"` → `"% PRIuMAX "`). All prior review feedback has been addressed, and Junio has explicitly endorsed patches 1–10 as ready to merge. The series touches only four files (`Documentation/git-cat-file.adoc`, `Documentation/gitprotocol-v2.adoc`, `builtin/cat-file.c`, and `t/t1017-cat-file-remote-object-info.sh`) beyond the preparatory refactoring, and all tests are passing. The potential optimization to make the `remote-object-info` protocol stateful for connection reuse is deferred to a follow-up series, with no impact on the current patch set.
