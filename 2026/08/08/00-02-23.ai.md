This is patch 8/10 in Pablo Sabater’s GSoC v6 series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The series is now feature-complete and ready for integration, with all prior review feedback addressed and Junio’s explicit endorsement for all ten patches.

This patch prepares the client to parse object type data from the server response, though the server does not yet advertise the "type" capability (that comes in patch 9/10). The changes are mechanical and follow the established pattern for size metadata. In `fetch-object-info.c`, the patch adds a `wants_type` flag and `types` array to `struct fetch_object_info_results`, extends the protocol request to include the "type" keyword when requested and supported, and maps the server’s type string (e.g., `"blob"`) to an internal `enum object_type` using `type_from_string_gently()`. The client now `die()`s if the server sends an unrecognized type string, aligning with Git’s defensive programming practices. In `builtin/cat-file.c`, the caller is updated to populate the `typep` field from the results and append "objecttype" to the allowed-atoms list when the server provides type data. The patch also updates `free_fetch_object_info_results()` to free the new `types` array and adds the necessary `#include "object.h"` for `enum object_type`.

The patch touches three files (`builtin/cat-file.c`, `fetch-object-info.c`, `fetch-object-info.h`) and introduces no behavior changes—it only extends the client-side parsing logic to handle type data once the server advertises support. The changes are uncontroversial and mirror the existing `wants_size`/`sizes` pattern, making the extension straightforward and low-risk. All tests are passing, and the series is now poised for integration.
