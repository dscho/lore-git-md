This thread is about a small but useful usability patch from Yoichi NAKAYAMA that improves the error message when `git worktree add` encounters an ambiguous remote branch name (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). Instead of a terse warning, the patch adds a detailed advice message explaining the ambiguity and offering two workarounds: specifying the fully qualified branch name (e.g., `origin/foo`) or setting `checkout.defaultRemote` in Git config. The advice is controlled by the new `advice.checkoutAmbiguousRemoteBranchName` setting, which is enabled by default.

Junio C Hamano reviewed the patch and found it generally sound but raised two substantive points about the advice message’s clarity and context. First, he noted that the same advice is shown in two different scenarios—when `worktree.guessremote` is set and when it isn’t—and suggested tailoring the message to each case, as the user’s intent (and thus the most helpful suggestion) may differ. Second, he critiqued the example command in the advice, arguing it could mislead users into treating `origin/` as a fixed literal rather than a placeholder for the actual remote name. He also flagged a minor style nit and asked for a clearer commit message explanation of the second scenario’s handling. The patch touches `builtin/worktree.c` and updates the test suite in `t/t2400-worktree-add.sh`.

The series is still under review, with no other participants having weighed in yet. While the patch is uncontroversial and self-contained, Junio’s feedback suggests a v2 may be needed to refine the advice message’s precision and context-awareness. The change remains a straightforward usability improvement with no functional impact on the DWIM logic itself.
