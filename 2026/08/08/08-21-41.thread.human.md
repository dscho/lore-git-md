This thread is about a usability patch for `git worktree add` that improves error messages when an ambiguous remote branch name is provided (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). The patch, authored by Yoichi NAKAYAMA, replaces the terse "matched multiple remote tracking branches" warning with a detailed advice message, gated behind `advice.checkoutAmbiguousRemoteBranchName` (enabled by default). The advice now suggests a command (`git branch -r --list '*/<name>'`) to dynamically list conflicting remotes, rather than showing a static list, to avoid overwhelming users and align with script-friendly workflows.

The patch also refines error handling by moving an existing `die()` call earlier in the code path, replacing a generic "invalid reference" message with a more specific diagnostic that explains the ambiguity. This change has been a point of discussion: D. Ben Knoble raised concerns about the unannounced behavior change, which Yoichi clarified as a usability improvement. Junio C Hamano’s latest feedback focuses on the commit message, requesting a clearer justification for the error-handling refinement by tracing the problematic flow (silent failure to resolve ambiguity -> `NULL` remote -> misleading error). The patch touches `builtin/worktree.c` and updates tests in `t/t2400-worktree-add.sh`.

The main open question is whether the command-based advice is more effective than a static list of remotes for user discovery. Junio initially preferred a static list for immediate usability, while the current approach favors flexibility. The patch is otherwise technically sound and ready for further review once the commit message addresses Junio’s request.
