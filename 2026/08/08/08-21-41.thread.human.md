This thread is about improving the error message when `git worktree add` encounters an ambiguous remote branch name (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). The original patch by Yoichi NAKAYAMA replaces the terse warning with a detailed advice message offering two workarounds: specifying the fully qualified branch name or setting `checkout.defaultRemote`. The advice is controlled by a new config key, `advice.checkoutAmbiguousRemoteBranchName`, enabled by default.

Junio C Hamano reviewed the patch and provided substantive feedback, focusing on the advice message's clarity and usefulness. Initially, he suggested tailoring the message to distinct scenarios (e.g., whether `worktree.guessremote` is set) and improving the phrasing of the example command. In the latest email, Junio refines his critique further: the current advice assumes the user's problem is *syntax* (not knowing how to specify a fully qualified branch name), but the real issue might be *discovery* (not remembering which remotes have the branch). He proposes listing the conflicting remotes (e.g., "the branch exists on `origin`, `upstream`, and `home`") to make the advice more actionable. This is a usability-focused refinement, not a rejection of the patch's direction.

The patch touches `builtin/worktree.c` and updates tests in `t/t2400-worktree-add.sh`. No functional changes to the DWIM logic are made; the improvement is purely about the advice message. The thread remains under review, and a v2 incorporating Junio's feedback is likely. Key open questions include how to split the advice message for different scenarios and how to phrase the example command to avoid implying `origin/` is a literal placeholder. The discussion is still centered on user experience, with no major technical objections raised.
