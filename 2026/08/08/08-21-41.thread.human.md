This thread improves the error message when `git worktree add` encounters an ambiguous remote branch name (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). The latest version of the patch, now at v4, adds a detailed advice message—gated behind the new `advice.checkoutAmbiguousRemoteBranchName` config (enabled by default)—that helps users resolve the ambiguity by suggesting a command (`git branch -r --list '*/<name>'`) to list conflicting remotes. The patch also refines error handling by moving an existing `die()` call earlier in the code path, replacing a generic "invalid reference" message with a clearer diagnostic that explains the ambiguity. This is purely a usability improvement, as the command already failed in these cases—just with less clarity.

The series has addressed all substantive feedback. Junio C Hamano’s concerns about the commit message’s clarity and the advice message’s usability have been resolved, though he still prefers a static list of conflicting remotes (e.g., "the branch exists on `origin`, `upstream`") over the command-based approach. Ben Knoble initially raised a critical workflow concern about the unannounced `die()` behavior, but this was mitigated by preserving `dwim_branch()`’s return behavior, and he now explicitly endorses signaling ambiguity when no deterministic resolution exists. The latest discussion shifts the design toward a quieter approach: Yoichi Nakayama proposes omitting warnings or advice in the `--guess-remote` case, as the command is designed to succeed even if the guess fails, avoiding noise when ambiguity doesn’t block the operation.

The patch touches `builtin/worktree.c` and updates tests in `t/t2400-worktree-add.sh`. It remains under review, with no technical objections left. The only unresolved question is whether the quieter approach for `--guess-remote` will be accepted, but this is a usability trade-off, not a blocker. The series is now functionally complete and awaiting maintainer pickup.
