This thread is about a patch from Yoichi NAKAYAMA that improves the error message when `git worktree add` encounters an ambiguous remote branch name (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). The current warning is terse, and the patch replaces it with a more detailed advice message, enabled by default via `advice.checkoutAmbiguousRemoteBranchName`.

The key debate centers on what the advice should actually say. Yoichi’s initial proposal focused on workarounds (like using fully qualified branch names or `checkout.defaultRemote`), but Junio C Hamano argued the message should first *identify* the conflicting remotes (e.g., "the branch exists on `origin`, `upstream`, and `home`") to address the more common user problem of *discovery* rather than syntax. The patch touches `builtin/worktree.c` and updates tests in `t/t2400-worktree-add.sh`, but the advice content remains contested. Junio’s feedback is substantive, focusing on usability and actionability, while Harald Nordgren’s recent reply is a surface-level endorsement of the idea without engaging with the technical discussion.

The thread is still under review, with open questions about whether to split the advice into scenario-specific variants, how to format the list of conflicting remotes, and whether the commit message adequately explains the shift toward discovery-focused advice.
