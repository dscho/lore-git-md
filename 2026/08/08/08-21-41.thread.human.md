This thread is about a patch series by Yoichi NAKAYAMA that improves the error message when `git worktree add` encounters an ambiguous remote branch name (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). The series has gone through four iterations, refining both the user-facing advice and the underlying error handling.

The patch replaces the terse "matched multiple remote tracking branches" warning with a detailed advice message, gated behind `advice.checkoutAmbiguousRemoteBranchName` (enabled by default). The advice uses a command (`git branch -r --list '*/<name>'`) to dynamically list conflicting remotes, rather than a static list, to avoid overwhelming users and support script-friendly workflows. The patch also moves an existing `die()` call earlier in the code path to provide a clearer diagnostic, replacing a generic "invalid reference" error with one that explains the ambiguity. This change was initially controversial but has been adjusted to avoid disrupting `dwim_branch()`'s return behavior, addressing workflow concerns raised by D. Ben Knoble.

Junio C Hamano, the maintainer, has reviewed the series and accepted the command-based advice approach, though he still prefers a static list of remotes for immediate usability. His feedback on the commit message’s clarity and placeholder names has been fully addressed in the latest version (v4). The only remaining open questions are minor: whether the command-based advice is more effective than a static list, whether *any* warning should be emitted for multiple matches, and a few surface-level code nits (unnecessary newline, braces). These are not blockers for merging.

The series is now functionally complete and touches `builtin/worktree.c` and `t/t2400-worktree-add.sh`. It includes updated tests and a new test for `--guess-remote` with ambiguous branches. The patch is ready for maintainer pickup, with no substantive objections remaining.
