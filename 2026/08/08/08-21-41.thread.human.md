This thread is about improving the error message when `git worktree add` encounters an ambiguous remote branch name (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). The series, now in its fourth iteration by Yoichi NAKAYAMA, replaces the terse "matched multiple remote tracking branches" warning with a detailed advice message that helps users resolve the ambiguity. The advice is configurable via `advice.checkoutAmbiguousRemoteBranchName` (enabled by default) and focuses on script-friendly discovery by providing a command (`git branch -r --list '*/<name>'`) to list conflicting remotes dynamically.

The latest discussion centers on Junio C Hamano’s proposal to extend `unique_tracking_name()` to optionally return the list of conflicting remotes, enabling a static list in the advice message (e.g., "the branch exists on `origin`, `upstream`"). This approach prioritizes immediate usability by eliminating the need for users to run an additional command, while Yoichi’s current implementation favors flexibility and avoids overwhelming users with a potentially long list. The trade-off between these two approaches remains unresolved, though Junio’s patch demonstrates a backward-compatible way to implement his preference without disrupting existing workflows. Minor code nits (indentation, unnecessary braces) and the question of whether to emit warnings in the `--guess-remote` case (where ambiguity doesn’t block the operation) are still open but not blockers.

Key participants include Yoichi (author), Junio (maintainer), and D. Ben Knoble (reviewer). Yoichi has addressed all substantive feedback, including moving a `die()` call earlier in the code path to improve diagnostics without altering `dwim_branch()`’s return behavior. Ben Knoble initially raised concerns about workflow disruption but now endorses signaling ambiguity—via warning or advice—only when necessary, supporting Yoichi’s proposal to omit it in the `--guess-remote` case. Junio’s feedback has shifted from technical correctness to user-experience refinements, such as the static list vs. command-based advice debate. The series is functionally complete and under review, with no major objections remaining.
