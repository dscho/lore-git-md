This thread is about improving the error message when `git worktree add` encounters an ambiguous remote branch name (e.g., `foo` when both `origin/foo` and `upstream/foo` exist). The patch, authored by Yoichi Nakayama, replaces the terse warning with a detailed advice message that helps users resolve the ambiguity. The advice is configurable via `advice.checkoutAmbiguousRemoteBranchName` (enabled by default) and focuses on providing a command (`git branch -r --list '*/<name>'`) to dynamically list conflicting remotes, rather than a static list.

The patch is under review, with key feedback focusing on three areas: the advice format (command vs. static list), an unannounced behavior change (moving an existing `die()` call earlier in the code path), and minor code style nits. Yoichi has clarified that the `die()` change is not a regression—it replaces a generic error message with a more specific one, and the command was already failing at a later point. D. Ben Knoble raised the behavior change as a concern, but Yoichi’s explanation suggests it’s a usability improvement rather than a breaking change. Junio C Hamano initially suggested a static list of remotes for better discoverability, but the current proposal favors a command-based approach for script-friendly flexibility. The patch touches `builtin/worktree.c` and updates tests in `t/t2400-worktree-add.sh`.

What’s still open: whether the command-based advice is the best approach, whether the commit message adequately explains the error-handling change, and whether Junio’s minor style nits will be addressed. The patch is otherwise ready for further review, with no major technical objections remaining.
