This thread is a follow-up to the recently merged patch series that improved error messages for ambiguous remote branch names in `git worktree add`, `git checkout`, and `git switch`. The series, originally authored by Yoichi Nakayama, was a usability improvement that replaced terse warnings with detailed, actionable advice when a branch name like `foo` matches multiple remotes (e.g., `origin/foo` and `upstream/foo`).

The new discussion picks up a latent bug in `git worktree add`'s one-argument form (e.g., `git worktree add ../topic-branch`). Currently, when the branch name matches multiple remote tracking branches, the command silently creates a local branch from HEAD, treating it the same as if no match existed. Junio C Hamano identified this as a bug, tracing it to an incomplete refactoring in 2018 that improved `git checkout` but left `git worktree add` unable to distinguish between zero and multiple matches. While the original series intentionally left this edge case untouched—since the command succeeds in this scenario—Junio now argues it should error out when ambiguity exists. Yoichi Nakayama agrees with the analysis and plans to implement the fix in a follow-up commit. The discussion is framed as a `#leftoverbits` item, documenting a known issue for future resolution rather than blocking the current work. No controversy or open questions remain, and the tone is collaborative. The fix will target the `unique_tracking_name()` function in `builtin/worktree.c`, addressing the historical oversight.
