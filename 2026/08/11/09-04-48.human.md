This is a bugfix patch targeting the geometric repacking strategy in Git's auto-maintenance.

The patch addresses an issue where Git's auto-maintenance with geometric repacking triggers too frequently—specifically when loose objects exceed a default threshold of just 100 objects. This low threshold causes excessive repacking, especially in repositories with concurrent writers, leading to race conditions where loose object directories are pruned while other processes are trying to write to them. The problem is exacerbated by the current implementation's approximation of object counts, which only checks a single shard directory (e.g., `objects/17/`), meaning even a handful of objects can trigger a repack.

Patrick Steinhardt proposes aligning the default threshold with `git gc`'s more conservative value of 6,700 loose objects. The change is minimal: a one-line update in `Documentation/config/maintenance.adoc` and another in `odb/source-files.c`. The patch includes a `Reported-by` trailer crediting Stefan Haller, who identified the issue in a real-world scenario with concurrent writers.

This looks like a well-motivated fix for a practical problem, with clear reasoning and a straightforward solution. The patch is part of the ongoing work to improve Git's repack machinery, an area Patrick has been actively refactoring. If you work with large or busy repositories, this change may reduce unnecessary maintenance overhead.
