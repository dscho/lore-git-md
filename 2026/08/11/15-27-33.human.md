This is a **performance feature** for Linux, adding reflink support to Git’s file copying and local clone operations. Junio’s reply raises a fundamental question about the patch’s design.

The patch proposes a fallback order of reflink → hardlink → byte copy, but Junio points out that object files are immutable—once written, they are never modified. Since reflinks only provide a benefit over hardlinks when the file might later be modified (triggering copy-on-write), and Git never modifies object files, he questions why reflinks should be preferred over hardlinks at all. Hardlinks are simpler, more widely supported, and avoid the overhead of the `FICLONE` ioctl, so for Git’s use case they may be the better choice.

The patch is otherwise well-crafted: it’s Linux-specific, thoroughly tested (including a fake-reflink helper for test coverage on non-reflink filesystems), preserves timestamps for `prune`/`gc` compatibility, and falls back gracefully. But Junio’s observation suggests the current ordering might be backwards—hardlinks could be the primary choice, with reflinks as an optional optimization for users who specifically want them. The author will need to clarify the rationale for the proposed order before the patch can move forward.
