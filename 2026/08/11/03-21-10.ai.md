This is the second patch in a two-part series fixing Bash completion for `git checkout -C <dir>`. It implements the actual behavior change: when completing paths for `git checkout` (including with `-C`), the completion now suggests only tracked paths (those in the index) rather than falling back to untracked files in `$PWD`. This aligns with the command’s purpose—operating on files already in the repository—and fixes a usability issue when using `-C` to specify a different working directory.

The patch modifies `_git_checkout()` in `contrib/completion/git-completion.bash` to call `__git_complete_index_file()` when revision reference completion yields no matches (or when `--` is present). This ensures tracked paths are offered as candidates, even when the working directory doesn’t match the repository root. The change is minimal and follows the refactoring in patch 1/2, which prepared the logic for this adjustment.

Test coverage is added in `t/t9902-completion.sh` to verify the fix. Two new tests confirm that:
1. `git checkout f` (no refs matching "f") completes only tracked paths (`file1`, `file2`), ignoring untracked files.
2. `git -C <path> checkout o` completes tracked paths in the specified repository, not the current directory.

The series follows a similar fix for `git diff` (mentioned in the cover letter), suggesting a pattern of addressing completion edge cases for commands with the `-C` option. The implementation is straightforward and uncontroversial, addressing a clear usability gap without broader implications. The patch is well-motivated, with clear test coverage and a clean diff. It’s ready for review and likely to be merged as-is.
