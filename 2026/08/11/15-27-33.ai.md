This is a **substantive review** from Junio C Hamano on the reflink patch series. The review raises a fundamental question about the patch's design: why attempt reflinks *before* hardlinks, given that object files are immutable and hardlinks are universally supported on local filesystems?

Junio's concern is technical and architectural. He notes that object files in Git are never modified after creation, so the copy-on-write mechanism of reflinks (which triggers only on modification) offers no practical benefit over hardlinks in this context. Hardlinks are simpler, more widely supported, and equally space-efficient for immutable files. The current fallback order (reflink → hardlink → byte copy) thus appears to prioritize a more complex mechanism over a simpler one without clear justification.

The review does not reject the patch outright but asks for elaboration on the rationale behind the chosen order. This is a classic Junio move: probing the design assumptions before accepting a performance optimization. The answer could clarify whether the order is arbitrary, motivated by future-proofing (e.g., reflinks might enable features hardlinks cannot), or based on observed behavior in specific environments (e.g., reflinks might perform better in some edge cases despite immutability).
