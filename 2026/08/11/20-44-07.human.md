This is a security feature patch introducing `http.sslVerifyStatus`, a new configuration option that enables Git to validate stapled OCSP responses during HTTPS connections. The patch addresses a gap in Git’s certificate verification: while Git already checks peer certificates and hostnames, it does not request or validate OCSP staples (revocation status information sent by the server), leaving it vulnerable to accepting revoked certificates. The behavior is backend-dependent—OpenSSL ignores staples unless explicitly enabled, while GnuTLS checks them by default—but this patch ensures consistent behavior by exposing libcurl’s `CURLOPT_SSL_VERIFYSTATUS` capability.

The patch adds a boolean `http.sslVerifyStatus` option (defaulting to `false`) that, when enabled, causes connections to fail if the server does not provide a staple. This fail-closed design aligns with security best practices, though the default remains `false` to avoid breaking remotes that don’t support stapling. The implementation includes per-URL configuration (e.g., `http.https://example.com/.sslVerifyStatus`) and fails loudly if the TLS backend lacks staple-checking support. The new test file `t/t5567-http-verify-status.sh` verifies the fail-closed behavior by confirming that enabling the option turns a working fetch into a failing one when the test server (which doesn’t staple) is used.

This is the second version of the patch, addressing Junio C Hamano’s feedback by removing an in-code comment explaining the default and backend differences. The rationale is now fully documented in the commit message, which is thorough and well-structured. The patch is uncontroversial and appears well-crafted, with clear motivation, careful handling of edge cases, and robust testing. The only open question is whether the default should eventually change to `true` or if users should be warned when staples are ignored, but that discussion can happen later.

The patch touches `http.c` and `Documentation/config/http.adoc`, with no symbol renames or behavioral changes when the option is disabled. It requires libcurl ≥ 7.41.0, which is already below Git’s minimum version, so no version guard is needed. This is a targeted, low-risk security improvement that fills a meaningful gap in Git’s HTTPS verification.
