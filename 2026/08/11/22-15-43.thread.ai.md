Thread identity
Subject: git-remote-https fails to retry with BASIC auth when proxy URL contains credentials
Series version: standalone bug report (no patch series)
Originating author: Tom Noonan II
Thread type: bug report

Core problem or goal
Git’s HTTP transport layer does not automatically extract and use the username:password pair from a proxy URL (e.g., `http://user:pass@proxy:port`) when the proxy responds with a 407 (Proxy Authentication Required) challenge. Instead, the connection aborts after the 407 response, even though the credentials are available in the environment variable (`HTTP_PROXY` or `HTTPS_PROXY`). The workaround—setting `GIT_HTTP_PROXY_AUTHMETHOD=basic`—forces Git to send credentials preemptively, which succeeds, but this is not the expected behavior for standard proxy URL formats.

Current status
Under review; no prior discussion or patch versions. The report presents evidence (detailed `GIT_CURL_VERBOSE` logs) that the current behavior is unintentional: the proxy URL format is standard, and other tools (e.g., `curl`) handle it transparently.

Key technical details
- **Subsystem**: HTTP transport layer (`remote-curl.c`, libcurl integration)
- **Environment variables**: `HTTP_PROXY`/`HTTPS_PROXY` (credentials in URL), `GIT_HTTP_PROXY_AUTHMETHOD`
- **HTTP exchange**: Initial CONNECT request omits credentials; proxy responds with 407 and `Proxy-Authenticate: Basic`; Git aborts instead of retrying with the credentials it already has.
- **Workaround**: Setting `GIT_HTTP_PROXY_AUTHMETHOD=basic` forces preemptive credential submission.
- **Expected behavior**: Automatic extraction and retry with BASIC auth when the proxy URL contains credentials.

Open questions and loose ends
- Is the current behavior intentional, or is this a bug? (The evidence strongly suggests the latter.)
- If a bug, should the fix be to:
  - Automatically extract credentials from the proxy URL and retry on 407?
  - Document the current behavior as a limitation?
  - Both?
