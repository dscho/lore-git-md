This is a usability-focused bugfix for `git worktree add`, now in its fourth iteration. The patch improves error messaging when a user attempts to create a worktree from an ambiguous remote branch name (e.g., `git worktree add ../foo-dir bar-topic` when both `origin/bar-topic` and `upstream/bar-topic` exist). Instead of failing with a generic "invalid reference" error, Git now dies early with a clear diagnostic and actionable advice, gated behind the new `advice.checkoutAmbiguousRemoteBranchName` config (enabled by default).

The implementation touches `builtin/worktree.c` and updates the test suite (`t/t2400-worktree-add.sh`). Key changes: the `unique_tracking_name()` call now captures the number of matching remotes, and if multiple matches are found, Git emits a detailed advice message suggesting either a fully qualified branch name (`origin/bar-topic`) or setting `checkout.defaultRemote`. The advice message uses a command-based approach (`git branch -r --list '*/<name>'`) to list conflicting remotes, aligning with script-friendly workflows. The patch also moves an existing `die()` call earlier in the code path to replace a misleading "invalid reference" error with a more specific diagnostic, without altering `dwim_branch()`'s return behavior.

Junio’s feedback on the commit message (placeholder names, explanation of the problematic code path) and the advice message’s usability (static list vs. command-based discovery) has been fully addressed in v4. The only remaining open question is whether the command-based advice is more effective than a static list of remotes, but this is not a blocker. Minor code nits (unnecessary newline, braces) remain unaddressed but are secondary. The patch is well-motivated, includes test coverage, and avoids workflow disruption, making it a straightforward usability win.
