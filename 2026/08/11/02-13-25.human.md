This is a bug report about a Windows-specific usability pitfall in Git’s textconv filter system. The author, Skybuck Flying, has refined their earlier report to focus more sharply on the root cause: a misconfigured textconv filter (`sed -e s/\r//`) that silently corrupts `git diff` output by stripping all 'r' characters instead of carriage returns (CR). The issue stems from Windows shell argument parsing, which mishandles the `\r` escape sequence in the `sed` command, turning it into `s/r//`.

The problem is well-documented with clear reproduction steps. The author demonstrates that the repository content itself is unaffected—only the diff output is corrupted—and provides a minimal example outside Git to confirm the behavior of the bundled `sed` executable. The impact is significant: users see misleading diffs with no warnings, making the issue difficult to diagnose. The suggested fixes are practical: document the Windows-specific risk of backslash escapes in textconv filters, add a warning for suspicious patterns like `\r`, or provide a built-in Git filter for CR stripping.

This is a real usability issue for Windows users, particularly those relying on AI-generated configurations. The report is actionable and avoids tangents about line-ending conventions or PATH limitations, making it a strong candidate for attention from maintainers focused on Windows compatibility or textconv safety. No responses from the Git project have been recorded yet, so the thread remains open for discussion.
