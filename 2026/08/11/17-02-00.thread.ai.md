Subject: [PATCH v2] http: add http.sslVerifyStatus to check OCSP staples
Series version: standalone patch (v3 pending)
Originating author: graysongordon-gl
Thread type: security feature patch

Core problem or goal
Git’s HTTPS certificate verification omits OCSP staple validation, leaving it vulnerable to accepting revoked certificates. The patch adds a boolean `http.sslVerifyStatus` option (default `false`) that enables staple validation via libcurl’s `CURLOPT_SSL_VERIFYSTATUS`, causing connections to fail if the server does not provide a staple. The design is fail-closed for security but defaults to `false` to avoid breaking remotes that do not support stapling.

Current status
Under review. This is the second version of the patch; a third version is expected to resolve Junio C Hamano’s procedural feedback (test script numbering conflict). The substantive discussion remains centered on Patrick Steinhardt’s challenge to the feature’s practical value and motivation, which the author has yet to address.

Key technical details
- New config key: `http.sslVerifyStatus` (boolean, default `false`)
- Per-URL override: `http.https://example.com/.sslVerifyStatus`
- Libcurl requirement: `CURLOPT_SSL_VERIFYSTATUS` (libcurl ≥ 7.41.0, already below Git’s minimum)
- Files touched: `http.c`, `Documentation/config/http.adoc`
- New test file: `t/t5567-http-verify-status.sh` (numbering conflict; will be renamed in v3)
- Behavior: fail-closed (connection fails if staple missing)
- Backend differences: OpenSSL ignores staples unless explicitly enabled; GnuTLS checks them by default
- Symbols: none renamed; new config key only

Open questions and loose ends
- Whether the default (`false`) should eventually change to `true` or if users should be warned when staples are ignored.
- Whether the feature’s limited practical impact (disabled by default, no backend unification, OCSP stapling’s declining relevance) justifies its inclusion. The author must provide a concrete use case or audience to address Patrick Steinhardt’s concerns.
