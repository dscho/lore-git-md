This is a review of a feature patch proposing a new `http.sslVerifyHost` configuration option.

Patrick Steinhardt responds to Ron Nazarov’s patch that would let users disable hostname verification in TLS connections while still validating the certificate chain. The patch is motivated by decentralized setups where self-signed certificates lack a matching Common Name (CN), making strict hostname checks fail.

Patrick’s review is substantive: he questions the security model, pointing out that accepting arbitrary certificates for a given endpoint still leaves the connection vulnerable to man-in-the-middle attacks. He argues that the new option oversells its security benefit compared to simply disabling TLS verification entirely, and suggests that both the commit message and documentation should explicitly warn users about the remaining insecurity.

The tone is measured but skeptical; Patrick does not outright reject the idea, but he clearly wants the trade-offs spelled out more honestly. No code-level feedback is given—this is purely a conceptual review of the security implications.
