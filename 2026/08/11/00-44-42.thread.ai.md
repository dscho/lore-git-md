Core problem or goal
A Windows user reports silent corruption in `git diff` output caused by Git’s textconv pipeline on Windows. The issue is not limited to a specific filter (e.g., `sed -e s/\r//`) but is a general flaw in how Git processes filter output on Windows, leading to silent character removal (e.g., "compareCache" → "compaeCache") in diff output while leaving repository content intact. The goal is to diagnose and fix the root cause, add diagnostics to prevent similar issues, and improve Windows usability for textconv filters.

Key technical details
- **Subsystem**: textconv filters, Windows compatibility (Git’s internal textconv execution path).
- **Trigger**: Any textconv filter on Windows, not limited to the earlier `sed` example. The issue is reproducible with simple filters (e.g., `cat` or `tr`).
- **Symptoms**: Silent corruption of identifiers (e.g., "compareCache" → "compaeCache") in `git diff` output; repository content remains uncorrupted. No warnings or errors are emitted. The corruption cannot be reproduced by running the filter manually outside Git.
- **Root cause**: Git’s internal handling of filter output on Windows, which mishandles certain characters (e.g., 'r') in the output stream. The issue is not specific to `sed` or MSYS argument parsing, as previously suspected.
- **Reproduction**: The author provides a concise test case demonstrating the issue with `git diff` and textconv filters on Windows. The corruption does not occur when the filter is run manually outside Git.
- **Workaround**: Remove the textconv filter or use `git diff --no-textconv`.
- **Suggested fixes**:
  - Add a `--debug-textconv` flag to log executed commands and filter output for troubleshooting.
  - Implement size-mismatch warnings to alert users when filter output is shorter than input (indicating potential corruption).
  - Provide Windows-safe documentation examples for textconv filters (e.g., `tr -d \r` or `dos2unix`).
  - Consider a built-in Git filter for CR stripping (e.g., `git diff --strip-cr`).
