Core problem or goal
A Windows user reported two related usability issues causing silent corruption in Git workflows:
1. **Textconv filter misconfiguration**: Unquoted backslashes in textconv filter commands (e.g., `sed -e s/\r//`) are misparsed by the shell, stripping all 'r' characters instead of carriage returns, corrupting `git diff` output without warnings. This was confirmed as a shell argument-parsing issue (not a Git flaw) and dismissed as a documentation gap or "Windows problem" by maintainers.
2. **Binary file corruption**: Overly broad global `.gitattributes` rules (e.g., `* text diff=lfclean`) force text filters onto binary files (PNGs, JPEGs), corrupting them during checkout. The root cause is now clarified: the `text` attribute (not the `diff` filter) triggers Git’s line-ending normalization (LF → CRLF), corrupting binaries. The issue is framed as a **systemic design risk** in Git’s attribute system, with calls for safeguards (warnings, automatic binary detection) or even the removal of global filters. The goal is to prevent silent corruption through improved diagnostics, documentation, or built-in protections, while clarifying whether Git should mitigate user misconfigurations or defer to user education.

Current status
Under review. The root causes are identified, but maintainer consensus is lacking:
- **Textconv issue**: Closed as a shell misconfiguration; no further action planned beyond potential documentation updates (Windows-safe examples in `gitattributes(5)`).
- **Binary corruption issue**: Active and unresolved. The author and Randall S. Becker (NonStop port maintainer) have highlighted the risks of global `.gitattributes` rules, demonstrating reproducible corruption of binaries (PNGs, JPEGs) during checkout. D. Ben Knoble’s recent email clarifies the mechanism: the `text` attribute (not `diff=lfclean`) is responsible for line-ending normalization, which corrupts binaries. Proposed mitigations include:
  - **Configuration**: Safer defaults for Windows (`core.autocrlf=input`, `core.ignorecase=true`, `core.filemode=false`), explicit binary declarations (e.g., `*.png binary`), and replacing `* text` with `* text=auto` (which uses Git’s heuristic to avoid misclassifying binaries).
  - **Documentation**: Add warnings about global `*` rules in `gitattributes(5)`, emphasize local `.gitattributes` usage, and provide Windows-safe filter examples (e.g., `tr -d \r`, `dos2unix`).
  - **Diagnostics**: Warnings for global `*` rules with `text` or textconv filters, or for files with binary extensions (e.g., `*.png`) subjected to text filters. Size-mismatch warnings during checkout.
  - **Safeguards**: Automatic binary file detection (e.g., ignore `text` for known binary extensions), built-in CR-stripping filters (e.g., `git diff --strip-cr`), or enforcing safer defaults (e.g., `text=auto`).
  - **Design changes**: The author advocates for removing global `.gitattributes` filters entirely, though this is unlikely to gain traction. Becker and Knoble imply the attribute system’s design is inherently risky but focus on incremental improvements.

Key technical details
- **Subsystems**: textconv filters, shell argument parsing, `.gitattributes` handling (precedence rules, global vs. local files, `text` vs. `text=auto`), checkout process, line-ending normalization (`core.autocrlf`), binary file detection (Git’s heuristic checks only the first "hunk").
- **Triggers**:
  - Textconv: Unquoted backslashes in filter commands (e.g., `sed -e s/\r//` → `s/r//`).
  - Binary corruption: Global `.gitattributes` rules like `* text diff=lfclean` (specifically the `text` attribute) applied to all files, including binaries. The `diff` filter itself does not corrupt binaries during checkout.
- **Symptoms**:
  - Textconv: Silent corruption of identifiers (e.g., "compareCache" → "compaeCache") in `git diff` output; repository content uncorrupted.
  - Binary corruption: Corrupted binary files (PNGs, JPEGs) during checkout due to LF → CRLF conversion; repository blobs intact. DLL files were unaffected due to lack of CR bytes, masking the issue’s scope.
- **Root causes**:
  - Textconv: Shell interprets unescaped backslashes; reproducible on Linux with identical syntax.
  - Binary corruption: `.gitattributes` precedence rules apply the `text` attribute to all files, triggering line-ending normalization. Git’s binary detection heuristic is unreliable for files with CR bytes early in their content.
- **Workarounds**:
  - Textconv: Quote backslashes (e.g., `sed -e "s/\\r//"`) or use `git diff --no-textconv`.
  - Binary corruption: Delete global `.gitattributes` and use local rules (e.g., `*.txt text`), mark binaries (e.g., `*.png binary`), or replace `* text` with `* text=auto`. Use `%f` in textconv commands on Windows to avoid text-mode file handling.
- **Suggested fixes**:
  - **Documentation**: Add Windows-safe examples (e.g., `tr -d \r`, `dos2unix`) and warnings about global `*` rules in `gitattributes(5)`.
  - **Diagnostics**: Warnings for global `*` rules with `text` or textconv filters, or for files with binary extensions subjected to text filters.
  - **Safeguards**: Size-mismatch warnings, built-in CR-stripping filters (e.g., `git diff --strip-cr`), automatic binary file detection (e.g., ignore `text` for known binary extensions like `*.png`), or enforce `text=auto` as the default for global rules. Safer defaults for Windows (`core.autocrlf=input`).
