Thread identity: Patch series (1/1) fixing an overly aggressive geometric repacking threshold in Git's auto-maintenance. Originating author: Patrick Steinhardt.

Core problem or goal: The geometric repacking strategy in Git's auto-maintenance triggers repacks of loose objects too frequently (default threshold: 100 loose objects) compared to `git gc`'s default (6700). This causes instability in high-concurrency repositories due to race conditions between repacking and loose object directory pruning. The thread has also surfaced a deeper architectural question: whether Git should stop pruning loose object sharding directories entirely to mitigate these race conditions at their source.

Current status: **Ready for integration.** Patch v1 remains unchanged and uncontroversial. The author and substantive reviewers (Justin Tobler, Elijah Newren) have confirmed the patch is correct as-is. The patch has not yet appeared in "What's cooking" and may have been overlooked by Junio. The follow-up discussion explores a potential future direction (not pruning loose object directories) but does not affect the current patch's status or design.

Key technical details:
- Files touched: `Documentation/config/maintenance.adoc`, `odb/source-files.c`.
- Symbols/config keys: `maintenance.geometric-repack.auto` (default value changed from 100 to 6700).
- Behavior change: Reduces frequency of geometric repacks for loose objects to match `git gc`'s threshold. The heuristic counts loose objects in only one fan-out directory and multiplies by 256, making it a rough estimate rather than a precise measurement. The author explicitly notes that the core issue is the overly aggressive default (100), not the estimation method. Historical context reveals the 6700 threshold was chosen to avoid triggering on a fully unpacked Git v0.99 repository while still activating for v1.0, and to prevent redundant repacks during incremental updates. Elijah Newren's review adds that the heuristic's `DIV_ROUND_UP` behavior means *2* loose objects in a fan-out directory are required to trigger a repack, further emphasizing the patch's motivation.
- Follow-up discussion: Patrick Steinhardt and Elijah Newren explore the trade-offs of not pruning loose object sharding directories. Pruning empty shards slightly speeds up lookups for nonexistent objects and reduces filesystem clutter, but forces frequent directory recreation during loose object writes, exacerbating race conditions. Patrick leans toward not pruning, arguing the performance cost is negligible (since Git prioritizes packfile searches) while the write churn is problematic. No decision or patch has been proposed for this tangential question.
- No on-disk format changes; purely a configuration default adjustment.
- Test coverage: Not explicitly mentioned, but the patch is motivated by user-reported instability in real-world high-concurrency scenarios.

Open questions and loose ends:

This is speculative and not tied to any immediate action or patch.
