This thread is about a proposed Git configuration option, `http.sslVerifyHost`, which would allow users to disable TLS hostname verification while retaining certificate verification via `http.sslCAInfo`. The goal is to provide a middle ground for users in decentralized environments (e.g., self-signed certificates without valid Common Names) who want to pin a specific CA certificate without disabling TLS verification entirely. Ron Nazarov introduced the patch as an RFC, but it has faced strong skepticism from reviewers.

Patrick Steinhardt initially raised concerns about the security trade-offs, arguing that the option oversells its benefits and fails to adequately warn users about its limitations, particularly its vulnerability to active man-in-the-middle (MITM) attacks. Brian M. Carlson has now joined the discussion, reinforcing and expanding on these concerns. Carlson argues that the option provides no meaningful security, as unsecured networks (like Wi-Fi) are vulnerable to active MITM attacks via ARP spoofing, undermining the proposed use case. He also points out that modern alternatives like ACME (Let’s Encrypt) and DANE make it easy to deploy properly configured TLS certificates, rendering the need for self-signed certificates with invalid Common Names obsolete. Carlson concludes that Git should reject the option outright, as it is unnecessary, misleading, and prone to misuse.

The thread has shifted from a discussion about *how* to implement the option to whether it should exist at all. No other participants have weighed in yet, and the author has not responded to the critiques. The key open questions now revolve around whether there are legitimate use cases where ACME/DANE are genuinely unavailable, and whether the security risks can be mitigated or clearly communicated to users. The patch remains under initial review, with no prior versions or merge status recorded.
