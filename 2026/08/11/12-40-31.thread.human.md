This thread is about an RFC patch series from Ron Nazarov proposing `http.sslVerifyHost`, a Git configuration key that would allow users to disable TLS hostname verification while keeping certificate verification via `http.sslCAInfo`. The goal is to help users in decentralized environments (like those using self-signed certificates without valid Common Names) pin a specific CA certificate without turning off TLS verification entirely.

The discussion has shifted from *how* to implement this feature to *whether* it should exist at all. Early reviewers, including Patrick Steinhardt and brian m. carlson, were skeptical, arguing that the option oversells its security benefits and could create a false sense of security, especially since it remains vulnerable to active man-in-the-middle (MITM) attacks like ARP spoofing. brian m. carlson went further, calling the feature unnecessary given modern alternatives like ACME and DANE, and pointing out that Common Names are obsolete in TLS verification (replaced by subjectAltName).

Patrick Steinhardt has since clarified his position, acknowledging that the option *can* be used securely when combined with certificate pinning (e.g., `http.sslCAInfo` or `http.sslCAPath`). This mirrors the security model of SSH’s `known_hosts`, where users pin a specific self-signed certificate, preventing MITM attacks as long as the private key stays secret. However, Patrick emphasized that the current patch fails to document this critical requirement, leaving users to figure it out on their own. He suggested updating the documentation to make it clear that `sslVerifyHost` must be paired with certificate pinning to avoid being trivially insecure.

The thread is still in the "should this exist?" phase, but Patrick’s conditional acceptance—contingent on stronger documentation—suggests the feature might move forward if the security trade-offs are made clearer. The next likely step is a v2 patch with improved documentation, followed by further debate about whether the security model is robust enough for inclusion. The original patch text is missing from the mailing list archive, so some details (like backward compatibility) remain unknown. For now, the key open questions are whether the security model is justified, how well the risks are communicated, and whether modern alternatives make this feature redundant.
