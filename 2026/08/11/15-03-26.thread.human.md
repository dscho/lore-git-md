This thread introduces a performance optimization for Git on Linux filesystems that support copy-on-write reflinks (like Btrfs, XFS, and ZFS). Vlad Petric proposes teaching Git to attempt reflink-based copies—where files share storage until modified—before falling back to hardlinks or traditional byte-for-byte copying. The change targets both generic file operations (`copy_file()`) and local clones, using Linux’s `FICLONE` ioctl while gracefully handling failures (e.g., unsupported filesystems) by reverting to existing methods.

The implementation is Linux-specific but unobtrusive: it preserves source timestamps (critical for `prune`/`gc` decisions) and maintains backward compatibility. Testing is robust, with a new LD_PRELOAD-based helper (`test-fake-reflink.c`) to simulate reflink behavior on any filesystem and a dedicated test script (`t0094-reflink.sh`) covering edge cases like hardlink fallback and timestamp integrity. The patch touches core files (`copy.c`, `clone.c`) and documentation, adding three new functions while keeping the fallback logic clear: reflink → hardlink (unless disabled) → byte copy.

So far, the patch appears uncontroversial. It’s a targeted optimization for Linux users with no impact on other platforms, and the author reports full test suite passes on ZFS, ext4, and tmpfs. No reviews or objections have surfaced yet, but given the thorough testing and conservative fallback design, it’s likely to proceed smoothly.
