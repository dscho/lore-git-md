This thread introduces a patch by Vlad Petric to add reflink support to Git’s file copying and local cloning operations, aiming to save disk space by using copy-on-write links (via Linux’s `FICLONE` ioctl) instead of hardlinks or full copies. The patch is under review, with test coverage and fallback logic (reflink → hardlink → byte copy) already implemented.

Junio C Hamano’s review raises a key design question: why prioritize reflinks over hardlinks for immutable object files, given that hardlinks are simpler, universally supported, and equally space-efficient in this context? The current fallback order appears to favor complexity without clear benefit, and Junio asks for justification. This is the sole open question; no other technical concerns have been raised yet. The patch’s fate hinges on Vlad’s response—whether the order is arbitrary, future-proofing, or based on unarticulated performance observations. No decisions or merges have occurred; the discussion is still in the design phase.
