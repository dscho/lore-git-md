This is a follow-up discussion in the thread about the Bash completion fix for `git checkout -C <dir>`. The author (Junio C Hamano) reflects on a potential edge case: whether completion for `git checkout other-branch <path>` should also suggest paths that exist in the target branch (`other-branch`) but are not currently in the index or working tree. Currently, the series restricts completion to tracked paths (those in the index), but Junio notes that resurrecting a path from another branch (e.g., `foolish` in his example) might be useful, even if the file is untracked in the working tree.

However, Junio acknowledges this scenario is unlikely in practice and lacks the completion machinery to implement it cleanly. The script (`git-completion.bash`) doesn’t have a helper to complete paths from an arbitrary tree (e.g., via `git ls-tree`), which would be needed to support this. He clarifies that this enhancement is beyond his current expertise in the completion subsystem and invites others to build on the series if they’re interested. The tone is pragmatic, noting that the existing fix (restricting to tracked paths) is a clear improvement over the previous behavior, even if it doesn’t cover every theoretical edge case.

No changes to the patches are proposed here—this is purely a discussion of future possibilities. The series remains well-scoped and uncontroversial, but this email adds context about a potential follow-up direction. The key files and subsystems (`contrib/completion/git-completion.bash`, `t/t9902-completion.sh`) are unchanged from the original submission.
