This thread began when Skybuck Flying reported two related issues causing silent corruption in Git workflows on Windows: (1) textconv filters misconfigured with unquoted backslashes (e.g., `sed -e s/\r//`) that strip all 'r' characters instead of carriage returns, corrupting `git diff` output, and (2) overly broad global `.gitattributes` rules (e.g., `* text diff=lfclean`) that force text filters onto binary files (PNGs, JPEGs), corrupting them during checkout. The textconv issue was dismissed as a shell misconfiguration, but the binary corruption problem remains unresolved and has since been framed as a systemic design flaw in Git’s attribute system.

Randall S. Becker, maintainer of the NonStop port, has now weighed in with practical advice and shared frustration about Git’s handling of text vs. binary files. He recommends safer defaults for Windows users (`core.autocrlf=input`, `core.ignorecase=true`, and `core.filemode=false`) to reduce Git’s tendency to misapply text filters, and emphasizes that users must explicitly declare binary files (e.g., `*.png binary`) because Git’s automatic detection—limited to checking only the first "hunk" of a file—is unreliable. Becker also warns about the fragility of clean/smudge and textconv filters, which can mangle binary content or crash on NUL bytes, and suggests using `%f` in textconv commands as a workaround. His email validates Skybuck’s core concern while shifting the focus from "Git is broken" to "Git’s defaults and heuristics are unsafe for Windows," treating this as a systemic usability issue rather than a platform-specific quirk.

The thread is still under review, with no maintainer consensus on how to address the binary corruption problem. Proposed fixes include documentation updates, warnings for global `.gitattributes` rules, automatic binary detection, and size-mismatch warnings during checkout, but none have been implemented or formally endorsed. Skybuck has escalated the issue to a critique of Git’s attribute system design, advocating for the removal of global filters entirely, though this is unlikely to gain traction. Becker’s input adds weight to the argument for better safeguards, but the project has yet to decide whether to treat this as a usability issue (e.g., warnings) or defer to user education. The discussion remains actionable, with practical workarounds available but no clear path forward for built-in protections.
