This is a **design discussion contribution** in the ongoing thread about improving Git’s interactive patch selection workflow. Patrick Steinhardt responds to Junio C Hamano’s clarification of Git’s philosophical boundary—avoiding competition with external tools like lazygit—by refining his earlier proposal for a text-based user interface (TUI).

Patrick concedes that a full TUI for `git history` (e.g., for moving commits or squashing) might be too ambitious and could overlap with tools like lazygit. However, he argues that a *limited* TUI for hunk selection—specifically, improving `git add -i` and related commands—could address core workflow gaps without stepping on external tools. His suggestion is narrowly scoped: a hierarchical, navigable interface for selecting hunks (e.g., files → hunks → lines) to replace the current linear prompt-loop model. This would not introduce a full-fledged UI framework (e.g., ncurses) but would focus on usability improvements like non-linear selection and better visual feedback.

The email does not propose a concrete implementation or patches, but it signals Patrick’s willingness to compromise on scope. His position now aligns more closely with Junio’s philosophy: Git should provide *minimal* interactive features that serve as a reference implementation, not polished UIs. The key question left open is whether even this limited TUI would be deemed too competitive with external tools, given Junio’s emphasis on avoiding overlap. For now, the thread remains in the design phase, with no clear consensus on whether Git should pursue incremental UI improvements or defer such work entirely to third-party tools.
