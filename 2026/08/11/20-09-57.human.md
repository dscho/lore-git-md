This is a refactoring patch series targeting the object database (ODB) subsystem, part of Patrick Steinhardt’s ongoing ODB abstraction effort. The v2 series unifies the previously separate `odb_write_stream` and `odb_read_stream` APIs into a single `odb_stream` structure, eliminating redundancy and enabling bidirectional streaming. The changes are purely structural—no behavior changes are intended—and touch 38 files across core object handling, archive formats, and packfile operations.

The series is now complete and ready for integration. All feedback from the v1 review has been addressed, including a critical bug fix in Patch 3/8 that ensures the correct object type is propagated to `hash_object_file()` in the in-memory ODB backend, preventing potential silent corruption. Other improvements include the removal of a stale comment in `odb/transaction.h`, a new cosmetic patch (7/8) to rename `struct input_zstream_data` to `struct zlib_stream` for clarity, and explicit documentation of file descriptor ownership semantics in Patch 8/8. The series has been endorsed by Karthik Nayak as "already in a good state" and by Justin Tobler, who confirmed it resolves all his earlier concerns.

The unification introduces a direction-agnostic `odb_stream` base structure with wrapper types (`odb_stream_write` and `odb_stream_read`) for the two special cases in `builtin/unpack-objects.c` and `odb/streaming.c`. This design trade-off sacrifices some type safety (unifying `char *` and `unsigned char *` buffers) for flexibility, but reviewers have not flagged this as a blocker. Edge cases—such as loop logic in zlib decompression and wrapper allocation correctness—have been tested and reviewed without raising further issues.

The series is based on Junio’s "10th batch" for the upcoming release and is expected to graduate to `next` or `master` soon. No new tests were added, but existing coverage (including the unit test `t/unit-tests/u-odb-inmemory.c`) has been updated to match the new API. While potential performance regressions in stream-heavy code paths (e.g., `pack-objects`) remain a theoretical concern due to added indirection, no reviewer has raised this as a practical issue.

This is a well-crafted, thoroughly reviewed refactor that aligns with the broader ODB abstraction goals. It’s a strong candidate for merging and unlikely to generate further controversy.
