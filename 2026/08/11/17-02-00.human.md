This is a security-focused feature patch adding a new `http.sslVerifyStatus` configuration option to Git. The patch enables Git to check stapled OCSP responses during TLS handshakes when fetching or pushing over HTTPS, addressing a gap where Git previously ignored revocation status information even when servers provided it.

The motivation is clear: without this option, Git will accept a revoked certificate if the server staples an OCSP response indicating revocation, creating a security vulnerability. The behavior differs across TLS backends (OpenSSL ignores stapled responses unless explicitly asked, while GnuTLS checks them automatically), making the current state inconsistent and potentially dangerous. The patch introduces a boolean config option that defaults to false (to avoid breaking existing setups) but allows users to enable OCSP staple verification on a per-remote basis.

The implementation is clean and well-considered. It adds the configuration option through Git's existing urlmatch system, allowing per-URL settings without additional plumbing. The code properly handles cases where the TLS backend doesn't support OCSP verification by failing loudly rather than silently continuing. The patch includes thorough documentation explaining the behavior differences across TLS backends and the fail-closed nature of the feature.

Test coverage is excellent, with a new test script that verifies both the basic functionality and edge cases like per-URL configuration. The tests are designed to work without requiring a full OCSP infrastructure by testing the fail-closed path (servers that don't staple anything should fail when the option is enabled).

This appears to be a well-crafted solution to a real security concern, with appropriate attention to backwards compatibility and clear documentation of the tradeoffs involved. The patch is self-contained and doesn't appear likely to generate controversy.
