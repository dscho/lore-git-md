This is the first patch in a two-part series fixing Bash completion for `git checkout -C <dir>`. The series targets a usability issue where path completion for `git checkout` (which should only suggest tracked files) incorrectly falls back to untracked paths when the `-C <dir>` option is used.

This patch is a no-op refactoring of the `git checkout` completion logic in `contrib/completion/git-completion.bash`. It reorganizes the control flow to avoid an early return when `--` is detected on the command line, instead making all completion branches explicit. The change is purely structural—no behavior is altered—but it sets the stage for the actual fix in patch 2/2. The diff shows a straightforward restructuring of the function’s case statements and conditional blocks, with no functional changes.

The motivation for this refactoring is clear: the current early return prevents the completion logic from applying its own fallback behavior (e.g., restricting to tracked paths) when no candidates are found. By removing this early return, the next patch can implement a more targeted fix for the `-C <dir>` case. The patch is well-scoped and uncontroversial, as it doesn’t change behavior but makes the code easier to modify.
