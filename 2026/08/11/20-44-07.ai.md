This is a **security feature patch** (v2) that adds `http.sslVerifyStatus`, a new configuration option enabling Git to validate stapled OCSP responses during TLS handshakes. The patch addresses a gap in Git’s HTTPS certificate verification: while Git already verifies peer certificates and hostnames via libcurl, it does not request or validate OCSP staples (revocation status information sent by the server), leaving it vulnerable to accepting revoked certificates. This version removes the in-code comment explaining the default and backend differences, as requested by Junio C Hamano in the v1 review, moving that rationale to the commit message instead.

The implementation adds a boolean `http.sslVerifyStatus` option (defaulting to `false`) that sets `CURLOPT_SSL_VERIFYSTATUS` in libcurl. The design is fail-closed: if the server does not staple a response, the connection fails. This ensures security but defaults to `false` to avoid breaking remotes that do not support stapling. The patch includes per-URL configuration support (e.g., `http.https://example.com/.sslVerifyStatus`) and fails loudly if the TLS backend lacks staple-checking capability. The new test file `t/t5567-http-verify-status.sh` verifies the fail-closed behavior by confirming that enabling the option turns a working fetch into a failing one when the test server (which does not staple) is used.

The patch touches `http.c` and `Documentation/config/http.adoc`, with no symbol renames or behavioral changes beyond the new option. It requires libcurl ≥ 7.41.0, which is already below Git’s minimum version, so no version guard is needed. The commit message provides a clear explanation of the security rationale, design trade-offs, and backend differences (OpenSSL ignores staples unless explicitly enabled, while GnuTLS checks them by default). The test suite covers per-URL configuration and ensures the option does not break existing workflows when disabled.

This is a well-crafted security improvement with thorough testing and documentation. The v2 update addresses the only review feedback (removing the in-code comment) without altering the core functionality. The patch is likely to be uncontroversial, though future discussion may explore whether the default should eventually change to `true` or if users should be warned when staples are ignored. The fail-closed approach aligns with security best practices, and the implementation is robust across different TLS backends.
