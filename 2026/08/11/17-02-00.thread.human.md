This thread introduces a security feature to Git’s HTTPS handling: a new `http.sslVerifyStatus` option that enables validation of OCSP staples, closing a gap where Git could accept revoked certificates. The patch, authored by graysongordon-gl, adds a boolean configuration key (defaulting to `false`) that tells libcurl to request and validate stapled revocation status during TLS handshakes. If the server doesn’t provide a staple, the connection fails—this fail-closed design ensures security but defaults to off to avoid breaking remotes that don’t support stapling.

The v2 update addresses the only review feedback from Junio C Hamano: removing an in-code comment about the default and backend differences, moving that rationale to the commit message instead. The implementation is otherwise unchanged, with per-URL configuration support, thorough testing in `t/t5567-http-verify-status.sh`, and no symbol renames or behavioral changes beyond the new option. The patch requires no version guards, as Git’s minimum libcurl version already supports the necessary `CURLOPT_SSL_VERIFYSTATUS` flag.

The feature has drawn no objections so far, and the v2 revision suggests it’s on track for acceptance. The remaining open question is whether the default should eventually flip to `true` or if users should be warned when staples are ignored—though this is a forward-looking concern rather than a blocker. The patch is a clean, well-tested security improvement that aligns with Git’s existing HTTPS configuration patterns.
