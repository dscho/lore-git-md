This thread is about a security feature patch that adds `http.sslVerifyStatus`, a boolean configuration option (defaulting to `false`) to enable OCSP staple validation in Git’s HTTPS transport. The patch, now in its fourth version, aims to close a security gap where OpenSSL-linked Git binaries (common in FIPS-compliant deployments) silently ignore OCSP staples and accept revoked certificates. The author, graysongordon-gl, has addressed all procedural feedback from prior rounds, including test script numbering conflicts, Meson build integration, and prerequisite robustness.

The feature is motivated by government and government-adjacent customers (e.g., US Department of Defense PKI) who mandate OCSP stapling and encounter Git servers with stapled responses. The design is fail-closed—connections fail if the server does not provide a staple—but defaults to `false` to avoid breaking remotes that lack stapling support. The latest version (v4) integrates the tests into an existing script (`t5551-http-fetch-smart.sh`) and improves prerequisite handling, making the patch technically complete and ready for final review.

Junio C Hamano’s feedback has been purely procedural, with no objections to the feature itself. Patrick Steinhardt initially questioned the patch’s purpose, arguing that OCSP stapling’s declining relevance might not justify the maintenance burden. However, the author’s response provided concrete evidence of the feature’s value for government deployments, framing the threat model as a low-to-medium severity CVE risk (stolen private key impersonation enabling data exfiltration). The remaining open question is whether the default should eventually change to `true` or if users should be warned when staples are ignored. The patch is now awaiting final review.
