This thread introduces a new security feature for Git: `http.sslVerifyStatus`, a configuration option that enables validation of stapled OCSP responses during TLS handshakes. The patch, authored by graysongordon-gl, addresses a gap in Git's HTTPS certificate verification by ensuring that revoked certificates are not accepted, even when the server provides a valid certificate chain. Currently, Git's behavior varies by TLS backend—OpenSSL ignores OCSP staples unless explicitly requested, while GnuTLS checks them by default—leading to inconsistent security across different builds.

The patch adds a boolean option, `http.sslVerifyStatus`, which defaults to `false` to avoid breaking existing workflows with remotes that don’t support stapling. When enabled, it sets `CURLOPT_SSL_VERIFYSTATUS` in libcurl, adopting a fail-closed design: if the server doesn’t staple a response, the connection fails. The implementation supports per-URL configuration and includes clear error messages if the TLS backend lacks staple-checking capability. Testing is thorough, with a new test file (`t/t5567-http-verify-status.sh`) verifying fail-closed behavior, per-URL configuration, and backward compatibility when the option is disabled.

The patch is well-documented, with strong explanations of backend differences and design trade-offs in the commit message. While the feature is likely to be uncontroversial, it may prompt discussion about whether the default should eventually change to `true` or if users should receive warnings when staples are ignored. The patch targets `http.c` and updates `Documentation/config/http.adoc`, requiring libcurl ≥ 7.41.0 (already below Git’s minimum version). No reviews or objections have been posted yet, so the discussion is still open.
