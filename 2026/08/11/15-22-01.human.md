This is a macOS-specific bugfix for Git’s fsmonitor daemon, addressing a performance regression that causes excessive timeouts and lstat() calls on loaded systems. The patch itself is small and uncontroversial—it adds an asynchronous flush of pending FSEvents notifications before the daemon waits for a cookie file event—but the discussion here clarifies *why* the fix is necessary.

Tamir’s reply provides a detailed historical and technical explanation for Patrick Steinhardt’s question about why flushing FSEvents helps despite the 1ms latency setting. The key takeaway is that Apple’s FSEvents API makes no guarantees about queue drainage within any latency interval, and the original fsmonitor implementation accounted for this by waiting indefinitely for the cookie event. A 2026 change (56cef9cb1a) introduced a 1-second timeout to prevent hangs on broken filesystems, but this inadvertently caused timeouts on functioning macOS systems under load, triggering expensive full-index scans. Tamir’s measurements show the regression is real: 781 of 910 requests timed out on a 1M-entry index, with one `git status` taking 52 seconds and performing nearly a million lstats.

The patch is narrowly scoped to the macOS backend and doesn’t affect other platforms. While the code changes are simple and already deemed "sensible" by Patrick, the commit message still needs strengthening with additional benchmark data (a request echoed by Junio and Koji Nakamaru). Tamir’s reply here doesn’t include new numbers, so that remains an open action item. The discussion also surfaces that this regression was foreseeable—Patrick himself warned about it in 2026—but the timeout change landed anyway.

This looks like a well-motivated, low-risk fix for a real problem. The only remaining hurdle is improving the commit message, which should be straightforward. If you care about macOS performance or fsmonitor reliability, this patch is worth tracking.
