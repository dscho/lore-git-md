This is the third iteration of a well-motivated feature series that converts the build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`). The goal is to let users enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The series is now cooking in `next` under the topic `dk/use-nsec-runtime`.

The v3 update addresses the last major blocker: cross-platform correctness. On platforms where `NO_NSEC` is defined (lacking nanosecond support), the code now forces `cfg->use_nanosec` to false, mirroring the current behavior where the nanosecond paths are skipped entirely. This prevents silent corruption when `core.useNanosec=true` is set on an unsupported platform, satisfying Junio’s concern about undefined behavior. The fix is minimal and uncontroversial.

The series consists of three patches. The first is a small, self-contained Meson build-system fix (aligning `man.base.url.for.relative.links` with the Makefile’s behavior) that Patrick Steinhardt already confirmed correct. The second is a no-op refactor of `repo_config_values_init` that reorganizes the code to match the struct declaration; it is purely mechanical and ready to advance. The third patch is the core change, introducing `core.useNanosec` (defaulting to false) and removing the `USE_NSEC` macro from the build system. The config key is documented in `Documentation/config/core.adoc`, and the racy-Git technical note is updated to list filesystems known to support nanosecond precision.

The architectural question of where to cache the `core.useNanosec` value remains open but is no longer blocking. The author’s partial control-flow analysis shows that all 214 call paths to `repo_config_values()` currently terminate at `the_repository`, meaning the `the_repository`-only limitation is already exposed and not a new constraint. Patrick Steinhardt suggested a global variable as a fallback if the project prefers not to expand the `the_repository` surface area, but the current implementation is acceptable for now. The series is based on master (2c78326f81) and has a minor textual conflict with `ty/repo-config-cleanups` in `seen`; if both topics advance, the conflict will need resolution.

Performance is no longer a concern: the v1 hot-path regression (a ~41× slowdown in `git diff` benchmarks) is fixed by caching the value in `repo_config_values`. Benchmark results confirm the fix restores performance to baseline. The series does not yet update tests, as the platform-dependent nature of the change complicates testing; the author is seeking advice on how to handle this. The naming question (`core.useNanosec` vs a more abstract name like `core.useExtendedPrecision`) is still open but not urgent.

The series is well-structured, addresses a real usability issue, and is now technically sound. The remaining open questions are minor and do not block integration. If you care about filesystem precision or build-system flexibility, this is worth following.
