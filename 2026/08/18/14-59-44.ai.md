This is the v3 cover letter for D. Ben Knoble’s three-patch series converting the build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`). The series is now cooking in `next` under the topic name `dk/use-nsec-runtime`.

The v3 iteration addresses the last cross-platform correctness blocker by `#ifdef`-ing out the `use_nanosec` field and all related code paths when `NO_NSEC` is defined, ensuring backward compatibility and preventing silent corruption on platforms that lack nanosecond support. This change directly responds to Junio C Hamano’s concern about the risk of undefined behavior when `core.useNanosec=true` is set on a `NO_NSEC` platform. The author also considered (but ultimately rejected) a more compact preprocessor rewrite of `is_racy_stat()` that would have interleaved `#ifndef NO_NSEC` with the ternary logic; the current approach is more explicit and easier to follow.

The series remains split into three patches: (1) a Meson build-system fix for `man.base.url.for.relative.links`, (2) a no-op refactor of `repo_config_values_init`, and (3) the core change introducing `core.useNanosec` and removing `USE_NSEC`. The first two patches are uncontroversial and ready to advance independently; the third patch is now technically complete and waiting for a final decision on where to cache the `core.useNanosec` value (`repo_config_values`, `repo_settings`, or a global variable). The author’s partial control-flow analysis of 214 call paths to `repo_config_values()` shows that every analyzed path currently terminates at `the_repository`, even though some intermediate nodes are exposed via public `libgit.a` interfaces, meaning the `the_repository`-only limitation is already exposed and may grow with this change. Patrick Steinhardt has suggested that requiring `the_repository`-cleanliness could block the series indefinitely and offered a global variable as a fallback if the project prefers to avoid expanding the `the_repository`-only surface area.

The series touches `Documentation/config/core.adoc`, `environment.c`, `read-cache.c`, `statinfo.c`, and several build-system files. The on-disk format is unchanged, and the performance regression identified in v1 (a ~41× slowdown in `git diff` benchmarks) is resolved by caching the value in `repo_config_values`. Benchmark results confirm the fix restores performance to baseline (21 ms vs 20 ms). The author has not yet updated the test suite, as the platform-dependent nature of the change complicates testing; advice on how to handle this in the test suite remains welcome. A textual and semantic conflict with `ty/repo-config-cleanups` in `seen` will require resolution if both topics advance.

The series is well-motivated, technically sound, and now addresses all known correctness and performance concerns. The remaining open question is architectural: where to cache the `core.useNanosec` value, with implications for per-repository variation (e.g., submodules) and the broader `the_repository` removal effort. The author has framed this as a request for comments rather than a blocker, and the series is otherwise ready for integration.
