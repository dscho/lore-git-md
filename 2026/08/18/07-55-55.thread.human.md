This thread introduces a new `receive-report` hook for Git’s `receive-pack`, letting server administrators filter or rewrite the status report sent to clients after ref updates. The series, now at v5, is authored by Karthik Nayak and was motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the status report must reflect the repository state *after* server-side operations (like background jobs) complete—even if those operations happen *after* the ref transaction is committed. The hook acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband.

The series is queued in Junio C Hamano’s `seen` branch and is ready for integration into `next`. All prior feedback has been addressed, including hook naming, exit status semantics, and documentation ambiguities. The implementation splits into three patches: a documentation update, a refactoring of status-report generation, and the core hook logic. The hook’s design intentionally decouples the reported status from the actual repository state—a point Junio initially questioned as a potential consistency violation. Karthik clarified that this divergence is deliberate and aligns with GitLab’s use case, where conservative client behavior (e.g., not updating remote-tracking branches when the hook reports failure) is the goal. The discussion highlights a philosophical trade-off: the hook prioritizes server-side control over Git’s traditional consistency guarantees, but no code changes are needed.

Key participants include Junio (who raised the consistency concern but queued the series anyway), Patrick Steinhardt (who provided substantive reviews and proposed the exit status alignment with `pre-receive`), and Phillip Wood (who questioned the single-script design but was satisfied by Karthik’s justification). The series touches `builtin/receive-pack.c`, adds test coverage in `t/t5412-receive-report-hook.sh`, and documents the hook in `githooks(5)` and `git-receive-pack(1)`. The only loose end is Junio’s suggestion to replace a boolean parameter (`detailed_reports`) with an `enum` for maintainability, but Karthik considers this non-urgent and no reroll is planned.
