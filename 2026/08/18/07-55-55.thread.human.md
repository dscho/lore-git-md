This thread introduces a new `report` hook for `git-receive-pack` to allow server administrators to intercept and modify the status report sent to clients after ref updates. The hook is motivated by GitLab’s need for multi-version concurrency control (MVCC), where the status report must reflect the repository state after all ref updates are committed but before the client receives confirmation. Karthik Nayak is the author, and the patch is currently under review with no prior versions posted.

The hook acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status causes `receive-pack` to die, treating the push as failed, but the current implementation discards the hook’s stdout in this case—a behavior that Junio C Hamano and Patrick Steinhardt find surprising and potentially problematic. This design ambiguity remains unresolved, though Karthik has accepted most of Patrick’s other suggestions, including clarifying the hook’s documentation, renaming a variable, and adjusting test output to verify the “remote:” prefix on stderr.

The patch touches `builtin/receive-pack.c`, updates `Documentation/githooks.adoc`, and adds a new test script (`t/t5412-report-hook.sh`). Test coverage includes passthrough behavior, failure modes, and sideband relay, but does not yet verify the interaction between exit status and stdout. The thread is now better positioned to converge on a design, but the exit status behavior is likely to remain a point of contention until resolved. The patch has not yet been queued in Junio’s integration branches.
