This thread introduces a new `report` hook for `git-receive-pack`, allowing server administrators to filter or modify the status report sent to clients after ref updates are committed. The patch, authored by Karthik Nayak, is motivated by GitLab’s need to integrate MVCC (multi-version concurrency control) systems, though the original submission lacked a clear explanation of why existing hooks couldn’t serve this purpose. Patrick Steinhardt’s recent review fills that gap, confirming the hook’s necessity and sharpening its design.

The hook acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. A non-zero exit status currently causes `receive-pack` to die, discarding the hook’s stdout—a behavior both Junio C Hamano and Patrick Steinhardt find surprising. Patrick argues the hook should always return zero to ensure the client receives a well-formed report, even when rejecting updates. This design ambiguity remains unresolved, though Patrick’s feedback moves the discussion toward a clearer contract.

Documentation has also been a focus. The patch includes a new test script (`t/t5412-report-hook.sh`) and updates to `githooks.adoc`, but reviewers have noted gaps: missing use-case examples, unclear exit-status semantics, and whether the hook should be mentioned in `git-receive-pack(1)`. Patrick’s suggestions—dropping the word “remote” from the hook description, clarifying client assumptions, and documenting non-zero exits as bugs—address these issues directly.

The patch is under active review, with no prior versions posted. While Kristoffer Haugsbakk’s earlier feedback was surface-level (style and documentation), Patrick’s review engages deeply with the technical and behavioral implications. The next steps will likely involve revising the exit-status logic and tightening the documentation before the patch can graduate to Junio’s integration branches.
