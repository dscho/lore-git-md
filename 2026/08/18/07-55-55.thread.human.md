The `receive-report` hook series by Karthik Nayak is now complete and ready for integration. This three-patch effort adds a new hook to `git-receive-pack` that lets server administrators intercept and modify the status report sent to clients after ref updates are committed. The hook, named `receive-report`, runs after all ref updates but before the report is finalized, receiving the pkt-line encoded status on stdin and replacing it with its stdout; stderr is forwarded to the client via the sideband channel. A zero exit code means the hook’s output is used as the report, while a non-zero exit rewrites all ref status lines to "receive-report hook failed" and overwrites any existing per-ref error messages, aligning with the behavior of the `pre-receive` hook.

The series has addressed all prior feedback, including Junio Hamano’s objection to the overly generic name `report` (now `receive-report`), Patrick Steinhardt’s proposal to align exit status semantics with `pre-receive`, and documentation ambiguities such as grammatical fixes and optional markers in `githooks.adoc`. The implementation is self-contained, avoiding the config-based hook infrastructure to sidestep parallelization complexity, and is well-documented in both `git-receive-pack.adoc` and `githooks.adoc`. The hook can affect the push outcome in three ways: rewriting individual ref status lines, aborting the entire push (by exiting non-zero), or modifying the initial `unpack` status line. Test coverage is thorough, with 224 lines added to `t/t5412-receive-report-hook.sh` covering passthrough behavior, failure modes, and edge cases.

Junio has queued the series in `seen` and confirmed it is ready for `next`. The series is motivated by GitLab’s need to implement MVCC on the server side, where the status report must reflect the repository state after all ref updates are committed but before the client receives confirmation. With all feedback addressed and the implementation finalized, this series is poised for graduation.
