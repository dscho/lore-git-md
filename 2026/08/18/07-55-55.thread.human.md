This thread is about a new `receive-report` hook for `git-receive-pack`, proposed by Karthik Nayak in a three-patch series (v5). The hook lets server administrators intercept and modify the status report sent to clients after ref updates are committed, addressing GitLab’s need for multi-version concurrency control (MVCC). The series is technically complete, queued in Junio C Hamano’s `seen` branch, and ready for integration into `next`.

The implementation adds a hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with stdout, and forwards stderr to the client via sideband. A non-zero exit code rewrites all ref status lines to indicate hook failure. The hook is documented in `githooks.adoc` and `git-receive-pack(1)`, with 224 lines of test coverage in `t/t5412-receive-report-hook.sh`. Junio initially raised concerns about the hook’s ability to report a state divergent from the actual repository, but Karthik clarified that this behavior is intentional for GitLab’s use case, where the client should not update remote-tracking branches if the hook reports failure.

All prior feedback has been addressed, including Patrick Steinhardt’s substantive reviews on exit status semantics and documentation, and Junio’s maintainability suggestion to replace the `detailed_reports` boolean with an `enum` (which Karthik agreed to in principle but did not implement, as no reroll is planned). The series remains split into three patches: a documentation-only patch, a refactoring of status-report generation logic, and the core hook implementation. Junio’s latest comments weaken the argument for a separate hook by noting that the `reference-transaction` hook could theoretically be extended, but no action is required at this stage. The series is now awaiting graduation to `next`.
