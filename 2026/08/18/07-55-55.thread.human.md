The `report` hook patch by Karthik Nayak is under active review for its second version. The patch introduces a server-side hook in `receive-pack` that lets administrators filter or modify the status report sent to clients after ref updates are committed. This is motivated by GitLab’s need to implement MVCC (multi-version concurrency control), where the status must reflect the repository state post-update but pre-client confirmation.

The core design—using a single-script hook modeled after `proc-receive` rather than Git’s config-based hook infrastructure—has been settled, with Karthik’s commit message now justifying this choice. However, Patrick Steinhardt has raised a significant behavioral concern: the current implementation treats a non-zero hook exit as a "nuclear option," causing `receive-pack` to die and the client to see a generic "remote end hung up" error. He proposes aligning the hook’s failure mode with `pre-receive` instead, rewriting all ref status lines to `"report hook failed"` and allowing a clean exit. This would improve error reporting while preserving the ability to abort in exceptional cases. The discussion is now focused on this refinement, with no new objections to the hook’s core functionality. Documentation updates are mostly complete, though minor clarifications about the `ng` line format and implementation details remain.

Key participants include Karthik (author), Junio (maintainer, who previously questioned the single-script design), Patrick (who drove the exit-status semantics debate), and Phillip Wood (who raised concerns about the hook’s design rationale). The patch is still under review, with the exit-status behavior as the primary open question. No merge status has been indicated.
