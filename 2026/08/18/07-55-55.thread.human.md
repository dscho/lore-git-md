This thread introduces a new `report` hook for `git-receive-pack`, allowing server administrators to filter or modify the status report sent to clients after ref updates are committed. The feature is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the status report must reflect the repository state post-update but before client confirmation. The patch is now in its second version, addressing all prior feedback except for one key design question: how the hook’s exit status should behave.

The current implementation treats a non-zero exit as a "nuclear option," discarding the hook’s stdout and causing `receive-pack` to die, which fails the push. Patrick Steinhardt has proposed aligning this behavior with the `pre-receive` hook—rewriting all ref status lines to `"report hook failed"` and allowing `receive-pack` to exit cleanly—while preserving the "nuclear option" for exceptional cases. Karthik Nayak, the author, acknowledges the proposal but describes the required output restructuring as "awkward," leaving the exit status semantics unresolved. Documentation updates are largely complete, though minor ambiguities remain, such as whether the optional `<reason>` field in `ng` lines requires a trailing newline.

The thread has seen substantive engagement from Patrick Steinhardt and Junio C Hamano, who raised concerns about the hook’s design and exit status behavior, while Kristoffer Haugsbakk and Phillip Wood contributed feedback on documentation and design rationale. The single-script design (modeled after `proc-receive`) has been justified in the commit message, addressing earlier objections, but no explicit maintainer endorsement has been given. The patch is otherwise ready for integration, pending resolution of the exit status question.
