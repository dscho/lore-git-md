This thread introduces a new `report` hook for `git receive-pack`, allowing server administrators to filter or modify the status report sent to clients after ref updates. The patch, authored by Karthik Nayak, is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the status report must reflect the repository state post-update but pre-client confirmation. The hook acts as a bidirectional filter, receiving the pkt-line encoded status on stdin and replacing it with its stdout, while forwarding stderr to the client via sideband. A non-zero exit status is treated as a "nuclear option," discarding stdout and causing `receive-pack` to fail the push.

The patch has been under review since its initial submission, with no prior versions posted. Key design decisions—such as the "nuclear option" behavior for non-zero exits—have been resolved in principle, aligning with Patrick Steinhardt’s arguments and Karthik’s acceptance. However, Junio C Hamano has raised concerns about the interaction between exit status and stdout, suggesting the current behavior may be surprising and require clearer documentation or revision. Documentation updates are planned for `githooks.adoc` and `git-receive-pack(1)`, though the location for documenting the `pkt-line` format remains unresolved. Minor test adjustments, such as verifying the "remote:" prefix on stderr, are also planned.

Phillip Wood’s recent review adds a new dimension to the discussion, questioning whether the hook’s single-script design (modeled after `proc-receive`) is still justified in light of Git’s config-based hook infrastructure, which supports multiple scripts per event. While he acknowledges that server-side hooks may reasonably favor a single-script approach, he argues the commit message should explicitly justify this choice rather than leaving it implicit. This is a substantive critique of the patch’s design rationale, though it does not propose specific code changes. Other participants, including Patrick Steinhardt and Kristoffer Haugsbakk, have focused on documentation clarity, test adjustments, and exit status semantics, with Steinhardt’s concerns now resolved in favor of the "nuclear option" approach. The thread remains open, with no maintainer decision on Junio’s concerns or Phillip’s design question.
