The `receive-report` hook patch series (v6) by Karthik Nayak introduces a new server-side hook for Git’s `receive-pack` that allows administrators to filter or modify the status report sent to clients after ref updates. This is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the reported status must reflect the repository state *after* all server-side operations—including those beyond `ref_transaction_commit()`—are complete. The hook acts as a bidirectional filter, receiving the pkt-line encoded status report on stdin and replacing it with its stdout, while forwarding stderr to the client via the sideband channel.

The series has addressed all prior feedback, including Junio C Hamano’s maintainability concerns (replacing a `detailed_reports` boolean with an `enum report_status_version`) and Patrick Steinhardt’s substantive reviews (tightening documentation and aligning exit status semantics with the `pre-receive` hook). Junio has queued the series in `seen`, and it is ready for integration into `next`. The latest version splits the work into four patches: documentation, refactoring (protocol version handling and status-report generation), and the core hook implementation. Test coverage in `t/t5412-receive-report-hook.sh` verifies passthrough behavior, failure modes, stdin/stdout handling, and sideband relay.

A key philosophical tension remains: the hook’s design intentionally decouples the reported status from the actual repository state, allowing the server to report a push as failed (`ng`) while still committing ref updates. This violates Git’s traditional principle that remote-tracking branches reflect the server’s state, but the commit message justifies the divergence with GitLab’s MVCC use case. Junio has acknowledged this trade-off but raised no blocking concerns. The only remaining loose ends are minor: Patrick Steinhardt’s surface-level style nit (unnecessary curly braces in `override_cmds_error()`) and a missed refactoring opportunity (unifying `report()` and `report_v2()`). Karthik plans to address these in a future reroll but confirms they do not affect functionality or design. The series is otherwise complete and awaiting graduation to `next`.
