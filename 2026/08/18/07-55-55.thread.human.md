This thread introduces a new `report` hook in Git’s `receive-pack` to allow server administrators to intercept and modify the status report sent to clients after ref updates. The hook is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the status must reflect the repository state after all updates are committed but before the client receives confirmation.

The patch is under review and remains unchanged in its core implementation. The primary design debate has shifted to whether the hook should integrate with Git’s config-based hook infrastructure (which supports multiple scripts per event) or remain a single-script hook modeled after `proc-receive`. Junio C Hamano has challenged the assumption that server-side hooks inherently justify a single-script design, arguing that the server/client distinction does not necessarily imply tighter control or simpler coordination. This sharpens the unresolved question: the commit message must now either justify the single-script approach or reconsider the hook’s architecture. Phillip Wood raised this concern earlier, and Junio’s skepticism suggests the current design may need further justification or revision.

Other aspects of the patch are largely settled. The hook’s exit status semantics—where a non-zero exit discards stdout and causes `receive-pack` to fail—have been agreed upon as a "nuclear option" for exceptional cases. Documentation updates (to `githooks.adoc` and `git-receive-pack(1)`) and minor test adjustments (e.g., verifying the "remote:" prefix on stderr) are still planned. Key participants include Karthik Nayak (author), Junio C Hamano (maintainer), Patrick Steinhardt (substantive reviewer), and Phillip Wood (who raised the config-based hook question). The thread remains focused on design justification rather than implementation changes.
