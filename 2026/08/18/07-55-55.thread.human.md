This thread is about a four-patch series (v6) by Karthik Nayak that introduces a new `receive-report` hook for `git-receive-pack`. The hook allows server administrators to intercept and modify the status report sent to clients after ref updates, addressing GitLab’s need for server-side MVCC (multi-version concurrency control). The series is now queued in Junio’s `seen` branch and ready for integration into `next`.

The core motivation is GitLab’s requirement to decouple the reported push status from the actual repository state, enabling conservative client-side behavior (e.g., not updating remote-tracking branches when the hook reports a failure). This design intentionally violates Git’s traditional consistency principle—that remote-tracking branches reflect the server’s state—justified by GitLab’s use case. Junio C Hamano has acknowledged this trade-off but raised no blocking concerns. The series has addressed all prior feedback, including Junio’s maintainability suggestion to replace a boolean flag with an `enum` for protocol-version clarity, and Patrick Steinhardt’s technical and documentation improvements.

Key participants include Karthik (author), Junio (maintainer), Patrick Steinhardt (substantive reviewer), and Kristoffer Haugsbakk (documentation reviewer). The series touches `builtin/receive-pack.c` and adds test coverage in `t/t5412-receive-report-hook.sh`. The hook is documented in `githooks.adoc` and `git-receive-pack(1)`, with the latter now also documenting the previously undocumented `proc-receive` hook. The only remaining open question is the philosophical tension around consistency, which the commit message explicitly acknowledges. No further changes are expected.
