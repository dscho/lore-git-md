This thread introduces a new `report` hook for `git-receive-pack`, allowing server administrators to filter or modify the status report sent to clients after ref updates. The feature is driven by GitLab’s need to implement MVCC (multi-version concurrency control), where the status report must reflect the repository’s state post-update but before client confirmation.

The patch, authored by Karthik Nayak, is under active review. It includes documentation (`githooks.adoc`) and a test script (`t/t5412-report-hook.sh`) covering passthrough behavior, failure modes, and sideband relay. However, the design’s core ambiguity—whether a non-zero exit status should discard the hook’s stdout—remains unresolved. Junio C Hamano and Patrick Steinhardt have raised concerns about this behavior, arguing it is surprising and may need revision or clearer documentation. Patrick also suggests the hook should always return zero to ensure the client receives a well-formed status report, even when rejecting updates.

Karthik has addressed some of Kristoffer Haugsbakk’s surface-level feedback, expanding the commit message to include GitLab’s MVCC use case and agreeing to document the hook in `git-receive-pack(1)`. However, the patch itself remains unchanged, and the substantive design questions—exit status semantics, documentation gaps, and test coverage for the exit status/stdout interaction—are still open. The thread is awaiting further input from Karthik on these points before progressing.
