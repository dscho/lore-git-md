This thread introduces a new `receive-report` hook for `git-receive-pack`, allowing server administrators to intercept and modify the status report sent to clients after ref updates are committed. The feature is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the final status must reflect operations occurring *after* `ref_transaction_commit()`. Karthik Nayak is the author, and the series is now in its seventh iteration (v7), with all prior feedback addressed.

The hook acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. A non-zero exit code rewrites all ref status lines to a generic error, effectively treating the push as failed—though ref updates are *not* rolled back. This design intentionally decouples the reported status from the actual repository state, a trade-off explicitly acknowledged in the commit message. While this violates Git’s traditional consistency guarantees (remote-tracking branches may not reflect the server’s state), it aligns with GitLab’s use case, where conservative client-side behavior (not updating remote-tracking branches when the hook reports failure) is desired.

The series is feature-complete and queued in Junio C Hamano’s `seen` branch, ready for integration into `next`. Key changes in v7 include unifying the `report()` and `report_v2()` functions into a single helper, replacing a boolean parameter with an `enum report_status_version`, and addressing surface-level nits (e.g., removing unnecessary curly braces). Test coverage in `t/t5412-receive-report-hook.sh` verifies passthrough behavior, failure modes, and the hook’s ability to modify the `unpack` status line. Documentation in `githooks.adoc` and `git-receive-pack.adoc` explains the hook’s three ways of affecting push outcome: rewriting ref status lines, aborting the push (non-zero exit), or modifying the `unpack` status line.

Junio’s earlier concern about the hook’s consistency implications remains a documented design choice rather than a blocker. The commit message clarifies that the hook owner is responsible for undoing ref changes if needed and that the feature is only appropriate for servers where rejected updates are not immediately visible to other readers. Patrick Steinhardt and Phillip Wood provided substantive reviews, all of which have been incorporated. The series has no unresolved technical objections and is poised for graduation to `next`.
