The `report` hook feature series, introduced by Karthik Nayak to allow server-side filtering of Git’s status reports, is now effectively complete and awaiting only a naming adjustment before moving forward. The series, currently queued in Junio C Hamano’s `seen` branch, adds a new `report` hook that runs after ref updates are committed but before the status report is sent to the client. The hook acts as a bidirectional filter, receiving the pkt-line encoded report on stdin and replacing it with its stdout, while forwarding stderr to the client via the sideband channel. This functionality is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side.

All prior feedback on the series has been addressed, including the exit status semantics, which were resolved in favor of Junio and Patrick Steinhardt’s proposal: a non-zero exit code rewrites all ref status lines to `"report hook failed"` and allows `receive-pack` to exit cleanly, aligning with the behavior of the `pre-receive` hook. The series is split into three patches—documentation, refactoring, and core implementation—and includes comprehensive test coverage for passthrough, failure modes, and sideband relay. Junio has already resolved a minor conflict with Justin Tobler’s concurrent "pluggable writes" series, and the only remaining open issue is the hook’s name, which Junio and Patrick both agree is too generic. Patrick has suggested `receive-report` as a more specific alternative, and Karthik is expected to address this in the next iteration while preserving the agreed-upon behavior. Once the naming feedback is resolved, the series is ready to graduate to `next`.
