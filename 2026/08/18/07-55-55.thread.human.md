This thread introduces a new `report` hook for Git’s `receive-pack`, allowing server administrators to intercept and modify the status report sent to clients after ref updates. The feature is motivated by GitLab’s need to implement MVCC (multi-version concurrency control), where the status report must reflect the repository state post-update but pre-client confirmation. The series, now at version 3, has addressed all prior feedback and is queued in Junio’s `seen` branch, ready for integration.

The implementation splits into three patches: a documentation update for existing hooks, a refactoring to extract status-report generation logic into a reusable helper, and the core hook implementation. The hook runs after ref updates are committed but before the status report is sent, acting as a bidirectional filter—it receives the pkt-line encoded report on stdin and replaces it with its stdout, while forwarding stderr to the client via sideband. Exit status semantics align with the `pre-receive` hook: a non-zero exit rewrites all ref status lines to `"report hook failed"` and allows `receive-pack` to exit cleanly. Junio manually resolved a conflict with Justin Tobler’s concurrent "pluggable writes" series, asking Karthik Nayak to sanity-check the resolution.

The only remaining open point is Junio’s objection to the hook name `report` as overly generic. He suggests reconsidering the naming before the series graduates to `next`, but this is not a blocker—expect a v4 addressing this while preserving the agreed-upon exit semantics and implementation. All other feedback has been resolved, including documentation clarity and the hook’s design rationale. The series is now in `seen` and expected to move to `next` in the next integration cycle.
