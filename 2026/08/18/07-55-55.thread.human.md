This thread introduces a new `report` hook for Git’s `receive-pack` to allow server administrators to intercept and modify the status report sent to clients after ref updates. The feature is driven by GitLab’s need to implement multi-version concurrency control (MVCC), where the status report must reflect the repository state after all updates are committed but before the client receives confirmation.

The series is now in its third iteration (v3) and is queued in Junio C Hamano’s `seen` branch, ready for integration. All prior feedback has been addressed, including the exit status semantics, which were resolved in favor of Junio and Patrick Steinhardt’s proposal: a non-zero exit code rewrites all ref status lines to `"report hook failed"` and allows `receive-pack` to exit cleanly, matching the behavior of the `pre-receive` hook. The series is split into three patches: a documentation update, a refactoring to extract status-report generation logic, and the core hook implementation. Junio manually resolved a conflict with Justin Tobler’s concurrent "pluggable writes" series, and Karthik Nayak has confirmed the resolution is correct.

The only remaining blocker before graduation to `next` is the hook’s name. Junio and Patrick object to `report` as overly generic and suggest `receive-report` as a more specific alternative. No other technical concerns are outstanding, and the series is otherwise ready for integration. Expect a v4 to address the naming feedback while preserving the agreed-upon implementation. Key participants include Karthik Nayak (author), Junio C Hamano (maintainer), and Patrick Steinhardt, all of whom have endorsed the current design.
