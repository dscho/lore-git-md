This is a **substantive review** of the v4 patch adding `http.sslVerifyStatus` for OCSP staple validation. The review comes from Patrick Steinhardt, a core contributor with deep domain knowledge of Git’s transport layer, and it surfaces several technical and documentation concerns that remain unresolved despite the patch’s prior acceptance by the maintainer.

The review focuses on three areas: **documentation accuracy**, **error message clarity**, and **test coverage**. On documentation, Patrick points out that the man page’s description of GnuTLS behavior is outdated—recent versions of GnuTLS and libcurl (since GnuTLS 3.8 and curl 8.10) now handle OCSP stapling identically to OpenSSL, so the backend-specific caveats no longer apply. He suggests converting the backend-specific notes into a bulleted list to accommodate future additions (e.g., mbedTLS) and asks whether other backends are known to fail or behave differently.

On error handling, Patrick proposes improving the error message when `CURLOPT_SSL_VERIFYSTATUS` fails by including the specific libcurl error string (via `curl_easy_strerror()`). This would help users diagnose whether the failure is due to a missing feature (`CURLE_NOT_BUILT_IN`) or some other issue, rather than leaving them with a generic "cannot verify" message.

The most significant request is for **additional test coverage**: Patrick asks whether it is feasible to test the positive case—where a server provides a valid OCSP staple and Git successfully validates it. The current tests only cover the fail-closed path (missing staple) and per-URL overrides, but do not verify that the feature actually works when stapling is available. This is a gap in the patch’s validation, as it leaves the core functionality untested in the test suite.

The review is **not a rejection**—Patrick acknowledges the patch’s procedural completeness and the author’s thorough responses to prior feedback—but it does identify **actionable improvements** that would strengthen the patch before it graduates to `master`. The open questions about backend behavior and test coverage are likely to generate follow-up discussion, and the author will need to address them to fully close the review cycle.
