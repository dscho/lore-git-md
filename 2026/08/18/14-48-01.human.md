This is a maintainer response to Artur Bieniek’s patch introducing `git pull --hard`, a new mode that resets the current branch, index, and working tree to the fetched branch using `git reset --hard`. Junio C Hamano expresses mild opposition to the feature, arguing that it doesn’t align with `git pull`’s core purpose of history integration and could increase the risk of accidental data loss for users who do make local changes.

Junio acknowledges that some users—those who never modify their working tree or history—might benefit from a convenient way to hard-reset to the upstream branch. However, he points out that the same outcome is already achievable with `git fetch` followed by `git reset --hard @{u}`, making the new option redundant. More critically, he worries that adding a destructive operation to `git pull` could lead to mistakes, particularly for users who *do* have local changes they care about.

The response is measured but firm: Junio prefers keeping destructive operations explicit and separate, rather than bundling them into a command primarily used for integration. This suggests the patch is unlikely to be merged in its current form unless the discussion shifts toward a stronger justification or a safer design. For now, the thread is at an early stage, with no other reviews or counterarguments yet.
