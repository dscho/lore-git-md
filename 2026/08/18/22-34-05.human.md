This is the first patch in a two-part bugfix series addressing a race condition in Git's geometric repacking mechanism that can cause `git replay` to crash with a segmentation fault. The issue occurs when objects involved in a merge become unreadable—such as when a multi-pack-index (MIDX) references a packfile that has been removed by a concurrent geometric repack—leading the merge machinery to return early with `result.clean < 0` and a `NULL` result tree. The current code in `pick_regular_commit()` only checks for `!result->clean`, missing the case where `clean` is negative, which causes it to dereference the `NULL` tree and crash.

The fix is straightforward: the patch adds an explicit check for `result->clean < 0` in `replay.c`, ensuring the command fails gracefully with an error message instead of crashing. The commit message explains the scenario clearly, and the added test in `t/t3650-replay-basics.sh` simulates the condition by removing an object mid-operation, verifying that `git replay` exits with a failure message rather than a segfault. The test also confirms that the merge machinery’s existing error messages (e.g., "Could not read <object>") are preserved, so users get meaningful feedback.
