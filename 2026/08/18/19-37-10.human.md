This is a security feature patch that adds `http.sslVerifyStatus`, a new boolean configuration option (default `false`) to enable OCSP staple validation in Git’s HTTPS connections. The patch is now in its fifth iteration and addresses all prior review feedback from Junio C Hamano and Patrick Steinhardt.

The feature closes a security gap where Git, when linked against OpenSSL, ignores OCSP staples and accepts revoked certificates. Government and FIPS-compliant deployments (e.g., US Department of Defense PKI) mandate OCSP stapling, and this patch allows them to enforce it via configuration. The design is fail-closed—connections fail if the server does not provide a staple—but defaults to `false` to avoid breaking remotes that do not support stapling.

Key improvements in v5 include a clearer commit message, updated documentation that accurately reflects backend behavior (GnuTLS and OpenSSL now behave identically in recent libcurl versions), and enhanced error messages that include the specific libcurl error string (`curl_easy_strerror()`) for better diagnostics. The test suite has been expanded with four new tests in `t5551-http-fetch-smart.sh`, covering the global and per-URL configuration, the default behavior, and the fail-closed behavior when staples are missing. The `SSL_VERIFYSTATUS` lazy prerequisite now uses `test_might_fail` to handle expected failures gracefully.

The patch is technically complete and ready for integration. Junio previously accepted v4 as technically sound, and the unresolved substantive feedback—documentation accuracy, error message clarity, and test coverage—has been addressed in this version. The only remaining open question is whether the default should eventually change to `true` or if users should be warned when staples are ignored, but this does not block merging. The feature’s maintenance burden is justified by its targeted use case, and the author has provided concrete evidence of its necessity in government deployments.
