Thread identity: Bugfix series addressing a race condition in Git's geometric repacking mechanism causing objects to be incorrectly reported as missing, leading to crashes in `git replay`. Two-patch series by Elijah Newren via GitGitGadget.

Core problem or goal: Fix a race condition where a multi-pack-index (MIDX) references a packfile removed by geometric repacking, causing processes using the stale MIDX to fail to locate objects. The issue manifests as a SIGSEGV in `git replay` and missing-object errors in other server-side operations (`git merge-tree`, `git diff`, `git rev-list`, `rev-parse`, `cat-file`). The root cause is that when an object exists in multiple packs covered by a MIDX and the *preferred* pack (the one the MIDX would normally use) is removed, the current code fails to find the object in the remaining packs because the non-MIDX lookup skips all packs covered by the MIDX, and the MIDX lookup fails when the preferred pack is missing. This results in a false negative affecting *all* object lookups, not just those using `OBJECT_INFO_QUICK`. Patch 1/2 ensures `git replay` fails gracefully when merge inputs are unreadable, while patch 2/2 modifies the packed-object backend to recover from MIDX-packfile mismatches by scanning all packs covered by the MIDX when the normal lookup fails.

Current status: **Under active design discussion.** The series remains a high-priority candidate for merging, but the architectural debate over patch 2/2’s implementation continues. The fix’s necessity is widely accepted, but the performance implications of the fallback logic—particularly the conditions under which it triggers—are still being refined. Junio C Hamano and Patrick Steinhardt have provided **substantive** reviews with no remaining technical objections to the core fix, while Jeff King (Peff) has raised **substantive** architectural and performance critiques. The latest exchange between Peff and Patrick clarifies that the bug affects *all* object lookups, not just `OBJECT_INFO_QUICK` callers, and that the fallback logic is only invoked when the MIDX *should* have found the object (due to the `bsearch()` check). Peff’s performance concern has evolved into a debate over whether the recovery logic should be tied to the `SECOND_READ` phase (Peff’s preference) or remain as currently implemented (triggering on any lookup failure). Peff’s latest email refines this concern by noting that when an object exists in a *newer* pack (not covered by the MIDX), the `SECOND_READ` phase will prioritize that pack due to reverse-mtime sorting, avoiding the need to scan all MIDX-covered packs. This means the fallback’s cost is only incurred when the object is *not* in a newer pack—i.e., when it truly requires scanning the MIDX-covered packs to recover from the race condition. The discussion now centers on optimizing the scan order and timing for correctness and performance, with the fallback’s overhead limited to edge cases.

Key technical details:
- Files touched: `replay.c` (graceful failure logic), `odb/source-packed.c` (MIDX recovery), and test files (`t/t3650-replay-basics.sh` for patch 1/2, `t/t5319-multi-pack-index.sh` for patch 2/2).
- Subsystems: geometric repacking, MIDX, packed-object backend, `git replay`.
- New behavior: `git replay` now fails gracefully with an error message when objects are unreadable; MIDX-packfile mismatches are recovered transparently by scanning packs in `find_pack_entry()`. The recovery logic is gated by the presence of a stale MIDX and only triggers when the MIDX *should* have found the object but didn’t. The fix targets `OBJECT_INFO_QUICK` callers but also addresses a broader correctness issue.
- New symbols: None (logic-only changes).
- No on-disk format changes.
- Test coverage: Added for both the `git replay` crash scenario (patch 1/2) and MIDX recovery logic (patch 2/2). Tests simulate unreadable objects and MIDX-packfile mismatches, verifying error messages and recovery behavior. The redundant `test_grep` check in patch 1/2's test was removed as part of the review process.
- The central functions under discussion are `find_pack_entry()` in `odb/source-packed.c` and the `fill_midx_entry()` helper. The current approach embeds recovery logic in `find_pack_entry()`, while Peff’s tri-state proposal would modify `fill_midx_entry()` to return a tri-state value (not found / found but unavailable / found and available) and shift responsibility for handling missing packfiles to callers. Patrick’s refinement suggests scanning only the packs covered by the MIDX when the preferred pack is missing, while Peff’s latest suggestion ties the fallback to `SECOND_READ` to optimize performance for `QUICK` callers. Peff’s latest email clarifies that reverse-mtime sorting in `SECOND_READ` ensures newer packs (not covered by the MIDX) are prioritized, limiting the fallback’s overhead to cases where the object is only in MIDX-covered packs.

Open questions and loose ends:
- **Design direction for patch 2/2**: The primary unresolved question is whether to adopt the current approach (recovery logic in `find_pack_entry()`), Patrick’s refinement (scanning only MIDX-covered packs), or Peff’s latest suggestion (tying the fallback to `SECOND_READ`). The tri-state design remains favored in principle, but the implementation details—such as the scan order, timing, and how to handle `OBJECT_INFO_QUICK` callers—remain open. Peff’s latest email argues that the fallback should only trigger during `SECOND_READ` to avoid unnecessary scans for `QUICK` callers, while preserving correctness for non-`QUICK` callers. The reverse-mtime sorting observation strengthens the case that the fallback’s overhead is limited to edge cases.
- **Performance implications**: Peff’s concern about scanning MIDX-covered packs when the preferred pack is missing has been refined: the fallback’s cost is only incurred when the object is *not* in a newer pack (not covered by the MIDX). This limits the overhead to cases where recovery is truly needed. The debate now focuses on whether to trigger the fallback during the first pass or defer it to `SECOND_READ`.
- **Follow-up work**: Elijah’s planned follow-up patches to address additional race-condition scenarios may be affected by the outcome of this discussion, particularly if the project adopts the tri-state design or modifies the scan order/timing.
