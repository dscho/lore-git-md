Thread identity: Bugfix series addressing a race condition in Git's geometric repacking mechanism causing objects to be incorrectly reported as missing, leading to crashes in `git replay` and other server-side operations. **Four-patch series by Elijah Newren via GitGitGadget, now at v2.**

Core problem or goal: Fix a race condition where a multi-pack-index (MIDX) references a packfile removed by geometric repacking, causing processes using the stale MIDX to fail to locate objects. The issue manifests as SIGSEGV in `git replay` and missing-object errors in other operations (`git merge-tree`, `git diff`, `git rev-list`, `rev-parse`, `cat-file`). The root cause is that when an object exists in multiple packs covered by a MIDX and the *preferred* pack is removed, the current code fails to find the object in the remaining packs because the non-MIDX lookup skips all packs covered by the MIDX, and the MIDX lookup fails when the preferred pack is missing. The series also addresses a leak in `git mktree --batch` (used in new test cases), demonstrates and fixes problems with `OBJECT_INFO_QUICK` readers, and introduces a lightweight recovery mechanism for `OBJECT_INFO_QUICK` lookups when packfiles vanish mid-operation.

Current status: **Series under active debate.** The core fix (patch 4/4) remains ready for merging, having adopted Jeff King (Peff)'s tri-state design for `fill_midx_entry()` and gating the recovery logic on `SECOND_READ` to optimize performance for `QUICK` callers. Peff's latest review of patch 4/4 raises three minor points: (1) the unchanged name of `fill_midx_entry()` despite its new tri-state return semantics may confuse future callers, though the risk is low; (2) the `stale_packs_detected` flag introduced in patch 3/4 may no longer be necessary now that the tri-state design is in place; and (3) a rewritten comment is unnecessary "patch fluff" that should be dropped. Peff explicitly acknowledges the `SECOND_READ`-gated recovery logic is now implemented as expected, framing these as preferences rather than blockers. Patch 3/4 remains the primary point of contention, with Peff's earlier critique challenging its architectural premise and arguing that `OBJECT_INFO_QUICK` is being misused by `git mktree --batch`. The debate centers on whether the fix should target the caller (`git mktree --batch`) or the object database layer, and whether the `stale_packs_detected` flag violates the `QUICK` flag's intended semantics. Patch 1/4 (v2) and patch 2/4 (v2) remain uncontroversial after addressing prior feedback. The series is rebased on `ps/odb-generic-corrupt-objects`, resolving a minor conflict.

Key technical details:
- Files touched: `replay.c` (graceful failure logic for `git replay`), `odb/source-packed.c` (MIDX recovery with tri-state return values and `SECOND_READ`-gated fallback), `midx.c`/`midx.h` (MIDX internals), `builtin/mktree.c` (leak fix in `git mktree --batch`), `odb.c`/`odb.h` (new `stale_packs_detected` flag in `struct object_database`), `packfile.c` (packfile open failure handling), and test files (`t/t3650-replay-basics.sh`, `t/t5319-multi-pack-index.sh`, `t/t5336-repack-reader-race.sh`).
- Subsystems: geometric repacking, MIDX, packed-object backend, `git replay`, `git mktree --batch`, `multi-pack-index expire`, object database core.
- New behavior: `git replay` fails gracefully with an error message when objects are unreadable; MIDX-packfile mismatches are recovered transparently by scanning packs in `find_pack_entry()` **only during `SECOND_READ`**. The recovery logic is gated by the tri-state return from `fill_midx_entry()` (`MIDX_FILL_MISS`, `MIDX_FILL_HIT`, `MIDX_FILL_OWNER_UNAVAILABLE`) and triggers when the MIDX *should* have found the object but the preferred pack is missing. The fix targets `OBJECT_INFO_QUICK` callers but also addresses a broader correctness issue. The leak in `git mktree --batch` is fixed by releasing the parsed tree buffer and its entries after use. The `stale_packs_detected` flag in patch 3/4 is intended to ensure `OBJECT_INFO_QUICK` lookups recover from vanished packfiles by forcing a rescan of the object database, but Peff's review argues this violates the `QUICK` flag's contract and may introduce unnecessary overhead. The flag is re-armed on every lookup of a vanished pack to prevent `QUICK` callers from skipping the second read.
- New symbols: `MIDX_FILL_MISS`, `MIDX_FILL_HIT`, `MIDX_FILL_OWNER_UNAVAILABLE` (enum values in `odb/source-packed.c`), `stale_packs_detected` (flag in `struct object_database`).
- No on-disk format changes.
- Test coverage: Added for the `git replay` crash scenario (patch 1/4), MIDX recovery logic (patch 4/4), `OBJECT_INFO_QUICK` readers (patch 3/4), and the `git mktree --batch` leak (patch 2/4). Tests simulate unreadable objects, MIDX-packfile mismatches, vanished packfiles, and repeated `QUICK` lookups, verifying error messages and recovery behavior. Patch 3/4's test file (`t/t5336-repack-reader-race.sh`) reproduces the race deterministically by driving a resident `git mktree --batch` process across two removal windows: one where a pack’s `.idx` is deleted before its `.pack`, and another where the `.pack` is deleted after its `.idx` was already mapped. Patch 4/4's tests in `t/t5319-multi-pack-index.sh` verify both the basic recovery scenario (an object surviving in a kept pack after its MIDX-owning pack is removed) and repeated `QUICK` lookups in a resident process, ensuring the `stale_packs_detected` flag is re-armed correctly. Peff notes that `git mktree --batch` has lacked dedicated test coverage since its introduction in 2009 (commit `f1cf2d8b14`) and suggests adding basic tests as a follow-up (`#leftoverbits`).

Open questions and loose ends:
- **Architectural debate over patch 3/4**: Peff's review challenges whether the `stale_packs_detected` flag is the correct approach for handling `OBJECT_INFO_QUICK` lookups. He argues that `git mktree --batch` is misusing the `QUICK` flag and that the patch violates its intended semantics by forcing a second read. The debate centers on whether the fix should be targeted at the caller (`git mktree --batch`) or the object database layer. Peff's latest feedback on patch 4/4 further questions whether the `stale_packs_detected` flag is still necessary now that the tri-state design is in place.
- **Race condition in patch 3/4**: Peff points out that if the `.idx` file is present but the `.pack` file vanishes, the code fails to set `stale_packs_detected`, leaving the reader in an inconsistent state. This edge case needs to be addressed.
- **Error message clarity**: The "error: packfile ... index unavailable" message is misleading when the object still exists in another pack. Peff suggests suppressing it or rewording it to better reflect the recovery mechanism.
- **Follow-up work**: The primary focus remains whether geometric repacking should adopt a grace period for redundant packfiles (per Derrick Stolee’s feedback) to reduce the race condition’s frequency and reliance on the fallback logic. This would involve modifying geometric repacking to leave redundant packfiles in place until all processes using them have finished, similar to the `multi-pack-index expire` mechanism. Elijah has acknowledged this as a worthwhile follow-up but has not proposed specific changes to the current series. Peff’s feedback adds two follow-up items: (1) adding basic test coverage for `git mktree --batch` to prevent similar leaks in the future, and (2) reconsidering the necessity of the `stale_packs_detected` flag in light of the tri-state design.
