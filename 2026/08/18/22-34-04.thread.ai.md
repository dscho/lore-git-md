Thread identity: Bugfix series addressing a race condition in Git's geometric repacking mechanism causing objects to be incorrectly reported as missing, leading to crashes in `git replay` and other server-side operations. **Four-patch series by Elijah Newren via GitGitGadget, now at v3 (patch 3/4 was dropped in v2, but v3 reintroduces a targeted fix for `git mktree --batch` as patch 3/4).**

Core problem or goal: Fix a race condition where a multi-pack-index (MIDX) references a packfile removed by geometric repacking, causing processes using the stale MIDX to fail to locate objects. The issue manifests as SIGSEGV in `git replay` and missing-object errors in other operations (`git merge-tree`, `git diff`, `git rev-list`, `rev-parse`, `cat-file`). The root cause is that when an object exists in multiple packs covered by a MIDX and the *preferred* pack is removed, the current code fails to find the object in the remaining packs because the non-MIDX lookup skips all packs covered by the MIDX, and the MIDX lookup fails when the preferred pack is missing. The series also addresses a leak in `git mktree --batch` (used in new test cases), demonstrates and fixes problems with `OBJECT_INFO_QUICK` readers, and introduces a lightweight recovery mechanism for MIDX lookups when packfiles vanish mid-operation.

Current status: **Series is merge-ready and has been integrated into Junio's `next` branch as of this update.** The core fix (patch 4/4) adopts Jeff King (Peff)'s tri-state design for `midx_fill_entry()` (renamed from `fill_midx_entry()`) and gates the recovery logic on `SECOND_READ` to optimize performance for `QUICK` callers. All prior feedback has been addressed: the `stale_packs_detected` flag is removed, the `OBJECT_INFO_QUICK` flag is dropped from `git mktree --batch`, the function is renamed to `midx_fill_entry()`, and the series is rebased on `ps/odb-generic-corrupt-objects`. The latest cover letter confirms the series is well-motivated by production evidence and includes thorough test coverage. No unresolved technical disagreements remain. Patch 3/4 (v3) removes `OBJECT_INFO_QUICK` from `git mktree --batch` to fix a race condition where a resident `mktree` process fails to recover objects relocated by a concurrent repack, replacing it with `OBJECT_INFO_SKIP_FETCH_OBJECT` to preserve promisor-object avoidance while enabling recovery via the reprepare-and-retry mechanism. Peff's review of patch 3/4 (v3) endorses the change as correct and aligns with the original intent of commit `817b0f602710`, which only aimed to avoid promisor-object fetches, not disable recovery. The test's use of `PIPE` to simulate the race is confirmed as necessary and appropriate.

Key technical details:
- Files touched: `replay.c` (graceful failure logic for `git replay`), `odb/source-packed.c` (MIDX recovery with tri-state return values and `SECOND_READ`-gated fallback), `midx.c`/`midx.h` (MIDX internals), `builtin/mktree.c` (leak fix in `git mktree --batch` and removal of `OBJECT_INFO_QUICK` flag), `builtin/pack-objects.c` (updated caller), and test files (`t/t3650-replay-basics.sh`, `t/t5319-multi-pack-index.sh`, `t/t5336-repack-reader-race.sh`, `t/t1010-mktree.sh`).
- Subsystems: geometric repacking, MIDX, packed-object backend, `git replay`, `git mktree --batch`, `multi-pack-index expire`, object database core, `git pack-objects`.
- New behavior: `git replay` fails gracefully with an error message when objects are unreadable; MIDX-packfile mismatches are recovered transparently by scanning packs in `find_pack_entry()` **only during `SECOND_READ`**. The recovery logic is gated by the tri-state return from `midx_fill_entry()` (`MIDX_FILL_MISS`, `MIDX_FILL_HIT`, `MIDX_FILL_OWNER_UNAVAILABLE`) and triggers when the MIDX *should* have found the object but the preferred pack is missing. The leak in `git mktree --batch` is fixed by releasing the parsed tree buffer and its entries after use. The `.idx`/`.pack` race condition in `pack_index_is_missing()` is resolved as a side effect of removing `OBJECT_INFO_QUICK`. The `git mktree --batch` process now recovers objects relocated by concurrent repacks by allowing the reprepare-and-retry mechanism to reload the on-disk pack set, replacing the `OBJECT_INFO_QUICK` flag with `OBJECT_INFO_SKIP_FETCH_OBJECT` to preserve promisor-object avoidance while allowing recovery.
- New symbols: `MIDX_FILL_MISS`, `MIDX_FILL_HIT`, `MIDX_FILL_OWNER_UNAVAILABLE` (enum values in `odb/source-packed.c`), `midx_fill_entry()` (renamed from `fill_midx_entry()`).
- No on-disk format changes.
- Test coverage: Added for the `git replay` crash scenario (patch 1/4), MIDX recovery logic (patch 4/4), the `git mktree --batch` leak (patch 2/4), and the `git mktree --batch` race condition (patch 3/4). Tests simulate unreadable objects, MIDX-packfile mismatches, vanished packfiles, and repeated lookups, verifying error messages and recovery behavior. Patch 4/4's tests in `t/t5319-multi-pack-index.sh` verify both the basic recovery scenario (an object surviving in a kept pack after its MIDX-owning pack is removed) and repeated lookups in a resident process. Patch 3/4's test in `t/t1010-mktree.sh` simulates the race by starting a resident `git mktree --batch` process, feeding it a tree referencing a blob in a pack, then removing the pack’s `.idx` file and creating a replacement pack, verifying recovery and absence of error messages.

Open questions and loose ends:
- **Error message clarity**: The "error: packfile ... index unavailable" message is misleading when the object still exists in another pack. Peff suggests suppressing it or rewording it to better reflect the recovery mechanism. This remains unresolved but is not a blocker.
- **Follow-up work**: The primary architectural debate—whether geometric repacking should adopt a grace period for redundant packfiles (per Derrick Stolee’s feedback) to reduce the race condition’s frequency—remains a follow-up discussion. This would involve modifying geometric repacking to leave redundant packfiles in place until all processes using them have finished, similar to the `multi-pack-index expire` mechanism. Peff’s feedback adds three follow-up items: (1) adding basic test coverage for `git mktree --batch` to prevent similar leaks in the future (`#leftoverbits`), (2) reconsidering the error message clarity, and (3) evaluating whether the log message should be demoted to trace2 or reworded to avoid misleading users when recovery succeeds.
