Thread identity: Bugfix series addressing a race condition in Git's geometric repacking mechanism causing objects to be incorrectly reported as missing, leading to crashes in `git replay`. Two-patch series by Elijah Newren via GitGitGadget.

Core problem or goal: Fix a race condition where a multi-pack-index (MIDX) references a packfile removed by geometric repacking, causing processes using the stale MIDX to fail to locate objects. The issue manifests as a SIGSEGV in `git replay` and missing-object errors in other server-side operations (`git merge-tree`, `git diff`, `git rev-list`, `rev-parse`, `cat-file`). Patch 1/2 ensures `git replay` fails gracefully when merge inputs are unreadable, while patch 2/2 modifies the packed-object backend to recover from MIDX-packfile mismatches by scanning all packs covered by the MIDX when the normal lookup fails.

Current status: **Under active design discussion.** The series was previously considered ready for integration after Junio C Hamano and Patrick Steinhardt provided **substantive** reviews with no remaining technical objections. However, Jeff King (Peff) has raised a **substantive** architectural critique of patch 2/2, proposing an alternative design where the packed-object backend returns a tri-state value from `fill_midx_entry()` to distinguish between (1) the object not being in the MIDX, (2) the object being in the MIDX but unavailable (e.g., due to a missing packfile), and (3) the object being available. This would shift responsibility for handling case (2) to callers, rather than embedding recovery logic in the backend. Peff also questions the broader necessity of the fix, noting that `is_pack_valid()` already handles similar race conditions for regular packfiles and that `OBJECT_INFO_QUICK` callers are expected to tolerate false negatives. The discussion now centers on whether the backend should be made more resilient to transient failures (Elijah’s approach) or whether callers should avoid `OBJECT_INFO_QUICK` if they cannot tolerate missing objects (Peff’s preference). Junio’s earlier procedural question about the redundant test check in patch 1/2 remains resolved (either Elijah or Junio can remove it during integration). The series remains a high-priority candidate for merging, but the outcome of the design discussion may require revisions to patch 2/2.

Key technical details:
- Files touched: `replay.c` (graceful failure logic), `odb/source-packed.c` (MIDX recovery), and test files (`t/t3650-replay-basics.sh` for patch 1/2, `t/t5319-multi-pack-index.sh` for patch 2/2).
- Subsystems: geometric repacking, MIDX, packed-object backend, `git replay`.
- New behavior: `git replay` now fails gracefully with an error message when objects are unreadable; MIDX-packfile mismatches are recovered transparently by scanning all packs covered by the MIDX in `find_pack_entry()`. The recovery logic is gated by the presence of a stale MIDX and only triggers when the MIDX *should* have found the object but didn’t. The fix is specifically targeted at `OBJECT_INFO_QUICK` callers, which would otherwise fail permanently.
- New symbols: None (logic-only changes).
- No on-disk format changes.
- Test coverage: Added for both the `git replay` crash scenario (patch 1/2) and MIDX recovery logic (patch 2/2). Tests simulate unreadable objects and MIDX-packfile mismatches, verifying error messages and recovery behavior. The redundant `test_grep` check in patch 1/2's test was removed as part of the review process.
- Peff’s critique highlights that `OBJECT_INFO_QUICK` is explicitly designed to allow false negatives for performance, and that `is_pack_valid()` already handles cases where the `.pack` file disappears but the `.idx` remains mmapped. He proposes a tri-state return value from `fill_midx_entry()` to allow callers to handle missing packfiles explicitly, avoiding an unnecessary `bsearch()` in the recovery path. This suggests the planned follow-up patch (addressing broader race conditions) may be less critical than initially thought.

Open questions and loose ends:
- **Design direction for patch 2/2**: Should the fix remain in the packed-object backend (Elijah’s current approach) or be moved to the caller level (Peff’s tri-state proposal)? This is the primary unresolved question and may affect the scope of Elijah’s planned follow-up work.
- **Necessity of the fix**: Peff’s feedback suggests the fix may be less urgent than initially thought, as `OBJECT_INFO_QUICK` callers are already expected to tolerate false negatives, and `is_pack_valid()` handles similar race conditions for regular packfiles. The discussion may lead to a narrower scope for the fix or a reevaluation of the planned follow-up patches.
