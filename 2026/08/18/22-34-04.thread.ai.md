Thread identity: Bugfix series addressing a race condition in Git's geometric repacking mechanism causing objects to be incorrectly reported as missing, leading to crashes in `git replay`. Two-patch series by Elijah Newren via GitGitGadget.

Core problem or goal: Fix a race condition where a multi-pack-index (MIDX) references a packfile removed by geometric repacking, causing processes using the stale MIDX to fail to locate objects. The issue manifests as a SIGSEGV in `git replay` and missing-object errors in other server-side operations (`git merge-tree`, `git diff`, `git rev-list`, `rev-parse`, `cat-file`). The root cause is that when an object exists in multiple packs covered by a MIDX and the *preferred* pack (the one the MIDX would normally use) is removed, the current code fails to find the object in the remaining packs because the non-MIDX lookup skips all packs covered by the MIDX, and the MIDX lookup fails when the preferred pack is missing. This results in a false negative affecting *all* object lookups, not just those using `OBJECT_INFO_QUICK`. Patch 1/2 ensures `git replay` fails gracefully when merge inputs are unreadable, while patch 2/2 modifies the packed-object backend to recover from MIDX-packfile mismatches by scanning all packs covered by the MIDX when the normal lookup fails.

Current status: **Under active design discussion.** The series was previously considered ready for integration after Junio C Hamano and Patrick Steinhardt provided **substantive** reviews with no remaining technical objections. Jeff King (Peff) then raised a **substantive** architectural critique of patch 2/2, proposing an alternative tri-state design where `fill_midx_entry()` returns a tri-state value to distinguish between (1) the object not being in the MIDX, (2) the object being in the MIDX but unavailable (e.g., due to a missing packfile), and (3) the object being available. This would shift responsibility for handling case (2) to callers, rather than embedding recovery logic in the backend. Patrick Steinhardt has now clarified that the fix addresses a **separate, more fundamental bug** affecting all object lookups, not just `OBJECT_INFO_QUICK` callers, and proposed a refined approach that aligns with Peff’s tri-state suggestion: scanning only the packs covered by the MIDX when the preferred pack is missing, avoiding the performance penalty of a full pack scan while preserving correctness. The series remains a high-priority candidate for merging, but the outcome of the design discussion may require revisions to patch 2/2.

Key technical details:
- Files touched: `replay.c` (graceful failure logic), `odb/source-packed.c` (MIDX recovery), and test files (`t/t3650-replay-basics.sh` for patch 1/2, `t/t5319-multi-pack-index.sh` for patch 2/2).
- Subsystems: geometric repacking, MIDX, packed-object backend, `git replay`.
- New behavior: `git replay` now fails gracefully with an error message when objects are unreadable; MIDX-packfile mismatches are recovered transparently by scanning all packs covered by the MIDX in `find_pack_entry()`. The recovery logic is gated by the presence of a stale MIDX and only triggers when the MIDX *should* have found the object but didn’t. The fix is specifically targeted at `OBJECT_INFO_QUICK` callers but also addresses a correctness issue affecting all object lookups.
- New symbols: None (logic-only changes).
- No on-disk format changes.
- Test coverage: Added for both the `git replay` crash scenario (patch 1/2) and MIDX recovery logic (patch 2/2). Tests simulate unreadable objects and MIDX-packfile mismatches, verifying error messages and recovery behavior. The redundant `test_grep` check in patch 1/2's test was removed as part of the review process.
- The central functions under discussion are `find_pack_entry()` in `odb/source-packed.c` and the `fill_midx_entry()` helper. The proposed tri-state design would modify `fill_midx_entry()` to return a tri-state value, while the current approach embeds recovery logic in `find_pack_entry()`.
