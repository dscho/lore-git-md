Thread identity: Bugfix series addressing a race condition in Git's geometric repacking mechanism causing objects to be incorrectly reported as missing, leading to crashes in `git replay`. Two-patch series by Elijah Newren via GitGitGadget.

Core problem or goal: Fix a race condition where a multi-pack-index (MIDX) references a packfile removed by geometric repacking, causing processes using the stale MIDX to fail to locate objects. The issue manifests as a SIGSEGV in `git replay` and missing-object errors in other server-side operations (`git merge-tree`, `git diff`, `git rev-list`, `rev-parse`, `cat-file`). The root cause is that when an object exists in multiple packs covered by a MIDX and the *preferred* pack (the one the MIDX would normally use) is removed, the current code fails to find the object in the remaining packs because the non-MIDX lookup skips all packs covered by the MIDX, and the MIDX lookup fails when the preferred pack is missing. This results in a false negative affecting *all* object lookups, not just those using `OBJECT_INFO_QUICK`. Patch 1/2 ensures `git replay` fails gracefully when merge inputs are unreadable, while patch 2/2 modifies the packed-object backend to recover from MIDX-packfile mismatches by scanning all packs covered by the MIDX when the normal lookup fails.

Current status: **Under active design discussion.** The series remains a high-priority candidate for merging, but the architectural debate over patch 2/2’s implementation continues. The fix’s necessity is widely accepted, but the performance implications of the fallback logic—particularly the conditions under which it triggers—are still being refined. Junio C Hamano and Patrick Steinhardt have provided **substantive** reviews with no remaining technical objections to the core fix, while Jeff King (Peff) and Derrick Stolee have raised **substantive** architectural and deployment-level concerns. The latest exchange between Peff and Patrick clarifies that the bug affects *all* object lookups, not just `OBJECT_INFO_QUICK` callers, and that the fallback logic is only invoked when the MIDX *should* have found the object (due to the `bsearch()` check). Peff’s performance concern has evolved into a debate over whether the recovery logic should be tied to the `SECOND_READ` phase (Peff’s preference) or remain as currently implemented (triggering on any lookup failure). Peff’s latest email notes that reverse-mtime sorting in `SECOND_READ` ensures newer packs (not covered by the MIDX) are prioritized, limiting the fallback’s overhead to cases where the object is *not* in a newer pack—i.e., when it truly requires scanning the MIDX-covered packs to recover from the race condition. Derrick Stolee’s feedback introduces a new dimension: the existing `git multi-pack-index expire` mechanism already mitigates similar races by leaving redundant packfiles in place until all processes using them have finished, a design critical for Windows stability. Stolee suggests geometric repacking could adopt a similar approach to reduce reliance on the fallback logic. The discussion now centers on optimizing the scan order, timing, and interaction with existing mechanisms to balance correctness, performance, and operational simplicity.

Key technical details:
- Files touched: `replay.c` (graceful failure logic), `odb/source-packed.c` (MIDX recovery), and test files (`t/t3650-replay-basics.sh` for patch 1/2, `t/t5319-multi-pack-index.sh` for patch 2/2).
- Subsystems: geometric repacking, MIDX, packed-object backend, `git replay`, `multi-pack-index expire`.
- New behavior: `git replay` now fails gracefully with an error message when objects are unreadable; MIDX-packfile mismatches are recovered transparently by scanning packs in `find_pack_entry()`. The recovery logic is gated by the presence of a stale MIDX and only triggers when the MIDX *should* have found the object but didn’t. The fix targets `OBJECT_INFO_QUICK` callers but also addresses a broader correctness issue.
- New symbols: None (logic-only changes).
- No on-disk format changes.
- Test coverage: Added for both the `git replay` crash scenario (patch 1/2) and MIDX recovery logic (patch 2/2). Tests simulate unreadable objects and MIDX-packfile mismatches, verifying error messages and recovery behavior. The redundant `test_grep` check in patch 1/2's test was removed as part of the review process.
- The central functions under discussion are `find_pack_entry()` in `odb/source-packed.c` and the `fill_midx_entry()` helper. The current approach embeds recovery logic in `find_pack_entry()`, while Peff’s tri-state proposal would modify `fill_midx_entry()` to return a tri-state value (not found / found but unavailable / found and available) and shift responsibility for handling missing packfiles to callers. Patrick’s refinement suggests scanning only the packs covered by the MIDX when the preferred pack is missing, while Peff’s latest suggestion ties the fallback to `SECOND_READ` to optimize performance for `QUICK` callers. Peff’s latest email clarifies that reverse-mtime sorting in `SECOND_READ` ensures newer packs (not covered by the MIDX) are prioritized, limiting the fallback’s overhead to cases where the object is only in MIDX-covered packs. Stolee’s feedback highlights the existing `multi-pack-index expire` mechanism as a complementary strategy to reduce the frequency of the race condition by deferring packfile deletion until all processes have finished using them.

The debate now focuses on whether to trigger the fallback during the first pass or defer it to `SECOND_READ`, and how to reconcile this with Stolee’s suggestion to reduce the race condition’s frequency by deferring packfile deletion.
