Thread identity: Bugfix series addressing a race condition in Git's geometric repacking mechanism causing objects to be incorrectly reported as missing, leading to crashes in `git replay` and other server-side operations. **Four-patch series by Elijah Newren via GitGitGadget, now at v2.**

Core problem or goal: Fix a race condition where a multi-pack-index (MIDX) references a packfile removed by geometric repacking, causing processes using the stale MIDX to fail to locate objects. The issue manifests as SIGSEGV in `git replay` and missing-object errors in other operations (`git merge-tree`, `git diff`, `git rev-list`, `rev-parse`, `cat-file`). The root cause is that when an object exists in multiple packs covered by a MIDX and the *preferred* pack is removed, the current code fails to find the object in the remaining packs because the non-MIDX lookup skips all packs covered by the MIDX, and the MIDX lookup fails when the preferred pack is missing. The series also addresses a leak in `git mktree --batch` (used in new test cases), demonstrates and fixes problems with `OBJECT_INFO_QUICK` readers, and introduces a lightweight recovery mechanism for `OBJECT_INFO_QUICK` lookups when packfiles vanish mid-operation.

Current status: **Series ready for merging.** The core fix (patch 4/4) has adopted Jeff King (Peff)'s tri-state design for `fill_midx_entry()` and gates the recovery logic on `SECOND_READ` to optimize performance for `QUICK` callers. The tri-state return values (`MIDX_FILL_MISS`, `MIDX_FILL_HIT`, `MIDX_FILL_OWNER_UNAVAILABLE`) distinguish between objects absent from the MIDX, those present but with an unavailable owning pack, and successful lookups. The recovery logic scans MIDX-covered packs only during the second read, ensuring objects relocated into new (non-covered) packs are found by the regular fallback, while genuine hidden duplicates are recovered transparently. Patch 3/4 (v2) introduces a `stale_packs_detected` flag in `struct object_database` to address `OBJECT_INFO_QUICK` lookups, forcing a rescan of the object database when a packfile vanishes mid-lookup. The flag is set when `open_pack_index()`, `open_packed_git_1()`, or `prepare_midx_pack()` fails due to missing files, and triggers a second read in `odb_read_object_info_extended()` even for `QUICK` lookups. The flag is re-armed on every lookup of a vanished pack (per the new email) to prevent `QUICK` callers from skipping the second read, and is cleared during the reprepare, limiting overhead to rare cases. Patch 1/4 (v2) addresses Junio's feedback by removing a redundant `test_grep` check and is now uncontroversial. Patch 2/4 (v2) fixes a memory leak in `git mktree --batch` by freeing the entry buffer and its contents before reuse. The series is rebased on `ps/odb-generic-corrupt-objects`, resolving a minor conflict. No remaining technical objections; the series is a high-priority candidate for merging.

Key technical details:
- Files touched: `replay.c` (graceful failure logic for `git replay`), `odb/source-packed.c` (MIDX recovery with tri-state return values and `SECOND_READ`-gated fallback), `midx.c`/`midx.h` (MIDX internals), `builtin/mktree.c` (leak fix in `git mktree --batch`), `odb.c`/`odb.h` (new `stale_packs_detected` flag in `struct object_database`), `packfile.c` (packfile open failure handling), and test files (`t/t3650-replay-basics.sh`, `t/t5319-multi-pack-index.sh`, `t/t5336-repack-reader-race.sh`).
- Subsystems: geometric repacking, MIDX, packed-object backend, `git replay`, `git mktree --batch`, `multi-pack-index expire`, object database core.
- New behavior: `git replay` fails gracefully with an error message when objects are unreadable; MIDX-packfile mismatches are recovered transparently by scanning packs in `find_pack_entry()` **only during `SECOND_READ`**. The recovery logic is gated by the tri-state return from `fill_midx_entry()` and triggers when the MIDX *should* have found the object but the preferred pack is missing (`MIDX_FILL_OWNER_UNAVAILABLE`). The fix targets `OBJECT_INFO_QUICK` callers but also addresses a broader correctness issue. The leak in `git mktree --batch` is fixed by releasing the parsed tree buffer and its entries after use. The `stale_packs_detected` flag ensures `OBJECT_INFO_QUICK` lookups recover from vanished packfiles by forcing a rescan of the object database, preserving speed for genuine misses while ensuring correctness. The flag is re-armed on every lookup of a vanished pack to prevent `QUICK` callers from skipping the second read.
- New symbols: `MIDX_FILL_MISS`, `MIDX_FILL_HIT`, `MIDX_FILL_OWNER_UNAVAILABLE` (enum values in `odb/source-packed.c`), `stale_packs_detected` (flag in `struct object_database`).
- No on-disk format changes.
- Test coverage: Added for the `git replay` crash scenario (patch 1/4), MIDX recovery logic (patch 4/4), `OBJECT_INFO_QUICK` readers (patch 3/4), and the `git mktree --batch` leak (patch 2/4). Tests simulate unreadable objects, MIDX-packfile mismatches, vanished packfiles, and repeated `QUICK` lookups, verifying error messages and recovery behavior. The redundant `test_grep` check in patch 1/4's test was removed in v2. Patch 3/4's test file (`t/t5336-repack-reader-race.sh`) reproduces the race deterministically by driving a resident `git mktree --batch` process across two removal windows: one where a pack’s `.idx` is deleted before its `.pack`, and another where the `.pack` is deleted after its `.idx` was already mapped. Patch 4/4's tests in `t/t5319-multi-pack-index.sh` verify both the basic recovery scenario (an object surviving in a kept pack after its MIDX-owning pack is removed) and repeated `QUICK` lookups in a resident process, ensuring the `stale_packs_detected` flag is re-armed correctly.

Open questions and loose ends:
- **Follow-up work**: The primary focus is whether geometric repacking should adopt a grace period for redundant packfiles (per Derrick Stolee’s feedback) to reduce the race condition’s frequency and reliance on the fallback logic. This would involve modifying geometric repacking to leave redundant packfiles in place until all processes using them have finished, similar to the `multi-pack-index expire` mechanism. Elijah has acknowledged this as a worthwhile follow-up but has not proposed specific changes to the current series. The two approaches are complementary: `expire` would minimize the race’s occurrence, while the fallback logic ensures correctness when the race does happen. Additional follow-up patches may address other race-condition scenarios, potentially leveraging the tri-state API and `SECOND_READ`-gated fallback.
