# Git mailing list daily digest for 2026/08/18

## The day in brief

The Git mailing list saw active discussion on several fronts today. A long-running zsh completion bugfix reached readiness, while a security feature for OCSP staple validation cleared its final documentation hurdle. Maintainer feedback on ODB refactoring raised design questions about error signaling conventions, and a new `report` hook for `git-receive-pack` sparked debate about its bidirectional filtering semantics. Two bugfix series—one addressing a geometric repacking race condition and another fixing a SIGSEGV in `git replay`—were posted, both with strong production motivation.

## Notable threads

### zsh completion bugfix reaches readiness
The v2 patch fixing zsh completion for `git -C <path> <command>` is now effectively unblocked after all substantive feedback was addressed. D. Ben Knoble confirmed the patch works as intended and accepted the deferral of remaining gaps (chained `-C` completion and the unrelated `git -<tab>` bug). Lutz Lengemann confirmed the patch is ready and has been updated in the GitGitGadget PR. The fix aligns zsh completion with the bash implementation by scanning past all global options to set `__git_cmd_idx`, ensuring completions work for constructs like `git -p checkout <TAB>`. The patch touches only `contrib/completion/git-completion.zsh` and is purely a shell-script behavior change with no on-disk format or CLI impact.

### OCSP staple validation clears final documentation hurdle
The `http.sslVerifyStatus` security feature, which enables OCSP staple validation via libcurl, is now technically complete and ready for `next` after addressing all review feedback. Grayson Gordon submitted v6 with Junio C Hamano’s requested documentation tweak, rephrasing the `http.sslVerifyStatus` description to focus on the user-facing outcome ("prevents connections to servers with revoked certificates") rather than technical jargon. The feature closes a security gap where Git ignores stapled OCSP responses, which is particularly relevant for government and FIPS-compliant deployments (e.g., US DoD PKI) that mandate stapling. The default remains `false` to preserve compatibility, but the fail-closed behavior when enabled ensures revoked certificates are rejected. The patch touches `http.c`, `Documentation/config/http.adoc`, and `t/t5551-http-fetch-smart.sh`, where four new tests verify the fail-closed behavior and per-URL scoping.

### ODB refactoring sparks design debate
Junio C Hamano raised two unresolved design concerns in Patrick Steinhardt’s seven-patch ODB refactoring series, which aims to make corrupt-object handling consistent and backend-agnostic. The first concerns the tri-state return convention in `odb_source_read_object_info()` (zero for success, positive for missing, negative for corrupt), which Junio argues overloads positive values with "half-error" meanings and suggests using negative error codes (e.g., `-ENOENT`) for all error conditions. The second questions the granularity of the `bad_pack` logic in patch 3/7, asking whether marking an entire pack as bad upon encountering a single corrupt object is too coarse for multi-pack scenarios. Neither concern has been addressed by the author yet, leaving the series in flux. The refactoring is part of the ongoing ODB abstraction effort and touches core ODB logic, backend implementations, and related utilities like `pack-objects.c` and `midx.c`.

### `report` hook for `git-receive-pack` introduces design ambiguity
Karthik Nayak introduced a new `report` hook for `git-receive-pack` that allows server administrators to intercept and modify the status report sent back to the client. The hook receives the pkt-line encoded status report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. Junio C Hamano raised design questions about the interaction between the hook’s exit status and its stdout, noting that the current implementation discards stdout entirely if the hook exits non-zero. This behavior is not clearly documented and could surprise administrators who expect the rewritten report to be honored regardless of exit status. The hook is motivated by GitLab’s need to implement a custom multi-version concurrency control (MVCC) system, but the design ambiguity may require revisiting before integration. The patch touches `builtin/receive-pack.c`, `Documentation/githooks.adoc`, and adds a new test script (`t/t5412-report-hook.sh`) with seven test cases.

### Geometric repacking race condition fixed
Elijah Newren posted a two-patch bugfix series addressing a race condition in Git’s geometric repacking mechanism that can cause objects to be incorrectly reported as missing. The issue arises when a multi-pack-index (MIDX) references a packfile that is subsequently removed by a geometric repack, leaving processes using the stale MIDX unable to locate objects. Patch 1/2 ensures `git replay` fails gracefully when merge inputs are unreadable, while patch 2/2 modifies the packed-object backend to recover from MIDX-packfile mismatches by scanning all packs covered by the MIDX when the normal lookup fails. The series is well-motivated by production evidence and includes thorough test coverage. The patches touch `replay.c`, `odb/source-packed.c`, and test files, and are likely to be uncontroversial.

## In brief
- **[PATCH] pull: introduce `--hard` mode**: Artur Bieniek proposed a `--hard` option for `git pull` that resets the current branch to the fetched branch using `git reset --hard`. Junio C Hamano objected on principle, arguing that `git pull` should remain focused on history integration and that destructive operations should remain explicit and separate (`git fetch && git reset --hard`).
- **Feature request: line-wise file indexing**: Ernst Reissner requested line-wise file indexing in Git, citing its usefulness in Gittyup. No technical details or prior discussion were provided.
- **RFC: Scalable connectivity check for large repositories**: Kristofer Karlsson proposed a two-part optimization for `check_connected()` to make it proportional to the incoming set, targeting large repositories with frequent small pushes. The RFC seeks feedback on problem importance and design soundness.
- **[PATCH] pack-objects: add Trace2 data point for total bytes written**: Junio C Hamano suggested simplifying the byte-accumulation logic by directly accumulating `bytes_written` in the common code path using `hashfile_total(f)` plus the hash algorithm’s raw size.
- **[PATCH 0/3] convert USE_NSEC to runtime config**: Junio C Hamano identified a correctness issue in the v3 patch series: the `use_nanosec` field in `struct repo_config_values` is unconditionally defined but only initialized when `NO_NSEC` is not defined, risking uninitialized reads in `NO_NSEC` builds. He proposed unconditionally initializing it to `0` in `repo_config_values_init()`.
- **[PATCH 0/7] odb: refactor handling of corrupt objects with OBJECT_INFO_DIE_IF_CORRUPT**: Junio C Hamano pointed out a typo in patch 5/7’s commit message subject line ("signal mark objects" → "signal missing objects").
- **[RFC PATCH] config: propagate editor failure exit code**: The thread remains unresolved, with maintainer direction pending. Karthik Nayak and brian m. carlson supported propagating the editor’s exit code, while Junio C Hamano framed the decision as a trade-off between conceptual correctness and script breakage.
- **[PATCH v2] format-rev: add `--abbrev`, `--color`, and `--date`**: Kristoffer Haugsbakk posted v2 of a five-patch series adding formatting options to `git format-rev`. The v2 iteration incorporates v1 feedback, fixes a memory leak in the `--date` callback, and adds two new refactoring patches addressing assertion placement and documentation reuse. The series is uncontroversial and under review.
