This thread is about Patrick Steinhardt’s seven-patch series refactoring how Git’s object database (ODB) handles corrupt objects when the `OBJECT_INFO_DIE_IF_CORRUPT` flag is used. The goal is to make error reporting consistent across backends (packed, loose, in-memory, files) and eliminate abstraction-breaking code that reconstructs error messages after the fact. The series is under review, with no merge status reported.

Junio C Hamano has raised two design-level concerns that remain unresolved. The first is the tri-state return convention in `odb_source_read_object_info()`—zero for success, positive one for missing objects, and negative for corruption—which Junio argues overloads the error-signaling mechanism. He suggests using negative error codes (like `-ENOENT`) for all error conditions instead. This concern resurfaced in his review of patch 4/7, where he reiterated that the loose backend’s use of `ret = 1` for missing objects could be confusing. The second concern is whether patch 3/7’s logic for marking an entire pack as "bad" upon encountering a single corrupt object is too coarse for multi-pack scenarios. Patrick has not yet responded to either point.

The series touches core ODB internals, including `odb.c`, `odb/source-*.c`, `packfile.c`, and `midx.c`, and introduces backend-specific error messages via a new `errmsg` parameter. No user-facing changes or on-disk format modifications are involved. Testing includes updates to `t1060-object-corruption.sh` and unit tests. The discussion is still focused on design trade-offs rather than implementation bugs, so expect a v2 if Patrick revises the return-value convention or the `bad_pack` logic.
