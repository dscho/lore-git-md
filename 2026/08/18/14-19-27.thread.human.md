This thread is about Patrick Steinhardt’s seven-patch series that refactors how Git’s object database (ODB) handles corrupt objects when the `OBJECT_INFO_DIE_IF_CORRUPT` flag is set. The goal is to make error reporting consistent across backends (loose, packed, multi-pack-index) and remove abstraction-breaking code that reconstructs error messages after the fact.

The series is under review, with a second version expected. Junio C Hamano raised two main design concerns: first, whether the current tri-state return convention (zero for success, positive for missing objects, negative for corruption) overloads the error-signaling mechanism, and second, whether the granularity of tracking corrupt objects (per-object rather than per-pack) is sufficient for multi-pack scenarios. The latest email resolves the first concern—Patrick has agreed to formalize the return convention using an enum and adopt negative error codes (like `-ENOENT`) for all error conditions, including missing objects. The second concern about granularity remains open, though Patrick clarified earlier that the series does not mark entire packs as bad, only specific objects.

Key technical changes include extending `odb_source_read_object_info()` to distinguish between missing and corrupt objects, propagating backend-specific error messages to the ODB layer, and removing the `has_packed_and_bad()` function. The loose backend no longer dies unconditionally on corruption; instead, the ODB layer decides whether to die based on the flag and available good copies. Tests were updated to verify the new behavior, including a case where a corrupted loose commit can still be read from an alternate repository. No user-facing changes or on-disk format modifications are involved.

The only remaining loose end is Junio’s question about whether object-level granularity is sufficient for multi-pack scenarios. Otherwise, the series is converging, with Patrick addressing feedback and preparing a v2.
