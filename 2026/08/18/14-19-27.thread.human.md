This thread is a seven-patch series from Patrick Steinhardt refactoring Git’s object database (ODB) subsystem to handle corrupt objects more consistently when the `OBJECT_INFO_DIE_IF_CORRUPT` flag is used. The goal is to make error reporting backend-agnostic, ensuring that corrupt objects are reported uniformly regardless of the storage backend (loose, packed, or multi-pack index). The series introduces a tri-state return convention for `odb_source_read_object_info()` (zero for success, positive for missing objects, negative for corruption) and propagates backend-specific error messages to the ODB layer.

Junio C Hamano has raised two unresolved design concerns. First, he argues that using a positive return value (1) to signal missing objects overloads the error-signaling mechanism and suggests negative error codes (e.g., `-ENOENT`) instead. Second, he questions whether marking an entire pack as bad upon encountering a single corrupt object is too coarse for multi-pack scenarios. Neither concern has been addressed by Patrick yet. The series is still under review, with no merge status reported.

The latest email is a minor correction from Junio, fixing a typo in the commit message of patch 5/7 ("signal mark objects" → "signal missing objects"). This is purely editorial and doesn’t advance the technical discussion. The key open questions remain the return convention and the `bad_pack` logic granularity. No other participants have weighed in on the design concerns so far.
