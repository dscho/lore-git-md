This thread is about Patrick Steinhardt’s seven-patch series to refactor how Git’s object database (ODB) handles corrupt objects when the `OBJECT_INFO_DIE_IF_CORRUPT` flag is used. The goal is to make error reporting consistent across backends and remove abstraction-breaking code that reconstructs error messages after the fact. The series is now in its second version, addressing Junio C Hamano’s feedback on return conventions and error propagation.

The key changes include formalizing a tri-state return convention with `enum odb_read_status` (success, error, or not found), introducing an `errmsg` parameter to propagate backend-specific error messages, and removing the `has_packed_and_bad()` function to make `OBJECT_INFO_DIE_IF_CORRUPT` fully generic. The files backend now prioritizes corruption errors over "not found" errors, ensuring consistent reporting. Junio raised a latent correctness issue—if a corrupt pack contains duplicate objects, the error-reporting mechanism can’t distinguish which copy was corrupt—but this remains unresolved. Karthik Nayak reviewed the series, focusing on code clarity, particularly whether raw integers or named enum constants should be used in return statements. Patrick pushed back, calling the change unnecessary, and Karthik has now conceded the point, though the stylistic tension lingers.

The series touches multiple ODB backends (loose, packed, files, in-memory) and related subsystems like packfiles and multi-pack indexes. Tests have been updated to verify the new behavior, including a case for reading corrupted loose objects from alternates. No merge status has been reported yet, and the unresolved questions—granularity of `bad_pack` logic and enum usage style—are minor but worth noting for future reference.
