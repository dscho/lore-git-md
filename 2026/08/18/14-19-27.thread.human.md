This thread is about Patrick Steinhardt’s seven-patch series refactoring how Git’s object database (ODB) handles corrupt objects when the `OBJECT_INFO_DIE_IF_CORRUPT` flag is set. The goal is to make error reporting consistent across backends and remove abstraction-breaking code that reconstructs error messages after the fact. The series is now in its second version, addressing Junio C Hamano’s feedback on return conventions and error propagation.

The core change formalizes a tri-state return convention (`ODB_READ_OK`, `ODB_READ_ERROR`, `ODB_READ_NOT_FOUND`) for `odb_source_read_object_info()`, ensuring backends distinguish between missing and corrupt objects. The files backend now filters out “not found” errors from the packed backend, so corruption errors are never masked, and the packed backend’s corruption takes precedence when both backends fail. The final patch removes the `has_packed_and_bad()` function, making `OBJECT_INFO_DIE_IF_CORRUPT` fully generic and allowing backend-specific error messages to propagate cleanly.

Karthik Nayak and Patrick Steinhardt have resolved the last open discussion about patch 3/7’s commit message, which initially claimed “not found” errors are prioritized. The actual logic prefers *any* error (including corruption) over “not found,” and only prioritizes the packed backend’s error when both backends report non-“not found” failures. Karthik now accepts the phrasing as technically correct when read narrowly, though the exchange underscores how subtle error-handling policies can be miscommunicated. Two issues remain unresolved: a stylistic tension over enum usage in patch 2/7 (Karthik prefers named constants for clarity, while Patrick defends the established convention) and a latent correctness issue Junio identified—if a corrupt pack contains duplicate objects, the error-reporting mechanism cannot distinguish which copy was corrupt. The series is still under review, with no merge status reported.
