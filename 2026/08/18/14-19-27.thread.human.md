This thread is about Patrick Steinhardt’s seven-patch series refactoring how Git’s object database (ODB) handles corrupt objects when the `OBJECT_INFO_DIE_IF_CORRUPT` flag is set. The goal is to make error reporting consistent across backends—loose objects, packfiles, and the files backend—by letting each backend generate its own error messages and removing code that reconstructs them after the fact.

The series is now in its second version, posted after Junio C Hamano’s feedback on the return convention was addressed with a new `enum odb_read_status` that distinguishes between missing and corrupt objects. Karthik Nayak has reviewed the patches, focusing on code clarity and the error-propagation logic in the files backend. The main technical change is that `OBJECT_INFO_DIE_IF_CORRUPT` now works generically: when an object is corrupt, Git dies with the first available error message from any backend, rather than relying on the now-removed `has_packed_and_bad()` function. Tests have been updated to verify the new behavior, including a case where a corrupted loose commit can still be read from an alternate repository.

What’s still open is mostly about documentation and edge cases. Junio has pointed out a latent correctness issue: if a corrupt pack contains duplicate objects, the current logic can’t tell which copy was corrupt, which could matter if the multi-pack index (MIDX) encounters a malformed pack. Karthik has also flagged the commit message for patch 3/7 as misleading—it claims “not found” errors are prioritized, but the actual logic prefers *any* error (including corruption) over “not found” errors, and only prioritizes the packed backend’s error when both backends report non-“not found” failures. Patrick has pushed back, arguing the current wording is technically correct when read narrowly, but the exchange highlights how easily error-handling policies can be misunderstood. The series is still under review, with no merge status reported.
