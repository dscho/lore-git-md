This is the sixth patch in Patrick Steinhardt's seven-patch series refactoring how the object database (ODB) handles corrupt objects when `OBJECT_INFO_DIE_IF_CORRUPT` is used. The series is part of the ongoing ODB abstraction effort.

This patch introduces a new `errmsg` parameter to the `read_object_info()` callback in the ODB source interface. The goal is to allow backend-specific error messages to bubble up to the ODB layer rather than forcing the ODB to reconstruct them after the fact. Currently, `do_oid_object_info_extended()` uses `has_packed_and_bad()` to guess where a corrupt object might be, but this function only works for the "files" backend and breaks abstraction by reaching into packed source internals.

The patch updates the packed and loose backends to populate the `errmsg` buffer with human-readable messages when reading an object fails (e.g., "packed object X (stored in Y) is corrupt" or "loose object X (stored in Y) is corrupt"). All existing callers are adapted to pass `NULL` for now; the next patch will introduce a user of this infrastructure. The changes are mechanical but important for consistency: they ensure that error messages are generated by the backend that knows the most about the failure, rather than being reconstructed later.

Files touched include `odb/source-packed.c`, `odb/source-loose.c`, `odb/source-files.c`, `odb/source-inmemory.c`, `odb.c`, `builtin/pack-objects.c`, `packfile.c`, and the unit test `t/unit-tests/u-odb-inmemory.c`. The patch is well-scoped and appears technically sound, with clear explanations in the commit message. It lays groundwork for the final patch in the series, which will use this new error-reporting mechanism to improve user-facing messages. No new user-facing behavior is introduced yet.
