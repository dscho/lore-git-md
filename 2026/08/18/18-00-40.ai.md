This is a review reply in the ODB refactoring series targeting consistent handling of corrupt objects. Junio C Hamano engages with the design choice in patch 1/7, which formalizes a tri-state return convention for `odb_source_read_object_info()`: zero for success, positive for missing objects, and negative for corrupt ones.

The review is substantive. Junio questions whether the packed backend’s existing positive-return-for-missing behavior was a contract violation or an accidental escape hatch, and whether the new convention risks overloading positive values with too many "half-error" meanings. He suggests that distinguishing missing objects via a negative error code (e.g., `-ENOENT`) might be cleaner than using positive values, but acknowledges that the current approach is already implemented in the packed backend and thus has de facto precedent.

No resolution is reached in this email; it is a design-level discussion about error signaling in the ODB layer. The thread is still in the early review phase, with no other replies recorded.
