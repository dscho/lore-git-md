This is the second email in Patrick Steinhardt’s seven-patch ODB refactoring series, and it is a **substantive review** from Junio C Hamano. The thread is still in its early stages—no other reviews have appeared yet.

Junio’s reply questions the design choice to use positive return values for missing objects. He notes that the packed backend’s existing behavior (positive for missing, negative for corrupt) already violated the documented contract, which might have made the inconsistency easier to overlook. His concern is whether this pattern—using positive values for "non-error errors"—is the right long-term direction. He suggests that it might be cleaner to treat missing objects as a distinct *kind* of error (negative return) rather than a non-error (positive return), which would keep the return-value space more uniform and avoid introducing a new class of "half-errors."

The review does not reject the patch outright, but it does flag a foundational design question that could ripple through the rest of the series. Patrick’s original motivation—distinguishing missing from corrupt so the ODB layer can try alternate sources—is not disputed; the debate is purely about how to signal that distinction in the API. Junio’s tone is exploratory ("Do we need to support many other... values?") rather than prescriptive, leaving room for Patrick to either defend the current design or adjust it in a follow-up iteration.

For a busy reader, this exchange signals that the series is still fluid: the first patch is small and mechanical, but the underlying design is not yet settled. If the distinction between missing and corrupt objects is important to you, this thread is worth watching; if you only care about the final behavior, waiting for v2 may be more efficient.
