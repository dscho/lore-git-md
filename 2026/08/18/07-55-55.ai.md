This is a feature patch introducing a new `report` hook for `git-receive-pack`. The hook allows server administrators to intercept and modify the status report sent back to the client after reference updates but before the response is finalized. The patch is authored by Karthik Nayak, who explains in the cover text that GitLab needs this functionality to implement a custom multi-version concurrency control (MVCC) system where post-push operations determine the final status reported to the user.

The implementation adds the hook to `builtin/receive-pack.c`, where it is invoked after all ref updates are committed but before the report is sent. The hook receives the pkt-line encoded status report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. A non-zero exit status causes `receive-pack` to die, treating the push as failed (though ref changes are not rolled back). The patch includes a new test script (`t/t5412-report-hook.sh`) with seven test cases covering passthrough, failure modes, stdin/stdout handling, and sideband relay.

The hook is intentionally not integrated with the config-based hook infrastructure, as that system is designed for parallelizable notification hooks, whereas this hook is a bidirectional filter. The documentation (`githooks.adoc`) is updated to describe the hook’s behavior, including how to rewrite `ok` lines to `ng` lines to reject individual ref updates.

This is a well-motivated patch with clear use-case documentation, thorough test coverage, and a clean implementation. It targets a real gap in Git’s server-side extensibility and is likely to see adoption in hosted-Git environments. The design avoids config-based hooks for sound technical reasons, and the test suite exercises edge cases like sideband relay and non-zero exits. No prior discussion or controversy is evident from the patch itself.
