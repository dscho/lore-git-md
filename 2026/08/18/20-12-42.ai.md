This is a **documentation tweak request** from Junio C Hamano on the v5 iteration of the `http.sslVerifyStatus` security feature patch. The patch itself remains **technically complete and ready for `next`**, but Junio is asking for a clearer, more user-centric rephrasing of the `http.sslVerifyStatus` documentation in `Documentation/config/http.adoc`.

The current wording describes the feature as "fail-closed" and focuses on the technical mechanism (OCSP stapling), which Junio finds unclear for end users. His suggested alternative shifts the emphasis to the user-facing outcome: refusing connections to servers with revoked certificates. The proposed phrasing avoids jargon ("fail-closed", "OCSP stapling") and instead explains the behavior in terms of what the user experiences ("refuse connecting to the server when its certificate has been revoked").

This is a **surface-level review**—it does not question the feature’s design, implementation, or motivation, nor does it introduce new technical requirements. The change is purely about improving the documentation’s clarity and accessibility. The author has already addressed all prior substantive feedback (error message improvements, test coverage, backend parity notes), and this is the final polishing step before the patch graduates to `next`. No further review from Patrick Steinhardt or other participants is expected, as the remaining open question (whether to include a positive test case) was deferred to maintainer discretion.

The patch’s core value remains unchanged: it closes a security gap where Git ignores OCSP staples, which is particularly relevant for government and FIPS-compliant deployments (e.g., US DoD PKI) that mandate stapling. The default (`false`) preserves compatibility, while the fail-closed behavior when enabled ensures revoked certificates are rejected. This tweak is unlikely to delay merging, as it is a minor wording adjustment rather than a technical revision.
