This is a **substantive review** of the v4 patch adding `http.sslVerifyStatus` to enable OCSP staple validation in Git’s HTTPS transport. The patch itself was accepted by Junio and is queued for integration, but Patrick Steinhardt raises several technical points that refine its implementation and documentation.

Patrick’s review focuses on three areas. First, he corrects the commit message’s claim about GnuTLS behavior: newer versions of GnuTLS (3.8+) and libcurl (8.10+) now handle OCSP stapling identically to OpenSSL, so the backend-specific differences described in the documentation are no longer accurate. He suggests rewording the documentation to reflect this convergence and possibly converting the backend-specific notes into a bulleted list for future extensibility. He also asks whether other TLS backends (like mbedTLS) behave similarly or if they fail outright.

Second, Patrick proposes improving the error message when `CURLOPT_SSL_VERIFYSTATUS` fails by including the specific libcurl error via `curl_easy_strerror()`. This would make the failure reason clearer to users, especially in cases where the backend lacks support for staple validation.

Finally, he requests additional test coverage: specifically, tests that verify the feature works as expected when a server *does* provide a valid OCSP staple. The current tests only cover the fail-closed path (missing staple) and per-URL overrides, but not the success case where a staple is present and accepted.

The review is constructive and targets edge cases rather than the core design. The author’s response to earlier feedback (e.g., providing concrete evidence for the feature’s necessity in government/FIPS deployments) has already addressed the main substantive concerns, so these suggestions are refinements rather than blockers. The patch remains on track for integration, but the author may want to incorporate these improvements in a follow-up iteration.
