This is the third patch in Patrick Steinhardt's seven-patch series refactoring how the object database (ODB) handles corrupt objects when `OBJECT_INFO_DIE_IF_CORRUPT` is used. The series is part of the ongoing ODB abstraction effort to make Git's object storage layer more modular and backend-agnostic.

This patch addresses a specific inconsistency in the packed-object backend: when an object is already marked as corrupt in a packfile, `find_pack_entry()` currently reports it as missing rather than corrupt. This breaks the abstraction established in earlier patches, where `odb_source_read_object_info()` is supposed to distinguish between missing (positive return) and corrupt (negative return) objects. The fix propagates corruption status up through the call stack, ensuring that known-bad objects are correctly flagged as corrupt rather than missing.

Key changes include:
- Modifying `find_pack_entry()` and its callers (`fill_midx_entry()`, `packfile_fill_entry()`) to accept an optional `struct packed_git **bad_pack` parameter, which is populated when an object is found to be corrupt.
- Updating `odb_source_packed_read_object_info()` to check for corruption status and return `-1` (corrupt) instead of `1` (missing) when a known-bad object is encountered.
- Mechanical updates to all call sites of `find_pack_entry()`, `fill_midx_entry()`, and `packfile_fill_entry()` to pass the new parameter (or `NULL` where the information isn't needed).

The patch touches seven files: `odb/source-packed.c`, `midx.c`, `midx.h`, `packfile.c`, `packfile.h`, `builtin/pack-objects.c`, and `t/helper/test-read-midx.c`. The changes are confined to the ODB subsystem and do not introduce new user-facing behavior. The motivation is clear: maintain consistency in how corrupt objects are reported across backends, which is critical for the ODB abstraction effort.

The patch appears well-structured and technically sound. It builds directly on the contract established in patch 1/7 and aligns with the series' goal of making error handling backend-agnostic. The inclusion of the `bad_pack` parameter (even though it's unused in this patch) suggests forward planning for future work, likely in a subsequent patch in the series. No test failures or edge cases are introduced here, but the changes are subtle enough that thorough review of the call sites would be prudent.
