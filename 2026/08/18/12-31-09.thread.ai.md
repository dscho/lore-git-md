Thread identity
Subject: RFC: Scalable connectivity check for large repositories
Series version: RFC (no patches yet)
Originating author: Kristofer Karlsson <krka@spotify.com>
Thread type: RFC / design discussion

Core problem or goal
Git’s current `check_connected()` function (used by `fetch` and `receive-pack`) verifies that every object reachable from the incoming commits is already present in the local repository by running `rev-list --objects --stdin --not --all --quiet`. In large repositories this traversal scales with the *entire* repository size rather than the size of the incoming change, creating unnecessary overhead for frequent small pushes. The goal is to make the check proportional to the incoming set while preserving correctness.

Current status
No patches posted; the thread is an RFC seeking feedback on whether the problem is worth solving and whether the proposed two-part optimization is sound.

Key technical details
- Function: `check_connected()` (called by `fetch` and `receive-pack`)
- Subsystems: connectivity check, object traversal, ref backend
- New behavior (proposed):
  1. “Opportunistic trusted-tree discovery” – replace eager traversal of boundary commits’ tree closures with a lazy, parent-diff-based cache that verifies only changed entries, pruning subtrees whose contents match a trusted parent.
  2. “Finding the boundary” – avoid the full `--not --all` traversal by seeding the walk with a small set of likely-useful refs (e.g., old values of updated refs) and imposing a bounded walk budget; if the boundary is closed within the budget, the check succeeds; otherwise, fall back to the current `rev-list` path.
- Old behavior: full `rev-list --objects --stdin --not --all --quiet` traversal.
- Edge cases (shallow clones, promisor remotes, replace objects, tree tips) are handled by falling back to the existing code path.
- Performance: preliminary numbers on a 3 M-commit, 200 K-ref repository show 30–150× speed-up for small pushes (5 commits, 45 changed files → 30 ms vs. 1 s; 1-commit trivial change → 7 ms vs. 1 s).

Open questions and loose ends
- Is the problem worth solving?
- Is the proposed direction sound?
- Are there additional edge cases that would force a fallback to the current implementation?
- How should the walk budget be sized and exposed (config knob, hard-coded, auto-tuned)?
