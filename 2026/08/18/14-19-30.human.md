This is the third patch in Patrick Steinhardt’s seven-patch series refactoring how the object database (ODB) handles corrupt objects when `OBJECT_INFO_DIE_IF_CORRUPT` is used. The series is part of the ongoing ODB abstraction effort to make Git’s object storage layer more modular and backend-agnostic.

This patch specifically addresses a correctness issue in the packed-object backend. Currently, if an object is already marked as corrupt in a packfile, subsequent lookups via `find_pack_entry()` incorrectly report it as missing rather than corrupt. The patch fixes this by propagating the "corrupt" status up through the call stack, ensuring that corrupt objects are consistently flagged as such rather than as missing. The change is mechanical but important: it aligns the packed backend with the new contract established in patch 1/7, where `odb_source_read_object_info()` must distinguish between missing (positive return) and corrupt (negative return) objects.

The patch touches seven files, including core ODB logic (`odb/source-packed.c`), multi-pack-index handling (`midx.c`), and packfile utilities (`packfile.c`). It modifies `find_pack_entry()` and related functions to accept an optional `struct packed_git **bad_pack` parameter, which is used to bubble up which packfile contains the corrupt object. While the patch doesn’t yet use this information (it’s reserved for a later patch in the series), the change is forward-looking and avoids a second refactoring pass.

The commit message is clear and well-motivated, explaining both the problem (corrupt objects being misreported as missing) and the solution (propagating corruption status). The patch includes no new user-facing behavior or options, and the on-disk format remains unchanged. Test coverage is not directly updated in this patch, but the changes are exercised by existing tests in `t1060-object-corruption.sh` and the broader ODB test suite.

This looks like a solid, well-crafted patch that addresses a real correctness issue. It’s narrowly scoped to the packed backend and doesn’t introduce controversy or complexity. If the rest of the series holds up to review, this patch is likely to be uncontroversial and mergeable.
