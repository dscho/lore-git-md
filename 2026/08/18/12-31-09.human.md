This is an RFC proposing a performance optimization for Git’s connectivity check (`check_connected()`), which is used during fetches and pushes. The author, Kristofer Karlsson, argues that the current implementation scales poorly with repository size—especially for servers with many refs or frequent pushes—because it performs work proportional to the *entire* repository rather than just the incoming changes.

The core idea is to split the connectivity check into two phases and optimize each independently. First, the author proposes an "opportunistic trusted-tree discovery" heuristic to avoid re-verifying objects that are already known to be trusted (e.g., unchanged subtrees shared with parent commits). Second, they suggest a bounded traversal to find the "boundary commits" (the edge between trusted and incoming history) without walking the entire ref set, falling back to the current method only if the boundary isn’t found quickly. Preliminary results show dramatic speedups (e.g., from 1 second to 7ms) for common push patterns like rebases or small updates.

The RFC is well-motivated and grounded in prior work (Patrick Steinhardt’s 2021 series and Justin Tobler’s `--skip-connectivity-check` option). The author acknowledges edge cases (shallow clones, promisor remotes, replace objects) and explains how their prototype handles them, though they note some scenarios (e.g., deepening fetches) still fall back to the current implementation. The tone is collaborative, inviting feedback on whether the problem is worth solving and if the direction is sound.

This looks like a serious effort to address a real pain point for large repositories. The proposed optimizations are targeted at common workflows, and the fallback mechanisms preserve correctness. If the benchmarks hold up, this could meaningfully reduce server load for high-traffic Git hosts. Worth watching for follow-up patches.
