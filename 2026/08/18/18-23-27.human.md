This is a review comment on the fourth patch in Patrick Steinhardt’s seven-patch series refactoring how the object database (ODB) handles corrupt objects. The series is part of the ongoing ODB abstraction effort to make error handling consistent and backend-agnostic.

Junio C Hamano’s feedback here is surface-level but points to a deeper design issue he raised earlier in the thread. He notes that the patch correctly changes the return value for missing objects from `-1` to `1`, aligning with the new tri-state convention (zero for success, positive for missing, negative for corrupt). However, he reiterates his concern that using a positive integer (`1`) to signal "missing" overloads the return value’s meaning and suggests replacing the raw integers with an enum (e.g., `OBJ_MISSING`, `OBJ_CORRUPT`, `OBJ_OK`) for clarity. This echoes his earlier objection to the same pattern in `odb_source_read_object_info()` and remains unresolved.

The review also approves the mechanical changes: replacing the `corrupt:` label with `out:` (since missing objects now exit through the same path) and adjusting the `die()` condition to trigger only for negative return values (corruption). These tweaks are necessary for the series’ goal of letting the ODB layer decide whether to die based on the `OBJECT_INFO_DIE_IF_CORRUPT` flag.

This patch itself is uncontroversial and looks ready to proceed, but Junio’s broader critique of the tri-state return convention casts a shadow over the entire series. Until that design question is addressed, the series may stall. For now, this is a minor adjustment to the loose backend’s error handling, but the unresolved discussion about return values could force a larger rework.
