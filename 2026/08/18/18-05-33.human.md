This is a review comment on the second patch in Patrick Steinhardt’s seven-patch series refactoring how the object database (ODB) handles corrupt objects. Junio C Hamano raises a design concern about the return-value convention introduced in patch 1/7 and applied here: the in-memory ODB source now returns `1` to signal a missing object, following the new tri-state convention (zero for success, positive for missing, negative for corrupt). Junio argues that hard-coding a positive value (`1`) is unclear and proposes replacing it with an enum that explicitly names the return states. He reiterates his preference—expressed earlier in the thread—for using negative error codes (e.g., `-ENOENT`) to signal missing objects, rather than positive values, as a cleaner and more extensible design. The comment is substantive but narrowly focused on the API design of `odb_source_read_object_info()`; it does not question the overall goal of the series or the logic of this specific patch. The discussion remains unresolved, with no indication yet of whether Patrick will revise the convention or defend the current approach.
