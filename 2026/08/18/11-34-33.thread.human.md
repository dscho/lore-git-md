This thread explores whether Git should add a `--hard` or `--reset` mode to `git pull`, allowing users to discard local state and sync to an upstream branch in one command. The discussion began with Artur Bieniek’s proposal for `git pull --hard`, which would reset the current branch, index, and working tree to the fetched branch using `git reset --hard`. After pushback from Junio C Hamano, the maintainer, the conversation shifted to a safer redesign: `git pull --reset`, which would error out by default if uncommitted changes exist, with an `--autostash` option to preserve them.

Artur now endorses Phillip Wood’s `--reset` redesign, arguing it addresses a specific workflow gap—syncing to a force-pushed or rebased upstream branch—that `git pull --ff-only` cannot handle. Junio, however, remains opposed, framing the feature as a philosophical misstep. He contends that `git pull`’s primary purpose is history integration, not working-copy management, and that users should explicitly discard local state with separate commands. His latest response dismisses the force-push/rebase use case as an anti-pattern that shouldn’t be automated, leaving the redesign’s future uncertain. Kristoffer Haugsbakk has suggested an alternative workflow (working directly with remote-tracking branches like `origin/main`), but this hasn’t gained traction yet.

The thread is at a crossroads: no updated patch has been posted, and Junio’s objections remain unaddressed. The core debate hinges on whether the force-push/rebase use case justifies the feature’s inclusion or whether it’s better handled through existing workflows. For now, the proposal remains under review, with its viability dependent on whether Junio’s stance softens or the discussion shifts to concrete technical trade-offs.
