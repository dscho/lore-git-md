This thread is about a proposed `git pull --reset` (originally `--hard`) feature to conveniently discard local state and sync to an upstream branch that may have been force-pushed or rebased. Artur Bieniek initially proposed `--hard`, but after pushback from Junio C Hamano—who opposes adding destructive operations to `git pull`—the discussion shifted to a safer redesign: `--reset` with `--discard-changes` (default, errors if uncommitted changes exist) and `--autostash` (preserves changes). Artur now endorses this redesign, arguing it addresses a real workflow gap where `git pull --ff-only` fails (force-pushed/rebased upstream branches).

Junio remains unconvinced, framing `git pull` as a tool for history integration, not working-copy management, and suggesting users should explicitly discard state with separate commands. Phillip Wood proposed the `--reset` redesign to address Junio’s safety concerns, but Junio hasn’t responded to the force-push/rebase use case or the redesign’s specifics. Kristoffer Haugsbakk recently weighed in with a surface-level critique, suggesting users could avoid the problem entirely by working directly with remote-tracking branches (e.g., `origin/main`), which update automatically during `git fetch`. This alternative hasn’t been addressed by others yet, leaving the core question—whether the use case justifies the feature—still unresolved. No updated patch has been posted, and the thread’s outcome hinges on Junio’s response to the redesign and the force-push/rebase argument.
