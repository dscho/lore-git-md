This thread proposes a new `--hard` (or `--reset`) mode for `git pull` to let users quickly discard local state and sync their working tree to an upstream branch that has been force-pushed or rebased. The idea targets users who treat their local checkout as a read-only mirror of upstream, where the only local changes are uncommitted edits that should be discarded when the upstream branch moves.

The discussion has evolved from an initial `--hard` patch to a safer `--reset` redesign (with `--discard-changes` and `--autostash` sub-options) and an alternative `git reset --pull --hard` design that moves the destructive operation to `git reset` while adding network I/O. Artur Bieniek, the author, now endorses the `--reset` redesign and has floated the `reset --pull` alternative. However, Junio C Hamano, the maintainer, remains firmly opposed, arguing that `git pull`’s primary purpose is history integration, not working-copy management, and that force-pushed or rebased upstream branches *should* require explicit user intervention rather than being automated. His latest response suggests the desired functionality belongs in a user-configured alias (e.g., `git sync = !git fetch && git reset --hard @{u}`) rather than a built-in command, framing the feature as a workflow preference rather than a missing capability.

No other substantive review feedback has emerged beyond Phillip Wood’s constructive `--reset` counterproposal and Kristoffer Haugsbakk’s suggestion to work directly with remote-tracking branches (which Artur clarified does not address the working tree update requirement). The thread is now at an impasse: Junio’s position is conceptual and unyielding, while Artur continues to argue for the feature’s practical utility. No updated patch has been posted, and the discussion’s next move rests with Artur.
