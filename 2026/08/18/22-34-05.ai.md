This is the first patch in a two-patch bugfix series addressing a race condition in Git's geometric repacking mechanism that can cause `git replay` to crash with a SIGSEGV when objects become temporarily unreadable. The issue stems from a missing check in `pick_regular_commit()` in `replay.c`, where the code only tests `if (!result->clean)` but ignores the case where `result->clean < 0` (indicating an unreadable object). This causes the merge machinery to attempt using `result->tree` when it is NULL, triggering the segfault.

The fix adds an explicit check for `result->clean < 0` and returns `NULL` with an error message, allowing `git replay` to fail gracefully instead of crashing. The patch also includes a new test in `t/t3650-replay-basics.sh` that simulates the scenario by removing the tree object for the `--onto` commit, verifying that the command fails without a segfault and that the error message includes the expected "Could not read" or "collecting merge info failed" text.

The change is minimal and targeted, touching only `replay.c` and the test file. It does not alter the root cause of the race condition (which is addressed in patch 2/2) but ensures that `git replay` behaves safely when the issue occurs. The test coverage is thorough, including setup for a three-commit replay scenario and cleanup. This patch is uncontroversial and should be a straightforward merge.
