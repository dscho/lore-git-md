Subject: [PATCH] pull: introduce `--hard` mode
Series version: v1 (initial submission, redesign proposed and now endorsed by author; alternative design floated)
Originating author: Artur Bieniek
Thread type: patch series (single patch)

Core problem or goal
Add a convenient way to discard local state and sync the working tree to an upstream branch that has been force-pushed or rebased, targeting users who have no local development (only a clean checkout of the upstream branch). The original proposal (`git pull --hard`) would reset the current branch, index, and working tree to the fetched branch using `git reset --hard`. The discussion has evolved to a safer redesign (`git pull --reset [--discard-changes | --autostash]`) that errors out by default if uncommitted changes exist, with an `--autostash` option to preserve them. A new alternative design (`git reset --pull --hard`) has been floated, which would move the destructive operation to `git reset` while adding network I/O (fetching the configured upstream). Junio C Hamano has now explicitly positioned the feature as unnecessary for core Git, suggesting it belongs in a user-configured alias instead. The core question remains whether the force-push/rebase use case justifies inclusion in Git, or whether it should be left to user workflows.

Current status
Under review; no prior versions. The original patch implements `--hard`, but the thread has shifted to a conceptual debate about the feature’s inclusion and multiple redesign proposals. Artur Bieniek now endorses Phillip Wood’s `--reset` redesign and has floated an alternative design (`git reset --pull --hard`). Junio has twice rejected the underlying motivation: first, framing `git pull`’s primary purpose as history integration, not working-copy management; and second, arguing that force-pushed or rebased upstream branches *should* require explicit user intervention rather than being automated via a convenience option. In his latest response, Junio dismisses both the original proposal and the `reset --pull` alternative, suggesting the functionality belongs in a user-configured alias (e.g., `git sync = !git fetch && git reset --hard @{u}`) rather than a built-in command. No updated patch has been posted.

Key technical details
- Files touched (original patch): `builtin/pull.c`, `Documentation/git-pull.txt`, `t/t5520-pull.sh`
- Original CLI option: `--hard` (now deprecated in favor of redesigns)
- Proposed redesign: `--reset` with sub-options `--discard-changes` (default, errors if uncommitted changes exist) and `--autostash` (stashes changes before reset, restores afterward)
- New alternative design: `git reset --pull --hard`, which would fetch the configured upstream and reset the working tree to it
- New behavior (both designs): `git fetch <remote> <branch>` followed by `git reset --hard FETCH_HEAD` (with safety checks or autostash)
- Rejects combinations with `--ff-only`, `--squash`, `--rebase`, etc.
- Preserves `--quiet` and submodule recursion settings from the pull context
- On-disk format: no changes
- Test coverage: basic usage, error conditions, submodule recursion (original patch); proposed redesigns would require additional tests for uncommitted changes, autostash behavior, and (for `reset --pull`) network I/O integration

Open questions and loose ends
- Whether the force-push/rebase use case is compelling enough to justify inclusion in Git. Junio frames this as a design philosophy question, citing `git pull --ff-only` as a sufficient alternative for syncing without integrating local changes, and now explicitly argues that the functionality should be implemented via user aliases rather than built-in commands. Artur Bieniek continues to argue that `--ff-only` cannot handle force-pushed or rebased upstream branches, and that working directly with remote-tracking branches (as suggested by Kristoffer) does not update the working tree.
- Whether Junio will accept either the `--reset` redesign or the `reset --pull` alternative, or further refine his objections. No response yet to Artur’s endorsement of the redesign, the force-push/rebase use case, or the `reset --pull` design beyond the alias suggestion.
- Whether introducing network operations into `git reset` (via `reset --pull`) would be more or less objectionable than adding destructive operations to `git pull`. Junio’s latest response does not engage with this design inversion.
- No other substantive review feedback has been posted beyond Junio’s principled opposition, Phillip’s counterproposal, Artur’s endorsement and alternative design, and Kristoffer’s workflow suggestion.

Participant positions
- Artur Bieniek (author): originally proposed `--hard` as a motivated, self-contained addition with thorough error handling and documentation. Now endorses Phillip’s `--reset` redesign and has floated an alternative design (`git reset --pull --hard`), arguing both address the core use case (syncing the working tree to a force-pushed or rebased upstream branch) while improving safety. Position remains substantive and constructive, focusing on practical utility and design trade-offs.
- Junio C Hamano (maintainer): firmly opposed to adding destructive operations to `git pull` or `git reset`, even with the proposed safety improvements. Argues the command’s primary purpose is history integration, not working-copy management, and that users should discard local state explicitly with separate commands. Now explicitly rejects the force-push/rebase use case as an anti-pattern that *should* require explicit user intervention, not automation, and suggests the functionality belongs in a user-configured alias rather than a built-in command. Position is conceptual, not technical; no engagement yet with the redesign’s specifics, the `reset --pull` alternative, or Artur’s clarification of the working tree requirement.
- Phillip Wood: proposes the `--reset` redesign (`git pull --reset [--discard-changes | --autostash]`) that directly targets Junio’s safety concerns by erroring out by default if uncommitted changes exist, with an opt-in `--autostash` option. Frames the redesign as safer than the existing `git fetch && git reset --hard @{u}` workflow while providing convenience. Position is substantive and constructive.
- Kristoffer Haugsbakk: questions the necessity of the feature by suggesting an alternative workflow (working directly with remote-tracking branches like `origin/main` instead of local branches). This sidesteps the need for `git pull --reset` entirely, as remote-tracking branches are updated automatically during `git fetch`. Position is surface-level, focusing solely on the use case’s justification rather than technical implementation or design philosophy. Also notes minor etiquette (bottom-posting). Artur has since clarified that this workflow does not address the working tree update requirement.
