Subject: [PATCH] pull: introduce `--hard` mode
Series version: v1 (initial submission)
Originating author: Artur Bieniek
Thread type: patch series (single patch)

Core problem or goal
Add a `--hard` option to `git pull` that resets the current branch, index, and working tree to the fetched branch using `git reset --hard`, discarding all local state (commits, tracked-file changes, and potentially untracked files). The proposal aims to provide a convenient shortcut for users who want to discard local changes and sync to upstream in a single command.

Current status
Under review; no prior versions. The patch implements the feature, updates `Documentation/git-pull.txt`, and adds tests in `t/t5520-pull.sh` covering basic usage, error conditions (conflicting options, multiple integration candidates), and submodule recursion behavior. Junio C Hamano has expressed a principled objection to the design, arguing that `git pull` should remain focused on history integration and that destructive operations should remain explicit and separate (`git fetch && git reset --hard`).

Key technical details
- Files touched: `builtin/pull.c`, `Documentation/git-pull.txt`, `t/t5520-pull.sh`
- New CLI option: `--hard`
- New behavior: `git pull --hard <remote> <branch>` → `git fetch <remote> <branch>` followed by `git reset --hard FETCH_HEAD`
- Rejects combinations with `--ff-only`, `--squash`, `--rebase`, etc.
- Preserves `--quiet` and submodule recursion settings from the pull context
- On-disk format: no changes
- Test coverage: basic usage, error conditions, submodule recursion

Open questions and loose ends
- Whether a destructive operation like `--hard` belongs in `git pull` or should remain a separate command sequence (`git fetch && git reset --hard`). Junio’s objection frames this as a design philosophy question rather than an implementation issue.
- No other substantive review feedback has been posted; the thread is now at a decision point awaiting the author’s response (defend the feature, propose an alternative, or abandon the effort).

Participant positions
- Artur Bieniek (author): proposes the feature as a motivated, self-contained addition with thorough error handling and documentation. Position remains unchanged.
- Junio C Hamano (maintainer): mildly but firmly opposed to adding destructive operations to `git pull`, citing the command’s primary purpose as history integration and the risk of accidental data loss. No technical review or suggested changes offered; feedback is purely conceptual.
