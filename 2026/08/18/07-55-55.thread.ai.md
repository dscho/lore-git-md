Subject: [PATCH v2] receive-pack: add new `report` hook for server-side status filtering
Series version: v2 (standalone patch)
Originating author: Karthik Nayak
Thread type: feature patch

Core problem or goal
Git’s `receive-pack` currently sends a fixed status report to the client after ref updates are committed. There is no way for server administrators to intercept or modify this report before it is finalized. The patch adds a new `report` hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status causes `receive-pack` to die, treating the push as failed (ref changes are not rolled back). The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the state of the repository after all ref updates are committed but before the client receives confirmation.

Current status
Under review; v2 posted addressing all prior feedback. The **central design question**—whether the hook should integrate with Git’s config-based hook infrastructure or remain a single-script hook modeled after `proc-receive`—has been **resolved in favor of the single-script design** and is now documented in the commit message. The **exit status semantics are now the primary unresolved issue**: Junio C Hamano has **endorsed Patrick Steinhardt’s proposal** to align the behavior with the `pre-receive` hook—rewriting all ref status lines to `"report hook failed"` and allowing `receive-pack` to exit cleanly, rather than treating a non-zero exit as a "nuclear option" (discarding stdout and causing `receive-pack` to die). Karthik Nayak has acknowledged the proposal but noted that restructuring the output logic would be "awkward." Documentation updates are complete, including the hook’s presence in `githooks.adoc` and `git-receive-pack(1)`, with the latter linking to `githooks(5)`. Minor test adjustments are complete, including verification of the "remote:" prefix on stderr. No further changes to the core implementation are expected unless the exit status semantics are revised.

Key technical details
- Files touched: `builtin/receive-pack.c`, `Documentation/githooks.adoc`, `Documentation/git-receive-pack.adoc`, `t/t5412-report-hook.sh`
- New hook name: `report`
- Invocation point: after all ref updates are committed, before the status report is sent
- Input: pkt-line encoded status report on stdin
- Output: replacement status report on stdout; stderr forwarded to client via sideband
- Exit code semantics: **proposed** non-zero exit rewrites all ref status lines to `"report hook failed"` and allows `receive-pack` to exit cleanly (Junio C Hamano and Patrick Steinhardt’s position); **current** non-zero exit discards stdout and causes `receive-pack` to die (treated as a "nuclear option" for exceptional cases)
- Hook is **NOT integrated with the config-based hook infrastructure** (deliberate choice to avoid parallelization and coordination complexity)
- Test coverage: passthrough, failure modes, stdin/stdout handling, sideband relay, and interaction between exit status and stderr output
- Documentation: The hook is documented in both `githooks.adoc` and `git-receive-pack(1)`, with the latter linking to `githooks(5)`. The commit message includes a concrete use-case example (GitLab’s MVCC system) and justifies the single-script design. Two documentation nits remain: avoiding implementation details (e.g., `execute_commands()`) in favor of behavioral descriptions (resolved), and clarifying the optional `<reason>` field in `ng` lines (including whether it requires a trailing newline, still ambiguous).

Open questions and loose ends
- **Exit status semantics**: Junio C Hamano has **endorsed Patrick Steinhardt’s proposal** to align the `report` hook’s failure mode with the `pre-receive` hook—rewriting all ref status lines to `"report hook failed"` and allowing `receive-pack` to exit cleanly. Karthik Nayak has noted that restructuring the output logic would be "awkward" but remains open to the change. This is now the **primary blocker** for the patch.
- **Documentation gap**: The `pkt-line` format documentation remains unresolved (whether to link to `gitprotocol-common.adoc` or elsewhere).
- **Documentation nit**: Clarify whether the optional `<reason>` field in `ng` lines requires a trailing newline (still ambiguous).
