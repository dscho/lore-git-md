Subject: [PATCH] receive-pack: add new `report` hook for server-side status filtering
Series version: standalone patch (no vN marker)
Originating author: Karthik Nayak
Thread type: feature patch

Core problem or goal
Git’s `receive-pack` currently sends a fixed status report to the client after ref updates are committed. There is no way for server administrators to intercept or modify this report before it is finalized. The patch adds a new `report` hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status causes `receive-pack` to die, treating the push as failed (ref changes are not rolled back). The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the state of the repository after all ref updates are committed but before the client receives confirmation.

Current status
Under review; no prior versions posted. The patch is self-contained, includes documentation (`githooks.adoc`) and a new test script (`t/t5412-report-hook.sh`) with seven test cases covering passthrough, failure modes, stdin/stdout handling, and sideband relay. Patrick Steinhardt has provided a substantive review that clarifies the hook’s necessity, tightens documentation, and raises behavioral concerns about exit status handling.

Key technical details
- Files touched: `builtin/receive-pack.c`, `Documentation/githooks.adoc`, `t/t5412-report-hook.sh`
- New hook name: `report`
- Invocation point: after all ref updates are committed, before the status report is sent
- Input: pkt-line encoded status report on stdin
- Output: replacement status report on stdout; stderr forwarded to client via sideband
- Exit code semantics: non-zero causes `receive-pack` to die, **and the hook’s stdout is discarded** (this behavior is contested; documentation does not yet clarify this)
- Hook is NOT integrated with the config-based hook infrastructure (intentionally, to avoid parallelization)
- Test coverage: passthrough, failure modes, stdin/stdout handling, sideband relay; **no test currently verifies the interaction between exit status and stdout**
- Documentation gaps: missing concrete use-case example (GitLab’s MVCC system), unclear whether `git-receive-pack(1)` should mention the hook, and no reference to `gitprotocol-v2(5)` for `pkt-line` format. Patrick Steinhardt suggests dropping the word “remote” from the hook description, clarifying that stderr forwarding depends on the client’s implementation, and documenting that a non-zero exit status should be treated as a bug rather than a normal rejection mechanism.

Open questions and loose ends
- **Design ambiguity**: Should the hook’s exit status override its stdout, or should the two signals be orthogonal? The current implementation discards stdout on non-zero exit, which Patrick Steinhardt and Junio C Hamano find surprising and potentially problematic. Patrick argues the hook should always return zero to ensure the client receives a well-formed status report, even when rejecting ref updates. No resolution yet.
- **Documentation gaps**: The patch does not explicitly state that a non-zero exit discards the rewritten report; this needs to be clarified in `githooks.adoc`. The commit message lacks a concrete use-case example (GitLab’s MVCC system), and it is unclear whether the hook should be documented in `git-receive-pack(1)` or only in `githooks(5)`. The `pkt-line` format is unexplained in the patch’s documentation. Patrick Steinhardt suggests additional clarifications: avoiding the word “remote” in the hook description, noting that stderr forwarding depends on the client’s implementation, and treating non-zero exit as a bug.
- **Test refactoring**: The test script’s repeated teardown logic (`rm -rf upstream`, `git remote remove`) may benefit from refactoring into a helper function, though this is a minor stylistic point. Patrick Steinhardt also suggests adjusting a test case to verify the “remote:” prefix appears on stderr output.
