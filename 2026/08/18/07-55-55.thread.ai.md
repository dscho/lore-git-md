Subject: [PATCH v4 0/3] receive-pack: add new `receive-report` hook for server-side status filtering
Series version: v4 (3 patches)
Originating author: Karthik Nayak
Thread type: feature patch series

Core problem or goal
Git’s `receive-pack` currently sends a fixed status report to the client after ref updates are committed. There is no way for server administrators to intercept or modify this report before it is finalized. The patch series adds a new `receive-report` hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the state of the repository after all ref updates are committed but before the client receives confirmation.

The patch is mechanical, with no behavior changes, and prepares the codebase for the hook implementation by centralizing the pkt-line formatting logic.    - Adjusting the boolean parameter name from `add_reports` to `detailed_reports` for clarity.
   No technical concerns were raised; Patrick explicitly states the patch "looks good" otherwise. **Patrick Steinhardt’s follow-up review** additionally suggests:
   - A grammatical fix in `git-receive-pack.adoc`: changing “Allowing the hook to rewrite” to “, which allows the hook to rewrite” for smoother flow.
   - A missing optional marker in `githooks.adoc`: `ng <refname> <reason>` should read `ng <refname>[ <reason>]` to match the protocol spec.
3. **Core implementation (applied)**: introduces the `receive-report` hook with the agreed-upon exit semantics. The hook runs after all ref updates are committed but before the status report is sent to the client. It receives the pkt-line encoded report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. A zero exit code means the hook’s stdout is used as the report; a non-zero exit rewrites all ref status lines to `"receive-report hook failed"` and discards the hook’s stdout, matching the behavior of the `pre-receive` hook. The implementation is self-contained and does not use the config-based hook infrastructure. **Patrick Steinhardt’s substantive review** raises two new points:
   - **Documentation of the "unpack" status line**: The current documentation lists only two ways the hook can affect the push outcome (rewrite individual refs or abort the entire push), but the protocol allows a third: the hook can change the initial `unpack ok` or `unpack <error>` line. Patrick asks whether this should be documented as a third option.
   - **Technical design of failure handling**: The new `ref_error` parameter in `generate_response()` adds a new `ng` line for every ref when the hook exits non-zero, but leaves any existing `cmd->error_string` untouched. This creates odd precedence: an explicit per-ref error is preserved even when the hook wants to signal a global failure. Patrick wonders whether it would be cleaner to overwrite all `cmd->error_string` fields instead of introducing a separate parameter. The question is left open; no code change is suggested yet.

Key technical details
- Files touched: `builtin/receive-pack.c`, `Documentation/githooks.adoc`, `Documentation/git-receive-pack.adoc`, `t/t5412-receive-report-hook.sh` (renamed from `t5412-report-hook.sh`)
- New hook name: `receive-report` (finalized; replaces the prior `report`)
- New helper function: `generate_response()` in `builtin/receive-pack.c` (extracted from `report()` and `report_v2()`; proposed rename to `generate_report()`)
- Boolean parameter: `add_reports` (proposed rename to `detailed_reports`)
- Invocation point: after all ref updates are committed, before the status report is sent
- Input: pkt-line encoded status report on stdin (each `ng <refname> <reason>` line ends with a newline; entire report terminated by a flush packet)
- Output: replacement status report on stdout; stderr forwarded to client via sideband
- Exit code semantics: non-zero exit rewrites all ref status lines to `"receive-report hook failed"` and allows `receive-pack` to exit cleanly (aligned with `pre-receive` hook)
- Hook is **NOT integrated with the config-based hook infrastructure** (deliberate choice to avoid parallelization and coordination complexity)
- Test coverage: 200 lines in `t/t5412-receive-report-hook.sh` covering passthrough, failure modes, stdin/stdout handling, sideband relay, and interaction between exit status and stderr output. The test suite exercises both success and failure cases, including custom failure messages and stderr relay.
- Documentation: The hook is documented in both `githooks.adoc` and `git-receive-pack(1)`, with the latter linking to `githooks(5)`. The commit message includes a concrete use-case example (GitLab’s MVCC system) and justifies the single-script design. Pkt-line format documentation links to `gitprotocol-pack[5]`. The preparatory documentation patch adds a `PROC-RECEIVE HOOK` section to `git-receive-pack.adoc`, explaining the existing `proc-receive` hook’s purpose and linking to `githooks(5)` for protocol details. **Patrick Steinhardt’s review suggested using `linkgit:git-receive-pack[1]` and copying the first paragraph from `githooks(5)` for consistency.**
- **New documentation ambiguities**:
  - The phrase “Allowing the hook to rewrite” in `git-receive-pack.adoc` should be rephrased to “, which allows the hook to rewrite” for smoother flow.
  - The pkt-line format in `githooks.adoc` should mark the `<reason>` field as optional: `ng <refname>[ <reason>]`.
  - The documentation should clarify whether the hook can modify the initial `unpack ok` or `unpack <error>` line, as the protocol allows this but the current text omits it.
