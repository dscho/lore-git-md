Subject: [PATCH] receive-pack: add new `report` hook for server-side status filtering
Series version: standalone patch (no vN marker)
Originating author: Karthik Nayak
Thread type: feature patch

Core problem or goal
Git’s `receive-pack` currently sends a fixed status report to the client after ref updates are committed. There is no way for server administrators to intercept or modify this report before it is finalized. The patch adds a new `report` hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status causes `receive-pack` to die, treating the push as failed (ref changes are not rolled back). The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the state of the repository after all ref updates are committed but before the client receives confirmation.

Current status
Under review; no prior versions posted. The patch remains unchanged in its core implementation. The **central design question**—whether the hook should integrate with Git’s config-based hook infrastructure (which supports multiple scripts per event) or remain a single-script hook modeled after `proc-receive`—has been **resolved in favor of the single-script design**. Karthik Nayak justified this choice by arguing that bidirectional communication inherently requires a single script: piping output from one hook to another would not work for `proc-receive`, and parallel execution is unsafe for this use case. Junio C Hamano and Phillip Wood’s concerns about the design rationale have been addressed by this clarification, though no explicit maintainer endorsement of the design has been given yet. The exit status semantics (non-zero exit discards stdout and causes `receive-pack` to die) remain the agreed direction, aligning with Patrick Steinhardt’s "nuclear option" argument. Documentation updates are still planned to clarify the exit status behavior in `githooks.adoc` and `git-receive-pack(1)`, link the hook to GitLab’s MVCC use case, and resolve the unresolved question of where to document the `pkt-line` format. Minor test adjustments (e.g., verifying the "remote:" prefix on stderr) are also planned, but no further changes to the core implementation are expected unless new design concerns arise.

Key technical details
- Files touched: `builtin/receive-pack.c`, `Documentation/githooks.adoc`, `t/t5412-report-hook.sh`
- New hook name: `report`
- Invocation point: after all ref updates are committed, before the status report is sent
- Input: pkt-line encoded status report on stdin
- Output: replacement status report on stdout; stderr forwarded to client via sideband
- Exit code semantics: non-zero exit discards stdout and causes `receive-pack` to die (treated as a "nuclear option" for exceptional cases)
- Hook is **NOT integrated with the config-based hook infrastructure** (deliberate choice to avoid parallelization and coordination complexity)
- Test coverage: passthrough, failure modes, stdin/stdout handling, sideband relay; **no test currently verifies the interaction between exit status and stdout**
- Documentation: The hook will be documented in both `githooks.adoc` and `git-receive-pack(1)`, with the latter linking to `githooks(5)` for details. The `pkt-line` format documentation remains unresolved (whether to link to `gitprotocol-common.adoc` or elsewhere). The commit message now includes a concrete use-case example (GitLab’s MVCC system) and justifies the single-script design.

Open questions and loose ends
- **Documentation gaps**: The `pkt-line` format documentation remains unresolved (whether to link to `gitprotocol-common.adoc` or elsewhere).
- **Test refactoring**: The test script’s repeated teardown logic may benefit from refactoring into a helper function, though this is a minor stylistic point. Patrick Steinhardt also suggested adjusting a test case to verify the "remote:" prefix appears on stderr output (now planned).
