Subject: [PATCH v5 0/3] receive-pack: add new `receive-report` hook for server-side status filtering
Series version: v5 (3 patches)
Originating author: Karthik Nayak
Thread type: feature patch series

Core problem or goal
Git’s `receive-pack` currently sends a fixed status report to the client after ref updates are committed. There is no way for server administrators to intercept or modify this report before it is finalized. The patch series adds a new `receive-report` hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the state of the repository after all ref updates are committed but before the client receives confirmation.

3. **Core implementation (applied)**: introduces the `receive-report` hook with the agreed-upon exit semantics. The hook runs after all ref updates are committed but before the status report is sent to the client. It receives the pkt-line encoded report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. A zero exit code means the hook’s stdout is used as the report; a non-zero exit rewrites all ref status lines to `"receive-report hook failed"` **and overwrites all `cmd->error_string` fields** (resolving the precedence issue raised by Patrick Steinhardt in v4). The implementation is self-contained and does not use the config-based hook infrastructure. **The hook’s ability to modify the initial `unpack` status line (e.g., `unpack ok` → `unpack push failed due to server error`) is now documented and tested**, addressing Patrick Steinhardt’s question about whether this should be treated as a third way the hook can affect the push outcome.

Key technical details
- Files touched: `builtin/receive-pack.c`, `Documentation/githooks.adoc`, `Documentation/git-receive-pack.adoc`, `t/t5412-receive-report-hook.sh` (renamed from `t5412-report-hook.sh`)
- New hook name: `receive-report` (finalized; replaces the prior `report`)
- New helper functions: `generate_report()` (extracted from `report()` and `report_v2()`; renamed from `generate_response()`), `run_receive_report_hook()`, and `override_cmds_error()` in `builtin/receive-pack.c`
- Boolean parameter: `detailed_reports` (renamed from `add_reports` as per Patrick Steinhardt’s suggestion)
- Invocation point: after all ref updates are committed, before the status report is sent
- Input: pkt-line encoded status report on stdin (each `ng <refname> <reason>` line ends with a newline; entire report terminated by a flush packet)
- Output: replacement status report on stdout; stderr forwarded to client via sideband
- Exit code semantics: non-zero exit rewrites all ref status lines to `"receive-report hook failed"` **and overwrites all `cmd->error_string` fields**, discarding existing per-ref errors (resolving the precedence issue raised by Patrick Steinhardt in v4). This aligns with the behavior of the `pre-receive` hook and allows `receive-pack` to exit cleanly.
- Hook is **NOT integrated with the config-based hook infrastructure** (deliberate choice to avoid parallelization and coordination complexity)
- Test coverage: 224 lines in `t/t5412-receive-report-hook.sh` covering passthrough, failure modes, stdin/stdout handling, sideband relay, interaction between exit status and stderr output, and the hook’s ability to modify the `unpack` status line. The test suite exercises both success and failure cases, including custom failure messages and stderr relay.
- Documentation: The hook is documented in both `githooks.adoc` and `git-receive-pack(1)`, with the latter linking to `githooks(5)`. The commit message includes a concrete use-case example (GitLab’s MVCC system) and justifies the single-script design. Pkt-line format documentation links to `gitprotocol-pack[5]`. The preparatory documentation patch adds a `PROC-RECEIVE HOOK` section to `git-receive-pack.adoc`, explaining the existing `proc-receive` hook’s purpose and linking to `githooks(5)` for protocol details. The documentation now explicitly lists **three ways the hook can affect the push outcome**:
  1. Rewriting individual ref status lines.
  2. Aborting the entire push (by exiting non-zero).
  3. Modifying the initial `unpack` status line (e.g., `unpack ok` → `unpack push failed due to server error`).
  The `<reason>` field in `ng` lines is now marked as optional: `ng <refname>[ <reason>]`.
