Subject: [PATCH] receive-pack: add new `report` hook for server-side status filtering
Series version: standalone patch (no vN marker)
Originating author: Karthik Nayak
Thread type: feature patch

Core problem or goal
Git’s `receive-pack` currently sends a fixed status report to the client after ref updates are committed. There is no way for server administrators to intercept or modify this report before it is finalized. The patch adds a new `report` hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status causes `receive-pack` to die, treating the push as failed (ref changes are not rolled back). The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the state of the repository after all ref updates are committed but before the client receives confirmation.

Current status
Under review; no prior versions posted. The patch remains unchanged in its implementation. Karthik Nayak has addressed **surface-level feedback** from Kristoffer Haugsbakk and Patrick Steinhardt by expanding the commit message to include concrete context about GitLab’s MVCC use case, planning to update `git-receive-pack(1)` to mention the hook, and clarifying documentation in `githooks.adoc` (dropping the word "remote", noting that stderr forwarding depends on the client, and treating non-zero exit as a bug). The variable `code` in `run_report_hook()` will be renamed to `ret`. Test adjustments are planned to verify the "remote:" prefix on stderr output. The test script’s teardown logic remains unchanged, though Patrick Steinhardt suggested refactoring it into a helper function.

Key technical details
- Files touched: `builtin/receive-pack.c`, `Documentation/githooks.adoc`, `t/t5412-report-hook.sh`
- New hook name: `report`
- Invocation point: after all ref updates are committed, before the status report is sent
- Input: pkt-line encoded status report on stdin
- Output: replacement status report on stdout; stderr forwarded to client via sideband
- Exit code semantics: non-zero causes `receive-pack` to die, **and the hook’s stdout is discarded** (this behavior is contested; documentation will clarify that non-zero exit should be treated as a bug, though the implementation may be revised to ignore the exit code entirely)
- Hook is NOT integrated with the config-based hook infrastructure (intentionally, to avoid parallelization)
- Test coverage: passthrough, failure modes, stdin/stdout handling, sideband relay; **no test currently verifies the interaction between exit status and stdout**
- Documentation gaps: The `pkt-line` format documentation remains unresolved (whether to link to `gitprotocol-common.adoc` or elsewhere). The commit message now includes a concrete use-case example (GitLab’s MVCC system).

Open questions and loose ends
- **Design ambiguity**: Should the hook’s exit status override its stdout, or should the two signals be orthogonal? The current implementation discards stdout on non-zero exit, which Patrick Steinhardt and Junio C Hamano find surprising and potentially problematic. Patrick argues the hook should always return zero to ensure the client receives a well-formed status report, even when rejecting ref updates. Karthik acknowledges this as a point of uncertainty but has not committed to a resolution, leaving the design open for further discussion. This ambiguity could affect real-world deployments, as administrators may expect the hook’s output to be honored regardless of exit status.
- **Documentation gaps**: The `pkt-line` format documentation remains unresolved (whether to link to `gitprotocol-common.adoc` or elsewhere).
- **Test refactoring**: The test script’s repeated teardown logic may benefit from refactoring into a helper function, though this is a minor stylistic point. Patrick Steinhardt also suggested adjusting a test case to verify the “remote:” prefix appears on stderr output (now planned).
