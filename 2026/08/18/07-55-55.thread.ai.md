Subject: [PATCH] receive-pack: add new `report` hook for server-side status filtering
Series version: standalone patch (no vN marker)
Originating author: Karthik Nayak
Thread type: feature patch

Core problem or goal
Git’s `receive-pack` currently sends a fixed status report to the client after ref updates are committed. There is no way for server administrators to intercept or modify this report before it is finalized. The patch adds a new `report` hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status causes `receive-pack` to die, treating the push as failed (ref changes are not rolled back). The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the state of the repository after all ref updates are committed but before the client receives confirmation.

Current status
Under review; no prior versions posted. The patch remains unchanged in its implementation. The primary design ambiguity—whether the hook’s exit status should override its stdout—has been resolved in principle: a non-zero exit is now treated as a "nuclear option" that discards stdout and causes `receive-pack` to die, ensuring the client never receives a malformed status report. This aligns with Patrick Steinhardt’s argument and Karthik Nayak’s acceptance. Phillip Wood has raised a new **substantive design question**: whether the hook should integrate with Git’s config-based hook infrastructure (which supports multiple scripts per event) or remain a single-script hook modeled after `proc-receive`. This question is now open and may require either a design justification in the commit message or a code change to adopt the config-based system. Documentation updates are still planned to clarify the exit status behavior in `githooks.adoc` and `git-receive-pack(1)`, and to link the hook to GitLab’s MVCC use case. The unresolved documentation question (where to document the `pkt-line` format) remains. Minor test adjustments (e.g., verifying the "remote:" prefix on stderr) are also planned, but no further changes to the core implementation are expected unless the config-based hook question prompts a redesign.

Key technical details
- Files touched: `builtin/receive-pack.c`, `Documentation/githooks.adoc`, `t/t5412-report-hook.sh`
- New hook name: `report`
- Invocation point: after all ref updates are committed, before the status report is sent
- Input: pkt-line encoded status report on stdin
- Output: replacement status report on stdout; stderr forwarded to client via sideband
- Exit code semantics: non-zero exit discards stdout and causes `receive-pack` to die (treated as a "nuclear option" for exceptional cases)
- Hook is NOT integrated with the config-based hook infrastructure (intentionally, to avoid parallelization)
- Test coverage: passthrough, failure modes, stdin/stdout handling, sideband relay; **no test currently verifies the interaction between exit status and stdout**
- Documentation: The hook will be documented in both `githooks.adoc` and `git-receive-pack(1)`, with the latter linking to `githooks(5)` for details. The `pkt-line` format documentation remains unresolved (whether to link to `gitprotocol-common.adoc` or elsewhere). The commit message now includes a concrete use-case example (GitLab’s MVCC system).
