Subject: [PATCH v3 0/3] receive-pack: add new `report` hook for server-side status filtering
Series version: v3 (3 patches)
Originating author: Karthik Nayak
Thread type: feature patch series

Core problem or goal
Git’s `receive-pack` currently sends a fixed status report to the client after ref updates are committed. There is no way for server administrators to intercept or modify this report before it is finalized. The patch series adds a new hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the state of the repository after all ref updates are committed but before the client receives confirmation.

The series is split into three patches:

2. **Refactoring (applied)**: extracts the status-report generation logic into a reusable `generate_response()` helper in `builtin/receive-pack.c`. The patch is mechanical, with no behavior changes, and prepares the codebase for the hook implementation by centralizing the pkt-line formatting logic. The helper takes a boolean parameter to control v2-specific reports and updates callers to pass a pre-allocated `strbuf`.
3. **Core implementation (applied)**: introduces the hook with the agreed-upon exit semantics. The hook runs after all ref updates are committed but before the status report is sent to the client. It receives the pkt-line encoded report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. A zero exit code means the hook’s stdout is used as the report; a non-zero exit rewrites all ref status lines to `"report hook failed"` and discards the hook’s stdout, matching the behavior of the `pre-receive` hook. The implementation is self-contained and does not use the config-based hook infrastructure.

Key technical details
- Files touched: `builtin/receive-pack.c`, `Documentation/githooks.adoc`, `Documentation/git-receive-pack.adoc`, `t/t5412-report-hook.sh`
- New hook name: `report` (subject to renaming; `receive-report` proposed as alternative)
- New helper function: `generate_response()` in `builtin/receive-pack.c` (extracted from `report()` and `report_v2()`)
- Invocation point: after all ref updates are committed, before the status report is sent
- Input: pkt-line encoded status report on stdin (each `ng <refname> <reason>` line ends with a newline; entire report terminated by a flush packet)
- Output: replacement status report on stdout; stderr forwarded to client via sideband
- Exit code semantics: non-zero exit rewrites all ref status lines to `"report hook failed"` and allows `receive-pack` to exit cleanly (aligned with `pre-receive` hook)
- Hook is **NOT integrated with the config-based hook infrastructure** (deliberate choice to avoid parallelization and coordination complexity)
- Test coverage: passthrough, failure modes, stdin/stdout handling, sideband relay, and interaction between exit status and stderr output
- Documentation: The hook is documented in both `githooks.adoc` and `git-receive-pack(1)`, with the latter linking to `githooks(5)`. The commit message includes a concrete use-case example (GitLab’s MVCC system) and justifies the single-script design. Pkt-line format documentation links to `gitprotocol-pack[5]`. The preparatory documentation patch adds a `PROC-RECEIVE HOOK` section to `git-receive-pack.adoc`, explaining the existing `proc-receive` hook’s purpose and linking to `githooks(5)` for protocol details.

Open questions and loose ends
