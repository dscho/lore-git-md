Subject: [PATCH 0/7] odb: refactor handling of corrupt objects with OBJECT_INFO_DIE_IF_CORRUPT
Series version: v2 (addresses Junio C Hamano’s feedback on return convention and error message propagation)
Originating author: Patrick Steinhardt
Thread type: patch series

Core problem or goal
Refactor the object database (ODB) subsystem to make handling of corrupt objects consistent and backend-agnostic when the `OBJECT_INFO_DIE_IF_CORRUPT` flag is used. The series extends `odb_source_read_object_info()` to distinguish between missing and corrupt objects, propagates backend-specific error messages to the ODB layer, and removes abstraction-breaking code that reconstructs error messages after the fact. The goal is to ensure that corrupt objects are reported consistently regardless of backend, and that error messages are generated by the backend that encountered the failure.

Current status
Under review; v2 posted and now complete. Junio C Hamano’s design-level concerns about the tri-state return convention have been fully addressed via the `enum odb_read_status` with negative error codes. The `errmsg` parameter introduced in patch 4/7 is now used in patch 7/7 to accumulate backend-specific error messages, and the abstraction-breaking `has_packed_and_bad()` function has been removed. Patrick Steinhardt has clarified the error-propagation logic in the files backend in response to Karthik Nayak’s review: the logic filters out `ODB_READ_NOT_FOUND` from the packed backend, ensuring that corruption errors are never masked by "not found" errors, and that the packed backend’s corruption takes precedence when both backends fail. The granularity of the `bad_pack` logic remains unresolved: Junio’s initial question about object-level granularity was clarified by Patrick (the patch does not mark entire packs as bad), but Junio has now identified a latent correctness issue—if a corrupt pack contains duplicate objects, the error-reporting mechanism cannot distinguish which copy was corrupt. Karthik Nayak’s code hygiene concern about returning raw integers instead of named enum constants in patch 2/7 remains unresolved, though Patrick has reiterated that this is a deliberate stylistic choice. Karthik Nayak, in a recent reply, concedes the patch is "fine as is" but notes that the argument about enum usage "goes both ways," signaling lingering unease about the maintainability risk of mixed style in the codebase. The commit message for patch 3/7 is now flagged as misleading: it claims "not found" errors are prioritized, but the actual logic prefers *any* error (including corruption) over "not found" errors, and only prioritizes the packed backend’s error when both backends report non-"not found" failures. The latest exchange between Patrick Steinhardt and Karthik Nayak confirms that the commit message’s phrasing ("prefer the error of the packed source in case both reads have failed") is technically correct when interpreted narrowly as referring to *non-NOT_FOUND* failures, but remains ambiguous about the broader error-handling policy. No changes to the code are proposed; the disagreement is now purely about documentation precision. No merge status reported.

Key technical details
- Files touched: `odb.c`, `odb/source-*.c` (in-memory, packed, loose, files), `odb.h`, `odb/source.h`, `packfile.c`, `packfile.h`, `midx.c`, `midx.h`, `builtin/pack-objects.c`, `t/helper/test-read-midx.c`, and test files (`t1060-object-corruption.sh`, `t/unit-tests/u-odb-inmemory.c`).
- Key functions modified: `odb_source_read_object_info()`, `read_object_info_from_path()`, `do_oid_object_info_extended()`, `find_pack_entry()`, `fill_midx_entry()`, `packfile_fill_entry()`, `odb_source_packed_read_object_info()`, `odb_source_loose_read_object_info()`, `odb_source_files_read_object_info()`, and the `read_object_info()` callback in all ODB sources. The `has_packed_and_bad()` function was removed in patch 7/7.
- New behavior introduced in patch 1/7: the `enum odb_read_status` (`ODB_READ_OK = 0`, `ODB_READ_ERROR = -1`, `ODB_READ_NOT_FOUND = -2`) formalizes the return convention for `odb_source_read_object_info()` and is now fully adopted across all ODB backends.
- Patch 3/7 introduced `ODB_READ_NOT_FOUND` and updated all ODB backends to return it for missing objects while preserving `ODB_READ_ERROR` for corruption and other failures. The error-propagation logic in the files backend filters out `ODB_READ_NOT_FOUND` from the packed backend, ensuring that corruption errors are never masked by "not found" errors, and that the packed backend’s corruption takes precedence when both backends fail. This design is now explicitly documented in the thread, but the commit message’s phrasing is misleading: it claims "not found" errors are prioritized, whereas the actual logic prefers *any* error (including corruption) over "not found" errors, and only prioritizes the packed backend’s error when both backends report non-"not found" failures. The latest exchange confirms the phrasing is technically correct when read narrowly (referring only to non-NOT_FOUND failures) but remains ambiguous about the broader policy.
- Patch 4/7 introduced the `errmsg` parameter to the `read_object_info()` callback, allowing ODB backends to populate backend-specific error messages.
- Patch 7/7 removed `has_packed_and_bad()` and made `OBJECT_INFO_DIE_IF_CORRUPT` fully generic: `do_oid_object_info_extended()` now tracks corruption status and accumulates error messages from all backends, dying with the first available message when the flag is set. The loose backend’s direct `die()` call was removed, and a test case was added to verify that a corrupted loose commit can still be read from an alternate repository.
- No new user-facing options or commands; changes are internal to the ODB subsystem.
- On-disk format unchanged.
- Test coverage: updated `t1060-object-corruption.sh` and unit tests in `t/unit-tests/u-odb-inmemory.c` to expect `ODB_READ_NOT_FOUND` for missing objects, and added a test case for reading corrupted loose objects from alternates.

Open questions and loose ends
- The granularity of the `bad_pack` logic remains a point of discussion. Junio’s initial question about object-level granularity was clarified by Patrick (the patch does not mark entire packs as bad), but Junio has now identified a latent correctness issue: if a corrupt pack contains duplicate objects, the error-reporting mechanism cannot distinguish which copy was corrupt. This edge case could surface if the multi-pack index (MIDX) encounters a malformed pack with duplicate objects. No resolution proposed; the point is left open for future consideration.
- The `die()` call for invalid object types in the loose backend remains unchanged due to test dependencies; noted as a potential future cleanup but not blocking the current refactoring.
- The unresolved stylistic tension over enum usage in patch 2/7 is now explicitly documented: Karthik Nayak suggested returning named enum constants (`ODB_READ_OK`, `ODB_READ_ERROR`) instead of raw integers to improve code clarity and safety, especially as the enum expands. Patrick Steinhardt has pushed back, arguing the return convention is well-established and that converting the entire call chain would add little value. Karthik’s recent reply concedes the patch is "fine as is" but notes the argument "goes both ways," leaving the maintainability risk of mixed style unresolved.
- The commit message for patch 3/7 is misleading: it claims "not found" errors are prioritized, but the actual logic prefers *any* error (including corruption) over "not found" errors, and only prioritizes the packed backend’s error when both backends report non-"not found" failures. The latest exchange between Patrick Steinhardt and Karthik Nayak confirms the phrasing is technically correct when read narrowly (referring only to non-NOT_FOUND failures) but remains ambiguous about the broader error-handling policy. Karthik advocates for rewording to clarify the design intent; Patrick defends the current phrasing as accurate when interpreted strictly.
