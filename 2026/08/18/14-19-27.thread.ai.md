Thread identity
Subject: [PATCH 0/7] odb: refactor handling of corrupt objects with OBJECT_INFO_DIE_IF_CORRUPT
Series version: v1 (initial submission, v2 anticipated)
Originating author: Patrick Steinhardt
Thread type: patch series

Core problem or goal
Refactor the object database (ODB) subsystem to make handling of corrupt objects consistent and backend-agnostic when the `OBJECT_INFO_DIE_IF_CORRUPT` flag is used. The series extends `odb_source_read_object_info()` to distinguish between missing and corrupt objects, propagates backend-specific error messages to the ODB layer, and removes abstraction-breaking code that reconstructs error messages after the fact. The goal is to ensure that corrupt objects are reported consistently regardless of backend, and that error messages are generated by the backend that encountered the failure.

Current status
Under review; v1 posted, v2 anticipated. Junio C Hamano’s design-level concerns have been fully addressed on the tri-state return convention: Patrick Steinhardt agreed to formalize the return values using an enum and to use negative error codes (e.g., `-ENOENT`) for all error conditions, including missing objects, rather than overloading positive values. The granularity of the `bad_pack` logic in patch 3/7 remains unresolved—while Patrick clarified that the patch does not mark entire packs as bad, Junio’s broader question about whether object-level granularity is sufficient for multi-pack scenarios is still open. No merge status reported. Patch 5/7’s commit message subject line was corrected from "signal mark objects" to "signal missing objects" per Junio’s review and Patrick’s confirmation.

Key technical details
- Files touched: `odb.c`, `odb/source-*.c` (in-memory, packed, loose, files), `packfile.c`, `midx.c`, `midx.h`, `builtin/pack-objects.c`, `t/helper/test-read-midx.c`, related headers, and test files (`t1060-object-corruption.sh`, `t/unit-tests/u-odb-inmemory.c`).
- Key functions modified: `odb_source_read_object_info()`, `read_object_info_from_path()`, `do_oid_object_info_extended()`, `find_pack_entry()`, `fill_midx_entry()`, `packfile_fill_entry()`, `odb_source_packed_read_object_info()`, `odb_source_loose_read_object_info()`, `odb_source_files_read_object_info()`, and the `read_object_info()` callback in all ODB sources. The `has_packed_and_bad()` function was removed.
- New behavior: `odb_source_read_object_info()` will return zero for success, negative values for all error conditions (including `-ENOENT` for missing objects), and backend-specific error messages propagated via the `errmsg` parameter. The return convention will be formalized in v2 using an enum. `OBJECT_INFO_DIE_IF_CORRUPT` is now handled generically in the ODB layer: when set, the process dies with the first available backend error message (e.g., "packed object X (stored in Y) is corrupt") or a generic message if none is provided. The loose backend no longer dies unconditionally when encountering corruption; instead, it reports the error to the ODB layer, which decides whether to die based on the flag and the availability of good copies from other backends.
- Patch 3/7 modifies `fill_midx_entry()` to track the pack containing a corrupt object via a `struct packed_git **bad_pack` parameter. The pack pointer is passed upward solely to enable richer error messages in patch 7/7, where the ODB layer can report which pack contained the corrupt object. The patch does not mark the entire pack as bad; only the specific objects flagged in the `bad_objects` oidset are considered corrupt. This resolves Junio’s concern about over-broad pack invalidation but leaves open whether the current granularity is sufficient for multi-pack scenarios.
- Patch 4/7 updates the loose-object backend to return negative values for all error conditions, removing redundant error handling.
- Patch 5/7 updates the files ODB source to propagate error codes from its child sources, preferring the packed source's error code when both fail. The commit message subject line was corrected from "signal mark objects" to "signal missing objects".
- Patch 1/7 updated the documentation and function signature in `odb/source.h` to formalize the return convention.
- Patch 2/7 mechanically updated the in-memory ODB source to return negative values for missing objects.
- Patch 6/7 introduced the `errmsg` parameter to the `read_object_info()` callback, allowing backends to populate backend-specific error messages.
- Patch 7/7 (final) removed `has_packed_and_bad()` and made `OBJECT_INFO_DIE_IF_CORRUPT` fully generic: `do_oid_object_info_extended()` now tracks corruption status and accumulates error messages from all backends, dying with the first available message when the flag is set. The loose backend's direct `die()` call was removed, and a test case was added to verify that a corrupted loose commit can still be read from an alternate repository.
- No new user-facing options or commands; changes are internal to the ODB subsystem.
- On-disk format unchanged.
- Test coverage: updated `t1060-object-corruption.sh` and unit tests in `t/unit-tests/u-odb-inmemory.c`.

Open questions and loose ends
- The granularity of the `bad_pack` logic remains a point of discussion: while Patrick clarified that the patch does not mark entire packs as bad, Junio’s broader question—whether the current object-level granularity is sufficient for multi-pack scenarios—remains unanswered.
- The `die()` call for invalid object types in the loose backend remains unchanged due to test dependencies; noted as a potential future cleanup but not blocking the current refactoring.
