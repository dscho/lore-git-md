This is the **v6 iteration of a security feature patch** that adds `http.sslVerifyStatus`, a boolean config option (default `false`) to enable OCSP staple validation via libcurl. The patch is now **technically complete and ready for `next`**, with all prior review feedback addressed, including Junio C Hamano’s final request for clearer documentation wording.

The feature closes a security gap where Git’s HTTPS certificate verification ignores OCSP staples, leaving OpenSSL-linked binaries (common in FIPS-compliant deployments like US Department of Defense PKI) vulnerable to accepting revoked certificates. When enabled, `http.sslVerifyStatus` causes connections to fail if the server does not provide a valid staple, aligning Git’s behavior with government and enterprise security mandates. The default remains `false` to avoid breaking remotes that do not support stapling, but the design is fail-closed for security.

Key technical details:
- **New config key**: `http.sslVerifyStatus` (boolean, default `false`), with per-URL override support (e.g., `http.https://example.com/.sslVerifyStatus`).
- **Libcurl requirement**: Uses `CURLOPT_SSL_VERIFYSTATUS` (libcurl ≥ 7.41.0, already below Git’s minimum version).
- **Files touched**: `http.c` (core logic), `Documentation/config/http.adoc` (user-facing docs), and `t/t5551-http-fetch-smart.sh` (four new tests covering fail-closed behavior, per-URL scoping, and edge cases).
- **Error handling**: Includes libcurl error strings (`curl_easy_strerror()`) to distinguish missing features (`CURLE_NOT_BUILT_IN`) from other failures.
- **Backend parity**: Recent libcurl versions (≥ 8.10) unify GnuTLS and OpenSSL behavior, obsoleting prior backend-specific caveats.

The v6 update focuses solely on **documentation clarity**, rephrasing the `http.sslVerifyStatus` description to emphasize the user-facing outcome ("prevents connections to servers with revoked certificates") rather than technical jargon ("OCSP stapling"). The commit message and test coverage remain unchanged from v5, which resolved all substantive feedback from Junio and Patrick Steinhardt. The only open question—whether to add a positive test case for valid staples—has been deferred, with the author noting the infrastructure (nginx in Docker) is available but awaiting maintainer input.

This patch is **low-risk for integration** but high-impact for the niche use case it targets. The default-off design ensures backward compatibility, while the fail-closed behavior when enabled addresses a concrete security requirement for government and enterprise users. No further technical changes are expected; the patch is poised for graduation to `next` pending Junio’s final review of the documentation wording.
