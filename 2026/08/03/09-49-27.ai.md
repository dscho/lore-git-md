This is a **bugfix patch** targeting the `git history squash` subcommand, part of the v10 series from Phillip Wood. The patch corrects a long-standing edge case in the implementation: when the first commit in the squash range is a merge commit, the current code incorrectly assumes it has only one parent, causing the squashed commit to drop all but the first parent. The fix ensures the squashed commit retains the full parent list of the original merge, preserving the merge topology.

The change is small but critical for correctness. The core logic in `resolve_squash_range()` no longer returns a `base` commit (the parent of the oldest commit in the range), and the caller (`cmd_history_squash()`) now directly uses `oldest->parents` when constructing the squashed commit. This matches the behavior of `git commit` and `git merge`, which both preserve the parent list of the commit being amended or merged into. The test case verifies the fix by creating a merge commit, amending it with a fixup, and then squashing the range to confirm the resulting commit has the correct parents and tree.

This patch is **substantive and tested**, addressing a real bug that could silently corrupt history by dropping merge parents. It is part of Phillip’s broader review of the `squash` subcommand, which has already influenced v11 of Harald’s series. While v11 is functionally complete and ready for integration, this fix remains relevant for any future iterations or backports. The change touches `builtin/history.c` and adds a new test case to `t/t3455-history-squash.sh`. Key names modified include `resolve_squash_range` (no longer returns `base_out`) and `cmd_history_squash` (now uses `oldest->parents` directly).
