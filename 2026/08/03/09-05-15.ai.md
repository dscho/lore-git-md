This is a **design discussion and reviewer feedback** on the `hn/history-squash` topic, focusing on message-handling behavior and user experience. Phillip Wood engages with Matt Hunter’s earlier proposal to introduce `--edit`/`--no-edit` options, offering a nuanced alternative that ties editor behavior to the type of commits being squashed.

Phillip begins by encouraging Matt to push back on dismissed design points if the rationale remains unclear, framing this as a productive way to improve the design. He then addresses Matt’s suggestion that `amend!` messages could be preserved by default when squashing, arguing that these messages are a stronger signal of user intent than other commit messages and should not be discarded lightly. This refines the earlier debate about whether `--reedit-message` should be removed or replaced, shifting the focus to preserving user intent rather than just editor behavior.

On the `--edit`/`--no-edit` proposal, Phillip suggests that scripts could simply use these options rather than relying on `core.editor` workarounds, reinforcing the value of scriptability. He then critiques the `--reedit-message` precedent in `git history fixup`, calling it "unfortunate" and proposing to deprecate it in favor of `--edit` for consistency with other Git commands. This aligns with Matt’s earlier argument for conventional option naming but goes further by questioning the entire premise of "reediting" in the squash context.

The most substantive contribution is Phillip’s new proposal: default editor behavior should depend on the *type* of commits being squashed. If the commits are primarily `fixup!` or `amend!` messages, the editor might not open (since the user’s intent is already clear), but for other commits, the editor would open to allow review. This introduces a dynamic default that could reduce friction for common cases while still allowing user override via `--edit`/`--no-edit`. The trade-off, as Phillip notes, is potential confusion if the behavior feels inconsistent.

The email advances the discussion by introducing a context-sensitive default and a path to deprecate `--reedit-message`, but it leaves key questions open: whether this dynamic behavior would be too subtle for users, how it interacts with the existing `--reedit-message` flag, and whether it fully addresses the broader correctness issues (e.g., reachability logic) that led to the topic’s ejection from `next`.
