This is a review comment from Junio on the second patch in Pablo Sabater’s GSoC v3 series, which adds a safety check to `fetch-object-info.c` to detect truncated server responses. The patch itself is a small, uncontroversial bugfix that `die()`s if the server sends fewer object-info lines than the client requested, preventing uninitialized data from being used.

Junio’s feedback is substantive but advisory. He notes that the tightening is obviously good, then raises a forward-compatibility question: what happens if the server sends *more* objects than requested? The current code allocates space for exactly the number of OIDs requested and loops for that many iterations, so it will not read past the end of the allocated arrays. However, Junio wonders whether the client would detect being out of sync with the server on the *next* request, or only when the connection shuts down. The question is not a blocker—Junio does not ask for a code change—but it suggests a potential robustness edge case that reviewers familiar with the protocol subsystem might want to consider. The patch as written remains correct and ready for integration; the discussion is about future-proofing rather than a flaw in the current implementation.
