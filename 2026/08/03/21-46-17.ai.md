This is the fourth patch in Pablo Sabater’s GSoC v3 series, which refactors the remote-object-info subsystem to use a dedicated `struct fetch_object_info_results` instead of the legacy `struct object_info`. The patch is part of the ongoing effort to extend `git cat-file --batch-command` with `%(objecttype)` support, enabling clients to request object type metadata from the server alongside size.

The refactoring itself is well-motivated and clean: it replaces an inefficient design (allocating one scalar per object per attribute just to hold pointers for `read_object_info()`) with a memory-efficient struct where the caller explicitly controls which fields are populated. This aligns with the feedback from Junio and Peff in earlier rounds and is now fully implemented. The patch also drops redundant code (`object_info_options`, `remote_atom_map[]`, and `free_object_info_contents()`), simplifying the codebase.

However, Junio’s reply identifies a forward-compatibility issue: the patch introduces the `ask_type` flag and related machinery (e.g., `wants_type`, `types` array) *before* the client-side parsing logic (patch 6/8) and server-side capability advertisement (patch 7/8) are added. If a user requests `%(objecttype)` at this stage and the server *does* support "type" (e.g., a newer server), the client will hit a `BUG()` because it lacks the parsing logic to handle the response. Pablo acknowledges this in his reply and plans to move the `ask_type` flag to a later patch where it fits correctly. This is a protocol hygiene issue rather than a correctness bug, and it does not block merging the series. The fix is straightforward and will be incorporated in the next iteration.

The patch touches `fetch-object-info.c`, `fetch-object-info.h`, `builtin/cat-file.c`, `transport.c`, and related headers, replacing the `object_info`-based parsing logic with the new struct. The new design uses a single array of lightweight structs where the caller decides which fields to populate, avoiding sentinel values entirely. This is a significant improvement over the previous approach, which relied on `OBJ_NONE` and boolean flags to signal missing data.

The series remains feature-complete and merge-ready, with all prior review feedback addressed. The only remaining loose end is the premature `ask_type` flag, which will be resolved in the next version. Reviewers familiar with the protocol subsystem may want to verify the error handling and protocol invariants, though the implementation follows the established pattern from the predecessor series. The patch is a key step in the end-to-end implementation of object type metadata support and is unlikely to be controversial.
