This is a **substantive fixup patch** for the `git history squash` implementation, part of Phillip Wood’s review series targeting Harald Nordgren’s v10. The patch tightens input validation by explicitly rejecting revision ranges with **more than one tip commit**, a case the current implementation cannot handle correctly.

The change replaces the `--boundary`-based approach with a more precise mechanism that tracks each commit’s parents and flags commits as tips. It introduces two new object flags (`SQUASH_SEEN` and `SQUASH_TIP`) to mark commits encountered during the revision walk and count tips. If the walk ends with anything other than exactly one tip, the command fails with a clear error message. The patch also improves error reporting by checking that every parent of each commit has been seen, producing more specific error messages than the generic "more than one base" message it replaces.

Test coverage is expanded to verify the new behavior: a new test case creates a synthetic commit with the same tree as an existing commit but a different parent, then attempts to squash it alongside another commit, expecting the command to fail. The patch also updates existing merge-handling tests to expect the new, more descriptive error message.

This is a **correctness fix** that prevents silent misbehavior when users accidentally specify ambiguous ranges. The implementation is careful (noting the object flag allocation policy) and the error messages are user-facing, so the change is worth attention even though v11 of the main series has since been posted. The stricter validation aligns with v11’s overall direction, though v11 does not adopt this exact mechanism.
