This is the fourth patch in Pablo Sabater’s GSoC v3 series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The patch introduces `struct fetch_object_info_results`, a dedicated struct for storing the results of `fetch_object_info()`, replacing the previous use of `struct object_info`. This refactoring is the core architectural change of the series, addressing feedback from Junio C Hamano and Jeff King about memory efficiency and design clarity.

Junio’s reply raises a forward-compatibility concern: at this point in the series (patch 4/8), the client does not yet parse the "type" field (added in patch 6/8), nor does the server advertise it (added in patch 7/8). If a user requests `%(objecttype)` against a newer server that *does* support "type", the client will hit a `BUG()` because the `ask_type` flag is introduced here but the parsing logic is not yet in place. Junio suggests this makes the introduction of `ask_type` premature, though he does not oppose the overall direction.

The patch itself is a well-motivated refactoring that replaces the `object_info`-based design with a cleaner, more memory-efficient approach. It removes redundant structures (`object_info_options`, `remote_atom_map[]`, `free_object_info_contents()`) and simplifies the code in `builtin/cat-file.c` and `fetch-object-info.c`. The changes are mechanical and do not alter behavior, but the timing of the `ask_type` flag introduction creates a temporary incompatibility that could trigger a crash if a user requests `%(objecttype)` before the full implementation is in place.

This is a minor issue that does not block merging, but it may prompt a small follow-up patch to defer the `ask_type` flag until the parsing logic is ready (patch 6/8). The series remains feature-complete and merge-ready, with all prior review feedback addressed and the architectural refactoring finalized. Reviewers focused on protocol robustness may want to verify that the temporary incompatibility is resolved before the series graduates to `next`.
