This is a bugfix patch in the ongoing GSoC series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. It is the second patch in the v3 series of eight, which has undergone significant refactoring to replace `struct object_info` with a dedicated `struct fetch_object_info_results`.

The patch addresses a preexisting robustness issue in `fetch-object-info.c`: the loop that reads the server's object-info response stops as soon as the packet reader returns anything other than `PACKET_READ_NORMAL`, but the caller assumes every requested object will be filled in. If the server sends fewer objects than requested, the end of the result arrays remains uninitialized, and the caller proceeds with invalid data. The fix adds a safety check that `die()`s if the loop exits before processing all requested OIDs, with a clear error message showing the expected and actual counts. The change is minimal (eight lines added, two lines modified) and confined to a single function.

The motivation is sound: silent truncation of server responses is a latent bug that could lead to subtle corruption or crashes. The fix is defensive and follows Git's established pattern of failing fast when protocol invariants are violated. The commit message is clear and concise, and the implementation is straightforward. No test coverage is added here, but the patch is part of a series that expands test coverage in `t5701` and `t1017` elsewhere. The change is uncontroversial and aligns with the series' overall goal of making remote-object-info queries more robust. Reviewers familiar with the object-info subsystem may want to confirm the error message is sufficiently descriptive, but the patch itself looks ready for integration.
