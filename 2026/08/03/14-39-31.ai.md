This is the fourth patch in the GSoC v3 series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The patch introduces `struct fetch_object_info_results`, a dedicated struct for storing the results of `fetch_object_info()`, replacing the previous use of `struct object_info`. This refactoring is the core architectural change of the series, addressing feedback from Junio C Hamano and Jeff King (Peff) about memory inefficiency and awkwardness in the v2 design.

The new struct holds only the fields the caller requests (currently size and type), using separate arrays for each attribute. The caller sets `wants_*` flags to indicate interest, and `fetch_object_info()` allocates arrays only for the attributes the server both advertised and answered. This avoids the need for sentinel values like `OBJ_NONE` and eliminates the `object_info_options` string list, `remote_atom_map[]`, and `free_object_info_contents()`. The patch also drops the now-unused `object_info_args` struct (removed in patch 3) and updates function signatures to pass the new struct directly.

Key changes include:
- `fetch_object_info()` now takes a `struct fetch_object_info_results *` instead of `struct object_info *` and `struct string_list *object_info_options`.
- `send_object_info_request()` is updated to accept explicit `ask_size` and `ask_type` flags instead of a string list.
- `builtin/cat-file.c` is simplified, removing the `remote_atom_map[]` and `protocol_placeholder_entry` machinery, and replacing `object_info` array handling with the new struct.
- The `free_fetch_object_info_results()` function is introduced to release the allocated arrays.

The patch touches `fetch-object-info.c`, `fetch-object-info.h`, `builtin/cat-file.c`, `transport.c`, and `transport.h`, and removes `free_object_info_contents()` from `object-file.c` and `odb.h`. The changes are mechanical and well-motivated, aligning the implementation with the hybrid design proposed by Junio and Peff. The new approach is cleaner and more memory-efficient, though reviewers familiar with the object-info subsystem may want to verify the edge cases around attribute allocation and error handling. No behavior changes are introduced; this is purely a refactoring to enable the type support added in later patches.
