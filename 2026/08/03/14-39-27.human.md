This is the third iteration of a Google Summer of Code feature patch series extending `git cat-file --batch-command` to support the `%(objecttype)` placeholder in remote-object-info queries. The series now consists of eight patches, up from six in v2, reflecting a significant architectural refactoring of the object-info storage and handling logic.

The core goal remains unchanged: enable end-to-end object type queries via the remote-object-info protocol, completing the last piece of metadata guaranteed to match between client and server after a fetch. The series is narrowly scoped to object type, with other metadata (disk size, delta base, object mode) explicitly ruled out as unreliable or context-dependent.

The most notable change in v3 is the introduction of a dedicated `struct fetch_object_info_results` to replace the previous `struct object_info`-based approach. This refactoring, spanning patches 3-4, was motivated by feedback from Junio C Hamano and Jeff King (Peff) in the v2 thread, who argued that the original design was inefficient and awkward for batch queries. The new struct holds an array of lightweight result entries, each containing only the fields the caller requested, avoiding wasted space and eliminating the need for sentinel values. This aligns with the protocol's transmission of raw strings (e.g., `"blob"`, `"1234"`) and bypasses the `read_object_info()` machinery entirely. The refactoring also drops the `object_info_options` string list and related plumbing, simplifying the code.

Patch 2 addresses a preexisting bug: the client now dies if the server sends fewer object-info lines than requested OIDs, preventing silent truncation. The remaining patches (5-8) implement the type support: the server learns to answer type queries, the client parses the response, the capability is advertised, and the default format is unified. The test suite (`t5701` and `t1017`) is updated to cover the new functionality, including Chandra Pratap's shell quoting nit from v2.

The series appears well-structured and addresses all prior feedback. The architectural changes are substantial but focused, and the commit messages clearly explain the motivation. The GSoC deadline is approaching, but this version looks like a strong candidate for merging. No major open questions remain, and the design now has buy-in from both Junio and Peff.
