This is a **maintainer response** in the ongoing design discussion for `hn/history-squash`, focusing on the user experience and message-handling behavior. Junio C Hamano engages with Phillip Wood’s proposal to make editor invocation context-sensitive—opening the editor by default only when the commits being squashed are not primarily `fixup!` or `amend!` messages.

Junio acknowledges that `git history` is experimental and thus open to UI tweaks, implicitly endorsing the idea of refining the command’s behavior. However, he raises a nuanced concern about Phillip’s proposal: while an `amend!` commit clearly signals that the user’s intent is to replace the target commit’s message (making editor invocation unnecessary), the case for `fixup!` commits is less clear. A `fixup!` commit indicates a code change but does not specify whether the associated log message should also be incorporated, leaving ambiguity about whether the editor should open. Junio also questions the behavior when multiple `amend!` commits are squashed together, suggesting this could introduce confusion.

The response highlights a tension between reducing friction for common cases (e.g., squashing `amend!` commits) and avoiding subtle, hard-to-predict behavior. Junio’s skepticism centers on whether the dynamic default would feel inconsistent or confusing to users, particularly when `fixup!` commits or multiple `amend!` commits are involved. This leaves the design question open: should the editor open by default, never open by default, or follow a context-sensitive rule—and if the latter, how should edge cases like `fixup!` commits be handled?

The email does not resolve the debate but signals that Junio is receptive to experimentation, given the command’s experimental status. The discussion remains active, with Phillip’s proposal now facing scrutiny over its potential to introduce complexity. For readers following the thread, this is a key moment: the maintainer’s feedback suggests that any final design will need to balance scriptability, user intent, and clarity, with particular attention to how `fixup!` and `amend!` commits are treated.
