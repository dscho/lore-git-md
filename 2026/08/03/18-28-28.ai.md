This is the fourth patch in Pablo Sabater’s GSoC v3 series, which refactors `fetch_object_info()` to use a dedicated `struct fetch_object_info_results` instead of `struct object_info`. Junio’s reply raises a forward-compatibility concern: the patch introduces the `ask_type` flag and related machinery (e.g., `wants_type`, `types` array) in this step, but the client-side parsing for "type" and server-side capability advertisement are not added until patches 6/8 and 7/8, respectively. If a user requests `%(objecttype)` at this stage and the server *does* support "type" (e.g., a newer server), the client will hit a `BUG()` because it lacks the parsing logic to handle the response. Junio suggests this makes the `ask_type` flag premature.

The concern is narrowly scoped to protocol robustness and does not challenge the patch’s correctness or the overall design. The patch itself is a well-motivated refactoring that replaces the inefficient `object_info`-based approach with a cleaner, memory-efficient struct, aligning with feedback from Junio and Peff. The `ask_type` flag is introduced here to avoid a later mechanical churn, but its presence could create a temporary mismatch between client and server capabilities. This is a protocol hygiene issue rather than a functional bug, and it does not block merging the series. However, it may prompt a follow-up discussion about whether the flag should be deferred until patch 6/8 or if the client should gracefully ignore unsupported attributes at this stage. The series remains feature-complete and merge-ready, with all prior review feedback addressed.
