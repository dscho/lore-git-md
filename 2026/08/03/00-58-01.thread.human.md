This thread is about a small but important fix to Git’s bash completion for `git diff`. The original patch, posted by Junio Hamano, aimed to make completion behave consistently—suggesting only tracked files, just like `git status` and `git add` do—especially when using `git -C` or when no revision matches the input. However, SZEDER Gábor quickly spotted a regression: the patch broke completion for `git diff --no-index`, which *should* include untracked files.

Junio has now responded, acknowledging the issue but pushing back on SZEDER’s proposed fix (scanning the command line for `--no-index`). He points out edge cases—like `--no-index` appearing anywhere in the command or being auto-triggered outside a repository—and instead suggests a simpler fallback: if Git’s completion logic finds no candidates, it should hand off to Bash’s native path completion. This keeps the main goal intact but introduces a minor quirk: untracked files that share a prefix with tracked ones (like `foo~` when `foo` exists) might be harder to complete. The thread is now at a crossroads, waiting for either a refined version of SZEDER’s approach or Junio’s fallback to be implemented. The patch is still in Junio’s `seen` branch, and no other reviewers have chimed in yet.
