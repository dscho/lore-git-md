This thread is about a bugfix for `git rebase` that addresses a regression affecting users who customize `core.commentChar` and use multiple worktrees. Markus Geiger identified a case where `git rebase` hardcodes the `#` comment character in its todo list for informational lines about checked-out refs in other worktrees, ignoring the configured `core.commentChar` value (e.g., `;`). This breaks parsing when the sequencer re-reads the todo list, causing the rebase to abort with `error: invalid command '#'`.

The issue is well-documented, with a minimal reproduction case and a clear root cause: the sequencer code in `sequencer.c` uses a literal `#` instead of the resolved `comment_line_char` for these advisory lines. The problem only surfaces when both `core.commentChar` is set to a non-default value *and* a branch in the rebased range is checked out in another worktree. This affects teams that customize `core.commentChar` (e.g., to avoid conflicts with issue references like `#123`) and rely on worktrees, making `git rebase` unusable without workarounds.

The patch is narrowly scoped and targets a specific code path, so it’s likely to attract attention from maintainers of the sequencer and rebase subsystems, as well as contributors working on worktree-related features. No prior discussion or versions of this patch have been posted yet, and the issue is not platform-specific. The fix should be straightforward—replacing the hardcoded `#` with the resolved `comment_line_char`—but the commit message in the current email doesn’t include the actual patch.
