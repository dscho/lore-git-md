This is a **design discussion** in the `hn/history-squash` thread, focusing on how the command should handle commit messages and editor interaction. Phillip Wood responds to Matt Hunter’s proposal for `--edit`/`--no-edit` options, offering a nuanced alternative that ties editor behavior to the type of commits being squashed.

Phillip begins by encouraging Matt to push back when design decisions are dismissed without clear justification, framing it as a way to improve the outcome. He then addresses Matt’s suggestion that `amend!` messages should be preserved for the first commit in a squash: while he agrees these messages signal user intent, he argues they should not be discarded lightly, regardless of which commit they’re attached to.

On the `--edit`/`--no-edit` debate, Phillip agrees the current `--reedit-message` option is poorly named for squashing (since it implies re-editing an existing message, not constructing a new one). He proposes deprecating it in favor of `--edit` for the newer `fixup` subcommand, aligning with Git’s conventions. However, he goes further, suggesting a smarter default for squashing: the editor should open *only* when squashing non-fixup/non-amend commits, as these are more likely to need manual review. This approach would reduce unnecessary editor invocations while still allowing overrides via `--edit` or `--no-edit`.

The discussion remains unresolved but advances the design significantly. Phillip’s proposal balances scriptability, user experience, and consistency with other Git commands, while addressing the core tension between preserving intent (`amend!`/`squash!` messages) and avoiding friction. The thread is now centered on refining this behavior rather than debating whether to remove `--reedit-message` entirely. No code changes have been submitted yet, but Phillip’s feedback is likely to shape the next iteration.
