This is a follow-up in the RFC thread about making Git's stash stack branch-aware or worktree-aware. Phillip Wood proposes a concrete technical solution to the detached HEAD gap identified in the previous discussion, advancing the design beyond the branch-aware approach.

Phillip addresses Vladimir's concern about detached HEAD worktrees by showing how to associate stashes with the specific commit (rather than branch) they were created on. He suggests using the reflog of HEAD and the first parent of stash commits to identify the most recent stash created in the current worktree, regardless of whether it was on a branch or detached. This approach avoids the need for synthetic branch names or configuration knobs, leveraging existing Git machinery (reflogs and commit parent pointers) to achieve per-worktree isolation without breaking backward compatibility. The solution is elegant: it requires no new ref namespaces, no changes to the on-disk format, and no new CLI options for basic functionality.

The proposal focuses on extending `git stash pop` with options to pop the most recent stash from the current branch *or* the current worktree, preserving the global stash stack for users who rely on its current behavior (e.g., moving changes between worktrees). This hybrid design unifies the branch-aware and worktree-aware approaches under a single mechanism, allowing users to choose the scope of stash isolation at operation time rather than through configuration. Phillip also suggests that `git stash list` could later gain filtering options for branch or worktree, but this is not a prerequisite for the core functionality.

This email shifts the discussion from "whether" to "how" to implement stash isolation. The technical feasibility of the branch-aware design is now well-established, and Phillip's reflog-based solution appears to resolve the detached HEAD edge case without introducing new complexity. The remaining open questions are primarily about user interface: whether `git stash pop` should default to branch-aware behavior, require an explicit flag, or support both branch and worktree filtering. The proposal is likely to appeal to Junio, as it avoids new configuration and maintains backward compatibility while addressing the original pain point (silent interference between worktrees).

Key technical details for future reference:
- **Mechanism**: Uses HEAD's reflog and stash commit first parents to associate stashes with the commit (not branch) they were created on.
- **Subsystems touched**: `git stash pop` (new options), reflog parsing, and potentially `git stash list` (future filtering).
- **Edge cases handled**: Detached HEAD worktrees, branch renames (via commit OIDs), and backward compatibility (no changes to existing stash entries).
- **New CLI options**: Proposed `--current-branch` and `--current-worktree` flags for `git stash pop`; no new configuration keys.
- **Backward compatibility**: Older Git versions will continue to see all stashes in `refs/stash`, but the new options will only apply stashes from the intended scope.
