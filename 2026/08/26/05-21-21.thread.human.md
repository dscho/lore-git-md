This thread is about a three-patch bugfix series by Elijah Newren that closes a safety gap in Git’s conflict resolution machinery. The series prevents users from accidentally corrupting repository state by running `git commit --amend` or `git commit <paths>` during conflict resolution for `git am`, `git revert`, and all forms of `git rebase`. These operations were already blocked for some commands, but the protection was incomplete—amending or updating individual paths during conflict resolution could leave the repository in an inconsistent state, since conflict resolution must record the entire tree on top of the current HEAD.

The series is now complete and ready for integration. Junio C Hamano and Phillip Wood have both reviewed and endorsed the approach, and all prior feedback has been addressed. The first patch reworded rebase error messages to avoid misleading users about when restrictions apply, the second extended protection against `git commit --amend` to the remaining commands while preserving interactive rebase directives like `squash` and `reword`, and the third (just posted) blocks `git commit <paths>` during conflict resolution. The core logic is consolidated into a new helper function, `sequencer_ongoing_operation()`, in `sequencer.c`, which cleanly distinguishes between conflict stops and clean interactive rebase stops.

No open questions remain, and the series is uncontroversial. It touches `builtin/commit.c`, `sequencer.c`, and `sequencer.h`, with test coverage added to `t3404-rebase-interactive.sh`, `t3507-cherry-pick-conflict.sh`, and `t4151-am-abort.sh`. The changes align with the ongoing `the_repository` removal effort, though one callsite retains `the_repository` due to lack of a readily available repository instance. The series is now awaiting Junio’s final integration.
