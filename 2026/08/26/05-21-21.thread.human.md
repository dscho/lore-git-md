This thread is about a three-patch series from Elijah Newren that tightens Git's safety checks during conflict resolution, preventing users from accidentally corrupting repository state with `git commit --amend` or `git commit <paths>` while resolving conflicts in `git am`, `git revert`, or any form of `git rebase`. The series is now at v3, addressing a maintainability nit from Phillip Wood by replacing hardcoded paths with existing helpers, but Junio C Hamano's latest review raises a deeper concern about the first patch's logic.

Junio's feedback on the error-message rewording in patch 1 questions whether the code can reliably tell *why* a rebase stopped—whether it was due to an empty commit or just a regular conflict. The current check (`whence == FROM_REBASE_PICK`) might not be precise enough, risking misleading error messages if the rebase stopped for other reasons. This isn't just about phrasing; it could force a rethink of how the series detects conflict states. Elijah has already signaled he'll address Phillip's maintainability feedback in v3, but Junio's point may require more substantial changes.

Phillip Wood remains supportive, calling the series "pretty sound" and a "useful improvement," and he's explicitly approved the third patch (blocking `git commit <paths>`). The series is otherwise ready for integration, with no objections to its core goal or correctness. The open question is whether Junio's concern will lead to a v4 or if Elijah can resolve it with minor adjustments. For now, the series is still under review, with no merge status recorded.
