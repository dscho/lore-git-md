This thread is about a bugfix patch series by Elijah Newren that extends Git's existing protections against unsafe commit operations during conflict resolution. The series aims to block both `git commit --amend` and `git commit <paths>` when resolving conflicts in `git am`, `git revert`, and all forms of `git rebase`, except for interactive rebase directives like `squash` or `edit`. The goal is to prevent users from accidentally corrupting repository state by amending the wrong commit or updating individual paths during conflict resolution.

The series is now at version 3, addressing earlier feedback from Phillip Wood and Junio C Hamano. Phillip's concerns about maintainability (hardcoded paths in the code) have been resolved, and Junio confirmed the technical soundness of the logic for detecting empty-commit stops. However, Junio has raised a new **substantive question** about the necessity of blocking `git commit <paths>` during conflict resolution for empty commits. He argues that a partial commit of an empty commit would still result in an empty commit, suggesting the restriction might be unnecessary. This question challenges the core logic of the patch and could lead to a significant revision or even removal of the restriction. Junio also continues to find the error message phrasing awkward and has proposed mechanical changes to improve clarity, such as renaming enum values and helper functions to include the word "empty."

Phillip Wood has been broadly supportive of the series, calling it a "useful improvement to our UI" and confirming the third patch is ready for integration. Elijah has addressed most feedback but must now respond to Junio's latest question and implement the proposed mechanical changes. The series remains under active review with no merge status recorded. The outcome of Junio's question will likely determine the next steps for the patch.
