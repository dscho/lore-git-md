Thread identity: bugfix patch series (5 patches) by Elijah Newren via GitGitGadget, targeting the merge machinery to prevent unsafe commit operations (`git commit --amend` and `git commit <paths>`) during conflict resolution for `git am`, `git revert`, and all forms of `git rebase`.

Core problem or goal: extend Git's existing protection against unsafe commit operations during conflict resolution to cover both `git commit --amend` and `git commit <paths>`, preventing users from accidentally amending the wrong commit or updating individual paths during conflict resolution, which can corrupt repository state. The fix reliably distinguishes between genuine conflict stops (where amending or partial commits would corrupt state) and internal `--amend` usage by interactive rebase directives (`squash`, `reword`, `edit`, `break`). The **substantive technical question** about the necessity of blocking `git commit <paths>` during conflict resolution for empty commits was resolved in v3: the restriction was removed after Junio C Hamano noted that the result would still be an empty commit and thus harmless. The series' core logic for `git commit --amend` (`whence == FROM_REBASE_EMPTY`) and for `git commit <paths>` (conflict resolution only) remains technically sound and uncontroversial.

Current status: patch series v3 is complete and pending final review. The first two patches (1-2/5) are preparatory: patch 1/5 is a pure refactoring (renaming `FROM_REBASE_PICK` to `FROM_REBASE_EMPTY` and `is_from_rebase()` to `is_from_rebase_empty()`, and replacing direct enum checks with helper calls) with no behavior change, while patch 2/5 removes the restriction on `git commit <paths>` during conflict resolution for empty commits. Patch 4/5 extends the existing protection against `git commit --amend` during conflict resolution to cover `git am`, `git revert`, and all `git rebase` variants, using the `sequencer_ongoing_operation()` helper introduced in patch 1/5. Patch 5/5 (newly added) extends the protection against `git commit <paths>` during conflict resolution to the same set of commands, reusing the same helper to distinguish between conflict stops (blocking partial commits) and clean rebase stops (allowing them). The series is **ready for final review** and likely to proceed to `next`; no merge status is recorded yet.

Key technical details:
- Files touched: `builtin/commit.c`, `sequencer.c`, `sequencer.h`, `wt-status.h`, and test coverage in `t3404-rebase-interactive.sh`, `t3507-cherry-pick-conflict.sh`, `t4151-am-abort.sh`, and `t3403-rebase-skip.sh`.
- New behavior: blocks `git commit --amend` and `git commit <paths>` during conflict resolution for `git am`, `git revert`, and all `git rebase` variants, except for interactive rebase directives (`squash`, `reword`, `edit`, `break`). The restriction on `git commit <paths>` during conflict resolution for empty commits has been removed. Error messages clarify the context: "cannot amend while resolving conflicts" (for `--amend`) and "cannot do a partial commit while resolving conflicts" (for `<paths>`).
- New symbols: `enum ongoing_operation` and `sequencer_ongoing_operation()` in `sequencer.h`/`sequencer.c`, consolidating logic for detecting active operations. The helper function distinguishes between conflict stops (marked by `stopped-sha` in `rebase-merge/`) and clean interactive rebase stops (marked by `amend`).
- No on-disk format changes or new CLI options.
- The series aligns with the `the_repository` removal effort by replacing `the_repository` with `s->repo` where possible, though the partial commit callsite retains `the_repository` due to lack of a readily available repository instance.
