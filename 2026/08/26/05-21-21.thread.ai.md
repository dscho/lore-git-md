Thread identity: bugfix patch series (5 patches) by Elijah Newren via GitGitGadget, targeting the merge machinery to prevent unsafe commit operations (`git commit --amend` and `git commit <paths>`) during conflict resolution for `git am`, `git revert`, and all forms of `git rebase`.

Core problem or goal: extend Git's existing protection against unsafe commit operations during conflict resolution to cover both `git commit --amend` and `git commit <paths>`, preventing users from accidentally amending the wrong commit or updating individual paths during conflict resolution, which can corrupt repository state. The fix reliably distinguishes between genuine conflict stops (where amending or partial commits would corrupt state) and internal `--amend` usage by interactive rebase directives (`squash`, `reword`, `edit`, `break`). The **substantive technical question** about the necessity of blocking `git commit <paths>` during conflict resolution for empty commits was resolved in v3: the restriction was removed after Junio C Hamano noted that the result would still be an empty commit and thus harmless. However, Phillip Wood has since raised a **substantive design question** about UI consistency: why allow partial commits during rebase but not during cherry-pick when both stop for empty commits, given that both write `CHERRY_PICK_HEAD` and `.git/MERGE_MSG`? This inconsistency may warrant clarification or a follow-up patch to align behavior or document the distinction.

This addresses Junio's stylistic feedback about naming clarity, which Phillip Wood confirmed are "much clearer." Patch 4/5 extends the existing protection against `git commit --amend` during conflict resolution to cover `git am`, `git revert`, and all `git rebase` variants, using the `sequencer_ongoing_operation()` helper introduced in patch 1/5. Phillip Wood's **surface-level review** of this patch confirms it is ready for integration, explicitly stating "This looks good now that it is using `rebase_path_*()` rather than hard coding the paths." The series is **technically complete** and likely to proceed to `next` in the near term, but Phillip Wood's **surface-level observation** about patch 2/5 introduces a minor point of discussion: he expresses mixed feelings about removing the restriction on `git commit <paths>` for empty commits, though this is not a blocker. Key technical details:
- Files touched: `builtin/commit.c`, `sequencer.c`, `sequencer.h`, `wt-status.h`, and test coverage in `t3404-rebase-interactive.sh`, `t3507-cherry-pick-conflict.sh`, `t4151-am-abort.sh`, and `t3403-rebase-skip.sh`.
- New behavior: blocks `git commit --amend` and `git commit <paths>` during conflict resolution for `git am`, `git revert`, and all `git rebase` variants, except for interactive rebase directives (`squash`, `reword`, `edit`, `break`). The restriction on `git commit <paths>` during conflict resolution for empty commits has been **removed** (patch 2/5), but this introduces a potential inconsistency with `git cherry-pick`, where partial commits are still blocked for empty commits. Error messages clarify the context: "The now-empty commit has been dropped -- cannot amend." (for `--amend` after an empty commit is dropped), "cannot amend while resolving conflicts" (for `--amend` during conflict resolution), and "cannot do a partial commit while resolving conflicts" (for `<paths>` during conflict resolution). Specific error messages for `git revert` ("cannot do a partial commit during a revert") and `git am` ("cannot do a partial commit during an am session") are also introduced.
- New symbols: `enum ongoing_operation` and `sequencer_ongoing_operation()` in `sequencer.h`/`sequencer.c`, consolidating logic for detecting active operations. The helper function distinguishes between conflict stops (marked by `stopped-sha` in `rebase-merge/`) and clean interactive rebase stops (marked by `amend`). The enum value `FROM_REBASE_NOW_EMPTY` and helper function `is_from_rebase_now_empty()` clarify that the commit *became* empty, replacing the prior names (`FROM_REBASE_EMPTY` and `is_from_rebase_empty()`), which were functionally equivalent.
- No on-disk format changes or new CLI options.
- The series aligns with the `the_repository` removal effort by replacing `the_repository` with `s->repo` where possible, though the partial commit callsite retains `the_repository` due to lack of a readily available repository instance.
