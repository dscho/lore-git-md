This is a **review follow-up** in the thread about protecting local upstream branches from deletion via `git branch -d`. Tuomas Ahola (a new participant in the thread) quotes a 2026 message from Junio C Hamano that suggests a more nuanced approach to the problem: instead of outright blocking deletion of a branch that is an upstream of another local branch, Git could *rewire* the dependent branch to point to the upstream’s own upstream (e.g., if `feature2` depends on `feature1`, and `feature1` is being deleted because it’s merged into `origin/master`, then `feature2` could be updated to depend on `origin/master` instead).

Tuomas’s email is brief but significant: it surfaces a prior discussion where Junio proposed this alternative design, which the original patch author (Harald Nordgren) may have misremembered or conflated with the current proposal. The quoted passage makes it clear that Junio’s objection to the current patch isn’t about the *goal* of protecting upstream branches, but about the *mechanism*—blocking deletion outright rather than offering a migration path for dependent branches. This shifts the debate from "should we protect upstream branches?" to "how should we protect them?" and provides a concrete technical alternative that could resolve the backward-compatibility concern.

The email doesn’t include new code or test cases, but it reframes the discussion around a design that Junio explicitly endorsed in the past. If the author revisits the series, this is likely the direction they’ll need to explore.
