Thread identity
Subject: [PATCH 0/2] Introduce die_for_incompatible_opts() helper
Series version: v2 (revised submission; parameter reordering patch dropped, va_end() fixed, EOF sentinel adopted)
Originating author: Junio C Hamano
Thread type: patch series (refactoring)

Core problem or goal
Replace the fixed-arity `die_for_incompatible_optN()` family (N = 2, 3, 4) with a single varargs helper `die_for_incompatible_opts()` that can handle an unbounded number of mutually exclusive command-line options. The change is purely internal API refactoring; no user-visible behavior is altered.

Current status
Under review (revised version). The series consists of a single patch implementing the agreed design:
- The varargs helper accepts `<int, const char *>` pairs terminated by `EOF` (-1).
- Static inline wrappers for 2–4 options are retained for compile-time safety.
- The `va_end()` omission from v1 is fixed.
- The hard-coded error-message formatting (capped at four options) remains unchanged to avoid i18n breakage.
- The parameter-reordering patch from v1 is dropped.

Key technical details
- Files touched: `parse-options.c`, `parse-options.h`; 14 built-in commands (`add`, `clone`, `commit`, `difftool`, `gc`, `grep`, `log`, `merge-tree`, `pack-objects`, `push`, `repack`, `replay`, `rev-list`, `show-ref`) and the `revision` subsystem use the new helper through existing wrappers, so their call sites do not change.
- New symbol: `die_for_incompatible_opts()` (varargs, EOF-terminated).
- Renamed symbols: none; the fixed-arity helpers remain with their original signatures.
- Old-vs-new behavior: identical; only the internal calling convention changes.
- On-disk format: unaffected.
- Test coverage: none mentioned; the change is plumbing-only and expected to be safe.

Open questions and loose ends
- **Compile-time safety vs. flexibility trade-off**: Jeff King (Peff) continues to advocate for `LAST_ARG_MUST_BE_NULL` (a sentinel macro enforcing a `NULL` terminator at compile time) over the `EOF` sentinel, arguing that the varargs helper cannot enforce argument correctness at compile time, unlike the fixed-arity wrappers. The static inline wrappers mitigate this risk for the common cases (2–4 options), but the varargs version itself remains less safe. Junio acknowledges this trade-off but retains the `EOF` sentinel for backward compatibility with existing callers. René Scharfe proposes two alternative approaches to address this tension:
  1. **EOF + NULL sentinel macro**: A macro that constructs the argument list with both `EOF` and `NULL` terminators, ensuring the internal function is never called directly and thus preventing unterminated lists.
  2. **Type-safe compound literal**: A variant using a `struct used_option` compound literal to enforce the correct argument pattern at compile time, eliminating the risk of mismatched types even in error-handling paths.
  Both proposals preserve the series’ goal and require no changes to existing call sites. The discussion remains framed as a design preference rather than a correctness issue, but René’s contributions provide actionable paths forward.
- **Sentinel choice rationale**: Junio’s retrospective observation notes that adopting `LAST_ARG_MUST_BE_NULL` (or an integer equivalent) would have been a better initial design, but the series now uses `EOF` (-1) to preserve backward compatibility. No further changes to the sentinel are proposed.
- **Hard-coded error-message formatting**: The error-message formatting remains hard-coded for four options to avoid breaking i18n message templates. Peff accepts this rationale.
- **Future-proofing**: The new helper is designed to handle more than four options, but no callers currently need this capability.
