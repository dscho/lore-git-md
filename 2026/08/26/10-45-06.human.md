This is the ninth iteration (v9) of a four-patch series improving user-facing error messages for `git worktree add`, `git checkout`, and `git switch` when an ambiguous remote branch name is provided. The series is now functionally complete and addresses all prior feedback, including the `--guess-remote` edge case in `git worktree add` and a shared advice helper refactoring. It has been cooking in `next` since v7, and this update makes only minor organizational adjustments—moving the `advise_disambiguating_remotes()` function definition earlier in the third patch to improve readability.

The core goal is to replace Git’s terse "matched multiple remote tracking branches" warning with a detailed, actionable advice message. For example, if a user runs `git worktree add ../foo-dir bar-topic` when both `origin/bar-topic` and `upstream/bar-topic` exist, they’ll now see a message like: *"Branch name 'bar-topic' appears in multiple remotes: origin, upstream. If you meant to create a worktree from a remote tracking branch, use `git worktree add -b bar-topic ../foo-dir origin/bar-topic`."* The advice is gated behind the `advice.checkoutAmbiguousRemoteBranchName` config (enabled by default) and provides a static list of conflicting remotes for immediate usability.

The series also fixes a latent bug in `--guess-remote`: previously, `git worktree add --guess-remote bar-topic` would silently succeed if multiple remotes had a `bar-topic` branch, which could lead to unexpected behavior. Now it errors out, aligning with the behavior of `git checkout` and `git switch`. The implementation avoids disrupting existing workflows by keeping `dwim_branch()`’s return behavior unchanged while moving an existing `die()` call earlier to provide a more specific diagnostic. Test coverage in `t/t2400-worktree-add.sh` verifies the new error case and advice suppression in quiet mode.

Key files touched include `builtin/worktree.c`, `builtin/checkout.c`, and `checkout.c`, with new helpers like `advise_disambiguating_remotes()` and updates to `unique_tracking_name()` to collect remote names. The series is well-motivated, with clear commit messages tracing the problematic code paths and justifying the changes. All prior review feedback has been addressed, and Junio’s final review noted only a minor organizational point (already fixed). The one remaining loose end—a follow-up fix for the one-argument `git worktree add` case (e.g., `git worktree add ../topic-branch`)—was scoped out by agreement and will be handled separately.

This is a straightforward usability improvement with no known downsides. The changes are localized, well-tested, and align with Git’s existing advice-message conventions. If you care about error message clarity or worktree behavior, this series is worth a quick skim.
