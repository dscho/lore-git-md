This is the fourth iteration of a feature patch series introducing the `receive-report` hook for `git-receive-pack`. The series is now cooking in `seen` and is ready for integration into `next`.

The hook allows server administrators to intercept and modify the status report sent to clients after reference updates are committed but before the response is finalized. This addresses GitLab’s need to implement a custom multi-version concurrency control (MVCC) system, where post-push operations determine the final status reported to the user. The implementation is clean and well-motivated, with thorough test coverage and clear documentation.

The sole change in this version is the renaming of the hook from `report` to `receive-report`, addressing feedback from Junio C Hamano and Patrick Steinhardt that the original name was overly generic. The new name is more specific and aligns with Git’s existing hook-naming conventions. The implementation and exit semantics remain unchanged: the hook receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status rewrites all ref status lines to `"receive-report hook failed"` and allows `receive-pack` to exit cleanly, matching the behavior of the `pre-receive` hook.

The series is split into three patches: a preparatory documentation update for the existing `proc-receive` hook, a refactoring patch that extracts the status-report generation logic into a reusable helper, and the core implementation of the new hook. The refactoring patch is mechanical and prepares the codebase for the hook by centralizing the pkt-line formatting logic. The test script (`t/t5412-receive-report-hook.sh`) exercises edge cases like passthrough, failure modes, stdin/stdout handling, and sideband relay.

No further technical concerns are raised, and the series is now ready for graduation to `next`. The conflict with Justin Tobler’s "pluggable writes" series has been resolved, and Karthik Nayak has confirmed the resolution is correct. The hook is intentionally not integrated with the config-based hook infrastructure, as it is a bidirectional filter rather than a parallelizable notification hook. This design choice is well-justified in the commit message.
