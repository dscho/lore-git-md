This is a follow-up in the stalled RFC thread about filesystem-level copy-on-write (CoW) or block cloning for `git worktree add`. Peter Morris pushes back on brian m. carlson’s claim that ReFS block cloning is unsafe due to unflushed writes, arguing that the Windows `CopyFile` API (which Git already uses for `git clone --block-clone`) prevents the corruption scenario by opening the source file with shared-read, deny-write semantics. He clarifies that the proposed optimization would therefore be safe on Windows (ReFS) and Linux (Btrfs via `FICLONE`), but not on macOS (APFS), where the necessary atomicity guarantees are unclear. This narrows the scope to two platforms but does not address the thread’s other major blocker: the need to refactor Git’s checkout machinery to support cross-worktree visibility. The discussion remains conceptual, with no implementation progress.
