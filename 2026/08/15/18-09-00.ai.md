This is a technical clarification in the stalled RFC thread about filesystem-level copy-on-write (CoW) for `git worktree add`. Peter Morris responds to brian m. carlson’s report of ReFS corruption by explaining how the Windows `CopyFile` API prevents the specific race condition Carlson described: it opens the source file with shared-read and deny-write semantics, blocking concurrent writes during the copy. Morris argues this makes the corruption scenario impossible on Windows, while acknowledging that Linux (`FICLONE`) and macOS lack equivalent protections. He concludes the optimization could safely target Windows and Linux, excluding macOS.

The clarification is narrowly scoped to the platform-specific correctness issue raised by Carlson, not the broader architectural challenges (checkout machinery refactoring, TOCTOU races) that remain unresolved. Morris’s argument hinges on `CopyFile`’s locking behavior, but he does not address whether this fully mitigates the underlying ReFS bug Carlson cited (unflushed writes causing corruption), nor does he engage with the Git LFS precedent where the issue surfaced. The thread’s core blockers—checkout visibility and platform reliability—are still unaddressed, and this reply does little to advance the stalled proposal. Readers should note that while Morris’s point about `CopyFile`’s locking is technically accurate, it may not resolve the fundamental concern about ReFS’s block cloning implementation. The optimization’s viability on Windows remains contested.
