This thread is about a bugfix for Git’s worktree repair functionality, specifically how it handles path resolution in `.git` files. The issue, introduced in Git v2.48.0, prevents `git worktree repair` from detecting mismatches when the `worktree.useRelativePaths` configuration is toggled between `true` and `false`. The problem arises because `read_gitfile_gently()` always returns an absolute path, obscuring the original path style and breaking symmetry in cross-references between `.git` files and `worktree/id/gitdir` entries.

Yoichi NAKAYAMA authored a single-patch series, now at v4, which introduces `read_gitfile_raw()` to return paths verbatim (absolute or relative) without normalization. This allows the repair logic to detect and correct mismatches when the configuration changes. The patch touches `setup.c`, `setup.h`, `worktree.c`, and the test script `t/t2406-worktree-repair.sh`, with expanded test coverage verifying transitions between absolute and relative paths in both main and side worktrees.

After addressing Junio’s feedback in v4—expanding the commit message to clarify the design rationale for splitting `read_gitfile_raw()` and `read_gitfile_gently()`—the patch is now ready for integration. Junio has marked it for the `next` branch, signaling it will undergo integration testing before graduating to `master`. No open questions or technical concerns remain, and the API design (caller-provided buffer, integer return codes) aligns with Git’s modern conventions. The fix is narrowly scoped and thoroughly tested, with no related work or dependencies.
