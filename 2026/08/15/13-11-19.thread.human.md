This thread is about a bugfix for Git’s worktree repair functionality, specifically how it handles path resolution in `.git` files. The issue, introduced in Git v2.48.0, prevents the repair logic from detecting mismatches when `worktree.useRelativePaths` is toggled between `true` and `false` because the existing `read_gitfile_gently()` function always returns an absolute path, obscuring the original path style.

Yoichi Nakayama, the author, has posted three versions of the patch. The latest (v3) addresses Junio Hamano’s feedback by splitting the API: `read_gitfile_raw()` now returns the verbatim path from the `.git` file (absolute or relative) without normalization, while `read_gitfile_gently()` retains responsibility for resolving relative paths and validating the referenced directory as a Git repository. This change enables the worktree repair logic to detect path style mismatches, but the integration in `worktree.c` remains contested. Junio has accepted the API split in `setup.c` but has not yet reviewed whether the caller in `worktree.c` should explicitly re-add path resolution and repository validation.

The patch touches `setup.c`, `setup.h`, `worktree.c`, and the test script `t/t2406-worktree-repair.sh`, with expanded test cases verifying the repair logic’s handling of transitions between absolute and relative paths. The only remaining open question is whether the worktree repair logic should explicitly perform repository validation after switching to `read_gitfile_raw()`. Yoichi argues that moving `is_git_directory()` out of `read_gitfile_raw()` avoids redundant path resolution and keeps the function narrowly focused, but Junio’s final verdict is still pending. The patch is otherwise ready for integration.
