This is a substantive technical reply in the ongoing RFC thread about filesystem-level copy-on-write (CoW) or block cloning optimizations for `git worktree add`. Brian M. Carlson raises a critical correctness issue with ReFS, the Windows filesystem that Peter Morris proposed as a supported platform for the optimization. Carlson reports that ReFS's block cloning implementation is unreliable: if data has been written but not flushed to disk, the resulting copy can be corrupt. He cites a recent Git LFS issue where this exact problem surfaced, describing ReFS's behavior as "horribly broken." His position is unequivocal: Git should not add ReFS support until only fixed versions of Windows are publicly available. This directly challenges the technical viability of the proposed optimization on Windows, which Morris had framed as a low-effort win due to existing `CopyFile` support. The email does not engage with the broader architectural questions about checkout machinery or cross-worktree visibility, but it introduces a concrete, platform-specific blocker that would need to be resolved before any implementation could proceed. Readers should note that this is not a theoretical concern—it is a demonstrated bug in a production tool (Git LFS) on a widely used platform (Windows), and it undermines the assumption that ReFS block cloning is safe to use. The thread's future direction may hinge on whether this issue can be mitigated or whether the optimization will need to exclude Windows entirely.
