This is a cautionary follow-up in the ongoing RFC thread about adding filesystem-level copy-on-write (CoW) or block cloning to `git worktree add`. Brian M. Carlson raises a serious correctness issue with ReFS, the Windows filesystem Peter Morris proposed as a supported backend. Carlson reports that ReFS's block cloning implementation is unreliable: if data has been written but not yet flushed to disk, the resulting copy can be corrupt. He cites a recent Git LFS issue where this exact problem surfaced, calling the behavior "horribly broken." His recommendation is blunt: Git should not support ReFS block cloning until Microsoft fixes the underlying flaw, which would mean excluding Windows from the optimization until only fixed Windows versions are in use.

The email does not engage with the broader architectural questions about checkout machinery or cross-worktree visibility, but it decisively undermines one of the technical foundations of the RFC. The issue is not theoretical—it has already caused real-world problems in Git LFS—and the fix depends on Microsoft, not the Git project. This makes ReFS a non-starter for the foreseeable future, removing a key platform from the proposed optimization and narrowing the scope to Linux (Btrfs) and macOS (APFS) only. The thread is now at a crossroads: either the RFC must pivot to exclude Windows entirely, or it must wait indefinitely for a Microsoft fix that may never come. Either way, the proposal looks less compelling without Windows support, given that the original motivation (AI coding agents) is likely to be Windows-heavy.
