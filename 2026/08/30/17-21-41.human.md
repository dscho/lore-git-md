This is Domen Kožar’s response to Junio C Hamano’s design objection against the `post-worktree-*` hook series. The patch set proposes a standardized way to run custom logic after worktree creation, removal, or movement, but Junio argued that user-written shell wrappers could achieve the same result without adding Git-native hooks.

Domen acknowledges the wrapper approach works when all callers are under the user’s control, but points out that in practice, worktrees can be created or removed by IDEs, AI coding agents, scripts, or direct user commands—none of which can be expected to use a shared wrapper. A repository-level hook, he argues, provides a single, reliable place to register lifecycle behavior regardless of how Git is invoked. He also highlights the difficulty of reliably reproducing `git worktree prune` in a wrapper, since it may remove zero or many entries, and a wrapper would have to guess which ones were actually pruned.

To address Junio’s concern about hook proliferation, Domen proposes consolidating the three hooks (`post-worktree-add`, `-remove`, `-move`) into a single `post-worktree` hook with a unified interface that distinguishes events by a subcommand argument. This would also address Caleb White’s earlier feedback about passing information Git already knows (like worktree paths and IDs) rather than requiring hooks to query it. Domen asks whether this narrower design, combined with the need to observe operations from uncontrolled callers, would meet the bar for a native hook.

The response is substantive and directly engages with Junio’s critique, but it does not yet resolve the fundamental question of whether the feature belongs in Git. The thread remains open, with the next step likely being Junio’s reaction to the proposed unified hook design. If accepted, this could lead to a v3 reroll; if not, Domen may need to reconsider the approach entirely. The patch set is still under review and not yet cooking in `next`.
