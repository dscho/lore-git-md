This is a CI/build system patch, the second iteration of a standalone improvement to GitHub Actions workflow configuration. The patch refines the concurrency control logic introduced in v1 to cancel stale workflow runs for pull requests while preserving the existing `skip-if-redundant` optimization for regular pushes.

The key change in v2 is a more detailed commit message that explicitly addresses the edge case Junio C Hamano raised in his review of v1: the new configuration now includes the workflow name in the concurrency group, ensuring each workflow has its own group per commit or pull request. This prevents simultaneous workflows triggered by the same commit from interfering with each other. The commit message also clarifies the old behavior (all workflows sharing a commit hash were in the same group) and the new behavior (separate groups per workflow, with cancellation enabled only for pull requests).

The implementation modifies `.github/workflows/main.yml` to use a dynamic `concurrency.group` expression that switches between pull request number and commit hash based on the event type, and sets `cancel-in-progress` to true only for pull request events. The code comment has been expanded to explain both the pull request and push behaviors, making the configuration self-documenting.

This version appears to be a direct response to Junio’s feedback, addressing his concern about workflow interference while maintaining the original goal of reducing CI resource waste. The patch is now more explicit about its scope and edge cases, which should make it easier to review and merge. No new technical risks have been introduced; the change remains confined to CI configuration and does not affect Git’s core functionality.
