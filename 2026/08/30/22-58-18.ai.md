This is a substantive reply in the ongoing bugfix thread about negative pathspec handling in `git ls-files` and `git add`. Junio C Hamano clarifies his earlier suggestion, agreeing with Diogo Castro that computing the common prefix *only* over positive pathspecs and then stripping it from both positive and negative pathspecs is incorrect. He now proposes a different approach: the common prefix should be recalculated to include *both* positive and negative pathspecs, but only when the negative pathspecs share a meaningful prefix with the positives.

The example Junio provides—`git add -- a/b/c a/b/d ':!a/b/x'`—illustrates the core design question: should negative pathspecs be treated as absolute (Diogo's current patch) or relative to the full tree (Junio's alternative)? In this case, the common prefix of all pathspecs (positive and negative) is `a/b/`, so stripping it would leave the negative pathspec as `:!x`, which would exclude `a/b/x` but not `a/b/c/x` or `a/y`. This aligns with Junio's preference for making negative pathspecs relative to the full tree, rather than preserving their absolute interpretation.

The discussion remains unresolved, but Junio's reply narrows the scope of disagreement. Both agree that the current behavior (stripping the positive-only prefix from negatives) is wrong, but they differ on whether the fix should preserve the performance optimization (Diogo's approach) or prioritize intuitive semantics (Junio's). No implementation of Junio's alternative has been proposed yet, so the thread is still at the design stage. The key technical detail to watch is whether the common prefix calculation will be extended to include negative pathspecs, which would affect both correctness and performance in edge cases like `git add -- a/b/c a/b/d ':!*.md'`.
