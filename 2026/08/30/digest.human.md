## Notable threads

### Unified `post-worktree` hook proposed to address design objection
The `post-worktree-*` hook series, which adds automation triggers for worktree lifecycle events, faced a fundamental design objection from Junio C Hamano, who argued that user-written shell wrappers could achieve the same functionality. Domen Kožar responded with a compromise: replacing the three separate hooks (`post-worktree-add`, `post-worktree-remove`, `post-worktree-move`) with a single unified `post-worktree` hook using a subcommand-style interface (`add`, `move`, `remove`) and passing all relevant paths and the worktree ID as arguments.

Domen contended that a Git-native hook is the only reliable way to notify external tools (like devenv, IDEs, or AI agents) of worktree lifecycle events triggered by callers outside the tool’s control, such as a user running `git worktree remove` directly or an IDE invoking `git worktree prune`. He cited racing with other worktree operations, handling damaged entries, and the inability to require all callers to use a wrapper as reasons a wrapper-based approach is insufficient. The proposed interface is narrower than the original series but retains the same core functionality, and Domen explicitly tied it to earlier feedback about passing information Git already has.

### Architectural concern raised about `dk/use-nsec-runtime` series
The `dk/use-nsec-runtime` series, which replaces the build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`), is technically sound and ready to graduate to `master`. However, Junio C Hamano raised a long-term architectural concern: the new dependency on `repo_config_values()` in `is_racy_stat()` forces an ordering constraint on future work. Specifically, any effort to support submodule operations in-process (e.g., `git diff --recurse-submodules`) will now require `repo_config_values()` to work on arbitrary repositories, not just `the_repository`. This is not a regression—`repo_config_values` was already limited to `the_repository`—but the new call site in `is_racy_stat()` makes the limitation more visible. The patch itself remains ready for `master`; the concern is forward-looking and does not block graduation.

### Use-after-free regression in `git stash show` reported
Nicolas Le Cam reported a use-after-free regression in `git stash show` when `--src-prefix` or `--dst-prefix` is used, introduced in Git 2.52.0 by commit 3ea35c64b ("stash: tell setup_revisions() to free our allocated strings"). The issue causes garbage in the diff header (e.g., `diff --git Uf.txt Uf.txt`) instead of the expected `diff --git a/f.txt b/f.txt`. The root cause is `OPT_STRING_F` storing pointers into `argv` elements that are later freed while `struct diff_options` still holds dangling pointers to those strings. The corruption is deterministic across versions but varies between runs in 2.53.0, strongly suggesting heap memory reuse after free. The report includes exact reproduction steps, expected vs. actual behavior, and a plausible root cause analysis, highlighting real-world impact on tools like `lint-staged` that rely on parseable diff output.

### Negative pathspec handling debate continues
The bugfix patch addressing incorrect prefix-stripping for negative pathspecs in `git ls-files` and `git add` remains unresolved. Diogo Castro argued that the "strip the common prefix" optimization is purely a performance feature for positive pathspecs, and extending it to negative pathspecs could negate its benefits. He provided the example `git add -- a/b/c a/b/d ':!*.md'`, where no common prefix exists across all pathspecs, forcing a full working-directory walk even though the positive pathspecs alone would allow limiting the walk to `a/b/`. Junio C Hamano clarified that the common prefix should be recalculated to include *both* positive and negative pathspecs, but only when the negative pathspecs share a meaningful prefix with the positives. The example `git add -- a/b/c a/b/d ':!a/b/x'` illustrates the core design question: should negative pathspecs be treated as absolute (Diogo's approach) or relative to the full tree (Junio's alternative)? The discussion remains at the design stage, with no alternative implementation proposed yet.
