This is a CI/build system patch, now receiving a **tested review** from Junio C Hamano. The review explicitly tests the edge case raised during the v1 discussion: whether a commit pushed to a user’s own repository (triggering a `push` event) and then submitted as a pull request (triggering a `pull_request` event) would now run twice in parallel, wasting CI resources.

Junio’s concern is that the v2 patch splits the concurrency group by workflow name and event type, so the same commit could end up in two separate groups (`workflow-name-commit-sha` for the push and `workflow-name-pull-request-number` for the PR). He suspects this scenario is rare in practice—most contributors push to forks without CI enabled—but still wants to confirm before merging. The review is substantive: it identifies a potential regression in the `skip-if-redundant` optimization for non-PR pushes, even if the risk is low. No objections are raised; the tone is exploratory rather than critical.
