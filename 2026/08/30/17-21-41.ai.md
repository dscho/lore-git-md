This is Domen Kožar’s response to Junio C Hamano’s fundamental design objection against the `post-worktree-*` hook series. The email proposes a compromise: replacing the three separate hooks (`post-worktree-add`, `post-worktree-remove`, `post-worktree-move`) with a single unified `post-worktree` hook that uses a subcommand-style interface (`add`, `move`, `remove`) and passes all relevant paths and the worktree ID as arguments.

The key argument is observability: Domen contends that a Git-native hook is the only reliable way to notify external tools (like devenv, IDEs, or AI agents) of worktree lifecycle events when those events are triggered by callers outside the tool’s control (e.g., a user running `git worktree remove` directly, or an IDE invoking `git worktree prune`). He cites specific pain points—racing with other worktree operations, handling damaged entries, and the inability to require all callers to use a wrapper—as reasons a wrapper-based approach is insufficient. Concrete examples from Alexander (Xcode state cleanup) and Phillip Wood (per-worktree config copying) are invoked to illustrate real-world use cases that would benefit from a standardized hook.

The proposed interface is narrower than the original series but retains the same core functionality: absolute paths, worktree IDs, and one event per pruned entry. Domen explicitly ties this to Caleb White’s earlier feedback about passing information Git already has, framing it as a way to avoid requiring hooks to query Git themselves. The email ends by asking whether this compromise meets Junio’s bar for a native hook, signaling openness to further iteration but seeking clarity before investing more effort. No new code is attached; this is purely a design discussion reply.
