Core problem or goal
Fix a clamping bug in Git's zlib wrapper (`git-zlib.c`) where `size_t` values were incorrectly clamped to the *bits* of `unsigned long` rather than its maximum value (`ULONG_MAX`). This could produce invalid buffer sizes (including zero) for zlib on platforms where `unsigned long` and `size_t` differ in bit size, affecting operations like object compression or packfile handling for very large buffers.

Current status
Patch submitted as a single commit via GitGitGadget. No prior discussion or review feedback yet. The fix is minimal and targeted, altering only the clamping logic in `zlib_pre_call()` and `zlib_post_call()` via a new helper function `zlib_uLong_cap()`. No tests or documentation changes included.

Key technical details
- **File touched**: `git-zlib.c`
- **New symbol**: `zlib_uLong_cap()` (helper function to clamp `size_t` to `ULONG_MAX`)
- **Behavior change**: Corrects clamping logic to use `ULONG_MAX` instead of `~0UL` (which was interpreted as bit width on some platforms).
- **Subsystems affected**: zlib compression/decompression (used in object storage, packfiles, etc.).
- **Edge case**: Platforms with `sizeof(size_t) > sizeof(unsigned long)` (e.g., 64-bit `size_t` with 32-bit `unsigned long`).
- **No on-disk format changes** or new CLI/config options.
