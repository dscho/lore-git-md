Subject: [PATCH] git-zlib: fix clamping of size_t to uLong
Series version: standalone patch (no series)
Originating author: Johannes Schindelin (Dscho)
Thread type: bugfix

Core problem or goal
Fix a clamping bug in Git's zlib wrapper (`git-zlib.c`) where `size_t` values were incorrectly clamped to the *bits* of `unsigned long` rather than its maximum value (`ULONG_MAX`). This could produce invalid buffer sizes (including zero) for zlib on platforms where `unsigned long` and `size_t` differ in bit size, affecting operations like object compression or packfile handling for very large buffers (>4GB).

Current status
Patch submitted as a single commit via GitGitGadget. Junio C Hamano reviewed the patch, confirming it as "an obvious fix" for the regression introduced in commit `d05d666977` (2026-05-08). The fix is minimal, altering only the clamping logic in `zlib_pre_call()` and `zlib_post_call()` via a new helper function `zlib_uLong_cap()`. No tests or documentation changes are included, and no further changes are requested. The patch is on track for merging.

Key technical details
- **File touched**: `git-zlib.c`
- **New symbol**: `zlib_uLong_cap()` (helper function to clamp `size_t` to `ULONG_MAX`)
- **Behavior change**: Corrects clamping logic to use `ULONG_MAX` instead of `~0UL` (which was interpreted as bit width on some platforms). The fix ensures values are clamped to the 0–4GB range expected by zlib's `uLong` type.
- **Subsystems affected**: zlib compression/decompression (used in object storage, packfiles, etc.).
- **Edge case**: Platforms with `sizeof(size_t) > sizeof(unsigned long)` (e.g., 64-bit `size_t` with 32-bit `unsigned long`).
- **No on-disk format changes** or new CLI/config options.
- **Regression source**: Commit `d05d666977` (2026-05-08), which aimed to handle >4GB data streams but misclamped sizes.
