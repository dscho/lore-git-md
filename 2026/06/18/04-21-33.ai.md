This is a follow-up in the `fetch.followRemoteHEAD` global configuration series. The thread is now focused on a single remaining design question: how to handle invalid configuration values for `fetch.followRemoteHEAD` and its per-remote counterpart.

Matt Hunter acknowledges Junio’s explanation of the ideal behavior—invalid values should be silently ignored if unused but warned or died upon if consulted—and agrees the current `git_config()` callback mechanism cannot easily implement this. He pushes back slightly on the idea of dying for unrecognized values, arguing that falling back to "never" with a warning is more user-friendly, especially when users run newer configurations on older Git versions. He offers to add a `NEEDSWORK` comment and a warning to the `fetch.followRemoteHEAD` parser (matching the per-remote behavior) to resolve the last open point before merging.

The rest of the series remains uncontroversial and merge-ready. This exchange is purely about a design nuance in configuration validation; no functional changes to the feature itself are proposed. The tone is collaborative, and the resolution—adding a `NEEDSWORK` comment and a warning—would close the thread. Key technical details for future reference: the global setting follows the `fetch.prune`/`remote.*.prune` precedence pattern, excludes "warn-if-not-$branch" at the global level, and integrates with the advice subsystem (`advice.fetchRemoteHEADWarn`). The configuration parser lives in `builtin/fetch.c`, and the validation concern applies equally to the existing per-remote `remote.<name>.followRemoteHEAD`.
