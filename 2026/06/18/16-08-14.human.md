This is Junio C Hamano, the Git maintainer, weighing in on the **stacked-branch safety** question raised by Phillip Wood in Harald Nordgren’s `git branch --delete-merged` series. The series aims to provide safe, automated cleanup of merged local branches, and this discussion centers on whether the command should protect branches that serve as upstreams for *other* branches not slated for deletion.

Junio’s response is skeptical of the need for this protection. He acknowledges the practice of stacked branches (where one branch builds on another) but argues that once a base branch has been merged and "graduated," it is no longer needed—even if other branches still depend on it. His reasoning: when rebasing a stacked branch, users typically reuse the *result* of merging the base branch into `main` (or another integration branch) rather than the base branch itself. If the base branch is deleted, the rebase can still proceed using the merge commit, so no workflow is broken.

This is a **key clarification** for the series’ safety design. Junio’s position suggests the stacked-branch protection may be unnecessary, which would simplify the implementation (avoiding the need to track upstream relationships during deletion). However, his question—*"Or am I missing something?"*—leaves room for counterarguments. The thread’s next step likely hinges on whether Harald or Phillip can demonstrate a realistic scenario where deleting a merged base branch *would* disrupt a stacked workflow.

For readers following the series, this exchange underscores that the core safety mechanisms (e.g., preserving checked-out branches, respecting push divergence) are settled, but the stacked-branch question remains open. Junio’s input carries significant weight, so if no compelling counterexample emerges, the protection may be dropped in the next iteration.
