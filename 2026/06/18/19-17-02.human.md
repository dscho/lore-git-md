This is a feature patch series that moves the `--squash` functionality from `git rebase` to a new `git history squash` subcommand, following the mailing-list discussion that favored a standalone tool over a rebase option. The series is now at v3 and consists of four patches.

Harald Nordgren shifts the implementation to `git history`, a command introduced by Patrick Steinhardt in 2025 as a unified interface for history-editing operations. The new `git history squash <revision-range>` folds an arbitrary commit range into its oldest commit, reusing that commit’s message and replaying any descendants on top. This design directly addresses Phillip Wood’s efficiency concern from the rebase thread: instead of picking each commit individually (which could trigger repeated conflict resolution), the new implementation computes a single three-way merge of the entire range against the upstream, mirroring `git merge --squash`.

The series adds 521 lines of code and a dedicated test script (`t/t3454-history-squash.sh`). Key user-facing features include support for arbitrary revision ranges (e.g., `@~3..` or `@~5..@~2`), graceful handling of merges inside the folded range, and a `--reedit-message` option that seeds the editor with every message from the folded commits, not just the oldest. The implementation touches `builtin/history.c` and adds a small helper in `Documentation/git-history.adoc`.

The cover letter explicitly ties this version to the earlier rebase discussion, noting that the move to `git history` resolves both the architectural efficiency issue and the workflow-integration debate. The series looks well-motivated and technically sound, with thorough test coverage and clear documentation. It should now be ready for focused review on the new command’s behavior and edge cases.
