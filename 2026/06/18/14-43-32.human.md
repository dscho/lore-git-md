This is a documentation patch thread, specifically a reply to Junio C Hamano’s v2 update to `Documentation/SubmittingPatches`. Kristoffer Haugsbakk raises a tangential but substantive discussion about the project’s long-standing practice of requiring code submissions for design proposals, rather than entertaining design-only discussions.

Kristoffer argues that the current policy—summarized in Junio’s "make us come to you, begging" canned response—is at odds with the new guidance’s emphasis on sparing effort when a design isn’t solid. He describes a common scenario: a contributor proposes a feature idea, asks if it would be accepted, and is told to submit code first, even if the implementation would be time-consuming. Kristoffer sees this as inefficient, especially for contributors who aren’t experienced C or Git developers, and suggests that design-only discussions could filter out unworkable ideas early, saving effort for both contributors and reviewers.

The reply doesn’t directly challenge Junio’s patch (which remains uncontroversial and narrowly scoped), but it surfaces a tension in the project’s contribution culture. Kristoffer’s critique is framed as a philosophical mismatch: the new documentation encourages early design discussion, while the canned response discourages it. He also notes the lack of a formal project idea tracker, implying that the mailing list is the only venue for such discussions, which may not be ideal for lightweight design proposals.

This is a surface-level review in the sense that it doesn’t engage with the technical content of Junio’s patch, but it’s substantive in its critique of project norms. The discussion is unlikely to derail Junio’s patch, but it may spark broader conversation about how the project handles early-stage contributions. For now, it’s a thoughtful observation from a frequent documentation contributor, worth noting for anyone following Git’s governance evolution.
