Thread identity
Subject: RFC: pinned references (ref + expected OID invariant)
Series version: none (thread root)
Originating author: Erik Östlund
Thread type: RFC / design discussion

Core problem or goal
Introduce a first-class Git concept called “pinned references”: a way to specify a reference (e.g., a tag) together with an expected object ID, ensuring that the ref exists, resolves, and points to the exact OID given. The goal is to combine the human readability of refs with the immutability of object IDs, creating a stable, meaningful reference that external tooling does not have to enforce.

Current status
Early-stage idea; no prior discussion or terminology in Git for this invariant. No code or patches exist. The strawman syntax (`refs/tags/v1.2.3?oid=a1b2c3d4`) has been largely set aside in favor of exploring whether the existing `<describeOutput>` syntax (`v2.54.0-0-g0b13e48a3`) could be extended with enforcement. Junio C Hamano has ruled out modifying `<describeOutput>` itself, as its behavior is too entrenched to change. The discussion now centers on whether a new mechanism (new command, new option, or new syntax) is justified by the use cases.

Key technical details
- No existing plumbing or porcelain command enforces this two-part check; the closest is `git rev-parse --verify <ref>^{object}`, which verifies type but not OID.
- Strawman syntax (`?oid=...`) is no longer under active consideration.
- `<describeOutput>` (`v2.54.0-0-g0b13e48a3`) expresses “ref plus OID” but does not enforce the invariant; Junio has clarified that changing its behavior is not feasible.
- Junio’s hypothetical enforcement rule: if the hop count is `-0-`, the hex part must exactly match the tag’s target OID; if the hop count is non-zero, the hex part must name a descendant commit.
- No files, subsystems, or symbols have been identified; the proposal remains conceptual.
- No on-disk format changes are implied.

Open questions and loose ends
- **Syntax**: Is a new command-line option (e.g., `git show v1.2.3 --expected-oid=a1b2c3d4`) preferable to a new syntax, or should this be a dedicated command (e.g., `git pin-verify`)?
- **Use cases**: Are the motivating scenarios (deployment, CI/CD) common enough to justify a new feature, or is this a niche need? Would users adopt it, or would they continue to enforce the invariant manually in scripts?
- **Safety**: Could this encourage users to rely on OIDs in ways that break when objects are garbage-collected or pruned? How should the feature handle dangling refs or pruned objects?
- **Implementation**: Would this require changes to the ref backend, or can it be implemented as a higher-level CLI check? If a new command is introduced, where should it live (builtin, script, or contrib)?
- **Documentation**: Patrick Steinhardt noted that `<describeOutput>` is under-documented and user-surprising; any new mechanism would need clear documentation and examples.

Participant positions
- **Erik Östlund (author)**: Proposes the concept, seeks feedback on terminology, prior art, and design direction. Open to alternative syntax and use-case validation. Has not yet responded to Junio’s input on `<describeOutput>`.
- **Patrick Steinhardt**: Points out that Git already has a syntax (`<describeOutput>`) that expresses “ref plus OID,” but it lacks enforcement. Does not take a position on whether the proposal is worth pursuing, but highlights the existing mechanism as a starting point. Emphasizes that `<describeOutput>` is under-documented and user-surprising.
- **Junio C Hamano (maintainer)**: Engages with the idea as a hypothetical but rules out modifying `<describeOutput>` due to its entrenched behavior. Suggests that any enforcement would need to be implemented as a new mechanism (new command, option, or syntax). Does not endorse or oppose the proposal, but his input shifts the discussion away from `<describeOutput>` as a viable path.

Related work
- Git’s `<describeOutput>` syntax (`gitrevisions(7)`), which provides a way to combine a ref and an OID but does not enforce the invariant. No prior versions or external dependencies identified.
