Thread identity
Subject: RFC: pinned references (ref + expected OID invariant)
Series version: none (thread root)
Originating author: Erik Östlund
Thread type: RFC / design discussion

Core problem or goal
Introduce a first-class Git concept called “pinned references”: a way to specify a reference (e.g., a tag) together with an expected object ID, ensuring that the ref exists, resolves, and points to the exact OID given. The goal is to combine the human readability of refs with the immutability of object IDs, creating a stable, meaningful reference that external tooling does not have to enforce.

Current status
Early-stage design discussion; no code or patches exist. The strawman syntax (`refs/tags/v1.2.3?oid=a1b2c3d4`) has been abandoned. Junio C Hamano ruled out modifying the existing `<describeOutput>` syntax (`v2.54.0-0-g0b13e48a3`) due to its entrenched behavior and backward-compatibility constraints. The discussion now focuses on whether a new mechanism (new command, new option, or new syntax) is justified by the use cases and whether it can avoid introducing parsing ambiguities or breaking existing workflows.

Key technical details
- No existing plumbing or porcelain command enforces this two-part check; the closest is `git rev-parse --verify <ref>^{object}`, which verifies type but not OID.
- `<describeOutput>` (`v2.54.0-0-g0b13e48a3`) expresses “ref plus OID” but is inherently lossy: it embeds an OID for portability, not verification, and is designed to work even when the receiver does not have the same refs as the sender.
- Junio’s hypothetical enforcement rule (if hop count is `-0-`, the hex part must exactly match the tag’s target OID; if non-zero, the hex part must name a descendant commit) is not viable due to backward-compatibility risks.
- Jeff King (Peff) highlighted that `<describeOutput>` parsing is already ambiguous (e.g., `foo-gcc14` misinterpreted as a describe pattern) and that any enforcement mechanism would risk breaking scripts or tools that rely on its current behavior.
- No files, subsystems, or symbols have been identified; the proposal remains conceptual. No on-disk format changes are implied.

Open questions and loose ends
- **Syntax**: Is a new command-line option (e.g., `git show v1.2.3 --expected-oid=a1b2c3d4`) preferable to a new syntax, or should this be a dedicated command (e.g., `git pin-verify`)? Can any new syntax avoid the parsing ambiguities that plague `<describeOutput>`?
- **Use cases**: Are the motivating scenarios (deployment, CI/CD) common enough to justify a new feature, or is this a niche need? Would users adopt it, or would they continue to enforce the invariant manually in scripts?
- **Safety**: Could this encourage users to rely on OIDs in ways that break when objects are garbage-collected or pruned? How should the feature handle dangling refs or pruned objects?
- **Implementation**: Would this require changes to the ref backend, or can it be implemented as a higher-level CLI check? If a new command is introduced, where should it live (builtin, script, or contrib)?
- **Documentation**: Patrick Steinhardt noted that `<describeOutput>` is under-documented and user-surprising; any new mechanism would need clear documentation and examples to avoid similar confusion.

Participant positions
- **Erik Östlund (author)**: Proposes the concept, seeks feedback on terminology, prior art, and design direction. Has not yet responded to Junio’s or Peff’s input on `<describeOutput>`.
- **Patrick Steinhardt**: Points out that Git already has a syntax (`<describeOutput>`) that expresses “ref plus OID,” but it lacks enforcement. Does not take a position on whether the proposal is worth pursuing, but highlights the existing mechanism as a starting point. Emphasizes that `<describeOutput>` is under-documented and user-surprising.
- **Junio C Hamano (maintainer)**: Rules out modifying `<describeOutput>` due to its entrenched behavior and backward-compatibility constraints. Suggests that any enforcement would need to be implemented as a new mechanism (new command, option, or syntax). Does not endorse or oppose the proposal, but his input shifts the discussion away from `<describeOutput>` as a viable path.
- **Jeff King (Peff)**: Raises a critical backward-compatibility concern: `<describeOutput>` is designed to work even when the receiver does not have the same refs as the sender, and enforcing a strict invariant would break existing workflows. References prior threads showing that `<describeOutput>` parsing is already ambiguous and that any enforcement mechanism would risk regressions. Aligns with Junio’s stance that `<describeOutput>` is not a viable path for pinned references.
