Subject: RFC: pinned references (ref + expected OID invariant)
Series version: none (thread root)
Originating author: Erik Östlund
Thread type: RFC / design discussion

Core problem or goal
Introduce a first-class Git concept called “pinned references”: a way to specify a reference (e.g., a tag) together with an expected object ID, ensuring that the ref exists, resolves, and points to the exact OID given. The goal is to combine the human readability of refs with the immutability of object IDs, creating a stable, meaningful reference that external tooling does not have to enforce.

Current status
Early-stage idea; no prior discussion or terminology in Git for this invariant. No code or patches exist yet. The strawman syntax is `refs/tags/v1.2.3?oid=a1b2c3d4`, but alternatives are now under discussion. Patrick Steinhardt has pointed out that Git already has a `<describeOutput>` syntax (`v2.54.0-0-g0b13e48a3`) that expresses a similar concept, but it does not enforce the OID invariant.

Key technical details
- No existing plumbing or porcelain command enforces this two-part check; the closest is `git rev-parse --verify <ref>^{object}`, which verifies type but not OID.
- Strawman syntax uses URL-style query parameters (`?oid=...`).
- Patrick Steinhardt’s alternative: extend the existing `<describeOutput>` syntax (e.g., `v2.54.0-0-g0b13e48a3`) with a `--verify` flag or similar enforcement mechanism.
- No files, subsystems, or symbols have been identified yet; the proposal remains conceptual.
- No on-disk format changes are implied at this stage.

Open questions and loose ends
- Syntax: Is `?oid=...` idiomatic, or should this leverage the existing `<describeOutput>` syntax with enforcement added? Is a new command-line option (e.g., `git show v1.2.3 --expected-oid=a1b2c3d4`) preferable?
- Use cases: Are the motivating scenarios (deployment, CI/CD) common enough to justify a new feature, or is this a niche need?
- Safety: Could this encourage users to rely on OIDs in ways that break when objects are garbage-collected or pruned?
- Implementation: Would this require changes to the ref backend, or can it be implemented as a higher-level CLI check? If leveraging `<describeOutput>`, would enforcement require changes to `git rev-parse` or a new command?
- Documentation: Patrick notes that `<describeOutput>` is under-documented and surprising to users; any solution would need to address this.

Participant positions
- Erik Östlund (author): Proposes the concept, seeks feedback on terminology, prior art, and design direction. Open to alternative syntax and use-case validation.
- Patrick Steinhardt: Points out that Git already has a syntax (`<describeOutput>`) that expresses "ref plus OID," but it lacks enforcement. Does not take a position on whether Erik’s proposal is worth pursuing, but highlights the existing mechanism as a starting point for discussion. Emphasizes that `<describeOutput>` is under-documented and user-surprising.

Related work
- Git’s `<describeOutput>` syntax (`gitrevisions(7)`), which provides a way to combine a ref and an OID but does not enforce the invariant. No prior versions or external dependencies identified.
