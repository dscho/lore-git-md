This is an RFC proposal for a new Git feature: **pinned references**—a way to specify a reference (like a tag) together with an expected object ID, ensuring both the ref and the OID exist *and* that the ref resolves to that OID.

Erik Östlund asks whether Git already has terminology, prior discussion, or a native mechanism for this "ref plus expected OID" invariant. The short answer is no—this appears to be a novel idea, at least in the form proposed. The strawman syntax (`refs/tags/v1.2.3?oid=a1b2c3d4`) suggests a URL-like query parameter, but Erik is open to alternatives.

The motivation is clear: tags are human-readable but mutable (can be moved or deleted), while object IDs are immutable but opaque. Combining both gives users a way to reference objects with *both* stability and meaning, without relying on external tooling to enforce the invariant. This could be useful for deployment systems, CI/CD pipelines, or any workflow where a tag’s immutability is critical but its human-readable name is also needed.

There’s no indication of prior art in Git itself—no config keys, command-line options, or plumbing commands that enforce this kind of two-part check. The closest existing feature is `git rev-parse --verify <ref>^{object}`, which verifies that a ref resolves to a specific object type, but it doesn’t let you specify the expected OID upfront. Erik’s proposal would make this a first-class concept, not just a post-hoc check.

The thread context (if any) isn’t provided here, but this email is the thread root. If discussion develops, likely points of contention will include:
- **Syntax**: Is `?oid=...` the right way to express this, or would a new command-line option (e.g., `git show v1.2.3 --expected-oid=a1b2c3d4`) be more Git-like?
- **Use cases**: Are there enough real-world scenarios where this is needed, or is this solving a niche problem?
- **Safety**: Could this encourage users to rely on OIDs in ways that break when objects are garbage-collected or pruned?
- **Implementation**: Would this require changes to the ref backend, or could it be implemented as a higher-level check in the CLI?
