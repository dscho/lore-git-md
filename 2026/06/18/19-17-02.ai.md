This is a feature patch series introducing `git history squash`, a new subcommand that folds a commit range into its oldest commit while preserving descendant history. The series is the third iteration of Harald Nordgren’s proposal, now reworked as a standalone `git history` operation rather than a `git rebase --squash` option, in direct response to the architectural and efficiency concerns raised in the thread.

The implementation takes an arbitrary revision range (e.g., `@~3..` or `@~5..@~2`), computes a single three-way merge of the entire range against the oldest commit’s parent, and replays any descendants on top. This design eliminates the repeated conflict stops that Phillip Wood identified in the earlier rebase-based approach. A merge commit inside the range is handled gracefully; only ranges with multiple bases are rejected. The `--reedit-message` option now seeds the editor with every folded-in message, not just the oldest, addressing the user-experience gap Phillip noted.

Four patches touch `builtin/history.c` (287 insertions, 38 deletions), add a new man page section in `Documentation/git-history.adoc`, and introduce a 250-line test script `t/t3454-history-squash.sh`. The series is based on `95e20213fa` and is available as GitGitGadget PR 2337. The range-diff shows the complete rewrite: the rebase implementation is dropped, and the history code is refactored to support the new subcommand.

This version directly addresses the two main technical objections from the previous round—efficiency and workflow integration—by moving the feature out of rebase and into the `git history` roadmap championed by Patrick Steinhardt. The implementation appears solid, with thorough test coverage and clear documentation, and should now be ready for Junio’s final assessment.
