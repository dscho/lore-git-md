This is a zsh completion bugfix for the `git -C <path>` global option, now receiving a **substantive review** from D. Ben Knoble. The patch itself remains a well-scoped, 9-line fix that restores expected completion behavior for `git -C <path> <command> <TAB>`, but the review surfaces deeper issues and opportunities for improvement.

Knoble confirms the patch works as advertised—completion now prioritizes directories after `-C`—but notes two limitations. First, the `_directories` helper does not account for chained `-C` options: `git -C dir -C <TAB>` completes paths relative to the current directory, not `dir`. Second, the broader issue Junio flagged—hard-coded command index assumptions breaking completion after other global options (`--git-dir`, `-c`, etc.)—remains unaddressed. Knoble suggests a more ambitious approach: accumulate all global options (not just `-C`) and pass the effective working directory to `_directories` via zsh’s state mechanism (`->dir`), though he acknowledges this would require a larger rewrite.

The review also reveals a separate, pre-existing quirk: `git -<TAB>` (without a command) produces redundant option descriptions and an unwanted file listing. This is not caused by the patch but is now more visible; Knoble’s `_complete_help` dumps show the completion system is falling back to `_files` after exhausting option tags.

No objections to the patch’s direction, but the feedback shifts the thread’s focus from "does this fix `-C`?" to "how far should we go in generalizing global-option handling?" The author’s original offer to extend the fix in a follow-up remains on the table. For now, the patch is a clear improvement for `-C` users, but the discussion suggests a more comprehensive solution may follow.
