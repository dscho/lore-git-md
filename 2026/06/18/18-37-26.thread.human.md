This thread introduces a new RFC proposal for **pinned references** in Git—a way to specify a reference (like a tag) alongside an expected object ID, ensuring both exist *and* that the ref resolves to that exact OID. The idea, proposed by Erik Östlund, aims to bridge the gap between human-readable tags (mutable) and immutable object IDs (opaque), offering a stable yet meaningful way to reference objects in workflows like deployments or CI/CD pipelines.

Git currently lacks a native mechanism for this "ref plus OID" invariant. The closest existing feature is `git rev-parse --verify <ref>^{object}`, which verifies a ref’s object type but doesn’t enforce an upfront OID check. Erik’s strawman syntax (`refs/tags/v1.2.3?oid=a1b2c3d4`) suggests a URL-like query parameter, though he’s open to alternatives. Key open questions include whether the syntax feels Git-like, whether the use cases justify the feature, and how it might interact with garbage collection or ref backend changes.

So far, this is purely exploratory—no code or patches have been shared. If discussion develops, expect debates over syntax, safety implications, and whether this solves a widespread problem or a niche one. For now, it’s an early-stage idea worth tracking if Erik (or others) follow up with a concrete proposal.
