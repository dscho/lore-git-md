This thread explores a new Git concept called “pinned references,” which would let users specify a reference (like a tag) alongside an expected object ID, ensuring the ref both exists and points to that exact commit. The idea aims to combine the readability of refs with the immutability of object IDs, giving external tools a stable way to reference commits without enforcing the invariant themselves. The discussion is still in the early design phase, with no code or patches yet.

The proposal initially considered extending Git’s existing `<describeOutput>` syntax (e.g., `v2.54.0-0-g0b13e48a3`), but Junio C Hamano ruled this out due to its entrenched behavior—it’s designed to be portable across repositories, not to enforce strict invariants. Jeff King (Peff) reinforced this point, warning that modifying `<describeOutput>` could break existing workflows that rely on its flexibility. For example, scripts might parse these strings without expecting strict validation, and Git’s current parsing is already ambiguous in edge cases (like refs named `foo-gcc14`). The discussion has since shifted toward alternative designs, such as a new command (e.g., `git pin-verify`) or a dedicated option (e.g., `git show v1.2.3 --expected-oid=a1b2c3d4`).

Key open questions remain: whether the use cases (like CI/CD deployments) justify a new feature, how to handle dangling refs or pruned objects, and where to implement the check (CLI, ref backend, or elsewhere). Erik Östlund, the proposal’s author, is seeking feedback on terminology and design, while Patrick Steinhardt noted that `<describeOutput>` is already under-documented and user-surprising—any new mechanism would need clear examples. So far, no one has strongly opposed the idea, but the focus is on finding a design that avoids breaking existing tools.
