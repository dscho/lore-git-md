This is a security and correctness fix for the ongoing `remote-object-info` feature in the GSoC v14 series. The patch addresses two critical issues in the format placeholder validation for remote object queries: a potential segfault from uninitialized `data->type` and incorrect error handling that could block local queries when sharing formats with remote operations.

The solution introduces an explicit allow-list (`remote_object_info_atoms`) for supported remote atoms ("objectname" and "objectsize") and modifies `expand_atom()` to return empty strings for unsupported placeholders in remote mode, matching `for-each-ref`'s behavior for known-but-inapplicable atoms. Key changes include: initializing `data->type` to `OBJ_BAD`, adding a NULL check for `type_name()`, removing the fatal `die()` for unsupported atoms, and updating documentation to reflect the new behavior (empty strings instead of errors for unsupported placeholders).

The patch touches `builtin/cat-file.c` (core validation logic), `Documentation/git-cat-file.adoc` (behavior documentation), and `t/t1017-cat-file-remote-object-info.sh` (updated tests that now expect empty strings instead of fatal errors). The test updates include a new explicit test for empty string returns on unknown placeholders and modifications to existing tests that previously expected `die()` behavior.

This is a substantive fix that resolves real safety issues while maintaining the series' security posture. The allow-list approach provides clear forward compatibility for future metadata types, and the memory safety improvements (initialization + NULL checks) address the segfault risk identified in review. The patch is well-motivated, with clear commit message explanations of both the problems and the chosen solution. All changes are localized to the remote-object-info feature and don't affect existing local `cat-file` behavior.
