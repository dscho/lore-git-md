This is **patch 9/11 in Patrick Steinhardt’s v6 refactoring series**, which restructures the reftable backend to enable lazy-loading of write configuration. The patch splits the `reftable_write_options` struct into two distinct types: `reftable_stack_options` (for stack-level configuration like hash ID and reload callbacks) and the original `reftable_write_options` (for write-specific settings like block size and compression). This separation allows callers to defer parsing write-critical configuration until the first write operation, addressing the "onbranch" recursion issue that motivated the series.

The changes are **mechanical but foundational**, touching 14 files in the `reftable/` directory and `refs/reftable-backend.c`. Key updates include:
- **New `reftable_stack_options` struct** for stack-level settings, replacing the use of `reftable_write_options` in `reftable_new_stack()`.
- **Dynamic write option passing** in functions like `reftable_stack_add()` and `reftable_stack_new_addition()`, which now accept explicit `reftable_write_options` parameters.
- **Hash ID handling** moved from `reftable_write_options` to the writer struct (`struct reftable_writer`), simplifying the API and avoiding redundant parsing.
- **Test updates** to reflect the new function signatures, including passing hash IDs explicitly in unit tests.

The patch is **well-motivated and uncontroversial**, addressing Justin Tobler’s earlier design questions about struct layout and use-cases. The separation of concerns (stack vs. write options) is clean and aligns with the series’ goal of decoupling backend initialization from write-config parsing. No major objections are expected, though reviewers may scrutinize edge cases in concurrent write operations or the impact on external reftable consumers (e.g., JGit). The changes are **backward-compatible** for Git’s internal use, as the reftable backend remains the sole caller of these APIs.
