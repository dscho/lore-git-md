This is the **tenth patch in Patrick Steinhardt’s 11-part v6 refactoring series** modernizing Git’s reference backend infrastructure. It extends the **lazy-loading design** (introduced for the files backend in patch 8/11) to the **reftable backend**, resolving the same "onbranch" configuration recursion issue.

The patch refactors `refs/reftable-backend.c` to **defer parsing write-critical configuration** (e.g., `reftable.blockSize`, `core.logAllRefUpdates`) until the first write operation. This eliminates the chicken-and-egg problem where early config reads (e.g., during `includeif.onbranch` processing) could trigger recursive ref store initialization. Key changes include:
- A new `reftable_be_write_options()` accessor that lazily parses and caches write options (block size, compaction settings, `log_all_ref_updates`) on first use.
- Moving `should_write_log()` to a later position in the file to access the lazy-loading accessor.
- Replacing direct `write_options` field access with calls to `reftable_be_write_options(refs)->opts` throughout the backend (e.g., in `reftable_stack_add()`, `reftable_stack_compact_all()`).
- A new `write_opts_lazy_loaded` struct that mirrors the reftable library’s `reftable_write_options` but adds Git-specific fields (`log_all_ref_updates`, `initialized` flag).

The patch also adds **test coverage** in two places:
1. `t/t0613-reftable-write-options.sh`: Verifies that `reftable.blockSize` can be configured via `includeif.onbranch`.
2. `t/t1400-update-ref.sh`: Adds a generic test confirming `core.logAllRefUpdates` works with "onbranch" conditions across both files and reftable backends.

This is a **well-motivated, low-risk change** that aligns the reftable backend with the files backend’s lazy-loading design. The refactoring is mechanical but critical for the series’ goal of eliminating initialization-order bugs. Justin Tobler’s review feedback (addressed in earlier patches) has already shaped the design, and the patch includes clear code comments explaining the lazy-loading rationale. The only potential concern is whether the new `reftable_be_write_options()` accessor introduces overhead in write-heavy workloads, but no such use-cases exist today. The patch is **ready for final review** and likely to merge as part of the series.
