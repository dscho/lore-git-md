This thread is about a small but practical usability fix for Git’s SSH signature handling. Grayson Tinker noticed that Git currently refuses to show *any* signature details—key, fingerprint, or validity—unless `gpg.ssh.allowedSignersFile` is configured, even if the user only wants to inspect the signature without automated principal validation. The patch relaxes this requirement, allowing basic signature information to be displayed regardless of configuration, while keeping principal validation optional.

The patch itself is straightforward: it touches `gpg-interface.c`, adds a fallback "novalidate" mode when the allowed signers file is unset, and shows the key type, fingerprint, and "Good"/"Bad" status. However, Junio C Hamano raised a usability concern—the patch emits an advice message for *every* SSH-signed commit when the allowed signers file is missing, which could become noisy in bulk operations like `git log --show-signature -100`. The message is currently unsuppressible, and Junio questioned whether the use case (inspection without validation) is common enough to justify this trade-off.

Grayson responded by explaining their motivation: they rely on cryptographic validation (ensuring commit integrity) but don’t need principal validation (verifying the signer’s identity). They acknowledged the noise issue but argued that the current behavior (an error) was also repetitive and worse. They’re open to making the advice suppressible but deferred to Junio’s judgment on the best UX balance. The thread is now at a decision point—whether to accept the current trade-off, adjust the advice mechanism, or revisit how common this use case really is. No code changes or tests have been proposed yet, and the patch remains under review.
