This is **patch 10/11 in Patrick Steinhardt’s v6 refactoring series** implementing lazy-loading for Git’s reftable backend. The patch mirrors the lazy-loading design already applied to the files backend (patch 8/11), resolving the "onbranch" configuration recursion issue by deferring write-critical config parsing until the first write operation.

The core change introduces `reftable_be_write_options()`, a lazy-loading accessor that parses and caches write options (block size, compaction settings, `log_all_ref_updates`) on first use. The `write_opts_lazy_loaded` struct in `struct reftable_ref_store` replaces the direct `write_options` field, ensuring config is only read when needed. The patch also moves `should_write_log()` to a later position in the file to access the new accessor, and updates all callers (e.g., `reftable_stack_add()`, `reftable_stack_compact_all()`) to use the lazy-loaded options instead of the raw struct.

Test coverage is expanded with two new tests:
- `t/t0613-reftable-write-options.sh` verifies that `reftable.blockSize` can be set via `includeif.onbranch`.
- `t/t1400-update-ref.sh` adds a generic test confirming `core.logAllRefUpdates` works with "onbranch" conditions, serving as a cross-backend sanity check.

The patch is **mechanical but critical**, completing the lazy-loading design for the reftable backend. It addresses Justin Tobler’s earlier design question about `log_all_ref_updates` placement by keeping it outside `reftable_write_options` (to maintain the library’s generic nature) while ensuring it is parsed consistently with other deferred settings. The changes are low-risk for users but high-impact for developers, eliminating initialization-order constraints and enabling future backend work. No substantive objections remain, and the patch is ready for final review.
