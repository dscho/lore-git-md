This is the **reply in the v5 refactoring series** addressing Justin Tobler’s review of patch 10/11, which extends lazy-loading configuration to the reftable backend. Patrick clarifies the **design rationale** behind the struct layout Justin questioned: `log_all_ref_updates` is kept outside `reftable_write_options` because it belongs to Git’s backend logic, not the reftable library’s internal write machinery.

The distinction is technical but important. `reftable_write_options` (block size, compression, etc.) are **library-level settings** that control how the reftable format itself is written, while `log_all_ref_updates` is a **Git-specific configuration** (`core.logAllRefUpdates`) that determines whether ref updates should generate reflog entries. The reftable library has no knowledge of Git’s config system or reflog semantics, so `log_all_ref_updates` cannot be part of its write options struct. This separation ensures the library remains **generic and reusable** (e.g., for JGit or other tools), while Git’s backend handles its own config-driven behavior.
