Feature feedback for the experimental `git history` command.

Rasmus Villemoes shares positive initial experiences with the new `git history` command, particularly appreciating its split functionality as an improvement over interactive rebase for dividing commits. He identifies two workflow enhancements that would make the tool more powerful:

1. **Iterative splitting**: Currently, when splitting a commit into three or more parts, users must manually track the new SHA-1 of the remaining changes after each split. Rasmus suggests an iterative mode (possibly via `--iter` flag) that would automatically continue splitting the remaining changes without requiring manual SHA-1 lookup between steps.

2. **Automatic atomization**: For cases requiring fine-grained splitting (like reorganizing changes from "row-wise" to "column-wise"), he proposes an `atomize` subcommand that would automatically split a commit into individual hunks, labeling each with filename and hunk number for easier subsequent reorganization via interactive rebase.

The feedback comes from real-world usage and reflects thoughtful consideration of complex editing workflows. The suggestions appear technically feasible and aligned with the command's purpose of simplifying history manipulation. Rasmus also inquires about adding completion support for this experimental command in git-completion.bash, including context-aware commit selection during splitting.

This is constructive feedback from an engaged early adopter, highlighting practical pain points in a new feature while acknowledging its core value. The suggestions merit consideration by the command's maintainers (likely Patrick Steinhardt's team, given their work on new built-ins).
