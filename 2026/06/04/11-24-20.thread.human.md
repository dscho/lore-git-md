Here's a human-readable summary of the thread so far:

A bug report highlights an inconsistency in how Git handles commit-graph Bloom filters. Tomasz Konojacki found that while `git commit-graph write` properly respects the `commitGraph.changedPaths` config to generate changed-path Bloom filters, these filters are unexpectedly omitted during automatic operations like `git gc` and fetches with `fetch.writeCommitGraph` enabled. 

The core issue appears to be that the automatic operations write the commit-graph itself but skip the Bloom filter generation step, despite the configuration being set. This creates a performance optimization gap - the filters, which speed up operations like `git log -L`, are only available when users manually regenerate graphs rather than getting built during routine maintenance. 

The report suggests this is likely unintentional behavior, as there's no obvious reason why the automatic operations would deliberately ignore this configuration. The thread may attract attention from commit-graph experts like Derrick Stolee, as it touches on performance-sensitive graph operations and configuration handling during maintenance tasks.
