This is a follow-up discussion in the thread about improving `git log --follow` behavior for subtree merges. Miklos Vajna responds to Jeff King's earlier concerns by proposing a refined approach to handle rename detection in merge commits.

The key refinement is a more precise rule for determining which parent to follow: rather than always defaulting to the first parent, the patch now examines each parent to see if it has "interesting" changes (using DIFF_FILE_VALID) to the followed file. If exactly one parent shows such changes, that parent's history will be followed, even if it's not the first parent. This maintains the conservative approach for ambiguous cases while specifically addressing the subtree merge scenario.

Miklos explains the technical implementation clearly, noting how the solution avoids making other cases worse while still solving the original problem.
