This is a bug report about Git's trailer parsing behavior, specifically how `--only-trailers` and `%(trailers:only)` format handles URLs in commit messages.

The core issue is that standalone URLs in commit messages (particularly in what would otherwise be trailer blocks) get incorrectly parsed as trailers with the URL scheme (`http`, `https`, `file`) treated as the trailer key. For example, a line containing just `https://example.com` gets normalized to `https: //example.com`.

The reporter, Kristoffer Haugsbakk, provides several concrete examples of problematic cases:
1. URLs intended as non-trailer content getting mangled (NTL)
2. Line-wrapped URLs accidentally creating `https` trailers (LW)
3. Normalization during patch processing introducing malformed trailers (NL)

The report includes analysis of Linux kernel commit messages showing 245 instances where `https: //` appears as a trailer, suggesting this is a real-world issue. Examples demonstrate how both unintended URL-trailers and intentional trailer formatting (like indented `Link` lines) can be affected.

While this behavior is technically consistent with Git's trailer parsing rules, it violates the design goal of avoiding false positives in trailer detection. The reporter suggests special-casing URL schemes to prevent this unwanted normalization, though acknowledges the solution isn't straightforward given edge cases like C-style comments after URL schemes.

The bug affects users who process commit messages with trailer-normalizing commands, particularly in projects where URLs commonly appear at message endings. The Linux kernel examples show this can happen both accidentally and through processing pipelines that normalize trailers.
