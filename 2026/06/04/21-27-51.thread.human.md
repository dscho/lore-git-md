This thread is about a bug in Git’s trailer parsing that mistakenly treats URLs in commit messages as trailers, affecting both `--only-trailers` and `%(trailers:only)` formatting. Kristoffer Haugsbakk reported the issue, identifying three real-world cases where URLs were mangled or misinterpreted, with 245 instances found in the Linux kernel’s history.

Jeff King (Peff) diagnosed the root cause—Git’s overly permissive trailer matching—and proposed a fix: modifying `find_separator()` in `trailer.c` to exclude lines containing `://` from trailer parsing. Junio C Hamano reviewed the approach, calling the `://` heuristic "much more robust" than a scheme whitelist, and the solution was implemented in a patch that handles all URL schemes uniformly while preserving legitimate trailers. The patch includes comprehensive test coverage for the three bug scenarios and updates documentation.

The patch has since been refined to version 2, incorporating Peff’s suggestion to use `starts_with(c, "://")` for better readability, which Junio endorsed. The commit message now explicitly notes the theoretical possibility of false positives (e.g., `1://`), though this edge case was deemed acceptable. The fix has been merged to `master`, resolving the issue without any remaining technical objections. A broader enhancement—special-casing bracketed text `[...]` as non-trailer content—was briefly discussed but remains exploratory. The current solution is minimal, targeted, and maintains Git’s design principles.
