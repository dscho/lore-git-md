This thread resolves a long-standing Windows-specific limitation that prevented Git from correctly handling objects larger than 4GB due to 32-bit truncation of object sizes on LLP64 platforms. The series, originally developed by Philip Oakley and maintained in Git for Windows, has now reached its second iteration (`v2`) with all production changes merged and validated in production.

The core change systematically replaces `unsigned long` with `size_t` in object-file handling code (`object-file.c`, `sha1dc_git.c`, `hash.h`, and ODB source files), ensuring that memory buffer lengths are correctly represented on all platforms where `size_t` is 64-bit. The series includes comprehensive test coverage in `t/t1007-hash-object.sh`, with nine test cases verifying direct file hashing, `--stdin` input, standard hashing, and filtered input with 5GB files. The baseline test (patch 1/6) demonstrated the original failure, while subsequent patches confirmed the fix across all relevant code paths.

Key participants—Johannes Schindelin, Junio C Hamano, and Patrick Steinhardt—have all approved the technical approach. Johannes, who signed off on all patches, confirmed the production validation in Git for Windows and clarified the type rationale, rejecting an alternative `objsize_t` approach in favor of `size_t` for memory-addressable sizes. Patrick’s suggestion to remove the `!LONG_IS_64BIT` prerequisite was accepted, making the 5GB tests universally applicable (though still marked `EXPENSIVE`). The final patch in the series adds a test for the `clean` filter code path, completing the coverage and ensuring no regressions in filtered input handling.

The series is now technically complete, with all design discussions resolved and conflicts addressed in `v2`. The changes are minimal and targeted, focusing solely on type conversions and test coverage, and should merge without further controversy.
