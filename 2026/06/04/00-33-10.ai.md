This is a review from the Git maintainer (Junio C Hamano) on a build system patch that aimed to remove duplicate library references in Makefile link recipes. The review identifies a potential issue with the proposed change's approach to library ordering during linking.

Junio explains that the current duplicate listing of `.a` files (both via explicit filtering and through `$(LIBS)`) serves an important purpose - it ensures object files are processed before library archives during linking. This ordering matters because the linker resolves symbols in a left-to-right pass. The patch's assumption that `$(LIBS)` will always contain all necessary archives in the correct order makes the build more fragile.

The review applies equally to all three modified rules (test helpers, fuzz targets, and unit tests). While the original motivation (eliminating macOS linker warnings) was valid, Junio suggests the solution needs to preserve the explicit ordering guarantee rather than simply removing the duplicate references. This maintains build reliability at the cost of some warning noise.

The review is substantive, engaging with the technical implications of the build process rather than surface-level concerns. It identifies a real correctness consideration that wasn't addressed in the original patch's rationale. The feedback suggests the author will need to find an alternative approach that satisfies both goals: clean builds and correct symbol resolution.
