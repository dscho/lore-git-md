This is feedback on the experimental `git history` command, specifically its `split` subcommand. The author, Rasmus Villemoes, reports positive initial experiences with the tool but suggests two workflow improvements:

1. **Iterative splitting** - Currently, splitting a commit into multiple parts requires manually finding the new SHA-1 after each split. The author proposes an iterative mode that would automatically continue splitting the remaining portion of the commit, similar to how `git add -p` can apply hunks across files.

2. **Automatic atomization** - For cases where a commit needs to be split into individual hunks (e.g., to reorganize changes from "row-wise" to "column-wise"), the author suggests an `atomize` subcommand that would automatically create one commit per hunk with descriptive prefixes like "[<filename> -- hunk #nn]".

The feedback comes from real-world usage and identifies concrete pain points in the current workflow. The suggestions appear well-motivated and technically feasible, though they would require careful design to handle edge cases (e.g., merge conflicts during iterative splitting). The author also asks whether experimental commands can be added to bash completion, specifically requesting commit selection for `git history split`.

This feedback is valuable input for the `git history` feature development, particularly as it comes from actual use rather than hypothetical scenarios. The command is still experimental, so such user experience reports are especially timely for shaping its evolution.
