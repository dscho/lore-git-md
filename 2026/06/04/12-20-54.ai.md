This is a follow-up discussion in the thread about improving `git log --follow` behavior for subtree merges. Miklos Vajna responds to Jeff King's earlier concerns about the patch's approach to handling renames in merge commits.

The key technical clarification is that the patch now uses `DIFF_FILE_VALID()` to determine which merge parents have "interesting" changes to the followed file - specifically changes that affect the file's content or rename status, while ignoring cases where the file is merely added or untouched. When only one parent shows such interesting changes, the patch follows that parent's history regardless of whether it's the first parent.

This addresses Jeff's concern about potentially making other cases worse by maintaining a conservative approach - the logic only activates when there's a clear single parent with relevant changes, preserving existing behavior for ambiguous cases. The implementation remains focused on the subtree merge use case where this single-parent-change scenario commonly occurs.

The exchange shows the patch author thoughtfully considering review feedback while maintaining the original goal of better handling subtree merges. The technical details suggest this is a well-considered refinement of the initial proposal rather than a major rework.
