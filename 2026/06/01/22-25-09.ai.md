This is a discussion thread about a Windows-specific Git issue where drive letters in local repository paths can cause problems when repositories are copied to different disks. The original poster (Skybuck Flying) discovered that when copying a Git repository to a new disk (from X: to Z:), the remote references still pointed to the original X: path, leading to potential confusion and cross-disk commits.

The thread explores several technical solutions:

1. **UNC Paths** - Using network-style paths (\\server\share) instead of drive letters, though these depend on Windows networking services being active.

2. **NTFS Mount Points** - Mounting disks to stable folder paths (like C:\ViteMirror) rather than using drive letters, which is more robust as it doesn't depend on networking services.

3. **Manual Remote Updates** - The original poster's workaround of manually updating the remote URLs after copying, combined with careful repository realignment steps.

The discussion highlights that this is a real architectural issue in how Git handles Windows paths, particularly for portable/virtual disk workflows. The most robust solution appears to be using NTFS mount points since they:
- Don't depend on drive letters
- Don't require networking services
- Provide stable paths that survive disk moves
- Behave similarly to Unix mount points

The thread contains detailed technical explanations of why each approach works (or doesn't work), along with specific commands for implementing the solutions. The original poster confirmed their manual realignment procedure worked, but the discussion suggests mount points would prevent the issue from occurring in the first place.
