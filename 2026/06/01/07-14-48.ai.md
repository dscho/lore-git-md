This is a discussion about Git's deprecation workflow process, prompted by Kristoffer Haugsbakk's series removing deprecated commit list functions. Junio C Hamano responds to Jeff King's (Peff) earlier question about whether the standard deprecation period was necessary.

Junio defends the current approach where deprecated functions remain available during a transition period, arguing that it distributes the update work across the community rather than concentrating it on the maintainer at merge time. While acknowledging that merge-time fixups could theoretically work (with tools like rerere helping), Junio prefers avoiding this bottleneck when possible, since the maintainer already handles many tasks that can't be delegated.

The exchange highlights two perspectives on project process: Peff's efficiency-focused view that immediate removal might reduce total work, versus Junio's maintainability perspective favoring gradual transitions to distribute workload. Both agree the current series is technically correct - this is purely a meta-discussion about process optimization.

The thread remains open-ended, as neither participant is proposing concrete changes to Git's deprecation policy. The discussion may inform future decisions about when transition periods are truly necessary versus when immediate removal would be preferable. The technical cleanup of the deprecated functions proceeds uncontested regardless.
