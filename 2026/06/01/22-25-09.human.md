This is a discussion thread about a Windows-specific Git workflow issue involving drive letters in repository paths. The original poster (Skybuck Flying) discovered that when a Git repository is copied to another disk, the remotes still reference the original drive letter (e.g., X:), which can lead to commits accidentally going to the wrong location.

The thread explores several technical solutions:

1. **UNC Paths** - Using network-style paths (\\server\share) instead of drive letters, though these depend on Windows networking services
2. **NTFS Mount Points** - Mounting disks to folder paths (like C:\ViteMirror) which don't depend on drive letters or networking services
3. **Manual Remote Updates** - The steps needed to realign repositories after moving them

The discussion provides detailed technical analysis of:
- How Git stores remote paths exactly as given
- Why drive letters in remotes are problematic for portable workflows
- The Windows service dependencies of each approach
- Step-by-step instructions for converting to mount points

The key takeaway is that NTFS mount points provide the most robust solution for this use case since they:
- Don't depend on Windows networking services
- Avoid drive letter issues entirely
- Provide stable paths that survive disk moves

This is a deep technical discussion of Windows filesystem integration with Git, particularly relevant for users managing repositories across multiple disks or virtual machines.
