This is a maintainer response to the `git son` feature proposal thread. Junio C Hamano weighs in with concerns about the broader utility of the proposed command.

Junio acknowledges the local use case for creating child repositories but questions whether it merits inclusion in core Git, given that the parent-child relationship established by `git son` wouldn't automatically replicate when others clone the parent repository. He notes the lack of mechanism to specify child repository locations within the parent's working tree for collaborators, which limits the feature's usefulness in distributed workflows.

The maintainer's stance is skeptical - while not rejecting the concept outright, he suggests the functionality may be better suited as a `contrib/` script rather than a core command, given Git's primary focus on collaborative workflows. This introduces a new dimension to the ongoing discussion, which had focused on technical implementation alternatives (new command vs enhanced submodules). Junio's feedback shifts the conversation toward distribution packaging and core Git's scope boundaries.

The response leaves open whether Evan Haque will revise the proposal to address these collaboration concerns or whether other participants will argue for the feature's inclusion despite the limitations Junio identified. The thread now has three distinct perspectives to reconcile: the original proposal, the submodule-based alternative, and now the maintainer's packaging/distribution concerns.
