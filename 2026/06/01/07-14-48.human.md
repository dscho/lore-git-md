This is a discussion about Git's deprecation workflow, prompted by Kristoffer Haugsbakk's series removing deprecated commit list functions. Junio C Hamano responds to Jeff King's (Peff) earlier question about whether the standard deprecation period was necessary for this case.

Junio defends the current approach where deprecated functions remain available during a transition period, arguing it distributes the update work across the community rather than concentrating it on the maintainer during merges. While acknowledging that merge-time fixups could technically handle the updates (with tools like rerere), Junio prefers avoiding this bottleneck when possible, since the integrator already has many unique responsibilities.

The exchange highlights two perspectives on process efficiency: Peff's view that immediate removal would have been simpler overall, versus Junio's preference for spreading maintenance work. Notably, neither side disputes the technical correctness of the current patch series - this is purely a meta-discussion about project workflow. The thread provides insight into how Git balances stability against maintenance overhead, with two long-time contributors offering complementary views on process optimization.
