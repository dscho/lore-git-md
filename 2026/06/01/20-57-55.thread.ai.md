Thread identity: RFC proposal from Skybuck Flying (Harald Houppermans) for major Git extensions to support modern development workflows, focusing on repository UUIDs for stable identification and now expanding to include fork lineage metadata through `.gitorigin` files.

Core problem: Git lacks built-in mechanisms for stable repository identification and provenance tracking. The expanded proposal now details how repository-level UUIDs combined with fork lineage metadata could address URL fragility and enable precise fork relationship tracking across repository moves/renames.

Key technical proposals:
- `.git/identity` file containing 128-bit UUID as permanent repository identifier
- New `.gitorigin` file storing `origin_uuid` and `last_synced` commit for fork lineage
- Optional parent UUID tracking for multi-generation fork relationships
- Divergence calculation capabilities (commits ahead/behind at each fork level)
- Mirror repository detection through lineage metadata
- All features designed as optional additions to avoid breaking changes

Current status: Proposal remains at RFC stage with no implementation patches. The latest follow-up provides concrete examples of how fork lineage metadata would solve current limitations in tracking repository provenance across organizational migrations and host changes.

Key technical details:
- UUIDs survive repository moves/renames while `.gitorigin` preserves fork relationships
- Enables reconstruction of full fork ancestry DAGs
- Backward compatibility through opt-in adoption
- Hosting provider cooperation would enhance the system
- Works in conjunction with previously proposed `.gitdeps`, `.gitsecurity`, and `.gitproject` files

Open questions:
- Whether these metadata systems belong in core Git versus higher-level tooling
- Implementation complexity of maintaining fork lineage metadata
- Hosting provider adoption requirements for full effectiveness
- Performance implications for repositories with deep fork histories
- Maintenance burden of new metadata formats
- Potential overlap with existing hosting provider fork systems

Participant positions: Still only Skybuck Flying's proposals at this stage; no reviews or responses yet recorded. The comprehensive nature suggests this may generate significant discussion about Git's scope and role in the modern development ecosystem, particularly regarding whether such metadata should be core functionality.

Related work: Implicitly compares to external systems like GitHub's fork networks and GitLab's repository mirroring, while proposing to bring similar capabilities into Git itself. The proposal positions these additions as solving fundamental identification and provenance problems that current hosting-specific implementations cannot address universally.
