This is a discussion about Git's deprecation workflow, sparked by Kristoffer Haugsbakk's series removing deprecated commit list functions. Patrick Steinhardt (the original API author) responds to Jeff King's (Peff) question about whether Git's standard deprecation process is always necessary.

Patrick acknowledges the trade-offs in deprecation workflows, noting that while small mechanical changes might not need a transition period, larger refactorings with a bigger "blast radius" benefit from giving in-flight topics time to adapt. He leaves the threshold between these cases as an open question.

The exchange doesn't impact the current patch series (which has Patrick's Acked-by and is technically sound), but provides insight into how core contributors think about API evolution. Patrick's perspective as someone who has both introduced and removed APIs carries weight in these discussions. The thread shows Git's maintainers actively reflecting on their own processes while executing them.
