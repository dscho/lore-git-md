Here’s the human-readable summary for a developer catching up on the thread:

Patrick Steinhardt’s `git history drop` series, now at v7, adds a new subcommand to remove commits from history and replay their descendants. The series is feature-complete, addressing all prior feedback: it modernizes the reset API (renaming functions, converting flags to enums, adding opt-in HEAD updates, and fixing a latent bug in the reset machinery), refactors code to eliminate duplication between replay and history paths, and implements the full `drop` command with conflict detection, dry-run support, and bare repository compatibility. The series also advances broader efforts like `the_repository` removal and prepares the reset API for future flexibility.

Junio C Hamano’s latest review surfaces a critical flaw in the `find_head_tree_change()` helper, which determines whether HEAD moves during a drop operation. The function fails when `--update-refs=head` is used because it looks for the *branch name* (e.g., `refs/heads/master`) in a ref update list that only contains `HEAD`. This mismatch causes the helper to incorrectly conclude HEAD hasn’t moved, skipping necessary index/worktree updates and risking repository inconsistency. Junio’s analysis is thorough, tracing the issue through multiple functions and clarifying edge cases like detached HEAD. The problem is high-impact but narrowly scoped—it doesn’t affect the core drop logic or prior API changes, just the synchronization step.

The series is otherwise ready for merging, with all substantive feedback incorporated. Christian Couder, Phillip Wood, and others have reviewed earlier iterations, and Junio’s dry-run consistency check was already addressed. The remaining work is limited to fixing the ref resolution logic in `find_head_tree_change()`. Once resolved, the series will be a significant addition to Git’s experimental `history` command, offering a safer alternative to `git rebase --onto` for commit removal.
