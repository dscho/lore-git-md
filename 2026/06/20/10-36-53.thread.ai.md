Core problem or goal
Optimize the `paint_down_to_common()` function in Git’s commit-reach subsystem to terminate early when one side of a merge-base query exhausts its commit queue, eliminating unnecessary traversal of large one-sided histories (e.g., repositories with import grafts or shallow histories). The optimization yields **100-1000x speedups** for asymmetric queries (e.g., steps reduced from 2.1M to 3 in a 2.6M-commit monorepo). The series is **technically complete, fully reviewed, and procedurally unblocked**, with **final documentation refinements to adopt consistent "ordered/unordered" region terminology now fully incorporated and the core side-exhaustion optimization implemented**.

This centralizes all termination conditions in `paint_queue_get()`, improving code clarity and maintainability. The `min_generation` check is now performed immediately after generation retrieval, before any counter decrements, aligning with the existing pattern for other termination conditions. The `topo_ceiling` check in the side-exhaustion optimization is updated to use `state->last_gen` instead of re-fetching the generation.

- **Edge-case test coverage**: Added five new test cases in `t6600-test-reach.sh` and `t6099-merge-base-side-exhaustion.sh` (patches 3/8 and 4/8 in v8) to exercise edge scenarios in the side-exhaustion optimization:
  - `in_merge_bases_many:self` – a commit is both the query and one of the inputs.
  - `get_merge_bases_many:duplicate-twos` – duplicate entries in the input list.
  - `get_merge_bases_many:pending-stale` – a STALE transition on an already-painted commit (tested via a diamond topology where a merge-base candidate is a descendant of another).
  - `get_merge_bases_many:infinity-both-sides` – both tips outside the commit-graph with non-monotonic dates (tested via a topology with skewed timestamps to force commit-date fallback).
  - **Diamond topology regression test** (`t6099-merge-base-side-exhaustion.sh`) – validates that `remove_redundant()` correctly filters redundant merge-base candidates when the side-exhaustion optimization terminates early. The test constructs a diamond-shaped graph where two tips (`A` and `X`) share two merge-base candidates (`B` and `C`), with `B` being an ancestor of `C`. The test verifies that only the shallowest candidate (`B`) is returned for both `--all` and single-result modes, and includes a fallback case without a commit-graph (where generation numbers are `INFINITY` and the optimization does not fire).
  The tests validate that the side-exhaustion optimization does not fire prematurely and that correct merge-bases are returned. Two new test topologies (`ps-*` diamond and `pi-*` skewed-timestamp) were introduced to support these cases, and the diamond topology in `t6099` (`A->B->C`, `A->e2->e1->C`, `X->f2->f1->C`, `X->B`) is now documented with a fixed-width ASCII graph for clarity.

The `se-*` topology tests a simple diamond where the correct merge base (`se-D`) has a higher date than its child (`se-C`), while `se2-*` adds a redundant ancestor (`se2-MB2`) to ensure the shallowest merge base (`se2-MB1`) is still found. Both topologies use `skew_commit` to force non-monotonic dates, and the tests verify that generation ordering (not commit-date ordering) governs the walk. This ensures the side-exhaustion optimization behaves correctly when one side of the query includes commits with `GENERATION_NUMBER_INFINITY`.
