Thread identity
Subject: [PATCH 0/6] commit-reach: optimize `paint_down_to_common()` for one-sided histories
Series version: v1 (initial submission, under review)
Originating author: Tian Yuchen
Thread type: patch series (performance optimization)

Core problem or goal
Optimize the `paint_down_to_common()` function in Git’s commit-reach subsystem to terminate early when one side of a merge-base query exhausts its commit queue, eliminating unnecessary traversal of large one-sided histories (e.g., repositories with import grafts or shallow histories). The goal is to address a known performance bottleneck where asymmetric histories force full traversal of one side even after the other side is exhausted.

Current status
Series is at v1, under active review. The core optimization (patch 3) has received its first **substantive technical review** from Derrick Stolee, who endorses the early-termination logic but proposes a **medium-weight implementation refinement**: relocating the early-exit check from the main loop to the `paint_queue_get()` dequeueing method for better code locality. Stolee also requests **performance benchmarks** to empirically validate that patch 2 (the refactoring) introduces no overhead and that patch 3 delivers the advertised speedup. The preparatory refactoring (patches 1–2) remains contested: Stolee’s **high-weight structural objection**—that patch 1 degrades code clarity without benefit—stands unresolved. His alternative (introduce `paint_queue` first while retaining `nonstale_queue` for `ahead_behind()`, then delete `nonstale_queue` later) would eliminate patch 1 entirely. Patches 4–6 (test/documentation coverage) remain unchallenged.

Open questions and loose ends
- **Structural refactoring dispute**: Whether to reorder patches 1–2 to preserve code clarity during the transition from `nonstale_queue` to `paint_queue`. Stolee’s proposal (eliminate patch 1) is pending the author’s response.
- **Implementation refinement**: Whether to move the early-exit check to `paint_queue_get()` (Stolee’s suggestion) or retain it in the main loop. This is a code-organization question, not a functional one.
- **Performance validation**: Whether to augment the series with benchmarks demonstrating no regression from patch 2 and the speedup from patch 3. Stolee’s request is actionable but not yet addressed.
- **Edge-case correctness**: Whether the finite-generation guard is overly conservative or could activate earlier (e.g., criss-cross merges, grafts, shallow histories). This remains unchallenged but unresolved.
- **Integration with Elijah Newren’s work**: The series incorporates Elijah’s test cases (PR #2150), but potential overlap or conflict in test coverage remains a loose end.

Key technical details
- Subsystem: commit-reach (merge-base calculation).
- Files touched: `commit-reach.c` (core logic), `Documentation/technical/paint-down-to-common.adoc` (new documentation), test scripts `t6099-merge-base-side-exhaustion.sh` and `t6600-test-reach.sh`.
- New/renamed symbols: `paint_queue` struct (patch 2), per-side counters (`p1_count`, `p2_count`, `pending_merge_bases`) (patch 2), `paint_count_transition()`, `paint_queue_put()`, `paint_queue_get()` (patch 2), local `max_nonstale` pointer (patch 1).
- Behavior change: walk terminates early when one side’s queue is exhausted, but only after entering the finite-generation region (where generation numbers guarantee final paint states). Stolee’s proposed refinement (moving the early-exit check to `paint_queue_get()`) would not alter this behavior.
- On-disk format: no changes.
- Test coverage: new tests for edge cases (patch 4: self/duplicate/pending-stale/infinity-both-sides; patch 5: diamond topology with redundant merge-base candidates, mixed finite/INFINITY generation numbers, criss-cross merges, grafts, shallow histories) and regression scenarios; benchmarks show 500x+ speedup on large one-sided histories (2.6M commits) with no regressions on smaller repositories (linux.git). Stolee requests additional performance benchmarks for patches 2–3.
