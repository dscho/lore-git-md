Core problem or goal
Optimize the `paint_down_to_common()` function in Git’s commit-reach subsystem to terminate early when one side of a merge-base query exhausts its commit queue, eliminating unnecessary traversal of large one-sided histories (e.g., repositories with import grafts or shallow histories). The optimization yields **100-1000x speedups** for asymmetric queries. This iteration (v3) introduces **four new patches** (2/8, 3/8, 4/8, 5/8) and **three follow-up patches** (6/8, 7/8, 8/8) that consolidate, harden, and document the changes. Patch 8/8 (new in v3) **consolidates termination conditions** by moving the `min_generation` check into `paint_queue_get()`, alongside existing stale-entry and side-exhaustion checks, and widens the generation-monotonicity BUG assertion to fire unconditionally.

The tests verify that redundant merge-base candidates are excluded and that the walk correctly transitions between generation-number regions. Uses `test_all_modes` for multi-mode validation.
- **Patch 4/8 (new in v3)**: Adds **trace2 step-counting instrumentation** to `paint_down_to_common()` to measure the number of commits visited during the paint walk. The patch increments a `steps` counter for each commit processed and emits the total via `trace2_data_intmax()` at the end of the walk. It extends the test infrastructure to **assert deterministic step counts** across all commit-graph modes (none, full, half, no-gdat) via a new `test_paint_down_steps()` helper. The test suite is updated to include step-count assertions for existing edge-case tests (self, pending-stale, infinity-both-sides, mixed-finite-infinity) and adds a new test (`merge-base --all commit-walk steps`) that verifies step counts for a large topology (81 steps in git.git). The step counts are **mode-dependent** (e.g., "self" test expects 45 steps in "none" mode but only 2 in "full" mode).
- **Patch 5/8 (new in v3)**: Introduces `struct paint_state` to replace the old `nonstale_queue` with per-side counters (`p1_count`, `p2_count`, `pending_merge_bases`). The counters are maintained by `paint_count_update()` and drained via `paint_queue_get()`. The patch is **mechanical and low-risk**, converting `paint_down_to_common()` to use `paint_state` while preserving equivalent behavior. The loop now terminates when the counters indicate no non-stale entries remain, replacing the old `max_nonstale` pointer-based check. The "pop first" form of `paint_queue_get()` (dequeue, then check counters) causes the loop to exit one iteration earlier in some topologies, reducing step counts by one in a few test cases (e.g., `pending-stale` drops from 6 to 5 steps). The existing `nonstale_queue` is left untouched for `ahead_behind()` to avoid coupling.
- **Patch 6/8 (new in v3)**: Removes two unused wrapper functions—`nonstale_queue_put_dedup()` and `nonstale_queue_get_dedup()`—that were rendered obsolete by the introduction of `struct paint_state` in patch 5/8. The wrappers were originally introduced to deduplicate commits by checking the `ENQUEUED` flag, but the new `paint_state` counters now handle this logic directly in `paint_down_to_common()`. The removal is **mechanical and low-risk**, deleting 18 lines of dead code with no behavior change. The core `nonstale_queue` functions remain in use by `ahead_behind()`.
- **Patch 7/8 (new in v3)**: **Implements the core optimization**: early termination of the merge-base walk when one side’s commit queue is exhausted. The patch adds an early-exit condition to `paint_down_to_common()` that triggers when either `p1_count` or `p2_count` drops to zero, no pending merge-base candidates remain, and the walk has entered the finite-generation region (`generation < GENERATION_NUMBER_INFINITY`). This ensures correctness by only activating the optimization in the finite region, where generation numbers provide reliable topological ordering. The patch also **widens the generation-monotonicity BUG assertion** to fire unconditionally, enforcing correct generation ordering for all callers. Performance benchmarks show dramatic improvements (e.g., `merge-base --all v2.0.0 v2.55.0-rc1`: 72,264 → 44,589 steps; `merge-base --all v2.55.0-rc1 v2.55.0-rc1~5`: 110 → 7 steps). The test suite is updated to reflect the reduced step counts, with `test_paint_down_steps` assertions now expecting fewer steps in some topologies (e.g., `pending-stale` drops from 6 to 5 steps due to the "pop first" form of `paint_queue_get()`).
- **Patch 8/8 (new in v3)**: **Consolidates termination conditions** by moving the `min_generation` check into `paint_queue_get()`, alongside existing stale-entry and side-exhaustion checks. It also **widens the generation-monotonicity BUG assertion** to fire unconditionally, enforcing correct generation ordering for all callers—not just those using `min_generation`. The patch stores `last_gen` in `struct paint_state`, ensuring `commit_graph_generation()` is called exactly once per dequeued commit. The loop in `paint_down_to_common()` now reads `state.last_gen` instead of recomputing the generation, and the `min_generation` check is performed immediately after dequeuing, before any other conditions. The "pop first" form of `paint_queue_get()` is preserved, keeping the optimization commit’s diff minimal. The patch updates the new technical documentation (`paint-down-to-common.adoc`) to include the `min_generation` cutoff as a fourth termination condition, with a dedicated subsection explaining its role in `remove_redundant()`.

The series is **well-tested and instrumented**, with **deterministic step-count assertions** for all commit-graph modes (none, full, half, no-gdat) and **self-verifying performance** via `run_all_modes` capturing trace2 output per mode. Benchmarks include both step counts (e.g., `paint_down_to_common steps 9` vs. `80` in git.git) and wall-clock times (e.g., `3.67s -> 5ms` for a 2.6M-commit monorepo). The test coverage spans edge cases (self/duplicate/pending-stale/infinity-both-sides), diamond topologies (`ps-*`, `pi-*`), mixed finite/INFINITY generation numbers, criss-cross merges, grafts, shallow histories, region transitions, redundant merge-base candidates, and single-merge-base selection.
