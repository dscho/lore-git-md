Thread identity
Subject: macOS CI hang in t5551/t5559 – root cause and fix
Series version: v1 (2-patch series: both from Jeff King; now merged for Git 2.55)
Originating author: Michael Montalbo (initial report), Jeff King (patch author), Patrick Steinhardt (CI alignment patch author, now on hold)
Thread type: bug report with proposed fix and CI policy discussion

Core problem or goal
Git’s CI jobs on GitHub’s macOS and Linux runners failed due to hangs or protocol errors in the `t5551` and `t5559` tests during an `ls-refs` advertisement of 100,000 loose refs. The root cause was **Apache’s `mod_http2` bug 70131**, which triggered either a mid-transfer abort (`curl 18`) or an indefinite HTTP/2 stall when the server-side 300-second timeout was hit. The goal was to eliminate these failures by addressing the underlying timeout or protocol issue through a combination of test optimizations and Apache configuration adjustments, while also establishing a consistent CI policy across GitHub and GitLab platforms.

Current status
The **2-patch series is merged** and will ship in Git 2.55. Junio C Hamano applied both patches with a minor stylistic tweak (initializing the isolated repository as bare to match the script’s convention). The third patch (Patrick Steinhardt’s `GIT_TEST_LONG` enablement for GitLab CI) remains **on hold pending a policy decision** about CI resource allocation and visibility. Junio has **rejected the idea of aligning GitLab CI coverage strictly with GitHub’s**, instead suggesting GitLab could run a **superset** of GitHub’s coverage (same tests plus additional ones). He has also raised a **practical visibility concern**: while GitHub CI results are easily accessible to maintainers via a TinyURL shortcut, GitLab CI results are not similarly visible, creating a barrier to treating GitLab as a first-class part of the workflow. No technical changes to the patch series are needed; the discussion remains focused on policy and infrastructure.

Key technical details
- Files touched: `t/lib-httpd/apache.conf` (Apache `Timeout` directive increased from 300 to 600 seconds), `t/t5551-http-fetch-smart.sh` (test isolation logic for the many-tags case).
- Subsystems: test suite, HTTP/2 and HTTP/1.1 transport, libcurl, Apache `h2_mod` and `mod_cgi`, timeout handling, ref backends (files, reftable), `git fast-import`, `git update-ref`, `git pack-refs`.
- New behavior:
  - Apache’s `Timeout` directive increased to 600 seconds, directly addressing the root cause of CI hangs.
  - The `t5551` many-tags test case now runs in an isolated bare repository, reducing runtime for the entire test script from ~2.7 seconds to ~1.9 seconds (normal runs) and from ~95 seconds to ~37 seconds (EXPENSIVE runs).
- Environment details:
  - libcurl: 8.6.0 (GitHub) vs 8.7.1 (GitLab); bug persists across versions.
  - macOS build image: 14 (GitHub) vs 15 (proposed); Linux CI failures now observed, with logs truncated but suspected to stem from the same Apache bug.
  - Apache `h2_mod` and `mod_cgi`: default `Timeout 300` was being hit; logs showed `AH01220: Timeout waiting for output from CGI script` and `AH00574: ap_content_length_filter: apr_bucket_read() failed`.
  - Upstream Apache bug 70131: confirmed as the source of hangs/stalls; affects both HTTP/1.1 (`t5551`) and HTTP/2 (`t5559`); reproducible without Git.
  - Timing data: cold-cache `upload-pack` advertisement of 100,000 loose refs takes ~10 seconds on a local SSD; warm-cache or packed-ref scenarios complete in <0.5 seconds. Reftable backend creates 50,000 refs in 150ms (vs ~220ms for files backend), a ~30% speedup.
  - Failure modes:
    - HTTP/1.1 (`t5551`): `curl 18 transfer closed with outstanding read data remaining` (mid-transfer abort).
    - HTTP/2 (`t5559`): indefinite stall (hang).
  - Observed inefficiency: reftable’s repeated `fstat` calls on `tables.list` during bulk ref creation, identified via `strace` and `perf` as a non-trivial cost. Peff speculates this could be optimized by trusting the stack after locking but deems it not worth the effort.
- On-disk format: none.
- Test coverage: `t5551`, `t5559` (expensive tests).
- Related precedent: commit 8f2146dbf1 (HTTP/2 flow-control stall fix), Apache bug 70131, `REF_TRANSACTION_FLAG_INITIAL` optimization.

Open questions and loose ends
- **CI policy and visibility**: Junio has **rejected strict alignment with GitHub’s coverage**, instead suggesting GitLab CI could run a **superset** of GitHub’s tests/events. He has raised a **visibility concern**: GitLab CI results are not as easily accessible to maintainers as GitHub’s, which may hinder adoption. The third patch (enabling `GIT_TEST_LONG` for GitLab CI) remains on hold until this is resolved. No concrete plan for improving GitLab CI visibility has been proposed yet.
- **Ref backend optimizations**: Peff’s post-mortem analysis of the dropped ref-packing patch surfaced two architectural notes:
  - Extending `REF_TRANSACTION_FLAG_INITIAL` to non-empty repositories (e.g., `git fast-import`) would be non-trivial.
  - A hypothetical ad-hoc optimization (writing directly to `packed-refs` without locking) was dismissed as "gross and fragile" due to ordering and backend-conditional risks.
