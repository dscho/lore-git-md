Subject: macOS CI hang in t5551/t5559 – root cause and fix
Series version: none (standalone patch)
Originating author: Michael Montalbo
Thread type: bug report with proposed fix

Core problem or goal
Git’s CI jobs on GitHub’s macOS runners (and now Linux CI) fail due to hangs or protocol errors in the `t5551` and `t5559` tests during an `ls-refs` advertisement of 100,000 loose refs. The root cause is **Apache’s `mod_http2` bug 70131**, which triggers either a mid-transfer abort (`curl 18`) or an indefinite HTTP/2 stall when the server-side 300-second timeout is hit. The goal is to eliminate these failures by addressing the underlying timeout or protocol issue, either through upstream fixes, test optimizations, client-side mitigations, timeout adjustments, or a combination thereof.

Current status
Michael Montalbo’s initial two-part fix (packing refs and aligning `$JOBS` with runner core count) reduced CI runtime from 360 minutes to 30–44 minutes on macOS but **did not resolve the underlying timeout issue**. The failure mode shifted to consistent `curl 18` mid-transfer aborts on macOS and similar failures on Linux CI (logs truncated). Patrick Steinhardt diagnosed the root cause as Apache’s 300-second timeout being hit during the `ls-refs` advertisement, reproducing the `curl 18` error locally and confirming the upstream Apache bug (70131) affects both HTTP/1.1 and HTTP/2. A **consensus has emerged among maintainers and reviewers** (Junio C Hamano, Jeff King, Patrick Steinhardt) to **avoid client-side mitigations** (e.g., `http.lowSpeedLimit`/`http.lowSpeedTime` settings) and **retry logic**, as these merely mask flakes rather than address the root cause. The preferred solution is now to **increase Apache’s `Timeout` directive** (e.g., from 300 to 600 seconds) to reduce the likelihood of hitting the problematic state, though no concrete patch has been proposed yet. Junio’s recent endorsement of this approach signals likely maintainer acceptance if implemented cleanly.
