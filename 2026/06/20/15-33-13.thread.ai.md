Thread identity
Subject: macOS CI hang in t5551/t5559 – root cause and fix
Series version: v1 (2-patch series: both from Jeff King; now merged for Git 2.55)
Originating author: Michael Montalbo (initial report), Jeff King (patch author), Patrick Steinhardt (CI alignment patch author, now on hold)
Thread type: bug report with proposed fix, CI policy discussion, and reftable performance analysis

Core problem or goal
Git’s CI jobs on GitHub’s macOS and Linux runners failed due to hangs or protocol errors in the `t5551` and `t5559` tests during an `ls-refs` advertisement of 100,000 loose refs. The root cause was **Apache’s `mod_http2` bug 70131**, which triggered either a mid-transfer abort (`curl 18`) or an indefinite HTTP/2 stall when the server-side 300-second timeout was hit. The goal was to eliminate these failures by addressing the underlying timeout or protocol issue through a combination of test optimizations and Apache configuration adjustments, while also establishing a consistent CI policy across GitHub and GitLab platforms. A secondary, post-resolution discussion emerged about **low-hanging performance optimizations in Git’s reftable backend**, specifically redundant `fstat` calls during bulk ref creation.

Current status
The **2-patch series is merged** and will ship in Git 2.55. Junio C Hamano applied both patches with a minor stylistic tweak (initializing the isolated repository as bare to match the script’s convention). The third patch (Patrick Steinhardt’s `GIT_TEST_LONG` enablement for GitLab CI) remains **on hold pending a policy decision** about CI resource allocation and visibility. Junio has **rejected the idea of aligning GitLab CI coverage strictly with GitHub’s**, instead suggesting GitLab could run a **superset** of GitHub’s coverage (same tests plus additional ones). Patrick Steinhardt has now proposed a **concrete, low-cost improvement to address Junio’s visibility concern**: adding a GitLab CI status badge to the project’s `README.md`. This would link directly to the pipelines page for the `master` branch on GitLab’s official mirror, making GitLab CI results as discoverable as GitHub’s without requiring any CI configuration changes. The badge addition is a one-line documentation tweak that could be merged independently of the third patch. The reftable performance discussion is **not actionable in the short term** but has been noted as a future optimization opportunity.

Key technical details
- Files touched: `t/lib-httpd/apache.conf` (Apache `Timeout` directive increased from 300 to 600 seconds), `t/t5551-http-fetch-smart.sh` (test isolation logic for the many-tags case), `README.md` (proposed addition of GitLab CI badge).
- Subsystems: test suite, HTTP/2 and HTTP/1.1 transport, libcurl, Apache `h2_mod` and `mod_cgi`, timeout handling, ref backends (files, reftable), `git fast-import`, `git update-ref`, `git pack-refs`, reftable internals (`refs_resolve_ref_unsafe()`, `tables.list` handling).
- New behavior:
  - Apache’s `Timeout` directive increased to 600 seconds, directly addressing the root cause of CI hangs.
  - The `t5551` many-tags test case now runs in an isolated bare repository, reducing runtime for the entire test script from ~2.7 seconds to ~1.9 seconds (normal runs) and from ~95 seconds to ~37 seconds (EXPENSIVE runs).
  - Proposed addition of a GitLab CI status badge to `README.md`, linking to the pipelines page for the `master` branch on GitLab’s official mirror.
- Environment details:
  - libcurl: 8.6.0 (GitHub) vs 8.7.1 (GitLab); bug persists across versions.
  - macOS build image: 14 (GitHub) vs 15 (proposed); Linux CI failures now observed, with logs truncated but suspected to stem from the same Apache bug.
  - Apache `h2_mod` and `mod_cgi`: default `Timeout 300` was being hit; logs showed `AH01220: Timeout waiting for output from CGI script` and `AH00574: ap_content_length_filter: apr_bucket_read() failed`.
  - Upstream Apache bug 70131: confirmed as the source of hangs/stalls; affects both HTTP/1.1 (`t5551`) and HTTP/2 (`t5559`); reproducible without Git.
  - Timing data: cold-cache `upload-pack` advertisement of 100,000 loose refs takes ~10 seconds on a local SSD; warm-cache or packed-ref scenarios complete in <0.5 seconds. Reftable backend creates 50,000 refs in 150ms (vs ~220ms for files backend), a ~30% speedup.
  - Failure modes:
    - HTTP/1.1 (`t5551`): `curl 18 transfer closed with outstanding read data remaining` (mid-transfer abort).
    - HTTP/2 (`t5559`): indefinite stall (hang).
  - Reftable performance quirk: 2,000 `fstat` calls during bulk ref creation (via `strace`/`perf`), consuming 85% of runtime. Root cause: `refs_resolve_ref_unsafe()`’s generic design, which doesn’t leverage reftable’s stack-based internals. Proposed optimization: trust the loaded stack after locking to avoid redundant filesystem checks.
- On-disk format: none.
- Test coverage: `t5551`, `t5559` (expensive tests).
- Related precedent: commit 8f2146dbf1 (HTTP/2 flow-control stall fix), Apache bug 70131, `REF_TRANSACTION_FLAG_INITIAL` optimization.

Open questions and loose ends

Patrick Steinhardt has proposed a **concrete, low-cost improvement** to address Junio’s visibility concern: adding a GitLab CI status badge to `README.md`. - **Ref backend optimizations**:
  - Reftable’s redundant `fstat` calls during bulk ref creation (2,000 calls, 85% of runtime) have been identified as a low-hanging optimization opportunity. The fix would involve trusting the loaded stack after locking, but this requires deeper refactoring of `refs_resolve_ref_unsafe()`. Patrick Steinhardt plans to file an issue to track this work but does not expect to address it soon.
  - Peff’s post-mortem analysis of the dropped ref-packing patch surfaced two architectural notes:
    - Extending `REF_TRANSACTION_FLAG_INITIAL` to non-empty repositories (e.g., `git fast-import`) would be non-trivial.
    - A hypothetical ad-hoc optimization (writing directly to `packed-refs` without locking) was dismissed as "gross and fragile" due to ordering and backend-conditional risks.
