Subject: macOS CI hang in t5551/t5559 – root cause and fix
Series version: none (standalone patch)
Originating author: Michael Montalbo
Thread type: bug report with proposed fix

Core problem or goal
Git’s CI jobs on GitHub’s macOS runners (and now Linux CI) fail due to hangs or protocol errors in the `t5551` and `t5559` tests during an `ls-refs` advertisement of 100,000 loose refs. The root cause is **Apache’s `mod_http2` bug 70131**, which triggers either a mid-transfer abort (`curl 18`) or an indefinite HTTP/2 stall when the server-side 300-second timeout is hit. The goal is to eliminate these failures by addressing the underlying timeout or protocol issue, either through upstream fixes, test optimizations, client-side mitigations, timeout adjustments, or a combination thereof.

Current status
Michael Montalbo’s initial two-part fix (packing refs and aligning `$JOBS` with runner core count) reduced CI runtime from 360 minutes to 30–44 minutes on macOS but **did not resolve the underlying timeout issue**. The failure mode shifted to consistent `curl 18` mid-transfer aborts on macOS and similar failures on Linux CI (logs truncated). Patrick Steinhardt diagnosed the root cause as Apache’s 300-second timeout being hit during the `ls-refs` advertisement, reproducing the `curl 18` error locally and confirming the upstream Apache bug (70131) affects both HTTP/1.1 and HTTP/2. Montalbo proposed a **client-side mitigation** (enabling Git’s `http.lowSpeedLimit` and `http.lowSpeedTime` settings) to convert indefinite hangs into fast, bounded failures, but this was **rejected by Jeff King (Peff)** as merely "punting" on the problem. Peff advocates for either **waiting for an upstream Apache fix** or **increasing Apache’s timeout value** to reduce the likelihood of hitting the problematic state. Patrick Steinhardt has now **proposed increasing Apache’s `Timeout` directive** as a pragmatic, Git-side fix that avoids client-side workarounds while directly addressing the root cause. No maintainer decision yet; the patch remains under review, with **no new code changes proposed beyond the existing two-part fix and the now-contested client-side mitigation**.
