Thread identity
Subject: macOS CI hang in t5551/t5559 – root cause and fix
Series version: v1 (2-patch series: both from Jeff King; Patrick Steinhardt's CI alignment patch dropped pending policy decision)
Originating author: Michael Montalbo (initial report), Jeff King (patch author), Patrick Steinhardt (CI alignment patch author, now on hold)
Thread type: bug report with proposed fix

Core problem or goal
Git’s CI jobs on GitHub’s macOS and Linux runners fail due to hangs or protocol errors in the `t5551` and `t5559` tests during an `ls-refs` advertisement of 100,000 loose refs. The root cause is **Apache’s `mod_http2` bug 70131**, which triggers either a mid-transfer abort (`curl 18`) or an indefinite HTTP/2 stall when the server-side 300-second timeout is hit. The goal is to eliminate these failures by addressing the underlying timeout or protocol issue through a combination of test optimizations and Apache configuration adjustments.

Current status
The **2-patch series is ready for merging**. The first patch (**increasing Apache’s `Timeout` directive from 300 to 600 seconds** in `t/lib-httpd/apache.conf`) directly addresses the root cause of CI hangs, while the second patch (**isolating the expensive test case into its own repository** in `t/t5551-http-fetch-smart.sh`) reduces runtime for subsequent tests. Junio C Hamano has indicated he will apply both patches with a minor stylistic tweak (initializing the isolated repository as bare to match the script’s convention) before the 2.55 final release. The third patch (Patrick Steinhardt’s `GIT_TEST_LONG` enablement for GitLab CI) has been **dropped from the series pending a policy decision** about CI resource allocation; it remains on hold until the discussion about whether GitLab should duplicate GitHub’s coverage or focus on additional events concludes.

Key technical details
- Files touched: `t/lib-httpd/apache.conf` (Apache `Timeout` directive), `t/t5551-http-fetch-smart.sh` (test isolation logic).
- Subsystems: test suite, HTTP/2 and HTTP/1.1 transport, libcurl, Apache `h2_mod` and `mod_cgi`, timeout handling.
- New behavior:
  - Apache’s `Timeout` directive increased from 300 to 600 seconds (patch 1/2), directly addressing the root cause of CI hangs.
  - The `t5551` many-tags test case now runs in an isolated repository (patch 2/2), reducing runtime for the entire test script from ~2.7 seconds to ~1.9 seconds (normal runs) and from ~95 seconds to ~37 seconds (EXPENSIVE runs). The isolated repository will be initialized as a bare repository to match the script’s convention, a cosmetic change Junio will apply locally.
- Environment details:
  - libcurl: 8.6.0 (GitHub) vs 8.7.1 (GitLab); bug persists across versions.
  - macOS build image: 14 (GitHub) vs 15 (proposed); Linux CI failures now observed, with logs truncated but suspected to stem from the same Apache bug.
  - Apache `h2_mod` and `mod_cgi`: default `Timeout 300` was being hit; logs showed `AH01220: Timeout waiting for output from CGI script` and `AH00574: ap_content_length_filter: apr_bucket_read() failed`.
  - Upstream Apache bug 70131: confirmed as the source of hangs/stalls; affects both HTTP/1.1 (`t5551`) and HTTP/2 (`t5559`); reproducible without Git.
  - Timing data: cold-cache `upload-pack` advertisement of 100,000 loose refs takes ~10 seconds on a local SSD; warm-cache or packed-ref scenarios complete in <0.5 seconds.
  - Failure modes:
    - HTTP/1.1 (`t5551`): `curl 18 transfer closed with outstanding read data remaining` (mid-transfer abort).
    - HTTP/2 (`t5559`): indefinite stall (hang).
- On-disk format: none.
- Test coverage: `t5551`, `t5559` (expensive tests).
- Related precedent: commit 8f2146dbf1 (HTTP/2 flow-control stall fix), Apache bug 70131.

Open questions and loose ends
- **Linux CI specifics**: Exact error and conditions for Linux failures remain unclear due to truncated logs; whether the same Apache bug is being hit is unconfirmed but suspected. No action is planned until more data is available.
- **Upstream Apache fix**: No timeline for a fix to Apache bug 70131; the Git project’s willingness to wait for upstream remains unresolved, but the consensus is to proceed with the timeout adjustment regardless.
- **CI resource allocation policy**: Junio raised a strategic question about whether GitLab CI should duplicate GitHub’s `GIT_TEST_LONG` coverage (pull requests and pushes to integration branches) or focus on *additional* tests/events not already covered by GitHub (e.g., scheduled runs, tag pushes). This is a policy decision, not a technical one, and the patch remains on hold until the discussion concludes. Patrick or another participant is expected to clarify GitLab’s capacity or propose an alternative scope for the patch.
