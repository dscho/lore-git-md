Subject: macOS CI hang in t5551/t5559 – root cause and fix
Series version: none (standalone patch)
Originating author: Michael Montalbo
Thread type: bug report with proposed fix

Core problem or goal
Git’s CI jobs on GitHub’s macOS runners frequently fail due to hangs or protocol errors in the `t5551` and `t5559` tests during an `ls-refs` advertisement of 100 000 loose refs. The failures now manifest across **multiple platforms** (macOS and Linux CI), including HTTP/2 flow-control stalls (hangs), `curl 18 transfer closed with outstanding read data remaining` errors (mid-transfer aborts), and truncated Linux CI logs. The goal remains eliminating these failures by addressing the underlying protocol or environmental issues, rather than masking them through test adjustments or environment updates.

Current status
Michael Montalbo’s proposed fix (packing refs and aligning `$JOBS` with runner core count) is implemented on `mm/macos-ci-hang-fix` and reduces CI runtime from a 360-minute timeout to 30–44 minutes on macOS, but **does not resolve the underlying issue**. The failure mode has **expanded**: macOS now consistently fails with `curl 18` mid-transfer aborts, and Linux CI has begun exhibiting similar failures (though logs are truncated). Jeff King (Peff) and Junio C Hamano **continue to question** whether the fix eliminates the HTTP/2 deadlock risk or merely masks it. Patrick Steinhardt has **ruled out** macOS-specificity, diagnosing a **libcurl version mismatch** (8.6.0 on GitHub vs 8.7.1 on GitLab) and a **macOS build image version discrepancy** (14 on GitHub vs 15 on GitLab), while also confirming the issue persists on Linux. The thread is now focused on **cross-platform root-cause analysis**, with environment version checks (libcurl, Apache `h2_mod`, OS images) and protocol-level debugging (HTTP/2 flow control, transfer aborts) prioritized. No maintainer decision yet; the patch remains under review, with **no new fixes proposed** beyond the existing two-part change.
