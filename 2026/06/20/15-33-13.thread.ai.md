Subject: macOS CI hang in t5551/t5559 – root cause and fix
Series version: v1 (2-patch series: both from Jeff King; merged for Git 2.55), plus two follow-ups (GitLab CI badge and `GIT_TEST_LONG` enablement; badge merged, `GIT_TEST_LONG` still on hold), a **merged performance optimization patch** for quadratic-time behavior in the reftable backend, and a **platform-compatibility follow-up** documenting the upstream Apache bug in a public location
Originating author: Michael Montalbo (initial report and platform-compatibility follow-up), Jeff King (patch author and performance analysis), Patrick Steinhardt (CI alignment, reftable analysis, and badge patch), Junio C Hamano (badge acceptance), Kristofer Karlsson (performance optimization patch author)
Thread type: bug report with proposed fix, CI policy discussion, reftable performance analysis, **performance optimization patch**, and **platform-compatibility documentation**

Core problem or goal
Git’s CI jobs on GitHub’s macOS and Linux runners failed due to hangs or protocol errors in the `t5551` and `t5559` tests during an `ls-refs` advertisement of 100,000 loose refs. The root cause was **Apache’s `mod_http2` bug 70131**, which triggered either a mid-transfer abort (`curl 18`) or an indefinite HTTP/2 stall when the server-side 300-second timeout was hit. The goal was to eliminate these failures by addressing the underlying timeout or protocol issue through a combination of test optimizations and Apache configuration adjustments, while also establishing a consistent CI policy across GitHub and GitLab platforms. A secondary, post-resolution discussion emerged about **low-hanging performance optimizations in Git’s reftable backend**, specifically redundant `fstat` calls and unbuffered reflog writes during bulk ref creation. A **quadratic-time scalability issue** in the reftable backend was **fully diagnosed and now has a merged fix**: the tombstone-based deletion design forced both `refs_verify_refname_available()` and `reftable_be_transaction_prepare()` to scan all tombstones during bulk ref re-creation, causing runtime to grow quadratically with the number of deleted refs (e.g., 1.8s → 7.1s for a 2x input size increase). The final follow-ups addressed **CI visibility** by adding a GitLab CI status badge to the project’s `README.md` and **CI resource allocation** (still under discussion), along with **platform-compatibility documentation** to ensure future contributors can access the upstream Apache bug context without hitting a login wall.

Current status
The **2-patch series is merged** and will ship in Git 2.55. Junio C Hamano applied both patches with a minor stylistic tweak (initializing the isolated repository as bare to match the script’s convention). The **GitLab CI badge addition is now merged**. The third patch (Patrick Steinhardt’s `GIT_TEST_LONG` enablement for GitLab CI) remains **on hold pending further discussion** about CI resource allocation. The reftable performance discussion has **concluded with a merged fix for the quadratic-time behavior**. Kristofer Karlsson’s patch, which exposes tombstones to iterator bounds checks, is now **merged** after demonstrating **measurable improvement in realistic workflows** (e.g., 27s → 0.09s for 8,000 refs in bulk deletion/re-creation). The **platform-compatibility follow-up** (Michael Montalbo’s Apache bug documentation) is **complete and publicly accessible** via an external pull request to Apache’s GitHub mirror.

- Files touched: `t/lib-httpd/apache.conf` (Apache `Timeout` directive increased from 300 to 600 seconds), `t/t5551-http-fetch-smart.sh` (test isolation logic for the many-tags case), `README.md` (addition of GitLab CI badge alongside the existing GitHub badge), `reftable/merged.c` (iterator logic), `reftable/refs.c` (ref lookup), `reftable/stack.c` (log iteration paths for tombstone visibility), **Apache’s GitHub mirror** (external documentation of bug 70131).
- Subsystems: test suite, HTTP/2 and HTTP/1.1 transport, libcurl, Apache `h2_mod` and `mod_cgi`, timeout handling, ref backends (files, reftable), `git fast-import`, `git update-ref`, `git pack-refs`, reftable internals (`refs_resolve_ref_unsafe()`, `reftable_stack_reload()`, `tables.list` handling, `fd_writer`, `merged_iter_next_entry()`, `merged_iter_next_void()`, `reftable_ref_iterator_advance()`, `reftable_backend_read_ref()`, `reftable_be_reflog_exists()`, `refs_verify_refname_available()`, `reftable_be_transaction_prepare()`, `prepare_single_update()`), **upstream Apache bug tracking**.
- New behavior:
  - Apache’s `Timeout` directive increased to 600 seconds, directly addressing the root cause of CI hangs.
  - The `t5551` many-tags test case now runs in an isolated bare repository, reducing runtime for the entire test script from ~2.7 seconds to ~1.9 seconds (normal runs) and from ~95 seconds to ~37 seconds (EXPENSIVE runs).
  - GitLab CI status badge added to `README.md`, linking to the pipelines page for the `master` branch on GitLab’s official mirror.
  - **Quadratic-time behavior fix**: Kristofer Karlsson’s patch exposes tombstones to iterator bounds checks in `merged_iter_next_void()`, allowing early termination when a tombstone’s name sorts after the target ref. This reduces runtime from O(n²) to O(n) for bulk ref deletion/re-creation workflows. The fix adds tombstone-skipping loops at call sites (e.g., `reftable_be_reflog_exists()`) to compensate for the iterator now returning tombstones. **Benchmark results**: 8,000 refs (delete `old-*`, create `new-*`) improved from 27s to 0.09s (300x speedup); recreate-same-refs improved ~100x.
  - **Platform-compatibility documentation**: Michael Montalbo’s external pull request to Apache’s GitHub mirror documents the upstream bug 70131 in detail, ensuring future contributors can access the diagnostic context without hitting a login wall.
- Environment details:
  - libcurl: 8.6.0 (GitHub) vs 8.7.1 (GitLab); bug persists across versions.
  - macOS build image: 14 (GitHub) vs 15 (proposed); Linux CI failures now observed, with logs truncated but suspected to stem from the same Apache bug.
  - Apache `h2_mod` and `mod_cgi`: default `Timeout 300` was being hit; logs showed `AH01220: Timeout waiting for output from CGI script` and `AH00574: ap_content_length_filter: apr_bucket_read() failed`.
  - Upstream Apache bug 70131: confirmed as the source of hangs/stalls; affects both HTTP/1.1 (`t5551`) and HTTP/2 (`t5559`); reproducible without Git. The bug report is now **publicly documented** via an external pull request to Apache’s GitHub mirror.
  - Timing data:
    - Cold-cache `upload-pack` advertisement of 100,000 loose refs takes ~10 seconds on a local SSD; warm-cache or packed-ref scenarios complete in <0.5 seconds.
    - Reftable backend creates 50,000 refs in 150ms (vs ~220ms for files backend), a ~30% speedup.
    - Bulk ref creation in reftable: 2,000 `stat()` calls on `tables.list` consume ~33ms (25% of runtime for 50,000 refs).
    - Reflog writes (unbuffered) consume ~70ms (54% of runtime) for 50,000 refs; buffering via stdio could halve this.
    - **Quadratic-time behavior before fix**: Deleting and re-creating 8,000 refs takes 1.8s; 16,000 refs takes 7.1s (4x increase for 2x input size). The issue is reproducible with `git for-each-ref | git update-ref --stdin` and stems from tombstone iteration in both `refs_verify_refname_available()` and `reftable_be_transaction_prepare()`.
    - **Quadratic-time behavior after fix**: 8,000 refs now take 0.09s (300x speedup); 16,000 refs take 0.18s. The O(n²) bottleneck is eliminated **even when compaction is disabled**.
  - Failure modes:
    - HTTP/1.1 (`t5551`): `curl 18 transfer closed with outstanding read data remaining` (mid-transfer abort).
    - HTTP/2 (`t5559`): indefinite stall (hang).
  - Reftable performance quirks:
    - `reftable_stack_reload()` calls `stat()` 2,000 times during bulk ref creation, accounting for 85% of runtime in `strace` analysis (~33ms).
    - `fd_writer` writes reflog entries individually without buffering, consuming ~70ms (54% of runtime).
    - Disabling reflog checks (`core.logallrefupdates=always`) paradoxically slows bulk ref creation from 129ms to 195ms due to increased `stat()` overhead.
    - A "never" reflog mode reduces runtime to 96ms, confirming the `stat()` overhead.
    - **Tombstone handling**: Deleted refs are marked as tombstones rather than purged, forcing subsequent operations to scan all tombstones to confirm refname availability. This design avoids compaction overhead but creates quadratic-time behavior during bulk ref re-creation.
  - Reproducibility issue: `git for-each-ref | git update-ref` triggers quadratic-time behavior due to tombstone iteration in both `refs_verify_refname_available()` and `reftable_be_transaction_prepare()`.
