Subject: macOS CI hang in t5551/t5559 – root cause and fix
Series version: none (standalone patch)
Originating author: Michael Montalbo
Thread type: bug report with proposed fix

Core problem or goal
Git’s CI jobs on GitHub’s macOS runners frequently fail due to hangs or protocol errors in the `t5551` and `t5559` tests during an `ls-refs` advertisement of 100,000 loose refs. The failures now span **multiple platforms** (macOS and Linux CI) and include HTTP/2 flow-control stalls (hangs), `curl 18 transfer closed with outstanding read data remaining` errors (mid-transfer aborts), and truncated Linux CI logs. The root cause has been identified as **Apache’s default 300-second timeout being hit** during the `ls-refs` advertisement, causing the server to terminate the connection mid-transfer. The goal is to eliminate these failures by addressing the underlying timeout or protocol issue, rather than masking it through test adjustments or environment updates.

Current status
Michael Montalbo’s proposed fix (packing refs and aligning `$JOBS` with runner core count) is implemented on `mm/macos-ci-hang-fix` and reduces CI runtime from a 360-minute timeout to 30–44 minutes on macOS, but **does not resolve the underlying timeout issue**. The failure mode has shifted: macOS now consistently fails with `curl 18` mid-transfer aborts, and Linux CI exhibits similar failures (though logs are truncated). Patrick Steinhardt has **diagnosed the root cause** as Apache’s 300-second timeout being hit during the `ls-refs` advertisement, reproducing the `curl 18` error locally by setting `Timeout 1` in Apache’s configuration. The thread is now focused on **whether to increase the timeout, further optimize the test, or extend keepalive mechanisms to cover `ls-refs`**. No maintainer decision yet; the patch remains under review, with **no new fixes proposed** beyond the existing two-part change.
