This thread is about a persistent CI hang in Git’s macOS (and now Linux) test suite, specifically in `t5551` and `t5559`, where an `ls-refs` advertisement of 100,000 loose refs triggers either a mid-transfer abort (`curl 18`) or an indefinite HTTP/2 stall. Michael Montalbo traced the root cause to **Apache’s `mod_http2` bug 70131**, which causes hangs or protocol errors when the server-side 300-second timeout is hit. His initial two-part fix—packing refs and aligning `$JOBS` with runner core count—reduced CI runtime from 360 minutes to 30–44 minutes on macOS but did not resolve the underlying timeout issue, instead shifting failures to `curl 18` aborts on macOS and similar errors on Linux CI.

Montalbo later proposed a **client-side mitigation**: enabling Git’s `http.lowSpeedLimit` and `http.lowSpeedTime` settings to convert indefinite hangs into fast, bounded failures. While Patrick Steinhardt and Junio C Hamano had previously raised concerns about the deadlock risk and requested deeper debugging (now addressed by the Apache bug diagnosis), Jeff King (Peff) has now weighed in with skepticism about the mitigation. He argues it merely "punts" on the problem by introducing spurious test failures and notes Git’s historical preference for eliminating flakes at the source rather than masking them. Peff suggests either **waiting for an upstream Apache fix** or **increasing Apache’s timeout value** as alternatives. The discussion now centers on the trade-offs between mitigation, upstream resolution, and test reliability, with no clear consensus yet on the best path forward. No new code changes have been proposed beyond the existing fix and mitigation.
