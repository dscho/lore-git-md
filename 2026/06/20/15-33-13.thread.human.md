The macOS CI hang thread has now fully converged on both the immediate fix and the deeper reftable performance analysis. The original 2-patch series—raising Apache’s `Timeout` directive to 600 seconds and isolating the many-tags test—is merged for Git 2.55, and the GitLab CI badge addition is also accepted. What remains open is purely forward-looking: the reftable backend’s quadratic-time behavior during bulk ref deletion and re-creation.

Jeff King and Patrick Steinhardt have now mapped the bottleneck to two tombstone-sensitive operations: `refs_verify_refname_available()` (scanning tombstones to confirm refname availability) and `reftable_be_transaction_prepare()` (reading each ref individually during transaction preparation). The latter was previously overlooked; Peff’s latest analysis shows it contributes roughly half the runtime overhead in artificial benchmarks like `git for-each-ref | git update-ref --stdin`. He sketches a potential optimization—merging the sorted list of transaction refs with reftable contents via an iterator—but defers further work, aligning with Patrick’s view that this is an edge case rather than a pressing issue. The thread leaves the quadratic-time behavior as a known architectural trade-off: tombstoning avoids compaction overhead but creates performance cliffs for bulk operations. No immediate fix is proposed, but the discussion provides a clear roadmap for future optimizations if real-world workflows begin hitting these limits.
