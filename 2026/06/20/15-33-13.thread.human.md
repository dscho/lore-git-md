This thread is about a persistent CI hang in Git’s macOS (and now Linux) test suite, specifically in `t5551` and `t5559`, where an `ls-refs` advertisement of 100,000 loose refs triggers either an indefinite HTTP/2 stall or a `curl 18` mid-transfer abort. The root cause is Apache’s `mod_http2` bug 70131, which hits a 300-second server-side timeout during slow CI runs. Michael Montalbo initially proposed a two-part fix—packing refs and aligning `$JOBS` with runner core counts—which cut macOS CI runtime from 360 minutes to 30–44 minutes but didn’t resolve the underlying timeout issue. The failure mode then shifted to consistent `curl 18` errors on macOS and similar failures on Linux CI, with logs often truncated.

The discussion has since focused on how to address the timeout. Montalbo suggested a client-side mitigation (enabling Git’s `http.lowSpeedLimit` and `http.lowSpeedTime` settings) to convert hangs into fast failures, but Jeff King (Peff) rejected this as merely "punting" on the problem, arguing it conflicts with Git’s preference for eliminating flakes at the source. Patrick Steinhardt recently weighed in, clarifying that the Apache bug affects both HTTP/1.1 and HTTP/2, meaning an upstream fix alone wouldn’t fully resolve the issue. He proposed increasing Apache’s timeout value as a pragmatic Git-side fix, which would reduce the likelihood of hitting the problematic state without introducing spurious test failures. This suggestion has refocused the thread on evaluating timeout adjustments, though no maintainer has yet endorsed a specific solution. The patch remains under review, with the core question still unresolved: whether to wait for an upstream Apache fix, adjust timeouts, or accept some level of flakiness.
