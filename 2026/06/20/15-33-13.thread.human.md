This thread is about a persistent CI hang in Git’s test suite on macOS (and now Linux) runners, specifically in `t5551` and `t5559` during an `ls-refs` advertisement of 100,000 loose refs. Michael Montalbo initially proposed a fix—packing refs and aligning `$JOBS` with runner core counts—which reduced CI runtime from a 360-minute timeout to 30–44 minutes but didn’t fully resolve the underlying issue. Jeff King (Peff) and Junio C Hamano questioned whether the fix eliminated the HTTP/2 deadlock risk or merely masked it, while Patrick Steinhardt identified a libcurl version mismatch (8.6.0 on GitHub vs. 8.7.1 on GitLab) and a macOS build image discrepancy (version 14 vs. 15) as potential environmental factors.

The latest update reveals the problem is broader than macOS: the same test now fails on Linux CI, though the exact error is unclear due to truncated logs. The macOS failure mode has shifted from a hang to a `curl 18` error ("transfer closed with outstanding read data remaining"), suggesting a mid-transfer abort rather than a stall. Patrick Steinhardt ruled out disabling the test as a solution, emphasizing the need for root-cause analysis. The thread remains focused on diagnosing whether the issue lies in Git’s HTTP/2 transport, libcurl, Apache’s `h2_mod`, or the virtualized environment. No maintainer decision has been made, and the patch is still under review while debugging continues. Key participants—Montalbo, Peff, Steinhardt, and Junio—agree the fix isn’t complete without addressing the underlying protocol or environmental issues.
