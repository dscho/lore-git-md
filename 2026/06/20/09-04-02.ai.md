This is the **stacked-branch safety implementation discussion** for the `git branch --delete-merged` series, now in its 16th iteration. Harald Nordgren responds to Junio C Hamano’s proposal for handling dependent branches (e.g., `feature2` stacking on `feature1`) when deleting merged branches. The email focuses on the **retargeting approach**—automatically updating the upstream of dependent branches to the branch that merged the deleted one (e.g., `origin/master`)—and raises two edge cases: recursion (chains like `b1→b2→b3`) and self-referential upstreams (e.g., `b3→b3`).

Key technical details for the AI summarizer:
- **Subsystem**: Branch management (`builtin/branch.c`).
- **Behavior change**: Proposed retargeting logic for dependent branches (e.g., `feature2@{u} → origin/master` if `feature1` is deleted).
- **Edge cases**:
  - **Recursion**: Chains of stacked branches (e.g., `b1→b2→b3`). Harald notes that a single pass may not suffice, and multiple passes could still fail.
  - **Self-reference**: Branches pointing to themselves as upstream (e.g., `b3→b3`). Suggests removing the upstream of dependent branches (e.g., `b2@{u} → unset`) and warning the user.
- **User experience**: Prefers warnings over errors for edge cases, as "no upstream" is not catastrophic.
- **Implementation complexity**: Retargeting requires careful handling of branch traversal order and may need iterative resolution.
- **Related work**: Mentions GitHub’s stacked-PR automation as a precedent for retargeting (though GitHub’s solution is simpler, as it only needs to update the base branch of a PR, not Git’s internal refs).

Harald’s tone leans toward **pragmatism**: retargeting is preferable to aborting, but edge cases should not block progress. The discussion suggests that the final design may need to:
1. Limit retargeting to one level of dependency (e.g., `b1→b2` but not `b1→b2→b3`).
2. Handle self-references by unsetting the upstream and warning.
3. Document the behavior clearly in the commit message and man page.

This email advances the thread by clarifying the **trade-offs of retargeting** and identifying unresolved edge cases, which will likely shape the v17 implementation. The next steps are to decide whether to:
- Implement retargeting with warnings for edge cases (Harald’s preference).
