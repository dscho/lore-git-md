Core problem or goal
Add a `nanosec` Meson build option that defines the `USE_NSEC` macro, matching the existing Autotools and Makefile-based `USE_NSEC` knob for sub-second file timestamp tracking. The thread has evolved from a straightforward build system parity patch into a comprehensive re-evaluation of `USE_NSEC`’s necessity, reliability, and interoperability. Jeff King’s testing demonstrates that historical "racy Git" concerns about filesystem timestamp granularity are obsolete on modern Linux, but new interoperability risks emerge when mixing `USE_NSEC` and non-`USE_NSEC` implementations (e.g., Git and JGit). The discussion now centers on whether the knob should be deprecated, flipped to `true` by default, or left as-is.

Current status
The original patch remains queued for merging by Junio C Hamano with no changes requested. The discussion has shifted from build system parity to the technical merits, risks, and long-term viability of `USE_NSEC`. Jeff King’s findings challenge the assumption that the knob is inherently problematic, but his interoperability caveats introduce new complexity. The thread is now a three-way debate: (1) keep the knob as-is (original patch), (2) flip its default to `true`, or (3) deprecate/remove it entirely.

Key technical details
- Files touched: `meson_options.txt`, `meson.build` (original patch)
- New Meson option: `nanosec` (boolean, default `false`)
- Macro defined: `USE_NSEC` (when `nanosec=true`)
- Subsystem: build system (Meson), filesystem timestamp handling, index interoperability
- On-disk or runtime behavior: `USE_NSEC` enables Git to track sub-second timestamps, which can trigger stat-dirty re-reads if mixed with non-`USE_NSEC` implementations (performance risk, not correctness). Modern Linux filesystems (ext4, ext2, vfat, CIFS) preserve nanosecond timestamps correctly, obsoleting historical "racy Git" concerns on these platforms.
- Kernel fixes: Timestamp rounding issues were resolved for most filesystems by kernel 4.3 (2015), with FAT support added later. This undermines the original rationale for `USE_NSEC` as a safety measure.
- Interoperability risks: JGit’s millisecond-resolution APIs could force stat-dirty re-reads if used with `USE_NSEC`-enabled Git. Similarly, a non-`USE_NSEC` Git writing an index with millisecond timestamps would appear stat-dirty to an `USE_NSEC`-enabled Git.
- Test methodology: Peff’s testing involved writing files, dropping caches, and re-reading timestamps with `ls --full-time` to verify consistency. No formal test coverage exists for interoperability edge cases.
- Documentation reference: `Documentation/technical/racy-git.adoc` (historical concerns now obsolete on modern Linux)

Open questions and loose ends
- **Is `USE_NSEC` still necessary as a safety measure?** Jeff King’s testing suggests the knob is redundant on modern Linux, but it is unclear whether this applies to other platforms (Windows, macOS, older kernels, or network filesystems). Further testing is needed to confirm.
- **Should the default for `USE_NSEC` change?** Peff’s findings could justify flipping the default in `config.make.uname` or the Meson option, but the interoperability risks (e.g., JGit compatibility) complicate this. No concrete proposal has been made.
- **Should `USE_NSEC` be deprecated or removed?** Patrick Steinhardt’s earlier skepticism about the knob’s value remains unresolved. If the knob is no longer problematic, does it still serve a purpose, or should it be removed to reduce complexity? No deprecation patch has been submitted.
- **Build system parity vs. deprecation:** The original goal of Meson/Autotools/Makefile parity is still achieved by the patch, but the discussion now questions whether all knobs should be mirrored or if some should be deprecated.
- **Interoperability trade-offs:** The performance risks of mixing `USE_NSEC` and non-`USE_NSEC` implementations (e.g., Git and JGit) are theoretical but untested. Should this block a default flip, or is the risk acceptable?
- **Rationale and trade-offs:** The commit message still omits a clear explanation of why a user might want `USE_NSEC` or the risks involved. This gap persists despite the expanded discussion.
