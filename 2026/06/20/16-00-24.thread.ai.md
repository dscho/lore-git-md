Core problem or goal
Add a `nanosec` Meson build option that defines the `USE_NSEC` macro, matching the existing Autotools and Makefile-based `USE_NSEC` knob for sub-second file timestamp tracking. The thread has evolved into a comprehensive re-evaluation of `USE_NSEC`’s necessity, reliability, interoperability, and configuration level (build-time vs. runtime). Jeff King’s testing demonstrated that historical "racy Git" concerns about filesystem timestamp granularity are obsolete on modern Linux, but new interoperability risks emerge when mixing `USE_NSEC` and non-`USE_NSEC` implementations (e.g., Git and JGit). Brian M. Carlson’s proposal to flip the default to `true` for most users, with a config knob for overrides and future auto-detection via `statfs`, and Patrick Steinhardt’s proposal to remove the build-time option entirely in favor of runtime configuration or auto-detection, shift the discussion toward concrete changes: prioritizing performance for the majority while retaining flexibility for edge cases, and questioning whether the knob should exist at all.

- Macro defined: `USE_NSEC` (when `nanosec=true` or default is flipped).
- Proposed runtime config knob: `core.useNsec` (boolean, default `true` on safe platforms, with auto-detection or user override).
- Subsystem: build system (Meson), filesystem timestamp handling, index interoperability, config system, repository initialization.
- On-disk or runtime behavior: `USE_NSEC` enables Git to track sub-second timestamps, which can trigger stat-dirty re-reads if mixed with non-`USE_NSEC` implementations (performance risk, not correctness). Modern Linux filesystems (ext4, ext2, vfat, CIFS, NTFS, FUSE) preserve nanosecond timestamps correctly, obsoleting historical "racy Git" concerns on these platforms.
- Kernel fixes: Timestamp rounding issues were resolved for most filesystems by kernel 4.3 (2015), with FAT support added later. This undermines the original rationale for `USE_NSEC` as a safety measure.
- Interoperability risks: JGit’s millisecond-resolution APIs could force stat-dirty re-reads if used with `USE_NSEC`-enabled Git. Similarly, a non-`USE_NSEC` Git writing an index with millisecond timestamps would appear stat-dirty to an `USE_NSEC`-enabled Git. Brian’s proposal mitigates this by retaining a config knob for users to override the default; Patrick’s proposal mitigates it by making the setting runtime-configurable.
- Proposed auto-detection: A future Linux-specific `statfs` call could auto-detect safe filesystems, but this introduces platform-specific code and complexity. Patrick’s proposal suggests this could be part of runtime configuration.
- Build-time vs. runtime configuration: The original patch implements a build-time option, but Patrick’s proposal argues that filesystem behavior varies at runtime, making a build-time knob too coarse. A runtime setting would allow Git to enable nanosecond resolution by default on safe platforms while providing a fallback for edge cases.
- Test methodology: Peff’s testing involved writing files, dropping caches, and re-reading timestamps with `ls --full-time` to verify consistency. No formal test coverage exists for interoperability edge cases, auto-detection, or runtime configuration.
- Documentation reference: `Documentation/technical/racy-git.adoc` (historical concerns now obsolete on modern Linux).
