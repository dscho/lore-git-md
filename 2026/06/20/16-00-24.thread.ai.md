Core problem or goal
Add a `nanosec` Meson build option that defines the `USE_NSEC` macro, matching the existing Autotools and Makefile-based `USE_NSEC` knob for sub-second file timestamp tracking. The thread has evolved from a straightforward build system parity patch to a deeper technical debate about whether `USE_NSEC` should exist at all, given historical concerns about filesystem timestamp granularity and "racy Git" issues. Jeff King’s recent testing suggests these concerns may no longer apply on modern Linux filesystems, reopening the question of the knob’s viability.

Current status
The original patch remains queued for merging by Junio C Hamano with no changes requested. The discussion has shifted from build system parity to the technical merits and risks of `USE_NSEC`. No new patch versions or deprecation proposals have been submitted, but Jeff King’s findings challenge the assumption that `USE_NSEC` is inherently problematic. The thread now centers on whether the knob is still necessary, whether its default should change, or whether it should be deprecated.

Key technical details
- Files touched: `meson_options.txt`, `meson.build` (original patch)
- New Meson option: `nanosec` (boolean, default `false`)
- Macro defined: `USE_NSEC` (when `nanosec=true`)
- Subsystem: build system (Meson), with implications for filesystem compatibility and timestamp handling
- On-disk or runtime behavior: `USE_NSEC` enables Git to track sub-second timestamps, which can trigger "racy Git" issues on filesystems with coarse timestamp granularity (e.g., CEPH, CIFS, NTFS, UDF) or network filesystems. Jeff King’s testing on modern Linux (ext4, ext2, vfat) suggests these concerns may be outdated, as nanosecond timestamps are preserved correctly.
- Test methodology: Peff’s test involved writing a file, dropping caches, and re-reading timestamps with `ls --full-time` to verify consistency. This methodology could be extended to other platforms/filesystems.
- Documentation reference: `Documentation/technical/racy-git.adoc` (cited by Peff as the source of historical concerns)
- Test coverage: none added; existing Autotools/Makefile tests cover the functionality

Open questions and loose ends
- **Is `USE_NSEC` still problematic?** Jeff King’s testing suggests the knob may be safe on modern Linux filesystems, but it is unclear whether this generalizes to other platforms (e.g., Windows, macOS, older kernels, or network filesystems). Further testing is needed to confirm.
- **Should the default for `USE_NSEC` change?** Peff’s findings could justify flipping the default in `config.make.uname` or the Meson option, but no concrete proposal has been made.
- **Should `USE_NSEC` be deprecated or removed?** Patrick Steinhardt’s earlier skepticism about the knob’s value remains unresolved. If the knob is no longer problematic, does it still serve a purpose, or should it be removed to reduce complexity?
- **Build system parity vs. deprecation:** The original goal of Meson/Autotools/Makefile parity is still achieved by the patch, but the discussion now questions whether all knobs should be mirrored or if some should be deprecated.
- **Rationale and trade-offs:** The commit message still omits a clear explanation of why a user might want `USE_NSEC` or the risks involved. This gap persists despite the expanded discussion.
