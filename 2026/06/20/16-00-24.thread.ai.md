Core problem or goal
Add a `nanosec` Meson build option that defines the `USE_NSEC` macro, matching the existing Autotools/Makefile knob for sub-second file timestamp tracking. The thread has evolved into a comprehensive re-evaluation of `USE_NSEC` necessity, reliability, interoperability, configuration level (build-time vs. runtime), auto-detection feasibility, and deprecation. Jeff King’s testing demonstrated that historical "racy Git" concerns about filesystem timestamp granularity are obsolete on modern Linux (ext4, ext2, XFS, vfat, CIFS, NTFS, FUSE), but interoperability risks emerge when mixing `USE_NSEC` and non-`USE_NSEC` implementations (e.g., Git and JGit). Proposals include (1) flipping the default to `true` (Brian M. Carlson), (2) deprecating/removing the knob (Patrick Steinhardt’s earlier position), (3) converting it to runtime-configurable (Patrick Steinhardt’s latest proposal), and (4) retaining the build-time option for parity (D. Ben Knoble’s latest position). The discussion centers on whether the original patch should proceed, whether runtime configuration is justified, and whether the knob’s existence is warranted.

Key technical details
- Files touched: `meson_options.txt`, `meson.build` (original patch); future work may involve `config.mak.uname`, `git-config` machinery, `git-init`, and potentially removing the Meson option or the entire `USE_NSEC` mechanism.
- New Meson option: `nanosec` (boolean, default `false` in original patch; proposed default `true` for most users in Brian’s proposal).
- Macro defined: `USE_NSEC` (when `nanosec=true` or default is flipped).
- Proposed runtime config knob: `core.useNsec` (boolean, default TBD; Peff suggests a conservative default (`false`), but Patrick’s latest proposal does not specify a default).
- Subsystems: build system (Meson, Makefile, Autotools), filesystem timestamp handling, index interoperability, config system, repository initialization.
- On-disk or runtime behavior: `USE_NSEC` enables Git to track sub-second timestamps, which can trigger stat-dirty re-reads if mixed with non-`USE_NSEC` implementations (performance risk, not correctness). Modern Linux filesystems (ext4, ext2, XFS, vfat, CIFS, NTFS, FUSE) preserve nanosecond timestamps correctly, obsoleting historical "racy Git" concerns on these platforms.
- Kernel fixes: Timestamp rounding issues were resolved for most filesystems by kernel 4.3 (2015), with FAT support added later. This undermines the original rationale for `USE_NSEC` as a safety measure.
- Interoperability risks: JGit’s millisecond-resolution APIs could force stat-dirty re-reads if used with `USE_NSEC`-enabled Git. Similarly, a non-`USE_NSEC` Git writing an index with millisecond timestamps would appear stat-dirty to an `USE_NSEC`-enabled Git. Brian’s proposal mitigates this by retaining a config knob for users to override the default; Patrick’s latest proposal mitigates it by making the setting runtime-configurable.
- Auto-detection challenges: Peff’s testing shows no reliable, portable way to detect whether a filesystem preserves nanosecond timestamps. The proposed detection sequence (write file, flush cache, re-read timestamp) is impractical for routine use (e.g., during `git init`). Patrick’s latest proposal sidesteps auto-detection by making the feature runtime-configurable.
- Build-time vs. runtime configuration: The original patch implements a build-time option, but Patrick’s latest proposal argues for **always compiling nanosecond support into Git** (when the platform allows it) and exposing it via a runtime config knob. This balances accessibility (users no longer need to rebuild Git) with safety (the feature remains opt-in). Junio’s response highlighted that `USE_NSEC` is optional (unlike `core.ignoreCase`), which may justify retaining a build-time knob for power users, but Patrick’s proposal reduces the need for it.
- Test methodology: Peff’s testing (write file, drop caches, re-read timestamps with `ls --full-time`) is now validated for XFS. No formal test coverage exists for interoperability edge cases, auto-detection, or runtime configuration. Patrick’s latest email acknowledges the desirability of automated testing but does not let its absence block progress.
- Documentation reference: `Documentation/technical/racy-git.adoc` (historical concerns now obsolete on modern Linux).
