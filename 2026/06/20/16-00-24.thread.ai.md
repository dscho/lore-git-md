Core problem or goal
Add a `nanosec` Meson build option that defines the `USE_NSEC` macro, matching the existing Autotools and Makefile-based `USE_NSEC` knob for sub-second file timestamp tracking. The thread has evolved into a comprehensive re-evaluation of `USE_NSEC`’s necessity, reliability, interoperability, configuration level (build-time vs. runtime), and auto-detection feasibility. Jeff King’s testing demonstrated that historical "racy Git" concerns about filesystem timestamp granularity are obsolete on modern Linux, but new interoperability risks emerge when mixing `USE_NSEC` and non-`USE_NSEC` implementations (e.g., Git and JGit). Proposals now include (1) flipping the default to `true` (Brian M. Carlson), (2) deprecating/removing the knob entirely (Patrick Steinhardt’s earlier position), (3) converting it to a runtime-configurable setting (Patrick Steinhardt’s latest proposal), and (4) implementing auto-detection via `statfs` (future work, now questioned by Peff’s testing). The discussion now centers on whether runtime configuration is feasible without auto-detection, and whether the added complexity is justified.

Key technical details
- Files touched: `meson_options.txt`, `meson.build` (original patch); future work may involve `config.mak.uname`, `git-config` machinery, `git-init`, and potentially removing the Meson option entirely.
- New Meson option: `nanosec` (boolean, default `false` in original patch; proposed default `true` for most users in Brian’s proposal).
- Macro defined: `USE_NSEC` (when `nanosec=true` or default is flipped).
- Proposed runtime config knob: `core.useNsec` (boolean, default TBD; Peff suggests a conservative default to avoid breaking edge cases).
- Subsystems: build system (Meson), filesystem timestamp handling, index interoperability, config system, repository initialization.
- On-disk or runtime behavior: `USE_NSEC` enables Git to track sub-second timestamps, which can trigger stat-dirty re-reads if mixed with non-`USE_NSEC` implementations (performance risk, not correctness). Modern Linux filesystems (ext4, ext2, vfat, CIFS, NTFS, FUSE) preserve nanosecond timestamps correctly, obsoleting historical "racy Git" concerns on these platforms.
- Kernel fixes: Timestamp rounding issues were resolved for most filesystems by kernel 4.3 (2015), with FAT support added later. This undermines the original rationale for `USE_NSEC` as a safety measure.
- Interoperability risks: JGit’s millisecond-resolution APIs could force stat-dirty re-reads if used with `USE_NSEC`-enabled Git. Similarly, a non-`USE_NSEC` Git writing an index with millisecond timestamps would appear stat-dirty to an `USE_NSEC`-enabled Git. Brian’s proposal mitigates this by retaining a config knob for users to override the default; Patrick’s proposal mitigates it by making the setting runtime-configurable.
- Auto-detection challenges: Peff’s testing shows no reliable, portable way to detect whether a filesystem preserves nanosecond timestamps. The proposed detection sequence (write file, flush cache, re-read timestamp) is impractical for routine use (e.g., during `git init`). Even on filesystems where truncation was historically problematic, Peff was unable to reproduce it.
- Build-time vs. runtime configuration: The original patch implements a build-time option, but Patrick’s proposal argues that filesystem behavior varies at runtime, making a build-time knob too coarse. Peff’s feedback suggests runtime configuration is desirable but may require a conservative default (e.g., `false`) to avoid breaking edge cases. Junio’s response highlights that `USE_NSEC` is optional (unlike `core.ignoreCase`), which may justify retaining a build-time knob for power users.
- Test methodology: Peff’s testing involved writing files, dropping caches, and re-reading timestamps with `ls --full-time` to verify consistency. No formal test coverage exists for interoperability edge cases, auto-detection, or runtime configuration.
- Documentation reference: `Documentation/technical/racy-git.adoc` (historical concerns now obsolete on modern Linux).
