Core problem or goal
Add a `nanosec` Meson build option that defines the `USE_NSEC` macro, matching the existing Autotools and Makefile-based `USE_NSEC` knob for sub-second file timestamp tracking. The thread has evolved into a comprehensive re-evaluation of `USE_NSEC`’s necessity, reliability, and interoperability. Jeff King’s testing demonstrated that historical "racy Git" concerns about filesystem timestamp granularity are obsolete on modern Linux, but new interoperability risks emerge when mixing `USE_NSEC` and non-`USE_NSEC` implementations (e.g., Git and JGit). Brian M. Carlson’s proposal to flip the default to `true` for most users, with a config knob for overrides and future auto-detection via `statfs`, shifts the discussion toward a concrete change: prioritizing performance for the majority while retaining a fallback for edge cases.

Current status
The original patch remains queued for merging by Junio C Hamano with no changes requested. The discussion has expanded from build system parity to the technical merits, risks, and long-term viability of `USE_NSEC`, now including a proposal to flip its default. No new patch versions, deprecation proposals, or default-flipping patches have been submitted yet. The thread is now a four-way debate: (1) keep the knob as-is (original patch), (2) flip its default to `true` (Brian’s proposal), (3) deprecate/remove it entirely (Patrick Steinhardt’s earlier position), or (4) implement auto-detection via `statfs` (future work). The original goal of Meson/Autotools/Makefile parity is still achieved by the patch, but the discussion now questions whether all knobs should be mirrored or if some should be deprecated or have their defaults changed.

Key technical details
- Files touched: `meson_options.txt`, `meson.build` (original patch); future work may involve `config.mak.uname`, `git-config` machinery, and filesystem detection code.
- New Meson option: `nanosec` (boolean, default `false` in original patch; proposed default `true` for most users).
- Macro defined: `USE_NSEC` (when `nanosec=true` or default is flipped).
- Subsystem: build system (Meson), filesystem timestamp handling, index interoperability, config system.
- On-disk or runtime behavior: `USE_NSEC` enables Git to track sub-second timestamps, which can trigger stat-dirty re-reads if mixed with non-`USE_NSEC` implementations (performance risk, not correctness). Modern Linux filesystems (ext4, ext2, vfat, CIFS, NTFS, FUSE) preserve nanosecond timestamps correctly, obsoleting historical "racy Git" concerns on these platforms.
- Kernel fixes: Timestamp rounding issues were resolved for most filesystems by kernel 4.3 (2015), with FAT support added later. This undermines the original rationale for `USE_NSEC` as a safety measure.
- Interoperability risks: JGit’s millisecond-resolution APIs could force stat-dirty re-reads if used with `USE_NSEC`-enabled Git. Similarly, a non-`USE_NSEC` Git writing an index with millisecond timestamps would appear stat-dirty to an `USE_NSEC`-enabled Git. Brian’s proposal mitigates this by retaining a config knob for users to override the default.
- Proposed auto-detection: A future Linux-specific `statfs` call could auto-detect safe filesystems, but this introduces platform-specific code and complexity.
- Test methodology: Peff’s testing involved writing files, dropping caches, and re-reading timestamps with `ls --full-time` to verify consistency. No formal test coverage exists for interoperability edge cases or auto-detection.
- Documentation reference: `Documentation/technical/racy-git.adoc` (historical concerns now obsolete on modern Linux).

Open questions and loose ends
- **Should the default for `USE_NSEC` flip to `true`?** Brian’s proposal justifies this based on Peff’s testing, but the interoperability risks (e.g., JGit compatibility) and potential edge cases on non-Linux platforms remain unresolved. No consensus has emerged on whether the performance benefits outweigh the risks.
- **Should the config knob be a build-time option or a runtime setting?** The original patch implements a build-time option, but Brian’s proposal suggests a runtime config knob. This would require changes to the config system and may complicate the build process.
- **Is auto-detection via `statfs` worth the added complexity?** The proposal introduces platform-specific code and potential maintenance burdens. Contributors may resist this in favor of simpler, cross-platform solutions.
- **Should `USE_NSEC` be deprecated or removed?** Patrick Steinhardt’s earlier skepticism about the knob’s value remains unresolved. If the knob is no longer problematic, does it still serve a purpose, or should it be removed to reduce complexity? No deprecation patch has been submitted.
- **Build system parity vs. deprecation/default flip:** The original goal of Meson/Autotools/Makefile parity is still achieved by the patch, but the discussion now questions whether all knobs should be mirrored or if some should be deprecated or have their defaults changed.
- **Interoperability trade-offs:** The performance risks of mixing `USE_NSEC` and non-`USE_NSEC` implementations (e.g., Git and JGit) are theoretical but untested. Should this block a default flip, or is the risk acceptable given the fallback config knob?
- **Rationale and trade-offs:** The commit message for the original patch still omits a clear explanation of why a user might want `USE_NSEC` or the risks involved. This gap persists despite the expanded discussion.
- **Platform coverage:** Peff’s testing focused on Linux; it is unclear whether the findings apply to Windows, macOS, older kernels, or network filesystems. Further testing is needed to confirm.
