This thread began as a simple patch to add a `nanosec` Meson build option mirroring the Autotools `USE_NSEC` knob, but has grown into a broader discussion about whether `USE_NSEC` is still useful, how it should be configured, and what its default behavior should be.

D. Ben Knoble’s original patch added the Meson option to maintain build system parity, particularly for source distributions like Gentoo where users might want to enable nanosecond timestamp tracking. The discussion quickly expanded when Jeff King (Peff) tested modern Linux filesystems (ext4, ext2, XFS, vfat, CIFS, NTFS, FUSE) and found that nanosecond timestamps are preserved correctly, making the historical "racy Git" concerns obsolete on these platforms. However, Peff also identified interoperability risks when mixing `USE_NSEC` and non-`USE_NSEC` implementations (e.g., Git and JGit), where stat-dirty re-reads could degrade performance.

The debate now centers on three competing proposals: Brian M. Carlson suggested flipping the default to `true` for most users, Patrick Steinhardt proposed deprecating or removing the knob entirely, and Knoble’s latest defense of the build-time option argues it should remain unless `USE_NSEC` is deprecated. Patrick’s newest proposal offers a middle ground—always compile nanosecond support into Git (when the platform allows it) but make it opt-in via a runtime config knob (e.g., `core.useNsec`). This avoids the auto-detection challenges Peff raised while making the feature more accessible than the current build-time knob. Junio has queued the original patch for merging, but the broader discussion remains unresolved.

Key open questions include whether the original patch should proceed, what the default for `core.useNsec` should be (Peff suggests `false` to avoid edge cases), and whether the added complexity of runtime configuration is justified. The thread has also revealed gaps in platform coverage (Windows, macOS, older kernels) and interoperability testing, leaving some trade-offs unaddressed. No concrete implementation for runtime configuration has been proposed yet, but Patrick’s latest email suggests a pragmatic path forward.
