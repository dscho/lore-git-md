This is a **performance bug report** targeting the reftable backend, part of the ongoing macOS CI hang thread. Jeff King (Peff) identifies a **quadratic-time slowdown** in `git update-ref` when re-creating many refs after deleting them. The issue surfaces only with the reftable backend and is reproducible with a simple script: deleting 8,000 refs and re-creating them takes 7 seconds, while 1,000 refs take 0.125 seconds—scaling by 8x input but 56x runtime.

The root cause appears to be tombstone handling in reftable’s iterator logic (`merged_iter_next_entry()`), though Peff hasn’t pinpointed the exact mechanism. This is a **substantive regression** compared to the files backend, where the same operation scales linearly. The commit message does not propose a fix, but the script and timing data provide a clear reproduction case for anyone working on reftable performance.

This is **not part of the already-merged CI hang fix** (which addressed Apache timeouts and test isolation). Instead, it’s a follow-up observation that may become a priority if reftable adoption grows. The quadratic behavior is likely to bite users with large refsets, making it worth attention despite Peff’s offhand framing as "more interesting" than micro-optimizations.
