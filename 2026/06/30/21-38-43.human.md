This is a bugfix patch for `git blame -b` output formatting, addressing the usability friction reported by Laszlo Ersek. René Scharfe implements Junio C Hamano’s proposed solution: stop reserving an extra hex digit for a caret marker that is never displayed when `-b` (blank boundary) is used. The patch refactors the mark-handling logic in `blame.c` to count and print boundary markers only when they are actually shown, ensuring abbreviated commit hashes respect the user’s `core.abbrev` setting.

The change is minimal and targeted, affecting only the `-b` mode of `git blame`. It introduces no new configuration variables and maintains backward compatibility for all other blame output modes. The patch splits the existing mark-handling code into reusable functions (`handle_marks`, `print_marks`, `count_marks`) and adjusts the abbreviation calculation to account for the maximum number of marks that might appear on any line. This ensures the commit hash column remains properly aligned regardless of which marks are active.

René notes the patch lacks tests, which is typical for early iterations of a fix. The implementation assumes multiple marks could appear on a single line but does not verify this edge case, though the code is written to handle it correctly. No downstream compatibility concerns have been raised in the thread so far, and the change aligns with the project’s preference for small, self-contained patches.

This patch directly addresses the core issue—manual workflows involving `git blame -b` and `git rebase -i` no longer require users to manually truncate commit hashes when pasting between the two commands. The fix is uncontroversial and appears ready for further review or testing.
