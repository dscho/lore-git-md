This is a follow-up in the `git replay --linearize` interface design debate, specifically Patrick Steinhardt’s reply to Johannes Schindelin’s critique of mirroring `git rebase`'s `--rebase-merges=<mode>` syntax.

Steinhardt acknowledges Schindelin’s usability concerns and accepts that consistency with `git rebase` is not an absolute requirement. His key point is that any divergence from `git rebase`’s interface must be **explicitly justified** in the commit message, not just implemented. He reiterates that he is open to a different design but wants the rationale documented so that future contributors understand why the project chose to deviate. This shifts the discussion from "should we mirror `git rebase`?" to "how do we document the trade-offs if we don’t?"

The email does not propose a specific alternative interface or resolve the debate, but it clarifies the bar for moving forward: the series must either (a) adopt `git rebase`’s syntax or (b) include a commit message that explains why that syntax is a poor fit for `git replay`. This requirement applies to both the `--linearize` flag and any future merge-handling modes (e.g., `--replay-cousins`). The thread remains blocked on this design question, alongside the unresolved regression in `--linearize` behavior.
