The `git blame -b` output formatting thread has reached a clear resolution. The issue began when Laszlo Ersek reported that `git blame -b` (which shows boundary commits as blank) was reserving an extra hex digit in commit hash abbreviations for a caret marker that was never displayed. This caused non-boundary commit hashes to exceed the user’s `core.abbrev` setting by one character, creating a minor but persistent friction in workflows that involve copying hashes from `git blame -b` into `git rebase -i`.

René Scharfe proposed a targeted fix that refactors the mark-handling logic in `blame.c` to dynamically calculate the space needed for boundary, ignored, or unblamable marks (like `^`, `*`, or `?`), reserving an extra hex digit only when these marks are actually shown. This ensures the abbreviated commit hash length matches the user’s `core.abbrev` setting without over-allocation. The patch is minimal, well-structured, and directly addresses the core problem. Laszlo has now confirmed the fix works as intended in his workflow, providing a `Tested-by` trailer and endorsing the change. No new configuration variables were needed, and the original reporter considers the issue resolved.

The discussion has converged on the patch, which is now awaiting final validation. The only loose ends are the lack of test coverage—René noted the patch doesn’t include tests—and the potential for edge cases, such as multiple marks per line, though the dynamic logic should handle them. No backward-compatibility concerns have been raised, and the patch preserves the fixed-width nature of the output. The next steps will likely involve adding tests to verify the fix and prevent regressions before the patch is merged.
