The thread began when Laszlo Ersek reported a usability friction in `git blame -b`: the command reserved an extra hex digit in commit hash abbreviations for a caret marker that was never displayed, causing non-boundary commit hashes to exceed the user’s `core.abbrev` setting by one character. This made it cumbersome to use the output in manual workflows like interactive rebase, where the hashes in the blame output didn’t match the length of those in the rebase TODO list.

René Scharfe posted a patch that refactors the mark-handling logic in `blame.c` to count and print boundary/ignored/unblamable marks only when they are actually shown. This ensures the abbreviated commit hash length aligns with the user’s `core.abbrev` setting, resolving the issue. Laszlo confirmed the fix with a Tested-by trailer, and Junio C Hamano reviewed the patch positively, marking it as straightforward and well-structured. The patch touches `blame.c`, updates `Documentation/git-blame.adoc`, and adjusts test expectations in `t/t8002-blame.sh`.

The patch is now ready for integration, with no backward-compatibility concerns raised. The only loose end is test coverage: René noted the patch lacks tests to verify the fix and prevent regressions, including edge cases like multiple marks per line. No one has yet proposed or objected to adding such tests. The thread is otherwise closed, with all participants considering the issue resolved.
