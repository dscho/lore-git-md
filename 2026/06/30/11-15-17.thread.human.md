The thread began with Laszlo Ersek reporting a minor but persistent usability issue in `git blame -b`: when showing boundary commits as blank, the command reserved an extra hex digit in commit hash abbreviations for a caret marker that was never displayed. This caused non-boundary commit hashes to exceed the user’s `core.abbrev` setting by one character, creating friction in manual workflows like interactive rebase, where pasting hashes required manual truncation.

René Scharfe posted a patch that refactors the mark-handling logic in `blame.c` to count and print boundary markers only when they are actually shown. The fix is minimal and surgical, introducing helper functions to centralize mark-handling and dynamically calculate alignment based on the maximum number of marks observed. Laszlo confirmed the patch resolves the issue with a Tested-by trailer, and the discussion has converged on the solution. The patch preserves the fixed-width nature of the output, minimizing backward-compatibility risks for scripts parsing `git blame` output.

The only loose end is test coverage: the patch currently lacks tests to verify edge cases like multiple marks per line or prevent regressions. René acknowledges this but did not verify whether such edge cases exist in practice. No downstream tools relying on the previous hash length have been identified, and the thread considers the issue resolved from a usability standpoint. The patch is now awaiting final validation before integration.
