The issue stems from `git blame -b` reserving an extra hex digit for a caret marker that is never displayed, causing non-boundary commit hashes to exceed the user’s `core.abbrev` setting by one character.

Junio C Hamano proposed a targeted fix—removing the unused caret marker reservation in `git blame -b` output—and René Scharfe has now posted a patch implementing this solution. The patch refactors the mark-handling logic in `blame.c` to dynamically calculate the space needed for boundary/ignored/unblamable marks (like `*` or `?`), ensuring the abbreviated hash length matches `core.abbrev`. The change is minimal, affecting only the `-b` mode, and requires no new configuration or on-disk format changes. While the patch is well-structured and addresses the core problem, René notes it lacks test coverage, and the thread remains open to confirm whether downstream tools or scripts parsing `git blame -b` output might break due to the formatting change.

No backward-compatibility concerns have been raised so far, and the discussion is converging on this fix as the right approach.
