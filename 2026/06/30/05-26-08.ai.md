This is a **substantive follow-up discussion** in the ongoing thread about the memory leak fix in `` `git history reword` ``. Jeff King (Peff) responds to Kaartic Sivaraam’s investigation into why some commits bypass Git’s commit slab cache, refining the technical understanding of the leak’s root cause.

Peff identifies the **commit-graph** as the most likely reason a commit buffer isn’t cached: when Git loads commit metadata from the commit-graph, it never opens the raw object, so there’s nothing to cache. He also notes two other possibilities: commits that are never parsed (so `` `parse_commit()` `` is never called), and repositories where `` `save_commit_buffer` `` is disabled. These scenarios all result in `` `repo_get_commit_buffer()` `` returning a freshly allocated buffer, which must be explicitly freed with `` `repo_unuse_commit_buffer()` ``—the exact leak the original patch fixed.

On the question of whether `` `free_commit_buffer()` `` is also needed, Peff acknowledges Sivaraam’s point that the leak only affects non-slab commits and the `` `git history reword` `` code path is unlikely to process enough commits to create meaningful cache pressure. However, he suggests that if there’s a natural point in the program where Git can signal it’s done with a commit, freeing cached buffers there would be a low-cost defensive measure—especially in repos with an up-to-date commit-graph, where cached entries are already sparse. He treats this as a separate, optional follow-up rather than a requirement for the current fix.

The discussion remains **diagnostic and forward-looking**: no regression or design flaw is being raised, and the original patch is still considered correct. The open question is now **why some commits bypass the slab cache**, with the commit-graph as the leading hypothesis. This insight could inform future optimizations or test coverage for `` `git history` `` and other commands that interact with commit buffers.
