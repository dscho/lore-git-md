This is the third patch in Phillip Wood’s 11-patch series fixing how `git rebase` handles dropped commits. It targets a subtle but important edge case in the sequencer: when an external merge strategy fails for reasons *other* than a conflict (e.g., an untracked file would be overwritten), the rebase machinery should reschedule the failed pick rather than treating it as a conflict.

The patch tightens error handling in `do_pick_commit()`. Previously, any non-zero exit code from `try_merge_command()` was treated as a conflict, but external merge tools can exit with codes like 2 to signal non-conflict failures. The new logic checks the exit code: 1 still means conflict, but any other non-zero code now returns -1, which tells the sequencer to reschedule the pick. The patch also adds a check for `write_message()` failures (e.g., disk full), which similarly trigger rescheduling.

A new test in `t3404-rebase-interactive.sh` verifies the behavior: it injects a merge tool that exits with code 2, confirms the pick is rescheduled, and checks that the rebase todo list remains intact. The test is minimal but effective, covering the core scenario without overcomplicating the setup.

This is a **substantive, tested-level fix** that plugs a real correctness gap. The change is narrow and surgical, touching only the merge-failure path in `sequencer.c`. The commit message clearly explains the motivation and the technical rationale, and the test ensures the fix is exercised in CI. The patch is part of the broader rebase-dropped-commit overhaul, but it stands on its own as a meaningful improvement to the sequencer’s robustness.
