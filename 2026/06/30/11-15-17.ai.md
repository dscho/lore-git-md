This is a user experience report about `git blame` output formatting, specifically the interaction between the `-b` (blank boundary) option and commit hash abbreviation.

The email describes a minor but persistent annoyance: when `git blame -b` is used, boundary commits are shown with a blank SHA-1, but the displayed commit hashes for *non-boundary* commits are still one nibble longer than the user's `core.abbrev` setting (e.g., 13 hex chars instead of 12). This happens because Git reserves an extra nibble to mark boundary commits with a caret (`^`), even when `-b` is used to suppress that caret. The result is that commit hashes in the output don't match the user's preferred abbreviation length, making it awkward to copy-paste them into commands like `git rebase`.

The author has worked around the issue with an alias that forces `--abbrev=11`, but notes that a hypothetical `blame.abbrev` config key would be a cleaner solution. They tested with Git 2.55 and found that `blame.blankBoundary` does not address the issue. The report is framed as a question ("shouldn't git-blame stop reserving a nibble?") but is effectively a feature request for more consistent abbreviation behavior.
