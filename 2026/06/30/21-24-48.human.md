This is a usability discussion about `git blame -b` output formatting. Junio C Hamano proposes a straightforward fix to the long-standing friction in manual workflows involving `git blame -b` and `git rebase -i`. The issue: when `git blame -b` abbreviates commit hashes, it reserves an extra hex digit for a caret marker that is never displayed, causing non-boundary commit hashes to exceed the user’s `core.abbrev` setting by one character. This mismatch forces manual truncation when pasting hashes from blame output into the rebase TODO list.

Junio now suggests simply removing the extra column reservation when `-b` is used, eliminating the need for a new configuration variable like `blame.abbrev`. The change would align `git blame -b`’s output with `core.abbrev` without breaking scripts or tools, since the extra digit was never actually used for anything. This is a low-risk tweak that directly addresses the usability pain point Laszlo Ersek described.

The discussion has shifted from debating whether the issue is worth fixing to how to fix it. Junio’s proposal is minimal and targeted: no new knobs, no backward-compatibility concerns, just a small adjustment to the output formatting logic in `blame.c`. If implemented, this would make `git blame -b` more intuitive for users who rely on it during interactive rebases.
