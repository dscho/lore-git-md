This thread is Patrick Steinhardt’s 13-patch series refactoring Git’s repository discovery and setup code to separate the two phases. The goal is to untangle the current intertwined logic in `setup.c`, making it easier to consolidate repository configuration into a single `repo_init()` function. The series introduces a new `struct repo_discovery` to hold discovery results, which has drawn mostly positive feedback so far, though some open questions remain about edge cases and long-term design.

Justin Tobler has been the most active reviewer, providing substantive feedback on several patches. His latest review of patch 5/13 raises a key question about whether the new `struct repo_discovery` API should enforce single-application semantics—meaning applying repository configuration more than once would be considered a bug. This touches on the series’ broader architectural direction and could influence how later patches handle reinitialization or environment variable overrides. Earlier, Justin had also flagged potential behavioral changes in patch 2/13 (silently ignoring misconfigurations when `GIT_WORK_TREE` is present) and ordering dependencies in the same patch, as well as shallow file precedence and environment variable design in patch 3/13. Junio C Hamano reviewed patch 2/13 for a minor typo but hasn’t weighed in on the substantive points yet.

The series is still under active review, with no merge decisions made. While the refactoring is intended to be behavior-preserving, Justin’s questions highlight areas where the separation of discovery and setup might expose edge cases—particularly around environment variable handling, worktree configuration, and the lifetime of the new `struct repo_discovery`. Patrick hasn’t yet responded to the open questions, so the discussion is likely to continue as the series evolves. The work builds on recent efforts like `ps/setup-drop-global-state` and `jk/repo-info-path-keys`, and aligns with broader goals like removing `the_repository` and abstracting the object database.
