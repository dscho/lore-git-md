This is the final patch in Phillip Wood’s 11-patch series fixing how `git rebase` handles dropped commits. It prevents the sequencer from incorrectly recording dropped commits as rewritten, which stops notes from being copied to the wrong commit and ensures post-rewrite hooks receive accurate information.

The patch adds a new `PICK_RESULT_DROPPED` enum value to `enum pick_result` in `sequencer.c`. When `do_pick_commit()` determines a commit should be dropped (because its changes are already upstream or it’s part of a fixup chain that collapses to nothing), it now returns `PICK_RESULT_DROPPED` instead of `PICK_RESULT_OK`. The caller (`pick_one_commit()`) skips calling `record_in_rewritten()` for dropped commits, which prevents the notes bug and avoids confusing post-rewrite hooks. However, if the dropped commit is the final one in a fixup chain, the patch still flushes the list of rewritten commits to maintain correct state.

The patch also adjusts the behavior of the "edit" command: if the commit being edited is dropped, `git rebase --continue` will no longer amend the previous pick. The commit message notes this is still recorded as rewritten when the rebase continues, calling it out as a separate issue to be addressed later.

Tests in `t3400-rebase.sh` and `t5407-post-rewrite-hook.sh` verify the fix. The first test confirms notes are not copied from dropped commits, while the second ensures post-rewrite hooks receive the correct list of rewritten commits when commits are dropped due to empty changes or fixup sequences.

This is a well-motivated, thoroughly tested fix for a long-standing bug. The series as a whole looks ready for merging, and this patch is the core behavioral change that delivers the promised fix.
