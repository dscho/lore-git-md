This is a **CI/build system** follow-up in the ongoing discussion about macOS CI hangs in the `t5551` and `t5559` tests. The technical fix (a two-patch series increasing Apache’s `Timeout` directive and isolating a slow test) is already merged for Git 2.55, but the third patch—enabling `GIT_TEST_LONG` for GitLab CI—remains on hold while the project debates CI policy and visibility.

Patrick Steinhardt responds to Junio C Hamano’s suggestion that GitLab CI could run a *superset* of GitHub’s test coverage rather than a strict mirror. He agrees in principle but emphasizes the practical risk: if GitLab’s coverage diverges from GitHub’s, contributors may end up submitting redundant merge requests to both platforms, wasting resources. While he acknowledges GitHub CI isn’t "canonical," he notes it’s the *de facto* reference for most contributors today.

The key new development is Patrick’s proposal to improve GitLab CI visibility. He links to the official Git mirror’s pipeline page and suggests adding a GitLab CI badge to the project’s `README.md`, mirroring the existing GitHub badge. This would give maintainers a one-click way to check GitLab CI status, addressing Junio’s concern that GitLab results are harder to find. The patch is trivial (two lines of Markdown), but the change signals a willingness to treat GitLab as a first-class CI platform. Whether this satisfies Junio’s broader policy question—whether GitLab should run *additional* tests beyond GitHub’s coverage—remains unresolved, but the visibility fix is a concrete step forward.
