This is a **bugfix patch** for `git blame -b` output formatting, addressing the usability friction reported by Laszlo Ersek. René Scharfe implements Junio C Hamano’s proposed solution: stop reserving an extra hex digit for a caret marker that is never displayed when `-b` (blank boundary) is used. The patch refactors the mark-handling logic in `blame.c` to count and print boundary/ignored/unblamable marks only when they are actually shown, ensuring the abbreviated commit hash length aligns with the user’s `core.abbrev` setting.

The change is minimal and targeted, affecting only the `-b` mode of `git blame`. It introduces two helper functions, `print_marks()` and `count_marks()`, to centralize the logic for handling marks (caret, `*`, `?`), replacing the previous hardcoded column reservation. The patch also updates `find_alignment()` to dynamically calculate the maximum number of marks needed per line, avoiding the over-allocation that caused the original issue. No new configuration options or on-disk format changes are required.

The patch is well-structured and addresses the core problem directly, but René notes it lacks test coverage. The commit message is concise but could benefit from a brief explanation of the user-facing impact (e.g., "eliminates manual truncation when pasting hashes from `git blame -b` into `git rebase -i`"). The refactoring appears robust, handling edge cases like multiple marks per line, though René acknowledges he did not verify whether such cases are possible in practice.

No backward-compatibility concerns are raised in the patch itself, but the thread’s open questions remain relevant: could scripts or tools parsing `git blame -b` output break if the formatting changes? The patch does not alter the fixed-width nature of the output, only the number of columns reserved for marks, so the risk seems low. However, downstream tools expecting a specific hash length might be affected if they rely on the current over-allocation.

This patch advances the discussion toward a concrete solution, shifting the focus from whether to fix the issue to how to validate the fix. The next steps will likely involve testing and addressing any edge cases surfaced during review. For now, it looks like a clean, well-motivated fix for a real usability pain point.
