This is a follow-up discussion about the recently merged memory leak fix in `` `git history reword` ``. Kaartic Sivaraam, the original patch author, writes to clarify some lingering technical questions about when and why the leak occurs.

The thread confirms that the fix itself is correct, but the explanation in the commit message was misleading. The leak does not depend on encoding headers, as previously thought. Instead, it happens when `` `repo_get_commit_buffer()` `` returns a freshly allocated buffer rather than one cached in Git’s commit slab. Kaartic is still investigating why some commits end up in the slab while others do not, but the immediate fix—calling `` `repo_unuse_commit_buffer()` `` after use—remains valid.

Jeff King’s earlier analysis suggested that `` `free_commit_buffer()` `` might be needed for memory efficiency when processing many commits, but Kaartic argues it is unnecessary here. The `` `git history reword` `` code path does not read enough commits to make slab cache pressure a concern, and the leak only appears for commits not already in the slab. The discussion is now focused on refining the commit message to reflect this more accurate understanding.

For a busy reader, this email is mostly housekeeping: the fix is already merged, and the conversation is about documentation and follow-up investigation rather than a live bug. The only actionable item is an eventual commit message update, which is unlikely to affect behavior. If you are not working on memory management or the `` `git history` `` command, this thread is safe to skip.
