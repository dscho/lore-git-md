This is a **feature clarification and design discussion** in the `git replay --linearize` thread, following Johannes Schindelin’s identification of a critical regression in the merged v5 series. Toon Claes responds to Schindelin’s argument that the `replayed_base` mechanism is necessary for correct single-branch replay and that `--linearize` should always flatten all replayed commits into a single linear history, even when multiple branches are involved.

Toon agrees with Schindelin’s assessment that `--linearize` should produce a single linear sequence regardless of input branches, calling this "predictable behavior." He acknowledges that this design choice extends the feature’s scope beyond merge commits, reinforcing the case for the current `--linearize` option name (rather than a `--replay-merges=linearize` sub-option, as previously debated). He also notes that users who want to preserve branch independence can still replay branches separately, though this may duplicate shared commits unless they manually adjust `COMMITTER_DATE`.

The email does not propose a code fix but clarifies the intended design and defends the current CLI naming. The discussion now centers on **documenting this behavior prominently** in the man page to avoid user surprises. This aligns with Patrick Steinhardt’s earlier demand for explicit justification of CLI design choices in commit messages, though Toon does not address that process-level expectation here. The regression itself remains unaddressed; a follow-up patch will likely be needed to restore the `replayed_base` logic or implement an equivalent solution. Key technical context: `replayed_base`, `--linearize`, `pick_regular_commit()`, and the distinction between single-branch and multi-branch replay scenarios.
