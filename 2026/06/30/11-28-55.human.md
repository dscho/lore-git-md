This is Patrick Steinhardt’s response to Junio C Hamano’s **medium-weight architectural question** about the opt-in `source` parameter design in the ODB refactoring series. The patch in focus (3/6) adds a `source` field to `struct object_info_source`, enabling multi-source object resolution—a key step toward pluggable ODB backends.

Patrick clarifies that the `source` parameter is *not* "almost always NULL," contrary to appearances. Most callers use `odb_read_object_info()`, which already has the source info, but the diff only shows low-level callers (like `packed_object_info()`) where the source is often unavailable. He defends the opt-in design as a pragmatic intermediate step, arguing that tracking the source at the `packed_git` level (as Junio and Justin Tobler suggested) would be a layering violation—packfiles can exist independently of their ODB source. The current approach avoids this by letting backends populate the `source` field only when requested.

On naming, Patrick acknowledges Justin’s earlier point that `oi->sourcep` is ambiguous (it could imply a pointer to `struct odb_source` rather than `struct object_info_source`). He doesn’t propose a fix here but hints that renaming the field (e.g., to `source_infop`) might help if the struct itself were renamed to `odb_source_info`. The technical workaround—assigning `&source->base` to avoid casting—is noted but not central to the debate.

The unresolved tension remains: Junio and Justin favor centralized source tracking for simplicity, while Patrick sees the opt-in design as necessary for incremental progress toward eliminating direct `packed_object_info()` usage. No code changes are proposed yet, but the discussion is now explicitly about trade-offs between flexibility and API clarity. The series is conceptually approved ("Great") but may need another iteration to address this architectural question.
