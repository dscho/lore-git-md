This is a usability discussion about `git blame -b` output formatting and its interaction with workflows like `git rebase`. Laszlo Ersek clarifies his earlier report: the issue isn’t that `git rebase`’s parser fails to handle longer abbreviated hashes, but that the mismatch between `git blame -b`’s output (13 hex digits when `core.abbrev` is 12) and the fixed-width hashes in the `git rebase` TODO list makes manual lookups cumbersome. When copying a commit hash from `git blame -b` into an editor’s search box to locate the corresponding line in the rebase TODO list, the extra nibble causes the search to fail unless manually trimmed.

The problem is purely ergonomic. `git blame -b` reserves an extra hex digit for a caret marker that is never displayed (since boundary commits are shown as blank), resulting in hashes that are one character longer than the user’s `core.abbrev` setting. This inconsistency disrupts copy-paste workflows, forcing users to manually adjust hashes when moving between `git blame` and other Git commands. Laszlo’s use case—using `git blame` to identify which commit in a patch series introduced a line, then jumping to that commit in `git rebase`—is a common one, and the extra step of trimming the hash is easy to forget.

Junio C Hamano’s earlier suggestion that `git rebase`’s parser should accept variable-length hashes (up to 16 digits) is now moot for this specific issue, since the problem lies in the manual workflow rather than the parser itself. The discussion now centers on whether `git blame -b` should stop reserving the unused nibble for aesthetic and practical consistency. There’s no indication of a deeper bug or compatibility risk; this is a minor but persistent papercut for users who rely on `git blame -b` in rebase workflows.

No patch has been proposed yet, and the thread remains open-ended. The fix would likely be a small adjustment in `blame.c` to avoid reserving the extra nibble when `-b` is used, but the change would need to weigh the benefit of consistency against the risk of breaking scripts that might (unwisely) parse `git blame` output with fixed-width assumptions. For now, this is a low-stakes but real usability issue worth addressing for users who frequently combine `git blame -b` with `git rebase`.
