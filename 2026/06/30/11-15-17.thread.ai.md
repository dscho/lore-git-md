Subject: git blame -b output formatting and commit hash abbreviation
Series version: none (standalone report)
Originating author: Laszlo Ersek (user report)
Thread type: user experience report / usability discussion

Core problem or goal
The thread began with a report that `git blame -b` (show boundary commits as blank) reserves an extra hex digit in commit hash abbreviations for a caret marker that is never displayed, causing non-boundary commit hashes to exceed the user’s `core.abbrev` setting by one character. The discussion has since clarified that the issue is not a bug in `git rebase`’s parser but a friction in manual workflows: when using `git blame -b` to identify a commit for editing during an interactive rebase, the abbreviated hash in the blame output is one nibble longer than the hashes in the rebase TODO list, forcing manual truncation when pasting.

Current status
No patch has been proposed. The original report framed the issue as a `git blame` output formatting quirk, and Junio C Hamano’s reply reframed it as a potential robustness problem in `git rebase`’s TODO list parser. Laszlo Ersek’s follow-up clarifies that the parser is not at fault; the issue is purely a usability pain point in manual workflows. The thread remains open, with no consensus on whether to adjust `git blame -b`’s output formatting or leave it as-is for aesthetic consistency.

Key technical details
- Command: `git blame -b`
- Related command: `git rebase -i` (manual workflow interaction)
