Subject: git blame -b output formatting and commit hash abbreviation
Series version: none (standalone patch)
Originating author: Laszlo Ersek (user report)
Thread type: bug report / usability discussion leading to a patch

Core problem or goal
The thread began with a report that `git blame -b` (show boundary commits as blank) reserves an extra hex digit in commit hash abbreviations for a caret marker that is never displayed, causing non-boundary commit hashes to exceed the user’s `core.abbrev` setting by one character. This creates a usability friction in manual workflows: when using `git blame -b` to identify a commit for editing during an interactive rebase, the abbreviated hash in the blame output is one nibble longer than the hashes in the rebase TODO list, forcing manual truncation when pasting.

Current status
A patch by René Scharfe has been posted, implementing Junio C Hamano’s proposed solution: remove the extra hex digit reserved for the unused caret marker in `git blame -b` output. The patch refactors the mark-handling logic in `blame.c` to count and print boundary/ignored/unblamable marks only when they are actually shown, ensuring the abbreviated commit hash length aligns with the user’s `core.abbrev` setting. The change is minimal, affecting only the `-b` mode of `git blame` and requiring no new configuration variables or on-disk format changes. The discussion is now focused on validating the patch, with no backward-compatibility concerns raised so far.

Key technical details
- Command: `git blame -b`
- Related command: `git rebase -i` (manual workflow interaction)
- Subsystems: blame output formatting (`blame.c`)
- Config keys: `core.abbrev` (no `blame.abbrev` proposed)
- Behavior: `git blame -b` previously abbreviated non-boundary hashes to `core.abbrev + 1` hex chars to reserve space for an unused caret marker; the patch removes this reservation, aligning the output with `core.abbrev`
- Files: `blame.c` (output formatting logic)
- Symbols: new helper functions `print_marks()` and `count_marks()` introduced to centralize mark-handling logic; `find_alignment()` updated to dynamically calculate mark columns
- On-disk format: none affected
- Test coverage: none yet; René notes the patch lacks tests

Open questions and loose ends
- Are there backward-compatibility risks for scripts or tools that parse `git blame -b` output if the formatting changes? The patch does not alter the fixed-width nature of the output, but downstream tools expecting a specific hash length might be affected.
- Should test coverage be added to verify the fix and prevent regressions?
- Are there edge cases (e.g., multiple marks per line) that need validation? René did not verify whether such cases are possible in practice.
