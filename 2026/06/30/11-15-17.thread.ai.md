Subject: git blame -b output formatting and commit hash abbreviation
Series version: none (standalone report)
Originating author: Laszlo Ersek (user report)
Thread type: user experience report / bug discussion

Core problem or goal
The thread began with a report that `git blame -b` (show boundary commits as blank) reserves an extra hex digit in commit hash abbreviations for a caret marker that is never displayed, causing non-boundary commit hashes to exceed the user’s `core.abbrev` setting by one character. The discussion has since expanded to whether the issue lies in `git blame`’s output formatting or in `git rebase`’s parser, which may not handle variable-length abbreviated hashes robustly.

Current status
No patch has been proposed. The original report framed the issue as a `git blame` output formatting quirk, but Junio C Hamano’s reply reframes it as a potential robustness problem in `git rebase`’s TODO list parser, which should accept longer abbreviations (up to 16 hex digits) as long as they uniquely identify the commit. The thread remains open, with no consensus on whether to adjust `git blame`, `git rebase`, or both.
