This is a **build system** and **platform compatibility** discussion about whether Git’s `USE_NSEC` option—currently a build-time knob—should become a runtime-configurable setting instead. Jeff King (Peff) responds to Patrick Steinhardt’s proposal to treat `USE_NSEC` like `core.ignoreCase`, agreeing that a runtime flag would be more flexible than a build-time option. He acknowledges the technical challenge of auto-detecting filesystem behavior (e.g., whether nanosecond timestamps are preserved) but endorses the general idea of making the setting user-configurable. The discussion now centers on how to implement runtime control, with no concrete patch yet submitted.

The original patch added a `nanosec` Meson option to mirror Autotools’ `USE_NSEC`, but the thread has evolved into a broader debate about whether the knob should exist at all. Peff’s earlier testing showed that modern Linux filesystems reliably preserve nanosecond timestamps, undermining the historical rationale for `USE_NSEC` as a safety measure. However, interoperability risks remain when mixing `USE_NSEC` and non-`USE_NSEC` implementations (e.g., Git and JGit), which could degrade performance. Brian M. Carlson proposed flipping the default to `true` for most users, while Patrick Steinhardt argued for removing the build-time option entirely in favor of runtime configuration.

Peff’s email adds technical nuance to the runtime-configuration proposal, noting that auto-detection would require flushing the kernel’s inode cache—a non-portable and potentially disruptive operation. He suggests that a user-configurable flag (e.g., `core.useNsec`) would be a pragmatic alternative, even if it lacks auto-detection. The discussion remains open-ended, with no consensus on whether to keep the build-time knob, flip its default, or replace it with runtime control. Junio C Hamano’s earlier response complicates the analogy to `core.ignoreCase` by noting that `USE_NSEC` is optional, not mandatory for correctness, which may justify retaining a build-time option for power users. The thread is now focused on implementation trade-offs rather than the original patch’s goal of build system parity.
