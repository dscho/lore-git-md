This is a usability discussion about `git blame -b` output formatting, specifically whether Git should stop reserving an extra nibble for a boundary-caret marker when `-b` is used.

Junio C Hamano responds to Laszlo Ersek’s report about `git blame -b` showing commit hashes one nibble longer than `core.abbrev` (e.g., 13 hex chars instead of 12). Junio first questions whether the real issue is in `git rebase`’s parser, which he suggests should accept any valid abbreviated hash (up to 16 hex chars) rather than insisting on the exact length initially provided. He notes that Git already extends abbreviations when necessary to avoid ambiguity, so a parser that rejects 13 hex chars when 12 were expected is likely buggy.

Junio then acknowledges the aesthetic point: when `-b` suppresses the boundary caret, reserving an unused column is unnecessary. However, he downplays the practical impact, suggesting that unless a parser strictly requires 12 hex chars, users might not even notice the extra digit. The discussion remains open-ended, with no patch or concrete plan yet—just a recognition that the current behavior is suboptimal and a hint that the fix might belong in `git rebase` rather than `git blame`.
