This is a follow-up discussion in the ongoing thread about a memory leak fix in the `git history reword` command. Jeff King (Peff) replies to Kaartic Sivaraam’s investigation into why some commit buffers bypass Git’s slab cache, which is the root cause of the leak.

Peff suggests the most likely reason for uncached commit buffers is that the commits were loaded from the commit-graph, meaning Git never opened the object itself and thus had nothing to cache. He also notes other possibilities: the command might be formatting unparsed commits, or `save_commit_buffer` could be disabled (though he considers this less likely). His analysis refines Sivaraam’s earlier finding that the leak occurs when `repo_get_commit_buffer` returns a freshly allocated buffer, not just when re-encoding is needed.

On the question of whether to call `free_commit_buffer` in addition to `repo_unuse_commit_buffer`, Peff is pragmatic. While the current leak only affects non-slab commits, he argues that if there’s an easy opportunity to free resources associated with a commit (e.g., when the program is done with it), it’s worth doing—especially if the command might process thousands of commits. However, he acknowledges this is a minor concern and not urgent, as the leak is rare and most repos with an up-to-date commit-graph won’t have many cached entries to begin with.

The discussion remains technical and focused on diagnosing the buffer management behavior. No objections to the original fix are raised, and the thread is now clarifying implementation details rather than questioning the correctness of the patch. The main takeaway is that the commit message should be updated to reflect the refined understanding of the leak’s cause.
