This is the first patch in Toon Claes's **v4 `--linearize` feature series** for `git replay`, which is now ready for merging. This patch is a **refactoring** that simplifies the codebase by converting the `enum replay_mode` (with values `REPLAY_MODE_PICK` and `REPLAY_MODE_REVERT`) into a single boolean `reverse` flag. The change is purely internal and does not alter behavior, but it eliminates redundant enum checks and BUG() assertions, making the code more maintainable.

The patch touches only `replay.c`, replacing all instances of `enum replay_mode` with the `reverse` boolean. The logic remains identical: when `reverse` is true, commits are processed in reverse order (revert mode), and when false, they are applied as-is (pick mode). The refactoring was debated in earlier iterations (notably by Justin Tobler, who questioned whether a boolean would scale for future modes), but the consensus settled on this approach as sufficient for the current dual-mode needs. The change also prepares the codebase for the upcoming `--linearize` feature by reducing complexity in the commit-processing logic.

This patch is part of a **three-patch series** that introduces the `--linearize` option to `git replay`. The series has undergone thorough review, with all feedback incorporated, including test coverage improvements and documentation clarifications. Junio Hamano has indicated the series is ready for merging to `next`. The refactoring here is a prerequisite for the core `--linearize` implementation in patch 3/3, which will use the simplified boolean logic to handle merge commits differently.

Key technical details include the removal of the `enum replay_mode` definition, the replacement of `mode` parameters with `reverse` in functions like `create_commit()` and `pick_regular_commit()`, and the elimination of BUG() checks for invalid enum values. The patch also updates the `replay_revisions()` function to derive the `reverse` flag from the `opts->revert` option. No new functionality is introduced, but the code is now cleaner and more focused.

The series as a whole is **well-motivated and technically sound**, addressing a real need for server-side linearization of merge-heavy histories. The refactoring in this patch is a small but important step toward that goal, and the entire series has benefited from substantive reviews by Junio Hamano, Elijah Newren, Justin Tobler, and Johannes Schindelin.
