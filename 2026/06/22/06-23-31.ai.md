This is the final version of Miklos Vajna's patch series improving `git log --follow` for non-linear history, specifically addressing rename tracking across merge commits. It resolves the last administrative hurdle (test numbering conflict) and is ready for maintainer merge.

The patch implements a commit-to-path mapping using a slab (`follow_pathspec_slab`) to store which path should be followed when visiting each commit. This replaces the previous single global variable approach that failed when history diverged. The solution handles both subtree merges (where renames occur inside the merge commit) and general cases where renames happen in parent histories. Key technical details include:

- New `follow_pathspec_slab` structure tracks per-commit pathspec information
- Modified traversal logic in `log_tree_commit()` propagates pathspecs to parent commits
- Maintains Git's current single-path limitation (no support for multiple simultaneous paths)
- Includes explicit handling for fork points where pathspecs diverge
- Updates documentation to remove the outdated "does not work well on non-linear history" caveat

The implementation touches core files (`revision.c`, `log-tree.c`, `diff.c`) and adds comprehensive test coverage in `t4219-log-follow-merge.sh` with three main scenarios: subtree merge rename tracking, renames from both merge sides, and diverged paths converging in common ancestors. All substantive technical feedback from Junio Hamano has been incorporated, including edge case handling at history fork points.

This is a well-crafted bugfix that addresses a long-standing limitation in Git's rename tracking while maintaining backward compatibility. The solution is elegant in its simplicity - using existing diff machinery with per-commit state rather than attempting to expand Git's path tracking capabilities. The patch series has reached consensus and only requires final test renumbering before merging.
