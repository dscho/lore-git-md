This is the fifth patch in Harald Nordgren’s v17 series implementing `git branch --delete-merged`, and it is the core implementation of the new subcommand. The patch itself is technically sound: it adds the `--delete-merged` option to `git branch`, which safely deletes local branches whose work has already been merged into their upstream, while preserving branches that are used as upstreams for other branches (stacked-branch protection). The implementation uses the `--forked` filter (introduced in patch 1/7) and the flags-based deletion API (refactored in patches 2–4/7), and it includes all the safety mechanisms discussed in the thread: protection for checked-out branches, missing upstreams, push-equals-upstream branches, per-branch opt-out, and stacked-branch protection.

Phillip Wood’s review focuses on the stacked-branch protection logic. The current implementation keeps the entire chain of upstreams (e.g., if `b1→b2→b3` and `b1` is merged, none of the three are deleted), which is safe but may leave unneeded branches. Phillip proposes an alternative: keep only the upstreams of unmerged branches, and clear the upstream config for any merged branches in the chain. For example, if `feature-3→feature-2→feature-1` and both `feature-1` and `feature-2` are merged, `feature-1` would be deleted, `feature-2` would be kept (because it is the upstream of `feature-3`), and its upstream config would be cleared. Phillip provides a complete, compilable implementation of this logic, though he notes it has not been tested beyond the existing test suite.

The review also includes a minor style suggestion: replacing a manual loop over `strset` with `strset_for_each_entry()`. This is a straightforward cleanup and does not affect functionality.

The thread context confirms that the stacked-branch protection design was finalized as "abort-and-notify" (fail with an error if a branch is used as an upstream), but the current implementation (upstream config clearing) is broken and must be revised. Phillip’s proposal is a refinement of the abort-and-notify approach, offering a more nuanced way to handle chains of upstreams while still preserving the safety guarantee. The choice between the two approaches is now the main open question for this patch.
