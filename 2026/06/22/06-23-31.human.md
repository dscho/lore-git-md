This is the final version of a well-crafted bugfix patch that improves `git log --follow` for non-linear history. The patch addresses a long-standing limitation where `--follow` would fail to track renames through merge commits, particularly affecting subtree merges.

The solution introduces a per-commit pathspec storage system (`follow_pathspec_slab`) that remembers which path to follow for each commit, eliminating the previous reliance on a single global variable that got overwritten during traversal. This makes the walk order irrelevant and properly handles cases where renames occur on different branches before a merge.

The implementation is thorough: it touches the core revision-walking logic in `revision.c` and `log-tree.c`, adds proper memory management, and includes comprehensive test coverage in the new `t4219-log-follow-merge.sh` test file. The tests cover subtree merges, renames from both sides of a merge, and complex diamond-shaped histories with diverging renames.

Junio has already approved the technical approach after careful review of edge cases, and the only remaining issue is a simple test numbering conflict that Miklos has resolved in this v4. The patch updates documentation to remove the outdated "does not work well on non-linear history" limitation from the `log.follow` config description.

This is ready for merging and represents a meaningful improvement to a frequently-used Git feature. The solution maintains backward compatibility while fixing a real pain point for users working with subtree merges or other non-linear histories.
