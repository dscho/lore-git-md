This is the fifth patch in Harald Nordgren’s seventeen-part series adding `git branch --delete-merged`, now in its final design iteration. The patch implements the core command that safely deletes local branches whose work is already merged into their upstream, while protecting branches that are themselves upstreams for other branches (the “stacked-branch” safety mechanism).

Phillip Wood’s review here is substantive. He identifies a design tension in the stacked-branch protection logic: the current implementation keeps *every* branch in a dependency chain (e.g., `b1→b2→b3`), which is maximally safe but may leave behind branches that are no longer needed. He proposes an alternative that keeps only the immediate upstream of any unmerged branch and clears the upstream config of any merged branch whose own upstream is being deleted. The example he gives is a chain `feature-3→feature-2→feature-1` where `feature-1` and `feature-2` are merged: his version would delete `feature-1`, keep `feature-2`, and clear `feature-2`’s upstream config, while still protecting `feature-1` if it is the upstream of an unmerged `feature-4`. He includes a complete, compilable code snippet that implements this logic.

The review also contains two surface-level suggestions: using `strset_for_each_entry()` instead of a manual loop over `candidates`, and a minor style nit about variable declaration placement.

The thread context shows that the stacked-branch protection design was already finalized as “abort-and-notify” (fail with an error if a branch is used as an upstream), so Phillip’s proposal is effectively a new design option rather than a bug fix. The current implementation in the patch is therefore not yet aligned with the agreed design, and the discussion here is about whether to adopt the more nuanced approach he describes.
