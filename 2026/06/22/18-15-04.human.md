This is a **substantive review** of the test coverage in patch 4 of Tian Yuchen’s six-patch series optimizing `paint_down_to_common()` for one-sided histories. Derrick Stolee raises two procedural concerns about the placement and effectiveness of the tests, though he does not challenge their correctness.

Stolee suggests the tests would be more persuasive if they appeared *before* the code changes in the series, so they could demonstrate that the old logic already handles these edge cases (or fails to) and that the new logic preserves or improves behavior. Currently, the tests arrive after the optimization (patch 3), which risks merely enforcing the new behavior rather than validating it. This is a common review preference in Git: tests should ideally prove the *need* for a change, not just its *effect*.

He also proposes augmenting the tests with a "commits walked" counter, exposed via tracing, to empirically demonstrate the performance benefit. The current tests verify correctness across Git’s three reachability backends (full graph, half graph, no graph), but they do not measure the reduction in traversal work. A counter would let the tests show, for example, that the `infinity-both-sides` case walks 500× fewer commits after the optimization. Stolee notes that the counter’s value would vary across backends, which could itself be a useful test signal.

The review is constructive and actionable, but it does not block the patch. It is a medium-weight suggestion about test design, not a functional objection. The author (Tian Yuchen) will need to decide whether to reorder the series or add the tracing counter in a follow-up.
