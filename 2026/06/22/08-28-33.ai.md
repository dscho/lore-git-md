This is the **final safeguard patch** in Patrick Steinhardt’s 11-part v5 refactoring series for Git’s reference backend, addressing the long-standing chicken-and-egg recursion issue with "onbranch" configuration conditions. The patch adds a **recursion guard** to `get_main_ref_store()` in `refs.c` to detect and abort recursive initialization attempts, ensuring the lazy-loading design introduced in earlier patches cannot be bypassed.

The change is minimal: a static `initializing` flag is added to `get_main_ref_store()`, set to `true` before backend initialization and cleared afterward. If the function is re-entered while `initializing` is already `true`, it triggers a `BUG()` with a descriptive message. This prevents infinite recursion during ref store creation, which could previously occur when "onbranch" conditions triggered early config reads that re-entered `get_main_ref_store()`.

The patch is a **defensive measure** rather than a functional fix—it doesn’t alter behavior under normal circumstances but ensures the lazy-loading mechanism (deferring write-config parsing until the first write operation) remains robust. The recursion guard complements the architectural changes in patches 8–10/11, which refactored the files and reftable backends to avoid early config reads that could trigger recursion. This patch specifically targets the main ref store, leaving other ref stores (e.g., worktrees) to rely on the lazy-loading design alone.

The commit message is concise but clear about the motivation: the recursion issue existed for some time without detection, and this patch improves observability. The change is unlikely to be controversial, as it’s a straightforward safeguard with no performance impact or backward-compatibility concerns. However, it’s a critical piece of the series, as it ensures the lazy-loading design cannot be undermined by edge cases.

This patch completes the v5 rewrite, which abandoned the v4 `ignore_refs` workaround in favor of a root-cause fix. The series now stands as a **foundational refactoring** of how ref backends interact with configuration, with implications for future backend work (e.g., ODB-based ref stores). The recursion guard is a small but essential part of that effort, providing a safety net for the more complex changes in earlier patches.
