This is the ninth patch in Patrick Steinhardt’s 11-part **v5 refactoring series** for Git’s reference backend, which introduces a **lazy-loading design** to resolve recursive initialization issues with "onbranch" configuration. This specific patch **splits the reftable backend’s write options** into two distinct structures: one for stack configuration (e.g., hash ID, reload callbacks) and another for write-specific settings (e.g., block size, compression). The goal is to decouple stack initialization from write-config parsing, enabling dynamic write option passing and deferring configuration until the first write operation.

The patch touches 14 files, primarily in the `reftable/` directory, and introduces a new `reftable_stack_options` struct to hold stack-specific settings. Key changes include:
- **API refactoring**: Functions like `reftable_new_stack()` and `reftable_stack_new_addition()` now accept separate options for stack and write configurations.
- **Dynamic write option passing**: Write operations (e.g., `reftable_stack_add()`, `reftable_stack_compact_all()`) now explicitly pass write options, allowing per-operation configuration.
- **Test updates**: Unit tests are adjusted to accommodate the new API, with hash IDs now passed directly to writer functions.

This is a **well-motivated refactoring** that aligns with the series’ goal of deferring write-config parsing to avoid recursion. The changes are mechanical but critical for the lazy-loading design, and the patch includes thorough test coverage to verify backward compatibility. The reftable backend’s refactor is the most complex part of the series, and this patch lays the groundwork for the lazy-loading implementation in patches 10–11. Reviewers like Jeff King (Peff) and Karthik Nayak may scrutinize the dynamic write option handling for edge cases (e.g., races in concurrent writes), but the approach is technically sound.
