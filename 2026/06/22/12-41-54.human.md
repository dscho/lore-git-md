This is the fourth iteration of a feature patch series that adds a `--linearize` option to `git replay`. The series teaches `git replay` to flatten merge commits, matching the default behavior of `git rebase --no-rebase-merges`. This version (v4) makes a minor test adjustment to prepare for an upcoming `mm/test-grep-lint` change, replacing a bare `grep` with `test_grep` in the range-diff test. All other feedback from v3 has already been incorporated: the documentation now includes `--linearize` in the SYNOPSIS, clarifies its mutual exclusivity with `--revert`, and improves the option description; the code adds a clarifying comment about `last_commit` handling during merge linearization; and the test suite verifies `--linearize` with `--advance`, tests `--revert`/`--linearize` incompatibility, and uses `git range-diff` to confirm patch equivalence.

The series remains well-structured: the first two patches refactor the code (replacing `enum replay_mode` with a boolean `reverse` flag and extracting a `put_mapped_commit` helper), while the third implements the core `--linearize` logic. The author explicitly positions this as a simpler alternative to Johannes Schindelin’s earlier merge-replay work (pull.2106) and reiterates that `--linearize` is intentionally omitted from `git history` due to lack of a clear use case. Potential trivial conflicts with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series are still noted but expected to be easy to resolve.

The implementation is clean and thoroughly tested. The new option is mutually exclusive with `--revert` (enforced by a `die_for_incompatible_opt2` check), and the test coverage now includes edge cases like replaying down to the root commit. The series has addressed all prior review feedback from Junio, Elijah Newren, and Justin Tobler, and no unresolved technical objections remain. It looks ready for final review and likely inclusion in `next`.
