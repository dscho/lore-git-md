The patch applies the same deferred-configuration pattern: write-critical settings (e.g., `reftable.blockSize`, `core.logAllRefUpdates`) are parsed only during the first write operation, avoiding early config reads that could trigger recursive ref-store initialization.

The core change is the introduction of `reftable_be_write_options()`, a lazy-loading accessor that parses and caches write options (block size, compaction settings, log-all-refs) on first use. The patch refactors `struct reftable_ref_store` to replace the direct `write_options` field with a lazily initialized `write_opts_lazy_loaded` struct, mirroring the files backend’s approach. All write operations—transactions, reflog creation, compaction—now use the accessor, ensuring deferred config is applied consistently. The `should_write_log()` helper is relocated to access the new lazy-loaded `log_all_ref_updates` setting, and test coverage is expanded to verify that "onbranch"-scoped config (e.g., `core.logAllRefUpdates = always`) works without recursion.

The patch touches 146 lines in `refs/reftable-backend.c`, primarily replacing direct `write_options` accesses with calls to `reftable_be_write_options()`. Test updates in `t/t0613-reftable-write-options.sh` and `t/t1400-update-ref.sh` add regression checks for "onbranch" conditions, including a new test that confirms `reftable.blockSize` can be configured via branch-specific includes. The changes are mechanical and align with the series’ architectural goal of decoupling ref-store initialization from config parsing, but the reftable backend’s complexity (e.g., stack compaction, reflog trimming) means edge cases—like concurrent writes or partial config updates—could surface in follow-up discussion. The patch is a critical step toward unifying the files and reftable backends under the same lazy-loading design, but its correctness hinges on the assumption that deferred config parsing won’t introduce race conditions or missed updates in write-heavy workloads.
