Core problem or goal
Generalize the `reprepare()` callback in the ODB subsystem into a more flexible `prepare()` callback that can optionally discard caches. This refactoring enables `git grep` to work generically with pluggable ODB backends by decoupling cache invalidation from ODB preparation, eliminating its direct dependency on the "files" backend's `odb_source_packed_prepare()` function. The goal is to create a backend-agnostic API that supports both cache-preserving and cache-flushing preparation, addressing the current limitation where `reprepare()` conflates these operations.

Current status
First iteration (v1). The series consists of 2 patches touching 12 files, primarily in `odb/`, with changes to `builtin/grep.c`, `midx.c`, `packfile.c`, and `odb.h`/`odb.c`. The refactoring replaces the existing `reprepare()` callback with a new `prepare()` callback that accepts an `enum odb_prepare_flags` parameter (`ODB_PREPARE_FLUSH_CACHES`) to control cache invalidation. The old `reprepare()` behavior is preserved as a wrapper around the new API for backward compatibility. No prior versions exist; this is the initial submission.

Key technical details
- Files touched: `odb/` (core changes), `builtin/grep.c`, `midx.c`, `packfile.c`, `odb.h`, `odb.c`
- New/renamed symbols: `odb_prepare()` (replaces `odb_reprepare()`), `enum odb_prepare_flags` with `ODB_PREPARE_FLUSH_CACHES` flag, removal of `odb_source_packed_prepare()` from public API
- Subsystems affected: ODB layer (object database abstraction), `git grep` builtin, midx, packfile
- Behavior: No functional change intended; the refactoring is mechanical but enables future generic ODB use cases (e.g., `git grep` with pluggable backends). The flag-based API allows callers to prepare the ODB without flushing caches, addressing the limitation where `reprepare()` conflated cache invalidation with preparation.
- Downcasting (e.g., `odb_source_packed_downcast`) is now handled within backend implementations, a shift from the old API where `reprepare()` directly called backend-specific functions like `odb_source_packed_prepare()`.
- Built on recent ODB work (`ps/odb-source-packed`).

Open questions and loose ends
- **Flag-based API design**: Whether the `ODB_PREPARE_FLUSH_CACHES` flag is sufficiently future-proof or could lead to ambiguity if additional flags are needed later. Toon Claes raised concerns about inconsistent flag usage in the `packed` backend (e.g., omitting the flag in `find_pack_entry()` where the old code flushed caches, and adding it in `read_object_info()` where it previously called `odb_source_reprepare()` directly). This could indicate a behavioral regression or unintended divergence from the original semantics.
