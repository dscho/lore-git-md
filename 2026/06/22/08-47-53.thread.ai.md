Core problem or goal
Generalize the `reprepare()` callback in the ODB subsystem into a more flexible `prepare()` callback that can optionally discard caches. This refactoring enables `git grep` to work generically with pluggable ODB backends by decoupling cache invalidation from ODB preparation, eliminating its direct dependency on the "files" backend's `odb_source_packed_prepare()` function. The goal is to create a backend-agnostic API that supports both cache-preserving and cache-flushing preparation, addressing the current limitation where `reprepare()` conflates these operations.

Current status
First iteration (v1). The series consists of 2 patches touching 12 files, primarily in `odb/`, with changes to `builtin/grep.c`, `midx.c`, `packfile.c`, and `odb.h`/`odb.c`. The refactoring replaces the existing `reprepare()` callback with a new `prepare()` callback that accepts an `enum odb_prepare_flags` parameter (`ODB_PREPARE_FLUSH_CACHES`) to control cache invalidation. The old `reprepare()` behavior is preserved as a wrapper around the new API for backward compatibility, **as confirmed by Patrick Steinhardt in response to Toon Claes' review**. No prior versions exist; this is the initial submission.

Key technical details
- Files touched: `odb/` (core changes), `builtin/grep.c`, `midx.c`, `packfile.c`, `odb.h`, `odb.c`
- New/renamed symbols: `odb_prepare()` (replaces `odb_reprepare()`), `enum odb_prepare_flags` with `ODB_PREPARE_FLUSH_CACHES` flag, removal of `odb_source_packed_prepare()` from public API
- Subsystems affected: ODB layer (object database abstraction), `git grep` builtin, midx, packfile
- Behavior: No functional change intended; the refactoring is mechanical but enables future generic ODB use cases (e.g., `git grep` with pluggable backends). The flag-based API allows callers to prepare the ODB without flushing caches, addressing the limitation where `reprepare()` conflated cache invalidation with preparation.
- Downcasting (e.g., `odb_source_packed_downcast`) is now handled within backend implementations, a shift from the old API where `reprepare()` directly called backend-specific functions like `odb_source_packed_prepare()`. **Patrick Steinhardt confirmed this is intentional**, though he acknowledged the commit message could better document the rationale.
- **Flag semantics clarified**: The `ODB_PREPARE_FLUSH_CACHES` flag was *not* omitted in `find_pack_entry()` because the old code called the non-flushing `odb_source_packed_prepare()`, preserving existing behavior. The change in `read_object_info()` is correct because it replaces a direct call to `odb_source_reprepare()` (which *did* flush caches) with the flagged variant.
- **Backward compatibility**: The `odb_reprepare()` wrapper is retained to minimize churn and preserve the existing API surface, as agreed between Patrick Steinhardt and Toon Claes.

Open questions and loose ends
- **Commit message documentation**: While Patrick confirmed the downcasting shift is intentional, he expressed uncertainty about how to document it in the commit message. This leaves the design rationale undocumented, which could confuse future reviewers.
- **Testing**: No discussion yet of whether the changes have been tested for edge cases (e.g., cache consistency across multiple `prepare()` calls with different flags, or interactions with pluggable backends). The flag semantics clarification reduces the risk of behavioral regressions but does not address broader testing coverage.
- **Future-proofing**: The `ODB_PREPARE_FLUSH_CACHES` flag is the only member of `enum odb_prepare_flags`; whether this design will scale if additional flags are needed remains unaddressed.
