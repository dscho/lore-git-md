This is the latest reply in Patrick Steinhardt’s 10-part refactoring series, where he responds to Jeff King’s (Peff) substantive critique of the recursive initialization issue in `get_main_ref_store()`. Patrick acknowledges Peff’s architectural concerns and agrees that the current workaround—selectively excluding "onbranch" config conditions—is not a true fix. Instead, he proposes a more fundamental redesign: lazy-loading all write-related configuration (like `core.logAllRefUpdates`) on the first write, rather than during ref backend initialization.

The key insight is that most config values parsed during initialization are only relevant for writes, not reads. For the "files" backend, this change should be straightforward, but the "reftable" backend will require significant refactoring to separate stack construction (which needs hash ID and callbacks) from write operations (which need log settings, shared permissions, etc.). Patrick frames this as a design flaw in the reftable backend’s current architecture and commits to iterating on the solution.

This reply marks a pivot in the series’ direction. While the v4 patches (not yet posted) will likely still include the `ignore_refs` flag as a stopgap, Patrick’s long-term plan now aligns with Peff’s suggestion to minimize early config loading. The discussion has shifted from a narrow recursion fix to a broader architectural question about how ref backends should interact with Git’s config system. This is a well-motivated change, but it may delay the series’ completion, as the reftable backend refactoring could be complex. The outcome will be worth watching for anyone interested in Git’s ref storage or config parsing subsystems.
