Thread identity
Subject: [RFC PATCH] clone: add --only/--except for sparse-checkout paths
Series version: RFC (not yet a patch series)
Originating author: Pushkar Singh
Thread type: feature proposal (RFC)

Core problem or goal
Allow users to specify sparse-checkout inclusion/exclusion paths directly during `git clone`, eliminating the need for a separate `git sparse-checkout set` step afterward. Targets monorepo workflows where developers only need a subset of the repository. The feature is positioned as a convenience layer over the existing `git sparse-checkout set` workflow, not as a replacement for or modification of the underlying sparse-checkout machinery.

Current status
Proposal stage; no implementation yet. Author has restated the goal, clarified the design intent (CLI convenience over file-based patterns), and deferred to domain experts on performance implications. Initial feedback from Jeff King (Peff) suggested an alternative design (file-based patterns) and raised interface/ergonomics questions. No further engagement from other participants, including cc’d sparse-checkout domain experts (Derrick Stolee, Elijah Newren).

Key technical details
- Files touched: `builtin/clone.c` (option parsing, integration with existing sparse-checkout logic)
- New CLI options (proposed): `--only=<pathspecs>` (inclusion), `--except=<pathspecs>` (exclusion)
- Alternative design (Peff): allow providing a patterns file (e.g., `.git/info/sparse-checkout`) at clone time, reusing existing sparse-checkout machinery without new flags
- Reuses existing sparse-checkout machinery; does not modify or replace it
- Scope limited to `git clone`; no mention of affecting `git fetch` or `git pull`
- Proposed interface styles: comma-separated values (`--only=README.md,frontend`) or repeated options (`--only=frontend --only=tests`); author prefers comma-separated form
- Performance note: feature would not enable partial clones of specific paths due to server-side limitations (most servers disable path-based filters). Primary value is ergonomic, not performance-related; author has not explored optimizing object fetching based on selected paths and defers to domain experts on feasibility.

Open questions and loose ends
- Interface design: CLI flags (author’s proposal) vs. file-based patterns (Peff’s alternative); community preference unknown. Author’s clarification emphasizes the feature’s role as a convenience layer for CLI users, not a fundamental change.
- Usefulness: whether the feature addresses a real pain point for enough users. No new evidence presented; thread still lacks engagement from sparse-checkout domain experts.
- Potential concerns: edge cases in pathspec parsing, interaction with existing `--sparse` flag, backwards compatibility, and whether the ergonomic benefits justify the complexity.
- Implementation details: how to cleanly integrate with existing sparse-checkout initialization logic.
- Prospects: whether the community considers the feature worth pursuing. Author’s ping and Peff’s feedback have not yet attracted substantive engagement from key stakeholders (e.g., Derrick Stolee, Elijah Newren).
- Performance implications: whether selected paths could be used earlier in the clone process to optimize object fetching (author defers to domain experts).

Participant positions
- **Pushkar Singh** (author): Proposes `--only`/`--except` CLI options for sparse-checkout paths during clone; prefers comma-separated values for pathspecs. Positions the feature as a convenience layer over `git sparse-checkout set`, targeting users who prefer CLI commands over manual file editing. Does not see the feature as a replacement for or modification of the underlying sparse-checkout machinery. Primary goal is ergonomic, not performance-related.
- **Jeff King (Peff)**: Suggests file-based patterns (e.g., `.git/info/sparse-checkout`) as a simpler alternative to new CLI options; questions whether the feature’s ergonomic benefits justify the complexity. Notes that path-based partial clones are impractical due to server-side limitations. Cc’s Derrick Stolee for domain expertise but does not endorse either design.
