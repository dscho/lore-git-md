Subject: [RFC PATCH] clone: add --only/--except for sparse-checkout paths
Series version: RFC (not yet a patch series)
Originating author: Pushkar Singh
Thread type: feature proposal (RFC)

Core problem or goal
Allow users to specify sparse-checkout inclusion/exclusion paths directly during `git clone`, eliminating the need for a separate `git sparse-checkout set` step afterward. Targets monorepo workflows where developers only need a subset of the repository.

Current status
Proposal stage; no implementation yet. Author has restated the goal and received initial feedback from Jeff King (Peff), who suggested an alternative design (file-based patterns) and raised questions about interface and ergonomics. No further engagement from other participants yet.

Key technical details
- Files touched: `builtin/clone.c` (option parsing, integration with existing sparse-checkout logic)
- New CLI options (proposed): `--only=<pathspecs>` (inclusion), `--except=<pathspecs>` (exclusion)
- Alternative design (Peff): allow providing a patterns file (e.g., `.git/info/sparse-checkout`) at clone time, reusing existing sparse-checkout machinery without new flags
- Reuses existing sparse-checkout machinery; does not modify or replace it
- Scope limited to `git clone`; no mention of affecting `git fetch` or `git pull`
- Proposed interface styles: comma-separated values (`--only=README.md,frontend`) or repeated options (`--only=frontend --only=tests`); author prefers comma-separated form
- Performance note: feature would not enable partial clones of specific paths due to server-side limitations (most servers disable path-based filters)

Open questions and loose ends
- Interface design: CLI flags (author’s proposal) vs. file-based patterns (Peff’s alternative); community preference unknown
- Usefulness: whether the feature addresses a real pain point for enough users
- Potential concerns: edge cases in pathspec parsing, interaction with existing `--sparse` flag, backwards compatibility
- Implementation details: how to cleanly integrate with existing sparse-checkout initialization logic
- Prospects: whether the community considers the feature worth pursuing; author’s ping and Peff’s feedback have not yet attracted engagement from sparse-checkout domain experts (e.g., Derrick Stolee, Elijah Newren)
- Ergonomic vs. performance trade-offs: feature’s primary value would be ergonomic, not performance-related

Participant positions
- **Pushkar Singh** (author): Proposes `--only`/`--except` CLI options for sparse-checkout paths during clone; prefers comma-separated values for pathspecs.
- **Jeff King (Peff)**: Suggests file-based patterns (e.g., `.git/info/sparse-checkout`) as a simpler alternative to new CLI options; questions whether the feature’s ergonomic benefits justify the complexity. Notes that path-based partial clones are impractical due to server-side limitations. Cc’s Derrick Stolee for domain expertise but does not endorse either design.

Related work
- Existing sparse-checkout feature (used as the underlying mechanism)
- Monorepo workflows and sparse-index optimizations (Derrick Stolee, Elijah Newren)
- Sparse-checkout patterns file (`.git/info/sparse-checkout`) as an existing interface for defining inclusion/exclusion rules
