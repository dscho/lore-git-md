This is the **stacked-branch protection design resolution** in Harald Nordgren’s `git branch --delete-merged` series, now in its final form. Phillip Wood formally endorses the **abort-and-notify** approach (rather than retargeting) as the default behavior for handling dependent branches (e.g., `feature2` stacking on `feature1`). The discussion clarifies the implementation strategy and resolves the last major design ambiguity before the v17 release.

The email focuses on the mechanics of **preserving upstream relationships** when deleting merged branches. Phillip proposes a single-pass algorithm that:
1. Iterates through all branches.
2. For each branch, checks if its upstream is slated for deletion.
3. If so, removes the upstream branch from the deletion set and repeats the check for the upstream’s upstream (to handle chains like `b1→b2→b3`).
4. For merged branches that are kept only because they are upstreams, clears their upstream configuration (e.g., `branch.b2.merge = ""`) and warns the user.

This approach avoids the complexity of retargeting (e.g., updating `feature2@{u}` to `origin/master`) while still protecting dependent branches from becoming stale. The key insight is that **clearing the upstream of merged branches is safe**—users are unlikely to rebase or inspect logs on merged branches, so the loss of `@{u}` is not disruptive. The algorithm is efficient (single pass) and handles recursion naturally by walking the upstream chain.

Phillip’s endorsement of this design **closes the last major debate** in the series. Junio C Hamano had previously expressed skepticism about retargeting, and this email aligns the implementation with his preference for simplicity. The v17 series will now:
- **Abort and notify** when a branch is used as an upstream (e.g., "Cannot delete 'feature1' because 'feature2' depends on it").
- **Clear the upstream** of merged branches that are preserved only because they are upstreams of other branches.
- **Warn the user** when upstream configurations are cleared.

The patch is **well-motivated and technically sound**. The design prioritizes safety (no stale rebase commits) and backward compatibility (no silent retargeting) while minimizing implementation complexity. The test suite already covers stacked-branch protection, and the upcoming v17 will add a test case for the warning behavior. This is a **ready-to-merge** feature that addresses a real workflow pain point—automated branch cleanup without breaking stacked branches.
