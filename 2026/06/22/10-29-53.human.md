This is a **CI/platform-compatibility bugfix** in the ongoing macOS CI hang investigation. Patrick Steinhardt identifies the root cause of the `curl 18 transfer closed with outstanding read data remaining` errors: **Apache’s default timeout (300 seconds) is being hit** when `git-http-backend` takes too long to advertise 100,000 loose refs. The fix is straightforward—**increase Apache’s `Timeout` directive** in `t/lib-httpd/apache.conf`—but the implications are broader.

The discovery explains why the failures shifted from hangs to mid-transfer aborts: the test environment’s Apache server is now actively killing the connection when the response takes too long. This affects **both macOS and Linux CI**, confirming the issue is not platform-specific. Patrick’s local reproduction (with `Timeout 1`) shows the same `curl 18` error, and Apache’s logs explicitly report CGI timeouts. The keepalive mechanisms in Git (TCP-level and sideband) don’t mitigate this because the timeout occurs at the HTTP server layer, not the transport or application layer.

This patch is **well-motivated and technically sound**, but it’s not yet proposed as a formal patch—it’s a diagnostic finding. The next step will likely be a patch to adjust the timeout, but the thread’s focus remains on **whether this fully resolves the underlying HTTP/2 flow-control stalls** or merely masks them. Junio and Peff’s earlier skepticism about the deadlock risk still applies, so expect further discussion before any fix lands. For now, this is the clearest explanation of the `curl 18` errors and a promising path forward.
