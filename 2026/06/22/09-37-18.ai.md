This is the implementation follow-up to Phillip Wood’s proposal to clear upstream configuration for merged branches that cannot be deleted due to stacked dependencies. Harald Nordgren reports that the upstream-clearing approach has now been implemented in **v17 of the `git branch --delete-merged` series**, marking the final design resolution for stacked-branch protection.

The change replaces the earlier abort-and-notify mechanism with a simpler, non-recursive strategy: when a merged branch is used as an upstream for an unmerged branch, its upstream configuration (`branch.<name>.remote` and `branch.<name>.merge`) is cleared rather than deleted. This avoids stale references without requiring complex retargeting logic, handles edge cases like self-referential upstreams (e.g., `b3→b3`) and dependency chains (e.g., `b1→b2→b3`) uniformly, and maintains backward compatibility. The implementation is paired with a warning message (e.g., "Cleared upstream of 'feature1' because 'feature2' depends on it") and is reflected in the `--dry-run` preview output.

With this update, the series is now **feature-complete** and ready for final review. All planned safety mechanisms—per-branch opt-out (`branch.<name>.deleteMerged=false`), `--dry-run` preview, and stacked-branch protection via upstream clearing—are implemented, and the test suite has been expanded to cover the new behavior. The only remaining work is likely minor polish (e.g., test cases for upstream-clearing messages) before the series can graduate to `next`. The design trade-off (simplicity over recursive retargeting) aligns with Phillip Wood’s feedback and Junio C Hamano’s lack of objection, suggesting broad consensus.
