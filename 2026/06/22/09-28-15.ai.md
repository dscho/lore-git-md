This is the **stacked-branch protection follow-up** in Harald Nordgren’s `git branch --delete-merged` series, now at v17. Phillip Wood revisits his earlier position and proposes an even simpler alternative to the abort-and-notify approach: **clearing the upstream configuration of merged branches that cannot be deleted because they are upstreams of unmerged branches**, instead of either aborting or attempting to reassign the upstream.

The new suggestion is a pragmatic middle ground that avoids the complexity of recursive retargeting while still preventing stale upstream references. It would require minimal code changes (clearing `branch.<name>.remote` and `branch.<name>.merge` for affected branches) and maintains backward compatibility. This approach sidesteps edge cases like self-referential upstreams (e.g., `b3→b3`) and chains of dependencies (e.g., `b1→b2→b3`) entirely, as it does not traverse or modify the dependency graph.

The proposal is framed as a question ("Is that easier than reassigning the upstream?") rather than a firm recommendation, leaving room for Harald to weigh implementation effort against user experience. If adopted, it would likely be paired with a warning message (e.g., "Cleared upstream of 'feature1' because it is used by 'feature2'") to explain the change. This would complement the existing `--dry-run` preview (patch 7/7) by allowing users to anticipate which branches would have their upstreams cleared.

The thread remains focused on the stacked-branch protection design, with all other aspects of the series (per-branch opt-out, `--forked` filter, flags-based API, and `--dry-run`) already resolved. The next steps would involve implementing the upstream-clearing logic, updating tests to verify the new behavior, and documenting the change in the commit message and man page.
