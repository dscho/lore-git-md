This is a substantive review from Kristofer Karlsson of the second patch in Pablo Sabater’s v6 series, which introduces abstraction functions for `git log --graph` lookahead. Kristofer identifies two fundamental problems with the current peek-based design: (1) the pending commit queue may not yet contain all relevant entries, and (2) commits in the queue haven’t been simplified, so their parent lists are still raw, causing the graph code to miss visual-root candidates when pathspec filters remove TREESAME parents. These issues are responsible for the three `test_expect_failure` cases in `t4218-log-graph-indentation.sh`.

Instead of peeking, Kristofer proposes a simpler alternative: maintain a two-slot lookahead buffer inside `struct git_graph` and populate it by calling `get_revision_internal()`. This approach fixes the test failures and removes the need for the new `revision_peek_next_commit()` and `revision_has_commits_after()` functions entirely. He notes one subtlety—`get_revision_internal()` marks commits as `SHOWN`, which would make `graph_is_interesting()` ignore them, so the function needs a small tweak to treat lookahead commits as interesting regardless of their `SHOWN` flag.

The proposal is well-motivated and directly addresses the architectural fragility that the abstraction layer was meant to solve. If adopted, it would simplify the series by eliminating the abstraction patch and replacing it with a more robust lookahead mechanism inside `graph.c`. The change looks technically sound and aligns with the thread’s goal of insulating the graph code from `revision.c` internals.
