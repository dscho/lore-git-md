This is a **substantive review** from Kristofer Karlsson that proposes a **fundamental redesign** of Pablo Sabater’s v6 patch 2/3 (the abstraction layer for `git log --graph` lookahead).

Kristofer identifies two critical flaws in the current peek-based approach. First, the pending commit queue (`revs->topo_queue`) may not contain all relevant commits yet, because processing one commit can affect others (e.g., parent rewriting or simplification). Second, commits in the queue have not yet been through `simplify_commit()`, so their parent lists are still raw. This means `graph_is_visual_root_candidate()`—which checks for `parents == NULL`—will miss cases where a TREESAME parent is later removed by simplification, causing the three `test_expect_failure` cases in `t4218` to fail.

Instead of peeking at the queue, Kristofer proposes a **lookahead buffer** inside `struct git_graph`. The graph code would call `get_revision_internal()` to populate a two-slot buffer (`lookahead[2]`) before processing each commit. This ensures the commits are fully simplified and their parent lists are final. He prototyped the change locally and reports that all three failing test cases now pass, though he had to tweak commit timestamps to make the output fully deterministic.

The redesign removes the need for the two new functions (`revision_peek_next_commit()` and `revision_has_commits_after()`) entirely, simplifying the interface between `graph.c` and `revision.c`. A small tweak to `graph_is_interesting()` is required to treat commits in the lookahead buffer as "interesting" regardless of their `SHOWN` flag, since `get_revision_internal()` marks them as `SHOWN` before the graph code processes them.

This is a **major architectural shift**—from a peek-based abstraction to a push-based lookahead buffer—and it directly addresses the core fragility that the v6 series was trying to solve. The proposal is well-motivated, technically sound, and backed by local testing. If adopted, it would likely require a v7 resend of the entire series.
