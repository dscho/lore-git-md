This is Patrick Steinhardt's **substantive review** of the final patch in Toon Claes's `git replay --linearize` series (v4 3/3). The review engages deeply with the patch's design and interface, raising a **significant architectural question** about the `--linearize` option's long-term extensibility.

Patrick observes that `git rebase` supports **three distinct modes** for handling merges:
1. `--no-rebase-merges` (the default, equivalent to `--linearize` in this patch)
2. `--rebase-merges` (replays merges but skips cousins via `--ancestry-path`)
3. `--rebase-merges=rebase-cousins` (replays all merges, including cousins)

The current `--linearize` implementation hardcodes only the first mode, which Patrick suggests may be **too restrictive**. He questions whether the interface should mirror `git rebase`'s full flexibility now, to avoid painting the code into a corner if additional modes are needed later. This echoes his earlier concern about Patch 1/3's boolean `reverse` flag (which he argued obscures callsite meaning and limits future extensibility).

The review also includes two **surface-level nits**:
- The BUG() message in `pick_regular_commit()` should use lowercase ("linearizing" instead of "Linearizing").
- A hint about the `--linearize` option could be added to the merge-commit error message, though Patrick acknowledges this might be awkward since the function isn’t guaranteed to be called from `git replay`.

Patrick’s tone is constructive, and he explicitly approves the core logic ("Makes sense"). However, the **interface design question** he raises is non-trivial: it challenges whether the patch’s narrow scope is sufficient for `git replay`’s stated goal of server-side `git rebase` emulation. This could spark a broader discussion about whether the series should be expanded to support all `git rebase` modes before merging, or if `--linearize` alone is a reasonable MVP.

Key technical symbols referenced:
- **CLI options**: `--linearize`, `--rebase-merges`, `--rebase-merges=rebase-cousins`, `--ancestry-path`
- **Functions**: `pick_regular_commit()`, `replay_revisions()`
- **Struct field**: `opts->linearize`
- **Error handling**: BUG() macro, die() messages

The review does not block the patch outright but **reopens the architectural debate** from Patch 1/3, suggesting the series may need another iteration to address extensibility concerns. Junio’s earlier "Will merge to 'next'" may be delayed pending resolution.
