This is a **v5 refactoring series** from Patrick Steinhardt that overhauls Git’s reference backend initialization to fix long-standing issues with "onbranch" configuration conditions. The series now implements a **lazy-loading design** for ref-store configuration, eliminating recursive initialization problems and ensuring consistent handling of branch-scoped settings like `core.logAllRefUpdates`.

The core problem was that ref backends were reading configuration too early—during store initialization—which could trigger recursive calls to `get_main_ref_store()` when "onbranch" conditions were present. This led to memory leaks, inconsistent config application, and performance regressions. The v5 solution defers all non-critical config parsing until the first write operation, splitting backend initialization into "read-only" and "write-ready" phases. This redesign addresses Jeff King’s architectural concerns about config cache inconsistencies and user-facing regressions (e.g., `git commit` ignoring `onbranch`-scoped settings).

Key changes span 11 patches:
- Patches 1–6 are carryovers from v4, cleaning up repository setup code, fixing memory leaks in `chdir_notify`, and moving `core.logAllRefUpdates` parsing into ref stores.
- Patches 7–10 implement the lazy-loading design: the "files" backend (patch 8) and "reftable" backend (patch 10) now parse write-related config only when needed. The reftable backend required a major refactor (patch 9) to split write options from stack construction.
- Patch 11 adds a safeguard against future recursion by tracking whether a ref store is already being initialized.

The series touches critical subsystems (`refs/`, `repository.c`, `setup.c`, `reftable/`) and introduces new backend APIs for deferred config parsing. Test coverage verifies that write operations respect deferred config, including edge cases like `onbranch`-scoped settings. While the reftable backend refactor is complex, the approach is well-motivated and aligns with Peff’s earlier endorsement of lazy-loading as the correct fix.

This is a **foundational change** for Git’s ref storage layer, with implications for future backend work (e.g., ODB-based ref stores). The series looks technically sound and addresses a real architectural problem, though the reftable backend changes may warrant extra scrutiny from reviewers familiar with that code. For anyone tracking Git’s ref backend evolution, this is a significant step forward.
