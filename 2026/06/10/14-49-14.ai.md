This is the third and final patch in the v2 series introducing a `--linearize` option to `git replay`. It implements the core functionality: when `--linearize` is specified, `git replay` flattens the commit topology by dropping merge commits and cherry-picking only the regular (single-parent) commits, matching the default behavior of `git rebase --no-rebase-merges`.

The patch adds the new CLI option (`--linearize`) to `builtin/replay.c`, introduces a corresponding boolean flag (`linearize`) in the `replay_revisions_options` struct, and modifies the replay machinery in `replay.c` to skip merge commits when the flag is set. The `pick_regular_commit` helper is updated to accept an optional `replayed_base` parameter, allowing it to build the linearized history incrementally. The implementation explicitly prevents `--linearize` from being used with `--revert` (they are mutually exclusive) and includes a BUG check to guard against unsupported reverse-linearize combinations.

Test coverage in `t3650-replay-basics.sh` verifies that merge commits are rejected by default, that `--linearize` produces the expected linearized history, and that the option works correctly when replaying all the way to the root commit. The patch also updates the man page (`Documentation/git-replay.adoc`) to document the new option.

This patch is well-structured and directly addresses the feedback from Junio’s v1 review: the merge-commit detection logic is now explicitly spelled out in an if/else block with a clarifying comment, and the test suite has been expanded to cover the root-commit edge case. The implementation is clean, the commit message is clear, and the feature aligns with the stated goal of enabling server-side rebase functionality. No open questions remain in this patch; the only loose end noted in the cover letter (whether `--linearize` should also be added to `git history`) is outside its scope.
