This is part 8/10 of Patrick Steinhardt's v4 series adding a `git history drop` subcommand, which builds on the experimental `git history` command. The patch focuses on the reset machinery that underlies the new drop functionality.

The change modifies `reset_working_tree()` to stop assuming the index is clean before reset operations. Previously, the function optimized by skipping cache tree updates since callers (rebase/sequencer) always started with a clean index. However, the new `git history drop` command may operate on a dirty index, so this assumption no longer holds.

The patch makes the cache tree update conditional on doing a hard reset, where we know the index will be clean afterward. While the original optimization provided negligible performance benefit, the commit maintains it for hard resets while fixing the correctness issue for other cases.

This is a straightforward change that removes an invalid assumption while preserving existing behavior where safe. It's part of the broader effort to make the reset API more robust for new callers like the history command. The patch touches only reset.c with minimal changes (5 insertions, 3 deletions) and maintains compatibility with existing callers.
