Patrick Steinhardt’s ten-part refactoring series to modernize Git’s reference backend infrastructure has taken a significant turn with Jeff King’s (Peff) latest review. The thread, now in its fourth iteration, centers on eliminating recursive initialization in `get_main_ref_store()`—a long-standing issue where "onbranch" config includes trigger ref store access during ref backend setup. While earlier versions focused on targeted fixes, Peff’s critique elevates the discussion to a broader architectural question: how should ref backends interact with Git’s config system?

Peff’s review zeroes in on the core tension between early config reads (necessary for backend initialization) and the recursive loops they create. He distinguishes between *repo metadata* (like `extensions.refStorage`, which must be read early and ignores includes) and *user-facing config* (like `core.logAllRefUpdates`, which should respect includes). The current design, he argues, creates a fragile dependency where config keys needed for ref backend initialization are read through the general config subsystem, which can trigger recursive ref store access via `includeif.onbranch`. His example—a regression where `git commit` fails to respect an `onbranch`-scoped `core.logAllRefUpdates` setting—demonstrates the real-world impact of this issue. Peff’s concerns extend to potential caching inconsistencies, where early config reads might skip includes that later reads would apply, leading to unpredictable behavior.

The review has already reshaped the series. Patrick’s v4 redesign introduces an `ignore_refs` flag in `struct config_options` to selectively block "onbranch" includes during ref store initialization, a direct response to Peff’s feedback. However, Peff’s critique suggests this may not be enough: he proposes a more principled approach where ref backends initialize with minimal config (just enough for reads) and defer additional config loading to a non-caching path like `repo_config()`. This would require a deeper refactoring of how backends interact with the config system, but it could resolve the recursion issue without the fragility of selective include blocking.

Key participants are aligned on the problem but differ on the solution. Karthik Nayak and Justin Tobler have reviewed earlier versions favorably, focusing on memory leaks, `chdir_notify` lifecycle fixes, and initialization logic. Junio C Hamano has not objected to the current design, but Peff’s review—backed by bisecting the regression and constructing test cases—carries significant weight. The thread’s outcome will likely influence how Git handles config parsing for ref backends long-term, particularly as new backends (like reftable) continue to evolve. For now, the open questions revolve around whether the `ignore_refs` flag is a sufficient fix or just a stepping stone toward a more comprehensive redesign.
