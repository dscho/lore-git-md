This is a performance optimization discussion in response to a patch that extends Git's memoized commit traversal to more commands. The thread continues from a previous patch series that made the `--contains` traversal robust against cycles.

Karthik Nayak raises a question about simplifying the logic in the commit_contains() function. He suggests potentially removing the `with_commit_tag_algo` flag entirely and just using generation number availability as the sole condition for choosing the memoized algorithm. This would make the code simpler by eliminating a special case for `git tag --contains`.

The discussion builds on the earlier work that showed dramatic performance improvements (104s -> 467ms) when using memoized traversal for commands like `git branch --contains`. Karthik's question probes whether the optimization's conditions could be made more straightforward while maintaining the same behavior.

This appears to be a thoughtful refinement suggestion from an experienced contributor (Karthik has worked extensively on ref backends and performance optimizations). The question focuses on code clarity rather than functionality, as the core performance benefits have already been demonstrated in the previous patches. The change would affect how Git chooses between memoized and non-memoized traversal paths when processing `--contains` queries across various commands.
