Thread identity: RFC patch series proposing behavior changes for `git history reword` (experimental command in Patrick Steinhardt's `git history` feature). Author Pablo Sabater is new to this subsystem. Current version is v1 with two patches.

Core problem/goal:
1. Modify `git history reword` to abort when new commit message matches original (unlike `git commit --amend`/`git rebase -i`), citing expensive branch updates and in-memory-only operation constraints. Implementation needs refinement to avoid impacting `git history fixup --reedit-message` which shares the same `commit_tree_ext()` function.
2. Add success feedback after reword operation showing original/rewritten commit hashes, with design discussion now expanded to consider consistency across all `history` subcommands following Junio's intervention.

Current status: Both patches build on Patrick Steinhardt's v11 `git history` series (Jan 2026). Patch 1's technical implementation has a proposed solution (status code differentiation) that addresses Patrick's scoping concerns. Patch 2's design discussion has shifted from philosophical debates to subsystem-level design considerations regarding output consistency across all `history` subcommands.

Key technical details:
- Changes in builtin/history.c and tests in t/t3451-history-reword.sh
- `repo_find_unique_abbrev()` used for hash feedback
- Shared `commit_tree_ext()` function would now return status code (1) for identical messages
  - `cmd_history_reword` treats this as abort condition
  - `cmd_history_fixup` ignores this status
- Feedback would show original and rewritten commit hashes (invalidated original being key motivation)
- Now requires analysis of output patterns across `history split`, `drop`, `fixup` subcommands

Open questions:
- Is no-op abort behavior justified given command constraints? (patch 1)
  - Junio's review strongly challenges this premise, citing timestamp/identity updates as valuable side effects
  - Suggests `--force` flag might be better default inversion
  - Raises consistency concerns with `amend`/`rebase` behavior
- Should feedback be implemented consistently across all `history` subcommands? (patch 2)
  - Junio's comment makes this the central design consideration
  - Requires analysis of existing subcommand output patterns
- Should `git history` align with or diverge from established Git commit rewriting patterns?
- Does `rebase --update-refs` already provide equivalent branch-updating capabilities?
