Thread identity: RFC patch series proposing behavior changes for `git history reword` (experimental command in Patrick Steinhardt's `git history` feature). Author Pablo Sabater is new to this subsystem. Current version is v1 with two patches.

Core problem/goal:
1. Modify `git history reword` to abort when new commit message matches original (unlike `git commit --amend`/`git rebase -i`), with ongoing debate about whether this behavior should be the default or require `--force`.
2. Establish consistent feedback patterns across all `git history` subcommands (reword, fixup, split, drop), balancing Git's "rule of silence" against porcelain command usability needs.

Current status: Both patches build on Patrick Steinhardt's v11 `git history` series. Patch 1's technical implementation (status code differentiation in `commit_tree_ext()`) remains pending Patrick's review. Patch 2's design discussion has expanded from reword-specific feedback to subsystem-wide output conventions following Junio's intervention.

Key technical details:
- Changes in builtin/history.c and tests in t/t3451-history-reword.sh
- Shared `commit_tree_ext()` function would return status code (1) for identical messages
  - `cmd_history_reword` treats as abort condition
  - `cmd_history_fixup` ignores status
- Feedback proposal now covers all subcommands:
  - reword/fixup: show old/new commit hashes
  - split: show new commit hashes
  - drop: potentially silent
- Uses `repo_find_unique_abbrev()` for hash display
- Design must consider relationship with `git commit --amend`, `git rebase -i`, and `git rebase --update-refs`

Open questions:
- Should no-op abort be default or require `--force`? (Junio favors latter)
- Is hash feedback valuable enough to justify breaking Git's rule of silence?
- Should feedback be:
  - Always shown (Pablo's preference)
  - Under `--verbose` (Patrick's earlier suggestion)
  - Subcommand-specific?
- How does `history`'s porcelain nature justify different standards from plumbing?
- Does `rebase --update-refs` make some `history` functionality redundant?

Participant positions:
