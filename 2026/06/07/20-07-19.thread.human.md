This thread is about refining the behavior of the experimental `git history reword` and `git history fixup` commands, which are part of Patrick Steinhardt’s broader `git history` feature. The discussion has evolved from abstract design principles to concrete usability concerns after Dominique Martinet tested the commands and uncovered real-world failure modes.

The core issue is that both commands can silently succeed (exit 0) while producing no visible effect. For example, `git history fixup` might leave staged changes untouched without explanation, and `git history reword` might create an unreachable commit without updating any ref. This makes it impossible for users to distinguish between a successful rewrite and a no-op, especially when the editor opens as expected. The thread had previously agreed on silent success for no-op message changes, but Martinet’s testing shows that silence can be misleading in practice.

Key participants—Junio C Hamano, Justin Tobler, Patrick Steinhardt, Phillip Wood, and Pablo Sabater—had already aligned on separating message comparison (for rewrite avoidance) from identity corrections, with a phased approach for committer changes. Martinet’s feedback now adds a new requirement: the commands should verify that the rewritten commit is reachable from some ref (either via `--update-refs` or as an ancestor of HEAD) before proceeding. This would prevent unreachable commits and ensure that feedback (like printing old and new commit hashes) is meaningful. The discussion is now focused on balancing silent efficiency with clear user feedback, while addressing the technical challenge of ref reachability.
