This RFC thread explores behavior changes for the experimental `git history reword` command, part of Patrick Steinhardt's broader `git history` feature. The initial proposal sought to make the command abort when commit messages are unchanged (unlike `git commit --amend`), citing performance concerns, while also adding success feedback showing original and rewritten commit hashes. 

Junio Hamano's recent intervention has significantly shifted the discussion. He challenges the technical rationale for aborting on unchanged messages, noting that timestamp updates serve a purpose in workflows involving difficult collaborators. More importantly, he emphasizes consistency with established Git commands like `amend` and `rebase -i` should take precedence over `git history`'s unique capabilities. His suggestion that a `--force` flag might better solve the underlying concern - while acknowledging this would now be a breaking change - indicates the current direction may need rethinking.

The thread now faces key questions: Should `git history reword` align with Git's existing commit-rewriting semantics rather than introducing new behavior? How might feedback mechanisms be designed to work consistently across all `history` subcommands without creating inconsistency with Git's broader patterns? With Junio's maintainer perspective now clearly articulated, the ball is back in the author's court to either revise the approach or make a compelling case for divergence from Git's established norms.
