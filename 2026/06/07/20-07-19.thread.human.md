The discussion around Pablo Sabater's RFC for `git history reword` has evolved from a focused technical proposal to a broader design conversation about feedback consistency across the entire `history` command suite. 

Junio Hamano's intervention shifted the debate, challenging both the technical rationale for aborting no-op rewrites and pushing for subsystem-wide consistency in output behavior. Pablo has responded by acknowledging that other `history` commands currently follow Git's "rule of silence" but makes a case that porcelain commands like these should provide basic hash feedback by default - showing old/new commit hashes for reword/fixup operations and new commit hashes for splits, while potentially keeping drop operations silent. He remains open to implementing this as a `--verbose` option if maintainers prefer.

The thread now hinges on two key questions: whether the feedback is valuable enough to justify diverging from Git's traditional silent behavior, and if so, how broadly it should be applied across the command family. Pablo's position on showing hashes by default for porcelain commands contrasts with Junio's emphasis on consistency with established Git patterns. Patrick Steinhardt, the original `history` command author, has yet to weigh in on this expanded discussion. The outcome will likely depend on whether Pablo can demonstrate that the feedback provides sufficient user benefit to warrant changing the existing behavior of multiple subcommands.
