Pablo Sabater's RFC series proposing behavior changes for `git history reword` (an experimental command in Patrick Steinhardt's `git history` feature) continues to evolve. The discussion has centered on two key changes: making `reword` abort when the new commit message matches the original (unlike `git commit --amend`), and adding success feedback showing the original and rewritten commit hashes.

In the latest exchange, Pablo addresses Patrick's technical concern about the shared `commit_tree_ext()` function used by both `reword` and `fixup --reedit-message`. He proposes having the function return a specific status code when messages are identical, which `reword` would treat as an abort condition while `fixup` would ignore. This refined approach maintains the desired behavior for `reword` without breaking `fixup` functionality, showing Pablo's substantive engagement with the review feedback.

The philosophical discussion about whether success feedback violates Git's "rule of silence" remains open, with Pablo has argued porcelain commands may warrant different standards and suggested verbose mode as a potential compromise. The technical refinement moves one piece forward while leaving room to resolve the broader design questions.
