The rationale is that `history reword` operates purely in-memory and must update all branches containing the original commit, making no-op rewrites unnecessarily expensive. The patch includes tests and raises the open question of whether this divergence from established behavior is justified.

The second patch, which just arrived, adds explicit success feedback - showing both the original and rewritten commit hashes - to match the user experience of other porcelain commands. The implementation is clean, using Git's standard commit ID abbreviation, and comes with thorough test coverage.

Both patches build on Patrick Steinhardt's v11 `git history` series from January 2026. The RFC nature of the series specifically seeks feedback on the design choice to diverge from amend/rebase behavior in the first patch, while the second patch appears to be a straightforward improvement that aligns with Git's UX conventions.
