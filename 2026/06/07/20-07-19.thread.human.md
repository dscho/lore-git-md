This thread is about refining the behavior of `git history reword`, an experimental command in Patrick Steinhardt’s `git history` feature. The focus has shifted from whether to skip no-op rewrites to how to make that behavior safe and observable. Pablo Sabater’s RFC patch series (now at v2) proposes silent success for commits where only the message is unchanged, but reviewers—especially Dominique Martinet and D. Ben Knoble—have identified critical gaps: users need feedback to know what happened, and the command must prevent accidental creation of unreachable commits.

The group has largely agreed on the core principle: unchanged messages should not trigger a rewrite, and the command should exit successfully in those cases. The sticking point is now the user experience. D. Ben Knoble proposed a detailed output format modeled on `git replay --update-refs=print`, showing old and new commit hashes for every updated ref, plus warnings for unreferenced objects. Patrick Steinhardt’s latest reply endorses the need for feedback but cautions that it must work consistently across all reference updates, not just HEAD. He also argues that strict reachability checks should be opt-in, as the command is designed to allow rewriting unreachable commits—a use case that shouldn’t be broken by default safety measures.

The discussion is converging on a design where feedback is mandatory (showing hash pairs for all refs) but strictness is configurable. Junio Hamano’s earlier guidance on phased implementation for committer identity changes remains in play, and the thread is now zeroing in on the mechanics of output formatting and safety verification. The next steps will likely involve a revised patch series that implements these requirements while preserving the command’s flexibility.
