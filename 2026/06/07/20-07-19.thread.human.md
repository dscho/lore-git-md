The thread discusses proposed changes to the experimental `git history reword` command, focusing on whether and how to provide feedback about successful operations. Pablo Sabater, a new contributor to this subsystem, initially proposed two changes: making the command abort when the new commit message matches the original (unlike similar commands like `git commit --amend`), and adding success feedback showing the original and rewritten commit hashes.

Patrick Steinhardt, the primary author of the `git history` feature, raised substantive concerns in his review. For the feedback proposal, he questioned whether it aligns with Git's traditional "rule of silence" and suggested the output might need to be more comprehensive (showing affected branches) or generalized across all `history` subcommands via a verbose mode.

In the latest response, Pablo thoughtfully engages with these concerns while defending the core motivation. He argues that some feedback is necessary for usability, since the current silent behavior makes it hard to verify success, and the rewritten commit hash is particularly important because the original becomes invalid. Pablo acknowledges Patrick's point about showing branch updates and is open to generalizing the approach, but maintains that basic feedback should exist even in non-verbose mode for this porcelain command.

The discussion remains open on several fronts: the scope of feedback (just commit hashes or also branch/HEAD changes), whether to make the approach consistent across subcommands, and how to balance Git's traditional silence with porcelain usability needs. Patrick's suggestion of a verbose mode appears to be emerging as a potential compromise path forward. The exchange demonstrates Pablo's thoughtful engagement with substantive review feedback while standing by the core user experience motivation for the change.
