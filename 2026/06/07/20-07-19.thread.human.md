This thread discusses proposed behavior changes for the experimental `git history reword` command, part of Patrick Steinhardt's broader `git history` feature. The key debate centers on whether the command should abort when the new commit message matches the original (unlike similar commands like `git commit --amend`), and if so, whether this should be the default behavior or require a `--force` flag. 

Junio Hamano has weighed in authoritatively suggesting the behavior should require `--force` to maintain consistency with Git's established patterns, while the original author Pablo Sabater prefers making it the default. The discussion has expanded to consider how all `git history` subcommands should provide feedback to users, balancing Git's traditional "rule of silence" against the needs of a porcelain command. 

In the latest exchange, Pablo confirmed technical details about editor integration but didn't advance the core debate. The thread remains at an impasse between Pablo's preference for immediate feedback and Junio's emphasis on consistency with existing Git behavior. Several open questions remain about output verbosity, editor behavior standardization, and how this functionality relates to existing commands like `rebase --update-refs`. Patrick Steinhardt, as the maintainer of the underlying `git history` feature, has yet to respond to the latest technical proposals.
