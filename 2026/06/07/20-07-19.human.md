This is an RFC patch series proposing two behavioral changes for the experimental `git history reword` command, which is part of Patrick Steinhardt's ongoing `git history` builtin effort.

The series makes two main changes to `git history reword`:
1. It aborts the operation when the commit message hasn't actually changed, avoiding unnecessary history rewrites. The patch notes this differs from `git commit --amend` and `git rebase -i` behavior, speculating those commands may need to update due to staged file changes.
2. It adds user feedback after a successful reword operation, making it clearer when the command has completed.

The rationale focuses on `git history`'s broader scope (updating all branches containing the commit) making unnecessary rewrites more expensive than in rebase/amend. The patches include tests verifying both behaviors.

This appears to be a well-motivated quality-of-life improvement for an experimental command. The author acknowledges uncertainty about why amend/rebase behave differently and invites discussion on whether the divergence is appropriate. The patches are cleanly separated with good test coverage.

As this targets an in-progress feature (`git history`), it may need to wait for that series to stabilize before being considered for merging. The RFC tag suggests the author is primarily seeking design feedback at this stage.
