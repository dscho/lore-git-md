This is an RFC patch series proposing behavior changes for the experimental `git history reword` command, which is part of the larger `git history` feature being developed. The series comes from a relatively new contributor and addresses two specific aspects of the reword operation.

The first patch would make `git history reword` abort when the new commit message is identical to the original, unlike `git commit --amend` and `git rebase -i` which proceed regardless. The rationale is that `git history` updates all branches containing the original commit (a more expensive operation) and works purely in-memory without touching the worktree or index, making the no-change case worth optimizing. The author acknowledges uncertainty about why the existing commands behave as they do and invites discussion.

The second patch adds user feedback after a successful reword operation, making it explicit when the change has been applied. Both patches include corresponding test cases in t/t3451-history-reword.sh.

The series builds on Patrick Steinhardt's ongoing `git history` work (referencing his v11 series from January 2026) and appears to be the author's first contribution to this subsystem. The changes are narrowly scoped and well-motivated, though the RFC flag suggests the author is particularly interested in feedback on the first patch's divergence from established amend/rebase behavior. The patches touch the relatively new builtin/history.c code and its test suite.
