This is an RFC patch proposing a behavior change for the experimental `git history reword` command, which is part of Patrick Steinhardt's larger `git history` feature effort. The patch comes from a relatively new contributor to this subsystem.

The change makes `git history reword` abort when the new commit message matches the original, unlike `git commit --amend` and `git rebase -i` which proceed regardless. The rationale is that `git history` has different constraints: it updates all branches containing the original commit (a more expensive operation) and works purely in-memory without touching the worktree or index. The author acknowledges this diverges from existing behavior but argues the optimization is justified given these differences.

The patch includes a test case verifying the new behavior. It's well-structured with clear commit message and references to prior discussions. The RFC flag suggests the author is particularly interested in feedback on whether this divergence from amend/rebase behavior is acceptable. This seems like a reasonable optimization given `git history`'s different architecture, but the discussion will likely focus on whether consistency with existing commands should take precedence.
