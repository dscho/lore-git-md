Here's the human-readable summary of this Git mailing list thread:

This thread covers Miklos Vajna's patch series that fixes a long-standing limitation in `git log --follow` when dealing with non-linear history, particularly rename tracking across merge commits. The current implementation fails because it uses a single global variable that gets overwritten when traversing different parent paths, which is problematic for subtree merges where rename history may diverge.

The solution is now ready for merging after two iterations. It introduces a `follow_pathspec_slab` structure to store per-commit pathspec information, allowing proper tracking through merge commits while maintaining Git's current single-path limitation. The implementation handles edge cases at history fork points by temporarily disabling rename following when multiple paths are encountered, preserving the existing behavior constraints of the diff machinery.

Junio Hamano has approved the technical aspects, and all substantive feedback has been incorporated. The only remaining task is administrative - renumbering one test file to avoid conflicts. The patch touches core files (revision.c, log-tree.c, diff.c) and adds comprehensive test coverage for subtree merges, renames from both merge sides, and diverged paths converging in common ancestors. This is a targeted bugfix that addresses a documented limitation without expanding Git's path tracking capabilities.
