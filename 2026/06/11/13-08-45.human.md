This is a follow-up in the ongoing discussion about disabling Git config includes for sandboxing purposes. Derrick Stolee responds to Jeff King's request for more details about the specific use case driving this feature.

Stolee explains the concrete scenario: a build system with strict sandboxing requirements is failing when users have Git config includes, because the build system tracks all inputs but doesn't account for these included config files (while properly ignoring core Git files in .git/). He notes this is happening through a third-party tool calling Git that he can't modify directly.

The response clarifies that this isn't about malicious configs but rather about build determinism - the includes are being used for quality-of-life aliases, not critical settings. Stolee seems open to alternative solutions, including pushing back on users to change their config practices if the community decides the risks outweigh the benefits.

This moves the discussion forward by providing the specific sandboxing context that motivated the patches, while showing the author's willingness to reconsider the approach based on the substantive concerns raised. The thread remains focused on finding the right balance between security/sandboxing needs and real-world workflow impacts.
