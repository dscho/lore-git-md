This is a bugfix patch addressing limitations in `git log --follow` when dealing with non-linear history. The patch improves rename tracking across merge commits, particularly in subtree merge scenarios where the current implementation would only follow one path through the history.

The core issue is that `--follow` currently stores the followed path in a single global variable (`opt->diffopt.pathspec`), which gets overwritten when traversing different parent paths in a merge. The solution introduces a commit-to-paths mapping (`follow_pathspec_slab`) that tracks which paths to follow for each commit's parents. This ensures rename detection works correctly regardless of traversal order through merge commits.

The patch includes:
1. A new slab structure to store per-commit pathspec information
2. Logic to propagate pathspecs to parent commits during traversal
3. Three new test cases demonstrating the fixed behavior:
   - Following renames through subtree merges
   - Handling renames from both sides of a merge
   - Tracking diverged paths that converge in a common ancestor

The implementation maintains the existing limitation that only a single path can be specified on the command line, but now correctly handles cases where that path was renamed through multiple branches. The documentation is updated to remove the "does not work well on non-linear history" caveat while keeping the single-path restriction.

This appears to be a well-considered solution to a long-standing limitation, with thorough test coverage demonstrating the problem scenarios. The patch follows Git's coding style and includes appropriate memory management for the new slab structure.
