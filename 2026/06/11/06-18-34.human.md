This is a bugfix patch that improves `git log --follow` behavior when following renames across non-linear history (particularly merge commits). The current implementation has a limitation where it only tracks one rename path at a time, causing it to miss history when multiple parents of a merge commit contain different rename paths for the same file.

The patch introduces a commit-to-paths mapping system (`follow_pathspec_slab`) that stores the paths to follow for each commit's parents. This ensures the correct paths are followed regardless of traversal order, fixing cases like:
- Subtree merges where a file was renamed inside the merged history
- Cases where different branches rename different files to the same name before merging
- General cases where renames happen in parent histories rather than the merge commit itself

The solution maintains the existing limitation that only one path can be specified on the command line, but properly handles cases where that path diverges across merge parents. The patch includes comprehensive tests demonstrating the fixed behavior.

This appears to be a well-constructed solution to a real limitation in Git's rename tracking. The implementation is careful to maintain existing behavior while fixing the merge case, and the test coverage is thorough, including both subtree merges and more complex criss-cross rename scenarios. The changes touch core revision walking code but are appropriately scoped to the rename-following logic.
