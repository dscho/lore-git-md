This is patch 8/10 in Patrick Steinhardt's v5 series introducing the `git history drop` subcommand. The patch modifies the reset machinery to properly handle dirty indexes when performing resets.

The change removes an optimization from 2022 that assumed callers would always pass a clean index to `reset_working_tree()`. That assumption held for rebase and sequencer operations, but breaks for the new `history drop` use case where the index may be dirty. The patch now only skips cache tree updates for hard resets, where we know the index will be completely overwritten.

The implementation is straightforward - it moves the `skip_cache_tree_update` flag to only apply for hard resets, and similarly restricts `prime_cache_tree()` calls to hard resets. The commit message notes this is a safe change since the original performance optimization was negligible anyway.

This is a small but important piece of the larger series, ensuring the reset machinery works correctly when called from the new history manipulation code. The change maintains backwards compatibility while enabling the new functionality.
