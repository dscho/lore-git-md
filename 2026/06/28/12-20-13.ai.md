This is a **substantive review** from Johannes Schindelin on Toon Claes's merged `git replay --linearize` series. The email identifies a **regression in v5** that causes commits to be silently dropped when replaying a single branch containing merge commits. Specifically, the fix for `--onto` edge cases in v5 inadvertently removed the `replayed_base` logic that preserved the linearized history of a single branch, leading to incorrect behavior where only the tip commit is replayed and intermediate commits are lost.

Schindelin provides a concrete example using a real Git commit topology (`master~2..master`), demonstrating that the current v5 implementation replays only the tip commit directly onto the `--onto` target, dropping the "Git 2.55-rc2" commit entirely. This differs from the expected behavior (and v4's behavior), which would preserve all commits in a linearized sequence. He explains that the `replayed_base` mechanism was originally introduced to prevent this exact issue.

The review also raises a **design question** about how `--linearize` should handle multiple branches. Schindelin argues that the only consistent approach is to linearize all replayed commits into a single sequence, as any attempt to preserve branch independence would lead to user surprises when branches share history (e.g., a merge of two replayed branches). He suggests that the current v5 logic may need to be reverted or redesigned to handle both single-branch and multi-branch cases correctly.

Key technical details:
- **Regression introduced in v5**: Removal of `replayed_base` logic causes commit dropping in single-branch scenarios.
- **Files affected**: `replay.c` (specifically `pick_regular_commit()`).
- **Test case**: Real-world topology (`master~2..master`) with merge commits.
- **Proposed solution**: Restore `replayed_base` or redesign multi-branch handling to avoid silent data loss.
- **Related symbols**: `replayed_base`, `--onto`, `--linearize`, `pick_regular_commit()`.
