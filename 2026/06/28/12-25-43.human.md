This is the fifth patch in a well-regarded performance series (v4 5/8) that optimizes Git’s merge-base calculation by terminating early when one side of the history is exhausted. The patch introduces `struct paint_state`, a new data structure that replaces the old `nonstale_queue`’s pointer-based termination logic with explicit counters for each side (PARENT1-only, PARENT2-only, and pending merge-base candidates). The counters are maintained by `paint_count_update()`, which adjusts the appropriate bucket based on the commit’s paint flags, and the loop now drains the queue via `paint_queue_get()`, which returns NULL when all counters reach zero.

The change is mechanical and behavior-preserving—both the old and new code detect when no non-stale entries remain—but the “pop first” form of `paint_queue_get()` (dequeue, then check counters) exits the loop one iteration earlier in some topologies, causing a few step counts to drop by one (e.g., the `pending-stale` test now reports 5 steps instead of 6). The existing `nonstale_queue` is left untouched for `ahead_behind()`, so this patch only affects `paint_down_to_common()`.

The commit message is clear and the diff is clean, with an exhaustive switch statement documenting all valid flag combinations. The counters are renamed to `parent1_count`, `parent2_count`, and `mb_candidate_count` (from `p1_count`, `p2_count`, and `pending_merge_bases`) and their types are changed from `int` to `size_t` for consistency with `prio_queue.nr`, addressing feedback from René Scharfe. The patch is uncontroversial and ready to merge.
