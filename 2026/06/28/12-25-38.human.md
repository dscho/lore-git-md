This is a **performance optimization and hardening series** for Git’s merge-base calculation, specifically the `paint_down_to_common()` function in the commit-reach subsystem. The series is now in its **fourth iteration (v4)**, addressing a critical regression introduced in v3 while refining the core optimization and its supporting infrastructure.

The goal is to **terminate early** when one side of a merge-base query exhausts its commit queue—no new merge-base candidates can emerge once one side is empty. This eliminates unnecessary traversal of large one-sided histories (e.g., repositories with import grafts or shallow histories), yielding **100-1000x speedups** for asymmetric queries. For example, a 2.6M-commit monorepo sees wall-clock times drop from **3.67s to 5ms** for cross-import queries, and git.git’s `merge-base --all v2.0.0 v2.55.0-rc1` improves from **110ms to 68ms**.

The series is **well-structured and collaborative**, with contributions from Kristofer Karlsson (primary author), Elijah Newren (test cases), and feedback from Derrick Stolee and René Scharfe. It includes **eight patches**, covering:
1. **Documentation** (a new technical deep-dive on `paint_down_to_common()`).
2. **Test coverage** (edge cases, regression tests, and deterministic step-count assertions).
3. **Instrumentation** (trace2 step-counting to measure performance).
4. **Refactoring** (introducing `struct paint_state` with per-side counters).
5. **The core optimization** (early termination when one side is exhausted).
6. **Cleanup** (removing dead code and consolidating termination conditions).

### Key improvements since v3

- **Fixed a critical regression** in patch 7/8: the generation-monotonicity BUG assertion was accidentally widened to fire unconditionally in v3, breaking correctness when `min_generation` was not set. The assertion now **only fires when generation-based ordering is active** (`min_generation` is set), restoring the original behavior.
- **Renamed counters** in `struct paint_state` for clarity (`parent1_count`, `parent2_count`, `mb_candidate_count`) and switched their types to `size_t` (suggested by René Scharfe).
- **Moved the `min_generation` check** into `paint_queue_get()` (patch 8/8), consolidating all halt conditions in one place and ensuring `commit_graph_generation()` is called exactly once per dequeued commit.
- **Improved test instrumentation**: The `test_paint_down_steps()` helper now provides diagnostic output on step-count mismatches, and `run_all_modes()` captures trace2 output per commit-graph mode for self-verifying performance.

### Performance and correctness

- The optimization is **gated by the finite-generation guard** (`generation < GENERATION_NUMBER_INFINITY`) to ensure correctness. Commits without commit-graph entries (generation `INFINITY`) are ordered by commit date, which is not topologically reliable, so the optimization only activates in the finite region.
- **Deterministic step counts** (measured via trace2) validate the optimization across all commit-graph modes (none, full, half, no-gdat). For example, the "self" test expects **45 steps in "none" mode but only 2 in "full"** mode.
- **Test coverage** spans edge cases (self/duplicate/pending-stale/infinity-both-sides), diamond topologies, mixed finite/INFINITY generation numbers, criss-cross merges, grafts, and shallow histories. The regression in v3 was caught by `t6600-test-reach.sh` (test 12, `get_merge_bases_many`), confirming the test suite’s robustness.
