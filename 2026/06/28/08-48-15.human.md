This is a **build system** and **platform compatibility** follow-up in the ongoing `USE_NSEC` discussion. Jeff King (Peff) expands on his earlier testing of the `USE_NSEC` knob, now confirming that modern Linux filesystems—including CIFS and even FAT—correctly handle nanosecond timestamps, making the original "racy Git" concerns largely obsolete on Linux. He also surfaces a 2015 kernel thread that documents fixes for CEPH, CIFS, NTFS, and UDF in kernel 4.3, further undermining the historical rationale for keeping `USE_NSEC` disabled by default.

Peff raises a new angle: interoperability between Git implementations (e.g., JGit, which may use millisecond-resolution APIs) or between Git versions built with and without `USE_NSEC`. While this doesn’t break correctness—Git already stores nanoseconds unconditionally and only uses them when `USE_NSEC` is enabled—it could create performance issues. For example, if JGit writes an index with millisecond timestamps and a `USE_NSEC`-enabled Git reads it, Git may treat all files as stat-dirty and re-read their contents unnecessarily. This is a performance penalty, not a correctness bug, but it’s a real-world edge case that could affect users who toggle the knob.

The email doesn’t propose any changes to the patch or the knob’s default, but it shifts the discussion toward a broader question: if `USE_NSEC` is no longer problematic on modern systems, should it be enabled by default, deprecated, or removed entirely? Peff’s findings suggest the knob’s risks are overstated, but the interoperability caveats add nuance. The thread now hinges on whether these edge cases are significant enough to justify keeping the knob around—or whether the time has come to simplify Git’s build system by removing it. No action is imminent, but this is a rare re-evaluation of a long-standing technical debt item.
