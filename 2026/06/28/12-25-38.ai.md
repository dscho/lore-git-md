This is a **performance optimization and hardening series** in Git’s commit-reach subsystem, targeting the `paint_down_to_common()` function used in merge-base calculations. The series is now in its **fourth iteration (v4)**, addressing a **critical regression** introduced in v3 while consolidating termination conditions and improving code clarity.

The core optimization teaches `paint_down_to_common()` to terminate early when one side of the history is exhausted—no new merge-base candidates can emerge once one side’s queue is empty. This eliminates unnecessary traversal of large one-sided histories (e.g., repositories with import grafts or shallow histories), yielding **100-1000x speedups** for asymmetric queries. The optimization is gated by the finite-generation guard (`generation < GENERATION_NUMBER_INFINITY`) to ensure correctness, and the series now **restores the `min_generation` guard** to the generation-monotonicity BUG assertion, fixing the regression that caused test failures in v3.

The series is **well-tested and instrumented**, with **deterministic step-count assertions** for all commit-graph modes (none, full, half, no-gdat) and **self-verifying performance** via `run_all_modes` capturing trace2 output per mode. Benchmarks show dramatic improvements: for example, `merge-base --all` across a 2.6M-commit monorepo drops from **3.67s to 5ms**, and step counts in git.git are reduced by **30-60%** for common queries. The test coverage spans edge cases (self/duplicate/pending-stale/infinity-both-sides), diamond topologies, mixed finite/INFINITY generation numbers, criss-cross merges, grafts, and shallow histories.

Key changes since v3:
- **Fixed the regression in patch 7/8**: The unconditional generation-monotonicity BUG assertion introduced in v3 is now properly guarded by `min_generation`, restoring correctness when the threshold is not set. This resolves the test failure in `t6600-test-reach.sh` (test 12, `get_merge_bases_many`) that caused Junio C Hamano to eject the series from `seen`.
- **Renamed counters for clarity**: `p1_count`, `p2_count`, and `pending_merge_bases` are now `parent1_count`, `parent2_count`, and `mb_candidate_count`, respectively, and their types are changed from `int` to `size_t` for consistency with `prio_queue.nr`.
- **Moved termination conditions into `paint_queue_get()`**: The `min_generation` check and `last_gen` monotonicity assertion are now consolidated inside `paint_queue_get()`, ensuring `commit_graph_generation()` is called exactly once per dequeued commit. The "pop first" form (pop, check, then decrement counters) keeps the optimization commit’s diff minimal.
- **Improved documentation**: The `min_generation` cutoff is now documented as a termination condition in the new technical document (`paint-down-to-common.adoc`), and the doc comment for `paint_queue_get()` is shortened to describe *what* it does rather than *how*.

The series is **collaborative and low-risk**. Patches 1-6/8 and 8/8 are **stable and ready to merge**, while patch 7/8 (the core optimization) is now **corrected and uncontroversial**. The test suite robustly catches regressions, and the benchmarks demonstrate the optimization’s impact. The changes are internal to the commit-reach subsystem with no on-disk format changes.

**Files touched**: `commit-reach.c`, `Documentation/technical/paint-down-to-common.adoc`, `Makefile`, `meson.build`, and test scripts (`t6099-merge-base-side-exhaustion.sh`, `t6600-test-reach.sh`).
**New/renamed symbols**: `paint_state` struct (with counters `parent1_count`, `parent2_count`, `mb_candidate_count`, `min_generation`, `last_gen`), `paint_count_update()`, `paint_queue_put()`, `paint_queue_get()`, trace2 step counter, `test_paint_down_steps()` helper.
**Behavior change**: The walk terminates early when `(!state->parent1_count || !state->parent2_count) && !state->mb_candidate_count && last_gen < GENERATION_NUMBER_INFINITY`. The generation-monotonicity BUG assertion now fires only when `min_generation` is set, restoring the original behavior. The "pop first" form of `paint_queue_get()` reduces step counts by one in some topologies (e.g., `pending-stale` drops from 6 to 5 steps).
