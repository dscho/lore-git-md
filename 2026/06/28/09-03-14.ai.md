This is a small bugfix patch targeting the reftable backend. Jeff King (Peff) fixes a memory leak in `reftable/writer.c` where the `reftable_writer` struct is allocated before input validation, causing it to leak if the block size is invalid. The fix moves the allocation after the validation check, which both plugs the leak and makes the function's flow more logical. The issue was introduced when a `BUG()` was converted to a regular error return in commit `445f9f4f35` (February 2025) and was recently flagged by Coverity.

The patch touches only `reftable/writer.c`, changing four lines to reorder the allocation. The commit message clearly explains the problem, the fix, and the rationale, including the relevant prior commit that introduced the leak. The change is minimal and self-contained, with no behavior change beyond fixing the leak.

This is a low-risk, high-value fix: the leak is unlikely to be hit in practice (it requires an invalid block size), but the fix is trivial and improves code hygiene. The patch is part of the reftable backend, which is an ongoing effort driven primarily by Patrick Steinhardt and Karthik Nayak, but this particular fix is a standalone bugfix rather than part of a larger series.

The patch was noticed via Coverity, which Peff mentions has a high false-positive rate, but this case is real and worth fixing. The fix itself is idiomatic for Git: reordering operations to avoid allocation before validation is a common pattern in the codebase. No tests are included, but the change is so small and the scenario so specific that additional test coverage would likely be overkill.

Key technical details for follow-up discussion: the function is `reftable_writer_new`, the error code is `REFTABLE_API_ERROR`, the prior commit that introduced the issue is `445f9f4f35`, and the allocation is now guarded by the block size check (`opts.block_size >= (1 << 24)`). The leak was present for over a year but only recently flagged due to nearby code changes.
