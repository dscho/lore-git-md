Originating author: Jeff King (Peff)
Thread type: bugfix patch

Core problem or goal
Fix a memory leak in the reftable backend's `reftable_writer_new` function where the `reftable_writer` struct was allocated before input validation, causing it to leak if the block size was invalid. The leak was introduced in commit `445f9f4f35` (February 2025) when a `BUG()` was converted to a regular error return. The patch was merged, but a minor textual conflict arose with a subsequent commit (`44f46f2be5`, "reftable: split up write options", 2026-06-25) that added a `hash_id` initialization near the leak fix.

Current status
Patch merged into `pu`. The conflict resolution is mechanical: the new `hash_id` initialization remains grouped with other `opts` setup, while the `reftable_calloc` allocation moves after the block-size check. No functional changes; the resolution is purely about code organization during integration. The reftable backend remains an active effort led by Patrick Steinhardt and Karthik Nayak.

Key technical details
- File: `reftable/writer.c`
- Function: `reftable_writer_new`
- Error code: `REFTABLE_API_ERROR`
- Allocation (`reftable_calloc`) now guarded by block size check (`opts.block_size >= (1 << 24)`)
- Conflict resolution: three-line reordering to preserve grouping of `opts` initialization
