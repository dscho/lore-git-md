This is a follow-up in the thread about optimizing ref-filter commands with memoized commit traversal, specifically addressing cycle detection in commit ancestry graphs.

Tamir Duberstein responds to Kristofer Karlsson's review of the cycle detection patch, agreeing that treating cycles as fatal errors (rather than falling back to a slower reachability walk) is the better approach. The key points:

1. The current implementation detects cycles caused by replacement refs (which can create ancestry loops) but falls back to a slower path when they're found.

2. Kristofer argued this fallback adds unnecessary complexity and that cycles should be treated as fatal errors, since they indicate malformed history. He pointed to similar error handling in `do_lookup_replace_object()` and `parse_commit_or_die()` as precedents.

3. Tamir confirms the test case creates a cycle that wouldn't be caught by the existing MAXREPLACEDEPTH check, but agrees with the principle that cycles should be fatal. He indicates this change has been implemented in v4 of the patch series.

The exchange shows the patch author quickly incorporating substantive technical feedback to simplify the code while maintaining safety. This continues the thread that has seen thorough review from multiple contributors (notably Jeff King) and demonstrates the project's collaborative refinement process.
