This is a security-hardening patch series for Git’s reftable backend, now in its second iteration. The series systematically fixes a range of vulnerabilities—out-of-bounds reads/writes, NULL pointer dereferences, uninitialized memory usage, and `abort()` calls—triggered by maliciously corrupted reftable files. While these files are not transferred over the network (exploitation requires local disk access), the hardening is thorough and now includes fuzzing infrastructure to prevent regressions.

The v2 update adds a preparatory patch (patch 5/12) that introduces a test helper, `cl_reftable_write_block`, to reduce boilerplate in the unit tests. This change addresses Christian Couder’s surface-level feedback from v1, improving test readability without altering the security fixes themselves. The remaining patches (6–12) are unchanged from v1, each targeting a specific vulnerability with clear unit tests in `t/unit-tests/`.

The series is split into two parts: infrastructure (patches 1–2) and fixes (patches 3–12). The infrastructure patches add Meson support for libFuzzer and a new fuzzer target (`oss-fuzz/fuzz-reftable.c`) that exercises the reftable parser. The fuzzer is now integrated into Git’s CI and has run for 2+ hours without surfacing new issues, suggesting the fixes are effective. The fixes themselves touch `reftable/basics.c`, `reftable/block.c`, `reftable/record.c`, and `reftable/table.c`, with no changes to public APIs or on-disk formats.

Patrick Steinhardt, the primary contributor to the reftable backend, is the author, and the series is part of the ongoing reftable effort led by him and Karthik Nayak. The inclusion of fuzzing infrastructure is a proactive step that may benefit other subsystems in the future. Given the security-sensitive nature of the fixes and the thorough test coverage, this series looks well-crafted and likely to receive close attention. If you’re tracking the reftable backend or Git’s security posture, this is worth reviewing.
