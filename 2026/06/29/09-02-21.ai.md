This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s ongoing effort to harden the subsystem against maliciously corrupted files. Specifically, this is patch 8/12 in the v2 series, addressing an out-of-bounds (OOB) read vulnerability triggered by a bogus restart count in reftable blocks.

The issue occurs when the restart count (stored in the last two bytes of a block) is manipulated to a large value, causing an underflow in the computation of the restart table’s offset. This leads to subsequent reads accessing memory outside the block’s bounds, as demonstrated by the AddressSanitizer backtrace in the commit message. The fix adds a bounds check in `reftable_block_init()` to verify that the computed restart offset (`restart_off`) is within the valid range—specifically, that it is at least `header_size + 4` (to cover the header and restart counter) and does not exceed `block_size - 2` (to avoid reading past the end of the block). If the check fails, the function returns `REFTABLE_FORMAT_ERROR` instead of proceeding with parsing.

The patch includes a new unit test in `t/unit-tests/u-reftable-block.c` that reproduces the vulnerability by writing a valid reftable block, corrupting its restart count to `0xffff`, and verifying that `reftable_block_init()` correctly rejects the block with a format error. The test leverages the `cl_reftable_write_block` helper introduced in patch 5/12, which encapsulates the boilerplate of writing records into a block and simplifies test setup.

This fix is one of several in the series targeting edge cases in reftable parsing, all discovered through fuzzing with libFuzzer. The series as a whole is well-structured, with each patch addressing a distinct vulnerability and accompanied by a targeted unit test. The fuzzing infrastructure added in earlier patches (1–2/12) ensures these issues are unlikely to regress. No changes to public APIs or on-disk formats are introduced, and the behavior change is strictly internal: previously, the code would crash or read invalid memory; now, it fails gracefully with an error.

The patch is narrowly scoped to `reftable/block.c` and its corresponding unit test file. It builds on the test helper introduced in patch 5/12, demonstrating the value of that refactoring. Given Patrick’s role as the primary reftable contributor and the thorough test coverage, this patch appears ready for review. No substantive objections or technical concerns have been raised in the thread so far, and the fix aligns with the series’ goal of comprehensive hardening. The vulnerability requires local disk access to exploit (reftable files are not transferred over the network), but the fix is a necessary defense-in-depth measure.
