This is the latest exchange in the ongoing `git replay --linearize` feature series, now at v5. The thread focuses on the command-line interface design for handling merge commits, a question that remains unresolved but does not block the current patch.

Patrick Steinhardt presses for consistency with `git rebase`'s existing three-mode interface (`--no-rebase-merges`, `--rebase-merges`, and `--rebase-merges=rebase-cousins`). He argues that since the series already acknowledges the need for all three behaviors—flattening merges, preserving topology, and aborting on merges—Git should reuse the same syntax rather than inventing new flags like `--linearize` or `--replay-cousins`. His position is not that the feature must support all modes immediately, but that the interface should be designed to accommodate them later without breaking changes.

Toon Claes acknowledges the point but prefers to proceed incrementally, adding `--linearize` now and extending the interface later. He sketches a possible future design with separate flags (`--no-merges`, `--replay-cousins`) or a unified `--replay-merges=<mode>` option, but does not commit to either. His argument is that the internal data structure need not mirror the CLI, so the code can evolve as needed. The exchange leaves the interface question open; no consensus has emerged, but the discussion is purely forward-looking and does not affect the correctness of the current implementation.

The series itself remains under review, blocked only by the regression Johannes Schindelin identified in v5: when replaying a single branch containing merge commits, `--linearize` incorrectly drops commits. That issue must be fixed before the patch can land, but this email does not address it. The interface debate is a separate concern and will likely continue in future iterations.
