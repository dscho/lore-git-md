This is the seventh patch in Patrick Steinhardt’s v2 twelve-patch series hardening Git’s reftable backend against maliciously corrupted files. It fixes an out-of-bounds read that occurs when a block header claims a size larger than the actual data available. The vulnerability surfaces in `reftable_block_init()` when computing the restart table offset and restart count, both of which are derived from the untrusted block size. The fix adds a bounds check in `reftable/block.c` that returns `REFTABLE_FORMAT_ERROR` if the claimed block size exceeds the buffer length, preventing the subsequent out-of-bounds access. The patch includes a new unit test in `t/unit-tests/u-reftable-block.c` that deliberately corrupts the 24-bit block size field to trigger the error path, verifying the fix works as intended.

The patch is part of the series’ third logical group (patches 6–12), which implements individual security fixes for vulnerabilities discovered by the libFuzzer-based fuzzing infrastructure introduced in patches 1–2. Patch 5/12, added in v2, provides the `cl_reftable_write_block` helper used here to reduce test boilerplate. The fix itself is minimal and targeted: a single nine-line addition in `reftable/block.c` and a thirty-three-line test case. No public APIs or on-disk formats change, and the new behavior is strictly safer—malformed input now fails gracefully instead of crashing.

Given Patrick’s role as the primary reftable contributor and the series’ thorough test coverage (each fix is paired with a unit test), this patch appears well-crafted and uncontroversial. The vulnerability is local-only (exploitation requires write access to the reftable file), but the hardening is comprehensive and proactive. No objections or technical concerns have been raised in the thread so far. The patch touches only `reftable/block.c` and its corresponding unit test file, making it self-contained and easy to review in isolation. The new test leverages the helper introduced in patch 5/12, demonstrating the helper’s intended use case.
