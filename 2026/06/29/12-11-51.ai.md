This is a **substantive review follow-up** in the ongoing `paint_down_to_common()` optimization series. Kristofer Karlsson identifies a **new regression** affecting the `!FIND_ALL` early-exit optimization when the commit queue falls back to commit-date ordering (instead of generation ordering). The issue surfaces in repositories with v1 commit-graph data, where commits may have finite topological levels but the queue is not generation-ordered, breaking the assumption that finite generation numbers imply a generation-ordered queue.

Kristofer traces the fallback’s origin to commit 091f4cf3 (2018), which was introduced to mitigate a performance regression in `git merge-base --all v4.8 v4.9` on the Linux kernel (636k commits walked instead of 167k). However, with the side-exhaustion optimization now in place, the same benchmark shows **no regression**—the walk terminates early regardless of queue ordering, suggesting the fallback may be redundant. Benchmarks confirm that side-exhaustion reduces the v1 case to **17ms** (vs. 188ms with the fallback), matching v2 performance.

Two potential fixes are proposed:
1. **Remove the fallback entirely**, always using `compare_commits_by_gen_then_commit_date`. This would simplify the code, fix the bug, and eliminate the unused `corrected_commit_dates_enabled()` function.
2. **Retain the fallback but disable optimizations** (like `!FIND_ALL` early exit) when generation ordering is inactive, via a `paint_state.gen_ordered` flag.

The discussion hinges on whether the fallback is still necessary. Kristofer leans toward removal, noting that commit-graph v1 data is rare (v2 has been the default since 2021) and side-exhaustion obviates the original performance concern. However, he seeks Derrick Stolee’s input on edge cases where the fallback might still be needed. The fix will be addressed in a **small follow-up patch** before Git 2.55 final, with tests to demonstrate the regression. This does not block the current v4 series but may require a **v5 reroll** to squash the fix.
