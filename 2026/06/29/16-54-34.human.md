This is Junio C Hamano weighing in on two specific design questions in the `git history squash` series, now at v6. The thread is in the final stages—Harald Nordgren has addressed all prior feedback, and the series is code-complete—but Junio’s comments here could still influence the implementation before it graduates to `next`.

The first point is about `fixup!`/`squash!` commits. Phillip Wood suggested the command should error out if a `fixup!` commit’s target lies outside the range being squashed. Junio agrees in principle, calling it “interesting” and saying it “at least deserves a warning.” He leans toward outright rejection unless the user’s intent to leave the fixup out is clearly deliberate. This is a usability call: if such cases are rare, failing fast with a clear error message is better than silently producing a suboptimal result. The implication is that the current implementation (which folds `fixup!` commits like any other) may need adjustment.

The second point is stricter input validation. Phillip proposed whitelisting a few `git rev-list` options (`--left-only`, `--right-only`, `--not`) to support more flexible range syntax. Junio pushes back hard, calling the whitelist approach “unrobust.” Instead, he advocates letting the rev-list machinery resolve the range first, then inspecting the resulting commit set for structural validity: is the range connected? Does it have a single “bottom” (the parent of the oldest commit) and a single “top” (the youngest commit whose children can be rewritten)? This is a classic Git design principle: parse first, validate later, rather than trying to predict what rev-list options will produce an acceptable shape. His stance is likely to carry the day—it’s the same philosophy used in `git rebase` and `git cherry-pick`.

Neither comment is a show-stopper, but both are substantive enough that Harald may need to tweak the input validation and `fixup!` handling in a v7. The rest of the series—merge commit handling, ref updates, `--reedit-message` template formatting, and test coverage—appears settled. If these two points are addressed, the series looks ready for Junio’s final review and integration.
