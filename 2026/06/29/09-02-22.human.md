This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s ongoing effort to harden the code against maliciously corrupted files. This is the ninth patch in the v2 series of twelve, which collectively address a range of vulnerabilities discovered through fuzzing.

The patch fixes a use of uninitialized memory in the block iterator’s binary search logic. When searching through restart offsets, the code may encounter an error while decoding a record. Although the error is detected, the code then attempts to release the record without having initialized it first. The fix is straightforward: initialize the record earlier in the function, before any error paths can be triggered. The change is minimal—just four lines moved—and touches only `reftable/block.c`.

This is a clear-cut bugfix with no user-visible behavior change. The issue is subtle but real: using uninitialized memory can lead to crashes or undefined behavior, and while the error path here is unlikely to be hit in normal operation, it is exactly the kind of edge case that fuzzing is designed to find. The fix is well-motivated and aligns with the series’ overall goal of hardening the reftable parser.

The patch is part of the middle section of the series, which focuses on individual fixes for vulnerabilities discovered by the fuzzer. Each fix is paired with a unit test in `t/unit-tests/`, though the test for this specific issue is not shown in this email (it was likely introduced in an earlier patch in the series). The series as a whole is well-structured, with fuzzing infrastructure, test helpers, and fixes all clearly separated.
