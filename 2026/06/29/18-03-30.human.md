This is the latest reply in the `git history squash` feature discussion, part of Harald Nordgren’s ongoing patch series (now at v6). Harald responds to Phillip Wood’s usability feedback on the `--reedit-message` template and `fixup!`/`squash!` commit handling.

Harald pushes back on Phillip’s proposed template format, arguing that omitting delimiters between commit messages would make the combined message harder to read, especially when commit bodies span multiple paragraphs. He cites the commits in this series as examples where the current `git rebase -i`-style template (with clear section breaks) works better. This is a practical concern: the template’s readability directly affects how easily users can craft a coherent squashed commit message.

On `fixup!` commits, Harald agrees with Phillip’s suggestion to error out if a `fixup!` commit’s target lies outside the squashed range. This aligns with Junio’s earlier endorsement of the idea and closes a potential usability trap where users might accidentally squash unrelated commits.

The exchange also clarifies merge commit handling. Harald confirms that the current implementation behaves as Phillip described: it allows squashing ranges containing merges (e.g., `A..G` in a diamond-shaped history) but rejects merges with external parents (e.g., `E..G` in Phillip’s example). This matches the design consensus reached earlier in the thread, though the documentation could still be improved to make this behavior explicit.

The tone is collaborative, with Harald acknowledging Phillip’s points while defending the current template design. The discussion is now focused on polish rather than core functionality—no major design changes are on the table. The next steps are likely to be minor adjustments to the template and input validation, followed by Junio’s final review. The series looks well-crafted and addresses a real workflow gap, but the template debate shows that even small UX details can spark meaningful discussion.
