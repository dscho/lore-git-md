This is a **CI/build system** follow-up to the ongoing effort to stabilize Git’s macOS CI by addressing hangs in the `t5551` and `t5559` tests. Junio C Hamano responds to Patrick Steinhardt’s proposal to enable `GIT_TEST_LONG` for GitLab CI on pull-request events, aligning it with GitHub’s behavior.

Junio broadly agrees with the goal of expanding test coverage across platforms but suggests a nuanced approach. He notes that if resources are constrained, it might be more valuable to have GitLab CI cover *different* scenarios rather than duplicating GitHub’s coverage. Specifically, he points out that the current setup already enables `GIT_TEST_LONG` for pull requests to any branch and pushes to integration branches (`next`, `master`, `main`, `maint`). If there are other branches or events (e.g., scheduled runs or manual triggers) that GitHub’s CI doesn’t cover, GitLab could focus on those instead of mirroring GitHub’s configuration.

The patch itself is straightforward: it introduces a `CI_EVENT` variable to normalize event-detection logic across GitHub and GitLab, then uses it to enable `GIT_TEST_LONG` for pull/merge requests and pushes to integration branches. Junio’s feedback doesn’t oppose the change but encourages considering whether GitLab’s CI could be used more strategically to complement GitHub’s coverage. The discussion remains constructive and low-stakes, with no technical objections to the patch as written. The series as a whole (including this patch) appears ready for merging once this minor strategic question is resolved.
