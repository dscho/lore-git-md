This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s ongoing series to harden the code against corrupted files. This is patch 9/12 in the v2 series, which now includes 12 patches after adding a preparatory test helper in response to Christian Couder’s feedback.

The patch fixes a use of uninitialized memory in the reftable block iterator’s binary search logic. When `block_iter_seek_key()` performs a binary search over restart offsets, it may encounter an error in `restart_needle_less()` if the record at the given offset cannot be decoded. Although the error is detected, the code then calls `reftable_record_release()` on a record that was never initialized, leading to undefined behavior. The fix moves the `reftable_record_init()` call earlier in the function, ensuring the record is always initialized before any potential error path.

The change is minimal: four lines moved up in `reftable/block.c`, with no new logic or error conditions introduced. The fix is paired with the rest of the series’ comprehensive test coverage and fuzzing infrastructure, which has already helped identify and address similar issues. This patch does not affect public APIs or on-disk formats, and the behavior change is strictly internal to error handling.

Given the series’ focus on security hardening and the straightforward nature of the fix, this patch appears well-motivated and low-risk. The use of uninitialized memory is a clear bug, and the fix aligns with the series’ goal of making the reftable backend more robust against corrupted files.
