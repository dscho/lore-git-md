This is a **substantive review** of the `git history squash` feature, part of Harald Nordgren’s v5 series (now v6). Phillip Wood raises usability and design questions that go beyond surface-level feedback, focusing on real-world workflows and edge cases. The review targets four key areas: commit message rewording, `fixup!`/`squash!`/`amend!` handling, merge commit behavior, and input validation.

Phillip’s central concern is **commit message usability**. He criticizes the v6 cover letter for lacking detail on how users can reword the squashed commit, and proposes a more polished template for `--reedit-message`. Instead of the current `git rebase -i`-style output (which includes commented-out `fixup!` subjects and replaced messages), he suggests a cleaner format: a summary list of commit subjects followed by only the *useful* messages (omitting `fixup!` subjects and original messages replaced by `amend!`). This would reduce noise and encourage better commit hygiene. He also suggests erroring out if a `fixup!` commit’s target is outside the squashed range, and hints at a future feature to squash arbitrary commit lists (not just ranges).

On **merge commits**, Phillip clarifies the current implementation’s behavior: it handles merges *within* the range (e.g., squashing `A..G` in a diamond-shaped history) but rejects merges with external parents (e.g., squashing `B..G` without `--ancestry-path`). He notes that the current design is sensible but could be documented more clearly. Patrick Steinhardt’s reply (summarized in the parent email) endorses rejecting external-parent merges by default, calling them "a can of worms."

The review also highlights **input validation gaps**. Phillip points out that the command accepts single-commit ranges (`@^!`) and non-ancestor ranges (e.g., `origin/seen^2^!` from `master`) without error, which could confuse users. He suggests stricter validation and proposes allowing `--not` and `--left-only`/`--right-only` to support more flexible range syntax (e.g., `A...B`). Patrick defends the current behavior, noting that other `git history` subcommands allow rewriting arbitrary branches, but Phillip’s examples show real usability pain points (e.g., no error when no branch is being rewritten).

This feedback is **actionable and substantive**, addressing both user experience and technical correctness. The next revision (v6) already incorporates some of these ideas (e.g., `--reedit-message` template improvements), but Phillip’s suggestions—especially around commit message templates and input validation—could further polish the feature. The tone is constructive, focusing on practical improvements rather than design overhauls.
