This is a **performance-critical regression fix** for the `paint_down_to_common()` optimization series that was previously declared ready to merge. Kristofer Karlsson, a key reviewer and co-author of the series, has identified a **latent bug** in the side-exhaustion optimization: when the commit queue falls back to commit-date ordering (due to missing or v1-generation commit-graph data), the optimization incorrectly assumes generation-number ordering, leading to premature termination and wrong results.

The issue surfaces in the `!FIND_ALL` early-exit path and affects repositories with v1 commit-graph data or no commit-graph at all. Benchmarks on the Linux kernel (`git merge-base --all v4.8 v4.9`) show the fallback path is rarely exercised in practice (commit-graph v2 has been the default since 2021), but the bug is real and must be fixed before the series can merge.

Kristofer proposes **two solutions**: (1) remove the commit-date fallback entirely, always using generation-number ordering, or (2) disable the optimizations when the queue is not generation-ordered. He leans toward the first option, which would simplify the code by removing the `corrected_commit_dates_enabled()` check and fix the bug in one step. The benchmark data suggests the fallback is no longer needed when side-exhaustion is active, as the optimization already handles the asymmetric-query case that originally motivated the fallback.

This is a **last-minute but necessary change** for the series. The fix is small and targeted, but it touches a core assumption of the optimization. Derrick Stolee’s input is being sought to confirm whether removing the fallback could introduce regressions in edge cases. The series remains **high-value** (100-1000x speedups for asymmetric queries) and **low-risk** (no on-disk format changes), but this bug must be resolved before merging. Expect a v5 reroll with either the fallback removal or a targeted disablement of the optimization in date-ordered mode.
