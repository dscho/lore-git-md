This is the third patch in Patrick Steinhardt’s six-part ODB refactoring series, which restructures `struct object_info` to support multi-source object resolution as part of the broader ODB abstraction effort. The patch adds a `source` field to the new `struct object_info_source` (introduced in patch 2/6), allowing backends to record which ODB source (loose, packed, or in-memory) an object was retrieved from. The change is mechanical: each backend (`odb/source-inmemory.c`, `odb/source-loose.c`, and `packfile.c`) now populates the `source` field during object lookup, while the `whence` enum remains in use until patch 5/6 removes it. The patch touches four files and introduces no behavior changes, but the new field is critical for future work where callers need to distinguish between multiple sources (e.g., pluggable backends).

Justin Tobler’s review is **substantive**, engaging with the architectural design rather than just the implementation. He raises a thoughtful question about whether the ODB source should be recorded at `struct packed_git` initialization time, rather than being passed as an optional parameter to `packed_object_info_with_index_pos()`. This echoes his earlier feedback on patch 1/6, where he questioned the same design choice. While he approves the current patch ("Looks good"), his question suggests the series’ approach to source tracking remains open for discussion. No alternative implementation is proposed, but the concern highlights a potential tension between the current opt-in design and a more centralized source-tracking mechanism.

The patch itself is narrow and well-scoped, with clear commit message documentation and no obvious flaws. The BUG check in `packfile.c` ensures callers cannot request source information without providing a valid `source` parameter, which is a sensible safeguard. The series’ direction has Junio’s conceptual approval ("Great"), so this patch is likely to proceed unless Justin’s architectural question gains traction or other reviewers surface deeper concerns.
