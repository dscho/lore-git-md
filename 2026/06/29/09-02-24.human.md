This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s ongoing series to harden the code against corrupted files. This is patch 11/12 in the v2 series, which already includes fuzzing infrastructure and fixes for several other vulnerabilities.

The patch fixes a NULL pointer dereference that occurs when seeking an iterator to a bogus offset in a reftable. When an offset points beyond the block, the code currently treats it as the end of iteration, leaving a partially-initialized block that later triggers a segmentation fault. The fix adds a bounds check in `table_iter_seek_to()` to return `REFTABLE_FORMAT_ERROR` when the offset is out of bounds, ensuring graceful failure instead of a crash.

The commit message includes a detailed stack trace from AddressSanitizer, showing the exact code path that leads to the NULL pointer access. The fix itself is minimal (two lines in `reftable/table.c`), but the accompanying test is thorough: it constructs a valid reftable, corrupts the log section offset in the footer to point past the end of the table, and verifies that seeking the log iterator returns an error rather than crashing. The test also recomputes the CRC to ensure the corruption is not caught by checksum validation, isolating the bug.

This patch continues the pattern established in earlier patches (6–10/12) of pairing each fix with a targeted unit test that corrupts a specific field to trigger the vulnerability. The series as a whole is well-motivated and clearly addresses real issues discovered through fuzzing. Given Patrick’s role as the primary reftable contributor and the systematic approach taken, this patch looks like a solid, uncontroversial addition to the hardening effort.
