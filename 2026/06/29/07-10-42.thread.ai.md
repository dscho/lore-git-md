Subject: `git receive-pack` hangs on zero-object push to promisor remote
Series version: none (standalone bug report)
Originating author: Wei Hu
Thread type: bug report

Core problem or goal
A zero-object ref update pushed to a repository configured as a promisor remote causes `git receive-pack` to hang indefinitely. The hang is specific to the combination of promisor configuration and the absence of any objects in the push; it does not occur in non-promisor repositories or when the promisor configuration or `.promisor` sidecar files are removed.

Current status
Resolved by commit d9982e8290 ("connected: close err_fd in promisor fast-path", 2026-05-15), which will ship in Git 2.55 (releasing today). The fix addresses the root cause (a file descriptor leak in the promisor fast-path), but lacks test coverage. Patrick Steinhardt invites Wei Hu to contribute a test case or offers to send one himself. No further technical discussion or controversy remains.

Key technical details
- Subsystems: promisor remote, `receive-pack`, connected.c (fast-path logic)
- Files: `.promisor` sidecar files, promisor remote configuration, `t/t5616-partial-clone.sh` (test case)
- Behavior: `receive-pack` hung indefinitely on zero-object push due to an unclosed file descriptor (`err_fd`) in the promisor fast-path; fixed by explicitly closing `err_fd` in commit d9982e8290
- Test coverage: reproduction script provided in the original report; Patrick Steinhardt’s follow-up includes a minimal test case patch for `t/t5616-partial-clone.sh` to prevent regressions

Open questions and loose ends

- Scope: no evidence that other promisor-related commands (e.g., `fetch`) are affected, but this was not explicitly ruled out
