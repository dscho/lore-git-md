This is the tenth patch in Patrick Steinhardt’s twelve-patch v2 series hardening Git’s reftable backend against maliciously corrupted files. The series is part of the ongoing reftable effort and introduces no user-visible changes—only internal safety checks that prevent crashes when parsing malformed reftable blocks.

This patch specifically fixes an out-of-bounds read that occurs when a restart offset in a reftable block is manipulated to point past the end of the records section. Restart offsets are supposed to reference uncompressed records within the block, but the code previously did not validate this, allowing an attacker with local disk access to trigger a segmentation fault. The fix adds a bounds check in `restart_needle_less()` (in `reftable/block.c`) that verifies the offset points to a valid record before proceeding. If the check fails, the function sets an error flag and returns early, causing the caller to receive `REFTABLE_FORMAT_ERROR` instead of crashing.

The patch includes a new unit test (`test_reftable_block__corrupt_restart_offset` in `t/unit-tests/u-reftable-block.c`) that constructs a block with a deliberately corrupted restart offset (set to `0xffffff`) and verifies that `block_iter_seek_key()` fails gracefully. The test uses the `cl_reftable_write_block` helper introduced in patch 5/12 to reduce boilerplate, demonstrating the helper’s value in simplifying test setup for corruption scenarios.

The fix is minimal and targeted: it adds a single bounds check without altering the reftable’s on-disk format or public API. The vulnerability is low-risk in practice (exploitation requires local write access to reftable files), but the hardening is thorough and aligns with the series’ goal of making the reftable backend robust against all known fuzzer-discovered edge cases. The patch looks well-crafted, with a clear commit message that includes an AddressSanitizer backtrace and a concise explanation of the fix. No objections or review comments have been raised yet.
