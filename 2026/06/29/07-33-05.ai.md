This is a **CI/build system** follow-up to Jeff King’s 3-patch series addressing macOS CI hangs in `t5551` and `t5559`. Patrick Steinhardt proposes a small but important addition to `ci/lib.sh` that would **enable `GIT_TEST_LONG` for GitLab CI on pull-request (merge-request) events**, bringing GitLab’s behavior into alignment with GitHub’s.

The patch normalizes the event-detection logic across CI platforms by introducing a new `CI_EVENT` variable that captures whether the pipeline was triggered by a `pull_request`/`merge_request_event` or a `push`. This variable is then used in the existing `case` statement that controls `GIT_TEST_LONG`, ensuring that long-running tests (including the expensive `t5551`/`t5559` cases) run on both GitHub and GitLab for pull/merge requests and for pushes to integration branches (`next`, `master`, `main`, `maint`). The change is purely infrastructural: no new tests are added, no timeouts are adjusted, and no behavior is altered for end users.

The motivation is clear: GitLab CI currently skips the long tests that are failing on GitHub, so the project is not catching the same flakes there. With the Apache timeout fix in place, the risk of hangs is now mitigated, making it safe to enable these tests on GitLab. The patch is a straightforward, low-risk extension of the existing logic and fits naturally with the broader effort to stabilize CI across platforms.

Files touched: `ci/lib.sh` (CI event detection and `GIT_TEST_LONG` logic). Subsystems: CI configuration, GitHub Actions, GitLab CI. No new behavior is introduced beyond what already exists on GitHub; the patch merely extends it to GitLab. The change is likely to be uncontroversial and should be merged alongside or shortly after Jeff’s series.
