This is a security-hardening patch for Git’s reftable backend, part of Patrick Steinhardt’s ongoing series to harden the code against corrupted files. This is patch 11/12 in the v2 series, addressing a NULL pointer dereference that occurs when seeking to a bogus offset in a reftable table.

The issue arises when an iterator is sought to an offset that points beyond the block. While this is valid for multi-block iteration (signaling the end of the table), it becomes a corruption issue when the offset comes from a section or index. The current code treats such out-of-bounds offsets as normal end-of-iteration, leaving the block partially initialized and later causing a NULL pointer dereference in `reftable_block_type()`. The fix adds a check in `table_iter_seek_to()` to return `REFTABLE_FORMAT_ERROR` when the offset is out of bounds, ensuring graceful failure instead of a crash.

The patch includes a new unit test (`test_reftable_table__seek_invalid_log_offset`) that corrupts the log section offset in the footer to verify the fix. The test constructs a valid reftable, manipulates the footer to point the log offset past the end of the table, and confirms that seeking the log iterator returns a format error rather than crashing. The test is thorough and leverages the `cl_reftable_write_block` helper introduced earlier in the series to reduce boilerplate.

This is a well-motivated fix with clear security implications, though the attack surface is limited (local disk access required). The commit message is detailed, including a full stack trace and explanation of the root cause. The test coverage is strong, and the fix itself is minimal and targeted. No changes to public APIs or on-disk formats are introduced. Given the series’ focus on hardening and the author’s role as the primary reftable contributor, this patch appears ready for review.
