This is the sixth patch in Patrick Steinhardt’s **v2 security-hardening series** for Git’s reftable backend, which systematically fixes vulnerabilities in parsing corrupted reftable files. This specific patch addresses an **out-of-bounds write** in log blocks caused by an integer underflow when the inflated block size (stored in the untrusted header) is smaller than the trusted header size. The fix adds a sanity check to reject such malformed blocks early, returning `REFTABLE_FORMAT_ERROR` instead of allowing zlib to write beyond the allocated buffer.

The vulnerability is demonstrated with a clear AddressSanitizer trace showing a heap-buffer-overflow when reconstructing a log block with a bogus size. The commit message explains the mechanics: log blocks store their inflated size in the header, and the code subtracts the header size to determine how much data zlib should inflate. If the stored size is smaller than the header, the subtraction underflows, leading zlib to write more data than the buffer can hold. The fix is straightforward: a guard clause ensures the block size is at least large enough to cover the header, block header, and restart counter (4 + header_size + 2 bytes).

The patch includes a **new unit test** in `t/unit-tests/u-reftable-block.c` that uses the `cl_reftable_write_block` helper (introduced in patch 5/12) to construct a log block, then corrupts its size field to trigger the error. The test verifies that `reftable_block_init()` correctly returns `REFTABLE_FORMAT_ERROR` instead of crashing. The test is concise and directly exercises the edge case, making it a strong regression guard.

This is a **well-crafted bugfix** with a clear security impact (local denial-of-service via corrupted reftable files), a minimal and targeted fix, and thorough test coverage. The commit message is detailed, including the ASan trace and a precise explanation of the underflow. Given Patrick’s role as the primary reftable contributor and the series’ integration of fuzzing infrastructure, this patch looks ready for review and likely to be merged without controversy. It’s part of a larger, proactive effort to harden the reftable backend against malformed input, and this specific fix is a textbook example of defensive programming.
