This is a follow-up discussion in an RFC thread about adding user feedback to the experimental `git history reword` command. Pablo Sabater responds to Patrick Steinhardt's review of their patch proposing success messages after reword operations.

The exchange centers on Git's "rule of silence" principle versus user feedback needs. Pablo argues that unlike core Git commands which stay silent on success, porcelain commands like `git history reword` should provide confirmation since users otherwise need to manually verify the operation worked. They defend showing only the rewritten commit hash (not HEAD or other branches) as the most immediately useful reference point for checking the new message.

Patrick had suggested a verbose mode might be a better home for such feedback, applied consistently across all `history` subcommands. Pablo agrees this could work but maintains some non-verbose output is still justified for basic confirmation. The discussion remains open-ended, with Pablo signaling willingness to expand the approach to other subcommands if the core idea is accepted.

The thread shows a new contributor thoughtfully engaging with design principles while advocating for improved usability. The outcome may influence how feedback is handled across the broader `git history` feature set. Technical questions about what constitutes helpful feedback (which hashes to show, verbosity levels) remain unresolved but are being explored constructively.
