This is a follow-up in the `git history reword` RFC thread, where Pablo Sabater responds to Junio C Hamano's question about output consistency across `git history` subcommands. The discussion has shifted from whether to add feedback to how that feedback should be implemented across the entire command family.

Pablo acknowledges that other `history` subcommands (split, drop, fixup) currently follow Git's "rule of silence" but argues that showing the new commit hash after a reword operation provides valuable information that would otherwise require manual searching. He suggests this feedback could reasonably be added to other subcommands as well, with each displaying relevant output:
- reword/fixup: show old and new commit hashes
- split: show hashes of newly created commits
- drop: potentially no output (as it removes rather than modifies commits)

The author remains open to implementing this as a `--verbose` option if the maintainers prefer, but maintains that basic hash information should be shown by default for porcelain commands like these. This positions the discussion as a design question about whether the `history` command family should diverge from Git's traditional silent behavior to provide more user feedback.

Junio's earlier intervention has effectively raised the stakes - what began as a simple patch to one subcommand now requires considering the entire `history` command suite's output conventions. Pablo's response shows willingness to expand the scope but needs to demonstrate why this feedback is sufficiently valuable to justify changing the existing silent behavior of other subcommands. The thread remains open with no clear resolution yet on whether the feedback will be accepted and, if so, how broadly it should be applied.
