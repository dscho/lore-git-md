This is a follow-up in the `git history reword` RFC thread, where Pablo Sabater responds to Junio Hamano's feedback about output consistency across the `history` subcommands. The discussion has shifted from whether to add feedback for `reword` specifically to how feedback should work across the entire `history` command family.

Pablo makes the case that showing the new commit hash after a reword is valuable user feedback, since the original commit hash becomes invalid after rewriting. He argues this avoids forcing users to manually search for the new hash with `git log`. While acknowledging other `history` subcommands (`split`, `drop`, `fixup`) currently follow Git's "rule of silence", he suggests similar feedback would be useful for them too - showing new commit hashes after `split` and `fixup`, though `drop` presents a challenge since it doesn't create new commits.

The email references an earlier suggestion from Patrick Steinhardt about using a `--verbose` flag, but Pablo maintains that basic hash feedback should be the default for `reword`. The thread is now at a design decision point - whether to:
1. Add feedback just for `reword` (Pablo's original patch)
2. Implement consistent feedback system across all `history` subcommands (Junio's implied preference)
3. Use a `--verbose` flag to control output (Patrick's earlier suggestion)

The discussion remains constructive, with Pablo engaging thoughtfully with the feedback while advocating for his UX perspective. The next steps likely involve either:
- A revised patch series proposing subsystem-wide feedback consistency
- Further discussion about whether `history` should diverge from Git's traditional silent behavior for porcelain commands
- Exploration of how `--verbose` might satisfy both camps
