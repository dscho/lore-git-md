Miklos Vajna has submitted a patch to fix a limitation in `git log --follow` when tracking file renames across non-linear history, particularly through merge commits. The current implementation fails in subtree merges because it uses a single global variable to track the followed path, which gets overwritten when traversing different branches.

The solution introduces a more robust approach using a commit-to-path mapping system (via a commit slab`) to properly track which path should be followed for each commit's parents. This ensures rename detection works correctly regardless of traversal order through merges. The patch includes new test cases demonstrating the fixed behavior and removes the documentation note about `--follow`'s previous limitations with non-linear history.

The changes touch the revision machinery, log tree handling, and add a new test script. This appears to be a well-architected solution to a long-standing issue, with thorough test coverage showing it handles both subtree merges and more complex dual-rename scenarios correctly. The implementation follows Git's existing patterns for commit-specific data storage. The patch is currently awaiting review from Junio Hamano and Jeff King.
