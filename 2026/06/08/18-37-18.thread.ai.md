Core goal: Implement `--linearize` option for `git replay` to flatten merge commits into linear history by walking only first parents, providing server-side functionality equivalent to `git rebase --no-rebase-merges`. **Design clarification (Toon Claes)**: `--linearize` is intended to produce a **single linear sequence** regardless of input branches, ensuring predictable behavior. This design choice extends the feature’s scope beyond merge commits and reinforces the current `--linearize` option name (vs. `--replay-merges=linearize`). **Key implication**: The feature deliberately **duplicates shared history** when replaying multiple branches, which may surprise users expecting branch independence.

**Critical issues (post-merge)**:
1. **Single-branch replay regression**:
   - **Root cause**: v5's base-selection logic **inadvertently removed the `replayed_base` mechanism** that preserved linearized history for single branches.
   - **Silent commit dropping**: Only the tip commit is replayed, intermediate commits (including merges) are lost.
   - **Johannes Schindelin confirmed** with test case (`master~2..master`), showing v5 replays only tip commit directly onto `--onto`, dropping "Git 2.55-rc2" commit entirely.
   - **Toon Claes acknowledged** the regression and agreed that `--linearize` should produce a single linear sequence regardless of input branches, calling this "predictable behavior."
   - **Follow-up required**: Restore `replayed_base` logic or redesign multi-branch handling. **Documentation update** needed to clarify intended behavior.

2. **Merge commit divergence handling** (Junio Hamano, Phillip Wood):
   - **Design limitation**: When replaying a merge commit that merges divergent branches (e.g., X and Y), the current implementation **silently drops one side** of the merge, grafting descendants onto the surviving parent.
   - **Toon Claes's clarification**: This is **intentional** and aligns with the feature’s design goal of producing a single linear sequence. Users who want to preserve branch independence can:
     - Use `--ref` to limit which refs are updated.
     - Peel commits to avoid treating them as refs.
   - **Trade-off**: The current behavior may **duplicate shared history** but ensures a predictable linear output.
   - **Follow-up required**: Document the behavior and add test cases to expose the limitation.

3. **CLI design inconsistency** (Patrick Steinhardt):
   - `--linearize` deviates from `git rebase`'s established syntax (`--rebase-merges`, `--no-rebase-merges`, `--rebase-merges=rebase-cousins`).
   - **Johannes Schindelin's counterargument**: Rejects `git rebase` as a usability anti-pattern, advocating for **intentional divergence** with clearer option names (e.g., `--replay-merges=<mode>` instead of `--rebase-merges`).
   - **Toon Claes's position**: Reinforces current `--linearize` name as appropriate given the feature’s scope (single linear sequence, not just merge commits).
   - **Design split**: Consistency (Patrick) vs. UX clarity (Johannes). **Now a philosophical and process-level debate** after Patrick conceded the UX argument but demanded **explicit justification in commit messages** for any divergence.
