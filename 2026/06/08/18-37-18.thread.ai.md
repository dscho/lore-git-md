**Post-merge behavioral edge case (new)**:
- **Merge commit divergence handling**: When replaying a merge commit (Z) that merges two divergent branches (X and Y), `git replay --linearize` drops the merge and grafts only the first-parent branch (X) onto the new history, leaving the other branch (Y) dangling. This differs from `git rebase --no-rebase-merges`, which replays both branches (X' and Y') to produce a fully linear history incorporating both sides of the merge. The current behavior may silently discard one side of the merge, potentially surprising users. Junio C Hamano proposes adding a test to document this behavior and suggests evaluating whether users should have control over which branch survives.
