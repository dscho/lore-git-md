Core problem or goal
Add a `--linearize` option to `git replay` that flattens merge commits, producing a linear history. The series provides a predictable, all-or-nothing flattening behavior that avoids dangling commits and ensures all replayed commits are linearized into a single topology. The goal is to offer a simpler alternative to Johannes Schindelin’s earlier merge-replay implementation (pull.2106).

Key technical details
- New CLI option: `git replay --linearize` (implemented in patch 3/3)
- **New restrictions**: `--linearize` cannot be used with multiple revision ranges (e.g., `topic2 topic3 topic4`) or `--contained` (error messages added in v8).
- Internal flags: `reverse` (boolean, retained), `linearize` (boolean, introduced in patch 3/3)
- Files touched: `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, `t3650-replay-basics.sh`
- New helper functions: `put_mapped_commit` (static, in `replay.c`, introduced in patch 1/3), `get_mapped_commit` (static, renamed from `mapped_commit` in patch 1/3), `resolve_replay_base` (static, introduced in patch 2/3)
- Modified functions: `pick_regular_commit` (restored `replayed_base` parameter, reordered parameters for clarity), `replay_revisions` (skips merge commits when `--linearize` is active, resolves replay base upfront, uses `put_mapped_commit` and `get_mapped_commit` for commit mapping, enforces single-branch restriction for `--linearize`)
- **Regression fix**: The `replayed_base` parameter has been restored to ensure all replayed commits are linearized into a single topology. Without it, the replay machinery loses track of the correct parent for commits following a merge, causing commit-dropping when replaying a single branch containing merge commits (e.g., `master~2..master` with `--linearize --onto master~2` now replays all commits, not just the tip).
- **Refactoring (patch 1/3)**: Introduces `put_mapped_commit()` and renames `mapped_commit()` to `get_mapped_commit()` for symmetry, encapsulating the logic for storing and retrieving rewritten commits in the `replayed_commits` map. This reduces code duplication in `replay_revisions()` and improves clarity. The change is purely internal and preparatory, with no behavior changes. Feedback from Justin Tobler and Patrick Steinhardt on earlier iterations (v2–v5) was addressed by reverting an enum-based approach in favor of this simpler design.
- **Refactoring (patch 2/3)**: Moves the logic for resolving the replay base from `pick_regular_commit()` to `replay_revisions()`, consolidating base-selection logic in one place. This improves clarity and maintainability, reduces `pick_regular_commit()`'s parameters from five to four, and prepares the ground for `--linearize`. The change is purely internal and introduces no behavior changes. The commit message explains the motivation: bundling base-selection logic in one place improves maintainability and reduces confusion about where the replay base is determined. The helper functions `put_mapped_commit` and `get_mapped_commit` (from patch 1/3) are used to maintain consistency in how replayed commits are tracked. **New detail**: The patch distinguishes between regular replay (where the base is either the replayed parent or `onto`) and revert replay (where the base is always `last_commit`), with the logic now centralized in `replay_revisions()`.
- **Algorithmic behavior**: `--linearize` ensures all replayed commits are flattened into a single linear history. Merge commits are dropped, and subsequent commits are reparented onto the last non-merge commit. The restriction to single branches in v8 ensures no emergent reachability issues.
- **Behavioral difference from `git rebase --no-rebase-merges`**: `git replay --linearize` drops merges and keeps only one branch (e.g., `A->X'` or `A->Y'` for a merge of `A->X` and `A->Y`), while `git rebase --no-rebase-merges` rewrites both branches and drops the merge (e.g., `A->X'->Y'` or `A->Y'->X'`). This difference is intentional, documented, and tested.
- **Interface design**: The series implements `--linearize` as a standalone flag, diverging from `git rebase`'s `--rebase-merges=<mode>` syntax. The commit message justifies this divergence by arguing that `--linearize` better describes the predictable, all-or-nothing flattening behavior and that mirroring `git rebase`'s syntax would repeat past UX mistakes.
- **Compatibility**: `--linearize` and `--revert` can be used together (mutual exclusivity removed in v7), but the **edge case** of combining them on a partial merge range (Junio’s concern) remains unresolved. **Mutual exclusivity with `--advance` is enforced**; documented in the man page.
- **Edge case handling**: root commits are explicitly replayed (merges are dropped); the if/else structure distinguishes merges, roots, and regular commits; `last_commit` handling during merge linearization is documented with clarifying comments. The **partial merge range edge case** (Junio’s concern) is not yet covered by tests.

Open questions and loose ends
- **Edge case**: Whether the replay machinery can safely handle the edge case where `--linearize` and `--revert` are combined on a partial merge range (e.g., a range that includes a merge commit (`M`) and one side of the merge (`A`), but excludes the other side (`B`) and the merge base (`O`)). Junio has cautioned that the current implementation may not reliably handle this scenario, but the issue is **no longer blocking graduation to `next`**.
- **Future work**: Whether `--linearize` should eventually support per-branch linearization (e.g., via `--ref` syntax). This is now deferred, with the v8 restriction serving as an interim solution. Toon’s `--ref` proposal (requiring `--ref <ref>` when `--linearize` is used) remains a potential future direction but is not implemented in v8.
- Whether `--linearize` should also be added to `git history` (author sees no clear use case but invites feedback).
