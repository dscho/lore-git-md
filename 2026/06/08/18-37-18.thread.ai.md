Core problem or goal
Add a `--linearize` option to `git replay` that flattens merge commits, producing a linear history. The series provides a predictable, all-or-nothing flattening behavior that avoids dangling commits and ensures all replayed commits are linearized into a single topology, even when multiple branches are involved. The goal remains to offer a simpler alternative to Johannes Schindelin’s earlier merge-replay implementation (pull.2106).

Key technical details
- New CLI option: `git replay --linearize` (implemented in patch 3)
- Internal flags: `reverse` (boolean, retained), `linearize` (boolean, introduced in patch 3)
- Files touched: `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, `t3650-replay-basics.sh`
- New helper functions: `put_mapped_commit` (static, in `replay.c`), `get_mapped_commit` (static, renamed from `mapped_commit`), `resolve_replay_base` (static, introduced in patch 2/3)
- Modified functions: `pick_regular_commit` (restored `replayed_base` parameter, reordered parameters for clarity), `replay_revisions` (skips merge commits when `--linearize` is active, resolves replay base upfront)
- **Regression fix**: The `replayed_base` parameter has been restored to ensure all replayed commits are linearized into a single topology. Without it, the replay machinery loses track of the correct parent for commits following a merge, causing commit-dropping when replaying a single branch containing merge commits (e.g., `master~2..master` with `--linearize --onto master~2` now replays all commits, not just the tip).
- **Refactoring (patch 2/3)**: Moves the logic for resolving the replay base from `pick_regular_commit()` to `replay_revisions()`, consolidating base-selection logic in one place. This improves clarity and maintainability, reduces `pick_regular_commit()`'s parameters from five to four, and prepares the ground for `--linearize`. The change is purely internal and introduces no behavior changes.
- **Algorithmic behavior**: `--linearize` ensures all replayed commits are flattened into a single linear history, even when multiple branches are involved. For example, replaying branches `Z` and `C` onto `X` with `--linearize` produces `A->X->Y->Z->B->C`, where all commits are linearized into a single topology. This avoids dangling commits and ensures predictability.
- **Behavioral difference from `git rebase --no-rebase-merges`**: `git replay --linearize` drops merges and keeps only one branch (e.g., `A->X'` or `A->Y'` for a merge of `A->X` and `A->Y`), while `git rebase --no-rebase-merges` rewrites both branches and drops the merge (e.g., `A->X'->Y'` or `A->Y'->X'`). This difference is intentional, documented, and tested.
- **Interface design**: The series implements `--linearize` as a standalone flag, diverging from `git rebase`'s `--rebase-merges=<mode>` syntax. The commit message justifies this divergence by arguing that `--linearize` better describes the predictable, all-or-nothing flattening behavior and that mirroring `git rebase`'s syntax would repeat past UX mistakes. The justification addresses Patrick Steinhardt’s requirement for explicit reasoning.
- Mutual exclusivity: `--linearize` and `--revert` cannot be used together; enforced by `die_for_incompatible_opt2`; documented in the man page.
- Edge case handling: root commits are explicitly replayed (merges are dropped); the if/else structure distinguishes merges, roots, and regular commits; `last_commit` handling during merge linearization is documented with clarifying comments.
