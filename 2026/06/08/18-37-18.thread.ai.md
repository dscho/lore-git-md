Core problem or goal
Add a `--linearize` option to `git replay` that flattens merge commits, producing a linear history. The series provides a predictable, all-or-nothing flattening behavior that avoids dangling commits and ensures all replayed commits are linearized into a single topology, even when multiple branches are involved. The goal is to offer a simpler alternative to Johannes Schindelin’s earlier merge-replay implementation (pull.2106).

Current status
v7 posted, **technically complete** and addressing all prior feedback. The series remains **queued in `next` but marked "On hold, waiting for response"** (Junio C Hamano, 2026-06-04) pending resolution of the **multi-branch ambiguity** with `--linearize`. The **regression** in `--linearize` behavior when replaying a single branch containing merge commits has been fixed by restoring the `replayed_base` parameter, ensuring all replayed commits are flattened into a single linear topology. The **interface design debate** is resolved: the series uses `--linearize` as a standalone flag, diverging from `git rebase`'s `--rebase-merges=<mode>` syntax, with the divergence justified in the commit message.

**Primary unresolved issue**: The **multi-branch ambiguity** with `--linearize` remains the central open question, now narrowed to three competing proposals:
1. **Status quo** (Junio’s position): Retain the current behavior (concatenating all branches into a single linear chain) as the direct result of the user’s explicit requests (`--linearize` + multiple branches). The escape hatch (separate invocations) is sufficient.
2. **Minimal fix** (Elijah’s position): Restrict `--linearize` to a single positive ref, aligning with `--advance`/`--revert` and eliminating ambiguity. This unblocks the series for merging but defers per-branch linearization.
3. **`--ref` syntax** (Toon’s proposal): Require `--ref <ref>` when `--linearize` is used, ensuring only the specified ref is updated (e.g., `git replay --linearize --onto master branchA branchB branchC --ref branchA`). All commits from the input branches are replayed linearly onto the target, but only the ref specified by `--ref` is updated. This preserves flexibility while eliminating emergent reachability.

Toon’s email does not commit to a specific solution but **narrows the design space** to these three options. The ball is now in Elijah’s and Junio’s courts to weigh the trade-offs between flexibility, predictability, and implementation effort. The **edge case** of combining `--linearize` and `--revert` on a partial merge range (Junio’s prior concern) is **no longer blocking graduation to `next`**.

Key technical details
- New CLI option: `git replay --linearize` (implemented in patch 3/3)
- **Proposed new syntax**: `git replay --linearize --onto <target> <branches> --ref <ref>` (e.g., `--ref branchA` to update only `branchA`). This would require tracking `last_commit` per branch to avoid commit duplication when replaying multiple branches independently.
- Internal flags: `reverse` (boolean, retained), `linearize` (boolean, introduced in patch 3/3)
- Files touched: `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, `t3650-replay-basics.sh`
- New helper functions: `put_mapped_commit` (static, in `replay.c`, introduced in patch 1/3), `get_mapped_commit` (static, renamed from `mapped_commit` in patch 1/3), `resolve_replay_base` (static, introduced in patch 2/3)
- Modified functions: `pick_regular_commit` (restored `replayed_base` parameter, reordered parameters for clarity), `replay_revisions` (skips merge commits when `--linearize` is active, resolves replay base upfront, uses `put_mapped_commit` and `get_mapped_commit` for commit mapping)
- **Regression fix**: The `replayed_base` parameter has been restored to ensure all replayed commits are linearized into a single topology. Without it, the replay machinery loses track of the correct parent for commits following a merge, causing commit-dropping when replaying a single branch containing merge commits (e.g., `master~2..master` with `--linearize --onto master~2` now replays all commits, not just the tip).
- **Refactoring (patch 1/3)**: Introduces `put_mapped_commit()` and renames `mapped_commit()` to `get_mapped_commit()` for symmetry, encapsulating the logic for storing and retrieving rewritten commits in the `replayed_commits` map. This reduces code duplication in `replay_revisions()` and improves clarity. The change is purely internal and preparatory, with no behavior changes.
- **Refactoring (patch 2/3)**: Moves the logic for resolving the replay base from `pick_regular_commit()` to `replay_revisions()`, consolidating base-selection logic in one place. This improves clarity and maintainability, reduces `pick_regular_commit()`'s parameters from five to four, and prepares the ground for `--linearize`. The change is purely internal and introduces no behavior changes. The commit message explains the motivation: bundling base-selection logic in one place improves maintainability and reduces confusion about where the replay base is determined. The helper functions `put_mapped_commit` and `get_mapped_commit` (from patch 1/3) are used to maintain consistency in how replayed commits are tracked.
- **Algorithmic behavior**: `--linearize` ensures all replayed commits are flattened into a single linear history, even when multiple branches are involved. For example, replaying branches `Z` and `C` onto `X` with `--linearize` produces `A->X->Y->Z->B->C`, where all commits are linearized into a single topology. This avoids dangling commits and ensures predictability.
- **Behavioral difference from `git rebase --no-rebase-merges`**: `git replay --linearize` drops merges and keeps only one branch (e.g., `A->X'` or `A->Y'` for a merge of `A->X` and `A->Y`), while `git rebase --no-rebase-merges` rewrites both branches and drops the merge (e.g., `A->X'->Y'` or `A->Y'->X'`). This difference is intentional, documented, and tested.
- **Interface design**: The series implements `--linearize` as a standalone flag, diverging from `git rebase`'s `--rebase-merges=<mode>` syntax. The commit message justifies this divergence by arguing that `--linearize` better describes the predictable, all-or-nothing flattening behavior and that mirroring `git rebase`'s syntax would repeat past UX mistakes.
- **Compatibility**: `--linearize` and `--revert` can now be used together (mutual exclusivity removed in v7), but Junio has raised concerns about the **edge case** where the replay range includes a merge commit (`M`) and one side of the merge (`A`), but excludes the other side (`B`) and the merge base (`O`). The current implementation may not reliably handle this scenario, and Junio has cautioned against lifting the restriction unless the code can consistently handle such cases. **Mutual exclusivity with `--advance` is enforced**; documented in the man page.
- **Multi-branch behavior**: The current implementation flattens all commits into a single linear history, concatenating branches in an order determined by the revision walk (not the user's command-line order). This results in all refs pointing to different commits along the same linear chain. Junio argues this is acceptable for cases where order is inconsequential (e.g., octopus merges of independent branches), while Elijah argues it violates the principle of least astonishment and is inconsistent with `--advance`/`--revert`. Toon’s `--ref` proposal would eliminate emergent reachability by ensuring only the specified ref is updated, though all commits from the input branches would still be replayed linearly onto the target.
- **Edge case handling**: root commits are explicitly replayed (merges are dropped); the if/else structure distinguishes merges, roots, and regular commits; `last_commit` handling during merge linearization is documented with clarifying comments. The **partial merge range edge case** (Junio’s concern) and the **multi-branch ambiguity** (Elijah’s and Junio’s concern) remain unresolved, though the latter is now narrowed to three competing proposals.

Open questions and loose ends
- **Primary open question**: Which of the three competing proposals will be adopted to resolve the **multi-branch ambiguity** with `--linearize`:
  1. **Status quo** (Junio’s position): Retain the current behavior (concatenating all branches into a single linear chain). Junio argues this is the direct result of the user’s explicit requests (`--linearize` + multiple branches) and that the escape hatch (separate invocations) is sufficient. Toon’s `--ref` proposal implicitly rejects this, as it seeks a more constrained interface.
  2. **Minimal fix** (Elijah’s position): Restrict `--linearize` to a single positive ref, aligning with `--advance`/`--revert`. This unblocks the series for merging but defers per-branch linearization. Elijah’s latest email reinforces the recoverability asymmetry and emergent reachability arguments, which remain unaddressed by Junio.
  3. **`--ref` syntax** (Toon’s proposal): Require `--ref <ref>` when `--linearize` is used, ensuring only the specified ref is updated. This preserves flexibility while eliminating emergent reachability but requires tracking `last_commit` per branch to avoid commit duplication. Toon’s email does not commit to this solution but presents it as a more explicit and user-friendly alternative to Elijah’s single-ref restriction.
  The ball is in Elijah’s and Junio’s courts to weigh the trade-offs. Toon’s preference leans toward the `--ref` syntax, but he acknowledges the implementation complexity and invites further discussion.
- **Secondary open question**: Whether the replay machinery can safely handle the edge case where `--linearize` and `--revert` are combined on a partial merge range (e.g., a range that includes a merge commit (`M`) and one side of the merge (`A`), but excludes the other side (`B`) and the merge base (`O`)). Junio has cautioned that the current implementation may not reliably handle this scenario, but the issue is **no longer blocking graduation to `next`**.
- **New edge case**: `--contained` (a hypothetical future option) is flagged as incompatible with `--linearize` due to similar reachability issues. Toon suggests disallowing the combination for now, pending a clearer design.
- Whether `--linearize` should also be added to `git history` (author sees no clear use case but invites feedback).
