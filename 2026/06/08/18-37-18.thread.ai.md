Subject: [PATCH 0/3] replay: introduce --linearize option

Core problem or goal
Add a `--linearize` option to `git replay` that flattens merge commits, producing a linear history. The series provides a predictable, all-or-nothing flattening behavior that avoids dangling commits and ensures all replayed commits are linearized into a single topology, even when multiple branches are involved. The goal is to offer a simpler alternative to Johannes Schindelin’s earlier merge-replay implementation (pull.2106).

Current status
v7 posted, **technically complete** and addressing all prior feedback. The series has been **queued in `next`** for integration testing (Junio C Hamano, 2026-06-04). The **regression** in `--linearize` behavior when replaying a single branch containing merge commits has been fixed by restoring the `replayed_base` parameter, ensuring all replayed commits are flattened into a single linear topology. The **interface design debate** is resolved: the series uses `--linearize` as a standalone flag, diverging from `git rebase`'s `--rebase-merges=<mode>` syntax, with the divergence justified in the commit message. **Mutual exclusivity between `--linearize` and `--revert` was removed in v7**, but Junio has raised a **potential edge case** where the replay range includes a merge commit (`M`) and one side of the merge (`A`), but excludes the other side (`B`) and the merge base (`O`). In this scenario, the replay machinery may lack sufficient context to correctly invert the commits, leading to undefined or confusing behavior. The current implementation does not reliably distinguish this case from the "safe" scenario where all commits are included, and Junio has cautioned against lifting the restriction unless the code can handle such cases in a way that is both logical and easy to explain. The edge case remains **unresolved but is no longer blocking graduation to `next`**.

**New unresolved issue**: Elijah Newren has identified a **principle-of-least-astonishment violation** in the `--linearize` implementation when multiple positive refs are provided (e.g., `git replay --linearize --onto main topic1 topic2`). The current behavior flattens all commits into a single linear history, concatenating branches in an order determined by the revision walk (not the user's command-line order). This results in both refs pointing to different commits along the *same* linear chain, which Elijah argues is inconsistent with the behavior of other `git replay` modes (`--advance` and `--revert`), which explicitly reject multiple positive refs to avoid ambiguity. Elijah challenges the commit message's claims that the current behavior is "the only way to ensure predictable results" and "predictable," proposing two alternatives: (a) disallow multiple positive refs with `--linearize` (aligning with `--advance`/`--revert`), or (b) track a `last_commit` per branch to preserve branch independence during linearization. Junio C Hamano has **pushed back against disallowing multiple refs**, arguing that:
1. **Unpredictable order is inherent to linearization**: Even with a single branch containing merges, the order of commits after linearization is arbitrary (e.g., which side of a merge comes first). Forcing users to split linearization into separate invocations doesn’t eliminate this ambiguity—it just moves it to a different workflow.
2. **The escape hatch is intentional**: The commit message’s advice to use separate invocations for independent branches is framed as a *choice*, not a limitation. Junio sees this as a feature: users who care about order can split their work, while those who don’t can let Git handle it. Disallowing multiple refs would remove this flexibility.
Junio’s position suggests the current behavior is **acceptable for most use cases**, even if not perfect. The discussion is now about **design philosophy** (flexibility vs. strictness) rather than technical correctness. The ball is in Toon Claes’s court to either:
- Accept the status quo and document the concatenation order (e.g., "commits are linearized in revision-walk order"),
- Restrict multiple refs (aligning with `--advance`/`--revert`), or
- Propose a middle ground (e.g., track per-branch state).

Key technical details
- New CLI option: `git replay --linearize` (implemented in patch 3/3)
- Internal flags: `reverse` (boolean, retained), `linearize` (boolean, introduced in patch 3/3)
- Files touched: `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, `t3650-replay-basics.sh`
- New helper functions: `put_mapped_commit` (static, in `replay.c`, introduced in patch 1/3), `get_mapped_commit` (static, renamed from `mapped_commit` in patch 1/3), `resolve_replay_base` (static, introduced in patch 2/3)
- Modified functions: `pick_regular_commit` (restored `replayed_base` parameter, reordered parameters for clarity), `replay_revisions` (skips merge commits when `--linearize` is active, resolves replay base upfront, uses `put_mapped_commit` and `get_mapped_commit` for commit mapping)
- **Regression fix**: The `replayed_base` parameter has been restored to ensure all replayed commits are linearized into a single topology. Without it, the replay machinery loses track of the correct parent for commits following a merge, causing commit-dropping when replaying a single branch containing merge commits (e.g., `master~2..master` with `--linearize --onto master~2` now replays all commits, not just the tip).
- **Refactoring (patch 1/3)**: Introduces `put_mapped_commit()` and renames `mapped_commit()` to `get_mapped_commit()` for symmetry, encapsulating the logic for storing and retrieving rewritten commits in the `replayed_commits` map. This reduces code duplication in `replay_revisions()` and improves clarity. The change is purely internal and preparatory, with no behavior changes.
- **Refactoring (patch 2/3)**: Moves the logic for resolving the replay base from `pick_regular_commit()` to `replay_revisions()`, consolidating base-selection logic in one place. This improves clarity and maintainability, reduces `pick_regular_commit()`'s parameters from five to four, and prepares the ground for `--linearize`. The change is purely internal and introduces no behavior changes. The commit message explains the motivation: bundling base-selection logic in one place improves maintainability and reduces confusion about where the replay base is determined. The helper functions `put_mapped_commit` and `get_mapped_commit` (from patch 1/3) are used to maintain consistency in how replayed commits are tracked.
- **Algorithmic behavior**: `--linearize` ensures all replayed commits are flattened into a single linear history, even when multiple branches are involved. For example, replaying branches `Z` and `C` onto `X` with `--linearize` produces `A->X->Y->Z->B->C`, where all commits are linearized into a single topology. This avoids dangling commits and ensures predictability.
- **Behavioral difference from `git rebase --no-rebase-merges`**: `git replay --linearize` drops merges and keeps only one branch (e.g., `A->X'` or `A->Y'` for a merge of `A->X` and `A->Y`), while `git rebase --no-rebase-merges` rewrites both branches and drops the merge (e.g., `A->X'->Y'` or `A->Y'->X'`). This difference is intentional, documented, and tested.
- **Interface design**: The series implements `--linearize` as a standalone flag, diverging from `git rebase`'s `--rebase-merges=<mode>` syntax. The commit message justifies this divergence by arguing that `--linearize` better describes the predictable, all-or-nothing flattening behavior and that mirroring `git rebase`'s syntax would repeat past UX mistakes.
- **Compatibility**: `--linearize` and `--revert` can now be used together (mutual exclusivity removed in v7), but Junio has raised concerns about the **edge case** where the replay range includes a merge commit (`M`) and one side of the merge (`A`), but excludes the other side (`B`) and the merge base (`O`). The current implementation may not reliably handle this scenario, and Junio has cautioned against lifting the restriction unless the code can consistently handle such cases. **Mutual exclusivity with `--advance` is enforced**; documented in the man page.
- **New multi-branch behavior**: When multiple positive refs are provided with `--linearize`, the current implementation flattens all commits into a single linear history, concatenating branches in an order determined by the revision walk (not the user's command-line order). This results in all refs pointing to different commits along the same linear chain. Junio argues this is acceptable for cases where order is inconsequential (e.g., octopus merges of independent branches), while Elijah argues it violates the principle of least astonishment and is inconsistent with `--advance`/`--revert`.
- **Edge case handling**: root commits are explicitly replayed (merges are dropped); the if/else structure distinguishes merges, roots, and regular commits; `last_commit` handling during merge linearization is documented with clarifying comments. The **new edge case** (partial merge range with `--linearize` and `--revert`) remains unresolved but is no longer blocking progress. The **multi-branch ambiguity** (Elijah's concern) is now the primary unresolved issue.
