Core goal: Implement `--linearize` option for `git replay` to flatten merge commits into linear history by walking only first parents, providing server-side functionality equivalent to `git rebase --no-rebase-merges`. **Design intent (now fully documented and tested)**: `--linearize` produces a **single linear sequence** regardless of input branches, even if this **duplicates shared history**. This design choice is **intentional, explicitly justified in commit messages and documentation**, and extends the feature’s scope beyond merge commits, reinforcing the current `--linearize` option name.

**Critical post-merge issues (v5) resolved in v6/v7:**
1. **Silent commit dropping regression** (highest priority, root cause confirmed and fixed):
   - **Root cause**: v5 inadvertently removed the `replayed_base` mechanism in `pick_regular_commit()`, causing only the tip commit to be replayed in single-branch scenarios.
   - **Fix**: v6 **restores `replayed_base` logic** by moving base resolution outside `pick_regular_commit()` (patch 2/3), ensuring all commits in the input range are replayed. The refactoring simplifies `pick_regular_commit()`'s interface and centralizes base-selection logic in `replay_revisions()`. New test `"replay with --linearize rebase multiple divergent branches into a single line"` verifies this.
   - **Design clarification**: `--linearize` now explicitly documents that it produces a single linear sequence, even if this duplicates shared history (e.g., when replaying multiple branches).

2. **Merge commit divergence handling** (design limitation acknowledged, documented, and tested):
   - **Root cause**: v5 silently dropped one side of divergent merges (e.g., replaying a merge of X and Y would graft descendants onto the surviving parent).
   - **Fix**: v6 **documents the behavior** in both commit messages and the `git-replay` man page, and adds a test (`"replay with --linearize of a divergent merge keeps both sides"`) to verify that both sides of a divergent merge are preserved in the linear history. The documentation clarifies that `--linearize` **drops merge commits but preserves both sides of divergent merges**.
   - **Workarounds**: Users who want branch independence can use `--ref` or peel commits.

3. **CLI design inconsistency** (strategic concern, now documented and justified):
   - **Issue**: `--linearize` deviates from `git rebase`'s `--rebase-merges` syntax.
   - **Resolution**: v6 **documents the rationale** in the commit message and man page, justifying the divergence as a **UX-driven choice** (clarity over consistency). The current `--linearize` naming is retained, with explicit explanation of its scope (single linear sequence, not just merge commits).
