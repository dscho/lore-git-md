This thread explores how to handle Git config includes in sandboxed environments, with Derrick Stolee proposing mechanisms to disable them entirely. The discussion has evolved significantly from the initial proposal of simple binary switches (environment variable and command-line flag) to considering more comprehensive sandboxing solutions.

Stolee originally implemented two ways to disable includes (via `GIT_CONFIG_INCLUDES=0` or `--no-includes`), but substantive reviews from Jeff King (Peff) raised concerns about partial security coverage and workflow breakage. Peff demonstrated real-world use cases where conditional includes separate work and personal email configurations, showing how a blanket disable would cause problems. Patrick Steinhardt supports the binary approach but had earlier suggested an allow-list alternative.

The latest email provides important context - Stolee reveals this stems from a sandboxed build system where third-party tools invoke Git commands, and includes fail when trying to access files outside the sandbox. He distinguishes between "quality-of-life" includes (which could be safely disabled) and critical ones, showing openness to push back on problematic config practices rather than modifying Git.

The thread is now converging toward recognizing that a comprehensive sandboxing solution would be better than piecemeal fixes for individual config vectors. Both Stolee and Peff are engaging constructively, with the concrete example helping ground the discussion in real constraints while maintaining focus on finding the right architectural solution. The binary disable mechanisms remain viable short-term, but the design direction appears to be shifting toward a more robust approach.
