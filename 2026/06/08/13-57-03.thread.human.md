Derrick Stolee's series to add mechanisms for disabling Git config includes has drawn thoughtful feedback from key contributors. The proposal introduces both an environment variable (`GIT_CONFIG_INCLUDES=0`) and command-line option (`--no-includes`) to globally skip config include processing, aimed at sandboxed build systems. While Patrick Steinhardt had previously questioned whether a binary on/off switch provides sufficient granularity, suggesting an allow-list approach might be better, the discussion has now deepened with Jeff King's review.

Peff raises substantive concerns about the proposal's scope and impact. He notes that disabling includes only addresses one potential sandbox escape vector while leaving others (like `core.attributesFile` or external commands) open, making this a partial solution. More critically, he demonstrates how the global disable could silently break common legitimate workflows, such as the widespread pattern of using conditional includes to separate work and personal email addresses. His review doesn't reject the concept but suggests the implementation may need refinement - either to better justify focusing specifically on includes when other config vectors remain, or to develop a more nuanced solution that preserves valid use cases.

The thread now reflects a clear consensus that while the current implementation solves immediate sandboxing needs, it may require future extension. Derrick has acknowledged the points about granular control, and the discussion has clarified the tension between security needs and workflow flexibility. Peff's intervention has moved the conversation forward by highlighting practical considerations that will need addressing, whether in this series or follow-up work. The patches remain useful for strict sandboxing scenarios, but contributors now recognize they may represent just the first step toward a more comprehensive solution.
