This is a review comment from D. Ben Knoble in the ongoing discussion about feedback output in the experimental `git history` command family. The thread has been debating whether and how much feedback to show after operations like reword, fixup, split, and drop.

Knoble offers practical suggestions for finding rewritten commits without requiring command output:
- For commits that were ancestors of HEAD, suggests checking `HEAD@{1}` or using `git-range-diff`
- For commits reachable from other refs, recommends checking the ref's reflog

The review is surface-level, focusing on alternative approaches rather than engaging with the deeper design questions about output consistency across subcommands or the porcelain/plumbing divide. Knoble doesn't take a position on whether feedback should be shown by default or under `--verbose`, instead providing workarounds that could make the feedback less critical.

This continues the pattern where technical contributors are offering implementation-focused suggestions while the higher-level design questions (raised by Junio) about command family consistency remain unresolved. The review doesn't advance the core debate but does provide useful context about how users might find rewritten commits without explicit feedback from the command.
