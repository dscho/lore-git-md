This is a bugfix patch addressing limitations in `git log --follow` when dealing with non-linear history and renames. The patch comes from Miklos Vajna and is directed to Junio Hamano and Jeff King.

The core issue is that `--follow` currently fails to properly track file renames across merge commits, particularly in subtree merges. The command would only follow one path through the merge, losing track of renames that happened in other branches. The patch introduces a commit-to-path mapping system (`follow_pathspec_slab`) that remembers which path to follow for each parent commit, ensuring rename tracking works correctly regardless of merge topology.

Key technical changes:
- Adds a new commit slab to store per-commit pathspecs
- Implements path propagation logic for merge parents
- Updates the `log.follow` documentation to remove the "non-linear history" limitation
- Includes new test cases demonstrating the fixed behavior

The patch appears well-constructed with:
- Clear commit message explaining the problem and solution
- Comprehensive test coverage for both subtree merges and cross-branch renames
- Careful memory management for the new slab structure
- No obvious performance regressions (the slab is only used when `--follow` is active)

This addresses a long-standing limitation in Git's rename tracking that has affected users trying to follow file history across complex merges. The solution is particularly relevant for projects using subtree merges or other non-linear history patterns.
