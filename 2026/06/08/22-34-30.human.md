This is a performance optimization discussion for ref-filter's `--contains` checks, building on the earlier patch that unified the ancestry traversal algorithm across commands.

Jeff King (Peff) raises an important technical consideration about the tradeoffs between depth-first and breadth-first traversal strategies. While the patch shows impressive speedups for cases with many refs (223x faster in one benchmark), Peff notes there may be regressions in shallow histories where breadth-first search would find the answer more quickly. He suggests combining the approaches by using generation numbers to intelligently choose between algorithms.

The thread also surfaces two historical context points:
1. The depth-first algorithm currently used by `git tag --contains` may have unaddressed cycle-handling issues (which could be problematic with replacement refs)
2. There was a deliberate decision in 2018 to make ancestry parsing failures consistently fail rather than treating them as "contains" matches

Peff references an older patch from Kristofer that proposed using generation numbers to optimize algorithm selection, suggesting this might be a better path forward than unconditionally using the depth-first approach. The performance numbers shown are compelling for the many-refs case, but the discussion indicates the optimization may need more nuance to avoid regressing other workflows.

This email doesn't reject the approach outright but suggests the patch may need refinement to handle edge cases and performance tradeoffs more carefully. The core idea of unifying the implementations remains sound, but the algorithm selection criteria may need adjustment.
