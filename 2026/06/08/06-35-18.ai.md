This is a bugfix patch addressing limitations in `git log --follow` when traversing non-linear history with renames. The patch comes from Miklos Vajna and is directed to Junio Hamano and Jeff King for review.

The core issue is that `--follow` currently fails to properly track file renames across merge commits, particularly in subtree merges. The existing implementation only stores the followed path in a single global variable (`opt->diffopt.pathspec`), which gets overwritten when traversing different branches of history, leading to incomplete or incorrect results.

The solution introduces a commit-to-path mapping system using a commit slab (`follow_pathspec_slab`) to track which path should be followed for each commit's parents. This ensures rename detection works correctly regardless of traversal order through merge commits. The implementation:

1. Stores the followed path for each commit in a slab
2. Restores the correct path when visiting each commit
3. For merges, computes the correct path for each parent by running rename detection between the merge and each parent
4. Includes new test cases demonstrating the fixed behavior

The patch removes the documentation note about `--follow` not working well with non-linear history, as this limitation is now addressed. It touches several files including the revision machinery, log tree handling, and adds a new test script.

This appears to be a well-considered solution to a long-standing limitation, with thorough test coverage demonstrating both the subtree merge case and a more complex dual-rename scenario. The implementation follows Git's existing patterns for commit-specific data storage and cleanup.
