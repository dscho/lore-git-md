This is the third and final patch in a feature series adding a `--linearize` option to `git replay`. The option mimics `git rebase --no-rebase-merges` by cherry-picking only non-merge commits, flattening the commit topology into a linear sequence.

The patch implements the core logic: it adds the `--linearize` command-line flag (exposed in `builtin/replay.c`), updates the internal `replay_revisions` function to skip merge commits when the flag is set, and introduces a new test (`t3650-replay-basics.sh`) that verifies the behavior. The commit message and documentation clearly position this as a server-side analogue to `git rebase`'s default mode, aligning with the broader goal of making `git replay` a building block for rebase-like operations.

The implementation is clean and focused. It reuses the existing `pick_regular_commit` helper, extending it with a `replayed_base` parameter to track the previous commit when linearizing. The test case is thorough, checking both the ref update output and the resulting commit graph. The patch also includes a safety check that prevents `--linearize` from being combined with `--revert`, which is a sensible guardrail.

This is a well-crafted feature addition that addresses a real use case (server-side rebase) and integrates smoothly with the existing `git replay` machinery. The series as a whole looks ready for review, and this patch in particular is likely to attract attention from anyone interested in the sequencer or server-side Git operations.
