Thread summary:

Performance investigation into worktree diff operations, initiated by D. Ben Knoble, has identified timestamp precision and index refresh behavior as the root causes of `git diff` slowdowns in secondary worktrees (223.3ms vs 3.4ms in main worktree). The thread has established that racy-git scenarios—where second-granularity timestamps force full content checks via `ie_match_stat`/`ce_modified_check_fs`—are the primary culprit, with `git update-index --refresh` and `USE_NSEC` (nanosecond timestamp precision) both serving as effective but incomplete solutions.

Jeff King (Peff) has now proposed and tested a concrete patch that directly addresses the racy-git entry mechanism he previously identified. The patch modifies `builtin/diff.c` to pass a new `DIFF_RACY_IS_MODIFIED` flag to `ie_match_stat()`, instructing it to treat racy entries as stat-dirty. This ensures they are counted by `diffcore_skip_stat_unmatch()`, triggering the index refresh that persists across subsequent `git diff` invocations. The patch successfully forces index refreshes (subsequent diffs drop from ~500ms to ~30ms), but introduces a performance regression in the first diff (~1800ms vs ~500ms). Peff hypothesizes the slowdown stems from redundant work in `diffcore_skip_stat_unmatch()`'s content check (`diff_filespec_check_stat_unmatch()`), which may be less efficient than `ie_match_stat()`'s (`ce_modified_check_fs()`). While the patch demonstrates a viable path to fixing the core issue, the tradeoff between first-diff slowdown and subsequent-diff speedup remains an open question.

The discussion has evolved through diagnosis (racy-git timestamp limitations), architectural analysis (index refresh/writeback behavior), and implementation tradeoffs (runtime vs build-time precision configuration). Historical context revealed the counter-based guard in `builtin/diff.c` (`1 < rev.diffopt.skip_stat_unmatch`), introduced in commit aecbf914 (2007) to address real-world performance issues. The guard was designed as an optimization to avoid unnecessary index refreshes when no stat-dirty paths existed, acting as both a boolean flag and a counter for "ghost changes" (stat-dirty but content-unchanged paths). While functionally correct, its dual-purpose nature has proven confusing, and its role in preventing index persistence in `git diff` (while allowing it in `git status`) remains a focal point. Peff's patch sidesteps the guard's complexity by ensuring racy entries increment the counter, but the guard's architectural merit is still under debate.

Three solution paths remain under active consideration:
1. **Index refresh fixes**: Peff's patch demonstrates a working implementation of modifying `diffcore_skip_stat_unmatch()` to count racy entries as dirty, though the first-diff performance regression may require further tuning. Alternatives include replacing the counter-based guard with a more explicit refresh mechanism.
2. **Timestamp precision improvements**: Expand `USE_NSEC` support (including Meson build system integration) or implement runtime configuration (e.g., `--use-nsec` flag with platform-specific auto-detection via `uname`/`statfs`).
3. **Runtime configuration**: A hybrid approach combining user control (manual flags) with automated optimization (e.g., detecting btrfs on Linux), while addressing concerns about detection complexity.

Technical details include:
- **Files touched**: `builtin/diff.c` (conditional guard logic, `DIFF_RACY_IS_MODIFIED` flag), diffcore subsystem (`diffcore_skip_stat_unmatch`, `diff_filespec_check_stat_unmatch`), index refresh/writeback paths (`refresh_index_quietly`, `repo_updated_index_if_able`), and `ie_match_stat()`.
- **Key symbols**: `rev.diffopt.skip_stat_unmatch` (counter-based guard), `DIFF_RACY_IS_MODIFIED` (new flag), `diff_auto_refresh_index`, `USE_NSEC`, `st_size` field in index entries.
- **Behavior changes**: Racy entries are now counted as stat-dirty, ensuring index refreshes persist. No on-disk format changes.
- **Performance tradeoffs**: First-diff slowdown (~3.6x) vs. subsequent-diff speedup (~16x).
- **Test coverage**: Performance measurements in worktree scenarios (e.g., `t/perf/p7820-git-diff-worktree.sh`), racy-git test cases, and platform-specific timestamp precision validation.

Open questions:

- Long-term direction: runtime configuration vs build-time `USE_NSEC` vs index refresh fixes, and how these approaches interact with broader project goals (e.g., Rustification, ODB abstraction).
