Thread summary:

Performance investigation into worktree diff operations, initiated by D. Ben Knoble, identified timestamp precision as the root cause of `git diff` slowdowns in secondary worktrees (223.3ms vs 3.4ms in the main worktree). The thread established that racy-git scenarios—where second-granularity timestamps force full content checks via `ie_match_stat`/`ce_modified_check_fs`—are the primary culprit. Solutions explored include `git update-index --refresh`, nanosecond timestamp precision (`USE_NSEC`), and architectural refinements to track or eliminate racy entries. Jeff King (Peff) now advocates for a minimal 8-line patch removing the `#ifdef USE_NSEC` guard in `read-cache.c:is_racy_stat()`, enabling nanosecond-aware timestamp comparisons unconditionally. This resolves the performance issue by leveraging existing infrastructure, but Junio C Hamano raised a correctness edge case: inconsistent nanosecond precision due to kernel inode cache eviction could reintroduce raciness if one entry (file or index) loses precision while the other retains it. Peff narrowed this to a highly specific sequence (file write, inode eviction, re-read within the same second as index write) and considers the risk minimal on Linux.

D. Ben Knoble’s follow-up frames the user-facing tradeoffs: Peff’s patch slows the first `git diff` (~1800ms vs ~500ms baseline) but speeds up subsequent ones (~30ms vs ~500ms), a tradeoff he accepts for shell prompt consistency. He highlights two open areas: (1) an unexplained 800ms gap in the first-diff regression, suggesting `diffcore_skip_stat_unmatch()`’s content check may be slower than `ie_match_stat()`’s, and (2) reducing racy entries at initial index write, tying this to broader `USE_NSEC` adoption (e.g., via Meson). Knoble’s email clarifies that manual workarounds like `git status` are undesirable, reinforcing the need for a solution that balances performance, correctness, and usability.

Technical details:
- **Files touched**: `read-cache.c` (`is_racy_stat`, `ie_match_stat`), with potential future changes to `builtin/diff.c` (conditional guard logic) or diffcore subsystem.
- **Key symbols**: `is_racy_stat()` (now unconditionally nanosecond-aware), `ie_match_stat()`, `rev.diffopt.skip_stat_unmatch`, `USE_NSEC`, `st_size` field in index entries, `diffcore_skip_stat_unmatch()`, `diff_filespec_check_stat_unmatch()`.
- **Behavior changes**: Racy entries are eliminated when nanosecond precision is available, but edge cases involving kernel inode cache eviction may reintroduce raciness under highly specific conditions. First-diff performance regression (~1800ms) observed due to `DIFF_RACY_IS_MODIFIED` logic.
- **Performance impact**: Resolves worktree diff slowdown (223.3ms → 3.4ms) in most cases, but first-diff regression remains unexplained. Correctness under high filesystem activity unvalidated.
- **Test coverage**: Performance measurements in worktree scenarios (`t/perf/p7820-git-diff-worktree.sh`), racy-git test cases, and platform-specific timestamp precision validation. Additional testing under kernel inode cache stress recommended.

Open questions:
- Whether Peff’s patch introduces correctness issues under Junio’s edge case (inconsistent nanosecond precision due to kernel cache eviction), and how to validate this on Linux and other platforms.
- Root cause of the first-diff performance regression (~1800ms vs expected ~1000ms), specifically whether `diff_filespec_check_stat_unmatch()` is inherently slower than `ce_modified_check_fs()`.
- Whether Junio’s `istate` field proposal (tracking racy entries for auto-refresh) remains relevant as a fallback or architectural refinement.
- Long-term direction for the counter-based guard in `builtin/diff.c` (`rev.diffopt.skip_stat_unmatch`), and whether it can be removed or simplified if timestamp precision is universally reliable.
- Platform-specific safety of unconditional `USE_NSEC`, particularly on non-Linux systems where kernel inode cache behavior may differ.

Participant positions:
