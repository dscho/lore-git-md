Thread summary:

Performance investigation into worktree diff operations, initiated by D. Ben Knoble, identified timestamp precision as the root cause of `git diff` slowdowns in secondary worktrees (223.3ms vs 3.4ms in the main worktree). The thread established that racy-git scenarios—where second-granularity timestamps force full content checks via `ie_match_stat`/`ce_modified_check_fs`—are the primary culprit. Solutions explored include `git update-index --refresh`, nanosecond timestamp precision (`USE_NSEC`), and architectural refinements to track or eliminate racy entries.

Jeff King (Peff) proposed and now prefers a minimal patch that removes the `#ifdef USE_NSEC` guard in `read-cache.c:is_racy_stat()`, enabling nanosecond-aware timestamp comparisons unconditionally. This 8-line change eliminates racy entries at the source by leveraging existing nanosecond precision infrastructure, resolving the performance issue without architectural changes. Testing confirms the problem "goes away" with this approach. However, Junio C Hamano raised a critical edge case: when two files (or a file and the index) are modified within the same millisecond, their nanosecond timestamps might not be equally preserved by the kernel’s in-memory cache. If one entry loses its nanosecond precision (e.g., due to cache eviction) while the other retains it, the comparison could yield incorrect results, potentially reintroducing racy entries. This concern stems from the original rationale for the `USE_NSEC` conditional—avoiding stat-matching failures when the kernel drops nanosecond precision—and suggests the patch may not fully resolve raciness in practice.

Junio’s earlier alternative proposal—adding a field to the `istate` structure to track racy entries for auto-refreshing—remains viable but is now secondary to Peff’s root-cause fix. Junio’s approach avoids propagating flags through the diff machinery and aims to sidestep the first-diff performance regression seen in Peff’s earlier `DIFF_RACY_IS_MODIFIED` patch (1800ms vs 500ms baseline). Historical context revealed the counter-based guard (`1 < rev.diffopt.skip_stat_unmatch`), introduced in commit aecbf914 (2007), as a dual-purpose mechanism that has proven confusing; Peff’s patch sidesteps this complexity entirely, but Junio’s edge case highlights a potential limitation.

Technical details:
- **Files touched**: `read-cache.c` (`is_racy_stat`, `ie_match_stat`), with potential future changes to `builtin/diff.c` (conditional guard logic) or diffcore subsystem.
- **Key symbols**: `is_racy_stat()` (now unconditionally nanosecond-aware), `ie_match_stat()`, `rev.diffopt.skip_stat_unmatch`, `USE_NSEC`, `st_size` field in index entries.
- **Behavior changes**: Racy entries are eliminated when nanosecond precision is available, but edge cases involving kernel inode cache eviction may reintroduce raciness.
- **Performance impact**: Resolves the worktree diff slowdown (223.3ms → 3.4ms) in most cases, but correctness under high filesystem activity remains unvalidated.
- **Test coverage**: Performance measurements in worktree scenarios (e.g., `t/perf/p7820-git-diff-worktree.sh`), racy-git test cases, and platform-specific timestamp precision validation. Additional testing under conditions that stress the kernel’s inode cache (e.g., high filesystem load) is now required.

Open questions:
- Whether Peff’s patch introduces correctness issues under Junio’s edge case (inconsistent nanosecond precision due to kernel cache eviction), and how to validate this.
- Whether Junio’s `istate` field proposal remains relevant as a fallback or architectural refinement, given the edge case.
- Long-term direction for the counter-based guard in `builtin/diff.c`, and whether it can be removed or simplified if timestamp precision is universally reliable.
