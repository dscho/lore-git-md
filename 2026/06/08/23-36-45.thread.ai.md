Thread summary:

Performance investigation into worktree diff operations, initiated by D. Ben Knoble, has identified timestamp precision and index refresh behavior as the root causes of `git diff` slowdowns in secondary worktrees (223.3ms vs 3.4ms in main worktree). The thread has established that racy-git scenarios—where second-granularity timestamps force full content checks via `ie_match_stat`/`ce_modified_check_fs`—are the primary culprit, with `git update-index --refresh` and `USE_NSEC` (nanosecond timestamp precision) both serving as effective but incomplete solutions.

Jeff King (Peff) proposed and tested a patch modifying `builtin/diff.c` to pass a new `DIFF_RACY_IS_MODIFIED` flag to `ie_match_stat()`, treating racy entries as stat-dirty to ensure they are counted by `diffcore_skip_stat_unmatch()`. While this forces index refreshes (subsequent diffs drop from ~500ms to ~30ms), it introduces a first-diff performance regression (~1800ms vs ~500ms), likely due to redundant work in `diff_filespec_check_stat_unmatch()`. Junio C Hamano now suggests a simpler alternative: leveraging `USE_NSEC` to eliminate racy entries at the source by delaying index writes by 50 milliseconds when nanosecond resolution is available. This would resolve raciness without architectural changes to the diff machinery or counter-based guard, reframing the solution toward timestamp precision as the primary lever.

The discussion has evolved through diagnosis (racy-git timestamp limitations), architectural analysis (index refresh/writeback behavior), and implementation tradeoffs (runtime vs build-time precision configuration). Historical context revealed the counter-based guard in `builtin/diff.c` (`1 < rev.diffopt.skip_stat_unmatch`), introduced in commit aecbf914 (2007) to address real-world performance issues. While functionally correct, its dual-purpose nature (acting as both a boolean flag and a counter for "ghost changes") has proven confusing, and its role in preventing index persistence in `git diff` (while allowing it in `git status`) remains debated. Peff's patch sidesteps the guard's complexity, but Junio's proposal questions whether architectural changes are necessary if timestamp precision can address the root cause.

Three solution paths remain under active consideration:
1. **Index refresh fixes**: Peff's patch demonstrates a working implementation, though the first-diff performance regression may require further optimization (e.g., avoiding redundant content checks in `diffcore_skip_stat_unmatch()`). Alternatives include replacing the counter-based guard with a more explicit refresh mechanism.
2. **Timestamp precision improvements**: Junio's proposal to delay index writes when `USE_NSEC` is available, eliminating racy entries at the source. This could be implemented as a build-time or platform-specific solution, with potential expansion of `USE_NSEC` support (including Meson build system integration).
3. **Runtime configuration**: A hybrid approach combining user control (manual flags) with automated optimization (e.g., detecting btrfs on Linux), as proposed by brian m. carlson. This path addresses concerns about detection complexity and spurious diffs in plumbing commands.

Technical details include:
- **Files touched**: `builtin/diff.c` (conditional guard logic, `DIFF_RACY_IS_MODIFIED` flag, potential index write delays), diffcore subsystem (`diffcore_skip_stat_unmatch`, `diff_filespec_check_stat_unmatch`), index refresh/writeback paths (`refresh_index_quietly`, `repo_updated_index_if_able`), and `ie_match_stat()`.
- **Key symbols**: `rev.diffopt.skip_stat_unmatch` (counter-based guard), `DIFF_RACY_IS_MODIFIED` (Peff's flag), `diff_auto_refresh_index`, `USE_NSEC`, `st_size` field in index entries, and potential new logic for delayed index writes.
- **Behavior changes**: Peff's patch counts racy entries as stat-dirty, ensuring index refreshes persist. Junio's proposal would eliminate racy entries entirely when nanosecond precision is available. No on-disk format changes.
- **Performance tradeoffs**: Peff's patch shows first-diff slowdown (~3.6x) vs. subsequent-diff speedup (~16x). Junio's approach aims to avoid such tradeoffs by addressing raciness at the source.
- **Test coverage**: Performance measurements in worktree scenarios (e.g., `t/perf/p7820-git-diff-worktree.sh`), racy-git test cases, and platform-specific timestamp precision validation.
