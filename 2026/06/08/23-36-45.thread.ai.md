Thread summary:

Performance investigation into worktree diff operations, initiated by D. Ben Knoble, has identified timestamp precision as the root cause of `git diff` slowdowns in secondary worktrees (223.3ms vs 3.4ms in main worktree). The thread has established that racy-git scenarios—where second-granularity timestamps force full content checks via `ie_match_stat`/`ce_modified_check_fs`—are the primary culprit, with `git update-index --refresh` and nanosecond timestamp precision (`USE_NSEC`) both serving as effective solutions.

Jeff King (Peff) has explored multiple approaches to address the issue. His latest patch removes the `#ifdef USE_NSEC` guard in `read-cache.c:is_racy_stat()`, enabling nanosecond-aware timestamp comparisons unconditionally. This minimal change (8 lines removed, 1 line added) eliminates racy entries at the source by leveraging existing nanosecond precision infrastructure, resolving the performance issue without architectural changes or performance tradeoffs. Testing shows the problem "goes away" with this approach. Peff now considers this the preferred solution, though he remains open to Junio C Hamano’s alternative proposal: adding a new field to the `istate` (index state) structure to track when `ie_match_stat()` encounters racy entries that would benefit from auto-refreshing. This would allow the "skip-stat-unmatch" logic to consider these entries without requiring a disruptive flag to propagate through the diff machinery. Junio’s proposal avoids the first-diff performance regression seen in Peff’s earlier `DIFF_RACY_IS_MODIFIED` patch, which modified `builtin/diff.c` to pass a flag treating racy entries as stat-dirty (~1800ms first-diff regression vs ~500ms baseline, though subsequent diffs improved from ~500ms to ~30ms).

The discussion has evolved through diagnosis (racy-git timestamp limitations), architectural analysis (index refresh/writeback behavior), and design refinements (tracking racy entries in `istate` vs. eliminating them at the source). Historical context revealed the counter-based guard (`1 < rev.diffopt.skip_stat_unmatch`), introduced in commit aecbf914 (2007) to address real-world performance issues, though its dual-purpose nature (acting as both a boolean flag and a counter for "ghost changes") has proven confusing. Peff’s latest patch sidesteps this complexity by eliminating racy entries entirely, while Junio’s proposal refines the architectural approach to avoid propagating flags through the diff machinery.

Two solution paths remain under active consideration:
1. **Timestamp precision improvements**: Peff’s latest patch, which enables nanosecond-aware timestamp comparisons unconditionally. This is the simplest and most fundamental fix, leveraging existing infrastructure and avoiding performance tradeoffs. Peff now explicitly prefers this approach.
2. **Index state tracking**: Junio’s proposed `istate` field to track racy entries, avoiding the need for a new flag while maintaining the same goal of ensuring racy entries are counted as stat-dirty. Peff acknowledges this as "fairly clean" but secondary to his root-cause fix.

A previously proposed runtime configuration approach (brian m. carlson) is now irrelevant given the effectiveness of Peff’s latest patch. Peff also addressed Junio’s question about `refresh_index_quietly()` in `cmd_diff()`, noting its current placement is harmless and that `--no-optional-locks` (which would conflict with index refreshes) is rarely used with `git diff`.

Technical details include:
- **Files touched**: `read-cache.c` (`is_racy_stat`, `ie_match_stat`), `builtin/diff.c` (conditional guard logic, potential `istate` field), and diffcore subsystem (`diffcore_skip_stat_unmatch`, `diff_filespec_check_stat_unmatch`).
- **Key symbols**: `is_racy_stat()` (now unconditionally nanosecond-aware in Peff’s latest patch), `ie_match_stat()`, `rev.diffopt.skip_stat_unmatch` (counter-based guard), `DIFF_RACY_IS_MODIFIED` (Peff’s earlier flag), `USE_NSEC`, `st_size` field in index entries, and the proposed `istate` field for tracking racy entries.
- **Behavior changes**: Racy entries are eliminated at the source when nanosecond precision is available (Peff’s latest patch), or tracked for auto-refresh (Junio’s proposal). No on-disk format changes.
- **Performance impact**: Peff’s latest patch resolves the worktree diff slowdown without introducing performance tradeoffs. Junio’s proposal aims to avoid the first-diff regression seen in Peff’s earlier approach.
- **Test coverage**: Performance measurements in worktree scenarios (e.g., `t/perf/p7820-git-diff-worktree.sh`), racy-git test cases, and platform-specific timestamp precision validation.

Open questions:
- Whether Peff’s latest patch introduces any hidden edge cases, given the original `USE_NSEC` conditional’s purpose (avoiding stat-matching failures when the kernel’s in-memory cache dropped nanosecond precision).
- Whether Junio’s `istate` field proposal would avoid the first-diff performance regression seen in Peff’s earlier patch, and how it compares to Peff’s latest patch in terms of simplicity and maintainability.
- Long-term direction: whether the counter-based guard in `builtin/diff.c` should be replaced with a more explicit refresh mechanism, given that timestamp precision now addresses the root cause.

Participant positions:
- **Jeff King**: Prefers addressing raciness at the source via his nanosecond-precision patch, which eliminates racy entries unconditionally. Open to Junio’s `istate` proposal as a fallback but considers it secondary. Dismissed concerns about `refresh_index_quietly()` as irrelevant in practice.
- **Junio C Hamano**: Favors addressing raciness at the source but proposed the `istate` field as a cleaner architectural alternative to Peff’s earlier flag-based approach. Prefers solutions that avoid propagating flags through the diff machinery.
- **D. Ben Knoble**: Established the performance baseline; likely to support the most effective solution (currently Peff’s latest patch).
- **brian m. carlson**: Proposed a runtime configuration mechanism, now irrelevant.
