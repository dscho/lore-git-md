Thread summary:

Performance investigation into worktree diff operations, initiated by D. Ben Knoble, identified timestamp precision as the root cause of `git diff` slowdowns in secondary worktrees (223.3ms vs 3.4ms in the main worktree). The thread established that racy-git scenarios—where second-granularity timestamps force full content checks via `ie_match_stat`/`ce_modified_check_fs`—are the primary culprit. Solutions explored include `git update-index --refresh`, nanosecond timestamp precision (`USE_NSEC`), and architectural refinements to track or eliminate racy entries.

Jeff King (Peff) proposed and now advocates for a minimal patch that removes the `#ifdef USE_NSEC` guard in `read-cache.c:is_racy_stat()`, enabling nanosecond-aware timestamp comparisons unconditionally. This 8-line change eliminates racy entries at the source by leveraging existing nanosecond precision infrastructure, resolving the performance issue without architectural changes. Testing confirms the problem "goes away" with this approach. However, Junio C Hamano raised a correctness edge case: when two files (or a file and the index) are modified within the same millisecond, their nanosecond timestamps might not be equally preserved by the kernel’s inode cache. If one entry loses its nanosecond precision (e.g., due to cache eviction) while the other retains it, the comparison could yield incorrect results, potentially reintroducing racy entries. Peff’s follow-up clarifies that the failure mode is benign in one direction (index mtime appearing truncated) but concedes a theoretical risk in the reverse (file mtime truncated while index retains precision). He narrows the edge case to a highly specific sequence—file write, inode eviction, and re-read within the same second as the index write—while the index’s inode remains cached. Though possible, he considers this unlikely enough to justify making `USE_NSEC` unconditional on Linux, where he suspects the behavior is now reliable.

Junio’s earlier alternative proposal—adding a field to the `istate` structure to track racy entries for auto-refreshing—remains viable but is now secondary to Peff’s root-cause fix. Junio’s approach avoids propagating flags through the diff machinery and aims to sidestep the first-diff performance regression seen in Peff’s earlier `DIFF_RACY_IS_MODIFIED` patch (1800ms vs 500ms baseline). Historical context revealed the counter-based guard (`1 < rev.diffopt.skip_stat_unmatch`), introduced in commit aecbf914 (2007), as a dual-purpose mechanism that has proven confusing; Peff’s patch sidesteps this complexity entirely, but Junio’s edge case highlights a potential limitation.

Technical details:
- **Files touched**: `read-cache.c` (`is_racy_stat`, `ie_match_stat`), with potential future changes to `builtin/diff.c` (conditional guard logic) or diffcore subsystem.
- **Key symbols**: `is_racy_stat()` (now unconditionally nanosecond-aware), `ie_match_stat()`, `rev.diffopt.skip_stat_unmatch`, `USE_NSEC`, `st_size` field in index entries.
- **Behavior changes**: Racy entries are eliminated when nanosecond precision is available, but edge cases involving kernel inode cache eviction may reintroduce raciness under highly specific conditions.
- **Performance impact**: Resolves the worktree diff slowdown (223.3ms → 3.4ms) in most cases. Correctness under high filesystem activity remains unvalidated, though Peff considers the risk minimal on Linux.
- **Test coverage**: Performance measurements in worktree scenarios (e.g., `t/perf/p7820-git-diff-worktree.sh`), racy-git test cases, and platform-specific timestamp precision validation. Additional testing under conditions that stress the kernel’s inode cache (e.g., high filesystem load) is now recommended, though not yet implemented.

Open questions:
- Whether Peff’s patch introduces correctness issues under Junio’s edge case (inconsistent nanosecond precision due to kernel cache eviction), and how to validate this on Linux and other platforms.
- Whether Junio’s `istate` field proposal remains relevant as a fallback or architectural refinement, given the narrowed edge case.
- Long-term direction for the counter-based guard in `builtin/diff.c`, and whether it can be removed or simplified if timestamp precision is universally reliable.
- Platform-specific safety of unconditional `USE_NSEC`, particularly on non-Linux systems where kernel inode cache behavior may differ.

Participant positions:
- **Jeff King**: Advocates for addressing raciness at the source via his nanosecond-precision patch, arguing the edge case is benign in one direction and improbable in the other. Leans toward making `USE_NSEC` unconditional on Linux but acknowledges platform-specific concerns.
- **Junio C Hamano**: Acknowledged Peff’s patch as elegant and effective ("That's cute") but raised a substantive correctness concern about kernel inode cache behavior. Earlier favored the `istate` field as a cleaner alternative but has not rejected Peff’s patch outright.
- **D. Ben Knoble**: Established the performance baseline; likely to support the most effective solution, but correctness remains a priority.
- **brian m. carlson**: Proposed a runtime configuration mechanism, now irrelevant.
