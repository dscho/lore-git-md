Thread summary:

Performance investigation into worktree diff operations, initiated by D. Ben Knoble, has identified timestamp precision as the root cause of `git diff` slowdowns in secondary worktrees (223.3ms vs 3.4ms in main worktree). The thread has established that racy-git scenarios—where second-granularity timestamps force full content checks via `ie_match_stat`/`ce_modified_check_fs`—are the primary culprit, with `git update-index --refresh` and nanosecond timestamp precision (`USE_NSEC`) both serving as effective solutions.

Jeff King (Peff) has explored multiple approaches to address the issue. His initial patch modified `builtin/diff.c` to pass a `DIFF_RACY_IS_MODIFIED` flag to `ie_match_stat()`, treating racy entries as stat-dirty to ensure they are counted by `diffcore_skip_stat_unmatch()`. While this forced index refreshes (subsequent diffs dropped from ~500ms to ~30ms), it introduced a first-diff performance regression (~1800ms vs ~500ms), likely due to redundant work in `diff_filespec_check_stat_unmatch()`. His second patch removes the `#ifdef USE_NSEC` guard in `read-cache.c:is_racy_stat()`, enabling nanosecond-aware timestamp comparisons unconditionally. This minimal change (8 lines removed, 1 line added) eliminates racy entries at the source by leveraging existing nanosecond precision infrastructure, resolving the performance issue without architectural changes or performance tradeoffs. Testing shows the problem "goes away" with this approach. Junio C Hamano has proposed an alternative design to Peff’s flag-based approach: adding a new field to the `istate` (index state) structure to track when `ie_match_stat()` encounters racy entries that would benefit from auto-refreshing. This would allow the "skip-stat-unmatch" logic to consider these entries without requiring a disruptive flag to propagate through the diff machinery. Junio also questioned the necessity of the existing `refresh_index_quietly()` call in `cmd_diff()` for tree-to-tree comparisons, though he acknowledged it is harmless.

The discussion has evolved through four phases: diagnosis (racy-git timestamp limitations), architectural analysis (index refresh/writeback behavior and the counter-based guard in `builtin/diff.c`), implementation tradeoffs (runtime vs build-time precision configuration), and design refinements (tracking racy entries in `istate`). Historical context revealed the counter-based guard (`1 < rev.diffopt.skip_stat_unmatch`), introduced in commit aecbf914 (2007) to address real-world performance issues, though its dual-purpose nature (acting as both a boolean flag and a counter for "ghost changes") has proven confusing. Peff’s latest patch sidesteps the guard’s complexity entirely by eliminating racy entries at the source, while Junio’s proposal refines the architectural approach to avoid propagating flags through the diff machinery.

Three solution paths remain under active consideration:
1. **Timestamp precision improvements**: Peff’s latest patch, which enables nanosecond-aware timestamp comparisons unconditionally. This is the simplest and most fundamental fix, leveraging existing infrastructure and avoiding performance tradeoffs.
2. **Index state tracking**: Junio’s proposed `istate` field to track racy entries, avoiding the need for a new flag while maintaining the same goal of ensuring racy entries are counted as stat-dirty.
3. **Index refresh fixes**: Peff’s earlier `DIFF_RACY_IS_MODIFIED` patch, which remains viable but introduces a first-diff performance regression and requires architectural changes to the diff machinery. Further optimization (e.g., avoiding redundant content checks in `diffcore_skip_stat_unmatch()`) may be needed if this path is pursued.

A previously proposed runtime configuration approach (brian m. carlson) is now less relevant given the effectiveness of Peff’s latest patch, though it may resurface if platform-specific edge cases emerge.

Open questions:

- Long-term direction: whether the counter-based guard in `builtin/diff.c` should be replaced with a more explicit refresh mechanism, given that timestamp precision now addresses the root cause.
- Feasibility of further optimizing Peff’s earlier `DIFF_RACY_IS_MODIFIED` patch to address the first-diff performance regression, should the timestamp precision approach encounter unforeseen issues.
