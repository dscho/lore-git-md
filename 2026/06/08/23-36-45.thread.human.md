This thread began as an investigation into why `git diff` runs dramatically slower in secondary worktrees (223ms vs 3.4ms) and has now narrowed in on how Git handles index refreshes and timestamp precision. D. Ben Knoble’s latest findings show that while `git diff` does refresh the index internally, a long-standing conditional guard appears to prevent the refreshed state from being written back to disk—effectively leaving the performance problem unsolved. This contrasts with `git status`, which explicitly persists its refreshed index.

The root cause remains racy-git scenarios where second-granularity timestamps force Git to perform expensive full-content checks. Earlier in the thread, enabling nanosecond precision (`USE_NSEC`) at build time was shown to resolve the slowdown, but Knoble now sees this as a temporary workaround rather than a proper fix. The discussion has since shifted toward runtime configuration of timestamp precision, with brian m. carlson proposing a mechanism that would let users or scripts opt into nanosecond support without requiring a rebuild. Jeff King and Junio C Hamano have both weighed in on the trade-offs between runtime flexibility and the complexity of auto-detection.

The immediate next step appears to be Knoble’s planned patch to add `USE_NSEC` support to the Meson build system, though the thread’s participants seem to agree that a runtime-configurable solution would be preferable in the long run. The open question—why `git diff`’s refresh doesn’t persist—remains unresolved, and the conditional guard Knoble identified may be the key to a more permanent fix.
