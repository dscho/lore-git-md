Initial profiling showed the slowdown occurring in stat checking and data conversion paths, with the issue traceable back to Git v2.50.0.

Jeff King has now provided crucial context, identifying this as a manifestation of Git's longstanding "racy git" behavior rather than a worktree-specific regression. His analysis reveals the slowdown occurs when files share modification times with their index entries, forcing full content checks. Interestingly, his tests showed worktrees sometimes performing *better* than the main worktree (20ms vs 189ms in his Linux kernel repo test case).

King points to the documented racy-git behavior and suggests enabling USE_NSEC at build time for finer-grained timestamps, which could reduce unnecessary content checks. This shifts the focus from potential worktree optimizations to a more fundamental aspect of Git's timestamp-based change detection. The discussion now centers on whether build configuration changes (USE_NSEC) could mitigate the issue rather than requiring code changes to the worktree subsystem.
