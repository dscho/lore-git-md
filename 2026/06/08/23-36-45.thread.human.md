This thread investigates a puzzling performance issue where `git diff` operations in secondary worktrees run 10x slower than in the main worktree. D. Ben Knoble initially reported the problem, with Jeff King (Peff) providing key technical analysis identifying it as a classic "racy git" scenario - when files and index entries share modification timestamps (to second precision), Git must perform expensive content checks to ensure safety.

The discussion has evolved through several key realizations: first, that manually refreshing the index with `git update-index --refresh` resolves the slowdown, confirming the racy-git diagnosis. Then, deeper investigation revealed that while `git diff` does refresh internally, it may not persist those updates, unlike `git status`. The core issue stems from timestamp precision - when operations occur within the same second, Git can't reliably determine what changed. 

Peff provided historical context about the USE_NSEC build option (introduced in 2009) that enables nanosecond-precision timestamps to avoid these situations. The conversation is now exploring whether to: 1) make timestamp precision configurable at runtime rather than build-time, 2) change how worktrees initialize their indexes, or 3) modify when diffs persist refreshed indexes. While automatic index refreshes offer a band-aid, the more fundamental solution likely involves improving timestamp handling, though this may require careful consideration of backward compatibility and platform support. The thread remains technical and solution-oriented, with both contributors focused on understanding the full implications before proposing specific changes.
