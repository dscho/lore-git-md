The worktree diff performance thread has centered on a slowdown in `git diff` operations within secondary worktrees—223.3ms versus 3.4ms in the main worktree—caused by timestamp precision limitations triggering unnecessary content checks. Jeff King (Peff) proposed a minimal fix: removing the `#ifdef USE_NSEC` guard in `read-cache.c` to enable nanosecond-aware timestamp comparisons unconditionally. This 8-line change resolves the performance issue by eliminating racy entries at their source, leveraging existing infrastructure. Testing confirmed the fix works, but Junio C Hamano raised a correctness concern: if the kernel’s inode cache evicts nanosecond precision for one entry (e.g., a file) while retaining it for another (e.g., the index), comparisons could yield false negatives, reintroducing raciness.

Peff has now responded to Junio’s edge case, acknowledging its validity but arguing the failure mode is benign. If the index’s mtime appears truncated, Git errs conservatively by treating the file as racy—a correct behavior. The reverse scenario (a file’s mtime appearing truncated while the index retains precision) is theoretically possible but improbable, requiring a highly specific sequence: a file is written, its inode is evicted, and it is re-read from disk—all within the same second the index is written—while the index’s inode remains cached. Peff considers this edge case unlikely enough to justify making `USE_NSEC` unconditional on Linux, where he believes the behavior is now reliable. He references platform-specific discussions with Patrick Steinhardt but does not propose a revised patch or testing plan.
