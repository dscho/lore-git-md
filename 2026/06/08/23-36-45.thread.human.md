This thread began with D. Ben Knoble reporting a puzzling 10x slowdown in `git diff` operations within secondary worktrees, where profiling showed excessive time spent in stat checks. Jeff King reoriented the discussion by identifying this as a manifestation of Git's longstanding "racy git" problem - when files share modification times with index entries, Git must perform expensive content checks to ensure correctness. King demonstrated this isn't worktree-specific and suggested enabling nanosecond-precision timestamps (USE_NSEC) at build time as a deeper solution.

In the latest exchange, Knoble confirms that manually refreshing the index (`git update-index --refresh`) resolves the slowdown, validating King's diagnosis. The discussion has now branched into exploring both tactical and strategic fixes: whether `git diff` should automatically refresh the index in these cases (though this might mask the root issue), and whether new worktrees should perform an index refresh during creation to avoid entering the racy state. Knoble is also investigating how to properly support the USE_NSEC option in Git's Meson build system, which currently lacks explicit configuration for this timestamp precision setting. The collaborative analysis has moved from initial symptom reporting to evaluating multiple solution paths that address both immediate usability concerns and the underlying filesystem timestamp precision limitations.
