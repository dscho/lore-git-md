This thread started as a performance investigation into why `git diff` runs dramatically slower in secondary worktrees (223ms vs 3ms in the main worktree). Jeff King traced the issue to timestamp precision: when Git’s timestamps only have second-level granularity, the racy-git detection logic forces full content checks on every file during diff operations. D. Ben Knoble later discovered a puzzling conditional in `builtin/diff.c`—`1 < !!diff_auto_refresh_index`—that seemed to block index refreshes from being written back, potentially explaining why `git diff` stays slow even after refreshing the index internally. Knoble suspected this might be dead code, but Junio C Hamano has now clarified that the guard is actually a counter-based mechanism: it only triggers a refresh if there are *actual* stat-dirty paths without content changes, not just any refresh.

The discussion has narrowed to three potential fixes: (1) making `git diff` persist its index refreshes (the conditional guard is now understood to be working as designed, but its necessity is debated), (2) enabling nanosecond timestamps via `USE_NSEC` (which Meson build support currently lacks), or (3) brian m. carlson’s proposal for runtime timestamp precision configuration, which would let Git auto-detect optimal settings or let users override them. The thread has ruled out the dead-code theory but remains focused on whether the counter-based guard is the right long-term solution or if the entire refresh logic needs rethinking. Jeff King and Junio favor runtime configurability, while Knoble questions whether `USE_NSEC` is the proper fix. No patches have been proposed yet, but the conversation is converging on implementation tradeoffs.
