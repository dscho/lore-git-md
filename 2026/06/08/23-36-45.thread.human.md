The worktree diff performance thread has homed in on a clean solution to the racy-git timestamp issue that was causing `git diff` to slow down dramatically in secondary worktrees—223 ms versus 3 ms in the main worktree. D. Ben Knoble’s investigation traced the problem to second-granularity timestamps, which forced Git to perform expensive full-content checks via `ie_match_stat` and `ce_modified_check_fs`.

Two main fixes have emerged. Jeff King (Peff) initially proposed a patch that added a `DIFF_RACY_IS_MODIFIED` flag to force index refreshes, which eliminated the slowdown for subsequent diffs but introduced a noticeable first-diff regression (1800 ms versus 500 ms). His more recent patch takes a simpler approach: removing the `#ifdef USE_NSEC` guard in `read-cache.c` to enable nanosecond-aware timestamp comparisons unconditionally. This minimal change—just eight lines removed and one added—eliminates racy entries at the source by leveraging existing nanosecond precision, resolving the performance issue without architectural changes or tradeoffs. Testing confirms the problem “goes away” with this approach.

Junio C Hamano has consistently favored addressing raciness at the source, and Peff’s latest patch aligns with that preference. Junio also suggested an alternative design that avoids introducing a new flag by tracking racy entries in the index state (`istate`) structure, which could refine Peff’s earlier approach without the first-diff penalty. The thread has narrowed to two viable paths: Peff’s nanosecond-precision patch, which is simple and effective, and the architectural refinements to index refresh logic. The counter-based guard in `builtin/diff.c`, originally introduced in 2007 to handle real-world performance issues, remains a secondary consideration but may eventually be replaced if timestamp precision proves robust across all platforms. For now, the focus is on validating Peff’s latest patch, which appears to be the front-runner.
