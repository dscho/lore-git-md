The worktree diff performance thread has reached a promising inflection point. D. Ben Knoble initially reported a dramatic slowdown—223.3ms versus 3.4ms—when running `git diff` in secondary worktrees, tracing the issue to timestamp precision limitations that force Git into racy-git scenarios. These scenarios trigger expensive full-content checks via `ie_match_stat` and `ce_modified_check_fs` whenever second-granularity timestamps make it impossible to trust stat information.

Jeff King (Peff) has now proposed what appears to be the most elegant solution yet: a minimal patch that removes the `#ifdef USE_NSEC` guard in `read-cache.c`, enabling nanosecond-aware timestamp comparisons unconditionally. This eight-line change leverages existing infrastructure to eliminate racy entries at their source, resolving the performance issue without architectural tradeoffs or regressions. Testing confirms the problem "goes away" with this approach, and Peff now considers it the preferred fix. Junio C Hamano’s recent reply—"That's cute"—signals mild approval of the simplicity and effectiveness of this solution, though the thread remains open to further validation of edge cases, particularly the original rationale for the `USE_NSEC` conditional.

The discussion has evolved through several phases: diagnosing the root cause (timestamp precision), exploring architectural workarounds (index refreshes, flag propagation), and now converging on a root-cause fix. Peff’s earlier proposal—a `DIFF_RACY_IS_MODIFIED` flag—introduced a first-diff performance regression (~1800ms), which led Junio to suggest an alternative: adding a field to the `istate` structure to track racy entries for auto-refreshing. While Junio’s proposal avoids propagating flags through the diff machinery, Peff’s latest patch sidesteps the issue entirely by eliminating racy entries upfront. The thread’s focus is now shifting toward confirming whether this unconditional use of nanosecond precision introduces any hidden edge cases, such as stat-matching failures on platforms where the kernel’s in-memory cache drops nanosecond precision. For now, the path forward appears to favor Peff’s patch, with Junio’s `istate` proposal serving as a fallback if validation uncovers issues.
