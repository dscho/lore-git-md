This is a feature patch series introducing a `--linearize` option to `git replay` to flatten merge commits, mirroring `git rebase --no-rebase-merges`. The series consists of three patches: two refactoring preparatory changes and the main implementation. Toon Claes is the author, with help from Johannes Schindelin (Dscho), who also contributes the first patch.

The motivation is to provide an alternative to Dscho’s earlier series (pull.2106) that implemented full merge replay in `git replay`. This series instead linearizes merges, which is the default behavior in `git rebase`. The new `--linearize` option is added only to `git replay`, not `git history`, as the author sees no clear use case for the latter. The cover letter notes potential conflicts with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series, but expects them to be trivial to resolve.

The refactoring patches restructure `enum replay_mode` into a boolean and add a helper function for mapping commits, setting up the main change. The core patch introduces the `--linearize` option, updates the documentation, and adds tests in `t3650-replay-basics.sh`. The implementation touches `replay.c`, `replay.h`, `builtin/replay.c`, and the man page.

Key technical details: the new option is exposed as `--linearize` in `git replay`, the internal logic is controlled by a boolean flag (`linearize`), and the test suite verifies the behavior. The series is based on commit `9ac3f193c05c` and has a change-id `20260604-toon-git-replay-drop-merges-807fa008d395`.

The cover letter positions this as a simpler alternative to Dscho’s merge-replay work, suggesting the two approaches could coexist. No prior discussion or review feedback is included in the input, so the series appears to be an initial RFC. The tone is collaborative, inviting feedback on whether `--linearize` should also be added to `git history`.
