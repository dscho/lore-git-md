This is a follow-up in the `git history drop` series discussion, focusing on the `reset_head()` API design. Patrick Steinhardt responds to Phillip Wood's substantive review feedback about making HEAD updates opt-in rather than opt-out in the reset machinery.

Patrick acknowledges Phillip's point about the awkwardness of the current API design where `RESET_HEAD_SKIP_REF_UPDATES` interacts with `RESET_HEAD_UPDATE_ORIG_HEAD`, but notes that reversing the logic would require handling edge cases where HEAD updates are disabled while ORIG_HEAD updates are enabled - a combination he considers "somewhat weird". On the naming question, Patrick suggests `reset_working_tree()` as a potential alternative that keeps "reset" terminology while better reflecting the function's behavior.

However, Patrick proposes deferring these API changes to a follow-up series, as the current patch set has already grown significantly in scope with the `reset_head()` refactoring. He leaves the door open for Phillip to push back if these changes are considered essential for the current series. This represents a pragmatic decision to keep the series focused while acknowledging the validity of the API design concerns raised.
