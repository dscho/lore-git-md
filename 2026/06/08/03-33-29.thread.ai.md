Subject: ref-filter optimization for --contains/--no-contains ancestry checks

Core optimization: Unifying and accelerating commit ancestry checking for ref-filter operations (`git branch --contains`, `git for-each-ref --contains` etc.) by reusing the memoized traversal algorithm previously only used by `git tag --contains`. The new approach caches positive/negative results across reference checks rather than performing independent graph walks per ref.

Key technical details:
- Replaces separate tag-specific algorithm with unified implementation in ref-filter.c and commit-reach.c
- Handles commit graph cycles (from replacement refs) via fallback to cycle-safe `repo_is_descendant_of()`
- Makes ancestry parsing failures consistently fail rather than sometimes matching
- Uses CONTAINS_IN_PROGRESS for cycle detection
- Adds tests for cycle handling and error cases

Performance impact: Up to 223x faster in benchmark case with 62,174 remote-tracking refs, substantively improving workflows using --contains filtering on repos with many refs.

Implementation history: Builds on prior work from 2011, 2015 and 2018 discussions, finally unifying the implementations as previously suggested. Patch appears to be first submission of this optimization.
