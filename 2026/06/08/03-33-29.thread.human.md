This thread discusses optimizing the ancestry checks used by ref-filter operations like `git branch --contains` and `git for-each-ref --contains`. The initial proposal unified the implementation with the faster algorithm previously only used by `git tag --contains`, showing dramatic speed improvements (up to 223x faster with many refs). Karthik Nayak reviewed the changes positively, and the author split the work into two patches addressing cycle handling and the broader ref-filter integration.

Jeff King (Peff) has now raised deeper technical considerations. While acknowledging the impressive speedups, he notes the original separate implementations existed for good reason - the tag-specific algorithm can be slower than breadth-first in certain cases, particularly when generation numbers are unavailable and the merge base is nearby. He suggests dynamically choosing the algorithm based on generation number availability. Peff also questions whether cycle handling should be addressed separately first, as it affects existing behavior, and whether the proposed in-progress commit tracking is the best approach. His review highlights potential regression cases in deep histories with few branches when generation numbers are missing.

The discussion has progressed from initial implementation to nuanced tradeoffs between performance and correctness across different repository topologies. While the optimization shows clear benefits, Peff's review indicates more work may be needed to handle edge cases optimally before the changes can be finalized.
