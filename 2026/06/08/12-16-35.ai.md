This is a substantive review from Junio C Hamano on the proposed behavior change for `git history reword`. The email challenges the technical rationale behind making `git history reword` abort when the commit message is unchanged, while also offering broader philosophical commentary on similar commands like `git commit --amend` and `git rebase -i`.

Junio makes several key points:
1. The current behavior of updating committer timestamp/identity (even with no message change) is an important effect that users may rely on
2. Consistency between similar commands (reword/amend/rebase) matters more than `git history`'s additional capabilities
3. The "better" design might be to *not* rewrite commits by default when unchanged, with a `--force` option - but changing this now would break established behavior

He notes this is particularly relevant when working with difficult collaborators where even small changes to their commits could cause friction. The review suggests `git rebase -i`'s `--update-refs` might already provide similar branch-updating capabilities to what `git history` offers.

This review shifts the discussion from a narrow implementation question to broader design considerations about commit rewriting behavior across Git's toolset. Junio's perspective as maintainer carries significant weight here, suggesting the patch may need rethinking to align with Git's established patterns rather than introducing new inconsistency.
