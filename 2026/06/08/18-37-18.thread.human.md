The `git replay --linearize` feature, recently merged to the 'master' branch, has hit a snag. Johannes Schindelin identified a regression in the v5 implementation that causes commits to be silently dropped when replaying a single branch containing merge commits. For example, replaying `master~2..master` with `--linearize` now replays only the tip commit directly onto the `--onto` target, omitting intermediate commits like "Git 2.55-rc2" entirely. This breaks the expected behavior, which should preserve all commits in a linearized sequence.

The issue stems from v5's fix for `--onto` edge cases, which inadvertently removed the `replayed_base` logic that maintained the linearized history of a single branch. Schindelin argues that the only consistent design for `--linearize` is to flatten all replayed commits into a single sequence, as preserving branch independence would lead to surprises when branches share history. He suggests the current logic may need to be reverted or redesigned to handle both single-branch and multi-branch cases correctly.

This is a high-priority concern, as it involves silent data loss in a merged feature. The regression wasn't caught by existing tests, revealing a gap in coverage for single-branch merge scenarios. Toon Claes, the series author, will likely need to address this promptly, possibly by restoring the `replayed_base` logic or proposing an alternative solution that avoids the data loss while maintaining the intended functionality. Junio Hamano and Phillip Wood, who previously identified a separate behavioral edge case with merge commit divergence, may weigh in on whether this regression affects their earlier analysis.
