This thread is about the fourth iteration of a three-patch series introducing a `--linearize` option to `git replay`, which flattens merge commits into linear history. The series is technically complete and has incorporated all feedback except for two architectural concerns, both centered on the first patch.

The core goal is to provide server-side functionality equivalent to `git rebase --no-rebase-merges`. Patch 1 refactored `replay.c` to replace an `enum replay_mode` with a boolean `reverse` flag, aiming to simplify code by eliminating redundant checks. However, Junio Hamano and Patrick Steinhardt have raised concerns that this boolean approach obscures the meaning at callsites (e.g., `create_commit(..., true)`) and may limit future extensibility if a third replay mode is ever needed. Toon Claes, the author, has acknowledged these concerns and agreed to revisit the patch, though no concrete alternative has been proposed yet.

Patches 2 and 3 are uncontroversial. Patch 2 introduced getter/setter helpers for the `replayed_commits` khash map, improving code clarity, while Patch 3 implements the `--linearize` functionality with comprehensive test coverage and documentation. Junio had previously indicated the series would merge to `next` once the architectural concerns were resolved, and Johannes Schindelin has signed off on all patches. The series is now awaiting a fifth iteration to address the boolean refactoring debate before it can proceed.
