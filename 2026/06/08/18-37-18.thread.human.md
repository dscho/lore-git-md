The `git replay --linearize` series was merged to `master` on July 15, but two critical issues have since emerged, sparking a heated design debate. The most urgent problem is a **silent commit-dropping regression** in single-branch replay: when linearizing a branch with merges, only the tip commit is preserved, while intermediate commits (including merges) are lost. Johannes Schindelin confirmed this with a test case showing that `git replay --linearize master~2..master` replays only the tip directly onto `--onto`, dropping the "Git 2.55-rc2" commit entirely. The root cause is the removal of the `replayed_base` logic in `pick_regular_commit()` during v5’s refactoring.

The second issue is a **CLI design inconsistency** with `git rebase`. Patrick Steinhardt argued that `--linearize` should adopt `git rebase`’s established syntax (`--rebase-merges`, `--no-rebase-merges`) for consistency, but Johannes Schindelin rejected this precedent, calling `git rebase`’s interface "hostile" and advocating for intentional divergence. He proposes `--replay-merges=<mode>` (e.g., `--replay-merges=replay-cousins`) as a clearer alternative, treating `--linearize` as a separate axis from merge-handling modes. This exchange has elevated the debate from a technical detail to a **philosophical split** between consistency and UX clarity, with no immediate resolution in sight. The regression remains the highest priority, but the CLI discussion will shape follow-up patches and could influence Git’s broader approach to history-editing commands.
