The `git replay --linearize` feature, now at version 7, is close to being merged but faces a key design debate about how it should handle multiple branches. The series adds a `--linearize` option to flatten merge commits into a linear history, offering a simpler alternative to Johannes Schindelin’s earlier merge-replay implementation. All prior technical feedback has been addressed, and the series is queued in Junio C Hamano’s `next` branch for integration testing.

The main unresolved issue is how `--linearize` should behave when given multiple positive refs (e.g., `git replay --linearize --onto main topic1 topic2`). Currently, it flattens all commits into a single linear chain, concatenating branches in an order determined by Git’s revision walk. Junio argues this is acceptable for cases like octopus merges, where order doesn’t matter, and sees the flexibility as a feature. Elijah Newren, however, calls this behavior confusing and inconsistent with other `git replay` modes, which reject multiple refs to avoid ambiguity. He points out that the current implementation makes the rare case (concatenating branches) easy at the expense of the common case (linearizing one branch while keeping others independent), and proposes either restricting multiple refs or tracking per-branch state to preserve independence.

The discussion has shifted from technical correctness to design philosophy, with Elijah framing the debate around usability and recoverability. His latest email makes a strong case for restricting multiple refs, at least temporarily, to avoid locking in a behavior that might later need to change. Toon Claes, the author, has not yet responded to this latest feedback, but the series remains in `next` while the debate continues. If no resolution is reached, this could delay graduation to `master`.
