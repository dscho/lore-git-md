The `git replay --linearize` series, introduced by Toon Claes, was merged to `master` in its v5 iteration on July 15, 2026, but has since revealed three critical post-merge issues. The most urgent is a **silent commit-dropping regression** in single-branch replay scenarios, where intermediate commits—including merges—are lost, leaving only the tip commit replayed directly onto the `--onto` target. Johannes Schindelin identified this as a data-loss bug and provided a test case demonstrating the problem, pinpointing the root cause as the removal of the `replayed_base` logic in `pick_regular_commit()`. The regression demands an urgent follow-up patch to restore the intended behavior.

The other two issues are strategic rather than functional. The first is a **CLI design inconsistency** with `git rebase`: Patrick Steinhardt argues for consistency with `git rebase`'s `--rebase-merges` syntax, while Johannes Schindelin rejects this as perpetuating a usability anti-pattern and advocates for clearer, intent-driven options like `--replay-merges=<mode>`. This debate has evolved into a **philosophical clash** over whether Git should prioritize consistency across commands or UX clarity, with Patrick now conceding the UX argument but insisting that any divergence must be **explicitly justified in the commit message**. The second issue, **merge commit divergence handling**, remains a secondary concern, with Junio Hamano and Phillip Wood noting that the current implementation silently discards one side of divergent merges.

The thread is now in a holding pattern, awaiting a follow-up patch to fix the regression and a design decision on the CLI. The regression is the highest priority, but the CLI debate—now framed as a question of **how to document design decisions**—could have lasting implications for how Git handles similar trade-offs in the future. Until these are resolved, the series remains critically flawed despite its merge to `master`.
