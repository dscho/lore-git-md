The goal is to supersede Johannes Schindelin’s earlier merge-replay implementation (pull.2106) with a simpler alternative that avoids dangling commits and ensures all replayed commits are linearized into a single topology.

### Key technical details

- New CLI option: `git replay --linearize` (implemented in patch 3/3).
- **Proposed syntax**: `git replay --linearize --onto <target> <branches> --ref <ref>` (Toon’s proposal). All commits from `<branches>` are replayed linearly onto `<target>`, but only the ref specified by `--ref` is updated.
- **Implementation challenge**: Avoiding commit duplication when replaying multiple branches independently (e.g., `branchB` and `branchC`) would require tracking `last_commit` per branch.
- **Edge case**: `--contained` (hypothetical future option) is flagged as incompatible with `--linearize` due to similar reachability issues.
- Internal flags: `reverse` (boolean), `linearize` (boolean).
- Files touched: `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, `t3650-replay-basics.sh`.
- New helper functions: `put_mapped_commit`, `get_mapped_commit`, `resolve_replay_base`.
- Modified functions: `pick_regular_commit` (restored `replayed_base` parameter), `replay_revisions` (skips merge commits when `--linearize` is active, resolves replay base upfront).
- **Algorithmic behavior**: `--linearize` ensures all replayed commits are flattened into a single linear history, even when multiple branches are involved. For example, replaying branches `Z` and `C` onto `X` with `--linearize` produces `A->X->Y->Z->B->C`, where all commits are linearized into a single topology.
- **Behavioral difference from `git rebase --no-rebase-merges`**: `git replay --linearize` drops merges and keeps only one branch (e.g., `A->X'` or `A->Y'` for a merge of `A->X` and `A->Y`), while `git rebase --no-rebase-merges` rewrites both branches and drops the merge (e.g., `A->X'->Y'` or `A->Y'->X'`). This difference is intentional, documented, and tested.
- **Compatibility**: `--linearize` and `--revert` can now be used together (mutual exclusivity removed in v7), but Junio has raised concerns about the edge case where the replay range includes a merge commit (`M`) and one side of the merge (`A`), but excludes the other side (`B`) and the merge base (`O`). The current implementation may not reliably handle this scenario. **Mutual exclusivity with `--advance` is enforced**; documented in the man page.
- **Multi-branch behavior**: The current implementation flattens all commits into a single linear history, concatenating branches in an order determined by the revision walk (not the user’s command-line order). Junio argues this is acceptable for cases where order is inconsequential (e.g., octopus merges of independent branches), while Elijah argues it violates the principle of least astonishment and is inconsistent with `--advance`/`--revert`. Toon’s `--ref` proposal would avoid concatenation by updating only the specified ref.
- **Edge case handling**: Root commits are explicitly replayed (merges are dropped); the if/else structure distinguishes merges, roots, and regular commits. The **partial merge range edge case** (Junio’s concern) and the **multi-branch ambiguity** (Elijah’s and Junio’s concern) remain unresolved.
