The `git replay --linearize` series (v7) is a technically complete feature addition that flattens merge commits into a linear history, offering a simpler alternative to Johannes Schindelin’s earlier merge-replay implementation. Authored by Toon Claes with preparatory work from Schindelin, the series has been queued in `next` for integration testing after addressing all prior feedback, including a regression fix for single-branch replay and interface design clarifications. The core behavior—dropping merges and producing a single linear topology—is now stable, with thorough test coverage and documentation.

The series has two remaining open questions. The first, raised by Junio C Hamano, involves an edge case where `--linearize` and `--revert` are combined on a partial merge range (e.g., a range including a merge commit and one side of the merge but not the other). While Junio cautioned that the current implementation may not handle this predictably, he no longer considers it a blocker for `next`. The second, more pressing issue is a **principle-of-least-astonishment violation** identified by Elijah Newren: when multiple positive refs are provided (e.g., `git replay --linearize --onto main topic1 topic2`), the current implementation flattens all commits into a single linear history with an opaque order, which Elijah argues is inconsistent with other `git replay` modes. Junio has pushed back on disallowing multiple refs, framing the current behavior as a pragmatic default for cases where order is inconsequential and emphasizing user flexibility. The ball is now in Toon’s court to address this ambiguity, either by documenting the concatenation order, restricting multiple refs, or proposing a middle ground.

Key participants include Toon Claes (author), Johannes Schindelin (preparatory work and interface design advocacy), Junio (maintainer, queued the series in `next`), and Elijah Newren (merge machinery expert, raised the multi-branch ambiguity). The series touches the replay machinery and sequencer internals, with mutual exclusivity between `--linearize` and `--advance` enforced but compatibility between `--linearize` and `--revert` restored in v7. Potential trivial conflicts exist with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series. The series remains in `next` pending resolution of the multi-branch ambiguity.
