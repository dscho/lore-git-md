The `git replay --linearize` series has reached its sixth iteration, addressing all critical issues that emerged after the premature merge of v5. Originally introduced as a feature to flatten merge commits into a linear history, v5 was merged but quickly revealed three major flaws: a regression causing silent commit dropping, unclear handling of divergent merge commits, and a poorly justified CLI inconsistency with `git rebase`. Toon Claes has now posted v6, which fixes the regression, documents the behavior, and provides the missing rationale for the CLI design.

The core of the fix lies in patch 2/3, which restores the `replayed_base` mechanism inadvertently removed in v5. This ensures that all commits in the input range are replayed, not just the tip, resolving the highest-priority regression. Patch 3/3—the focus of this update—implements the `--linearize` option with expanded documentation and test coverage. The documentation now explicitly states that `--linearize` produces a single linear sequence, even if this duplicates shared history, and clarifies how divergent merges are handled. The commit message also justifies the CLI naming (`--linearize` instead of following `git rebase`'s `--rebase-merges` syntax), addressing Patrick Steinhardt’s demand for explicit rationale.

Johannes Schindelin identified the regression and advocated for UX clarity, while Phillip Wood confirmed edge cases around merge divergence. Junio C Hamano, who merged v5, is likely to merge v6 as a bugfix and documentation update. The series is now ready for re-review, with no further design changes proposed—the philosophical debate about CLI consistency remains unresolved but is now documented. The expanded test suite verifies edge cases like root commits, multiple branches, and `--contained` with `--linearize`, ensuring the feature behaves as intended.
