The `git replay --linearize` series (v7) adds an option to flatten merge commits into a linear history, and it has been queued in `next` for integration testing. Toon Claes is the primary author, with preparatory work by Johannes Schindelin. The series addresses all prior feedback and fixes a regression in `--linearize` behavior when replaying a single branch with merge commits.

The interface design debate is settled: `--linearize` is a standalone flag, diverging from `git rebase`'s `--rebase-merges=<mode>` syntax, with the divergence justified in the commit message. Mutual exclusivity between `--linearize` and `--revert` was removed in v7, but Junio raised a potential edge case where the replay range includes a merge commit and only one side of its history, which the current implementation may not handle reliably. This remains unresolved but is no longer blocking progress.

Elijah Newren has now raised a new concern about a principle-of-least-astonishment violation when multiple branches are replayed with `--linearize`. Without `--linearize`, `git replay --onto main topic1 topic2` replays each branch independently, updating both refs to their replayed tips. With `--linearize`, the same command flattens all commits into a single linear history, concatenating the branches in an order determined by the revision walk—not the user’s command-line order. This means both refs end up pointing to different commits along the same linear chain, which Elijah argues is surprising and inconsistent with other `git replay` modes (`--advance` and `--revert`), which reject multiple positive refs to avoid ambiguity. He suggests either disallowing multiple positive refs with `--linearize` or tracking a `last_commit` per branch to preserve branch independence. The ball is now in Toon’s court to address this inconsistency.
