The `git replay --linearize` series was merged to `master` on July 15, but a critical regression has since been identified: when replaying a single branch containing merge commits, v5 silently drops all commits except the tip, directly replaying it onto `--onto`. Johannes Schindelin confirmed this with a real-world example, showing that intermediate commits (including merges) are lost—a silent data loss bug that differs from v4’s correct behavior.

The latest discussion shifts focus to the command-line interface design. Patrick Steinhardt argues that `git replay` should adopt the same merge-handling syntax as `git rebase` (`--rebase-merges`, `--no-rebase-merges`, `--rebase-merges=rebase-cousins`) for consistency, rather than introducing new flags like `--linearize` or `--no-merges`. While he acknowledges that supporting all modes immediately isn’t necessary, he insists the interface should be future-proof and documented if deviating from `git rebase`. This raises a broader design question: should `git replay` mirror `git rebase`’s CLI vocabulary to avoid user confusion, or is a separate path justified?

The regression remains the most urgent issue, but Patrick’s point about interface consistency could shape how the follow-up patch addresses both the bug and future merge-handling options. Junio’s input may be needed to resolve this design debate. The series is otherwise complete, with all prior technical concerns resolved.
