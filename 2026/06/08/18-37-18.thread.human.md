The `git replay --linearize` feature, introduced in a recently merged three-patch series by Toon Claes, has hit a subtle but important behavioral difference from its closest analog, `git rebase --no-rebase-merges`. The series was fully merged into Junio Hamano’s `seen` branch on July 15 after five iterations, with all prior feedback addressed—including a last-minute refactoring that replaced a controversial boolean helper with clearer explanatory comments and a base-selection logic fix.

The feature itself works as advertised: it flattens merge commits into linear history by walking only first parents, providing server-side functionality equivalent to `git rebase --no-rebase-merges`. However, Junio Hamano identified a post-merge edge case: when replaying a merge commit that merges two divergent branches, `git replay --linearize` grafts only the first-parent branch onto the new history, leaving the other branch dangling. This differs from `git rebase --no-rebase-merges`, which replays both branches to produce a fully linear history incorporating both sides of the merge. Phillip Wood confirmed this behavior in a recent review, explaining that replay cherry-picks each commit onto its rewritten parent, whereas rebase replays all commits in sequence. Neither contributor has judged the behavior as incorrect, but both agree it should be documented—and possibly made configurable.

The series is otherwise complete, with all architectural concerns resolved and expanded test coverage for complex rebase scenarios. The next step is likely a follow-up patch to either adjust the behavior or add a `--first-parent=<branch>` option, giving users control over which branch survives when replaying divergent merges. For now, the feature is ready for the next release, but this edge case may prompt further discussion before it becomes a stable part of Git.
