This is a **design discussion** in the final stages of Harald Nordgren’s `git branch --delete-merged` series, focusing on how to handle **stacked branches** (e.g., `feature2` depending on `feature1` as its upstream) when `feature1` is deleted. Junio C Hamano now fully accepts Phillip Wood’s argument that deleting a merged branch used as an upstream would break `@{u}` references and implicit `git rebase` workflows, and the conversation has shifted to implementation details.

The email explores three possible behaviors when `git branch --delete-merged` encounters a branch that is still the upstream of another unmerged branch: **fail the operation**, **clear the dependent branch’s upstream**, or **repoint the dependent branch’s upstream** to the branch that merged the deleted one (e.g., `origin/master`). Junio suggests the safest default is to **fail and ask the user**, but also notes that similar logic might need to extend to `git branch -d` for consistency.

This is a **substantive design decision** that will shape the final safety architecture of the feature. The series is otherwise complete and well-tested, so this is likely the last open question before final review. If implemented as a failure mode, it would add another layer of protection against accidental workflow disruption, aligning with the series’ overall emphasis on safety.
