This is a bug report about unexpected behavior in `git log` when given a file argument. Vincent Lefevre reports two distinct issues with Git 2.53.0, both involving `git log <file>` not showing commits that modify the specified file.

In the first case, running `git log git-gui/git-gui--askyesno.sh` on the Git project's own repository produces no output, while adding `-m` (show merge commits) reveals three non-merge commits that touch the file. This suggests the default behavior is silently omitting relevant history.

The second case involves an MPFR repository where `git log --reverse AUTHORS` shows only two commits: one creating the file and an unrelated commit that doesn't modify AUTHORS. Without `--reverse`, the command also includes a commit that predates the file's creation. The reporter notes this contradicts the man page claim that `--reverse` only affects output order, not commit selection.

The email provides exact commit hashes, reproduction steps, and repository states (specific commit IDs) for both cases. No patch is proposed - this is purely a bug report identifying what appears to be incorrect commit filtering logic in `git log`'s file history tracking. The issues appear to be edge cases around merge handling and commit ordering that could affect users trying to track file history.
