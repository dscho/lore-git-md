This is the thirteenth iteration of a security-hardened feature series that adds `git cat-file --batch-command` support for querying remote object metadata without full downloads. The series is now complete and ready for merging, with all prior review feedback addressed in this final version.

The core implementation introduces a new `remote-object-info` command that lets clients safely request object sizes (and eventually other metadata) from servers supporting the object-info capability in protocol v2. The key security improvement in v13 is dynamic capability-based validation: instead of a static allow-list, the client now validates requested format placeholders against the server's advertised capabilities, closing a potential information-leak vector. Other notable hardening includes memory leak fixes in transport-helper, improved error messages, and strict protocol v2 enforcement.

Pablo Sabater addresses the last mechanical concerns raised in review: the capability validation loop now uses backward iteration (necessary for safe list compaction) with an explicit cast to `int` and explanatory comment, and the commit message for dispatch_calls() was clarified. The series also adds better error reporting for short OIDs and avoids unnecessary server requests when no supported placeholders are present. All changes are fully rebased on current master (4621f8ce5e).

The implementation maintains backward compatibility while being forward-compatible for future metadata types. Currently only objectsize is supported end-to-end, with objecttype and other fields returning empty strings (matching `for-each-ref` behavior). The author raises an open design question about how to distinguish "unsupported" vs "no data" responses for future placeholders like %(rest) or %(objectmode), suggesting either a "???" placeholder or maintaining the current empty-string approach.

The series includes comprehensive test coverage (new t1017-cat-file-remote-object-info.sh) and moves test utility functions to lib-cat-file.sh for reuse. All prior substantive reviews from Junio Hamano, Patrick Steinhardt, and others have been addressed, with no outstanding objections. The type-safety issue previously identified in fetch_object_info() was determined to originate from an external topic and will be resolved via evil merge during integration.
