This is a **reply in the refactoring series** targeting Git’s reference backend, specifically patch 7/8 of Patrick Steinhardt’s 8-part series. The email is a direct response to Jeff King’s substantive critique of the patch’s design, which proposed an architectural alternative to the current workaround for recursive initialization.

Patrick acknowledges Peff’s point that the recursion stems from `ref_store_init()` relying on the general config subsystem (via `repo_settings_get_log_all_ref_updates()`) but pushes back on the proposed solution. He argues that reading ref backend config via `read_repository_format()`—which ignores *all* includes—is overly broad, since only `includeif.onbranch` conditions cause the recursion. Other include conditions (e.g., `includeif.gitdir`) should remain valid for ref backend config. He also notes that lazy-loading config settings (Peff’s alternative 1) would be cumbersome, as multiple backends (like reftable) rely on config at initialization time.

The key technical detail here is Patrick’s counter-proposal: extend `struct config_options` with an `ignore_refdb` toggle to selectively disable `onbranch` includes during ref backend initialization. This would preserve other include conditions while avoiding the recursion, offering a middle ground between the current workaround and Peff’s more invasive suggestion. He commits to prototyping this approach, signaling a potential v4 of the patch.

This reply reopens the design discussion for patch 7/8, which had previously been accepted as a pragmatic solution. The outcome could shape how Git handles ref backend config parsing in the future, with implications for both current and future backends. The thread remains focused on initialization hygiene, a recurring theme in Patrick’s broader ref backend modernization effort.
