This is an early-stage design discussion about **pinned references**—a proposed Git feature to combine a reference (like a tag) with an expected object ID for stability and human readability.

Patrick Steinhardt responds to Erik Östlund’s RFC by pointing out that Git already has a syntax that *approximates* this idea: the `<describeOutput>` format (e.g., `v2.54.0-0-g0b13e48a3`). This format embeds a tag name and an object ID in a single string, but it doesn’t enforce the invariant that the tag must resolve to that exact OID. If they don’t match, the result is just a different object ID, which could be confusing. Patrick calls this one of Git’s "more surprising" syntaxes, hinting that it might not be the ideal foundation for a new feature.

The key takeaway is that while Git has *something* resembling pinned references, it doesn’t actually solve the problem Erik raised. The `<describeOutput>` format is a historical artifact, not a deliberate design for enforcing ref-OID consistency. This leaves the door open for further discussion: should Git add a new mechanism (like Erik’s `?oid=` syntax or a CLI flag), or is the existing syntax "good enough" despite its quirks?

For now, this is still a conceptual thread with no code or patches. If Erik or others push forward, the next steps would likely involve nailing down syntax, use cases, and implementation trade-offs. Worth watching if you care about ref handling or deployment workflows, but not yet actionable.
