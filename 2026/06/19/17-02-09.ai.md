This is a maintainer response to the `git log <file>` bug report, clarifying the first issue (merge commits being omitted) as intentional behavior related to subtree merges rather than a bug.

Junio C Hamano explains that the silent omission of commits when running `git log git-gui/git-gui--askyesno.sh` is a known consequence of Git's subtree-merge mechanism. The file exists at different paths in different parts of the history (root level in the git-gui project, subdirectory in the Git project), and the revision walker needs explicit direction to track both paths. He provides a workaround: `git log -- git-gui/git-gui--askyesno.sh git-gui--askyesno.sh` will show the full history by telling Git to consider both the subdirectory and root-level paths.

The response does not address the second issue (the `--reverse` behavior discrepancy) at all, leaving that part of the original report still open. The explanation focuses on the technical reason for the merge-handling behavior but does not state whether this is considered the correct user-facing behavior or if it might change in the future. The tone suggests this is working-as-designed, though the lack of documentation about this subtree-merge quirk in the `git log` man page could still be seen as a usability gap.
