This is a bug report about unexpected behavior in `git log` when given a file argument. Vincent Lefevre describes two separate issues observed in Git 2.53.0.

First, running `` `git log git-gui/git-gui--askyesno.sh` `` produces no output, but adding `-m` (which splits merge commits) reveals three non-merge commits. This suggests the default behavior is silently omitting relevant history, which Vincent calls "unhelpful" and likely incorrect.

Second, in a different repository, `` `git log --reverse AUTHORS` `` shows only two commits: one creating the file and another unrelated commit that doesn’t touch `AUTHORS`. Without `--reverse`, the same command also includes a commit made *before* the file existed, which is clearly wrong. The man page states `--reverse` should only affect output order, not which commits are selected.

The report includes precise reproduction steps, commit hashes, and repository references, making it easy for someone to verify. No patch is proposed—this is purely a problem description. The issues appear to be real edge cases in `git log`'s file-history logic, possibly related to how it handles merges and file creation events. If confirmed, these would be legitimate bugs worth fixing.
