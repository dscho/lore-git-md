This thread reports two subtle but potentially serious bugs in `git log` when tracking file history. Vincent Lefevre discovered that `git log <file>` can silently omit commits that modified the specified file, producing incomplete or misleading results.

The first issue affects the Git project's own repository: running `git log git-gui/git-gui--askyesno.sh` shows no output by default, but adding `-m` (to show merge commits) reveals three relevant non-merge commits that actually touch the file. This suggests the default file-history logic is incorrectly filtering out valid commits.

The second case involves an MPFR repository where `git log --reverse AUTHORS` shows only two commits - one creating the file and an unrelated commit that doesn't modify AUTHORS. Without `--reverse`, the command incorrectly includes a commit that predates the file's creation, directly contradicting the man page's claim that `--reverse` only affects output order.

Vincent provides exact reproduction steps, commit hashes, and repository states for both cases. The issues appear to be edge cases in Git's commit filtering logic, particularly around merge handling and commit ordering. No solutions or patches have been proposed yet - this is currently just a detailed bug report that could affect users trying to accurately track file history.
