Vincent Lefevre reported that `git log <file>` omits commits in two edge cases: merge commits unless `-m` is used, and unexpected behavior with `--reverse` that contradicts the documentation. Junio Hamano has now clarified that the first issue—omitting merge commits—is intentional and tied to Git's subtree-merge handling. When a file exists at different paths in different parts of history (e.g., `git-gui/git-gui--askyesno.sh` in the Git project vs. `git-gui--askyesno.sh` in the original git-gui project), `git log` silently filters out commits from the "other" path unless explicitly told to track both. The workaround is to specify both paths: `git log -- git-gui/git-gui--askyesno.sh git-gui--askyesno.sh`.

The second issue—`--reverse` altering commit selection in a way that includes commits predating the file's creation—remains unaddressed. Junio’s response suggests the merge-handling behavior is working as designed, though it’s unclear whether the lack of documentation about this subtree-merge quirk is considered a usability issue. No patches or fixes have been proposed yet, and the thread is still awaiting further discussion or a decision on the `--reverse` discrepancy.
