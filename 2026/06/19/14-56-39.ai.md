This is the client-side implementation patch for the `remote-object-info` command in `git cat-file --batch-command`, completing the feature series. It enables querying object metadata (currently just size) from remote repositories without downloading the full objects, using Git's protocol v2 object-info capability.

The patch adds the `remote-object-info` command to `git cat-file --batch-command`, allowing users to request object information from a remote in a single round-trip. Unlike the existing `info` command which processes objects one at a time, `remote-object-info` accepts multiple object IDs in a single request (e.g., `remote-object-info <remote> <oid1> <oid2> ...`), significantly reducing network overhead. The implementation handles both regular and `--buffer` modes, with special logic to batch remote requests while maintaining the expected command execution flow.

Key technical details include:
- New `parse_cmd_remote_object_info()` function that validates input, establishes transport connections, and processes responses
- Dynamic capability validation against server-advertised features
- Support for all three transport protocols (git://, file://, http://) with protocol v2 enforcement
- Input size limits (8K URL length, 10,000 objects per request) to prevent abuse
- Strict error handling for malformed OIDs, unsupported filters, and missing objects
- Integration with the existing batch-command infrastructure while optimizing for remote operations
- Comprehensive test coverage (680-line test file) verifying behavior across transports and edge cases

The implementation currently supports only object size queries, with object type and other fields returning empty strings (matching `for-each-ref` behavior). The patch includes clear documentation about this limitation and warns users not to rely on the current default format. The test suite verifies correct behavior with various transport configurations, including servers with and without the object-info capability.

This patch represents the culmination of the 13-iteration series, addressing all prior review feedback about security, error handling, and protocol compliance. The feature is now ready for integration, with the only remaining open question being how to distinguish "unsupported" vs "no data" responses for future metadata types.
