This is a maintainer response to a `git log` bug report about file history tracking. Junio C Hamano acknowledges the reported behavior as a known limitation of Git's subtree-merge handling rather than a bug. The issue affects `git log <file>` when examining files that were merged via subtree (like `git-gui/git-gui--askyesno.sh` in the Git repository), where commits modifying the file are silently omitted unless `-m` is used.

Junio explains the root cause: the file exists at different paths in different parts of the history (root level in the original `git-gui` project, subdirectory in the merged Git repository). The revision walker fails to connect these paths during traversal. His suggested workaround is to explicitly list both paths: `git log -- git-gui/git-gui--askyesno.sh git-gui--askyesno.sh`. This tells Git to consider both locations when filtering commits.

The response does not address the second reported issue about `--reverse` altering commit selection, leaving that part of the bug report still open. No patch is proposed, and the maintainer's tone suggests this behavior is considered an inherent limitation of the current subtree-merge implementation rather than something requiring a fix. Users tracking file history across subtree merges will need to use the workaround or accept the current behavior.
