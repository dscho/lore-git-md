This is a design discussion about the `git history squash` feature, now in `next`. Patrick Steinhardt responds to Junio C Hamano’s open question about how the command should handle refs (branches or tags) that point to commits *inside* the squashed range.

Patrick rejects the idea of silently pruning such refs as "extremely surprising" to users. Instead, he proposes a fourth option: **detect the ambiguity and reject the operation**, optionally prompting the user to clarify their intent. This approach preserves flexibility for future iterations while avoiding silent data loss. He notes that users can already achieve the behavior of retargeting all refs to the squashed commit by explicitly passing `--update-refs=head`, leaving room to add other modes (like preserving intermediate refs) later if demand arises.

The response is pragmatic and aligns with the broader `git history` vision of being explicit about ref updates. No code changes are proposed yet; this is purely a design clarification. Expect Harald Nordgren to incorporate this guidance into a future revision before the feature graduates to `master`.
