This thread is about a **serious data-loss bug in Git's sparse-checkout mode**. The reporter, charmocc, has identified that `git checkout` behaves dangerously when sparse mode is enabled: while it correctly aborts in normal mode if an untracked file would be overwritten, in sparse mode it *silently overwrites the file* and then issues a misleading warning suggesting the file was preserved. This creates a false sense of safety, as users may believe their uncommitted changes were retained when they were actually lost.

The report includes clear reproduction steps, expected vs. actual behavior, and system details, making it easy for reviewers to verify. The core issue appears to be a logic flaw in how sparse-checkout interacts with Git’s working directory state checks. The warning message ("The following paths were already present...") is particularly confusing because it implies the file was *not* overwritten, when the opposite is true.
