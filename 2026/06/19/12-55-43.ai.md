This is a **substantive review** of the core implementation patch in Harald Nordgren’s `git history squash` series (v3 3/4). Patrick Steinhardt raises three technical concerns about the range-resolution logic in `resolve_squash_range()`:

1. **Input validation**: The function accepts any string as a revision range without upfront syntax checking, risking cryptic errors later. Patrick suggests validating the range format before parsing.
2. **Ancestry ambiguity**: The current `--boundary` traversal may include commits outside the ancestry path of the range’s oldest commit, potentially yielding multiple boundary commits even when a single unambiguous base exists. Adding `--ancestry-path` would tighten the resolution.
3. **Merge commit handling**: The code silently discards intermediate merge commits, which is probably correct, but Patrick questions whether the same logic should apply to the range’s tip or base if they are merges. The current implementation does not explicitly restrict them.

The review also notes that `setup_revwalk()` (used later in `cmd_history_squash()`) already filters out merges, which may conflict with the intent to allow them in the squashed range.

No code suggestions are provided; the feedback is diagnostic, identifying edge cases the current implementation does not handle. The thread’s earlier design resolution (rejecting operations with refs pointing into the squashed range) is unaffected.
