This is the eleventh patch in the GSoC RFC v13 series implementing `git cat-file --batch-command` support for remote object metadata queries. The series is now complete and ready for merging, with this patch addressing a critical security and robustness issue in the format placeholder validation logic.

The patch replaces the previous `strstr()`-based validation with a strict allow-list of supported atoms (`objectname` and `objectsize`) for remote queries. This fixes two serious problems: (1) uninitialized `data->type` values causing segfaults when expand_atom() recognizes an atom but the remote doesn't support it, and (2) the previous behavior where unknown atoms would trigger `die()` via `strbuf_expand_bad_format()`, breaking local queries that shared the same format string.

Key changes include:
- A new `remote_object_info_atoms[]` array defining supported placeholders
- Dynamic validation against server capabilities in `expand_atom()`
- Empty string returns for unsupported atoms (matching `for-each-ref` behavior)
- Initialization of `data->type` to `OBJ_BAD` and NULL checks for `type_name()`
- Updated documentation and tests reflecting the new behavior

The implementation maintains backward compatibility while being forward-compatible - currently unsupported placeholders like `%(objecttype)` now return empty strings rather than failing. This matches the series' security-hardened design philosophy, where strict validation and graceful degradation are preferred over abrupt failures.

The patch touches core validation logic in `builtin/cat-file.c`, updates the man page caveats section, and modifies tests to expect empty strings instead of fatal errors. All changes are well-motivated and address specific review feedback about safety and robustness. The allow-list approach provides clear security boundaries while remaining extensible for future metadata types.
