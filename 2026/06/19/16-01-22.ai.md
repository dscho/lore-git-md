This is a **design discussion** in the `git branch --delete-merged` series, focusing on the stacked-branch safety mechanism. Junio C Hamano now fully endorses Phillip Wood’s argument that deleting merged branches used as upstreams for other branches (e.g., `feature1` if `feature2` stacks on it) would break `@{u}` references and implicit `git rebase` workflows. The email explores how to implement this protection, proposing two user-facing options: either abort the deletion (safest) or automatically retarget the dependent branch’s upstream to the branch that merged the deleted branch (e.g., `origin/master`).

Key technical details for follow-up discussion:
- **Subsystem**: branch management (`git branch --delete-merged` and `git branch -d`).
- **Behavioral impact**: The protection will apply to both `--delete-merged` and `-d` (since both check "is merged to upstream?").
- **Files/functions**: The logic will live in `delete_merged_branches()` and `delete_branches()` in `builtin/branch.c`.
- **Detection**: The code must identify branches used as upstreams for other branches (e.g., via `branch.<name>.merge` config).
- **User choices**: Two proposed behaviors:
  1. **Abort**: Fail the deletion and notify the user (e.g., "Cannot delete branch 'feature1' because 'feature2' depends on it").
  2. **Retarget**: Automatically update the dependent branch’s upstream (e.g., `feature2@{u}` → `origin/master`).
- **Open question**: Whether to extend this protection to other dependencies (e.g., reflog references, worktrees, or non-upstream relationships).

Junio’s tone suggests a preference for the abort-and-notify approach as the default, with retargeting as an optional flag (e.g., `--retarget-upstreams`). The discussion may also clarify whether this protection should be opt-in or opt-out. The next iteration of the series (v17) will likely implement one of these designs, finalizing the stacked-branch safety mechanism.
