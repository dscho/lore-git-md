Thread identity
Subject: `git log <file>` omits commits that modify the file
Series version: standalone bug report (no patch series)
Originating author: Vincent Lefevre
Thread type: bug report

Core problem or goal
`git log <file>` fails to show commits that modify the specified file in two edge cases: (1) when the file history involves subtree merges, commits are silently omitted unless multiple paths are explicitly specified; (2) when `--reverse` is used, commit selection logic is altered in a way that contradicts the man page, including commits that predate the file's creation.

Current status
The first issue (subtree merges) is clarified as intentional behavior, not a bug. Junio C Hamano explains that the omission occurs because the file existed at different paths in different parts of the history (root level in git-gui, subdirectory in Git), and the revision walker requires explicit direction to track both paths. A workaround is provided: `git log -- git-gui/git-gui--askyesno.sh git-gui--askyesno.sh`. The second issue (`--reverse` behavior) remains unresolved and unaddressed.

Key technical details
- Subsystem: revision walking (`git log`)
- Command: `git log <file>`
- Flags involved: `-m` (show merge commits), `--reverse` (reverse output order)
- Edge cases: subtree merges (path divergence), file creation history, commit ordering
- Workaround for subtree merges: specify all historical paths explicitly (e.g., `git log -- path1 path2`)
- Test coverage: none yet; reporter provided exact reproduction steps and commit hashes
- Files: `git-gui/git-gui--askyesno.sh` (Git repo, moved from root in git-gui), `AUTHORS` (MPFR repo)
- Behavior: commits modifying the file are filtered out when the file's path changed across merges unless all paths are specified; `--reverse` alters commit selection logic
