This is a security proposal for Git hook safety in locally extracted repositories. The author, Jamison Phillips, identifies a potential supply-chain attack vector: when repositories are downloaded as ZIP/tarballs rather than cloned, their `.git/hooks` directory may contain malicious scripts that execute without warning on standard Git commands.

The RFC suggests a three-part verification system:
1. First-time detection of executable hooks triggers an interactive prompt for user approval
2. Approved hooks are cryptographically hashed and stored in a global config directory
3. Subsequent runs verify hooks against the stored hashes, re-prompting if changes are detected

The proposal aims to provide explicit user consent for hook execution in non-cloned repositories, addressing what the author describes as a "massive blind spot" in developer security. The approach appears thoughtfully designed with defense-in-depth principles, though the implementation details (particularly around hash storage and management) would need technical review. This touches on ongoing security discussions around Git hooks, making it likely to generate substantive discussion about both the threat model and solution architecture.
