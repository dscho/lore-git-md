This is a cover letter for a 2-patch series addressing a behavior change in `git commit --amend`. The series aims to modify Git's behavior when amending a commit with no actual changes (a "no-op" amend).

The core issue is that currently, `git commit --amend --no-edit` always creates a new commit object (with a new hash) even when nothing substantive has changed, because it updates the committer timestamp to "now". The proposed change would preserve the original commit hash in such no-op cases by reusing the existing committer date when no other aspects of the commit (tree, author, committer info, or signature) have changed.

The series is structured as:
1. A preparatory refactoring to extract `commit_index_files_or_die()` helper
2. The main behavior change to implement no-op amend preservation

The changes touch `builtin/commit.c` and add extensive tests in `t/t7501-commit-basic-functionality.sh`. The documentation is also updated to clarify this behavior.

This appears to be a well-motivated quality-of-life improvement that would make `--amend` more predictable when used in scripts or automated workflows. The test coverage looks thorough, checking various edge cases around what constitutes a "no-op" amend. The change is backward compatible since it only affects cases where nothing substantive is being amended.
