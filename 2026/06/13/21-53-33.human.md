Security discussion on hook verification proposal. brian m. carlson raises significant concerns about the broader security model of working with untrusted repositories, arguing that the proposed hook verification system could create a false sense of security. They point out several other attack vectors (like filter drivers) that would remain unaddressed, and question whether prompting users aligns with Git's Unix philosophy of explicit commands having immediate effect.

The response highlights practical problems with the proposal: non-interactive environments (CI/CD) would break, the global state could grow indefinitely, and hook safety is context-dependent (a hook safe in one repo may be dangerous in another). This is a substantive technical pushback from a long-time contributor with deep security knowledge, suggesting the original proposal may need to reconsider its scope or framing to account for Git's broader security model. The thread now faces a key question: whether to pursue targeted hook improvements or acknowledge that repository trust is fundamentally binary in Git's design.
