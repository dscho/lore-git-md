This is a response in the ongoing thread about implementing a global `fetch.followRemoteHEAD` configuration option. Matt Hunter addresses Junio C Hamano's substantive review of the implementation details from the previous patch.

Key points addressed:
1. Terminology clarification - Matt acknowledges Junio's point about using "configuration variable" rather than "option" to avoid confusion with command-line options, while asking if "setting" might be an acceptable alternative in some contexts.

2. Case sensitivity - Matt accepts Junio's argument for using case-sensitive matching (`strcmp`) rather than case-insensitive (`strcasecmp`) for configuration values, noting the inconsistency with how remote-specific values are handled and the potential confusion given that config variable *names* are case-insensitive.

3. Error handling - Matt agrees with Junio's concern that using `die()` for invalid configuration values is too aggressive, particularly in single-shot fetch scenarios where the setting wouldn't even be used. He proposes falling back to UNCONFIGURED state for unrecognized values, which would default to the "create" behavior.

The response shows good technical engagement with the review points while maintaining the original design intent.
