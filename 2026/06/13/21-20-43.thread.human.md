Jamison Phillips proposed a security enhancement to prevent automatic execution of potentially malicious hooks in repositories extracted from ZIP files or tarballs. The RFC suggests a verification system that would prompt users before running new hooks, store cryptographic hashes of approved hooks, and require re-approval for any changes. The goal is to close a security gap where currently, unpacked repositories can run hooks without warning while cloned ones don't.

brian m. carlson has raised significant concerns about the approach, arguing that Git's security model doesn't protect against untrusted working trees in general. They point out other attack vectors like malicious filter configurations would remain, and question how the interactive prompts would work in automated environments. The response also highlights practical issues with maintaining global approval state and notes that hook safety depends heavily on context - what's safe in a trusted dotfiles repo might be dangerous elsewhere.

The discussion has now broadened from implementation details to more fundamental questions about Git's security boundaries and whether the proposed solution might create a false sense of security while not addressing related risks. Key open questions remain about the scope of the problem and whether hook verification alone provides meaningful protection given other potential attack surfaces.
