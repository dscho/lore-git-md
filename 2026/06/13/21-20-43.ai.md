This is a security proposal for Git's handling in unzipped/local repositories. Jamison Phillips identifies a potential supply-chain attack vector where malicious hooks could execute automatically when developers work with repositories extracted from ZIP/tarball archives (unlike cloned repositories which exclude hooks by default).

The RFC suggests a three-part verification system:
1. First-time interception of executable hooks with user confirmation prompt
2. Cryptographic hashing of approved hooks stored in a global config directory
3. Subsequent silent execution only for verified hooks, with re-prompting for any changes

The proposal targets a real security gap - currently, extracted repositories can silently execute arbitrary hook scripts without user awareness. The suggested approach mirrors security patterns from other tools that require explicit approval for untrusted code execution. The implementation would need to carefully consider the global state location (platform differences), hash collision resistance, and whether to scope approvals per-repository or per-hook.

This touches Adrian Ratiu's ongoing hook configuration work but approaches from a security rather than configuration angle. The core challenge will be balancing security with workflow disruption - the prompt could annoy users working with many legitimate local hooks while protecting against malicious ones.
