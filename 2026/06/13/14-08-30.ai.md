This is the first patch in a two-part documentation series from Weijie Yuan, updating contributor guidelines about patch etiquette. The patch focuses on improving guidance around responding to reviews before sending new patch versions.

The changes modify both `MyFirstContribution.adoc` (the new contributor guide) and `SubmittingPatches` (the canonical reference) to emphasize that authors should discuss their planned changes in the mailing list thread before rerolling patches. The key addition is making explicit that patch updates shouldn't be the only response to review feedback - authors should first explain their reasoning about which suggestions they'll implement, which they disagree with, and any alternative approaches they're considering.

The motivation is clear from the commit message: this prevents reviewers from having to infer the author's reasoning from code changes alone, and allows discussion of the approach before implementation work is done. The changes appear well-targeted to common mailing list patterns where new contributors sometimes send new versions without sufficient prior discussion.

The patch touches core documentation files that shape contributor expectations, so getting the wording right matters. The proposed text seems reasonable, though as an RFC, the exact phrasing may evolve based on feedback. The changes are consistent with observed mailing list discussions about improving review workflows.
