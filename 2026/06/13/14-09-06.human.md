This is the second patch in a 2-part RFC series from Weijie Yuan proposing updates to Git's contributor documentation regarding patch review etiquette. The series builds on improving guidance around two key aspects of the review process: discussing feedback before rerolling (patch 1) and appropriate reroll timing (this patch).

The current patch focuses on establishing clearer expectations around how quickly contributors should send updated versions of their patches. It adds guidance section to both `MyFirstContribution.adoc` and `SubmittingPatches` that:

1. Suggests a default of no more than one new version per day to allow for batching feedback
2. Lists factors that may warrant deviation from this default (series size, review depth, amount of rework needed, and how close the topic is to acceptance)

The changes appear well-motivated by real mailing list patterns where contributors sometimes send multiple versions in quick succession before reviewers have had time to respond. The patch demonstrates the proposed approach by clearly explaining the rationale for each addition.

As an RFC, the exact phrasing may evolve based on feedback, but the content aligns with established best practices and incorporates advice from experienced contributors like Patrick Steinhardt. The changes target core documentation files that shape new contributor expectations, so getting the tone and balance right is important.
