Thread identity: RFC proposal for secure hook execution in unzipped/local Git repositories, authored by Jamison Phillips. This is a security-focused thread addressing a supply-chain attack vector where ZIP/tarball-extracted repositories can execute arbitrary hooks without user awareness.

Core problem: The current behavior creates a security gap where malicious hooks could execute automatically, unlike cloned repositories which exclude hooks by default. Jamison's original proposal suggested a three-part verification system with user confirmation prompts, cryptographic hashing of approved hooks, and subsequent silent execution for verified hooks.

Key technical considerations expanded:
- Global state location needs platform-specific handling (raised in initial proposal)
- Hash collision resistance requirements (initial proposal)
- Scope decision needed (per-repository vs per-hook approvals) (initial proposal)
- Security model limitations: brian m. carlson notes Git's security model doesn't guarantee safety with untrusted working trees, citing other attack vectors like malicious filter configurations
- Workflow impacts: Interactive prompts problematic in non-interactive contexts (CI/CD, container builds), particularly affecting Git LFS hook installation
- State management concerns: Global approval state could grow indefinitely and create risks when transferred between machines
- Context sensitivity: Hook safety is context-dependent, making blanket approvals potentially dangerous

Current status: The discussion has shifted from implementation details to deeper architectural considerations about Git's security boundaries. brian m. carlson's response suggests the proposal might create a false sense of security while not addressing other attack vectors, and questions the ZIP-based distribution workflow that motivated the RFC.

Open questions:
