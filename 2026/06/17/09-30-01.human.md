This is a short follow-up in the ongoing discussion about adding a `--squash` option to `git rebase`. Harald Nordgren responds to Patrick Steinhardt’s endorsement of a `git history squash` subcommand, which was proposed as an alternative to Harald’s `git rebase --squash` patch series.

Harald acknowledges Patrick’s point that `git history squash` would fit naturally into the `git history` roadmap but expresses a preference for the rebase-based approach. His argument is that `git rebase --squash` is more intuitive because it automatically understands the commit range relative to the upstream, whereas `git history` feels more detached from the current branch state. This is a user-experience perspective rather than a technical one, and it highlights a potential discoverability advantage for the rebase implementation.

The email does not address the architectural concerns raised earlier by Phillip Wood—specifically, the efficiency risks of the current rebase implementation or the lack of interactive message editing. Instead, it focuses on the trade-off between integration with existing workflows (`rebase`) and the flexibility of a new command (`history`). The thread remains unresolved, with the key technical objections still unanswered and two viable but competing directions on the table.
