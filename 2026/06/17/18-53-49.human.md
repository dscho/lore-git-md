This is a thread update from Junio C Hamano, the Git maintainer, checking on the status of Derrick Stolee’s patch series to disable Git config includes. The series proposed two mechanisms—an environment variable (`GIT_CONFIG_INCLUDES=0`) and a command-line option (`--no-includes`)—to prevent Git from processing config include directives, primarily for sandboxing use cases.

Junio’s email notes that the discussion has stalled after Stolee provided concrete details about his use case: a third-party build tool calling Git in a sandboxed environment where config includes fail because they reference unregistered files. Stolee acknowledged the concerns raised by Jeff King (Peff) about the risks of a binary on/off switch (e.g., breaking workflows that rely on conditional includes for work/personal email separation) and expressed openness to alternative solutions, including pushing back on users to change their config practices.

The thread has shifted from implementation details to a broader design question: whether Git should provide a targeted fix for this sandboxing problem or if the issue should be addressed by changing user behavior. Peff’s earlier feedback highlighted security and workflow tradeoffs, and Stolee’s latest reply grounded the discussion in real-world constraints (e.g., inability to modify the third-party tool). Junio’s message suggests he sees the series as potentially retracted unless further discussion emerges.

For a busy reader, this is a low-stakes update: the series is in limbo, and the conversation has moved from code to design philosophy. The patch itself is small and well-tested, but the underlying question—how Git should handle sandboxing—remains unresolved. If you care about config system security or build reproducibility, this thread is worth monitoring for future proposals. Otherwise, it’s safe to ignore for now.
