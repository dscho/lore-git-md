This is the fifth patch in Patrick Steinhardt’s 17-part ODB abstraction series (v3), converting the packed object storage backend into a proper `struct odb_source`. It embeds the base `struct odb_source` into `struct odb_source_packed`, assigns it the new `ODB_SOURCE_PACKED` type, and wires up lifecycle management by implementing the `free` callback and registering a `chdir_notify` handler to reparent the source’s path when the working directory changes.

The patch is a mechanical but foundational step in the ODB abstraction effort. It moves the packed source closer to the interface established by the loose source, ensuring both backends use the same embedded-base pattern and lifecycle callbacks. The `free` callback now properly cleans up the packfile list and `strmap` of paths, replacing the old `packfile_store_free()` function. The `chdir_notify` handler is a forward-looking addition: while not strictly needed yet (the packed source currently inherits paths from its parent files source), it will become necessary once the packed source starts using its own path in a later patch.

The diffstat (60 insertions, 22 deletions) reflects the shift of logic from `packfile.c` to `odb/source-packed.c`, removing the now-redundant `packfile_store_free()` and adding the new callbacks. The patch also introduces the `odb_source_packed_downcast()` helper, mirroring the loose source’s precedent, and updates the files source’s `free` callback to use the new ODB interface. No functional changes are introduced yet—this is purely plumbing—but it sets the stage for the callback wiring in subsequent patches.

The patch has already received surface-level review from Justin Tobler, who confirmed the mechanical alignment with the loose source’s pattern. No deeper engagement with the ODB design or lifecycle implications has occurred yet, and the series remains blocked by unresolved refdb issues (memory leaks, duplicate refdb creation) that Patrick is addressing in a separate 11-patch fix series. This patch is a prerequisite for those fixes, as it establishes the proper ODB source interface the refdb code will interact with.
