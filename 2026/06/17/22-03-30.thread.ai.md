Subject: t4216-log-bloom.sh: TAP parse errors on non-x86 due to char signedness assumption
Series version: none (standalone bug report)
Originating author: Todd Zullinger
Thread type: bug report

Core problem or goal
The test `t4216-log-bloom.sh` assumes that `char` is signed by default (true on x86) and uses `test_cmp` output to set the `SIGNED_CHAR_BY_DEFAULT` prerequisite. On architectures where `char` is unsigned, the diff output from `test_cmp` is not suppressed, causing TAP parse errors that break the test harness. The underlying question is whether the test’s behavior is correct (i.e., the Bloom filter logic is architecture-dependent) or if the test or the `test-tool read-graph bloom-filters` code is broken.

Current status
No prior discussion in this thread; this is the initial report. The failure is confirmed on non-x86 platforms, but it is not a regression—older builds also failed to set `SIGNED_CHAR_BY_DEFAULT` there. The test is skipped on these platforms, so the impact on end users is likely low, but the TAP parse errors could obscure other test failures in CI.

Key technical details
- Files touched: `t/t4216-log-bloom.sh`, `test-tool read-graph bloom-filters` (implied)
- Subsystem: commit-graph Bloom filters (path-change tracking in `git log`)
- Symbols: `SIGNED_CHAR_BY_DEFAULT` prerequisite, `test_cmp` output handling
- Behavior: On x86, `test_cmp` shows no diff and the prerequisite is set; on non-x86, the diff output (`52a9` vs. `c01f`) triggers TAP parse errors
- On-disk format: none (this is a runtime behavior issue)
- Test coverage: `t4216-log-bloom.sh` (specifically the `highbit1` test case)

Open questions and loose ends
1. Is the test *supposed* to fail on non-x86 (i.e., is the Bloom filter logic architecture-dependent)?

3. Should the fix silence the TAP errors (e.g., redirect `test_cmp` to `/dev/null`) or address the underlying `char` signedness assumption?
