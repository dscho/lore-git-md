Subject: t4216-log-bloom.sh: TAP parse errors on non-x86 due to char signedness assumption
Series version: none (standalone bug report)
Originating author: Todd Zullinger
Thread type: bug report

Core problem or goal
The test `t4216-log-bloom.sh` assumes `char` is signed by default (true on x86) and uses `test_cmp` output to set the `SIGNED_CHAR_BY_DEFAULT` prerequisite. On architectures where `char` is unsigned, the diff output from `test_cmp` leaks into the TAP stream, causing parse errors that break the test harness. The underlying question—whether the Bloom filter logic is architecture-dependent—remains unresolved but is orthogonal to the immediate fix. The goal is to eliminate the TAP parse errors by removing the redundant prerequisite.

Current status
Junio C Hamano, Patrick Steinhardt, and Jeff King (Peff) agree that the `SIGNED_CHAR_BY_DEFAULT` prerequisite is unnecessary and should be removed. The prerequisite is used only by the `highbit1` test, which runs `true` regardless of the outcome, making the check redundant. The proposed fix is to drop the `test_cmp` check and the prerequisite, resolving the TAP parse errors without altering the test’s logic or the underlying Bloom filter code. The issue existed since mid-2024 but only became visible after a June 2026 change (`389c83025d`) tightened the TAP harness to fail on invalid output. The timing context—clarified by Peff and accepted by Junio—explains why the problem surfaced only now. No objections have been raised, and the discussion suggests this is the uncontroversial path forward.
