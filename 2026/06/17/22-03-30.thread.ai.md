Subject: t4216-log-bloom.sh: TAP parse errors on non-x86 due to char signedness assumption
Series version: none (standalone bug report)
Originating author: Todd Zullinger
Thread type: bug report

Core problem or goal
The test `t4216-log-bloom.sh` assumes `char` is signed by default (true on x86) and uses `test_cmp` output to set the `SIGNED_CHAR_BY_DEFAULT` prerequisite. On architectures where `char` is unsigned, the diff output from `test_cmp` is not suppressed, causing TAP parse errors that break the test harness. The underlying question is whether the test’s behavior is correct (i.e., the Bloom filter logic is architecture-dependent) or if the test or the `test-tool read-graph bloom-filters` code is broken.

Current status
Junio C Hamano and Patrick Steinhardt agree that the `SIGNED_CHAR_BY_DEFAULT` prerequisite is unnecessary and should be removed entirely. The prerequisite is only used by one test (`highbit1`), which runs `true` regardless of the outcome, making the check redundant. The proposed fix is to drop the `test_cmp` check and the prerequisite, resolving the TAP parse errors without altering the test’s logic or the underlying Bloom filter code. No objections have been raised, and the discussion suggests this is the likely path forward. The original author of the 2024 change (Taylor Blau) has not yet weighed in, but Junio’s position implies the fix is uncontroversial.

Key technical details
- Files touched: `t/t4216-log-bloom.sh` (test script only)
- Subsystem: commit-graph Bloom filters (path-change tracking in `git log`)
- Symbols: `SIGNED_CHAR_BY_DEFAULT` prerequisite (to be removed), `test_cmp`, `highbit1` test case
- Behavior: On x86, `test_cmp` shows no diff and the prerequisite is set; on non-x86, the diff output (`52a9` vs. `c01f`) triggers TAP parse errors. The fix removes the check entirely.
- On-disk format: none (runtime behavior issue)
- Test coverage: `t4216-log-bloom.sh` (specifically the `highbit1` test case)

Open questions and loose ends
1. Is the test’s assumption about `char` signedness correct (i.e., should the Bloom filter logic vary by platform)? This remains unresolved but is orthogonal to the immediate fix. The discussion has not revisited this question, focusing instead on the TAP parse errors.
2. Whether Taylor Blau (original author of the 2024 change) has additional context or objections. Junio’s email suggests this is unlikely to block the fix.

Participant positions
- Todd Zullinger: reported the issue, provided reproduction details, and noted it is not a regression. Position: the test’s assumption is problematic, but it is unclear whether the behavior is correct or broken.
- Patrick Steinhardt: initially proposed a `test_lazy_prereq` fix to suppress TAP errors without changing the test’s logic. Later acknowledged that dropping the prerequisite entirely is a viable alternative.
- Junio C Hamano: prefers removing the `SIGNED_CHAR_BY_DEFAULT` prerequisite entirely, as it is unused elsewhere and the test’s behavior (skipping on non-x86) doesn’t justify the complexity. Position: the simplest solution is to drop the check, resolving the TAP parse errors without side effects.
