Subject: [PATCH] completion: zsh: fix completion for `git -C <path> <command>`
Series version: standalone patch (v1 sent, v2 pending)
Originating author: Lutz Lengemann
Thread type: bugfix

Core problem or goal
The zsh Git completion script (`contrib/completion/git-completion.zsh`) fails to complete commands or arguments when the global `-C <path>` option is used, due to three hard-coded assumptions: (1) the `_arguments` spec omits `-C`, (2) the command index is always 1, and (3) `-C` paths are not collected for the bash helpers. Junio C Hamano highlighted that the broader issue is the zsh wrapper’s inconsistent handling of global options compared to the bash implementation, leaving `--git-dir`, `--work-tree`, `-c`, and others similarly broken.

Current status
Patch v1 sent; no prior iterations. The 9-line fix adds `-C` to the `_arguments` spec, scans past leading `-C <path>` pairs to set `__git_cmd_idx`, and accumulates `-C` arguments into `__git_C_args` for the bash helpers. Junio’s feedback identified a design gap: the patch addresses `-C` but not other global options, and suggested aligning the zsh wrapper with the bash implementation (`__git_main` in `git-completion.bash`). D. Ben Knoble’s substantive review surfaced two technical limitations: (1) the patch’s local variables (`__git_C_args` and `i`) appear unused in the zsh wrapper despite being marked `local`, raising propagation concerns, and (2) directory completion for `-C` does not handle chained `-C` options (e.g., `git -C dir -C <tab>` completes directories in `.` instead of `dir`). Knoble also reported a separate but related bug: `git -<tab>` produces redundant and "funky" output (repeated option descriptions and a giant file listing), indicating broader `_arguments` inconsistencies. The author has not responded to either review. Knoble’s follow-up ping after three weeks of silence signals continued interest but no progress; the thread remains stalled.
