This is Junio C Hamano’s final sign-off on Matt Hunter’s 7-patch series introducing the global `fetch.followRemoteHEAD` configuration option. The series is now functionally complete and ready for merging, with all prior review feedback addressed.

The only remaining concern is a design shortcoming in how invalid configuration values are handled: the current implementation silently ignores unrecognized values for `fetch.followRemoteHEAD`, just as the existing per-remote parser does for `remote.<name>.followRemoteHEAD`. Junio suggests a more robust approach—warning or dying when an invalid value is actually used, while staying silent when the value isn’t needed—but acknowledges this isn’t a blocker. He recommends adding an in-code `NEEDSWORK` comment to flag the issue for future improvement.

The series itself is well-crafted, following established Git configuration patterns (like `fetch.prune`/`remote.*.prune`) and maintaining backward compatibility. It provides a global fallback for the per-remote `remote.<name>.followRemoteHEAD` setting introduced in Git 2.48, eliminating repetitive configuration while preserving override capability. Documentation, test coverage, and advice-system integration are all thorough. If you care about consistent fetch behavior across repositories, this is a clean, uncontroversial addition.
