This is a **reply from Patrick Steinhardt** to Junio C Hamano’s substantive review of the third patch in his four-patch series adding `git refs update`. The series aims to consolidate reference manipulation under a unified `git refs` interface.

Patrick **agrees in principle** with Junio’s concern about the lack of a dedicated "create" operation, calling the current approach (using NUL object IDs for atomic creation/deletion) "cumbersome." He proposes adding a `create` subcommand as a more intuitive alternative, which would reject updates to existing refs. This suggests the series may evolve to include a fifth subcommand in a future iteration.

He also **addresses the test coverage gap** Junio identified: the current test for "update creates a new reference" doesn’t verify failure when attempting to create an existing ref. Patrick clarifies that atomicity *is* supported (via NUL object IDs) and commits to adding a test to demonstrate this. The example he provides (`git refs update $NEW_OID $NULL_OID`) mirrors `git update-ref`’s existing behavior, reinforcing the series’ goal of consistency.

The reply is **brief but constructive**, signaling Patrick’s willingness to refine the design. The next steps will likely involve a v2 series incorporating a `create` subcommand and expanded test coverage. **Key details to watch**: how the `create` subcommand interacts with `--create-reflog` (already supported in `update`), and whether the atomicity guarantees align with `git update-ref`’s semantics. The `refs/` subsystem and CLI consistency remain central to the discussion.
