This is a thread conclusion email from Derrick Stolee, formally retracting the `[PATCH 0/3] Add ways to disable config includes` feature proposal. The author explicitly agrees with Junio C Hamano’s suggestion to mark the topic as retracted after six days of silence and substantive concerns about security trade-offs and workflow breakage.

The retraction closes a three-patch series that introduced two mechanisms (`GIT_CONFIG_INCLUDES=0` environment variable and `--no-includes` command-line option) to disable Git config include directives. The original motivation was to address sandboxing needs in a third-party build system where config includes fail by accessing unregistered files, but the discussion revealed significant drawbacks: the binary on/off switch could break legitimate workflows (e.g., work/personal email separation via conditional includes), and the partial coverage left other config vectors open, raising security concerns about piecemeal solutions. Jeff King (Peff) and Patrick Steinhardt engaged in substantive review, with Peff pushing the discussion toward a broader sandboxing approach instead of an includes-specific fix. Stolee’s final position acknowledges that the risks outweigh the benefits, and he now favors pushing back on users to avoid problematic config practices rather than implementing the feature.

The thread’s evolution—from a technical implementation discussion to a fundamental design reconsideration—highlights the tension between sandboxing requirements and Git’s flexibility. The retraction leaves the original problem (third-party tools failing due to config includes) unresolved but signals that the project is unlikely to adopt a binary disable mechanism without a more comprehensive solution. Future work may explore targeted sandboxing or allow-list approaches, but for now, the topic is closed.
