This is the third patch in Patrick Steinhardt’s five-part series adding reference-writing subcommands to `git refs`. It introduces the `git refs update` subcommand, which mirrors the behavior of `git update-ref` with a nearly identical interface: `git refs update <ref> <new-value> [<old-value>]`.

The implementation is straightforward and closely follows the pattern established in the previous patch (`git refs delete`). The subcommand supports the same options as `git update-ref`: `--message=<reason>` for reflog entries, `--no-deref` to update symbolic references directly, and `--create-reflog` to force reflog creation. It also retains `update-ref`’s implicit creation behavior: if `<old-value>` is omitted or set to all-zeroes (`0{40}`), the reference is created if it doesn’t exist; if `<new-value>` is all-zeroes, the reference is deleted. This behavior is the main point of contention in the series, as Junio C Hamano has argued for explicit atomic creation via a separate `create` subcommand (added in v2) rather than allowing `update` to create references.

The patch includes 268 lines of new tests in `t/t1465-refs-update.sh`, covering all the expected behaviors: creation, modification, deletion, symref handling, reflog creation, and error cases (invalid OIDs, mismatched old values, empty messages, wrong argument counts). The tests are thorough and follow the same style as the `delete` subcommand’s tests, making the series feel cohesive.

This is a well-crafted feature addition that fits cleanly into the `refs/` subsystem. The implementation is technically sound, with clear commit messages and robust test coverage. The only unresolved question is whether `update`’s implicit creation behavior will survive future iterations—Junio’s preference for explicit atomicity via `create` remains at odds with Patrick’s argument for backwards compatibility. For now, this patch delivers exactly what it promises: a drop-in replacement for `git update-ref` under the `git refs` umbrella.
