This is a **design discussion reply** in the ongoing thread about Patrick Steinhardt’s four-patch series adding `git refs delete`, `update`, and `rename` subcommands. The email responds to Junio C Hamano’s substantive review of the third patch, which focused on naming consistency, atomic creation semantics, and error message formatting.

Patrick acknowledges Junio’s mechanical suggestions (standardizing on `<old-value>` in the synopsis and quoting object IDs in error messages) and implements them. However, he **pushes back on the design pivot toward a dedicated `git refs create` subcommand**. Instead, he proposes retaining the current `update` subcommand’s ability to implicitly create or delete references using sentinel values (`0{40}` for deletion, `0{40}` as `<old-value>` for creation). His rationale: preserving compatibility with `git update-ref` and avoiding unnecessary restrictions on `update`.

This reply keeps the series in **design-review limbo**. The core tension remains unresolved: Junio prefers explicit, race-free creation via a dedicated `create` subcommand, while Patrick favors flexibility and backwards compatibility. The next step is likely a v2 iteration that either:
- Adds `git refs create` while keeping `update`’s implicit creation behavior (a hybrid approach), or
- Drops the implicit creation feature entirely, forcing users to choose between `create` and `update`.

For readers tracking the thread, this email signals that the series is still fluid. The outcome will shape how Git users manipulate references in the future—whether through a unified but permissive `update` command or a stricter, more explicit set of subcommands.
