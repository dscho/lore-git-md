This thread is about a small but long-overlooked bug in Git’s zsh completion: when you type `git -C <path> <command> <TAB>`, zsh fails to offer completions for the command or its arguments. The issue has been around for years, affecting a common workflow (`git -C` is widely used), but the completion script made three hard-coded assumptions that broke as soon as `-C` was involved.

The patch, sent by an author whose name isn’t yet widely recognized on the list, fixes the problem with a nine-line change to `contrib/completion/git-completion.zsh`. It teaches the zsh wrapper to recognize `-C`, scan past any leading `-C <path>` pairs to find the real command, and collect the `-C` arguments so the bash helpers run `git` in the right directory. The commit message is clear: the fix is intentionally scoped to `-C`, but the same underlying issue (a hard-coded command index) affects other global options like `--git-dir`, `--work-tree`, and `-c`, and the author is open to extending the fix in a follow-up if the list wants it.

So far there’s been no review traffic, so the patch is still in its initial state. If it lands as-is, users will get the expected completions for `git -C` without any new configuration or side effects. The broader question—whether to tackle the other global options now or later—is still open.
