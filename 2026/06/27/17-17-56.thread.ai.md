Subject: http: fix regression rejecting HTTPS proxy URLs
Series version: standalone patch (no series)
Originating author: Johannes Schindelin
Thread type: bug report and fix

Core problem or goal
A regression in commit `663d7abe07ea` (http: reject unsupported proxy URL schemes, 2026-05-05) causes Git to incorrectly reject HTTPS proxy URLs (`https://...`) as unsupported, despite the code already being configured to handle them. The fix addresses a control-flow error in `set_curl_proxy_type()` where the HTTPS branch falls through to a `return -1` intended for unknown schemes. Junio C Hamano now questions whether the function should return an error at all, suggesting a refactor to `void` to eliminate the error-return path entirely.

Current status
Patch submitted; no prior versions. The fix is a minimal, self-contained change to `http.c` (two lines added) that mirrors the early returns used for HTTP and SOCKS proxies. Junio’s review proposes an alternative design: refactoring `set_curl_proxy_type()` to return `void` instead of `int`, which would simplify the logic and remove the possibility of similar fall-through bugs. No tests are included, as the change addresses a specific logic error rather than introducing new behavior. The regression was discovered while investigating a Coverity report about unchecked `curl_easy_setopt()` calls, which are noted as orthogonal to this fix.

Key technical details
- File touched: `http.c`
- Function modified: `set_curl_proxy_type()`
- New behavior: HTTPS proxy URLs are now correctly accepted and configured
- Old behavior: HTTPS proxy URLs were incorrectly rejected due to fall-through to `return -1`
- Proposed refactor: change `set_curl_proxy_type()` to return `void`, removing the error-return path
- Subsystem: HTTP transport layer, specifically proxy URL validation in `get_curl_handle()`
- No on-disk format changes or new symbols introduced

Open questions and loose ends
- Whether to refactor `set_curl_proxy_type()` to return `void` as a follow-up, tightening the function’s contract and eliminating the error-return path entirely. This would require auditing all callers to ensure they do not rely on the current error return.
