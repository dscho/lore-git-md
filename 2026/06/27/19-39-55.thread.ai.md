Thread identity
Subject: `git ls-remote` hangs with 100 % CPU on specific repository
Series version: none (user support report)
Originating author: Steffen Nurpmeso
Thread type: bug report / user support

Core problem or goal
A user reported that `git ls-remote https://gitlab.xiph.org/xiph/opus.git` initially entered an apparent infinite loop consuming 100 % CPU, then later exhibited a low-speed timeout instead of the busy-loop. The issue is tied to constrained network conditions (possibly involving the Anubis proxy) and remains unresolved at the code level.

Current status
The original busy-loop symptom has not recurred, but the command now fails with a low-speed timeout unless `http.lowSpeedLimit` and `http.lowSpeedTime` are adjusted. No patch or merge has been produced; the root cause inside Git is still unidentified.

Key technical details
Command: `git ls-remote`
Repository URL: `https://gitlab.xiph.org/xiph/opus.git`
Suspected external factors: Anubis proxy rate-limiting, constrained network conditions
Debugging tools used: `GIT_TRACE_CURL=1`
Work-around configuration: `http.version=HTTP/1.1`, `http.lowSpeedLimit`, `http.lowSpeedTime` (all acknowledged as debugging aids, not recommended settings)
New symptom: low-speed timeout instead of busy-loop under identical network constraints

Open questions and loose ends
- The root cause of both the original busy-loop and the subsequent low-speed timeout inside Git remains unknown.
- No confirmation whether the issue is reproducible on other networks or after bypassing the proxy.
- No similar reports from other users of the same repository have been recorded.
- The process still blocks indefinitely without progress feedback, even when the timeout is avoided.
