This is a follow-up in the `git replay --linearize` thread, now fully merged but with a newly identified behavioral edge case. Phillip Wood chimes in to clarify how the current implementation differs from traditional flattening rebase (`git rebase --no-rebase-merges`).

Phillip confirms Junio’s observation: `git replay --linearize` does not flatten merge topologies the same way rebase does. Instead of replaying both sides of a merge (X and Y) to produce a linear history (X' followed by Y'), `git replay` grafts only one branch (the first-parent chain) onto the new history, leaving the other branch dangling. This means one side of the merge is silently discarded, which could surprise users expecting behavior equivalent to `git rebase --no-rebase-merges`.

The distinction is subtle but important. Rebase’s flattening logic cherry-picks *all* commits in the revision range (excluding merges), while `git replay` cherry-picks each commit onto its rewritten parent, effectively preserving the first-parent chain but dropping the rest. Phillip’s explanation reinforces Junio’s earlier test case, which proposed documenting this behavior or giving users control over which branch survives.
