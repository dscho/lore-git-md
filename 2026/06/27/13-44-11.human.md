This is the third patch in the `git replay --linearize` feature series, now at v5. Phillip Wood joins the thread to clarify a key behavioral difference between `git replay --linearize` and `git rebase --no-rebase-merges`.

Phillip confirms Junio’s observation: `git rebase --no-rebase-merges` flattens a divergent merge by rewriting *both* branches and dropping the merge commit, producing a linear history like `A->X'->Y'`. In contrast, `git replay --linearize` drops the merge commit and keeps only *one* branch (either `X'` or `Y'`), leaving the other branch dangling. This is not a bug but a fundamental difference in how the two commands handle topology flattening.

The discussion does not propose changing the current behavior; instead, it reinforces the need for clear documentation and a test to lock in the semantics. Junio’s proposed test (included in the email) creates a true divergent merge (`base->X` and `base->Y` merging at `Z`) and verifies that only one of `X` or `Y` survives after `--linearize`. This test would serve as a regression guard and a concrete example for users.
