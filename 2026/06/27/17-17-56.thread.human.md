This thread is about a small but important bugfix in Git’s HTTP transport layer. Johannes Schindelin identified a regression introduced in commit `663d7abe07ea` (May 2026), which mistakenly rejects HTTPS proxy URLs (`https://...`) as unsupported, even though the code is already set up to handle them. The issue is a control-flow error in `set_curl_proxy_type()`: the HTTPS branch configures the CURL handle correctly but then falls through to a `return -1` meant for unknown schemes. The fix adds an explicit `return 0` after HTTPS setup, matching the pattern used for HTTP and SOCKS proxies.

The patch is minimal—just two lines in `http.c`—and the commit message clearly explains the problem, the regressing commit, and the fix. No tests are included, but the change is self-contained and addresses a specific logic error rather than new behavior. The regression was likely spotted while investigating a Coverity report about unchecked `curl_easy_setopt()` calls, though those are unrelated to this fix. There’s no controversy or edge cases here; it’s a straightforward correctness fix for proxy URL validation in `get_curl_handle()`, which runs whenever Git makes HTTP/HTTPS requests via libcurl. The patch is part of GitGitGadget PR 2161 but stands alone.
