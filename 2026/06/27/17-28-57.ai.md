This is patch 3/7 in the v2 series extending `` `git log -L` `` to support range-scoped diff stat formats, whitespace checking, and the ``-G`` pickaxe. The patch fixes an off-by-one bug in the hunk headers produced by the line-range filter, ensuring they match the format used by `` `git diff` `` exactly.

The bug manifests when one side of a hunk has no lines (count 0), such as the old side of a pure insertion. The hand-rolled hunk header code incorrectly used the line number of the change itself as the begin value, whereas `` `git diff` `` and xdiff’s own emitter use the line *before* the change. This produced headers like ``@@ -25,0 +18,9 @@`` in a 24-line file, where the correct header should be ``@@ -24,0 +18,9 @@``. The patch replaces the hand-rolled header logic with a new ``xdiff_emit_hunk_header()`` helper that wraps xdiff’s own ``xdl_emit_hunk_hdr()``, ensuring consistency with the rest of Git’s diff output. As a side effect, the patch also aligns the omission of a count of 1 (``@@ -22 +22 @@`` instead of ``@@ -22,1 +22,1 @@``), another small but visible difference from `` `git diff` ``.

The change touches ``diff.c`` and adds the new helper to ``xdiff-interface.c`` and its header. The test fixtures in ``t/t4211-line-log.sh`` are regenerated to reflect the corrected headers, with two edge cases now fixed: the ``no-assertion-error`` test (which has carried the bug since its introduction in 2025) and the ``vanishes-early`` test (which regressed when the line-log output was routed through the standard diff pipeline). The patch is purely a bugfix and does not change the line-range filter’s core logic, but it is a prerequisite for the later patches that reuse the filter for stat and whitespace checks.

The implementation is clean and well-motivated: the commit message clearly explains the off-by-one, the test cases that expose it, and the rationale for reusing xdiff’s emitter. The new helper is minimal and self-contained, and the test updates are mechanical. No new edge cases are introduced, and the patch does not interact with the series’ later features (stat, whitespace, or pickaxe). The only open question is whether the change might affect downstream tools that parse ``-L`` output, but the commit message justifies the change as a correctness fix, and the test updates suggest the project considers this the expected behavior.
