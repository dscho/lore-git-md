This is a **substantive review** of patch 10/13 in the `git cat-file --batch-command` remote object-info series, focusing on the client-side implementation. Karthik Nayak raises several technical concerns about the patch’s design, error handling, and integration with the transport layer.

The review centers on three main issues. First, **documentation and abstraction**: the patch’s comments and commit message unnecessarily tie the new `fetch-object-info.c` code to `git cat-file`, even though the functionality is meant to be generic and reusable. Karthik suggests rewording to focus on the function’s purpose rather than its current user.

Second, **error handling and robustness**: the patch silently skips objects that lack size data (returning empty strings instead of failing), which Karthik argues is problematic. He points out that this creates ambiguity about whether the command succeeded or failed, and complicates future extensibility by requiring a "missing value" token that must avoid conflicting with valid data. He also notes that the code does not validate server responses strictly enough—it should `BUG()` if the server returns an unsupported field, and it should clarify whether the absence of a requested field (like "size") is an error or a valid outcome.

Third, **transport layer integration**: the patch piggybacks on `fetch_refs_via_pack()` rather than adding a dedicated vtable entry for object-info queries, which Karthik finds architecturally awkward. He questions whether this violates the function’s contract and suggests updating the transport API documentation to reflect the new behavior. He also flags redundant code in `transport-helper.c` and an incorrect commit message reference to `git cat-file` (which isn’t introduced until the next patch).

The review is **substantive**—it engages with the patch’s design choices, error-handling philosophy, and integration strategy, not just surface-level nits. Karthik’s feedback is likely to require non-trivial changes to the patch, particularly around error handling and transport layer cleanliness. The discussion about silent failures versus explicit errors could also spark broader debate about the series’ user-facing behavior.
