The `git history squash` feature, proposed by Harald Nordgren, is nearing completion with its seventh iteration but remains held up by three key design questions. The command aims to collapse a commit range into its oldest commit while preserving descendant history, offering a more efficient alternative to interactive rebase for large ranges. Junio C Hamano has signaled intent to merge the series ("Will replace"), but Phillip Wood's latest review highlights unresolved usability and correctness gaps that may require an eighth version.

Harald has addressed most prior feedback in v7: the command now rejects ranges whose oldest commit is a `fixup!`/`squash!`/`amend!`, adopts a squash-message template intended to match `git rebase -i`'s behavior, and includes stricter input validation. However, Phillip's follow-up identifies critical deviations from established Git patterns. The most pressing issue is the `--reedit-message` template, which currently preserves the original commit order rather than reordering `fixup!`/`squash!` markers after their targets—a behavior users expect from `git rebase -i`. Harald has agreed to explore this change, but it may not make v8. Additionally, Phillip argues the command should check *all* commits in the range (not just the oldest) for marker targets outside the squashed range, warning that the current implementation could produce misleading results for edge cases like nested markers. While Harald acknowledges the need, he notes this would significantly increase complexity.

The debate over whether `--reedit-message` should be the default remains open. Phillip frames this as a commit hygiene issue, noting that `git rebase -i` forces users to review squashed messages by default. Harald has dismissed this concern, but Phillip's persistent questioning suggests the maintainers may need to weigh in. The series is otherwise functionally complete, with Junio's "Will replace" indicating readiness for integration once these final questions are resolved. A v8 is likely needed to address the template reordering and expanded input validation, while the default behavior question may require broader consensus.
