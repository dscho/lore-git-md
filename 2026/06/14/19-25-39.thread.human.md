The `git history squash` feature, proposed by Harald Nordgren, is now in its ninth iteration and ready for integration. This new Git subcommand efficiently collapses a range of commits—including those with merge commits—into a single commit while preserving descendant history, avoiding the repeated conflict stops of a rebase-based approach. All prior feedback has been addressed, including critical fixes for `rev-list` option validation and `amend!` message handling, and Junio C Hamano has signaled his intent to queue the series for the next release.

The implementation is functionally complete, with key improvements like autosquash alignment (matching `git rebase -i --autosquash` behavior), robust input validation, and a `--reedit-message` option that lets users interactively combine commit messages. The command rejects operations with refs pointing to commits inside the squashed range by default, guiding users to `--update-refs=head` to explicitly retarget the current branch. While there’s a minor unresolved debate about whether `--reedit-message` should be the default for commit hygiene, this doesn’t block integration.

Notably, Junio has endorsed D. Ben Knoble’s vision of using `git history squash` and `git replay` as a faster, non-interactive backend for `git rebase --autosquash`. This architectural shift—aiming to replace the internals of `git rebase -i` entirely—positions the `squash` command as a foundational piece of Git’s future history-editing infrastructure. The series is technically sound and awaits formal queuing in Junio’s next "What's cooking" report.
