Harald Nordgren’s `git history squash` series, now at v3 and queued in `next`, proposes a new subcommand to collapse a commit range into a single commit while preserving descendant history. The series has already pivoted from a `git rebase --squash` approach to a standalone `git history squash` command, addressing earlier efficiency and UX concerns. The most recent design question—how to handle refs pointing to commits inside the squashed range—was resolved by Patrick Steinhardt: the operation will reject by default unless the user explicitly opts in with `--update-refs[=head]`, avoiding silent orphaning of refs like bisection markers.

The series is now facing a fresh round of technical scrutiny. In a detailed review of the core implementation, Patrick Steinhardt identified three edge cases in the range-resolution logic: the function currently accepts any string as a revision range without upfront validation, risks including commits outside the ancestry path of the range’s oldest commit, and silently discards intermediate merge commits without clarifying whether the range’s tip or base should be allowed to be merges. These issues don’t challenge the design direction but could lead to cryptic errors or unintended behavior. The earlier consensus on ref handling remains intact, and the series is still in `next` pending updates to address these implementation details. Harald has not yet responded to the review.
