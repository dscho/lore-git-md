The `git history squash` feature, recently queued in `next`, is facing a late-stage design question about how it should handle branch or tag refs pointing to commits *inside* the squashed range. The series—now at v3 with 4 patches by Harald Nordgren—was applied after addressing all prior feedback, including efficiency concerns (single three-way merge) and UX improvements (full commit message templating via `--reedit-message`).

Junio C Hamano has raised an edge case: when squashing a range like `o---A---B---C` into `o---X`, what should happen to refs pointing to `A` or `B`? He contrasts `git replay` (which rewrites all refs) with `git rebase` (which updates only the target branch unless `--update-refs` is used) and asks whether `git history squash` should adopt the rebase model. If `--update-refs` is enabled, should such refs be *removed* (since they may represent manual bisection markers that lose meaning) or *retargeted* to the squashed commit `X`? Junio leans toward removal but leaves the question open, framing it as a broader `git history` command design decision for Patrick Steinhardt.

The thread remains open, but this is not a blocker—just a clarification needed before the feature graduates to `master`. Expect follow-up from Harald and Patrick to settle the behavior. The rest of the implementation (range parsing, merge logic, message templating) is unchanged and uncontested.
