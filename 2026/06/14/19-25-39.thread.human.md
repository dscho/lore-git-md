Here’s the human-mode summary for a developer catching up:

The `git history squash` feature, proposed by Harald Nordgren, is now in its eighth iteration and effectively complete. This new subcommand collapses a commit range into its oldest commit while preserving descendant history, offering a more efficient alternative to the conflict-prone rebase workflow. The latest version (v8) addresses all prior feedback, including a critical regression where `rev-list` options like `--reverse` could silently distort the resolved range—this is now fixed by forcing the walk order back to `--reverse --topo-order` and warning if user options would interfere.

Key improvements in v8 include full alignment with `git rebase -i --autosquash`: the `--reedit-message` template now groups `fixup!`, `squash!`, and `amend!` commits under their targets, making the editor experience consistent with interactive rebase. The command also relaxes its handling of fixup/squash markers—rejecting only those whose targets lie outside the range—so multiple fixups for the same in-range commit can fold together cleanly. Merge commits are allowed as long as the range has a single base, and interior merges are preserved.

The series touches `builtin/history.c` (core implementation), `sequencer.c` (reused helpers for autosquash grouping), and adds extensive tests in `t/t3455-history-squash.sh`. Junio’s earlier "Will replace" sign-off on v7 suggests this version is likely to be queued for the next release. The only unresolved discussion is whether `--reedit-message` should be the default, but this is a minor usability tweak that doesn’t block integration. The implementation is now technically sound and ready for wider use.
