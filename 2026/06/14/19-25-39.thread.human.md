The `git history squash` feature, proposed by Harald Nordgren in its sixth iteration, is nearing completion after addressing all prior feedback. This tool allows users to collapse a range of commits—including those with merge commits—into a single commit while preserving descendant history, offering a more efficient alternative to the conflict-prone rebase workflow.

The latest version (v6) has resolved key technical concerns, including input validation (now using shape-based checks to reject malformed histories), merge commit handling (rejecting those with external parents while allowing fully contained merges), and the `--reedit-message` flag, which now omits `fixup!`/`amend!` noise and presents a cleaner template with minimal visual separation. The series also supports flexible input syntax (e.g., `HEAD~3.. ^topic`) and includes robust test coverage. Junio Hamano, Phillip Wood, and Patrick Steinhardt have all weighed in, with their feedback incorporated into the final design.

A recent user test by Matt Hunter, while largely positive, raised a few usability questions. Hunter endorsed Phillip Wood’s critique of the `--reedit-message` template, suggesting it could be even more streamlined by omitting fully commented-out `fixup!` messages while retaining a summary list of commit subjects. He also wondered whether `squash!` messages should be treated differently from `fixup!` messages (which are currently discarded) and questioned why `--reedit-message` isn’t the default, given that users often follow `git history squash` with `git history reword`. Additionally, Hunter noted a potential recoverability issue if `--update-refs` moves branches unexpectedly, though this isn’t specific to the squash feature.

The series is now code-complete and awaiting Junio’s final review. While Matt’s feedback highlights minor usability tweaks—such as template formatting or default behavior—no further design changes are expected. The only remaining open questions are whether to adjust the template for even greater clarity and whether to make `--reedit-message` the default, both of which are usability considerations rather than technical blockers.
