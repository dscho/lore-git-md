Here’s the human-readable summary for a developer catching up on the thread:

The `git history squash` feature, proposed by Harald Nordgren, has reached its seventh iteration and is now effectively complete. The command lets users collapse a range of commits—including those with merge commits, as long as all parents are within the range—into a single commit while preserving descendant history. This avoids the repeated conflict stops that a rebase-based approach would require.

Key improvements in v7 addressed all prior feedback: stricter input validation (rejecting ranges whose oldest commit is a `fixup!`, `squash!`, or `amend!`), alignment of the `--reedit-message` template with `git rebase -i`’s squash behavior, reordered CLI usage, and expanded documentation. The series also introduced a safety mechanism that rejects operations if any refs point to commits inside the squashed range, with an advice message guiding users to `--update-refs=head` to explicitly retarget the current branch.

Phillip Wood’s substantive review raised lingering usability questions—whether `--reedit-message` should be the default, whether the template should reorder commits to match `rebase -i`’s autosquash behavior, and whether to reject ranges where a non-oldest marker’s target lies outside the range. However, Junio C Hamano’s latest reply signals the series is ready for integration, noting the v7 changes as reasonable and giving his maintainer sign-off. The feature is now queued for the next release, with no further design changes expected.
