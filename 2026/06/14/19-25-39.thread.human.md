The `git history squash` feature, proposed by Harald Nordgren, is nearing completion but still has a few rough edges to smooth out before it’s ready for merging. The command is designed to collapse a range of commits—whether linear or containing merges—into a single commit while preserving descendant history, offering a more efficient alternative to the conflict-prone rebase approach.

The current implementation (v5) is functionally complete, with a new `git history squash` subcommand that performs a three-way merge of the specified range against the oldest commit’s parent and replays descendants on top. It rejects operations where refs point to commits inside the squashed range by default, guiding users to explicitly retarget their branch with `--update-refs=head`. The `--reedit-message` flag lets users edit the squash commit message, seeding the editor with all folded-in commit messages in chronological order. The series also refactors some plumbing, like adding a `message_template` parameter to `commit_tree_ext()`, to support this functionality cleanly.

Phillip Wood’s recent review highlighted several usability gaps that Harald now plans to address in v6. These include tightening input validation to reject single-commit ranges (e.g., `@^!`) and ranges that aren’t ancestors of `HEAD`, as well as clarifying how the command handles `fixup!`, `squash!`, and `amend!` commits—particularly whether `amend!` messages can reword the squashed commit. Phillip also raised concerns about merge commits with parents outside the range, which the current tests don’t cover. Harald agreed to tackle these issues but pushed back on a minor syntax suggestion, preferring the existing `<base>..<tip>` form over a proposed two-argument alternative.

The core design has already been settled, with Junio and Patrick Steinhardt signing off on the ref-handling logic and other key aspects. Once Harald addresses the remaining edge cases, expands test coverage, and clarifies the documentation, Junio will likely give the series a final review. No further design changes are expected, so the focus now is on polishing the implementation to handle real-world use cases robustly.
