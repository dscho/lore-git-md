The `git history squash` command, proposed by Harald Nordgren, is now in its 11th iteration and functionally complete, ready for integration into the next Git release. The command efficiently collapses a commit range (including merges) into its oldest commit while preserving descendant history, avoiding the repeated conflict stops of a rebase-based approach. After extensive review, the design has stabilized around key decisions: message editing is now the default (with `--no-edit` as an opt-out), the command rejects operations that would leave local branches dangling (with advice to use `--update-refs=head`), and it enforces strict input validation—including rejecting ranges with multiple tips, root commits, or ambiguous boundaries.

Phillip Wood’s thorough reviews have shaped much of the final implementation. His latest contribution is a critical bugfix for merge commits: when squashing a range whose oldest commit is a merge, the command now correctly preserves all parents of the merge (previously, it would drop all but the first parent). This aligns with Git’s existing behavior in `git commit` and `git merge` and prevents silent history corruption. The fix is small but essential, and while Harald’s v11 series is already queued for merging, this patch remains relevant for future iterations or backports.

The thread has also clarified a long-term vision: Junio Hamano and D. Ben Knoble endorse using `git history squash` as a faster, non-interactive backend for `git rebase --autosquash` when combined with `git replay`. This would eliminate the performance penalty of the current rebase implementation in common cases. While not part of the immediate merge, this aspiration positions the `squash` command as a foundational piece of Git’s evolving history-editing infrastructure.

All technical feedback has been addressed, including Phillip’s earlier patches on stricter range validation, ref-handling refinements, and message preservation rules. The series is now awaiting Junio’s formal queuing in `next`, with no open questions blocking integration. The only remaining discussion points are forward-looking: how `squash` might integrate with `rebase` in the future, and whether Phillip’s stricter message-preservation rules (requiring explicit `--reedit-message` for `squash!`/`amend!` commits) will influence later versions. For now, the command is ready for use as a standalone tool.
