Here’s the human-mode summary for a developer catching up on the thread:

The `git history squash` command, proposed by Harald Nordgren, is now functionally complete in its 13th iteration and ready for integration. The feature collapses a commit range (including merges) into its oldest commit while preserving descendant history, offering a faster alternative to `git rebase -i` for linearizing history without repeated conflict resolution. The series has addressed all prior technical feedback, including stricter range validation, merge-parent preservation, and ref-handling protections.

Key improvements in v13 include a structural split into eight focused patches, making the 1,500-line core implementation more digestible for review. The command now opens an editor by default with an autosquash-style template (matching `git rebase -i --autosquash`), while `--no-edit` skips editing and uses the oldest commit’s message or the last `amend!` targeting it. Stricter validation rejects ranges reaching root commits, multiple tips, or external parents, and protects all local branches descended from the squashed range unless explicitly retargeted with `--update-refs=head`. Phillip Wood’s review patches—covering range validation, merge-parent preservation, and ref-handling—have been fully adopted, along with his fixup patches for edge cases like multi-tip rejection and root-commit errors.

The series has strong maintainer support, with Junio C Hamano marking it "Will replace" in v7 and endorsing its use as a backend for `git rebase --autosquash` when combined with `git replay`. While Harald initially expressed frustration with Git’s asynchronous review process, v13’s decomposition suggests an attempt to accommodate incremental review. The only remaining open question is whether Harald will address Phillip Wood’s final roadmap items (e.g., a ref-filter display bug in patch 3.5), but these are minor refinements rather than blockers. The series is technically complete and likely to land in `next` soon.
