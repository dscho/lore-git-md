Proposal to fold commit ranges into a single commit, implemented as `git history squash` standalone subcommand after architectural pivot from `git rebase --squash`. **Series v3 (4 patches) by Harald Nordgren remains queued in `next`** but requires updates to address **three technical concerns** about range-resolution logic; the ref-handling design is now **fully finalized** after Junio C Hamano’s endorsement.

Core problem: efficiently collapse a linear or merge-commit-containing range (`@~3..`, `@~5..@~2`) into its oldest commit while preserving descendant history, avoiding the repeated conflict stops of a rebase-based approach. **Finalized behavior**: refs pointing to commits inside the squashed range (e.g., `o---A---B---C` → `o---X`) will **be detected and rejected by default**, with an `advice()` message suggesting `--update-refs` (or `--update-refs=head`) to explicitly retarget them to the squashed commit.

Implementation details (unchanged unless noted):
- New subcommand `git history squash [--reedit-message] [--update-refs[=head]] <range>`

- Rejects ranges with multiple bases
- `--reedit-message` seeds editor with **all folded-in commit messages** (oldest first) via `build_squash_message()`

**Technical concerns (Patrick Steinhardt, unresolved)**:
1. **Input validation**: `resolve_squash_range()` accepts any string as a revision range without upfront syntax checking, risking cryptic errors later.
2. **Ancestry ambiguity**: The current `--boundary` traversal may include commits outside the ancestry path of the range’s oldest commit, potentially yielding multiple boundary commits even when a single unambiguous base exists. Adding `--ancestry-path` would tighten the resolution.
3. **Merge commit handling**: The code silently discards intermediate merge commits, which is probably correct, but Patrick questions whether the same logic should apply to the range’s tip or base if they are merges. The current implementation does not explicitly restrict them, while `setup_revwalk()` (used later in `cmd_history_squash()`) filters out merges, creating a potential inconsistency.

**Design resolution (Patrick Steinhardt, Junio C Hamano)**:
- **Default behavior**: Reject the operation if any refs point to commits inside the squashed range, with an `advice()` message guiding users to `--update-refs[=head]`.
- **Rationale**: Avoids surprising users by silently orphaning refs (e.g., bisection markers) or retargeting them without clear justification. The conservative approach allows future iteration.
- **`--update-refs` flag**: Modeled after `git rebase`; supports `=head` to retarget refs to the squashed commit (e.g., `--update-refs=head`).
