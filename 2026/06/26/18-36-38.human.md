This is the latest update in the ongoing `git history squash` feature series, now targeting a v6 release. Harald Nordgren acknowledges Junio C Hamano’s feedback about the command’s input syntax limitation—specifically, that the current `<base>..<tip>` design cannot handle complex workflows like excluding certain branches. Harald signals openness to exploring multi-argument support (e.g., `git history squash ^main HEAD^{/base}..:/tip`) but does not yet propose a concrete implementation.

The series remains focused on folding a commit range into a single commit via a three-way merge, with strict validation for ancestry, refs pointing inside the range, and merge commit handling. While core functionality is complete, v6 will address Phillip Wood’s review gaps: stricter input validation (rejecting single-commit ranges and non-ancestor ranges), handling of `fixup!`/`squash!`/`amend!` commits, and clearer documentation of edge cases like merges with external parents. The ref-handling design—rejecting operations with interior refs by default, with `--update-refs=head` as a workaround—has been finalized.

This email is brief but significant: it confirms the series is still active and that a key usability limitation (input syntax flexibility) may be revisited. For now, the `<base>..<tip>` form remains the only supported syntax, but Harald’s willingness to explore alternatives suggests this could change in a future iteration. The patch is well-motivated and technically sound, but the input syntax debate highlights a potential friction point for users with complex workflows.
