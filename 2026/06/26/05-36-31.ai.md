This is the third patch in the `git replay --linearize` series, continuing the discussion about the interface design for handling merge commits. Toon Claes responds to Patrick Steinhardt’s review of patch 3/3, engaging with the forward-looking question of whether `--linearize` should mirror `git rebase`'s three-mode interface (`--no-rebase-merges`, `--rebase-merges`, and `--rebase-merges=rebase-cousins`).

Toon acknowledges the validity of Patrick’s concern but does not propose an immediate design change. Instead, he outlines a possible future evolution of the command-line interface: the default behavior would replay merges while preserving topology (aligning with Johannes Schindelin’s earlier merge-replay work), `--linearize` would flatten merges (the current patch), `--no-merges` would abort on merges (restoring the pre-patch behavior), and `--replay-cousins` would replicate `git rebase --rebase-merges=rebase-cousins`. He notes that these options are mutually exclusive and could be expressed either as separate flags or as a single `--replay-merges=<mode>` option, though he personally prefers separate flags for usability. Toon emphasizes that the internal data structure does not need to correlate 1:1 with the CLI design and that the code can evolve later to support additional modes. He concludes that adding `--linearize` now is acceptable and that future options can be introduced incrementally.

Toon also addresses Patrick’s surface-level nit about the BUG message capitalization, agreeing to lowercase the first word (`"linearizing"`), and briefly discusses whether the error message for merge commits should hint at the `--linearize` option, ultimately deciding against it because the `replay_revisions` function cannot assume it is being called by `git replay`.

The email does not resolve the interface design question but clarifies Toon’s thinking and signals openness to future extension. The series remains under review, with the only remaining technical loose end being the unresolved `enum replay_mode` refactoring in patch 1 (which Toon has already agreed to revisit). No new code changes are introduced in this reply.
