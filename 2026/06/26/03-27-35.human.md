This is a **CI/platform-compatibility** follow-up in the ongoing macOS CI hang investigation. Michael Montalbo now identifies **Apache’s `mod_http2` as the likely culprit** behind the `curl 18` mid-transfer aborts and HTTP/2 hangs, filing an upstream bug report and proposing a potential fix. The issue manifests differently across HTTP/1.1 (connection closed, triggering `curl 18`) and HTTP/2 (stream not reset, causing indefinite hangs), but both stem from the same root cause: Apache’s timeout mechanism failing to properly handle stalled transfers. Montalbo confirms the problem is reproducible without Git (using only Apache and a quiet CGI script) and persists across multiple curl versions, ruling out Git or curl as the source.

To mitigate the issue while waiting for an upstream Apache fix, Montalbo proposes enabling Git’s existing but disabled **stall-based timeout mechanism** (`http.lowSpeedLimit` and `http.lowSpeedTime`) for HTTP tests. This would convert indefinite hangs into bounded failures, making CI flakes fail fast and loudly rather than silently timing out. The suggested values (1 byte/sec floor, 60-second window) are intentionally conservative to avoid false positives on slow runners. Montalbo also floats the idea of **test-level retries** (though he’s skeptical) or further optimizing slow tests, but focuses on the stall timeout as the most actionable near-term solution.

The patch snippet provided is minimal and scoped to `t/lib-httpd.sh`, with the option to override the limits or disable them entirely. Montalbo seeks feedback on whether this approach is reasonable, noting that it could be narrowed further (e.g., per-command via `git -c`) if a smaller blast radius is preferred. The thread remains in diagnostic mode—no formal patch has been sent yet—but this email advances the discussion by pinpointing the upstream issue and offering a pragmatic workaround. The ball is now in the maintainers’ court to weigh the trade-offs of enabling the timeout versus waiting for an Apache fix.
