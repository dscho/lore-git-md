This is the third and final patch in the v5 series introducing the `--linearize` option to `git replay`. It implements the core functionality: when `--linearize` is specified, `git replay` skips merge commits and replays only non-merge commits, flattening the commit topology to match the behavior of `git rebase --no-rebase-merges`. The patch is technically complete, addressing all prior feedback and fixing a bug in `--onto` handling when replaying multiple divergent branches.

The implementation touches `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, and `t/t3650-replay-basics.sh`. The key change is in `replay_revisions()`, where merge commits are now conditionally skipped when `--linearize` is active, leaving `last_commit` unchanged so that subsequent commits are replayed onto the previous non-merge commit. The option is mutually exclusive with `--revert` (enforced by `die_for_incompatible_opt2`) and documented in the man page. Test coverage is thorough, including cases for `--linearize` with `--advance`, `--revert`/`--linearize` incompatibility, replaying down to the root commit, and a new test for replaying multiple divergent branches with `--onto` (which uncovered and fixed the `replayed_base` bug).

The patch is ready for integration; all prior review feedback has been addressed, and the only remaining discussion point—whether to extend the interface now to mirror `git rebase`'s three-mode design—does not block merging the current implementation. The series is part of the broader effort to implement `git rebase` functionality on the server side, with this patch specifically targeting the default (`--no-rebase-merges`) behavior. Potential trivial conflicts with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series are noted but expected to be easy to resolve.
