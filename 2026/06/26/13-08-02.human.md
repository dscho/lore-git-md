This is a **refactoring and performance instrumentation** patch in the commit-reach subsystem, part of Tian Yuchen’s ongoing series to optimize `paint_down_to_common()`. Patch 5/8 introduces `struct paint_state`, a new data structure that replaces the old `nonstale_queue` with per-side counters (`p1_count`, `p2_count`, `pending_merge_bases`). The counters track how many commits are queued for each side (PARENT1-only, PARENT2-only, or both), enabling the early-termination optimization introduced earlier in the series.

The patch converts `paint_down_to_common()` to use `paint_state` and its helper functions (`paint_queue_put()`, `paint_queue_get()`, `paint_count_update()`). The main loop now terminates when all counters reach zero, replacing the old `max_nonstale` pointer-based check. This is behaviorally equivalent—both detect when no non-stale commits remain—but the new approach is more explicit and easier to reason about. The "pop first" form of `paint_queue_get()` (dequeue, then check counters) means the loop exits one iteration earlier in some topologies, causing a few test step counts to drop by one (e.g., `6 -> 5` in the `pending-stale` test).

The patch leaves `nonstale_queue` intact for `ahead_behind()`, avoiding a larger refactor. The exhaustive `switch` in `paint_count_update()` documents all valid flag combinations in one place, improving maintainability. The accompanying update to `Documentation/technical/paint-down-to-common.adoc` removes outdated references to `max_nonstale` and describes the new counter-based termination logic.

This is a **clean, well-motivated refactor** that prepares the ground for the next patch (6/8), which will add the early-termination optimization. The commit message clearly explains the design and the minor behavioral change (step-count reduction). The patch is **ready for review** and should be uncontroversial—it’s a mechanical restructuring with no functional regressions.
