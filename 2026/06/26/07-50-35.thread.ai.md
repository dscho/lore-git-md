Core problem or goal
Eliminate the global `excludes_file` variable by migrating it into `struct repo_config_values` as part of the ongoing libification effort. The series abstracts XDG fallback lazy-loading into a dedicated getter, adds proper heap memory management, and prepares the codebase for further modularization.

Current status
v2 is complete and under active review; both patches have received substantive feedback. The series was initially posted without threading headers, but this was acknowledged and is not expected to recur. Junio C Hamano previously approved the second patch, marking it ready for the `next` integration branch, but has now raised a **critical design concern** about the temporary guard (`if (repo != the_repository)`) in the getter and cleanup functions. This guard was intended to avoid BUG() assertions in uninitialized submodules but is now contested as potentially masking bugs. The series is at a decision point: the guard must be revisited before the patch can proceed.

Key technical details
- Files touched: `dir.c`, `environment.c`, `environment.h`, `repository.c`
- New symbols: `repo_excludes_file()` getter, `repo_config_values_clear()` helper (extended)
- Memory management: heap allocation for `excludes_file`, cleanup via extended helper; temporary global state dependency noted in TODO
- Guard: temporary `if (repo != the_repository)` in getter and cleanup to avoid BUG() in uninitialized submodules (pattern reused from prior work, now contested)
- No user-visible behavior changes; foundational for libification
- Subsystems: ignore-file handling, XDG config resolution, repository configuration

Open questions and loose ends
- **Guard design**: Junio objects to the current guard, arguing it masks bugs by bypassing BUG() checks. Alternatives include:
  - Removing the guard entirely and letting BUG() trigger (preferred by Junio for debugging)
  - Replacing it with a stricter check (e.g., `repo->initialized`)
  - Justifying the guard’s necessity more rigorously
- **Long-term libification**: The guard is intended as a temporary measure until the codebase is fully prepared for per-repository configuration. Junio suggests this preparation should happen now, not later.
- **Impact on existing lazy-loading**: No objections raised, but the guard discussion may prompt re-examination of initialization timing.
- **Submodule safety**: The guard’s original purpose (avoiding BUG() in uninitialized submodules) remains valid, but its implementation is now in question.
