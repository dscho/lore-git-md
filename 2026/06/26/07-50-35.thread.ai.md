Thread type: patch series (refactoring, libification)

Core problem or goal
Eliminate the global `excludes_file` variable by migrating it into `struct repo_config_values` as part of the ongoing libification effort. The series abstracts XDG fallback lazy-loading into a dedicated getter, adds proper heap memory management, and prepares the codebase for further modularization.

Current status
v2 is under active review; both patches have received substantive feedback. The series was initially posted without threading headers (now resolved). Junio C Hamano previously approved the second patch for the `next` branch but has since raised a **critical design concern** about the temporary guard (`if (repo != the_repository)`) in the getter and cleanup functions, arguing it masks bugs by bypassing BUG() assertions. **SZEDER Gábor identified a build-breaking issue** in the first patch: the `repo_excludes_file()` getter declares an unused `struct repository *repo` parameter, causing `-Werror=unused-parameter` failures under `DEVELOPER=1`. Junio has now proposed a **pragmatic fix** for the build issue: mark the parameter as `UNUSED` in the first patch, then remove the annotation in the second patch when the parameter is actually used. The series is at a decision point: the guard design remains contested, but the build issue now has a clear path forward. The question of whether to squash the two patches is also open.

Key technical details
- Files touched: `dir.c`, `environment.c`, `environment.h`, `repository.c`

Open questions and loose ends
- **Guard design**: Junio objects to the current guard, arguing it masks bugs by bypassing BUG() checks. Alternatives include:
  - Removing the guard entirely and letting BUG() trigger (preferred by Junio for debugging)
  - Replacing it with a stricter check (e.g., `repo->initialized`)
  - Justifying the guard’s necessity more rigorously (e.g., documenting why uninitialized submodules are expected to call this function)
- **Patch structure**: Junio mused about squashing the two patches for readability, but no decision was made. This may influence how the series evolves.
- **Long-term libification**: Junio suggests the guard’s removal should coincide with full preparation for per-repository configuration, not deferred.
- **Submodule safety**: The guard’s original purpose (avoiding BUG() in uninitialized submodules) remains valid, but its implementation is now in question.
