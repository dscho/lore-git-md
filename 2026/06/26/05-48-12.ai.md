This is the second patch in the v5 `--linearize` series for `git replay`, a pure refactoring that improves code clarity with no behavior change. It addresses the readability concerns raised in v4 about how `pick_regular_commit()` selects a base commit by adding detailed comments and renaming the `onto` parameter to `default_base`. The patch also reorders function parameters to group `struct commit` arguments together, making the interface more intuitive.

The core change is the expanded comment block explaining the logic: `pick_regular_commit()` looks up the parent of the commit being replayed in `replayed_commits` to find the ancestor to replay onto. If no ancestor is found (e.g., for the first commit in the range), it falls back to `default_base`. During reverts, commits are replayed in reverse order, so the lookup never succeeds, and `last_commit` is passed as the base instead. This clarification was prompted by Junio and Patrick Steinhardt’s feedback on the v4 `enum replay_mode` refactoring, which they felt obscured the function’s intent.

The patch also fixes a latent naming issue: the `onto` parameter was misleading because it is only used as a fallback, not as the primary base. Renaming it to `default_base` makes the function’s behavior clearer. The parameter reordering (moving `default_base` before `replayed_commits`) groups all `struct commit` arguments together, improving readability at the callsite.

This patch is uncontroversial and ready for integration. It directly responds to prior review feedback and lays the groundwork for the `--linearize` implementation in patch 3 by making the base-selection logic easier to understand. The only potential conflict is with Patrick Steinhardt’s `git history drop` series, but it is expected to be trivial to resolve.
