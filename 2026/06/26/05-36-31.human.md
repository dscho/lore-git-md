This is the third patch in the `git replay --linearize` series, now at v4. The email is Toon Claes’s reply to Patrick Steinhardt’s substantive review of the `--linearize` implementation.

Toon engages directly with Patrick’s design question about whether `--linearize` should mirror `git rebase`’s three modes (`--no-rebase-merges`, `--rebase-merges`, and `--rebase-merges=rebase-cousins`). He sketches a possible future CLI design: default behavior would replay merges preserving topology (using Johannes Schindelin’s earlier merge-replay work), `--linearize` would flatten merges (this patch), `--no-merges` would abort at merges (current behavior), and `--replay-cousins` would rebase cousins. He acknowledges that these options are mutually exclusive but prefers separate flags over a `--replay-merges=<mode>` enum-style argument. The bottom line: he sees `--linearize` as a reasonable first step that does not preclude later extension.

Toon also accepts Patrick’s surface-level nit about the BUG message capitalization and briefly discusses whether the merge-skipping comment in `replay.c` should hint at the `--linearize` option, concluding that it would be awkward since the function is not tied to `git-replay`.

The thread remains open on the interface design question, but the patch itself is technically ready: all prior feedback has been addressed, the code is clean, and the test coverage is thorough. If the project decides that `--linearize` alone is sufficient for now, this patch is likely to land as-is.
