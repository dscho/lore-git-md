This thread is about a bugfix patch from Junio C Hamano that addresses two issues in `git history --reword`: a file stream leak that could cause problems on Windows by leaving file handles open, and an inefficient file-handling pattern in `fill_commit_message()` that wrote a buffer to a file, flushed it, then reopened it in append mode. The patch has evolved to v2 after Patrick Steinhardt raised a reliability concern—the original version removed error checking on the initial `fwrite()` call, risking silent corruption if the write failed. Junio agreed to restore this check in v2, which now ensures the commit message (critical data) will either be fully written or trigger a `die()`, while non-critical status information remains at risk of truncation due to a broader, deferred issue in `wt_status_print()`.

The fix is straightforward and well-contained: it consolidates file handling into a single stream opened for writing, eliminates the redundant reopen, and closes the stream before launching the editor. This resolves the Windows compatibility issue and restores the missing error checking without introducing new risks. The broader `wt_status_print()` problem—where status information could still be silently truncated—is acknowledged but explicitly left for a future patch. No other reviewers have weighed in on whether that should be addressed separately.

The patch touches only `builtin/history.c` and modifies `fill_commit_message()` to replace the old two-phase file handling with a single, more efficient approach. It’s been tested and is considered merge-ready for its original goals, with the v2 changes addressing Patrick’s feedback. The issue was introduced in January 2026 (commit d205234c), and the fix is now uncontested.
