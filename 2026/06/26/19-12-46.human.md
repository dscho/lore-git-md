This is the maintainer's review of the second patch in Tian Yuchen's two-patch series to move the `excludes_file` global variable into `struct repo_config_values` as part of the libification effort. The patch itself is a refactoring that adds proper heap memory management and updates the configuration system, but Junio C Hamano raises fundamental concerns about the approach.

Junio questions the temporary guard (`if (repo != the_repository)`) that prevents BUG() assertions in uninitialized submodules. He suggests this guard might be masking real issues: if `repo_config_values()` is designed to BUG() when called on an uninitialized repository, then silently skipping the cleanup (or the getter) could hide bugs rather than fix them. He proposes either making the guard more explicit (e.g., checking `repo->initialized`) or removing it entirely to let the BUG() surface, arguing that the rest of the codebase should eventually handle per-repository configuration properly.

The review also challenges the null-check on `repo_config_values()`: if the function is expected to always return a valid pointer for an initialized repository, then returning early on NULL could again hide problems. Junio’s tone suggests he sees these workarounds as technical debt that should not be carried forward. His closing remark—"Let it be noticed by repo_config_values() function to catch offending callers for now"—implies he prefers the patch fail fast rather than silently skip operations.

This is a substantive review that goes beyond surface-level feedback. It targets the core design choice of the patch and could require a significant rework if the author follows Junio’s suggestion to remove the guard. The thread is now at a crossroads: the patch was previously approved for `next`, but this review may delay that until the guard issue is resolved. Readers following the libification effort should watch whether Tian revises the patch or whether other reviewers weigh in on the trade-off between safety and strictness.
