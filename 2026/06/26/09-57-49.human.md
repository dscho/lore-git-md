This is the latest update in the `git history squash` feature series, where Harald Nordgren responds to Phillip Wood’s substantive review of v5. The patch series proposes a new `` `git history squash` `` subcommand to fold a commit range into a single commit while preserving descendant history, avoiding the conflict-prone rebase workflow.

Harald acknowledges Phillip’s concerns about edge cases—single-commit ranges (e.g., `@^!`), non-ancestor ranges, and the command’s single-argument limitation—and agrees to address them. However, he pushes back on one point: Phillip’s suggestion to allow two separate revisions (e.g., `` `git history squash ^:/base :/tip` ``) instead of the current `<base>..<tip>` syntax. Harald argues the existing syntax is clearer and functionally equivalent, though this may remain a point of discussion.

The core design (three-way merge, ref-handling logic, `--reedit-message`) is settled, but Phillip’s feedback highlights lingering usability gaps. The next revision will likely tighten input validation, clarify error messages, and document behavior for `fixup!`/`squash!`/`amend!` commits and merge commits with external parents. The series is otherwise code-complete and well-tested for complex merge topologies, but these edge cases need resolution before Junio’s final review. If you’re following Git’s history-editing tools, this is worth monitoring for the final polish.
