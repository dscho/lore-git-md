Core problem or goal
Fix two related issues in `git history --reword`: (1) an inefficient file-handling pattern in `fill_commit_message()` that wrote a buffer to a file, flushed it, then reopened the file in append mode; (2) a file stream leak that could cause problems on Windows by leaving the file handle open before launching the external editor. The patch also restores explicit error checking on the initial `fwrite()` call, addressing a reliability concern raised by Patrick Steinhardt in the v1 review. The broader error-handling gap in `wt_status_print()` is acknowledged but deferred as out of scope.

Current status
Patch v2 is now ready for review and integration. The original goals (stream leak and Windows compatibility) remain uncontested, and the reliability concern (restoring error checking on `fwrite()`) has been addressed. Patrick Steinhardt's follow-up confirms that the patch does not worsen the existing risk of silent corruption in `wt_status_print()`: the commit message (critical data) will either be fully written or trigger a `die()`, while the status information (non-critical) remains at risk of truncation. The broader `wt_status_print()` issue is explicitly deferred.

Key technical details
Files touched: `builtin/history.c`
Function modified: `fill_commit_message()`
New behavior: opens file once in write mode, writes buffer directly via `fwrite()` with explicit `die()` on failure, closes stream before editor launch
Old behavior: wrote buffer via `write_file_buf()` (which dies on failure), flushed, reopened in append mode, left stream open
Platform impact: fixes Windows compatibility issue (open file handles blocking other processes); error-checking gap affects all platforms but is now addressed for the initial write
Test coverage: no test failures or edge cases mentioned; fix is well-contained and includes explicit error checking on the initial write
Symbols/functions: `fill_commit_message()`, `fwrite()`, `fclose()`, `wt_status_print()`
