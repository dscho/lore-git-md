Subject: [PATCH] history: fix file stream leak and inefficient file handling in reword
Series version: standalone patch (v2 expected)
Originating author: Junio C Hamano
Thread type: bugfix patch

Core problem or goal
Fix two related issues in `git history --reword`: (1) an inefficient file-handling pattern in `fill_commit_message()` that writes a buffer to a file, flushes it, then reopens the file in append mode; (2) a file stream leak that can cause problems on Windows by leaving the file handle open before launching the external editor. Patrick Steinhardt's review additionally identified a latent error-handling gap: the patch removes explicit error checking on the initial file write, risking silent corruption if the write fails. Junio now agrees to restore the error check in v2.

Current status
Patch is ready for v2 to address Patrick's reliability concern (restoring error checking on `fwrite()`). The original goals (stream leak and Windows compatibility) remain uncontested and are considered merge-ready. A broader error-handling issue in `wt_status_print()` is acknowledged but deferred as out of scope for this patch.

Key technical details
Files touched: `builtin/history.c`
Function modified: `fill_commit_message()`
New behavior: opens file once in write mode, writes buffer directly via `fwrite()` with restored `die()` on failure, closes stream before editor launch
Old behavior: wrote buffer via `write_file_buf()` (which dies on failure), flushed, reopened in append mode, left stream open
Platform impact: fixes Windows compatibility issue (open file handles blocking other processes); error-checking gap affects all platforms
Test coverage: no test failures or edge cases mentioned; fix is well-contained but now includes explicit error checking on the initial write
Symbols/functions: `fill_commit_message()`, `fwrite()`, `wt_status_print()`
