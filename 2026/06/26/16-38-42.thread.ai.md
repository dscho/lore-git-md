Core problem or goal
Fix two related issues in `git history --reword`: (1) an inefficient file-handling pattern in `fill_commit_message()` that writes a buffer to a file, flushes it, then reopens the file in append mode; (2) a file stream leak that can cause problems on Windows by leaving the file handle open before launching the external editor. Patrick Steinhardt's review additionally surfaces a latent error-handling gap: the patch removes explicit error checking on the initial file write, risking silent corruption if the write fails.

Current status
Patch is ready for merge on its original goals (stream leak and Windows compatibility), but Patrick's review identifies a new reliability concern: the absence of error checking on the initial `fwrite()` call could allow a partially-written file to go unnoticed. No updated patch has been posted yet.

Key technical details
Files touched: `builtin/history.c`
Function modified: `fill_commit_message()`
New behavior: opens file once in write mode, writes buffer directly via `fwrite()`, closes stream before editor launch
Old behavior: wrote buffer via `write_file_buf()` (which dies on failure), flushed, reopened in append mode, left stream open
Platform impact: fixes Windows compatibility issue (open file handles blocking other processes); error-checking gap affects all platforms
Test coverage: no test failures or edge cases mentioned; fix is well-contained but now has an identified reliability risk

Open questions and loose ends
- Whether to restore explicit error checking on the initial `fwrite()` call, or to accept the risk of silent partial writes given that `wt_status_print()` also lacks error checking.
- No other reviewers have weighed in on Patrick's concern.
