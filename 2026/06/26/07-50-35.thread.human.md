This thread is a follow-up to the recently merged `excludes_file` migration, where Tian Yuchen is extending the libification effort by moving nine more global configuration variables into `struct repo_config_values`. The series (v7) is technically complete and CI-clean, but it’s now facing its first substantive review feedback from Junio C Hamano.

The core goal remains eliminating globals and centralizing memory management to prepare for further modularization. The series migrates editor/pager/askpass programs, apply whitespace settings, four enums (`push_default`, `autorebase`, `object_creation_mode`, `attributes_file`), and the new `askpass_program`. Tian raised two RFC questions upfront: whether migrating program paths is worthwhile (he argues yes for per-repo toolchain flexibility) and how this relates to prior discussions about `git_branch_track` (which he avoided due to complexity).

Junio’s review of patch 4/9 uncovered a potential memory leak in the migration pattern: when `pager_program` is reassigned, the old value isn’t freed. This isn’t just a nit—it’s a correctness issue that could affect other string-valued fields in `repo_config_values` (like `editor_program` or `askpass_program`). The problem is systemic: the cleanup function (`repo_config_values_clear()`) handles teardown but not intermediate re-assignments. Tian will need to address this either by freeing old values or documenting that re-assignment isn’t supported.

The series is still under review, with no other feedback yet. Open questions include Tian’s RFC points, the memory management fix, and a promised follow-up cleanup for `repo_config_values` comments. The submodule limitation (where `repo_config_values_clear()` silently returns for submodules) remains unresolved but isn’t a blocker. For now, the focus is on fixing the leak before the series can progress.
