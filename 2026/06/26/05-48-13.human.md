This is the third and final patch in the v5 series introducing the `--linearize` option to `git replay`. It implements the core functionality: when `--linearize` is specified, `git replay` drops merge commits and replays only the non-merge commits in sequence, matching the behavior of `git rebase --no-rebase-merges`. The patch is technically complete, addressing all prior review feedback, and is ready for integration.

The implementation is straightforward: when `--linearize` is active, merge commits are skipped in the replay loop, leaving the `last_commit` variable unchanged so that subsequent commits are replayed onto the previous non-merge commit. This ensures the commit topology is flattened. The option is mutually exclusive with `--revert` (enforced by `die_for_incompatible_opt2`) and is documented in the man page with a clear description of its effect. The patch also includes a bug fix for `--onto` handling when replaying multiple divergent branches, ensuring child commits are replayed onto the correct parent.

Test coverage is thorough, with new cases verifying `--linearize` works with `--advance`, that it rejects incompatible options (`--revert`), and that it produces the same patches as the original commits (verified via `git range-diff`). A particularly important test confirms the fix for the `--onto` bug: when replaying two branches (one with a merge commit) onto a common base, the resulting history is correctly linearized. The tests reuse the existing history setup, making them easy to follow.

The patch touches `replay.c`, `replay.h`, `builtin/replay.c`, `Documentation/git-replay.adoc`, and `t3650-replay-basics.sh`. The changes are confined to the replay machinery and do not affect other subsystems. The only remaining discussion point is whether to extend the interface now to mirror `git rebase`'s three-mode design (`--no-rebase-merges`, `--rebase-merges`, `--rebase-merges=rebase-cousins`) or to implement `--linearize` incrementally. Toon has outlined a possible future evolution but prefers to merge this as-is and extend later. This does not block integration.

The patch is well-crafted, with clear commit messages, good test coverage, and no unresolved technical objections. It addresses a real use case (server-side rebase implementation) and aligns with the project’s goal of making `git replay` a robust alternative to `git rebase`. The reversion of the controversial `enum replay_mode` refactoring in v5 (replaced with improved comments) resolves the readability concerns raised by Junio and Patrick Steinhardt, making this a clean, uncontroversial addition.
