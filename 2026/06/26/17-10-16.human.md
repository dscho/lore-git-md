This is Junio C Hamano's review of the final patch in Toon Claes's now-merged `git replay --linearize` series. The series itself is complete and in Junio's `seen` branch, but Junio is raising a subtle behavioral question about how `--linearize` handles divergent merge topologies.

The patch implements `--linearize` by dropping merge commits and mapping them to their first parent in the `replayed_commits` OID map. Junio observes that when replaying a history like `A -> X` and `A -> Y` merged at `Z`, the current implementation will drop `Z` and graft any descendants onto the last replayed commit (say `Y'`), leaving `X'` (and its ancestors) orphaned. The result is a linear history that contains only one of the two divergent branches, not both. This differs from a typical flattening rebase (e.g., `git rebase --no-rebase-merges`), which would replay both `X` and `Y` as linear commits, preserving both branches in the output.

Junio is not calling this a bug, but he wonders whether users might want control over which branch survives, and he suggests documenting the behavior and adding a test to lock it in. He provides a concrete test case that creates a true divergent merge (`base -> X` and `base -> Y` merged at `Z`) and verifies that only one of `X` or `Y` appears in the replayed output. The test is ready to drop into the existing test suite and would serve as both regression protection and user-facing documentation of the current behavior.
