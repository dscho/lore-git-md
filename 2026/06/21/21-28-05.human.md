This is a follow-up in the ongoing worktree diff performance thread. Jeff King (Peff) responds to Junio C Hamano’s suggestion to use nanosecond timestamp precision (`USE_NSEC`) to eliminate racy entries by proposing a minimal patch that enables nanosecond comparisons in `is_racy_stat()`. The patch removes the `USE_NSEC` guard, allowing Git to compare timestamps with full nanosecond resolution, which Peff argues should reduce raciness to near-zero in practice.

Peff’s patch is straightforward: it deletes the `#ifdef USE_NSEC` conditional in `read-cache.c`, letting Git always use nanosecond precision when comparing index and file mtimes. He adds a debug warning to help track any remaining racy entries, though he expects these to be vanishingly rare—on the order of one in a billion files—given the resolution. The patch touches only a few lines of code and does not introduce new behavior, but rather lifts an existing restriction.

The motivation is clear: with nanosecond precision, the chance of a file and the index sharing the same timestamp is negligible, so the "racy" logic that forces full content checks becomes unnecessary. Peff notes that even if a single file does collide, the performance impact is minimal. He also addresses a potential concern about `USE_NSEC` being conditional in the first place, suggesting that the original issue (nanoseconds being wiped from the kernel’s in-memory cache) does not apply when simply comparing timestamps for ordering.

This patch is a direct alternative to Junio’s earlier proposal to delay index writes by 50 milliseconds. Peff’s approach is simpler—it requires no runtime delays or platform-specific logic—and leverages existing code paths. The tradeoff is that it depends on nanosecond resolution being reliable, which may not hold on all filesystems or platforms. Peff does not address whether this should be a build-time or runtime decision, leaving that question open for further discussion.

The patch looks well-crafted and addresses the root cause of the performance issue without architectural changes. If nanosecond precision is widely supported, this could be a clean solution. However, the thread’s earlier skepticism about `USE_NSEC` reliability suggests this may not be the final word. The next steps will likely involve testing on diverse filesystems and platforms to confirm the patch’s safety.
