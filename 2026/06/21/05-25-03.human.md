This is the final review round for a security-hardened feature series that adds `git cat-file --batch-command` support for querying remote object metadata. Chandra Pratap provides a surface-level review of Pablo Sabater’s v13 patch series, focusing on two design questions raised in the cover letter.

The first question concerns how to handle unsupported format placeholders like `%(objecttype)` or future ones like `%(rest)`. The series currently returns empty strings (matching `for-each-ref` behavior), but Eric Ju previously suggested using a placeholder like `"???"`. Chandra argues against this, noting that scripts would need extra logic to handle literal question marks, and some atoms might legitimately return `"???"`. He suggests failing cleanly instead, though this would break backward compatibility with scripts expecting empty strings.

The second question is a tangent about short OID support in the object-info protocol. Chandra points out that the server (`a2ba162cda`) only accepts full OIDs, unlike local `git cat-file`, which supports short OIDs and disambiguation. He rejects the idea of a `--pick-first` option for short OIDs, as it could return wrong object info without server-side verification. He also dismisses sending a list of possible OIDs to the client, noting that Git treats disambiguation as a local UI concern, not a network operation, and `git fetch` already requires full OIDs.

The review is brief and mechanical, offering no new technical insights or code feedback. It resolves the open design question by advocating for a fail-fast approach, though this would require a breaking change. The series itself remains ready for merging, with all prior substantive feedback addressed.
