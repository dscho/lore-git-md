This is a **design discussion reply** in the ongoing pinned references thread. Jeff King (Peff) weighs in with a cautionary perspective, drawing parallels to two prior discussions where Git’s `<describeOutput>` syntax (`v2.54.0-0-g0b13e48a3`) caused unintended behavior.

Peff highlights a 2024 thread where a branch name like `foo-gcc14` was misinterpreted as a describe-style name for object `cc14`, even though no such tag existed. He argues that Git’s current lenient parsing of `<describeOutput>` is intentional: the format is designed to work even when the receiver lacks the original ref (e.g., `v2.54.0`), so enforcing strict local validation would break interoperability. While he suggests Git *could* silently fall back to treating the hex part as a raw OID if the ref is missing, he implies this might undermine the original goal of Erik Östlund’s pinned references proposal—combining human-readable refs with machine-enforced OID stability.

Peff also links to a 2025 series where Junio C Hamano explored tightening `<describeOutput>`’s rules, reinforcing that any enforcement would need to be carefully balanced against backwards compatibility. His input shifts the discussion toward practical trade-offs: strict validation risks regressions, while loose parsing sacrifices the very invariant pinned references aim to guarantee. The thread remains conceptual, with no code or implementation plans, but Peff’s feedback adds weight to the idea that a new mechanism (rather than modifying `<describeOutput>`) may be the only viable path forward.
