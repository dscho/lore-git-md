This is a technical follow-up in the ongoing worktree diff performance thread. Jeff King (Peff) proposes a concrete patch to address the root cause he previously identified: racy-git entries slipping through the counter-based guard in `git diff`, preventing index refreshes and forcing repeated expensive content checks.

The patch modifies `builtin/diff.c` to pass a new flag (`DIFF_RACY_IS_MODIFIED`) to the diff machinery when `skip_stat_unmatch` is active. This flag forces `ie_match_stat()` to treat racy entries as modified, ensuring they increment the counter and trigger an index refresh. Peff reports the patch works—subsequent `git diff` calls become fast (~30ms)—but notes a performance quirk: the first diff after the patch takes 1800ms (up from 500ms), likely because the index refresh is now done from scratch rather than reusing stat-cleanliness data.

Peff is candid about the tradeoffs: the patch fixes the immediate issue but may not be worth deeper optimization, as racy entries are cleared by any index refresh (including `git status`). The broader question remains whether this is the right architectural fix or if the counter-based guard should be replaced entirely. The patch itself is small and targeted, touching only `builtin/diff.c` and introducing a new flag to the diff machinery. It does not address the long-term direction (runtime configuration vs build-time `USE_NSEC` vs index refresh fixes) but provides a working proof-of-concept for one of the two solutions Peff previously outlined.
