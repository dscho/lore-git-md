This is the latest update in the long-running `git branch --delete-merged` series, now at v16. Harald Nordgren steps back from the proposed retargeting logic for stacked branches (e.g., updating `feature2@{u}` to `origin/master` if `feature1` is deleted) after realizing the implementation complexity. Instead, he suggests a simpler approach: **skip deletion entirely when a branch is used as an upstream for another branch**, deferring the retargeting feature to a future iteration.

The change in direction is pragmatic. The retargeting logic would require handling edge cases like recursive chains (`b1→b2→b3`) and self-referential upstreams (`b3→b3`), which Harald notes would add significant code complexity. By avoiding these cases for now, the series can proceed with a minimal, safe implementation that preserves backward compatibility. This aligns with Junio C Hamano’s earlier preference for aborting deletion when dependencies exist, though it leaves the door open for retargeting to be added later.

The patch series is otherwise complete, with all other safety mechanisms (checked-out branches, push divergence, per-branch opt-out, and `--dry-run`) already implemented and tested. This email signals that the final v17 will likely focus on adding the stacked-branch protection as a simple "abort and notify" check, rather than attempting full retargeting. For users, this means the command will err on the side of caution, requiring manual intervention to delete branches with dependencies. The trade-off is clear: less automation now for a simpler, more reliable implementation.
