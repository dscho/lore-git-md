This is a follow-up in the ongoing worktree diff performance thread, clarifying the history and design intent behind the counter-based guard in `builtin/diff.c`.

Junio expands on his earlier clarification by providing the original 2007 discussion thread that led to commit aecbf914, which introduced the `skip_stat_unmatch` counter. The link shows the patch was motivated by a real-world performance issue where `git diff` was unnecessarily refreshing the index for every invocation, even when no stat-dirty paths existed. The counter mechanism was designed to avoid this overhead by only triggering a refresh when actual ghost changes (stat-dirty but content-unchanged paths) were detected.

The email reinforces that the guard is not a bug but a deliberate optimization, though Junio acknowledges its dual-purpose nature (acting as both a boolean flag and a counter) has proven confusing. This historical context helps frame the current debate: whether to keep the existing counter-based logic, replace it with a more explicit refresh mechanism, or pursue alternative solutions like runtime timestamp precision configuration. The files involved remain `builtin/diff.c` and the diffcore subsystem, with `rev.diffopt.skip_stat_unmatch` and `diff_auto_refresh_index` as key symbols. No new technical proposals are introduced, but the clarification strengthens the case for architectural continuity.
