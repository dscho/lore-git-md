This is **patch 7/10 in the v4 refactoring series** by Patrick Steinhardt, now under **substantive review** by Jeff King (Peff). The patch addresses a long-standing recursion issue in Git’s reference backend initialization, where "onbranch" config includes trigger recursive calls to `get_main_ref_store()` during repository setup.

Peff’s review raises two core concerns. First, he identifies a **regression in config behavior**: prior to a 2024 refactoring (eafb126456), Git respected "onbranch" includes for `core.logAllRefUpdates`, but now the setting is ignored if it comes from an "onbranch" path. While Peff acknowledges this is an edge case, he worries it reflects a broader lack of clarity about when and how ref backend config is loaded. Second, he flags potential **caching hazards**: if early config reads (like `core.logAllRefUpdates`) skip "onbranch" includes, those skipped values might persist in Git’s config cache, leading to inconsistent behavior for unrelated config lookups later. He couldn’t reproduce this in testing but suspects the current approach relies on fragile ordering.

The review is **technically sharp but cautious**, avoiding a prescriptive fix. Peff suggests ref backends should initialize with minimal config (just enough for reads) and defer non-critical settings to a later, non-caching config pass. This aligns with Patrick’s broader goal of modernizing the ref backend but challenges the current patch’s workaround. The discussion is now focused on **architectural hygiene**—whether the recursion fix should be a targeted bandage (Patrick’s `ignore_refs` flag) or part of a larger refactoring to untangle config loading from ref initialization.

For readers tracking the series, this is the **most critical review** so far. Peff’s concerns don’t invalidate the patch but highlight deeper design questions that could shape future ref backend work.
