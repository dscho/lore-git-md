This is a **substantive review reply** in Patrick Steinhardt’s 10-part ref backend refactoring series, specifically addressing the recursive initialization issue in `get_main_ref_store()` triggered by "onbranch" config includes. Jeff King (Peff) responds to Patrick’s v2 patch 7/8 with a deeper technical critique of the config-parsing model, raising concerns about edge cases, caching inconsistencies, and the broader architectural implications of the current approach.

Peff clarifies his earlier suggestion: he now distinguishes between *repo metadata* (like `extensions.refStorage`, which must be read early via `read_repository_format()` and ignores includes) and *user-facing config* (like `core.logAllRefUpdates`, which should respect includes). His core concern is that the current design creates a fragile dependency where config keys needed for ref backend initialization (e.g., `core.logAllRefUpdates`) are read through the general config subsystem, which can trigger recursive ref store access via `includeif.onbranch`. He demonstrates this with a concrete example where `git commit` fails to respect an `onbranch`-scoped `core.logAllRefUpdates` setting due to the ref backend’s early config read (a regression introduced by eafb126456 in 2024).

The review highlights two risks: (1) users may unknowingly set config keys that won’t work with `onbranch` includes, and (2) the config cache could produce inconsistent states if early reads skip includes that later reads would apply. Peff admits he couldn’t reproduce the latter issue but suspects the system is "getting lucky" with current ordering. He suggests a more principled approach: ref backends should initialize with minimal config (enough for reads) and defer additional config loading to a non-caching path like `repo_config()`.

This reply shifts the discussion from a narrow recursion fix to a broader question about how ref backends should interact with the config system. Peff’s critique is substantive and tested (he bisected the regression and constructed test cases), making it a key input for Patrick’s v4 redesign. The thread’s outcome will likely influence how Git handles config parsing for ref backends long-term, particularly for future backends that may require early config access.
