This is the review summary for Justin Tobler’s six-patch series converting `git-receive-pack` from `tmp_objdir` to ODB transactions. Patrick Steinhardt’s reply is a **substantive, tested review** that signals strong support for the series’ direction while raising several technical and design issues that will need to be addressed in a v2.

The series is part of the ongoing ODB abstraction effort led by Patrick himself. It replaces the temporary object directory mechanism in `receive-pack` with the newer `odb_transaction` subsystem, staging incoming objects via transactions rather than ad-hoc directories. The immediate goal is to make `receive-pack` backend-agnostic in how it stages objects, though the actual object writes (handled by `git-index-pack` and `git-unpack-objects`) remain tied to the "files" backend for now. A follow-up series is planned to address that limitation.

Patrick’s review is thorough and constructive. He identifies a **correctness issue** in patch 3/6: `odb_transaction_begin()` can return success (0) while leaving the `out` parameter as `NULL` if a transaction is already active on the ODB. The convenience wrapper `odb_transaction_begin_or_die()` does not handle this case, risking crashes or silent failures. This is a serious concern that will need to be fixed before the series can land.

On patch 6/6, which actually replaces `tmp_objdir` in `receive-pack`, Patrick raises several **behavioral and design questions**. The patch stops adding the transaction’s object directory as an alternate (previously done via `tmp_objdir_add_as_alternate`), only propagating it through environment variables. This change isn’t documented in the commit message and could affect child processes like `git-index-pack`. He also questions the purpose and naming of the new `ODB_TRANSACTION_RECEIVE` flag, which isn’t documented in the header, and suggests the patch might be clearer if split into two (flag introduction and application in `receive-pack`). Additionally, he notes that the error message "unable to start ODB transaction" uses the acronym "ODB", which may confuse users unfamiliar with Git internals.

The review also includes **surface-level feedback** on patches 4/6 and 5/6, noting minor documentation nits and proposing a design alternative for the `env` callback (passing a `struct strvec` as input instead of returning a `NULL`-terminated array). These are not blockers but will likely be addressed in the next iteration.

Overall, the series is well-motivated and the changes appear mechanical but non-trivial. The feedback is constructive and aligns with the series’ goals, but a v2 will be needed to address the correctness issue, behavioral changes, and interface design questions. If those are resolved, this looks like a solid step forward for the ODB abstraction effort.
