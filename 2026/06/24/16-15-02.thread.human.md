This thread is about a long-standing but rarely discussed quirk in Git’s submodule handling: when you run `git fetch --recurse-submodules`, Git tries to fetch the submodule commits for *every* branch that was updated in the superproject, not just the one you’re actually using. If any of those commits are missing—say, because someone pushed a personal branch without pushing the submodule—Git fails the entire fetch, even if you never intended to check out that branch.

Ben Knoble kicked off the discussion by asking why Git can’t just make the submodule commit available for later fetching, which would sidestep the problem. Mike Crowe reframed it as a resilience issue: a single bad push (intentional or not) shouldn’t break fetches for everyone else. The thread is still in the problem-definition phase—no patches have been proposed yet, and the core question is whether Git should relax this behavior by default, add a new option to control it, or leave things as they are. The outcome will likely hinge on how much the current behavior is seen as a safeguard versus an unnecessary annoyance.
