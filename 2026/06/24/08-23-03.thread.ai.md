Core problem or goal
The series systematically hardens Git’s reftable backend against security vulnerabilities triggered by maliciously corrupted reftable files. The initial report identified an out-of-bounds write, but subsequent fuzzing with libFuzzer uncovered additional issues: out-of-bounds reads/writes, NULL pointer dereferences, uninitialized memory usage, calls to `abort()`, and invalid memory access during block parsing. Although reftable files are not stored remotely (exploitation requires local disk access), the hardening is comprehensive and includes new fuzzing infrastructure to prevent regressions and discover future issues.

Key technical details
- **Files touched**:
  - Build system: `meson.build`, `meson_options.txt`, `oss-fuzz/meson.build` (patch 1), `Makefile` (patch 2)
  - Fuzzing: `oss-fuzz/fuzz-reftable.c` (fuzzer target, patch 2)

  - Testing: `t/unit-tests/` (new unit tests for each fix, including `u-reftable-basics.c` for patch 3, `u-reftable-record.c` for patch 4, `u-reftable-block.c` for patches 6–10, and `u-reftable-table.c` for patches 11–12), `t/unit-tests/lib-reftable.{c,h}` (new helper function `cl_reftable_write_block` in patch 5).
- **New symbols**: `cl_reftable_write_block` (test helper, introduced in patch 5/12). No changes to public APIs or on-disk format.
- **Behavior**: Old-vs-new is strictly safer; no user-visible changes. The fixes address edge cases in parsing corrupted files, ensuring graceful failure (e.g., returning `REFTABLE_FORMAT_ERROR` instead of crashing). All fixes replace crashes, infinite loops, or undefined behavior with error returns. The fuzzing infrastructure is now fully integrated and exercises the three main entry points into the reftable parser (`reftable_table_init_ref_iterator`, `reftable_table_init_log_iterator`, and `reftable_table_iterator_init`).
- **Fuzzing infrastructure**: New Meson build option `-Dfuzzers_link_args=` to pass linker arguments for libFuzzer. The fuzzer target (`oss-fuzz/fuzz-reftable.c`) feeds arbitrary byte sequences to the reftable parser. Recommended setup uses `-Db_sanitize=address,fuzzer-no-link` alongside the new option. The fuzzer is integrated into Git’s CI via `ci/run-build-and-minimal-fuzzers.sh` and oss-fuzz.
- **Test helper details**: `cl_reftable_write_block` encapsulates the repetitive logic of writing records into a reftable block and appending it to a buffer. It is defined in `t/unit-tests/lib-reftable.c` and declared in `t/unit-tests/lib-reftable.h`. The helper is used in patches 6–12 to simplify test cases for block corruption scenarios. **Both Junio and Christian have confirmed the helper successfully reduces boilerplate as intended.**
- **Patch 6/12 specifics**: Fixes a heap-buffer-overflow in the log block parser (`reftable/block.c`). The test case (`t/unit-tests/u-reftable-block.c`) corrupts the block size field to trigger the overflow. Patrick **rejected Toon Claes’s proposed test improvements**, clarifying that the current approach (writing a size of 1) is the most direct way to trigger the bug. The rejected alternatives were:
  1. A sanity check (`cl_assert_equal_i(block_size, 82)`) to verify the expected block size before corruption.
  2. Using a minimally invalid size (5 instead of 1) to reduce off-by-one risks.
  **Rationale**: The bug requires the block size to be smaller than the header size (1–3 bytes), so `1` is the most direct trigger. The sanity check would not catch the out-of-bounds write because the offset would still be valid (just misaligned).
- **Patch 7/12 specifics**: Fixes an out-of-bounds read in `reftable_block_init()` (`reftable/block.c`). The test case (`t/unit-tests/u-reftable-block.c`) now dynamically calculates the corruption value: it reads the actual block size, verifies it (`cl_assert_equal_i(block_size, 47)`), and then corrupts it by adding 1. This ensures the test always targets the minimal invalid size (one byte beyond the buffer) and is more robust than the original hardcoded value (`0xffffff`).
