Core problem or goal
The series systematically hardens Git’s reftable backend against security vulnerabilities triggered by maliciously corrupted reftable files. The initial report identified an out-of-bounds write, but subsequent fuzzing with libFuzzer uncovered additional issues: out-of-bounds reads/writes, NULL pointer dereferences, uninitialized memory usage, calls to `abort()`, and invalid memory access during block parsing. Although reftable files are not stored remotely (exploitation requires local disk access), the hardening is comprehensive and includes new fuzzing infrastructure to prevent regressions and discover future issues.

The helper takes a buffer, block type, array of records, and record count, then writes the records into a block and appends it to the buffer. - **Patch 3/12 specifics**: Fixes an out-of-bounds read in `binsearch()` (`reftable/basics.c`) when called with an empty range (`sz == 0`). The unit test (`test_reftable_basics__binsearch_empty`) verifies the fix by passing an empty range and a comparison function that fails if called, ensuring the function returns 0 without invoking the comparison.
- **Patch 4/12 specifics**: Fixes a call to `abort()` in `reftable_ref_record_decode()` (`reftable/record.c`) when encountering an invalid ref value type. The fix validates the value type before storing it in the record and returns `REFTABLE_FORMAT_ERROR` instead of crashing. The unit test (`test_reftable_record__ref_record_decode_invalid_value_type`) verifies the behavior by feeding an out-of-range value type (`REFTABLE_NR_REF_VALUETYPES`) and confirming the function returns the expected error code.
- **Patch 6/12 specifics**: Fixes a heap-buffer-overflow in the log block parser (`reftable/block.c`). The vulnerability occurs when the inflated block size is smaller than the header size, leading to an out-of-bounds write during zlib decompression. The fix adds a sanity check to reject blocks where the size is insufficient to cover the header, returning `REFTABLE_FORMAT_ERROR` instead of crashing. The unit test (`test_reftable_block__corrupt_log_block_size`) reproduces the issue by corrupting the block size field to a value smaller than the header. The test uses the `cl_reftable_write_block` helper to reduce boilerplate. Patrick **rejected Toon Claes’s proposed test improvements**, clarifying that the current approach (writing a size of 1) is the most direct way to trigger the bug, as the vulnerability requires the block size to be smaller than the header size (1–3 bytes). The rejected alternatives were:
  1. A sanity check (`cl_assert_equal_i(block_size, 82)`) to verify the expected block size before corruption.
  2. Using a minimally invalid size (5 instead of 1) to reduce off-by-one risks.
  **Rationale**: The bug requires the block size to be smaller than the header size (1–3 bytes), so `1` is the most direct trigger. The sanity check would not catch the out-of-bounds write because the offset would still be valid (just misaligned). **Junio C Hamano has approved this patch**, stating the fix is "obviously correct."
- **Patch 7/12 specifics**: Fixes an out-of-bounds read in `reftable_block_init()` (`reftable/block.c`). The vulnerability occurs when the block size, read from untrusted data, exceeds the actual data available, leading to an out-of-bounds read when accessing the restart count or computing the restart table offset. The fix adds a bounds check to verify the claimed block size fits within the available data, returning `REFTABLE_FORMAT_ERROR` if not. The unit test (`test_reftable_block__corrupt_block_size`) now dynamically calculates the corruption value: it reads the actual block size, verifies it (`cl_assert_equal_i(block_size, 47)`), and then corrupts it by adding 1. This ensures the test always targets the minimal invalid size (one byte beyond the buffer) and is more robust than the original hardcoded value (`0xffffff`). **Junio C Hamano has approved this patch**, stating the fix is "obviously correct."
- **Patch 8/12 specifics**: Fixes an out-of-bounds read in `reftable_block_init()` (`reftable/block.c`) when a bogus restart count underflows the restart table offset calculation. The vulnerability occurs when the restart count, read from untrusted data, is used to compute `restart_off = block_size - 2 - 4 * restart_count` without validation. If `restart_count` is large enough, `restart_off` underflows and becomes negative, leading to an out-of-bounds read when accessing the restart table. The fix adds a bounds check to verify `restart_off` is within the valid range (`header_size + 4` to `block_size - 2`). If not, the function returns `REFTABLE_FORMAT_ERROR`. The unit test (`test_reftable_block__corrupt_restart_count`) reproduces the issue by writing a valid ref record into a block, then corrupting the restart count to `0xffff` (the maximum 16-bit value). The test uses the `cl_reftable_write_block` helper and verifies the function now returns `REFTABLE_FORMAT_ERROR` as expected. The ASan backtrace in the commit message confirms the crash occurs when `reftable_get_be24()` attempts to read from an invalid memory address during block parsing.
