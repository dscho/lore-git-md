This is the second patch in Harald Nordgren’s v15 `--track=fetch` series, implementing the user-facing feature that automatically fetches the remote branch before creating a local tracking branch. The patch extends `` `git checkout` `` and `` `git switch` `` with a `--track=fetch` mode, allowing users to write `` `git checkout -b topic --track=fetch origin/main` `` and have Git fetch `origin/main` before checking it out, ensuring the new branch starts from the latest remote tip rather than a potentially stale local copy.

The implementation adds a new `fetch` flag to the checkout options, introduces `fetch_remote_for_start_point()` to encapsulate the fetch logic, and updates the `--track` option parser to accept comma-separated modes (`direct`, `inherit`, `fetch`). The fetch logic resolves the remote-tracking ref through the configured fetch refspec, handles bare remote names by following `refs/remotes/<remote>/HEAD`, and gracefully falls back to the existing local ref if the fetch fails. Documentation for both `` `git-checkout` `` and `` `git-switch` `` is updated to describe the new mode, and the test suite verifies edge cases: successful fetches, offline fallback, namespace resolution, ambiguous refspec handling, quiet mode, and invalid input rejection.

The patch is technically complete, with all requested code nits from Phillip Wood’s v14 review addressed in v15: `RESOLVE_REF_NO_RECURSE` was dropped to match `` `git checkout` ``’s behavior, redundant `check_refname_format()` checks were removed, brace initialization (`= {0}`) replaced `memset()`, and `refs_ref_exists()` is used with `NULL` OID out-params. The test suite was streamlined from 280 to ~180 lines by removing redundant tests, replacing manual revision comparisons with `test_cmp_rev`, and rewording test titles to avoid confusing terminology (e.g., “namespace” → “remote-tracking prefix”). Junio’s earlier technical approval still applies, but the maintainer’s final decision hinges on whether the workflow benefits—reducing merge conflicts and duplicated work by aligning Git’s behavior with user expectations—justify the feature’s inclusion. No new technical objections are expected, and the implementation is now cleaner and more maintainable.
