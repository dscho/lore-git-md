This is the v8 iteration of a GSoC patch series that teaches `git repo info` to expose repository paths (`gitdir` and `commondir`) in both absolute and relative formats. The series extracts path-formatting logic from `rev-parse` into a new `format_path()` helper in `path.c`, then uses it to implement four new `git repo info` fields: `path.commondir.absolute`, `path.commondir.relative`, `path.gitdir.absolute`, and `path.gitdir.relative`.

Key technical details:
- The core `format_path()` helper (renamed from `append_formatted_path()` in v7) now uses "replace" semantics instead of "append", eliminating temporary buffer allocations and aligning with precedent in `ls-tree.c`.
- The helper supports four formatting modes via the `path_format` enum: `UNMODIFIED`, `RELATIVE`, `RELATIVE_IF_SHARED`, and `CANONICAL`.
- `rev-parse` is refactored to use the shared helper, replacing ~44 lines of duplicated logic while preserving exact backward compatibility.
- The new `git repo info` fields are implemented via four new getter functions (`get_path_commondir_absolute()`, etc.) that call `format_path()` with the appropriate mode.
- Files touched: `path.c`/`path.h`, `builtin/rev-parse.c`, `builtin/repo.c`, `Documentation/git-repo.adoc`, and a new test script `t/t1900-repo-info.sh`.
- The series maintains strict backward compatibility; all existing `rev-parse` output is preserved, and the new fields are purely additive.

This version addresses all feedback from Junio C Hamano and Phillip Wood:
- Renamed the helper to `format_path()` and changed its semantics to replace the destination buffer (eliminating wasteful intermediate allocations).
- Refactored `print_path()` in `rev-parse.c` to handle `FORMAT_DEFAULT` first, then map to `path_format` in a single `switch` statement for better readability and future-proofing.
- The API design has received explicit approval from Phillip Wood, and the series is now structurally complete.

The author has considered alternative names (`replace_formatted_path`, `strbuf_format_path`, `populate_formatted_path`) but settled on `format_path()` as the most intuitive. The implementation is ready for maintainer pickup and graduation to `next`; the remaining stylistic refinements in v8 are non-blocking polish. Test coverage is thorough, including edge cases, worktree scenarios, and error conditions.
