This is a discussion about a submodule-related usability issue in Git.

Ben Knoble and Mike Crowe are debating a behavior where `git fetch --recurse-submodules` fails fatally if a submodule commit referenced in a fetched superproject branch is not available on the submodule's remote. Mike argues this creates a "denial of service" scenario: a developer working on both superproject and submodule can push a superproject branch that breaks fetching for anyone else, even if the branch is personal and not intended for general use. Ben initially questioned why the submodule commit wouldn't be made available, but Mike clarified that this is about resilience—users shouldn't be able to break others' fetches unintentionally.

The thread is still in the problem-definition phase; no patch or proposed solution has been posted yet. The discussion suggests this is a real pain point for teams using submodules, but the right fix isn't obvious. If a patch does emerge, it will likely need to balance correctness (submodules should resolve) with robustness (fetches shouldn't fail on unrelated branches).
