This is the sixth patch in Patrick Steinhardt’s 11-patch security-hardening series for the reftable backend. It fixes an out-of-bounds read vulnerability triggered when a reftable block header claims a block size larger than the actual data available.

The bug occurs in `reftable/block.c` during block initialization: the code reads a 24-bit block size from the untrusted header and uses it to compute the restart table offset without validation. If the claimed size exceeds the buffer length, subsequent reads for the restart count (stored at `block_size - 2`) access out-of-bounds memory. The patch adds a simple bounds check that returns `REFTABLE_FORMAT_ERROR` if the claimed size is larger than the available data.

The fix is minimal and targeted: a nine-line addition in `reftable/block.c` and a corresponding 45-line unit test in `t/unit-tests/u-reftable-block.c`. The test constructs a valid block, corrupts the block-size field to the maximum 24-bit value (0xffffff), and verifies that the parser fails gracefully instead of crashing. The commit message includes a full AddressSanitizer backtrace demonstrating the original crash.

This is a clear, well-motivated security fix with excellent test coverage. It follows the pattern established in earlier patches in the series: each fix is paired with a unit test that reproduces the specific corruption scenario. Given Patrick’s role as the primary reftable contributor and the straightforward nature of the fix, this patch is likely to be uncontroversial and ready for merging.
