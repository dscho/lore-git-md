Thread identity
Subject: [PATCH 0/6] receive-pack: use ODB transactions instead of tmp_objdir
Series version: v1 (initial submission, now complete)
Originating author: Justin Tobler
Thread type: patch series (infrastructure refactoring)

Core problem or goal
Replace direct use of `tmp_objdir` interfaces in `git-receive-pack` with the newer `odb_transaction` subsystem, moving the command toward ODB-backend agnosticism. The series stages incoming objects via transactions rather than temporary object directories, though actual object writes remain tied to the "files" backend (via `git-index-pack` and `git-unpack-objects`). A follow-up series is planned to make the object writes themselves backend-agnostic.

Current status
Complete v1 submission (all six patches posted). Patches 1–5 prepare the ODB transaction layer for backend-agnostic use by surfacing previously silent failures and introducing new interfaces. Patch 6 replaces `tmp_objdir` calls in `builtin/receive-pack.c` with `odb_transaction` interfaces, introducing the `ODB_TRANSACTION_RECEIVE` flag to preserve `receive-pack`'s eager directory creation and "incoming" prefix naming. **Patches 2/6 and 3/6 have received substantive review from Patrick Steinhardt**, who identified previously silent failures in the "files" transaction backend (patch 2) and a correctness issue in the error-handling design of `odb_transaction_begin()` (patch 3). Feedback is constructive and does not challenge the series' direction, though it raises forward-looking questions about transaction architecture and requires a follow-up fix for the NULL-transaction case.

Key technical details
- Files touched: 44 total across the series (30 previously + 14 in patch 6: `builtin/receive-pack.c`, `object-file.c`, `odb/transaction.c`, `odb/transaction.h`, and others).
- New/modified interfaces: `odb_transaction_begin()` now takes an `enum odb_transaction_flags` parameter and returns `int`; `odb_transaction_env()` replaces `tmp_objdir_env()`; `odb_transaction_files_prepare()` (renamed from `prepare_loose_object_transaction`); `odb_transaction_begin_or_die()` (convenience wrapper); `odb_transaction_commit()` (now returns `int`). The `odb_transaction_files` backend gains a `prefix` field to support "incoming" vs. "bulk-fsync" distinction.
- Subsystems: `receive-pack`, ODB transaction layer, object-file management, and callers of the transaction API (`add`, `unpack-objects`, `update-index`, `cache-tree`, `read-cache`).
- Behavior: no user-facing changes; purely internal refactoring. Error handling is now explicit: previously silent failures in transaction setup, commit, abort, or environment access are propagated. The `ODB_TRANSACTION_RECEIVE` flag ensures `receive-pack`'s eager directory creation and "incoming" prefix are preserved. **Patch 2/6 specifically addresses silent failures in `odb_transaction_files_{prepare,begin,commit}()`, including temporary directory creation and object migration failures. Patch 3/6 introduces a correctness issue where `odb_transaction_begin()` can return success (`0`) while leaving the `out` parameter as `NULL` if a transaction is already active on the ODB, which the convenience wrapper `odb_transaction_begin_or_die()` does not handle, risking crashes or silent failures.**
- Symbols: `prepare_loose_object_transaction` -> `odb_transaction_files_prepare`; `odb_transaction_begin()` signature changed to `int odb_transaction_begin(struct odb_transaction **out, enum odb_transaction_flags flags)`; `odb_transaction_commit()` now returns `int`; `odb_transaction_begin_or_die()` added; `odb_transaction_env()` added; `ODB_TRANSACTION_RECEIVE` flag introduced.
- Test coverage: not mentioned; likely unchanged. Correctness depends on existing test suite exercising `receive-pack` and its child processes.

Open questions and loose ends
- **Patch 2/6**: Patrick Steinhardt raised two forward-looking questions:
  1. Why the transaction functions remain in `object-file.c` instead of `odb/source-files.c` (acknowledged as outside the patch's scope).
  2. The ODB transaction system's single-transaction-per-ODB limitation, which is inconsistent with reference transactions' multi-transaction design. This is not addressed here but noted for future work.
- **Patch 3/6**: Patrick Steinhardt identified a correctness issue in the error-handling design of `odb_transaction_begin()`: the function can return success (`0`) while leaving the `out` parameter as `NULL` if a transaction is already active on the ODB. The convenience wrapper `odb_transaction_begin_or_die()` does not account for this case, meaning callers could proceed with a `NULL` transaction pointer without realizing it. This requires a follow-up fix to either treat an existing transaction as an error condition or ensure the wrapper dies if `out` is `NULL` after a successful call.
- Follow-up work explicitly noted: backend-agnostic object writes.
