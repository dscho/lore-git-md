Core problem or goal
Replace `tmp_objdir` usage in `git-receive-pack` with the `odb_transaction` subsystem to advance ODB-backend agnosticism. The series stages incoming objects via transactions (replacing temporary object directories) while preserving existing object-write behavior (via `git-index-pack`/`git-unpack-objects` and the "files" backend). All blocking feedback from v1 and v2 is addressed; follow-up work (error-handling improvements, lazy directory creation, explicit abort interface, detangling object-write paths, redundant validation removal, surfacing previously ignored errors, propagating backend errors to callers, environment-variable plumbing for child processes, flag-based behavioral preservation for `receive-pack`, and the transaction-leak issue in `odb_transaction_commit()`) is explicitly deferred to maintain focus. Two open items remain from prior rounds, both deferred to future work:
- Header dependency concern in patch 9/11: Patrick Steinhardt questioned whether splitting `odb/transaction.h` from `odb/source.h` is worthwhile, given the tight coupling introduced by `enum odb_transaction_flags`. Justin Tobler agrees the separation may complicate future ODB abstraction work and plans to explore merging the headers in a future series. No code changes made; the discussion remains at the design level.
- Latent transaction-leak in patch 7/11: `odb_transaction_commit()` frees the transaction *before* returning any backend error, leaking the transaction object. The leak predates this series (it existed in the old `void` version) but becomes more visible with the error-return conversion. Acknowledged and deferred: Justin plans to fix it in a follow-up series by clearing the transaction even on failure, and Patrick suggests introducing a separate `odb_transaction_release()` function to make the lifecycle explicit. The fix is uncontroversial.
- **New open question in patch 6/11**: Junio C Hamano raises a safety concern about the error-handling flow in `odb_transaction_begin()`: if `odb_source_begin_transaction()` fails, the caller’s `*out` pointer might be left in an undefined state, potentially leading to a dangling reference or double-free. Junio suggests a conditional assignment pattern (`if (!(ret = ...)) odb->transaction = *out;`) to ensure the ODB’s internal state (`odb->transaction`) is updated only when the backend call succeeds. This is a low-level C safety issue; resolution will determine whether a follow-up fix is needed.
- **New open question in patch 8/11**: Junio C Hamano identifies an error-handling gap in `odb_transaction_files_env()`: it calls `odb_transaction_files_prepare()` but ignores its return value, so if preparation fails, the function still pushes the transaction’s object directory into the child process’s environment. This could lead to a child process seeing an invalid or partially initialized object directory. The fix is to propagate the error code: if preparation fails, return the error and avoid pushing the environment variables. This is a surface-level review (error-handling oversight) rather than a substantive design concern.
- **New open question in patch 11/11**: Junio C Hamano raises a design question about transaction lifecycle management in error paths: if `unpack_with_sideband()` fails, `execute_commands()` returns early without committing or explicitly aborting the transaction. While the `atexit()` handler will clean up the temporary directory (matching the old `tmp_objdir` behavior), Junio asks whether an explicit `odb_transaction_abort()` call is warranted for clarity, consistency, or to handle non-file-based backends that might not rely on `atexit()` cleanup. This is not a bug—everything will be cleaned up on process exit—but a design question about whether the transaction lifecycle should be made more explicit in error paths. Justin has not yet responded; resolution will likely be a follow-up patch, as the series is otherwise complete.
