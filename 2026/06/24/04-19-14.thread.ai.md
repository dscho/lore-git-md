Core problem or goal
Replace `tmp_objdir` usage in `git-receive-pack` with the `odb_transaction` subsystem to advance ODB-backend agnosticism. The series stages incoming objects via transactions (replacing temporary object directories) while preserving existing object-write behavior (via `git-index-pack`/`git-unpack-objects` and the "files" backend). All blocking feedback from v1 and v2 is addressed; follow-up work (error-handling improvements, lazy directory creation, explicit abort interface, detangling object-write paths, redundant validation removal, surfacing previously ignored errors, propagating backend errors to callers, environment-variable plumbing for child processes, flag-based behavioral preservation for `receive-pack`, and the transaction-leak issue in `odb_transaction_commit()`) is explicitly deferred to maintain focus. Two open items remain from prior rounds, both deferred to future work:
- Header dependency concern in patch 9/11: Patrick Steinhardt questioned whether splitting `odb/transaction.h` from `odb/source.h` is worthwhile, given the tight coupling introduced by `enum odb_transaction_flags`. Justin Tobler agrees the separation may complicate future ODB abstraction work and plans to explore merging the headers in a future series. No code changes made; the discussion remains at the design level.
- Latent transaction-leak in patch 7/11: `odb_transaction_commit()` frees the transaction *before* returning any backend error, leaking the transaction object. The leak predates this series (it existed in the old `void` version) but becomes more visible with the error-return conversion. Acknowledged and deferred: Justin plans to fix it in a follow-up series by clearing the transaction even on failure, and Patrick suggests introducing a separate `odb_transaction_release()` function to make the lifecycle explicit. The fix is uncontroversial.
- **Safety concern in patch 6/11 (resolved in v4)**: Junio C Hamano raised a low-level C issue in `odb_transaction_begin()`: if `odb_source_begin_transaction()` fails, the caller’s `*out` pointer might be left in an undefined state, potentially leading to a dangling reference or double-free. Justin confirms that `odb_source_begin_transaction()` leaves `*out` untouched on failure, but agrees with Junio’s suggestion to defensively guard the assignment to `odb->transaction` using a conditional pattern (`if (!(ret = ...)) odb->transaction = *out;`). This ensures the ODB’s internal state is updated only when the backend call succeeds. The fix is planned for v4.
- **Error-handling gap in patch 8/11 (resolved in v4)**: Junio C Hamano identifies that `odb_transaction_files_env()` ignores the return value of `odb_transaction_files_prepare()`, so if preparation fails, the function still pushes the transaction’s object directory into the child process’s environment. This could lead to a child process seeing an invalid or partially initialized object directory. Justin acknowledges the issue and confirms that `odb_transaction_files_prepare()` can fail (e.g., if temporary directory creation fails). The fix is to propagate the error code: if preparation fails, return the error and avoid pushing the environment variables. This is a surface-level review (error-handling oversight) rather than a substantive design concern.
- **Design question in patch 11/11 (resolved)**: Junio C Hamano raised a question about transaction lifecycle management in error paths: if `unpack_with_sideband()` fails, `execute_commands()` returns early without committing or explicitly aborting the transaction. While the `atexit()` handler will clean up the temporary directory (matching the old `tmp_objdir` behavior), Junio asked whether an explicit `odb_transaction_abort()` call is warranted for clarity, consistency, or to handle non-file-based backends that might not rely on `atexit()` cleanup. Justin agrees that an explicit abort would improve clarity and consistency but defers the change to a follow-up series, noting that the current behavior is functionally correct and matches the old `tmp_objdir` behavior. The deferral is pragmatic: the series is otherwise complete, has strong approval from Patrick Steinhardt, and the explicit abort is not a blocker for integration. The resolution is recorded as deferred follow-up work.
- **Design observation in patch 6/11 (new in v2)**: Patrick Steinhardt notes that some call sites (e.g., `cache_tree_update()`) create and immediately commit transactions, which may warrant revisiting. Justin clarifies that these call sites use transactions as an optimization to batch `fsync` operations, and follow-up work is in progress to address this pattern by starting transactions at a higher layer and passing them down. The observation is acknowledged and deferred to future work.
