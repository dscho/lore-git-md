Core problem or goal
Replace `tmp_objdir` usage in `git-receive-pack` with the `odb_transaction` subsystem to advance ODB-backend agnosticism. The series stages incoming objects via transactions (replacing temporary object directories) while preserving existing object-write behavior (via `git-index-pack`/`git-unpack-objects` and the "files" backend). A follow-up series is planned to make object writes themselves backend-agnostic.

Open questions and loose ends
- **Patch 1/6**:
  - Naming consistency: **resolved in v2** by renaming `fsync_loose_object_transaction()` and `flush_loose_object_transaction()` to `odb_transaction_files_fsync()` and `odb_transaction_files_flush()` for consistency with `odb_transaction_files_prepare()`.
- **Patch 2/6**:
  - **Latent error-handling gap**: callers of `odb_transaction_files_prepare()` (e.g., `write_loose_object()`, `odb_source_loose_write_stream()`) are not updated to handle its new error returns, leaving error propagation incomplete. Not a regression, but a robustness concern for future work.
  - **Abort semantics**: Junio asks whether an explicit "abort-transaction" mechanism is needed, or if failure during commit implicitly aborts the transaction. **Design-level question** for future patches.
  - ODB transaction system’s single-transaction-per-ODB limitation, inconsistent with reference transactions’ multi-transaction design (noted for future work).
- **Patch 3/6**:
  - **Blocking issue**: `odb_transaction_begin()` can return success (`0`) with `out` as `NULL` if a transaction is already active. The convenience wrapper `odb_transaction_begin_or_die()` does not handle this case, risking crashes or silent failures. Requires follow-up to either treat an existing transaction as an error or ensure the wrapper dies if `out` is `NULL`.
- **Patch 4/6**:
  - Minor documentation nit: clarify that passing a `NULL` transaction to `odb_transaction_commit()` is a no-op returning success (`0`).
- **Patch 5/6**:
  - Minor documentation improvements (grammar, possessive form).
  - Design alternative for the `env` callback: instead of returning a `NULL`-terminated array owned by the backend, the callback could take a `struct strvec` as input and return an error code. Framed as a question; no immediate action required.
- **Patch 6/6**:
  - **Blocking issue**: behavioral change where the transaction’s object directory is no longer added as an alternate, only propagated via environment variables. This change is undocumented in the commit message and could affect child processes.
  - **Blocking issue**: `ODB_TRANSACTION_RECEIVE` flag’s purpose is undocumented in the header; name isn’t self-explanatory. Patrick questions whether the lazy vs. eager directory creation distinction is necessary long-term.
  - **User-facing terminology**: error message uses "ODB" acronym, which may confuse users.
  - **Code organization**: inconsistent use of transaction parameter vs. `the_repository` access.
  - **Future work**: investigate whether lazy directory creation is needed at all (possible `NEEDSWORK` comment); consider splitting the patch into two (flag introduction and application in `receive-pack`).
- **Merge integration**:
  - The evil merge resolved conflicts with `ps/odb-source-packed` and `ps/refs-avoid-chdir-notify-reparent`; no action required from Justin beyond the planned v2.
  - The series is now entangled with other ODB/ref backend work, so minor adjustments may occur during integration.
- Follow-up work explicitly noted: backend-agnostic object writes.
