This thread is about a security-hardening patch series for Git’s reftable backend, now at version 2. The series systematically addresses vulnerabilities discovered by fuzzing, where maliciously corrupted reftable files could trigger crashes or memory corruption. Patrick Steinhardt is the author, and the series has so far received only surface-level feedback from Christian Couder, which has already been addressed.

The latest email covers the sixth patch in the series, which fixes a heap-buffer-overflow in the log block parser. The bug occurs when a corrupted block header claims an inflated size smaller than the header itself, causing zlib to write beyond the allocated buffer. The fix adds a simple sanity check to reject such blocks early, returning a format error instead of crashing. The patch includes a unit test that uses the helper function introduced earlier in the series to construct the corrupted block and verify the fix. Like the rest of the series, this change is purely defensive—no user-visible behavior changes, just safer handling of malformed input.

The series is now fully self-contained: it includes fuzzing infrastructure, a test helper to reduce duplication, and individual fixes for each vulnerability, all with corresponding unit tests. No open technical questions remain, and the fuzzer now runs for hours without surfacing new issues. The next step is likely review from other reftable experts, but so far the patches appear ready for integration.
