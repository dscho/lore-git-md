Patrick Steinhardt’s twelve-patch series to harden Git’s reftable backend against maliciously corrupted files has reached its second iteration. The series began as a response to an out-of-bounds write vulnerability but expanded after fuzzing with libFuzzer uncovered additional issues—out-of-bounds reads and writes, NULL pointer dereferences, uninitialized memory usage, and calls to `abort()`—all triggered by carefully crafted reftable files. While these files are not remotely accessible (exploitation requires local disk access), the hardening effort is thorough and now includes new fuzzing infrastructure to prevent regressions and catch future vulnerabilities.

The series is split into three parts: fuzzing infrastructure (patches 1–2), a test helper to reduce boilerplate in unit tests (patch 5), and the security fixes themselves (patches 3–4 and 6–12). The second version addressed Christian Couder’s feedback on test readability by introducing `cl_reftable_write_block`, a helper function that simplifies test cases for block corruption scenarios. The latest patch (11/12) fixes a NULL pointer dereference that occurs when an iterator is sought to a bogus offset, ensuring graceful failure instead of a crash. Each fix is accompanied by a targeted unit test, and the fuzzer now runs for over two hours without surfacing new issues, suggesting the hardening is comprehensive.

No substantive objections have been raised so far. Christian Couder’s review of the first version focused on test hygiene rather than the security fixes, and his suggestion has been incorporated. The series touches the reftable internals (`reftable/block.c`, `reftable/table.c`), the build system, and the test suite, but introduces no changes to public APIs or on-disk formats. The fixes are strictly safer than the old behavior, returning errors instead of crashing when parsing corrupted files. With the fuzzing infrastructure now in place and all known vulnerabilities addressed, the series appears ready for final review and integration.
