This is a v2 resubmission of Harald Nordgren’s usability improvement series that makes Git’s error messages more helpful when users accidentally misformat remote/branch arguments. The series targets two common mistakes: `git branch --set-upstream-to=origin main` (missing slash) and `git push origin/main` (slash instead of space). Both patches now gate their advice on the corresponding `advice.*` config option, ensuring users who disable the hint pay no performance penalty, and extract the detection logic into clean helper functions.

The v2 rewrite addresses Junio C Hamano’s feedback from v1 by restructuring the commit messages to clearly state the intended command, the common slip, and the resulting error, making the motivation immediately obvious. The implementation now only triggers advice when the likely intended remote-tracking ref exists (e.g., `origin/main`), reconstructing the user’s probable intent—setting the upstream for the current branch. This refinement narrows the scope of the advice while maintaining its helpfulness.

The first patch modifies `builtin/branch.c` to detect missing slashes in `--set-upstream-to` arguments, verify the remote exists, and confirm the corresponding remote-tracking ref (`refs/remotes/<remote>/<branch>`) is present before suggesting the correct form. The second patch updates `builtin/push.c` to identify slash-separated arguments that aren’t valid paths or remotes, validate the remote portion, and suggest the space-separated form. Both patches include thorough test coverage in `t/t3200-branch.sh` and `t/t5529-push-errors.sh`, respectively.

The series appears well-crafted: the changes are focused, non-disruptive, and backed by clear tests. The config-gated advice ensures the feature is opt-out, and the helper functions keep the call sites readable. While the first patch’s premise was initially contested, the v2 refinements—particularly the stricter detection logic—address Junio’s concerns about accuracy and intent reconstruction. The second patch’s implementation now avoids unnecessary computation when advice is disabled, resolving the technical feedback from v1.

This is a straightforward usability win that should benefit new users without complicating the codebase. The remaining open question is whether the config-based advice approach is the right long-term solution, but the current implementation provides a clean, opt-in mechanism for improving error messages. If the series holds up under further review, it could serve as a template for similar improvements elsewhere.
