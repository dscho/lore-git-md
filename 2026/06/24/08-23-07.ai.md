This is the fourth patch in Patrick Steinhardt’s 11-patch security-hardening series for the reftable backend. It fixes a crash-triggering bug in `reftable/record.c`: when the code encounters an invalid ref value type (anything outside the valid `REFTABLE_REF_VAL1`, `REFTABLE_REF_VAL2`, `REFTABLE_REF_SYMREF`, or `REFTABLE_REF_DELETION` range), it currently calls `abort()`, treating the condition as a programming error. The patch changes this to return a `REFTABLE_FORMAT_ERROR` instead, ensuring graceful failure when parsing untrusted (corrupted) reftable files. The fix also defers setting the record’s `value_type` field until after the type has been validated, preventing the record from being left in an inconsistent state.

The patch touches only `reftable/record.c` and adds a new unit test in `t/unit-tests/u-reftable-record.c` (`test_reftable_record__ref_record_decode_invalid_value_type`). The test verifies that decoding a ref record with an invalid value type (here, `REFTABLE_NR_REF_VALUETYPES`, which is out of bounds) returns `REFTABLE_FORMAT_ERROR` rather than crashing. The fix is minimal and targeted, addressing a single edge case without altering the public API or on-disk format.

This is a clear security hardening measure: while reftable files are not remotely accessible, local corruption could still trigger crashes, and `abort()` is an unnecessarily harsh response for untrusted input. The patch aligns with the series’ overall goal of making the reftable parser robust against malformed files. The accompanying test ensures the fix is effective and prevents regressions. Given the series’ context (fuzzer-discovered issues, CI-integrated fuzzing infrastructure), this patch looks like a well-motivated and thoroughly tested contribution.
