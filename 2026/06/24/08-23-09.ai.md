This is the sixth patch in Patrick Steinhardt’s 11-patch security-hardening series for the reftable backend. It fixes an out-of-bounds read vulnerability triggered when a reftable block header claims a block size larger than the actual data available.

The issue occurs in `reftable/block.c` during block initialization. The block size is read from the untrusted block header and used to compute the restart table offset and restart count without validation. If the claimed size exceeds the actual data length, the code attempts to read the restart count from memory beyond the allocated buffer, causing a segmentation fault. The fix adds a sanity check that verifies the claimed block size fits within the available data, returning `REFTABLE_FORMAT_ERROR` if not.

The patch includes a new unit test in `t/unit-tests/u-reftable-block.c` that deliberately corrupts the block size field to trigger the vulnerability, confirming the fix prevents the out-of-bounds access. The test constructs a valid block, then overwrites the 24-bit block size field with the maximum value (0xffffff), ensuring the parser rejects the corrupted data rather than crashing.

This is a targeted security fix with no user-visible behavior changes. The vulnerability requires local disk access to exploit (reftable files are not transferred over the network), but the hardening is part of a systematic effort to eliminate all parsing edge cases in the reftable backend. The fix is minimal, well-tested, and consistent with the series’ overall approach of graceful error handling over crashes.
