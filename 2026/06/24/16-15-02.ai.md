This is a discussion in an ongoing thread about a submodule fetch behavior issue. The thread centers on whether Git's current behavior of failing a fetch when it cannot retrieve a submodule commit (even for non-checked-out branches) is overly strict.

Ben Knoble initially questioned why the submodule commit isn't made available for fetching, suggesting this would avoid the problem. Mike Crowe clarifies that the issue arises with personal branches where the submodule commit may not be pushed (intentionally or accidentally), and argues that a user's personal branch should not cause fetch failures for others. He frames this as a resilience concern: a single bad push should not disrupt others' fetches.

The key technical detail is that ``git fetch --recurse-submodules`` attempts to fetch submodule commits for *all* updated superproject branches, not just the one being checked out. This can fail if any referenced submodule commit is missing from the remote, even if the user never intends to use that branch. The discussion implies this is a long-standing behavior rather than a recent regression, and no patch has been proposed yet—this is still at the problem-definition stage. The likely point of contention will be whether to relax the fetch failure or provide a new option to control this behavior.
