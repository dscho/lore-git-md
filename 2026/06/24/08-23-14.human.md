This is the final patch in Patrick Steinhardt’s 11-patch security-hardening series for the reftable backend. It fixes an out-of-bounds read when opening a truncated reftable file.

The bug occurs in `reftable_table_new()`: the code computes the table’s data size by subtracting the footer size from the file size, but it never checks whether the file is large enough to contain both the header and the footer. If the file is truncated, the subtraction underflows, causing the footer to be read from memory outside the allocated buffer. The fix adds a simple bounds check that returns `REFTABLE_FORMAT_ERROR` if the file is too small.

The patch includes a new unit test in `t/unit-tests/u-reftable-table.c` that constructs a valid reftable, truncates it just below the footer size, and verifies that `reftable_table_new()` fails cleanly instead of crashing. Like the rest of the series, this is an internal-only change with no user-visible behavior or on-disk format impact.

With this patch, the series is now complete: all 11 fixes are in place, the fuzzer runs for hours without finding new issues, and every vulnerability has a corresponding unit test. The hardening is thorough, well-motivated, and clearly scoped to the reftable parser’s handling of corrupted files. Given Patrick’s role as the primary reftable contributor and the security-sensitive nature of the fixes, this series looks like a strong candidate for merging.
