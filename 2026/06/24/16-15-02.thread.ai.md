Subject: submodule fetch resilience: should missing submodule commits block superproject fetch?
Series version: none (problem-definition discussion)
Originating author: Ben Knoble
Thread type: design discussion / bug report

Core problem or goal
Git’s `git fetch --recurse-submodules` currently fails the entire superproject fetch if any updated branch references a submodule commit that is missing from the submodule remote. This happens even for branches the user never intends to check out (e.g., personal topic branches), making the fetch brittle against accidental or intentional omissions of submodule commits.

Current status
No patch series exists yet; the thread is still defining the problem. The behavior is described as long-standing, not a recent regression. Two potential directions are surfacing: (1) relax the fetch failure so missing submodule commits no longer block the superproject fetch, or (2) introduce a new option to control whether missing commits should be treated as errors.

Key technical details
- Command: `git fetch --recurse-submodules`
- Subsystems: submodule, fetch
- Behavior: fetch fails if *any* updated superproject branch references a missing submodule commit, regardless of whether that branch is checked out
- No new CLI options, config keys, or on-disk format changes proposed yet
- Test coverage: none added; the discussion implies existing tests would need to be updated to reflect any new behavior

Open questions and loose ends
- Should missing submodule commits be silently ignored, or should there be a way to opt into strictness?
- If an option is added, should it be a config key, a command-line flag, or both?
- What should the default behavior be: strict (current) or lenient?
- How should the user be notified when a submodule commit is skipped?
- Are there security or data-integrity implications to relaxing the requirement?

Participant positions
- Ben Knoble: questions why the submodule commit isn’t made available for fetching, suggesting this would avoid the problem.
- Mike Crowe: argues that a user’s personal branch should not cause fetch failures for others; frames this as a resilience concern (single bad push should not disrupt others’ fetches). Position is substantive: engages with the behavior’s impact on real-world workflows.
