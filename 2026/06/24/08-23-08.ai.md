This is the fifth patch in Patrick Steinhardt's 11-patch security-hardening series for the reftable backend. It fixes an out-of-bounds (OOB) write vulnerability in `reftable/block.c` that occurs when parsing a maliciously corrupted log block.

The bug arises in the log block reconstruction logic. Log blocks store reflog data compressed with zlib, and the inflated size (including the header) is read from the block header. The code subtracts the trusted header size from this untrusted block size to determine how many bytes zlib should inflate. If the block size is smaller than the header size, this subtraction underflows, causing zlib to write beyond the allocated buffer. The patch adds a sanity check ensuring the block size is at least large enough to cover the header, a 4-byte block header, and a 2-byte restart counter, returning `REFTABLE_FORMAT_ERROR` if not.

The fix is accompanied by a new unit test in `t/unit-tests/u-reftable-block.c` that constructs a valid log block, corrupts its size field to trigger the underflow, and verifies the error is caught. The test reproduces the exact AddressSanitizer-reported heap-buffer-overflow shown in the commit message.

This is a clear security fix targeting a specific, demonstrable vulnerability. The patch is minimal, well-explained, and includes both the fix and test coverage. As part of the reftable hardening series, it addresses an issue discovered by fuzzing and is unlikely to be controversial. The vulnerability requires local disk access to exploit (reftable files are not transferred over the network), but the hardening is still valuable for robustness.
