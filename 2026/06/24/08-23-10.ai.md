This is the seventh patch in Patrick Steinhardt’s 11-patch security-hardening series for the reftable backend. It fixes an out-of-bounds read vulnerability triggered when a reftable block contains a maliciously crafted restart count.

The bug occurs in `reftable/block.c` during block initialization. The restart count is stored in the last two bytes of the block and is used to compute the offset of the restart table without validation. If the count is large enough, the offset calculation underflows, causing subsequent reads to access memory outside the allocated block. The patch adds a sanity check ensuring the computed restart offset is within bounds (at least `header_size + 4` and at most `block_size - 2`). If not, the function returns `REFTABLE_FORMAT_ERROR` instead of proceeding.

The fix is accompanied by a new unit test in `t/unit-tests/u-reftable-block.c` that constructs a block with a deliberately corrupted restart count (0xffff) and verifies the parser rejects it with the expected error. The test uses the `clar` unit-test framework and exercises the exact code path that previously caused the out-of-bounds read.

This is a targeted security fix with no user-visible behavior change. The vulnerability requires local disk access to exploit (reftable files are not transferred over the network), but the hardening is part of a systematic effort to eliminate all parser edge cases. The patch is well-scoped, includes a clear test case, and integrates cleanly with the fuzzing infrastructure introduced earlier in the series. Given the reftable backend’s role in ref storage and Patrick’s position as its primary contributor, this fix is likely to be uncontroversial.
