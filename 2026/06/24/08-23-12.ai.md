This is the ninth patch in Patrick Steinhardt’s 11-patch security-hardening series for the reftable backend. It fixes an out-of-bounds read vulnerability triggered by a maliciously crafted restart offset in a reftable block.

The issue occurs when a restart offset—stored in the restart table and intended to point to a record within the block—is corrupted to point beyond the records section. During key lookup (`block_iter_seek_key`), the code attempts to decode the record at the bogus offset, leading to an invalid memory access in `get_var_int` (called via `reftable_decode_keylen` and `restart_needle_less`). The patch adds a bounds check in `restart_needle_less` to verify that the restart offset is within the valid range (i.e., before the restart table itself). If the check fails, the function sets `args.error` and returns an error, preventing the out-of-bounds read.

The fix is minimal and targeted: a single bounds check in `reftable/block.c` (lines 446–452) and a corresponding unit test in `t/unit-tests/u-reftable-block.c` that constructs a block with a deliberately corrupted restart offset (0xffffff) and verifies that `block_iter_seek_key` fails gracefully with `REFTABLE_FORMAT_ERROR`. The test is thorough, covering the full lifecycle of block creation, corruption, and attempted access.

This patch is part of the series’ second half (patches 3–11), which addresses individual vulnerabilities discovered by the new fuzzer. Like the others, it is internal-only: no changes to public APIs, on-disk format, or user-visible behavior. The hardening is strictly defensive, ensuring the parser fails safely rather than crashing when encountering corrupted data. The commit message includes a full ASan backtrace, making the issue and fix easy to understand.
