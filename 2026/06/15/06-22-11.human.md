This is a bugfix patch addressing limitations in `git log --follow` when dealing with non-linear history and renames. The patch comes from Miklos Vajna and is now in its third iteration after feedback from Junio Hamano.

The core issue is that `--follow` currently fails to properly track file renames across merge commits, particularly in subtree merges or when renames happen on different sides of a merge. The current implementation only stores the followed path in a single global variable, which gets overwritten when traversing different parent paths.

The solution introduces a commit-to-path mapping system using a commit slab to track which path should be followed when visiting each parent commit. This ensures rename tracking works correctly regardless of traversal order through non-linear history. The patch includes:

1. A new `follow_pathspec_slab` to store paths per commit
2. Logic to propagate pathspecs to parent commits
3. Three test cases demonstrating the fixed scenarios:
   - Subtree merges with renames
   - Merges where both sides renamed files
   - Complex diamond-shaped history with renames on both sides

The implementation appears well-considered, with careful attention to memory management and edge cases. The test coverage is thorough, exercising both the original subtree merge case that motivated the fix as well as more complex rename scenarios Junio suggested during review.

This addresses a long-standing limitation in `--follow` behavior that has affected users trying to track file history across merges. The patch also updates the documentation to remove the warning about `--follow` not working well with non-linear history.
