This is the fifth patch in Johannes Schindelin's 7-part series addressing Windows platform compatibility for handling objects larger than 4GB, where `size_t` is 64-bit but `unsigned long` is 32-bit. This patch focuses on converting in-memory object size handling in `pack-objects` to use `size_t` consistently.

The patch updates all size-related functions in `pack-objects` (`oe_size`, `oe_delta_size`, etc.) to use `size_t` instead of `unsigned long`, removing the 4GB cap that previously caused `upload-pack` to fail when serving large objects. It eliminates three `cast_size_t_to_ulong()` calls in `check_object()` that were guarding `in_pack_size`, while maintaining compatibility with the still-`unsigned-long` `object_info::sizep` field (which will be converted in a later patch).

Key technical details:
- Updates both the accessors and setters for object sizes in `pack-objects`
- Modifies the `delta_size` array to store `size_t` values
- Fixes test failures in `t5608` where `upload-pack` failed on >4GB objects
- Maintains transitional compatibility with unconverted subsystems
- Builds on commit 606c192380 which made `write_reuse_object()` track sizes as `size_t`
- Follows the pattern established in earlier patches of the series

The changes are mechanical but important for correct large object handling on Windows. The patch has already been reviewed by Patrick Steinhardt in v1 discussion, where he noted the elimination of temporary `unsigned long sz` variables in packfile.c as an improvement. This version incorporates no new changes from v1 beyond the series-wide rebase.

This continues the systematic conversion of size handling throughout Git's object storage stack, with each patch building on the last to eventually provide full 64-bit size support on Windows platforms.
