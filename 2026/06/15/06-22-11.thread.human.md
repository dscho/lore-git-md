Miklos Vajna has sent the third version of a patch fixing `git log --follow`'s handling of file renames across merge commits. The current implementation loses track of renamed paths when traversing non-linear history, particularly in subtree merges where the rename occurs in the merge commit itself. 

The solution introduces a commit-to-path mapping system that properly tracks which path to follow when visiting each parent of a merge. This ensures rename detection works correctly regardless of traversal order. The patch includes tests covering three complex scenarios: subtree merges with renames, merges of unrelated histories with renames, and diamond-shaped histories with renames on both sides.

Compared to previous versions, this iteration simplifies the path tracking (only following one path per commit), adds a new test case, fixes test numbering, and removes an obsolete workaround. The implementation appears solid with thorough test coverage, addressing a long-standing limitation while maintaining backward compatibility. This should significantly improve rename tracking in complex repository histories.
