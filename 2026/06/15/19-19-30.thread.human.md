This thread began as a proposal to make `git rebase --abort` more discoverable by adding hints in two contexts: when an "exec" step fails during rebase, and in status messages during commit splitting or editing. The status-message additions remain uncontroversial, but the exec-failure hint has sparked a deeper debate about what `git rebase` is *for*.

Harald Nordgren has now clarified that his patch targets a specific workflow: using `git rebase` as a loop to run checks on each commit, where a single exec failure should terminate the entire process. This isn’t a traditional rebase—it’s treating the command as a control structure rather than a history-editing tool. Junio and Phillip Wood have both questioned whether this niche use case belongs in Git’s built-in interface. Junio suggests it might be better served by a dedicated script or command, while Phillip argues that if the hint is kept, it should guide users toward `--skip` or editing the todo list instead of (or in addition to) `--abort`.

The patch itself is technically sound: it splits exec-failure messages into a failure-specific warning followed by a neutral `--abort` hint, and suppresses the hint for conflict-induced failures. But the thread has shifted from implementation details to a fundamental question: should Git accommodate this workflow at all? No new code or proposals have been introduced, and Harald hasn’t yet responded to the critiques about alternatives. The discussion now hinges on whether this use case is common or important enough to warrant built-in support.
