Harald Nordgren’s patch series aims to make `git rebase --abort` more discoverable by adding hints in two places where only `--continue` was previously mentioned: when an "exec" step fails during rebase, and in the status help text shown during commit splitting or editing. The status-message changes are uncontroversial and ready to go, but the exec-failure addition has sparked a nuanced discussion about when such hints are genuinely helpful.

Phillip Wood and Junio C Hamano have both weighed in on the exec-failure case. Phillip initially opposed the idea on workflow grounds but now supports it after Junio framed the hint as a low-cost "escape hatch" for new users rather than a workflow recommendation. The agreed design splits the message into two parts: a failure-specific warning (e.g., "exec command failed: <command>") followed by a neutral `--abort` suggestion, avoiding any implication that aborting is the preferred action. The hint will also be suppressed if the exec failure is due to a conflict, preserving the existing distinction between exec failures (where continuing is more likely) and conflicts (where aborting might be more common).

Junio’s latest review, however, raises a new question: whether the hint is justified in *all* exec-failure cases. Using Harald’s example—a missing test file during a rebase—Junio points out that the user doesn’t need to "fix" anything; they can simply `--continue` once the file is added later. This suggests the hint might be noise in transient failures (like missing files) and more appropriate for irrecoverable ones (like broken scripts). The discussion is now focused on refining the hint’s scope, though the core design (split messages, conflict-induced suppression) remains intact. The next revision will likely adjust the conditional logic to exclude cases where continuing is the natural resolution.
