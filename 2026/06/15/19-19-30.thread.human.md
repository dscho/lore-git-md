This thread is about a patch from Harald Nordgren that adds `git rebase --abort` hints to failure and status messages, aiming to improve rebase’s user interface consistency. The patch targets two scenarios: when an "exec" step fails during rebase, and in status help text during commit splitting or editing. However, the discussion has shifted from the patch’s technical details to whether Git should even accommodate the workflow it serves—a niche use case where `git rebase` is used as a control structure to run checks on each commit, and a single exec failure should terminate the process.

Key participants include Harald (the author), Phillip Wood (a reviewer), and Junio C Hamano (the maintainer). The status-message additions remain uncontroversial, but the exec-failure hint has sparked debate. Junio and Phillip argue that aborting after a single exec failure isn’t a "normal" rebase use case, and Junio suggests this workflow might be better handled by a dedicated command or external script. Phillip has pressed further, questioning why users would want to check commits without fixing failures, and proposing alternatives like guiding users toward `--skip` or todo-list editing. Harald has defended the hint as a universal "escape hatch" for new users but hasn’t addressed these critiques directly.

The patch itself modifies `sequencer.c`, `wt-status.c`, and test files, with the exec-failure message split into a failure-specific warning and a neutral `--abort` hint. The hint is suppressed for conflict-induced failures, but Junio has suggested further refinements to exclude transient failures (e.g., missing files). Phillip also identified a feature gap: `git rebase --skip` doesn’t handle rescheduled exec commands, which could be a more appropriate response than aborting. The thread’s future direction remains unclear, with no consensus on whether the workflow is valid or how the hint should evolve. For now, the patch is still at v1, and the discussion is stuck on whether this edge case deserves built-in support.
