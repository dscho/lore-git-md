This thread is about a small but user-visible improvement to Git’s rebase interface: adding `--abort` hints to failure and status messages where only `--continue` was previously shown. Harald Nordgren proposed the change to make the abort option more discoverable, especially for new users stuck in interrupted rebases. The series is now at v1, with full consensus on the design.

The patch targets two scenarios: when an `exec` step fails during rebase (currently only suggests `--continue`), and in rebase status help text (where `--abort` was missing). The exec-failure change has evolved from initial pushback to a clear plan: split the message into two parts—first explaining the failure and how to continue, then neutrally suggesting `--abort` as an "escape hatch." Phillip Wood and Junio Hamano shaped this approach, emphasizing that the hint should avoid implying abort is the recommended action. The status-message additions remain uncontroversial and unchanged.

Harald’s latest email grounded the discussion in a concrete example: a rebase interrupted by a failed `exec` (due to a nonexistent test file) where the user sees no visible way out. This real-world case reinforced the need for consistency—conflict messages already include `--abort`, so exec failures should too. The next revision will implement the split-message structure in `sequencer.c`, with no open questions or objections remaining. The change is low-risk, touching only message wording in `sequencer.c` and `wt-status.c`, with tests updated in `t/t7512-status-help.sh`.
