This is a feature proposal for a new `--squash` option in `git rebase` that folds a range of commits into their first commit while preserving the original message. The patch series has evolved from its initial `--fixup-all` naming to align with Junio C Hamano's suggestion to follow the `merge --squash` pattern.

The key changes in v2:
- Renamed the option from `--fixup-all` to `--squash`
- Made the option imply the merge backend (no longer requiring explicit `--autosquash`)
- Added tests showing interaction with `rebase.autosquash` config
- Clarified documentation to reflect the new behavior

The implementation remains largely the same - it modifies `sequencer.c` to handle the range-folding behavior and adds extensive test coverage in `t3415-rebase-autosquash.sh`. The tests verify various scenarios including:
- Basic range squashing
- Handling fixup! commits in the middle of the range
- Skipping dropped commits
- Proper behavior with merge commits
- Edge cases like single-commit ranges

Junio's earlier review raised concerns about whether this feature is necessary given existing alternatives like `git reset --soft` + `git commit --amend`. Harald Nordgren maintains that a dedicated rebase option provides better discoverability and UX, while agreeing to the naming change. The thread shows progress on the technical implementation while the core debate about necessity continues.

This appears to be a well-structured and thoroughly tested proposal that could be particularly useful for users who frequently need to consolidate commit ranges during development. The test coverage is extensive (118 new test lines) and the documentation is clear. The main open question remains whether the maintainers will accept the UX improvement argument.
