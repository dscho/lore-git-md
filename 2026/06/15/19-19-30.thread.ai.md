Thread identity: Documentation patch adding `git rebase --abort` hints to failure and status messages, authored by Harald Nordgren. Series remains at v1.

Core problem or goal: Improve rebase user interface consistency by making the `--abort` option more discoverable in rebase interruption contexts. The patch initially proposed adding `--abort` advice in two scenarios: when an "exec" step fails during rebase, and in status help text during commit splitting/editing. The discussion has now clarified that the exec-failure hint targets a niche workflow—using `git rebase` as a control structure to run checks on each commit, where a single exec failure should terminate the entire process. This admission reframes the patch as addressing a specific scripting use case rather than a general rebase operation, raising the question of whether Git should accommodate this workflow with built-in hints or expect users to handle it via external scripts.

Current status: Initial version (v1) of patch series. The status-message additions (in `wt-status.c` and tested in `t/t7512-status-help.sh`) remain uncontroversial and unchanged. The exec-failure addition (in `sequencer.c`) has reached consensus on the split-message design (failure-specific warning followed by neutral `--abort` hint) and conditional logic to exclude conflict-induced exec failures. However, the thread’s focus has shifted to the validity of the workflow itself: Junio and Phillip Wood argue that aborting after a single exec failure is not a "normal" rebase use case, and Junio suggests this workflow might be better served by a dedicated command or script. Harald’s confirmation of the niche use case has not resolved this tension, leaving the patch’s future direction unclear.

Key technical details: Modifies three files: `sequencer.c` (exec-failure message), `wt-status.c` (rebase status help), and `t/t7512-status-help.sh` (tests). The exec-failure message splits into two parts: a failure-specific warning (e.g., "exec command failed: <command>") followed by a neutral `--abort` suggestion ("You can also abort the rebase with `git rebase --abort`."). The abort hint is suppressed if the exec failure is due to a conflict. Junio’s earlier review suggested further refinement to conditionally suppress the hint for transient failures (e.g., missing files), though criteria remain unspecified. Phillip Wood’s critique introduces two additional technical considerations: (1) teaching `git rebase --skip` to handle rescheduled exec commands (a feature gap), and (2) guiding users toward editing the todo list for bad commands, neither of which are addressed by the current patch.

Open questions and loose ends:
- Should Git accommodate the niche workflow of using `git rebase` as a control structure for commit checks, or should users be expected to handle this via external scripts or a dedicated command? Junio’s framing suggests the latter, but no concrete alternative has been proposed.
- If the hint is retained, should it be revised to guide users toward `--skip` or todo-list editing instead of (or in addition to) `--abort`, as Phillip Wood suggests?
- Is there a need to implement `git rebase --skip` support for rescheduled exec commands, as Phillip suggests?
- Should the hint be suppressed for transient exec failures (e.g., missing files), and if so, what criteria should determine this?
