Thread identity: Documentation patch adding `git rebase --abort` hints to failure and status messages, authored by Harald Nordgren. Series remains at v1.

Core problem or goal: Improve rebase user interface consistency by making the `--abort` option more discoverable in all rebase interruption contexts. The patch adds `--abort` advice in two scenarios: when an "exec" step fails during rebase, and in status help text during commit splitting/editing. The discussion has evolved to question whether the patch’s premise—that exec failures warrant an `--abort` hint—is justified, or whether it caters to a niche workflow that `git rebase` is not designed to support.

Current status: Initial version (v1) of patch series. The status-message additions (in `wt-status.c` and tested in `t/t7512-status-help.sh`) remain uncontroversial and unchanged. The exec-failure addition (in `sequencer.c`) has reached consensus on the split-message design (failure-specific warning followed by neutral `--abort` hint) and conditional logic to exclude conflict-induced exec failures. However, the thread now centers on whether the hint’s premise is valid: Junio and Phillip Wood argue that aborting is rarely the right response to exec failures, and Junio further questions whether the workflow Harald’s patch targets (aborting the entire rebase after a single exec failure) is even a "normal" use case for `git rebase`. Junio suggests this workflow might be better served by a dedicated command or script, reframing the patch as potentially misaligned with rebase’s intended purpose.

Key technical details: Modifies three files: `sequencer.c` (exec-failure message), `wt-status.c` (rebase status help), and `t/t7512-status-help.sh` (tests). The exec-failure message splits into two parts: a failure-specific warning (e.g., "exec command failed: <command>") followed by a neutral `--abort` suggestion ("You can also abort the rebase with `git rebase --abort`."). The abort hint is suppressed if the exec failure is due to a conflict. Junio’s earlier review suggested further refinement to conditionally suppress the hint for transient failures (e.g., missing files), though criteria remain unspecified. Phillip Wood’s critique introduces two additional technical considerations: (1) teaching `git rebase --skip` to handle rescheduled exec commands (a feature gap), and (2) guiding users toward editing the todo list for bad commands, neither of which are addressed by the current patch.

Open questions and loose ends:
- Is the workflow Harald’s patch targets (aborting the entire rebase after a single exec failure) a valid or "normal" use case for `git rebase`? Junio’s reply suggests it may not be, framing it as a niche scenario better served by a dedicated tool.
- Should the patch be revised to guide users toward `--skip` or todo-list editing instead of (or in addition to) `--abort`? Phillip Wood’s critique implies this, but no concrete proposal has been made.
- Is there a need to implement `git rebase --skip` support for rescheduled exec commands, as Phillip suggests?
- If the hint is retained, should it be suppressed for transient exec failures (e.g., missing files), and if so, what criteria should determine this?

Participant positions:

Position is substantive (engages with user experience, real-world pain points, and implementation details). Has not yet responded to Junio’s or Phillip’s critiques about workflow validity or alternatives.

Position is substantive (engages with user experience, learning curves, and rebase’s intended purpose). No review trailers yet.
