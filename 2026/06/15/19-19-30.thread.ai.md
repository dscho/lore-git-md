Thread identity: Documentation patch adding `git rebase --abort` hints to failure and status messages, authored by Harald Nordgren. Series remains at v1.

Core problem or goal: Improve rebase user interface consistency by making the `--abort` option more discoverable in all rebase interruption contexts. The patch adds `--abort` advice in two scenarios where only `--continue` was previously mentioned: when an "exec" step fails during rebase, and in status help text during commit splitting/editing. The goal is framed as a low-cost "escape hatch" for new users, but the discussion now centers on whether this guidance is appropriate for *all* exec failures or only irrecoverable ones.

Current status: Initial version (v1) of patch series. The status-message additions (in `wt-status.c` and tested in `t/t7512-status-help.sh`) remain uncontroversial and unchanged. The exec-failure addition (in `sequencer.c`) has reached consensus on the split-message design (failure-specific warning followed by neutral `--abort` hint) and conditional logic to exclude conflict-induced exec failures. However, the thread now grapples with two competing visions: (1) Harald’s position that the hint should be shown for *all* exec failures as a universal escape hatch, and (2) Phillip Wood’s argument that aborting is rarely the right response, with alternatives like `--skip` or todo-list editing being more constructive. Junio’s earlier concern about transient failures (e.g., missing files) remains unresolved, and Phillip’s critique deepens the divide over whether the hint’s current scope is justified.

Key technical details: Modifies three files: `sequencer.c` (exec-failure message), `wt-status.c` (rebase status help), and `t/t7512-status-help.sh` (tests). The exec-failure message splits into two parts: a failure-specific warning (e.g., "exec command failed: <command>") followed by a neutral `--abort` suggestion ("You can also abort the rebase with `git rebase --abort`."). The abort hint is suppressed if the exec failure is due to a conflict. Junio’s review suggested further refinement to conditionally suppress the hint for transient failures, though criteria remain unspecified. Phillip Wood’s reply introduces two new technical considerations: (1) teaching `git rebase --skip` to handle rescheduled exec commands (a feature gap), and (2) guiding users toward editing the todo list for bad commands, neither of which are addressed by the current patch.

Open questions and loose ends:
- Should the `--abort` hint be suppressed for transient exec failures (e.g., missing files), or is it justified in all cases as a low-cost training aid? Junio’s concern remains unaddressed.
- If conditional suppression is adopted, what criteria should determine whether the hint is shown (e.g., irrecoverable vs. recoverable failures)?
- Should the patch be revised to guide users toward `--skip` or todo-list editing instead of (or in addition to) `--abort`? Phillip Wood’s critique implies this, but no concrete proposal has been made.
- Is there a need to implement `git rebase --skip` support for rescheduled exec commands, as Phillip suggests?

Participant positions:

Position is substantive (engages with user experience, real-world pain points, and implementation details). In his latest reply, he restates the original motivation but does not engage with Junio’s or Phillip’s technical concerns about transient failures or workflow alternatives.

Instead, he advocates for guiding users toward `--skip` or todo-list editing, and identifies a feature gap in `--skip`’s handling of rescheduled exec commands. Position is substantive (engages with user behavior, workflow realism, and technical gaps).

Position is substantive (engages with user experience, learning curves, and implementation trade-offs). No review trailers yet.
