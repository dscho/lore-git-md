Thread identity: Documentation patch adding `git rebase --abort` hints to failure and status messages, authored by Harald Nordgren. Series remains at v1.

Core problem or goal: Improve rebase user interface consistency by making the `--abort` option more discoverable in all rebase interruption contexts. The patch adds `--abort` advice in two scenarios where only `--continue` was previously mentioned: when an "exec" step fails during rebase, and in status help text during commit splitting/editing. The goal is framed as a low-cost "escape hatch" for new users, not a workflow recommendation.

Current status: Initial version (v1) of patch series. The status-message additions (in `wt-status.c` and tested in `t/t7512-status-help.sh`) remain uncontroversial and unchanged. The exec-failure addition (in `sequencer.c`) has reached consensus on the split-message design (failure-specific warning followed by neutral `--abort` hint) and conditional logic to exclude conflict-induced exec failures. Junio’s latest review raises a new consideration: whether the abort hint should be shown for *all* exec failures or only for irrecoverable ones (e.g., broken scripts), as transient failures (like missing files) may not warrant the hint. Harald’s reply does not engage with this technical question, leaving it unresolved.

Key technical details: Modifies three files: `sequencer.c` (exec-failure message), `wt-status.c` (rebase status help), and `t/t7512-status-help.sh` (tests). The exec-failure message will now split into two parts: a failure-specific warning (e.g., "exec command failed: <command>") followed by a neutral `--abort` suggestion ("You can also abort the rebase with `git rebase --abort`."). The abort hint is suppressed if the exec failure is due to a conflict. Junio’s review suggests further refinement may be needed to conditionally suppress the hint for transient failures (e.g., missing files), though the exact criteria remain unspecified.

Open questions and loose ends:
- Should the `--abort` hint be suppressed for transient exec failures (e.g., missing files), or is it justified in all cases as a low-cost training aid? Junio’s concern remains unaddressed by Harald’s reply.
- If conditional suppression is adopted, what criteria should determine whether the hint is shown (e.g., irrecoverable vs. recoverable failures)?

Participant positions:
- Harald Nordgren (author): Proposes adding `--abort` advice to exec-failure messages for consistency with conflict cases, citing user confusion in ill-planned rebases (e.g., referencing a nonexistent test file during an exec step). Position is substantive (engages with user experience, real-world pain points, and implementation details). In his latest reply, he restates the original motivation but does not engage with Junio’s technical concern about transient failures, leaving the question unresolved.
