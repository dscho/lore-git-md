This is a platform compatibility discussion about handling large objects (>4GB) on Windows (LLP64) systems. The thread continues a series that converts object header length handling from `unsigned long` to `size_t` to properly support large files.

Patrick Steinhardt raises a thoughtful question about whether using a platform-independent `uint64_t` type (via a typedef like `objsize_t`) would be better than `size_t` for object sizes. He wonders if there are any supported platforms where `size_t` is 32-bit that would still need to handle large objects, though he acknowledges the changes so far have worked well in Git for Windows.

The context shows this is a mature series with all production code changes already validated in Git for Windows, and Johannes Schindelin has signed off. The current approach using `size_t` has proven stable, but Patrick's suggestion opens a design discussion about whether to make the size type more explicitly platform-independent. This isn't blocking - the series is technically sound - but it's a consideration for future similar conversions.

The patch itself (which this email replies to) mechanically updates `hash_object_file()` and `write_object_file_prepare()` to use `size_t`, continuing the systematic LLP64 compatibility work. The changes are straightforward and well-tested, with Patrick now exploring whether the type choice could be even more future-proof.
