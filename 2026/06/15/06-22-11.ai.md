This is a bugfix patch addressing limitations in `git log --follow` when dealing with non-linear history and renames. The patch comes from Miklos Vajna and is now in its third iteration.

The core issue is that `--follow` currently fails to properly track file renames across merge commits, particularly in cases like subtree merges where the rename happens in the merge commit itself. The current implementation stores the followed path in `opt->diffopt.pathspec`, which gets overwritten when visiting different parents of a merge, leading to incomplete history traversal.

The solution introduces a commit-to-path mapping system (`follow_pathspec_slab`) that tracks which path should be followed when visiting each parent commit. This ensures rename tracking works correctly regardless of traversal order through merge commits. The patch:

1. Adds infrastructure to store and retrieve paths for each commit
2. Updates the path tracking during commit traversal
3. Includes tests covering three scenarios:
   - Subtree merges with renames
   - Merges of unrelated histories with renames
   - Diamond-shaped histories with renames on both sides

Notable changes from previous versions:
- Simplified from tracking multiple paths per commit to just one path, as the rename following code doesn't handle path splits/merges anyway
- Added a new test case for related histories (the diamond scenario)
- Fixed test numbering conflict by using t4219
- Removed a workaround that's no longer needed

The patch appears well-constructed with thorough test coverage. It addresses a long-standing limitation in `--follow` behavior while maintaining backward compatibility. The implementation is careful about memory management and handles edge cases like multiple parents. This should significantly improve rename tracking in complex histories.
