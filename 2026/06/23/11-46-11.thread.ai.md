Core problem or goal
Enable Git to safely reclaim disk space in partial clones by pruning unneeded promisor objects without breaking future fetches. The work targets the promisor packfile machinery, the `git maintenance` task scheduler, and possibly new config keys or CLI options to control when and how unreachable-but-promisor-backed objects are discarded.

Current status
Still in prototyping/exploratory phase; no formal patch series has been posted yet. Earlier progress reports established the problem space; this update continues the narrative and invites community feedback.

Key technical details
None explicitly surfaced in the email itself. The linked blog post is expected to contain:
- Files touched: likely `promisor-remote.c`, `builtin/gc.c`, `builtin/maintenance.c`, `packfile.c`, `t/t5329-*` (partial-clone tests)
- New or renamed symbols: possibly a new maintenance task (`gc-promisor`), config keys (`maintenance.gcPromisor`, `fetch.writePromisorPack`), or CLI options (`--prune-promisor`)
- Behavior change: safe pruning of unreachable promisor objects, with re-fetch fallback
- On-disk format: no changes expected; the work should be backward-compatible
- Test coverage: new tests in `t/t5329-*` or `t/t5619-*` to verify prune safety and re-fetch correctness

Open questions and loose ends
- Design direction: which objects are safe to prune, and how to mark them
- Integration: how the new prune logic interacts with existing `git maintenance` tasks
- Performance: impact on fetch latency after pruning
- Configurability: what knobs should be exposed to users
- Edge cases: handling of shallow clones, grafted history, or alternate object directories
