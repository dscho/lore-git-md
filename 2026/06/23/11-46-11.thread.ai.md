Subject: GSoC 2026 – Improving disk space recovery for partial clones (progress report weeks 3–6)
Series version: none (narrative update, not a patch series)
Originating author: Siddharth Shrimali
Thread type: GSoC progress report

Core problem or goal
Enable Git to safely reclaim disk space in partial clones by pruning unneeded promisor objects without breaking future fetches. The work targets the promisor packfile machinery, the `git maintenance` task scheduler, and new config keys or CLI options to control when and how unreachable-but-promisor-backed objects are discarded.

Current status
Prototyping phase continues; no formal patch series posted yet. The week 6 blog post refines the design proposed in week 5: the `git maintenance run --task=gc-promisor` subcommand and `maintenance.gcPromisor.enabled` config key remain central, but the grace period is now configurable (default 30 days) and the `.keep`-file safety mechanism has been extended to record pruned objects per-remote, addressing concerns about promisor packs from multiple remotes. Integration with the existing `git maintenance` scheduler is still under discussion—whether `gc-promisor` should run before or after `gc` is unresolved. Performance testing on large promisor packs is planned but not yet executed.

Key technical details
- Files touched: `promisor-remote.c`, `builtin/gc.c`, `builtin/maintenance.c`, `packfile.c`, `t/t5329-partial-clone-prune.sh` (new test script)
- New or renamed symbols: `cmd_maintenance__gc_promisor()`, `git_config_get_gc_promisor_enabled()`, `--task=gc-promisor` CLI option, config keys `maintenance.gcPromisor.enabled` (boolean) and `maintenance.gcPromisor.gracePeriod` (integer, days)
- Behavior change: unreachable promisor objects are pruned only if they are older than the configured grace period and are recorded in a per-remote `.keep` file for later re-fetch; the prune operation is now remote-aware, avoiding cross-remote data loss
- On-disk format: backward-compatible; no changes to existing pack or index formats, but `.keep` files now include remote-specific markers
- Test coverage: new tests in `t/t5329-partial-clone-prune.sh` verify prune safety, re-fetch fallback, grace-period enforcement, and multi-remote handling

Open questions and loose ends
- Integration: whether `gc-promisor` should run before or after `gc` in the maintenance scheduler, and how to handle scheduling conflicts (e.g., if both tasks are enabled)
- Performance: impact on fetch latency after pruning large promisor packs, especially for repositories with many remotes; performance testing is pending
- Configurability: whether to expose additional knobs (e.g., prune aggressiveness, per-remote grace periods)
- Edge cases: handling of shallow clones, grafted history, alternate object directories, and promisor packs from multiple remotes (partially addressed by per-remote `.keep` files, but not yet fully resolved)
- Safety: whether the per-remote `.keep`-file mechanism is sufficient for recovery, or if a more robust mechanism (e.g., a dedicated recovery log) is needed
- CLI vs. config: whether the grace period should be configurable via CLI (`--grace-period=<days>`) or only via config
