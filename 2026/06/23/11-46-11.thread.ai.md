Subject: GSoC 2026 – Improving disk space recovery for partial clones (progress report weeks 3–10)
Series version: none (narrative update, not a patch series)
Originating author: Siddharth Shrimali
Thread type: GSoC progress report

Core problem or goal
Enable Git to safely reclaim disk space in partial clones by pruning unneeded promisor objects without breaking future fetches. The work targets the promisor packfile machinery, the `git maintenance` task scheduler, and new config keys or CLI options to control when and how unreachable-but-promisor-backed objects are discarded.

Current status
Prototyping phase continues; no formal patch series posted yet. The week 9–10 blog post confirms the design direction: the `git maintenance run --task=gc-promisor` subcommand and `maintenance.gcPromisor.enabled` config key remain central, with the grace period (default 30 days) configurable via both config (`maintenance.gcPromisor.gracePeriod`) and CLI (`--grace-period=<days>`). The per-remote `.keep`-file safety mechanism is implemented, addressing concerns about promisor packs from multiple remotes. Integration with the existing `git maintenance` scheduler is resolved: `gc-promisor` runs *after* `gc` to avoid interfering with the latter’s pack consolidation. Performance testing on large promisor packs has expanded to include repositories with up to 10 remotes, with initial results showing acceptable fetch latency post-prune; edge cases (shallow clones, grafted history, alternate object directories) remain under evaluation.

Key technical details
- Files touched: `promisor-remote.c`, `builtin/gc.c`, `builtin/maintenance.c`, `packfile.c`, `t/t5329-partial-clone-prune.sh` (new test script)
- New or renamed symbols: `cmd_maintenance__gc_promisor()`, `git_config_get_gc_promisor_enabled()`, `--task=gc-promisor` CLI option, `--grace-period=<days>` CLI option, config keys `maintenance.gcPromisor.enabled` (boolean) and `maintenance.gcPromisor.gracePeriod` (integer, days)
- Behavior change: unreachable promisor objects are pruned only if they are older than the configured grace period and are recorded in a per-remote `.keep` file for later re-fetch; the prune operation is remote-aware, avoiding cross-remote data loss. The task runs after `gc` in the maintenance scheduler.
- On-disk format: backward-compatible; no changes to existing pack or index formats, but `.keep` files now include remote-specific markers and a timestamp to support grace-period enforcement.
- Test coverage: new tests in `t/t5329-partial-clone-prune.sh` verify prune safety, re-fetch fallback, grace-period enforcement, multi-remote handling, scheduler integration, and performance on large promisor packs (up to 1 GB). Performance tests now include repositories with up to 10 remotes, showing fetch latency increases of <5% post-prune.

Open questions and loose ends
- Edge cases: handling of shallow clones, grafted history, alternate object directories, and promisor packs from more than 10 remotes (performance testing ongoing)
- Safety: whether the per-remote `.keep`-file mechanism is sufficient for recovery in all scenarios, or if a more robust mechanism (e.g., a dedicated recovery log) is needed
- Configurability: whether to expose additional knobs (e.g., prune aggressiveness, per-remote grace periods)
- Performance: finalizing benchmarks for repositories with >10 remotes and very large promisor packs (>1 GB)
- CLI vs. config: the grace period is configurable via both CLI and config, but the interaction between the two (e.g., CLI override, config precedence) is not yet documented
