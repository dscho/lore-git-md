This is a **bugfix** targeting submodule handling during recursive fetches. Mike Crowe reports that when `git fetch --recurse-submodules` encounters a submodule commit that doesn’t exist on the remote (common in personal branches or WIP commits), the entire fetch fails with a hard error, even if the missing commit isn’t relevant to the current branch. The issue disrupts CI systems and user workflows, as repeated fetches may succeed only after the problematic branch is no longer updated.

The problem arises because Git attempts to fetch *all* submodule commits referenced by *any* updated superproject branch, not just the current tracking branch. Mike demonstrates this with a reproducible script involving a superproject and submodule, where a dangling submodule commit on a non-tracking branch causes the fetch to fail. Two workarounds are proposed—disabling recursion entirely (`--no-recurse-submodules`) or retrying the fetch—but neither is ideal.

Mike suggests two potential solutions: (1) limit recursive fetches to submodule commits referenced by the current tracking branch, or (2) treat submodule fetch failures as non-fatal (though this risks masking legitimate errors). The commit message doesn’t propose a specific implementation, but the issue is clearly motivated by real-world pain points, particularly in CI environments.

The reproduction script is thorough, setting up a minimal test case with SSH-based remotes to avoid protocol restrictions. The script creates a superproject and submodule, introduces a dangling submodule commit on a new branch, and demonstrates the fetch failure. This makes the issue easy to verify and debug.

This patch is likely to attract attention from submodule maintainers (e.g., Christian Couder or Jonathan Nieder, though the latter is now focused on Jujutsu) and contributors who’ve worked on recursive fetch logic. The trade-off between strictness and usability will be a key discussion point—whether to prioritize correctness (failing early) or flexibility (allowing partial fetches).
