This thread is about a bug in Git’s submodule handling during recursive fetches. Mike Crowe reports that when `git fetch --recurse-submodules` encounters a submodule commit that doesn’t exist on the remote—common in personal branches or work-in-progress commits—the entire fetch fails with a hard error, even if the missing commit isn’t relevant to the current branch. The issue disrupts CI workflows and user operations, as repeated fetches may only succeed after the problematic branch is no longer updated.

The root cause is that Git attempts to fetch *all* submodule commits referenced by *any* updated superproject branch, not just those tied to the current tracking branch. Mike provides a reproducible script demonstrating the problem, where a dangling submodule commit on a non-tracking branch causes the fetch to fail. Two workarounds exist—disabling recursion (`--no-recurse-submodules`) or retrying the fetch—but neither is ideal. Mike suggests two potential fixes: limiting recursive fetches to commits referenced by the current tracking branch, or treating submodule fetch failures as non-fatal (though this risks masking legitimate errors).

The thread is likely to draw interest from submodule maintainers (e.g., Christian Couder) and contributors familiar with recursive fetch logic. The key discussion point will be the trade-off between strictness (failing early to ensure correctness) and flexibility (allowing partial fetches to avoid workflow disruptions). No solution has been proposed yet, so this may require multiple iterations to resolve.
