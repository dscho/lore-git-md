This is a **bugfix** targeting submodule handling during fetches. Mike Crowe reports that when `git fetch --recurse-submodules` encounters a submodule commit that doesn’t exist on the remote (common in personal branches or WIP commits), the entire fetch fails with a hard error. The issue disrupts CI systems and confuses users, as even unrelated branch updates trigger the failure.

The problem stems from Git’s current behavior: it attempts to fetch *all* submodule commits referenced by *any* updated or new superproject branch, not just the one being tracked. This is overly aggressive—developers often push superproject branches with submodule commits that aren’t yet available on the submodule’s remote. The error manifests as either "unadvertised object" (SSH) or "not valid" (JGit) messages, causing the fetch to exit non-zero.

Mike includes a reproducible test script that sets up a superproject and submodule, creates a dangling submodule commit on a new branch, and demonstrates the fetch failure. He suggests two potential fixes: (1) limit recursive fetches to the current tracking branch, or (2) treat submodule fetch failures as non-fatal (though this could mask legitimate errors). Neither is implemented here—this is a problem report, not a patch.

The impact is real but situational: it only affects repositories with submodules and users who fetch branches containing unpushed submodule commits. The workaround (`git fetch || git fetch`) is racy, and `--no-recurse-submodules` disables all submodule processing. The issue feels like an unintended side effect of Git’s eagerness to prefetch submodule content, and the proposed mitigations are reasonable but not yet actionable.

For now, this is a heads-up for anyone using submodules in shared repositories. If you’ve seen mysterious fetch failures in CI, this might explain them. The thread is worth watching if you care about submodule ergonomics—Mike’s report is clear, and the reproduction script makes it easy to verify. No patches yet, but the problem is well-documented.
