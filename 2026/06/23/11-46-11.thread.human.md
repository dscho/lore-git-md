Siddharth Shrimali’s GSoC 2026 project to improve disk space recovery for partial clones continues to make progress, with weeks 9 and 10 focusing on refining the `gc-promisor` maintenance task. The core design remains unchanged: a new `git maintenance run --task=gc-promisor` subcommand will prune unreachable promisor objects older than a configurable grace period (default 30 days), using per-remote `.keep` files to ensure safe re-fetching. The task is now confirmed to run *after* `git gc` in the maintenance scheduler to avoid interfering with pack consolidation, and the grace period can be set via both config (`maintenance.gcPromisor.gracePeriod`) and CLI (`--grace-period=<days>`).

Performance testing has begun, with initial results showing minimal fetch latency increases (<5%) after pruning for repositories with up to 10 remotes. However, edge cases—such as shallow clones, grafted history, and promisor packs from more than 10 remotes—are still under evaluation. The `.keep`-file safety mechanism, now implemented with timestamps, is being scrutinized for robustness, and the author is seeking feedback on whether additional configurability (e.g., per-remote grace periods) is needed. No formal patches have been posted yet, and the thread remains open for wider review, though no other Git contributors have engaged so far. The work touches key files like `promisor-remote.c` and `builtin/maintenance.c` and builds on prior GSoC efforts and the existing `git maintenance` infrastructure.
