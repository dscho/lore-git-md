This is a discussion about behavior consistency in the experimental `git history reword` command, part of Patrick Steinhardt's larger `git history` feature effort. Junio C Hamano responds to Phillip Wood's suggestion about checking committer identity in addition to commit messages when determining whether a reword operation should be considered a no-op.

Junio questions the fundamental premise of aborting on unchanged messages (or committer info), pushing back against the idea that this should be treated as an error condition. His position is that silently accepting identical input is more user-friendly than failing, as the user explicitly requested that state. This challenges the current direction of the patch series, which had been moving toward explicit no-op detection based on earlier feedback.

The exchange highlights an important philosophical question about Git's behavior: should commands fail when they don't change anything, or should they silently accept no-op operations? Junio's stance suggests he favors the latter approach for consistency with other Git commands. This may require Pablo Sabater to rethink the v2 implementation, potentially moving away from the `COMMIT_TREE_ABORT_ON_SAME_MESSAGE` flag entirely.

The thread continues to evolve the design toward a more comprehensive solution for handling no-op cases across Git's history-modifying commands, with Junio now advocating for a less intrusive approach than the current patch implements.
