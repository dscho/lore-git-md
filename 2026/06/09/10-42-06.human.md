This is a v2 revision of an RFC patch series proposing behavior changes for the experimental `git history reword` command, part of Patrick Steinhardt's larger `git history` feature effort. The series comes from Pablo Sabater, a relatively new contributor to this subsystem.

The key change in v2 is a pivot from the original approach - instead of making `git history reword` abort by default when the commit message is unchanged, the new version introduces a flag to control this behavior. This follows Junio Hamano's feedback that forcing an abort might be too opinionated. The implementation now modifies `commit_tree_ext()` to support this optional check while not affecting other subcommands that might not want this behavior.

The series also includes some test improvements, notably using `GIT_EDITOR=true` for test cases where the message doesn't change (a suggestion from D. Ben Knoble). Interestingly, Pablo has split out the user feedback portion of the original proposal into a future series, focusing this iteration purely on the abort behavior.

The motivation remains the same: `git history reword` performs more expensive operations (updating all branches containing the original commit) compared to `git commit --amend`, making the no-change case worth optimizing. The RFC status suggests Pablo is still seeking input on whether this behavior should extend to `git history fixup --reedit-message`, where the tradeoffs may differ.

The patches are narrowly scoped to the new builtin/history.c code and its test suite, building on Patrick Steinhardt's v11 `git history` series. The implementation looks clean, though the discussion thread indicates there may still be open questions about flag naming (`--force` vs `--force-rewrite`) and how this fits with Git's broader conventions.
