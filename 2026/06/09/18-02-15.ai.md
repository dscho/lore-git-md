This is a discussion thread about the behavior of the experimental `git history reword` command when no changes are made to a commit message. Justin Tobler is responding to Junio C Hamano's questioning of whether unchanged messages should trigger an abort.

Justin presents a use case where a user might want to abort a reword operation mid-process - perhaps realizing they selected the wrong commit or decided the original message was fine. He agrees with Junio that an error message isn't necessary when no changes are made, but sees value in having the operation silently skip rewriting when the message is unchanged. 

The discussion has evolved from Pablo Sabater's original RFC patch that proposed aborting on unchanged messages to now considering a more subtle approach where no-op cases would be handled quietly. Justin specifically argues against checking committer identity as part of the no-op detection, noting this would prevent aborting rewrites of commits where the user isn't the original committer.

This exchange continues the thread's broader exploration of how Git should handle no-op modifications across history-rewriting commands. The emerging consensus appears to favor silent handling over explicit failure, though implementation details like whether to include a short `-r` option for `--avoid-unnecessary-rewrite` remain open. The discussion touches on fundamental UX questions about when and how Git should intervene in user-initiated operations that don't actually change repository state.
