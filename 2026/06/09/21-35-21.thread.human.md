Junio C Hamano has proposed adding a `--rename` option to `git update-ref` to support his workflow for managing "evil merges" - merge-fix stored under `refs/merge-fix/` that resolve semantic conflicts between topics being integrated. The patch is now in its third iteration, with the core functionality allowing atomic ref renaming with reflog preservation while explicitly excluding branch refs (which should use `git branch --rename`).

The latest email provides deeper insight into Junio's integration workflow, explaining how merge-fix commits are named (`refs/merge-fix/$A--$B`) to track fixes needed when topics A and B interact. The combinatorial complexity arises when merge orders change, requiring these refs to be repointed - the exact use case motivating the low-level rename capability. This explains why existing branch operations wouldn't suffice for these internal refs.

The patch has evolved through three versions with input from Patrick Steinhardt, who engaged substantively on both technical implementation and documentation. All major issues appear resolved, with only broader architectural questions about future ref command organization remaining open. The discussion shows productive collaboration between Junio (as both maintainer and patch author) and Patrick (as a refs subsystem expert), with the feature now clearly motivated and ready for integration.
