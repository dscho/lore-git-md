This is a configuration discussion about the behavior of remote HEAD tracking in Git. The author, Matt Hunter, explains their preference for disabling remote HEAD tracking (`git remote set-head <name> -d`) to reduce noise in branch listings, but notes this setting gets overridden by fetch operations since commit a1f34d595503 introduced the `remote.<name>.followRemoteHEAD` configuration.

The key points:
1. The current `followRemoteHEAD` setting requires per-remote configuration and doesn't support wildcards
2. Setting it globally causes odd side effects like "half-baked" remote definitions
3. The author proposes adding a global default setting (`remote.followRemoteHEAD`) that would apply to all remotes unless overridden

This appears to be a genuine usability concern for users who manage multiple repositories and want consistent remote HEAD tracking behavior. The proposed solution seems reasonable from a technical standpoint, though it would need to be implemented carefully to avoid breaking existing configurations. The email reads as a thoughtful exploration of the problem space rather than a demand for immediate changes.
