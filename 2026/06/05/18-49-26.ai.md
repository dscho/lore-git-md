This is a feature proposal introducing two worktree-related improvements: copy-on-write worktree creation and shared-branch worktrees. The series comes from Jason Newton via GitGitGadget.

The first patch adds `--reflink` support to `git worktree add`, enabling copy-on-write worktree creation on supported filesystems (btrfs/Linux via FICLONE, macOS via clonefile()). This avoids the disk and I/O cost of full checkouts when creating multiple worktrees from the same repository. The patch includes a significant benchmark showing substantial disk savings (from ~5.3GB for 4 normal worktrees down to near-zero allocation with reflink). The behavior can be configured via `worktree.reflink` (true/false/auto).

The second patch changes worktree behavior to allow checking out the same branch in multiple worktrees, which was previously prohibited. This enables parallel work on the same branch across different worktrees, though it still prevents checking out branches that are mid-rebase or mid-bisect elsewhere. The patch notes this changes a default behavior and updates two test assertions accordingly.

The implementation touches core worktree functionality in builtin/worktree.c, adds new copy-on-write primitives in copy.[ch], and includes extensive test coverage in t2400-worktree-add.sh. The changes appear well-motivated by real-world scaling needs (the cover letter mentions "a fleet of agents each needing an isolated checkout") and include measurable performance benefits.

This seems like a substantial but carefully considered change to worktree behavior, particularly valuable for users managing many worktrees on copy-on-write filesystems. The benchmark results suggest the reflink approach could provide major efficiency gains in appropriate environments. The shared-branch capability also represents a long-standing limitation in worktree functionality that some users have likely worked around in ad-hoc ways.
