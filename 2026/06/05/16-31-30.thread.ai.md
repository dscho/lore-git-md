Thread identity: Proposal to add global `remote.followRemoteHEAD` configuration option as default for all remotes, building on the per-remote `remote.<name>.followRemoteHEAD` introduced in Git 2.48.

Core problem: The current `remote.<name>.followRemoteHEAD` setting requires per-remote configuration, creating management overhead for users who want consistent behavior across multiple repositories with different remote names. Matt Hunter proposes a global default to avoid repetitive configuration while maintaining the existing per-remote override capability.

Key technical details: The new global setting (exact namespace TBD - either `remote.followRemoteHEAD` or `fetch.followRemoteHEAD`) would serve as fallback when no remote-specific setting exists. Implementation must preserve backward compatibility where per-remote settings take precedence. Jeff King confirms the design parallels existing configuration patterns like `fetch.prune` falling back to `remote.*.prune`. The review acknowledges edge cases around remote definition semantics (where any configured key makes a remote "exist") but considers these inherent to Git's remote configuration model.

Current status: Initial proposal validated by Jeff King as addressing a legitimate gap in the original feature implementation. Naming convention remains open between `remote.*` and `fetch.*` namespaces, with technical merits for both approaches.

Open questions: Final determination of configuration namespace (`remote.followRemoteHEAD` vs `fetch.followRemoteHEAD`). Whether documentation should explicitly call out the interaction with remote definition edge cases.

Participant positions:
- Matt Hunter: Original author with concrete use case (reducing branch listing noise) and initial implementation consideration.
- Jeff King: Provided substantive review validating the need and design approach, drawing parallels to existing configuration patterns. Left naming as an open question rather than prescribing a solution.

Related work: The feature builds directly on `remote.<name>.followRemoteHEAD` introduced in Git 2.48. Design follows established precedent of `fetch.prune`/`remote.*.prune` fallback hierarchy.
