Thread identity: Proposal to add global `remote.followRemoteHEAD` configuration option as default for all remotes, building on the per-remote `remote.<name>.followRemoteHEAD` introduced in Git 2.48.

Core problem: The current `remote.<name>.followRemoteHEAD` setting requires per-remote configuration, creating management overhead for users who want consistent behavior across multiple repositories with different remote names. Author Matt Hunter proposes a global default to avoid repetitive configuration.

Key technical details: The new `remote.followRemoteHEAD` would serve as fallback when no remote-specific setting exists. Current implementation updates remote HEAD ref on every fetch when enabled. Proposal must maintain backward compatibility with existing per-remote settings (which would take precedence) and handle cases where remotes are defined without wildcards.

Open questions: How to handle interaction between global and per-remote settings in edge cases. Whether the configuration hierarchy (global default vs remote-specific) follows existing patterns in similar Git config options.

Participant positions: Initial proposal from Matt Hunter, who has identified a concrete use case (reducing noise in branch listings) and considered edge cases in the current implementation. No other participants yet as this is the thread root.
