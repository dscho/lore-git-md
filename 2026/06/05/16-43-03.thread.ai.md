Thread identity: Bugfix for ref-filter subsystem performance regression in `git branch`, `git branch --remotes`, and `git tag` commands when many unrelated loose refs exist.

Core problem: Commit dabecb9db2 ("for-each-ref: introduce a '--start-after' option", 2025-07-15) changed ref iteration behavior, causing performance degradation in common ref listing operations when repositories contain many loose refs. The regression affected commands that don't use --start-after by making them scan all loose refs unnecessarily.

Current status: Patch restores prefix-scoped iteration for non-start-after cases while maintaining --start-after functionality. Performance improvements are dramatic - from ~2.8s to ~0.1s for operations with 10,000 unrelated loose refs. Patch has been reviewed by Patrick Steinhardt and Junio C Hamano.

Key technical details: Fix modifies ref iteration logic in ref-filter to optimize the common case where no start-after is needed. Implementation preserves ref-filter state semantics while avoiding unnecessary I/O for loose refs. Includes comprehensive performance tests demonstrating the fix's impact.

Participant positions: Patrick Steinhardt reviewed the iterator construction vs seeking behavior. Junio C Hamano reviewed future compatibility considerations. Both appear satisfied with the solution.

Related work: Builds on commit dabecb9db2 which introduced the --start-after feature that originally caused the regression.
