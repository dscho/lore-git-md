This is a feature proposal regarding the `followRemoteHEAD` configuration option introduced in Git 2.48. The author, Matt Hunter, describes their workflow of disabling remote HEAD tracking via `git remote set-head -d` to reduce noise in branch listings, but notes this setting is now overridden by each fetch due to the new `remote.<name>.followRemoteHEAD` configuration.

The core issue is that the current implementation requires per-remote configuration, which becomes cumbersome when managing multiple repositories with varying remote names. Hunter proposes adding a global default setting (`remote.followRemoteHEAD`) that would apply to all remotes unless overridden by a specific `remote.<name>.followRemoteHEAD` setting.

The email thoughtfully considers edge cases, noting how the current wildcard-less implementation creates "half-baked" remote definitions when configured globally. The proposal appears technically sound and addresses a real configuration management pain point, though it would need to carefully handle the interaction with existing per-remote settings. The tone is constructive and open to alternative solutions, suggesting the author has done their homework before proposing the change.
