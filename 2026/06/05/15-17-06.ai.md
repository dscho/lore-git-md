This is a substantive review of a feature patch adding metadata tracking to Git worktrees. Phillip Wood raises two key concerns about the proposed functionality:

1. **Purpose Questioned**: He suggests that "what is this worktree for" might be better addressed by branch descriptions (via `branch.<name>.description`) rather than worktree-specific notes, except for detached HEAD cases. This challenges the fundamental need for the feature.

2. **Alternative Suggestion**: Rather than creation timestamps, he proposes that last-updated timestamps (based on HEAD reflog dates) would be more practically useful for identifying stale worktrees.

The review doesn't dispute the technical implementation (which has already been refined to use description files per Junio's earlier suggestion) but focuses on whether the feature solves real user needs. This moves the discussion from implementation details to design rationale, suggesting the patch may need stronger justification to proceed.

The exchange highlights an important tension in feature development - even well-implemented additions face scrutiny about whether they belong in core Git. Phillip's comments reflect practical experience about what metadata would actually help workflow management.
