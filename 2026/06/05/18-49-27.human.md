This is the first patch in a series introducing copy-on-write worktree creation, a performance optimization for creating multiple worktrees from the same repository. The patch comes from Jason Newton via GitGitGadget.

The change adds a `--reflink` option to `git worktree add` that uses copy-on-write filesystem features (FICLONE on Linux, clonefile() on macOS) to create new worktrees by sharing storage with the source worktree rather than performing a full checkout. This can dramatically reduce disk usage and I/O when creating many worktrees from the same base, as only modified files need new storage. The implementation includes:

- A new `reflink_file()` helper in copy.c that handles the low-level reflink operations
- Filesystem capability detection to gracefully fall back to normal checkouts when reflinks aren't supported
- Configuration via `worktree.reflink` (true/false/auto)
- Comprehensive test coverage in t2400-worktree-add.sh

The patch appears well-considered, with clear documentation of the feature and its limitations. The benchmark results in the commit message show significant disk savings (from ~5.3GB for 4 normal worktrees to near-zero allocation with reflink). The implementation maintains all existing worktree protections while adding this optimization.

This looks like a valuable addition for users who frequently create multiple worktrees on copy-on-write filesystems (btrfs, XFS, APFS etc.), particularly in CI/CD or automated testing scenarios. The careful fallback behavior ensures it won't break existing workflows on unsupported platforms.
