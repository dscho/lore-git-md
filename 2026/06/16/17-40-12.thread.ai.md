Core problem or goal
When `git rebase` drops a commit because its changes are already present in the target branch, the sequencer incorrectly copies that commit’s notes to the current HEAD commit. This corrupts the repository’s note history. The discussion has expanded to encompass broader correctness issues in how the rebase machinery handles dropped commits, including fixup sequences, edit commands, and skip operations.

Current status
The original patch is under active review, with no prior versions. The implementation adds a `dropped_commit` output parameter to `do_pick_commit()`, propagates this flag through `pick_one_commit()` and `single_pick()`, and skips note copying when the commit is dropped. Junio C Hamano and Phillip Wood have identified multiple substantive issues:
1. The patch may break `record_in_rewritten()` logic for sequences involving fixup commits, potentially mapping notes to the wrong rewritten commit.
2. The rebase machinery has three additional bugs related to dropped commits: (a) final fixup cleanup, (b) edit command handling, and (c) skip command handling.
3. Documentation does not clarify when users can expect notes to be lost during rebase.
Uwe Kleine-König has addressed surface-level feedback (test script style) but has not resolved the fixup-commit edge case or added documentation. Phillip Wood has volunteered to address the broader rebase-dropped-commit issues in follow-up patches.
