Thread identity
Subject: [PATCH] sequencer: avoid copying notes from dropped commits during rebase
Series version: standalone patch
Originating author: Uwe Kleine-König
Thread type: bugfix patch

Core problem or goal
When `git rebase` drops a commit because its changes are already present in the target branch (via a different commit), the sequencer subsystem incorrectly copies that commit’s notes to the current HEAD commit. This results in notes being attached to the wrong commit, corrupting the repository’s note history.

Current status
The patch is under active review. No prior versions exist. The implementation adds a `dropped_commit` output parameter to `do_pick_commit()`, propagates this flag through `pick_one_commit()` and `single_pick()`, and skips note copying when the commit is dropped. A test script (originally `t3322-notes-rebase.sh`, now proposed for relocation to `t3400-rebase.sh`) verifies the fix. Junio C Hamano has identified two substantive issues: (1) the patch may break `record_in_rewritten()` logic for sequences involving fixup commits, potentially mapping notes to the wrong rewritten commit, and (2) the documentation does not clarify when users can expect notes to be lost during rebase. Uwe Kleine-König has addressed surface-level feedback (test script style: redirection spacing, avoiding `@` for `HEAD`, not writing outside `$TRASH_DIRECTORY`, and using `test_must_fail` for command failure assertions) but has not resolved the fixup-commit edge case or added documentation. Uwe argues that documentation should be self-evident but acknowledges this is subjective.

Key technical details
Files touched: `sequencer.c` (core logic), test script (proposed for relocation from `t3322-notes-rebase.sh` to `t3400-rebase.sh`)
New symbols: `dropped_commit` output parameter in `do_pick_commit()`
Behavior change: notes are no longer copied from commits that are dropped during rebase; the fixup-commit edge case remains unresolved
Test coverage: exercises the edge case where a commit’s changes are already present in the target branch; does not yet cover fixup-commit sequences
On-disk format: unchanged

Open questions and loose ends
1. **Fixup-commit edge case**: If a non-dropped commit is followed by a dropped fixup, the current patch may prevent flushing the pending commit list in `record_in_rewritten()`, potentially mapping notes to the wrong rewritten commit. Uwe has deferred this to someone with deeper Git internals knowledge.
2. **Documentation**: No updates yet to clarify when users can expect notes to be lost during rebase. Uwe considers this self-evident but Junio views it as a blocker.
3. **Test location**: Uwe now agrees with Junio’s suggestion to integrate the test into `t3400-rebase.sh` rather than keeping it in a new script.
