This is a **substantive review** of a documentation patch that adds `git rebase --abort` hints to rebase failure and status messages.

Phillip Wood raises a targeted concern about the patch's core premise: whether the "failed exec" case (where a rebase step's `exec` command fails) is truly analogous to the conflict case. His argument is that a failed exec is typically a minor issue (like a test failure) that the user will want to fix and continue, whereas conflicts are often so severe that aborting is the only practical option. He suggests that adding `--abort` advice in the exec case might mislead users into thinking they *should* abort when continuing is usually the better choice.

The review does not address the status-message changes (which add `--abort` hints during commit splitting/editing), implying those are uncontroversial. The focus is solely on the exec-failure scenario in `sequencer.c`. Phillip’s feedback is grounded in workflow realism rather than code mechanics, making it a substantive critique of the patch’s design rationale. No alternative implementation is proposed, but the objection is clear enough to warrant reconsideration of that specific part of the change.
