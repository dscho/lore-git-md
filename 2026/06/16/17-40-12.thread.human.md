This thread began with a patch series from Phillip Wood to fix a bug where `git rebase` incorrectly copies notes from dropped commits to the current HEAD. The series grew into a nine-patch systemic overhaul addressing edge cases across rebase operations, including empty commits, fixup sequences, edit commands, and merge strategy failures. Junio approved the series and marked it ready for the `next` branch, with only minor typofixes pending.

However, Uwe Kleine-König has now reported that the bug persists in **interactive rebase** (`-i`) while disappearing in non-interactive mode. When rebasing a branch interactively and manually skipping commits that become empty, notes from dropped commits are still incorrectly copied into neighboring commit messages. The same rebase without `-i` completes correctly, suggesting the issue is specific to the interactive backend. Uwe’s report includes exact reproduction steps, commit hashes, and output snippets, making the regression easy to verify.

The discrepancy between backends contradicts the series’ test coverage, which verified both the apply and merge backends. The likely cause is a subtle difference in how the interactive backend handles `record_in_rewritten()`, the function modified in the final patch to skip notes for dropped commits. Phillip or another contributor will need to investigate why the interactive path still copies notes, possibly adjusting the fix or expanding test coverage in `t3404-rebase-interactive.sh`. This is a high-priority follow-up, as it undermines the series’ core fix. No new patches have been proposed yet, but the thread is now focused on diagnosing and resolving this backend-specific regression.
