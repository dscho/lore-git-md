This thread is about fixing a bug in `git rebase` where notes from dropped commits (e.g., those with empty changes) are incorrectly copied to the current HEAD, corrupting note history. The discussion expanded into a systemic audit of how the rebase machinery handles dropped commits across all operations, including edge cases like external merge strategy failures (e.g., merge tool crashes) and command execution failures (e.g., `git commit` failing to run).

Phillip Wood authored a 9-patch series (v3) that addresses the core issue and all known edge cases. The series is complete, approved by Junio C Hamano, and ready for the `next` branch pending minor typofixes. Key changes include:
- Fixing error handling for external merge strategies and command execution failures.
- Introducing `enum pick_result` to distinguish dropped commits from other outcomes, enabling the core behavioral change in the final patch.
- Expanding test coverage for both "apply" and "merge" backends, fixup sequences, and post-rewrite hooks.

The series is self-contained, with Uwe Kleine-König’s original patch superseded. Reviewers like Oswald Buddenhagen and Andrei Rybak provided surface-level feedback (e.g., grammar, punctuation), which has been addressed. A known limitation remains: the "edit" command still erroneously records dropped commits as rewritten, but this is documented and flagged for a separate fix. No substantive objections remain, and the series is expected to land in the next Git release.
