This thread began when Uwe Kleine-König reported a bug in `git rebase`: when a commit is dropped (e.g., because its changes are already present), its notes are incorrectly copied to the current HEAD, corrupting the repository’s note history. Phillip Wood responded with a 9-patch systemic overhaul (v3) that addresses the issue for non-interactive rebase and `--empty=drop` in interactive rebase, covering edge cases like fixup sequences, edit commands, external merge strategy failures, and command execution failures. The series has been approved by Junio C Hamano and is ready for the `next` branch pending minor typofix squashing.

However, Uwe later reported a regression: the fix does not work for interactive rebase (`-i`) when commits are dropped via user-initiated actions like `git rebase --skip` or `--continue` without committing. This is because the series only handles commits dropped by `--empty=drop` (the non-interactive default), not the `--empty=ask` behavior (default in interactive rebase), which inconsistently drops commits on `--continue` but keeps them on `--skip`. Phillip acknowledged the gap and plans a follow-up to address it, but the current series is still considered complete for its intended scope.

The patches touch `sequencer.c` and expand test coverage in `t3400-rebase.sh`, `t3404-rebase-interactive.sh`, and `t5407-post-rewrite-hook.sh`, though gaps remain for interactive rebase’s user-initiated drops and the `--empty=ask` quirk. Key technical changes include introducing `enum pick_result` to clarify the sequencer’s return values and ensuring `record_in_rewritten()` skips dropped commits. Junio’s approval confirms the series is technically sound, and the regression will not block its integration. Oswald Buddenhagen’s recent reply was purely procedural, offering a generic `Acked-by` without substantive review.
