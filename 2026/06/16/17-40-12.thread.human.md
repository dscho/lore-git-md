This thread is about a bugfix patch from Uwe Kleine-König that prevents Git from incorrectly copying notes from dropped commits during rebase. When a commit is dropped because its changes are already present in the target branch, the sequencer currently attaches that commit’s notes to the current HEAD, corrupting the repository’s note history. Uwe’s patch adds a `dropped_commit` flag to track when a commit is dropped and skips note copying in those cases.

The patch is under review, with Junio C Hamano identifying two substantive issues: the fix may break `record_in_rewritten()` logic for sequences involving fixup commits, potentially mapping notes to the wrong rewritten commit, and the documentation doesn’t clarify when users can expect notes to be lost. Uwe has addressed surface-level feedback (test script style, using `test_must_fail`), but the fixup-commit edge case remains unresolved, and he has pushed back on the need for documentation, arguing the behavior should be self-evident. Phillip Wood suggested the approach, but no explicit review has been provided yet.

The patch touches `sequencer.c` and includes a new test script (`t3322-notes-rebase.sh`), though Junio has suggested integrating it into `t3400-rebase.sh` instead. The test covers the edge case where a commit’s changes are already present but doesn’t yet address fixup-commit sequences. The patch is not yet ready for merging, but the underlying issue is acknowledged as real, and the approach is sound if the remaining gaps are closed.
