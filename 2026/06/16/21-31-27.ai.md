This is a technical clarification in the ongoing SHA-1/SHA-256 interoperability effort. Brian M. Carlson responds to Junio C Hamano’s two security-focused questions about packfile URIs and large-object promisors, providing detailed explanations of the current implementation and its limitations.

For **packfile URIs**, Brian explains that the interoperability layer requires each received pack to connect to the existing repository history so that unmapped objects can be resolved using stored mappings. Packfile URIs break this assumption because they deliver multiple packs that are only complete *in aggregate*, not individually—especially the dynamically generated protocol pack, which arrives first and is almost never connected to the local history. While this could theoretically be fixed by pausing `git index-pack`, downloading all URIs, indexing them, and then resuming, no such implementation exists yet. The limitation is not fatal for single-algorithm repositories (unconnected objects are simply ignored), but in a multi-algorithm world it prevents indexing entirely.

On **large-object promisors**, Brian clarifies that the server must possess the *entire* history to generate object mappings, which rules out promisor remotes that offload objects to secondary storage. However, this only affects submodule mappings, shallow clones, and partial clones—regular fetches and clones work fine against existing servers as long as no submodules are involved. Submodule mappings are explicitly gated behind a security override because the client cannot verify that the SHA-1 and SHA-256 object IDs correspond to the same commit; without this check, a malicious server could map a secure SHA-256 submodule commit to an insecure SHA-1 commit.

The response also touches on delta handling: when objects are rewritten from SHA-1 to SHA-256, deltas are preserved by mapping the base and target objects to their new names, avoiding the cost of full redeltification. Brian includes a concrete example (`git clone --object-format=sha256:sha1 https://github.com/bk2204/lawn.git`) to demonstrate that the branch works today for repositories without submodules.
