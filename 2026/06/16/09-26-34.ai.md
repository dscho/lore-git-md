This is the v3 cover letter for a three-patch feature series adding a `--linearize` option to `git replay`. The series teaches `git replay` to flatten merge commits, matching the default behavior of `git rebase --no-rebase-merges`. This version incorporates all feedback from Junio, Elijah Newren, and Justin Tobler: the documentation now includes `--linearize` in the SYNOPSIS and usage array, clarifies its mutual exclusivity with `--revert`, and improves the option description; the code adds a clarifying comment about `last_commit` handling during merge linearization; and the test suite expands coverage to verify `--linearize` with `--advance`, test `--revert`/`--linearize` incompatibility, and use `git range-diff` to confirm patch equivalence. The series touches `replay.c`, `replay.h`, `builtin/replay.c`, the man page, and the test script `t3650-replay-basics.sh`.

The refactoring patches (1 and 2) remain unchanged from v2: patch 1 replaces the `enum replay_mode` with a boolean `reverse` flag, and patch 2 extracts the `put_mapped_commit` helper and renames `mapped_commit` to `get_mapped_commit`. Patch 3 implements the core `--linearize` logic, now with improved documentation and test coverage. The series is positioned as a simpler alternative to Johannes Schindelin’s earlier merge-replay work (pull.2106), and the author reiterates that `--linearize` is intentionally omitted from `git history` due to lack of a clear use case. Potential trivial conflicts with Kristoffer’s documentation changes and Patrick Steinhardt’s `git history drop` series are still noted but expected to be easy to resolve.

Key technical details: the new CLI option is `git replay --linearize`; internal flags are `reverse` (boolean) and `linearize` (boolean); the implementation is mutually exclusive with `--revert` (guarded by a BUG check); and root commits are explicitly replayed while merges are dropped. The test suite now includes cases for replaying down to the root commit, `--linearize` with `--advance`, `--revert`/`--linearize` incompatibility, and a `git range-diff` check for patch equivalence. No unresolved technical objections remain, and the series is ready for final review.
