This is a **design refinement discussion** in the ongoing GSoC patch series that standardizes Git’s path-formatting logic. The series introduces a new `append_formatted_path()` helper to eliminate duplicated path-formatting code across commands, with `rev-parse` as the first consumer.

Phillip Wood (a seasoned reviewer) and the author (K Jayatheerth) are finalizing the API design for the upcoming v6 iteration. The key point of contention was `PATH_FORMAT_DEFAULT`, a value in the shared `path_format` enum that behaves identically to `PATH_FORMAT_UNMODIFIED` but exists solely to preserve `rev-parse`’s backward-compatible behavior. Phillip called this an "API wart" and suggested keeping the backward-compatibility logic localized to `rev-parse` rather than exposing it to other callers.

In this email, Phillip clarifies his preferred approach: **keep `rev-parse`’s existing enums and convert them to the shared `PATH_FORMAT_*` values inside `print_path()`**, rather than introducing a new local enum. This keeps the option-parsing code unchanged while still isolating the quirk to `rev-parse`. The author had proposed a slightly more involved solution (a local enum), but Phillip’s suggestion is simpler and achieves the same goal. The author has already agreed to implement this in v6.

This is the last substantive design feedback before the series graduates to Junio’s `next` branch. The v6 iteration will likely be the final one unless new issues emerge. The patch is well-motivated, thoroughly reviewed, and addresses a real maintenance problem (duplicated path-formatting logic). The implementation is clean, test coverage is comprehensive, and the design now aligns with Git’s preference for explicit plumbing interfaces.
