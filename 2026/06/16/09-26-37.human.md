This is the third and final patch in a well-prepared feature series adding a `--linearize` option to `git replay`. The patch implements the core functionality: when `--linearize` is given, `git replay` drops merge commits and replays only the regular (single-parent) commits, matching the default behavior of `git rebase --no-rebase-merges`.

The implementation is straightforward and clean. The new boolean `linearize` flag is added to the `replay_revisions_options` struct, and the option is exposed in the command-line interface with mutual exclusivity enforced against `--revert`. The core logic lives in `replay.c`: when a merge commit is encountered and `--linearize` is active, the commit is skipped, leaving `last_commit` unchanged so that subsequent commits are reparented onto the previous non-merge commit. The patch also updates the documentation to include `--linearize` in the SYNOPSIS and usage array, adds a clear description of the option, and documents its incompatibility with `--revert`.

Test coverage is thorough. The updated test script verifies that `--linearize` works with `--advance`, rejects the `--revert`/`--linearize` combination, and confirms that the resulting patch sequence is identical to the original (using `git range-diff`). Two additional test cases check that replaying down to the root commit and replaying with `--advance` both produce the expected linearized history.

The patch is clearly ready for final review. All prior feedback from Junio, Elijah Newren, and Justin Tobler has been addressed, and the implementation is consistent with the series' stated goal of providing a server-side equivalent to `git rebase --no-rebase-merges`. The only remaining loose end is a forward-looking design question about extensibility, but that does not affect the correctness or usability of the current feature. If you care about `git replay` or server-side rebase workflows, this patch is worth a quick look.
