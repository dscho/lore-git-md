This thread is about Patrick Steinhardt’s patch series adding four new subcommands—`delete`, `update`, `create`, and `rename`—to `git refs` to consolidate reference manipulation functionality. The series is now at its second version, with the latest email introducing the `git refs create` subcommand, which enforces atomic creation semantics ("must not exist").

The core debate revolves around balancing atomicity, backwards compatibility, and ergonomics in reference creation. Junio C Hamano prefers explicit atomicity (via `create`), while Patrick argues for retaining `update`’s implicit creation behavior (via `0{40}` or omitted `<old-value>`) to preserve script compatibility. The `create` subcommand resolves this tension by offering a dedicated atomic path, leaving `update`’s behavior unchanged for now. Patches 1/5 (mechanical refactoring) and 2/5 (`delete`) are uncontroversial and ready to merge, while 3/5 (`update`) remains tied to the unresolved debate.

The new `create` subcommand is straightforward: it rejects attempts to create existing references and supports options like `--create-reflog` and `--message`. Its 151-line test suite covers basic functionality, symref handling, and error cases. The patch is technically sound and aligns with Junio’s feedback from v1, but the broader question of whether `update` should reject non-existent references (or continue allowing implicit creation) remains open. Other loose ends include reflog handling in `rename` (deferred to a future patch) and error message consistency.

Key participants are Patrick Steinhardt (author) and Junio C Hamano (maintainer). Patrick has addressed most of Junio’s v1 feedback, including naming consistency and test coverage, but the atomicity debate persists. The series interacts with ongoing efforts like the `the_repository` removal and reftable backend work, though no direct conflicts are expected. For now, the `create` subcommand is likely to be merged as-is, while the fate of `update`’s implicit creation behavior awaits further discussion.
