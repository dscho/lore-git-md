This is a **substantive review** from Junio C Hamano on the third patch of Patrick Steinhardt’s four-patch series adding `git refs update`. Junio raises a **design concern** about the absence of a dedicated "create" operation, which could leave users without a way to atomically ensure a reference does *not* already exist before creating it. He suggests two alternatives: (1) repurpose the `update` subcommand to handle creation (using a sentinel value like `""` for `<oldoid>` to signal "must not exist") and deletion (using `""` for `<newoid>`), or (2) add a separate `create` subcommand that rejects updates to existing refs. The current implementation’s `update` subcommand implicitly creates refs if they don’t exist, which Junio implies may be insufficient for safety-critical workflows.

The review also **points out a gap in test coverage**: the existing test for "update creates a new reference" does not verify the failure case where creation is attempted on an existing ref. This omission suggests the current implementation lacks atomicity guarantees, a potential footgun for users who rely on `git update-ref --create-reflog` (which *does* enforce "must not exist" semantics).

This feedback is **likely to shape the series’ direction**, as it touches on the core design of the `git refs` interface. The thread’s next steps will probably involve Patrick addressing whether to add a `create` subcommand, adjust `update`’s behavior, or justify the current approach. The review is concise but carries weight due to Junio’s role as maintainer and his focus on usability and safety. **Key technical details to watch**: the handling of `<oldoid>`/`<newoid>` sentinel values, atomicity guarantees, and how this interacts with reflog creation (`--create-reflog`).
