Core problem or goal: Consolidate reference manipulation functionality (previously scattered across `git-update-ref`, `git-symbolic-ref`, and other commands) under a unified `git refs` interface. The series adds four new subcommands—`delete`, `update`, `create`, and `rename`—to improve discoverability and reduce fragmentation in Git’s reference-handling commands. The central design question—**how to balance atomicity, backwards compatibility, and ergonomics in reference creation**—was resolved: `git refs update` retains the same implicit creation semantics as `git update-ref` (using `$NULL_OID` for atomic "must not exist" checks), while `git refs create` provides an explicit atomic alternative. **Open usability questions**:
1. Whether the `--no-deref` option’s behavior for symbolic reference (symref) handling is intuitive or well-documented, as raised by Toon Claes and clarified by Patrick Steinhardt. The option does not enable symref creation but instead controls whether the command fails when the target reference already exists as a symref. For example, if `refs/heads/symref` is a symref pointing to `refs/heads/target`, `git refs create refs/heads/symref $OID` would create `refs/heads/target` (dereferencing the symref), while `--no-deref` would make the command fail instead. The option’s obscurity and counterintuitive behavior (e.g., requiring prior knowledge of symref existence) remain a usability concern. **New**: Toon Claes now proposes **eliminating `--no-deref` entirely**, arguing that its behavior is too obscure and that users should instead use `git ref` (for dereferenced operations) or `git symbolic-ref` (for symref-specific operations). This would fragment the unified `git refs` interface but avoid the cognitive overhead of `--no-deref`. No code changes are proposed, as the series is already merged, but the feedback highlights a tension between interface unification and CLI ergonomics.
2. **Symref renaming support in `git refs rename`**: Patrick Steinhardt confirmed that the subcommand **does not support renaming symrefs**, citing backend limitations. This gap is now explicitly documented in the test suite (v4) and error messages, though the man page still omits it. The limitation stems from the backend’s inability to handle symrefs in rename operations, rather than a deliberate design choice.
