This is a substantive review comment on the GSoC path-formatting series. Phillip Wood raises a design concern about the API introduced in the series: the `PATH_FORMAT_DEFAULT` enum value, which exists solely to accommodate `rev-parse`'s backward-compatibility needs, creates what he calls an "API wart" that other users of the new `append_formatted_path()` helper shouldn't have to deal with.

The review suggests keeping the existing `rev-parse`-specific enums and converting them to the shared `PATH_FORMAT_*` values inside `print_path()`, rather than exposing the `DEFAULT` concept in the public API. This would make the helper cleaner for future users while preserving `rev-parse`'s exact behavior. Phillip notes the conversion logic already exists in the current code, implying this change would be straightforward.

This is a targeted but important critique that doesn't question the series' overall goal (eliminating duplicate path-formatting code) but does challenge a key design decision. The thread has been moving toward consensus on the technical approach, but this review reopens a fundamental API question that could affect how clean and maintainable the new helper is long-term. The author will need to either justify the current design or rework it to address Phillip's concern.
