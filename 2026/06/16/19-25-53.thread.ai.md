Thread identity
Subject: Adopt Assisted-by: trailer for AI-assisted commits
Series version: none (RFC discussion)
Originating author: Marius Spix
Thread type: design discussion / contributor housekeeping

Core problem or goal
Git currently handles commit message trailers inconsistently: `--signoff` adds an empty line before the trailer and suppresses the trailer if the commit message is otherwise empty, while `--trailer` does not normalize newlines or suppress empty-message trailers. The thread proposes (1) normalizing trailer behavior so that `--trailer "\nAssisted-by: ..."` behaves like `--signoff`, and (2) adopting an `Assisted-by:` trailer to formally attribute AI-assisted commits, propagating it automatically during merge/squash operations to align with the Linux kernel’s recent adoption of the same trailer.

Current status
No decisions or patches yet; the thread remains in exploratory discussion. The proposal faces early pushback on both technical and philosophical grounds. No consensus has emerged on whether Git should adopt `Assisted-by:` or modify `--trailer` behavior.

Key technical details
- Subsystem: commit message parsing and trailer handling (`sequencer.c`, `commit.c`, `trailer.c`)
- Proposed new trailer: `Assisted-by:` (contentious)
- Proposed behavior changes: normalize newline handling in `--trailer`, suppress empty-message trailers, auto-propagate `Assisted-by:` during merge/squash
- No on-disk format changes; purely behavioral
- Clarification: `--trailer "Assisted-by: ..."` already works without explicit `\n`; the original example’s newline was redundant

Open questions and loose ends
- Should Git adopt `Assisted-by:` at all, or is it a project-specific policy decision that Git should avoid?
- Should `Assisted-by:` be treated as a “taint” marker (like `Co-authored-by:`) and auto-propagated during merges/squashes?
- Should `--trailer` normalize newlines and suppress empty-message trailers to match `--signoff` behavior, or is the current inconsistency intentional?
- What constitutes “AI assistance” for attribution purposes (e.g., grammar fixes vs. code generation)?
- Does the Linux kernel’s adoption of `Assisted-by:` set a precedent that Git should follow, or is it irrelevant to Git’s design philosophy?

Participant positions
- **Marius Spix** (originator): Proposes adopting `Assisted-by:` and normalizing `--trailer` behavior to match `--signoff`, framing it as alignment with the Linux kernel.
- **Kristoffer Haugsbakk**: Pushes back on both fronts. Argues that `--signoff`’s special treatment is a historical quirk, not a model for other trailers, and that Git has historically rejected hardcoding project-specific trailers (citing a 2013 `Fixes:` patch rejection as precedent). Views `Assisted-by:` as requiring Git to make policy decisions (e.g., auto-propagating "taint") that the project has avoided. Notes that `--trailer` already works as expected without explicit newlines, undercutting the original motivation for normalization. Position is skeptical; no alternative implementation offered.

Related work
- Linux kernel’s recent `Assisted-by:` requirement for AI-assisted commits (cited as precedent by Marius, contested by Kristoffer).
- 2013 Git mailing list discussion rejecting a hardcoded `Fixes:` trailer (cited by Kristoffer as precedent against project-specific trailers).
