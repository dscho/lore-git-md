This is a **substantive review** from Junio C Hamano on the third patch of Patrick Steinhardt’s four-patch series adding `git refs update`, `delete`, and `rename` subcommands. The review focuses on **design consistency** and **atomicity semantics**, with implications for the entire series.

Junio raises three key points. First, he notes a **naming inconsistency**: the `delete` subcommand uses `<oldvalue>` in its synopsis, while `update` uses `<old-value>` and `<new-value>`. He suggests standardizing on `<old-value>` for both to improve clarity and consistency. This is a minor but important housekeeping detail that will likely be addressed in a v2.

Second, he revisits the **design question of atomic creation semantics**, which he previously flagged in the cover letter. The current `update` subcommand allows implicit creation of references (if `<old-value>` is omitted or `0{40}`), but lacks a way to enforce "must not exist" semantics. Junio now expresses a **slight preference for splitting this into two subcommands**: `update` (which would fail if the reference does not exist) and a new `create` subcommand (which would fail if the reference already exists). This would provide atomicity guarantees for workflows that need them, such as CI/CD pipelines or distributed reference updates. He also suggests moving the `--create-reflog` option to the `create` subcommand, since it would no longer be relevant to `update`.

Third, Junio points out a **minor output inconsistency**: the error message for invalid object IDs in `update` omits quotes around the object name, while `delete` includes them. This is a surface-level nit, but it underscores the importance of consistent user-facing output.

The review does not question the technical implementation of the patch itself, which is well-tested and aligns with the series’ goal of consolidating reference operations. Instead, it targets **higher-level design choices** that will shape how users interact with the new subcommands. The preference for explicit `create`/`update` separation is particularly significant, as it would require non-trivial changes to the CLI, documentation, and test coverage. This feedback is likely to drive a v2 iteration of the series, with the maintainer’s input carrying substantial weight.

For readers following the thread, this review confirms that the series is in a **design-review phase**, with atomicity semantics as the primary open question. The eventual resolution will determine whether `git refs` adopts a more granular (and potentially safer) interface or retains the current implicit-creation approach. The discussion is worth watching for anyone interested in Git’s reference-handling internals or the broader effort to improve CLI discoverability.
