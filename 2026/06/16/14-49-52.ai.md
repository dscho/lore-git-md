This is the first patch in a six-part platform compatibility series addressing Windows LLP64 limitations for handling objects larger than 4GB. The patch adds a test case to `t/t1007-hash-object.sh` that demonstrates the current failure when hashing a 5GB file on systems where `unsigned long` is 32-bit (e.g., Windows). The test uses `git hash-object --literally --stdin` to avoid writing the object, thus bypassing unrelated code paths like zlib compression and packfile handling.

The test is marked as `EXPENSIVE` and `test_expect_failure` with prerequisites `SIZE_T_IS_64BIT` and `!LONG_IS_64BIT`, reflecting the current limitation. The test infrastructure (a 5GB zero-filled file generated by `test-tool genzeros`) and expected SHA-1/SHA-256 hashes are already set up in the test's `setup` block. This patch serves as a baseline for the subsequent type-conversion patches, which will systematically replace `unsigned long` with `size_t` in the object-file handling code paths.

Key technical details for follow-up discussion:
- Test file: `t/t1007-hash-object.sh`, new test case at line 264.
- Test prerequisites: `EXPENSIVE,SIZE_T_IS_64BIT,!LONG_IS_64BIT`.
- Command under test: `` `git hash-object --stdin --literally` ``.
- File generation: `test-tool genzeros $((5*1024*1024*1024))`.
- Expected hashes: `large5GB` (SHA-1: `0be2be10a4c8764f32c4bf372a98edc731a4b204`, SHA-256: `dc18ca621300c8d3cfa505a275641ebab00de189859e022a975056882d313e64`).

The test is designed to be minimal and focused, targeting only the type truncation issue without introducing unrelated dependencies. The series' later patches will walk the call chain from this test, converting the relevant `unsigned long` variables to `size_t` to resolve the 32-bit truncation. The test infrastructure added here will be reused by the other test cases in the series.
