This is a **substantive review** from Phillip Wood addressing a design concern in the ongoing GSoC patch series that standardizes path formatting in Git. The series introduces a new `append_formatted_path()` helper and refactors `rev-parse` to use it, but Phillip identifies an API wart in how the patch exposes `PATH_FORMAT_DEFAULT` to callers.

Phillip’s key point: the current implementation forces all users of `append_formatted_path()` to handle `PATH_FORMAT_DEFAULT`, which exists solely to accommodate `rev-parse`’s backward-compatibility needs. He suggests keeping the existing `rev-parse`-specific enums (`format_type` and `default_type`) and converting them to the shared `path_format` enum *inside* `print_path()`, rather than exposing the quirk to other callers. This would make the API cleaner for future users while preserving `rev-parse`’s exact behavior.

The review is narrowly scoped to the API design but carries weight because it touches a core principle: Git’s plumbing commands prioritize explicit, unambiguous interfaces. Phillip’s suggestion would isolate the backward-compatibility hack to `rev-parse` instead of leaking it into the shared helper. The patch author will need to either justify the current design or rework the conversion logic to address this concern. No code changes are proposed yet—this is a design-level discussion.
