This is Junio C Hamano’s review of Matt Hunter’s v2 patch series introducing the global `fetch.followRemoteHEAD` configuration variable. The series extends Git 2.48’s per-remote `remote.<name>.followRemoteHEAD` with a global default, following the established `fetch.prune`/`remote.*.prune` pattern.

Junio acknowledges the improvements in v2—particularly the switch to non-fatal error handling for unrecognized values and case-sensitive matching—but raises a new concern about the configuration state management. Currently, if `fetch.followRemoteHEAD` is set to an invalid value, the code silently ignores it, leaving the `fetch_config->follow_remote_head` field in an indeterminate state. Junio suggests this should at least be reset to an explicit "unspecified" or "default" value (e.g., `FOLLOW_REMOTE_UNCONFIGURED`) to avoid potential confusion or bugs in later logic.

He also outlines an ideal behavior: invalid values should only trigger warnings (or errors) when the setting is *actually used* during a fetch, not during configuration parsing. This would require a more sophisticated approach than the current `git_config()` callback, which processes values at parse time. Junio notes that the existing per-remote `remote.*.followRemoteHEAD` likely doesn’t follow this ideal either, so the new code isn’t making things worse—but it’s spreading the same "badness" (i.e., parse-time validation) more widely.

The review is substantive but pragmatic. Junio isn’t blocking the series; he’s flagging a design choice that could lead to subtle issues (e.g., a typo in the config value going unnoticed until the setting is needed). His tone suggests this is a "nice to fix" rather than a "must fix," but addressing it would improve consistency and robustness. The ball is now in Matt’s court to decide whether to adjust the implementation or document the current behavior as a known limitation.
