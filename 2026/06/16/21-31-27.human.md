This is a technical clarification in the ongoing SHA-1/SHA-256 interoperability effort. Brian M. Carlson responds to Junio C Hamano’s two security-focused questions about how the interoperability layer handles packfile URIs and large-object promisors.

For **packfile URIs**, the current implementation cannot process packs that aren’t individually connected to the existing history. Since packfile URIs deliver multiple packs (including a dynamically generated protocol pack that arrives first), the system would need to pause indexing, download and index all URI packs, then resume—something not yet implemented. This limitation is specific to multi-algorithm repositories: unconnected objects are fatal here, whereas single-algorithm repos simply ignore them.

On **large-object promisors**, the server must have the full history to provide object mappings, but clients don’t blindly trust them. For shallow/partial clones, the client already trusts the server’s truncated history; if the client later fetches missing objects and runs `git fsck`, it will detect dishonest mappings. Submodules are trickier: because their data lives in separate repos, the protocol rejects submodule mappings unless the user explicitly allows them, due to the risk of a malicious server mapping a secure SHA-256 commit to an insecure SHA-1 one.

The explanation is detailed and pragmatic, acknowledging both the current limitations and the security trade-offs. No new patches or code are introduced—this is purely a design discussion. The thread remains open, awaiting further feedback on whether these constraints are acceptable or require rework.
