This is a **bugfix** for Git's notes handling during rebase operations, specifically addressing a long-standing issue where notes from disappearing commits incorrectly persist. Phillip Wood replies to Uwe Kleine-König's test patch, questioning whether a new test file is necessary rather than extending an existing one.

The bug occurs when a commit vanishes during rebase because its changes are already present in the target branch (but not from the same patch). In this scenario, the commit's notes should not transfer to the rebased parent, but currently do. Uwe's test demonstrates this with a simple commit graph (`A-B-C` on `master` and `A-BD` on a branch), where rebasing `B+C` onto `BD` incorrectly attaches `B`'s note to `BD`. This has been a practical problem for Uwe since 2023, particularly when using notes to track Message-Ids of sent patches, leading to tracking confusion.

Phillip's response is **surface-level**: he suggests the test might be more effective if added to an existing file (like `t3400-rebase.sh`) rather than creating a new one (`t3322-notes-rebase.sh`). He also notes that a prior thread (linked in Uwe's email) included a potential fix, which could serve as a starting point for anyone interested in resolving the issue.
