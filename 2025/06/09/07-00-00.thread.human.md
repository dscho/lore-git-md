This thread explores different approaches to handling duplicate tags in Git, with three distinct proposals now on the table. The original suggestion was to improve error messages by showing commit hashes when a tag already exists, helping users distinguish between harmless duplicates (same commit) and potentially dangerous overwrites (different commit). Maintainer Junio Hamano pushed back, arguing the current simple "tag already exists" message is sufficient since users can investigate further when needed.

A new proposal from Hilco Wijbenga shifts the discussion by suggesting making tag creation idempotent - silently succeeding if the requested tag already points to the same commit, while still failing for conflicting tags. This behavioral approach would solve the original problem without changing error messages. 

The thread now presents three options: enhanced error messages (original proposal), status quo (Junio's preference), or idempotent behavior (new suggestion). The discussion remains focused on user experience and the principle of least surprise, without requiring changes to Git's underlying tag storage. While technical implementation would still center on `builtin/tag.c`, the conversation has broadened to consider whether silent success in idempotent cases aligns with user expectations for the `tag` command. No clear consensus has emerged yet between these approaches.
