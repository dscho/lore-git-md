This thread explores how Git should handle attempts to create duplicate tags, with three main approaches under discussion. The original proposal suggested showing more detailed error messages when a tag exists, distinguishing between harmless duplicates (same commit) and dangerous ones (different commit). Junio Hamano argued the change wasn't necessary, maintaining that the current simple "tag already exists" message suffices.

Hilco Wijbenga then proposed making tag creation idempotent when the target commit matches, which sparked new technical considerations. The latest email from Junio points out a key complication: this approach would behave differently for lightweight versus annotated tags, since annotated tags contain additional metadata like signatures. Silently succeeding could inadvertently discard this metadata when re-tagging, creating an unexpected inconsistency.

The discussion now centers on whether the benefits of idempotency outweigh these complexities. Junio remains neutral but highlights that any implementation would need to either handle tag type matching, document the behavioral differences clearly, or reconsider changing the current behavior altogether. While the original goal was to reduce user confusion between harmless and dangerous duplicates, the conversation has revealed deeper technical tradeoffs that need resolution before moving forward.
