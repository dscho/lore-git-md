This thread explores how Git should handle duplicate tags, particularly focusing on lightweight tags that point to the same commit. The original proposal sought to improve error messages when recreating tags, distinguishing between harmless duplicates (same commit) and dangerous ones (different commits). The current implementation allows recreating lightweight tags pointing to the same commit without requiring `--force`, while still enforcing the force requirement for annotated tags or tags with different targets.

Key participants include Junio Hamano, who supports the technical rationale that lightweight tags can be idempotent since they store no metadata, and Justin Tobler, who raised concerns about losing useful feedback for automation workflows. Randall Becker also supports the idempotency approach. 

Junio recently responded to Justin's concerns, critiquing the example workflow (`git tag T O && git push --tags`) as not robust for multi-remote scenarios and suggesting `--follow-tags` as a better alternative. While Justin sees value in distinguishing between tag creation and no-op cases, Junio considers this distinction non-essential. This exchange highlights differing perspectives on scriptability impacts but doesn't challenge the core technical approach.

The thread appears headed toward accepting the lightweight tag idempotency change, with the understanding that some automation use cases may lose feedback. Broader discussions about error message improvements and comprehensive validation remain open but seem likely to be addressed separately if at all. The maintainer's position suggests the patch is technically sound and ready to proceed, despite unresolved peripheral concerns.
