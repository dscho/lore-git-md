This is a response in the ongoing discussion about Git's handling of duplicate tags, specifically addressing the idempotency proposal. Junio Hamano acknowledges Hilco Wijbenga's suggestion to make tag creation idempotent when the tag already points to the same commit, but raises an important technical caveat.

The key point here is that while the idempotent approach would work cleanly for lightweight tags (where matching commit hashes could safely allow silent success), it becomes problematic for annotated or signed tags. These tag types contain additional metadata beyond just the commit reference, so silently accepting a duplicate request could inadvertently change the tag's type or lose signature information.

Junio notes this creates an inconsistency in behavior between lightweight and annotated tags, which users might find surprising. The response maintains his earlier position that the current behavior (always failing on duplicates) may still be preferable, though he doesn't outright reject the idempotency idea - just highlights its complications.

This moves the discussion forward by identifying a concrete technical hurdle for the idempotency proposal, suggesting that any implementation would need to either:
1) Handle tag type differences explicitly (making the behavior more complex)
2) Accept the inconsistency between tag types
3) Perhaps reconsider whether the change is worth these complications

The email maintains the thread's technical focus while adding new considerations about tag type handling that weren't fully explored in earlier messages.
