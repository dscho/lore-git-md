Thread examining approaches to handle duplicate tags in Git, with three design proposals under discussion. Original issue focused on modifying `builtin/tag.c`'s `create_tag()` to improve error messages when a tag exists, distinguishing between same-commit (harmless) and different-commit (dangerous) cases. Current positions include: original detailed hash display, Junio Hamano's preference for minimal messaging, and Hilco Wijbenga's comprehensive tag idempotency requiring exact equivalence of all attributes.

Junio Hamano now proposes a technical implementation for partial tag idempotency, changing behavior rather than just messages. His patch makes lightweight tag creation idempotent when pointing to the same commit (allowing repeated `git tag T O` without `--force` if T already points to O), while maintaining existing behavior for annotated tags (still requiring `--force`) and different-target cases. Implementation modifies object comparison in `builtin/tag.c` and updates `t/t7004-tag.sh` tests.

This creates three distinct approaches in play:
1. Mirth Hickford's message-only middle ground (simple messages for same-commit, explicit warnings for dangerous overwrites)
2. Hilco Wijbenga's full attribute comparison for complete idempotency
3. Junio's lightweight-only partial idempotency with behavioral change

Key technical considerations expanded:
- Implementation spectrum from message tweak (Mirth) to full validation (Hilco) to Junio's selective behavior change
- New asymmetry between lightweight and annotated tag semantics
- Whether error message improvements alone suffice versus behavioral changes
- Test coverage for both allowed cases and maintained restrictions
- Scripting compatibility implications of behavioral changes

Junio's position has evolved from status quo preference to proposing a minimal behavioral change that partially addresses idempotency while avoiding message complexity. This introduces new tradeoffs between implementation complexity, behavioral consistency across tag types, and the thread's original safety goals. The patch doesn't directly address error message improvements that initiated the discussion, potentially leaving that aspect unresolved even if this change merges. No consensus yet between message refinement, partial behavior change, or comprehensive idempotency.
