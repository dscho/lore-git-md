This thread examines approaches to improve Git's handling of duplicate tags, focusing on three distinct design proposals. The original discussion centered on modifying `builtin/tag.c`'s `create_tag()` to show more detailed error messages when a tag exists, including whether it points to the same commit (dangerously) a different one. Junio Hamano opposed this, arguing the current generic "tag already exists" message suffices since users can investigate manually.

Hilco Wijbenga now proposes a third approach: making tag creation idempotent when the requested tag already points to the same commit, while still failing for conflicting tags. This would change `git tag hello v1.9.5` to succeed silently if 'hello' exists at v1.9.5, addressing the original use case through behavior rather than messaging.

Key technical details remain focused on `builtin/tag.c`, handling both lightweight and annotated tags without modifying underlying storage. The thread now presents three positions:
1. Original: Show commit hashes in errors to distinguish cases
2. Junio: Keep current simple error message
3. Hilco: Make same-commit tagging idempotent

Open questions include:
- Whether silent success for idempotent cases violates principle of least surprise
- If behavioral change is preferable to improved messaging
- How each approach impacts scripting use cases

Junio's position remains that the current behavior is sufficient, while the alternatives aim to reduce user confusion between harmless and dangerous duplicates. No resolution has emerged yet between these approaches. The discussion remains technical without broader tag storage implications.
