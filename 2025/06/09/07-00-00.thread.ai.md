Thread examining approaches to handle duplicate tags in Git, focusing on a lightweight tag idempotency implementation. Original issue sought improved error messages in `builtin/tag.c`'s `create_tag()` to distinguish same-commit (harmless) vs different-commit (dangerous) tag duplicates. Current implementation allows recreating lightweight tags pointing to same commit without `--force`, while requiring force for annotated tags or different targets. Key conditions: existing lightweight tag with matching target (`oideq(&object, &prev)`). Test coverage verifies correct behavior for all cases.

Technical rationale (from Junio Hamano) holds that lightweight tags can be idempotent since they store no metadata, while signed/annotated tags must create new objects (due to timestamps/tagger identity) and maintain force requirements. Justin Tobler raised a UX consideration about feedback loss for automation (`git tag T O && git push --tags` workflows), which Junio has dismissed as non-essential, critiquing the example workflow as non-robust and suggesting `--follow-tags` as the preferred alternative. This maintains the technical position that lightweight tag idempotency is correct while indicating the automation feedback concern may be dismissed.
