This thread examines approaches to improve Git's handling of duplicate tags, with three design proposals under discussion. The original issue centered on modifying `builtin/tag.c`'s `create_tag()` to show more detailed error messages when a tag exists, including whether it points to the same commit (harmless) or a different one (dangerous). Junio Hamano opposed this, arguing the current generic "tag already exists" message suffices since users can investigate manually.

Hilco Wijbenga proposed making tag creation idempotent when the requested tag already points to the same commit, while still failing for conflicting tags. Andreas Schwab identified a key limitation: the approach doesn't account for cases where the existing tag differs in type (annotated vs lightweight), meaning silent success could inadvertently convert between tag types. Junio's latest response expands on this technical complication, noting that while lightweight tag idempotency would be straightforward, annotated tags introduce complexity because their additional metadata (signatures, messages) would be silently discarded.

The thread now presents three positions with new technical considerations:
1. Original: Show commit hashes in errors to distinguish cases
2. Junio: Keep current simple error message
3. Hilco: Make same-commit tagging idempotent (now considering tag type preservation)

Key technical details focus on `builtin/tag.c` handling both lightweight and annotated tags without modifying storage. The discussion has expanded to consider:
- Silent success for idempotent cases might violate principle of least surprise when tag types differ
- Whether behavioral change (with type checking) is still preferable to improved messaging
- How each approach impacts scripting use cases that might rely on current behavior
- Implementation constraints around annotated tag metadata preservation

Junio maintains that current behavior may be sufficient, while implicitly suggesting any idempotency implementation would need to either handle tag type matching, document behavioral differences, or reconsider the change's complexity. The discussion remains technical, focused on tag creation behavior rather than broader storage implications, with no resolution yet between these approaches. The new tag type consideration adds significant complexity to the idempotency proposal.
