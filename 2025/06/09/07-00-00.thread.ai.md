Thread examining approaches to handle duplicate tags in Git, with three design proposals under discussion. Original issue focused on modifying `builtin/tag.c`'s `create_tag()` to improve error messages when a tag exists, distinguishing between same-commit (harmless) and different-commit (dangerous) cases. Current positions include: original detailed hash display, Junio Hamano's preference for minimal messaging, and Hilco Wijbenga's comprehensive tag idempotency requiring exact equivalence of all attributes.

Mirth Hickford now proposes a middle ground - maintaining current simple messages for same-commit cases while adding "but points at a different commit" only for dangerous overwrites. This compromise:
1. Avoids raw hash display (addressing Junio's readability concerns)
2. Preserves current behavior's simplicity
3. Provides actionable overwrite warnings (original goal)
4. Requires only target commit comparison (lighter than Hilco's full attribute check)

Technical considerations expanded to include:
- Implementation complexity spectrum from simple message tweak (Mirth) to full attribute validation (Hilco)
- Behavioral consistency between lightweight/annotated tags
- Scripting compatibility with current failure modes
- Whether error message improvements alone satisfy the need without full idempotency

Junio maintains status quo preference but implicitly sets a high bar for any idempotency implementation. Hilco's approach remains the most comprehensive but complex solution. Mirth's proposal offers a viable intermediate path that may resolve the original safety concern without the implementation burden of full idempotency. No consensus yet between status quo, message-only improvement, or comprehensive behavioral change.
