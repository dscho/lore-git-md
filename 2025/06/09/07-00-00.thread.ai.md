Thread examining approaches to handle duplicate tags in Git, with three design proposals under discussion. Original issue focused on modifying `builtin/tag.c`'s `create_tag()` to provide more detailed error messages when a tag exists, distinguishing between same-commit (harmless) and different-commit (dangerous) cases. Junio Hamano opposed this, favoring the current generic "tag already exists" message.

Hilco Wijbenga's refined idempotency proposal now requires exact tag equivalence for silent success - matching both commit references and all tag attributes (type, messages, signatures for annotated tags). This addresses Junio's technical concerns about naive implementations allowing silent type conversions between lightweight and annotated tags. The proposal maintains core idempotency goals while preventing metadata loss scenarios.

Current positions:
1. Original: Show commit hashes in errors to distinguish cases
2. Junio: Keep current simple error message
3. Hilco: Make tagging idempotent only for exactly matching tags (commit + full attributes)

Technical considerations now include:
- Full tag equivalence checking required for safe idempotency
- Implementation complexity in `builtin/tag.c` to validate all tag attributes
- Behavioral consistency between lightweight and annotated tag handling
- Scripting use cases that might rely on current failure modes
- Whether the added implementation complexity justifies the behavioral change

Junio's position remains that current behavior may be sufficient, while implicitly suggesting any idempotency implementation must properly handle the full complexity of tag type differences. The discussion has evolved from simple commit reference checking to a more comprehensive approach that could make idempotency viable if implemented carefully. No resolution yet between maintaining status quo versus adopting the more complex but potentially more user-friendly idempotent behavior.
