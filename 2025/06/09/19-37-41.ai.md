This is a discussion about tag creation behavior in the ongoing thread about improving error messages for duplicate tags. Hilco Wijbenga proposes an alternative approach to the original suggestion - instead of showing more detailed error messages when a tag already exists, they suggest making tag creation idempotent when the requested tag already points to the same commit. 

The key technical point is that `git tag hello v1.9.5` would become a no-op if 'hello' already points to v1.9.5, while still failing if the existing tag points elsewhere. This would address the original concern about distinguishing harmless duplicates from dangerous overwrites through behavior rather than messaging.

This represents a third design option in the thread, differing from both:
1. The original proposal to show commit hashes in error messages
2. Junio's position to keep the current simple error message

The suggestion introduces new considerations about the principle of least surprise - whether silently succeeding for idempotent cases aligns with user expectations for the `tag` command. The thread now has three distinct approaches to handling tag conflicts, with no clear consensus yet emerging. The discussion remains focused on `builtin/tag.c`'s behavior without touching the underlying tag storage mechanisms.
