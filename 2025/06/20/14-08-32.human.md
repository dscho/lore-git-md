This is a continuation of the discussion about Git's code formatting tools and policies, specifically focusing on when and how style suggestions should be applied.

Christian Couder responds to Junio Hamano's earlier points about clang-format usage, maintaining that many of the tool's suggestions fall into "bikeshedding territory" rather than clear improvements. He argues against enforcing style changes that could annoy contributors, spark unnecessary debates, or produce contextually wrong suggestions - particularly around line wrapping where the tool doesn't consider surrounding line lengths.

The exchange reveals differing philosophies: Junio sees value in consistent style application for new code (even for marginal improvements), while Christian prefers a more selective approach that only flags unambiguous improvements. Christian suggests the risks of over-eager formatting (inconsistent line lengths, misplaced groupings) outweigh the benefits of mechanical consistency.

Technical suggestions from earlier in the thread are acknowledged but not resolved - post-commit hooks, format-patch integration, and documentation updates remain potential paths forward. The core tension persists between Junio's view of style as an evolving standard (where new code should follow current norms) and Christian's pragmatic stance that many formatting changes simply aren't worth the cost in contributor friction or review overhead.

The discussion remains productive but shows no immediate convergence - the fundamental question is whether Git should prioritize mechanical consistency (accepting some imperfect outputs) or human judgment (accepting some style variation to avoid bad automated suggestions). Both sides agree the current tool produces too many low-value suggestions, but differ on whether the solution lies in better configuration or more selective enforcement.
