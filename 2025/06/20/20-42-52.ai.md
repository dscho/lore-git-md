This is a follow-up discussion in the SHA-256 default transition thread, specifically addressing test coverage for backward compatibility. Junio C Hamano raises concerns about ensuring post-3.0 Git maintains full functionality with historical SHA-1 repositories, particularly those without explicit repository format versions. brian m. carlson confirms comprehensive testing of this scenario, noting that the test suite would show widespread failures if basic operations like clone/fetch/push between SHA-1 repositories were broken.

Key technical details confirmed in this exchange:
- The test coverage for SHA-1 compatibility is currently spread across multiple test files rather than concentrated in a single dedicated test
- Repository initialization with version 0 format (no extensions) is explicitly tested
- Some tests even verify behavior without any config file present
- A previously undiscovered bug in this area was caught and fixed before submission

The discussion reveals an important long-term testing strategy: after Git 3.0 release, the GIT_TEST_DEFAULT_HASH variable can be switched from sha256 to sha1 to continue verifying SHA-1 compatibility. This builds confidence that the SHA-256 default won't accidentally break existing SHA-1 repository workflows.

The exchange demonstrates the thoroughness of the testing approach and provides additional validation of the series' readiness, though it doesn't introduce any new technical changes to the patches themselves.
