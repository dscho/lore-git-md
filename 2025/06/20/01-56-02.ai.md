This is a discussion about the hash algorithm transition constants in the ongoing SHA-256 default effort. Junio C Hamano questions the need for the new GIT_HASH_ORIGINAL constant introduced in patch 02/10 of the series, which is currently just a synonym for GIT_HASH_SHA1 but meant to document cases where SHA-1 is required by legacy formats (like bundle v1/v2).

The key technical point is whether GIT_HASH_ORIGINAL provides meaningful documentation value beyond just using GIT_HASH_SHA1 directly. Junio argues that using GIT_HASH_SHA1 already clearly indicates SHA-1 is required, and that GIT_HASH_ORIGINAL's name misleadingly suggests it could change (when in fact these legacy formats will always require SHA-1). The constant was added to explicitly mark code paths tied to historical formats, but Junio is skeptical this adds clarity versus the existing SHA1 constant.

This discussion probes an architectural decision in the SHA-256 transition series - whether to maintain this documentary distinction between "SHA-1 by default" (GIT_HASH_DEFAULT) and "SHA-1 by historical necessity" (GIT_HASH_ORIGINAL). The outcome could affect how future developers understand and modify these hash algorithm constraints in the codebase.
