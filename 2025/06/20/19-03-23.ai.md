This is a follow-up discussion in the git-credential-netrc symbolic port bugfix thread, raising broader questions about credential manager behavior with symbolic ports.

Brian Carlson questions whether the current patch's approach of accepting symbolic ports in the netrc helper is the right architectural direction. They raise several important points about credential manager consistency:

1. Whether symbolic ports work with credential managers outside email contexts (like HTTP)
2. Whether credential matching works when credentials are stored with symbolic names but looked up with numeric ports (or vice versa)
3. Whether this behavior is documented in the credential manual
4. Suggests an alternative approach where `git-send-email` would resolve symbolic ports to numbers before credential lookup

The questions imply this might be solving the symptom rather than the root cause, and that the credential system may not be designed to handle port name/number equivalency consistently across all helpers. The maintainer had previously approved the technical validation changes based on RFC6335, but this new message suggests reconsidering the architectural approach.

Key technical considerations raised:
- Credential matching behavior between symbolic and numeric port representations
- Documentation expectations in `git-credential(1)`
- Whether port resolution belongs in the credential helper or the calling code (`git-send-email`)

This introduces new architectural questions that weren't part of the original patch review, potentially requiring changes to the solution direction despite the earlier RFC6335-based consensus. The thread may now need to discussing credential system design principles rather than just the specific netrc helper fix.
