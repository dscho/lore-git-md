This is a continuation of the discussion about Git's `.clang-format` configuration and style enforcement. Junio C Hamano responds to Christian Couder's earlier comments about the tool's output quality and when style suggestions should be enforced.

The key points in this email:
1. Junio suggests a post-commit hook (rather than pre-commit) for style feedback, to avoid forcing suboptimal changes while still providing guidance
2. He distinguishes between style fixes for new code (worth considering) versus existing code (not worth churn)
3. Disagrees with Christian about what constitutes "false positives" - believes even minor improvements are worth catching in new code
4. Notes GitHub CI only runs style checks on PRs, not regular pushes, which he finds appropriate
5. Acknowledges some special cases where long lines might be justified (like function declarations for grep-ability)

The discussion continues to explore the tension between mechanical consistency and human judgment in code formatting, with Junio taking a pragmatic middle ground - wanting to catch style issues early but not enforce them rigidly on existing code. The thread remains open on how best to implement these checks without creating unnecessary churn or burden for contributors.
