This is a discussion about Git's code formatting tools and policies, specifically focusing on the trade-offs between automated style enforcement and human judgment. Christian Couder responds to Junio Hamano's earlier points about when and how to apply clang-format suggestions.

Christian argues against Junio's position that clang-format's line-wrapping suggestions should be followed for new code, even when the improvements are minor. He maintains that many of these suggestions fall into "bikeshedding territory" rather than representing clear improvements, citing examples where the tool breaks logical grouping of related code or creates inconsistent line lengths. Christian warns that overly aggressive style checking risks annoying contributors, sparking unproductive debates, and potentially introducing wrong suggestions due to lack of context.

The discussion reveals differing philosophies: Junio sees value in consistent mechanical improvements for new code, while Christian prefers fewer, higher-confidence suggestions to avoid churn. Christian proposes that tools should help produce coherent whole-file formatting patches rather than making piecemeal suggestions, allowing files to reach a stable, readable state before further changes.

Technical considerations include:
- The challenge of handling line wrapping when surrounding code has varying line lengths
- Special cases like function declarations where grep-ability may justify style exceptions
- Potential approaches like preparatory formatting patches to establish consistent baselines

The exchange highlights ongoing tensions in the style enforcement discussion: mechanical consistency vs. human judgment, when to apply checks (pre-commit vs. pre-merge), and how to handle edge cases where automated tools produce questionable output. Both agree that current tooling produces too many low-value suggestions, but differ on whether the solution is better configuration or more selective enforcement.
