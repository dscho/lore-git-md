This is a continuation of the ongoing discussion about Git's `.clang-format` configuration and automated code formatting. Junio C Hamano responds to Brian m. carlson's push for making clang-format enforcement more strict and automated.

Junio cautions against a "fire-and-forget" approach to automated formatting, arguing that the current tool output still contains many suggestions that would actually make the code less readable, not just stylistically different. He distinguishes between subjective style preferences (where consistency might be valuable) and objective readability concerns (where the tool's suggestions are actively harmful). 

The response emphasizes that until the tool's configuration can reliably produce high-quality output, enforcing its suggestions automatically would degrade code quality rather than improve it. This counters Brian's position that the project should accept "good enough" mechanical formatting for the sake of consistency, similar to Go's `gofmt` approach.

The exchange highlights the core tension in the thread: whether to prioritize mechanical consistency (Brian's position) or human judgment about readability (Junio's position). Junio's latest response suggests the project isn't yet at a point where automated enforcement would be beneficial, though he leaves open the possibility of revisiting this if the tool's output improves.
