Junio Hamano raises questions about the GIT_HASH_ORIGINAL constant introduced in the SHA-256 transition series. This is a technical discussion about the second patch in the series, which adds a new constant to distinguish between SHA-1 usage that's required by legacy formats versus other SHA-1 usage.

Hamano questions the value of having GIT_HASH_ORIGINAL as a synonym for GIT_HASH_SHA1, noting that since it represents a fixed historical fact (older formats that hardcode SHA-1), it's unclear why we'd need this indirection when we could just use GIT_HASH_SHA1 directly. He suggests that using GIT_HASH_SHA1 in these cases already clearly indicates the code must keep using SHA-1 regardless of the default hash algorithm.

The discussion touches on an important distinction in the series' approach: while GIT_HASH_DEFAULT provides flexibility point for future hash algorithm changes, GIT_HASH_ORIGINAL is meant purely as documentation to mark places where SHA-1 is fundamentally required. Hamano seems skeptical about whether this documentation value justifies the additional constant, suggesting the existing GIT_HASH_SHA1 usage might be sufficient to convey the same meaning.

This exchange highlights a potential point of contention in the series - whether the new constant adds meaningful value or just introduces unnecessary complexity. The response from the original author will likely need to clarify the documentation rationale more concretely or consider simplifying the approach.
