Thread identity: Cover letter for a series preparing Git's transition to SHA-256 as the default hash algorithm, targeting Git 3.0 when built with WITH_BREAKING_CHANGES. Authored by brian m. carlson, who previously led the hash-algorithm-agnostic internals work.

Core problem/goal: Implement SHA-256 as the built-in default hash algorithm while maintaining backward compatibility, allowing testing before Git 3.0 release. The series introduces constants (GIT_HASH_DEFAULT for SHA-256, GIT_HASH_ORIGINAL for SHA-1) to distinguish between default/legacy vs intentional SHA-1 usage, with ongoing discussion about their long-term naming.

Key technical details:
- New hash.h constants GIT_HASH_DEFAULT and GIT_HASH_ORIGINAL implemented
- GIT_HASH_DEFAULT now conditionally defined as SHA-256 (with WITH_BREAKING_CHANGES) or SHA-1 (without) in final patch
- GIT_HASH_ORIGINAL used in 9 files handling legacy formats (bundle, transport, serve) that must remain SHA-1
- Repository setup and legacy format handling updated to use new constants (11 files changed across patches)
- Test suite adjusted with GIT_TEST_BUILTIN_HASH variable and --hash=builtin test_oid option
- DEFAULT_HASH_ALGORITHM test prerequisite added
- 8 commands updated to use GIT_HASH_DEFAULT when operating outside repository
- Repository initialization uses GIT_HASH_DEFAULT for new repos while maintaining GIT_HASH_ORIGINAL for existing ones
- REPOSITORY_FORMAT_INIT macro and read_repository_format function modified in setup.c/setup.h
- Technical discussion reveals subtle interactions between repository version handling (-1 case) and hash algorithm selection
- Edge cases examined where repositories might not declare format version but still try to use
- handle_extension_v0() behavior potentially affected by clear_repository_format() call
- Final patch implements nested preprocessor indentation style fix per Junio's review
- Junio C Hamano's final review highlights need for comprehensive testing of backward compatibility with version-less SHA-1 repositories, ensuring full functionality when built with SHA-256 default

Current status: Series now complete with SHA-256 as default when WITH_BREAKING_CHANGES is set. Junio C Hamano approves technical approach and provides final style correction (preprocessor indentation). Earlier suggestion remains to post-transition rename GIT_HASH_ORIGINAL to something explicitly mentioning SHA-1 (e.g. GIT_HASH_MUST_BE_SHA1) for long-term clarity. Final review emphasizes testing verification of legacy repository compatibility.

Open questions/loose ends:
- Final naming of SHA-1 constant (transitional GIT_HASH_ORIGINAL vs permanent GIT_HASH_MUST_BE_SHA1)

- Need to set hash_algo to GIT_HASH_ORIGINAL before reading config requires clarification

- Need to confirm comprehensive testing coverage for legacy SHA-1 repositories, especially those without explicit core.repositoryformatversion declarations
