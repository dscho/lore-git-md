This thread documents the completion of a major technical milestone - implementing SHA-256 as Git's default hash algorithm when built with the WITH_BREAKING_CHANGES option, paving the way for Git 3.0. The series, authored by brian m. carlson, builds on years of foundational work to make Git's internals hash-algorithm-agnostic.

The key achievement is a clean transition mechanism: SHA-256 becomes the default through the GIT_HASH_DEFAULT constant when WITH_BREAKING_CHANGES is set, while maintaining backward compatibility via GIT_HASH_SHA1_LEGACY for cases requiring SHA-1. The final version improved test infrastructure to dynamically detect the hash algorithm rather than hardcoding assumptions. Junio C Hamano has approved the technical approach after extensive review.

While the implementation is complete, two items remain open before this can ship. First, documentation needs updating for the handle_extension_v0() function. Second, there's an unresolved debate about whether external commands should use the new default (GIT_HASH_DEFAULT) as brian m. carlson implemented, or fall back to SHA-1 (GIT_HASH_SHA1_LEGACY) as Patrick Steinhardt advocates for script compatibility. These decisions will need resolution before the SHA-256 default appears in a release.

The work represents a significant step toward Git 3.0, though interoperability between SHA-1 and SHA-256 repositories remains as future work. The series has been thoroughly tested and incorporates feedback from multiple reviewers, with the final version addressing Junio's request for better test infrastructure through dynamic hash algorithm detection.
