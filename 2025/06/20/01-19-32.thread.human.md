This thread centers on preparing Git for a major transition - making SHA-256 the default hash algorithm when built with the WITH_BREAKING_CHANGES flag, targeting Git 3.0. The series, authored by brian m. carlson (who previously led the foundational work to make Git's internals hash-algorithm-agnostic), introduces new constants to distinguish between default/legacy versus intentional SHA-1 usage.

The technical implementation has been thoroughly reviewed and approved by maintainer Junio C Hamano after extensive discussion of edge cases in repository initialization. Testing confirms backward compatibility with version-less SHA-1 repositories, with comprehensive test coverage spanning multiple scenarios. The only remaining discussion point is the naming of the SHA-1 constant used for legacy formats - while the current GIT_HASH_ORIGINAL works, alternatives like GIT_HASH_MUST_BE_SHA1 (Junio's suggestion) and GIT_HASH_LEGACY_SHA1 (the author's counter-proposal) are being considered. The author has shown flexibility on this final naming issue while maintaining the important semantic distinction between SHA-1 usage required by legacy formats versus optional SHA-1 selection.

Once this naming question is resolved, the series appears ready for inclusion. The larger SHA-256 interoperability work remains as separate follow-up work, and the Git 3.0 release timing is not yet determined. The discussion reflects the care being taken to ensure this significant architectural transition maintains backward compatibility while providing clear signaling about hash algorithm requirements.
