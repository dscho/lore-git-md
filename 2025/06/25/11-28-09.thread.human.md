Here's a human-readable summary of the thread so far:

A performance regression has been reported in `git for-each-ref` when working with large numbers of tags. Andrzej Dębski from Dropbox found that operations like `git for-each-ref --format="%(refname)" refs/tags --merged HEAD` became significantly slower starting with Git 2.40.0 compared to 2.39.5, particularly in repositories with around 65,000 tags. The slowdown appears to stem from the `tips_reachable_from_bases` function introduced in commit cbfe360b140, where execution time scales with the number of tags.

This regression impacts real-world workflows at Dropbox, where their Go tooling relies on this command. The performance degradation persists through at least Git 2.50. The core issue seems to be the new reachability checking for merged refs, which particularly affects operations using the `--merged` filter on large tag sets. The thread is currently open with the question of whether this regression warrants a fix, given that the command worked faster in earlier versions.
