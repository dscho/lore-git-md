Performance regression confirmation in `git for-each-ref --merged` with large tag sets. Kristoffer Haugsbakk confirms Andrzej Dębski's report of a significant slowdown in `git for-each-ref --merged` operations when processing repositories with ~65K tags, comparing Git 2.39.5 (fast) to versions 2.40.0 through 2.50 (slow). The regression stems from the `tips_reachable_from_bases` function introduced in commit cbfe360b140, where execution time scales linearly with tag count. This particularly impacts Dropbox's monorepo workflows that rely on Go tooling.

The email serves primarily to bring the original author of the problematic commit into the discussion, suggesting this is being treated as a legitimate regression worth addressing. No new technical details are added beyond the original report, but the confirmation from another party lends weight to the issue's validity. The thread appears to be moving toward solution-finding, with the next logical step being input from the commit author or other performance experts.

For users with large tag sets, this regression makes certain operations 20+ seconds slower than they were in Git 2.39.5, representing a clear performance degradation that warrants attention from the Git maintainers. The fact that the slowdown correlates directly with tag count suggests the issue will only become more pronounced as repositories grow.
