This thread addresses a bug in `git pull --prune` where case-conflicting references (like `origin/TOM/b2` and `origin/tom/b2`) cause the entire pruning operation to fail on case-insensitive filesystems (common on macOS and Windows). The original reporter, ryenus, identified the issue in refs.c where batch deletions abort if any case conflicts exist.

The initial proposed solution involved processing each reference deletion individually rather than in batches, which brian m. carlson helped validate by providing testing methods for case-insensitive environments. However, Karthik Nayak has now raised concerns that this approach would cause significant performance degradation, particularly for the reftable backend. He suggests two alternatives: a short-term fix that simply skips duplicate refs in case-insensitive mode (shown in a prototype diff), and a more comprehensive long-term solution involving proper conflict resolution in reference transactions that would align with ongoing work on batched updates in git-fetch.

The discussion now centers on balancing correctness with performance - while the individual transaction approach solves the immediate problem, it may not be the right architectural direction given the performance implications and ongoing work in related areas. The thread awaits further input on whether to proceed with the simpler short-term solution or wait for more fundamental transaction handling improvements.
