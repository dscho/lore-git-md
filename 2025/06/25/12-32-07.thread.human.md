This thread addresses a bug in `git pull --prune` on case-insensitive filesystems (like macOS and Windows), where attempts to prune references fail if there are case conflicts (e.g., `origin/TOM/b2` vs `origin/tom/b2`). The discussion has evolved through several technical approaches, starting with individual transaction handling (rejected for performance reasons) to the current proposal of a strmap-based solution that detects conflicts by normalizing refnames to lowercase while preserving original casing. 

A key development came from Patrick Steinhardt, who strongly advocated making the reftable backend the default solution, citing its inherent handling of case sensitivity and other technical advantages. Junio C Hamano endorsed this direction, suggesting an experimental flag as an interim step toward eventual reftable adoption in Git 3.0. The discussion now includes considerations around migration documentation and ecosystem compatibility, with reftable seen as the preferred long-term fix.

Chris Torek recently expanded the scope by pointing out that macOS's Unicode normalization behavior introduces additional collision scenarios beyond simple case-folding—different Unicode sequences representing the same character (like decomposed vs. precomposed umlauts) can also conflict on HFS+/APFS. This complicates the strmap approach, as it would need to account for both case folding and Unicode normalization equivalences. While no specific solution is proposed, this observation reinforces the argument for reftable as a more robust backend solution, as it inherently avoids these filesystem-specific quirks.

The thread remains active with two viable paths: Jayatheerth K's strmap-based interim solution or pushing forward with reftable adoption. Junio and Patrick's alignment on reftable as the future default suggests momentum in that direction, though practical considerations (documentation, migration, and ecosystem readiness) still need addressing. Chris's note serves as a reminder that filesystem behaviors can introduce subtle edge cases that may favor the reftable approach in the long run.
