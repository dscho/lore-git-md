This thread addresses a bug in `git pull --prune` where case-conflicting references (like `origin/TOM/b2` and `origin/tom/b2`) cause failures on case-insensitive filesystems (common on macOS/Windows). The issue stems from how batch reference deletions handle these conflicts in refs.c.

After technical discussion, initial solutions like individual transactions (too slow) and adjacent-ref filtering (invalidated by brian m. carlson) have been set aside. The conversation has shifted toward reftable as a more robust solution, since its design inherently handles case preservation better than the filesystem-based backend. Junio C Hamano has now weighed in with a lighthearted but telling comment, encouraging reftable adoption ("the more adopters we have, the merrier") while acknowledging it's still maturing. His tone suggests reftable is the preferred path forward, though the project isn't mandating it. The thread remains open on whether to accelerate reftable adoption for affected systems or wait for broader ref transaction improvements, with performance considerations being the key constraint.
