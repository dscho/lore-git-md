This thread addresses a bug in `git pull --prune` where case-conflicting references (e.g., `origin/TOM/b2` and `origin/tom/b2`) cause failures on case-insensitive filesystems like those default on macOS and Windows. The issue stems from how batch deletions in `refs.c` handle these conflicts, currently failing the entire operation if any case variants exist.

The discussion began with ryenus's bug report, followed by Karthik Nayak proposing two approaches: a short-term fix filtering out case-conflicting refs before deletion, and a longer-term solution involving improved transaction handling for batched updates. However, brian m. carlson has now identified a flaw in the filtering approach—it incorrectly assumes conflicting refs appear adjacently in the list, when in reality they can be interleaved due to bytewise sorting. Brian suggests reftable as a more robust alternative for case-insensitive systems, as it inherently handles case preservation without filesystem limitations.

The conversation continues to weigh immediate workarounds against deeper architectural changes, with performance implications for different ref backends remaining a key factor. While the short-term filtering solution now appears unworkable, the broader context ties into ongoing efforts around batched reference updates in git-fetch. Testing methods for case-insensitive environments, previously shared by brian m. carlson, remain relevant for validating any proposed fixes.
