Bug report and proposed fix for `git pull --prune` failure on case-insensitive filesystems when pruning case-conflicting references. Originated by ryenus, the issue occurs in refs.c (lines 2863-2895) where batch reference deletions fail entirely if any case-conflicting refs (e.g. `origin/TOM/b2` vs `origin/tom/b2`) are present on case-insensitive filesystems (macOS/Windows default). 

The initial solution proposed modifying `refs_delete_refs()` to handle each reference deletion in a separate transaction, but Karthik Nayak has raised performance concerns about this approach, particularly for the reftable backend. Karthik suggests two paths forward: a short-term fix that filters out case-conflicting refs before deletion (shown in a diff), and a longer-term solution involving proper conflict resolution in reference transactions that would maintain batching while handling case conflicts. This aligns with ongoing work on batched updates in git-fetch (`kn/fetch-push-bulk-ref-update` series).

Technical context includes: filesystem behavior where differently-cased refs map to same underlying file, current transaction model limitations, and the performance tradeoffs between correctness and throughput. brian m. carlson previously provided testing methods for case-insensitive environments (JFS on Linux via loopback, APFS/HFS disk images on macOS via `hdiutil`), which Jayatheerth K acknowledged. 

Current status: the discussion has shifted from the original individual-transaction approach to considering both immediate workarounds and architectural solutions tied to broader ref transaction improvements. Key open questions are whether to prioritize the short-term filter solution or wait for more comprehensive transaction handling, and how to validate either approach in case-insensitive environments. Performance impact on the reftable backend is now a central consideration.
