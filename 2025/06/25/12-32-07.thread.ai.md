Bug report and proposed fix for `git pull --prune` failure on case-insensitive filesystems when pruning case-conflicting references. Originated by ryenus, the issue occurs in refs.c (lines 2863-2895) where batch reference deletions fail entirely if any case-conflicting refs (e.g. `origin/TOM/b2` vs `origin/tom/b2`) are present on case-insensitive filesystems (macOS/Windows default). 

Technical approaches have evolved through review:
1. Initial individual transaction approach rejected due to performance concerns (Karthik Nayak on reftable impact)
2. Karthik's adjacent-case filtering invalidated by brian m. carlson showing non-contiguous conflicts
3. Jayatheerth K now proposes strmap-based solution tracking lowercase ref names for conflict detection while preserving original casing
   - Uses `str_tolower()` normalization
   - Issues warnings for skipped refs rather than failing entire operation
   - Maintains batch transaction model
4. brian m. carlson advocates reftable backend as robust solution for case-insensitive systems
5. Junio C Hamano lightheartedly endorses reftable adoption ("the more adopters we have, the merrier")
6. Patrick Steinhardt now strongly advocates making reftable the default backend, citing technical advantages (case-sensitivity handling, compression, efficiency) and reporting successful large-scale GitLab testing. Identifies ecosystem compatibility (incomplete libgit2/Gitoxide support) and filesystem-dependent scripts as adoption blockers, suggesting experimental flag enablement as interim step toward Git 3.0 default.

Technical context remains:
- Filesystem behavior mapping differently-cased refs to same file
- Transaction model limitations
- Performance tradeoffs between correctness (strmap/reftable) and throughput (batch operations)
- Testing methods for case-insensitive environments (JFS/APFS/HFS) established by brian m. carlson
- Reftable implementation status across ecosystem (JGit complete, libgit2/Gitoxide partial)
