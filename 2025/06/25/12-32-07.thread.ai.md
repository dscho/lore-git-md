Bug report and proposed fix for `git pull --prune` failure on case-insensitive filesystems when pruning case-conflicting references. Originated by ryenus, the issue occurs in refs.c (lines 2863-2895) where batch reference deletions fail entirely if any case-conflicting refs (e.g. `origin/TOM/b2` vs `origin/tom/b2`) are present on case-insensitive filesystems (macOS/Windows default). 

The proposed solution modifies `refs_delete_refs()` to handle each reference deletion in a separate transaction rather than batching, preventing single failures from aborting all pruning. Key changes would: process deletions individually, count failures while allowing successes, and report overall status. The author provides detailed code analysis but cannot test directly (lacking case-insensitive environment), raising open questions about testability. The technical approach appears sound but needs validation from someone with appropriate test setup. Core issue remains the filesystem interaction where differently-cased refs map to same underlying file, with current transaction model not accounting for this edge case.
