Bug report and proposed fixes for `git pull --prune` failure on case-insensitive filesystems when pruning case-conflicting references. Originated by ryenus, the issue occurs in refs.c where batch reference deletions fail on case conflicts (e.g. `origin/TOM/b2` vs `origin/tom/b2`) on macOS/Windows filesystems. Technical approaches have evolved through review:

1. Initial individual transaction approach rejected due to performance concerns (Karthik Nayak)
2. Karthik's adjacent-case filtering invalidated by brian m. carlson showing non-contiguous conflicts
3. Jayatheerth K's strmap solution tracks lowercase ref names for conflict detection while preserving original casing
   - Uses `str_tolower()` normalization
   - Issues warnings for skipped refs
   - Maintains batch transaction model
4. Chris Torek expands scope to include Unicode normalization collisions on HFS+/APFS (decomposed vs precomposed characters)
5. brian m. carlson advocates reftable backend as robust solution
6. Patrick Steinhardt strongly advocates making reftable default, citing technical advantages and GitLab testing success
7. Junio C Hamano endorses reftable adoption path via `features.experimental` flag, identifies documentation needs

Technical context:
- Filesystem behaviors (case folding + Unicode normalization)
- Transaction model limitations
- Performance tradeoffs between strmap/reftable solutions
- Testing methods for case-insensitive environments established
