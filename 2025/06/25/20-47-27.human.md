This is a technical explanation from Junio C Hamano about Git's revision range mechanics in response to a user question about filtering tagged commits.

Junio clarifies that `git log`'s revision ranges work through reachability calculations between positive and negative commit sets, not through direct filtering of displayed commits. He explains why the user's attempt with `--exclude=ref/tags/v*` doesn't work - this flag only affects reference selection when using glob patterns, not the actual commit display. The core limitation is that Git's revision selection fundamentally operates on commit graphs through reachability, making it impossible to arbitrarily exclude intermediate commits (like tags) without also excluding their descendants.

The response suggests the user's grep-based workaround is actually the closest possible solution given Git's current capabilities, though it comes with formatting tradeoffs. This appears to be a fundamental constraint of Git's design rather than a missing feature that could be easily added. The explanation is thorough and authoritative, making clear that what the user wants to do isn't possible with Git's current revision selection model.
