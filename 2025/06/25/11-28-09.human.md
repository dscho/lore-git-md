Performance regression report in `git for-each-ref` with large tag sets. Andrzej Dębski from Dropbox reports a significant slowdown in `git for-each-ref --format="%(refname)" refs/tags --merged HEAD` operations when processing repositories with ~65K tags, comparing Git 2.39.5 (fast) to 2.40.0+ (slow). The performance degradation appears linked to the `tips_reachable_from_bases` function introduced in commit cbfe360b14.

The issue manifests in Dropbox's large monorepo environment where tag counts grow daily. Benchmarking shows execution time decreases proportionally when tags are removed, suggesting the new algorithm doesn't scale well with large tag collections. The report questions whether this qualifies as a regression worth fixing, given the command was previously faster.

The email provides clear reproduction details and version comparisons, making it a well-documented performance issue. The impact appears substantial for organizations managing repositories with tens of thousands of tags, though the report doesn't quantify the slowdown percentage. This seems likely to prompt discussion about optimization strategies for the ref-filtering code paths.
