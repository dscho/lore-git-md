This is a technical explanation from Junio C Hamano about Git revision range semantics in response to a user question about excluding tagged commits from `git log` output.

The email clarifies that `--exclude` operates on reference selection (affecting which refs are included in the positive set for reachability calculations) rather than being a post-processing filter for displayed commits. It explains why the user's attempt with `--exclude=ref/tags/v*` didn't work as intended - since they weren't using `--all` or `--glob`, the exclude had no effect on their specific v2.3.0..v2.4.0 range query.

The response provides a detailed explanation of how revision ranges work in Git's underlying model: as a set operation between positive and negative commit sets based on reachability. This makes it fundamentally impossible to arbitrarily exclude intermediate commits (like tags) from the displayed history while maintaining proper reachability relationships. The user's grep-based workaround is acknowledged but framed as working around the fundamental limitations of the intended use of revision ranges.

Key technical details include: the distinction between reference selection (`--all`, `--glob`) and revision range specification, the set-theoretic model of positive/negative commit sets and reachability, and why intermediate commit exclusion would break the model. The response suggests this isn't a missing feature but rather a conceptual limitation of how Git models history traversal.
