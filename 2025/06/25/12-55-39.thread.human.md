This thread covers a performance optimization series for Git's pathspec bloom filters, addressing Kai Koponen's report that combined pathspec queries were slower than separate invocations. The core innovation is a new `struct bloom_keyvec` abstraction that manages multiple bloom keys, replacing direct `struct bloom_key *` usage in `rev_info`.

The series has gone through five iterations, with v5 introducing several key improvements: better API boundaries between test and production code, consistent naming conventions, and comprehensive documentation. The implementation now properly handles multiple literal pathspecs while maintaining the fast path for single pathspec cases. Performance measurements show dramatic improvements - from 2.36s down to 0.24s for multi-pathspec queries in the LLVM repository.

The final patch completes the series by modifying `forbid_bloom_filters()` to allow bloom filter usage with multiple literal pathspecs, while still excluding wildcard pathspecs. The test suite has been expanded to verify correct behavior with various pathspec combinations. Reviewers including Junio Hamano, Patrick Steinhardt, and Derrick Stolee have provided extensive feedback throughout the series, with all substantive technical concerns now addressed.

While the core functionality is stable, some future work remains open: handling PATHSPEC_ICASE with `core.ignorecase`, optimizing `nowildcard_len`, and potential case-sensitivity improvements. The series represents a significant performance win for a common revision traversal case while maintaining all existing constraints and behaviors.
