This thread focuses on optimizing Git's pathspec bloom filters to handle multiple literal pathspecs more efficiently. The work was prompted by Kai Koponen's report that combined pathspec queries were slower than separate invocations. The series introduces a new `struct bloom_keyvec` abstraction that manages multiple bloom keys, replacing direct `struct bloom_key *` usage in `rev_info`.

The latest patch finalizes the optimization by modifying `forbid_bloom_filters()` to allow bloom filter usage when all pathspec items are literal, regardless of count, while still rejecting wildcards. Performance improvements are substantial - showing 1.33x speedup in Git's own repository and 7.5x in the LLVM repository. The implementation includes comprehensive test coverage for multiple pathspec cases and maintains backward compatibility.

Key contributors include Derrick Stolee, who provided important refactoring suggestions and benchmark formatting, and Lidong Yan who reviewed the changes. The series has addressed all technical concerns raised during review, with the final discussions now focused on commit message refinements. The changes touch bloom.c/h, revision.c/h, blame.c, and line-log.c, with test updates in t4216-log-bloom.sh.

Open questions remain about potential case sensitivity optimizations and handling of PATHSPEC_ICASE, but these are deferred to future work. The current series is considered ready for merging, having significantly improved performance for multiple literal pathspec queries while maintaining the existing behavior for wildcard pathspecs.
