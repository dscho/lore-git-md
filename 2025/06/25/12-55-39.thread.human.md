This thread focuses on optimizing Git's pathspec bloom filters, particularly for handling multiple pathspec queries more efficiently. The core of the work is a new `struct bloom_keyvec` abstraction that manages multiple bloom keys, replacing direct pointer usage in `rev_info`. The series has undergone several iterations (now at v4) with input from Junio Hamano and Patrick Steinhardt, addressing API naming, type usage, and test/production boundary concerns.

Lidong Yan, the series author, recently responded to Junio's question about case sensitivity in bloom filters. Through code analysis and timing tests on the llvm-project repository, Yan confirmed the current implementation is strictly case-sensitive, regardless of `core.ignorecase` settings. Measurements show significant performance differences: exact-case queries run in 0.089s while mixed-case take 0.458s, demonstrating the optimization only helps exact matches. This leaves potential for future work to consider case-insensitive filesystems when building filters.

The series is stable for its primary goal of optimizing multiple literal pathspecs while maintaining the fast path for single pathspecs. Open questions about case sensitivity and wildcard optimizations have been intentionally deferred, as noted in earlier discussions. The changes touch bloom.c/h, revision.c/h, and related files, with comprehensive test updates. Junio and Steinhardt have reviewed the core functionality, and Yan has addressed all substantive technical feedback in the current iteration.
