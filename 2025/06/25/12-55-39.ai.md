This is a performance optimization patch series targeting Git's bloom filter implementation for pathspec matching. The series addresses a known limitation where bloom filters are only used for single pathspecs, causing significant slowdowns when multiple pathspecs are provided (like `git log -- file1 file2` versus separate invocations for each file).

The first patch introduces a new `bloom_keyvec` struct to hold multiple bloom keys, replacing the single `bloom_key` pointer. This is a preparatory refactoring that enables the main change. The second patch implements the core optimization by checking each pathspec's bloom keyvec against commit filters, along with necessary initialization and cleanup code.

The motivation comes from a real-world performance issue reported by Kai Koponen, where combined pathspec queries were much slower than separate ones. Benchmark results show the optimized version now matches the performance of separate invocations. The changes touch bloom filter internals across multiple files (bloom.c/h, revision.c/h) and include test updates.

Key technical details:
- New `struct bloom_keyvec` to manage multiple pathspec keys
- Modified bloom filter checking logic in `revision.c` to handle keyvecs
- Preserved existing single-pathspec optimization path
- Test updates in t4216-log-bloom.sh to verify behavior

The implementation appears thorough, with clear commit messages explaining both the problem and solution. The performance claims are backed by specific test cases, though the exact speedup numbers aren't quantified beyond "as fast as" separate invocations. This seems like a well-motivated optimization for a known pain point in a performance-critical code path.
