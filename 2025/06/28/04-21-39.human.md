Performance optimization patch introducing infrastructure for multiple pathspec bloom filters. This is the first of two patches in a series addressing the limitation where Git's bloom filters only accelerated single pathspec queries (like `git log -- file1`). The patch comes from Kai Koponen's observation that combined pathspecs were slower than separate invocations.

The patch introduces `struct bloom_keyvec` to manage multiple bloom keys, replacing the direct `struct bloom_key *` usage in `rev_info`. It adds new functions for keyvec creation/destruction (`create_bloom_keyvec`, `destroy_bloom_keyvec`) and checking (`bloom_filter_contains_vec`). The changes convert all bloom key handling to use the new vector structure while maintaining the existing single-pathspec fast path.

The implementation touches bloom.c/h and revision.c/h, with careful attention to memory management and API design. This version (v3) incorporates Junio Hamano's feedback from earlier reviews, including using FLEX_ARRAY for keys and tightening variable scoping. The patch appears well-structured and focused, with clear commit message explaining the motivation and changes.

While this patch only enables the single-pathspec case (with bloom_keyvec_nr limited to 0 or 1), it lays the groundwork for the follow-up patch that will actually enable multiple pathspec optimization. The changes are primarily internal plumbing with no user-visible behavior changes yet.
