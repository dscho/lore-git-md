Performance optimization patch for `git fetch --prune` with large ref counts.

This is the first of two patches in a series addressing the O(N^2) performance of `git fetch --prune` when dealing with repositories containing many refs. The current implementation performs inefficient nested loop checking of each pruned ref against all local refs, resulting in billions of strcmp calls and minutes of runtime for large repos (410 seconds for 28k pruned refs in a 126k ref repo).

The patch restructures the dangling ref detection to use the same O(N*logN) approach already employed by `git remote prune`, where the prune list is sorted for binary search. The key changes are:
- Collecting all refs to prune in a string_list upfront
- Moving the dangling ref warning to after all prune operations
- Using refs_warn_dangling_symrefs() instead of per-ref checks

This provides dramatic speedup (410s -> 4s in the test case) but changes output ordering - dangling ref warnings now appear grouped at the end rather than interleaved with deletion messages. The patch preserves all functionality while significantly reducing CPU usage.

The implementation touches builtin/fetch.c, modifying the prune_refs() function to use the more efficient approach. The author considered but deferred further optimization to O(N) complexity due to uncertainty about ref_store iterator sorting guarantees. The current solution already meets their immediate needs while being a clear improvement over the original.

This change sets up for the second patch which will remove now-unused dangling ref warning code from refs.c. The main open question remains whether the output ordering change is acceptable given the performance benefits.
