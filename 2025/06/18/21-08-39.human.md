Performance optimization for `git fetch --prune` with large ref counts. This is the first of two patches addressing O(N^2) behavior in dangling ref detection during pruning.

The patch restructures `builtin/fetch.c` to use the same O(N*logN) approach as `git remote prune`, where the prune list is sorted for binary search rather than checking each ref individually. The author reports dramatic improvements - from 410 seconds (with 3.6B strcmp calls) down to 4 seconds when pruning 28k refs from a repo with 126k refs.

The tradeoff is that dangling ref warnings now appear grouped at the end rather than interleaved with deletion messages. The patch appears well-constructed with a clear commit message explaining both the technical change and performance impact. The author notes they considered but didn't pursue an O(N) optimization due to uncertainty about ref_store iterator sorting guarantees.

This is part of an RFC series seeking feedback on whether the output ordering change is acceptable given the significant performance gains. The patch preserves all functionality while changing only the message ordering, and builds on existing efficient patterns from `git remote prune`.
