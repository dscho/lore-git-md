This RFC thread explores optimizing `git fetch --prune` performance for repositories with many refs, where the current O(N^2) implementation can take minutes to complete. Phil Hord's two-patch series restructures the pruning logic to use an O(N*logN) approach similar to `git remote prune`, dramatically reducing runtime (from 410s to 4s in test cases).

The technical solution involves collecting refs upfront in a sorted string list and moving dangling ref warnings after pruning operations. While this changes the output ordering slightly, reviewers agree the performance benefits justify it. Jacob Keller has given a Reviewed-by for the first patch, and Junio C Hamano reacted positively to the cleanup patch. Jeff King (peff) has now weighed in with additional context, confirming the approach is sound and noting that while an O(N) optimization might be possible using ref_store iterators, the current solution is sufficient given other bottlenecks.

The thread shows consensus forming around accepting the patches despite minor output ordering changes, with peff's latest email reinforcing the design decisions by explaining the approach aligns with existing interfaces like refs_warn_dangling_symrefs(). The series appears ready for merging, with the understanding that further optimizations could be explored later if needed.
