This thread discusses an RFC patch series from Phil Hord optimizing `git fetch --prune` performance for repositories with many refs. The current implementation has an O(N^2) bottleneck when pruning refs, taking 410 seconds for 28k refs due to inefficient string comparisons. The proposed solution restructures the code to use an O(N*logN) approach matching `git remote prune`, dramatically improving performance to just 4 seconds in the same test case.

The series consists of two patches: one implementing the new approach (with warnings grouped at end rather than interleaved), and a second removing now-unused helper functions. Junio C Hamano responded positively to the cleanup patch with a "Nice." comment, though this isn't a formal Ack. The main open question has been whether the change in warning output ordering (from interleaved to grouped) would cause problems for tooling.

Jacob Keller recently weighed in, strongly supporting the new grouped output format as more readable for humans and questioning whether the old interleaved ordering was actually needed for scripting. This moves the discussion forward by providing developer support for accepting the output change as part of the optimization. The core technical solution remains sound, and the thread now appears to be converging toward accepting the series with its current behavior.
