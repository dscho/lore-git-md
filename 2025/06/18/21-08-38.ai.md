Performance optimization for `git fetch --prune` with large ref counts. This RFC patch series addresses a severe O(N^2) performance problem in `git fetch --prune` when operating on repositories with many refs. The current implementation makes 2.6 billion strcmp calls when pruning 15,000 refs from a 174,000-ref repository, taking 470 seconds, while the proposed change reduces this to under 1 second.

The core issue is in the dangling ref detection logic, which currently uses a nested loop comparing each prune candidate against all refs. The patch restructures this to match the more efficient O(N*logN) approach used by `git remote prune`, where the prune list is first sorted for binary search. The tradeoff is that dangling ref warnings will now appear grouped at the end of output rather than interleaved with deletion messages.

The series consists of two patches: the first optimizes the fetch implementation, while the second removes now-unused dangling ref warning code from refs.c. The author notes the output ordering change could potentially be preserved with more complex code, and solicits feedback on whether this is worth the additional complexity. The performance improvement is dramatic enough that this seems likely to be accepted despite the output format change, unless there are strong objections about the reordered messages breaking existing tooling.
