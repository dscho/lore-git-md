Haylin Moore has identified a performance bottleneck in Git's reftable implementation during network operations like cloning. The issue stems from the reftable_writer using small 4KB block sizes by default, resulting in many serial write operations that each take about 3ms - significantly slowing down operations over network mounts. 

The investigation points to DEFAULT_BLOCK_SIZE (4096) as the culprit, though it's unclear from the code where this value is actually set. While reftable.adoc documentation mentions block size in a way that suggests configurability, there doesn't appear to be an actual mechanism to adjust this setting. The email raises important questions of whether this should be configurable and if the current behavior is intentional, but stops short of proposing specific changes. This appears to be the beginning of a performance investigation that could lead to either documentation improvements or code changes to optimize network operations.
