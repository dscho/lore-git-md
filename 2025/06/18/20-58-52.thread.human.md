This thread explores performance considerations around Git's reftable storage format, particularly the block size configuration. Haylin Moore initially reported slow network operations with the default 4KB block size, prompting Brian M. Carlson to clarify that `reftable.blockSize` is configurable and that JGit defaults to 64KB for write-heavy workloads, highlighting the tradeoffs between write performance and read efficiency.

Patrick Steinhardt has now weighed in, providing additional context about the 4KB default (filesystem alignment) and Google's preference for 64KB blocks in their Spanner backend. While confirming the configurability of the setting, he questions whether reftable writes are actually the bottleneck in network clones, since reftables require explicit opt-in and may not significantly impact clone speeds. This introduces a productive skepticism about the original performance diagnosis, potentially redirecting future investigation toward other factors affecting clone performance. The discussion remains technical and focused, now covering both storage system interactions and the need to verify assumptions about where performance bottlenecks actually lie.
