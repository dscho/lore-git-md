This is a performance-related inquiry about Git's reftable backend behavior. Haylin Moore reports observing that Git performs small 4KB writes during clones over network mounts, causing significant slowdowns despite each individual write being fast. They've traced this to the `DEFAULT_BLOCK_SIZE` in reftable_writer, which appears hardcoded to 4096 bytes in the current implementation.

The email questions whether this block size is configurable, noting that while the reftable documentation mentions block sizes in a way that suggests configurability, it's unclear whether this is just for internal development purposes. There's no patch attached - this is purely an informational query seeking clarification about potential performance tuning knobs for network-mounted repository operations.

The issue appears legitimate and well-observed, though the solution space isn't yet clear - it could involve exposing the block size as a configuration option, implementing adaptive buffering, or perhaps there's already an undocumented way to control this behavior. The question seems likely to interest both reftable maintainers and users dealing with network filesystem performance.
