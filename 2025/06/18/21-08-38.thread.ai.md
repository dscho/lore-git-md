Thread identity: RFC patch series from Phil Hord addressing performance optimization for `git fetch --prune` with large ref counts.

Core problem: Current `git fetch --prune` implementation has O(N^2) performance when pruning refs from repositories with many refs (e.g. 410 seconds for 28k pruned refs in a 126k ref repo due to billions of strcmp calls). The issue stems from inefficient dangling ref detection using nested loops.

Solution: Two-patch series restructuring to use O(N*logN) approach matching `git remote prune`:
1. First patch modifies builtin/fetch.c's prune_refs() to:
   - Collect all refs to prune in string_list upfront
   - Move dangling ref warnings to after all prune operations
   - Use refs_warn_dangling_symrefs() instead of per-ref checks
2. Second patch removes now-unused:
   - refs_warn_dangling_symref() helper function
   - refname field from warn_if_dangling_data struct
