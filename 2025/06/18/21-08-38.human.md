Performance optimization for `git fetch --prune`'s O(N^2) behavior. This RFC patch series addresses a severe performance bottleneck where pruning many refs (e.g. 15,000 out of 174,000) could take 470 seconds due to inefficient dangling ref checking. The current implementation uses nested loops with O(N^2) strcmp operations, while the proposed change adopts the more efficient O(N) approach used by `git remote prune`.

The main tradeoff is that the output order changes - dangling ref notices will appear after all deletion messages rather than interleaved. The author questions whether preserving the original output order (which would require more complex code) is worth it, given that `git remote prune` already uses a similar output format.

The changes touch `builtin/fetch.c` and `refs.c`, removing some now-unused dangling ref warning code. The performance improvement is dramatic - the example case drops from 470 seconds to under 1 second. This looks like a well-motivated optimization that addresses a real-world scaling problem, though the output format change may need discussion.
