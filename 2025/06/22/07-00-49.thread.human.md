The thread began with a report from kryzet about seeing "badFilemode" and "missingTaggerEntry" warnings when cloning git.git from GitHub, despite the clone completing successfully. The warnings referenced numerous object hashes, raising questions about potential repository corruption.

Jeff King (Peff) responded authoritatively, explaining these are harmless historical artifacts from Git's early development rather than signs of actual problems. The warnings appear when fsck checks are enabled during transfer and stem from practices that were later standardized: some early tags lack tagger fields, and old tree objects use non-standard file modes (100664 instead of 100644). These objects persist in clones due to Git's immutable object model.

Peff noted an inconsistency in fsck behavior - the tag warning appears by default while file mode warnings require --strict mode, yet fetch/push always use strict checking. He suggested this severity classification might need review but didn't propose immediate changes. The response effectively resolves the original report by confirming the warnings are benign while providing configuration options to suppress them and identifying a potential area for future fsck behavior improvement.
