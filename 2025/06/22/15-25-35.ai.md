This is the third and final patch in Maxim Cournoyer's v2 series implementing helper-side resolution of symbolic port names in git-credential-netrc, despite the credential protocol documentation specifying numeric ports only. The patch completes the implementation by:

1. Adding a new `Git::is_port()` helper function that validates both numeric ports and symbolic service names (using `getservbyname`), returning the latter's numeric equivalent
2. Modifying git-credential-netrc to use this function, properly handling symbolic ports rather than misclassifying them as protocols
3. Adding port validation to git-send-email that similarly accepts both numeric and symbolic ports
4. Updating tests to reflect the new behavior, including a new test case for invalid ports

The implementation maintains backward compatibility while adding support for symbolic ports like "smtps" that were previously rejected. The changes affect multiple components:
- The credential helper now properly processes ports from netrc files
- git-send-email validates SMTP ports using the same logic
- Perl's Git.pm gains the new port validation utility function
- Test cases verify both valid and invalid port handling

This patch represents the most substantial change in the series, implementing the core functionality after the preparatory warning additions in patch 2. The technical approach is sound, with proper error handling and test coverage. However, it directly contradicts Brian Carlson's interpretation of the credential protocol documentation, which specifies "port number" (implying numeric-only). The patch does not address this protocol documentation issue, leaving that question unresolved.

The implementation quality appears high, with:
- Clear separation of concerns in the new `is_port` utility function
- Consistent behavior between credential helper and send-email
- Appropriate test coverage including negative cases
- Maintained backward compatibility

This completes the technical implementation of helper-side port resolution, though the design debate about whether symbolic ports should be supported at all (per protocol docs) remains open for maintainer decision.
