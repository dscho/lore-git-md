Bugfix thread about interactive rebase in secondary worktrees. Denilson Sá Maia provides more detailed reproduction steps for the intermittent "local changes would be overwritten" error during `git rebase -i` in secondary worktrees. The issue occurs when rebasing a secondary branch against main/upstream with unrelated changes, specifically listing files from the target branch as supposedly modified in the worktree. 

Key technical details: The problem requires interactive rebase (`-i` flag) and manifests when the secondary branch has changes to file `foo` while main has unrelated changes. The error incorrectly claims worktree changes exist for files modified in main. Denilson confirms the worktrees are on the same local filesystem with no cloud sync, and demonstrates the issue persists after stripping most config options except core.repositoryformatversion. 

The reproduction steps suggest the bug relates to how interactive rebase handles the checkout of target branch state in secondary worktrees, where it misidentifies incoming changes from the base branch as local modifications. This builds on Phillip Wood's earlier investigation into potential causes around line endings, filters, or index refresh timing. The consistent reproducibility in this large repository contrasts with earlier uncertainty about intermittent behavior, potentially helping diagnosis. No workarounds or fixes are yet proposed - the email primarily serves to narrow the triggering conditions.
