This is a bug report about Git failing with "Permission denied" errors on Windows DFS network shares in versions 2.36+ while working fine in 2.21 and older. The reporter, Erwan Leroy, provides a detailed investigation showing the issue only occurs when accessing paths through DFS (not direct UNC paths) and affects users regardless of their actual permissions, suggesting a regression in Git's handling of DFS paths.

The error occurs during basic operations like `git remote add` when Git tries to rename lock files. The key observations are: 1) it's version-dependent (broken in 2.36+), 2) DFS-specific, and 3) affects new installations regardless of user permissions. The reporter has done solid troubleshooting to isolate these factors but lacks build environment to bisect further.

This appears to be a legitimate platform compatibility issue affecting Windows users on DFS shares. The clear version cutoff and DFS-specific behavior make it likely a regression from changes in Git's filesystem handling. The report is well-structured with error output and systematic elimination of variables, though it would benefit from exact SHA-1 hashes of the failing/succeeding versions if bisection becomes possible.
