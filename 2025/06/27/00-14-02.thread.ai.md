Windows DFS-mounted network drive regression report from Erwan Leroy, with ongoing investigation by Git for Windows maintainer Johannes Schindelin (Dscho). Core issue: Git versions 2.36+ fail with "Permission denied" when writing config files on DFS paths (working on direct UNC paths and in Git <=2.21), specifically during lock file operations renaming `.git/config.lock` to `.git/config`. Regression window spans 2.21 through at least 2.50.

Technical details expanded: Erwan Leroy clarified their three-tiered storage architecture showing DFS namespace (`\\xxx.local\Basecamp`) resolving to working direct Samba shares (`\\atl-xx\Basecamp`), with drive-letter mappings (Y:) inheriting DFS failures. This confirms drive-letter issues stem from underlying DFS path problems while direct UNC and local paths work correctly.

Current resources: Schindelin provided pre-compiled Git for Windows versions (gitforwindows.org/git-snapshots/) for bisection. Open questions remain about why `rename()` operations fail specifically on DFS paths despite working on direct UNC paths with similar semantics. Primary reference remains Git for Windows issue #3825 (originally linked by brian m. carlson).

Key observations:
- Failure occurs during config file lock/rename operations
- Affects DFS paths and their drive-letter mappings
- Direct UNC paths and local drives unaffected
- Version-specific: working <=2.21, broken >=2.36
