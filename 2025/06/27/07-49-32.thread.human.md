This thread explores a proposal to introduce a new `git refs list` subcommand as part of a broader effort to consolidate ref-related commands. The initial RFC patch series from GSoC participant Meet Soni, with mentoring from experienced contributors, implemented the command by reusing `for-each-ref`'s ref-filter logic while adding features like `--include-root-refs` for HEAD/pseudoref handling. Maintainer Junio Hamano questioned the need for a new command, suggesting a wrapper approach (like `git branch`/`tag`) could achieve the same discoverability benefits without code duplication.

The discussion has now clarified that the command should indeed be a thin wrapper around `for-each-ref`, as Shejialuo confirmed agreement with Junio's position. This reinforces the maintainer's technical direction from earlier in the thread. While the original implementation introduced parallel code paths, the consensus now favors redesigning it as a wrapper to avoid duplication while still improving discoverability through the `git refs` hierarchy.

Parallel to this debate, Jean-Noël Avila has been making uncontroversial documentation improvements to standardize option syntax and man page style across both commands. These documentation changes are progressing independently of the command interface discussion.

The key open question remains whether the discoverability benefits justify introducing any new command at all, versus simply better documenting existing `for-each-ref` usage patterns. With the wrapper approach now clearly favored, the next steps likely involve Meet Soni's implementation being revised accordingly or the proposal being adjusted to focus solely on documentation improvements.
