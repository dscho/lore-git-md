This thread began as an RFC proposing a new `git refs list` subcommand to consolidate ref-related functionality, authored by GSoC participant Meet Soni with mentoring from experienced contributors. The initial implementation reused ref-filter logic from `git for-each-ref` while adding discoverability through a `git refs` hierarchy. Maintainer Junio C Hamano questioned the need for a new command, advocating instead for a wrapper approach (like git branch/tag) to avoid code duplication and potential behavioral divergence, citing the checkout/switch/restore split as a cautionary example. Shejialuo later supported this wrapper direction.

In parallel, Jean-Noël Avila has been improving documentation for both commands, with Junio providing detailed feedback on man page consistency that Jean-Noël is addressing in a v2.

The discussion took a technical turn when Patrick Steinhardt identified a significant issue with the default output format's performance in large repositories like Chromium, where object type resolution creates a 6.65x slowdown. While agreeing with the wrapper approach in principle, Steinhardt argues this specific default behavior warrants reconsideration for the new command, providing concrete benchmarks showing ~150ms vs ~22ms difference. This introduces a new dimension to the thread - whether performance optimizations can justify controlled divergence in default behaviors while maintaining shared infrastructure. The maintainer's position on strict behavioral parity now faces a data-backed challenge regarding real-world impact on large repositories.
