Bugfix investigation for interactive rebase in secondary worktrees. Phillip Wood responds to Denilson Sá Maia's report about `git rebase -i` incorrectly detecting dirty state in secondary worktrees while non-interactive rebase works fine. The thread has established this is a real issue affecting Git 2.49.0 on Darwin/arm64, where interactive rebase fails with false "local changes would be overwritten" errors only in secondary worktrees created via `git worktree add`.

Wood explores two potential technical causes: line ending/filter attributes affecting the files listed in the error, or a missing index refresh before checkout in the interactive rebase codepath. He notes the index is refreshed when `--autostash` is used but isn't certain about the default case. The response seeks additional details about the worktree setup - whether it's on the same filesystem as the main repository and if any cloud sync services are involved - to help diagnose the intermittent nature of the issue.

The problem appears to be specific to interactive rebase's handling of temporary checkouts in secondary worktrees, with the core worktree state detection logic incorrectly reporting files as modified when they haven't changed. The investigation continues to pinpoint whether this stems from attribute handling, index refresh timing, or another aspect of the rebase machinery's worktree state tracking.
