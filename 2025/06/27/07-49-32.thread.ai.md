RFC patch series proposing `git refs list` subcommand as first step in ref command consolidation effort, with parallel documentation improvements. Authored by GSoC participant Meet Soni with mentoring from experienced contributors. Initial version (205 lines added) establishes new `builtin/refs.c` infrastructure reusing ref-filter logic from `git for-each-ref` with all existing features: pattern matching, sorting, formatting, and filters (`--points-at`, `--merged`, `--contains`), plus `--include-root-refs` flag for HEAD/pseudoref handling. Test infrastructure runs existing `for-each-ref` suite against new command via `GIT_REFS_LIST_CMD=refs list`.

Maintainer Junio C Hamano questions justification for new command, suggesting wrapper implementation (like `git branch`/`tag`) could achieve discoverability without code duplication. Author Meet Soni clarifies primary motivation is improved discoverability through `git refs` hierarchy. Hamano expresses skepticism about adding new commands that could diverge from existing functionality, citing Git's history of avoiding multiple ways to do similar things and referencing `git checkout` split into `git switch`/`git restore` as precedent where consolidation wasn't the right direction. While acknowledging `git refs list` might not be harmful with strict feature parity, warns against introducing subtle behavioral differences that could confuse users. Maintainer position solidifies around wrapper approach preserving existing behavior while improving organization.

Documentation improvements (Jean-Noël Avila) proceed in parallel, with initial minimal docs expanded via follow-up patches standardizing option syntax in both commands. Hamano reviews `git-for-each-ref` man page improvements focusing on consistency (option syntax standardization, `_<placeholder>_` convention, tighter descriptions), identifying remaining style issues (synopsis section header format, unitalicized placeholders, literal option references). Jean-Noël Avila agrees to produce v2 addressing all style issues, making this documentation track uncontroversial and progressing independently of technical design debate.

Open questions remain on whether consolidation under `git refs` justifies new command given maintainer's strong position favoring wrapper pattern. Technical foundation via ref-filter reuse is sound, but community needs to evaluate discoverability benefits against maintenance concerns and potential for subtle behavioral divergence. Documentation standardization continues as separate work while wrapper approach emerges as likely resolution path for command interface debate.
