RFC patch series proposing `git refs list` subcommand as first step in ref command consolidation effort. Authored by GSoC participant with mentoring from experienced contributors, this initial version exactly mirrors `git for-each-ref` functionality while establishing new `builtin/refs.c` infrastructure (205 lines added across two files). Implementation reuses `for-each-ref` ref-filter logic, supporting all existing features: pattern matching, sorting, formatting, and filters (`--points-at`, `--merged`, `--contains`). Introduces `--include-root-refs` flag for explicit HEAD/pseudoref handling.

Test infrastructure added in second patch creates `t/t1461-refs-list.sh` that runs existing `for-each-ref` test suite against new command via `GIT_REFS_LIST_CMD=refs list` parameterization. Documentation review from Jean-Noël Avila provides detailed feedback on man page formatting, with improvements to option descriptions and standardizing imperative mood phrasing. Maintainer Junio C Hamano responds to Avila's formatting suggestions, noting the documentation appears minimally modified from `git-for-each-ref.adoc` and suggesting direct patches to that source file for spacing around pipe characters in option alternatives. Files involved: `Documentation/git-refs.adoc` and `Documentation/git-for-each-ref.adoc`.

Maintainer Junio C Hamano questions the justification for creating a new command to replace `git for-each-ref`, challenging two specific rationales from the proposal. Author's response acknowledges this concern about potential feature divergence and backport pressure, conceding it could lead to code duplication rather than simplification. This exchange crystallizes the core tension: while technical implementation successfully replicates functionality through shared ref-filter infrastructure, the strategic justification for a parallel command remains unconvincing to the maintainer.

Open questions now center on whether command consolidation can proceed without feature divergence or if alternative migration strategies (like gradual deprecation of for-each-ref) might address maintainer concerns. The technical foundation remains sound - strict compatibility via ref-filter reuse and comprehensive test coverage - but the proposal's rationale requires stronger community buy-in to progress. Documentation review process continues in parallel, with maintainer steering contributors toward upstream improvements that would benefit both commands. Future discussion likely needs to address project policy and interface design philosophy more than implementation details.
