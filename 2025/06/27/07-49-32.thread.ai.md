RFC patch series proposing `git refs list` subcommand as first step in ref command consolidation effort, with parallel documentation improvements. Authored by GSoC participant Meet Soni with mentoring from experienced contributors. Initial version mirrors `git for-each-ref` functionality (205 lines added) while establishing new `builtin/refs.c` infrastructure, reusing ref-filter logic with all existing features: pattern matching, sorting, formatting, and filters (`--points-at`, `--merged`, `--contains`). Includes `--include-root-refs` flag for HEAD/pseudoref handling. Test infrastructure in second patch runs existing `for-each-ref` suite against new command via `GIT_REFS_LIST_CMD=refs list`.

Maintainer Junio C Hamano questions justification for new command, suggesting wrapper implementation (like `git branch`/`tag` listings) could achieve discoverability without code duplication. Author Meet Soni clarifies primary motivation is improved discoverability through `git refs` hierarchy. Maintainer emphasizes wrapper approach would satisfy discoverability while avoiding maintenance burden. Documentation improvements (Jean-Noël Avila) proceed in parallel, with initial minimal docs now expanded via follow-up patches standardizing option syntax in both commands. Latest documentation patch reviewed by Hamano focuses on `git-for-each-ref` man page, improving consistency (option syntax standardization, `_<placeholder>_` convention, tighter descriptions) while identifying remaining style inconsistencies (synopsis section header format, unitalicized placeholders, literal option references) for future work.

Jean-Noël Avila responds to Hamano's review of the initial documentation patch, agreeing to produce a v2 that completes the standardization work by addressing all remaining style issues in the `git-for-each-ref` man page. This includes fixing synopsis section header format, properly italicizing placeholders, and converting literal option references to standard form. The documentation track progresses independently of the ongoing technical design debate about command interface philosophy.

Open questions remain on whether consolidation under `git refs` justifies a new command given maintainer preference for wrapper pattern. Technical foundation via ref-filter reuse is sound, but community needs to evaluate discoverability benefits against maintenance concerns. Documentation standardization continues as uncontroversial parallel work while wrapper approach emerges as potential compromise preserving existing behavior while improving command organization.
