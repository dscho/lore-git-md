This is a bug report concerning Windows-specific filesystem behavior with DFS-mounted network drives. The reporter, Erwan Leroy, describes a regression where newer Git versions (2.36+) fail with "Permission denied" errors when writing to config files on DFS paths, while older versions (2.21 and below) work fine. The issue appears specifically with DFS resolution - direct UNC path access works even with newer Git versions.

Key technical details:
- The error occurs during operations that create lock files (like `git remote add`)
- The failure manifests when renaming `.git/config.lock` to `.git/config`
- The problem is reproducible across different Windows workstations
- The regression window is between Git 2.21 and 2.36

The report suggests this might relate to changes in Git's filesystem handling for Windows, though the exact cause isn't identified. The reporter is seeking either a known workaround or guidance on which changes in the 2.21-2.36 range might have introduced this behavior. This appears to be a legitimate regression report with clear reproduction steps and version bracketing, though without deeper Windows/DFS expertise it's hard to assess whether the root cause lies in Git or the network configuration. The fact that direct UNC access works suggests the issue may involve how newer Git versions interact with DFS path resolution or locking mechanisms.
