This thread explores how Git's submodule handling breaks when users configure a default remote name other than "origin". Jacob Keller reported the issue, noting his workflow uses "upstream" as the default remote, which exposes hardcoded "origin" assumptions in submodule operations. The discussion has evolved to consider several solutions, including using the superproject's `.gitmodules` URL directly, persisting remote names during initialization, or enforcing "origin" consistency.

Junio Hamano has raised concerns about reliability, particularly how detached HEAD states and remote renaming complicate the problem. The latest development comes from Keller, who hit implementation roadblocks while testing the `.gitmodules` URL approach. He found that supposedly repository-agnostic functions in `remote.c` still hardcode `the_repository`, with some functions slated for removal in Git 3.0. This surfaces new technical questions about how to properly pass repository pointers through the remote handling code.

The core tension remains between respecting user configuration flexibility and ensuring reliable submodule operations. While the problem space is now well-understood, each potential solution path reveals deeper implementation challenges that need resolution before the behavior can be safely changed. The thread shows active collaboration between Keller (providing real-world testing and implementation exploration) and Hamano (emphasizing reliability constraints), with the discussion now focused on concrete code changes needed to support any solution.
