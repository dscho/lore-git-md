This is a bug report and potential feature proposal regarding submodule behavior when `clone.defaultRemoteName` is set to something other than "origin". Jacob Keller encountered an issue where submodule operations fail because `repo_get_default_remote` in `builtin/submodule--helper.c` hardcodes "origin" as the remote name, ignoring the configured default.

The problem manifests when fetching submodule commits, with Git failing because it can't find the expected remote. Keller suggests several potential solutions: checking for a single remote first, respecting `clone.defaultRemoteName`, and falling back to "origin". He also floats the idea of adding a new submodule-specific config option to control this behavior.

The issue touches on Git's submodule implementation and remote handling infrastructure. The hardcoded "origin" assumption appears to be a long-standing behavior that doesn't account for users who configure alternative default remote names. This could be particularly relevant for users who standardize on different remote naming conventions in their workflows.

Keller's proposed solution path suggests a more flexible approach to remote selection, with a clear fallback chain. The mention of detached HEAD state handling indicates this might affect more than just initial submodule setup. The patch would likely need to modify `repo_get_default_remote` and potentially add new config options, affecting both the submodule helper and config parsing code.
