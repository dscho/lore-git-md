This is a discussion about improving submodule remote handling when `clone.defaultRemoteName` differs from "origin". Junio Hamano responds to Jacob Keller's earlier report about submodule operations failing with custom remote names.

The core issue remains the hardcoded "origin" assumption in `repo_get_default_remote()` within `builtin/submodule--helper.c`. Hamano explores several angles: whether the custom remote name is recorded anywhere in the repository (it isn't currently), the unreliability of using the current `clone.defaultRemoteName` value since it can be overridden, and the specific problem occurring in detached HEAD states.

Hamano suggests additional approaches beyond Keller's proposed 3-step solution: (1) tracing where a detached HEAD came from via reflog (as a "step 1.5"), (2) recording the remote name during submodule initialization, or (3) having `git submodule update --init` ignore `clone.defaultRemoteName` entirely to enforce "origin" consistency. The last approach would make the codepath more predictable if submodules are always accessed via the superproject.

Key technical considerations include: the interaction with detached HEAD states, whether to persist remote names during submodule initialization, and whether to enforce consistency ("always origin") versus flexibility (honoring user configuration). The discussion highlights that this touches deeper questions about submodule design - whether they should be treated as independent repositories or tightly controlled by the superproject.

This moves the thread forward by introducing new solution vectors while maintaining focus on the core problem of reliable remote resolution in submodule operations. The exchange suggests the fix may require more design work than initially apparent, particularly around the detached HEAD case and long-term configuration strategy.
