Thread identity: Bug report and feature proposal regarding submodule behavior when `clone.defaultRemoteName` differs from "origin", reported by Jacob Keller.

Core problem: Submodule operations fail when `clone.defaultRemoteName` is configured to something other than "origin" because `repo_get_default_remote` in `builtin/submodule--helper.c` hardcodes "origin" as the remote name. This affects fetching submodule commits and potentially other operations relying on remote resolution.

Current status: No patches submitted. Discussion is at the proposal stage with Keller outlining potential solutions: (1) check for single remote first, (2) respect `clone.defaultRemoteName`, (3) fall back to "origin", and (4) possibly add new submodule-specific config option.

Key technical details: The issue centers on `repo_get_default_remote` in `builtin/submodule--helper.c` which currently ignores user configuration. The fix would need to modify this function and potentially add new config parsing for submodule-specific remote naming. The change would affect submodule initialization and update workflows where users have customized their default remote names.

Open questions: Should the solution use existing `clone.defaultRemoteName` or introduce new submodule-specific config? What should the exact fallback chain be (single remote -> configured default -> "origin")? How does this interact with detached HEAD states in submodules?

Participant positions: Jacob Keller has identified the issue and proposed solution directions. No other contributors have weighed in yet.

Related work: This connects to broader discussions about submodule usability and configuration flexibility. The hardcoded "origin" assumption appears to be a long-standing behavior that hasn't previously accounted for customized remote naming conventions.
