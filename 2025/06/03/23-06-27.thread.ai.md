Thread identity: Bug report and feature proposal regarding submodule behavior when `clone.defaultRemoteName` differs from "origin", reported by Jacob Keller, with Junio Hamano now participating.

Core problem: Submodule operations fail when `clone.defaultRemoteName` is configured to something other than "origin" due to `repo_get_default_remote` in `builtin/submodule--helper.c` hardcoding "origin". This affects fetching submodule commits and other remote-dependent operations, particularly in detached HEAD states. The discussion has expanded to consider whether submodules should respect user configuration or enforce consistency by always using "origin".

Current status: Jacob Keller confirms his real-world workflow uses "upstream" as the default remote name, exposing the hardcoded "origin" assumption. The solution space now includes: (1) using the superproject's `.gitmodules` URL directly to bypass remote naming, (2) recording remote names during `submodule init`, (3) leveraging single-remote cases, (4) reflog-based origin tracing for detached HEADs, and (5) enforcing "origin" consistency by ignoring user config in submodule contexts. Junio Hamano has raised concerns about reliability of reflog inspection and configuration persistence.

Key technical details: The issue centers on `repo_get_default_remote`'s hardcoded behavior, with new considerations around: superproject `.gitmodules` URL usage, real-world remote renaming patterns (e.g., GitHub workflows converting "origin" to "upstream"), and URL-to-remote matching logic. The change would affect submodule initialization, update, and fetch workflows. Potential solutions may require modifications to both remote selection logic and submodule initialization recording mechanisms.

Open questions: Should remote names be persisted during initialization? Is the superproject's `.gitmodules` URL reliable enough to bypass remote naming? How to handle URL-to-remote matching when remotes are renamed? Should submodules privilege superproject configuration over local settings? Is reflog inspection sufficiently reliable for detached HEAD resolution? The fundamental tension remains between configuration flexibility ("respect user's remote names") and operational reliability ("enforce origin consistency").

Participant positions: Jacob Keller has expanded the solution space with practical workflow examples and proposed leveraging `.gitmodules` URLs. Junio Hamano continues to emphasize the need for reliable solutions, particularly around detached HEAD cases and configuration persistence. The discussion shows increasing focus on tradeoffs between flexibility and consistency.

Related work: Connects to broader submodule design questions about independence versus superproject control. The hardcoded "origin" assumption intersects with ongoing configuration flexibility efforts. The discussion may influence future submodule remote handling design, particularly around initialization-time recording of critical metadata.
