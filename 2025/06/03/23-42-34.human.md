Maintainer response to submodule remote naming issue. Junio Hamano engages with Jacob Keller's report about submodule operations failing when `clone.defaultRemoteName` differs from "origin". The discussion explores several solution approaches while questioning some underlying assumptions.

Hamano first seeks clarification about whether the issue stems from using a custom remote name in submodule setups. He notes that `clone.defaultRemoteName` can be overridden during clone, making the current config value unreliable for determining the original remote name. He suggests that checking for a single remote (Keller's option 1) might be better, and proposes an intermediate step to examine where a detached HEAD originated via reflog.

The response questions whether a new config option is truly needed, proposing two alternative directions: either have submodule initialization record the remote name used during cloning, or make submodule clones always use "origin" regardless of `clone.defaultRemoteName`. Hamano observes that if submodules are only accessed via the superproject, the actual remote name may not matter.

This moves the discussion forward by challenging some premises while offering concrete technical alternatives. The exchange highlights the tension between configuration flexibility and implementation simplicity in submodule handling.
