Refactoring patch in Patrick Steinhardt's maintenance task execution series (v4 06/12). This patch factors out task execution logic from `maintenance_run_tasks()` into a new `maybe_run_task()` helper function. The extraction prepares for an upcoming change that will split maintenance tasks between foreground and background phases when running as a daemon.

The new `maybe_run_task()` encapsulates the core logic for conditionally running a single maintenance task (checking auto-conditions, tracing, and error handling) while maintaining identical behavior. It takes the task struct, repository, options, and config as parameters. The function returns 1 on task failure, propagating errors up to the caller.

This is a straightforward code organization change that:
- Moves the task execution loop body into a dedicated function
- Preserves all existing behavior including trace2 regions and error reporting
- Keeps the same parameter passing pattern seen elsewhere in the series
- Sets up for the phase split work coming in later patches

The change affects `builtin/gc.c` by making the task execution flow more modular while maintaining the same test coverage. This continues the series' pattern of methodical refactoring to support the race condition fixes and phase separation work that follows.
