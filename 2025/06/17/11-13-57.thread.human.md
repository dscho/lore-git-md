This thread examines a subtle edge case in Git's rename detection when files are renamed and then replaced with symlinks (or otherwise repopulated). Michal Suchánek originally reported that Git fails to track the rename relationship in these cases. Elijah Newren clarified this is expected behavior - Git's rename detection only works when files are deleted in the source or added in the destination, not when the original path gets repopulated.

New technical details have emerged showing the issue is more fundamental. Even with Git's `-B` (break detection) option enabled, the rename still isn't properly tracked - Git reports it as a copy instead. Michal demonstrated this through several test cases showing how Git treats mode changes (like converting a file to a symlink) as complete file deletions and additions, breaking the rename relationship despite identical content.

The discussion has revealed two key insights: First, this isn't just about symlinks - it's a general limitation in how Git tracks file identity across changes. Second, there's a discrepancy between Git's internal representation (which sees the files as unrelated) and user expectations about rename tracking. The core tension now is whether and how to address this without breaking existing workflows or causing performance regressions, particularly in merge operations. While viewing operations might be easier to fix, changes to merge behavior would require careful consideration of merge-ort's assumptions.
