This is a technical clarification about Git's rename detection behavior when files are replaced with other content (including symlinks) in the same commit where they were renamed.

Elijah Newren responds to Michal Suchánek's bug report about rename detection failing with symlinks, explaining that the core issue isn't specifically about symlinks but rather about Git's general behavior when a renamed file's original path is reused in the same commit. The response clarifies that Git's rename detection by default only considers files that are purely added or deleted, not those present in both source and destination. 

Newren notes this behavior could potentially be addressed using break detection (a more aggressive rename detection mode), but cautions that break detection has known issues and would significantly impact merge performance, especially in merge-ort. The email provides clear examples demonstrating both the reported behavior and how symlink renames do work when not combined with file replacement.

The response suggests this isn't a simple bug to fix due to fundamental assumptions in Git's diff and merge machinery, and implies that changing this behavior would require substantial work with significant performance tradeoffs. This moves the discussion from "is this a bug?" to "is this worth fixing given the costs?" while providing the technical context needed to make that evaluation.
