This is a bug report demonstrating an issue with Git's rename detection when dealing with symlinked files. Michal Suchánek shows a sequence where:

1. They first rename a file (`somefile` to `somefile-renamed`) and commit it
2. Then create a symlink from the original name (`somefile`) to the renamed file
3. When amending the commit, Git fails to recognize this as a rename operation, instead showing the original file as deleted and replaced with a symlink

The core issue is that Git's rename detection doesn't appear to handle cases where a file is replaced with a symlink pointing to its renamed counterpart. This could cause confusion in version history when tracking file movements that involve symlinks.

The report is concise but clearly demonstrates the problematic behavior through concrete steps and commit diffs. While it doesn't propose a solution, it effectively highlights a real edge case in Git's rename tracking that might warrant attention from developers working on the diff/rename detection code.
