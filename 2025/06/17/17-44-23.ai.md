This is a technical response to a bug report about Git's rename detection behavior with symlinks. Elijah Newren provides a detailed analysis of the issue reported by Michal Suchánek, clarifying that the core problem isn't specifically about symlinks but rather about Git's general behavior when a renamed path is immediately repopulated with new content.

Newren explains that Git's rename detection by default only considers files that are either deleted in the source or added in the destination - it doesn't track renames for files that exist in both versions. He notes this is actually the expected behavior of Git's diff machinery, though it may be surprising in this edge case. The response distinguishes between symlink rename detection (which already works) and this specific scenario where a renamed file's original path is repopulated.

The email also discusses the `--break` detection option that could potentially help here, but warns it has known bugs when combined with rename detection and would significantly impact performance, especially in merge operations. Newren mentions that merge-ort (Git's newer merge strategy) makes assumptions against break detection being active, suggesting retrofitting support would be non-trivial work with substantial performance tradeoffs.

This response provides important technical context for the original bug report, shifting the focus from symlink-specific behavior to Git's fundamental rename detection mechanics and the practical constraints around modifying this behavior. It suggests the issue may be more complex than initially presented, involving deep architectural considerations in Git codebase.
