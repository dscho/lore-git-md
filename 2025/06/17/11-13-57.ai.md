This is a bug report demonstrating an issue with Git's rename detection when dealing with symlinked files.

The email shows a sequence where:
1. A file `somefile` is renamed to `somefile-renamed` (commit 5d51b10)
2. A symlink `somefile` pointing to `somefile-renamed` is created and committed via `--amend` (commit 377d9bd)

The key observation is that Git's rename detection fails to recognize that `somefile-renamed` is the renamed version of the original `somefile` when there's an intervening symlink. Instead of showing the rename, Git shows the original file as deleted and the new file as newly created, missing the rename relationship.

The issue appears to be in Git's diff machinery which doesn't properly track renames across symlink operations. This could affect workflows where files are replaced with symlinks while maintaining content continuity. The reporter doesn't propose a solution but asks whether this behavior can be fixed.

This seems like a legitimate edge case in rename detection that could affect users who mix symlinks and file operations. The reproduction case is clear and minimal, making it a good starting point for investigation. The impact is likely limited to specific workflows involving symlinks, but the behavior is clearly unintentional from Git's perspective.
