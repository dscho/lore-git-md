Thread summary:

Solaris build compatibility issues with sed, focusing on two problems: (1) non-critical warning about missing newline in version-def.h generation, and (2) error about unsupported `-E` flag in config-list.h generation (introduced by e1b81f54da). Brad Smith initially reported the issues and Collin Funk confirmed them, noting the newline warning is likely benign while the `-E` flag error is more serious due to Solaris' native sed lacking extended regex support prior to POSIX.1-2024. Junio C Hamano responded with a patch addressing both issues: adding an explicit newline in GIT-VERSION-GEN and rewriting the sed expression to use basic regex (BRE) instead of extended regex (ERE), removing the `-E` flag dependency while maintaining matching behavior.

Brad Smith confirmed Junio's patch resolves both Solaris build problems, with the BRE pattern `/^`*[a-zA-Z].*\..*`*::$/` replacing the ERE version. Collin Funk provided final verification, reporting successful builds on both Solaris 10 and Linux with identical output, confirming the empty config_name_list issue is resolved, and added a Reviewed-by tag. Eli Schwartz weighed in earlier on the `gsed` discussion, noting GNU sed is only available as an optional third-party package on Solaris and expressing skepticism about requiring it. 

In follow-up discussion, Brad Smith provides additional context about GNU sed's inclusion in Solaris distributions, noting Solaris 11 includes GNU sed as part of the base OS while earlier versions (like Solaris 10) do not, referencing Oracle's documentation. This reinforces the thread's consensus that mandating GNU tools would be problematic for older Solaris installations. Collin Funk and Eli Schwartz had earlier reinforced the value of Junio's portable solution, acknowledging that while GNU sed is commonly available on Solaris machines, it's not part of the default installation for all versions. They note Solaris's non-standard tools (like its `date` command) have caused similar issues in the past, but agree requiring GNU tools would be an unattractive solution. 

The exchange serves as post-resolution commentary validating the chosen approach, with all participants implicitly endorsing the portable solution over mandating GNU utilities. The thread concludes with clear consensus favoring solutions that work with native tools rather than requiring GNU alternatives, with all reported Solaris build issues resolved through Junio's patch that maintains cross-platform compatibility.
