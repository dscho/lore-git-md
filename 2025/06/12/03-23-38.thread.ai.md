Thread summary:

Solaris build compatibility issues with sed, focusing on two problems: (1) non-critical warning about missing newline in version-def.h generation (introduced by f6a2efdc9b), and (2) error about unsupported `-E` flag in config-list.h generation (introduced by e1b81f54da). Brad Smith initially reported the issues and Collin Funk confirmed them, noting the newline warning is likely harmless while the `-E` flag error is more serious due to Solaris' native sed lacking extended regex support prior to POSIX.1-2024. Junio C Hamano responded with a patch addressing both issues: rewriting the sed expression to use basic regex (BRE) instead of extended regex (ERE) for the `-E` flag problem, and adding explicit newlines via `printf "%s\n"` for the version-def.h issue.

Brad Smith confirmed Junio's patch resolves both Solaris build problems, with the BRE pattern `/^`*[a-zA-Z].*\..*`*::$/` replacing the ERE version. Collin Funk provided final verification, reporting successful builds on both Solaris 10 and Linux with identical output, confirming the empty config_name_list issue is resolved, and added a Reviewed-by tag. Eli Schwartz weighed in earlier on the `gsed` discussion, noting GNU sed is only available as an optional third-party package on Solaris and expressing skepticism about requiring it. 

In follow-up discussion, Brad Smith provides additional context about GNU sed's inclusion in Solaris distributions, noting Solaris 11 includes GNU sed as part of the base OS while earlier versions (like Solaris 10) do not, referencing Oracle's documentation. Collin Funk and Eli Schwartz reinforced the value of Junio's portable solution, acknowledging that while GNU sed is commonly available on Solaris machines, it's not part of the default installation for all versions. They note Solaris's non-standard tools (like its `date` command) have caused similar issues in the past, but agree requiring GNU tools would be an unattractive solution.

Eric Sunshine provides post-resolution commentary on shell script portability, noting the version-def.h fix could have used simpler `echo` statements instead of `printf "%s\n"`, as the original issue was introduced in f6a2efdc9b which used `printf "%s"` without newlines in several places. He suggests `echo` is generally preferable to `printf` for simple string output cases since it automatically handles newlines correctly. Paul Smith responds to this with a caution about `echo` portability issues across different Unix implementations, noting that while `printf` requires explicit newline handling, it's more standardized and safer for cases where the output might contain special characters or start with hyphens. This reinforces why the `printf`-based solution (as implemented in Junio's patch) was the more robust choice despite being slightly more verbose.

Eric Sunshine acknowledges Paul Smith's point about `echo` portability concerns, agreeing that `printf` is indeed the safer choice when the output text might contain special characters or start with hyphens. This reinforces why Junio's earlier patch using `printf "%s\n"` was the correct solution for the version-def.h generation issue, despite Eric's initial suggestion that `echo` could have been simpler. The exchange serves as a post-mortem reflection on shell scripting best practices, with both contributors agreeing that while `echo` might work for simple cases, `printf` is more standardized and reliable for production code. This doesn't change the already-implemented solution but provides useful context for future similar situations where developers might face the `echo` vs `printf` tradeoff.
