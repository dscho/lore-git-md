This is a response in the `rebase--` RFC thread, taking a position on merge-vs-rebase workflows rather than directly engaging with the technical proposal. The email comes from Nico Williams, who advocates strongly for rebase-only workflows and shares an alternative conflict-resolution approach using bisection.

The core argument is that rebase workflows inherently provide better conflict resolution by keeping changes "always on top" of upstream, making conflicts smaller and more manageable. Nico shares a personal script that uses bisection to find the first upstream commit where a conflict arises, along with links to similar tools like git-imerge that take this approach. While acknowledging some cases where merges are unavoidable, the position is that cherry-picking and rebasing should be preferred whenever possible.

The response doesn't critique the `rebase--` tool's technical merits but rather questions the underlying need by suggesting merge-heavy workflows should be avoided.
