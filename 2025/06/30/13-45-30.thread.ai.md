Thread identity: Ongoing discussion about credential helper behavior in Git, focusing on HTTP status codes and credential persistence during failed operations. Originated from a Gitea/AGit workflow using git-credential-oauth helper, with primary participants Brian M. Carlson (maintainer) and Michal Suchánek (reporter).

Core problem: Git's credential helper interface clears stored authentication tokens after failed operations, creating friction in OAuth workflows. The core disagreement centers on whether this security measure should distinguish between authentication failures (401 Unauthorized) and operation failures (403 Forbidden/404 Not Found), with Brian maintaining the current behavior is correct protocol implementation while Michal argues for preserving valid credentials across non-authentication failures.

Current status: Brian has clarified HTTP protocol semantics per RFC 9110, explaining servers should use 401 only for invalid credentials and 403/404 for valid-but-unauthorized operations. He confirms Git has no built-in credential preservation for failures but acknowledges a config option could theoretically be added, though with concerns about troubleshooting complexity and documentation impact. The fundamental impasse remains between Git's security model and real-world OAuth workflow needs.

Key technical details:
- Behavior affects all Git-managed credential helpers during operation failures
- Security design assumes operation failures may indicate credential issues
- HTTP status code distinctions (401 vs 403/404) are critical but server-dependent
- git-credential-oauth helper specifically impacted but not uniquely
- Potential config option discussed but with maintainer concerns about side effects

Open questions:
- Whether server misconfiguration (improper 401 usage) is the root cause
- If Git's security model could accommodate credential preservation for known-valid cases
- Feasibility of adding a config option without compromising security or increasing support burden

Participant positions:
- Brian M. Carlson maintains current behavior correctly implements HTTP protocol semantics and security best practices, suggests server-side fixes
- Michal Suchánek continues advocating for client-side changes to preserve valid credentials during non-authentication failures
- Fundamental disagreement persists between protocol-level security design and practical workflow requirements

Related work:
- Gitea issue #34583 documents the observed behavior in AGit workflows
- RFC 9110 cited as authoritative reference for HTTP status code semantics
- SSH credential persistence noted as unaffected alternative
- No active patches to change core behavior, discussion remains theoretical
