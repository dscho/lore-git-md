This thread discusses a persistent issue with Git's credential helper behavior, where valid authentication tokens are cleared after failed operations - even when the failure has nothing to do with authentication. The original reporter, Michal Suchánek, encountered this in a Gitea/AGit workflow using the git-credential-oauth helper, where valid OAuth tokens were being unnecessarily purged.

Maintainer Brian M. Carlson has explained this is intentional security design - Git treats any operation failure as potentially credential-related to prevent lockouts from persistent bad credentials. In the latest exchange, Brian provides technical context about HTTP status codes, noting servers should use 403 (Forbidden) or 404 (Not Found) rather than 401 (Unauthorized) when credentials are valid but the operation fails, as this preserves the credentials. He suggests the root issue may be server misconfiguration rather than Git behavior.

While Brian acknowledges a configuration option could theoretically be added to preserve credentials, he expresses concerns about the complexity this would introduce for troubleshooting. The discussion remains at an impasse between Git's security model (which assumes operation failures may indicate credential problems) and real-world OAuth workflows (where failures often occur for unrelated reasons). No core Git changes are expected, leaving affected users to either modify server behavior or implement custom credential helper workarounds.
