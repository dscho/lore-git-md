This is a response in an ongoing thread about credential helper behavior in Git, specifically regarding credential persistence after failed operations.

Brian M. Carlson confirms that Git's current behavior of clearing credentials after failed operations is intentional, not a bug. They explain this design prevents users from being stuck with invalid credentials that would continue to fail. The response comes from a security perspective, where preserving bad credentials could create an authentication deadlock.

The original reporter had suggested preserving credentials after failures, particularly problematic in OAuth workflows where re-authentication is disruptive. Carlson offers a workaround - creating a custom credential helper that ignores erase commands while delegating other operations to existing helpers. This would allow credential persistence while maintaining core functionality.

The exchange highlights a tension between security practices (clearing potentially compromised credentials) and user experience (avoiding repeated authentication prompts). Carlson's position suggests this behavior is unlikely to change in core Git, leaving custom credential helper implementations as the solution path for those wanting different behavior.

This appears to be a definitive answer from a Git maintainer on the design rationale, likely closing the discussion unless new technical arguments emerge about why the current behavior is problematic beyond user inconvenience.
