This is a follow-up in the ongoing discussion about the proposed `git refs list` subcommand, which aims to consolidate reference-related functionality under a single command hierarchy. Maintainer Junio C Hamano responds to a confusing statement from shejialuo about potential code duplication between the new command and existing `git for-each-ref`.

Hamano clarifies that a thin wrapper approach (where `git refs list` would internally call `git for-each-ref`) could achieve the goal of command grouping without duplicating functionality or breaking existing users. He points to the precedent of `git branch` and `git tag` listing modes, which already use this pattern to provide `for-each-ref` features while maintaining separate implementations.

The exchange highlights the maintainer's continued skepticism about creating parallel commands without clear technical differentiation, while offering a potential path forward that would satisfy both the discoverability goals and implementation concerns. This suggests the discussion is moving toward interface design philosophy rather than technical feasibility, with Hamano steering contributors toward solutions that minimize maintenance overhead.
