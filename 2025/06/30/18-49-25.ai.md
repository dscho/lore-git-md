Feature and performance optimization for the `git last-modified` command. This patch adds Bloom filter support to skip unnecessary diff computations during the revision walk, yielding significant speedups in some cases.

The implementation adds Bloom filter checks before computing diffs, using the existing changed-path Bloom filter infrastructure. When filters indicate no possible path changes (a negative" result), the diff computation is skipped entirely. The patch includes new `bloom.h` and `commit-graph.h` includes, adds a `bloom_key` field to the `last_modified_entry` struct, and implements the `maybe_changed_path()` helper to check filters.

Performance tests show dramatic improvements in some scenarios: 50.6% faster for top-level checks and 36.4% faster for subdirectory checks. The recursive case shows minimal change (0.4%), likely because it still requires examining most commits. The implementation builds on Taylor Blau's prior Bloom filter work and maintains compatibility when filters aren't available (falling back to full diff computation).

Key technical details:
- New `bloom_key` field in `last_modified_entry` populated via `fill_bloom_key()`
- `maybe_changed_path()` helper checks filter contents before diffing
- Memory management extended to clear Bloom keys during cleanup
- Performance impact measured in `t/perf/p8020-last-modified.sh`
- Falls back gracefully when Bloom filters are unavailable

The change is well-contained within `last-modified.c` and appears to integrate cleanly with the existing implementation. The performance gains validate the approach, though the recursive case shows there may be room for further optimization. This represents a significant step in the command's development, addressing one of the major performance bottlenecks identified earlier in the thread.
