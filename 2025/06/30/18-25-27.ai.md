Bugfix addressing comment character selection when core.commentChar="auto" during conflict resolution. This is the third version of Ayush Chandekar's patch, now incorporating test optimizations from earlier reviews.

The patch modifies the comment character selection logic in builtin/commit.c to ignore trailing comment blocks (like conflict markers) when auto-selecting a comment character. This prevents Git from incorrectly treating existing conflict markers as active comment characters, which could cause them to appear in final commit messages. The change uses ignored_log_message_bytes() to calculate a cutoff point before scanning for comment characters.

A new test case in t/t3418-rebase-continue.sh verifies the fix by simulating a rebase conflict with core.commentChar="auto" and confirming the comment character remains '#' as expected. The test has been optimized from v2 to reuse existing test infrastructure more efficiently.

The patch maintains backward compatibility while fixing a regression introduced in a6c2654f83 (rebase -m: fix --signoff with conflicts, 2024-04-18). The solution is surgical, focusing specifically on the conflict marker case without broader architectural changes, which aligns with the ongoing discussion about potentially deprecating core.commentChar="auto" entirely.

Key technical details:
- Adds cutoff calculation using ignored_log_message_bytes()
- Modifies character scanning loop to stop at cutoff point
- Preserves original comment character (#) when conflict markers are present
- Test case verifies behavior with rebase --continue
- Avoids deeper refactoring while the core.commentChar="auto" deprecation discussion continues

The patch appears well-contained and addresses the immediate issue while the broader architectural questions around comment character handling remain under discussion. It represents a pragmatic solution that doesn't preclude future changes to the auto-selection mechanism.
