Maintainer feedback on refs command consolidation. Junio C Hamano responds to Meet Soni's RFC for a new `git refs list` subcommand, expressing concerns about command proliferation and divergence. While acknowledging the discoverability motivation, Hamano cautions against creating subtle behavioral differences from existing commands like `git for-each-ref`, noting Git's history of both consolidation and splitting commands based on user needs.

The response highlights philosophical tensions in interface design - whether refs should be treated uniformly (as the underlying mechanism suggests) or whether user-facing commands should reflect conceptual differences between ref types (branches, tags, HEAD). Hamano suggests maintaining strict feature parity if the new command proceeds, while implicitly questioning whether a wrapper approach (like existing branch/tag commands) might better serve discoverability without code duplication.

This continues the thread's central debate about whether command consolidation justifies new infrastructure, with the maintainer leaning toward conservative evolution of existing patterns. The exchange surfaces important design considerations for any ref-related command reorganization.
