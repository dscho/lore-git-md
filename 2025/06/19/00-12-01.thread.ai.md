Bug report thread summary:

Subject: `git checkout -b` succeeds during rebase when it should fail
Author: Grant Birchmeier
Thread type: Bug report
Status: New report with workaround suggested, root cause still under investigation

Core issue: Creating a new branch with `git checkout -b` succeeds during an active rebase, unlike regular `git checkout` which properly fails. This leaves the original branch in an unrecoverable state, forcing users to complete the rebase on the new branch. The behavior contradicts Git's expected protection against operations that could corrupt in-progress rebases.

Technical details: The rebase state detection logic appears incomplete, failing to prevent branch creation during an active rebase. The inconsistency between `git checkout` (fails) and `git checkout -b` (succeeds) suggests the branch creation path bypasses the rebase state check that normally protects against mid-operation branch switches.

Workarounds: Jacob Keller suggests two recovery methods - first trying `git rebase --abort` to reset the rebase state, then using `git reflog` to restore the original branch or recover intermediate work. These provide temporary solutions while awaiting a proper fix.

Reproducibility: Clear reproduction steps provided showing the branch "ilogger" becoming unusable after creating/switching to "net5" during rebase. The workarounds address the immediate usability impact but don't resolve the underlying bug.

Open questions: Why does the rebase state check not cover branch creation? Is this specific to certain rebase backends? Should `git checkout -b` fail like regular checkout, or is there a safe way to support branch creation during rebase?

Related work: This may connect to ongoing sequencer and rebase internals work. Phillip Wood would be a likely reviewer given his sequencer expertise, though no technical analysis has been contributed yet. The thread remains at the bug-report stage without deeper implementation discussion.
