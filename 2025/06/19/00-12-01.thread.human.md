The thread discusses a bug where `git checkout -b` incorrectly succeeds during an active rebase, unlike regular `git checkout` which properly fails to protect the rebase state. Grant Birchmeier originally reported that this leaves the original branch in an unrecoverable state, forcing users to complete the rebase on the newly created branch instead.

Jacob Keller has now responded with practical workarounds for affected users: first trying `git rebase --abort` to reset the rebase state, then using `git reflog` to recover the original branch or any intermediate work. While this doesn't address the underlying issue - why branch creation bypasses the rebase state checks - it provides immediate help for users encountering the problem.

The core inconsistency remains: Git's rebase protection logic appears incomplete, allowing branch creation when it should fail like other disruptive operations during rebase. The thread is still awaiting input from rebase/sequencer experts (likely Phillip Wood) about whether this is a general issue or specific to certain rebase backends, and what the correct behavior should be.
