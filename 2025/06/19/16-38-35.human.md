This is a discussion about Git's `.clang-format` rules and the `make style` tool. Junio Hamano raises concerns about the usefulness and adoption of the automated code formatting tool, noting that its suggestions are a mixed bag - some improvements but also many questionable or clearly worse changes. He demonstrates this by showing the tool's output when run against recent commits, pointing out cases where the formatting changes either don't improve readability or actively make the code worse.

The key points are:
1. The tool is likely underused because it's not well integrated into developer processes (hard to run on commit ranges)
2. The current `.clang-format` rules produce many false positives and suboptimal suggestions
3. Some formatting changes are purely mechanical and not worth the churn when the original code is already acceptable
4. The tool could be more useful if it focused only on wrapping overly long lines rather than reformatting already-readable code

Junio suggests two improvements: better tooling integration (to make it easier to run on commit ranges) and refining the formatting rules to reduce false positives. The discussion highlights the tension between automated consistency and human judgment in code formatting.
