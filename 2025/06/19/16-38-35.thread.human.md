This thread explores whether and how to automate code formatting in Git using `clang-format`, balancing consistency against readability. Junio C Hamano started by examining real-world cases where the tool produces mixed results—sometimes improving code but often making harmful suggestions that break logical grouping, particularly in signature handling and fast-import/export code. Christian Couder agreed, noting many suggestions are false positives not worth enforcing.

Brian m. carlson advocated for standardizing on the tool's output regardless of imperfections, similar to Go's `gofmt` philosophy, proposing CI integration with containerized execution to ensure consistent results. Collin Funk raised concerns about version instability and suggested editor configurations as an alternative. Brian countered that containerization solves version issues and that editor-based approaches have security and coverage limitations.

Junio now clarifies his position further, distinguishing between subjective style preferences (where consistency may justify automation) and objectively worse formatting that reduces readability. He argues the tool isn't yet reliable enough for blind automation, as it still produces harmful suggestions. The discussion remains divided between those prioritizing mechanical consistency (Brian) and those emphasizing human judgment (Junio, Christian), with open questions around enforcement timing, special cases like function declarations, and technical implementation. The core tension persists: whether to accept imperfect-but-consistent automation or wait for more polished tooling.
