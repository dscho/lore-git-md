This thread examines Git project's approach to code formatting, particularly around the `.clang-format` configuration and `git clang-format` tool. The discussion began with Junio C Hamano identifying real-world cases where the tool produces mixed results - some helpful suggestions but also problematic ones that break alignment in signature handling and fast-import/export code. Christian Couder agreed, noting specific issues with line wrapping in signature code where the tool both incorrectly unwraps short lines and worsens alignment.

Brian m. carlson advocated for a standardized approach similar to Rust and Go projects, suggesting treating clang-format output as canonical regardless of personal preferences. His proposals included configuration refinements, CI integration with containerized execution to handle version inconsistencies, and the productivity benefits of eliminating style debates. Collin Funk raised concerns about version instability and proposed editor-based solutions instead, which Brian countered by emphasizing the limitations of editor configurations and the need for automated, consistent enforcement.

In the latest email, Junio provides further nuance, distinguishing between enforcement for existing code (where style changes may cause unnecessary churn) versus new contributions (where style suggestions should be followed). He supports GitHub CI's current approach of checking pull requests but not pushes to 'seen', and highlights the importance of preserving grep-ability in function declarations. The discussion continues to balance mechanical consistency benefits against human judgment, with open questions about when to enforce rules (pre-commit vs pre-merge), how to handle special cases, and whether to accept "good enough" automated formatting versus more selective enforcement. Technical workflow suggestions include post-commit hooks, format-patch integration, and documentation updates for new contributors.
