Junio Hamano responds to Phillip Wood's proposal about pathspec error handling in `git add --update`. This is a discussion about behavior expectations in pathspec matching, particularly around exclude patterns.

Junio disagrees with Phillip's suggestion that Git should error when exclude patterns match nothing, arguing this would create unnecessary noise. He distinguishes between positive pathspecs (where no matches indicate a likely user mistake) and exclude patterns (where no matches are often the desired outcome). The example `git add -- \*.c ':!auto-generated.c'` demonstrates how silent non-matching excludes are useful - if there's no auto-generated.c, that's fine since the user didn't want to add it anyway.

The response highlights a philosophical difference in how to handle pathspecs: Phillip wants consistency in treating all patterns (both positive and negative) as requiring matches, while Junio advocates for distinguishing their semantics. Junio also draws a parallel to .gitignore behavior, where non-matching patterns are silently accepted. This suggests the discussion may need to consider wider implications beyond just the `git add -u` case.

Key technical points mentioned: the distinction between positive and negative pathspec matching behavior, the `.gitignore` precedent, and the specific example of `:!auto-generated.c` patterns. The empty repository case that started the thread isn't directly addressed here, but the principles discussed would apply to that situation as well.
