Refactoring patch in Patrick Steinhardt's maintenance task execution series, focusing on splitting tasks into foreground/background phases to address lock contention issues.

This patch (8/12 in v3) introduces a structural split between foreground and background maintenance tasks in `builtin/gc.c`, preparing for resolution of packed-refs lock contention problems. The key change is modifying the `maintenance_task` struct to contain separate function pointers for foreground and background execution phases, where foreground tasks run before detaching and background tasks after. All existing tasks are initially assigned to the background phase via the `.background` field, maintaining current behavior while establishing the framework.

The implementation adds an `enum task_phase` to track execution context and modifies `maybe_run_task()` to accept a phase parameter, using it to select the correct function pointer and set appropriate Trace2 regions ("maintenance foreground" vs "maintenance"). The task execution flow in `maintenance_run_tasks()` now explicitly runs foreground tasks before attempting to detach, then background tasks afterward.

This change lays groundwork for future patches that will move reference-related tasks (pack-refs, reflog-expire) to the foreground phase to prevent extended lock contention, while keeping other maintenance operations in the background. The patch maintains all existing functionality as a transitional step, with behavior changes to follow in subsequent patches.

Technical details include:
- New `foreground` and `background` function pointers in `maintenance_task` struct
- `TASK_PHASE_FOREGROUND`/`TASK_PHASE_BACKGROUND` enum for execution context
- Updated `maybe_run_task()` signature and logic to handle phases
- Separate Trace2 regions for phase tracking
- Two-pass task running in `maintenance_run_tasks()`
- All tasks currently assigned to background phase (no behavior change yet)
- Maintains existing auto-condition checking and error handling
- Preserves the existing detach/foreground fallback behavior

The patch continues the series' pattern of careful refactoring to enable race condition resolution while improving code structure. It specifically addresses the architectural need to distinguish between tasks that can run safely in the background and those that must complete quickly in the foreground to avoid lock issues.
