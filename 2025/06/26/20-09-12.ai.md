Bugfix/Platform compatibility discussion regarding Windows signal handling behavior in the ongoing git-daemon signal handling series. This email exchange between Carlo Marcelo Arenas Belón and Phillip Wood focuses on the Windows-specific implementation details of the SIGCHLD handler setup.

The key technical debate centers on whether the Windows sigaction() wrapper should:
1. Initially match Windows signal() behavior (current proposal) by not setting errno for SIGCHLD
2. Immediately implement proper POSIX sigaction() semantics by setting errno=EINVAL

Carlo Marcelo Arenas Belón discovered through testing that Windows' signal() doesn't set errno for SIGCHLD (contrary to documentation) when using Git's SIGCHLD number (17), but does set errno when using MSVC's number (20). He advocates for initially matching signal() behavior to avoid regressions, with potential future transition to proper sigaction() semantics.

Phillip Wood had previously suggested standardizing on POSIX behavior by setting errno=EINVAL, arguing this would be more maintainable long-term. The discussion reveals platform-specific quirks in Windows signal handling that complicate the transition, including:
- Inconsistent errno setting between different Windows implementations
- Discrepancy between documented and actual behavior
- Different SIGCHLD numbering between Git's compatibility layer and native Windows

The email ends with Carlo Marcelo Arenas Belón suggesting to involve Johannes Schindelin (dscho) for additional Windows expertise, indicating this platform-specific behavior may require deeper investigation before finalizing the approach. This discussion represents a microcosm of the larger architectural debate in the thread about balancing platform compatibility with clean abstractions.
