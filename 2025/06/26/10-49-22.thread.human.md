This thread investigates a puzzling bug where `git rebase -i` incorrectly reports "local changes would be overwritten" in secondary worktrees, while regular rebase works fine. The issue appears specific to worktrees created with `git worktree add` and occurs intermittently, making it hard to reproduce. 

Kristoffer Haugsbakk initially suggested examining the reporter's extensive hook configuration as a possible factor, but Denilson Sá Maia has now clarified that while many hooks are registered through Husky, only `commit-msg` and `pre-push` are actually active. This rules out interference from other unused hooks and helps narrow the focus to the core issue in how interactive rebase handles worktree state detection. 

The investigation continues into why the rebase operation sometimes misdetects dirty state in secondary worktrees, with the problem appearing to stem from improper bookkeeping during the multi-step interactive rebase process. The intermittent nature suggests possible race conditions or edge cases in temporary checkout handling that only manifest in certain commit history scenarios.
