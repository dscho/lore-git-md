This thread investigates an intermittent bug where `git rebase -i` fails in secondary worktrees with false "local changes would be overwritten" errors, while non-interactive rebase works fine. The issue, reported by Denilson Sá Maia, occurs specifically in worktrees created via `git worktree add` on Git 2.49.0 (Darwin/arm64) and appears related to how interactive rebase manages worktree state during its multi-step operation.

Kristoffer Haugsbakk has followed up, noting the reporter's extensive hook configuration and asking whether git-branchless is in use, suggesting these might contribute to the complex interactions causing incorrect dirty-state detection. While no solution has been identified yet, the investigation has narrowed to consider how hooks and worktree state tracking interact during rebase operations. The thread remains focused on reproducing this edge case that affects only secondary worktrees while primary ones work correctly.
