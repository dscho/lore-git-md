Bugfix targeting interactive rebase behavior with worktrees. This report describes a long-standing issue where `git rebase -i` fails in secondary worktrees with spurious "local changes would be overwritten" errors, while non-interactive rebase works fine. The problem appears intermittently depending on commit history and only manifests in secondary worktrees - the same operation succeeds in the main worktree.

The reporter has observed this behavior for months but cannot provide a minimal reproduction case since it depends on complex interactions between commits across worktrees. The error suggests the interactive rebase codepath incorrectly detects file modifications when operating in a secondary worktree context, though the exact mechanism isn't clear from the report.

Key technical details include:
- Affects `git rebase -i` but not plain `git rebase`
- Only occurs in secondary worktrees created via `git worktree add`
- Error claims local changes exist when none do
- Git version 2.49.0 on Darwin/arm64
- May relate to how interactive rebase handles worktree bookkeeping during its multi-step operation

This appears to be a genuine worktree interaction bug rather than user error, given the clear differential behavior between interactive/non-interactive modes and main/secondary worktrees. The intermittent nature suggests it may involve race conditions or improper state tracking during the rebase's temporary checkouts.
