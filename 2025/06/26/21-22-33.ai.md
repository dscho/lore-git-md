This is the first patch in a 2-part RFC series proposing pipe-based child process tracking as an alternative to signal handling in git-daemon. It introduces infrastructure in run-command.c for parent-child process tracking via pipes rather than SIGCHLD signals.

The patch adds a new `parent_ipc_in` field to `struct child_process`, initialized to -1, which will hold the read end of a pipe from the parent's perspective. In the child process (start_command), it closes this descriptor if set, ensuring the parent can detect the child's exit via pipe closure. This is the first step toward implementing the "poor man's pidfd" approach discussed in the thread.

The change is minimal but foundational - it doesn't yet implement the actual notification system that would replace SIGCHLD handling. The accompanying RFC discussion suggests this approach could avoid platform-specific signal handling issues entirely, though it introduces new concerns about file descriptor management and scaling with many child processes.

This represents a significant architectural shift from both the original SA_RESTART approach and the documentation-only proposal. The implementation appears clean and focused, though its viability depends on the performance characteristics and edge case handling that would be addressed in subsequent patches. The Windows-specific signal handling debates remain unresolved but may become moot if this pipe-based approach proves robust across platforms.
