Git thread summary:

Bug report about interactive rebase (`git rebase -i`) failing in secondary worktrees with false "local changes would be overwritten" errors, while non-interactive rebase works correctly. The issue is intermittent and depends on commit history, affecting Git 2.49.0 on Darwin/arm64. Key symptoms: failure only in secondary worktrees created via `git worktree add`, with incorrect dirty state detection during interactive rebase's multi-step operation. Denilson Sá Maia clarifies their hook configuration - while many hooks are registered via Husky, only `commit-msg` and `pre-push` are active, ruling out most hook interference as a cause. The investigation continues into the core worktree state detection problem, focusing on how interactive rebase handles temporary checkouts in secondary worktrees. Current understanding suggests the issue lies in the rebase machinery's bookkeeping of worktree state rather than being caused by hook activity. The thread remains focused on diagnosing this edge case where secondary worktrees incorrectly report dirty state during interactive rebase operations while primary worktrees function correctly.
