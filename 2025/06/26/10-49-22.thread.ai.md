Git thread summary:

Bug report about interactive rebase (`git rebase -i`) failing in secondary worktrees with false "local changes would be overwritten" errors, while non-interactive rebase works correctly. The issue is intermittent and depends on commit history, making it hard to reproduce. Affects Git 2.49.0 on Darwin/arm64. Key symptoms: failure only in secondary worktrees created via `git worktree add`, with the error incorrectly claiming local modifications exist. The problem appears to be in how interactive rebase handles worktree state during its multi-step operation, possibly involving race conditions or improper bookkeeping of temporary checkouts. Kristoffer Haugsbakk's follow-up suggests examining the reporter's extensive hook configuration and potential git-branchless usage as possible factors in the worktree state misdetection, though no definitive cause has been identified yet. The thread remains focused on diagnosing this edge case where secondary worktrees incorrectly report dirty state during interactive rebase operations while primary worktrees function correctly. The investigation continues into whether hooks or other configuration aspects contribute to the complex interaction causing the intermittent failures.
