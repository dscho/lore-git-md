Git thread summary:

Bug report about interactive rebase (`git rebase -i`) failing in secondary worktrees with false "local changes would be overwritten" errors, while non-interactive rebase works correctly. The issue affects Git 2.49.0 on Darwin/arm64 and occurs when rebasing a secondary branch against main/upstream with unrelated changes, specifically listing files from the target branch as supposedly modified in the worktree. 

Denilson Sá Maia provided detailed reproduction steps confirming the issue: it requires interactive rebase (`-i` flag) and manifests when the secondary branch has changes to file `foo` while main has unrelated changes. The error incorrectly claims worktree changes exist for files modified in main, persisting after stripping most config options except core.repositoryformatversion. Worktrees are on the same local filesystem with no cloud sync, ruling out those factors.

Phillip Wood's technical analysis identified two potential causes: line ending/filter attributes affecting files, or missing index refresh before checkout in interactive rebase. The new reproduction data suggests the bug specifically relates to how interactive rebase handles target branch state checkout in secondary worktrees, where it misidentifies incoming base branch changes as local modifications. This consistent reproducibility in a large repository (contrasting earlier intermittent reports) helps diagnosis by narrowing triggering conditions to the interaction between rebase's temporary checkouts and worktree state tracking. No workarounds or fixes are yet proposed - current focus remains on root cause analysis of the state detection discrepancy between primary and secondary worktrees during interactive rebase operations.
