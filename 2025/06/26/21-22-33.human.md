This is part of a proposed pipe-based child process tracking solution for git-daemon, an alternative to the signal-handling approaches under debate in the ongoing thread.

Carlo Marcelo Arenas Belon introduces the first of two patches that would replace SIGCHLD-based child tracking with a pipe mechanism. This initial patch adds infrastructure to `run-command.c` - a new `parent_ipc_in` field in `child_process` struct to hold a pipe file descriptor, and logic to close the read end of the pipe in the child process. The approach resembles a "poor man's pidfd" using basic pipe operations rather than Linux-specific APIs.

The change is minimal but foundational - it doesn't yet implement the actual notification system, which would come in a follow-up patch. The commit message is terse, assuming readers are following the broader discussion about signal handling alternatives. This appears technically sound but leaves open questions about performance impact and edge cases (like accidental pipe closure) that were raised in the thread.

As part of the three-way architectural debate (SA_RESTART toggling vs documentation-only vs pipe-based), this represents a significant shift toward avoiding signal handling entirely. Windows compatibility appears to be a driving factor, though the patch itself is platform-agnostic. The approach would need to prove itself against the other proposals' simplicity (documentation) or incrementalism (SA_RESTART).
