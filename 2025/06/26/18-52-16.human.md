This is a performance analysis of `git log --follow` slowness, continuing the thread investigating why file history traversal is much slower than expected even with commit-graph optimizations enabled.

Jeff King explains that `--follow` currently bypasses two key performance optimizations: it can't use commit-graph changed-path Bloom filters (which normally speed up path queries) and it can't prune uninteresting side branches during traversal. This happens because `--follow` needs to track path changes across renames, making the standard optimizations unsafe. The current implementation is described as a "hacky" bolt-on to the traversal machinery, with the "right" solution being a more integrated approach that could track path changes through renames while still applying optimizations.

The email suggests that while Bloom filters could potentially be adapted to work with `--follow`, it would require significant special-case handling in the current implementation. This provides important context for why the performance is poor in Kai's test case and hints at the architectural challenges involved in improving it.
