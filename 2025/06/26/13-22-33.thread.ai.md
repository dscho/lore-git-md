Thread identity: Bugfix for commit message comment character selection when core.commentChar="auto", affecting rebase, cherry-pick, revert, and merge operations with conflicts. Original patch by Ayush Chandekar with mentoring from Ghanshyam Thakkar, now at v3 with test optimizations.

Core problem: When auto-selecting a comment character during commit message editing, Git incorrectly considers conflict markers (like "<<<<<<<") as candidate comment characters, potentially causing these markers to appear in final commit messages. The issue spans multiple operations and involves deep architectural questions about state management and configuration precedence, particularly between `core.commentChar="auto"` and `core.commentstring`.

Current status: Chandekar's v3 patch implements a surgical fix using ignored_log_message_bytes() to calculate a cutoff point before scanning for comment characters, specifically addressing conflict markers while maintaining backward compatibility. The test case in t/t3418-rebase-continue.sh has been optimized to reuse existing infrastructure. Meanwhile, Phillip Wood's proposal to deprecate `core.commentChar="auto"` entirely remains under discussion, with Junio Hamano acknowledging the consistency benefits of Wood's interim suggestion to hardcode `comment_line_str` to '#' in auto mode. Chandekar's earlier experimental refactoring (repo_get_comment_line_str()) revealed test failures and configuration precedence issues that remain unresolved.

Key technical details:
- Core change in builtin/commit.c adds cutoff calculation using ignored_log_message_bytes()
- Modifies character scanning loop to stop at cutoff point
- Preserves original comment character (#) when conflict markers are present
- Test case in t/t3418-rebase-continue.sh optimized to reuse existing files
- Current implementation uses hardcoded '#' for conflict section detection
- Fixes regression from a6c2654f83 (rebase -m: fix --signoff with conflicts)
