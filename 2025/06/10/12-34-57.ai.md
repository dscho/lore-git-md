This is a feature patch series introducing a new `--trailer` option to `git rebase`, along with necessary infrastructure changes to handle trailers in-process rather than using the external `interpret-trailers` helper.

The series builds on previous RFC feedback from Phillip Wood, addressing his review comments. The first patch refactors trailer handling to work entirely in-memory via a new `amend_strbuf_with_trailers()` function, eliminating fork/exec overhead. The second patch implements the actual `--trailer` feature for rebase, which forces use of the merge backend (since the apply/am backends lack message filtering), automatically enables `--force-rebase` to rewrite fast-forwarded commits, and appends the specified trailer(s) to each rewritten commit. State is preserved in `$state_dir/trailer` to support interrupted rebases.

Key technical details include:
- New test file `t3440-rebase-trailer.sh` covering various scenarios
- Changes across `builtin/rebase.c`, `trailer.c`, and sequencer files
- The implementation stores trailer state for resumption
- Forced merge backend usage when trailers are specified
- Automatic `--force-rebase` behavior with trailers

The series appears well-tested with passing CI runs (except for a known Debian network issue) and thorough test coverage. The implementation follows the suggested approach from previous discussion, moving trailer handling into the main process rather than using an external helper. This could be a useful feature for workflows that need to systematically add trailers (like Signed-off-by) during rebase operations.
