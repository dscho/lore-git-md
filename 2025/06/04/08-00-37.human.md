This is a bug report about inconsistent behavior between `git clone` and `git checkout` when trying to capture output while also showing progress to the user. Nathan Royce reports that while redirecting a clone's output to a variable while simultaneously displaying progress works fine, the same technique fails with checkout.

The issue emerged from a practical use case - cloning only part of a large texlive repository (6GB full, 8MB with `--filter=blob:none`) where the user wanted both progress feedback and the ability to parse error messages from the output. The test case shows the working clone command versus the failing checkout command, both using a subshell with `2>&1 | tee /dev/stderr` redirection.

The report mentions discussion in IRC channels and consideration of alternatives like `GIT_TRACE=1`, but these don't fully address the need to both show progress and capture output for parsing. The patch appears to be investigating a real inconsistency in Git's behavior, though it's presented more as a problem report than a proposed solution. The use case seems legitimate for scripting scenarios where users want both interactive feedback and programmatic access to command output.
