This is a follow-up in the ongoing discussion about submodule behavior when `clone.defaultRemoteName` differs from "origin". Jacob Keller responds to Junio Hamano's technical questions and expands on potential solutions.

The core issue remains that submodule operations fail when the default remote isn't named "origin", particularly in detached HEAD states. Keller confirms his personal workflow uses "upstream" as the default remote name, which breaks the hardcoded assumption in `repo_get_default_remote`.

The email explores several solution directions: recording the remote name during submodule setup, using the superproject's URL directly instead of remote names, or having the parent project specify the remote name in `.gitmodules`. Keller notes that simply ignoring `clone.defaultRemoteName` during submodule initialization (forcing "origin") might not work for his workflow where he needs to interact with submodules directly.

The discussion is advancing toward more concrete solutions, with both participants contributing technical insights. Keller's latest suggestion of using the superproject's URL directly appears promising, as it would bypass the remote naming issue entirely. The thread remains active with multiple viable approaches under consideration, though no consensus has yet emerged on the best path forward.
