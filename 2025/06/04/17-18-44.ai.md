This is a bugfix proposal for submodule remote handling when `clone.defaultRemoteName` differs from "origin". Jacob Keller responds to Junio Hamano's technical questions while expanding the solution space.

The core issue remains submodule operations failing when the default remote isn't named "origin", particularly in detached HEAD states. Keller confirms his workflow uses "upstream" as the default remote name, causing failures when submodule--helper hardcodes "origin". He explores several solution directions: using the superproject's configured URL directly, recording the remote name during initialization, or leveraging the single-remote case.

New technical considerations emerge: the superproject's `.gitmodules` already contains the submodule URL, which could bypass remote naming entirely. Keller also notes real-world complications where developers rename remotes (e.g., GitHub workflows converting "origin" to "upstream"). The discussion now weighs tradeoffs between configuration flexibility ("respect user's remote names") and operational reliability ("enforce origin consistency").

Key unresolved questions include whether to persist remote names during `submodule init`, how to handle URL-to-remote matching, and whether to privilege the superproject's configuration over submodule-local settings. The exchange suggests the solution may require changes to both remote selection logic and submodule initialization recording.
