This is a design discussion in the ongoing `imap-send` OAuth2.0 authentication series, specifically about the libcurl password handling logic. Junio Hamano questions why the patch checks for non-OAuth methods rather than explicitly checking for PLAIN/LOGIN when setting CURLOPT_PASSWORD. He suggests the current approach seems backwards and proposes alternative logic that would explicitly list the password-using methods.

Aditya Garg explains the conservative approach was to avoid potential regressions, since the original code unconditionally set CURLOPT_LOGIN_OPTIONS even for methods like CRAM-MD5. Without access to CRAM-MD5 servers for testing, he preferred minimal changes to the existing logic while cleanly implementing OAuth2.0 support.

Junio emphasizes the importance of clear commit messages and in-code comments to document these design decisions for future maintainers, praising Aditya's verbal explanation ("Set CURLOPT_LOGIN_OPTIONS irrespective...") as exactly the kind of clarification that should be captured in the code history. The exchange shows careful attention to backward compatibility while working towards cleaner authentication handling in the IMAP client.
