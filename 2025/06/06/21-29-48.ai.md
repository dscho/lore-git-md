This is a technical follow-up in the ongoing discussion about submodule behavior with non-standard remote names, focusing on implementation challenges when trying to use the superproject's URL directly.

Jacob Keller reports encountering obstacles while exploring the approach of using the superproject's `.gitmodules` URL directly (rather than relying on remote names). The main issue stems from `remote.c` functions that claim repository-agnostic behavior but internally hardcode `the_repository`, particularly in the deprecated `read_remotes_file` and `read_branches_file` functions. These functions are slated for removal in Git 3.0.

The email poses two key technical questions about modifying this code: (1) whether patches to make these functions properly accept a repository pointer would be acceptable, and (2) whether to modify functions to take a repository pointer instead of a `remote_state` structure when making them submodule-aware. Keller notes the asymmetry in navigation between repository and remote_state structures.

This moves the discussion into concrete implementation challenges while maintaining the thread's focus on finding reliable ways to handle submodule remotes without hardcoding "origin". The exploration touches on both the immediate fix (making config reading work with submodule repositories) and broader architectural questions about parameter passing in the remote handling code. The mention of deprecated functions adds urgency to the solution approach, as any changes would need to align with their planned removal.
