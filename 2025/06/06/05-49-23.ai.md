This is a follow-up clarification to the already-merged pack-bitmap memory leak fixes. The email contains a grammar correction for the commit message of the v5 series, specifically addressing the explanation of why `roots_bitmap` needs unconditional freeing in `find_boundary_objects()`.

The key technical point being clarified is that `cascade_pseudo_merges_1()` operates on `roots_bitmap` as a mutable reference but does not assume ownership, meaning the caller (`find_boundary_objects()`) remains responsible for cleanup regardless of success/failure. The original phrasing had grammatical issues ("but not takes" -> "but does not take") and unclear logical flow in explaining the leak scenario.

The proposed wording makes two improvements: (1) fixes the grammar to properly use "does not take" and (2) more clearly states the consequence - that success paths would leak the bitmap. This maintains the same technical meaning as the original fix (which was already correct in code) while improving documentation.

The thread context shows this is purely a documentation polish for an already-complete series, with Junio Hamano having identified the unclear wording and Lidong Yan proposing the improved version. No code changes are needed as the actual memory safety behavior was correct in the merged version.
