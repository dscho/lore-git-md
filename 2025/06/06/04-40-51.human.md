This is a discussion about the OAuth2.0 authentication implementation in `imap-send`, specifically focusing on the password handling logic for libcurl. The conversation between Aditya Garg and Junio Hamano centers on whether to explicitly check for PLAIN/LOGIN authentication methods rather than the current approach of checking for non-OAuth methods when setting passwords.

Junio suggests the current code appears backwards - it assumes any non-OAuth method should use password authentication, when in reality only PLAIN and LOGIN methods should. He proposes making this explicit in the code. Aditya explains the conservative approach was to avoid potential regressions, as the original code unconditionally set these options even for methods like CRAM-MD5. 

The key points under discussion are:
1. Whether to change the logic to explicitly list supported password methods (PLAIN/LOGIN)
2. The importance of thorough documentation in commit messages to explain the rationale
3. Adding in-code comments to clarify the behavior around CURLOPT_LOGIN_OPTIONS

Aditya agrees to add clarifying comments while preferring to keep the current logic to maintain stability, but leaves the final decision to Junio. This is part of the larger v13 series that adds OAuth2.0 support to `imap-send` while fixing several authentication-related issues. The discussion shows careful consideration of backward compatibility and maintainability concerns.
