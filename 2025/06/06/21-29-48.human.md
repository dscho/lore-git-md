This is a technical follow-up in the ongoing discussion about submodule behavior with non-standard remote names. Jacob Keller is exploring an approach to use the superproject's `.gitmodules` URL directly rather than relying on remote names, but has hit implementation challenges in `remote.c`.

The key issue is that `remote.c` functions that should work with any repository (like those for reading remote config) still internally use the deprecated `the_repository` global. Keller found this in `read_remotes_file` and `read_branches_file` functions, noting they're slated for removal in Git 3.0. He's considering modifying these to properly accept repository pointers.

Keller is seeking guidance on whether such changes would be acceptable, and what approach would be best - adding repository parameters or switching from `remote_state` to repository pointers. He wants to reuse existing remote-handling logic both for URL-based remote matching and single-remote detection, rather than reimplementing this functionality.

This email advances the technical exploration of one solution path (URL-based approach) while surfacing new implementation constraints in Git's remote handling code. The discussion remains focused on implementation strategy rather than revisiting the higher-level design questions about remote naming in submodules.
