Git refs list RFC: Proposal for new `git refs list` subcommand to consolidate ref listing functionality, originally targeting both `git-show-ref` and `git-for-each-ref` as part of a Google Summer of Code project. Current implementation (2-patch series) introduces basic `git refs list` with filtering options and show-ref-style pattern matching, implemented in `builtin/refs.c` using ref iterators with comprehensive tests in `t1461-refs-list.sh`.

Junio C Hamano raised fundamental concerns about the premise, noting `rev-parse --verify` can handle `show-ref`'s key use case (exit status checking for single refs), questioning the need for unification. Meet Soni's follow-up acknowledges this point and shifts discussion to broader consolidation goals, raising two key questions: (1) whether to focus solely on improving `for-each-ref` if `show-ref` is redundant, and (2) what novel value a unified interface could provide beyond replicating existing functionality.

Open questions now span multiple levels: philosophical (whether command consolidation is justified here), strategic (what problems a new command should solve that current tools don't), and technical (how to design such a command if proceeding). The thread has moved from implementation details to fundamental design questions about Git's ref-related command architecture. Core tension remains between maintaining discrete tools with clear purposes versus creating unified interfaces that might simplify workflows but risk command proliferation without clear benefits. Future discussion needs to establish either consensus on the unification premise or pivot to alternative approaches for improving ref-related functionality.
