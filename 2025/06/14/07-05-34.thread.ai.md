Git refs list RFC: Initial proposal and first implementation patch for new `git refs list` subcommand to consolidate ref listing functionality (currently split between `git-show-ref` and `git-for-each-ref`). Part of a Google Summer of Code project. Current implementation (2-patch series) introduces basic `git refs list` with `--branches`/`--tags`/`--head` filtering and show-ref-style pattern matching (suffix-based from refname with complete path components). Implementation adds new `list` subcommand to `builtin/refs.c` using `refs_for_each_*` iterators, includes object existence verification, and preserves show-ref's default behavior of showing all refs when unfiltered. 

The series includes comprehensive tests (95 lines in `t1461-refs-list.sh`) verifying the new command's behavior and its parity with `git show-ref` for supported flags. Tests exercise all implemented features and follow project conventions. Technical implementation appears solid with clean integration into refs command framework.

Junio C Hamano has raised fundamental concerns about the proposal's premise, questioning whether unifying `show-ref` and `for-each-ref` is necessary or desirable. He suggests `show-ref`'s primary advantage (exit status checking for single refs) can be achieved with `rev-parse --verify`, and that the project might be better served by using existing tools rather than adding a new command. This shifts the discussion from implementation details to project philosophy - whether Git benefits from command consolidation in this case.

Open questions now include both technical and philosophical aspects: (1) whether to proceed with unification at all (Hamano's concern), (2) if proceeding, whether to keep show-ref-style matching as default or switch to for-each-ref patterns, (3) how to handle backward compatibility with existing scripts, (4) which features to preserve from both commands, and (5) long-term vision for potentially replacing both existing tools. The technical foundation remains sound but faces new scrutiny about its necessity. Future discussion must address the higher-level concern about command proliferation before proceeding with feature details.
