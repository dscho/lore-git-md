This is a response to a bug report about fsck warnings during cloning. Jeff King explains that the "badFilemode" and "missingTaggerEntry" warnings are expected historical artifacts in git.git's early history, not signs of repository corruption. The warnings stem from non-standardized practices in Git's early days (tags without tagger fields and unusual file modes) that were later formalized.

Key technical details clarified:
- The warnings appear when transfer.fsckObjects or fetch.fsckObjects is enabled
- Specific issues identified: v0.99 tag lacks a tagger field, old trees use mode 100664 instead of standard 100644
- These objects persist in clones due to Git's immutable object model
- Configuration options to suppress these specific warnings are provided

The response also notes an inconsistency: git fsck shows only the tag warning by default, requiring --strict to see badFileMode warnings, while fetch/push always use strict mode. Jeff suggests this behavior deserves review to better classify warning severities (security-critical vs historical quirks), but doesn't propose specific changes.

This effectively resolves the original report by confirming the warnings are harmless historical artifacts while providing workarounds and identifying a potential area for future fsck behavior improvement.
