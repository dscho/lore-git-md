Performance bug in `git rev-list` with multiple paths and commit-graph

Kai Koponen reports a surprising performance regression when using `git rev-list` with multiple paths and the commit-graph feature. With the commit-graph enabled, querying two paths together takes significantly longer (650ms) than the sum of querying each path individually (90ms + 100ms). The issue is reproducible in the Go repository and appears when using path-limiting with a count limit (-10 in the example), where one might expect the combined query to be at least as fast as separate queries.

The commit-graph's changed-path Bloom filters should theoretically help accelerate such path-limited queries, but the current implementation seems to have an optimization gap when handling multiple paths. The behavior is counterintuitive since the count limit should allow early termination when enough commits are found. The report includes clear reproduction steps and timing measurements, making this a well-documented performance issue that warrants investigation.
