This thread introduces a performance optimization for `git fetch --prune` that addresses a significant bottleneck in how dangling refs are detected. The current implementation has a O(N²) time complexity when pruning many refs, which becomes painfully slow at scale (e.g., taking 400+ seconds to prune tens of thousands of refs). The proposed solution replaces this with an O(N*logN) approach borrowed from `git remote prune`, where the prune list is first sorted to enable binary search.

The first patch in this series implements the core optimization, modifying `prune_refs()` in builtin/fetch.c to collect and sort refs before checking for dangling ones. It also improves the warning message format to show both the dangling ref and its former target (with cleaner formatting). The changes maintain identical functionality while reducing runtime dramatically - from minutes to under a second in test cases. Jacob Keller has already reviewed and approved the approach with a Reviewed-by. A second patch will follow to clean up the now-unused old implementation. The changes touch fetch and remote builtins plus refs.c, with a net reduction in code size. This appears to be a straightforward, impactful optimization that leverages proven approach from related functionality.
