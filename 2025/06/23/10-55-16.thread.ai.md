This two-patch series enhances Git's test infrastructure by improving the `test_seq` helper function with a new `-f` format option. The thread began with a discussion about test output readability, leading to Patch 1 cleaning up t7422-submodule-output.sh by replacing confusing `printf` constructs with simpler `echo` commands. Patch 2 adds the `-f` option to `test_seq` that mimics GNU `seq -f` behavior for printf-style formatting of sequence numbers, now including documentation for the new feature as suggested by Justin Tobler.

Junio C Hamano has reviewed and approved Jeff King's implementation, confirming key design choices: using `%d` instead of `%g` for integer sequences, maintaining automatic newline behavior matching GNU seq, and intentionally not supporting multiple format specifiers to avoid complex parsing. Justin Tobler subsequently reviewed the changes, agreeing with the design decisions and prompting the documentation update now included in the implementation. Todd Zullinger raised a potential edge case where numeric format strings could be misinterpreted, proposing (but not insisting on) a `%` character check to fail fast on invalid usage.

Jeff King and Eric Sunshine engaged in a brief exchange about the historical context of printf cleanup in t7422-submodule-output.sh, with Jeff maintaining his echo-based solution offers better readability than both the original printf version and prior cleanup attempts. Eric Sunshine contributed additional historical context in two parts: first noting similar printf cleanup work from April 2025, and later raising performance considerations regarding awk vs shell implementations for different sequence sizes, referencing Patrick Steinhardt's prior rejection of shell-based sequence generation in t0610 due to performance concerns with large sequences (10,000+ items).

In the latest discussion, Jeff King responds to Eric Sunshine's performance concerns with timing data showing the shell implementation outperforms awk at 10,000 items on his system, though acknowledging awk may win at 50,000 items or on loaded systems. He investigates implementation details: awk makes per-item write() calls while the shell version uses built-in echo commands. Jeff advocates prioritizing code clarity over micro-optimization, suggesting the small absolute time differences (milliseconds) make this a reasonable tradeoff given test_seq's typical usage patterns.

Jeff also responds to Todd Zullinger's format string validation suggestion, explaining why he prefers to rely on shell printf's natural handling of invalid input rather than adding explicit checks. Jeff notes this approach preserves flexibility for creative uses like `%%d` or repeated line generation while maintaining implementation simplicity. The tradeoff is that some typos might not be caught immediately but would surface through test failures. This position aligns with the series' overall minimalist design philosophy.

The changes affect 9 test files across multiple subsystems (reftable, submodules, merges), replacing verbose shell loops or awk invocations with simpler `test_seq -f` calls. The implementation has complete documentation following the established design decisions (`%d` formatting, single specifier limitation). While there are some tradeoffs (one test case in t7422 still requires a shell loop, potential performance considerations for very large sequences, and format string validation questions), the consensus is these are reasonable limitations. With no substantive objections raised and both Junio and Justin approving, the implementation is considered complete and ready for merging. The validation and performance discussions remain potential future refinement points if real-world usage demonstrates the need for adjustments.
