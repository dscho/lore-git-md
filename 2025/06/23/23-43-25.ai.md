This is a performance optimization patch series addressing a quadratic-time bottleneck in `git fetch --prune`. The issue occurs when checking for dangling refs during pruning operations, where the current implementation makes O(N^2) string comparisons when pruning many refs.

The key problem is that the current code uses a nested loop comparing each prune candidate against all refs, which becomes extremely slow with large numbers of refs (e.g., 2.6 billion strcmp calls when pruning 15k refs from 174k total). The patch replaces this with a more efficient O(N*logN) approach already used by `git remote prune`, where the prune list is first sorted to enable binary search.

The second patch removes the now-unused old implementation of dangling ref warning. The author notes they've improved the output formatting slightly to maintain clarity despite the changed ordering, though this was not strictly necessary since `git remote prune` already accepted similar output.

The changes touch the fetch and remote builtins plus refs.c, with a net reduction of 29 lines. The performance impact is dramatic - from 470 seconds to under 1 second in the reported test case. This appears to be a well-motivated optimization addressing a clear performance pain point, with the solution borrowing from an existing proven approach in related functionality.
