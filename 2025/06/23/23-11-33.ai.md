This is part 5 of a 7-part series refactoring submodule remote lookup logic, continuing the effort to remove `the_repository` usage. The patch focuses on improving the fallback behavior for determining a submodule's default remote name.

The key change refactors `repo_get_default_remote()` to use the existing `remotes_remote_for_branch()` logic, which provides better handling of cases where the remote name isn't "origin". The new implementation first checks the branch's configured remote, then falls back to using the sole remote if only one exists, before finally defaulting to "origin". This is more robust than the previous hardcoded "origin" fallback.

The patch introduces a new `repo_default_remote()` function in remote.c that encapsulates this logic while being repository-aware (taking a `struct repository*` parameter). It replaces all callers of the old function with this new one. The implementation involves:
- Moving branch lookup into a new `repo_branch_get()` helper
- Using `remotes_remote_for_branch()` for the actual remote determination
- Maintaining the existing behavior of returning an allocated string via xstrdup()

A new test case verifies the behavior works when the remote has been renamed from "origin" to something else. The test creates a multi-level submodule structure, renames the remote in the middle submodule, and confirms `submodule update` still works correctly.

This change is part of the broader effort to make submodule remote handling more robust and repository-agnostic. It builds on previous patches in the series that refactored remote and branch handling to work with repository pointers rather than assuming `the_repository`. The test coverage helps ensure the new behavior works as intended while maintaining compatibility with existing configurations.
