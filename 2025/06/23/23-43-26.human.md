Performance optimization patch that dramatically speeds up `git fetch --prune` operations by eliminating a quadratic-time bottleneck in dangling ref detection.

The current implementation checks each pruned ref against all local refs one by one, leading to O(M*N) complexity where M is pruned refs and N is total refs. In a real-world case with 126k refs (28k being pruned), this caused 3.6 billion strcmp calls and took 410 seconds - often causing remote timeouts. The patch replaces this with the same O(N*logM) approach already used by `git remote prune`, first sorting the prune list to enable binary search.

The change touches fetch.c, remote.c and refs.c, with a net reduction of 13 lines. Performance impact is dramatic - the same operation now completes in under 1 second. The patch also improves the dangling ref warning messages to be more explicit about which refs are affecting others, though this is a secondary benefit compared to the performance gains.

This is part of a 2-patch series (1/2 here) that removes the old implementation entirely in the follow-up. The approach borrows proven code from related functionality and has already been reviewed by Jacob Keller. The changes look solid and address a clear pain point in large repositories.
