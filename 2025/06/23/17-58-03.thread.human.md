This thread explores a performance optimization opportunity in Git's commit-graph bloom filters when used with `git rev-list --changed-paths` for multiple pathspec queries. The initial report from Kai Koponen highlighted a 3x slowdown when querying two paths together versus separately in the Go repository. Junio C Hamano explained this is by design - the current implementation intentionally disables bloom filters for multiple pathspecs due to technical constraints.

The discussion has since progressed to analyze the underlying mechanisms. The key insight, confirmed by both Lidong Yan and Junio, is that the current bloom filter implementation uses AND logic (requiring all queried paths to match) when multiple paths are specified, whereas the desired behavior requires OR semantics (matching any path). The technical focus has narrowed to two core functions - `prepare_to_use_bloom_filter()` and `forbid_bloom_filters()` - which would need modification to support this.

The solution path is now clearer but involves non-trivial changes: restructuring how bloom keys are stored (currently two keys per path in a single array) and modifying the results combination logic. Any implementation would need to maintain the existing single-path optimization while adding efficient OR-semantics support for multiple paths. The thread remains open for bloom filter experts to propose specific implementation approaches that meet these requirements.
