This thread examines a performance anomaly in `git rev-list --changed-paths` when filtering by multiple paths. Kai Koponen initially reported that querying two paths (`src/clean.bash` and `src/Make.dist`) in the Go repository took 650ms, while querying them individually summed to only 190ms - a surprising 3x slowdown despite count limits that should enable early termination. The issue persisted across different Git versions and count limits, suggesting a fundamental inefficiency in multi-path filtering.

Junio C Hamano clarified that this is expected behavior, not a bug. The commit-graph's bloom filters, which enable the fast path for single-path queries, are intentionally disabled when multiple paths are specified - a design constraint documented in the code (`forbid_bloom_filters()` in revision.c). This explains why the performance doesn't scale linearly and why early termination optimizations don't apply to multi-path queries. While this settles the immediate question about the current behavior, it leaves open whether the design could be extended to handle multiple paths more efficiently in future versions. The discussion provides clear technical grounding for both the current limitations and potential future optimization opportunities in path filtering.
