This thread explores a performance issue with `git rev-list --changed-paths` when filtering by multiple paths in commit-graphs using bloom filters. Kai Koponen initially reported that querying two paths in the Go repository took 650ms while individual queries summed to 190ms. Junio C Hamano explained this is expected behavior - the commit-graph's bloom filters are intentionally disabled for multiple pathspecs, as documented and enforced by `forbid_bloom_filters()`.

The discussion has evolved into a technical exploration of potential optimizations. Junio noted the existing `bloom_keys[]` array structure could theoretically accommodate multiple paths by adding more keys, while cautioning about implementation complexity. Lidong Yan's contribution clarified a key insight: the current implementation creates an AND condition (requiring all paths to match), whereas the desired behavior for multiple pathspecs requires an OR condition (matching any path). This explains why simply extending the key storage wouldn't solve the problem.

The thread has now precisely identified two key challenges for any future optimization: the key storage mechanism in `revs->bloom_keys[]` and the logical operation being performed. While the discussion remains open-ended, participants are maintaining a clear understanding of the current design constraints while exploring avenues for improvement. The focus has shifted from a simple performance report to a deeper technical discussion about bloom filter implementation details.
