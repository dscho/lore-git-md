This is a performance optimization thread for `git fetch --prune` with large ref counts. The discussion has now shifted to finalizing the wording of warning messages about dangling symrefs after pruning.

Junio C Hamano responds to Jacob Keller's observation about the "will become dangling" phrasing in the --dry-run output being temporally confusing since the deletion hasn't actually occurred yet. Hamano notes this phrasing makes sense specifically for --dry-run mode, implying the non-dry-run version should use present-tense wording like "is now dangling" since the deletion has actually occurred.

This represents the last remaining point of discussion in what has otherwise been a well-received optimization series. The technical approach (switching from O(N^2) to O(N*logN) performance) has been validated by multiple reviewers, with Jeff King providing detailed technical analysis and Jacob Keller giving a Reviewed-by. The only outstanding issue is this minor wording refinement for the warning messages, which appears to be converging on using "will become" for --dry-run and "is now" for actual execution.

Key technical details at play:
- The warning messages are generated by refs_warn_dangling_symrefs()
- The output format is being made more explicit about which deleted ref caused the dangling state
- The distinction between --dry-run and actual execution output is being clarified
- The changes build on the already-approved ref-handling optimizations in the series

The thread shows consensus forming around accepting these changes, with only this final wording polish remaining before likely integration into mainline.
