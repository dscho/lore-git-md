Performance optimization for `git fetch --prune`'s dangling ref reporting. This patch series addresses a severe O(N^2) performance issue in the command's current implementation, where checking for dangling ref could take nearly 8 minutes (470 CPU seconds) when pruning 15,000 refs from a repository with 174,000 refs.

The core problem stems from an inefficient nested loop that compares every pruned ref against every existing ref. The solution borrows a more efficient O(N*logN) approach already used by `git remote prune`, which first sorts the refs to enable binary search. The patches also include minor output formatting improvements to maintain consistency with the new processing order.

The changes touch the fetch and remote builtins along with the refs subsystem, removing the old slow implementation entirely. While the performance gains are dramatic (reducing runtime from minutes to under a second), the functional behavior remains the same except for slightly more explicit output about deleted branches when reporting dangling symrefs.
