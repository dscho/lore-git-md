Feature improvement in submodule remote lookup, completing a series that refactors submodule remote handling to be repository-agnostic and more robust against remote name changes. This final patch introduces URL-based remote matching as a fallback when the default remote name lookup fails.

The patch adds a new `repo_remote_from_url()` helper that scans a repository's remotes for one matching a given URL. This is used in `get_default_remote_submodule()` to first try matching the submodule's configured URL against the parent project's remotes before falling back to the existing `repo_default_remote()` logic. The change makes submodule updates work correctly when users rename their default remote (e.g., via `clone.defaultRemoteName`) while maintaining the existing behavior when URL matching isn't possible.

Key technical details:
- New `repo_remote_from_url()` in remote.c iterates through remotes using existing `remote_has_url()` check
- `get_default_remote_submodule()` now resolves relative URLs and attempts URL matching first
- Falls back to existing branch/remote lookup if URL matching fails
- Includes test case demonstrating successful update with renamed remote
- Touches remote.h, remote.c, builtin/submodule--helper.c, and test scripts
- Builds on previous series work to make remote handling repository-aware

The change completes the series' goal of making submodule remote handling more robust while removing `the_repository` assumptions. The test coverage verifies the new URL-based lookup works with renamed remotes while maintaining backward compatibility. The implementation appears clean with proper memory management (freeing URL strings) and builds on the preparatory refactoring from earlier patches.
