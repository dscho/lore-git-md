Performance issue with `git rev-list --changed-paths` path filtering in commit-graph. Kai Koponen follows up on their initial report with additional system information and version details, confirming the performance anomaly persists in Git 2.50.0. The email provides concrete reproduction steps showing that querying two paths together (`src/clean.bash` and `src/Make.dist`) takes 650ms, while querying them individually sums to only 190ms (90ms + 100ms) in the Go repository. This disproportional slowdown occurs despite the presence of a count limit (`-10`) that should theoretically allow early termination.

The issue appears fundamental to the commit-graph's path filtering implementation, as it manifests across different count limits (-1, -10, unlimited) and shows the same relative slowdown (though absolute times vary). Koponen's expectation is that multi-path queries should take no longer than the sum of individual path queries, and ideally less due to potential early termination opportunities when searching for multiple paths simultaneously.

The email includes detailed system configuration showing the test environment uses Git built with GCC 14.2, glibc 2.41, and OpenSSL 3.4.1 on x86_64. While this provides useful context for reproduction, it doesn't suggest any environment-specific factors contributing to the issue. The problem appears to be algorithmic in nature, likely in how the commit-graph handles the intersection of multiple path filters during traversal.
