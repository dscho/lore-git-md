Performance issue with `git rev-list --changed-paths` path filtering in commit-graph. Kai Koponen initially reported and analyzed a performance anomaly where querying multiple paths (`src/clean.bash` and `src/Make.dist`) in the Go repository took 650ms while individual queries summed to 190ms. Junio C Hamano clarified this is expected behavior - the commit-graph's bloom filters are intentionally disabled for multiple pathspecs as documented, enforced by `forbid_bloom_filters()` in revision.c (lines 674-686). 

Kai Koponen acknowledged this design but suggested potential for sequential bloom filter checks per path. Junio Hamano responded with technical analysis, identifying `prepare_to_use_bloom_filter()` and `forbid_bloom_filters()` as key functions needing modification. He noted the existing `bloom_keys[]` array structure (using two keys per path - directory and full path) could theoretically accommodate multiple paths by adding more keys. Lidong Yan's technical follow-up clarified a critical constraint: the current `bloom_keys[]` implementation creates an AND condition (requiring all paths to match), whereas multiple pathspec queries require OR semantics. This explains why simply extending the key array wouldn't work - the logical operation would remain incorrect.

The discussion frames this as a potential feature request requiring careful implementation to preserve single-path optimization benefits while addressing both the key storage mechanism and logical operation challenges. Technical focus remains on `prepare_to_use_bloom_filter()` and `forbid_bloom_filters()` functions, with open questions about how to implement OR semantics efficiently without regressing single-path performance. Junio's invitation for bloom filter expert review remains open, with the problem space now more precisely scoped to include both storage representation and logical operation requirements.
