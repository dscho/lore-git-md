Performance issue with `git rev-list --changed-paths` path filtering in commit-graph. Kai Koponen initially reported a performance anomaly in the Go repository where multi-path queries (650ms) were slower than summed single-path queries (190ms). Junio C Hamano confirmed this is expected due to bloom filters being disabled for multiple pathspecs via `forbid_bloom_filters()` in revision.c (674-686). 

Technical discussion has centered on two key constraints: (1) the current `bloom_keys[]` array structure (two keys per path) creates AND semantics, while OR semantics are needed for multiple pathspecs, and (2) both `prepare_to_use_bloom_filter()` and `forbid_bloom_filters()` would need modification. Lidong Yan identified the fundamental logical operation mismatch, which Junio confirmed in this follow-up, noting that supporting OR semantics would require restructuring to maintain separate bloom key arrays per pathspec element. 

Core functions requiring changes include:
- `bloom_filter_contains()` (logical operation handling)
- `check_maybe_different_in_bloom_filter()` (result combination)
- `release_revisions()` (memory management of restructured key storage)

The solution path is now technically scoped but non-trivial, needing careful implementation to preserve single-path optimization benefits while adding multi-path OR semantics. Open questions remain about the most efficient storage representation and whether the bloom filter's probabilistic nature complicates multi-path queries. Junio's invitation for bloom filter expert review stands, with the problem space clearly defined around both storage architecture and logical operation requirements.
