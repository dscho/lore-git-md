Performance optimization patch series addressing quadratic-time bottleneck in `git fetch --prune` when checking for dangling refs during pruning operations. Current implementation makes O(N^2) string comparisons when pruning many refs (e.g., 2.6-3.6 billion strcmp calls when pruning 15k-28k refs from 126k-174k total). Solution replaces nested loop with O(N*logN) approach from `git remote prune` by first sorting prune list to enable binary search. First patch modifies `prune_refs()` in builtin/fetch.c to collect refs in sorted string_list before checking for dangling refs. Second patch removes now-unused old implementation `refs_warn_dangling_symref()` from refs.c (17 lines deleted). Performance impact dramatic - from 410-470 seconds to under 1 second in test cases. Output formatting improved to show both dangling ref and what it pointed to (with "refs/remotes/" prefix stripped for readability), maintaining clarity despite changed ordering. Solution borrows proven approach from related functionality in `git remote prune`. Includes Reviewed-by from Jacob Keller. Series complete with both optimization and cleanup patches now submitted.

Jeff King (peff) reviews implementation details, raising two considerations: (1) The printf-style interface for reporting dangling refs may be fragile as it requires exact format string matching between callers; suggests passing indentation/dry-run flags directly instead, though acknowledges current approach may suffice given only two callers. (2) The ad-hoc stripping of "refs/remotes/" prefixes in output differs from standard ref shortening behavior; recommends using refs_shorten_unambiguous_ref() for consistency, though doesn't insist on immediate change. Review maintains positive trajectory while identifying potential refinements to interface design and output formatting that could be addressed now or in future cleanup. No major objections raised to core optimization approach.
