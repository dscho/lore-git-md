Security vulnerability in Git's Bash completion allowing shell command injection via branch names containing special characters (specifically `>` redirection operator). Reported by Ondrej Pohorelsky. When creating and switching to branches with `>` in their names, Bash tab completion interprets the character as a shell redirection operator rather than part of the branch name, leading to unintended file creation (demonstrated with `>/tmp/dangerfile`). The branch creation itself works but creates unusual ref paths. Zsh properly escapes special characters during completion.

Kristoffer Haugsbakk initially proposed extending `git-check-ref-format` to disallow `>` characters in refnames entirely as a hardening measure. Phillip Wood responded that the root issue lies in the completion script's failure to properly quote refnames containing shell metacharacters, not in the refname format itself, noting Git's ref format already permits numerous other potentially problematic characters (`<`, `$`, `&`, `;`, etc.) that would need similar escaping in shell contexts.

Junio Hamano firmly agrees with Wood's position, characterizing this as purely a completion code bug requiring proper shell metacharacter escaping rather than a refname validation issue. The maintainer's guidance settles the architectural debate, establishing consensus that the fix should focus on proper quoting in `git-completion.bash` while maintaining Git's flexible refname character allowances for backward compatibility. No patches have been proposed yet, but the expected solution path is now clear: modify the Bash completion script to escape special characters during tab completion, particularly for branch name operations. The issue remains open for implementation, with the specific location in the completion code still to be identified. Reproduction shows the vulnerability affects Git 2.49 on Fedora and likely other versions/distributions using Bash completion.
