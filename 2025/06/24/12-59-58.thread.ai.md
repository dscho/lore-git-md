Security vulnerability in Git's Bash completion allowing shell command injection via branch names containing special characters (specifically `>` redirection operator). Reported by Ondrej Pohorelsky. When creating and switching to branches with `>` in their names, Bash tab completion interprets the character as a shell redirection operator rather than part of the branch name, leading to unintended file creation (demonstrated with `>/tmp/dangerfile`). The branch creation itself works but creates unusual ref paths. Zsh properly escapes special characters during completion.

Kristoffer Haugsbakk initially proposed extending `git-check-ref-format` to optionally disallow `>` characters in refnames entirely as a hardening measure beyond just fixing the Bash completion issue. Phillip Wood responded that the root issue lies in the completion script's failure to properly quote refnames containing shell metacharacters, not in the refname format itself. Wood notes Git's ref format already permits numerous other potentially problematic characters (`<`, `$`, `&`, `;`, etc.) that would need similar escaping in shell contexts, suggesting fixing the completion script's quoting behavior is more appropriate than restricting refname characters at the validation level. This maintains backward compatibility while addressing the security issue.

The discussion highlights the tension between security hardening and maintaining flexible refname conventions, with Wood advocating for proper escaping in the interface layer (completion scripts) rather than changing the data model layer (refname validation). No patches have been proposed yet, but the architectural position is now clearer: shell safety should be handled where shell interpretation occurs. Reproduction steps show branch name misinterpretation as shell command with redirection. Affects Git 2.49 on Fedora, likely impacts other versions/distributions using Bash completion. Exact location in Git's completion code requiring fix remains unidentified.
