This is a follow-up discussion about the `test_seq -f` feature implementation in the test infrastructure. Jeff King responds to Todd Zullinger's suggestion about adding validation for the format string in `test_seq -f`.

The key points are:
1. Todd had proposed adding a check to ensure the format string contains a `%` character to catch typos where users might accidentally pass a number as the format string (e.g., `test_seq -f 1 5`).
2. Jeff notes that while GNU seq does similar validation, Git's implementation relies on shell printf behavior which would handle garbage input safely.
3. Jeff points out the proposed check might incorrectly reject valid cases like `%%d` or prevent creative uses like `test_seq -f "same line" 50` to generate repeated lines.
4. Regarding the usage note suggestion from Justin, Jeff prefers keeping the implementation simple rather than adding validation, though acknowledges this might be seen as lazy.

The discussion reveals some tradeoffs in the design - stricter validation could prevent typos but might also limit valid use cases. Jeff's position leans toward minimalism, accepting that edge cases would be caught by test failures rather than upfront validation. This maintains the current implementation's simplicity while leaving open the possibility of adding validation later if real-world usage demonstrates the need.
