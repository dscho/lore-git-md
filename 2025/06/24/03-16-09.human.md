This is a technical discussion about optimizing path filtering in commit-graph's bloom filters. Lidong Yan responds to Junio Hamano's analysis of Kai Koponen's performance feature request, pointing out a key logical mismatch in the current implementation. The discussion centers on how multiple pathspec queries currently work as an AND operation (requiring all paths to match) when an OR operation (any path matching) would be more useful for the common case of checking multiple changed paths.

Lidong identifies the core issue: the `revs->bloom_keys[]` array currently implements an AND condition between paths, which is too restrictive for the intended use case. They note this explains why checking paths individually (190ms total) is faster than checking them together (650ms) - the combined query is effectively looking for commits that modified all specified files rather than any of them.

The email suggests this isn't just an implementation detail but a fundamental design consideration for how bloom filters should handle multiple pathspecs. The discussion remains technical and constructive, with Lidong building on Junio's earlier analysis while introducing this new perspective about the logical operation being performed.
