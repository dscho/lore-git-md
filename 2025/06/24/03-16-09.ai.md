This is a technical discussion about optimizing path filtering in commit-graph bloom filters. Lidong Yan responds to Junio Hamano's analysis of Kai Koponen's performance feature request, identifying a key misunderstanding in how the bloom filter keys currently work.

The core issue is that the current implementation using `revs->bloom_keys[]` creates an AND condition (requiring all paths to match), whereas the desired behavior for multiple pathspecs requires an OR condition (matching any of the specified paths). Yan points out this explains why the current implementation can't simply be extended by adding more keys - the logical operation would remain incorrect.

The discussion remains focused on the technical implementation details, particularly around the `prepare_to_use_bloom_filter()` and `forbid_bloom_filters()` functions Junio previously identified. Yan's contribution clarifies that any solution would need to address both the key storage mechanism and the logical operation being performed, suggesting this may be more complex than initially thought. The thread continues to explore potential optimizations while maintaining awareness of the current design constraints.
