Git daemon signal handling and child process tracking redesign (v4/RFC) continues with three competing approaches: SA_RESTART toggling (original series), documentation-only (Phillip Wood), and pipe-based tracking (RFC). Core issues involve platform-specific signal behaviors (SA_RESTART, EINTR) and child process cleanup races, complicated by Windows SIGCHLD inconsistencies.

Current technical landscape:
1. Original SA_RESTART approach (Carlo Marcelo Arenas Belon):
   - set_sa_restart() helper in daemon.c
   - Platform-specific poll() interruption handling
   - Windows sigaction() behavior (errno=EINVAL vs signal())
   - Autoconf SA_RESTART detection (new patch)
     - AC_CACHE_CHECK for signal.h support
     - Sets NO_RESTARTABLE_SIGNALS=UnfortunatelyYes when unavailable
     - Junio noted variable naming inconsistency (ac_cv_siginterrupt vs NO_RESTARTABLE_SIGNALS)

2. Minimal documentation approach (Phillip Wood):
   - Remove SA_RESTART manipulation
   - Document platform behaviors
   - Rely on git-daemon's EINTR handling

3. Pipe-based tracking RFC (now refined with Phillip Wood's detailed feedback):
   - `parent_ipc_in` field in `struct child_process`
   - Child closes pipe descriptor to notify parent
   - Parent monitors pipes via poll() (signal-free)
   - Dynamic pollfd array with O(n) scanning
   - Windows currently excluded
   - Latest refinements from discussion:
     * Renaming `poll_pipe` -> `signal_pipe` (Phillip's suggestion)
     * Signal handler placement debates (beginning vs end)
     * Moving `signal(SIGCHLD)` call from handler to event loop (Phillip's AIX recursion fix)
     * Proper EINTR handling in write() (Phillip's maintainability concern)
     * Pipe creation failure handling debate (optional vs mandatory/die())
     * SIGPIPE considerations with sigaction
     * Keeps pipe FD open despite FD_CLOEXEC failure (safe leak)
     * Considering per-child pipes vs single daemon-wide pipe (Junio's observation)
   - Phillip advocates for stronger guarantees: mandatory pipes, explicit error handling
