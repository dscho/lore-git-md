This thread continues the discussion about redesigning Git daemon's signal handling and child process tracking, with three main approaches under consideration: toggling SA_RESTART flags, documenting platform behaviors, or implementing a new pipe-based tracking system. The latest email focuses on build system preparation for the SA_RESTART approach, with Junio Hamano reviewing Carlo Marcelo Arenas Belón's patch that adds autoconf detection for SA_RESTART support.

The patch introduces a test to check for SA_RESTART availability at configure time, setting NO_RESTARTABLE_SIGNALS if unsupported. Junio noted a quirk where the test fails when SA_RESTART is defined (due to malformed text) but succeeds when undefined, and raised questions about variable naming consistency between the autoconf cache and makefile. This appears to be groundwork that would be useful regardless of which approach is ultimately chosen, as even the documentation-based solution would benefit from knowing platform capabilities.

The core debate remains unresolved, with the pipe-based approach now having two implementation patches but still lacking Windows support. Key open questions include resolving the EINTR safety debate, evaluating the pipe method's performance characteristics, and determining Windows compatibility strategies. The thread shows active technical engagement from Carlo, Phillip Wood, and Junio, with the build system work suggesting the SA_RESTART approach remains under serious consideration alongside the newer pipe-based alternative.
