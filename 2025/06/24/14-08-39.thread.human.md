This thread explores three competing approaches to redesigning Git daemon's signal handling and child process tracking, with the core challenge being platform-specific behaviors around signals (SA_RESTART, EINTR) and race conditions in child cleanup. The original SA_RESTART approach by Carlo Marcelo Arenas Belón now includes autoconf detection for SA_RESTART support, while Phillip Wood advocates a minimal documentation-only solution. A third, more radical pipe-based tracking approach has emerged as an RFC, which would eliminate signals entirely by using pipes to monitor child processes.

The latest email shows Carlo responding to Phillip's detailed review of the pipe implementation. Carlo defends several design choices while incorporating feedback, such as considering renaming `poll_pipe` to `signal_pipe` and addressing pipe write() error handling. The discussion remains technical and constructive, with Carlo explaining why keeping pipes open even if FD_CLOEXEC fails wouldn't harm child processes, and debating signal handler placement for portability. Notably, the pipe approach solves both the original race condition and AIX recursion issues that plagued other solutions.

Junio C Hamano has been reviewing the SA_RESTART detection implementation details while noting variable naming inconsistencies. The thread now awaits comparative analysis of all three approaches, with the pipe-based solution gaining traction as it addresses multiple issues simultaneously. Performance implications of the pipe-per-child model remain an open question, particularly regarding FD overhead and O(n) scanning with many children. Windows support also needs resolution, as the current pipe implementation excludes Windows due to platform differences.
