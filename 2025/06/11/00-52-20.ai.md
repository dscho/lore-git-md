This is the final patch in a 6-part series refactoring Git's submodule remote lookup logic, introducing URL-based remote matching as the primary lookup method before falling back to existing heuristics.

The patch adds a new `repo_remote_from_url()` helper that scans a repository's remotes to find one matching a given URL. It modifies `repo_get_default_remote()` to accept an optional URL parameter, using this new helper when provided before falling back to the existing logic (branch-based lookup, then single-remote check, then "origin" fallback). The submodule helper is updated to first try finding a remote matching the submodule's configured URL (resolving relative URLs if needed) before proceeding with the previous fallback chain.

The change addresses cases where users rename their default remote (e.g., via `clone.defaultRemoteName`), preventing submodule updates from failing due to looking for a non-existent "origin" remote. The implementation maintains the existing fallback paths as a safety net for cases where the submodule's URL has been manually changed. New test cases verify behavior with renamed remotes and multiple remotes.

Key technical details for future reference:
- New `repo_remote_from_url()` in remote.c scans `repo->remote_state->remotes` for URL matches
- Modified `repo_get_default_remote()` signature adds `const char *url` parameter
- `get_default_remote_submodule()` now resolves relative URLs using `resolve_relative_url()`
- Tests in t7406 verify behavior with renamed/multiple remotes
- Maintains all existing fallback paths for backward compatibility

This completes the series' goal of improving submodule remote handling, building on the earlier infrastructure work and crash fixes while introducing more robust URL-based remote resolution.
