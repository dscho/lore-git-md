Refactoring and improving Git's submodule remote lookup logic through a 6-part series. The changes begin with infrastructure work: moving helper functions to dir.h (starts_with_dot_slash() and starts_with_dot_dot_slash() helpers consolidated from submodule--helper.c and submodule-config.c into dir.h as static inline functions with PATH_MATCH_XPLATFORM support). Part 2 focuses on removing `the_repository` dependencies from remote.c functions, converting `read_remotes_file()`, `read_branches_file()`, `remotes_remote_get_1()`, and related functions to accept a `struct repository*` parameter instead of using the global `the_repository`.

Part 3/6 fixes a crash in `branch_release()` during repository teardown when handling uninitialized branch merge state, addressing a subtle issue where `branch->merge` array could be accessed without checking for NULL despite `merge_nr` being non-zero. This occurs when remote state initialization creates branches with non-zero `merge_nr` but NULL `merge` array, and the fix enables safer submodule repository initialization.

Part 4/6 improves fallback remote name logic when submodules are in detached HEAD state, moving away from hardcoding "origin" as the fallback. It introduces a new `repo_default_remote()` helper in remote.c that reuses `remotes_remote_for_branch()` logic, providing more robust fallback handling by checking the branch's configured remote first, then looking for a single remote, before falling back to "origin". The submodule--helper code is simplified to use this new helper rather than implementing its own similar-but-different logic. A new test case in t7406 verifies behavior with renamed remotes.

Part 5/6 performs a mechanical relocation of `get_default_remote_submodule()` in builtin/submodule--helper.c to appear after `resolve_relative_url()`, preparing for future changes where it will depend on that function. This is purely code reorganization with no behavioral impact - the function is moved verbatim from one location to another in the same file. The commit explains this preparatory work will make future refactoring easier to review by separating mechanical relocation from functional changes.

The final patch (6/6) introduces URL-based remote matching as the primary lookup method before falling back to existing heuristics. It adds a new `repo_remote_from_url()` helper that scans a repository's remotes to find one matching a given URL. It modifies `repo_get_default_remote()` to accept an optional URL parameter, using this new helper when provided before falling back to the existing logic (branch-based lookup, then single-remote check, then "origin" fallback). The submodule helper is updated to first try finding a remote matching the submodule's configured URL (resolving relative URLs if needed) before proceeding with the previous fallback chain.

The change addresses cases where users rename their default remote (e.g., via `clone.defaultRemoteName`), preventing submodule updates from failing due to looking for a non-existent "origin" remote. The implementation maintains the existing fallback paths as a safety net for cases where the submodule's URL has been manually changed. New test cases verify behavior with renamed remotes and multiple remotes.

Key technical details for future reference:
- New `repo_remote_from_url()` in remote.c scans `repo->remote_state->remotes` for URL matches
- Modified `repo_get_default_remote()` signature adds `const char *url` parameter
- `get_default_remote_submodule()` now resolves relative URLs using `resolve_relative_url()`
- Tests in t7406 verify behavior with renamed/multiple remotes
- Maintains all existing fallback paths for backward compatibility
