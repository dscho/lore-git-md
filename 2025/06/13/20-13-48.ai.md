Platform compatibility follow-up discussion about CI testing for Solaris builds.

Jean-Noël AVILA raises an important question about preventing future Solaris build regressions by suggesting the implementation of CI testing for such platforms. This comes after the thread's successful resolution of two Solaris-specific build issues (sed's `-E` flag incompatibility and newline handling in version-def.h generation) that were caught only after being reported by Solaris users.

The email references Collin Funk's verification that Junio Hamano's patch successfully resolved both issues, producing identical output on Solaris 10 and Linux systems. While the immediate technical problems are solved, Jean-Noël points to a systemic issue - these regressions were introduced unknowingly, suggesting the need for automated detection.

This proposal touches on several practical considerations from earlier thread discussion:
1) The varying availability of GNU tools across Solaris versions (base in Solaris 11 vs optional in Solaris 10)
2) The preference established in this thread for solutions that work with native tools rather than requiring GNU alternatives
3) The broader context of Solaris' non-standard tools causing similar issues in the past

The suggestion implies either:
- Solaris CI runner in Git's existing infrastructure
- Alternative approach like compile-time feature detection
- Documentation of platform-specific requirements

No technical implementation is proposed yet, but the email serves as a prompt for discussion about long-term solutions to catch similar platform-specific issues earlier in the development cycle. The thread's prior consensus on portable solutions would likely inform any CI approach, favoring tests that verify behavior with standard tools rather than assuming GNU extensions.
