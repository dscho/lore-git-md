This is the second patch in a bugfix series addressing batched reference updates, specifically handling D/F conflicts in `git receive-pack`. The patch builds on prior work that fixed similar issues in `git fetch`.

The core change restructures `execute_commands_non_atomic()` in `builtin/receive-pack.c` to process reference deletions in a separate transaction phase from other updates, using a new `processing_phase` enum (PHASE_DELETIONS/PHASE_OTHERS). This mirrors the solution used in `git fetch` to avoid D/F conflicts that arise when batched updates process a deletion and creation of conflicting paths simultaneously. The implementation now lazily creates transactions only when needed and maintains the same safety guarantees while being more efficient than the pre-batched approach.

Key technical details include:
- The phase-based processing ensures deletions happen before creations
- Transactions are now created only when updates exist (lazy creation)
- Test coverage in `t/t5516-fetch-push.sh` verifies the D/F conflict resolution works correctly
- Hook output now consistently shows deletions before updates (visible in the test expectation changes)

The patch represents the final polished version after four rounds of review, incorporating all feedback around terminology ("D/F conflict" standardization), code structure (replacing the `only_deletions` flag with phases), and test coverage. It builds on commits 9d2962a7c4 (original batched updates) and 23fc8e4f61 (related fetch fix).

This completes the series' goal of making batched reference updates production-ready by addressing the last known edge cases from GitLab's Gitaly service experience. The solution maintains performance benefits (still using fewer transactions than sequential mode) while properly handling directory/file conflicts.
