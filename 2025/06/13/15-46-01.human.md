This is a follow-up discussion on a bugfix patch in Patrick Steinhardt's series addressing batched reference updates. The patch in question handles D/F conflicts in `git receive-pack` by separating reference deletions into their own transaction phase.

Junio Hamano acknowledges the patch's technical merit but raises important concerns about the long-term solution. While the current two-phase approach (deletions first, then other updates) improves upon the previous behavior, it still leaves the system in a non-atomic state if the second phase fails. Hamano suggests adding a NEEDSWORK comment to document this limitation and proposes a test_expect_failure case to track the known issue.

The discussion highlights an inherent tension in the batched updates feature - while the current solution makes things better than before (using fewer transactions than the sequential approach would), it doesn't fully deliver on the promise of atomic reference updates. The patch is being queued as-is, but with clear recognition that deeper refactoring will be needed to properly handle these cases within a single transaction.

This exchange shows the careful balance between shipping practical improvements now versus waiting for perfect solutions, with maintainers ensuring the limitations are properly documented for future work.
