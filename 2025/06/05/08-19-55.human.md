Bugfix for batched reference updates in `git receive-pack`. This is the second patch in a v2 series addressing edge cases found in GitLab's production use of batched reference updates.

The patch fixes a filesystem directory/file conflict case that occurs when pushing both a deletion (e.g. `refs/heads/branch/conflict`) and creation (e.g. `refs/heads/branch`) in the same batch. Previously, these would fail when processed together in a batched transaction. The solution splits reference updates into two phases - first processing all deletions, then other updates - matching the approach used in `git fetch`.

The implementation introduces a `PHASE_DELETIONS`/`PHASE_OTHERS` system in `execute_commands_non_atomic()` that processes the commands in two separate transactions. While this means `receive-pack` now always uses exactly two transactions (rather than potentially more without batching), it maintains the performance benefits of batched updates while avoiding the F/D conflicts.

Test coverage is added in `t/t5516-fetch-push.sh` to verify the fix works for the conflict case. The patch also updates hook output ordering in several existing tests to reflect the new processing sequence (deletions first). This builds on earlier work in commit 9d2962a7c4 that introduced batched updates to `receive-pack`.

The change appears well-considered, with clear motivation from production experience and alignment with the established solution in `git fetch`. The phase-based approach addresses Junio Hamano's earlier readability concerns about the v1 implementation.
