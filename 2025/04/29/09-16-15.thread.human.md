This thread focuses on Leon Michalak's work to unify how diff context is handled between interactive patch operations (like `git add -p`) and regular diff output. The core idea is to have these interactive commands inherit the `diff.context` and `diff.interhunkcontext` configurations consistently, similar to how `diff.algorithm` works.

Junio Hamano provided key technical guidance, suggesting using `-1` as an internal sentinel value to represent unset contexts (since negative values are invalid for actual diffs). This maintains the current defaults (3 lines of context, 0 for interhunk spacing) when no value is specified. Leon has accepted this approach, though he noted a minor edge case where someone could explicitly pass `--unified=-1` which would be treated as no value - but concluded this isn't a practical concern.

The main remaining architectural question is where to place the validation layer for these values - whether in the UI or core diff machinery. Phillip Wood had earlier raised concerns about dynamic context changes (via `GIT_DIFF_OPTS`), but that discussion has been deferred for now. The implementation is moving forward with initializing contexts through `repo_diff_setup` while preserving the ability to override via command-line flags. The thread shows careful attention to both technical details and architectural boundaries in the diff subsystem.
