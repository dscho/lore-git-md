This is a clarification response in the ongoing object store refactoring series, specifically addressing Junio Hamano's question about collision checks in patch 7/13. Patrick Steinhardt explains why fetching promisor objects for collision checks is problematic.

The key point is about trust models in object verification. Patrick agrees with Junio's interpretation that the current behavior creates an inconsistent trust model - it should either trust the first-seen object (current fetch source) or verify against all remotes, not just promisors. The current implementation effectively treats promisors as more trusted than other remotes, which Patrick argues is likely unintentional and wasteful since the promisor is often the same as the current fetch source.

Patrick acknowledges this behavior should be fixed but will remove these patches from the current series to focus on the broader API cleanup. The discussion reveals an underlying design question about how Git should handle trust verification between different object sources, particularly in partial clone scenarios. This leaves open the question of what the "correct" behavior should be for collision checks involving promisor objects.
