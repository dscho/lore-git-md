This is a discussion thread about the handling of nested paths in Git's replace refs functionality, now considering whether to tighten or loosen the rules around path qualification.

Junio C Hamano responds to Patrick Steinhardt's concerns about whether nested replace ref paths were intentionally supported. He agrees this was likely not a designed behavior and leans toward tightening the rules to prohibit extra path levels between "refs/replace/" and the object name. His main concern is the potential for multiple replacement objects for the same commit if nested paths are allowed, which could lead to unpredictable behavior depending on filesystem read order.

The email highlights two key technical considerations: 1) The risk of inconsistent behavior when multiple replace refs target the same object via different path levels, and 2) The philosophical question of whether Git should prevent such problematic cases rather than document them. While acknowledging the current implementation's inconsistency (where decoration logic handles paths differently than other parts), Hamano suggests the "feature" is obscure enough that tightening the rules might not break real-world usage.

This moves the discussion from a simple bugfix toward a design decision about whether to officially support nested paths. The thread now faces a choice between three paths: 1) Fix the inconsistency by tightening path rules everywhere, 2) Fix it by loosening decoration to match other code paths, or 3) Document the current behavior as intentional. The security implications of allowing multiple replacement objects for the same commit remain the primary technical concern against option #2.
