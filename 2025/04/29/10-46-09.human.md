Bugfix for nested replace ref paths in commit decoration, with discussion of broader implications.

Patrick Steinhardt responds to Tao Klerks' patch fixing an inconsistency in how Git handles nested replace ref paths (like `refs/replace/2012-migration/abc123`). While the patch itself is straightforward - making `add_ref_decoration()` use the same "last slash" logic as `register_replace_ref()` - Steinhardt raises important questions about whether this behavior should be officially supported.

The response notes that git-replace(1) documentation doesn't mention nested paths, questioning if the current behavior is intentional or accidental. Steinhardt flags compatibility concerns with older Git versions and alternative implementations (JGit, libgit2) that might not handle nested paths. The technical suggestion is to extract a common function for replace ref parsing to ensure consistent behavior across all call sites.

This moves the discussion beyond the immediate bugfix to consider whether Git should formally support and document nested replace ref paths, weighing backwards compatibility against the demonstrated use case of organizing replacements by purpose. The patch itself remains sound, but its acceptance may hinge on resolving these broader questions.
