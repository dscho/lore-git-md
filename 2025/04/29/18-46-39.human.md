This is a discussion about Git's handling of nested replace refs (like `refs/replace/2012-migration/abc123`), which has evolved from a bugfix into a design debate. Junio Hamano responds to Patrick Steinhardt's concerns about whether nested paths should be officially supported.

Hamano believes the nested path support was likely unintentional and would have preferred to prohibit it during initial implementation. He raises concerns about potential confusion if multiple replace refs point to different objects for the same base object name, as there's no clear resolution mechanism. While acknowledging the current inconsistency in commit decoration behavior, he suggests the rarity of such usage makes tightening the rules potentially safer than expanding support.

The discussion highlights fundamental questions about replace ref semantics: whether nested paths offer legitimate use cases worth supporting, how to handle them consistently across Git's codebase, and what backward compatibility implications might arise. Hamano doesn't strongly oppose the feature but clearly prefers the simpler, more constrained approach that would come from rejecting nested paths entirely.

This email moves the conversation from technical implementation toward design philosophy, with the maintainer expressing cautious skepticism about expanding replace ref capabilities while leaving the final decision open for further discussion.
