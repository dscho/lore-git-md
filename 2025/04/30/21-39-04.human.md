This is a response to a bug report about `git restore -m` resurrecting committed merge conflicts. Junio C Hamano explains this is actually intentional behavior dating back to Git's original conflict resolution design from 2009.

The key insight is that Git deliberately preserves conflict state information even after commits, allowing developers to revisit and re-resolve conflicts if needed. The response references commit cfc5789a which introduced this capability, noting that operations like `git add` and `git commit` were specifically excluded from the list of actions that would clear this state.

Hamano suggests the reporter try `git reset --hard` between steps to see if that changes the behavior, implying this would clear the conflict state. The response frames this not as a bug but as a design choice - the ability to restore conflicts after committing can be useful when realizing a resolution was incorrect. The advice is simply to avoid using `git restore -m` if you don't want this behavior.

This clarifies that what appeared to be a bug is actually working as designed, though the behavior may not be well-documented. The response provides historical context and rationale while maintaining Git's existing behavior.
