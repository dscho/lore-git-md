This thread discusses an unexpected behavior in `git restore -m` where it can resurrect committed merge conflict markers. The original reporter demonstrated that after committing files containing conflict markers (from an unresolved merge), running `git restore -m .` brings those markers back into the working tree - behavior that isn't documented in the man pages.

Junio Hamano has now responded, explaining this is actually intentional design dating back to 2009 (commit cfc5789a). Git preserves conflict state information even after committing, allowing users to revert their conflict resolution if needed. This differs from commands like `merge` or `reset` which clear conflict state. While the behavior may surprise users, it serves a purpose - letting developers recover from bad conflict resolutions. Junio suggests using `git reset --hard` to fully clear the state if desired, or simply avoiding `restore -m` when working with previously committed conflicts. The thread appears resolved with this explanation of the historical rationale.
