This is a discussion about Git's commit behavior with pathspecs, specifically addressing user confusion around unstaged changes being included when committing specific files.

Junio Hamano confirms that there is currently no way to make `git commit file.txt` respect only staged changes (like `git commit` does) rather than including unstaged changes (like `git commit -a` does for specified paths). He explains the historical context: Git originally only had `--include` behavior (committing both staged and unstaged changes), then added `--only` as a safer alternative, but neither matches what the user wants.

Hamano suggests that a new `--cached` mode could be added to provide this functionality, drawing a comparison to `git diff --cached` which shows only staged changes. While he sees no fundamental reason against implementing this, he notes this would be a new feature rather than a behavior change to existing modes. The discussion highlights a gap in Git's commit interface where users currently must either stage everything first or use workarounds to achieve selective staging behavior.
