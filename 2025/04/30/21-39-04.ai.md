This is a response to the bug report about `git restore -m` resurrecting committed conflict markers. Junio Hamano provides historical context and design rationale, suggesting this is intentional behavior rather than a bug.

The response explains that the behavior dates back to the original 2009 implementation of conflict resolution tracking (commit cfc5789a). The key insight is that Git deliberately preserves conflict state information even after `git add` or `git commit` operations, allowing users to revert their conflict resolution if needed. This contrasts with operations like `git merge` or `git reset` which clear the conflict state.

Hamano notes this design choice enables users to recover from broken conflict resolutions after committing. He suggests the reporter could use `git reset --hard` to clear the state if undesired, and humorously advises simply not using `git restore -m` if the behavior isn't wanted. The response implies this is working as designed, though the behavior may be surprising to users who don't expect committed conflicts to be recoverable in this way. No changes to Git's behavior are proposed - the email serves to close the question by explaining the historical rationale.
