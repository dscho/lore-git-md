bugfix: Unexpected behavior in `git restore -m` after committing merge conflicts

This email reports an unexpected interaction between `git restore -m` and previously committed merge conflicts. The reporter demonstrates that after creating and committing a merge conflict (including conflict markers), running `git restore -m .` can resurrect the conflict markers in the working tree, despite the conflict having been resolved and committed.

The reproduction steps show a clear sequence where:
1. A file is modified and committed on two branches
2. A merge creates a conflict (with standard conflict markers)
3. The conflicted state is committed (including the markers)
4. `git restore -m .` unexpectedly brings back the conflict markers

The reporter notes this behavior isn't documented and questions whether it's a bug or undocumented feature. The issue occurs with Git 2.34.1 on Linux. The commit message suggests this could be problematic as it allows resurrecting conflict markers that were intentionally committed, potentially confusing users who expect `restore -m` to only affect uncommitted changes.

Key technical details:
- Affects the merge/restore interaction logic
- Reproducible with simple file operations
- Involves the `-m` (merge) option of `git restore`
- May relate to how Git handles committed conflict markers versus active merge state

This appears to be either a bug in conflict state tracking or an undocumented edge case in the restore command's behavior with committed conflicts. The report is well-structured with clear reproduction steps and version information, making it easy to investigate.
