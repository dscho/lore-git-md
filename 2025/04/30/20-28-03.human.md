This is a design discussion about the implementation approach for Scalar's new `--no-maintenance` flag, following up on the recently submitted patch series. Junio Hamano raises architectural concerns about where maintenance scheduling decisions should live in the codebase.

While agreeing with the feature's motivation (preventing maintenance.lock conflicts in automated environments), Hamano questions why maintenance toggling is handled within `register_dir()` rather than by the calling commands (`cmd_register()`/`cmd_clone()`). He notes this creates an inconsistency where `cmd_reconfigure()` still unconditionally enables maintenance, suggesting the deeper issue is that maintenance control is too tightly coupled with directory registration.

The feedback proposes a more modular design where `register_dir()` would only handle repository enlistment, leaving maintenance scheduling decisions to the command-level callers. This would provide clearer separation of concerns and avoid the current awkwardness where the new flag's behavior doesn't extend to all maintenance-related operations. The critique is constructive, focusing on long-term code organization rather than rejecting the feature itself.
