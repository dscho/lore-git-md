Scalar feature patch series introducing `--no-maintenance` flag for repository setup commands (`scalar register` and `scalar clone`), with ongoing design discussion about architectural placement of maintenance control. Original implementation modified `register_dir()` to accept maintenance preferences, with test coverage in t9210-scalar.sh and t9211-scalar-clone.sh.

Junio Hamano's architectural concerns focus on separation of responsibilities, advocating for maintenance toggling at command level (`cmd_register()`/`cmd_clone()`) rather than in `register_dir()`. His technical arguments emphasize: (1) inconsistency with `cmd_reconfigure()`'s unconditional maintenance enabling, (2) conflation of directory registration and maintenance setup concerns, and (3) improved code clarity through explicit command-level calls. He notes that since `toggle_maintenance()` must be called directly for `--no-maintenance` cases anyway, routing through `register_dir()` provides no meaningful abstraction benefit.

Derrick Stolee defends the centralized `register_dir()` approach as handling "recommended settings" while acknowledging the `cmd_reconfigure()` oversight. Junio's latest response reinforces his position with two key principles: single-responsibility functions (keeping `register_dir()` focused on registration) and direct command-level control being more maintainable for future extensions. He acknowledges the flag's dual-form implementation (`--[no-]maintenance`) is properly handled in the current code.

Open questions remain: (1) final architectural placement of maintenance control (centralized vs explicit per-command), (2) reconciliation with `cmd_reconfigure()`'s behavior, and (3) implications for future configuration customizations. The core functionality (preventing maintenance.lock conflicts via setup-time opt-out) is uncontested. Test coverage in t9210/t9211 remains valid but may need restructuring based on the architectural resolution. The discussion highlights a fundamental tension between centralized configuration (Stolee) versus explicit command-level control (Hamano), with significant implications for Scalar's evolution. Stolee's anticipated v2 implementation is expected to address these concerns while preserving the flag's original purpose.
