Scalar feature patch series introducing `--no-maintenance` flag for repository setup commands (`scalar register` and `scalar clone`), now in design discussion about architectural placement of maintenance control. Original implementation modified `register_dir()` to accept maintenance preferences, with test coverage in t9210-scalar.sh and t9211-scalar-clone.sh.

Junio Hamano's review raised architectural concerns about responsibility boundaries, suggesting maintenance toggling belongs at command level (`cmd_register()`/`cmd_clone()`) rather than in `register_dir()`, citing three issues: inconsistency with `cmd_reconfigure()`'s unconditional maintenance enabling, conflation of directory registration and maintenance setup, and need for clearer separation of concerns.

Derrick Stolee responds in this follow-up, acknowledging the `cmd_reconfigure()` oversight but defending `register_dir()` as a centralized configuration point for "recommended settings" (with maintenance being one such setting). He expresses concern that moving control upward might lead to duplicated logic if more customizations are added later, while committing to explore restructuring options for v2. The core functionality - preventing maintenance.lock conflicts in automated environments via setup-time opt-out - remains uncontested.

Open questions pending v2 implementation: (1) whether maintenance control is intrinsic to directory registration's responsibility, (2) how to reconcile `cmd_reconfigure()`'s behavior with the new opt-out capability, and (3) how to maintain clean separation if more configuration customizations emerge. Test coverage for existing functionality remains valid but may need expansion for restructured code paths. The thread awaits Stolee's revised implementation addressing these architectural concerns while preserving the flag's original purpose.
