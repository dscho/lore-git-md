Scalar feature patch series introducing `--no-maintenance` flag for repository setup commands (`scalar register` and `scalar clone`), now in design discussion about architectural placement of maintenance control. Original implementation modified `register_dir()` to accept maintenance preferences, with test coverage in t9210-scalar.sh and t9211-scalar-clone.sh.

Junio Hamano's initial review raised architectural concerns about responsibility boundaries, suggesting maintenance toggling belongs at command level (`cmd_register()`/`cmd_clone()`) rather than in `register_dir()`, citing three issues: inconsistency with `cmd_reconfigure()`'s unconditional maintenance enabling, conflation of directory registration and maintenance setup, and need for clearer separation of concerns.

Derrick Stolee responded defending `register_dir()` as a centralized configuration point for "recommended settings" while acknowledging the `cmd_reconfigure()` oversight. Junio Hamano's follow-up reinforces his position with two technical arguments: (1) explicit command-level calls improve code visibility compared to parameter-passing through `register_dir()`, and (2) since `toggle_maintenance()` must be called directly for the `--no-maintenance` case anyway, there's no abstraction benefit to routing through `register_dir()`. He acknowledges the current implementation could work if maintenance remains the only customization but suggests explicit control would better accommodate future extensions.

Open questions pending v2 implementation: (1) architectural placement of maintenance control (centralized in `register_dir()` vs explicit per-command calls), (2) reconciliation with `cmd_reconfigure()`'s behavior, and (3) handling future configuration customizations. The discussion highlights tension between centralized configuration (Stolee) versus explicit command-level control (Hamano), with implications for Scalar's evolution. Core functionality (preventing maintenance.lock conflicts via setup-time opt-out) remains uncontested. Test coverage in t9210/t9211 remains valid but may need adjustment for restructured code. Stolee's v2 implementation is anticipated to address these architectural concerns while preserving the flag's original purpose.
