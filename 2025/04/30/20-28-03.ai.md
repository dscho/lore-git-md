This is a design discussion about the implementation approach for the `--no-maintenance` feature in Scalar commands. Junio Hamano raises architectural concerns about where maintenance toggling should be controlled, suggesting it belongs at the command level (`cmd_register()`/`cmd_clone()`) rather than being passed down to `register_dir()`.

The email acknowledges the soundness of the feature's motivation (preventing maintenance.lock conflicts in automated setups) but questions the deeper design. Key points made: (1) `cmd_reconfigure()` still unconditionally enables maintenance, creating inconsistency, (2) maintenance control seems misplaced in `register_dir()` when it should be the caller's responsibility, and (3) the current approach conflates directory registration with maintenance setup.

This suggests the patch series, while functionally complete, may need restructuring to properly separate concerns. The feedback implies the maintenance toggle` should move up the call stack, with `register_dir()` handling only core registration duties. This would affect both existing commands and leave open whether `cmd_reconfigure()` should also gain a `--no-maintenance` flag or simply stop toggling maintenance.
