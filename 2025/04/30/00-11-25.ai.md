This is a follow-up in the ongoing discussion about nested paths in replace refs, where Junio C Hamano appears to be softening his initial opposition after Tao Klerks' explanation of the existing safeguards. 

The key development is Junio now acknowledges the current error checking that prevents multiple replacement objects for the same commit ("duplicate replace ref targets") provides sufficient safety. This addresses his earlier concerns about unpredictable behavior from filesystem read order. His comment "I offhand see no more reason to forbid it" suggests he may be moving toward accepting nested path support, though he doesn't explicitly endorse it yet.

The exchange confirms that Git already handles problematic cases by failing operations with clear errors when duplicate replacements exist, as Klerks described. This validation occurs at runtime rather than path structure enforcement. The "clean up your replace refs" remark indicates the system guides users toward correct usage even with nested paths.

This moves the thread closer to resolution, with the security concerns now mitigated by the documented error handling. The remaining open question is whether to formally document and support nested paths in git-replace(1), or maintain them as an undocumented but tolerated feature. Junio's concession suggests the debate may be shifting toward Klerks' position of keeping the functionality, possibly with added documentation.
