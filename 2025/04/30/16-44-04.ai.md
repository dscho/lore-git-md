This is a discussion thread about Git's staging behavior, specifically around how `git commit <file>` handles unstaged changes. Junio C Hamano responds to a user's question about why unstaged changes get committed when specifying a file path, noting this is the documented `--only` mode behavior.

Key technical points from the response:
- Confirms there is currently no way to make `git commit <file>` respect only staged changes
- Explains the historical context: `--only` mode (current default) was introduced as a safer alternative to the original `--include` behavior
- Proposes a hypothetical `--cached` mode that would only commit staged changes for specified paths, drawing analogy to `git diff --cached`
- Notes this would require adding a new mode rather than changing existing behavior

The discussion highlights a UX gap where users might expect path-limited commits to respect staging like the no-args `git commit` does. Junio's response leaves the door open for implementing such a mode while making clear it doesn't exist. This could lead to either documentation improvements or a feature proposal for a new `--cached` commit mode.
