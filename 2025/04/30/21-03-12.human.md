Bug report about unexpected behavior in `git restore -m` after committing merge conflicts.

Terry Bear reports that `git restore -m .` can unexpectedly restore merge conflict markers in a file even after the conflicted state has been committed. The detailed reproduction steps show that after creating a merge conflict, committing it, then running `git restore -m .`, the conflict markers reappear in the working tree.

The reporter notes this behavior isn't documented and questions whether it's a bug or undocumented feature. The issue occurs with Git 2.34.1 on Linux. While the report is clear and well-documented with reproduction steps, the impact seems limited since it requires a specific sequence of operations (committing merge conflicts then attempting to restore them). The behavior does appear counterintuitive - one wouldn't normally expect committed content to revert to conflict markers - suggesting this may warrant investigation by the Git maintainers.
