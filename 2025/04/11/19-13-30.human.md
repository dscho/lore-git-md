Bugfix addressing state detection in interrupted `git am` operations.

Phillip Wood proposes a solution to the issue where Git incorrectly reports an interrupted `git am` as a rebase in `git status`. The root cause is that `git am` writes the `.git/rebase-apply/applying` file too late in its process - only after reading patch files, which means an early Ctrl-C interruption leaves the repository in an ambiguous state.

The proposed fix moves the writing of the state file earlier in the `builtin/am.c` process, before patch reading begins. This would ensure proper state detection even if the operation is interrupted. The change is small and focused, touching only the timing of when the state->rebasing flag gets written to disk.

This builds on the earlier technical analysis by D. Ben Knoble, who identified the discrepancy between how `git status` and shell prompts detect operation state. While the prompt correctly identifies AM/REBASE states by checking multiple files, `git status` relies solely on the presence of `applying` which may be there yet when interrupted.

The patch appears well-targeted to the specific issue without introducing broader architectural changes. It maintains the current behavior for successful operations while fixing the edge case of early interruption. The change is minimal and low-risk, touching only the sequence of operations within `git am`'s existing state management.
