The reporter observed that after editing, staging, and then re-editing the same line, `git stash -k` appeared to create a diff between HEAD and unstaged changes rather than between staged and unstaged changes as expected. The technical explanation revealed that stash entries are structured as two commits (index state and working tree state), and demonstrated how to selectively apply just the working tree changes using `git cherry-pick -m 2` to target the second parent of the stash commit. While this confirms the current behavior is intentional, it doesn't directly address whether the merge conflicts are an unavoidable consequence of this design.
