This is a technical clarification in the ongoing discussion about multi-remote synchronization workflows. Klaus Frank responds to D. Ben Knoble's suggestion of using a local repository as the authoritative source by explaining their specific CI/CD-based use case where no persistent local repository exists.

The key new information is:
- The synchronization is performed by a stateless CI/CD job acting as a "cron job" rather than a persistent local repo
- A concrete example is provided involving the GNOME gdm project with 5 potential remotes (original GNOME GitLab, personal fork, personal GitLab instance, GitLab.com, and GitHub)
- The sync script needs to handle cases where different remotes may be authoritative for different branches (original repo for upstream code, personal fork for changes)

This reinforces the original problem's constraints where traditional local-repository-based solutions don't apply, and highlights the complexity of determining authoritative sources in a multi-remote CI environment. The example demonstrates why simple push/pull mirroring or single-source approaches may be insufficient for real-world multi-platform development workflows.

The response doesn't propose new solutions but provides important context about the CI/CD execution environment that any solution would need to accommodate, particularly the lack of persistent local state and need for branch-specific authority rules. This moves the discussion toward more concrete requirements for any potential Git feature or workflow to address these synchronization needs.
