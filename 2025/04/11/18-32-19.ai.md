Technical analysis of state detection discrepancy in interrupted `git am`:

This follow-up email from D. Ben Knoble provides a detailed technical comparison between how the shell prompt and `git status` detect interrupted operations, revealing the root cause of the reported inconsistency. The key findings are:

1. The shell prompt script (`git-prompt.sh`) has more nuanced state detection, distinguishing between rebase (`REBASE`), apply (`AM`), and an ambiguous state (`AM/REBASE`) when it finds a `rebase-apply` directory but can't determine the specific operation.

2. `wt-status.c` makes a binary distinction - if there's no `applying` file, it assumes a rebase is in progress, which leads to the misleading message when `git am` is interrupted.

3. Both implementations date back to 2007 (prompt) and 2012 (status), with their original authors CC'd, suggesting this discrepancy has existed for over a decade.

The email suggests a potential solution path: having `git status` adopt the prompt's more cautious approach by acknowledging uncertainty when the operation type can't be determined, rather than defaulting to rebase state. This would require changes to `wt-status.c`'s state detection logic.

The analysis provides concrete code references to both implementations, establishing this as a clear bug in state reporting rather than state cleanup. The next steps would likely involve:
- Deciding whether to make status match the prompt's behavior
- Determining if the ambiguous state should trigger different cleanup advice
- Possibly unifying the state detection logic between these components
