This is a bugfix proposal addressing the inconsistent state detection between `git am` and `git status` when `git am` is interrupted.

Phillip Wood identifies the root cause: `git am` currently writes the `.git/rebase-apply/applying` file too late in its execution (after reading patch files), while `git status` relies on this file to distinguish between `am` and `rebase` operations. The proposed solution moves the file creation earlier in the `am` process, before patch reading begins. The patch modifies `builtin/am.c` to write the state file immediately after initializing the rebase/apply state.

Key technical details:
- The fix changes when `git am` writes the state marker file (either "rebasing" or "applying")
- Maintains the same file-based state tracking but ensures it's written earlier
- Preserves all existing state machine behavior, just makes it detectable sooner
- Does not address the cleanup of lingering state files (focuses purely on correct state reporting)

This builds on D. Ben Knoble's earlier analysis that identified the discrepancy between shell prompt detection (which correctly shows AM/REBASE state) and `git status` behavior. The patch represents a minimal change to align the two behaviors without larger architectural changes to the state tracking system.

The change appears well-scoped and directly addresses the reported issue where interrupted `git am` operations were incorrectly reported as rebases. The patch maintains the existing state machine logic while fixing the timing, suggesting it's a low-risk change that doesn't introduce new state handling complexity.
