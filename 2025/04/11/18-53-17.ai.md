This is a reply in an ongoing discussion about adding a `--no-hooks` global option to disable Git hooks. The thread has seen debate about whether this feature is necessary given existing alternatives like `--no-verify` and `core.hooksPath=/dev/null`, with concerns raised about silent failures and whether performance issues should be addressed by optimizing hooks rather than bypassing them.

D. Ben Knoble shares a concrete use case where a pre-push hook running slow tests interferes with shell operations due to poor SIGINT handling. They describe frustrations with npm-based projects where hooks get re-enabled on install, leading to inconsistent behavior. While acknowledging the hooks need fixing, they argue `--no-hooks` would provide a cleaner temporary workaround than remembering per-command `--no-verify` flags. Knoble also suggests this could help shift the culture toward putting mandatory checks in server-side hooks rather than client-side ones.

The technical implementation remains unchanged from Stolee's original proposal, adding the global option and `GIT_HOOKS` environment variable with static int optimization in `run_hooks_opt()`. The reply doesn't introduce new code but provides real-world validation of the pain points the feature aims to address, particularly in JavaScript/npm ecosystems where hook management tools like husky are common.
