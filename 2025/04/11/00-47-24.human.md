This is a security-related follow-up in the resolved `safe.directory` thread, providing additional technical clarification about the `--no-local` workaround behavior.

Brian m. carlson confirms Jeff King's observation about version-specific behavior of `git clone --no-local` in Git 2.48.0+, explaining the underlying reason: regular clones attempt hardlinking which has security implications across ownership boundaries, while `--no-local` triggers the more secure `git-upload-pack` path that properly handles untrusted repositories. 

The email suggests a potential future improvement - automatically detecting and using `--no-local` when cloning from repositories owned by other users - but marks this as a non-urgent follow-up task ("#leftoverbits"). This comes as a post-resolution note after the thread had already established three complete workarounds and confirmed the security design was intentional.

The technical detail here reinforces the thread's key conclusion about process isolation being central to the security model, while also showing there's still room for user experience improvements in edge cases. The suggestion is framed as optional future work rather than something needing immediate attention.
