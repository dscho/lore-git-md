This is a bug report about unexpected pathspec matching behavior in `git add`. The reporter, Piotr Siupa, demonstrates that when a repository contains both a literal file named `f*` and another file matching the wildcard pattern `f*` (like `foo`), `git add 'f*'` only stages the literal `f*` file on first run, rather than both files as expected. The behavior corrects itself on subsequent runs, where `foo` then gets staged.

The issue appears in both Git 2.43.2 and the current development version (2.49.0.805.g082f7c87e0), suggesting it's a longstanding behavior rather than a recent regression. The minimal reproduction case (fresh repo with just `foo` and `f*` files) makes the bug easy to verify. No workaround is mentioned, though the fact that subsequent `git add` commands work suggests some caching or state issue in the pathspec matching logic.

Key technical details for future reference:
- Affects `git add` with wildcard pathspecs when literal matches exist
- First run fails to match pattern, subsequent runs succeed
- Files involved: `foo` (content doesn't matter) and literal `f*`
- Likely related to how Git handles literal vs. wildcard interpretation in pathspecs
- No crash or data loss, just incomplete staging behavior

The report is clear and well-formatted with a minimal test case, making it easy to reproduce. The behavior described does appear to violate user expectations for wildcard matching.
