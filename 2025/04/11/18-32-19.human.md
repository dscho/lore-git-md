This is a bugfix thread analyzing inconsistent state reporting between `git status` and shell prompts when `git am` is interrupted. D. Ben Knoble provides a technical deep dive into the discrepancy, tracing it to different detection logic in the shell prompt script versus `wt-status.c`.

The analysis shows the shell prompt (from git-prompt.sh) makes a three-way distinction between rebase, apply, and ambiguous states, while `git status` assumes any `rebase-apply` directory without an `applying` file must be a rebase. This explains why users see conflicting messages after interrupting `git am`.

The email identifies the relevant historical commits that introduced this divergence and suggests a potential solution path: having `git status` acknowledge the ambiguity rather than assuming rebase state. The thread has now clearly pinpointed the core issue as being in state detection logic rather than cleanup behavior, moving the discussion toward concrete implementation questions about how to best represent uncertain states to users.
