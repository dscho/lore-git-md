This is a follow-up in the ongoing discussion about symlink handling behavior when `core.symlinks` configuration changes, with specific focus on Windows environments.

Andrej Zhilenkov responds to brian m. carlson's position that symlinks should be globally enabled when possible, pushing back slightly on the practicality of this approach. While agreeing in principle that global enablement is ideal, Zhilenkov notes two real-world concerns: (1) users may be reluctant to make global system changes for a single repository's needs, and (2) he's seeing Windows users incorrectly setting `core.symlinks` at the local repository level (when Git for Windows sets it at system level by default).

The email highlights a potential documentation or usability issue - Windows users appear to be misunderstanding how to properly enable symlinks, leading them to set local configs that may not work as expected. This adds nuance to the earlier discussion about Windows privilege requirements, showing there may be user education needed beyond just the technical constraints.

The exchange continues to explore the tension between ideal technical solutions (global symlink enablement) and practical user behavior in constrained environments, without yet proposing concrete changes to Git's behavior. The thread remains focused on understanding real-world usage patterns while maintaining the core design principle that symlink capability is determined at repository creation.
