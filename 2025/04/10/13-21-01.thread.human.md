This thread examines an inconsistency in how Git's `safe.directory = *` setting behaves differently between `git status` (which honors the wildcard to bypass ownership checks) and `git clone` from local paths (which still enforces ownership verification). The original reporter, Nikolaus Rath, documented this discrepancy in Git 2.43.0, showing clone failing with a "dubious ownership" error while status succeeds in the same environment.

Jeff King (Peff) has now clarified that this is intentional behavior, not a bug. The difference arises because Git clears environment variables—including `GIT_CONFIG_*` settings—when spawning child processes during clone operations. This explains why the wildcard setting works for `git status` (a single-repository operation) but not for `git clone` (which involves an `upload-pack` child process in the source repository). The design prioritizes security consistency with non-local transports that can't pass environment variables.

Peff suggests two practical workarounds: setting the config globally in `~/.gitconfig` or explicitly passing it to upload-pack during clone. While this behavior may be surprising to users, the response indicates it's a deliberate security tradeoff that has been discussed before in Git's development history. The thread remains open for further discussion about whether this behavior should be documented more clearly or modified for better usability.
