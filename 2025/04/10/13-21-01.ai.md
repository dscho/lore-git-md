Potential security issue with inconsistent `safe.directory` enforcement. The email reports that while `git status` respects the `safe.directory = *` wildcard setting (allowing operations in any directory regardless of ownership), `git clone` from a local repository still performs ownership checks and rejects the operation. This creates an inconsistency in security policy enforcement where some operations bypass the intended relaxation of ownership checks.

The reporter demonstrates this with a concrete example using Git 2.43.0, showing `git status` succeeding while `git clone` fails with the standard "dubious ownership" error message despite the wildcard setting. The behavior suggests either a bug in the implementation or an intentional design choice that isn't documented. The email doesn't reference any prior discussion about this specific case, positioning it as a new observation about security policy enforcement gaps.

Key technical details:
- Affects local repository operations (clone from local path)
- Involves the security-sensitive `safe.directory` config
- Demonstrates inconsistent behavior between read operations (`status`) and write operations (`clone`)
- Uses the wildcard (`*`) setting which should theoretically apply to all operations

This appears to be either a security bug (if the wildcard should apply universally) or a documentation gap (if clone operations are intentionally excluded from the wildcard exception). The reporter doesn't propose a solution but raises it as a question about expected behavior, suggesting it may need maintainer input to determine whether this is working as designed or requires fixing.
