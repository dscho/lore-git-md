This is a technical discussion about Change-IDs in Git commit headers, continuing the ongoing debate about whether to add persistent identifiers to track commit evolution.

Junio Hamano responds to Nico Williams' argument for explicit Change-IDs by raising concerns about fundamental limitations in the proposal. He acknowledges the value of tracking commit evolution but argues the current Change-ID approach is structurally insufficient for anything beyond simple single-commit updates. The key issue is that a single Change-ID field cannot properly represent more complex scenarios like parallel development branches or multi-commit revisions without additional metadata.

Hamano specifically highlights the distributed nature of Git as a complicating factor, noting that without global synchronization, Change-IDs alone cannot determine the actual evolution path when multiple commits share the same identifier. He contrasts this with IDE-based tracking solutions, which he suggests might handle such cases better.

The email takes a firm stance against adding known-incomplete solutions to Git's core data structures, suggesting the Change-ID approach as currently proposed would violate Git's design principles. This continues the thread's central tension between workflow convenience and Git's content-addressable purity, now with specific technical objections about the proposal's limitations in distributed development scenarios.
