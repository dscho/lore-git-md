This is a response in a thread about working directory status checking, specifically addressing the request for a simple command to detect repository dirtiness through exit codes.

Junio C Hamano responds to Ross Goldberg's inquiry about a potential feature request for a simple dirtiness-checking command with configurable criteria. The response argues that once options are introduced to specify different types of dirtiness (staged, unstaged, untracked files), the problem space becomes complex enough that separate existing commands may be preferable. 

The email suggests several existing commands for different dirtiness checks:
- `git diff --cached --quiet` for index changes
- `git diff --quiet` for working tree vs index
- `git diff --quiet HEAD` for working tree vs HEAD
- `git describe --always --dirty` (though notes it doesn't handle untracked files)
- `git clean -n` as a potential complement for untracked files

The key technical points are that (1) different dirtiness checks require different commands, (2) combining these checks would introduce complexity that may not warrant a new command, and (3) the simplest`git describe --always --dirty` approach has limitations regarding untracked files. The response maintains a skeptical stance toward creating a new unified command while providing practical alternatives using existing tooling.
