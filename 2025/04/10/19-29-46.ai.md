This is a follow-up in the ongoing thread about symlink handling behavior, specifically addressing Windows privilege models and configuration preferences.

Andrej Zhilenkov responds to brian m. carlson's position that symlinks should be globally enabled when possible, pushing back slightly on the idea of requiring global configuration changes. While agreeing that global enablement is ideal, Zhilenkov notes practical concerns about users who only need symlinks for specific repositories and observes that many Windows users incorrectly set `core.symlinks` at the local rather than system level.

The email introduces two new practical considerations: first, that users may reasonably want to avoid global configuration changes when only certain repositories require symlink support, and second, that there appears to be widespread misunderstanding among Windows users about how to properly configure symlink behavior (with incorrect local-level settings being common despite Git for Windows' system-level defaults).

This continues the thread's exploration of how to balance security constraints with usability, now with additional focus on configuration ergonomics and real-world user behavior patterns. The discussion remains centered on whether the current behavior (no automatic conversion when `core.symlinks` changes) should be maintained, with Zhilenkov's latest points suggesting that the status quo may create practical difficulties for Windows users who need per-repository control.
