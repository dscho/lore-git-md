This is a conceptual discussion about Change-IDs and their parallels to file tracking in Git.

Theodore Ts'o draws an analogy between Change-IDs and inode numbers, arguing that both represent attempts to track semantic identity across transformations (file renames/copies for inodes, commit splits/merges for Change-IDs). He notes the same fundamental complexities that make file tracking via inodes problematic would apply to Change-IDs, though acknowledges some may value Change-IDs more highly for code review workflows.

- Identifies similar ambiguity challenges when tracking identity across transformations
- Distinguishes between semantic" Change-IDs and more limited "patch set IDs"
- References historical SCM debates about file tracking approaches

The email suggests a middle path - while skeptical of full Change-IDs, Ts'o proposes "patch set IDs" as a potentially more feasible alternative that could benefit both web-based and mailing list review workflows. This positions the discussion after Junio Hamano's distributed systems critique by exploring a narrower scope that might avoid those architectural concerns.

The thread context shows this continues debate about whether any form of commit tracking can work within Git's distributed model while meeting code review needs. Ts'o's patch set ID suggestion appears as a potential compromise between workflow desires and technical constraints.
