This is a security-related clarification about the `safe.directory` behavior in Git. Jeff King explains that the observed inconsistency between `git status` and `git clone` operations is actually working as designed, not a bug. 

The key insight is that `git clone` internally spawns a new `git-upload-pack` process in the source repository, and Git deliberately clears environment variables (including `GIT_CONFIG_*` settings) when switching between repositories. This explains why the `safe.directory = *` setting appears to work for read operations like `status` but not for `clone` - the setting isn't being passed through to the child process.

Jeff suggests two workarounds: either set the `safe.directory` in the global config file (`~/.gitconfig`) which will persist across processes, or explicitly pass the config to the upload-pack command via the `-u` flag during cloning. The explanation provides important context about Git's security-conscious design decisions around environment handling, particularly why config settings don't automatically propagate between repository operations.

This response from a core maintainer effectively resolves the open question from the thread about whether the behavior was intentional, while offering practical solutions for users encountering this limitation. The explanation ties into broader Git's security model and the tradeoffs involved in environment variable handling.
