Ludo Pulles reported a bug where interrupting `git am` with Ctrl-C leaves Git in an inconsistent state, incorrectly showing a rebase in progress. The issue persists in Git 2.49.0 on Linux, requiring manual cleanup of `.git/rebase-apply`.

D. Ben Knoble's investigation revealed deeper complexities. While `git am` warns about using Ctrl-D for clean exits, the real problem lies in how different components interpret the interrupted state. The shell prompt correctly shows an "AM/REBASE" ambiguous state, but `git status` misleadingly reports a rebase. Knoble found that `git am --abort` works correctly for cleanup, while `git rebase --continue` fails as expected.

The technical root cause traces back to 2007-2012 code in state detection. The shell prompt's logic in `git-prompt.sh` properly identifies ambiguous states, while `wt-status.c` makes an oversimplified assumption that any `rebase-apply` directory means a rebase is in progress. This explains the decade-old discrepancy users have encountered.

The discussion has now shifted from initial bug reporting to solution design. The clearest path forward appears to be updating `wt-status.c` to match the prompt's more nuanced state detection, potentially showing an "interrupted operation" message when the exact state can't be determined. This would resolve the misleading rebase message while maintaining the existing cleanup options. The next steps will likely involve implementing and testing this approach.
