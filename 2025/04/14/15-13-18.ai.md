This is a technical discussion about patch series tracking mechanisms, specifically evaluating Theodore Ts'o's proposed "Patch Set ID" system as an alternative to Change-IDs.

Junio Hamano responds positively to Ts'o's proposal, particularly appreciating how single-commit series naturally emerge as a degenerate case of the more general multi-commit support. The proposal introduces a `--series` flag for `git commit` that establishes parent-child relationships, with IDs preserved across rebases and cherry-picks, and integrated with `format-patch`/`am` workflows.

Hamano raises one remaining concern about tracking evolution history - while the system can identify different iterations by commit strands, it lacks explicit metadata to determine the temporal ordering of independent rewrites or distinguish between parallel development branches sharing the same Patch Set ID. The timestamp-based ordering might not be sufficiently robust for all use cases.

The email confirms the technical cleanliness of Ts'o's approach, which provides clearly defined semantics through commit parentage rather than convention-based footers. This positions the Patch Set ID as a viable alternative to Change-IDs that satisfies several of the maintainer's previously stated requirements, though the history-tracing limitation may need further consideration before final adoption.
