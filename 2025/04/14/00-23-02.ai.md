This is a technical discussion about implementing GPG signing for Git's email patch workflow, focusing on transport authentication rather than commit signature preservation. Klaus Frank responds to brian m. carlson's technical constraints by proposing a more concrete implementation approach while acknowledging the current limitations.

The email presents a detailed technical proposal for both sender and receiver sides of the patch workflow. On the sending side, Frank suggests three potential methods: embedding commit signatures as plain text, clear-signing the entire email, or using detached signatures in a multipart message. The proposal includes specific GPG command-line options that `git format-patch` should support (`--homedir`, `--keyring`, etc.).

For the receiving side (`git am`), Frank outlines a verification workflow with different trust levels (defaulting to TOFU with auto-key-import, with options for stricter verification). The proposal also considers edge cases like unsigned patches (with configurable warnings) and even floats the idea of PGP encryption support for security-sensitive patches.

Key technical elements mentioned include:
- RFC 4880 (clearsign) and RFC 3156 (PGP/MIME) standards
- GPG verification flags like `--auto-key-import` and trust models
- The distinction between transport authentication and commit preservation
- Potential new configuration options for `git am` verification strictness

The tone is pragmatic, acknowledging that while the community currently accepts unsigned patches, transport authentication could provide valuable integrity checking. The proposal is technically detailed but recognizes that implementation would require careful consideration of trust models and backward compatibility.
