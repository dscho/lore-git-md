This is a technical discussion about patch authentication methods in Git's email workflow, continuing the thread about GPG signing approaches. Junio C Hamano (Git maintainer) responds to Konstantin Ryabitsev's introduction of the patatt solution used by the Linux kernel community.

The email reinforces the distinction between two authentication needs in patch workflows: transport authentication (verifying patch origin during transmission) versus commit signatures (which are invalidated by patch application). Hamano agrees with Ryabitsev's framing that these serve different purposes from object-level signing like `git commit --signed`.

Key technical context includes:
- patatt implements DKIM-like headers supporting multiple algorithms (PGP, SSH, ed25519)
- The solution is production-proven in the Linux kernel workflow
- Header-based approaches avoid committer identity issues that break commit signatures
- Discussion continues about integrating such functionality into core Git

The exchange shows the maintainer acknowledging the viability of patatt's approach while implicitly keeping open the question of how/whether to adopt similar functionality in Git's native tooling. The thread has progressed from problem identification through technical constraints to evaluating real-world implementations, with header-based authentication emerging as a leading solution.
