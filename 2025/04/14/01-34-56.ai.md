This is a contribution to the ongoing discussion about GPG signing in Git's email workflow, specifically addressing practical implementation approaches.

Konstantin Ryabitsev responds to Klaus Frank's question about GPG-signed patches by reframing the discussion around end goals - distinguishing between personal attestation needs and contributor verification requirements. He introduces patatt, a tool used in the Linux kernel community that offers a more flexible approach than traditional PGP signing, supporting multiple signature types (PGP, SSH, ed25519) through a custom header mechanism similar to DKIM.

The response provides a concrete example of an alternative to the PGP-based solutions previously discussed in the thread, particularly relevant given the earlier concerns about GnuPG availability and implementation constraints. The patatt approach aligns with brian m. carlson's suggestion of header-based signing methods while demonstrating a working implementation in a major project (the Linux kernel).

Key technical details include:
- Multiple signature algorithm support (PGP, SSH, ed25519)
- DKIM-like header-based signing approach
- Existing production use in the kernel community
- Reference implementation available on GitHub

This contribution expands the solution space beyond the PGP-focused discussion, offering a potentially simpler alternative that addresses some of the platform compatibility concerns raised earlier while maintaining the ability to verify patch authenticity during transport. The response doesn't directly address commit signature preservation, maintaining the thread's clear separation between transport authentication and commit signing concerns.
