This thread explores the challenges of maintaining Git repositories across multiple remotes (like GitHub, GitLab, and internal servers), particularly for CI environments that can't maintain persistent local state. The discussion has crystallized around two competing approaches: automated synchronization between remotes (complex but CI-friendly) versus using a local repository as the single source of truth (simpler but requiring persistent storage).

D. Ben Knoble championed the local-source model, suggesting cron jobs to push to multiple remotes. However, Klaus Frank's latest response highlights critical limitations - the fragility of depending on one machine and the backup burden. Frank considers abandoning GitLab entirely for SSH-based workflows with static site generators, though this still doesn't solve the stateless CI case that sparked the discussion.

The core tension remains unresolved: remote-to-remote sync handles CI but is complex, while local-source approaches are simpler but fail for stateless environments. Technical hurdles around force-pushes, branch authority, and object transfer efficiency persist. With neither approach fully addressing the original CI use case, the thread appears to be reaching an impasse unless someone can bridge these architectural divides or propose a third way.
