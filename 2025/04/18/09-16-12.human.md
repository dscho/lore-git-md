This is a follow-up in the ongoing discussion about `git help`'s error message formatting for nonexistent commands. Jeff King (Peff) weighs in with technical analysis of the proposed solutions, pointing out several practical constraints:

Peff explains that Git doesn't actually know whether an argument is a command or topic when passing it to `man`, since it lacks a complete list of documentation topics. He evaluates several approaches to improve the error messaging:

1. Checking `man`'s exit code to append a more informative message, though notes this may be unreliable across different man implementations and viewers (like browsers for HTML docs).

2. Having `help` warn when falling back to topic lookup, though this would create noise for valid topics.

3. Maintaining a list of known topics, which would work for core docs but miss third-party content.

The analysis highlights the tradeoffs between correctness and practicality, with no clear ideal solution. Peff's technical depth suggests this may require either accepting some imperfection or significant plumbing work to track documentation topics properly. The thread continues to explore how to best handle this edge case in Git's help system.
