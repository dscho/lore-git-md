This is a follow-up in the ongoing discussion about potential data loss when combining `git stash` and `cherry-pick --abort`. Markus Raab clarifies their earlier bug report by adding a critical missing step - a `git stash pop` before the `cherry-pick --abort` - that makes the files actually disappear rather than just being stashed.

The key new information is:
1. The complete reproduction path now shows files being permanently lost (not just stashed) when popping the stash before aborting the cherry-pick
2. Markus provides a recovery script that finds and extracts the lost files from Git's object database, confirming they still exist as dangling objects
3. This strengthens the original claim of data loss, countering brian m. carlson's earlier suggestion that the files were safely preserved in the stash

The discussion is now clearly about actual data loss rather than just restoration behavior. The recovery script suggests the files aren't truly gone from the object database, but they do become inaccessible through normal Git commands. This appears to be a genuine bug in how Git handles state when these operations are combined, though the exact mechanism isn't yet fully explained in the thread.
