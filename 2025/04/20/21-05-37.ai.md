This is a maintainer response in the ongoing thread about `git stash` and `cherry-pick --abort` interaction leading to data loss. Junio C Hamano clarifies that the behavior is not specific to stash operations but is a general property of how `cherry-pick --abort` works - it intentionally discards all working tree and index changes to return to the pre-cherry-pick state, regardless of whether those changes came from a stash pop or manual edits.

The key technical clarification is that `cherry-pick --abort` is designed to wipe all uncommitted changes (index and working tree) to restore the repository to HEAD state, which explains why stashed changes applied via `stash pop` disappear. The maintainer emphasizes this is expected behavior, not a bug, though it may be surprising to users.

An important distinction is made between `stash pop` (applies and drops the entry) versus `stash apply` (keeps the stash entry). The response suggests the real issue is using `pop` when there's any chance of needing to revert, since `apply` preserves the stash entry for recovery via `reset --hard`. This shifts the discussion from being about a bug to being about user education on stash semantics.

The response implicitly rejects the thread's earlier characterization of this as a bug requiring code changes, instead framing it as expected behavior that users should understand. It suggests documenting this interaction pattern rather than changing the implementation. No mention is made of potential improvements to make the behavior less surprising or to automate recovery of lost stashes.
