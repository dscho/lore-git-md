Maintainer response on stash/cherry-pick abort interaction.

Junio Hamano clarifies that the reported file loss during `cherry-pick --abort` is expected behavior, not a bug specific to stash operations. He explains that any working tree changes (whether from `stash pop` or manual edits) will be discarded by `--abort`, as its purpose is to fully reset to the pre-cherry-pick state. The key insight is that this isn't a stash interaction issue - it's how cherry-pick abort is designed to work with any working tree modifications.

The response shifts focus to proper stash usage patterns, strongly recommending `stash apply` over `stash pop` when there's any chance of later needing to revert changes, since `pop` destroys the only copy of the stashed state. This preserves the stash entry for recovery via `reset --hard` if needed. While not addressing the original bug report directly, the explanation provides important workflow guidance that would prevent the reported data loss scenario.

The tone is educational rather than dismissive, framing this as a learning opportunity about Git's operation sequencing expectations. No commitment is made to change behavior, but the explanation implicitly rejects classifying this as a bug needing fixing.
