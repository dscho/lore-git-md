This is a clarification in the ongoing HTTP/2 support regression thread for Git for Windows. Lars Eriksen provides an important correction to the previous diagnosis - the issue isn't with Git's internal HTTP operations (which can use either SSL backend as previously discussed), but specifically with the standalone `curl.exe` command bundled with Git for Windows that their deployment scripts rely on.

The key new information is that their corporate deployment scripts directly use the bundled `curl.exe` (not Git's HTTP operations) for POST operations, and this standalone curl no longer supports HTTP/2 in recent versions. This explains why the `http.sslBackend` configuration proposed earlier wouldn't help their specific case, as it only affects Git's internal HTTP operations.

The thread now has two distinct but related issues:
1. The originally discussed Git internal HTTP/2 support (with workaround via `http.sslBackend`)
2. The newly clarified standalone curl.exe HTTP/2 support regression (no workaround yet proposed)

This changes the technical context significantly - while the internal Git operations might be workaround-able via configuration, the standalone curl.exe appears to be built without HTTP/2 support regardless of SSL backend choice. The impact remains serious for users relying on the bundled curl.exe for HTTP/2 operations in corporate environments where installing alternative curl builds isn't permitted.
