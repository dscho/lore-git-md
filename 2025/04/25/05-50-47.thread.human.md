This thread reports a Windows-specific case sensitivity issue in Git. A user encountered problems when working with files that had case conflicts (`button`/`Button` and `tabs`/`Tabs`) in a Svelte project. Despite `git status` showing a clean working tree, Git prevented branch switching due to phantom untracked files, suggesting the index and working tree were out of sync regarding file casing. The issue persisted through standard fixes like `git rm --cached` and resets, only resolving after manual file deletion in Windows Explorer.

The core problem involves Git's handling of case changes on Windows filesystems, particularly around the `core.ignorecase` setting. The reporter provided detailed reproduction steps showing inconsistent behavior, though no minimal test case was included. This appears to be a genuine edge case in Git's case-sensitivity logic that would be of particular interest to Windows maintainers like Johannes Schindelin. The temporary workaround of manual file deletion suggests the issue may lie in how Git tracks and reconciles case changes across operations.
