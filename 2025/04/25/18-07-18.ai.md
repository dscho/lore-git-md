This is a technical clarification in the ongoing Meson shell path detection thread. Eli Schwartz provides a detailed explanation about shell naming conventions and POSIX compliance in response to Junio Hamano's question about supporting non-standard shell names.

The email makes several key points about shell implementations:
1) POSIX requires the shell to be named "sh" regardless of its location, though the standard doesn't specify an absolute path
2) Most systems provide `/bin/sh` as a symlink to various shell implementations (bash, dash, ksh, etc.)
3) Systems without a POSIX-compliant `/bin/sh` (like Solaris) typically provide an alternative path (e.g., `/usr/xpg4/bin/sh`) for POSIX compliance
4) The concept of a shell not named "sh" is impossible under POSIX - systems may have multiple shells but must provide one named "sh"

Schwartz argues that supporting alternate shell names isn't necessary since:
- POSIX mandates the "sh" name
- Systems needing special handling (like Solaris) already have mechanisms to ensure POSIX compliance
- The current Meson implementation properly handles these cases through standard PATH searching

The response confirms that the current patch series' approach of preferring `/bin/sh` while allowing PATH searching is correct and POSIX-compliant. It also indirectly validates the existing `-Dsane_tool_path=` configuration option as sufficient for any special cases.

This email appears to resolve Junio's final question about shell naming, reinforcing that the current implementation properly handles all POSIX-compliant systems while maintaining compatibility with Git's existing behavior. The technical details provided give additional context about why the current solution is robust and why supporting alternate shell names isn't necessary.
