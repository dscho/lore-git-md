This is a follow-up discussion in the ongoing thread about shell path detection in Meson builds, specifically addressing edge cases and compatibility requirements for different shell implementations.

The email from Eli Schwartz responds to brian m. carlson's detailed explanation of shell compatibility issues, particularly focusing on non-POSIX-compliant shells that might be installed as `/bin/sh` on various systems. Schwartz agrees with the technical assessment but expresses strong opinions about system configurations that use zsh as `/bin/sh`, considering it a conformance bug that should be fixed at the distribution level rather than accommodated in Git's build system.

Key technical details mentioned include:
- AT&T ksh's lack of `local` support (which Git requires)
- NonStop systems defaulting to AT&T ksh as `sh`
- Debian's historical use of zsh as `/bin/sh` with pipeline subshell issues
- The continued need for `-Dsane_tool_path=` configuration to handle these edge cases

Schwartz reinforces that the current Meson implementation properly handles these cases through its configuration system, though they argue that distributions should enforce stricter POSIX compliance rather than relying on workarounds in individual projects. The discussion confirms that the technical solution in the patch series is sound and covers all known edge cases through existing configuration options.

This email doesn't introduce new technical concerns but rather provides additional context about why the flexibility in the current implementation is necessary, while also expressing philosophical views about how systems should be configured at the distribution level. The thread appears technically resolved, with this being more of a commentary on broader ecosystem issues than a request for changes to the proposed solution.
