This thread addresses a bug in `pack-objects` where `should_include_obj()` (line 4310 in `builtin/pack-objects.c`) incorrectly processes non-existent objects during promisor pack operations, triggering a BUG() assertion. Nikolas Garza originally reported the issue occurring after upgrading from Git v2.47 to v2.49, with the root cause traced to commit c08589efdc5 ("index-pack: repack local links into promisor packs") from v2.48.0. Jonathan Tan identified the problematic commit introduced an assumption that `should_include_obj()` would only be called on existing objects, proposing to fix this by making the function return 0 for absent objects.

Sam Estep has now provided a reliable reproduction case demonstrating the BUG() assertion in Git v2.51.0 when performing `git fetch --no-show-forced-updates` on a large Nixpkgs repository clone with tree filtering. The error consistently manifests when `pack-objects` attempts to repack local links into promisor packs, validating the bug's persistence across versions and architectures (x86_64-linux and aarch64-darwin). The reproduction steps involve cloning a Nixpkgs mirror and repeatedly fetching updates until the BUG() triggers, though it remains unclear if configuration settings like `fetch.all=true` and `fetch.prune=true` affect occurrence.

The thread shows active collaboration between Garza (reporter), Estep (reproduction case), and Tan (proposed fix) to diagnose and address the issue. Key technical elements remain the promisor pack handling in `builtin/pack-objects.c` and object existence checking in `should_include_obj()`. Tan's proposed solution to make `should_include_obj()` return 0 for absent objects is now being validated against the new reproduction case, moving the thread closer to having a testable fix. The bug appears specific to promisor pack operations introduced in v2.48.0, with the main blocker now being confirmation of the fix approach before implementation.
