Thread identity: Feature proposal for a new `git rebase-checkout` command to avoid unnecessary rebuilds during rebase in large codebases, initiated by Ramkumar Ramachandra.

Core problem: Current rebase workflow in large projects like LLVM triggers full rebuilds due to timestamp changes during conflict resolution, even when no actual content conflicts exist. This is particularly painful in CMake-based builds where timestamp changes force reconfiguration.

Proposed solution: Introduce `git rebase-checkout` that would:
1. Create new branch based on target (e.g. main)
2. Cherry-pick commits from source branch
3. Rename new branch to replace old one
This preserves original commit timestamps rather than updating them as in standard rebase.

Key technical details:
- Targets workflow pain point in large codebases with expensive rebuilds
- Could theoretically be implemented via existing plumbing (cherry-pick + branch rename)
- Would provide first-class command for this optimization

Current status: Initial proposal stage, seeking feedback on general usefulness for inclusion in core Git.

Open questions:
- Whether this optimization is broadly useful enough for core Git
- Potential edge cases in timestamp preservation behavior
- Alternative implementation approaches

Participant positions:
- Ramkumar Ramachandra proposing the feature based on LLVM workflow experience

Related work: Build system interactions with version control (particularly CMake), existing rebase alternatives like `git rerere`.
