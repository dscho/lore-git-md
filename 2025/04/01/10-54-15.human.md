This is a feature proposal addressing a workflow pain point in large codebases. Ramkumar Ramachandra describes a common scenario when working with LLVM: frequently rebasing feature branches against a fast-moving main branch triggers unnecessary rebuilds due to timestamp changes, even when there are no actual conflicts. The rebuilds persist despite using ccache because CMake reconfiguration and custom build tools still process the changed files.

The proposal suggests a new `git rebase-checkout` command that would create a cleaner rebase workflow by: (1) making a new branch from main, (2) cherry-picking the commits from the old branch, and (3) renaming the result back to the original branch name. This approach would theoretically preserve file timestamps when no content changes occur during rebase.

While acknowledging this could be scripted with existing Git plumbing, Ramkumar is gauging interest in having it as a core feature. The proposal seems well-motivated for large-project workflows where rebuild costs are significant, though it's unclear how widely this pain point affects other Git users. The email doesn't include a concrete implementation, focusing instead on validating the concept's usefulness.
