This is a refactoring and bugfix patch targeting Git's parse-options infrastructure, specifically the `OPTION_INTEGER` type handling. It's part 2 of a 5-patch series (no cover letter context provided).

The patch addresses several issues with integer option parsing:
1. The current implementation uses `int` for storage but doesn't verify the passed pointer has sufficient size, risking buffer overflows
2. It uses `strtol()` which returns `long` but casts to `int`, potentially truncating values
3. There's no way to handle integers larger than `INT_MAX` even when the underlying variable could support them

The solution introduces a `precision` field to track the size of the target variable (1, 2, 4, or 8 bytes) and uses `strtoimax()` for parsing. Range checking is added based on the precision. The patch updates several builtin commands (`fmt-merge-msg`, `merge`, `show-branch`, `tag`) to include the new precision field, and adds tests verifying the new 16-bit integer handling.

Key technical details for future reference:
- New `precision` field in `struct option` tracks integer size
- Uses `strtoimax()` instead of `strtol()` for parsing
- Range checks based on precision (e.g. -32768 to 32767 for 16-bit)
- Test case demonstrates 16-bit integer handling and range checking
- Follow-up will address signedness verification (mentioned but not implemented here)
