The thread explores ways to optimize rebase workflows in large codebases where timestamp changes during conflict resolution trigger unnecessary rebuilds. Ramkumar Ramachandra originally proposed a new `git rebase-checkout` command that would cherry-pick commits while preserving original timestamps, avoiding the rebuild issue common in CMake-based projects like LLVM.

Brian m. carlson has now suggested that the experimental `git replay` command might address this need without requiring a new command. Unlike standard rebase, `git replay` performs non-interactive rebases without touching the working tree or index, and by default doesn't update references (requiring explicit piping to `git update-ref`). While currently marked experimental, this existing functionality could potentially solve the timestamp preservation problem while using established plumbing.

The discussion now centers on whether `git replay` can fully satisfy the use case or if the proposed `rebase-checkout` still offers unique advantages. Key open questions include the stability and future of the experimental `replay` command, and whether its reference update behavior provides sufficient workflow ergonomics compared to a purpose-built solution. The thread has shifted from evaluating a new proposal to comparing implementation approaches for solving the underlying timestamp preservation challenge.
