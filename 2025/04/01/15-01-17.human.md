This is a refactoring and bugfix patch that improves integer handling in Git's parse-options API. It's part 2 of a 5-part series (though no cover letter was provided for context).

The patch addresses several subtle issues with `OPTION_INTEGER` parsing:
1. Currently there's no size checking when storing parsed integers, risking overflow/underflow
2. The parsing uses `strtol()` which returns a `long`, but stores to an `int` without proper range checking
3. Callers can't specify they want to handle larger integers than `int` can hold

The solution introduces a `precision` field that tracks the size of the target integer variable (via `sizeof`), allowing proper range checking and support for different integer sizes (8/16/32/64-bit). It also switches to `strtoimax()` for parsing to handle larger values. The patch updates several builtin commands to use the new field and adds tests verifying the range checking works.

The changes are well-motivated and the implementation looks thorough, with test coverage for the new behavior. This appears to be a solid improvement to a potentially dangerous area of the codebase.
