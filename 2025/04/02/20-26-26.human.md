Refactoring in the reftable API series. This is a review comment on patch 6/16 of Patrick Steinhardt's reftable refactoring series, which aims to improve the API's clarity and structure for external consumers.

Justin Tobler suggests a further naming improvement to accompany the rename from `reftable_block` to `reftable_block_data`. While he agrees with the overall direction, he points out that the subsequent patch's rename of `block_reader` to `block` would create awkward `block->block` member access patterns. He proposes changing the member name from `block` to `data` for better readability.

This is a pattern seen throughout the review thread - while the technical implementation of the refactoring is sound (as Justin confirmed in patches 4-5), reviewers are helping polish the API's ergonomics. The suggestion is minor but shows careful attention to how the API will be used in practice. The change would affect several files but would be straightforward to implement as part of the ongoing series.
