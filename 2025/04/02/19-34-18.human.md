This is a discussion about the potential benefits of standardizing change IDs in Git commits, particularly for code review workflows. Remo Senekowitsch builds on Martin von Zweigbergk's initial proposal by highlighting how a `change-id` header could improve patch tracking across different development models.

The email makes a strong case for how change IDs would benefit not just Gerrit-style workflows, but also modern forge platforms (GitHub/GitLab) and traditional mailing list projects. The key insight is that change IDs would help reviewers track patch evolution across revisions, whether those come as force-pushes in PRs or as new patchset emails. This addresses current pain points where reviewers either lose context with force-pushes or deal with messy fixup commit chains.

Senekowitsch notes that mailing lists currently handle this better than forges by preserving all patch versions, but lack tooling to intelligently connect related versions. A standardized ID could enable new mailing list tools to show interdiffs between patch revisions - functionality that's proven valuable in Gerrit but could benefit the entire ecosystem.

The argument is well-constructed and adds meaningful perspective to the standardization effort, showing how it could unify and improve code review across Git's diverse collaboration models. The email doesn't propose technical implementation details, but makes a compelling case for why Git itself should support the header rather than leaving it to individual tools.
