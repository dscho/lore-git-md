This thread continues the discussion about standardizing change IDs across version control tools, with a focus on how Git might implement them while maintaining compatibility with tools like Jujutsu. The latest contribution from Nico Williams adds an important temporal dimension to the conversation, clarifying that the need for unique change IDs varies across different phases of development.

The discussion has evolved from initial philosophical differences (particularly around Jujutsu's automatic descendant rewriting versus Git's detached HEAD model) to concrete technical proposals. Two main implementation approaches have emerged: one using Git refs (`refs/change-IDs/`) to store change ID mappings, and another proposing auxiliary data structures that might integrate with the commit graph. Patrick Steinhardt has been actively working on extending `rev-parse` to support change IDs, while also considering how to handle rebase and cherry-pick operations.

Williams' latest input reinforces that change IDs serve different purposes during active development (where uniqueness is important) versus after merging (where tracing history becomes more important than uniqueness). This insight helps frame why tools might implement change IDs differently while still aiming for interoperability. The ability to trace a commit through backports and forward-ports emerges as a key use case that implementations should support.

Open questions remain about the performance characteristics of different approaches, how to handle namespace collisions, and the exact syntax for referencing change IDs. The thread continues to balance immediate technical concerns with the broader goal of cross-tool compatibility, with participants carefully considering how different implementations would affect workflows across the entire development lifecycle.
