This thread continues the discussion about standardizing Change-IDs in Git commit messages, now focusing on practical adoption challenges. The core debate centers on where to store Change-ID metadata - in commit trailers (as Junio Hamano suggested) or alternative header-like mechanisms.

Oswald Buddenhagen raised important user experience concerns about trailers being visually intrusive, particularly for small projects. Jacob Keller has now reinforced this with a concrete example from Linux kernel development, where Change-ID trailers were rejected specifically because they were considered "eye sores" that polluted commit messages. This real-world case highlights how aesthetic concerns can be a genuine barrier to adoption, even when the technical approach is sound.

The discussion has evolved to consider three key requirements: reliable metadata storage, usable editing tools, and clean visual integration. While Junio's trailer-based approach remains technically viable, participants are identifying practical workflow challenges - particularly around email-based patch submission (via `git am`) and how metadata would be preserved. The Linux kernel's position serves as a cautionary example that even technically sound solutions can fail if they don't meet project aesthetic standards.

No clear resolution has emerged yet, but the thread is now focused on implementation quality and adoption feasibility. The next steps appear to involve either: (1) developing tooling to make trailers less intrusive while maintaining their technical benefits, or (2) exploring header-like storage mechanisms that might better preserve metadata through email workflows without visual pollution. Both approaches would need to address the version history ambiguity cases that have been raised earlier in the thread.
