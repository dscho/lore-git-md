This thread continues the discussion about standardizing Change-ID generation methods, now with three distinct approaches on the table. The debate began with Martin von Zweigbergk advocating for Jujutsu's random generation method, which has proven effective operationally. brian m. carlson then raised security concerns about random IDs potentially leaking sensitive data and proposed deterministic alternatives using SHA-256 or HMAC-SHA-256, citing Git's design principles and upcoming stash functionality as requiring determinism.

D. Ben Knoble has now introduced a third approach, suggesting content-based tracking similar to Git's rename detection. His proposal would compare commit trees rather than messages, using Git's existing range-diff functionality as a model. This offers a middle ground that aligns with Git's native capabilities while still providing stable change tracking.

The discussion now balances three competing priorities: Jujutsu's operational simplicity with random IDs, security-conscious deterministic hashes, and Git-compatible content-based tracking. Each approach has merit - random IDs work well in practice, deterministic methods address security concerns, and content tracking leverages Git's existing strengths. The thread remains open on which direction standardization should take, with the security considerations raised by brian m. carlson adding weight to the deterministic side while Knoble's suggestion provides an alternative path that might satisfy both workflow and compatibility needs.
