This thread continues the discussion about standardizing Change-IDs in Git commit messages, with a focus on how they should behave during cherry-picking operations and whether uniqueness should be enforced. The conversation has evolved to consider three main approaches: strict uniqueness, branch-aware tracking, and forge-specific enforcement.

The latest contribution from Toon Claes provides valuable real-world context from GitLab's implementation. GitLab handles version tracking through its merge request UI and branch history rather than relying on Change-IDs, storing this metadata outside Git's object database. This suggests Change-IDs may be more critical for mail-based workflows (like Git's own development process) or tools like Jujutsu that don't have built-in branch tracking.

Key points of contention remain: whether Change-IDs should uniquely identify commits (making cherry-picks problematic) or follow changes across branches, and whether enforcement should happen at the Git level or be left to individual forges. Martin von Zweigbergk's forge-based enforcement proposal and Williams' cherry-pick propagation approach represent different solutions to these challenges. Junio Hamano has yet to weigh in definitively but has emphasized the need to consider tooling impacts.

The thread shows no clear consensus yet, but the GitLab example provides concrete data about how one major platform solves similar problems through different means. This helps ground the abstract standardization discussion in practical implementation realities. The core tension remains between semantic purity (where Change-IDs would have strict rules) and workflow flexibility (where different tools and platforms might handle tracking differently).
