This thread explores how Git handles symlinks when the `core.symlinks` configuration changes, particularly focusing on Windows environments. The discussion began with Andrej Zhilenkov questioning whether Git should automatically convert between symlinks and regular files when this setting is modified. Maintainer brian m. carlson clarified this is intentionally unsupported behavior, comparing it to similar design decisions in Git LFS.

The conversation has evolved to highlight Windows-specific challenges. Creating symlinks on Windows requires elevated privileges unless Developer Mode is enabled, and corporate environments often restrict these permissions. Git for Windows defaults to disabled symlinks due to these constraints. While brian m. carlson maintains that global enablement is the preferred solution, Zhilenkov's latest response notes practical concerns remain. Many Windows users incorrectly configure symlinks at the repository level rather than system-wide, and some may need symlink support only for specific repositories without wanting to change global settings.

Key open questions include whether documentation should better explain Windows privilege requirements, if someone might implement a checkout re-evaluation mechanism, and how to balance security constraints with usability. The thread continues to explore whether the current behavior creates unnecessary hurdles for Windows users who need per-repository control over symlink handling.
