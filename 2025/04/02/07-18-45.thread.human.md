This thread explores the behavior of Git's symlink handling when the `core.symlinks` configuration changes after repository creation. The discussion was initiated by Andrej Zhilenkov, who encountered issues when toggling this setting. Maintainer brian m. carlson confirmed this is an intentional design limitation - `core.symlinks` acts as a filesystem capability hint set at repository creation, similar to `core.filemode`, and Git doesn't automatically convert between symlinks and regular files when this setting changes.

The thread has evolved with Zhilenkov providing a concrete Windows use case: Git for Windows defaults to disabled symlinks, and users may only discover they need symlinks after cloning. The current workaround (manually removing symlinks before re-checkout) is cumbersome, prompting the suggestion for an automated refresh mechanism. While Unix use cases remain hypothetical, the Windows scenario adds weight to considering improved workflows.

The maintainer has drawn parallels to similar challenges in Git LFS and left the door open for contributions that might address both cases. Key open questions remain about documentation improvements, specific use cases justifying design changes, and potential implementation of a checkout re-evaluation mechanism.
