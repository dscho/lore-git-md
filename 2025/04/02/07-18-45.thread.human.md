This thread explores Git's handling of symlinks when the `core.symlinks` configuration changes, particularly focusing on Windows environments. The discussion began with Andrej Zhilenkov describing a common Windows scenario where users clone a repository with symlinks disabled (the default on Windows) only to later discover they need symlink support, requiring cumbersome workarounds.

Maintainer brian m. carlson confirmed that Git intentionally doesn't automatically convert between symlinks and regular files when `core.symlinks` changes, drawing parallels to similar challenges in Git LFS. The thread has since focused on Windows-specific considerations, where symlink creation requires elevated privileges unless Developer Mode is enabled. brian notes that while developers should ideally enable symlinks system-wide, corporate environments often prevent this, creating tension between security constraints and functionality needs.

The discussion remains open on several fronts: whether to improve documentation about this behavior, the feasibility of implementing a checkout re-evaluation mechanism, and how common this scenario is in practice. The maintainer has provided concrete examples from both Windows and Unix environments, noting that symlink functionality tends to be binary (either works or doesn't) rather than something that can gracefully degrade.
