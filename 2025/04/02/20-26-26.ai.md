This is a naming suggestion in the reftable API refactoring series. Justin Tobler responds to Patrick Steinhardt's patch 6/16 which renamed `struct reftable_block` to `struct reftable_block_data` to better reflect its role as a pure data container. The change was part of clarifying the distinction between data storage (`reftable_block_data`) and access logic (to be renamed to `reftable_block` in the next patch).

Justin proposes an additional refinement: renaming the `block` field within `struct block_reader` to `data` to avoid the potentially confusing `block->block` syntax that would result from the upcoming rename of `block_reader` to `block`. This is a minor but logical suggestion that would improve code readability without affecting functionality.

The suggestion is narrowly focused on naming consistency within the reftable block reader subsystem (`reftable/block.[ch]`). It doesn't challenge the technical approach of the series, which has already received positive reviews for patches 4-6. The thread context shows this is part of a mature refactoring effort with only minor documentation and naming issues being discussed at this stage.
