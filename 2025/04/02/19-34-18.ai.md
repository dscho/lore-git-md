This is a discussion contribution to the ongoing change-id standardization effort, expanding on potential benefits beyond the original cross-tool interoperability focus. Remo Senekowitsch highlights how a standardized `change-id` could improve code review workflows across different Git ecosystems, particularly addressing pain points in both mailing-list and forge-based workflows.

The email makes several key observations about current workflow limitations: force-pushes in Git forges obscure review history, leading to suboptimal workarounds like fixup commits, while mailing lists lack tooling to track patchset evolution. The proposed `change-id` could enable better version tracking and interdiff generation for both forge PRs and mailing list patches. 

Senekowitsch specifically notes this would help mailing-list-oriented projects like Git and Linux kernel development by providing infrastructure to associate patch versions across resubmissions, similar to Gerrit's model. The argument positions the change-id as a foundational element for building better review tooling across all Git collaboration models.

The contribution doesn't propose technical changes to the standardization effort itself, instead reinforcing its value by identifying additional stakeholders (standalone review tools and Git forges) and use cases (interdiff generation, patchset tracking) that would benefit from the header. This expands the discussion beyond the original tool-specific implementations to broader ecosystem impacts.
