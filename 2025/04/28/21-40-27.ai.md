This is a review comment from Junio Hamano on patch 6/13 of Patrick Steinhardt's object store cleanup series, focusing on the justification for the API changes.

Junio notes that while the commit message describes the new `has_object()` API as having "better defaults" (not fetching promisor objects or reloading packfiles by default), it doesn't sufficiently explain why these defaults are preferable. He suggests the justification would be clearer if shown that most callers don't actually want these behaviors, and that the few callers that do could explicitly opt-in with flags (or handle fetching themselves after a failure). This critique applies to both this patch and the previous one in the series.

The comment doesn't raise any technical concerns about the implementation itself, which has already been reviewed and approved by Karthik Nayak. Rather, it's a documentation-level suggestion to improve the commit message's rationale. This fits with the series' broader goal of cleaning up the object store API as part of the `the_repository` removal effort, where clear communication of design decisions is important for maintainability.

Key technical context for future reference:
- The series replaces `repo_has_object_file()` with `has_object()`
- New behavior avoids promisor fetches (`HAS_OBJECT_FETCH_PROMISOR` flag needed to enable)
- Also avoids packfile reloads by default
- Patch 6 handles "trivial conversions" across the codebase
- Junio's point suggests the commit message could better articulate the design philosophy behind these defaults
