This is a technical discussion about promisor object handling in reference validation, part of Patrick Steinhardt's object store cleanup series. Junio Hamano raises an important question about the patch that changes `ref_resolves_to_object()` to skip promisor object fetching when validating references.

The core issue is whether reference validation should consider objects that exist only in promisor remotes as "valid". The patch changes the behavior to only check local objects (with packed object rechecking), which makes the validation stricter. Junio points out this changes the definition of a "broken" reference - previously it meant "not available locally or from promisors", but now means only "not available locally".

The discussion touches on trust models - whether we should assume references should only point to objects we've already fetched, or whether it's acceptable to point to objects we could fetch on demand. The one-line code change itself is straightforward, replacing the old `repo_has_object_file()` call with the new `has_object()` API, but the semantic implications for partial clone workflows need careful consideration.

This is one of two remaining open questions (along with the collision check behavior in patch 7) that need resolution before this otherwise well-reviewed series can be integrated. The exchange shows the careful balancing required when changing low-level object storage behavior that affects multiple subsystems.
