This is a bug report about inconsistent behavior in shallow submodule checkouts. Pavel Pavlov demonstrates that when checking out a submodule from a non-default GitHub branch, Git unexpectedly fetches the entire history rather than doing a shallow clone as expected. He provides two test repositories showing the difference - one works correctly (2.9MB checkout) while the other incorrectly fetches the full history (34MB). 

The key observation is that this behavior depends on GitHub's default branch settings - shallow checkouts fail when the submodule points to a non-default branch. The issue appears to be either in Git's submodule handling or GitHub's branch resolution logic. While the working tree contents end up identical, the incorrect case wastes significant bandwidth and storage.

The report is well-documented with clear reproduction steps and test repositories, making it doesn't propose a solution but cleanly demonstrates a real performance problem that affects users with large submodules or slow connections. The next step would likely be investigation into whether this is a Git bug or GitHub-specific behavior.
