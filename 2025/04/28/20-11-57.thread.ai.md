Git thread summary:

Bug report and proposal to improve `git branch -f` output clarity. Junio Hamano identifies confusing behavior where the command redundantly reports "set up to track" messages even when no tracking configuration changes, while failing to indicate branch tip movement - the more operationally significant information.

Current behavior in branch.c always shows tracking setup messages for branches with existing remote tracking, creating noise. Three specific improvements proposed: (1) only show tracking messages when relationship actually changes, (2) enhance messages to show previous tracking config (when available), and (3) add explicit "Reset branch" output for tip movement, similar to `git checkout -B`.

D. Ben Knoble engages with counterpoints and refinements, questioning whether suppressing tracking messages might confuse users accustomed to seeing them. They suggest enhanced messages showing previous tracking config could be preferable to suppression. Discussion explores UX tradeoffs:
- Retention of tracking messages as confirmation signals vs. verbosity
- Information loss considerations with force flags like `-f`
- Potential message formats displaying old/new tracking configs
- Parallels to `git checkout -B`'s branch movement reporting
- Broader principles around force flag requirements

The changes would affect output formatting logic in branch.c while maintaining backward compatibility. The thread remains in design refinement phase, seeking consensus on desired behavior before implementation. No patches submitted yet; focus is on nailing down UX improvements for users frequently resetting branches with `-f`. Key open questions center on message verbosity tradeoffs and whether to modify or suppress existing tracking notifications.
