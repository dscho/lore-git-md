This is a technical discussion about the behavior of the proposed `git-blame-tree` command in merge scenarios. Junio Hamano raises important edge cases regarding how the command should determine "most recent modification" in histories with merges, particularly how it should handle "ours" vs "theirs" merge strategies.

The email points out two key gaps in the current RFC series: lack of end-user documentation (expected at this stage) and missing test coverage for merge scenarios. Hamano presents two topological examples where the behavior might be ambiguous - one where a path changes on one branch but stays constant on another, and another where the merge direction is reversed.

The core question is whether the command should consider the merge commit itself as the modification point (when it selected one version over another) or the original commit where the content last changed. This becomes particularly relevant when dealing with tree-level changes rather than individual files. The absence of tests for these cases suggests the behavior may not yet be fully specified or implemented.
