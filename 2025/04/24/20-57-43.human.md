This is a bug report about unexpected behavior in `git for-each-ref` when handling push tracking information for newly created local branches. Sam Harwell reports that when querying push tracking status for an unpushed local branch, the command incorrectly shows the branch as "gone" and includes the remote tracking ref in the output, rather than showing empty values as expected.

The issue occurs in a complex remote configuration setup designed to mimic GitHub's fork workflow in Azure DevOps. The reporter provides detailed remote configurations showing how different remotes handle branch mappings, particularly for user-specific branches in a `dev/user/branch` format. The key problem is that `for-each-ref` seems to be prematurely calculating push tracking information based on the refspec configuration, even for branches that haven't been pushed yet. This manifests when using format placeholders like `%(push:track,nobracket)` and `%(push)`.

The bug appears in Git 2.49.0 on Windows, though it's unclear if this is platform-specific. The report is well-documented with clear reproduction steps, expected vs actual behavior, and relevant configuration details, making it easy to investigate. This seems like a legitimate edge case in the refspec handling logic that could affect users with similar complex remote setups.
