This is a bug report about unexpected behavior in `git for-each-ref` when handling push tracking information for unpushed local branches. The issue occurs in a complex remote configuration setup where multiple remotes have different refspec mappings for branches.

Sam Harwell reports that when querying tracking information for a new local branch that hasn't been pushed yet, `git for-each-ref` incorrectly shows the branch as "gone" for push tracking and displays the remote tracking ref instead of an empty string. The expected behavior would be to show empty values since the branch hasn't been pushed to any remote.

The bug manifests when using the `%(push:track,nobracket)` and `%(push)` format specifiers with a local branch that exists only in `refs/heads/`. The report includes detailed remote configuration showing three different remotes with distinct fetch/push refspec mappings, suggesting the issue may relate to how Git handles push tracking calculations in multi-remote setups.

The bug appears well-documented with clear reproduction steps and expected/actual behavior comparison. It affects Git 2.49.0 on Windows, though the platform may not be relevant to the core issue. The reporter's configuration shows a non-trivial remote setup attempting to emulate GitHub's fork workflow in Azure DevOps, which may help reproduce the issue.

Key technical details for future reference:
- Format specifiers involved: `%(push:track,nobracket)`, `%(push)`, `%(upstream:track,nobracket)`, `%(upstream)`
- Remote config shows complex refspec patterns with branch name rewriting
- Issue occurs with local branches that haven't been pushed yet
- Actual output shows "gone" status and remote ref when empty values were expected
