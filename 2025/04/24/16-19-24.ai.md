Feature proposal with open design questions about merge behavior.

Junio Hamano raises important questions about how the proposed `git-blame-tree` command should handle merge commits when determining the "most recent modification" of a path. The current implementation (as described in the thread) walks history backwards tracking path states, but the RFC lacks documentation and test coverage for merge scenarios.

The core uncertainty centers on merge semantics: when a path's content comes from one side of a merge (like in the example where B` is merged into a branch containing modifications), should the command attribute the change to the merge commit itself, to the last modification on the winning side, or follow some other logic? Hamano provides two concrete topology examples where this distinction matters, noting that neither the documentation nor test suite currently addresses these cases.

This email doesn't propose solutions but highlights a gap in the RFC's design needs to resolve before finalization. The question touches on fundamental version control semantics and will affect how users interpret the command's output in real-world merge-heavy histories. The thread context shows this joins other open questions about naming and behavior that remain before the feature can graduate from RFC status.
