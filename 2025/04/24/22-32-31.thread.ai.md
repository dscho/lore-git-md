Git thread summary: Discussion about supporting symlinks in `.git` internals, particularly `objects/`, prompted by Git LFS compatibility issues with Android's `repo` tool. Current behavior shows problems with path canonicalization when operations run from symlinked `.git/objects`, causing failures in Git LFS's directory detection. Maintainer Junio C Hamano clarifies the project's stance, distinguishing between symlinking individual subdirectories (an existing but unsupported practice, as used by `git-new-workdir`) and symlinking the entire `.git` directory (not intended to be supported). The response endorses brian m. carlson's position that Git should take a clear stance - either properly support the pattern with tests or explicitly discourage it with warnings. Multiple worktree support uses a different mechanism (`.git` as regular file) that shouldn't be confused with direct symlinking.

Open questions remain about whether to: (1) officially support symlinking specific internal directories with test coverage, (2) explicitly discourage it via warnings, or (3) maintain current behavior. Technical considerations involve filesystem edge cases, path resolution, and compatibility tradeoffs affecting both core and tools like Git LFS. Unknown how alternative implementations (JGit, Game of Trees) handle such symlinks. The discussion has progressed from problem identification to establishing boundaries between acceptable and unacceptable symlinking patterns, with maintainer input moving the conversation toward requiring a documented position.
