This is a technical follow-up in the `git send-email` OAuth2/Outlook patch series, specifically addressing the Outlook Message-ID handling patch (2/3). Greg Kroah-Hartman raises an important consideration about enterprise Outlook deployments that wasn't covered in the current implementation.

The patch currently detects Outlook servers via hardcoded hostnames (`smtp.office365.com` and `smtp-mail.outlook.com`), but Greg points out this won't cover company-hosted Outlook servers that may exhibit the same Message-ID behavior. He suggests making this detection configurable rather than hardcoded, which would allow enterprise users to opt-in to the Outlook-specific Message-ID handling when needed.

This feedback directly relates to Brian M. Carlson's earlier concern about CNAMEs and Outlook detection robustness. The current implementation's hostname-based detection appears too narrow for real-world Outlook deployments. Greg's suggestion of a config variable would provide a more flexible solution that could handle both Microsoft-hosted and enterprise Outlook servers while avoiding false positives.

The core Message-ID extraction logic itself isn't questioned - the technical approach of parsing the SMTP response for the correct Message-ID remains sound. This is purely about improving the detection mechanism's coverage. The thread shows the authors have been responsive to feedback through multiple iterations, so we can expect this suggestion to be addressed in a future version.
