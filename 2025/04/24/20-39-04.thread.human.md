This thread has been discussing improvements to signature handling in Git's `fast-export` and `fast-import` commands, with a particular focus on how to clearly communicate that these features are still experimental. The discussion started with technical implementation questions, moved through policy debates about when to change default behaviors, and has now settled on refining the documentation to properly set user expectations.

Junio Hamano, the Git maintainer, has taken a pragmatic approach - keeping the current default behavior (which strips signatures) while clearly marking the new `--signed-commits` option as experimental in the documentation. Christian Couder and others have contributed to refining how we communicate this experimental status, suggesting additional clarity about potential future changes to default behaviors. While there's agreement that the features need an experimental label, there are subtle differences in opinion about how explicitly to document possible future default changes.

The technical implementation currently:
- Marks `--signed-commits` as experimental in all relevant documentation
- Maintains the original default behavior (equivalent to `strip` mode)
- Includes warnings about potential future signature format changes
- Has removed the temporary `FAST_EXPORT_SIGNED_COMMITS_NOABORT` escape hatch
- Contains test cases verifying the current behavior matches `strip` mode

Some technical questions remain unresolved, particularly around test failures from earlier approaches and how signatures will ultimately be handled in the protocol. But for now, the thread has reached consensus on the documentation approach while deferring deeper technical decisions about signature formats. The discussion shows how the project balances introducing new capabilities with maintaining stability and clear communication about feature maturity.
