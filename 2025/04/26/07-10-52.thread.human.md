This thread addresses a bug in how Git handles commit decorations for replace refs that are organized in nested paths (e.g., `refs/replace/2012-migration/abc123`). While the replace mechanism itself correctly processes such refs, the decoration logic was only stripping the base `refs/replace/` prefix, leading to warnings and missing decorations.

The patch fixes this by making the decoration logic consistent with how replace refs are registered - it now properly handles nested paths by finding the object ID after the last slash in the refname. The change comes with two new test cases verifying both the decoration behavior and basic functionality of nested replace refs.

The fix is focused and low-risk, as it doesn't modify core replace functionality but rather aligns the decoration logic with existing behavior. This will benefit users who organize their replace refs hierarchically, though such usage patterns appear to be relatively uncommon in practice. The patch includes appropriate test coverage and a clear commit message explaining both the problem and solution.
