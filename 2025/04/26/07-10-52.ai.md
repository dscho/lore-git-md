This is a bugfix patch addressing an inconsistency in how Git handles structured paths for replace refs. The issue affects commit decoration when replace refs are organized in nested paths under refs/replace/.

The core problem is that while `register_replace_ref()` correctly handles replace refs in subpaths (like refs/replace/2012-migration/abc123), the decoration logic in `log-tree.c` was only removing the "refs/replace/" prefix, causing warnings and missing decorations. The patch fixes this by making the decoration logic use the same "last part of ref path" approach as the replace registration code.

The changes are:
1. Modified `add_ref_decoration()` to find the object ID by looking for the last slash in the refname rather than assuming it immediately follows "refs/replace/"
2. Added two new test cases:
   - One in t4207-log-decoration-colors.sh verifying decorations work with nested replace paths
   - Another in t6050-replace.sh testing basic functionality of replace refs in nested paths

The patch appears well-constructed with clear commit message explanation and appropriate test coverage. This fixes a real inconsistency that would affect users who organize their replace refs hierarchically, though such usage may be relatively uncommon. The change is low-risk as it doesn't modify the core replace functionality, just aligns the decoration logic with existing behavior.
