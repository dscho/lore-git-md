This is a conceptual response in the ongoing Change-ID discussion, addressing Junio Hamano's fundamental concerns about the semantics of change tracking in Git.

Nico Williams proposes a two-ID system to handle the rebase/split/squash scenarios that Junio highlighted as problematic. The key idea is separating:
1. A "code review ID" that persists across all versions of a changeset during review
2. A "commit change ID" that tracks sufficiently similar versions of individual commits

Nico argues this dual approach would maintain review continuity while allowing for commit transformations. He suggests the code review ID would be more suitable for ref-based usage (like in the original `git switch` proposal), though remains skeptical about needing per-commit symbolic names for porting purposes.

The response also pushes back against Junio's skepticism about Change-ID semantics deserving commit header status, arguing that project-specific interpretations (like URI templates for finding concluded reviews) are sufficient without requiring universal mechanical precision. Nico maintains that the implementation details can vary while preserving the core utility of tracking changes through review cycles.

This moves the discussion forward by offering a concrete technical approach to the workflow contradictions Junio identified, while defending the fundamental value proposition of Change-IDs despite their inherent fuzziness in some scenarios. The proposal attempts to balance Git's mutable history model with the desire for stable change references during code review.
