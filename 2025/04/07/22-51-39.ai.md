This is a conceptual response in the ongoing Change-ID standardization discussion, addressing Junio Hamano's concerns about the fundamental utility of Change-IDs in Git workflows. Remo Senekowitsch presents several key points:

First, they clarify technical aspects of Change-ID ergonomics, noting that Jujutsu's implementation uses a "reverse-hex" alphabet and mutable/immutable commit distinction to enable short memorable identifiers (1-3 characters) for working commits. While not currently in Git, this demonstrates potential usability benefits.

The response then tackles Junio's core objections about rebasing and commit transformations. Remo argues that Change-IDs remain useful even when commits are rebased, as review tools can automatically recognize morally equivalent commits by comparing both the ID and content. For the 20% case where commits are split or combined, they acknowledge Change-IDs don't perfectly solve these scenarios but argue the ambiguity doesn't cause practical problems - tools can still track evolution meaningfully.

Most significantly, Remo introduces a new workflow scenario they consider more common than Junio's 80/20 split: stacked patchsets where multiple interdependent commits evolve together through rebases and amendments. Here Change-IDs provide clear value by tracking individual commit evolution across transformations while maintaining relationships between commits in the stack.

The email maintains that while Change-IDs don't solve all version control problems, their benefits for common workflows justify standardization, and semantic disagreements between tools are unlikely to hamper interoperability. The response attempts to shift the discussion from abstract concerns to concrete, frequently-encountered workflow patterns where the feature proves valuable.
