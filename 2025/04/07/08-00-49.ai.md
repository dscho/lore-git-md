This is a technical discussion about implementation approaches for Change-ID storage in Git, continuing the ongoing standardization effort between Gerrit, GitButler, and Jujutsu.

Patrick Steinhardt responds to Nico Williams' proposal to use Git refs (`refs/change-IDs/`) as a storage mechanism for Change-IDs, expressing several concerns. He argues that refs are problematic because they can be modified by remote users in ways that could corrupt the Change-ID mapping, requiring special handling that would complicate Git's core refs subsystem. He also reiterates that Change-IDs are not always unique, making the single-commit-per-ref model fundamentally mismatched. While acknowledging Nico's suggestion to have refs point to objects listing multiple commits, Patrick finds this approach increasingly awkward and remains unconvinced about using refs for this purpose.

The exchange highlights key technical challenges in the Change-ID implementation: the tension between mutable refs and immutable Change-IDs, namespace pollution concerns, and the need to handle non-unique identifiers. Patrick's response suggests preference for an auxiliary data structure approach over ref-based storage, though he doesn't propose an alternative here. This continues the thread's exploration of implementation tradeoffs between ref-based solutions and other approaches like commit graph integration or separate indexing.
