This is a refactoring patch in Patrick Steinhardt's reftable API series, specifically addressing naming consistency in the block handling code. The patch renames `struct block_reader` to `struct reftable_block` and updates all related functions to match this new naming scheme (e.g., `block_reader_init` becomes `reftable_block_init`).

Justin Tobler had previously suggested renaming the internal `block` field to `data`, but notes that this would create the awkward `block->data.data` access pattern. Patrick agrees with the concern and instead opts to rename the field to `block_data` for clarity while avoiding the chained access issue.

The change is purely mechanical - renaming types and functions without altering behavior - and continues the series' goal of improving API clarity for external consumers. This follows Patch 6's similar renaming of `struct reftable_block` to `struct reftable_block_data`, showing a systematic approach to type naming in the reftable subsystem.

Key technical details:
- Affects `reftable/block.c` with function and type renames
- Updates all callers to use new `reftable_block` naming
- Field renamed from `block` to `block_data` to avoid confusion
- Part of broader effort to make reftable API more standalone-friendly
- No behavior changes, just naming improvements
- Follows naturally from previous patch's type renaming
- Maintains consistency with series' API design goals

The change appears uncontroversial, with Justin Tobler effectively approving the approach in his review comment. This continues the positive review trend for this mature refactoring series.
