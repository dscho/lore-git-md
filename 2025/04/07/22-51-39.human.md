This is a conceptual response in the ongoing Change-ID standardization discussion, addressing Junio Hamano's concerns about the practical utility of Change-IDs in Git workflows.

Remo Senekowitsch defends the Change-ID proposal by focusing on real-world usage patterns. He highlights how Jujutsu's implementation shows practical ergonomics (using short, memorable reverse-hex identifiers) and suggests this could be adapted for Git. The key arguments address:

1. **Rebasing Workflows**: Change-IDs help tools automatically recognize morally equivalent commits after rebasing, allowing review tools to mark rebased commits as "already reviewed" when content is unchanged. This maintains review continuity despite history rewriting.

2. **Commit Splitting/Combining**: While acknowledging these operations create ambiguity about which commit inherits the Change-ID, Remo argues this doesn't cause practical problems - tools can clearly show what changed, and some review context may be lost but the core tracking remains useful.

3. **Primary Use Case**: Contests Junio's 80/20 split, emphasizing that Change-IDs shine most for complex patchset maintenance (like stacked PRs) where commits are constantly rebased and amended while maintaining dependencies. This is presented as a more common scenario than Junio suggested.

The response maintains that while Change-IDs don't solve all version control problems, their benefits for common collaborative workflows justify standardization, and semantic disagreements between tools are unlikely to cause interoperability issues. The tone is pragmatic, focusing on demonstrated utility rather than theoretical purity.
