This is a technical discussion about implementing Change-ID tracking in Git, specifically debating the use of Git refs as a storage mechanism. Patrick Steinhardt responds to Nico Williams' proposal to use `refs/change-IDs/` for tracking Change-IDs by raising two main concerns:

1. **Security and integrity risks**: Patrick argues that using refs would allow remote users to potentially corrupt repositories by pushing malformed Change-ID references. While workarounds exist (like special handling of these refs), he believes this would add problematic complexity to Git's core systems.

2. **Non-uniqueness mismatch**: He reiterates that Change-IDs aren't always unique (a point previously established in the thread), while refs can only point to single commits. Though Nico suggests using intermediate objects to list multiple commits, Patrick finds this approach increasingly awkward.

The exchange highlights the ongoing tension between leveraging existing Git mechanisms (refs) versus creating new specialized infrastructure for Change-ID tracking. Patrick's skepticism suggests this implementation path may face resistance unless these concerns are addressed, though the discussion remains technical rather than dismissive. The thread continues to explore alternative approaches to this cross-tool standardization effort.
