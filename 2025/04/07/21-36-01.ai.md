This is a conceptual response in the ongoing Change-ID standardization discussion, specifically addressing Junio Hamano's fundamental concerns about the semantics of change tracking in Git workflows.

Nico Williams proposes a two-tiered Change-ID system to address Junio's critique about commit splitting/combining scenarios. The first tier would be a "code review ID" that persists across all versions of a change during review (including splits and squashes), while the second would be a "commit change ID" that tracks individual commit versions. This aims to resolve the semantic ambiguity Junio highlighted about which commits should inherit which IDs during history rewriting.

The response also pushes back against Junio's skepticism about Change-ID header placement, arguing that while the semantics may be project-specific, the core utility (linking review iterations and finding approved changes) is consistent enough to warrant first-class treatment. Nico suggests the exact interpretation could be tool-specific while maintaining a common interface pattern (likely URI-based lookup for concluded reviews).

Key technical points:
- Introduces dual-ID concept (code_review_id + commit_change_id)
- Suggests ref-based storage might work better for code review IDs
- Acknowledges but downplays need for commit-specific symbolic names
- Proposes URI templates as a flexible resolution mechanism

This moves the discussion forward by offering a concrete mechanism to address the workflow contradictions Junio identified, while maintaining the original proposal's goals. The response doesn't fully resolve the philosophical tension between immutable IDs and mutable history, but provides a pragmatic approach to handle common code review transformations.
