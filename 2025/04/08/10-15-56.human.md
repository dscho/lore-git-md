This is a discussion about preserving commit headers during rebase operations, following up on an earlier RFC patch. Phillip Wood responds to brian m. carlson's concerns about propagating potentially malformed metadata through rebase operations.

Phillip acknowledges the validity of brian's concerns about header validation and compatibility issues, particularly regarding future Git versions. He suggests the possibility of making header preservation opt-in, but pushes back slightly on the characterization of this as "spreading corruption," noting that merging would preserve the same headers without creating new commits.

The response highlights that GitHub has been using `git replay` (which preserves headers) for rebases since mid-2023, suggesting there may be real-world use cases for this functionality. Phillip also raises an interesting point about documentation clarity around encoding of commit headers versus just the commit message.

The discussion remains open-ended, with both technical and philosophical questions about how to balance functionality (preserving useful metadata) with data integrity (preventing propagation of malformed data). Phillip invites further input from Patrick Steinhardt and others, indicating this will likely require more discussion before reaching consensus.
