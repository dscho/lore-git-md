This is a discussion about the tradeoffs of preserving extra commit headers during rebase operations, continuing the thread about Phillip Wood's RFC patch.

Junio C Hamano weighs in on the ongoing debate about header preservation in `git rebase -m`. He notes that rebase already makes selective decisions about which standard headers to preserve (like author info) versus which to drop (like parent hashes and GPG signatures). The core concern is that arbitrary extra headers have unknown semantics - the rebase machinery can't determine which should propagate versus which might become invalid or misleading after rewriting commits.

The email raises philosophical questions about header propagation safety, pointing out that even standard headers like GPG signatures lose validity when commits change. Junio suggests some headers might serve as historical markers even when technically invalid, but expresses concern about propagating truly unknown headers whose meaning might be corrupted by rebase operations.
