This is a technical discussion about Change-ID tracking in distributed Git workflows, specifically addressing Junio Hamano's concerns about commit evolution.

Martin von Zweigbergk responds to Junio's critique of Change-IDs by acknowledging their limitations in complex distributed scenarios. While Change-IDs work well for simple cases with a single remote (where the system can track rewrites like C1→C2), they break down in more complex situations - particularly when commits with the same Change-ID appear from multiple remotes without clear lineage.

The response draws a parallel to Mercurial's Changeset Evolution system, noting that Git would need similar "obsolescence graph" tracking to properly handle cases where commits are rewritten across different remotes. The key limitation is that without explicit predecessor/successor metadata, Git cannot automatically determine the evolution order when encountering Change-ID-sharing commits from previously unseen remotes.

This exchange highlights a fundamental tension in the Change-ID proposal: while useful for basic distributed workflows, the system lacks the machinery to handle the full complexity of commit evolution that Git's native reflog provides in single-repository contexts. The discussion suggests that truly robust distributed evolution tracking would require additional metadata similar to Mercurial's approach.
