Junio Hamano continues the discussion on Change-IDs by raising concerns about tracking commit evolution in distributed workflows. This is a conceptual challenge to the Change-ID proposal, focusing on how to maintain meaningful history when commits are split, combined, or modified across different contributors' repositories.

The key points are:
1. Junio questions how Change-IDs should handle commit transformations - when a single commit is split into multiple (or vice versa), which commit(s) should inherit the original ID(s)?
2. He contrasts this with reflog-based tracking, which maintains clear ordering within a single repository but doesn't work well for distributed collaboration.
3. The core issue is that Change-IDs create unordered sets of related commits, making it difficult to reconstruct the actual evolution history across different contributors' work.

This is a significant conceptual challenge to the Change-ID proposal, as it questions whether the system can adequately represent the non-linear, distributed nature of Git development. Junio suggests that some form of predecessor/successor relationship tracking would be needed to make Change-IDs truly useful for understanding how changes evolve.

The email doesn't propose solutions but rather highlights a fundamental tension between the Change-ID concept and Git's distributed nature. This continues the thread's pattern of questioning whether Change-IDs can provide enough value to justify their complexity.
