This is a discussion thread about preserving extra commit headers during rebase operations, following up on an earlier RFC patch. Phillip Wood responds to brian m. carlson's concerns about propagating potentially malformed commit metadata.

Phillip acknowledges the validity of brian's concerns about header validation and compatibility issues, particularly regarding future Git versions adding new headers. He suggests making header preservation opt-in could address some concerns, but pushes back slightly on characterizing this as "spreading corruption" since the same issues would exist if users merged rather than rebased. He notes GitHub has been successfully using `git replay` (which preserves headers) for rebases since 2023.

The response highlights an interesting documentation gap - while Git re-encodes all headers during commit message processing, the documentation only explicitly mentions encoding applying to the commit message body. Phillip asks whether `fsck` could be improved to catch more of the malformed metadata cases brian described (invalid timezones, email formats, encodings etc.), and notes that `git rebase` currently only requires headers to be parseable by the lenient `split_ident()`.

The thread remains open with both technical and philosophical questions about how to balance header preservation (useful for server-side workflows) against data integrity concerns. Phillip explicitly invites further input from Patrick Steinhardt and others on these tradeoffs. Key technical points under discussion include: opt-in mechanisms, validation requirements, documentation clarity around encoding behavior, and potential `fsck` improvements.
