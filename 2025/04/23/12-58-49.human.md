This is a discussion about Change-ID usage in Git workflows, specifically examining how GitLab handles version comparisons versus mail-based workflows.

Toon Claes provides insights into GitLab's merge request functionality, explaining how it tracks commit history for branches to enable version diffs. The key point is that GitLab's UI allows comparing any two versions of a branch through dropdown menus, maintaining this history outside Git's object storage. This contrasts with mail-based workflows where Change-IDs would serve a similar purpose of linking related commits.

The email highlights an important distinction: GitLab's approach relies on branch metadata it maintains, while Change-IDs embed the linking information directly in commits. Claes suggests Change-IDs become particularly valuable in workflows without persistent branch references (like email or Jujutsu). The discussion adds practical implementation context to the ongoing thread about Change-ID standardization, showing how different systems handle commit relationships.
