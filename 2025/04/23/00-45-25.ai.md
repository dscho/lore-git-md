This is a discussion about change tracking semantics in Git workflows, specifically examining GitLab's patch evolution capabilities versus Change-ID approaches.

Nico Williams responds to Remo Senekowitsch's analysis of GitLab's patch tracking limitations by acknowledging the UI shortcomings but maintaining that GitLab demonstrates the feasibility of tracking patch evolution without Change-IDs. The exchange highlights several key technical points: GitLab's current implementation only shows interdiffs between consecutive versions when commenting on whole diffs (not specific commits), lacks functionality to compare against latest versions, and requires browser-based workflows that some developers find cumbersome.

Williams argues that while Change-IDs could help in cases of complete commit rewrites with changed subject lines, they may not be necessary for most workflows. He notes that GitLab's current capabilities - despite their limitations - show that sophisticated tracking can be achieved without Change-IDs, though he doesn't oppose their introduction. The discussion reveals differing developer preferences between browser-based and terminal-based review workflows, with Williams expressing frustration at the context-switching required by web UIs.

This email moves the thread toward evaluating whether Change-IDs would meaningfully improve upon existing patch tracking methods that already work reasonably well in production systems like GitLab, while acknowledging that neither approach perfectly solves all evolution tracking scenarios. The tension remains between semantic purity (Change-IDs) and practical, if imperfect, existing solutions (GitLab's implementation).
