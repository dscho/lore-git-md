This is a discussion about the uniqueness requirements for Change-IDs in Git patch tracking. Nico Williams responds to Junio Hamano's point about the benefits of Git's object uniqueness by arguing that Change-IDs should not be required to be unique, as their primary purpose is to link different versions of a patch series during code review.

Williams makes several key points: First, he questions whether Git's object hash uniqueness is truly beneficial for Change-IDs, noting that while Git enforces uniqueness for objects and refs, Change-IDs serve a different purpose. He describes how Change-IDs need to be non-unique during the review process to track patch evolution, and even after approval, cherry-picking between branches could reintroduce non-uniqueness. His recommendation is clear: if Change-IDs are adopted, they should not be required to be unique.

This email adds technical nuance to the ongoing discussion about Change-ID implementation, specifically challenging the assumption that uniqueness is always desirable. It represents a pragmatic perspective focused on the real-world use case of tracking patch evolution through the review and backporting process. The argument is well-reasoned and grounded in the practical workflow needs that Change-IDs aim to address.
