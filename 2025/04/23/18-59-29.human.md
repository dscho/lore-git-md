This is a discussion about Change-ID implementation approaches in Git forges, specifically comparing GitLab's internal tracking with Change-ID headers in commits.

Nico Williams responds to Toon Claes's description of GitLab's branch tracking system, noting that GitLab appears to use internal synthetic commit IDs based on similarity checking rather than explicit Change-ID headers. The email makes several key points:

1) GitLab's approach demonstrates that server-side reflogs and similarity checking can provide much of the functionality that Change-IDs aim to solve, without requiring explicit metadata in commits.

2) While Change-IDs could help track rewritten commits, Nico argues this is a relatively rare case compared to typical commit splitting/squashing.

3) The discussion reveals two competing approaches: GitLab's server-side tracking versus Change-ID's commit-embedded metadata, with Nico ultimately favoring the former as more user-friendly.

4) Nico suggests that for backporting use cases, conventional ticket IDs in commit subjects may provide sufficient tracking without new metadata standards.

The email represents a pragmatic counterpoint in the ongoing Change-ID discussion, favoring existing mechanisms (server-side tracking, similarity checking) over new commit metadata standards. It's a thoughtful contribution from someone with code review experience, though it doesn't directly address some of the cross-forge compatibility questions raised earlier in the thread.
