This is a discussion about rebase behavior and authorship preservation, continuing the thread about rebase status reporting improvements. Phillip Wood and Johannes Schindelin are debating a fundamental inconsistency in how Git handles authorship during interrupted operations.

The core issue is that `git commit` behaves differently when used after conflicts in `git cherry-pick` (preserves authorship via CHERRY_PICK_HEAD) versus `git rebase` (loses authorship). Johannes argues this is a serious usability problem that should be fixed by teaching `git commit` to recognize rebase's author-script metadata, noting that even as rebase's inventor he's been bitten by this behavior. Phillip counters that the current design (where users must use `git rebase --continue`) is more maintainable, as making `git commit` rebase-aware would introduce complexity and potential fragility.

The discussion reveals deeper architectural tensions:
- Historical reasons for the divergence (dating back to 2011)
- The challenge of balancing backward compatibility with usability
- Different philosophies about whether `git commit` should be "smart" about rebase state
- Concerns about the sequencer code's organization and maintainability

While this doesn't block the original patch series, it highlights an ongoing design challenge in Git's history-rewriting operations that may warrant future attention. Phillip maintains his position that the current behavior is the lesser evil, while Johannes advocates for consistency even if it requires significant refactoring.
