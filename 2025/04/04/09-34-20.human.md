This is a technical discussion about implementing change-ID tracking in Git, continuing the ongoing thread about cross-tool standardization.

Patrick Steinhardt responds to Nico Williams' suggestion of using Git refs (`refs/change-IDs/`) to index change IDs, arguing this would be problematic. He notes two key mismatches: (1) refs are meant to be mutable by design, whereas change IDs should remain stable, and (2) refs can only point to single commits while change IDs may have multiple matches (non-unique). 

Instead, Patrick proposes using an alternative data structure for caching change ID information, suggesting either extending commit graphs or creating a dedicated change-ID index. This builds on his earlier proposal to leverage Git's existing ambiguous hash resolution mechanism rather than repurposing the ref system.

The exchange highlights the technical tradeoffs between different implementation approaches while maintaining focus on the core requirements of change-ID tracking: stability, non-uniqueness handling, and performance. The discussion remains productive, with Patrick offering concrete alternatives rather than just rejecting the ref-based approach.
