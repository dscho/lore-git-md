This is a discussion about rebase behavior and authorship preservation, continuing the thread about rebase status reporting improvements.

Johannes Schindelin responds to Phillip Wood's explanation about why `git commit` during a rebase doesn't preserve authorship like it does during cherry-pick operations. While Phillip argues that the current behavior is intentional and making `git commit` work with rebase would be fragile, Johannes pushes back strongly, calling this a significant usability issue that should be fixed despite the implementation challenges.

The key technical points:
- Cherry-pick preserves authorship via CHERRY_PICK_HEAD, which rebase intentionally removes
- Rebase stores authorship in `.git/rebase-merge/author-script` instead
- Johannes suggests teaching `git commit` to also read from rebase's author-script
- Phillip counters that this would be complex and fragile, and users should just use `git rebase --continue`

Johannes makes an emotional appeal about how even he (as the inventor of interactive rebase) frequently gets tripped up by this behavior, arguing that the pain points to deeper architectural issues that should be addressed. The discussion reveals a fundamental tension between historical implementation choices and modern usability expectations.

This doesn't directly impact the current patch series about rebase status reporting, but surfaces an important design question about consistency between rebase and cherry-pick behavior that may warrant future attention. The exchange is quite technical but reveals differing philosophies about when to preserve backward compatibility versus improving user experience.
