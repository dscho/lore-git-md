This is a continuation of the discussion about change ID semantics in version control systems, with Elijah Newren providing concrete counterarguments from real-world Gerrit usage patterns.

Elijah challenges the assumption that change IDs should be unique, drawing from extensive experience with Gerrit-based projects where duplicate change IDs are actively used to track backports across LTS branches. He describes how teams verify critical fixes by searching for the same change ID across multiple branches, creating what he calls "N+1 commits sharing the same change-id" where N is the number of supported LTS versions.

The email makes several key points about practical workflow implications:
1) Current Git lacks the automatic descendant rebasing that tools like Jujutsu use to maintain change ID uniqueness
2) Gerrit workflows heavily rely on preserved change IDs for backport verification, contrary to Jujutsu's model
3) Cherry-pick trailers often create dead-ends in commit history that make backport tracking difficult
4) Commands like `git switch <change-id>` would be problematic for projects using non-unique change IDs

Elijah's contribution shifts the discussion from theoretical design to concrete workflow needs, particularly around long-term maintenance. He questions whether the proposed change ID standardization adequately considers backport-heavy environments, suggesting the current proposals might break existing Gerrit-based workflows that depend on non-unique change IDs for cross-branch tracking.

The email highlights a fundamental tension in the standardization effort: whether to prioritize change IDs as unique identifiers for command-line convenience (Jujutsu model) or as persistent markers for cross-branch tracking (Gerrit model). This represents a significant fork in the road for the standardization effort, with Elijah providing strong evidence that the Gerrit model is already solving real problems in large-scale maintenance scenarios.
