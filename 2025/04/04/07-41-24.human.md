This is a thoughtful contribution to the ongoing discussion about change ID standardization between Git and Jujutsu, focusing on the temporal aspects of change ID uniqueness.

Remo Senekowitsch synthesizes several threads of the conversation, acknowledging Nico Williams' point that both rebase and cherry-pick can produce multiple commits with the same change ID in different scenarios. He now agrees both operations should preserve change IDs by default, which aligns with Gerrit's preferences and Jujutsu's capabilities.

The key new insight here is the temporal dimension of change ID usage - distinguishing between active development (where Jujutsu users benefit most from unique IDs) and post-merge scenarios (where backport tracking occurs). Remo argues these phases have different uniqueness requirements that can coexist without conflict, suggesting the debate might be over-constrained by considering all cases uniformly.

The email advances the discussion by proposing a more nuanced view of when uniqueness matters, potentially resolving some philosophical differences. It also reinforces Jujutsu's ability to handle non-unique IDs while maintaining workflow benefits, though doesn't address the technical implementation questions raised earlier in the thread.
