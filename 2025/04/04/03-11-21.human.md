This is a discussion about change ID semantics in Git, specifically addressing how they should behave across branches and cherry-picks. Nico Williams responds to Martin von Zweigbergk's concerns about duplicate change IDs by presenting concrete use cases where multiple commits with the same change ID are not just possible but desirable.

Nico argues that change IDs should not be required to be unique across a project, as this would break important workflows like backporting bugfixes (common in projects like OpenSSL and PostgreSQL) and maintaining parallel development branches for different approaches or OS releases. He points out that detached HEAD mode is actually his preferred working style, and that Git's current behavior of not updating refs in this mode is expected and correct.

The email provides three specific scenarios where duplicate change IDs are useful: 1) security fix backports to support branches, 2) parallel experimental implementations of features, and 3) maintaining OS-release-specific package variants. Nico emphasizes that Fossil's approach of indexing change IDs might make branch searching feasible, but this would be complex to implement in Git.

This contribution strengthens the case against enforcing change ID uniqueness, providing real-world examples that challenge Martin's assumption that duplicate IDs would be rare. The discussion continues to grapple with fundamental questions about whether change IDs should serve as lineage markers (Nico's view) or unique identifiers (Martin's preference).
