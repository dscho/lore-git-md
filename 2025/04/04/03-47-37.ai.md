This is a continuation of the change ID standardization discussion, specifically addressing how tools should handle duplicate change IDs in backport workflows. Martin von Zweigbergk responds to Elijah Newren's proposal about treating non-unique change IDs similarly to abbreviated hashes (erroring on ambiguity).

The email clarifies Jujutsu's current behavior where duplicate change IDs are allowed but marked as "divergent" (shown in red in logs), with potential future changes to either error on ambiguity or make the display less alarming. Martin emphasizes that while duplicate IDs are uncommon in most workflows (not being cherry-picked), the tool should still handle them gracefully, even if the UX is slightly degraded in those cases.

Key technical points include:
- Jujutsu currently resolves ambiguous change IDs to all matching commits
- Future may change to error like abbreviated hashes (referencing issue #5632)
- Visual indication of divergent commits may be softened (PRs #5800, #5850)
- Users can always fall back to full commit hashes when needed

This moves the discussion forward by:
1) Confirming Jujutsu's flexibility around duplicate IDs
2) Showing willingness to adjust UX for backport cases
3) Providing concrete implementation references
4) Maintaining that uniqueness is still the common case worth optimizing for

The response helps bridge the gap between Gerrit-style branch-aware change IDs and Jujutsu's review-unit model by acknowledging the need to handle duplicates while preserving the ability to error on ambiguity. It leaves open whether the final solution will follow Elijah's hash-like proposal or maintain Jujutsu's current multiple-resolution approach with improved UX.
