This is a technical discussion about authorship preservation during rebase operations, emerging from the "rebase status reporting improvements" series. The conversation between Johannes Schindelin and Phillip Wood examines a fundamental inconsistency in Git's behavior:

The core issue revolves around how `git commit` handles authorship metadata differently when used after:
1. A conflicted cherry-pick (preserves original authorship via CHERRY_PICK_HEAD)
2. A conflicted rebase (loses authorship, requiring `git rebase --continue` to preserve it)

Johannes argues this is a serious usability issue that should be fixed by teaching `git commit` to also recognize rebase's `.git/rebase-merge/author-script` metadata, similar to how it handles CHERRY_PICK_HEAD. He notes this confusion affects even experienced users like himself, despite being the inventor of interactive rebase.

Phillip maintains the current behavior is intentional (dating back to 2011) and argues:
- The divergence stems from rebase's additional features like `--reset-author-date`
- Making `git commit` rebase-aware would be fragile and hard to maintain
- Users should consistently use `git rebase --continue` for conflict resolution

Key technical points:
- Current mechanism: cherry-pick uses CHERRY_PICK_HEAD while rebase uses separate files (MERGE_MSG and author-script)
- Historical context: This split was introduced in d7e5c0cbfb0 (2011)
- Implementation challenge: Rebase's additional features complicate adopting cherry-pick's approach
- Johannes counters that the code organization pain points to needed architectural cleanup

This discussion doesn't block the current patch series but surfaces a deeper design question about command behavior consistency that may warrant future work. The exchange highlights a tension between historical implementation choices and modern usability expectations in Git's history-rewriting operations.
