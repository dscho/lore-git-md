This is a discussion about change ID handling in the ongoing Git/Jujutsu interoperability effort. Elijah Newren follows up on Martin von Zweigbergk's explanation of Jujutsu's current behavior when multiple commits share the same change ID. 

The key point is how tools should handle ambiguous change IDs - Jujutsu currently shows all matching commits (marked as "divergent"), while Git would likely error out like it does with ambiguous hashes. Elijah probes the practical implications, wondering what a Jujutsu checkout operation would do with multiple matches, and muses that Git's `log --no-walk` showing multiple commits could be an intriguing behavior.

Martin clarifies that while multiple matching change IDs are rare (mostly from cherry-picks), Jujutsu may change from showing all matches to erroring out, and is working to make the UI less alarmist about divergences. The discussion remains productive, with both sides exploring edge cases while acknowledging the different design philosophies between the tools.
