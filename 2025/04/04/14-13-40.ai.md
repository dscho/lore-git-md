This is a discussion about rebase behavior and authorship preservation during conflict resolution, continuing from the patch series about rebase status reporting improvements.

Phillip Wood responds to Johannes Schindelin's concerns about inconsistent authorship behavior between `git commit` during rebase versus cherry-pick operations. The core disagreement centers on whether to make `git commit` rebase-aware to preserve authorship metadata, with Johannes advocating for usability improvements and Phillip emphasizing implementation stability.

Phillip explains the technical constraints: rebase uses `.git/rebase-merge/author-script` rather than CHERRY_PICK_HEAD, and the presence of `--reset-author-date` makes cherry-pick's approach unsuitable. He argues that teaching `git commit` to handle rebase cases would create UI complexity, as users would need to know when to use `--amend` versus regular commit. Phillip suggests the cleaner solution would be for `git commit` to refuse conflict resolutions entirely, directing users to `git <cmd> --continue` consistently.

Johannes counters that the current behavior frequently trips up even experienced users (including himself as rebase's inventor) and suggests the code organization indicates a need for architectural cleanup. Phillip acknowledges the sequencer could use refactoring but expresses concern about the review and implementation burden.

The discussion reveals a fundamental tension between Git's historical implementation choices and modern usability expectations, with no immediate resolution. Phillip's position suggests this architectural question may remain open while the current rebase status reporting series moves forward.
