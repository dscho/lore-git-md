This is a follow-up in the symlink behavior discussion thread, where Andrej Zhilenkov provides their specific use case for wanting to change core.symlinks after repository creation. The email responds to brian m. carlson's question about motivations for this workflow.

The key new information is a concrete Windows-based scenario where users might need to enable symlinks after initial clone: Git for Windows defaults to disabled symlinks, and users may only discover their need for symlinks after cloning. Zhilenkov describes the current workaround (manual symlink removal before re-checkout) as cumbersome, suggesting an automated refresh mechanism would be more user-friendly.

The email also speculates about potential Unix use cases (disabling symlinks globally while enabling per-repo), though the author admits they can't think of concrete examples. This maintains the thread's focus on Windows-specific symlink challenges while leaving the door open for other scenarios.

Technical details remain consistent with the thread's established context: core.symlinks as a filesystem capability hint set at repository creation, with no automatic conversion between representations. The new Windows-specific motivation adds weight to the discussion but doesn't fundamentally alter the technical constraints previously outlined by the maintainer.
