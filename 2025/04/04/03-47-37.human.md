This is a follow-up in the ongoing discussion about change ID semantics, particularly around handling duplicate IDs in backport workflows. Martin von Zweigbergk clarifies Jujutsu's current behavior and potential future changes regarding non-unique change IDs.

Martin explains that Jujutsu currently allows multiple visible commits with the same change ID (called "divergent" commits), showing them in red in logs, but acknowledges this might be unnecessarily alarming. He notes they're considering changing this to either show all matching commits or error out when a change ID is ambiguous, similar to how Git handles abbreviated hashes. 

The email emphasizes that while duplicate change IDs are relatively rare (most commits aren't cherry-picked), the tool doesn't need to optimize for this case - it's acceptable if working with duplicates requires slightly more effort (like falling back to full commit hashes). This positions Jujutsu's approach as more flexible than strict about uniqueness, while still acknowledging the practical challenges duplicate IDs create.

The response aims to reconcile earlier concerns raised in the thread about backport workflows needing duplicate IDs with Jujutsu's design philosophy. Martin provides links to three active Jujutsu GitHub issues/pull requests showing they're actively working on improving the user experience around this case.
