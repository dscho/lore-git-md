This is a follow-up in the symlink behavior discussion, where Andrej Zhilenkov provides their specific use case for wanting to change core.symlinks after repository creation. The email explains a Windows-centric scenario where symlinks are disabled by default, and users may only realize they need them after cloning a repository.

The key motivation presented is that Windows users typically clone repositories with symlinks disabled (the Git for Windows default), then later discover they need symlinks enabled for certain repositories. Currently, this requires manual intervention - either re-cloning with the correct setting or manually removing and re-checking out affected files. Zhilenkov suggests it would be more user-friendly if Git could automatically handle this transition when core.symlinks is changed in the local config.

The email acknowledges this might be a Windows-specific pain point, as the reverse case (disabling symlinks on Unix) seems less likely to be needed. This provides concrete context for the earlier theoretical discussion about whether Git should support runtime changes to symlink handling.

The response maintains a constructive tone while clearly articulating the practical workflow problem. It doesn't propose a specific implementation, but rather aims to justify why this edge case might deserve consideration despite the maintainer's earlier explanation of the current design constraints.
