This is a submodule behavior explanation email in an ongoing thread about submodule checkout behavior. Lucas Seiki Oshiro provides a detailed response to Bill Torpey's questions about why recursive clones don't automatically check out the HEAD of submodule branches.

The email clarifies that submodules are fundamentally designed to track specific commits pinned in the superproject's history, not branch heads. Oshiro uses Git's own sha1collisiondetection submodule as a public example, demonstrating how submodule references are stored in the parent repository and how they can be examined without even initializing the submodule.

Key points explained:
- The `git submodule update --remote --recursive` command Torpey found helpful actually changes the submodule to track the branch HEAD (as specified in .gitmodules), which differs from the default behavior of tracking the pinned commit
- This leaves the submodule in an "unstaged" state that requires explicit committing in the superproject
- Submodules should be thought of as versioned dependencies where changes must be explicitly recorded

The response is thorough and patient, using concrete examples from Git's own repository to illustrate the concepts. It effectively addresses Torpey's confusion while reinforcing that the observed behavior is by design rather than a bug. The email moves the thread toward resolution by providing clear technical explanations for the behavior Torpey encountered.
