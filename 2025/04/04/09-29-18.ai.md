Feature proposal for change-ID handling in Git, building on the ongoing cross-tool standardization discussion. Patrick Steinhardt suggests adapting Git's existing ambiguous hash resolution mechanism to handle duplicate change-IDs in a similar way to Jujutsu's approach. The proposal would make Git show an error with candidate commits when a change-ID is ambiguous, mirroring the current behavior for short object IDs. This aligns with the emerging consensus around rebase/cherry-pick behavior while addressing the temporal aspects of change-ID uniqueness discussed in the thread.

The implementation would extend Git's existing ambiguous object resolution system to recognize change-IDs alongside object hashes, showing similar error messages with commit candidates when multiple matches exist. This provides a clear path forward for handling the non-uniqueness cases that arise during active development phases, while maintaining Git's strict error-throwing model rather than Jujutsu's command-specific ambiguity handling.

Key technical points include:
- Leveraging existing `rev-parse` infrastructure for ambiguity detection
- Formatting change-ID error messages to match hash ambiguity warnings
- Maintaining backward compatibility with current hash-based operations
- Potential need for new plumbing to extract and index change-IDs

The proposal represents a practical middle ground between Git's strict model and Jujutsu's more permissive approach, while fitting naturally into Git's existing error handling patterns. It addresses one of the key open questions in the thread about standardizing cross-tool behavior while respecting Git's workflow expectations.
