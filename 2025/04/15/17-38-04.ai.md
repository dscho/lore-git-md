This is a technical review follow-up in Patrick Steinhardt's series hardening integer handling in Git's parse-options infrastructure, specifically addressing patch 4/5 which introduces `OPTION_UNSIGNED`.

René Scharfe points out a type safety issue in the implementation where signed integer types (`int8_t`, `int16_t`, etc.) are incorrectly used for storing unsigned values in the new `OPTION_UNSIGNED` handler. The patch should be using the corresponding unsigned types (`uint8_t`, `uint16_t`, etc.) for the pointer casts when storing parsed values. This matches the intended behavior of the new option type which is specifically for unsigned integer parsing.

The review identifies a clear implementation bug that would undermine the type safety goals of the series. The incorrect signed types could lead to sign extension issues when storing large unsigned values. This feedback comes on top of Phillip Wood's earlier review which identified the need for negative value rejection and proper `errno` handling in this same patch.

The technical context shows this is part of a broader effort to strengthen Git's option parsing with:
- Compile-time signedness validation (already approved in patch 5/5)
- Proper overflow detection
- Clear separation between signed and unsigned parsing
- Type-safe storage of parsed options

The series is progressing through rigorous review with multiple contributors (Phillip Wood, Junio C Hamano, now René Scharfe) catching different aspects of the implementation. This particular review focuses narrowly on the type correctness of the storage mechanism for the new unsigned option type.
