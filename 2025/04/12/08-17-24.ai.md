This is a refactoring patch in Patrick Steinhardt's ongoing object-file subsystem reorganization series. Jeff King provides detailed technical feedback questioning whether the split of index-related functions from object-file.c to read-cache.[ch] is conceptually appropriate.

Key technical observations:
- The functions in question (like `index_path()`) historically predate and conceptually operate independently of Git's index subsystem
- Their current index_state parameter was added later for attribute handling
- Many callers (hash-object, git-replace, diff) don't actually need index functionality
- The functions' core purpose is object creation rather than index operations
- There's an open question about whether attribute lookup even uses the index parameter

The feedback suggests that while the mechanical split is fine, the conceptual grouping may be ideal - these functions don't clearly belong in either object-file.c or read-cache.[ch]. This raises architectural questions about where such "boundary" functionality should live in the refactored codebase.

This email doesn't propose an alternative solution but provides important historical context and usage analysis that may influence the series' final organization. The feedback is constructive and grounded in deep Git internals knowledge, highlighting how seemingly straightforward refactorings can expose subtle subsystem boundary questions.
