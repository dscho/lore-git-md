This is a technical proposal for implementing patch series tracking in Git, building on an ongoing discussion about change IDs and version tracking.

Theodore Ts'o proposes a "Patch Set ID" system that would track relationships between commits in a series. The key idea is that commits would carry an optional patch set ID that persists across operations like rebase and cherry-pick. By default, each commit would have its own ID (making it a series of one), but using `git commit --series` would inherit the parent's patch set ID to group related changes.

The proposal aims to address several needs: distinguishing between new replies and amended patches in email threads, maintaining series relationships through various Git operations, and providing backward compatibility where singleton commits behave like traditional Change-IDs. The IDs would be visible in `format-patch` output and preserved by `git am`.

This represents a concrete technical alternative to the Change-ID approach discussed earlier in the thread. Ts'o emphasizes the clarity of semantics as a key motivation, with the system that would track user intent ("this is part of a series") rather than trying to infer relationships. The proposal appears well-considered, though it would require implementation work and likely further discussion about edge cases and integration with existing workflows.
