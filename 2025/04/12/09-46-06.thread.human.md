This thread investigates inconsistencies in how Git commands handle wildcard pathspecs (like `f*`). Initially focused on fixing `git add`, Lucas Seiki Oshiro discovered that `git ls-files` and `git grep` work correctly while `add`, `commit`, and `rm` prioritize literal matches over wildcard expansion. This suggests deeper architectural differences in pathspec processing across commands.

Junio C Hamano provided historical context, explaining that `git add`'s current behavior may stem from a deliberate early design choice to help users add files with literal glob characters (like `f*`) in their names. This suggests the inconsistencies aren't accidental but reflect different evolution paths - some commands updated for proper wildcard handling while others preserved the original exact-match behavior.

The discussion has shifted from a straightforward bugfix to considering architectural implications. Key open questions include whether to standardize behavior across all commands (potentially breaking workflows relying on the current exact-match behavior) or maintain the divergence with clearer documentation. The test strategy also needs adjustment to account for these command-specific behaviors, particularly on Windows where filename limitations add complexity.
