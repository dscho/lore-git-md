This is a technical proposal for implementing patch series tracking in Git, offering an alternative to the Change-ID approach discussed earlier in the thread. Theodore Ts'o suggests a "Patch Set ID" mechanism that would be more tightly integrated with Git's native operations.

The proposal introduces a new `--series` flag for `git commit` that would establish parent-child relationships between commits in a patch series. The key behaviors would be:
1. New commits without `--series` get their own unique Patch Set ID (same as commit ID)
2. Commits with `--series` inherit their parent's Patch Set ID
3. The field persists through rebases, cherry-picks, and email operations
4. `git format-patch` would include the ID after the `---` separator
5. `git am` would preserve the ID when applying patches

This approach differs from Change-IDs by making series membership explicit through user action (`--series` flag) rather than automatic footer generation. It maintains the ability to track individual patches (like Change-IDs) while adding native support for grouping related commits. The design appears to address some of the reachability concerns raised earlier in the thread by making series relationships optional and clearly demarcated.

The email positions this as a more Git-native solution with well-defined semantics, though it would require changes to several core commands (`commit`, `format-patch`, `am`). The proposal doesn't yet address how this would interact with existing Change-ID implementations in tools like Gerrit, or whether there would be migration considerations for projects already using Change-IDs.
