This is a clarification about `git stash -k` behavior in response to a bug report. Lucas Seiki Oshiro explains that the current behavior where `-k` preserves staged changes while stashing only unstaged changes is working as documented, quoting the manpage to show this is intentional design rather than a bug. The email provides technical details about how stash entries are structured as two commits (index state and working tree state) and demonstrates how to selectively apply the working tree changes from a stash using `git cherry-pick` with the `-m 2` option to target the second parent of the stash commit.

The response suggests the reported behavior is expected, though it doesn't directly address whether this leads to the merge conflicts mentioned in the original report. It provides a workaround for accessing the stashed working tree changes independently of the index state, which could help users facing the conflict scenario. The explanation references stash's internal commit structure and standard Git operations (`cherry-pick`) rather than proposing any changes to stash's behavior, indicating this is likely the intended (if perhaps surprising) interaction between staged changes and `stash -k`.
