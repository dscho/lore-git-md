This is a clarification about `git stash -k` behavior in response to a bug. Lucas Seiki Oshiro explains that the current behavior where `-k` creates a stash diff between HEAD and unstaged changes (rather than staged vs unstaged) is actually correct according to the documentation. The manpage states that staged changes should remain intact when using `-k`, and the stash entry properly captures both index and working tree states as separate commits.

The email provides a technical workaround for users who specifically want to extract the working tree changes from a stash entry: using `git cherry-pick -n -m 2 stash` to apply just the working directory changes (the second parent of the stash commit) without creating a new commit. This demonstrates the underlying stash implementation where each entry contains both index and working tree states as separate commits.

The response suggests the original report may have misunderstood the intended behavior of `git stash -k` rather than identifying a bug. The explanation is thorough and references both documentation and implementation details, though it doesn't address whether the behavior could be improved to better handle the workflow that triggered the original report.
