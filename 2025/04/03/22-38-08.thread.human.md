Derrick Stolee has proposed adding a `--no-hooks` global option to Git, modeled after `--no-advice`, which would allow users to temporarily bypass hook execution. The implementation would check a new `GIT_HOOKS` environment variable in `run_hooks_opt()` and touches documentation, core command handling, and hook execution logic. The change aims to provide a cleaner alternative to current workarounds like deleting hooks or setting invalid `core.hooksPath` values.

Brian M. Carlson has responded with a thoughtful analysis of the proposal. While acknowledging the utility for expert workflows (noting Jenkins currently uses `/dev/null` as a security workaround), Carlson raises concerns about silent hook disabling potentially breaking Git LFS functionality in less detectable ways compared to current explicit failures. The feedback draws parallels to other powerful-but-potentially-dangerous Git features like `git reset --hard`, suggesting the feature may be worth accepting while recognizing its potential for misuse. This has opened a discussion about balancing workflow flexibility against ecosystem impacts, particularly regarding Git LFS integration and security implications. The thread now awaits further input from other contributors about these tradeoffs.
