Derrick Stolee's proposal to add a `--no-hooks` global option and `GIT_HOOKS` environment variable has sparked thoughtful discussion about how Git should handle hook execution. The feature would provide a supported way to disable hooks, addressing performance concerns and expert workflow needs, particularly for read-only operations and optional hooks like pre-commit.

The discussion has drawn substantive technical feedback from multiple contributors. Brian M. Carlson raised important security considerations, noting how silent hook disabling could impact Git LFS and comparing it to other powerful-but-dangerous features. Stolee clarified the intended use cases while acknowledging risks, particularly for mandatory hooks like those in Microsoft's VFS for Git.

Phillip Wood has now joined the conversation with a more fundamental critique, questioning whether the feature solves the right problem. He argues that slow hooks should be fixed through parallel processing rather than bypassed, and challenges the characterization of current workarounds like `core.hooksPath=/dev/null` as unsafe. While acknowledging the technical soundness of the implementation, Wood remains skeptical about the feature's overall value.

Key points still under discussion include:
- Whether performance issues should be addressed by improving hooks rather than bypassing them
- The safety and prevalence of existing hook-disabling techniques
- How to properly document and restrict the feature to prevent misuse
- Whether the primary use case (pre-commit hooks) is better served by existing `--no-verify`

The thread remains active with Stolee's proposal facing both technical scrutiny and philosophical pushback, particularly around whether this is the right solution to the problem of slow hooks. Contributors are engaging thoughtfully with both the implementation details and the broader implications for Git's design philosophy.
