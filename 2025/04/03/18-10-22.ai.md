This is a discussion email in the ongoing change ID standardization thread, focusing on the practical implications of change ID uniqueness and tooling behavior.

Nico Williams responds to Elijah Newren's concerns about using change IDs as commit identifiers, agreeing that `git rebase main <change ID>` would be problematic UI since multiple commits can share the same change ID. He emphasizes that change IDs serve primarily as documentation to track commit evolution rather than as unique references. The email explores several key technical challenges:

1) Reference resolution complexity - With non-unique change IDs, Git would need sophisticated disambiguation mechanisms (like branch context or interactive selection) that don't currently exist.

2) Multiple ID proposal - Suggests commits might need both feature-level and commit-level change IDs to handle different granularities of tracking.

3) Operation consistency - Argues cherry-pick must preserve change ID if rebase does, since rebase is built on cherry-pick operations.

The discussion continues the thread's evolution from theoretical design to practical implementation concerns, particularly around how tools should handle the inherent non-uniqueness of change IDs during rewrite operations. Nico's perspective as a tooling implementer adds weight to the growing consensus that any standard must account for real-world ID duplication scenarios.
