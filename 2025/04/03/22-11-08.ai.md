Feature proposal for change ID handling during cherry-pick and rebase operations, continuing the cross-tool standardization discussion.

Kane York proposes concrete behavior rules for how `change-id` footers should be handled during cherry-pick and rebase operations, building on the thread's discussion about whether change IDs represent authorship (preserved) or review units (regenerated). The proposal introduces several new flags and behaviors:

For cherry-pick:
- Default behavior changes to generate fresh `change-id` while storing the original in a new `cherry-picked-change` header
- Adds `--preserve-change-id` flag to maintain current behavior

For rebase:
- Introduces `--[no-]preserve-change-id` flag controlling default behavior
- Implements special handling for different rebase actions:
  * 'pick' preserves by default
  * 'fixup' uses earlier commit's ID
  * 'squash' presents both IDs for user choice
  * 'merge' generates new ID
  * Other actions require no special handling

The proposal attempts to balance Gerrit's need for cross-cherry-pick tracking with Jujutsu's preference for avoiding duplicates, while providing configuration options. It builds on the thread's recognition that different tools have valid but conflicting needs around change ID semantics, particularly regarding whether they represent authorship (Git's current view) or review units (Jujutsu/Gerrit perspective).

Key technical elements introduced:
- New `cherry-picked-change` header
- `--preserve-change-id` flag for cherry-pick
- `--[no-]preserve-change-id` for rebase
- Action-specific rebase behaviors
- Interaction between squash operations and change ID selection

This represents a concrete implementation proposal in the ongoing standardization effort, attempting to reconcile the operational patterns observed in Jujutsu with Git's existing behavior and Gerrit's requirements. The proposal notably doesn't address how short prefix matching would work with these rules, which remains an open question from earlier in the thread.
