Feature proposal for native Git change ID support, responding to cross-tool standardization effort.

Patrick Steinhardt responds to Martin von Zweigbergk's proposal for standardizing change IDs across Gerrit, GitButler, and Jujutsu, expressing general support while suggesting Git should natively implement the functionality rather than relying on commit trailers. He outlines several concrete benefits of change IDs: tracking patch evolution, reliable cherry-pick detection, and easier history rewriting. While not objecting to the proposed 32-character reverse-hex format, Steinhardt focuses on what Git would need to implement to properly support change IDs.

The email proposes four key integration points for Git: generation in commit-creating commands, preservation during rewrites, revision specification by change ID, and commit graph filtering. Steinhardt acknowledges potential performance concerns but suggests indexing could address them, and raises backward compatibility as the primary open question - though he suspects existing tools already handle similar metadata without issues. The message concludes with an offer to help implement change ID support in Git if the community approves.

This response advances the discussion by moving from cross-tool standardization to concrete Git integration requirements, while maintaining alignment with the original goals of the change ID effort. The technical specifics focus on commit creation/rewrite commands (`git-commit`, `git-rebase`), object writing plumbing (`git-commit-tree`), and query capabilities (revision syntax, graph filtering). The backward compatibility question remains open but appears surmountable based on existing tool behavior.
