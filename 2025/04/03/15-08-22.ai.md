This is a technical discussion about authorship preservation during rebase operations, emerging from the rebase status reporting improvements series.

Phillip Wood responds to Johannes Schindelin's inquiry about why `git commit` during a rebase loses authorship information, unlike `git cherry-pick` which preserves it through CHERRY_PICK_HEAD. Phillip explains the historical divergence: rebase intentionally removes CHERRY_PICK_HEAD and instead stores authorship in `.git/rebase-merge/author-script` to avoid confusing `git status` output. The difference dates back to 2011 when CHERRY_PICK_HEAD was introduced, and is further complicated by rebase's `--reset-author-date` option which makes adopting cherry-pick's mechanism impossible.

Phillip argues against trying to make `git commit` work for preserving authorship during rebase, citing implementation complexity and fragility in distinguishing rebase-initiated commits from other operations. He maintains the position that users should consistently use `git rebase --continue` for conflict resolution commits, as this has always been the supported path for authorship preservation.

The discussion surfaces an architectural inconsistency between rebase and cherry-pick's handling of authorship metadata, though Phillip views this as an intentional design choice rather than a bug. The exchange doesn't propose any immediate code changes to the ongoing patch set, but highlights a potential area for future consideration regarding command behavior consistency.
