This thread explores a reported discrepancy in submodule checkout behavior that turned out to be a misunderstanding of Git's submodule model. Bill Torpey initially reported that recursive clones of their superproject checked out a different submodule commit than when cloning the submodule directly, expecting both to follow the 'staging' branch specified in .gitmodules. 

Lucas Seiki Oshiro has provided thorough technical explanations clarifying that submodules are fundamentally designed to track specific commits recorded in the superproject's history, not branch heads. Using the git/git repository's own submodule as an example, Lucas demonstrated how to inspect submodule references and explained that `git submodule update --remote --recursive` is needed to sync with branch tips - creating changes that must then be committed in the superproject. 

The discussion has shifted from a potential bug report to an educational exchange about Git's submodule architecture. While Torpey's use case expects automatic branch tracking, the responses emphasize that submodules act more like versioned dependencies where updates require explicit steps. The thread remains open as Torpey continues to work through these concepts with their private repository setup, though no actual Git bug has been identified.
