This is a technical discussion about change ID behavior during cherry-pick and rebase operations, part of the ongoing cross-tool standardization effort for change IDs. Remo Senekowitsch responds to Nico Williams and Elijah Newren's suggestions about change ID preservation semantics.

The email focuses on two key operational contexts where change ID behavior needs clear definition: rebase (seen as commit amendment) versus cherry-pick (seen as patch duplication). Remo argues these operations have fundamentally different semantic purposes that should inform change ID handling - rebase should preserve IDs since it's modifying existing work, while cherry-pick (used for backporting) should generate new IDs to avoid duplication. This contrasts with the parent email's view that cherry-pick should preserve IDs like rebase does since rebase is implemented via cherry-pick.

Remo introduces Jujutsu's approach as a counterexample, where the equivalent "duplicate" operation intentionally doesn't preserve change IDs. The email highlights the practical tradeoff: preserving IDs during cherry-pick would increase duplicate IDs in the tree (reducing their utility) for minimal benefit. However, Remo maintains that any consistent Git behavior would still be better than no standardization at all.

The discussion surfaces important design questions about whether change ID behavior should follow implementation mechanics (cherry-pick as primitive) or user semantics (amendment vs duplication). This has implications for backporting workflows and how tools handle ID collisions. The email doesn't propose concrete solutions but helps frame the operational philosophy debate that needs resolution in the standardization effort.
