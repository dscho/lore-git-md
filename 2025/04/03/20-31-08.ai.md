This is a continuation of the change ID standardization thread, focusing on practical implications of non-unique change IDs in real-world usage. Remo Senekowitsch responds to Theodore Ts'o's observations about change ID uniqueness in Gerrit workflows, building on Elijah Newren's earlier concerns.

The email reinforces that while change ID non-uniqueness exists in practice (as Ts'o documented with examples from LTS backporting and patch series manipulation), this doesn't invalidate the concept's usefulness. Remo argues that uniqueness failures are localized - a compromised change ID affects only that specific patch's review history without polluting others. This positions non-uniqueness as a quality-of-implementation issue rather than a fundamental flaw.

Key technical points carried forward from the thread include: change IDs being regenerated during cherry-picks in some workflows, the risk of semantic drift when IDs persist through significant changes, and the reality that some tooling already handles these cases by treating IDs as hints rather than guarantees. Remo's contribution maintains the perspective that partial uniqueness still delivers value, keeping the discussion grounded in practical benefits rather than theoretical purity.

The exchange continues to highlight the tension between ideal change ID properties (stable, unique identifiers) and real-world constraints (user behavior, tool limitations, backporting needs). This moves the thread toward solutions that must accommodate both proper usage patterns and edge cases where the model breaks down. The technical challenge remains how to design reference resolution and tool integration that works robustly with this mixed-quality input.
