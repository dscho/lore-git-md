This is a continuation of the discussion about standardizing change IDs in Git, focusing on branch context and commit identification challenges. Martin von Zweigbergk responds to Nico Williams' concerns about using change IDs in operations like rebase and switch.

The key technical points raised:
1) Martin clarifies that while multiple commits with the same change ID can exist in a repository (particularly after cherry-picking), it's typically rare to have more than one visible commit with a given change ID at any time, since rewritten commits usually become unreachable.
2) He acknowledges that Git's reluctance to work in detached HEAD mode and not automatically updating refs for rewritten commits reduces the usefulness of change IDs for operations like rebase.
3) The discussion explores how change IDs might work with cherry-picks - whether they should be preserved (potentially creating multiple commits with same ID) or regenerated, with Martin noting this depends on workflow patterns.
4) Martin suggests change IDs could still be useful for read-only commands even if their utility is limited for operations that rewrite history.

The exchange highlights ongoing tensions between:
- The convenience of short, unique-enough change IDs for daily use
- The challenges of maintaining unambiguous commit identification across branches and operations
- How different workflows (like frequent cherry-picking) might affect change ID semantics

This moves the discussion forward by surfacing concrete scenarios where change ID behavior needs clear specification, particularly around history-rewriting operations and branch contexts. The thread remains focused on balancing practical usability with unambiguous semantics.
