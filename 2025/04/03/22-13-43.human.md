This is a discussion about change ID semantics in Git operations, specifically examining how change IDs could work with `git rebase` and `git switch` commands.

Nico Williams responds to Martin von Zweigbergk's suggestion about using change IDs with `git rebase` and `git switch`, expressing concerns about the practicality. The key points are:

1. Nico questions what `git rebase main <change ID>` would actually do, suggesting it might need to be similar to a hypothetical `git cherry-pick --from $branch --change-id $change_id` operation.

2. They strongly challenge the idea of `git switch <change ID>`, pointing out that since multiple commits can share the same change ID across different branches, this would be ambiguous without additional context.

3. The discussion reveals a semantic tension between Martin's view that there's typically only one visible commit per change ID in a repo, and Nico's expectation that there could be many - especially when considering feature development where related commits (features, fixes, tests) might share a change ID.

4. Nico suggests that if multiple commits share a change ID, Git would need UI mechanisms to disambiguate, possibly by showing branch contexts or requiring explicit branch specification.

The exchange highlights the ongoing challenge in standardizing change ID behavior across Git operations, particularly around how to handle cases where the same change ID appears in multiple contexts. This touches on deeper questions about whether change IDs should identify individual changes or groups of related changes.
