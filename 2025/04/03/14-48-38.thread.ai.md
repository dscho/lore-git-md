Thread summary:

Bug report and analysis of submodule checkout behavior discrepancy between recursive clones and direct submodule clones. Original reporter Bill Torpey observed that recursive cloning (via SSH with --recursive) of a superproject resulted in submodule 'src' (registered as https://github.com/nyfix/OpenMAMA-omnm.git) checking out commit 7bb809da9746051b96c0448f8137f25eaf8c15d1, while direct cloning the same submodule URL checked out commit a092be3bc330f53f644b53d80881bf30cadd367f (on 'staging' branch). 

Torpey provided their .gitmodules file showing 'staging' branch specification and reported that `git submodule update --remote --recursive` resolves their issue, though they're confused why this extra step is needed. Lucas Seiki Oshiro has now given a detailed technical explanation of Git's submodule model, demonstrating with git/git's sha1collisiondetection submodule as an example. Key technical clarifications include:
- Submodules are pinned to specific commits recorded in superproject history, not branch heads
- How to inspect submodule states with `git rev-parse` and `git log -- <submodule>`
- The role of `git submodule update --remote --recursive` in checking out latest commits from .gitmodules-specified branches
- The need to commit resulting changes in the superproject to persist updates

The discussion confirms this is not a bug but rather a documentation/education issue about Git's submodule design, where superprojects track specific commits rather than branch tips. Open questions remain about whether the specific case reveals any edge case in branch specification handling during recursive clones, though no reproducible test case exists yet. Torpey continues to seek understanding while maintaining they cannot share their private repository configuration.
