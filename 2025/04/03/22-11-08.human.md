This is a proposal for standardizing change-id behavior during cherry-pick and rebase operations, continuing the cross-tool collaboration discussion. Kane York builds on the ongoing thread about how different tools (Jujutsu, Gerrit, GitButler) handle change IDs, particularly focusing on cherry-pick and rebase scenarios.

The email offers concrete suggestions for Git's behavior: cherry-pick would generate new change-ids by default while preserving the original in a new header, with an option to keep the original ID. For rebase, it proposes detailed rules for different operations (pick, fixup, squash, merge), generally preserving change-ids during picks but allowing override, while handling more complex cases like squashes with user interaction.

The proposal attempts to balance several competing concerns from the thread: Gerrit's need to track changes across cherry-picks, Jujutsu's preference to avoid duplicate IDs, and Git's existing behavior patterns. It represents a practical middle ground that could work across tools while maintaining Git's flexibility. The level of detail suggests serious consideration of real-world workflows, though some might find the rebase rules complex.
