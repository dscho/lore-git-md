Bug report and proposed fix for partial clone backfill command's option parsing on s390x (big-endian) systems, where OPT_INTEGER writes a 4-byte int into an 8-byte size_t field (min_batch_size in struct backfill_context), causing corruption due to uninitialized upper bytes. The reporter provided detailed analysis with Debian bug tracker reproduction case showing 8-byte size_t on s390x.

The issue has been resolved upstream via a more comprehensive fix in parse-options.c that addresses integer width and signedness problems generally, superseding the specific OPT_MAGNITUDE solution proposed earlier. Patrick Steinhardt confirmed the fix is already merged into Git's `next` branch, making the thread's earlier discussion about OPT_MAGNITUDE vs changing min_batch_size to int moot. The reporter's high-quality analysis was acknowledged, though the specific case was already covered by prior work.

Key technical resolution: parse-options.c now handles integer parsing in a platform-robust way that prevents the s390x corruption case. No similar OPT_INTEGER/size_t mismatches should remain in the codebase due to this systematic fix. The thread serves as documentation of both the specific s390x manifestation and the broader solution's coverage of such cases.
