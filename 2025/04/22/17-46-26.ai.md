Performance optimization patch for the new `git-blame-tree` command, incorporating Bloom filters to speed up path-change detection. This is the third patch in a 5-part RFC series introducing tree-level blame functionality.

The patch adds Bloom filter support to avoid unnecessary diff computations during the revision walk. When Bloom filters are available (via commit-graphs), the command first checks if paths of interest might have changed at each commit before computing a full diff. The implementation:
- Adds Bloom key storage to the `blame_tree_entry` struct
- Introduces a new `maybe_changed_path()` helper to consult Bloom filters
- Includes proper cleanup of Bloom keys when entries are released
- Shows dramatic performance improvements in benchmarks (5.1s -> 0.75s for kernel repo)

The changes integrate cleanly with the existing blame-tree infrastructure while maintaining all current functionality. The performance gains are substantial enough that this seems like a must-have optimization for the command. The patch builds on Taylor Blau's prior Bloom filter work and follows Git's established patterns for filter usage.

Key technical additions:
- New `blame_tree_entry.key` field for Bloom keys
- `fill_bloom_key()` calls during path addition
- `maybe_changed_path()` predicate function
- Proper memory management via `clear_bloom_key()`
- Integration with commit-graph generation checks

The implementation appears production-ready with comprehensive handling of edge cases (missing filters, infinite generation numbers). The performance numbers suggest this optimization could be a game-changer for the command's usability on large repositories.
