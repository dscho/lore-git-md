This is a technical discussion about change ID formats in Git commits, specifically comparing reverse-hex IDs versus URI-based approaches. The thread continues with Remo Senekowitsch responding to D. Ben Knoble's concerns about initial ID application timing and URI portability issues.

Senekowitsch strongly advocates for the reverse-hex format, arguing it provides better tool-agnostic properties and longevity compared to URIs. He notes that Jujutsu has already implemented this approach successfully, with commits being pushed to various remotes. The discussion highlights practical concerns with URIs - GitHub's URL scheme limitations, URI scheme obsolescence risks, and the chicken-and-egg problem of applying review URIs to local commits.

The exchange reveals two key technical points: (1) change IDs should be applied by the commit-creating tool (Git/Jujutsu) at commit time, either randomly for new commits or inherited from predecessors, and (2) while force-push detection could theoretically provide some tracking capabilities, it would require complex heuristics compared to the simplicity of change IDs. The thread shows growing consensus around reverse-hex IDs but leaves open questions about initial application workflows and how this fits into broader patch tracking solutions.
