This RFC continues to explore the design of a new `git-blame-tree` command for tracking modifications across directory trees. The discussion has centered on whether to integrate this functionality into `git blame` or keep it as a separate command. 

Toon Claes' latest contribution strengthens the case for a standalone command, citing several technical advantages: the ability to efficiently process multiple files in a single history walk (unlike `git log -1` per file), concrete use cases like GitLab's need for paginated tree-wide blame, and adherence to UNIX principles by avoiding context-dependent behavior in `git blame`. He argues that discoverability is more about documentation than command structure.

The thread remains unresolved on this key question, though Junio Hamano has established important constraints: any integration must preserve `git blame path/to/file`'s current line-by-line behavior. Other open questions include merge commit handling (awaiting test cases) and whether the default behavior should be recursive or non-recursive (though all agree it should be configurable). 

The core implementation is production-ready with significant performance improvements from Bloom filters and priority queues. Contributors remain engaged, with Marc Branchaud advocating for integration, Toon Claes now making a strong case for separation, and Junio providing maintainer guidance. The RFC awaits resolution on merge test cases and final command structure before proceeding.
