This thread continues the debate around a proposed feature for tracking file modifications across directory trees, originally pitched as `git-blame-tree`. The technical implementation is largely settled, with a production-ready 7-patch series that implements core functionality with several optimizations. However, the discussion remains stuck on naming and integration questions.

The key sticking points are whether to position this as a variant of `git blame` (emphasizing technical similarities in how both track object modifications) or as a distinct operation (reflecting different user mental models for file history versus line history). Junio Hamano has been firm that `git blame path/to/file` must maintain its current line-by-line behavior, while Patrick Steinhardt argues the underlying mechanics justify the "blame" terminology. Marc Branchaud, who previously advocated for integration under the now-retracted "ascribe-tree" name, now proposes "last-touch" as a neutral alternative that avoids the "blame" connotation while describing the operation's purpose.

Three integration approaches remain on the table: full integration into `git blame`, a plumbing/public split, or keeping it as a separate command. The discussion has covered merge behavior semantics, default recursion settings, and UI constraints, with test coverage still needed for merge scenarios. Contributors remain divided, with Marc favoring integration, Toon Claes advocating for a separate command, and Junio emphasizing user experience considerations. The "last-touch" suggestion adds another option to the naming debate but doesn't resolve the underlying architectural question. Until these questions are settled, this useful feature remains in RFC limbo.
