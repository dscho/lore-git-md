This RFC discusses a proposed new command for tracking file modifications across directory trees, currently named `git-blame-tree`. The 7-patch series implements core functionality with three layers of performance optimizations, achieving sub-second performance even on large repositories like the Linux kernel. The command tracks path states through history using custom traversal logic and priority queues, with contributions from Taylor Blau and Derrick Stolee on the optimization work.

While the technical implementation appears production-ready, several design questions remain open. The thread initially focused on naming concerns, with Marc Branchaud suggesting alternatives like folding the functionality into `git blame` or choosing a name that avoids the "blame" terminology. Now Junio Hamano has raised an important gap regarding merge commit handling - the current implementation lacks clear semantics and test coverage for how it should attribute changes when paths are modified through merges. He provides concrete examples where the behavior needs clarification, joining other unresolved questions about default modes and output formats.

The command's performance characteristics make it potentially valuable, but these final design decisions - particularly around merge behavior - will significantly impact how users interpret its output. The thread shows consensus on the technical merits but needs resolution on these higher-level questions before the feature can move forward.
