This thread continues discussion of the proposed `git-blame-tree` command, which would track modifications across directory trees rather than individual files. The RFC series implements core functionality with significant performance optimizations, but key design questions remain unresolved.

Junio Hamano has now responded to Toon Claes' arguments for keeping this as a separate command, proposing a hybrid UI approach where `git blame` could detect tree-mode operation when given directory paths or multiple files, while maintaining traditional line-by-line blame for single files. He suggests an explicit `--tree` flag to override this heuristic. However, Junio strongly objects to calling this operation "blame" at all, arguing it's conceptually closer to a parallelized `git log -1` across paths rather than true blame functionality.

The discussion has evolved through several phases: initial technical implementation review, debate over whether to integrate with `git blame` or create a new command, and now fundamental questions about naming and conceptual alignment. Key participants include the original author (implementation), Jeff King (technical review), Marc Branchaud (integration advocate), Toon Claes (separate command proponent), and Junio Hamano (maintainer perspective).

Three pathways remain under consideration: full integration into `git blame`, a plumbing/public split, or a separate command. Junio's latest response adds weight to the separate command option while providing concrete syntax ideas if integration is pursued. The thread awaits either stronger justification for the "blame" naming or movement toward an alternative command name that better reflects the batch log-like operation Junio describes.
