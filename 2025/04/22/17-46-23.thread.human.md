This RFC thread explores a proposed new command, currently called `git-blame-tree`, which tracks modifications across directory trees with impressive performance optimizations (now sub-second for kernel-scale repositories). The series implements core functionality with three performance layers: Bloom filters, a priority queue algorithm, and revision walk optimizations. Key contributors include the primary author, Jeff King (who helped name it), Taylor Blau (Bloom filters), and Derrick Stolee (priority queue).

Two main design questions remain open. First, the naming: Marc Branchaud suggested folding it into `git blame` as a new mode rather than creating a separate command, while others question using "blame" terminology at all. Second, merge behavior: Junio Hamano raised important questions about how the command handles paths modified on only one side of a merge, with Toon Claes now acknowledging these cases need test coverage and clearer semantics. The author plans to address both issues in the next revision - first by working through concrete test cases for merge scenarios before formalizing the behavior.

The command is otherwise production-ready, with comprehensive performance gains and core functionality implemented. The RFC status remains while these final design questions are resolved, particularly around merge commit handling which could significantly impact real-world usage in complex histories.
