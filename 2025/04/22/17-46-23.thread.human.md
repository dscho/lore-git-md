This thread continues the discussion around a proposed new Git command for tracking modifications across directory trees, originally pitched as `git-blame-tree`. The core functionality is implemented and performs well, but debate continues about how to name and integrate it into Git's command structure.

The latest contribution from Jeff King adds historical context, pointing out that the tool's lineage with an older "git-last-modified" script and questioning whether "blame-tree" is the right name at all - it's not strictly about blame semantics nor limited to tree operations. He suggests two alternative approaches: either adding a `--last-modified` option to `git log`, or creating a standalone `git last-modified` command. Both would focus on the tool's actual capability of tracking modifications across arbitrary paths.

The discussion remains at an architectural level, with several key questions still open:
1. Should this be integrated into existing commands (`git blame` or `git log`) or remain standalone?
2. What name best captures the functionality without misleading users ("blame-tree" is contested, "last-touch" and "last-modified" are new proposals)?
3. How should merge scenarios be handled, particularly when files are modified on different branches?

Notable positions in the thread include:
- Junio Hamano emphasizing user mental models and backward compatibility
- Patrick Steinhardt defending technical similarities to existing commands
- Marc Branchaud proposing compromise names like "last-touch"
- Jeff King now suggesting historical alternatives that might bypass the naming debate entirely

The implementation itself appears solid, but the discussion shows no immediate signs of converging. The next steps likely involve either:
- The original author synthesizing these proposals into a revised approach, or
- Junio providing clearer direction on which integration path he would accept
