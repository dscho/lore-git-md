This is a technical discussion about Change-ID uniqueness requirements in the ongoing standardization effort. Remo Senekowitsch responds to Junio Hamano's concerns about Jujutsu's random generation approach by arguing that 128-bit random Change-IDs provide sufficient collision resistance in practice.

Key technical points:
- Jujutsu currently uses 128-bit random Change-IDs (vs Git's 160-bit commit hashes)
- Senekowitsch asserts uniform distribution makes collisions practically irrelevant
- Notes cherry-picking will naturally create duplicate Change-IDs regardless of generation method
- Argues Change-ID collisions are less problematic than commit hash collisions

The response challenges Hamano's preference for content-based guarantees by:
1) Questioning whether perfect uniqueness is actually needed
2) Pointing to Jujutsu's existing production experience
3) Highlighting that workflow operations (cherry-picks) create duplicates anyway

This continues the thread's evolution from theoretical guarantees toward practical considerations, with Senekowitsch representing the "random generation with production validation" position. The exchange surfaces important implementation details about Jujutsu's current Change-ID size (128 bits) and its collision handling capabilities.
