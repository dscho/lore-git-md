This is a discussion about build system refactoring, specifically addressing the historical inconsistency between `HAVE_FOO` and `NO_FOO` macro naming in Git's build configuration. The email comes from Junio Hamano in response to Patrick Steinhardt's suggestion about unifying the approach to function availability checks.

Junio explains the original intention behind the dual macro system: `HAVE_FOO` indicates actual system support for a feature, while `NO_FOO` allows deliberately opting out of using a system feature even when available (as with `NO_REGEX` for sparse builds). He notes that most features don't need this opt-out capability, making the dual system overkill in most cases.

While acknowledging the inconsistency, Junio suggests that moving forward, the project could standardize on using `HAVE_FOO` exclusively, with builders disabling features by manually setting `!HAVE_FOO` rather than using `NO_FOO`. He's open to this change despite the one-time migration cost for build scripts.

The discussion is part of a larger 6-patch series modernizing Git's build system, with this particular thread focusing on cleaning up historical cruft in feature detection macros. The exchange shows careful consideration of backward compatibility while moving toward more maintainable conventions.
