This is a technical discussion about Change-ID semantics in the context of Git commit footers, specifically addressing the reverse-hex vs. URI format debate. Remo Senekowitsch responds to D. Ben Knoble's concerns about initial Change-ID application timing and reinforces the advantages of the reverse-hex approach.

The email makes several key technical points: (1) Change-IDs should be generated by the commit-creating tool (Git/Jujutsu) either randomly for new commits or inherited from predecessors, (2) reverse-hex format avoids URI scheme obsolescence risks and GitHub URL compatibility issues, and (3) force-push detection alone is insufficient for reliable patch tracking due to `git range-diff`'s instability and performance characteristics.

Senekowitsch reports successful real-world implementation in Jujutsu, suggesting the reverse-hex approach is production-ready. The discussion reveals two distinct technical constraints: GitHub's slash-handling in refs creates format limitations, while `git range-diff`'s cubic complexity makes it unsuitable for backend use in forges. The thread continues to favor reverse-hex IDs but now includes concrete implementation experience and deeper analysis of alternative tracking mechanisms.
