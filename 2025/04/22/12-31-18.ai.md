Bugfix targeting the backfill command's option parsing on s390x systems. The patch addresses a test failure in the partial clone backfill functionality where the min_batch_size parameter gets corrupted on big-endian architectures.

The core issue stems from a type mismatch: the backfill command uses OPT_INTEGER to parse --min-batch-size into a size_t field, which causes incorrect value assignment on big-endian systems when sizeof(int) != sizeof(size_t). The reporter demonstrates this by showing how strtol() writes only to the first 4 bytes of the 8-byte size_t on s390x, leaving the upper bytes uninitialized.

Two potential solutions are proposed: 1) switching to OPT_MAGNITUDE which handles size_t properly, though this might not work universally if size_t isn't unsigned long; or 2) changing min_batch_size's type to int, pending confirmation that practical batch sizes won't exceed INT_MAX. The reporter includes a test case reference from Debian's bug tracker and provides detailed system information showing the 8-byte size_t on their s390x platform.

The bug appears well-analyzed with clear reproduction steps and thoughtful consideration of solution tradeoffs. The patch would affect builtin/backfill.c's option parsing and potentially the struct backfill_context definition. The discussion will likely focus on which fix approach to take (type change vs. parser change) and whether there are other similar OPT_INTEGER/size_t mismatches elsewhere in the codebase.
