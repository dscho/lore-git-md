This is a technical discussion about qsort() verification in Git's build system, part of the ongoing Meson build system refactoring series. The email focuses on whether to use platform-specific knowledge or generic detection for qsort() performance issues.

Eli Schwartz argues for encoding known problematic platforms (AIX and MinGW) rather than trying to generically detect qsort() performance issues, citing historical evidence from config.mak.uname and CMake behavior. They note that while CMake unconditionally uses Git's qsort on Windows (likely due to known performance issues), the current Meson approach checks for qsort() existence rather than performance characteristics.

Patrick Steinhardt prefers maintaining a generic detection approach, arguing it's simpler to maintain and that platform-specific exceptions can be added later if needed. The key technical question is how to detect platforms where the system qsort() exhibits O(n^2) behavior at build time, which Eli suggests may not be feasible.

The discussion reveals an underlying tension between the build system approaches: the Makefile historically encoded platform knowledge while Meson favors generic detection. This ties into the series' broader goal of standardizing function availability verification while maintaining compatibility. The thread context shows this is one of several open questions in the build system modernization effort, alongside Windows networking verification and macro naming conventions.
