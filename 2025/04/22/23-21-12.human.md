This is a discussion about Change-ID uniqueness requirements in the ongoing standardization effort. Remo Senekowitsch responds to Junio Hamano's concerns about Jujutsu's random generation approach for Change-IDs.

Senekowitsch defends Jujutsu's implementation which uses 128-bit random Change-IDs, arguing that:
1) The probability distribution is sufficiently uniform for practical purposes
2) 128 bits provides enough entropy to make collisions extremely unlikely
3) Collisions are somewhat expected due to cherry-picking operations anyway
4) Jujutsu's system already handles duplicate Change-IDs gracefully

The response contrasts with Hamano's preference for content-based Change-IDs that would leverage Git's existing cryptographic hashes. Senekowitsch suggests the practical impact of collisions is less severe than Hamano implies, since cherry-picking workflows naturally produce duplicates that systems must handle regardless.

This exchange highlights the ongoing tension in the thread between theoretical guarantees (Hamano's content-based approach) and practical implementation concerns (Senekowitsch's random generation method). The discussion remains technical but grounded in real-world system behavior, with Senekowitsch providing concrete details about Jujutsu's current production implementation.
