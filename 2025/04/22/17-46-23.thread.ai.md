This RFC thread continues discussion of the proposed `git-blame-tree` command, a new tool for tracking modifications across directory trees. The 7-patch series implements core functionality in new files `blame-tree.[ch]` and `builtin/blame-tree.c`, with test coverage in `t/t8020-blame-tree.sh` and performance benchmarks in `t/perf/p8020-blame-tree.sh`. The command tracks path states via `blame_tree_entry` structs with three optimization layers (Bloom filters, priority queue algorithm, revision walk initialization bypass) providing significant speedups.

Technical implementation includes generation-number-sorted priority queue, active path propagation, truncated revision walks, optimized parent diff processing, and direct boundary commit handling. Functionality preserves recursive/non-recursive modes, path filtering, and commit-hash/path output format, with tradeoffs around revision walk initialization.

Key discussions and updates:
1. Merge commit handling (Junio Hamano, Toon Claes):
   - Need test coverage for merge scenarios (path modified on one branch, merge resolution cases, file/tree coexistence)
   - Semantic ambiguity in change attribution
   - Author acknowledges need for test coverage in next version

2. Naming and integration debate (Marc Branchaud, Junio Hamano, Kristoffer Haugsbakk, D. Ben Knoble, Toon Claes):
   - Three technical pathways under consideration:
     1. Full integration into `git blame` with new UI behaviors (Marc's proposal)
     2. Plumbing/public split (Knoble's suggestion)
     3. Separate command (original approach)
   - Junio clarifies UI constraints: `git blame path/to/file` must maintain line-by-line behavior
   - Toon Claes adds technical arguments for separation:
     - Multi-file processing in single history walk (efficiency advantage over `git log -1` per file)
     - GitLab's concrete use case for pagination across tree files
     - UNIX philosophy argument against context-dependent output formats
     - Discoverability as documentation challenge rather than UI structure
   - Junio notes `git log -1` already provides "last commit" info, making new way redundant
   - Default recursion behavior discussion (open to non-recursive default with option)
   - Porcelain/plumbing distinction adds weight to integration argument

3. UI design constraints (Junio Hamano, Marc Branchaud, Toon Claes):
   - `git blame path/to/file` behavior must remain unchanged for backward compatibility
   - Recursive vs non-recursive directory behavior under discussion:
     - Marc advocates non-recursive default with option to recurse
     - Junio initially saw recursive behavior (like `git ls-files`) as natural
     - Both agree configurable recursion is essential regardless of default
   - Performance considerations may favor non-recursive default to avoid overwhelming output
   - Toon emphasizes output format differences between file/directory arguments as integration obstacle
