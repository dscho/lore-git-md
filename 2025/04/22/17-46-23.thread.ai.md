RFC for path modification tracking functionality (formerly `git-blame-tree`) continues with "last-modified" as the leading naming candidate. The 7-patch series implements core functionality in `blame-tree.[ch]` and `builtin/blame-tree.c` with test coverage in `t/t8020-blame-tree.sh` and performance benchmarks in `t/perf/p8020-blame-tree.sh`. Technical components include `blame_tree_entry` structs, Bloom filters, priority queue algorithm, and revision walk optimizations.

Four integration pathways remain under consideration:
1. Full integration into `git blame` with new UI behaviors
2. Plumbing/public split
3. Separate command (original approach)
4. `git log --last-modified` variant (Jeff King's proposal)

Naming consensus solidifies around "last-modified":
- Patrick Steinhardt endorses name as accurately describing path modification tracking
- Aligns with Jeff King's historical `git-last-modified` script precedent
- Avoids "blame" terminology that Junio Hamano noted creates incorrect user expectations
- Resolves accessibility concerns raised about "ascribe-tree" (Marc Branchaud)
- "last-touch" remains secondary alternative

Technical considerations:
- Patrick Steinhardt cautions against tight `git log` integration due to:
  - Command mode proliferation
  - Potential option incompatibilities
- Recommends standalone `git last-modified` with minimal `--format` support
- Toon Claes adds concerns about semantic clarity with revision ranges
- Implementation remains production-ready pending final structure decision

Open questions:
- Final command structure selection among four pathways
- Merge behavior specification with test cases (Toon Claes)
- Non-recursive default behavior confirmation
- UI design if choosing integration path
- Output formatting requirements (plumbing vs porcelain)
- Pathspec handling differences between `git log` and modification tracking
