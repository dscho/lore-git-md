This is a philosophical response in the ongoing Change-ID standardization discussion. Junio C Hamano counters Nico Williams' technical arguments by drawing parallels to Git's approach to file renames, emphasizing Git's design philosophy around metadata.

Hamano clarifies Theodore Ts'o's earlier point about simplicity, explaining that Git's choice not to record renames/copies in commit objects isn't just about simplicity but about correctness. He provides a concrete example of how an IDE might incorrectly mark a copied file when the actual intent was to create new content from a boilerplate. 

The key argument is that Git intentionally avoids recording certain metadata at commit time (like renames) because it can be wrong or misleading, instead preferring to derive this information dynamically when needed. This serves as an analogy for why Git might resist recording Change-IDs as well - the same philosophical concerns about baking potentially incorrect or misleading metadata into commits apply.

Hamano's response suggests that any Change-ID proposal must address these fundamental concerns about metadata correctness and the ability to reinterpret history later, not just technical implementation details. The email reinforces the core tension in the discussion: workflow convenience versus Git's content-addressable design principles.
