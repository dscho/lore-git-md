This is a continuation of the Change-ID standardization discussion, with Theodore Ts'o responding to Nico Williams' concerns about implementation approaches. The email focuses on practical challenges with Change-ID semantics and tooling behavior.

Theodore raises several concrete issues with current Change-ID usage patterns that complicate standardization: inconsistent tool behavior during cherry-picks (some preserve IDs while others regenerate them), undefined semantics for split/merged patches, and human errors from manual footer editing. He suggests these might improve if Change-IDs move to commit headers but notes similar problems could persist if tools allow arbitrary amendments.

The email proposes potential solutions including using heuristics (which Nico opposes) to automatically handle ID inheritance during patch modifications, with user override capabilities. Theodore also questions whether Change-IDs need indexing support to improve usability, comparing the situation to Git's early design choice to avoid tracking file renames explicitly.

Key technical points include:
- Current ecosystem inconsistencies in Change-ID handling during cherry-pick operations
- Undefined behavior for patch splitting/merging scenarios
- Potential indexing benefits versus raw commit message grepping
- Historical parallel to Git's file rename tracking design decisions

The discussion remains philosophically divided between Theodore's pragmatic concerns about real-world tool behavior and Nico's preference for simple, well-defined metadata. Theodore positions this as a classic simplicity-vs-completeness tradeoff, acknowledging Junio Hamano's ultimate decision-making role while clearly articulating the case for cautious, minimal solutions.
