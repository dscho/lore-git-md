This is a philosophical debate about Change-ID semantics in the Git commit header, continuing the ongoing discussion about tracking commit evolution.

Theodore Ts'o responds to Nico Williams' preference for UUID-like Change-IDs by raising concerns about inconsistent semantics in current implementations. He notes that Change-IDs today can be randomly set by humans or modified unpredictably by tools during operations like cherry-picking, leading to unreliable tracking. While moving Change-IDs to the commit header might help, he questions whether this fully solves the problem if tools can still modify them arbitrarily.

Ts'o explores possible semantics for Change-IDs when commits are split or merged, suggesting they could either propagate unchanged or accumulate like parent commits in an octopus merge. He proposes that similarity heuristics (which Williams dislikes) might help determine when to preserve or regenerate Change-IDs, with user overrides for edge cases.

The email also questions the practical value of Change-IDs compared to existing commit hashes and summaries, suggesting that indexed Change-IDs might need to offer clear advantages to justify their complexity. Ts'o frames this as a fundamental design choice between simplicity (like Git's approach to file renaming) and comprehensive tracking, acknowledging this is ultimately a matter of philosophical preference where Junio Hamano's opinion will be decisive.

This response maintains the thread's central tension between lightweight and comprehensive solutions while adding concrete examples of real-world implementation challenges with Change-IDs. Ts'o's pragmatic concerns about tool behavior and user experience provide new considerations for the ongoing debate.
