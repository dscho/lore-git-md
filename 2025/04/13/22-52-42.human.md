This is a technical discussion about GPG signing in Git's email workflow, continuing the thread about limitations of commit signatures when sending patches via `git send-email`.

Brian M. Carlson responds to Klaus Frank's inquiry by confirming that Git doesn't currently have built-in support for GPG-signed patches. They explain two key technical challenges: PGP/MIME signatures can interfere with patch application (due to encoding issues and MIME parsing difficulties), and Git lacks verification capability for such signatures. 

The email notes historical list discussions have generally favored evaluating patches on technical merit rather than authenticity, though Carlson acknowledges some workflows might benefit from verification. They suggest two potential approaches that could be implemented: proper PGP/MIME support (though this would be complex to implement correctly), or alternatively including commit/signature metadata in email headers to allow reconstructing verifiable commits.

The response is technically detailed and constructive, clearly explaining the current limitations while leaving the door open for future solutions. It builds on Matt Hunter's earlier explanation of fundamental constraints while proposing some possible directions forward. The tone suggests this is a solvable problem, just not one with existing out-of-the-box support in Git today.
