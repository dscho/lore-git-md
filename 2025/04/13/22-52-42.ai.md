This is a technical discussion about GPG signing in Git's email workflow, continuing the thread about limitations of commit signatures when sending patches via `git send-email`. Brian m. carlson responds to Klaus Frank's original inquiry with additional technical context and potential alternative approaches.

The email confirms that Git currently lacks built-in support for signed patches via `git send-email`, explaining that PGP/MIME signing would be the technically correct approach but comes with its own challenges. The response notes that `git am` struggles to properly extract data from PGP/MIME-signed messages, and that Git has no capability to verify such signatures even if they were applied. The historical context provided is important - the Git community has generally prioritized patch quality over authenticity in the mailing list workflow.

Brian m. carlson suggests two potential paths forward: implementing proper PGP/MIME support (acknowledging this would be non-trivial due to MIME parsing requirements), or an alternative approach that would include commit metadata in email headers to allow signature reconstruction. The latter approach appears to be something the author might prototype themselves, though they note the final decision about preserving signatures would remain with maintainers.

Key technical details include:
- PGP/MIME would require quoted-printable or base64 encoding to prevent mail server interference
- Current `git am` limitations in handling MIME structures
- The community's historical preference against signature requirements for patch acceptance
- The proposed header-based approach for preserving commit metadata

This response moves the discussion from identifying limitations to considering concrete technical solutions, while maintaining realistic expectations about implementation challenges and community acceptance. The email provides important context about why this functionality hasn't been implemented despite periodic interest, while leaving the door open for future proposals.
