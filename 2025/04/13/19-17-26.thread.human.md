This thread explores the challenges and potential solutions for authenticating patches in Git's email workflow. The discussion began with Klaus Frank identifying two distinct needs: preserving commit signatures (which turns out to be impossible due to how `git am` changes committer information) and verifying patch transport authenticity (where several approaches are possible).

Technical contributors like Matt Hunter and brian m. carlson clarified the constraints, noting that while commit signatures can't survive the patch workflow, transport authentication could be implemented via PGP signatures (either embedded or in headers), multipart messages, or alternative methods. brian m. carlson particularly highlighted platform compatibility issues with GnuPG on macOS and suggested header-based approaches that could work better with SSH signatures.

The conversation has now expanded with Konstantin Ryabitsev introducing patatt, a tool used by the Linux kernel community that takes a flexible, header-based approach similar to DKIM. This supports multiple signature types (PGP, SSH, ed25519) and offers a working example of the kind of solution brian m. carlson had suggested. While this doesn't solve the fundamental limitation around commit signatures, it provides a practical path forward for transport authentication that addresses some of the earlier concerns.

Key open questions include which authentication method to prioritize, how to handle systems without GnuPG, what trust model to use by default, and how to document both the limitations and new features. The thread has productively moved from problem identification to evaluating concrete implementation options, with the Linux kernel's patatt example providing a real-world reference point for one viable approach.
