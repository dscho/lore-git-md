This is a technical response about GPG signing in Git's email workflow, specifically addressing the limitations of commit signatures in patch workflows.

Matt Hunter responds to Klaus Frank's question about GPG-signed patches by explaining the fundamental design constraints that make commit signatures problematic for email patches. The key insight is that when patches are applied via `git am`, the committer identity changes to the recipient, which would invalidate any original signature. This explains why Git's toolchain (including `format-patch`, `am`, `rebase`, and `cherry-pick`) deliberately ignores or drops signatures during these operations.

The response highlights that this behavior is intentional and consistent across Git's patch workflow tools, suggesting the current approach is by design rather than an oversight. The explanation focuses on the technical reality that commit signatures are tied to specific commit objects and histories, making them incompatible with patch-based workflows where commit metadata necessarily changes during application.

This moves the thread forward by clarifying why the original approach (signing commits before sending patches) won't work as intended, though it doesn't yet propose alternative solutions for end-to-end signed patch workflows. The response implies that any solution would need to work around Git's fundamental object model constraints regarding commit identities.
