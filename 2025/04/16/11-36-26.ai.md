This is a technical discussion about Change-ID format specifications in the ongoing patch series tracking debate. Remo Senekowitsch responds to concerns about using URIs for Change-IDs by advocating for the original fixed-width reverse-hex format. The email makes several key technical arguments:

1) **Format advantages**: The reverse-hex ID format is presented as more flexible and downstream-agnostic compared to URIs, since it doesn't bake in assumptions about specific tools or hosting platforms. Senekowitsch notes this allows multiple consumers to interpret the ID differently.

2) **Implementation practicality**: Generating random reverse-hex IDs during local commit creation is described as trivial, avoiding the chicken-and-egg problem of needing a URI before the commit exists. The email contrasts this with URI-based approaches that would require knowing the review location beforehand.

3) **Longevity concerns**: URIs are criticized as potentially ephemeral, with domains and schemes changing over time, while reverse-hex IDs would remain stable. The email suggests it's better to have tools construct URIs from stable IDs than to embed URIs directly.

4) **Tooling implications**: Using GitHub's URL scheme as an example, Senekowitsch argues that more restrictive formats actually enable more reliable downstream tooling by avoiding problematic characters (like slashes in refs).

5) **Relationship to interdiffs**: The response flips the original question about interdiffs making Change-IDs unnecessary, arguing that Change-IDs would actually enable better interdiff tooling by providing stable reference points.
