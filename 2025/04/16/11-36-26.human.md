This is a discussion about the format and semantics of Change-IDs in Git commit messages, part of the ongoing thread about patch series tracking approaches. Remo Senekowitsch argues against using URIs for Change-IDs, advocating instead for the originally proposed fixed-width reverse-hex format.

The key points made are:
1) Reverse-hex IDs are more flexible and tool-agnostic than URIs, which would lock users into specific code review systems' URL schemes
2) Randomly generated reverse-hex IDs can be added locally when creating commits, avoiding the chicken-and-egg problem of needing a URI before the commit exists
3) Free-form URIs risk becoming obsolete as tools change over time, while a standardized format would remain usable
4) Change-IDs actually enable better interdiff tooling rather than replacing it, by providing stable identifiers for tracking commit evolution

The email reinforces the Change-ID approach as a simpler, more maintainable solution compared to URI-based alternatives, while acknowledging this is part of a larger discussion about patch series management that includes other approaches like predecessor-successor relationships. The technical argument is well-reasoned and grounded in practical implementation experience.
