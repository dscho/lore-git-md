This is a follow-up discussion in the ongoing thread about configuration precedence between `pull.ff=only` and branch-specific rebase settings. D. Ben Knoble responds to Junio C Hamano's concerns about whether `pull.ff=only` should strictly enforce fast-forward behavior regardless of rebase settings.

The email provides a detailed analysis of the documentation for relevant Git configuration options (`pull.ff`, `branch.<name>.rebase`, and `branch.autoSetupRebase`). Knoble argues that branch-specific rebase settings should be treated as an explicit user opt-in that overrides `pull.ff=only`, similar to how command-line `--rebase` flags currently behave. They highlight that the documentation doesn't clearly specify precedence between these options.

The discussion reveals a philosophical difference in interpretation: Hamano views `pull.ff=only` as a strict safety measure against non-fast-forward operations, while Knoble sees it as a default behavior that should yield to explicit rebase preferences. Knoble suggests their proposed behavior would be useful for workflows where users want topic branches to rebase while protecting main branches from accidental merges.

The email raises the question of whether `pull.ff=true` (the default) might be a better solution for Knoble's use case, though they note this wouldn't provide the same protection against accidental merges. The discussion remains unresolved, with Knoble inviting further clarification if their position isn't clear.
