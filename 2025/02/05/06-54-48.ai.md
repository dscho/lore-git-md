Technical implementation concerns for branch status timestamp tracking.

Patrick Steinhardt raises important scalability concerns about the proposed timestamp tracking solution for branch status messages. Building on Junio Hamano's earlier technical assessment that timestamp tracking is feasible but requires careful design, Patrick points out a specific performance bottleneck: repositories with thousands or hundreds of thousands of references would require updating metadata for every reference during fetches, even when most references don't change. This would be particularly problematic with the "files" backend where each reference update requires a separate file operation.

The email highlights that the technical solution being discussed would need to handle extreme cases where a repository might have hundreds of thousands of references, and that simply recording no-op updates via reflog entries could create unacceptable performance overhead. This adds a new dimension to the implementation challenges beyond the architectural considerations Junio previously outlined, suggesting that any solution that works for small repositories might not scale well to very large ones.

This input moves the technical discussion forward by identifying a concrete constraint that would need to be addressed in any implementation - the solution must either find a way to efficiently record timestamps without per-reference filesystem operations, or accept that the feature won't scale to the largest repositories. The concern is particularly relevant given Git's use in monorepo environments where reference counts can be extremely high.
