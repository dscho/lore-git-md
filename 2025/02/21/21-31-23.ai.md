This is a review response from Junio C Hamano regarding Phillip Wood's bugfix for `git add -p` hunk splitting behavior. The patch in question (first in a two-part series) changes split hunks to default to "undecided" state rather than inheriting their parent's selection status.

Junio provides historical context, noting the current behavior dates back to the original implementation where this edge case wasn't carefully considered. While generally supportive of the change, he raises a nuanced concern about potential workflow regression for users who intentionally split already-selected hunks to selectively discard parts. He describes a scenario where power users might first accept a large hunk, then split it to reject specific sub-hunks - a workflow that would become more cumbersome with the proposed change.

The review doesn't request specific changes but highlights an alternative perspective that wasn't addressed in the original patch discussion. This introduces a new dimension to consider regarding user expectations and backward compatibility in interactive workflows. The concern is framed as a tradeoff between fixing counterintuitive behavior for most cases versus potentially disrupting established power-user patterns.

- Original behavior: split hunks inherit parent's selected/undecided state
