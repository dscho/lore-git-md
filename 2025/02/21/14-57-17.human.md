Bugfix for `git add -p`'s hunk splitting behavior after manual edits. This is the second patch in Phillip Wood's series addressing edge cases in interactive patch selection.

The patch fixes a subtle issue where editing a hunk (changing context lines to deletions or vice versa) could leave the hunk's internal `splittable_into` counter out of sync with its actual contents. The fix updates the splitting logic in `add-patch.c` to properly recount potential split points after edits, though the commit notes this is an edge case since users rarely edit and then split hunks.

The implementation adds careful tracking of line types during the recount operation, incrementing `splittable_into` when transitioning between different line types (context/added/removed). A new test case verifies the behavior by editing a hunk to change a context line to a deletion, then splitting it into more parts than would have been possible before the edit.

This follows the first patch's theme of improving hunk state management, maintaining Phillip Wood's pattern of thorough test coverage (21 new test lines) for the interactive patch interface he maintains. The change is surgical and well-explained, though the commit message acknowledges the scenario is unlikely to affect most users.
