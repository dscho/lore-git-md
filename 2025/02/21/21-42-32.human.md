This is the second patch in a two-part bugfix series addressing edge cases in `git add -p`'s hunk splitting behavior. While the first patch (about hunk state inheritance) has drawn more discussion, this one is technically uncontested and fixes a subtle issue where manual hunk edits could leave the `splittable_into` count out of sync.

The patch ensures that when users edit a hunk (changing deletion lines to context lines or vice versa), the system properly recalculates how many sub-hunks the edited version can be split into. Phillip notes this is an edge case since users rarely edit and then split the same hunk, but Junio Hamano confirms the fix with a wry reference to similar assumptions made during `add -i`'s original implementation.

The change is small (12 lines in `add-patch.c`) but comes with thorough test coverage (21 new test lines) that verifies the fix by:
1. Creating a file with splittable changes
2. Using a fake editor to modify line types
3. Verifying proper splitting into three parts
4. Confirming the final staged content matches expectations

Junio spots a minor formatting issue in the test script (missing space before `>file`) but otherwise approves the technical approach. This patch appears ready to go in once the discussion around the first patch's user experience implications is resolved.
