Phillip Wood's series to improve `git add -p`'s hunk splitting behavior has reached a resolution, with the most contentious change being deferred. The discussion between Phillip (the `add -p` expert) and Junio (maintainer) concluded that while changing split hunks to default to "undecided" rather than preserving their selection state is technically preferable, the potential disruption to existing workflows makes it too risky for the upcoming Git 2.50 release. Phillip will drop this change for now, with the understanding that it could be reconsidered if Git 3.0 introduces a feature flag mechanism for opt-in behavior changes.

The second patch in the series, which fixes an edge case where manual hunk edits could leave internal state inconsistent, remains valid and just needs minor test formatting adjustments before being merged. 

The thread also surfaced two longer-standing UX issues in `add -p` that may warrant future attention: the lack of visual state indicators when revisiting hunks, and a discrepancy between the documented and actual behavior of the J/K navigation commands. These were acknowledged as legitimate problems but are being treated as separate from the immediate hunk splitting improvements. The discussion remained focused and constructive throughout, with both technical merits and user experience considerations being weighed carefully.
