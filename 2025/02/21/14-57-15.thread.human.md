Phillip Wood's patch series to improve `git add -p`'s hunk splitting behavior has evolved into a nuanced discussion about interface design tradeoffs. The original proposal would make split hunks default to "undecided" state, addressing an inconsistency where users are prompted about already-selected hunks. Junio Hamano countered with an alternative approach - skipping prompts for selected sub-hunks to preserve power-user workflows.

In the latest exchange, Phillip expresses concerns that Junio's skip-prompt solution might create new confusion by making split hunks invisible during navigation. He acknowledges the dilemma between interface clarity and workflow efficiency, noting this edge case may not warrant extensive debate. The discussion has surfaced two broader UX limitations: the inability to revisit decisions after processing all hunks, and poor visibility into a hunk's current state when returning to it.

While the second patch (fixing manual edit synchronization) remains technically sound awaiting minor test formatting fixes, the first patch's design direction remains open. The core question is whether to prioritize clear state transitions (Phillip's approach) or workflow preservation (Junio's alternative), with neither solution clearly superior. Phillip suggests the issue's corner-case nature may make perfect resolution impractical, hinting the current discussion may be reaching its natural conclusion.
