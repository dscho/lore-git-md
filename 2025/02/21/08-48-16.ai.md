Performance benchmarking infrastructure discussion between GitLab and Google contributors.

This email from Patrick Steinhardt responds to Emily Shaffer's suggestions about Google's potential involvement in Git's continuous benchmarking effort. The key technical points center around two main concerns: actionability of performance reports and test repository characteristics. Patrick expresses skepticism about performance reports that don't include reproducible test cases, citing past experiences where proprietary repository data made issues impossible to debug. He agrees with Emily's long-term vision of standardized test repositories with different scaling characteristics (massive history vs large objects etc.), though notes this would likely require multiple distinct repositories.

The discussion reveals an emerging technical requirement: any performance reporting system must either work with fully reproducible test cases or provide sufficiently detailed repository metadata (#commits, object size distribution, etc.) to make proprietary-repo results actionable. Patrick also confirms the alert system would only report significant regressions, not routine "all clear" status updates. The email shows alignment between GitLab and Google on core goals while surfacing important implementation constraints around data sharing and reproducibility.

Notable that both organizations have experienced recent performance regression pain (GitLab in releases, Google over past 3 months), creating shared motivation. The thread now has concrete technical inputs from two major Git users with different infrastructure constraints (GitLab CI vs potential Google Cloud resources). Open questions remain about how to structure test repositories and what metadata makes proprietary-repo results useful without exposing sensitive data.
