Bugfix for `git add -p`'s hunk splitting behavior after manual edits. This is the second patch in Phillip Wood's series addressing edge cases in interactive patch selection.

The patch fixes a subtle issue where editing a hunk (changing context lines to deletions or vice versa) could leave the hunk's internal `splittable_into` count out of sync with its actual contents. The fix updates the split count during the recount operation that happens after editing, tracking whether we've seen a change in line type (context vs. addition/deletion) to determine split points. The implementation adds state tracking via a `marker` variable that follows line type transitions.

A new test case demonstrates the fix by:
1. Creating a file with changes that would normally split into two hunks
2. Using a fake editor to modify a context line into a deletion
3. Verifying the edited hunk can now be split into three parts
4. Confirming the final staged content matches expectations

While Phillip notes this is an edge case (users rarely edit then split hunks), the fix maintains consistency in the interface. The change is localized to `add-patch.c` with corresponding test additions in `t3701`, following the pattern established in the first patch of the series. The commit message clearly explains both the technical issue and its practical rarity.
