Bugfix for `git add -p` hunk splitting behavior, part 1 of 2 in a series addressing edge cases in interactive patch selection. This patch modifies how split hunks inherit their state from the original hunk they were split from.

The change ensures that when a hunk is split in the interactive patch interface, all resulting sub-hunks are marked as "undecided" rather than inheriting the selection state of the original hunk. This fixes a usability issue where splitting a selected hunk would automatically select all resulting sub-hunks without prompting the user, which was counterintuitive since splitting typically indicates the user wants to selectively apply parts of the hunk.

The implementation touches `add-patch.c` with two key changes: initializing new hunks with `UNDECIDED_HUNK` status during both the initial setup and subsequent line processing. A new test case in `t3701-add-interactive.sh` verifies the corrected behavior by checking that split hunks properly prompt for user input. The test creates a scenario where only some parts of a split hunk should be selected, validating the new undecided state behavior.
