This is a bug report about unexpected behavior in `git diff` output during merge conflicts. The reporter, Yurii Kartsev, describes a scenario where changes from a specific commit ("Version update") are not shown in the initial `git diff` output after a merge conflict, but only appear after staging the conflicted file and using `git diff --cached`.

The issue occurs when merging a branch where:
1. A merge conflict arises in pom.xml
2. The initial `git diff` shows two diffs related to the conflict but omits changes from the "Version update" commit
3. After staging the file, `git diff --cached` correctly shows all changes including the version update

The reporter provides a sample repository and terminal output to reproduce the issue. They're using Git 2.39.5 on macOS arm64 with clang 16.0.0. The bug appears to involve the merge conflict display logic in `git diff`, where certain changes are being hidden from the initial diff output but become visible after staging. This could indicate either a display logic bug or potentially a more fundamental issue with how merge conflicts are tracked.

Key technical details:
- Affected command: pom.xml file during merge
- Git version: 2.39.5 (Apple's fork)
- Platform: macOS arm64 (Darwin 24.3.0)
- The issue involves the interaction between `git diff` and `git diff --cached` during merge conflicts
- The reporter couldn't test on current Git due to build issues with gettext

The report is well-structured with clear reproduction steps and attached test case, suggesting this is a legitimate bug worth investigating rather than user error. The behavior difference between unstaged and staged diff views points to potentially interesting merge/diff machinery behavior.
