This thread addresses a Windows-specific bug in `git mv` where renaming a symlink would incorrectly rename its target instead of the symlink itself. The root cause lies in Windows API behavior where `CreateFileW` dereferences symlinks by default unless explicitly told not to with the `FILE_FLAG_OPEN_REPARSE_POINT` flag. Johannes Schindelin (Dscho) identified the issue and provided a minimal but impactful one-line fix in `compat/mingw.c` that adds this flag while maintaining compatibility with regular files.

The fix is now been reviewed by Junio Hamano and is being queued for integration into the `next` branch, indicating it meets Git's quality standards. The change is verifiable through existing tests 38 and 39 in `t7001-mv.sh` when run on Windows systems capable of creating symlinks. While this fix is independent of Dscho's broader work on Windows symlink support, it solves an immediate correctness issue for users working with symlinks created through other means. The patch includes thorough documentation linking to Windows API references and prior related commits, providing clear context for the change. With no outstanding technical objections, this fix is on track to be included in an upcoming release.
