Here's a human-readable summary of the thread so far:

This thread addresses a Windows-specific bug in `git mv` where renaming a symlink would incorrectly rename its target rather than the symlink itself. The issue stems from how Windows' `CreateFileW` API handles reparse points (Windows' equivalent of symlinks) by default.

The fix is straightforward - adding the `FILE_FLAG_OPEN_REPARSE_POINT` flag to prevent automatic dereferencing while maintaining existing functionality for regular files. The bug was caught by existing tests (t7001-mv.sh tests 38-39), though only manifests when run on Windows systems with proper symlink support.

Johannes Schindelin (Git for Windows maintainer) has reviewed the patch and recommends upstreaming it regardless of ongoing symlink support work, noting that symlinks can be created through other means besides Git. The change is minimal (just one line in mingw.c) but important for correct behavior on Windows.
