This is a review response to Phillip Wood's patch fixing edge cases in `git add -p`'s hunk splitting behavior. Justin Tobler provides feedback on the first patch in the series, which changes split hunks to be marked "undecided" rather than inheriting their parent hunk's selection state.

Justin confirms the technical approach makes sense, noting the patch explicitly sets both the initial hunk and subsequent split hunks to UNDECIDED_HUNK status. He observes this change aligns with user expectations when splitting hunks to select subsets of changes, though acknowledges this could require more manual selections for large hunks split into many pieces. The review highlights two key implementation details: the initialization of `hunk->use` in both the main split function and the line processing loop, and the test case verifying the new behavior with a sequence of user inputs (n/K/s/n/y/q).

No objections are raised to the technical solution, though Justin does note the explicit UNDECIDED_HUNK assignment for subsequent hunks may be redundant since they'd inherit that state anyway. The feedback suggests the patch is well-reasoned and properly tested, with only minor stylistic observations about the implementation. This appears to be a straightforward review confirming the patch's approach while noting a small implementation detail that could potentially be simplified.
