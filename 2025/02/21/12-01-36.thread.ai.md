This thread addresses a Windows-specific bug in `git mv` symlink handling, where renaming a symlink incorrectly renamed its target instead of the symlink itself. The root cause is Windows API behavior where `CreateFileW` dereferences symlinks unless explicitly told not to with `FILE_FLAG_OPEN_REPARSE_POINT`. The fix adds this flag alongside existing `FILE_FLAG_BACKUP_SEMANTICS` in `compat/mingw.c`, maintaining compatibility with regular files while properly handling symlinks.

The regression is detectable by existing tests 38 and 39 in `t7001-mv.sh` when run on Windows with symlink creation capabilities. Johannes Schindelin (Dscho) notes this should be upstreamed regardless of ongoing symlink support work, as symlinks can be created through other means. The change is minimal (one line) but impactful for Windows users working with symlinks. The patch provides thorough background including prior related commits, Windows API documentation, and the original bug report. No outstanding technical objections or requested changes remain.
