Performance optimization for `git bisect` initialization in large repositories.

Junio C Hamano presents an experimental patch addressing the known performance bottleneck in `git bisect` initialization for large repositories (like the Linux kernel with 572k+ revisions). The current implementation can take 18+ minutes on SSDs and up to an hour on HDDs for the initial bisection step. The patch explores three potential optimizations:

1. **Midpoint merge traversal**: Instead of processing merges in commit-list order, try merges starting from the middle of the list first. This alone shows dramatic improvement, reducing runtime from ~20 minutes to ~30 seconds in test cases while maintaining good bisection accuracy (19 commits from theoretical halfway vs original 17,871).

2. **Loosened halfway threshold**: Currently disabled, this would allow larger slack (3% vs 0.1%) in the "good enough" criteria during early bisection steps when the candidate set is still large.

3. **Early discard of non-viable candidates**: Also currently disabled, this would mark commits as non-viable if they're closer to the good end than a merge already known to be too far from halfway.

The patch implements the first approach (midpoint traversal) with added trace2 instrumentation and leaves the other two as commented-out experiments. Key changes include collecting merges into an array and processing them from the middle outward, plus some structural reorganization of the bisection logic in `bisect.c`. The results show the midpoint approach finds a similarly good bisection point much faster, though Junio notes the other ideas might warrant further exploration despite being trickier to implement correctly.
