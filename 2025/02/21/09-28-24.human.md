Performance optimization discussion for `git bisect` midpoint selection.

Uwe Kleine-König responds to Junio Hamano's experimental patch that dramatically improved `git bisect` performance by implementing midpoint merge traversal. While acknowledging the core optimization's effectiveness, Uwe proposes an alternative approach that would use a scaled bisection on the topological commit list rather than the current middle-out processing.

The suggested method would:
1. Take the middle commit from a `git rev-list --topo-order` output
2. Check its "distance" from the ideal midpoint
3. Make proportional adjustments to find the next candidate

Uwe notes this might not find the absolute best bisection point but could offer different tradeoffs. This comes as the thread has largely settled on Junio's core optimization approach, with some discussion remaining about optional modes and future directions like first-parents-first bisection.

The email doesn't propose concrete code changes but rather floats an algorithmic idea for consideration alongside the already-working midpoint traversal solution. It represents a continuation of the performance optimization discussion rather than a challenge to the core approach.
