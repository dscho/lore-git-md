This is patch 7/16 in a performance optimization series for the refs subsystem, focusing on batched refname availability checks in the files backend. The patch refactors the initial transaction logic in the files backend to use the new batched verification API introduced earlier in the series, though the performance impact isn't yet realized since the underlying implementation still processes refs individually. The change prepares for future optimizations that will improve performance during repository cloning and ref format migrations.

The key technical change moves from individual `ref_verify_refname_available()` calls to collecting refnames in a `refnames_to_check` string list and verifying them in bulk via the new `refs_verify_refnames_available()` function. The patch maintains the same locking semantics and error handling, just restructuring the verification to happen after all refnames are collected but before the packed-refs transaction commits.

This continues the series' pattern of first establishing the batched verification pattern (seen in patches 4-6) before implementing the actual performance optimizations. The commit message notes this is groundwork for future patches that will realize the speedups, particularly for operations involving many refs. The changes touch the files backend's transaction preparation logic, specifically the initial transaction case that handles bulk ref creation scenarios.
