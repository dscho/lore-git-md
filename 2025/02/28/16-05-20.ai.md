Bugfix discussion regarding `git rev-list` topological ordering with `--no-walk`. Clement Moyroud clarifies that Phillip Wood's suggested combination of `--topo-order --no-walk` does not work as hoped, because the `--no-walk` flag explicitly disables topological ordering according to the documentation. This confirms that the current implementation has no way to maintain topological relationships between input commits while restricting processing to just those commits (without walking ancestors).

The key technical insight is that Git currently treats `--no-walk` as mutually exclusive with topological sorting - when `--no-walk` is active, commits are either shown in input order (`--no-walk=unsorted`) or reverse chronological order (`--no-walk=sorted`), with no option to preserve topological relationships between the input commits when timestamps collide. Clement suggests this may require a new flag or mode that combines the benefits of both: restricting to input commits while still applying topological sorting when dates match.

This email moves the discussion from exploring existing solutions to recognizing the need for potential API changes. The core limitation is now clearly identified as a gap in the `rev-list` interface rather than a misunderstanding of existing flags. The thread remains focused on Clement's original use case of automated cherry-picking workflows where maintaining commit relationships is crucial but processing the full graph is prohibitively expensive.
