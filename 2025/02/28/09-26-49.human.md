Performance optimization for reftable backend in the ongoing refs subsystem series. This is patch 12/16 in v4 of Patrick Steinhardt's performance optimization series for refname availability checks.

The change implements seeking capability for reftable reference iterators, building on the iterator reseek foundation established in earlier patches. The implementation is straightforward since the low-level reftable iterators already support seeking. Two notable aspects: (1) reflog iterators explicitly don't support seeking as there's no clear use case yet, and (2) the patch adds error checking for `reftable_stack_init_ref_iterator()` that was previously missing.

The diff shows the technical implementation - adding a `seek` method to the iterator vtable, properly managing memory for the prefix string, and ensuring error handling. This continues the series' trend of measurable performance improvements, though specific benchmarks for this patch aren't called out (the series overall shows 2.32x reftable speedup with 10k refs against 100k existing).

This is a well-contained change that fits cleanly into the larger optimization effort, with clear explanations of both what's implemented and what's intentionally excluded (reflog seeking). The implementation appears solid and maintains consistency with the series' cross-backend interface approach.
