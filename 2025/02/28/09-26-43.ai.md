Performance optimization patch extending batched refname availability checks to the files backend, part of a larger series addressing refs subsystem inefficiencies. This is patch 6/16 in v4 of the series, following the reftable backend changes in patch 5/16.

The patch modifies the files backend to batch refname availability checks during normal transactions, similar to the reftable changes made previously. It focuses on two key contexts where batching makes sense: during reference locking (when checking for packed ref conflicts) and transaction preparation. The implementation introduces a `refnames_to_check` string list to accumulate refnames for batched verification, while carefully maintaining the existing locking semantics to avoid breaking user expectations.

A notable tradeoff is acknowledged - the batched check happens before locking packed-refs, creating a potential race window where packed-refs could change after verification but before the transaction completes. The patch documents this as an accepted limitation to avoid introducing global locking behavior that might surprise users. The changes touch core files-backend operations including `lock_raw_ref()`, `lock_ref_for_update()`, and `files_transaction_prepare()`, with careful attention to error handling and cleanup paths.

This continues the series' pattern of first establishing API changes (patches 1-3), then implementing batched verification infrastructure (patch 4), and now applying it systematically across backends. The files backend implementation shows more complexity than reftable due to its multiple verification contexts, requiring careful analysis of which paths benefit from batching. Performance measurements from earlier in the series suggest these changes will contribute to the overall 1.19x files backend speedup when complete.
