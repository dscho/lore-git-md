This is a technical discussion about bitmap iterator implementation in the ongoing MIDX bitmap optimization series.

Patrick Steinhardt responds to Taylor Blau's patch that replaces `ewah_iterator` with `ewah_or_iterator` for type bitmap iteration. The change affects how commit, tree, blob and tag objects are processed in the pack-bitmap.c file, introducing new `*_all` fields and `base_nr` parameter usage across all object types.

Steinhardt raises a consideration about whether to maintain the simpler non-layered iterator for non-MIDX cases, but acknowledges the current unified approach's advantages: reduced conditional logic and minimal performance impact. He notes the implementation relies on proper initialization of `base_nr` and `*_all` fields even in single-pack scenarios.

The exchange continues the thread's focus on bitmap iteration efficiency and MIDX integration, specifically addressing:
- The tradeoff between specialized vs unified iterator paths
- Memory layout requirements for both MIDX and non-MIDX cases
- Performance characteristics of the bitwise OR operations
- Field initialization invariants needed to maintain correctness

This represents an implementation detail refinement in the larger bitmap optimization work, with Steinhardt providing a thoughtful review point about case handling while ultimately endorsing the current direction.
