Documentation update clarifying the procedure for handling breaking changes in Git. This is a follow-up to previous discussions about how to manage backward-incompatible changes leading up to Git 3.0.

The patch makes several adjustments to the BreakingChanges.adoc document. It removes a leftover reference to the abandoned "feature.git3" runtime switching approach, now that the project has settled on using a compile-time switch (WITH_BREAKING_CHANGES) instead. The text is updated to better explain that this mechanism allows breaking changes to be prepared incrementally over time, while keeping them hidden until the major version boundary. It also notes that the anticipated CI job for testing breaking changes has now been implemented.

The changes reflect decisions from prior discussion threads, including the rejection of runtime configuration in favor of compile-time control (particularly important for documentation changes). The patch also implicitly addresses (by omission) questions about repository format changes, suggesting these should be handled separately via the extensions.* system rather than being part of this breaking changes mechanism.

This appears to be a straightforward documentation cleanup that codifies previously agreed-upon project decisions, removing outdated information while making the intended process clearer.
