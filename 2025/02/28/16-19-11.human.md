This is a follow-up discussion about Phillip Wood's proposed change to `git add -p` hunk splitting behavior, which would mark split hunks as "undecided" rather than inheriting their parent hunk's selection state. The thread shows the author and maintainer converging on the technical merits of the change but hesitating due to backward compatibility concerns.

Phillip has decided to drop the patch for now, acknowledging Junio's caution about changing long-standing behavior that users may rely on. They discuss possibly revisiting it for Git 3.0 if a versioned feature mechanism is introduced. The exchange also surfaces two related UX issues: the lack of visual state indication when revisiting hunks, and a mismatch between the documented and actual behavior of the `J`/`K` navigation commands.

Junio expresses a preference against adding configuration knobs for these behaviors, favoring either keeping the status quo or making clean behavioral changes when appropriate (like in a major version bump). The discussion remains constructive, with both participants clearly articulating the tradeoffs between interface consistency and stability. While this specific change is being deferred, the thread has helped identify some broader `add -p` usability issues that may warrant future attention.
