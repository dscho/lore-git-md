Performance optimization patch (5/16) in the refs subsystem series, transitioning reftable backend to batched refname availability checks.

This patch modifies the reftable backend to collect refnames for verification in a batch rather than checking them individually during transaction preparation. While the current implementation still performs the same underlying checks (via the new `refs_verify_refnames_available()` function introduced in patch 4/16), this change sets up the infrastructure for future optimizations that will take advantage of batched processing. The key changes are:

1. Introduces a new `refnames_to_check` string list to accumulate refnames during transaction preparation
2. Moves the verification step to after all refnames have been collected
3. Maintains all existing error handling and transaction flags
4. Preserves the sorting behavior (via `string_list_sort`) that was implicit in the previous per-ref checks

The patch is part of a larger effort to optimize refname availability checks across Git's ref backends, with particular focus on improving reftable performance when handling tombstone references. While this specific change doesn't yet demonstrate performance improvements (as noted in the commit message), it's a necessary step toward the batched iterator optimizations that will come in later patches of the series.

The implementation appears clean and maintains the existing behavior while preparing for future optimizations. It follows the pattern established in earlier patches of the series, building on the new batch verification API while keeping the changes focused on the reftable backend. The patch maintains compatibility with the transaction preparation flow and properly cleans up allocated resources.
