Bugfix for mailmap handling in `git check-mailmap` when processing full mailmap entries.

Jacob Keller reports a segmentation fault and unexpected behavior in `git check-mailmap` when processing mailmap entries that contain both old and new name/email pairs (so-called "full" entries). The crash occurs when passing just an email address to check, as the code passes NULL for the name parameter to `map_user()`. 

The patch attempts to fix this by:
1. Changing `check-mailmap.c` to pass an empty string instead of NULL for the name parameter
2. Modifying `mailmap.c` to handle cases where a mailmap entry has exactly one subitem but no simple entry
3. Adding a test case that verifies the fix works with full mailmap entries

The author notes that while their solution fixes their test case, it causes another existing test to fail (the whitespace syntax test) by unexpectedly translating a previously untranslated name. They're seeking help understanding the mailmap code better to find a more complete solution.

Key technical details:
- The issue stems from how `map_user()` handles NULL vs empty string names
- Full mailmap entries store mappings in subitems rather than direct name/email fields
- The current fix attempts to handle single-subitem cases specially
- The test case demonstrates the expected behavior with a full mailmap entry mapping "Bugs <bugs@company.xx>" to "Bug Reports <bugs-new@company.xx>"

This appears to be a genuine bug that could affect users relying on full mailmap entries, though the proposed solution may need refinement based on the unexpected test failure. The patch touches core mailmap functionality but is narrowly scoped to the specific crash case.
