Feature proposal and response regarding pre-push hook limitations in identifying new commits during push operations, particularly when creating new remote branches. Original author Jayce Cao identified performance issues where current pre-push hooks must scan entire branch histories when pushing to new branches, as `git rev-list` shows all commits rather than just new ones being transmitted. Brian M. Carlson responded with technical analysis of both performance and security aspects.

For performance, Carlson referenced Git LFS's optimization using `git rev-list --not --remotes=origin` to exclude objects reachable from remote-tracking refs, while noting this fails when remotes are specified as URLs rather than names (common in EGit/JGit). On security, Carlson highlighted fundamental limitations where hooks can be bypassed via `--no-verify` and aren't invoked by alternative Git implementations like libgit2, suggesting server-side verification would be more robust.

Core technical challenges involve: the pre-push hook's lack of direct access to transmitted commits, inefficiency of current workarounds using `git ls-remote` and `git rev-list` in large repositories, and the remote URL vs name distinction affecting optimization approaches. The discussion touches Git's push protocol internals, hook infrastructure, and cross-client compatibility.

Open questions remain about: potential changes to Git's hook interface for more efficient commit identification, whether protocol-level modifications might help, and whether the pre-push hook approach is fundamentally advisable given security bypass possibilities.
