This thread investigates a significant performance regression in Git's reftable backend when creating large numbers of references, originally reported by brian m. carlson with a 30x slowdown compared to the traditional files backend. The discussion has progressed through several stages of analysis:

Initial findings pinpointed tombstone records in reftable (created during deletions) as preventing auto-compaction while still forcing expensive conflict checks. Patrick Steinhardt's optimization of `repo_get_oid()` to skip exact object ID checks narrowed the performance gap from 30x to 32x, and Jeff King's profiling revealed that `refs_verify_refname_available()` now accounts for 80% of the remaining overhead.

The current focus is on two main optimization paths: batching ref updates to process conflict checks more efficiently (especially for common prefixes like "refs/heads/") and suppressing ambiguous ref warnings either through a global config or new API flag for bulk operations. Steinhardt has confirmed plans to implement both approaches.

A side discussion emerged when Christian Couder suggested modifying reftable's auto-compaction heuristics to consider entry counts rather than file sizes, which could help with tombstone-heavy cases. Steinhardt acknowledged the theoretical benefit but argued the approach would be too expensive to implement, as it would require parsing entire reftable files on every write operation. This keeps the focus on the previously identified verification bottlenecks rather than pursuing compaction heuristic changes.

The investigation has maintained a clear trajectory from initial problem identification through to concrete optimization strategies, with Steinhardt and King driving the technical analysis. With the performance bottlenecks now well understood and solutions in development, the thread appears to be moving toward resolution while preserving the reftable backend's correctness guarantees.
