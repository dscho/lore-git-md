This thread investigates a significant performance regression in Git's reftable backend when creating many references after deletions, originally reported by brian m. carlson showing up to 78x slowdowns compared to the traditional files backend. The root cause was identified as tombstone records in reftable preventing auto-compaction while still requiring expensive conflict checks during mass ref creation.

Patrick Steinhardt and Jeff King (Peff) have proposed several optimizations: skipping redundant `repo_get_oid()` checks (already yielding a 3x speedup), batching ref updates to process conflict checks more efficiently, and suppressing ambiguous ref warnings during bulk operations. Christian Couder has now suggested a more fundamental change to reftable's compaction strategy - triggering based on entry counts rather than file sizes - which could better handle tombstone-heavy scenarios. While this would require deeper changes to the reftable implementation, it addresses the core issue that current size-based thresholds don't properly account for the fragmentation caused by mass deletions.

The discussion has progressed from identifying the regression to having multiple concrete optimization paths: short-term fixes to reduce overhead in `git-update-ref`, medium-term batching improvements, and potential long-term changes to reftable's compaction heuristics. The original test case (creating 50,000 refs) remains the benchmark for evaluating these improvements, with the files backend's 181ms performance as the target to approach.
