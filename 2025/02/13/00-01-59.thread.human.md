This thread investigates a significant performance regression in Git's reftable backend when creating large numbers of references, originally showing a 30x slowdown compared to the traditional files backend. The core issue stems from tombstone records interfering with reftable's auto-compaction while requiring expensive conflict checks in `refs_verify_refname_available()`.

After initial optimizations by Patrick Steinhardt (reducing the gap from 30x to 32x) and Jeff King's analysis identifying the verification function as the remaining bottleneck (80% of runtime), the discussion has focused on two main solutions: batching ref updates and suppressing ambiguous ref warnings during bulk operations. Earlier ideas about adjusting compaction heuristics were set aside due to impractical overhead.

In the latest development, Steinhardt explains why the batching approach faces deeper architectural challenges than initially thought. The reftable backend supports reseekable iterators, but the generic ref iterator infrastructure doesn't yet have this capability - iterators are immediately freed when exhausted. This limitation prevents the efficient parallel iteration needed for optimal batching. Steinhardt reveals this is part of ongoing work he's been doing for months to optimize iterator lifetimes, similar to previous reftable-specific improvements.

While this means the performance fixes will require more foundational work than hoped, the thread has successfully identified both the immediate bottleneck and the necessary architectural changes to address it. The discussion remains focused and productive, with Steinhardt taking ownership of the iterator revamp while maintaining the project's correctness guarantees. The original test case (50,000 ref creation) continues to guide the optimization efforts.
