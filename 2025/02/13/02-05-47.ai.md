This is a feature proposal regarding the pre-push hook's ability to accurately identify commits being pushed, particularly when pushing to a new branch. The author, Jayce Cao, wants to implement sensitive data checking in pre-push hooks but faces a challenge: when pushing to a new remote branch, `git rev-list` shows all commits in the branch's history rather than just the new ones being pushed. This creates unnecessary overhead for large repositories with millions of commits, as the hook would examine commits that already exist remotely.

The current workaround involves using `git ls-remote` to get remote commits and then filtering with `git rev-list $local_oid ^$haves`, but the author notes this becomes inefficient when the remote has many branches. The core issue is that the pre-push hook lacks direct access to which commits will actually be transmitted during the operation.

This touches on Git's push protocol internals and hook infrastructure. The problem appears genuine for large repositories where scanning entire histories would be prohibitively expensive. The author is looking for a more efficient way to get just the new commits that will be transmitted, possibly requiring changes to how Git provides information to the pre-push hook. The proposal doesn't suggest a specific solution but invites discussion about better approaches to this limitation.
