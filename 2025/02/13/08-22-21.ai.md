This is a technical discussion about optimizing the reftable backend's performance during mass ref operations, specifically addressing the conflict detection overhead.

Jeff King (peff@peff.net) responds to Patrick Steinhardt's analysis of the reftable performance issues during mass ref creation after deletion. While agreeing with the tombstone-related auto-compaction issue, Peff probes deeper into why conflict checks remain so expensive despite the small table size (360k). He identifies that the current implementation performs a full merged iteration of all tables for each individual ref update, suggesting this could be optimized by batching ref updates and processing them in parallel with a single pass through the merged tables.

Peff also examines Steinhardt's proposed `repo_get_oid()` optimization, noting that the performance hit comes not from general revision parsing but from a specific warning about ambiguous refnames (from commit 798c35f). He suggests either disabling this warning globally (via `core.warnAmbiguousRefs`) or adding a more targeted API flag to suppress it for bulk operations. The email provides important technical insights into two distinct optimization opportunities - batching conflict checks and refining object ID parsing - that could significantly improve the reftable backend's performance in this edge case.
