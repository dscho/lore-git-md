Performance optimization discussion regarding reftable compaction heuristics.

Patrick Steinhardt responds to Christian Couder's suggestion about modifying reftable auto-compaction logic to consider entry counts rather than file sizes. The context is the ongoing investigation into reftable performance during mass ref operations, where tombstone records from deletions prevent compaction due to the current size-based heuristics.

Steinhardt acknowledges the theoretical merit of counting entries instead of file sizes, particularly for edge cases involving many small tombstone records. However, he notes this would require parsing entire reftable files to count entries, as the format doesn't currently store record counts in headers/footers. He argues this overhead would be too expensive for the auto-compaction check that runs on every write operation.

This exchange represents a side discussion in the larger performance investigation, maintaining focus on the core issue that tombstone-heavy reftables don't trigger compaction under current heuristics. Steinhardt's response suggests this particular optimization isn't worth pursuing given implementation costs, keeping attention on the more promising paths of batching ref verification and warning suppression that were previously identified as the primary bottlenecks.
