Performance optimization patch for ref backend migration, now facing architectural reconsideration.

Karthik Nayak responds to Junio Hamano's suggestion that reflog management should be handled separately from backend migration. While acknowledging that a standalone `git reflog drop` command would be useful for general reflog cleanup, Karthik argues that the `--skip-reflog` flag still provides important performance benefits during migration. The key points are:

1. Performance justification: For large repositories (millions of refs), skipping reflog migration can significantly reduce migration time when reflogs aren't needed, which is critical since migration blocks all other operations.

2. Use case clarification: The flag isn't meant as a general reflog management tool, but specifically to optimize migration when reflogs are known to be unwanted (e.g., in server-side repos where they were enabled temporarily for debugging).

3. Alternative approach: While `git reflog drop` could be used before migration, having the skip option directly in the migration command provides more control and avoids the need for separate operations.

The discussion has shifted from implementation details to the architectural question of whether performance optimizations should be built into the migration command or handled through separate reflog management tools. Karthik makes the case that both approaches have merit and the migration-specific optimization remains valuable for production use cases like GitLab's large repositories.
