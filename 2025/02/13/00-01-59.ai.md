Performance issue report showing severe slowdown in reftable backend during mass ref creation.

Brian M. Carlson reports a significant performance regression when creating 50,000 refs using the reftable backend compared to the traditional files backend. The test involves deleting all refs in a Linux kernel repository clone and then recreating them from a prepared input file. The files backend completes in about 5.5 seconds, while reftable takes nearly a minute (57.44 seconds) - approximately 30x slower.

The test setup uses two modern Linux machines (Ubuntu 24.04 and Debian unstable) with Git's 'next' branch. The script provided creates synthetic refs across multiple namespaces (heads, remotes, tags) to simulate a realistic distribution. While acknowledging this is a synthetic benchmark, Carlson notes it was intended to model the reference update portion of an initial large push operation.

Key technical details include:
- Test methodology uses `/usr/bin/time` to measure performance
- Memory usage is similar between backends (~160MB RSS)
- The script can be modified to use real refs from a local Linux repo clone
- Includes migration step to reftable format when testing that backend

The report doesn't analyze root causes but suggests the issue should be easy to profile given the dramatic performance difference. This appears to be a serious regression for repositories with many refs, though the impact on more common workflows remains to be seen. The clear reproduction script and controlled test conditions make this a well-documented performance investigation.
