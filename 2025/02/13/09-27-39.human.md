This is a performance optimization suggestion in the ongoing reftable backend investigation. Christian Couder proposes an alternative approach to triggering auto-compaction in the reftable backend, which currently doesn't kick in during mass ref deletions because the geometric sequence remains intact based on file sizes rather than entry counts.

The suggestion comes as a follow-up to Patrick Steinhardt's explanation of why auto-compaction isn't happening during mass ref deletions - because the second table containing only deletions is much smaller in size, preserving the geometric sequence. Couder floats the idea of using entry counts rather than file sizes as the metric for determining when to compact, which could potentially trigger compaction more appropriately in this scenario.

The email is framed as a theoretical suggestion rather than an immediate proposal ("Not that I think we should work on this right now"), indicating it's more of a brainstorming contribution to the ongoing performance discussion. This adds another potential optimization path to the existing set being considered (batching ref updates and suppressing ambiguous ref warnings). The suggestion appears technically sound at first glance, though its implementation complexity and performance impact would need evaluation.
