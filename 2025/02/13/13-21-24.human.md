This is a technical discussion about potential optimizations for the reftable backend's auto-compaction behavior, continuing the performance investigation thread.

Patrick Steinhardt responds to Christian Couder's suggestion about counting entries (rather than file size) to trigger reftable compaction. While acknowledging the theoretical merit of the idea for edge cases like mass ref deletions, Steinhardt explains why it wouldn't be practical: reftable files don't store entry counts in their headers/footers, so implementing this would require fully parsing each table during every write operation to count entries. This would make the already performance-sensitive auto-compaction check too expensive.

The exchange highlights an important trade-off in the reftable design - the current size-based compaction trigger is intentionally simple and fast, even if it sometimes misses optimization opportunities in pathological cases. Steinhardt's response reinforces that any compaction strategy must remain lightweight since it runs frequently during write operations. This discussion represents a side path from the main thread's focus on `refs_verify_refname_available()` optimizations, showing the team carefully considering but ultimately shelving alternative approaches that would require deeper architectural changes.
