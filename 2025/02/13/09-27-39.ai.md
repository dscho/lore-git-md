Performance optimization discussion for reftable backend's compaction behavior. Christian Couder responds to Patrick Steinhardt's explanation of why auto-compaction doesn't trigger after mass ref deletions (where tombstones create small tables that don't meet size-based compaction thresholds). Couder suggests an alternative compaction trigger mechanism - counting entries per file rather than file sizes - as a potential future optimization path.

The suggestion directly addresses the root cause identified in the thread (tombstone records preventing auto-compaction while requiring expensive conflict checks). This would modify reftable's geometric compaction strategy to consider entry count rather than physical file size, which could help trigger compaction more appropriately after operations that create many small tombstone records. The proposal is framed as theoretical rather than immediate work, acknowledging the ongoing optimization efforts around `repo_get_oid()` skipping and potential batching improvements.

Key technical aspects:
- Current compaction uses file sizes in geometric sequence calculation
- Tombstone-heavy tables are small but numerous, failing current size thresholds
- Entry-count-based compaction could better reflect actual database fragmentation
- Would require modifying reftable's compaction heuristics
- Positioned as complementary to other optimizations under discussion
