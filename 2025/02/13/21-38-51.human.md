This is a performance optimization discussion regarding commit mark clearing in Git's commit.c. René Scharfe responds to Patrick Steinhardt's analysis of his earlier patch that restructured parent commit processing to reduce peak memory usage.

The key points in this follow-up:
1. René clarifies that the algorithm remains depth-first, just with earlier processing of side branches (second+ parents) rather than accumulating them in a list.
2. He questions whether there are actually any cases where the new approach would perform worse, challenging Patrick's suggestion about potential regressions in "branch thicket" scenarios.
3. While test suite measurements show modest improvements (max list length reduced from 12 to 4), René frames the change as an obvious improvement with no apparent downsides.

The discussion remains technical but has shifted from implementation details to a philosophical debate about optimization value - whether eliminating an unnecessary accumulation pattern is worthwhile even without dramatic real-world performance gains. René maintains there's no reason to keep the less efficient approach if the new one has no downsides.
