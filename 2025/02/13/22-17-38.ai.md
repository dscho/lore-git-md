This is a performance discussion in the ongoing reftable backend investigation, focusing on the impact of ambiguous refname warnings. Brian m. carlson responds to Jeff King's suggestion about disabling these warnings, agreeing that both the warning flag and iterator improvements would help performance.

The email reinforces the emerging consensus that ambiguous refname warnings (introduced in commit 798c35f) create unnecessary overhead in automated workflows. Brian specifically highlights that `git update-ref` operations during pushes and API calls always work with full object IDs where these warnings provide no value. They argue that even interactive users of `git update-ref` (like scripters) would prefer performance over these warnings.

Key technical points for future reference:
- The discussion centers around `core.warnAmbiguousRefs` config and `warn_on_object_refname_ambiguity` internal flag
- Primary use case is reference updates in push/API contexts where full OIDs are guaranteed
- Performance impact is most noticeable in `git update-ref` operations with many refs

This response strengthens the case for either removing these warnings entirely or making them opt-in, particularly for automated workflows. It provides real-world justification from a user perspective (server backends, GUIs, scripting) for prioritizing performance over the warning functionality.
