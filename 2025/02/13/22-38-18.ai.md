This is a bugfix discussion regarding tag fetching behavior in protocol v2. Taylor Blau confirms Igor Todorovski's report that commit 3f763ddf28 ("fetch: set remote/HEAD if it does not exist") unintentionally broke tag decoration when fetching specific commits with depth limits. The issue occurs because the commit added "HEAD" to ref_prefixes, which now prevents the server from returning tags unless explicitly requested.

Taylor provides technical analysis suggesting the root cause lies in the interaction between three commits: 3f763ddf28 change, 6c915c3f85 (which modified HEAD fetching logic), and e70a3030e7 (original protocol v2 hash-only fetch optimization). He proposes a fix that would unconditionally add "refs/tags/" to ref_prefixes when tag following is enabled, but seeks confirmation from the original authors (CC'd) since this area involves subtle protocol v2 behavior.

Key technical points:
- The regression affects `git log --decorate` output for shallow-fetched commits
- Original assumption from e70a3030e7 about when to skip tag listing no longer holds
- Proposed solution modifies builtin/fetch.c to always include tags prefix when tags are requested
- Discussion involves protocol v2 fetch semantics and remote/HEAD handling

This appears to be a genuine regression with a plausible fix proposed, though the solution touches sensitive protocol behavior and requires review from experts in this area. The thread is now awaiting input from the original authors of the related commits.
