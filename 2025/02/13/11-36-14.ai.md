This is a bug investigation report about file collisions during cloning and their potential connection to ongoing renormalization filter issues.

Josef Wolf reports discovering file collision warnings when cloning a repository on a case-sensitive filesystem, where no case-sensitivity issues should exist. The colliding files (like 'Projects/P-0113/B.ets5hash') are the same ones causing problems during renormalization operations. These files contain hash values for a proprietary application that must match the data files exactly.

The report explains the files' history: originally committed as binary blobs before the author understood how to regenerate them, later moved to .gitignore with a smudge filter for regeneration, but kept in the repo as a fallback. This hybrid approach (both in .gitignore and occasionally committed) may be causing the collision warnings. The author notes they cannot yet reproduce this in a fresh test case.

The email connects this to the ongoing renormalization investigation by questioning why these collisions cause complete renormalization failures even when resolved during rebase. This appears to be a new dimension to the previously reported CRLF conversion issues during renormalize rebase, suggesting the file collisions may be interacting with the filter pipeline in unexpected ways.

Key technical details for future reference:
- Collision warnings appear on case-sensitive Linux filesystem
- Affected files are *.ets5hash files containing application-critical hashes
- Files exist both in .gitignore and occasionally committed
- Smudge filter (ets-utils -s) regenerates hashes
- Same files cause problems during renormalization rebase
- Connection between clone collisions and renormalization failures not yet understood

The investigation continues to uncover complex interactions between Git's attribute processing, filter pipeline, and repository state management, with this email adding file collision behavior to the mix of symptoms being examined.
