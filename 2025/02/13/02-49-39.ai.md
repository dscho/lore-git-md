Response to Jayce Cao's pre-push hook efficiency concerns from Brian M. Carlson.

This is a technical response addressing performance and security limitations in pre-push hooks for commit verification. Brian M. Carlson responds to Jayce Cao's proposal about efficiently identifying new commits during push operations, particularly when creating new remote branches.

The response highlights fundamental security limitations with the pre-push hook approach itself, noting that hooks can be bypassed via `--no-verify` and aren't invoked by alternative Git implementations like libgit2. Carlson suggests reading Git's hook restriction FAQ and implies server-side verification would be more robust.

For the performance concern, Carlson references Git LFS's optimization using `git rev-list --not --remotes=origin` to exclude objects reachable from remote-tracking refs. However, he notes this fails when remotes are specified as URLs rather than names (common in EGit/JGit). The response doesn't propose new solutions but provides context about existing approaches and their limitations.

Key technical details include the `--not --remotes` optimization, the remote URL vs name distinction, and implications for alternative Git clients. The discussion remains open-ended, with Carlson acknowledging no known better solution while questioning whether the approach itself is advisable given security bypass possibilities. The exchange touches Git's hook security model, push protocol internals, and cross-client compatibility concerns.
