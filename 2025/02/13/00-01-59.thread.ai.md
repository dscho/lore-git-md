Performance regression investigation in reftable backend during mass ref creation, with optimization focus on `refs_verify_refname_available()` bottleneck and reftable compaction heuristics. Originally reported by brian m. carlson showing 30x slowdown (57.44s vs files backend (5.5s) when creating 50,000 refs, with root cause identified as tombstone records preventing auto-compaction while requiring expensive conflict checks.

Current status:
- Patrick Steinhardt's `repo_get_oid()` optimization (skipping exact object ID checks) reduced gap from 30x to 32x (reftable: 16.3s→5.9s, files: 223ms→181ms)
- Jeff King's analysis shows `refs_verify_refname_available()` now accounts for ~80% of remaining runtime
- Manual ref packing after deletion shows reftable can outperform files backend (129ms vs 223ms)
- Christian Couder's entry-count-based compaction proposal evaluated but deemed impractical due to parsing overhead

Key technical findings:
1. Primary bottleneck remains in `refs_verify_refname_available()` due to:
   - Repeated scans of ref hierarchy during conflict checks
   - Overhead from ambiguous ref warnings (commit 798c35f)
2. Two concrete optimization paths for immediate focus:
   - Batching ref updates to process conflict checks in single merged iteration
   - Suppressing ambiguous ref warnings via new API flag for bulk operations
3. Compaction heuristics discussion concluded:
   - Size-based triggers remain preferred over entry counting
   - Tombstone handling requires alternative solutions beyond compaction tuning

Participant positions:
- Patrick Steinhardt confirms:
  - Will implement batching for `refs_verify_refname_available()`
  - Prefers API flag over global config for warning suppression
  - Rejects entry-count compaction due to performance overhead
- Jeff King's bottleneck analysis remains guiding optimization priorities
- Christian Couder's compaction idea explored but set aside

Open questions:
- Whether files backend would show similar `refs_verify_refname_available()` scaling issues (unverified)
- Exact implementation approach for batching conflict checks
- Final design of warning suppression API flag

The investigation has narrowed to two high-value optimizations (batching and warning suppression) while concluding that compaction heuristic changes aren't viable. The original performance test case (50,000 ref creation in linux.git) remains the benchmark, with attention now focused on implementing the identified solutions to the verification bottleneck while maintaining reftable's correctness guarantees. The discussion has effectively ruled out compaction tuning as a solution path, keeping focus on the ref update workflow improvements.
