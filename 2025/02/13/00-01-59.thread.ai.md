Key technical findings:
1. Primary bottlenecks:
   - Fundamental iterator limitations preventing stateful reseeking
   - Repeated scans of ref hierarchy during conflict checks
   - Overhead from ambiguous ref warnings (commit 798c35f) now unanimously deemed unjustified for automated workflows
2. Iterator-specific issues:
   - Current design frees iterators immediately after use
   - Files backend could restart binary searches while reftable cannot
   - Sorted refnames could enable forward-only optimizations
3. Warning-specific consensus:
   - Checks should occur at ref creation rather than read time
   - Current implementation's performance impact unacceptable in push/API contexts
   - `git update-ref` operations with full OIDs gain no value from warnings
   - Edge case detection can be preserved through alternative timing
