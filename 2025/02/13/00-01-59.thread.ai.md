Performance regression investigation in reftable backend during mass ref creation, with root cause identified and multiple optimization paths forward. Originally reported by brian m. carlson showing 30x slowdown (57.44s vs 5.5s) when creating 50,000 refs compared to files backend. Patrick Steinhardt confirmed the issue, identifying the root cause as tombstone records in reftable preventing auto-compaction while requiring expensive conflict checks during mass ref creation after deletion - creating worst-case 78x slowdown (17.5s vs 223ms in linux.git test).

Key technical findings:
- Manual ref packing after deletion makes reftable outperform files (129ms vs 223ms)
- Current optimization in `git-update-ref` (skipping `repo_get_oid()` for exact object IDs) provides significant speedup (reftable: 16.3s→5.9s, files: 223ms→181ms)
- Jeff King identifies two additional optimization opportunities: (1) batching ref updates to process conflict checks in a single merged iteration rather than per-ref, and (2) suppressing ambiguous refname warnings (from commit 798c35f) either globally via `core.warnAmbiguousRefs` or through a new API flag for bulk operations
- The `repo_get_oid()` optimization reduces gap from 30x to 32x, indicating more work needed

Steinhardt plans to send patches for the `repo_get_oid()` optimization while continuing investigation into other improvements. Peff's analysis suggests the conflict check overhead could be substantially reduced through batching, while the ambiguous ref warning could be selectively disabled for bulk operations. The issue appears to be a fundamental limitation of reftable's tombstone design rather than a straightforward bug, with multiple promising optimization paths now identified. Original test methodology remains valid for benchmarking improvements, with memory usage (~160MB RSS) previously shown similar between backends. Impact remains significant for initial push scenarios in repositories with many refs.
