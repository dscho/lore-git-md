Performance regression investigation in reftable backend during mass ref creation, with optimization focus on `refs_verify_refname_available()` bottleneck, iterator infrastructure limitations, and now ambiguous refname warning overhead. Originally reported by brian m. carlson showing 30x slowdown (57.44s vs files backend 5.5s) when creating 50,000 refs, with root cause identified as tombstone records preventing auto-compaction while requiring expensive conflict checks.

Current status:
- Patrick Steinhardt's `repo_get_oid()` optimization reduced gap from 30x to 32x (reftable: 16.3s→5.9s, files: 223ms→181ms)
- Jeff King's analysis shows `refs_verify_refname_available()` accounts for ~80% of remaining overhead, now specifically identifying ambiguous refname warnings as major contributor
- Manual ref packing after deletion shows reftable can outperform files backend (129ms vs 223ms)
- Iterator infrastructure remains key blocker for batching optimizations
- Two approaches now under consideration for warning overhead:
  1. Temporary global flag disable in `update-ref.c` (quick fix)
  2. Architectural `GET_OID_SKIP_OBJREF` flag with broader command integration

Key technical findings:
1. Primary bottlenecks:
   - Repeated scans of ref hierarchy during conflict checks
   - Overhead from ambiguous ref warnings (commit 798c35f)
   - Fundamental iterator limitations preventing efficient batching
2. Warning-specific issues:
   - Global flag approach risks state management complexity
   - Per-call flag creates complications in `revision.c` for mixed input cases
   - Warning's utility questioned given it mainly catches edge cases
3. Optimization paths:
   - Revamp generic iterator infrastructure to support reseeking (Steinhardt)
   - Either suppress warnings via quick global flag or architectural per-call flag
   - Consider removing warning entirely given performance cost vs benefit

Participant positions:
- Patrick Steinhardt confirms:
  - Will implement generic iterator reseeking capability as prerequisite for batching
  - Prefers API flag over global config for warning suppression
  - Rejects entry-count compaction due to performance overhead
- Jeff King now suggests:
  - Either keeping simpler global flag approach
  - Or removing warning entirely given limited utility
  - Demonstrates comprehensive `GET_OID_SKIP_OBJREF` patch as alternative
- Christian Couder's compaction idea explored but set aside

Open questions:
- Implementation timeline for generic iterator reseeking support
- Final decision on warning handling approach (global flag vs per-call flag vs removal)
- Whether files backend would show similar verification scaling issues
- Impact assessment of warning removal on edge case detection

The investigation has expanded to consider both the foundational iterator changes needed for batching and the immediate question of ambiguous refname overhead. King's analysis suggests the warning may not justify its performance cost, opening a new dimension to the optimization discussion. Steinhardt's iterator work remains the prerequisite for the most significant improvements, but the warning overhead presents a separate optimization opportunity that could yield more immediate gains. The linux.git 50,000-ref benchmark continues to guide prioritization while the discussion acknowledges multiple layers of optimization potential.
