This is a follow-up in the ongoing investigation into Git filter and renormalization issues, now uncovering a new problem with file collisions during cloning.

Josef Wolf reports encountering file collision warnings when cloning a repository on Linux (where the filesystem is case-sensitive), with the same files that previously caused issues during renormalization. The affected files are hash files for a proprietary application that were originally committed to the repository before Josef developed a smudge filter to regenerate them. Despite being added to .gitignore, these files were periodically committed as a fallback, which may explain the collision warnings.

The email raises two key questions: why these collisions occur when cloning (despite being on a case-sensitive system), and why they cause the renormalization process to fail completely even when resolved during rebase. Josef notes he hasn't been able to reproduce these issues in a fresh test repository yet.

This appears to be a new dimension to the ongoing filter/renormalization problems Josef has been investigating, suggesting the original issue may be more complex than initially thought, involving interactions between ignored files, filter behavior, and repository history. The collision warnings on a case-sensitive system are particularly puzzling and may indicate deeper repository corruption or unexpected Git behavior.
