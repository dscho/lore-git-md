This is a bugfix patch in a series enhancing `git fsck`'s packed-refs validation. It specifically addresses a corruption case where embedded NUL characters in refnames could bypass existing validation checks.

The patch adds detection for NUL characters within refnames in packed-refs files, which could otherwise create security and correctness issues by allowing malformed refnames to pass validation. The issue was reported by R. Diez, who found that the current validation would accept refnames with embedded NULs as long as the portion before the first NUL was valid.

The implementation introduces a new `refname_contains_nul()` helper function that scans for embedded NULs using `memchr()`, then uses this in `next_record()` to die with an error message if such corruption is detected. The commit message clearly explains the problem scenario where pointer arithmetic for refname length calculation could miss embedded NULs, and the solution's approach.

This is part of a larger v5 series (position 5/8) that's adding comprehensive validation to packed-refs handling, with previous patches having added header format checking, line termination verification, and other safety measures. The patch maintains the series' focus on security and correctness while adding another specific validation case.
