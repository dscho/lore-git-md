This thread centers on refactoring `show-branch.c` to eliminate its longstanding `MAX_REVS` limitation by moving commit flag storage from direct bit manipulation to a more flexible commit-slab system. The original proposal introduced basic integer slab storage, but Junio Hamano pointed out this doesn't truly solve the scaling problem - proper support would require bit array storage with cross-word manipulation helpers.

Jeff King's follow-up provides a key implementation insight: Git's existing but unused `_with_stride` slab variant could serve as the foundation for this bit array approach, having supported array-per-commit storage since 2013. This moves the discussion from conceptual requirements to practical implementation, though actual code using this capability remains forthcoming. The thread remains focused on the technical challenge of replacing fixed limits with properly scalable storage, with next steps including implementing the bit array helpers and demonstrating the lifted constraints through new tests.
