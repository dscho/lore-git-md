This is part 7/8 of a bugfix series adding comprehensive packed-refs validation to `git fsck`. The patch specifically adds verification that packed-refs files marked with the "sorted" trait in their header are actually sorted by refname.

The key changes are:
1. Extracts the refname comparison logic from `cmp_packed_ref_records()` into a new `cmp_packed_refname()` helper for reuse
2. Modifies `packed_fsck_ref_header()` to detect the "sorted" trait in the packed-refs header
3. Adds a new `packed_fsck_ref_sorted()` function that:
   - Scans the packed-refs file when the "sorted" trait is present
   - Compares each refname with the previous one using `cmp_packed_refname()`
   - Reports errors via new `FSCK_MSG_PACKED_REF_UNSORTED` when out-of-order refs are found
4. Includes extensive test coverage verifying:
   - Proper handling of both sorted and unsorted files
   - Correct error reporting for out-of-order refs
   - No false positives when the "sorted" trait is absent

The implementation avoids memory-intensive approaches by re-parsing the file for the sortedness check rather than storing all refnames. This maintains the series' focus on memory efficiency while adding another layer of validation to catch malformed packed-refs files.

The patch appears well-integrated with the rest of the series, reusing existing infrastructure and following the established pattern of adding focused validation checks with clear error reporting. The test coverage is thorough, including cases with peeled refs and verifying the sorted check is only performed when explicitly requested via the header trait.
