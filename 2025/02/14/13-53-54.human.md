Bugfix discussion for tag fetching regression in protocol v2. This is a follow-up to Taylor Blau's analysis of a regression where tags are no longer fetched when fetching specific commits with depth limits, caused by commit 3f763ddf28 ("fetch: set remote/HEAD if it does not exist"). Bence Ferdinandy, the author of the original commit, confirms this is the same issue that came up in another thread and shares his previous investigation.

Bence notes he had reached a similar conclusion to Taylor's proposed fix (unconditionally adding "refs/tags/" to ref_prefixes when tag following is enabled), but found that simply removing the empty check breaks many things while reordering operations does not. He expresses uncertainty about why this is the case, suggesting there may be subtle interactions in the fetch protocol v2 implementation that aren't fully understood. The thread remains stuck waiting for input from more knowledgeable protocol experts to determine the correct fix that won't introduce new issues while restoring the expected tag fetching behavior.

The discussion highlights the complexity of the fetch protocol v2 implementation, particularly around tag handling and ref_prefixes management, where seemingly simple changes can have unexpected consequences. The regression affects shallow fetches of specific commits where tag decoration is expected but no longer works.
