This is a follow-up in the ongoing thread about CRLF conversion and clean/smudge filters, where Josef Wolf responds to Brian M. Carlson's suggestion to use Git's built-in `eol=crlf` attribute instead of custom filters.

Josef explains that his use case requires more than just line ending conversion - he needs to both enforce CRLF line endings *and* canonicalize XML element ordering in his proprietary application's files. The example shows mixed line endings within XML files (CRLF for tags but LF for content), and mentions the files get randomly reordered on each application startup. This necessitates a clean filter that handles both transformations.

The response clarifies why the simpler `eol=crlf` approach wouldn't suffice for this specific case, as it remains a valid solution for pure line-ending conversion scenarios. The thread continues to explore the architectural limitations of Git's filter system, particularly around history rewriting operations where clean filters are bypassed.
