Bugfix patch adding NUL character detection to packed-refs validation, part of a larger series improving `git fsck`'s reference verification. This is v4 5/8 in the series, which focuses on catching corrupted refnames that contain embedded NUL characters.

The patch addresses a specific corruption case where a refname in the packed-refs file contains NUL bytes before the line terminator. Currently, the code calculates refname length by pointer subtraction and passes it through `check_refname_format()`, but this misses embedded NULs since the check only sees the string up to the first NUL. The solution adds a new `refname_contains_nul()` helper that scans the entire refname buffer for NUL bytes, causing the program to die if any are found.

Key technical details:
- New helper function `refname_contains_nul()` uses `memchr()` to scan for NUL bytes
- Added check in `next_record()` that triggers before `check_refname_format()`
- Error message follows existing pattern for dangerous refnames
- Fixes a case reported by R. Diez where corruption could go undetected
- Maintains the series' focus on thorough packed-refs validation

The patch fits into the larger series by adding another layer of validation to the packed-refs parsing logic, specifically for the refname portion. It complements the header validation and filetype checks from other patches in the series. The implementation is straightforward and well-contained, with clear documentation of the edge case being addressed.
