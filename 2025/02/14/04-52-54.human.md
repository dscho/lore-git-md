Bugfix for packed-refs validation catching embedded NUL characters in refnames. This is part 5/8 of a larger series hardening `git fsck`'s packed-refs validation, though it stands alone as a clear improvement.

The patch addresses a subtle corruption case where a packed-refs file could contain NUL bytes embedded in refnames. Currently, the code calculates refname length by finding the next newline, but if there's a NUL byte before that, `check_refname_format()` would only validate up to the NUL, potentially missing corruption. The solution adds a new `refname_contains_nul()` helper that scans the entire refname for embedded NULs, causing the program to die if found.

The change is well-motivated by a real-world report and adds a clear safety check. The implementation is straightforward - a simple memchr scan of the refname buffer. While this adds a small performance overhead, it's justified by the security implications of potentially malformed refnames. The patch includes good documentation explaining the edge case being fixed.

This appears to be a solid improvement to the packed-refs validation that closes a real hole in the verification logic. It fits well with the broader series' goal of making packed-refs validation more robust.
