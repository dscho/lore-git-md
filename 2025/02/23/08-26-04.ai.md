Performance optimization patch continuing the discussion about memory usage in commit mark clearing. This is a resend of René Scharfe's patch that restructures `clear_commit_marks_many()` to reduce peak memory usage from O(n) to O(1) by clearing parent lists earlier in the traversal. The key change moves the parent list declaration inside the loop and processes it immediately after each commit, rather than accumulating all parents across the entire operation. 

The implementation maintains the same depth-first traversal behavior while reducing the maximum parent list length observed in tests from 12 to 4. The patch touches only commit.c, modifying the control flow of `clear_commit_marks_many()` with a 4-line change that moves and reorders the parent list handling. The technical discussion has already established this is correct and provides modest memory improvements, though not "orders of magnitude" gains in typical cases.

The remaining open question from the thread was whether these measured improvements (reducing parent list length from 12 to 4 in tests) justify inclusion on their own merits, or if stronger evidence of practical impact in real-world merge-heavy repositories is needed. The patch appears ready for maintainer consideration, with no outstanding technical objections about its correctness or implementation approach.
