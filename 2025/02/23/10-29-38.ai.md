Performance issue with rename detection in `git diff` when filtering paths.

The email reports a significant performance degradation (4+ minutes vs <1 second) when using `--find-renames` on a merge commit containing large modified files, even when those files are excluded via path filtering. The key observations are:

1. The slowdown occurs even when there's only one modified file in the commit and no actual renames to detect, suggesting rename detection may be running unnecessarily in cases where it can't possibly find anything.

2. The author questions whether rename detection could be optimized to only run when there are actual additions/deletions in the diff, since pure modifications (without any file additions/removals) make renames extremely unlikely.

The issue appears in the diff machinery when combining path filtering (`:!*/foo/stubs/*`) with rename detection, particularly affecting large files. The email doesn't propose a specific code change but raises two fundamental questions about the current rename detection logic's efficiency and potential optimization opportunities. This could be relevant to the diffcore-rename.c implementation and its interaction with path limiting.
