Performance issue with rename detection in `git diff` when filtering paths.

Devste Devste reports a significant slowdown (4+ minutes vs <1 second) when using `--find-renames` with path filtering that excludes a large modified file. The slowdown occurs even when: (1) the commit contains only modified files (where rename detection should theoretically be irrelevant), and (2) when excluding the large file via pathspec. The same operation with `--no-renames` is much faster.

The email raises two questions about potential optimizations: (1) why rename detection runs at all when there are only modified files (no additions/deletions where renames would be detectable), and (2) whether rename detection could be deferred or skipped when a commit contains only modifications. The case appears to be a real-world performance pain point, though the author notes the scenario without any additions/deletions is extremely rare.

This looks like a legitimate performance optimization opportunity in Git's diff machinery, though the impact would likely be limited to edge cases. The report is well-documented with clear reproduction steps and timing comparisons.
