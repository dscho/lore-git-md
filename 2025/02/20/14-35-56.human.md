Performance issue report about slow initial bisection step.

Uwe Kleine-König reports that the first step of a bisect operation in a large repository (Linux kernel) is surprisingly slow, taking 18 minutes on a reasonably powerful machine and nearly an hour on another system. The bisect range spans over 572,000 revisions. While the user doesn't recall such long delays in past bisections, they're unsure whether this is a regression or just normal behavior for such a large history.

The report includes concrete timing measurements and system specifications, suggesting this might be worth investigating as a potential performance regression in `git bisect`. The slow operation appears to be the initial revision selection and checkout phase, before any actual testing begins. No analysis of the root issue is provided - this is a straightforward performance observation report from a user experiencing unexpectedly long wait times during a routine debugging operation.
