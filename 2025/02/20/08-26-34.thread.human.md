This thread examines limitations in `git clone --shallow-exclude`, initially triggered by a bug in Git 2.45.2 (since fixed in 2.48) where commit hash exclusions incorrectly produced "ambiguous deepen-not" errors. While branch-based exclusions work correctly, a new workflow limitation emerged for GitLab CI's "Merged Result Pipelines" - these create temporary merge topologies that break branch-based exclusion, and commit hash exclusion can't handle unreferenced merge bases.

D. Ben Knoble has proposed a practical workaround for CI environments: rather than struggling with shallow exclusion's limitations, teams could use blobless clones combined with targeted `git rev-list` operations (like `master..topic`) to fetch commit histories more efficiently than full clones. While this fetches more commits than strictly necessary, it avoids the shallow exclusion constraints and still provides significant performance benefits over full repository clones (which take ~13 minutes for large repos like the Linux kernel).

The discussion has evolved from diagnosing bugs to exploring real-world solutions, with the blobless clone approach emerging as a viable alternative while deeper protocol limitations remain unresolved. No maintainer has yet weighed in on whether the underlying exclusion behavior might be enhanced to better support CI workflows, leaving open questions about Git's shallow clone capabilities in complex merge scenarios.
