This thread has clarified the limitations and current behavior of `git clone --shallow-exclude`, particularly for CI workflows. The discussion identified two key issues: a now-fixed bug with commit hash exclusions (resolved in Git 2.48) and inherent implementation constraints that make commit hash exclusions impractical despite protocol support. Maintainers have documented these limitations, with blobless clones (`--filter=blob:none`) emerging as the recommended alternative.

Erik Cervin Edin's recent contribution adds important real-world data from GitHub Actions, showing inconsistent behavior when excluding different branch names (`master` fails while `maint` works). This mirrors earlier GitLab CI reports and suggests platform-specific variations in shallow clone handling. The thread has reached consensus that while the protocol could theoretically support more flexible exclusions, current implementations - both in Git itself and hosting platforms - make shallow clones unreliable for certain CI use cases. The discussion appears to be winding down with blobless clones as the most robust solution, though the GitHub-specific branch name inconsistency may warrant follow-up investigation.
