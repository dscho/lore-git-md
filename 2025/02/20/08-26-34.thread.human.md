This thread began as a bug report about `git clone --shallow-exclude` behavior in Git 2.45.2, where two different failure modes were observed - one with branch names ("no commits selected") and another with commit hashes ("ambiguous deepen-not"). Elijah Newren clarified that the branch name behavior was working as designed (it correctly reports when no history remains), while the commit hash case was a bug that was fixed in Git 2.48.

Now, Philipp Hahn has surfaced a real-world scenario where the current design limitations create problems. In GitLab CI's "Merged Result Pipelines", temporary merges make branch-based exclusion fail because the target branch becomes an ancestor. The natural solution would be to exclude by the merge base commit hash, but this remains unsupported despite the earlier bug fix. The performance impact is substantial - Philipp reports 13-minute full clones when only the most recent commits are needed.

While the original technical issues are resolved, this follow-up highlights an important use case where the current shallow clone capabilities fall short for modern CI workflows. The discussion may prompt consideration of expanding `--shallow-exclude` to better support commit hash exclusion in future Git versions. For now, users facing this limitation in CI environments will need to continue with full clones or find alternative workarounds.
