This thread explores the limitations of `git clone --shallow-exclude` in GitLab CI environments, particularly for "Merged Result Pipelines" scenarios. The discussion began with a bug report about incorrect error messages when excluding by commit hash (fixed in Git 2.48), but has evolved to address deeper workflow challenge.

Philipp Hahn's latest email provides important technical context about why the temporary merge topology in GitLab CI breaks both branch-based and commit-hash exclusion approaches. The temporary merge commit causes `git rev-list` to miss the intended commits, while commit hash exclusion creates unwanted root commits. This confirms the fundamental limitations of the current shallow exclusion mechanism for this use case.

The thread has converged on blobless clones (`--filter=blob:none`) as a promising alternative, though performance characteristics remain to be evaluated. Philipp indicates this approach might work based on positive experiences with similar filters, while acknowledging it would fetch more commits than strictly necessary. The discussion remains practical and solution-oriented, with participants working around protocol limitations rather than expecting immediate fixes.

Key open questions include whether protocol extensions could eventually support this use case better, and what documentation updates might help users navigate these limitations. While no maintainer has yet weighed in on the CI-specific concerns, the thread has produced a viable workaround and clarified the technical constraints.
