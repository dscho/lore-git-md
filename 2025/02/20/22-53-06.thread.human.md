However, he noted this isn't user-friendly currently. He also pointed out that shallow clones, while solving the local storage issue, can be resource-intensive for servers. 

The discussion remains focused on explaining Git's immutable history model and exploring workarounds rather than proposing code changes. Both responses emphasize that true history truncation would break Git's fundamental design, while offering practical alternatives with different tradeoffs for storage and server load.
