This is part 1 of a 3-patch series introducing protocol v2 capability for promisor remote advertisement, building on previous discussion in the thread. The patch adds a new "promisor-remote" capability to protocol v2, allowing servers to suggest promisor remotes to clients and clients to selectively accept them.

The core mechanism involves two new config options:
- `promisor.advertise` (server-side) controls whether to advertise promisor remotes
- `promisor.acceptFromServer` (client-side) controls which advertised remotes to accept

The protocol exchange includes URL-encoded remote names and URLs in a structured format. The implementation handles the capability advertisement, response parsing, and tracking accepted remotes. A comprehensive test script (`t5710`) verifies the behavior under different config combinations.

This appears to be a well-considered addition to the promisor remote infrastructure, with thorough documentation and testing. The patch builds on established patterns from other protocol capabilities while leaving room for future enhancements (such as additional remote metadata or selective object omission). The thread context shows this has undergone several rounds of review addressing security and architectural concerns.
