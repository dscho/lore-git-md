**AI thread summary:**

Bug report and analysis of HTTP authentication regression in Git 2.46+ introduced by commit 610cbc1dfb ("http: allow authenticating proactively"). Peter Georg reported git-http-push fails to properly use netrc file credentials in two scenarios: (1) with http.proactiveAuth unset/"none", initial connections use netrc but subsequent attempts fail (error 22); (2) with proactiveAuth "auto"/"basic", netrc is ignored entirely. The regression affects all versions since 2.46 via HTTPS URLs, with curl logs showing credential flow differences. Reverting 610cbc1dfb restores expected behavior.

Brian m. carlson's response confirms this is unintended but explains the fundamental incompatibility: proactiveAuth is designed for credential helpers that can return non-password credentials (like Bearer tokens), which netrc cannot provide. The documentation specifies netrc is only used when no credentials are provided, and libcurl doesn't expose netrc credential existence, making it impossible to safely use netrc with proactiveAuth's design goal of avoiding 401 responses. While promising further investigation, carlson suggests git-credential-netrc from contrib as a temporary workaround. The technical analysis indicates this involves complex interactions between netrc, credential helpers, and proactiveAuth with no simple fix that preserves all behaviors - any solution must balance backward compatibility with proactiveAuth's intended design. Core issues remain open regarding how to reconcile these authentication mechanisms while maintaining existing netrc workflows.
