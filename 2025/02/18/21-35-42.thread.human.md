This thread examines compatibility issues between Git's packfile handling and NFSv4, specifically around file permissions during server failover recovery. The core problem stems from Git creating temporary packfiles with read-write permissions before setting them read-only (0444), which causes access failures when NFSv4 re-evaluates original permissions during state recovery - a deviation from POSIX semantics where files opened O_RDWR can later be made read-only.

Brian M. Carlson has now responded to Bryan Maloney's points about NFSv4 specifications, arguing that the fundamental issue lies with NFSv4's non-POSIX behavior rather than Git's implementation. Carlson proposes that NFS servers could better handle this case during state recovery, suggesting potential server-side solutions in Linux's kernel NFS server or userspace implementations. The response raises serious concerns about repository corruption risks if Git were to accommodate NFSv4's behavior, particularly around file descriptor management and potential race conditions where EBADF errors could lead to data loss.

The discussion maintains that Git's current behavior is correct by POSIX standards and that the packfile workflow relies on these guarantees for atomic file replacement. While acknowledging the real-world impact on NFSv4 users, participants view this as an NFSv4 standards compliance issue rather than a Git bug, with Carlson strongly arguing that server-side fixes would be preferable to modifying Git's core file handling which could introduce new edge cases and integrity risks.
