This is a response in the ongoing promisor-remote/LOP series discussion about security and protocol design. Christian Couder addresses Patrick Steinhardt's concerns about server-side influence over remote names in the promisor remote advertisement system.

The email clarifies that the current implementation does not actually let servers control remote names - it only allows clients to optionally match advertised remotes against their existing configuration (via `promisor.acceptFromServer`). Couder pushes back against the idea that this takes control away from users, explaining the matching is entirely client-configured.

In response to Steinhardt's suggestion of using opaque promisor IDs instead of names/URLs, Couder acknowledges the idea but suggests it would be better suited for a follow-up series. He argues the current approach using existing name/URL information is sufficient for many use cases and keeps the implementation simple. The email ends with an offer to drop this patch if preferred, showing willingness to compromise on the controversial aspect while maintaining the core functionality.

Key technical details mentioned:
- The security model relies on client-side configuration (`promisor.acceptFromServer`)
- Current matching is based on either names ("KnownName") or names+URLs ("KnownUrl")
- The implementation avoids introducing new concepts (like IDs) to keep complexity low

This continues the thread's security discussion while maintaining focus on the v5 series' goal of establishing basic promisor remote advertisement capabilities. The exchange highlights remaining architectural questions about remote identification that may need resolution before finalizing the design.
