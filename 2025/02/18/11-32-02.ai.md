This is a feature patch introducing protocol v2 capability for promisor remote advertisement, part of the ongoing promisor-remote/LOP series (now at v5). The patch adds server-side configuration (`promisor.advertise`) and client-side controls (`promisor.acceptFromServer`) to negotiate which promisor remotes a client may use directly rather than fetching through the server.

Key technical details:
- Server advertises promisor remotes in format `name=<pr-name>[,url=<pr-url>]` when `promisor.advertise=true`
- Client replies with accepted remote names when `promisor.acceptFromServer=All`
- New functions in promisor-remote.[ch] handle capability negotiation:
  - `promisor_remote_info()` generates server advertisement
  - `promisor_remote_reply()` processes client response
  - `mark_promisor_remotes_as_accepted()` tracks accepted remotes
- Comprehensive test script `t5710-promisor-remote-capability.sh` verifies:
  - Advertisement behavior with different config settings
  - Object availability after clone/fetch operations
  - Interaction with existing promisor remote infrastructure

The implementation builds on prior work in the series, with resolved items including case-sensitive URL comparison and test naming standardization. Open questions remain around remote name validation and MIDX interactions, but this patch solidifies the core protocol capability.
