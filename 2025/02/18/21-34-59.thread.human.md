The thread began with Peter Georg reporting a regression in Git 2.46+ where git-http-push fails to properly use netrc file credentials. The issue stems from changes in proactive authentication (commit 610cbc1dfb) and manifests in two ways: either netrc works initially but fails on retries, or gets ignored entirely depending on http.proactiveAuth settings. Peter provided detailed reproduction steps and confirmed reverting the problematic commit fixes the behavior.

Brian m. carlson has now responded, acknowledging the regression but explaining the deeper technical conflict. The proactiveAuth feature was designed to work with credential helpers that can provide token-based authentication, while netrc can only handle basic auth. The documentation specifies netrc should only be used as a fallback, and libcurl's design makes it impossible to safely combine with proactiveAuth's goal of avoiding 401 responses. While promising to investigate further, Brian suggests using git-credential-netrc as a temporary workaround, noting that any proper fix will need to carefully balance backward compatibility with the proactiveAuth feature's intended behavior.

The discussion reveals this is more than a simple bug - it's a fundamental design tension between different authentication mechanisms that will require careful consideration to resolve without breaking existing workflows.
