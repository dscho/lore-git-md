This is a protocol v2 capability implementation for promisor remotes, part of the ongoing promisor-remote/LOP series (now at v5). The patch adds server-client negotiation mechanics for promisor remote advertisement and acceptance, with Christian Couder responding to Patrick Steinhardt's feedback from the previous version.

Key technical details:
- Server advertises promisor remotes via new `promisor-remote` capability in protocol v2, with config controlled by `promisor.advertise`
- Client accepts advertised remotes via `promisor.acceptFromServer` config with "KnownName" and "KnownUrl" options
- Core functions added in promisor-remote.[ch]:
  - `promisor_remote_info()` generates server advertisement
  - `filter_promisor_remote()` processes client acceptance
  - `mark_promisor_remotes_as_accepted()` tracks accepted remotes
- Server enables `--missing=allow-promisor` for pack-objects when client accepts remotes
- Comprehensive tests in t5710-promisor-remote-capability.sh verify:
  - Advertisement behavior
  - Object availability post-clone/fetch
  - Integration with existing promisor infrastructure

The response addresses several review points:
- Removes redundant `redact_non_printables()` call since URL encoding already handles sanitization
- Clarifies function documentation about server-side usage
- Renames test server from 'server2' to 'lop' for clarity
- Keeps future-looking notes about protocol extensions despite suggestion to remove them
- Maintains current lenient character handling for remote names/URLs while noting stricter validation may be needed if storage is added

The patch represents the core protocol implementation work for the LOP system, with architectural decisions about remote naming and security hardening still open for discussion.
