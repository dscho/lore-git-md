This thread addresses a bugfix series for gitk that corrects Japanese filename encoding issues during merge conflict resolution, with broader implications for non-ASCII filename handling across platforms. The original author Kazuhiro Kato proposed a solution that initially forced UTF-8 encoding, but feedback from Konstantin Khomoutov revealed Windows compatibility concerns where native code pages must be preserved. Junio C Hamano has been guiding the technical direction, suggesting a configuration-based approach (`gitk.pathencoding`) rather than hardcoded UTF-8.

The latest email from Junio provides a detailed technical review of the second patch, which handles merge conflict filename decoding. He identifies a subtle but important flaw in the current implementation - the patch performs byte slicing (removing the "diff --git" prefix) before encoding conversion, which could still break non-ASCII filenames. Junio recommends converting the entire line first, then slicing, to ensure proper character handling. He also suggests broadening the patch's description to clarify that it fixes all non-ASCII filename handling, not just Japanese cases.

The discussion has evolved from a specific Japanese encoding issue to a more general solution for proper non-ASCII filename support in gitk. Key open questions remain about the implementation path - whether to use automatic platform detection or a user-configurable approach, and how broadly to apply the encoding support. The patches will need to be updated based on Junio's feedback before final submission to gitk maintainer Johannes Sixt's repository. This represents one of the first serious attempts to solve Windows-compatible encoding handling in gitk's Tcl/Tk interface.
