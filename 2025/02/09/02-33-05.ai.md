This is a technical discussion about Git's attribute handling during history rewriting operations, specifically addressing the philosophical question of whether filters should apply consistently across all commits or respect historical `.gitattributes` versions.

D. Ben Knoble responds to Josef Wolf's argument that only the newest `.gitattributes` should apply universally during rebase operations. The key technical point is that Git cannot automatically use future `.gitattributes` versions when operating on older commits because (1) there may be multiple valid future versions due to branching history, and (2) there's no efficient way to determine which future version to use. 

The email makes two architectural observations: First, when operations logically work on older history, it's reasonable for Git to respect the repository state at that specific commit. Second, while Git defaults to this behavior, it does provide mechanisms (like explicit attribute source specification) to override it when needed. Knoble suggests this distinction might warrant documentation to clarify Git's design philosophy around historical attribute handling.

This continues the thread's exploration of the tension between workflow convenience (wanting consistent filtering) and Git's fundamental design (respecting historical repository states). The response reinforces that Git's current behavior is architecturally sound, though potentially surprising to users with Josef's specific needs where historical `.gitattributes` are unusable. The suggestion for an "explainer" aligns with earlier proposals to document these behaviors in Git's FAQ or man pages.
