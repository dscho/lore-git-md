Cross-compilation issue in Git's Meson build system where host's shell path (/usr/bin/sh) leaks into target builds, causing git fetch failures when target expects /bin/sh. Originally reported by Peter Seiderer while converting Buildroot package from autoconf to Meson for Git 2.48.1. Problem stems from `find_program('sh')` calls not distinguishing build-time vs target-time executables.

Patrick Steinhardt proposed initial solution using Meson's `native:` parameter to separate paths - adding `native: true` to build-time tool lookups (asciidoc, perl, python) while introducing new `target_*` variables (target_shell, target_perl etc.) for target-side paths. Peter Seiderer raises concerns about this approach based on Meson documentation, noting the `[binaries]` section specifies build-time tools rather than target paths. He identifies a specific bug where `perl.found()` is incorrectly used instead of `target_perl.found()` in template configuration.

Technical details: original issue manifests in meson.build lines 186 (shell detection) and 685 (SHELL_PATH definition), causing ENOENT when target lacks /usr/bin/sh. Current discussion focuses on proper separation of build-host vs target-host program paths for shell (`sh`), Perl, Python and other tools where paths differ between environments. The fix conflicts with Patrick's in-flight meson improvements series, so will be submitted after that lands. Key open question remains about correct Meson cross-compilation approach - whether native: parameter plus target_* separation fully addresses the issue or if alternative configuration method needed. Affects any cross-compiled Meson build where host and target paths differ.
