This thread addresses a cross-compilation issue in Git's build systems where the host system's shell path leaks into target builds, causing failures when the target expects a different path (e.g., `/usr/bin/sh` vs `/bin/sh`). The problem was originally by Peter Seiderer while working on Buildroot's Git package conversion from autoconf to Meson for Git 2.48.1. It affects both Meson and make builds but manifests differently - Meson dynamically detects paths while make historically assumed matching host/target paths.

Patrick Steinhardt proposed an initial Meson solution using `native:` parameters, but Peter raised concerns about Meson documentation compliance. Junio Hamano then expanded the discussion to question whether similar fixes should be made to make-based builds given its historical lack of cross-compilation support. 

In the latest email, Peter Seiderer observes that make-based cross-compilation may have worked fine in practice because users were content with the hardcoded defaults (like SHELL_PATH=/bin/sh), while only native build users tended to customize paths. This suggests the issue may not be as pressing for make builds as it is for Meson builds, supporting Junio's pragmatic inclination to focus the fix on Meson only.

The discussion now balances technical solutions for Meson (Patrick's approach vs alternatives) against the broader question of whether to maintain build system parity by fixing make or accept their differing behaviors. Junio appears to lean toward an asymmetric solution - proper cross-compilation support in Meson while leaving make's limitations unchanged, given make users' historical satisfaction with the status quo. The thread remains open on the final Meson implementation approach and how it will coordinate with Patrick's in-flight Meson improvements series.
