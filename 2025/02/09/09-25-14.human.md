This is a bug report and platform compatibility question about Git's handling of line endings and filters in `.gitattributes`. Josef Wolf reports that despite explicitly setting `text eol=crlf` for certain file patterns in `.gitattributes`, `git ls-files --eol` shows these files with LF line endings on both Linux and Windows/MSYS2 systems. The issue appears when using a custom smudge/clean filter (`filter=etsfile`) for XML files that need canonical ordering, with a complex `.gitattributes` setup that mixes text, binary, and filtered files.

The email provides a clear reproduction case with the full `.gitattributes` configuration and `ls-files` output, showing a discrepancy between the expected CRLF line endings and the actual LF endings being reported. This suggests either a bug in Git's attribute handling when filters are involved, or perhaps an interaction between the `text=auto`, `eol=crlf`, and `filter=` directives that isn't working as intended. The reporter notes they've checked for overriding configurations in info/attributes and gitconfig, ruling out those as causes.

This appears to be a genuine issue that could affect others using similar filter+line-ending combinations, though it's unclear yet whether it's a bug in Git or a misunderstanding of how these features interact. The reporter's careful documentation of their setup and clear demonstration of the unexpected behavior makes this worth investigating for anyone working on Git's attributes or platform-specific line ending handling.
