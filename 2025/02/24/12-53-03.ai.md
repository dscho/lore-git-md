Bugfix follow-up on Windows config file race conditions

Patrick Steinhardt responds to Allen Li's report about Windows-specific race conditions during concurrent config file operations. He clarifies that while his atomic rename work (merged for Git 2.48.0 addressed part of the problem, complete resolution requires two components: POSIX-style rename support and proper file handle sharing flags. The current issue stems from `fopen()` implementations on Windows not using `FILE_SHARE_DELETE`, which prevents atomic renames when files are open.

Key technical details include:
- Current `_wfopen()` implementation lacks `FILE_SHARE_DELETE` support
- Alternative `_wfsopen()` doesn't support the needed delete sharing mode
- Full solution would require reimplementing file opening using `CreateFileW()`

The response confirms this is a known limitation in the current Windows implementation rather than a regression, and suggests the path forward would involve low-level Windows API work to properly support atomic operations during concurrent access. This affects all config file operations on Windows where readers might hold open file handles during write operations.
