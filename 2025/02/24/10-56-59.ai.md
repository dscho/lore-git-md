This is a bugfix discussion regarding `git gc --auto`'s heuristics for reflog cleanup. Patrick Steinhardt explains why the automatic garbage collection failed to clean up Markus Gerstel's excessively large reflog (180MB with 823,921 entries) despite standard configuration. The key insight is that `git gc --auto` only considers the object database state (number of packfiles and loose objects) when deciding whether to run, completely ignoring reflog size. 

The specific edge case occurs in Markus's cronjob sequence where `git reset --hard` writes reflog entries regardless of whether changes were actually fetched, while `git gc --auto` skips reflog pruning if no new objects were created. This creates a scenario where reflogs grow indefinitely without triggering auto-gc, even though the repository otherwise appears clean. The behavior is inherent to the current design rather than a version-specific bug.

The discussion highlights a potential design flaw in `need_to_gc()`'s reflog pruning is coupled with object database maintenance, which can lead to missed cleanup opportunities for repositories with frequent ref updates but infrequent object changes. The thread suggests this might warrant investigation as either a long-standing edge case or an area for potential improvement in gc heuristics.
