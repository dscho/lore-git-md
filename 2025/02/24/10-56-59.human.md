This is a bugfix discussion regarding `git gc --auto`'s heuristics for reflog cleanup. Patrick Steinhardt explains why Markus Gerstel's repository accumulated a massive 180MB reflog over 6 years despite regular `gc --auto` runs. The key insight is that auto-gc only triggers based on object database state (too many packfiles or loose objects), not reflog size. 

In Markus's cronjob sequence, if `git fetch` finds no new changes while `git reset --hard` always writes a reflog entry, the repository can accumulate reflog entries without triggering auto-gc's cleanup. This explains the observed behavior where manual `git gc` worked but auto-gc didn't intervene.

The discussion highlights a clear edge case in the auto-gc logic that could affect any repository with frequent no-op resets. While the immediate workaround (using full `git gc`) solves Markus's case, the thread suggests this may warrant a deeper look at whether reflog size should factor into auto-gc decisions. The analysis is technically sound and points to a plausible design limitation rather than a version-specific bug.
