This is a technical discussion about timestamp type usage in the rerere subsystem, continuing from Junio Hamano's earlier comment about potential overuse of `timestamp_t`.

Jeff King responds to Junio's observation that filesystem timestamps (like those used in rerere records) might be better represented with `time_t` rather than `timestamp_t`. While agreeing with the general principle, Jeff points out complications in this specific case - rerere timestamps need to be compared with user-provided cutoff times that come as `timestamp_t` via `repo_config_get_expiry_in_days()`. 

He argues against creating parallel functions for `time_t` operations, suggesting instead that conversion should happen right after `stat()` calls. Jeff notes this isn't a trivial change though, as proper conversion requires overflow checks and better error handling than currently exists in `gm_time_t()`.

The exchange represents a thoughtful technical discussion about type safety and system interfaces, with both maintainers agreeing the current implementation is correct but potentially suboptimal from a type system design perspective. This appears to be a non-urgent refinement that could be addressed in future cleanup work.
