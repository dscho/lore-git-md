This is a technical clarification in the ongoing discussion about Git's clean/smudge filters and history rewriting. Elijah Newren responds to Josef Wolf's questions about why conflicts still occur during rebase operations despite using the `renormalize` option.

Elijah explains that the `renormalize` option only triggers a virtual check-out/check-in for files that actually need three-way merging during a rebase. Files that can be resolved by simply reusing their existing hash (without examining content) bypass the filtering process entirely. This explains why some files might still show conflicts while others don't.

The key insight is that Git's merge machinery is optimized to avoid unnecessary file content examination when possible, which means filters aren't universally applied during history rewriting operations. Elijah suggests a small documentation clarification to make this behavior more explicit, proposing updated wording for the `renormalize` option description.

This exchange highlights both the technical sophistication of Git's merge machinery and the subtle interactions between different features (filters, merge strategies, and history rewriting). While the thread has largely settled on practical solutions for linear history cases, this clarification helps explain some of the edge cases users might encounter.
