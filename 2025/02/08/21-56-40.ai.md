This is a technical clarification in the ongoing discussion about Git's clean/smudge filters and renormalization behavior during history rewriting operations. Elijah Newren responds to Josef Wolf's questions about why conflicts still occur despite the `renormalize` option being described as performing a "virtual check-out and check-in" of files.

Newren explains that the renormalization only applies to files that actually require three-way merging - files that can be resolved by simple hash comparison bypass the filtering process entirely. This explains why conflicts can appear even with renormalization enabled. He proposes a documentation clarification to make this limitation more explicit, suggesting rewording the man page to specify that the virtual check-out/check-in only occurs for files needing three-way merges.

The email reinforces the current behavior as correct (if perhaps under-documented) and provides architectural context about when Git's merge machinery examines file contents versus when it can work purely with object hashes. This continues the thread's pattern of progressively deeper technical explanations about the interaction between Git's filtering system and merge operations.
