This is a technical follow-up in the ongoing discussion about Git's renormalization behavior with clean/smudge filters during history rewriting operations. Josef Wolf provides concrete feedback on the various rebase approaches suggested earlier in the thread, particularly focusing on their limitations when dealing with XML file normalization and associated hash files.

The email reports that:
1. The suggested `-X renormalize` approach alone didn't work for their use case
2. Combining `-X renormalize` with `git add --renormalize` only works if run before rebase
3. Their specific workflow involves XML files that get randomly reordered by a proprietary application, requiring canonical sorting in the clean filter
4. They encounter persistent conflicts with ignored hash files that are regenerated by the smudge filter
5. There's confusion between the documented "virtual check-out/check-in" behavior and the actual conflict generation during renormalization

Key technical details for future reference:
- The working solution requires both `-X renormalize` and manual `git add --renormalize` steps
- The conflict issues appear related to the interaction between the XML canonicalization and hash file regeneration
- The `--attr-source=$(git rev-parse HEAD)` parameter is used to properly handle historical commits
- There's an open question about why manual `git rm` works but the same operation fails when run via rebase's `-x` hook

The email highlights a gap between the theoretical understanding of renormalization (as explained by Elijah Newren) and the practical behavior when dealing with complex filter scenarios involving both content normalization and auxiliary file management. The discussion appears to be reaching the limits of Git's current renormalization capabilities for this particular workflow.
