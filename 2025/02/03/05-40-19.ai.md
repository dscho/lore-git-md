This is a continuation of the test infrastructure discussion about failure handling in unit tests, specifically addressing the NULL dereference risk when `check()` macros fail. Patrick Steinhardt responds to Jeff King's earlier observation about unsafe test patterns in the reftable test suite.

The key technical points:
- Acknowledges the current test framework's problematic behavior of continuing execution after failed checks
- Notes this is a systemic issue affecting many tests, not just the reftable example
- Contrasts with the planned `clar` framework which aborts on assertion failures
- Raises the open question of whether to:
  - Fix existing tests with manual returns (as Jeff suggested)
  - Wait for the `clar` migration to handle it systematically

The discussion remains unresolved but clarifies the tradeoffs - fixing now would require widespread test changes with potential memory leak risks, while waiting for `clar` pushes the solution to a future transition. The reftable-specific aspects of the original thread (the approved patch series) are not discussed here - this is purely about test framework design patterns that happen to use reftable tests as an example case.
