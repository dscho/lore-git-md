Feature patch in the `git backfill` series, adding configurable batch sizing for blob downloads in partial clones. This is patch 3/5 in v3 iteration of the series, implementing the `--min-batch-size` option discussed in earlier reviews.

The patch introduces a `--min-batch-size=<n>` parameter to control how many missing objects are grouped in each server request, defaulting to 50,000. The commit message provides extensive performance data from real-world repositories (Git, nodejs/node, microsoft/fluentui, Linux) showing how different batch sizes affect pack count, total size, and operation time. Key findings: smaller batches (5K-25K) often yield better compression ratios than larger ones, though with modest time overhead, while very large batches (500K) can significantly increase server processing time without size benefits.

Implementation adds the option to both documentation and command-line parsing, plus a test verifying batch size behavior via trace2 events. The test confirms batches are properly split when below the minimum threshold while still completing the backfill operation. The patch follows the series' established patterns, building on the `backfill_context` struct introduced earlier.

This addresses all technical feedback from previous rounds, with no outstanding implementation questions. The only remaining thread discussion point is whether to keep the experimental flag, which isn't relevant to this specific patch. Performance data strongly justifies the path-based batching approach, particularly for repositories with suboptimal pack layouts.
