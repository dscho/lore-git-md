The thread started with Allen Li reporting a Windows-specific issue where concurrent Git config file reads (like `git rev-parse`) and writes (`git config`) can fail with "Permission denied" errors, unlike on Linux. This persists even after Patrick Steinhardt's atomic rename improvements in Git 2.48.0.

Patrick has now responded, explaining the root cause lies deeper in Windows file handling. While his earlier work helped, complete resolution requires proper support for two Windows-specific features: POSIX-style renames and file handle sharing flags. The current implementation using `_wfopen()` lacks the necessary `FILE_SHARE_DELETE` flag that would allow atomic operations when files are open. A proper fix would need to use the lower-level `CreateFileW()` API instead.

This confirms the issue isn't a regression but a known limitation in how Git handles Windows file operations. The problem affects all config file operations on Windows where readers might have files open during writes. While there's no immediate solution, Patrick's response clarifies the technical path forward would involve reworking Windows file opening at a fundamental level.
