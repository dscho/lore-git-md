This is a technical discussion about Git's content filtering behavior during history operations, specifically focusing on cherry-pick's limitations.

Chris Torek responds to Josef Wolf's frustration about Git sometimes operating on smudged files despite having clean/smudge filters configured. The core issue stems from Git's optimization techniques that assume filters remain constant - an assumption that breaks when filters change between commits. 

Torek explains that Git's famous speed comes partly from these optimizations, which interact poorly with changing filters. The `--renormalize` option exists to bypass these optimizations when needed, but cherry-pick lacks this capability (unlike merge and checkout operations). He suggests this might warrant adding renormalize support to cherry-pick in builtin/revert.c.

The email provides historical perspective on Git's performance tradeoffs while acknowledging the current limitation in cherry-pick's handling of filter changes.
