This is a bug report about platform-specific race conditions in Git's config file handling on Windows. The reporter, Allen Li, describes a reproducible issue where concurrent config reads and writes lead to "Permission denied" errors and fatal "unknown error" messages when reading configuration - behavior that doesn't occur on Linux.

The core problem manifests when one process repeatedly reads config (via commands like `git rev-parse`) while another repeatedly modifies it (via `git config`). On Windows, this leads to readers sometimes encountering corrupted or inaccessible config files. Li notes this affects all commands that read config, not just the test case shown.

Li references Patrick Steinhardt's recent atomic rename work for lockfiles (merged for Git 2.28) but reports the issue still occurs in 2.28 RC builds on Windows. The hypothesis is that while the atomic rename prevents some corruption cases, it may still allow readers to see incomplete config file states during the rename operation.

The report is framed as a platform compatibility issue (working on Linux but failing on Windows) and comes with clear reproduction steps. While the submitter acknowledges this may not be high priority, the bug appears legitimate and could affect any Windows user with concurrent Git operations. The report doesn't propose a solution but seeks help understanding and fixing the Windows-specific behavior.
