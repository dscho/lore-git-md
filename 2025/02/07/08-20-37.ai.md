This is a technical update in the ongoing discussion about improving Git's branch status messages, specifically addressing the feasibility of tracking fetch timestamps for remote branches. Karthik Nayak responds to Patrick Steinhardt's analysis of the performance constraints involved in recording fetch timestamps, particularly with the current non-atomic nature of fetch operations.

Karthik confirms Patrick's assessment that even with reftables, the current fetch implementation would require N separate updates (one per ref) unless using `--atomic`. He reveals he has just posted a patch series implementing "partial transactions" that would allow single-transaction updates even when some ref updates fail, which would significantly optimize this case for reftables. This connects directly to the thread's technical discussion about making timestamp tracking feasible.

The email provides a concrete development that could unblock the timestamp proposal: Karthik's work on partial transactions would enable the atomic-like behavior needed to make timestamp recording efficient. This represents progress on one of the key technical prerequisites identified earlier in the thread, though the series is just posted (v1) and not yet merged.
