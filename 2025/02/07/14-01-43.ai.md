Technical clarification on cherry-pick renormalization behavior in Git's merge machinery.

Elijah Newren provides a detailed technical explanation of why cherry-pick operations don't automatically renormalize files, even when using the `-Xrenormalize` strategy option. The key points:

1. Renormalization in merge operations (including cherry-pick) only applies during 3-way content merges of individual files. When one side of history hasn't modified a file (as in Josef's case of rebasing to root), no renormalization occurs.

2. The limitation is fundamental to Git's merge architecture - proactively renormalizing all files would be prohibitively slow for large repositories. This affects both the legacy recursive and newer ort merge backends.

3. The explanation confirms that this isn't a bug but an intentional performance optimization, though it creates a usability gap for cases like Josef's linear history rewriting.

4. Newren endorses Phillip Wood's earlier suggested workflow (using `git add --renormalize` during rebase) as the proper solution for linear history cases, while noting it won't work for non-linear histories.

The email provides important architectural context about when and why Git's renormalization features work (or don't work), particularly clarifying that:
- The `-Xrenormalize` option exists but has limited applicability
- Merge-based operations only normalize during actual 3-way merges
- Performance constraints prevent more comprehensive normalization
- The behavior is consistent across both merge backends
