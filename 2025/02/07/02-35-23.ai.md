This is a proposal for extending Git's branch configuration options to better handle fast-forward vs. rebase workflows. Alex Henrie responds to D. Ben Knoble's earlier discussion about the interaction between `pull.ff=only` and branch-specific rebase settings by suggesting new configuration options.

The email introduces two potential new configuration knobs:
1. `branch.<name>.ffOnly` - would enforce fast-forward-only behavior for specific branches
2. `branch.autoSetupFfOnly` - would automatically apply ffOnly to newly created branches

This builds on the ongoing thread about configuration precedence between global fast-forward settings and branch-specific rebase preferences. Alex's suggestion aims to provide more granular control by allowing users to specify fast-forward requirements at the branch level rather than globally, which could help resolve the current ambiguity in configuration precedence.

The proposal represents an alternative approach to D. Ben Knoble's earlier suggestion of `pull.merge=ff`, focusing instead on making fast-forward controls more specific rather than splitting the pull behavior into separate merge/rebase contexts. This continues the thread's exploration of how to balance safety (preventing accidental merges) with workflow flexibility (allowing intentional rebases).

Key technical points:
- Would require adding new branch.* configuration options
- Complements existing branch.<name>.rebase functionality
- Particularly targets main branch protection use cases
- Introduces the concept of automatic ffOnly setup for new branches

The suggestion doesn't address all open questions from the thread (like warning systems for rebase contexts), but offers a different direction for solving the core configuration precedence issue. This keeps the discussion active while providing another potential solution path.
