Bugfix targeting `git am --3way` behavior when applying patch series. The email identifies an edge case where intermediate commit hashes aren't properly tracked when earlier patches in a series apply cleanly but later ones require 3-way merge. The issue occurs when:

1. A patch series contains multiple commits modifying the same file
2. An early commit applies cleanly (despite file content differences)
3. A later commit fails to apply cleanly and needs 3-way merge
4. The merge fails because Git didn't record intermediate hashes from the cleanly-applied earlier patch

The author provides a detailed bash script demonstrating the problem through four test scenarios:
- Sanity test showing normal application to identical content
- "Good" case where forced 3-way merge works
- "Bad" case showing the hash tracking failure
- Workaround involving applying patches twice

Key technical details:
- Problem manifests in `git am`'s handling of `--3way` with clean-applying patches
- Missing intermediate hashes cause merge failures for subsequent patches
- Workaround involves reconstructing history by applying to original commit first
- No existing flag forces 3-way merge for clean-applying patches
