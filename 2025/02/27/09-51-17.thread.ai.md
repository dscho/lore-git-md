Thread identity: Bug report about `git am --3way` behavior when applying patch series where early patches apply cleanly but later ones require 3-way merge.

Core problem: When applying a multi-patch series with `git am --3way`, if early patches in the series apply cleanly (despite file content differences) and later patches require 3-way merge, Git fails to track intermediate commit hashes properly. This causes merge failures for subsequent patches that depend on those intermediate states.

Current status: Issue identified and reproduced with test cases, but no fix yet proposed. Workaround involves applying patches twice to reconstruct proper history.

Key technical details:
- Affects `git am`'s `--3way` option when processing series with mixed clean/dirty applies
- Failure occurs when:
  1. Multiple patches modify same file
  2. Early patches apply cleanly (no conflict detected)
  3. Later patches need 3-way merge
  4. Missing intermediate states cause merge failure
- Demonstrated via four test scenarios showing:
  - Normal application to identical content
  - Successful forced 3-way merge
  - Hash tracking failure case
  - Workaround using double application passes

Open questions:
- Should `git am` be modified to track intermediate states even for clean applies?
- Would a new flag forcing 3-way for all patches solve this?
- How to handle backward compatibility if behavior changes?
