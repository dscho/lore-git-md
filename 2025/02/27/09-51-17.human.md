This is a bug report and analysis of an edge case in `git am --3way` behavior. Nikita Leshenko describes a scenario where applying a patch series with multiple commits that modify the same file can fail when:

1. The first commit applies cleanly (despite the file being different)
2. The second commit requires a 3-way merge
3. Git fails because it didn't create intermediate hashes for the first clean-applying patch

The issue occurs because Git skips creating fake ancestors when a patch applies cleanly, which then causes problems for subsequent patches that need those intermediate states. The email includes a detailed bash script that reproduces the issue across several test repositories, demonstrating both the failure occurs and a workaround (applying the patches first to the original commit to reconstruct the intermediate hashes).

The core question is whether there's a way to force 3-way merges for all commits in a series, even when some apply cleanly. This appears to be a genuine edge case in the patch application logic that could affect users applying multi-commit patch series where later patches depend on intermediate states that Git doesn't preserve when earlier patches apply cleanly. The reproduction script is thorough and the analysis seems technically sound.
