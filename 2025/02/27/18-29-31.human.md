This is the second patch in a two-part series fixing object freshening behavior in multi-cruft pack scenarios. The patch addresses a specific edge case where objects in large cruft packs couldn't be freshened during repacks when using `--max-cruft-size`.

The core issue stems from how Git handles objects that exist in cruft packs larger than the size threshold. Currently, these objects are skipped entirely during repacking, making it impossible to update their mtimes (modification times) even when newer versions exist. The patch modifies `want_found_object()` to properly consider mtimes when deciding whether to retain or freshen objects in cruft packs.

Key changes include:
- Adding logic to compare mtimes of objects in existing cruft packs against new versions
- Introducing a new `ignore_packed_keep_in_core_has_cruft` flag to track when cruft packs are being retained
- Extending test coverage in `t7704-repack-cruft.sh` to verify the new behavior

The solution is technically sound but comes with a tradeoff - it may result in keeping additional copies of objects when freshening is needed. The patch includes thorough test cases demonstrating both packed and loose object freshening scenarios.

This completes the series started in patch 1/2, which simplified cruft pack aggregation logic. Together they improve Git's handling of cruft packs with size limits while maintaining the ability to properly freshen objects.
