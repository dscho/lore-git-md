This is a bug report and troubleshooting request regarding Git's renormalization behavior with custom filters. Josef Wolf is experiencing a persistent issue where his CRLF-enforcing clean filter isn't being properly applied during a rebase --renormalize operation, despite all configuration appearing correct.

The email details a thorough setup where:
1. A custom filter is configured to enforce CRLF line endings (unusual on Linux but intentional for this case)
2. The filter is properly registered in .gitattributes and verified via check-attr
3. A rebase --renormalize operation is attempted with a helper script to amend commits
4. Despite this, no commits in the history actually contain the expected CRLF endings

This appears to be a continuation of the ongoing thread about CRLF conversion timing issues, though Josef's specific case shows the renormalization process failing entirely rather than producing inconsistent results. The setup seems correct on the surface, making this a potentially tricky edge case in Git's filter application during history rewriting.

The email doesn't propose a solution but seeks debugging help, suggesting this may reveal either a gap in Git's renormalize implementation or an undocumented interaction between filters and rebase. Given the thread's history, this could lead to deeper investigation of how Git processes filters during complex operations.
