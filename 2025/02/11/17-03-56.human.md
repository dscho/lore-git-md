This is a discussion thread about the recently completed refactoring series for partial reference transactions in Git. Phillip Wood raises some thoughtful concerns about the implementation approach.

Phillip questions whether the series' core premise—using transactions for partial updates—is conceptually sound. He points out that Git's reference updates aren't truly atomic in the first place (other processes can see intermediate states), and suggests that a separate interface might be clearer than adding a `--allow-partial` flag to transactions. His critique focuses on whether the implementation choice could obscure important behavior from future readers of the code.

The discussion comes after a 6-patch series that introduced partial transaction support, primarily to improve reftable backend efficiency while maintaining compatibility. The series had already gone through extensive review and refinement, with Patrick Steinhardt providing detailed feedback that was incorporated. Phillip's comments represent a higher-level architectural concern that wasn't raised during the earlier technical reviews.

This exchange highlights an interesting tension between implementation pragmatism (reusing the transaction infrastructure) and conceptual purity (having a distinct interface for non-atomic operations). Phillip's perspective suggests the change might benefit from more explicit documentation about the transaction model's limitations and the rationale for this approach.
