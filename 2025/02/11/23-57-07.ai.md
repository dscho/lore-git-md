Technical investigation into failed CRLF conversion during renormalize rebase.

Josef Wolf reports continued issues with CRLF line ending conversion during a `--renormalize` rebase operation, building on previous thread discussion where binary file corruption concerns were resolved but CRLF timing issues remain open. The setup involves:
- A clean filter (`ets-utils -c`) that enforces CRLF line endings
- A no-op smudge filter (`ets-utils -s`)
- `.gitattributes` marking files as `-text` with the filter
- Verification that attributes are correctly recognized via `check-attr` and `ls-files`

The key observation is that despite proper attribute configuration and a rebase operation with `-X renormalize` plus a helper script that runs `add --renormalize`, no CRLF conversion occurs in any revision. The test methodology checks both working tree files and historical versions via `git show`, finding no CRLF endings anywhere. This suggests either:
1. The clean filter is not being invoked during the renormalization process despite being properly configured
2. The filter's output is being discarded or overwritten by subsequent processing steps
3. Some interaction between the `-text` attribute and the renormalization process prevents the expected conversion

The case differs from the previously resolved binary file issue as it involves an active transformation (CRLF conversion) that should occur but doesn't, rather than an unwanted transformation that was being prevented. The thread's ongoing focus on CRLF conversion timing anomalies appears directly relevant here.
