This is a protocol design question about bundle-uri advertisement in Git, specifically regarding filtered clones. Brian Celenza is investigating how servers could provide optimized bundles when the client's filtering preferences aren't known until after the bundle request.

The core issue is a protocol sequencing problem: the client must request bundles before specifying its filter preferences in the fetch command, forcing servers to guess at the optimal bundle. This can result in clients receiving more data. The email asks whether this is simply the current protocol limitation or if there are mechanisms (or prior art) for clients to provide early hints about their filtering intentions.

Key technical details:
- Current command sequence: capability exchange → ls-refs → bundle-uri → fetch (with filters)
- Problematic gap: bundle selection happens before filter preferences are available
- Use case: optimized bundle delivery for filtered clones (like blobless clones)

The question touches on protocol design tradeoffs between strict sequencing and flexibility for optimizations. No specific solution is proposed - the email seeks clarification about current behavior and potential precedents for early-intent signaling in Git's protocol. This appears to be early-stage exploration rather than a concrete proposal, with the author checking for existing solutions before considering protocol changes.
