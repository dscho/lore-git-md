This thread explores a protocol design question about how Git servers could optimize bundle-uri advertisements for filtered clones. Brian Celenza identifies a sequencing issue in the current protocol: clients must request bundles before specifying their filter preferences during fetch, forcing servers to guess at the optimal bundle configuration. This can result in clients receiving unnecessary data, particularly for use cases like blobless clones.

The discussion centers on whether this is an inherent protocol limitation or if there are existing mechanisms (or prior art) that allow clients to provide early hints about their filtering intentions before the bundle request phase. The technical challenge lies in the strict command sequence of capability exchange → ls-refs → bundle-uri → fetch, where filter preferences only become available after bundle selection must occur. While no concrete solutions are proposed yet, the thread examines protocol design tradeoffs between maintaining strict sequencing and enabling optimization opportunities. This appears to be early-stage research, with the author seeking to understand current behavior and potential precedents before considering protocol modifications.
