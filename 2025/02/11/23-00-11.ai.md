This is a design discussion response in the ongoing thread about persistent exclusion patterns for `git clean`, now focusing on the conceptual framing of "precious" files versus traditional exclusions.

Junio Hamano responds to Ivan Shapovalov's patch adding `clean.exclude` and `--remove-excluded` with several key points. He questions the semantic appropriateness of treating command-line `-e` patterns as "precious" files, noting this would break backward compatibility with existing expectations about excluded files being expendable. The response highlights a conceptual gap in the current implementation - while the patch focuses only on `git clean`, the "precious" concept would ideally need integration with other commands like `git add` and `git switch` to be fully effective.

The feedback suggests two distinct improvements to the approach: First, separating the sources of patterns (command-line vs config) helps avoid backward compatibility issues. Second, the concept of "precious" files should be more comprehensive, potentially requiring new mechanisms like `.gitprecious` files or extended `.gitignore` syntax that would work across the entire Git ecosystem, not just `git clean`. Junio notes that projects may want to share precious file definitions (like `config.mak`) across contributors, which the current config-based approach can't support since configs don't propagate between repositories.

The response maintains concerns about the `clean.exclude` naming, suggesting it's both too narrow (implying only `clean` integration) and semantically incorrect (since "exclude" traditionally means expendable files). The discussion appears to be shifting toward a more comprehensive "precious files" system that would require significant additional work beyond the current patch series. Junio's comments suggest the current implementation may be too limited in scope to properly address the underlying use case.
