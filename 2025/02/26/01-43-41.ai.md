Bugfix for `git rev-list` commit ordering when dates collide. This patch addresses an issue where `git rev-list --no-walk=sorted` fails to properly order commits when they share identical commit dates, instead preserving their input order. The reporter demonstrates this with a test case showing how the current behavior breaks automated cherry-picking workflows that rely on topological ordering.

The core problem occurs when processing commits through stdin with `--no-walk=sorted` - the command currently only uses commit dates for sorting, with no fallback to topological relationships when dates match. This creates problems for the reporter's real-world use case of creating customer-specific patch builds from a subset of commits, where correct topological ordering is essential for successful automated cherry-picking.

The email includes a reproduction case and system information, but does not propose a specific code solution. The reporter asks whether there might be better sorting approaches and notes the lack of a pure topological sorting option in `git rev-list`'s `--no-walk` mode. The issue appears to be a genuine limitation in the command's sorting logic rather than a misunderstanding of its behavior.

Key technical details for future reference: the problem manifests when using `git rev-list --reverse HEAD | git rev-list --no-walk=sorted --stdin` with commits sharing identical timestamps. The current implementation lacks a secondary sort criterion (like topology) when dates collide. The reporter's workflow depends on stable topological ordering for automated cherry-picking operations.
