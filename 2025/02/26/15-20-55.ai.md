This is a design discussion about naming of filter options in `git cat-file`, part of Patrick Steinhardt's series to add bitmap-accelerated object type filtering. The thread has already seen significant technical development of the core filtering capabilities and bitmap infrastructure.

Toon Claes disagrees with Patrick's choice to use `--objects-filter` instead of the more standard `--filter=` option name used elsewhere in Git (like in `git rev-list`). He argues that:
1. The existing `--filters` option in `git cat-file` doesn't accept arguments, so there's no ambiguity with `--filter=`
2. Many other Git commands already use `OPT_PARSE_LIST_OBJECTS_FILTER` which defines `--filter=`
3. Consistency across commands is preferable

This touches on Git's command-line interface design principles, where Patrick had proposed diverging from the established pattern to avoid potential confusion with the existing `--filters` option. The discussion doesn't introduce new technical concerns about the underlying filtering functionality, but rather focuses on the user-facing API design choice.

The exchange shows the careful consideration given to command-line interface consistency in Git, even for options that are being newly introduced as part of a larger performance optimization effort. This is a relatively minor point in the context of the broader series, but one that could affect user experience and command consistency.
