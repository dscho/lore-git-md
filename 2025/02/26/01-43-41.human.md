This is a bug report about commit ordering in `git rev-list`. Clement Moyroud has found that when using `--no-walk=sorted` with commits that have identical timestamps, the command fails to maintain topological order, which can break automated cherry-picking workflows.

The issue manifests when processing commits through stdin - while `git rev-list HEAD` shows commits in correct topological order, piping that same list through `--no-walk=sorted` scrambles the order when timestamps match. The reporter suggests falling back to parent/child relationships in such cases.

The motivation comes from a real-world use case where a team needs to cherry-pick a subset of commits for customer-specific builds, requiring reliable topological ordering. The current behavior makes this automation unreliable when commits share timestamps. The report includes a minimal reproduction case and full system diagnostics.

This appears to be a legitimate edge case in Git's sorting logic that could affect users relying on `--no-walk=sorted` for automation. The report is well-documented with clear reproduction steps and practical motivation, though it doesn't propose a specific code solution.
