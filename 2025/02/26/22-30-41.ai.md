Bugfix discussion regarding `git rev-list` sorting behavior with identical timestamps. Clement Moyroud responds to D. Ben Knoble's suggestion about using `--topo-order`, explaining why it doesn't solve their specific problem. The key issue is that while `--topo-order` considers commit ancestry, it operates on the full commit graph rather than just the input commits from stdin, resulting in hundreds of thousands of extra commits being included in the output.

This email provides important technical clarification about the limitations of existing flags for the use case of topological sorting of a specific commit subset. The workflow requires processing only the input commits (for customer-specific patch builds) while maintaining their topological order, particularly when timestamps collide. The discussion reveals that neither `--no-walk=sorted` (date-based) nor `--topo-order` (full-graph-based) currently meets this need.

The exchange highlights a gap in Git's commit sorting options - there appears to be no way to perform topological sorting limited to just the input commit set. This affects automated cherry-picking workflows where commit timestamps may collide. The thread remains in the problem analysis phase, with no proposed code changes yet, but the clarification helps narrow the solution space for any future patches.
