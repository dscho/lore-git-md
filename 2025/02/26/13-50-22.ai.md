Bugfix in the packed-refs fsck series (v7 6/9) addressing NUL character validation in refnames.

This patch adds detection for embedded NUL characters in packed refnames, which could previously bypass validation checks. The issue was reported by R. Diez, who found that the existing `check_refname_format()` could miss corruption when a refname contained NUL bytes, as it would only validate up to the first NUL. The patch introduces a new helper function `refname_contains_nul()` that scans the entire refname string for embedded NULs, causing the program to die if any are found.

The implementation adds the check in `next_record()` where refnames are processed, maintaining the series' focus on rigorous packed-refs validation. The commit message provides clear technical details about the vulnerability and solution, including the pointer arithmetic involved in refname parsing and how NULs could corrupt this process. The patch includes appropriate attribution to reporters and mentors, following project conventions.

Key technical points for future reference:
- New function `refname_contains_nul()` scans refname buffers for embedded NULs
- Check inserted in `packed-backend.c::next_record` before format validation
- Maintains consistency with the series' goal of catching packed-refs corruption
- References specific bug report showing real-world impact
- Adds die() message following existing pattern for dangerous refnames
