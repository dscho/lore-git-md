This is a follow-up discussion in the `git add -p` hunk splitting thread, focusing on the first patch that changes split hunk state inheritance. Phillip Wood responds to Junio Hamano's concern about potential workflow regression for power users who intentionally split already-selected hunks to selectively discard parts.

The key technical point is that currently, when a selected hunk is split, all sub-hunks remain selected but the interface still prompts for the first sub-hunk - an inconsistency Phillip finds confusing. His patch would make all sub-hunks undecided by default, requiring explicit selection of each part. While this provides clearer behavior for most cases, Junio notes it could disrupt advanced workflows where users split already-selected hunks to efficiently deselect specific parts.

Phillip acknowledges the tradeoff: the change makes the common case more intuitive (users splitting to select subsets) but could require more steps for the power-user workflow (splitting to deselect parts). He maintains the current behavior is confusing due to the prompt/selection state mismatch, but doesn't dismiss Junio's concern about workflow impact.

The discussion remains unresolved on whether to:
1. Accept the change as an improvement despite some workflow impact
2. Find a middle ground (e.g., different behavior based on context)
3. Preserve legacy behavior for advanced users

The patch modifications are in `add-patch.c` affecting hunk state handling, with corresponding tests in `t/t3701-add-interactive.sh`. This remains an active discussion about balancing intuitive defaults versus established power-user workflows in interactive staging.
