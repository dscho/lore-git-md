This thread explores a subtle but important limitation in `git rev-list`'s commit ordering behavior, particularly for automated workflows. The discussion began when Clement Moyroud reported that `--no-walk=sorted` fails to maintain topological order when commits share identical timestamps, which matters for their cherry-picking pipeline. Initial suggestions focused on existing flags like `--topo-order`, but Phillip Wood's technical insight revealed these don't combine properly with `--no-walk`.

The latest update confirms the core issue: Git currently has no way to both restrict processing to input commits *and* maintain their topological relationships when timestamps collide. While `--topo-order` handles the sorting, it requires walking the full commit graph, and `--no-walk` explicitly disables topological sorting. This leaves a gap for workflows like Clement's that need both constraints.

The discussion has progressed from problem identification through careful evaluation of existing options to recognizing the need for potential API changes. Participants have systematically eliminated workarounds, with Clement demonstrating that no current flag combination solves their use case. The thread now stands at an inflection point - having proven the limitation exists in Git's current design, the next steps would involve proposing and evaluating solutions, likely through a new flag or mode that bridges this functionality gap.
