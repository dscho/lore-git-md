This thread discusses a bug report about `git rev-list --no-walk=sorted` not maintaining topological order when commits share identical timestamps. Clement Moyroud originally reported the issue, which affects automated cherry-picking workflows in customer-specific patch builds where stable topological ordering is required. The problem manifests when piping commit hashes through stdin with commands like `git rev-list --reverse HEAD | git rev-list --no-walk=sorted --stdin`.

D. Ben Knoble suggested exploring the existing `--topo-order` flag as a potential solution. However, Clement has clarified that this doesn't work for their use case because `--topo-order` operates on the full commit graph rather than just the input commits from stdin, causing it to include hundreds of thousands of extra commits in the output. The core issue is that Git currently lacks a way to perform topological sorting limited to just a specified set of input commits, particularly when those commits have identical timestamps.

The discussion has revealed that neither the date-based sorting of `--no-walk=sorted` nor the full-graph topological sorting of `--topo-order` meets the needs of this workflow. While the problem is now clearly understood, no patches have been proposed yet - the thread remains in the analysis phase, working toward identifying an appropriate solution that would maintain topological order for just the input commit set.
