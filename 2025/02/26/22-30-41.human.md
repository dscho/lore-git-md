Bugfix discussion regarding `git rev-list` sorting behavior with identical timestamps. Clement Moyroud responds to D. Ben Knoble's suggestion about using `--topo-order`, explaining why it doesn't solve their specific problem. The issue arises when cherry-picking commits for customer-specific patch builds - while `--topo-order` would provide topological sorting, it includes all ancestors of the input commits (adding 400k+ extra commits in their real-world case), which is undesirable for their workflow.

The core problem remains that `--no-walk=sorted` only uses commit dates for ordering and doesn't fall back to topological sorting when timestamps collide. This creates problems for automated workflows that need stable topological ordering of a specific commit subset. The discussion continues to explore solutions that would maintain the input commit set while providing proper topological ordering when timestamps match.
