This is a discussion thread clarification regarding object ID parsing behavior in `git-update-ref`, part of the larger performance optimization series for the refs subsystem.

Junio Hamano responds to Patrick Steinhardt's patch that proposed skipping ambiguity checks when parsing object IDs in `git-update-ref`. The core issue revolves around whether the command should warn about ambiguous references (where an object ID could also be a branch name) when processing updates. 

Hamano acknowledges the documentation could be clearer about accepting extended SHA-1 expressions (not just full hexadecimal OIDs) in the command's parameters. While sympathetic to the confusion, he notes the original 2005 implementation intended to accept any valid object name format. He suggests updating the manual to better document this behavior rather than changing the parsing logic.

The discussion confirms that squelching the ambiguity warning makes sense for this plumbing command since: (1) the command's documentation frames parameters as object IDs, (2) it's primarily used non-interactively where warnings would be unseen, and (3) users can always disambiguate references explicitly with full ref paths if needed. Hamano emphasizes this change wouldn't affect the actual resolution behavior - full OIDs would still resolve to objects rather than same-named refs.

This exchange clarifies design intent for the `git-update-ref` command's parsing behavior while the larger series focuses on performance optimizations. The discussion helps establish context for documentation updates while validating the proposed warning suppression aligns with the command's plumbing nature.
