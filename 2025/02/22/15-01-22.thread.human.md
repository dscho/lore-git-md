This thread discusses Git's behavior when a user requests `--filter=blob:none` but the server doesn't support filtering. John Giorshev reported that Git currently falls back silently to full blob downloads in this case, which causes performance problems for their repository scanning tool. They proposed making this a hard error instead.

Jeff King (Peff) weighed in on the discussion, noting an inconsistency in Git's current behavior: while it silently falls back when filters are unsupported, it fails hard when filters are explicitly disallowed by the server. He pointed out that the silent fallback might be worse than immediate failure from a performance perspective, since users expecting partial clones could instead get unexpectedly large downloads. 

The discussion remains open on whether to modify this behavior and how to handle backward compatibility. One possibility is making the strict behavior configurable as a transition path, though Jeff noted that Git's existing handling of explicitly disallowed filters might make the change reasonable without additional configuration. The technical details center around protocol negotiation in `fetch-pack.c` and filter capability handling.
