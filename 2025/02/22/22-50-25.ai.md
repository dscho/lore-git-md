Bugfix report regarding `git gc --auto` not triggering for large reflogs. Markus Gerstel reports discovering a repository where automated `git gc --auto` runs in a cronjob failed to clean up an excessively large reflog (180MB with 823,921 entries) over a 6-year period, despite the repository having standard configuration that should enable reflog updates. The issue was observed with Git 2.36.6, and while they couldn't test newer versions, a manual `git gc` successfully cleaned up the reflog.

The report suggests a potential gap in Git's automatic garbage collection heuristics where very large reflogs might not trigger the expected cleanup. The repository had typical settings (`logallrefupdates=true`) that should maintain reflogs, making this an unexpected failure case. The workaround of adding explicit `git gc` to the cronjob resolved the immediate issue, but the underlying behavior warrants investigation for future Git versions.

Key technical details include the specific Git version (2.36.6), the reflog size threshold that wasn't caught (180MB/823k entries), and the standard repository configuration that should have enabled proper reflog maintenance. This appears to be either a long-standing edge case in the gc heuristics or possibly a regression that was fixed in later versions.
