This thread examines a gap in Git's automatic garbage collection where `git gc --auto` fails to clean up excessively large reflogs, despite standard configurations that should maintain them. The issue was reported by Markus Gerstel, who observed a 180MB reflog with over 800k entries persisting for years. Patrick Steinhardt identified the root cause: the current heuristics only evaluate the object database state (like packfiles) when deciding whether to run, completely ignoring reflog size. This creates problems in scenarios like cronjobs that frequently update refs (e.g., via `git reset --hard`) without creating new objects, allowing reflogs to grow unchecked.

Junio C Hamano has now joined the discussion, broadening the scope beyond just reflogs. He points out that this is part of a larger design issue where `git gc --auto`'s triggering conditions don't account for all garbage collection tasks—including reflog pruning, worktree cleanup, and rerere stale data. He highlights technical hurdles, such as the lack of APIs to check reflog staleness without pruning and unclear state tracking in other subsystems. This suggests that fixing the issue will require both design work to document all GC tasks and implementation work to add necessary query APIs.

The conversation is shifting from diagnosing this specific edge case toward considering a more systematic overhaul of GC heuristics. Such a change could impact multiple subsystems (reflog, worktree, rerere) and their integration with the core GC logic. For now, the immediate workaround remains running explicit garbage collection in cronjobs, but the thread indicates this may warrant deeper investigation as either a long-standing oversight or an opportunity for broader heuristic improvements.
