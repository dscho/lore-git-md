Here's a human-readable summary of the thread so far:

The thread began with a report from Markus Gerstel about `git gc --auto` failing to clean up a very large reflog (180MB with over 800,000 entries) over six years, despite standard configuration settings that should maintain reflogs. Initial investigation suggested this might be either a version-specific bug (observed in Git 2.36.6) or a long-standing edge case.

Patrick Steinhardt has now provided the key insight: the issue stems from how `git gc --auto` makes its cleanup decisions. The command only considers the state of the object database (number of packfiles and loose objects) when deciding whether to run, completely ignoring reflog size. This creates a problematic scenario in Markus's case where frequent `git reset --hard` operations in cronjobs write reflog entries even when no new objects are created, causing reflogs to grow indefinitely without triggering auto-gc.

The discussion has revealed this to be a design limitation rather than a version-specific bug, highlighting how reflog pruning is currently coupled with object database maintenance in a way that can miss cleanup opportunities for repositories with frequent ref updates but infrequent object changes. While the immediate workaround is to add explicit gc to cronjobs, the behavior suggests a potential area for improvement in Git's gc heuristics.
