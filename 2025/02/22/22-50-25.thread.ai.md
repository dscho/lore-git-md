Thread discussing `git gc --auto` heuristics for reflog cleanup, initiated by Markus Gerstel's report of a repository where automatic garbage collection failed to clean up an excessively large reflog (180MB with 823,921 entries over 6 years) despite standard configuration (logallrefupdates=true). Patrick Steinhardt explains the root cause: `git gc --auto` only evaluates object database state (packfiles/loose objects) when deciding whether to run, completely ignoring reflog size. The specific failure scenario occurs in cronjobs where `git reset --hard` writes reflog entries regardless of whether changes were fetched, while `git gc --auto` skips reflog pruning if no new objects were created, allowing reflogs to grow indefinitely without triggering cleanup. This reveals a design flaw in `need_to_gc()` where reflog pruning is unnecessarily coupled with object database maintenance, creating missed cleanup opportunities for repositories with frequent ref updates but infrequent object changes. The behavior appears inherent to current design rather than version-specific (observed in 2.36.6 but likely affects all versions). Immediate workaround is explicit gc in cronjobs, but the discussion suggests this may warrant investigation as either a long-standing edge case or an area for heuristic improvement. Key technical details: reflog size threshold missed (180MB/823k entries), standard config that should maintain reflogs, cronjob sequence with `git reset --hard` creating reflog entries without object changes.
