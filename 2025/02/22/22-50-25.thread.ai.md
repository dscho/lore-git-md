Thread discussing `git gc --auto` heuristics for reflog cleanup, initiated by Markus Gerstel's report of a repository where automatic garbage collection failed to clean up an excessively large reflog (180MB with 823,921 entries over 6 years) despite standard configuration (logallrefupdates=true). Patrick Steinhardt identified the root cause: `git gc --auto` only evaluates object database state (packfiles/loose objects) when deciding whether to run, completely ignoring reflog size, creating a design flaw where reflog pruning is unnecessarily coupled with object database maintenance. Junio C Hamano expands the discussion to consider the broader design issue, noting that auto-GC currently only considers object database state while ignoring other GC tasks (reflog, worktree, and rerere cleanup). He highlights technical challenges including the lack of APIs to query stale reflog data without pruning, uncertainty about rerere's internal state tracking, and unknown worktree prune conditions, suggesting any solution would require both design work (documenting all GC tasks) and implementation work (adding new query APIs where needed). The thread has evolved from diagnosing a specific edge case (cronjobs creating reflog entries without object changes) toward considering a more systematic approach to GC heuristics that could affect multiple subsystems (reflog.c, rerere.c, worktree.c) and their interaction with gc.c core logic. The lack of existing measurement APIs for some subsystems may complicate implementation. Key technical details remain the original failure scenario (180MB/823k reflog entries missed by current heuristics) and the cronjob sequence with `git reset --hard` creating reflog entries without object changes.
