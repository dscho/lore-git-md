Thread discussing `git gc --auto` heuristics for reflog cleanup, initiated by Markus Gerstel's report of a repository where automatic garbage collection failed to clean up an excessively large reflog (180MB with 823,921 entries over 6 years) despite standard configuration (logallrefupdates=true). Patrick Steinhardt identified the root cause: `git gc --auto` only evaluates object database state (packfiles/loose objects) when deciding whether to run, completely ignoring reflog size, creating a design flaw where reflog pruning is unnecessarily coupled with object database maintenance. Junio C Hamano expanded the discussion to consider broader design issues, noting auto-GC currently only considers object database state while ignoring other GC tasks (reflog, worktree, rerere cleanup), highlighting technical challenges including lack of APIs to query stale reflog data without pruning.

Patrick Steinhardt now proposes a significant architectural shift: refactoring GC heuristics by moving responsibility from `git gc --auto` to `git maintenance`, leveraging its existing task-based architecture. The proposal suggests adding a dedicated reflog expiration task to `git maintenance` to replace `git gc`'s all-in-one approach, acknowledging technical challenges around querying stale data across subsystems (reflog, rerere, worktree). Steinhardt suggests checking just the HEAD reflog as a potential optimization heuristic while recognizing this wouldn't be as thorough as a full scan. This represents a pivot from earlier focus on fixing `git gc --auto`'s heuristics toward a more modular approach that would affect multiple components: `git maintenance` would gain new capabilities while `git gc` might be deprecated for auto-GC use cases, enabling more configurable maintenance operations like geometric repacking that are difficult under the current model.

Key technical details remain the original failure scenario (180MB/823k reflog entries missed by current heuristics) and the cronjob sequence with `git reset --hard` creating reflog entries without object changes. The discussion has evolved from diagnosing a specific edge case to considering two distinct architectural solutions: either expanding `git gc --auto's` heuristics (as initially discussed by Junio) or restructuring maintenance responsibilities (as now proposed by Steinhardt). Open questions include which subsystems would need new query APIs, whether HEAD-reflog checking would provide sufficient coverage, and how this change would interact with existing `git maintenance` tasks and configurations.
