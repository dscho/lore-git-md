Git thread summary (AI mode):

Performance optimization for bundle-uri reference negotiation during fetches, originally proposed by Scott Chacon. Current implementation copies only `refs/heads/` references from bundles to `refs/bundles/`, while Chacon's change widens refspec to `refs/` for improved fetch negotiation, demonstrating dramatic performance improvements (32% to 1% object downloads in GitLab OSS repo).

Key technical developments:
- Junio Hamano identified critical issues: (1) reference mapping change (`refs/heads/foo`→`refs/bundles/foo` vs `refs/heads/foo`→`refs/bundles/heads/foo`) risks breaking existing users; (2) multiple bundles could overwrite references, leaving objects unanchored for GC; (3) misleading `branch_name` variable after change.
- Derrick Stolee (original bundle-uri designer) confirmed this exposes unconsidered edge cases in tag handling, suggesting tags should be peeled to commits and represented as fake branches to maintain fetch advertisement behavior while preserving performance benefits.
- Scott Chacon responded with alternative proposals: (1) `--bundle-for-uri` option for `git bundle` to handle reference sanitization; (2) temporary use of `refs/bundle/tags/` during fetch negotiation followed by cleanup. Updated tests now check `refs/bundle/heads/` rather than direct `refs/bundle/` access.

Current status:
- Performance benefits remain clear but implementation must address:
  1. Consistent reference naming across bundles (heads vs direct mapping)
  2. Prevention of reference overwrites between bundles
  3. Backward compatibility concerns
  4. Tag handling strategy (peeling vs temporary tags vs bundle creation changes)
- Chacon's response shifts focus toward handling complexity in fetch negotiation rather than bundle creation.

Open questions:
- Should solution modify bundle creation (`--bundle-for-uri`) or fetch negotiation (temporary tag handling)?
- What constitutes "usable" tag references in `refs/bundle/tags/` context?
- Will the simpler fetch-side solutions maintain performance while properly handling edge cases?
- How to validate solution across multiple bundle scenarios (interaction effects)?

Participant positions:
