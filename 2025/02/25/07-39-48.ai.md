Performance optimization series for refs subsystem (v2 patch 12/16) - Technical clarification on iterator naming.

Patrick Steinhardt responds to shejialuo's question about naming consistency between two iterator seek functions in the reftable backend implementation. The discussion clarifies the architectural distinction between high-level and low-level iterator operations in the refs subsystem.

The email explains that `reftable_ref_iterator_seek()` operates on Git's generic `struct ref_iterator` interface while `reftable_iterator_seek_ref()` works with the lower-level reftable library's iterator. Steinhardt defends the current naming scheme as appropriately reflecting their different abstraction levels, with prefixes indicating which structure they operate on. This is part of the larger refs iterator optimization series where such implementation details affect performance characteristics.

Key technical points include the clear separation between Git's ref iterator abstraction layer versus the underlying reftable library's implementation, and how seek operations are implemented at both levels. The response indicates this naming distinction is intentional and won't be changed in this series, though the question itself suggests reviewers are paying attention to API consistency across the refs subsystem changes.
