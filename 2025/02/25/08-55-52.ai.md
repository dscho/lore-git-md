Performance optimization patch (6/16) in the refs subsystem series, implementing batched refname availability checks for the files backend. This follows the reftable backend changes in patch 5/16 and builds on the new `refs_verify_refnames_available()` API introduced in patch 4/16.

The patch modifies `refs/files-backend.c` to collect refnames needing availability checks during transaction preparation, then verifies them in a single operation before locking packed-refs. Key changes include:
- Adding a `refnames_to_check` parameter to `lock_raw_ref()` and `lock_ref_for_update()`
- Deferring packed-refs conflict checks until after all updates are processed
- Maintaining the existing locking sequence despite its race condition limitations
- Adding proper cleanup for the new string list

The implementation carefully considers five different contexts where refname checks occur, focusing optimization on the two high-impact cases (normal ref updates and repository initialization). The patch acknowledges but accepts a race condition where packed-refs could change between verification and locking, preserving existing semantics that users may rely on.

This continues the series' pattern of backend-specific optimizations following API changes, with the files backend showing more complexity than reftable due to its multiple check contexts. The changes touch only the files backend implementation while maintaining interface consistency across backends. Performance impact measurements for this specific optimization aren't provided, but the series previously reported 1.23-1.27x speedups for files backend operations.
