This is a discussion about Git's behavior when `--filter=blob:none` is requested but the server doesn't support filtering. Jeff King (peff@peff.net) responds to John Giorshev's proposal to make this a hard error rather than silently falling back to full downloads.

Jeff considers both sides of the argument - maintaining backward compatibility versus failing fast when the optimization can't be honored. He notes that Git already fails hard when a server explicitly disallows a specific filter (like `blob:none` or `sparse:oid`), suggesting the current silent fallback behavior might be inconsistent. The discussion touches on protocol negotiation in `fetch-pack.c` and filter capability handling.

Key observations include:
1. The inconsistency between how Git handles unsupported filters (silent fallback) versus explicitly disallowed filters (hard error)
2. The potential performance impact of silent fallback being worse than immediate failure
3. The possibility of making this configurable as a transition path

Jeff leaves the question open-ended, noting that while config options could provide backward compatibility, the existing behavior for explicitly disallowed filters suggests the change might be reasonable without configuration. The discussion remains active on whether to modify the behavior and how to handle backward compatibility concerns.
