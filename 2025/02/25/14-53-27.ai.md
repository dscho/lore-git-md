This is a bugfix patch in the signed-commits fast-export/import series. Phillip Wood identifies a memory leak issue in the v5 patch series that adds signed commit support. The problem stems from a change that converted a static buffer to dynamically allocated memory in `find_commit_multiline_header()` but didn't update callers to free the returned string. The leak occurs in `handle_commit()` where the signature string is used but not freed.

The patch series being discussed (v5) had already received extensive review and was considered production-ready, with this being a late-discovered issue. The memory leak specifically affects the signed commit handling path when signatures are present. Phillip notes the inconsistency between the function's documentation (which still claims the returned string doesn't need freeing) and its actual behavior after the changes.

Key technical details:
- The leak occurs in `builtin/fast-export.c`'s handling of GPG signatures
- The problematic function is `find_commit_multiline_header()` which now returns allocated memory via `strbuf_detach()`
- Callers in `handle_commit()` and `handle_tag()` need to free the signature strings
- The test suite (`t/t9350-fast-export.sh`) exercises these code paths but doesn't detect the leak

This appears to be the only outstanding issue in an otherwise well-reviewed series that implements signed commit support for fast-export/import with multiple handling modes (abort/verbatim/strip). The thread context shows this is part of a larger effort that has already addressed buffer safety issues and received approval from key maintainers.
