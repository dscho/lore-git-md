This thread investigates unexpected pack file regeneration during Git's automatic garbage collection. Pierre Ossman initially reported that Git appears to unnecessarily recreate pack files in large repositories, contrary to documentation suggesting existing packs should be preserved until `gc.autoPackLimit` is reached. Han Young suggested this might relate to partial clone behavior, where `git-repack` currently always repacks promisor packs even when marked as keep packs.

Pierre has now confirmed that while partial clones do exhibit this behavior, he's also seeing similar issues in regular repositories like TigerVNC, where week-old 21MB packs are being regenerated unnecessarily. This suggests the problem may have multiple causes - both the known promisor pack handling in partial clones and potentially other mechanisms in standard repositories.

The discussion now needs input from packfile experts to help interpret these observations. Key questions remain: why are small, recent packs being regenerated in non-partial-clone scenarios, and how does this interact with the documented gc thresholds? Pierre is seeking guidance on diagnostic steps to help identify the root causes, as the issue appears more complex than initially thought, spanning both specialized and general repository configurations.
