This is a follow-up discussion on a bugfix patch for gitk's handling of non-ASCII filenames during merge conflicts. Junio C Hamano provides technical feedback on Kazuhiro Kato's proposed solution, which aims to fix garbled Japanese filenames by properly decoding the raw bytes from git output.

Junio points out that while the patch's core approach (using Tcl's `encoding convertfrom`) is correct for character conversion, the implementation may have a subtle issue with byte/character positioning. He suggests it would be safer to first decode the entire line before extracting the filename portion, since the current approach of taking bytes 10-end could potentially split multi-byte characters.

The discussion also touches on making the patch's scope clearer - while it was motivated by Japanese filenames, the fix actually applies to all non-ASCII cases. Junio recommends updating the patch title to reflect this broader applicability. This continues the thread's theme of balancing platform-specific encoding concerns with general solutions, though the technical focus here is narrower than the earlier platform-compatibility discussions.
