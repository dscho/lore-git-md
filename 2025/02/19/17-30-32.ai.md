This is a technical discussion about the UTF-8 encoding fix for gitk, specifically addressing concerns about Windows compatibility.

Konstantin Khomoutov raises important concerns about the first patch in Kazuhiro Kato's series, which adds `encoding system utf-8` to gitk's Tcl/Tk script. The critique focuses on how this change might behave differently on Windows systems compared to Linux/macOS. Khomoutov demonstrates through a Tcl shell example that forcibly setting UTF-8 as the system encoding could break filename handling on Windows, where the system encoding is typically a Windows code page like CP1251 for Cyrillic. The example shows that changing the system encoding affects Tcl's ability to match filenames via glob patterns.

The key technical concern is that while the patch works for UTF-8-based systems (Linux/macOS), it may cause problems on Windows by incorrectly assuming UTF-8 encoding for filenames that are actually in the system's native code page. Khomoutov suggests this could lead to both matching failures (files not being found) and display corruption (incorrect character rendering) when gitk tries to interpret Windows-encoded filenames as UTF-8.

This email introduces a new platform-specific consideration to the thread that wasn't previously discussed, potentially requiring a more nuanced solution that handles different encoding scenarios across operating systems. The critique doesn't reject the need for the fix but questions the implementation approach's portability.
