Performance optimization patch for the files backend's refname availability checks, part of a larger series (v2, 6/16) improving ref operations performance across Git's ref backends. This patch extends the batching approach introduced in patch 4/16 to the files backend, following the reftable backend optimization in patch 5/16.

The patch focuses on two key contexts where batched checks can be applied in the files backend: during reference locking (when checking for packed ref conflicts) and repository initialization. It introduces a `refnames_to_check` string_list to collect references needing verification, then performs a single batched check via `refs_verify_refnames_available()`. The implementation maintains existing behavior while deferring checks to reduce redundant operations.

Notable tradeoffs acknowledged: the current design accepts a potential race condition where packed-refs could change between the batched check and actual reference update, as locking packed-refs earlier would change user-visible semantics. The patch explicitly documents this limitation while preserving the existing locking sequence.

Technical changes include modifications to `lock_raw_ref()` and `lock_ref_for_update()` to accept the new string_list parameter, plus the addition of batch verification logic in `files_transaction_prepare()`. The patch touches 42 lines in refs/files-backend.c, with careful preservation of all existing error paths and cleanup routines.

This sets up for further optimizations in subsequent patches while maintaining backward compatibility. The series' performance improvements (1.58x-7.56x speedups in later patches) will build on this infrastructure.
