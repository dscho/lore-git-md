This is a technical follow-up in a thread about Git's content filtering during history operations, specifically addressing the limitations of renormalization approaches.

Elijah Newren, the maintainer of `git filter-repo`, chimes in to explain why the previously suggested `git add --renormalize` approach has fundamental limitations. He notes that this method requires a full checkout and index, which conflicts with `filter-repo`'s design to operate without these (including in bare repositories). Newren suggests that what's really needed is a way to query how Git would renormalize content without actually performing a checkout, though he acknowledges this would require access to `.gitattributes` information.

The email references an existing GitHub issue (#375) about this functionality in `filter-repo`, where a workaround was proposed. Newren seems open to the idea of adding proper support but indicates it would require deeper Git plumbing capabilities. This response reinforces Brian M. Carlson's earlier recommendation that `filter-repo` is the most robust solution for complex filtering cases, while also explaining why the current integration isn't seamless.

The discussion continues to highlight the gap between Git's content filtering capabilities and the needs of users performing history rewrites, with no immediate solution beyond the existing workarounds.
