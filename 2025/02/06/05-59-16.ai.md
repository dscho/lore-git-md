Bugfix patch adding NUL character detection to packed-refs parsing. This is part 5/8 of a series addressing packed-refs validation issues, specifically focusing on catching embedded NUL characters in refnames that could bypass existing format checks.

The patch introduces a new helper function `refname_contains_nul()` that scans for embedded NUL bytes in refnames parsed from packed-refs files. Currently, the packed-backend calculates refname length by pointer subtraction between the start of the refname and the next newline, which could miss corruption if valid refname characters appear before an embedded NUL. The new check ensures such cases are caught by explicitly scanning the entire refname buffer for NUL bytes before proceeding with format validation.

Key technical details:
- New `refname_contains_nul()` function uses `memchr()` to scan for NUL bytes
- Added check in `next_record()` that dies if embedded NULs are found
- Maintains same error handling pattern as existing refname validation
- Addresses specific corruption vector reported by R. Diez
- Part of broader packed-refs validation effort mentored by Patrick Steinhardt and Karthik Nayak

The change is narrowly focused on the NUL detection case while fitting into the larger validation architecture being built in this series. The implementation follows the pattern established in earlier patches for handling malformed packed-refs entries.
