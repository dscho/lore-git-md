Bugfix for packed-refs validation catching embedded NUL characters in refnames. This is part of a larger series (v3 5/8) improving packed-refs file integrity checks, building on feedback from Patrick Steinhardt and Junio Hamano.

The patch addresses a specific corruption case where NUL bytes embedded in a refname could bypass validation. Currently, Git calculates refname length by pointer subtraction between the start and newline positions, then validates the portion before the first NUL. This means a refname like "good\0bad" would validate as "good" while silently truncating the rest.

The solution introduces a new `refname_contains_nul()` helper that scans the entire refname for embedded NULs using `memchr()`. When found, Git now dies with an error rather than silently accepting the truncated refname. The change plugs a security hole where malformed refnames could potentially bypass validation checks.

This is a focused, well-explained fix with clear motivation from a reported issue. The implementation is straightforward and maintains the existing error handling pattern. As part of the larger validation effort, it complements other checks being added to the packed-refs backend.
