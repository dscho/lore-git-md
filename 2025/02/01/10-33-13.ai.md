Test infrastructure discussion about unit test framework behavior.

This email from Phillip Wood responds to Jeff King's observation about undefined behavior in the reftable unit tests when `reftable_new_stack()` fails. The core issue is that the test framework's `check()` macro doesn't terminate execution on failure, which can lead to NULL pointer dereferences when tests continue running after a failed allocation.

Phillip explains the current design rationale - allowing tests to accumulate multiple failures and provide additional context via `test_msg()` - but acknowledges the safety issue. He notes the correct pattern would be for tests to manually return after failed checks. The discussion touches on the ongoing transition to the `clar' test framework which does terminate on failures (albeit potentially leaking memory), raising the question of whether to fix existing tests or wait for the framework transition.

Key technical points:
- Current `check()` behavior: continues execution after failure
- Safe usage pattern requires manual `return` after failed checks
- `clar` framework changes this behavior by exiting on failure
- Memory leaks on test failure are considered lower priority than test crashes

This represents a test infrastructure design discussion separate from the already-approved reftable series, with implications for how future unit tests should be written and whether existing tests need updating during the framework transition.
