This is a technical discussion about hash algorithm type representation in the ongoing SHA-1/SHA-256 interoperability work, specifically addressing patch 3/14 in the series introducing Rust code to Git.

Ezekiel Newren responds to Junio C Hamano's concerns about changing from `int` to `uint32_t` for the hash algorithm type. While Junio suggested a typedef approach (`hash_algo_type`) as a semantic compromise, Newren strongly advocates for using `uint32_t` directly when dealing with FFI boundaries between C and Rust. He explains that Rust enums can't safely cross the FFI boundary due to potential ABI instability and undefined behavior risks, even with `#[repr(C)]` annotations.

The exchange highlights an important design tension in this Rust integration work: maintaining FFI safety while preserving code clarity. Newren frames the type change not as arbitrary but as necessary technical debt resolution for cross-language compatibility. This patch remains a focal point in the series, with the discussion now centered on balancing type safety against code documentation value.
