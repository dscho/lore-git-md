This is a technical review of patch 12/14 in the SHA-1/SHA-256 interoperability series, focusing on the proposed binary loose object map format. Patrick Steinhardt raises several substantive design questions about the format specification and naming.

Key points raised:
1. Questions whether "loose object map" is the right name since it will store non-loose objects like shallows and submodules. Suggests reconsidering the name before finalizing the new format.
2. Asks if the legacy loose-object-idx format can be dropped entirely since it appears nonfunctional.
3. Requests clarification on which hash algorithm is used for the .map filename checksum (assumes main hash but wants it documented).
4. Questions why pack-objects rather than repack would handle the map file maintenance.
5. Detailed technical questions about the format specification:
   - How key/value pairs are identified and counted
   - NUL byte alignment rules
   - Object name disambiguation approach
   - Why subsequent format tables are sorted by first format
6. Provides an alternative design proposal using separate lookup tables per hash format with offsets to a main table, discussing both static and streaming variants.

The review doesn't challenge the fundamental need for the feature but digs deep into implementation choices, suggesting the current design may have some non-obvious tradeoffs. The alternative proposal is framed as a discussion starter rather than a demand for changes. This continues the pattern of thorough technical review seen in earlier patches of this series.

Open questions center on format design tradeoffs, with no new concerns raised about the broader Rust integration or build system issues discussed in earlier patches. The review maintains the thread's technical depth while focusing narrowly on this patch's object map implementation.
