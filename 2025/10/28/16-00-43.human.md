This is a design discussion about worktree support in `git refs migrate`, following up on Patrick Steinhardt's review of the patch series.

Junio Hamano raises two key questions about the worktree migration behavior. First, he questions whether the current "all-or-nothing" approach (where all worktrees must use the same ref backend) might be too restrictive, suggesting we could theoretically allow mixed backends (reftable for main repo, files for worktrees). Second, he proposes making the command more user-friendly by automatically switching to the main worktree when needed, rather than failing with an error.

The discussion also touches on documentation wording - both agree the "known limitations" section should be updated, though they differ slightly on phrasing. Junio notes that any "must do X" requirement still constitutes a limitation, even if the original worktree restriction has been lifted.

This email advances the architectural discussion by probing edge cases and usability considerations beyond the initial implementation. The thread remains focused on refining the worktree migration design before proceeding with the patch series restructuring suggested in Patrick's review.
