This is a technical refinement in the SHA-1/SHA-256 interoperability series, focusing on FFI (Foreign Function Interface) design between Rust and C components. The patch adds a function to look up hash algorithm structures from Rust by converting algorithm numbers to pointers, but Junio C Hamano raises concerns about the naming and type safety of the interface.

Key technical points:
- Adds `hash_algo_ptr_by_offset()` in C to get a `git_hash_algo` pointer from an algorithm number
- Exposes this via FFI to Rust through `HashAlgorithm::hash_algo_ptr()`
- Uses `*const c_void` rather than a proper Rust type for the C struct pointer
- Junio questions:
  - The "by_offset" naming as implementation-detail leakage
  - Inconsistent terminology between algorithm "number" vs "instance"
  - Why `git_hash_algo` isn't properly typed in Rust's FFI like `ObjectID` was

The discussion reveals ongoing tension in the FFI design between:
1. Direct mirroring of C implementation details (array offsets)
2. Creating clean Rust abstractions that hide C internals
3. Maintaining type safety across the boundary

This patch sits at a key junction in the series where these design philosophies collide, with Junio's feedback suggesting the Rust-side API should better abstract the C implementation details. The void pointer approach may indicate either:
- Temporary scaffolding to be replaced later
- Or a deliberate choice to keep the C struct opaque in Rust

The thread context shows this is part of broader discussions about FFI safety and abstraction boundaries in the Rust/C interop work.
