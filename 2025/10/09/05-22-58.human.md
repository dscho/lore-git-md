This is a follow-up discussion in the merged refactoring series about tag verification behavior. Patrick Steinhardt responds to Jialuo's question about whether corrupted tag objects should trigger fatal errors rather than being silently skipped during ref optimization.

The core debate centers on how to handle tag objects where the claimed type doesn't match the actual object type. While `git fsck` already detects and reports these corruptions, the question is whether operations like ref optimization should fail hard (die) when encountering them, or continue with a warning. Patrick argues that failing would prevent legitimate optimization of other references when just one tag is corrupt, and suggests warnings might be a better middle ground.

This touches on Git's broader philosophy about how strictly to enforce object integrity during normal operations versus specialized verification tools. The discussion remains open, with Patrick inviting more opinions on whether to add non-fatal warnings for these cases. The exchange shows careful consideration of both repository integrity and practical usability tradeoffs.
