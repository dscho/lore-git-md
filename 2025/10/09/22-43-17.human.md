This is a response in the ongoing security discussion about preventing arbitrary code execution in untrusted repositories. Michael Lohmann synthesizes the current state and various proposals, clarifying that:

1. The token approach is essentially an automated way to populate `safe.directory` for user-created repos
2. Environment variables/flags (`--assume-unsafe`, `GIT_ASSUME_UNSAFE`) offer temporary overrides
3. There's consensus that Git should still function (with warnings) in unsafe mode rather than failing
4. The most contentious part remains dropping the default trust of user-owned repos

Lohmann agrees with Jeff King that defining unsafe behavior (skipping repo config, disabling hooks) should precede safety marking mechanisms. He notes path-based approaches have edge cases (like moved repos), but doesn't strongly advocate for tokens over alternatives. The email helps untangle the discussion's components while acknowledging the core architectural decision (token vs config allowlist) remains unresolved. The tone is constructive, focusing on clarifying dependencies between proposals rather than pushing a specific solution.
