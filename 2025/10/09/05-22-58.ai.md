This is a post-merge discussion about tag verification philosophy in the refs subsystem, specifically addressing how to handle corrupted tag objects during peeling operations. The thread follows Patrick Steinhardt's recently merged 14-patch series that modernized ref iteration and tag peeling behavior.

Jialuo raised a design question about whether Git should fail loudly (die) rather than silently skip storing peeled OIDs when encountering invalid tags. Patrick responds by distinguishing between different contexts: while `git fsck` should report corruption, reference optimization operations should continue working even with broken tags to avoid making repositories unusable. He suggests adding warnings as a middle ground and invites broader discussion on the approach.

Key technical points:
- The merged series already enforces type verification during peeling (patch 12/14)
- Current behavior skips storing peeled OIDs for invalid tags rather than failing
- `git fsck` already detects and reports tag-object type mismatches
- Reference optimization operations (like `git pack-refs`) would become unusable if they died on corruption

The discussion touches on broader themes about Git's philosophy for handling repository corruption - whether to fail-safe (continue with warnings) or fail-secure (die on detection). Patrick leans toward the former for reference operations while acknowledging the need for clearer user feedback. This connects to ongoing discussions about object database integrity checks and `git fsck` behavior.
