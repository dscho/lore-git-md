This is a discussion thread response debating the merits of Rust vs C in the context of Git's ongoing Rust integration effort. Eric Wong responds to Ezekiel Newren's comparison of C and Rust features, offering counterpoints about C's capabilities and expressing skepticism about Rust's tradeoffs.

Key technical points raised:
- Argues C can approximate some Rust safety features through extensions like `__cleanup__`, `-Wconversion`, and `__must_check`
- Questions Rust's async/await model due to memory overhead concerns compared to event loops
- Notes C23's `<stdckdint.h>` provides checked arithmetic similar to Rust's
- Prefers C's simpler build model over Rust's cargo ecosystem due to concerns about centralization
- Suggests evolutionary C improvements would be more inclusive than Rust adoption

The email reveals ongoing philosophical divides:
- Language complexity tradeoffs (Wong prefers clear high/low level separation)
- Build system preferences (distro packages vs language-specific managers)
- Async programming models (event loops vs coroutines)
- Community accessibility concerns about Rust's compile-time requirements

This discussion occurs after technical consensus was reached on the Rust infrastructure patches, indicating these are broader philosophical positions rather than blocking concerns. Wong's perspective emphasizes C's existing capabilities and the value of incremental improvement, while acknowledging the ship has sailed on Git's Rust direction. The exchange provides useful context about alternative approaches to memory safety and concurrency that may inform future C-focused contributions.
