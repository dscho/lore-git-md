Thread identity: Bugfix for files-backend symref name validation, specifically targeting HEAD ref names. Patch series by [author name not provided], currently at v2.

Core problem: The refs subsystem lacked runtime validation for HEAD ref names during updates, allowing invalid HEAD refs to be created via operations like `git reset`. While `git fsck` checked these via `fsck_head_link()`, the validation wasn't available to `git refs verify` or during normal repository operations.

Current status: v2 patch moves validation logic from fsck.c to the refs subsystem, making it consistently available. Adds runtime checks in files-backend.c's `split_symref_update()` to prevent invalid HEAD creation using existing `refname_is_safe()` infrastructure. Includes new test case in t7102-reset.sh that verifies `git reset` rejects malformed HEAD refs (e.g., `refs/../foo`).

Key technical details: Validation moved from `fsck_head_link()` to refs subsystem. Added check in `files-backend.c` during ref updates. Touches refs/files-backend.c, t/t7102-reset.sh. Behavior change: operations that would create invalid HEAD refs now fail early rather than creating corrupt state. Implementation is minimal (10 lines of core logic) and leverages existing validation infrastructure. Jeff King (Peff) and Junio C Hamano now agree the validation should use the full refname validation pattern (`check_refname_format()` + `refname_is_safe()`) rather than just `refname_is_safe()`. Peff questions whether validation is needed in `split_symref_update()` since it operates on existing symrefs that should have been validated when created, noting `resolve_ref_unsafe()` already performs some validation.
