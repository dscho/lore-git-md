This is a concluding discussion in the performance optimization thread about macOS mmap/munmap operations. Jeff King (Peff) responds to Koji Nakamaru's findings that the extreme mmap counts prompting the original optimization were caused by an unusually small `packedGitLimit = 128m` configuration rather than inherent Git behavior.

Peff confirms this explains the observed behavior, noting there's no general reason to use such a small window size since modern OSes handle memory pressure well. He finds it interesting that batching optimization still showed speed improvements in the constrained case, though acknowledges Nakamaru's solution of removing the restrictive config makes the optimization unnecessary for normal Git usage.

The exchange serves as post-mortem validation that the original performance issue was configuration-specific, with Peff suggesting the macOS kernel behavior observations might be useful background knowledge despite the patch being withdrawn. The thread has reached consensus that proper repository configuration (`packedGitWindowSize`) and maintenance (`git gc`) are the appropriate solutions rather than munmap queueing.
