This is a performance optimization patch for macOS mmap/munmap operations that is now being withdrawn. Koji Nakamaru confirms the root cause of the excessive mmap/munmap calls was an unusually small `packedGitLimit = 128m` setting in their local configuration, not a general Git issue. Normal Git operations show only 9 mmap calls versus the 3 million seen with the restrictive config, making the optimization unnecessary for standard usage.

The patch had implemented thread-safe wrappers in `compat/osxmmap.c` with a 65530-entry queue matching Linux's `vm.max_map_count` default. While it showed dramatic improvements in artificial scenarios (reducing `git ls-tree` sys time from 27m15s to 24s with 943k operations), testing revealed these scenarios don't reflect real-world Git behavior. Torsten Bögershausen had provided documentation-focused review suggestions, including renaming `COUNT_MAX` to `MAX_UNMAP_COUNT` and making the munmap deferral configurable via Makefile.

The thread concludes with consensus that repository maintenance (`git gc`) and proper configuration are the solution rather than munmap queueing. Nakamaru has incorporated some of Bögershausen's suggestions locally but is withdrawing the patch as the optimization addresses a non-issue for standard Git usage on macOS. No open questions remain - the investigation validated Jeff King's earlier concerns that the performance issue was configuration-induced rather than inherent to Git's macOS implementation.
