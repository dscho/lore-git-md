This is a follow-up discussion in the ongoing thread about the `commitGraph.changedPaths` config option, focusing on the behavior semantics of the config's boolean values. Derrick Stolee responds to Junio Hamano's concerns about the proposed implementation where `false` doesn't imply `--no-changed-paths`.

Stolee explains the tri-state nature of the existing `--[no-]changed-paths` flag system (-1/0/1 values) that handles three cases: forcing write, forcing no-write, or persisting existing filters. He clarifies that the current config proposal makes `true` imply `--changed-paths` while `false` maintains the default behavior (persisting existing filters) rather than forcing removal, which Junio had suggested should be symmetric.

The key technical point is that this design choice preserves backward compatibility with background maintenance scenarios where filters might exist from prior runs. Stolee describes a use case where a global `true` could be overridden by a repo-specific `false` without destructively removing existing filters. The discussion reveals an underlying tension between config symmetry and non-destructive behavior in the commit-graph filter system.

This email advances the thread by providing concrete rationale for the asymmetric config design while acknowledging Junio's concerns about consistency. It also signals that the Microsoft team (via Emily Yang) is considering both approaches, with the implications for large monorepos being a key factor. The exchange highlights how subtle configuration semantics can have significant operational consequences in Git's maintenance workflows.
