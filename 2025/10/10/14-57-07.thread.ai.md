Thread summary:

Bug report and fix addressing Git's pattern matching behavior for double-asterisk (`**`) in `.gitignore` and `.gitattributes` files, where patterns like `foo**/bar` incorrectly matched paths like `foobar` despite documentation stating `**` must be surrounded by slashes for special meaning. The issue stems from `match_pathname()`'s optimization in `dir.c` that strips matching prefixes before `fnmatch()`, losing directory boundary context.

Jeff King (Peff) submitted an RFC patch proposing to modify `dir.c` to preserve one character when passing to `fnmatch()`, preventing false matches while maintaining optimizations for non-wildcard patterns. He characterized the solution as a "disgusting hack" that correctly fixes the core issue but may need refinement for edge cases. A new test in `t/t0008-ignores.sh` verifies the fix.

Junio Hamano reviewed Jeff's solution and suggested two refinements: (1) Moving the "whole pattern matched" check before prefix stripping for cleaner logic, and (2) Considering a more targeted fix that only adjusts the prefix when encountering `**/` patterns rather than always keeping one character. Junio noted that while Jeff's solution works, the performance benefit of prefix stripping may be minimal beyond skipping `fnmatch` entirely for non-wildcard patterns.

Sruteesh Kumar responded to Junio's review, questioning the fundamental value of the prefix-stripping optimization itself and requesting clarification on its performance benefits. They strongly objected to Junio's proposed targeted fix for `**/` patterns, calling it an unacceptable special case that would bypass this scenario in the code, indicating preference for Jeff's more general solution despite its "disgusting hack" characterization.

Jeff King has now provided detailed benchmark results comparing four variants of Git's pattern matching behavior: original implementation (`git.orig`), complete removal of prefix matching (`git.none`), keeping only the full-match optimization (`git.fullonly`), and the proposed "minusone" approach. The data shows prefix-stripping provides significant performance benefits (1.46x faster than no optimization for exact matches) and that the one-character context preservation performs equivalently to the original implementation while fixing the `**` matching bug. The benchmarks confirm `fnmatch()` is substantially slower than `strcmp()`, validating the optimization's value.

Current technical consensus favors Jeff's original "minusone" solution as it:
1. Fixes the documented `**` matching behavior
2. Maintains performance benefits for common cases
3. Has minimal code footprint
4. Avoids special-casing `**/` patterns

Open questions resolved by this analysis:
- Prefix-stripping optimization provides meaningful performance benefits
- General solution (keeping one character) outperforms targeted fixes
- Performance impact justifies the optimization's continued use
