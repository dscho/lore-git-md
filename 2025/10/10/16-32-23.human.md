Junio C Hamano responds to Derrick Stolee's explanation of the tri-state behavior for commit-graph changed-path Bloom filters. This is part of the ongoing discussion about how to configure these filters, where the current implementation has an asymmetric design that differs from typical Git boolean options.

Junio acknowledges Stolee's clarification that `--no-changed-paths` actually means "strip existing filters" rather than just preventing new ones from being written. He notes this explains the unusual behavior he observed. The discussion highlights a key pain point: when a user sets the global config to 'true' but a repo-specific config to 'false', the behavior (preserving existing filters) may not match user expectations.

Junio suggests improving the documentation to clearly explain that:
- `true` acts like always passing `--changed-paths`
- `false` stops new filter writes but doesn't remove existing ones
- The option needs to distinguish itself from the `--no-changed-paths` CLI behavior

The email doesn't propose code changes but focuses on clarifying the user-facing documentation to prevent confusion. This reflects the careful consideration being given to how this feature will work in practice, especially in complex scenarios like Microsoft's monorepo use cases mentioned earlier in the thread.
