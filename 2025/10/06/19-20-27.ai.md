This is a continuation of the Git 3.0 planning discussion from the Contributor's Summit, focusing on SHA-256 transition timelines and ecosystem readiness.

The email captures a lively debate about whether to set a hard deadline for SHA-256 support in Git 3.0. Taylor Blau notes their team has been using end-of-2026 as an internal benchmark for SHA-256 delivery, while acknowledging the project shouldn't delay purely for this feature. Brian m. carlson emphasizes the security rationale, citing the $10k cost to create SHA-1 collisions, and argues for including SHA-256 in Git 3.0 with a firm date, even if full interoperability work isn't complete.

Key tensions emerge around ecosystem adoption - Elijah Newren and Peff question whether forges will actually support SHA-256 repositories when Git 3.0 ships, with Peff arguing release timing should depend on forge readiness rather than just core Git implementation. Brian counters that smaller forges won't implement SHA-256 until it's in a major release. Taylor pragmatically notes there will always be stragglers, and users will blame Git if major forges don't support the new hash algorithm.

The discussion also touches on other Git 3.0 scope items including reftable becoming the default reference backend and planned deprecations. Patrick Steinhardt mentions maintaining a BreakingChanges document tracking removals, while Taylor suggests implementing "brown-outs" (temporary feature disablements) for deprecated functionality. The thread ends with agreement to continue the discussion on-list, with Brian volunteering to kick off that conversation.

This email highlights the complex coordination challenges between core Git development and the broader ecosystem, particularly around the SHA-256 transition. The tension between technical readiness (Brian's security concerns) and practical adoption (Peff's forge support questions) remains unresolved, suggesting this will be a major discussion point in the coming months.
