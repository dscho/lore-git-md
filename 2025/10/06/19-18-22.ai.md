This is a discussion about introducing first-class conflict handling in Git, part of the ongoing Git Contributor's Summit 2025 follow-up series. The conversation explores various technical approaches to representing merge conflicts as persistent Git objects rather than transient working directory states.

Key technical considerations include:
- Storage formats (special tree objects vs commit headers vs dedicated conflict objects)
- GC behavior for conflict artifacts
- Backward compatibility with existing workflows
- Server-side handling of conflict objects
- Integration with new commands like `git replay` while maintaining old porcelain behavior

The discussion reveals active interest from tool developers (jj, Git Butler) who currently implement workarounds, with proposals to standardize these approaches in core Git. Notable suggestions include using special tree objects with unique file modes (potentially aligning with SHA-256 transition work) and initially keeping conflict objects local-only. The thread shows consensus on the value but uncertainty about implementation timeline, with some advocating for Git 3.0 inclusion while others caution against feature creep.

Unresolved questions center on:
- The definitive object format
- Degree of backward compatibility required
- Whether to modify existing commands or focus on new porcelain
- Server-side acceptance policies
- Binary file conflict handling

The discussion connects to broader efforts around `git replay` development and repository format evolution, with follow-up expected on the mailing list to propose concrete formats. No immediate blockers were identified, but the complexity suggests this may be a longer-term project rather than a Git 3.0 candidate.
