This is a discussion about standardizing Change-ID headers in Git commits, part of the ongoing Git Contributor's Summit 2025 thread about history rewriting tools and Change-ID proposals.

The email captures a working session where Taylor Blau, Philip Metzger, and others debate the technical implementation and semantics of Change-IDs - persistent identifiers for logical changes across history rewrites. Key points include storage location (commit headers vs auxiliary metadata), with most agreeing headers work well since they survive rebases on platforms like GitHub. The more contentious issue is semantic rules for when Change-IDs should be preserved versus regenerated - cherry-picking is noted as a case where some tools (GitButler, Gerrit) generate new IDs while others might preserve them.

The discussion reveals fundamental tensions between wanting standardized representation (the header format) versus flexible semantics. Taylor argues semantics must be consistent within a repository but can vary between tools, while others like Martin question whether any semantic agreement is needed at all. Elijah Newren suggests practical experience with the header format may be more valuable than theoretical alignment at this stage, hinting at revisiting the topic after real-world usage.

Technical specifics mentioned include: the Change-ID being treated as an opaque identifier without versioning, concerns about how forges handle automatic rebases/squashes, and edge cases around commit splitting/merging that complicate semantic rules. The email shows this is part of broader ecosystem integration work connecting to tools like Gerrit, GitHub, and GitButler, with no immediate resolution on semantic standardization.
