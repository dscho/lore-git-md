Feature implementation for submodule path encoding, with ongoing design discussion about URL encoding helper placement and case sensitivity handling.

This email from Junio C Hamano continues the discussion about the submodule path encoding series, focusing on two key technical points in the implementation. First, he questions the case sensitivity handling in the URL encoding scheme, asking why uppercase letters are encoded as `_a` rather than using standard URL percent-encoding (`%41`). This probes whether the chosen encoding truly solves case collision issues on case-insensitive filesystems.

Second, Junio pushes back against the phrasing "For now" in the documentation about the encoding scheme being URL-based, arguing the project should choose a single encoding method that won't require future migrations. This reflects his broader concern about maintaining backward compatibility and avoiding future config option proliferation.

The technical implementation shown includes:
- New `repository_format_submodule_encoding` flag in repository.h
- Config handling in setup.c for the `extensions.submoduleEncoding` option
- Case-aware encoding in `strbuf_addstr_case_encode()` helper
- Comprehensive test coverage in t7425-submodule-encoding.sh that verifies:
  - Mixed legacy/new encoding handling
  - Clone behavior with/without encoding enabled
  - Nested submodule path cases
  - Parallel cloning scenarios

The thread context shows this is part of a near-complete series where the main outstanding question is where to place the URL encoding helper function (`is_rfc3986_unreserved()`). Junio's position is that strbuf.[ch] is inappropriate unless strbuf itself needs URL encoding functionality, suggesting submodule.c as a better home since that's its current user.
