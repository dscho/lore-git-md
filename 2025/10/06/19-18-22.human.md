This is a discussion about introducing first-class conflict handling in Git, part of the ongoing Git Contributor's Summit 2025 follow-up notes. The conversation explores what "first-class conflicts" would mean (storing conflict states as commit headers or special tree objects), potential use cases (enabling collaborative conflict resolution and stack-based workflows), and implementation challenges.

Key points from the discussion include:
- First-class conflicts would allow saving and sharing unresolved merge states, similar to how tools like `jj` currently handle them
- Several storage options were debated (commit headers vs. special tree objects), with tradeoffs around GC behavior and discoverability
- The group considered whether this should be a Git 3.0 feature, with concerns about overloading the major release
- There was interest in learning from existing tools' approaches while designing a native Git solution

The discussion appears exploratory rather than conclusive, with no clear consensus yet on implementation details or timeline. The thread suggests this will require more design work before implementation, particularly around backward compatibility and interaction with existing commands like rebase.
