This is a follow-up discussion in the submodule gitdir path encoding series, now in its fifth iteration. Junio C Hamano is responding to Adrian Ratiu's v3 cover letter, which proposed making the encoding feature opt-in via a repository extension (`extensions.submoduleEncoding`).

The key points raised are about compatibility and migration paths. Junio notes that using an extension makes repositories with encoded submodules incompatible with older Git versions, which could affect tools with embedded Git. He also seeks clarification on whether enabling the extension would require converting existing submodules to the new encoding scheme, emphasizing the importance of consistency in the approach.

The response suggests Junio is generally supportive of the simplified design but wants to ensure there are no edge cases where the system would need to guess between encoded and non-encoded paths. This touches on one of the "remaining considerations" noted in the thread summary - how the encoding scheme interacts with existing submodules.

The exchange shows the series is nearing finalization, with the maintainer focusing on real-world usage implications rather than technical implementation details at this stage.
