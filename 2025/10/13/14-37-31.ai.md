This is the final patch in a series introducing reference optimization infrastructure, currently focused on naming the flag for checking optimization needs without performing it. Junio Hamano weighs in on the ongoing naming discussion, rejecting the proposed `--required` flag as semantically incorrect - it implies mandatory action rather than the intended "should we optimize?" check. He suggests alternatives like `--check-for-auto` that better capture the lightweight advisory nature of the check.

The email confirms the technical implementation is sound, comparing it to the existing `should_pack_refs()` logic. Hamano emphasizes this is about cost-benefit analysis ("are we better off if we repacked?") rather than mandatory optimization. This leaves the series functionally complete but blocked on finalizing the flag name, with `--check-for-auto` now emerging as the leading candidate to replace `--required`.

Key technical context for future reference:
- The check is designed to be cheap (especially important for GitLab's Gitaly)
- Behavior parallels existing `should_pack_refs()` for files backend
- Return values already standardized (0=optimize needed, 1=not needed)
- Implementation spans all ref backends (files/packed/reftable)
- Testable via `GIT_TEST_REFTABLE_AUTOCOMPACTION`

The naming debate appears to be the final blocker before this series can be merged, with consensus forming around terminology that better reflects the advisory nature of the optimization check.
