This is a follow-up in the const-correctness discussion around the patch-id subsystem's interaction with the hashmap API. Junio Hamano responds to Okhuomon Ajayi's acknowledgment that their initial const-correctness fix was problematic, as it broke functionality by preventing necessary modifications to diff options during processing.

Hamano suggests that if Ajayi can make a convincing case that the hashmap API should not be changed to accommodate this use case, that justification itself could serve as the resolution - allowing removal of the NEEDSWORK comment while keeping the current implementation that casts away constness. He emphasizes that such a justification would need to thoroughly explain why the hashmap API's const requirements are correct for this situation, making the current implementation the only reasonable approach.

The email shows the discussion moving from a specific code fix attempt to considering broader API design questions. Hamano's guidance indicates this may become either: (1) a documentation update solidifying the current behavior as intentional, or (2) if the hashmap API proves flexible enough, a more involved solution that maintains const-correctness while allowing the diff modifications. The ball remains in Ajayi's court to research and propose the next steps.
