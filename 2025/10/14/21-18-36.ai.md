This is a discussion about hash algorithm usage in patch-id computation, continuing the thread about standardizing SHA1 usage for patch IDs. Brian m. carlson raises concerns about the proposed enforcement of SHA1 in `builtin/patch-id.c`, noting that SHA-256 repositories currently produce SHA-256 patch IDs and this behavior has been in place since Git 2.29.

The key technical objection is that mandating SHA1 conflicts with future-proofing needs, particularly given government-mandated SHA1 deprecation timelines (noting 2030 as a key deadline). Brian suggests maintaining the current behavior of using the repository's default hash algorithm while adding an optional flag to control hash selection, rather than hardcoding SHA1.

This introduces new considerations to the ongoing discussion:
1. The current implementation's SHA-256 output capability is intentional and long-standing
2. Future SHA1 deprecation requirements may force another change if SHA1 is hardcoded now
3. A configurable approach (via new option) might better serve both backward compatibility and future needs

The comment highlights a tension between documentation accuracy (which specifies SHA1) and practical forward compatibility needs. This suggests the solution may need to address both the documentation and the implementation, possibly through deprecation warnings or phased changes rather than immediate enforcement of SHA1.
