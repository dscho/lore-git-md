This is a follow-up discussion about the deprecation of `core.preferSymlinkRefs` configuration, focusing on wording and implementation details of the warning system. Junio C Hamano provides several suggestions for improving the patch's documentation and warning messages.

Key points raised:
- Suggests rephrasing the deprecation notice in config.txt to be more positive ("Symbolic refs will always be written as textual symrefs")
- Questions whether to use `NOT_CONSTANT(-1)` in the conditional compilation
- Notes the warning message uses "symref format" terminology which may not be official (he prefers "textual symref")
- Observes the warning is emitted before attempting to lock, which might be intentional to ensure the warning appears even if locking fails

The discussion focuses on polishing the deprecation messaging rather than challenging the deprecation itself. The technical implementation remains unchanged - still using a static `warn_once` variable in `create_ref_symlink()` to emit warnings, with the actual symlink writing behavior being disabled when `WITH_BREAKING_CHANGES` is defined. The thread shows careful attention to documentation wording and user messaging for this backward-incompatible change.
