Proposal to change default value of `rerere.enabled` from off to on, with discussion of timing (Git 3.0 vs 2.x series) and usability concerns. Thread originator Junio Hamano initially suggested Git 3.0 as natural version for enabling the now-mature feature after years of opt-in usage. Kristoffer Haugsbakk identified key usability issues including confusing "Reused recorded resolution" output, non-intuitive `git rerere forget` workflow requiring conflict state, and unclear documentation. Taylor Blau supports default enablement but questions waiting for 3.0, suggesting it could happen in 2.52 given rerere's battle-tested status. D. Ben Knoble has reinforced visibility concerns in multiple messages, noting the "Reused recorded resolution" messages can be easily missed during conflict resolution and highlighting a disconnect between rerere's automatic resolutions and `git-status` reporting of unresolved conflicts.

Junio Hamano's latest response confirms Kristoffer's findings about the `git rerere forget` workflow requiring conflict state, while suggesting an optimization where users could record correct resolutions immediately after forgetting rather than restarting the merge. This exchange concretely illustrates one of the major usability pain points around cache management. Technical details remain unchanged: `rerere` would become active by default with current known behaviors. Open questions now include whether UI improvements (message visibility, status reporting alignment, cache management workflow) should precede enablement, and whether version number constraint (3.0) is necessary. Emerging consensus suggests the technical implementation is sound but user-facing aspects need polish regardless of timing decision. Thread status remains active with two paths forward: immediate enablement in 2.x with known UI issues versus delayed enablement in 3.0 pending UX improvements, with increasing acknowledgment that some UI work may be done in parallel with or after default-flip rather than strictly before.
