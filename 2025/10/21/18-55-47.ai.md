This is a discussion about the proposal to enable `rerere.enabled` by default in Git 3.0. Kristoffer Haugsbakk responds to Junio Hamano's initial RFC with mixed feedback about the rerere feature's current usability.

The email provides real-world user experience with rerere, noting several pain points: the output during conflict resolution can be confusing with reused resolution messages appearing randomly in the output, the process for selectively removing cached resolutions is non-obvious (requiring multiple steps while in a conflict state), and the documentation is hard to understand. The author contrasts this with git-reflog which they find more straightforward to use.

While supportive of the general idea to enable rerere by default (especially for users who frequently rewrite history), the email suggests the feature may not benefit users who perform many merges before landing changes. The feedback highlights that while the technical implementation may be mature, the user interface and documentation could still use improvement to make the feature more approachable. The author notes they won't be able to follow up on the thread.

Key technical details mentioned: the multi-step process required for `git rerere forget` on specific paths, the placement of "Reused recorded resolution" messages in output, and the contrast with reflog usability. The email references Junio's blog post about rerere pitfalls as being difficult to understand.
