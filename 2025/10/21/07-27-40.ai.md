This is a technical proposal for the ongoing `git grep` file filtering discussion, suggesting an implementation approach for configurable attribute-based exclusion. Jeff King builds on Eloy's earlier ideas about script compatibility and generalized filtering, proposing a `grep.defaultpathspec` configuration that would let users set default exclusions while allowing scripts to override them by explicitly specifying pathspecs.

The key technical contribution is a patch adding a `defaultpathspec` strvec in `builtin/grep.c` that gets used when no explicit pathspec is provided. This would allow configurations like `git config grep.defaultPathspec :^po` to exclude translation files by default, while maintaining backward compatibility since any explicit pathspec (like scripts using `.` for "everything") would override the default. The approach leverages Git's existing pathspec machinery rather than introducing new filtering logic.

The email notes some tradeoffs: the default pathspec replaces rather than augments user-specified pathspecs, which might be either a limitation or a feature depending on use cases. Jeff also points out that similar functionality could be achieved today with aliases, though those require user retraining and don't help with scripts.

This moves the discussion forward by providing a concrete, minimally invasive implementation path that addresses several concerns from the thread: it's configurable rather than changing defaults, preserves script compatibility through explicit overrides, and uses existing Git concepts (pathspecs) rather than inventing new mechanisms. The proposal aligns with the thread's emerging consensus around attribute-based solutions while sidestepping the contentious default behavior changes.
