This is a user experience contribution to the ongoing `git clone --shallow-exclude` discussion, providing real-world testing results from GitHub Actions workflows. Erik Cervin Edin shares concrete test cases showing inconsistent behavior between excluding `master` versus `maint` branches in shallow clones, with the former failing with a connection error while the latter succeeds.

The email demonstrates a practical CI use case similar to Philipp Hahn's earlier GitLab scenario, where commit linters need access to a variable commit range (origin/master..HEAD) but shallow clones complicate this. Erik's testing reveals that while `--shallow-exclude=maint` works as expected (expanding the clone to 43 commits), the same approach with `master` fails with "the remote end hung up unexpectedly", suggesting either a GitHub-specific issue or an undocumented limitation in branch name handling.

Key technical details include:
- Reproduction steps showing the divergent behavior between `master` and `maint` exclusions
- Mention of `postBuffer` configuration as a potential workaround (though deemed unlikely to help)
- Confirmation that GitHub Actions currently uses depth=1 clones by default
- Indirect evidence that commitlinter tools rely on `git log` and are affected by shallow clone limitations

The contribution doesn't propose solutions but adds valuable empirical data to the thread, particularly regarding GitHub's implementation differences from GitLab's behavior. The inconsistency between branch names suggests there may be server-side or protocol-level variations in how different default branch names are handled during exclusion operations. This reinforces the thread's emerging consensus that blobless clones may be more reliable than shallow clones for CI workflows.
