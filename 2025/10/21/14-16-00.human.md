Feature implementation for `git-history split subcommand`, the final patch in Patrick Steinhardt's v5 series introducing new history editing capabilities. This adds a `git history split` command that interactively splits a commit into two commits by letting users select which changes to move into a new parent commit.

The implementation handles the common but complex workflow of splitting a commit via interactive rebase, reducing it to a single command. Users can either select changes interactively (using the same interface as `git add -p`) or limit changes via pathspec. The command preserves authorship and handles edge cases like empty commits, with extensive test coverage (447 lines across 18 test cases).

Key technical aspects:
- Uses the interactive add-patch interface for hunk selection
- Maintains commit authorship and handles message editing
- Integrates with the series' shared replay infrastructure
- Rejects merges and unrelated commits
- Preserves worktree/index state during operation

This completes the series' goal of providing Jujutsu-inspired history editing while avoiding merges per community feedback. The implementation appears robust with thorough testing and clear documentation positioning it as complementary to `git-rebase`.
