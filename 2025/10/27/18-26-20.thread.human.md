This thread centers on extending `git refs migrate` to support linked worktrees, enabling migration between ref storage formats (files and reftable) in repositories with multiple worktrees. The implementation handles this through a multi-phase approach with rollback capabilities, touching several ref backend components and adding new test coverage.

Patrick Steinhardt's initial review identified several architectural concerns, leading to a proposed reorganization of the patch series into clearer phases. The discussion has clarified that worktrees must share the same ref storage format due to existing `extensions.refStorage` constraints, making uniform storage a hard requirement. This simplifies the technical design by eliminating mixed-format scenarios but introduces user experience questions about requiring operations to start from the main worktree.

Junio C Hamano's latest input confirms this constraint is intentional, framing the main-worktree requirement as a safety mechanism rather than a limitation. While this provides technical clarity, Kristoffer Haugsbakk has raised valid concerns about whether this design places implementation details above user expectations, drawing parallels to how `git gc` handles worktrees more transparently.

The thread now appears to have consensus on the core architecture, with remaining work focusing on documentation and messaging. Key open items include how to clearly explain the uniform storage requirement to users, whether to adjust error messages for educational value, and finalizing the patch series organization per Patrick's suggestions. The discussion reflects Git's ongoing balance between technical constraints and usability, particularly as the project evolves its ref storage infrastructure.
