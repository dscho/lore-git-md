This thread discusses extending `git refs migrate` to support repositories with linked worktrees, enabling conversion between files-based and reftable ref storage formats. The technical implementation involves handling multiple worktrees through temporary storage and rollback capabilities, with changes to refs.c, files-backend.c, and extensive test coverage.

Patrick Steinhardt's review suggested reorganizing the series into three phases: backend changes first, then refactoring migration logic, and finally worktree iteration. The discussion revealed two key constraints: uniform storage format is required across all worktrees (mixed formats would break compatibility), and running the command from the main worktree serves as a safety measure against surprising users with implicit repository modifications.

Kristoffer Haugsbakk's recent contribution shifts focus to user experience, arguing that requiring main worktree operation feels like exposing implementation details. They compare this to `git gc`'s worktree-agnostic behavior and question whether mixed storage formats provide any real user benefit. While not proposing specific code changes, this perspective highlights the need for careful documentation and error messaging to explain the current design's safety tradeoffs.

Junio C Hamano had initially raised similar UX concerns, suggesting the team must decide whether to frame the main-worktree requirement as a temporary limitation or inherent design choice. The discussion now balances technical constraints (particularly around `extensions.refStorage` compatibility) against user expectations of consistent behavior across worktrees. Open questions remain about final architecture, documentation wording, and handling edge cases like prunable worktrees.
