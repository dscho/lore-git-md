This is a bugfix targeting Git's whitespace error highlighting system. Alice Carlotti reports that `WS_BLANK_AT_EOF` warnings fail to appear in certain edge cases - specifically when the final diff hunk has either zero old lines or zero new lines. This most commonly affects new files (where EOF whitespace issues frequently occur) and when using `-U0` diff output.

The root cause lies in how line numbers are handled for empty hunks - they're deliberately decremented by 1 compared to non-empty hunks (so an empty file shows 0,0 while a non-empty one shows 1,N). The current parsing logic in `diff.c:find_lno()` doesn't account for this discrepancy when checking for whitespace errors.

The patch suggests two potential solutions: either adjust the line number calculation when lengths are zero, or reuse the more comprehensive range parsing code from `apply.c:parse_range()`. The commit references prior discussion establishing the current hunk numbering behavior, showing good attention to historical context. This appears to be a well-analyzed fix for a real (if somewhat edge-case) bug in whitespace detection.
