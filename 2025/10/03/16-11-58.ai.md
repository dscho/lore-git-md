This is a bugfix discussion for the interactive add functionality, specifically addressing edge cases in hunk navigation and command permissions.

Junio C Hamano responds to René Scharfe's patch fixing the hunk rollover behavior in `git add --interactive`. While acknowledging the correctness of René's fix for the decided/undecided hunk handling, Junio identifies a deeper architectural issue in the command permission system that affects multiple interactive add operations.

The core issue lies in `add-patch.c` where the `permitted` bitmask (controlling available commands like split 's') isn't reset between hunk evaluations. This causes commands to remain available even when they shouldn't be - like allowing 's'plit on unsplittable hunks if a previous hunk was splittable, or allowing invalid 'k' navigation after initial rejection. Junio traces this to the 2019 C rewrite of the interactive add code.

Interestingly, Junio notes this bug accidentally created a useful feature - allowing wrap-around navigation with 'j/J' even when not explicitly offered in the prompt. The original Perl implementation prevented this by properly resetting permissions. The discussion suggests this might be worth preserving as intentional behavior while fixing the underlying permission system bugs.

The thread shows the patch is technically sound for its specific hunk rollover case, but has uncovered broader interactive add issues that may warrant follow-up work. The permission system bugs affect multiple commands (split, navigation) and have existed since the C conversion, indicating they may require careful consideration to fix without breaking any accidentally-useful behaviors that have emerged.
