This thread examines performance issues in `git status` related to the untracked files cache, particularly when the `--untracked-files=all` flag conflicts with configuration. Initial reports from Windows and Linux users showed 3-4x slowdowns when the cache is bypassed. Matthew Hughes identified the root cause: the `--no-optional-locks` flag prevents cache updates via `repo_update_index_if_able()`, creating a "sticky cache" effect where the initial state persists.

Devste Devste has now confirmed this affects real-world tools like SourceTree, where fixed command-line arguments prevent cache updates. The performance impact is significant (3.4s vs 0.8s in some cases), and users must resort to workarounds like manually running `git status --untracked-files` outside their normal workflow. The core issue remains that the cache update mechanism depends on optional locks being enabled, which conflicts with how some GUI tools operate. While the technical cause is understood, it's unclear whether this lock dependency is intentional or needs redesign to accommodate common tooling patterns.
