This is a follow-up discussion in the interactive add bugfix thread, focusing on interface documentation and behavior clarification.

Junio C Hamano and René Scharfe are refining the wording around hunk navigation commands in `git add --interactive`. They agree the current documentation is misleading when describing the 'J' command as "leave this hunk undecided" - in reality, these navigation commands preserve any previous decision (use/skip) rather than resetting to undecided. René proposes clearer documentation phrasing that simply describes the movement behavior without implying state changes.

The discussion reveals two long-standing interface limitations: there's no direct way to revert a hunk back to undecided status after making a decision, and once all hunks in a file are decided, there's no built-in way to revisit and change those decisions. These aren't regressions but inherent limitations carried over from the original scripted implementation.

The exchange shows the patch series has prompted deeper examination of the interactive add interface's design choices. While the immediate bugfixes are technically sound, this thread highlights opportunities for improving both the documentation and potentially the command set to better match user expectations and workflows. The tone remains constructive, with both participants carefully analyzing the gap between current behavior, documentation, and what users might reasonably expect.
