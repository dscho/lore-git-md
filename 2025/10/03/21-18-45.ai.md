This is a technical discussion about hunk navigation behavior in `git add --interactive`, specifically addressing edge cases in the rollover logic when moving between hunks.

Junio Hamano responds to René Scharfe's patch that modified `patch_update_file()` to skip decided hunks when rolling over to the next hunk. He questions whether this is the right behavior for the 'J' (join) command, suggesting users might want to walk through all hunks regardless of their decided state. 

The email highlights several key technical points:
1. The current inconsistency in navigation behavior - while forward rollover (hunk_index >= file_diff->hunk_nr) is handled, backward navigation ('K' command) lacks similar wrap-around logic when hunk_index goes negative
2. The problematic use of size_t for hunk_index which complicates negative value handling
3. The different expected behaviors between 'J' (which may need to see all hunks) versus 'j' (which likely should skip decided hunks)

Junio identifies this as part of a larger navigation consistency problem in the interactive add interface, noting that neither the current implementation nor the proposed patch correctly handles moving to the last hunk when at the first hunk with 'K'. The discussion reveals deeper architectural questions about hunk state management and command semantics that go beyond the immediate bugfix.
