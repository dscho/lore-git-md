Thread examining performance impact of untracked files cache behavior in `git status`, focusing on interactions between `--untracked-files=all` flag and `status.showUntrackedFiles=all` config. Original report (Windows) and Matthew Hughes (Linux) showed 3x slowdown when cache is bypassed due to flag/config mismatch (e6a653554b). Devste Devste confirmed core issue and revealed additional complexity: 1) Cache becomes "sticky" once established, and 2) Common tooling flags may interfere with cache updates. New timing data showed 3.4s vs 0.8s differences.

Matthew Hughes has isolated `--no-optional-locks` as the specific flag causing cache update failures when combined with `--untracked-files=all`, identifying `repo_update_index_if_able()` in `cmd_status` as the critical path that only executes when `use_optional_locks` returns true. Concrete timing data shows >1s vs ~300ms performance difference when this flag is present. The findings demonstrate the cache update mechanism depends on optional locks being enabled, though the exact relationship remains to be explained. Reproduction case uses `GIT_CONFIG_GLOBAL=/dev/null` to isolate behavior.

Current understanding: cache behavior depends on both initial conditions (flag/config symmetry) and undocumented interactions with specific flags, particularly `--no-optional-locks` which prevents cache updates via the `repo_update_index_if_able()` path. The "sticky cache" phenomenon may stem from this lock-related update failure. Open questions: whether this lock dependency is intentional design or oversight, and whether other flags (`--porcelain`, `--ignore-submodules=dirty`, `--no-ahead-behind`) have similar effects. Performance impact (3-4x slowdown) confirmed across Windows and Linux when cache updates fail.
