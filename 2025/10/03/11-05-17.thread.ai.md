Thread examining performance impact of untracked files cache behavior in `git status`, focusing on interactions between `--untracked-files=all` flag and `status.showUntrackedFiles=all` config. Original reports from Windows and Linux (Matthew Hughes) showed 3x slowdown when cache is bypassed due to flag/config mismatch (e6a653554b). Core issue confirmed by Devste Devste with additional complexity: 1) Cache becomes sticky once established, and 2) Common tooling flags (particularly `--no-optional-locks`) interfere with cache updates via `repo_update_index_if_able()` path, creating 3.4s vs 0.8s performance differences.

Matthew Hughes isolated `--no-optional-locks` as the specific flag preventing cache updates when combined with `--untracked-files=all`, with timing data showing >1s vs ~300ms differences. Devste Devste confirmed real-world impact in SourceTree usage where fixed command-line arguments (including `--no-optional-locks`) create permanent performance degradation due to the sticky cache phenomenon - once established with these flags, the cache cannot be refreshed through normal tool operation. Practical workaround identified (manual `git status --untracked-files` runs) but highlights design tension between cache assumptions and tooling constraints.

Key technical details: cache update mechanism depends on optional locks being enabled through `repo_update_index_if_able()`, but this dependency is not clearly documented. The "sticky cache" behavior emerges when tools like SourceTree use flag combinations that prevent updates while inheriting cache state from other operations. Open questions remain about whether this lock dependency is intentional design, whether other flags (`--porcelain`, `--ignore-submodules=dirty`) have similar effects, and how to reconcile the optimization with real-world tool constraints. Performance impact (3-4x slowdown) confirmed across platforms when cache updates fail.
