This is a discussion about interactive add behavior and potential follow-up work after the recent bugfix patches.

Junio C Hamano responds to René Scharfe's observations about the interactive add interface, noting that while the current behavior has some accidental features (like hunk navigation wrap-around), users have come to rely on them. The discussion centers around two key points:

1. The current implementation allows reverting decided hunks back to undecided state through an indirect method (splitting hunks), which Junio acknowledges as a useful side effect of the underlying bugs.

2. The accidental wrap-around navigation behavior (where j/J commands cycle back to the first hunk) has become expected behavior, suggesting it should be preserved intentionally rather than fixed away. Junio proposes formalizing this by always allowing J/K navigation and adjusting the prompt strings accordingly.

The email reveals deeper architectural questions about the interactive add system, particularly around:
- The `permitted` bitmask system that controls command availability
- Navigation behavior consistency between different commands (j/k vs y/n/e)
- Documentation gaps around movement commands

Junio hints at potential further bugs in other interactive add commands beyond the already-fixed j/k/J/K/s cases, suggesting more comprehensive review may be needed. The tone indicates these are follow-up considerations rather than blockers for the current fixes, positioning them as potential future improvements to the interactive add interface.
