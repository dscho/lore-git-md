This is a follow-up discussion in the cbindgen support series, focusing on platform compatibility and build system implications. Toon Claes raises two key points about the final patch's implementation:

First, they question whether requiring cbindgen as an additional dependency alongside cargo might limit platform support, asking whether platforms that support Rust will reliably have cbindgen available. This touches on the series' broader goal of maintaining wide platform support while introducing Rust infrastructure.

Second, they note that the current verification approach - where each Rust-rewritten subsystem's C file includes the generated bindings - could lead to duplicate signature checks when subsystems include each other's headers. While acknowledging this as a reasonable tradeoff for now (given only varint.c currently uses this), they flag it as something that might need revisiting as more subsystems are converted to Rust.

The discussion shows thoughtful consideration of the series' long-term maintainability implications while recognizing the pragmatic choices made in the current implementation. It doesn't propose immediate changes but surfaces considerations that may inform future iterations of the Rust/C interop infrastructure.
