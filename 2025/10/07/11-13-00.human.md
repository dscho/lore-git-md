This is a follow-up in the submodule gitdir path encoding series, addressing migration of existing submodule directories when the new encoding extension is enabled.

Adrian Ratiu responds to Junio C Hamano's concern about mixed encoding states in repositories where some submodules were created before enabling the new `extensions.submoduleEncoding` config. The current v3 approach leaves existing gitdirs unencoded for backward compatibility, but Junio argues this creates an inconsistent state that complicates the code.

Ratiu acknowledges this is a valid point and proposes changing course in v4: when the extension is first enabled, Git would migrate all existing submodule gitdirs to the new encoded names. This would eliminate the need to handle mixed states in the code, though it comes with the cost of a one-time migration operation.

The exchange shows the series is nearing its final form, with this being one of the last design decisions to settle. The migration approach would provide cleaner semantics (all gitdirs either encoded or not) at the expense of potentially breaking third-party tools that might have paths hardcoded to the unencoded names. Ratiu seems willing to make this tradeoff unless others object.
