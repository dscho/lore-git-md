This is part 3/6 of the packfile store API refactoring series, focusing on `git grep`'s pack preloading behavior. The patch simplifies how `git grep` initializes packfiles when running with multiple threads by directly calling `packfile_store_prepare()` instead of going through the intermediate `packfile_store_get_packs()` wrapper.

The change is straightforward - the grep command was only using `get_packs()` to trigger packfile initialization via its side effect, not actually using the returned pack list. The patch cuts out this indirection since the initialization function is now exposed. This maintains the same thread-safety behavior while being more direct about the intent.

This continues the series' pattern of converting callers to use the more predictable `packfile_store_prepare()` API before eventually removing the confusing `get_packs()` variant. The grep.c change is particularly low-risk since it wasn't even using the problematic return value that differs between MIDX and non-MIDX cases. The commit references recent history (commit 4188332569) where the relevant function became publicly accessible.

Technical details: modifies one line in `builtin/grep.c`, replacing a `packfile_store_get_packs()` call with direct `packfile_store_prepare()` invocation. No behavior change expected since grep was already ignoring the return value. The patch fits cleanly into the series' incremental approach, touching a third subsystem (after object naming and gc) while maintaining the same careful, focused changes seen in previous parts.
