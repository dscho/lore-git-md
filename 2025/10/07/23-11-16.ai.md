This is a follow-up in the thread about `git bundle --all` behavior, where the original reporter Andrew Harmon provides a concrete reproduction case to demonstrate the behavior that was recently clarified as expected by maintainer Junio C Hamano.

The email shows a complete workflow where:
1. A repository is cloned from GitLab (showing multiple remote-tracking branches under `refs/remotes/origin/*`)
2. A bundle is created with `--all` (correctly including all refs, verified via `git bundle verify`)
3. The bundle is cloned, resulting in only the `refs/heads/*` branches being available as remote-tracking branches

Andrew expresses continued confusion about why the behavior differs from cloning directly from GitLab, despite Junio's explanation that this matches Git's standard remote cloning semantics. The reproduction confirms the bundle contains all refs (including remote-tracking ones) but the clone operation only imports the local branches, exactly as Junio described.

Key technical details reinforced:
- The bundle creation (`--all`) correctly includes all refs (both `refs/heads/*` and `refs/remotes/origin/*`)
- The clone operation follows standard Git behavior by only fetching `refs/heads/*` as remote-tracking branches
- The disconnect comes from expecting bundle cloning to behave differently than regular remote cloning

The thread remains focused on documentation needs rather than code changes, with Andrew's reproduction serving as a concrete example that could inform improved documentation. The core question persists around how to best explain why bundle cloning behaves this way and document the proper techniques (explicit fetch or mirror clone) for complete repository transfer.
