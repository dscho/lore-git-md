This is a bugfix for color handling in `git status` output, specifically addressing an inconsistency between different status markers when using `--short -z` flags.

Jeff King clarifies that the original reporter's expectation of complete color suppression with `--short -z` doesn't match Git's documented behavior - color is still expected in `--short` output, while `--porcelain` (implied by `-z`) suppresses it. However, he confirms there is indeed a bug in the current implementation where modified (`M`) and untracked (`??`) markers behave differently under these flags.

The proposed fix adjusts the color handling in `wt-status.c` to make untracked file markers consistent with other status outputs by moving the color application before the null-termination check. This matches the pattern used in similar functions like `wt_shortstatus_unmerged()`. The change is focused and mechanical, touching only the color application logic for untracked files in short status output.

Key technical details:
- Fixes inconsistent behavior between `M` (colored) and `??` (uncolored) markers
- Modifies `wt_shortstatus_other()` in `wt-status.c`
- Aligns with existing patterns in `wt_shortstatus_unmerged()`
- Maintains current documented behavior where `--short` keeps colors while `--porcelain` suppresses them

The patch appears straightforward and well-justified, though Jeff notes the `-z --short` combination is somewhat unusual since these flags serve different purposes (human-readable vs machine-readable output). No new tests are included, but the change is small and focused that existing test coverage should verify the behavior.
