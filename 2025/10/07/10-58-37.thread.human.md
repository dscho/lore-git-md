This thread began as an architectural discussion about naming conventions in the refs subsystem following Patrick Steinhardt's merged 14-patch series that refactored tag peeling behavior. The core tension was between maintaining both `struct ref` and the newly introduced `struct reference`, with initial concerns about naming purity versus technical constraints.

After thorough discussion involving Patrick Steinhardt, Jeff King, Toon Claes, and Junio Hamano, the project reached consensus to accept this duality as intentional technical debt. Junio's final email confirmed that unification would be impractical due to `peer_ref` linkage complications, while preserving the series' 13% performance improvements. The resolution maintains both types indefinitely, with `struct reference` becoming the preferred type for new APIs.

In a follow-up, Patrick provided additional technical justification for the split, explaining that `struct ref` remains tightly coupled with remote operations (containing transport-specific fields), while `struct reference` serves as a minimal abstraction for core ref operations. This separation enables new capabilities like standalone reference operations and clearer type semantics. The email reinforced the architectural compromise by demonstrating concrete benefits: peeled ref operations outside iteration, potential for higher-level queries, and improved semantic distinction.

With Junio's earlier conclusion and Patrick's technical elaboration, the discussion is now fully resolved with no remaining open questions. The merged series stands as-is, with clear documentation of the design rationale and future API direction established.
