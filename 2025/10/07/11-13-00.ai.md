This is a follow-up in the submodule gitdir path encoding series, addressing Junio C Hamano's concerns about consistency when enabling the new `extensions.submoduleEncoding` feature. Adrian Ratiu responds to Junio's observation that the current v3 approach leaves existing submodule gitdirs unencoded when the extension is enabled, creating a mixed state.

Adrian acknowledges this is a valid concern and agrees that migrating all submodule gitdirs to the new encoding scheme when the extension is enabled would provide better consistency. The current v3 implementation maintains backwards compatibility by leaving existing gitdirs untouched, but Adrian now sees this as potentially over-cautious. He proposes to implement this migration in v4 unless there are objections, which would simplify the code's assumptions about which paths are encoded.

This email marks a significant shift in the approach to handling existing submodules, moving from preserving legacy paths to considering a one-time migration to the new encoding scheme. The change would affect how the feature interacts with repositories that already have submodules, ensuring all gitdirs follow the same encoding rules once the extension is enabled. This addresses one of the remaining open questions in the series about how to handle the transition between old and new submodule storage formats.
