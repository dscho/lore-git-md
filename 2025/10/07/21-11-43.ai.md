This is a bug report about inconsistent behavior between `git bundle --all` and `git clone` when dealing with remote refs. The issue occurs when trying to create complete repository snapshots for offline use.

The core problem is that while `git bundle create --all` correctly includes all refs (both local branches and remote tracking branches), `git clone` from such a bundle only fetches the local branch refs (`refs/heads/*`), leaving the remote tracking refs (`refs/remotes/origin/*`) inaccessible. This creates a disconnect in the expected workflow for air-gapped environments where users rely on bundles to transfer complete repository states.

The report includes clear reproduction steps showing that `git bundle list-heads` confirms all refs are present in the bundle, but they don't become available after cloning. The workaround requires manually fetching the remote refs with a specific refspec. The impact is significant for offline workflows where users expect `--all` to mean all refs will be available after cloning.

Three potential solutions are proposed: modifying clone behavior to fetch all bundle refs, having bundle creation remap remote refs, or at minimum improving the documentation to clarify this limitation. The bug was discovered in a Windows environment (git 2.45.2) but appears to be a general design issue rather than platform-specific.

Key technical details for future reference:
- Affects the bundle/clone interface for ref handling
- Specifically impacts `refs/remotes/origin/*` refs in bundles
- Current workaround uses `git fetch origin 'refs/remotes/origin/*:refs/remotes/origin/*'`
- The `--all` flag's promise vs. behavior mismatch is central to the issue
- Particularly relevant for offline/air-gapped repository transfer scenarios
