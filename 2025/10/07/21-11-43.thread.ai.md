Thread identity: Bug report about inconsistent behavior between `git bundle --all` and `git clone` regarding remote refs, affecting complete repository snapshot workflows.

Core problem: When creating a bundle with `git bundle create --all`, all refs (local branches and remote tracking branches) are included, but cloning from such a bundle only fetches local branch refs (`refs/heads/*`), leaving remote tracking refs (`refs/remotes/origin/*`) inaccessible. This creates a significant limitation for offline workflows where users expect complete repository state transfer.

Current status: Bug reported with clear reproduction steps showing `git bundle list-heads` confirms all refs are present in the bundle, but they remain unavailable after cloning without manual intervention. The workaround requires explicitly fetching remote refs with `git fetch origin 'refs/remotes/origin/*:refs/remotes/origin/*'`.

Key technical details: The issue stems from a mismatch between bundle creation (which honors `--all` to include all refs) and clone behavior (which defaults to only fetching `refs/heads/*`). The problem affects the bundle/clone interface's ref handling, particularly for `refs/remotes/origin/*` refs in bundles.

Open questions: Three potential solutions under consideration - (1) modify clone behavior to fetch all bundle refs by default, (2) have bundle creation remap remote refs to make them more accessible, or (3) at minimum improve documentation to clarify this limitation. The bug was discovered on Windows (git 2.45.2) but appears to be a general design issue.

Impact: Significant for offline/air-gapped repository transfer scenarios where users rely on `--all` to mean all refs will be available after cloning. The current behavior creates unexpected gaps in repository state transfer.
