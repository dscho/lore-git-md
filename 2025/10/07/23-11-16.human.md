This is a follow-up in the discussion about `git bundle --all` behavior, where the original reporter Andrew Harmon provides more details about their specific workflow to help clarify the issue. 

The email shows a concrete example of creating a bundle from a GitLab repository and then cloning from it, demonstrating that only `refs/heads/*` branches are available after cloning, while the remote-tracking branches (`refs/remotes/origin/*`) from the original repository are not. Andrew questions whether the issue stems from how refs are stored in the bundle.

Maintainer Junio Hamano had previously explained this is expected behavior - bundles follow Git's standard remote cloning semantics where remote-tracking branches from the source aren't automatically fetched. The email includes Junio's response suggesting two proper solutions: an explicit fetch of remote refs or using a mirror clone approach.

The thread has shifted from being a bug report to a documentation/clarification issue, with Andrew now seeking to better reconcile their expectations with Git's actual behavior. The example workflow serves as a good test case for potential documentation improvements that could help users understand the distinction between bundle contents and clone behavior.
