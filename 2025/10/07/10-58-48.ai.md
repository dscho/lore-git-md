This is patch 11/13 in a refactoring and bugfix series addressing tag peeling behavior in Git's refs subsystem. The patch focuses on preventing storage of invalid peeled object IDs for tags where the tagged object's type doesn't match the tag's claimed type.

The change modifies both the files and reftable backends to use the new `PEEL_OBJECT_VERIFY_OBJECT_TYPE` flag (introduced in patch 10) when peeling tags during ref storage operations. This ensures that if a tag claims to point to a commit but actually points to a blob (or other type mismatch), Git will detect this and skip storing the peeled value rather than persisting an invalid reference.

The patch includes two test cases:
1. For the files backend, verifying that `git pack-refs` doesn't store peeled values for invalid tags
2. For the reftable backend, using a clever test that creates two tags pointing to the same object with conflicting type claims to verify the inconsistency is caught

This change makes tag verification behavior consistent regardless of whether peeled values are cached in the refdb, addressing a subtle corruption case where commands like `git-for-each-ref` could silently accept invalid tags when using cached peeled values. The implementation builds on the type verification infrastructure from previous patches while maintaining the series' focus on removing global state and improving refs subsystem robustness.
