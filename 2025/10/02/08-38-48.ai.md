This is a documentation-focused follow-up in the ongoing worktree UX discussion. Michal Suchánek responds to Junio Hamano's points about why nested worktree complaints are rare and the bare repository pattern.

The email makes two key documentation suggestions:
1. Adding guidance in `git worktree add`'s command description to explicitly discourage in-tree worktrees, as this is where users would naturally look for such advice
2. Better documenting the bare repository + worktrees pattern, noting that while obvious to Git experts, it's not clear to documentation readers

Michal emphasizes the disconnect between what's obvious to Git internals experts versus what users encounter in the documentation. The thread has largely settled on documentation improvements rather than behavior changes, with this email reinforcing that direction while suggesting specific locations for the new guidance.

The technical context remains:
- Worktree directories appear as untracked in status output
- Nested worktree creation is a common user pitfall
- Bare repositories prevent nesting issues by lacking a primary worktree
- Shell prompt performance constraints limit status behavior changes

This moves the discussion toward concrete documentation locations rather than debating design philosophy, with Michal advocating for more explicit warnings in the `git worktree add` command docs and clearer explanation of the bare repository pattern.
