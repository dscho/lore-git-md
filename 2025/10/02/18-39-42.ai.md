This is the second patch in a documentation series improving `git worktree` usage examples, specifically addressing side-by-side branch checkouts from bare repositories. The patch adds an example showing how to create multiple worktrees from a bare clone, with each worktree representing a different branch.

The key technical points from the discussion:
- The example originally showed creating a bare repository named `.git` within a directory, which Junio Hamano noted could be ambiguous (is it a non-bare clone or a bare repo with worktrees?)
- The revised version now demonstrates two patterns:
  1. Bare-centric approach: Using `project.git` naming convention for the bare repo with worktrees added via `--git-dir`
  2. Primary-worktree approach: Cloning into a `main` directory and adding worktrees as siblings
- The author clarifies the intended use case is long-lived worktrees per branch (rather than ephemeral topic branches), similar to some other VCS workflows

Open questions from this exchange:
- Whether to keep both approaches in the documentation or focus on one
- How to clearly communicate the tradeoffs between bare-centric and primary-worktree patterns
- The philosophical debate about whether all worktrees should be "equal" or if a primary worktree is preferable

The patch remains documentation-only, modifying `Documentation/git-worktree.txt` to add this example section. It builds on prior feedback about repository naming conventions and continues the thread's theme of improving worktree usability through better documentation rather than behavior changes.
