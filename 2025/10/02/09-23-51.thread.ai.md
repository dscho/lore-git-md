Interactive add bug report and interface discussion summary:

Ulrich Windl reported a regression in `git add --interactive` hunk selection behavior in Git 2.51.0 where the "J" (join) command would reprocess decided hunks incorrectly after mixed "y"/"n" responses. The bug was in `add-patch.c`'s `patch_update_file()` function handling hunk state transitions during join operations.

René Scharfe submitted fixes addressing two issues: First, modifying `patch_update_file()` to properly skip decided hunks (marked with `UNDECIDED_HUNK`) when rolling over. Second, fixing the `permitted` bitmask system by moving it into the hunk processing loop scope. The changes included three test cases covering hunk rollover and command validation scenarios.

Junio Hamano's latest response raises deeper questions about navigation behavior, identifying inconsistencies between forward ('J') and backward ('K') hunk movement. Key technical issues under discussion:
1. Current implementation handles forward rollover (hunk_index >= file_diff->hunk_nr) but lacks equivalent wrap-around for negative hunk_index
2. Use of size_t for hunk_index complicates negative value handling
3. Semantic differences between 'J' (may need all hunks) vs 'j' (should skip decided hunks)
4. Missing wrap-around logic when moving to last hunk from first hunk with 'K'

Phillip Wood previously reviewed the patches, raising concerns about array bounds safety and test redundancy that René addressed. The discussion has evolved to focus on interface design, with Junio and René refining terminology around hunk state transitions.

Technical details requiring attention:
- `UNDECIDED_HUNK` state handling in `patch_update_file()`
- `permitted` bitmask scope and flag management (`ALLOW_SPLIT`, `ALLOW_GOTO_*`)
- Navigation consistency between commands (j/k vs J/K vs y/n/e)
- size_t vs signed integer for hunk_index
- Test coverage for wrap-around scenarios
- Documentation accuracy for hunk state transitions

The fixes are technically sound for immediate integration, but the discussion reveals broader interface questions needing resolution:
1. Whether to support wrap-around navigation intentionally
2. How to handle backward navigation edge cases
3. Distinguishing "view all hunks" (J/K) from "next undecided hunk" (j/k) behaviors
4. Formalizing hunk state reversion mechanism
5. Addressing inability to revisit decisions after all hunks are marked

The thread demonstrates careful analysis of both immediate regression and underlying architectural issues in the interactive add command system, with clear paths forward for both urgent fixes and longer-term interface improvements. Junio's latest input expands the scope to include navigation symmetry and type safety considerations.
