Interactive add bug report and fix summary:

Ulrich Windl reported a regression in `git add --interactive` hunk selection behavior in Git 2.51.0 where the "J" (join) command would incorrectly reprocess already-decided hunks after mixed "y"/"n" responses. The bug was in `add-patch.c`'s `patch_update_file()` function handling hunk state transitions during join operations.

René Scharfe submitted a fix patches addressing two distinct issues: First, modifying `patch_update_file()` to properly skip decided hunks (marked with `UNDECIDED_HUNK`) when rolling over to the next undecided hunk. Second, fixing the `permitted` bitmask system that controls command availability (split, navigation) by moving it into the hunk processing loop scope to ensure reset between evaluations. The changes include three test cases: join-first and join-after-accept scenarios for the hunk rollover fix, plus a new test verifying rejection of invalid commands on unsplittable hunks.

Phillip Wood (interactive add maintainer) reviewed the initial patch, raising concerns about array bounds safety and test redundancy that René addressed through detailed technical explanations. Junio C Hamano identified the deeper architectural issue with the `permitted` bitmask, noting it accidentally enabled useful wrap-around navigation behavior that might warrant preserving as a feature.

Key technical details:
- `UNDECIDED_HUNK` state handling in `patch_update_file()`
- `permitted` bitmask scope change affecting `ALLOW_SPLIT` and `ALLOW_GOTO_*` flags
- Three test scenarios covering hunk rollover and command validation
- Architectural debt from 2019 C rewrite of interactive add

The fixes are technically sound and ready for integration, though the discussion suggests potential follow-up work to intentionally support wrap-around navigation if desired. The thread demonstrates careful analysis of both immediate regression and underlying architectural issues in the interactive add command system.
