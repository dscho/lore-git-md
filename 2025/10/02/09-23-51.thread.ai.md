Interactive add bug report and interface discussion summary:

Ulrich Windl reported a regression in `git add --interactive` hunk selection behavior in Git 2.51.0 where the "J" (join) command would reprocess decided hunks incorrectly after mixed "y"/"n" responses. The bug was in `add-patch.c`'s `patch_update_file()` function handling hunk state transitions during join operations.

René Scharfe submitted fixes addressing two issues: First, modifying `patch_update_file()` to properly skip decided hunks (marked with `UNDECIDED_HUNK`) when rolling over. Second, fixing the `permitted` bitmask system by moving it into the hunk processing loop scope. The changes included three test cases covering hunk rollover and command validation scenarios.

Phillip Wood reviewed the patches, raising concerns about array bounds safety and test redundancy that René addressed. Junio C Hamano identified deeper architectural issues with the `permitted` bitmask, noting it accidentally enabled useful wrap-around navigation behavior that users now rely on.

The discussion has evolved to focus on interface design and documentation improvements. Junio and René are refining terminology around hunk state transitions, agreeing that describing commands as "leaving hunks undecided" is misleading since they preserve prior decisions rather than resetting to undecided. They highlight two interface limitations: no direct way to revert a hunk to undecided state, and no way to revisit decisions after all hunks in a file are marked.

Technical details requiring attention:
- `UNDECIDED_HUNK` state handling in `patch_update_file()`
- `permitted` bitmask scope and flag management (`ALLOW_SPLIT`, `ALLOW_GOTO_*`)
- Navigation consistency between commands (j/k vs y/n/e)
- Test coverage for three specific scenarios
- Documentation accuracy for hunk state transitions

The fixes are technically sound and ready for integration, but the discussion suggests follow-up work to:
1. Intentionally support wrap-around navigation
2. Review other interactive add commands for similar issues
3. Improve documentation of movement capabilities, distinguishing "next hunk" (J/K) from "next undecided hunk" (j/k)
4. Consider formalizing the hunk state reversion mechanism
5. Address the inability to revisit decisions after all hunks are marked

The thread demonstrates careful analysis of both immediate regression and underlying architectural issues in the interactive add command system, with clear paths forward for both the urgent fixes and longer-term interface improvements. The latest discussion reveals how bugfixes can uncover deeper design questions about expected versus actual behavior in long-standing features.
