This is a maintainer workflow discussion in the ongoing thread about Git patch review practices. Junio C Hamano provides more detail on his personal review methodology, clarifying that his approach is actually more nuanced than simply always applying patches first. He explains that experience with the codebase allows him to triage patches into three categories:

1. Small, obviously correct patches that can be reviewed directly in email
2. Medium-sized changes where having the target code open in another window suffices
3. Complex series that require full application and examination with Git tools like `git log -p` with wider context or `git show` for full file inspection

Junio notes that while the third case isn't daily occurrence, it's common enough to be part of his regular workflow. This expands on his earlier statement about patches being just a transmission medium, showing how he actually uses a spectrum of review techniques depending on change complexity. The response directly addresses Henrique Soares' follow-up question about whether maintainers always apply patches first, providing concrete examples of when different approaches are appropriate.

Key technical details include:
- Use of `git log --reverse -p` for examining applied patch series
- Context expansion flags like `-W` and `-U8` for deeper changes
- `git show` for viewing full file states at specific revisions
- The triage system based on patch complexity and maintainer familiarity

This email doesn't introduce new tools but rather provides insight into the decision-making process of an experienced maintainer when choosing review methods. It complements the earlier tool-focused discussion (b4, mutt scripts) with a more philosophical perspective on review heuristics.
