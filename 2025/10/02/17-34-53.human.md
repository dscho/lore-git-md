This is a discussion about the design approach for reference validation in Git, specifically whether to use a standalone `git refs verify` command or extend `git fsck` with subsystem-specific options.

Junio C Hamano responds to Patrick Steinhardt's justification for a separate `git refs verify` command by drawing a distinction between two types of verification needs. He agrees that having isolated verification entry points is useful for development and debugging, but questions whether they all need to be exposed as separate end-user commands. 

The key point of contention is whether reference verification should follow the pattern of other subsystem-specific verify commands (commit-graph, multi-pack-index) or whether these checks should be exposed through `git fsck` with specific flags (like `--refs-only`). Hamano notes that while bundle verification makes sense as a standalone command (since bundles exist independently of repositories), other subsystems like refs and commit-graphs are repository-bound and don't necessarily need separate user-facing commands.

This discussion represents an architectural decision point in the ongoing work to centralize reference validation. While the technical solution (validating refs in `split_symref_update()`) is agreed upon, the user interface question remains open. The exchange shows thoughtful consideration of Git's command design patterns and the balance between developer needs and end-user interface simplicity.
