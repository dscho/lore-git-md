This thread began with Ulrich Windl reporting a regression in `git add --interactive`'s hunk selection behavior in Git 2.51.0, specifically around the "J" (join) command incorrectly reprocessing decided hunks. René Scharfe submitted fixes addressing both the immediate bug in `patch_update_file()` and issues with the `permitted` bitmask system, with Phillip Wood and Junio Hamano providing review feedback. The discussion revealed that the bugfix uncovered deeper interface design questions, particularly around navigation behaviors that users have come to rely on, like wrap-around hunk cycling and indirect hunk reversion through splitting.

The latest email focuses on refining the interface documentation and terminology. Junio and René are working to clarify the semantics of the j/J/k/K navigation commands, noting that the current description of "leaving hunks undecided" is misleading since the commands actually preserve prior decisions rather than resetting them. They're proposing updated documentation that better distinguishes between moving to the "next hunk" versus "next undecided hunk." The discussion also highlights two interface limitations: the inability to directly revert a hunk to undecided state and the lack of a way to revisit decisions after all hunks in a file are marked.

While the technical fixes are ready for integration, the thread has evolved into a broader conversation about improving the interactive add interface's clarity and addressing these newly recognized limitations. The participants are taking care to preserve useful behaviors that emerged accidentally while making the interface more intuitive through better documentation.
