Ulrich Windl reported a regression in Git 2.51.0 where `git add --interactive`'s hunk joining ("J" command) would incorrectly reprocess already-decided hunks. René Scharfe submitted a fix for this in `add-patch.c`, modifying `patch_update_file()` to properly skip decided hunks during join operations. Phillip Wood, the interactive add maintainer, reviewed the patch and raised concerns about array bounds safety and test redundancy, which René addressed by clarifying the bounds protection and explaining how the two test cases serve distinct purposes - one catching the regression scenario and another verifying core functionality.

Junio C Hamano has now weighed in, confirming René's fix is correct for the immediate issue but identifying a deeper architectural problem in the command permission system. The `permitted` bitmask that controls available commands (like split 's') isn't properly reset between hunk evaluations, causing commands to remain available when they shouldn't be. This dates back to the 2019 C rewrite of the interactive add code. Interestingly, Junio notes this bug accidentally created a useful feature - allowing wrap-around navigation with 'j/J' even when not explicitly offered - which might be worth preserving while fixing the underlying issues.

The thread shows the original hunk-joining bug is effectively resolved, but has uncovered broader interactive add issues that may require follow-up work. The permission system bugs affect multiple commands and have existed since the C conversion, suggesting careful consideration will be needed to fix them without breaking any accidentally-useful behaviors.
