This is a discussion about the design philosophy for `git replay`'s output format, building on the recently finalized atomic reference updates implementation.

Kristoffer Haugsbakk suggests modeling `git replay`'s output after `git-for-each-ref`'s flexible `--format` system rather than its current command-oriented approach. The key points are:

1. The email draws parallels between `git replay`-each-ref's single-purpose output design (just ref data) and what `git replay` fundamentally does (outputting old-to-new commit mappings).

2. It proposes that a format-based approach could better support client-side workflows needing to:
   - Feed data to `post-rewrite` hooks
   - Handle custom reflog messages
   - Integrate with `git update-ref`'s various input modes

3. The suggestion implies this would make the command more composable by letting users build their own pipelines from the fundamental data rather than baking specific behaviors into `git replay` itself.

This comes as a late-stage design suggestion after the thread had largely settled on implementation details. While the atomic update functionality itself isn't questioned, Haugsbakk raises a philosophical point about command design that could influence future iterations. The email doesn't propose specific code changes but rather suggests rethinking the output model to better align with Git's Unix-style composability principles.

The suggestion appears well-intentioned but may be too late for the current series, given the extensive review cycle already completed. It also doesn't address the server-side use case that drove much of the atomic update work. However, the core idea about format flexibility could merit consideration for future enhancements to `git replay`'s interface.
