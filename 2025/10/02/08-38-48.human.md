This is a documentation-focused follow-up in the ongoing discussion about git-worktree behavior and UX. Michal Suchánek responds to Junio Hamano's interpretation of why complaints about worktree "noise" in status output are rare, suggesting that users simply avoid nested worktrees rather than tolerating the output.

The key new point is a concrete documentation suggestion: adding guidance in the `git worktree add` command description to explicitly recommend against creating worktrees inside the main worktree. Michal notes this is the natural place users would look for such advice, rather than in the examples Junio referenced earlier.

The email also reinforces Eric Sunshine's earlier point about documenting the bare repository + worktrees pattern, with Michal emphasizing that this workflow (which naturally prevents nesting issues) isn't obvious to users who only read the official docs. The exchange highlights a gap between what Git experts consider "obvious" and what actually needs explicit documentation for typical users.

This continues the thread's shift from debating behavior changes to focusing on documentation improvements, with Michal providing specific suggestions about where and how to add guidance that could prevent common pitfalls.
