This is a continuation of the cherry-pick tracking discussion, with Junio Hamano clarifying Git's historical design philosophy around cherry-picks versus merges. Hamano emphasizes that Git's current cherry-pick trailer format (recording just the source SHA-1) was designed for public same-project workflows like Linux kernel maintenance, where both original and cherry-picked commits exist in the same repository. He argues the preference for merges over cherry-picks is technical rather than ideological - merges create explicit history links that tools can follow, while cherry-picks create implicit relationships that are harder to track.

Hamano pushes back against the characterization that Git lacks "well-integrated support" for trunk-based development, suggesting the real need is better tooling to help developers choose correct fork points and manage merge-up/merge-down workflows. He expresses skepticism about adding metadata to track cherry-pick relationships, calling such links "vague" and "ill-defined" compared to Git's native parent-child commit relationships.

The email reinforces the core tension in the thread: whether to extend Git's core to better support distributed cherry-pick workflows (as proposed by others) versus maintaining Git's original design focused on explicit history structure. Hamano's position leans toward the latter, while acknowledging room for tooling improvements within that model.
