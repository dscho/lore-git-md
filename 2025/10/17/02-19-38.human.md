This is a bug report about `protocol.file.allow` not being honored when set locally. The reporter demonstrates that while `--global` configuration for this setting works as expected (allowing file:// protocol access), the same setting with `--local` fails to override the default security restriction. The issue occurs when trying to add or update submodules using local file paths, which Git blocks by default for security reasons. The reporter specifically wants to enable file:// access only for certain repositories via local config, but the current behavior forces them to either use global config (less secure) or find workarounds.

The bug appears in Git 2.39.5 through at least 2.51.1, suggesting it's a longstanding issue rather than a regression. The security implications are noted - file:// protocol is disabled by default for good reason, but the inability to make granular exceptions via local config creates an unnecessary all-or-nothing choice for users who need this functionality in specific repositories. 

The report is well-structured with clear reproduction steps and version information, making it easy to verify. This looks like a legitimate bug in Git's config precedence handling for protocol restrictions, affecting users who need to work with local submodules while maintaining secure defaults.
