Bugfix targeting commit-graph handling with alternate object stores.

This report documents a segmentation fault that occurs when using commit-graphs with repositories that have alternates configured. The issue manifests when a repository cloned with `--reference` tries to update its commit-graph after the referenced repository's commit-graph files have been removed or become inaccessible. Instead of gracefully handling the missing files, Git crashes with a SIGSEGV when trying to write tree hashes from a NULL pointer.

The backtrace shows the crash occurs in `write_graph_chunk_data()` when processing commit data, specifically when trying to write tree hashes. The reporter provides detailed reproduction steps involving two clones (one normal, one with alternates) and shows how the alternate-enabled clone fails after 14 days when upstream changes have occurred. The commit-graph chain files show different states between the normal and alternate-enabled repositories.

The reporter suggests two potential solutions: either have Git detect and handle missing commit-graphs from alternates by rebuilding the graph from scratch, or warn users that commit-graphs don't work well with alternates and recommend disabling `fetch.writeCommitGraph` in repositories used as alternates. The bug appears in Git 2.43.0 and affects Linux systems with glibc 2.39.

Key technical details for future reference:
- Crash occurs in `write_graph_chunk_data()` when `tree` is NULL
- Involves interaction between commit-graphs and alternate object stores
- Related to `fetch.writeCommitGraph` configuration
- Backtrace shows the failure chain from `cmd_fetch` through commit-graph writing functions
- Reporter provides specific commit-graph chain file contents showing the divergence between normal and alternate-enabled repos
