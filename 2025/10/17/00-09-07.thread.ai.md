Thread identity: Regression report for `git diff --quiet` behavior in v2.51.1, originating from Jake Zimmerman. Thread type: bug report.

Core problem: `git diff --quiet HEAD` incorrectly produces output for newly staged files in v2.51.1 when it should remain silent as documented, violating the `--quiet` flag's explicit requirement to "Disable all output of the program." The regression stems from commit b55e6d36eb ("diff: ensure consistent diff behavior with ignore options").

Current status: Jeff King (Peff) has implemented and Junio C Hamano strongly endorses a conservative fix redirecting output to /dev/null when `diff_from_contents` is active in quiet mode, restoring pre-regression behavior. The solution modifies `diff_flush` to force /dev/null output with `DIFF_FORMAT_NO_OUTPUT` while maintaining exit status checking. A new test case in t4035 verifies the fix using `diff-tree -w`. Junio suggests this approach may make `diff_flush_patch_quietly()` redundant in future.

Key technical details:
- Affects `builtin/diff.c` and `diff.c` handling of `--quiet` flag
- Regression occurs when comparing HEAD to index with newly staged files
- Original change triggered content-level diffs via `diff_from_contents` breaking quiet mode
- Solution forces /dev/null output via `DIFF_FORMAT_NO_OUTPUT` in `diff_flush`
- External diff programs correctly handle quiet mode via `cmd.no_stdout`
- Test coverage added via t4035
- Johannes Schindelin identified potential gaps in `run_diff_cmd()` for unmerged paths
- Most other unchecked `o->file` uses appear benign but warrant review

Open questions:
- Future removal of `diff_flush_patch_quietly()` if new approach proves sufficient
- Need for additional guarding in `run_diff_cmd()` for unmerged paths
- Whether to expand test coverage to other diff scenarios before merging
- Potential broader simplifications in diff output control system
