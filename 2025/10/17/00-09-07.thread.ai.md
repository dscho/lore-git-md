Thread identity: Regression report for `git diff --quiet` behavior in v2.51.1, originating from Jake Zimmerman. Thread type: bug report.

Core problem: `git diff --quiet HEAD` incorrectly produces output for newly staged files in v2.51.1 when it should remain silent as documented, violating the `--quiet` flag's explicit requirement to "Disable all output of the program." The regression stems from commit b55e6d36eb ("diff: ensure consistent diff behavior with ignore options").

Current status: Jeff King (Peff) has implemented a conservative fix redirecting output to /dev/null when `diff_from_contents` is active in quiet mode, restoring pre-regression behavior. A new test case in t4035 verifies the fix. Johannes Schindelin's analysis confirms the fix's core mechanism but identifies potential gaps in coverage, particularly around `run_diff_cmd()`'s handling of unmerged paths.

Key technical details:
- Affects `builtin/diff.c` and `diff.c` handling of `--quiet` flag
- Regression occurs when comparing HEAD to index with newly staged files
- Original change triggered content-level diffs via `diff_from_contents` breaking quiet mode
- Jeff's solution modifies `diff_flush` to force /dev/null output with `DIFF_FORMAT_NO_OUTPUT`
- External diff programs correctly handle quiet mode via `cmd.no_stdout`
- Test coverage added via t4035 using `diff-tree -w`
- Johannes identifies remaining concerns in `run_diff_cmd()` for unmerged paths where `o->file` is used without `dry_run` check
- Most other unchecked `o->file` uses appear benign but warrant review

Open questions:
- Whether to merge current fix as stopgap or wait for more comprehensive solution
- Need for additional guarding in `run_diff_cmd()` for unmerged paths
- Potential impact on optimization opportunities from original change
- Whether to expand test coverage to other diff scenarios
