This is a technical discussion about the `ObjectID` struct implementation in the ongoing SHA-1/SHA-256 interoperability patch series, specifically addressing FFI considerations between C and Rust code.

The email responds to Patrick Steinhardt's suggestion about using a Rust enum for `ObjectID` representation. Brian m. carlson explains that while an enum would provide better type safety in pure Rust code, it cannot be used for FFI boundary because it wouldn't be compatible with C code that needs to cast to/from this type. The current implementation uses a struct with a `u32` algorithm field and fixed-size hash array (`[u8; GIT_MAX_RAWSZ]`) specifically to maintain FFI compatibility.

Key technical points:
- The discussion confirms the FFI constraints that prevent using Rust enums at the boundary
- The current implementation is explicitly designed as a transitional solution until all C code using this type can be removed
- The exchange highlights the tension between Rust's type safety ideals and practical FFI requirements in this interoperability work

This email reinforces the design decisions made in patch 4/14 of the series while leaving open the possibility of migrating to a more Rust-idiomatic enum-based approach in the codebase's future evolution.
