Technical discussion about Rust hasher implementation details in the SHA-1/SHA-256 interoperability series.

This email from brian m. carlson responds to Patrick Steinhardt's review comments on patch 11/14, which introduces Rust functionality for hashing objects. The discussion focuses on two main aspects of the `Hasher` implementation:

1. **Safe vs unsafe hashing**: The author explains the distinction comes from Taylor's prior work, where "safe" hashing uses SHA-1-DC (for security) while "unsafe" can use faster algorithms when processing trusted data (like self-generated packfiles). They agree to defer this distinction until actually needed.

2. **Hasher initialization pattern**: The current implementation uses separate `alloc()` and `init()` calls rather than a combined `git_hash_new()`. The author notes this provides flexibility for resetting hash state later, but is open to switching if reviewers prefer the combined approach.

The email also acknowledges two minor issues to fix in v2: missing documentation for the `Hasher` struct and consideration of the initialization pattern. This continues the series' pattern of refining FFI boundary details while maintaining the core approach of wrapping C hash functionality in Rust.

Key technical points:
- References `git_hash_sha1_init_unsafe` as precedent for performance/security tradeoff
- Current `Hasher` design uses `*mut c_void` for context pointer
- Open question about whether to keep separate alloc/init or switch to combined `git_hash_new`
- Builds on prior hash algorithm abstraction work in earlier patches

The discussion remains focused on implementation choices rather than fundamental design, suggesting the core approach has consensus while details are being worked out. This patch appears to be proceeding smoothly through review with only minor adjustments needed.
