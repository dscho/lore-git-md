This is a design discussion about worktree support in `git refs migrate`, continuing the thread on ref storage format migration.

Patrick Steinhardt responds to Junio Hamano's questions about two key aspects of the worktree migration implementation. First, regarding mixed backends (reftable for main repo + files for worktrees), Patrick explains this would require backwards-incompatible changes to how `extensions.refStorage` works across worktrees, and while the idea has merit, the current implementation doesn't support it without significant rework.

Second, on the UX question of automatically switching to the main worktree when migration is run from a linked worktree, Patrick expresses concern this might surprise users by silently affecting the main repository's refs. He suggests keeping the current behavior where the command explicitly fails when run from a linked worktree, as this makes the scope clearer.

The discussion also touches on documentation wording, with Patrick maintaining his position that the "known limitations" section should be removed now that worktree support exists, while Junio sees the main-worktree requirement as still constituting a limitation worth documenting. This exchange shows the patch series is nearing maturity but still has some design decisions to resolve around user expectations and documentation.
