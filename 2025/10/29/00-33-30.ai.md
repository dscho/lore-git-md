This is a technical discussion in the ongoing SHA-1/SHA-256 interoperability patch series, specifically addressing the representation of hash algorithms at the Rust/C FFI boundary in patch 3/14.

The email responds to Patrick Steinhardt's suggestion to use a Rust enum (via bindgen) rather than a `uint32_t` for representing hash algorithms in the FFI interface. brian m. carlson explains that using an enum would cause problems because Git sometimes zero-initializes object IDs, which would lead to undefined behavior in Rust when an enum is set to an invalid value (zero not being a valid enum variant). This reinforces the earlier consensus that `uint32_t`/`u32` is the correct FFI-safe choice for this interface.

The discussion highlights a key constraint in the FFI design - the need to maintain compatibility with Git's existing object initialization patterns while ensuring Rust safety guarantees. This exchange further solidifies the technical rationale behind the current implementation approach in the series, where hash algorithms are represented as simple integers at the FFI boundary rather than more type-safe Rust enums.

The response also hints at future patches in the series that will demonstrate the practical implications of this design choice, suggesting the zero-initialization issue has broader consequences for the object ID handling implementation.
