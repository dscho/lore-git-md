This is a technical discussion in the ongoing SHA-1/SHA-256 interoperability patch series, specifically addressing the object mapping format design. Junio C Hamano responds to brian m. carlson's patch introducing a new binary loose object map format.

The key points center around clarifying terminology and considering legacy format support. Junio notes initial confusion about the term "loose object format" being used to describe the object ID mapping mechanism rather than the traditional zlib-deflated object storage format. He questions whether maintaining support for reading the legacy ASCII-based `loose-object-idx` mapping format is worthwhile if there's no ongoing need to write it.

The discussion touches on the mapping file's purpose - storing bidirectional correspondences between object IDs in the primary and compatibility hash algorithms when `compatObjectFormat` is in use. The legacy format uses simple newline-delimited pairs of hexadecimal hashes, while the new binary format (introduced in this patch series) offers more efficient storage and lookup.

Junio raises the practical consideration of whether to drop legacy format reading support if maintaining it carries any implementation cost, suggesting the team evaluate whether backward compatibility is truly needed. This continues the thread's pattern of refining technical details while the core approach of implementing the mapping in Rust remains accepted.
