This is a technical discussion about the hash algorithm representation in the ongoing SHA-1/SHA-256 interoperability work, specifically addressing patch 3/14 in the series introducing Rust infrastructure.

Patrick Steinhardt responds to brian m. carlson's explanation about using `uint32_t` rather than Rust enums for representing hash algorithms at the FFI boundary. The core issue is that zero-initialization requirements for `object_id` structures would cause undefined behavior with Rust enums, since they require valid discriminants. While Patrick acknowledges that adding an "uninitialized" enum variant is theoretically possible, he agrees with brian that this would make the API cumbersome to use throughout the codebase.

The exchange confirms the technical rationale behind the current approach in the series, where hash algorithms are represented as `uint32_t`/`u32` across the FFI boundary rather than using Rust's enum types. This maintains safety while accommodating the zero-initialization requirements of Git's object storage layer. The discussion appears to reach consensus on this implementation detail, with Patrick's follow-up reinforcing rather than challenging the design choice.

This email doesn't introduce new technical alternatives or objections, but rather provides additional context about why the enum approach would be problematic in practice, supporting the series' current direction.
