This is a discussion about Git's release process in response to test failures on NonStop systems. Randall Becker (rsbecker@nexbridge.com) weighs in on Kristoffer Haugsbakk's suggestion to introduce release candidates for maintenance releases.

Randall expresses a preference for keeping maintenance releases focused strictly on fixes rather than new functionality, arguing that significant changes should go through main releases with proper release candidates. He acknowledges that critical fixes (like CVEs) might sometimes require breaking changes, but suggests these should be rare exceptions rather than the norm.

The discussion stems from recent issues in Git v2.51.1 and v2.51.2, including the NonStop test failures that were already addressed via a `TEST_SHELL_PATH` workaround. While the technical issue is resolved, the conversation has shifted to broader questions about release engineering practices.

Randall's position appears more conservative than Kristoffer's proposal, advocating for tighter constraints on maintenance releases rather than adding more process overhead. The exchange highlights ongoing tensions between release stability and quality assurance in Git's maintenance workflow.
