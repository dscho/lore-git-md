This is a technical discussion about type choices in the ongoing SHA-1/SHA-256 interoperability work, specifically addressing the representation of hash algorithms at the C/Rust FFI boundary.

The email responds to Junio C Hamano's concern about inconsistent use of `uint32_t` versus `int` in the codebase. Brian m. carlson argues for using fixed-size types (`uint32_t` etc.) in structure definitions and FFI boundaries, reserving `int`/`unsigned` only for loop counters and other purely C-internal uses. They justify this by pointing to past problems caused by size assumptions (like Windows compatibility issues and 1GiB file size limits in diff code) and Rust's preference for explicit sizing.

The discussion is part of patch 3/14 in a series introducing Rust infrastructure for hash algorithm interoperability. While the immediate context is about hash algorithm representation, the subtext is establishing good practices for the project's first major Rust integration. The exchange shows healthy technical debate about balancing pragmatism (the current `uint32_t` choice works fine for the immediate need) with long-term codebase consistency.
