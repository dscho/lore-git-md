This is a discussion about UX design for the `git refs migrate` command's worktree support, focusing on whether the main-worktree requirement should be enforced or automatically handled.

Patrick Steinhardt responds to Kristoffer Haugsbakk's concerns about the user experience of requiring `git refs migrate` to be run from the main worktree. While acknowledging the UX friction, Patrick explains the technical constraints that led to this design: the current architecture assumes uniform ref storage format across all worktrees (via `extensions.refStorage`), making per-worktree migration impossible without breaking backward compatibility. He notes this could be revisited with significant refactoring of worktree ref handling.

The discussion reveals differing perspectives on user expectations: Kristoffer argues commands should behave consistently regardless of worktree context (like `git gc`), while Patrick points out subtle existing worktree-specific behaviors in reference maintenance. Patrick is open to relaxing the main-worktree requirement if consensus emerges that repository-wide operations from secondary worktrees are acceptable, though he initially favored explicit user awareness of the operation's scope.

Key technical points mentioned include the challenges of atomic multi-worktree migrations and the hypothetical benefits of per-worktree ref formats for migration robustness. The thread shows movement toward resolving the UX concern while maintaining the established technical constraint of uniform ref storage formats.
