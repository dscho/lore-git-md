This is a philosophical discussion about Git workflow practices, specifically addressing the merge-vs-rebase debate. Junio Hamano (Git maintainer) responds to Mark Bauermeister's suggestion of an anti-merge-commit campaign by taking a balanced stance.

Hamano acknowledges that both extremes - excessive merge commits and constant rebasing - are problematic. He notes that while pointless back-merges into feature branches are wasteful, constant rebasing can be worse as it hides integration history and may result in less-tested code being merged. The key suggestion is that developers should make occasional trial merges to test compatibility with upstream changes, but shouldn't necessarily keep these in the final history.

The response maintains Git's neutral position on workflow preferences while gently pushing back against absolutist positions. Hamano's perspective as the project maintainer carries weight, though he frames this as advice about developer education rather than prescribing any particular workflow. The discussion continues the thread's theme of workflow philosophy without introducing technical changes to Git itself.
