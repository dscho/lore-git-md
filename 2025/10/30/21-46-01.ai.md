This is a follow-up in the ongoing discussion about Git maintenance releases and NonStop platform testing issues. Randall Becker provides additional context about why NonStop issues weren't caught earlier despite existing CI infrastructure. 

The key technical detail is that NonStop's Jenkins-based CI system has significant latency - each test run requires over a day to complete, leading to a 2-3 week backlog when tracking frequent commits. This explains why the shell compatibility issues (previously discussed in the thread) weren't detected before the v2.51.2 release. The test failures only became apparent when the problematic changes reached the maintenance release before the weekly CI cycle could catch them.

Randall confirms that Jeff King's `TEST_SHELL_PATH=/bin/bash` workaround has resolved the immediate test failures, and notes this specific issue wasn't present in v2.51.1. The email provides important operational context about the challenges of maintaining real-time testing coverage on NonStop systems due to resource constraints, which helps explain the earlier discussion about whether maintenance release candidates would be practical or effective.

This response doesn't introduce new technical problems but rather fills in the background about NonStop's testing limitations that led to the original issue going undetected. It supports Junio Hamano's earlier position that additional pre-release steps might not help given existing testing bottlenecks, while also showing the specific constraints NonStop contributors face in keeping up with development changes.
