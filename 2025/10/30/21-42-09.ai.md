This is a follow-up in the ongoing SHA-1/SHA-256 interoperability patch series, specifically addressing memory allocation at the Rust FFI boundary. The email resolves an open question from the thread about whether to use `malloc()` or Git's `xmalloc()` for allocating hash contexts exposed to Rust.

The author (brian m. carlson) agrees with Junio C Hamano's observation that `xmalloc()` would be more consistent with Git's conventions, and commits to changing the implementation accordingly. The rationale given is that while Rust handles its own allocations and panics on OOM, the FFI boundary code should maintain Git's standard practices.

This change affects patch 09/14 in the series, which exposes hash context functions to Rust. The specific function being modified is `git_hash_alloc()`, which will now use `xmalloc()` instead of plain `malloc()`. This aligns with the thread's broader discussion about FFI boundary safety and consistency, though it doesn't fundamentally alter the technical approach to hash algorithm interoperability.

The resolution of this point helps narrow the open questions in the thread, though several other design decisions remain ongoing (library linking strategy, Hasher naming, object map format documentation, etc.). This change demonstrates the careful attention being paid to FFI boundary details in this first major Rust integration for Git.
