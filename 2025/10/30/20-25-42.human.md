This is a discussion about Git's release process, specifically whether maintenance releases should have release candidates. Kristoffer Haugsbakk had previously suggested introducing release candidates for maintenance releases after some issues were found in Git v2.51.2 on NonStop systems. 

Junio Hamano responds by questioning the value of this approach, pointing out that 'master' already serves as a continuous test bed where changes must first pass through 'next'. He notes that issues like the NonStop shell divergence should ideally be caught during normal development on 'master' or 'next', and expresses skepticism that those not testing 'master' would test maintenance candidates either.

Haugsbakk concedes Junio's point, agreeing that he is "probably 99.9% likely to be correct" about the limited value of maintenance release candidates. The exchange highlights the tension between wanting more testing for stable releases and the practical realities of Git's development workflow, where 'master' is meant to serve as the primary testing ground.

The discussion builds on the earlier resolved issue about NonStop test failures while shifting focus to broader release engineering questions. Junio's response provides the maintainer perspective on why additional pre-release steps for maintenance versions may not be as effective as some contributors might hope.
