This is a discussion response in the ongoing documentation patch thread about removing the `git diff X..Y` syntax in Git 3.0. Brian m. carlson raises strong objections to the proposed change, arguing it would break many existing scripts and forges, and expresses concern about the potential for future reintroduction with different semantics.

The response makes several key technical arguments: (1) the change would impact long-term support distributions that might skip versions, leading to inconsistent behavior when the syntax is later reintroduced; (2) Git has historically avoided changing revision-related syntax meanings; and (3) the breakage would be widespread enough to warrant keeping the current behavior permanently. The email references the specific scenario of distros moving from Git 2.51 to 3.xx as particularly problematic.

This introduces a significant new perspective in the thread, moving beyond Junio's implementation concerns to question the fundamental premise of the change. The argument centers on backward compatibility risks rather than the syntax's current confusing nature that motivated the original proposal. The response suggests this might be a case where Git is "stuck with" the current behavior forever due to its widespread use.
