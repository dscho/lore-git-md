Refactoring patch in Taylor Blau's repack modularization series (tb/incremental-midx-part-3), continuing the systematic extraction of repack functionality into dedicated modules. This is patch 21/49 in v2 of the series.

The patch factors out the pack installation logic from `cmd_repack()` into a new `generated_pack_install()` function. This handles the complex process of moving newly created pack files from their temporary location to their final destination, including:

- Adjusting file permissions before rename
- Handling missing optional extensions
- Cleaning up unneeded extension files
- Error checking for required extensions

The extraction follows the series' pattern of moving functionality out of `builtin/repack.c` in preparation for making it part of the repack API. The commit message notes this is groundwork step for future API exposure. The implementation maintains all existing behavior while improving code organization.

This continues the series' focus on:
1) Modularizing repack functionality
2) Establishing clear API boundaries
3) Maintaining behavior during refactoring
4) Following established naming conventions (using `generated_pack_` prefix)

The change is mechanical and low-risk, affecting only the internal structure of the repack command while keeping all external behavior identical. It builds on previous patches that standardized the `generated_pack` naming (patch 20/49) and moved related infrastructure out of the builtin.
