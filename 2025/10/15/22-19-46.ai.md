Junio C Hamano responds to Martin von Zweigbergk's documentation patch proposing removal of the `git diff X..Y` syntax in Git 3.0. While expressing general agreement with the principle that the current behavior is misleading (showing a two-dot diff when the syntax suggests a range diff), Hamano raises practical concerns about implementation readiness.

The key technical point is Hamano's observation that the patch only documents the planned removal without providing the actual code changes protected by a `WITH_BREAKING_CHANGES` macro, which he considers necessary for such a backward-incompatible change. This suggests the patch is incomplete from an implementation perspective despite being conceptually sound.

Hamano acknowledges the historical context - that the current behavior resulted from reusing the revision range parser rather than implementing a dedicated diff parser - but cautions that "real life may bite us back," hinting at potential backward compatibility issues not yet addressed in the proposal. The response maintains the thread's focus on preparing for Git 3.0 while introducing new considerations about how breaking changes should be technically implemented.
