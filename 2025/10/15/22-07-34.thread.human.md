Martin von Zweigbergk proposed removing the misleading `git diff X..Y` syntax in Git 3.0, where it currently shows a two-dot diff while appearing to suggest a range diff. His initial patch added documentation about this planned breaking change in BreakingChanges.adoc, positioning it as preparation for the major version bump.

Junio Hamano responded with general agreement about the syntax being confusing but raised important practical concerns. While conceptually sound, the patch lacks the necessary implementation details - notably, the actual code changes protected by a `WITH_BREAKING_CHANGES` macro that Hamano considers essential for backward-incompatible changes. He acknowledged the historical context (the current behavior stems from reusing the revision range parser) but cautioned about unaddressed backward compatibility risks, suggesting "real life may bite us back." The discussion now needs to address both the conceptual agreement about the syntax problem and the practical considerations around implementation strategy for Git 3.0.
