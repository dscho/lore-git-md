This thread discusses a proposed breaking change for Git 3.0 regarding the potentially confusing `git diff X..Y` and `X...Y` syntax. Martin von Zweigbergk originally suggested removing the double-dot notation, with Justin Tobler expanding the proposal to include triple-dot notation as well. The core issue is that these syntaxes reuse revision range notation while behaving differently in `git diff` versus other commands.

Junio Hamano has raised important implementation constraints, particularly how the triple-dot notation is used in `git checkout` for fork points. brian m. carlson strongly opposes the change due to compatibility concerns, while Kristoffer Haugsbakk suggests following Git's typical deprecation patterns rather than immediate removal. D. Ben Knoble has now entered the discussion, supporting the removal of double-dot notation while noting it wouldn't conflict with his planned revset work.

In the latest email, D. Ben Knoble offers concrete alternatives to address Junio's concerns. He proposes using `git diff --merge-base X Y` as an existing documented replacement for the triple-dot syntax, and suggests new notation like `X^{M-Y}` for merge-base operations that could work across commands. He also highlights the semantic mismatch where `git diff X...Y` and `git log X...Y` show different information despite using similar syntax.

The discussion continues to explore how to balance syntax cleanup with backward compatibility, whether to use a deprecation period, and how to coordinate changes across multiple commands. The thread has evolved from focusing solely on `git diff` to considering broader implications for Git's revision syntax, with participants weighing both technical constraints and user experience concerns.
