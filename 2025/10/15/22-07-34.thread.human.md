This thread discusses a proposal to remove the potentially confusing `git diff X..Y` syntax in Git 3.0, where it currently shows a two-dot diff but could be misinterpreted as showing a range diff (like `git diff $(git merge-base X Y) Y`). Martin von Zweigbergk originally proposed documenting this planned breaking change, which Junio C Hamano conceptually agreed with while noting the patch needed actual code changes protected by a `WITH_BREAKING_CHANGES` macro.

The discussion has now taken a significant turn with brian m. carlson's strong objections. He argues the change would break many existing scripts and forges, particularly for long-term support distributions that might skip versions. His core concern is that Git has historically avoided changing revision-related syntax meanings, and the breakage would be so widespread that we might be effectively "stuck with" the current behavior permanently. This introduces substantial new considerations beyond Junio's initial implementation concerns.

The thread now has agreement that the current syntax is confusing but diverging views on whether and how to change it - with Martin proposing removal, Junio wanting proper gating for backward compatibility, and brian m. carlson arguing the change may be too disruptive to make at all. The path forward remains unclear, with open questions about implementation approach and the real-world impact on existing usage.
