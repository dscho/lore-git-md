This thread discusses a proposed breaking change for Git 3.0 regarding the `git diff X..Y` syntax, which currently shows a two-dot diff but could be misleading as it doesn't match the range diff semantics users might expect. Martin von Zweigbergk originally proposed removing this syntax to allow for potential future reintroduction with more intuitive behavior matching `git diff $(git merge-base X Y) Y`.

The discussion has revealed differing perspectives. Junio C Hamano agrees with the motivation but noted the initial patch was incomplete, lacking the actual code changes protected by a `WITH_BREAKING_CHANGES` macro. In response, Martin clarified this was meant as a discussion starter and expressed willingness to implement the macro protection in a v2 patch. He also revealed additional motivation - preparing for potential future revset-like functionality similar to Mercurial or Jujutsu (jj), though he's not volunteering to implement that feature.

However, brian m. carlson has raised strong objections about backward compatibility impacts, arguing the change would break many existing scripts and forges, particularly for long-term support distributions moving from Git 2.51 to 3.xx. The thread has now shifted from implementation details to a fundamental debate about whether the change should proceed at all, with brian arguing Git may need to keep the current behavior permanently due to widespread use. The discussion remains unresolved, with open questions about concrete compatibility impacts and whether this type of syntax change is appropriate for a major version bump.
