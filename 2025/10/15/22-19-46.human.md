This is a reply in the ongoing discussion about deprecating the misleading `git diff X..Y` syntax. Junio C Hamano responds to Martin von Zweigbergk's initial documentation patch that proposed removing this syntax in Git 3.0.

Junio expresses general agreement with the principle behind the change, acknowledging that the current behavior (where `X..Y` shows a two-dot diff rather than the expected range diff) resulted from historical implementation shortcuts. However, he raises a practical concern about real-world impact and notes the patch isn't yet ready for merging because it lacks accompanying code changes protected by a `WITH_BREAKING_CHANGES` macro.

The response maintains the thread's focus on preparing for Git 3.0 while introducing a new technical requirement for implementing breaking changes. Junio's feedback suggests this will need both documentation and code changes to properly stage the deprecation, though he doesn't reject the core proposal. The discussion remains open about how to handle backward compatibility and migration impacts.
