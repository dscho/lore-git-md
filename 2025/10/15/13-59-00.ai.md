This is a follow-up discussion in the ongoing patch-id hash algorithm configuration thread, raising concerns about plumbing commands and configuration variables.

Kristoffer Haugsbakk questions the wisdom of adding configuration variables to plumbing commands like `git patch-id`, arguing that such commands should avoid configuration state since they're primarily used in scripts. They express a preference for explicit command-line options (like `--stable`) over configuration variables to avoid potential issues with scripts relying on configuration state.

The email directly responds to Junio Hamano's earlier message outlining the configuration approach, which proposed two potential configuration variables (one for fallback behavior outside repositories, one for overriding the automatic choice) alongside a command-line option. While not rejecting the overall solution, Haugsbakk's intervention introduces a new dimension to the discussion: the principle that plumbing commands should minimize configuration dependencies.

This raises important questions about the patch-id implementation strategy:
- Should plumbing commands indeed avoid configuration variables as a general rule?
- How to balance script reliability concerns with the convenience of persistent configuration for patch-id's hash algorithm?
- Whether the command-line-first approach (already endorsed by Junio) sufficiently addresses these concerns without needing configuration variables at all.
