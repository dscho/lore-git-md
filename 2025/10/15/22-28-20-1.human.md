Documentation patch proposing breaking change for `git diff X..Y` syntax, now receiving pushback on compatibility concerns.

Brian m. carlson raises significant objections to Martin von Zweigbergk's proposal to remove the `git diff X..Y` syntax in Git 3.0. While the thread previously saw conceptual agreement about the syntax being misleading, carlson argues the change would break many existing scripts and forges, particularly given the syntax might later be reintroduced with different semantics.

The key concern is backward compatibility - carlson notes Git has historically avoided changing revision-related syntax meanings, and suggests we're effectively "stuck with" the current behavior forever. They paint a vivid scenario where long-term support distros upgrading from Git 2.x to 3.x would face semantic changes if the syntax were later reintroduced differently.

This moves the discussion from implementation details (previously focused on whether to use `WITH_BREAKING_CHANGES`) to questioning whether the change should happen at all. The objection comes from a maintainer perspective focused on real-world impact rather than conceptual purity, suggesting the proposal may face stiffer resistance than initially anticipated. The thread now appears to be at a tension point between cleaning up confusing interfaces and maintaining backward compatibility.
