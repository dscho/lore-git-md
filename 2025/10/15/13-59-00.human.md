This is a follow-up discussion in the ongoing patch-id hash algorithm debate, raising questions about configuration design for plumbing commands.

Kristoffer Haugsbakk questions the need for configuration variables in `git patch-id`, arguing that plumbing commands should avoid config state since they're primarily used in scripts. They express a preference for explicit `--stable` command-line options over config variables, noting this prevents scripts from accidentally depending on configuration state.

The email responds to Junio Hamano's earlier suggestion of having both command-line options and configuration variables for hash algorithm selection in patch-id functionality. While the thread has largely converged on this configurable approach, Haugsbakk's comment introduces a valid architectural concern about keeping plumbing commands configuration-free where possible.

This raises an interesting tension between the flexibility of config-based solutions (which the thread had been moving toward) and the purity of stateless plumbing commands. The discussion may need to address whether patch-id's use cases justify breaking from typical configuration-free plumbing conventions, or if command-line options alone would suffice.
