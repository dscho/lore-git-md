Maintainer clarification on `git bundle` design intent and usage patterns. Junio C Hamano responds to Andrew Harmon's confusion about bundle cloning behavior by explaining the feature's original purpose and how it deliberately mirrors standard Git remote cloning semantics.

The email reinforces that `git bundle` was specifically designed to enable repository transfer when network cloning isn't possible, with behavior that intentionally parallels regular remote operations. Junio notes that while remote-tracking branches can be included in bundles (as Andrew demonstrated), their handling during cloning follows Git's conservative default fetch behavior - just as with network clones, users must explicitly request remote refs if needed.

Junio suggests two key insights: (1) the behavior Andrew observed is working as designed to maintain consistency with Git's standard cloning model, and (2) the `--mirror` clone option provides the complete repository copy functionality Andrew seems to want. The response is thorough but maintains the thread's conclusion that no behavior change is needed - the solution lies in better understanding (and potentially better documenting) the existing mechanisms.
