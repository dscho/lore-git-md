Post-merge discussion on tag verification behavior in refs backend.

Jialuo raises a thoughtful question about the handling of corrupted tags in Patrick Steinhardt's recently merged refs series. The series (specifically patch 12/14) changed how backends store peeled object IDs, now skipping storage when tag verification fails rather than storing potentially bogus data. 

Jialuo suggests this might be too lenient - since corrupted tags indicate repository corruption that `git fsck` would catch, perhaps the code should fail more aggressively by either reporting an error or dying outright. The current behavior could give users a false sense that everything is fine when there's actually underlying corruption.

This is a nuanced design question about error handling philosophy - whether to be permissive (let broken but partially usable state persist) or strict (fail fast on corruption). The thread shows no immediate response yet, but given the series is already merged, any change would likely need to come as a follow-up patch. The discussion touches on core Git reliability concerns while acknowledging the technical correctness of the merged solution.
