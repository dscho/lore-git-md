Security proposal for preventing arbitrary code execution in untrusted repositories (RFC). Core issue: Git executes user-defined code (hooks, core.pager, etc.) without verification when operating on any repository, creating security risks. Original proposal involved per-user secret tokens stored in `~/.gitsecret`, copied during `git init`/`git clone` and verified before executing user-defined code, with a new `git allow` command for manual approval of existing clones. Author has a 150-line bash prototype and proposed phased migration.

Brian Carlson critiques the token approach, identifying flaws: inherits problems from Git's per-user security model (breaking containers/shared repos), creates token pollution in containers, and remains vulnerable to token copying attacks. Proposes alternative design using config-based allowlists (`[safe]` section) to explicitly permit specific config options and hooks, with `includeIf` for selective enabling. This shifts focus from repository provenance to execution permissions.

Key technical details include token storage format vs config allowlist syntax, verification hooks placement, and backward compatibility. Open questions now span three dimensions: (1) Taylor Blau's submodule trust propagation concern (unaddressed in latest response); (2) Randall Becker's enterprise token format extensibility (unaddressed); (3) New architectural tension between token-based (Michael) and config-based (Brian) approaches, with Brian's critique emphasizing container pollution and copyable secret weaknesses. The silent migration strategy remains unexamined in this exchange.
