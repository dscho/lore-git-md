Security proposal for preventing arbitrary code execution in untrusted repositories (RFC). Core issue: Git executes user-defined code (hooks, core.pager, etc.) without verification when operating on any repository, creating security risks. Original proposal involved per-user secret tokens stored in `~/.gitsecret`, copied during `git init`/`git clone` and verified before executing user-defined code, with a new `git allow` command for manual approval of existing clones. Author had a 150-line bash prototype and proposed phased migration.

Brian Carlson critiqued the token approach, identifying flaws: inherits problems from Git's per-user security model (breaking containers/shared repos), creates token pollution in containers, and remains vulnerable to token copying attacks. Proposed alternative design using config-based allowlists (`[safe]` section) to explicitly permit specific config options and hooks, with `includeIf` for selective enabling. This shifts focus from repository provenance to execution permissions.

Taylor Blau clarified their earlier submodule concern, focusing instead on nested bare repositories - the token system would need to ignore parent repository tokens in nested scenarios to maintain security, requiring manual approval and thus not fully eliminating trust prompts as originally claimed. Michael Lohmann confirmed the security model for submodules - each would need its own signed token in its `.git/modules/` subdirectory, with `--recursive` potentially automating this signing.

Michael Lohmann responded to Brian's critique, proposing modifications to the token model: environment variable (`GIT_ALLOW=true`) and CLI flag (`--allow`) as opt-out mechanisms for container/shared repo scenarios, per-user token files (rather than shared global secret) to mitigate token copying attacks, and floated idea of revocable individual tokens. Raised question about how current `.git` exposure differs from token exposure risk. Acknowledged Brian's config allowlist approach as "interesting" without fully engaging with its advantages.

Jeff King (Peff) structured the security problem into two phases: (1) defining "unsafe" behavior (skipping repo-level config, disabling hooks in untrusted contexts), referencing prior discussion about maintainability as key concern; (2) safety marking mechanisms, suggesting simpler alternatives like environment variables (`GIT_ASSUME_UNSAFE`) or config-based safe directories (similar to `safe.directories`). Proposed these as opt-in features initially, with commands like `git-prompt` using `--assume-unsafe` flags, allowing gradual adoption before considering default behavior changes. Emphasized practical experience before committing to any marking scheme.

Michael Lohmann's synthesis email clarified the current security model (marking repositories as safe through ownership or `safe.directories` config) and identified four discussion threads: (1) token-based approach as automated `safe.directories` population; (2) temporary overrides via flags/environment variables; (3) softening enforcement to warnings; (4) removing owner-based safety assumption. Noted path-based safety vulnerabilities when repositories move, while tokens could automate safe marking but inherit path-based issues. Agreed with Jeff King that defining unsafe behavior should precede safety marking mechanisms, though saw these as separable concerns.

Key technical details include token storage format vs config allowlist syntax, verification hooks placement, and backward compatibility scenarios. Open questions: (1) Taylor's nested bare repo constraints on token design; (2) Randall Becker's enterprise token format concerns; (3) Architectural tension between token-based and config-based approaches; (4) Silent migration strategy; (5) Submodule handling implementation details; (6) Relative risk of current `.git` exposure vs token exposure; (7) Viability of revocable tokens; (8) Jeff King's phased implementation approach and whether it resolves the token-vs-config debate. The thread remains at a design decision point between fundamentally different security models, with Jeff King's pragmatic path forward that could unblock implementation while maintaining security goals. No maintainer has yet indicated preferred direction.
