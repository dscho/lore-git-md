Security proposal for preventing arbitrary code execution in untrusted repositories (RFC). Core issue: Git currently executes user-defined code (hooks, core.pager, etc.) without verification when operating on any repository, creating security risks. Proposed solution involves per-user secret tokens stored in ~/.gitsecret, copied during `git init`/`git clone` and verified before executing user-defined code. New `git allow` command would manually approve existing clones. Filesystem-based trust mechanism designed to maintain existing functionality while blocking malicious repos. Author has working 150-line bash prototype and proposes phased migration: silently add tokens in a minor release before making verification mandatory in Git 3.0. Open questions: migration strategy acceptability, particularly silent token addition assumption that most active clones would update before enforcement. Technical details include token storage format, verification hooks placement, and backward compatibility considerations. Proposal references real-world vulnerabilities but silent migration aspect may prove controversial among maintainers.
