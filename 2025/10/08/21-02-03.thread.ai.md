Security proposal for preventing arbitrary code execution in untrusted repositories (RFC). Core issue: Git currently executes user-defined code (hooks, core.pager, etc.) without verification when operating on any repository, creating security risks. Proposed solution involves per-user secret tokens stored in ~/.gitsecret, copied during `git init`/`git clone` and verified before executing user-defined code. New `git allow` command would manually approve existing clones. Filesystem-based trust mechanism designed to maintain existing functionality while blocking malicious repos. Author has working 150-line bash prototype and proposes phased migration: silently add tokens in a minor release before making verification mandatory in Git 3.0. Taylor Blau raised concerns about submodule trust propagation, questioning whether tokens would be copied to recursively cloned submodules - if not, users would still need manual verification for submodules, potentially undermining the security benefits. This exposes a gap in the original claim to maintain all existing functionality while improving security. Open questions now include both the original migration strategy acceptability (particularly silent token addition) and the newly identified submodule trust propagation issue. Technical details needing clarification include token storage format, verification hooks placement, backward compatibility, and now specifically the system's behavior with recursive submodule clones. Proposal references real-world vulnerabilities but both the silent migration aspect and submodule handling may prove controversial among maintainers.
