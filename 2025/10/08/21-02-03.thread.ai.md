Security proposal for preventing arbitrary code execution in untrusted repositories (RFC). Core issue: Git executes user-defined code (hooks, core.pager, etc.) without verification when operating on any repository, creating security risks. Original proposal involved per-user secret tokens stored in `~/.gitsecret`, copied during `git init`/`git clone` and verified before executing user-defined code, with a new `git allow` command for manual approval of existing clones. Author has a 150-line bash prototype and proposed phased migration.

Brian Carlson critiques the token approach, identifying flaws: inherits problems from Git's per-user security model (breaking containers/shared repos), creates token pollution in containers, and remains vulnerable to token copying attacks. Proposes alternative design using config-based allowlists (`[safe]` section) to explicitly permit specific config options and hooks, with `includeIf` for selective enabling. This shifts focus from repository provenance to execution permissions.

Taylor Blau clarifies their earlier submodule concern, focusing instead on nested bare repositories - the token system would need to ignore parent repository tokens in nested scenarios to maintain security, requiring manual approval and thus not fully eliminating trust prompts as originally claimed. Michael Lohmann confirms the security model for submodules - each would need its own signed token in its `.git/modules/` subdirectory, with `--recursive` potentially automating this signing.

Michael Lohmann now responds to Brian's critique, proposing modifications to the token model: environment variable (`GIT_ALLOW=true`) and CLI flag (`--allow`) as opt-out mechanisms for container/shared repo scenarios, per-user token files (rather than shared global secret) to mitigate token copying attacks, and floats idea of revocable individual tokens. Raises question about how current `.git` exposure differs from token exposure risk. While acknowledging Brian's config allowlist approach as "interesting", doesn't fully engage with it or address its core advantages over tokens.

Key technical details include token storage format vs config allowlist syntax, verification hooks placement, and backward compatibility scenarios. Open questions now span: (1) Taylor's nested bare repo constraints on token design; (2) Randall Becker's enterprise token format concerns (unaddressed); (3) Architectural tension between token-based (Michael) and config-based (Brian) approaches, with Brian's critique emphasizing container pollution and copyable secret weaknesses; (4) Silent migration strategy remains unexamined; (5) Submodule handling implementation details and recursive signing implications; (6) New questions about relative risk of current `.git` exposure vs token exposure; (7) Viability of revocable tokens as mitigation. The thread remains at a design decision point between fundamentally different security models, with the token approach evolving but still facing core challenges identified by Brian's critique. No maintainer has yet indicated preferred direction.
