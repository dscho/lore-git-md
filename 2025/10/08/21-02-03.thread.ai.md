Security proposal for preventing arbitrary code execution in untrusted repositories (RFC). Core issue: Git executes user-defined code (hooks, core.pager, etc.) without verification when operating on any repository, creating security risks. Original proposal involved per-user secret tokens stored in `~/.gitsecret`, copied during `git init`/`git clone` and verified before executing user-defined code, with a new `git allow` command for manual approval of existing clones. Author has a 150-line bash prototype and proposed phased migration.

Brian Carlson critiques the token approach, identifying flaws: inherits problems from Git's per-user security model (breaking containers/shared repos), creates token pollution in containers, and remains vulnerable to token copying attacks. Proposes alternative design using config-based allowlists (`[safe]` section) to explicitly permit specific config options and hooks, with `includeIf` for selective enabling. This shifts focus from repository provenance to execution permissions.

Taylor Blau clarifies their earlier submodule concern, focusing instead on nested bare repositories - the token system would need to ignore parent repository tokens in nested scenarios to maintain security, requiring manual approval and thus not fully eliminating trust prompts as originally claimed. This surfaces additional implementation constraints for the token approach.

Key technical details include token storage format vs config allowlist syntax, verification hooks placement, and backward compatibility scenarios. Open questions now span: (1) Taylor's nested bare repo constraints on token design; (2) Randall Becker's enterprise token format concerns (unaddressed); (3) Architectural tension between token-based (Michael) and config-based (Brian) approaches, with Brian's critique emphasizing container pollution and copyable secret weaknesses; (4) Silent migration strategy remains unexamined. The thread remains at a design decision point between fundamentally different security models, with the token approach accumulating edge case constraints while the config alternative presents its own tradeoffs. No maintainer has yet indicated preferred direction.
