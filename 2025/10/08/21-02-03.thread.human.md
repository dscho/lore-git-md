This thread explores a security proposal to prevent arbitrary code execution when working with untrusted Git repositories. The core issue is that Git currently executes user-defined code (hooks, pagers, etc.) from any repository without verification, creating potential security risk. The original proposal suggested per-user secret tokens stored in `~/.gitsecret` that would be copied during `git init`/`git clone` and verified before executing user-defined code.

Discussion has revealed significant challenges with the token approach, particularly around container usage and shared repositories. Brian Carlson proposed an alternative config-based allowlist system that would explicitly permit specific config options and hooks. Meanwhile, Taylor Blau and Michael Lohmann have examined edge cases around nested repositories and submodules.

Jeff King (Peff) has now entered the conversation with a structured approach, separating the problem into two phases: first defining what "unsafe" behavior should entail (like skipping repo-level config and disabling hooks in untrusted contexts), and then determining how to mark repositories as safe. He suggests simpler alternatives to the token system, such as environment variables or config-based safe directories, and advocates for an opt-in initial implementation to gather real-world experience before committing to any particular marking scheme.

The thread remains at a design crossroads between the original token proposal (now being modified in response to feedback) and alternative approaches like Brian's config allowlist and Peff's simpler marking mechanisms. Key open questions include handling of nested repositories, submodule security, and whether to prioritize a comprehensive solution versus incremental improvements. No maintainer has yet indicated a preferred direction, but Peff's pragmatic approach may help move the discussion toward actionable next steps while preserving the core security goals.
