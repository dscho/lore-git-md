This thread explores security measures to prevent arbitrary code execution when working with untrusted Git repositories. The original proposal by Michael suggests a token-based system where repositories would carry cryptographic tokens from `~/.gitsecret` to verify trust, with a `git allow` command for manual approval. The approach aims to reduce trust prompts but has drawn significant technical critiques.

Brian Carlson raised fundamental concerns about the token model, particularly its incompatibility with containerized environments and shared repositories. He proposed an alternative config-based allowlist system that would explicitly permit specific hooks and config options, shifting focus from repository provenance to execution permissions. This has created a design fork in the discussion.

Taylor Blau has refined their earlier concern about submodules, now focusing on nested bare repositories. They note that the token system would need to ignore parent repository tokens in nested scenarios to maintain security, meaning users would still need manual approval in these cases - a usability tradeoff the original proposal didn't account for. Meanwhile, Randall Becker's questions about enterprise token formats and the silent migration strategy remain unaddressed.

The thread now presents two distinct architectural approaches (token-based vs config-based) with unresolved questions about container compatibility, nested repositories, and enterprise needs. No maintainer has yet indicated a preferred direction, leaving core design questions open while surfacing additional constraints on the token-based path. The discussion remains active with competing proposals on the table.
