This thread discusses a security proposal to prevent arbitrary code execution when working with untrusted Git repositories. The core issue is that Git currently execute user-defined code (hooks, pagers, etc.) without verification, which malicious repositories could exploit.

The proposal introduces a per-user secret token stored in ~/.gitsecret that would be copied into new repositories during init/clone. Git would verify this token before executing any user-defined code, aborting if missing. This would maintain existing functionality for legitimate repositories while protecting against malicious ones. The author suggests a phased rollout: silently adding tokens in a minor release before making verification mandatory in Git 3.0.

Key aspects include a new `git allow` command for manually approving existing clones and a filesystem-based trust mechanism. The author has implemented a 150-line proof-of-concept and seeks feedback on balancing security benefits against migration challenges, particularly around the silent migration strategy which assumes most active clones would be updated before the breaking change. The proposal is well-researched with references to real vulnerabilities, though the silent migration aspect may prove controversial.
