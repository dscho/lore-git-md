This is a maintainer clarification about `git bundle` behavior in an ongoing thread about remote ref handling during cloning from bundles.

Junio C Hamano provides additional context about the design philosophy behind `git bundle`, emphasizing its original purpose as a network-less alternative to cloning. He explains that the current behavior (where remote-tracking branches aren't fetched by default) intentionally mirrors Git's standard remote cloning semantics - the bundle acts as a transport mechanism that preserves the same fetch behavior as a network clone would.

The email offers two key technical clarifications: First, that the bundle creation itself is working correctly (Andrew's bundle contains all refs as expected with `--all`). Second, that the clone operation's selective fetching of only local branches is by design, matching how Git handles remote clones. Junio suggests using `git clone --mirror` against the bundle file as the proper way to achieve a complete repository copy, analogous to mirror cloning from a remote.

This response reinforces the thread's established position that the behavior is intentional, while acknowledging that Andrew's use case might represent an unanticipated scenario. The email provides concrete guidance about mirror cloning from bundles while maintaining that the current behavior aligns with Git's core design principles for repository transfer operations.
