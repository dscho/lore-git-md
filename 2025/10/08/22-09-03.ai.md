This is a security proposal follow-up addressing nested repository concerns. Michael Lohmann responds to Taylor Blau's clarification about nested bare repositories (not submodules as previously misstated) in the ongoing discussion about preventing arbitrary code execution in untrusted repositories.

Michael confirms the security model for submodules - each would need its own signed token in its `.git/modules/` subdirectory, with `--recursive` potentially automating this signing. This maintains the proposal's core security invariant where every repository operation requires explicit user approval via token verification.

The exchange surfaces an important implementation detail: the token system must handle nested repository structures while preventing automatic inheritance of parent repository credentials, as that would undermine the security model. Michael's response suggests the design would treat each repository (including submodules) as an independent security domain requiring separate approval.

This continues the architectural tension between the token-based approach (requiring per-repository secrets) and Brian Carlson's config-based alternative (using allowlists). The submodule handling illustrates how the token model scales to complex repository structures while maintaining its verification requirements, though at the cost of additional secret management complexity.
