Security proposal for preventing arbitrary code execution in untrusted repositories.

This RFC proposes a security mechanism to prevent arbitrary code execution when interacting with untrusted Git repositories, while maintaining all existing functionality. The core issue is that Git currently executes user-defined code (hooks, core.pager, etc.) without verification when operating on any repository, which can be exploited by malicious repositories.

The proposed solution involves generating a per-user secret token stored in ~/.gitsecret, which gets copied into new repositories during `git init` or `git clone`. Before executing any user-defined code, Git would verify the presence of this token, aborting if missing. This would protect against attacks where users accidentally interact with malicious repositories, while maintaining seamless operation for legitimate use cases.

The proposal acknowledges migration challenges, suggesting a phased approach where a future minor release could silently add tokens to existing clones before making the check mandatory in Git 3.0. The author has implemented a proof-of-concept as a 150-line bash wrapper and provides links to background information and attack demonstrations.

Key technical details include:
- New secret token storage in ~/.gitsecret
- Token verification before hook/config execution
- New `git allow` command for manual approval of existing clones
- Filesystem-based trust mechanism

The author seeks feedback on balancing security benefits against migration pain, particularly around the silent migration strategy which assumes most active clones would be updated before the breaking change in Git 3.0. The proposal appears well-researched with references to real-world vulnerabilities and a working prototype, though the silent migration aspect may prove controversial.
