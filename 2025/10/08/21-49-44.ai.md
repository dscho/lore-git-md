This is a follow-up in the security proposal thread about preventing arbitrary code execution in untrusted repositories. Taylor Blau corrects and clarifies their earlier submodule-related concern, focusing now on nested bare repositories rather than submodules.

The key technical point is that the proposed token-based security mechanism would need to explicitly not respect tokens from parent repositories in nested bare repo scenarios, otherwise it would fail to provide security guarantees. This leads to a usability tradeoff - users would still need to manually approve such repositories rather than having automatic trust via the token system.

The email doesn't introduce new design alternatives but sharpens the discussion around edge cases in the token-based approach, particularly regarding repository nesting. It highlights that some user interaction would remain necessary even with the token system, contrary to the original proposal's claim of eliminating most trust prompts. The thread remains at an architectural crossroads between token-based and config-based approaches, with this exchange surfacing additional implementation constraints for the token path.
