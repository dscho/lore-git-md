This thread centers on a 5-patch series (v2) introducing cbindgen support for Rust-C interoperability in Git, focusing on automated header generation and verifying varint implementation consistency between Rust and C. The discussion has evolved to address three interconnected challenges: build system integration, version policy decisions, and project structure planning.

The core issue is a circular dependency where libgit.a needs generated C headers that require built Rust code which itself depends on libgit.a. Ezekiel Newren has now proposed splitting cbindgen into a separate Cargo workspace crate as the only viable solution, arguing this structural change must happen now rather than later. This would require developers to run cargo before make/meson during local development, though CI could pre-generate headers to avoid build-time penalties.

Version compatibility remains contentious. While Patrick Steinhardt has shown new openness to versions beyond Rust 1.49 due to gccrs progress, Brian M. Carlson strongly opposes 1.49 due to platform support limitations, advocating instead for 1.63 to enable LLVM-based toolchains. Newren's latest email reveals tight constraints - newer cbindgen versions require Rust 1.68.0+, while version 1.49 can only use cbindgen 0.1.0, with 1.63 requiring dependency overrides that become increasingly fragile for older versions.

Junio Hamano is following the technical implications closely, while Toon Claes has raised concerns about technical debt from the proposed header organization. The thread now awaits Carlson's promised patch proposing specific version policy changes, which should provide the technical justification Patrick has requested for the 1.63 target. The workspace structure proposal from Newren represents a significant architectural shift that would enable proper cbindgen integration but comes with development workflow impacts that need careful consideration.
