This is a technical discussion about conflict representation in Git's proposed extended tree format, specifically addressing how to handle merge conflicts at the commit vs. tree level.

Elijah Newren raises concerns about brian m. carlson's current proposal to represent conflicts via special "conflict tree" entries at the top level of trees. He argues this would unnecessarily penalize performance for all `git log` operations by forcing traversal of additional objects, even for users not utilizing conflict features. The performance impact comes from requiring log operations to examine not just commits but also their referenced trees to detect conflicts.

Newren advocates instead following the approach used by jj and GitButler, where conflicts are represented by multiple top-level trees (or possibly commits) referenced from the commit object itself. This keeps conflict detection at the commit level, avoiding the need to traverse additional objects during log operations. He notes this would better align with existing tools' implementations and maintain performance for non-conflict cases.

The email suggests temporarily removing conflicted tree support from the extended tree proposal, as the current approach appears misaligned with both performance requirements and existing practice from related tools. This represents a refinement of the ongoing discussion about how to balance new functionality with Git's core performance characteristics and ecosystem interoperability.

Key technical points:
- Current proposal would impact `git log` performance universally
- Alternative approach keeps conflict detection at commit level
- Alignment with jj/GitButler implementations is desirable
- Suggests deferring conflicted tree support for now
