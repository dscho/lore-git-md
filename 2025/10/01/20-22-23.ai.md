This is a discussion about worktree design philosophy and user expectations, continuing the thread about whether worktree directories should be treated as untracked in the main repository's status.

Sergey Organov challenges Junio's assumption that worktrees should have a clear primary/sibling relationship, suggesting users may expect a model where worktrees are equal peers within a single repository directory structure. He provides an example layout where worktrees are siblings under a common `.git` directory rather than having one primary worktree.

The email makes two key observations about user behavior:
1. Many users intuitively expect worktrees to be equal peers rather than having a primary worktree
2. The current `git worktree add` command allows (and even encourages) creating worktrees anywhere within the primary worktree without warning, which may lead to the problematic" nested layouts being discussed

Sergey suggests two potential improvements to the worktree creation UX:
- Automatically place new worktrees as siblings to the main worktree (in `../`)
- Require explicit confirmation when creating worktrees inside the main worktree

This continues the thread's exploration of how Git's worktree implementation aligns (or fails to align) with user expectations and workflows. The discussion now includes concrete suggestions for modifying the worktree creation interface to better guide users toward the intended directory structure patterns.
