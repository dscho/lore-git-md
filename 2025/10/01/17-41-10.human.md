This is a technical discussion about extending Git's tree format to handle mixed-hash submodules and conflict markers, building on brian m. carlson's RFC proposal. Jeff King (peff) offers alternative implementation suggestions focused specifically on the submodule case, while acknowledging the broader proposal's goals.

Peff suggests simplifying the submodule handling by using a dummy SHA-256 hash (000...1) with standard gitlink mode, rather than introducing a new mode 130000. This would make older Git versions recognize the entry as a submodule while still allowing new versions to process the mixed-hash case. He argues this degrades more gracefully when encountered by older clients.

The email raises concerns about the BER encoding in filenames from the original proposal, citing potential issues with filesystem compatibility, user confusion, and pathname parsing. Peff proposes an ASCII-based alternative format like "sha1-<hash>-path" that would be more human-readable and filesystem-friendly, though less space-optimal.

A key discussion point revolves around tree entry sorting - whether extended entries should sort by their full encoded name (potentially confusing diffs) or by their final path component (violating tree ordering for older clients). Peff leans toward accepting some display ugliness in exchange for simpler implementation, suggesting diff post-processing could clean up the output.

The email maintains a constructive tone while probing edge cases in the original design, particularly around backward compatibility and user experience. It represents an important technical dialogue about how to balance extensibility with Git's core invariants, though focuses narrowly on the submodule case rather than the broader conflict marker use case from the original RFC.
