This thread explores a proposed extension to Git's tree format to support mixed-hash submodules (where repositories using different hash algorithms reference each other) and conflict markers. The discussion originated from Contributor Summit conversations, with brian m. carlson driving the initial proposal and Jeff King (peff) now engaging with alternative approaches.

The core debate centers on two competing encoding strategies: brian's BER-like binary encoding (cleaner paths but harder to debug) versus peff's ASCII-based filename encoding (more visible but potentially uglier). There are also diverging views on whether to use mode 130000 entries or modify S_IFGITLINK with a sentinel OID for better backward compatibility.

Peff's latest contribution shifts the focus to practical challenges, revealing that the current Git implementation accidentally handles some mixed-hash cases through hash truncation/zero-padding, though this relies on undocumented behavior. He identifies two key implementation hurdles: the need to handle index entries (not just trees) and the tension between strict validation versus preserving this accidental compatibility. The discussion has narrowed to prioritize mixed-hash submodules, with conflict markers potentially deferred.

Junio C Hamano continues to guide the conversation, emphasizing the need to maintain Git's core invariants around tree ordering and object identity. While no final decision has been made, the thread has progressed from theoretical proposals to concrete implementation tradeoffs, with peff's ASCII encoding approach gaining traction due to its debuggability and backward compatibility advantages, despite some aesthetic compromises. The solution will need to address not just tree storage but also index consistency and migration from the current quasi-working state.
