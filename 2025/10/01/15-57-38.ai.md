This is a feature patch introducing a new `split` subcommand to the proposed `git-history` command, part of Patrick Steinhardt's ongoing RFC series (now at v4 with 17 patches). The subcommand simplifies splitting a single commit into two by interactively selecting which changes should move to a new parent commit.

The implementation handles several key scenarios:
- Splitting tip, root, and in-between commits
- Interactive hunk selection via the same interface as `add -p`
- Pathspec filtering to limit which files are considered
- Validation to prevent empty commits
- Preservation of original authorship and commit message conventions

Technical details include:
- New `split_commit()` function in `builtin/history.c` that:
  - Creates temporary index for staging selected changes
  - Uses modified `write_in_core_index_as_tree()` from earlier in series
  - Constructs two new commits (split-out and modified original)
- Comprehensive test suite (`t/t3452-history-split.sh`) covering:
  - Basic splitting scenarios
  - Edge cases (merge commits, empty splits)
  - Pathspec filtering
  - Worktree/index state handling

The patch follows the series' pattern of building on existing infrastructure (sequencer, add-patch) while adding focused new functionality. It maintains backward compatibility and integrates with the series' broader goal of providing Jujutsu-inspired history editing operations. The implementation appears thorough, with careful attention to edge cases and user experience considerations.
