This is a technical clarification in the ongoing Git 3.0 release planning discussion, specifically addressing SHA-256 interoperability workflows. Brian m. carlson responds to Junio C Hamano's question about handling unpublished SHA-1 work when pushing to a SHA-256-converted repository.

The email clarifies several key constraints in the current SHA-256 interoperability implementation. First, it notes there's no support yet for adding an algorithm to an existing repository (though this is a desired feature). For protocol behavior, it explains that pushes must use the server's main algorithm due to protocol v2 limitations - v2 doesn't support pushes, and v0 doesn't allow algorithm selection during push operations.

Carlson provides a workaround where users could create a SHA-256/SHA-1 clone from the server, pull changes from their SHA-1 repo, and then push to the SHA-256 server. However, they emphasize that directly pushing from SHA-1 to SHA-256/SHA-1 clones isn't currently supported. The response also makes clear that protocol v2 push support won't be added as part of this effort to avoid scope creep.

The technical details focus on algorithm handling during fetch/push operations, particularly around when object mapping occurs (client-side except for specific cases like shallows and partial clones). This continues the thread's progression from high-level planning to concrete implementation constraints, now with specific workflow limitations and workarounds documented.
