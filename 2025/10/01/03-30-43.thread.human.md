This thread explores how Git maintainers review patches, with a focus on the tools and workflows they use. It began with Henrique Soares asking about current practices, prompting responses that span historical context, tool recommendations, and maintainer philosophy. Kristoffer Haugsbakk referenced Jeff King's 2016 workflow documentation, while Konstantin Ryabitsev highlighted the `b4 shazam` tool for applying patch series. Jeff King himself offered to share updated versions of his review scripts and mutt integrations.

Junio C Hamano, Git's maintainer, established the core principle that email is merely a transmission medium - real review happens in a local Git environment using Git's native tools. In the latest exchange, Soares sought clarification on how this principle translates to practice, leading Junio to confirm it's a two-step process: first applying patches to a temporary branch or worktree, then using standard Git tools for review before returning to email for discussion. This reinforces that the actual review work should leverage Git's capabilities rather than trying to examine raw patches in email clients.

The discussion has evolved from collecting concrete tool examples to validating fundamental workflow concepts, particularly for newcomers learning Git's email-based development model. While tools like `b4` and Peff's scripts provide practical implementations, Junio's guidance emphasizes that the specific tools matter less than the principle of doing substantive review in a proper Git environment. The thread remains open to further exploration of how historical workflow documentation and modern tooling can best serve new contributors.
