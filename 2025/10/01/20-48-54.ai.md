This is a discussion about improving the user experience of `git worktree add` commands, specifically regarding the common pitfall of creating worktrees inside the primary worktree directory.

Junio Hamano responds to Sergey Organov's observation that new users often unintentionally create worktrees inside their primary worktree (rather than as sibling directories) because the command accepts any path without warning. Junio confirms this is a known UI issue, sharing that he personally always uses "../" prefixes to avoid it, and suggests potential solutions: better documentation and possibly adding warnings when users attempt to create nested worktrees.

The exchange builds on the ongoing discussion about worktree visibility in `git status` by addressing a related workflow problem - the ease of accidentally creating worktrees in suboptimal locations. This connects to earlier points about the design philosophy that treats worktrees as peer entities rather than nested components, and the challenges of communicating this model to users.

Key technical details mentioned:
- Current `git worktree add` behavior accepts any path within the primary worktree
- Common user behavior of running the command without "../" prefix
- Potential solutions: documentation improvements and/or warning messages
- The discussion suggests this could be a more productive direction than debating the core status behavior, focusing instead on preventing the problematic usage pattern through better UX.
