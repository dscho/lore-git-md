This is a technical discussion about alternative approaches to the proposed extended tree format for handling mixed-hash submodules and conflict markers. Jeff King (peff) responds to brian m. carlson's RFC with several concrete suggestions that trade off different aspects of compatibility, user visibility, and implementation complexity.

Key technical points raised:
1. Proposes using S_IFGITLINK mode with a sentinel OID (000...1) instead of mode 130000 for better backward compatibility with older Git clients, though this approach wouldn't help the conflict marker case
2. Suggests ASCII-based encoding in filenames (e.g., "sha1-<hash>-path") rather than BER encoding, citing concerns about:
   - User debuggability
   - Filesystem handling of non-UTF-8 names
   - Potential path separator conflicts
3. Explores sorting implications, considering both pathname-based sorting (which would break older clients) and prefix-based sorting (which complicates modern Git's diff display)
4. Proposes accepting some user-visible ugliness in exchange for simpler implementation, with potential post-processing in diffcore to clean up display

The discussion focuses particularly on the submodule use case, acknowledging that conflict markers might need a separate solution. Peff's suggestions aim to minimize surprises for older Git clients while keeping the implementation tractable, though they introduce new tradeoffs around name visibility and diff handling.

This represents a significant refinement of the original proposal, narrowing the scope to prioritize the mixed-hash submodule case while identifying specific pain points in the encoding and sorting design. The exchange highlights the tension between backward compatibility, clean user experience, and implementation complexity that characterizes Git's hash transition efforts.
