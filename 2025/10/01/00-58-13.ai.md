This is an RFC proposal for extending Git's tree format to support mixed-hash submodules and conflict markers, presented as a discussion starter rather than a serious implementation plan. The email comes from a discussion at the Contributor Summit about two potential needs: supporting submodules with different hash algorithms than their parent repository, and first-class conflict handling. The author proposes a "minimally incompatible" extension to the tree format that would use an extended mode type for submodules, demonstrating the concept with a shell script that creates a test repository with a specially crafted tree object.

The proposal includes a new documentation file describing the extended tree format specification, though the author makes clear this is just a prototype to gauge community reaction. The approach is intentionally "a little gross" (as acknowledged in the email) and expected to trigger `git fsck` warnings, positioning it as a boundary case to explore how far the tree format could be stretched. The author emphasizes this is not something they plan to implement properly, but rather a thought experiment to inform future design discussions about hash algorithm interoperability and conflict representation.

Key technical points for future reference: the proposal introduces a new tree entry mode (130000) that would carry additional metadata for submodules, specifically targeting the case where a submodule uses a different hash algorithm (SHA-256) than its parent (SHA-1). The shell script demonstrates creating such an entry with extended metadata following the submodule name. The documentation file (gitformat-extended-tree.adoc) would presumably detail how this format could also accommodate conflict markers, though its contents aren't shown in the email. This appears to be controversial by design, meant to provoke discussion about the limits of Git's extensibility.
