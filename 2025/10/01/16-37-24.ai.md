Git maintainer Junio C Hamano responds to Brian Carlson's extended tree format RFC with several technical questions and observations about the proposed design. The discussion focuses on implementation details of the BER-like encoding scheme for extended tree entries.

Key points raised:
- Clarification request about how the length-prefixed extended data interacts with tree entry ordering requirements (the pathname field must still sort correctly despite containing binary metadata)
- Concerns about debugability of the BER encoding scheme, suggesting it may produce hard-to-interpret binary data
- Discussion of extensibility tradeoffs, noting that while the format allows for future type-specific extensions, uncontrolled extension could lead to non-canonical representations
- Specific question about sort ordering for conflict tree entries in complex merge scenarios (criss-cross and octopus merges with multiple stage entries)

The tone remains constructive but probing, with Junio acknowledging the inherent ugliness of the approach while engaging with its details. This represents the maintainer's technical vetting of a complex proposal that would introduce new on-disk formats, with particular attention to how it interacts with Git's existing invariants around tree ordering and object identity.
