Extended RFC proposal for Git tree format modifications to support mixed-hash submodules and conflict markers, originating from Contributor Summit discussions. Author brian m. carlson has progressed from initial prototype to formal specification (`gitformat-extended-tree.adoc`), with Jeff King (peff) now driving implementation-focused refinements.

Core design considerations now span:
- Encoding strategies: BER-like binary (bit-flipped) vs peff's ASCII ("sha1-<hash>-path")
- Mode proposals: 130000 vs S_IFGITLINK with sentinel OID (000...1)
- Index representation requirements revealed by peff's experiments showing current accidental cross-algorithm compatibility through hash truncation/zero-padding
- Implementation hooks identified in `add_to_index()` for future algorithm validation
- Conflict representation approaches after Elijah Newren's performance critique

Technical tradeoffs expanded:
- BER encoding's path cleanliness vs ASCII's debuggability
- Index-to-tree vs index-to-filesystem alignment requirements
- Current undocumented hash padding behavior (SHA-256 submodules in SHA-1 repos work via truncation, vice versa via zero-padding)
- Tension between strict validation in `add_to_index()` and preserving accidental interop
- Conflict tree performance impact on `git log` vs commit-level alternatives

New implementation challenges:
- Jeff King's patch to add `oid.algo` validation in `add_to_index()` gains consensus from brian m. carlson as appropriate during transition
- Current behavior (relying on hash truncation/zero-padding) will be temporarily rejected until proper cross-algorithm support is implemented
- Submodules confirmed broken in interop mode, with fixes planned but not yet implemented
- brian m. carlson's interop testing hasn't hit this edge case yet, focusing on test repositories
- Maintainer preference for stricter validation solidifies, prioritizing data integrity over accidental compatibility

The discussion has shifted from theoretical encoding strategies to concrete migration challenges, with consensus forming around:
1. Temporarily enforcing single-hash-algorithm consistency via `add_to_index()` validation
2. Deliberately handling cross-algorithm cases in the extended tree format work rather than relying on undocumented behavior
3. Maintaining focus on proper multi-hash support implementation
4. Balancing strict validation against real-world usage patterns

Mixed-hash submodules remain primary use case, with conflict markers likely to follow jj/GitButler's commit-level pattern. The maintainer engagement continues to focus on preserving Git's core invariants while accommodating cross-algorithm scenarios, with both encoding strategies still under consideration but now informed by concrete index behavior findings, performance analysis, and maintainer input on validation requirements. The extended tree format proposal must now address:
- Tree storage format (still debating encoding strategies)
- Index consistency requirements
- Strict `add_to_index()` validation during transition
- Migration path for existing mixed-hash submodule users
- Revised approach to conflict representation that avoids performance penalties
