Extended RFC proposal for Git tree format modifications to support mixed-hash submodules and conflict markers, originating from Contributor Summit discussions. Authors brian m. carlson and Jeff King (peff) continue refining implementation constraints, now focusing on `add_to_index()` behavior for foreign-hash submodules.

Core design considerations now span:
- Encoding strategies: BER-like binary (bit-flipped) vs ASCII ("sha1-<hash>-path") vs new hybrid approach emerging from peff's experiments
- Mode proposals: 130000 vs S_IFGITLINK with sentinel OID (000...1)
- Index representation requirements refined by peff's experimental `add_to_index()` modifications showing path transformation tradeoffs
- Implementation hooks in `add_to_index()` now have concrete validation requirements including strict hash matching
- Conflict representation approaches after Elijah Newren's performance critique
- Transition period handling of undocumented SHA-256-in-SHA-1 behavior

Technical tradeoffs expanded:
- BER encoding's path cleanliness vs ASCII's debuggability vs new index/tree divergence approach
- Index-to-tree vs index-to-filesystem alignment requirements with peff's discovery of lookup ambiguity
- Current undocumented hash padding behavior (SHA-256 submodules in SHA-1 repos) now understood to require deliberate handling, with brian m. carlson advocating strict rejection
- Tension between strict validation and interop shifts toward index cleanliness as priority
- Confirmed race condition in double submodule resolution
- Transition period implications of rejecting previously-tolerated hash mismatches

Implementation status:
- Jeff King's experimental path-munging approach in `add_to_index()` revealed fundamental lookup problems
- New consensus forming to keep index clean (store real hashes) and limit transformations to tree serialization
- brian m. carlson's interop testing continues focusing on test repositories
- Maintainer preference solidified for solutions preserving index consistency
- Submodule resolution race condition identified as blocker for any implementation
- peff indicates upcoming implementation ("next week") with tests for hash validation

The discussion has progressed from encoding strategies to concrete implementation constraints, with key takeaways:
1. Index representation must remain clean and consistent, even if trees use transformed formats
2. Path transformation creates unacceptable lookup complexity in the index
3. Tree serialization becomes the logical boundary for cross-algorithm representation
4. Race conditions in submodule resolution require careful handling
5. Implementation must prioritize index integrity over syntactic convenience
6. Transition period will temporarily break undocumented SHA-256-in-SHA-1 usage

Mixed-hash submodules remain the primary use case, with implementation now constrained by:
- Index consistency requirements ruling out path transformations
- Need to handle submodule resolution races
- Tree serialization as the remaining viable transformation point
- Performance implications of any divergence between index and tree formats
- Immediate need to reject invalid hash combinations despite transition pain

The extended tree format proposal must now specifically address:
- Clean index representation with real hashes
- Tree serialization strategy (BER vs ASCII) for cross-algorithm cases
- Race-free submodule resolution
- Migration implications of index/tree format divergence
- Revised validation requirements in `add_to_index()`
- Transition plan for previously-tolerated hash mismatches
