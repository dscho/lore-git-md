Extended RFC proposal for Git tree format modifications to support mixed-hash submodules and conflict markers, originating from Contributor Summit discussions. Author brian m. carlson has progressed from initial prototype to formal specification (`gitformat-extended-tree.adoc`), with Jeff King (peff) now driving implementation-focused refinements.

Core design considerations now span:
- Encoding strategies: BER-like binary (bit-flipped) vs peff's ASCII ("sha1-<hash>-path")
- Mode proposals: 130000 vs S_IFGITLINK with sentinel OID (000...1)
- Index representation requirements revealed by peff's experiments showing current accidental cross-algorithm compatibility through hash truncation/zero-padding
- Implementation hooks identified in `add_to_index()` for future algorithm validation
- Conflict representation approaches after Elijah Newren's performance critique

Technical tradeoffs expanded:
- BER encoding's path cleanliness vs ASCII's debuggability
- Index-to-tree vs index-to-filesystem alignment requirements
- Current undocumented hash padding behavior (SHA-256 submodules in SHA-1 repos work via truncation, vice versa via zero-padding)
- Tension between strict validation in `add_to_index()` and preserving accidental interop
- Conflict tree performance impact on `git log` vs commit-level alternatives

New implementation challenges:
- Must handle both tree and index representations consistently
- Need to either formalize or reject current padding behavior
- ASCII encoding scope may expand to cover index compatibility cases
- Filesystem unpredictability favors simpler index-to-filesystem alignment
- Conflict representation must avoid performance regressions for non-conflict cases

Junio Hamano has weighed in on Jeff King's findings about the current accidental compatibility between SHA-1 and SHA-256 submodules, expressing maintainer concerns about relying on undocumented behavior. The discussion now focuses on whether to:
1. Add explicit validation in `add_to_index()` to reject incompatible hash formats (comparing `oid.algo` against repository's `hash_algo`)
2. Preserve existing workflows that rely on the accidental cross-algorithm operation
3. Handle potential conversion at the `add_to_index()` level

Elijah Newren's intervention adds a new dimension regarding conflict representation:
- Current "conflict tree" approach would degrade `git log` performance
- Suggests following jj/GitButler's commit-level conflict markers instead
- Recommends temporarily removing conflicted tree support from proposal
- Highlights need to maintain performance for non-conflict cases

The conversation has shifted from theoretical encoding strategies to concrete migration challenges, with Junio indicating preference for stricter validation unless compelling use cases emerge for preserving current behavior. This intersects with the broader extended tree format proposal, which must now address:
- Tree storage format (still debating encoding strategies)
- Index consistency requirements
- Handling of existing quasi-working edge cases
- Potential need for stricter `add_to_index()` validation
- Migration path for existing mixed-hash submodule users
- Revised approach to conflict representation that avoids performance penalties

Mixed-hash submodules remain primary use case, with conflict markers now likely to follow jj/GitButler's commit-level pattern rather than tree entries. The maintainer engagement continues to focus on preserving Git's core invariants while accommodating cross-algorithm scenarios, with both encoding strategies still under consideration but now informed by concrete index behavior findings, performance analysis, and maintainer input on validation requirements.
