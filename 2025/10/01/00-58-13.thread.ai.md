Extended RFC proposal for Git tree format modifications to support mixed-hash submodules and conflict markers, originating from Contributor Summit discussions. Author has progressed from initial prototype demonstration to formal specification with new `gitformat-extended-tree.adoc` document. 

Core proposal introduces backwards-compatible extension mechanism using mode 130000 tree entries with BER-like encoding (bit-flipped to ensure non-zero bytes) for length/type/flag fields. Two initial object types defined: conflict trees for merge representation and extended submodules for mixed-hash scenarios (e.g. SHA-256 submodule in SHA-1 parent repo). Specification includes XOR-based encoding scheme for submodule OIDs when parent/child repositories use different hash algorithms, plus criticality flags to control handling of unknown extensions.

Technical specifics: format deliberately triggers git fsck warnings in older clients while maintaining parseability, with concrete example showing SHA-256 submodule representation in SHA-1 repository. Design emphasizes minimal incompatibility - older Git versions would see entries but consider them malformed due to apparent tree sorting issues. Documentation includes full encoding details needed for potential future implementation, though current patch remains purely a specification (no code changes beyond adding doc file).

Thread maintains exploratory nature, now shifting from prototype demonstration to formal specification phase. Proposal continues to focus on informing discussions about Git's extensibility limits regarding hash algorithm interoperability and conflict representation, with no concrete implementation timeline. Key open question remains how this extension mechanism would interact with other in-flight hash transition efforts.
