Documentation and UX discussion about git-worktree placement practices. Eric Sunshine responds to Junio's suggestion about warning users against creating worktrees inside the main worktree directory.

The email makes several key points about the current state and potential changes to worktree documentation and behavior. Eric notes that the git-worktree manpage already consistently shows examples using "../" prefixes for worktree paths, suggesting the documentation may not be the issue if users are ignoring these examples. He expresses skepticism that adding a "best practices" section would help, given that users may be copying commands from external sources rather than reading official docs.

On the technical side, Eric argues against adding warnings for nested worktree creation, pointing out that many users (including experienced contributors) intentionally use this pattern without problems. He notes there's no technical limitation preventing nested worktrees - the only downside being the need to manage .gitignore entries or tolerate status output noise. The email provides evidence that this is a common practice, citing past list discussions and specific examples from prominent contributors.

Eric does suggest one concrete documentation improvement: adding coverage of the bare repository + worktrees workflow pattern, which is officially supported but not currently documented. The email maintains a neutral-to-skeptical tone about changing current behavior while acknowledging the UX concerns raised in the thread. It provides historical context about existing practices and documents the current state of the manpage examples.
