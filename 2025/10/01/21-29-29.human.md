This is a discussion about git-worktree UX and documentation, continuing the ongoing thread about worktree behavior and user expectations.

Eric Sunshine responds to Junio Hamano's suggestion about potentially warning users against creating worktrees inside the main worktree directory. He points out that the documentation already consistently shows examples using "../" prefixes, suggesting the issue may be with users not reading docs rather than insufficient guidance. 

The email makes several key points: First, that adding more documentation about "best practices" may not help if users aren't reading the existing docs. Second, that warnings against nested worktrees could annoy users who intentionally use this workflow without problems. Third, that the only downside is aesthetic (status output noise) rather than technical. 

Eric also suggests expanding documentation to cover the bare repository workflow, which is officially supported but not well-documented. The tone is pragmatic, noting that while nested worktrees might not be ideal for everyone, they work fine technically and some experienced users prefer them. This moves the discussion toward concrete documentation improvements rather than behavior changes.
