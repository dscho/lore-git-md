This is the first patch in a 3-part series introducing Message-ID tracking in Git commits, focused on modifying mailinfo.c to always collect Message-IDs from incoming patches. The change makes mailinfo.c unconditionally store the Message-ID header from emails, removing the previous conditional that only did so when add_message_id was true. This prepares for the series' goal of storing Message-IDs as commit headers rather than just trailers. The patch updates the logic in two places: collecting the Message-ID during header parsing, and checking both add_message_id and message_id when deciding whether to include it in the trailer.

The implementation is straightforward - it removes the add_message_id guard from the Message-ID collection code and adds the check to the trailer insertion logic instead. This maintains backward compatibility with existing git am -m behavior while enabling the new header-based storage approach. The change is minimal (5 lines modified) and focused entirely on mailinfo.c's email parsing logic.

This appears to be a well-scoped plumbing change that cleanly separates the concerns of collecting versus using Message-IDs. The commit message clearly explains the motivation (git-am now requires Message-IDs unconditionally) and the technical impact. No test changes are included in this patch, suggesting they'll come later in the series. The change seems unlikely to cause controversy as it doesn't affect user-visible behavior yet, just internal data collection.
