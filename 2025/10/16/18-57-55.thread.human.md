This thread proposes adding Message-ID tracking to Git commits specifically for email-based workflows like the Linux kernel, where linking commits to mailing list discussions would help automation. James Bottomley's initial three-patch series (v1) implements this by storing Message-IDs as commit headers while maintaining compatibility with existing trailer-based approaches. The discussion initially focused on clarifying how this differs from Change-ID systems, with Kristoffer Haugsbakk noting they share technical implementation but serve different purposes (email workflows vs Git-native change tracking).

Junio Hamano has now raised significant concerns about the implementation approach. He argues that storing Message-IDs in commit headers could complicate operations like rebase and cherry-pick, requiring special handling for these headers. He also questions whether the current design might break the common "format-patch | am" workflow, since format-patch output wouldn't naturally include these headers. While not opposing the feature's goal, Hamano's critique suggests the header-based storage mechanism may need rethinking to avoid workflow disruptions.

The thread now faces key questions about metadata storage - whether to persist with headers (despite the operational concerns), switch to trailers (despite the earlier distinction from Change-ID systems), or find another approach. The core use case remains valid, but the implementation path forward is uncertain pending responses to Hamano's technical objections.
