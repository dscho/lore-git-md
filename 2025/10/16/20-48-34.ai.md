Performance optimization for `git last-modified` with correctness discussion.

D. Ben Knoble responds to Toon Claes's claim that the new `git last-modified` implementation is "more correct" than the old one, pointing out that correctness should be binary rather than a spectrum. The email highlights a specific case where the old implementation produces different results from `git log --max-count=1` when run with versus without a path argument, showing the old version returning commit 5b49c1af for pkt-line.h in the no-args case versus 15df15fe when the path is specified.

Knoble speculates this might relate to maintenance branch merges being topologically earlier despite having later timestamps, but expresses uncertainty about the exact cause of the discrepancy. The exchange surfaces an important edge case for the new algorithm to handle consistently, though it's not yet clear whether this represents a bug in the old implementation or an expected difference in behavior between the two commands. The discussion continues the thread's focus on ensuring the optimized implementation matches `git log --max-count=1` behavior exactly, which has been established as the correctness benchmark.
