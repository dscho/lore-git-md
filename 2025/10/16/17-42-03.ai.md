This is a follow-up discussion in the ongoing thread about deprecating the `git diff X..Y` and `X...Y` syntax. Kristoffer Haugsbakk suggests an alternative approach to the breaking change proposal - gradual deprecation rather than immediate removal in Git 3.0.

The email notes that current Git practices typically involve a deprecation period before removal, citing `core.commentString=auto` and the reftable transition as examples where features were deprecated first. Kristoffer questions whether the double-dot and triple-dot syntax should follow this pattern rather than being slated for immediate removal in 3.0.

This introduces a new consideration to the thread's open questions - whether to balance the desire for syntax cleanup with Git's typical deprecation practices. The suggestion implies a potential middle path between Martin's original removal proposal and brian m. carlson's compatibility concerns. The email also references Martin's acknowledgment that his initial patch was meant as a discussion starter and his willingness to add the WITH_BREAKING_CHANGES macro in a v2 version.

Key technical detail is the reference to Git's existing deprecation patterns, particularly the `core.commentString=auto` case where deprecation and removal happened in the same cycle, versus other features that had longer deprecation periods. This adds a new dimension to the compatibility discussion, suggesting Git's versioning policies may need explicit consideration in the decision.
