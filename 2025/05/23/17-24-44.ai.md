Junio Hamano responds to Max Rhodin's RFC for `git-ghost` with a practical alternative approach. He suggests that `git blame` run in reverse could potentially serve similar purposes for understanding deleted code, though acknowledges the inherent difficulty in tracing removed content since it requires knowing what to look for in historical revisions. 

The response offers a concrete workflow for investigating deleted code: checking out old revisions (potentially using `git bisect` to efficiently locate the last version containing the code) and then tracing forward from there. This contrasts with the proposed `git-ghost` solution which would proactively capture deletion rationale.

Key technical points mentioned:
- The fundamental challenge of deleted content tracing (needing to know what to look for in historical revisions)
- Practical debugging workflow using `git bisect` and revision checking
- Implicit comparison between proactive metadata capture (`git-ghost`) and reactive historical investigation

The response doesn't directly critique the RFC but provides an experienced maintainer's perspective on existing tools that could address similar needs. It suggests the proposed tool's value proposition might need stronger differentiation from existing Git capabilities.
