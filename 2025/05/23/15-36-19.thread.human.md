This thread discusses a subtle bug in `git send-email` where editing or skipping the first patch in a series (when using `--in-reply-to`) causes subsequent patches to thread incorrectly. The original issue arises because the script's message numbering gets out of sync when users edit messages, particularly affecting the first patch's threading position.

Junio C Hamano identified a complication with the initial proposed fix (switching to `$num_sent` tracking) - it would break when processing patches in batches due to counter resets. Jacob Keller then raised concerns about the code clarity, questioning why message editing affects the counters at all. The latest patch from the author takes a different approach: when users skip (`n`) or edit (`e`) a message, it now decrements both the message counter and Message-ID serial number to maintain proper numbering. This avoids the batch processing issue but may still need to address Keller's maintainability concerns about the state management logic.

The discussion now centers on finding a solution that: (1) correctly maintains threading after edits, (2) properly handles batch processing edge cases, and (3) results in clear, maintainable code. While the latest patch solves the immediate technical problem, the participants may want to weigh in on whether this approach or a more fundamental refactoring would be preferable long-term.
