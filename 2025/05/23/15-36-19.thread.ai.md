Subject: git send-email threading behavior fix for edited first patch in series. Core problem: when using --in-reply-to and editing first patch, subsequent patches incorrectly thread to original target rather than first patch. Root cause: threading logic used $message_num == 1 check which fails after editing (increments $message_num). Original solution proposed replacing with $num_sent == 1 check and moving $num_sent++ before threading check. Current status: Junio C Hamano identified critical flaw in solution regarding batch processing (--batch-size) where $num_sent reset at batch boundaries would cause incorrect threading behavior for first message of each new batch. Key technical details: affects perl/git-send-email.pl threading logic when both --in-reply-to is set AND first patch is edited. Batch processing interaction introduces new complexity - solution must now handle cases where counter resets occur mid-series. Open questions: how to robustly track first-message status across batch boundaries, whether to introduce separate state tracking for threading purposes, potential performance tradeoffs of alternative approaches. Participants: original author proposed initial fix, Junio C Hamano identified batch processing edge case. Discussion now focused on finding solution that works for both single-patch editing and batch processing scenarios. Related work: no other similar counter logic identified in script yet, but batch processing interactions may require broader review of state management.
