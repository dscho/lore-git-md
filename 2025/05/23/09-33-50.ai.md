Performance optimization for the `git last-modified` command, incorporating Bloom filters to speed up revision walks. This patch builds on the v2 series implementing the new command, specifically adding Bloom filter support when available in the commit-graph.

The key technical addition is a new `maybe_changed_path()` function that checks Bloom filters before computing expensive diffs during the revision walk. When filters indicate no possible changes to tracked paths, the diff can be skipped entirely. The implementation handles Bloom filter setup via `fill_bloom_key()` during path initialization and proper cleanup with `clear_bloom_key()`. Performance measurements show dramatic improvements - from 5.1s to 0.75s in the Linux kernel repository case when using optimized builds.

The patch touches several subsystems:
- Adds Bloom filter checks to the core `last_modified_run()` logic
- Extends `last_modified_entry` struct to store Bloom keys
- Integrates with commit-graph Bloom filter settings
- Maintains backward compatibility when filters aren't available
- Includes proper memory management for Bloom filter resources

This appears to be a well-integrated optimization that builds on Taylor Blau's prior Bloom filter work while fitting cleanly into the existing `last-modified` architecture. The performance gains are substantial and the implementation follows established patterns from other Git codebase uses of Bloom filters. The changes are focused and don't appear to introduce new edge cases, maintaining the existing behavior when filters are unavailable.
