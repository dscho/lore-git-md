This is a discussion about test coverage for the memory leak fixes in pack-bitmap.c. Taylor Blau and Lidong Yan are debating the value of a specific test case that checks for memory leaks when loading corrupt bitmaps, which was added as the third patch in the series.

Taylor initially questioned whether the test was necessary, given that Git already has tests for graceful fallback when reading corrupt bitmaps (via existing tests like "truncated bitmap fails gracefully"). He also expressed concerns about the fragility of the test's implementation, which manually parses bitmap files to inject corruption.

Lidong clarified that the test's purpose is specifically to detect memory leaks under corruption scenarios, which would be caught by ASAN when `SANITIZE_LEAK` is enabled. He also shared an alternative approach that would move test logic into pack-bitmap.c via corruption-injection helpers, though this would require adding test-specific code to the main implementation.

Taylor acknowledges the value in testing for memory leaks specifically, and agrees that testing for leaks with `SANITIZE_LEAK` is reasonable. The discussion suggests they may keep the test but potentially refine its implementation to be less fragile. The key technical points are around whether to:
1. Keep the test as-is to specifically validate leak-free behavior under corruption
2. Modify the test to use a more robust method of injecting corruption
3. Potentially move some test logic into pack-bitmap.c itself

The thread shows consensus on the core memory leak fixes (patches 1-2) while working through the finer points of test coverage for edge cases.
