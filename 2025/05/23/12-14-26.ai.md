This is a feature and bugfix series for `imap-send`, now in its fourth iteration, which both fixes critical configuration parsing issues and expands authentication support. The series has evolved significantly from earlier versions, with v4 adding PLAIN authentication support for OpenSSL alongside the previously discussed OAuth2.0 and CRAM-MD5 fixes.

The first patch remains the crucial configuration parser fix that prevents `cfg->folder` from being incorrectly NULLed out when other IMAP settings are modified, addressing a regression from commit 6d1f198f34. The second patch introduces OAuth2.0 authentication support via curl's native API (OAUTHBEARER/XOAUTH2), which was the major architectural change in v2-v3. New in v4 is the third patch adding PLAIN authentication method support for OpenSSL users, expanding compatibility options. The fourth patch completes the memory leak fixes for CRAM-MD5 authentication that began in v2, now ensuring proper cleanup in all error paths.

The series has undergone thorough review, with v4's changes being relatively minor refinements: improved commit message wording, clearer error messaging, and the new PLAIN authentication method. The thread history shows this work has addressed all technical concerns raised by reviewers including Jeff King, Eric Sunshine, and Junio Hamano, with the curl-native OAuth2.0 implementation satisfying both licensing concerns and technical requirements. The configuration parser fixes remain critical as they correct a severe usability issue that made `imap-send` unreliable with certain configurations.

Key technical additions in v4 include the new PLAIN authentication handler for OpenSSL users (`auth_plain()` function) and expanded documentation covering all supported authentication methods. The implementation maintains backward compatibility while adding modern OAuth2.0 support, with proper RFC compliance and provider-specific handling for major services like Gmail and Outlook. With these final refinements and the comprehensive memory management fixes, the series appears ready for merging, resolving long-standing issues in this less-frequently-used but important component of Git's email workflow.
