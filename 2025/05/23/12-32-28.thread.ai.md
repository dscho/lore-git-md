Git thread summary:

RFC proposal by Max Rhodin for a new `git-ghost` tool to track context around deleted code lines, storing metadata in per-file `.ghost` files with optional per-repo configuration. The tool would prompt users for explanations during commits and provide a `git ghost view` command. The proposal contrasts with `git notes` and seeks feedback on concept and implementation as a userland extension.

Junio Hamano responded with a practical alternative using existing tools (`git blame` in reverse, `git bisect`), questioning whether the tool offers sufficient advantage over current workflows. Lucas Seiki Oshiro further challenges the proposal's premise, arguing `git log` with proper filtering could serve similar purposes and that commit messages on empty-line changes could capture deletion context. Both responses suggest the solution may be over-engineering for problems addressable through better use of current tools.

Key technical points:
- Fundamental challenge of tracing deleted content in version control
- Comparison between proactive metadata capture (`git-ghost`) and reactive historical investigation
- Specific counterproposals using `git blame`, `git bisect`, and `git log -- <file>`
- Alternative approach using empty-line commits with messages
- The tool would be implemented as a userland extension requiring no core Git changes

Open questions:
- Whether the tool offers enough advantage over existing workflows to justify adoption
- How well the tool would integrate with existing Git capabilities
- Whether the problem is better solved through improved documentation of current tools' capabilities

Participant positions:
- Max Rhodin (proponent): specialized tool needed for deleted code context
- Junio Hamano: skeptical, suggests existing tools may suffice
- Lucas Seiki Oshiro: argues current Git functionality can address the need

The discussion remains at the conceptual level, focusing on whether the tool's value proposition justifies its creation rather than implementation details. The thread reflects a broader pattern in Git development where new tools face scrutiny to demonstrate clear differentiation from existing capabilities.
