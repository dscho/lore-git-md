Git thread summary:

RFC proposal by Max Rhodin for a new `git-ghost` tool to track context around deleted code lines, storing metadata in per-file `.ghost` files with optional per-repo configuration. The tool would prompt users for explanations during commits and provide a `git ghost view` command. The proposal contrasts with `git notes` and seeks feedback on concept and implementation approaches before proceeding as a userland extension requiring no core Git changes.

Junio Hamano responds with a practical alternative approach, suggesting `git blame` run in reverse could serve similar purposes for understanding deleted code, while acknowledging the inherent difficulty in tracing removed content. He outlines a concrete workflow using `git bisect` and revision checking to investigate deleted code by locating the last version containing the code and tracing forward. The response provides an experienced maintainer's perspective on existing tools that could address similar needs, implicitly questioning whether the proposed tool's value proposition is sufficiently differentiated from existing Git capabilities.

Key technical points:
- Fundamental challenge of deleted content tracing (needing to know what to look for in historical revisions)
- Comparison between proactive metadata capture (`git-ghost`) and reactive historical investigation
- Practical debugging workflow using `git bisect` and revision checking
- The tool would be implemented as a userland extension requiring no core Git changes

Open questions:
- Whether the proposed tool offers enough advantage over existing workflows to justify adoption
- Potential implementation approaches for the RFC proposal
- How well the tool would integrate with existing Git capabilities
