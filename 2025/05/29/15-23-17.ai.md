Performance optimization in the promisor-remote subsystem, with discussion of potential behavior change. This email from Junio C Hamano responds to Han Young's patch that removes redundant promisor object verification checks in `promisor_remote_get_direct()`. While acknowledging the performance rationale (the current `is_promisor_object()` checks are indeed slow for large repos), Junio raises several important concerns about the proposed change.

First, he questions whether all objects passed to this function are truly guaranteed to be promisor objects, as the callers appear to simply pass objects not found locally rather than explicitly filtering for promisor objects. This suggests the original claim in the commit message may be inaccurate. Second, he notes the behavior change - the function would now die on any failed fetch, not just for objects that were actually promised. This could have implications for error handling that aren't fully understood.

Junio also speculates about a deeper solution - whether `is_promisor_object()` itself could be optimized by pre-computing and caching results like the reverse index does. The discussion highlights that while the performance problem is real, the proposed solution may be oversimplifying the actual object verification requirements and changing error semantics in potentially significant ways. The thread now awaits input from the CC'd reviewers (Christian Couder and Jonathan Tan) on these technical concerns.
