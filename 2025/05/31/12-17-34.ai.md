This is a bugfix patch addressing compatibility issues in `git refs verify` with older-format worktrees. The patch builds on the ongoing discussion about worktree ref verification failures that occur when checking worktrees created with Git v2.43.0 or older.

Kristoffer Haugsbakk provides review feedback on shejialuo's proposed fix. The key technical points are: the issue stems from `git refs verify` failing (exit 255) when encountering worktrees that lack a `refs` directory, which was a valid configuration in pre-v2.43.0 Git. The failure was introduced in v2.48.0 by commit 7c78d819e6a ("ref: support multiple worktrees check for refs") rather than the previously identified commit 8f4c00de95.

The review suggests improvements to the commit message clarity and test implementation. Kristoffer notes the test case should use `git rev-parse --git-dir` instead of hardcoding `.git` paths, following Eric Sunshine's earlier suggestion. There's also discussion about whether this qualifies as a regression severe enough to require fixing in the current release cycle, given that the issue has existed since v2.48.0 while the stderr output regression from `git fsck` is more recent.

The technical solution remains unchanged from shejialuo's patch - modifying `files_fsck_refs_dir()` in `refs/files-backend.c` to ignore ENOENT errors specifically for linked worktrees. The test case demonstrates the fix by simulating the old directory layout and verifying `git refs verify` no longer fails. The discussion highlights the importance of accurately reproducing the old worktree structure in tests to properly validate the fix.
