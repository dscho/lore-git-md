This is a technical discussion about potential optimizations to Git's index handling, specifically exploring alternatives to the current sorted-array approach. Jon Forrest follows up on Junio Hamano's explanation of the current index implementation by proposing a hash-based in-memory structure instead of the sorted array.

Jon suggests storing the in-memory cache as a hash table keyed by pathname, which would eliminate the need for sorting when looking up files. He acknowledges the on-disk index could remain in any order, but raises the key question of whether the overhead of hash table creation would outweigh the current approach of building cache_entry structs and sorting them.

This email represents a pivot from the thread's earlier focus on write amplification and split indexes, now exploring a different optimization vector. The proposal is speculative at this stage - Jon hasn't implemented anything yet and is primarily raising the idea for discussion. The technical merits would depend on benchmarking the hash table overhead versus the current sorting approach, which Jon explicitly calls out as the critical factor needing investigation.
