This is a follow-up discussion on the `git last-modified` implementation, specifically addressing revision walk initialization behavior in the v2 patch series.

Patrick Steinhardt raises a concern about the current handling of non-commit inputs in the command's revision walk initialization. The patch had removed the `prepare_revision_walk()` call that previously validated inputs, instead using a `no_walk` flag that silently ignores non-commit objects. Patrick questions whether this silent failure is the right approach, suggesting an explicit validation check would be more appropriate.

The discussion builds on Toon Claes's earlier change that simplified the revision walk initialization by removing dependency on `log_tree_commit()`. While this optimization was technically sound, it introduced this behavioral change in input validation. The thread context shows this is part of ongoing polish work on an otherwise functionally complete implementation, with multiple reviewers having already addressed core architecture, performance optimizations, and documentation.

Key technical details:
- The command uses revision walk machinery with `no_walk=1` flag
- Previous input validation came from `prepare_revision_walk()`
- Current behavior silently ignores non-commit inputs
- Core functionality in `last-modified.[ch]` and `builtin/last-modified.c`

This appears to be one of the final implementation quality issues to resolve before the series can be considered complete. The experimental status provides some flexibility, but Patrick's point suggests this might need addressing before merging to avoid confusing behavior for users. The discussion continues the pattern of thorough review from Patrick, who has previously provided detailed feedback on this series.
