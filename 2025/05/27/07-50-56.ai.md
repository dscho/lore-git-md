This is a discussion thread clarification in the promisor-remote protocol enhancement series, specifically addressing documentation and configuration design questions from the v2 review.

Patrick Steinhardt follows up on Christian Couder's responses to his v2 review comments about the `promisor.sendFields` configuration. The key clarification is that the config controls which field *names* are advertised, not name-value pairs - the actual values come from the remote's existing configuration (like `remote.<name>.partialCloneFilter`). Patrick suggests improving the documentation format by listing supported fields as bullet points rather than inline text, making it more maintainable as new fields are added.

The discussion confirms that the current global `promisor.sendFields` setting is sufficient for now, though it could be made per-remote later if needed. Christian explains that servers will advertise the filter/token values already configured for each remote, allowing different values per advertised promisor. Patrick acknowledges this understanding and agrees the per-remote configuration isn't currently necessary.

The exchange also touches on the behavior when clients use different filters than advertised, with Christian noting this is existing promisor-remote behavior that falls back to the main server when objects are missing. Patrick suggests this interaction could be better documented to help reviewers understand the broader context, though agrees it's not specific to this series.

This email doesn't introduce new technical changes but helps clarify the design decisions and documentation approach for the field advertisement mechanism in the promisor-remote protocol extension. All open questions from the v2 review appear resolved, with agreement on both the configuration semantics and documentation improvements.
