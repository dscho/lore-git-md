This is a performance optimization patch for the `git last-modified` command, part of the v2 series implementing path modification tracking. The email from Patrick Steinhardt provides detailed technical review feedback on Toon Claes's proposed faster algorithm.

The core of the optimization replaces the initial simple revision walk with a priority queue approach using generation numbers, similar to algorithms used in `git commit-reach.c`. The patch shows significant speed improvements - up to 9.8x faster with Bloom filters on the Linux kernel repo compared to the original implementation.

Patrick's review focuses on several implementation details needing polish:
1. The `active_paths` struct could use a bitmap instead of byte-per-flag storage
2. Global variable `scratch` should be replaced with context passing
3. Header includes should be sorted lexicographically
4. Some naming could be improved (`free_one_active_path` -> `commit_active_paths_release`)
5. Leftover TODO comments need addressing
6. Documentation of the `--max-depth` option reference that doesn't exist
7. Clarification needed around merge commit handling (which parent gets priority)

The review confirms the algorithmic approach produces identical results to the simpler version while being significantly faster, as demonstrated by the performance numbers. Most concerns are about code organization and style rather than fundamental design, suggesting the optimization approach itself is sound. The thread context shows this builds on prior consensus around Bloom filter usage and priority queue traversal from earlier discussion.
