This is a technical follow-up in the ongoing discussion about Git backup strategies, specifically exploring direct fetch-based approaches as an alternative to the previously discussed bundle and state-tracking methods.

Abhishek Dalmia investigates using `git fetch-pack` for incremental backups but hits protocol limitations (HTTPS unsupported, SSH connection failures) when trying to fetch only new objects without requiring previous objects. The experiments show the current CLI doesn't support this workflow directly. The email also mentions exploring API-based blob downloads as an alternative, though this approach faces rate limits and performance issues.

The message references Jeff King's earlier suggestion about avoiding timestamp-based approaches in favor of ref state snapshots, but doesn't directly engage with that solution. Instead, it explores a different path (direct fetch operations) that appears technically unviable with current Git tooling. The key technical constraints revealed are: protocol limitations for partial fetches, the impracticality of maintaining full clones for incremental purposes, and the inadequacy of API-based solutions for bulk operations.

This appears to be exploring a dead-end approach compared to the more promising state-tracking and bundle methods previously discussed, though it does helpfully document concrete technical barriers to fetch-based solutions. The email doesn't propose any new solutions or challenge the existing consensus around pack-based approaches, but rather serves as a negative result showing what doesn't work.
