Jon Forrest originally suggested this as a UX improvement, noting that `git commit -a`'s current behavior (only staging changes to tracked files) can surprise users expecting more comprehensive staging.

Junio C Hamano has now added to this historical perspective, explaining that early Git lacked `.gitignore` functionality when `commit -a` was implemented, making the conservative approach (only staging tracked files) a practical necessity at the time. He also notes that experienced users typically modify existing files more often than creating new ones, making the current behavior ergonomic for common workflows.

The discussion reveals a split in perspectives: Nico Williams strongly opposes changing `-a`'s behavior but is neutral on adding `-A`, while the historical analysis from Kristoffer and Junio provides context without taking a position on the proposal itself. Key open questions include how the new option would handle ignored files and whether it should maintain exact parity with `git add -A`. The thread has established that the current behavior has deep technical roots, but hasn't yet reached consensus on whether the modern context (with robust ignore functionality) justifies adding the proposed `-A` option.
