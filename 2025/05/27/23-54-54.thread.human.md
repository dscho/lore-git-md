The thread explores modifying `git add -p` to handle merge conflicts, which currently fails when operating on conflicted files. Jarrad Whitaker originally proposed the feature, with Chris Torek providing a technical analysis showing the challenge lies in Git's index model—conflicted files exist in stages 1-3 (base/ours/theirs), while `git add -p` assumes stage 0 (unconflicted) state. This creates an architectural hurdle, as the index cannot currently represent both conflict markers and partial resolution simultaneously.

In a new follow-up, Whitaker suggests a thought experiment: having `git add -p` automatically resolve conflicts by discarding the stage 1-3 versions when first invoked on a conflicted file. This would sidestep the need for complex index modifications but raises concerns about user expectations—such behavior might be surprising, as it immediately marks the file as resolved. The discussion remains exploratory, weighing trade-offs between implementation complexity (maintaining parallel conflict state) and UX (potential unexpected resolution). 

Phillip Wood, the expert on `git add -p`'s interactive machinery, has not yet weighed in, and his input will be key to determining whether this or another approach is viable.
