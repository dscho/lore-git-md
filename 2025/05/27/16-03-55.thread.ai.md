Thread identity: Feature proposal from Jon Forrest about `git commit` behavior, suggesting adding a `-A` option to stage new files automatically alongside `-a`'s behavior, with historical context now provided by Kristoffer Haugsbakk.

Core problem: `git commit -a` only stages modifications to tracked files, not new untracked files, which can surprise users expecting more comprehensive staging. The proposal suggests `git commit -A` would behave like `git add -A` vs `git add -u` - staging both modified tracked files and new untracked files. Historical analysis reveals this behavior dates to Git's 2005 implementation using `git-diff-files --name-only` piped to `git-update-cache`, possibly intentionally avoiding accidental staging of unwanted files.

Current status: Discussion stage with mixed reception. Jon Forrest proposed the change as a UX improvement, while Nico Williams opposes modifying `-a` but is neutral on adding `-A`. Kristoffer Haugsbakk provided historical context showing the current behavior has deep technical roots (original implementation f0b32737ad5, documentation cb95bf488b4) but took no position on the proposal. No implementation yet.

Key technical details: Would modify `builtin/commit.c` to add new flag handling parallel to `-a` but with `ALL` semantics. Original implementation used diff-files/update-cache pipeline that only processed tracked files. Behavior would need clear separation: `-a` for modified tracked files only (current behavior with historical justification), `-A` for both modified and new files (proposed addition). Implementation questions remain about handling ignored files and edge cases around partial staging.

Open questions: How to handle ignored files (should they be included like `git add -A` does?), whether to maintain exact `git add -A` parity, potential edge cases around partial staging. Historical context suggests original behavior may have been intentionally conservative about staging, which could inform these decisions.
