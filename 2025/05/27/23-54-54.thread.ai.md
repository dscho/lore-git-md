Thread identity: Feature request to modify `git add -p` behavior regarding merge conflicts, from Jarrad Whitaker, with technical analysis from Chris Torek and new proposal from Whitaker.

Core problem: Proposal to allow `git add -p` on files with merge conflicts, which currently fails. Requires fundamental changes to Git's index model where conflicted files exist in stages 1-3 (base/ours/theirs) while `git add -p` assumes stage 0 (unconflicted) state. Whitaker now proposes an alternative approach where `git add -p` would automatically resolve conflicts by discarding stage 1-3 versions when first invoked on conflicted files.

Current status: Initial proposal met with technical constraints about index representation. New proposal explores tradeoff between implementation complexity (maintaining parallel conflict state) and user experience (automatic resolution). No implementation exists yet. Phillip Wood's input still needed on interactive add implications.

Key technical details: Two potential paths identified:
1. Parallel representation of conflict markers and partial resolution (breaking current mutual exclusivity of stages)
2. Whitaker's new proposal: automatic conflict resolution on first `git add -p` invocation, removing stages 1-3
Both approaches would impact `git restore` and other commands expecting atomic conflict resolution via `git add`. The automatic resolution path would be simpler to implement but could surprise users by immediately marking files as resolved.

Open questions: Whether automatic resolution would be too dangerous/unexpected. How to handle edge cases where partial resolution interacts with remaining conflicts. Phillip Wood's expertise needed to assess impact on interactive patch machinery.
