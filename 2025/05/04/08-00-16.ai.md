This is a bug report about unnecessary warning messages in `git show -s`. Junio Hamano observes that when using `git show -s` (which suppresses diff output), Git still checks and warns about rename detection being skipped due to hitting the `diff.renameLimit`, even though no rename detection is actually needed when no diff is being shown.

The issue stems from Git's default enablement of rename detection (-M) combined with the renameLimit mechanism. While the warning would be appropriate for diff-generating operations (like --stat or --raw), it's irrelevant for `-s` which explicitly avoids computing diffs. The patch suggests this is wasteful computation that could be optimized away.

Key technical details:
- The warning comes from diffcore_rename.c's handling of renameLimit
- The check happens even with `-s` which sets `rev.diffopt.output_format` to not show diffs
- The commit demonstrates the issue with a repo having many file changes (6123+ files)

This appears to be a straightforward optimization opportunity - skipping rename detection checks when we know we won't show diffs. The report doesn't include a proposed fix but clearly identifies the problematic behavior and its trigger conditions.
