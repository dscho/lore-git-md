Security-focused proposal for deterministic Change-IDs. Brian M. Carlson responds to Martin von Zweigbergk's defense of Jujutsu's random-byte Change-ID approach with concerns about determinism and potential security vulnerabilities.

Carlson argues strongly against random generation, citing two main issues: Git's general commitment to deterministic behavior (referencing their own stash import/export work that requires bit-for-bit reproducibility), and security concerns about potential side-channel leaks through commit metadata. They propose two deterministic alternatives - either a SHA-256 hash of the original commit data or an HMAC-SHA-256 with a fixed key.

The email also suggests a config option to disable Change-ID generation entirely for privacy-conscious users, noting they would personally use this option. This positions the Change-ID feature as potentially opt-in rather than mandatory, which contrasts with Jujutsu's current implementation where these IDs appear necessary for core workflows.

This response adds significant new considerations to the Change-ID standardization discussion, shifting focus from workflow functionality to security and reproducibility requirements. Carlson brings maintainer-level perspective (referencing ongoing work) and security expertise to the conversation, which may require Jujutsu's team to address these concerns directly. The proposal for deterministic generation would represent a fundamental change from Jujutsu's current working implementation.
