This is a follow-up in the merge-tree optimization thread, addressing Junio's naming suggestion for the new `--mergeability-only` flag. Elijah Newren explains why he initially chose not to use `--dry-run` for the flag, clarifying important implementation details about object creation behavior.

The response notes that while the flag avoids writing objects for the "outer layer" of the merge (which is what most users would think of as the merge result), it still performs and stores object writes in two cases: (1) when computing merge bases, and (2) when handling rename/rename conflicts where both sides modified the same file. This subtlety means `--dry-run` could be misleading since some object creation still occurs.

The technical details provided about when objects are/aren't written help frame the naming discussion by showing the actual behavior doesn't perfectly match either conventional `--dry-run` semantics (no changes at all) or the proposed `--mergeability-only` (some changes allowed). This suggests the naming decision may need to weigh clarity against technical precision, with potential alternatives being to document the caveats of `--dry-run` or find a third name that better captures the partial-object-creation behavior.

The exchange represents the first substantive discussion point in the thread, moving beyond initial review into design considerations. The core functionality remains uncontested while the naming convention becomes the focus. Future discussion may explore whether users would find the object-creation caveats acceptable under a `--dry-run` name or if a different name would better serve both accuracy and usability.
