This is a performance fix for the reftable backend, addressing a regression introduced by a recent refactoring. Patrick Steinhardt explains that commit fd888311fbc restructured how reftable blocks are read, but inadvertently caused a significant slowdown when processing blocks of an unwanted type. The refactoring moved block reading logic into the "block.c" subsystem but changed when uninteresting blocks are discarded - now they're fully decoded before being rejected, rather than being discarded immediately after type checking.

The performance impact is substantial: benchmarks show a 1.57x slowdown when creating 100k refs. The fix modifies `reftable_block_init()` to accept a `want_type` parameter and return early if the block doesn't match, avoiding unnecessary decoding work. This restores performance, with the fixed version now running 1.62x faster than the regression.

The patch includes changes to the block reading interface and updates unit tests to pass the new `want_type` parameter. The commit message is thorough, with clear before/after benchmarks and a detailed explanation of both the problem and solution. This appears to be a well-justified and carefully measured performance optimization for a regression the author themselves introduced.
