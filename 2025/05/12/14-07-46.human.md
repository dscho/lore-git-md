This is a bugfix discussion regarding `git pull --rebase` unexpectedly dropping commits after changing a repository's remote URL. Phillip Wood provides technical analysis of the issue, explaining that the problem stems from how `git merge-base --fork-point` interacts with the reflog after a remote URL change.

The key insight is that after changing the remote URL with `git remote set-url`, the reflog still contains entries from the old remote. When `git pull --rebase` runs its internal `merge-base --fork-point` calculation, it incorrectly uses these stale reflog entries, causing commits to be excluded from the rebase. Phillip offers two workarounds: either use `git fetch && git rebase --no-fork-point` to bypass the problematic fork-point logic, or rename the remote rather than changing its URL to avoid reflog contamination.

Phillip also raises an important design question about whether `git pull --rebase` should use fork-point` by default, noting that while convenient for handling rewritten history, it can lead to surprising behavior like this case. He points out there's currently no way to disable it through configuration, which compounds the problem.
