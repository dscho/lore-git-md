This thread addresses a performance regression in Git's reftable backend that was introduced by commit fd888311fbc. The regression caused unnecessary decoding of blocks before checking their type, significantly slowing down `update-ref` operations. 

The patch from Karthik Nayak fixes this by modifying `reftable_block_init()` to accept a `want_type` parameter and skip full decoding when the block type doesn't match. Benchmarks show this not only fixes the regression but actually improves performance beyond the original state - making `update-ref` operations 1.62x faster than the regressed version and 1.57x faster than before the regression. The changes touch core reftable reading logic in `table.c` while maintaining backward compatibility through a `REFTABLE_BLOCK_TYPE_ANY` fallback.

The fix is well-validated with performance measurements and includes necessary test updates. This appears to be a clean solution to a significant performance issue in the reftable implementation.
