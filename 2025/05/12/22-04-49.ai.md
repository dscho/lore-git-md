This is a security-focused response in the ongoing Change-ID standardization discussion. Brian m. carlson raises concerns about Jujutsu's random byte generation approach for Change-IDs, proposing a deterministic alternative and configurable opt-out.

The email makes three key technical arguments against random Change-IDs: 1) Git's deterministic nature is relied upon for features like stash import/export (referencing their own upcoming series), 2) random values could create security side channels for leaking sensitive data, and 3) privacy-conscious users may want to disable Change-IDs entirely. The proposed solution is either a SHA-256 hash of commit data or HMAC-SHA-256 with a fixed key, plus a configuration option to suppress Change-ID generation.

This introduces new security considerations to the thread, directly challenging Jujutsu's working implementation. The arguments reference concrete use cases (stash reproducibility) and threat models (credential leakage via commit metadata). The config option suggestion acknowledges that some workflows may need to avoid Change-IDs entirely, adding a new dimension to the compatibility discussion. The response maintains the thread's technical focus while shifting emphasis from workflow requirements to security and determinism concerns.
