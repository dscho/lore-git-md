This is a discussion about filesystem safety in the packed-refs optimization series, specifically focusing on how to handle empty packed-refs files. Patrick Steinhardt is responding to shejialuo's proposal about maintaining backward compatibility while planning stricter validation in Git 3.0.

Patrick raises important considerations about the historical behavior of Git packed-refs files. While shejialuo notes that modern Git always writes headers (since commit 694b7a1999) and maintains runtime compatibility with empty files, Patrick questions whether older Git versions might have produced truly empty packed-refs files. He suggests that if empty files were never valid output, we should start warning about them now rather than waiting for Git 3.0.

The discussion reveals a tension between immediate safety checks and maintaining backward compatibility. Patrick makes a key point about the deprecation timeline - if we're going to reject empty files in Git 3.0, the verification checks should be introduced well before the runtime behavior changes to give users time to adapt. This is part of the ongoing refinement of the packed-refs optimization work that has already seen significant review and iteration.
