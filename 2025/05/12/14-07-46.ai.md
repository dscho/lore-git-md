This is a bugfix discussion regarding `git pull --rebase` behavior when changing remote URLs, with new analysis from Phillip Wood. The thread has established that the issue stems from how `merge-base --fork-point` interacts with reflog entries after a remote URL change, causing commits to be incorrectly dropped during rebase.

Phillip explains the technical mechanism: after changing the remote URL, the upstream branch's reflog still contains entries from the old remote (commit G in this case). When `pull --rebase` internally uses `merge-base --fork-point`, it excludes commits reachable from these stale reflog entries, leading to the observed commit dropping. He provides two workarounds: using `git fetch && git rebase --no-fork-point` to bypass fork-point calculation, or renaming the remote rather than changing its URL to avoid reflog contamination.

The email highlights a design tension in `pull --rebase`'s default use of fork-point - while useful for handling rewritten upstream history, it creates surprising behavior in URL-change scenarios. Phillip notes the current implementation ignores the `rebase.forkPoint` config setting, which could otherwise provide user control over this behavior.

Key technical details for future reference: the issue manifests when using `remote set-url` followed by `pull --rebase`, with the problematic behavior traceable to reflog entries persisting from the old remote. The fork-point calculation appears to prioritize these stale reflog entries over the actual commit topology. The workarounds demonstrate the behavior is not fundamental to rebase itself but rather to how fork-point interacts with remote changes.

The discussion continues to explore whether this represents a bug to be fixed or a behavior that should be documented/configured differently, with Phillip's analysis providing concrete technical grounding for either path forward. The thread maintains focus on the original reproduction case while expanding understanding of the underlying mechanisms.
