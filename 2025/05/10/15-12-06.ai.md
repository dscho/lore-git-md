This is a feature proposal addressing an interaction between sparse-checkout and symlinks. Gabriel Scherer identifies a problem where symlinks in a sparse-checkout become dangling if their targets are outside the checked-out area. The proposal suggests two potential solutions: either copying the target file's content when needed, or automatically expanding the sparse-checkout to include symlink targets.

The issue arises in a specific use case involving a large repository (typst/packages) where symlinks are used to deduplicate files, but CI workflows using sparse-checkout break when encountering these symlinks. The email thoughtfully presents both technical approaches and asks for feedback on implementation choices - whether to copy content or expand checkout scope, and how to configure this behavior.

Key technical points for future reference: the problem manifests when b/file symlinks to a/file while only b/ is in sparse-checkout; proposed solutions involve either content copying (with potential duplication) or automatic sparse-checkout expansion (requiring special handling for 'reapply'). The discussion will likely center around which approach better maintains repository invariants while solving the immediate problem.
