This is a feature proposal addressing sparse-checkout behavior with symlinks. Gabriel Scherer reports that when using sparse-checkout with repositories containing symlinks, users can end up with broken symlinks if the target files aren't included in the sparse checkout. This creates problems for their use case involving a large repository (typst/packages) where they're using symlinks to deduplicate files.

The email proposes two potential solutions: (1) silently copying the target file's content when the symlink target isn't in the sparse checkout, or (2) automatically adding the target file to the sparse checkout set. The author seeks feedback on which approach would be preferable and how such a feature should be configured.

The proposal appears well-motivated by a concrete use case involving CI testing of a large repository, though it would affect any sparse-checkout user working with symlinks. The author thoughtfully considers tradeoffs between the approaches and explicitly asks for interface design suggestions, showing this is an early-stage proposal seeking community input rather than a fully-baked solution. The interaction between sparse-checkout and symlinks is indeed a subtle edge case that hasn't received much public discussion before.
