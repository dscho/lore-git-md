This thread addresses a bug where Git could silently overwrite `.gitmodules` entries when adding a new submodule at a path that previously hosted a different submodule. The core issue stems from Git reusing old submodule names derived from paths, which becomes problematic when submodules are moved rather than renamed.

K Jayatheerth has been iterating on a fix, with significant guidance from maintainer Junio Hamano. The discussion initially considered a simple `--force` option but evolved toward a safer automatic solution after Junio emphasized configuration integrity over convenience. The current approach detects name/path conflicts using `submodule_from_name()` and either errors out or generates unique names by appending incrementing numbers (foo, foo1, foo2) when conflicts occur.

The latest patch implements this automatic naming scheme while maintaining compatibility with existing `submodule.active` configuration handling. Test cases in t7400 verify the basic error behavior and naming logic, though edge cases around nested submodules remain marked as `NEEDSWORK`. The solution represents a thoughtful balance between safety and usability, reflecting Git's stability priorities while addressing the original problem of accidental configuration overwrites.
