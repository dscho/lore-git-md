**Thread summary: Feature patch adding MPTCP support for Git on Linux (v4)**

Initial patch series introduces Multi-Path TCP (MPTCP) support for Linux systems, enabling bandwidth aggregation across multiple network paths (WiFi + 5G). Implementation requires kernel (IPPROTO_MPTCP) and glibc support, with fallback to TCP. Client-side uses GIT_ENABLE_MPTCP environment variable, server-side via git-daemon --mptcp flag. Carefully handles __linux__ guards and checks for kernel 5.6+ and glibc getaddrinfo() support. Author motivation cites large-repo transfers (50GB+) benefiting from aggregation/failover, with Apple's cloud usage as precedent. Technical implementation modifies socket initialization in network code.

Version 3 fixed fallback logic error where MPTCP protocol was incorrectly used when disabled, ensuring proper fallback to IPPROTO_TCP when unsupported. Issue discovered through Wireshark packet inspection during testing. Maintainer Junio Hamano expressed skepticism about the approach's viability, questioning whether application-level MPTCP support is the right direction given limited ecosystem adoption.

Muhammad Nuzaihan responds to maintainer concerns by providing MPTCP adoption context: stable since 2020 (Linux kernel 5.6), Apple's 12-year production use in iOS cloud services, and Go 1.24's default support as precedent. Draws parallel to IPv6 adoption curve. Shares personal motivation from poor hotel network experiences but acknowledges server-side benefits may be more significant. References but downplays 2022 Linux MPTCP CVE as outdated. Maintainer's fundamental question remains unanswered - no new technical implementation details or performance data provided to justify Git-specific need versus system-level configuration. Thread remains stalled on architectural debate about whether Git should lead in MPTCP adoption versus waiting for broader ecosystem support.

Open questions persist regarding Makefile vs env var configuration approach, still lacks concrete performance measurements demonstrating Git-specific benefits. While technical implementation appears sound (with v3's protocol fallback fix), maintainer's high-level concerns about feature necessity and ecosystem readiness create significant adoption barrier unless either broader deployment evidence or unique Git use cases are demonstrated. The exchange highlights a philosophical divide between proactive protocol adoption versus conservative system-level dependency approach.
