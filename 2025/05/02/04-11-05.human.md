This is a bugfix discussion regarding `git apply --intent-to-add` behavior. Ryan Hodges responds to Junio Hamano's concerns about the proposed fix (making `--intent-to-add` imply `--index`) by demonstrating a serious flaw in the current implementation: when applying a patch with `--intent-to-add`, Git incorrectly marks existing tracked files as deleted in the index. 

Hodges provides a concrete example showing how applying a simple new-file patch causes an unrelated file to appear staged for deletion. He argues this behavior is clearly wrong and needs fixing, regardless of the solution path. The email also explains the original motivation for `--intent-to-add` - to maintain consistency between `apply`, `diff`, and `commit` operations by properly tracking new files without immediately staging them.

The thread remains at an impasse between two positions: Hamano's concern that automatically adding `--index` might create other edge cases (since other options like `--cached` also affect the index), and Hodges' demonstration that the current behavior is actively harmful. The discussion appears to need either a more comprehensive solution or a re-evaluation of whether the documented behavior should be considered correct despite these issues.
