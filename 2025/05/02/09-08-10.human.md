This is a follow-up discussion about the `git whatchanged` deprecation series. Patrick Steinhardt questions why the deprecation isn't being listed in Git 3.0's breaking changes document, given that the patches clearly start the deprecation process for `git whatchanged`. He suggests two possible interpretations of Junio's approach: either this is an intentional delay to first gauge usage via mailing list feedback before formal deprecation, or there's a disconnect between the patches' apparent intent and their documentation impact.

The exchange highlights an interesting tension in the deprecation strategy - whether to announce removals upfront in breaking changes (setting clear expectations) or to first introduce warnings and assess impact before committing to removal. Patrick's probing suggests he sees value in more explicit communication of the deprecation path, while Junio's original comment framed this as purely preparatory work. This discussion may influence whether future deprecations get documented in BreakingChanges.adoc earlier in the process.
