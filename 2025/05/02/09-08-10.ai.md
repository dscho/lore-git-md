This is a follow-up discussion in the thread about deprecating `git whatchanged`. Patrick Steinhardt questions why the deprecation isn't being listed in Git 3.0 breaking changes, given that the patches seem to start the deprecation process. He suggests two possible interpretations of the approach: either this is the beginning of formal deprecation, or it's a way to survey usage before deciding whether to deprecate.

The thread context shows this is part of a 2-patch series establishing standardized deprecation infrastructure, with `git whatchanged` as the first example. The series moves deprecation logic to core (usage.c), updates documentation with warnings, and modifies tests to either use the new `--i-still-use-this` flag or migrate to alternatives like `git log --raw`. 

Key technical elements at play:
- The `you_still_use_that()` helper in usage.c
- Modified builtin/log.c for `whatchanged` handling
- Documentation updates in git-whatchanged.adoc
- Test changes across t4013, t4202, t9300, and t9301
- Explicit non-inclusion in BreakingChanges.adoc

This email raises an important process question about whether deprecation warnings should be accompanied by immediate breaking change notices, or whether they should first serve as usage surveys. The thread shows this is establishing a potential standard deprecation path, but hasn't yet attracted reviewer feedback on either technical implementation or process questions.
