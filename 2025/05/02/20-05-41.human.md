This is part 2/3 of Junio Hamano's series introducing optional file specifications in Git (the `:(optional)` prefix). The email responds to Patrick Steinhardt's concern about whether empty files should be treated the same as missing files (both are currently silently skipped).

Junio acknowledges the current behavior may have been deeply considered, noting the original motivation came from an older discussion he doesn't fully recall. He suggests the syntax was designed to be extensible - if users want different handling of empty files, new variants like `:(optional,ignore-empty)` could be added later.

The response indicates Junio views this as a starting point that can evolve based on real needs, while maintaining the door open for more granular control. He expresses hope that interested parties (who recently showed enthusiasm for the feature) will drive any further refinements, as he's not deeply invested in the specifics.

This moves the thread toward resolution by clarifying the current behavior was likely a pragmatic choice rather than a strongly-motivated design, while showing how future use cases could be accommodated without breaking backward compatibility. The ball is now in the court of those who want the feature to decide if the current behavior suffices or if they want to propose extensions.
