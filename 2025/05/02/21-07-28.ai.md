This is a final review comment on the v3 series implementing the last two `git gc` replacement tasks (worktree pruning and rerere GC). Junio Hamano acknowledges the series is otherwise ready but raises a fundamental concern about the rerere GC auto-configuration approach.

While approving the overall direction and quality of the series, Hamano argues the current rerere-gc auto-condition (based on directory entry count) provides little practical value compared to a simple boolean toggle. His key objection is that unlike object repacking (where one run clears the condition), rerere GC leaves entries behind, making the count-based heuristic ineffective at preventing repeated unnecessary runs. He suggests waiting until the storage format allows better staleness detection before implementing sophisticated auto-GC logic.

The comment maintains the position from earlier in the thread that simpler heuristics are preferable, now explicitly recommending a boolean flag instead of the entry-count threshold. This represents the last open design question before merging, though Hamano's phrasing ("I would prefer") suggests it may not block the series given his overall approval.

Technical context for future summaries:
- The v3 simplification changed rerere GC from a three-phase scan to checking `.git/rr-cache` entry count
- Hamano's critique focuses on the fundamental difference between rerere GC and object GC semantics
- Suggests future storage format changes could enable better auto-GC conditions
- Current implementation preserves `die(FAILED_RUN, "rerere")` error handling
- Maintains compatibility with existing rerere config options
