This is a bug report about Git's safe.directory behavior when cloning over SSH. The reporter describes a scenario where they cannot clone a bare repository owned by a different user group, even after adding the directory to safe.directory as suggested by Git's error message.

The key technical details are:
- The remote bare repo is owned by group a_and_b with 770 permissions
- User b has SSH key access but gets "dubious ownership" error
- Adding safe.directory config doesn't resolve the issue
- rsync works fine, proving SSH access itself is functional
- The problem persists across similar NixOS systems

The reporter argues this should work by default since multi-user repository access is a common need. The core issue appears to be that Git's safe.directory check isn't properly accounting for SSH-based access scenarios where the local and remote users differ. The error suggests a configuration fix that doesn't actually solve the problem, indicating either a bug in the safe.directory implementation or a missing feature for SSH use cases.

This seems like a legitimate usability issue that could affect any multi-user Git environment not using centralized hosting platforms. The report provides clear reproduction steps and demonstrates the configuration workaround fails, suggesting deeper investigation is needed into how ownership checks interact with remote operations.
