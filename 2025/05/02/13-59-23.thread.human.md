This thread began with a Windows-specific bug report about `git svn` failures, but has evolved into a broader discussion about how Git manages its legacy code. Arnoud Berendsen originally reported two issues with `git svn` on Windows: `.gitignore` path stripping problems and Perl warnings during branch initialization. Johannes Schindelin (Dscho) acknowledged the Windows maintenance challenges and hinted at potential deprecation.

Patrick Steinhardt then shifted the conversation to question the purpose of Git's `contrib/` directory, using `git svn` as an example (though it was later clarified that `git svn` is actually a core command, not in `contrib/`). Junio Hamano proposed a framework for handling legacy components: promote to core maintenance, spin off as independent projects, or remove entirely.

In the latest email, Steinhardt responds to Junio's framework by drawing parallels to Linux kernel staging drivers and suggesting concrete action. He proposes removing clearly unmaintained parts of `contrib/` while identifying other components (like CMake support and Coccinelle rules) that might deserve promotion to core. The discussion has moved from abstract policy to actionable next steps, though the original Windows-specific `git svn` issues remain unresolved. The thread now has clear direction for evaluating `contrib/` contents while the broader legacy code policy takes shape.
