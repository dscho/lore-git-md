This thread has evolved from a specific bug report about `git svn` failures on Windows to a broader discussion about Git's maintenance philosophy for contributed but unmaintained tools. 

The original issue, reported by BERENDSEN Arnoud, detailed intermittent failures in `git svn clone` on Windows with cryptic Perl warnings and branch initialization errors. Johannes Schindelin (Dscho) acknowledged the Windows-specific challenges and suggested using WSL as a workaround, while raising the possibility of deprecating Windows support for `git svn` due to lack of maintainers.

Patrick Steinhardt has now expanded the conversation to question the purpose of Git's `contrib/` directory as a whole, where `git svn` and other scripts reside. He argues that many scripts in `contrib/` create a false impression of being officially supported when they are effectively unmaintained. Steinhardt proposes either a comprehensive cleanup of neglected scripts or reconsidering whether such tools belong in Git's main repository at all.

While the technical details of the original `git svn` failures (Perl warnings and branch initialization problems) remain unresolved, the discussion has shifted to a policy level. The thread now centers on how Git should handle contributed tools that lack active maintainers, with `git svn` serving as a case study of the broader challenge.
