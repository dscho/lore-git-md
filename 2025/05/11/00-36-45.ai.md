Bugfix patch addressing core issue in `git apply --intent-to-add` behavior.

This second patch in Raymond Pasco's series fixes the fundamental problem where `--intent-to-add` (`-N`) would corrupt the index by writing to it without first reading the existing contents. The issue stems from incorrectly gating the index read operation on `check_index` (used for `--index` mode) rather than `update_index` (which indicates any index modification). The change ensures the index is properly loaded before making intent-to-add entries, preventing the previously observed behavior where tracked files could be incorrectly marked as deleted.

The patch modifies `apply.c` to use `update_index` as the condition for reading the index in `apply_patch()`. This aligns with the flag's documented purpose - `update_index` is set whenever the index will be modified (including in `--intent-to-add` mode), while `check_index` is specific to `--index` operations. The fix maintains all existing behavior while properly supporting the intent-to-add workflow.

This change directly addresses the core issue demonstrated by Ryan Hodges where `--intent-to-add` would clobber the index. It builds on the first patch's error handling improvements by now correctly initializing the index state before modification. The simple one-line diff belies its importance - this was the key missing piece that made `--intent-to-add` fundamentally broken for non-trivial cases.

The patch carries forward attribution to both the original reporter (Johannes Altmanninger's 2021 work) and the recent demonstration of breakage (Ryan Hodges). With this change, the series is now halfway to fully resolving the longstanding issues with `--intent-to-add` behavior while maintaining its original purpose as a worktree-focused operation for new files.
