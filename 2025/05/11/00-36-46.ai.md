Bugfix patch in the `--intent-to-add` index corruption series. This third patch in the 5-part series tightens the conditions under which index entries are written when using `--intent-to-add` (`-N`), ensuring the index is only modified for truly new files.

The change modifies the `create_file()` function in `apply.c` to replace a simple `state->update_index` check with a more precise condition that combines `check_index` with a test for both `ita_only` mode and the file being a new addition (`patch->is_new > 0`). This prevents the command from incorrectly writing index entries for tracked files while maintaining the intended behavior of recording intent-to-add for genuinely new files.

The patch addresses a subtle interaction between the `--intent-to-add` and `--index`/`--cached` flags that could lead to index corruption. It builds on the previous patches' foundation of proper index initialization and error checking by now precisely controlling when index writes occur. The change is minimal (just one line modified) but critical for correct behavior, ensuring `git apply -N` remains a worktree-only operation except for its specific purpose of recording new file additions.

Technical details include:
- Maintains the `ita_only` behavior from previous patches
- Adds explicit check for `patch->is_new` to prevent modifying tracked files
- Preserves the `conflicted_threeway` handling path
- Keeps the same function signature and return behavior

This represents another step toward fully resolving the index corruption issues while maintaining all legitimate use cases for `--intent-to-add`. The change aligns with the series' overall goal of making `git apply -N` safe while keeping its useful functionality for staging new files.
