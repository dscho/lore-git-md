This is a follow-up in the `git-blame-tree` RFC thread, addressing merge behavior questions. Toon Claes responds to Junio Hamano's inquiry about how the command handles "most recent modification" detection in merge-heavy histories. The email acknowledges the need for merge case documentation and test coverage, which were intentionally deferred during the RFC phase to avoid premature work if the concept was rejected.

Key technical points for future summarizers: The discussion focuses on two specific merge topologies where a path's content comes from different sides of a merge (either mainline or side branch). The author agrees these scenarios need test coverage in the next version, suggesting the behavior may need clarification when:
- A path is modified on one branch but unchanged on another before merging
- The merge resolution picks content from one parent over another
- The same path exists as both a file and a tree

The response indicates merge semantics will be a focus area for the next revision, alongside the previously identified naming questions. No concrete resolution is proposed yet - the author prefers to work through the test cases first before formalizing the behavior. This keeps the thread's two main discussion points (naming and merge handling) active while moving the latter toward more concrete analysis.
