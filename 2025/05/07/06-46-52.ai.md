This is a follow-up discussion in the RFC patch series introducing new trailer functionality for `git rebase` and `git am`. The thread centers around two proposed features: a dedicated `--reviewby` flag and a more general `--trailer` option.

Li Chen responds to Junio Hamano's architectural concerns about code duplication and scalability. The key technical points in this reply are:

1. Defends the current `--reviewby` implementation by noting it mirrors the existing `--signoff` approach in sequencer.c rather than using interpret-trailers, since the latter operates on files/stdin while rebase needs in-memory operation. Points out the parallel `--trailer` option already uses trailer.c's `amend_file_with_trailers()`.

2. Argues for keeping a dedicated `--reviewby` flag by analogy to `--signoff`, noting some projects require Reviewed-by trailers as policy. Suggests it could be refactored to share trailer infrastructure with signoff if desired.

3. Acknowledges the scalability concern about proliferating dedicated flags but presents the convenience tradeoff - users would otherwise need aliases to achieve the same workflow.

The discussion remains open on whether to:
- Keep both features or drop `--reviewby` in favor of only `--trailer`
- Refactor to share more trailer-handling infrastructure
- Maintain the current parallel implementations

The technical context involves sequencer.c's trailer handling, the distinction between rebase backends, and the existing interpret-trailers machinery. The thread shows active design discussion about balancing convenience features against code maintainability.
