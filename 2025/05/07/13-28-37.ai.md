This is a reply in the RFC thread about adding a `--skip-connectivity-check` option to `git receive-pack`. Patrick Steinhardt provides additional context from GitLab's perspective to better justify the proposed optimization.

The key new information is that GitLab's Gitaly service has repository-specific knowledge that allows it to perform more efficient connectivity validation than Git's general-purpose check. Specifically, Gitaly knows that all objects in its repositories are always fully connected, and that received packfiles get filtered to maintain this invariant. This enables Gitaly to use a simpler object walk validation that wouldn't be safe for general Git repositories.

Steinhardt references a prior proposal (linked) where this approach was rejected for general Git usage but notes it's valid within GitLab's controlled environment. The reply strengthens the case for the RFC by explaining why GitLab needs to bypass Git's built-in check - their system performs equivalent validation with repository-specific optimizations that Git can't assume universally.

This addresses one of the open questions from the thread summary about whether GitLab's use case justifies core Git changes. The technical details about Gitaly's object connectivity guarantees provide important missing context for evaluating the security implications of the proposed skip mechanism.
