This is a naming debate in the ongoing `git-blame-tree` RFC discussion. Marc Branchaud strongly advocates against introducing a new command, arguing that the functionality should be integrated into the existing `git blame` command instead. He suggests that having two separate blame commands would worsen Git's reputation for obscurity, proposing that `git blame` should automatically handle directories differently from files (showing last-touched commits for each file when given a directory path).

Marc acknowledges Toon Claes' defense of the `blame-tree` name but remains unconvinced, emphasizing user experience over implementation concerns. He counters Toon's technical argument about differing codebases by suggesting either co-locating the implementations in blame.c or refactoring into separate files under a unified `git blame` interface. The email includes references to Jeff King's original naming rationale but interprets it as supporting integration rather than separation.

The discussion remains unresolved but has progressed to concrete alternatives like `git latest-revs` or `git when-modified`, with Marc maintaining that folding into `git blame` would provide the most intuitive user experience. This represents a key design decision point for the feature, with Marc's position adding weight to the naming debate that was already underway in the thread.
