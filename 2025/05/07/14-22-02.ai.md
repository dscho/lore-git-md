This is a naming discussion thread for the proposed `git-blame-tree` command, part of the ongoing RFC series introducing tree-level blame functionality.

Toon Claes responds to Marc Branchaud's concerns about the command name, defending the "blame-tree" terminology while remaining open to alternatives. The exchange reveals several perspectives: Marc argues the name contributes to Git's perceived obscurity and suggests either folding it into `git blame` (as a `--latest` mode) or choosing a completely different name without "blame". Toon counters that "blame" is an established Git concept that clearly communicates the command's purpose, and expresses concern that integrating with `git blame` would be technically awkward given the different implementations.

The thread references Jeff King's original naming rationale (where he considered `ls-tree` integration before settling on the blame analogy) but shows no clear consensus emerging. Toon ultimately takes a pragmatic stance - while preferring "blame-tree" for its clarity to Git users, he indicates willingness to accept alternatives like "latest-revs" or "when-modified" if the community prefers.

This discussion represents one of the key remaining open questions in the RFC (alongside merge behavior specification), with the technical implementation otherwise appearing production-ready. The naming debate touches on broader concerns about Git's command proliferation and user experience, making it likely to continue drawing commentary before finalization.
