This is a technical discussion about the command-line interface design for diff context overrides in interactive patch commands (part of the ongoing feature series).

Junio C Hamano responds to Phillip Wood's suggestion about documentation organization, agreeing that the option descriptions should be moved to a common include file. However, he strongly disagrees with the current implementation's behavior where `-U<n>` and `--inter-hunk-context=<n>` imply `--interactive/--patch`. 

The core argument is that automatically enabling interactive mode when context overrides are specified is problematic for several reasons: it creates ambiguity in command interpretation (particularly for `git add` which has both `-i` and `-p` variants), and it unnecessarily restricts future use cases where context width might be useful in non-interactive modes. 

Hamano proposes instead making it an error to use these options without explicitly specifying `-i` or `-p`, while leaving the door for future extensions where context width could be meaningfully used in non-interactive contexts. This represents a significant design change from the current patch implementation, requiring updates to both the documentation and option validation logic.

The discussion continues the thread's focus on refining the user interface aspects of the diff context control feature, with this email specifically addressing the interaction between context overrides and interactive mode selection. The technical implementation remains sound, but the UX design is being reconsidered based on maintainer feedback about future extensibility and command clarity.
