Naming debate continuation in git-blame-tree RFC thread.

Marc Branchaud continues advocating for integrating the new tree-blame functionality into the existing `git blame` command rather than creating a separate `git-blame-tree`. He argues that having two blame-related tools would worsen Git's reputation for command proliferation. His key technical proposal is to make `git blame` automatically handle directories differently from files, using the path type to determine whether to show line-level or file-level attribution.

The email provides concrete implementation suggestions:
1. Either merge the new 500-line tree-blame code into blame.c` alongside the existing 3000-line file-blame implementation
2. Or refactor into three components: `blame-file.c`, `blame-tree.c`, and a unified `blame.c` frontend

Marc directly addresses Toon Claes' counterarguments:
- Disputes that combining would hurt usability, calling the directory-vs-file behavior "intuitively useful"
- Challenges the technical difficulty claim, suggesting the code size impact is reasonable
- Rejects the "obscurity" concern about unified blame, calling it more discoverable

The thread remains at an impasse on naming, with:
- Toon defending `blame-tree` as conceptually clear but open to alternatives
- Marc strongly preferring `git blame` integration
- Other suggested names (`latest-revs`, `when-modified`) remaining secondary options

This email deepens the naming discussion with specific implementation pathways and stronger usability arguments, while the technical implementation of the feature itself remains unchanged from prior patches. The debate now centers entirely on command structure and user experience rather than core functionality.
