Feature proposal for `git receive-pack` with security implications. This is the second patch in a 2-part RFC series introducing a `--skip-connectivity-check` option, following the test infrastructure added in patch 1. The change allows bypassing Git's built-in object graph validation when receiving pushes, targeting GitLab's use case where connectivity is verified through an external staging system.

The implementation adds a hidden boolean option `--skip-connectivity-check` that, when enabled, skips the `check_connected()` call in `execute_commands()`. The patch includes a test case demonstrating successful push of an incomplete pack when the check is disabled, contrasting with the failure case tested in patch 1. The option is marked as hidden (OPT_HIDDEN_BOOL) to discourage casual use.

Key technical details:
- New global `skip_connectivity_check` flag in `builtin/receive-pack.c`
- Modified `execute_commands()` to conditionally skip connectivity validation
- Test case in `t/t5412-receive-pack.sh` verifies successful push with missing objects when check is disabled
- Option deliberately hidden from normal usage via OPT_HIDDEN_BOOL

Security considerations are central here - while the commit message notes the check is "critical" for normal operation, it proposes making the bypass available for specialized cases. The hidden flag suggests the author anticipates this being used primarily through controlled interfaces rather than direct user invocation. The test demonstrates the expected behavior but doesn't address potential abuse scenarios.

This will likely prompt discussion about:
- Whether the hidden flag is sufficient protection
- Alternative configuration approaches (config vs env var)
- Whether GitLab use case justifies core Git changes
- Potential security implications of exposing this bypass mechanism
- Whether the test coverage adequately captures edge cases

The patch appears technically sound but raises significant security questions that will need thorough review, particularly from contributors familiar with Git's security model and GitLab's transaction system.
