Keller raises an important practical consideration: if Change-IDs were stored in headers rather than trailers, there would need to be a way to preserve them through email-based patch workflows (like `git am`). This touches on the thread's ongoing tension between metadata persistence and user experience.

The contribution reinforces Oswald's point about aesthetic concerns being a barrier to adoption, while adding the Linux kernel's position as a data point. It also implicitly questions whether header-based storage would solve the workflow compatibility issues that trailers currently face in email-based collaboration. The email doesn't propose solutions but provides valuable real-world context about why the visual impact matters in practice.
