Performance optimization follow-up addressing memory management in batched reference updates. Jeff King (peff) identifies an inconsistency in string ownership between the batched reference update implementation and other call paths in the receive-pack error handling code. The current implementation duplicates strings for error messages when storing in the strmap and again when assigning to cmd->error_string, while other paths don't allocate at all.

The proposed change modifies `ref_transaction_error_msg()` to return string literals rather than allocated strings, eliminating the need for callers to free the result. This requires:
- Changing the return type to `const char *`
- Removing string duplication in receive-pack's error path
- Adjusting strmap cleanup to not free values (since they're literals)
- Updating all callers to handle the const return value

The change affects multiple commands (fetch, receive-pack, update-ref) but maintains identical behavior while simplifying memory management. This builds on the earlier batched reference update work by Karthik Nayak, which already introduced the `ref_transaction_error_msg()` helper in patch 5 of the series. The modification would make the API more consistent with Git's typical string handling patterns where possible.

Key technical points:
- Eliminates potential memory leaks in error paths
- Reduces allocations for error message handling
- Requires const-casting when storing literals in strmap
- Maintains same error message content and formatting
- Affects core refs.c and multiple builtin commands

This appears to be a logical refinement of the error reporting infrastructure introduced in the series, though it may warrant verification that no callers actually modify the returned strings (which would now be UB). The change is narrowly focused on memory management without altering the batched update behavior or performance characteristics.
