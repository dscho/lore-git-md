This is a discussion about Change-ID metadata storage in Git commits, specifically addressing the aesthetic concerns around trailer-based implementations.

Jacob Keller shares a real-world experience where his team's attempt to use Change-ID trailers in Linux kernel commits was rejected, primarily due to their visual intrusiveness in commit messages. This reinforces Oswald Buddenhagen's earlier point about trailers being "eye sores," especially in projects that don't otherwise use trailers. 

The email highlights a key tension in the Change-ID discussion: the need for persistent metadata versus maintaining clean commit messages. Keller notes that if Change-IDs were stored in headers rather than trailers, it would require different handling for email-based patch workflows (like `git am`), suggesting this is an important consideration for any alternative implementation.

This contribution adds practical weight to the ongoing discussion about finding a balance between functionality and aesthetics in Change-ID implementations. It shows how real projects have faced and rejected trailer-based approaches due to visual pollution concerns, which could inform the current design discussions around more subtle integration methods. The mention of Linux kernel maintainers' perspective provides valuable data point about what might be acceptable in large, conservative ecosystems.
