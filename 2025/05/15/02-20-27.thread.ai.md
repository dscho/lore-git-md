Thread identity: Documentation and UX patch clarifying commit descriptions in interactive rebase todo lists are comments, not directives. Originating author Elijah Newren, with follow-up from Reto and Phillip Wood. Core discussion about whether to prefix commit messages with '#' in rebase todo output.

Core problem or goal: Prevent users from mistakenly editing commit descriptions in rebase todo lists by making it visually obvious these are comments. Debate centers on balancing error prevention against readability, particularly regarding syntax highlighting impact.

Current status: Elijah's initial patch (version not specified) proposed prepending '#' to commit messages. Phillip Wood strongly supports this approach in his latest response, confirming the code changes look correct and suggesting a minor test improvement. The discussion has established this would be Git's fourth distinct use of '#' in output formats.

Key technical details:
- Modifies sequencer.c to prepend '#' to commit messages in todo list output
- Affects both regular pick lines and merge directives
- Updates tests in t3404, t3415, t3430, t5520, t7512
- Phillip suggests replacing grep/sed pipeline with `sed -n "!/^#/p"` in t5520
- Three existing uses of '#' in Git output cited as precedent:
  1. In merge command lines (between parents and subject)
  2. Appending '# empty' to empty commits
  3. As comment character in todo lists
- Uses hardcoded '#' instead of comment_line_str configuration
- Commit messages serve as primary navigation aids during rebases

Open questions/loose ends:
- Final resolution between readability and error prevention goals
- Whether editor behavior should influence Git's format (Phillip argues no)
- Impact on users who rely on commit messages for rebase navigation
- Whether to use hardcoded '#' or respect comment_line_str config

Participant positions:
- Elijah Newren (original author) advocates change to prevent user errors
- Reto objects based on readability impact during rebase navigation
- Phillip Wood strongly defends the approach, citing:
  - Consistency with existing Git output patterns
  - That editor implementations should handle Git's format correctly
  - That current behavior already uses '#' in merge command lines
  - Provides maintainer-level approval of technical approach
