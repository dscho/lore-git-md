This is a discussion about Change-ID implementation approaches in the ongoing thread about standardizing change tracking in Git. Oswald Buddenhagen responds to Junio Hamano's position that Change-IDs should be handled as commit message trailers rather than core Git object metadata.

Buddenhagen makes several nuanced points: while agreeing Change-IDs don't strictly need to be in commit objects, he notes there's no strong reason they couldn't be, comparing the situation to email headers where auxiliary metadata is conventionally included. He argues for at least proving Git can preserve such metadata intact, though acknowledges proper support would require creation/editing tools.

The email highlights key use cases for Change-IDs - tracking evolving changes across branches - where having the ID in the commit message itself provides practical advantages for operations like squashing. However, Buddenhagen also recognizes the visual clutter concern, particularly for smaller projects, suggesting a more integrated Git implementation might make Change-IDs more palatable to such users.

The discussion remains technical and constructive, with Buddenhagen offering a middle-ground perspective between Junio's trailer-based approach and more invasive Git modifications. His points about metadata handling and user experience considerations add depth to the thread's exploration of Change-ID tradeoffs.
