This is a discussion about a documentation/UX patch for Git's interactive rebase interface. The original patch (from Elijah Newren) proposed prefixing commit descriptions in the rebase todo list with '#' to make it clearer they are comments rather than rebase directives. 

Reto raised concerns that syntax highlighting in editors might dim these prefixed messages, making them harder to read during rebase operations where commit messages serve as important navigation aids. Phillip Wood defends the approach, noting Git already uses '#' in similar contexts (merge command lines and empty commits) and argues that only lines starting with '#' should be treated as comments by editors.

The debate centers on balancing error prevention (preventing users from mistakenly editing commit messages thinking they'll affect the rebase) against readability during interactive rebase sessions. Phillip's latest response emphasizes this is a hardcoded '#' rather than using comment_line_str, and suggests editor implementations that dim mid-line '#' characters are buggy.

This appears to be a well-reasoned technical discussion between experienced contributors, with valid points on both sides about user experience tradeoffs. The thread hasn't reached consensus yet, but Phillip's arguments about existing precedent and proper editor behavior may carry weight in future discussion.
