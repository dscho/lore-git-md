This is a naming and integration discussion for the proposed `git-blame-tree` (or alternative) functionality. Jeff King responds to Marc Branchaud's "last-touch" naming proposal by tracing the command's lineage back to an earlier "git-last-modified" script, suggesting the current "blame-tree" name may be doubly inaccurate - both for using "blame" and for implying tree-specific operation when the tool actually works with arbitrary pathspecs.

King explores two alternative integration approaches: (1) a `git log --last-modified` variant that would output commit hashes and raw diffs for paths matching the initial pathspec, stopping when all paths have been accounted for, and (2) a standalone `git last-modified` command that could offer similar flexibility with format/diff options. Both proposals emphasize the tool's core functionality - tracking modification times across arbitrary path sets rather than just tree entries.

The email doesn't resolve the naming debate but adds technical nuance by:
1. Challenging the "tree" component of the current name as too narrow
2. Demonstrating how the functionality could conceptually fit into `git log`'s pathspec processing
3. Showing how output formatting could be achieved through existing diff/log mechanisms
4. Maintaining focus on the tool's actual capability (path modification tracking) rather than implementation details

This continues the thread's central tension between technical implementation similarities (with blame/log) and user mental model differences, while introducing new integration possibilities that might bypass the naming debate entirely. The discussion remains at the architectural level with no immediate resolution, though King's historical context and alternative proposals provide fresh angles for consideration.
