Bug report about `git submodule` behavior when adding submodules with same name but different paths. The reporter demonstrates a case where moving a submodule (using `git mv`) and then adding a new submodule with the original name causes the original submodule's information to be lost from `.gitmodules`. The key issue is that Git uses the submodule name (not path) as the identifier in `.gitmodules`, and when a new submodule is added with the same name, it overwrites the existing entry rather than creating a disambiguated one.

The reporter provides clear reproduction steps showing:
1. Creating a parent repo with a "child" submodule
2. Moving it to "child_old" (which updates path in `.gitmodules` but keeps the name)
3. Adding a new "child" submodule at the original path
4. Observing the original submodule's configuration is lost

The expected behavior would be to preserve both configurations, perhaps by disambiguating names (e.g. using ".path" suffixes). The bug affects Git 2.49.0 and could lead to data loss of submodule origins when repositories are reorganized this way. The report is well-documented with complete system info and clear reproduction steps.
