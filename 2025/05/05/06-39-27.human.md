This is a performance discussion about handling large packed-refs files during fsck operations, continuing from the platform compatibility thread about BSD errno behavior.

Patrick Steinhardt from GitLab chimes in with real-world data on packed-refs file sizes, noting that while most are under 50MB (often under 5MB), outliers like GitLab's own repository can reach 2GB. This supports Jeff King's earlier suggestion to use mmap() instead of strbuf for reading packed-refs during fsck, particularly for large repositories in fork networks.

The discussion reveals interesting scale differences between GitHub and GitLab's largest cases - where GitHub's torvalds/linux fork network creates ~1.5GB packed-refs files, GitLab's worst case is even larger at 2GB. While not urgent (as Patrick notes these systems have beefy resources), the mmap optimization would be sensible for these extreme cases.

This side-thread remains distinct from the core BSD errno resolution (where lstat() is the agreed solution), but provides useful context about real-world repository scaling that may inform future fsck optimizations. The performance discussion appears to be converging toward a potential mmap refactoring, though no patches have been proposed yet.
