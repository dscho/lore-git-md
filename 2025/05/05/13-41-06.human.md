This is a bug report about `git submodule` behavior when dealing with renamed submodules. The reporter, Moritz, demonstrates that when you move a submodule (using `git mv`) and then add a new submodule with the original name, Git silently overwrites the old submodule's information in `.gitmodules` rather than preserving both entries.

The issue occurs because Git uses the submodule name (not path) as the key in `.gitmodules`, and moving a submodule only updates its path while keeping the original name. When adding a new submodule with the same name but different path, Git overwrites the existing entry instead of creating a new one with a disambiguated name (like appending ".path" as suggested).

The report includes clear reproduction steps showing how the old submodule's URL information is lost, and suggests expected behavior where both submodules would be preserved with distinct names. This appears to be a genuine bug in submodule handling that could cause data loss scenarios when reorganizing repositories with submodules. The report is well-structured with clear before/after examples and system information.
