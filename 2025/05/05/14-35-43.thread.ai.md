Feature inquiry from Akash S (Commvault) about incremental Git backup strategies to replace full `git clone --bare` daily backups. Core question remains whether Git's object model can support change-based snapshots with enterprise-grade reliability. Discussion has evolved through multiple technical approaches with quantitative analysis:

1. **Bundle-based incrementals** (Justin Tobler, Abhishek Dalmia):
   - Validated mechanics: initial full `--all` bundle followed by time-based incrementals
   - Confirmed restore process: `git clone -bare` plus `git fetch` with explicit `refs/*:refs/*` pattern
   - Edge cases: bundle dependency chains, timestamp vulnerability (backdated commits)

2. **State-tracking alternatives** (Jeff King/peff):
   - Snapshot file tracking backed-up objects (parsing bundle headers)
   - Direct ref snapshots (`for-each-ref`) with thin packs (`pack-objects`)
   - Advantages: eliminates timestamp vulnerability, better state control
   - Packed objects in linux.git show 56x space savings over loose (2.4GB vs 135GB)
   - Additional inode overhead for loose objects makes filesystem approaches less viable

3. **Filesystem-level approaches** (Michal Suchánek):
   - Initial ZFS/Btrfs deduplication proposal shown 14x less space-efficient than pack-based
   - Updated incremental approach using shared clones with `fetch -p` and `repack -adk --cruft --local`
   - Requires `--mirror` for initial clone to simplify updates
   - Maintains technical correctness but doesn't challenge pack-based superiority
   - Now positioned as suboptimal fallback option with untested implementation

4. **Metadata discussion closure** (Jeff King/peff has dismissed Randall Becker's suggestion of incorporating blame/annotation metadata as not useful for core backup needs.

Technical progression shows:
- All approaches maintain focus on reliability requirements
- Bundle method viable but with timestamp limitations
- State-tracking provides most robust solution (timestamp + space efficiency)
- Filesystem approaches quantitatively inferior (14x worse space efficiency)
- Pack-based solutions clearly superior for space conservation
- Metadata exploration considered and rejected

Critical constraints:
- Must ensure complete data integrity
- Bundle restore cannot mirror remote's `--all` behavior
- Enterprise needs timestamp-independent solutions
- Storage efficiency remains key factor

Open questions:
