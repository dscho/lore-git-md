This is a follow-up discussion in the platform compatibility thread about packed-refs handling, now shifting focus to performance optimization.

The email from shejialuo acknowledges Jeff King's (Peff) and Patrick Steinhardt's explanations about the performance implications of reading large packed-refs files. The key points from prior discussion that inform this response are: (1) current code reads entire packed-refs into memory rather than using mmap, (2) while most packed-refs files are small (<5MB), outliers like GitLab's 2GB case exist, and (3) mmap would be more efficient even without process sharing.

Shejialuo confirms understanding of the performance considerations and states intent to submit a patch converting the packed-refs reading to use mmap. This represents a logical next step in the thread, moving from the BSD errno resolution to optimizing the file handling that was incidentally noticed during that work. The mmap approach aligns with existing Git practices for large file handling and would benefit repositories with extremely large ref counts.

The technical context for the future patch includes:
- Current implementation in wrapper.c reads packed-refs into strbuf
- GitLab.com metrics show 99% of cases are <50MB but 2GB outliers exist
- mmap would avoid memory copying and enable sharing with other processes
- Follows from Jeff King's observation during BSD errno discussion

This positions the upcoming patch as a performance optimization building on the platform compatibility work, with clear motivation from real-world repository scaling data. The change appears uncontroversial given the established patterns for similar cases in Git's codebase.
