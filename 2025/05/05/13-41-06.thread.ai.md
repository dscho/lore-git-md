Git submodule name/path collision bug report. Reporter demonstrates that when a submodule is moved (via `git mv`) and a new submodule is added with the original name, Git's `.gitmodules` handling overwrites the original configuration rather than preserving both entries. Current behavior uses submodule name as primary key in `.gitmodules`, causing data loss when:

1. Submodule "child" exists at path "child"
2. `git mv child child_old` updates path but keeps name="child"
3. New submodule added with name="child" at original path
4. Original submodule's config disappears from `.gitmodules`

Expected behavior would disambiguate by preserving both configurations, possibly via path-qualified names. Reproduction provided for Git 2.49.0 showing clear data loss scenario. Issue affects repository reorganizations where submodule names are reused at original paths after moves. No workaround mentioned; potential solutions would need to either:
- Make `.gitmodules` entries path-aware
- Generate unique names when collisions occur
- Preserve original config with warning
