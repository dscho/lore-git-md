This is a contributor housekeeping discussion about the status of unmaintained scripts in Git's `contrib/` directory, sparked by the ongoing `git svn` Windows issues.

Patrick Steinhardt responds to Johannes Schindelin's suggestion to deprecate Windows support for `git svn` by broadening the discussion to question the purpose of Git's `contrib/` directory as a whole. He argues that many scripts there create a false impression of being officially supported when they are actually unmaintained, suggesting either a comprehensive cleanup or reconsideration of keeping the directory in the main Git repository.

The email references the `git svn` discussion as a specific example of this broader problem, where Windows users encounter cryptic errors with a tool that lacks active maintainers. Steinhardt notes there's no clear strategy for `contrib/` and proposes two options: either perform a cleanup to remove long-neglected scripts, or reconsider whether such scripts belong in Git's main repository at all.

This shifts the conversation from the specific Windows `git svn` issues to a more fundamental question about Git's maintenance philosophy regarding contributed-but-unmaintained tools. The key technical context remains the Perl warnings and branch initialization failures from the original report, but the focus is now on the policy question of how to handle such cases systematically rather than fixing this particular issue.
