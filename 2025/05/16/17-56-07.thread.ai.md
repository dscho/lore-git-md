MPTCP support thread summary:

This thread discusses Multipath TCP (MPT CP) support for Git on Linux systems, initially proposing automatic use of MPTCP v1 when available with fallback to regular TCP for the legacy Git protocol (port 9418). The discussion has evolved into a debate between automatic adoption versus configurable opt-in, with Brian Carlson advocating for conservative compatibility and Muhammad Nuzaihan defending the implementation's robustness.

Key technical details include: MPTCP's dual IPv4/IPv6 support, the v1/v0 distinction (v1 having proper fallback mechanisms), current limitation to port 9418 connections, and compile-time `#ifdef` checks. The implementation modifies socket creation in `connect.c` without configuration changes initially. Muhammad has now proposed three specific technical improvements: (1) adding a `__linux__` compile-time check to explicitly limit the feature to Linux, (2) handling `EAI_SOCKTYPE` errors (POSIX-standard error for unsupported socket types) to fall back to regular TCP, and (3) maintaining the existing `IPPROTO_MPTCP` availability check.

Brian has raised multiple compatibility concerns: (1) stripped-down kernels lacking MPTCP support despite headers being present (common in containers), (2) IPv6-only connections on IPv4-only MPTCP systems, (3) historical issues with Go 1.24's server-side MPTCP rollout (CVE-2022-49198), and (4) the Linux-only nature needing explicit documentation. He advocates for making MPTCP configurable via `.gitconfig` while keeping it default-off.

Phillip Wood has now joined the discussion, reinforcing Brian's compatibility concerns while offering concrete implementation suggestions. He proposes a Makefile knob (USE_MPTCP) defaulting to on for Linux builds, addressing container compatibility issues. Phillip emphasizes the need to verify error handling against Linux's actual MPTCP behavior rather than relying solely on POSIX error codes. He also stresses documentation quality, urging clear explanation of MPTCP's benefits (bandwidth aggregation for large repos) and tradeoffs in commit messages, referencing Junio Hamano's review standards.

Muhammad has provided empirical validation (Wireshark screenshots) demonstrating successful MPTCP operation with the legacy protocol. He maintains that MPTCP v1's improved fallback behavior addresses these concerns, while proposing to add a `--mptcp` flag for `git-daemon` as a server-side opt-in. He cites MPTCP's 15-year maturity (v1 improvements since 2020) and personal use cases with large repositories (50GB) benefiting from bandwidth aggregation and failover. The implementation remains client-side only (`connect.c`) currently.

Open questions include: whether to make MPTCP configurable client-side (via Makefile knob and/or runtime config), how to handle cross-platform limitations (Linux-only with macOS as possible future work, excluding FreeBSD), and documentation of platform limitations. The technical discussion has progressed on fallback mechanisms but configuration design and documentation remain unresolved, with Phillip's suggestions providing concrete steps toward a more robust implementation while maintaining Git's cross-platform philosophy.
