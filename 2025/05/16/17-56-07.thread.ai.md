MPTCP support thread summary:

This thread discusses Multipath TCP (MPT CP) support for Git on Linux systems, initially proposing automatic use of MPTCP v1 when available with fallback to regular TCP. The discussion has evolved through architectural concerns, technical implementation details, configuration design, and now includes server deployment considerations.

Muhammad Nuzaihan's original proposal has been strengthened with production deployment evidence and implementation improvements using `core.mptcp` configuration (default false for clients, true for servers). Matthieu Baerts (Linux kernel MPTCP maintainer) provided key technical clarifications explaining Linux's MPTCP requirements through `IPPROTO_MPTCP` socket creation, validating the approach while addressing Junio Hamano's initial RFC 6897 transparency concerns. Matthieu confirmed Linux's robust fallback to TCP when MPTCP is unavailable, with production-proven behavior since Apple's 2013 deployment.

Junio's latest email focuses on server-side deployment, particularly `git-daemon` usage patterns. He confirms understanding that MPTCP doesn't impact non-MPTCP socket performance but notes the opt-in requirement's adoption challenges. A new practical concern emerges regarding `inetd`-managed `git-daemon` deployments, where MPTCP support would be determined by `inetd`'s socket configuration rather than Git's settings. While server-side MPTCP is low-risk (falling back to TCP when clients don't request it), this introduces a new documentation requirement for server administrators. Junio also observes declining `git://` protocol usage in favor of HTTPS/SSH, though this doesn't directly affect the MPTCP discussion.

Key technical details established include: MPTCP's mandatory opt-in nature on Linux, dual IPv4/IPv6 support, Linux-specific socket requirements, current port 9418 limitation, platform-specific checks in `connect.c`, header overhead implications, and now `inetd` integration considerations. The proposal maintains Git-idiomatic configuration while addressing platform constraints.

Open questions now include: (1) final configuration approach (global vs per-repository/host settings), (2) performance impact documentation needs, (3) use case justification beyond WiFi/Ethernet handoff, (4) latency/throughput tradeoff guidance in documentation, and (5) `inetd` deployment documentation requirements. The thread continues productive collaboration between Git contributors and MPTCP maintainers, with Junio ensuring the design aligns with Git's configuration philosophy while surfacing real-world deployment considerations. Matthieu's technical clarifications and Junio's operational insights have strengthened the proposal's foundation while leaving policy decisions to Git maintainers.
