This is a performance-oriented question about Git's index handling. Jon Forrest asks whether the index is fully resorted on every `git add` operation (which would be inefficient) and proposes an alternative "index index" design where only a smaller metadata file would need sorting.

The proposal suggests maintaining two files: an unsorted main index that grows by appending, and a smaller sorted "index index" containing just filenames and pointers. Deletions would be marked in-place in the main index and cleaned up later by `git fsck`. Jon acknowledges this may have been considered before and asks for feedback.

The email shows thoughtful analysis of a real performance concern, though it's unclear how much overhead the current sorting actually causes in practice.
