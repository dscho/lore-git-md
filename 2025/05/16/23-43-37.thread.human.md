Jon Forrest proposed a "two-file index" design to optimize Git's index file handling, aiming to avoid expensive full resorting during `git add` operations in large repositories. His approach would separate sorted filename lookups from unsorted entry storage, reducing data movement at the cost of added complexity.

K Jayatheerth provided a clarifying response, explaining that Git's current index implementation already maintains an in-memory sorted array, with disk writes simply serializing this structure. While acknowledging the theoretical appeal of Jon's proposal, Jayatheerth noted practical tradeoffs: the "index index" approach could reduce write amplification for adds but would complicate read operations and introduce synchronization overhead between files. The response pointed to existing optimizations like split index and untracked cache that already address some performance concerns, suggesting the new design might only benefit edge cases with very large repositories. 

The discussion remains at the conceptual stage, with no implementation yet. Key open questions include the proposal's impact on other index operations, performance characteristics, and compatibility with existing tools. While Jon's idea presents an interesting direction, Jayatheerth's response suggests the current implementation may already be well-optimized for typical use cases.
