Performance optimization for packfile handling focusing on syscall reduction in multi-pack-index scenarios, originally proposed by Patrick Steinhardt and refined through discussion with Jeff King. The thread has concluded with maintainer approval of a two-patch series that safely reduces syscalls while preserves Git's packfile integrity invariants, with ongoing implementation discussion.

Core problem addressed: Stale MIDX entries were causing repeated failed lookups of missing packfiles via multiple syscall (access() and stat()). While impact is small in well-maintained repos, the optimization provides measurable performance improvements without compromising safety.

Final solution (v2 series now queued by Junio Hamano):
1. First patch documents critical ordering requirements for auxiliary file checks (`.keep`, `.promisor`, `.mtimes`) relative to packfile existence checks, establishing two key invariants: (a) auxiliary files must exist before their `.idx` file during creation, and (b) must be deleted after their `.pack` file during removal
2. Second patch implements negative lookup cache in midx.c (Jeff King's suggestion) by storing -1 in midx->packs[] for missing entries, with performance measurements showing 4x speedup for `git log --patch` and syscall reduction from 24,083 to 83 in test case

Technical implementation details:
- prepare_midx_pack() caches failed lookups using -1 sentinel
- nth_midxed_pack() returns NULL for cached misses
- close_midx() skips -1 entries during cleanup
- Maintains all safety constraints through type-punned pointers following Git conventions
- Preserves correct cleanup paths and existing midx cache invalidation during repacking
- Jeff King proposes two cleaner alternatives to current type-punning approach:
  a) MIDX_PACK_ERROR macro to hide magic number
  b) Separate pack_errs bit array to track failures (more thorough refactoring)
- Both alternatives maintain same performance characteristics while improving code clarity

New safety concerns raised by Junio Hamano regarding Jeff King's bit array proposal:
1. Interaction between prepare_midx_pack()'s error caching and subsequent pack access patterns needs verification
2. Safety of passing potentially NULL pack pointers to is_pack_valid() (which doesn't handle NULL inputs)
3. Correctness of pointer arithmetic when accessing packs across base/non-base pack boundaries (pack_int_id - m->num_packs_in_base)

Jeff King's latest analysis confirms:
- fill_midx_entry() correctly handles pack lookups by always calling prepare_midx_pack() first
- prepare_midx_pack()'s midx_for_pack() call is redundant for some callers but necessary for others
- Potential fragility in midx-write.c functions (want_included_pack() and fill_included_packs_batch()) regarding non-base MIDX files
- Suggests returning pack pointers directly from prepare_midx_pack() could simplify some call sites while acknowledging edge cases remain
- Identifies subtle interactions between MIDX chain traversal and pack ID resolution that could benefit from refactoring
