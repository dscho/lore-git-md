This is a discussion response in the ongoing thread about removing Git's exec-path from non-Git child processes' PATH environment variable. Phillip Wood raises several key points in response to the original patch series from D. Ben Knoble.

Phillip argues that the core issue stems from scripts making incorrect assumptions about Git's installation layout rather than Git's PATH modification being inherently problematic. He notes that distributions have discretion over where Git's contrib scripts are installed, making fixed-path assumptions unreliable. More importantly, he highlights that Git intentionally modifies the environment (including PATH) when spawning child processes like editors to maintain version consistency - for example, ensuring `git diff` called from an editor uses the same Git version as the parent process.

The response suggests that while the first two patches (test cleanup and strvec API conversion) are welcome improvements, the rationale for the PATH modification changes in patches 3-4 may be justified. Phillip provides a workaround for users who want a clean environment in editor-spawned terminals, while maintaining that Git's current behavior serves important version-consistency purposes.

This continues the thread's central tension between security (removing internal paths from child environments) and compatibility (maintaining consistent Git version execution). Phillip's perspective favors the compatibility side, particularly emphasizing the importance of GIT_EXEC_PATH for version matching in subprocesses. The discussion remains unresolved, with the author planning to submit alternative versions of the patch for comparison.
