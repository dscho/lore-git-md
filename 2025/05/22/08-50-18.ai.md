The conversation between Karthik Nayak and Jeff King explores whether `strmap_put()` should accept `const void*` parameters to avoid explicit casting in the reference transaction code.

Jeff King argues against changing the strmap API to accept const pointers, explaining that C's type system limitations make it impossible to properly represent the desired const semantics. He notes that while strmap doesn't modify the data, callers might need non-const access later, so explicit casting at the call site is safer than silently dropping const-ness in the API. He also outlines (but rejects as too cumbersome) a potential runtime-checked approach using separate const/non-const functions.

Karthik initially suggests the const change might be worthwhile as a #leftoverbits item, but ultimately agrees with Jeff's analysis about the type system limitations and safety tradeoffs. The discussion confirms that the current approach with explicit casting is the most practical solution, despite not being theoretically ideal.

This exchange doesn't affect the already-approved batched reference updates series, but provides valuable context for future API design considerations.
