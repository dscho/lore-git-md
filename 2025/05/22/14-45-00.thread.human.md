Here's the updated human-readable summary:

The thread began with Roel Sengers reporting a significant performance regression in `git status` when working with hard-linked large files (1GB+), even when those files are in `.gitignore`. The initial reproduction showed a dramatic difference - 16 seconds for hard links versus 2ms for regular copies of the same files.

Justin Tobler has now responded with a technical analysis explaining the root cause: Git treats hard links differently because creating them modifies the original file's metadata (link count and ctime), which causes Git to perform a full index refresh. For regular copies, since the original file's metadata remains unchanged, Git can skip this expensive operation. Justin provided a concrete workaround - setting `core.trustCTime=false` - which eliminates the performance gap by telling Git to ignore ctime changes.

While this explains the behavior and offers a practical solution, the deeper questions remain open: Should Git be this sensitive to metadata changes for hard links? Is there a way to optimize this case, particularly for ignored files? The thread now awaits input from maintainers or others who might have insights into whether this is working as intended or represents an opportunity for optimization.
