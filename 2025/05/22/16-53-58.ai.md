This is a bug report about HEAD.lock contention between Git operations and maintenance processes. The reporter describes a scenario where their automated system running Git commands (including stash, checkout, fetch) intermittently fails during `git checkout b2` due to a HEAD.lock file existing. The issue appeared after upgrading from Git 2.39.5 to 2.47.2. 

Key technical details: the reporter observed via GIT_TRACE_PERFORMANCE that Git's auto-maintenance (triggered after fetch) sometimes runs in detached mode and acquires HEAD.lock, which conflicts with their checkout operation. They suspect the maintenance process is the lock holder and are considering disabling auto-detach via maintenance.autoDetach=false as a workaround.

The report provides a clear reproduction sequence and version change context, but doesn't include stack traces or exact error messages. The core question is whether this is expected behavior (with maintenance legitimately taking locks) or a bug in lock contention handling between user operations and background maintenance. The reporter is specifically asking for maintainer input on whether their proposed workaround is appropriate or if this warrants a code fix.
