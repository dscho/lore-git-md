This is the second patch in a 4-part bugfix series addressing integer overflow issues in multi-pack-index repacking, specifically targeting a potential 64-bit overflow scenario. The patch 2/4 focuses on preventing overflow in the calculation of expected pack sizes during repacking by using shifted integer arithmetic.

The key technical change reorders operations and introduces bit-shifting (14 bits) to avoid overflow when multiplying pack_size by referenced_objects. The solution divides pack_size by total objects first, then multiplies by referenced objects, with the shift operations maintaining about 4 significant digits of accuracy while preventing overflow for pack sizes under 1PB. The patch uses the new u64_mult() and u64_add() utilities introduced in patch 1/4, with rounding added via the `+ (1u << 13)` term before the final right shift.

This approach was previously endorsed by Taylor Blau based on production experience with large packs. The implementation matches the solution described in the thread summary, with no changes from v1 as the technical approach had consensus. The patch modifies midx-write.c's repack logic where it calculates expected sizes for batch repacking, specifically in the fill_included_packs_batch() function.

The commit message clearly explains the overflow scenario (2^28 objects at 1KB each could overflow 64-bit math) and the solution's accuracy tradeoffs. The code changes are thorough, including both the arithmetic restructuring and clear explanatory comments about the 14-bit shift's purpose and limitations. This patch completes the series' technical fixes after patch 1/4 addressed 32-bit overflows and patch 3/4 handles type consistency.
