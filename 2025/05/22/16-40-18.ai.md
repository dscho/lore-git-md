Performance regression analysis with workaround suggestion for hard link index refresh issue.

This email from Justin Tobler responds to Roel Sengers' bug report about `git status` performance with hard-linked large files. The key technical explanation is that Git's index refresh behavior differs between hard links and copies due to metadata changes - specifically, creating a hard link updates the link count and ctime of the original file, triggering a full index refresh, while copies don't modify the original file's metadata.

The email provides a concrete workaround: setting `core.trustCTime=false` to make Git ignore ctime differences. This directly addresses the reported 16s vs 2ms performance gap by preventing the unnecessary index refresh. The explanation clarifies why the behavior occurs (metadata changes vs content changes), but doesn't yet address whether this is the desired behavior or if there should be special handling for hard links to ignored files.

This moves the thread forward by:
1. Confirming the root cause (metadata-triggered index refresh)
2. Providing an immediate workaround
3. Leaving open the deeper design question of whether Git should optimize this case

The response is technically sound but doesn't yet engage with the broader questions from the original report about whether this behavior is correct or could be improved. The workaround suggests the issue may be more about Git's metadata sensitivity than hard link handling specifically.
