**Bug report about performance regression with hard-linked files**

Roel Sengers reports a significant performance issue when Git encounters hard links to large files in the working directory. The key observation is that while copying a 1GB file (listed in `.gitignore`) results in near-instantaneous `git status` operations, creating a hard link to the same file causes `git status` to take 16 seconds to complete.

The report includes a clear reproduction script showing that:
1. A fresh repo with a 1GB binary file
2. Copying the file to an ignored location (`ignore.bin`) shows normal performance (2ms)
3. Hard-linking the same file shows dramatically worse performance (16s)

The reporter notes this occurs both with and without git-lfs enabled, and that while they could work around it by copying files instead, this would be storage-inefficient for their 80GB workflow. The behavior is particularly surprising since the file is explicitly ignored via `.gitignore`.

This appears to be a genuine performance bug in Git's index refresh logic when dealing with hard links, where it's doing unnecessary work for ignored files. The clear reproduction case and timing measurements make this a well-documented report that should be straightforward to investigate.
