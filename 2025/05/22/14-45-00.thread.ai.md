Thread identity: Performance regression report about `git status` being slow with hard-linked large files (1GB+) in working directories, even when files are in `.gitignore`. Original reporter Roel Sengers provided reproduction showing 16s vs 2ms difference between hard links and regular copies. Justin Tobler has now responded with technical analysis.

Core problem: Git performs full index refreshes when encountering hard links to large files (even ignored ones) due to metadata changes (link count and ctime updates), while skipping this for regular copies. This creates significant performance penalty for workflows using hard links for space efficiency with large files.

Current status: Justin Tobler confirmed the root cause and provided a workaround (setting `core.trustCTime=false` to ignore ctime differences), which resolves the immediate performance gap. The deeper design questions about whether this behavior is correct or could be optimized remain open.

Key technical details:
- Issue manifests in `git status` performance
- Root cause is metadata-triggered index refresh (link count/ctime changes)
- Workaround via `core.trustCTime=false` confirms the diagnosis
- Still affects files listed in `.gitignore`
- Reproduction uses 1GB file to demonstrate scale of problem
- Open questions:
  - Should Git optimize index refresh behavior for hard links?
  - Should `.gitignore` status affect this behavior?
  - Is this a regression or long-standing behavior?
