This is a technical discussion in the ongoing thread about removing Git's exec-path from non-Git child processes' PATH environment variable. Phillip Wood responds to D. Ben Knoble's initial series with concerns about the proposed changes.

Phillip argues that the core issue stems from scripts making incorrect assumptions about Git's installation layout rather than Git's environment modification being inherently problematic. He notes that distributions have discretion over where contrib scripts are installed, making fixed-path assumptions unreliable. The discussion highlights Git's legitimate need to modify the environment when running editors - specifically maintaining GIT_EXEC_PATH in PATH ensures version consistency when editors spawn Git subprocesses (like for showing staged diffs), preventing subtle version mismatch bugs.

The email raises important considerations about environment handling tradeoffs: while the proposed changes aim to prevent Git internals from leaking into non-Git processes, Phillip contends that Git's current behavior of setting GIT_EXEC_PATH serves important version consistency purposes. He suggests alternative approaches for users wanting clean environments, like shell scripts to sanitize PATH and unset Git-specific variables.

Phillip supports the first two patches (test cleanup and strvec API conversion) but expresses skepticism about patches 3 and 4's rationale. His response adds weight to the emerging consensus that the narrow editor-focused approach may be insufficient, as it doesn't address the legitimate cases where Git needs to modify PATH for its own subprocess consistency. The discussion continues to highlight the tension between security (preventing internal tool exposure) and functionality (maintaining versioned subprocess execution).
