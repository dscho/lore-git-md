Thread identity: Bug report and fix series for HEAD.lock contention between Git operations and maintenance processes, originating from a user experiencing failures after upgrading from Git 2.39.5 to 2.47.2, with Patrick Steinhardt leading the solution effort and Emily Shaffer from Google providing corroboration.

Core problem: Race condition where maintenance in detached mode (`--auto --detach`) spawns git-gc which locks packed-refs, conflicting with concurrent ref-modifying operations like checkout. The version change (2.39.5->2.47.2) suggests this behavior relates to maintenance changes in recent Git versions. Google has independently encountered this issue in production, confirming it's a real-world problem.

Current status: Patrick Steinhardt has sent the promised patch series (20250527-b4-pks-maintenance-ref-lock-race-v1-0-e1ceb2dea66e@pks.im) to address the race condition. The solution modifies git-maintenance to handle ref-packing tasks before daemonization, making the caller wait for ref packing completion. The thread has progressed from diagnosis to implementation stage.

Key technical details:
- Reproduction involves concurrent checkout and maintenance operations
- Maintenance runs in detached mode during fetch-triggered auto-maintenance
- HEAD.lock contention occurs between git-gc's packed-refs locking and user operations
- Current workaround: adjust `core.packedRefsTimeout` (masks but doesn't fix)
- Solution implementation: patch series modifies git-maintenance to run ref-packing pre-daemonization
- Expected behavior change: maintenance caller waits for ref packing completion
