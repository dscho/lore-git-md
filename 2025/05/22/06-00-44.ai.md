This is a technical discussion about potential improvements to the `strmap` API, arising as a follow-up to the now-completed batched reference updates series. Jeff King (peff) responds to Karthik Nayak's suggestion about making `strmap` handle const pointers more cleanly.

The discussion centers on whether `strmap_get()`/`strmap_put()` should accept `const void*` parameters to avoid casting away constness in the batched ref updates code. Peff argues against this change, pointing out that while the current implementation requires explicit casting, it's actually safer than silently casting away constness in the API. He explains the type system limitations in C that make this tricky to solve cleanly, and sketches (but ultimately rejects) a possible runtime-checked solution involving const-specific variants of the functions.

Key technical points:
- Current `strmap` API uses `void*` for both storage and retrieval
- Proposed change would accept `const void*` on input but still return `void*`
- Peff identifies this as potentially dangerous as it hides const-casting
- Discussion reveals fundamental C type system limitations for this use case
- Alternative runtime-checked approach proposed but deemed too cumbersome
- The `#leftoverbits` tag remains as a non-blocking future consideration

This email doesn't propose any immediate changes to the batched ref updates series (which is already approved) but documents an interesting API design discussion that may inform future `strmap` improvements.
