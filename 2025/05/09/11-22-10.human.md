This is a follow-up in the ongoing discussion about incremental Git repository backups, focusing on filesystem-level approaches.

Michal Suchánek expands on his earlier filesystem-based proposal for incremental backups, suggesting a method using shared clones with `fetch -p` and `repack -adk --cruft`. The key points are:

1. He clarifies that the initial clone should use `--bare --mirror` for easier updates, and recommends repacking with `-adk` (including the `--cruft` flag) to reduce repository size while avoiding corruption.

2. The incremental approach involves creating shared clones of the full backup, updating their origin URLs, and fetching with `-p` to prune deleted references. Repacking requires the `--local` flag in this setup.

3. Michal notes this method hasn't been tested and acknowledges it will accumulate cruft over time. The resulting repositories would be valid for inspection or export but should be made read-only to prevent corruption.

This continues the thread's pattern where filesystem approaches remain technically possible but are acknowledged as suboptimal compared to pack-based solutions. The proposal doesn't address the previously noted space efficiency issues with filesystem methods or challenge the established superiority of pack-based approaches. It does provide a more detailed workflow for those who might need a filesystem-based fallback option.
