This is a bug report and feature request regarding `git log` filtering and display issues when trying to exclude spammy bot commits.

Oswald Buddenhagen describes several pain points when trying to filter out bot-generated spam from repository history. The current workaround using `--perl-regexp --author` is cumbersome and unintuitive. More critically, using `--graph` with filtered output produces broken history visualization since parent rewriting logic doesn't handle this case properly.

The report also notes that path-based filtering (viewing only a specific subdirectory) creates incomplete branch/tag displays, as decorations are omitted for commits not shown in the output. The author suggests it would be useful to have "fake" decorations with visual indicators when parent rewriting occurs.

These issues particularly impact `git log --all` and the gitk interface, making it difficult to get a clear overview of repository activity when spam commits are present. The problems appear to stem from how history simplification interacts with various filtering options and visualization tools.

The report doesn't propose specific implementation solutions, instead highlighting real-world usability problems that emerge when trying to manage repositories with high volumes of bot-generated commits. The issues described suggest gaps in Git's filtering and visualization capabilities that could benefit from improved handling of excluded commits.
