This is a follow-up investigation in the ongoing thread about `git pull --rebase` dropping commits after remote URL changes. Tuomas Ahola has identified a related anomaly in how `git merge-base --fork-point` behaves differently depending on whether the remote is accessed via its original URL or a newly added duplicate.

The key observation shows that when a repository has two remotes pointing to the same upstream (one via `set-url` and one freshly added), `merge-base --fork-point` returns different results - a concrete commit hash for the original remote but nothing for the duplicate remote. This suggests the fork-point calculation may be incorrectly tied to remote URL history rather than commit topology.

This finding appears directly relevant to the original bug where commits disappear during rebase operations after remote URL changes, as both involve Git's handling of remote tracking relationships. The investigation is now moving from reproduction to root cause analysis, with this new data point about `merge-base` behavior potentially explaining why the rebase operation fails to properly preserve commits in the original scenario.

The thread continues to make progress in understanding this long-standing behavior (present since Git 2.0), with multiple contributors now collaborating to identify the underlying mechanism.
