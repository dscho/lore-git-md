This is a bug investigation related to the ongoing `git pull --rebase` commit-dropping issue. Tuomas Ahola reports a similar anomaly in `git merge-base --fork-point` behavior when changing remote URLs, which may be related to the original bug where commits disappear after a remote URL change.

The key observation shows that after changing a repository's origin URL and adding an upstream remote (both pointing to git/git), `git merge-base --fork-point` produces different results: it finds a commit hash when querying origin/next but returns nothing for upstream/next, despite both remotes pointing to the same URL. This suggests the fork-point calculation is incorrectly tied to the remote name rather than the actual commit history.

The test case uses Ben Knoble's Git fork as a starting point, checking out the 'next' branch and demonstrating the inconsistent behavior between identically-configured remotes. This appears to be another manifestation of the underlying issue where Git's tracking of commit relationships gets confused after remote URL changes.

The finding is significant because `merge-base --fork-point` is used internally by `git pull --rebase`, potentially explaining why commits get dropped in the original scenario. The empty result from the upstream remote case matches the symptom where commits disappear rather than being rebased. This provides a new angle for debugging the long-standing behavior that has existed since Git 2.0.
