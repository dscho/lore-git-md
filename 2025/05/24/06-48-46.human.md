This is the first patch in a two-part series addressing submodule configuration safety. It focuses on preventing silent overwrites of `.gitmodules` entries when reusing paths for new submodules.

The patch modifies `module_add()` in `builtin/submodule--helper.c` to detect when a submodule name derived from the path (like 'child') is already associated with a different path in the repository's config. In such cases, it will now either error out (default) or, with `--force`, auto-increment the name (creating 'child2', 'child3', etc.) to avoid conflicts. This prevents accidental loss of configuration when moving submodules and then reusing their old paths.

The implementation adds checks using `submodule_from_name()` to verify name/path associations, with forced naming handled via a `strbuf` loop. A new test in t7400-submodule-basic.sh verifies the behavior by simulating a submodule move and subsequent failed re-add attempt.

This change addresses a real pain point where Git's previous behavior could silently overwrite configuration, though the solution is somewhat conservative - it errs on the side of safety by requiring explicit user action (either renaming or using `--force`) rather than making assumptions about path reuse. The patch appears well-constructed with proper memory management and includes a clear test case.
