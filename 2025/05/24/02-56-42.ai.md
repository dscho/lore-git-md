This is a bugfix patch addressing an issue in `git send-email`'s threading behavior when sending patch series in batches. The problem occurs when the first patch of a new batch is sent - due to how `$num_sent` is incremented and reset, it can incorrectly trigger the same threading logic meant for the very first patch of the entire series.

The patch originally tried to fix shallow threading by using `$num_sent` instead of `$message_num` to identify the first message, but as Junio points out, this creates a new issue where the first message of each batch (after the initial one) would also be treated as the first message. The discussion reveals the need for a more precise way to identify the true first message of the entire series, separate from batch boundaries.

Key technical details:
- The problematic code is in `git-send-email.perl` around line 2060
- Involves the `$num_sent` counter and batch processing logic
- Affects email threading headers (`In-Reply-To` and `References`)
- The issue manifests when using `--batch-size` with `--thread`

The thread shows the patch needs revision to properly distinguish between "first message of series" and "first message of batch". This appears to be a subtle edge case in email threading that only surfaces with specific batch size configurations.
