This is a response in the ongoing discussion about Microsoft Graph API support for `git send-email`. Brian m. carlson raises strong objections to the proposal on grounds of protocol standardization and vendor neutrality.

The core argument is that Git should not adopt proprietary email transport methods, drawing a line at supporting only the two standard approaches (SMTP and sendmail binary). The response cites historical precedent with Microsoft's proprietary formats like TNEF and MAPI as examples of problematic non-standard approaches that Git has avoided. The position extends to opposing similar proprietary integrations with other major providers like Google or Amazon.

While acknowledging the performance and Message-ID preservation benefits Aditya demonstrated, carlson frames these as Microsoft-specific issues that should be addressed at the provider level rather than worked around in Git. They contrast this with their own positive experience using standard SMTP with Postfix/Dovecot and Google's SMTP servers.

The response does leave a narrow path forward - if the Graph API were to become an open standard with multiple implementations, it might warrant consideration. However, the current proposal's Microsoft-specific nature is presented as fundamentally incompatible with Git's commitment to open standards and vendor-neutral protocols.

This represents the first substantive pushback in the thread, shifting the discussion from technical implementation details to broader philosophical questions about Git's scope and standards compliance. The response doesn't engage with the credential helper implementation specifics, focusing instead on the higher-level appropriateness of the feature.
