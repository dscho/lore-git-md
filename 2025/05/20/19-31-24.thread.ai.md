[PATCH] Proposal: Add Windows update tip to git help/version output

Thread identity: Standalone feature patch proposing Windows-specific help text, now in design discussion phase with maintainer input. Original implementation remains unmerged pending resolution of platform boundary questions.

Core problem: Improving Windows user awareness of `git update-git-for-windows` while avoiding misleading users of other Windows Git builds (Cygwin, MINGW, custom compilations). The challenge spans both technical detection accuracy and philosophical questions about upstream/downstream responsibilities.

Current status: Patch version 1 remains unchanged since initial proposal. Discussion has progressed from implementation details (`_WIN32` detection) to fundamental policy questions after brian m. carlson's reinforced opposition to any platform-specific help in upstream Git.

Technical details:
- Existing patch modifies `list_common_cmds_help()` in help.c
- Uses `_WIN32` detection (acknowledged as too broad)
- Would display tip for all Windows builds regardless of origin
- No version output or configuration mechanism implemented

Open questions:
- Policy: Should upstream Git contain platform-specific help text? (brian m. carlson: no)
- Detection: Is accurate Git for Windows identification feasible? (brian m. carlson: opposes even exploring this)
- Ownership: Should this be exclusively a Git for Windows downstream patch?
- Awaiting Git for Windows maintainer (Johannes Schindelin) perspective

Participant positions:
- Original author: implemented initial solution
- brian m. carlson: strongly opposes any upstream platform-specific messaging, citing:
  1. No existing accurate detection mechanism
  2. Update mechanisms are distribution responsibilities (Debian parallel)
  3. Avoids upstream entanglement with corporate proxy/AV issues
- Junio C Hamano: previously probed if targeted approach could work, now facing fundamental policy objection
- Johannes Schindelin's input remains outstanding

The discussion has reached an impasse between:
1. Potential path forward with accurate detection (if policy objections overcome)
2. Downstream-only solution (Git for Windows patch)
3. Abandoning the feature entirely

brian m. carlson's latest response makes clear their opposition is principled rather than implementation-specific, significantly raising the bar for upstream inclusion. The thread now effectively requires either:
- Johannes Schindelin to advocate strongly for upstream inclusion with counterarguments, or
- Consensus that this belongs exclusively in Git for Windows

The technical discussion is effectively paused until this policy question resolves. Junio's next steps will likely depend on whether other maintainers weigh in to break the deadlock.
