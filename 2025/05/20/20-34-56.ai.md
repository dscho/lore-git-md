This is a technical clarification in the ongoing MPTCP support discussion, providing key implementation details from the Linux kernel perspective. Matthieu Baerts (Linux MPTCP maintainer) responds to Junio Hamano's questions about protocol behavior and configuration granularity.

The email confirms that Linux's MPTCP implementation requires explicit opt-in via `IPPROTO_MPTCP` socket creation, explaining why RFC 6897's transparent approach wasn't adopted. Matthieu details the fallback behavior: when MPTCP isn't available or fails, connections seamlessly continue with regular TCP. He notes this resilience has been proven in production by Apple since 2013. The Linux kernel automatically returns plain TCP sockets from `accept()` when clients don't request MPTCP, supporting the proposal's default-server-enabled approach.

On performance tradeoffs, Matthieu acknowledges MPTCP's header overhead (12B per connection) makes it less ideal for single-path or local connections, validating Junio's latency concerns. He suggests configuration should follow Git's existing patterns, proposing both global (`core.mptcp`) and per-repository settings, similar to protocol version or GPG signing controls. The email emphasizes maintaining user control while noting server-side enablement has minimal impact since it only activates when clients request it.

Key technical points clarified: MPTCP's mandatory opt-in nature on Linux, robust fallback mechanics, and header overhead implications. The discussion now centers on configuration design - whether to support repository/host-specific settings alongside global toggles, and how to document appropriate use cases. Matthieu's response strengthens the technical foundation while leaving policy decisions (configuration granularity, default values) to Git maintainers.
