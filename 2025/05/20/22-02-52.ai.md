Junio Hamano's follow-up in the MPTCP support thread focuses on server-side deployment considerations, particularly around `git-daemon` usage patterns. This is a technical clarification email rather than a new proposal.

The email addresses two key points: First, Junio confirms his understanding that Linux's MPTCP implementation deliberately avoids impacting non-MPTCP socket performance, though he laments the resulting opt-in requirement's effect on adoption. Second, he raises a new practical concern about `git-daemon` deployment - noting that when run via `inetd` (still common for Git servers), MPTCP support would depend on `inetd`'s socket configuration rather than Git's own settings.

Junio references Matthieu's earlier explanation about server-side MPTCP being low-risk (since it falls back to TCP when clients don't request it), but questions how this interacts with `inetd`-managed deployments. He also parenthetically notes that `git://` protocol usage has declined in favor of HTTPS/SSH, though this doesn't directly impact the MPTCP discussion.

The email doesn't introduce new technical elements but surfaces an important deployment consideration that wasn't previously addressed: MPTCP's server-side benefits may be limited unless both the Git client *and* the hosting environment (whether standalone `git-daemon` or `inetd`) are properly configured. This could influence the configuration design discussion, particularly around documentation requirements for server administrators.
