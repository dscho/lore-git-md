This thread addresses a security and compatibility issue where Git's internal binaries are unintentionally exposed in the PATH for non-Git child processes, particularly affecting Windows users with Vim integration. The initial patch series (v1) from D. Ben Knoble proposes removing git_exec_path() from PATH for non-Git commands while maintaining it for Git's own subprocesses, with careful handling of platform differences including Windows Unicode requirements.

The discussion has evolved with significant input from multiple reviewers. Johannes Schindelen provided Windows-specific guidance, while Junio C Hamano suggested an alternative design using a drop_git_exec_path flag. Patrick Steinhardt raised concerns that the current approach might be too broad, proposing making PATH modification opt-in rather than opt-out, and identified several implementation issues including a memory leak.

Phillip Wood's latest contribution adds important nuance by detailing concrete cases where PATH consistency is necessary for Git's own operations - hooks, shell aliases, rebase --exec, and bisect run all require child processes to reliably find the same Git installation. He also highlights the unreliability of assuming filesystem relationships between git and related tools like git-jump across different distributions. These points complicate the security/functionality tradeoff, suggesting the solution must preserve PATH consistency for Git's internal needs while still achieving the security goal for external processes. The thread remains active with open questions about the right default behavior and Windows-specific testing requirements.
