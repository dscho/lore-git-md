The thread continues to explore how Git should handle its executable path in child processes, balancing security against compatibility. The core issue is that Git currently exposes its internal binaries in the PATH for all child processes, which could be a security risk, but removing this behavior might break workflows that rely on version consistency for Git subprocesses.

Key participants have weighed in with technical perspectives:
- Phillip Wood argues that modifying PATH to include Git's directory would be too disruptive, as it would affect all child processes (not just Git internals), while the current GIT_EXEC_PATH approach is more targeted
- Patrick Steinhardt acknowledges this concern, noting the tradeoff between the broader PATH modification approach (better version consistency but more invasive) versus the narrower GIT_EXEC_PATH method (less disruptive but potentially incomplete)
- Junio Hamano had earlier suggested focusing first on editor invocations as a narrower test case

Author D. Ben Knoble is preparing two versions of the patch series for comparison:
1. The original broad solution affecting all non-Git commands
2. A narrower version focused just on editor invocations

The discussion has uncovered several technical nuances:
- Windows Unicode handling requirements complicate any changes
- There are subtle differences between PATH and GIT_EXEC_PATH behavior
- The ongoing deprecation of "dashed" Git commands (like git-commit) affects the solution
- Distribution packaging practices may impact how scripts expect to find Git tools

While the strvec API conversion parts of the series have been approved, the core design question remains open: how to securely limit PATH exposure while maintaining the version consistency that Git's subprocesses need. The thread shows the community carefully weighing these competing concerns before settling on an approach.
