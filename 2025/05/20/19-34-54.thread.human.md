This thread addresses security and compatibility issues around how Git exposes its internal binaries in the PATH environment variable for child processes. The core problem is that while Git needs its exec-path in PATH for its own subprocesses (like hooks and rebase operations), exposing these paths to all child processes (such as editors) creates potential security risks. D. Ben Knoble's initial patch series proposed a broad solution affecting all non-Git commands, but discussion has revealed complexities that may warrant a narrower approach.

The technical landscape involves several key considerations: Windows Unicode handling for environment variables, consistency requirements for Git's own subprocesses, and the relationship between PATH and GIT_EXEC_PATH. The patches already include improvements like converting editor.c to use the strvec API and better test isolation in t7005-editor.sh.

Recent discussion has centered on two main questions: whether the solution should be broad (affecting all non-Git commands) or narrow (focused just on editor invocations), and how to handle legacy cases like dashed commands (git-*) that may still depend on PATH access. Junio Hamano and Patrick Steinhardt both favor the narrower approach, while the author is now preparing both versions for comparison. CI test failures have surfaced, possibly indicating deeper assumptions about PATH dependencies that need investigation.

Participants have raised important considerations: Phillip Wood highlighted Windows-specific Unicode handling requirements, Patrick Steinhardt noted real-world usage of git-sh-setup despite its documentation status, and Johannes Schindelen has been involved for Windows platform expertise. The author is currently analyzing the CI failures and considering how to handle hooks and other Git subprocesses that legitimately need PATH access, likely making this an explicit opt-in behavior rather than a blanket removal.

The thread remains active with open questions about design direction and implementation details, but converging toward either a narrower solution or a configurable approach that maintains compatibility while improving security.
