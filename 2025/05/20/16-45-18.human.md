This is a naming discussion in the final stages of a promisor-remote protocol enhancement series. Junio C Hamano weighs in on the naming of a helper function that finds promisor remote information by name, clarifying that his earlier suggestion for `remote_nick_find()` was context-specific to a strvec-based implementation.

Junio notes that with the current struct-based approach (using `struct promisor_info`), a more descriptive name like `promisor_info_find()` might be appropriate if name-based lookup is the primary access pattern. He also suggests considering alternative data structures like strmap or string_list if name-based lookup is the dominant operation, hinting that the current linear search approach might not be optimal.

The discussion is part of final polishing for a v3 series that has otherwise addressed all technical feedback. Junio's comments focus on API design principles rather than blocking issues, leaving the final naming decision to the maintainers while offering architectural considerations about data structure choices. The thread shows the project's attention to detail in naming and data modeling even for internal helper functions.
