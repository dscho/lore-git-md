This is a performance optimization proposal for Git's revision traversal logic, specifically targeting how boundary commits are identified. The patch comes from a new contributor (lidongyan) and is marked as RFC (Request For Comments), indicating they're seeking feedback on the approach.

The core issue relates to how Git handles `UNINTERESTING` commits when boundary marking is enabled (`revs->boundary`). Currently, when encountering such commits, Git continues traversing their parents even though only the earliest `UNINTERESTING` commits will ultimately be marked as boundaries. The proposed change would make the process stop traversal after the first `UNINTERESTING` parent when boundary marking is active.

The patch is minimal - just a few lines modifying `process_parents()` in revision.c - but touches core revision walking logic. The author doesn't include performance measurements or test cases, which would be important for evaluating whether the optimization provides meaningful gains. As an RFC, this seems like a starting point for discussion rather than a final proposal. The change appears safe at first glance (it only affects behavior when `revs->boundary` is true), but reviewers will likely want to verify it doesn't break edge cases in boundary commit detection.
