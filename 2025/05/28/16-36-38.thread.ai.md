RFC proposal for optimizing boundary commit traversal in revision walking.

The thread begins with a proposal to optimize `revision.c`'s boundary commit handling when `revs->boundary` is set. Currently, `get_revision_internal()` continues traversing parents of UNINTERESTING commits even though only the earliest UNINTERESTING commits are marked as boundary. The suggested change would add a `break` condition in `process_parents()` to stop early in this case, potentially improving performance for commands using `--boundary`.

The initial proposal lacks performance measurements or test cases demonstrating the optimization's impact. It also doesn't address whether any existing callers might depend on the current full traversal behavior. The change targets core revision walking machinery (`revision.c`, `process_parents()`), so while small, it could affect various commands using boundary marking like `git log --boundary`. Key open questions include: what performance gains could be expected, whether there are edge cases where full traversal is necessary, and what testing would be required to validate the change.
