This is a technical response to a feature request about `git add -p` behavior with merge conflicts. Chris Torek explains why the current implementation prevents `git add -p` from operating on conflicted files, diving deep into Git's index mechanics.

The core issue stems from how Git represents merge conflicts in the index - storing multiple staged versions (base/ours/theirs) that are mutually exclusive with a stage zero (resolved) entry. Allowing `git add -p` to operate on conflicted files would require fundamentally how the index handles these states, which would be a significant architectural change.

Torek provides a thorough walkthrough of Git's index operations during normal workflows and merge conflicts, highlighting that the current design enforces a strict separation between conflicted (multiple stages) and resolved (stage zero) states. He notes this might be a design limitation rather than an intentional restriction, but changing it would require careful consideration of interactions with other commands like `git restore`.

The response is informative but effectively shuts down the immediate feasibility of the proposal due to architectural constraints, while leaving the door open for someone to tackle the substantial work of redesigning this part of Git's internals. This appears to be a case where what seems like a simple UI improvement would require deep plumbing changes.
