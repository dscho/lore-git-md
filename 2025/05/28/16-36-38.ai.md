Performance optimization for boundary commit traversal in revision walking.

This RFC proposes a potential optimization in `revision.c`'s boundary commit handling. Currently, when `revs->boundary` is set and `get_revision_internal()` encounters an UNINTERESTING commit, it continues traversing parents even though only the earliest UNINTERESTING commits will be marked as boundary. The patch suggests breaking early from parent traversal when `revs->boundary` is true, which could save unnecessary work.

The change is minimal - just adding a `break` condition in `process_parents()` when `revs->boundary` is set. This targets a core part of Git's revision walking machinery, so while the change is small, it could have wide-ranging performance implications for commands that use boundary marking (like `git log --boundary`).

The author doesn't include performance measurements or test cases showing the impact, which would be important for evaluating whether this optimization is worthwhile. The commit message also doesn't discuss whether there are cases where the current behavior is actually required (for example, if some caller depends on the full traversal happening even for boundary cases). This seems like the kind of change that would benefit from some performance numbers and analysis of whether it could break any existing use cases.
