This is a technical response to the feasibility of modifying `git add -p` to handle merge conflicts, from Chris Torek. The email provides a deep dive into Git's index mechanics to explain why the current behavior exists and what architectural changes would be needed to support the proposed feature.

The core insight is that merge conflicts are represented in Git's index by storing multiple staged versions of a file (stages 1-3 for base/ours/theirs), while `git add -p` fundamentally assumes and operates on a single stage 0 (unconflicted) version. Allowing `git add -p` on conflicted files would require either (1) maintaining both conflict markers and partial resolution in parallel (breaking the current index model where stage 0 and higher stages are mutually exclusive), or (2) fundamentally changing how conflicts are represented in the index.

Torek notes this isn't impossible, but would be a significant architectural change touching core index behavior and requiring careful consideration of interactions with other commands like `git restore`. The email serves as both an education on Git's internals and a reality check about the scope of changes needed - suggesting the proposal would require someone willing to undertake major index surgery rather than being a simple `add-interactive.c` tweak.

Key technical constraints highlighted:
- Index can't currently represent both partial resolution (stage 0) and conflict state (stages 1-3) simultaneously
- Conflict resolution workflow assumes atomic transition from conflicted->resolved via `git add`
- Original design allowed for but never implemented multiple stage-1/3 entries for complex merges

The response positions this as a non-trivial design challenge rather than dismissing the use case, leaving the door open for someone to propose concrete index modifications while making clear this isn't a surface-level change.
