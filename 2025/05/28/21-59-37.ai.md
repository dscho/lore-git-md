This is a follow-up in the ongoing discussion about signature handling in Git's fast-export/fast-import functionality, specifically addressing process questions around experimental feature defaults.

Junio Hamano responds to Elijah Newren's query about why this case warrants an immediate default behavior change rather than following Git's typical deprecation timeline. The key distinction is that the problematic behavior (requiring explicit opt-out for signature stripping) was only present in unreleased code (2.50-rc0) and represents a breaking change from the long-standing default of silently stripping signatures. 

Hamano frames this as correcting a mistake in the original implementation that violated Git's principle of making new features opt-in rather than opt-out. The change restores the previous behavior that users had relied upon, while still allowing the new signature handling capabilities to be explicitly enabled. This differs from typical deprecations where behavior changes affect already-released versions.

The email reinforces that this is a special case justified by:
1. The change affecting only pre-release code
2. Reverting to established behavior rather than introducing new behavior
3. Maintaining the principle that new features should be opt-in

This response helps clarify the decision-making process while showing alignment on the technical solution (marking the feature experimental while restoring the original default behavior). The discussion continues to balance technical needs with Git's stability commitments and development processes.
