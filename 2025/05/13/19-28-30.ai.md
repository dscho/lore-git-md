This is a follow-up discussion on the object database refactoring series, specifically addressing naming conventions and documentation clarity around the `odb_alternate` concept. Toon Claes builds on Patrick Steinhardt's explanation of why `odb_alternate` was chosen over "shard" as the naming pattern for the refactored object database components.

The key technical point is the clarification that the primary object directory is now be considered as the "primary alternate" in this model, with other alternates forming a linked list. Toon notes this architectural detail wasn't sufficiently documented in patch 02/17 (the struct rename patch) and suggests adding explanatory text to make this relationship clearer to future readers.

This is a non-blocking documentation refinement to an already-approved series. The core technical approach (using `odb_alternate` naming and treating the primary storage as just another alternate) remains unchanged from the v2 consensus. The suggestion focuses specifically on improving the conceptual documentation in the commit message of patch 02/17 to better explain the primary/secondary alternates relationship.

The exchange confirms the naming convention is now settled (`odb_alternate` with potential future variants like `odb_packed_alternate`), while identifying one remaining documentation gap to address before or after integration. No changes to the actual code or API design are being proposed here - this is purely about making the existing design's rationale more accessible.
