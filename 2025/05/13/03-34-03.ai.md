This is a bugfix patch addressing submodule configuration safety, part of an ongoing thread about preventing accidental `.gitmodules` overwrites when reusing paths for new submodules. The patch modifies `module_add()` to detect when a submodule name would conflict with an existing configuration entry pointing to a different path.

The key change introduces a check using `submodule_from_name()` to detect name/path mismatches. When found, it either errors out (default) or, with `--force`, generates a unique name by appending incrementing numbers (foo, foo1, foo2). This implements the automatic conflict resolution approach favored by Junio Hamano in earlier discussion. The patch also includes a new test case in t7400 that verifies the error behavior when attempting to reuse a name.

Technical changes focus on the submodule helper code, particularly around the name/path validation logic. The implementation maintains compatibility with existing `submodule.active` configuration handling through the `submodule_active_matches_path()` helper. The solution appears well-considered, with test coverage for the basic conflict case, though the thread summary notes that edge cases around nested submodules may still need attention.

This represents a significant iteration from the thread's starting point, moving from a simple `--force` option to a more sophisticated automatic naming scheme that better preserves configuration integrity while still allowing path reuse when needed. The patch aligns with Git's stability priorities while providing a practical solution to the original problem.
