This is a follow-up discussion on the oidmap refactoring series, specifically addressing patch 2/3 which introduces `oidmap_get_size()`. Patrick Steinhardt responds to Jeff King's explanation about the patch's behavior in the replace-object subsystem.

The key point centers on the distinction between checking the hashmap's allocated table size versus its actual entry count. While Jeff's original commit message suggested these were functionally equivalent for the replace-object case (since entries are only added), Patrick clarifies that they are not actually equivalent in general - the table size is typically larger than the entry count. However, he agrees that for the specific use case of checking whether the map is empty (the only operation performed in replace-object), either metric would suffice.

This exchange highlights a subtle but important implementation detail in the oidmap API encapsulation. The discussion doesn't propose any changes to the patch itself, but rather provides additional context about why the existing behavior is correct despite the initial confusion. The thread continues to demonstrate careful attention to API design details in this refactoring effort.
