Bugfix discussion regarding `git pull --rebase` behavior with remote URL changes. Mr Bill confirms Phillip Wood's analysis that the issue stems from stale reflog entries affecting fork-point calculation after changing a remote's URL. He notes that `git merge-base --fork-point` returns different results between clone_1 (commit C) and clone_2 (commit G) due to the lingering reflog entry from the old remote. Bill expected `git fetch` to update the upstream HEAD information, but the fork-point calculation still uses the outdated reflog data. He confirms Phillip's suggested workaround of using `git fetch && git rebase --no-fork-point` works in his case. The email serves as validation of the technical explanation while highlighting the user expectation that fetch operations should fully synchronize remote state.
