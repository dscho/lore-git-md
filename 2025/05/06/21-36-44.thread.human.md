This thread investigates a long-standing issue where `git pull --rebase` unexpectedly drops commits after changing a repository's remote URL. The original report demonstrated that commits F-G would disappear when rebasing after switching a clone's remote, with the behavior traceable back to Git 2.0 (commit d717282532) and confirmed across multiple versions.

Tuomas Ahola has now identified a related anomaly in `git merge-base --fork-point`, which may explain the root cause. When testing with two remotes pointing to the same URL (git/git), the command returns different results - finding a commit hash for origin/next but nothing for upstream/next. Since `pull --rebase` uses fork-point internally, this inconsistency could be why commits get dropped rather than rebased after remote URL changes.

The thread has progressed from initial bug report to bisect confirmation (by D. Ben Knoble) to this new insight about fork-point behavior. While the issue has existed since 2012, these findings provide a concrete direction for further debugging by connecting the commit-dropping symptom to potential problems in how fork-point calculations handle remote changes. The reporter remains engaged for follow-up investigations.
