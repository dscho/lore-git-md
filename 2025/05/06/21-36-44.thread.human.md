This thread investigates a surprising behavior in `git pull --rebase` where commits can be silently dropped after changing a repository's remote URL. The issue was originally reported by Bill, who demonstrated a reproducible case where commits F-G disappeared when rebasing after pointing clone_2 to a different remote. 

D. Ben Knoble's bisect revealed this behavior has existed since Git 2.0, persisting through multiple major versions. Tuomas Ahola then discovered related anomalies in `git merge-base --fork-point` calculations after URL changes. Phillip Wood provided the key technical explanation: when a remote URL changes, the upstream branch's reflog retains entries from the old remote, and `pull --rebase`'s internal fork-point calculation incorrectly uses these stale entries, excluding commits that should be preserved. He suggested two workarounds: either use `git fetch` followed by `git rebase --no-fork-point`, or rename the remote instead of changing its URL.

Bill has now confirmed Phillip's analysis, noting that while he expected `git fetch` to fully synchronize remote state, the fork-point calculation still references outdated reflog data. He verified that Phillip's workaround successfully preserves the commits. The discussion has clarified both the technical mechanism and real-world impact, though questions remain about whether to modify this long-standing behavior or better document it. The thread has maintained focus on the original reproduction case while thoroughly exploring the underlying rebase/fork-point interaction.
