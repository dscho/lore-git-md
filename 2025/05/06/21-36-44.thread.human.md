This thread investigates a surprising behavior where `git pull --rebase` drops commits after changing a repository's remote URL. The issue was first reported by Bill, who provided a reproducible case showing commits disappearing rather than being properly rebased. D. Ben Knoble's bisect revealed this has been a long-standing issue since Git 2.0, affecting multiple major versions.

The investigation took a significant step forward when Tuomas Ahola discovered related anomalies in `git merge-base --fork-point` behavior with changed remotes, showing the calculation depends on remote names rather than commit history. This matters because `pull --rebase` uses fork-point internally.

Phillip Wood has now provided the clearest technical explanation yet: when a remote URL changes, the upstream branch's reflog retains entries from the old remote. The fork-point calculation then incorrectly excludes commits reachable from these stale entries, causing the observed commit dropping. He suggests two workarounds - using explicit fetch+rebase without fork-point, or renaming remotes instead of changing URLs.

The discussion has shifted from diagnosing the behavior to considering solutions. While the current implementation clearly has surprising edge cases, there's debate about whether this represents a bug to fix or a behavior that needs better documentation and configuration options. Phillip notes the existing `rebase.forkPoint` config setting is currently ignored, which could provide user control if implemented.

The core team now understands both the reproduction case and the underlying mechanism, with workarounds available while the long-term solution is determined. The thread remains active with participants available for further investigation.
