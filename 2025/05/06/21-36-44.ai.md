This is a bug report concerning unexpected behavior with `git pull --rebase` when changing a repository's remote URL. The reporter, Bill, demonstrates a scenario where local commits disappear after changing a clone's upstream and performing a rebase pull.

The issue occurs in a multi-repository setup where:
1. A base repo has commits A-B-C
2. A first clone (clone_1) adds commits F-G
3. A second clone (clone_2) is made from clone_1
4. After base adds commits D-E, clone_2's remote is changed to point to base
5. `git pull --rebase` in clone_2 drops commits F-G entirely instead of rebasing them
6. The same operation in clone_1 (which still points to clone_1) works as expected

The report includes a detailed reproduction script showing the commit sequence and demonstrating the discrepancy between clone_1 (which retains commits) and clone_2 (which loses them). The behavior appears across multiple Git versions (2.35.8 and 2.46.2) on Slackware Linux.

Key technical details:
- The issue manifests when changing remotes with `git remote set-url`
- The unexpected behavior occurs specifically during `git pull --rebase`
- The test case shows the problem is reproducible with simple linear commits
- The reporter is available to provide more context or test additional scenarios

This appears to be a legitimate edge case in Git's rebase logic when dealing with changed remotes, though it's unclear whether this represents a bug or undocumented behavior. The thorough reproduction case makes it easy to verify and investigate further.
