Original report from Bill demonstrated reproducible case: base repo has A-B-C, clone_1 adds F-G, clone_2 is made from clone_1. Tuomas Ahola discovered related `git merge-base --fork-point` anomalies when changing remote URLs, showing inconsistent results between identically-configured remotes (origin vs upstream pointing to same URL). Phillip Wood's analysis connects these findings by explaining the technical mechanism: after changing the remote URL, the upstream branch's reflog retains entries from the old remote (commit G). When `pull --rebase` internally uses `merge-base --fork-point`, it excludes commits reachable from these stale reflog entries, causing the observed commit dropping. Phillip provides two workarounds: `git fetch && git rebase --no-fork-point` sequence, or renaming the remote instead of changing its URL to avoid reflog contamination.

Key technical details: manifests when using `remote set-url` followed by `pull --rebase`, with fork-point calculation prioritizing stale reflog entries over actual commit topology. The issue highlights a design tension in `pull --rebase`'s default fork-point behavior - useful for rewritten history but problematic for URL changes. Phillip notes the current implementation ignores the `rebase.forkPoint` config setting that could provide user control.
