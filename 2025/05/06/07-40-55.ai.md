This is a bugfix review comment in the ongoing "maintenance task decomposition" series. Christian Couder points out that the worktree pruning task still has a memory leak in the `worktree_prune_condition()` function that Eric Sunshine had identified in an earlier review round. The leak occurs when the function early-exits via `goto out` after finding a worktree that should be pruned - the `wtpath` allocated by `should_prune_worktree()` is not freed in this path, though it is properly freed in the normal case. This is a straightforward oversight in the cleanup logic that needs to be addressed before the series can be merged. The issue doesn't affect the overall design of the worktree pruning task but is an implementation detail that needs fixing.
