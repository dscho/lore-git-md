Bug report about `git pull --rebase` losing commits after remote URL change. Mr Bill describes a scenario where custom commits disappear when performing a rebase pull after changing a clone's remote URL. The issue is reproducible with a clear test script that demonstrates the problem: when clone_2 changes its origin from clone_1 to base and does a rebase pull, commits F and G vanish, while clone_1 (which didn't change its remote) retains them as expected.

The report is well-documented with ASCII commit graphs showing expected vs actual behavior, and includes a complete shell script to reproduce the issue. The problem occurs across multiple Git versions (2.35.8 and 2.46.2) on Slackware Linux. This appears to be a legitimate bug in Git's rebase logic when handling remote URL changes, though it's possible there may be some user misunderstanding about how `remote set-url` interacts with the rebase operation.

The test case is particularly valuable as it provides a clean reproduction path for developers to investigate. The reporter offers to answer follow-up questions and notes they can reproduce this in their actual ffmpeg development environment as well. This looks like a potentially serious issue for users who change remotes and expect their local commits to be preserved during rebase operations.
