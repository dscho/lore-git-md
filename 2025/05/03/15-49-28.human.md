This is a performance discussion about `git fsck`'s handling of large packed-refs files, emerging from the platform compatibility thread about BSD errno behavior.

Jeff King responds to shejialuo's questions about why using `mmap` would be preferable to reading the entire packed-refs file into a strbuf. He explains that even without process sharing, `mmap` is more efficient than copying data into a new allocation. The discussion centers on GitHub's fork networks as a real-world case where packed-refs files can grow very large (potentially gigabytes) due to storing refs from thousands of forks.

King provides concrete numbers from the Linux kernel repository - about 55k forks with ~30k ref data each, totaling ~1.5GB. While this isn't prohibitive for GitHub's infrastructure, it makes a strong case for using `mmap`. He notes this isn't even the worst-case scenario, as some projects have larger ref namespaces.

The email also touches on some implementation considerations for switching to `mmap`, including Windows locking behavior and NUL-termination handling. While this performance optimization isn't urgent (the thread's main focus was the BSD errno issue), it's a clear improvement that could benefit large-scale deployments. The discussion remains technical and collaborative, with both participants working through the tradeoffs.
