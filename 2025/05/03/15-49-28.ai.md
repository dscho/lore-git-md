This is a follow-up discussion in the platform compatibility thread about packed-refs file handling in `git fsck`. Jeff King (peff@peff.net) responds to shejialuo's questions about memory management strategies for large packed-refs files.

The email focuses on performance considerations when reading packed-refs during fsck operations, particularly for very large repositories like GitHub's fork networks. Jeff explains that while the current strbuf approach works, mmap would be more efficient for repositories with packed-refs files that can grow to gigabytes in size (citing GitHub's Linux fork network as an example where this could reach ~1.5GB). He notes this isn't strictly necessary but would be an optimization, and points out some implementation considerations around mmap usage (NUL-termination, Windows locking behavior).

The discussion remains technical and collaborative, with Jeff providing detailed analysis of the memory tradeoffs while acknowledging the current implementation is functional. This continues the thread's secondary discussion about fsck performance optimizations, though it doesn't directly relate to the main thread resolution about O_NOFOLLOW errno handling.
