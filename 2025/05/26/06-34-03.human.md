This is a technical discussion email in the ongoing thread about Git's exec-path security and compatibility issues. Patrick Steinhardt is responding to Phillip Wood's concerns about maintaining version consistency for Git subprocesses.

The key point here is a refinement of the PATH vs GIT_EXEC_PATH distinction in the proposed changes. Phillip had raised an important concern that simply adding the Git executable path to PATH (as in /usr/bin) would have much broader effects than the current approach of adding GIT_EXEC_PATH, which only affects Git's internal program lookups. Patrick acknowledges this as a valid consideration.

This exchange highlights one of the core tensions in the proposed changes - how to maintain version consistency for Git's own subprocesses (hooks, aliases, etc.) while minimizing impact on other programs. The discussion suggests that the current GIT_EXEC_PATH approach may be less disruptive than modifying PATH directly, even if both approaches could theoretically solve the version consistency problem.

This email doesn't introduce new patches but helps clarify the technical tradeoffs between different approaches to solving the underlying problem. It shows the careful consideration being given to how changes might affect real-world usage patterns and user expectations.
