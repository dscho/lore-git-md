This is a technical discussion about signature handling in `git fast-export`/`fast-import`, continuing the thread's focus on verification workflows. Elijah Newren responds to Christian Couder's v2 patch series that extracts algorithm information from signatures, proposing a clearer taxonomy of use cases for signature handling during export/import operations.

The email identifies four distinct user scenarios for signature handling:
1. (A) Preserve signatures unconditionally (even if invalid)
2. (B) Validate signatures on import (error/drop if invalid)
3. (C) Re-sign commits if original signatures become invalid
4. (D) Always re-sign commits regardless of original validity

Newren argues that signature verification during export would be redundant for most use cases, particularly since intermediate processing may invalidate signatures anyway. He questions the value of Christian's proposed `--summary` flag for `git verify-commit` in the context of fast-export workflows, noting it doesn't directly address the export/import signature handling challenges.

Key technical points raised:
- The thread continues grappling with how to represent signature metadata (protocol vs hash algorithm)
- SSH signature handling remains complex due to key-type/hash algorithm coupling
- Performance tradeoffs between signature verification and export speed
- Fundamental limitations of signature preservation across export/import pipelines

This moves the discussion toward clarifying requirements before implementing solutions, with Newren providing concrete framework for evaluating design choices. The exchange highlights ongoing tension between verification accuracy and practical workflow considerations in the signature handling improvements.
