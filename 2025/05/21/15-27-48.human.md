This is a technical discussion email in an ongoing thread about Git's exec-path security and compatibility issues. Phillip Wood responds to Patrick Steinhardt's concerns about PATH modification for Git's child processes.

Phillip argues that prepending the Git executable's directory (like /usr/bin) to PATH would be more disruptive than the current approach of adding GIT_EXEC_PATH. He notes that modifying PATH to include the Git binary's directory would affect lookups for all programs, not just Git's internal tools, which could have unintended side effects. The current GIT_EXEC_PATH approach is more surgical, only influencing the location of Git's own helper binaries.

The email reinforces the thread's central tension between security (removing internal paths from child environments) and compatibility (ensuring Git subprocesses can find the correct versions of tools). Phillip's position favors maintaining the current behavior for PATH modification, seeing it as the lesser of two evils compared to the alternative of prepending the Git binary directory.

This exchange highlights the nuanced tradeoffs in the design, with different developers weighing in on how to draw the line between security hardening and maintaining expected behavior for Git's various subprocess invocation mechanisms.
