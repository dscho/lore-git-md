Thread summary:

Proposal] git imap-get-recipients helper for patch email workflows. Aditya Garg suggests adding a Perl script to extract To/Cc recipients from an IMAP message by message ID, intended for use with `git send-email --to-cmd` when sending patch revisions. The tool would automate recipient population currently done manually, mimicking GUI email client behavior. Junio Hamano raises significant concerns about the approach, questioning whether simply copying To/Cc lists from previous messages would lead to suboptimal recipient selection for patch revisions. He emphasizes v2 emails should consider both original recipients and commenters from the v1 thread, suggesting the tool might encourage lazy practices if it only replicates previous recipients without context.

Hamano provides additional technical and philosophical feedback in follow-up, noting several practical barriers: Git's current avoidance of Perl dependencies and new contrib/ additions, plus uncertainty about where such a tool would logically fit in Git's architecture. He suggests the b4 tool's contributor features may already address the need, proposing extension rather than new development as a better path forward. The response maintains skepticism about the tool's fundamental approach while offering concrete alternatives - either demonstrate clear value through implementation or consider enhancing existing infrastructure like b4 that already handles thread-aware recipient analysis.

Key technical gaps remain: IMAP data source (personal mailbox vs public archive), authentication methods, and whether the tool would analyze just the original message or also its replies. Additional constraints now include Perl dependency avoidance, contrib/ directory policy, and architectural fit questions. The philosophical stance remains that theoretical proposals carry less weight than working code demonstrating real value, with b4 integration suggested as a potential alternative path.

The current status is that the proposal remains on hold pending either a revised implementation addressing these concerns or a demonstration of why existing tools like b4 cannot meet the need. No patches have been submitted yet; this remains a discussion of the concept's fit with Git's email-based workflow and contribution philosophy.
