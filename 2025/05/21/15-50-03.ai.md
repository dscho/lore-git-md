Security/feature discussion about Git's child process environment handling, specifically the propagation of GIT_EXEC_PATH. This is part of the ongoing thread about securing Git's process spawning while maintaining version consistency across child processes.

Justin Tobler raises a technical clarification about GIT_EXEC_PATH inheritance in child processes, responding to Patrick Steinhardt and Phillip Wood's discussion about PATH vs GIT_EXEC_PATH requirements. The key point is that when GIT_EXEC_PATH is explicitly set in the parent process (to override defaults), that setting should logically propagate to child Git processes to maintain version consistency. This suggests GIT_EXEC_PATH handling may need to be treated separately from the broader PATH modifications being debated in the thread.

The email highlights an important distinction in the security/compatibility tradeoffs: while PATH modifications affect all child process lookups, GIT_EXEC_PATH specifically controls Git's internal tool locations. Justin's observation implies that even if the narrow (editor-focused) approach is adopted for PATH changes, GIT_EXEC_PATH propagation might need separate consideration to properly handle cases where it's explicitly overridden. This adds nuance to the ongoing discussion about how to balance security (removing internal paths from general PATH access) with version consistency requirements for Git's own subprocesses.
