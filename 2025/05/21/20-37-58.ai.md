This is a bugfix patch addressing sparse directory handling in Git's threaded name-hash initialization, following up on previous discussion about whether to frame it as a correctness fix or performance optimization.

Alex Mironov responds to Junio Hamano's request for clarification in the commit message and performance measurements. The reply confirms the change should be treated as a correctness fix for general cases, though it originated from performance considerations in specialized VFS setups where files exist outside sparse cones. Benchmarks show no significant performance impact in typical usage scenarios.

The email references commit 5f11669586 which fixed the same issue in the single-threaded path, and indicates the commit message follows Derrick Stolee's wording from that earlier change. The core technical point remains ensuring sparse directory entries (marked S_ISSPARSEDIR) are excluded from the name_hash table consistently across both initialization paths.

Key technical details for future reference:
- The change affects name-hash.c's lazy_name_thread_proc function
- Maintains consistency with CE_HASHED flag behavior
- No hashmap operations are performed on sparse directory entries
- Performance impact is negligible in standard sparse checkout cases
- The patch emerged from edge cases in custom sparse implementations where sparse.expectFilesOutsideOfPatterns=true is used
- Follows the pattern established in the single-threaded fix (5f11669586)
