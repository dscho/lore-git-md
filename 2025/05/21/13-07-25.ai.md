This is a technical discussion in the ongoing thread about removing git_exec_path() from non-Git commands' PATH, with new Windows Unicode handling considerations raised.

Phillip Wood responds to Patrick Steinhardt's suggestion that PATH modification might not be necessary at all, pushing back with concrete use cases where maintaining PATH consistency is still important. He identifies several scenarios where child processes (hooks, shell aliases, rebase --exec, bisect run) need to find the same Git executable as the parent process, noting that without PATH modification, these could accidentally pick up a different Git installation from the user's PATH.

The email also reinforces an earlier point about the unreliability of using git_exec_path() to locate related tools like git-jump, observing that packaging decisions make the filesystem relationship between these tools and the Git executable unpredictable across different distributions. This discussion surfaces important edge cases that need consideration in the PATH modification logic, particularly around:
- Maintaining execution environment consistency for Git's own child processes
- The tension between security (removing unnecessary PATH entries) and functionality (ensuring related Git commands can find each other)
- Platform-specific packaging variations that affect assumptions about tool locations

The exchange highlights that while the original patch's security goal is valid, the solution needs to carefully preserve Git's own internal consistency requirements, especially for its own subprocesses. This adds complexity to the decision about whether PATH modification should be opt-in versus opt-out, and what the default should be.
