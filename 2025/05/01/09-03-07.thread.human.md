This thread addresses a long-standing bug in `git apply --intent-to-add` (`-N`) where the command incorrectly clobbers the index, marking tracked files as deleted. The issue was first reported by Johannes Altmanninger in 2021 with a patch series that proposed making `-N` imply `--index`, but the approach was questioned by Junio Hamano due to potential conflicts with other index-modifying flags like `--cached` and `--3way`. Recently, Ryan Hodges demonstrated concrete breakage where applying a patch with `-N` corrupts the index by removing unrelated tracked files.

Raymond Pasco has now provided a technical deep dive, confirming Hodges' findings and clarifying that `-N` was only meant to affect worktree changes, not replace the entire index. He notes that Altmanninger's original patch (v3) had correct code despite a misleading commit message, and suggests documenting `- N` as mutually exclusive with `--index` and `--cached`. Pasco has offered to refresh and resubmit the patch if Altmanninger is unavailable.

The thread has progressed from theoretical concerns to demonstrated breakage, and now to a clearer technical understanding of both the bug and the proposed fix. The path forward appears to be: (1) adopt Altmanninger's v3 code with corrected documentation, (2) explicitly prevent `-N` from being used with other index-modifying flags, and (3) possibly have Pasco shepherd the patch if the original author doesn't resurface. Junio's input will be key in determining whether this solution adequately addresses his earlier concerns about interaction with other apply modes.
