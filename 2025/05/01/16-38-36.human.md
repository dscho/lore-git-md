This is a follow-up in the ongoing discussion about Scalar's `--no-maintenance` flag architecture. Junio Hamano responds to Derrick Stolee's defense of keeping maintenance control within `register_dir()`, reinforcing his position that explicit calls at the command level (`cmd_register()`/`cmd_clone()`) would improve code clarity.

Hamano makes two key points: First, that having maintenance toggles at the call sites makes the behavior more immediately visible to code readers, as opposed to burying it in shared infrastructure. Second, he notes that since `cmd_reconfigure()` will need to call `toggle_maintenance()` directly anyway (to handle the opt-out case), there's no real simplification benefit to centralizing the logic in `register_dir()`.

The exchange remains collegial but highlights a fundamental design tension - whether maintenance configuration belongs with other "recommended settings" in the registration helper, or whether it should be managed explicitly by each command. Hamano leans toward the latter, suggesting this approach will scale if more customizations are added later. The discussion remains unresolved pending Stolee's v2 implementation.
