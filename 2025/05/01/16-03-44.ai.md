This is a follow-up discussion in the thread about fixing the p5332 performance test script. Jeff King responds to Junio Hamano's suggestion that better change-tracking tools might have caught the earlier oversight, arguing that the issue was more about test coverage than change tracking. The key points:

Jeff notes the root cause was actually a *lack* of change where one was needed (the test wasn't updated when the disjoint packs feature was removed), making change-tracking tools less relevant. He suggests compiler warnings or test failures are the usual mechanisms to catch such issues, but acknowledges the perf tests are rarely run. While CI integration for perf tests has been discussed, he's skeptical about the cost-benefit tradeoff.

The exchange highlights two ongoing challenges: (1) ensuring test coverage keeps pace with feature changes, especially for less-frequently-run tests like performance benchmarks, and (2) the broader CI infrastructure issues mentioned earlier in the thread where test dependencies aren't properly installed. Jeff takes a pragmatic view that while earlier detection would be nice, the impact was limited since the buggy code wasn't actively causing problems. The discussion remains focused on process improvements rather than technical changes to the already-merged fix.
