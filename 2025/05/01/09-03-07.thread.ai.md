Thread summary:

This thread addresses a serious bug in `git apply --intent-to-add` (`-N`) where the command incorrectly clobbers the entire index contents, marking tracked files as deleted. The issue was originally reported by Johannes Altmanninger in 2021 with a v3 patch series proposing to make `--intent-to-add` imply `--index`, though this approach was questioned by Junio Hamano due to potential conflicts with other index-modifying options like `--cached` and `--3way`. Recent discussion was reignited by Jason Cho's inquiry and Ryan Hodges' concrete demonstration of the destructive behavior.

Raymond Pasco's new analysis confirms the bug's technical details: 1) `--intent-to-add` was designed to work only with worktree changes but currently replaces the full index, 2) Altmanninger's original patch had correct code despite its confusing commit message, and 3) the option should be documented as mutually exclusive with both `--index` and `--cached`. Pasco offers to refresh and resubmit the patch if needed.

Key technical points:
- Three apply modes exist (worktree-only, index+worktree, index-only)
- Current implementation violates the principle that `--intent-to-add` should only affect new files being added
- The bug causes real workflow breakage when maintaining consistency between apply/diff/commit operations

Participants:

- Cho/Hodges: Recent reporters demonstrating actual breakage
- Pasco: Current technical analysis and patch refresh offer

Open questions:
