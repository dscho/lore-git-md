This is a follow-up discussion about a performance test fix for multi-pack reuse. Jeff King responds to Junio Hamano's earlier comment about whether better change-tracking tools could have caught the issue. 

Jeff explains that the tools Junio suggested wouldn't have helped in this case because the problem wasn't about changes that were made, but rather about a test that *wasn't* updated when related code changed. He notes that normally such issues would be caught by tests or compiler warnings, but performance tests like p5332-multi-pack-reuse.sh are rarely run. 

While acknowledging it would be nice to catch these issues sooner, Jeff points out that since the broken test wasn't actually being used, the impact was minimal. He expresses skepticism about running performance tests in CI due to the CPU time tradeoff, though he does note that the test did ultimately work as intended by catching the inconsistency when someone finally ran it.

The exchange highlights an ongoing tension between thorough testing and practical constraints, with Jeff taking a pragmatic view that while early detection is ideal, some latency in finding test issues may be an acceptable tradeoff for rarely-run performance tests. The actual bug (incorrect "+" prefix in test input) was already fixed in the previous email, so this message focuses more on the process implications.
