This is a maintainer response in the ongoing `git apply --intent-to-add` bugfix thread. Junio Hamano weighs in on the proposed solution to make `--intent-to-add` imply `--index`, pointing to existing documentation that suggests the behavior is more nuanced than the patch assumes. The key observation is that `--index` is not the only way to affect the index (e.g. `--cached` also does), and automatically forcing `--index` could create incorrect behavior in some cases. Hamano questions whether the original patch is still relevant given this understanding, implying the solution may need reconsideration.

The response casts doubt on the technical approach of the v3 patch series while not outright rejecting it. It highlights an important design constraint: that index-modifying behavior in `git apply` has multiple pathways beyond just `--index`. This suggests any fix would need to account for interactions with other index-affecting options like `--cached` and `--3way`.

The thread now appears at a decision point - either the status quo with the documented behavior, or develop a more comprehensive solution that properly handles all index-modifying scenarios when `--intent-to-add` is used. The original bug report about tracked files being incorrectly marked as deleted remains unaddressed, but Hamano's intervention indicates the solution path is less straightforward than initially proposed.
