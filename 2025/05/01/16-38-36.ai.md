This is a follow-up in the ongoing discussion about Scalar's `--no-maintenance` flag architecture. Junio Hamano responds to Derrick Stolee's defense of keeping maintenance control within `register_dir()`, reinforcing his position that explicit calls at the command level (`cmd_register()`/`cmd_clone()`) would provide better long-term maintainability.

Hamano makes two key technical arguments: (1) explicit calls at each command site make maintenance behavior more visible to code readers, contrasting with parameter-passing through `register_dir()` which obscures caller differences, and (2) since `toggle_maintenance()` must still be called directly for the `--no-maintenance` case anyway, there's no real abstraction benefit to routing through `register_dir()`. He acknowledges the current implementation could suffice if maintenance remains the only customization, but suggests the explicit approach would better accommodate future extensions.

The email doesn't introduce new code changes but strengthens the architectural case for the v2 restructuring Stolee committed to explore. It highlights an important tension between centralized configuration (Stolee's preference) versus explicit command-level control (Hamano's recommendation), with implications for how future Scalar customizations might be implemented. The discussion remains focused on clean separation of concerns while preserving the original goal of avoiding maintenance.lock conflicts in automated environments.
