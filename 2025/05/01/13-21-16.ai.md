This is a design discussion follow-up in the Scalar `--no-maintenance` flag series. Derrick Stolee responds to Junio Hamano's architectural feedback about where maintenance control should live in the codebase.

Stolee acknowledges the oversight regarding `cmd_reconfigure()`'s unconditional maintenance enabling, agreeing it needs addressing. The core discussion revolves around whether maintenance toggling belongs in `register_dir()` (current implementation) or should move up to command-level callers like `cmd_register()`/`cmd_clone()` (Hamano's suggestion).

Stolee presents a counter-perspective that `register_dir()` serves as a centralized configuration point for "recommended settings" (including maintenance), and that moving control upward might lead to duplicated logic if more customizations are added later. However, he commits to exploring restructuring options for v2 while maintaining the flag's core functionality of preventing maintenance.lock conflicts in automated setups.

The email doesn't propose concrete code changes yet, instead framing this as preliminary thinking before implementation work. Key unresolved questions include: whether maintenance control is truly part of directory registration's core responsibility, how to handle `cmd_reconfigure()`'s behavior, and how to maintain clean separation of concerns if more configuration customizations emerge. The thread remains in design discussion phase pending Stolee's v2 implementation.
