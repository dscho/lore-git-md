This is a discussion contribution about Change-ID tracking and commit evolution, building on Junio C Hamano's proposal for predecessor-successor relationships. Kristoffer Haugsbakk shares their practical experience with tracking patch versions through custom email headers (`X-Commit-Hash` and `X-Previous-Commits`) and suggests a more flexible approach to indexing commit relationships.

The email provides concrete examples of how the author has manually tracked patch revisions across multiple versions (v1-v3) using custom email headers, noting the Message-ID field isn't reliable for this purpose. This serves as a real-world example of tracking commit evolution outside Git's native mechanisms.

A key new suggestion is the idea of user-defined custom indexes in Git's object database, which would allow different workflows to define their own identifiers and relationships without requiring consensus on a single Change-ID format. The author illustrates this with the example of creating an index for stable patch-ids to speed up cherry-pick detection.

This contribution advances the discussion by:
1) Providing empirical data on alternative tracking methods
2) Suggesting a more flexible indexing system that could accommodate diverse workflow needs
3) Raising the question of whether standardized Change-IDs are necessary if users can define their own relationship tracking

The email doesn't propose specific code changes but offers valuable perspective from someone implementing version tracking in practice. The custom indexing idea in particular could influence how the community thinks about accommodating different Change-ID approaches without core Git modifications.
