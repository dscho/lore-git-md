This is a feature patch that enhances `git pull --rebase` to properly handle fork-point options. The change allows users to explicitly control whether to use the fork-point algorithm during rebase operations, both via command-line flags (`--fork-point`/`--no-fork-point`) and through the `rebase.forkpoint` config setting.

The patch addresses a reported issue where `git pull --rebase` was always using the fork-point behavior, which wasn't always the desired outcome. The implementation adds new option handling in `builtin/pull.c`, including:
- New static variables to track fork-point preferences
- A command-line option for fork-point control
- Config parsing for `rebase.forkpoint`
- Logic to determine whether to use fork-point based on both config and command-line options
- Clear messaging about the fork-point decision via stderr output

The change appears well-contained, touching only the pull machinery's rebase integration. The patch includes clear conditional logic for handling the preference cascade (command-line overrides config, with a default of using fork-point when unspecified). The implementation maintains backward compatibility while adding the requested flexibility.

Key technical details for future reference:
- New config: `rebase.forkpoint` (boolean)
- New option: `--fork-point`/`--no-fork-point` for `git pull --rebase`
- Modified function: `cmd_pull()` now checks fork-point preferences before calling `get_rebase_fork_point()`
- Behavior change: When fork-point is disabled, clears `rebase_fork_point` even if one could be found
- Output: Now prints whether rebase is using fork-point via `fprintf_ln(stderr)`
