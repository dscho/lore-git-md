This is a continuation of the `git-blame-tree` naming and integration debate, with Marc Branchaud strongly advocating for integrating the functionality into `git blame` rather than creating a separate command. The email responds to Toon Claes' arguments for keeping the commands separate, focusing on three key points:

Marc counters the UNIX philosophy argument by noting many Unix utilities (like `diff` and `ls`) already change behavior based on input type (file vs directory). He provides concrete examples where context-dependent behavior is the norm rather than an exception. The discussion of machine parsing is dismissed as a non-issue since `git blame` isn't plumbing and scripts would know their input types.

The discoverability argument is flipped - Marc contends that extending `git blame` makes the feature more visible to existing users through tab completion and accidental discovery (like passing a directory), while a new command would remain obscure. He draws parallels to `git add` which handles both files and directories without needing separate commands.

Technical implementation concerns are addressed by noting that script authors would know their input types when invoking the command, making output format differences manageable. Marc suggests pipe-reading scripts could explicitly declare expected formats rather than trying to auto-detect, which would be needed regardless of the command structure.

This email reinforces the ongoing tension between command integration and separation, with Marc providing detailed counterarguments to Toon's position while maintaining the thread's focus on user experience and practical implementation concerns rather than technical feasibility. The core naming objection ("blame" being conceptually wrong for tree operations) remains unaddressed in this response.
