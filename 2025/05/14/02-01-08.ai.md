This is a bugfix patch addressing submodule configuration safety when reusing paths. The v3 iteration from K Jayatheerth implements Junio Hamano's suggested approach for handling name/path conflicts in submodule additions, building on previous thread discussion about preventing silent `.gitmodules` overwrites.

The core change modifies `module_add()` to detect when a requested submodule name already refers to a different path in the existing configuration. By default, this now errors out, requiring explicit `--name` specification. With `--force`, it generates unique numbered names (child1, child2 etc.) similar to filesystem behavior. The implementation introduces `submodule_active_matches_path()` to efficiently check path coverage under `submodule.active` without redundant config reads.

Key technical improvements in v3 include proper memory management for auto-generated names (fixing a potential leak noted in review), C style fixes (declaration ordering), and expanded test coverage in t7400 verifying both the error case and numbering scheme. The patch maintains compatibility with existing `submodule.active` handling while adding safety checks.

The solution addresses the original issue where moved submodules could have their config silently overwritten, though some efficiency questions around multiple config lookups remain marked with NEEDSWORK. This version appears to incorporate all substantive feedback from the thread while preserving the core approach of failing safe by default with `--force` providing an escape hatch. The test demonstrates the protection via a sequence of submodule add/move/re-add operations.
