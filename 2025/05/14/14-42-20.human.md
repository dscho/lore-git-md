This is a discussion about the UI design and discoverability of the proposed `git-blame-tree` command, specifically addressing whether it should be integrated into `git blame` or remain a separate command.

Toon Claes responds to Marc Branchaud and Junio Hamano's earlier discussion about integrating the tree-level blame into `git blame`. He argues against the DWIM (Do What I Mean) approach that would make `git blame` behave differently based on whether the argument is a file or directory, calling this behavior "obscure" and preferring the Unix philosophy of single-purpose commands. He provides concrete use cases from GitLab's workflow where passing multiple files to `git-blame-tree` is more efficient than current alternatives like `git log -1` or piping `git blame` through grep.

The email highlights two key points of contention: 1) whether the functionality should live in a new command or as an option to `git blame`, and 2) concerns about discoverability versus clear command behavior. Toon makes a case that a separate command with clear documentation strategy would be better than overloading `git blame` with context-dependent behavior that produces radically different output formats. The discussion remains open, with performance considerations and real-world use cases now added to the debate.
