This is a follow-up discussion in the completed oidmap refactoring thread, specifically about the second patch that introduced `oidmap_get_size()`. Jeff King clarifies Patrick Steinhardt's question about the distinction between checking the hashmap's allocated table size versus the actual entry count in the replace-object subsystem. 

The key point is that while the two metrics (table size vs entry count) are not generally equivalent, they produce the same result for the specific use in `lookup_replace_object()` because that code only needs to know if the map is empty or not. Since the replace-map only grows smaller (entries are added but never removed), a non-zero table size reliably indicates at least one entry exists. Jeff acknowledges Patrick's observation that the original explanation could have been clearer by focusing on the emptiness check rather than size comparison, but considers the matter settled since the patch is already in the 'next' branch with Patrick's ack.
