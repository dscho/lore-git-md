Performance optimization discussion around promisor-remote object verification. Han Young responds to Junio Hamano's concerns about their earlier patch that removed `is_promisor_object()` checks from `promisor_remote_get_direct()`. The thread has revealed deeper complexities in the promisor object system.

Han confirms the performance bottleneck comes from `is_promisor_object()` needing to parse every object in promisor packfiles, which is extremely slow for large repositories. They explain why Junio's suggestion of caching this data on disk isn't feasible - the definition of promisor objects is dynamic since local objects can become promisor objects.

The discussion has surfaced two key assumptions in the original patch that may not hold: (1) callers don't actually verify objects are promisor objects before passing them, just that they're missing locally, and (2) the error behavior changes subtly - the function will now die on any fetch failure rather than just for promised objects. Han notes they've observed different error messages in testing but the end result (command failure) is the same.

This remains an active discussion about how to safely optimize promisor object handling while maintaining correct behavior. The core performance problem is clear, but the solution space now appears more complex than initially thought, involving both implementation details and behavioral contracts.
