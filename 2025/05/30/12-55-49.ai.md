This is a bugfix patch addressing a locking race condition in the maintenance "gc" task, following similar fixes for "pack-refs" and "reflog-expire" tasks in earlier patches of the series.

The patch splits the GC task into two phases - before and after detach - mirroring the approach used in git-gc itself. The key changes include:
1. Renaming `gc_before_repack()` to `gc_before_detach()` for clarity
2. Adding a hidden `--skip-maintenance-before-detach` flag to control when pre-detach steps run
3. Updating the maintenance task to use separate before/after detach callbacks
4. Modifying tests to account for the new flag

Ben Knoble raises a question about the implementation - if `--no-detach` is specified, why do we still need to skip the before-detach steps? This suggests there may be some subtlety in the interaction between the maintenance runner and git-gc's own detach logic that warrants closer examination.

The changes are focused on builtin/gc.c and its test file, with careful attention to the locking sequence around repository maintenance operations. The patch appears well-structured and follows the pattern established by previous fixes in the series, though the question about detach behavior indicates there may be room for clarification in the implementation approach.
