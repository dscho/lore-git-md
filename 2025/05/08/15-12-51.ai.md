This is a discussion about UI design considerations for integrating the proposed `git-blame-tree` functionality into `git blame`. Marc Branchaud and Junio Hamano are working through the details of how the command should behave when given paths, particularly around recursion and maintaining backward compatibility.

Key points in this email:
- Junio firmly states that `git blame path/to/file` must maintain its current line-by-line annotation behavior and cannot change, as this would break existing expectations. He notes that `git log -1` already provides the "last commit" information that was being considered as an alternative behavior.
- The discussion turns to recursion behavior for directories, where Marc suggests making non-recursive the default with an option to recurse, citing potential performance concerns with recursive output. Junio expresses no strong preference but notes that recursive behavior (like `git ls-files`) had seemed natural to him initially.
- Both agree that regardless of the default, having an option to control recursion would be useful. Marc emphasizes the importance of not overwhelming users with output by default.

This continues the thread's central debate about whether and how to integrate the tree-level blame functionality into the existing `git blame` command versus keeping it separate. The exchange clarifies important constraints around backward compatibility while leaving open the question of recursion defaults, which appears to be moving toward a configurable solution rather than a hard requirement either way.
