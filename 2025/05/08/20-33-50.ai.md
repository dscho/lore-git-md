This is a follow-up discussion in the completed series optimizing packed-refs memory usage, specifically addressing mmap strategy considerations. Jeff King (peff@peff.net) responds to Junio Hamano's observation that the temporary snapshot approach may be unnecessary for fsck operations.

The email focuses on technical details of mmap implementation choices. Jeff agrees with Junio's assessment that direct mmap/verify/unmap would be more appropriate than the temporary snapshot helper for fsck operations. He examines the mmap_strategy handling, noting that MMAP_NONE only occurs when NO_MMAP is set, since there's no config mechanism to set the strategy directly.

Jeff explores deeper implications about the mmap implementation, questioning whether MMAP_NONE could be eliminated entirely by relying on git_mmap()'s emulation, though he identifies edge cases with MMAP_PREVENTS_DELETE and NO_MMAP combinations that might make this problematic. He also ponders the efficiency tradeoffs of MMAP_TEMPORARY versus direct buffer reads, but concludes these are likely not worth revisiting given the existing SMALL_FILE_SIZE threshold logic.

Key technical details mentioned:
- The packed-refs fsck path will use direct mmap/verify/unmap pattern
- MMAP_NONE is only triggered by NO_MMAP compile-time setting
- Potential edge cases with MMAP_PREVENTS_DELETE and NO_MMAP
- SMALL_FILE_SIZE threshold maintains read_in_full() code path
- git_mmap() emulation handles mmap-incapable platforms

This discussion provides final implementation guidance for the series, confirming the direct mmap approach while documenting some historical mmap strategy considerations that don't need to be changed. The exchange represents the final technical clarification before the series is integrated.
