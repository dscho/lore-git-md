This is a review comment on the gitk SHA-256 support patch series. Johannes Sixt provides several technical observations about the implementation details in the first patch of the series.

Key points raised:
- The commit message should be cleaned up to remove outdated references to the patch's evolution and irrelevant details
- Questions whether the regex in `gotocommit` should use the new `$hashlength` variable rather than hardcoding 63
- Notes inconsistent indentation (spaces vs tabs) in the code
- Points out that the error message for unsupported hash algorithms doesn't properly interpolate `$objformat`
- Questions the need for the temporary `objformat` variable and unused `hashalgorithm` variable

The review focuses on code quality issues rather than the SHA-256 functionality itself, suggesting tighter implementation and better variable handling. These appear to be minor cleanup opportunities rather than fundamental flaws in the SHA-256 support approach. The feedback comes after the full two-patch series was submitted but before any other reviews, indicating this may be the first technical scrutiny of the implementation details.
