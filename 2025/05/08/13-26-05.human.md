This is a continuation of the discussion about whether to implement directory-level blame as a new `git-blame-tree` command or integrate it into existing `git blame` functionality. Marc Branchaud strongly advocates for integration, arguing that adding another command would make Git's already large command set harder to discover and use effectively. He makes several key points:

1. The existing `-tree` commands are all plumbing (low-level internals) rather than porcelain (user-facing commands), so adding a user-facing `blame-tree` would be inconsistent with Git's current patterns.

2. Advanced users who might need this functionality are unlikely to discover it if it's a separate command, whereas they would naturally find it if integrated into `git blame`'s documentation.

3. Git's command proliferation is already a known usability issue, and new commands should only be added after careful consideration of alternatives.

The discussion highlights an important design tension between discoverability and command organization. While the technical implementation of directory-level blame is ready, this naming and integration question remains a key blocker for the feature's acceptance. The thread shows the Git community's careful consideration of how new features should fit into the overall user experience.
