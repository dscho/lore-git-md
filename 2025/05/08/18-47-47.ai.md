This is a tangential suggestion in the ongoing discussion about Git backup strategies. Michal Suchánek proposes an alternative approach using filesystem-level deduplication for full repository snapshots, rather than the bundle-based incremental solutions being discussed.

The email suggests that filesystems with built-in deduplication (like ZFS or Btrfs) could store multiple full repository clones while only consuming space for unique objects. This would maintain the simplicity of the current `git clone --bare` approach while potentially reducing storage overhead through filesystem magic. However, Michal notes this doesn't solve the need for multiple full backups and would still require supplemental approaches (bundles or tarballs) for that purpose.

This contribution introduces a third architectural option alongside the previously discussed bundle-based and state-tracking approaches. It's notable for being storage-layer rather than Git-layer, and while it doesn't address the core timestamp vulnerability issue raised earlier, it provides a different perspective on handling the storage efficiency problem. The suggestion appears technically sound but may not fully meet the enterprise reliability requirements that have been a focus of the thread, as it still relies on periodic full snapshots.
