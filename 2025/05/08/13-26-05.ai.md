This is a continuation of the discussion about integrating directory-blame functionality into Git, specifically debating whether to create a new `git-blame-tree` command or extend existing `git blame`.

Marc Branchaud strongly advocates against adding a new command, arguing that:
1. The `-tree` commands are plumbing not meant for regular users, unlike the proposed `blame-tree` which would be porcelain
2. Feature discovery is harder with separate commands - users who know `git blame` would more likely find directory-blame functionality if it were integrated there
3. Git's command proliferation is already problematic and new commands should only be added after serious consideration of alternatives

He counters Kristoffer Haugsbakk's point about existing `-tree` commands by noting they are all plumbing tools, not user-facing porcelain like `blame-tree` would be. Marc emphasizes that as an experienced Git user, he would likely discover directory-blame functionality if it were part of `git blame`, but might never find a separate `blame-tree` command.

The exchange highlights the core tension in the RFC between creating a new focused tool versus extending an existing one, with Marc firmly in the integration camp based on user experience and discoverability concerns. This continues the thread's ongoing debate about the best architectural approach for this functionality.
