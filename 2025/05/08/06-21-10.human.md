This is a review follow-up in the gitk SHA-256 support thread. Johannes Sixt (Hannes) points out several remaining hardcoded references to 40-character SHA-1 hashes that were missed in Takashi Iwai's patches adding SHA-256 support to gitk. The issues are all in Tcl code that handles commit IDs - in functions dealing with long IDs, short IDs, patch generation, and tag creation.

Hannes notes these are similar to the regex and length issues he previously identified in the first patch, suggesting a consistent cleanup pass is needed. The locations mentioned (longid, shortids, setlink, mkpatch, mktag) all appear to be UI/display-related functions that need to respect the repository's hash length rather than assuming SHA-1's 40 characters.

This continues the pattern from earlier reviews where the implementation is technically correct but needs more thorough updates to fully eliminate SHA-1 length assumptions. The feedback is constructive and specific, identifying exactly which procs need attention, which should help ensure the final version properly handles both hash algorithms everywhere.
