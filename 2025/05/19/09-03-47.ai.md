This is a follow-up discussion in the bundle-uri parsing thread, focusing on numeric input handling and Windows compatibility. Phillip Wood responds to Jeff King's comments about 64-bit value parsing, noting that most existing config values use `unsigned long` rather than 64-bit types. The exchange reveals two key technical points: first, that `repo_config_get_ulong()` and related functions accept multiplier suffixes (like 'k' or 'm'), which may not be appropriate for the bundle-uri case where bare integers are expected; second, that the bundle-uri parsing needs to be strict about input validation since it handles data from external servers.

Jeff King had previously suggested banning `*scanf()` usage, particularly with `%s` placeholders due to security risks, though numeric placeholders are less dangerous. Phillip agrees with this assessment, noting the particularly ugly example in `builtin/gc.c` that uses a custom format string to limit input size. The discussion suggests a preference for the Git codebase's usual pattern of reading into a buffer first, then parsing.

This email doesn't introduce new code changes but reinforces the technical rationale behind the earlier move away from `sscanf()` to the new `strtoul_u64()` helper. It also surfaces an open question about whether numeric parsing should be strict (digits-only) or more lenient (allowing whitespace), which could affect future parsing conventions across the codebase. The exchange hints at potential future work to introduce `repo_config_get_u64()` infrastructure while acknowledging the current solution's adequacy.
