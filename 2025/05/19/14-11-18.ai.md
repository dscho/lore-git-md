This is a discussion email in the promisor-remote protocol enhancement series, specifically addressing Patrick Steinhardt's review comments on v2 of the patches. The email focuses on clarifying design decisions around field handling in the protocol extension.

Christian Couder responds to several points from Patrick's review of the documentation and implementation:

1. Defends the current global `promisor.sendFields` configuration approach rather than making it per-remote, arguing the current design already supports different filters/tokens per remote and that per-remote configuration can be added later if needed.

2. Explains the purpose and handling of the "partialCloneFilter" and "token" fields in detail:
   - The filter field lets clients verify server-side filter configuration matches their own
   - The token field enables future authentication without dictating specific usage patterns
   - Emphasizes these fields are currently only used for validation, not operation

3. Documents protocol behavior changes in v3:
   - Now requires (MUST) clients ignore unknown fields rather than recommending (SHOULD)
   - Renames implementation details ("allowed_fields" -> "known_fields")
   - Spells out abbreviated terms in documentation

4. Justifies the incremental approach to token handling, arguing it's better to establish the field passing mechanism separately from any future standard usage patterns.

The email shows the author incorporating feedback while defending certain design choices as pragmatic solutions that don't preclude future enhancements. It provides important context about the security and compatibility considerations shaping the protocol design, particularly around the token field's future evolution path.
