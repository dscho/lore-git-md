This is a follow-up discussion in the UTF-8 alignment thread, where Junio C Hamano responds to Phillip Wood's concerns about encoding assumptions in the proposed solution. 

Junio acknowledges that Git's existing UTF-8 width calculation tools (like `utf8_strwidth()`) are fundamentally limited to UTF-8 and would misbehave with other encodings like latin-1 or ISO/IEC 2022. He notes this is a systemic issue affecting multiple Git features including `diff --stat`, though he's unsure whether UTF-8 handling has been fully fixed even for those cases.

Regarding implementation approach, Junio suggests that manually calculating padding via `printf()` (as Phillip proposed) would be preferable to using `strbuf_utf8_align()`, as it allows more control over column width allocation and truncation of overly long entries. This pushes back slightly on Jiang Xin's current implementation direction while validating Phillip's technical concerns.

The exchange highlights an important trade-off between correctness (handling all cases) and practicality (working within Git's existing UTF-8 assumptions). Junio's response indicates the project may need to accept some encoding limitations while still optimizing the implementation approach. This moves the thread forward by narrowing the discussion to specific implementation choices rather than fundamental design questions.
