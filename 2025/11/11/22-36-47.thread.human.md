This thread addresses a security vulnerability in Git's attribute macro expansion system, where deeply nested macros could theoretically cause a stack overflow. The core issue was identified in `attr.c`'s recursive implementation, which could be exploited by maliciously crafted attribute files with extremely deep macro chains.

Jeff King (Peff) proposed converting the recursive implementation to an iterative one using a LIFO queue, maintaining the same behavior while eliminating the stack overflow risk. The discussion initially considered whether additional safeguards like reduced file size limits were needed, but consensus has formed that the iterative solution alone is sufficient. Peff clarified an important detail: while it was thought macros could chain across nested `.gitattributes` files, Git actually restricts macro definitions to top-level files only. This architectural choice means the vulnerability is constrained to macro expansion within a single file, making the attack surface even smaller than initially considered.

The current state is that the iterative solution is clearly the right approach, converting what would have been a stack overflow into a more manageable heap allocation issue. While there was some discussion about potentially reducing the maximum attribute file size from 100MB to 10MB, this appears unlikely to be pursued unless someone steps forward to implement it. The thread has effectively reached consensus that the core fix is sound and additional protections aren't strictly necessary given Git's existing safeguards and the constrained nature of the vulnerability.
