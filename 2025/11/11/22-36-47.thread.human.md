This thread addresses a security vulnerability in Git's attribute macro expansion system, where deeply nested macros could cause stack overflows. Jeff King (Peff) proposed converting the recursive implementation to an iterative one using a LIFO queue, which eliminates the stack overflow risk while maintaining the same expansion behavior. The initial discussion found consensus that this was a reasonable approach, though D. Ben Knoble noted it trades stack issues for potential heap exhaustion.

Patrick Steinhardt has now joined the discussion, raising concerns that while the iterative solution prevents stack overflows, it doesn't fully address resource exhaustion - an attacker could still consume excessive memory with extremely long macro chains. He suggests a hard recursion limit might provide better overall protection by constraining both stack and memory usage while enabling clearer error messages. 

The core debate now centers on security tradeoffs: Jeff's patch solves the immediate stack overflow vulnerability, while Patrick advocates for a more comprehensive approach to resource constraints. Both agree the practical risk is low, as legitimate operations would rarely approach these limits and hosting platforms already have size protections. The thread remains open on whether to proceed with the current iterative solution or consider adding explicit limits to the attribute expansion system.
