This thread addresses a security vulnerability in Git's attribute macro expansion system, where deeply nested macros could cause stack exhaustion. The core issue involves recursive processing in attr.c that could be exploited by malicious macro chains, though the attack surface is limited since macros can only be defined in top-level .gitattributes files.

The technical solution has converged on converting the recursive implementation to an iterative one using a LIFO queue, maintaining the same behavior while eliminating stack overflow risks. Jeff King (Peff) led this approach, noting that while heap exhaustion remains theoretically possible, it would require extremely large input files and is more manageable than stack issues. Existing protections include a 100MB file size limit.

Recent discussion has shifted to risk assessment. Junio C Hamano has questioned how realistic the threat is, doubting whether repositories with malicious macro chains would be worth cloning in practice. He suggests the iterative solution alone may be sufficient and raises the possibility of gathering data on real-world macro usage patterns from hosting providers. Patrick Steinhardt, who had initially suggested additional limits, now agrees the current approach is adequate for now but leaves open the possibility of future safeguards if needed.

The thread appears to be moving toward closure, with the main outstanding considerations being whether to document the failure mode changes and whether to gather more usage data before finalizing. The consensus favors the iterative solution as providing sufficient protection given the limited practical risk.
