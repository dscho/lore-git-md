Thread identity: Security fix for stack overflow in Git's attribute macro expansion system (attr.c).

Core problem: The recursive implementation of attribute macro expansion could be exploited via maliciously deep macro chains to cause stack exhaustion, potentially crashing Git during operations like clone or diff. While requiring ~200k nested macros to trigger naturally, this represents a real (if low-risk) vulnerability.

Current status: Initial patch proposing conversion from recursive to iterative implementation using LIFO queue. No version history yet as this is the first submission.

Key technical details:
- Replaces recursive `macroexpand_one()` in `attr.c` with iterative approach using new `attr_state_queue` struct
- Maintains depth-first expansion order identical to original behavior
- Uses ALLOC_GROW for dynamic queue sizing
- Preserves all existing attribute resolution semantics
- Test case demonstrates fix by creating 3000-macro chain and verifying resolution under stack-constrained environment (using ULIMIT_STACK_SIZE)

Open questions: None raised yet - appears ready for review. Key points to verify would be queue growth behavior under extreme cases and confirmation no edge cases exist in expansion ordering.

Participant positions: Only original author (not yet identified by name in this first message) has participated so far.

Related work: This appears to be a standalone security hardening change not directly tied to other in-flight efforts. The attribute system was last substantially modified in 2.40.0 with the introduction of "attribute macros" feature.
