Thread identity: Security fix for stack overflow in Git's attribute macro expansion system (attr.c).

Core problem: The recursive implementation of attribute macro expansion could be exploited via maliciously deep macro chains to cause stack exhaustion, potentially crashing Git during operations like clone or diff. While requiring ~200k nested macros to trigger naturally, this represents a real (if low-risk) vulnerability.

Current status: Initial patch proposing conversion from recursive to iterative implementation using LIFO queue. Discussion has expanded to consider broader security tradeoffs between stack vs heap exhaustion and whether explicit limits should be imposed.

Key technical details:
- Replaces recursive `macroexpand_one()` in `attr.c` with iterative approach using new `attr_state_queue` struct
- Maintains depth-first expansion order identical to original behavior
- Uses ALLOC_GROW for dynamic queue sizing
- Preserves all existing attribute resolution semantics
- Test case demonstrates fix by creating 3000-macro chain and verifying resolution under stack-constrained environment (using ULIMIT_STACK_SIZE)
- New consideration: iterative approach converts stack overflow risk to potential heap exhaustion
- Security analysis: would require "many millions or even billions" of attributes to trigger OOM
- Hosting platforms likely already have size limits that would block such attacks

Open questions: 
- Whether to proceed with pure iterative solution or add explicit recursion/memory limits
- Whether to document the failure mode shift (stack->heap)
- Whether compute resource exhaustion merits protection given legitimate operations can also be resource-intensive

Participant positions:
- Jeff King (Peff): original patch author proposing iterative solution
- D. Ben Knoble: raised heap allocation considerations but agrees with approach
- Patrick Steinhardt: suggests considering hard limits as alternative that would constrain both stack and memory usage while enabling clearer error messages

Related work: This appears to be a standalone security hardening change not directly tied to other in-flight efforts.
