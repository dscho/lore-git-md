Feature implementation for the `GIT_REF_URI` environment variable proposal. This second patch in the series builds on the refactoring from patch 1 to enable specifying reference backends and storage locations via URI syntax (e.g., `reftable:///path/to/refs`). The implementation handles URI parsing in `get_ref_store_from_uri()` and integrates it with the main ref store initialization in `get_main_ref_store()`.

Key technical details include:
- URI format validation requiring `<backend>://<path>` syntax
- Support for both files and reftable backends
- Error handling for malformed URIs, unknown backends, and empty paths
- Worktree compatibility where the URI-specified directory applies to all worktree operations
- Comprehensive test coverage in t1423-ref-backend.sh verifying:
  - Error cases (empty URI, invalid format, unknown backend)
  - Cross-backend read/write operations between files and reftable
  - Reference migration scenarios

The implementation defers ref store initialization until hash algorithm is known (required for reftable), addressing a timing constraint noted in the commit message. The tests demonstrate practical use cases including reading from and writing to alternate backend locations while maintaining reference consistency.

This completes the series' goal of enabling non-blocking reference migrations, particularly useful for large repositories transitioning between backends. The changes are focused in refs.c with supporting documentation updates in git.adoc. The security implications of arbitrary reference storage locations remain an open consideration not addressed in this patch.
