This is a follow-up discussion in the performance regression thread about tag peeling verification. Patrick Steinhardt responds to Junio Hamano's questions about the rationale behind the original verification changes and the current performance impact.

The key technical points clarified are:
1. The performance hit occurs during write operations when caching peeled values, particularly problematic for the reftable backend which updates frequently
2. Runtime verification of tagged object types is typically skipped to avoid overhead on every read
3. The corruption protection remains important as broken tags can propagate from remotes without fsck checks

Patrick defends maintaining write-side verification despite the performance cost because:
- It provides runtime corruption detection for tags received from remotes
- The alternative of verifying on every read would make the performance regression visible in normal operations
- The issue only manifests in corrupt repositories, but such corruption can occur through normal operations

The discussion reinforces the tradeoffs between performance and corruption protection that led to the approved solution of narrowing verification to just tagged objects. Patrick's response provides additional context about why the original broader verification was implemented while acknowledging its performance consequences.
