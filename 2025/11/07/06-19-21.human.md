This is a follow-up discussion in the performance regression thread about tag peeling verification. Patrick Steinhardt responds to Junio C Hamano's analysis of the original issue, providing additional context about the tradeoffs involved.

Patrick confirms Junio's understanding of the original motivation for validating peeled tags - caching peeled objects while validating their types to amortize the verification cost. He explains that the performance impact primarily affects write operations, which is more noticeable in the reftable backend where writes are more frequent.

The discussion reveals an important nuance: while the current fix addresses write-side performance, runtime reads of cached peeled tags still don't verify object types by default. Patrick argues this is acceptable because the issue only manifests in corrupt repositories, and adding verification to reads would make the performance regression visible during normal operation.

He raises a security consideration - corrupted tags could come from remotes and end up in user repositories since clients don't perform fsck by default. While one could argue corrupted repositories are already broken, Patrick advocates for maintaining the write-side verification as a mitigation strategy to help clients detect corruption at runtime.

This exchange provides important context about the security-performance tradeoffs that informed the final solution, which Junio has already approved for inclusion. The discussion appears to be wrapping up with consensus on the technical approach.
