Junio Hamano raises a fundamental design question about the RFC's approach to binary file attribute reporting, suggesting the diff machinery may be the wrong layer for this functionality. This is a significant shift from the technical format discussion that dominated earlier thread iterations.

The core argument is that binary-ness is an intrinsic property of a tree object, not a diff property, and thus belongs in tree inspection tools like `git ls-tree` rather than `git diff`. Hamano notes that putting this in diff machinery would incorrectly frame binary status as a property of changes between commits rather than of the objects themselves. He suggests `git show` and `git log` could instead surface this information by querying tree characteristics during history traversal.

This intervention challenges the RFC's foundational premise, potentially redirecting the feature's implementation path. The email doesn't directly engage with the TAB-delimited format discussion but implicitly questions whether the current technical refinements are solving the right problem. Hamano's perspective as Git's maintainer carries significant weight, though he doesn't outright reject the diff-based approach - he frames it as an open design question about where this metadata truly belongs in Git's object model.

Key implications:
- The discussion may need to pivot from format details to architectural placement
- Tree-oriented commands (`ls-tree`, `cat-file`) emerge as alternative candidates
- Binary status reporting would shift from change-centric to object-centric
- Existing format work could potentially transfer to these other commands if the direction changes

This represents the first high-level design challenge to the RFC's approach, coming from a position that will likely require addressing before implementation can be finalized.
