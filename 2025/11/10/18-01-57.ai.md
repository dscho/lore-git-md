This is a discussion about the proposed `--committer` option for `git commit`, focusing on use case justification. Brian M. Carlsen responds to Phillip Wood's skepticism about the need for committer identity switching within a single repository by providing concrete scenarios where this would be useful.

The response outlines three specific cases where users might need to alternate committer identities: (1) contributors working on the same project under both personal and corporate identities (citing their own work on Git as an example), (2) projects requiring Contributor License Agreements (CLAs) that mandate specific email addresses matching organizational accounts (using Google's requirements as a hypothetical), and (3) business use cases where different legal actions (like approving vs receiving payments) might need distinct identities for audit purposes.

These examples directly address the core objection raised in the thread - that environment variables and config settings should suffice for identity management. Carlsen demonstrates human-facing workflows where command-line override would provide meaningful convenience over existing mechanisms, particularly in contexts requiring frequent identity switching or legal/compliance scenarios. The response strengthens the case for the feature by moving beyond abstract symmetry arguments to concrete, practical applications that existing solutions handle less elegantly.
