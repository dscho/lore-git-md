This is a follow-up in the ongoing discussion about adding revert capability to `git replay`. Siddharth Asthana responds to Junio Hamano's point about needing to support selective, non-contiguous commit reverts (rather than just ranges) for auditability purposes.

The key clarification is that since `git replay` uses the same revision parsing as `git log`, it already supports specifying individual commits to revert (like `git replay --revert <target> <commit1> <commit4>`), which addresses the use case of reverting specific faulty commits from a merged branch. Siddharth plans to add a test to verify this behavior and document the capability.

This continues the thread's focus on making the revert functionality flexible enough to handle both bulk operations (for efficiency) and selective reverts (for auditability). The implementation appears to be converging on a design that leverages Git's existing revision parsing while addressing real-world workflow needs.
