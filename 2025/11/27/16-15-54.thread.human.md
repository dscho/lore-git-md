This thread discusses a behavior change for the experimental `git replay` command to make it drop commits that become empty during replay (where their changes are already present in the target branch). This matches how `git rebase` and `git cherry-pick` handle such cases with their `--empty=drop` option.

The patch modifies `replay.c` to detect empty commits by comparing tree OIDs, preserving only those that were originally empty (not just becoming empty during replay). It includes test coverage in t3650 showing how branch pointers update when tip commits are dropped. Phillip Wood suggested adding an option to retain empty commits if users rely on the current behavior, and there's an open question to Elijah Newren about a technical detail in the implementation.

Since `git replay` is still marked experimental, the breaking change is considered acceptable. The changes affect both the core functionality and documentation, with the implementation appearing thorough and well-tested. The discussion remains focused on whether to provide backward compatibility for the old behavior.
