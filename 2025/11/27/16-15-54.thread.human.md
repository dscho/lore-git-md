This thread discusses modifying the experimental `git replay` command to automatically drop commits that become empty during replay (when their changes already exist in the target branch), matching the behavior of `git rebase` and `git cherry-pick` with similar empty commit handling. The change, now in its fourth iteration, has evolved through careful review from key contributors.

Phillip Wood, the patch author, has addressed all technical feedback across the versions. The implementation in `replay.c` now correctly identifies empty commits by comparing tree OIDs, preserves originally-empty commits, and properly handles branch pointer updates when tips are dropped. Junio Hamano, the maintainer, has endorsed the core approach and suggested minor improvements to commit messages and test clarity. Elijah Newren confirmed the technical approach aligns with his own work and helped simplify the test cases.

The latest version (v4) removes a test authoring preference (`--only` flag) that had been questioned in earlier reviews, while maintaining all the key functionality. The documentation has been updated to clearly explain the new behavior. While there's discussion about potentially adding an option to retain empty commits in the future, there's consensus that dropping them should be the default for this experimental command.

With all substantive issues resolved and the implementation thoroughly reviewed, this change appears ready for inclusion in Phillip Wood's `ps/history` branch. The thread demonstrates how even experimental features undergo rigorous review in the Git project, with multiple rounds of feedback leading to a polished final result.
