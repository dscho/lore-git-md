This is a bugfix and behavior change for the experimental `git replay` command. Phillip Wood addresses an issue where `git replay` would create empty commits when replaying changes that are already present in the target branch, which could be confusing since the message wouldn't match the content. The patch modifies the behavior to drop such commits instead, aligning with how `git rebase --reapply-cherry-pick --empty=drop` and `git cherry-pick --empty-drop` work.

The change is implemented by comparing tree hashes before and after the merge operation in `replay.c`, dropping commits when the resulting tree matches the target branch's tree (indicating no new changes). The patch includes a new test case that verifies this behavior, showing how a branch pointer moves to the last non-dropped commit when its tip commit becomes empty.

While this changes existing behavior, the author notes this is acceptable since `git replay` is still marked as experimental. The implementation looks clean with appropriate test coverage, and the commit message clearly explains both the problem and solution. The author also raises a question to Elijah Newren about some existing code structure in `replay.c`, suggesting this may be part of an ongoing collaboration.
