This is a bugfix and behavior change for the experimental `git replay` command. The patch modifies `git replay` to drop commits that become empty during replay (where their changes are already present in the target branch), matching the behavior of `git rebase --reapply-cherry-picks --empty=drop` and `git cherry-pick --empty=drop`. The change affects both the core replay functionality and its documentation.

The key technical aspects are:
- The logic in `replay.c` now compares tree OIDs to detect when a commit becomes empty (where the replayed changes match the target branch state)
- Empty commits that were originally empty (not just becoming empty during replay) are preserved
- Branch pointers are updated to point to the last non-dropped commit when their tip commit is dropped
- A new test case in t3650 verifies this behavior by showing how `topic1` gets updated when `F` commit is dropped

The patch notes this is a breaking change but justified by `git replay`'s experimental status. Phillip Wood suggests they could add an option to retain empty commits if users rely on the current behavior. There's also a question to Elijah Newren about whether setting `result->tree` before `merge_incore_nonrecursive()` was just for avoiding a local variable or had deeper purpose.

The changes touch replay.c's commit picking logic, the git-replay documentation, and add test coverage. The implementation appears thorough with clear test cases showing both the dropping of redundant commits and preservation of originally-empty commits.
