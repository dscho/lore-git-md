This thread investigates a bug where `git diff --cached --no-ext-diff --find-copies-harder --quiet` incorrectly reports no changes (exit status 0) when changes actually exist, while the equivalent `--exit-code` variant works correctly. The issue particularly affects scripts like git-prompt.sh when configured with diff.renames=copies-harder.

Technical analysis has identified that the problem stems from how the diff queue processing diverges between `--quiet` and `--exit-code` modes when rename detection is active. In the `--quiet` path, processing stops prematurely after the first file due to an interaction between the "quick" flag and rename detection, causing the change tracking to get incorrectly reset. The bug appears long-standing but was only recently uncovered by a distro patch that sets copies-harder by default.

D. Ben Knoble's latest contribution suggests the issue may involve additional complexity - specifically how `diff_setup_done` and `diff_from_contents` interact when external diffs are disabled. This points to the external diff configuration path as another potential factor in the incorrect behavior, though the exact mechanism remains unclear. The discussion continues to focus on understanding why the queue processing differs between modes and how to fix it without breaking other flag combinations.
