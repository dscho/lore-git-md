Chris Torek provides a detailed comparison between direct patch application and three-way merging, explaining why the latter can succeed where the former fails.

The email clarifies that `git cherry-pick` inherently performs a three-way merge using full commit history, while `git apply` by default does a simpler patch application. The key difference is that three-way merging has access to the original base version of the file, allowing it to recognize when changes appear to be already applied (like in the `apple_utils.cc` case) rather than failing on context mismatches. Chris explains how `git apply --3way` bridges this gap by attempting to reconstruct the three-way merge scenario from patch metadata when possible.

The explanation includes concrete examples of patch application works at the line level and how three-way merging compares base/ours/theirs versions to handle changes more robustly. Chris notes this can lead to silent acceptance of seemingly-applied changes, which appears to be working as designed rather than being a bug. The footnote about SHA-1 collisions is an aside about Git's underlying content-addressable storage model.
