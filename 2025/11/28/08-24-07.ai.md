This is a technical clarification in the ongoing `git replay --revert` feature development thread. Siddharth Asthana responds to Elijah Newren's correction about the command's handling of disconnected commits in revert operations.

The key revelation is that while the command accepts syntax like `git replay --revert <target> <commit1> <commit4>`, it doesn't actually revert just those two commits as Siddharth initially thought. Instead, it follows Git's standard revision range behavior, reverting all ancestors of both commits (similar to how `git log` shows all history for multiple references). True disconnected commit support would require implementing `--no-walk` functionality, which currently fails with errors or segfaults due to uninitialized objects.

Elijah explains the current limitations in detail:
- The check for multiple positive refs (`rinfo.positive_refexprs > 1`) prevents processing before the revision walk
- Attempting `--no-walk` currently results in either ordering errors or segfaults
- The behavior differs from what one might expect from the command syntax

Siddharth acknowledges the misunderstanding and agrees to:
- Keep the current series focused on basic `--revert` functionality
- Consider `--no-walk` support for disconnected commits as a future enhancement
- Not claim support for disconnected commits in the current implementation

This exchange clarifies an important limitation in the feature's advertised capabilities and helps set expectations for what the initial implementation can and cannot do. The discussion remains technical and constructive, with both parties aligned on the actual behavior versus the desired functionality.
