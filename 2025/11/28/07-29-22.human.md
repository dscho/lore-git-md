This is a follow-up discussion in the `git replay` behavior thread, focusing on dropping commits that become empty during replay. Junio C Hamano is responding to Phillip Wood's patch that makes `git replay` automatically drop commits when their changes already exist in the target branch, matching the behavior of `git rebase` and `git cherry-pick` with `--empty=drop`.

Junio agrees with the approach, noting that while partial changes might still result in mismatched commit messages, completely empty commits are clearly better off being dropped. He confirms that originally-empty commits should remain, and supports making this the default behavior for the experimental `git replay` command. The discussion remains open about potentially adding an option to retain empty commits if users rely on the current behavior.

The exchange shows consensus forming around this behavior change, with Junio treating Phillip's patch as ready-for-harvesting material pending any final adjustments. The technical details about branch pointer updates and test coverage from the original patch remain relevant, but this email focuses more on validating the conceptual approach.
