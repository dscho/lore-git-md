This is a technical discussion about revision range parsing in the context of the `git replay --revert` feature, focusing on how to handle negative refs and disconnected commit specifications.

Elijah Newren responds to Junio Hamano's suggestions about handling negative refs (like `^topic~7`) in revision ranges for the `--revert` mode. He notes that rejecting negative refs outright (option 1) would break a key use case for `git replay --onto` which explicitly supports multiple branch rebasing with negative ref syntax in the documentation. While `--revert` only operates on single branches, having different parsing rules between modes would create inconsistency.

For Junio's second suggestion of interpreting negative refs specially, Elijah points out this functionality would be broadly useful beyond just `git replay` - particularly for `git log` - and suggests implementing it as a general revision walking flag that could be shared across commands. He proposes this flag could be implied by `--advance` and `--revert` modes while remaining optional for `--onto`.

Regarding ancestry-path queries, Elijah agrees they inherently deal with connected commit sets, but raises the larger issue that determining whether to treat inputs as traditional ranges versus disconnected commits may require an explicit flag rather than heuristic guessing. He questions whether the complexity is worthwhile when users could simply invoke `replay` multiple times for truly disconnected commits.

The discussion highlights the tension between:
1. Maintaining consistent revision parsing across Git commands
2. Preserving existing `--onto` use cases documented in the manual
3. Adding flexibility for disconnected commit handling
4. Avoiding over-complication of the current `--revert` implementation

Key technical points:
- Negative ref syntax (`^A B`) is currently valid and documented in `--onto` use cases
- True disconnected commit support may need a new revision walking flag
- Ancestry-path queries naturally work with connected commits
- Implementation complexity must be weighed against marginal utility

The exchange shows the careful consideration being given to both backward compatibility and future extensibility in Git's revision parsing architecture.
