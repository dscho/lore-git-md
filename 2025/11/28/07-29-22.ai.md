This is a follow-up discussion in the `git replay` behavior change thread, where Junio C Hamano is responding to Phillip Wood's patch that makes `git replay` drop commits that become empty during replay (matching `rebase` and `cherry-pick` behavior).

Junio agrees with the core approach, noting that when a commit's changes are already present in the target branch, keeping it would leave a misleading commit message. He highlights that this mismatch exists even for partially-applied commits, though the empty case is more obvious. Junio explicitly endorses dropping empty ones while preserving originally-empty commits, calling both decisions sensible.

The email reveals this is still in RFC/RFH (request-for-comments/honest-feedback) stage, with Junio noting it's acceptable to base on Phillip's in-progress `ps/history` topic branch. He concurs with Phillip's suggestion that dropping empty should be the default, leaving room to add an option later if users actually need to retain empty commits.
