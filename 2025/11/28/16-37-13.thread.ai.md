Bugfix for `git-last-modified` bitmap initialization issue in `builtin/last-modified.c`, now marked for backport to maint. The command tracks changed paths between commits using a scratch bitmap of `eword_t` (uint64_t) elements. Original bug passed element count rather than byte count to `memset()`, causing incorrect behavior (more visible on s390x big-endian but not endian-specific). Anders Kaseorg reported the test failure that revealed the issue. Toon Claes proposed the one-line fix multiplying count by `sizeof(eword_t)` in the `memset` call, which Jeff King reviewed (Helped-by) and agreed resolves the immediate issue.

King suggested two potential architectural improvements: (1) introducing a `CLEAR_ARRAY` macro to handle size calculations automatically, though noted this might be too specialized, and (2) encapsulating bitmap clearing in a `bitmap_clear()` function to avoid direct field manipulation. He acknowledged these may be over-engineering for this case. Anders Kaseorg later provided a technical correction to King's suggestion, noting that for pointer fields the correct syntax would be `sizeof *lm->scratch->words` or `sizeof lm->scratch->words[0]` rather than `sizeof(lm->scratch->words)`.

Junio C Hamano confirms the fix is correct and notes the bug dates back to v2.52.0, making it suitable for the maint branch. The patch remains unchanged from Toon Claes' original submission, which was already reviewed by Jeff King and confirmed to resolve the s390x test failures. No new technical discussion is added - this is effectively the maintainer's approval stamp on the already-agreed solution. The thread appears resolved with this acknowledgement, with consensus on the minimal fix while having explored broader code hygiene considerations about pointer arithmetic and potential future improvements to prevent similar bugs. All participants (Kaseorg, Claes, King, Hamano) have contributed to refining both the solution and the surrounding context.
