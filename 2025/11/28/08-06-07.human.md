This is a follow-up discussion in the ongoing thread about making `git replay` drop commits that become empty during replay. Elijah Newren responds to Phillip Wood's patch, generally agreeing with the approach but suggesting some test improvements.

Elijah confirms the core behavior change makes sense, noting he had a similar local implementation. He agrees with dropping commits that become empty (while preserving originally-empty ones) and thinks Phillip's implementation is slightly cleaner than his own. The discussion also touches on a minor historical question about why `result->tree` was being set before `merge_incore_nonrecursive()`, but neither remembers the original reason and both agree Phillip's approach using a temporary variable is better.

For the test case, Elijah suggests simplifying the verification approach. Rather than Phillip's complex sed-based method that simulates branch updates without actually making them, Elijah proposes directly updating the branches and using `test_when_finished` to clean up afterward. His alternative test would be more straightforward to read while still verifying the same behavior - that commits becoming empty are dropped and branch pointers are properly updated.

The exchange shows technical alignment on the core change while productively discussing implementation details. With both the patch author and another experienced contributor (Elijah) agreeing on the approach, and maintainer Junio having previously endorsed the direction, this appears to be moving toward consensus. The remaining work seems to be finalizing the test implementation and perhaps addressing the historical question about `result->tree`.
