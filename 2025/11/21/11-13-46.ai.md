This is the second patch in a three-part bugfix series addressing regressions in `git fetch`'s batched reference updates, specifically focusing on fixing non-conflicting tags not being committed when other conflicts exist. The regression was introduced by commit 0e358de64a which added batched reference updates.

The patch modifies `do_fetch()` to commit the transaction for non-atomic fetches even when there are errors, ensuring non-conflicting tags are applied while still properly reporting conflicts. The key change is adding transaction commit logic in the cleanup section when `retcode` is set and the fetch isn't atomic. This fixes cases where `fetch_and_consume_refs()` and `backfill_tags()` would previously skip committing the transaction entirely on errors.

The patch adds three new test cases:
1. Verifying basic `--tags` fetching works
2. Ensuring non-conflicting tags are fetched even when conflicts exist
3. Confirming tag backfilling works when fetching specific refspecs

The changes maintain backward compatibility while fixing the core issue. The test improvements include proper cleanup with `test_when_finished` and verification of tag presence/absence using `for-each-ref`. The solution handles both direct tag fetching and backfilling scenarios, with clear error reporting for conflicts while still applying non-conflicting updates.

This is a well-tested fix that addresses the regression while keeping the existing behavior for atomic fetches. The test coverage verifies both the basic functionality and edge cases around tag conflicts. The patch builds on the refactoring from patch 1/3 and sets up for the final patch which will ensure other post-fetch operations persist through failures.
