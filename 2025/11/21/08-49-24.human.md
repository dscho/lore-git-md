This is a follow-up in the ongoing discussion about `git submodule` behavior with `--single-branch` when initializing submodules with branch specifications in `.gitmodules`.

Uwe Kleine-König responds to D. Ben Knoble's explanation that the current behavior is documented, arguing that the documentation and implementation are both flawed in this context. He points out that while the submodule initialization correctly fetches the specified commit (b33a8abe), the tracking configuration incorrectly defaults to HEAD rather than respecting the branch specified in `.gitmodules`.

The key technical clarification is that the commit being fetched isn't actually part of the remote's HEAD branch, only in the specified scarthgap branch, yet the clone operation succeeds. Uwe suggests this implies `--branch` is being handled implicitly during initialization phase, and proposes that `--single-branch` should default to the `.gitmodules` branch when available, matching the behavior of regular `git submodule update --init`.

This email advances the discussion by providing a concrete example where the current behavior leads to a logical inconsistency, strengthening the case for modifying either the documentation or the implementation. The tone remains constructive while clearly identifying what Uwe sees as a design flaw in the current approach.
