This is a discussion email in the ongoing `git-history` command RFC thread, focusing on implementation details and design questions raised by Elijah Newren's review feedback. Phillip Wood responds to several key concerns about the proposed history editing functionality.

Phillip engages with Elijah's points about branch handling, noting that while finding all descendant branches is the ideal long-term solution, starting with single-branch support might be pragmatic if the full implementation proves too involved. He confirms the current split implementation maintains the invariant that split commits sum to the original commit's changes, addressing concerns about index preservation during interactive editing.

On extended header handling, Phillip questions whether copying headers like "encoding" makes sense during splits or rewording since the message gets re-encoded anyway. He suggests that when splitting commits, neither automatically associating the original message with the first nor second commit is safe - instead both should prompt the user to edit with the original message as a starting point.

The email reveals several subtle implementation choices that need resolution: how to handle commit metadata during edits, whether to preserve certain extended headers, and the proper way to seed commit messages during splits. Phillip's responses indicate these aren't blockers but will require thoughtful handling in the next revision, aligning with Junio Hamano's preference for incremental improvements while acknowledging Elijah Newren's valid concerns about edge cases.
