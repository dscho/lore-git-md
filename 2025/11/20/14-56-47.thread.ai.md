Git thread summary:

Feature request for a `git cp` command to copy files while preserving history/blame information, analogous to `git mv` for moves. Original author Martin Guy presented a concrete use case of splitting mp3.c into mad.c, lame.c, and twolame.c while maintaining accurate attribution, now clarifying that their primary need is for `git blame` to automatically follow copied lines back to their original source without manual intervention, as current blame stops at file split points.

Kristoffer Haugsbakk demonstrated Git's existing rename detection (`git log --find-copies-harder`) can track copied content across files, showing example output where a file copied three ways maintains proper source attribution. D. Ben Knoble added historical context by referencing Gentoo's Git patches that implemented similar functionality for ebuild developers, providing concrete evidence of real-world need.

The discussion now encompasses: 1) the original blame-tracking use case for explicit copy recording, 2) demonstration of existing dynamic detection capabilities, 3) evidence of prior implementations, and 4) a clarified technical gap where log-based detection doesn't automatically propagate to blame. Key technical details include Git's copy detection mechanics (`--find-copies-harder` flag behavior) versus explicit recording needs for blame, with Martin Guy suggesting this would parallel `git mv`'s line-tracking capabilities. Open questions remain about whether this requires new functionality (like `git cp`) or could be addressed within existing features, and no maintainer or subsystem expert has yet weighed in on implementation feasibility or desirability in core Git. The thread remains focused on use cases where accurate attribution across file splits is critical for historical tracking.
