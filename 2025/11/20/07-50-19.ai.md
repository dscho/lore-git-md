Bugfix addressing a Windows-specific segfault in path validation with `:(optional)` prefix.

Jeff King analyzes a reported segfault that occurs when using `git config get --type=path` with values starting with `:(optional)` on Windows. The root cause stems from commit 749d6d166d which changed the contract of `git_config_pathname()` - now callers must initialize the destination pointer and check for NULL after success, since the function may return success without setting the value for optional paths.

The analysis reveals multiple affected callers beyond the original report, including `blame.ignorerevsfile` handling (which can trigger double-free issues) and the `git-config` command itself. Jeff provides a sample fix for the blame case and discusses broader interface design questions, suggesting the current behavior may be surprising for cases with multiple optional paths.

Key technical points:
- The bug manifests when callers assume `git_config_pathname()` always sets the destination pointer on success
- Multiple callers need updating to handle the new NULL-return case
- The `git-config` command faces additional questions about what to display for unset optional paths
- A deeper interface redesign using a `struct config_pathname` is proposed to better communicate path existence

This appears to be a well-analyzed response to a real bug, though the discussion reveals the fix may require careful consideration of the interface contract and multiple caller updates. The proposed structural changes suggest this could evolve into a simple bugfix into a more significant API improvement.
