Follow-up in feature discussion about `git cp` command for tracking copied files.

D. Ben Knoble responds to Martin Guy's clarification about the need for `git blame` to automatically track copied lines by explaining that Git's move tracking (including for `git mv`) works the same way as copy detection - through post-hoc reconstruction rather than explicit recording in the commit. They reference a 2005 email from Linus Torvalds that established this design principle, where Linus argued against storing rename metadata directly in commits, favoring instead the dynamic detection approach that Git uses today.

This reinforces the technical distinction between the original request (which wanted explicit recording of copies for blame purposes) and Git's current architecture where all movement/copy tracking happens through content-based detection after the fact. The response suggests the current behavior is intentional rather than an oversight, though doesn't directly address whether the blame use case could or should be handled differently from the log case that was demonstrated earlier in the thread.

Key technical details include:
- Confirmation that `git mv` uses the same post-hoc detection as other rename/copy operations
- Reference to foundational design decision against storing movement metadata in commits
- Implicit question about whether blame could/should get special treatment compared to log

The exchange helps clarify the architectural constraints while leaving open whether there's room to improve blame's handling of copied content within those constraints. No new implementation suggestions are offered in this message.
