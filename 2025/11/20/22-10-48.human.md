This is a technical clarification in the ongoing discussion about implementing a `git cp` command for tracking copied files in Git history. D. Ben Knoble responds to Martin Guy's concern about `git blame` not automatically following copied lines by explaining that Git's move tracking (via `git mv`) also works through post-hoc reconstruction rather than explicit recording in history. 

The email points to a 2005 thread where Linus Torvalds explained this design decision, noting that Git prefers reconstructing file relationships dynamically rather than storing explicit metadata. This suggests that any solution for copy tracking would likely follow the same pattern rather than introducing new history metadata.

The exchange highlights a key tension in the feature request: while users want seamless blame tracking across file copies, Git's architecture favors reconstructing these relationships at read-time rather than recording them at write-time. This technical note may influence whether the proposed `git cp` command would be implemented or if the solution would focus on improving existing detection mechanisms.
