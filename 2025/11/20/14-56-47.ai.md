This is a feature request proposing a new `git cp` command to handle file copying while preserving history/blame information, similar to how `git mv` works for moves.

The author Martin Guy, is working on splitting a large source file (mp3.c) into three smaller files (mad.c, lame.c, and twolame.c). They want the history/blame information to properly track the relevant portions of code into each new file, similar to how `git mv` preserves history when moving/renaming files. Currently, they can only achieve this for one file at a time by using `git mv` followed by manual copying for the others.

The request acknowledges this is a relatively rare use case but suggests it would be useful for file splitting scenarios. The email doesn't propose any implementation details or discuss technical feasibility - it's purely a feature suggestion at this stage. The request appears well-motivated by a concrete use case but doesn't address how this would interact with Git's existing rename detection mechanisms or whether there might be alternative solutions using existing commands.
