This is a feature patch introducing the `split` subcommand for `git-history`, part of Patrick Steinhardt's v6 series implementing flexible history editing operations. The patch enables interactive splitting of a commit into two parts by selecting hunks to move into a new commit that becomes the parent of the original (now modified) commit.

Key technical details:
- Uses `run_add_p_index()` for interactive hunk selection (currently under review focus regarding code organization)
- Creates two commits: one with selected changes (new parent) and one with remaining changes (modified original)
- Preserves authorship and validates non-empty results
- Includes extensive tests covering various split scenarios (root commits, tip commits, path-limited splits)
- Handles worktree/index state preservation
- Currently limited to splitting into two commits (Elijah Newren questions whether to support N-way splits)

Open questions from review:
- Should splitting support N commits rather than just two?
- Code organization of `run_add_p_index()` vs `run_add_p()`
- Whether HEAD reachability requirement is necessary
- How edited hunks should be handled
- Whether commit message retention behavior is optimal
- Test appears to contradict hook execution claims

The implementation builds on prior infrastructure work in the series (generalized index handling, replay machinery) while introducing the interactive split workflow. Review feedback indicates the patch is functionally sound but may need refinement in several areas before finalization.
