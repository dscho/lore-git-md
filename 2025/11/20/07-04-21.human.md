This is a technical review follow-up in the ongoing `git-history` series, focusing on the add-patch subsystem refactoring. Elijah Newren questions the implementation approach for the new `run_add_p_index()` function, which enables in-memory index patching for the history editing operations.

Newren notes his limited familiarity with the add-patch code but raises a valid architectural concern: the new function appears to be a modified copy of `run_add_p()`, which could lead to maintenance issues. He suggests the existing function might instead call the new one with `r->index` as a parameter, unless there's a technical reason this wouldn't work.

The question highlights an important design point in this infrastructure refactoring, which is separating the add-patch functionality from its original interactive add context. While earlier patches in the series were straightforward mechanical changes, this review identifies a potential area where the code organization could be improved to avoid duplication. The response from Patrick Steinhardt will likely clarify whether the current structure is necessary or could be simplified.
