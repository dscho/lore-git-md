This is a follow-up in the `git cp` feature request thread, focusing on the distinction between dynamic copy tracking and explicit history recording. Martin Guy clarifies that while `git log --find-copies-harder` can retroactively detect copies, their primary need is for `git blame` to automatically follow copied lines back to their original source without manual intervention. They observe that current blame stops at the file split point, requiring users to manually switch to tracking the original file.

The email highlights a key technical gap between Git's dynamic rename/copy detection (which works for log operations) and the desired behavior for blame tracking. Martin suggests this functionality would fit naturally alongside `git mv`'s line-tracking capabilities, though they acknowledge uncertainty about Git's internal mechanisms. The discussion remains focused on use cases where maintaining accurate attribution across file splits is important for historical tracking, with no resolution yet on whether this requires new core Git functionality or could be addressed within existing features.
