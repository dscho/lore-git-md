This is a feature request proposing a new `git cp` command to handle file copying while preserving history attribution, similar to how `git mv` works for moves.

Martin Guy describes a specific use case where they're splitting a large source file (mp3.c) into three smaller ones (mad.c, lame.c, and twolame.c). They want the blame history to follow the relevant lines to each new file, just as it does when using `git mv`. Currently, they can only achieve this for one file by combining `git mv` with manual copying for the others.

The request acknowledges this is a relatively rare need but suggests it would be valuable for file splitting scenarios. The proposal is light on implementation details, focusing instead on the user-facing behavior - specifically that blame should trace back to the original file for both copies, mirroring `git mv`'s functionality.

While the email doesn't propose a specific implementation approach, it clearly identifies a gap in Git's file management commands. The use case seems legitimate for codebase refactoring scenarios, though the frequency of such needs may be low enough that most users haven't encountered this limitation before.
