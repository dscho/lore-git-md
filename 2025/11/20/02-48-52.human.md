Bugfix for `git describe`'s commit traversal order, with performance tradeoffs. Ben Boeckel follows up on a thread about `git describe` not using topological order when traversing commits, which can lead to incorrect tag descriptions in certain commit graph shapes.

The patch provides a straightforward fix that makes the traversal accurate by following ancestry order, but comes with a significant performance penalty when run without an up-to-date commit-graph (going from "instant" to "minutes" in some cases). The change fixes an existing test case that was marked as expect-fail.

Ben presents two main options moving forward: either accept the performance hit for accuracy (possibly with a warning when commit-graph is stale), or add an `--accurate` flag that makes the correct behavior opt-in since it may change existing descriptions. He notes that a previous commit (7379046221) inadvertently "fixed" the original reproduction case by stopping the search early, and provides an updated reproduction script that still demonstrates the issue.

The patch appears technically sound and addresses a real correctness issue, though the performance implications will need discussion. The thread context suggests this has been an ongoing discussion about the right tradeoff between accuracy and speed in `git describe`.
