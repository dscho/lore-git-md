This thread explores the idea of adding a `git cp` command to copy files while preserving history and blame information, similar to how `git mv` handles moves. The original use case came from Martin Guy, who needed to split an audio file (mp3.c) into multiple components while maintaining accurate attribution. 

Several contributors have clarified that Git already has mechanisms to track copied content through its rename detection system (`--find-copies-harder`), as demonstrated by Kristoffer Haugsbakk. D. Ben Knoble and Lucas Seiki Oshiro provided important context, explaining that Git intentionally avoids storing explicit movement metadata in commits, instead reconstructing file relationships after the fact through content analysis—a design principle dating back to Linus Torvalds' early decisions. Martin Guy's latest response expresses appreciation for this explanation but doesn't advance the technical discussion.

The core question remains whether Git's existing content-based detection is sufficient for blame purposes, or if new functionality (like `git cp`) would be needed to better support file-splitting workflows. No maintainers have yet commented on whether such a feature would be desirable or feasible within Git's architecture. The thread has established that the current behavior is by design, but leaves open whether practical use cases might warrant exceptions or enhancements.
