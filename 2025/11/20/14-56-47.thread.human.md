Martin Guy has proposed adding a `git cp` command that would copy files while preserving history and blame information, similar to how `git mv` handles moves. The suggestion comes from Martin's current work splitting a large source file (mp3.c) into three smaller files (mad.c, lame.c, and twolame.c). While `git mv` can preserve history for one of the resulting files, there's currently no equivalent for copying portions to multiple new files while maintaining proper attribution.

This appears to be a niche but legitimate use case for codebase refactoring, particularly when breaking up large files. The proposal is at an early stage - it presents the user need clearly but doesn't yet address implementation considerations or how this might interact with Git's existing rename detection. No technical discussion or alternative approaches have been raised yet in the thread. The feature would primarily benefit developers undertaking similar file-splitting refactors.
