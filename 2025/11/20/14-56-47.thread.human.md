This thread explores whether Git should add a `git cp` command to explicitly track file copies while preserving history, similar to how `git mv` handles moves. The original proposal from Martin Guy cited a concrete need when splitting audio codec files (mp3.c into mad.c, lame.c, etc.) while maintaining accurate blame attribution. Kristoffer Haugsbakk demonstrated that Git's existing rename detection (`git log --find-copies-harder`) can dynamically track copied content across files, showing it maintains source attribution even when files are split and modified.

D. Ben Knoble added historical context by referencing Gentoo's custom Git patches that implemented similar functionality for ebuild developers, showing this isn't just a theoretical need. While Gentoo's implementation proves the concept has real-world value, the thread hasn't yet settled whether mainline Git should adopt it. The discussion now balances three perspectives: the user-facing workflow need, the capabilities of dynamic detection, and prior art from downstream implementations. Key open questions remain about whether log-based detection fully satisfies blame use cases for split files and whether an explicit command would offer advantages in intent recording or performance. No maintainers have yet commented on the technical feasibility or desirability of adding such a command to core Git.
