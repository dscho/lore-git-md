This thread began with a feature request for a `git cp` command to copy files while preserving history and blame information, similar to how `git mv` handles moves. Martin Guy presented a concrete use case involving splitting an MP3-related file while maintaining accurate attribution. Contributors demonstrated that Git's existing rename detection (`git log --find-copies-harder`) can track copied content across files, and provided historical context about similar functionality has been implemented before (notably in Gentoo's Git patches).

The discussion clarified that Git handles both moves and copies through post-hoc content-based detection rather than explicit metadata storage, a design principle dating back to Linus Torvalds' early decisions. Multiple participants confirmed this architectural approach aligns with Git's snapshot-based model. While the existing mechanisms work for log-based history tracking, there remains an open question about whether `git blame` could be enhanced to better handle copied content within these constraints.

Randall Becker recently raised a tangential but interesting technical question about whether Git's content similarity algorithms could theoretically detect SHA-1 collisions during rename/copy detection. While this doesn't directly advance the `git cp` proposal, it explores an edge case of the content-matching behavior that underlies Git's approach to tracking file relationships. The core discussion remains focused on use cases where accurate attribution across file operations is critical, with broad agreement about why Git uses its current content-based methods but open questions about potential enhancements to blame tracking.
