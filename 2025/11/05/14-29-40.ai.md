This is a feature patch series introducing `--trailer` support to `git rebase`, part of an ongoing effort to move trailer processing in-process rather than forking to `interpret-trailers`. The series has gone through multiple revisions based on feedback from Phillip Wood, Junio Hamano, and Kristoffer Haugsbakk.

The first three patches refactor trailer handling to centralize logic and eliminate fork/exec overhead. They:
1. Extract buffer-based trailer processing into a reusable `process_trailers()` function
2. Move this function to `trailer.h` for broader access
3. Replace external `interpret-trailers` calls with direct in-process trailer appending

The final patch adds `--trailer` support to `git rebase`, currently limited to the merge backend. It validates trailer input early and rejects attempts to use trailers with the apply backend. The implementation includes comprehensive tests in the new `t3440-rebase-trailer.sh`.

The series appears well-considered, with each refactoring step building toward the final feature. The commit messages reference specific review feedback that shaped each revision, showing responsiveness to maintainer input. The test coverage is thorough, including both positive and negative cases for trailer validation and backend compatibility.

Key technical details for future reference:
- New public API: `process_trailers()` in trailer.h
- Modified commands: `commit`, `interpret-trailers`, `rebase`, `tag`
- New config: none, but adds trailer handling to existing rebase machinery
- Test file: t3440-rebase-trailer.sh with 134 lines of test cases
- Backend limitation: explicitly rejects apply backend with trailers
- Validation: checks trailer format early in rebase startup

The main points likely to come up in discussion are:
1. Whether the apply backend limitation is acceptable long-term
2. Any edge cases in trailer parsing that might be exposed by rebase's usage
3. Potential follow-up work to extend this to other commands
