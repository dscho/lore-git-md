The thread reports a bug in Git's submodule handling when working with repositories using different hash algorithms. Martin Wilck found that checking out a SHA1 submodule from within a SHA256 repository fails when using shallow clones (`--depth=1`), while working fine with full clones. The failure occurs specifically when the submodule's remote HEAD isn't an ancestor of the requested branch ("next" in this case), suggesting the shallow fetch logic isn't properly accounting for branch configurations in mixed-hash scenarios.

The report includes detailed reproduction steps using the multipath-tools repository from openSUSE and confirms the issue doesn't appear when both repositories use SHA1. While a manual workaround exists (fetching the specific branch directly), this isn't practical for automated workflows. The core functionality that's broken - `git clone --recurse-submodules --depth=1` in mixed-hash environments - remains an important use case that currently fails. The bug was observed in Git 2.52.0.rc1 on Linux with OpenSSL 3.1.4.
