Security follow-up discussing heap vs stack tradeoffs in attribute macro expansion fix.

Ben Knoble responds to Jeff King's initial patch converting recursive attribute macro expansion to an iterative approach to prevent stack overflow attacks. While agreeing with the general approach, Ben raises a subtle point about memory implications - the iterative solution trades stack usage for heap allocation, potentially converting a stack overflow into an out-of-memory condition. 

The discussion highlights that while this is likely a reasonable tradeoff (with heap generally being more robust against malicious inputs than stack), it's worth explicitly acknowledging the shift in failure modes. Ben notes the current implementation doesn't attempt more sophisticated memory optimizations like path pruning, judging such optimizations unwarranted given the niche usage of attribute macros. 

Key technical points for future reference:
- Original vulnerability: recursive `macroexpand_one()` in `attr.c` could be exploited via deep macro chains
- Current solution: iterative approach using `attr_state_queue` (LIFO)
- New consideration: heap allocation behavior under malicious input
- Context: attribute macros remain a relatively obscure feature despite some specialized uses

The exchange suggests the patch is technically sound but prompts maintainers to consider whether any explicit memory limits or documentation about failure modes would be appropriate. No changes to the implementation are proposed at this stage.
