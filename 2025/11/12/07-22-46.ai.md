This is a discussion response in the ongoing thread about adding signature-stripping functionality to `git fast-import`. Christian Couder engages with Elijah Newren's analysis of the problem space and proposed alternatives.

The email reinforces the technical rationale for implementing signature validation during import rather than export, agreeing with Newren's assessment that fast-import is the only point in the pipeline where signature validity can be properly assessed. Couder acknowledges but pushes back on Newren's alternative proposal of tracking unsigned OIDs in the export/import format, noting this could allow invalid signatures to persist if keys are revoked between export and import.

Key technical points include: the proposed 'strip-if-invalid' mode would use the same validation criteria as `git verify-commit` (requiring all necessary keys/revocation data to be available), and that signature checking must happen at import time to properly handle cases where validity changes between export and import. The discussion surfaces an important naming consideration - alternative approaches would need distinct names to avoid misleading users about what validation actually occurs.

The exchange highlights the fundamental tension in the design space: between cryptographic purity (where any history rewrite invalidates all downstream signatures) and practical use cases (where users want to selectively preserve signatures on unmodified portions of history). Couder appears to favor implementing the more intuitive behavior first while leaving room for alternative approaches to be added later under different names. The response doesn't directly address Junio's earlier concerns about cascading invalidation but does reinforce that the implementation will match `verify-commit`'s behavior.
