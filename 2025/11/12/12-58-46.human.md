Bug report: Git fails to check out SHA1 submodules in SHA256 repositories when using `--depth=1`. Martin Wilck reports that attempting to clone a SHA256 repository containing a SHA1 submodule with `git submodule update --depth 1` fails with an error about not finding the remote ref, while the same operation without `--depth 1` succeeds.

The issue appears when the submodule's HEAD isn't an ancestor of the desired branch (in this case "next"). The error suggests Git is only fetching the remote HEAD rather than respecting the configured branch setting in either `.gitmodules` or `.git/config`. Wilck provides a manual workaround involving fetching the specific commit hash directly, but notes this isn't suitable for scripting.

Interestingly, the problem doesn't occur in pure SHA1 repositories or when cloning the submodule directly with `git clone -b next --depth=1`. The report includes detailed reproduction steps and system information showing this occurs with Git 2.52.0.rc1 on a Linux system with both SHA1 and SHA256 support. This looks like a genuine edge case in Git's submodule handling when mixing hash algorithms with shallow clones.
