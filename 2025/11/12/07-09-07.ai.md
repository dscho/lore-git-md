This is a security-related follow-up in the thread about recursive attribute macro expansion in Git's attribute system.

Jeff King responds to Ben Knoble's concerns about the tradeoff between stack and heap exhaustion in the proposed iterative solution. The key points are that heap allocation is preferable because (1) heap limits are much larger than stack limits (8MB default stack vs potentially GBs of heap), and (2) heap allocation failures can be detected and handled gracefully in C, unlike stack overflows which typically cause crashes.

The discussion reveals some existing Git protections: a 100MB limit on attributes files (from commit 3c50032ff5) and configurable tree depth limits that would indirectly constrain macro chaining across files. Jeff notes these limits were chosen pragmatically based on hosting provider experience rather than deep analysis.

The email highlights Git's general security philosophy for resource exhaustion: let processes die when they exceed reasonable resource bounds, relying on OS-level protections for hosted environments. This approach accepts that malicious actors could trigger OOM conditions but considers this no worse than other ways to consume resources, while legitimate operations are unlikely to hit these limits.

The thread continues to weigh whether additional explicit limits would be valuable versus relying on existing mechanisms. This email reinforces the iterative solution's security benefits while acknowledging the broader context of Git's resource management strategy.
