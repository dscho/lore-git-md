Bug report about submodule checkout failure in SHA256 repositories when using --depth=1.

Martin Wilck reports a specific failure case when trying to check out a SHA1 submodule from within a SHA256 repository using shallow clones. The key symptom is that `git submodule update --depth 1` fails with an error about not finding the remote ref, while the same command without `--depth 1` succeeds. The issue appears when the submodule's remote HEAD is not an ancestor of the desired branch (in this case "next"), suggesting the shallow fetch logic isn't properly respecting the submodule branch configuration.

The report includes detailed reproduction steps using a specific repository (multipath-tools from openSUSE) and shows the problem doesn't occur in SHA1 repositories. A workaround involving manual fetching of the specific branch is provided, but the reporter notes this isn't ideal for scripting purposes. The ultimate goal of making `git clone --recurse-submodules --depth 1` work remains unachievable with this bug present.

The system info shows this was tested with a development version of Git (2.52.0.rc1) built from a specific commit, running on Linux with OpenSSL 3.1.4. The report is thorough, including both the expected and actual behavior, and demonstrates the reporter has done significant investigation into the problem's boundaries (testing different repository types and clone methods). The issue appears to be a genuine bug in Git's submodule handling when dealing with mixed hash algorithms and shallow clones.
