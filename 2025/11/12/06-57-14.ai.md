Security hardening discussion regarding attribute macro expansion tradeoffs.

Patrick Steinhardt responds to Jeff King's patch converting recursive attribute macro expansion to an iterative approach to prevent stack overflows. While agreeing the iterative solution works, Steinhardt raises concerns that it merely shifts the failure mode from stack exhaustion to potential heap exhaustion when processing maliciously deep macro chains.

The key observation is that while iteration prevents immediate stack overflow, an attacker could still create resource exhaustion by forcing Git to process extremely long macro chains that consume excessive memory. Steinhardt suggests a hard recursion limit might be preferable as it would both prevent stack overflows and constrain memory usage, while also enabling clear error messages when limits are exceeded.

The discussion highlights two perspectives on security tradeoffs: Jeff King's patch focuses on eliminating the immediate stack overflow vulnerability, while Steinhardt considers broader system impact including memory usage and error handling. Both agree the practical risk is low given existing hosting platform protections against extremely large attribute files.

Technical considerations mentioned include:
- Current implementation would require "many millions or even billions" of attributes to trigger OOM
- Hosting platforms likely already have size limits that would block such attacks
- Compute resource exhaustion is considered less critical since legitimate operations can also be resource-intensive

The email leaves open whether to proceed with the iterative approach or consider adding explicit limits, inviting further discussion about the preferred security model for handling malicious attribute expansions.
