Thread identity: Bug report about submodule checkout failure in SHA256 repositories when using --depth=1, reported by Martin Wilck.

Core problem: When checking out a SHA1 submodule from within a SHA256 repository using shallow clones (`--depth 1`), the operation fails with "remote ref not found" even though the same command without `--depth 1` succeeds. The issue occurs specifically when the submodule's remote HEAD is not an ancestor of the desired branch (e.g. "next"), indicating the shallow fetch logic isn't properly handling submodule branch configuration in mixed hash-algorithm scenarios.

Current status: Unresolved bug with a known workaround (manual fetching of the specific branch), but no fix yet. The reporter has demonstrated the issue doesn't occur in pure SHA1 repositories.

Key technical details:
- Affects `git submodule update --depth 1` and `git clone --recurse-submodules --depth 1`
- Reproduction case shown using multipath-tools repository from openSUSE
- Tested with Git development version 2.52.0.rc1 (specific commit given)
- System environment: Linux with OpenSSL 3.1.4
- Failure mode: Shallow fetch doesn't respect submodule branch config when dealing with SHA1 submodule in SHA256 superproject
- Workaround exists but isn't scriptable

Open questions:
- Why does the shallow fetch logic behave differently for SHA1 submodules in SHA256 repos?
- How to make the branch configuration properly propagate to the shallow fetch operation?
- Is this a general issue with mixed hash-algorithm repositories or specific to this submodule configuration?
