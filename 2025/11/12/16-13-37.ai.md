This is a bugfix for the new `git last-modified` command, addressing an inconsistency in its output compared to `git log --max-count=1` when files are specified via grep output versus direct path. The patch was previously framed as an optimization but is now been revealed to also correct incorrect results - for example, showing different commit hashes for the same file depending on whether it was specified directly (`pkt-line.h`) or matched via grep output.

Junio Hamano initially planned to exclude this from v2.52 since it missed the pre-rc1 merge window, but Toon Claes makes the case that this should be treated as a bugfix (not just an optimization) given it fixes demonstrably wrong behavior. The inconsistency occurs in the path-following algorithm that tracks file modifications through commit history. Claes notes this is particularly important since v2.52 will be the first release to include the `last-modified` subcommand at all.

The thread reveals some communication gaps - Junio wasn't initially aware of the correctness aspect, as the v4 cover letter focused on performance and didn't clearly highlight the bugfix nature. The test case in the original patch showed changed output order rather than demonstrating the incorrect hash issue. This follow-up provides concrete examples of the inconsistent behavior being fixed.
