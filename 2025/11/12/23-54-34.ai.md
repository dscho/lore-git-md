Bugfix and hardening patch for the hash algorithm transition, implementing the previously discussed validation to prevent mixed-hash submodule additions.

This patch from brian m. carlson implements the proposed hardening against mixed hash-algorithm repositories by modifying `git add` and `git submodule add` to reject submodules that use a different hash algorithm than their parent repository. The change centers on `object-file.c` where it adds validation in `index_path()` to compare the submodule's hash algorithm with the parent repository's algorithm.

The patch includes comprehensive tests in both `t/t3700-add.sh` and `t/t7400-submodule-basic.sh` that verify the rejection behavior works in both directions (SHA-1 submodule in SHA-256 repo and vice versa). The tests also confirm no submodule entry gets added to the index in these cases. The implementation follows the thread's established consensus that mixed-hash repositories are invalid by design, though it notes this can't be detected by `git fsck` due to potential false positives.

Key technical details:
- Modifies `index_path()` in `object-file.c` to compare `oid->algo` with the parent repo's `hash_algo`
- Returns an explicit error message when hash algorithms mismatch
- Tests cover both `git add` and `git submodule add` paths
- Test cases verify both SHA1-in-SHA256 and SHA256-in-SHA1 scenarios
- Maintains the thread's position that this is a deliberate design constraint
- Follows up on Junio's confirmation that mixed-hash repos are unsupported

The patch appears well-constructed with thorough test coverage and a clear implementation that matches the discussed design constraints. It directly addresses the original thread's concerns while avoiding the fsck false-positive problem noted in the commit message.
