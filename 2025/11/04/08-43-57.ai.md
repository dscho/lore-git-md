This is a refactoring patch that adds infrastructure for checking reftable optimization needs as part of the larger maintenance task checking series. The patch introduces `reftable_stack_compaction_required()`, a new function that allows querying whether the reftable backend needs compaction without actually performing it.

The function takes a `use_heuristics` parameter to distinguish between two modes: when false, it simply checks if all tables can be compacted to a single table; when true, it uses geometric progression heuristics to determine if compaction would be beneficial. The implementation handles edge cases like stacks with fewer than 2 tables (which never need compaction) and propagates errors from the underlying segment analysis.

The patch includes unit test updates that verify the new function's behavior matches the existing auto-compaction logic. Tests confirm the function correctly reports when compaction is required based on table count and segment analysis, maintaining consistency with the stack's actual compaction behavior.

This builds on the thread's earlier discussion about separating error checking from segment evaluation, with the implementation preserving that separation while providing a clean API for maintenance checks. The function will be used by the upcoming 'is-needed' subcommand to determine when ref optimization maintenance tasks should run.
