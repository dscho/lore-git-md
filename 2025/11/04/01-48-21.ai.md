This is a technical discussion about naming and FFI design in the SHA-1/SHA-256 interoperability patch series, specifically addressing patch 6/14 which introduces hash algorithm lookup functions.

The email focuses on resolving naming concerns raised by Junio Hamano about the `hash_algo_ptr_by_offset()` function in the C/Rust FFI layer. Brian Carlson defends the current naming choice, explaining that alternatives like "by_id" or "by_index" have their own issues, and notes the pointer return type (`hash_algo_ptr`) already distinguishes it from the numeric return of `hash_algo_by_name()`. 

Key technical points include:
- The function returns a pointer to a `git_hash_algo` struct rather than exposing the full struct definition to Rust
- This is a temporary measure until better Rust abstractions can be implemented
- Performance considerations for compile-time evaluation of hash sizes in Rust (`raw_len` and `hex_len` functions)

The discussion reveals ongoing design tensions around:
- Naming clarity at the FFI boundary
- Tradeoffs between temporary solutions and ideal abstractions
- Compiler optimization opportunities in Rust vs C

This follows earlier resolved debates about type safety and memory allocation at the FFI layer, showing the series is now focusing on finer-grained API design questions. The exchange demonstrates the careful attention being paid to making the Rust/C interface both correct and ergonomic, even for transitional code.
