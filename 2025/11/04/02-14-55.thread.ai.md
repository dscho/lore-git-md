RFC proposal for a new binary file reporting mechanism in `git diff` has evolved significantly after maintainer feedback. The original proposal suggested extending raw diff` format with binary status prefixes ('bb', 'bt', etc.), but Junio C Hamano has raised fundamental design objections and proposed an alternative direction.

Current status: The proposal is effectively on hold pending a more comprehensive design that can handle multiple file attributes (binary status, incomplete lines, line endings) in an extensible way. Junio suggests a new `--raw-extended` option using letter codes like "bt,ic,cl" for binary/text, incomplete lines, and CRLF/LF status respectively, with N-letter tuples for N-way diffs.

Key technical details from both proposals:
- Original approach modified `struct diff_options` to add binary reporting
- New suggestion would require designing an extensible attribute reporting system
- Both aim to provide machine-parseable output while preserving human-readable format
- Comprehensive test coverage exists for binary-only case in t4015-diff-binary.sh

Open questions and design challenges:
1. How to design an extensible format that can:
   - Report multiple file attributes
   - Scale to N-way diffs
   - Remain backward compatible
2. Whether to pursue:
   - A binary-only solution (original approach)
   - A general attribute reporting mechanism (Junio's suggestion)
   - Alternative output channels (e.g., separate machine-readable output)
3. Implementation complexity tradeoffs between targeted vs. general solutions

Participant positions:
- Junio C Hamano strongly opposes modifying raw diff format for binary-only case
  * Argues for more comprehensive solution addressing multiple attributes
  * Concerned about format proliferation and N-way diff scalability
- Original author now needs to either:
  * Design a more general attribute reporting system
  * Justify why binary-only solution is sufficient
  * Consider alternative approaches entirely

The thread has shifted from implementation details to fundamental design questions. Next steps require addressing architectural concerns about format extensibility and attribute reporting before any technical implementation can proceed. No other contributors have weighed in yet. The author faces a choice between redesigning the solution to meet the maintainer's extensibility requirements or abandoning the current approach.
