Thread identity: Bug report about `git grep -l` output formatting regression with filenames containing dashes.

Core problem: When using `git grep -l` (list filenames only mode) on files containing dashes, the output incorrectly displays the first dash as a colon and applies color highlighting to the text before the colon. This is a regression introduced between Git 2.49.1 and 2.51.1. New information suggests the issue may involve interaction with external pagers like Delta.

Current status: Reported as a regression, not yet fixed. Works correctly in Git 2.47.3 and 2.49.1, broken in 2.51.1. Additional reproduction case found using Delta pager.

Key technical details:
- Affects `git grep -l` output formatting specifically
- Only occurs with filenames containing dashes
- First dash gets replaced with colon in output
- Text before colon appears in pink color (unintended highlighting)
- Reproducible across different shells (zsh, bash) and terminals
- Minimal reproduction: `echo foo > test-one; git add test-one; git grep -l foo` shows `test:one`
- New observation: Also occurs with Delta pager but not with `--no-pager`
- Coloring behavior unclear when using `--color=never` with pager

System context:
- Reported on Fedora 42
- Git 2.51.1 built with GCC 15.2 and glibc 2.41
- Delta pager version not specified

Open questions:
- What specific change between 2.49.1 and 2.51.1 introduced this behavior?
- Is this related to color output handling or filename parsing in grep machinery?
- Are there other filename patterns that might be affected?
- Does the pager interaction indicate an issue in Git's pager handling or Delta's parsing?
- Why does `--no-pager` avoid the issue while `--color=never` behavior is unclear?
