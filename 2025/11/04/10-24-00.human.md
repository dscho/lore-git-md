This is a naming discussion in the ongoing SHA-1/SHA-256 interoperability work, specifically about the Rust/C FFI boundary in patch 6/14 of the series.

Junio C Hamano follows up on an earlier discussion about the naming of hash algorithm lookup functions, proposing clearer alternatives to address the current ambiguity. The key issue is that `hash_algo_ptr_by_offset()` and `hash_algo_by_name()` both use "hash_algo" terminology but return fundamentally different things (a pointer to a struct vs. a numeric ID).

Hamano suggests two concrete improvements:
1. Renaming `hash_algo_ptr_by_offset` to `hash_algo_ptr_by_algo_number` to better reflect that it returns a pointer to a struct
2. Renaming `hash_algo_by_name` to `hash_algo_num_by_name` to clarify it returns a numeric ID

This continues the thread's pattern of careful attention to FFI boundary details, now focusing on making the API self-documenting through precise naming. The suggestions aim to eliminate potential confusion between the numeric algorithm identifiers and the full algorithm structs while maintaining the technical distinction that was previously agreed upon (using `uint32_t` rather than Rust enums at the FFI boundary).

The discussion remains constructive, with Hamano offering specific alternatives rather than just critiquing the current names. This suggests the technical approach is sound but could benefit from clearer naming to help future maintainers.
