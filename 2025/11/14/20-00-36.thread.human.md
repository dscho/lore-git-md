The thread began by addressing a resolved issue with Ubuntu's Rust-based `sudo` implementation, which was fixed in maint-2.51. The discussion then shifted to macOS CI reliability, specifically focusing on flaky Perforce tests (t98xx). Junio Hamano initially proposed removing these tests entirely due to their instability and maintenance costs, but Koji Nakamaru identified the root cause as an architecture mismatch - x86_64 Perforce binaries running on arm64 CI runners via Rosetta translation. Nakamaru provided a working patch to switch to native arm64 binaries (helix-core-server.tgz from bin.macosx12arm64) and update to Perforce r24.2.

In the latest email, Junio acknowledges Nakamaru's diagnosis and shows openness to the solution, but raises two technical questions about the implementation: whether using x86_64-based macos-14-large runners would be preferable to switching binaries, and why r24.2 was chosen when both older (r23.2) and newer (r25.1) versions also offer arm64 binaries. This moves the discussion forward from whether to fix the tests to how best to implement the fix, with considerations about version compatibility across platforms. The same P4WHENCE URL serves both macOS and Linux, so the version choice has broader implications. While Nakamaru's solution appears technically sound, Junio's questions suggest the final approach may still evolve based on these implementation details. The thread remains active with these open technical questions, though the general direction now favors keeping the tests with an architecture-compatible fix rather than removing them.
