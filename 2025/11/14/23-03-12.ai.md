This is a follow-up in the submodule gitdir path encoding series, focusing on migration challenges for existing deployments. Josh Steadmon from Google provides real-world feedback about their internal use of an early version of this encoding scheme, noting two key operational concerns with the current implementation.

The email reveals that Google has been using a similar submodule encoding approach for years without the `extensions.submoduleEncoding` config, creating a migration challenge. While the current series works with these pre-encoded submodules regardless of the config value, there's no automated path to migrate existing repos to the new extension-based system. Josh highlights the special nature of repository format extensions that prevents them from being set via distributed configs.

Two specific pain points emerge: 1) The inability to automatically enable `extensions.submoduleEncoding` for existing repositories without manual user intervention, and 2) The lack of a way to default-enable the encoding for new repositories through distributed configuration (similar to `init.defaultObjectFormat`). Josh suggests a possible downstream workaround of force-enabling the extension but seeks better solutions from the list.

This feedback introduces important deployment considerations to the previously technical-focused discussion, particularly around the transition story for early adopters. The issues raised don't challenge the core architecture but highlight real-world adoption friction that may need addressing before wider rollout. The thread now expands to include migration strategy alongside the settled technical implementation.
