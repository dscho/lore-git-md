This is a follow-up in the ongoing discussion about `git check-ignore` exit code behavior with negative patterns. David Goldstein provides additional context about how he discovered the bug while investigating differences between `grep` and `ripgrep` behavior regarding ignored files. His debugging path involved using `git check-ignore -v` to understand why some files appeared both ignored and not ignored, which led him to uncover the exit code discrepancy.

The email reinforces that this was a debugging discovery rather than a production issue, aligning with Junio Hamano's earlier characterization of `check-ignore` as primarily a debugging tool. Goldstein's experience shows the bug's practical impact was minimal - it didn't actually explain his original ripgrep investigation, which turned out to be about tracked files matching ignore patterns rather than an ignore mechanism problem.

This adds weight to the emerging maintainer perspective that while technically incorrect exit code violates documentation, the command's debugging nature makes this a low-priority issue. The thread appears to be moving toward either accepting the current behavior with documentation clarification or leaving it unchanged, given the lack of real-world impact and the command's non-critical role in workflows.
