This is a follow-up in the ongoing discussion about `git check-ignore` exit code behavior with negative patterns. David Goldstein provides additional context about how he discovered the issue while debugging differences between `grep` and `ripgrep` behavior. 

The email doesn't introduce new technical information about the bug itself, but rather explains the real-world scenario that led to its discovery. Goldstein was investigating why `ripgrep` showed different results with and without `--no-ignore`, and while using `git check-ignore -v` to understand ignore patterns, he noticed the exit code discrepancy. He ultimately determined the root cause was unrelated to Git's behavior - tracked files matching `.gitignore` patterns were being treated differently by `ripgrep` since it doesn't know Git's tracking status.

This background reinforces the earlier maintainer perspective from Junio Hamano that the exit code behavior, while technically incorrect, likely has minimal practical impact since `check-ignore` is primarily a debugging tool. The email suggests the original bug report emerged from a somewhat tangential investigation rather than a critical workflow failure. The discussion appears to be winding down with a likely outcome of documenting the current behavior rather than changing it.
