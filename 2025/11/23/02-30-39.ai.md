This is a technical discussion email in the ongoing `git-history` feature series, focusing on branch handling and commit metadata preservation during history editing operations.

Elijah Newren responds to Phillip Wood's questions about the single-branch limitation in the current `git-history` implementation. He argues that properly handling multiple branches (using ancestry-path revision walking) would actually be simpler and more robust than the current approach, which risks incorrect behavior when commits belong to multiple branches. He references his earlier implementation sketch showing how to use `git replay` machinery for this purpose.

The discussion confirms that the current split implementation maintains an invariant where the sum of split commits equals the original commit's changes, even when users make small edits during splitting. This addresses Elijah's earlier concern about potential incompatibility between test requirements and user capabilities.

Significant attention is given to commit metadata handling during rewording and splitting. While rewording likely should preserve most extended headers, Phillip questions whether preserving the encoding header makes sense since the message gets re-encoded. For splits, they agree neither commit should automatically inherit the original message - both should prompt the user input seeded with the original text. Elijah emphasizes the importance of explicitly documenting these behaviors rather than letting them emerge as implementation side-effects.

The email highlights two key unresolved technical questions: whether to use the more robust multi-branch handling from the start (Elijah's position) versus a phased single-branch approach (Phillip's pragmatic view), and how to properly handle various commit metadata fields during editing operations. These intersect with the broader tension between Junio Hamano's push for early experimental merging and Phillip's expectation that more substantive changes are still needed.
