This is a design discussion about the `GIT_REF_URI` environment variable proposal for reference backend selection, part of the ongoing ref storage migration work.

Junio Hamano raises several concerns about the current implementation approach. He questions the fundamental assumption that all reference backends should support arbitrary storage locations via a single URI string, noting that future backends (like cloud-based ones) might not fit this model. For the existing files/reftable backends, he suggests backend-specific solutions might be simpler since there are only two implementations currently.

The core issue emerges around migration use cases - Hamano points out that a single URI variable is insufficient for migration scenarios which inherently require specifying both source and destination locations. He also critiques the generic `GIT_REF_URI` name as misleading if the variable's behavior is specifically to duplicate writes to an additional backend (as implied by the non-blocking migration use case), suggesting a more precise name would be needed.

This email represents significant architectural pushback on the current design, particularly around:
1. The one-size-fits-all URI approach's applicability to future backends
2. The sufficiency of a single URI for migration workflows
3. The semantic clarity of the environment variable name and behavior

The discussion continues the thread's exploration of how to best enable non-blocking migrations while maintaining flexibility for future backend implementations. Hamano's comments suggest the current proposal may need reworking to properly address these concerns before proceeding.
