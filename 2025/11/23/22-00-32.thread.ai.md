Thread identity: Discussion about deprecation strategy for `git whatchanged`, a legacy command that shows commit history with diff output.

Core problem: Recent change (since Git 2.51.0) introduced a `--i-still-use-this` opt-in flag requirement for `git whatchanged`, making it harder to use. Daniel Hammer argues this creates unnecessary friction for users who rely on this command in their daily workflow, while Kristoffer Haugsbakk defends it as an intentional breaking change to accelerate migration.

Current status: The command has been documented as deprecated since 2013, with the stricter opt-in requirement added in Git 2.51.0. No version changes mentioned in this exchange. Kristoffer indicates the current approach won't be reversed.

Key technical details:
- `git whatchanged` provides similar functionality to `git log -p --raw --no-merges` with certain default flags
- Current implementation requires `--i-still-use-this` flag to bypass deprecation warning
- Documentation has noted its legacy status since 2013
- Suggested workaround: create global alias to maintain familiar command

Open questions:
- Whether any additional migration guidance should be provided beyond what exists
- If the severity of user impact warrants reconsideration (though Kristoffer suggests this is settled)
- Whether similar deprecation strategies will be applied to other legacy commands

Participant positions:
- Daniel Hammer: Strongly objects to current approach, calls it a "DevEx regression", prefers documentation-only deprecation
- Kristoffer Haugsbakk: Defends current strategy as intentional, provides historical context and migration paths, states this won't be reversed
