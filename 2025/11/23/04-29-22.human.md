This is a design discussion about the proposed `GIT_REF_URI` environment variable for reference backend selection, part of the ongoing ref storage migration work.

Junio Hamano raises several concerns about the current proposal. He questions whether all reference backends should be required to support arbitrary storage locations, noting that some future backends might not even have a concept of a local storage path (e.g., cloud-based backends). For the existing files and reftable backends, he suggests backend-specific solutions might be simpler.

The core issue emerges around migration use cases - Hamano points out that a single URI variable may be too ambiguous for migration scenarios where you need to specify source and destination locations. He suggests the current name `GIT_REF_URI` is too generic if the intended behavior is specifically to duplicate writes to a secondary location during migration.

The email continues the architectural discussion from earlier in the thread about how best to represent reference storage locations, with Hamano advocating for clearer semantics around the variable's purpose. This represents important design feedback that will likely shape the final implementation before the feature is merged.
