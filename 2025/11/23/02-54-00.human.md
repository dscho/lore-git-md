This is a discussion about the `git-history` command series, focusing on the handling of commits that appear in multiple branches.

Elijah Newren clarifies that his earlier feedback about multi-branch handling wasn't just a feature request, but rather a bug concern in the current implementation. The current `git-history` implementation doesn't properly handle commits that exist in multiple branches' histories, which could lead to unexpected divergence when rewording or splitting such commits.

He outlines three potential solutions: (1) document the limitation and warn users, (2) detect and error out on multi-branch cases unless explicitly overridden, or (3) rewrite all affected branches. Elijah strongly favors option 3, arguing it's actually simpler to implement than the current single-branch approach, more user-friendly, and would avoid potential future compatibility issues like those seen with `git-switch`/`git-restore`.

This email represents a key moment in the thread where Elijah makes a technical case that what was previously seen as a feature request is actually a bug fix that would simplify rather than complicate the code. The discussion highlights the tension between Junio Hamano's preference for minimal initial functionality and the maintainers' concerns about shipping with known problematic behavior.
