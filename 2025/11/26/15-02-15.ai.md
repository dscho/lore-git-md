This is a follow-up in the ongoing discussion about `git clone` config parsing regression with whitespace in `-c`/`--config` arguments. Jeff King (peff) responds to Junio Hamano's proposed minimal fix, pointing out that the historical whitespace-trimming behavior affected more code paths than just `git clone` - it also impacted `GIT_CONFIG_PARAMETERS` environment variable parsing. He demonstrates that older Git versions would trim whitespace on both sides of the equals sign in config parameters, while current versions reject such input.

The email highlights two key technical details: first, that Junio's proposed fix only addresses leading whitespace trimming in `clone.c` while the original behavior also trimmed trailing whitespace before the equals sign; second, that this behavior was already silently broken for `git -c` since 2021's config format changes without anyone noticing. Peff remains skeptical about preserving what he views as an accidental feature, especially since the impact appears limited to edge cases and some third-party tools.

This moves the discussion forward by clarifying the scope of the original behavior and questioning whether any fix is truly needed. The technical specifics about which whitespace was trimmed where (both sides of equals in `GIT_CONFIG_PARAMETERS` vs just leading in `clone -c`) will be important for any future fix attempts. The email also surfaces the question of whether third-party tools should adapt to Git's stricter parsing rather than Git maintaining backward compatibility for what was effectively a bug.
