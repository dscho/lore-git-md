This thread discusses Vaidas Pilkauskas's series adding HTTP 429 (rate limiting) retry support to Git's HTTP client. The v2 implementation introduces configurable retry behavior with RFC-compliant handling of Retry-After headers, new configuration options, and extensive test coverage. Taylor Blau had previously reviewed v2, raising questions about defaults and implementation details while approving the trace2 instrumentation.

Jeff King (Peff) has now weighed in with deeper architectural concerns. He questions whether the current retry delay implementation in run_active_slot() is the right layer, suggesting http_request_reauth() or run_one_slot() might be more appropriate. Peff proposes leveraging curl's built-in CURLINFO_RETRY_AFTER where available, though this would require conditional compilation. He also identifies test portability issues with date handling and recommends excluding deprecated HTTP code paths (http-push.c and http-walker.c) from the changes.

While the series appears functionally complete from earlier reviews, Peff's feedback indicates significant restructuring may be needed. His suggestions touch on core architectural decisions that could affect how retries integrate with Git's existing HTTP stack. The author will need to address these concerns, particularly around the retry mechanism's placement and the curl version compatibility implications, before the series can progress further. Taylor Blau and Peff's combined feedback now sets clear direction for a potential v3 iteration.
