This thread introduces HTTP 429 (rate limiting) retry support to Git's HTTP client, addressing a common pain point when interacting with API-limited servers. The series adds three configurable options: http.maxRetries (defaulting to 0 for opt-in behavior), http.retryAfter (setting a fallback delay), and http.maxRetryTime (capping total delay at 300s). The implementation carefully handles both standard Retry-After header formats while maintaining backward compatibility.

The first patch established the core retry logic with comprehensive test coverage through a new t5584 test script. The second patch, just submitted, fixes a pre-existing memory leak in HTTP error message handling that became more apparent during retry testing. This fix properly manages string buffers during error message display without changing user-visible behavior. A third patch is expected to add trace2 instrumentation for monitoring retry operations.

The author is still considering whether to expand the retry behavior to include 50x status codes, as was attempted in a previous iteration. The implementation shows attention to both functionality and debuggability, with tests covering various scenarios including invalid headers and environment overrides. Documentation updates accompany the changes to explain the new configuration options.
