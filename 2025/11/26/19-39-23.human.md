This is a response in the ongoing discussion about adding revert capability to `git replay`, specifically addressing design concerns about the `--revert` flag's interaction with other options.

Siddharth Asthana acknowledges Phillip Wood's critique that the current `--revert` implementation creates unrealistic scenarios when combined with `--onto`. The example in the documentation (reverting commits from one branch onto another) doesn't match practical use cases. The thread has reached consensus that revert should be a distinct operation mode rather than a modifier flag.

The response identifies several concrete issues to fix in the next version:
1. The current test cases create empty revert commits because they don't properly model commit ancestry
2. A bug in revert message generation where full commit messages are passed instead of just subject lines
3. Need to use `test_commit_message()` for proper message validation

Siddharth confirms the plan to restructure the feature as a standalone operation mode that reverts commits in their original branch context, similar to how `--advance` works but with reversed changes. This addresses the core architectural concern raised by multiple reviewers. The response shows good engagement with feedback while identifying specific technical improvements needed before resubmitting.
