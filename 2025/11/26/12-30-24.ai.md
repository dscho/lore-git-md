This is a feature patch series introducing HTTP 429 (rate limiting) retry support to Git's HTTP client. The cover letter describes a three-part implementation that would make Git automatically handle rate-limited responses from hosting services rather than failing immediately.

The series adds three new http.* config options to control retry behavior: maxRetries (default 0 for opt-in), retryAfter (fallback delay when no Retry-After header), and maxRetryTime (300s ceiling on delays). The implementation handles both delay-seconds and HTTP-date Retry-After formats per RFC standards. Patch 1 contains the core retry logic with extensive test coverage, Patch 2 fixes a pre-existing memory leak in error message handling that becomes more visible with retries, and Patch 3 adds trace2 instrumentation for monitoring retry operations.

The author notes this is a previous attempt at retry support (which included 50x status codes) and asks whether those should be included here too. The implementation appears thorough, including documentation updates and a new 429-line test script. The opt-in design preserves backward compatibility while solving a real pain point for users hitting rate limits. The memory leak fix and trace2 integration suggest good attention to detail in both functionality and debuggability.
