Bugfix discussion regarding `git clone -c` whitespace handling regression.

Jeff King weighs in on the ongoing discussion about whether to restore whitespace-trimming behavior for `git clone -c` arguments. He agrees with Junio Hamano's assessment that the original behavior was an accidental quirk rather than a deliberate feature, though acknowledges it became widely used over time.

Key points:
- The whitespace-trimming was specific to `git clone -c` and inconsistent with other Git commands
- The original report appears to stem from buggy calling code that happened to work due to this quirk
- While restoring the behavior is possible, Jeff questions whether it's worth the effort given the limited legitimate use cases
- He notes similar whitespace-handling quirks might exist elsewhere in Git's option parsing

Jeff's position is pragmatic - he'd be fine leaving the regression as-is since it fixes an inconsistent behavior, but wouldn't object if someone wants to implement a fix. The email highlights the tension between maintaining backward compatibility and cleaning up historical quirks in Git's command-line interface.
