This is the first patch in a 3-part series implementing HTTP 429 (rate limiting) retry support for Git's HTTP client. The patch introduces core retry logic with three new config options: `http.maxRetries` (default 0, opt-in), `http.retryAfter` (fallback delay when no Retry-After header), and `http.maxRetryTime` (300s delay ceiling). 

The implementation handles RFC-compliant Retry-After headers in both delay-seconds (integer) and HTTP-date (RFC 2822) formats, with immediate retry for past dates. The design is fail-fast - if any delay exceeds maxRetryTime, Git fails immediately with a clear error rather than capping the delay. Configuration can be overridden via environment variables (GIT_HTTP_* equivalents).

The patch touches multiple HTTP-related files (http.c, http.h, remote-curl.c etc.) to add the new functionality and error handling. It includes extensive test coverage in new test script t5584-http-429-retry.sh, verifying basic retry behavior, header formats, configuration combinations, maxRetryTime limits, and edge cases. The tests use a mock HTTP server to simulate 429 responses with various Retry-After headers.

Key technical details for future reference:
- New HTTP_RATE_LIMITED (7) status code added to http.h
- struct slot_results gains retry_after field
- Configuration parsing in http_options() for the three settings
- Retry logic implemented in http_request_reauth()
- sleep_for_retry() helper handles the actual delay
- Tests cover all major scenarios including invalid headers, environment overrides, and timing validations

The implementation appears thorough and well-tested, addressing a practical pain point for users hitting rate limits while maintaining backward compatibility through opt-in configuration. The extensive test coverage (429 lines of test script) suggests careful consideration of edge cases.
