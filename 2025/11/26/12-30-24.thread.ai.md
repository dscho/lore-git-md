HTTP 429 (rate limiting) retry support for Git's HTTP client. Series v3 from Vaidas Pilkauskas implements RFC-compliant handling of Retry-After headers with both delay-seconds and HTTP-date formats, using curl's native CURLINFO_RETRY_AFTER parsing (curl >= 7.66.0) with fallback to manual header parsing. The implementation introduces three config options: http.maxRetries (default 0), http.retryAfter (default 0 changed from -1 in v2), and http.maxRetryTime (300s delay ceiling). The series has evolved through multiple iterations addressing feedback from Jeff King and Taylor Blau.

Core changes in the final implementation:
- Simplified retry mechanism using blocking sleep() instead of non-blocking delays
- Full curl-native Retry-After parsing support with fallback to manual parsing
- Default http.retryAfter changed to 0 for immediate retries when no header present
- Comprehensive test coverage including edge cases for invalid Retry-After formats
- Added trace2 instrumentation for retry monitoring
- Proper handling of Retry-After: 0 per RFC 9110
- Environment variable overrides for all three config options
- Test suite uses test-tool date exclusively for portability

Technical implementation details:
- struct slot_results retains retry_after field
- HTTP_RATE_LIMITED (7) status code unchanged
- Configuration parsing in http_options()
- Retry logic consolidated in http_request_recoverable()
- New helper show_http_message_fatal() in remote-curl.c consolidates error handling
- Fails fast when delays exceed maxRetryTime rather than capping

Files touched: http.c, http.h, remote-curl.c, t/t5584-http-429-retry.sh, t/lib-httpd/http-429.sh. The series has addressed all major feedback points from v2, with Jeff King's technical direction fully incorporated around using curl's native capabilities and improving test portability. Taylor Blau's trace2 instrumentation suggestion was implemented. The blocking sleep() simplification represents a design shift from v2's non-blocking approach, trading some theoretical efficiency for implementation clarity.

Review consensus shows the implementation is technically complete with no outstanding objections. The series provides a mature solution for handling HTTP 429 responses, particularly useful for services like GitHub and GitLab that implement API rate limits.
