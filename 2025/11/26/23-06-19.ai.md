This is a design discussion about naming the operation modes in `git replay`, specifically debating whether to use technical terms (`--onto`, `--advance`) or operation names (`--rebase`, `--cherry-pick`). Elijah Newren responds to Junio Hamano's suggestion that the current `--onto` and `--advance` flags are misnamed and should instead reflect their corresponding sequencer operations.

Elijah argues that while the three replay modes do parallel the three main sequencer operations (rebase, cherry-pick, revert), the proposed `--rebase` and `--cherry-pick` names could be confusing in the context of `git replay`'s explicit range specification. He provides concrete examples showing how the current `--onto` and `--advance` syntax more clearly indicates what is being replayed onto what, while the proposed names might misleadingly suggest the base argument (`main`) is being operated on rather than serving as the target.

The discussion touches on the tension between catering to Git experts (who might appreciate the parallel to sequencer operations) versus making the command more self-descriptive for new users. Elijah suggests the current names better serve the latter goal, as `git replay` intentionally removes HEAD assumptions present in traditional rebase/cherry-pick, requiring more explicit specification of commit ranges and update targets.

This exchange represents a key interface design decision point for the `git replay` command while it remains experimental. The thread has previously established that revert capability should be a distinct mode (not a flag), and this discussion focuses on whether to align the other two modes' names with their sequencer counterparts or maintain more technically precise but potentially less intuitive names. The outcome will affect both user experience and the conceptual model presented in documentation.
