Memory leak fix in HTTP error handling, part of the HTTP 429 retry series.

This patch addresses a pre-existing memory leak in `show_http_message()` that became more apparent with the new HTTP 429 retry support. The function was modifying the caller's strbuf in place via `strbuf_reencode()` before displaying error messages, causing memory leaks when called before `die()`. The issue affected all HTTP error paths but was particularly visible in the new retry tests where error paths are exercised more frequently.

The fix creates a local strbuf copy for message processing, ensuring proper cleanup before function return. This maintains the leak while keeping the same functionality - the change is in memory management only, not behavior. The patch includes the expected strbuf initialization, copying, and cleanup pattern.

Key technical details: the leak occurred in `remote-curl.c`'s error message display path, specifically around charset re-encoding. The fix adds 10 lines while removing 4, introducing a local `msgbuf` to isolate the re-encoding operation. All existing error cases (HTTP_MISSING_TARGET, HTTP_NOAUTH, etc.) benefit from this fix, not just the new HTTP_RATE_LIMITED case.

This is the second patch in a 3-part series, following the core retry logic implementation and preceding planned trace2 instrumentation. The change is straightforward with clear test coverage via the existing t5584 tests that detected the leak under LeakSanitizer. No new tests are added as the existing retry tests already verify the fixed code path.
