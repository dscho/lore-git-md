Performance optimization for the patience diff algorithm. This is a follow-up to Yee Cheng Chin's patch that reduces unnecessary binary searches in `find_longest_common_sequence()` by checking if new lines can simply be appended to the current sequence rather than searching for their position. 

Junio C Hamano reviews the patch and approves it as a "stupid and obvious" optimization that is actually quite clever. The change adds a boundary condition check before calling `binary_search()` to see if the encountered unique line appears after the entire current longest subsequence. In such cases (which are common when diffing similar files), the line can be directly appended without searching. The patch maintains the fallback to binary search when needed, preserving correctness while improving performance.

The optimization builds on profiling data showing binary searches accounted for 50-60% of runtime in patience diff operations. Benchmarks across multiple repositories had shown 8-14% speedups in `git log --patience` with this change, as the binary search path is rarely needed (only 0.01-1.46% of cases). The implementation adds just 4 lines of boundary checking logic while maintaining the existing behavior when required.

Key technical details for future reference: The change modifies `xdiff/xpatience.c`'s `find_longest_common_sequence()` function, specifically the loop that processes entries from the hashmap. The new condition checks `longest == 0` (empty sequence) or `entry->line2 > sequence[longest - 1]->line2` (line appears after current sequence) to avoid binary search. The variable `i` gets set to either `longest - 1` (for append case) or the result of `binary_search()` (fallback case).
