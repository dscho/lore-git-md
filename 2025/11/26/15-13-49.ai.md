This is a follow-up in the thread about `git config` path handling and the `:(optional)` prefix behavior. Jeff King (Peff) responds to Junio Hamano's defense of the current design where optionality is per-setting rather than per-variable.

Key technical points:
- Junio's example shows system-wide configs can define fallback paths with optional user overrides via `:(optional)` prefixes
- Peff notes this design prevents the inverse workflow where users might want to completely ignore system paths and only use optional local files
- The discussion reveals a gap in Git's config system - there's no clean way to "unset" a single-valued variable like there is for list-like variables
- Both agree the current implementation enables useful workflows but may be limiting others

The exchange highlights design tradeoffs in the current approach:
- Per-setting optionality enables system-wide config patterns but constrains other use cases
- The lack of variable unsetting complicates certain configuration patterns
- Neither participant has concrete use cases needing the alternative approaches

This moves the thread from implementation details to higher-level design considerations about config system capabilities, though without immediate action items. The core segfault issue appears resolved with the current interface being maintained.
