This is a critical review of the `git replay --revert` feature implementation, focusing on fundamental design questions and test quality issues. Phillip Wood raises several substantive concerns about the current approach:

1. **Use case confusion**: Questions the practical utility of updating a feature branch with reverted commits rebased onto main, suggesting the current behavior may not solve real-world problems. The test case demonstrates this by producing empty revert commits due to unrealistic test setup.

2. **Design alternative**: Proposes making `--revert` a distinct mode rather than combining with `--onto`, potentially defaulting to reverse commit order to minimize conflicts. This suggests the current implementation may have misaligned the revert operation with its natural use cases.

3. **Implementation bugs**: Points out a concrete bug in revert message formatting that escaped detection because tests only checked for "Revert" prefix rather than full message content. The empty commits in test output also reveal problematic test construction.

4. **Test quality critique**: Highlights inadequate test verification (missing `test_commit_message()` checks) and unrealistic test scenarios that don't reflect real revert operations. The empty commits indicate the test doesn't properly model file changes during reverts.

The review shifts the discussion from implementation details to fundamental design validity, suggesting the feature may need rethinking rather than just fixing current test failures. It also provides specific guidance on improving test rigor through better message verification and more realistic scenarios. This comes as the feature already faces known test failures and coordination challenges with parallel sequencer refactoring work.
