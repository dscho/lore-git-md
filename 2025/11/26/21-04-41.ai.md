This is a design discussion in the ongoing `git replay` feature series, specifically about the revert functionality. Junio Hamano responds to Siddharth Asthana's points about two distinct revert workflows in GitLab's context.

The email highlights two valid but distinct use cases for reverts: bulk undoing of merge requests (where efficiency matters) versus selective commit-by-commit reverts (where auditability is key). Junio notes that while the current `git replay` implementation handles ranges well, it doesn't optimally support selectively reverting non-contiguous commits from a merged branch - a workflow that would require multiple single-commit operations under the current design.

The discussion touches on interface limitations, pointing out that neither `git replay`'s current range-based arguments nor `git revert A..B` cleanly support the "revert specific commits from a merge" scenario. This suggests potential future direction for the tool's evolution beyond the current series' scope, though the immediate focus remains on the commit-by-commit revert mode being implemented.

The exchange reinforces the architectural decision to keep revert as a distinct operation mode in `git replay` while acknowledging there may be room for more sophisticated selection mechanisms in the future. This positions the current work as establishing the foundational revert capability that could later be extended for more complex use cases.
