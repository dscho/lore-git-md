This is a follow-up in the ongoing bug report about `git fetch --tags` behavior in bare repositories. David Bohman responds to Randall Becker's suggested `--force` workaround by clarifying the core issue: while the workaround addresses the immediate problem, the regression in behavior (introduced in Git 2.51.0) is that previously, rejected tags wouldn't prevent other new tags from being stored, whereas now the entire operation fails when any tag is rejected. 

Key technical details for future reference:
- The issue manifests in bare repositories when force-pushed tags exist upstream
- Output shows "[new tag]" for tags like v9.18.41/v9.20.15/v9.21.14 but they don't appear in `git tag` output
- Exit status is 1 (failure) when any tag is rejected (like 'stable' in this case)
- Behavior changed between Git 2.50.1 (worked) and 2.51.0 (broke)
- The `--force` flag works around the issue but doesn't explain why the regression occurred

The email confirms the problem isn't specific to the bind9 repository and maintains focus on the core issue: why tag rejection now causes complete operation failure in bare repos when it previously only affected the rejected tag. This keeps the thread focused on debugging the tag update logic rather than workarounds.
