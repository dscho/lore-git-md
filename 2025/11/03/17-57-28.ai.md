This is a bug report related to the recently merged `ps/ref-peeled-tags` series, which streamlined handling of annotated tag references in Git's ref backend storage. The series had dependencies on `jt/repo-structure` and `tb/incremental-midx-part-3.1` which had already landed, making it ready for merging to 'next'.

Junio C Hamano reports a regression where `git tag --list --sort=version:tag` no longer sorts version tags numerically (e.g., v2.10.0 now appears between v1.19.0 and v2.2.0 instead of after v2.9.0). The issue appears immediately after merging `ps/ref-peeled-tags`, as the command works correctly with the previous merge (9ab444ed). The problem affects the tag sorting functionality, which is separate from but may interact with the ref backend changes in the merged series.

Key technical details:
- The `ps/ref-peeled-tags` series modified ref-filter parsing to handle annotated tag objects more efficiently
- The regression appears in version sorting (`--sort=version:tag`) which depends on proper tag object parsing
- The issue is reproducible and clearly correlated with the merge of this series
- The problem affects the `git tag` command's output ordering

This appears to be an unintended side effect of the ref-filter optimizations, where the version sorting functionality is not properly preserving the numeric ordering semantics. The report provides clear reproduction steps and bisection information, making it straightforward to investigate the interaction between the ref backend changes and tag sorting behavior.
