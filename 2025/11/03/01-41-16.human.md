Bug report follow-up with reproduction steps for `git fetch --tags` issue in bare repositories. David Bohman provides a minimal test case showing that when a tag is force-moved in the main repository, a bare clone fails to properly fetch new tags while reporting them as "new tag" in the output. The test demonstrates that despite the command output claiming tags like "v5" were fetched, they don't actually appear in the repository's tag list. The rejection of the "stable" tag (which would clobber an existing tag) appears related, as the command exits with status 1.

This adds important context to the ongoing discussion by showing the issue isn't specific to the original bind9 repository and can be reproduced in a controlled local setup. The behavior suggests a possible interaction between tag rejection handling and new tag updates in bare repositories, where one rejected tag might be causing the entire operation to fail silently for other tags. The reproduction steps may help maintainers investigate why this changed between Git 2.50.1 and 2.51.0.
