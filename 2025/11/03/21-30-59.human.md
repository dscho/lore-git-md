This is a bugfix follow-up in the ongoing discussion about a regression in version tag sorting introduced by the ps/ref-peeled-tags changes. Jeff King identifies and proposes a fix for the root cause of the issue where numeric version tags (like vsample-1.0, vsample-2.0, vsample-10.0) were being sorted incorrectly using ASCII comparison rather than numeric sorting.

The problem occurs because the `maybe_object` field in the expand_data struct isn't being reset between tag evaluations, causing the first parsed object to be incorrectly reused. Jeff's simple one-line fix resets this field before processing each tag, which should restore proper numeric sorting behavior. The fix is minimal and targeted, though Jeff notes there might be a more appropriate place to do the reset.

This follows Junio's earlier bisect that pinpointed commit 054f5f45 (ref-filter: parse objects on demand) as the source of the regression, and his provided test case that demonstrated the failure in both loose and packed tag scenarios. The fix appears straightforward and well-reasoned, addressing a clear regression in functionality that was recently introduced.
