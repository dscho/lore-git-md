This is a brief technical reply in the ongoing discussion about a regression in `git fetch --tags` behavior in bare repositories. Chris Torek points out that the pre-2.51.0 (where rejected tags didn't prevent other new tags from being stored) versus post-2.51.0 behavior (where any tag rejection fails the entire operation) is likely due to the new reference transaction system. 

The key observation here is that the system now appears to enforce atomicity - either all tag updates succeed or none do. Chris raises the philosophical question of which behavior (the old permissive one or the new atomic one) should be considered correct, implying this might not be a straightforward bug but rather a design decision with tradeoffs.

This moves the discussion from "here's a regression" to a deeper question about the intended semantics of tag updates in Git, particularly in bare repositories. The reply suggests maintainers will need to decide whether to restore the old behavior or document the new atomic behavior as intentional.
