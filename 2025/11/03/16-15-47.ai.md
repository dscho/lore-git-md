This is a follow-up discussion in the feature patch series introducing diff algorithm configurability to `git blame`. Junio C Hamano responds to Phillip Wood's observation about the interaction between `--no-minimal` and the new `--diff-algorithm` option.

Junio proposes a long-term direction for handling diff algorithm options across Git commands, suggesting that:
1. `--diff-algorithm=<name>` should be the canonical way to specify algorithms
2. `--no-<name>` flags should generally be deprecated as they don't make sense in a multi-algorithm context
3. Commands should either support all algorithm variants consistently or none at all

For the current patch series, Junio suggests that while keeping `--minimal` is acceptable (since the series adds support for multiple algorithms), `--no-minimal` should be deprecated as it becomes meaningless when other algorithms are available. This aligns with the principle that boolean toggles don't work well for multi-choice selections.

The discussion represents final polish for the series, addressing the legacy `--minimal` flag behavior in the new multi-algorithm world. Junio's comments provide maintainer guidance on the preferred direction for algorithm selection interfaces, though the immediate patch series only needs to handle the `--no-minimal` case appropriately.

This email doesn't require any code changes to the series but provides important design philosophy that will inform future work on diff algorithm selection interfaces across Git commands. The feedback suggests marking `--minimal` as OPT_HIDDEN (as Phillip previously suggested) would be a step toward this deprecation path.
