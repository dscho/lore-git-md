This is a bugfix follow-up in the ongoing discussion about a regression in version tag sorting. Junio C Hamano reports that bisecting points to commit 054f5f45 ("ref-filter: parse objects on demand") as the root cause of broken version sorting for tags. The issue manifests when using `git tag --list --sort=version:tag`, where numeric versions are not being sorted correctly (e.g., "v2.10.0" appearing between "v1.19.0" and "v2.2.0").

The email includes a simple reproduction test that demonstrates the problem works with both loose and packed refs. The test creates annotated tags with version numbers (1.0, 2.0, 10.0) and verifies they sort correctly by version. This regression is particularly problematic as it affects the core functionality of Patrick Steinhardt's recent ref-peeled-tags work.

The issue appears to be urgent, as it impacts basic version sorting functionality that users would reasonably expect to work. Since this affects a recently merged topic, the maintainers will likely need to decide between fixing the regression or potentially rolling back the change. The test case provided gives a clear way to verify any proposed fix.
