This is a bugfix discussion regarding `git fetch --tags` behavior in bare repositories. Karthik Nayak confirms being able to reproduce the issue reported by David Bohman, where force-pushed tags cause `fetch --tags` to both reject moved tags (correctly) but also silently fail to store other tags while reporting them as "[new tag]". 

The thread has already established this is a regression introduced in Git 2.51.0's reference transaction system, which enforces atomic failure where earlier versions allowed partial success. Karthik notes they're investigating the transaction reference updates specifically, suggesting progress toward identifying the root cause. 

This email doesn't introduce new technical details but confirms the issue is reproducible and being actively worked on. The core tension remains between the technical correctness of atomic transactions versus user expectations from a long-standing command. The misleading "[new tag]" reporting while tags aren't actually stored appears to be a particularly problematic aspect of the current behavior.
