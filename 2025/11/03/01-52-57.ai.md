This is a brief response in the ongoing discussion about the `git fetch --tags` regression in bare repositories. Chris Torek points out that the behavior change (where tag updates now either all succeed or all fail) is likely due to the new reference transaction system introduced in Git 2.51.0. He raises the key question of whether the pre-2.51 behavior (where rejected tags didn't prevent other new tags from being stored) or the current behavior (atomic failure on any rejection) is actually the bug.

The comment suggests the regression might be an intentional (though perhaps undesirable) consequence of the reference transaction changes rather than an accidental bug. This shifts the discussion from diagnosing the regression to evaluating which behavior is correct - the old per-tag updates or the new atomic behavior. The technical focus remains on the tag update logic in bare repositories, now with consideration of how the reference transaction system affects this case.
