This is a bugfix follow-up in the ongoing discussion about a regression in version tag sorting introduced by the ps/ref-peeled-tags changes. The maintainer Junio C Hamano provides a concrete test case showing the failure, which occurs when sorting annotated tags with version numbers (e.g., "1.0", "2.0", "10.0") using `--sort=version:tag`. The test demonstrates the issue persists whether tags are loose or packed.

The regression was bisected to commit 054f5f45 ("ref-filter: parse objects on demand"), which is a core part of Patrick Steinhardt's ref-peeled-tags work. The test shows numeric version sorting is broken - it would incorrectly sort "10.0" before "2.0" due to ASCII rather than numeric comparison. This affects the `git tag --list` output when version sorting is requested.

The test case is minimal and clearly demonstrates the regression, showing both loose and packed tag scenarios. This appears to be a high-priority issue since it affects a basic version sorting functionality that worked correctly before the ref-peeled-tags changes. The test would serve both to verify any fix and prevent future occurrences of this regression.

Key technical details:
- Failing command: `git tag --list --sort=version:tag`
- Affected versions: since 054f5f45 in ref-filter.c
- Test tags: vsample-1.0, vsample-2.0, vsample-10.0
- Expected order: 1.0, 2.0, 10.0
- Current broken behavior: likely 1.0, 10.0, 2.0 (ASCII sort)
- Test covers both loose and packed ref cases

This email moves the discussion from theoretical regression report to concrete reproduction, providing Patrick Steinhardt with what's needed to diagnose and fix the numeric sorting issue in the ref-filter object parsing changes.
