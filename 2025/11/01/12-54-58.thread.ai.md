Thread identity: Bug report about `git-subtree` not respecting `commit.gpgSign` configuration, affecting users who expect GPG-signed commits during subtree operations.

Core problem: When `git-subtree` generates commits during subtree operations (split, push, etc.), it ignores the `commit.gpgSign` configuration that controls whether commits should be GPG-signed. This creates unsigned commits even when users have globally configured Git to sign all commits.

Current status: Initial bug report from Fa showing the issue occurs with Git 2.43.0 on Windows 10, with reproducible case in their SteamworksParser repository (starting from commit `a2883a6`). No responses or proposed fixes yet.

Key technical details: The bug affects the `git-subtree` script (likely in `contrib/subtree/`), specifically its commit generation logic which should check `commit.gpgSign` before creating commits. The issue impacts users who rely on GPG signing for subtree operations.

Open questions: Whether this affects all subtree operations or just specific ones (split/push), and whether there might be other signing-related configurations that should also be respected. The fix would need to maintain backward compatibility with existing behavior when `commit.gpgSign` is not set.

Participant positions: Only the reporter (Fa) has commented so far, providing a clear bug report with reproduction steps. No maintainer or other contributors have responded yet.

Related work: The `git-subtree` script has had various maintenance and bug fix efforts over time, but this specific signing configuration issue appears to be newly reported. The behavior differs from core Git commands which do respect `commit.gpgSign`.
