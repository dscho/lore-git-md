This is a technical discussion about Git's command-line option parsing behavior, specifically around `git clone -c` and `--config` arguments with whitespace.

Jeff King (peff) responds to Junio C Hamano's analysis of the whitespace-trimming behavior in `git clone` config arguments. He clarifies that the "stuck" form (`-cfoo`) is valid and equivalent to `-c foo`, explaining why some whitespace-containing forms previously worked. He notes the long option `--config=KEY=VALUE` is valid while `--config KEY=VALUE` (without equals) is not, though the documentation doesn't consistently show the equals form.

The discussion reveals that Git was previously lenient in accepting whitespace around config keys (e.g., `' KEY=VALUE'`), which conflicted with Git's config key format specifications. While this behavior existed since 2010, both agree it was likely unintentional and shouldn't be preserved for backward compatibility, comparing it to an "accidental Feature" scenario.

The email also touches on broader documentation issues around option syntax consistency in Git's manpages, though peff suggests this is a larger project rather than an urgent bug. The key takeaway is that the recent change removing whitespace-trimming appears correct despite breaking some historical usage, as the old behavior violated config format rules.
