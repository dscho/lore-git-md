Junio C Hamano provides technical clarification on Git's smudge filter constraints, reinforcing and expanding upon Johannes Sixt's earlier explanation about why smudge filters cannot reliably access working tree files. This is a follow-up in the ongoing discussion about secret management workflows using Git filters.

The email explains two concrete scenarios where attempting to read working tree files during smudging would fail: (1) when checking out a commit where the file didn't previously exist in the working tree, and (2) during transitions between commits where the working tree version may be from a different revision or mid-checkout. Junio emphasizes that the `%f` parameter should only be used to identify the output destination path, not as a way to access file contents.

Key technical details include:
- Smudge filters operate on blob content from the object database, not working tree files
- Working tree files may be missing or contain unrelated content during checkout operations
- The current documentation's "Depending on..." phrasing could be simplified to be more direct
- The filter must function purely as a content transformer without external file access

This reinforces the architectural limitation that makes the original secret restoration approach unworkable, while suggesting potential documentation improvements. The email doesn't propose new solutions but provides important context about Git's internals that any alternative approach would need to respect. The discussion remains focused on understanding constraints rather than advancing specific implementations.
