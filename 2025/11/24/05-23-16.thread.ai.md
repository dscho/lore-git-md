Regression in `git clone` config parsing with `-c`/`--config` arguments:

A regression was reported where `git clone -c` and `--config=` arguments with whitespace around keys (e.g. `'-c KEY=VALUE'`) fail in v2.52.0+ due to removal of whitespace trimming behavior from commit dcecac2580ef. The behavior dated back to 2010's commit 8bfa77867. Jeff King (peff) provided historical analysis showing whitespace-trimming originated in 2010 predating environment variable handling, with config parameter handling evolving through multiple changes (2010, 2011, 2021). The trimming was already effectively broken since 2021's config format changes, and only affects `git clone -c` as other paths use different mechanisms.

New analysis from Jeff King reveals the historical behavior was more extensive than initially understood - it affected both `git clone` and `GIT_CONFIG_PARAMETERS` environment variable parsing, trimming whitespace on both sides of the equals sign. Current behavior rejects such input entirely. Junio C Hamano's analysis confirms documentation specifies `-c key=value` as separate arguments without supporting quoted forms, and that whitespace-trimming violated Git's config key format rules. He initially thought this was a bug but now sees it as a quirk of option parsing.

Two competing fixes had emerged:
1. Johannes Schindelin (Dscho) proposed introducing `STRING_LIST_SPLIT_TRIM_FIRST` flag for selective key trimming
2. Junio Hamano proposed a minimal fix in `builtin/clone.c`'s `write_config()` with explicit key trimming

Jeff King now argues more strongly against any fix, noting:
- The behavior was already silently broken for `git -c` since 2021 without reports
- Original trimming affected both sides of equals sign, not just leading whitespace
- Impact appears limited to edge cases and third-party tools
- Third-party tools should adapt to Git's stricter parsing

Technical details:
- Original whitespace-trimming code was in config.c around line 649 in v2.51.2
- Value-trimming was silently dropped earlier in 2011's commit 06eb708f33 (per D. Ben Knoble)
- Junio's patch uses simple `isspace()` loop for key trimming only
- Behavior was Git-specific and not general option parsing convention

Current status:
- Consensus forming that original behavior was correct to remove despite breaking historical usage
- Discussion shifted to whether any fix is needed versus treating as intentional bugfix
- Peff now advocates leaving regression as correction of accidental behavior unless strong case made

Open questions:
- Whether to implement any fix given broader scope of original behavior
- Documentation issues around option syntax in manpages
- Impact assessment for Git LFS, Bamboo and other tools
- Whether third-party tools should adapt instead of Git maintaining backward compatibility

Participant positions:
- Jeff King and Junio Hamano agree original behavior was accidental but widely used
- Jeff King now strongly advocates leaving regression as intentional bugfix
- Johannes Schindelin had proposed infrastructure-level fix
- Junio Hamano offered simpler clone-specific solution marked as temporary
- D. Ben Knoble provided historical context about earlier value-trimming removal

Related work:
- Git LFS and Bamboo CI workflows known to be affected
- 2011's commit 06eb708f33 that silently dropped value-trimming
- 2021 config format changes that made original behavior effectively broken
- General option parsing behaviors elsewhere in Git (e.g. `strtol()` handling)
