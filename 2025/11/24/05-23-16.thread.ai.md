Regression in `git clone` config parsing with `-c`/`--config` arguments:

A regression was reported where `git clone -c` and `--config=` arguments with whitespace around keys (e.g. `'-c KEY=VALUE'`) fail in v2.52.0+ due to removal of whitespace trimming behavior from commit dcecac2580ef. The behavior dated back to 2010's commit 8bfa77867.

Jeff King (peff) provided historical analysis showing whitespace-trimming originated in 2010 predating environment variable handling, with config parameter handling evolving through multiple changes (2010, 2011, 2021). The trimming was already effectively broken since 2021's config format changes, and only affects `git clone -c` as other paths use different mechanisms. Valid forms are `-cfoo` (stuck form) equals `-c foo`, `--config=KEY=VALUE` valid while `--config KEY=VALUE` invalid.

Junio C Hamano's analysis confirms documentation specifies `-c key=value` as separate arguments without supporting quoted forms, and that whitespace-trimming violated Git's config key format rules. He initially thought this was a bug but now sees it as a quirk of option parsing, questioning the utility of preserving leading whitespace in config values.

Two competing fixes have emerged:
1. Johannes Schindelin (Dscho) proposed introducing `STRING_LIST_SPLIT_TRIM_FIRST` flag to selectively trim whitespace only from keys while leaving values untouched, modifying `config.c`, `string-list.c`, and `string-list.h`.
2. Junio C Hamano now proposes a more targeted fix in `builtin/clone.c`'s `write_config()` function, adding explicit whitespace trimming (20 lines added) with a NEEDSWORK comment marking it as temporary. This differs from Schindelin's approach by avoiding changes to string-list infrastructure.

Technical details:
- Original whitespace-trimming code was in config.c around line 649 in v2.51.2
- Value-trimming was silently dropped earlier in 2011's commit 06eb708f33 (per D. Ben Knoble)
- Change specifically affects config parsing during clone operations
- Junio's patch uses simple `isspace()` loop for key trimming only

Current status:
- Consensus formed that original behavior was correct to remove despite breaking historical usage
- Both proposed fixes aim to restore key-trimming while keeping value handling strict
- Discussion shifted to implementation approach (targeted vs infrastructure change)

Open questions:
- Which fix to accept (Junio's minimal clone.c change vs Schindelin's string-list modification)
- Broader documentation issues around option syntax in manpages
- Impact assessment for Git LFS, Bamboo and other tools relying on historical behavior
- Timeline for eventual deprecation of this compatibility measure

Participant positions:
- Jeff King and Junio Hamano agree original behavior was accidental but widely used
- Johannes Schindelin proposed infrastructure-level fix for selective trimming
- Junio Hamano now offers simpler clone-specific solution marked as temporary
- D. Ben Knoble provided historical context about earlier value-trimming removal

Related work:
- Git LFS and Bamboo CI workflows known to be affected
- 2011's commit 06eb708f33 that silently dropped value-trimming
