Regression in `git clone` config parsing with `-c`/`--config` arguments:

A regression was reported where `git clone -c` and `--config=` arguments with whitespace around keys (e.g. `'-c KEY=VALUE'`) fail in v2.52.0+ due to removal of whitespace trimming behavior from commit dcecac2580ef. The behavior dated back to 2010's commit 8bfa77867. Jeff King (peff) provided historical analysis showing whitespace-trimming originated in 2010 predating environment variable handling, with config parameter handling evolving through multiple changes (2010, 2011, 2021). The trimming was already effectively broken since 2021's config format changes, and only affects `git clone -c` as other paths use different mechanisms.

Jeff King's deeper analysis revealed the historical behavior was more extensive than initially understood - it affected both `git clone` and `GIT_CONFIG_PARAMETERS` environment variable parsing, trimming whitespace on both sides of the equals sign. Current behavior rejects such input entirely. Junio C Hamano's analysis confirmed documentation specifies `-c key=value` as separate arguments without supporting quoted forms, and that whitespace-trimming violated Git's config key format rules. He initially thought this was a bug but now sees it as a quirk of option parsing.

The discussion has concluded with consensus that no fix should be implemented, treating the change as an intentional correction of what was effectively already broken behavior. Jeff King acknowledges Junio's position to leave the regression unfixed while expressing mild concern about impact on Git LFS and similar tools. He notes any potential fix would be strictly limited to supporting `-c foo=bar` as a single argument (the Git LFS case), but maintains strong preference for letting the breakage stand to encourage callers to adapt to Git's stricter parsing rules. Junio C Hamano's final message humorously noted he wouldn't block a fix but wouldn't prioritize reviewing it, reinforcing the regression will stand.

Technical details:
- Original whitespace-trimming code was in config.c around line 649 in v2.51.2
- Value-trimming was silently dropped earlier in 2011's commit 06eb708f33 (per D. Ben Knoble)
- Behavior was Git-specific and not general option parsing convention
- Potential minimal fix scope would be limited to `-c foo=bar` single-argument cases
- Git LFS confirmed affected by single-argument case
- Junio's simple "trim" patch remains available but unlikely to be pursued

Current status:
- No fix will be implemented, treating the change as an intentional bugfix
- Third-party tools (Git LFS, Bamboo CI) will need to adapt to stricter parsing
- Documentation issues around option syntax in manpages may be addressed separately
- Discussion effectively concluded with maintainers accepting regression as correction

Participant positions:
- Jeff King and Junio Hamano agree original behavior was accidental but widely used
- Jeff King strongly advocated leaving regression as intentional bugfix, with mild concern for Git LFS impact
- Johannes Schindelin's infrastructure-level fix not pursued
- Junio Hamano's simpler clone-specific solution also abandoned
- D. Ben Knoble provided historical context about earlier value-trimming removal

Related work:
