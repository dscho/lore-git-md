Regression in `git clone` config parsing with `-c`/`--config` arguments:

A regression was reported where `git clone -c` and `--config=` arguments with whitespace around keys (e.g. `'-c KEY=VALUE'`) fail in v2.52.0+ due to removal of whitespace trimming behavior from commit dcecac2580ef. The behavior dated back to 2010's commit 8bfa77867.

Jeff King (peff) provides historical analysis:
- The whitespace-trimming behavior originated in 2010 predating environment variable handling
- Config parameter handling evolved through multiple changes (2010, 2011, 2021)
- The trimming was already effectively broken since 2021's config format changes
- Current change only affects `git clone -c` as other paths use different mechanisms

Junio C Hamano's earlier analysis noted:
- Documentation specifies `-c key=value` as separate arguments, not supporting quoted forms
- Current behavior may have been incorrect
- Documentation omits `--config=K=V` form despite it working
- Trimming whitespace violates Git's config key format rules

Technical details:
- Original whitespace-trimming code was in config.c around line 649 in v2.51.2
- Value-trimming was silently dropped earlier in 2011's commit 06eb708f33 (per D. Ben Knoble)
- Change specifically affects config parsing during clone operations

Open questions:
- Whether to treat as regression or documentation-correcting behavior change
- Whether to document `--config=K=V` form consistently
- How to handle backward compatibility given behavior existed since 2010

The discussion has shifted from regression report to examining whether the pre-v2.52.0 behavior was correct. Jeff's analysis suggests the removed behavior was likely never intentional and conflicts with config rules, moving the discussion toward accepting this as a correction rather than regression. Final assessment remains open.
