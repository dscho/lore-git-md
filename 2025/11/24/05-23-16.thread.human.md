This thread discusses a regression in `git clone` where `-c` and `--config` arguments with whitespace around keys (e.g., `'-c KEY=VALUE'`) stopped working in Git 2.52.0+. Jeff King traced this to commit dcecac2580ef, which removed whitespace trimming behavior that had existed since 2010. 

Jeff and Junio agree the old behavior was technically incorrect—it violated Git's config key format rules—but was preserved through multiple changes until now. The discussion has shifted from treating this as a regression to recognizing it as correcting an accidental feature. While the old behavior was convenient for some users, it was never properly supported in the documentation, which specifies `-c key=value` as separate arguments.

Junio now acknowledges the whitespace handling was more of an option-parsing quirk than a bug, though he questions the value of preserving leading whitespace in config values. He suggests the ideal would have been rejecting such whitespace from the start, but given the long-standing behavior, he's skeptical about whether it's worth engineering a fix just to deprecate it later. The consensus appears to be that the new behavior, while breaking some historical usage, is correct and aligns with Git's config specifications. Documentation updates may still be needed to clarify the valid forms (`-cfoo`, `-c foo`, `--config=KEY=VALUE`).
