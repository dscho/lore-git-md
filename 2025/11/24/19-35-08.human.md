This is a technical clarification in the ongoing discussion about Git's clean/smudge filters for secret management workflows. Junio Hamano responds to Kache Hit's question about why smudge filters cannot safely read from disk, even when they properly handle stdin/stdout operations.

Hamano explains that the prohibition isn't purely dogmatic but stems from real-world scenarios where the working tree file might not exist or might contain unrelated content when the smudge filter runs. He walks through concrete examples: checking out a commit where the file didn't previously exist, or switching between versions where the working tree contains modified or smudged content from a different commit. The filter must work purely from the blob content provided on stdin because the working tree file's state is unreliable during these operations.

The email also suggests improving Git's documentation to make this constraint clearer, proposing more direct wording that emphasizes %f should only be used to identify the output path, not as a way to access working tree content. This continues the thread's pattern of experienced contributors helping Kache understand Git's architectural constraints while still engaging with the underlying workflow needs.

The response doesn't introduce new solutions but solidifies why the original approach is fundamentally limited by Git's design, reinforcing Johannes Sixt's earlier technical clarification. It leaves open how to address Kache's actual use case while respecting these constraints.
