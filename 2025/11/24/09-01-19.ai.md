This is a technical response in the ongoing thread about Git's clean/smudge filters for secret restoration workflows.

Johannes Sixt responds to Kache Hit's question about why smudge filters can't access the working tree file on disk, confirming the documented behavior is intentional. The reply emphasizes that while the filter receives the filename via %f, it must remain a pure content transformation - reading only from stdin and writing only to stdout, without filesystem access. This maintains Git's filter design philosophy of side-effect-free operations.

The response doesn't address potential workarounds or the security rationale behind the restriction, focusing instead on clarifying the current contract of filter behavior. This suggests the limitation is fundamental to Git's filter architecture rather than an implementation detail that could be relaxed. The exchange leaves open whether alternative approaches might exist for the secret restoration use case while making clear the current design won't support direct working tree access in smudge filters.
