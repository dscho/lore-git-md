This is a follow-up discussion in the completed xdiff refactoring series, specifically addressing type safety changes for Rust FFI compatibility. The email focuses on clarifying the rationale behind changing `xrecord_t.ptr` from `char` to `uint8_t` in patch 03/10.

Ezekiel Newren responds to Phillip Wood's query about the commit message's mention of Unicode code points, explaining that the primary motivation is indeed Rust FFI compatibility (matching Rust's `u8` type), but also notes that xdiff operates on raw bytes rather than Unicode characters. The discussion reveals xdiff's agnosticism toward text encoding - it treats all input as byte strings regardless of whether they contain UTF-8, UTF-16, or other encodings. This has implications for the Rust FFI design, as using `&[u8]` rather than `&str` avoids potential UTF-8 validation issues.

The email also confirms the practical constraints that led to using casts rather than a broader refactoring of xdiff's function signatures, with both agreeing this was the right tradeoff. This exchange demonstrates the careful consideration given to type system choices at the C/Rust boundary, particularly around string/byte handling semantics, even after the series has been merged.
