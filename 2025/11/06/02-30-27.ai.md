This is a feature proposal for improving `git blame` functionality. Simon Richter identifies a gap in the current `--reverse` mode of `git blame` - it helps find when a line was last present, but doesn't directly identify the commit that removed the line or explain why. The current behavior can be confusing when it points to merge commits where multiple branches diverged rather than the actual removal commit.

The email suggests extending `git blame` to better handle the common workflow of tracking down why a line was removed from historical versions. While the message doesn't propose a specific implementation, it clearly describes the pain point: users want to not just find when a line disappeared, but understand the removal's context through the commit message that removed it.

This touches on Git's revision history analysis capabilities and would likely involve changes to the blame machinery in `builtin/blame.c`. The request seems reasonable and well-motivated by a concrete use case, though the technical challenges of reliably identifying "the commit whose message is most likely to explain things" (versus just the first commit where the line is absent) would need careful consideration. The proposal could spark discussion about whether this belongs in core Git or as a porcelain command.
