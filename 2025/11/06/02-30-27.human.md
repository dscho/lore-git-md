**Feature exploration for enhanced blame functionality**

Simon Richter raises an interesting use case that isn't fully addressed by `git blame --reverse`. They want to find not just when a line was removed, but specifically which commit's message best explains why it disappeared - particularly in cases where multiple branches diverge.

The email suggests `git blame --reverse` gets them close but not all the way to their goal, as it can point to merge points rather than the actual explanatory commit. This appears to be a real pain point in code archaeology workflows, though the email doesn't propose a specific solution.

The request seems well-motivated by practical experience ("once again I've found myself..."), and touches on an area where Git's tooling could potentially be enhanced. The problem statement is clear, though some readers might want to see concrete examples of where the current behavior falls short. This could spark interesting discussion about whether this belongs in core Git or as a helper script, and what heuristics might identify the "most explanatory" commit.
