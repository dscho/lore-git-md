Here's the updated human-readable thread summary:

The thread discusses improving `git blame --reverse` to better track when and why lines were removed from files. Simon Richter originally pointed out that the current implementation only shows when a line last appeared, not which commit actually removed it - a particular pain point when merges are involved, as the last appearance might be in a merge commit rather than the actual removal.

Ben Knoble has now suggested a practical workaround using `git log -S` (pickaxe search) to manually find when specific content disappeared. He provided examples showing how to search for removed lines by their content or by function/variable names when the exact line isn't unique enough. While this doesn't solve the core problem with merge commits, it gives users a way to track down many removals without waiting for blame enhancements.

The discussion remains open on how to properly implement this in blame itself, particularly around handling merge cases and determining which removal commit's message best explains the change. There's also the question of whether this belongs in core blame or as a separate command. For now, the pickaxe workaround provides a usable solution while the deeper design questions get worked out.
