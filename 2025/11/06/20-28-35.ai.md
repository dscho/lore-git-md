Platform compatibility fix for flaky reftable test on Cygwin, addressing Windows filesystem behavior.

Ramsay Jones confirms Patrick Steinhardt's proposed workaround using `test-tool truncate` instead of shell redirection (`: >"$f"`) successfully stabilizes the intermittently failing test 29 in t0610-reftable-basics.sh. The test runs completed successfully across 320 iterations (32 parallel runs × 10 stress cycles) on a Windows 10 system with 16 logical cores. This validates the approach despite neither contributor fully grasping the underlying Windows API behavior that causes the original shell method to fail.

The email provides important context about Cygwin testing constraints - sequential test runs take 4+ hours on modern hardware, motivating parallel execution despite occasional hangs. Jones notes this isn't a regression (present since Git 2.51) and pragmatically endorses the workaround pending deeper understanding of the root cause.

Key technical details:
- Test 29 verifies reftable corruption handling by truncating `.git/reftable/*.ref` files
- Windows' file handle semantics differ from POSIX expectations
- `test-tool truncate` appears more reliable than shell redirection for this operation
- Parallel test execution (`-j8`) exacerbates timing-sensitive failures

The thread shows consensus forming around this platform-specific adaptation, with Johannes Sixt's earlier Windows API analysis providing the missing explanation for why the workaround succeeds where shell redirection fails. This represents a practical solution to unblock Cygwin testing while the reftable backend matures.
