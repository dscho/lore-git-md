This is a review comment on the `git history reword` subcommand implementation in Patrick Steinhardt's history editing series. SZEDER Gábor points out several significant differences between the proposed `reword` command and the equivalent interactive rebase operation that aren't adequately documented or justified.

The main critique is that unlike interactive rebase, `git history reword` doesn't check out the commit being modified, which removes the ability to examine the full file state when writing a new commit message. The reviewer notes this is particularly problematic for non-trivial rewording where seeing the "big picture" is helpful. While acknowledging there may be cases where avoiding a checkout is desirable (like fixing simple typos), they argue the command should support both workflows.

The review also questions the interface design, suggesting that requiring users to specify the commit upfront is less intuitive than interactive rebase's instruction sheet approach. The feedback highlights missing documentation about these behavioral differences and insufficient test coverage of the no-checkout behavior.

This appears to be substantive feedback about a user experience difference that wasn't adequately addressed in the initial implementation. The concerns seem well-founded and would likely need to be resolved before the feature could be considered complete, either through interface changes or clearer documentation of the tradeoffs. The comment doesn't fundamentally challenge the feature's viability but identifies important usability gaps.
