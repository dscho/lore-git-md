This is a review response from Junio Hamano on a feature addition to `git replay` that introduces a `--revert` option. The patch aims to enable server-side revert operations by reusing cherry-pick infrastructure with swapped base/pickme trees.

Junio raises several technical concerns about the implementation. He notes the revert message generation appears duplicated rather than properly refactored from existing sequencer code, suggesting this should be done in a preliminary patch. He questions whether the boolean `is_revert` parameter would be clearer as an enum if more pick variants are anticipated.

The review also requests clarification on why `--revert` must be incompatible with `--contained`, suggesting the documentation should explain the inherent contradiction rather than just stating the restriction. Junio examines the example usage scenarios and wonders about unstated topological requirements between branches being reverted.

While the core 3-way merge approach for implementing reverts looks sound, Junio points out some code quality issues like overly long lines and questions the NULL-clearing pattern for merge options. The feedback maintains a constructive tone while identifying several areas where the patch could be improved for maintainability and clarity before merging.
