This is a follow-up in the ongoing discussion about secret management in Git configuration files, specifically addressing dotfile workflows.

Chris Torek shares his personal approach to managing dotfiles with secrets, which differs from the template-based solution he previously suggested. He keeps his configuration files in a repository without leading dots (e.g., "gitconfig" instead of ".gitconfig") and uses a custom installer to deploy them to their proper locations. This makes it visually obvious during editing whether one is working with the template or the live file.

The approach appears to be a pragmatic workaround that avoids some of the version control complexities discussed earlier in the thread, though Chris notes it's tailored to his personal needs and acknowledges limitations with modern software that dynamically modifies configuration files. He also hints at the reverse workflow (updating the repository from active files) would be more challenging to implement.

This response provides a concrete example of how one experienced Git user handles the problem, though it doesn't directly address Kache Hit's concern about mixed-content configuration files where credentials appear alongside third-party-managed settings. The discussion continues to highlight the tension between Git's architectural constraints and real-world configuration management needs.
