Feature implementation with significant behavioral difference from existing workflow.

SZEDER Gábor raises important concerns about the `git history reword` subcommand's behavior compared to interactive rebase's reword operation. The key issue is that unlike rebase which checks out the commit being reworded, this implementation operates purely in-memory without checking out files. This creates a substantial usability gap when rewording non-trivial commits where examining the full file state would be helpful.

The email notes this behavioral difference is undocumented in both the commit message and user-facing documentation, and lacks test coverage for this specific aspect. SZEDER suggests the command should ideally support both workflows - in-memory operation for simple typo fixes and checkout-based operation for more complex rewording.

Additionally, the interface design is questioned for requiring users to specify the commit to reword upfront rather than selecting from an interactive list like rebase's instruction sheet. This could make the command less intuitive and more error-prone in practice.

The feedback highlights a tension between the series' goal of providing lightweight history editing and maintaining the full functionality users expect from similar operations. This appears to be a case where the new command's simplification may have gone too far by removing capabilities that experienced users rely on during commit message editing.

The concerns are well-founded and technical in nature, focusing on real workflow impacts rather than implementation details. They suggest the reword subcommand may need significant redesign to be truly useful, particularly around the checkout behavior and selection interface. This feedback comes late in the series' review cycle (v6) and addresses a core user experience aspect that wasn't previously discussed.
