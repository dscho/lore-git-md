This thread centers on adding a `--revert` capability to `git replay`, primarily to support GitLab's Gitaly service in performing server-side reverts on bare repositories. The feature has progressed through several versions with input from key contributors like Elijah Newren, Phillip Wood, and Junio Hamano. The design has solidified around treating revert as a distinct operation mode (separate from `--onto` and `--advance`) that preserves commit-by-commit reversal with individual messages.

The implementation handles complex cases like non-linear histories and selective non-contiguous commit reversal while maintaining atomic ref updates. Recent versions have focused on code quality improvements—better memory management, consolidated validation logic, and test simplification. A notable technical challenge has been sharing commit reference formatting between `sequencer.c` and `replay.c`, with discussion around whether to use flags or structs for parameter passing.

A new discussion has emerged about whether `git replay --revert` should respect the `revert.reference` configuration setting, mirroring `git revert`'s behavior. Kristoffer Haugsbakk raises an important philosophical question about plumbing commands and configuration—should they ignore user configs for consistency, or require explicit opt-out? This touches on a broader design consideration for the project as it balances shared infrastructure needs with distinct use cases.
