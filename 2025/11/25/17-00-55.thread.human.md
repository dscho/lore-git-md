This thread centers on extending `git replay` to support reverting commits, primarily for GitLab's Gitaly service. The current implementation (v4) has reached technical completion after extensive review from Phillip Wood, Patrick Steinhardt, and Junio Hamano. The core functionality now handles reverts as a distinct operation mode, processing commits in chronological order (newest-first) and dropping empty reverts by default to match `git cherry-pick` behavior. A key refactoring consolidates revert message generation into a shared `sequencer_format_revert_message()` helper, addressing earlier concerns about split logic.

While the technical implementation is sound, the interface design remains under discussion. Christian Couder and Toon Claes have proposed restructuring the command as subcommands (`replay revert`, `replay onto`), but there's growing consensus to defer this change to avoid scope creep. The latest patch from Siddharth Asthana cleanly extracts the revert message logic into a reusable helper, marking the final technical piece before merge consideration. Junio's active engagement suggests this feature is nearing readiness, though some documentation polish and test edge cases remain. The team is balancing immediate GitLab requirements against long-term interface clarity, with the current approach prioritizing getting the well-reviewed functionality merged first.
