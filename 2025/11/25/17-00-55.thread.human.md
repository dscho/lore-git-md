This thread centers on adding a `--revert` capability to `git replay`, primarily for GitLab's server-side operations. The initial implementation reused cherry-pick infrastructure to reverse commits directly on bare repos, with test coverage in t3650-replay-basics.sh. While Johannes Schindelin approved the approach ("looks fine to me"), test failures emerged in revert operations, and Junio Hamano has been guiding refinements to code organization and documentation.

Phillip Wood's recent review raises deeper concerns, questioning the feature's fundamental design. He argues the current implementation may not solve real-world problems, as demonstrated by test cases producing empty revert commits due to unrealistic setups. His critique highlights a bug in message formatting that escaped detection because tests only checked for "Revert" prefixes rather than full content. Wood suggests making `--revert` a distinct mode rather than combining it with `--onto`, potentially defaulting to reverse commit order to minimize conflicts.

The thread now faces two levels of issues: the immediate test failures Junio noted, and Wood's broader concerns about whether the feature solves the right problem in the right way. These come alongside coordination challenges with Patrick Steinhardt's parallel "history" series refactoring work. The path forward likely requires addressing both the concrete implementation issues and the higher-level design questions Wood has raised.
