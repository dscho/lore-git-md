This thread centers on the addition of a `--revert` capability to `git replay`, primarily for GitLab's Gitaly service. The feature, now in its sixth iteration, allows reversing commits directly on bare repositories while preserving individual commit messages, treating reverts as merges with swapped arguments. The implementation introduces a distinct `REPLAY_MODE_REVERT` operation mode and consolidates revert message generation into a reusable `sequencer_format_revert_message()` helper function. Key contributors include Phillip Wood, Patrick Steinhardt, and Junio Hamano, with design input from Elijah Newren.

The series has evolved through multiple versions, with each addressing review feedback: adding test coverage, improving memory management, refining message formatting, and fixing compiler warnings. The current version handles complex cases like reverts of reverts and merge commits, processes commits newest-first to minimize conflicts, and aligns with `git cherry-pick` behavior by dropping empty reverts. All substantive technical issues have been resolved, and the series is ready for merging with maintainer consensus established.

A recent follow-up discussion highlighted one remaining edge case: while the current implementation correctly blocks ambiguous revision ranges (like `main f1 f2`), it may be overly restrictive by also preventing valid multi-range cases (such as `HEAD~5..HEAD~3 HEAD~1..HEAD`). This was acknowledged as a potential area for future refinement, but not as a blocking issue. The thread demonstrates that the feature has reached technical maturity, with only minor observations remaining for possible follow-up work.
