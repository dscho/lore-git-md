This thread centers on extending `git replay` to support reverting commits, primarily for GitLab's Gitaly service. The current implementation (v4) handles reverts as a distinct operation mode, processing commits in chronological order (newest-first) to minimize conflicts and dropping empty reverts by default—aligning with git cherry-pick's behavior rather than interactive revert. These decisions, confirmed through discussion with Phillip Wood, match Git's existing sequencer logic.

The technical foundation is solid, with thorough reviews from Phillip Wood, Patrick Steinhardt, and Junio Hamano. The series has evolved through four versions, refining memory management, test coverage, and consolidating revert message formatting into a shared helper function. While the core functionality is nearly ready, the interface design remains under discussion—particularly whether to use subcommands (e.g., `replay revert`) or flags. Most participants, including Siddharth Asthana (the patch author) and Christian Couder, favor deferring this restructuring to avoid scope creep.

The remaining work involves final test adjustments and documentation updates. Junio's engagement suggests this feature is on track for merging once these polish items are addressed, though the broader interface questions may resurface in future iterations.
