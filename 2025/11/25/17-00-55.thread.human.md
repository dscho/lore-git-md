This thread centers on extending Git's `replay` command with a `--revert` capability, primarily for GitLab's Gitaly service. The feature allows reversing commits directly on bare repositories while preserving individual commit messages. The design has solidified through discussion with key contributors like Elijah Newren, Phillip Wood, and Junio Hamano, establishing that reverts should be a distinct operation mode (not combinable with other modes) that handles complex revision ranges while maintaining atomic ref updates.

The implementation has progressed through several versions, with v2 introducing core functionality and v3 incorporating defensive checks and memory management improvements. Recent technical refinements focus on commit reference formatting boundaries between interactive (sequencer) and non-interactive (replay) contexts, with Patrick Steinhardt proposing potential unification via flags.

Phillip Wood's latest review provides constructive feedback on v2, suggesting test simplifications and implementation refinements while validating the core approach. He notes opportunities to streamline test organization, improve OID handling in revert messages, and factor out common validation code. These suggestions aim to improve code quality without altering the settled design.

Open questions remain around test coverage edge cases, documentation of commit-by-commit versus bulk approaches, and integration with Patrick Steinhardt's parallel "history" series. The naming debate for operation modes continues, with Junio Hamano proposing alternatives to the current `--onto`/`--advance` terminology. The implementation appears robust, with thorough test coverage and ongoing attention to architectural consistency from both reviewers and the maintainer.
