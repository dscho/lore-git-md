This thread introduces a new `--revert` mode for `git replay`, primarily to support GitLab's Gitaly service needs for server-side history rewriting on bare repositories. The feature has evolved through five versions, with v5 now ready for merging after extensive review from key contributors.

The implementation treats reverts as merges with swapped arguments (effectively reversing the diff direction), following patterns established in `sequencer.c`. Notable technical decisions include processing commits in chronological order (newest-first), dropping empty revert commits by default, and consolidating message formatting logic into a reusable helper function. The series maintains clear boundaries between plumbing and porcelain behavior by explicitly controlling format output.

Phillip Wood provided particularly thorough review feedback, leading to improvements in documentation, error handling, and internal consistency (notably the `revs.reverse` handling). Junio Hamano and Patrick Steinhardt also confirmed the technical soundness of the approach. While there's an ongoing discussion about restructuring the interface (possibly using subcommands like `replay revert`), that work is being deferred to avoid scope creep in this series.

The v5 iteration addresses final polish items like test script formatting and function documentation clarity. With all substantive feedback incorporated and comprehensive test coverage in place, this appears ready for merging as a well-considered addition to Git's server-side tooling.
