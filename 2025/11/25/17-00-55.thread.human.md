This thread introduces a new `--revert` capability to the `git replay` command, primarily for GitLab's Gitaly service to support server-side history rewriting in bare repositories. The feature treats reverts as merges with swapped arguments to reverse changes, creating new commits with standard revert messages while making the current user the author.

The design decisions emerged from discussion with key contributors including Elijah Newren, Phillip Wood, and Junio Hamano. Revert was established as a distinct operation mode (not combinable with other modes), with commit-by-commit reversal preferred for message preservation. The implementation handles complex revision ranges and maintains plumbing behavior by ignoring user configurations.

Through three versions, the series has evolved with refinements from reviewer feedback. Phillip Wood in particular validated core functionality while suggesting improvements to test organization, code quality, and architectural consistency. The current iteration shows careful attention to memory management, error handling, and maintainability concerns.

The implementation is thorough, touching multiple subsystems while maintaining consistency with existing `replay` behavior. It includes comprehensive tests for various scenarios including conflicts and bare repository cases. A few open questions remain around edge case coverage and documentation, but the technical approach appears sound and well-considered. The changes address GitLab's use case while fitting cleanly into Git's existing infrastructure.
