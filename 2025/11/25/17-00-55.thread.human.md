This thread centers on adding `--revert` capability to `git replay`, primarily for GitLab's Gitaly service. The second version of the patch series has reached technical consensus on key design points: reverts operate as a distinct mode (not combinable with `--onto` or `--advance`), handle commit-by-commit reversal with preserved messages, and support complex revision ranges while maintaining topological constraints. Elijah Newren, Phillip Wood, and Junio Hamano have shaped the interface to require explicit target branch specification (e.g., `git replay --revert main main..feature`).

The implementation includes two main parts: refactoring revert message generation into a shared helper, and the core `--revert` functionality with comprehensive tests. While the architectural direction is settled, Patrick Steinhardt's latest review suggests several code quality improvements—adding `BUG()` checks, using `FREE_AND_NULL()` consistently, simplifying option validation, and deduplicating ref update logic. These are minor refinements to an otherwise mature implementation.

One remaining discussion point is whether the message formatting helper should also handle commit references, as Patrick questions the current separation. The broader naming debate around operation modes (Junio favoring `--rebase`/`--cherry-pick` versus Elijah defending `--onto`/`--advance`) remains open but doesn't block progress. The series appears ready for final polishing before integration.
