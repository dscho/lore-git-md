This is a discussion about the `--revert` feature addition to `git replay` that was proposed earlier. Johannes Schindelin responds to Siddharth Asthana's patch with an alternative suggestion and some feedback on the implementation approach.

The key technical suggestion is to consider using `git merge-tree` directly for reverting entire Merge Requests at once rather than commit-by-commit, which could avoid merge conflicts. Johannes provides the specific command syntax for this approach (`git merge-tree --merge-base $TIP HEAD $BASE`) and notes its tradeoffs - it's more efficient but doesn't preserve the individual commit history of the revert.

On the implementation, Johannes gives general approval ("the patch itself looks fine to me") but offers two critiques: 1) the test suite may be overly extensive, suggesting a preference for more focused tests that don't unnecessarily lengthen CI runtimes, and 2) an implicit concern about test suite bloat affecting developer workflow. The discussion touches on GitLab's Gitaly use case but doesn't challenge the core functionality or implementation details of the `--revert` option itself. The exchange maintains the patch's focus on server-side operations while introducing an alternative approach worth considering for bulk reverts.
