Junio C Hamano (Git maintainer) weighs in on the `git clone -c` whitespace parsing regression discussion, agreeing with Jeff King's technical analysis but expressing some hesitation about the path forward.

This is part of an ongoing thread about unexpected whitespace handling in `git clone` config arguments. The discussion has established that the pre-v2.52.0 behavior (trimming whitespace in `-c ' key=value'` forms) was technically incorrect according to Git's config specifications, though it had worked since 2010.

Junio acknowledges Jeff's explanation that the old behavior resulted from parsing the "stuck form" of short options (`-c' key=value'`), which preserves whitespace in the value. While initially unsure, Junio now agrees the current behavior is technically correct, though he notes stripping whitespace could be seen as a usability feature in this specific case.

The email reveals some tension between technical correctness and backward compatibility. Junio considers but dismisses the idea of temporarily restoring the old behavior with a deprecation warning, seeing it as unnecessary engineering overhead for what was essentially a bug. The discussion appears to be converging on accepting the behavior change as a documentation correction rather than a regression, though Junio's "I dunno" suggests some remaining ambivalence about the user impact.
