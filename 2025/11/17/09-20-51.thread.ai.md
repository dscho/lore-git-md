Thread identity: Bug report about `git submodule` behavior with `--single-branch` when initializing submodules with branch specifications in `.gitmodules`.

Core problem: When initializing a submodule with `--single-branch` where `.gitmodules` specifies a branch (e.g. scarthgap), Git correctly checks out the specified commit (b33a8abe in example) but incorrectly sets remote tracking to HEAD (master) rather than the configured branch. This causes subsequent `git submodule update --remote` operations to fail as they cannot find the expected remote branch (refs/remotes/origin/scarthgap).

Current status: Bug is reproducible across Git versions from 2.47.3 through current master (2.52.0.rc2). No fixes or workarounds have been proposed yet. The issue appears to be in the interaction between submodule initialization and single-branch cloning logic.

Key technical details: The bug manifests in the submodule initialization sequence where:
1. The clone fetches correct commit (FETCH_HEAD points to b33a8abe)
2. Tracking configuration incorrectly defaults to remote HEAD (master)
3. Subsequent operations fail when looking for the specified branch
4. Affects both checkout and update operations in submodules

Open questions: 
- Is this a regression or long-standing behavior?
- Should `--single-branch` respect `.gitmodules` branch specifications?
- What is the correct fix location - submodule.c or clone/fetch logic?
