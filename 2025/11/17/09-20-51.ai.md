This is a bug report about `git submodule` behavior with `--single-branch`. The issue occurs when initializing a submodule that has a branch specified in `.gitmodules` - while the initial checkout correctly uses the specified commit (b33a8abe in the example), the remote tracking is incorrectly set to HEAD (master) rather than the configured branch (scarthgap). This causes subsequent `git submodule update --remote` operations to fail since they can't find the expected remote branch.

The problem is reproducible across Git versions (2.47.3 through current master 2.52.0.rc2). The reporter provides clear reproduction steps showing the discrepancy between the expected branch tracking (scarthgap) and actual behavior (master). The impact is that submodule updates fail when trying to sync with the remote repository.

Key technical details:
- The bug manifests in the interaction between `--single-branch` and branch specifications in `.gitmodules`
- The initial clone fetches the correct commit (FETCH_HEAD points to b33a8abe) but sets up wrong tracking
- Subsequent operations fail when looking for refs/remotes/origin/scarthgap
- Affects both checkout and update operations in submodules

The report is well-documented with concrete examples and version information, suggesting this is a legitimate bug rather than user error. The behavior contradicts what one would expect when specifying a branch in `.gitmodules`, making this likely to be accepted as a real issue needing fixing.
