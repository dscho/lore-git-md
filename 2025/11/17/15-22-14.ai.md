This is a follow-up in the submodule gitdir path encoding series, addressing deployment concerns raised by Josh Steadmon from Google's experience with their internal implementation. Adrian Ratiu responds to two key migration challenges: the inability to automatically enable the new `extensions.submoduleEncoding` for existing repositories, and the desire to set this by default for new repositories without command-line flags.

The main technical proposal is a build-time configuration option that would force-enable the extension, avoiding the need for downstream patches while solving both migration scenarios. Adrian confirms plans to add test coverage for backward compatibility (disabling the extension after use) in the upcoming v5 series. The response maintains the technical approach while offering a practical solution for large-scale deployments, though it doesn't address the core limitation that repository extensions can't be set via distributed configs.

Key technical details include:
- Continued use of `extensions.submoduleEncoding` as the opt-in mechanism
- Build-time configuration as a migration workaround
- Planned test expansion in t7425-submodule-encoding.sh
- No changes to the underlying encoding scheme or `submodule_name_to_gitdir()` resolution

The exchange shows the series transitioning from design validation to deployment planning, with Google's real-world experience informing the final implementation details before the feature stabilization.
