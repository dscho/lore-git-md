This is a feature proposal for adding an optional versioning system to Git, distinct from tags and branch names. The author, Skybuck Flying, suggests creating a new subsystem that would allow commits to carry explicit version identifiers (like decimal numbers or semantic versions) through either commit headers, dedicated refs, or new object types. The system would be entirely opt-in and disabled by default to avoid disrupting existing workflows.

The proposal outlines several potential benefits, including standardized version tracking for builds and CI, easier reproducible builds, and reducing reliance on custom branch naming conventions. The author presents three technical approaches for storing version information and suggests new porcelain commands like `git version` and `git version bump`. Key open issues include whether automatic version incrementing should be core functionality and how to store the version data without disrupting Git's existing object model.

The RFC is well-structured and clearly motivated, though it raises significant design questions about how versioning would interact with Git's immutable data model and existing version-tracking mechanisms like tags. The proposal is explicitly framed as early-stage discussion, with no patches yet submitted, to gauge community interest before investing in implementation work. This seems like a thoughtful exploration of whether Git's minimalism around versioning is a strength to preserve or a gap to address.
