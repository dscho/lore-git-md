This thread began with Johannes Schindelin proposing a simple fix to include the `scalar` command in the `make strip` target, but Junio Hamano saw an opportunity for broader Makefile improvements around artifact handling. Junio proposed restructuring how build artifacts (both programs and DLLs) are categorized and processed, introducing a new `OTHER_ARTIFACTS` variable alongside the existing `OTHER_PROGRAMS`.

In the latest response, Johannes agrees with Junio's Makefile approach but raises important questions about build system consistency. He notes that meson already handles stripping automatically, while CMake lacks stripping support entirely - a gap he attributes to CMake's focus on Windows/Visual Studio workflows. More significantly, Johannes suggests potentially abandoning CMake support altogether, given meson's adoption as the modern build system and CMake's failure to meet Visual Studio debugging needs.

The discussion now has two tracks moving forward: the immediate Makefile changes (where consensus appears to be forming) and the larger question of CMake's future role. While the technical details of the Makefile restructuring seem straightforward, Johannes' suggestion to drop CMake could prove controversial, particularly for Windows developers who rely on it. The thread remains active with these architectural questions still open.
