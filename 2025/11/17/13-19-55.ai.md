This is a feature proposal for adding an optional versioning system to Git, distinct from tags and branch names. The author suggests this could provide a standardized way to track and increment versions that survives operations like rebase and cherry-pick, while remaining entirely opt-in to avoid disrupting existing workflows.

The proposal outlines three potential technical implementations: commit headers, dedicated refs, or new object types. It also sketches new porcelain commands for version management. Key claimed benefits include better scriptability, reproducible builds, and reducing ad-hoc versioning solutions. The RFC explicitly asks whether there's community interest in such a feature before proceeding with implementation.

The proposal is thoughtfully structured with clear separation of concerns from existing Git features, and acknowledges the philosophical questions around adding mutable metadata. However, it lacks concrete examples of pain points from current versioning approaches that this would solve, and doesn't address how this would interact with bisect, blame, or other history-sensitive operations. The storage approaches would have non-trivial implications for Git's object model and interoperability.
