This is a discussion contribution in the ongoing `git worktree` documentation thread, specifically addressing the debate about nested worktree usage.

Johannes Schindelin weighs in with a practical counterpoint to Eric Sunshine's position that nested worktrees are technically sound. He shares a concrete experience where following the "worktrees outside main worktree" advice led to data loss - when he cleaned up his main worktree after checking `git status`, he accidentally orphaned a nested worktree containing important work. This real-world example strengthens the case for nested worktrees by showing how the alternative can be more dangerous in practice.

The email doesn't introduce new patches but provides valuable maintainer perspective on the nested worktree debate. Schindelin's experience suggests that while nested worktrees may have some gitignore management overhead (as noted earlier in the thread), the alternative workflow carries its own risks that may be more severe. This moves the discussion beyond theoretical pros/cons to actual user experience consequences.

The thread remains at an impasse between documentation approaches, but this contribution from a long-time Git contributor adds weight to the argument that warning against nested worktrees might be counterproductive. It also highlights how documentation decisions can have real-world consequences for users' workflows and data safety.
