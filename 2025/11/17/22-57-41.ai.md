This is a maintainer response in the ongoing `git worktree` documentation thread, specifically addressing Johannes Schindelin's real-world example of data loss from non-nested worktrees. Junio Hamano acknowledges the severity of the case where deleting the main worktree orphaned a secondary worktree containing important work, while considering the tradeoffs in Git's design.

The email makes several key technical points:
1. Confirms there's no practical way to prevent `rm -fr` from deleting the main worktree while secondary worktrees exist
2. Notes that while `git worktree list` could have revealed the secondary worktree, this violates the principle of worktree independence
3. Explores the tension between safety (wanting `git status` to show all worktrees) and worktree isolation (keeping worktrees independent)
4. Suggests the traditional recommendation against nesting worktrees was primarily to prevent accidental `git add` of worktree contents, which is less severe than data loss

This response effectively validates Schindelin's safety argument for nested worktrees while maintaining Git's design philosophy of worktree independence. The discussion appears to be converging toward removing the documentation warning against nested worktrees, with the remaining debate being how to best document the tradeoffs between nested and non-nested approaches. The email doesn't propose specific documentation changes but provides important context that will inform the final wording.
