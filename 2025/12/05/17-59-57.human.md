Performance optimization follow-up for promisor object handling, focusing on memory management details.

Jeff King responds to Aaron Plattner's measurements showing minimal memory impact from commit buffer cleanup in promisor object processing. He explains that the test case (`git rev-list --objects`) already disables commit buffer saving by default, making the memory difference negligible in this specific scenario. 

He suggests alternative test commands that would better demonstrate the memory impact, like using `--format=%s` which forces commit content loading. Jeff also connects this to his earlier proposal about using `parse_object_with_flags()` with `PARSE_OBJECT_SKIP_HASH_CHECK` - that approach would avoid loading commit contents when commit-graph is available, making the buffer cleanup mostly redundant in those cases.

The email maintains a technical but practical tone, acknowledging that while the immediate memory savings are small, proper cleanup might still be worth including for cases not covered by commit-graph optimizations. Jeff contrasts two implementation approaches (immediate freeing vs. temporary global flag disabling) without strong preference, noting both are reasonable given the context.

This continues the thread's focus on optimizing promisor pack handling while showing how different test scenarios can reveal or hide particular performance characteristics. The discussion remains focused on implementation details rather than introducing new architectural concerns.
