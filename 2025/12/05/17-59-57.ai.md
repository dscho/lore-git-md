Performance optimization follow-up for promisor object handling, focusing on memory management refinements.

Jeff King responds to Aaron Plattner's measurements showing minimal memory impact from commit buffer cleanup in promisor object processing. He explains that the test case (`git rev-list --objects --all --exclude-promisor-objects`) doesn't trigger the optimization because rev-list already disables `save_commit_buffer` by default. He suggests alternative test commands that would better demonstrate the effect, like using `--format=%s` to force commit content loading.

The email discusses two approaches to managing commit buffers: Aaron's direct `free_commit_buffer()` call after parsing, and Jeff's alternative suggestion from earlier in the thread to use `parse_object_with_flags()` with `PARSE_OBJECT_SKIP_HASH_CHECK` which would avoid loading commit contents when commit-graph is available. Jeff notes that even with his preferred approach, keeping the explicit buffer freeing might still be valuable for commits not covered by the commit-graph.

Jeff references prior art in `ref-filter` (commit 359b01ca84) that temporarily unsets `save_commit_buffer` during traversals, but suggests the current direct freeing approach may be simpler for this custom traversal code. The discussion remains focused on fine-tuning the memory management aspect of the performance optimization, with Jeff providing context about when and how different approaches would show benefits.
