This is a technical discussion about debugging stale Git locks, specifically addressing concerns around PID file naming conventions and implementation constraints.

Patrick Steinhardt weighs in on the ongoing debate about how to track process IDs for lockfiles. He agrees with earlier concerns that the proposed `.lock.pid` suffix would cause problems for the files reference backend, particularly with compatibility for alternative Git implementations and older versions. While he sees some merit in the debugging concept, he questions whether introducing a repository extension (as a potential solution) would be worth the complexity for the limited benefit.

Steinhardt suggests two approaches: either adding a toggle to let callers opt out of PID file creation (though this might reduce the feature's usefulness since ref operations are the main source of lock issues), or an unconventional solution of appending PID information directly to loose reference files (despite this triggering existing fsck warnings). The discussion continues to balance debugging utility against implementation constraints, with no clear resolution yet. The thread remains focused on finding a solution that works across all Git implementations while maintaining backward compatibility.
