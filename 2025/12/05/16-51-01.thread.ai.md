Thread identity: feature proposal from Cedric Sodhi about adapting Git to version control structured data (databases) rather than just filesystems.

Core problem: Git currently versions filesystem-based working directories, but many users need version control for structured data with schemas (databases). The choice between structured data and version control is currently forced. The proposal explores whether Git could be extended to handle database contents directly.

Current status: Initial proposal stage, no implementation. Two approaches suggested: (1) FUSE-based filesystem mapping (would let existing Git work but with performance overhead) or (2) modifying Git's backend to directly read database contents (would require architectural changes to handle mixed data types).

Key technical details: Focuses on Git's data model limitations with structured data. FUSE mentioned as possible integration path. Performance concerns with FUSE approach. Mixed-data handling (files + database records) identified as challenge for direct backend modification approach.

Open questions: Which approach is more promising? Are there other integration strategies? What would the community support? How to handle performance and mixed-data cases?

Participant positions: Only author (Cedric Sodhi) so far, seeking feedback on direction.

Related work: None mentioned yet, but likely connects to prior discussions about Git's data model and ODB abstraction work.
