Feature proposal discussion about multi-branch commit handling in `git-history`.

Elijah Newren raises significant concerns about the current implementation's handling of commits that exist in multiple branches, arguing this mirrors what he considers a fundamental design flaw in `git rebase`. The core issue is whether `git-history` should by default modify commits that are ancestors of multiple branches, potentially causing unexpected divergence.

Newren strongly advocates for one of three alternative approaches: (1) erroring out when a commit is in multiple branches unless explicitly allowed, (2) requiring explicit flags to specify multi-branch behavior, or (3) rewriting all affected branches by default. He warns that the current "current-branch-only" approach risks becoming entrenched behavior that will be hard to change later, even if marked experimental.

Patrick Steinhardt maintains the current behavior is intentional, citing his own workflow where commits exist on multiple dependent branches but should only be edited on the current branch. He raises practical concerns about the performance impact of checking all references for multi-branch cases, especially with long-lived release branches.

This represents a fundamental philosophical difference in history editing approaches - Steinhardt prioritizes predictable single-branch operations while Newren emphasizes maintaining branch relationships. The discussion highlights tension between Git's conservative defaults and more aggressive history editing capabilities inspired by tools like Jujutsu. The resolution of this debate will significantly impact the command's usability for complex branch topologies.
