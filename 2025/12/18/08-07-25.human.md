This is a technical discussion about the PID file naming scheme for debugging stale locks, part of an ongoing thread about lockfile improvements. Patrick Steinhardt raises concerns about the current naming approach ("foo-pid.lock") potentially conflicting with legitimate refnames like "foo-pid" in rare cases. He suggests an alternative using forbidden refname characters (e.g., "foo:pid.lock") but notes this comes with tradeoffs: increased filesystem operations and more cleanup risk from crashes.

The email highlights two key tensions: 1) the need for a naming scheme that won't collide with refnames while remaining ignorable by other Git implementations, and 2) the performance and reliability implications of writing additional PID files. Patrick leans toward making this feature opt-in rather than default due to these costs, though he acknowledges the debugging benefits. The discussion appears to be moving toward weighing these implementation details rather than questioning the core functionality, which seems generally accepted.
