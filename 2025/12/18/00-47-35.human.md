This is a follow-up in the lockfile debugging thread, where Junio Hamano provides design feedback on Paulo Casaretto's v2 patch for PID-based lockfile tracking. The discussion has progressed from initial implementation details to higher-level API and compatibility concerns.

Junio raises two key points about the proposed `core.lockfilePid` configuration. First, he notes that repository extensions (rather than plain config) are Git's established mechanism for signaling features that older versions shouldn't touch, suggesting `extensions.lockfilePID` would be more appropriate. Second, he points out the naming inconsistency in using mixed case with the all-caps "PID" acronym, recommending `lockfilePID` throughout.

The feedback shows the patch is nearing readiness but needs these design adjustments to align with Git's conventions. Junio's comments focus on backward compatibility (how older Git versions should behave when encountering these files) and naming consistency - both important considerations for production use. The thread continues to refine what started as a debugging feature into something that must properly integrate with Git's existing versioning and configuration systems.
