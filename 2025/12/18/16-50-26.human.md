This is a bugfix and behavior change for the experimental `git replay` command, now at version 4 of the patch series. The change makes `git replay` drop commits that become empty during replay (when their changes already exist in the target branch), matching the behavior of `git rebase --reapply-cherry-picks --empty=drop` and `git cherry-pick --empty=drop`. Originally-empty commits are preserved.

The implementation compares tree OIDs to detect empty commits, updates branch pointers when tip commits are dropped, and includes test coverage. The documentation is updated to clarify the new behavior. Phillip Wood acknowledges this is a breaking change but notes `git replay` is marked experimental to allow such improvements. The patch has already received positive feedback from Elijah Newren and Junio Hamano, with all technical issues resolved in previous versions.

The v4 change is minor - removing an unnecessary `--only` flag when creating an empty commit in the test. The patch is based on Phillip Wood's `ps/history` branch and appears ready for inclusion, with the maintainer having previously endorsed the core approach. The test case demonstrates how branch `topic1` updates when commit `F` is dropped because its changes already exist upstream.
