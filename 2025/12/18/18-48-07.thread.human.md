This thread discusses Matthew Hughes' RFC proposal to add a `maintenance.configFile` option that would let users specify an alternate config file for git-maintenance operations, similar to how `-c`/`GIT_CONFIG` work for general Git config but scoped to the maintenance subsystem. The initial implementation modifies `builtin/gc.c` and includes tests in `t/t7900-maintenance.sh`.

Patrick Steinhardt provided the first round of feedback, raising important considerations about whether git-maintenance should automatically handle config file inclusion, pointing out code style issues, and identifying gaps in scheduled maintenance support via `git for-each-repo`. He also proposed extending `for-each-repo` with a `--file` option and raised follow-up questions about service file updates and config migration paths.

Junio Hamano has now weighed in with a detailed maintainer review. While not rejecting the proposal, he questions whether a maintenance-specific solution is the right approach, suggesting a more general read-only base config with writable overlays might better serve the stated use case of version-controlled global configs. His review identifies several technical issues: the commit message needs clearer problem/solution framing, there are code style violations to address (NULL check syntax, brace usage, line wrapping), and the test script has portability concerns and could better verify config isolation. Junio's feedback provides concrete guidance for improving the patch while encouraging the author to reconsider the design approach.

Key open questions include whether to proceed with the maintenance-specific solution or pursue a more general config overlay approach, how to handle the technical implementation details Junio highlighted, and how to address Patrick's earlier points about scheduled maintenance integration. The thread remains active with the ball in Matthew Hughes' court to respond to this feedback.
