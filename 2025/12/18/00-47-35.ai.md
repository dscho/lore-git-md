This is a follow-up in the lockfile debugging thread, focusing on repository compatibility and configuration naming conventions. Junio Hamano responds to Paulo Casaretto's v2 patch implementing PID-based lockfile tracking, raising two key technical points about the design.

First, he identifies a version compatibility issue: older Git versions won't respect the new `.pid.lock` files, potentially causing interference during concurrent operations. He suggests using a repository extension (`extensions.lockfilePID`) instead of a config variable, as unknown extensions trigger a safety check in `verify_repository_format()` that would prevent older Git versions from operating on the repository.

Second, he critiques the configuration variable naming. While noting that multi-word configs typically use CamelCase, he points out that "PID" (as an acronym) should remain all-caps, making `core.lockfilePid` inconsistent. He suggests `core.lockfilePID` would be more appropriate, and this naming would naturally carry over to the proposed extension version.

The email doesn't introduce new functionality but rather focuses on hardening the implementation against edge cases (older Git versions) and aligning with Git's naming conventions. These are maintainer-level concerns about long-term maintainability rather than fundamental objections to the feature itself. The suggestions appear aimed at making the change more robust and idiomatic before final acceptance.
