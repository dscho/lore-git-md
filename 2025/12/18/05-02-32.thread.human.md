This thread discusses a proposal to add a `--snapshot` option to `git commit` that would create timestamped copies of staged files before committing. The initial implementation would store these copies in `.git/snapshots/` with names based on the commit message.

The proposal is facing significant pushback from experienced contributors. Phillip Wood first questioned whether this feature makes sense conceptually, since Git's entire model is already built around commits as snapshots. Chris Torek has now expanded on those concerns with technical analysis, pointing out that the current implementation (1) duplicates functionality Git already provides efficiently through tree objects, (2) makes incorrect assumptions about staged files, and (3) wastes space compared to Git's native storage. Both suggest that if there's a real need being addressed, it would be better served through temporary branches or stash-like commits rather than copying files.

The original author has not yet responded to these fundamental concerns or provided clear use cases justifying why this feature is needed. The discussion currently lacks any demonstrated need that isn't already well-covered by Git's existing capabilities. Technical implementation quality has also been questioned, particularly around error handling and the use of shell commands where Git's internal APIs would be more appropriate.

Unless the proposer can articulate compelling use cases that Git's current model doesn't address, this feature appears unlikely to move forward in its current form. The technical feedback suggests that any similar functionality would need to be redesigned to work with Git's object model rather than against it.
