This is a v4 patch in the `git replay` behavior discussion, focusing on dropping commits that become empty during replay. The patch modifies the experimental `git replay` command to automatically drop commits whose changes already exist in the target branch, matching the behavior of `git rebase --reapply-cherry-picks --empty=drop` and `git cherry-pick --empty=drop`.

The key technical changes are in `replay.c` where it now compares tree OIDs to detect empty commits, preserving only originally-empty commits while dropping those that become empty during replay. The patch also handles branch pointer updates when tip commits are dropped and adds test coverage in t3650. The documentation is updated to reflect this new behavior.

Notable implementation details:
- Uses `oideq()` for tree comparison between `replayed_base_tree` and result tree
- Preserves branch pointer updates when dropping commits (shown in test case where topic1 updates to point to rebased C when F is dropped)
- Test case demonstrates the behavior with `--ancestry-path` and `--branches` options
- Removes `--only` flag from test case commit creation (was a test authoring preference in v3)

The patch has evolved through four versions with all technical feedback addressed:
- Junio C Hamano suggested punctuation improvements (v2)
- Elijah Newren recommended test simplifications (v1)
- Final clarification about test authoring style resolved (v4)

The thread shows consensus on the technical approach, with the maintainer and other contributors approving the implementation. The only remaining open question is whether to add a future option to retain empty commits, but this is deferred as the current behavior is considered the sensible default for the experimental command. The patch is based on Phillip Wood's `ps/history` branch and appears ready for inclusion.
