This is the second and final patch in a v2 series implementing HTTP 429 (rate limiting) retry support for Git's HTTP client. The patch focuses on adding detailed trace2 instrumentation to monitor retry operations.

The instrumentation tracks several key aspects of rate limit handling:
- Retry attempt numbers (http/429-retry-attempt) to show progression through the retry sequence
- Server-provided Retry-After values (http/429-retry-after) from 429 responses
- Actual sleep durations (http/retry-sleep-seconds) within trace2 regions
- Error conditions like retry exhaustion or exceeded time limits (http/429-error)
- Source of retry delays (server header vs config default)

The implementation adds trace2 calls at strategic points in the retry logic flow - when starting a retry attempt, when checking retry limits, when sleeping, and when encountering various error conditions. The trace2 data uses both integer (intmax) and string values appropriately for different metrics.

This complements the core retry functionality from patch 1 by providing observability into real-world rate limiting scenarios. The instrumentation will help operators understand retry patterns, diagnose failures, and tune configuration based on actual behavior. The patch maintains consistency with Git's existing trace2 patterns and integrates cleanly with the retry infrastructure added in the first patch.

Key technical details:
- Adds trace2 calls in http.c at critical points in the retry flow
- Uses standard trace2 patterns (data_intmax, data_string, regions)
- Documents all new trace2 events in the commit message
- Maintains clean separation from core retry logic
- Follows same error handling patterns as rest of series

The patch appears well-structured and focused, adding valuable debugging capabilities without complicating the core retry logic. It completes the series by providing the observability layer that makes the feature operational in production environments.
