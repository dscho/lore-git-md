This thread documents a regression in `git subtree` functionality that appeared in Git 2.52.0, where squashed subtree operations that worked in 2.51.1 now fail with non-fast-forward errors. The issue stems from commit 83f9dad7d6, which changed how subtree split commits are detected during history reconstruction.

The original reporter has provided detailed analysis showing the problem occurs when pushing subtree changes, particularly with squashed subtree histories. They've identified that the new version examines only immediate commits while the old version traversed ancestry, leading to broken parent links in the reconstructed history. A reproduction case was demonstrated using the Athena Framework monorepo.

In the latest update, the reporter notes they're seeing a new error ("could not rev-parse split hash") in some cases, suggesting the issue's behavior may vary with repository history depth. They're working to create a minimal test case starting from scratch rather than relying on the Athena monorepo, and have requested testing on Git 2.43.7 to establish baseline behavior. The discussion remains focused on precisely understanding the regression's boundaries to inform whether commit 83f9dad7d6 should be modified or reverted. No solutions have been proposed yet, but the methodical investigation continues.
