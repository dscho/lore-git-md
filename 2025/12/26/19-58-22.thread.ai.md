Thread identity: Bug report and proposed fix for regression in `git subtree` functionality when pushing subtree changes, specifically affecting squashed subtree operations that worked in Git 2.51.1 but fail in 2.52.0.

Core problem: A regression introduced in Git 2.52.0 (by commit 83f9dad7d6 "subtree: fix split after annotated tag was squashed merged") causes subtree push operations to fail when dealing with squashed subtree histories. The issue stems from changes in how subtree split commits are detected, where the new version fails to properly traverse ancestry for linear squash commits. The follow-up patch series now addresses both the original regression and a separate "recursion depth exceeded" bug on Debian/Ubuntu systems.

Key technical details:
- Affects `git subtree` operations where subtrees were added with `--squash`
- Specifically impacts history reconstruction during subtree operations
- `should_ignore_subtree_split_commit()` heuristic fails for rebased/cherry-picked squash commits due to incorrect parent assumptions
- Current implementation assumes squash commits will either have no parents or only parents that are also squash commits
- Final solution completely removes the problematic heuristic rather than trying to fix it
- GPG signing support added in Git 2.51.0 may affect commit verification expectations
- Tree objects remain identical between working/broken cases
- Minimal reproduction script demonstrates both the regression and recursion depth issues
- Performance impact confirmed (regression is both functional and performance)
- Verified working in Git 2.43.0 (pre-dating problematic commit)
- Testing shows fixed version runs 3x faster than original working version (10.8s vs 33.0s) and nearly 2x faster than broken version (10.8s vs 18.7s)
- Performance improvement confirms heuristic was both incorrect and a bottleneck
- Tested on real-world repository (clock component subtree split) and Athena Framework monorepo
