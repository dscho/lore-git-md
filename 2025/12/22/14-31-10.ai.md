This is a feature proposal and discussion starter about improving merge conflict metadata and user experience, particularly around rebase operations. The email comes from a Rust compiler developer who has implemented enhanced conflict marker diagnostics in rustc and is seeking better ways to expose Git's internal state.

The author describes their current rustc implementation that detects conflict markers and provides contextual help by:
1. Using `git rev-parse --git-path rebase-merge` to find rebase metadata
2. Extracting branch names from Git's internal files and via `git branch --points-at`
3. Providing tailored error messages showing which branches/commits are involved in the conflict

Key technical points raised:
- Current approach has performance concerns with `--points-at` in large repos
- Some useful metadata (like rebase-onto branch name) isn't directly available
- Distinguishing between rebase-vs-pull operations isn't straightforward
- The proposal suggests Git could expose more metadata to help tools provide better UX

The email raises several questions about Git internals:
1. Whether there are better ways than `--points-at` to identify rebase-onto branches
2. How to reliably detect if a rebase was triggered by `git pull`
3. Whether Git would consider adding more metadata exposure

The author also floats the idea of modifying Git's conflict marker output to include more contextual information by default, while acknowledging potential verbosity concerns for experienced users. The proposal comes from observed user confusion around conflict resolution in various Git operations (rebase, pull, merge, stash).
