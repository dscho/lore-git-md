This is a technical discussion in the ongoing `git-history` command RFC thread, focusing on branch selection strategy for history rewriting operations. Phillip Wood responds to Patrick Steinhardt's proposal to implicitly define the rewrite range as commits between the target commit and HEAD (similar to `git rebase --update-refs`).

Wood expresses skepticism about Steinhardt's scaling concerns regarding walking all branches to find descendants of the target commit. He argues that in practice, most refs are tags or remote branches, leaving a manageable number of local branches to process. He also notes the target is likely recent, allowing quick pruning of older branches during the walk.

The key disagreement centers on rewrite behavior: Steinhardt's HEAD-to-commit approach would only update branches pointing into the implicit range (like rebase), while Wood advocates rewriting all descendant branches for consistency. Wood finds the rebase-like behavior potentially confusing for users expecting comprehensive history updates.

This continues the thread's core debate about branch selection strategy, with Wood aligning more closely with Elijah Newren's earlier arguments for comprehensive branch walking while offering additional practical observations about repository ref distributions. The exchange highlights the need to balance implementation complexity against user expectations for predictable history editing behavior.
