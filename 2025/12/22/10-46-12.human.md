This is a technical discussion in the ongoing `git-history` command RFC thread, focusing on branch selection strategy for history rewriting operations.

Phillip Wood responds to Patrick Steinhardt's proposal to implicitly define the rewrite range as commits between the target commit and HEAD (similar to `git-replay`'s approach). Wood expresses skepticism about this approach, arguing it would behave more like `git rebase --update-refs` rather than rewriting all descendant branches as intended.

Wood makes two key technical points: First, he questions Steinhardt's scaling concerns about walking all branches, noting that most refs in large repositories are tags or remote branches, leaving a manageable number of local branches to process. Second, he argues the HEAD-to-target walk would create confusing inconsistency by missing some descendant branches, preferring comprehensive branch walking instead.

The exchange highlights a core design tension in the `git-history` proposal - balancing simplicity and performance against complete and predictable behavior. Wood's position aligns with Elijah Newren's earlier arguments for comprehensive branch walking, though he focuses more on user experience implications than implementation details. This keeps open the fundamental question of how to best define the scope of branches affected by history editing operations.
