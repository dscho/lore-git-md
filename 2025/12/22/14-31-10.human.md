This is a feature proposal and discussion starter about improving merge conflict diagnostics, particularly how Git could expose more metadata to help tools like rustc provide better error messages during rebase conflicts.

Esteban Küber, a rustc developer focused on developer experience, explains how rustc currently detects and explains merge conflict markers in code. They've implemented a solution that uses Git's rebase metadata to provide more context about which branches are involved in the conflict, but it requires workarounds like scanning branch tips with `git branch --points-at`, which can be inefficient.

The email shows before-and-after examples of rustc's conflict marker diagnostics, demonstrating how branch names make the output more helpful. However, the current approach doesn't cover all cases (like `git stash pop` or `git merge` conflicts) and has performance concerns with large repositories.

Key questions raised:
1. Is there a better way than `--points-at` to identify the branch being rebased onto?
2. Can Git distinguish between rebases triggered by `git rebase` vs `git pull`?
3. Would Git consider adding this metadata explicitly for both third-party tools and its own UI?

The proposal also floats the idea of modifying Git's conflict marker output to include more context by default, though acknowledges potential verbosity concerns for experienced users. The email seeks feedback on these ideas from the Git community.
