User perspective on multi-branch handling for git-history. Matthias Beyer responds to Phillip Wood's question about branch rewriting preferences in the git-history command discussion, advocating for explicit rather than automatic multi-branch operations.

Matthias clarifies his earlier position on the multi-branch commit handling debate, explaining his user perspective that favors simple, explicit operations by default. He reiterates his expectation that the tool should only rewrite commits on the current branch unless explicitly instructed otherwise via a command-line flag. This aligns with his previous comments in the thread where he expressed concerns about automatic rewriting of multiple branches.

The response emphasizes a design philosophy prioritizing explicit user control over "magic" automatic behavior, even when that behavior might be more convenient in some cases. Matthias doesn't raise technical objections to multi-branch rewriting but rather expresses a preference for conservative defaults that require explicit opt-in for more powerful operations. This position contrasts with some other participants who advocate for more automatic multi-branch handling (like Elijah Newren's option c) but aligns with Patrick Steinhardt's current implementation approach.

The email doesn't introduce new technical considerations but reinforces the user experience aspect of the ongoing design debate, particularly around the principle of least surprise.
