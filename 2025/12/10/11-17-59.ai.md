This is a platform compatibility discussion regarding the macOS iconv workaround, specifically addressing the tradeoffs of using Homebrew's libiconv versus system libraries.

Carlo Marcelo Arenas Belón raises concerns about René Scharfe's proposed solution of defaulting to Homebrew's libiconv on macOS. The key objection centers on binary compatibility - when building universal (fat) binaries targeting multiple macOS architectures, system libraries may be preferred over Homebrew versions for consistency. This could reintroduce the iconv behavior issues the patch aims to fix.

The email suggests an alternative approach: introducing a `NO_HOMEBREW` Makefile flag, analogous to existing flags for other package managers like Fink and MacPorts. This would give users explicit control over whether to prefer Homebrew libraries, addressing cases where universal binary compatibility or other constraints make system libraries preferable despite their known issues.

The discussion continues the thread's exploration of solution tradeoffs, now considering deployment and packaging implications beyond the core technical fix. This represents a shift from the previous focus on in-code workarounds and platform detection mechanisms to broader ecosystem considerations. The suggestion of a `NO_HOMEBREW` flag introduces a new dimension to the solution space that may need evaluation alongside the existing code-based and build-system approaches.
