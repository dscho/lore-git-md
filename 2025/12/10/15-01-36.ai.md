This is a feature proposal for safer behavior in `git reset --hard` when dealing with uncommitted staged changes.

The RFC suggests adding a warning and requiring `--force` when `git reset --hard` would discard staged content that has never been committed to any branch. The motivation comes from a potentially destructive scenario where users initialize a new repository, stage files, then accidentally wipe them before ever committing. While the blobs remain temporarily as dangling objects, the filenames are lost and most users wouldn't know how to recover them.

The proposed behavior would print a warning listing the affected files and require explicit confirmation via `--force`. This aligns with Git's general philosophy of safer defaults for destructive operations. The author provides a clear reproduction case showing the current behavior and outlines the proposed warning message format. Two key questions are raised for discussion: whether the safety benefit justifies the added complexity, and whether there are legitimate workflows this might disrupt.

The proposal appears well-considered, addressing a real foot-gun scenario while maintaining the ability to force through when needed. The implementation would touch the reset command's safety checks and warning system. If accepted, this would be a user-visible behavior change that might warrant documentation updates to explain the new warning. The author expresses willingness to implement the change pending community feedback.
