This is a continuation of the debate about multi-branch commit handling in the proposed `git-history` command. Elijah Newren strongly opposes Patrick Steinhardt's current approach of only rewriting the current branch by default, calling it a repeat of what he sees as `git-rebase`'s fundamental design mistake. He outlines three alternative approaches (a-c) and makes clear this is a dealbreaker issue for him, going so far as to say he would actively recommend against using the command if merged in its current form.

The exchange reveals a philosophical divide: Patrick sees the current behavior as the simpler, more predictable default for most workflows, while Elijah argues it creates dangerous edge cases and wants either safety checks (a), explicit user choice (b), or multi-branch rewriting by default (c). Patrick shows some willingness to consider a hybrid of (a) and (b) if the reference checking can be made efficient, but notes git-replay (which Elijah worked on) took the opposite approach from the start by defaulting to multi-branch operations.

This email escalates the stakes in the ongoing discussion, with Elijah framing the current design as potentially making the command unusable in his view, while Patrick remains open to compromise solutions that don't degrade performance for simple cases. The thread now awaits input from other contributors and maintainers on this fundamental design question.
