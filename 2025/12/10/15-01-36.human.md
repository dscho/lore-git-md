This is a feature proposal for safer behavior in `git reset --hard`. The patch suggests adding a warning when the command would discard staged changes that have never been committed to any branch, requiring explicit `--force` to proceed.

The motivation comes from a common pitfall where users initialize a new repository, stage files, and then lose all their work with `reset --hard` before ever committing. While the blobs technically remain as dangling objects until garbage collection, this isn't practical recovery path for most users who won't know about `git fsck --lost-found`.

The proposed behavior would warn about files that exist only in the index (not reachable from any commit) and require confirmation, similar to Git's other safety mechanisms. The author acknowledges this adds some complexity but argues it's justified by preventing data loss, and invites discussion about potential workflow impacts.

The proposal seems well-reasoned and addresses a real footgun scenario, particularly for new users. The implementation would need to carefully consider edge cases (like partial staging) and whether the warning should be suppressible via config. The author appears open to feedback and willing to implement the change if the community agrees it's worthwhile.
