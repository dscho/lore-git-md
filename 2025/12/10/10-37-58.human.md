Feature proposal discussion for `git-history` command, focusing on multi-branch commit handling behavior.

Matthias Beyer weighs in on the ongoing debate about how `git-history` should handle commits that exist on multiple branches. He expresses a user perspective favoring conservative behavior by default, where operations would only affect the current branch unless explicitly told to do otherwise with a flag. This aligns with Patrick Steinhardt's current implementation approach but contrasts with Elijah Newren's argument for rewriting all containing branches by default.

Beyer's rationale centers on preferring explicit over implicit behavior, stating he doesn't "like too much magic" in tools. He suggests the simple case should be simple (affecting only current branch) while more extensive operations should require explicit flags. This echoes earlier concerns raised about workflow safety but frames them in terms of user expectations rather than technical constraints.

The email doesn't introduce new technical arguments but provides an important data point in the design discussion - a user perspective favoring conservative defaults. This comes as the thread has been largely dominated by developer perspectives on implementation tradeoffs. The exchange with Phillip Wood suggests this may influence how the team documents and positions the experimental feature's behavior.
