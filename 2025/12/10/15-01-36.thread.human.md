This thread discusses an RFC proposal to modify `git reset --hard` to warn about or prevent accidental loss of staged-but-uncommitted changes, which the command currently discards silently. The proposal suggests adding warnings or requiring `--force` for such cases, framing it as a safety improvement. 

Git maintainer Junio C Hamano has pushed back, noting that `--hard` has always been explicitly documented as destructive, and changing this behavior could disrupt established workflows. While open to discussion, Junio's position is that the current behavior is intentional. Eric Sunshine pointed out a minor wording issue in Junio's response, which was corrected, but this doesn't affect the core debate. 

The discussion has stalled, with no new technical arguments emerging. The proposal remains in RFC status, facing conceptual resistance from the maintainer. The broader question—whether Git should add more safeguards for destructive operations—remains unresolved, but for now, the status quo holds.
