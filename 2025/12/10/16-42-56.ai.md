This is a follow-up in the ongoing macOS iconv conversion issue thread, focusing on build system considerations. Torsten Bögershausen raises several practical concerns about René Scharfe's proposed Homebrew libiconv solution.

The email questions whether Homebrew's libiconv supports UTF-8-MAC encoding (a macOS-specific variant) and whether it passes the t3910 test suite. Torsten also notes his long-term use of MacPorts' libiconv and points out existing build switches (`NO_DARWIN_PORTS`, `NO_FINK`) for alternative package managers, suggesting a similar `NO_HOMEBREW` flag might be warranted.

This introduces new technical considerations to the Homebrew-based solution path:
- Compatibility with macOS-specific UTF-8-MAC encoding
- Test coverage implications (t3910 specifically)
- Parallels with existing package manager exclusion flags
- Potential need for explicit user control over Homebrew usage

The questions highlight gaps in the current proposal's coverage of real-world deployment scenarios, particularly regarding encoding support and existing build system patterns. This moves the discussion toward more comprehensive solution design that accounts for multiple package managers and their specific characteristics. The thread's technical scope now includes both the core iconv state handling and broader build system integration concerns.
