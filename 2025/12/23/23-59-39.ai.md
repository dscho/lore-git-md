This is a follow-up discussion in the ongoing feature enhancement thread about showing default branch comparisons in `git status`. The author Harald Nordgren responds to concerns raised by Yee Cheng Chin about the rigidity of the current upstream/origin fallback chain for determining the default branch.

Nordgren acknowledges the validity of the concerns regarding different workflow patterns, particularly for cases like detached HEAD states (gh-pages) and permanently forked version branches. He suggests making the feature opt-in rather than enabled by default, and proposes a more flexible configuration approach using `repo.settings.statusGoalBranch` (or similar) that would allow repository-wide settings while still permitting branch-specific overrides.

The email highlights the tension between the author's personal workflow (which clearly separates origin/master and origin/develop branches) and more complex scenarios involving multiple remotes or non-standard branch structures. Nordgren maintains that repository-level configuration is important for the feature's usefulness, while conceding that branch-level opt-outs would be necessary for special cases.

This continues the thread's exploration of how to balance the feature's utility against the diversity of Git workflows, with configuration flexibility emerging as a key requirement. The discussion remains focused on design decisions rather than implementation details at this stage.
