This thread explores enhancing `git status` to show configurable branch comparisons, originally proposed by Harald Nordgren to help track drift from mainline branches. The current v2 patch series introduces performance optimizations and improved memory management while maintaining the existing status output structure. Key participants include Junio C Hamano, who raised early concerns about triangular workflows, and Yee Cheng Chin, who identified issues with hardcoded remote preferences in multi-remote scenarios.

The discussion has shifted from implementation details to broader design questions about configurability. Brian m. carlson's latest contribution highlights additional cases where the current hardcoded remote name preferences ("upstream"/"origin") would fail, particularly with non-standard remote names or organizational naming conventions. This reinforces earlier concerns and suggests the need for either repository-wide configuration or per-user customization. The examples demonstrate real-world workflows where the current design would break down, including localization scenarios where non-English remote names might be preferred.

Open questions now focus on finding the right balance between flexibility and complexity, with particular attention to triangular workflows, multi-remote scenarios, and special branch handling. The thread shows consensus emerging around making the feature more configurable, though the exact mechanism remains under discussion - whether through repository settings, branch-specific overrides, or user-level preferences. The implementation will likely need to respect git configuration settings for remote naming while maintaining backward compatibility.
