Harald Nordgren's configurable branch comparison feature for `git status` has been merged, allowing users to compare against multiple branches through the new `status.compareBranches` setting. While the implementation is complete and tested, a significant design discussion has emerged about how branch names should be resolved.

The current implementation uses hardcoded remote-tracking branch prefixes, which works but limits flexibility. Junio Hamano has strongly advocated addressing this now rather than later, arguing the current approach could unintentionally lock in behavior that conflicts with Git's standard refname resolution rules. Jeff King (Peff) has now weighed in with technical proposals for more flexible alternatives.

Peff suggests two approaches: first, enhancing `repo_interpret_branch_name()` to properly handle `@{upstream}` and `@{push}` syntax relative to comparison branches rather than always using the current HEAD. Second, he proposes supporting dynamic pattern expansion (like "origin/%s") that could unify various branch naming conventions. Both solutions would maintain better consistency with Git's existing DWIM (Do What I Mean) ref resolution behavior.

The discussion has reached a decision point: keep the current restricted-but-simple remote-tracking behavior, or adopt more flexible resolution rules that would enable comparisons against any ref type (local branches, tags, etc.) while matching Git's standard lookup behavior elsewhere. While the feature works as merged, the maintainer and senior contributors are pushing to resolve this design question before the behavior becomes entrenched in real-world use.
