This is a patch in the experimental `git replay` series that changes its behavior to drop commits that become empty during replay (where changes already exist in the target branch), matching the behavior of `git rebase --reapply-cherry-picks --empty=drop`. The patch is now at v4 with all technical feedback addressed, including test simplifications and commit message improvements.

The implementation in `replay.c` compares tree OIDs to detect empty commits, preserving only originally-empty commits while dropping those that become empty during replay. It also properly updates branch pointers when tip commits are dropped. Test coverage in t3650 has been updated to verify the new behavior.

Maintainer Junio C Hamano indicates the patch is ready to be applied, though notes there's an open question about whether to base it on `master` branch or the experimental `ps/history` branch where it currently lives. The patch author Phillip Wood suggests this dropping behavior should be the sensible default, with the option to add a flag later if users need to retain empty commits.

All technical aspects appear resolved, with the implementation matching what Elijah Newren had independently developed. The thread shows consensus on both the approach and implementation details, with only the base branch decision remaining before final inclusion.
