This is a technical discussion in the ongoing RFC thread about the proposed `git-history` command, focusing on conflict resolution and branch update behavior in multi-branch rewrites.

Elijah Newren responds to Patrick Steinhardt's proposal to implicitly define commit ranges for branch rewrites as the commits between the target commit and HEAD. Newren strongly disagrees with this approach, arguing it violates the principle of least astonishment (POLA) by potentially leaving some dependent branches unmodified while others are rewritten. He sees this as creating inconsistent repository states that would surprise users.

Newren presents three alternative solutions that would avoid POLA violations: (1) rewrite all branches descending from the commit (with existing implementation available), (2) walk all dependent branches to warn users about multiple affected branches, or (3) require explicit user specification of rewrite scope through mutually exclusive flags. He dismisses performance concerns about branch walking as unlikely to be noticeable in practice, especially compared to the user experience costs of surprising behavior.

The email highlights a fundamental disagreement in the design philosophy - Steinhardt wants to optimize for simple UI by hiding complexity, while Newren prioritizes predictable behavior even if it requires more upfront user specification. This tension between implicit "magic" and explicit control has been a recurring theme in the thread. Newren's position aligns with his previous concerns about `git-rebase` behavior, suggesting he views this as a similar safety issue that needs addressing early in the design.
