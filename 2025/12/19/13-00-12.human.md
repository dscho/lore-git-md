This is a technical follow-up in the `git-history` feature series, specifically addressing implementation details of the `split` subcommand. Patrick Steinhardt responds to Phillip Wood's question about why the code forks a `read-tree` subprocess rather than using `unpack_trees()` directly or writing the index to disk in-process.

The exchange reveals that the current implementation's use of `read-tree` was inherited from other parts of Git that similarly interface with `run_add_p()`, which requires an on-disk index. Steinhardt acknowledges this as suboptimal and commits to changing the approach, indicating the code will be modified to handle the index operations more directly.

This email doesn't introduce new functionality but shows the kind of implementation refinement happening in response to code review. The change appears straightforward and uncontroversial, focused on internal plumbing improvements for the history editing feature.
