This is a feature proposal in the ongoing `git-history` command discussion, specifically addressing the multi-branch commit handling behavior. Patrick Steinhardt, the series author, is responding to the thread's consensus that automatically rewriting dependent branches is the preferred default behavior (matching `git-replay` and Jujutsu's approach).

The key development is Patrick's proposed solution to the technical challenge of identifying which branches to rewrite when operating on a single commit (rather than a range). He suggests implicitly using the range from the target commit to HEAD, which would maintain a simple user interface while enabling the desired multi-branch behavior. This would avoid requiring users to specify ranges when they only want to modify one commit.

Patrick indicates he's willing to revise his earlier position (which favored explicit, current-branch-only operations) if this approach is acceptable to others. The email shows the discussion moving toward resolution on this contentious point, with the author engaging constructively with feedback from Junio Hamano, Phillip Wood, and others. The proposed solution appears technically sound while preserving UI simplicity - a promising direction for this experimental history-editing feature.
