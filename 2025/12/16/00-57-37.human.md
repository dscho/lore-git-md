This is a technical explanation about Git's rename detection behavior during merges, clarifying why `git merge` doesn't diff branch endpoints directly.

Elijah Newren provides a detailed response to Luca Balsanelli's question about why rename detection appears to work differently between `git diff` and `git merge`. The key point is that merge operations fundamentally work by comparing each branch to their common ancestor (merge-base), not by comparing the branch tips directly. This explains why a rename might be visible in a direct `git diff` between branches but not during a merge.

Newren outlines several concrete problems that would arise if merges tried to diff endpoints directly: inability to determine rename direction, missing rename/rename conflicts, and semantic confusion about whether changes represent additions or removals. He emphasizes that this isn't about different diff machinery - both commands use the same underlying mechanisms, but with different comparison strategies due to their distinct purposes.

The explanation also touches on the specific case that prompted the question, where both branches modified a file so substantially that the new versions are similar to each other but not to the original, creating a potentially confusing scenario. This serves as a good example of why the three-way merge approach is necessary.
