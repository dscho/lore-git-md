This is a technical explanation of Git's merge rename detection behavior, clarifying why `git merge` doesn't diff branch endpoints directly. Elijah Newren provides a detailed response to Luca Balsanelli's question about apparent inconsistency between `git diff` and `git merge` rename detection.

The email authoritatively explains that merge operations fundamentally work by diffing each branch against the merge base, not the branch endpoints against each other. This is necessary to properly determine rename directionality and detect rename/rename conflicts. Several concrete scenarios are provided where endpoint-only comparison would fail: ambiguous rename direction (A->B vs B->A), hidden rename/rename conflicts (A->B and A->C appearing as B->C), and undetected content merges when unrelated files are renamed to the same name.

The response emphasizes this isn't a difference in diff machinery but rather a fundamental property of three-way merges - they must compare against the merge base to understand whether changes represent additions or deletions. The observed behavior where `git diff branch1 branch2` shows renames while `git merge` doesn't is therefore expected and correct, as merge is examining different commit pairs (base->branch rather than branch->branch).

This closes the technical investigation by confirming the behavior is intentional and explaining the underlying merge algorithm constraints.
