This is a feature patch for the experimental `git replay` command, now in its third version, that changes its behavior to drop commits that become empty during replay (where their changes already exist in the target branch). The change aligns `git replay` with the behavior of `git rebase --reapply-cherry-picks --empty=drop` and `git cherry-pick --empty=drop`.

The patch modifies the core replay logic in `replay.c` to detect empty commits by comparing tree OIDs, preserving only originally-empty commits while dropping those that become empty during replay. It also properly handles branch pointer updates when tip commits are dropped, demonstrated by a new test case showing how `topic1` is adjusted when commit `F` is dropped. The documentation is updated to reflect this new default behavior.

The implementation has received thorough review and approval from both the maintainer (Junio C Hamano) and other contributors (Elijah Newren). All technical feedback from previous versions has been addressed, with only minor punctuation improvements to the commit message remaining. The author notes this is a breaking change but justified by `git replay`'s experimental status, leaving room for a future option to retain empty commits if needed.

This version is based on Phillip Wood's `ps/history` branch and appears ready for inclusion, representing a well-vetted improvement to the experimental replay functionality.
