This is a feature patch for the experimental `git replay` command, now in its second version with all technical feedback addressed. The change makes `git replay` drop commits that become empty during replay (when their changes already exist in the target branch), matching the behavior of `git rebase --reapply-cherry-picks --empty=drop` and `git cherry-pick --empty=drop`. Originally-empty commits are preserved.

The implementation in `replay.c` now compares tree OIDs using `oideq()` to detect empty commits, with branch pointers properly updated when tip commits are dropped (tracked via a new `replayed_base_tree` variable). Test coverage in t3650 demonstrates the behavior where topic1 updates to point to rebased C when F is dropped as redundant. Documentation is updated to clarify the new default behavior.

All technical concerns from the thread have been resolved, with Junio Hamano endorsing the core approach and Elijah Newren confirming it matches his own implementation. The only remaining open question is whether to eventually add an option to retain empty commits for users who might rely on the old behavior, though this isn't blocking current progress. The patch is ready for inclusion, with Phillip Wood considering whether to base the next version on `master` or the `ps/history` branch.
