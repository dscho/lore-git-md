This is a bug report regarding the submodule gitdir path encoding series, specifically addressing patch 4/10 which introduces the `extensions.submodulePathConfig` feature.

Josh Steadmon reports a discrepancy between the documented behavior and actual implementation when cloning repositories with submodules. While the patch claims Git will automatically add `submodule.<name>.gitdir` config entries for new submodules when the extension is enabled, his testing shows this isn't happening during `git clone --recurse-submodules` operations. Notably, the expected error message about missing configs also fails to appear, suggesting either a gap in the validation logic or an edge case in the clone path that bypasses the new requirements.

The issue appears to be a concrete manifestation of the theoretical problem Josh previously raised about fallback mechanisms with pre-existing encoded paths. This real-world case demonstrates the validation system isn't catching missing configs as intended during submodule initialization, which could lead to inconsistent repository states. The report adds weight to ongoing discussions about the extension's validation robustness, particularly how it handles automated operations like cloning.

This feedback comes at a critical point in the series' development, where the architectural consensus is otherwise settled but implementation details are being polished. The team will likely need to address this before finalizing the patch series, as it touches on core functionality claims made in the documentation.
