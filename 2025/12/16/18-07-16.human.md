Maintainer follow-up on `git rev-list --filter` behavior documentation.

Junio Hamano responds to Justin Tobler's question about whether there are legitimate use cases for the current default behavior where explicitly provided objects bypass filters. He acknowledges there likely aren't any good use cases (agreeing it might warrant future fixing), but offers a plausible explanation for why the behavior went unnoticed - in the primary use case of object transfer for lazy clones, users typically specify commit ranges where commit objects wouldn't be filtered anyway.

The response reinforces the thread's emerging consensus: while the current behavior is suboptimal and surprising, it hasn't caused practical problems in the main use case. Hamano's comment about "fixing it someday" keeps the door open for future changes while accepting the status quo for now. This maintains alignment with Patrick Steinhardt's earlier caution about backward compatibility concerns.

The exchange provides useful context about why this edge case exists and why changing it isn't urgent, even as all parties recognize the behavior isn't ideal. The documentation patch remains valid as it accurately describes the current implementation while this discussion helps future contributors understand the tradeoffs involved.
