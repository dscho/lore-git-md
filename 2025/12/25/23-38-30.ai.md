Performance investigation follow-up on slow `git pack-refs --all`. Brian m. carlson identifies the likely cause of the `should_pack_ref` check that verifies each ref points to a valid object by calling `ref_resolves_to_object`. This explains the strace observations of object directory accesses, though the need to actually open object files rather than just checking OIDs remains unclear.

The reply notes that NFS exacerbates the performance impact, as checking 37 pack files and their indices over network storage creates significant overhead. A key observation is that repacking the repository first (reducing the number of pack files) dramatically improves ref-packing time, suggesting pack file count is a major factor. The suggestion to set `receive.unpackLimit=1` to minimize loose objects reflects common forge configurations that optimize for this case.

This moves the investigation forward by pinpointing the object existence verification as the root of the object access pattern, while leaving open whether the implementation could be optimized to avoid opening objects. The NFS context and pack file count impact provide actionable mitigation paths, though the fundamental discrepancy with JGit's approach remains unresolved.
