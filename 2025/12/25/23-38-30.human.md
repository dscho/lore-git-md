This is a technical discussion about performance issues with `git pack-refs --all` in large repositories. Brian m. carlson responds to Martin Fick's report of slow ref packing (5+ minutes vs JGit's 20s) by identifying two key factors: 

First, Git verifies ref validity by checking object existence via `should_pack_ref`, which explains the strace-observed object directory accesses. While this explains some overhead, Brian notes the actual file opening behavior seems excessive. 

Second, NFS exacerbates the problem by making pack file access expensive - the repository's 37 pack files require network roundtrips. Brian suggests repository maintenance practices like setting `receive.unpackLimit=1` to minimize loose objects, noting that forges often optimize this way.

The response advances the thread by clarifying why object access occurs during ref packing (a core mystery from the initial report) while leaving open whether the verification could be optimized.
