This is a performance issue report about `git pack-refs --all` being unexpectedly slow on a large repository. The reporter, Martin Fick, describes a production Gerrit server with ~3M refs where packing refs takes over 5 minutes, causing lock contention. Key technical details include:

The repository has ~90M objects, ~50GB data, and gets ~300 updates between maintenance cycles. While the packed-refs file itself is large, the slowness appears to come from unexpected object access during ref packing - an strace shows 200+ object directory opens and ~26K writes. The reporter notes that JGit handles the same operation in under 20s, and that repacking the repository first speeds up the ref packing, suggesting the issue may relate to how Git handles object access during ref packing. The repository is on NFS, which may be a factor. System info shows Git 2.45.2 on Linux with glibc 2.17.

The core mystery is why `pack-refs` would be reading objects at all, as this seems unnecessary for simply packing references. The reporter provides enough diagnostic details (timings, strace output, comparison with JGit) to suggest this is a genuine performance bottleneck worth investigating, though the NFS factor may complicate analysis. The impact on Gerrit servers makes this particularly relevant for users with large reference counts.
