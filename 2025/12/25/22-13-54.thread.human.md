This thread investigates why `git pack-refs --all` runs much slower (5+ minutes) than JGit (20 seconds) on large Gerrit repositories with ~3 million refs. The discussion began with Martin Fick's initial performance report and has evolved through detailed analysis from Jeff King and follow-up benchmarking from Martin.

The latest findings show the bottleneck isn't in I/O operations - writes complete quickly (29K writes in 15 seconds) - but rather in the 4 minutes of gaps between writes. The focus has shifted to memory access patterns, particularly how Git interacts with mmap over NFS (the storage backend in this environment). Martin suspects either slow NFS-backed mmap reads of the packed-refs file or inefficient in-memory ref lookups might be the culprit.

Patrick Steinhardt, drawing from GitLab's experience, confirms NFS can be problematic and suggests using perf(1) to generate flame graphs for deeper analysis. While the reftable backend remains architecturally superior for this use case, the current investigation aims to understand and potentially improve the files backend's behavior in high-refcount scenarios.

The discussion has moved past earlier hypotheses about write buffering and verification overhead, now concentrating on memory access patterns in Git's existing implementation. Martin's persistent benchmarking continues to drive the investigation forward, with the community working to pinpoint the exact cause of the performance gap between Git and JGit in these environments.
