Here's the human-readable thread summary:

This thread investigates a performance issue where `git pack-refs --all` runs unexpectedly slow on large repositories, particularly affecting Gerrit servers. Martin Fick reported the original case where packing ~3M refs took over 5 minutes (compared to JGit's 20s) on a repository with ~90M objects. Initial analysis showed Git was unnecessarily accessing objects during what should be a reference-only operation, with strace revealing 200+ object directory opens.

Brian m. carlson's follow-up identified the root cause: Git verifies each ref points to a valid object via `ref_resolves_to_object`, explaining the object access pattern. The NFS storage exacerbates the issue, as checking numerous pack files over the network creates overhead. A key finding is that repacking the repository first (reducing pack file count) significantly improves performance, suggesting a mitigation path via `receive.unpackLimit=1` to minimize loose objects.

While this explains the current behavior, the thread remains open on whether Git could optimize this verification to avoid object access entirely, and why JGit achieves better performance with the same operation. The discussion has practical implications for high-refcount deployments like Gerrit servers.
