This thread investigates why `git pack-refs --all` runs much slower (5+ minutes) than JGit (20 seconds) on large Gerrit repositories with ~3 million refs. The initial analysis pointed to tag peeling and object verification as the bottleneck, since Git must check each ref individually by reading object headers, while JGit appears to avoid this overhead. Martin Fick, who reported the issue, has challenged this explanation, noting that JGit handles the same operations much faster in their environment despite similar network conditions.

The discussion has now shifted focus to potential inefficiencies in Git's write path. Martin suggests investigating whether the implementation uses too many small unbuffered writes or misses optimization opportunities during the packing operation. This builds on earlier observations that repacking objects first helped performance, hinting at I/O patterns being a factor.

While the reftable backend (which amortizes verification costs differently) remains a promising architectural solution, the thread continues to explore why Git's current files backend performs orders of magnitude slower than JGit in this scenario. Key open questions center on whether there are optimization opportunities in Git's write codepath that could narrow the performance gap without requiring a full backend switch. The core challenge remains understanding the implementation differences that lead to such divergent performance characteristics between Git and JGit when handling millions of refs.
