This thread investigates the surprisingly slow performance of `git pack-refs --all` on large repositories with millions of references, particularly in Gerrit server environments where Git takes 5+ minutes compared to JGit's 20 seconds for the same operation. The initial analysis identified that Git's reference packing involves expensive verification of each reference through object existence checks and tag peeling, compounded by NFS overhead when accessing many pack files.

Jeff King and brian m. carlson have been exploring the fundamental differences in how Git's traditional packed-refs backend and JGit's reftable approach handle these operations. While both must perform the same verification work for correctness, reftable distributes the cost differently - amortizing the peeling overhead across reference updates rather than concentrating it during packing. Reftable can also maintain peeled references during compaction and potentially reuse already-loaded object information, though it doesn't eliminate the verification requirements entirely. The discussion suggests reftable's design may offer inherent performance advantages for high-refcount scenarios by reorganizing when and how often the verification work occurs, though the exact implementation details and potential optimizations remain an area for further exploration. The thread continues to examine whether Git could adopt similar approaches to reduce the packing overhead while maintaining the necessary safety checks.
