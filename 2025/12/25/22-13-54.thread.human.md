This thread investigates why `git pack-refs --all` runs slowly (5+ minutes) on large Gerrit repositories with ~3 million refs, compared to JGit's 20-second performance on the same data. The discussion has evolved through several phases of analysis.

Martin Fick originally reported the issue, with Jeff King (Peff) providing key technical analysis. Initial theories about verification overhead or write buffering have been ruled out - strace data shows the actual write operations complete quickly (29K writes in 15s), but Git spends ~4 minutes in unexplained gaps between writes. The focus has shifted to memory access patterns, particularly how Git interacts with NFS via mmap when reading the packed-refs file.

Patrick Steinhardt from GitLab has confirmed similar NFS performance issues in their experience. While the reftable backend (used by JGit) remains architecturally superior for this case, the current investigation aims to understand and potentially improve the files backend's behavior. Peff suggests building Git with NO_MMAP to better isolate I/O costs and reiterates the need for perf flame graphs to pinpoint the exact bottleneck. The core question remains: are the delays caused by NFS mmap characteristics or inefficient in-memory operations? Martin continues to drive the investigation with detailed benchmarking while Peff and Patrick provide expert analysis of the low-level behavior.
