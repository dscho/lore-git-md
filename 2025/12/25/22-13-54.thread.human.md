This thread investigates why `git pack-refs --all` runs slowly (5+ minutes) on large Gerrit repositories with ~3 million refs, compared to JGit's 20-second runtime on the same data. Initial analysis by Jeff King identified that Git performs expensive object verification - checking each ref resolves to a valid object and peeling tags by reading their headers - which explains the observed file accesses (200+ opens, 26K writes). While `refs/heads/` refs should only point to commits, Git must handle the general case where refs might be manually corrupted.

Brian m. carlson has now weighed in, cautioning against skipping verification even for branch refs, since manual updates could create invalid states that the code should handle safely. The discussion has shifted to whether the reftable backend (currently being developed) could avoid this overheads by maintaining pre-peeled references, potentially offering inherent performance advantages for high-refcount scenarios. While this suggests a promising direction, the thread hasn't yet explored implementation specifics or whether reftable would fully eliminate verification needs. The core tension remains between performance optimization and maintaining Git's robust handling of edge cases in repository state.
