Thread identity: Workflow question about rebasing branches after automatic code reformatting (e.g. clang-format), originating from Simon Richter.

Core problem: Automatic reformatting tools create widespread whitespace/formatting changes that cause numerous merge conflicts during rebase operations. Current solution involves creating an empty commit at branch point, then using `git filter-branch` to apply consistent formatting across all commits before rebasing, making formatting changes effectively invisible to Git's conflict detection.

Current status: First alternative approach proposed - Kristoffer Haugsbakk suggests git-branchless's `git-test` as potential solution. Original filter-branch method remains only proven approach so far.

Key technical details:
- Problem occurs when rebasing reformatted code against upstream changes
- Current workflow uses filter-branch to normalize formatting history
- git-branchless approach would apply formatters across commit stacks via worktree strategy
- Potential for parallel processing of formatting changes
- Solution would transform trees per snapshot rather than through three-way merges
- Practical concerns raised about git-branchless complexity (creates many refs/hooks)

Open questions:
- Are there better existing Git features for this workflow?
- Could git-branchless or similar tooling help automate this process?
- How to scale solution across multiple branches?
- Is git-branchless's complexity worth the benefit for this use case?
- Would snapshot-based approach actually prevent merge conflicts in practice?
