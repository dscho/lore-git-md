This is a documentation refinement discussion in the ongoing thread about `git worktree` terminology.

Junio C Hamano responds to Eric Sunshine's review of Sam Bostock's patch about clarifying `--expire` behavior for missing worktrees. While agreeing with the "expire"->"prune" wording change, Junio raises a deeper issue about the fundamental description of the `prune` subcommand itself. He argues that explaining "prune" using the same verb is unhelpful, especially for non-native speakers, and proposes a more detailed explanation that distinguishes between three scenarios of worktree removal.

The key technical points are:
1. The current `prune` documentation is too terse and potentially confusing
2. There are three distinct worktree removal scenarios that should be clearly documented
3. The proposed new wording for `prune` would explicitly mention it only removes metadata when the working tree is already lost
4. This ties into Julia's recent work about avoiding circular command explanations

This moves the discussion beyond just the `--expire` terminology to the more fundamental question of how to best document the different ways worktrees can be removed. Junio's suggestion would require updating the base `prune` documentation in addition to the `--expire` changes already proposed. The thread now has two documentation aspects to resolve: the immediate `--expire` terminology and this broader `prune` explanation issue.
