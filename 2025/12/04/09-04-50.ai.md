This is a follow-up in the Windows drive-letter remotes thread, where Konstantin Khomoutov responds to the original bug report. The email clarifies that Git's behavior of preserving the exact remote path (including drive letters) during cloning is working as designed - it's simply recording the URL exactly as provided by the user. 

Khominov suggests two alternative Windows-specific solutions beyond the UNC paths already discussed in the thread: using NTFS junction points (which can mount drives at folder paths) and the `mountvol` command. This maintains the technical discussion about Windows filesystem alternatives while reinforcing that Git's current behavior is intentional rather than buggy.

The response doesn't propose any Git changes but adds to the growing list of workarounds for the Windows-specific issue of drive-letter paths in remotes. It positions the problem as one of user expectation (wanting remotes to automatically adjust when repositories move) versus Git's design principle of faithfully recording exactly what the user specified. The mention of junction points introduces another Windows filesystem feature that could help avoid the issue entirely by using folder-based paths rather than drive letters.
