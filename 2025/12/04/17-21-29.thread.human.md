This thread focuses on optimizing how Git handles promisor objects in partial clone scenarios, particularly for large packs. The initial problem was that promisor object initialization was parsing all objects (including blobs) unnecessarily, causing significant performance overhead (76 minutes down to 2 minutes in initial testing).

The discussion has refined the approach through several iterations. Aaron Plattner's original patch skipped full parsing for blobs, Patrick Steinhardt improved memory efficiency, and Jeff King's refined solution using `parse_object_with_flags()` with commit-graph integration brought further gains (down to 49 seconds). A key insight was handling `OBJ_NONE` objects that appear during revision walks via `mark_uninteresting()` - these needed to be treated similarly to blobs.

The latest email from Jeff King provides important context about why performance measurements varied between test cases - it depends on whether promisor checks happen before or after objects are marked uninteresting in the revision walk. He also notes that commit-graph availability (which can be missing in Scalar worktrees) significantly impacts the optimization's effectiveness.

The technical approach is now well-understood, with all edge cases addressed. Aaron Plattner will submit a v2 patch incorporating both the type-check fixes and Jeff King's flag-based optimization. While the core solution is settled, maintainers should be aware that real-world performance will depend on environmental factors like commit-graph presence.
