This is a discussion response in the RFC thread about improving `git format-patch`'s handling of merge commits. Junio Hamano weighs in on Dominique Martinet's proposal to add warnings when merges are skipped.

The key points from this response are that warnings should be context-sensitive: they would be helpful when *no* commits are formatted (indicating the user might have expected output), but would be noise in common workflows where users intentionally include merge-heavy ranges (like `trunk..mytopic` with back-merges) and expect the merges to be skipped silently.

This introduces a new consideration not previously discussed in the thread - that the warning behavior needs to distinguish between "empty output" cases (where warnings are useful) versus "partial output with skipped merges" cases (where warnings would be annoying). The response suggests the current RFC's blanket warning approach would be too intrusive for established workflows.

The thread now has two clear positions to reconcile: the original proposal's goal of making merge-skipping more visible versus the maintainer's concern about spamming users in common scenarios. Future iterations will likely need to address this distinction through either conditional warnings or configuration options.
