This is a feature proposal addressing a UX issue in `git format-patch`. The patch suggests adding a warning when merge commits are silently skipped during patch generation, which currently happens without any user notification.

The author notes that this silent behavior can be surprising, particularly for users of newer merge-heavy workflows like those encouraged by `jj`. The proposed change would print a warning showing the commit hash when a merge commit is skipped. The RFC raises questions about when exactly to show this warning (only when no other commits are formatted? always?) and whether it should include more context like the commit subject.

The implementation is straightforward - removing the hardcoded `max_parents=1` limit and adding a warning check in the commit processing loop. The author acknowledges this needs proper tests and possibly a config knob if the warning proves too noisy, and invites feedback on the approach before submitting a more polished version.

This seems like a well-motivated quality-of-life improvement for users who might otherwise be confused by the current silent behavior. The patch is small and focused, though as noted it would benefit from tests and clearer documentation of the warning behavior in the final version.
