Thread summary:

RFC patch proposing to improve `git format-patch` behavior with merge commits by adding warnings when they are skipped. Currently, format-patch silently skips merge commits (those with multiple parents) due to its hardcoded single-parent limitation, which can surprise users of merge-heavy workflows like those used with `jj` (Jujutsu VCS).

The patch modifies `builtin/log.c` to:
1. Remove the implicit `max_parents=1` limitation
2. Explicitly detect merge commits via `commit->parents->next`
3. Issue warnings using `warning()` when skipping merges, including the commit OID via `oid_to_hex()`

Junio Hamano has now responded with a key consideration: warnings should be context-sensitive. They would be helpful when no commits are formatted (indicating the user might have expected output), but would be noise in common workflows where users intentionally include merge-heavy ranges (like `trunk..mytopic` with back-merges) and expect the merges to be skipped silently.

Open questions now include:
- How to distinguish between "empty output" cases (where warnings are useful) versus "partial output with skipped merges" cases (where warnings would be annoying)
- Whether to make warnings conditional on empty output or add configuration options
- Should the warning include the commit subject in addition to OID
- Needs test coverage for both warning and non-warning scenarios
- Needs proper option handling for any new warning controls

The thread now presents two positions to reconcile: the original goal of making merge-skipping more visible versus avoiding spam in established workflows. The solution will likely involve more sophisticated warning logic than the current blanket approach. The change still maintains the fundamental behavior of not generating patches for merge commits, just making the skipping more visible when appropriate.
