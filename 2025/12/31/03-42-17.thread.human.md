This RFC thread explores improving `git format-patch`'s handling of merge commits, which are currently skipped silently. The original patch proposed adding warnings when merges are skipped, aiming to help users of merge-heavy workflows like Jujutsu (jj) who might be surprised by missing patches. The discussion has evolved through key inputs from maintainers and reviewers.

Junio Hamano raised the central design consideration: warnings should be context-sensitive. While useful when no output is generated (indicating potential user confusion), they'd become noise in workflows where users intentionally process ranges containing merges (like `trunk..topic` branches with periodic merges). This leaves the thread with open questions about when to trigger warnings and how to configure them.

Jeff King (Peff) then contributed a crucial technical review, spotting a potential segfault in the original implementation when handling root commits (those with no parents). His suggested fix - adding a null check before dereferencing parent pointers - demonstrates the attention to edge cases that makes his reviews so valuable. Notably, Peff avoided the design debate, keeping his feedback narrowly focused on correctness.

The thread now has two clear threads to resolve: the design question of warning behavior (with Junio's context-sensitivity concern) and the implementation robustness (with Peff's null-check fix). Any revised version will need to address both the when-to-warn logic and the memory safety, while likely adding tests for both the warning behavior and edge cases like root commits. The discussion remains productive, with the next step being a v2 patch addressing these points.
