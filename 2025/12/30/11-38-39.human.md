Bugfix follow-up to the fsmonitor Linux implementation. Junio Hamano reports memory leaks detected when running the fsmonitor tests with SANITIZE=leak. The leak occurs during daemon initialization, specifically in the hashmap allocation within `fsmonitor_run_daemon()`. 

The test failure shows the daemon successfully starting and responding to queries, but leaks 512 bytes from an un-freed hashmap allocation when the test attempts to implicitly start the daemon. This appears to be a cleanup oversight in the otherwise thorough fsmonitor Linux implementation that was recently introduced.

While the core functionality works (the daemon properly handles filesystem watching and responds to queries), this leak would need to be addressed before the feature could be considered production-ready. The stack trace helpfully pinpoints exactly where the allocation occurs, making this a focused fix for the original author to address.

This follows up on the larger fsmonitor Linux support thread where the implementation had already addressed several rounds of review feedback around memory safety and portability. The current issue appears to be one of the final polish items needed for the feature.
