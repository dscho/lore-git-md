This is a follow-up discussion in the Windows symlink preparation series, specifically addressing patch 4/5 about `strbuf_readlink()` buffer limits. Junio Hamano weighs in on the resolved discussion between Patrick Steinhardt and Johannes Schindelin about buffer size limits for symlink targets.

The key technical question was whether to impose a practical upper bound on symlink path lengths, particularly for Windows compatibility. Johannes Schindelin had proposed a 32,768 character limit based on Microsoft documentation, which Patrick accepted. Junio now raises a concern about this being a platform-specific solution in generic code, suggesting either: (1) a termination condition for the buffer growth loop when hitting very large sizes, or (2) his preferred simpler alternative of just raising the hard limit to 32kB universally while acknowledging Windows as the motivating case.

The proposed patch replaces the `PATH_MAX`-based limit with a fixed 32kB (`1<<15`) buffer size, with a comment explaining this matches Windows' practical limits while avoiding platform-specific `PATH_MAX` issues. This maintains the series' goal of robust symlink handling while sidestepping the theoretical unbounded growth concerns Patrick originally raised. The change is minimal (6 lines) and focused solely on the buffer size definition in `strbuf.c`.

This email represents final polishing of the already-reviewed series, with Junio providing maintainer guidance to reconcile the Windows-specific solution with cross-platform code hygiene. The technical consensus appears to be coalescing around the fixed 32kB limit as a reasonable compromise between safety and practicality.
