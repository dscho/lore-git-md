This is a technical explanation of Git's revision walking internals, specifically addressing how `git log --reverse` works. Junio C Hamano responds to Jon Forrest's question about the implementation details.

The response clarifies that `--reverse` operates in two phases: first collecting commits in forward order (newest-to-oldest) via the standard traversal mechanism in `get_revision_internal()`, then storing them in a queue. Only after completing the forward traversal does it output the commits in reverse order from this queue. This explains why the parent pointer-based traversal can still produce oldest-to-newest output - it's achieved by buffering the commits during initial traversal rather than trying to walk the graph in reverse directly.

The explanation focuses on the `.commits` list as the key data structure enabling the reverse output, confirming Jon's suspicion about commit lists being involved. The response suggests the implementation is straightforward once you understand this two-phase approach, though it doesn't go into deeper details about the queue management or memory implications of buffering all commits before output.
