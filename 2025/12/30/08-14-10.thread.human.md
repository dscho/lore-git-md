This thread has been investigating an interaction between fsmonitor and split-index that was leading to index corruption, particularly when `index.skipHash` is enabled. Johannes Schindelin identified the root cause - that skipping the hash computation left the shared index OID null, causing later issues when fsmonitor's dirty bitmap referenced unloaded entries. 

Paul Tarjan has now confirmed Johannes' analysis and proposed a proper fix that addresses the underlying issue rather than just the symptom. His solution makes `write_shared_index()` generate a real OID even when `index.skipHash` is true, while preserving the original skipHash setting. This passes all relevant tests and makes the need for fsmonitor-specific bounds checking unnecessary.

The core fsmonitor implementation - with its process isolation, Windows compatibility, and Linux inotify support - remains production-validated and unaffected by this change. The discussion has shifted to an orthogonal issue in the split-index handling that happened to surface through fsmonitor assertions. 

Paul has offered several paths forward for integrating this fix, either as a standalone patch, as part of his fsmonitor series, or deferring if others are already working on the skipHash/split-index interaction. The technical solution is now clear, with only the integration approach remaining to be decided. Johannes' earlier recommendation to remove the bounds-check patch from the fsmonitor series appears validated by this more comprehensive fix.
