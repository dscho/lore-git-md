This is a bugfix follow-up to the Linux fsmonitor implementation, addressing a memory leak found during testing. Junio Hamano reports that running the test suite with `SANITIZE=leak` reveals a 512-byte leak in the fsmonitor daemon's hashmap initialization path. The leak occurs when the daemon is started implicitly during a client query in test case t7527.

The stack trace shows the allocation originates in `hashmap.c` during daemon startup (`fsmonitor_run_daemon`), specifically when initializing the watch descriptor tracking table. The test output demonstrates the failure scenario: an implicit daemon start during a query operation, followed by proper daemon status checks, but with the leak detected after shutdown.

This appears to be a straightforward resource cleanup issue in the Linux fsmonitor backend, where the hashmap allocated during initialization isn't being freed when the daemon terminates. The report doesn't include a fix, but the precise location and nature of the leak are clearly identified, making this a focused issue for the original author to address.

The thread context shows this is the third iteration of the Linux fsmonitor patchset, with previous rounds having addressed several other leaks and safety issues. This newly discovered leak suggests the test coverage with leak sanitizer is effectively catching edge cases, though it's notable that this particular issue wasn't caught in earlier reviews.
