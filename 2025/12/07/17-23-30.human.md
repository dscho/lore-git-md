Thread continuation in the structured data versioning discussion, with Cedric Sodhi responding to Simon Richter's database-native approach proposal.

Cedric remains skeptical about implementing version control directly in databases, arguing this would effectively require reimplementing Git's features. While acknowledging the need for database-specific tooling, he maintains that Git could handle relational data well if properly mapped to filesystem structures. 

The key technical point is Cedric's proposed mapping strategy: normalizing database contents by sorting elements (like KiCad's UIDs) line-by-line to create stable diffs. He suggests this could work for 99% of cases, with options ranging from one file per table down to one file per row/element. The latter approach could even detect moves without requiring stable UIDs by leveraging Git's rename detection.

Cedric sees the main obstacle as Git's current inability to transparently access database contents, not any fundamental algorithmic limitation. His position contrasts with Simon's database-native approach, maintaining that filesystem semantics (particularly hierarchy and rename detection) offer valuable versioning capabilities that would be lost in a pure database solution. The exchange continues to explore the tradeoffs between filesystem-based and database-native versioning for structured data.
