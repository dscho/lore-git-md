This thread addresses a serious data-loss bug in `git pull --rebase` when repositories have multiple push URLs. The core problem occurs when pushing to one destination succeeds while another fails, followed by a rebase that incorrectly drops local commits due to miscalculated fork points. The issue stems from inconsistent remote-tracking states after partial push successes.

Three solutions are under consideration: Phillip Wood proposes modifying `git pull --rebase` behavior when certain push configurations are present; Junio Hamano suggests calculating fork points before fetching rather than after; and Kartik Agaram (the original reporter) advocates for making push operations atomic so remote-tracking refs only update when all push URLs succeed.

In the latest exchange, Phillip points out limitations in Kartik's atomic push approach, noting that push URLs often point to different servers than pull URLs, meaning the problem could persist even with atomic pushes. Phillip also highlights confusing behavior around `remote.pushDefault` configuration, which doesn't update remote-tracking refs as expected when set to a URL rather than a remote name. This discussion reveals deeper complexities in Git's URL handling that any solution will need to address.

The thread remains active with participants converging on understanding the problem's boundaries. While a workaround exists (`git fetch && git rebase --no-fork-point`), the core issue requires careful design to avoid introducing new edge cases or breaking existing workflows that rely on partial push success. The discussion continues to weigh the tradeoffs between the three proposed approaches.
