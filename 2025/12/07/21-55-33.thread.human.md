This thread addresses a serious data loss scenario in `git pull --rebase` when repositories have multiple push URLs configured. The core issue occurs when pushing succeeds to one URL but fails on another - subsequent rebase operations can drop local commits due to incorrect fork-point calculations. The problem stems from push-originated reflog entries when push and pull URLs differ, combined with how Git examines the upstream branch's reflog to find the most recent common ancestor (originally mischaracterized as looking for descendants).

Technical understanding has solidified around several key points: the fork-point calculation happens before fetching, examines reflog entries to handle upstream resets, and the current behavior emerges when these reflog entries come from different servers than the pull operation. Phillip Wood provided an important correction about the fork-point algorithm's directionality (looking for ancestors, not descendants), referencing official documentation to clarify the mechanism.

Several solution approaches are under consideration, ranging from disabling fork-point when push URLs are configured (Phillip Wood's proposal) to improved warning messages (Junio Hamano's suggestion). The discussion has identified new requirements around providing explicit user control over fork-point behavior when modifying the default handling.

Participants continue to weigh tradeoffs between different solutions while ensuring any changes respect Git's documented behavior.
