This thread addresses a serious data-loss bug in `git pull --rebase` when working with repositories configured with multiple push URLs. The core issue occurs when a push partially succeeds (updating one remote but failing on a mirror), followed by a rebase that incorrectly drops local commits due to inconsistent remote-tracking branch states.

Phillip Wood provided the initial technical analysis, identifying the problem in the fork-point calculation logic and proposing a configuration-based solution that would bypass fork-point when multiple push URLs are detected. He also documented a workaround using explicit `--no-fork-point`.

Junio Hamano has now weighed in with a more fundamental architectural proposal: restructure the pull-rebase sequence to calculate the rebase range *before* fetching, rather than after. This would avoid the inconsistent remote-tracking state entirely by locking in the rebase parameters prior to any reference updates. While more complex to implement, this approach would provide a robust solution without requiring special configuration checks.

The discussion remains focused on finding the right balance between fixing this edge case and maintaining the expected behavior for simpler workflows. Both proposed solutions - Phillip's configuration-based approach and Junio's architectural change - aim to prevent data loss while keeping the common case simple. The thread has attracted attention from both the original reporter (Kartik Agaram) and core contributors, reflecting the importance of fixing this subtle but dangerous behavior.
