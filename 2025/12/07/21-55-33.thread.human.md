This thread examines a subtle data loss scenario in `git pull --rebase` when repositories have multiple push URLs configured. The issue occurs when pushing succeeds to one destination (e.g., a hub) but fails on another (e.g., a mirror), followed by a rebase operation that incorrectly drops local commits due to miscalculated fork-points. The root cause involves inconsistent remote-tracking states from push operations to different servers than the pull operation.

Initial analysis revealed three potential solutions: Phillip Wood's configuration-based approach, Junio Hamano's architectural change (later found to already be happening), and Kartik Agaram's atomic push proposal. The discussion has since uncovered that fork-point calculation already occurs before fetching, contrary to earlier assumptions, and that the problem stems from push-originated reflog entries when push and pull URLs diverge.

Phillip Wood now suggests disabling fork-point calculation entirely when `pushurl` is configured as a broad mitigation, while Junio Hamano considers this approach alongside improved user messaging via `advise()`. The team is weighing tradeoffs between simple but potentially overbroad solutions versus more precise fixes that maintain existing functionality for valid cases. A current workaround (`git fetch && git rebase --no-fork-point`) remains valid while the discussion continues.

Key participants include Kartik Agaram (who reported the issue), Phillip Wood (driving configuration-based solutions), and Junio Hamano (evaluating architectural implications). The thread has revealed the problem to be more complex than initially understood, with push/pull URL divergence and pre-existing fork-point behavior adding new dimensions to the solution space.
