This is a continuation of the structured data versioning discussion, with Cedric Sodhi responding to Simon Richter's database-native versioning proposal. The email focuses on defending Git's potential for relational database versioning while acknowledging the need for custom tooling.

Cedric argues that Git could handle relational data through filesystem mapping strategies, countering Simon's KiCad example which showed line-oriented diff challenges with CAD data. He proposes several mapping approaches: normalizing database tables into sorted files (one element per line), table-to-file mapping, or even row/element-to-file mapping. The latter could leverage Git's move detection without requiring stable UIDs.

Key technical points include the observation that proper normalization (sorting by UIDs) would produce clean diffs when content changes, and that filesystem hierarchy semantics offer advantages over monolithic database files. Cedric maintains there's no fundamental algorithmic barrier - just a need for transparent access methods to bridge Git's filesystem model with database contents.

The response indicates continued divergence in the thread between database-native approaches and Git adaptation strategies. Cedric's position remains that Git's core capabilities are sufficient if properly mapped, though he concedes the need for database-specific tooling.
