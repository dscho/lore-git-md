This is a technical discussion about potential solutions for the `git pull --rebase` data loss issue with multiple push URLs. Phillip Wood responds to Junio Hamano's suggestion about either disabling fork-point calculation when pushurls are configured or improving user diagnostics.

The key new consideration Phillip raises is that if fork-point calculation is disabled for pushurl cases, there needs to be a way to explicitly skip fork-point usage during pulls. Currently, while users can force fork-point usage with `--fork-point`, there's no direct way to disable it when it's the default behavior.

The discussion continues to weigh the tradeoffs between:
1. Phillip's original proposal to disable fork-point for pushurl cases
2. Junio's suggestion of enhanced diagnostics via `advise()`
3. Now with the added constraint that any solution must provide user control over fork-point behavior

The thread has established that the core issue stems from push-originated reflog entries when push and pull URLs differ, causing fork-point miscalculations. The current workaround (`git fetch && git rebase --no-fork-point`) remains valid, but the discussion is now focusing on how to properly integrate a solution into Git's configuration and command-line interface.

Technical context for future reference:
- The fork-point calculation happens in `get_rebase_fork_point()` and related functions
- Current behavior examines upstream branch's reflog before fetching
- Push operations to different servers create problematic reflog entries
- `remote.pushDefault` behavior with URLs rather than remote names is a related concern
- Any solution must maintain compatibility with documented fork-point behavior while addressing the pushurl divergence case
