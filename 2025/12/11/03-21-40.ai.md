This is a technical discussion about the `git pull --rebase` data loss bug in repositories with multiple push URLs. Junio Hamano responds to Phillip Wood's observation that the fork-point calculation already happens before fetching (contrary to earlier assumptions), and that the problematic reflog entries originate from pushes to different servers than the pull operation.

The key technical points are:
1. The root cause is now understood to be push-originated reflog entries when push and pull URLs diverge (e.g., pushing to a hub while pulling from a mirror)
2. Phillip Wood suggests disabling fork-point calculation entirely when `remote.<remote>.pushurl` is configured as a blunt mitigation
3. Junio Hamano considers this approach but also raises the alternative of improving user diagnostics via `advise()` messages

The discussion reveals new constraints on potential solutions:
- Any fix must account for the pre-existing pre-fetch fork-point calculation behavior
- Solutions must handle the push/pull URL divergence case
- The interaction between push-originated reflog entries and fork-point heuristics is problematic

Junio Hamano's response indicates the team is weighing tradeoffs between:
- Simplicity (disable fork-point for pushurl cases) vs precision (more targeted fixes)
- Automatic behavior changes vs improved user education
- The risk of over-broad solutions affecting valid use cases

This moves the thread forward by narrowing the solution space while surfacing new considerations about the user experience implications of different approaches. The core technical challenge remains handling the push/pull URL divergence case without breaking legitimate fork-point usage scenarios.
