Bugfix for a segmentation fault in `git replay` when given a non-existent target for `--onto`. 

This reports a regression where passing a non-existent reference to `git replay --onto` causes a segfault rather than a proper error message. The reporter bisected the issue to commit 15cd4ef1 ("replay: make atomic ref updates the default behavior") from November 2025, which is currently in both master and next branches. The bug manifests when running commands like `git replay --onto="$doesntexist" "$commit^!"`.

The reporter provides a bisect script that demonstrates the issue by intentionally passing a bad reference and checking for exit code 139 (segfault). The expected behavior would be to fail gracefully with an error message rather than crashing. The bug appears to affect both the current development branches (seen and next) as well as the mainline.

This appears to be a straightforward crash bug with clear reproduction steps. The commit that introduced the regression is identified, which should help with fixing it. The reporter has done thorough investigation work including bisecting and testing across multiple branches. The bug affects core functionality of the relatively new `git replay` command, making it worth prompt attention from maintainers.
