This is a review comment on the PID file debugging feature for lockfiles, focusing on configuration granularity. Jeff King (peff@peff.net) questions whether the per-component configuration scheme in Paulo Casaretto's v3 implementation is necessary, given that the refname collision concerns have been resolved with the tilde-based naming approach.

Jeff acknowledges the value of the feature for debugging stale locks but suggests simplifying the configuration to a binary on/off switch via core.lockfilePid, eliminating the subsystem-specific flags (index, config, refs, etc.). He considers but dismisses most use cases for granular control, though he entertains one hypothetical scenario where someone might want to avoid filesystem overhead for frequently-updated components like refs while keeping it enabled for others.

The comment represents a potential simplification of the implementation by removing the component-level configuration infrastructure that was previously discussed and implemented. This would affect the LOCKFILE_* flag parameters and reduce the configuration surface area. Jeff's position contrasts with earlier discussions that assumed subsystem granularity was important, though he leaves the door open for counterarguments about performance impacts.

This feedback comes after the final implementation review stage where Junio had flagged documentation and error handling issues, suggesting the feature is otherwise technically sound. The question now shifts from implementation details to interface design philosophy - whether to maintain maximum flexibility or optimize for simplicity in the configuration.
