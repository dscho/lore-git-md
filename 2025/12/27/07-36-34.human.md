This is a technical discussion about performance optimizations for `git pack-refs` in high-refcount repositories, specifically examining the tradeoffs between verification safety and speed.

Jeff King responds to brian m. carlson's concerns about optimizing ref verification by noting that while the reftable backend still performs peeling, it does so more efficiently by amortizing the cost across ref updates rather than concentrating it during packing operations. The key insight is that reftable's design inherently reduces redundant work - it avoids re-verifying during compaction and may benefit from objects already being in memory from prior operations.

The discussion highlights an important architectural difference between the traditional files backend and reftable: the files backend's packing operation must verify each ref from scratch, while reftable maintains verification state. This helps explain why reftable could offer better performance for Martin Fick's reported case, though both backends ultimately perform the same fundamental verification work.

The email maintains a cautious tone about making assumptions about ref validity, agreeing with brian m. carlson that manual ref updates could create invalid states that need verification. The technical details suggest reftable may be the more promising path forward for performance improvements rather than trying to optimize the current files backend's verification approach.
