This is a review comment on the PID-based lock debugging feature, focusing on configuration granularity.

Jeff King (peff) responds to Paulo Casaretto's v3 patch implementing `~pid.lock` files for debugging stale locks. While he approves of the tilde-based naming solution that avoids refname collisions, he questions whether the per-component configuration (modeled after `core.fsync`) is necessary. 

Peff suggests the simpler binary choice of "all or nothing" might suffice, since the main use cases are either wanting PID debugging universally or not at all. He acknowledges a possible counter-argument about filesystem overhead for frequently-written components like refs, but considers this edge case unlikely to justify the added complexity of subsystem-specific controls.

The comment represents a late-stage design refinement suggestion, building on the thread's earlier resolution of technical concerns around naming, Windows support, and cross-version compatibility. Peff's observation could potentially remove several LOCKFILE_* parameters if the core team agrees to simplify the configuration approach.
