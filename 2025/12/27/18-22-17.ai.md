This is a technical discussion thread about improving merge conflict metadata and user experience during rebase operations, with a focus on making this information more accessible to tools like rustc without requiring Git command invocations.

Ben Knoble responds to Esteban Küber's investigation of parsing Git's internal state files directly, noting potential issues with the reftable backend's different reference storage approach. He suggests this might motivate contributing support to libgit2 rather than parsing Git's files directly. The discussion then focuses on two concrete proposals from Küber: 1) providing merge/rebase metadata in a more structured format than the current text-based MERGE_MSG, and 2) enhancing conflict markers to include branch information alongside commit SHAs.

Key technical points in this exchange include concerns about the stability of parsing MERGE_MSG's free-form text, the complexity of reliably extracting remote URLs, and the observation that branch names alone may not fully capture the "ours/theirs" relationship in all cases. Knoble suggests the proposal would benefit from specifying exactly what metadata tools need, and questions whether simply adding branch names to conflict markers fully addresses the underlying issue of code location swapping between rebase/merge operations.

The thread shows progress toward concrete solutions while surfacing important implementation considerations. The discussion remains focused on balancing tool accessibility with Git's internal architecture constraints, with particular attention to the reftable backend implications and the tradeoffs between structured metadata and enhanced user-facing output. No clear consensus has emerged yet on the preferred approach.
