This thread began with a bugfix from Troels Thomsen addressing a receive-pack crash when handling symbolic references that point beyond their namespace. The fix modified `check_aliased_update_internal()` to properly handle fully-qualified ref names, with a test case verifying the behavior. While Junio Hamano acknowledged the technical merit of the fix, he raised security concerns, proposing that receive-pack should instead reject such cross-namespace symref updates entirely.

The discussion has since evolved into a debate about Git's namespace model. Troels argues that since symrefs require explicit server-side configuration, cross-namespace links are intentional and hooks can enforce stricter policies if needed. He suggests documenting the current permissive behavior rather than changing it. Junio, however, firmly maintains that security boundaries should be strict by default, rejecting the documentation-only approach as insufficient. He views namespace boundaries as security features that shouldn't be bypassed without explicit opt-in mechanisms.

The core disagreement now centers on Git's security philosophy - whether namespaces should form strict isolation boundaries (Junio's position) or whether symrefs should be allowed to intentionally bridge them (Troels' view). While the original crash is resolved, the thread remains at an impasse with no proposed implementation for Junio's stricter policy yet. Both sides acknowledge hooks could enforce either approach, but differ on what the default behavior should be. The test case's validity under potential behavior changes remains an open question as the discussion continues to explore the balance between security and flexibility in Git's design.
