This is a technical discussion about improving merge conflict metadata and user experience during rebase operations, with a focus on making the information more accessible to tools and users.

Ben Knoble responds to Esteban Küber's exploration of parsing Git's internal state files to identify rebase/merge context without invoking Git commands. He raises concerns about the reftable backend's different storage approach and suggests libgit2 might be a better path for tool integration. The discussion then shifts to Esteban's concrete proposals: (1) structured metadata output as an alternative to parsing text files like MERGE_MSG, and (2) enhanced conflict markers that show branch names alongside commit SHAs.

The proposed conflict marker format variations for different operations (rebase, merge, pull) aim to clarify which code belongs to which branch - a current pain point where the "ours/theirs" distinction swaps between rebase and merge. Ben engages with the proposal while noting edge cases (remote URLs, branchless operations) and questioning whether branch name display fully addresses the underlying confusion about code location in conflicts.

The exchange shows progress from problem analysis to specific solution design, with open questions about implementation approaches and backward compatibility. Both participants demonstrate deep technical engagement with Git's internals while considering real-world tooling constraints.
