This is a feature proposal for improving merge conflict markers during rebase operations, continuing an ongoing discussion about better metadata for tool-assisted conflict resolution.

Esteban Küber follows up on earlier suggestions about identifying rebase state without invoking Git commands (a security concern for the Rust compiler team). They've found workarounds by parsing Git's internal files directly, though some solutions rely on fragile text parsing of MERGE_MSG. The key findings are that .git/rebase-merge files provide enough information to distinguish rebase types, and FETCH_HEAD can identify pull-initiated rebases.

The email proposes two main changes: First, making merge metadata available in structured format rather than just free-form text. Second, and more significantly, enhancing conflict markers to include branch information alongside commit SHAs. The proposal includes concrete examples showing how this would look for different operations (rebase, merge, pull with/without rebase), arguing this would make conflict resolution more intuitive since the "our/their" orientation currently swaps based on operation type.

The discussion remains focused on improving tooling support while maintaining security boundaries. The branch-aware conflict markers in particular appear to be a well-motivated UX improvement that could benefit all users, not just tooling. The thread shows productive technical discussion with multiple viable approaches emerging.
