Bugfix proposal for batched reference update error reporting regression. This is Jeff King's response to the confirmed regression where specific error messages (like "trying to write non-commit object") were lost during batched reference updates in Git 2.51.0.

King provides a detailed technical analysis of why the error messages are being dropped - the batched update infrastructure currently only preserves numeric error codes while discarding the detailed error strings. He proposes modifying the ref transaction API to properly propagate these messages through several layers:

1. The core change would make `ref_transaction_maybe_set_rejected()` accept and store error detail strings
2. The `ref_transaction_for_each_rejected_update()` callback would be extended to receive these details
3. Callers like `receive-pack` would then have access to the full error messages

The included patch demonstrates this approach by restoring the lost "non-commit object" message in receive-pack, though King notes it's just a proof-of-concept with known issues (memory leaks, incomplete coverage of all error paths). He suggests Karthik Nayak (original author of the batched updates feature) should take over the final implementation.

This appears to be a well-considered fix for a clear regression, though the solution requires careful coordination across multiple components of Git's ref transaction system. The patch shows good understanding of both the technical problem and the architectural constraints involved in error reporting.
