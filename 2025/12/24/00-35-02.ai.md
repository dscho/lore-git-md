This is a bugfix patch series addressing an issue with shallow clones when the ref-in-want protocol feature is enabled. The problem has existed since ref-in-want was introduced in 2018, causing shallow clones to fail with a protocol error when uploadpack.allowRefInWant is enabled.

The root cause is that upload-pack sends protocol v2 sections in the wrong order - it sends wanted-refs before shallow-info, violating both the documented protocol specification and client expectations in fetch-pack.c. The first patch simply swaps two lines in upload-pack.c to correct the section ordering. The second patch adds a regression test to verify shallow fetches work properly with ref-in-want enabled.

The changes are minimal (just 2 lines modified) but important for correct protocol behavior. The test case added in t5703-upload-pack-ref-in-want.sh provides coverage for this previously untested combination of features. The commit message clearly identifies the longstanding issue and provides the exact error message users would see, making it easy to understand the impact.

Key technical details for future reference:
- Bug manifests when both shallow clone and uploadpack.allowRefInWant are enabled
- Protocol violation involves section ordering in upload-pack.c
- Client expects shallow-info before wanted-refs per gitprotocol-v2.adoc
- Fix is straightforward line swap in upload-pack.c
- Test verifies shallow fetch with ref-in-want works post-fix
