This is a discussion response in the ongoing thread about configurable branch comparison in `git status` output. Maintainer Junio C Hamano is responding to concerns raised by Yee Cheng Chin about the hardcoded remote preferences in the proposed feature.

The exchange highlights several key issues with the current implementation's assumptions about remote naming conventions ("upstream" and "origin" being treated as special). Chin points out real-world scenarios where these names don't apply, including:
- Custom remote names like "official" for upstream or personal fork names
- Multi-remote repositories where the important remote isn't obvious
- Special branches like 'gh-pages' that don't follow normal conventions
- Permanently forked version branches (v2.x vs v3.0)

Hamano agrees these are valid concerns, particularly noting that the current approach doesn't properly account for the push/pull configuration mechanisms Git already has. The discussion is shifting from implementation details to broader design questions about how to make the feature flexible enough to handle diverse workflows while remaining useful.

This response doesn't propose specific solutions but validates the concerns raised, suggesting the feature will need more configurability (likely at both repository and branch levels) to be generally useful. The gh-pages example is highlighted as particularly problematic for the current design. The thread continues to explore how to balance utility with workflow diversity.
