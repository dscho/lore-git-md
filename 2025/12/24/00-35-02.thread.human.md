This thread addresses a bug in Git's protocol handling where shallow clones fail when the ref-in-want feature is enabled. The issue stems from upload-pack sending protocol sections in the wrong order (wanted-refs before shallow-info) when both features are active, violating the documented v2 protocol specification.

A two-patch series has been proposed to fix this. The first patch makes the minimal code change needed - swapping two lines in upload-pack.c to correct the section ordering. The second patch, just submitted, adds a test case that verifies shallow clones now work correctly with ref-in-want enabled. The test creates a shallow clone against a server with uploadpack.allowRefInWant=true, which would previously fail with a protocol error.

The fix is straightforward and aligns with the documented protocol, so no major objections are expected. The test case follows existing patterns in t5703-upload-pack-ref-in-want.sh and provides regression protection for this feature combination that wasn't previously covered. As this is the initial submission, the patches are awaiting review from the community, particularly from those familiar with the protocol implementation like Jeff King or Patrick Steinhardt.
