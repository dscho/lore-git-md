This is a feature patch introducing PID tracking for Git lockfiles to aid in debugging stale locks. The patch series has progressed through v3 with significant discussion around naming conventions and refname collision avoidance.

The patch adds an optional feature that creates companion PID files alongside lockfiles (e.g. `foo~pid.lock` next to `foo.lock`) containing the locking process's PID. The tilde separator was chosen as it's forbidden in refnames but allowed in Windows filenames, avoiding namespace collisions. The feature is controlled via `core.lockfilePid` config with component-level granularity (index, config, refs etc.), defaulting to disabled.

When lock conflicts occur, Git now checks for and reads existing PID files regardless of config, providing context-aware error messages indicating whether the locking process is still running. The implementation handles cleanup via tempfile registration and includes comprehensive tests covering various scenarios (stale locks, running processes, config combinations).

Key technical details:
- New `LOCK_PID_*` component flags and `lockfile_pid_components` config
- PID file format follows Git object header style (`pid <value>`) for extensibility
- Windows compatibility via `mingw_kill()` updates
- Integration across all major lockfile users (index, config, refs etc.)
- 139-line test script `t/t0031-lockfile-pid.sh` verifying behavior

The thread has seen extensive discussion around:
1. Naming scheme (settled on `~pid` infix)
2. Refname collision avoidance (confirmed safe with tilde)
3. Configuration granularity (per-component with `core.lockfilePid`)
4. Cross-platform compatibility (Windows support verified)
5. Edge cases (abnormal termination, stale PID files)
