Thread identity: Bug report about regression in error reporting for non-commit objects when using batched reference updates, affecting push, fetch, and update-ref commands across both files and reftable backends. Originated from Elijah Newren.

Core problem: Git 2.51.0 silently regressed detailed error reporting ("trying to write non-commit object") in favor of generic messages ("invalid new value provided") when pushing non-commit objects to refs/heads/*. The issue extends beyond push to also affect fetch and update-ref --batch-updates when using ALLOW_FAILURE, where operations can silently fail in status output. Root cause traces to the original batch reference update implementation (23fc8e4f61) rather than the later receive-pack optimization (9d2962a7c44) initially identified.

Current status: Regression confirmed by Junio C Hamano as unintentional. Jeff King has proposed a fix modifying the ref transaction API to restore detailed error messages while maintaining batched update performance. The proposal now requires broader changes to address multiple command interfaces and error case coverage.

Key technical details: The regression stems from batched reference updates losing error context. Jeff King's solution involves:
- Adding `details` parameter to `ref_transaction_maybe_set_rejected()`
- Storing details in `ref_update` via new `rejection_details` field
- Extending callback to receive details string
- Updating all backends (files, packed, reftable) to pass through error messages
New considerations include:
- Handling machine-readable output formats for fetch/update-ref
- Memory management of detail strings across multiple command contexts
- Backward compatibility for existing ref transaction interface users
- Consistent error reporting for ALLOW_FAILURE cases

Open questions: 
- How to properly manage memory for error detail strings across multiple command contexts
- Whether and how to include details in machine-readable output formats
- Tradeoffs between human-readable sideband vs machine-readable ref status
- Scope of changes needed for fetch and update-ref interfaces
Jeff King suggests Karthik Nayak (original batched updates author) should likely finalize the implementation.

Participant positions: Elijah Newren reported the regression. Junio C Hamano confirmed it was unintentional. Jeff King has expanded the scope of the technical solution but notes it needs refinement, suggesting Karthik Nayak take over the final implementation. No other participants have weighed in yet.

Related work: The regression stems from performance optimizations in batched reference updates (23fc8e4f61, 9d2962a7c44). The fix will need to work consistently across both files and reftable backends while maintaining the performance benefits of batched updates.
