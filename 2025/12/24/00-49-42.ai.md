This is a discussion about configuration flexibility for the proposed `git status` branch comparison feature. Yee Cheng Chin responds to Junio C Hamano's concerns about hardcoded remote preferences in the current implementation, providing real-world context from maintaining the MacVim fork.

The email highlights several key workflow considerations that challenge the current design's assumptions. Chin notes that not all users configure separate push/pull remotes, especially for feature branches where collaborators need to pull from the same branch. They argue the feature should still show divergence from the mainline even when push/pull remotes aren't fully configured.

Chin introduces a concrete example from MacVim maintenance where "upstream" is context-dependent - sometimes referring to their personal fork versus the main MacVim repo, other times referring to MacVim versus the original Vim project. This demonstrates how the current hardcoded "upstream/HEAD" or "origin/HEAD" assumptions break down in complex forking scenarios.

The response suggests the feature might need to evolve toward supporting multiple comparison points rather than a single default branch. Chin speculates users may eventually want to see divergence from several reference branches simultaneously, particularly in projects with layered forks or multiple integration points.
