This is a feature proposal and design discussion about improving merge conflict metadata and UX during rebase operations. Esteban Küber responds to D. Ben Knoble's suggestions about existing Git features that could help with identifying rebase state, while also raising new concerns and proposals.

The email confirms that several existing Git files and references (.git/rebase-merge, FETCH_HEAD, MERGE_MSG) can provide enough information for tooling to identify rebase state without invoking Git commands directly, though some parsing relies on potentially fragile text formats. Küber specifically notes concerns about relying on the exact formatting of MERGE_MSG messages like "Merge branch 'main' into branch-name".

Two key proposals emerge: 1) exposing merge/rebase metadata in a more structured format for tools, and 2) enhancing conflict markers to include branch information alongside commit SHAs. The proposed marker format would explicitly show branch names in various rebase/merge scenarios to help users understand the conflict context. Examples demonstrate how this might look for `git rebase`, `git merge`, and `git pull` (both with and without --rebase).

The discussion remains focused on improving tooling support for conflict resolution, now with concrete suggestions for UI changes. While Küber has found workable solutions using existing Git internals, the proposals suggest these could be made more robust and user-friendly. The thread shows progress toward addressing the original problem but leaves open questions about the stability guarantees of current interfaces and the desirability of the proposed marker changes.
