This is a follow-up in the ongoing macOS iconv encoding conversion thread, specifically addressing the build-system approach to prefer Homebrew's libiconv over the system version. René Scharfe clarifies the behavior of his proposed `config.mak.uname` changes regarding architecture-specific Homebrew installations on Apple Silicon.

Key technical details:
- The patch already handles both `/opt/homebrew/opt/libiconv/` (native ARM64) and `/usr/local/opt/libiconv/` (x86-64 under Rosetta 2) cases
- It will prefer the native ARM64 version when both are present
- Falls back to x86-64 version if that's the only one installed
- Maintains escape hatch to force system iconv via explicit `ICONVDIR` setting

The response confirms the solution accounts for Yee Cheng Chin's Rosetta 2 compatibility concern while maintaining consistency with Git's existing gettext handling. This builds on the thread's established understanding that Homebrew's libiconv provides a working alternative to macOS 15+'s broken system implementation for stateful encodings like ISO-2022-JP.

The exchange shows progress toward resolving one of the three proposed solution approaches (build-system detection), though the thread's broader questions about combining approaches and handling non-Homebrew systems remain open.
