This is a UX improvement proposal for SSH authentication failures. Ryan Johnson identifies a common pain point where Git's SSH authentication failures don't indicate which SSH client implementation is being used, which can differ from what the user expects due to multiple SSH installations on a system (system vs bundled versions on Windows/macOS/Linux).

The core issue is that when authentication fails, Git simply shows a generic permission denied message without revealing it might be using a different SSH binary than the one the user tested manually. This leads to frustrating debugging sessions where users don't realize the root cause is a client mismatch.

The proposed solution would have Git:
1. Display the SSH command path it's actually using
2. Detect and list other available SSH binaries on the system
3. Suggest how to configure a different SSH client via `core.sshCommand`

The change would only trigger on authentication failures, not successes. The author argues this is particularly important for Git as a standard tool, where such UX issues create unnecessary friction for both beginners and experienced users. The proposal is framed as shifting responsibility from users having to debug obscure configuration issues to the tool providing clear diagnostics.

Key technical points for future reference:
- Affects SSH authentication failure paths
- Would add detection of multiple SSH binaries in PATH/common locations
- Would modify error output to show used SSH path and alternatives
- References common installation paths on Windows (System32 vs Git bundled), macOS (system vs Homebrew), and Linux (system vs Snap/Flatpak)
- Suggests using `core.sshCommand` as the solution
- Implicitly touches Git's cross-platform SSH client selection logic

The proposal is likely to be uncontroversial as it improves diagnostics without changing behavior, though implementation might need to consider:
- Platform-specific path detection
- Performance impact of scanning for SSH binaries
- Whether to make the multi-SSH detection optional/configureable
