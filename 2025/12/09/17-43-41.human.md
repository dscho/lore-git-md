This is a discussion about the multi-branch commit handling behavior in Patrick Steinhardt's proposed `git-history` command series. Martin von Zweigbergk weighs in on the ongoing debate between Patrick Steinhardt and Elijah Newren about how the command should handle commits that appear in multiple branches.

Martin strongly agrees with Elijah Newren's position that the command should default to rewriting all branches containing the modified commit (option c), which matches the behavior in Jujutsu (jj) where Martin is a maintainer. He argues this is the right approach based on Jujutsu's experience, noting that cases where users want to modify a commit while leaving some descendants unchanged are extremely rare. 

Martin also addresses the performance concerns about checking references (option a), suggesting that while checking all branches might be expensive in repositories with hundreds of thousands of branches, he expects this would primarily be a server-side issue where users wouldn't run interactive history editing tools anyway.

The discussion continues to center around finding the right balance between safety (preventing accidental history divergence) and usability (not burdening common cases with extra flags or checks). Martin's perspective as a Jujutsu maintainer provides real-world evidence that the more aggressive branch-rewriting behavior (option c) works well in practice.
