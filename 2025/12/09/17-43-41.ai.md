This is a discussion about the multi-branch commit handling behavior in Patrick Steinhardt's proposed `git-history` command series. Martin von Zweigbergk weighs in on the ongoing debate between Patrick Steinhardt and Elijah Newren regarding how the command should handle commits that appear in multiple branches.

Martin strongly supports Elijah Newren's position (option c) that the command should rewrite all branches containing the commit by default, aligning with Jujutsu's behavior where he is a maintainer. He argues this is the right approach based on Jujutsu's experience, noting that wanting to rewrite only some descendants is extremely rare. For those edge cases, Jujutsu provides a `duplicate` command as a workaround.

On the implementation concerns, Martin suggests that checking all branches for commit ancestry (option a) should be performant enough in practice, though acknowledges there may be scaling issues with repositories having hundreds of thousands of branches. He speculates such large repositories would likely be server-side where users wouldn't run interactive history editing commands.

The email reinforces the philosophical divide in the thread between Git's conservative approach (Patrick's current-branch-only behavior) and Jujutsu-inspired flexibility (Elijah and Martin's multi-branch rewriting). Martin's perspective as a Jujutsu maintainer adds weight to the argument that the multi-branch case is both safe and desirable as a default.
