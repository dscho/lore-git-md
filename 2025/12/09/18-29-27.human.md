This is a discussion contribution in the ongoing debate about the behavior of the new `git-history` command's handling of commits that exist on multiple branches. Kristoffer Haugsbakk weighs in strongly in favor of Elijah Newren and Martin von Zweigbergk's position that the command should default to updating all branches containing the modified commits, rather than Patrick Steinhardt's current-branch-only approach.

The email makes several key points: First, it provides concrete examples (splitting formatting fixups and fixing typos) where modifying commits across all branches would be the expected behavior. Second, it endorses Elijah's earlier arguments about safer multi-branch handling. Third, it connects this to Jujutsu's successful implementation of similar functionality, while acknowledging the Git context of branch-focused workflows.

Kristoffer suggests that while the all-branches behavior might be surprising compared to Git's current commands, it represents a better default for a new command designed specifically for history editing. The email also speculates about potential future workflows involving temporary integration branches, though it recognizes the current limitations of `git-history` regarding merge commits.

This contribution adds weight to the growing consensus that favors more aggressive branch updating, while maintaining a constructive tone that acknowledges implementation challenges. The discussion remains unresolved but appears to be trending toward reconsidering the default behavior before the feature lands in 'next'.
