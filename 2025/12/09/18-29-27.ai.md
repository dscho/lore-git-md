This is a discussion contribution to the ongoing debate about multi-branch commit handling in the `git-history` command series. Kristoffer Haugsbakk weighs in strongly in favor of Elijah Newren's position advocating for rewriting all branches containing affected commits by default, directly challenging Patrick Steinhardt's current-branch-only approach.

The email makes several key arguments: (1) common history editing operations like splitting commits or fixing typos would naturally apply across all branches containing those commits, (2) the proposed behavior aligns well with stacked branch workflows, and (3) while divergent histories are possible, they represent an edge case that shouldn't dictate defaults. Haugsbakk references Jujutsu's "mega merge" strategy as inspiration for how multi-branch editing could enable powerful workflows, though acknowledges the current `git-history` implementation doesn't handle merges.

Notably, this adds a new voice to the debate between Patrick's conservative approach (favoring explicit opt-in for multi-branch operations) and Elijah/Martin's more aggressive stance (favoring automatic multi-branch updates). The contributor brings practical workflow examples supporting the latter position while acknowledging implementation complexity. The message also highlights the tension between Git's traditional branch-centric model and Jujutsu-inspired approaches that treat commits more independently.
