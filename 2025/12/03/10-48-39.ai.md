Feature implementation completing the v7 series for `git-history`'s split subcommand. This final patch introduces the interactive splitting of commits into two parts, building on the infrastructure from previous patches (in-memory index patching, cache-tree support, and replay machinery).

The implementation handles splitting of tip, root, and in-between commits while preserving working tree and index state. Key technical aspects include:
- Uses the new `run_add_p_index()` from patch 9/12 for in-memory index operations
- Leverages `write_in_core_index_as_tree()` modified in patch 11/12
- Applies the `ADD_P_DISALLOW_EDIT` flag from patch 10/12 to prevent hunk editing conflicts
- Validates against empty commits (either split-out or remaining)
- Preserves original authorship and commit metadata
- Includes extensive test coverage (452 lines) for various scenarios

The command workflow matches interactive rebase's split functionality but with a simpler interface (`git history split $COMMIT`). It shows the diff and prompts for which hunks to move to a new commit, then creates two commits (the split-out changes and the remainder) while maintaining the original branch position. Pathspecs can limit which changes are considered for splitting.

Potential discussion points:
- The implementation currently uses a temporary index file despite the in-memory infrastructure, due to `read-tree` requirements
- Test coverage verifies edge cases like empty commits, merge commits, and path limiting
- The documentation example clearly shows the before/after state
- Hooks are intentionally not executed for the rewritten commits
