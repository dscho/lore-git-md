This is a user discussion about the behavior of the proposed `git-history` command's branch handling during history editing operations.

Matthias Beyer weighs in on SZEDER Gábor's concern about the potentially "scary" behavior of rewriting all descendant commits when using the new `git-history` command. The discussion centers around a complex branch topology where multiple branches share common ancestors.

Beyer suggests that by default, the command should only allow rewriting commits that are ancestors of the current branch (branch2 in the example), requiring explicit flags to modify other branches. This would prevent accidental rewriting of unrelated branches (like branch1, branch3, and branch4) that happen to share common history. The comment reflects a user perspective on safety boundaries for the new history editing capabilities.

This feedback comes as the `git-history` series (now at v7) nears potential inclusion in Git, with its `reword` and `split` subcommands implementing non-conflicting operations on linear histories. The discussion highlights one of the remaining open questions about how the tool should handle more complex repository topologies.
