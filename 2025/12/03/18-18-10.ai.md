This is a discussion about the scope of history rewriting operations in the proposed `git-history` command series, specifically regarding multi-branch commit handling.

Matthias Beyer responds to SZEDER Gábor's concerns about the potentially "scary" behavior of rewriting commits that have multiple descendants across different branches. The discussion stems from Patrick Steinhardt's earlier indication that the `git-history` commands would rebase all descendants when modifying history, similar to Jujutsu's behavior.

Beyer offers a user perspective, suggesting that by default the command should only allow rewriting commits that are ancestors of the current branch (branch2 in the example), requiring explicit flags to modify commits with descendants on other branches. The example shows a complex history where commit B has descendants on four different branches (branch1-branch4), making its modification potentially disruptive without clear user intent.

This feedback touches on one of the open questions from the series regarding multi-branch commit handling tradeoffs. The discussion highlights the tension between Jujutsu-inspired behavior (rewriting all descendants by default) and Git's more conservative approach to history modification. Beyer's position aligns with making the behavior more restrictive by default to prevent accidental widespread history rewrites.
