This is a follow-up discussion about the lockfile PID debugging feature, focusing on NFS environments. Torsten Bögershausen builds on the existing thread about adding `.lock.pid` files to identify lock holders, suggesting an enhancement for distributed filesystem scenarios.

The core proposal remains unchanged from the initial implementation: creating PID companion files when `GIT_LOCK_PID_INFO=1` is set, with tempfile integration for cleanup and process-alive checking via `kill(pid, 0)`. Torsten's contribution specifically addresses NFS use cases where lock files might be shared across multiple machines. He suggests including the hostname alongside the PID in the companion file, noting Git already has the `xgethostname()` function available for this purpose.

This raises new technical questions about the feature's scope: whether to track host information for distributed debugging, and if so, whether to make it a separate opt-in or bundle it with PID tracking. The suggestion implies potential false positives could occur in NFS environments if only PIDs are considered, since different machines might coincidentally have processes with identical PIDs holding locks. No implementation is proposed yet - this is positioned as a design consideration that would expand the debugging metadata while maintaining the existing tempfile-based cleanup mechanism.
