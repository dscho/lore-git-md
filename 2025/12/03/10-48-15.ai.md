This is a discussion about potential future subcommands (`drop` and `reorder`) for the `git-history` command series. The email is part of the ongoing RFC proposal for the `git-history` feature.

Patrick Steinhardt responds to D. Ben Knoble's real-world use cases for the previously implemented (but now removed) `drop` and `reorder` subcommands. Knoble provides concrete examples where these subcommands proved useful in his workflow: using `drop` to clean up temporary commits when splitting work across branches, and using `reorder` to rearrange WIP commits during development.

Steinhardt acknowledges the value of these subcommands but notes technical challenges in implementing them with the current replay-based infrastructure, particularly around conflict handling. He suggests a potential path forward where initial versions could simply bail on conflicts, with plans to iterate on the implementation later.

The exchange highlights a tension in the series' evolution - while the current v6 focuses on `reword` and `split`, there's clear user demand for the broader functionality originally envisioned. The discussion suggests these subcommands may be reconsidered for future iterations, though their implementation would need to adapt to the series' new technical foundation in the replay machinery. The email reinforces that the current series represents only part of the envisioned `git-history` functionality, with more subcommands likely to follow if the core infrastructure proves successful.
