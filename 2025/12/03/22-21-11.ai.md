This is a follow-up discussion about the lockfile debugging feature, specifically addressing the refs collision risks identified by Jeff King. Junio Hamano proposes an alternative approach to the PID file mechanism that might avoid the refs namespace collision problem entirely.

The suggestion pivots from creating `.lock.pid` companion files to instead maintaining a single audit log file (`$GIT_DIR/lockfile-audit`) that would record lock acquisitions in append-only mode. This would eliminate the risk of refs collisions since no additional files are created in the refs namespace. The proposal considers using O_APPEND to handle concurrent writes safely, though notes this might introduce other complexities around log file management and record formatting.

This represents a significant design shift from the original implementation, moving from per-lock PID files to a centralized logging approach. The key technical considerations now include: log file location (must be outside refs namespace), record format constraints (fixed-size entries for atomic writes), and multi-process synchronization requirements. The suggestion implicitly addresses peff's collision concerns while maintaining the debugging capability's core purpose.

The thread continues to explore activation mechanisms (now suggesting a file-based trigger rather than environment variable) while grappling with the fundamental tension between debuggability and safety. This proposal would require substantial implementation changes but offers a path forward that avoids the dangerous edge case with ref operations.
