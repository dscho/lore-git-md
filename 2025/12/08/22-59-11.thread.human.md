This thread addresses a macOS-specific character encoding regression in Git's test suite, where macOS 15's built-in `iconv` implementation fails to properly handle stateful encoding conversions (specifically ISO-2022-JP to UTF-8) during buffer growth operations. The issue was first reported by René Scharfe and confirmed by Yee Cheng Chin as a regression in macOS 15, stemming from Apple's switch to a custom `iconv` implementation based on a problematic FreeBSD version.

Three solution approaches have emerged: René's original code workaround with state resets, Torsten Bögershausen's platform-specific detection, and René's newer proposal to use Homebrew's `libiconv` when available. The latter approach gained validation when René confirmed Homebrew's implementation properly handles UTF-8-MAC encoding (with some alias variations) and passes most tests, except for a known decomposed filename edge case.

The discussion has now shifted to implementation details. In the latest exchange, René and Carlo Marcelo Arenas Belón are working through practical build system considerations - particularly how to handle universal (multi-architecture) macOS binaries and where to place package manager configuration flags in the Makefile. They agree on adding a `NO_HOMEBREW` flag for consistency with existing patterns like `NO_DARWIN_PORTS`, while keeping the Homebrew path opt-in via `ICONVDIR` override.

Key open questions remain about the hierarchy between different `libiconv` sources (Homebrew vs MacPorts vs system), final flag placement, and handling systems without alternative `libiconv` installations. The thread shows steady progress toward a solution that balances technical correctness with real-world deployment constraints across diverse macOS environments.
