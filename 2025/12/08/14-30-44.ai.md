This is a response to a bug report about data loss in `git pull --rebase` with multiple push URLs. Phillip Wood confirms the issue and provides technical analysis of why it occurs: when a push partially fails (succeeding on one URL but not another), the subsequent rebase incorrectly uses the fork-point logic, causing it to drop local commits that were actually pushed successfully to one remote.

The key insight is that `git push` updates the remote-tracking branch (refs/remotes/origin/master when pushing to "mirror"), making the fork-point calculation think there's nothing to rebase. Phillip suggests a workaround using `git fetch && git rebase --no-fork-point` and references prior discussion about adding a `--no-fork-point` option to `git pull`, though previous attempts lacked tests.

The response identifies the core issue in the fork-point calculation logic during rebase operations after partial push failures, particularly affecting repositories with multiple push URLs. Phillip links to two relevant past discussions about fork-point problems, indicating this may be a recurring pain point in the rebase/pull integration. The suggested workaround bypasses the problematic fork-point logic entirely.
