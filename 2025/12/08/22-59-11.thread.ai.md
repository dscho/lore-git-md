Character encoding conversion issue with iconv(3) on macOS affecting t3900 tests, originally reported by René Scharfe. The problem involves incomplete ISO-2022-JP to UTF-8 conversion in `reencode_string_iconv()` where macOS's iconv implementation loses state between buffer growth operations for stateful encodings. Yee Cheng Chin confirmed this is specific to macOS 15 (not present in 14.8.2), despite Apple's broader iconv implementation switch from GNU to custom in macOS 14. Collin Funk provided historical context about Apple's custom iconv being based on a buggy FreeBSD version.

Two workaround approaches are under discussion:
1. René Scharfe's original patch using an `ICONV_BREAKS` compile-time flag that forces full-string reconversion during buffer growth, including explicit state reset via `iconv(conv, NULL, NULL, NULL, NULL)`
2. Torsten Bögershausen's alternative proposal that:
   - Tracks original input size rather than recalculating
   - Uses `#ifdef __APPLE__` for platform-specific targeting
   - Omits the explicit state reset call
   - Maintains the same core retry-with-larger-buffer approach

Both solutions address the macOS 15 regression in `reencode_string_iconv()`'s state handling during buffer expansion in convert.c. The thread maintains consensus that this is a platform regression (not a Git bug), with technical focus now shifting to implementation details of the workaround. Key open questions include:
- Whether to use a configurable flag (`ICONV_BREAKS`) or platform detection (`__APPLE__`)
- The necessity and safety of explicit state reset calls
- Relative merits of tracking original vs. recalculated input size
