Character encoding conversion issue with iconv(3) on macOS affecting t3900 tests, originally reported by René Scharfe. The problem involves incomplete ISO-2022-JP to UTF-8 conversion in `reencode_string_iconv()` where macOS's iconv implementation loses state between buffer growth operations for stateful encodings. Yee Cheng Chin confirmed this is specific to macOS 15 (not present in 14.8.2), despite Apple's broader iconv implementation switch from GNU to custom in macOS 14. Collin Funk provided historical context about Apple's custom iconv being based on a buggy FreeBSD version.

Three solution approaches are now under discussion:
1. René Scharfe's original code-based workaround using `ICONV_BREAKS` compile-time flag with explicit state reset during buffer growth
2. Torsten Bögershausen's alternative code-based approach using `__APPLE__` platform detection but lacking state reset (shown incomplete by test failures)
3. René's new build-system approach detecting and preferring Homebrew's libiconv when available (`/opt/homebrew/opt/libiconv/` or `/usr/local/opt/libiconv/`)

Technical analysis has established:
- macOS 15+ has a platform regression in stateful encoding handling
- Explicit state reset (`iconv(conv, NULL, NULL, NULL, NULL)`) is essential for correct operation
- Torsten's alternative currently fails t0028-working-tree-encoding.sh due to missing state reset
- Homebrew libiconv provides a known-good alternative implementation
- The build-system approach doesn't cover systems without Homebrew

Key open questions:
- Whether to combine approaches (e.g. Homebrew preference + fallback workaround)
- Final decision between `ICONV_BREAKS` flag vs `__APPLE__` detection for code workaround
- Handling of non-Homebrew macOS 15+ systems
- Verification of solution completeness across all stateful encodings
