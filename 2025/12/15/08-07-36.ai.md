This is a technical discussion about git-am behavior with mbox files, specifically in the context of applying a Linux kernel patch series addressing dyndbg regressions.

Jeff King (peff) explains why Jim Cromie is experiencing different patch application failures when using mbox files downloaded from lore.kernel.org versus the mutt-based workflow that worked previously. The core issue is that lore's mbox files preserve the order messages were received rather than the intended patch sequence, and git-am applies patches in the order found without any heuristics for sorting.

Key technical points:
- git-am processes mbox messages in file order without regard to dates or patch numbering
- Non-patch messages (like cover letters) can interfere unless filtered with --empty=drop
- Mutt's message sorting by RFC822 date happened to produce the correct order
- b4 tool's "am" subcommand can properly reconstruct the intended patch series order

The email suggests b4 as a more robust solution than manual mbox handling, noting it can:
- Version selection (picking latest series in multi-version threads)
- Proper patch ordering
- Automatic filtering of non-patch messages

This continues the thread's theme of patch application challenges being a problem distinct from (but complicating validation of) the underlying dyndbg fixes. The discussion has shifted from diagnosing the problem to recommending tooling solutions.
