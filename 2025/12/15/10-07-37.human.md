This is a feature patch for the experimental `git replay` command, implementing behavior to drop commits that become empty during replay (when their changes already exist in the target branch). The change aligns `git replay` with the behavior of `git rebase --reapply-cherry-picks --empty=drop` and `git cherry-pick --empty=drop`.

The patch modifies the commit-picking logic in `replay.c` to compare tree OIDs to detect empty commits, preserving only originally-empty commits while dropping those that become empty during replay. When a branch tip commit is dropped, the branch pointer is updated to point to the last non-dropped commit. The change includes documentation updates and a new test case showing the behavior when commit `F` is dropped from `topic1`.

The implementation has gone through review with Elijah Newren providing suggestions that were incorporated, including test simplification and commit message formatting improvements. Maintainer Junio C Hamano has endorsed the core approach, agreeing that dropping empty commits is sensible when changes exist in the target branch. The patch is still marked as experimental, allowing for this behavior change, with the option to add a flag later if users need to retain empty commits.

The technical implementation appears solid, with clear test coverage and alignment with existing Git behaviors. The discussion shows consensus on the approach, with the main remaining question being whether to base the next version on `master` or the `ps/history` branch.
