This thread documents and discusses the behavior of `git rev-list --filter` when objects are explicitly provided. Justin Tobler's patch clarifies in the documentation that such objects bypass filter restrictions by default, only respecting filters when `--filter-provided-objects` is specified. The behavior stems from Patrick Steinhardt's conservative implementation prioritizing backward compatibility for partial clone users, though no positive use cases for this default exist.

Junio Hamano has accepted the documentation patch as accurate while expressing dissatisfaction with the design. In a follow-up, he speculates the behavior persisted because commit objects (the typical filtered target in partial clones) are rarely filtered out, which may explain why the issue wasn't noticed earlier. Both Steinhardt and Hamano emphasize that while the current behavior is suboptimal, changing it would require careful research into potential impacts on partial clone workflows.

The thread has established consensus that:
1) The documentation should reflect the current implementation
2) The behavior exists solely for compatibility, not by design
3) No known use cases justify the current default
4) Future changes would need safety assurances

The minimal documentation patch remains queued for merge, preserving the option to revisit the design later. The discussion provides valuable context about the behavior's origins and the practical constraints that shaped it.
