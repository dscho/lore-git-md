This is a follow-up to the recently fixed `git replay` segfault bug, where Kristoffer Haugsbakk proposes an additional improvement to error handling. The thread had previously addressed a NULL pointer dereference when using `--onto` with a non-existent commit, which has now been fixed with René Scharfe's patch.

Kristoffer shares a work-in-progress change that would make `git replay` fail more explicitly when given invalid commit-ish arguments for either `--onto` or `--advance`. The proposed patch modifies `peel_committish()` to call `die()` with a descriptive error message when the commit cannot be found, rather than silently returning NULL. This would distinguish between missing arguments (which currently show the "root commit not supported" message) and invalid arguments.

The author notes this is still untested and raises a question about memory leaks during error conditions, suggesting this is an early-stage proposal rather than a final patch. This builds on Phillip Wood's earlier observation about the preexisting behavior of treating invalid and missing arguments identically, though the current proposal doesn't yet address the root commit limitation that remains marked as FIXME in the code.

Key technical details include:
- Changes to `builtin/replay.c`'s `peel_committish()` function
- New error message format for invalid commit-ish arguments
- Potential interaction with existing error paths and memory management
- Maintains the distinction between this change and the unresolved root commit support limitation

This appears to be a logical next step in improving `git replay`'s error handling, though it may need testing and refinement before being ready for submission. The change is narrowly scoped to argument validation while leaving the larger architectural questions about root commit support for future work.
