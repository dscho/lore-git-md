This is a feature patch modifying the experimental `git replay` command to drop commits that become empty during replay, matching the behavior of `git rebase --reapply-cherry-picks --empty=drop` and `git cherry-pick --empty=drop`. The change is part of an ongoing effort to refine `git replay`'s behavior while it remains experimental.

The core change compares tree OIDs in `replay.c` to detect when a commit's changes are already present in the target branch, dropping such commits while preserving originally-empty commits. When a branch tip commit is dropped, its reference is updated to point to the last non-dropped commit. The implementation uses a temporary variable for `result->tree` assignment as suggested in previous feedback.

Test coverage in t3650-replay-basics.sh demonstrates the behavior, showing how `topic1` updates to point to rebased `C` when `F` is dropped. The test has been simplified from v1 to directly check branch states rather than reconstructing output via sed, incorporating Elijah Newren's suggestions. The test also verifies branch pointer updates and uses `test_when_finished` for cleanup.

The patch is based on the `ps/history` branch, though Phillip Wood is considering whether to rebase on `master` for the next version. The commit message notes this is a breaking change but justified by `git replay`'s experimental status, leaving room for a future option to retain empty commits if user feedback indicates it's needed.

Technical details include:
