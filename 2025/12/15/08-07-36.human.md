This is a technical discussion about patch application workflows, specifically addressing issues with applying Linux kernel patches from mbox files downloaded from lore.kernel.org.

Jeff King explains why Jim Cromie is experiencing different patch application failures when using mbox files directly from lore.kernel.org versus extracting patches manually with mutt. The core issue is that lore's mbox files preserve the order messages were received (which may not match the intended patch sequence), while `git am` applies patches in the exact order found in the input file.

The email highlights several subtle problems with mbox-based patch application:
- Non-patch messages (like cover letters and reviews) may be incorrectly processed
- Patch ordering can be wrong since lore's ordering doesn't necessarily reflect the intended sequence
- Subject line heuristics for ordering have limitations

King recommends using the `b4` tool's `am` command instead of direct mbox processing, as it handles both version selection (when multiple patch series versions exist) and proper patch ordering automatically. This builds on earlier thread discussion where different workflow approaches were compared, with `b4` emerging as the most reliable solution for this complex patch series.

The email doesn't propose any code changes to Git itself, but rather shares practical advice for working with kernel patch series where strict application order matters (as in the ongoing dyndbg regression fixes). It serves as a workflow tip that could help others facing similar patch application challenges.
