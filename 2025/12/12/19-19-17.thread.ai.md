Summary of git replay raw hash behavior discussion:

Thread examines behavior of `git replay` when given raw commit hashes instead of branch references. Current implementation silently creates new commits in object database but provides no output or ref updates when input lacks branch decoration (works only with branch-decorated commits). Example problematic usage: `git replay --onto master master..45ab67bc`.

Key technical details:
- Limitation stems from `DECORATION_REF_LOCAL` check in `handle_ref_update`
- Creates commits but leaves them unreachable (no ref updates or output)
- Works as designed but may not match user expectations

Proposed directions:
1. Add mode to print new commit IDs for scripting/experimentation
2. Error out to make limitation explicit
3. Keep current behavior but document clearly

Use cases mentioned:
- Scripting scenarios where branch names aren't desired
- Experimental workflows creating temporary commits

Open questions:
- Should this be considered a bug or enhancement?
- Which solution best balances safety and flexibility?
- Would printing commit IDs create new footguns?

Related work:
- `git replay` documentation and existing ref update behavior
- Similar commands' handling of raw hashes (e.g. `git cherry-pick`)
