Bugfix addressing Rust build system incompatibility between GNU and BSD sed variants.

Eric Sunshine confirms D. Ben Knoble's analysis of the macOS build failure, agreeing that the GNU-specific `-s` flag in the sed command is unnecessary for parsing cargo's host platform information. The current implementation breaks on BSD-derived sed (like macOS's) when determining library naming conventions (`gitcore.lib` vs `libgitcore.a`) for Rust builds.

The core issue lies in the sed command processing `cargo -vV` output to extract the host platform string (e.g., `x86_64-apple-darwin`). While the original code used GNU sed's `-s` flag (which treats input files separately), Eric points out this can be replaced with the more portable combination of `-n` (suppress automatic printing) and `p` (print only matching lines) flags. This maintains the same functionality while working across sed implementations.

The problematic code was introduced in commit e509b5b8be as part of Windows Rust support. The discussion suggests this was likely an oversight rather than an intentional GNU dependency, as the `-s` flag doesn't appear necessary for the simple pattern matching being performed. The fix would unblock Rust-enabled builds on macOS while maintaining existing behavior on other platforms.

This appears to be a straightforward fix with clear technical merit, though no patch has been submitted yet. The change would be localized to the build system's Rust support logic and doesn't affect runtime behavior. The discussion remains technical and collaborative, with consensus forming around the solution approach.
