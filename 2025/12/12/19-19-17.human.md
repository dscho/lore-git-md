This is a feature discussion about the behavior of the new `git replay` command when working with raw commit hashes rather than branch names.

The author, Yee Cheng Chin, points out that `git replay` currently only shows output or updates references when replaying commits tied to a local branch. When given raw commit hashes (like `master..45ab67bc`), it silently creates new commits in the object database without any feedback about what was created. This makes it difficult to use the command for experimentation or scripting where branch names aren't desired.

The email suggests two possible improvements: either adding a mode that prints the created commit hashes for manual handling, or making the command fail with an error when given raw hashes to avoid silent behavior. The current behavior is described as confusing since the command succeeds but provides no output or feedback about what it did.

This appears to be a well-articulated observation about a rough edge in the new command's UX. The use case for working with raw commits seems reasonable, particularly for experimentation and scripting scenarios where branch names might be undesirable. The patch would likely be welcome as it improves the command's usability without changing its core functionality.
