This is a follow-up discussion about the ongoing platform compatibility effort to require C99 flexible array syntax in Git's codebase. Patrick Steinhardt questions the approach of tying this change to the Git 3.0 breaking changes document, suggesting it might be better handled as a test balloon like other C99 feature adoptions.

The email raises several technical points: (1) the change doesn't seem more breaking than previous C99 feature introductions, (2) proposes two alternative implementation approaches (unconditional conversion of FLEX_ARRAY sites vs. maintaining backward compatibility), and (3) suggests the Git 3.0 tie-in might be premature since problematic platforms could still be discovered.

Key considerations mentioned include the minimal code impact (just a few lines either way) and the established pattern of testing C features before full adoption. The discussion centers on process rather than technical objections, with Steinhardt acknowledging the change's technical soundness while questioning its classification as a breaking change warranting Git 3.0 documentation.

This continues the thread's examination of how to phase out legacy C constructs while maintaining Git's backward compatibility guarantees, with particular focus on the project's established patterns for introducing modern C features.
