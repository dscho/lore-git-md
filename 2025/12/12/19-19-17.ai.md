This is a feature discussion about the behavior of `git replay` with raw commit hashes. The email points out that while `git replay` successfully processes commits when given raw hashes (without branch reference), it doesn't output the resulting commit IDs or update any refs, which could be confusing or problematic for users.

The key observations are:
1. Current behavior silently creates new commits in the object database when given raw hashes, but provides no output or ref updates (only works with branch-decorated commits)
2. The author suggests this could be useful for experimentation or scripting where branch names aren't desired
3. Two potential solutions are proposed: either add a mode that prints the new commit IDs, or error out to make the limitation clearer

The email includes concrete examples of the problematic usage patterns (`git replay --onto master master..45ab67bc` and similar). This appears to be a genuine usability concern rather than a bug, as the command is working as currently designed - the question is whether that design should be changed.

The discussion touches on the `DECORATION_REF_LOCAL` check in `handle_ref_update` as the current limiting factor. This seems like it could spark debate about whether the current behavior is intentional (and thus should error) or an oversight (and should be enhanced). The mention of scripting use cases provides concrete motivation for considering a change.
