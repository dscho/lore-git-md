This is a follow-up discussion in the ongoing `git-history` command RFC thread, specifically addressing documentation accuracy in the patch series introduction.

Patrick Steinhardt clarifies an earlier point about the scope of the `git-history` command's subcommands. While the original cover letter listed several potential use cases (reordering, splitting, dropping, and squashing commits), Elijah Newren correctly notes that the current v6 series only implements two subcommands (`reword` and `split`). Patrick confirms this was intentional - earlier versions had more subcommands, but the series has never included implementations for all the originally proposed operations.

This exchange highlights an important documentation issue in the series: the introductory text needs to accurately reflect the current implementation scope rather than the original vision. The thread shows maintainers paying close attention to ensuring the documentation matches reality of what's being proposed, even in introductory material. This level of scrutiny suggests the series is nearing readiness for experimental merging, though some documentation updates are still needed.
