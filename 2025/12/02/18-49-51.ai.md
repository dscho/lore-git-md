This is a discussion about branch handling behavior in the experimental `git-history` command series, specifically around how it should handle commits that exist in multiple branches' histories.

Patrick Steinhardt responds to Elijah Newren's concerns about the current implementation's handling of commits that appear in multiple branches. The current implementation only verifies that the commit is part of the current branch, not that it's exclusive to that branch. Elijah had raised this as a potential bug, suggesting three solutions: documentation/warning, erroring out for multi-branch cases, or automatically rewriting all affected branches.

Patrick argues this isn't a bug but working as designed, as he personally frequently has commits on multiple branches (like dependent patch series) and would only want to modify the current branch. He raises concerns that checking for multi-branch presence could be expensive (requiring walking all references) and suggests doing nothing for now, with the option to add a flag for multi-branch rewriting later.

Key technical points:
- Current behavior only checks commit is in current branch via `verify_reachable_from_head()`
- Potential performance impact of checking all references
- Design question around whether multi-branch modification would be surprising
- Series is explicitly marked experimental to allow future behavior changes

The discussion reveals differing perspectives on what constitutes expected behavior for history editing tools, with Patrick favoring a more conservative approach that matches his personal workflow, while Elijah advocates for either preventing or properly handling multi-branch cases from the start. The experimental nature of the command provides flexibility to adjust based on user feedback.
