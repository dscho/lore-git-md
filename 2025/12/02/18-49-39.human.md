This is the final patch in Patrick Steinhardt's v6 series introducing the `git history` command, specifically implementing the "split" subcommand. The patch allows interactively splitting a commit into two parts by selecting hunks to move into a new commit that becomes the parent of the original.

The implementation follows Jujutsu's model of binary splits (always creating exactly two commits) and preserves authorship while prompting for new commit messages. The patch includes extensive test coverage for various edge cases like path limiting, hook execution, and worktree preservation.

In this email, Patrick responds to Elijah Newren's review feedback, agreeing to several improvements:
- Will prompt for messages for both commits (not just the split-out one)
- Will preserve extended headers that were being discarded
- Will disable hunk editing for now to avoid complications
- Explains the rationale behind requiring split commits to be reachable from HEAD (as a temporary conservative measure)

The discussion reveals some remaining design questions about whether to eventually support multi-way splits and how to handle unrelated commits, but Patrick advocates for starting simple. The patch appears well-tested and thoughtfully implemented, though some interface decisions may evolve based on user feedback.
