This is a discussion about branch handling behavior in the experimental `git-history` command, specifically around whether commits that exist on multiple branches should be modified across all branches by default.

Patrick Steinhardt responds to Elijah Newren's concerns about potential branch divergence when editing commits that exist in multiple branches' histories. The current implementation only modifies the current branch, which Patrick argues is intentional design rather than a bug. He notes the command already verifies the commit is part of the current branch (though not exclusively), and shares his personal workflow where commits often exist on multiple dependent branches intentionally.

The discussion centers on three potential approaches to handling multi-branch cases: (1) document and warn, (2) error out unless user opts in, or (3) rewrite all relevant branches automatically. While Elijah advocates for option 3 as being both simpler to implement and more user-friendly, Patrick expresses concerns about performance implications of checking all references and suggests the current single-branch behavior may actually be what users expect. He leaves open the possibility of adding an opt-in flag for multi-branch rewriting in the future.

This exchange highlights an important design decision point for the new command, with Patrick leaning toward keeping the current focused behavior for the experimental phase while acknowledging the need to clearly document the limitations. The thread shows healthy technical debate about balancing correctness, performance, and user expectations in a new feature.
