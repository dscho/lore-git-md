This thread continues the discussion about adding process ID tracking to Git's lockfiles for debugging purposes. Paulo Casaretto's v2 patch introduced `.pid.lock` files to help identify processes holding locks, with the design evolving through feedback from Jeff King, Taylor Blau, Patrick Steinhardt, and Junio Hamano. The current implementation includes a configurable approach (`core.lockfilePID`), confirmed backward compatibility, and comprehensive tests.

The technical discussion has now shifted to edge cases in production scenarios. Ben Knoble's latest email raises an important question about abnormal process termination - whether the PID information would remain accessible if a crash prevents proper lock cleanup. While the patch handles PID file cleanup via tempfile mechanisms, it's unclear if stale locks would leave the system in a state where the PID information is still useful for debugging. This highlights a gap in the failure mode analysis that may need addressing before finalizing the feature.

Key participants have established positions: Paulo is implementing the changes, Taylor influenced the naming scheme, Jeff advocated for subsystem control, and Junio confirmed the backward compatibility. The remaining open questions now focus on NFS behavior verification, final naming conventions, documentation updates, and - with Ben's input - ensuring the solution works reliably in crash scenarios. The implementation appears technically sound overall, but this latest discussion suggests one more edge case to consider before the feature is production-ready.
