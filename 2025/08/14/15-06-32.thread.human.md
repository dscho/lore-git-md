This thread addresses a bug in submodule handling when the superproject and submodule use different hash algorithms (SHA-1 vs SHA-256). The core issue involves shallow submodule clones failing due to hash length mismatches when interpreting padded commit hashes as refnames. Michael Schroeder originally proposed truncating the superproject's longer hashes when fetching in submodules.

The discussion has evolved through several stages. Michael's v2 patch modified `builtin/submodule--helper.c` to use the submodule's hash algorithm when converting commit hashes during fetch operations, addressing Junio Hamano's feedback by using `hash_to_hex_algop()` instead of manual truncation. However, Brian M. Carlson raised fundamental concerns about whether mixed hash algorithms in submodules should be supported at all, citing potential data corruption risks and the impossibility of automatically converting tree objects between algorithms.

In the latest exchange, Michael pushes back against Brian's position, arguing that mixed-hash submodules already work in practice for non-shallow clones (with SHA-1 main repos truncating submodule hashes and SHA-256 main repos padding them with zeros). He maintains that the shallow clone case is the only real problem needing fixing and expresses skepticism about Brian's proposed compatObjectFormat solution.

The thread now presents a tension between pragmatic and architectural approaches: should Git fix the immediate shallow clone issue (Michael's position) or first resolve the broader questions about mixed-hash viability (Brian's position)? While the technical discussion continues, the patch series addressing the shallow clone case appears ready to proceed independently of these larger design questions. Key participants remain Michael Schroeder (author), Junio Hamano (implementation feedback), and Brian M. Carlson (architectural concerns).
