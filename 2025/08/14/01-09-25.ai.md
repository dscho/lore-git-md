This is a technical proposal about SHA-1/SHA-256 interoperability in Git, specifically focusing on improving the storage mechanism for hash mappings. The email comes from Brian Carlson, who has been leading the hash transition work.

The core issue is that the current flat-file approach (`loose-object-idx`) for storing SHA-1/SHA-256 mappings doesn't scale well for certain cases like shallow clones, partial clones, and submodules. The file isn't optimized for search and requires loading everything into memory, which becomes problematic as the number of mappings grows. The email outlines several key requirements for a new storage format, including bidirectional lookup efficiency, incremental updates, and support for multiple hash algorithms.

Several potential solutions are floated: extending pack index v3 format, using multi-pack indexes, or creating a reftable-like format. The proposal is still in the design phase, with Carlson seeking feedback from experts on Git's storage formats before implementing a solution. The email references ongoing work in Carlson's `sha256-interop` branch and mentions upcoming Git Merge talk about this effort.

Key technical details include the need to store object types with mappings (for GC purposes), the desire to avoid loading all mappings into memory, and the importance of supporting future hash algorithms beyond just SHA-1/SHA-256. The proposal builds on existing work documented in the hash transition document and pack index v3 format.
