This thread continues the long-running discussion about how to store bidirectional SHA-1/SHA-256 object ID mappings for Git's hash interoperability work. The core challenge is finding a storage format that supports efficient lookups in both directions while allowing incremental updates. Three main approaches have emerged: Junio Hamano's two-file separation, Derrick Stolee's reftable-inspired format, and Eric Wong's SQLite-based proposal.

brian m. carlson, who has been driving the interoperability effort, has now responded to the SQLite suggestion with strong objections. They point to SQLite's poor performance with Java implementations (which motivated the creation of reftable) and raise concerns about license stability, drawing parallels to Oracle's controversial changes to Berkeley DB's license. This effectively rules out SQLite as an option, narrowing the field to the remaining two proposals.

The discussion has expanded beyond pure technical considerations to include ecosystem-wide factors like cross-implementation compatibility and licensing risks. While the technical evaluation continues (with performance benchmarks and integration complexity still needing assessment), the SQLite option appears off the table. The thread now focuses on weighing Hamano's file separation approach against Stolee's reftable-like format, with workflow preferences and long-term maintainability becoming key decision factors.
