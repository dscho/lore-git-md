[Thread summary: SHA-1/SHA-256 interoperability storage format proposal]

Thread identity: Technical proposal from brian m. carlson about improving hash algorithm interoperability storage in Git, with Junio C Hamano now participating in the design discussion. Focus remains on limitations of current `loose-object-idx` and alternatives for efficient SHA-1/SHA-256 mapping storage, part of carlson's `sha256-interop` branch work.

Core problem: Current mapping storage scales poorly for shallow/partial clones and submodules due to inefficient search and memory usage. Need new format supporting bidirectional lookups, incremental updates, multiple algorithms while remaining memory-efficient. Junio adds specific concerns about maintaining mutable vs. immutable data separation.

Technical requirements: Must store object types (for GC), avoid full-memory loading, support future algorithms. Junio critiques proposed pack index v3 bit-reuse, suggesting proper format changes instead. New considerations: separating static mappings (potentially sorted) from dynamic metadata (shallow info), with different storage strategies for each.

Current status: Active design discussion phase. Junio's feedback introduces architectural considerations about layering static/dynamic data, questioning whether reftable-like complexity is needed for core mappings while acknowledging value for auxiliary data. Original proposal's tradeoffs under reevaluation.

Key technical details: Discussion now contrasts:
- Static mappings: Stable once computed, could use simple sorted format
- Dynamic metadata: Small subset needing flexible updates
Proposed using main mapping table order as index into auxiliary data. Parallels drawn to packed/loose refs model for balancing read/write needs.

Open questions refined: 
- How to cleanly separate static/dynamic data layers?
- Is pack index v3 extension still viable or need new format?
- What's the minimal viable format for core mappings vs. auxiliary data?
- How to handle the write-path for constantly added objects?

Participant positions:
- carlson: Original proposer considering multiple format options
- Hamano: Skeptical of bit-reuse in pack index, advocates proper format extension. Suggests simpler base format for static data with auxiliary layer.

Related work: Still connects to carlson's SHA-256 work and reftable, but discussion now more focused on architectural separation of concerns inspired by Git's ref storage model. Hash transition docs remain foundational reference.
