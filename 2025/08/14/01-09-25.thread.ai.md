[Thread summary: SHA-1/SHA-256 interoperability storage format proposal]

Thread identity: Technical proposal from brian m. carlson about improving hash algorithm interoperability storage in Git, specifically addressing limitations of the current `loose-object-idx` flat-file approach for SHA-1/SHA-256 mappings. This is part of ongoing work in carlson's `sha256-interop` branch and relates to Git's hash transition effort.

Core problem: Current mapping storage doesn't scale well for shallow clones, partial clones, and submodules due to inefficient search and memory usage when handling large numbers of SHA-1/SHA-256 object ID mappings. Need a new storage format that supports bidirectional lookups, incremental updates, and multiple hash algorithms while being memory-efficient.

Technical requirements: Must store object types (for GC), avoid loading all mappings into memory, support future hash algorithms beyond SHA-1/SHA-256. Current implementation uses `loose-object-idx` which lacks these properties.

Proposed solutions under consideration: Extending pack index v3 format, using multi-pack indexes, or creating a reftable-like format. Design still in early phase with no implementation yet. References existing hash transition documentation and pack index v3 format as foundations.

Current status: Proposal stage seeking feedback from storage format experts. Upcoming Git Merge talk will cover this effort. Builds on long-running hash transition work that carlson has led, including making Git internals hash-agnostic.

Open questions: Which storage approach best meets requirements? How to balance lookup performance with memory efficiency? What implications for existing features like shallow clones?

Related work: Connects to carlson's prior SHA-256 work, pack index v3 format, and reftable development. Mentioned as part of broader hash transition effort documented in project docs.
