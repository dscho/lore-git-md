[Thread summary: SHA-1/SHA-256 interoperability storage format proposal]

Thread identity: Technical discussion between brian m. carlson and Junio C Hamano about storage format for bidirectional SHA-1/SHA-256 object ID mappings, part of carlson's `sha256-interop` branch work. Thread has evolved from initial proposal to focused architectural discussion.

Core problem: Need efficient storage format supporting bidirectional lookups between hash algorithms that handles both static mappings (stable once computed) and dynamic metadata (shallow boundaries, incremental updates). Must avoid linear searches while maintaining memory efficiency and supporting future algorithms. Current status: Active design phase with convergence toward two-layer approach inspired by Git's packed/loose refs model. Discussion now focuses on concrete implementation tradeoffs between extending pack index v3 versus creating new format.

Key technical details:
- Prototype uses dual hashmaps (SHA-1<->SHA-256) but needs disk format
- Pack index v3 extension would reuse abbreviated names + mapping tables
- Dynamic data (shallow info) requires different storage strategy than static mappings
- `git gc` integration proposed for periodic repacking/compaction
- Fundamental challenge: sorting by one hash makes reverse lookups linear
- Junio's architectural input emphasizes separating static/dynamic data layers

Open questions:
- Final format choice: pack index v3 extension vs dedicated new format
- Exact division between static mapping table and dynamic metadata
- Write-path handling for constantly added objects
- Whether to adopt reftable-like complexity for auxiliary data
- Performance tradeoffs of various lookup strategies

Participant positions:
- carlson: Focused on practical implementation, explains why simple sorting fails for bidirectional lookups. Proposes gc integration and pack index v3 extension path.
- Hamano: Continues advocating architectural separation, skeptical of bit-reuse in pack index. Suggests simpler base format for static data with auxiliary layer.

Related work: Connects to carlson's SHA-256 interoperability work, reftable design, and Git's ref storage model. Hash transition docs remain key reference. Discussion shows technical progress while maintaining focus on core requirements.
