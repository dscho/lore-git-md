This is a technical discussion about the storage format for SHA-1/SHA-256 object ID mappings, continuing the thread started by brian m. carlson's proposal. Junio C Hamano weighs in with several design considerations and questions about the proposed approaches.

Hamano questions why the existing `loose-object-idx` isn't sorted, noting that maintaining a single sorted file would be impractical due to constant object additions. He critiques the idea of repurposing a bit in the pack index v3 format, suggesting that if more substantial changes are needed, the format should be properly extended rather than using bit-stealing tricks.

The email proposes separating concerns between static mapping data (which could use a consolidated sorted format) and dynamic metadata (like shallow clone information), suggesting these could live in different storage layers. Hamano notes that multi-level rollup formats like reftable might be overkill for the static mapping data, while dynamic attributes could benefit from a separate, more flexible storage mechanism.

Key technical points raised include: the stability of hash mappings once computed, the small proportion of objects needing dynamic metadata, and the potential for using the order in a main mapping table as an index into auxiliary data. The discussion continues to explore the balance between read-optimized base formats and write-friendly overlay mechanisms, drawing parallels to the packed/loose refs model.
