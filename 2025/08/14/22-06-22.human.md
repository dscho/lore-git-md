This is a technical discussion about SHA-1/SHA-256 interoperability storage formats, continuing the thread about efficient mapping between hash algorithms. Brian m. carlson responds to Junio Hamano's feedback on the design challenges.

The core issue remains how to store bidirectional object ID mappings efficiently, particularly addressing the limitations of the current `loose-object-idx` approach. Hamano had suggested separating static mapping data from dynamic metadata (like shallow clone info), similar to how Git handles packed vs loose refs. Carlson agrees this could work, noting they could use a base file plus incremental updates, with periodic compaction via `git gc`.

A key technical point clarified is why the current format isn't sorted - sorting by one hash algorithm would still require linear searches for the other. Carlson explains the pack index v3 approach uses abbreviated names with mappings to full IDs, which could inspire the new format. The discussion is now converging on having:
1. A main sorted mapping table (static data)
2. Auxiliary storage for dynamic metadata (like shallow info)
3. Periodic compaction of incrementals

The exchange shows progress toward a solution that balances lookup efficiency with write performance, though implementation details remain to be worked out. Carlson appears receptive to Hamano's architectural suggestions while bringing concrete technical insights from their work on the `sha256-interop` branch.
