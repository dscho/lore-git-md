Bugfix for submodule handling when different hash algorithms are used between superproject and submodule. This patch addresses an issue where shallow submodule clones fail when the submodule uses a different hash algorithm than the main repository.

The core problem occurs because Git pads submodule commit hashes with zeros when the submodule's hash algorithm differs from the superproject's. Normally this isn't an issue since submodules are cloned non-shallow by default, but with `--shallow-submodules` or `--depth` in submodule update, the zero-padded hash causes fetch failures as Git tries to interpret the full padded hash as a refname.

The fix modifies `builtin/submodule--helper.c` to properly truncate the commit hash to the submodule's hash algorithm length before fetching. Key changes include:
1. Extending `get_default_remote_submodule()` to optionally return the submodule's hash algorithm
2. Modifying `fetch_in_submodule()` to truncate the commit hash using the submodule's hash algorithm size
3. Updating callers to pass NULL for the hash algorithm parameter when they don't need it

The patch appears well-contained and focused, touching only the necessary parts of the submodule helper code. It includes a clear explanation of both the problem and solution in the commit message. This addresses a real edge case that could affect users mixing hash algorithms with shallow submodule clones.
