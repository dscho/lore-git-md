This is a follow-up discussion about the git-rebase documentation improvements, specifically on how to describe the rebase internals. The thread has already seen significant discussion about command usage and revision range behaviors, with consensus forming around maintaining `git checkout` in current docs while planning a systematic migration to `git switch`/`restore` for Git 3.0.

Junio C Hamano responds to Julia Evans' suggestion about keeping the `git log` description to help users understand rebase performance characteristics. He points out that the current description inaccurately portrays rebase as having two separate steps (a fast enumeration step and slow filtering step), when in reality the enumeration and filtering happen together in a single operation through either the `format-patch | am` or `rev-list | cherry-pick` pipelines.

Junio suggests either:
1. Combining the first two steps into one simplified description that focuses on the conceptual outcome ("list of commits to replay"), or
2. If keeping them separate, clearly marking it as a conceptual white lie for educational purposes

This continues the thread's theme of balancing technical accuracy with approachability in documentation.
