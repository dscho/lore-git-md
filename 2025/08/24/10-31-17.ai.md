Performance optimization discussion for `git describe`'s depth computation, proposing an alternative implementation using commit-slabs instead of khash.

Jeff King responds to René Scharfe's khash-based optimization with an alternative approach using commit-slabs, which were originally designed for this type of zero-cost lookup scenario. The key technical points include:

1. The commit-slab approach uses array indexing via commit->index rather than hashing, trading some memory overhead (allocating space for all commits) for potentially better cache performance in dense cases.

2. Benchmark results show the khash version is slightly faster (1.03x) than the commit-slab version, though both significantly outperform the original implementation (1.31x and 1.28x faster respectively).

3. The email raises several important questions about the tradeoffs between these approaches:
   - Performance characteristics for different commit density patterns
   - Flexibility in value size handling
   - Potential to eliminate the commit->index field entirely by using pointer hashing
   - Possibility of extending the technique to non-commit objects

The discussion suggests broader implications for Git's data structures, particularly around how object metadata is managed across different subsystems. The performance difference between approaches appears small enough that other factors (memory usage, code complexity, future flexibility) may become deciding factors in choosing an implementation.
