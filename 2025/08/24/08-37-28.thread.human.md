This thread explores performance optimizations for Git's commit metadata management, comparing two competing approaches: khash-based sets and commit-slabs. The original discussion focused on `git describe`'s depth computation, where René Scharfe's khash implementation showed a consistent 3% speed advantage over Jeff King's commit-slab alternative, though both significantly improved upon the original quadratic implementation. The tradeoffs were well understood - khash offered slightly better performance for sparse commit access while commit-slabs provided simpler maintenance for dense commit sets.

Jeff King has now shared experimental results from applying both approaches to author-date storage in topological sorting. Testing `git rev-list --author-date-order` on the Linux kernel (a dense commit scenario), the commit-slab version proved dramatically faster - 7x better than the khash alternative. This validates Jeff's earlier position about commit-slabs excelling in dense access patterns, though he acknowledges their macro-heavy interface remains cumbersome. While these results don't change the `git describe` optimization (where khash still shows an edge), they demonstrate that neither data structure is universally superior - the optimal choice depends on specific access patterns. The discussion has evolved from raw performance comparisons to a more nuanced understanding of when each approach shines, with implications for future metadata management decisions across Git's codebase.
