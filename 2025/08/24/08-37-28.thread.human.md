This thread has been exploring the performance tradeoffs between two data structure approaches in Git's core: khash-based storage versus commit-slabs. The discussion began by comparing these methods for specific use cases in `git describe` and topological sorting, where each showed advantages in different scenarios (khash for sparse access, slabs for dense traversals).

Jeff King has now conducted a more radical experiment, moving all object flag storage from direct struct access to khash lookups. Using Coccinelle to automate much of the conversion, he found significant performance penalties - operations like `merge-base` slowed by 25% and `rev-list --objects --all` nearly doubled in runtime. These results quantify the cost of hash lookups versus direct flag access, supporting the emerging consensus that direct struct access remains optimal for performance-critical paths.

The experiment revealed edge cases needing manual handling, such as `describe.c`'s direct flag assignments, while demonstrating the feasibility (with caveats) of more flexible storage approaches. This builds on earlier findings where khash showed a 3% advantage for sparse commit scenarios in `git describe`, while commit-slabs maintained a 2-6% edge in dense topological sorts after benchmark corrections.

Key participants including René Scharfe, Jeff King, and Junio Hamano have contributed to a nuanced understanding that neither approach universally dominates. The discussion now has concrete data to inform future decisions about when to prefer direct access versus more abstracted storage, with maintenance complexity and access patterns being key factors. Open questions remain about khash's underperformance and whether hybrid approaches might emerge, but the thread has significantly advanced the project's understanding of these core data structure choices.
