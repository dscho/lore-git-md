Feature implementation for the `git-history` command's `reword` subcommand, building on the RFC v3 infrastructure. This patch adds the ability to rewrite commit messages while preserving all other commit metadata, similar to `git rebase -i`'s "reword" action but as a standalone operation.

The implementation handles the full workflow: validating the target commit isn't a merge, checking for clean working state, collecting the commit chain that needs rewriting, preserving original authorship, and applying the changes. It supports both direct message specification via `-m` and interactive editing. The command maintains HEAD position and includes comprehensive tests covering edge cases like empty messages, root commits, and merge commit rejection.

Key technical details:
- New `cmd_history_reword()` function implementing the core logic
- Uses existing `collect_commits()` and `apply_commits()` infrastructure from earlier patches
- Preserves original author and tree while allowing message changes
- Validates against empty commit messages
- New test file `t/t3454-history-reword.sh` with 6 test cases
- Documentation updates in `git-history.adoc`

The implementation follows the series' pattern of building on prepared infrastructure while adding focused new functionality. It demonstrates careful attention to edge cases and user experience, maintaining the quality seen in previous subcommand implementations like `split` and `drop`. The tests provide good coverage of both happy paths and error conditions.

This completes the set of history-editing subcommands proposed in the RFC, with `reword` joining `drop`, `reorder`, and `split`. The implementation appears ready for review, though design questions remain about how these subcommands will interact in more complex editing scenarios.
