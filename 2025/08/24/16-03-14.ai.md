This is the final patch in Patrick Steinhardt's RFC series introducing the new `git-history` command, implementing the "split" subcommand. The discussion has shifted to UX details around commit message handling during splits, with Junio C Hamano advocating for showing the original message in both resulting commits to preserve context. Patrick acknowledges this feedback and plans to modify the implementation to at least show the split-out changes in the editor (similar to `git commit`), while continuing to consider the message template approach.

Key technical details from this exchange:
- The split operation currently creates a commit from selected hunks as parent of the original
- Maintains original authorship but forbids empty commits
- Current message handling shows original message only in one commit
- Junio argues for showing original message in both commits to avoid information loss
- Patrick will modify to show changes in editor (like `git commit`) while still considering message template approach

This continues the thread's pattern of refining UX details while maintaining the conservative implementation strategy approved by Junio. The discussion remains focused on practical workflow considerations rather than fundamental design questions, suggesting the core approach is stabilizing. Patrick's responsiveness to feedback indicates the RFC process is working as intended to shape the feature before finalization.
