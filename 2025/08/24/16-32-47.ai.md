Performance optimization discussion for `git describe`'s depth computation, comparing khash and commit-slab implementations.

René Scharfe responds to Jeff King's commit-slab alternative proposal with additional benchmarking data and technical analysis. The key points:

1. Performance comparison shows khash maintains a small but consistent 3% speed advantage over commit-slabs in both test runs (1.03x faster), while both significantly outperform the original linear scan (1.31-1.4x faster).

2. Technical tradeoffs:
   - Khash uses less memory for sparse commit sets but requires key storage
   - Commit-slabs have zero-cost lookup but allocate for all commits
   - Khash supports removal operations while commit-slabs don't
   - Commit-slabs may perform better for dense commit sets with long-lived data

3. Exploration of potential enhancements:
   - Pointer-based hashing could eliminate commit->index field
   - Discussion of portable hashing strategies for non-aligned pointers
   - Consideration of dynamic value sizes in hash implementations

4. Maintenance considerations:
   - Commit-slabs require no rehashing or key management
   - Potential to replace object flags for non-commit objects
   - Error-proneness of shared flag space in current implementations

The exchange highlights that while both approaches solve the quadratic complexity problem effectively, the choice may depend on specific use cases and broader architectural considerations beyond just this optimization. The small performance difference suggests other factors like memory usage patterns and future maintainability may be deciding factors.
