Performance optimization and refactoring series for Git's line-log functionality (git log -L), focusing on merge commit processing. Series consists of 4 patches: 1 performance optimization followed by 3 subjective cleanups.

Core change in patch 1 optimizes merge commit handling in line-log.c by restructuring `process_ranges_merge_commit()` to combine two separate passes (diff computation and processing) into one. This avoids computing tree diffs against secondary parents when the first parent shows no changes to tracked paths, yielding significant speedups: 2.25x in git.git (25.8% merges) and 1.32x in linux.git (7.5% merges). The change removes the need for storing diff queues per parent, eliminating the `free_diffqueues()` helper (-15 lines net).

Patch 2 refactors the same function to eliminate a dynamically allocated parents array, instead iterating directly through the commit's parent list. While the runtime impact is "unmeasurable", this simplifies memory management by removing the `parents` array and its allocation/free operations, converting array-indexed access to direct linked-list traversal, and maintaining identical blame assignment while reducing code complexity (net reduction of 12 lines).

Patch 3 addresses a code quality issue in `process_ranges_ordinary_commit()` by initializing a local `diff_queue_struct` with `DIFF_QUEUE_INIT` before use. While functionally harmless (the uninitialized data was overwritten without being read), this change makes the code more obviously correct to human readers (1 line modified).

Patch 4 (final) simplifies the series by flipping the merge commit condition check in `process_ranges_arbitrary_commit()` from checking "if not a merge" to directly checking "if is a merge". This 3-line change makes the logic more straightforward by putting the merge case first, completing the series' cleanup of merge commit processing.

All changes are internal to line-log.c with cumulative -43 LOC across 63 modified lines. No user-facing behavior changes or test/documentation updates - purely implementation improvements combining measurable performance gains (patch 1) with code quality refinements (patches 2-4). The series maintains clear separation between optimization and maintainability enhancements, with patch 1's performance measurements establishing the baseline impact in merge-heavy histories. The cumulative effect is a more maintainable implementation that's also significantly more efficient for merge-heavy histories.
