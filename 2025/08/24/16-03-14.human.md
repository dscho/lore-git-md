Feature implementation in the `git-history` RFC series, focusing on the "split" subcommand.

This email continues the discussion around the `git-history split` implementation, specifically addressing how commit messages should be handled when splitting a commit. Junio C Hamano had suggested showing the original message for both resulting commits after a split operation, arguing this preserves more context for the user. Patrick Steinhardt acknowledges this feedback and plans to modify the implementation to at least show all changes being split out in the editor (similar to `git commit`'s behavior), while still considering the broader message handling approach.

The exchange highlights one of the UX design challenges in this new command - balancing Git's traditional workflows with inspiration from tools like Jujutsu (jj). This is part of patch 11/11 in the RFC series, which implements the core split functionality allowing interactive division of commits similar to `add -p`. The thread shows active collaboration between the author and maintainers to refine the design before finalizing the implementation.
