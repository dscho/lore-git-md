This is a feature proposal discussion for the new `git-history` command, specifically addressing hook integration. Kristoffer Haugsbakk suggests that the command should trigger the `post-rewrite` hook, particularly for the `split` subcommand, to maintain consistency with Git's existing rewrite operations. This would cover all rewrite patterns: one-to-one (like rebase), many-to-one (squash), and one-to-many (split).

The suggestion comes in the context of Patrick Steinhardt's RFC series introducing Jujutsu-inspired history editing commands (`drop`, `reorder`, `split`). While previous discussion focused on implementation details and UX comparisons with Jujutsu, this email raises a new architectural consideration about hook integration that wasn't previously addressed in the thread.

The proposal would require modifying the command's behavior to:
1. Consistently fire `post-rewrite` for all operations
2. Handle the split case specially as a one-to-many rewrite
3. Document this behavior alongside other rewrite-hook-triggering commands

This suggestion touches on Git's hook system consistency and could influence how the command integrates with existing Git workflows. It doesn't appear to conflict with any of the previously discussed design decisions, but would require additional implementation work to track and report the rewrite mappings appropriately.
