Thread identity: Performance optimization discussions comparing khash-based and commit-slab approaches across multiple Git subsystems, now expanding to examine object flag storage strategies.

Core problem: Evaluating competing data structures (khash vs commit-slabs vs direct access) for performance-critical metadata storage in Git, with distinct patterns emerging across different usage scenarios. The investigation has progressed from `git describe` depth computation and topological sorting to a radical experiment in object flag storage, revealing fundamental tradeoffs between flexibility and performance.

Key technical details:
- `git describe` optimization (sparse access):
  - Khash (René Scharfe): 3% faster (1.31-1.4x vs original)
  - Commit-slab (Jeff King): simpler, better for dense commits
  - Both preserve object flag space for candidate tags
- Topological sorting experiment (dense access):
  - New `obj_timestamp` khash type with OID-based hashing
  - Corrected benchmarks show:
    - git.git: 2% slower with khash (547ms slab vs 559ms hash)
    - linux.git: 6% slower with khash (11.02s slab vs 11.68s hash)
  - Profiling shows khash operations account for minimal runtime
- Object flag storage experiment:
  - Jeff King's radical conversion of all flag storage to khash
  - Introduces `objflags` khash table with helper functions
  - Benchmarks show severe penalties:
    - 25% slowdown for `merge-base`
    - 93% slowdown for `rev-list --objects --all`
  - Reveals special cases needing manual handling (e.g. `describe.c`)
- Structural considerations:
  - Khash better for sparse data, supports removals
  - Commit-slabs excel in dense scenarios, no rehashing
  - Direct access remains fastest for high-frequency operations
  - Khash interface more flexible but with significant overhead
  - Coccinelle proves useful for large-scale code transformations
