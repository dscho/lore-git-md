This is a review comment on the `git history reorder` subcommand implementation in Patrick Steinhardt's RFC series. Kristoffer Haugsbakk questions the use-case for an imperative reorder command compared to interactive rebase, noting that while the drop subcommand has clear semi-interactive use cases, reordering seems better suited to rebase's interactive interface. They suggest the example doesn't clearly demonstrate when this would be preferable to rebase.

Kristoffer also points out two typos in the commit message and questions whether the documentation should refer to "current `HEAD` commit" or just "current commit". The technical implementation itself isn't challenged - the focus is on UX design and documentation clarity. This continues the thread's pattern of scrutinizing user-facing aspects of the new command, though from a different angle than previous discussions about message handling and Jujutsu comparisons.
