This is a discussion about the `reorder` subcommand in Patrick Steinhardt's proposed `git-history` feature, specifically addressing Kristoffer Haugsbakk's questions about its use cases and documentation.

Patrick explains that the `reorder` subcommand provides a lightweight alternative to interactive rebase for moving commits, particularly useful when quickly rearranging recently created commits. He shares that this pattern proved valuable in Jujutsu (jj), where direct imperative commands often feel more natural than editor-based rebase instructions. The example shows moving commit `:/fourth` before `:/second` using revision syntax, with Patrick noting that simple cases can also use `HEAD` for the current commit.

Kristoffer had questioned when this would be preferable to interactive rebase, comparing it to using Vim's Ex mode - technically possible but not clearly advantageous. Patrick's response emphasizes the ergonomic benefits for small, focused history edits. The exchange also includes minor documentation tweaks, with Patrick agreeing to clarify "currently checked-out commit" instead of "current `HEAD` commit".

This continues the thread's theme of examining each subcommand's boundaries with existing Git functionality, with `reorder` facing particular scrutiny about its differentiation from interactive rebase.
