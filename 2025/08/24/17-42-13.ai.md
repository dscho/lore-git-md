This is a feature proposal introducing a new `git-history` command for history editing operations, inspired by Jujutsu (jj) functionality. The RFC v2 from Patrick Steinhardt expands the initial proposal with a new "reword" subcommand and various improvements.

The series now includes 16 patches that:
1. Add sequencer infrastructure changes to support history editing
2. Introduce the `git-history` command with subcommands:
   - `drop`: Remove a commit and rebase its children
   - `reorder`: Move a commit before/after another commit
   - `split`: Interactively split a commit into two
   - `reword`: Change a commit's message (new in v2)
3. Add management commands for interrupted operations (`abort`, `continue`, `quit`)
4. Include extensive test coverage for all subcommands

Key technical aspects:
- Built on Git's sequencer infrastructure with a new `REPLAY_HISTORY_EDIT` mode
- Uses cherry-pick mechanics initially (with plans to improve)
- Handles in-memory index operations for interactive splitting
- Preserves authorship and timestamps where appropriate
- Includes safety checks for working tree/index state
- Documents all subcommands with examples

The implementation currently has some intentional limitations:
- No merge commit support (will be lifted later)
- Uses cherry-pick continue mechanism (to be improved)
- Marked as experimental in documentation

The thread context indicates active discussion about:
- Hook integration (post-rewrite confirmed for v3)
- Comparison with Jujutsu's approach
- Documentation refinements
- Value proposition of `reorder` vs interactive rebase

This represents a significant new capability for Git, providing imperative-style editing commands that complement the existing interactive rebase workflow. The implementation appears thorough, with careful attention to safety and edge cases. The maintainer has approved the conservative implementation strategy, suggesting this has a good chance of progressing once remaining design questions are resolved.
