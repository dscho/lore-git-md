This is a follow-up in the thread about `git status` timing sensitivity, providing additional context about the underlying "racy git" problem. Damien Cassou shares a collection of resources explaining the long-standing issue where rapid file modifications can cause Git to miss changes due to timestamp resolution limitations in filesystems.

The links include Git documentation, technical blog posts, and historical discussions that trace this behavior back to Git's early design decisions around stat-based change detection. Several of the resources specifically discuss how this affects tools like Git LFS and JGit, showing the problem's broader impact beyond core Git.

This email doesn't propose a solution but rather enriches the technical background for the ongoing discussion. The references suggest this is a fundamental limitation of stat-based approaches rather than an implementation bug, which may influence how (or whether) the Git community chooses to address the originally reported `git status` behavior. The well-curated resource list indicates serious engagement with the problem's historical and technical dimensions.
