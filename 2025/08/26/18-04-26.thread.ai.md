New thread: Rust compatibility proposal from Randall Becker, discussing making Rust an optional dependency for specific commands while maintaining C-only builds on platforms without Rust support (particularly NonStop). Core problem: balancing Rust adoption with platform compatibility. Randall's initial position advocates following Git's historical pattern with optional dependencies, keeping core functionality in C while allowing Rust for specific commands.

Brian Carlson strongly opposes optional Rust, arguing it would complicate core functionality (diff/log/show/index-pack/fetch-pack) and undermine security benefits. Technical objections: Rust integration touches fundamental operations (SHA-1/SHA-256 mapping), conditional compilation creates untestable paths, and project policy rejects C-only fallbacks. Carlson frames this as project-direction issue, citing security trends favoring mandatory memory-safe languages. No solutions offered for platform concerns - positioned as all-or-nothing.

Key open questions: how this impacts existing Rustification work (Ezekiel Newren's efforts), whether core maintainers (Junio, PLC) will accept split dependency model, and what commands could realistically remain C-only if Rust becomes required for core operations. Fundamental disagreement emerging between platform compatibility (Becker) and security/modernization (Carlson) perspectives. Related work: SHA-256 interoperability (Carlson's long-running branch) and Rustification effort.
