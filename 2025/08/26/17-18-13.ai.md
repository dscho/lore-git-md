This is a performance and safety patch for `git range-diff` that addresses memory exhaustion issues when comparing very large commit ranges. The patch adds a configurable memory limit for the cost matrix calculation, preventing both integer overflow and excessive memory allocation.

The core issue occurs when `range-diff` processes extremely large commit ranges (250,000+ commits), where the n×n cost matrix allocation can attempt to use hundreds of GB of memory. The patch introduces a new `--max-memory` option that accepts human-readable sizes (defaulting to 4GB on 64-bit systems) and fails gracefully with a clear error message when the limit would be exceeded. The implementation checks the required matrix size (n² × sizeof(int)) before allocation and compares it against the configured maximum.

Key technical details:
- New `max_memory` field in `struct range_diff_options`
- Default values of 4GB (64-bit) and 2GB (32-bit) via `RANGE_DIFF_MAX_MEMORY_DEFAULT`
- Memory size parsing via new `parse_max_memory()` callback
- Human-readable error messages using `strbuf_humanise_bytes()`
- The check occurs in `get_correspondences()` before matrix allocation
- Affects three call sites: builtin/log.c, builtin/range-diff.c, and log-tree.c

The patch includes thorough analysis of the problem (including stack traces and reproduction details from Shopify's monorepo) and considers alternative approaches (commit counting, streaming) before settling on the memory limit solution. It references prior discussion on the mailing list and carries an Acked-by from Johannes Schindelin. The implementation appears well-tested and carefully considered, with clear error messages and reasonable defaults.
