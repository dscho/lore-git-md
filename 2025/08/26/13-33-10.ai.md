This is a post-merge discussion about the warning system design in the recently completed `core.commentChar=auto` deprecation series. Phillip Wood defends his implementation's user-friendly approach against Oswald Buddenhagen's critique that it is over-engineered.

The debate centers on whether Git should provide detailed migration advice (Wood's position) or simply direct users to existing tools like `git config --show-origin` (Buddenhagen's preference). Wood argues that since this is a forced config update, Git should minimize user friction by offering concrete suggestions for both using the default comment character and setting a fixed one. He acknowledges the complexity cost but considers it justified for better user experience.

Buddenhagen's objections focus on three points: the change affects few users, the advice could be seen as condescending, and the guidance may be incomplete for read-only config edge cases. Wood counters that Git's reputation for difficulty warrants proactive assistance, the advice isn't lecturing but helpful, and while the solution for read-only files isn't exhaustive, it provides a workable path forward.

This exchange highlights the ongoing tension in Git's design philosophy between user convenience and implementation simplicity, particularly for configuration migrations. The discussion remains civil but shows no immediate resolution, with both sides maintaining their positions on the appropriate level of guidance for breaking changes.
