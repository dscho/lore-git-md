This is a follow-up in the thread about `git status` timing sensitivity, providing additional technical context about the underlying race condition phenomenon. Damien Cassou shares a collection of resources explaining the "racy git" problem, where rapid file modifications can cause Git to miss changes due to timestamp resolution limitations in filesystems. The links cover documentation (Git's racy-git technical note), historical context (Ben Lynn's git-from-the-bottom-up), practical examples (Tyler Cipriani's blog), related issues in Git LFS, Stack Overflow explanations, and a JGit-focused presentation by Matthias Sohn. These resources collectively suggest this is a known limitation of stat-based change detection rather than a new bug, though the current thread explores whether Git's implementation could handle it better. The email doesn't propose a solution but provides valuable background for the ongoing discussion.
