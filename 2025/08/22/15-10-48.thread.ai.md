[git status] Timing sensitivity in file change detection reported by Damien Cassou. Core issue: when a file is modified twice in rapid succession (sub-second interval), `git status` fails to detect the second change unless file size or timestamp changes. Reproducible across platforms (macOS/Linux) in Git 2.50.1. Underlying cause appears related to stat-based change detection where rapid modifications don't trigger expected metadata updates. Well-documented reproduction case provided via shell script that toggles between working/broken states by inserting sleep between modifications. Technical focus: investigating the stat cache implementation in `wt-status.c` and related filesystem monitoring code. Open question: whether this is a fundamental limitation of stat-based approaches or an implementation detail that could be improved. Practical impact likely limited to edge cases since most real-world edits naturally change size or have observable delays.
