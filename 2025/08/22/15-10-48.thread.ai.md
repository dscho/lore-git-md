[git status] Timing sensitivity in file change detection reported by Damien Cassou. Core issue: when a file is modified twice in rapid succession (sub-second interval), `git status` fails to detect the second change unless file size or timestamp changes. Reproducible across platforms (macOS/Linux) in Git 2.50.1. Underlying cause appears related to stat-based change detection where rapid modifications don't trigger expected metadata updates. Well-documented reproduction case provided via shell script that toggles between working/broken states by inserting sleep between modifications. Damien Cassou has now provided additional technical context linking this to the known "racy git" problem, with references to Git's technical note, historical explanations (Ben Lynn), practical examples (Tyler Cipriani), Git LFS issues, Stack Overflow discussions, and JGit analysis (Matthias Sohn). These resources confirm this is a fundamental limitation of stat-based approaches in filesystems with timestamp resolution constraints, though the thread continues to explore whether Git's implementation in `wt-status.c` could mitigate the issue. Open question remains whether this warrants implementation changes given the edge-case nature of the scenario (most real-world edits naturally change size or have observable delays between modifications). Technical focus remains on stat cache behavior and filesystem monitoring implementation details.
