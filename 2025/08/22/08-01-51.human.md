This is a proposed bugfix for the case-insensitive filesystem ref collision issue, following up on the ongoing discussion about reftable adoption. Karthik Nayak suggests a small code change to the files backend that would allow fetches to partially succeed when encountering case-colliding refs, rather than failing completely. The patch modifies `files-backend.c` to mark transactions with name conflicts as allowed-to-fail, which would let Git store the first conflicting ref it encounters while still warning about the collision. This differs from the pre-2.51 behavior where the last ref would win silently, but maintains some functionality rather than blocking the entire fetch operation.

The example output shows the command succeeding for some refs while reporting errors on others, with the first case variant (`SampLe`) being stored rather than the last. While this doesn't solve the underlying filesystem limitation, it provides a smoother degradation path than the current hard failure. The patch appears clean and focused, though it's worth noting the maintainer has previously expressed strong preference for reftable adoption over files backend workarounds. This seems to be offered as an interim solution while the ecosystem moves toward reftable.
