This thread explores a subtle timing issue in `git status` where rapid file modifications (sub-second intervals) can be missed unless the file size or timestamp changes. Damien Cassou initially reported the problem with a clear reproduction case across platforms in Git 2.50.1, pointing to potential issues in `wt-status.c`'s stat cache implementation.

Damien has now provided additional context by sharing resources about the "racy git" problem - a known limitation where filesystem timestamp resolution can cause Git to miss rapid changes. The collection includes technical documentation, historical explanations, and real-world examples from Git LFS and JGit, suggesting this is a fundamental challenge with stat-based detection rather than a new bug. While the resources don't propose a solution, they help frame the discussion around whether Git's current implementation could be improved or if this represents an inherent constraint of the approach. The practical impact appears limited to edge cases, as most real-world edits naturally change file size or have observable delays between modifications. The thread remains open for further technical discussion about potential improvements to Git's change detection.
