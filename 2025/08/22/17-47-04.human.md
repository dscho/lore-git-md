Maintainer response in ongoing filesystem case-sensitivity discussion. Junio Hamano questions Karthik Nayak's proposed fix for "lock file exists" errors in bare repository fetches, probing technical details and suggesting alternative approaches.

Hamano raises several concerns about the patch that modifies error handling in the files backend. He questions whether the change properly distinguishes between genuine name conflicts and other lock file scenarios, and whether the new error code (REF_TRANSACTION_ERROR_NAME_CONFLICT) actually enable progress where the transaction previously failed. The response suggests the fix might only improve error messaging without solving the underlying transactional blocking issue.

The email also proposes a more fundamental solution: modifying refs_verify_refnames_available() to account for case-insensitive filesystem behavior when using the files backend. This would require new backend-specific functionality to properly detect case collision issues at the filesystem level. Hamano notes the current implementation misses certain directory/file (D/F) conflicts on case-challenged systems.

This maintains the thread's technical depth while reinforcing the maintainer's position that files backend modifications should address root causes rather than symptoms. The response keeps focus on proper transactional semantics and backend architecture rather than accepting workarounds, consistent with Hamano's earlier preference for reftable adoption.
