Bugfix report regarding `git status` file change detection timing sensitivity.

Damien Cassou reports an odd timing-dependent behavior in `git status` where rapid file modifications may not be detected. The issue manifests when a file is modified twice in quick succession - if the modifications happen fast enough (without a 1-second delay between them), `git status` fails to report the second change. The behavior is reproducible across platforms (macOS and GNU/Linux) with Git 2.50.1.

Key observations from the report:
- The issue only occurs when file modifications happen rapidly (sub-second)
- Changing the file's timestamp or size forces detection to work
- The test case uses a simple shell script that modifies a file twice, with an optional sleep between modifications

This appears to be related to Git's stat-based file change detection mechanism, where rapid modifications may not trigger the expected filesystem metadata changes that Git uses to detect modifications. The reporter is specifically interested in understanding the underlying C code implementation that causes this behavior.

The report is well-documented with a clear reproduction case (attached script) and identifies specific conditions where the behavior changes. This looks like a legitimate edge case in Git's change detection that could affect users performing rapid file operations, though the practical impact may be limited since most real-world edits would either change file size or have natural delays between modifications.
