This is a feature patch implementing the "split" subcommand for the proposed `git-history` command, part of Patrick Steinhardt's RFC series. The discussion focuses on the user experience of splitting commits, specifically how to handle commit message templates during the operation.

Junio C Hamano weighs in on the UX design, advocating for showing the original commit message as the template for both new commits created by the split operation. His rationale is practical - when users realize they've combined too many changes into one commit (often while writing the message), having the original message available in both splits makes it easier to properly divide the changes without losing context. This contrasts with some alternative approaches like only showing the message for the first split commit or using different templates.

The exchange highlights the tension between Git's traditional approaches and inspiration from tools like Jujutsu (jj), with Junio favoring a solution that minimizes information loss during the split. This feedback will likely influence the v2 implementation of the split subcommand, though the thread shows there may be multiple valid approaches to this particular UX detail. The discussion remains productive, with other parts of the series, as the maintainer provides concrete design input while allowing room for future refinement.
