Bug report follow-up with bisect results confirming the root cause of "lock file exists" errors during fetch operations in bare repositories. Joe Drew reports that bisecting between Git 2.39.5 and 2.51.0 identifies Karthik Nayak's commit 0e358de64a ("fetch: use batched reference updates") as introducing the behavior change. The issue occurs specifically when fetching repositories containing refs with case collisions (ptv-2164 vs PTV-2164 in this case) on macOS's case-insensitive filesystem.

The email confirms that using the reftable backend (with `--ref-format=reftable`) resolves the issue, as reftable avoids filesystem-level locking entirely. This aligns with the thread's emerging consensus that the batched ref transaction behavior is working as intended by properly detecting case collisions that previously went unnoticed in the one-by-one update approach.

The bisect results provide concrete evidence that the behavior change was introduced intentionally as part of improving reference update correctness, rather than being a regression. This strengthens the maintainer's position that the solution lies in adopting reftable rather than modifying the files backend behavior. The email doesn't propose any new solutions but provides valuable confirmation of the technical analysis from earlier in the thread.
