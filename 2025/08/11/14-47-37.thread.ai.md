Thread identity: Bug report and discussion about `git clone -c key=value --recurse-submodules` behavior regarding configuration propagation to submodules.

Core problem: Discrepancy in how `-c` configurations are handled when placed before vs after `clone` command, particularly affecting submodule initialization. When `-c` precedes `clone`, configurations propagate to submodules; when after, they only affect the superproject. This impacts authentication-related configurations like `url.new.insteadOf`.

Current status: Initial bug report identified the behavior and workaround. D. Ben Knoble now argues this is not a bug but expected behavior per documentation, shifting discussion to documentation clarity vs behavior change.

Key technical details:
- `git -c key=value clone` (pre-command `-c`) passes config to command process
- `git clone -c key=value` (post-command `-c`) sets config in new repository only
- Submodule initialization only receives pre-command configurations
- `url.<name>.insteadOf` particularly affected due to authentication needs

Open questions:
- Should documentation be updated to clarify this distinction?
- Should behavior be modified to propagate post-command `-c` to submodules?
- Should `url.<name>.insteadOf` be called out specifically in clone caveats?
