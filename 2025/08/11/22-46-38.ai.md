This is a discussion about the strvec API conversion in the editor-related patch series, specifically addressing patch 4/4. Eric Sunshine raises two key points about the proposed change to make the editor API accept a strvec for environment variables rather than a const char* array.

First, he notes the commit message lacks clear motivation for why this change is beneficial, despite showing the API's historical evolution. The patch demonstrates technical feasibility (only one non-NULL env caller exists, which already has a strvec) but doesn't articulate the improvement's value.

Second, he questions the API design choice itself, suggesting the change violates the principle of accepting the narrowest possible type. By requiring callers to provide a strvec rather than a simpler const char* array, the API becomes less flexible for potential future callers that might not naturally have a strvec available. This could unnecessarily constrain the interface's generality.

The discussion occurs in the context of an otherwise technically complete v3 series that has Johannes Schindelin's sign-off on this strvec conversion. While the implementation appears sound, Eric's feedback highlights missing documentation of the rationale and potential design tradeoffs in the API change. The thread shows no fundamental objections to the patch's approach, but these specific points about motivation and interface design remain open for the author to address.
