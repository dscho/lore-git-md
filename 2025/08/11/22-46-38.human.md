This is a follow-up discussion in the ongoing series modernizing editor-related test infrastructure and API, specifically addressing the strvec API conversion in editor.c/h. Eric Sunshine raises questions about the motivation and design choice in patch 4/4 of the series.

Eric expresses confusion about why the change from a const array of strings to a strvec is beneficial, noting the commit message doesn't explain the motivation. He points out that the current API accepts the more general const char* const* parameter, while the proposed change would require callers to have a strvec available, which he views as unnecessarily restrictive.

The discussion highlights an important design consideration about API contracts - whether to accept the most general type possible versus adopting project-specific types. This patch had previously received sign-off from Johannes Schindelin, but Eric's questions suggest the rationale may need to be more clearly articulated before final acceptance.

This exchange represents the final piece of feedback needed before the series can be considered ready for integration, following earlier rounds of review that addressed test modernization, security improvements, and environment handling patterns. The author will likely need to clarify the benefits of using strvec in this context to satisfy Eric's concerns.
