Bugfix discussion regarding ambiguous object ID handling in corrupted repositories.

Patrick Steinhardt responds to Jon Forrest's report about `git cat-file` showing duplicate abbreviated hashes when encountering ambiguous object IDs in a corrupted repository. The key technical points are:

1. The issue occurs when manually copying a blob object to create two entries with different hashes but identical content, which Patrick notes is an intentional repository corruption case.

2. The root cause is that `show_ambiguous_object()` gets confused because while there appear to be two objects (due to the manual copying), they actually hash to the same content. The `repo_find_unique_abbrev()` function then generates identical shortened hashes for what appears to be the same object.

3. Patrick questions whether this needs fixing since:
   - It requires manual repository corruption
   - `git-fsck` would detect this corruption
   - There's no indication this occurs in real-world usage

4. He asks for clarification on:
   - Whether this happens without intentional corruption
   - If the behavior has changed in recent Git versions (since Jon specified testing with Git 2.50)

This moves the discussion from bug reporting to analysis, focusing on whether the edge case warrants a fix given it requires repository corruption. The technical details about the interaction between `show_ambiguous_object()` and `repo_find_unique_abbrev()` would be important context for any future discussion about potential fixes.
