This is a discussion about the behavior of `git clone -c` with submodules, continuing a bug report about configuration propagation. D. Ben Knoble argues that the current behavior may not actually be a bug, based on documentation analysis.

The key observation is that `git -c key=value clone` (with `-c` before the command) and `git clone -c key=value` (with `-c` after) are technically different operations with different semantics. The first applies the configuration to the entire git process, while the second only applies it to the newly created repository after initialization.

The email suggests that while the behavior might be surprising (especially for URL rewrites needed for authentication), it appears to be working as documented. However, the author notes that `url.<name>.insteadOf` configurations might deserve an explicit mention in the caveats section of `git-clone(1)` since they share similar timing issues with other special configurations like `remote.<name>.mirror`.

This isn't proposing a fix, but rather analyzing whether the reported behavior is actually incorrect. The discussion highlights an important distinction in git's command-line parsing that affects configuration handling during complex operations like recursive submodule cloning.
