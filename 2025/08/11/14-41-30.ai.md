This is a discussion thread about the `git repo info` command implementation, specifically focusing on the lexicographical sorting behavior of output keys. Phillip Wood raises a concern about the design decision to sort output keys lexicographically rather than preserving input order.

The thread context shows this is part of a v9 patch series that's already approved for merging, implementing a new `git repo info` command to migrate repository metadata queries from `git rev-parse`. The current implementation in patch 2/8 adds the `references.format` field and enforces lexicographical sorting of output keys regardless of input order.

Phillip argues this sorting makes script parsing harder since scripts can't rely on output order matching their input order, forcing them to parse each key-value pair rather than using positional expectations. He notes that while JSON output (since removed) might have needed deduplication, the current key-value format doesn't require sorting for deduplication - a hash table or seen-keys array would suffice given the small fixed number of keys.

The technical implementation shows the sorting is enforced via `qsort_strcmp()` in `print_fields()`, with fields defined in `repo_info_fields[]` already in lexicographical order. The test suite (`t1900-repo.sh`) verifies basic functionality but doesn't yet test the sorting behavior (which was noted as pending in the thread summary).

This appears to be a late-stage design critique of an already-approved feature, questioning whether the lexicographical sorting provides sufficient benefit to justify the parsing complexity it imposes on scripts. The discussion may influence whether this behavior gets adjusted in a follow-up patch or documented as an intentional design constraint.
