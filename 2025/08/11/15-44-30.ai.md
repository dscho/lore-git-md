This is a discussion about the output sorting behavior in the `git repo info` command implementation, specifically regarding the `references.format` field.

Junio C Hamano is responding to Phillip Wood's critique of the lexicographical sorting behavior in Lucas Seiki Oshiro's patch series. Phillip had argued that sorting the keys lexicographically makes script parsing unnecessarily complex, since script authors would need to check each key's value rather than relying on positional output matching their input order. He noted that while JSON output (since removed) required deduplication, this could have been achieved without sorting given the small fixed number of keys.

Junio concisely endorses Phillip's position with "Very good. Thanks," indicating agreement with the critique of the current lexicographical sorting implementation. This suggests the maintainer's preference for changing the behavior to preserve input order, which would simplify scripting use cases. The exchange represents final polishing feedback on a series that's otherwise approved for inclusion, with this being one of the last open design questions before merging.

Key technical details in play:
- Current behavior uses `qsort_strcmp()` for lexicographical sorting
- Phillip proposes either hash table or array-based deduplication instead
- The field in question is `references.format` (reporting "files" or "reftable")
- This affects the `git repo info` command's machine-readable output formats (keyvalue and nul)

The discussion highlights a tension between internal consistency (lex sort) and practical usability (input order preservation) in command output design.
