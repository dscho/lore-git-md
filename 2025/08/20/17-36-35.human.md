This is a response from Junio C Hamano to Patrick Steinhardt's RFC series introducing a new `git-history` command. The email focuses on two key design considerations for the proposed history editing functionality.

First, Junio notes the command should handle `notes.rewriteref` itself rather than relying on cherry-pick infrastructure, since cherry-pick deliberately doesn't handle notes rewriting (as explained in the footnote). This is important for maintaining note consistency during history rewrites.

Second, Junio comments on the current limitation to linear history, calling this a sensible design decision but also suggesting future expansion could allow rewriting commits reachable from multiple branches. He proposes potential safeguards like protected branches that would abort if affected by rewrites.

The response shows engagement with the RFC's technical direction while raising specific considerations around note handling and multi-branch scenarios. Junio's footnote provides useful context about the philosophical difference between history rewriting (discarding old history) versus cherry-picking (creating parallel history). This suggests the `git-history` command's design needs to carefully consider which model it follows for various operations.
