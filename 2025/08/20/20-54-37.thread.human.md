Here's the updated human-readable thread summary:

Joe Drew reported a bug where Git 2.51.0 on macOS ARM64 shows spurious "lock file exists" errors during fetch operations in bare repositories, particularly when mirroring remote refs. The issue doesn't occur in Git 2.39.5. Jeff King initially suggested two possibilities: case-sensitivity conflicts on macOS's case-insensitive filesystem (where similar branch names like "ptv-2164" and "PTV-2164" could collide), or a regression in ref transaction handling. Using the reftable backend works around the issue since it doesn't use filesystem locking.

Patrick Steinhardt has now weighed in, confirming the case collision scenario is plausible and identifying that the new batched transaction mode in git-fetch may be making the problem more visible. Where older versions might have completed the operation with inconsistent state, the newer batched transactions now fail entirely when encountering what the filesystem sees as duplicate refs due to case variations. The discussion is now focused on whether this represents a regression in transaction logic or simply exposes a pre-existing case-sensitivity issue that was previously masked. Patrick suggests improving the handling of case collisions by allowing the transaction to continue with non-problematic refs rather than failing completely. The reftable backend remains a viable workaround while the core issue is investigated.
