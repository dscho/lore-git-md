This thread examines spurious "lock file exists" errors during fetch operations in bare repositories, originally reported by Joe Drew on macOS ARM64 with Git 2.51.0. The core issue stems from case-sensitivity conflicts on macOS's case-insensitive filesystem interacting with Git's batched ref transaction mode introduced in 2.51.0. Jeff King and Patrick Steinhardt traced the problem to improved case collision detection that now properly flags what were previously undetected filesystem inconsistencies.

The discussion has evolved through several technical phases: initial diagnosis revealed this wasn't a regression but rather improved correctness exposing hidden filesystem issues; Karthik Nayak proposed modifying the files backend as an interim solution while reftable remains the preferred long-term fix; and recent exchanges have surfaced compatibility concerns with tools like cgit when using reftable.

In the latest development, Patrick Steinhardt clarified reftable's backward compatibility design - older Git versions should still detect the repository via a HEAD dummy value even if they don't understand reftable format. His response to Jeff King suggests that if cgit completely fails to recognize reftable-formatted repositories (as observed), this may indicate a bug in reftable's compatibility layer that needs addressing.

The thread maintains consensus that reftable is the technically superior solution, but acknowledges real-world adoption challenges. The files backend modification remains under consideration as a transitional measure, with Junio Hamano emphasizing the need for clear documentation of its batched-operation scope. Ecosystem compatibility issues, particularly with tools that link against Git's internals rather than using its CLI, continue to be a concern that may require attention in both the short and long-term solutions.
