This thread investigates spurious "lock file exists" errors during fetch operations in bare repositories, originally reported by Joe Drew on macOS ARM64. The issue stems from case-sensitivity conflicts on macOS's case-insensitive filesystem interacting with Git's new batched ref transaction mode in git-fetch(1).

Joe Drew's latest email confirms through bisection that the behavior change was introduced by Karthik Nayak's commit implementing batched reference updates (0e358de64a). This isn't a regression but rather improved correctness - the new code properly detects case collisions (like "ptv-2164" vs "PTV-2164") that previously could cause silent inconsistencies. The reftable backend avoids these issues entirely as it doesn't use filesystem locks.

The core disagreement remains between Junio Hamano's position that reftable is the definitive solution (and that files backend modifications would delay necessary migration) versus Karthik Nayak's proposed transitional patch to make the files backend more tolerant of case collisions. Jeff King and Patrick Steinhardt have contributed technical analysis confirming the batched transactions are working as intended, with Patrick shifting focus to user guidance during the transition.

With the bisect results now confirming the technical root cause, the discussion appears to be moving toward practical considerations: whether to accept Karthik's transitional patch, how to document the migration path to reftable, and what warnings to provide users about filesystem limitations. The maintainer's strong preference for reftable adoption remains the primary obstacle to any files backend modifications.
