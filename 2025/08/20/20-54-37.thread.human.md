Here's a human-readable summary of the thread so far:

Joe Drew reported a puzzling issue where Git 2.51.0 on macOS ARM64 fails with "lock file exists" errors during fetch operations in bare repositories, even for branches that don't exist. This wasn't happening in Git 2.39.5. The errors suggest phantom lock files are being detected, though no actual lock files are present when checked.

Jeff King has weighed in with two possible explanations. First, he suspects this could be a case-sensitivity issue on macOS's filesystem, where similarly-named branches (like "ptv-2164" and "PTV-2164") might trigger lock conflicts that get cleaned up too quickly to see. He suggests trying the reftable backend as a workaround since it doesn't use filesystem locks. Second, Jeff notes the version discrepancy is unusual for a simple case collision and recommends building Git from source to bisect when the regression appeared, offering to help with that process if needed.

The thread is now focused on determining whether this is a case-sensitivity quirk, a regression in ref handling, or something specific to the ARM64 macOS environment. Jeff has provided concrete next steps to investigate further.
