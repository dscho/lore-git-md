This thread began with a report of mysterious "lock file exists" errors during fetch operations in bare repositories on macOS, where Git 2.51.0 started failing where 2.39.5 had worked. Jeff King and Patrick Steinhardt traced this to case-sensitivity conflicts on macOS's case-insensitive filesystem interacting with Git's new batched ref transaction mode. The discussion revealed this wasn't a regression but rather improved correctness exposing previously undetected filesystem-level issues.

The core technical team - including Patrick Steinhardt, Jeff King, and Junio Hamano - quickly converged on reftable as the proper solution, with Junio firmly rejecting any workarounds for the files backend. The consensus was that reftable avoids these filesystem issues entirely while providing other benefits, and should be recommended as production-ready. Patrick shifted focus to improving user guidance about the underlying filesystem limitations during transition.

Karthik Nayak has now proposed a technical alternative - modifying the files backend to allow partial success during fetches with colliding refs, preserving the first conflicting ref rather than failing completely. While this 4-line change would improve the user experience for those not yet on reftable, it directly contradicts Junio's clear preference to push users toward reftable rather than maintain the files backend's collision handling. The patch appears technically sound but faces an uphill battle given the maintainer's stance. With the discussion having already reached consensus on reftable adoption, this late-stage proposal may serve primarily to document an alternative approach rather than change the outcome.
