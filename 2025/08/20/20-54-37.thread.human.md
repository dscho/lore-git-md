This thread addresses a bug where bare repositories on macOS ARM64 report spurious "lock file exists" errors during fetch operations, first reported by Joe Drew in Git 2.51.0. The issue stems from case-sensitivity conflicts on macOS's case-insensitive filesystem interacting with Git's batched ref transaction mode. Jeff King and Patrick Steinhardt traced this to a correctness improvement in Git 2.51.0 that now properly detects case collisions which previously went unnoticed.

The discussion has evolved through several phases: initial diagnosis identified reftable as the preferred long-term solution (avoiding filesystem locks entirely), while Karthik Nayak proposed a targeted modification to the files backend as an interim fix. His patch specifically adjusts error handling for batched operations (fetch, receive-pack, and update-ref --batch-updates) to use a more precise error code when lock file creation fails. 

Junio Hamano has emphasized the need for clear documentation of this batched operation scope in the commit message, which Nayak has now confirmed he will include in his final patch submission. The thread maintains consensus that while reftable remains the ultimate solution, this files backend modification provides a reasonable stopgap measure. However, ecosystem adoption challenges - particularly cgit's current incompatibility with reftable - remain a significant concern that may slow the transition.
