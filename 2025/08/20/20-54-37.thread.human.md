This thread began with Joe Drew reporting spurious "lock file exists" errors during fetch operations in bare repositories on macOS ARM64, specifically between Git versions 2.39.5 (working) and 2.51.0 (failing). Investigation by Jeff King and Patrick Steinhardt revealed the root cause: case-sensitivity conflicts on macOS's case-insensitive filesystem interacting with Git's new batched ref transaction mode. The behavior change was confirmed via bisect to commit 0e358de64a ("fetch: use batched reference updates"), which properly detects case collisions that previously went unnoticed.

The discussion has evolved into a broader architectural debate. While all agree the reftable backend cleanly resolves the issue by avoiding filesystem locks entirely, there are concerns about ecosystem adoption - particularly with tools like cgit that link directly against older Git libraries. Karthik Nayak has proposed modifying the files backend to return more specific error types (REF_TRANSACTION_ERROR_CREATE_EXISTS) for case collisions, allowing batched operations to continue processing. This is positioned as a transitional solution for users who cannot immediately switch to reftable.

Junio Hamano remains skeptical of files backend modifications, arguing they paper over deeper issues with case-insensitive filesystem handling. The latest exchange sees Nayak clarifying implementation details of his patch while acknowledging the fundamental limitations. Both recognize the need for better backend-specific verification hooks and clearer migration paths to reftable. The thread appears to be converging on reftable as the long-term solution, with increased focus on documenting the transition and addressing compatibility concerns in dependent tools.
