This is a review response regarding the `split` subcommand implementation in Patrick Steinhardt's `git-history` RFC series. D. Ben Knoble provides detailed feedback on the message handling and user experience aspects of the interactive splitting functionality.

Key technical points raised:
- Questions the message handling approach where only the first split commit gets a new message while the second retains the original, suggesting using the original as a template for both
- Notes the SPLIT_MSG template differs from standard commit templates and isn't recognized by editors
- Proposes aligning with regular commit templates (including verbose/status options) while prepending split-specific instructions
- Observes the "all or nothing" behavior when aborting - unlike interactive rebase, changes aren't left partially staged, requiring re-staging for another attempt
- Suggests documenting this behavior difference

The feedback focuses on UX polish rather than core functionality, indicating the basic implementation is sound but could benefit from more familiar workflows. Knoble's suggestions aim to make the splitting process more intuitive by aligning with existing Git conventions around commit message editing and partial operation states.

This continues Knoble's pattern of thorough technical review seen in earlier patches, now focusing on the interactive splitting workflow rather than implementation mechanics. The feedback doesn't challenge the fundamental approach but offers concrete suggestions to improve usability.
