This is part 12 of Patrick Steinhardt's ongoing refactoring series to move packfile management into a dedicated `packfile_store` structure. The patch introduces a new helper function `packfile_store_load_pack()` that consolidates the common pattern of checking if a packfile exists in the store and adding it if not.

The new function handles:
1. Converting the .idx path to the corresponding .pack path for hashmap lookup
2. Checking if the packfile already exists in the store
3. Loading and adding new packfiles when needed
4. Returning either the existing or newly loaded packfile

Karthik Nayak responds positively to this change, noting it addresses his earlier observation about midx.c handling packfile loading directly. He asks two technical questions:
1. Why not use `strmap` for the packfile store's map instead of the current hashmap implementation
2. Confirms the function's behavior matches expectations for returning existing/new packfiles

The patch modifies several callers (fast-import.c, index-pack.c, midx.c, packfile.c) to use the new helper, removing duplicate packfile loading logic. The changes are mechanical but improve encapsulation by centralizing packfile loading logic within the packfile store abstraction.

This continues the series' steady progress in moving packfile operations out of the generic object database while maintaining identical behavior. The discussion remains focused on implementation details of the abstraction rather than architectural concerns.
