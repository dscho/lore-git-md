Bugfix report for ref locking behavior in bare repositories during fetch.

Joe Drew reports encountering a "lock file exists" error when performing a fetch operation in a newly created bare repository, specifically when using Git 2.51.0 on macOS (installed via Homebrew). The error occurs during reference updates, claiming a lock file exists for a branch that doesn't yet exist locally, though the branch does exist on the remote. The issue does not manifest with Apple's bundled Git 2.39.5.

The problem appears when running a fetch command that mirrors remote refs to local refs, similar to what `go mod download` executes. The error suggests a race condition or incorrect lock file handling in newer Git versions when creating new references in bare repositories. The reporter has verified no actual lock files exist in the refs directory when the error occurs.

Key technical points for future reference:
- Reproducible with Git 2.51.0 but not 2.39.5
- Occurs during `git fetch` with refspecs that create new references
- Error claims existence of `.lock` files that don't actually exist
- Affects bare repositories specifically
- System diagnostics show ARM64 macOS with clang 17.0.0

The report includes system diagnostics but notes the proprietary nature of the repository prevents sharing reproduction details. The error message suggests either a regression in lock file handling or a platform-specific issue in newer Git versions, particularly around the refs backend in bare repositories. The reporter is open to further debugging but has likely hit a known class of issues around reference transactions and lock file cleanup.
