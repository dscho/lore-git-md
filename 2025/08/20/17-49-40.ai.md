This is a technical discussion in the ongoing RFC thread about the proposed `git-history` command, focusing on notes handling and multi-branch operation considerations.

Ben Knoble responds to Junio Hamano's feedback on Patrick Steinhardt's RFC series, agreeing with the need to properly handle `notes.rewriteref` in the new command. The discussion centers around two key aspects: notes handling semantics and potential future support for multi-branch history editing.

On notes handling, both Junio and Ben emphasize that the command should properly implement notes rewriting behavior, distinguishing between history rewriting operations (which should respect `notes.rewriteref`) and cherry-pick operations (which deliberately don't).

The conversation then shifts to the possibility of expanding beyond linear history editing. Ben draws parallels between Junio's suggestion of multi-branch operation and both Git's existing `rebase --update-refs` functionality and Jujutsu's behavior. He proposes considering pushed/unpushed commits as a safety heuristic while still allowing force-push scenarios, suggesting Git could borrow from Jujutsu's approaches here.

The email also contains a meta-comment appreciating the project's willingness to learn from other tools (like Jujutsu and the Vim/Neovim ecosystem) while maintaining Git's core workflow. This continues the thread's theme of carefully adapting external innovations to fit Git's model.
