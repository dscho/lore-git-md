This is a review response discussing the `split` subcommand implementation in Patrick Steinhardt's `git-history` RFC series.

D. Ben Knoble provides detailed feedback on the message handling and user experience aspects of the `split` subcommand. The review focuses on two main areas: commit message templates and editor behavior. 

First, Knoble questions the current approach where only the first split commit gets a new message while the second retains the original. They suggest showing the original message as a template for both commits, giving users more context when writing new messages. This is compared to Jujutsu's different approach, though Knoble acknowledges this may be a matter of preference.

Second, the review notes that the SPLIT_MSG template differs from Git's standard commit template and isn't recognized by editors as a commit message file. Knoble proposes using the regular template format with the split-specific instructions prepended, while also respecting standard commit.* configs. 

The review also observes that aborting the split leaves users in a different state than interactive rebase - requiring re-staging changes to retry, rather than preserving partial work. Knoble suggests documenting this "all or nothing" behavior.

These are thoughtful UX suggestions from an engaged reviewer, building on earlier technical feedback in the thread. The comments focus on making the new command feel more consistent with Git's existing patterns while maintaining flexibility for history editing workflows.
