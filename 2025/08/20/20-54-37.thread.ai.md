Thread summary:

Bug report and investigation into spurious "lock file exists" errors during fetch operations in bare repositories, originally reported by Joe Drew on macOS ARM64 with Git 2.51.0. Core issue involves phantom lock file errors when mirroring remote refs in bare repos, not present in Git 2.39.5. Jeff King initially identified two potential causes: case-sensitivity conflicts on macOS's case-insensitive filesystem (where branches like "ptv-2164" vs "PTV-2164" could collide) or a regression in ref transaction handling between 2.39.5 and 2.51.0. Patrick Steinhardt confirms the case collision scenario and identifies the new batched ref transaction mode in git-fetch(1) as a likely factor - where previously one-by-one updates might complete with inconsistent state, batched transactions now fail entirely when attempting to lock what the filesystem considers the same ref multiple times due to case variations.

Technical details:
- Specific versions involved: 2.39.5 (working) vs 2.51.0 (failing)
- Reftable backend (`--ref-format=reftable`) works as workaround by avoiding filesystem locks
- Batched ref transaction behavior introduced between these versions appears central
- macOS case-insensitive filesystem may be hiding underlying case collision issues

Open questions:
- Whether this represents a regression (new behavior catching real problems) or bug (incorrect lock state tracking)
- How previous versions handled case-colliding refs (possibly with undetected inconsistencies)
- Best approach to gracefully handle case collisions in batched transactions

Current understanding suggests the batched transaction logic is properly detecting what was previously an undiagnosed case-sensitivity issue, though the behavior change appears as a regression. Patrick proposes detecting and ejecting problematic refs from transactions while continuing with others. The reftable backend remains a viable workaround for affected users. Next steps would involve testing with reftable, bisecting Git versions to identify the exact behavior change, and potentially modifying the batched transaction logic to handle case collisions more gracefully.
