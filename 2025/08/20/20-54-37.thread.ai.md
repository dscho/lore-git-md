Thread summary:

Bug report regarding ref locking behavior in bare repositories during fetch operations, reported by Joe Drew. Core issue involves spurious "lock file exists" errors when creating new references during fetch in Git 2.51.0 on macOS ARM64 with clang 17.0.0, not present in Git 2.39.5. The error occurs specifically when mirroring remote refs to local refs in bare repos, with phantom lock files being reported for non-existent branches. Jeff King suggests two potential explanations: case-sensitivity issues on macOS's case-insensitive filesystem where colliding branch names (e.g., "ptv-2164" vs "PTV-2164") could cause lock file conflicts, or an actual regression in ref transaction handling between 2.39.5 and 2.51.0. Technical details include the reftable backend as a workaround (`--ref-format=reftable`) since it doesn't use filesystem-based locking, and the specific versions in question (2.39.5 vs 2.51.0). Jeff notes the version discrepancy is unexpected for a simple case collision scenario and recommends building Git from source to bisect when the regression was introduced, offering guidance if needed. Open questions remain about whether this is a case-sensitivity issue, regression, or platform-specific bug, with next steps including testing with reftable backend and bisecting Git versions to identify the problematic commit. The reporter has verified the absence of actual lock files when the error occurs, suggesting incorrect lock state tracking in newer versions.
