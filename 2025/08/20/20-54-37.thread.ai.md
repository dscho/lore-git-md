Bug report and investigation into spurious "lock file exists" errors during fetch operations in bare repositories, originally reported by Joe Drew on macOS ARM64 with Git 2.51.0. Core issue involves phantom lock file errors when mirroring remote refs in bare repos, not present in Git 2.39.5. Jeff King and Patrick Steinhardt identified the root cause as case-sensitivity conflicts on macOS's case-insensitive filesystem interacting with Git's new batched ref transaction mode in git-fetch(1). 

Technical details:
- Specific versions involved: 2.39.5 (working) vs 2.51.0 (failing)
- Batched ref transactions (introduced between these versions) now properly detect case collisions that previously went unnoticed
- Old one-by-one updates could result in flip-flopping ref values without detection
- Reftable backend (`--ref-format=reftable`) avoids filesystem locks and case collision issues entirely
- macOS case-insensitive filesystem masks underlying case collision issues
- Karthik Nayak's patch modifies files backend to return REF_TRANSACTION_ERROR_CREATE_EXISTS (instead of GENERIC) for EEXIST lock file errors
- Junio Hamano questions whether this properly addresses transactional semantics
- Nayak clarifies this change specifically targets batched updates (fetch/receive-pack/update-ref --batch-updates) which ignore non-GENERIC errors
- Both acknowledge deeper issues with refs_verify_refnames_available() on case-insensitive filesystems
- Joe Drew's bisect confirms commit 0e358de64a ("fetch: use batched reference updates") as introducing the behavior change
- Bisection proves case collision hypothesis and shows batched transactions working as designed
- New confirmation from Dave Evans via Jeff King that reftable backend resolves the fetch errors
- Evans reports cgit incompatibility due to direct linking against older Git libraries without reftable support
- Jeff King notes reftable's backward compatibility design (HEAD dummy value) suggests cgit issue may be more severe

Current consensus:
- Not a regression but improved correctness revealing hidden filesystem-level problems
- Batched transaction behavior is working as intended by detecting case collisions
- Previous behavior allowed silent inconsistencies with case-colliding refs
- Reftable remains positioned as the preferred solution
- Junio Hamano maintains skepticism about files backend modifications while engaging technically
- Karthik Nayak's patch provides an interim solution for batched operations
- Ecosystem adoption challenges emerge with tools like cgit that tightly couple to Git internals

Open questions/options:
- Whether REF_TRANSACTION_ERROR_CREATE_EXISTS provides sufficient semantic distinction
- Need for backend-specific verification hooks to properly handle case-insensitive filesystems
- Documentation strategy for both reftable recommendation and any interim files backend behavior
- Need for clearer migration path from files backend to reftable
- Libgit2 reftable implementation status remains relevant for ecosystem adoption
- User warning messaging about filesystem limitations during transition period
- Handling of tools like cgit that link directly against Git's implementation
- Extent of reftable backward compatibility issues in the wild

Participant positions:

- Jeff King had suggested waiting for Git 3.0 for broader reftable adoption, now provides real-world confirmation of reftable solution
- Junio Hamano strongly supports immediate reftable recommendation as production-ready while technically engaging with files backend modifications
- Karthik Nayak proposes practical files backend modification as transitional solution for batched operations
- Joe Drew's bisect provides concrete evidence supporting the technical analysis
- Dave Evans' report via Jeff King confirms reftable solution while highlighting ecosystem challenges
- All agree reftable is the cleanest long-term solution but acknowledge transitional pain points
