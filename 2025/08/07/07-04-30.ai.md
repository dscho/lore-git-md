This is a follow-up discussion in the ongoing "commit-graph: remove reliance on global state" series, specifically addressing patch 2/9 about Bloom filter counters. Patrick Steinhardt responds to Junio Hamano's concerns about using signed vs unsigned integers for counting Bloom filters.

The key technical point revolves around whether counters that can never be negative should be unsigned types. Junio had previously argued there are valid cases for signed counters (sentinel values or error returns), while Patrick maintains that when no such cases exist (as in this specific Bloom filter implementation), unsigned types better communicates the semantic constraint.

Patrick accepts Junio's general reasoning about signed integers being appropriate when sentinels or error returns are needed, but argues this particular case doesn't require those capabilities. The counters are simple non-negative values tracking entries from 0 to NUM_ENTRIES, making unsigned integers both semantically correct and self-documenting.

This exchange represents the philosophical debate about integer types that was noted in the thread summary, though here it's focused on a concrete implementation choice rather than blocking progress. The series has already incorporated Junio's maintainer guidance on type selection, with this being a specific example where Patrick believes unsigned types are justified despite the general preference for signed integers in error-handling contexts.
