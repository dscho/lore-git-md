This is a follow-up discussion on the git-rebase documentation improvements, focusing on performance considerations in commit selection.

Phillip Wood responds to Junio Hamano's clarification about the rebase internals, agreeing that the current documentation's two-step model (listing commits then filtering) doesn't match the actual single-pass implementation. However, he notes there is still a meaningful performance distinction within the single pass - the initial commit selection is fast, while cherry-pick detection (which happens during that pass) can be slow, especially with many upstream commits.

The discussion centers on how to best represent this in the documentation. Phillip supports either:
1. Combining the steps into one simplified description (as Junio suggested)
2. Keeping them separate but clearly marking it as a conceptual model rather than implementation truth

He references the historical context for `--reapply-cherry-picks` (added in 2020) which was specifically introduced to optimize this known performance bottleneck. The exchange shows the careful balance being struck between technical accuracy and pedagogical clarity in the rebase documentation.
