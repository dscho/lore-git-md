This is a maintainer discussion thread about Git's alias behavior, specifically regarding the security and reliability implications of allowing aliases to shadow built-in commands.

Junio C Hamano responds to Elijah Newren's points about command shadowing, acknowledging both the technical and social aspects of the issue. He confirms that while the current system doesn't perfectly prevent recursive aliases (demonstrating with a `git loop` example that allowing command shadowing would break script reliability and helper expectations. 

The email highlights two key technical details: 1) the imperfect prevention of recursive aliases (showing a case where `!git loop foo` bypasses the recursive alias detection), and 2) the broader impact on script authors and those helping users if built-in commands could be redefined. Hamano notes that while configuration variables already alter porcelain command behavior, script authors using porcelain commands are "beyond salvation" in terms of reliability expectations.

This discussion reinforces the thread's conclusion that command shadowing prevention is intentional, though it acknowledges some edge cases in the current implementation. The security implications raised earlier in the thread remain valid, with this email focusing more on the practical scripting and support consequences of any potential changes to this behavior.
