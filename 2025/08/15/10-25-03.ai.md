This is a documentation refinement discussion in the ongoing git-rebase man page improvement thread.

Phillip Wood responds to Julia Evans' consideration of which rebase internals details to include in the documentation. The exchange focuses on balancing technical accuracy with approachability, particularly around performance characteristics of rebase operations. Julia had proposed keeping the `git log` step description to help users understand rebase performance, suggesting it distinguishes between a "fast" log step and "slow" patch-id step for cherry-pick detection.

Phillip questions whether most users would understand the underlying patch-id mechanics well enough for this distinction to be useful. He notes the performance impact is most noticeable in large, fast-moving repositories and partial clones, where the current implementation's suboptimal blob fetching exacerbates the issue. Phillip suggests that if mentioning the potential slowness, the documentation should also note this step can be skipped (presumably via `--reapply-cherry-picks`).

The discussion reveals differing perspectives on where to draw conceptual boundaries when describing rebase's internal steps - Julia favors a model that helps users reason about performance, while Phillip emphasizes the actual implementation realities. This ties back to Junio's earlier suggestion to generalize the steps description rather than mentioning specific commands like `git log`.

Key technical points mentioned include:
- Patch-id generation mechanics for cherry-pick detection
- Performance characteristics in large repositories and partial clones
- The `--reapply-cherry-picks` option as a performance optimization
- Ongoing debate about how to structure the conceptual model of rebase operations

This continues the thread's theme of refining the technical accuracy of rebase documentation while maintaining approachability, now focusing on performance considerations and implementation details that might warrant documentation.
