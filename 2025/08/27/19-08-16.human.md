This is a proposal to use SQLite for SHA-1/SHA-256 object ID mappings in the ongoing hash interoperability work. Eric Wong suggests SQLite as an alternative to the custom formats currently under discussion (Derrick Stolee's reftable-inspired approach and Junio Hamano's two-file separation).

Wong argues SQLite meets all the stated requirements for the mapping storage: efficient bidirectional lookups, small incremental updates, type information for garbage collection, and support for multiple hash algorithms. He notes SQLite's portability and transactional capabilities, while acknowledging its mmap limitations and the project's closed development model.

The email positions SQLite as a mature alternative that could reduce Git's custom format proliferation. Wong contrasts this with Git's historical trend toward more compiled code and complex build systems, expressing nostalgia for Git's earlier script-heavy architecture. This is a new perspective in the thread, which had previously focused on custom storage solutions.

The proposal doesn't address how SQLite would integrate with Git's existing object storage model or compare performance-wise to the other proposed formats. It's more of a high-level suggestion than a concrete implementation plan, but offers a potentially simpler path than designing a new storage format from scratch.
