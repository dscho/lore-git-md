This is a policy discussion email in the ongoing Rust infrastructure thread, specifically addressing concerns about portability and security implications of introducing Rust as a non-optional component.

Taylor Blau responds to Elijah Newren's distinction between interoperability (which is working well with the current FFI approach) and portability (where Rust compilers are less widely available than C). Blau acknowledges the portability reduction but argues this is an acceptable tradeoff, comparing it to existing platform limitations where some systems can't run the latest Git versions. 

The key points center on security implications: Blau counters concerns about backporting security fixes across language boundaries by noting (1) Rust's likely security advantages over C, and (2) the project's established practice of thorough backporting. He suggests security vulnerabilities would be handled the same way regardless of language transitions, with fixes applied to older versions when needed.

This email doesn't introduce new technical elements but provides important perspective on the policy debate, particularly around how security maintenance might work post-Rust. It reinforces the Rust proponents' position that portability reduction is manageable given Git's existing version support practices, while acknowledging the real but addressable challenges of cross-language security maintenance. The response is measured and grounded in the project's historical practices rather than hypotheticals.
