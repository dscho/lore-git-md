New proposal in SHA-1/SHA-256 interoperability discussion: SQLite-based mapping storage

Eric Wong enters the thread with a counterproposal to both Hamano's two-file separation and Stolee's reftable-inspired format, suggesting SQLite as the storage backend for bidirectional hash mappings. This represents a third architectural approach to the problem, differing fundamentally from the existing proposals by leveraging an external database system rather than custom Git formats.

The key argument centers on SQLite's maturity and capabilities matching the stated requirements: efficient bidirectional lookups, small atomic updates, mmap support, and type metadata storage. Wong positions this as reducing cognitive overhead compared to new custom formats, noting SQLite's portability even on resource-constrained systems. Technical specifics mentioned are SQLite's transaction support, ALTER TABLE for hash algorithm expansion, and in-memory database options.

Potential drawbacks acknowledged include SQLite's default mmap size limits and the project's closed contribution model. The email also includes broader commentary on Git's architectural direction away from scripting languages, though this appears tangential to the core proposal.

This suggestion introduces new evaluation dimensions to the ongoing discussion:
- External dependency tradeoffs vs custom format control
- SQLite's performance characteristics for mixed lookup/update patterns
- Long-term maintenance implications of database schema vs file formats
- Whether SQLite's feature set aligns with Git's specific access patterns

The proposal doesn't directly engage with the existing reftable vs two-file debate, instead offering a qualitatively different approach that would need comparative evaluation against both. It notably doesn't address how SQLite storage would interact with Git's existing object storage layers or whether it could meet the O(log N) lookup requirement at scale.
