Refactoring patch splitting `add-patch` declarations into a new header file, part of the larger `git-history` RFC series. This is preparatory infrastructure work for the history editing commands.

The patch moves declarations related to `add-patch.c` out of `add-interactive.h` into a new `add-patch.h`, leaving only non-patch functionality in the original header. The implementation is straightforward - 23 lines removed from `add-interactive.h`, 26 added to the new header, plus adding the include to `add-patch.c`.

Junio Hamano notes that while the split makes conceptual sense (separating patch-specific functionality from other interactive add operations), it's surprising the change doesn't update existing clients of the patch machinery like `git reset -p`. These clients currently include all of `add-interactive.h` but likely only need the new `add-patch.h` subset. This suggests potential follow-up work to clean up includes in those callers.

The change appears well-contained and mechanically sound, though as Junio points out, it may be incomplete regarding client updates. The patch is part of a larger refactoring effort to support the new `git-history` command's needs while also improving code organization. The separation of concerns here could make the codebase more maintainable long-term by reducing unnecessary header dependencies.
