Bugfix for progress meter delay functionality, part of the signal-free timer implementation effort.

This patch fixes a long-standing bug in Git's progress meter delay handling where the delay was effectively always 1 second due to improper flag resetting. Johannes Sixt explains that while the API allows custom delay times via `start_delayed_*()` functions, the implementation would incorrectly count down the delay on every progress update after the first second because the `progress_update` flag wasn't being reset. The fix copies the flag state to a local variable and resets the global flag immediately.

The patch makes two key changes:
1. Fixes the delay counting logic by properly handling the `progress_update` flag
2. Changes the default delay from 2 to 1 second to match the actual behavior users have been experiencing (and apparently not complaining about)

The changes affect both the progress.c implementation and the git.adoc documentation. Sixt notes this has been broken since the feature's inception, surviving multiple previous changes to the progress API. The fix is straightforward and maintains the existing signal-free approach that was previously agreed upon in the thread.

This appears to be a well-justified bugfix that aligns the documented behavior with reality while preserving the signal-free timer implementation direction. The patch is focused and includes both code and documentation updates. The change from `sig_atomic_t` to `int` (rather than `bool`) reflects consideration for potential backporting to maintenance branches.
