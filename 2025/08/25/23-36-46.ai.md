This is a clarification about shallow clone implementation details in the ongoing grafts removal discussion.

Junio Hamano explains that shallow cloning operations (--depth, --shallow-since, --unshallow) don't use either the grafts mechanism being removed or the intended replacement mechanism (git replace). Instead, they use their own internal mechanism that happens to share some code paths but stores data separately from regular grafts. This addresses Bagas Sanjaya's question about whether shallow clones would transition to git replace.

The response confirms that shallow clone functionality won't be directly affected by grafts removal since it already uses a distinct implementation, though it does share some underlying code. This is an important technical clarification for the thread, as it means one of the two major concerns (shallow clones) may not require migration work, though the other (history.git) remains unresolved.

Key technical points:
- Shallow clone operations have their own mechanism separate from grafts
- They share some code paths with grafts but store data differently
- This means grafts removal shouldn't impact shallow clone functionality
- The explanation comes from the Git maintainer with implementation knowledge

The response doesn't address the history.git use case, keeping that part of the discussion open while resolving the shallow clone question. This moves the thread forward by narrowing the scope of potential impacts from grafts removal.
