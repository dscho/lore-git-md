This thread discusses an edge case in `git cat-file`'s handling of ambiguous object IDs, where manually corrupted repositories with objects that have colliding prefixes can lead to unhelpful duplicate hash hints. Jon Forrest initially reported that `git cat-file -t` would show identical abbreviated hashes (like 7898192) for different objects without displaying the full hashes to distinguish them.

Patrick Steinhardt analyzed the issue, noting it requires intentional repository corruption and questioning whether such an artificial scenario warrants a fix, since `git-fsck` would detect the corruption. The discussion then shifted to whether this could occur without corruption and if the behavior had changed in recent versions.

Junio Hamano has now weighed in, observing that the root issue lies in the disambiguation code not validating objects when generating shortened names. He proposed a concrete one-line fix in `object-name.c` that would modify how abbreviation lengths are calculated, changing the comparison from raw bytes (`GIT_MAX_RAWSZ`) to hexadecimal characters (`GIT_MAX_HEXSZ`). This change would affect all ambiguous object cases, not just this corruption scenario, potentially providing better distinction between objects that differ only in their final bytes. The fix is minimal but addresses the core issue while moving the discussion from whether to fix it to how best to implement the solution.
