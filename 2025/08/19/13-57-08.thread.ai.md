Thread identity: Discussion about planned removal of git grafts functionality in Git 3.0, focusing on real-world usage impacts particularly for the Linux kernel history repository (history.git).

Core problem: The grafts mechanism is scheduled for removal, but key use cases like history.git still depend on it to connect segments of Linux kernel history. The replacement mechanism (git replace) needs to be verified as fully capable of handling these cases before grafts can be safely removed.

Current status: Grafts remain available but marked for removal in Git 3.0. No specific migration path for history.git has been demonstrated yet.

Key technical details:
- history.git uses grafts to stitch together different segments of Linux kernel history
- git replace is the intended replacement mechanism
- Shallow clones (--depth=1) may have grafts dependencies that need verification

Open questions:
- How to migrate history.git from grafts to replace without breaking existing references
- Whether shallow clone functionality depends on grafts internally
- What documentation/migration instructions need to be added to Git 3.0 release notes

Participant positions:
- End user strongly objects to removal until history.git migration path is proven
- Requests explicit confirmation about shallow clone compatibility
