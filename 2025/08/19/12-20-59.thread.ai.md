Reftable fsck validation series (v2) - completing stack integrity checks. Authored by Karthik Nayak, this 5-patch series adds comprehensive fsck validation for basic reftable stack integrity while maintaining strict separation between Git's fsck implementation and reftable internals. The v2 iteration incorporates feedback from Shejialuo's review of v1, with key changes including passing `struct reftable_fsck_info` as pointers rather than by value, continuing fsck checks across all worktrees despite failures, more specific error messages distinguishing table name vs extension issues, using relative paths in error messages, and additional test cases.

The series progresses through: [1/5] alphabetizing `fsck_msg_type` with whitespace tweaks reverted per Junio's request; [2/5] implementing table name validation via new `reftable/fsck.[ch]` with callback patterns to maintain library independence; [3/5] adding stack count validation; [4/5] validating trailing newlines in `tables.list` (where Junio first raised architectural questions about validation boundaries); [5/5] completing the series with sequential update index validation.

Junio Hamano's latest feedback on patch 5/5 extends his earlier architectural concerns, questioning whether update index sequence validation belongs in fsck or should be part of runtime reftable reader checks. He argues that since reftable is still new and not the default backend, now would be the ideal time to enforce stricter validation at runtime rather than only during fsck. This forms a consistent philosophical position that runtime code should catch these issues (like sequential update indices in `tables.list` and trailing newlines) rather than leaving them to fsck.

The discussion highlights key technical tensions:
- Current implementation maintains strict separation between fsck and reftable internals via `REFTABLE_FSCK_ERROR_UPDATE_INDEX` and `badReftableUpdateIndex`
- Tradeoff between runtime strictness (potentially failing operations) versus fsck-only validation
- Window of opportunity to tighten rules before reftable becomes widely deployed
- Future work still needed to validate that table names match their internal headers

Shejialuo's v1 review feedback has been addressed while maintaining the core architectural approach. Junio's new feedback introduces deeper questions about validation philosophy that may require reconsidering whether some checks (particularly in patches 4/5 and 5/5) should move from fsck to core reftable reading code. The series remains technically sound but now faces an open architectural discussion about the appropriate layer for different validation types, with implications for both implementation and test cases. Karthik had noted this series represents incremental progress in the larger reftable backend development effort with Patrick Steinhardt, carefully using lock files and sed in tests to simulate corruption scenarios. The validation scope may expand based on this discussion's outcome.
