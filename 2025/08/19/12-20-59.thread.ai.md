Reftable fsck validation series (v2) - completing stack integrity checks. Authored by Karthik Nayak, this 5-patch series adds comprehensive fsck validation for basic reftable stack integrity while maintaining strict separation between Git's fsck implementation and reftable internals. The v2 iteration incorporates feedback from Shejialuo's review of v1, with key changes including: passing `struct reftable_fsck_info` as pointers rather than by value, continuing fsck checks across all worktrees despite failures, more specific error messages distinguishing table name vs extension issues, using relative paths (e.g., `reftable/tables.list`) in error messages, and additional test cases for failure modes.

The series progresses through: [1/5] alphabetizing `fsck_msg_type` and fixing `gitmodulesLarge` documentation; [2/5] implementing table name validation via new `reftable/fsck.[ch]` with `reftable_fsck_info` struct and refined `badReftableTableName` message, including callback pattern (`reftable_fsck_report_fn`, `reftable_fsck_verbose_fn`) to maintain library independence, validation of table name format (hex min/max hashes with `.ref` extension), and distinction between malformed names vs bad extensions; [3/5] adding stack count validation through `reftable_fsck_valid_stack_count()` and `badReftableStackCount`; [4/5] validating trailing newlines in `tables.list` with `REFTABLE_FSCK_ERROR_STACK_LIST_MISSING_NEWLINE` and `badReftableStackListNewline`; [5/5] completing the series with sequential update index validation via `REFTABLE_FSCK_ERROR_UPDATE_INDEX` and `badReftableUpdateIndex`. Test coverage in `t0614-reftable-fsck.sh` verifies all checks, including new cases for table name validation that handles both main and worktree backends with verbose output when requested via fsck options.

Shejialuo's v1 review feedback has been substantially addressed in v2 while maintaining the core architectural approach: naming conventions now consistently use `reftable-fsck.h` for library API patterns, error messages distinguish between table name format violations (`badReftableTableName`) and extension issues (`badReftableTableExtension`), test paths use relative `.git/reftable/tables.list` paths per Git conventions, and the implementation continues using direct `opendir/readdir` to preserve reftable's library independence from Git internals. The validation checks remain organized as separate functions (`reftable_fsck_valid_table_name()`, `reftable_fsck_valid_stack_count()`, etc.) with error definitions local to each check, though future work may consolidate these as the validation suite grows. Karthik notes this series represents incremental progress in the larger reftable backend development effort primarily driven by Patrick Steinhardt and himself, with deeper validation checks (tables, blocks, references) planned for future work. The v2 cover letter references the detailed v1 discussion while confirming all review feedback has been either implemented or explicitly addressed with technical justifications for design choices. Open questions from v1 about optimal code organization have been resolved in favor of maintaining reftable's independence, with potential future refactoring acknowledged as the validation scope expands.
