This is a discussion thread about improving Git's history manipulation workflows, specifically around squashing fixup commits. Bernd Petrovitsch responds to R. Diez's description of a common workflow pain point - where multiple fixup commits get interleaved with other work during long build processes.

Petrovitsch offers a simple solution using existing `git rebase -i` functionality, demonstrating how to manually squash fixup commits (fixA1 and fixA2) into their parent commit (A) through interactive rebase. This contrasts with R. Diez's earlier suggestion for new `git history` subcommands or GUI tools to handle such cases more intuitively.

The exchange highlights the tension between learning Git's existing powerful-but-complex tools versus creating more specialized interfaces for common workflows. While Petrovitsch's solution works, it requires knowing the rebase syntax and counting commits (HEAD~11), which may not be obvious to all users. The thread continues exploring how to make such operations more accessible while maintaining Git's flexibility.
