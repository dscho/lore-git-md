Patrick Steinhardt's RFC for a new `git-history` command continues to generate discussion, now focusing on how it should relate to Git's existing history manipulation tools. The proposed command (currently at v1 with thirteen patches) would introduce `drop`, `reorder`, and `split` subcommands, building on Git's sequencer infrastructure while taking inspiration from Jujutsu's (jj) flexible history editing.

The latest exchange centers on command boundaries, sparked by Sergey Organov's question about whether `git-history` might subsume parts of `git rebase`. Ben Knoble responded by noting that `rebase --onto` already handles the "rebase there" case Organov described, and playfully inverted the framing to suggest rebase duplicates cherry-pick functionality rather than the other way around. This highlights an ongoing design question: where to draw the line between history editing (rebase-style operations that discard old history) and commit copying (cherry-pick-style operations that preserve original commits).

The thread has seen substantive technical review from Knoble on implementation details like array reversal logic and index behavior, while Junio Hamano previously weighed in on notes handling. The RFC remains in early stages with several open questions around merge commit support, conflict handling, and performance characteristics. The current design discussion suggests the command's ultimate scope and relationship to existing tools may still evolve before the series progresses further.
