This RFC thread discusses Patrick Steinhardt's proposed `git-history` command, which introduces `reword` and `split` subcommands for flexible history editing. The series builds on Git's replay infrastructure while drawing inspiration from Jujutsu's capabilities, focusing on non-conflicting operations after discussions at the Git Contributor's Summit.

The technical discussion has progressed significantly, with Elijah Newren and Phillip Wood reaching alignment on the branch handling strategy - they now favor automatically rewriting all affected branches, though some edge cases remain. Junio Hamano continues advocating for merging an experimental version to 'next' for user testing, while reviewers emphasize resolving fundamental issues first. The implementation includes substantial infrastructure work like separating add-patch functionality and enabling in-memory index operations.

A new concern from SZEDER Gábor highlights a key usability gap: unlike interactive rebase which checks out files during rewording, this implementation operates purely in-memory. This could hinder complex message edits where examining file states is helpful. SZEDER also questions the interface design that requires upfront commit specification rather than interactive selection. These are substantial workflow considerations that may require redesign of the reword subcommand to match user expectations.

The thread shows growing technical consensus on core mechanisms but reveals important user experience questions that emerged late in the review cycle. Patrick now faces balancing Junio's push for early testing with addressing both the branch handling implementation details and these new interface concerns before the feature can be considered complete.
