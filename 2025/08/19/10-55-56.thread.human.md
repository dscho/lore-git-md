This RFC thread explores Patrick Steinhardt's proposal for a new `git-history` command, inspired by Jujutsu (jj)'s flexible history editing capabilities. The initial thirteen-patch series introduces three subcommands: `drop` for commit removal, `reorder` for rearranging commits, and `split` for interactively dividing commits. The implementation builds on Git's sequencer infrastructure while adding new interactive workflows, particularly for the `split` operation which features hunk selection via `add-patch` and extensive test coverage.

Key reviewers D. Ben Knoble and Junio C Hamano have engaged deeply on technical details. Knoble has provided meticulous feedback across multiple patches - first on the `drop` subcommand's commit collection logic and in-memory index handling, and now on the `split` subcommand's user experience. His latest review notes that while the core functionality works, the message handling could better align with Git conventions by using the original commit message as a template for both split commits rather than just the second one. He also observes that aborting a split currently loses all staging progress, unlike interactive rebase which preserves partial work.

Junio has weighed in on design-level considerations, particularly around notes handling and operation semantics, endorsing the current focus on linear history while leaving room for future multi-branch support. The discussion reveals several open questions around merge commit handling, conflict resolution, and performance characteristics that will need addressing before this could graduate from RFC status. The thread shows healthy technical engagement with the proposal's ambitious goal of bringing Jujutsu-like flexibility to Git's native command set.
