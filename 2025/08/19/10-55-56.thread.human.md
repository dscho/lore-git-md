This thread continues Patrick Steinhardt's RFC proposal for a new `git-history` command that would offer Jujutsu-inspired history editing operations. The series is now at version 3, having grown to twenty-three patches that include both preparatory infrastructure work and command implementations.

The latest patch is a small but important refactoring of the cache-tree infrastructure to support writing in-memory indexes as trees. It generalizes `write_in_core_index_as_tree()` to work with any `struct index_state` rather than always using the repository's index. This change, while modest (just 6 lines across three files), provides needed flexibility for the history editing operations planned in later patches. The implementation maintains existing behavior while allowing callers to operate on non-repository index states - likely important for temporary indexes used during history rewriting.

The series continues to evolve with both infrastructure preparation (now including sequencer changes, hook execution support, and this cache-tree modification) and design discussions about scope. Patrick has indicated the series may be reorganized after this RFC round, potentially stopping after the `reorder` implementation while keeping `squash` and other subcommands for future work. Open questions remain about the `split` subcommand's diff visibility and how the new history edit mode will interact with existing sequencer operations.
