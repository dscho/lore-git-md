Patrick Steinhardt's proposed `git-history` command continues to generate thoughtful discussion about Git's command architecture. The RFC v3, now an eighteen-patch series, introduces history editing operations (`drop`, `reorder`, `split`, `reword`) with management commands (`abort`/`continue`/`quit`), drawing inspiration from Jujutsu (jj) while building on Git's sequencer infrastructure. Key participants include Patrick (driving implementation), Phillip Wood (providing detailed refinements), and now Oswald Buddenhagen weighing in on design philosophy.

The technical implementation has evolved through review feedback: Phillip helped simplify the `skip_commit_summary` flag, improve the `split` subcommand to edit both commit messages, and identify opportunities to reuse the sequencer's existing reword capability. Patrick plans to resolve conflicts with Jeff King's parallel work in 'seen' before sending a final RFC version, then split the series after implementing `reorder`.

A new voice in the discussion, Oswald Buddenhagen, challenges the subcommand approach itself. He argues separate atomic commands would be more discoverable through documentation than forced grouping under `git-history`, noting that requiring aliases creates inconsistency. He also questions the proposed scope boundaries as arbitrary and points to the existing "revise" tool as evidence that atomic commands work well in practice. This reinforces Elijah Newren's earlier concerns about command proliferation while adding concrete critiques of the subcommand model's documentation and usability implications.

The thread now balances two levels of discussion: the immediate technical refinements (where consensus is forming around specific implementations) and the broader architectural question of whether these operations belong together under one command. Patrick maintains the subcommand approach provides better discoverability and logical grouping, while Oswald and others suggest the Git ecosystem might be better served by discrete, focused tools. The mention of the third-party "revise" tool provides a concrete example for comparison as this design discussion continues.
