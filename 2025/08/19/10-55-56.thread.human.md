Patrick Steinhardt's `git-history` command series has reached its final form with the completion of the `split` subcommand in v7. The series introduces two powerful history editing tools - `reword` for commit message editing and now `split` for dividing commits - built on shared infrastructure including replay machinery, in-memory index operations, and refactored add-patch components.

The new `split` implementation lets users interactively divide a commit's changes into two parts while preserving the working tree state. It builds on several technical foundations from earlier patches: in-memory index patching, cache-tree support, and a new flag to prevent hunk editing conflicts. The command handles commits at any position in the history (tip, middle, or root) and includes extensive test coverage for edge cases. While it currently uses a temporary index file due to `read-tree` requirements, the implementation is designed to operate primarily in memory.

Junio Hamano has signaled readiness to merge this experimental feature to the 'next' branch for wider testing. The series represents a significant step toward more flexible history editing in Git, drawing inspiration from tools like Jujutsu while maintaining Git's core workflows. Some open questions remain about multi-branch handling and future subcommands like `drop` and `reorder`, but the current implementation provides solid foundations for both immediate use and future expansion.
