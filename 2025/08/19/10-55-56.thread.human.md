This RFC thread continues Patrick Steinhardt's proposal for a new `git-history` command, which would provide flexible set of history editing operations inspired by Jujutsu (jj). The series has evolved through three versions totaling twenty-six patches, with recent focus shifting to preparatory infrastructure work that will support the new command.

The latest patch refactors the `add-patch` subsystem to better isolate its dependencies from the general interactive add machinery. This follows an earlier header split and now removes `add-patch`'s dependency on initializing the full `add-i-state`, instead storing just the needed configuration directly. Junio Hamano has explicitly approved this change, noting the improved code organization. While technically part of the `git-history` preparation, these changes benefit Git's core codebase more broadly.

Earlier in the thread, Kristoffer Haugsbakk provided positive feedback on the `split` subcommand's intuitive syntax while identifying an error message inconsistency in `reword`. The discussion has also touched on cache-tree refactoring that enables writing arbitrary in-memory indexes as trees, with Junio noting potential applications to `git commit -o <pathspec>` workflows.

The thread shows active collaboration between Patrick (driving the implementation), Kristoffer (focusing on UX polish), and Junio (providing architectural perspective). While the core `git-history` functionality remains in development, the preparatory infrastructure improvements are already yielding cleaner code organization that benefits the wider project. Several open questions remain about error message consistency, subcommand interactions, and documentation relationships with existing commands like `rebase -i`.
