This RFC thread explores Patrick Steinhardt's proposal for a new `git-history` command (v7 series) that would add `reword` and `split` subcommands for flexible history editing. The discussion has evolved through multiple technical phases, with the current focus on how to handle branch selection during rewrites.

The core debate centers on whether to automatically update all branches pointing to rewritten commits (Elijah Newren's position) or limit updates to a HEAD-to-target walk (Steinhardt's compromise). Phillip Wood recently strengthened Newren's case by analyzing real-world repository structures, showing most refs are tags/remotes rather than local branches, making comprehensive walking more practical than initially assumed. 

D. Ben Knoble's latest contribution highlights a practical workflow consideration - the current proposals would leave "stacked branches" (those pointing to rewritten commits but whose refs are outside the rewrite range) untouched, requiring manual rebasing. While this matches existing Git behavior, Knoble notes it creates extra steps for users. Interestingly, this also means untouched branches effectively serve as backups of pre-rewrite states.

Key open questions remain about:
1. The optimal branch selection strategy (with growing support for local-branch-only updates)
2. Performance implications for large repositories
3. How to document expected behavior for different branch types
4. Whether to preserve the current three-operation-mode design

The discussion remains technical but productive, with participants like Newren, Wood and now Knoble providing concrete examples and real-world considerations to inform the design. Steinhardt has yet to respond to the latest round of feedback, particularly Wood's ref distribution analysis and Knoble's workflow observations. Junio Hamano will ultimately need to weigh these arguments when considering whether to merge the experimental series to the 'next' branch.
