This RFC thread explores Patrick Steinhardt's proposal for a new `git-history` command, inspired by Jujutsu (jj) functionality, which would provide flexible history editing operations building on Git's sequencer. The series has evolved through three versions with twenty-six patches, including preparatory infrastructure work, command scaffolding, and implementations of subcommands like `drop`, `reorder`, `split`, and `reword`.

Recent discussion has focused on both user experience and technical refinements. Kristoffer Haugsbakk praised the intuitive syntax of the `split` subcommand while noting an error message inconsistency in `reword`. Meanwhile, Patrick introduced cache-tree refactoring to enable writing arbitrary in-memory indexes as trees, which Junio Hamano observed could benefit `git commit -o <pathspec>` workflows, though he cautioned about hook exposure considerations.

The latest patch splits `add-patch` declarations into a new header file as part of the preparatory work. While Junio agrees this separation of concerns makes sense conceptually, he points out that existing clients like `git reset -p` still include the full `add-interactive.h` when they likely only need the new `add-patch.h` subset, suggesting potential follow-up cleanup. This change continues the series' pattern of both enabling new functionality and improving the codebase's organization.

Open questions remain about error message consistency, subcommand interaction in complex workflows, and how to balance simplicity with flexibility. The discussion now spans multiple technical layers, from user-facing design to low-level infrastructure changes, with active participation from both the feature author and the Git maintainer.
