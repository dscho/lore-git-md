Patrick Steinhardt's proposed `git-history` command continues to generate discussion, now focusing on how to handle branch updates during history editing operations. The v7 series implements `reword` and `split` subcommands for flexible history editing, building on Git's replay machinery while drawing inspiration from Jujutsu. The current debate centers on Steinhardt's compromise proposal to automatically update branches found in a HEAD-to-target walk, which aims to balance automation with performance.

Elijah Newren has raised significant concerns about this approach, arguing it could leave some dependent branches unmodified while others are rewritten - creating potentially confusing inconsistencies. As the merge machinery expert, Newren suggests three alternatives: rewriting all dependent branches (which he notes would actually require less code), walking all branches to detect and warn about multiple affected branches, or requiring explicit user specification via flags. He disputes Steinhardt's performance concerns, pointing out that Jujutsu handles full branch walking efficiently even in large repositories.

This reveals a fundamental tension in the design - Steinhardt prioritizes a simple, single-commit focused UI while Newren emphasizes the importance of consistent behavior to avoid disconnected histories. Other contributors remain engaged but haven't yet weighed in on this latest exchange. The discussion now needs to resolve whether Git's infrastructure can support Newren's more comprehensive approach without unacceptable performance costs, and whether the current compromise satisfies the project's standards for predictable behavior.
