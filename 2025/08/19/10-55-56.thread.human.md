Here's a human-readable summary of the thread's current state:

Patrick Steinhardt has proposed a new `git-history` command with three subcommands (`drop`, `reorder`, and `split`) that would provide more flexible history editing than Git currently offers. The RFC series is at version 1 with thirteen patches that include preparatory work, command scaffolding, and initial implementations of each subcommand. The design takes inspiration from Jujutsu (jj) while building on Git's existing sequencer infrastructure.

The discussion has now turned to fundamental questions about how this new command should relate to Git's existing history manipulation tools. Sergey Organov and D. Ben Knoble are debating whether `git-history` should absorb some of what `git rebase` does today, or whether it should remain distinct. Organov argues that rebase already has superior features (like interactive mode and merge handling) and that cherry-pick's range support was a historical misstep. Knoble points out that `rebase --onto` can handle some of the use cases being discussed, though with different behavior regarding history preservation.

Meanwhile, the implementation still has several open questions to resolve, including merge commit support, conflict handling, performance characteristics, and various edge cases. The thread shows active engagement from multiple contributors as they work through both the technical details and the architectural implications of adding this new command to Git.
