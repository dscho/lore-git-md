This thread began with Jeff King's series fixing incorrect behavior around dangling symrefs in `git fetch`, particularly with the `followRemoteHEAD=create` configuration. The original patches cleaned up test infrastructure and fixed core refs backend behavior to properly handle remote HEAD symrefs while allowing intentional deletions. Junio C Hamano had already accepted this series as complete, with the patches now in the 'next' branch.

Toon Claes later identified an edge case where the series unintentionally blocked null-to-null updates of dangling symrefs via `git update-ref --stdin`, and proposed a follow-up fix. While technically sound, Junio's latest response raises an important design question: since `update-ref` already provides a dedicated `symref-delete` command, should the more general `update` command be expanded to handle symref deletions too? This touches on deeper questions about API semantics and whether we should maintain strict separation between reference update types.

The technical aspects are clear - the follow-up would allow explicit deletions while maintaining all original protections against accidental clobbering. Both the files-backend and reftable-backend would be modified identically, with new test coverage demonstrating the behavior. The remaining discussion centers on whether this change aligns with Git's intended refs API design, or if the existing `symref-delete` command should remain the sole mechanism for removing symbolic references.
