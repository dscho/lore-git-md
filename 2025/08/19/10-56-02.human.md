Feature implementation in the `git-history` command series, adding the "reorder" subcommand.

This patch introduces the second major subcommand to Patrick Steinhardt's proposed `git-history` tool, following the "drop" subcommand from earlier in the series. The new `reorder` command provides a more direct way to rearrange commits than interactive rebase, allowing users to specify that a commit should come before or after another commit in the history.

The implementation builds on the same infrastructure as the "drop" command, reusing the `collect_commits()` and `apply_commits()` helpers while adding new logic for commit rearrangement. The command accepts either `--before` or `--after` to position a commit relative to another, with validation to ensure the commits are related and not merge commits. The patch includes extensive test coverage (218 lines) verifying edge cases like root commits, conflict detection, and various reordering scenarios.

As with the rest of the series, this is an RFC-quality implementation with some limitations - notably it still doesn't handle merge commits in the rewritten history. The commit message could better explain why this approach might be preferable to existing rebase workflows, though the examples clearly demonstrate the simpler syntax compared to interactive rebase. The test coverage appears thorough, suggesting this is a serious proposal rather than just a proof-of-concept.
