This thread discusses Git's hash algorithm strategy, initiated by Askar Safin's proposal for a regular 10-year transition policy starting with SHA-1 to SHA-256 in Git 3.0. The discussion has evolved to address both policy and technical migration challenges.

Brian m. carlson has provided key technical updates showing the codebase's readiness through architectural improvements: hash algorithm abstraction layer, reduced hard-coded hash values in tests (down to ~40 files), and increased use of relative references. In response to Simon Richter's workflow concerns about build systems relying on SHA-1 commit comparisons, Brian clarifies the migration strategy preserves backward compatibility - existing SHA-1 repositories remain fully functional, and new SHA-1 repositories can still be created. 

The interoperability work (allowing SHA-1 IDs in SHA-256 repositories) exists in a working state but requires refinement before upstream submission. Current limitations exclude some advanced features (shallow/partial clones, submodules) from full interoperability. This addresses Simon's specific need for ancestor tests and hash format conversion, though not yet complete for all repository types.
