This thread continues discussions about the planned removal of git grafts in Git 3.0, with particular focus on impacts to the Linux kernel history repository (history.git) and now also shallow clone operations. The grafts mechanism, which allows stitching together different history segments, is scheduled for removal in favor of git replace, but users are raising concrete concerns about whether this transition will be seamless.

A key open question is how history.git will migrate from grafts to replace without breaking existing references. Now Bagas Sanjaya has raised another important consideration - whether shallow clone operations (including initial shallow clones, deepening, and unshallowing) might internally depend on grafts functionality. While git replace is meant to be the replacement mechanism, there hasn't yet been technical confirmation that it can transparently handle all these cases.

The thread reflects a pattern of users requesting specific verification that critical workflows won't break before supporting the grafts removal. Both the history.git use case and now shallow clone operations appear to be areas that may need explicit documentation in the Git 3.0 release notes if the deprecation proceeds. The discussion remains unresolved as these practical concerns about migration paths and compatibility have yet to be fully addressed.
