This thread discusses concerns around the planned removal of Git's grafts functionality in Git 3.0, particularly focusing on two critical use cases: the Linux kernel's history.git repository and shallow clone operations. The grafts mechanism, while marked for deprecation, is still relied upon for stitching together Linux kernel history segments and appears to be internally used in shallow clone operations (as evidenced by "grafted" markers in `git log` output from shallow clones).

Askar Safin, a user who depends on shallow clone functionality, has strongly objected to the removal until these use cases are properly addressed. Their testing shows that current shallow clones (like `git clone --depth=1`) visibly use grafts, raising concerns about whether the replacement mechanism (git replace) will properly support this functionality. Bagas Sanjaya has also requested explicit confirmation about shallow clone compatibility with git replace.

The core issue remains unresolved: while git replace is intended as the replacement for grafts, there's no demonstrated migration path for history.git or verification that shallow clone operations will continue to work after the removal. The thread has identified these as concrete blockers that need to be addressed before proceeding with the deprecation. Documentation and migration instructions will also need to be prepared for the Git 3.0 release notes to help users transition away from grafts.
