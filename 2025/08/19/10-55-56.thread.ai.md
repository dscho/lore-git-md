Thread identity: RFC proposal for new `git-history` command with subcommands `drop` and `reorder`, inspired by Jujutsu (jj) functionality. Authored by Patrick Steinhardt. Series now at v1 with six patches - three preparatory patches modifying sequencer and cache-tree internals, command scaffolding, and two implemented subcommands (`drop` and `reorder`).

Core problem/goal: Provide more powerful history editing operations than raw rebase -i, taking inspiration from Jujutsu's workflow while building on Git's existing sequencer infrastructure. The `drop` subcommand automates commit removal while `reorder` moves commits before/after others, both avoiding manual interactive rebase steps.

Current status: Six-patch RFC series with:
1-3) Preparatory changes to sequencer and cache-tree
4) Command scaffolding
5) `drop` subcommand implementation
6) New `reorder` subcommand
Not yet in any integration branch. Implementation has known limitations around merge commits and conflict handling.

Key technical details:
- New builtin/history.c implements both subcommands sharing:
  - `collect_commits()` and `apply_commits()` helpers
  - Sequencer integration via `sequencer_pick_revisions()`
  - Branch updates via `reset_head()`
- `drop` specifics:
  - Root commit support (creates new empty root when needed)
- `reorder` additions:
  - New `replace_commits()` helper
  - `--before`/`--after` options
  - Graph manipulation in `cmd_history_reorder()`
- Preparatory changes:
  - Sequencer modifications:
    - `skip_commit_summary` and `restore_head_target` in `struct replay_opts`
    - HEAD reset logic in `pick_commits()`
  - Cache-tree refactoring:
    - `write_in_core_index_as_tree()` now takes explicit `struct index_state`
- Test coverage:
  - 800+ lines across t/t3XXX-history-*.sh
  - t3450-history-drop.sh tests commit removal cases
  - New t3451-history-reorder.sh tests:
    - Basic reordering in both directions
    - Edge cases and root handling
    - Conflict scenarios

Open questions/loose ends:
- Still no support for merge commits in rewritten history
- Conflict handling remains basic (falls back to cherry-pick --continue)
- Future subcommands (split) not yet implemented
- Performance impact of repeated rewriting unmeasured
- Cache-tree changes may need broader review
- Need evaluation of interaction with other history-rewriting ops
