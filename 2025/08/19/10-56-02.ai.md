Feature implementation in the `git-history` series, adding the "reorder" subcommand. This is patch 6/11 in the RFC series introducing new history editing commands inspired by Jujutsu (jj).

The new `git history reorder` command allows moving a commit to come before (`--before`) or after (`--after`) another specified commit, automating what would normally require interactive rebase. The implementation:
- Uses the same collect_commits()/apply_commits() helpers from the earlier "drop" subcommand
- Adds new replace_commits() helper to handle the commit reordering logic
- Rejects merge commits (like the drop command)
- Includes extensive test coverage (218 lines) verifying:
  - Basic reordering in both directions
  - Edge cases (making commits, root handling)
  - Conflict detection and resolution
  - Input validation

Key technical details:
- New options: `builtin/history.c` gains `--before` and `--after` flags
- Core logic in `cmd_history_reorder()` handles the commit graph manipulation
- Uses same sequencer infrastructure as drop command
- Documentation updates show usage examples
- Tests in t3451-history-reorder.sh cover all major scenarios

Limitations/considerations:
- Still no merge commit support (consistent with drop)
- Conflict resolution falls back to cherry-pick --continue
- Performance impact of repeated commit rewriting not measured
- Part of larger series - depends on earlier sequencer/cache-tree changes

This continues the pattern seen in earlier patches of building Jujutsu-inspired functionality on Git's existing infrastructure while adding thorough test coverage. The implementation appears well-structured and the commit message clearly explains the motivation and behavior.
