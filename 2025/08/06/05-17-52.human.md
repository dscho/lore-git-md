This is a maintainer follow-up in the closed `git mv --after` discussion thread, providing deeper technical context about Git's rename detection philosophy.

Junio C Hamano elaborates on Git's fundamental design choice to perform rename detection heuristically at read-time rather than recording renames explicitly during commit creation. He explains this allows Git to: (1) spend computational effort only when actually needed (during operations like `git blame`), and (2) improve detection algorithms over time without being constrained by historical recording methods.

The email suggests an alternative approach where users could provide supplemental rename hints (perhaps stored as Git notes) to help specific commands like `git blame` when the heuristics fail, while still keeping this metadata separate from core commit objects. This maintains Git's content-oriented model while acknowledging practical needs for manual override capabilities.

As the thread is already definitively closed, this serves as educational material about Git's design principles rather than proposing new directions. The maintainer's technical explanation reinforces why the original `--after` proposal was rejected while showing how similar needs might be addressed within Git's existing framework.
