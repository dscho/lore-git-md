This is a bugfix patch in Patrick Steinhardt's reflog migration series, specifically addressing a race condition in HEAD reflog generation for the files backend. The patch introduces a new `REF_LOG_VIA_SPLIT` flag to help detect when HEAD's target changes during a transaction that would generate a reflog entry.

The core issue stems from how `split_head_update()` currently handles HEAD reflog generation - it reads HEAD at transaction start but doesn't lock it, leading to two possible race conditions where either (1) a needed reflog entry gets skipped or (2) an unnecessary one gets created. The patch mitigates the second case by double-checking HEAD's target after locking and aborting the transaction if a race is detected.

Key technical changes include:
- New `REF_LOG_VIA_SPLIT` flag marking reflog updates created via `split_head_update()`
- Parent-child relationship tracking between updates via `parent_update` pointer
- Race detection by comparing HEAD's current target against the parent reference
- Transaction abortion with "HEAD has been racily updated" error when races occur
- Proper old-OID propagation from parent updates

The solution is somewhat heavy-handed (aborting the whole transaction) but justified given the rarity of the race scenario in practice. The patch acknowledges it doesn't fully solve all possible races (particularly HEAD switching to reference another updated ref) but provides a pragmatic improvement. This builds on earlier work in the series around transaction handling and reflog consistency.
