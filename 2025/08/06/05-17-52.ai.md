This is a technical follow-up from Junio C Hamano in the closed `git mv --after` discussion thread, providing deeper insight into Git's rename detection philosophy while exploring hypothetical implementation boundaries.

The email elaborates on Git's fundamental design choice to perform rename detection heuristically at read-time rather than recording explicit rename operations at write-time. Hamano explains this allows Git to: (1) defer computational costs until needed, (2) improve detection algorithms over time without changing historical data, and (3) handle cases where the original rename context isn't known when files are moved.

While maintaining the rejection of tracking renames in commit objects, Hamano outlines a potential middle ground: allowing users to provide supplemental rename hints (like "line N-M of file G became line L-K of file F") that could be stored externally (e.g. in Git notes) and consulted by commands like `git blame`. This would preserve Git's content-oriented model while giving users a way to improve rename detection accuracy for specific cases.

The email serves as both a philosophical reinforcement of Git's design and a technical exploration of how future tools might work within those constraints. It maintains the thread's educational tone while demonstrating how Git's principles translate into concrete implementation boundaries. The hypothetical note-based approach would require new infrastructure for storing and querying rename hints without modifying core objects.
