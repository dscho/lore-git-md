This is a follow-up discussion in the commit-graph refactoring series about integer type choices, specifically regarding Bloom filter counters.

Oswald Buddenhagen responds to Patrick Steinhardt's defense of using unsigned integers for Bloom filter counts (which can never be negative) by pointing out that unsigned types have their own pitfalls. He references several authoritative sources (Google C++ Style Guide, Critical Escher Tech blog, Sound Software research, and Stack Overflow) that caution against overusing unsigned integers due to potential underflow bugs and other hazards. 

The exchange reveals an interesting philosophical divide in type system usage - while Patrick argues unsigned types better document the non-negative invariant, Oswald counters with real-world experience where this approach led to bugs in his own project (isync). This is a nuanced technical discussion that doesn't block the series (which has broader reviewer approval) but provides useful context about integer type selection tradeoffs that may inform future decisions.
