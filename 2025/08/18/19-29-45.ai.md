This is a feature request proposing to allow nested interactive rebases, specifically to enable modifying earlier commits during an ongoing rebase operation. The author describes a common workflow pain point where they realize they forgot changes after continuing a rebase, and currently having to abort and restart the whole process.

The core proposal suggests modifying `git rebase` to handle nested cases by:
1. Generating a new todo list for the inner rebase and prepending it to the current one
2. Resetting to the new start point while preserving the outer rebase context
3. Limiting this to the merge backend (not the apply backend)

The email includes a proof-of-concept Fish shell implementation that works by:
- Backing up the current rebase state
- Generating a new todo list through a dummy rebase operation
- Merging the new todo list with the existing one
- Handling label conflicts by appending numbers to duplicates
- Continuing the combined rebase operation

Key technical aspects for future reference:
- Focuses on the merge backend (`.git/rebase-merge`)
- Modifies the rebase todo list format
-i/--interactive flag required
- Involves `GIT_SEQUENCE_EDITOR` trickery
- Handles label name collisions
- Uses `git reset --hard` to reposition

The author is gauging interest before potentially implementing this in core Git, noting they could alternatively maintain it as a wrapper script if the feature is unlikely to be accepted upstream. The implementation would need to address edge cases not handled by the prototype (as noted in the script's disclaimer).
