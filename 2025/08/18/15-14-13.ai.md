This is a continuation of the discussion about improving `git stash --keep-index` behavior to better handle unstaged changes during interactive rebase workflows. Phillip Wood responds to Junio Hamano's question about whether the proposed `--unstaged` behavior should be enabled by default rather than requiring a new option.

Wood agrees that automatically applying the new behavior when a stash was created with `--keep-index` would make sense, though notes there's currently no way to detect this after creation. He proposes adding a trailer to the stash commit message to record when `--keep-index` was used, which would allow the stash pop operation to apply only unstaged changes in those cases.

The email continues the technical discussion about implementation details, referencing Wood's earlier script that demonstrated how to safely restore only unstaged changes using a three-way merge with the stash's index state as the base. The script's approach of creating a temporary index file and handling merge conflicts remains relevant to the proposed solution.

This response moves the discussion forward by addressing the maintainer's design philosophy concerns while maintaining backward compatibility. The key technical challenge identified is reliably detecting which stashes were created with `--keep-index`, with the commit message trailer proposal offering a potential solution. The thread remains focused on finding a robust way to support the interactive rebase testing workflow without breaking existing stash usage patterns.
