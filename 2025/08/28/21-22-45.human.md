This is a discussion about the memory limit implementation for `git range-diff` in the ongoing performance/safety patch series. Junio Hamano responds to Elijah Newren's suggestion about error message wording and raises a new point about the interface design.

Junio agrees with Newren's proposed rewording of the memory limit error message from "X bytes available" to "limited to X bytes" to avoid confusion about system memory reporting. This addresses a potential user experience issue where the original phrasing might mislead users into thinking it was reporting their system's free memory rather than the configured limit.

More significantly, Junio questions whether the feature should start as a command-line option only, without a configuration variable. He suggests this would allow gauging real-world usefulness before committing to a permanent configuration interface. This represents a shift from the current approach that includes both command-line and config options in the patch.

The exchange shows maintainers converging on the error message wording while opening a new discussion about the feature's interface design philosophy. The core memory limit functionality itself remains uncontested, but how users interact with it is now under reconsideration. This follows the thread's pattern where implementation details are solid while interface decisions receive careful scrutiny.
