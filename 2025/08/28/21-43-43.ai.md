Technical discussion response in SHA-1/SHA-256 interoperability format debate.

brian m. carlson responds to Eric Wong's SQLite proposal for storing bidirectional hash mappings, providing two key objections. First, they note SQLite's poor performance with Java implementations like JGit, citing this as the original motivation for creating the reftable format instead. Second, they express concerns about SQLite's license stability, drawing parallels to Oracle's controversial changes to Berkeley DB's license and the resulting maintenance burden.

The response maintains carlson's position of evaluating all approaches but firmly rules out SQLite on these grounds. This introduces new constraints to the ongoing format discussion: any solution must not only meet the technical requirements (O(log N) lookups, incremental updates) but also maintain cross-implementation compatibility and avoid potential licensing risks. The exchange highlights how the decision matrix now includes both technical performance characteristics and ecosystem/legal considerations.

Key technical terms referenced include `loose-object-idx` (the current problematic flat file format), reftable (Stolee's proposed alternative), and JGit (the Java implementation affected by SQLite performance). The response does not address the other proposed formats (Hamano's two-file model or Stolee's reftable-like approach) directly, focusing solely on rebutting the SQLite suggestion while implicitly maintaining the need for a custom solution.
