This is a bug report about inconsistent behavior in Git's rebase conflict resolution workflow. Stephen Finucane observes that when resolving conflicts during a rebase, using `git rebase --continue` preserves both authorship metadata and commit message from the original commit, while using `git commit` (followed by `git rebase --continue`) only preserves the commit message. This can silently strip authorship information due to muscle memory from merge workflows.

The email questions whether this is intentional behavior, a technical limitation (like unavailable authorship metadata during commit), or something that could be improved - either by preserving metadata in the commit path or preventing `git commit` usage during rebase conflicts. The issue appears in the rebase state machine where different code paths handle metadata preservation differently between the direct continue operation versus the two-step commit+continue approach.

Key technical details include the different handling of authorship metadata between these paths, the potential for silent metadata loss, and the user experience impact of muscle memory leading to unintended behavior. The question touches on Git's internal state management during rebase operations and whether the current behavior represents a bug or design tradeoff. No specific files or functions are mentioned in the email, but this would involve the rebase machinery's interaction with the commit creation process.
