This is a bug report about inconsistent behavior during rebase conflict resolution. Stephen Finucane observes that when resolving conflicts, using `git rebase --continue` preserves both authorship metadata and commit messages, while using `git commit` followed by `git rebase --continue` only preserves the commit message. This can accidentally strip authorship information while leaving the commit message intact, which could go unnoticed.

The email questions whether this is intentional behavior, a technical limitation (like unavailable authorship metadata during commit), or something that could potentially be fixed. The author notes they encounter this due to muscle memory from merge conflict resolution habits rather than intentional use of the separate commit command.

This appears to be a genuine usability issue that could lead to unintended metadata loss during rebases. The report is clear and well-explained, though it doesn't include reproduction steps or version information. The question seems worth discussing as it affects a common workflow scenario.
