This is a bugfix patch in Patrick Steinhardt's reftable/libgit2 compatibility series, addressing race conditions in the reftable backend's locking behavior. The patch standardizes the use of the `REFTABLE_STACK_NEW_ADDITION_RELOAD` flag across all operations that modify the reftable stack, ensuring consistent handling of the stack state when acquiring locks. Previously, some operations would bail out if they detected concurrent writes during the lock acquisition phase, which was overly conservative since Git already performs necessary reference checks under lock.

The key change is making all stack modification operations (ref renaming, copying, reflog creation/deletion, and expiration) use the reload flag, which causes the stack to be refreshed after lock acquisition rather than failing on stale state. The patch also fixes an ordering issue in reflog expiration where the iterator was created before the lock, which could lead to races.

This change improves the user experience by reducing spurious failures from concurrent operations while maintaining safety through proper locking. The implementation removes one redundant manual stack reload and updates several call sites to use the standardized approach. The patch is part of the larger effort to make reftable robust enough for libgit2 integration, with all test cases passing.
