This thread explores improving `git stash` workflows for testing staged changes during interactive rebases, where the current `--keep-index` behavior can cause conflicts when popping stashes. The original proposal by D. Ben Knoble identified that storing both index and working tree states in the stash leads to these issues, suggesting a new stash format that excludes the index state entirely.

Phillip Wood contributed a shell script demonstrating a technical solution using `git merge-tree` to safely restore only unstaged changes from a `--keep-index` stash. His approach creates a temporary index file to preserve the real index state during conflict resolution, showing promise for evolving into a proper `--unstaged` option for `git stash pop`.

Junio Hamano has now weighed in, questioning whether this behavior should be enabled by default rather than requiring a new option. He suggests the original `--keep-index` design assumed users wouldn't modify working tree files while testing staged changes, implying the current behavior might suffice for that narrower use case. This introduces a philosophical question about whether to expand stash's capabilities or maintain its original focused purpose.

The discussion continues to balance technical feasibility (demonstrated by Wood's script) with design considerations around backward compatibility and user expectations. Key technical elements under discussion include the stash commit structure and the three-way merge approach using `stash_oid^1` and `stash_oid^2` components. The thread remains active with open questions about whether the new behavior should complement or replace `--keep-index`.
