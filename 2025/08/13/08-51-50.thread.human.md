This thread explores a proposed `git stash --only-unstaged` feature to improve commit-splitting workflows during interactive rebases, particularly when testing staged changes while temporarily setting aside unstaged ones. The current `--keep-index` behavior can cause conflicts during pop operations because it preserves working tree state in both stash commits.

Phillip Wood (sequencer/rebase expert) demonstrated the technical feasibility using `git merge-tree` and proposed a backward-compatible solution: adding a trailer (`Stash-created-with: --keep-index`) to stash commit messages. This would enable automatic unstaged-change-only behavior during pop operations while maintaining compatibility with existing stashes. Junio Hamano (maintainer) initially questioned whether the original `--keep-index` behavior might suffice but engaged with Wood's practical workflow arguments.

Ben Knoble (tooling) has been verifying cross-feature compatibility and documentation clarity. In the latest exchange, he highlights a disconnect between the current docs' "edit/build/test" example (which implies working tree modifications) and `--keep-index`'s original assumption that working tree files wouldn't change during testing. Knoble suggests either updating the documentation to clarify expectations or modifying the implementation to match the example's implied behavior.

The technical consensus is coalescing around Wood's trailer-based approach, which handles stash import/export cases well. Open questions remain about edge cases in merge conflict resolution when the trailer is present and whether this solution should eventually replace `--keep-index` entirely. The discussion has progressed from design validation to focusing on precise metadata format and addressing documentation/implementation alignment.
