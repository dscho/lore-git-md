This thread explores a proposed `git stash --only-unstaged` feature to improve commit-splitting workflows during interactive rebases, particularly when testing staged changes while temporarily setting aside unstaged ones. The current `--keep-index` behavior can cause conflicts when popping the stash if working tree files were modified during testing.

Phillip Wood (sequencer/rebase expert) demonstrated a technical solution using `git merge-tree` to preserve the real index state during conflict resolution. Maintainer Junio Hamano initially questioned whether the change was necessary, but discussion has since converged on a backward-compatible approach: adding a trailer (likely `Stash-created-with: --keep-index`) to stash commit messages, enabling automatic unstaged-change-only behavior during pop operations.

Ben Knoble (tooling) identified documentation gaps, noting the existing `--keep-index` example implies working tree modifications without warning about potential conflicts. Wood agrees the docs should be clarified, but the group now faces a choice: either update documentation to explain the current behavior or implement Wood's more sophisticated solution to avoid conflicts entirely. Wood leans toward the latter if user feedback confirms the need, awaiting input from J. Dettweiler who originally raised the workflow pain point.

The proposal has progressed from design validation to implementation specifics, with consensus forming around the trailer mechanism. Remaining questions center on conflict resolution edge cases and whether to align documentation with current behavior or modify the behavior to match user expectations set by the examples. Wood is driving the technical details with Hamano providing high-level guidance, while Knoble ensures documentation and user experience considerations remain in focus.
