This is a discussion thread about the proposed `git stash --only-unstaged` feature, focusing on edge cases and implementation details of the current stash behavior.

Ben Knoble provides a concrete reproduction of the problem the new flag aims to solve, showing how `git stash --keep-index` still causes conflicts when popping stashes during commit-splitting workflows. The test case demonstrates that even with `--keep-index`, the stashed index state can interfere with later operations, contrary to what some users might expect from the documentation.

The analysis reveals that conflicts arise because the stash object contains both working tree and index states, even when using `--keep-index`. Knoble explores workarounds like selective file restoration with `git restore`, but notes these are cumbersome and not well-documented. The message reinforces the need for a cleaner solution that completely separates unstaged changes from index state in stash operations.

This discussion helps validate the original proposal by showing real-world pain points with current stash behavior during interactive rebases. It also surfaces some subtle aspects of how stashes currently work that the new implementation would need to handle carefully. The thread continues to explore the boundaries between the proposed `--only-unstaged` and existing `--keep-index` behaviors.
