This is a discussion about the output ordering behavior in the new `git repo info` command, specifically regarding the `references.format` field implementation.

Lucas is responding to Phillip Wood's concerns about the command's current behavior of sorting output keys lexicographically. Phillip had argued that preserving input order would make the output easier to parse in scripts, while the current sorting adds unnecessary complexity.

Lucas defends the current approach of deduplicating keys (which requires sorting) as being simpler to implement, noting that it also helps avoid repeated "key not found" errors for the same unknown key. He suggests that if users need order preservation, they could request one key at a time like with other Git commands, or accept duplicated keys and errors.

The discussion reveals a tension between implementation simplicity and script usability. While Phillip's position on order preservation was ultimately accepted by Junio (as noted in the thread summary), Lucas here presents the case for the simpler sorted/deduplicated approach, suggesting alternatives like allowing duplicates might be preferable to adding hash table complexity.
