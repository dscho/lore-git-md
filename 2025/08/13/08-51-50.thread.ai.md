git stash --only-unstaged feature proposal to improve commit-splitting workflows during interactive rebases. Author's original motivation: need to test staged changes while temporarily setting aside unstaged changes, with current --keep-index solution still storing index in stash and causing potential conflicts. Proposed --only-unstaged would create stash entries containing only working tree changes, leaving index untouched in both working directory and stash object.

Technical details refined by D. Ben Knoble's analysis: examination of stash tree objects shows conflicts during pop operations actually stem from working tree state (stash@{0}^{tree}) rather than index state (stash@{0}^2^{tree}) as previously assumed. Both commits in current stash format contain the same conflicting changes, making --keep-index insufficient for the use case. Proposed solution would modify stash object format to support entries without any index state, making pop operations safer by avoiding these conflicts entirely.

Junio Hamano's earlier concerns about use case differentiation between --keep-index and --only-unstaged remain open, but Knoble's empirical evidence strengthens case for new flag by showing current alternatives don't fully solve the problem. Core workflow pain point remains interactive rebase testing where users need to temporarily remove working tree changes without disturbing staged state or risking conflicts on restore.

Implementation considerations: must maintain backward compatibility with existing stash operations while adding support for index-less stash entries. Current discussion suggests this is a well-motivated change with clear technical justification from an active contributor familiar with Git internals. Next steps likely involve addressing Junio's remaining questions about edge cases and whether the new behavior should fully replace rather than complement --keep-index in some scenarios.
