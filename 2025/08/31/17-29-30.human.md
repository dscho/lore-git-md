This is a performance optimization discussion regarding the `git describe` command. 

René Scharfe responds to Junio Hamano's "What's cooking" status update about a patch that improves `git describe`'s performance by using khash to track commits in the queue rather than scanning them. While the patch was marked as ready to graduate to 'next', René requests keeping it in 'seen' (the experimental branch) for now. 

The reason given is that Jeff King (Peff) has proposed an alternative approach using oidset instead of khash, which may be superior. René plans to conduct further performance measurements before deciding between the two implementations. This shows careful consideration being given to choosing the optimal data structure for this performance-sensitive code path.

The exchange demonstrates Git maintainers' typical workflow - experimental changes get tested in 'seen', promising ones move to 'next' (the staging branch), and only thoroughly vetted changes reach 'master'. The discussion also highlights how performance optimizations often involve comparing alternative implementations.
