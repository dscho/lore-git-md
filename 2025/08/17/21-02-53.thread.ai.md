[PATCH] Feature request: GUI for interactive history manipulation

R. Diez requests graphical interface for Git history operations including mouse-driven commit manipulation (drag-and-drop reordering, visual squashing, interactive diff inspection), having evaluated 15 existing GUIs as unsuitable. Three approaches emerged: 1) new GUI generating rebase instructions (Junio suggests as GSoC project), 2) Patrick Steinhardt's `git history` CLI backend (9-part series in `builtin/` implementing structured subcommands), and 3) Bernd Petrovitsch's demonstration of existing `git rebase -i` capabilities.

R. Diez's workflow pain points with CLI-based history manipulation include: 1) cognitive overhead of commit position tracking (HEAD~11 syntax), 2) loss of original commit sequences after rebase in git-gui, 3) manual branch management for safe experimentation, and 4) compilation breakage when squashing before verification. The plane ticket analogy illustrates frustration with current CLI workflows.

Junio C Hamano responds to Bernd Petrovitsch's demonstration of `git rebase -i` fixup operations, noting the CLI solution works but doesn't address the GUI accessibility need. This highlights the tension between expert CLI workflows (using `rebase -i`, HEAD~N syntax) and R. Diez's request for more approachable graphical tools, particularly for compilation-fixup cycles that create messy histories.

Ben Knoble provided CLI techniques addressing some pain points: 1) `git reflog <branch>` for recovery, 2) defensive branching workflow (create branch -> rewrite history -> reset if needed), and 3) `commit --fixup/squash` with `rebase --autosquash` for partial automation. These solutions don't eliminate conflict potential or fully bridge the GUI/CLI gap.

Patrick's `git history` implementation (reorder/drop/split subcommands with --before/--after args) remains potential technical foundation, with open questions about: 1) squash subcommand implementation, 2) failure-recovery integration, and 3) making exploratory workflows accessible. The discussion continues evaluating which pain points can be addressed by existing CLI patterns versus requiring new tooling (GUI or enhanced CLI).

Key technical terms for follow-ups: reflog, immutable objects, defensive Git branching, autosquash workflow, upstream vs push references in rebase, HEAD~N syntax, compilation-fixup cycle management. The core tension remains between expert CLI proficiency and making history manipulation approachable for less experienced users.
