This is a design discussion about implementing JSON output for `git log`, part of the broader JSON output effort across Git commands. Junio Hamano responds to Ron Ziroby Romero's questions about implementation approach and flag naming.

Hamano strongly advises against adding a new `--json` flag for `git log`, contrasting it with the `git status --json` case where a new flag was necessary due to lacking format options. For `git log`, he argues the existing `--pretty` mechanism should be used (e.g. `--pretty=json`) since it's already designed for format selection.

On implementation, Hamano suggests avoiding modification of `pretty.c` with JSON-specific conditionals, as its formatting logic (whitespace handling, indentation etc.) is fundamentally at odds with JSON's machine-readable nature. While he doesn't explicitly endorse creating a new `json-log.c`, his critique implies the JSON output may need its own dedicated path rather than piggybacking on pretty-print infrastructure.

The response shows the project's preference for reusing existing mechanisms where possible (`--pretty` vs new flag) while recognizing when architectural separation makes sense (JSON output needing different core logic than human-oriented formatting). This continues the thread's progression from philosophical concerns to concrete implementation guidance.
