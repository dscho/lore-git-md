git mv --after proposal for tracking external renames

Thread identity: Subject proposes adding `--after` flag to `git mv` to handle post-facto file renames, similar to Mercurial's `hg mv --after`. Originating author is FMorschel, a first-time contributor. Thread type is feature proposal.

Core problem: When IDEs or refactoring tools move files outside Git's control, the VCS may not properly track these as renames in history. Current workarounds involve manual `git mv` or relying on Git's rename detection heuristics.

Current status: Initial proposal with no patches yet. Author acknowledges this might duplicate prior discussion and requests guidance.

Technical details: Would modify `builtin/mv.c` to add `--after` flag behavior, changing how index updates are processed when the move has already occurred on filesystem. Needs to handle edge cases like externally moved modified files.

Open questions: Whether this duplicates existing functionality; exact semantics for modified files; whether the change should be in `git mv` or as a separate plumbing command.

Participant positions: Only FMorschel so far, seeking feedback on proposal viability and prior art. No maintainer or regular contributor responses yet.

Related work: Mercurial's `hg mv --after` is cited as prior art. May relate to Git's existing rename detection heuristics and how they cover this case.
