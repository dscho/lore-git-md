git mv --after proposal for tracking external renames

Thread identity: Subject proposes adding `--after` flag to `git mv` to handle post-facto file renames, similar to Mercurial's `hg mv --after`. Originating author is FMorschel, a first-time contributor. Thread type is feature proposal now effectively closed by maintainer input.

Core problem: When IDEs or refactoring tools move files outside Git's control, the VCS may not properly track these as renames in history. Current workarounds involve manual `git mv` or relying on Git's rename detection heuristics.

Current status: Maintainer Junio C Hamano has confirmed the proposal is incompatible with Git's fundamental design. The thread has shifted from feature discussion to documenting Git's rename tracking philosophy. No patches were sent.

Technical details: Would have modified `builtin/mv.c` to add `--after` flag behavior, but maintainer and other contributors have explained Git doesn't record renames in commits - it detects them heuristically when comparing trees. `git mv` is just a convenience wrapper for `git rm` + `git add`. Torvalds' 2005 email establishes this as an intentional architectural choice that won't change.

Open questions: None remaining - the proposal is closed as incompatible with Git's design. Future discussion could explore alternative approaches within Git's existing rename detection model.
