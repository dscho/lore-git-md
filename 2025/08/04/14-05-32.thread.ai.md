git mv --after proposal for tracking external renames

Thread identity: Subject proposed adding `--after`/`--cached` flag to `git mv` to handle post-facto file renames, similar to Mercurial's `hg mv --after`. Originating author was FMorschel, a first-time contributor. Thread type was feature proposal, definitively closed by maintainer input with subsequent emails providing educational context.

Core problem: When external tools (IDEs/refactoring) move files outside Git's control, users want better rename tracking. Current solutions involve manual `git mv` or relying on Git's rename detection heuristics.

Current status: Maintainer Junio C Hamano confirmed the proposal violates Git's fundamental design. Thread concluded with three educational postscripts: (1) Johannes Sixt's terminological note suggesting `--cached` would be more Git-idiomatic than `--after`, (2) Konstantin Khomoutov's citation of Torvalds' 2005 email explaining Git's design philosophy, and (3) FMorschel's closure confirmation accepting the maintainer position while noting personal preference.

Technical details: Would have modified `builtin/mv.c` to add any such flag, but core contributors explained Git doesn't track renames - it detects them heuristically when comparing trees. `git mv` is just a convenience for `git rm` + `git add`. Torvalds' 2005 email establishes this as immutable design, emphasizing Git's content-based rather than file-operation-based approach.

Open questions: None - proposal is closed. Future discussion could only explore approaches fitting Git's existing rename detection model.
