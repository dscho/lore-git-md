git mv --after proposal for tracking external renames

Thread identity: Subject proposes adding `--after` flag to `git mv` to handle post-facto file renames, similar to Mercurial's `hg mv --after`. Originating author is FMorschel, a first-time contributor. Thread type is feature proposal.

Core problem: When IDEs or refactoring tools move files outside Git's control, the VCS may not properly track these as renames in history. Current workarounds involve manual `git mv` or relying on Git's rename detection heuristics.

Current status: Initial proposal with no patches yet. Konstantin Khomoutov has responded with technical analysis challenging the need for the feature given Git's rename detection model.

Technical details: Would modify `builtin/mv.c` to add `--after` flag behavior, but Khomoutov points out Git doesn't record renames in commits - it detects them heuristically when comparing trees. `git mv` is just a convenience wrapper for `git rm` + `git add`, so `--after` wouldn't provide additional tracking capability beyond existing rename detection.

Open questions: Whether this feature is needed at all given Git's rename detection works the same regardless of how files were moved. Need to address Khomoutov's point that IDE/refactoring tool moves don't actually need special handling to preserve history. Original questions about modified file handling remain unresolved.

Participant positions: FMorschel proposed the feature seeking feedback. Khomoutov has raised significant technical objections about the proposal's premise, suggesting it may be solving a non-problem. No maintainer input yet.

Related work: Mercurial's `hg mv --after` is cited as prior art, but Khomoutov notes Git's rename tracking works fundamentally differently. Relates to Git's existing rename detection heuristics which may already cover this case adequately.
