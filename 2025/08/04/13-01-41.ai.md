This is a follow-up discussion about the compiler warning fix for the revert/cherry-pick sequencer code. Jeff King considers an alternative approach to the previously proposed solution for the const sentinel value issue.

The original patch (summarized in the thread context) addressed a clang warning by initializing a const variable used as a sentinel in the sequencer logic. The sentinel's address (not value) indicates option states: &sentinel_value means unset, NULL means disabled, other values mean set. The initial solution chose to initialize the variable to 0 with a comment.

In this follow-up, Jeff King suggests another option not previously considered: removing the "const" qualifier entirely. He notes that while the pointers using this sentinel are "const char *", they could safely point to a non-const variable. This might make the code less mysterious than either the initialization-with-comment approach or the other alternatives previously discussed (using magic number addresses or making the variable static).

The discussion continues to weigh clarity versus technical correctness in this low-level C code pattern used by the revert/cherry-pick machinery. The core issue remains how to properly handle a sentinel value whose address (not content) serves as a marker in the sequencer's option parsing logic.
