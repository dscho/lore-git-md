Technical discussion about wildcard behavior in `git refs list`/`for-each-ref`.

Phillip Wood follows up on an earlier discussion about double-asterisk (`**`) pattern matching behavior in ref listing commands. He notes that currently `**` behaves like `*` unless it appears between slashes, which is somewhat unintuitive given the `WM_PATHNAME` flag being set. While initially agreeing with Junio Hamano's suggestion to make `**` match across hierarchy boundaries, Phillip now expresses reservations about changing existing behavior.

The email clarifies that while the current implementation allows matching subhierarchies through patterns like `refs/heads/m*/**`, it's less convenient than a true recursive wildcard. Phillip mentions the possibility of adding a wildmatch flag to enable more flexible `**` matching (as existed in rsync's original code), but notes this would constitute a behavior change for `for-each-ref`.

This discussion appears to explore edge cases for potential future enhancements, separate from the current `git refs list` implementation which maintains strict compatibility with `for-each-ref` behavior. The thread shows careful consideration of backward compatibility implications when evolving ref listing functionality.
