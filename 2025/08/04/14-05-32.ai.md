Feature proposal for a `git mv --after` flag to handle post-facto file renames.

FMorschel proposes adding a `--after` flag to `git mv` that would allow users to explicitly tell Git about file renames that have already occurred on the filesystem. This is modeled after Mercurial's `hg mv --after` functionality. The primary use case appears to be integration with IDEs and language refactoring tools that perform file moves outside of Git's control - the flag would help ensure Git still tracks these moves correctly in the commit history.

The proposal is straightforward and addresses a real workflow issue where external tools modify the filesystem in ways Git might not automatically detect as renames. The author acknowledges this might be a duplicate request and asks to be pointed to any prior discussion if so. As a first-time contributor, they also politely request guidance on any additional information needed.

From a technical perspective, this would involve modifying the `git-mv` command to accept the new flag and handle the index updates differently when the normal pre-move checks can't be performed. The change would primarily affect `builtin/mv.c` and related rename detection logic. The proposal doesn't include implementation details or discuss potential edge cases (like how to handle modified files that were moved externally), which would likely need to be addressed in any actual patch series.
