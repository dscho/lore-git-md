[PATCH 0/9] commit-graph: remove global state dependencies

Series by Patrick Steinhardt completing the commit-graph subsystem's transition away from global state as part of the broader `the_repository` removal effort and ODB abstraction work. The 9-patch series refactors commit-graph.[ch], builtins, and test helpers to eliminate `the_repository` and `the_hash_algo` dependencies while enabling future pluggable object storage.

Key technical changes:
- Type consistency: converted signed counters to unsigned (bloom filter stats, loop counters, array indices) and changed `struct commit_graph_opts` fields from `int` to `size_t`
- Hash algorithm handling: replaced macros with functions taking explicit `hash_algo` parameters; stored full `hash_algo` pointers; updated all size calculations
- Trace2: added `trace2_data_uintmax()` for unsigned value logging (reviewed by Taylor Blau as straightforward and uncontroversial)
- Parameter cleanup: removed redundant `struct repository*` parameters where `odb_source` provided context
- Verification, progress reporting, and file operations updated to use repository context consistently
- Test helpers updated to match new parameter requirements

Open discussions:
1. Integer type choices (patch 2/9):
   - Oswald Buddenhagen initially questioned using `size_t` for bloom filter counters (semantic appropriateness, size impact, OPT_UNSIGNED compatibility)
   - Patrick Steinhardt defended the change citing existing code patterns and negligible memory impact
   - Junio Hamano now pushes back, arguing:
     * Platform-native integers more appropriate unless specifically dealing with memory sizes
     * Overflow protection needed regardless of type
     * Signed integers can represent uninitialized states (-1)
     * Questions value of -Wsign-compare warnings driving such changes
   - Taylor Blau has weighed in supporting Junio's position:
     * `size_t` primarily for memory-related counts, not general object counting
     * Cites MIDX code using `uint32_t` for non-memory object counts
     * Questions whether "always non-negative" alone justifies type change
     * As original author of counters (commits 312cff5207, 59f0d5073f), sees no need for change
     * Open to discussion if other motivations exist
   - Philosophical divide: Steinhardt follows existing `size_t` counting patterns vs Hamano/Blau advocating semantic-based type selection
   - Unresolved; may require reconsideration of patch 2/9's type changes

Behavior remains unchanged throughout series (confirmed by unmodified test suite). The work achieves two long-term goals: (1) complete removal of direct `the_repository` usage in commit-graph subsystem, and (2) foundational improvements for future pluggable ODB abstraction. The core technical merits of global state removal are not in question - current discussion is specifically about integer semantics in one component (bloom filter counters), with implications for broader type selection patterns in future patches.
