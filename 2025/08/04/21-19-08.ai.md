This is a design discussion about JSON output implementation in Git, specifically regarding `git log --json` vs `git log --pretty=json` and code organization.

Junio Hamano responds to Ron Ziroby Romero's questions about implementing JSON output for `git log`. He strongly advises against using the `--json` flag, arguing that since `git log` already has the `--pretty` format mechanism, adding `--json` would be redundant when `--pretty=json` would suffice. He contrasts this with `git status` which lacks format options and thus may need `--json` as a one-off.

Hamano also weighs in on the implementation approach, suggesting that trying to modify `pretty.c` with JSON-specific conditionals would be problematic since the pretty-printing infrastructure is designed for human-readable output (with whitespace handling, indentation etc.) rather than machine-parseable JSON. This implies support for creating a separate `json-log.c` implementation.

The email continues the thread's progression from philosophical concerns to concrete implementation choices, with Hamano providing clear guidance on both the user interface (favoring `--pretty=json`) and implementation architecture (suggesting a clean break from pretty.c). This positions the discussion for Romero to proceed with a formal proposal incorporating these design decisions.
