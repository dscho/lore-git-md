This is a discussion about wildcard matching behavior in the `git refs list` series. Phillip Wood responds to Junio Hamano's clarification about how ref patterns work in the current implementation, pointing out that the matching rules are not intuitive or consistent. 

Phillip notes that the current wildcard behavior (inherited from `for-each-ref`) makes it impossible to predict whether a pattern will do a prefix match or exact match just by looking at the pattern itself. He highlights a practical problem for scripting use cases where you might want to query a ref's properties - you either need to know the ref exists already (which could be racy) or manually verify the match by including `%(refname)` in the output. 

While the series maintains compatibility with `for-each-ref`'s current behavior, Phillip's comment underscores that this comes with usability tradeoffs. The discussion suggests this might be an area for future improvement, though the current approach prioritizes consistency with existing behavior over enhanced wildcard functionality. This is part of the ongoing refinement of the `git refs list` command as it nears final review.
