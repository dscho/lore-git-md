This thread explored a proposal to add a `--after` flag to `git mv` that would help track file renames made outside of Git (e.g., by an IDE). The discussion quickly revealed this would violate Git's fundamental design philosophy, as explained by maintainer Junio C Hamano and supported by historical context from Linus Torvalds' 2005 email. Git doesn't track renames explicitly - it detects them heuristically when comparing content.

While the proposal was definitively closed, the thread became a rich discussion of Git's design. Johannes Sixt noted that `--cached` would be more Git-idiomatic terminology than `--after`, while Konstantin Khomoutov and Kristoffer Haugsbakk provided important context about Git's content-oriented approach. The original proposer, FMorschel, gracefully accepted the outcome while noting their personal preference.

In a thoughtful follow-up, Junio explored the boundaries of what might be possible within Git's constraints. While reaffirming that commit objects won't record renames, he suggested a hypothetical middle ground: users could provide rename hints (like specific line mappings) that tools like `git blame` might consult from external storage (Git notes). This preserves Git's content model while potentially improving rename detection accuracy for specific cases. The thread now stands as a comprehensive reference on Git's rename philosophy and the careful balance between user needs and architectural principles.
