Behavioral clarification for `git refs list` wildcard matching.

Phillip Wood follows up on earlier discussion about wildcard behavior in the new `git refs list` command (which shares matching logic with `git for-each-ref`). The thread had previously considered changing how double-asterisk (`**`) patterns work, but Phillip now expresses reservations after reviewing the current implementation details.

Key technical points:
- Current behavior silently converts invalid `**` patterns (those not between slashes) to single `*` via wildmatch.c's WM_PATHNAME mode
- This means `refs/heads/m**` currently acts like `refs/heads/m*`, only matching top-level branches starting with 'm'
- Matching subhierarchies requires explicit patterns like `refs/heads/m*/**`

Phillip notes that while changing wildmatch behavior to make `**` work more intuitively (matching across hierarchies) would be possible via a new flag, this would constitute a behavior change for existing `for-each-ref` usage. The email suggests maintaining current behavior for compatibility, leaving potential wildcard enhancements as future work.

This discussion occurs in the context of the nearly-complete `git refs list` series, where wildcard behavior consistency between the new command and `for-each-ref` is important. The thread shows the team carefully considering backward compatibility implications when evolving ref listing functionality.
