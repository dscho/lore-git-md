This is a follow-up discussion in the ongoing string handling refactoring series, specifically addressing edge case behaviors when converting from `strbuf_split*()` to `string_list_split*()`.

Jeff King and Junio Hamano are finalizing details about whitespace trimming behavior in the conversion. The key points resolved in this exchange:

1. **Delimiter handling**: Confirmed that `string_list_split` without NOEMPTY flag matches `strbuf_split`'s behavior of including empty elements when multiple delimiters appear consecutively.

2. **Whitespace trimming**: The original patches used `STRING_LIST_SPLIT_TRIM` which trims both sides, while some original code only right-trimmed. Junio suggests dropping TRIM to match original strictness, but both agree the leniency is likely harmless since:
   - merge-tree docs don't specify strict spacing rules
   - git-notes explicitly specifies single-space separation
   - No real-world cases would likely break from the more permissive handling

3. **API quirks**: Jeff notes surprise at `strbuf_split`'s "horrible gotchas" (leaving delimiters in results, empty element creation), reinforcing the value of the conversion to `string_list`'s more predictable behavior.

The discussion shows maintainer alignment on accepting the slightly more lenient whitespace handling as a reasonable tradeoff for cleaner code, given the lack of strict requirements in the original interfaces. This resolves one of the last open questions in the series.
