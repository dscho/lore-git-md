This thread addresses a bug in Git's zip archive generation where deflating large files could fail with a "deflate error (0)" when `core.bigFileThreshold=1` forces more files through the streaming deflate path. The issue stems from incorrect assumptions in `archive-zip.c` about zlib's behavior - specifically that `git_deflate()` with Z_FINISH would always return Z_STREAM_END in one pass, when zlib's documentation actually requires handling multiple calls when the output buffer is too small.

Justin Tobler proposed a fix that restructures the deflation into a proper do-while loop that continues until Z_STREAM_END is received, while maintaining correct CRC and size accounting. René Scharfe, the original author of this code, has reviewed the patch and confirmed it's a valid fix. René notes they had previously thought making the output buffer twice as big as input would suffice (based on deflateBound() guarantees), but this didn't account for zlib's internal stream state. While suggesting the logic could theoretically be rolled into the first loop, René agrees this would unnecessarily complicate the fix and that Justin's approach is correct.

The patch appears well-justified with clear technical analysis and has now received positive feedback from the original code author. With no objections raised and the core issue validated, this fix seems ready for inclusion. The discussion remains focused on the specific zlib interaction problem without introducing new concerns.
