Bugfix follow-up in blobless clone fetch issue. Justin Su identifies that the previously reported fetch failures in blobless clones (`--filter=blob:none`) only occur when `transfer.fsckObjects` or `fetch.fsckObjects` is enabled. This explains why Jeff King couldn't reproduce the issue initially - the problem manifests specifically when object verification is turned on during fetches to newly added remotes.

The key finding narrows down the reproduction case: running `git -c fetch.fsckObjects=true fetch upstream` in a blobless clone should reliably trigger the "fatal: did not receive expected object" error. This suggests the fsck verification is failing when checking objects transferred from the new remote, likely due to some mismatch between the filtered clone's object expectations and what the server provides when fsck is active.

The thread continues to investigate an edge case in partial clone behavior, now with the important additional constraint that it only occurs with object verification enabled. This makes the issue more serious as it affects users who have fsck enabled for security/safety reasons, while being invisible to those who don't. The next steps would involve understanding why fsck fails in this specific filtered clone scenario.
