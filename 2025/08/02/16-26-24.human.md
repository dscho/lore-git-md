This is a meta-discussion about Git's CodingGuidelines document, specifically how to handle existing violations when updating the guidelines. The email comes from Junio Hamano in response to Christian Couder's attempt to clarify wording around `_release()`/`_clear()` function conventions.

Junio provides important context about the nature of CodingGuidelines - they are aspirational standards that accumulated organically over Git's early years, not strict rules that perfectly describe the existing codebase. He notes that while violations exist in the code, they should not be used as justification for new violations, and that fixing old violations is only worthwhile when touching related code anyway.

The core suggestion is to focus documentation efforts on clarifying this aspirational nature in the document's preamble, rather than trying to perfect individual guideline items. This would help new contributors understand that existing violations are tolerated exceptions, not precedents to follow.

This email represents a philosophical clarification rather than a technical one, coming from Git's maintainer to guide how the project thinks about coding standards. It suggests the `_release`/`_clear` discussion might be better addressed by framing the guidelines' intent more clearly rather than debating individual function naming patterns.
