Bugfix for fsck verification in blobless clones, continuing the thread about fetch failures with fsck enabled.

Jeff King provides a concrete reproduction case and confirms his proposed fix works for the issue where blobless clones fail fetches when fsckObjects is enabled. The minimal test case demonstrates how a filtered clone lacking an old blob (but having a newer version) fails when fetching a reference that points to the old blob, even though this is expected behavior for a partial clone.

The key technical detail is that the fix marks promisor objects as "checked" when verification fails due to their intentional absence in a partial clone, preventing fsck from treating them as corruption. The reproduction script is particularly valuable as it isolates the issue from external repositories and shows the problematic sequence: creating a server with two versions of a file, cloning it with blob filtering, then fetching from a fork that references the older blob.

This moves the discussion forward by providing both a working solution and a clear test case, though performance concerns about the `is_promisor_object()` check remain open. The email implicitly invites review from Jonathan Tan (original author of related code) while demonstrating the fix's effectiveness. The reproduction case also helps verify whether similar issues might affect other filter types beyond blob:none.
