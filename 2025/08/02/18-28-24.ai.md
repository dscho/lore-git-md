This is a follow-up in the blobless clone fetch failure thread, providing a key discovery about the reproduction conditions. Justin Su identifies that having `transfer.fsckObjects=true` in the global config appears to trigger the fetch failure in blobless clones when adding new remotes. This explains the earlier divergence in reproduction results between the original reporter and Jeff King.

The email suggests modifying the reproduction steps to explicitly set `fetch.fsckObjects=true` when fetching from the new remote, which should make the failure consistently reproducible. This narrows down the problem to an interaction between object verification during fetch and blobless clone behavior, particularly when deltas reference missing base objects.

The discovery points to fsck operations as a contributing factor to the "did not receive expected object" errors, though the root cause likely still involves how the server generates deltas for filtered clones. This new information provides a more reliable way to reproduce the issue for debugging purposes, moving the thread closer to identifying whether this represents a protocol violation or an edge case in fsck behavior with partial clones.
