This is a technical discussion about the ongoing investigation into spurious "lock file exists" errors during fetch operations in bare repositories. Patrick Steinhardt responds to Jeff King's analysis of the issue, which involves potential case-sensitivity conflicts on macOS's case-insensitive filesystem when mirroring remote refs.

Patrick confirms the case collision scenario is plausible and adds that the new batched` mode in git-fetch(1) might be exacerbating the issue. Unlike the previous one-by-one ref updates (which could result in inconsistent state but complete the operation), batched transactions now fail entirely when attempting to lock what the filesystem considers the same ref multiple times due to case variations.

Key technical points raised:
- Suggests the batched ref transaction behavior (introduced between 2.39.5 and 2.51.0) may be the root cause
- Questions what happened in previous versions with case-colliding refs (possibly inconsistent state that went undetected)
- Proposes detecting and handling case collisions more gracefully by ejecting problematic refs from the transaction while continuing with others

The discussion remains focused on determining whether this is a regression in the ref transaction logic versus a pre-existing case-sensitivity issue that's now being properly caught. The reftable backend remains a viable workaround since it avoids filesystem-based ref storage entirely.
