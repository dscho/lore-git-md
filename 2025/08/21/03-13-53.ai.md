This is a bug report identifying a regression in `git subtree split` functionality introduced in Git v2.44. The issue occurs when splitting a subtree that contains squashed subtree merges, where the resulting split history becomes incomplete compared to previous Git versions.

The reporter, Colin Stagner, provides a detailed minimal working example demonstrating the problem manifests when using `git subtree add --squash` followed by `git subtree split`. The key observation is that commits containing squashed subtree merges (which lack the "git-subtree-mainline:" marker) are being incorrectly filtered out by `should_ignore_subtree_split_commit()`, causing parts of the history (specifically nested subtree content) to be omitted from the split result.

The regression appears to stem from commit 98ba49ccc247, part of a larger subtree-related patch series. The reporter has verified the behavior differs between v2.43 (correct) and v2.44 (incorrect), with the latter missing the `deeper/` directory contents in the split output. The issue specifically affects the interaction between squashed subtree merges and the split operation's commit filtering logic.

This appears to be a legitimate regression report with clear reproduction steps and analysis pointing to the likely problematic commit. The impact is limited to users performing subtree splits on repositories containing squashed subtree merges, but for those cases it results in incomplete history being generated. The technical details provided would help maintainers quickly verify and potentially fix the issue.
