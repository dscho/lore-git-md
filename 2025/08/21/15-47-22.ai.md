Junio Hamano weighs in on the ongoing discussion about case collision detection in batched ref transactions, supporting immediate adoption of the reftable backend rather than adding special-case collision handling code. 

The email is a brief reply to Jeff King's suggestion that waiting for Git 3.0 might allow avoiding additional collision detection code. Hamano counters that reftable is already production-ready and could be recommended to users immediately, without waiting for a major version bump. This positions reftable not just as a long-term solution but as a viable near-term workaround for the case collision issues being discussed.

The response suggests the Git maintainer sees reftable as sufficiently stable, which could influence the direction of the thread away from Patrick Steinhardt's proposed case collision detection changes. The key technical point is that reftable avoids the filesystem-level case collision problems entirely by using a different storage mechanism that doesn't rely on individual lock files for each reference.

This moves the discussion toward considering whether to prioritize documentation/education about reftable adoption versus implementing transitional code changes in the files backend. The maintainer's stance implies confidence in reftable's readiness, which may shift the focus toward migration strategies rather than temporary fixes for the files backend.
