This is a discussion thread about the proposed `git-history` command series, specifically addressing its relationship to existing rebase and cherry-pick functionality.

Sergey Organov raises an interesting point about the potential overlap between the new `git-history` command and `git rebase`. He notes that while `git rebase` can move history to a new base ("this" to "there"), it lacks the inverse operation of bringing history into the current branch ("that" to "here"), which would be similar to cherry-pick but more powerful. He questions whether this functionality should be added to `git rebase` (perhaps as `--pick`) or incorporated into the new `git-history` command.

The email builds on Junio Hamano's earlier comments about the design of `git-history`, particularly around notes handling and linear history limitations. Organov's contribution focuses on the broader workflow implications, suggesting the new command might either duplicate or eventually subsume parts of `git rebase`.

This discussion highlights an important design consideration for the `git-history` series - how it should complement versus replace existing Git commands, and whether it might become a more general framework for history manipulation operations. The thread shows the community is thinking carefully about the command's scope and long-term role in the Git ecosystem.
