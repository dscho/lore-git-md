This is a discussion thread about the proposed `git-history` command, specifically around its relationship with `git rebase` and cherry-pick functionality. Sergey Organov raises a point about the limitations of `git rebase` and how the new command might address them.

The email suggests that `git rebase` lacks the ability to specify both source and destination histories (akin to cherry-pick's ability to copy commits to another branch), and questions whether this functionality should be part of the new `git-history` command. Organov speculates whether this might lead to `git-history` subsuming much of `git rebase`'s functionality, or if Git might eventually refactor rebase to use the new git-history infrastructure.

This discussion touches on several key aspects of the ongoing `git-history` proposal:
- The distinction between history editing (rebase-style) and commit copying (cherry-pick-style) operations
- Potential overlap between the new command and existing rebase functionality
- The question of whether `git-history` should grow to include more rebase-like features
- The architectural implications for Git's command structure if `git-history` becomes a more general history manipulation tool

The email doesn't propose specific code changes but rather raises design questions that would need to be addressed as the `git-history` feature evolves. It suggests that the project may need to consider how these different history manipulation tools (rebase, cherry-pick, and the proposed history command) should relate to each other in the long term.
