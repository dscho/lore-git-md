This is a contributor guidance email from Junio Hamano regarding patch submission practices, specifically about how to properly document prerequisite patches in a patch series.

Junio responds to Meet Soni's patch series introducing the new `git refs exists` command (part of GSoC work) by pointing out an issue with how the prerequisite patches are listed. Rather than including numerous prerequisite-patch-id lines that make it difficult for reviewers to recreate the development environment, Junio suggests a more standard approach: clearly stating which commit from mainline Git the work is based on, plus any necessary topic branches that need to be merged.

He provides a concrete example from Patrick Steinhardt's earlier work as a model, emphasizing that this approach makes it easier for reviewers to test the changes. The key points are to (1) base work on a clear mainline commit, (2) minimize the number of additional topic branches needed, and (3) present this information concisely rather than with raw patch IDs.

This is typical maintainer guidance about submission hygiene rather than technical feedback on the patch content itself. The email doesn't comment on the merits of the `refs exists` feature but focuses on improving the patch submission process. It's useful advice for any contributor, especially those new to the Git mailing list workflow.
