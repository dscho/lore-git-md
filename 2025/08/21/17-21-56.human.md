This is a discussion about the design boundaries between `git-history`, `git rebase`, and `git cherry-pick` in Patrick Steinhardt's RFC series for a new history editing command.

Ben Knoble responds to Sergey Organov's suggestion that `git rebase` lacks functionality equivalent to cherry-picking ranges, pointing out that `git rebase --onto` already provides similar capabilities. Knoble playfully inverts Organov's framing, suggesting that if anything, rebase duplicates cherry-pick functionality rather than the reverse.

The exchange highlights ongoing questions about how the proposed `git-history` command should relate to existing Git commands. Organov had suggested rebase should subsume cherry-pick-like functionality, while Knoble's response indicates the existing rebase infrastructure may already cover this ground. This touches on core architectural questions raised in the RFC about whether `git-history` should eventually replace parts of rebase/cherry-pick or coexist with distinct boundaries.

The discussion remains conceptual rather than implementation-focused, with no new technical details about the `git-history` series itself. It represents the kind of high-level design debate the RFC was intended to provoke about Git's history manipulation tools.
