This is a design discussion in the ongoing RFC thread about the proposed `git-history` command, specifically debating the boundaries with existing `git rebase` and `git cherry-pick` functionality.

Sergey Organov continues the architectural discussion with Ben Knoble about whether `git-history` should subsume parts of rebase functionality. The key points are:

1. Organov argues that `git rebase` lacks the ability to rebase "that" history onto "here" while preserving the original history (unlike cherry-pick which preserves the source). He suggests this would eliminate the need for `git cherry-pick <range>`.

2. Knoble counters that `git rebase --onto=<here> <that-upstream> <that>` already provides this functionality, though Organov notes this modifies `<that>` rather than preserving it.

3. Organov makes a broader argument that rebase has superior features (interactive mode, exec, merge handling) and that cherry-pick should be plumbing while rebase handles user needs. He suggests cherry-pick's range support was a historical mistake and rebase should have gained pick functionality instead.

The discussion highlights the ongoing tension in the thread about where to draw boundaries between these history manipulation commands. Organov's position suggests a more aggressive consolidation into rebase-like functionality, while the RFC currently positions `git-history` as a separate command building on cherry-pick infrastructure.

This exchange doesn't introduce new technical details about the `git-history` implementation but continues the meta-discussion about Git's command architecture that will inform how the RFC series evolves. The thread shows active debate about whether the new command should complement or subsume existing functionality.
