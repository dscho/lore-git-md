This is a bug report identifying a regression in `git subtree split` functionality introduced in Git v2.44. The issue occurs when splitting a directory that contains squashed subtree merges in its history.

Colin Stagner demonstrates that after commit 98ba49ccc247, `git subtree split -P sub` produces incomplete history when the directory contains squashed subtree merges. The test case shows that files from nested subtrees (like `deeper/two_deep`) are missing from the split output, while they were correctly included in v2.43 and earlier.

The problem appears to stem from `should_ignore_subtree_split_commit()` incorrectly filtering out commits that should be preserved, particularly those created with `--squash` which lack the "git-subtree-mainline:" marker the function checks for. The report includes a minimal working example that clearly reproduces the issue and shows the difference in behavior between versions.

This looks like a legitimate regression that could affect users who rely on subtree splitting with squashed merges. The report is well-documented with clear reproduction steps and version comparisons, making it easy to verify. The issue appears to require a fix to the commit filtering logic in the subtree split implementation.
