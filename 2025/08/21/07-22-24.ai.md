This is the third patch in Jeff King's series fixing color handling regressions in Git's interactive patch mode (`-p`/`--patch`). The patch addresses a subtle issue where commands like `checkout -p` weren't properly falling back to `color.ui` settings when `color.diff` wasn't explicitly configured.

The core problem stems from the 2021 Perl-to-C conversion, where the Perl version used `git config --get-colorbool` which automatically handled fallbacks, but the C version relies on `want_color()` which depends on the main command having loaded color config. The patch fixes this by making `add-interactive.c` manually check `color.ui` when other color configs aren't set, rather than relying on the parent command's config parsing.

Key technical details:
- New logic in `check_color_config()` explicitly checks `color.ui` when primary color settings (`color.diff`, `color.interactive`) are unset
- Avoids the problematic approach of modifying `want_color()` which could affect plumbing commands
- Adds test coverage verifying `color.ui` fallback works across all interactive commands (`add`, `checkout`, `commit`, `reset`, `restore`, `stash`)
- Maintains the existing behavior where plumbing commands can avoid porcelain config by not calling `git_color_config()`

The solution is particularly notable for its surgical approach - fixing the issue at the interactive code level rather than requiring each command to handle color config properly. The patch includes a comprehensive test that verifies the fix works across all affected commands while maintaining the expected behavior when `color.ui=false` is set.

This completes one of the core issues identified in the series, ensuring consistent color behavior regardless of which command invokes the interactive mode. The implementation carefully balances correctness with maintaining Git's historical approach to color handling in plumbing versus porcelain commands.
