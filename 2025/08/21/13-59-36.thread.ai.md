Thread identity: Discussion about compatibility breakage in Git 2.51.0's `git whatchanged` deprecation warning when used by Jenkins GitSCM plugin.

Core problem: The newly required `--i-still-use-this` flag for the deprecated `git whatchanged` command breaks Jenkins' GitSCM plugin, which calls this command internally without ability to modify the invocation. While the Jenkins team has been notified, the author proposes adding a Git configuration option (suggesting names like `core.ignoreDeprecations` or `core.iReallyMeanIt`) to bypass the CLI requirement.

Current status: No patches yet proposed, just discussion of potential solutions. The deprecation warning in Git 2.51.0 remains active by default.

Key technical details: The change affects any tool that calls `git whatchanged` without the new required flag. The proposed config option would suppress the warning system-wide rather than per-command.

Open questions: Whether to implement a config-based override, what naming to use if so, and how to balance deprecation enforcement with real-world compatibility needs. The plugin maintainers' response timeline is unknown.

Participant positions: Single reporter so far highlighting the Jenkins compatibility issue and proposing config-based solution. No other feedback yet on the proposal.

Related work: Git's ongoing effort to clean up deprecated commands and interfaces, with `git whatchanged` being a long-standing candidate for removal (documented as deprecated since Git 1.5.5 in 2008).
