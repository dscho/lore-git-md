This is a bugfix patch in Patrick Steinhardt's reflog migration infrastructure series, specifically addressing race conditions in HEAD reflog generation. The patch introduces a new `REF_LOG_VIA_SPLIT` flag to handle cases where HEAD's target changes between the initial check and lock acquisition during reflog updates.

The core issue involves two race scenarios when updating references that HEAD points to: (1) missing a needed reflog entry if HEAD changes to point to an already-processed reference, and (2) incorrectly writing a reflog entry if HEAD stops pointing to a processed reference. The solution adds post-lock verification of HEAD's target and aborts the transaction if a race is detected, though it acknowledges this doesn't fully solve the first race scenario.

Key technical changes include:
- New `REF_LOG_VIA_SPLIT` flag marking split updates
- Parent-child linkage between updates via parent_update pointer
- Post-lock verification of HEAD's target against the parent reference
- Propagation of old OID from parent update when available
- Transaction abortion on detected races with "HEAD has been racily updated" error

The patch acknowledges this is a heavy-handed solution but justifies it by noting the rarity of these race conditions in practice. The implementation specifically modifies `split_head_update()` and `lock_ref_for_update()` in refs/files-backend.c, adding 38 lines while modifying 2. This builds on previous work in the series around reflog transaction handling and completes the race mitigation strategy discussed with Jeff King earlier in the thread.
