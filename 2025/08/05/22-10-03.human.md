Performance investigation update for `git cat-file --batch-command` slowdown.

Rob Browning follows up on his initial report about poor performance regression in `git cat-file --batch-command`'s `info` subcommand when processing many object requests. The original issue showed sustained high disk reads (300-400MB/s) with very low throughput (32 hashes/sec cold) in a large repository (~125GB, 3M objects).

New testing suggests the problem may be hardware-specific. When testing with an internal NVMe drive (rather than the original external USB-connected SSD), performance improves significantly - starting slow but reaching 37k hashes/sec after warm-up. This suggests the extreme slowdown may be related to the external storage configuration rather than a fundamental Git issue.

While still interested in understanding the root cause, Browning indicates he'll likely work around the issue by replacing the problematic hardware rather than pursuing a Git-side fix. This update provides important context for the original report, showing the performance characteristics can vary dramatically based on storage hardware. The thread remains open for further investigation, but the urgency appears reduced given the hardware workaround.
