Here's a human-readable summary of the thread so far:

Rob Browning has reported a significant performance issue with `git cat-file --batch-command` when used to process object information requests in large repositories. In a test repository of about 125GB with 3 million objects, the command only processes 32 hashes per second with a cold cache, while maintaining high disk read rates (300-400MB/s) that don't improve across runs. This performance is dramatically worse than a custom Python implementation that achieves 1,500 hashes/sec cold and 9,000 hashes/sec warm.

Interestingly, `git cat-file` itself performs much better (53,000 hashes/sec) after the cache is warmed by the custom tool, suggesting the issue lies in how Git manages its working set during batch operations, likely related to mmap usage. The report specifically focuses on the `info` subcommand of `--batch-command`, which retrieves basic object metadata without content.

Rob has provided clear reproduction steps and comparative benchmarks, making this a concrete performance regression report. While offering to assist with testing or potential fixes, they note they can work around the issue in their bup backup tool if this isn't considered a priority for the Git project. The report presents a clear case for optimization in Git's batch object metadata handling.
