Maintainer follow-up on git mv --after/cached proposal

This is a maintainer response in the closed thread about adding rename-tracking functionality to `git mv`. Junio Hamano responds to Johannes Sixt's terminological suggestion that `--cached` would be more Git-idiomatic than `--after` if such a feature were implemented.

The email explores two possible interpretations of the original request: (1) a "smart" mode that would automatically detect and pair moved files by comparing working tree and index states, which Git currently lacks infrastructure for, and (2) a simpler mode that would just record explicit rename pairs provided by the user. The latter functionality essentially exists today through manual `git mv A B` sequence.

Hamano notes that while automatic detection of renames (the first interpretation) isn't fundamentally impossible, it would require new logic to match missing and untracked paths. He speculates this could range from a simple-but-imprecise implementation (effectively `git add .`) to more sophisticated path analysis, though none of this currently in Git's codebase.

The response maintains the thread's conclusion that Git's design philosophy rejects explicit rename tracking, while providing technical clarification about what hypothetical implementations might entail. This serves as an educational coda to the discussion rather than reopening the debate.
