Feature implementation with documentation feedback for the `git-history split` subcommand. This is patch 11/11 in Patrick Steinhardt's RFC series introducing a new `git-history` command inspired by Jujutsu's history editing capabilities.

Jean-Noël Avila provides detailed documentation review for the newly introduced `split` subcommand, focusing on formatting consistency and clarity. Key points addressed:

1. **Synopsis formatting**: Notes the `--message` option should be explicitly shown since it's specific to `split`, and suggests simplifying the general synopsis since other subcommands currently have no options.

2. **Parameter naming**: Points out inconsistency between `<revision>` and `<commit>` usage in the documentation, recommending standardization.

3. **Option ordering**: Questions whether the documented option order matches Git's conventions, particularly for `--message` appearing after the commit parameter.

4. **Pathspec documentation**: Suggests improving the pathspec reference by linking to gitglossary(7) rather than just mentioning it.

5. **Message handling**: Implicitly notes the documentation should clarify that the editor is only launched when `--message` isn't provided.

6. **Example formatting**: While not proposing changes to the example content, the review implies the existing example properly demonstrates the split workflow.

The feedback is entirely documentation-focused, not touching the implementation code shown in the diff. It aligns with Git's documentation standards while accepting the core functionality as proposed. This continues the pattern seen in earlier patches where documentation polish is being systematically addressed across all subcommands.

Technical context from the implementation (visible in the diff but not commented on):
- The split operation uses interactive hunk selection similar to `add -p`
- Creates a new commit from selected hunks, making it parent of the original
- Preserves authorship from the original commit
- Forbids creating empty commits (must select some but not all hunks)
- Supports pathspec limiting of which changes can be split out

This review represents the final documentation polish for the initial RFC series, following earlier rounds of feedback on the `drop` and `reorder` subcommands. The thread shows maintainer approval for the overall approach while incrementally refining the user-facing documentation.
