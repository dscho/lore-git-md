Platform compatibility improvement with alternative approach to signal handling.

Johannes Sixt responds to Carlo Marcelo Arenas Belón's two-patch series that replaced `setitimer()` with `alarm()` for progress meter updates. While acknowledging the series' technical merits, Sixt proposes a more radical solution: completely eliminating signal-based progress updates in favor of direct time checking. The prototype implementation removes all SIGALRM/alarm/setitimer infrastructure and instead tracks elapsed time using `getnanotime()`, checking for updates every 1/8th second. This approach would:
- Remove all signal handling code from progress.c
- Replace the volatile `progress_update` flag with direct time checks
- Modify the test infrastructure to work with the new timing approach
- Maintain the same user-visible progress reporting behavior

The changes are contained to progress.c and its header, plus minor test helper adjustments. Key technical changes include:
- New `last_update` timestamp in `struct progress`
- `check_update_delay_expired()` helper replacing signal checks
- Modified `display()` and `display_progress()` signatures
- Removal of all signal setup/teardown functions
- Test updates to use progress-specific force updates

This represents a significant architectural shift from the incremental approach in the original series, potentially offering simpler code at the cost of more frequent time checks. The proposal invites discussion about whether to:
1. Proceed with the original signal-based approach
2. Adopt this timer-based alternative
3. Consider hybrid approaches

Reviewers would need to evaluate:
- Performance impact of frequent time checks vs signal overhead
- Behavior on systems with coarse timer resolution
- Interaction with existing throughput calculations
- Potential regressions in progress update frequency
