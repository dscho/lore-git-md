This is a proposal for an alternative approach to the ongoing progress meter signal handling changes. Johannes Sixt suggests eliminating signal-based progress updates entirely in favor of direct time checks in the progress code.

The email presents a prototype that replaces the SIGALRM/alarm/setitimer mechanism with simple wall-clock timing checks in `progress.c`. Instead of using signals to trigger updates, the progress code now checks elapsed time directly via `getnanotime()`, updating roughly every 1/8th second. The changes remove all signal handling infrastructure while maintaining the same user-visible behavior.

Key aspects of the proposal:
- Removes all signal-related code (sigaction, setitimer, alarm)
- Replaces with periodic checks using `getnanotime()`
- Updates progress display when elapsed time exceeds threshold
- Maintains same test interface but updates it to work with new approach
- Shows working prototype with `git clone` on Linux

This represents a more fundamental change than the current series (which just switches from setitimer to alarm), potentially simplifying the code further. The approach appears promising but would need validation on various platforms and workloads. The email invites feedback on whether this direction seems worthwhile compared to the incremental signal handler improvements in the current patches.
