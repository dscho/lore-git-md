Bugfix and signal handling improvement for progress meter shutdown safety.

This second patch in the series addresses the race condition identified in the `setitimer()` to `alarm()` conversion for progress reporting. The key change introduces a three-state shutdown protocol for the SIGALRM handler to safely terminate progress updates without risking unsafe signal handler execution during process termination.

The patch modifies the `progress_update` flag from a boolean to a tri-state value with clear semantics: 0 (no progress), 1 (potential update needed), and 2 (shutdown in progress). The signal handler now checks this state before rearming the timer, while `clear_progress_signal()` properly sequences the state transition to 2 (shutdown) before disabling the alarm. This ensures no timer rearm can occur during shutdown.

All progress display logic is updated to check only the least significant bit (state 1) when determining if updates are needed, maintaining functionality while adding the shutdown safety. The changes are contained to `progress.c` and focus narrowly on the shutdown sequence without altering the core progress reporting behavior.

Technical details:
- Introduces tri-state `progress_update` (0/1/2) replacing boolean flag
- Modifies `progress_interval()` handler to respect shutdown state
- Updates all progress checks to use `(progress_update & 1)`
- Preserves existing display behavior while adding safe shutdown
- Maintains compatibility with throughput display updates

This completes the series' goal of replacing `setitimer()` with `alarm()` while addressing the critical shutdown race condition. The implementation appears robust and well-contained, with all progress-related code properly updated to handle the new state transitions. Reviewers will want to verify the atomicity of the state changes and confirm no edge cases remain in the shutdown sequence.
