Subject: Replacing setitimer() with alarm() for progress meter signaling

This thread discusses modernizing Git's progress meter signal handling, originally using POSIX.1-2017 obsolescent setitimer(). Carlo Marcelo Arenas Belón's two-patch series replaced setitimer() with alarm(), simplifying code while maintaining functionality through a tri-state shutdown protocol. The changes removed platform-specific code and improved Windows compatibility.

Johannes Sixt proposes an alternative approach eliminating signal-based updates entirely in favor of direct time checking via getnanotime(). This would remove all signal handling infrastructure, replacing it with periodic time checks (every 1/8th second) and timestamp tracking in struct progress. The proposal maintains identical user-visible behavior while potentially simplifying the codebase, though requiring evaluation of:
- Performance tradeoffs between time check frequency and signal overhead
- Behavior on systems with coarse timer resolution
- Impact on throughput calculations
- Progress update frequency consistency

Key technical details:
- Original series: alarm() replacement with tri-state progress_update (0=no progress, 1=update, 2=shutdown)
- New proposal: last_update timestamp and check_update_delay_expired() helper
- Both approaches maintain same progress display behavior
- Signal-based vs timer-based architectural tradeoffs

Open questions center on which approach to adopt, with options including:
1. Original signal-based alarm() implementation
2. Timer-based alternative
3. Potential hybrid solutions

The thread now requires evaluation of these competing approaches' technical merits and platform compatibility implications before proceeding.
