This thread explores modernizing Git's progress meter signal handling, originally proposing to replace the obsolescent setitimer() with alarm(). Johannes Sixt has since introduced a more comprehensive signal-free approach using getnanotime() checks, which has gained traction after addressing Junio Hamano's initial performance concerns. The solution promises better Windows compatibility by eliminating signal dependencies entirely.

Sixt's latest contribution fixes a long-standing bug in the progress delay functionality, where the configured delay (GIT_PROGRESS_DELAY) was incorrectly capped at 1 second due to flag handling issues. The minimal patch corrects this while updating the default delay from 2 to 1 second to match the de facto behavior users have experienced. Though this change is independent of the broader signal-handling discussion, Sixt notes it could serve as a hook point for Carlo Arenas Belón's original alarm() proposal if needed.

The thread has effectively settled on Sixt's signal-free approach, with only performance measurements and minor implementation refinements remaining before potential submission. The progress meter will now properly respect configured delays while the underlying architecture moves toward a more portable solution that eliminates signal handling entirely.
