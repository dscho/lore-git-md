Feature implementation with behavioral concern. This is a review comment on patch 3/5 of the RFC series introducing `git refs list` as a wrapper around `git for-each-ref`. Phillip Wood raises concerns about inheriting what they consider confusing pattern-matching behavior from `for-each-ref` into the new command.

The email focuses on the pattern matching semantics where `refs/h*` returns nothing while `refs/heads/m*` works, and `refs/heads` works while `refs/heads*` fails. Phillip suggests the new command should either always require explicit wildcards or consistently do prefix matching when no wildcard is present, rather than inheriting the current inconsistent behavior.

This feedback comes late in the review cycle (v4) where the technical implementation is otherwise solid, with shared core logic between commands already established. The concern is purely about user experience rather than implementation correctness. The thread context shows this is one of the final pieces of feedback before potential merging, with previous rounds having addressed architectural and documentation issues.

Key technical elements referenced include the `for_each_ref_core()` helper function and `COMMON_USAGE_FOR_EACH_REF` macro that enable the shared implementation between `for-each-ref` and the new `refs list` command. The pattern matching behavior in question would be inherited through this shared components.
