This is a review comment on patch 3/5 of the "git refs list" feature series, which introduces a new subcommand as a thin wrapper around `git for-each-ref`. Phillip Wood raises concerns about inheriting what they see as confusing behavior from `for-each-ref` regarding reference pattern matching.

The review focuses on the pattern matching behavior where:
- `refs/h*` matches nothing while `refs/heads/m*` works
- `refs/heads` shows all branches but `refs/heads*` shows nothing

Phillip suggests the new command might benefit from more intuitive pattern matching rules, either requiring explicit wildcards or consistently doing prefix matches. This is presented as feedback rather than a blocking concern, coming late in a series that has otherwise addressed all major architectural issues and is nearing merge readiness.

The patch itself follows the established pattern of the series, sharing core logic via the `for_each_ref_core()` helper and documentation via included AsciiDoc fragments. The review doesn't challenge the technical implementation but questions whether this is the right moment to reconsider some user-facing behavior before locking it into a new command.
