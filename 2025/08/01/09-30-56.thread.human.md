The thread addresses a bug where blobless clones (created with `--filter=blob:none`) fail when fetching from new remotes if `transfer.fsckObjects` or `fetch.fsckObjects` is enabled. The failure occurs because fsck incorrectly treats intentionally missing blobs as corruption rather than legitimate omissions in a partial clone.

Jeff King has now provided both a concrete reproduction case and a working fix. His test demonstrates how a filtered clone (lacking an old blob but having a newer version) fails when fetching a reference to the old blob. The solution marks promisor objects as "checked" when verification fails due to their intentional absence, preventing fsck from flagging them as corrupt. While this resolves the immediate issue, questions remain about the performance impact of additional promisor checks.

The discussion has progressed from problem identification to solution validation, with Jeff's reproduction case being particularly valuable as it isolates the issue from external repositories. The fix appears effective for blob filtering, though it remains to be seen whether similar issues affect other filter types.
