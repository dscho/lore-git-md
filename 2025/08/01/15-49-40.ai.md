This is a discussion about pattern matching behavior in the new `git refs list` command, which inherits its ref selection logic from `git for-each-ref`. Phillip Wood and Junio Hamano are debating the current wildcard semantics, with Phillip finding the hierarchical matching behavior confusing while Junio argues it's useful for practical workflows.

The current behavior treats single asterisks (`*`) as matching within a single hierarchy level (e.g., `refs/heads/m*` matches `morning` but not `mid/night`). Junio proposes keeping this behavior while potentially introducing double-asterisk (`**`) syntax for cross-hierarchy matching, which would address Phillip's concern about unintuitive results while preserving the existing useful filtering capabilities.

Key technical points:
- Current pattern matching is anchored at hierarchy boundaries
- Single `*` matches within one hierarchy level only
- Double `**` might be repurposed for cross-hierarchy matching
- Behavior directly impacts both `for-each-ref` and the new `refs list` command

The discussion appears to be converging on maintaining current single-asterisk semantics while considering `**` as a future enhancement for more flexible matching. This would resolve the immediate concern about behavioral divergence between the commands while leaving room for improved pattern matching capabilities.
