This is a follow-up discussion about the recently merged series removing the `core.commentChar=auto` configuration option. The thread focuses on the user experience design of the deprecation warning system.

Junio C Hamano responds to Oswald Buddenhagen's critique of Phillip Wood's approach to helping users migrate away from the deprecated `auto` setting. Buddenhagen had argued that the current implementation adds unnecessary complexity by trying to be overly helpful, suggesting Git should simply tell users to use `git config --show-origin` and let them figure out the fix themselves.

Hamano acknowledges the appeal of simpler code but ultimately sides with Wood's more user-friendly approach, noting that most users prefer clear instructions over having to solve configuration problems themselves. He concedes Buddenhagen's point that the current advice might not always lead to the optimal solution (particularly when dealing with read-only config files), but considers this an acceptable trade-off.

The exchange highlights differing philosophies about how much hand-holding Git should provide during breaking changes - a tension between code simplicity and user experience that often surfaces in maintenance discussions. With the series already merged, this appears to be a retrospective design discussion rather than a request for changes.
