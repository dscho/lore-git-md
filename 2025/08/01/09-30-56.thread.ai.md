Core problem: Fetch operations fail with "fatal: did not receive expected object" and "invalid index-pack output" in blobless clones (`--filter=blob:none`) after adding a new remote, specifically when `transfer.fsckObjects` or `fetch.fsckObjects` is enabled. The failure occurs during object transfer despite correct remote object listing, with the issue now understood to be triggered by fsck operations interacting with server-side delta generation for missing base objects.

The root cause appears to be fsck object verification failing when deltas reference base blobs that are intentionally absent in the filtered clone, suggesting either a protocol violation or an fsck edge case with partial clones.

Open questions: Whether this represents a bug in fsck's handling of filtered clones (should it skip verification of intentionally missing bases?) or in the server's delta generation strategy for filtered fetches.
