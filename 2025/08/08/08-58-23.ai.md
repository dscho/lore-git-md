This is a technical follow-up in the ongoing discussion about Git's scalability for AI workflows. Tanish Desai responds to Skybuck Flying's experimental setup with their own implementation details and findings.

Desai describes a Docker-based approach using GCP instances with Ubuntu 22.04, where each Docker pod connects to a central Git server via SSH. The system uses hostname-specific instruction files in a shared repository to coordinate AI agents (via gemini-cli). Three distinct merge/conflict resolution strategies were tested: direct commit-and-merge (with conflict feedback to the AI), patch-based queuing (using `git am -3`), and file-level locking.

Key technical observations emerge: file-level locking reduces conflicts but doesn't scale beyond a few agents, while patch queuing avoids some conflicts but has its own scaling limitations. The Docker volume-mounted patch system is noted as an alternative to Skybuck's PostgreSQL message queue. Performance metrics suggest diminishing returns with more than 4 agents under current approaches.

This reply provides concrete implementation data that reinforces the thread's central theme: Git's merge and locking mechanisms are fundamentally mismatched to AI-scale parallelism. The Docker/GCP architecture contrasts with Skybuck's Windows/PostgreSQL setup while facing similar core limitations. The message advances the thread by documenting another real-world workaround pattern and its empirical constraints, though it doesn't propose modifications to Git itself.
