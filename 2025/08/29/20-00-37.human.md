This is a discussion thread about Rust integration policy, specifically focusing on type safety and FFI considerations in the ongoing Rust support series.

Brian m. carlson responds to the initial Rust policy document (patch 1/15) with several technical considerations about C/Rust interoperability. They agree with the proposal's preference for fixed-size types (i32/i64) over platform-dependent C types like `long`, noting this avoids portability issues Git has historically encountered. However, they raise concerns about manually maintaining parallel type definitions between C and Rust, suggesting this could lead to subtle bugs, particularly on big-endian systems.

The discussion highlights two key tensions in the Rust integration: the desire for idiomatic Rust code versus the practical need for reliable FFI interoperability, and the tradeoffs between manual type definitions versus generated bindings. Brian suggests using cbindgen for structure definitions to prevent synchronization issues, while still allowing for idiomatic Rust implementations where possible. The exchange shows thoughtful engagement with the technical challenges of the Rust migration while generally supporting the overall direction.
