Submodule gitdir path encoding series (v5) - complete implementation with final design discussions on URL encoding scheme, helper placement, and path length handling. The series implements path encoding to prevent filesystem conflicts in submodule gitdirs via `extensions.submoduleEncoding` config option, with all major components including platform-portable length validation and test coverage.

Core architecture maintains unified directory structure in `.git/modules/` with path resolution through `submodule_name_to_gitdir()`. Junio C Hamano's review raised three key concerns: 1) case sensitivity handling in the encoding scheme (questioning `_a` vs standard URL percent-encoding), 2) documentation phrasing about encoding permanence, and 3) proposing automatic truncation+uniquification for long paths rather than erroring out. The URL encoding helper function placement debate has narrowed to url.[ch] vs submodule.c (Junio prefers submodule.c).

Implementation includes:
- `repository_format_submodule_encoding` flag in repository.h
- Config handling in setup.c
- Case-aware encoding via `strbuf_addstr_case_encode()`
- Comprehensive coverage in t7425-submodule-encoding.sh
- Refactored `add_submodule()` using centralized path helpers

New development: Adrian Ratiu now agrees with Junio that strict length checking (erroring out on long paths) may be unnecessary and suggests either:
1. Dropping the length validation entirely (letting OS handle failures), or
2. Using hashed prefixes (`<hash>_<name>`) for encoded paths

This marks a shift from the v5 approach where patch 5/5 implemented explicit length checking. The discussion now explores tradeoffs between:
- Current simple filesystem mapping (.git/modules/ paths encoded except for legacy)
- Junio's truncation+uniquification proposal
- Adrian's new hashed prefix idea
- Jeff King's question about whether explicit handling is needed at all

Open questions:
1. Final encoding scheme (current `_a` vs %-encoding for case handling)
2. Documentation phrasing about encoding permanence
3. URL helper placement (url.[ch] vs submodule.c)
4. Windows reserved names (carryover)
5. Long path strategy (now considering: drop checks, hash prefixes, or truncate+uniquify)

The series remains functionally complete with helper placement debate effectively closed. All prior feedback on config collision risks and migration implications addressed.
