This is a technical discussion about hardening the reftable writer API in the context of a bugfix series. The email continues the conversation about patch 3/3, which addresses potential corruption when update indices are modified after header writing begins.

Karthik Nayak responds to Patrick Steinhardt's suggestion to make the API stricter by either (1) detecting writer state before allowing limit changes or (2) removing `set_limits()` entirely by making indices required at construction time. While Karthik sees merit in the second approach's immutability guarantees, he notes implementation challenges due to the callback flow between `reftable_addition_add()` and `reftable_writer_new()`. The current design would require extensive refactoring of internal and external callers.

After considering alternatives like modifying callback signatures (which he deems poor design), Karthik proposes a pragmatic solution: keep `set_limits()` but add state checks to enforce it must be called before any records are written. This maintains the current API while preventing the corruption scenario, as the writer already errors if limits aren't set. The discussion shows technical alignment on the problem but diverges on implementation tradeoffs between API purity and refactoring cost.
