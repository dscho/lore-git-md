This is a technical discussion about hardening the reftable writer API in the third patch of a series addressing reftable migration issues. Karthik Nayak and Patrick Steinhardt are working through the best way to prevent invalid 'update_index' modifications after header writing begins in the reftable writer.

The key development here is that Karthik has settled on an implementation approach after considering Patrick's suggestions. Rather than the more invasive option of restructuring the API to make indices required parameters in `writer_new()` (which would require significant refactoring of callback flows), Karthik proposes to keep the current structure but add stricter validation. The solution will check for any existing writer state when `reftable_writer_set_limits()` is called and error out if records have already been queued.

This represents a pragmatic middle ground that maintains the current API surface while still preventing the dangerous case of late limit modifications. The discussion shows good technical alignment between the two developers, with Karthik carefully considering the implementation tradeoffs before settling on this solution for the next version of the patch.
