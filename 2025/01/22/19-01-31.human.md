This is a bug report about Windows-specific file locking behavior when using reftables. Christian Reich demonstrates that when a Java program (JGit) holds a lock on reftable files, Git's `pack-refs` command fails to unlink the files and repeatedly asks the user whether to retry, rather than gracefully handling the locked state.

The issue occurs when:
1. A repository uses reftables (created with `--ref-format=reftable`)
2. A JGit process holds the files open (simulated here with a sleep)
3. Someone runs `git update-ref` followed by `git pack-refs`

The reporter expects Git to either successfully unlink the files or, if that fails due to locks, silently skip the operation and try again later, as suggested by reftable documentation. Instead, Git presents the user with multiple retry prompts before giving up.

The bug appears well-documented with clear reproduction steps and demonstrates a real-world scenario where Git's Windows file handling could be more robust. This seems like a Windows-specific edge case in the reftable implementation that could affect users mixing Git and JGit on the same repository.
