Performance optimization proposal for batch remote removal. Brian M. Carlson weighs in on the ongoing discussion about extending `git remote remove` to handle multiple remotes, providing concrete performance data from real-world experience. 

Carlson describes a scenario where maintaining 80,000 refs across numerous developer remotes made single-remote removal operations painfully slow due to quadratic packed-refs rewriting. They highlight that batch removal would allow performing the operation in a single ref transaction, avoiding this performance pitfall. The email also notes that simply editing `.git/config` isn't sufficient since it wouldn't clean up remote-tracking branches.

The message includes specific timing data showing that `git remote rename` on a repository with 45,000 refs took 45 minutes before optimizations, now reduced to about a minute with reftable. This serves as both a cautionary tale about ref-handling performance and evidence that improvements are possible. While acknowledging shell workarounds work for small repositories, Carlson strongly advocates for the native implementation to handle large-scale cases efficiently.

This contribution shifts the discussion from philosophical debate to concrete performance considerations, providing maintainers with real-world data points about the quadratic scaling problem and validating the need for batch operations solution. The email also implicitly makes the case that this isn't just a convenience feature but a genuine performance optimization for certain workflows.
