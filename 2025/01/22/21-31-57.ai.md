This is a discussion thread continuation about the hash algorithm refactoring series, specifically focusing on edge cases in the `hash_algo_by_ptr()` function and NULL pointer handling.

The email captures Junio C Hamano's agreement with Jeff King's analysis from earlier in the thread. The key points are:

1. They confirm the decision to have `hash_algo_by_ptr()` return `GIT_HASH_UNKNOWN` when given an unsafe algorithm pointer, which prevents silent mixing of safe/unsafe variants while maintaining safety.

2. Jeff's analysis revealed a pre-existing NULL pointer handling issue where `hash_algo_by_ptr(0)` currently returns garbage data that gets written into object IDs, though this doesn't currently cause problems in practice since the garbage data isn't used.

3. Both agree this NULL handling issue should be fixed separately from the current series, though the UNKNOWN return approach would at least make such cases fail explicitly rather than continuing with corrupt state.

4. The discussion reinforces that making unsafe variants unidentifiable (via UNKNOWN return) is the right direction, as it prevents undefined behavior and forces any incorrect usage to fail visibly rather than silently.

This email represents final maintainer approval of the pointer-to-ID conversion approach for unsafe algorithms, while noting (but deferring) the separate NULL pointer handling issue. The thread shows consensus forming around the safety improvements in the series while identifying areas for future work.
