Design discussion on OS version capability integration approach.

Christian Couder responds to Junio's position on merging the OS version information into the existing agent capability string. While acknowledging the documentation warnings against programmatic parsing exist for both capabilities, Christian argues for keeping them separate to make legitimate parsing easier for use cases like server-side OS statistics. He questions how OS information would cleanly integrate with the existing agent string format given the variability in how `GIT_USER_AGENT` might be configured.

Key technical points raised:
- Reiterates that clear documentation should be sufficient to prevent misuse
- Argues for making parsing straightforward for valid use cases
- Notes practical challenges in combining OS info with the free-form agent string
- Points out the agent string's format is only "typically" package/version, not strictly enforced

This continues the architectural debate between:
1. Christian's position: Separate capability enables clean parsing for legitimate stats while maintaining security warnings
2. Junio's position: Combined capability simplifies protocol since both fields carry the same parsing warnings

The exchange reveals Christian sees more value in the OS version data's practical uses than Junio, while both agree on the importance of discouraging feature detection via parsing. The discussion now hinges on whether the parsing convenience outweighs protocol simplicity, with implementation details of the combined approach being a new concern.
