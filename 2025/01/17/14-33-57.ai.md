This is a bugfix patch in a series addressing packed-refs validation issues, specifically focusing on detecting embedded NUL characters in refnames. The patch adds a check in `next_record()` to catch corrupted refnames containing NUL bytes, which could otherwise create security vulnerabilities or subtle bugs when truncated refnames remain technically valid.

The key technical aspects are:
1. Introduces `refname_contains_null()` helper that compares strbuf length against strlen to detect embedded NULs
2. Places the check in `next_record()` where refnames are parsed from the packed-refs file
3. Currently uses strlen() comparison but will switch to more efficient memchr() per Patrick Steinhardt's suggestion
4. Dies immediately when NULs are detected, maintaining the existing error handling pattern in this code path

Patrick has approved the core approach while suggesting optimizations, and the author acknowledges the terminology correction (NUL vs NULL) and performance improvement. The patch addresses a specific case from a referenced bug report where git fsck couldn't detect certain malformed refs, though the placement in the parsing code rather than fsck infrastructure may warrant further discussion about architectural alignment with the broader ref verification work.

This is part of an ongoing series where Patrick is pushing for more backend-agnostic validation approaches, but this particular check appears to be an uncontroversial improvement to packed-refs parsing safety. The author plans to incorporate the suggested memchr() optimization in the next version.
