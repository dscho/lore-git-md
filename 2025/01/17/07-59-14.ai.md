This is the third and final patch in a series addressing reftable migration improvements, specifically focusing on preventing corruption when writing reftable files. The patch fixes a subtle bug in the reftable writer where `update_index` values could be modified after the header was written, potentially causing header/footer mismatches.

The change adds a guard in `reftable_writer_set_limits()` to BUG() if called after the first block is written, ensuring the header and footer values remain consistent. This is a defensive programming measure that prevents a class of corruption issues where later modifications to the update index range would create an inconsistent state in the written reftable file.

The patch is narrowly focused on the reftable writer implementation, specifically touching `reftable/writer.c`. It builds on the previous two patches in the series (which addressed function visibility and integer type safety) to further harden the reftable infrastructure. The change is particularly relevant for repositories converting from loose refs to reftable format, where such corruption was originally discovered.

Key technical details include the use of the existing `w->next` field as a sentinel for header writing completion, and the introduction of a BUG() check rather than silently ignoring the update. The patch maintains all existing behavior while adding the new safety check, with no changes to the on-disk format or public API.

This completes the series' technical improvements to the reftable backend following earlier corruption reports, with all three patches working together to improve reliability during the migration path. The change is straightforward and unlikely to be controversial, as it clearly prevents a real problem without introducing new complexity.
