Thread summary:

This thread addresses memory leaks and inconsistent behavior in Git's ref-filter code when handling ahead-behind and is-base calculations across commands (branch, for-each-ref, tag, verify-tag). The core issue stems from committish references being stored in separate string lists for formatting versus sorting operations, causing leaks when sorting preceded formatting and incorrect results in the reverse case.

Two solutions have been proposed:
1. René Scharfe's approach makes the bases and is_base_tips string lists static variables shared between operations, eliminating ref_format_init()/ref_format_clear() functions.
2. Jeff King's alternative modifies ref_sorting_options() to take an explicit ref_format parameter, maintaining connection between formatting/sorting without static variables.

Key technical details:
- Both solutions resolve the memory management issues and ordering-dependent behavior
- Scharfe's approach is simpler code but introduces static state
- King's approach requires more boilerplate in callers but better aligns with lib-ification goals
- Changes affect multiple commands (branch, for-each-ref, tag, ls-remote)
- King's patch updates parse_sorting_atom() to use provided format struct
- Existing tests verify correct behavior with sorting operations using these atom types

New considerations from latest discussion:
- The `ls-remote` command currently lacks a `ref_format` struct, which would need to be added under either solution
- Some sorting atoms (like `authordate`) fail gracefully when outside a repo, but others (like ahead-behind calculations) produce inconsistent results depending on local object availability
- Remote references may or may not have corresponding local objects, leading to potential sorting inconsistencies
- Reveals broader design question about which sorting atoms should be allowed for remote operations

Current status:
