This thread examines competing approaches to refactor Git's ref-filter subsystem, which handles reference formatting and sorting across multiple commands (branch, for-each-ref, tag, verify-tag, and ls-remote). The core issue involves managing state for ahead-behind and is-base calculations, where previous implementations caused memory leaks due to uncoordinated string lists.

Two main solutions have emerged: René Scharfe advocates for static variables to share state between operations, offering simpler code at the cost of some explicitness. Jeff King proposes explicitly passing ref_format structs through the API, better supporting Git's lib-ification goals but requiring more boilerplate. Junio Hamano has indicated a preference for Jeff's more explicit approach.

In the latest exchange, René acknowledges the technical merits of both solutions while raising deeper architectural questions. He suggests the "ahead-behind" atom might benefit from being split into separate components, and questions whether ref_format is the ideal home for these structures versus alternatives like ref_filter or a new dedicated struct. While maintaining his preference for simplicity, René leaves the door open to either approach, noting he could resubmit his original patch if there's consensus to relocate the underlying data structures.

The discussion remains technically resolved but architecturally unresolved, with both contributors thoughtfully engaging on long-term design tradeoffs. The ls-remote command has surfaced additional considerations about remote reference sorting that may need follow-up work regardless of the core solution chosen. With Junio's input favoring explicit parameters and both principal contributors acknowledging each other's technical points, the thread appears to be converging toward Jeff's approach, though final resolution awaits.
