This is a bugfix patch in a series adding ref consistency checks, specifically targeting NULL byte detection in packed refnames.

The patch addresses a subtle corruption case where a packed-refs file could contain embedded NULL bytes in refnames that would go undetected. Currently, Git calculates refname length by pointer subtraction between the start and newline, then validates the name format - but this misses NULLs after a valid prefix. The patch adds a new `refname_contains_null()` helper that compares the strbuf length against the strlen() of its content to catch such cases, failing verification if they differ.

Key technical details:
- New function `refname_contains_null()` compares strbuf.len vs strlen(buf)
- Integrated into `next_record()` where packed refs are parsed
- Fails verification with descriptive error if NULLs are found
- Builds on prior work in the series by adding another validation layer
- References a specific bug report showing fsck missed these cases
- Maintains the series' pattern of focused, testable verification steps

The change is narrowly scoped but plugs a real hole in ref validation. It follows the series' incremental approach by tackling one specific corruption vector before moving to broader entry validation in subsequent patches. The implementation appears straightforward and the error case is clearly communicated.
