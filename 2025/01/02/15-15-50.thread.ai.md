Thread summary:

Bug report and analysis of `git log` date filtering anomalies with time-disordered commits. Originating reporter Sarah Gastner identified inconsistent behavior where commit 501976cc34e (2023-03-13) appears in some date ranges but not others, reproducible across platforms on Git 2.47.1. René Scharfe's investigation reveals the root cause: the commit chain contains timestamp violations where child commit 4346c5e5e29 (March 7) appears after parent 501976cc34e (March 13), likely from history rewriting with `git rebase --committer-date-is-author-date` that didn't update commit times. 

The core issue stems from Git's traversal optimization that stops when encountering commits older than the `--after` date, which fails with non-chronological commit dates. Technical analysis shows this is a known limitation of the date-filtering implementation rather than a straightforward bug. Potential solutions (adding search slack, special handling of out-of-order commits, or full traversal) would introduce performance costs or new edge cases. Current behavior represents a pragmatic tradeoff where users modifying history must account for date inconsistencies. 

Open questions remain about whether to: 1) document this as expected behavior, 2) implement more sophisticated (but potentially expensive) handling of time-disordered commits, or 3) maintain the current optimization despite its limitations.
