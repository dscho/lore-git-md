Bugfix tightening describe-like output parsing to prevent misinterpretation of branch:path syntax when paths contain hash-like suffixes. This is the second patch in a series addressing object name resolution edge cases, following the unpaired curly braces fix.

The patch modifies `object-name.c` to strictly validate the `${REFNAME}-${INTEGER}` portion of describe-like output (e.g. `v1.7.4.2-679-g3bee7fb`) before accepting the hash portion. This prevents false matches when paths contain segments that look like abbreviated hashes (e.g. `branchname:path/to/i-gaffed` would previously match commit `affed` if it existed). The new `ref_and_count_parts_valid()` function enforces that:
- The portion before `-g` must contain a valid refname
- Followed by a dash and numeric count
- With comprehensive validation of the refname portion using `check_refname_format()`

Test cases in `t6120-describe.sh` verify:
- Files containing hash-like suffixes are properly handled as paths
- Malformed describe-like strings with invalid refnames are rejected
- Backward compatibility with legitimate describe output is maintained

The patch addresses a real-world issue reported by Gabriel Amaral where path resolution could be hijacked by coincidental hash-like strings. While the core functionality is sound, the cover letter notes potential backward compatibility questions around invalid refnames that may need discussion. The implementation appears thorough with clear test coverage for both the primary case and edge conditions.
