This is the second patch in a bugfix series addressing edge cases in Git's object name resolution. It tightens parsing of describe-like output to prevent misinterpretation of branch:path syntax when the path contains segments that look like commit hashes.

The patch fixes cases where filenames containing "-gHASH" (e.g. "branchname:path/to/i-gaffed") could be incorrectly interpreted as requests for commit objects rather than file contents. It enforces that describe-style syntax must have both a valid refname and numeric count before the "-gHASH" portion, preventing false matches against arbitrary strings.

The implementation adds validation in object-name.c to check that:
1. The portion before "-g" contains a valid refname
2. There's a proper numeric count between the refname and hash
3. The overall format matches Git's documented describe output syntax

Test cases verify both the positive case (properly formatted describe output still works) and negative cases (malformed strings and path-like inputs are rejected). The changes maintain backward compatibility with all valid existing uses while closing a security-adjacent hole where malformed input could trigger unexpected object lookups.

This appears to be a well-considered fix that builds on the first patch's work to handle curly brace edge cases, now addressing another class of ambiguous object name scenarios. The test coverage is thorough and the implementation follows Git's existing patterns.
