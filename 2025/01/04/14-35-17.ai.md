This is a maintainer response in the ongoing bugfix series addressing object name resolution issues with unpaired curly braces and describe-like output validation. Junio C Hamano weighs in on the second patch's backward compatibility concerns regarding branch:path interpretation.

The key focus is on the patch's handling of describe-like strings (e.g., `${garbage}-g${hash}`) where the maintainer raises several important considerations. He strongly opposes requiring `${valid_refname}` to exist locally, noting this would break existing workflows. He's also skeptical about validating refnames against current rules since validity definitions may differ from when the reference was originally created.

The maintainer introduces a broader philosophical question about how Git should handle strings that could be interpreted multiple ways by different parts of the object-name code. He suggests treating ambiguous cases (like `${garbage}-gaffed` which could refer to either an object name or a path) similarly to how Git already handles ambiguous short hashes - by declaring them ambiguous rather than trying to resolve them one way or another.

This response shifts the discussion from the specific implementation details to higher-level design principles about how Git should handle ambiguous object names. The maintainer seems to be pushing for a more consistent and principled approach to ambiguity resolution across the codebase, rather than adding more special cases to the parser. The feedback suggests the current patch may need architectural reconsideration to align with these broader parsing philosophies.
