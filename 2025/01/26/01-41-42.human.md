This is a technical discussion about Windows reftable backend compatibility, specifically around file unlinking behavior. Junio Hamano responds to Patrick Steinhardt's proposed solution for handling file-in-use errors on Windows, which introduced a `MINGW_DONT_HANDLE_IN_USE_ERROR` flag to control retry behavior.

Hamano expresses concerns about the approach, calling the macro-based solution "yucky" and questioning whether completely bypassing the retry loop is too drastic. He suggests a middle ground - keeping the non-interactive retry attempts but avoiding the interactive fallback - might be more user-friendly while still addressing the core issue. The email also raises important questions about whether the problematic cases involve files held by the Git process itself (which should be fixed by code reorganization) versus files held by external processes (where retries might still be valuable).

This continues the architectural debate about where to handle Windows' file locking behavior - at the platform layer (as Steinhardt proposed) versus within reftable's implementation. Hamano's comments add weight to the discussion about balancing technical correctness with user experience, while acknowledging Windows' unique constraints compared to POSIX systems.
