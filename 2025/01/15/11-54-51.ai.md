Bugfix for reftable migration corruption in multi-batch scenarios, specifically addressing header/trailer max_update_index mismatch.

Karthik Nayak responds to Brian Carlson's bug report with a fix for the reftable migration corruption issue. The problem occurs when migrating repositories with many refs and reflog updates, where the header's max_update_index (set to 1) mismatches the trailer's correct higher value. Nayak confirms Carlson's analysis that this only manifests in multi-batch migrations.

The fix introduces a new max_index field in ref_transaction to track the highest update index across all operations. This value is then used to properly set the reftable writer's limits before any blocks are written, preventing the header/trailer inconsistency. The patch modifies refs.c to track the max index during transaction setup and updates reftable-backend.c to use this value when setting writer limits.

Key technical details:
- Adds transaction->max_index to track highest update_index across all operations
- Modifies reftable writer initialization to use this max_index upfront
- Removes redundant max_update_index tracking during reflog writing
- Includes a test case that creates 5000 refs followed by 3000 updates to trigger the multi-batch scenario

The patch maintains all existing functionality while fixing the corruption case. Nayak requests Carlson test the fix against their real-world repositories (with 2983 and 44832 refs) that originally exhibited the problem. The changes are focused on the test case directly reproduces the failure scenario described in the bug report.
