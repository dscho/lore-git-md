This is a continuation of the thread about Git help message output behavior, specifically addressing the inconsistency between different subcommands. Jonas Konrad expands on his original bug report by providing more examples of the inconsistent behavior across Git subcommands. He notes that `git -h` writes to stdout with exit status 0 (as he expects), `git reflog -h` writes to stdout but exits non-zero, while `git branch -h` writes to stderr - creating three different behaviors for what should be similar operations.

Jonas challenges Matěj Cepl's earlier claim that writing help to stderr follows UNIX conventions, arguing that if this were Git's intended behavior, then many other subcommands would need to be changed to match. He questions the logic that would make one subcommand's help "substantial" (worthy of stdout) while another's is not, pointing out that usage frequency doesn't seem to be the determining factor. The email strengthens the case for inconsistency being the core issue, though it doesn't propose a specific solution beyond suggesting the current behavior is confusing to users.

Key technical details mentioned include the specific commands showing different behaviors (`git -h`, `git reflog -h`, `git branch -h`), their output streams (stdout vs stderr), and their exit codes (0 vs non-zero). The thread remains at an impasse between two views: UNIX convention (stderr for help) vs consistency and usability (stdout for all help). No maintainer input has been provided yet to clarify Git's official stance on this matter.
