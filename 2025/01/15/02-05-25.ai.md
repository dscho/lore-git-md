This is a follow-up in the security release thread regarding packaging constraints for NonStop environments. Randall Becker (rsbecker@nexbridge.com) responds to Junio Hamano's clarification about the version metadata issue, explaining the strict certification requirements for NonStop platform builds. 

The key technical constraint is that NonStop builds must be directly traceable to unmodified Git repository commits - tarballs are unacceptable for certification purposes due to security policies. Becker emphasizes that the community requires verifiable commit-based builds rather than tarballs, which they consider potentially compromisable. This prevents them from packaging v2.47.2 despite the version metadata issue being benign in practice.

The email reveals an important downstream packaging constraint that wasn't fully addressed by the earlier technical clarification - while the DEF_VER inconsistency doesn't affect version reporting, the NonStop environment's certification process has stricter requirements about build provenance. Becker's role as a trusted build manager means he must skip v2.47.2 entirely and direct users to v2.48.1 instead, as it doesn't have the version metadata issue.

This highlights a tension between Git's security release process (where version metadata is normally a low priority) and enterprise environments with strict compliance requirements. The email provides important context about real-world deployment constraints that may need consideration in future security release procedures, particularly regarding version metadata consistency across all release artifacts.
