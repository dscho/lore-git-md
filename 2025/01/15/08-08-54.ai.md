This is a bugfix and documentation clarification regarding the `--expire-to` option in `git repack`. The discussion focuses on how the option's behavior differs from what users might expect based on its documentation.

The key issue is that `--expire-to` doesn't actually write to the specified directory as implied by the docs, but rather uses it as a base name for generated pack files. This creates confusion when users specify paths ending in "pack/", expecting the files to be placed inside that directory. Instead, the command strips "pack/" and uses the parent directory as the base, creating files like "pack-*.{mtimes,idx,pack}" rather than "pack/pack-*".

The thread reveals two specific problems:
1. The documentation is misleading about the parameter being a directory when it's actually treated as a base name
2. The behavior breaks when users provide paths that don't end in "pack/", though this edge case isn't fully explored in this email

The email agrees with these concerns but doesn't propose a specific solution - it's primarily acknowledging the documentation/behavior mismatch. This appears to be part of an ongoing discussion about improving the `--expire-to` functionality in `git repack`.
