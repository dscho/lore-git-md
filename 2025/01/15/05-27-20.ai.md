This is a clarification in the ongoing security release thread about version metadata handling, specifically addressing NonStop platform build requirements.

Junio Hamano responds to Randall Becker's concerns about NonStop-certified builds needing to correlate directly with Git repository commits rather than tarballs. He confirms that building from a cloned repository checked out at the v2.47.2 tag will correctly report "2.47.2" when running `git version`, regardless of the DEF_VER variable in GIT-VERSION-GEN. This is because the build process will use `git describe` when run from a Git repository rather than the tarball's static version string.

The response highlights that the version reporting discrepancy only affects tarball builds, which NonStop doesn't use anyway due to their certification requirements. Hamano seems puzzled why this remains a blocking issue for NonStop since their build-from-repo approach would naturally produce correct version strings. This suggests either a misunderstanding of NonStop's exact certification constraints or that there may be additional unstated requirements about build provenance verification that go beyond simple version string accuracy.

Key technical details: the GIT-VERSION-GEN script's behavior differs between repository builds (using `git describe`) and tarball builds (using DEF_VER), with the security fixes being present in both cases. The discussion centers on version metadata reporting rather than the security content itself, which was previously established as properly backported across all versions.
