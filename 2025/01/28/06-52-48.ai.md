This is a technical follow-up in the ongoing Windows reftable backend compatibility discussion, focusing on file unlinking behavior specifics. Johannes Sixt responds to Patrick Steinhardt's questions about Windows file deletion semantics, clarifying key distinctions in how different processes interact with file locks.

Sixt explains that the proposed `CreateFileW`+`FILE_FLAG_DELETE_ON_CLOSE` approach only works when processes cooperate via `FILE_SHARE_DELETE`, which isn't generally guaranteed. He distinguishes between two scenarios: (1) files opened by other Git processes (where POSIX-like behavior is desirable) and (2) files opened within the same process (where deletion while open isn't expected). This refines the earlier discussion by separating inter-process from intra-process file handling.

The email advocates for removing mingw_unlink()'s interactive prompt (which asks users about locked files) in favor of a cooperative strategy, noting the prompt's limited practical utility. Sixt observes this prompt rarely appears in modern usage, though acknowledges his own narrow Git usage patterns may not represent all cases. The response continues the architectural debate about where to handle Windows-specific behaviors while moving toward concrete implementation choices.
