This is a technical follow-up in the ongoing Windows reftable backend compatibility discussion. Johannes Sixt responds to Patrick Steinhardt's questions about Windows file unlinking behavior, clarifying key points about process cooperation requirements.

Sixt explains that the proposed `CreateFileW` approach with `FILE_FLAG_DELETE_ON_CLOSE` only works when processes cooperate by using `FILE_SHARE_DELETE`, which is not generally the case. He distinguishes between two scenarios: files opened by other Git processes (where POSIX-like behavior is desirable) versus files opened within the same process (where deletion while open isn't expected).

The email reinforces Sixt's position that the interactive prompt in `mingw_unlink()` is rarely useful in practice, advocating instead for a cooperative strategy that provides POSIX-like behavior for concurrent Git processes while accepting Windows' limitations for files held by the current process. This continues the architectural debate about where to handle Windows' non-POSIX behavior - at the platform layer or within specific components like reftable.
