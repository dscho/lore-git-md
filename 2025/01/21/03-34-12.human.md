This is the final patch in a 3-part series addressing reftable corruption issues, specifically focusing on preventing invalid updates after records are written. The patch modifies `reftable_writer_set_limits()` to return an error if called after any records are added, fixing a potential mismatch between header and footer values in the reftable format.

The change is well-motivated by the thread's context - it prevents corruption that could occur when update indices are modified mid-write. The implementation checks the writer's last_key field to detect if records have already been written, and returns REFTABLE_API_ERROR in that case. All callers are updated to handle the new return value.

The patch appears technically sound with thorough updates to:
- The writer API and its documentation
- All existing call sites in the reftable backend
- Unit tests to verify the new behavior
- Error code definitions

This completes the series' goal of hardening the reftable migration path against corruption, with this patch specifically addressing the temporal safety of index updates. The solution maintains API stability while making misuse difficult, as discussed in earlier thread iterations.
