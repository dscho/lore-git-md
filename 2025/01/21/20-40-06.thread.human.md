This thread reports and investigates a serious reflog regression in Git 2.48.1 where symbolic reference updates (like HEAD) incorrectly record all-zero OIDs in their reflogs, while direct branch updates work correctly. Nika Layzell originally reported the issue, demonstrating broken behavior where HEAD@{1} shows invalid hashes after branch updates.

Jeff King has now identified the root cause - an overly aggressive early return in `lock_ref_for_update()` introduced in commit 297c09eabb ("refs: allow multiple reflog entries for the same refname"). He proposes a simple one-line fix removing this early return, which resolves the issue without breaking existing tests. However, he notes some uncertainty about why the problematic check was originally added, suggesting the fix needs validation from the original author of that commit.

The regression affects core reflog functionality for any symbolic reference operations, making this a high-priority issue. King's proposed solution appears straightforward, though the thread awaits confirmation that removing the early return won't introduce other edge cases. Given the severity of the bug - breaking reflog queries for common workflows - this would likely warrant a fix release once properly reviewed.
