This is the final patch in a 3-part series hardening the reftable backend against corruption during large repository migrations. The patch enforces that `reftable_writer_set_limits()` can only be called before any records are written, preventing header/footer mismatches in the reftable format.

The key technical changes are:
- Converting `reftable_writer_set_limits()` from void to return int, allowing it to fail with REFTABLE_API_ERROR if called after writing begins
- Adding state tracking check using `last_key.len` to detect if records have been written
- Updating documentation to clearly specify the API contract
- Adding unit tests for the error case as suggested by Patrick Steinhardt

The discussion reveals some implementation nuances:
- Patrick suggests using `next` field rather than `last_key` for state tracking, but Karthik explains `last_key` provides stricter validation
- The change is preventative rather than fixing existing bugs, as noted in the documentation update
- Small formatting improvements are being made opportunistically to align with Git's style

This completes the series addressing:
- API visibility concerns (patch 1)
- 32-bit integer overflow (patch 2)
- Writer state validation (this patch)

All technical feedback has been incorporated and the series is ready for merging, providing robust protection against corruption during reftable operations. The final implementation includes both the core safety check and comprehensive test coverage of the error case.
