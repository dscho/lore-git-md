Bug report concerning case-insensitive filesystem behavior in `git add`.

This email reports unexpected behavior when using `git add` with case-mismatched filenames on case-insensitive filesystems (like Windows). The author describes a scenario where attempting to add a file with incorrect case (e.g., `sourcefile.c` when the actual filename is `SourceFile.c`) silently fails - the file isn't staged, yet the command exits successfully without any output. The author questions whether this is intended behavior or a bug, noting the potential for users to commit without realizing files were missed.

The issue appears to be a behavioral inconsistency - while one might expect either successful staging (matching the case-insensitive filesystem behavior) or an explicit error message, Git currently does neither. This could lead to silent failures in workflows. The report is clearly written with a specific, reproducible example, though it doesn't propose a solution or patch. The behavior described would affect all Windows and macOS users working with case-mismatched filenames.
