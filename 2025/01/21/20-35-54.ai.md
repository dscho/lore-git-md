This is a brief response in the ongoing Git GSoC 2025 planning thread, specifically addressing the proposal to move project documentation in-tree.

Junio Hamano responds to Patrick Steinhardt's suggestion about maintaining the list of microprojects in the_repository elimination and other small tasks) as Documentation/Projects.txt. While generally supportive of the idea to improve discoverability and accuracy, Hamano adds an important constraint: each listed project should have a clear expiration date to prevent the accumulation of stale entries. He draws a parallel to the maintenance burden of stale topic branches that never graduate to 'next', indicating this is about keeping the project's documentation as actively maintained as its code.

The response doesn't reject the proposal but adds a specific governance requirement that would need to be addressed in any implementation. This continues the thread's theme of balancing accessibility of project ideas with maintenance discipline, now with explicit criteria from the project maintainer. The condition suggests that simply copying the current out-of-tree list wouldn't be sufficient - the format would need to include metadata about project lifespans.
