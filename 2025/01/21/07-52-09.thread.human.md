This thread discusses a bug report about `git add` behavior on case-insensitive filesystems (like NTFS on Windows or HFS+ on macOS). The reporter describes a scenario where attempting to stage a file with incorrect case (e.g., `git add sourcefile.c` when the actual filename is `SourceFile.c`) fails silently - the file isn't added to the index, yet the command exits successfully without any warning. This could lead to users committing changes while unknowingly missing files.

The behavior appears inconsistent with how case-insensitive filesystems typically work, where one might expect either successful staging (matching the filesystem's case-insensitive matching) or at least an explicit error message. The thread is just starting, so there aren't yet any responses analyzing whether this is intended behavior or a bug that needs fixing. The issue would impact all Windows and macOS users who work with repositories containing case-mismatched filenames.
