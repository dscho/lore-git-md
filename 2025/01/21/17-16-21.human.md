Bug report follow-up regarding case-insensitive filesystem behavior in `git add`. Torsten Bögershausen confirms the reported behavior where Git accepts an incorrectly-cased filename on Windows/macOS without staging the file or providing feedback. He explains this occurs because the filesystem itself reports the incorrect casing as valid, so Git's usual "no match" error path isn't triggered. While not taking a firm position on whether this is a bug or missing feature, he suggests using `git status` as a workaround to verify staged changes before committing. This keeps the discussion open while acknowledging the real-world impact on users who might unknowingly commit without their intended changes. The response doesn't propose a solution but provides technical context for why the current behavior occurs.
