This is a discussion about the core functionality of the OS version reporting feature in Git's capabilities system, specifically addressing fundamental design questions raised by Junio Hamano.

Junio continues to express skepticism about the value of OS version reporting, suggesting the feature's justification remains weak. He notes that Git version differences (already reported via user-agent) are likely more relevant than OS information, and proposes an alternative approach of extending the existing agent capability to optionally include OS details rather than creating a separate mechanism. This would maintain backward compatibility while providing similar information.

The email focuses on API design simplification, with Junio proposing to eliminate the dual-API (raw+sanitized versions) by having `os_version()` always return sanitized output. His suggested implementation would: query the raw system version, immediately sanitize it, cache the result, and return only the sanitized form to all callers. This would reduce the API surface while addressing security concerns about raw string handling.

- Fundamental question remains about whether OS version reporting provides enough value to justify the feature
- Alternative proposal to extend existing user-agent capability rather than add new OS-specific mechanism
- Clear direction to simplify API by removing raw version access and always returning cleaned strings
- Implementation approach for sanitized-only version caching
