This is a feature patch in the promisor-remote/Large Object Promisor (LOP) series (v4 4/6), focusing on the protocol v2 capability for advertising promisor remotes from server to client. Patrick Steinhardt provides detailed feedback on Christian Couder's implementation, primarily focusing on documentation clarity and security considerations.

The patch adds server-side support for advertising promisor remotes via a new protocol v2 capability, allowing servers to suggest alternative remotes where objects might be available. Patrick notes the implementation is clean but raises several important points: the commit message duplicates documentation content unnecessarily, the remote name validation appears too lenient, and there are security concerns around config injection from untrusted remotes that need addressing.

Key technical observations from Patrick include:
- The URL encoding/validation should be stricter for remote names (only alphanumeric)
- Received remote data needs stronger validation before being stored in config
- The state tracking of accepted remotes could be clearer about server/client roles
- Test setup could use more descriptive naming (server2 → promisor)

The feedback suggests the patch is generally sound but needs tightening around security boundaries and could improve documentation organization. This continues the thread's pattern of careful security review while moving the promisor-remote capability forward.
