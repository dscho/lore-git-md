Bugfix patch adding NUL character detection in packed-refs refnames.

This patch is part of the v2 series improving packed-refs validation (5/8). It specifically addresses a gap where embedded NUL characters in refnames could go undetected during packed-refs parsing. The issue was reported by R. Diez, showing that `git fsck` could miss these corruptions when the truncated portion before the first NUL was still a valid refname.

The fix introduces a new `refname_contains_nul()` helper that uses `memchr()` to scan for embedded NULs in the parsed refname string. This check is added to `next_record()` in packed-backend.c, causing the program to die with an error if such corruption is found. The implementation follows the series' pattern of strict validation and builds on prior work using `memchr()` for similar checks.

The patch includes a detailed commit message explaining the edge case and solution, with references to the original report and acknowledgments to mentors Patrick Steinhardt and Karthik Nayak. The change is focused and well-contained, touching only packed-backend.c with a straightforward 19-line addition that includes both the new helper function and its integration into the parsing logic.

Key technical details for future reference: The validation occurs during packed-refs iteration, specifically in `next_record()`. The new function `refname_contains_nul()` checks for NULs using `memchr()` across the full refname length (including the terminating NUL). The error message uses "packed refname contains embedded NULL" phrasing. This complements but does not replace the existing `check_refname_format()` validation.
