This is a security-focused design proposal for the promisor-remote/LOP series, suggesting a significant architectural change to how promisor remotes are identified and managed.

Patrick Steinhardt proposes replacing the current name-based promisor remote identification with an opaque ID system (like UUIDs) to address security and usability concerns. The key aspects are:

1. **Security model shift**: Instead of matching advertised remote names, servers would advertise promisor IDs, and clients would generate local names (e.g., "origin-promisor") while storing the ID in config. This prevents servers from dictating remote names and reduces attack surface.

2. **New configuration scheme**: Introduces three granular controls for promisor management ("new", "update", "prune") that can be combined, replacing the current binary "all"/"knownName" options. These would be scoped to the current remote's promisors.

3. **Protocol change**: Requires modifying the v2 capability to advertise IDs instead of names, though Patrick notes this could be deferred since client-side implementation isn't ready yet.

The proposal maintains the series' focus on security while attempting to preserve user control over remote naming. It introduces new configuration keys (`remote.*.promisor` as a multivalue and `remote.*-promisor.id`) and requires client-side logic for ID-based promisor tracking. This represents a more complex but potentially more robust approach than the current name-matching design, particularly for corporate environments where promisor URLs might need to change while maintaining security.

The email doesn't directly conflict with Junio's earlier case-sensitivity decisions but suggests a different architectural direction that would supersede some of those concerns. It leaves open how this would interact with the ongoing MIDX compatibility questions and shared foundational patches.
