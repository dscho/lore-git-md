This is a security-focused design proposal for the promisor-remote/LOP series, suggesting a significant architectural change to how promisor remotes are identified and managed.

Patrick Steinhardt proposes replacing the current name-based promisor remote identification with an opaque ID system (like UUIDs) to improve security and flexibility. The key idea is to decouple the user-facing remote names from the server-advertised identifiers, preventing potential attacks where a malicious server could manipulate remote names. The proposal includes a detailed mechanism for tracking promisors via ID-based config entries and suggests reworking the `promisor.acceptFromServer` config into more granular "new/update/prune" options.

The email continues an ongoing security discussion in the thread, where Junio Hamano had previously raised concerns about URL comparison security. Patrick's approach would require protocol changes (switching from names to IDs) but argues this could be done without blocking the current series, as the client-side implementation could follow later. The proposal aims to balance security against the agility needs of corporate environments that want dynamic promisor management.

This represents a substantial design shift from the current approach, though Patrick notes it could be implemented incrementally. The suggestion will likely require careful consideration from other contributors, particularly regarding protocol compatibility and the practical implications of ID-based tracking. The security benefits appear compelling, but the trade-off is increased complexity in the promisor management system.
