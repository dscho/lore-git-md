This is a review response in the ongoing bugfix series about packed-refs validation checks. Junio Hamano is pushing back on several aspects of the proposed header validation in patch 4/8.

The key technical disagreements center around how strictly to validate the packed-refs header:
1. **Historical compatibility**: Junio notes the header format has evolved (from Git 1.5.0 onward) and was designed to be extensible, so rejecting older formats would break compatibility.
2. **Trait handling**: The current patch treats any deviation from the exact modern header string as an error, but Junio argues this should instead parse traits (like "peeled", "sorted") and only error on mandatory ones the runtime can't handle.
3. **Error reporting philosophy**: Junio advocates for only reporting issues that would actually cause runtime problems, not stylistic differences from current output.

The review also catches some implementation issues:
- A potentially misleading `line_number` counter that doesn't actually track lines
- Questions about whether missing headers should be reported at all (they were valid in early Git versions)

This continues the thread's pattern of Junio providing historical context and pushing for validation that matches runtime behavior rather than idealized formats. The feedback suggests the header validation needs significant rework to properly handle version compatibility and trait parsing before integration.
