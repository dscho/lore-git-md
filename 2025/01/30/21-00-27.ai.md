This is a follow-up in the ongoing Git GSoC 2025 planning thread, where Junio Hamano proposes a simplified maintenance mechanism for microproject documentation. The discussion has been focused on how to handle stale or unmaintained project entries in Documentation/Projects.txt.

Junio suggests replacing the current "best-before" ownership model with an automatic expiration system that would mechanically drop entries past their expiration date unless actively renewed by community consensus. This approach would eliminate the single-point-of-failure risk of individual owners while maintaining project hygiene. He draws a comparison to how topic branches could benefit from similar automatic expiration rules.

The proposal represents a shift from Kaartic Sivaraam's original "best-before" system that required manual maintenance by designated owners. Junio's mechanical approach would make the documentation more self-maintaining while still allowing for project revival if there's renewed interest. The suggestion comes as part of broader discussions about documentation practices and project inclusion criteria for GSoC 2025.

Key technical aspects include: the proposed timestamp-based expiration mechanism, the distinction between automatic dropping versus manual renewal, and the potential application of similar rules to long-lived topic branches. The email doesn't directly address any of the specific microprojects under consideration, but rather focuses on improving the maintenance infrastructure that would contain them.

This continues the thread's evolution toward more robust documentation practices while maintaining Junio's characteristic focus on maintainability and reducing maintainer burden. The proposal will likely require response from the GSoC org admins (Kaartic Sivaraam and Christian Couder) regarding its integration with their parallel documentation efforts.
