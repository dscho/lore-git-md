Bugfix for promisor pack handling in `git repack` with keep-pack settings.

This is a follow-up email in the thread about `git repack` not properly respecting keep-pack settings (`--keep-pack`, `.keep` files, and `gc.bigPackThreshold`) when handling promisor packs. Junio C Hamano responds to Tomáš Trnka's patch, noting he doesn't have technical feedback but points to two related prior discussions about repack and promisor objects interaction. He suggests the patch would be better reviewed by the authors of those previous threads (Tony Hanyang and Jonathan Tan) rather than himself.

The technical content remains the same as in the original patch: modifying `repack_promisor_objects()` in builtin/repack.c to pass keep-pack options to the pack-objects subprocess when repacking promisor objects during ALL_INTO_ONE repacks. The change preserves existing behavior when `pack_kept_objects` is true. The RFC question about test placement (t7700-repack.sh vs t0410-partial-clone.sh) is still open.

Key technical details for future reference:
- Function signature change for `repack_promisor_objects()` to accept `keep_pack_list`
- Added `--honor-pack-keep` and `--keep-pack` options to pack-objects invocation
- Maintains special handling when `pack_kept_objects` is enabled
- Related prior work identified in two previous threads about repack/promisor interaction

The thread continues to focus on resolving the inconsistency in keep-pack handling between regular and promisor pack repacking, with the patch appearing technically sound but still needing test coverage and review from domain experts.
