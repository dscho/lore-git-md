This thread addresses a regression in Git's fetch protocol v2 behavior where tag decoration breaks when fetching specific commits with depth limits, originally reported by Igor Todorovski. The issue stems from an interaction between three commits that modified how ref prefixes are handled during fetches, particularly around HEAD and tag references.

Taylor Blau initially proposed unconditionally adding "refs/tags/" to ref prefixes as a fix, but Junio Hamano raised concerns about the architectural implications of this approach, noting the brittleness of incrementally building ref prefixes. The discussion has deepened with Jeff King (Peff) now weighing in. Peff agrees with Junio's assessment but argues the root cause is specifically the unconditional addition of "HEAD" to ref prefixes, not Taylor's tag-related changes.

Peff offers two alternative solutions: a minimal fix making HEAD prefix addition conditional (similar to existing tag logic), and a more comprehensive approach that explicitly handles HEAD fetches. His analysis reveals subtle protocol semantics where an empty prefix fetches all refs while any prefix restricts the advertisement. This creates complexity when coordinating multiple components (fetch refs, tags, HEAD) that may need to add prefixes.

The thread now faces a choice between implementing Peff-suggested stopgap fixes or undertaking a more substantial redesign of the prefix handling mechanism. While the immediate issue affects tag decoration in specific fetch scenarios, the discussion has uncovered deeper questions about the protocol's optimization potential versus implementation complexity, particularly around SHA-1-only fetches where minimal advertisement would be ideal. The path forward remains open, with the community weighing short-term solutions against longer-term architectural improvements.
