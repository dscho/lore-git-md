This is a technical review response in the ongoing promisor-remote/Large Object Promisor (LOP) series (v4/6), focusing on protocol v2 capability implementation. Patrick Steinhardt provides detailed feedback on Christian Couder's patch that adds 'promisor-remote' capability to protocol v2.

The review identifies several areas needing attention:
1. Documentation clarity - suggests reducing commit message duplication with technical docs and better explaining client-side wiring (or lack thereof)
2. Security concerns - flags insufficient input validation for remote names/URLs from untrusted sources, particularly around non-alphanumeric characters
3. Implementation details - questions the dual strvec approach for names/urls versus a strmap, and suggests clearer server/client state tracking
4. Test improvements - proposes renaming 'server2' to 'promisor' for clarity
5. Future-proofing - recommends removing speculative future-use text from docs

Key technical observations:
- The patch currently lacks proper security boundary for remote names (should restrict to alphanumeric)
- URL handling needs stricter validation to prevent config injection
- State management between server/client could be more explicit
- The core protocol change itself (adding promisor-remote capability) appears sound

The review maintains the thread's focus on security semantics while addressing specific implementation choices in this protocol capability patch. It doesn't challenge the overall approach but identifies concrete areas needing refinement before merging.
