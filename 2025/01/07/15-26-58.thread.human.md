This thread began as a discussion about random number generation in the reftable backend but has expanded into a broader examination of Git's system-wide RNG reliability, particularly around OpenSSL's CSPRNG implementation. Patrick Steinhardt initially raised concerns about OpenSSL's RAND_bytes() failing on some platforms, which could affect reftable's temporary file naming. Testing confirmed these issues only cause temporary failures (requiring retries) rather than data corruption.

The conversation has now shifted to platform-specific challenges. Randall Becker highlighted ia64 systems' lack of alternative RNG backends, while Brian m. carlson's latest contribution explores potential workarounds for NonStop platforms, including leveraging libbsd's fallback getentropy implementation. Brian notes these are stopgap measures - test failures might be addressed while deeper security concerns around entropy quality remain, particularly for cryptographic operations like TLS/SSH.

Junio Hamano's earlier proposal to simplify the RNG approach remains under consideration, but platform constraints complicate any sweeping changes. The thread reveals an ongoing tension between the need for reliable unique identifiers, OpenSSL's limitations, and the reality of maintaining support for legacy systems like ia64 (scheduled for 2025 EOL). While reftable-specific concerns have been mitigated, the core issue of Git's RNG backend reliability across all platforms remains unresolved.
