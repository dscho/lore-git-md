The thread centers on how reftable should handle random number generation for temporary filenames and retry delays, particularly when system entropy is exhausted. Patrick Steinhardt's initial two-part solution—first improving Git's cryptographic random number infrastructure, then applying it to reftable—has reached an impasse. While the first part was accepted, Junio Hamano strongly objects to having reftable depend on Git's CSPRNG layer, despite Randall Becker's validation that the fix addresses real OpenSSL failures on NonStop systems.

The discussion has clarified that reftable currently uses `git_rand()` (not `rand()`) for two non-cryptographic purposes: spreading out retry delays to avoid thundering herds and generating temporary filenames to prevent collisions. Junio maintains these don't justify crossing subsystem boundaries, suggesting either using standard `rand()` or even constant values if perfect randomness isn't critical. He also questions whether Git should work around platform PRNG issues rather than requiring proper implementations.

The philosophical divide is now clear: Patrick's approach prioritizes comprehensive platform coverage by addressing observed failures, while Junio advocates strict subsystem isolation and pushing back on platforms to fix their implementations. With no new technical arguments emerging, the path forward likely depends on whether the reftable maintainers can either justify the dependency to Junio's satisfaction or find an alternative that meets both technical and architectural requirements.
