This is a technical follow-up in the ongoing discussion about Git's handling of smartcard-based GPG signing keys. Jeff King (peff@peff.net) responds to Carlos Maiolino's investigation of why `git tag -s` silently falls back to a different key when the configured `user.signingKey` (on a smartcard) is unavailable.

The key technical clarification is that Git simply passes the configured key string to GPG without any awareness of key availability - it relies entirely on GPG's response to determine success or failure. Peff seeks to narrow down whether the issue stems from Git incorrectly passing the key (which would show in GIT_TRACE output) versus GPG accepting but then substituting the key (which would be a GPG-level behavior).

The email highlights two diagnostic scenarios to distinguish these cases: comparing behavior between config-specified keys versus CLI-specified keys, and examining whether GIT_TRACE shows the correct key being passed even when the wrong key ends up being used. This suggests the next steps in debugging should focus on concrete GIT_TRACE outputs to determine where in the pipeline the key substitution occurs.

The security implication remains central - both parties agree Git should at least warn when unable to use the specifically requested signing key, particularly for hardware-backed keys where silent fallback undermines security expectations. The thread is progressing toward identifying whether the fix needs to be in Git's GPG invocation plumbing or whether GPG itself needs modification to properly report key substitution scenarios.
