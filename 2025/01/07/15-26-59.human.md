This is the first patch in a two-part series addressing entropy handling in the reftable backend, specifically focusing on OpenSSL's CSPRNG failures when system entropy is exhausted. The patch introduces a new `CSPRNG_BYTES_INSECURE` flag that allows callers to opt into weaker cryptographic randomness when strong randomness isn't strictly necessary.

The change primarily affects the `csprng_bytes()` interface, which now accepts flags to control its behavior. The key modification is for OpenSSL's implementation, where it will fall back to `RAND_pseudo_bytes()` when entropy is low and the insecure flag is set. Other platforms' implementations (arc4random, getrandom, etc.) remain unchanged since they either don't fail or already handle low-entropy cases gracefully.

The patch includes updates to all existing callers (like `git_rand()`) to maintain current behavior by default (passing flag=0), while the follow-up patch will modify the reftable code to use the new insecure mode for temporary filenames. The author notes this is a deliberate security tradeoff - the flag ensures callers must explicitly opt into weaker randomness rather than silently accepting it.

The changes are well-contained and the commit message provides thorough analysis of different platforms' behaviors. This looks like a thoughtful solution to a real problem, though reviewers will likely want to verify the security boundary is properly maintained.
