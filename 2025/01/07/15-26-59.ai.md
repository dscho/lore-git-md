Reftable entropy handling series part 1: introducing insecure random bytes fallback. This first patch modifies Git's cryptographic random number generation infrastructure to allow callers to opt into accepting less secure random bytes when the system entropy pool is exhausted.

The core change adds a `CSPRNG_BYTES_INSECURE` flag to the `csprng_bytes()` interface, which primarily affects OpenSSL's behavior. When the flag is set and OpenSSL reports the generated bytes aren't cryptographically secure (via `RAND_pseudo_bytes()`), the function will still return them rather than failing. Other platforms' implementations either don't have this distinction (arc4random, getrandom) or can't be configured to bypass blocking (getentropy).

The patch includes mechanical updates to all existing callers to pass `0` (the default secure-only behavior). The reftable backend will use the insecure mode in the following patch. The commit message provides a thorough analysis of each platform's behavior and justifies the flag-based approach over silently accepting insecure bytes everywhere, noting this maintains security awareness at call sites.

Key technical details:
- New flag in `wrapper.h` with clear documentation
- OpenSSL implementation switched from `RAND_bytes()` to `RAND_pseudo_bytes()`
- All existing `csprng_bytes()` and `git_rand()` callers updated to pass `0`
- No behavior change for non-OpenSSL platforms
- Prepares for reftable's tempfile naming use case where cryptographic security isn't critical

This appears to be a well-considered change with clear commit message rationale and thorough implementation. The security tradeoffs are explicitly analyzed and the patch maintains backward compatibility while enabling the specific reftable improvement in the series.
