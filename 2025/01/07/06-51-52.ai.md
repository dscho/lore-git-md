This is a bugfix discussion regarding random number generation failures in the reftable backend on ia64 systems. Patrick Steinhardt responds to Randall Becker's report of test t0610.47 failing with "unable to get random bytes" errors during concurrent ref updates.

The analysis identifies two key callsites for random bytes in reftable: `format_name()` (which uses `git_rand()`) and `reftable_stack_reload_maybe_reuse()` (using plain `rand()`). The failures are traced to `format_name()` exhausting OpenSSL's entropy pool on ia64 systems using PRNGD, particularly under heavy concurrent load. Patrick notes this isn't a regression in 2.48.0-rc2 but rather a preexisting, low-probability issue.

The proposed solution involves modifying the CSPRNG interface to optionally accept insecure random bytes when strong entropy isn't critical, demonstrated through a draft patch adding a `CSPRNG_BYTES_INSECURE` flag. The changes would affect multiple components including the reftable stack, gc scheduler, and test helpers. Patrick suggests this isn't urgent for 2.48.0 since the failure is rare and doesn't cause data corruption, just aborted operations.

Key technical details for future reference: the issue manifests in `reftable/stack.c`'s `format_name()` function, involves OpenSSL's `RAND_bytes()` vs `RAND_pseudo_bytes()`, and centers around the `csprng_bytes()`/`git_rand()` interface in wrapper.c. The proposed flag would allow callers to specify when pseudo-randomness is acceptable, particularly for non-security-sensitive operations like generating temporary filenames.
