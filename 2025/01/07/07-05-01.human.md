Performance optimization follow-up: readability improvement for LSan leak detection.

This is the first of three post-merge patches refining the LSan (LeakSanitizer) race condition fixes that were recently merged. Jeff King proposes an inversion of the return value logic in the leak-checking function to make the code more intuitive. The function previously returned success (0) when no leaks were found, requiring awkward negation in the shell pipeline. Now it returns success when leaks are detected, which better matches the natural flow of the code.

The change renames the function from `check_test_results_san_file_empty_` to `check_test_results_san_file_has_entries_` to reflect its new behavior. The implementation remains essentially the same - it still uses the same `find | grep` pipeline to scan for leaks while filtering out known false positives - but the logic is now more straightforward. Callers continue to use negation where appropriate (`! check_test_results_san_file_has_entries_`), but this reads more naturally than the previous double-negative style.

This appears to be a clean, well-motivated change that improves code readability without altering the underlying functionality. It's part of the ongoing effort to make the LSan solution more maintainable after the core technical work was completed. The patch is small and focused, touching just two files with minimal changes to the actual logic.
