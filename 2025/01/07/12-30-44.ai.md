This is a test fix addressing a flaky SIGPIPE test in the submodule subsystem. The patch is part of a larger series (v3 02/10) focused on CI fixes.

The test in t7422 checks whether `git submodule status --recursive` properly propagates SIGPIPE signals when its output pipe is closed early. The original implementation was unreliable because it relied on grep terminating the pipe after seeing one line of output, which could race with the subprocess's buffered output. The test would sometimes pass (when the pipe closed mid-output) and sometimes fail (when the subprocess finished before the pipe closed).

The fix creates a stress test scenario by generating 2000 nested submodules, ensuring the subprocess's output buffer fills completely. This forces the SIGPIPE to occur reliably when grep terminates the pipe after matching the first submodule path. The commit includes a helpful diff showing how the original test could be modified to reliably demonstrate the race condition.

Key technical details:
- Modifies t/t7422-submodule-output.sh
- Introduces a complex test setup with 2000 generated submodules
- Uses git plumbing commands (hash-object, mktree, commit-tree) to create the test repository
- Maintains the same test assertions (empty stderr, exit code 13/SIGPIPE)
- Acknowledges help from Jeff King (peff)

The solution appears well-considered and addresses the root cause of the flakiness rather than just masking symptoms. The extensive test setup suggests this was a tricky race to trigger reliably, but the approach seems sound for forcing buffer saturation.
