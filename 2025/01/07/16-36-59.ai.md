This is a discussion about the removal of deprecated remote configuration mechanisms, specifically focusing on backward compatibility concerns with legacy scripts.

Junio Hamano responds to Patrick Steinhardt's assertion that `git remote` has completely replaced the old `.git/branches/` and `.git/remotes/` configuration mechanisms. While acknowledging Patrick's point about current usage patterns, Junio raises an important concern about backward compatibility - legacy scripts from "ancient days" may still rely on these mechanisms regardless of modern practices.

The key technical concern is that silent removal could break existing automation. Junio strongly reiterates his earlier suggestion (previously endorsed by Christian Couder) to implement warning checks in remote.c when these legacy configuration paths are accessed. This would mirror the approach taken with `pack-redundant` removal, where explicit warnings and migration instructions were provided before complete removal.

The discussion shows alignment on the technical implementation path (adding warning infrastructure in remote.c) while highlighting different perspectives on the urgency of removal. Junio's response emphasizes the project's responsibility to existing users, even when removing features deprecated for 14-20 years. This maintains the thread's focus on careful, well-communicated deprecation strategies as part of the broader breaking changes infrastructure work.
