Thread summary:

Vadim Zeitlin's proposal to add configuration allowing symlinked submodules has progressed from conceptual approval to implementation details. The feature would relax Git's current validation requiring submodule paths to be directories (not symlinks), addressing a legitimate workflow need for shared submodules across projects/worktrees in trusted environments. brian m. carlson provided technical guidance on implementation via `validate_submodule_path` modification with config-controlled behavior, while Junio Hamano highlighted bootstrapping considerations for initial configuration.

In the latest update, Zeitlin confirms Hamano's suggested two-step clone-then-configure workflow is acceptable for this niche use case, eliminating the need for special clone support. The primary remaining open question is the configuration option name, with Zeitlin proposing `safe.submodules` (acknowledging inconsistency with existing safe.* options) or `submodule.validate` for feedback. Technical implementation remains focused on modifying `validate_submodule_path` with config-controlled behavior, likely storing state in struct repository.

Key unresolved items include final option naming decision (`safe.submodules` vs `submodule.validate` being the current candidates), patch submission (Zeitlin indicates intent to prepare soon), and documentation covering both the configuration option and recommended usage patterns. The security-workflow tradeoff remains framed as an opt-in relaxation for trusted environments, continuing Git's broader conversation about balancing hardening with practical needs. Implementation will involve changes to `validate_submodule_path` and potentially struct repository for config state, with no planned modifications to clone machinery.
