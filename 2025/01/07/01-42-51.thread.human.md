The thread began with Randall Becker reporting a test failure in Git 2.48.0-rc2 where the reftable backend's concurrent ref update test (t0610.47) was failing on ia64 systems with "fatal: unable to get random bytes" errors. The issue appears specific to ia64's PRNGD implementation when under heavy concurrent load, causing some ref updates to be aborted.

Patrick Steinhardt investigated and found the problem stems from two places in the reftable code that generate random numbers - one for temporary filenames and another for stack reloading. The core issue is that the code always requests cryptographically secure random numbers, which can exhaust the entropy pool on ia64 systems during high-load scenarios. This isn't a new bug introduced in 2.48.0, but rather a preexisting condition that's more likely to surface on certain architectures.

Patrick proposed a solution that would allow callers to specify when insecure random numbers are acceptable (like for temporary filenames), demonstrated through a draft patch adding a `CSPRNG_BYTES_INSECURE` flag. However, he noted this isn't urgent for the 2.48.0 release since the failure is rare and doesn't cause data corruption - it just aborts operations when entropy is low. The discussion has identified the key technical components involved and a potential path forward for a more robust solution.
