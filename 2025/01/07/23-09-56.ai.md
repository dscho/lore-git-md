This is a security/feature discussion regarding submodule path validation. Brian m. carlson responds favorably to Vadim Zeitlin's proposal for a config option to disable Git's symlink validation for submodule paths, which was introduced as a security hardening measure in e8d0608944.

The response acknowledges the legitimate workflow use case where symlinked submodules save disk space and initialization time for large repositories shared across multiple projects. Brian notes this aligns with recent discussions about balancing security hardening with practical workflow needs, suggesting the security list may not always be the best venue for such defense-in-depth measures that can break existing setups.

Technically, Brian outlines a straightforward implementation path involving a new global variable (or repository struct field) to control the validation behavior, to be set via config and checked in `validate_submodule_path`. Documentation would be required for the new option. While not committing to implement it themselves, they indicate the change would be reasonable and provide implementation guidance for anyone interested in submitting a patch.

The response moves the discussion forward by providing core team validation of the concept while leaving the actual implementation open for contribution. Key technical points include the config-controlled validation toggle and the specific function (`validate_submodule_path`) that would need modification. The security versus usability tradeoff is framed as part of an ongoing conversation about Git's hardening approach.
