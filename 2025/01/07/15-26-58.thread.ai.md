Reftable entropy handling bugfix series (v2) addressing OpenSSL CSPRNG failures when system entropy is exhausted, now at design philosophy crossroads. Patrick Steinhardt's two-part solution (general CSPRNG infrastructure + reftable application) faces Junio Hamano's refined architectural objections despite technical validation from Randall Becker on NonStop systems.

Core changes and status:
- Part 1 (accepted) modified Git's cryptographic random number generation with `CSPRNG_BYTES_INSECURE` flag in `csprng_bytes()`
- Part 2's reftable application (temporary filenames/retry delays) now contested by Junio on dependency boundary grounds after clarifying the code already used `git_rand()`
- Randall Becker's input confirmed OpenSSL's PRNGD server failures on ia64 NonStop under load
- Junio suggests either reverting to standard `rand()` where possible or considering constant values if randomness isn't critical

Technical specifics:
- OpenSSL properly detects insecure state via `RAND_pseudo_bytes()`
- Reftable changes maintain mathematical behavior (`UINT32_MAX` for delays)
- Two specific use cases in reftable/stack.c under scrutiny:
  1. Retry delay calculation (randomness spreads out retries)
  2. Temporary filename generation (randomness prevents collisions)
- Junio questions whether perfect randomness is required for these non-cryptographic purposes

Key positions:
- Patrick Steinhardt: Comprehensive solution addressing real test cases with security boundaries
- Randall Becker: Validates fix works on affected systems, reveals PRNGD fragility
- Junio Hamano: Accepts CSPRNG changes but strongly opposes reftable use, preferring:
  - Standard library (`rand()`) for non-crypto needs
  - Possibly constant values if randomness isn't critical
  - Pushing back on platforms with broken implementations ("fix your rand(3)")

Open questions:
- Architectural: Should reftable maintain stricter isolation from Git's CSPRNG infrastructure?
- Practical: Are constant values or `rand()` sufficient for reftable's non-crypto randomness?
- Platform policy: Should Git work around PRNGD/server entropy issues or require platforms to fix implementations?
- Detection value: Does the PRNGD overload visibility justify the solution's architectural impact?

The discussion has evolved from technical validation to core design philosophy, with Junio drawing a clear boundary around reftable's dependencies. While the technical solution works, its architectural fit remains contested between comprehensive platform coverage and subsystem isolation principles. The path forward hinges on whether reftable's randomness needs justify crossing the dependency boundary Junio seeks to maintain.
