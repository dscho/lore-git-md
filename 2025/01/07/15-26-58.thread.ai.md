Reftable entropy handling bugfix series (v2) addressing OpenSSL CSPRNG failures when system entropy is exhausted. Author Patrick Steinhardt's two-part solution is now complete: part 1 modified Git's cryptographic random number generation infrastructure to allow insecure fallback, and part 2 applies this to reftable temporary filenames and retry delays.

Core changes:
- Part 1 (already reviewed) added `CSPRNG_BYTES_INSECURE` flag to `csprng_bytes()` interface (in `wrapper.h`), allowing opt-in to less secure random bytes when system entropy is exhausted
- OpenSSL implementation switched from `RAND_bytes()` to `RAND_pseudo_bytes()` to properly detect insecure state
- Part 2 modifies reftable stack to use insecure mode for two specific cases: retry delays during stack reloads and temporary filename generation
- All existing non-reftable callers maintain current secure-only behavior (passing `0`)

Technical specifics:
- Platform-by-platform analysis in part 1 covers OpenSSL (`RAND_pseudo_bytes`), arc4random, getrandom, and getentropy behaviors
- Reftable changes maintain same mathematical behavior (using `UINT32_MAX` instead of `RAND_MAX` for delay calculation)
- Explicit security boundary maintained - insecure mode must be opted into at each call site
- Real-world failure scenario documented where concurrent test processes exhaust entropy on NonStop systems using OpenSSL

Security considerations:
- Thorough commit messages justify flag-based approach over silent fallback
- Reftable tempfile naming and retry delays identified as safe use cases for insecure bytes
- Original security concerns about deprecated `RAND_pseudo_bytes()` addressed through explicit opt-in
- No behavior change for non-OpenSSL platforms
