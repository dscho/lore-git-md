This is the second part of Patrick Steinhardt's reftable entropy handling bugfix series, applying the new insecure random bytes capability introduced in part 1 to the reftable stack implementation. The patch addresses test failures observed when multiple processes exhaust the system entropy pool during reftable operations.

The changes modify two specific reftable use cases that don't require cryptographic randomness: retry delays during stack reloads and temporary filename generation. Both call sites are updated to use the new `CSPRNG_BYTES_INSECURE` flag. The commit message provides a detailed reproduction scenario showing how concurrent test processes were failing when the entropy pool was exhausted on NonStop systems using OpenSSL.

Key technical details:
- Updates `reftable_stack_reload_maybe_reuse()` to use insecure random bytes for calculating retry delays
- Modifies `format_name()` to use insecure bytes for temporary filename suffixes
- Maintains the same mathematical behavior (using `UINT32_MAX` instead of `RAND_MAX` for the delay calculation)
- References the part 1 changes that made this possible by introducing the opt-in insecure mode

The patch appears well-contained and directly applies the infrastructure from part 1 to solve a concrete problem. The security implications are minimal since these were already non-cryptographic uses of randomness, and the change makes the system more robust under heavy load. The commit message thoroughly documents the motivation and includes a real-world failure report.
