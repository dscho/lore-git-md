This is a technical discussion about ref-filter API design between René Scharfe and Jeff King, continuing their debate about memory management for ahead-behind and is-base calculations in Git's ref-filter subsystem.

The email responds to Jeff King's proposal for an alternative solution that uses explicit parameter passing of ref_format structs rather than static variables. René acknowledges the technical merits of both approaches but raises deeper architectural concerns about the separation of concerns between used_atom and the string_lists that store committish references.

- Questions the atomicity of "ahead-behind", suggesting it might be better split into separate ahead/behind atoms with numeric sorting
- Explains his earlier approach using explicit ref_format passing (similar to Jeff's proposal) did work but didn't address the root issue of separated data structures
- Raises architectural questions about whether ref_format is the right home for these components, mentioning struct ref_filter or a new dedicated struct as alternatives
- Notes that moving used_atom (currently static) would be painful regardless of approach
- Leaves the door open to either solution, suggesting he could resubmit his original patch if there's consensus to move the data elsewhere soon

The discussion remains focused on long-term API design tradeoffs rather than immediate fixes, with both contributors acknowledging technical validity of each other's approaches while maintaining their preferred directions. The core tension remains between immediate code simplicity (René's static variables) versus future lib-ification needs (Jeff's explicit parameters). No new technical solutions are proposed in this message - it primarily responds to and reflects on the alternatives already presented in the thread.
