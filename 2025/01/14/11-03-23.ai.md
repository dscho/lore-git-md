Build system refactoring addressing fuzzer build issues with `common-main.o` and multiple `main()` definitions. Jeff King proposes a more fundamental solution than the current `--allow-multiple-definition` workaround by restructuring how `common-main.o` is included in fuzzer builds. The key changes would: 1) Split `GITLIBS` into separate variables for program vs library dependencies, 2) Exclude `common-main.o` when building with fuzzing engines (which provide their own `main()`), and 3) Maintain the dummy `main()` for test-compile fuzzers. This would eliminate the need for the problematic linker flag while preserving all build scenarios. The proposal notes two required follow-up fixes: moving `common_exit()` functionality into `libgit.a` and properly detecting when to include the dummy `main()`. This approach appears more architecturally sound than the current solution, though it requires careful handling of the transitional state where `common-main.o` contains both `main()` and other shared functionality. The changes would affect the core build system (`Makefile`) and fuzzer build logic, with potential implications for any platform-specific build configurations that currently rely on the multiple-definition behavior.
