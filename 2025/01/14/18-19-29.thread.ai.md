[Security] ANSI escape sequence injection in Git's sideband channel (CVE-2024-32002, CVE-2024-52005/GHSA-7jjc-gg6m-3329). Johannes Schindelin's implementation provides configurable sanitization via `sideband.allowControlCharacters` with evolving granularity (boolean values, string values for ANSI color sequences, extended to comma-separated values for cursor/erase sequences), plus per-URL configuration via `sideband_apply_url_config()`. Core sanitization in `strbuf_add_sanitized()` validates against policy without allocations.

The mature v5 series has production validation in Git for Windows (1+ year) and Red Hat (6+ months), with technical reviews confirming implementation soundness. Current defaults permit color sequences while requiring explicit opt-in for higher-risk sequences like cursor movement and erase commands. Junio C Hamano now opposes these security-hardening defaults, advocating for no filtering by default (historical behavior) based on concerns about GitHub/Red Hat deployment breakage and legacy character encodings (IEC/ISO 2022:1994). This represents a maintainer override of the security team's position despite production validation.

Schindelin maintains terminal escape injection requires safe-by-default behavior, arguing even trusted remotes can be compromised. brian m. carlson supports Junio's opt-in position citing SSH precedents and GitHub pre-receive hook compatibility. D. Ben Knoble's "swiss cheese" security model argument and Patrick Steinhardt's URL-specific whitelisting proposal remain technically valid but now face maintainer opposition. The implementation allows URL-specific overrides (`sideband.<url>.allowControlCharacters`) though Junio rejects the middle ground of allowing colors while blocking other sequences as arbitrary.

Test coverage in `t/t5409-colorize-remote-messages.sh` verifies all sequence types and URL-specific behavior. Documentation warns about server trust boundaries while explaining configuration options. Technical implementation is uncontested; debate now centers on maintainer preference for backward compatibility over security hardening, with Junio explicitly rejecting both the current production-validated defaults and the security team's recommendations.
