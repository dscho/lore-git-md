[Security] ANSI escape sequence injection in sideband channel (CVE-2024-32002, CVE-2024-52005/GHSA-7jjc-gg6m-3329). Johannes Schindelin's implementation provides configurable sanitization via `sideband.allowControlCharacters` (boolean/string/comma-separated values for color/cursor/erase sequences) with per-URL configuration via `sideband_apply_url_config()`. Core sanitization in `strbuf_add_sanitized()` validates without allocations, replacing control characters with caret notation (e.g., `^[` for escape sequences) to prevent terminal state corruption and input buffer injection attacks.

The mature v5 series (rebased to v2.53.0 in v4) had production validation in Git for Windows (1+ year) and Red Hat (6+ months) with secure defaults permitting colors while requiring opt-in for higher-risk sequences. Current implementation affects all sideband output including error messages from remote operations like `git clone`, with test coverage in `t/t5409-colorize-remote-messages.sh` verifying color sequence sanitization from pack-objects hooks.

Junio C Hamano's maintainer override reverts to unfiltered behavior by default in current versions, removing the `default` keyword that enabled basic color filtering. Schindelin's v4 positions secure-by-default behavior as a breaking change for Git 3.0 while maintaining opt-in security in 2.x series (`sideband.allowControlCharacters=color` required for previous behavior). The debate centers on security philosophy (secure-by-default vs backward compatibility) with:
- Schindelin strongly opposing opt-in approach, arguing terminal emulators cannot distinguish legitimate from malicious sequences
- brian m. carlson supporting opt-in model citing SSH precedents
- D. Ben Knoble's "swiss cheese" security model and Patrick Steinhardt's URL whitelisting proposals remaining valid but overridden

Implementation allows future policy changes while current defaults shift security responsibility to end users. URL-specific overrides (`sideband.<url>.allowControlCharacters`) remain supported but discouraged. Schindelin seeks security expert input on sanitizing untrusted input before interpreter exposure, with the technical foundation now established for both immediate protection and potential future default behavior changes in Git 3.0.
