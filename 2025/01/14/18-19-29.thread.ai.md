[Security] ANSI escape sequence injection in sideband channel (CVE-2024-32002, CVE-2024-52005/GHSA-7jjc-gg6m-3329). Johannes Schindelin's implementation provides configurable sanitization via `sideband.allowControlCharacters` with per-URL configuration through `sideband_apply_url_config()`. Core sanitization in `strbuf_add_sanitized()` validates without allocations, replacing control characters with caret notation (e.g., `^[` for escape sequences) to prevent terminal state corruption and input buffer injection attacks.

The mature v5 series (rebased to v2.53.0 in v4) had production validation in Git for Windows (1+ year) and Red Hat (6+ months). Latest patches introduce nuanced control with URL-scoped configuration via `sideband.<url>.allowControlCharacters` mirroring Git's `http.<url>.*` pattern, default behavior allowing ANSI color sequences (`\033[31m` etc) via `ALLOW_ANSI_COLOR_SEQUENCES`, and new bitmask flags for cursor movements (`ALLOW_ANSI_CURSOR_MOVEMENTS`), erase sequences (`ALLOW_ANSI_ERASE`), and full passthrough (`ALLOW_ALL_CONTROL_CHARACTERS`).

Junio Hamano's review raises multiple fundamental concerns: (1) criticizes version-dependent defaults as poor UX, advocating explicit user choice; (2) suggests testing opt-in mechanisms before flipping defaults; (3) challenges the whitelist security model, proposing instead to blacklist known-dangerous sequences while allowing others by default. His latest feedback provides a concrete example of legitimate functionality broken by current design - terminal title updates using ESC ] 0; <string> BEL sequence, which he uses in his workflow to monitor long-running processes from other terminal tabs. This strengthens his earlier position that some users legitimately need non-color control characters (including ISO/IEC 2022 encoding sequences in multilingual environments), suggesting the current approach forces an unnecessary security/functionality tradeoff.

The review follows Junio's earlier technical input about ISO/IEC 2022 encoding collisions, which can switch back to ASCII despite "remote: " prefix, making security implications more substantial than initially assessed. His perspective as maintainer carries significant weight, indicating the implementation may need significant redesign - either reworking the configuration approach or reconsidering the fundamental security model from whitelist to blacklist. The terminal title use case demonstrates that the current whitelist is too restrictive for practical workflows.

Current implementation in v4 introduces conditional compilation via `WITH_BREAKING_CHANGES` to toggle between permissive (current) and secure (future) defaults, with URL-specific overrides (`sideband.<url>.allowControlCharacters`). Test coverage in `t/t5409-colorize-remote-messages.sh` verifies behaviors through `TURN_ON_SANITIZING` prerequisite.
