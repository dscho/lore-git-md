This thread explores whether `git replace` should respect `GIT_NAMESPACE` boundaries, after Josh Bleecher Snyder observed that replacement objects created in one namespace affect operations in others - contrary to the isolation normally provided by namespaces. 

Christian Couder provided historical context, noting that replace refs were originally discussed as a way to create different repository "views" (like timestamp-fixed versions), but their interaction with namespaces hasn't been considered before. He observed that namespaces are primarily a server-side feature often paired with alternates, and servers typically disable replacement refs. This suggests the current behavior may stem from these features not being designed to work together, rather than being an intentional design choice.

The discussion remains open, with key questions still unanswered: Should replacements be namespace-scoped like other refs? If this is a bug, would fixing it require code changes or just documentation updates? Christian's response adds useful background but doesn't take a position on how to resolve the issue. So far, no patches have been proposed - the thread is still in the investigation phase, establishing whether this behavior is expected or needs changing.
