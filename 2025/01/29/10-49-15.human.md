Feature proposal: pre-checkout hook for branch validation

Mike Weltevrede proposes adding a `pre-checkout` hook to complement the existing `post-checkout` hook. The key motivation is enforcing branch naming policies before the checkout occurs, preventing users from accidentally working on improperly named branches. Currently, they're using a combination of `post-checkout` (which runs after the fact) and `pre-push` (which catches the issue too late), but neither provides the ideal user experience of preventing the invalid checkout entirely.

The email raises an interesting architectural question - why doesn't Git already have this hook when it has similar pre-operation hooks for commit and push? Mike acknowledges this might be a deliberate design choice and is curious about the reasoning. The proposal is at an early stage, presented as an idea rather than a concrete implementation.

This touches on Git's hook system design philosophy and could spark discussion about where validation should happen (client-side hooks vs. server-side enforcement) and whether checkout-time validation aligns with Git's principles. The use case seems legitimate for teams wanting to enforce naming conventions, though the mailing list may debate whether this belongs in core Git or should be handled via other means.
