Martin von Zweigbergk (Jujutsu VCS) examines an edge case in Git's histogram and patience diff algorithms where lines with differing counts between file versions are matched as unchanged. The test case shows a line "c" appearing once in original vs twice in modified file (`a,b,c,d,e,f` → `a,b2,c,d2,c,e2,f`), with Git's histogram diff matching the first "c" as unchanged despite the count mismatch. This behavior contrasts with Jujutsu's implementation which initially allowed but later restricted such matches (jj-vcs/jj#761) due to perceived arbitrariness. The email questions whether Git's behavior is intentional design or an accidental fallback to Myers diff, noting the algorithm's documented preference for matching unique lines (count=1) first. The discussion probes subtle tradeoffs in diff algorithm behavior that affect line matching precision, with implications for both Git and alternative VCS implementations that may rely on these edge cases. No resolution or Git maintainer response yet recorded. Technical focus remains on the diff.c implementation details and whether the observed behavior constitutes a bug or intentional heuristic.
