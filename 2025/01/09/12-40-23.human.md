This is a follow-up discussion on a bugfix for `git blame`'s handling of large `--abbrev` values. The original issue involved an out-of-bounds read when using `fwrite` for OID emission, which was fixed by reverting to `printf` with length truncation. The v2 patch addressed alignment issues with special commit markers (^, *, ?) and improved test coverage.

Shejialuo's email raises an interesting usability point: it seems odd that Git even accepts `--abbrev` values larger than the maximum possible hash length (`GIT_MAX_HEXSZ`). While the technical fix is sound (explicitly capping the length before `printf`), the comment suggests there might be room for improving the user interface by either warning about or rejecting absurdly large values upfront.

The discussion shows the patch has already gone through careful review, with Johannes Schindelin identifying both the original buffer safety issue and test coverage problems. The current solution appears robust, handling both security concerns and formatting edge cases. Shejialuo's observation about the interface design could spark further discussion about input validation, though the immediate buffer safety issue is properly addressed.
