The thread examines a regression in `git fetch` where tags pointing to shallow boundary commits weren't being fetched with `--depth=1`, first appearing between Git 2.47.1 and 2.48.rc0. Danila Manturov originally reported the issue, which Bence Ferdinandy traced to protocol-specific behavior - it occurs with native SSH/HTTPS transports but works correctly with JSch.

Bence proposed a fix that reorders tag/HEAD prefix additions in `do_fetch()`, moving HEAD before tags, which Danila confirmed resolves their use case. In the latest email, Bence provides a technical analysis showing the current code's conditional tag addition (only when `ref_prefixes` is empty) fails because HEAD is always added first. While the reordering works, it feels like a band-aid solution, and questions remain about why the original design used this conditional approach and why reordering works when a direct fix doesn't.

The discussion has progressed from identifying the regression to understanding its transport-specific nature and developing a working solution, though concerns persist about whether this addresses the root cause or merely masks deeper issues in how different protocols handle prefix ordering. Key technical aspects under examination include `transport_ls_refs_options.ref_prefixes` manipulation and the `uses_remote_tracking()` check.
