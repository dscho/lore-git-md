This is a bug report and discussion starter about the behavior of Git's histogram diff algorithm when matching lines with different counts between file versions. Martin von Zweigbergk observes that when a line appears once in the original file but twice in the modified version, Git's histogram diff still matches them as unchanged, which seems counterintuitive to the algorithm's stated approach of first matching unique lines.

The email includes a clear minimal test case showing this behavior, where line "c" appears once in the original but twice in the modified file, yet is still matched as unchanged in the diff output. Martin questions whether this is intentional behavior or perhaps a fallback to Myers diff algorithm, noting that his own VCS project (Jujutsu/jj) initially allowed such matches but later changed this behavior after user reports of inconsistency with Git.

The email invites discussion from Git maintainers about whether this behavior is correct or should be changed. It's a well-presented issue with clear reproduction steps and context about how other tools handle similar cases, making it easy for maintainers to evaluate whether this warrants a behavior change in Git's diff algorithm.
