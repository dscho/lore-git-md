Git grep EOF matching inconsistency: A bug report identified that `git grep '^$'` incorrectly matches at end-of-file (reporting line number N+1 for an N-line file), diverging from standard grep behavior. Jeff King's investigation traced this to a 2010 merge (34349bea60) that introduced lookahead code in `builtin-grep.c`, removing an empty-file check and adding a null terminator, combined with line-skipping optimizations (a26345b608). The discussion has produced three solution approaches: 1) King's original boundary check in `grep.c`'s `look_ahead()` to skip matches at buffer end (where `m.rm_so == *left_p`), 2) Andreas Schwab's `REG_NOTEOL` flag proposal using POSIX regex extensions, and 3) King's newer trailing-newline stripping approach. 

Key technical findings show `REG_NOTEOL` fixes the original case but breaks legitimate end-of-line matches (like `t$`) in files without trailing newlines, while newline stripping would make buffer ends consistently represent line ends. The core challenge remains maintaining standard grep behavior across three file scenarios: files with/without trailing newlines, and their interaction with different regex patterns (`^$`, `t$`). PCRE (`-P` flag) already behaves correctly. The thread has clearly identified the 2010 regression's effects and now weighs implementation tradeoffs between boundary checks, regex flags, and input normalization approaches to resolve the long-standing compatibility issue.
