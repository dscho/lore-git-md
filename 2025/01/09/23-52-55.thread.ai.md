Git grep EOF matching inconsistency: A bug report identified that `git grep '^$'` incorrectly matches at end-of-file (reporting line number N+1 for an N-line file), diverging from standard grep behavior. Jeff King's investigation revealed the issue stems from a 2010 merge (34349bea60) that introduced lookahead code in `builtin-grep.c`, removing an empty-file check and adding a null terminator. The bug involves uninitialized memory access that was coincidentally working until the merge, combined with line-skipping optimizations from a26345b608.

King has proposed a fix adding a boundary check in `grep.c`'s `look_ahead()` function to explicitly skip matches at buffer end (where `m.rm_so == *left_p`), preventing false positives for `^$` patterns. The patch addresses the core issue where non-PCRE regex engines may spuriously match empty strings after the last newline, while maintaining compatibility with standard grep behavior. Andreas Schwab has suggested an alternative approach using the `REG_NOTEOL` flag in the regex matcher to prevent end-of-line anchor matching at buffer end, which would provide a more standardized solution through POSIX regex extensions rather than boundary checks.

Technical details include: the fix targets zero-width matches in multi-line buffer processing (not per-line `match_line()` handling); PCRE (`-P` flag) already behaves correctly; and the discussion now includes tradeoffs between boundary check versus regex flag approaches. The core issue has been clearly identified, with two potential solution paths available - King's boundary check in lookahead logic versus Schwab's proposed `REG_NOTEOL` flag usage in regex handling. Both approaches would resolve the compatibility divergence that has persisted since 2010, with implementation tradeoffs to be considered.
