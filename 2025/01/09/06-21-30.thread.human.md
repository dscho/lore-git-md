This thread addresses a subtle bug in `git blame`'s handling of object ID output when using large `--abbrev` values, which could lead to out-of-bounds reads. The issue stemmed from a change that switched from `printf` to `fwrite` for OID emission. Patrick Steinhardt initially fixed it by reverting to `printf` with a length cap, but Johannes Schindelin pointed out this broke alignment for special commits (marked with ^, *, ? prefixes) and the test case wasn't properly verifying the issue.

The discussion has refined the solution further. Steinhardt now proposes moving the length check after the prefix handling, which would simplify the fix by eliminating the need for a buffer size adjustment while still preventing overreads. There's also agreement that the test should verify that absurdly large abbrev values (like 9000) get properly truncated to the hash algorithm's size, rather than passing through unchanged.

The changes affect OID output in `builtin/blame.c` and are verified in `t/t8002-blame.sh`, with the behavior being more noticeable in SHA-256 mode due to its longer hash size. The thread shows careful attention to both security (preventing buffer overreads) and maintaining expected formatting in edge cases, with active participation from key contributors Steinhardt and Schindelin.
