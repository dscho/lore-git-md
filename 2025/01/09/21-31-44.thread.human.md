This thread examines an edge case in Git's diff algorithms, where lines with differing counts between file versions are sometimes matched as unchanged. Martin von Zweigbergk (Jujutsu VCS) initiated the discussion by comparing Git's behavior with their implementation, noting that Git's histogram diff matches a line ("c") as unchanged even when its count differs between versions (one "c" in original vs. two in modified).

The test case shows `a,b,c,d,e,f` becoming `a,b2,c,d2,c,e2,f`, where Git treats the first "c" as unchanged despite the duplicate in the modified version. This contrasts with Jujutsu's approach, which initially allowed but later restricted such matches due to concerns about arbitrary behavior. The discussion probes whether Git's handling is intentional design or an algorithmic fallback to Myers diff, with implications for tools relying on precise line matching. The thread may explore tradeoffs between strict matching rules and practical diff quality across VCS implementations.
