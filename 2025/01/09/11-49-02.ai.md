This is a bug report regarding changed behavior in `git fetch` with shallow clones between Git 2.47.1 and 2.48.rc0. The reporter, Danila Manturov, works on TeamCity's Git integration tests and noticed that tags are no longer being fetched with shallow clones in the newer version.

The issue is demonstrated with a minimal test case using a GitHub repository containing two tags (tag1 and tag2) on different commits. With Git 2.47.1, a shallow fetch (`--depth=1`) would include the tag pointing to the most recent commit (tag1), but in 2.48.rc0 this behavior has changed and no tags are fetched. The reporter suspects this regression was introduced by commit 5f212684abb66c9604e745a2296af8c4bb99961c.

The repository structure shows tag1 on the most recent commit and tag2 on the initial commit, making it clear this isn't just about tags on non-shallow commits. The report includes complete reproduction steps and version comparison, suggesting this is a well-investigated issue that could affect users relying on shallow fetch behavior for tags.

For AI context: The key technical details are the `--depth=1` shallow fetch no longer retrieving tags that point to the shallow boundary commit, which worked in 2.47.1. The regression appears in 2.48.rc0 and is potentially linked to commit 5f212684abb (though the reporter doesn't analyze why that commit might cause this). The test repository shows this affects tags on the shallow boundary commit itself, not just deeper history.
