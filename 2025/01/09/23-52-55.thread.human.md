The thread began with a report that `git grep '^$'` incorrectly matches at the end of files, showing line N+1 for an N-line file, while standard grep doesn't. Jeff King traced this to a 2010 change in the grep code that introduced lookahead logic while removing an empty-file check. The bug had gone unnoticed because it involved subtle memory behavior that happened to work until now.

King has now followed up with a fix that addresses the core issue. His patch modifies the `look_ahead()` function in `grep.c` to explicitly skip matches occurring exactly at the buffer end, preventing the regex from matching the empty string after the final newline. The solution is minimal and maintains compatibility with standard grep behavior while working around quirks in certain regex engines. Notably, the issue doesn't appear when using PCRE (-P flag) or when bypassing the look-ahead optimization.

The fix preserves the existing optimization structure while properly handling this edge case that's been present since 2010. This resolves a genuine behavioral divergence from standard grep that had persisted across Git versions for over a decade.
