This is a follow-up in the ongoing reftable/RNG discussion thread, where Junio Hamano is responding to Patrick Steinhardt's position on random number generation in the reftable stack.

The email focuses on a specific technical point from the previous discussion: whether the reftable stack's use of `git_rand()` for generating temporary filenames and backoff delays could be replaced with simpler alternatives. Patrick confirms there are no correctness implications if the random values become predictable - the worst case would be increased contention, but the system would still function properly. The key technical detail is that the reftable's update indices already provide sufficient uniqueness even without random suffixes.

Junio suggests two possible simplifications: either using the system's `rand()` function (which would be more reliably tested across platforms) or even hardcoding a constant value. This would both address the immediate OpenSSL CSPRNG issues on ia64 systems and help reduce Git-specific dependencies in the reftable library. The discussion remains focused on the reftable-specific aspects while acknowledging the broader system-wide RNG problems that have emerged in the thread.
