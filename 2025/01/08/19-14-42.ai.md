This is part 4 of an 8-part refactoring series to clean up Git's hash algorithm handling by eliminating separate "unsafe" variants of hash operations. The patch introduces a new `unsafe_hash_algo()` function that provides access to a wrapped version of a hash algorithm struct, replacing the previous pattern of having separate `unsafe_` prefixed functions for each operation.

The key technical changes include:
- Adding an `unsafe` pointer field to `struct git_hash_algo` that points to the unsafe variant of the algorithm
- Implementing `unsafe_hash_algo()` in object-file.c to return either the unsafe variant (if available) or the original algorithm
- Defining a new `sha1_unsafe_algo` struct that implements all the unsafe SHA-1 operations
- Wiring up the unsafe SHA-1 variant to the main SHA-1 algorithm via the new `unsafe` pointer

The new approach allows callers to simply obtain the appropriate algorithm pointer once (safe or unsafe) and then use the standard function names (`init_fn`, `update_fn`, etc.) rather than having to remember to use different function names throughout their code. This eliminates the risk of mixing safe and unsafe operations accidentally.

The patch builds on the test infrastructure from earlier in the series and continues the groundwork for future hash algorithm flexibility. It represents a significant simplification of the API while maintaining backward compatibility. The implementation follows the pattern suggested by Jeff King in earlier discussion.
