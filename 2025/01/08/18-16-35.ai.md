This is a follow-up in the reftable/random number generation thread, specifically addressing the crash safety implications of random suffix generation. Patrick Steinhardt clarifies several key points about the reftable implementation's behavior when random suffixes collide:

1. Correctness vs. availability: Confirms that suffix collisions don't cause data corruption (contrary to Junio's concern), but could lead to temporary update failures (denial of service) until stale files are cleaned up. Demonstrates this with a forced collision test case using a hardcoded suffix value.

2. Windows-specific considerations: Notes that Windows' file locking behavior could exacerbate the issue, though recent rename-emulation improvements have mitigated this.

3. Platform-specific failures: Argues against switching to `rand()` as a solution for OpenSSL CSPRNG failures, maintaining this would be a regression (making suffixes predictable) while not solving the root issue. Suggests the ia64 failures may be environmental rather than fundamental.

Key technical details:
- References commit 9abda98149 fixing unseeded randomness
- Shows reftable can recover from collisions by creating new files
- Notes Windows edge case with open file deletion
- Points to other `git_rand()` callsites as potential failure points

The email reinforces Patrick's position that:
- The reftable implementation is robust against suffix collisions
- OpenSSL CSPRNG failures should be addressed at the root rather than worked around in reftable
- Platform-specific issues (ia64, NonStop) may have environmental factors

This moves the discussion forward by providing concrete evidence about collision behavior while maintaining skepticism about platform-specific failure modes being inherent to the RNG implementation.
