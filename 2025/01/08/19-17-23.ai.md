Bugfix targeting object ID output in `git blame`, with a behavioral regression concern.

This is part of Patrick Steinhardt's patch series addressing signed/unsigned comparison warnings in Git's codebase (v4 13/16). The specific patch fixes a `-Wsign-compare` warning in `builtin/blame.c` by changing how object ID lengths are handled during output. The original code used a mix of `int` and `size_t` for hash lengths, which could trigger compiler warnings. The patch adds a BUG() assertion to validate the abbreviation length and casts the value to `size_t` for consistency.

Johannes Schindelin points out a behavioral regression: while the original code using `printf()` would stop at NUL characters when printing abbreviated hashes, the new `fwrite()` version continues reading memory beyond the hash string if given an overly large abbreviation value (like `--abbrev=99999`). This could lead to out-of-bounds memory access. The issue demonstrates a subtle difference between printf's string handling and fwrite's binary-oriented behavior that wasn't caught in the initial patch review.

Key technical details:
- The change affects `emit_other()` in `builtin/blame.c`
- Involves the `abbrev` parameter and `OUTPUT_LONG_OBJECT_NAME` flag
- Switches from `printf("%.*s")` to `fwrite()` for output
- Maintains the same `MINIMUM_ABBREV` validation
- Part of broader warning-cleanup effort (note removal of `DISABLE_SIGN_COMPARE_WARNINGS`)

This appears to be a case where a well-intentioned warning fix introduced a subtle behavioral change that could have security implications. The thread will likely need to discuss whether to revert the change, add bounds checking, or find another way to handle the type conversion without the memory safety issue.
