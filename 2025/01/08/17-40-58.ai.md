This is a technical discussion about reftable's correctness requirements for random number generation, specifically addressing crash safety in the face of OpenSSL CSPRNG failures.

The email continues the thread's evolution from optimization concerns to recognizing randomization as a correctness requirement for reftable operations. Patrick Steinhardt explains a concrete crash scenario where predictable temporary file suffixes could lead to data corruption: if Git dies mid-transaction after moving a temp file but before updating the tables.list index, a subsequent process using the same suffix would fail. While reftable can clean up stale tables, it doesn't do so proactively on every write.

Junio Hamano expresses skepticism about relying on cryptographic randomness for correctness, drawing a parallel to hash collisions. The discussion highlights a tension between:
1. The newly understood need for unique suffixes to prevent corruption
2. The unreliability of OpenSSL's RAND_bytes() on some platforms
3. Philosophical concerns about correctness depending on randomness

Key technical points:
- The race condition makes suffix uniqueness critical for crash safety
- Current implementation uses git_rand() which depends on OpenSSL
- Alternatives like system rand() or constants may not provide sufficient guarantees
- The problem spans beyond reftable to any git_rand() usage

This moves the thread toward needing a solution that provides both:
- Sufficient randomness for crash safety
- Reliability across all supported platforms
- Minimal dependence on problematic RNG implementations

The discussion remains unresolved, with Junio questioning whether correctness should depend on randomness at all, while Patrick acknowledges the practical requirement revealed by the crash scenario.
