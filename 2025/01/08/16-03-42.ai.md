This is a discussion about submodule path validation, specifically regarding whether to add an option to disable the validation that prevents submodule paths from being symlinks. The thread stems from a regression where a previously working submodule setup (using symlinks) broke after commit e8d06089 introduced stricter path validation.

Junio Hamano expresses concerns about the interaction between this potential configuration option and Git's bootstrapping process, particularly how it would work during `git clone`. Vadim Zeitlin suggests the use case is special enough that the current workflow (cloning without `--recurse-submodules` and initializing later) is acceptable, though Junio notes this was reported as a regression from previously working behavior.

The discussion touches on naming the configuration option, with "submodule.validate=no" proposed as a possibility, though Junio defers to others for better naming suggestions. The validation currently only checks that submodule paths aren't symlinks, but the naming leaves room for potential future validation checks.

Key technical points include the specific commit (e8d06089) that introduced the validation, the chicken-and-egg problem of configuration during clone, and the question of whether this should be a standalone option or part of a more general submodule validation framework. The thread shows the Git maintainer seeking input from submodule users about real-world needs while being cautious about configuration design.
