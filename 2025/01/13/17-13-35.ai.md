This is a bugfix series addressing two object name resolution issues, with the second patch being a backward-incompatible change that tightens parsing rules for describe-like output.

The first patch fixes object name resolution when refs contain curly braces, addressing cases like `foo@{...}` and `foo^{/${SEARCH_TEXT_WITH_COLON}}:${PATH}`. The solution involves special handling when `@` or `^` precede curly braces, though the commit notes this may need revisiting if more curly brace usage patterns emerge.

The second and more significant patch enforces stricter validation of describe-like output formats (`${REFNAME}-${INTEGER}-g${HASH}`). Previously, Git would accept any garbage before the `-gHASH` portion, which could lead to incorrect object resolution (e.g., interpreting a path component as an object name). The new validation ensures both the refname portion and integer count are properly formatted. While this is technically a backward-incompatible change, the commit message argues it's necessary to prevent ambiguity and allow future naming extensions. The patch includes test cases demonstrating both the fixed behavior and edge cases like `v2.48.0-rc2-161-g6c2274cdbc^0`.

The series touches `object-name.c` and adds tests in `t/t1006-cat-file.sh` and `t/t6120-describe.sh`. The changes appear well-considered, with thorough commit messages explaining the rationale and potential impacts. The v3 iteration includes improved readability and additional test coverage for edge cases mentioned in previous discussion.
