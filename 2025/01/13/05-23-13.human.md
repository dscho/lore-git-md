This is a follow-up discussion in the ongoing thread about ref-filter memory management, specifically the interaction between sorting and formatting operations. Jeff King notes an edge case in `git ls-remote` where the current patch would require adding a `ref_format` struct, even though this command doesn't normally use formatting. 

He points out this isn't a major issue, but it surfaces a deeper problem: `ls-remote` with sorting atoms that require object access (like `authordate` or `ahead-behind`) can fail in confusing ways depending on local repository state. The command sometimes fails with a clear "not a git repository" error, but in other cases fails with missing object errors when it has partial access to objects.

While acknowledging this is separate from the immediate memory leak fix being discussed, King highlights how the current behavior leads to inconsistent sorting results for `ahead-behind` depending on what objects happen to be locally available. The observation doesn't propose a solution but flags an area where the ref-filter interface might need more robust handling of object access requirements.
