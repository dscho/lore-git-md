Bug report: `git bisect` performance issue on large repositories

Askar Safin reports that `git bisect old v3.0` takes an unacceptably long 21 minutes to run on the Linux kernel repository (with ~13 million objects). The operation appears to be CPU-bound, with `git bisect--helper` consuming 100% of a single core, suggesting no parallelization is being used.

The report includes detailed reproduction steps showing the bisect operation between v6.13-rc7 and v3.0 tags, which leaves 535,608 revisions to test. The test was performed on Debian 12 with Git 2.39.5 on real hardware with tmpfs storage.

While the report doesn't include comparative timings from other bisect operations or repositories, the 21-minute runtime for this common developer workflow on a major project clearly indicates a real performance pain point. The author suggests parallelization as a potential solution and promises follow-up tests with newer Git versions.

This appears to be a legitimate performance bottleneck that could significantly impact developers working with large repositories. The thorough reproduction details make it easy to verify, though additional context about whether this represents a regression or how it compares to other large repositories would be helpful.
