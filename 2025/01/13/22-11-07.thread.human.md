Askar Safin reported that setting up a bisect between v6.13-rc7 and v3.0 (spanning over 535,000 revisions) takes 21 minutes with CPU usage pegged at 100% on a single core. Testing shows the bottleneck is in `git bisect--helper` during the revision walking phase of bisect setup.

Follow-up testing with Git 2.47.1 confirms the issue persists, indicating this is a fundamental limitation in the current single-threaded implementation rather than a version-specific bug. The problem is particularly acute for massive histories like the kernel's (13 million objects, 87,000 files at HEAD). While the reporter has offered to do additional testing if needed, the existing data clearly shows the need for parallelizing the bisect setup phase to improve performance on large repositories. The thread establishes this as a concrete case where multi-threading the revision walking could provide significant speedups.
