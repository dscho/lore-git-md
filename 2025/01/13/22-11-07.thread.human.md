Here's a human-readable thread summary:

A performance issue has been reported with `git bisect` when used on very large repositories like the Linux kernel. The reporter found that running `git bisect old` between Linux versions v6.13-rc7 and v3.0 took 21 minutes while maxing out a single CPU core, suggesting inefficient single-threaded processing. The test was conducted on modern hardware with Git 2.39.5 running against a Linux repository containing over 535,000 revisions, 13 million objects, and 87,000 files at HEAD - all stored on tmpfs to eliminate disk I/O as a factor.

The bottleneck appears to be in `git bisect--helper`, which doesn't take advantage of potential parallelism despite the massive revision range. The reporter used the newer `new/old` bisect syntax (rather than traditional `good/bad`) and plans to test with a more recent Git version to see if the behavior improves. This highlights a scalability challenge for bisect operations on repositories with extremely long histories.
