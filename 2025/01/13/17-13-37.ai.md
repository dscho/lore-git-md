Bugfix addressing describe-like output validation in object name parsing. This is the second patch in a v3 series that tightens validation for `${REFNAME}-${INTEGER}-g${HASH}` patterns to prevent ambiguous object name resolution.

The patch introduces stricter parsing rules for describe-like output formats to avoid misinterpreting filenames containing `-gHASH` as object references. It adds a new `ref_and_count_parts_valid()` function that verifies the `${REFNAME}-${INTEGER}` portion matches Git's refname rules before accepting it as a describe output. This fixes cases where paths like `branchname:path/to/file/named/i-gaffed` could incorrectly resolve to object `affed` rather than the intended file.

The change is intentionally backward-incompatible, rejecting previously-accepted garbage prefixes before `-gHASH`. The commit argues this is necessary to maintain unambiguous object naming, especially given possible future relaxations of refname rules. Test cases verify both the desired behavior (proper file access) and rejection of malformed describe patterns.

Key technical details:
- New validation in `object-name.c` checks refname format and integer suffix
- Tests in `t6120-describe.sh` cover edge cases including nested modifiers
- Maintains compatibility with valid describe output like `v2.48.0-rc2-161-g6c2274cdbc^0`
- Fixes a real-world issue reported by Gabriel Amaral
- Follows up on earlier curly brace handling fixes in the series

The patch appears well-considered with thorough test coverage, though the backward incompatibility may need discussion. It completes the series' goal of tightening object name resolution while preserving legitimate use cases.
