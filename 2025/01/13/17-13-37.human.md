Bugfix tightening validation of describe-like object names. This is the second patch in a v3 series addressing object name resolution edge cases, following up on Junio Hamano's work.

The patch makes Git more strict when parsing describe-style revision names (format `${REFNAME}-${INTEGER}-g${HASH}`). Previously, Git would accept any garbage before the `-gHASH` portion, which could cause ambiguous cases like `branchname:path/to/file/named/i-gaffed` to be misinterpreted as referring to commit `affed` rather than the intended file. The code now validates that the portion before `-gHASH` consists of a valid refname followed by a dash and non-negative integer.

This is a deliberate backward-incompatible change, but the author argues it's necessary to prevent ambiguity and allow for potential future loosening of refname rules. The patch includes thorough test coverage, including cases with describe modifiers (e.g., `v2.48.0-rc2-161-g6c2274cdbc^0`) and edge cases with invalid refname characters.

The change appears well-considered, with clear motivation explained in the commit message and comprehensive test additions. It addresses a real-world issue reported by Gabriel Amaral while maintaining compatibility with legitimate describe output formats. The patch builds on the series' earlier work on curly brace handling while focusing specifically on the describe-format validation problem.
