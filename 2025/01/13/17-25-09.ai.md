This is a refactoring patch in the ongoing discussion about memory management in Git's ref-filter code, specifically addressing how ahead-behind and is-base calculations share state between formatting and sorting operations.

Junio C Hamano weighs in on Jeff King's proposed solution to explicitly pass the ref_format struct to sorting operations, rather than using static variables as in René Scharfe's approach. The patch modifies ref_sorting_options() to take a ref_format parameter, requiring updates to all callers (branch, for-each-ref, tag, and ls-remote commands). Notably, ls-remote gains a ref_format struct initialization/cleanup despite not using formatting features, maintaining API consistency.

Key technical changes include:
- ref_sorting_options() now requires ref_format parameter
- parse_sorting_atom() operates on provided format struct rather than dummy one
- All command callers updated to pass their format struct
- ls-remote gains format struct management despite not using formatting
- Sorting atom parsing now shares format state with formatting operations

The discussion highlights two competing approaches: Scharfe's simpler static variable solution versus King's more explicit parameter passing that better aligns with lib-ification goals. Hamano acknowledges King's approach may be more future-proof despite requiring more boilerplate, suggesting the project may be moving toward accepting this direction. The patch successfully passes existing tests while moving toward a more explicit API design.

This moves the thread toward resolution by demonstrating the explicit parameter approach is viable and not overly burdensome, though the final decision between approaches remains open. The ls-remote changes also surface broader questions about how object-dependent sorting should behave for remote operations, which may need separate consideration.
