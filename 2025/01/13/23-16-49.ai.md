Performance investigation of `git bisect` slowdown on large repositories. Askar Safin confirms their earlier findings about `git bisect old` performance issues on the Linux kernel repository persist in Git 2.47.1, showing the problem hasn't been addressed in recent versions. The original report demonstrated a 21-minute runtime for bisect setup between v6.13-rc7 and v3.0 (spanning 535,608 revisions) with CPU-bound behavior in `git bisect--helper`. 

The email notes the bisect implementation appears largely unchanged in newer Git versions, making further version testing unlikely to reveal different results unless specifically requested. This reinforces the core issue is a fundamental performance limitation in the single-threaded revision walking during bisect initialization, particularly problematic for massive histories like the Linux kernel's. The reporter remains willing to conduct additional testing if needed, but considers the current data sufficient to demonstrate the persistent bottleneck.

Key technical details for future reference: the problem manifests in `git bisect--helper` during the setup phase when processing hundreds of thousands of commits, with the Linux kernel repo serving as the test case (13M objects, 87k files at HEAD). The reporter uses the newer `old/new` terminology rather than traditional `good/bad`, though this doesn't affect the performance characteristics. The thread establishes this as a clear case where parallelizing revision walking could provide significant improvements for large repository workflows.
