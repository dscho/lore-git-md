This is a discussion about Git's config file handling and security implications. Jeff King (peff) responds to Randall Becker's inquiry about Git's behavior when system-wide and user config files/directories are missing. 

Peff clarifies that the core issue isn't the missing config files themselves (which would simply return no value), but rather the inability to create lock files in non-existent directories when writing configs. He explains this is expected behavior - Git intentionally doesn't auto-create system directories like `/usr/local/etc` as that's outside Git's scope and a packaging concern. For user configs, auto-creation could be problematic for system users without proper home directories.

The response suggests this is primarily a UX issue with unclear error messages rather than a bug. Peff proposes a small improvement to make lock file errors more descriptive, showing a patch that would surface the actual directory creation failure rather than just reporting a lock file problem. However, he notes this would only marginally improve the situation.

The exchange highlights Git's conservative approach to file system operations outside repository boundaries, prioritizing predictable behavior over convenience when dealing with system paths and permissions. The proposed error message change appears uncontroversial but doesn't fundamentally alter Git's security stance on directory creation.
