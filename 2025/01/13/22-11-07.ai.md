Performance issue report for `git bisect` on large repositories.

This is a performance bug report showing that `git bisect old` takes an unreasonably long time (21 minutes) when run on the Linux kernel repository between v6.13-rc7 and v3.0. The reporter provides detailed reproduction steps showing the command pegging a single CPU core at 100% usage throughout the operation, suggesting the bisect operation is not taking advantage of potential parallelism.

The report comes with complete system specifications (Debian 12, Git 2.39.5, bare metal hardware) and notes the test was run on tmpfs to eliminate disk I/O as a bottleneck. The reporter plans to test with a newer Git version and report back, but the fundamental issue appears to be that the bisect operation is CPU-bound and single-threaded when processing the Linux kernel's 535,608 revisions between these versions.

Key technical details for future reference: the operation involves `git bisect--helper`, which appears to be the bottleneck, and the reporter suggests parallelization as a potential solution. The test case specifically uses `git bisect new/old` syntax (rather than good/bad) to set up the bisect range. The Linux repository in question contains over 13 million objects and 87,000 files at HEAD.
