Bugfix for Windows reftable file locking behavior, addressing interactive prompts during failed unlink operations.

Patrick Steinhardt responds to Christian Reich's bug report about Windows-specific file locking issues in the reftable backend. The problem manifests when JGit holds locks on reftable files while Git attempts concurrent operations, causing unwanted interactive prompts on Windows when `git pack-refs` fails to unlink locked files. 

Steinhardt confirms this behavior contradicts the reftable specification's expectation that failed unlinks should be silently skipped. He identifies the root cause in `mingw_unlink()`'s error handling, which currently prompts users when files are locked (via `is_file_in_use_error()` check). The issue occurs in two scenarios: during `reftable_be_pack_refs()` calling `reftable_stack_clean()`, and when reloading the stack to prune unreferenced tables.

Key technical details include the Windows-specific implementation path through `mingw_unlink()` and `_wunlink()`, with the problematic behavior triggered by `is_file_in_use_error()` checks. The patch (promised in follow-up) will need to modify this Windows-specific unlink behavior to align with the reftable spec's silent-failure expectations. This touches core reftable operations and Windows platform compatibility, requiring coordination between the reftable (Steinhardt/Nayak) and Windows (Schindelin) maintainers.
