This is a bug report regarding GPG key selection behavior in `git tag -s`. The thread involves a discrepancy between documented behavior and actual behavior when signing tags with smartcards.

Carlos Maiolino reports that when his configured signing key (stored on a smartcard) is unavailable, Git silently falls back to using a different key rather than failing or warning. This contradicts the documented behavior where `user.signingKey` should determine the key used. Jeff King initially suggested checking for config overrides and examining the GPG command with `GIT_TRACE`, which revealed that while Git properly passes the key when specified via CLI, it behaves differently when the configured key is unavailable.

The core issue appears to be Git's silent fallback behavior when the specified signing key cannot be accessed (in this case, when the smartcard containing the key is disconnected). The expected behavior would be either failure or an explicit warning when the configured key cannot be used. This affects the reliability of signed tags when using hardware-backed keys.

Key technical details include:
- The `user.signingKey` configuration option
- GPG command invocation via `gpg --status-fd=2 -bsau <key>`
- Smartcard-based key storage scenarios
- Silent fallback behavior when primary key is unavailable

This appears to be a legitimate bug in Git's key selection logic that could impact users relying on hardware security modules for signing. The behavior difference between CLI-specified keys and config-specified keys suggests the issue lies in Git's key availability handling rather than GPG itself.
