This is a discussion about triangular workflow detection mechanisms in Git, with Junio C Hamano proposing deeper architectural considerations beyond the immediate scripting solutions.

The email builds on previous suggestions for detecting '_incoming' branches (via `git fetch -p` + `git branch -r` or `git ls-remote`) by questioning the fundamental approach. Hamano identifies a bootstrapping problem - new branches wouldn't have their '_incoming' counterparts initially, making existence checks unreliable for workflow detection. He suggests this indicates a need for proper protocol-level support rather than branch naming conventions.

Key technical proposals include:
1. A hypothetical protocol capability where servers could advertise required push targets (e.g., redirecting `B` pushes to `refs/for/B`)
2. A generic "custom capabilities" advertisement mechanism mirroring `--server-option` but server-to-client
3. A concrete alternative using `refs/capabilities/incoming` as a workflow marker

The discussion shifts from branch detection techniques to workflow signaling architecture, with Hamano framing the current solutions as workarounds for missing protocol features. This introduces new considerations about Git's extensibility mechanisms while maintaining the original goal of reliable CI workflow detection.
