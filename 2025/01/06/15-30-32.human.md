This is a discussion about improving branch detection in triangular workflows, where CI systems need to check for special '_incoming' branches. Junio Hamano weighs in with several architectural considerations beyond the immediate scripting solutions proposed earlier.

The email suggests the current approaches (checking for branch existence via `git rev-parse`, `git fetch`+`git branch`, or `git ls-remote`) may be addressing symptoms rather than the root problem. Hamano identifies a fundamental workflow issue: new branches can't follow the pattern until they're first created, making existence checks unreliable for bootstrapping.

He proposes two more systemic solutions: either extending Git's protocol to natively support such workflows (where the server could advertise required push targets), or using a dedicated capability-ref (like `refs/capabilities/incoming`) as a more robust marker than branch naming patterns. These suggestions aim to move beyond fragile branch-name parsing toward explicit workflow signaling.

The discussion has evolved from specific command alternatives to considering protocol-level changes, though Hamano notes these are just exploratory thoughts rather than concrete proposals. This shifts the conversation toward whether Git should provide better primitives for custom workflows versus requiring users to build solutions atop existing commands.
