This is a technical discussion about the behavior of histogram/patience diff algorithms when matching lines with different occurrence counts between file versions. The thread examines whether lines with differing counts should be considered matching, with Jonathan Tan providing historical context from JGit's implementation (the basis for Git's histogram diff) and analyzing the implications.

Key technical details include:
- Current behavior in Git/JGit only rejects lines when left-side count > right-side count (an unexplained asymmetry)
- The original motivation was to use low-occurrence lines as stable context markers
- jj (Jujutsu VCS) recently changed to reject all differing counts since it lacks a Myers diff fallback
- Git would fall back to Myers anyway in these cases, making the change less impactful
- The discussion references specific line number checks in JGit's HistogramDiffIndex.java

The email suggests this is likely a historical artifact rather than intentional design, but argues against changing Git's behavior since:
1) The fallback to Myers diff would produce similar output anyway
2) Different VCSes naturally produce different diffs
3) The current behavior has been stable for years

The thread touches on fundamental diff algorithm tradeoffs around what constitutes meaningful context versus noise, with references to Bram Cohen's original patience diff rationale. This could become relevant if future patches propose changing Git's histogram diff behavior to align with jj's approach.
