Security discussion continuation regarding GitHub PATs in remote URLs. This email from rsbecker@nexbridge.com shares a practical perspective from implementing a custom credential layer to handle GitHub Personal Access Tokens (PATs) without core Git modifications. The author notes that PATs are fundamentally insecure when persisted on disk due to lacking password protection, though doesn't speculate why GitHub adopted this model beyond potential CVE avoidance.

Key technical details include: PATs are required for `git push` operations in their environment, and their primary use case involves scripted Pull Request creation from NonStop systems lacking GitHub GUI integration. The custom solution involves careful memory management of cached PATs, though the implementation remains proprietary. This reinforces Brian m. carlson's earlier point about credential helpers being a more maintainable solution than core Git modifications.

The email provides real-world validation of the security concerns raised earlier in the thread, particularly around PAT persistence risks, while demonstrating an alternative approach through external credential management. It also surfaces a less-discussed use case (automated PR creation) that relies on PAT authentication. The technical specifics around NonStop platform constraints and memory management challenges for credential caching add new dimensions to the discussion about where PAT handling responsibility should lie in the Git ecosystem.
