This is a follow-up in the `git blame` buffer safety thread, addressing a newly discovered pre-existing buffer overflow risk in the OID formatting code. Patrick Steinhardt responds to Johannes Schindelin's analysis that moving the length check after the `memset(hex, ' ', length)` operation would create a buffer overrun vulnerability, as the unguarded `memset` could write beyond the `hex` buffer's bounds when processing large `--abbrev` values.

The discussion reveals this is a latent issue predating the current refactoring work, not introduced by the recent changes. Steinhardt acknowledges that even Schindelin's earlier proposed fix (setting `length = GIT_MAX_HEXSZ + 3`) would still leave a 2-byte overrun possibility. He plans to send an additional commit to properly address this separate safety concern while maintaining the v2 approach's prefix-aware length truncation for the primary issue.

Key technical points:
- The vulnerability exists in `builtin/blame.c` where `memset` writes spacing characters before length validation
- Affects both SHA-1 and SHA-256 hash formats when processing large abbreviation values
- Demonstrates the careful analysis required for security-sensitive formatting code
- Confirms the v2 approach's correctness while identifying an orthogonal safety issue

This exchange shows the thread moving from the original out-of-bounds read fix to uncovering and addressing a related buffer overflow, with both authors collaborating to ensure comprehensive safety improvements. The solution will now require two distinct fixes: one for the read issue and another for the write vulnerability.
