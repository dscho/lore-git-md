This is a follow-up discussion in the security-focused `git blame` bugfix thread regarding the handling of large `--abbrev` values.

Shejialuo raises a design question about whether Git should allow `--abbrev` values exceeding `GIT_MAX_HEXSZ` at all, noting it seems unusual from a user perspective. Johannes Schindelin responds by referencing his earlier explanation about the current behavior's rationale - specifically how prefix characters (like `^` for boundary commits) interact with OID alignment requirements in blame output formatting.

The exchange clarifies that while the current series fixes the security issues with large abbrev values, the underlying design decision to permit such values remains unchanged. This appears to be a philosophical discussion about input validation versus graceful handling of edge cases, rather than a technical issue with the proposed fixes. The thread shows consensus on the security fixes while leaving open the broader question of whether the CLI should reject invalid-length abbrev values entirely.
