Bugfix for git grep EOF matching inconsistency. Jeff King follows up on his earlier investigation with a proposed fix for the `git grep '^$'` false positive at end-of-file. The patch adds a check in `grep.c`'s `look_ahead()` function to explicitly skip matches that occur at the exact buffer end (where `m.rm_so == *left_p`), preventing the regex from matching the empty string after the last newline. 

The change addresses the core issue where `regexec_buf()` implementations (particularly non-PCRE) can spuriously match `^$` at buffer end. King notes the problem disappears with PCRE (`-P` flag) or when bypassing look-ahead, suggesting this is a quirk of certain regex engines when processing buffers containing newlines. The fix is minimal and maintains compatibility with standard grep behavior while avoiding deeper changes to the decade-old look-ahead logic.

Key technical points for future reference: the fix touches `grep.c`'s pattern matching path, specifically the `look_ahead()` function's handling of zero-width matches at buffer boundaries. The issue manifests when scanning multi-line buffers (not per-line processing in `match_line()`), and interacts with regex engine specifics - PCRE behaves correctly while other implementations may not. The patch preserves the existing optimization structure while adding a boundary case check.
