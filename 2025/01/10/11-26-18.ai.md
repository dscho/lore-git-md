Security bugfix addressing a boundary condition in `git blame`'s object ID handling when using `-b` with large `--abbrev` values. This is the second patch in Patrick Steinhardt's v3 series fixing multiple security issues in `git blame`'s OID formatting.

The patch specifically fixes an out-of-bounds write that occurs when `-b` (blank boundary commits) is combined with an `--abbrev` value exceeding `GIT_MAX_HEXSZ`. The current code uses `memset()` with the user-provided length directly, risking segfaults. The solution replaces this with `strlen(hex)` to ensure we only write the actual hash length, while still respecting the blank boundary formatting.

Key technical details:
- Fixes unsafe `memset(hex, ' ', length)` call by using `strlen(hex)` instead
- Maintains alignment with both SHA-1 and SHA-256 repositories
- Adds two new test cases in `t/t8002-blame.sh`:
  - Verifies correct blank spacing with normal `--abbrev` values
  - Confirms proper truncation with excessive `--abbrev` values (9000 chars)
- The solution builds on the series' earlier work by integrating with the safe OID formatting approach established in patch 1
- Tests demonstrate the fix handles both typical and extreme cases while preserving the blank boundary commit display format

This completes the series' comprehensive security hardening of `git blame`'s OID handling, addressing all three identified vulnerabilities (out-of-bounds read, buffer overflow, and now this boundary commit write issue) while maintaining compatibility across hash algorithms and existing formatting expectations.
