Performance optimization for `git bisect`'s quadratic algorithm in large repositories. Jeff King follows up on earlier analysis of the bisection performance problem with a concrete patch that reduces runtime by ~40% (from 16m51s to 9m34s) in the Linux kernel repository test case.

The patch modifies `clear_distance()` in `bisect.c` to only clear COUNTED flags along the same commit traversal path used by `count_distance()`, rather than clearing all commits globally. This addresses part of the O(n²) behavior where each commit was previously forcing a full graph traversal for flag cleanup. The implementation uses recursive parent traversal with UNINTERESTING/COUNTED flag checks to limit scope.

Key technical details: the patch changes the flag-clearing strategy while maintaining the same commit-walking logic as `count_distance()`, including handling of parent chains. The improvement is significant but still leaves fundamentally quadratic behavior, as noted in the email. Jeff King suggests a more comprehensive solution would involve rewriting the bisection count algorithm to use a single reverse-topo-order traversal, though this isn't implemented here.

The email provides a useful benchmark command (`git rev-list --bisect`) for testing the core expensive operation independently. This continues the thread's progression from problem identification to initial optimization, with clear next steps for further algorithmic improvements. The patch demonstrates a practical improvement while acknowledging deeper architectural work remains.
