Performance analysis of quadratic behavior in `git bisect` initialization. Jeff King examines the code path that causes slow bisect operations on large repositories like Linux kernel history (1M+ commits). The bottleneck appears in `do_find_bisection()` where the algorithm performs O(n²) operations - for each commit in the list, it potentially traverses the entire commit graph via `count_distance()` and `clear_distance()`. 

Key technical details: The current implementation clears distance flags across all commits after each distance calculation, which may be unnecessarily broad. King suggests a possible optimization by limiting flag clearing to just the commits reachable from the current commit being processed, though notes this would still leave worst-case quadratic behavior. The analysis confirms this as a fundamental algorithmic limitation rather than filesystem or I/O bottleneck, aligning with previous timing measurements showing CPU-bound behavior.
