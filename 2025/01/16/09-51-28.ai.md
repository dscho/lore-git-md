This is a technical discussion about ref-filter's ahead-behind calculation implementation, continuing the ongoing thread about memory management and API design in the ref-filter subsystem.

Jeff King responds to René Scharfe's concerns about the atomicity of the ahead-behind "molecule" and proposes an alternative approach to storing commit references. While agreeing that separate ahead/behind atoms would be more flexible, King notes he's unsure of the practical need for this. The core of his response is a new implementation that moves the ahead-behind base commits from the format->bases string_list into individual atom structs, eliminating the need for the bases list entirely.

Key technical aspects of King's proposal:
- Stores commit references directly in used_atom.u.base.commit rather than in format->bases
- Requires counting ATOM_AHEADBEHIND atoms to determine base count
- Maintains same calculation logic in filter_ahead_behind() but with different data access pattern
- Leaves is_base_tips as future work but suggests same approach could apply
- Removes format->bases entirely from struct ref_format

The email continues the thread's theme of exploring different approaches to state management, with this version representing a middle ground between the previous static-variables vs explicit-parameters debate. King acknowledges this doesn't fully resolve the architectural questions about where this state belongs (ref_format vs ref_filter vs atom structs), but presents it as a pragmatic step that eliminates one problematic data structure while keeping the door open for future refactoring.

The discussion remains focused on technical implementation details rather than user-facing behavior, with both contributors demonstrating deep engagement with the subsystem's internals. King's proposal appears to be a new third option in the ongoing design discussion, though he positions it as a transitional solution rather than a final answer.
