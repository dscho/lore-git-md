Technical discussion about output flushing in help text implementation.

This email continues the technical discussion between Junio Hamano and Jeff King about the implementation details of standardizing help text output. The conversation focuses on whether to flush stdout unconditionally when handling `-h` help requests, even though the primary concern in the original implementation (commit 116d1fa6c6) was specifically about stderr flushing.

Junio clarifies that his earlier comment about "tricky" referred to code readability rather than implementation difficulty - specifically the cognitive overhead of understanding why flushing would be conditional on the file handle being stderr. Jeff maintains that while it's unlikely for processes to write to stdout before processing `-h` flags, a defensive approach with unconditional flushing would be safer.

The exchange reveals an implementation detail that wasn't fully addressed in previous patches: the vreportf() helper being discussed was historically stderr-specific, which may have led to the original conditional flushing behavior. Both maintainers agree that unconditionally flushing stdout before writing help text (via write() syscalls) is reasonable since the process will exit immediately afterward anyway. This discussion doesn't change the core functionality but refines the implementation approach for edge cases.
