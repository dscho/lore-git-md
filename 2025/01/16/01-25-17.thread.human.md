This thread documents the effort to standardize Git's help text output behavior, ensuring `git cmd -h` consistently writes to stdout rather than stderr. The work originated from Jonas Konrad's observation of inconsistency between parse-options API (stdout) and manual usage() implementations (stderr). 

The implementation has introduced several key helpers - `show_usage_if_asked()`, `show_usage_with_options_if_asked()`, and `usage_with_options_internal()` - to centralize stdout behavior while maintaining backward compatibility. A technical discussion between Jeff King (peff) and Junio Hamano clarified that unconditional stdout flushing via write() syscalls is acceptable since the process exits immediately after help output, addressing earlier concerns about stream handling.

The latest patch refactors the output mechanism further by introducing `vfreportf()` as a new base function that takes a FILE* parameter, replacing the stderr-specific `vreportf()`. This supports writing to either stream while maintaining consistent flushing behavior. The patch also adds the `show_usage_if_asked()` helper to consolidate the common pattern of checking for `-h` and calling `usage()`. While maintaining exit code 129 for now, the commit message notes this may change to 0 in the future.

Test coverage via t0012-help.sh with `GIT_TEST_HELP_MUST_BE_STDOUT` ensures compliance. The series has converted usage_with_options() calls in 14 builtins and addressed special cases in subcommands like credential and fetch-pack. With all technical feedback addressed regarding both the standardization goal and output stream handling, the implementation appears complete and ready for inclusion.
