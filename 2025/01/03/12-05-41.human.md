This is a follow-up discussion in the performance optimization series addressing LSan race conditions in Git's test suite. Patrick Steinhardt responds to Jeff King's patch that changes how leak detection works in the test infrastructure.

The key point is a thoughtful observation about the trade-off in Jeff's approach: while moving to log-based leak checking (rather than aborting on first leak) provides better control over false positives, it means tests will now run to completion even when leaks occur. This could make debugging slightly harder since multiple leaks might appear in the logs rather than failing immediately at the first one.

Patrick acknowledges this is likely an acceptable trade-off given the current state of Git's test suite, where memory leaks are rare enough that the benefits of better false positive handling outweigh the debugging inconvenience. The exchange shows careful consideration of practical testing trade-offs between immediate failure and comprehensive reporting.

This email doesn't propose any changes to the series but provides valuable perspective on the real-world implications of the chosen approach, reinforcing that the solution is making a conscious design choice rather than overlooking potential downside.
