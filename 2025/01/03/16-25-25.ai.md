This is a follow-up discussion in the ongoing thread about hash function initialization in `git fast-import`, specifically addressing the architectural approach to make hash handling more robust.

Junio Hamano concurs with Patrick Steinhardt's proposal to store the hash function type within `struct git_hash_ctx` itself, eliminating the current brittle approach where callers must track initialization variants. The suggested API pattern would have initialization functions like `git_hash_sha1_init()` set the hash method internally, with subsequent operations (`update`, `final_oid`) automatically using the stored type. This builds on the immediate fix (switching to `unsafe_init_fn` in `stream_blob()`) while providing a cleaner long-term solution that could benefit other subsystems beyond fast-import.

The discussion indicates alignment on moving toward encapsulated hash state management, though implementation details remain to be worked out. This connects to broader concerns about hash function safety and the ongoing Meson build system changes mentioned earlier in the thread. The proposed design would help prevent similar initialization-related bugs while maintaining synchronization between hash implementations.
