Performance optimization follow-up discussing LSan leak detection strategy in the Git test suite. Patrick Steinhardt responds to Jeff King's patch that changes how leak detection works when running tests under LeakSanitizer (LSan). The key change in Jeff's patch was switching from aborting tests immediately on leaks (via `abort_on_error=1`) to letting tests complete and checking logs afterward (via `exitcode=0`), since Git test infrastructure now reliably checks LSan logs after each test snippet.

Patrick notes one potential downside: with the new approach, tests run to completion even when leaks occur, which could produce multiple leak reports and make it harder to identify which specific command caused the initial leak. However, he acknowledges the Git codebase is now in good enough shape regarding memory management that this tradeoff is acceptable. The discussion reflects the project's ongoing refinement of its sanitizer integration strategy, balancing diagnostic precision against test execution behavior. This follows the broader thread's theme of pragmatic solutions to LSan's threading-related false positives while maintaining effective leak detection.
