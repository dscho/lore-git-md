This is a performance optimization discussion about LSan (LeakSanitizer) handling in Git's test suite, part of an ongoing series (patch 3/6). Jeff King and Patrick Steinhardt are discussing the tradeoffs of changing how leaks are detected in test runs.

The key change in this patch switches LSan from aborting immediately on leaks (which would stop the test case) to running to completion and checking logs afterward. Patrick notes this could make it harder to pinpoint exactly which command caused a leak when multiple occur in one test snippet, since we lose the immediate abort behavior. Jeff acknowledges this but points out that (1) leaks are now rare enough that it's unlikely to be a major issue, and (2) the process name is still logged, providing some context.

Both agree the current state of leak detection is clean enough that this tradeoff is acceptable. Jeff mentions that users can still override the behavior for specific test runs if needed. The discussion shows thoughtful consideration of practical debugging needs versus test suite robustness, with both participants comfortable moving forward with the log-based approach.
