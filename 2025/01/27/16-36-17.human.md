Bugfix investigation for `git fetch` tag behavior in shallow clones. Bence Ferdinandy digs deeper into the protocol-sensitive issue where tags pointing to shallow boundary commits aren't fetched with `--depth=1`. The problem stems from commit 5f212684abb66c9604e745a2296af8c4bb99961c and appears transport-dependent - working with JSch but failing with native SSH/HTTPS.

Bence identifies the key code in `builtin/fetch.c` where tag and HEAD prefixes are added to `transport_ls_refs_options.ref_prefixes`. The current order (tags first, then HEAD) causes tags to be skipped when `ref_prefixes` is non-empty. Reversing this order (HEAD first, then tags) empirically fixes the issue while maintaining backward compatibility, though the underlying reason remains unclear.

The investigation reveals this behavior dates back to e70a3030e7 (2018) where Jonathan Nieder added the `ref_prefixes` emptiness check. Bence notes that simply removing this check breaks many tests, while reordering the prefixes doesn't, suggesting there may be deeper protocol-specific behaviors at play. The email ends with an open question about why these two seemingly similar approaches (removing the check vs reordering) have different effects, hinting this might be a temporary fix rather than a complete solution.
