This is a technical response in the ongoing Windows reftable backend compatibility discussion, specifically addressing Junio Hamano's concerns about the proposed `MINGW_DONT_HANDLE_IN_USE_ERROR` solution.

Patrick Steinhardt defends his approach to immediately fail on file-in-use errors for reftable operations rather than implementing a retry loop. The key technical points are:

1. The reftable backend already handles stale files gracefully by retrying deletions in subsequent `git-pack-refs` calls, making immediate failure acceptable.

2. The file contention comes from external processes (like JGit), not from Git itself, and these processes are unlikely to release the file during a short retry window (71ms).

3. Windows' `FILE_SHARE_DELETE` usage means the blocking process must be non-Git (as Git processes would allow deletion).

4. The proposed solution avoids unnecessary user-facing delays for a scenario where success is improbable.

Steinhardt acknowledges Hamano's concerns about the yuckiness of the macro-based solution but maintains it's the least bad option given the constraints. He also confirms the reftable implementation doesn't suffer from the self-locking issues Hamano raised as a concern.

The email reinforces the architectural position that reftable can tolerate failed deletions (unlike core Git) and that the Windows-specific behavior should be handled at the library level rather than through platform-layer modifications that might affect other Git components.
