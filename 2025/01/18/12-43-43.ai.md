This is a technical discussion about hash algorithm safety in the ongoing hash algorithm refactoring series.

Jeff King follows up on his earlier suggestion about how `hash_algo_by_ptr()` should handle unsafe algorithm variants. He proposes making the function return `GIT_HASH_UNKNOWN` when given an unsafe variant pointer, which would force callers to explicitly handle such cases rather than silently converting them to safe variants. His test shows this change doesn't break the test suite, suggesting the current code paths don't actually rely on unsafe variant conversion.

The email reveals a deeper issue: the existing implementation has undefined behavior when passed NULL pointers (as happens in some test cases), silently converting the NULL to a garbage algorithm ID. Jeff demonstrates this with a BUG() insertion that triggers during grep tests. While this is pre-existing behavior unrelated to the current series, it highlights why returning UNKNOWN would be safer - it would make such cases fail explicitly rather than continuing with corrupt state.

Key technical points:
- Current `hash_algo_by_ptr()` silently converts unsafe variants to their safe counterparts
- Proposed change would make unsafe variants unidentifiable (returning UNKNOWN)
- Test suite passes with this change, suggesting no current dependencies
- Revealed NULL pointer case shows existing undefined behavior in algorithm lookup
- NULL handling is out of scope for this series but demonstrates value of explicit UNKNOWN returns

The discussion continues the thread's focus on making hash algorithm usage more robust by preventing silent conversions and undefined behavior. Jeff's analysis shows the proposed change would improve safety without breaking existing functionality, while incidentally exposing a separate NULL-handling issue that could be addressed later.
