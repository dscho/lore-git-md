Bugfix for credential-cache helper's capability negotiation, now at v5 with improved commit message.

This patch finalizes the fix for credential-cache's handling of authentication type (authtype) capabilities, transitioning from unconditional inclusion via CREDENTIAL_OP_HELPER to capability-gated inclusion via CREDENTIAL_OP_RESPONSE. The technical changes remain focused in builtin/credential-cache--daemon.c with two condition checks updated, plus a new test case in t/lib-credential.sh that verifies the capability-aware behavior by demonstrating the failure case where "credential fill" would print incomplete credentials without this fix.

The v5 iteration specifically addresses prior review feedback by enhancing the commit message to better explain: (1) the behavioral change aligns with documented behavior in git-credential.txt which specifies authtype should only be sent when explicitly via CREDENTIAL_OP_RESPONSE capability, (2) the impact where previously unexpected authtype attributes were being discarded by credential.c, and (3) includes the regression-protecting test case. The patch appears ready for merging with no outstanding technical concerns raised in reviews.

Key technical details for future reference: The change affects credential attribute transmission in the credential-cache daemon's response handling, specifically around authtype and credential fields. The test verifies proper capability negotiation by checking credential fill output when authtype capability is not provided. The behavioral change centers on moving from OP_HELPER to OP_RESPONSE capability checks when deciding whether to include sensitive credential attributes in responses.
