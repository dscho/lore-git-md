This is a follow-up discussion about fixing false positives in LSan (LeakSanitizer) reports during threaded Git tests. Jeff King proposes several alternative solutions to address a race condition that was previously worked around with thread barriers.

The core issue stems from `fast_unwind_on_malloc=0` in LSAN_OPTIONS, which improves stack traces for leak detection but causes race conditions in threaded programs. Jeff demonstrates that removing this option eliminates the false positives while potentially making leak traces less informative. He presents several options:

1. Remove `fast_unwind_on_malloc=0` by default, requiring manual override for better traces
2. Keep it by default but disable for CI runs
3. Apply it per-script or per-test basis
4. Ignore the false positives by modifying LSAN's exit behavior and filtering known false positives

The most intriguing proposal is the last one - a targeted filter that maintains good stack traces while suppressing the known false positives. This would avoid both the thread barrier workarounds and the loss of diagnostic information.

The discussion builds on recent work to handle LSan races (merged to 'next') but suggests this might be a simpler solution. Jeff notes he's still investigating reporting the issue upstream to LSan developers. The proposal represents a pragmatic middle ground between diagnostic quality and test reliability.
