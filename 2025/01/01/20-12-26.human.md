This is a performance optimization series addressing LSan (LeakSanitizer) race conditions in Git's test suite. Jeff King proposes a less invasive solution than his previous approach (jk/lsan-race-with-barrier) to handle false positive leak reports that occur during threaded test execution.

The series takes a pragmatic approach by teaching the test infrastructure to ignore known false positive patterns in LSan output rather than trying to fix the underlying race condition in the sanitizer's stack unwinding code. This builds on prior work (370ef7e40d) that similarly filtered uninteresting LSan output. The key insight is that we can safely detect and skip these false positives by examining the logs rather than trying to prevent them at runtime.

The changes focus on test-lib.sh's LSan configuration, removing the problematic abort_on_error behavior and adding careful log filtering. Jeff demonstrates the solution works by intentionally introducing a memory leak in test-date.c and verifying the test suite correctly catches real leaks while ignoring the known false positives. The series maintains diagnostic quality for actual leaks while making the test suite more reliable under threaded execution.

This appears to be a well-considered solution that balances technical correctness with practical maintainability. The approach avoids deeper changes to Git's threading code or LSan configuration that might have broader side effects. The careful verification (including preserving two patches from the previous attempt) suggests this is production-ready for maintainers to consider merging.
