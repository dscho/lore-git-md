This is a technical discussion about Windows file handling in the reftable backend, continuing the debate about where to handle Windows' file-in-use errors. Patrick Steinhardt responds to Johannes Sixt's architectural concerns about his earlier patch that proposed modifying the Windows compatibility layer.

Steinhardt clarifies that his atomic rename fixes (391bceae4350) don't solve this particular issue because the problem involves third-party clients like JGit keeping files open. He explains the technical constraints that make it difficult to handle the issue purely within the reftable layer - the library automatically inherits Windows compatibility behaviors through git-compat-util.h, and reimplementing this would lose useful features like wide-character support.

The email presents two possible approaches: 1) the original proposal to modify mingw_unlink() with a new flag, or 2) introducing a reftable-specific unlink wrapper. Steinhardt expresses openness to alternatives but notes both solutions have tradeoffs. The discussion remains focused on finding the right architectural layer to handle Windows' file locking semantics while maintaining compatibility with POSIX expectations and third-party tools.
