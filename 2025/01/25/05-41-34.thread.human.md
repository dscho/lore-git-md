This thread examines a Windows compatibility issue with the reftable backend, where file unlinking behavior differs between POSIX and Windows systems. The core problem stems from Windows preventing unlink operations on open files, conflicting with reftable's expectations. Patrick Steinhardt initially proposed modifying the platform layer via a `MINGW_DONT_HANDLE_IN_USE_ERROR` flag, while Johannes Sixt later offered alternative solutions using Windows API functions that avoid platform changes.

Junio Hamano has now weighed in, expressing concerns that Steinhardt's approach of completely bypassing unlink retries might be too extreme. He suggests preserving non-interactive retries (which help with external process locks) while eliminating interactive prompts, proposing a middle ground between the original solution and doing nothing. This adds another dimension to the ongoing architectural debate about whether to handle the issue at the platform layer (Steinhardt) versus within reftable itself (Sixt).

The discussion now includes multiple viable approaches with different tradeoffs: platform modifications, Windows API solutions, and potential code restructuring to avoid self-unlinking. All proposals must still address compatibility concerns raised by Christian Reich regarding Git for Windows integration. With Junio's input shifting the conversation toward a more nuanced retry behavior, the thread awaits either implementation of the new suggestions or further technical analysis of their implications.
