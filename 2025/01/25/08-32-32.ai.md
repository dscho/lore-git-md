This is a technical follow-up in the Windows reftable file handling discussion, where Patrick Steinhardt responds to Johannes Sixt's architectural questions about where to handle Windows' file-in-use errors.

Steinhardt clarifies that his earlier atomic rename fixes (391bceae4350) don't apply here because this case involves third-party clients (specifically JGit) keeping files open, which Git can't control. He explains two key constraints preventing a reftable-layer solution: 1) the automatic inclusion of Windows compatibility functions via git-compat-util.h makes it impossible to bypass the platform layer, and 2) reimplementing the compat layer would lose useful features like wide-character handling.

The email proposes two potential solutions - either keep the current approach of modifying mingw_unlink() with a new flag, or introduce a reftable-specific unlink wrapper that calls the modified version. Steinhardt expresses openness to alternative approaches but notes both solutions would require significant plumbing changes. The discussion remains focused on architectural boundaries between platform abstraction and subsystem implementation, with no clear resolution yet.
