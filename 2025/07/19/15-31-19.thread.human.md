This thread discusses a potentially confusing output from `git bisect` when commits are skipped during bisection. The original report from Begad Habib demonstrated that in a simple 3-commit linear history (good, skipped, bad), after marking the endpoints and skipping the middle commit, `git bisect` would list both the known-good commit and the skipped commit as potential bad candidates - even though it had correctly identified the actual bad commit.

Junio C Hamano has now responded, acknowledging the report and CC'ing the primary author of the `git bisect skip` functionality for their evaluation. The core issue appears to be in the output formatting rather than the bisection logic itself, which correctly finds the bad commit. The discussion now centers on whether this behavior is intentional (perhaps to show all untested commits) or should be modified to exclude known-good states from the "could be bad" list.

The thread is awaiting input from bisect experts to determine if this warrants a code change to the output formatting, or if the current behavior should be preserved with improved documentation. Any changes would need to consider backward compatibility, as the output format might be parsed by scripts. The next steps will likely involve technical evaluation from maintainers familiar with the bisect implementation's design intent.
