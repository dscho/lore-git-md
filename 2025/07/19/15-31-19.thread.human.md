This thread examines a report about potentially confusing output from `git bisect` when commits are skipped during bisection. Begad Habib originally reported that known-good commits were appearing in the "could be bad" list in a simple 3-commit test case (good, skipped, bad). Junio C Hamano acknowledged the report and engaged Christian Couder, the original author of Git's bisect functionality, for expert evaluation.

Christian Couder has now responded with a detailed technical analysis. He identified potential confusion in the original reproduction steps, noting that the `git bisect skip` command was likely used incorrectly (skipping a good commit rather than the intended middle commit). Couder clarifies that Git's output about the "first bad commit" refers to the earliest possible bad commit in history, not just the currently marked bad commit - a distinction that explains much of the reported behavior. He references documentation showing this is expected behavior when skipping commits adjacent to the bad commit. While unable to reproduce the exact output showing good commits in the "could be bad" list, Couder leaves open the possibility of edge cases if better reproduction steps can be provided.

The discussion has now clarified several key aspects of bisect behavior while leaving the door open for further investigation if the original reporter can provide more precise reproduction details. The next steps likely involve either confirmation that the current behavior is correct (with possible documentation improvements) or identification of a specific edge case needing code changes.
