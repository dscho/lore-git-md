This is a follow-up discussion in the performance optimization thread about memory overhead comparisons between prio_queue and commit_list implementations. Jeff King responds to René Scharfe's analysis of memory usage characteristics, acknowledging he had overlooked the stability counter in prio_queue entries.

The exchange clarifies that while both data structures have similar base storage needs (two pointers for commit_list vs one pointer plus a stability ID for prio_queue), the prio_queue's use of ALLOC_GROW leads to about 25% average overallocation. Scharfe suggests this likely makes commit_list more memory-efficient in practice, though both note malloc's per-allocation overhead could affect the comparison.

This discussion provides important context about implementation tradeoffs that could inform future decisions about data structure choices in Git's core, though it doesn't require any changes to the already-approved patch series. The technical details about memory characteristics complement the earlier performance-focused analysis in the thread.
