[PATCH v3] git send-email: add IMAP sent-folder archiving

Aditya Garg's patch series implements IMAP-based message archiving in `git send-email`, enabling providers like iCloud Mail to store SMTP-sent messages via IMAP. The v3 iteration finalized naming as "imap-sent-folder" while maintaining core functionality to archive messages through `git imap-send` after SMTP transmission. Implementation spans `git-send-email.perl` (message handling) and `imap-send.c` (header preservation).

Key technical details:
- Config option: `sendemail.imapSentFolder`
- CLI flag: `--imap-sent-folder`
- Preserves Bcc headers in archive copies
- Uses existing `git imap-send` infrastructure with header parsing adjustments
- Parameter accepts any valid IMAP folder name, not just default "Sent" folders

Evolution from previous versions:
- v1: Initial "imapfolder" implementation
- v2: Incorporated Eric Sunshine's doc fixes and improved failure handling
- v3: Renamed to "imap-sent-folder" per Junio's preference while maintaining folder flexibility

Participant positions:
- Junio C Hamano: Confirmed the "imap-sent-folder" name doesn't restrict folder choice (string parameter allows any name), addressing Garg's concern while maintaining sent-specific terminology. Later reinforced that `send-email`'s advanced features (CC management, cover letters) make archive-after-send preferable to manual pipe-to-imap alternatives.
- Aditya Garg: Initially worried name might imply restriction to "Sent" folders; now fully accepts the naming after clarification that custom folders like 'git' archives are supported. In latest message, questions whether the feature's scope aligns with Git's needs given SMTP alternatives, introducing new skepticism about the feature's necessity.
- brian m. carlson: Balanced feature value with naming concerns

Current status:
- Naming debate fully settled - "imap-sent-folder" terminology accepted with understanding it supports arbitrary folders
- Core archiving functionality stabilized
- Workflow philosophy previously confirmed: archive-after-send (A2) provides sufficient value without needing pure-IMAP (B2) transport implementation
- Now facing new philosophical debate about whether the feature belongs in Git at all, despite prior consensus on implementation approach

Open questions:
- Whether the archiving-after-SMTP workflow provides enough unique benefit to warrant core Git support versus manual pipe approaches
- Pure-IMAP transport mode (B2) remains unimplemented by design, now with additional questioning of whether even A2 mode is justified
- No outstanding technical issues, but fundamental feature justification now under reconsideration

The series had appeared merge-ready after v3 naming and technical resolution, but Garg's latest skepticism introduces new uncertainty about the feature's core premise. Junio's previous arguments about `send-email`'s advanced features being worth preserving may need reinforcement or reconsideration in light of this new challenge to the feature's fundamental value proposition.
