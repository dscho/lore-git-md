Bugfix discussion regarding `git bisect` output with skipped commits. Junio Hamano acknowledges a user report about potentially confusing behavior when `git bisect` lists known-good commits as possible bad candidates after skipping intermediate commits. The original reporter provided a clear reproduction case showing that while the tool correctly identifies the bad commit, its final output includes both the skipped commit and an already-marked-good commit in the "could be bad" list.

This appears to be primarily a user interface issue rather than a functional bug, as the underlying bisection logic works correctly. Junio has CC'd the original author of the skip functionality for their input, suggesting this warrants deeper consideration from the bisect experts. The core question is whether the current output behavior is intentional (perhaps to show all untested states) or should be modified to exclude known-good commits from the potential bad list.

The thread is just starting, but given Junio's involvement and the clear reproduction case, it's likely to attract attention from maintainers familiar with the bisect interface. The discussion may need to balance output precision against potential backward compatibility concerns if the format were to change.
