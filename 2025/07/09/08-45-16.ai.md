This is a technical clarification in the gitk tag visualization discussion. Chris Torek responds to Adi Shavit's proposal by pointing out that the current identical appearance of local and remote tags in gitk reflects their fundamental equivalence in Git's object model - they "not only look identical, they *are* identical". 

The email identifies two technical approaches to distinguish them: either gitk query remotes directly via `git ls-remote`, or modify Git's fetch mechanism to track remote tag provenance. Torek notes the second approach would require introducing "remote tags" as a new Git concept, which he assesses as "not technically difficult but probably controversial" due to potential design implications.

This response shifts the discussion from UI design considerations to deeper architectural questions about whether tag tracking should be handled at the gitk level (lighter but less integrated) or in core Git (more fundamental but requiring consensus on new concepts). The email doesn't reject the feature request but highlights non-obvious implementation constraints that weren't addressed in the original proposal.
