This is a technical response in the ongoing SIGCHLD handling thread, specifically addressing Windows platform concerns.

Johannes Sixt responds to Carlo Marcelo Arenas Belón's work on standardizing SIGCHLD handling across platforms, focusing on the Windows (MinGW) implications. The key points are:

1. Signal number irrelevance: Argues that the specific numeric value (17 vs 22) shouldn't matter since code should use SIGCHLD rather than hardcoded numbers. This challenges part of the technical rationale in the original series.

2. Windows signal limitations: States that true signals don't exist in native Windows (outside Cygwin), making SIGCHLD and related SA_RESTART discussions irrelevant for MinGW builds. Notes Windows only has a limited SIGALRM emulation that doesn't behave like POSIX signals.

The response suggests the Windows-specific aspects of the SIGCHLD standardization effort may need reconsideration, as the fundamental assumptions about signal behavior don't apply to native Windows environments. This adds complexity to the platform compatibility work, particularly around patch 2 which deals with signal number handling. The comment comes from someone with Windows porting experience (as evidenced by the MinGW-specific knowledge), though they position themselves as a bystander" to the main discussion.
