This is a technical clarification in the gitk tag visualization discussion. Chris Torek responds to Adi Shavit's feature request by pointing out that the current identical appearance of local and remote tags in gitk reflects their actual identical nature in Git's object model - unlike branches, tags don't inherently track their origin.

Torek outlines two potential implementation approaches: either gitk would need to actively query remote status (via `git ls-remote`), or Git itself would need new infrastructure to track tag origins during fetch operations. He notes the second approach would be a significant (and likely contentious) change to Git's core functionality, while the first would keep changes localized to gitk's UI layer.

The response suggests the proposed visualization enhancement may be more foundational work than initially apparent, with implications beyond just gitk's display logic. This moves the discussion from pure UI design considerations into deeper questions about Git's tag handling architecture.
