This thread explores ways to improve gitk's tag visualization by distinguishing local tags from those that exist on remotes—a feature that exists for branches but not tags. The original proposal suggested UI approaches like remote name suffixes, color coding, or tooltips, with opt-in configuration.

Chris Torek added important context, noting that tags' uniform appearance reflects Git's object model, where tags are fundamentally identical objects regardless of origin. He outlined two implementation paths: gitk could query remotes directly (lighter but less integrated) or core Git could be modified to track remote tag provenance (more fundamental but potentially controversial). This shifted the discussion from pure UI design to deeper architectural questions.

Marc Branchaud then surfaced decade-old threads about tracking remote tags, showing these debates aren't new. Historical discussions from 2010 reveal similar proposals to store remote tags under refs/remotes/ and debates about whether tags should behave like branches regarding remote tracking. This context suggests core changes would face longstanding concerns about tag semantics and namespace organization.

Key open questions remain: Should the solution live in gitk or core Git? If in gitk, which UI approach works best? If in core, how to address historical objections? The thread has moved from initial UI ideas to weighing architectural tradeoffs with awareness of past attempts. No clear consensus has emerged yet, but participants now have fuller context about the technical and historical landscape.
