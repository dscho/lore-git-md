[PATCH 0/19] object-file: prepare for pluggable loose object backends

Patrick Steinhardt's 19-part series refactors object-file.c to eliminate `the_repository` dependencies, enabling pluggable object database support. The series is now complete with `the_repository` fully removed from object-file.c, marking subsystem independence from global state. Key changes include introducing `odb_write_object()` as backend-agnostic interface (with a documentation typo fixed in patch 09/19), migrating compression levels to repo settings, and refactoring loose object handling using `struct odb_source`.

A regression was found in `git fast-import` due to delayed config parsing (Phillip Wood reports `git -c core.compression=500 fast-import` now fails where it previously accepted invalid values silently), raising questions about settings timing. The latest patch converts loose object iteration functions (`for_each_loose_file_in_objdir` -> `for_each_loose_file_in_source`) to use `odb_source` parameters, affecting 10 files with clean mechanical conversion. Toon Claes positively notes the improved interface design moving away from direct path passing.

In patch 15/19 (removing `the_repository` from `force_object_loose()`), Karthik Nayak and Toon Claes identify an architectural inconsistency where the function checks for loose object existence across the entire object database while writing to a specific source. Nayak observes this is particularly odd since the function's precondition (object exists in packed form) would make the loose check always return true, suggesting the check may be redundant or misaligned with the function's purpose. This builds on Claes' earlier observation about the scope mismatch between checking and writing operations.

Karthik Nayak provides review feedback across multiple patches:
- On patch 02/19: notes grammatical error in commit message regarding `the_hash_algo` alternatives and questions inclusion of `read-cache-ll.h` header while approving core changes
- On patch 05/19: confirms architectural consistency where database-level operations like `freshen_loose_object()` take `object_database` parameters while source-specific ones use `_source` suffix, approving the mechanical conversion of freshening logic
- On patch 08/19: notes naming inconsistency with established `_source` suffix pattern for functions operating on specific sources, suggesting consideration of suffix for consistency even though the function is inherently tied to loose files backend

Current technical state:
- Object-file.c fully repository-agnostic with all operations parameterized
- 100 files modified (~730/+670 lines) in total
- Compression level validation now via `prepare_repo_settings()`
- Loose object iteration converted to source-based interface
- Maintains backward compatibility except for fast-import edge case
- Clear pattern established: database-wide ops use `object_database`, source-specific use `_source` suffix

Open considerations:
- Handling of delayed config parsing for critical settings like compression
- Performance impact of additional parameter passing
- Future handling of non-loose backends
- Platform-specific considerations for object creation modes
- Architectural quirk in `force_object_loose()` behavior (check vs write scope mismatch) now with additional analysis from Nayak confirming redundancy concern
- Consistency of parameter passing patterns across all object-file functions (including naming conventions as noted by Nayak)

The series demonstrates successful conversion of core subsystems to repository-agnostic operation while maintaining compatibility, positioning Git for pluggable storage backends. Reviewers continue identifying subtle behavioral implications and maintaining architectural consistency, with Nayak's latest analysis of `force_object_loose()` highlighting a potentially redundant check that may need reconsideration in the context of the new source-based architecture.
