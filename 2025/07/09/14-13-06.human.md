This is a technical discussion about Windows signal handling compatibility, part of the ongoing git-daemon signal handling redesign thread.

Phillip Wood and Carlo Marcelo Arenas Belón are debating how the Windows compatibility layer should handle `sigaction(SIGCHLD)` when replacing existing `signal()` calls. The core disagreement centers on whether the Windows implementation should:
1. Match Windows' `signal()` behavior (Carlo's preference for initial safety)
2. Follow standard `sigaction()` semantics (Phillip's preference for consistency)

- Windows' `signal()` doesn't set errno for invalid signals, contrary to documentation
- The current patch returns -1 without setting errno to match this behavior
- Phillip argues this creates platform inconsistency and suggests setting errno=EINVAL
- Carlo reveals Windows actually does set errno when using different signal numbers

The discussion remains unresolved but has narrowed to whether to:
- Initially match Windows' quirky `signal()` behavior to avoid regressions (Carlo)
- Enforce standard `sigaction()` behavior immediately (Phillip)

This is a relatively minor implementation detail in the larger signal handling redesign, but shows the careful consideration being given to cross-platform behavior.
