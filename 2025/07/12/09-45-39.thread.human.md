This thread explored how Git handles line endings on Windows, particularly when tools need consistent line endings for text analysis. It started with Jason Cho reporting that `license_header.txt` was checked out with CRLF line endings despite having `core.eol=lf` and `core.autocrlf=false` configured. Torsten Bögershausen confirmed this is expected behavior when files were originally committed with CRLFs.

Several contributors chimed in with technical clarifications. Johannes Sixt suggested using `core.whitespace` settings to suppress CRLF markers in diffs, though Jason clarified their need was for consistent line endings in the actual file content, not just diff display. Lidong Yan provided the key insight that `core.eol=lf` only affects conversions during staging (`git add`), not during checkout - Git intentionally preserves the original line endings unless overridden by attributes. Jason later acknowledged this explanation matched Git's documented behavior.

The discussion revealed a tension between Git's philosophy of content preservation and the needs of text analysis tools that require normalized line endings. While the immediate question was resolved (explaining why the configuration didn't work as expected), the broader design question remains open - whether Git should offer more control over checkout-time line ending conversion. For now, the consensus is to use Git attributes or external tools if forced normalization is needed during checkout.
