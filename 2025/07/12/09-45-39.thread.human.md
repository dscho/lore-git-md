This thread explores line ending behavior in Git, particularly on Windows, where Jason Cho encountered unexpected CRLF line endings in a file despite having `core.eol=lf` and `core.autocrlf=false` configured. Initial analysis by Torsten Bögershausen confirmed this was working as designed - the file was committed with CRLFs originally, and Git preserved them. Jason's use case involves a code analysis tool where line ending differences cause problems when tracking function movements between files.

The discussion has evolved through several approaches: the standard solution of using `.gitattributes` for line ending control, Jason's preference for simpler global configuration via `core.eol`, and now Johannes Sixt's suggestion to use `core.whitespace` with `cr-at-eol` to clean up diff output without changing the actual line endings. This last approach addresses the visual clutter of CR markers in diffs while leaving the file's storage format unchanged.

While the thread has surfaced multiple ways to handle line ending presentation, the core tension remains between Git's attribute-based design for line ending control and some users' desire for simpler global configuration. Johannes's suggestion provides a practical workaround for diff readability, but doesn't resolve the underlying compatibility challenges Jason faces in their analysis tool workflow. The discussion highlights how Git's flexible but sometimes unintuitive line ending handling can create real-world friction for certain use cases.
