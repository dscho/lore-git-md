Platform compatibility discussion about line ending behavior on Windows, specifically with Git for Windows 2.47.0.windows.2. Jason Cho reported that `license_header.txt` (from DBeaver project) is checked out with CRLFs despite `core.eol=lf` and `core.autocrlf=false` settings. Torsten Bögershausen hypothesized the file was committed with CRLFs originally (which Git preserves by default), and Jason's follow-up `git ls-files --eol` output confirmed this (`i/crlf` stored, `w/crlf` checked out), proving the behavior is working as designed rather than being a Git for Windows bug.

Jason reveals their broader context: building a code analysis tool where line ending differences break string equality comparisons when tracking function movements between files. While acknowledging the standard solution (adding `* text=auto` to `.gitattributes` and creating a renormalization commit), they express a preference for simpler configuration via `core.eol` rather than managing attributes. This highlights a tension between Git's attribute-based line ending control design and Jason's desire for global configuration simplicity.

Key technical details established: the file's internal CRLF representation, consistent checkout behavior, and absence of overriding attributes. The discussion has shifted from diagnosis to workflow preferences, with open questions about whether `core.eol` should be enhanced for such use cases or if the attribute system remains the intended solution. The thread demonstrates Git's line ending conversion hierarchy where attributes take precedence over global configs, and surfaces a real-world use case where this design causes friction for tooling integration.
