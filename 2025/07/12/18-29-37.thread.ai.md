Thread identity: Proposal to improve git-submodule defaults and configuration, focusing on making submodule handling more intuitive for novices while preserving backward compatibility.

Core problem: Current submodule behaviors around pushing and cloning can lead to common pitfalls for new users, particularly around un-pushed submodule commits and uninitialized submodules after clone. The author identifies four specific pain points where defaults or config options could be improved.

Proposed changes:
1. Change default of `push.recurseSubmodules` from "no" to "check" when `submodule.recurse` isn't set, preventing accidental pushes of un-pushed submodule commits while avoiding automatic pushes.
2. Either modify existing "check" mode or add "checkStrict" mode to verify submodule references exist on the specific remote being pushed to, not just any remote.
3. Add `clone.recurseSubmodules` config option (defaulting to true) to automatically initialize submodules on clone, preventing common build failures.
4. Add `--builtin` flag to `git config get` to query default values, aiding in troubleshooting across different environments.

Current status: Initial proposal with no responses yet. Author has personally tested first and third proposals via config overrides. Seeking feedback on edge cases and current defaults' rationale.

Key technical details:
- Affects `push.recurseSubmodules` behavior and defaults
- Potential new "checkStrict" mode for submodule push verification
- New `clone.recurseSubmodules` config option
- New `--builtin` flag for `git config get`

Open questions:
