This is a follow-up in the ongoing discussion about `git imap-send` message marking behavior, focusing on the control interface design. Junio C Hamano pushes back against Aditya Garg's proposed simultaneous introduction of both a config option (`imap.markAsRead`) and command-line flag (`--mark-as-read`), arguing this appears poorly considered rather than deliberately designed.

The key technical point is that per-invocation control (via CLI option) should be the initial mechanism, with config coming later only if proven widely useful. Junio specifically questions whether the use case warrants persistent configuration at all, suggesting the need may vary situationally - particularly when considering future `send-email` integration where FCC copies might need different marking behavior than direct `imap-send` usage.

This elevates a previously secondary concern about control granularity to a primary design issue. The response also reinforces Junio's earlier code style critique as a mandatory change, while the curl version compatibility problem remains the most pressing technical blocker. The exchange continues to center on architectural decisions rather than implementation details, with Junio advocating for more deliberate feature introduction patterns in Git's established style.
