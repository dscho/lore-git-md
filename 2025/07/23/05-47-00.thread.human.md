This thread addresses a bug report and design discussion about how `git diff`'s content-ignoring options (like `-I<regex>` and `-w`) interact inconsistently with metadata-focused output formats (`--name-only`, `--name-status`). The original report from Lidong Yan showed that files filtered out of full diff output due to ignored changes would still appear in `--name-only` listings, creating a UX inconsistency.

After technical analysis confirmed this stems from Git's diffcore architecture (where content filtering happens too late for metadata outputs), Junio Hamano established the core design principle: metadata outputs deliberately avoid examining blob contents for performance. However, contributors like Arne and Jeff King argued this violates the principle of least surprise, showing cases where `--name-only` lists files that wouldn't appear in full diff output.

Lidong Yan proposed a patch introducing `diffcore_ignore()` to handle filtering earlier in the pipeline, making it apply consistently to human-readable formats while preserving current behavior for machine-readable outputs like `--raw`. The solution carefully balances UX consistency with performance needs and backward compatibility.

In the latest response, Junio raises two key concerns about the implementation: it narrowly focuses on `-I<regex>` while similar issues exist for other content-ignoring options like `-w`, and questions the efficiency of running diff operations twice. He suggests generalizing the solution to handle all `diff_from_contents` cases while maintaining performance. The discussion has now shifted from debating the core issue to refining the implementation approach, with Junio also providing guidance on commit message style. The patch appears headed toward acceptance once these architectural considerations are addressed.
