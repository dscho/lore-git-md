This thread examines an edge case in `git diff` where the `--ignore-matching-lines` option doesn't affect `--name-only` output, contrary to some users' expectations. The discussion began with Lidong Yan's bug report in Git 2.49.0, where technical analysis revealed this is intentional - metadata-focused outputs like `--name-only` avoid examining file contents for performance reasons, as Junio C Hamano authoritatively explained.

While the implementation makes technical sense (using SHA comparisons rather than content examination to generate metadata), Arne's latest contribution shifts the debate to user experience. They argue the current behavior violates the principle of least surprise, since files can appear in `--name-only` output that wouldn't show changes in a full diff. This creates a disconnect between what users might assume (that `--name-only` shows files with non-ignored changes) and what actually happens (showing files with any changes, ignoring content filters).

Eric Sunshine earlier improved the technical documentation around this behavior, including suggesting better citation formats. The core question remains open: should performance optimizations in metadata generation override user expectations about consistent behavior across diff output formats? While Junio's design principle stands firm, Arne's UX-focused perspective adds weight to considering whether the documentation should more prominently explain this potentially surprising interaction.
