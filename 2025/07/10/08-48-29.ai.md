Performance optimization for bloom filter pathspec handling in revision traversal. This is the final patch in a series that enables bloom filter optimization for multiple literal pathspecs while maintaining the fast path for single pathspecs.

The patch modifies `forbid_bloom_filters()` to allow bloom filter usage when all pathspec items are literal, removing the previous limitation that blocked multiple pathspecs. It updates the pathspec initialization loop in `prepare_to_use_bloom_filter()` to handle multiple items, creating a bloom keyvec for each literal pathspec. The test suite is expanded to verify:
- Bloom filters are now used for multiple literal pathspec combinations
- Wildcard-containing pathspecs still bypass bloom filters
- Results match non-bloom-filtered queries

Key technical changes include:
- Looping through all pathspec items in `forbid_bloom_filters()` to check for non-literal magic bits
- Using `revs->pruning.pathspec.nr` to determine keyvec count instead of hardcoding 1
- Proper cleanup of temporary path allocations in the multi-pathspec case
- New test cases covering combinations of literal pathspecs and wildcards

The implementation maintains all existing constraints:
- Still skips bloom filters for any pathspec with wildcards
- Preserves case-sensitive matching behavior
- Keeps the single-pathspec fast path (now handled as a special case of the general loop)

This completes the series' goal of optimizing combined pathspec queries while maintaining correctness. Performance measurements show significant speedups (0.24s vs 2.36s in LLVM repo tests) for the multi-pathspec case while keeping single-pathspec performance unchanged.
