This is part 3 of a 4-part performance optimization series for Git's pathspec bloom filters, introducing a new `struct bloom_keyvec` to manage multiple bloom keys. The change addresses a limitation where combined pathspec queries were slower than separate invocations.

The patch replaces the direct `struct bloom_key *` usage in `rev_info` with the new keyvec abstraction, which groups keys by pathspec items. The key change is moving from an "any key matches" condition to requiring that *all* keys in a keyvec report "definitely not changed" for a commit to be considered unchanged. This maintains the fast path for single pathspec cases while laying groundwork for future multi-pathspec optimizations.

New API functions `bloom_keyvec_new()` and `bloom_keyvec_free()` handle lifecycle management, while `bloom_filter_contains_vec()` checks all keys in a keyvec against a bloom filter. The implementation carefully handles path normalization and maintains existing case sensitivity behavior.

This is a well-structured change that clearly builds on prior review feedback, with thorough documentation and clean separation of concerns. The performance impact is already measurable (0.24s vs 2.36s for multi-pathspec queries in the LLVM repo), though the current patch still limits keyvecs to single pathspecs as a transitional step.
