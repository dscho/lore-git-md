This thread examines HTTP protocol compliance regarding language tag handling in Git's HTTP transport, specifically how to handle invalid locale values like "C" and "POSIX" in Accept-Language headers. The original patch proposed filtering these system locales to comply with IANA language tag requirements, modifying `http.c` with corresponding test coverage.

Junio Hamano initially questioned whether this addressed actual breakage or was purely preventative, referencing a GitLab issue that turned out to be unrelated. Brian Carlson clarified this is primarily a standards compliance improvement rather than a fix for observed problem, though it could prevent potential issues. Carlson also corrected a terminology error in the patch description that will be addressed in v2.

Collin Funk's recent contribution has expanded the discussion by questioning the fundamental approach. While acknowledging the practical constraints, Funk suggests Git could either accept all values or attempt proper BCP 47 language tag conversion, though recognizes this would require a comprehensive language database. This introduces new considerations about the balance between correctness and practicality, though without concrete proposals to change the current implementation.

The thread remains in a holding pattern awaiting Carlson's v2 submission, with open questions about whether this qualifies as a bugfix (which might expedite merging) versus a standards cleanup (which would follow the normal review cycle). The technical implementation continues to focus on filtering specific invalid locales while maintaining the existing test coverage.
