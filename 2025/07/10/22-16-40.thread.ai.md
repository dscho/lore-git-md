Thread concerns HTTP protocol compliance regarding language tag handling in Git's HTTP transport, specifically filtering invalid locale values ("C", "POSIX", and variants) from Accept-Language headers as these system locales violate IANA language tag requirements. The patch modifies `http.c` with test coverage in `t/t5541-http-push-smart.sh` verifying filtering behavior.

Junio Hamano initially questioned whether this addresses actual breakage (referencing GitLab issue gitlab-org/gitlab#412077 showing authentication failures) or is purely preventative standards compliance. Brian Carlson clarified the issue was only an example of incorrect header usage, not evidence of actual breakage. The change remains primarily a hygiene improvement to adhere to standards rather than a fix for observed problems, though it could theoretically prevent issues where users expect localized responses.

Collin Funk raised a more fundamental question about the approach - suggesting that instead of just filtering out "C" and "POSIX" locales, Git should either accept all values or attempt to map system locales to proper BCP 47 language tags. However, they acknowledged the practical limitation Carlson mentioned about requiring a comprehensive language tag database for proper conversion. Han Young expanded on these concerns, noting additional platform-specific challenges with musl's locale support and ambiguity in language matching (e.g., distinguishing pt_PT vs pt_BR), suggesting the simpler filtering approach may be more practical given cross-platform implementation complexity.

Carlson previously acknowledged Junio's correction about a terminology error in the patch description - "LANGUAGE header" should have been "LANGUAGE environment variable". This documentation clarification will be incorporated in a v2 patch while the technical implementation remains unchanged.

Technical implementation continues to target "C" and "POSIX" filtering in `http.c` per IANA standards. Open discussion points are: (1) whether this qualifies as a bugfix versus a refactoring (affecting merge timing), (2) whether selective filtering is preferable to comprehensive solutions like locale mapping given platform variability, and (3) whether to expand filtering beyond just "C"/"POSIX" to include other problematic locales. Test coverage in t5541 remains valid for verifying the filtering behavior. The thread awaits either further substantive feedback or the promised v2 submission.
