Bugfix for commit message comment character selection when conflict markers are present. This is the first patch in Ayush Chandekar's v5 series addressing issues with `core.commentChar="auto"`.

The patch fixes a specific case where Git would incorrectly consider conflict markers (like "<<<<<<<") as candidate comment characters during commit message editing, potentially causing these markers to appear in final commit messages. The solution modifies the character scanning logic in `builtin/commit.c` to ignore trailing comments (like conflict sections) when auto-selecting a comment character, preserving the original '#' character when appropriate.

The change is well-motivated, tracing the bug's origin to a 2024 rebase change (a6c2654f83) and including a new test case in t3418 that verifies the comment character remains stable during rebase operations with conflicts. The patch has been through multiple rounds of review with mentoring from Christian Couder and Ghanshyam Thakkar, and appears ready for inclusion.

This is part of a two-patch series that provides an interim solution until `core.commentChar="auto"` is removed in Git 3.0. The second patch (not shown here) standardizes the config-level behavior by resetting to '#' when auto-selection is enabled.
