Junio Hamano responds to the autostash configuration discussion with a nuanced technical analysis of the current behavior and its implications. This is a follow-up to Johannes Sixt's suggestion to document rather than validate the pull.autostash configuration.

Key technical points:
- Notes git_pull_config() currently honors rebase.autostash but not merge.autostash, calling this inconsistency
- Argues pull operations should be as cautious as manual rebases regarding autostash behavior
- Suggests two potential long-term solutions:
  1. Remove rebase.autostash support from git_pull_config() (breaking change for Git 3.0)
  2. Add pull.autostash that maps to the appropriate rebase/merge autostash setting
- Expresses personal preference against pull.autostash as it encourages less careful pull behavior

The email reveals deeper architectural questions about:
- Relationship between pull, rebase, and merge configuration
- Backward compatibility vs behavior consistency
- Whether pull should inherit or mirror rebase/merge settings

This moves the discussion beyond documentation to consider the underlying design principles for configuration inheritance between Git commands. Junio's mention of Git 3.0 as a potential breaking change milestone adds a new timeline consideration to the thread.
