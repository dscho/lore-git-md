Proposal for config validation architecture with registration mechanism.

Lidong Yan responds to Junio Hamano's concern about distinguishing core Git config from third-party extensions by proposing a registration-based validation system. The key idea is to have each subsystem explicitly register its known configuration keys and their validation functions through new `git_xxx_config_register()` hooks. This would allow both core Git and third-party code to participate in config verification.

The proposal outlines two concrete approaches:
1. Direct registration API where subsystems call functions like `register_bool_key()` for simple types or provide custom validation functions via a `struct key_ent` for complex cases
2. External specification files (`.gitconfigspec`) that could be loaded to validate config without modifying Git code

This builds on the earlier `git config verify` subcommand idea but addresses the critical extensibility requirement by making the validation system open to both core and third-party participation. The registration mechanism would allow Git to distinguish between legitimate unknown keys (registered by extensions) and likely typos (unregistered keys that match no known pattern).

The technical details suggest the validation would support:
- Basic type checking (bool, int, date)
- Custom validation functions for complex cases
- Both built-in and external specification of valid keys
- Clear separation between core and extension configs through explicit registration

This represents a significant architectural step forward from the previous discussion, moving from problem identification to a concrete technical proposal that attempts to satisfy all constraints (validation for core Git while preserving extensibility). The next steps would likely involve evaluating the implementation complexity of this registration system and whether it could be introduced incrementally.
