This is a cover letter for a bugfix series addressing issues with `core.commentChar="auto"` behavior during commit message editing. The series is now at v5 with two patches that together provide both an immediate fix and architectural standardization.

The first patch prevents Git from incorrectly scanning conflict markers (like "<<<<<<<") as potential comment characters when auto-selecting a comment prefix, which could lead to these markers appearing in final commit messages. The fix uses `ignored_log_message_bytes()` to properly bound the character scanning in `builtin/commit.c` and adds a test case in `t/t3418-rebase-continue.sh`.

The second patch implements Phillip Wood's architectural solution to standardize behavior by resetting `comment_line_str` to '#' when `core.commentChar` is set to "auto". This small but significant change (4 insertions, 2 deletions in `config.c`) ensures consistent behavior during configuration transitions and serves as an interim solution until `core.commentChar="auto"` is removed in Git 3.0.

The v5 update adds proper attribution to Phillip Wood for the second patch using a "Based-on-a-patch-by" trailer, as agreed with maintainer Junio Hamano. The series has received reviews from multiple contributors including Christian Couder and Kristoffer Haugsbakk, and is now considered complete and ready for inclusion. The changes affect rebase, cherry-pick, revert, and merge operations when conflicts occur, with test coverage verifying the fixes.
