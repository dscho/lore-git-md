This is the first patch in a two-part bugfix series addressing issues with `core.commentChar="auto"` when handling commit messages containing conflict markers. The patch specifically fixes a regression where Git would incorrectly scan conflict markers (like "<<<<<<<") as potential comment characters during rebase/cherry-pick operations, potentially causing these markers to appear in final commit messages.

The technical solution introduces a cutoff point in `builtin/commit.c` using `ignored_log_message_bytes()` to prevent scanning the trailing conflict marker section when auto-selecting a comment character. This ensures the original comment character ('#') is preserved when conflict markers are present. The change is verified by a new test case in `t/t3418-rebase-continue.sh` that confirms the comment character remains stable during a rebase with conflicts.

The patch addresses a regression introduced in commit a6c2654f83 ("rebase -m: fix --signoff with conflicts") where Git started including conflict comments in the message file. While the "auto" comment character feature was originally added in 2014 (84c9dc2c5a), this specific bug manifested after the 2024 change. The solution is cleanly implemented with minimal changes (6 lines modified) and includes thorough test coverage.

This patch represents the immediate bugfix portion of the series, while the second patch (not shown here) handles the architectural standardization aspect by resetting to '#' when `core.commentChar="auto"` is set. The series has gone through multiple iterations (now at v5) with mentoring from Christian Couder and Ghanshyam Thakkar, and appears ready for inclusion as an interim solution until `core.commentChar="auto"` is fully deprecated in Git 3.0.
