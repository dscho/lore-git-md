Documentation clarification regarding `git rebase` behavior and terminology. This is a follow-up to Rodney Bates' report about apparent contradictions in the `git rebase` man page.

Nico Williams responds to the original bug report by explaining that the confusion stems from interpreting the word "reset" in the documentation. The key clarification is that when the man page states "the current branch is reset to <upstream>", it means the branch pointer is moved to point to the same commit (changing the branch's history), not that the working tree switches to the upstream branch. This maintains consistency with the diagram showing the topic branch being rewritten while master remains unchanged.

The response focuses on terminology clarification rather than proposing documentation changes. It defends the current wording by explaining that "reset" in this context refers to Git's branch pointer movement operation, not a workspace switch. This interpretation aligns with Git's standard behavior where rebase always rewrites the current branch (topic in the example) rather than the upstream (master).

The exchange highlights a potential documentation pain point around the term "reset" which may confuse users familiar with other version control systems or general computing terminology. While not proposing specific changes, the response suggests the current text is technically accurate if read with precise Git terminology in mind. The thread remains open for further discussion about whether the documentation should be made more explicit about this behavior.
