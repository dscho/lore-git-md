Bug report for Git for Windows (not upstream Git) regarding file permission issues on Windows 11 Pro (10.0.22631). James Gao reports that Git 2.50.1 fails basic operations (git init, git add, git pull) with "Permission denied" errors when writing to .git/objects and index files, even as Administrator. The issue affects repository metadata and working tree files, persists across operations, and occurs on a fresh system with latest Git for Windows x64 build. Repository is confirmed on local NTFS drive (not cloud/network storage), and downgrading to Git 2.24.1.2 resolved the issues, suggesting a regression in Git for Windows 2.50.1's file handling on this specific configuration.

Brian m. carlson responded initially, unable to reproduce on Linux, suggesting Windows-specific factors. Provided troubleshooting steps: checking CIFS/SMB shares, avoiding special folders (Documents, OneDrive), using regular NTFS disks. Directed to Git for Windows issue tracker with specific diagnostic needs (storage location, filesystem type). Maintained this is likely environment-specific rather than universal regression.

Johannes Schindelin (Git for Windows maintainer) probed further about error message context and whether repository is on network drive. James Gao confirmed local NTFS storage and complete error messages, clarifying "lts" was a typo for "latest". While hesitant to test newer snapshots due to risk to 20+ local repositories, confirmed downgrade to 2.24.1.2 worked. Schindelin had suggested trying latest snapshot build before downgrading and linked possible duplicate GitHub issue. The thread remains focused on Windows-specific troubleshooting with no upstream Git implications identified. Open questions: whether issue reproduces in latest snapshot build, and exact nature of regression in 2.50.1's file handling on this configuration.
