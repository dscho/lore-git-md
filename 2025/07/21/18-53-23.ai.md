This is a discussion about naming and documentation clarity in the promisor-remote protocol extension series, specifically focusing on the terminology used for configuration variables in patch 2/5. The thread has reached v6 with all implementation aspects settled, but Junio Hamano raises concerns about the use of "field" terminology versus established "configuration variable" concepts.

Junio questions whether introducing new terminology ("field") for what are fundamentally configuration variables (like `remote.<name>.<variable>`) adds unnecessary confusion. He suggests the series should either:
1. Consistently use "configuration variable" terminology throughout, including renaming `promisor.sendFields`/`checkFields` to match, or
2. If keeping "field" terminology, properly standardize list parsing across Git first (which would significantly expand the series scope).

Christian Couder defends the "field" terminology as simpler for users, noting many existing config variables already accept comma/space-separated lists. In v6 he added clarifying documentation explaining "field" refers to remote config variable names/values, but Junio argues this creates a disconnect with Git's long-established configuration variable concepts.

The discussion reveals a tension points:
- Backward compatibility with existing list-parsing config variables
- Terminology consistency with Git's configuration model
- Whether to expand scope to standardize list parsing or keep focused on promisor functionality

Key technical references:
- `promisor.sendFields`/`checkFields` config variables
- Remote configuration variables (`remote.<name>.<variable>`)
- Existing list-parsing behavior in other config variables

This appears to be the final documentation-level discussion before potential merge, with all implementation aspects already resolved in v6. The outcome will affect how users interact with the new promisor remote validation features.
