This is a discussion about naming and documentation clarity in the promisor-remote protocol extension series, specifically around the "promisor.sendFields" and "promisor.checkFields" configuration variables.

Junio Hamano raises several concerns about the terminology and implementation approach in this v5/v6 patch series. The core issue revolves around whether to use the term "field" (a new concept in this series) versus the established Git configuration terminology of "variable" when referring to remote attributes like partialCloneFilter. Hamano argues that introducing new terminology ("field") for what are fundamentally configuration variables adds unnecessary confusion, especially since users will need to interact with these through existing remote.* config variables.

The discussion reveals a tension between maintaining consistency with existing configuration variable terminology versus introducing new domain-specific language ("fields") for the promisor protocol. Christian Couder defends the "field" terminology as being clearer in this context, though Hamano remains unconvinced. There's also debate about whether to support both comma and space separators in list values, with Hamano cautioning against perpetuating lenient parsing patterns.

This email captures important final review feedback on naming and documentation clarity before the series is merged. While the technical implementation appears settled (as noted in the thread summary), these interface design questions about terminology and user-facing documentation remain open for resolution between the maintainer and patch author.
