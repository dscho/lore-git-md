Bugfix for commit message comment character selection when conflict markers are present. This is part 1 of a 2-patch series addressing an issue where Git's auto-selection of comment characters incorrectly scans conflict markers (like "<<<<<<<") when core.commentChar is set to "auto".

The patch modifies the character scanning logic in builtin/commit.c to skip over trailing comment blocks (like conflict markers) when selecting a comment character. This prevents Git from mistakenly treating conflict markers as active comment characters, which could cause them to appear in final commit messages. The change uses the existing ignored_log_message_bytes() function to determine where to stop scanning.

A new test case in t/t3418-rebase-continue.sh verifies the fix by ensuring the '#' character remains the comment character even when conflict markers are present. The commit message provides clear background on when the bug was introduced (commit a6c2654f83) and acknowledges mentoring from Christian Couder and Ghanshyam Thakkar.

This appears to be a well-crafted fix for a real issue, with proper test coverage and clear commit message explanation. It's part of a larger discussion about how to handle comment character selection, with part 2 of the series addressing the architectural concerns through config standardization.
