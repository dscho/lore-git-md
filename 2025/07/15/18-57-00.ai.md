This is the first patch in a two-part bugfix series addressing issues with `core.commentChar="auto"` during conflict resolution operations like rebase. The patch specifically prevents Git from incorrectly considering conflict markers (like "<<<<<<<") as candidate comment characters when auto-selecting a comment character for commit messages.

The key technical change modifies `builtin/commit.c` to use `ignored_log_message_bytes()` to calculate a cutoff point in the message buffer, ensuring the character scanning loop stops before reaching conflict markers. This preserves the original '#' comment character when conflict markers are present, preventing them from appearing in final commit messages. The change is verified by a new test case in `t/t3418-rebase-continue.sh` that confirms the comment character remains stable during a rebase with conflicts.

The patch fixes a regression introduced in commit a6c2654f83 ("rebase -m: fix --signoff with conflicts") where Git started writing conflict comments to the rebase message file. While the immediate bug is fixed here, the second patch in the series will address broader architectural concerns about `core.commentChar="auto"` configuration handling. The solution represents a compromise between Chandekar's initial simpler approach and Phillip Wood's more comprehensive config-parsing solution that was discussed earlier in the thread.
