Bugfix for commit message comment character selection when conflict markers are present. This is part 1 of a 2-patch series addressing issues with `core.commentChar="auto"` during operations like rebase that involve conflict resolution.

The patch fixes a case where Git would incorrectly consider conflict markers (like "<<<<<<<") as candidate comment characters when auto-selecting a comment character, potentially causing these markers to appear in the final commit message. The solution modifies `adjust_comment_line_char()` in builtin/commit.c to skip scanning the trailing comment block (where conflict markers appear) when selecting the comment character, using the existing `ignored_log_message_bytes()` helper.

The change is well-motivated with clear background on when the bug was introduced (commit a6c2654f83) and includes a new test case in t3418-rebase-continue.sh that verifies the comment character remains stable when conflict markers are present. The patch has been through multiple iterations (now at v4) with mentoring from Christian Couder and Ghanshyam Thakkar, suggesting it's a well-vetted solution to a real problem.

This addresses the immediate bug while part 2 of the series handles the broader architectural concerns around config parsing. The fix is focused and maintains backward compatibility, making it a low-risk change that solves a concrete issue users might encounter during conflict resolution.
