This is the cover letter for v4 of a bugfix series addressing issues with `core.commentChar="auto"` behavior during commit message editing. The series now contains both the immediate fix for conflict marker scanning (patch 1) and the architectural standardization of comment character behavior (patch 2).

The first patch modifies `builtin/commit.c` to prevent Git from incorrectly considering conflict markers as candidate comment characters when auto-selecting a comment prefix. It introduces a cutoff calculation using `ignored_log_message_bytes()` to stop scanning at conflict markers, preserving the original '#' character. This fixes a regression from commit a6c2654f83 and includes a verification test in `t/t3418-rebase-continue.sh`.

The second patch standardizes behavior by modifying `git_default_core_config()` to reset `comment_line_str` to '#' when `core.commentChar` is set to "auto". This addresses architectural concerns about configuration state management while maintaining existing behavior for explicit comment character settings. The change is small (4 insertions, 2 deletions) but has significant implications for consistency across Git operations.

The series represents a compromise between Chandekar's initial surgical fix and Phillip Wood's more comprehensive config-parsing approach. It now awaits final review from Wood and Junio Hamano to confirm it properly handles all aspects of the issue while maintaining consistency with Git's configuration architecture. The solution specifically targets operations like rebase, cherry-pick, revert, and merge that involve commit message editing during conflict resolution.
