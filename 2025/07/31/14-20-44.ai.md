This is a technical follow-up in the Rust FFI type compatibility discussion within the xdiff optimization series. Phillip Wood questions the practical benefits of mirroring Rust primitive types (`u8`, `usize`, `u64`) in C structs when the Rust side will likely convert the data to idiomatic types like slices anyway. He raises two key points: (1) if Rust code constructs slices from pointer/length pairs for actual usage, the C-side type alignment provides little advantage, and (2) if data copying occurs anyway, one could just as well use standard C types (`*c_char`, `c_long`) in FFI boundary structs and convert during the copy.

The exchange highlights an implementation tension in the Rust-C interop strategy - while Ezekiel Newren previously argued that matching types reduces FFI errors, Phillip suggests this may be premature optimization if the Rust side performs conversions regardless. This probes whether the type alignment actually simplifies the code or just shifts complexity to different layers. The discussion remains focused on whether the proposed type changes in `xrecord_t` provide tangible maintainability benefits given real-world usage patterns in the Rust code.
