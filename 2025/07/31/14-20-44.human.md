This is a technical discussion about Rust FFI type compatibility in the ongoing Rust integration series. Phillip Wood questions Ezekiel Newren's proposal to make C structs use Rust-compatible types (u8, usize) for FFI purposes, focusing on practical usage patterns.

Phillip raises a key implementation concern: if Rust code will need to convert these FFI-compatible structs into idiomatic Rust types (like slices) anyway, then the benefit of changing C-side types may be minimal. He suggests that keeping standard C types (c_char, c_long) on the C side and doing type conversion in Rust might be simpler, especially if data copying is unavoidable.

The exchange highlights an important tension in the Rust integration effort - whether to optimize for clean FFI boundaries at the cost of C-side changes, versus minimizing C-side changes at the cost of more Rust-side conversion logic. Phillip's questioning suggests this design decision needs more concrete justification around actual usage patterns in the xdiff optimization work.
