This is a discussion about terminology in the ongoing promisor-remote protocol extension series, specifically around whether to use "field" or "configuration variable" in the naming and documentation of new features.

Christian Couder responds to Junio Hamano's concerns about terminology consistency in the v5/v6 patches. The key points of contention are:

1. **Terminology Debate**: Junio argues the new `promisor.sendFields`/`checkFields` configs should use "variable" terminology to match Git's established config model (section/subsection/variable), while Christian prefers "field" as a distinct concept for the protocol context. Christian suggests the protocol-transmitted values aren't truly mutable "variables" on the client side.

2. **List Parsing**: Junio notes the lenient comma/space list parsing in the current implementation perpetuates an existing anti-pattern. Christian acknowledges this but is waiting for consensus on whether to: (a) add a refactoring for standardized list parsing to this series, (b) handle it separately later, or (c) keep the current behavior.

3. **Documentation Clarity**: Christian added documentation in v6 explaining "field" specifically refers to the `<variable-name>` part of remote configs (e.g., `partialCloneFilter` in response to Junio's concern about confusion between "variable" and "field" terms.

The discussion remains unresolved, with Christian indicating willingness to change to "variable" terminology if that's the consensus, but noting potential confusion with environment variables and protocol semantics. The thread shows the series is otherwise technically complete (v6 implementation finalized, tests passing) with this being the last major design question before integration.
