This is a technical discussion about edge cases in the proposed rebase commit-skipping warning feature. Johannes Sixt (Hannes) raises important concerns about the fundamental assumptions behind detecting skipped commits during rebase conflict resolution.

Hannes challenges the core premise that Git can reliably determine why a commit becomes empty during rebase. He outlines several scenarios where the current detection approach would produce misleading warnings: manual conflict resolution followed by commit, resetting to a different commit, splitting changes, or making additional modifications. His key point is that Git cannot distinguish between these legitimate user actions and the specific case of skipping an already-applied commit.

The email directly addresses Cameron Steffen's suggestion that merely checking for no staged changes plus an active rebase commit would suffice for detection. Hannes argues this would generate false positives in real-world usage, as the rebase machinery cannot know what operations the user performed during conflict resolution. This critique aligns with Junio Hamano's earlier concerns about warning accuracy but provides concrete workflow examples where the warnings would be incorrect.

This intervention significantly complicates the feature's design, suggesting the warning system may need to be either much more sophisticated (tracking user actions during conflict resolution) or much more conservative (only warning in unambiguous cases). The discussion now appears to be shifting from implementation details to whether the feature's core premise is viable given real-world rebase workflows.
