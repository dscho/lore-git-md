Git thread summary:

Bug report and discussion about inconsistent path exclusion syntax handling between `git ls-files` and `git grep`, focusing on the `:^:Documentation/RelNotes` pathspec that works in `git ls-files` but fails in `git grep` with "ambiguous argument" error. Junio C Hamano initially confirmed the issue in `setup.c`'s filename verification path (`die_verify_filename()` and `looks_like_pathspec()`), noting the shorthand `:^:` syntax is deliberately confusing while the longhand `:(exclude)` form works correctly. D. Ben Knoble provided additional technical analysis showing `git grep` processes the argument differently - it fails in `verify_filename()` when `looks_like_pathspec()` only recognizes longhand magic. Debugging revealed the verification code doesn't properly handle the optional trailing colon in shorthand pathspecs, causing `check_filename()` to incorrectly try stat'ing the text after `:^:`. The discussion identifies the root cause as insufficient DWIM handling in `git grep`'s argument processing, with Junio cautioning about potential side effects of changing the behavior. Key technical details include the `!seen_dashdash` case in `git grep`'s argument handling and the difference in how `:^<path>` versus `:^:<path>` are processed. The thread remains open with the question of whether to fix the shorthand behavior or recommend the unambiguous longhand syntax.
