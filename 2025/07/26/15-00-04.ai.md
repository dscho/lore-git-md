This is a technical discussion about detecting skipped commits during rebase conflict resolution, part of the ongoing feature proposal to warn users about silent history modifications.

Cameron Steffen responds to Johannes Sixt's concerns about false positives in detecting skipped commits during rebase. The core challenge remains distinguishing between legitimate empty commits (which should trigger a warning) and other scenarios where users intentionally modify history during conflict resolution. 

Steffen suggests two detection mechanisms: (1) tracking whether the first post-conflict `git commit` is non-empty (indicating the pending commit wasn't skipped), and (2) emitting warnings when users hard reset before continuing. These aim to address Sixt's workflow examples where simple detection would fail, though the solutions still appear partial.

The exchange highlights fundamental limitations in Git's ability to track user actions during conflict resolution. While Steffen proposes narrowing the warning scope to more detectable cases, the discussion reveals deep technical challenges in achieving reliable detection without false positives. The thread continues to grapple with whether any warning implementation can be both accurate and useful given Git's current architecture.
