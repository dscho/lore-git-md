This is a technical discussion thread about the rebase warning feature for skipped commits. Junio Hamano points out a logical inconsistency in Cameron Steffen's proposed approach to detecting skipped commits during rebase conflict resolution.

The key issue revolves around distinguishing between different types of empty steps in a rebase operation. Hamano notes that Steffen's suggested warning message ("skipped previously applied commit") would be inaccurate if used for all cases where a commit becomes empty during conflict resolution, since the emptiness might not necessarily mean the commit was previously applied.

The discussion reveals a fundamental tension in the implementation:
1. Steffen wants to warn whenever a commit is skipped due to becoming empty, regardless of the reason
2. Hamano argues the warning should only trigger when we can definitively determine the commit was skipped because it was already applied

This exchange highlights that the current guard condition (checking `rebase_path_message()`) may not be sufficient for Steffen's broader detection approach. The thread shows the technical challenge has shifted from simply implementing a warning to properly modeling the rebase state machine to accurately classify different skip conditions.

The discussion remains focused on the sequencer.c implementation, with particular attention to how the warning interacts with `--skip` operations and the various pathways through the rebase state machine.
