Performance optimization and bugfix for `git remote rename` handling of symbolic refs.

This email from Junio Hamano reviews Patrick Steinhardt's work-in-progress patch that addresses both the symbolic ref handling bug and performance issues in `git remote rename`. The patch represents a significant improvement over the current implementation, reducing rename operations from potentially hours to just 7 seconds for repositories with 100k refs.

The key technical changes include:
- Introducing a single atomic transaction via new `queue_one_rename()` helper
- Using `refs_for_each_rawref` to handle all refs including unresolved ones
- Direct refname splicing without resolution/reconstruction
- Maintaining symbolic ref status through rename operations
- Leveraging Karthik Nayak's reflog migration infrastructure

Junio notes the patch's clean integration of the transaction mechanism into the existing `rename_info` structure and approves of the overall approach. He raises one potential concern about directory/file conflicts during rename operations that might mirror issues seen in recent ref transaction work, though this doesn't appear to be a blocker.

The patch still needs to implement reflog migration handling, which Patrick has noted should be straightforward. This appears to be the final piece needed before the comprehensive fix can be completed. The changes touch core ref handling in `builtin/remote.c` and interact with several ref-related APIs including `get_main_ref_store()` and `refs_for_each_rawref`.
