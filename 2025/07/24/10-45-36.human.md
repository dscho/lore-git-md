Bugfix for remote HEAD ref handling during rename operations. Jeff King responds to a report about `git remote rename` failing to properly transfer symbolic HEAD refs when the remote was created with `-m` and has an unborn HEAD. He confirms the bug and provides a simplified reproduction case.

The proposed fix involves two key adjustments to the remote rename logic: first, using `for_each_rawref` instead of `for_each_ref` to ensure all refs are processed, and second, adding `RESOLVE_REF_NO_RECURSE` to prevent unwanted recursion when resolving symbolic refs. The patch appears well-targeted to the specific issue while also considering edge cases like corrupt refs.

Jeff notes this relates to similar ref-handling challenges addressed in the newer `git refs migrate` command and CCs Patrick Steinhardt (pks) for potential code reuse. He also identifies a related bug where `git fetch` could overwrite an unborn HEAD ref when `remote.*.followRemoteHEAD` is set, suggesting this logic should preserve existing values.

The response demonstrates thorough understanding of the issue while keeping the fix focused. The additional bug mention shows attention to related edge cases without expanding scope unnecessarily.
