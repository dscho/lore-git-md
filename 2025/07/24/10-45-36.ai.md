Bugfix for symbolic ref handling during remote rename operations, particularly affecting unborn HEAD refs. Jeff King confirms the reported issue where `git remote rename` fails to properly transfer symbolic HEAD refs when the remote was created with `-m` flag. He provides a simplified reproduction case and proposes a two-part fix:

1. Modifies ref iteration to use `for_each_rawref` instead of `for_each_ref` to catch all refs including unresolved ones
2. Adds `RESOLVE_REF_NO_RECURSE` flag to prevent recursive resolution during the rename operation

The patch touches `builtin/remote.c`, specifically the ref handling logic in the `read_remote_branches` function and the ref iteration in `mv`. Jeff notes this relates to similar challenges faced in the `git refs migrate` command and suggests involving its author (pks) for potential code reuse. He also identifies a related bug where `git fetch` could incorrectly overwrite unborn HEAD refs due to overzealous `followRemoteHEAD` logic.

Key technical points:
- Original issue manifests when renaming remotes created with `-m` flag
- Fix requires changes to ref iteration and resolution behavior
- Potential follow-up needed for `followRemoteHEAD` logic
- References `RESOLVE_REF_READING` and `RESOLVE_REF_NO_RECURSE` flags
- Mentions `get_main_ref_store(the_repository)` API usage

The proposed solution appears well-reasoned and addresses the core issue while identifying related areas that may need attention. The reproduction case clearly demonstrates the problem and the fix's effectiveness.
