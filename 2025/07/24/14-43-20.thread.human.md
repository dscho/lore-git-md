This thread discusses a user experience improvement for `git rebase`. The core issue is that when a user resolves all conflicts during a rebase by completely removing changes (effectively dropping the commit), Git currently skips that commit silently. The proposal suggests adding an explicit notification when this occurs, since the silent behavior can lead to users unintentionally modifying their history without realizing it.

The change would modify the rebase machinery's output a message in these cases, likely in builtin/rebase.c. While a small change, it touches a fundamental workflow that many developers use daily. The proposal comes from a real pain point in interactive development, where the current behavior can cause confusion. There hasn't been prior discussion of this specific issue in the mailing list archives, making this a fresh proposal rather than a recurring request.

The key consideration will be balancing the need for clear feedback against keeping rebase output concise. The change aligns with Git's philosophy of making operations transparent, but would need to avoid adding unnecessary verbosity to what is already a complex command's output. No implementation has been proposed yet - this email is primarily raising the issue for discussion among maintainers and contributors familiar with the rebase machinery.
