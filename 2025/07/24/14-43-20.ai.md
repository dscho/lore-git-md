This is a feature proposal for the rebase command. The email suggests adding a notification when Git skips a commit during rebase due to the user resolving all conflicts by removing changes. Currently this happens silently, which can be confusing since users may not realize a commit was effectively dropped from their history.

The proposal comes from a real workflow pain point - when resolving rebase conflicts by removing all changes, the subsequent `git rebase --continue` skips the commit without any explicit feedback. This could lead to unintended history modifications going unnoticed. The author doesn't propose a specific implementation but raises the issue for discussion.

The change would affect the rebase machinery's user feedback system, likely modifying the output in builtin/rebase.c where conflict resolution messages are handled. While a small change, it touches a core workflow that many users interact with daily, so the UX implications would need careful consideration.

This seems like a reasonable quality-of-life improvement that aligns with Git's general philosophy of making operations transparent. The lack of prior discussion in the thread suggests this is a new proposal rather than a recurring request. The change would need to balance verbosity (adding yet another rebase message) against clarity (making important state changes visible).
