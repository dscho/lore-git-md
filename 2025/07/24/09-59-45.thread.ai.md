Bug report and fix for `git remote rename` symbolic ref handling:
- Subject: `git remote rename` fails to update unborn remote HEAD ref when created with `-m`
- Reporter: Unspecified (using Git 2.50.1 on Windows), confirmed by Jeff King (Peff)
- Core issue: Symbolic ref transfer during remote rename operations, particularly affecting unborn HEAD refs created with `-m` flag
- Current status: Jeff King has proposed a fix, Patrick Steinhardt (pks) has reviewed and identified broader architectural concerns
- Key technical details:
  - Broken sequence: `remote add -m <branch>` followed by `remote rename`
  - Problem: Old remote keeps HEAD ref while new remote gets non-symbolic HEAD
  - Expected: HEAD ref should transfer maintaining symbolic status
  - Fix approach:
    - Use `for_each_rawref` instead of `for_each_ref` to catch unresolved refs
    - Add `RESOLVE_REF_NO_RECURSE` flag during rename operation
  - Performance issues identified:
    - Current implementation creates N+M*2 ref transactions (inefficient for reftable)
    - Non-atomic operation (deletes before recreations)
    - Unnecessary `refs_resolve_ref_unsafe()` calls
    - Severe performance impact with large ref counts (100k refs taking hours)
  - Suggested improvements:
    - Single transaction approach
    - Leverage Karthik Nayak's reflog migration infrastructure
  - Affected files: `builtin/remote.c` (ref handling in `read_remote_branches` and `mv`)
  - Related APIs: `get_main_ref_store(the_repository)`, `RESOLVE_REF_READING`
- Open questions:
  - Need to reconcile immediate fix with broader ref migration redesign
  - Follow-up needed for `followRemoteHEAD` logic in `git fetch` that may overwrite unborn HEAD refs
  - Implementation strategy for atomic rename operation
- Related work:
  - Similar challenges faced in `git refs migrate` command
  - Potential interaction with ref backend abstraction work
  - Karthik Nayak's reflog migration infrastructure
- Participant positions:
  - Jeff King confirmed the issue and proposed fix
  - Patrick Steinhardt agrees with technical approach but highlights deeper architectural issues
  - Performance concerns raised regarding current implementation
- Reproduction remains valid:
  1. Create bare server repo
  2. Client: `git remote add -m main origin <url>`
