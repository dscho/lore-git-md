Bug report:
- Subject: `git remote rename` fails to update unborn remote HEAD ref when created with `-m`
- Reporter: Unspecified (using Git 2.50.1 on Windows)
- Core issue: Symbolic ref handling during remote operations when HEAD is unborn

Technical details:
- Triggered by sequence: `remote add -m <branch>` followed by `remote rename`
- Broken behavior: After rename, old remote keeps HEAD ref while new remote gets non-symbolic HEAD
- Expected: HEAD ref should transfer to new remote name maintaining symbolic ref status
- Affects: Remote HEAD ref handling in unborn state (no commits yet)
- Likely cause: Remote rename logic doesn't properly handle symbolic ref transfer for unborn HEAD

Reproduction:
1. Create bare server repo
2. Client repo: `git remote add -m main origin <url>`
3. Client repo: `git remote rename origin newname`
4. Observe HEAD ref remains at refs/remotes/origin/HEAD while refs/remotes/newname/HEAD becomes non-symbolic

Analysis:
- General logic bug, not Windows-specific
- Reproduction steps clearly demonstrate the issue
- Expected/actual behavior well-documented in report
