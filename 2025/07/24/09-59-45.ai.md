Bugfix targeting remote ref handling. This reports an issue where `git remote rename` fails to properly update the remote HEAD reference when it's in an "unborn" state (not yet pointing to any commit). The problem occurs specifically after using `git remote add -m` to set up a new remote with a default branch.

The bug manifests when:
1. Creating a bare server repo and a client repo
2. Adding a remote with `-m` to set the default branch
3. Attempting to rename that remote

Expected behavior is for the remote HEAD ref to be properly transferred to the new remote name, but instead the symbolic ref becomes invalid after the rename. The report includes detailed reproduction steps showing the HEAD ref remains with the old remote name while the new remote's HEAD becomes non-symbolic.

The issue appears to be in the remote rename logic's handling of unborn HEAD refs. The reporter is using Git 2.50.1 on Windows, but this seems like a general logic bug rather than platform-specific. The report is thorough with clear reproduction steps and expected/actual behavior comparisons, making it easy to verify.
