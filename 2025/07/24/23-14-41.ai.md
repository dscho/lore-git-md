This is a bugfix discussion regarding NFS permission handling in Git's packfile operations. Brian m. carlson responds to Tim Cederquist's report about `git clone` failing on FSx Ontap NFS storage due to fsync permission errors.

The core disagreement centers on whether Git should adapt to the NFS server's non-POSIX behavior or maintain strict POSIX compliance. Carlson argues this is clearly an NFS server bug since POSIX requires that open file descriptors ignore file mode restrictions for writing. They note the current 444 permission scheme is intentional - packfiles are meant to be immutable after creation, and write permissions aren't needed since deletion (via unlink) doesn't require them.

Carlson points out this affects other software (zsh, Emacs, other Git implementations) and suggests fixing the NFS server would be the proper solution rather than having Git work around non-compliant behavior. The response implies resistance to changing the permission scheme to 600 as suggested, as that would mask the underlying server compliance issue while potentially introducing other problems.

Key technical details include the POSIX requirement that open file descriptors ignore mode restrictions (O_RDWR should work regardless of 444 permissions), and the observation that this pattern is widely used across Unix software. The discussion highlights a tension between practical workarounds for real-world deployments versus maintaining standards compliance.
