This is the first patch in a bugfix series addressing `git apply --intent-to-add` behavior. The patch fixes incorrect index handling that has made the feature non-functional since Git 2.19 except in empty repositories.

The core issue is that `--intent-to-add` mode (which creates special index entries while applying patches to the worktree) wasn't properly reading the existing index before making changes. This caused it to clobber the index with an empty-tree state, incorrectly marking all existing files as deleted. The fix modifies `read_apply_cache()` in `apply.c` to read the index whenever it will be either checked or updated, since both operations require the current index state.

The patch builds on prior reports from Ryan Hodges and an original patch attempt by Johannes Altmanninger. The change is minimal (a single-line condition modification) but critical for correct behavior. The commit message provides clear technical rationale for why checking both `check_index` and `update_index` flags is necessary rather than just the latter.

This appears to be a well-constructed fix for a long-standing bug. The patch has already received Junio Hamano's approval in the thread discussion. It touches core apply functionality but in a focused way, with the change clearly scoped to fixing the index reading behavior while leaving other aspects of intent-to-add handling for subsequent patches in the series.
