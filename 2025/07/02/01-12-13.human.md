Performance optimization for `git fetch --prune`'s dangling ref reporting, part 1/3 of a series addressing quadratic time complexity. This patch replaces the current O(M*N) implementation (where M is pruned refs and N is total refs) with an O(N*logM) approach by sorting the prune list and using binary search, matching the algorithm already used in `git remote prune`. The author demonstrates dramatic improvements - from 410 CPU seconds and 3.6 billion strcmp calls down to under 1 second in a test case with 126k refs (pruning 28k). 

The patch modifies the warning message format to include both the dangling ref and the deleted ref name, as the new implementation no longer prints these adjacent in the output. Changes touch fetch and remote builtins plus refs.c, with careful handling of both dry-run and actual prune cases. The implementation appears clean and well-motivated, with a reviewed-by tag from Jacob Keller. This is clearly a significant performance win for repositories with many refs.
