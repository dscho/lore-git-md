Performance optimization for `git fetch --prune`'s dangling ref reporting.

This is a performance-focused patch series addressing a quadratic time complexity in `git fetch --prune` when reporting dangling refs. The current implementation uses nested loops comparing each ref to be deleted against all refs, leading to 2.6 billion strcmp calls in a real-world case with 15,000 refs being pruned from 174,000 total refs (taking 470 CPU seconds). The new approach sorts the prune list first, enabling binary search and reducing the operation to O(N*logN) time - the same case now completes in under 1 second.

The series consists of three parts: (1) the main optimization switching to the more efficient algorithm used by `git remote prune`, (2) removal of the old warning function, and (3) cleanup of the interface for dangling symref warnings. The output format is slightly adjusted to be more explicit about deleted branch names, though the author notes this was not strictly necessary as `git remote prune` already worked without this information.

Key technical details: The optimization involves restructuring the ref comparison to first sort the prune_refs list, then use binary search when checking each ref. The changes touch the fetch and remote builtins along with refs.c/refs.h interfaces. The dangling symref warning output now includes the deleted branch name explicitly due to the changed ordering.

This appears to be a well-motivated optimization addressing a clear performance bottleneck in large repositories. The patch series has gone through multiple iterations (now at v4) with the author noting they accidentally omitted the first commit in v3. The changes are focused and the performance impact is demonstrated with concrete metrics.
