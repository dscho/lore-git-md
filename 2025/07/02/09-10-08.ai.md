This is a discussion about path resolution functionality in the new `git repo-info` command, part of Lucas Seiki Oshiro's GSoC project. Phillip Wood responds to Lucas's consideration of adding special-case paths (grafts, index, objects, hooks) to match `git rev-parse --git-path` behavior.

Phillip raises two key concerns about the current approach: (1) maintaining duplicate path resolution logic in both `repo-info` and `rev-parse` risks future divergence, and (2) requiring users to manually concatenate paths (like hooks directory + hook name) creates unnecessary friction. He advocates for directly exposing the complete paths users need rather than just base directories. Phillip also suggests adding `git-prefix` to the planned fields (git-dir, common-dir, toplevel-dir, superproject-working-tree).

The email continues the thread's tension around command scope - while Lucas appears cautious about expanding path resolution, Phillip pushes for more comprehensive coverage that would subsume `rev-parse --git-path` functionality. This touches on the open question of command boundaries between `repo-info` and existing Git plumbing. The discussion remains technical and constructive, with Phillip focusing on user experience and maintenance concerns rather than outright rejecting Lucas's approach.
