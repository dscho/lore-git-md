This is a bugfix addressing memory detection on BSD systems, specifically focused on endianness handling in `git gc --auto`'s RAM calculation. The email responds to Junio Hamano's concerns about byte-order dependence in the v3 patch's bit-shifting approach for partial `sysctl()` returns. Carlo Marcelo Arenas Belón acknowledges the endianness issue and proposes a revised solution that:

1. Adds conditional compilation for big-endian systems (using `GIT_BYTE_ORDER`)
2. Maintains the `uint64_t` type change from v3 to avoid signedness issues
3. Shifts right (rather than left-then-right) on big-endian systems to properly clear upper bits
4. Still allows partial returns (unlike v2) but with safer handling

Key technical points:
- The fix targets `builtin/gc.c`'s `total_ram()` function
- Preserves the ability to work with 32-bit FreeBSD systems (which would always return 0 under v2's full-8-byte requirement)
- Introduces platform-specific logic only for big-endian architectures (primarily affecting PowerPC)

The discussion reveals ongoing tension between:
- v2's simpler "full 8-byte or nothing" approach
- v3's more complex but functional partial-return handling (now needing endian fixes)
- The practical reality that 32-bit FreeBSD systems would be locked out by v2's strictness

Carlo leans toward keeping partial return support with proper endian handling, arguing it provides better functionality for 32-bit systems with minimal overhead (since big-endian checks would only affect niche architectures). The thread remains unresolved on whether this complexity is justified versus reverting to v2's stricter but simpler approach.
