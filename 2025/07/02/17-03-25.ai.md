This is a review response in the ongoing thread about making reftable the default ref storage format. Junio C Hamano provides feedback on Patrick Steinhardt's patch series, focusing on the documentation and implementation details of the reftable transition.

Junio suggests enhancing the BreakingChanges.adoc documentation to more clearly articulate why making reftable the default is necessary, beyond just listing its technical benefits. He proposes adding language about the impracticality of requiring per-user opt-in to the superior format.

The review also discusses the implementation approach in setup.c, comparing it to brian m. carlson's SHA-256 transition strategy. Junio proposes a more centralized way to handle breaking changes via a dedicated header file (`<bc.h>`) that would collect all version-dependent defaults. This would make future transitions cleaner and provide better visibility into planned breaking changes.

Key technical points raised include:
- The current implementation uses direct conditionals in setup.c
- Alternative approach would use `REF_STORAGE_FORMAT_DEFAULT` macro
- Potential benefits of co-locating all breaking change defaults
- Backward compatibility considerations for the 3.0 transition

Junio notes that the test changes in t0001-init.sh look correct and straightforward. The review maintains a generally positive tone while suggesting architectural improvements to the breaking change infrastructure. This positions the reftable transition as part of a larger pattern of versioned defaults that may need coordinated management.
