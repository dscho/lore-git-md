Performance optimization for `git fetch --prune`'s O(N²) slowdown. 

Phil Hord addresses a severe performance issue where `git fetch --prune` could take nearly 8 minutes (470 CPU seconds) when pruning 15,000 refs from a repository with 174,000 refs. The bottleneck occurs because the current implementation uses nested loops comparing each prune candidate against every ref, making 2.6 billion strcmp calls. 

The patch replaces this with the more efficient O(N*logN) algorithm already used by `git remote prune`, which first sorts the prune list for binary search. While functionally equivalent, this changes the output order of dangling ref warnings - a minor behavioral difference that the patch explicitly handles by improving the warning messages. 

This v3 iteration cleans up the API interface and removes some questionable ref-shortening logic from earlier versions. The changes touch core refs handling code across builtin/fetch.c, builtin/remote.c and refs.c, suggesting careful review is warranted given the performance-critical nature of this code path. The dramatic speedup (470s → <1s in the test case) makes this a high-value optimization for repositories with many refs.
