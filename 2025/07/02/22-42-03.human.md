This is a follow-up in the ongoing bugfix thread about BSD system memory detection for `git gc --auto`. Carlo Marcelo Arenas Belón responds to Junio Hamano's concerns about the v3 patch's handling of partial `sysctl()` returns.

The key issue is that v3's bit-shifting approach to handle partial memory reports (less than 8 bytes) was incorrect on big-endian systems and could produce wrong values. Carlo acknowledges the problem and proposes a revised version that would:
- Only apply the shift on big-endian systems (using `GIT_BYTE_ORDER`)
- Keep the `uint64_t` type change from v3 to avoid signedness issues
- Still allow partial returns (unlike v2's strict 8-byte requirement)

However, Carlo notes that reverting to v2's simpler approach (only accepting full 8-byte returns) might be better, though it would mean 32-bit FreeBSD systems would always report 0 memory. The discussion continues to weigh the tradeoffs between robustness (v2) and broader compatibility (v3 with fixes).

This email shows the careful iteration happening in this thread, with each version addressing prior concerns while sometimes revealing new edge cases. The core question remains whether to accept partial memory reports at all, or require full 8-byte returns for safety.
