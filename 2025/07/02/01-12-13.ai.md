Performance optimization for `git fetch --prune`'s dangling ref reporting, addressing a known quadratic time complexity issue. This is the first of three patches in v4 of the series, implementing the core algorithmic improvement.

The patch replaces the existing O(M*N) implementation (where M is pruned refs and N is total refs) with an O(N*log(M)) approach by sorting the prune list and using binary search, matching the algorithm already used in `git remote prune`. The author provides concrete metrics showing the change reduces runtime from 410 seconds to under 1 second in a test case with 126k refs (pruning 28k). The message format is adjusted to include the deleted ref name since the warning is no longer emitted immediately after the deletion line.

Changes span `builtin/fetch.c`, `builtin/remote.c`, and `refs.c`, with the main work in restructuring the prune logic to first collect and sort refs before checking for dangling symrefs. The warning message format is updated in both fetch and remote to explicitly show which deletion caused each dangling ref, though this appears to be a side effect of the implementation change rather than a primary goal. The patch carries a Reviewed-by from Jacob Keller and appears technically sound, building on established patterns from `git remote prune`.
