This is a brief technical note about case-insensitive filesystem behavior, expanding on the ongoing discussion about `git pull --prune` failures. Chris Torek points out that on macOS, Unicode normalization (not just case folding) can cause path collisions, using the example of German umlauts that can be represented in multiple Unicode forms. He notes this creates additional complexity to the already tricky problem of reference pruning on case-insensitive systems, though he doesn't propose a specific solution.

The email serves as a useful reminder that the strmap-based approach being discussed would need to handle not just case differences but also Unicode normalization forms to be fully robust on macOS. This reinforces the earlier arguments from brian m. carlson and Patrick Steinhardt that the reftable backend may be the more comprehensive long-term solution, as it avoids filesystem-level naming issues entirely. The note doesn't change the direction of the thread but adds another data point about the challenges of the current filesystem-based ref storage.
