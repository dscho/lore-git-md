This thread discusses a performance optimization for `git fetch --prune` when reporting dangling refs. The current implementation has a quadratic time complexity that becomes painfully slow in repositories with many refs - in one real-world case with 15,000 refs being pruned from 174,000 total, it took 470 CPU seconds due to 2.6 billion string comparisons.

The patch series proposes switching to a more efficient algorithm that first sorts the prune list, enabling binary search and reducing the operation to O(N*logN) time. The same test case now completes in under 1 second. The changes consist of three parts: the main optimization, removal of the old warning function, and cleanup of the dangling symref warning interface. The output format is slightly adjusted to be more explicit about deleted branch names, though the author notes this was more for consistency than necessity.

The series is now at version 4, with the author correcting an earlier omission from v3. The changes are focused on the performance bottleneck and have been tested with concrete metrics showing significant improvement. The optimization touches the fetch and remote builtins along with refs.c/refs.h interfaces, restructuring the ref comparison logic to use sorting and binary search. This appears to be a well-motivated improvement for large repository workflows.
