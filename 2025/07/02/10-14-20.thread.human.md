Patrick Steinhardt's proposal to make reftable the default ref storage format in Git 3.0 has drawn its first substantive review from maintainer Junio Hamano. The thread began with Patrick's two-patch series documenting the planned breaking change and implementing an experimental flag to enable early testing. Junio's response focuses on improving both the documentation and implementation approach.

Junio suggests expanding the BreakingChanges.adoc documentation to better explain why a default switch is necessary, moving beyond just listing reftable's technical advantages (like atomic writes and better Unicode handling) to address the impracticality of expecting every user to manually opt-in to the superior format. On the implementation side, he draws parallels to brian m. carlson's SHA-256 transition work and proposes a more systematic approach to handling breaking changes - suggesting a dedicated header file to centralize version-dependent defaults like the ref storage format. This would both clean up the current conditional logic in setup.c and provide better visibility into future planned changes.

While the technical discussion continues, the review maintains a constructive tone, with Junio explicitly approving the test changes in t0001-init.sh. The thread now awaits responses from other key stakeholders like Karthik Nayak (co-developer of the reftable integration) and brian m. carlson (who led the SHA-256 transition), as well as feedback from the broader ecosystem including libgit2 and JGit maintainers. The proposal appears to be on a good trajectory, with the maintainer's feedback focusing on making the transition infrastructure more robust rather than questioning the fundamental direction.
