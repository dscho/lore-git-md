This is a follow-up in the ongoing Windows DFS-mounted network drive regression thread, providing additional technical details about the network setup where Git fails with "Permission denied" errors during config file operations.

Erwan Leroy clarifies their organization's three-tiered storage architecture: 1) Direct Samba shares (working UNC paths like `\\atl-xx\Basecamp`), 2) DFS namespace (`\\xxx.local\Basecamp` resolving to those UNC paths - where Git fails), and 3) Drive-letter mappings (Y: drive pointing to DFS paths - also failing). The key new information confirms that drive-letter access failures are indeed just manifestations of the underlying DFS path issue, while direct UNC paths and local drives work correctly.

The email reinforces the version-specific nature of the problem (working in Git <=2.21, broken in >=2.36) and expresses intent to use the pre-compiled version archive provided by Johannes Schindelin to help bisect the regression. No new error cases or technical analysis is presented beyond the network topology clarification, but the detailed description of the DFS/UNC relationship may help diagnose why Git's file operations succeed on seemingly similar paths.

For future reference in this thread: The core issue involves `rename()` operations on `.git/config.lock` files specifically when accessed through DFS paths, with working cases including direct UNC paths and local drives. The affected versions span Git 2.21 through at least 2.50, with bisection still needed to pinpoint the exact breaking change. Network configuration specifics now include DFS namespace usage (`\\xxx.local\Basecamp`) resolving to working UNC paths, with drive letters inheriting the DFS behavior.
