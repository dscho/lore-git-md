This is the cover letter for version 2 of a series implementing SHA-256 as Git's default hash algorithm when built with WITH_BREAKING_CHANGES, preparing for Git 3.0. The series builds on earlier work to make Git's internals hash-agnostic and now takes the next step by making SHA-256 the default while maintaining backward compatibility.

The key changes in v2 include renaming of constants (GIT_HASH_ORIGINAL becomes GIT_HASH_SHA1_LEGACY for clarity, adding a build option to control the default hash in tests, and improved commit messages addressing review feedback. The series carefully distinguishes between explicit SHA-1 usage (GIT_HASH_SHA1), legacy SHA-1 fallback (GIT_HASH_SHA1_LEGACY), and the new default (GIT_HASH_DEFAULT).

The implementation handles several tricky edge cases: repository initialization when no hash is specified, version-less repositories defaulting to SHA-1 for backward compatibility, and proper rejection of v1-only extensions in v0 repos. The test suite has been expanded to verify behavior across different repository formats and configurations.

An ongoing discussion point is how commands that operate outside repositories (like index-pack and ls-remote) should behave - whether to use the new default (SHA-256) for forward compatibility or maintain SHA-1 behavior for script compatibility. The author argues for the former while Patrick Steinhardt prefers the latter. This remains unresolved in this version.

The series appears thorough and well-tested, with careful consideration of backward compatibility while moving toward SHA-256 as the default. The changes are focused on the build system and internal constants rather than user-facing behavior (when not using WITH_BREAKING_CHANGES), making this a safe step toward the eventual Git 3.0 transition.
