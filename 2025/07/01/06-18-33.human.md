This is a bug report thread about Windows DFS-mounted network drive compatibility, specifically a regression in Git versions 2.36+ where config file operations fail with "Permission denied" errors. Erwan Leroy provides additional details about their network setup in response to Johannes Schindelin's request for clarification.

The key new information is a three-tiered network architecture: direct Samba shares (working with Git), DFS namespace (failing with Git), and drive-letter mappings to DFS (also failing). Erwan confirms that drive letters mapping to local filesystems work fine, while those pointing to DFS paths exhibit the same failure as accessing DFS directly via UNC paths.

The thread remains focused on diagnosing a regression that appears between Git 2.21 and 2.36, with Schindelin having provided resources for version bisection. The specific failure occurs during config file operations when Git attempts to rename lock files, but the exact cause remains unclear. Erwan plans to use the provided Git for Windows snapshots to help narrow down the problematic version range.

This appears to be a genuine regression affecting real-world Windows enterprise environments using DFS, though the technical details of the failure mode still need to be pinned down. The discussion is methodical and cooperative, with both parties working to isolate the specific conditions that trigger the bug.
