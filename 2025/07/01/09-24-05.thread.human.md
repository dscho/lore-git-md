Here's the updated human-readable thread summary:

Dilyan Palauzov reported a concerning bug where treeless and blobless clones (created with `--filter=tree:0`) would fail on the first `git pull` attempt after a 5-day delay, showing missing object errors that suggested repository corruption. The second pull would then succeed, fetching a small number of objects. This pointed to an inconsistency between the commit graph and object database in how promisor remotes handle missing objects.

Jeff King has now provided a thorough analysis and proposed solution. He identified a race condition where maintenance repacks can make objects temporarily unavailable between commit graph lookups and object database checks. His fix modifies `fetch-pack.c` to recheck packed objects when verifying existence after finding them in the commit graph. The change is carefully considered - while normally expensive, this recheck is justified when we already have the commit graph, as it implies the objects should exist locally.

The investigation also revealed deeper questions about how filtered clones should handle submodule operations, particularly when parent trees are missing), but these are noted as separate from the immediate race condition fix. King suggests involving Jonathan Tan for review given his promisor remote expertise. This appears to be a well-researched solution to a real edge case in partial clone behavior, though focused, may lead to broader discussions about submodule handling in filtered repositories.
