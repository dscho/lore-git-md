A bug report from Дилян Палаузов highlights a concerning issue with treeless and blobless clones in Git 2.50.0. The problem occurs when performing a filtered clone (either tree:0 or blobless) and then waiting several days before running `git pull`. The first pull attempt consistently fails with errors about missing objects and repository corruption, while a second attempt succeeds by fetching the missing objects.

The reporter provides clear reproduction steps showing that the initial clone works correctly, but after time passes, Git incorrectly reports corruption when objects are missing from the commit graph but still available from the promisor remote. This suggests a bug in how partial clones handle object availability checking over time, particularly around the interaction between commit graphs and promisor remotes.

While the workaround of running `git pull` twice works, this is clearly not ideal behavior. The well-documented report with consistent reproduction makes this a solid candidate for investigation by the partial clone/promisor remote maintainers. The issue appears to be in the core functionality of filtered clones rather than being repository-specific.
