This is a discussion about the behavior and interface of the new `git last-modified` command, which tracks file modification history. Kristoffer Haugsbakk raises several points about the command's path handling that may surprise users.

The command currently shows inconsistent behavior between top-level files and files in subdirectories. Without `-r`, it reports directories rather than individual files when given subdirectory paths, while still showing individual files at the top level. This differs from other Git commands where pathspecs typically match files directly regardless of depth.

The `-r` flag enables full recursion, but Kristoffer suggests the default behavior should be more intuitive - either always showing individual files (with recursion controlled separately) or being consistent about directory vs file output. They demonstrate how pathspec magic still works as expected, but argue the basic case should be more straightforward.

The thread context shows this is part of the final polishing phase for the `last-modified` command, which has already gone through several rounds of performance optimization and naming changes. The current implementation shows significant speed improvements (36-50% in common cases) but this email focuses on usability concerns rather than technical implementation.

This appears to be one of the last remaining design questions before the command could be considered for merging, alongside some minor style fixes mentioned in the thread. The discussion suggests the command is otherwise functionally complete and well-tested, but may need tweaks to match user expectations around path handling.
