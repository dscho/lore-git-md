This is a bug report about an issue with treeless and blobless clones. The reporter, Дилян Палаузов, documents a consistent problem where after performing a filtered clone (either `--filter=tree:0` or blobless), waiting some time (in this case 5 days), and then running `git pull`, the first attempt fails with errors about missing objects and repo corruption, while the second attempt succeeds.

The key technical details are:
- The initial clone works fine (`git show` shows expected commit)
- After time passes, the first `git pull` fails with messages about missing objects in the commit graph but not object database, suggesting corruption
- The second `git pull` succeeds, fetching 22 objects (137.56 KiB) and fast-forwarding
- The issue appears consistently across different repositories
- Git version 2.50.0 is affected

The error messages suggest the promisor remote (used for partial clones) is not properly handling the case where commit graph information exists but some objects are missing. The workaround of running `git pull` twice is noted, but this is clearly not ideal behavior.

This appears to be a real bug in how partial clones handle object availability checking over time, likely related to the interaction between commit graphs and promisor remotes. The report is well-documented with clear reproduction steps and version information, making it a solid bug report that warrants investigation by the partial clone/promisor remote maintainers.
