This is a bug report about partial clones (treeless and blobless) where `git pull` fails on the first attempt after some time has passed since the initial clone, but succeeds on a second attempt. The reporter, Дилян Палаузов, provides a detailed reproduction showing that after a treeless clone, waiting several days, then running `git pull` results in errors about missing objects that appear to be in the commit graph but not the object database. The second `git pull` then completes successfully.

The issue appears consistently across different repositories and seems related to how partial clones handle fetching objects after some time has elapsed. The error messages suggest Git thinks there's repository corruption when trying to fetch objects that should be available from the promisor remote. The reporter is using Git 2.50.0 and includes the complete output showing the failed and successful pull attempts, plus the resulting changes from the successful pull.

This looks like a legitimate issue in partial clone behavior that could affect users relying on these space-saving clone options. The report is well-documented with clear reproduction steps and version information, making it easier for maintainers to investigate. The problem appears to be in the interaction between the commit graph and promisor remote functionality when fetching updates after time has passed.
