This is a discussion follow-up in the SHA-256 default hash algorithm transition series, specifically addressing the distinction between explicit SHA-1 usage and legacy SHA-1 fallback behavior.

Patrick Steinhardt responds to brian m. carlson's explanation of the new hash algorithm constants (GIT_HASH_SHA1 vs GIT_HASH_ORIGINAL/LEGACY_SHA1). He agrees with the semantic distinction, noting it clarifies previously ambiguous cases in the code where SHA-1 usage wasn't clearly intentional. The discussion focuses on two key scenarios: command-line explicit SHA-1 selection (GIT_HASH_SHA1) versus format-implied legacy behavior (GIT_HASH_ORIGINAL).

Steinhardt provides a concrete example from the reftable format, where version 1 implicitly uses SHA-1 (GIT_HASH_ORIGINAL) while version 2 explicitly specifies the hash algorithm (GIT_HASH_SHA1 or GIT_HASH_SHA256). This illustrates the value of the distinction for understanding format-specific requirements. The exchange confirms consensus on the constants' semantic meaning while acknowledging they will always share the same numeric value (SHA-1) in practice.

The discussion doesn't introduce new technical changes but reinforces the design rationale behind the hash constant separation that was previously established in the series. It shows the distinction is being validated by other contributors who have encountered similar ambiguity in the codebase.
