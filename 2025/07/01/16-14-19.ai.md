This is a maintainer response in the ongoing discussion about case-insensitive filesystem handling and reftable adoption. Junio C Hamano replies to Patrick Steinhardt's push for making reftable the default backend, expressing surprise that reftable isn't mentioned in Git 3.0's planned breaking changes. He endorses using `features.experimental` as the opt-in mechanism, noting it already controls four other settings. 

Junio acknowledges the script compatibility concerns Patrick raised, but suggests the plumbing commands Patrick has developed should cover most direct filesystem access needs. He proposes creating migration documentation to help users transition away from direct `.git/refs/` manipulation, positioning this as a solvable problem rather than a blocker. The tone suggests strong support for reftable adoption while recognizing the need for careful transition planning.

Key technical points mentioned include:
- Current `features.experimental` controls 4 config variables
- Documentation gap in Git 3.0 breaking changes
- Plumbing command coverage for ref operations
- Need for migration guide targeting script authors

This moves the reftable discussion forward by:
1. Confirming experimental flag as viable opt-in path
2. Identifying documentation work needed (breaking changes + migration guide)
3. Downplaying script compatibility as an absolute blocker
4. Maintaining momentum toward eventual default status while acknowledging transition requirements

The exchange solidifies reftable's position as the preferred solution to the case-sensitivity issues while addressing practical adoption concerns. Junio's response suggests the technical merits are convincing and the remaining work is primarily around documentation and ecosystem preparation.
