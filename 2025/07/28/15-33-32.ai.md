This is a feature patch discussion regarding the `git reflog write` subcommand implementation in Patrick Steinhardt's reflog migration series. Kristoffer Haugsbakk raises an important usability concern about refname resolution behavior in the new subcommand.

The key issue is that while `git reflog show` automatically resolves shorthand branch names (like "branch") to their full refname ("refs/heads/branch"), the new `write` subcommand requires explicit full refnames. This creates an inconsistency where writing to "branch" actually creates a reflog entry for the one-level ref "branch" rather than the expected branch ref, which could mislead users into thinking they truncated the branch's reflog when they actually created a separate one.

Kristoffer points out this differs from other reflog subcommands like `drop` which handle shorthand names as expected. The documentation currently doesn't warn about this behavior or guide users toward using full refnames. This could lead to confusion and potential data integrity issues if users accidentally create reflog entries in the wrong location.

The discussion connects to the ongoing reflog infrastructure work by highlighting a user-facing inconsistency in the new subcommand's behavior compared to existing reflog operations. While the technical implementation of writing reflog entries is sound (as established in previous thread discussion), this feedback suggests the need for the new subcommand to either:
1) Match the automatic refname resolution behavior of other reflog commands, or
2) Explicitly document and warn about the stricter refname requirements

The thread context shows this is part of a mature series (now at v2) that's already addressed several technical challenges around reflog migration between storage backends, with recent focus on OID handling and flag behavior. This new feedback shifts attention to the user experience aspects of the new functionality.
