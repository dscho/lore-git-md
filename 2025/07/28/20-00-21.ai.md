Technical clarification on C/Rust type compatibility in xdiff FFI.

This is a follow-up to the ongoing discussion about type alignment between C and Rust in the xdiff subsystem, specifically regarding the `char` type. Collin Funk provides a precision to Ezekiel Newren's earlier statement about C treating `char` as signed 8 bits, noting that the C standard actually leaves `char` signedness implementation-defined. They demonstrate this with a portable test program showing `char` is signed on x86_64 Linux but unsigned on aarch64 Linux.

This reinforces the importance of using explicit types like `u8` in the Rust FFI interface rather than relying on C's `char` semantics, as the Rust side needs consistent byte-oriented behavior regardless of the C implementation's `char` signedness. The email doesn't propose any code changes but provides important context for the cross-platform implications of the type system decisions being made in the xdiff Rust integration work.

The observation is particularly relevant given the thread's broader discussion of platform compatibility challenges, where such implementation-defined behaviors could surface differently across architectures. This fits into the series' ongoing work to ensure robust FFI boundaries between C and Rust components, where precise type matching affects both correctness and performance.
