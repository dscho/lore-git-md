This is a continuation of the thread about `-h` behavior with Git aliases, focusing on how to handle help requests when aliases inject additional arguments. Junio Hamano responds to Jeff King's observations about edge cases where alias-injected arguments can cause `-h` to unexpectedly run commands rather than showing help.

Hamano strongly agrees with the core fix (showing alias info for lone `-h`) but pushes back against Jeff's more complex proposal to strip alias-injected flags when processing `-h`. He argues this would introduce "voodoo magic" into Git's alias handling. Instead, Hamano advocates for a simpler approach: always stopping after showing the alias expansion when `-h` is present, regardless of whether the alias is a built-in command or shell command.

The discussion reveals a philosophical divide - Jeff wants to make `-h` work intuitively even with complex aliases, while Hamano prefers a simpler, more predictable model where `-h` strictly shows the alias definition. Hamano does endorse one of Jeff's suggestions: preventing shell command aliases from executing when `-h` is present, calling this a clear improvement.

This email moves the thread from technical edge cases toward a design decision about Git's alias philosophy - whether to make `-h` "just work" through special handling (Jeff's view) or maintain strict textual substitution by having users manually reconstruct commands after seeing alias definitions (Hamano's preference). The tone remains constructive, with both agreeing the initial fix is worthwhile while debating how far to extend it.
