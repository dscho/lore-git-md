Performance optimization series for xdiff string hashing, building on Phillip Wood's prior refactoring work. Alexander Monakov proposes speed improvements through two key changes: (1) splitting xdl_hash_record() into verbatim and whitespace-aware variants (8% speedup in git log benchmarks), and (2) implementing an optimized djb2 hash variant (1.5x speedup target) inspired by but independently implemented from Glibc's ELF symbol lookup approach. The changes focus on xdiff/xutils.{c,h} with minimal diff noise (17 lines net added in first patch, 66 lines modified in second).

Monakov has clarified the licensing situation - while inspired by Noah Goldstein's Glibc implementation, his version is an original work adapted for xdiff's length-bounded strings rather than NUL-terminated ones, making it GPLv2-compatible. Junio Hamano has now accepted this after Eli Schwartz's earlier license compatibility verification.

Phillip Wood's benchmarking shows mixed results: hyperfine measurements indicate only 2% speedup over previous patch (1.02x) and 11% over master (1.11x) for `git log`, with his xxhash implementation still 3% faster (1.03x). He used GCC with -O2 -march=native on an i5-8500, noting similar inlining benefits with xxhash. This contrasts with Monakov's earlier cycle-based measurements showing 7-11% improvements. Phillip questions whether the REASSOC_FENCE macro's compiler-specific optimization justifies maintenance costs given modest real-world gains and existing alternatives.

Monakov provides additional benchmark data from a Skylake processor showing 7.6-12% speedups (versus 2.7-10% on Phillip's i5-8500), with the combined patches delivering better relative improvement on this architecture. Phillip confirms the revised benchmark table format is clearer, now showing pre-calculated speedup percentages alongside raw cycle and instruction counts. He clarifies his testing setup - using GCC 12.2.0 on an i5-8500 with -O2 -march=native, and notes he used the system xxhash library rather than compiling it himself.

Technical discussion reveals key nuances: Phillip confirms no measurable difference with/without REASSOC_FENCE on his hardware, while Alexander explains why standard C atomics wouldn't achieve the same effect (they only constrain memory ordering, not register evaluation). Phillip acknowledges this distinction makes sense. The exchange highlights remaining open questions about cross-platform behavior - Phillip's Coffee Lake i5-8500 shows smaller gains than Alexander's Skylake benchmarks, and they discuss whether to conditionally enable optimizations based on compiler/architecture. Phillip indicates he may try 'perf stat' measurements for better cross-CPU comparability but notes limited availability in the near term.

Key open questions remain about: (1) reconciling performance measurement discrepancies across architectures (Skylake vs Coffee Lake), (2) cross-platform behavior implications, (3) whether to conditionally enable the optimization only on x86_64 with GCC/Clang, and (4) validating real-world impact through standardized benchmarking.
