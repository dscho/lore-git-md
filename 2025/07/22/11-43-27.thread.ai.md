Git imap-send documentation update. Thread root introduces a patch improving the `git imap-send` man page by adding a new section explaining the `--list` option for discovering IMAP folders, with Gmail as a concrete example showing client-visible vs server-side folder name mapping (e.g. "Junk" -> "[Gmail]/Spam"). Version 2 follows up with a minor but important wording fix, changing "need to be" to "need not be" when describing the relationship between client and server folder names. The documentation clarifies how to interpret verbose IMAP LIST output to determine correct folder names for patch submission, with annotated example output showing Gmail's specific naming scheme while noting the approach generalizes to other providers. No code changes - purely a documentation improvement addressing a common point of confusion.

Junio C Hamano responds to Aditya Garg's patch, agreeing the current docs are insufficient but questioning whether verbosity is the core issue. He suggests the unfriendliness of exposing raw IMAP protocol messages (with attributes like `\HasNoChildren` and server-side paths such as "[Gmail]/Spam") might warrant a code change to present folder names in a more user-friendly way rather than just documenting the current output format. 

Aditya Garg replies to Junio's suggestion, arguing against implementing a friendlier output format due to two technical challenges: the difficulty of reliable regex parsing in C and variability in output formats across different IMAP servers. Garg maintains that the current verbose output provides necessary technical details for power users to locate subfolders and tags, suggesting the documentation approach (explaining how to interpret raw IMAP LIST output) is more maintainable than normalizing output in code. The thread now presents a clear design tension between hiding protocol details (Junio's position) versus exposing them as necessary technical information (Garg's position). Key technical details remain the IMAP LIST output format showing folder attributes in parentheses followed by server-side paths, with Gmail's "[Gmail]/" prefix being the concrete example while the approach generalizes to other providers. The thread remains unresolved on whether to accept the doc-only solution or push for code changes to improve the user experience.
