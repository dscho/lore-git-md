This is a follow-up discussion in the IMAP sent-folder archiving feature thread, where Aditya Garg raises new doubts about the feature's fundamental justification. The email directly questions whether the IMAP archiving capability belongs in Git at all, given that users could alternatively use SMTP directly or pipe output to `git imap-send`.

Garg's key argument is that since IMAP-capable users likely have SMTP access too, the archiving functionality may be necessary. This challenges Junio Hamano's earlier position that `git send-email`'s advanced features (CC management, cover letters) make archive-after-send valuable. The technical implementation was previously settled in v3 with the "imap-sent-folder" naming and functionality, but now faces philosophical reconsideration.

The discussion has shifted from implementation details to whether the feature should exist. Garg specifically distinguishes between the IMAP-only transport mode (B2, which remains unimplemented) and the archive-after-SMTP mode (A2) that the patch implements, questioning both. This introduces new uncertainty about merging the series despite its technical readiness.

The thread now hinges on whether the Git community sees sufficient unique value in integrated IMAP archiving compared to manual alternatives. Junio's previous arguments about `send-email`'s advanced features may need re-examination in light of this challenge to the feature's core premise.
