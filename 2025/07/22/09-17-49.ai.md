This is a bugfix targeting partial clone behavior, specifically addressing a race condition between commit graph lookups and object repacking during fetches in filtered repositories.

Jeff King provides a detailed analysis of the issue originally reported by Dilyan Palauzov, where treeless/blobless clones fail on first pull after a delay. He reproduces the problem with a minimal test case showing that fetch operation spawns endless sub-fetches when trying to diff submodules in a repository missing tree objects. The key discovery is a race where maintenance repacks can make objects temporarily unavailable between commit graph lookups and object database checks.

The proposed fix modifies `fetch-pack.c` to pass `HAS_OBJECT_RECHECK_PACKED` when checking object existence after finding a commit in the graph. This ensures the check accounts for recent repacks. King notes this might be the right solution since commit graph presence implies we expect the object to exist locally, making the repack rescan acceptable despite normally being expensive.

The email raises several important considerations: whether fetch behavior should differ in tree-less repos, if submodule diffs should skip lazy-fetching when parent trees are missing, and potential performance impacts. These are marked as orthogonal to the immediate race condition. The analysis references commit 5d4cc78f72 which introduced the current behavior and suggests involving Jonathan Tan for review given his work on promisor remotes.

This appears to be a well-investigated fix for a real edge case in partial clone behavior, though the interaction with submodule fetching suggests there may be broader design questions to consider about how filtered clones handle submodule operations. The patch itself is focused and comes with clear reasoning about why the change should be safe.
