Performance optimization follow-up regarding case sensitivity in pathspec bloom filters.

Lidong Yan responds to Junio Hamano's question about how bloom filters handle case sensitivity, confirming through code analysis and empirical testing that the current implementation is case-sensitive regardless of `core.ignorecase` settings. The investigation shows bloom filters are built without checking `config.ignoreCase`, with paths added to the hashmap and filter in their original case.

The email includes concrete timing measurements from the llvm-project repository demonstrating significant performance differences between exact-case, icase-prefixed, and mixed-case queries (0.089s vs 0.281s vs 0.458s), proving the bloom filter optimization only helps exact-case matches. This confirms the optimization doesn't currently handle case-insensitive filesystems, leaving potential future work to consider `core.ignorecase` when building filters.

Key technical details:
- Analysis focuses on `get_or_compute_bloom_filter()` in bloom.c
- Paths are added to `path_hashmap` without case normalization
- Test methodology uses `git commit-graph write` with `--changed-paths`
- Performance impact shown via `git log` with exact/icase/mixed-case pathspecs
- Results consistent with MacOS default case-insensitive filesystem behavior

This email provides important empirical evidence about current bloom filter behavior while leaving the case-sensitivity optimization question open for future consideration, as previously noted in the thread summary.
