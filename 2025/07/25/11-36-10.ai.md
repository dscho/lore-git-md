Bugfix discussion regarding `REF_HAVE_OLD` flag behavior during reflog updates. Jeff King responds to Patrick Steinhardt's patch that preserves the `REF_HAVE_OLD` flag for log-only updates while skipping old-OID verification, noting an inconsistency in how `split_head_update()` handles the flag compared to `split_symref_update()`.

Jeff observes that while the patch's approach makes sense (using `REF_LOG_ONLY` to skip old-OID checks while keeping `REF_HAVE_OLD` as a signal), it reveals that `split_head_update()` currently doesn't clear `REF_HAVE_OLD` like `split_symref_update()` does. This means HEAD reflog updates currently perform unnecessary old-OID checks that would be skipped after the patch.

The key technical concern raised is whether this could lead to non-atomic behavior in transactions where a log-only update succeeds while the main ref update fails. Jeff notes that while ref transactions are designed to be atomic, there has been recent discussion about non-atomic cases that might affect this. He also connects this to his own recent work on dangling symref handling, where he encountered similar flag behavior issues with HEAD updates.

The discussion suggests the need to:
1. Consistently apply the `REF_LOG_ONLY` check pattern across all similar cases
2. Verify atomicity guarantees when log-only updates are involved
3. Consider whether `ref_update_check_old_target()` should also respect `LOG_ONLY`

This is a careful technical review identifying subtle consistency issues in the refs backend's flag handling, building on Patrick's work to improve the reflog migration infrastructure. The exchange shows both developers working through edge cases in the interaction between ref updates and their associated reflog entries.
