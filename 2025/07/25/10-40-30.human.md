This is a feature proposal for a new Git config option to enforce committing `.gitignore` and `.gitattributes` files before other changes in a commit.

Kirill Sploshnov proposes adding a `commit.requireIgnoreFirst` config option that would block commits when `.gitignore` or `.gitattributes` changes are staged alongside other files. The goal is to prevent accidental commits of large generated files or binary assets that should have been excluded, particularly in project-based workflows like game development where these files are often project-local rather than repository-wide.

The proposal is motivated by real-world problems in software ecosystems like Unity and Unreal Engine, where developers frequently import projects into repositories. The current behavior can lead to bloated histories and LFS misconfigurations when users run `git add .` without first committing the ignore rules. The suggested solution is modeled after similar protections in tools like pre-commit.

The implementation would enforce this at commit time (not during staging) and provide a helpful error message with recovery instructions. The author notes this could be extended to support custom patterns but suggests starting with the fixed paths. They've considered and rejected alternatives like repository-wide ignore files and git hooks as being either too inflexible or too intrusive.

The proposal is well-articulated with clear problem statements, use cases, and design rationale. It targets a real pain point in certain workflows while maintaining Git's flexibility. The author indicates willingness to implement if the concept is accepted. This seems like a thoughtful addition that could benefit teams working with project-based assets, though the discussion may explore whether the config option needs to be more flexible from the start.
