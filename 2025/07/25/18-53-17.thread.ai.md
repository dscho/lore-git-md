Thread identity: RFC proposal for a permanent-history Git workflow with structured branch lifecycle management, originating from Skybuck Flying.

Core problem/goal: Introduce an alternative Git workflow that preserves all development history by never deleting branches, using explicit state tracking (active/merged/rejected) and sequential versioning. Aims to address four key problems: history loss from branch deletion, branch sprawl, lack of developer continuity, and accidental data risk. Seeks to provide full traceability and "time-travel" capabilities while maintaining Windows compatibility.

Key technical details:
- Branch naming convention: `UserPrefixContributionNNN-Description` with sequential versioning
- State management via directory-like tags: `active/`, `merged/`, `rejected/`, `revive/`
- Proposed custom commands:
  * `NewContribution`: Creates new branch from master
  * `SetActive`/`SetMerged`/`SetRejected`/`SetRevive`: Branch state transitions
  * `BackTo` + `TheFuture`: Two-phase historical workflow (recreate old branch + rebase onto current master)
- Implementation currently as Bash scripts with Windows compatibility challenges in CMD/PowerShell
- Windows-specific considerations for branch naming/length and script execution

Current status: Expanded proposal (v0) with additional workflow details and problem motivation. No implementation patches yet - remains conceptual with example aliases/scripts.

Open questions:
- Windows path length limitations with many long-lived branches
- Scaling concerns with branch sprawl in large repositories
- Potential core Git feature inspiration or integration points
- General applicability beyond personal workflows
- Script portability across platforms (Bash to PowerShell/CMD)

Participant positions: Skybuck Flying (author) provides expanded workflow details and new command examples. Still no other participants as this remains an early RFC discussion.
