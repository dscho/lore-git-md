This is a technical follow-up in the ongoing discussion about improving `git rebase`'s handling of skipped commits during conflict resolution. Junio C Hamano responds to Cameron Steffen's suggestion to reuse the existing "skipped previously applied commit" warning message pattern.

The key technical point raised is the challenge of reliably detecting when a commit was skipped specifically because its changes were already applied (versus other reasons a commit might become empty during rebase). Hamano expresses uncertainty about how to make this determination robustly, particularly after user intervention during conflict resolution.

The email reinforces the thread's focus on maintaining precision in the warning system while acknowledging the appeal of message consistency. It surfaces an important implementation detail - the need for accurate state tracking through the rebase operation's various phases, especially across user-controlled conflict resolution sessions.

This moves the discussion forward by highlighting a specific technical hurdle (state determination post-conflict) that the implementation will need to address, while keeping aligned with the thread's established direction of reusing existing warning infrastructure where possible.
