Thread identity: Proposal for new `commit.requireIgnoreFirst` config to enforce committing `.gitignore`/`.gitattributes` before other changes, targeting project-based workflows like game development with nested ignore files.

Core problem: Prevents accidental commits of files that should have been excluded when `.gitignore`/`.gitattributes` changes are staged alongside other modifications. Current workflow allows these files to be committed in any order, risking inclusion of unwanted files (e.g. large binaries, cache files).

Proposed solution: Boolean config `commit.requireIgnoreFirst` that blocks commits when both (1) staged changes to `.gitignore`/`.gitattributes` exist and (2) other files are staged. Error message would guide users to reset and recommit properly. Inspired by similar `pre-commit` enforcement for its config file.

Technical details: Hooked at commit time (not `git add`), with potential for future extension to custom path patterns. Contrasts with alternatives like repo-wide ignores (doesn't solve staging order) or hooks (adoption barrier). References similar existing mechanisms (`receive.denyCurrentBranch`, GitHub ignore templates).

Open questions: Whether use case justifies core Git support vs external tooling. Potential discussion points about configurability (path patterns), error message wording, and interaction with other commit-time checks. Author offers to implement if concept approved.
