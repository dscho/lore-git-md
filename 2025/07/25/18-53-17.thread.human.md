This RFC thread proposes a novel Git workflow called "permanent-history" that preserves all development branches indefinitely with structured state management. The original proposal from Skybuck Flying outlined a system where branches are never deleted but instead transition through explicit states (active/merged/rejected) using directory-like tagging system, with Windows-compatible naming conventions like `UserPrefixContributionNNN-Description`.

The follow-up email provides important additional context, detailing four core problems the workflow addresses: preventing history loss, managing branch sprawl, maintaining developer continuity, and reducing accidental data risk. It introduces new technical details about the proposed workflow commands, particularly the "Back to the Future" combo - `git back-to` to recreate historical branches and `git TheFuture` to rebase them onto current master. The implementation currently exists as Bash scripts that work in Linux/Git Bash environments but face Windows compatibility challenges in CMD/PowerShell.

The thread remains at the conceptual stage with no patches yet submitted, but the expanded explanation helps clarify how developers would interact with the system through state transition commands (`set-active`, `set-rejected` etc.) and the time-travel development pattern. Windows compatibility remains a key open question, along with broader concerns about scaling with many long-lived branches and potential inspiration for core features. The author is actively seeking feedback on these aspects and possible integration points with mainline Git.
