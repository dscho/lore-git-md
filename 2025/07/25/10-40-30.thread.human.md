This thread discusses a proposal to add a `commit.requireIgnoreFirst` config option that would enforce committing changes to `.gitignore` or `.gitattributes` before other files when both are staged. The original author argues this would prevent accidental commits of files that should be excluded, particularly in project-based workflows with nested ignore files.

Torsten Bögershausen has challenged the premise, demonstrating that in a simple test case, Git already behaves as desired - when adding files with a new `.gitignore`, only the ignore file gets staged. He requests a reproducible test case showing the actual problem and questions whether core Git support is needed versus existing solutions like hooks or CI checks. The discussion has shifted to whether there's a real technical gap here, with Torsten emphasizing the importance of clearly demonstrating the problem before discussing solutions.

Key open questions remain about whether the use case justifies a core Git feature, how it would be deployed across workstations, and whether alternative approaches like training or server-side checks would be more appropriate. The tone remains constructive, but the proposal now needs to address the challenge that Git's current staging behavior may already handle the core concern in many cases.
