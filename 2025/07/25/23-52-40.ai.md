Bugfix follow-up discussion about alias handling with `-h` flag, focusing on edge cases with external commands.

Junio Hamano responds to René Scharfe's patch fixing the `-h` alias behavior, raising additional concerns about the interaction between Git's alias system and external commands. The core issue remains how Git handles `-h` when it's both a help request and a valid flag (like in `grep`), but the discussion now explores more complex scenarios.

Hamano identifies two problematic cases: First, with external commands (like GNU grep) where Git shows alias info followed by the command's help output when given just `-h`, which may be undesirable. Second, with Git commands where the alias info disappears when `-h` is combined with other arguments, potentially confusing users about what happened to their additional arguments.

The key technical observation is that the current behavior (even with the proposed fix) creates inconsistency between how Git treats its own commands versus external ones in aliases. Hamano questions whether Git should run the underlying command after showing alias expansion, noting this works safely for Git's own commands (which uniformly handle `-h`) but could be risky for arbitrary external commands.

The discussion suggests the solution might need to consider: 1) whether the alias points to a Git command or external one, 2) whether to show alias info at all when `-h` is present with other arguments, and 3) how to handle cases where arguments might get "lost" in the help output. This goes beyond the original bug's scope but reveals deeper design questions about alias behavior.
