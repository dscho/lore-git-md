This is a follow-up in the ongoing MemorySanitizer discussion thread, specifically addressing instrumentation challenges in cryptographic libraries.

Jeff King reports on his investigation into MemorySanitizer (MSan) warnings in Git's interaction with OpenSSL and libcurl. He first proposes a potential local fix using `msan_unpoison()` for the `git_mkstemps_mode()` function, but expresses skepticism about this approach leading to "insanity" due to the proliferation of manual annotations required. He suggests the better long-term solution is building all dependencies with MSan instrumentation.

To demonstrate the scope of the problem, Jeff shares a detailed MSan trace showing uninitialized memory warnings originating deep within OpenSSL's `BIO_new_file` function, propagating through libcurl initialization, and ultimately affecting Git's HTTP transport. The trace shows these issues are outside Git's direct control, occurring in system libraries that Git links against. He concludes that these false positives from uninstrumented cryptographic libraries would be impractical to suppress with local workarounds.

This email highlights the broader challenges of using MSan with Git when system dependencies aren't instrumented, reinforcing Jeff's earlier position that proper instrumentation of all dependencies is the only robust solution. The discussion remains technical and focused on instrumentation strategies rather than indicating any security vulnerabilities in Git itself.
