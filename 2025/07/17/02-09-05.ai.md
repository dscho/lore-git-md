This is a bugfix addressing a potential integer truncation issue in the ref-cache iterator code. Jeff King points out a questionable `(int)` cast in Karthik Nayak's pagination implementation that could theoretically cause problems with extremely long refnames (though notes this is unlikely in practice given filesystem constraints).

The issue occurs in `cache_ref_iterator_seek()` where refname length calculations use `int` instead of `size_t`, potentially truncating values between 2GB-4GB. While the current usage is safe due to subsequent `strncmp()` casting back to `size_t`, Jeff argues this sets a bad precedent and provides a straightforward patch to use `size_t` consistently.

This is a tangential but important observation in the ongoing refs/pagination thread, separate from but related to the memory safety issues being discussed. The fix is simple and non-controversial, though it doesn't directly address the uninitialized memory access that's the thread's primary focus. Jeff's attention to detail here exemplifies the careful code review that helps maintain Git's robustness, even for edge cases unlikely to manifest in normal usage.
