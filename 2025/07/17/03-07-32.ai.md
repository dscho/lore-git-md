This is a feature patch proposing a new `pull.autoStash` configuration option, directly addressing the ongoing thread about validation and inheritance of configuration keys. The patch introduces a new config option that mirrors `rebase.autoStash` functionality but with clearer semantics for pull operations.

The technical implementation adds `pull.autoStash` to the config system with precedence over `rebase.autoStash` when both are set. The patch modifies `builtin/pull.c` to track both config values separately and implements the precedence logic. Documentation is added to `Documentation/config/pull.adoc` explaining the new option's behavior and its relationship to `rebase.autoStash`.

This directly responds to Junio Hamano's observation about the inconsistent handling of autostash settings between rebase and merge operations during pull. The patch takes the approach of adding a new pull-specific key rather than removing `rebase.autostash` support, which aligns with one of the technical solutions discussed in the thread. The implementation is clean and well-documented, though it doesn't address the broader configuration validation issues raised earlier in the thread.

Key technical details for future reference:
- New config key: `pull.autoStash`
- Precedence: `pull.autoStash` > `rebase.autoStash`
- Implementation files: `builtin/pull.c` and `Documentation/config/pull.adoc`
- Behavior: Same as `rebase.autoStash` but pull-specific
- Default value: false
- Can be overridden by `--autostash`/`--no-autostash` CLI flags

This patch represents a concrete step in the configuration inheritance discussion, though it may conflict with Junio Hamano's expressed preference against adding `pull.autostash`. The clean implementation and documentation suggest it could serve as a model for similar configuration inheritance cases if accepted.
