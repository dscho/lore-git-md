This RFC thread about introducing Rust infrastructure to Git has evolved into a multi-faceted discussion with technical, policy, and licensing dimensions. The core technical architecture for the xdiff implementation remains stable, with Rust/C interop layers and build system support solidified. However, the conversation has shifted toward enterprise compliance needs and now licensing considerations.

Randall Becker has been the compliance requirements for regulated industries, establishing clear expectations around CVE backports (30-day SLA for critical issues) and demanding formal documentation for any proposed LTS branch maintainer structure. His responses to Ezekiel Newren's maintainer proposal emphasize that good intentions aren't enough - regulated users need documented procedures, governance structures, and audit-compliant processes.

A new licensing discussion has now emerged, with Johannes Schindelin weighing in on how to handle Rust code's relationship with Gitoxide. Drawing lessons from the libgit2 license incompatibility, he proposes adding a GPLv2+exception header to new Rust code that would explicitly permit use in Gitoxide (which is MIT/Apache licensed). This aims to prevent ecosystem fragmentation while maintaining Git's core licensing. Phillip Wood has raised concerns about the long-term effects of such exceptions, setting up a tension between license purity and practical collaboration needs.

The thread now has three parallel tracks: the stable technical implementation, the unresolved enterprise compliance requirements (where Becker's operational demands remain unmet), and this new licensing discussion that could significantly impact how Rust code flows between Git and related projects. All three will need resolution before the Rust effort can move forward conclusively.
