This RFC thread on introducing Rust infrastructure to Git remains at an impasse, with technical solutions now largely settled but policy questions unresolved. The core debate centers on timing and platform support, with Patrick Steinhardt and Gentoo's Sam James advocating for a gradual transition where Rust remains optional until Git 3.0 (projected for 2026), while Brian Carlson pushes for faster adoption to maintain momentum.

The technical implementation is ready, with Rust modules for xdiff complete and build system changes under review. The `ivec` interoperability type has been finalized after extensive discussion, with Ezekiel Newren and Brian Carlson confirming it as the right approach for C/Rust boundary crossing. A new test candidate (`varint.c`) has been proposed as a smaller-scale validation of the approach.

Key sticking points remain around platform support - particularly for NonStop (Randall Becker) and Cygwin (Ramsay Jones) - and the project's ability to maintain parallel C/Rust implementations for security backports. Junio Hamano has expressed concerns about long-term maintenance burdens, while Taylor Blau argues the security benefits outweigh these costs. The discussion has drawn parallels to Git's historical C99 transition, with Collin Funk noting the project's traditional caution with such changes.

Sam James' latest email reinforces the distributor perspective, emphasizing that even a single release cycle with optional Rust components would help packaging ecosystems adapt. While no one opposes Rust adoption in principle, the thread shows a growing divide between those prioritizing immediate technical benefits (Carlson) and those focused on smooth ecosystem transition (Steinhardt, James). The `varint.c` test balloon may offer a path forward for concrete validation while the larger policy questions continue to be debated.
