This thread continues the long-running discussion about introducing Rust infrastructure into Git, specifically focusing on the xdiff subsystem. The RFC series (now at v3) has reached a technical impasse regarding Rust adoption, with all compiler alternatives (mrustc, gccrs) deemed unsuitable for production use. The technical implementation is largely settled, with the `ivec` type design finalized and build system changes under review.

Key participants have staked out positions: Taylor Blau argues Rust's security benefits justify reduced portability, while Brian Carlson provides concrete examples of Rust's productivity advantages but shares concerns about compiler maturity. Sam James and Collin Funk advocate for a cautious timeline aligned with Git 3.0, drawing parallels to the project's historical approach to C99 adoption. Randall Becker highlights the impact on NonStop, revealing its maintenance relies on individual effort rather than vendor support. Patrick Steinhardt proposes a middle path where Rust features would be optional during the transition period.

Junio Hamano, the maintainer, has now responded to Steinhardt's proposal. While agreeing with the cautious approach, he raises practical concerns about how many features could realistically be made optional without maintaining dual implementations or disrupting core functionality. He also questions the status of existing Rust code in `contrib/` that isn't integrated with the current work. The discussion continues to balance technical merits against transition feasibility, with no clear resolution yet on timing or governance of the Rust adoption plan.
