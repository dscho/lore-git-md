This RFC thread explores introducing Rust as a hard dependency in Git, specifically targeting performance optimizations in the xdiff component (5-19% claimed gains in certain `git log` operations). The current series (v7/7) has completed CI integration and focuses on structural refactoring of xdiff internals, with Rust-based hash functions while keeping most of xdiff in C. Key participants include Ezekiel Newren (series author), Junio Hamano, Phillip Wood, brian m. carlson, and Taylor Blau.

The technical discussion has converged on using C-side type changes (u8/usize/u64) for Rust interoperability, with performance improvements demonstrated when whitespace flags are disabled. However, Junio notes the current implementation isn't yet upstream-ready, needing a whitespace-aware xxhash variant to handle all diff modes. Phillip Wood has identified several technical concerns around error handling regressions and type change impacts on external consumers like libgit2 and Vim.

New distribution concerns have emerged from Gentoo maintainers Eli Schwartz and Haelwenn Monnier, highlighting practical deployment obstacles: amd64 builds requiring multiple Rust versions from source (via mrustc), while HPPA/Alpha/m68k lack Rust support entirely. There's also concern about circular dependencies if libgit2 (used by Rust's git2 crate) were to depend on a Rust-ified xdiff. The discussion now includes build system considerations, with suggestions to use meson's Rust support rather than cargo to mitigate some issues.

Policy questions remain open around minimum Rust version requirements (currently adjusted to 1.63.0), `Cargo.lock` inclusion, and how to handle platforms that cannot support Rust. Junio and Taylor Blau support a Debian-stable+1-year version policy, putting responsibility on platform maintainers for toolchain availability. The thread continues to balance measurable performance gains against these real-world deployment constraints, with no clear consensus yet on whether the benefits justify the ecosystem impact.
