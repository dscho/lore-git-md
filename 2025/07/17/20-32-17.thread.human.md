The RFC series introducing Rust infrastructure for Git's xdiff remains in limbo, with all technical solutions now exhausted but policy questions still unresolved. The latest version of the implementation is complete, including Rust modules for xdiff and a carefully designed `ivec` type that bridges C and Rust while avoiding layout instability issues. While the technical design has gained broad acceptance—with even initial skeptics like Ben Knoble now supporting the approach—the debate has shifted to policy concerns around platform support and transition timing.

Key participants have staked out positions: Taylor Blau argues the security benefits justify accepting some platform limitations, while Brian Carlson points to concrete productivity gains from Rust in his own work. On the other side, Sam James and Collin Funk draw parallels to Git's cautious C99 transition, advocating for a slower timeline aligned with gccrs stabilization in 2026. Randall Becker and Ramsay Jones provide concrete examples of platform impacts, with Jones already unable to build Git on Cygwin due to Rust requirements. Patrick Steinhardt has proposed a middle path where Rust features would be optional until Git 3.0, gaining support but facing new questions from Junio Hamano about practical scope.

The latest development, Josh Steadmon's email clarifies that Google's existing Rust needs are met by gitoxide, leaving the in-tree `contrib/libgit-*` directories dormant for now. This addresses one of Junio's open questions but doesn't resolve the core tension between immediate adoption advocates and those favoring a more gradual transition. With technical implementation settled but policy questions still hotly debated, the thread appears to be reaching an inflection point where project leadership may need to make a decisive call on timing and platform support tradeoffs.
