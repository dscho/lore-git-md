This RFC thread explores introducing Rust as a hard dependency in Git, specifically targeting xdiff optimizations that show 5-19% performance gains. The current series (v7/7) focuses on structural refactoring of xdiff internals, including line parsing/hashing separation and xxhash optimizations, while adding Rust build infrastructure. 

Junio Hamano has acknowledged the technical merit but questions whether performance gains come from the Rust implementation or hash algorithm changes. He's made clear there's no consensus to fully replace xdiff's C code yet. The RFC currently proposes using Rust-based hash functions only for specific cases (when whitespace flags are disabled). Several technical concerns remain open, particularly around maintaining xdiff as a standalone C library for third-party consumers like libgit2 and Vim.

The discussion has expanded to include significant policy questions, especially around platform compatibility. Gentoo maintainer Eli Schwartz raised practical deployment obstacles, noting that some architectures (HPPA/Alpha/m68k) lack Rust support entirely, while others face burdensome build requirements. This challenges earlier assumptions about Rust's broad support. A tentative policy is emerging around requiring only Debian-stable+1-year Rust versions, with Ezekiel Newren adjusting the minimum version accordingly.

Elijah Newren's latest email provides important context about the work's evolution, clarifying that this isn't just a direct translation but includes both cleanup and performance improvements across multiple xdiff components. He positions the current series as exploratory, focusing on introducing Rust-based hash functions while keeping most xdiff in C, with the DJB2a hash optimization being a particularly valuable discovery.

Key open questions remain around Windows/32-bit support, version policy documentation, dependency management, and how to handle platforms without Rust support. The technical debt considerations are growing, including FFI patterns and performance measurement methodology. While the performance gains are measurable, the community is still evaluating whether they justify the compatibility tradeoffs and maintenance burden.
