This is a discussion about the `--extended` output format implementation for the `git last-modified` command, part of the ongoing feature series implementing tree-level path modification tracking.

Toon Claes responds to Junio C Hamano's detailed feedback about the extended output format documentation. The key points under discussion are:

1. **Format clarity**: Junio notes the documentation's use of "Unless" is confusing when describing the interaction between `-z` and `--extended` flags, suggesting simpler phrasing would be clearer.

2. **Message termination**: The current spec doesn't clearly define how to detect the end of commit messages in the extended format. Junio probes whether unindented lines or EOF mark message boundaries, and mentions plans to modify `pretty_print_commit()`'s empty line handling.

3. **Future extensibility**: Junio raises concerns about adding future multi-line fields, suggesting explicit tagging (like "message SP <message>") would be better than special-casing the commit message.

4. **NUL handling**: The mixed NUL/LF termination in `-z --extended` mode needs clarification, particularly around message boundaries.

Toon acknowledges these are valid concerns and indicates the extended format implementation may need to be reworked or possibly dropped from the series, as their immediate product needs can be met with just the single-line output format. This suggests the extended format discussion may be deferred to a future iteration of the feature.

The exchange highlights fundamental design questions about how to balance machine-readability, future extensibility, and consistency with existing Git formats like `git-cat-file`. The thread shows the series is in its final stages, with this output format being the last major design decision before potential inclusion.
