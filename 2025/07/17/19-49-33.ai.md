This is a bugfix addressing an integer truncation issue in the ref-cache iterator code, part of the ongoing pagination support work for `git for-each-ref`.

Jeff King identified a potentially problematic `(int)` cast in `cache_ref_iterator_seek()` where refname length calculations could theoretically truncate very large values (between 2GB-4GB) to negative numbers. While this is unlikely to cause practical issues given filesystem constraints on refname lengths, it sets a bad precedent and could lead to incorrect comparisons for extremely long refnames. The issue occurs during the binary search implementation when calculating substring lengths for comparison.

Karthik Nayak acknowledges the oversight and agrees with Jeff's proposed fix to use `size_t` consistently for the length calculations. The fix involves changing the type of `len` from `int` to `size_t` and removing the unnecessary cast of `strlen(refname)`. Karthik notes they should also cast the pointer arithmetic `slash - refname` to `size_t` for consistency, though this wasn't included in Jeff's initial suggestion.

This follows the recent memory safety resolution in the same function where uninitialized `prefix_state` was fixed. The thread shows careful collaborative review catching edge cases in the pagination implementation, with Jeff identifying this subtle type safety issue and Karthik promptly addressing it while maintaining the function's core seek behavior for ref iteration.
