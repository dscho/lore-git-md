This is a continuation of the discussion about `pull.autoStash` configuration behavior, specifically addressing backward compatibility concerns when changing how auto-stashing works during merge operations.

Junio Hamano responds to Lidong Yan's concern that switching merge operations to check `merge.autoStash` instead of `rebase.autoStash` might confuse users who currently rely on the existing behavior. Hamano acknowledges this would be a behavior change but argues it would be a one-time adjustment, with users able to consult documentation and update their configuration accordingly.

The key new development is Hamano's endorsement of Yan's proposal to make `pull.autoStash` override both `rebase.autoStash` and `merge.autoStash` when explicitly set to false. This would allow users to maintain different auto-stash behaviors for local operations (using operation-specific configs) versus pulls (using `pull.autoStash`). 

The discussion continues to weigh design tradeoffs between:
1. Backward compatibility (current behavior where `rebase.autoStash` affects merges)
2. Configuration clarity (separate controls for different operation types)
3. User control (ability to set different policies for local operations vs pulls)

Hamano's position appears to be shifting toward accepting some backward incompatibility in favor of clearer configuration semantics, while preserving user flexibility through the override mechanism. This moves the thread closer to resolution on the core design question while still leaving open the exact final behavior.
