RFC series proposing Rust as hard dependency with xdiff optimizations (5-19% claimed perf gain), now at version 7/7 with CI integration complete. Series methodically prepared xdiff internals through structural refactoring (patch 5/7's line parsing/hashing separation in `xrecord_t` type changes to u32/u64 (patch 4/7), and xxhash optimization (19% speedup in `git log --oneline --shortstat` when `XDF_WHITESPACE_FLAGS` unset). Final patch adds `build_rust.sh`, CI workflows, and Makefile/Meson integration with debug/release flags.

Elijah Newren provides historical context on the work's evolution, clarifying it originated from xhistogram improvements and expanded organically to xmerge and other xdiff components, with deliberate tradeoffs between maintainability and performance. He highlights the DJB2a hash optimization discovery as key motivation for this RFC series, positioning it as both cleanup and performance work. The current scope focuses on Rust-based hash functions while keeping most xdiff in C, with potential future expansion to other components.

Junio Hamano acknowledges the series' value while questioning performance attribution (hash algorithm changes vs Rust implementation). He clarifies no consensus exists to fully replace xdiff's C implementation with Rust - current RFC only introduces Rust-based hash function for specific cases (whitespace flags disabled). In response to patch 6/7's conditional xxhash optimization, Junio notes it's a good proof of concept but not yet upstream-ready, needing a whitespace-aware variant of xxhash to handle all diff modes and completely replace `xdl_hash_record()`. This reinforces Phillip Wood's concerns about maintaining xdiff as standalone C library for third-party consumers (libgit2, Vim).

Technical consensus remains on type casting approach: brian m. carlson, Taylor Blau, and Elijah Newren agree C-side type changes (u8 for bytes, usize/u64 for system independence) are preferable for Rust interoperability, with Taylor Blau proposing to document these principles in CodingGuidelines. Phillip Wood's detailed reviews identify multiple technical concerns: patch 4/7's type changes may be unnecessarily disruptive, patch 5/7 has error handling regressions in `xdl_parse_lines()` affecting external consumers, and suggests optimization in `xdl_hash_record()` by reusing pre-parsed line length data.

Policy discussion expands with new compatibility concerns from Eli Schwartz (Gentoo maintainer) and Haelwenn Monnier: Rust presents practical deployment obstacles for distributions - amd64 requires building multiple Rust versions from source via mrustc (burdensome), while HPPA/Alpha/m68k lack Rust support entirely, potentially stranding these platforms on Git 2.50. Even s390 users face auditability issues with precompiled binaries. Monnier raises new circular dependency concerns if libgit2 (used by Rust's git2 crate) were to depend on a Rust-ified xdiff, suggesting meson's Rust support as alternative to cargo for build system simplification. Schwartz requests clarification on minimum Rust version requirement (currently unspecified) and notes GCC-rs might eventually help. These distribution packaging realities directly challenge Phillip Wood's "widely supported" assertion and brian m. carlson's mandatory Rust adoption position.

Debian-stable+1-year Rust version policy gains traction with Junio Hamano and Taylor Blau supporting platform maintainer responsibility for toolchain availability. Ezekiel Newren adjusts RUST_VERSION from 1.87.0 to 1.63.0 to align with this policy. Newren and brian m. carlson debate `Cargo.lock` inclusion - Newren argues for reproducibility citing Rust documentation, while brian m. carlson maintains distribution packaging concerns. This unresolved policy tension may require PLC input.
