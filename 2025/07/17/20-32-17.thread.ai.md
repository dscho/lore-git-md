RFC series proposing Rust as hard dependency with xdiff optimizations (5-19% claimed perf gain), now at version 7/7 with CI integration complete. Series refactored xdiff internals through structural changes (line parsing/hashing separation in `xrecord_t` type changes to u32/u64, xxhash optimization showing 19% speedup in `git log --oneline --shortstat` when `XDF_WHITESPACE_FLAGS` unset). Final patch adds `build_rust.sh`, CI workflows, and Makefile/Meson integration.

Performance analysis from Phillip Wood shows 8% speedup from inlining whitespace flag check in `xdl_hash_record()` and 6% additional from XXH3_64bits in C, matching Rust performance (15% total), suggesting most gains come from hash algorithm choice rather than Rust. Junio Hamano questions XXH3 performance on non-SIMD architectures and probes necessity of changing C-side type definitions to match Rust primitives (u8, usize, u32) rather than standard C types (uint8_t, size_t). While Rust's 32-bit `char` vs C's 8-bit `char` necessitates `u8` for byte strings on Rust side, Junio notes `uint8_t` is effectively `unsigned char` in C, questioning value of introducing `u8` typedef. Phillip Wood further challenges the type alignment strategy, arguing that if Rust code converts FFI data to idiomatic types (like slices) anyway, the C-side type matching provides little practical benefit and may just shift complexity between layers.

Ezekiel Newren counters with concrete FFI examples showing how aligned types enable zero-copy interop. Demonstrates `xxh3_64()` case where C `u8*` and `usize` directly convert to Rust slice via `std::slice::from_raw_parts()`, allowing safe operation on C-allocated memory without copies. Mentions more advanced "ivec type" optimization (excluded from series for length) that further leverages type alignment for vector interop. This addresses Phillip Wood's conversion-layer concern by showing aligned types allow idiomatic Rust usage of C structures at FFI boundary.

New performance-focused follow-up from Ezekiel Newren addresses whitespace handling tradeoffs: Rust's XXH3_64bits shows speed benefits (19% faster in non-whitespace modes) but cannot efficiently handle whitespace-ignoring modes due to xxhash's requirement for contiguous memory, while C's DJB2a processes bytes individually. Raises two key questions: (1) whether Git accepts maintainable-but-slower code when it improves security, and (2) practical demonstration challenges for subsequent changes. This reveals a new technical hurdle in the Rust integration - optimizing for zero-copy interop (via type alignment) versus handling all xdiff use cases with equivalent performance.

Platform discussions include Windows target considerations (`i686-win7-windows-gnu`/`x86_64-win7-windows-gnu` targets requiring Rust 1.78+), Windows build fixes addressing toolchain compatibility and critical `xrecord_t.ha`/`s_xdlclass.ha` type mismatch (u64 vs unsigned long) that would break `xdl_classify_record()` with 32-bit overflow. Gentoo Rust support constraints detailed: no support for HPPA/Alpha/m68k, partial s390 (s390x only), and 32-bit issues (musl, i486, sparc32, riscv32). GCC-rs mentioned as potential solution leveraging existing GCC backends, with Pierre-Emmanuel Patry clarifying multi-year timelines for supporting Rust 1.78 on non-LLVM platforms.
