Notes macOS/Solaris Prefix users lack Rust despite official macOS compatibility. Sam James from Gentoo responds to Newren, clarifying their position is not to block Rust but to ensure practical obstacles are properly considered. Highlights Gentoo-specific concerns: (1) Rust's platform support gaps for new architectures despite platform relevance, (2) bootstrapping problems leaving new platforms without any Git version, (3) backporting issues making old C-only versions impractical, and (4) supply chain risks from Rust crate dependencies. Collin Funk reinforces this last point by quantifying the supply chain exposure with data showing 500+ transitive dependencies pulled during `cargo build`, raising concerns about whether each dependency's value justifies its inclusion.

Mike Hommey and Brian Carlson exchange technical details about `Cargo.lock` behavior in Git's context. Hommey initially clarifies that `Cargo.lock` only changes with dependency updates rather than toolchain version changes. Carlson counters with personal experience showing the file can change unexpectedly even without dependency updates, causing build issues with `--locked` flag in older Rust versions. This provides concrete edge cases in Rust's dependency resolution that could impact Git's build reproducibility.

Brian Carlson responds to Ezekiel Newren's concerns about build reproducibility and auditing by highlighting real-world security maintenance challenges from his experience with Git LFS. He presents three stark options for dependency management: (1) omit `Cargo.lock` (current proposal), (2) push Rust ecosystem for LTS releases, or (3) restrict dependencies to projects with Git's longevity guarantees. The core tension is between Rust's rapid release cadence and Git's need for long-term stability, particularly regarding security scanners flagging unused portions of dependencies. Carlson strongly advocates against checking in `Cargo.lock` to avoid becoming a magnet for security vulnerability reports, even at the cost of initial build reproducibility.
