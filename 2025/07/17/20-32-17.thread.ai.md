Performance analysis from Phillip Wood shows 8% speedup from inlining whitespace flag check in `xdl_hash_record()` and 6% additional from XXH3_64bits in C, matching Rust performance (15% total), suggesting most gains come from hash algorithm choice rather than Rust. Junio Hamano questions XXH3 performance on non-SIMD architectures and probes necessity of changing C-side type definitions to match Rust primitives (u8, usize, u32) rather than standard C types (uint8_t, size_t). While Rust's 32-bit `char` vs C's 8-bit `char` necessitates `u8` for byte strings on Rust side, Junio notes `uint8_t` is effectively `unsigned char` in C, questioning value of introducing `u8` typedef. Phillip Wood further challenges the type alignment strategy, arguing that if Rust code converts FFI data to idiomatic types (like slices) anyway, the C-side type matching provides little practical benefit and may just shift complexity between layers. This deepens the design tension between maintaining idiomatic C code versus optimizing for Rust FFI safety through type mirroring.

Technical follow-up in patch 4/7 shows concrete FFI benefits of matching C-side type definitions to Rust primitives (`u8`, `usize`, `u64`) rather than standard C types (`uint8_t`, `size_t`). Key rationale: (1) Rust's 32-bit `char` vs C's 8-bit requires explicit `u8` for byte strings, (2) identical type names reduce FFI boundary errors. Example shows C struct with Rust-compatible types that cleanly mirrors in Rust's `#[repr(C)]` struct, enabling safe FFI without type conversion ambiguity. Implementation detail: xdiff loop counters will change to `usize` (Rust's size type) to avoid casts, showing practical FFI considerations in xdiff optimizations where type consistency affects both performance and cross-language compatibility.
