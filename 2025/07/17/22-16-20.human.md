This is a follow-up discussion about MemorySanitizer (MSan) instrumentation in Git, specifically around false positives from uninstrumented cryptographic libraries.

Jeff King reports on his investigation into MSan warnings that appear when running Git's test suite with MSan enabled. He first suggests a potential fix using `msan_unpoison()` for the `git_mkstemps_mode()` function, but then discovers much more pervasive issues when testing the full suite. The output shows MSan flagging uninitialized memory access deep within OpenSSL and curl initialization paths - far from Git's own code and not something that can be easily annotated away.

The email serves as a reality check about the limitations of MSan when dealing with uninstrumented system libraries. While the earlier discussion focused on fixing specific MSan warnings in Git's ref iterator code, this shows the broader challenge of getting clean MSan runs when cryptographic dependencies aren't built with MSan instrumentation. Jeff King's tone suggests that while local workarounds are possible, the more robust solution would be to build all dependencies with MSan - a potentially significant undertaking.

This continues the thread's theme of rigorous memory safety analysis but shifts focus from specific bugs to instrumentation challenges in Git's ecosystem. The discussion remains technical and solution-oriented, with Jeff King providing concrete evidence of the problem's scope.
