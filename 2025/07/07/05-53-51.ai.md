This is a design discussion email in the ongoing thread about change ID tracking in Git's email workflow. Junio Hamano is advocating for a more generic solution than either the original mail header approach or commit trailers.

Junio makes several key points: First, he firmly rejects using mail headers specifically for change-IDs, arguing commit trailers are the proper place for them. However, he acknowledges there may be legitimate cases where arbitrary commit headers need preservation during email transfer. His proposed solution is a generic `--extra-headers` option for `git format-patch` that would encode all non-standard commit headers as `X-git-extra-commit-header` mail headers, with values encoded in iso8859-1.

The email clarifies this is not an endorsement of putting change IDs in headers, but rather a mechanism to handle cases where headers are used (whether wisely or not). The generic approach would work equally well for community-approved headers and third-party additions. Junio suggests this would let mailinfo extract the information while leaving interpretation to higher-level tools.

This represents a significant shift in the thread's direction, moving from debating change-ID-specific solutions to discussing a framework for arbitrary header preservation. The proposal would require changes to both format-patch and mailinfo, with encoding schemes to be specified. It remains unclear how this would interact with the existing commit_extra_header mechanism or whether it would satisfy the original use case that prompted the thread.
