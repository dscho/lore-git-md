This is a discussion about the ongoing debate around change-ID tracking in Git's email workflow, specifically regarding whether to use commit headers versus trailers.

Junio Hamano responds to Drew DeVault's preference for using mail headers to preserve change-IDs, strongly advocating instead for using standard commit trailers. He argues that trailers are more reliable as they are automatically preserved by most Git operations (like rebase and cherry-pick) and are more visible to users since they appear in the commit message body. He expresses skepticism about the value of change-IDs if they're treated as non-essential metadata that can be easily lost.

The email introduces a counter-proposal for a more generic solution: adding a `--extra-headers` option to `git format-patch` that would preserve arbitrary commit headers (not just change-IDs) by encoding them as `X-git-extra-commit-header` mail headers. This would solve the broader problem of preserving structured metadata through email workflows while keeping the actual commit objects clean of non-standard headers.

Key technical points:
- Current debate centers on X-Change-ID mail headers vs. commit message trailers
- Hamano's proposal would handle any extra commit headers, not just change-IDs
- The suggested implementation would encode headers with format: `X-git-extra-commit-header: name=value`
- Includes consideration for header encoding (mentioning iso8859-1 as example)

This represents a significant shift in the discussion, moving from a specific change-ID solution to a more general metadata-preservation mechanism. The proposal would require changes to both `format-patch` (for generation) and `am`/`mailinfo` (for parsing), similar to the current change-ID patches but with broader scope. The email doesn't address how this would interact with the existing change-id parsing logic proposed in v2 of the series.
