This is a discussion about the design of the new `git reflog write` subcommand, specifically around how it should resolve refnames. The email is part of the larger reflog migration infrastructure series (now complete) that was recently merged.

Junio Hamano is responding to Patrick Steinhardt's concerns about DWIM (Do What I Mean) behavior for the new `reflog write` command. The key issue is that unlike `reflog drop` which only operates on existing reflogs, `reflog write` needs to handle cases where the reflog doesn't exist yet - making DWIM resolution problematic since there's no existing reflog to base the resolution on.

Hamano agrees that DWIM behavior would be confusing for this plumbing-like command, comparing it to `update-ref` which also operates on potentially non-existent refs. He muses about whether the broader design of `git reflog` using DWIM was a UI mistake that could be corrected by moving reflog operations into commands like `git branch` and `git tag`, but acknowledges this would likely be too disruptive at this point.

This discussion represents the final design decisions around the new subcommand's behavior, settling on requiring fully-qualified refnames rather than trying to guess user intent when writing to new reflogs. The exchange shows careful consideration of both user experience and implementation constraints in the context of Git's existing conventions.
