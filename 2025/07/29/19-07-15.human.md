This is a technical clarification in the ongoing `the_repository` removal thread about merge message configuration behavior. Phillip Wood points out that the refactoring in patch 1 unintentionally changed how conflicting `merge.log` and `merge.summary` config values are handled. 

Previously, the last-specified config value would win (standard Git config behavior), but the new `adjust_shortlog_len()` function always prefers `merge.log` over `merge.summary`, regardless of their order in config files. Phillip notes this is a behavioral regression from the expected last-one-wins pattern, suggesting the callback-based config parsing should be preserved to maintain consistency with Git's configuration philosophy.

This adds another dimension to the existing discussion about whether silent config validation is acceptable, showing that the refactoring introduced multiple subtle behavior changes that may need addressing. The observation comes from someone clearly familiar with Git's config parsing patterns, lending weight to the concern.
