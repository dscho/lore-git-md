This thread contains a 2-patch series by René Scharfe as part of the ongoing `the_repository` removal effort, focusing on the `fmt-merge-msg` builtin and related merge configuration. The series systematically removes global state dependencies while maintaining functionality of merge message formatting.

Patch 1 moved merge log configuration from the global `merge_log_config` variable to a new `adjust_shortlog_len()` function in fmt-merge-msg.{c,h}. The behavioral change where invalid `merge.summary` values now go unreported when overridden by command-line `--log` (previously they triggered errors during config parsing) has become the focal point of discussion. Junio Hamano maintains he cannot immediately determine if this change is an improvement or regression, jokingly offering his conservative default stance that any behavior change from refactoring should be considered a regression. Ayush Chandekar has joined the discussion questioning whether the new silent behavior is acceptable. The open questions remain: whether to document this change in the commit message, whether the silent behavior is acceptable, or if the original validation behavior should be restored.

Patch 2 removes `the_repository` usage from builtin/fmt-merge-msg.c through mechanical conversions to `repo` parameters and `repo_config()`. Junio found an issue with the patch reordering config parsing after `parse_options()`, violating the standard pattern where config should be read first then overridden by command-line options. This remains unresolved - requiring either justification for the change or restoration of original order while keeping the `the_repository` removal.

The series demonstrates the `the_repository` removal effort's precision - each patch tackles one global dependency while maintaining behavior. Changes span environment.c, fmt-merge-msg.{c,h}, builtin/fmt-merge-msg.c, and tests. Key technical details include the new `adjust_shortlog_len()` function and the shift to `repo_config()` usage. The discussion with Junio and Ayush highlights how even mechanical refactoring requires careful consideration of surrounding patterns and semantics, particularly around Git's configuration philosophy regarding validation of overridden values. The core unresolved issue remains the timing and reporting of configuration validation when values are overridden by command-line options.
