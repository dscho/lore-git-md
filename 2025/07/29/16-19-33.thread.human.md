René Scharfe's series to remove `the_repository` usage from `fmt-merge-msg` has sparked a detailed discussion about configuration behavior. The patches refactor merge log configuration, moving from global state to a cleaner function-based approach, but have uncovered subtle interactions in how Git processes configuration.

The thread began with Junio Hamano questioning whether silently ignoring invalid `merge.summary` values (when overridden by command-line `--log`) was an intentional change or a regression. Ayush Chandekar joined this discussion about validation behavior. Now Phillip Wood has identified another behavioral shift: the new implementation changes how `merge.log` and `merge.summary` interact in config files. Where Git previously processed them in order (last one wins), the refactored code now always prefers `merge.log`, breaking the standard config precedence rules.

These discussions highlight how even mechanical refactoring touches deep semantic questions about Git's configuration system. The open questions now include: whether to preserve invalid value reporting, how to handle config precedence correctly, and whether to document these behaviors more explicitly. Junio's initial patch review also flagged an ordering issue where config parsing happens after command-line options, contrary to Git's usual pattern. The thread shows the careful balance required when modernizing Git's codebase - even well-intentioned cleanups can ripple through subtle behaviors that maintainers and contributors value.
