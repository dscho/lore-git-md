This is a performance optimization discussion in the remote ref renaming series, focusing on D/F conflict handling in the files backend. Patrick Steinhardt responds to Junio Hamano and Justin Tobler's earlier discussion about whether to handle directory/file conflicts at the transaction layer or in the application code.

The core issue is that the files backend cannot atomically handle cases where a ref rename would result in a directory/file conflict (like moving "refs/heads/parent/child" to "refs/heads/parent"). While the reftable backend could handle this easily, the files backend's locking semantics make it impossible without potentially breaking external implementations.

Patrick proposes three potential solutions: (1) detect prefix relationships and use two transactions when needed, (2) simply refuse nesting/unnesting renames entirely (a backwards-incompatible change), or (3) attempt atomic renames but fail with guidance when conflicts occur. He leans toward option 3 as a pragmatic middle ground, noting that hierarchical remote renames are extremely rare in practice.

This discussion represents the final open question in an otherwise-approved performance series that dramatically improves remote operations (from hours to seconds for large ref counts). The maintainers seem willing to accept the current limitations with the understanding that more fundamental transaction layer improvements could come later.
