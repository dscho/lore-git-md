This is a discussion about the `git reflog write` subcommand's behavior regarding DWIM (Do What I Mean) reference resolution, specifically for non-existent reflogs. The email is part of the completed 9-patch series on reflog migration infrastructure.

Junio Hamano responds to Patrick Steinhardt's concerns about DWIM behavior in `git reflog write`. The key points are:

1. Unlike `git reflog drop` which only operates on existing reflogs (allowing safe DWIM), `git reflog write` must handle non-existent reflogs, making DWIM resolution problematic since there's no existing reflog to guide the resolution.

2. Hamano agrees that DWIM would be too "magicky" for this plumbing-ish command, comparing it to `update-ref` which requires explicit reference names when working with non-existent refs.

3. He raises (but quickly dismisses) the idea of fundamentally changing Git's UI by removing DWIM from `git reflog` entirely and compensating by adding reflog management to `git branch` and `git tag`. However, he acknowledges this would be too disruptive at this stage.

The discussion highlights the tension between user convenience (DWIM) and explicit behavior in low-level commands, particularly when dealing with non-existent references. This is a design consideration that was ultimately resolved in the final series by requiring fully-qualified refnames for the `git reflog write` subcommand.
