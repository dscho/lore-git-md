This is a discussion about refname resolution behavior in the new `git reflog write` subcommand, part of Patrick Steinhardt's ongoing reflog migration infrastructure work. The thread has been debating whether the command should use DWIM (Do What I Mean) behavior like other reflog subcommands, where shorthand names like "branch" automatically resolve to "refs/heads/branch".

Patrick explains the key technical difference that makes DWIM problematic for `write`: unlike `drop` which only operates on existing reflogs, `write` can create new reflogs. This means there's no existing reflog to check when resolving shorthand names, making automatic resolution potentially unsafe. The discussion includes comparisons to `git update-ref`'s similar behavior (which is at least documented) and real-world reports of user confusion from Ben Knoble.

The core tension is between consistency (having all reflog subcommands behave the same way) and safety (avoiding potentially surprising automatic resolution when creating new reflogs). Junio Hamano has suggested adding DWIM to `write` for consistency, while Patrick remains concerned about the magic behavior when there's no existing reflog to validate the resolution. The thread continues to explore solutions that might satisfy both concerns.
