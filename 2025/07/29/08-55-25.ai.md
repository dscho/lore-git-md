This is a bugfix patch addressing race conditions in HEAD reflog generation, part of Patrick Steinhardt's ongoing reflog migration infrastructure series (v3 7/9). The patch focuses on the files backend's handling of reflog entries when HEAD points to a reference being updated.

The core issue involves two race scenarios in `split_head_update()` where HEAD's target can change between initial read and update: (1) missing a needed reflog entry if HEAD moves to a processed ref, or (2) creating an incorrect reflog entry if HEAD moves away from a processed ref. The patch introduces a `REF_LOG_VIA_SPLIT` flag to help detect the second case by verifying HEAD still points to the expected ref after locking, though acknowledges the first race remains unfixable without impractical global locking.

Key technical details include:
- New `REF_LOG_VIA_SPLIT` flag marking reflog-only updates from split operations
- Parent-child linkage between updates via `parent_update` field
- Post-lock validation of HEAD's target against the parent refname
- Propagation of old-oid from parent update to maintain consistency
- Explicit error for detected races via "HEAD has been racily updated" message

The changes affect `refs/files-backend.c` with 38 lines added and 2 modified, primarily around the `split_head_update()` and `lock_ref_for_update()` functions. The solution is partial by design, as Patrick notes some races are fundamentally unavoidable without unacceptable performance penalties. This continues the series' careful balancing of correctness and practicality in reflog handling.
