Git mailing list digest: Explanation of `--diff-filter` behavior

This is a response to Eric Salem's bug report about `git log --diff-filter` behavior. K Jayatheerth explains that the observed behavior where `--diff-filter=d` (exclude deletions) produces no output without additional flags is expected, not a bug. The key insight is that diff filters only apply when Git actually computes diffs - the default output format doesn't trigger diff generation, so the filter has nothing to operate on.

The response clarifies that flags like `--stat` or `--name-only` work because they explicitly request diff computation. Jayatheerth provides two workarounds for Eric's use case of getting commit hashes while excluding deletions: one using `--name-only` piped to `grep` to filter empty lines, and another using `--stat` with more complex `grep` filtering. The explanation suggests this is a documentation clarity issue rather than an implementation bug, as the behavior makes technical sense once the interaction between output formats and diff generation is understood.

For future reference in this thread: The core technical point is that `--diff-filter` requires diff computation to have any effect, which doesn't happen with basic output formats like `%H`. The workarounds demonstrate how to force diff generation while still getting just commit hashes. This affects any use of exclusion filters (`a`-`z`) with minimal output formats, not just the deletion case. The response implies the documentation could be clearer about this dependency between output format and filter application.
