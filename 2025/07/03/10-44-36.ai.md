Follow-up diagnostic finding in credential helper investigation.

Michal Suchánek reports back on Junio Hamano's suggestion to use GIT_TRACE_CURL for HTTP-level visibility into the credential helper behavior. The tracing reveals a key difference between server implementations: the problematic forge instance consistently returns HTTP 401 status codes regardless of operation success/failure, while the development version of the same software correctly returns 403 for failed operations. This confirms the earlier mitmweb observations and suggests the issue may be server-side rather than Git client behavior.

The finding indicates the credential invalidation problem stems from incorrect HTTP status code implementation in the server software, not Git's credential helper logic. Michal notes this appears resolvable by upgrading the server software to a version that properly implements HTTP status code semantics (401 for authentication needed, 403 for authorization denied).

This moves the discussion toward resolution by:
1. Confirming server behavior varies by version
2. Showing the development version implements expected status codes
3. Suggesting the path forward is server upgrade rather than Git changes

The thread appears to be converging on this being primarily a server implementation issue, though the interaction with Git's credential caching behavior still merits attention for robustness across server implementations. No changes to Git's credential helper behavior are proposed at this stage.
