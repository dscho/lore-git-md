This is a technical discussion about implementation strategy for the reftable-as-default transition in Git 3.0, specifically addressing how to handle versioned defaults for breaking changes.

Junio Hamano proposes consolidating all breaking-change default definitions (including both the reftable format and SHA-256 hash algorithm) into a single `<bc.h>` header file, rather than scattering conditionals throughout the codebase. He suggests this would make the 3.0 transition easier to manage and less error-prone, allowing defaults to be adjusted in one place and providing better visibility into planned changes. The approach mirrors patterns from the SHA-256 transition but centralizes them.

Key technical points include:
- Current implementation in setup.c uses direct `#ifdef` conditionals
- Proposed alternative defines `REF_STORAGE_FORMAT_DEFAULT` in a header
- Similar pattern could apply to `GIT_HASH_DEFAULT`
- Header file approach would make future adjustments (like delaying reftable default to 4.0) simpler
- Unchanged defaults in subsystem headers would act as fallbacks

This continues the architectural discussion from earlier in the thread, now focusing specifically on code organization rather than documentation or ecosystem concerns. The proposal represents a significant change to the implementation strategy that Patrick Steinhardt would need to consider for the next of his patch series.
