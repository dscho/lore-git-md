This thread discusses adding change-ID tracking to Git's email workflow to help patch management systems track changes through review cycles. The original proposal (now at v2) suggested adding an X-Change-ID mail header that would round-trip between commit messages and emails. The series includes patches for both generating these headers when formatting patches and parsing them back when applying patches.

Junio Hamano has now weighed in with strong reservations about using mail headers, arguing instead for standard commit trailers which are more reliably preserved by Git operations. He proposes a more generic solution: a `--extra-headers` option for `git format-patch` that would preserve arbitrary commit metadata (not just change-IDs) through email workflows by encoding them as special mail headers. This would keep commit objects clean while solving the broader metadata preservation problem.

The discussion has revealed several perspectives: Aditya Garg raised concerns about email infrastructure limitations with custom headers, while Drew DeVault provided testing data showing some email clients preserve them. Jeff King contributed technical solutions for testing the feature but hasn't taken a position on the approach. The core debate now centers on whether to pursue the original change-ID specific solution or shift to Junio's more generic proposal, with implications for both implementation complexity and long-term maintainability. Testing methodology has been established but not yet implemented in the series.
