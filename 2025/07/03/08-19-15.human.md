This is a follow-up discussion on the `--skip-until` pagination feature for `git for-each-ref`, focusing on race condition analysis. Patrick Steinhardt responds to Junio C Hamano's concerns about concurrent modification scenarios.

The exchange clarifies the behavior when refs are modified between paginated requests: if the marker ref is deleted or new refs are inserted before it in sort order, the pagination still works as intended - the next page will start after the last-seen position regardless of intervening changes. This confirms the name-based skipping approach maintains correct pagination semantics even with concurrent modifications, though it may result in skipped or duplicated refs in edge cases (which the thread has already documented as inherent tradeoffs).

The discussion reinforces that the implementation's design choices - particularly preferring O(log N) name-based seeking over numeric offsets - remain sound despite these race conditions, which are unavoidable with concurrent modifications. No code changes are proposed here; this is purely a design clarification confirming the expected behavior matches the actual implementation.
