This is a review comment in the ongoing "repo info command" feature series. Eric Sunshine raises an important compatibility concern about the output format of the new `git repo info` command, specifically regarding quoting of values in the key-value output format.

The thread context shows this is v6 of a series implementing a new plumbing command to report repository metadata (replacing several `git rev-parse` use cases). The command currently supports three fields (reference format, bare/shallow status) with both human-readable (`keyvalue`) and machine-parsable (`nul`) output formats.

Eric argues that the command should implement proper quoting (using `quote_c_style`) from the start, even though the current fields don't currently need quoting. His key points:
1. Future fields might output values with "funny" characters (not just paths)
2. Documenting and implementing quoting now ensures better forward compatibility
3. Tools that ignore the documentation would break on their own, not due to Git's changes
4. This avoids potential for breaking changes when new fields are added later

This contrasts with Lucas's position in the cover letter that quoting can be deferred since it doesn't affect the current patchset. Eric's comment suggests this is a more fundamental design decision that should be addressed early rather than treated as an implementation detail to be added later.

The comment doesn't propose specific code changes but rather advocates for a design principle regarding output format stability. This is particularly relevant given the command's plumbing nature where machine parsing is an important use case. The discussion touches on Git's general philosophy around compatibility and output format stability.
