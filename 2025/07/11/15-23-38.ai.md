This is a follow-up discussion on the HTTP protocol compliance patch regarding language tag handling. Justin Tobler provides a technical review of Brian Carlson's proposed changes to filter invalid "C" and "POSIX" locales from Accept-Language headers.

Tobler notes the patch aligns with existing behavior in `get_preferred_languages()` when NO_GETTEXT is defined, where these locales are already filtered. He examines the implementation in `http.c` that skips these values during header construction and verifies the test cases in t5541 that demonstrate: (1) no header sent when only invalid locales are present, (2) valid headers when mixed with proper language tags.

The review suggests a potential alternative approach - validating language codes by length (2-3 characters per ISO 639) which would implicitly filter "C" and "POSIX" without explicit checks. However, Tobler acknowledges this stricter validation may not provide practical benefits beyond the current solution. He confirms the test coverage adequately verifies the filtering behavior for both standalone and mixed locale cases.

This continues the thread's technical evaluation of whether selective filtering (current patch) is preferable to more comprehensive solutions like locale mapping or length-based validation. The discussion remains focused on implementation details rather than reopening the fundamental approach debate from earlier in the thread.
