This is a technical discussion about HTTP protocol compliance regarding language tag validation in Git's HTTP transport.

Collin Funk responds to Justin Tobler's suggestion about using length-based validation for language tags in Accept-Language headers. Tobler had proposed checking that language codes (before any '_') are 2-3 characters long, which would naturally filter out invalid "C" and "POSIX" values without explicitly listing them. 

Funk agrees this approach seems better than the current patch's explicit filtering of just "C" and "POSIX", as it would: (1) handle more invalid cases beyond just those two values, (2) avoid the need to maintain a list of valid BCP 47 language tags, and (3) provide more comprehensive validation while still being simple to implement. 

The exchange shows the thread moving toward considering this alternative validation approach, though Tobler had noted it might not provide much practical benefit over the current solution. This continues the thread's theme of balancing standards compliance with implementation simplicity, now with a bit more technical detail about possible validation heuristics.
