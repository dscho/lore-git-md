This is a follow-up discussion in the thread about HTTP protocol compliance for language tag handling. Han Young responds to Collin Funk's suggestion about converting system locales to BCP 47 language tags, pointing out practical limitations with this approach.

The email notes that even if Git attempted to map locales to BCP 47 tags, there's no guarantee the resulting language would be supported on all systems - particularly highlighting issues with musl libc (which lacks locale support entirely) and variations in locale availability across Linux distributions. Han also raises the non-trivial problem of language matching when multiple variants exist (like Portuguese from Portugal vs. Brazil).

While acknowledging the database requirement Funk mentioned earlier, Han suggests hardcoding locale names might work, but identifies a separate challenge: filtering out locales that glibc itself doesn't support. This continues the thread's theme of balancing standards compliance with practical implementation constraints, though doesn't propose a concrete alternative to the current patch's selective filtering approach.

The exchange maintains the technical focus on HTTP header handling while surfacing deeper platform compatibility considerations that would affect any more comprehensive solution. No new code changes are suggested - this remains a discussion of design tradeoffs.
