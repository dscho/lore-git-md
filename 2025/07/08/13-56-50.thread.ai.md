Thread identity: Two-part series deprecating and removing `core.commentChar=auto` configuration option, initiated by Phillip Wood, now facing reconsideration after Junio C Hamano's feedback. This change affects interactive commit/rebase workflows where Git automatically selects comment characters.

Core problem: The `core.commentChar=auto` feature's heuristic for selecting comment characters is fundamentally flawed, failing in cases involving commit templates with comments, prepare-commit-msg hooks adding comments, and rebase's fixup/squash operations. The design limitations make the feature unreliable, but Junio now questions whether deprecation is the right path versus fixing or documenting limitations.

Current status:
- Patch 1/2 documents deprecation in BreakingChanges.adoc and core.adoc, guards functionality behind `WITH_BREAKING_CHANGES` ifdefs, and marks affected tests
- Patch 2/2 implements user-facing deprecation warnings with comprehensive advice generation
- Junio has proposed alternative approaches: (1) keep "auto" but make it equivalent to "#" when specified, or (2) document the feature's limitations as known issues while leaving it in place
- Test failures (including one from Ayush Chandekar's prior bugfix) reveal cases where the "auto" behavior is too literal, though Ayush now seeks clarification on Junio's specific technical concerns about these failures

Technical details:
- Changes span Documentation/config/core.txt, BreakingChanges.adoc, builtin/commit.c, config.c
- New `struct comment_char_cfg` tracks config file state
- Config callback records file locations and duplicate keys
- Test updates in t/t7502-commit.sh, t/t3404-rebase-interactive.sh, t/t7502-commit-porcelain.sh
- Implementation uses compilation flags for future removal in Git 3.0
- Fixing the feature would require major code reorganization to gather all comment information upfront
