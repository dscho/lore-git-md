This thread discusses the proposed deprecation and removal of Git's `core.commentChar=auto` configuration option, which automatically selects a comment character for interactive workflows like commit and rebase. Phillip Wood initiated the change, arguing the feature is fundamentally broken due to architectural limitations in how Git handles comment characters across templates, hooks, and rebase operations.

Junio Hamano initially questioned the deprecation path, suggesting alternatives like silently treating "auto" as "#" or documenting the feature's limitations. However, in the latest exchange, Junio has moved closer to Phillip's position. He now acknowledges that the deprecation warnings will properly handle configuration scopes (global vs local) and agrees that a silent fallback to "#" would be inadequate since users likely chose "auto" because standard characters didn't work for their use case.

The technical implementation appears settled, with the deprecation machinery now correctly identifying where "auto" was configured. The remaining question is whether to proceed with full removal in Git 3.0 (Phillip's preference) or keep the feature with documented limitations. Junio still expresses some reservations about user impact but seems increasingly convinced by Phillip's arguments about the feature's inherent flaws.

This represents significant progress toward resolution, with the discussion now focused on the final decision about the feature's fate rather than implementation details. Phillip has addressed Junio's technical concerns while maintaining his stance that deprecation is the right path forward.
