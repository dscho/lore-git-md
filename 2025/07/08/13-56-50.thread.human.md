This thread has been discussing the deprecation and planned removal of Git's `core.commentChar=auto` configuration option, which automatically selects a comment character for interactive workflows like commit message editing. The feature has proven fundamentally flawed in several scenarios, particularly when commit templates or hooks add their own comments.

Phillip Wood has led the effort to remove this problematic feature, proposing a two-patch series that first documents the deprecation and then implements user-facing warnings. After extensive discussion, Junio C Hamano has withdrawn his earlier technical objections about configuration scope handling, though he still questions whether complete removal is justified versus simply documenting the feature's limitations.

The latest exchange focuses on practical aspects of the deprecation warnings. Phillip confirms the warnings will recommend updating the setting in the same scope where `auto` is currently configured (system, user, or local), but raises an important edge case: when `auto` is set in a system-wide config file that the user can't modify, should the advice suggest overriding it in their personal config instead? The plan remains to make Git error out when encountering `auto` after version 3.0, rejecting Junio's earlier suggestion to silently fall back to `#` which could cause confusion.

With the technical implementation now solid and scope handling properly addressed, the discussion has narrowed to these final user experience considerations. Phillip indicates he'll send an updated patch series soon, suggesting this long-running thread is nearing resolution. The core disagreement now is philosophical - whether to completely remove a broken feature or document its limitations - rather than technical.
