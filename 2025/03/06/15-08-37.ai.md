Performance optimization for the refs/files backend, implementing batched refname availability checks during transactions. This is patch 6/16 in a series focused on optimizing refname checks across Git's ref backends.

The patch extends the batching approach from the reftable backend (patch 5/16) to the files backend, though with more complexity due to multiple call sites. It identifies two key locations where batching makes sense: during lock acquisition (when checking for packed ref conflicts) and initial transaction setup. The implementation queues refnames during `lock_raw_ref()` and performs a single batched check via the new `refs_verify_refnames_available()` API (introduced in patch 4/16) before proceeding with the transaction.

A notable tradeoff is acknowledged: the packed-refs file could change between the batched check and actual locking, creating a potential race condition. The patch maintains the existing locking sequence to avoid changing user expectations, accepting this limitation. The changes are mechanical, adding a `refnames_to_check` parameter through the call stack and consolidating verification logic.

Key technical details:
- Modifies `lock_raw_ref()` and `lock_ref_for_update()` to collect refnames
- Adds batched verification in `files_transaction_prepare()`
- Maintains existing error handling (TRANSACTION_NAME_CONFLICT)
- Preserves current packed-refs locking semantics despite race condition
- Follows same pattern as reftable backend changes in patch 5/16
- Files modified: `refs/files-backend.c` (42 lines changed)
- Functions touched: `lock_raw_ref()`, `lock_ref_for_update()`, `files_transaction_prepare()`
- Data structures: Uses `string_list` for batching (same as reftable impl)
- Error paths: Maintains existing TRANSACTION_NAME_CONFLICT behavior

This continues the series' pattern of backend-agnostic optimizations while respecting each backend's specific constraints. The race condition with packed-refs is noted as a known limitation that would require more invasive changes to fix.
