Performance optimization patch (7/16) extending batched refname verification to the files backend's initial transactions. This patch refactors the files backend's initial transaction handling to use the batched refname availability checking API introduced earlier in the series. While currently maintaining the same per-ref checking behavior, this sets up for future performance improvements when cloning or migrating to the files backend by collecting refnames into a string_list for consolidated verification.

The changes modify `files_transaction_finish_initial()` to:
1. Collect all refnames into `refnames_to_check` string list during initial scan
2. Perform a single batched verification after locking packed-refs
3. Maintain identical error handling (TRANSACTION_NAME_CONFLICT) and validation logic
4. Preserve special handling for symbolic refs, root refs and reflogs

Key technical details:
- Adds new `refnames_to_check` string_list alongside existing `affected_refnames`
- Moves verification after packed-refs locking but before transaction commit
- Keeps same BUG check for old_oid in initial transactions
- Follows same pattern as patch 5/16's reftable changes
- Prepares for future optimizations while currently maintaining same behavior

The patch is part of the broader effort to optimize refname availability checks across all backends, with this specifically targeting the files backend's initial transaction path. While not yet showing performance gains in this patch, it enables subsequent optimizations that will benefit cloning and format migration scenarios. The changes maintain all existing validation semantics while restructuring the code to support batched operations.
