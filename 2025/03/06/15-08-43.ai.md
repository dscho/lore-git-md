Performance optimization for reftable backend implementing iterator seeking capability.

This patch (12/16 in the refs optimization series) adds seeking support to reftable iterators, building on the iterator reseek foundation established in previous patches. The implementation leverages existing low-level reftable seeking capabilities while making two deliberate design choices: reflog iterators explicitly don't support seeking (as there's no clear use case for seeking reflog entries), and the patch now properly checks for initialization success of `reftable_stack_init_ref_iterator()`.

Key technical changes include:
- Adding a `seek` method to the reftable ref iterator vtable
- Making the `prefix` field heap-allocated to support reseeking
- Implementing proper cleanup of the prefix in `reftable_ref_iterator_release`
- Adding explicit error checking for iterator initialization
- Adding a BUG() assertion for attempts to seek reflog iterators

The changes are localized to `refs/reftable-backend.c` and maintain backward compatibility with existing iterator usage patterns. This completes the reftable-specific portion of the iterator reseek capability, complementing the merged iterator support added in patch 11/16. The implementation follows the same pattern seen in other backend optimizations in this series, though notably differs in its handling of reflog iterators where seeking is explicitly prohibited rather than implemented.

Karthik Nayak had previously reviewed an earlier version of this patch with only minor wording suggestions, and the current implementation appears technically sound as part of the overall optimization series. The patch demonstrates measurable performance improvements in the reftable backend while maintaining clear boundaries around supported functionality.
