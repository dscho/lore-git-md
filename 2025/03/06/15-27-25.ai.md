Bugfix for the merge-ort backend addressing a crash during cherry-pick operations involving directory renames. The issue occurs when cherry-picking a commit that moves a file into a directory that was itself renamed in the current branch, causing an assertion failure in `process_renames()`. Dmitry Goncharov originally reported the issue with a clear test case showing both the crash in ort and incorrect behavior in the recursive backend.

The problematic scenario involves:
1. A file moved from `tools/hello` to `hello` on one branch
2. A separate file `world` being moved into `tools/world` on another branch
3. Attempting to cherry-pick the second move results in either a crash (ort) or incorrect conflict resolution (recursive)

Goncharov's initial fix attempted to ignore directory renames that suggest moving a file to itself, but Elijah Newren notes this produces misleading conflict messages. Newren indicates he has an alternative fix coming that will:
- Incorporate the test case into existing merge tests (t6423 rather than new t3515)
- Properly handle the directory rename conflict
- Not worry about fixing the recursive backend since it's slated for removal

The patch touches merge-ort.c's rename collection logic and adds test coverage. This appears to be a legitimate edge case in the merge machinery that needs proper conflict detection rather than crashing. Newren's response suggests the fix will properly surface the directory rename conflict to users.
