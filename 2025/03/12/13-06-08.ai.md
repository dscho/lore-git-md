Performance optimization series for refs subsystem (patch 7/16) - files backend batch verification.

This patch continues the refname availability check optimization series by implementing batched verification for initial transactions in the files backend. The change refactors the initial transaction logic to collect refnames into a string list (`refnames_to_check`) rather than verifying them individually, though the actual performance gains will be realized in later patches that optimize the batch verification itself.

The key technical change moves from per-ref `refs_verify_refname_available()` calls to collecting all refnames first in `refnames_to_check` before batch verification. Unlike the reftable backend implementation in patch 5/16, this version deliberately avoids sorting the refnames to maintain the files backend's lock-free behavior, accepting a potential race condition as a performance tradeoff.

Reviewer shejialuo notes redundant text in the commit message and reiterates their question from patch 5/16 about the sorting inconsistency between backends. The thread context shows this is an acknowledged but non-blocking issue, with the files backend's unsorted approach being an intentional design choice for performance reasons despite the theoretical race condition.

This patch serves as preparatory work for the iterator reuse optimization that will be completed in patch 16/16, with the series having already gained final technical approval from Karthik Nayak. The files backend implementation follows the pattern established in earlier patches while maintaining its backend-specific constraints.
