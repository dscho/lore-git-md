This is a follow-up discussion in the cruft pack size limit thread, focusing on potential mechanisms to mark packs as "frozen" when they approach size limits.

Taylor Blau responds to Junio Hamano's suggestion about using a .keep-like mechanism to mark packs that have reached their size limit. While acknowledging the idea's merit, Taylor points out practical limitations: the current .keep mechanism doesn't distinguish between user-requested keeps and system-generated ones, and creating a new .frozen mechanism would add complexity. He also notes that with the current size-based accumulation order, large packs (like a 198MB one) would rarely need repacking anyway.

Regarding Junio's suggestion about extending pack headers to record size limits, Taylor considers this a longer-term possibility but maintains that the current v3 implementation (with strict size enforcement) is sufficient for now. The discussion appears to be winding down, with Taylor indicating the v3 patch should still be queued while leaving room for future improvements to pack metadata handling.

Key technical points:
- Current .keep mechanism limitations in distinguishing user vs system needs
- Potential future directions involving pack header extensions
- Reaffirmation that v3 behavior adequately handles the immediate needs
- Implicit acceptance that strict size limits will remain for now

The email doesn't introduce new code changes but rather discusses design considerations that could influence future work, while confirming the existing approach remains valid. The thread seems to be reaching its natural conclusion with this exchange.
