Performance optimization for the files backend in the refname availability checking series. This is patch 6/16 in v6 of the series, implementing batched refname availability checks for the files backend similar to what was done for reftable in the previous patch.

The patch modifies `files-backend.c` to collect refnames needing verification into a string list during transaction preparation, then performs a single batched check via `refs_verify_refnames_available()` rather than individual `refs_verify_refname_available()` calls. The author identifies five call sites for refname verification in the files backend, determining only two (in `lock_raw_ref()` and `files_transaction_finish_initial()`) are suitable for batching.

Key changes include:
- Adding a `refnames_to_check` string list parameter to `lock_raw_ref()` and `lock_ref_for_update()`
- Modifying `files_transaction_prepare()` to collect and verify refnames in batch
- Maintaining the existing (suboptimal) packed-refs locking sequence to avoid changing user-visible behavior, despite the race condition this introduces
- Proper cleanup of the temporary string list

The patch follows the same pattern as the reftable optimization in patch 5/16, completing the files backend portion of the batched verification infrastructure. Performance measurements from earlier in the series show 1.19-1.27x speedups for the files backend in benchmarks. The implementation appears thorough, with clear analysis of the tradeoffs around packed-refs locking semantics.
