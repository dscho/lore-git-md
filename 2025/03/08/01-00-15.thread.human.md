This thread addresses a bug in Git's diffcore-rename logic that could trigger a BUG() condition or access uninitialized memory when combining break detection (-B) with --follow options. The issue, present since Git v2.31.0, stems from incorrect assumptions in the break_idx tracking logic that didn't account for how --follow can skip paths.

Olaf Hering originally reported the bug, and Elijah Newren provided a fix that adds safety checks around break_idx access while maintaining the optimization's benefits. The patch includes a test case in t4206-log-follow-harder-copies.sh, though it currently only reliably fails under valgrind.

Jeff King (Peff) has now joined the discussion, agreeing with the technical solution but raising concerns about test reliability. He notes the test doesn't fail under ASan/UBSan and has found that the bug behaves differently with directory pathspecs versus direct file paths. While the core fix remains uncontested, the conversation has shifted to improving test coverage for this edge case. The changes remain focused on diffcore-rename.c's handling of broken pairs, with the test case being the main point of ongoing discussion.
