Bugfix targeting diffcore-rename's interaction between break detection and --follow.

This patch fixes a BUG() condition that could occur when using both break detection (-B) and --follow together in Git's rename detection logic. The issue stems from a 2020 optimization (commit 9db2ac56168e) that changed how rename destinations are tracked, assuming broken pairs would always be processed consecutively. This assumption fails when --follow skips certain paths, potentially leading to incorrect index lookups or access to uninitialized memory.

The fix adds additional safety checks around the break_idx tracking, ensuring we don't try to access invalid array indices when the expected pairing doesn't occur. The patch includes a test case that demonstrates the issue (though it notes the test may only reliably fail under valgrind due to uninitialized memory access).

The bug was reported by Olaf Hering after being present since Git v2.31.0, and while the fix is relatively small, the commit message provides thorough context about the underlying assumptions and why they failed in this edge case. The changes affect diffcore-rename.c's handling of broken pairs and adds a new test in t4206-log-follow-harder-copies.sh.
