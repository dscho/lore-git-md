This is a technical discussion about limitations in Git's path-filtered log behavior with subtree merges, building on Oswald Buddenhagen's bug report. Johannes Schindelin analyzes why `git log --follow` fails to properly track directory renames in subtree-merged histories, particularly affecting git-gui's development workflow.

The email digs into implementation details in `tree-diff.c`, specifically the `try_to_follow_renames()` function. Schindelin outlines what would be needed to support directory-level rename tracking: replacing single-path comparisons with strset/strvec operations, modifying pathspec handling, and accounting for performance implications. He notes the current silent failure when passing directories to `--follow` is problematic.

Key technical points include the need to:
- Replace single-path queue access with multi-path handling
- Modify pathspec matching to work with multiple items
- Restructure the rename-following logic to handle directory cases
- Consider performance impacts of nested loops

The analysis suggests this would be a non-trivial change with potential performance tradeoffs, while also highlighting the current UX issue where Git silently accepts invalid directory arguments to `--follow`. The discussion focuses on the technical feasibility rather than proposing a concrete solution, indicating this may require deeper architectural work in Git's revision walking code.
