This is a cover letter for a bugfix and CI infrastructure series addressing potentially unsafe assertions in Git's codebase. The v2 series introduces a static analysis job to detect assertions with possible side effects and provides a safer alternative macro.

The series builds on previous discussion that validated both the technical approach (a clever compiler trick to detect problematic assertions) and resolved licensing concerns about the detection method. The core idea is to replace risky `assert()` calls with a new `BUG_IF_NOT()` macro that remains active in production builds.

Key changes in v2 include:
- Documentation that the compiler trick's author has placed it in public domain
- Confirmation that the approach works reliably across GCC, Clang and MSVC
- The series now systematically converts the 9 flagged assertions across merge machinery, object storage, and parallel checkout subsystems

The cover letter explains the motivation well: while CodingGuidelines could warn about risky assertions, this CI-based approach provides automated enforcement. The static analysis catches assertions containing function calls (potential side effects), though human review confirms the current cases appear safe. The solution is pragmatic - rather than trying to perfectly analyze side effects, it converts the flagged assertions to use the safer macro.

This appears to be a well-considered improvement to Git's code safety infrastructure. The technical approach has been vetted in the thread, and the implementation touches only the necessary assertions while maintaining compatibility. The series seems ready for inclusion pending any final review comments.
