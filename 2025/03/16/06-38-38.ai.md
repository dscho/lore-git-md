This is a follow-up in the thread about safer assertion handling in Git's codebase, specifically addressing licensing concerns around the CI detection approach for problematic assertions.

The email resolves the licensing uncertainty around the clever compiler trick used in patch 2/3 to detect assertions with potential side effects. Elijah Newren reports that after contacting the original author of the two-line technique (which redefines `assert()` to reference an undefined symbol), they have placed it into the public domain with no warranty. This clears the way to proceed with the current implementation approach without licensing concerns.

The core technique remains: during static analysis builds, the CI script redefines `assert(expr)` as `(void)(not_supposed_to_survive || (expr))`, causing compilation to fail if the assertion contains function calls (potential side effects). This had been technically validated earlier in the thread (working reliably across GCC, Clang and MSVC), but was held up by licensing questions about the clever implementation.

With this resolution, the series can move forward with its original approach to:
1. Introduce BUG_IF_NOT() for always-active assertions
2. Implement automated CI detection of risky assertions
3. Convert flagged cases to use the safer infrastructure

The affected subsystems remain merge machinery (merge-ort.c, merge-recursive.c), object storage (object-file.c), and parallel checkout, with minor updates to sequencer and scalar. Elijah indicates he will send a revised version of the patch with updated commit message documentation about the licensing status.
