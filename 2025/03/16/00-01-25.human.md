This is a reply in the ongoing thread about Windows-specific race conditions in file handling, specifically addressing the second patch which fixes an `EACCES` vs `EEXIST` mapping issue in MinGW file operations.

Johannes Schindelin raises concerns about Patrick Steinhardt's proposed fix for the Windows file locking race condition. While acknowledging the fix works for the reftable test case, Schindelin points out that `ERROR_ACCESS_DENIED` on Windows can indicate either a file deletion race (as in the test case) or genuine permission issues. The current patch would incorrectly report "file exists" for permission-denied cases, potentially masking real problems when users lack write permissions in safe directories.

Schindelin suggests alternative approaches: either handling `EACCES` differently higher in the stack, making the behavior Windows-specific with backoff logic, or finding a way to distinguish between the two error cases. The concern is particularly relevant because the change affects all callers of `open()` with `O_CREAT` through the lockfile machinery, not just the reftable case.

This adds an important perspective to the discussion Junio requested Windows expert input on, highlighting a potential side effect of the current solution that wasn't fully considered in the initial review. The thread now needs to resolve whether the patch's benefits outweigh this risk or if a more nuanced solution is needed.
