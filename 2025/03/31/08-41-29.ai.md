Refactoring of reftable block iterators to support reseeking. This is part 11/16 in Patrick Steinhardt's ongoing series to improve the reftable API for external consumers.

The patch separates iterator initialization from seeking operations, storing the block pointer during initialization so the iterator can be reseeked without requiring the block parameter on subsequent seeks. Key changes include:
- New `block_iter_init()` function that takes the block and stores it in the iterator
- Modified `block_iter_seek_key()` and `block_iter_seek_start()` to operate on pre-initialized iterators
- Updated all callers to first initialize then seek
- Maintained test coverage with adjustments to test cases

This change enables future work to expose a `reftable_iterator` interface for blocks by making the iterators properly reusable. The implementation is mechanical but important groundwork - it follows the series' pattern of incremental improvements to the block reading pipeline while maintaining clear public/private boundaries. The changes affect core iteration logic in `reftable/block.c` and its callers across the codebase, with corresponding test updates in the unit test suite.
