New AI thread summary:

This thread introduces a new `--must-filter` option for `git fetch` and `git clone` that enforces server-side filter support. Currently, when a server doesn't support the requested filter, these commands merely warn and proceed without filtering. The patch changes this behavior to fail with an error when `--must-filter` is specified.

The implementation spans multiple layers:
- Command-line interfaces in `builtin/{clone,fetch}.c` add the new option
- Transport plumbing in `transport.{c,h}` propagates it via new `must_filter` field in `struct git_transport_options`
- Protocol handling in `fetch-pack.c` checks server capability and `die()`s if filtering is required but unavailable
- New test cases in `t0410-partial-clone.sh` (currently marked `test_expect_failure`)

The change addresses user requests from a Stack Overflow discussion and prior mailing list threads for stricter filter enforcement. Key technical details:
- Maintains backward compatibility (default remains warning-only behavior)
- Affects all filter types (blob:none, sparse:oid, etc.)
- Touches core fetch/clone machinery without modifying on-disk formats
- Adds capability check during protocol negotiation

Open questions:
- Test status (why marked `test_expect_failure`?)
- Whether to extend similar behavior to other commands using filters
- Potential interaction with promisor remotes and partial clone edge cases

The patch provides a focused solution to ensure users can enforce filtering requirements when partial clone behavior is critical to their workflow.
