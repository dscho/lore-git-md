This is a review comment on a patch that adds SHA implementation reporting to `git version --build-options`. Junio C Hamano agrees with the feature's goal but raises concerns about the implementation approach.

The core issue is about maintainability and consistency in how SHA implementation detection is handled. The current patch uses an if/elif/endif cascade that assumes only one SHA implementation is defined, which could become problematic if multiple implementations are ever defined simultaneously. Junio suggests making each implementation check independent (#if defined) rather than chained, which would both make the code clearer and help catch build misconfigurations.

He also questions whether the human-readable labels ("OpenSSL", "blk", etc.) are necessary, proposing instead to output the raw define names (SHA1_OPENSSL) which would be more precise and require less maintenance. This touches on a deeper architectural question about how these implementation choices should be represented throughout Git's codebase.

The feedback doesn't reject the feature but focuses on making the implementation more robust and maintainable. It's a typical mid-review refinement discussion where an experienced maintainer spots potential future maintenance issues in an otherwise sound patch. The ball is now in the patch author's court to either justify the current approach or revise it based on these concerns.
