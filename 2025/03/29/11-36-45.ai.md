This is a review response in the ongoing thread about reporting SHA implementations in `git version --build-options`. Junio C Hamano raises several technical concerns about the implementation approach in patch 1/2, focusing on maintainability and consistency issues with the current if/elif/endif cascade for detecting SHA implementations.

The key points are:
1. The current implementation assumes only one SHA1_* symbol is defined, but there's no clear synchronization between this code and other parts of the system (like hash.h) that make similar assumptions.
2. The if/elif/endif chain creates maintenance burden as new implementations are added, requiring developers to find the "right place" in the cascade.
3. The code could be simplified by making each implementation check independent (#if defined() blocks rather than if/elif), which would also help catch misconfigurations where multiple implementations are defined.
4. Questions whether human-readable names are necessary, suggesting using the raw symbol names (SHA1_OPENSSL) might be more straightforward for developer-oriented output.

This feedback doesn't reject the patch's goal but suggests significant implementation changes to make the code more maintainable and robust. The concerns are particularly relevant given this is developer-facing output where raw technical accuracy may be preferred over human-friendly formatting. The response implies the patch may need a respin to address these architectural concerns before proceeding.
