This is a technical discussion about build system behavior and test suite variable propagation, continuing the thread about GIT-BUILD-OPTIONS regression.

Jeff King (peff@peff.net) responds to Taylor Blau's clarification about the problematic test case (using t/interop rather than t/perf as originally mentioned). The core issue remains that GIT-BUILD-OPTIONS can override manually passed variables in test suite invocations, particularly affecting compilation-dependent tests.

Peff suggests the deeper issue may be that certain variables like GIT_PERF_MAKE_OPTS and GIT_INTEROP_MAKE_OPTS shouldn't be in GIT-BUILD-OPTIONS at all, since they don't affect the main build. He outlines two key complications: 1) the current behavior where initial make invocations cache these variables, and 2) the syntax mismatch between make and shell variable formats. While proposing a more fundamental solution (reading values directly when running tests), he acknowledges this might be too disruptive to existing workflows.

The email reveals tension between fixing the immediate regression (Taylor's proposal to only emit non-empty variables) and addressing what Peff sees as underlying design issues. Peff questions whether supporting the specific broken workflow is worth the complexity, noting these are developer-facing tools with limited usage. However, he doesn't strongly oppose Taylor's solution if it can be implemented cleanly.

Key technical points mentioned:
- The distinction between make variables and environment variables in test invocations
- The config.mak vs. GIT-BUILD-OPTIONS interaction
- Potential solutions involving make -epn parsing
- The developer-specific nature of affected test suites (t/interop, t/perf)

The discussion highlights the challenge of balancing backward compatibility with cleaner design in Git's build/test infrastructure.
