This is a technical discussion about build system behavior affecting test suite variable propagation, continuing the thread about GIT-BUILD-OPTIONS regression.

Jeff King (peff@peff.net) responds to Taylor Blau's clarification about the problematic test case (using t/interop rather than t/perf as originally mentioned). The core issue remains that GIT-BUILD-OPTIONS can override manually specified variables in test invocations, particularly affecting compilation-related test suites.

Peff suggests the deeper issue may be that these test-specific variables (like GIT_PERF_MAKE_OPTS) shouldn't be in GIT-BUILD-OPTIONS at all, since they don't affect the main build. He identifies two complications with removing them: potential reliance on the current behavior, and the need to parse make-formatted config.mak in shell scripts. While acknowledging Taylor's proposed fix (only non-empty variables in GIT-BUILD-OPTIONS) would work, Peff questions whether supporting this edge case is worth the complexity, given these are developer-facing tools with limited usage.

The email highlights the tension between fixing a clear regression and maintaining clean architectural boundaries in the build system. Peff seems open to Taylor's solution but cautions about adding complexity for what he sees as a marginal use case. The discussion remains unresolved but has narrowed to considering whether to prioritize backward compatibility or cleaner long-term design.
