Bug report about `git fetch --prune --atomic` core dump when encountering a lock file.

This is a bug report demonstrating a crash in Git when running `git fetch --prune --atomic` while a lock file exists in the repository. The reporter provides clear reproduction steps: after cloning a repository and creating a test branch, they manually create a lock file (`test.lock`) in the refs directory, then attempt an atomic fetch operation. Instead of gracefully handling the lock conflict, Git aborts with a core dump showing a BUG message from refs.c about an operation on a closed reference transaction.

The error suggests the atomic fetch transaction isn't properly handling the case where it can't acquire a lock, leading to an assertion failure rather than a clean error message. The reporter includes system information showing this occurs on Git v2.49.0-rc1 running on Linux with glibc 2.35. The core dump indicates this is a serious error condition that should be handled more gracefully, particularly since lock conflicts can occur in normal operation (e.g., when another Git process is legitimately running).

Key technical details for future reference:
- Triggered by `fetch --prune --atomic` with existing lock file
- Error occurs in refs.c line 2435
- BUG message: "abort called on a closed reference transaction"
- Creates a core dump file (core.1298748 in this case)
- System info shows Git built from commit 683c54c999

This appears to be a legitimate bug in the atomic reference transaction handling that warrants investigation by the refs subsystem maintainers. The reporter has provided all necessary details to reproduce and diagnose the issue.
