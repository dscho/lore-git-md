This thread continues the effort to add SHA-256 repository support to gitk, reviving and completing work originally started by Rostislav Krasny four years ago. Takashi Iwai has taken up the task, submitting a two-patch series that would make gitk properly handle SHA-256 repositories - an important step for distributions like openSUSE that use SHA-256 workflows.

The discussion has progressed through several rounds of review from Johannes Sixt (gitk's maintainer), who identified both implementation details needing correction and larger design questions. The first patch's basic SHA-256 support implementation has been defended by Iwai regarding some specific choices - particularly the regex range check in `gotocommit` and the split between `objformat` and `hashalgorithm` variables. These explanations help clarify the design intent behind certain decisions that initially appeared as potential problems.

Several key tasks remain before the series can be merged:
1. Addressing five additional locations with hardcoded SHA-1 length assumptions that Johannes identified
2. Resolving the design question about whether hash length preferences should be algorithm-specific or repository-agnostic
3. Implementing code quality improvements to the first patch (message cleanup and indentation fixes)
4. More thorough testing of hash parsing edge cases

The changes remain focused on gitk's Tcl UI layer, keeping the work contained while bringing one of Git's last major components into SHA-256 compatibility. The discussion shows good progress, with Iwai actively engaging with review feedback while maintaining clear justifications for certain original design choices. The path forward is now well-defined, with the remaining work being more mechanical than conceptual.
