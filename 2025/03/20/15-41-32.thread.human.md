This thread covers a two-part series adding SHA-256 repository support to gitk, completing work originally started by Rostislav Krasny four years ago. Takashi Iwai has revived and updated the patches to address gitk's inability to handle SHA-256 repositories, which is particularly important for openSUSE's workflow.

The first patch implemented basic SHA-256 support through Tcl changes, introducing a dynamic hash length system. Johannes Sixt provided thorough review feedback, noting several code quality issues around commit messages, indentation, and hardcoded values that needed addressing. The second patch added hash-algorithm-aware length preferences, which Sixt questioned from a design perspective - suggesting users might prefer consistent behavior across repositories regardless of hash type.

In the latest review, Sixt identified five remaining locations where SHA-1 length assumptions ("40") still appear in the code, spanning tag generation, patch creation, and display formatting. These should be converted to use the dynamic `$hashlength` variable like the rest of the implementation. While these are mechanical fixes rather than design issues, they'll need to be addressed before merging.

Key outstanding items:
1. Resolving the design question about whether length preferences should be algorithm-specific or repository-agnostic
2. Addressing all remaining hardcoded SHA-1 length assumptions in the code
3. Incorporating Sixt's earlier feedback on code quality and commit messages

The changes are confined to gitk's UI layer and don't affect core Git operations. This work represents one of the final pieces needed for full SHA-256 ecosystem compatibility.
