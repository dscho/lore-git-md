This thread focuses on adding SHA-256 repository support to gitk, reviving a 4-year-old effort to complete Git's ecosystem compatibility. The initial two-patch series from Takashi Iwai implements basic SHA-256 handling through Tcl modifications, including dynamic hash length detection and UI updates. Johannes Sixt's thorough review identified several technical issues, particularly around hardcoded SHA-1 assumptions that needed conversion to use variable lengths.

In the latest update, Iwai acknowledges and agrees to address five remaining procedures (`longid`, `shortids`, `setlink`, `mkpatch`, `mktag`) that still contain fixed 40-character length references, moving toward resolving one of the key outstanding technical items. While these conversions appear straightforward, the more fundamental design question remains open: whether hash length display preferences should be algorithm-specific (Iwai's position, motivated by openSUSE's real-world SHA-256 needs) or repository-agnostic (Sixt's preference for consistent user settings across repositories).

The discussion has clarified both the technical requirements and user experience tradeoffs. With Iwai committing to clean up the remaining length conversions and Sixt's earlier feedback on message/indentation still pending, the series appears functionally complete but needs these final polish items resolved before merging. Once done, this will eliminate one of the last major gaps in Git's SHA-256 ecosystem support.
