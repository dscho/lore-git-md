Atomic fetch/prune crash bug investigation and fix: A critical regression in Git v2.49.0-rc1 causes core dumps when running `git fetch --prune --atomic` if lock files exist, triggered by commit c92abe71df ("builtin/fetch: fix leaking transaction with `--atomic`"). The bug manifests as a BUG message from refs.c:2435 about operations on closed reference transactions, with two confirmed reproduction cases: (1) original report with test.lock in refs/, and (2) Justin Tobler's simplified test using a mirrored repository with manual lock files. The root cause involves improper error handling where lock conflicts trigger assertion failures rather than graceful cleanup in atomic reference transactions.

The fix modifies `builtin/fetch.c`'s error path to explicitly free failed transactions instead of relying on abort, preventing the BUG() trigger while maintaining c92abe71df's memory leak fixes. Justin Tobler's accompanying test case verifies atomic fetch now fails gracefully (without crashing) when encountering locked references, marked REFFILES-specific as it depends on filesystem lock behavior. Key technical changes include replacing implicit transaction cleanup with explicit free+NULL assignment, preserving atomic operation guarantees while fixing the crash. The solution addresses both the immediate regression and provides a regression test documenting expected behavior when atomic operations encounter locks. The patch maintains the original memory safety improvements while eliminating the dangerous crash path, with the test case serving as both verification and specification of correct error handling.
