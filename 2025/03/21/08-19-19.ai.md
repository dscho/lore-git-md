This is a discussion response about proposed `git bisect` worktree functionality. Junio C Hamano responds to Jim Cromie's RFC suggesting worktree support for bisection, offering a more incremental approach using existing capabilities.

The response suggests that `git bisect --no-checkout` already provides the necessary foundation for the proposed workflow, allowing users to manage their own checkouts across multiple worktrees while letting bisect handle the commit selection logic. This would avoid needing new core Git features while still enabling the debugging use cases described.

Key technical points raised: the existing `--no-checkout` mode separates commit selection from checkout operations, making it suitable for custom worktree management; the response questions whether limiting to two worktrees is necessary when N could be supported; and notes that third-party tools could already build on this existing functionality rather than waiting for new features.

The email maintains a constructive tone while pushing back on the need for new core functionality, positioning this as something that could be implemented externally first to validate the approach. It leaves open whether the original proposal's direct worktree integration might still be valuable if the external approach proves cumbersome.
