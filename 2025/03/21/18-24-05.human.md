Security refinement for remote object info format validation in v12 series.

This email from Peijian Ju responds to Jeff King's feedback on the security validation for the remote-object-info batch command in the ongoing remote object info series. The discussion focuses on two key improvements to the format string validation:

1. The author agrees with Jeff's suggestion to implement an allow-list approach (option 2) for validating placeholders in the format string, which would automatically treat any new placeholders as unsupported until explicitly allowed. This is seen as more maintainable than tracking disallowed placeholders.

2. They also discuss Jeff's proposal to handle unsupported placeholders gracefully by returning placeholder values (like "???") rather than erroring out. The author suggests this could provide forward compatibility as new placeholders are added.

The email also clarifies behavior for three mixed local/remote object scenarios, proposing that remote-object-info should:
- Always query the remote even if objects exist locally
- Fail for objects that only exist locally
- Maintain a clear separation from the local `info` command's functionality

This represents the final security and usability refinements to the remote object info feature after twelve iterations of review, with all major technical issues now resolved. The discussion shows careful consideration of both security hardening and future extensibility.
