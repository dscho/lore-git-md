This is a discussion about the design principles behind the `--no-optional-locks` feature for porcelain commands like `git describe` and `git diff`. Jeff King (peff) responds to Junio Hamano's clarification about the porcelain/plumbing distinction, agreeing that porcelain commands refresh indexes for correctness rather than performance.

Key technical points:
- Jeff explains how `git status --no-optional-locks` currently works - it updates the index internally for correctness but doesn't write it out to avoid lock contention
- He notes he had previously considered `git diff` as a candidate for this feature in 2017
- For scripting scenarios where the index cannot be touched, he outlines three problematic alternatives to using porcelain commands with optional locks:
  1. Accepting potentially incorrect stat-dirty results from plumbing
  2. Using a secondary index file with performance overhead
  3. Using in-memory index updates via porcelain commands

The discussion continues to explore the tradeoffs between correctness and lock contention in automation scenarios, with Jeff providing concrete examples of why the porcelain approach might be justified despite Junio's plumbing-first philosophy. The thread remains focused on finding the right balance between Git's design principles and practical scripting needs.
