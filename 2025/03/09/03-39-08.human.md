This is a discussion about the design philosophy behind optional locks in Git commands, specifically regarding the proposed `--no-optional-locks` option for `git describe` and `git diff`.

Jeff King (peff) responds to Junio Hamano's clarification about porcelain commands refreshing indexes for correctness rather than performance. While agreeing the original patches were incorrectly motivated, peff defends the underlying goal by explaining how `git status`'s existing `--no-optional-locks` implementation works - it updates the index internally for correctness but avoids writing it out to prevent lock contention.

The email explores three approaches scripts could take when needing to avoid lock contention: (1) accept potentially stale results from plumbing commands, (2) use a separate index file (with performance costs), or (3) use porcelain commands with `--no-optional-locks` that maintain correctness without writing. Peff notes he had previously considered `git diff` as a candidate for optional locks back in 2017, and while `git describe` seems less likely to need it, there's no harm in supporting it.

This continues the thread's central tension between maintaining Git's porcelain/plumbing design principles while addressing real-world scripting needs. The discussion remains productive, with peff offering concrete technical alternatives while respecting Junio's architectural concerns.
