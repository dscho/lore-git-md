Git shell command override RFC (Ayman Bagabas) - Security and design concerns raised

Proposes allowing git-shell built-in commands to be overridden via executable scripts in git-shell-commands directory, with core changes to shell.c command dispatch logic. Initial implementation relocates `cd_to_homedir()` and adds path construction/execution flow for override scripts before built-in fallback. Key technical elements include `make_cmd()` path building, `access()` checks, and `execv()` execution while maintaining backward compatibility.

Elijah Newren has raised substantial security and compatibility objections, arguing the approach introduces multiple risks: security vulnerabilities, broken internal command execution (e.g. `git-stash`), debugging complications, and potential disruption to plumbing command consumers. His technical analysis suggests these issues may be fundamental to the design rather than surface-level, challenging the RFC's core premise. The discussion now centers on whether the feature's benefits outweigh these inherent risks, with Newren advocating against proceeding in current form.

Open questions expanded to include:
- Whether security and compatibility concerns are addressable or fundamental
- If alternative approaches (PATH wrappers, aliases) could achieve goals without the risks
- Whether the feature's use cases justify the potential downsides

Technical details remain as previously described (shell.c modifications, execution flow changes) but now with significant counterpoints regarding their safety and impact on Git's internal command execution patterns. The RFC status persists as the proposal faces this substantive design challenge.
