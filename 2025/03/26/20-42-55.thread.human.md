This thread investigates a persistent test failure affecting the `backfill --min-batch-size` feature on s390x and sparc64 architectures, first noticed during the release candidate period and now resurfacing in Debian builds. The issue specifically fails the "do partial clone 2, backfill min batch size" test on these big-endian platforms, suggesting a possible endianness-related problem in either the batch size handling or trace2 event recording.

Patrick Steinhardt has taken the lead in debugging, proposing to modify the test infrastructure to use `test_grep` instead of plain `grep` in the `test_trace2_data` helper function. This change, combined with verbose test output, will reveal the actual trace2 data being recorded when the test fails. The expected JSON structure containing the promisor fetch_count value isn't being matched, but it's unclear whether this indicates a problem with the batch size handling or just the trace2 event recording. 

While two independent reports confirm the issue's reproducibility, the original feature author Derrick Stolee has not yet engaged with the debugging effort. The thread now awaits either test results from the modified debugging approach or input from the feature author to determine whether this requires platform-specific fixes or test adjustments. The consistent failure across big-endian architectures points to an underlying endianness assumption that needs to be addressed.
