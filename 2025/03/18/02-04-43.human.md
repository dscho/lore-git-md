This is a follow-up in the performance discussion about `git add .` behavior in large repositories. Yissachar Radcliffe questions some technical points from Brian M. Carlson's earlier explanation about why `git add .` is slower than `git status` or `git add -u`.

The email clarifies that piping `git status` to `git add` does actually handle untracked files (contrary to Carlson's statement that it behaves like `git add -u`), since `git status` lists both tracked and untracked files. Radcliffe then asks why the untracked cache optimization couldn't be specifically enabled for the common `git add .` case, even if it's not supported for more complex pathspecs.

The core tension here is between the practical observation that `git add .` could theoretically be much faster (as demonstrated by the piping workaround) and the design constraints that currently prevent using the untracked cache optimization in this case. While the thread has established this isn't a bug, Radcliffe reasonably pushes back on whether the current performance gap is truly necessary, suggesting there may be room for targeted optimization of the most common pathspec case.
