This is a follow-up in the performance discussion about `git add .` behavior in large repositories. Yissachar Radcliffe questions some technical points from Brian M. Carlson's earlier explanation about why `git add .` can't use the untracked cache optimization that makes `git status` faster.

The email makes three key technical points: First, it corrects a minor misunderstanding about `git status` output including untracked files (contrary to `git add -u` behavior). Second, it proposes that while complex pathspecs might not benefit from the untracked cache, the common `git add .` case could be special-cased for optimization. Third, it argues the current performance gap between direct `git add .` and the `git status | git add` workaround is unnecessarily large.

The discussion remains focused on the technical feasibility of optimizing `git add .` specifically, suggesting the current behavior may warrant reconsideration despite the general pathspec complexity constraints. No new performance measurements are provided, but the email implies the existing speed difference makes a compelling case for investigating targeted optimizations.
