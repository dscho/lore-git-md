Windows lockfile race condition discussion continues with SQLite-style polling proposed as alternative.

This email continues the discussion about fixing Windows-specific race conditions in lockfile creation, specifically addressing Johannes Schindelin's concerns about using the undocumented `RtlGetLastNtStatus()` API. Patrick Steinhardt now proposes an alternative approach inspired by SQLite's polling strategy, which he provides technical details from SQLite's implementation.

Key points in this response:
1. Rejects Johannes' suggestion to treat all `EACCES` as `EEXIST` in the lockfile subsystem, arguing it would still be incorrect when `EACCES` indicates genuine permission issues rather than deletion races.
2. Acknowledges the maintainability concerns around undocumented Windows APIs.
3. Proposes a SQLite-style polling solution that would retry operations on certain Windows error codes (ERROR_ACCESS_DENIED, ERROR_SHARING_VIOLATION, etc.) with 25ms delays up to 10 times.
4. Clarifies that the issue affects the general lockfile subsystem, not just reftable, though reftable tests make it more visible.
5. Indicates willingness to implement the polling solution if acceptable.

Technical details worth noting for future reference:
- SQLite's approach uses `winIoerrCanRetry1` macro to identify retryable errors
- Proposed retry mechanism would involve 25ms sleeps with 10-attempt limit
- Error cases to handle would include ERROR_ACCESS_DENIED, ERROR_SHARING_VIOLATION, ERROR_LOCK_VIOLATION, etc.
- Implementation would likely need to go in `mingw_open()` or the lockfile subsystem
- Distinction between reftable-specific symptoms and general lockfile issue remains important

The discussion has now narrowed to two main alternatives:
1. The original NtStatus-based precise detection (technically ideal but uses undocumented API)
2. The new SQLite-style polling approach (more maintainable but less precise)

Patrick appears open to implementing option 2 if the maintainability concerns about option 1 are deemed decisive. The thread will likely see either a new patch implementing the polling solution or further discussion about whether the NtStatus approach's benefits outweigh its maintenance costs.
