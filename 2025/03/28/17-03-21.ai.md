This is the third patch in a series improving rebase status reporting, specifically addressing user guidance during merge conflicts in interactive rebase. The patch focuses on suggesting the correct command to continue after a merge conflict - either `git rebase --continue` or `git commit` depending on how the merge was initiated.

The key change detects whether a merge conflict occurred via a rebase 'merge' instruction (which preserves authorship information) versus an 'exec git merge' command (which doesn't). The patch adds a new `merge_during_rebase_in_progress` flag to `struct wt_status_state` and modifies the status output to suggest `git rebase --continue` when appropriate, falling back to the existing `git commit` suggestion for exec-initiated merges.

Technical details include:
- New field in wt-status.h to track merge instruction origin
- Logic in wt-status.c to parse rebase's done file and detect merge commands
- Modified status output logic to show context-appropriate continuation command
- Two new test cases in t7512-status-help.sh covering both merge scenarios

The change is well-motivated by the authorship preservation issue and maintains backward compatibility while adding the more helpful suggestion. The implementation is clean with clear test coverage of both code paths. This completes the series' goal of improving rebase status reporting consistency.
