Windows lockfile race condition fix - consensus reached on NtStatus approach

Johannes Schindelin now agrees to proceed with Patrick Steinhardt's original solution using the undocumented `RtlGetLastNtStatus()` API to precisely detect Windows' `STATUS_DELETE_PENDING` condition. This comes after extensive discussion of three potential approaches:

1. The NtStatus method (now accepted) which precisely identifies pending deletions
2. Johannes' earlier proposal to broadly treat all `EACCES` as `EEXIST` (rejected as too imprecise)
3. A SQLite-style polling approach (considered but ultimately not pursued)

The issue affects Windows lockfile handling when files are marked for deletion, causing flaky test failures in t0610's reftable operations. While the problem could theoretically affect any lockfile usage, it's most visible in reftable's compaction process where lockfiles are frequently created and deleted.

Johannes had initially opposed the NtStatus solution due to its undocumented status, but after evaluating the tradeoffs, concludes it's the only approach that provides the necessary precision. He notes that while PostgreSQL used this API and SQLite avoided it with polling, Git will proceed with the more accurate solution despite its undocumented nature.

The resolution means the v2 patch series can now move forward with:
1. An uncontroversial Meson build fix
2. The NtStatus-based lockfile handling fix

This concludes a technical discussion that balanced Windows API stability concerns against the need for precise error handling in Git's lockfile subsystem.
