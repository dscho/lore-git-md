[PATCH 0/3] rebase status reporting improvements

Series from <author> improving interactive rebase usability across three key areas: merge commit handling, status output formatting, and post-merge guidance. Core changes:

1. Fixes `rebase -r` failure when creating merge commits after empty merge conflict resolution (sequencer.c). Bug manifested when merge base equals one parent, causing incorrect empty-tree detection. Patch modifies `commit_staged_changes()` to check `MERGE_HEAD` presence before skipping commit creation, adds cleanup of `MERGE_HEAD` on merge failure. Includes new test case in t3418.

2. Improves rebase status output by abbreviating merge/fixup commit lines (wt-status.c). Extends hash abbreviation to handle 'merge -C' and 'fixup -C' command formats where hash appears in third field. Introduces special case detection in `abbrev_oid_in_line()` with increased `strbuf_split_max` field count (3→4) while maintaining existing behavior for other command types. Uses new `hash` strbuf pointer to abstract field selection.

3. Corrects misleading post-merge message by distinguishing between rebase-initiated merges (suggest `git rebase --continue`) and exec-initiated merges (suggest `git commit`). Adds `merge_during_rebase_in_progress` flag to `struct wt_status_state` to track merge origin, parses rebase's done file to detect merge commands. Includes two new test cases in t7512 covering both scenarios.

Technical scope:
- Sequencer: merge commit creation logic and failure cleanup
- Wt-status: rebase status formatting (now covering all command types) and context-aware messaging
- Tests: t3418 (rebase-continue), t7512 (status-help) with expanded coverage
