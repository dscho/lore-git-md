Windows lockfile race condition discussion continues with new SQLite-inspired proposal.

This email continues the discussion about fixing a race condition in Windows lockfile handling that causes flaky tests in the reftable backend. Patrick Steinhardt responds to Johannes Schindelin's concerns about using the undocumented `RtlGetLastNtStatus()` API by proposing an alternative approach inspired by SQLite's polling strategy.

The core issue remains distinguishing between genuine permission errors (`EACCES`) and cases where a file is pending deletion on Windows. While Patrick's v2 patch used the precise but undocumented NT status API, Johannes objects to this on maintainability grounds. Patrick now suggests adopting SQLite's approach of retrying certain errors (including `ERROR_ACCESS_DENIED`) with a simple polling mechanism (25ms delays, up to 10 retries).

Key points in this response:
1. Patrick acknowledges Johannes' concern about undocumented APIs being unacceptable
2. Proposes the SQLite polling approach as a documented alternative
3. Clarifies the issue affects the general lockfile subsystem, not just reftable
4. Notes this would make races less likely rather than eliminating them entirely
5. Suggests the fix should go in the lockfile system rather than reftable-specific code

The discussion has now narrowed to evaluating this third approach, which appears to balance technical correctness with maintainability concerns. Patrick seems open to implement this if Johannes agrees, though he notes it's a mitigation rather than a complete solution. The email maintains a constructive tone while firmly establishing that the issue is broader than just reftable.
