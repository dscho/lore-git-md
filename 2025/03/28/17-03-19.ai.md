Bugfix for interactive rebase with merge commits. This is the first patch in a series improving rebase status reporting.

The patch fixes a specific edge case in `git rebase -r` (interactive rebase with merges) where an empty merge resolution (no changes after conflict resolution) would incorrectly skip creating a merge commit. The issue occurs in `sequencer.c` when the merge base equals one parent, causing the empty-tree detection to trigger prematurely. This left commits from the side branch missing from the rebased history and could leave the repository in a confusing "still merging" state after rebase completion.

The fix modifies `commit_staged_changes()` to check for `MERGE_HEAD` presence before deciding to skip commit creation, ensuring merge commits are properly created even with empty resolutions. It also adds cleanup of `MERGE_HEAD` when merges fail to start, matching existing behavior for `MERGE_MSG`. The change is accompanied by a new test case in `t3418-rebase-continue.sh` that verifies merge commit creation after empty resolution.

Technical details:
- Key change: `sequencer.c` now checks `file_exists(git_path_merge_head(r))` before skipping commit creation
- Related cleanup: `do_merge()` now removes `MERGE_HEAD` on failure to match `MERGE_MSG` handling
- Test coverage: new scenario in t3418 verifies merge commit creation with empty resolution
- Builds on previous fix e032abd5a0 for failed pick operations

The patch appears well-contained with clear motivation and thorough test coverage. It addresses a specific but meaningful usability issue in interactive rebase workflows involving merges.
