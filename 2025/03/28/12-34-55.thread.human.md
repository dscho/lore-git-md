This thread addresses a regression in gitk (Git's graphical history viewer) that causes stack exhaustion on Cygwin systems due to a recursive loop in path handling. The issue stems from changes in v2.49.0 that were intended to prevent accidental execution of Windows executables in the worktree, but inadvertently broke Cygwin compatibility.

The core problem involves gitk's `_which` function, which now creates a circular dependency when converting Cygwin's Unix-style PATH to Windows format. The reporter demonstrates that treating Cygwin as a standard Unix system (by removing the Cygwin-specific path conversion) resolves the immediate issue, though this leaves some Windows-specific behavior in place without clear justification. They suggest a more precise fix would be to limit the security-related exec/open overrides to Windows platforms only, excluding Cygwin, and mention having an alternative patch implementing this approach.

The regression originated from commit 4cbe9e0e2, which addressed Windows security concerns about executing worktree files. The discussion highlights the need to carefully distinguish between Windows native and Cygwin environments when implementing platform-specific behavior in gitk's TCL code. The reporter's proposed solution would maintain the Windows security improvements while restoring Cygwin functionality.
