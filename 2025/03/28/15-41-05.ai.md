This is a Windows-specific bugfix for lockfile subsystem race conditions, now converging on a solution after technical debate. Johannes Schindelin responds to Patrick Steinhardt's v2 patch series proposing three approaches to handle Windows' `EACCESS` errors during file operations with `O_CREAT|O_EXCL`. 

The core issue involves Windows' behavior where `CreateFileW` returns `ERROR_ACCESS_DENIED` when a file is pending deletion, which affects Git's reftable operations during concurrent access. The thread had previously debated between: 1) using the undocumented `RtlGetLastNtStatus()` API for precise error detection, 2) broadly treating all `EACCES` as `EEXIST`, and 3) implementing SQLite-style polling with retries.

Johannes now reluctantly accepts the `RtlGetLastNtStatus()` solution despite initial objections about its undocumented status, after considering the alternatives. He acknowledges this is the only solution that precisely detects pending deletions, and addresses his own concern about initialization timing. The discussion reveals the technical tradeoffs between correctness (NtStatus) and maintainability (polling), with Windows-specific considerations about API stability and error handling patterns.

Key technical points resolved:
- The fix will use `STATUS_DELETE_PENDING` detection via `RtlGetLastNtStatus()`
- Affects the lockfile subsystem broadly, not just reftable
- Johannes confirms initialization timing won't corrupt the NTSTATUS value
- SQLite polling approach (25ms delays, 10 retries) remains as a fallback option if NtStatus proves problematic

This marks a resolution to the technical debate, with Johannes conceding the precision of the NtStatus approach outweighs maintainability concerns for this case. The patch series can now proceed with this implementation unless new objections arise about the Windows API usage.
