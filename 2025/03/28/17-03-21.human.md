This is the final patch in a series improving rebase status reporting, specifically addressing how merge conflicts are handled during interactive rebases. The patch fixes a misleading message that would suggest `git commit` when continuing a rebase after resolving merge conflicts, which would lose authorship information. Instead, it now suggests `git rebase --continue` when the merge was initiated via a rebase 'merge' instruction (preserving authorship), while still falling back to `git commit` for merges initiated via 'exec git merge'.

The change adds a new `merge_during_rebase_in_progress` flag to track the merge's origin and adjusts the status output accordingly. The patch includes thorough test coverage with two new test cases that verify the different suggestions for 'merge' vs 'exec git merge' scenarios. The implementation is clean and well-contained, touching only the necessary parts of wt-status.c while maintaining existing behavior for non-rebase merges.

This completes the series' goal of improving rebase usability, particularly around merge operations, with all three patches working together to handle edge cases and provide clearer guidance to users. The changes are straightforward and unlikely to be controversial, building logically on the previous patches in the series.
