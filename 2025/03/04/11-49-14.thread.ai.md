RFC proposal for `git init` language-specific `.gitignore` support continues evolving with Junio C Hamano's latest clarification reinforcing template mechanism boundaries. The maintainer explicitly limits legitimate template usage to Git-specific configuration files (`.git/info/excludes` and hooks), pushing back against Oleg Taranenko's `--only-gitignores` proposal by emphasizing the template system's original narrow scope. This clarification strengthens the architectural constraint that any solution must work within Git's existing mechanisms without introducing language-specific special cases.

Three approaches remain under consideration: (1) rejected language-specific built-ins, (2) Randall Becker's regex-based system, and (3) the selective template proposal. All must now contend with Hamano's reinforced position that even `.gitignore`-specific template handling may exceed Git's design boundaries unless clearly tied to Git's own configuration needs. The mention of `.git/info/excludes` serves as both technical clarification and architectural marker - proposals stretching beyond this scope face high barriers to acceptance.

Key unresolved questions now include: (1) whether any form of language-aware `.gitignore` handling can satisfy the maintainer's neutrality principle, (2) if the template mechanism's original design precludes even narrowly scoped ignore-file solutions, and (3) whether this use case should be addressed entirely outside core Git via documentation/scripting. The thread's trajectory suggests diminishing prospects for core changes unless proponents can demonstrate their solution aligns perfectly with Git's template philosophy while solving needs unaddressable through trivial post-init scripting. Next steps require either patches proving the `--only-gitignores` approach respects these tightened constraints or community consensus to pursue non-core solutions.
