This is the second and final patch in a series addressing object freshening behavior in multi-cruft pack scenarios. The patch focuses on fixing an edge case where objects in large cruft packs couldn't be freshened during repacks when using `--max-cruft-size`.

The core issue occurs when an object exists in a cruft pack that exceeds the size threshold and thus won't be rewritten. Previously, Git would fail to freshen such objects because it would skip them entirely during enumeration. The patch introduces a new `ignore_packed_keep_in_core_has_cruft` flag and modifies `want_found_object()` to handle this case by:

1. Preserving objects from non-cruft packs unconditionally
2. For cruft pack objects, keeping them only if their mtime is older than the version being packed
3. Falling back to the pack's mtime when individual object mtimes can't be loaded

The implementation changes span `builtin/pack-objects.c`, with supporting modifications to `packfile.c` and `packfile.h` to expose `kept_pack_cache()`. The patch includes comprehensive test coverage in `t/t7704-repack-cruft.sh` that verifies the mtime comparison logic works correctly, including cases with both packed and packed-then-loose objects.

The commit message has been refined based on Elijah Newren's review to clarify the mtime comparison behavior (now correctly described as "at least as recent" rather than the initially reversed wording). The patch appears technically sound with thorough test coverage, though Patrick Steinhardt has raised a separate operational concern about potential long-term repacking behavior that remains under discussion.
