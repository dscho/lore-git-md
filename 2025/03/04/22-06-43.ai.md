This is a design discussion email in the ongoing thread about marking mentoring program patches in `git format-patch` subjects. Junio Hamano responds to Patrick Steinhardt's proposal of a `--patch-prefix` flag as an alternative to the original `--subject-extra-prefix` approach.

Junio argues against introducing new flags, advocating instead for using the `--subject-prefix` mechanism already in Git. He explains the existing distinction between `--subject-prefix` (for persistent project-specific prefixes) and `--rfc` (for occasional use), suggesting that GSoC markers should fall into the former category. The email demonstrates how combining these could produce subjects like "[GSoC PATCH 0/6]" or "[GSoC PATCH WIP 0/6]" without new flags.

Key technical points raised:
- Rejects `--patch-prefix` as confusing alongside `--subject-prefix`
- Clarifies semantic difference between persistent (`--subject-prefix`) and ad-hoc (`--rfc`) markers
- Shows how existing flags can combine to produce desired output
- Argues GSoC markers should be treated as persistent project identifiers
- Notes `--rfc` can insert text anywhere in subject, not just as prefix

This email significantly advances the design discussion by:
1. Providing clear reasoning against flag proliferation
2. Demonstrating how existing mechanisms can solve the use case
3. Introducing the concept of persistent vs. temporary markers
4. Showing concrete subject line examples
5. Rejecting the premise that GSoC needs special handling separate from other project identifiers

The email moves the discussion toward potentially simpler solutions while maintaining clear distinctions between existing flag purposes. It represents a strong maintainer position favoring interface simplicity over specialized additions.
