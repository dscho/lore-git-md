This is a follow-up in the Rust crate packaging thread, specifically addressing the newly surfaced Windows compatibility issue with the symlink approach from patch 2/5. Josh Steadmon responds to Junio Hamano's report of Windows test failures caused by the `git-src` symlink pointing to `../..`.

The email confirms this symlink is currently the only known solution that satisfies both key requirements: enabling `cargo package` functionality while keeping Rust configuration out of the main Git tree. Steadmon explores two potential paths forward - investigating Cargo workspaces (which might require a root-level Cargo.toml) and presents two fallback options if that fails: temporarily limiting usage to source builds only (option #1) or moving the crates to separate repositories with Git as a submodule (option #2, following patterns like zlib-sys).

The response maintains focus on the specific Windows symlink limitation while situating it within the series' broader context of crate packaging constraints. Steadmon expresses a preference for the conservative option #1 (source builds only) as an interim solution, leaving the door open for more disruptive changes if Rust integration gains more traction. The technical details center on build system interactions (symlinks, workspaces, submodules) rather than core Git functionality.
