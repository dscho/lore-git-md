This is a follow-up in the Rust crate packaging thread, addressing a newly surfaced Windows compatibility issue with the symlink approach from patch 2/5. Josh Steadmon responds to Junio Hamano's report that Windows test jobs are failing due to the `../..` symlink added to access Git sources from the isolated build directory.

Steadmon explains the symlink is currently the only known solution that satisfies both requirements: enabling `cargo package` functionality while keeping Rust configuration out of the main Git repository root. He suggests investigating a Cargo workspace approach (which would require a root-level Cargo.toml) as a potential alternative, though its viability remains untested.

If the workspace approach fails, Steadmon outlines two fallback options: temporarily limiting usage to source builds only (preventing crate packaging), or moving the Rust crates to separate repositories with Git sources as submodules. He expresses preference for the first option as a short-term solution, reserving the more disruptive repository split for potential future adoption if the Rust bindings gain significant traction.

The response maintains the technical focus of the thread while acknowledging the Windows constraint as a clear blocker that needs resolution before the series can be considered fully cross-platform. The tone suggests openness to alternatives but defends the current design's tradeoffs.
