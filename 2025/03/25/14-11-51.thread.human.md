This thread reports a bug in gitk's handling of PATH resolution when searching for the git executable. The issue occurs when a non-executable file named 'git' exists in an early PATH directory - gitk incorrectly tries to execute it rather than continuing to search for a properly executable git binary. This leads to a misleading "Cannot find a git repository here" error.

The reporter describes a concrete development scenario where they maintain wrapper scripts in ~/overlay that sometimes get left non-executable after debugging sessions. While shells and other tools properly skip non-executable files in PATH, gitk currently only checks for file existence before attempting execution. The fix would involve modifying gitk's PATH search (specifically line 82 of the main script) to verify executability with `[ -x $file ]` before running any found git binary. This appears to be a straightforward bug with clear reproduction steps and a legitimate use case.
