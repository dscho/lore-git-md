This is a discussion about Windows compatibility issues in the Rust crate packaging solution for libgit integration, specifically regarding the symlink approach in patch 2/5 of the series.

Junio Hamano responds to Josh Steadmon's exploration of alternatives to the problematic git-src symlink approach on Windows. The thread has established that while the current solution meets the dual requirements of enabling cargo package functionality while keeping Rust configuration out of the main Git tree, it fails on Windows due to symlink limitations.

Hamano expresses openness to adding a root-level Cargo.toml file if it's analogous to other build configuration files like Makefile, rather than cluttering the root with numerous new files. He encourages Steadmon's plan to test the Cargo workspace approach, which might resolve the Windows issue while maintaining the project's cleanliness goals.

The email acknowledges Steadmon's proposed fallback options if workspaces don't work: (1) temporarily limiting to source builds only (Steadmon's preferred interim solution) or (2) moving crates to separate repositories with Git as a submodule (following the zlib-sys pattern). Hamano sees option #1 as a way to build momentum and expertise in the Rust integration effort before considering more disruptive changes.

Key technical points mentioned include:
- The workspace approach might maintain source access requirements
- Comparison to other -sys crates' solutions
- The temporary nature of option #1 as a stepping stone
- The potential for future transition to option #2 if Rust integration gains traction

The discussion shows the project maintaining its technical requirements while pragmatically addressing platform limitations, with leadership open to different architectural approaches as the Rust integration effort evolves.
