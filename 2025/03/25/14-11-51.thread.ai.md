Gitk PATH resolution bug report - thread summary:

A bug report identifies incorrect PATH resolution behavior in gitk where it attempts to execute non-executable files named 'git' found in PATH directories, rather than properly checking for executable permissions first. The issue manifests when a non-executable file named 'git' exists in an early PATH directory (e.g., ~/overlay debugging wrappers), causing gitk to fail with "Cannot find a git repository here" rather than continuing PATH search for a valid executable.

The problem is isolated to line 82 of gitk's main script where the current existence check (`[ -f $file ]`) needs enhancement to verify executability (`[ -x $file ]`). This represents a clear bug with straightforward reproduction steps where gitk's behavior diverges from standard PATH resolution conventions followed by shells and `which`. The reporter's use case of maintaining occasionally non-executable wrapper scripts in a personal overlay directory demonstrates legitimate workflow impact.

The fix has been proposed yet, but the technical solution appears uncontroversial - modifying the PATH search to include an executable permission check before attempting execution. This would align gitk's behavior with standard PATH resolution expectations while maintaining compatibility with existing valid configurations. The change would specifically affect gitk's git binary location logic without broader implications for other Git components.
