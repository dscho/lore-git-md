Bugfix for gitk's PATH resolution behavior. This patch reports an issue where gitk incorrectly attempts to execute non-executable files named 'git' found in PATH directories, rather than properly checking for executable permissions before attempting execution.

The core problem occurs when a non-executable file named 'git' exists in an early PATH directory. While shells and `which` properly skip non-executable files, gitk currently only checks for file existence (via `[ -f $file ]`) before trying to execute it. This leads to a misleading "Cannot find a git repository here" error when the non-executable file exists, rather than continuing to search PATH for a valid git executable.

The reporter provides a concrete debugging scenario where they maintain wrapper scripts in a personal overlay directory (~/overlay) that sometimes get left non-executable after debugging sessions. The current behavior makes gitk fail in this common development workflow where other tools work as expected.

The issue is localized to line 82 of gitk's main script, where the executable check needs to be enhanced. This appears to be a straightforward bug with clear reproduction steps and a legitimate use case, suggesting the fix would be non-controversial. The patch would need to modify the PATH search to verify executability (likely via `[ -x $file ]`) before attempting to run any found git binary.
