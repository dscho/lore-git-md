Security-focused feature proposal for git-shell command overrides.

This v2 patch from Ayman Bagabas continues the discussion about allowing git-shell built-in command overrides via scripts in git-shell-commands. The implementation modifies shell.c to first check for override scripts (using make_cmd() and access()) before falling back to built-in command execution. The key changes from v1 are: removal of RFC status, tightened commit message wording, and dropped CC list.

The technical approach remains: when git-shell processes a command, it now first looks for a same-named executable in git-shell-commands before using the built-in implementation. This enables use cases like access-controlled receive-pack wrappers. The patch moves cd_to_homedir() earlier to ensure proper path resolution for override scripts.

Security considerations dominate the ongoing discussion, particularly whether intercepting built-ins (vs adding new commands via existing git-shell-commands) introduces new attack vectors. The patch maintains the same access patterns as current git-shell-commands functionality, suggesting equivalent security properties. However, the thread has raised questions about whether built-in command interception specifically could enable novel exploits in git-shell's constrained environment.

The implementation appears straightforward with clear fallback behavior, though the security implications remain under active discussion. The narrowed scope to git-shell-specific behavior has resolved earlier architectural concerns, leaving focused security analysis as the primary remaining consideration.
