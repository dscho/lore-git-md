Feature/bugfix: Adding rename detection disable support to merge-ort to match merge-recursive behavior.

This second patch in the 3-part series enables merge-ort to respect the `no-renames` option and `merge.renames` configuration, bringing it to parity with merge-recursive's capabilities. The author explains they initially omitted this feature assuming performance was the only reason users disabled rename detection, but now acknowledges behavioral use cases exist after years of real-world experience with merge-ort's optimized rename detection.

The changes are straightforward: a new early exit path in `detect_and_process_renames()` when detection is disabled, plus documentation updates. The doc changes both add the option to merge-ort's supported flags and remove it from the "ignored by ort" list for recursive strategy, reducing that list from three to two options. The patch maintains clean separation from the other changes in the series while contributing to the overall goal of making merge-ort a drop-in replacement for merge-recursive.

Key technical details for future reference: the implementation checks `opt->detect_renames == 0` to skip rename processing, sets `redo_after_renames` and `cached_pairs_valid_side` flags to 0 in this case, and preserves all existing documentation cross-references to git-diff's similar option. The change affects core merge machinery behavior when users explicitly disable rename detection via config or command line.
