This is a discussion about Git's error handling patterns, specifically around assertions and BUG() macros, continuing from a merge-ort bugfix thread. Junio Hamano responds to Elijah Newren's proposal for a BUG_ON() macro, highlighting their philosophical differences on assertion ergonomics.

The core debate centers on whether assertions should include explanatory messages. Junio strongly favors explicit BUG() calls with descriptive messages, arguing they help future developers understand the intent behind checks. He provides a concrete example where a message would reveal a potential off-by-one error in array bounds checking. While he acknowledges the safety improvements of removing NDEBUG from BUG_ON(), he maintains that the inability to include explanations is a significant drawback.

Junio does offer a compromise position: he'd accept a BUG_ON() variant that includes both a condition and message parameter (BUG_ON(condition, message)), which would prevent misuse while preserving explanatory power. The discussion remains collegial but underscores a fundamental tension between concise assertion syntax and maintainer-friendly verbosity in error handling.

This exchange represents high-level maintainer discussion about project conventions rather than immediate code changes. The original merge-ort fix appears settled, while this standards debate may influence future error handling patterns across Git's codebase.
