This is a follow-up discussion in the promisor-remote NULL dereference bugfix thread, focusing on architectural questions about URL handling behavior. Christian Couder responds to Junio Hamano's review of v3, addressing several key concerns about the promisor remote implementation.

The discussion centers on whether promisor remotes should follow standard Git remote conventions (using the remote name as a fallback when no URL is configured) or require different behavior specific to promisor use cases. Christian argues for maintaining consistency with standard remote behavior, particularly for cases where client, server and promisor remote share a filesystem and could rely solely on remote names without URLs.

Key technical points in the response:
- Defends the r->name fallback approach by describing a valid use case where all components share a filesystem
- Explains that remote names are already exposed in the "name=" field, so URL fallback doesn't expose new information
- Agrees to remove an unnecessary comment about empty URLs
- Changes URL comparisons to use strcasecmp() for consistency with remote_nick_find()
- Maintains that empty URL warnings provide better diagnostics than silently failing

The exchange reveals deeper questions about promisor remote architecture that may need future consideration:
1. Whether promisor remotes should diverge from standard remote conventions
2. The appropriateness of name fallback when names may be meaningless to remote servers
3. The granularity and timing of URL validation warnings

While the immediate NULL dereference fix is sound and ready for inclusion, this discussion points to potential follow-up work needed to align promisor remote behavior with its specific requirements versus general remote conventions. The thread shows careful consideration of both immediate safety fixes and longer-term API design questions.
