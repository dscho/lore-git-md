This thread addresses a Windows-specific race condition affecting Git's file handling, particularly in the reftable compaction sequence. The initial two-patch series from Patrick Steinhardt proposed: (1) adding `O_CLOEXEC` support in MinGW file operations, which Junio approved, and (2) changing error code translation from `EACCES` to `EEXIST` for files marked for deletion - a fix that resolved test flakiness but raised concerns.

Johannes Schindelin (Git for Windows maintainer) has now weighed in with important platform expertise. While confirming the patch correctly handles the reftable case, he warns that Windows' `ERROR_ACCESS_DENIED` can indicate either pending deletion (where `EEXIST` is appropriate) or genuine permission issues (where `EACCES` should remain). The current implementation would mask real access problems by always reporting `EEXIST`. He suggests either handling the distinction at a higher level or implementing a back-off mechanism.

The discussion now centers on finding a solution that maintains the race condition fix while properly distinguishing between these cases. Junio had previously requested exactly this kind of Windows expert review, and the thread awaits either a revised approach from Patrick or consensus on how to proceed. The first patch (O_CLOEXEC support) remains uncontroversial and could potentially be applied separately.
