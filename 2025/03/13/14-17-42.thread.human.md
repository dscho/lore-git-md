This thread addresses a Windows-specific race condition in Git's lockfile handling that causes flaky test failures, particularly visible in the reftable tests. The discussion has evolved through several approaches to solve the core issue where Windows' `_wopen()` with `O_CREAT|O_EXCL` returns `EACCES` when a file is marked for deletion, requiring careful distinction between genuine permission errors and pending deletion cases.

The initial v2 patch series contained two parts: an uncontroversial Meson build fix and a more contentious solution using Windows' undocumented `RtlGetLastNtStatus()` API for precise error detection. Johannes Schindelin (Git for Windows maintainer) strongly objected to using undocumented APIs, prompting Patrick Steinhardt (the patch author) to propose an alternative SQLite-inspired polling approach that would retry operations on certain Windows error codes with timed delays.

The NtStatus approach offers technical precision by directly detecting `STATUS_DELETE_PENDING` cases, while the polling alternative would handle a broader set of error conditions (ERROR_ACCESS_DENIED, ERROR_SHARING_VIOLATION etc.) through retries with 25ms delays. Patrick acknowledges the maintainability concerns but argues against Johannes' simpler suggestion to treat all `EACCES` as `EEXIST`, as this could mask genuine permission problems.

The discussion now hinges on choosing between technical precision (NtStatus) and long-term maintainability (polling), with Patrick indicating willingness to implement the polling solution if preferred. The uncontroversial build system fixes could potentially proceed separately while this architectural decision is resolved. The outcome will influence not just reftable but Git's general lockfile handling on Windows, making this an important precedent for future Windows compatibility work.
