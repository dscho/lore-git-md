The thread has reached a resolution on how to handle a tricky Windows-specific race condition in Git's lockfile subsystem. The issue stems from Windows' behavior where file operations with `O_CREAT|O_EXCL` can return `EACCESS` when a file is marked for deletion, causing flaky test failures. After extensive technical debate between Patrick Steinhardt and Johannes Schindelin (Git's Windows expert), three approaches were considered: using an undocumented Windows API for precise error detection, broadly treating all `EACCES` errors as `EEXIST`, or implementing SQLite-style polling with retries.

Johannes has now reluctantly accepted Patrick's preferred solution using the undocumented `RtlGetLastNtStatus()` API to detect `STATUS_DELETE_PENDING`, despite his initial objections about relying on undocumented Windows internals. This approach provides the most precise detection of the race condition. Johannes was convinced after evaluating the alternatives - the broad `EACCES` handling was too imprecise, and the polling solution would be less reliable. He also addressed his own concern about potential initialization timing issues with the NTSTATUS value.

The SQLite-style polling approach (with 25ms delays and 10 retries) will remain as a fallback option if the NtStatus solution proves problematic in practice. The fix will be applied to Git's general lockfile handling, not just the reftable subsystem where the issue was initially observed. With this consensus between the main technical stakeholders, the patch series can now move forward with the NtStatus implementation unless new concerns emerge about the Windows API usage.
