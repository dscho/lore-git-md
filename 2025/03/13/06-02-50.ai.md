Security-focused discussion about remote object info format string validation.

This email from Jeff King continues the security-focused discussion about format string validation in the remote object info implementation. The conversation follows up on a segfault vulnerability discovered when unsupported placeholders (like `%(objecttype)`) were used in the format string for remote object queries. Peijian Ju had proposed iterating through the format string to detect unsupported placeholders, but Jeff suggests two alternative approaches that might be more maintainable: either checking for disallowed pointers after the mark_query pass, or implementing an allow-list check in the atom expansion functions.

Jeff also raises an interesting design question about whether the system should gracefully handle unsupported placeholders by returning empty values rather than erroring out, particularly since the protocol might allow intermixing remote and local object requests. This touches on both security aspects (preventing crashes from malformed input) and usability considerations (how strict the validation should be). The discussion builds on the extensive security hardening work already done in previous iterations of this series, now focusing on final refinements to the client-side parsing logic.
