Bugfix for a Windows-specific race condition in file locking, part 2 of a 2-patch series addressing flaky test t0610. This patch fixes a MinGW quirk where `_wopen()` with `O_CREAT|O_EXCL` incorrectly returns `EACCESS` when another process has marked the file for deletion via `DeleteFileW()`, rather than the expected `EEXIST`.

The issue manifests in reftable operations during compaction, where multiple processes race to update the "tables.list" lockfile. Windows' `CreateFileW()` API (used internally by `_wopen`) returns `ERROR_ACCESS_DENIED` for files pending deletion, causing the lockfile subsystem to bail out rather than retrying. The patch maps this error to `EEXIST`, allowing proper retry behavior.

Patrick Steinhardt reports this fixes the previously flaky t0610 test, which failed 20-30% of runs on Windows CI systems. While theoretically affecting all lockfile operations, the author notes this race is particularly likely in reftable compaction due to its specific locking pattern. The change is minimal (13 lines added to `mingw.c`) and maintains POSIX semantics.

This completes the series' goal of fixing Windows test flakiness, with the first patch having addressed a separate `O_CLOEXEC` flag handling issue. Together they provide robust file handling for Git's Windows port.
