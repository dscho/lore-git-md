Windows platform compatibility fix for race condition in file handling, part 2 of 2.

Junio C Hamano provides a non-expert review of Patrick Steinhardt's second patch in this series, which addresses a MinGW-specific race condition where `_wopen()` with `O_CREAT|O_EXCL` incorrectly returns `EACCESS` when another process has marked the file for deletion via `DeleteFileW()`. The patch changes this to return `EEXIST` instead, which better matches the expected POSIX behavior and fixes flaky tests in the reftable lockfile handling.

The review focuses on the technical correctness of the error code mapping. While Junio acknowledges the explanation in the added comment about how Windows' `CreateFile()` with `CREATE_NEW` can return `ERROR_ACCESS_DENIED` during pending deletions, he expresses uncertainty about whether this error code could ever indicate other conditions. He specifically calls for Windows API experts to verify that `ERROR_ACCESS_DENIED` in this context always and only indicates an existing-but-pending-deletion file case, rather than potentially masking other access-related issues.

The patch itself is small (13 lines changed) and targets `compat/mingw.c`, modifying the error translation while maintaining existing behavior for other cases. It includes detailed comments explaining the Windows API behavior and lockfile implications. While the first patch in the series (handling `O_CLOEXEC` flags) has already received Junio's approval as sensible, this second patch's more subtle behavior change still needs expert validation despite the author's testing showing it resolves the reftable test flakiness.
