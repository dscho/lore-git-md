This is a follow-up in the ongoing discussion about reproducible Git bundle generation, focusing on security implications and practical approaches.

Simon Josefsson responds to Kyle Lippincott's technical analysis, confirming that the reproducibility issues occur during `git clone` operations rather than bundle creation itself. He notes that while identical bundles can be created within the same clone, different clones produce different results despite various attempted workarounds (dumb protocol, rsync).

The email clarifies the security motivation behind this effort - enabling third-party verification of bundle contents as part of software supply chain security, drawing parallels to existing reproducible build efforts for tarballs and gzip. Simon acknowledges that environment-specific reproducibility (same toolchain/versions) would already be an improvement over the current situation where bundles are completely irreproducible.

This moves the discussion forward by:
1. Confirming the clone operation as the source of non-determinism
2. Explicitly stating the security use case
3. Setting realistic expectations about environment requirements for reproducibility
4. Positioning this as part of broader software supply chain security efforts

The email doesn't introduce new technical solutions but helps ground the technical discussion in concrete security requirements, suggesting the thread may now shift toward evaluating solutions that balance reproducibility with practical constraints.
