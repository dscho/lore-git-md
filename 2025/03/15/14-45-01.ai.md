This is a bug report about path-restricted log behavior with subtree merges. Oswald Buddenhagen describes encountering confusing output when running `git log .` in the git-gui subdirectory, which primarily shows merge commits without the expected history of changes being merged. The report suggests this relates to Git's limited handling of subtree merges and draws a parallel to the known limitation where `--follow` only works for single files.

The issue appears when examining repositories that use subtree merge strategies, where the path-filtered log fails to show the actual commits that introduced changes to the specified path, instead showing only the merge commits that brought those changes into the current branch. This makes it difficult to trace the history of changes in subprojects or subdirectories managed via subtree merging.

The email notes this behavior is particularly problematic in git-gui's history and mentions the display in gitk exacerbates the confusion. A comparison is made to the `--follow` option's single-file limitation, suggesting these might be related underlying limitations in Git's path-filtering logic.

This appears to be a genuine usability issue for developers working with subtree-merged codebases, though the report doesn't propose a specific solution. The connection to `--follow`'s limitations hints that fixing this might require non-trivial changes to Git's revision walking logic for path-filtered operations. The report serves primarily to document the issue rather than propose a patch.
