This thread examines a subtle but important limitation in Git's path-filtered history viewing, where `git log .` in a subdirectory (like git-gui/) shows primarily merge commits rather than the expected file history. Oswald Buddenhagen originally reported this behavior, prompting deep technical analysis from Johannes Schindelin and Junio Hamano about fundamental constraints in Git's `tree-diff.c` and revision walking machinery, particularly around handling directory-level renames in subtree-merged histories.

The core issue stems from how Git tracks path evolution across merges - the current single-path queue access can't properly handle cases where files are moved to different locations in parallel histories that later merge. Junio Hamano identified this as an architectural limitation requiring changes to how Git tracks multiple paths during revision walking. While no solution has been implemented yet, the discussion has clarified that directory-following behavior needs to be part of a broader rethinking of path-tracking in merge scenarios.

Jeff King's recent contribution provides immediate practical help, explaining why path filtering fails (the original commits modify paths like "git-gui.sh" while merges update "git-gui/git-gui.sh") and offering a workaround: explicitly listing both path variants with `git log -- git-gui/ git-gui.sh`. This doesn't solve the underlying technical challenge but gives users a way to see the complete history until more sophisticated path-tracking is implemented. The thread remains open for further discussion about core architectural changes needed to properly handle such cases.
