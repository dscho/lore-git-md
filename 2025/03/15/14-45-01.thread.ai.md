Junio Hamano expands on this analysis, agreeing the current single-path queue access (`q->queue[0]`) is fundamentally limited for merge-heavy histories. He makes three critical observations: (1) `--follow-renames` breaks down when paths are renamed differently in parallel histories that later merge, (2) a proper solution requires per-ancestor path tracking during revision walking, and (3) directory-level rename following would emerge naturally from a more general solution for tracking multiple paths. Hamano emphasizes these are architectural limitations requiring core revision walking changes, suggesting the solution path should first address single-path following in merge scenarios before generalizing to multiple paths.

The discussion now clearly frames directory-following as part of a larger path-tracking challenge in Git's revision walking subsystem. Key technical hurdles remain: replacing single-path queue access with ancestry-aware multi-path handling, restructuring rename-following logic for merge cases, and addressing performance implications. The silent failure mode for directory arguments to `--follow` remains an acknowledged UX issue, though any fix would require substantial changes to path-filtering and rename-tracking subsystems. No concrete implementation has been proposed yet, but the analysis suggests the problem touches core architecture decisions around how Git tracks path evolution across complex histories.
