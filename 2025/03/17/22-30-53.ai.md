This is a follow-up discussion on the assert() safety series, specifically about documentation and developer awareness of the new CI checks.

Taylor Blau suggests adding guidance in Documentation/CodingGuidelines about the new assert() restrictions and CI checks. The concern is that developers might write assertions with side effects that pass local testing but fail in CI, since the check-unsafe-assertions.sh script isn't run by default in 'make test'. The suggestion is to document that all assert() must be side-effect-free and point to the CI check script for verification.

However, Taylor acknowledges this might open a larger discussion about when to use assert() versus BUG_IF_NOT() that could be counterproductive. The email doesn't propose specific wording, just raises the question of whether documentation would help developers understand the new expectations. The thread context shows this is a minor follow-up to an otherwise complete series that has already addressed all technical and licensing concerns, with the core changes (BUG_IF_NOT() introduction and CI checks) already reviewed and approved.
