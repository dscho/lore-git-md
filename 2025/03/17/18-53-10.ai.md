Performance issue report about slow `git add .` operations in large repositories. The email describes a significant performance gap between `git add .` (1.5-2s) and `git status` (~300ms) in a repository with ~27k directories and ~78k paths, despite having fsmonitor and untracked cache enabled. The author notes that nearly all time is spent in `read_directo` operations, and has found workarounds using targeted adds or piping `git status` output to `git add` that perform much better (<500ms). The core question is why the built-in `git add .` operation doesn't leverage the same optimizations that make `git status` fast, given they're working with similar directory scanning requirements. The report comes from a MacOS environment using Git 2.49.0, suggesting this may be a platform-specific or version-specific performance characteristic worth investigating. The author's workaround demonstrates the potential for optimization, though the email doesn't propose any specific code changes - it appears primarily aimed at understanding and diagnosing the performance discrepancy.
