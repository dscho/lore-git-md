Thread summary:

Performance investigation into `git add .` slowness compared to `git status` in large repositories (~27k dirs, ~78k paths) on MacOS with Git 2.49.0. Initial observation showed `git status` completes in ~300ms (with fsmonitor and untracked cache enabled) while `git add .` takes 1.5-2s with most time spent in `read_directo` operations. Brian M. Carlson clarifies the technical distinction: `git add .` must scan the entire working tree for both modified tracked files and new untracked files, while `git add -u` (like `git status`) only examines tracked files already in the index. The untracked cache optimization used by `git status` isn't applicable to `git add .` with pathspec matching due to complexity constraints. The workaround of piping `git status` to `git add` effectively mimics `git add -u` behavior by only processing tracked files. Carlson frames this as an intentional design tradeoff where the convenience of `git add .` comes with inherent performance costs in large repositories, recommending `git add -u` when new file addition isn't needed. The thread establishes this is not a bug but rather an expected consequence of different command semantics, with no immediate plans to bridge the optimization gap between these related operations. Platform/version details remain relevant context for the behavior analysis.
