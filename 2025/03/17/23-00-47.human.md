This is a performance discussion about the different behaviors of `git add` variants in large repositories. Brian M. Carlson explains why `git add .` is inherently slower than `git add -u` or piping `git status` output to `git add` - it must scan the entire working tree for new untracked files, while the other commands only examine tracked files. 

The key technical reason is that the untracked cache optimization (which makes `git status` fast) isn't used when a pathspec like `.` is explicitly given, as the general case would be too complex to handle. The response clarifies that this isn't a bug but rather a fundamental difference in what each command is asked to do.

Carlson suggests getting accustomed to `git add -u` for better performance, reserving `git add .` only when new file addition is needed. The explanation is thorough and technically sound, though it doesn't propose any changes to the current behavior - just a clear rationale for why things work as they do. This seems like a definitive answer to the original performance question.
