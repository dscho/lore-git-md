This thread investigates why `git add .` runs significantly slower than `git status` in large repositories (1.5-2s vs ~300ms) on MacOS with Git 2.49.0. The original observation noted that while both commands scan the directory structure, `git add .` spends nearly all its time in `read_directo` operations without benefiting from the same optimizations that make `git status` fast (fsmonitor and untracked cache).

Brian M. Carlson has clarified the technical reasons behind this performance gap: `git add .` must scan the entire working tree to handle both modified tracked files and new untracked files, while `git status` and `git add -u` can optimize their scans by focusing only on tracked files already in the index. The untracked cache optimization used by `git status` isn't applicable to `git add .` when using pathspecs (like `.`) because general pathspec matching would make the optimization too complex.

The thread has identified workarounds - using targeted adds or piping `git status` output to `git add` can achieve sub-500ms performance. Carlson recommends `git add -u` as a faster alternative when users don't need to add new files. While this explains the current behavior as an intentional design tradeoff, the core question remains whether some optimizations could be shared between these related operations without compromising their different semantic requirements.
