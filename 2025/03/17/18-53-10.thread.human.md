The thread examines why `git add .` runs significantly slower than `git status` in large repositories, particularly on MacOS. Brian M. Carlson initially explained this is expected behavior: `git add .` must scan the entire working tree for both modified and new files, while `git status` (like `git add -u`) only checks tracked files and can use the untracked cache optimization. This makes `git status` about 5-6x faster in the reported case (~300ms vs 1.5-2s).

Yissachar Radcliffe has now challenged some technical details of that explanation. While agreeing that complex pathspec cases are hard to optimize, they argue the common `git add .` pattern could be special-cased to bridge much of the performance gap. The discussion has shifted from "this is working as designed" to considering whether targeted optimizations might be worthwhile for this frequently used command. The core tradeoff remains - convenience versus performance - but there's new interest in exploring whether the current implementation strikes the right balance.
