This thread examines why `git add .` runs significantly slower than `git status` in large repositories, particularly on MacOS. The performance gap stems from fundamental differences in what these commands must scan: `git status` (with fsmonitor) can leverage caches to check ~78k paths in ~300ms, while `git add .` requires a full working tree scan taking 1.5-2s since it must discover both modified tracked files and new untracked files.

The discussion has revealed a technical-cultural divide. Brian M. Carlson explains that Git's internals make optimizing `git add .` difficult due to pathspec matching constraints, and notes that core Git developers rarely use this command because it risks accidentally staging unwanted files. Yissachar Radcliffe counters that the performance gap seems unnecessarily large for a common user workflow, suggesting special-case optimizations might be possible. While Carlson acknowledges the technical possibility of such optimizations in `dir.c`, he makes no promises about acceptance, highlighting how workflow preferences influence which optimizations get attention. The thread remains open with unresolved questions about whether this performance difference represents a necessary tradeoff or an addressable oversight.
