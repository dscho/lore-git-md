Performance clarification on `git add` behavior differences in large repositories.

This email from Brian M. Carlson provides technical context about why `git add .` performs differently than `git add -u` or `git status` in large repositories. The key distinction is that `git add .` must scan the entire working tree to find both modified tracked files and new untracked files, while `git add -u` only examines tracked files already in the index. The untracked cache optimization used by `git status` isn't applicable to `git add .` when a pathspec is specified (like the `.` directory) because the general case of pathspec matching would make the optimization too complex.

The email explains that piping `git status` to `git add` effectively works like `git add -u` since status only lists tracked files. While acknowledging the convenience of `git add .`, Carlson recommends using `git add -u` as a faster alternative when new file addition isn't needed. The response provides clear technical rationale for the performance characteristics but doesn't propose any code changes to address the underlying optimization gap between the commands. This appears to be an intentional design tradeoff rather than a bug, with the performance difference being an expected consequence of the different semantic requirements of each command variant.
