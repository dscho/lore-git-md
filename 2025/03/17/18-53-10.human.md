Performance issue report about slow `git add .` in large repositories.

Yissachar Radcliffe reports significant performance issues with `git add .` in a large repository, where the operation takes 1.5-2 seconds despite having core.fsmonitor and core.untrackedCache enabled. The slowdown appears to come from directory traversal, with the command visiting nearly 27,000 directories and 78,000 paths. 

Interestingly, `git status` runs much faster (~300ms) in the same repository, and workarounds like `git add <specific paths>` or `git add -u .` show better. The reporter has even created a script that pipes `git status` output to `git add` which runs in under 500ms, demonstrating that the built-in `git add .` behavior seems unnecessarily slow.

The report suggests there may be optimization opportunities in how `git add .` handles directory traversal compared to other similar commands. The issue appears reproducible on Git 2.49.0 running on macOS 15.3. This could be worth investigating for performance-minded contributors, though more data about the repository characteristics and possible benchmarking would help assess the scope of improvement.
