Refactoring follow-up in the protocol v2 fetch series. Taylor Blau responds to Jeff King's earlier patch (5/9) that refactored `refspecs_to_ref_prefixes()` in `refspec.c`, addressing the confusing naming of the `rs->fetch` field which currently uses `REFSPEC_FETCH`/`REFSPEC_PUSH` enum values despite being essentially a boolean.

Taylor proposes two alternative cleanups: either (1) rename the field to `type` and keep the enum values while adding a switch/case structure with a BUG() catch-all, or (2) keep the field name as `fetch` but simplify to plain boolean 0/1 values since the field's meaning is fundamentally binary. He leans toward the second approach as cleaner, noting the current enum values don't add meaningful type safety when the field name already conveys the boolean nature.

This is a minor but thoughtful code quality improvement to the already-reviewed refactoring work, maintaining the series' high standard of careful attention to API clarity. The discussion shows good technical judgment about when enums provide value versus when they might overcomplicate simple binary states.
