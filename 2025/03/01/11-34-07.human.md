This is a bugfix for a memory leak in the reftable infrastructure, continuing the thread about memory management issues in the reftable code. H Z originally reported what they thought was a test-only leak, but René Scharfe has identified a more significant production code leak in `reftable_reader_new()` where the 'name' field allocation would be lost if initialization failed mid-process.

The patch takes a minimal approach to fixing the issue by adding cleanup of the 'name' field in error paths while maintaining the existing allocation timing. It's a straightforward one-line addition that properly frees the allocated memory when `block_source_read_block()` or `parse_footer()` fail. The fix appears well-scoped and addresses the core issue without introducing additional complexity.

Interestingly, the thread also revealed a documentation inconsistency - the header file mentions a non-existent `reftable_reader_destroy()` function, though this isn't addressed in the current patch. The original test case that sparked the investigation turns out to no longer exhibit the leak due to prior refactoring.
