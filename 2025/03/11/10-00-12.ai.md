This is a proposal for a potentially significant refactoring of Git's timestamp handling, changing `timestamp_t` from `uintmax_t` to `intmax_t` to better align with platform `time_t` types and avoid signed/unsigned comparison warnings.

The email notes that while Git currently uses unsigned timestamps_t, most platforms (Linux/glibc, Windows/MSVC, and likely macOS/FreeBSD) use signed time_t, which can cause compiler warnings during comparisons. The author acknowledges there's no current need for pre-1970 dates in Git, but wants to eliminate the type mismatch. They correctly identify this would be a substantial change due to widespread use of timestamp_t throughout the codebase.

Key technical points for future reference: the change would affect all timestamp handling code (originally introduced in commits dddbad728c and 28f4aee3fb), potentially touching many files that deal with time operations. The proposal doesn't mention any current bugs caused by the unsigned behavior, focusing instead on compiler warnings and type consistency. The author is wisely seeking consensus before undertaking what would be a large-scale change with subtle implications for time handling throughout the codebase.

This seems likely to spark discussion about whether the change is worth the churn, whether there are any hidden assumptions about timestamp values in the codebase, and whether the compiler warnings are significant enough to warrant the effort. The platform compatibility angle (matching system time_t) is a strong argument, but the scale of changes needed may give reviewers pause.
