This is a response to a bug report about git-rebase's behavior with reverted and reapplied commits. Elijah Newren clarifies that the current behavior is working as documented - when a commit exists upstream with the same changes, it is correctly omitted during rebase. He points out some inaccuracies in the reporter's test case, noting that the commits on different branches aren't actually identical if there's any time lag between their creation.

Newren suggests a more precise rebase command (`git rebase --onto main br~1 br`) and explains that the `--reapply-cherry-picks` option would be the appropriate solution here, contrary to the reporter's claim that it creates empty commits. He notes this option only creates empty commits in specific cases (when the original commit was empty or results in no changes), which doesn't apply to this scenario.

The response maintains that the current behavior is correct and documented, while offering guidance on how to properly handle this edge case. This appears to be a case of expected behavior being misunderstood rather than an actual bug, though the discussion highlights some subtle aspects of rebase's commit selection logic.
