Bugfix follow-up discussing strvec API design implications for the promisor-remote NULL URL handling. This email from Christian Couder responds to Junio Hamano's review questions about whether the strvec API itself should enforce non-NULL values, rather than just fixing the immediate promisor-remote segfault.

The discussion explores three potential API-level solutions: making xstrdup() BUG on NULL, having xstrdup() return NULL for NULL input, or aligning strvec_push() behavior with strvec_push_nodup() to accept NULLs. Christian argues these are separate issues that can wait until after the 2.49.0 release, with the current patch focused only on the immediate promisor-remote fix.

Christian clarifies the promisor-remote behavior when URLs are missing: the 'names' and 'urls' strvecs are only used for server advertisement validation when 'promisor.acceptfromserver' is set to KnownName/KnownUrl. He explains the logic for remote rejection in each mode and notes the patch doesn't change actual fetching behavior - clients still can't use server-provided URLs even when accepted.

The email also addresses Junio's concern about ignoring empty URLs, explaining that for KnownName mode it's simpler to ignore URLs entirely, and that future modes might use advertised URLs directly. Christian notes he's added warnings in v2 to help diagnose rejections due to missing URLs. He confirms fixing the redundant NULL check Junio pointed out in the URL encoding logic.

Key technical details for future reference: the discussion centers on strvec_push()/xstrdup() NULL handling semantics, promisor.acceptfromserver validation modes (KnownName vs KnownUrl), and the distinction between advertisement validation versus actual URL usage. The patch maintains backward compatibility while adding warnings, with test coverage for missing URL scenarios.
