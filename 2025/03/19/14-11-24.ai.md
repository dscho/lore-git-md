This is a feature proposal for `git bisect` functionality. The email suggests two related but distinct enhancements to the bisect workflow:

1. **Worktree bisecting**: The primary proposal is for `git bisect` to support switching between multiple worktrees during the bisection process. This would allow keeping both "good" and "bad" states available simultaneously for detailed comparison and forensic analysis. The author suggests this could enable advanced debugging tools like `rr` to perform side-by-side record/replay comparisons.

2. **Manual hunch testing**: A secondary suggestion introduces a hypothetical `git bisect try` command that would let users test specific commits outside the normal bisection algorithm, useful when developers have hunches about likely problematic commits. The proposed syntax would mark commits as good/bad after testing.

The proposal is currently at the RFC stage without implementation details. The motivation focuses on enabling better debugging workflows by maintaining parallel testable states during bisection. The worktree aspect seems particularly promising for complex debugging scenarios where comparing states is valuable, while the "try" feature might be more controversial as it deviates from bisect's systematic approach.

Key technical points for future reference:
- Proposed command: `git bisect worktrees ../wk-A:../wk-B`
- Hypothetical command: `git bisect try <commit> [good|bad]`
- Potential integration with `rr` debugger for A/B comparison
- Would require worktree management during bisect steps
