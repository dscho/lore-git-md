This is part of the ongoing bugfix discussion about `git blame` porcelain output for ignored/unblamable lines. Karthik Nayak responds to Junio Hamano's critique of their initial approach, which proposed modifying the SHA-1 line prefixes in porcelain mode. Hamano had rejected this as too disruptive to existing parsers that rely on the strict "^[0-9a-f]{40}" format as a delimiter.

The email shows Karthik acknowledging the backward compatibility concerns and reconsidering their position. They note that users explicitly setting `blame.markIgnoredLines` or `blame.markUnblamableLines` would reasonably expect the documented '?'/'*' markers, but agree to explore alternative implementations that don't break existing porcelain parsers.

Key technical context carried forward:
- The porcelain format's strict parsing rules for commit object name lines
- Existing parsers' expectation of clean SHA-1 delimiters
- The tension between documented behavior and backward compatibility
- Metadata emission patterns in porcelain vs line-porcelain modes

This moves the thread toward resolution by showing the original proposer accepting the interface constraints. The next step would be to see an alternative implementation that adds the ignored/unblamable information through metadata lines rather than SHA-1 prefix modification, aligning with Patrick Steinhardt's earlier accepted approach. The discussion remains focused on implementation details rather than fundamental design questions.
