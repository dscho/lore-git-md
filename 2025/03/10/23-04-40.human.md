This is a technical clarification in the ongoing discussion about index lock behavior in Git commands.

Junio Hamano responds to Benjamin Woodruff's question about whether `git status`'s documentation is incorrect regarding background index refreshes. He explains the distinction between in-memory index updates (required for correctness) and writing to disk (a performance optimization that requires locking). The key points:

1. In-memory index refreshes are mandatory for command correctness, regardless of whether the result gets written to disk.
2. Disk writes are optional performance optimizations that help other processes avoid redundant refreshes.
3. The lock contention issue arises specifically from these optional disk writes, not from the core refresh operation.
4. The current locking protocol requires coordination between processes, which not all tools (like IDEs or build systems) properly implement.

This email doesn't introduce new patches but provides important technical context about why the current behavior exists and how it differs from what the documentation might imply. It reinforces that the core issue is about disk writes rather than refreshes themselves, which helps frame the ongoing discussion about `--no-optional-locks` behavior. The response maintains Junio's previously stated position while offering a more detailed technical explanation.
