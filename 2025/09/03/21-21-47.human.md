This is a follow-up discussion about the recently merged series on deprecating `git whatchanged`. Eric Sunshine raises an important point about interactive use cases that wasn't fully addressed in the original implementation. While the series provided good guidance for scripted usage (suggesting `git log --raw --no-merges`), Eric notes that many users rely on `git whatchanged` due to muscle memory and its mnemonic value, suggesting the deprecation message should also include advice for interactive users.

Kristoffer Haugsbakk proposes adding this guidance to the BreakingChanges documentation rather than expanding the runtime error message, concerned about overwhelming users with too much information. Eric counters with a suggestion for a concise alias recommendation that could be included in the deprecation message without being too lengthy.

The exchange highlights an ongoing tension in deprecation messaging - balancing thorough guidance with readability, particularly for different usage patterns. While the technical implementation is settled, this discussion shows there's still room to refine the user experience aspects of the deprecation process.
