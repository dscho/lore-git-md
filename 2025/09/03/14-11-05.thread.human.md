Here's a human-readable summary of the thread so far:

A bug report from elhmn highlights unexpected behavior in Git's reference transaction hooks. When updating an existing reference (like moving a branch pointer), the hook receives the transaction formatted as a CREATE operation with a zero old_oid, rather than the expected UPDATE format showing the reference's previous value. This occurs consistently across both the traditional file-based ref backend and the newer reftable backend.

The reporter provides a clear test case showing that when moving refs/heads/master from commit B to A, the hook sees "0000000... <A> refs/heads/master" instead of "<B> <A> refs/heads/master". Interestingly, Git's own test suite appears to expect this behavior, raising the question of whether this is an intentional design choice or a long-standing bug. The report is well-documented with reproduction steps and version information (Git 2.51.0 on Ubuntu 20.04.6 LTS), but leaves open the question of whether and how the behavior should be changed.
