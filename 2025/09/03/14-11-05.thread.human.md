This thread began with a report from elhmn about what appeared to be unexpected behavior in Git's reference transaction hook - when updating an existing ref, the hook was showing a zero old_oid (like a CREATE operation) rather than the ref's previous value. Initial investigation showed this behavior was consistent across both file and reftable backends and appeared to match the test suite's expectations, raising questions about whether this was intentional.

Jeff King has now clarified that this behavior is indeed correct and documented. The hook shows the old value that was *passed to the transaction*, not necessarily the ref's current state. When no old value is specified (as in a force update), the hook properly shows all zeros as documented in githooks(5). Jeff acknowledges this creates a limitation - hooks can't distinguish between creating a new ref and force-updating an existing one when no old value is provided - but explains that changing this established interface now would be difficult without breaking backwards compatibility.

The thread has effectively been resolved with this authoritative explanation confirming the behavior is intentional (if imperfect) rather than a bug. The discussion highlights a known design tradeoff in the hook interface that's unlikely to change given stability constraints.
