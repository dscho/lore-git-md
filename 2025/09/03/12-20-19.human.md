This is a follow-up discussion about the `split` subcommand in Patrick Steinhardt's `git-history` RFC series, addressing usability feedback from D. Ben Knoble. The email focuses on three key issues with the `split` implementation:

1. **Diff visibility**: Knoble reports not seeing the expected diff between old and new trees during the split operation, except when editing hunks. Steinhardt confirms this should work and asks for a reproducible case, acknowledging the complexity of the wt-status interfaces.

2. **Message options mismatch**: The error message references a `-F` option that isn't actually implemented (only `-m` exists currently). Steinhardt explains this was an intentional simplification for the initial implementation but agrees `-F` should be added eventually.

3. **Error recovery**: When users provide empty commit messages, the command aborts completely rather than letting them retry. Steinhardt recognizes this as a valid usability concern but notes the technical challenges involved with in-memory index handling, marking it as future work.

The exchange shows Steinhardt actively engaging with feedback while being transparent about current limitations. The discussion highlights the careful balance being struck in this RFC between introducing powerful history editing capabilities and maintaining robustness, with several interface refinements still needed around the interactive workflow.
