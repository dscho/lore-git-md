This appears to be a bug report regarding the reference transaction hook's behavior when updating existing refs. The author, elhmn, observes that the hook reports a CREATE action with a zero OID for the old value when updating an existing reference, rather than the expected UPDATE action showing the previous ref value.

The issue is reproducible with both the file and reftable backends, demonstrated through a clear test case where updating `refs/heads/master` shows `0000...` as the old OID instead of the actual previous value. The author notes this contradicts their expectation based on the documented CREATE/UPDATE format in the test suite, but acknowledges the test suite itself seems to expect this zero-OID behavior.

The report is well-structured with reproduction steps and references to existing test cases, though it leaves open whether this is intentional behavior or a bug. This could be important for anyone relying on the reference transaction hook for accurate ref change auditing.
