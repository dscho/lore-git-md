This is a clarification about reference transaction hook behavior, responding to a bug report about old_oid values in ref updates.

Jeff King explains that the observed behavior (showing zero OID for updates) is actually correct and documented. The hook shows the old value *passed to the transaction*, not necessarily the ref's current value. When no old value is specified (as in a force update), the hook shows all zeros per the documented behavior in githooks(5). 

The response notes this makes it impossible for hooks to distinguish between "create new ref" and "force update existing ref" cases when no old value is specified. While acknowledging this as a design shortcoming, Jeff explains why changing it now would be difficult - the interface is established and backwards-compatible solutions (like adding new signaling mechanisms) would be complex.

Key technical points:
- Confirms zero OID is expected when no old value is passed to the transaction
- References githooks(5) documentation of this behavior
- Explains the semantic limitation this creates for hooks
- Notes the stability constraints preventing interface changes

This effectively resolves the original question by confirming the behavior is intentional (if imperfect) rather than a bug. The response provides authoritative documentation references and explains the current behavior's rationale while acknowledging its limitations.
