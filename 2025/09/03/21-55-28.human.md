This is a follow-up discussion about the `split` subcommand in Patrick Steinhardt's `git-history` RFC series. D. Ben Knoble reports an issue where the expected diff between old and new trees isn't showing up during interactive splitting, despite Patrick confirming this should work. 

Ben provides a detailed reproduction case using the `split` command on a commit three steps back, trying both quick acceptance ("y,q") and manual editing ("e") of hunks. In both cases, no status information appears in the commit message template, and the second commit gets created automatically without showing the diff changes. 

Patrick had acknowledged the wt-status interfaces are complex and requested a reproducer, which Ben has now provided along with his build method (using DEVELOPER=1 mode). The exchange suggests there may be bugs in how the status collection interacts with the split operation's workflow. 

The discussion continues the thread's pattern of thorough interface review, with Ben persistently testing edge cases and Patrick responsive to feedback. This particular issue appears to affect the core user experience of seeing what changes will be split between commits.
