This is a follow-up discussion in the dangling symrefs thread, focusing on edge case handling in `git update-ref`. Jeff King responds to Toon Claes's proposal to allow null-to-null updates of dangling symrefs, which would preserve compatibility with some existing workflows (like those in Gitaly).

Jeff acknowledges the edge case but argues the double-null-oid pattern is conceptually odd - it effectively requests a no-op deletion of an already-deleted symref. He suggests callers should use simpler forms like `delete FOO_HEAD` or `update FOO_HEAD 000...000` without the redundant old-oid check. While he's open to considering the change for backward compatibility, his preference is to keep the stricter semantics to avoid complicating the refs code further.

The technical discussion remains focused on whether to make this exception in the refs backend's validation logic. Jeff notes the proposed implementation (affecting both files and reftable backends) would work as intended if adopted, but would need updated comments. The thread continues weighing API design purity against real-world usage patterns.
