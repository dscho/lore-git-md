This thread explores optimizations for Git's push behavior when the server already has most objects, particularly in cases like amended commits or branch transfers where unchanged blobs get resent unnecessarily. Sainan initially identified the issue, tracing it to a 2014 change that disabled aggressive edge marking for non-shallow repositories. Testing revealed that `git repack -adb` (which creates reachability bitmaps) enables proper object reuse for amended commits, but common operations like `git pull` can invalidate this advantage by creating new packs without bitmaps.

Jeff King provided key technical insights about how Git's reachability bitmaps work. He explained that even partial bitmap coverage provides benefits - Git can use any existing bitmaps it encounters in the commit history, only needing to traverse newer, uncovered commits. This means stale bitmaps still offer meaningful bandwidth savings, though fresh bitmaps provide maximum efficiency. The discussion has evolved to consider both bitmap maintenance strategies and smarter negotiation heuristics that can better leverage partial coverage.

The core tradeoffs being examined are between the bandwidth savings from optimized pushes versus the computational overhead of maintaining fresh bitmaps. Open questions remain about how to automatically regenerate bitmaps after fetches, whether this should be part of standard pull operations, and how to handle repositories where frequent repacking isn't practical. The conversation connects to broader Git infrastructure work around geometric repacking, automatic maintenance scheduling, and protocol efficiency improvements.
