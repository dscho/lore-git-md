This is a technical clarification about Git's existing push optimization behavior, responding to Sainan's feature inquiry about object reuse during push operations.

Simon Richter explains that Git already implements the basic optimization Sainan was asking about - during push, the receiving server sends its known commit references, and the sender omits any objects (including blobs) reachable from those commits. This means in the common case where blobs haven't changed, they won't be resent.

However, Simon notes two important limitations of this existing mechanism: 1) it requires the sender repository to have full history to properly walk the commit graph (so shallow clones can't take full advantage), and 2) the receiver only shares branch tips rather than a complete object list, which keeps protocol overhead manageable but means some redundant transfers may still occur when the sender lacks certain branches.

The response suggests the core functionality Sainan wants exists, but may not work optimally in all repository configurations. This provides important context for any future discussion about potential improvements - any enhanced optimization would need to address these specific edge cases while maintaining reasonable protocol efficiency. The technical details about how the existing negotiation works (commit reachability rather than direct object listing) help explain why the current behavior has these constraints.
