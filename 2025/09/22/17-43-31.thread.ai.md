Git release notification inquiry thread summary:

Velocifyer's original question about automated Git release changelog delivery has evolved into a comprehensive discussion of notification mechanisms, now covering four approaches: GitHub's release feed, git-scm.com RSS, Christian Couder's `getreleases` script, and the proposed "git-announce" list. Technical constraints around tag-based solutions were established by Jeff King and Junio Hamano, citing script compatibility, immutable tags, object size concerns (14K vs 1K), and design principle violations.

Christian Couder defended the single-list status quo (git@vger.kernel.org) to maintain community cohesion, arguing against specialized lists due to the subjective nature of "important" announcements. Junio Hamano's latest response adds technical nuance, acknowledging that a read-only announce list could work without fracturing the community if properly configured (with responses routed elsewhere), but emphasizes the practical resource constraints of maintaining another list. He shifts the discussion from philosophical objections to implementation concerns, setting a clear condition for further consideration: concrete offers to help with the operational burden.

The thread now contains complete arguments on both sides, with key unresolved points being: 1) the tension between unified discussion and specialized notification needs, 2) the subjective definition of announcement importance, and 3) whether existing technical solutions (RSS, scripts) adequately address the original push-notification use case. Hamano's response moves toward closure by establishing that the barrier is resource-based rather than ideological, while leaving the door for someone to step forward with maintenance commitments. The discussion remains technically grounded while acknowledging both philosophical differences in communication preferences and practical limitations of volunteer maintenance capacity.
