Git release notification inquiry thread summary:

Velocifyer's original question about automated Git release changelog delivery via email/RSS has evolved into a technical discussion of notification mechanisms and tag content strategies. Jeff King and Junio Hamano have established three viable notification approaches: 1) GitHub's native feed (https://github.com/git/git/releases.atom), 2) git-scm.com RSS, and 3) potential `RelNotes` symlink tracking. Historical context reveals some early Git tags (v0.99.5, v1.4.3.2) contained release notes, but this practice was not widespread.

Technical constraints preventing tag-based solutions are now fully documented: script compatibility, immutable tags, object size concerns (14K vs current ~1K tags), and the fundamental design principle against unnecessary data duplication. Performance impacts of larger tag objects (frequently accessed for peeling) and GitHub's potential use of tag contents for its releases page were analyzed. Both participants agree data duplication between tags and RelNotes files lacks justification unless third-party tools specifically require tag-embedded content.

The discussion suggests API integration as a cleaner alternative for platforms like GitHub needing richer release metadata, though no specific implementation path is proposed. All core questions about release notification mechanisms are addressed with multiple technically sound options presented, while tag-based approaches have been conclusively ruled out due to performance and design concerns. The thread has reached natural closure with all viable notification channels identified and their tradeoffs clearly articulated, including historical context about early tag practices.
