This is a follow-up discussion about push optimization when servers already have most objects, focusing on edge cases where current optimizations fall short.

Sainan responds to Simon Richter's explanation of Git's existing push optimization by pointing out two scenarios where it doesn't work as well as desired. First, when amending commits, the server may have the new commit's parent (and thus all its blobs/trees) but still ends up transferring them redundantly because it doesn't recognize the new commit. Second, even simple branch-to-branch transfers can unnecessarily resend unchanged blobs when only the commit objects are new.

The email suggests these are fundamental limitations of the current reachability-based approach, distinct from the previously discussed shallow clone issues. Sainan also briefly mentions (but sets aside) the more complex case of forks stored in the same server repository, noting this could be worked around if the core issues were addressed.

The discussion continues to explore real-world pain points where Git's object reuse during push could be smarter, particularly for workflows involving frequent commit amendments and branch operations. The technical challenge appears to be balancing protocol efficiency against more comprehensive object reuse awareness.
