This is a follow-up discussion in the reftable fsck validation series, specifically addressing patch 5/5 which adds update index sequence validation. Junio Hamano raises an architectural question about whether this validation belongs in fsck or should be part of the runtime reftable reader checks.

The email continues the thread's central tension around validation boundaries between fsck and runtime operations. Junio argues that since reftable is still new and not the default backend, now would be the ideal time to enforce stricter validation at runtime rather than only during fsck. This echoes his earlier feedback on patch 4/5 about trailing newline validation, suggesting a consistent philosophical position that runtime code should catch these issues rather than leaving them to fsck.

The discussion touches on implementation details from the patch: the current check verifies sequential update indices in `tables.list` (like ensuring 0003 is followed by 0004) but doesn't yet validate that table names match their internal headers. Karthik had noted this deeper validation would come in future work.

Key technical points at stake include:
- Whether `REFTABLE_FSCK_ERROR_UPDATE_INDEX` and `badReftableUpdateIndex` should exist as fsck-specific checks
- The tradeoff between runtime strictness (potentially failing operations) versus fsck-only validation (allowing corruption to persist until detected)
- The window of opportunity to tighten rules before reftable becomes more widely deployed

This email doesn't propose specific code changes but invites reconsideration of the series' fundamental approach to validation boundaries. The discussion may influence whether some checks get moved from fsck to core reftable reading code, which would require changes to both the implementation and test cases in patches 4/5 and 5/5.
