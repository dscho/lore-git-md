This is a security-focused follow-up in the ongoing performance optimization discussion around khash vs commit-slab data structures in Git.

Jeff King responds to René Scharfe's security concerns about using `oidhash()` in `git describe`'s depth computation. While acknowledging the theoretical vulnerability where attackers could force hash collisions to degrade performance to O(N^2), Jeff argues the current `commit->index` approach is similarly vulnerable to manipulation. He suggests improving `oidhash()` security by XOR-ing additional hash bits rather than avoiding hash tables altogether.

The proposed patch modifies `oidhash()` to incorporate a second word of the object ID as entropy, making targeted collisions significantly harder while maintaining performance. Jeff notes this change would add minimal overhead compared to the existing hash comparison costs. The discussion reflects a pragmatic approach - recognizing the security concern but prioritizing practical solutions over theoretical worst cases, given Git's existing performance characteristics.

This email advances the thread by moving from identifying security risks to proposing concrete mitigations, while maintaining the performance focus of the original optimization work. The tone suggests the security improvements would be worthwhile but not urgent, fitting with Git's general security posture where denial-of-service attacks are lower priority than data integrity issues.
