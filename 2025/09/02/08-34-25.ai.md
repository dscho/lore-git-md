This is a bugfix patch addressing reference update behavior on case-insensitive filesystems, part of a 2-patch series. The change specifically fixes how the files backend handles reference creation conflicts where references differ only in case (e.g. refs/heads/foo vs refs/heads/Foo).

The patch modifies the error type returned from `lock_raw_ref()` from generic to `REF_TRANSACTION_ERROR_CREATE_EXISTS` when a case conflict is detected. This allows batched reference updates (used by fetch/receive-pack) to properly reject just the conflicting reference while applying other updates, rather than failing the entire transaction. The behavior now preserves the first reference and rejects subsequent case conflicts, which is considered an acceptable compromise since the files backend cannot store case-colliding references anyway.

Key technical changes include:
- Error type change in refs/files-backend.c's `lock_raw_ref()`
- Enhanced error messaging in builtin/fetch.c to warn case-insensitive users about the limitation and suggest migrating to reftable
- New test cases in t/t1400-update-ref.sh and t/t5510-fetch.sh verifying the behavior

The patch maintains backward compatibility while improving the user experience by:
- Allowing partial reference updates to succeed rather than failing entirely
- Providing clear guidance about the filesystem limitation
- Offering migration path to reftable backend which doesn't have this issue

This fixes a regression introduced in Git 2.51 when reference updates switched to batched transactions, where previously case-colliding references would silently overwrite each other. The solution is well-motivated by real-world reports and includes thorough test coverage.
