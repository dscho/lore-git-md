This thread addresses batched reference update issues on case-insensitive filesystems, specifically problems introduced in Git 2.51 when reference updates switched to batched transactions. The series fixes two key issues in the files backend: (1) incorrect error handling for case conflicts between references (e.g. refs/heads/foo vs refs/heads/Foo), now properly returning REF_TRANSACTION_ERROR_CREATE_EXISTS rather than aborting the entire transaction, and (2) a filesystem lock leak during file/directory case conflicts (e.g. refs/heads/foo vs refs/heads/Foo/bar) through case-folding checks during availability verification.

Karthik Nayak's latest patch modifies `lock_raw_ref()` in refs/files-backend.c to lowercase reference names when checking for conflicts on case-insensitive filesystems, enabling proper F/D conflict detection in `refs_verify_refnames_available()` without leaking filesystem details. The change uses STRING_LIST_INIT_DUP for proper string handling and maintains the partial-update behavior where non-conflicting refs remain unchanged. Junio Hamano's review requests stronger justification for how lowercasing solves F/D conflicts, notes an incorrect Reported-by attribution, and suggests commit message improvements while not objecting to the technical approach.

Test coverage in t/t5510-fetch.sh verifies the fix by creating a repository with 'foo/bar' and 'Foo' branches, confirming fetch fails with refname conflict while preserving existing references. The change affects `git fetch`, `git receive-pack`, and `git update-ref --batch-updates`, with user-facing warnings in `builtin/fetch.c` recommending reftable migration.

Patrick Steinhardt previously reviewed the technical approach, suggesting refinements: moving command context in commit messages, using `string_list_append_nodup()` with `strbuf_detach()` for memory efficiency, and improving warning message attribution.
