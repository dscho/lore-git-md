This thread addresses batched reference update issues on case-insensitive filesystems, specifically problems introduced in Git 2.51 when reference updates switched to batched transactions. The series fixes two key problems in the files backend: (1) incorrect error handling for case conflicts between references (e.g. refs/heads/foo vs refs/heads/Foo), now properly marked as REF_TRANSACTION_ERROR_CREATE_EXISTS rather than aborting the entire transaction, and (2) a filesystem lock leak during file/directory case conflicts (e.g. refs/heads/foo vs refs/heads/Foo/bar) by implementing proper case-folding checks during availability verification.

Patrick Steinhardt reviewed Karthik Nayak's initial patch modifying `lock_raw_ref()` in refs/files-backend.c to return REF_TRANSACTION_ERROR_CREATE_EXISTS for case conflicts, confirming the technical approach while suggesting documentation improvements. He recommended clarifying that git-fetch and git-receive-pack already handle partial updates, moving the batched update explanation earlier in the commit message, and making tests work with both files and reftable backends. He also noted a minor style issue with uppercase "OKAY" that should be standardized.

The first patch modified error handling in `lock_raw_ref()` with enhanced error messaging in builtin/fetch.c warning case-insensitive users about the limitation and suggesting reftable migration, with test coverage in t/t1400-update-ref.sh and t/t5510-fetch.sh. The second patch completed the solution by addressing file/directory conflicts through case-folding checks in refs/files-backend.c, preventing lock file leaks during transaction aborts while maintaining backend separation, with additional test cases in t/t5510-fetch.sh.
