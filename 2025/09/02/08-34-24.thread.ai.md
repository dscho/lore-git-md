This thread addresses batched reference update issues on case-insensitive filesystems, specifically problems introduced in Git 2.51 when reference updates switched to batched transactions. The series fixes two key issues in the files backend: (1) incorrect error handling for case conflicts between references (e.g. refs/heads/foo vs refs/heads/Foo), now properly returning REF_TRANSACTION_ERROR_CREATE_EXISTS rather than aborting the entire transaction, and (2) a filesystem lock leak during file/directory case conflicts (e.g. refs/heads/foo vs refs/heads/Foo/bar) through case-folding checks during availability verification.

Karthik Nayak's latest patch modifies error handling in `lock_raw_ref()` to properly handle case conflicts while allowing partial application of non-conflicting references. Junio Hamano's review raises important technical considerations: the solution must distinguish genuine case conflicts from other lockfile scenarios (leftover locks/competing processes) by verifying a lock conflict is truly a case-variant of another ref in the current transaction before special handling. Junio requests the commit message better explain batched update vs transaction semantics and suggests additional verification logic while tentatively accepting the partial-update approach.

The change affects `git fetch`, `git receive-pack`, and `git update-ref --batch-updates`, preserving the first conflicting reference while rejecting case-variant updates. User-facing warnings in `builtin/fetch.c` explain the limitation and recommend reftable migration. Test coverage in `t/t1400-update-ref.sh` verifies the new partial-update behavior, with Junio suggesting expanded tests for edge cases.
