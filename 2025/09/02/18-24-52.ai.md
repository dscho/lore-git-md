Performance optimization for `git describe` depth computation using oidset to avoid quadratic complexity.

This patch from René Scharfe improves the performance of `git describe`'s depth computation by replacing a linear scan of commit flags with an oidset-based tracking system. The key problem being solved is avoiding quadratic complexity when checking if all remaining commits in the queue are flagged, which previously required scanning the entire queue each time a flagged commit was dequeued.

The solution introduces an oidset to track unflagged commits, allowing constant-time checks for whether any unflagged commits remain. This provides a significant performance improvement - benchmarks show a 1.4x speedup (610ms vs 855ms) when describing commits between v2.41.0 and v2.47.0. The approach was chosen over alternatives like maintaining a count of flagged items (which would still require scanning in some cases) or using an object flag (which would reduce available flags for candidate tags).

The implementation carefully handles several edge cases:
- Initial population of the oidset with all unflagged commits
- Removal of commits when they're processed
- Updates when parent commits are flagged/unflagged
- Memory cleanup with oidset_clear()

This builds on prior work (commit 08bb69d70f) and incorporates feedback from Jeff King to use oidset rather than a custom khash implementation. The change is focused on builtin/describe.c, modifying the finish_depth_computation() function while maintaining the same behavior. The patch appears well-tested and benchmarked, with clean commit message explaining the rationale and alternatives considered.

This optimization fits into the broader thread discussion about performance-critical data structures in Git, though it sidesteps the khash vs commit-slab debate by using the simpler oidset abstraction. The implementation avoids the security concerns around custom hash functions discussed in the thread by relying on Git's standard oidset implementation.
