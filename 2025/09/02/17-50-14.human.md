Bug report about `git ls-remote` failing in container-mounted worktrees. Cristian Dinu describes a scenario where `git ls-remote` fails when run inside a container that has a Git worktree mounted read-only. The command incorrectly checks for the presence of the repository's worktree metadata (which exist on the host but not in the container) rather than just operating on the explicitly provided remote URL.

The issue occurs with Git 2.51.0 when:
1. A bare repo exists on the host
2. A worktree is created from it
3. The worktree directory is mounted into a container
4. `git ls-remote` is run inside the container against a different remote

The command fails with "not a git repository" because it tries to verify the worktree's gitdir reference (which points to a host path that doesn't exist in the container). The reporter suggests `ls-remote` should skip repository checks when a remote URL is explicitly provided.

This appears to be a legitimate bug in the repository discovery logic. The report is well-documented with clear steps to reproduce, though it doesn't yet include analysis of the relevant code paths. The behavior seems unintentional and could affect other container-based workflows.
