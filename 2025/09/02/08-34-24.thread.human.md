This thread addresses a regression in Git's handling of reference updates on case-insensitive filesystems, introduced when batched transactions were implemented in Git 2.51. The original issue caused either silent overwrites of case-colliding references (pre-2.51) or complete transaction failures (post-2.51). The two-patch series provides a middle ground: it now properly detects case conflicts and rejects only the problematic references while allowing other updates to proceed.

The first patch, already discussed, improves error handling by returning a specific `REF_TRANSACTION_ERROR_CREATE_EXISTS` error for case conflicts rather than failing the entire transaction. The second patch, newly arrived, focuses on preventing filesystem lock leaks during directory/file case conflicts (like refs/heads/foo vs refs/heads/Foo/bar) by implementing proper case-folding checks. Both patches include comprehensive test coverage in t/t1400-update-ref.sh and t/t5510-fetch.sh.

The solution maintains backward compatibility while providing clearer error messages that guide users toward the reftable backend, which doesn't suffer from these case-sensitivity issues. This represents a practical compromise given the filesystem limitations, allowing most reference updates to succeed while properly flagging conflicts that can't be resolved on case-insensitive systems. The changes are confined to the files backend (refs/files-backend.c) and affect primarily fetch operations where batched reference updates are common.
