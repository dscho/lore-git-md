Review comment on reftable fsck validation series.

This is a review comment from Junio Hamano on patch 4/5 of Karthik Nayak's reftable fsck validation series, which adds checks for trailing newlines in `tables.list` files. The patch detects when the file lacks a terminating newline, treating this as evidence of manual tampering since the reftable backend always writes newlines.

Junio questions whether this specific check makes sense given that other forms of corruption (like inserted blank lines) would already be caught by the normal parser. He suggests it might be more consistent to have the runtime code reject incomplete lines rather than making this a special fsck case. The concern is that the current approach creates an asymmetry where some corruptions are runtime errors while others are fsck-only.

This is a thoughtful technical critique of the patch's design approach rather than a request for specific code changes. It suggests the validation logic might need to be reconsidered for consistency with how other malformations are handled. The comment doesn't reject the patch outright but invites discussion about whether the newline check belongs in fsck at all versus being part of the standard file parsing.

The exchange shows careful attention to the series' goal of robust validation while maintaining clean separation between runtime and fsck behaviors. Junio's comment focuses on conceptual consistency rather than implementation details, characteristic of his architectural review style.
