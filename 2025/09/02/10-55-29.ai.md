This is a technical follow-up in the ongoing discussion about "lock file exists" errors in bare repositories, specifically addressing reftable compatibility concerns.

Patrick Steinhardt responds to Jeff King's observation about cgit failing to recognize reftable-formatted repositories, clarifying that older Git versions should still be able to discover the repository through the HEAD dummy value despite not understanding the reftable format. He notes this is part of reftable's backward compatibility design, where the presence of the "refstorage" extension would cause old versions to bail out gracefully rather than failing to recognize the repository entirely.

The email suggests that if cgit cannot detect the repository at all (as Jeff observed), this would indicate a bug in reftable's compatibility layer that would need fixing. This is an important data point in the broader discussion about ecosystem adoption challenges for reftable backend, particularly for tools like cgit that link directly against Git's C code rather than using the CLI interface.

The exchange reinforces that while reftable remains the preferred technical solution for the underlying lock file issues, its real-world adoption faces hurdles from tools that make assumptions about Git's internal implementation. This particular case may reveal a concrete compatibility issue in reftable's design that needs addressing alongside the files backend modifications being discussed as an interim solution.
