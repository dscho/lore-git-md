This is a review comment on patch 4/5 of the reftable fsck validation series, focusing on the trailing newline check implementation. Junio Hamano questions the selective nature of only checking for missing trailing newlines in `tables.list` while potentially ignoring other forms of file corruption. He suggests that if the reftable reader already detects various malformations at runtime, it might be more consistent to make the newline check part of that general validation rather than a special fsck case.

The review raises an architectural question about where validation boundaries should lie - whether fsck tooling should catch issues the normal reader would silently accept, or if runtime reading code should be equally strict. This touches on the series' core principle of maintaining separation between reftable internals and Git's fsck infrastructure. The comment implies the current approach might create an inconsistent user experience where some corruptions are caught immediately while others (like missing newlines) only surface during explicit fsck runs.

This follows earlier discussion in the thread about error detection granularity, where v2 already improved message specificity between table name vs extension issues. The review doesn't propose specific code changes but prompts reconsideration of the validation philosophy, suggesting runtime checks might be a more holistic solution than layering fsck-specific validations.
