Bug report about `git ls-remote` failing in container-mounted worktrees.

Cristian Dinu reports that `git ls-remote` fails when run inside a container where a Git worktree is mounted read-only. The command fails with "not a git repository" because it checks the worktree's gitdir path (which points to the host system's filesystem location) rather than recognizing it should operate purely on the remote repository specified in the command.

The issue occurs in a specific workflow: creating a bare repo with a worktree, mounting just the worktree directory into a container, then running `git ls-remote` against a different remote repository. The command incorrectly validates the local repository state (via the worktree's gitdir pointer) rather than operating purely on the remote URL provided.

Key technical details:
- Reproducer involves creating a worktree from a bare repo, mounting just the worktree into a container
- Fails with Git 2.51.0
- The Ansible git module triggers this when doing remote operations
- The gitdir path in the mounted worktree points to an inaccessible host path

The report suggests `git ls-remote` should skip local repository checks when a remote URL is explicitly provided. This appears to be a legitimate bug in the command's repository validation logic, particularly affecting containerized workflows where worktrees are mounted read-only. The report is well-documented with clear reproduction steps and context about the real-world impact (Ansible automation).
