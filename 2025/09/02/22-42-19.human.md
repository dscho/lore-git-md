This is a bugfix patch in the reftable fsck validation series, specifically addressing update index sequencing. Junio Hamano questions the architectural decision to implement this check in fsck rather than runtime validation, noting that since reftable is still new and not the default backend, now would be the ideal time to tighten validation rules universally.

The patch adds a check that reftable table names in `tables.list` must have sequential update indices (each table's min/max range must start where the previous left off), implemented via `REFTABLE_FSCK_ERROR_UPDATE_INDEX` and `badReftableUpdateIndex`. The validation tracks expected sequences using `prev_max` in `reftable_fsck_check()`, with test cases verifying detection of sequence breaks.

Junio's review raises an important philosophical question about validation boundaries that echoes his earlier concern about the trailing newline check in patch 4/5. He suggests runtime validation might be more appropriate than fsck-only checks, especially for a new feature where backward compatibility concerns are minimal. This continues the thread's ongoing discussion about the proper separation between reftable internals and Git's fsck infrastructure.

The patch itself appears well-implemented with clear test coverage, but Junio's feedback suggests the series may need to reconsider some architectural decisions before proceeding. This represents the final patch in the v2 series, completing the core stack integrity checks while explicitly noting deeper table-internal validation remains for future work.
