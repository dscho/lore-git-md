This is a discussion about interface design for the `git replay --update-refs` feature, focusing on default behaviors and server-side use cases.

Christian Couder responds to Elijah Newren's review of Siddharth Asthana's patch series that adds atomic reference updates to `git replay`. The key points center around whether `--update-refs` should be the default behavior (as Newren suggests) or remain opt-in. Couder notes that while this might have been reasonable shortly after `git replay`'s introduction, the command has now been experimental for 18 months, making such a behavioral change potentially disruptive.

The exchange highlights differing perspectives on server-side needs. Couder clarifies that atomic operations (the series' default) are particularly valuable for server workflows like GitLab/Gitaly, where `git replay` is already useful due to its in-memory operation without requiring a worktree. This addresses Newren's confusion about which aspects specifically benefit server operations.

The discussion remains unresolved on several interface questions raised earlier in the thread, including flag naming (`--update-refs` vs alternatives) and whether multiple update modes are truly necessary. Couder's response maintains the position that atomic-by-default behavior aligns well with server requirements, though he doesn't directly engage with Newren's broader concerns about interface complexity. The thread continues to show active debate about balancing backward compatibility with optimal design for this experimental-but-maturing command.
