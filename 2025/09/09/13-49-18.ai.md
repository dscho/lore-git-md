This is a discussion thread continuation in the reftable fsck validation series (v3 in progress), specifically addressing feedback on patch 2/5 regarding table name validation. The email focuses on two key architectural questions that emerged from Patrick Steinhardt and Shejialuo's reviews.

First, regarding the duplicate "Checking references consistency" message between backends, Shejialuo suggests either moving it to generic code or making it backend-specific (e.g., "Checking reftable references consistency"), though expresses uncertainty about the latter approach's phrasing. Karthik hasn't yet committed to a solution here.

More significantly, the thread debates whether the reftable library should determine fsck error severities. Shejialuo argues strongly against this, noting it would improperly couple the fsck infrastructure with reftable internals. They explain Git's current compile-time severity assignment via `msg_id_info` and runtime configurability via `fsck.[message id]`. Karthik agrees, acknowledging the complexity of implementing library-determined severities and concluding it wouldn't be worth the architectural tradeoffs. This maintains the series' principle that reftable should report errors but let Git handle severity classification.

The discussion shows the careful boundary-drawing between reftable internals and Git's validation framework, with Karthik accepting the community's preference for keeping severity decisions in Git proper. This email doesn't introduce new patches but solidifies design decisions that will shape the upcoming v3 revision of the series.
