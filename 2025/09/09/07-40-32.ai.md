This is a discussion email in the ongoing submodule gitdir path encoding series, focusing on cross-implementation compatibility concerns. Patrick Steinhardt responds to Adrian Ratiu's patch introducing a config override mechanism for submodule gitdir paths, raising several important considerations about the migration strategy.

The email highlights potential breakage for alternative Git implementations (JGit, libgit2, Gitoxide) that may not yet support the new `submodule.<name>.gitdirpath` config key. Steinhardt proposes two alternative approaches: 1) a repository extension (potentially opt-in via `init.useSubmoduleGitdirExtension`) to ensure clients understand the new path scheme, and 2) maintaining the old `.git/modules/` location with random suffixes for conflict resolution rather than introducing a new `.git/submodules/` directory.

Key technical points raised:
- The current approach may require a phased rollout with waiting periods for implementation adoption
- Repository extensions could provide stronger compatibility guarantees but are "heavy-handed"
- An opt-in extension model could balance migration safety with flexibility
- Questions whether the new directory structure is strictly necessary versus modifying the existing one

This email significantly expands the design discussion beyond the current implementation, introducing new considerations about the migration timeline, opt-in mechanisms, and alternative approaches to path conflict resolution. The suggestions could impact the series' direction, particularly around versioning and backward compatibility strategies.
