This is a follow-up discussion in the submodule gitdir path encoding series, specifically addressing the config override mechanism introduced in patch 3/9. Adrian Ratiu clarifies the purpose of the `submodule.<name>.gitdirpath` config override feature in response to Phillip Wood's query about its role in cross-implementation compatibility.

Key points:
- The config override is positioned as a complementary feature rather than a core requirement for JGit/libgit2 interoperability, since the series will use a repository extension in v3 for that purpose
- The override remains useful for testing and custom encoding schemes, but isn't automatically set to avoid config bloat
- Adrian acknowledges Phillip's point about the feature's relationship to the directory structure change and commits to clarify this in the v3 commit message
- The discussion confirms the series is moving toward using an extension-based approach for cross-implementation support rather than relying solely on config overrides

Technical context:
- The override mechanism lives in `submodule_name_to_gitdir()`'s path resolution logic
- Maintains backward compatibility while allowing custom paths
- Part of broader changes to handle submodule gitdir path encoding conflicts
- Connected to the ongoing discussion about `.git/submodules/` vs `.git/modules/` directory structures

This email doesn't introduce new technical changes but helps refine the series' design rationale, particularly around how different components (config overrides, directory structure, repository extensions) interact to solve the submodule path encoding problem. The exchange shows consensus forming around using repository extensions as the primary cross-implementation compatibility mechanism while keeping config overrides as an optional feature.
