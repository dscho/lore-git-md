This is a discussion about interface design for the `git replay --update-refs` feature, focusing on default behaviors and server-side use cases. Christian Couder responds to Elijah Newren's review of Siddharth Asthana's patch series, addressing two key points:

First, regarding making `--update-refs` the default behavior, Couder agrees this would have been preferable but notes `git replay` has been in the wild for 18 months (since v2.44.0), making such a behavioral change potentially disruptive despite its experimental status. This suggests the window for major interface changes may have passed.

Second, Couder clarifies the server-side benefits of the atomic update functionality, explaining that `git replay` is already server-friendly due to its in-memory operation (no worktree requirement), and that atomic transactions further enhance this by providing reliability. This addresses Newren's confusion about which aspects benefit server workflows.

The exchange highlights ongoing tension between ideal interface design and backward compatibility constraints, with Couder advocating for practical considerations given the command's existing usage. The discussion remains focused on reconciling the patch series' goals with real-world deployment constraints rather than introducing new technical proposals.
