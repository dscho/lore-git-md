This thread continues discussions around planning for Git 3.0, particularly focusing on the challenges of SHA-256 interoperability. The conversation was initiated by brian m. carlson following the Contributor Summit, with the core question being whether to proceed with the original release schedule or wait until the SHA-256 work (currently about halfway complete) is finished.

The discussion has evolved to include both technical proposals and process considerations. brian m. carlson has proposed a `git hash convert` subcommand for repository migration between hash algorithms, while Patrick Steinhardt has been driving efforts to gather ecosystem input before finalizing timelines. Technical work continues in the `sha256-interop` branch, which builds on Patrick's Rust series.

Recent emails have focused more on coordination with the broader Git ecosystem. Patrick proposed engaging with maintainers of major Git implementations (libgit2, JGit, Gitoxide, go-git) and hosting platforms. Michal Suchánek's latest response supports this approach while noting the omission of Gitea from the initial list of platforms to consult. There's general agreement that SHA-1 support will remain for existing repositories even after SHA-256 becomes the default.

Key participants include brian m. carlson (technical migration tools), Patrick Steinhardt (ecosystem coordination), Taylor Blau (ecosystem analysis), Randall Becker (JGit concerns), and Junio Hamano (maintainer perspective). The thread maintains parallel tracks examining both technical solutions and collaborative planning approaches, with current focus shifting toward establishing a structured process for gathering ecosystem feedback before making final decisions about Git 3.0's timing.
