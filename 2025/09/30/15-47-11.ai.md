Junio Hamano responds to Michal Suchánek's inquiry about whether the sibling-directory best practice for worktrees is documented, clarifying that the original worktree designers never anticipated users would want to create worktrees inside the main repository checkout. He acknowledges this assumption may need revisiting if users are consistently confused by the current behavior. 

The email highlights two key points about the design philosophy: first, that worktrees were conceived as peer entities to the main checkout rather than nested within it, and second, that documentation could be improved if this expectation isn't intuitively clear to users. Junio draws a distinction between "side-by-side" checkouts (which he considers reasonable) versus "in-repository" checkouts (which he views as potentially confusing).

The discussion now includes comparative analysis with other VCS workflows, where Michal notes some systems commonly maintain multiple branch checkouts within a repository directory structure. Junio counters that Git's design assumes worktrees exist alongside rather than inside the primary checkout, suggesting this reflects established Git usage patterns rather than arbitrary implementation choices.

This exchange surfaces deeper questions about whether Git's worktree abstraction should adapt to workflows from other VCSes or maintain its current philosophical stance, with implications for both documentation and potential behavior changes.
