This is a follow-up in the ongoing discussion about worktree directory handling, specifically whether worktrees should be created inside the main repository directory. Michal Suchánek responds to Jason Cho's earlier recommendation to avoid nested worktrees, questioning whether this best practice is documented and pointing out that other version control systems commonly use nested checkouts.

The email highlights a key disconnect - while Git's current behavior (treating worktree directories like nested repositories) may help prevent branch-switch collisions (as Jason demonstrated), Michal notes this isn't obvious to users coming from other VCS systems where nested checkouts are standard. He also points out that in workflows where each branch gets its own worktree, the collision scenario Jason described wouldn't occur.

This continues the thread's exploration of whether Git's current behavior is the right design tradeoff between preventing footguns and accommodating familiar workflows from other systems. The exchange surfaces an important documentation gap - if nested worktrees are discouraged, this should be clearly stated in the official documentation rather than being implicit in the implementation's behavior.
