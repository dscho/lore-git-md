This is a follow-up in the ongoing discussion about `git apply`'s fuzzy matching behavior with structurally similar code blocks. Guo Tingsheng provides a concrete real-world example showing how the patch application can go wrong when splitting and reapplying patches from a commit.

The email demonstrates a Java example where two similar Javadoc comment changes (`List<List<String>>` and `List<List<Object>>`) get swapped during application due to line number shifts and identical surrounding context. This confirms the earlier theoretical concern with a practical case, showing how the changes intended for lines 145 and 170 in the original commit end up being misapplied to each other's locations after patch splitting and merging.

The author agrees with Junio Hamano's earlier assessment that this is an inherent limitation of patch application heuristics, not a bug, and supports the idea of adding warnings for ambiguous patch applications. The example serves to illustrate why this would be valuable - even with clear semantic differences in the changes, the structural similarity of the surrounding code leads to incorrect application.

This exchange highlights both the practical impact of the limitation and the need for better user feedback when patch application may be ambiguous, while acknowledging there's no perfect technical solution to the underlying matching problem.
