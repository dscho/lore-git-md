This is a follow-up in the mergetool environment variables thread, where Randall Becker is trying to understand the variable passing mechanism for custom mergetools.

Randall attempts to synthesize the current understanding: Git includes shell fragments from mergetools/ directory rather than creating dedicated shells, and the BASE/LOCAL/REMOTE/MERGED variables are shell variables (not exported environment variables) that are only available to these included fragments. He notes this means custom mergetools not packaged with Git won't have access to these variables through the documented mechanism, forcing them to work around by parsing working index files instead.

Key technical points in this email:
- Confirms understanding that mergetools/ directory contains included shell code rather than standalone executables
- Notes variables aren't exported to sub-shells (explaining why `env` didn't show them)
- Identifies difference in behavior between built-in mergetools (get variables) vs custom ones (don't)
- Suggests workaround of parsing working index files (file_BASE_num etc.) for custom tools

The email advances the thread by proposing a concrete model of how the variable passing works in practice, while highlighting the documentation mismatch for custom tools. It doesn't yet confirm whether the variables are actually available in the shell context as Johannes suggested, but provides a plausible explanation for why they wouldn't appear in `env` output. The core question remains whether the current behavior is intentional (with docs needing clarification) or a bug in variable scoping.
