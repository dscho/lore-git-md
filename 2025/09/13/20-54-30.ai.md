This is part 2 of a 4-patch series fixing batched reference update issues on case-insensitive filesystems, specifically addressing error handling when lock files exist. The patch refines the error classification in `lock_raw_ref()` to properly distinguish between case conflicts within a transaction and pre-existing reference locks.

The key change modifies the files backend to return `REF_TRANSACTION_ERROR_CREATE_EXISTS` (rather than `REF_TRANSACTION_ERROR_GENERIC`) when encountering a lock file for a pre-existing reference. This allows batched updates to fail only the conflicting individual reference while processing others, matching the behavior seen with case conflicts. The patch includes a new test case in t/t5510-fetch.sh that verifies this behavior by creating a lock file and confirming the fetch operation fails only for the locked reference while successfully updating others.

The implementation carefully maintains the existing behavior for case conflicts within a transaction (still using `REF_TRANSACTION_ERROR_CASE_CONFLICT`) while adding proper handling for the lock file case. The commit message and code comments clearly explain the distinction between these error conditions and their implications for batched operations. This change builds on the series' foundation of precise error classification while addressing an edge case that could previously cause unnecessary batch failures.
