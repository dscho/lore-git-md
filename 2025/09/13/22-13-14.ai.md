This is a clarification in the ongoing thread about `safe.directory` failures in shared repositories. Carlo Arenas Belón points out that the error message about dubious ownership is actually being generated by the Git process running on the remote server (`my.server`), not the local clone operation. 

The key technical insight is that the security check failure occurs server-side during the remote repository access, which means the `safe.directory` configuration would need to be set on the server, not the client. The suggested workaround is to first log into the server via SSH as the same user (`myuser`) and attempt the configuration there.

This shifts the troubleshooting focus from client-side configuration to server-side Git behavior, suggesting the original reporter may have been trying to apply the workaround in the wrong context. The response doesn't address why the server-side Git is rejecting the repository ownership, but correctly identifies the locus of the problem. This is a potentially important clarification for debugging the issue, though it doesn't yet explain why the server-side Git would reject a repository that appears properly configured for shared access.
