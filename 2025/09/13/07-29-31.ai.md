Bugfix discussion continuing the `git apply` fuzzy matching thread. Guo Tingsheng provides a concrete real-world example demonstrating how structurally similar Java method documentation blocks can cause misapplication when patches are split and applied separately. The example shows two adjacent JavaDoc comments for overloaded `ExcelWriter` methods where the type parameter changes (`List<String>` vs `List<Object>`) get swapped during application due to identical surrounding context.

The email confirms Junio Hamano's earlier assessment that this is an expected limitation of the heuristic matching algorithm, not a bug, while providing stronger evidence of the problem's real-world impact. The reproduction method involves splitting a commit's patch into fragments and applying them to parallel branches, a workflow where line number shifts between applications are likely. The key technical detail is that when hunks from the same original patch are applied to different branches, their original line numbers become unreliable, forcing fuzzy matching that can fail on structurally identical blocks.

The discussion remains focused on potential UX improvements rather than algorithmic changes, with both parties agreeing that warning about ambiguous patch applications would be valuable. The example demonstrates how even documentation changes (normally low-risk) can be misapplied in codebases with repetitive patterns. No new solutions are proposed beyond the previously suggested warning system, but the concrete example strengthens the case for such a feature by showing how easily the problem can occur in real Java codebases with overloaded methods.
