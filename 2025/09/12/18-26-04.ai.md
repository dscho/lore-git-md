This is a follow-up discussion about the `split` subcommand implementation in Patrick Steinhardt's `git-history` RFC series (v3). D. Ben Knoble reports an issue where they expected to see a diff between old and new trees during the split operation, but only sees modified file listings. After some back-and-forth debugging, they realize the status information was present all along (showing modified files), but they were expecting a full diff output. 

The discussion reveals that:
1. The current implementation shows modified files list in the editor template (via `commit.verbose=true`), but not a full diff
2. The second commit in a split operation currently retains the original commit's tree and message unchanged
3. There's some confusion about the expected UI behavior between the participants

This appears to be a UI/UX clarification rather than a technical implementation bug. The thread shows active debugging between the contributor and reviewer to identify the mismatch in expectations about what information should be displayed during the split operation. The exchange highlights an area where the command's behavior might benefit from clearer documentation or more explicit diff output.
