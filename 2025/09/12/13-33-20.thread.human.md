This thread explores a subtle but important limitation in `git apply`'s patch matching algorithm, where structurally similar code blocks can cause patches to be misapplied. The original report showed HTML components with identical button markup leading to changes being applied to the wrong component. Now, Guo Tingsheng has provided a Java example where overloaded methods with nearly identical JavaDoc comments can cause documentation changes to swap between methods when patches are split and applied separately.

Junio Hamano maintains that this is an expected behavior given the heuristic nature of patch matching, especially when line numbers shift between patch creation and application. The new Java case demonstrates how even documentation changes - typically considered safe - can be affected in codebases with repetitive patterns. Both examples highlight scenarios where wider context (via `git diff -U8`) helps but doesn't eliminate the fundamental ambiguity.

The discussion has converged on the view that while the core algorithm works as designed, there's room for improving the user experience. The most promising direction appears to be adding warnings when patch application encounters ambiguous matches, though no one has yet stepped up to implement this. The thread serves as both a cautionary note about patch application edge cases and a documented starting point for anyone interested in working on the warning system enhancement.
