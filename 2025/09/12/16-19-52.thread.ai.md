Thread identity: Discussion about `git update-ref` behavior with pseudorefs, particularly `MERGE_HEAD`, following recent changes that prevent writing to pseudorefs while conflicting with established advice.

Core problem: Since commit 8e4f5c2dc26e ("refs: refuse to write pseudorefs", 2024-05-15), Git rejects attempts to modify pseudorefs via `git update-ref`, contradicting commit b6d2558c9ea3 ("builtin/commit: suggest update-ref for pseudoref removal", 2020-08-21) which recommended this method for aborting merges. This creates a workflow breakage where users must manually edit `.git/MERGE_HEAD` directly, particularly problematic in worktree scenarios.

Current status: Patrick Steinhardt has proposed a technical solution to special-case pseudorefs in `git-update-ref` while maintaining architectural boundaries. The approach would allow targeted pseudoref updates (starting with `MERGE_HEAD`) outside normal ref transactions, restoring the documented functionality without treating pseudorefs as normal refs.

Key technical details: The proposal suggests carefully scoped pseudoref support that would:
- Keep pseudoref updates separate from normal ref transactions
- Initially focus on `MERGE_HEAD` as the most critical use case
- Avoid bleeding pseudoref logic into the main ref system
- Maintain backend-agnostic pseudoref manipulation

Open questions: 
- Exact implementation boundaries for the special-casing
- Whether to extend support to other pseudorefs beyond `MERGE_HEAD`
- How to ensure the solution doesn't complicate the refdb abstraction
- Whether this approach satisfies the original security/architectural motivations behind 8e4f5c2dc26e

Participant positions: 
- Johannes Sixt originally reported the discrepancy and workflow impact
- Patrick Steinhardt has proposed the special-casing solution, positioning it as a middle path between full support and complete prohibition
- No other contributors have weighed in yet on the proposal

Related work: The thread connects to two prior commits - 8e4f5c2dc26e (current restriction) and b6d2558c9ea3 (original advice). The discussion may need to consider broader pseudoref management patterns and worktree support implications.
