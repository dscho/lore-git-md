This is a bug report about conflicting behavior in Git's handling of pseudorefs like MERGE_HEAD. Johannes Sixt points out that while Git's merge commit message advises using `git update-ref -d MERGE_HEAD` to abort a merge, this command now fails due to a recent change that prevents writing pseudorefs via update-ref. The same restriction prevents manually setting MERGE_HEAD to a specific commit, forcing users to directly manipulate the file in .git/ instead.

The issue stems from two conflicting changes: a 2020 update that added the update-ref advice in commit messages (to work across ref backends), and a 2024 change that blocked pseudoref modifications via update-ref. The current workaround of directly writing to .git/MERGE_HEAD is particularly awkward in secondary worktrees where the path is less straightforward.

This appears to be a genuine usability regression where documented functionality no longer works as advertised. The email doesn't propose a specific fix but invites discussion about how to resolve the contradiction between the advice Git gives and what it actually allows. The thread may need to choose between restoring update-ref access to pseudorefs or updating the commit message template's advice.
