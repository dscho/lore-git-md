This thread examines Git's longstanding design choice to accept any string as a `user.email` configuration value without validation. The discussion began with usharerose questioning this permissiveness, prompting responses that reveal the field's complex real-world usage beyond simple email addresses.

Randall Becker first highlighted a concrete production impact - GitHub's SSO integration repurposes this field to store authentication tokens on NonStop systems, which strict validation would break. Konstantin Ryabitsev then provided technical context about email validation's inherent complexities, noting that local mail systems can expand even unconventional addresses. The latest contribution from Thomas Guyot strengthens the case against validation by emphasizing three key points: server-side hooks can handle validation more comprehensively, Git's flexible commit construction makes client-side enforcement impossible to fully implement, and migration scenarios may require preserving original (non-compliant) metadata from other version control systems.

The thread has converged on recognizing that while the current lack of validation might seem surprising, there are multiple technical and practical reasons maintaining this flexibility. Guyot notes that `git commit` already warns about potentially problematic emails, suggesting the existing balance of guidance without enforcement may be sufficient. No maintainers have yet weighed in on whether this aligns with Git's design philosophy, but the accumulating real-world use cases make a strong argument for preserving the status quo, perhaps with better documentation about recommended validation approaches through hooks.
