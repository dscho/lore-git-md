This thread discusses improvements to git-clone's handling of malformed bundle-URI server responses, with two related patch series from Patrick Steinhardt and Toon Claes addressing various edge cases. The core debate centers on error handling philosophy: whether to require strict protocol validation (failing on invalid server responses) or implement client-side workarounds for real-world deployment scenarios.

Patrick's original series fixed cases like ignoring bundle advertisements without URIs and handling invalid packet lines. Toon followed up with patches to prevent segfaults when 'creationToken' appears without 'uri' and to downgrade certain errors to warnings. The discussion has revealed two perspectives: Justin Tobler and Junio Hamano generally favor strict validation to surface configuration errors, while Toon argues from GitLab's production experience that some client-side resilience is needed for existing server deployments that send fixable-but-invalid data.

In the latest exchange, Justin responds to Toon's practical arguments by maintaining that server-side fixes should be the primary solution, though he acknowledges the niche case where client-side workarounds might be justified. The technical focus remains on connect.c's error handling and the t5558 test coverage, with the segfault fix being uncontroversial while the error-to-warning conversion represents the philosophical divide. The thread shows the project balancing protocol purity against real-world deployment constraints, with no clear resolution yet on the error handling strategy.
