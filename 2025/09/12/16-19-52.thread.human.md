The thread discusses a regression in `git update-ref`'s handling of pseudorefs like `MERGE_HEAD`. Johannes Sixt reports that since commit 8e4f5c2 ("refs: refuse to write pseudorefs"), Git's documented advice to use `git update-ref -d MERGE_HEAD` to abort a merge no longer works, failing with an error about refusing to update pseudorefs. This change also prevents advanced workflows that manually set `MERGE_HEAD` to specific commits.

The current workaround - directly writing to `.git/MERGE_HEAD` - is problematic, especially in secondary worktrees where the path must be constructed manually. This contradicts the original intention behind commit b6d2558, which aimed to provide a backend-agnostic way to manage pseudorefs. The thread highlights a disconnect between Git's documented advice and actual behavior, though no specific solution has been proposed yet. The issue affects both basic merge abort scenarios and more advanced workflows requiring manual MERGE_HEAD manipulation.
