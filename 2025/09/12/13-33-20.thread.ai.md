Thread identity: Bug report about `git apply` misapplying patches when files contain structurally similar code blocks, particularly when line numbers shift between patch creation and application. Original report demonstrated with HTML components having identical button markup.

Core problem: The patch application algorithm can incorrectly match patches to structurally identical but semantically wrong locations when (1) multiple code blocks share identical structure, (2) line numbers shift, and (3) context lines match multiple locations. The reporter showed a case where a button text change in HeaderComponent was misapplied to FooterComponent.

Current status: Maintainer Junio C Hamano acknowledges the behavior but considers it an expected limitation of the heuristic matching approach rather than a bug. The tool cannot guarantee correct placement when context lines match multiple locations, especially after line number shifts.

Key technical details: The issue manifests in files with repeated patterns (UI components, configs, generated code). Wider context (via `git diff -U8`) can help but not eliminate ambiguity. The problem stems from fundamental limitations in patch application heuristics when facing identical context matches.

Open questions: Potential future enhancement to detect and warn about ambiguous patch applications, though this remains marked as a starter project idea rather than an active effort. No current plans to modify the core matching algorithm to handle such cases differently.

Participant positions: Original reporter demonstrated a clear reproduction case. Junio C Hamano responded that this is working as designed given the inherent ambiguity in patch application when context lines match multiple locations. Suggested wider diff context as mitigation but emphasized no foolproof solution exists.

Related work: No prior discussions referenced. The response leaves open the possibility of future UX improvements around ambiguous patch detection while maintaining the current heuristic behavior.
