This is a discussion contribution about Git's `user.email` validation, adding new perspectives to the ongoing thread. Thomas Guyot's email reinforces the case against strict client-side validation by highlighting three key points: server-side validation through hooks can provide more comprehensive checks (including integration with directory services), the impossibility of fully enforcing email validity due to Git's flexible commit construction capabilities, and the importance of preserving original metadata when importing from other SCMs.

The response builds on previous technical arguments from Ryabitsev about email validation complexities and Becker's production use case, but introduces new considerations about version control interoperability and the distributed nature of Git's data model. Guyot notes that `git commit` already provides warnings about potentially invalid emails, suggesting the current balance of guidance without enforcement may be sufficient.

Technically, the email references commit message format flexibility as a fundamental constraint that would prevent any client-side validation from being truly authoritative. It also raises the rarely-discussed case of SCM migration scenarios where preserving original (potentially non-compliant) metadata might be desirable for historical accuracy. These points suggest that even if validation were added, bypass mechanisms would be essential.

The contribution maintains the thread's trajectory toward preserving the status quo, though it does not address whether Git project might want to document recommended validation approaches (like hook implementations) as an alternative to built-in enforcement. No new technical implementation details are proposed, keeping the discussion at the philosophical/design level.
