This is a help request about managing inode exhaustion on an NFS server storing many small Git repositories. The author describes a situation where thousands of small repositories (typically with ~5 commits each) are being stored daily, consuming inodes faster than disk space. They've tried repacking objects and archiving older repos, but these measures haven't fully solved the problem, leading them to increase disk size solely to gain more inodes.

The key constraints are: 1) repositories cannot be deleted as they contain valuable data, 2) the NFS stores only the .git directories which are exposed as remotes, and 3) existing solutions like repacking and archiving have proven insufficient. The author is seeking alternative strategies from the Git community to better handle this scaling challenge.

This appears to be a real operational pain point with NFS and Git's object storage model, though the small repository size and strict retention requirements make it somewhat atypical. The email doesn't propose any specific solution, instead asking for community input, so follow-up discussion may focus on alternative storage strategies, filesystem tuning, or Git configuration optimizations for this high-volume, small-repo use case.
