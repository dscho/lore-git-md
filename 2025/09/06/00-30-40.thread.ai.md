Bug report and discussion of regression in `git fetch --tags` behavior in bare repositories, introduced in Git 2.51.0 and persisting through 2.51.2. Original reporter David Bohman identified the issue when fetching tags (v9.18.41, v9.20.15, v9.21.14) in a bind9 repository, where tags were reported as fetched but not stored, with the operation failing due to rejected 'stable' tag updates. Karthik Nayak has now independently reproduced the issue in both the original bind9 case and a minimal test case, confirming the general nature of the problem.

Technical analysis traces the regression to the reference transaction system introduced in 2.51.0, which enforces atomic failure where pre-2.51 versions allowed partial success. The discussion has evolved from initial diagnosis to active investigation, with two perspectives emerging: David Bohman emphasizes user impact, noting the behavioral change in a mature tool risks compatibility issues and highlights misleading error reporting (tags marked successful when not stored). The technical implementation perspective, now supported by Nayak's reproduction, acknowledges this as a consequence of the reference transaction model's atomicity guarantees.

Key open questions include: whether atomic failure is an intentional (if undesirable) consequence of reference transactions, which behavior (old per-tag or new atomic) should be considered correct, and how to address the discrepancy between reported and actual tag storage. The reproducible test cases (both original bind9 scenario and minimal reproduction) provide concrete ground for evaluating solutions. The thread maintains focus on tag update mechanics while considering broader implications for Git's behavior in bare repositories and error reporting accuracy, with Nayak indicating further technical analysis is forthcoming. The discussion balances technical consistency of the new reference transaction system against practical user expectations from a long-standing command.
