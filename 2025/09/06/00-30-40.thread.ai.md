Bug report for regression in `git fetch --tags` behavior in bare repositories, introduced in Git 2.51.0 and persisting in 2.51.2. Reporter David Bohman first observed tags being reported as fetched but not appearing in repository (bind9 repository tags v9.18.41, v9.20.15, v9.21.14), with command exiting status 1 and rejected 'stable' tag update. Now provides minimal reproduction case showing general issue: in bare repository setup, force-pushing a tag in main repo causes subsequent `fetch --tags` in bare clone to both reject moved tag (expected) and fail to store other new tags (unexpected). Tags like `v5` reported as "[new tag]" but missing from `git tag`, while `stable` correctly rejected due to clobbering. Junio C Hamano originally couldn't reproduce; Randall Becker suggested `--force` workaround. New test case confirms core issue isn't bind9-specific but general bare repo behavior when tags force-pushed, ruling out network/repo-specific factors. Key findings: exit status 1 suggests tag rejection may fail entire operation despite misleading success reports for other tags, and behavior changed from working correctly in Git 2.50.1. Open questions remain about why fetch output shows successful tag updates that don't materialize, and exact mechanism causing this in bare repos. The reproducible test case enables maintainers to debug tag update logic, with next steps being analysis of why bare repo tag storage fails when other tags are rejected.
