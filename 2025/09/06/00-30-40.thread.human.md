This thread examines a regression in `git fetch --tags` behavior in bare repositories, introduced in Git 2.51.0 and persisting through 2.51.2. David Bohman originally reported the issue when fetching tags in a bind9 repository, where tags were incorrectly reported as fetched but not actually stored, particularly when force-pushed tags were involved. Chris Torek's technical analysis traced the regression to the new reference transaction system's atomic failure behavior, which differs from the pre-2.51 partial success model.

Karthik Nayak has now confirmed being able to reproduce the issue in both the original bind9 case and a minimal test case, reinforcing that this is a genuine regression rather than an edge case. The core problem remains the discrepancy between the command's output (reporting tags as successfully fetched) and the actual storage behavior (where new tags fail to store when any tag update is rejected).

The discussion has evolved from initial diagnosis to evaluating whether this atomic failure behavior is intentional or an undesirable side effect. Key open questions center on reconciling the technical consistency of the new reference transaction system with user expectations from this long-standing command. With multiple developers now confirming the issue, attention is shifting toward potential solutions that might preserve atomicity while providing more accurate feedback about which tags were actually stored.
