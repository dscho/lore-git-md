This thread examines a regression in `git fetch --tags` behavior in bare repositories, introduced in Git 2.51.0 and persisting in 2.51.2. David Bohman originally reported that tags were being reported as fetched but not actually stored in the repository, with the command exiting with status 1 when encountering rejected tag updates. A minimal reproduction case confirmed the issue: in bare repositories, force-pushed tags now cause the entire fetch operation to fail atomically, whereas pre-2.51.0 versions would still store other new tags despite rejecting moved ones.

Chris Torek's analysis suggests this change stems from the new reference transaction system in 2.51.0, which enforces atomic behavior. The discussion has shifted from diagnosing the regression to evaluating whether the old per-tag behavior or new atomic behavior should be considered correct. Bohman raises important practical concerns about the change's impact on users - both the unexpected behavioral shift in a mature tool and the misleading error reporting that claims tags were fetched when they weren't stored. While the atomic behavior may be technically consistent with the reference transaction model, the thread is now weighing whether this represents an improvement or an unintended consequence that needs reconsideration. The reproducible test case remains valuable for further evaluation of tag update logic in this context.
