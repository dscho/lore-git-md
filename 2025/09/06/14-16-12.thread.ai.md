Thread "Managing inode exhaustion with many small Git repos on NFS" addresses operational scaling challenges when storing thousands of small Git repositories (typically ~5 commits each) on NFS servers where inode exhaustion occurs before disk space constraints. Core constraints remain: repositories cannot be deleted (valuable data), NFS stores only .git directories exposed as remotes, and existing solutions have proven insufficient.

Technical proposals have evolved through multiple iterations:
1. Initial suggestions from Randall S. Becker included `git gc --aggressive` and `sparse-checkout`
2. Brian M. Carlson provided detailed configuration recommendations:
   - Pack file optimizations: `fetch.unpackLimit=1` (later refined to `transfer.unpackLimit=1`), adjusted `gc.autoPackLimit`, and `git repack -d --cruft`
   - Storage backend: reftable migration with version compatibility considerations
   - Filesystem-level tuning for ext4/btrfs (Linux-specific)
3. Kousik Sanagavarapu's implementation report:
   - Confirmed adoption of `transfer.unpackLimit=1`
   - Shared active GC settings: `receive.autogc=true`, `gc.auto=1`, `gc.autopacklimit=1`
   - Highlighted operational constraints: high push volume, immutable ext4/NFS backend

Brian M. Carlson's latest response provides critical performance analysis of Kousik's GC settings, warning that `gc.auto=1` with `autopacklimit=1` would trigger expensive repacks after every push. They share a practical reference point from their workplace (repacking every ~40 pushes) as a more sustainable alternative, noting `transfer.unpackLimit=1` is widely used at major forges without performance issues due to packed object optimizations like bitmaps.
