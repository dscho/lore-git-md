This is a follow-up discussion in the completed ODB transaction refactoring series, focusing on the safety and justification for removing transaction nesting support. Taylor Blau raises concerns about the trade-offs in the design change.

The thread has already established the core refactoring work moving transaction handling from bulk-checkin to object-file with clear API boundaries. The specific patch being discussed removes the ability to nest ODB transactions, requiring callers to explicitly check for existing transactions.

Taylor questions whether the simplification of the internal API justifies the increased burden on callers, noting that:
1. The change requires callers to manually check for existing transactions
2. Missing these checks could lead to BUG() conditions
3. The commit message doesn't clearly articulate the benefits that outweigh these risks

He provides a concrete example showing how nested transactions currently work (where inner transactions are no-ops) versus the new model where callers must manage transaction state explicitly. The concern is that this shifts complexity from the API implementation to its users, potentially introducing new failure modes.

This discussion doesn't propose changes to the already-completed series, but seeks clarification on the design rationale - particularly whether the internal simplification provides enough benefit to justify the increased caller responsibility. The thread context shows Patrick Steinhardt had previously asked similar questions about the trade-offs, which were addressed in later versions of the patch.
