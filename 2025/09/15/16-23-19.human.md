This is a discussion about the safety implications of extending `--ignore-other-worktrees` to `git rebase`. Junio Hamano responds to Phillip Wood's concerns about allowing rebase operations on branches checked out in other worktrees.

The exchange highlights two key safety considerations: First, rebasing a branch that's checked out elsewhere could lead to confusion since rebase actively modifies the branch (unlike checkout which may just be reading it). Second, if a user wants to rebase in a different worktree, it may indicate they have uncommitted changes in the original worktree that aren't ready to be rebased.

Junio suggests two alternative workflows: either perform the rebase in the worktree where the branch is already checked out, or consider whether the branch is actually in a state ready for rebasing. This continues the thread's shift from implementation details to fundamental questions about whether rebase should support this feature at all, given the higher risks compared to checkout operations.

The discussion remains unresolved but is moving toward either stronger warnings for rebase cases or potentially excluding rebase from this feature entirely. This maintains the thread pattern where checkout scenarios have clearer safety characteristics while rebase integration raises more complex workflow questions.
