Feature proposal for a `git history split` subcommand, part of Patrick Steinhardt's ongoing `git-history` command series (now at RFC v3). This patch implements a simplified workflow for splitting commits, which normally requires a multi-step rebase process. The command would let users split a commit interactively by selecting which changes to move to a new commit, then automatically preserving the original commit with remaining changes.

The implementation currently shows modified files (but not full diffs) in the editor template when splitting, using `commit.verbose=true`. Phillip Wood suggests improving the UX by allowing message editing for both resulting commits rather than just the new one, and notes this functionality could potentially be integrated into the sequencer to also benefit interactive rebase. Patrick agrees with both points.

This is one of several subcommands in the `git-history` proposal inspired by Jujutsu (jj) that aim to make complex history operations more accessible. The series is nearing its final RFC version before being split up, with this particular implementation looking well-motivated but likely to see some UX refinements based on the feedback.
