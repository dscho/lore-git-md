This is a behavior change for `git add -p` that improves hunk splitting interaction, part of Phillip Wood's ongoing work on the interactive patch interface.

The patch modifies how `git add -p` handles hunk states after splitting. Currently, when a user splits a hunk that was already marked as selected or unselected, all resulting sub-hunks inherit that state. This can be frustrating when users want to selectively apply parts of a split hunk, as they must manually navigate back to deselect individual pieces. The change makes split hunks start in an "undecided" state, prompting the user to explicitly choose for each sub-hunk.

The implementation is carefully gated behind the `WITH_BREAKING_CHANGES` flag to maintain backward compatibility, as some users may rely on the current behavior. The change is documented in BreakingChanges.adoc and comes with a new test case verifying the new behavior. This appears to be a well-considered improvement to the interactive workflow, though the opt-in mechanism means it won't affect most users immediately. The patch is the first of two in this series, building on previous discussion about hunk state management in the interactive add interface.
