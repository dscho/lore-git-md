This is a behavior change patch for `git add -p`'s hunk splitting functionality, part of Phillip Wood's ongoing series to improve interactive patch handling. The change modifies how split hunks inherit their selection state when the `WITH_BREAKING_CHANGES` flag is enabled.

The patch introduces a new behavior where split hunks are marked as `UNDECIDED_HUNK` rather than inheriting the parent hunk's selection state. This means users will be prompted to select/deselect each split hunk individually, addressing the current workflow issue where only the first split hunk is interactive while others inherit the parent's state silently. The change is gated behind `WITH_BREAKING_CHANGES` due to backward compatibility concerns raised in previous discussion.

Key technical details:
- Modifies `split_hunk()` in `add-patch.c` to set `use = UNDECIDED_HUNK` for all split hunks when `WITH_BREAKING_CHANGES` is defined
- Updates `Documentation/BreakingChanges.adoc` to document the behavior change
- Adds a new test case in `t/t3701-add-interactive.sh` verifying the new undecided state behavior under `WITH_BREAKING_CHANGES`

The implementation follows the agreed approach from thread discussion, using the existing `WITH_BREAKING_CHANGES` mechanism rather than introducing new version-gating. The test case demonstrates the new workflow where splitting a previously selected hunk requires explicit reselection of desired parts. This represents the first of two patches in the v2 series, with the core behavior change now properly isolated from other improvements.
