This is a cover letter for a two-patch bugfix series targeting `git add -p`'s hunk splitting behavior in `add-patch.c`. The series builds on previous discussion about state inheritance during hunk splitting and post-edit status updates.

The first patch modifies hunk splitting behavior so newly created hunks are marked as "undecided" rather than inheriting their parent's selection state, but gates this behind the `WITH_BREAKING_CHANGES` compile-time switch to maintain backward compatibility. The second patch fixes synchronization of the `splittable_into` field after hunk lines are edited.

Key technical changes include:
- New `UNDECIDED_HUNK` state handling in `add-patch.c` when splitting hunks
- Documentation of behavior change in `BreakingChanges.adoc`
- Enhanced test coverage in `t/t3701-add-interactive.sh` for both splitting and editing scenarios
- Conditional test execution based on `WITH_BREAKING_CHANGES` presence

The series has already incorporated feedback from Junio Hamano and Justin Donnelly, with V2 changes focusing on:
- Restricting the behavior change to `WITH_BREAKING_CHANGES` builds
- Improved commit message clarity
- Test case refinements including proper spacing in redirections

The implementation follows the thread's resolution to use existing version-gating mechanisms rather than introducing new ones, with the technical fixes deemed ready for integration while UX improvements remain tracked for future work. The changes demonstrate careful attention to backward compatibility concerns while addressing real usability issues in hunk splitting workflows.
