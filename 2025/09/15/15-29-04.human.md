This is the second patch in Phillip Wood's series improving `git add -p`'s hunk splitting behavior, focusing on a technical fix for splitability calculations.

The patch addresses an edge case where editing a hunk (changing context lines to deletions or vice versa) could leave the `splittable_into` count incorrect. The fix recalculates this count during the edit operation. While Phillip notes this is unlikely to affect most users (since people rarely edit and then split the same hunk), the change ensures correct behavior in all cases.

The implementation modifies `recount_edited_hunk()` in `add-patch.c` to track line type changes and update `splittable_into` accordingly. A new test case in `t3701` verifies the fix by editing a hunk to change a context line to a deletion, then splitting it - demonstrating the corrected split count calculation.

This patch builds on the first in the series (which handled state inheritance during splitting) and appears ready for integration, with clear test coverage and a straightforward implementation. The changes are well-contained to the hunk editing logic and don't affect the broader `WITH_BREAKING_CHANGES` behavior introduced earlier in the thread.
