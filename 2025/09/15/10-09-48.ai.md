This is a discussion about integrating `--ignore-other-worktrees` into `git rebase`, part of Gabriel Scherer's series improving worktree safety checks. Phillip Wood raises concerns that rebasing a branch checked out in another worktree is fundamentally more dangerous than checkout cases, since rebase actively modifies the branch. He questions whether we should encourage this behavior at all, suggesting instead that users might be better served by rebasing a detached HEAD when making experimental changes.

The technical implementation in Gabriel's patch adds the flag to `struct rebase_options`, wires it through the command-line parsing, and modifies the branch-checking logic in `builtin/rebase.c` to respect the flag. Documentation updates and test coverage in `t/t3400-rebase.sh` verify both the default failure case and the override behavior.

The discussion highlights a key design tension: while checkout operations might reasonably offer an escape hatch for read-only use cases, rebase's branch-modifying nature makes concurrent access more hazardous. Phillip's comment suggests the safety implications may warrant different handling than checkout/switch scenarios, potentially requiring either stronger warnings or alternative workflows like detached HEAD operations. This introduces new considerations for the series' finalization beyond the current focus on advice message wording.
