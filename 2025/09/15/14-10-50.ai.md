Feature refinement for `git-history` command's HEAD management. Phillip Wood follows up on Patrick Steinhardt's implementation of HEAD rewinding after cherry-pick-like operations in the `git-history` command. He suggests considering a detached HEAD approach similar to `git rebase`, which would prevent branch reflog pollution and enable convenient result verification via `git range-diff $branch@{1}...HEAD`. 

The discussion reveals an implementation detail question about whether `git-history` currently detaches HEAD at operation start (like rebase does) or maintains branch attachment throughout. Phillip advocates for the detached HEAD approach used by rebase, noting its benefits for both reflog cleanliness and post-operation verification. This builds on their earlier exchange about unifying HEAD management between rebase and cherry-pick operations via the new `restore_head_target` option.

Key technical points:
- Current implementation uses same reflog message as rebase
- Detached HEAD approach would mirror rebase behavior
- Would enable clean `range-diff` verification of changes
- Avoids polluting branch reflog with intermediate states
- Relates to ongoing discussion about HEAD management unification
