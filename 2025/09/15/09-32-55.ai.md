This is a feature patch implementing the `split` subcommand for the proposed `git-history` command, part of Patrick Steinhardt's RFC v3 series. The patch follows up on Phillip Wood's feedback about improving the commit message editing flow during splits.

The `split` subcommand aims to simplify the complex manual process of splitting a commit into multiple parts. The current implementation shows modified files list in the editor template (using `commit.verbose=true`) but doesn't show full diffs, which has been noted as a potential UI mismatch with user workflows. Phillip Wood suggested two key improvements: allowing message editing for both resulting commits (not just the first one), and considering sequencer integration to make the functionality available in `rebase -i`.

Patrick acknowledges both points in his response, agreeing to implement message editing for both commits and noting the value of sequencer integration. This aligns with the thread's broader theme of leveraging existing Git infrastructure where possible. The exchange also touches on the ongoing discussion about command architecture philosophy - whether new history editing operations should be standalone commands or integrated into existing ones like `rebase -i`.

Technical details worth noting for future reference:
- Current behavior uses file lists rather than full diffs in the editor template
- Second commit preserves original tree and message by default
- Implementation currently outside sequencer (potential future integration point)
- Phillip Wood's suggestion about reusing sequencer's commit creation/message editing code
- UI expectation mismatch regarding diff display vs modified files list

The patch represents incremental progress in the series, with Patrick responsive to feedback while maintaining focus on the core functionality. The discussion highlights how this feature intersects with several ongoing architectural questions in the Git project, particularly around command design and sequencer reuse.
