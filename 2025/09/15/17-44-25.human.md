This is a discussion about behavior changes in `git add -p`'s hunk splitting functionality, specifically regarding how split hunks inherit their selection state. Phillip Wood's patch proposes marking all split hunks as "undecided" rather than inheriting the parent hunk's selection state, which would prompt the user to review each split hunk individually. While this improves workflow for users who want to selectively apply parts of a split hunk, it comes with a trade-off for users who want to keep all split hunks selected.

Junio Hamano raises concerns about the change being gated behind the `WITH_BREAKING_CHANGES` flag, questioning whether this warrants a version-bump switch. He suggests that if both behaviors are useful in different scenarios, it might be better to make this configurable at runtime via a configuration variable or interactive command rather than tying it to a version switch.

The discussion reflects Git's careful approach to behavior changes - balancing improvements against backward compatibility, and preferring runtime configurability over compile-time switches when possible. The patch appears technically sound but the discussion is now focusing on the right mechanism to introduce the change.
