This is a refactoring and feature series introducing transaction interfaces to Git's object database (ODB) subsystem, building on previous work to prepare for pluggable ODB backends. The series comes from Justin Tobler as version 2, addressing feedback from Patrick Steinhardt and others in the ongoing discussion.

The key changes in this iteration include:
- Making `end_odb_transaction()` a no-op when no transaction exists and adding guards against mismatched transactions
- Updating `object_file_transaction_begin()` to accept a `struct odb_source` instead of `struct object_database` for better alignment with future pluggable backends
- Renaming `object_file_transaction_end()` to `object_file_transaction_commit()` for consistency
- Adding missing documentation for the ODB-level transaction functions
- Preserving the current `git update-index --verbose` behavior rather than trying to fix its quirky option parsing order issues in this series

The patch series relocates transaction code from bulk-checkin.[ch] to object-file.c (removing 438 lines while adding 386), establishes clearer API separation between generic ODB-specific and files-backend-specific transaction handling, and removes transaction nesting capability. It updates callers in cache-tree.c, object-file.c, read-cache.c, and builtin/update-index.c to use the new interfaces.

Notable technical details for future reference:
- New ODB layer functions: `odb_transaction_{begin,commit}()`
- Files-backend functions: `object_file_transaction_{begin,commit}()`
- Removed `flush_odb_transaction()` by merging its functionality
- Added assertions for transaction/ODB state consistency
- Transitional state mixes ODB and files-backend code in object-file.c
- Future calls will use `source->backend.transaction_start()` when pluggable backends exist
- The `--verbose` behavior in update-index stems from parse_options_step() implementation since 2010

The series appears well-constructed with thorough commit messages and careful attention to the review feedback. The main outstanding question is how to handle the `--verbose` edge case long-term, but the decision to defer that is reasonable given the scope of this refactoring.
