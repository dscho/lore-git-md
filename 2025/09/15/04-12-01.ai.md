Bugfix for `git send-email` handling of Reply-To headers. This patch addresses a specific issue where using `--compose --reply-to` together would result in duplicate Reply-To headers in the email, causing rejection by some email providers like Gmail.

The problem occurs in the interaction between two mechanisms: the Reply-To header inserted into the intro message template, and the subsequent header copying that happens during message processing. Currently, the code copies the Reply-To header without checking if one was already parsed from the intro message.

The fix modifies the header parsing logic in `pre_process_file` to detect and store the Reply-To header value when processing the intro message, similar to how it already handles In-Reply-To and References headers. This prevents the duplicate header by ensuring the value is only set once.

Key technical details:
- Modifies `git-send-email.perl` to add a new condition in the header parsing block
- Checks for Reply-To header case-insensitively (`/^Reply-To: (.*)/i`)
- Stores the value in the existing `$reply_to` variable rather than duplicating it
- Maintains consistency with existing header handling patterns in the function

The patch is straightforward and focused, touching only the necessary code path. The commit message clearly explains both the problem and solution, though it might benefit from mentioning that this affects the compose/edit workflow specifically. No test changes are included, which might be worth noting since this is a behavioral change in email header handling.
