This is a bugfix patch series for `git add -p`'s hunk splitting behavior, following up on previous discussion in the thread. Phillip Wood addresses two issues in the interactive patch interface:

1. The first patch changes how split hunks inherit their selection state. Currently, split hunks keep the same selection as their parent, which can force users to manually navigate back to deselect parts they don't want. The new behavior (gated behind `WITH_BREAKING_CHANGES`) marks all split hunks as "undecided" so users get prompted for each one. This is a more logical workflow but potentially disruptive, hence the breaking changes guard.

2. The second patch fixes an edge case where editing a hunk (changing deletions to context lines or vice versa) could leave the hunk's splittable state incorrect. While rare in practice, the fix ensures the split count stays accurate after edits.

The changes are well-motivated and address real usability pain points, particularly the first patch which improves the splitting workflow. The implementation follows Git's conventions for potentially disruptive changes by using the existing `WITH_BREAKING_CHANGES` mechanism. Test coverage is thorough, including both the new default behavior and the breaking changes path.

This series appears ready for inclusion, having incorporated feedback from the previous round (notably Junio's input about using the existing breaking changes infrastructure). The changes are focused and the commit messages clearly explain both the problems and solutions.
