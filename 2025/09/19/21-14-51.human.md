This is a feature proposal for a new rebase strategy to handle semantic conflicts in non-atomic commits. Antonio Mennillo responds to feedback from brian m. carlson about their `git-rebase-clean` tool, which aims to reduce redundant conflict resolution during rebases of semantically dependent commits (like interface changes followed by implementations).

The tool now proposes a three-step approach: temporarily squash commits to resolve conflicts with full context, then reconstruct the original commit structure using Git's native diff/apply machinery. This preserves granular history while avoiding the "conflict cascade" where similar semantic conflicts must be resolved repeatedly in a traditional rebase. The author acknowledges this doesn't make commits truly atomic - semantic inconsistencies remain in history - but it makes rebasing such histories more manageable.

Key improvements in v2.0.0 include removing language-specific dependencies (tree-sitter) to align with Git's content-agnostic philosophy, though some limitations remain around cases requiring human judgment (like header file dependencies). The author plans further refinements in v3.0.0, including better handling of edge cases like submodules and merge commits.

The discussion highlights the tension between Git's ideal of atomic commits and real-world development practices, particularly with junior developers or legacy codebases. While the tool offers practical benefits for certain workflows, questions remain about whether it should be integrated into Git core given architectural constraints and the potential for mismatched user expectations.
