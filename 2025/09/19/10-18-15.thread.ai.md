Bug report: double-free crash in `git stash show -p` with invalid options. Thread originated by Lauri Niskanen documenting a crash when passing invalid arguments (e.g. `--invalid`), with regression identified by Kristoffer Haugsbakk as introduced in commit 748bd094 ("builtin/stash: fix leak in `show_stash()`", 2024-06-11). Core issue is in `show_stash()` where `strvec_clear()` attempts to free already-freed memory during error cleanup after option parsing fails, triggering "free(): double free detected in tcache 2".

Technical details: crash occurs at `builtin/stash.c:1047` during cleanup path. Valgrind traces confirm memory originally allocated via `strdup()` is freed twice. Root cause analysis by Junio Hamano and Jeff King reveals `setup_revisions()` processes arguments by shifting elements in the strvec array without NULL-terminating unused slots, causing `strvec_clear()` to encounter duplicate entries during cleanup. Additional memory leaks identified when "-p" argument is rearranged, indicating broader strvec management issues in `setup_revisions()` affecting other commands like `git bisect`.

Key technical findings:
- `setup_revisions()` shifts arguments left without NULLing originals, violating strvec invariants
- `free_removed_argv_elements` flag in `setup_revision_opt` should be set for strvec callers
- Current behavior leaks memory when rearranging arguments (e.g., `git stash show -p --`)
- Issue affects multiple commands using `setup_revisions()` with strvecs

Solution approaches under discussion:
1. Local fix for `show_stash()` that NULLs unused slots after `setup_revisions()`
2. Systemic fix modifying `setup_revisions()` to NULL unused slots, changing its API contract
3. New `setup_revisions()` wrapper that would:
   - Automatically enable `free_removed_argv_elements`
   - Correct the strvec's `.nr` field
   - Maintain NULL termination of the array

Jeff King's latest analysis confirms Junio's NULL-termination fix is correct despite initial off-by-one concerns, explaining the post-increment behavior. Proposes simpler alternative that only NULL-terminates at the new `left` boundary rather than clearing entire unused portion. Junio Hamano questions whether minimal NULL-termination is sufficient when multiple elements are consumed, noting `strvec_clear()` operates on `.nr` count rather than NULL detection. This raises key technical decision point about whether solution needs comprehensive cleanup of consumed elements.

Test coverage gaps identified in current suite, particularly rearranged-argument cases. Performance impact of NULL assignments not yet measured. Discussion continues weighing tradeoffs between:
- Quick local fix (easier to backport but leaves similar issues elsewhere)
- Systemic solution (more maintainable long-term but requires broader changes)
- Wrapper approach (comprehensive but adds abstraction layer)

Technical implementation considerations:
- Current behavior violates strvec assumptions in multiple ways
- Wrapper solution would prevent similar issues across all commands
- Junio confirms earlier patch only addressed NULL termination aspect
- Test suite needs enhancement to catch rearranged-argument leaks

Open questions:
- Whether minimal NULL-termination suffices or full cleanup needed
- Backportability vs long-term maintainability tradeoffs
- Exact implementation details of wrapper solution
- Scope of affected commands beyond `stash` and `bisect`
- Performance implications of additional NULL assignments
- Interaction with leak detection infrastructure
- Proper handling of free_removed_argv_elements flag

Participant positions:
- Jeff King favors minimal NULL-termination at boundary
- Junio Hamano questions if this sufficiently addresses strvec invariants
- Both agree solution must handle multiple-consumed-element cases
- Collaborative analysis ongoing to determine optimal approach
