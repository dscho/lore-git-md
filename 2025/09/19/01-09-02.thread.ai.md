SHA-1/SHA-256 interoperability series part 1 (9 patches) by brian m. carlson continues with documentation updates and test preparation for Git's planned hash function transition in version 3.0. The series now includes six of its nine patches, with the latest addition extending `git rev-parse` to expose compatibility hash information.

Core changes include comprehensive documentation updates covering pack file formats (v3 index), tag signature handling, and the new `gitformat-loose.adoc` that precisely describes loose object storage with examples for both SHA-1 and SHA-256 repositories. The new `rev-parse` functionality adds a `compat` mode to `--show-object-format` that prints the compatibility hash algorithm when configured (via `extensions.compatobjectformat`), or an empty line when none exists. This extends the existing option to handle four cases: `storage` (current default), `input`, `output`, and `compat`.

Technical infrastructure includes `rev-parse --output-hash` for compatibility hash printing, updates to fsck for proper GPG signature header expectations, and test infrastructure with `COMPATIBILITY_HASH` prerequisite. The new `rev-parse` implementation checks `the_repository->compat_hash_algo` and prints its name if set, with thorough test coverage verifying behavior in SHA-256 repositories with/without SHA-1 compatibility mode.

The loose object format specification details file structure, naming convention, and content format including header prefix (type, size, null byte) and zlib compression, with concrete examples for empty tree and simple blob storage. Files touched include `Documentation/` (multiple format docs), `builtin/rev-parse.c`, `t/` (test infrastructure updates in `t1500-rev-parse.sh`), and core commands (`rev-parse`, `fsck`).

The series remains focused on non-controversial groundwork, carefully separating documentation and test preparation from more substantive interoperability implementation work planned for future parts. Each patch is logically independent while contributing to the overall goal of supporting multiple hash algorithms, with the author continuing to position this as prerequisite work that can merge independently of more complex hash transition components to follow.
