Bug report clarification regarding Git's rename detection with symlinks.

Michal Suchánek provides additional technical details to clarify the core issue with Git's rename detection when files are replaced with symlinks. The key point is that Git treats the transition from a regular file to a symlink (even with identical content) as a complete file deletion and addition of a new entity, rather than a mode change. This creates an inconsistency where Git's diff view shows the operations as completely separate (delete file + add symlink), yet rename detection fails to properly track the original file's movement.

The email includes concrete diff examples showing how Git represents:
1. A file deletion and symlink creation with identical content as two separate operations
2. The same content appearing in two new files (one symlink, one regular) with no rename detection between them

This demonstrates that Git's internal handling of symlinks versus regular files is fundamentally different from how it presents these changes to users, leading to confusing behavior in rename detection. The issue appears to be more about Git's diff machinery treating symlinks as completely distinct from regular files, rather than just a rename detection limitation.
