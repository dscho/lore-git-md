Bug report clarification regarding Git's rename detection with symlinks and file repopulation.

Michal Suchánek responds to Elijah Newren's explanation of Git's rename detection behavior, providing concrete evidence that the issue goes beyond just symlink cases. The key technical point is that Git's diff machinery treats mode changes to/from symlinks as complete file deletions and additions, even when the content remains identical. This creates an inconsistency where Git's internal representation considers the files completely unrelated, yet rename detection still fails to properly track the relationship between the original file and its new name.

The email includes three diff examples demonstrating:
1. A file being deleted and replaced with a symlink of the same content (shown as unrelated operations)
2. The same scenario repeated to emphasize the behavior
3. An additional case showing a file deletion alongside two file additions with identical content, where no rename is detected

Michal argues this reveals a fundamental discrepancy in Git's behavior - the diff presentation shows symlinks and regular files as completely distinct entities, yet rename detection fails to recognize the rename of the original file that (from the user's perspective) has no relationship to the newly created symlink. This goes beyond the initial understanding of the issue as being about files remaining present in the target version, showing it's more about how Git handles mode changes during rename tracking.

The discussion continues to explore edge cases in Git's rename detection, with this email providing concrete evidence that the problem affects more than just merge operations and persists even with break detection enabled. The core tension remains between Git's internal representation of file identity and user expectations about rename tracking.
