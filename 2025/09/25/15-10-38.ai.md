Bugfix for `git add -p`'s hunk splitting behavior after edits. This is the final patch in Phillip Wood's series addressing hunk splitting in the interactive patch interface.

The patch fixes an edge case where editing a hunk (changing context lines to deletions or vice versa) could leave the hunk's `splittable_into` count incorrect. The core change updates `recount_edited_hunk()` in `add-patch.c` to recalculate splittability by tracking line type transitions (context to diff or vice versa) during recounting. Each transition point marks a potential split location.

A new test case in `t/t3701-add-interactive.sh` verifies the fix by:
1. Creating a file with a hunk that initially splits into two parts
2. Editing the hunk to change a context line to a deletion
3. Confirming the edited hunk now properly splits into three parts
4. Verifying the final staged content matches expectations

The change is low-risk as it affects only the relatively rare case where users both edit and then split the same hunk. The implementation maintains the series' established pattern of tracking hunk state explicitly rather than inheriting properties from parent hunks. This completes the thread's goal of making hunk->splittable_into consistently accurate regardless of editing history.

With this patch, the series' technical work is complete - all design questions from earlier iterations have been resolved, test coverage is comprehensive, and the maintainer-approved approach is fully implemented. The changes will ship unconditionally without version gating or runtime configuration.
