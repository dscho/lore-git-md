This is part 3/9 of brian m. carlson's SHA-1/SHA-256 interoperability series, focusing on GPG signature handling in tag objects. The patch clarifies the design rationale for having either `gpgsig` or `gpgsig-sha256` headers in tags, but not both simultaneously (except in hypothetical multi-algorithm scenarios).

The key technical point is that tag signature headers follow strict mutual exclusivity based on the repository's hash algorithm. In SHA-256 mode, the in-body signature uses SHA-256 while an SHA-1 signature (if present) moves to the `gpgsig` header. During conversion to SHA-1 format, these roles reverse - the SHA-256 signature moves to `gpgsig-sha256` header while the SHA-1 signature returns to the body. This design emerged from an accidental omission in Git 2.29 that shipped without proper SHA-256 signature support, leading brian m. carlson to implement a backward-compatible solution for 2.30 rather than risk breaking existing experimental SHA-256 tags.

The discussion with Patrick Steinhardt reveals two important implementation details: 1) The current behavior is intentional (not an oversight) to maintain compatibility with tags created during the 2.29 window, and 2) The only scenario where both headers might appear is if supporting a third hash algorithm like SHA-3-512 in the future. The patch documents these design decisions in the Git documentation to clarify the actual behavior for users and developers.
