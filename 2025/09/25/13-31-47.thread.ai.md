Bug report about `git merge --no-ff` failing with "stash failed" error on Windows, originally reported by Nikolay Shustov. The issue occurs specifically with repositories containing files that have trailing dots in their names (e.g., "/something/blah."), imported from Perforce via `git p4` on Windows. Eric Sunshine confirmed this matches documented Windows filesystem limitations where shell/UI functions fail on dot-terminated filenames, explaining why the same merge works on Linux. The error manifests during Git's internal stash handling during merges, though `git stash create` works fine when run separately.

Diagnostic information shows the problem arises when Git attempts to access these problematic filenames during merge operations. Nikolay Shustov's latest email confirms the root cause analysis and reveals that while Windows shell/UI has limitations with dot-terminated filenames, lower-level Windows APIs (as used by Cygwin) can handle them correctly. This suggests potential solution approaches using appropriate Windows APIs rather than shell functions. The reporter validated the issue by recreating it in a previously working repository, strengthening the case for a Git-side solution.

The thread has progressed from initial reporting through root cause confirmation to solution exploration phase. Key technical details include: Windows path handling differences between shell/UI functions (which fail) and lower-level APIs (which work), the specific failure during `merge --no-ff` stash operations, and the `git p4` import context. Johannes Schindelin (Dscho) remains involved as the primary Windows expert, with Eric Sunshine having provided the initial platform-specific behavior confirmation. Next steps would involve concrete proposals to either modify Git's Windows path handling to use appropriate APIs or implement filename normalization during problematic operations.
