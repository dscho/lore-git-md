Bug report about `git merge --no-ff` failing with "stash failed" error on Windows, originally reported by Nikolay Shustov. The issue occurs specifically with repositories containing files that have trailing dots in their names (e.g., "/something/blah."), imported from Perforce via `git p4` on Windows. Eric Sunshine confirmed this matches documented Windows filesystem limitations where shell/UI functions fail on dot-terminated filenames, explaining why the same merge works on Linux. The error manifests during Git's internal stash handling during merges, though `git stash create` works fine when run separately.

Diagnostic information shows the problem arises when Git attempts to access these problematic filenames during merge operations. The reporter's manual renaming of files to include trailing dots (from original Perforce import) triggered the platform-specific behavior. A control case with a `git p4` repository lacking such filenames works correctly, confirming the correlation. Johannes Schindelin (Dscho) is involved in the investigation, which has progressed from initial information gathering to confirmed root cause analysis. The thread now awaits proposed solutions - either modifying Git's Windows path handling to normalize such filenames or documenting this as a known `git p4`/Windows limitation. The technical specifics point to Windows API functions like `open()` and `fopen()` failing on dot-terminated paths during stash operations.
