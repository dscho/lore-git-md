Bug report about `git merge --no-ff` failing with "stash failed" error, originally reported by Nikolay Shustov. The error occurs during Git's internal stash handling during merges, with diagnostic attachments provided (standard bug report and trace2 logs). The working theory points to problems in Git's stash handling during merges manifesting in certain environments, as the same merge scenario works correctly when the repository is hosted on Linux, suggesting platform-specific factors like filesystem behavior or permissions.

New diagnostic information reveals the repository contains files with trailing dots in their names (e.g., "/something/blah."), originally imported from a Perforce depot via `git p4` on Windows. This caused filename normalization issues where Git initially showed the files as both removed and untracked, requiring manual intervention. The reporter confirms `git stash create` works fine when run directly, suggesting the issue is specific to stash-merge interaction rather than stash itself. The problem appears tied to Windows environments with `git p4`-imported paths containing trailing dots, though this correlation isn't yet confirmed as causal.

Johannes Schindelin (Dscho) has joined the investigation, initially suggesting running `git stash create` separately to isolate the failure point. The thread remains in information-gathering phase with no proposed fixes yet, but the new details about dot-terminated filenames and `git p4` import history provide a promising diagnostic path. The reporter stands ready to conduct further experiments if this direction seems relevant to diagnosing the root cause.
