The thread investigates a Windows-specific failure where `git merge --no-ff` reports "stash failed" when operating on repositories containing files with trailing dots in their names (e.g., "file."), originally imported from Perforce via `git p4`. Nikolay Shustov originally reported the issue with diagnostic logs, showing the problem only on Windows while working correctly on Linux.

Eric Sunshine has now identified the root cause by referencing Microsoft documentation that explicitly warns against filenames ending with periods on Windows. While the filesystem supports such names, Windows shell and core functions like `open()` fail when accessing them, explaining why Git's internal stash operations during merges encounter problems. This matches Nikolay's observation that manually renamed files with trailing dots trigger the issue, while repositories without such filenames work fine.

Johannes Schindelin (Dscho) is involved in the investigation, though no fix has been proposed yet. The discussion has shifted from diagnosis to considering solutions—either modifying Git's path handling on Windows to normalize these filenames or documenting this as a known limitation with `git p4` imports. The thread remains active with the core issue now clearly understood as a Windows platform constraint interacting with Perforce-imported paths.
