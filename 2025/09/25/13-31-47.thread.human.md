This thread documents a Windows-specific bug where `git merge --no-ff` fails with a "stash failed" error when operating on repositories containing files with trailing dots in their names (e.g., "file."). The issue was originally reported by Nikolay Shustov after importing such filenames from Perforce via `git p4`. Eric Sunshine confirmed this stems from documented Windows filesystem limitations where shell/UI functions fail on dot-terminated paths, though the same operations work fine on Linux.

The investigation has progressed from initial reports to confirmed root cause analysis. Shustov's latest email validates that while Windows shell utilities choke on these filenames, lower-level Windows APIs (as used by Cygwin) can handle them correctly, suggesting potential paths for a fix. Johannes Schindelin (Dscho) is involved in the discussion, which now stands at a decision point between modifying Git's Windows path handling to use more permissive APIs or documenting this as a known limitation of `git p4` imports on Windows. The technical specifics point to failures in Windows' `open()` and `fopen()` during stash operations, with Cygwin's successful handling of these paths offering a possible implementation model for a solution.
