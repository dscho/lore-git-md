This is part 3 of a 9-patch series on SHA-1/SHA-256 interoperability, specifically addressing how GPG signatures are handled in tag objects. The email clarifies a design decision around signature headers that came up during review.

Brian m. carlson explains that the current dual-header approach (where tags can have either `gpgsig` or `gpgsig-sha256` headers but not both) was an intentional compatibility choice. Originally planned for Git 2.29, the implementation was accidentally dropped, leading to an interim state where SHA-256 tags were created without proper header support. The current design ensures these tags remain valid while preventing signature confusion across hash algorithms.

The response makes clear that signature headers follow a strict transformation pattern when converting between hash algorithms: the in-body signature always matches the tag's current hash format, while compatibility signatures move between body and headers. This maintains consistency while allowing for future expansion to additional hash algorithms like SHA-3-512.

This patch appears to be settling a reviewer's question about the design rationale rather than proposing new changes. The explanation shows careful consideration of real-world deployment scenarios, including LTS distributions running older Git versions. The technical details align with the series' established approach to hash algorithm interoperability.
