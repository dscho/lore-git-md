This is a discussion about Git's patch workflow optimization, specifically exploring ways to get more testing coverage for the 'next' branch. Ben Knoble builds on Kristoffer Haugsbakk's suggestion that large Git-using projects could test against 'next' by proposing a Rust-inspired "crater" approach - where known major Git users would run their test suites against Git's development branches.

The email references Rust's "crater" system (a distributed test infrastructure that runs community projects against compiler changes) as a potential model for Git. Ben suggests coordinating with major Git-using projects to automatically run their tests against Git's 'next' and 'master' branches, possibly on every commit. This would theoretically provide broader real-world testing coverage than relying solely on Git's own test suite and maintainer testing.

The proposal appears thoughtful but remains at a conceptual level - it doesn't address implementation details like how to identify/recruit these "big users", what infrastructure would be needed, or how to handle test result reporting. The suggestion comes in the context of ongoing discussions about whether the 7-day 'next' branch integration period could be safely shortened if more testing coverage were available.
