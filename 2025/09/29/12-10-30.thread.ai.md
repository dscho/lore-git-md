Proposal to improve cherry-pick commit message tracking with three competing approaches: Rasmus Villemoes' hook-based version-aware format, Oswald Buddenhagen's git-notes bidirectional linking alternative, and brian m. carlson's suggestion to use existing `prepare-commit-msg` hooks. Junio C Hamano provided historical context explaining the current bare SHA-1 trailer format originated from Linux kernel workflows where both original and cherry-picked commits were public in the same project, making SHA-1s sufficient identifiers.

Buddenhagen responds to Hamano's clarification, acknowledging the original design intent while noting a persistent perception that Git treats cherry-picks as "second-class" compared to merges. He observes this perception may have slowed progress on cherry-pick tracking features despite Hamano's openness to improvements. The discussion highlights a disconnect between Git's original public same-project assumptions and modern trunk-based development needs.

Key technical points remain the three proposals: Villemoes' new hook mechanism for version context, Buddenhagen's git-notes solution requiring no core changes, and carlson's existing hook approach. Open questions include hook exit semantics (Villemoes), notes implementation specifics (Buddenhagen), and hook applicability (carlson), with the fundamental tension between new functionality versus working within current systems. All acknowledge SHA-1 reference limitations in distributed backports, with the social/historical context now framing the technical debate about built-in support for distributed workflow tracking.
