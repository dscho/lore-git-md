Proposal to improve cherry-pick commit message tracking with three competing approaches: Rasmus Villemoes' hook-based version-aware format, Oswald Buddenhagen's git-notes bidirectional linking alternative, and brian m. carlson's suggestion to use existing `prepare-commit-msg` hooks. Junio C Hamano provided historical context explaining the current bare SHA-1 trailer format originated from Linux kernel workflows where both original and cherry-picked commits were public in the same project, making SHA-1s sufficient identifiers.

Buddenhagen has now responded to Hamano's technical defense of Git's trunk-first development philosophy, arguing it makes unrealistic assumptions about developer discipline and faces four practical barriers in large projects: difficulty determining oldest target branches, excessive testing requirements, merge conflicts requiring messy fixups, and complex history visualization. He expands his git-notes proposal into a broader system for tracking "weak provenance info" covering cherry-picks, rebases, and amends, which could also address change-id standardization needs. This would require handling stale links through garbage collection but offers more flexible history tracking than ancestry-based approaches.

Hamano had previously countered characterization of cherry-picks as "second-class," explaining structural advantages of trunk-first development where fixes flow from oldest branches forward. He expressed skepticism about non-ancestral commit relationships as "vague" and "ill-defined," while leaving room for tooling to help implement merge-based workflows. The technical debate now centers on whether cherry-pick tracking should reinforce Git's ancestry model (Buddenhagen's notes) or require new relationship semantics (Villemoes' hooks), with Hamano emphasizing structural history relationships over ad-hoc linking.

Key open questions include hook exit semantics (Villemoes), notes implementation specifics including garbage collection (Buddenhagen), and applicability of existing hooks (carlson). The fundamental tension remains between new functionality versus working within current systems, now with Buddenhagen framing git-notes as part of a larger commit provenance system that would need to handle rewrite operations and stale reference cleanup, while Hamano maintains the importance of ancestry purity in Git's design philosophy.
