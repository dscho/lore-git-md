Proposal to improve cherry-pick commit message tracking with three competing approaches: Rasmus Villemoes' hook-based version-aware format, Oswald Buddenhagen's git-notes bidirectional linking alternative, and brian m. carlson's suggestion to use existing `prepare-commit-msg` hooks. Junio C Hamano provided historical context explaining the current bare SHA-1 trailer format originated from Linux kernel workflows where both original and cherry-picked commits were public in the same project, making SHA-1s sufficient identifiers.

Buddenhagen responded to Hamano's clarification, acknowledging the original design intent while noting a persistent perception that Git treats cherry-picks as "second-class" compared to merges. Hamano counters this characterization with a technical defense of Git's current approach, explaining the structural advantages of trunk-first development where fixes flow from oldest branches forward, creating clear ancestry relationships. He expresses skepticism about proposals to add non-ancestral commit relationships, describing them as "vague" and "ill-defined," while leaving room for tooling that could help users implement the preferred merge-based workflow more easily.

Key technical points remain the three proposals: Villemoes' new hook mechanism requiring core changes, Buddenhagen's git-notes solution working within current systems, and carlson's existing hook approach. The discussion now centers on whether cherry-pick tracking should reinforce Git's ancestry model (Buddenhagen's notes) or require new relationship semantics (Villemoes' hooks), with Hamano emphasizing the importance of structural history relationships over ad-hoc linking. Open questions include hook exit semantics (Villemoes), notes implementation specifics (Buddenhagen), and the applicability of existing hooks (carlson), with the fundamental tension between new functionality versus working within current systems now framed by Hamano's defense of Git's ancestry-based design philosophy.
