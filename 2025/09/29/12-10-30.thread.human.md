This thread explores proposals to improve how Git tracks cherry-picked commits across versions and repositories. Rasmus Villemoes originally suggested a hook-based system to replace the standard "(cherry picked from commit X)" message with version-aware context, while Oswald Buddenhagen proposed using git-notes for bi-directional linking instead. Brian m. carlson offered a middle path via existing prepare-commit-msg hooks.

Junio Hamano provided crucial historical context, explaining that the current SHA-1-only format originated from Linux kernel workflows where both original and cherry-picked commits were public in the same project. The feature was made opt-in after users found the references unnecessary for private branch cherry-picks. This background helps frame the current discussion, showing the limitations of SHA-1 references for distributed backport scenarios that the various proposals aim to address.

The core tension remains between adding new functionality (Villemoes' version-aware hooks) versus adapting existing systems (Buddenhagen's notes or carlson's hook approach). Key open questions include implementation specifics for each proposal and how they handle edge cases, with Hamano's historical perspective suggesting the solution space should account for both public and private cherry-picking workflows.
