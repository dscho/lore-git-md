This thread explores how Git tracks cherry-picked commits in commit messages, with three competing proposals on the table: Rasmus Villemoes suggests a new hook mechanism, Oswald Buddenhagen advocates for git-notes integration, and brian m. carlson proposes using existing prepare-commit-msg hooks. 

Junio Hamano provided important historical context, explaining that Git's current SHA-1 trailer format was designed for Linux kernel workflows where both original and cherry-picked commits were public in the same repository. Buddenhagen's latest response acknowledges this context while noting a persistent perception that Git treats cherry-picks as second-class operations. He observes that Hamano's clarification reveals openness to better tracking solutions, despite Git's original design assumptions favoring public same-project workflows.

The discussion highlights a technical-social divide: while the three technical proposals (hooks, git-notes, existing infrastructure) offer concrete solutions, there's also an underlying conversation about how Git's historical design assumptions may have unintentionally discouraged better cherry-pick tracking for modern distributed workflows. The thread remains open-ended, with no clear consensus yet on which technical approach to pursue, but with growing recognition that the status quo's limitations stem from historical context rather than intentional design.
