This is a proposal to shorten the 'next' branch integration period for documentation-only changes, made in the context of the ongoing patch workflow optimization discussion.

Kristoffer Haugsbakk suggests that documentation patches could safely graduate from 'next' to 'master' in less than the standard 7-day period, arguing that the risks are lower than for code changes. The key points are that documentation changes (1) are less likely to conflict with concurrent changes, (2) have lower impact if bugs slip through (rendering issues rather than functional bugs), and (3) subjective improvements are already vetted by review before merging to 'next'. The proposal maintains the same review standards but aims to reduce integration overhead for both contributors and maintainers.

The email references Junio Hamano's earlier message about the fixed 7-day period being important for catching bugs in code changes, but suggests this may be unnecessarily conservative for documentation. It acknowledges some potential downsides - missing late feedback from doc-diff users and rendering regressions - but considers these acceptable tradeoffs.

This builds on the thread's broader theme of optimizing patch flow while maintaining quality, offering a concrete case where process could be safely streamlined. The suggestion appears well-reasoned but doesn't address how to objectively define "documentation-only" changes or whether this would complicate the maintainer's workflow by requiring case-by-case judgment of graduation timing.
