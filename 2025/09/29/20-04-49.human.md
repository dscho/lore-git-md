**Documentation patch workflow proposal**  

Kristoffer Haugsbakk suggests an exception to the standard 7-day 'next' branch waiting period for pure documentation changes. The rationale is that doc patches have lower risk (rendering issues being less severe than code bugs) and shorter integration cycles could reduce overhead for both contributors and maintainers.  

The proposal notes that doc changes rarely conflict, making them good candidates for faster graduation. It also points out that subjective doc improvements are typically vetted during review, so late-stage objections would be unusual. The main tradeoff would be missing some opportunistic feedback from developers who check doc-diff outputs, but this is framed as a minor concern.  

This builds on Junio Hamano's earlier thread about optimizing patch flow, but focuses narrowly on documentation as a low-risk area for experimentation. The suggestion maintains the same review standards while potentially streamlining integration.  

The idea appears well-reasoned but doesn't address how "pure documentation" would be defined or whether this might create inconsistency in the graduation process. It also assumes doc changes are inherently less risky—a premise that might benefit from data (e.g., historical doc-related reverts).  

As a focused optimization within the broader workflow discussion, this could be a practical middle ground for testing shorter 'next' periods without compromising code stability.
