This is a discussion follow-up about the new `git refs get` plumbing command. Ben Knoble raises thoughtful questions about the design choice to require exact refnames without DWIM (Do What I Mean) expansion, which differs from `git rev-parse`'s behavior.

The email questions whether removing DWIM might actually make scripting harder in some cases, since scripts accepting user input would need to manually expand shorthand names (like "main" to "refs/heads/main"). While acknowledging that strict refname checking has advantages, the author suggests a potential middle ground: adding a `--dwim` flag later to give script writers flexibility while keeping strict behavior as the default.

This touches on a key tension in Git's plumbing commands - whether to prioritize predictability (the current `refs get` approach) or convenience (DWIM behavior). The discussion doesn't propose any code changes yet, but raises important considerations about how the new command might evolve or interact with existing tools. The thread context shows this is part of a well-considered GSoC project that has already implemented and tested the strict behavior as an intentional design choice.
