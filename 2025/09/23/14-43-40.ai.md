This is a technical follow-up in the ongoing discussion about handling deprecated commands in the build system when `WITH_BREAKING_CHANGES` is enabled. Junio Hamano responds to Patrick Steinhardt's suggestion about potentially keeping man pages for deprecated commands with replacement notices rather than completely removing them.

Junio acknowledges Patrick's idea but notes it would require significant architectural changes to the current build system assumptions. The current model tightly couples binary installation with man page generation - programs listed in `EXCLUDED_PROGRAMS` (like `git-whatchanged`) have neither their binaries nor documentation built/installed. This allows the doc-lint system to skip checking documentation for excluded commands.

The email highlights a key tension in the discussion: Patrick's user-focused approach (wanting to maintain documentation with deprecation notices) versus the existing technical constraints Junio describes. Junio suggests that implementing Patrick's proposal would require first decoupling several interconnected build system behaviors around `EXCLUDED_PROGRAMS`, which appears non-trivial.

This exchange keeps the core technical question open - whether to pursue the more user-friendly documentation approach (requiring build system changes) or maintain the current simpler but less informative removal strategy. The thread continues to balance implementation complexity against user communication needs for deprecated features.
