This is a licensing discussion in the context of the ongoing Rust infrastructure work, specifically addressing how to avoid repeating the libgit2/Git license incompatibility with the new Rust code.

Johannes Schindelin responds to Phillip Wood's concerns about adding license headers to new Rust code that would allow compatibility with Gitoxide. He provides historical context about how libgit2's license incompatibility created barriers to code sharing between projects, leading to duplicated efforts and missed opportunities for innovation. Schindelin argues this is a chance to avoid repeating that mistake by making the new Rust code explicitly compatible with Gitoxide's dual MIT/Apache license from the start.

The key points are:
1. Schindelin clarifies he's not proposing relicensing existing code, just ensuring new Rust code can be shared with Gitoxide
2. He suggests using GPLv2+exception for new Rust files, similar to Git's own suggested license header
3. He emphasizes this enables future discussion about code sharing rather than preemptively blocking it
4. The discussion reveals a tension between maintaining Git's current licensing and enabling Rust ecosystem collaboration

This email continues the thread's pattern of balancing technical progress with broader ecosystem considerations, now focusing on licensing rather than the previous compliance discussions. The proposal appears thoughtful but would require significant community discussion given the licensing implications.
