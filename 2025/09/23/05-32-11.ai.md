This is a discussion about the governance and repository management of Git's proposed LTS (Long-Term Support) releases for platforms that cannot adopt Rust when it becomes mandatory in Git 3.0. The email is part of the ongoing Rust infrastructure RFC series, specifically addressing where LTS maintenance should occur.

Patrick Steinhardt argues against Junio Hamano's suggestion to host LTS releases in a separate repository, proposing instead to keep them in the canonical Git repository. His key concerns are:

1. **Maintainer support**: LTS maintainers may need mailing list review processes and security coordination (git-security@ access)
2. **Trust and oversight**: Avoiding unobserved forks by less-trusted contributors
3. **User confusion**: Preventing fragmentation where users report LTS issues to main Git maintainers
4. **Release consistency**: Avoiding split history between initial/maintained LTS versions
5. **Fork prevention**: Reducing risk of hard forks by keeping everything under the official project umbrella

Steinhardt counters Hamano's "single pointer" solution by noting it doesn't address the underlying coordination challenges. He proposes a compromise where:
- LTS development happens externally (e.g. on a forge) for contributor convenience
- Final releases undergo mailing list review before being tagged in the canonical repository

This maintains the Git repository as the source of truth while allowing flexible workflows. The discussion highlights tensions between:
- Decentralized maintenance vs project oversight
- Contributor convenience vs release integrity
- Rust transition timelines vs legacy platform support

The thread remains unresolved on whether to:
1. Fully separate LTS maintenance (Hamano's preference)
2. Integrate with oversight (Steinhardt's proposal)
3. Hybrid development/release model (new compromise)

This governance question impacts how Git will handle the Rust transition's compatibility guarantees and could set precedents for future breaking changes. The discussion connects to broader themes in the RFC about managing transitions while maintaining stability.
