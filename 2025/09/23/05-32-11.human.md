This is a discussion about the governance and hosting of future Git LTS (Long-Term Support) releases for platforms that cannot adopt Rust, as part of the broader Rust transition effort.

Patrick Steinhardt responds to Junio Hamano's proposal to host LTS releases in a separate repository, arguing instead for keeping them in the main Git repository. He cites several concerns: the LTS maintainers may need guidance from the core team, security coordination would be harder with an external fork, users would still associate LTS issues with the main project, and having some releases in one place and others elsewhere could cause confusion. He also worries about encouraging a hard fork of Git.

Hamano had suggested that a clear pointer to the separate LTS releases would suffice, but Steinhardt counters with a compromise: let LTS development happen externally (e.g., on a forge) but require final releases to be tagged in the canonical repository via pull request review. This would maintain a single source of truth while giving LTS maintainers workflow flexibility.

The exchange highlights the tension between project control and maintainer burden as Git prepares to support both Rust-required and Rust-free versions. Steinhardt's position leans toward centralized governance with some workflow concessions, while Hamano seems more willing to delegate entirely for the LTS line. The discussion remains constructive, with both sides seeking practical solutions to the coming split in Git's platform support.
