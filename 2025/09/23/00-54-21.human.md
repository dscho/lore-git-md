Jeff King provides technical clarification on bitmap behavior during pushes, responding to Sainan's testing with `git repack -adb`. This is part of the ongoing discussion about optimizing object reuse during push operations when servers already have most objects.

King explains that bitmaps should still provide benefits even after a `git pull` creates new bitmap-less packs, contrary to Sainan's initial concern. The bitmap format is designed to degrade progressively - when checking reachability for a new commit, Git can traverse back until hitting a bitmap-covered commit, then use that to fill in the rest. He provides a concrete example showing how this works for both linear and branched history.

The response suggests the key factor is whether to use bitmaps at all, rather than their freshness. Git will attempt to use existing bitmaps even if some traversal is needed, as the system can't predict how much traversal will be required beforehand. This addresses one of the open questions from the thread about bitmap maintenance requirements.

The technical depth of the response indicates this is moving into implementation details of the bitmap approach, building on earlier discussions about tradeoffs between bandwidth efficiency and maintenance overhead. King's explanation provides reassurance that the bitmap solution may be more robust than initially feared regarding pack freshness.
