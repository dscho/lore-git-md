The thread continues the architectural debate around commit graph handling in Git's pluggable object database (ODB) effort, with Patrick Steinhardt and Derrick Stolee presenting competing visions for how commit graphs should integrate with the new system.

Steinhardt's original 6-patch series refactored commit graph handling to prepare for pluggable ODB backends, moving tracking from object_database to odb_source across multiple files. Junio Hamano and Stolee have argued that commit graphs should remain repository-wide concept, serving as a structured cache for commit data regardless of storage format. Steinhardt maintains they are implementation details of specific storage formats (like packfiles) that alternative backends might handle differently.

In his latest response, Steinhardt clarifies his position isn't about changing commit objects themselves, but allowing different storage formats for metadata like generation numbers and bloom filters. He proposes three backend function pointers to handle graph-related operations, arguing this source-specific approach better accommodates diverse storage needs while maintaining abstraction. He cites potential use cases like cloud databases or SQLite that might handle this metadata more efficiently than current commit-graph files.

While acknowledging Stolee's alternative (repository-level graph handling with backend queries) could work, Steinhardt considers it potentially more complex. He hints at an upcoming design document to formalize these ideas after completing two more patch series. The exchange remains constructive but highlights the fundamental tension between abstraction purity and practical implementation in the ODB effort - whether commit graphs are core repository concepts or storage-specific optimizations. The thread remains at an architectural crossroads, with Steinhardt's concrete interface proposals likely to inform future discussions.
