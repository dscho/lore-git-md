Patrick Steinhardt's ongoing refactoring of commit graph handling for the pluggable ODB effort has sparked a fundamental architectural debate. The series aims to transition commit graph tracking to work with the new ODB infrastructure, but disagreement persists about whether commit graphs should be treated as repository-wide structures or storage-format-specific optimizations.

Junio Hamano and Derrick Stolee maintain that commit graphs serve as a fundamental repository-level cache for speeding up operations like `struct commit` population, regardless of storage backend. Stolee's latest response emphasizes that even alternative storage formats would benefit from this higher-level caching layer, citing Azure DevOps' efficient use of integer labels as an example. He argues the logical role of commit graphs transcends their current physical implementation tied to object storage.

Steinhardt counters that commit graphs are implementation details of specific storage formats (like packfiles) rather than core repository concepts. His refactoring preserves current behavior while preparing for backend-specific implementations, maintaining that alternative backends might provide equivalent functionality differently.

The discussion remains at an impasse between these competing visions: Steinhardt's push for storage-specific flexibility versus the repository-wide coherence model advocated by Hamano and Stolee. This debate exemplifies the broader challenges in the ODB abstraction effort, where conceptual purity must be balanced against practical infrastructure evolution. No clear resolution has emerged yet, leaving the series' future direction uncertain.
