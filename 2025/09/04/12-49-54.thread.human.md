Patrick Steinhardt's series refactoring commit graph handling for the pluggable ODB effort has sparked a deep architectural debate. The initial patches mechanically transitioned commit graph tracking to individual object sources (odb_source), but Junio Hamano and Derrick Stolee argue commit graphs are conceptually repository-wide - a "structured cache" that spans the entire object store despite physical storage location.

Steinhardt has now countered this view, maintaining that commit graphs are primarily a performance optimization for Git's current storage format rather than a fundamental concept. He argues alternative backends might provide similar functionality differently, and his changes merely prepare for future flexibility while maintaining current single-graph behavior. This positions commit graphs as implementation details of specific storage formats rather than intrinsic to Git's object model.

The discussion remains at an impasse between these views: repository-wide conceptual purity versus backend-specific implementation flexibility. While patches 1-5's mechanical cleanups have support, the core architectural question - whether commit graphs belong at the object_database or odb_source level - remains unresolved. This debate exemplifies the broader challenges in the pluggable ODB effort, where infrastructure changes must balance conceptual clarity with practical extensibility.
