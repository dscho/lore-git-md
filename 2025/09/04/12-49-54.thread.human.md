Patrick Steinhardt's series refactoring commit graph handling for the pluggable ODB effort has sparked a substantive discussion about the fundamental nature of commit graphs in Git's architecture. The latest patch (6/6) moves commit-graph storage to `struct odb_source`, treating graphs as implementation details of storage formats. Taylor Blau has raised important concerns about this approach, noting that while the graph structure itself may be storage-specific, generation numbers and Bloom filters provide semantic metadata that transcends any single backend.

The technical debate centers on two key points: whether the patch unintentionally changes behavior by allowing alternate ODB commit graphs where previously only the main store's graph was used, and whether generation numbers should be considered fundamental repository metadata (as Junio and Derrick Stolee argue) rather than backend implementation details. Blau makes a nuanced case that these features serve purposes beyond just optimizing packfile access.

While the mechanical refactoring proceeds uncontroversially, the architectural question remains open. Steinhardt plans to formalize his source-specific approach in a future design document, but the discussion has revealed deeper philosophical differences about how future storage backends should handle commit graph metadata. The series continues to advance the ODB abstraction work while leaving room for further discussion about the proper abstraction level for generation numbers and Bloom filters.
