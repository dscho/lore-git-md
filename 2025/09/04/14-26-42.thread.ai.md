RFC PATCH series introducing Rust infrastructure to Git core, now at v5 with 9 patches, maintains Junio C Hamano's ack while undergoing build system redesign. Authored by Patrick Steinhardt with varint subsystem proof-of-concept, CI modernization, and phased transition (optional in 2.52, default in 2.53, mandatory by 3.0). Current discussion focuses on LTS (Long-Term Support) repository management for platforms unable to adopt Rust when it becomes mandatory.

Technical developments expanded with clarified policy documentation flow:
- SHA-1/SHA-256 interoperability confirmed as requiring Rust dependency in Git 3.0, with single-hash operation remaining possible without Rust
- Build system transitioning to hybrid model with Newren's build_rust.sh wrapper and Phillip Wood's explicit disable instructions (WITH_RUST=NoThanks)
- Varint subsystem (varint.rs) confirmed as first mandatory Rust component in 3.0
- Policy document provenance clarified: originated in Elijah Newren's rust branch, modified by Ezekiel Smith before inclusion in series
- Junio Hamano seeks further clarity on modification review process and original authors' endorsement of changes
- Timeline estimates remain fluid (Rust mandatory in 3.0 after 1 year/4 cycles) with Hamano calling current plan "hopelessly optimistic" for some architectures
- Current platform blockers: m68k's 16-bit alignment (Glaubitz working) and hash interoperability limitations (SZEDER's concerns)

New LTS repository governance discussion from Steinhardt opposes Hamano's separate repository proposal, advocating for canonical repository hosting with:
1. External development on forges for contributor convenience
2. Mailing list review before final tagging in main repository
Key arguments against separation:
- Maintainer support needs (git-security@ access, mailing list coordination)
- Trust/oversight concerns with external forks
- User confusion and issue reporting fragmentation
- Release consistency and split history risks
- Hard fork prevention through official project umbrella
