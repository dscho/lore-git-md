RFC PATCH series introducing Rust infrastructure to Git core, now at v5 with 9 patches (consolidated from v4's 10), transitioning Rust from optional to mandatory by Git 3.0. Authored by Patrick Steinhardt, tracking meson implementation (v1), Makefile preparation (v2), Makefile integration (v3), varint subsystem conversion (v4/v5), final polish (v5), policy documentation (v5), CI modernization (v5), and now expanded CI testing (new patch). The foundational v1 patch establishes build system support for compiling Git with Rust components via Meson configuration, adding `Cargo.toml` and `src/lib.rs` as entry points with Rust 2018 edition compatibility for gcc-rs backend support. Key technical progression includes:

- Build system: Complete meson and Makefile integration with `WITH_RUST` toggle, Rust source tracking, and quiet build output. Patch 3 specifically adds Makefile support mirroring meson infrastructure from v1, introducing `rust` phony target, `$(RUST_LIB)`, `QUIET_CARGO`, `RUST_SOURCES`, and `CARGO_ARGS` for debug/release configurations. Build artifacts (`target/`, `Cargo.lock`) added to clean targets and `.gitignore`. Initial v1 implementation adds `cargo-meson.sh` wrapper (approved by Brian m. carlson) handling debug/release builds and output placement, with Meson rules for library compilation and Rust-native tests. Final v5 polish adds `Cargo.lock` to `make clean` target (addressing feedback from SZEDER Gábor and Junio C Hamano), marking build system work as complete. New v2 preparation patch reorders Makefile variable definitions (176 lines including `CFLAGS`, `LDFLAGS`, test flags) to appear after config.mak inclusion, enabling upcoming conditional compilation via `WITH_RUST` flag.

- CI modernization: Expanded patch converts obsolete "pedantic" CI job into Fedora-based build testing Meson with breaking changes enabled, adding distro coverage beyond Ubuntu and validating breaking changes flag needed for Rust integration. Updates GitHub Actions and GitLab CI configs to replace pedantic job with `fedora-breaking-changes-meson`, installing Meson/Ninja on Fedora and running tests in this configuration. New changes add `cargo` to dependency installation scripts for both Fedora and Ubuntu/Debian environments, and set `WITH_RUST=YesPlease` and `-Drust=enabled` flags in breaking-changes test execution. Strategically prepares for Rust testing across both build systems while maintaining existing coverage, now with explicit Rust toolchain validation.

- Type safety: Varint conversion (v4 5/9 and v5 5/9) standardizes on explicit integer widths (`uint64_t` for values, `uint8_t` for lengths) in dir.c, read-cache.c, varint.c, varint.h, replacing implicit types like `uintmax_t` and `int`. This mechanical change ensures platform independence and prepares for Rust reimplementation, noting varints are bounded (max 16 bytes encoded). Junio C Hamano accepted the technical approach while noting `uint8_t` for length is acceptable but not strictly necessary, anticipating future discussions about Rust's `u64` vs C's `uint64_t`. The v5 iteration implements Ezekiel Newren's suggestion with careful attention to maintaining existing logic while updating types (e.g., `int varint_len` -> `uint8_t varint_len`, `uintmax_t decode_varint()` -> `uint64_t decode_varint()`).

- Rust varint implementation: New patch introduces Rust version of varint subsystem (`src/varint.rs`) as test balloon for Rust integration, chosen for simplicity and isolation. Provides identical C-compatible interface via `#[no_mangle]` extern functions `decode_varint` and `encode_varint`, maintaining same overflow handling semantics. Uses `usize` for values and `u8` for lengths/buffers, with Rust's safer pointer operations (`std::ptr::copy_nonoverlapping`) while matching C behavior. Comprehensive tests verify edge cases including overflow conditions. Build system changes ensure Rust version is used when `WITH_RUST` enabled, falling back to C otherwise. Follows type safety improvements from earlier patches, demonstrating incremental porting approach for Rust/C interop.

- Build reporting: New v5 4/9 patch adds Rust status reporting to `git version --build-options` and `git bugreport` output via simple `#ifdef WITH_RUST` conditional in `help.c`. Reports "rust: enabled" or "rust: disabled" following same pattern as existing features like fsmonitor. Minimal 6-line change focused on debugging visibility during transition period where dual C/Rust implementations may coexist.

- Documentation: BreakingChanges document updated with corrected indentation and commit message typo fixes in v5. New policy documentation patch adds formal transition timeline section outlining three milestones: optional Rust (2.52), default-enabled (2.53), and mandatory (3.0 planned H2 next year). Clarifies "test balloon" period as temporary phase for distributor adaptation while maintaining mandatory direction. Details LTS plan for pre-3.0 releases (4 bugfix/6 security cycles) with Git project control over backports. Includes build flags (`WITH_RUST=YesPlease`, `-Drust=enabled`) and positions transition as project-controlled while allowing ecosystem extensions. Kristoffer Haugsbakk previously contributed formatting fixes for Rust adoption timeline section. Junio C Hamano continues questioning "test balloon" terminology given mandatory transition, while Patrick Steinhardt defends it as intentionally permissive language to encourage contributions, citing SHA-256 interoperability precedent.

Brian m. carlson's review of v4 verified compatibility with their SHA-256 interoperability series (93 patches), indicating general approval of technical approach ("looked reasonable") and mentioning potential follow-up contributions for Rust formatting and CI tooling. Maintained neutral stance on LTS model while emphasizing need for security team consensus. Patrick Steinhardt expressed willingness to assist with LTS implementation while reinforcing Git project ownership.
