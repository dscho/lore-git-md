Derrick Stolee provides important context about existing tooling: `git backfill` handles blobless clones (fetching missing blobs) but isn't optimized for treeless clones, where refilling trees would be expensive. Notes that `scalar clone` already implements blobless-by-default behavior, serving as Git's testing ground for new clone optimizations before they might graduate to mainline Git commands. This establishes Scalar's role as an incubator for clone optimizations while maintaining `git clone`'s backward compatibility.

Junio Hamano weighs in on feature adoption strategy, arguing against creating new commands like `git big-clone` for mature features. He advocates integrating proven optimizations into existing commands like `git clone` when ready, either as new options or smart defaults (with user consent). Hamano emphasizes discoverability through main commands rather than specialized variants, positioning Scalar as a testing ground where features can prove themselves before potentially becoming core Git functionality.

Patrick Steinhardt responds to the treeless clone discussion with technical analysis of tree backfilling challenges. Proposes a depth-based batching approach (root trees first, then level-by-level) but acknowledges it would still perform poorly compared to blob backfilling. Explores server-side assistance possibilities but concludes required information would be equivalent to having the trees themselves. Strongly recommends against treeless clones in practice, reinforcing Stolee's position about their impracticality for backfilling workflows.
