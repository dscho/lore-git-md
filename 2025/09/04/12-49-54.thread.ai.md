Patrick Steinhardt's 6-patch series refactoring commit graph handling for the pluggable ODB effort remains at a design crossroads, with fundamental architectural disagreement between repository-wide versus source-specific graph models. The series mechanically transitioned commit graph tracking from object_database to odb_source across commit-graph.[ch], odb.[ch], packfile.c, revision.c, blame.c, and bloom.c (-164/+167 lines total), with patches 1-5 establishing new access patterns and the sixth completing the architectural shift.

Junio Hamano and Derrick Stolee argue commit graphs logically span the entire object store, with Stolee characterizing them as a "structured cache" operating at repository level. Steinhardt counters that commit graphs are implementation details of specific storage formats (like packfiles) rather than fundamental repository concepts. In his latest response, Steinhardt clarifies his proposal isn't about changing commit object types but about allowing different storage formats for metadata like generation numbers and bloom filters, providing concrete examples where alternative storage (cloud databases, SQLite) might handle this metadata more efficiently.

The technical proposal centers on moving graph-related decisions into object source backends via three function pointers: 1) existence check for cached graph representations, 2) bloom filter/generation number loading, and 3) commit loading via cached representation. Steinhardt argues this source-specific approach better accommodates diverse storage needs while maintaining abstraction, though he acknowledges Stolee's repository-level graph handling alternative could work with potentially more complexity.

Key unresolved questions:
- Fundamental architectural choice between repository-wide vs source-specific graphs
- Reconciliation with broader ODB abstraction goals
- Need for design revisions to maintain cross-source graph coherence if adopting repository-wide model
- Whether commit graphs should be treated as fundamental or implementation-specific
- How to resolve the tension between physical storage implementation and logical caching role

The discussion has evolved to include concrete interface proposals, with Steinhardt hinting at an upcoming design document to formalize these ideas after completing two more patch series. The exchange exemplifies the careful balancing act in the ODB effort between abstraction purity and practical implementation concerns, with the core architectural tension remaining between Steinhardt's source-specific flexibility and Hamano/Stolee's repository-wide coherence model.
