Feature implementation for the `git-history` command series, specifically adding the `split` subcommand. This is patch 17/18 in the RFC v3 series, building on extensive preparatory work to enable flexible history editing operations inspired by Jujutsu (jj).

The `split` subcommand simplifies the complex process of splitting a commit into two parts by interactively selecting which changes to move into a new commit. The implementation handles several key aspects:

1. Interactive hunk selection using the existing add-patch infrastructure (now separated and enhanced in earlier patches)
2. Tree manipulation to create the split commits while preserving original authorship
3. Validation to prevent empty commits (either the split-out or remaining portion)
4. Pathspec support to limit which files are considered for splitting
5. Hook integration (prepare-commit-msg, post-commit, post-rewrite)
6. Comprehensive test coverage including edge cases (root commits, empty splits, merge commits)

Technical details include:
- Uses the new `run_add_p_index()` function from earlier patches for in-memory index operations
- Leverages the tree-based status collection added in previous infrastructure work
- Maintains the new post-rewrite hook mapping support (added in patch 16) to properly track rewritten commits
- Handles commit message editing with the same workflow as regular commits (including commit.verbose config)

The implementation appears thorough, with 468 lines of new tests covering various scenarios. This continues the series' pattern of careful, incremental development with strong test coverage. The change fits naturally with the existing `drop` and `reorder` subcommands, using the same underlying sequencer infrastructure.
