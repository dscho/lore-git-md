This is a discussion about the Rust infrastructure RFC, specifically addressing the proposal to make Rust mandatory in Git 3.0. Eric Sunshine raises concerns about the current "optional" approach to Rust adoption, arguing it doesn't function as a true test balloon since Git will silently fall back to C implementations without surfacing platform compatibility issues to maintainers.

Sunshine points out that traditional Git test balloons deliberately fail to compile when unsupported features are missing, forcing packagers to engage with the problem. The current Rust implementation's opt-in nature means many packagers may never attempt the Rust build path, leaving the project unaware of real-world compatibility issues. He suggests making Rust enabled by default with an opt-out mechanism would better serve the testing purpose.

The email also implicitly questions whether the project has enough data to justify the proposed mandatory Rust timeline, given that some packagers (like NonStop maintainers) have already signaled Rust support challenges. This feedback comes as part of the broader RFC discussion about introducing Rust infrastructure to Git core, where the third patch proposed adding a BreakingChanges.adoc section declaring Rust would become mandatory in Git 3.0 (estimated 2H 2026).

The exchange highlights a key tension in the transition strategy between gathering meaningful platform compatibility data and maintaining build flexibility during the experimental phase. Sunshine's critique suggests the current approach may not adequately pressure-test the Rust requirement before it becomes mandatory.
