This thread continues the discussion around introducing Rust infrastructure to Git, now focused on governance questions about the transition plan. The technical implementation is largely settled, with all 9 patches in the v6 series reviewed and CI-validated, including a varint subsystem proof-of-concept demonstrating mixed C/Rust compilation. The core disagreement now centers on how to handle the Rust mandate's flexibility provisions in BreakingChanges.adoc. Phillip Wood had endorsed these provisions as allowing Git to defer the Rust requirement if ecosystem readiness lags, similar to the reftable transition. However, Junio Hamano raises practical concerns about whether a truly breaking change can be deferred to a minor release without fundamentally altering its scope, suggesting the only viable path would be reducing the change's impact. He interprets the clause differently, seeing it more as a way to abandon optional Rust support if maintenance becomes burdensome rather than as a mechanism for graceful deferral.

This exchange occurs against the backdrop of earlier governance tensions around LTS branch management, where Hamano favors a decentralized "friendly fork" model while Patrick Steinhardt advocates a hybrid approach with canonical repository tagging. The technical work continues progressing toward phased adoption (optional in 2.52, default in 2.53, mandatory by 3.0), but this latest discussion highlights remaining questions about how versioning semantics should interact with major infrastructure transitions.
