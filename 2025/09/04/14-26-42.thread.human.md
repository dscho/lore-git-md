This RFC thread continues to evolve the discussion around introducing Rust infrastructure to Git's core, now at version 5 of the patch series with 9 patches. While Junio has given his ack for the general direction, significant redesign work remains - particularly around build system integration and platform support.

The latest development comes from SZEDER Gábor, who raises an important concern about how the Rust requirement (planned to become mandatory in Git 3.0) will interact with another major change coming in that release - the SHA-1/SHA-256 interoperability work. He points out that if SHA-256 interop features depend on Rust code, platforms that can't support Rust (and thus must use the proposed LTS release) would lose this critical functionality. This creates a potential gap for repository migrations between hash algorithms.

The thread shows the implementation ownership broadening, with Ezekiel Newren now taking lead on build system redesign and Windows support, while Patrick Steinhardt transitions to overseeing the overall roadmap. Several key areas remain in flux, including build system architecture (moving from Meson-first to a hybrid approach), Windows platform specifics, and dependency management. Distribution maintainers like Sam James have added important concerns about licensing audits for external crates and offline build requirements.

Notably, the project maintains its aggressive timeline (optional Rust in 2.52, default in 2.53, mandatory in 3.0) despite these open questions. The varint subsystem remains the validated proof-of-concept, while other technical components like crate structure and header generation continue to be refined. The discussion has expanded to include platform detection methods, cbindgen packaging verification, and formal policies for adding new crate dependencies.
