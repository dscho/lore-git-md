This RFC thread continues to evolve the discussion around introducing Rust infrastructure to Git core, now in its sixth iteration. The series, authored by Patrick Steinhardt with contributions from Ezekiel Smith and others, has reached technical completeness with all 9 patches validated by CI. The current focus has shifted from implementation details to governance questions around long-term maintenance and versioning policy.

Junio Hamano maintains his ack of the technical approach but is probing the practical implications of the proposed Rust mandate timeline (optional in 2.52, default in 2.53, mandatory by 3.0). A key sticking point is the management of LTS (Long-Term Support) branches - Hamano advocates for a clean fork model similar to Git for Windows, expressing concerns about endorsing maintainers who may lack deep Git expertise. Steinhardt, while agreeing to reword the flexibility clause in BreakingChanges.adoc, proposes a more integrated approach where distribution maintainers could collaborate with core contributors under canonical repository tags.

The latest email from Steinhardt suggests deferring detailed LTS handover decisions, removing specific language about the process from the documentation. This reflects an emerging pragmatic consensus that these questions are premature while the Rust transition is still in progress. Phillip Wood has endorsed the flexibility provisions as prudent risk mitigation, while Johannes Schindelin has suggested a lieutenant model for LTS maintenance.

On the technical front, all major blockers have been resolved - the varint subsystem proof-of-concept demonstrates mixed C/Rust compilation viability, the crate has been renamed from "git" to "gitcore", and Windows/MSVC build issues are clearly scoped for post-series resolution. What remains is finalizing the governance framework that will guide this significant architectural change through its phased rollout and long-term maintenance.
