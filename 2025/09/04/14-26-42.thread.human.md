This RFC thread explores introducing Rust infrastructure to Git core, now in its sixth iteration with all 9 patches complete. The technical implementation has matured, demonstrating mixed C/Rust compilation through a varint subsystem replacement, with CI validation across all build pathways. The series outlines a phased adoption plan (optional in 2.52, default in 2.53, mandatory by 3.0) and has Junio Hamano's conditional approval - he maintains his preference for a separate repository but agrees the Rust mandate could be revisited if ecosystem readiness lags, similar to the reftable transition precedent.

A new dimension has emerged in the governance discussion around LTS branches. Hamano advocates for a decentralized "friendly fork" model akin to Git for Windows, where competent maintainers would independently manage Rust-free LTS branches without requiring main project endorsement. Patrick Steinhardt expresses reservations about maintainer quality in this model, proposing instead a hybrid approach where external LTS development would undergo mailing list review before final tagging in the canonical repository. Hamano counters that this undermines the very decentralization the model requires.

While the technical implementation continues progressing toward potential inclusion in Git 2.52, this governance question about LTS management remains unresolved. The exchange reveals differing philosophies: Hamano's trust in decentralized competent maintainers versus Steinhardt's preference for centralized quality control. This tension between project control and ecosystem diversity will need resolution as the Rust adoption plan moves forward.
