This is a follow-up discussion in the performance optimization thread comparing data structures for Git metadata storage, specifically regarding the `git describe` optimization using oidset versus khash approaches.

Jeff King responds to René Scharfe's observation about potentially using raw commit indexes instead of commit objects in the khash implementation. He acknowledges the theoretical possibility of using just uint32_t indexes for further memory reduction, noting this would align with commit-slab's approach of direct indexing. However, he points out this would require significant architectural changes (replacing object pointers with indexes throughout) for minimal measured performance benefit.

The exchange confirms the oidset solution (already approved in v2) remains the preferred approach, with Jeff King explicitly stating satisfaction with this resolution. The discussion highlights the broader context of Git's object storage model, where sequential allocation enables various indexing strategies, though most remain theoretical given the current implementation tradeoffs.

Key technical points:
- Commit index-based hashing would require pervasive changes to index-based addressing
- Performance measurements didn't justify the more radical approach
- Oidset solution maintains the 1.4x speedup while using standard Git infrastructure
- Thread's security hardening conclusions remain unchanged by this tangent
