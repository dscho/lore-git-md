This is a reply in the ongoing thread about making Rust mandatory in Git 3.0. Eric Sunshine raises concerns about the effectiveness of the current "test balloon" approach for Rust adoption, arguing that the optional nature of the initial implementation means it won't properly surface platform compatibility issues. He contrasts this with Git's historical use of test balloons that would fail to build on unsupported platforms, forcing packagers to engage with the project.

The key technical critique is that the current implementation (where Git silently falls back to C when Rust isn't available) won't generate the necessary feedback from packagers, especially those who may not be following the mailing list discussions. Sunshine suggests making Rust enabled by default with an opt-out mechanism as a more effective way to test platform readiness.

This reply doesn't introduce new technical elements but focuses on the strategic approach to Rust adoption. It references known platform concerns (particularly from NonStop maintainers) and suggests the current implementation may not adequately address them. The discussion continues to center on balancing forward progress with ecosystem impact, with the mandatory Rust timeline (2H 2026) and LTS version (2.52) remaining key points of consideration.
