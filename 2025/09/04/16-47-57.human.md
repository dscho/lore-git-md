This is a discussion about partial clone defaults and discoverability in the ongoing thread about making blobless clones more user-friendly.

Junio Hamano responds to Derrick Stolee's suggestion about a potential `git big-clone` command by arguing that new features should ultimately be integrated into mainline Git commands rather than living as separate tools. He points out that a dedicated `big-clone` command would suffer from the same discoverability issues as `scalar clone` currently does. 

Hamano suggests that mature features from experimental areas like Scalar should be incorporated into `git clone` itself, either as new options or potentially as automatic optimizations (with user consent) based on repository size. This reflects Git's philosophy of gradually promoting proven features from experimental to core functionality.

The exchange highlights the tension between maintaining backward compatibility in core Git` commands while still making new optimizations accessible to users. Hamano's position leans toward eventual integration rather than maintaining parallel commands, though the details of how and when to do this remain open for discussion.
