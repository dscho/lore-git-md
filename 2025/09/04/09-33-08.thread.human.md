This thread explores making blobless clones (where only commit and tree objects are fetched initially) the default behavior in Git, building on existing `--filter=blob:none` functionality. The proposal includes new commands to fetch missing blobs with progress tracking and convert between full and partial clones. 

Derrick Stolee and Patrick Steinhardt have established key technical boundaries: blobless clones (already implemented in `scalar clone`) are practical for general use with `git backfill` handling missing blobs, while treeless clones are only viable for CI environments where fast cloning outweighs the cost of later tree fetches. Junio Hamano advocates integrating proven optimizations into main Git commands rather than creating new ones, using Scalar as a testing ground.

A new concern has emerged from Konstantin Ryabitsev, who warns that blobless clones might increase server load similarly to shallow clones, as they can't use pre-generated packfiles. This infrastructure consideration adds an important counterpoint to the client-side optimizations discussed so far, suggesting the default behavior change needs careful evaluation of server impacts.

The discussion has converged on treeless clones being CI-only, with blobless clones as the primary optimization path, but now must also weigh server resource implications. Open questions remain about how to surface these optimizations in core Git commands while maintaining backward compatibility and server stability.
