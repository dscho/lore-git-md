This thread explores making partial clones more user-friendly, with a focus on blobless clones (which omit file contents initially) as a potential default for `git clone`. The discussion has clarified that while treeless clones (which omit directory structures) have limited use in CI environments where speed matters more than history access, blobless clones are the more broadly useful optimization for development workflows.

Derrick Stolee provided important context about existing tooling, noting that `git backfill` handles blobless clones well while `scalar clone` already implements blobless-by-default behavior as a testing ground for optimizations. Junio Hamano weighed in on feature strategy, advocating for integrating proven optimizations into main commands rather than creating specialized variants. Patrick Steinhardt analyzed the technical challenges of treeless clones, ultimately agreeing with Stolee that they're only practical for CI builds where fast cloning outweighs the need for path history access.

The discussion has converged on several points: blobless clones are the primary optimization path for general use, treeless clones have narrow CI applicability, and Scalar serves as an incubator for features that may later graduate to core Git. Open questions remain about how to make these optimizations more discoverable and when they might become default behaviors in mainline Git.
