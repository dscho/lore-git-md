Technical response from Brian Carlson addressing Rust platform compatibility concerns in the ongoing xdiff Rust port discussion. This email directly counters Patrick Steinhardt's proposal to use older Rust versions for broader platform support, providing detailed technical arguments about compiler and standard library dependencies.

Carlson makes several key technical points:
1. gccrs targeting Rust 1.49 won't expand platform support because it inherits the same standard library limitations as Rust 1.49, meaning newer platforms like Apache NuttX remain unsupported regardless of compiler choice
2. LLVM's cross-compilation capabilities actually make it more flexible than GCC for porting to new platforms
3. Older Rust versions (like 1.49) would break essential FFI tools like bindgen/cbindgen, increasing risk of cross-language bugs especially on less common architectures
4. The project has had multiple public discussions about Rust adoption since at least the 2024 Contributor Summit, making this transition far from "out of nowhere"

The email provides concrete examples from Carlson's professional experience where Rust tooling (particularly bindgen) prevented serious compatibility issues during a C-to-Rust migration. It also notes several real-world Rust adoptions (GNOME's librsvg2, Python's cryptography package) that faced similar platform concerns but ultimately succeeded.

Carlson strongly opposes making Rust optional, arguing this would create unsustainable maintenance burdens and negate Rust's safety benefits. The response includes a previously proposed policy position that mandatory Rust adoption is necessary to achieve the project's security and maintainability goals.

Platform-specific details mentioned:
- Current Debian stable ships Rust 1.48 (five years old)
- LLVM already supports AIX, Solaris, and QNX through recent porting efforts
- GCC maintains support for DEC Alpha and IA64 where LLVM does not
- gccrs's Rust 1.49 target would miss modern platform additions

The email reinforces Carlson's consistent position that platform maintainers should adapt to Rust rather than holding back adoption, while acknowledging the technical work required for less common architectures. It concludes by referencing the unanimous 2024 Contributor Summit decision to adopt Rust, suggesting the current debate is about implementation rather than principle.
