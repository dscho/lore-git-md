[RFC] Git patch workflow optimization discussion initiated by maintainer Junio C Hamano, analyzing bottlenecks in current patch lifecycle with focus on delays between 'seen' and 'next' branch transitions. Thread examines four recent merged topics showing cases where patches remained in 'seen' despite readiness, identifying maintainer bandwidth as primary constraint. Taylor Blau proposed requiring at least one positive "ack" from another contributor before merging, providing a patch to Documentation/SubmittingPatches to formalize this. Junio Hamano responds with concerns about defining qualified reviewers, noting edge cases like first-time contributors giving drive-by acks or known-sloppy developers rubber-stamping patches too quickly, suggesting tighter language focusing on reviewers who actively helped polish patches while remaining skeptical about preventing poor-quality acks. Taylor Blau counters with a REVIEWERS file proposal, modeled after GitHub's CODEOWNERS but scaled for Git's smaller size, suggesting it could start with just the maintainer and expand to include trusted reviewers over time. He clarifies Google's internal Git usage (based on 'next') wouldn't help validate shorter 'next' periods due to their slower update cadence. On maintainer expansion, Junio agrees Git isn't large enough for subsystem maintainers and acknowledges coordination overhead of maintainer quorum model, clarifying his earlier suggestion was more thought experiment than concrete proposal. Kristoffer Haugsbakk now proposes shortening the 'next' branch integration period specifically for documentation-only changes, arguing they pose lower risk than code changes due to reduced conflict potential and impact of any missed issues (rendering problems rather than functional bugs). The proposal maintains existing review standards but suggests documentation changes could safely graduate from 'next' to 'master' faster than the standard 7-day period. It acknowledges potential downsides like missing late doc-diff feedback but considers these acceptable tradeoffs. Kristoffer Haugsbakk also responds to Taylor Blau's concerns about limited testing of 'next' by suggesting large Git-using projects could theoretically test against both 'next' and 'master' branches, though this remains a conceptual suggestion without implementation details or incentives analysis. Ben Knoble builds on this testing suggestion by proposing a Rust-inspired "crater" approach where known major Git users would run their test suites against Git's development branches (both 'next' and 'master') on every commit, similar to Rust's regression detection system. This represents an expansion of testing discussion while maintaining the conceptual nature of proposals. Junio Hamano now acknowledges Kristoffer Haugsbakk's documentation change proposal, confirming maintainers already exercise discretion by sometimes sending trivial typo fixes directly to 'master' rather than through 'next', validating the risk assessment behind documentation-specific exceptions while showing pragmatic case-by-case approach currently in use. The thread maintains data-driven tone while shifting focus to incentivizing quality review participation and improving testing coverage.
