Bugfix investigation with platform-specific implications. Eric Sunshine confirms Nikolay Shustov's suspicion about trailing dots in filenames being the likely root cause of the `git merge --no-ff` failure on Windows. The email cites Microsoft documentation explicitly warning against filenames ending with periods, noting that while the filesystem may support them, Windows shell and UI do not, causing functions like `open()` and `fopen()` to fail when Git attempts to access such files.

This connects directly to the earlier diagnostic information about files imported from Perforce via `git p4` on Windows, where the original filenames contained trailing dots. The manual renaming workaround Nikolay employed (changing "/something/blah" to "/something/blah.") appears to have triggered the underlying platform limitation. The confirmation that another `git p4` repository without such filenames works fine further strengthens this correlation.

The email doesn't propose a fix but provides authoritative documentation that explains why the issue occurs specifically on Windows. This moves the investigation from hypothesis to confirmed root cause analysis, narrowing the problem to Windows' handling of dot-terminated filenames during Git's internal stash operations during merges. The next steps would likely involve either modifying Git's Windows path handling to normalize such filenames or documenting this as a known limitation with `git p4` imports on Windows.
