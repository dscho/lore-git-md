This is a bugfix discussion thread about Windows filesystem behavior with dot-terminated filenames affecting Git operations.

Eric Sunshine confirms Nikolay Shustov's suspicion that dot-terminated filenames are the likely culprit behind the `git merge --no-ff` failure. He cites Microsoft documentation explicitly warning against ending filenames with periods on Windows, noting that while the filesystem may support such names, Windows shell and UI do not. The technical explanation is that Windows system calls like `open()` and `fopen()` will fail when given dot-terminated filenames.

The context here is that these problematic filenames originated from a Perforce depot and were imported via `git p4` on Windows, where they manifested as duplicate entries (both removed and untracked) until manually corrected. This appears to be a known issue with Windows filesystem handling, though Git's behavior in this edge case could potentially be improved.

The thread is narrowing in on a specific platform-specific edge case that affects Git's stash handling during merges. While not yet proposing a fix, this confirmation of the root cause moves the discussion from diagnosis toward potential solutions. The next steps would likely involve determining whether Git should handle these filenames more gracefully on Windows or explicitly warn about them during operations like `git p4` imports.
