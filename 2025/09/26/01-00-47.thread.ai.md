This thread discusses the deprecated `git whatchanged` command and migration paths to modern alternatives, initiated by Kristoffer Haugsbakk. The original discussion established that `git whatchanged` is a legacy wrapper around `git log` with specific defaults, and proposed concrete replacement commands: `git log --no-merges --raw` for direct output parity, with `--stat` or `--name-only` as more readable alternatives. Junio C Hamano has weighed in with a practical refinement, suggesting the `--no-merges` option may not be worth including in the standard replacement recipe due to verbosity concerns, implying `git log --raw` might suffice for most users.

Neal Miller provides a user experience data point showing that their specific `git whatchanged` alias using `-p --abbrev-commit --pretty=medium` can be directly replaced with `git log` using identical flags, demonstrating that some existing configurations may not need the `--raw` or `--no-merges` options under discussion. This case is specific to patch-style output (`-p`) rather than the default `whatchanged` behavior, but validates the flexibility of the migration path.

The thread shows consensus that `git whatchanged` should be phased out in favor of more flexible `git log` invocations, with ongoing discussion focused on command-line ergonomics. Current alternatives under consideration are: `--raw` (with or without `--no-merges`), `--stat`, `--name-only`, and case-specific flag preservation as demonstrated by Neal. Junio's position introduces a potentially impactful simplification to the standard recommendation, while Neal's example shows that some users may need only a command name change. No technical objections to deprecation have been raised, and the discussion remains focused on optimizing the transition experience across different usage patterns.
