This is a discussion about the ongoing debate around the new `git refs get` plumbing command, specifically addressing its discoverability and architectural placement. Junio C Hamano responds to Ben Knoble's concerns about the new subcommand's target audience and questions the consolidation rationale.

Junio challenges the argument that users will naturally discover `git-refs` over time, pointing out the same effort could make `show-ref` more discoverable instead. He digs deeper into the fundamental question of why Git needs this consolidation, suggesting it might be "make-work" without clear benefits, referencing the xkcd standards comic about proliferating standards. The email raises architectural concerns about whether creating a new command family is justified versus extending existing tools like `show-ref`.

Key technical considerations highlighted include: the tension between creating new command families versus extending existing ones, the practical challenges of script writer discoverability, and questioning whether the consolidation goal itself provides sufficient user benefit. Junio's skepticism about the architectural direction contrasts with Patrick Steinhardt's earlier defense of the `git-refs` approach as completing the reference-handling operation set. The discussion remains unresolved on whether this functionality belongs in a new command or should extend `show-ref`.
