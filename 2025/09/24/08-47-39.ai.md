This is a discussion about the behavior of `git rebase -i`'s fixup command with `-C` flag, following Junio Hamano's authoritative rejection of Mathias Rav's proposed change to preserve current commit's author info.

Johannes Sixt ("Hannes") presents a counter-use-case where the proposed behavior would be useful: when a commit that was originally a fixup for a later commit needs to be reordered but causes conflicts. He suggests this isn't about fixing previous commits (which aligns with Junio's stance on preserving original authorship) but rather about properly attributing work that was misordered. Hannes proposes extending `squash` with similar metadata control as an alternative path forward.

Key technical points raised:
- Reiterates the core disagreement about when authorship should be preserved vs. updated
- Introduces new scenario of "reverse fixups" where early commits actually belong to later work
- Suggests `squash` command as alternative vehicle for metadata control features
- Acknowledges Junio's semantic argument about "fixup" meaning while proposing alternative interpretation

This keeps the discussion alive despite Junio's clear position, offering a concrete alternative implementation path (`squash` extension) and new motivating scenario (conflict-avoiding reordering of misordered fixups). The thread now has both a maintainer's design principle and a contributor's proposed alternative approach in play.
