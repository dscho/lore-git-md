This is a discussion about Git release notification mechanisms, specifically responding to a proposal for a dedicated "git-announce" mailing list. Christian Couder explains the project's preference for keeping all communications on the main git@vger.kernel.org list rather than creating specialized sub-lists.

The response highlights two key reasons against splitting to a separate announcement list: 1) maintaining community cohesion by avoiding fragmentation across multiple lists, and 2) the subjective nature of what constitutes "important" announcements (like Git for Windows updates or Git Rev News) that would still require individual filtering even with a dedicated release notes list.

This continues the thread's exploration of release notification options, now addressing the human/organizational aspects of list management rather than the technical solutions previously discussed. The reply suggests the project values unified community discussion over specialized notification channels, even if that means some recipients need to filter messages themselves.
