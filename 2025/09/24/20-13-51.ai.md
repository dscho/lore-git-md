This is a technical discussion thread within the reftable fsck validation series, specifically addressing patch 4/8 which handles update index validation in reftable stacks. The conversation focuses on terminology refinement for describing index ordering requirements.

Karthik Nayak responds to Junio Hamano's suggestion to use "monotonically increasing" instead of "sequential" to describe update index ordering, noting that the former might incorrectly imply equality is allowed between adjacent tables' indices. Karthik proposes "ascending order" as an alternative that better captures the strict inequality requirement (prev_table.max_update_index < cur_table.min_update_index).

The exchange demonstrates careful attention to technical precision in documentation, building on earlier discussions where Patrick Steinhardt identified that compaction scenarios could legitimately produce non-consecutive indices. This led to relaxing the validation from requiring strictly consecutive indices to allowing gaps while maintaining ordering. The current discussion refines how to best describe this relaxed validation in the code and documentation.

- The validation enforces prev_table.max_update_index < cur_table.min_update_index
- "Sequential" was deemed misleading after allowing gaps
- "Monotonically increasing" might incorrectly permit equality
- "Ascending order" is proposed as the clearest alternative
