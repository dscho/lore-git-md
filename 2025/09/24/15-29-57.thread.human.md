This thread began with a report of a subtle `git stash -u` edge case where moving and modifying a tracked file (demonstrated with `d1/f` to `d2/f`) caused the stash to only record the deletion, not the untracked version. D. Ben Knoble explained the mechanics: stashes store untracked files in stash^3, and `git stash show` hides them by default unless `-u` is used. He provided recovery methods and noted this exposes an edge case for moved+modified files.

Hosam Aly followed up, clarifying their real-world context involved Java file moves with package changes. They proposed changing the default of `stash.showIncludeUntracked` from false to true, arguing the current behavior is counterintuitive compared to `git status` and particularly confusing when a stash contains only untracked files (making `git stash show` appear empty).

Maintainer Junio C Hamano has now responded, acknowledging the usability argument. While generally reluctant to change long-standing defaults, he shows unusual sympathy for this case, noting two key constraints: such a change would typically require a major version bump (Git 3.0) due to potential widespread effects, and users already signal they care about untracked files by using `-u`. He even suggests the configuration option itself might have been unnecessary. The discussion has shifted from the original edge case to broader questions about interface design and change management, with the possibility of a default change remaining open but requiring careful version compatibility consideration.
