`git stash` bug report and feature discussion: untracked files handling during complex operations and default visibility. Original issue demonstrated data loss scenario where moving+modifying a tracked file (`d1/f` to `d2/f`) caused `git stash -u` to only record the deletion, not the untracked version. D. Ben Knoble explained mechanics: stashes store untracked files in stash^3, why `git stash show` without `-u` hides them, and provided recovery methods (`git restore -SW -s stash^3 d2/f`, `git stash branch`). Current behavior preserves new content in working tree while index keeps original, exposing a stash edge case for moved+modified files.

Hosam Aly follows up, acknowledging initial misunderstanding of `stash show` behavior but clarifying real-world context involved Java file moves with package changes. They propose changing `stash.showIncludeUntracked` default from false to true, arguing current behavior is counterintuitive compared to `git status` and particularly confusing when a stash contains only untracked files (making `git stash show` appear empty). The feature request focuses on usability, noting the configuration option exists but isn't the default.

Maintainer Junio C Hamano responds to the default change proposal, acknowledging usability arguments while noting two key constraints: 1) such behavioral changes typically require a major version bump (Git 3.0) due to potential widespread impact, and 2) users explicitly opt-in to stashing untracked files (via `-u`) already signals they care about these files. While maintaining reluctance to change long-standing defaults, Hamano expresses unusual sympathy for this case, even suggesting the configuration option itself might have been unnecessary ("I am actually tempted to argue that the presence of the configuration variable...is a bug"). The response keeps open the possibility of changing the default while highlighting version compatibility considerations. Thread maintains technical context about stash storage format (stash^3 for untracked files) while shifting toward policy questions about interface design and change management.
