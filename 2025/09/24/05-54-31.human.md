This is a technical discussion about update index validation in the reftable fsck series. Patrick Steinhardt raises concerns about patch 4/8's strict sequentiality check for table update indices in the reftable stack.

Patrick questions whether requiring gapless sequence numbers (where each table's min_update_index must be exactly prev_table->max_update_index + 1) is too restrictive. He provides a concrete example where compaction could legitimately create gaps - when deleting intermediate records during compaction, the resulting table might truthfully report a higher min_update_index than the previous table's max_update_index.

The core suggestion is to relax the validation to only enforce that new tables have strictly increasing update indices (min_update_index > prev_table->max_update_index) rather than requiring gapless continuity. This would better accommodate valid compaction scenarios while still catching truly corrupt or out-of-order tables.

This appears to be a thoughtful technical critique from someone familiar with reftable's compaction behavior. The proposed relaxation seems reasonable given the example, though it would need evaluation by the patch author (Karthik Nayak) to confirm whether the current strict check was intentionally guarding against other cases.
