Subject: rebase behavior with semantically dependent commits. Thread type: feature proposal and workflow discussion. Originating author: anthem87 (Antonio Mennillo).

Core problem: Rebasing semantically dependent commits (interface changes followed by implementations) creates repeated conflict resolution when changes appear across multiple commits. Current rebase workflow forces users to resolve similar conflicts multiple times, particularly for semantic conflicts where `git rerere` (which only remembers textual resolutions) is ineffective.

Current status: Original `git-rebase-clean` tool (AGPL-3.0-or-later) proposed squashing before rebase was rejected by brian m. carlson as unacceptable history loss. Implementation includes automated commit reconstruction, edge case handling, and 23 passing tests.

Key technical details: New approach first squashes commits to resolve conflicts with full context, then replays saved diffs to reconstruct original commit structure. Handles empty commits and binary files. Targets semantic conflicts where interface changes invalidate dependent implementations - a scenario `git rerere` cannot address. Repository remains at https://github.com/anthem87/clean-rebase with production use history (5+ months, 30-40 branches).
