Junio C Hamano's response in this thread about `git status` command suggestions provides the maintainer perspective on why different unstaging commands are suggested before versus after the first commit. 

The email confirms the technical necessity behind the different suggestions, explaining that before any commit exists, `git rm --cached` is the only viable option since there's no commit to restore from. After the first commit, `git restore --staged` becomes possible and more appropriate as it can reset files to their HEAD state rather than completely removing them from tracking. 

Hamano emphasizes this isn't an inconsistency but rather the correct behavior given the underlying repository state - the commands suggested are precisely what would be needed in each scenario. The response implies this is working as intended rather than being a UX issue to fix, though it doesn't directly address whether the documentation could better explain this distinction to users.

Key technical points reinforced:
- Before first commit: No HEAD exists, so `rm --cached` is only option to unstage while preserving worktree file
- After first commit: `restore --staged` can reference HEAD to properly unstage while maintaining file tracking
- Using `rm --cached` post-commit would regress file tracking state rather than just unstaging changes

The response positions this as an inherent technical distinction rather than a UX inconsistency, suggesting the current behavior is correct. This likely closes the discussion unless someone proposes concrete documentation improvements or challenges the technical assessment.
