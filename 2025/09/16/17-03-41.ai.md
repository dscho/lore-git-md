This is a follow-up in the ongoing discussion about `git clone --shallow-exclude` limitations, specifically addressing the GitLab CI use case. D. Ben Knoble responds to Philipp Hahn's inquiry about why commit-hash-based exclusion is considered "flawed" in the implementation.

The email suggests an alternative approach for the GitLab CI scenario: instead of trying to use `--shallow-exclude` with commit hashes, Knoble proposes using a blobless clone combined with a targeted `git rev-list` operation (specifically `master..topic` to get the commits of interest). This would fetch more commits than strictly necessary but would avoid the shallow exclusion limitations while still being more efficient than a full clone.

The response highlights the practical trade-offs in the CI context - while not as precise as the desired shallow exclusion by commit hash, a blobless clone may provide a workable solution that balances clone size with the need to access specific commit histories. This suggests the discussion is moving toward exploring alternative solutions rather than just documenting limitations.

Key technical elements mentioned:
- The `git rev-list master..topic` range syntax
- Blobless clones as a potentially lighter alternative
- Implicit performance comparison between full clones, shallow clones, and blobless clones

The email doesn't directly address the technical reasons why commit-hash exclusion is flawed, but offers a pragmatic alternative path forward for the specific CI use case. This keeps the thread focused on real-world solutions while the deeper protocol limitations remain an open question.
