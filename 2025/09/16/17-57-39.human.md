This is a follow-up in the ongoing discussion about `git clone --shallow-exclude` limitations in CI pipelines. Philipp Hahn responds to D. Ben Knoble's suggestion about using `git rev-list` by explaining why it fails in GitLab's "Merged Result Pipelines" scenario. The temporary merge commit created by GitLab causes `master..temp` to only include the merge commit itself, missing the topic branch commits that are actually needed.

Hahn also identifies another issue with `--shallow-exclude` - when excluding commit E, commit A becomes a root commit containing all files up to that point, rather than maintaining the original commit structure. This creates problems for workflows that depend on the exact commit history.

The discussion explores two potential solutions: continuing to refine shallow exclusion behavior versus adopting blobless clones (`--filter=blob:none`) as an alternative approach. While blobless clones would fetch more commits than strictly needed, they may provide a more reliable solution for CI pipelines while still being more efficient than full clones. The thread continues to explore the tradeoffs between these approaches for real-world CI use cases.
