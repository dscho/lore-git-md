This is a discussion about shallow clone limitations in GitLab CI workflows, continuing the thread about `--shallow-exclude` behavior. D. Ben Knoble responds to Philipp Hahn's question about why commit hash exclusion is considered "flawed" in Git's implementation.

The email suggests an alternative approach for Philipp's GitLab CI use case where linters need access to commits between the fork point and topic branch (master..topic). Instead of trying to use `--shallow-exclude`, Knoble proposes using a blobless clone combined with later fetching specific commits, acknowledging this would fetch more commits than strictly necessary but should still be more efficient than a full clone.

The response highlights the ongoing challenge of finding optimal cloning strategies for CI pipelines that need access to specific commit ranges. While not addressing the core protocol limitation directly, it offers a practical workaround that might help in Philipp's specific scenario. The suggestion indicates that the community is actively thinking about alternative solutions to the shallow clone limitations.
