This is a user experience question about Scalar's configuration behavior. Matthew Hughes reports confusion after running `scalar register` in a repository, later discovering it had silently set several configuration options (like `status.aheadBehind false`) without clear indication of their origin. He suggests either improving documentation or having `scalar register` annotate the config changes it makes.

The core issue is discoverability - users may not realize which config values come from Scalar versus their own settings. The question touches on Git's broader configuration management challenges, where the provenance of settings isn't always clear. The proposed solutions (documentation vs. config comments) represent different approaches to making Scalar's behavior more transparent.

Key technical details mentioned:
- Specific config option modified: `status.aheadBehind`
- Scalar command involved: `scalar register`
- Implicit behavior: silently setting multiple config values

This appears to be a genuine usability concern that could spark discussion about Scalar's configuration strategy and Git's config management patterns more generally. The question is well-framed and identifies a concrete pain point that others may have encountered.
