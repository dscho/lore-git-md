This is a response in an ongoing discussion about handling semantically dependent commits during rebase. Brian m. carlson provides feedback on Antonio Mennillo's proposed `git-rebase-clean` tool.

The response makes two key points: First, it suggests that semantically dependent changes should ideally be grouped into atomic commits that compile and pass tests together, rather than being split across multiple commits. Second, it points to `git rerere` as an existing solution for remembering conflict resolutions during complex rebases.

Carlson expresses skepticism about the squash-then-rebase approach proposed by Mennillo, stating that most Git users would consider the loss of commit history granularity unacceptable. The tone is constructive but firm in rejecting the proposed workflow as something the Git project would want to encourage.

This moves the discussion forward by clarifying core Git expectations around commit atomicity and pointing to existing tooling (`rerere`) that addresses part of the problem. The response doesn't engage with the specific implementation of `git-rebase-clean` but rather questions its fundamental premise.
