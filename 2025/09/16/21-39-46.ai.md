This is a feature proposal and workflow discussion about rebase behavior with semantically dependent commits. The email introduces a userland tool called `git-rebase-clean` that addresses a specific pain point in Git's rebase workflow.

The core issue describes a "semantic conflict cascade" where interdependent commits (like interface changes followed by implementations) trigger repeated conflicts during rebase, forcing users to re-resolve similar conflicts across multiple commits. The proposed solution is a workflow tool that first squashes the feature branch into a single commit before rebasing, trading commit granularity for atomic conflict resolution. The tool has been used in production for 5+ months across 30-40 feature branches, showing reduced conflict resolution time, though with some IDE-specific edge cases around conflict marker handling.

Key technical details include: the tool's repository at https://github.com/anthem87/clean-rebase, its AGPL-3.0-or-later licensing (with historical MIT versions), and observed IDE limitations with IntelliJ's conflict marker handling. The author poses three main questions to the community: whether the semantic dependency issue is a known/expected limitation, if the squash-then-rebase pattern merits documentation in Git's official guidance, and whether there are existing internals or extensions that handle dependent commits more gracefully.

The email also includes a licensing clarification note about the transition from MIT to AGPL, which may spark discussion about contribution guidelines though the author notes this may be out of scope. The proposal appears well-motivated with real-world usage data, though it introduces a trade-off between history granularity and conflict resolution simplicity that may be controversial among Git users who value fine-grained commit preservation. The tool's approach resembles an extreme form of the "rebase -i" squash workflow, but packaged as an automated solution.
