This is a follow-up discussion in the command deprecation framework series, specifically addressing an edge case with the `whatchanged` command removal when built with `WITH_BREAKING_CHANGES=YesPlease`. Jeff King identifies a Makefile issue where `git-whatchanged` is still being built despite being removed from the builtin table, causing confusing "cannot handle as builtin" errors. The executable's presence also prevents proper alias shadowing since the command is treated as an external command rather than a deprecated builtin.

Key technical points:
- The Makefile incorrectly includes `git-whatchanged` in `BUILT_INS` even with `WITH_BREAKING_CHANGES`
- This creates a stale executable that conflicts with the deprecation system
- The error occurs because the command is missing from the builtin table entirely rather than being marked deprecated
- Alias shadowing fails because the system sees `whatchanged` as an external command
- The solution involves conditional Makefile changes and dealing with leftover executables

The discussion reveals an integration gap between the deprecation system and the build system, where removal from the builtin table wasn't properly coordinated with the Makefile changes. This affects both direct command execution and alias behavior, contradicting the intended transition path for removed commands. The issue appears resolvable through Makefile adjustments and cleanup of stale executables.
