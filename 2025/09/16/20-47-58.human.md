This is a follow-up discussion in the command deprecation framework series, specifically addressing edge cases in alias handling of deprecated commands. Kristoffer Haugsbakk responds to Junio Hamano's observation about test failures when `WITH_BREAKING_CHANGES=YesPlease` is set.

The key issue revolves around the behavior of mutually recursive aliases involving deprecated commands (`whatchanged` and `pack-redundant`). The test expects verbose alias loop detection output, but instead gets a simpler "cannot handle as builtin" error after the commands were removed in commit 07572f220a8. 

Haugsbakk notes this behavior seems correct for direct command invocation, but questions why the same error occurs when trying to alias `whatchanged` to another command like `status`. This contradicts the stated goal of allowing users to create their own aliases for deprecated commands. The discussion suggests there may be an unintended side effect in how removed commands interact with the alias system.

This represents the final integration issue for the otherwise complete deprecation framework series. The resolution will determine whether test expectations need updating or if the behavior needs adjustment to properly support command aliasing after removal.
