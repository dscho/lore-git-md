This thread explores how to handle semantically dependent commits during rebase operations, where changes in one commit (like an interface change) require corresponding updates in later commits (like implementations). The original proposal from anthem87 suggested a `git-rebase-clean` tool that would first squash feature branches into a single commit before rebasing, trading commit granularity for simpler conflict resolution. The tool has seen production use but raises questions about Git's philosophy around history preservation.

Brian m. carlson has now weighed in, representing what appears to be a common Git community perspective. He argues that semantically related changes should ideally be atomic commits that work together, suggesting the root issue might be in how changes are initially structured. He points to `git rerere` (which remembers conflict resolutions) as an existing solution and strongly indicates that the squash-then-rebase approach would be rejected by the community due to its loss of history granularity, calling this trade-off "unacceptable."

The discussion now stands at a philosophical crossroads - between preserving detailed commit history (a core Git value) and simplifying conflict resolution for dependent changes. While anthem87's tool has shown practical benefits in some environments, the response suggests the Git community is unlikely to adopt this approach officially. The thread leaves open whether there might be alternative solutions within Git's existing tooling that could address the underlying issue without sacrificing history granularity.
