This is a follow-up discussion about the limitations of `--shallow-exclude` with commit hashes, prompted by a real-world GitLab CI use case. The email comes from Philipp Hahn who is trying to optimize shallow clones for merge request pipelines.

The thread had previously established that excluding by branch name works as designed (producing "no commits selected" when appropriate) while excluding by commit hash was buggy but fixed in Git 2.48. Philipp now asks why commit hash exclusion remains unsupported, presenting a concrete scenario where branch name exclusion fails for GitLab's "Merged Result Pipelines" feature. In these pipelines, the base commit (E in the diagram) is no longer referenced by any branch after a temporary merge, making commit hash exclusion the only viable approach.

Key technical details include:
- The problematic workflow involves GitLab CI pipelines that need to analyze commits since a merge base (E) but don't have persistent storage
- Current workaround using `CI_MERGE_REQUEST_TARGET_BRANCH_NAME` fails for merged result pipelines because the temporary merge makes the target branch an ancestor
- The desired solution would use `CI_MERGE_REQUEST_DIFF_BASE_SHA` (commit E's hash) with `--shallow-exclude`, but this remains unimplemented
- Performance impact is significant - full kernel repository clones take 13 minutes when only the top 1-100 commits need analysis

The email raises an important practical case where the current shallow clone exclusion behavior creates real workflow pain points, particularly in CI environments. It doesn't propose a specific code change but seeks design rationale and alternative solutions, suggesting this may spark discussion about expanding `--shallow-exclude` capabilities.
