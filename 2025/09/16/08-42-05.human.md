This is a technical discussion about implementing the `reword` subcommand for the proposed `git-history` command. Phillip Wood responds to Patrick Steinhardt's concerns about reusing the sequencer's existing reword functionality.

Phillip argues that since `git-history` already uses the sequencer for cherry-picking (via `sequencer_pick_revisions()`), it should be straightforward to extend this approach for rewording by passing a todo-list with "reword $oid" commands. He notes that both cherry-pick and rebase share the same todo-list processing logic in the sequencer, so there shouldn't be a fundamental mode conflict.

The email clarifies that while there are valid arguments for avoiding the sequencer entirely (to prevent unnecessary worktree updates), Phillip sees no good reason to use the sequencer for cherry-picking while implementing other operations like reword separately. He suggests adding a new sequencer entry point that accepts todo-lists directly, which would provide most needed functionality with minimal new code.

Phillip also raises an interesting side issue about `git status` potentially confusing `git-history` operations with cherry-picks, suggesting this will need addressing eventually. The exchange shows Phillip advocating for deeper sequencer integration while Patrick remains cautious about mode interactions, though both seem aligned on finding a middle ground that shares core operations.
