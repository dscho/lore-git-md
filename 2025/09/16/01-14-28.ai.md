This is a bugfix for the `git send-email` command's handling of Reply-To headers when using both `--compose` and `--reply-to` options together. The issue causes duplicate Reply-To headers in outgoing emails, which email providers like Gmail reject.

Junio C Hamano provides feedback on NeilBrown's patch, confirming the problem description is clear but suggesting improvements to the commit message. The key technical insight is that the fix works by modifying the header parsing logic in `git-send-email.perl` to properly capture the Reply-To header value into the `$reply_to` variable during pre-processing, preventing it from being duplicated in the `@xh` array that gets blindly copied to the final message.

The review notes two specific issues with the patch submission: (1) a mismatch between the author address in the email From: header and the Signed-off-by line, and (2) a preference for more imperative language in describing the solution. The actual code change is minimal - just 3 lines added to handle Reply-To headers similarly to how In-Reply-To and References are already processed.

This appears to be a straightforward fix for a real-world usability issue, though the review suggests some minor polishing of the commit message before final acceptance. The technical approach seems sound and focused on the specific interaction between compose mode and reply-to functionality.
