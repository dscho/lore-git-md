This is a follow-up discussion about edge cases in the command deprecation framework, specifically around the `whatchanged` command removal. Jeff King identifies that the Makefile still builds `git-whatchanged` even when compiled with `WITH_BREAKING_CHANGES=YesPlease`, which leads to confusing behavior where the command fails with "cannot handle whatchanged as a builtin" rather than being properly removed or allowing aliases to work.

The key issue is that the leftover builtin executable prevents the alias system from working as intended - users can't alias `whatchanged` to another command like `status` because Git still sees the (non-functional) builtin version. Jeff proposes a Makefile fix to prevent building `git-whatchanged` when breaking changes are enabled, though notes this doesn't solve the problem for existing builds where the executable remains.

This discussion highlights an important integration issue that needs resolution before the deprecation series can be finalized - either the test expectations need updating to match the current behavior, or the system needs adjustment to properly support command aliasing after removal as originally intended. The core technical approach remains sound, but this edge case around build artifacts and alias precedence needs to be addressed.
