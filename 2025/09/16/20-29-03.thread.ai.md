Thread identity: User experience discussion about Git's command suggestions in different repository states, specifically comparing `git status` output before versus after initial commit.

Core problem: Inconsistency in `git status` advice for unstaging files - suggests `git rm --cached` before first commit but `git restore --staged` afterward. Technical investigation confirms this is necessary rather than a UX inconsistency, as pre-commit there's no HEAD to restore from.

Current status: Maintainer (Junio C Hamano) and technical analysis (D. Ben Knoble) confirm behavior is correct given technical constraints. No proposed implementation changes, though documentation improvements remain possible.

Technical details:
- Before first commit (no HEAD):
  - Only `git rm --cached` possible (no commit to restore from)
  - Removes from index while preserving worktree file
  - Behavior dates to 2009 `is_initial` check
- After first commit (HEAD exists):
  - `git restore --staged` becomes available (promoted over reset in 2019)
  - Resets index to HEAD state (preferred over rm --cached)
  - Can handle unstaging without dropping tracking
- Implementation difference stems from fundamental repository state
- `restore --staged` fails in unborn repo with "could not resolve HEAD"

Key implications:
- Difference reflects technical necessity not UX oversight
- Historical changes (2009, 2019) shaped current behavior
- New users may still find this confusing despite technical reasons
- Related commands: `git reset` (HEAD-dependent) could theoretically be suggested but `restore` is preferred modern alternative

Open questions:
- Should documentation better explain this distinction?
- Would clarifying text in `git status` help users understand why suggestions differ?
- Is there value in making `restore --staged` more graceful in unborn repos?
