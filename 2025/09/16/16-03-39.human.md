This is a discussion about behavior changes in `git add -p`'s hunk splitting functionality, specifically whether to treat the proposed changes as a bugfix or a breaking change requiring version gating.

Junio Hamano responds to Phillip Wood's patch series that would mark split hunks as "undecided" by default rather than inheriting their parent hunk's state. Phillip had implemented this behind a `WITH_BREAKING_CHANGES` flag after earlier maintainer feedback about potential user impact.

Junio strongly objects to using the breaking changes mechanism here, arguing it should only be used when there's clear consensus the old behavior is fundamentally wrong and must be abandoned. He presents two alternatives: either treat this unconditionally as a bugfix (if the current behavior is truly nonsensical) or make it configurable at runtime (if both behaviors have merit).

Phillip has indicated he doesn't find the current behavior particularly useful and questions whether it warrants a configuration option. Junio suggests they could simply change the behavior and see if users complain, rather than prematurely invoking the breaking changes process.

The exchange highlights Git's careful approach to behavior changes - the maintainer is pushing for either a stronger justification that this is clearly wrong (allowing an unconditional fix) or preserving user's ability to choose, rather than using the heavier-weight version-gating mechanism. The technical implementation appears sound, but the change management strategy remains under discussion.
