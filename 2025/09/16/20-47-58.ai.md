This is a follow-up discussion in the command deprecation framework series, specifically addressing edge case behavior with removed commands and aliases. The email focuses on an unexpected interaction between the `whatchanged` command removal and alias handling when compiled with `WITH_BREAKING_CHANGES=YesPlease`.

Key technical observations:
- The test failure in t0014 shows a divergence between expected verbose alias loop messages and the new "cannot handle as builtin" error for mutually recursive aliases between `whatchanged` and `pack-redundant`
- Kristoffer Haugsbakk confirms the behavior occurs on the branch itself, not just in tests
- The core issue appears when trying to alias whatchanged to another command (like `status`), which still fails with the same "cannot handle as builtin" error despite the command being removed
- This contradicts the expected behavior where users should be able to alias removed commands to working alternatives

The email raises two specific concerns:
1. Whether the error message should be more neutral (like "command not found") for removed commands
2. Why the system prevents reusing the `whatchanged` name via aliases after its removal, contrary to the stated goal of allowing users to create transition aliases

This represents the final integration issue for the series, touching core files like `usage.c` and `builtin/log.c`. The discussion suggests the need to either adjust the test expectations or modify the behavior to properly support command aliasing after removal. The resolution will determine whether the current behavior is an intentional design choice or an unintended side effect of the deprecation framework's implementation.
