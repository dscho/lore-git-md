This is a discussion about behavior changes in `git add -p`'s hunk splitting functionality, part of an ongoing patch series. Phillip Wood is responding to Junio Hamano's feedback about whether the change should be gated behind a breaking-changes flag.

The core issue is that currently when a selected hunk is split in `add -p`, all resulting hunks inherit the "selected" state, which Phillip argues is counterintuitive - users typically split hunks because they want to selectively stage parts. His patch changes this to mark split hunks as "undecided" instead, prompting the user for each one.

Junio questions whether this needs version-gating via WITH_BREAKING_CHANGES, suggesting it could either be treated as a straightforward bugfix (no gating needed) or made configurable at runtime. Phillip responds that while he considers the current behavior buggy enough to change unconditionally, he had previously implemented version-gating based on Junio's earlier caution about behavior changes.

The exchange shows the careful consideration Git maintainers give to backward compatibility, even for behaviors that may seem clearly suboptimal. Phillip appears open to either approach (unconditional change or runtime configuration) depending on Junio's final decision, though he expresses skepticism about adding a config option for what he sees as an obscure use case.

This discussion represents the final design decision needed before the technical changes (which appear well-tested and documented) can be finalized and merged.
