Feature proposal for `git-history reword` subcommand, now being reconsidered in light of sequencer capabilities. This email from Patrick Steinhardt responds to Phillip Wood's suggestion to reuse the sequencer's existing reword functionality (used in interactive rebase) rather than implementing a separate path in `git-history`. 

Key technical points: Patrick acknowledges the potential simplification from using a todo-list with "reword $oid" entries, but notes this would put the operation in interactive-rebase mode rather than history-editing mode. He expresses concerns about the complexity of introducing a new history-editing mode that aliases interactive-rebase behavior, as this would require widespread changes in sequencer.c. 

The discussion reveals an architectural tension between clean code reuse and maintaining distinct operational modes. Patrick suggests a middle path of sharing core operations between sequencer and git-history while avoiding full mode unification, though he stopped short of implementing this due to complexity. This email confirms his earlier decision to drop the current `reword` implementation from the series, with plans to revisit the approach when the feature is reintroduced later.

The exchange highlights ongoing design work around how to best leverage Git's existing infrastructure for new user-facing commands, with Phillip Wood advocating for maximum reuse and Patrick balancing that against implementation complexity and mode separation concerns. The sequencer's todo-list mechanism emerges as a potentially unifying architecture point for history editing operations.
