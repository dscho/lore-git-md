This is a discussion about behavior changes in `git add -p`'s hunk splitting functionality, specifically around whether to mark split hunks as "undecided" by default. The patch is part of Phillip Wood's ongoing work to improve `add-patch.c` and follows up on previous discussions about hunk state handling.

The core technical issue involves how split hunks inherit their selection state from the original hunk. Currently, all split hunks inherit the original's "selected" state, which can force users to navigate back to deselect later hunks. The proposed change would mark all split hunks as "undecided" instead, making it easier to selectively stage parts of a split hunk.

The key discussion point is the mechanism for introducing this change. Phillip originally proposed gating it behind `WITH_BREAKING_CHANGES` due to concerns about changing established behavior, but Junio questions whether this qualifies as a breaking change needing version gating. Junio suggests either treating it as a bugfix (no gating) or making it configurable at runtime. Phillip expresses skepticism about the current behavior's usefulness and the value of adding configuration for it.

The email references prior discussion [1] where Junio expressed uncertainty about whether this change was safe enough for a minor version bump, leading Phillip to use the breaking changes guard in v2. Phillip indicates willingness to revert to the v1 approach (unconditional change) if Junio now considers it acceptable as a bugfix.

This exchange highlights Git's careful approach to behavior changes - balancing improvement against backward compatibility, with maintainers weighing whether changes warrant version gates, configuration options, or can be treated as pure bugfixes. The technical implementation appears settled, with the remaining question being purely about the change management strategy.
