This is a maintainer response in the thread about `git status`'s inconsistent unstage suggestions before vs after initial commit. Junio Hamano explains the technical rationale behind the different commands suggested in each case.

Before the first commit, `git rm --cached` is suggested because there's no commit to restore from - the file only exists in the index and working tree. After the first commit, `git restore --staged` becomes possible (and more appropriate) since it can reset the index to HEAD's state, which `rm --cached` cannot do.

The response frames this as an inevitable consequence of the repository's technical state rather than a UX inconsistency to be fixed. Hamano's tone suggests this is working as designed, with the different commands accurately reflecting what's possible/appropriate in each scenario. The explanation is thorough but doesn't propose any changes to the current behavior.

This moves the thread from observation to authoritative explanation, though it leaves open whether documentation could better clarify this distinction for new users. The response doesn't invite further discussion but provides a clear technical basis for the current behavior.
