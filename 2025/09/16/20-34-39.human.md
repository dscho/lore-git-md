This is a user experience discussion about Git's command suggestions in different repository states. Anselm Schüler points out an inconsistency in `git status` advice for unstaging files - it suggests `git rm --cached` before the initial commit but switches to `git restore --staged` afterward.

The core issue is that these different suggestions could confuse new users who expect consistent interface patterns. The difference stems from technical constraints: `git restore --staged` requires an existing HEAD to reference for resetting, while `git rm --cached` works independently of commit history.

The email cleanly restates the behavioral difference that was initially posted with formatting issues. It focuses the discussion on why Git presents different commands in these two states, without yet proposing solutions. This appears to be a genuine usability observation rather than a bug report, and the clear presentation makes it easy for maintainers to consider whether the inconsistency should be addressed through documentation changes or potential command standardization.
