This is a follow-up discussion about transaction handling in the ongoing ODB refactoring series, specifically addressing concerns about removing nested transaction support.

Justin Tobler responds to Taylor Blau's concerns about the safety and usability implications of removing nested transaction support in the ODB API. The original patch (part 1/6 of the series) had removed the nesting mechanism in favor of requiring callers to explicitly check for pending transactions, which Taylor noted could be more error-prone.

Justin acknowledges the trade-offs and proposes an alternative approach that would:
1. Keep the safety of no-op behavior for nested transactions by having `begin_odb_transaction()` return NULL when a transaction is already active
2. Still achieve the main goal of ensuring `end_odb_transaction()` always flushes when given a non-NULL transaction
3. Remove the need for explicit pre-checking by callers

The discussion highlights the tension between API simplicity and caller convenience. While the refactoring aims to establish clearer guarantees about transaction flushing, there's careful consideration being given to how to do this without making the interface more difficult to use correctly. Justin indicates he'll send an updated version incorporating this feedback.

This exchange shows the series is nearing completion but still undergoing thoughtful review of its API design choices, particularly around error handling and caller responsibilities. The conversation demonstrates healthy scrutiny of the trade-offs between internal simplicity and external usability.
