This is a user experience question about Git's command suggestions in different repository states.

Anselm Schüler points out an inconsistency in Git's status output: before any commits exist in a repository, `git status` suggests using `git rm --cached` to unstage files, while after the first commit it suggests `git restore --staged`. The question asks why these different suggestions appear in what seem like similar situations.

The difference stems from Git's internal handling of the index in a fresh repository versus one with commits. Before any commits exist, removing a file from the index with `git rm --cached` makes sense because there's no history to restore from - the file simply shouldn't be in the initial commit. After commits exist, `git restore --staged` becomes the more appropriate suggestion since it can reference the repository's history.

This appears to be a genuine usability question rather than a bug report. The behavior is intentional but not well-documented, which could confuse new users who encounter both forms of the suggestion. The thread may attract discussion about whether this inconsistency should be preserved for technical reasons or standardized for user experience.
