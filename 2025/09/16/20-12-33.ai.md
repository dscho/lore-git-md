This is a bugfix targeting threading support detection on HP-UX systems. The patch addresses two related issues in Git's build configuration: misleading output about pthread linking options during configuration, and incorrect runtime behavior due to improper pthread detection.

The core problem stems from how Git's configure script checks for pthread support. Currently it tests empty string first (""), then -mt, -pthread, and -lpthread. On HP-UX, this leads to false positives because the empty string test passes (due to transitive pthread dependencies from gettext), but then fails at runtime with "cannot create async thread" errors. The author demonstrates this with a failed `git clone` attempt.

The proposed fix removes the empty string test from the option list in configure.ac, forcing explicit pthread linkage. This matches HP-UX's documented requirement that multithreaded applications must explicitly link against pthreads with -lpthread or -mt. The patch also notes the configure script's help text would need updating to reflect the actual options being tested.

The issue appears specific to HP-UX's toolchain behavior where gettext pulls in pthreads transitively, masking the need for explicit linkage. The author provides technical details from HP-UX's pthread manpage and shows how the current configuration test produces false positives. They've also encountered similar issues in other projects (MIT Kerberos) suggesting this may be a broader HP-UX + gettext compatibility concern.

Key technical points for future reference:
- configure.ac tests pthread options in order: previously "" first, now would be -mt first
- HP-UX requires explicit -lpthread or -mt linkage despite gettext's transitive dependency
- Current behavior causes runtime failures in operations needing threads (like git clone)
- Related to GNU gettext >= 0.23's pthread dependency behavior
