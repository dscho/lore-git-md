New participant joins the `git-history` command discussion with a dissenting view on command structure.

Oswald Buddenhagen weighs in on the ongoing debate about whether history editing operations should be structured as subcommands of `git-history` or as separate top-level commands. He challenges Patrick Steinhardt's argument that subcommands aid discoverability, suggesting instead that proper documentation would serve this purpose better. Buddenhagen argues that requiring aliases for efficient use creates inconsistency between documentation examples and actual usage patterns.

He also questions the proposed scope boundaries of `git-history`, noting that the current definition has gray areas that will likely expand as more edge cases are considered. While acknowledging Patrick's consideration of alternative command names like `git-histedit`, Buddenhagen suggests `git-revise` as a more natural name - coincidentally matching an existing third-party tool with similar functionality.

This email represents a new voice in the architectural discussion, advocating for a more traditional Unix-style approach of separate single-purpose commands rather than the subcommand model. The feedback doesn't propose specific technical changes to the current implementation but challenges the fundamental design philosophy behind it. This perspective adds weight to earlier concerns raised by Elijah Newren about command proliferation, though Buddenhagen's solution (atomization) differs from Newren's suggestion of consolidation.
