Feature proposal for improved rebase handling of semantically dependent commits, with significant revision based on-list feedback.

Antonio Mennillo responds to brian m. carlson's critique of their initial `git-rebase-clean` tool by introducing a substantially redesigned v2.0.0 that attempts to preserve commit granularity while still avoiding semantic conflict cascades. The new approach first squashes commits temporarily to resolve conflicts with full context, then reconstructs the original commit structure by replaying saved diffs. This addresses the core objection about history preservation while maintaining the tool's original goal of reducing repeated conflict resolution.

Key technical changes in v2.0.0 include: automated commit reconstruction after conflict resolution, support for edge cases (empty commits, binary files), and 23 passing integration tests. The author now proposes this as a potential experimental rebase strategy (`--squash-restore`) rather than a separate tool, asking whether this approach overlaps with existing mechanisms.

The email reveals an important clarification about the tool's target scenario: it specifically addresses semantic conflicts (where interface changes invalidate dependent implementations) that `git rerere` cannot handle, as rerere only remembers textual conflict resolutions. The author acknowledges their junior developer context where enforcing atomic commits isn't always practical.

This represents a notable evolution from the initial proposal, now attempting to bridge the workflow philosophy gap between history preservation and conflict resolution efficiency. The implementation appears more sophisticated, though real-world testing remains pending. The thread continues to explore whether this represents a genuine improvement to Git's rebase capabilities or an unnecessary complication of standard workflows.
