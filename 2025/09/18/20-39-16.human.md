This is a technical discussion about the behavior of `git fetch --dry-run` with partial clones, continuing from a bug report about unexpected config modifications.

Jeff King responds to Junio Hamano's point that the current behavior - where dry-run fetches leave behind healthy objects that can speed up subsequent real fetches - may actually be preferable to strict dry-run semantics. While acknowledging the technical possibility of using tmp-objdir for true dry-run behavior (as suggested earlier), Jeff now agrees the performance benefits of the current approach may outweigh purity concerns.

The discussion reveals deeper architectural considerations: promisor objects exist in a gray area where they violate normal object storage rules but are marked as such in config. Jeff notes the current implementation ties promisor information to repo config rather than packfiles themselves, which becomes problematic when using alternate object directories via GIT_OBJECT_DIRECTORY. However, he concludes these are likely not worth changing given the edge-case nature of the issue.

The exchange highlights how what initially appeared as a bug report has evolved into a nuanced discussion of tradeoffs between correctness, performance, and implementation complexity in Git's object handling. Both contributors seem to be converging on accepting the current behavior as a reasonable compromise.
