This is the fourth patch in a 5-part bugfix series addressing issues with `git config get --type=color` functionality. The patch specifically restores backward compatibility for a documented use case where users retrieve color reset sequences without specifying a config key.

The patch fixes a regression introduced in commit 4e51389000 where `git config get --type=color --default="reset" ""` stopped working, while the older `git config --get-color "" "reset"` syntax still functioned. The change adds special-case handling in builtin/config.c to directly call `get_color()` when three conditions are met: an empty config key is provided, the type is color, and a default value exists.

The implementation adds 13 lines of code - 2 lines in builtin/config.c to handle the special case, and 11 lines in t1300-config.sh to test both the new subcommand behavior and its equivalence with the older syntax. The test demonstrates that both command forms now produce identical output for color values.

This change maintains documented behavior while addressing a user-reported issue from SZEDER Gábor. The patch follows logically from the series' earlier test cleanup work, with all review feedback from previous iterations incorporated. The solution acknowledges this is a color-specific special case that wouldn't make sense for other config types, as color parsing transforms the default value rather than returning it verbatim.
