This is a technical discussion about a protocol-level bug in Git's `--negotiate-only` fetch behavior, building on an earlier thread about `git fetch --dry-run` modifying config files.

The email thread has uncovered a clear bug in how `--negotiate-only` interacts with the fetch protocol when the client and server have no common commits. Kevin Puetz and Jeff King have identified that after receiving a NAK (indicating no common history), the client incorrectly makes an empty request instead of exiting, causing the server to unexpectedly send a packfile. The bug appears to be in both client and server code paths in upload-pack.c, with the server incorrectly falling through to UPLOAD_SEND_PACK state when it should handle this as a special case.

Randall Becker's question adds an interesting wrinkle about how shallow clones (`--depth=1`) might interact with this edge case, though this appears to be a separate consideration from the core protocol bug. The discussion remains technical and focused, with participants clearly identifying code locations and protocol specifications that need adjustment.

The bug appears fixable now that the problematic code paths have been identified, though there are open questions about whether the server should respond with an empty "ready" or NAK in this case. This is a good example of the mailing list working effectively to diagnose a subtle protocol issue.
