This thread continues the discussion about making the `exact_match` parameter optional in the string-list API's `get_entry_index()` function. The original patch from shejialuo proposed allowing NULL for this parameter to reduce boilerplate in callers that only need the index position. 

Junio C Hamano has consistently skeptical, questioning both the tradeoff (adding implementation complexity for small caller convenience) and the semantic validity of cases where callers wouldn't care about exact-match information. Ben Knoble initially supported the patch's approach but in this latest response engages more directly with Junio's concerns about semantic meaning, though without providing concrete examples of valid use cases that would ignore exact-match results.

The discussion remains at an impasse between two API design philosophies: Junio favors explicit output parameters that preserve semantic clarity, while the patch's proponents prioritize reducing trivial boilerplate in calling code. No new technical arguments or code changes have emerged since the initial proposal. The core question remains unresolved - whether the convenience justifies both the implementation cost and potential loss of semantic information at call sites.
