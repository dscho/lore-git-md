This thread discusses a proposed change to Git's string-list API that would make the `exact_match` parameter optional in `get_entry_index()`. The patch author, shejialuo, originally suggested allowing NULL for this parameter to reduce boilerplate when callers only need the index position. The change would add a few NULL checks in the implementation while simplifying some call sites.

Junio Hamano, the Git maintainer, has expressed reservations about this approach, questioning whether the small convenience for callers justifies the added complexity in the library implementation. He maintains that exact-match information is always semantically relevant for string-list operations. Ben Knoble initially supported the change but has since engaged with Junio's deeper concerns about the semantic meaning of the API.

In the latest exchange, shejialuo has stepped back from the technical debate to address a more immediate concern - the organization of the patch series. Recognizing that splitting the changes across multiple commits may have caused confusion, they propose rebasing the work into a single commit for clarity. This pragmatic response shows the author is responsive to feedback, though the fundamental disagreement about API design philosophy remains unresolved.

The technical implementation remains unchanged - a small modification to `string-list.c` that would allow NULL `exact_match` parameters. The discussion now appears to be at an impasse between those who value caller convenience and those who prioritize semantic clarity in the API design. With the author focusing on presentation improvements rather than new arguments, the thread may be nearing its conclusion unless someone can provide compelling use cases where ignoring exact-match information would be legitimate.
