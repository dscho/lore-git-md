This is a historical explanation of Git's `add` command behavior regarding invalid pathspecs. Jeff King (peff) traces the current "all-or-nothing" behavior back through Git's history to 2006 commits, showing it was an intentional design choice inherited from cogito (an early Git frontend). The thread confirms this is working as designed, though peff acknowledges the alternative "partial success" approach has some merit.

Key points from peff's response:
1. The behavior dates back to multiple 2006 commits that unified error handling across `add` and `commit`
2. Original cogito behavior matched what Jon expected (ignoring invalid paths), but this was considered a bug
3. Changing behavior now would risk confusion due to established expectations
4. Technical challenges include the binary nature of exit codes making partial success hard to communicate

The email provides closure to the thread by confirming the behavior is intentional while acknowledging the design tradeoffs. No changes to the current behavior are proposed, but the historical context may inform future discussions about potential improvements to pathspec handling.
