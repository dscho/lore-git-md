This is a discussion about Git's pathspec handling behavior in `git add`, continuing the thread about whether invalid pathspecs should cause complete command failure.

Jeff King provides historical context tracing this behavior back through Git's code evolution, showing it was intentionally designed this way from early versions (2006) and even predates Git in the cogito tool. He notes the original cogito behavior matched Jon Forrest's expectation (ignoring invalid pathspecs), but this was considered a bug at the time.

Key technical considerations raised:
- The binary exit code problem (0 vs 1) makes partial success/failure states difficult to represent
- Git's conservative philosophy prefers doing nothing when command intent is ambiguous
- Changing behavior now could cause confusion due to established expectations

The email suggests the current behavior is unlikely to change despite differing user expectations, due to both historical precedent and technical constraints around error signaling. No concrete proposal for change is made, but the historical analysis provides useful context for understanding why the current implementation exists as it does. The discussion remains open-ended regarding whether this design should be reconsidered in light of modern use cases.
