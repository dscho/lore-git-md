This thread has explored the technical constraints of Git's "dumb" HTTP protocol, particularly around repository path handling and metadata requirements. Milan Hauth originally reported that while local repositories can be accessed with or without the `.git` suffix, the HTTP protocol strictly requires `.git` and pre-generated `info/refs` files. 

Core contributors including Brian M. Carlson and Jeff King explained that these limitations stem from HTTP's lack of native atomic operations and directory listing capabilities, making the current behavior an intentional design choice rather than an oversight. The discussion revealed that the dumb HTTP protocol is incompatible with reftable backends and may be deprecated in Git 3.0.

Patrick Steinhardt proposed using reftable's `tables.list` as an alternative to `info/refs`, but Junio Hamano noted this wouldn't fully address the need for pack file discovery. The thread has reached consensus that directory scraping (like httpdirfs implements) would be unreliable and insecure if built into Git, with Carlson strongly opposing such an approach. 

The current state is that dumb HTTP will remain constrained by its fundamental protocol limitations, with reftable adoption potentially offering partial improvements but not eliminating the need for pre-generated metadata. The maintainers have effectively closed the door on protocol changes that would require parsing HTTP directory listings.
