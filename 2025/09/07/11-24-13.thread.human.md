This thread explores the differences in how Git handles repository paths between local filesystem access and the "dumb" HTTP protocol. Milan Hauth initially reported that while local repositories work with or without the `.git` suffix (e.g., `/path/to/repo` or `/path/to/repo.git`), the HTTP protocol strictly requires the `.git` suffix and pre-generated `info/refs` metadata. This creates friction for simple HTTP server setups, particularly affecting tools like httpdirfs.

Brian M. Carlson provided the technical rationale for this design, explaining that HTTP lacks native directory listing capabilities (without WebDAV) and atomic operations, making the `info/refs` file essential for reliable repository access. He also noted that the dumb HTTP protocol is incompatible with the upcoming reftable backend and may be removed in Git 3.0.

In follow-up discussion, Milan clarified they were specifically interested in more flexible path handling for read-only operations like `git ls-remote`, `fetch`, and `pull`, while understanding the constraints for write operations. Brian's latest response reinforces that HTTP's fundamental limitations—particularly its inability to natively discover repository contents without pre-generated manifests—make the current behavior necessary. He draws parallels to early directory-less filesystems and notes that WebDAV, which Git has chosen not to adopt, would be required for more flexible access patterns.

The discussion has narrowed to focus on whether read-only HTTP operations could safely relax some requirements, but Brian's explanation suggests the protocol's constraints are deeply rooted in HTTP's design rather than arbitrary Git implementation choices. With reftable adoption on the horizon potentially obsoleting the current dumb HTTP protocol, the thread appears to be converging on the conclusion that significant changes to this behavior are unlikely.
