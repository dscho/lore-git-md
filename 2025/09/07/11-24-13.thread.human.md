This thread explores the limitations of Git's "dumb HTTP" protocol, which behaves differently from local repository access. The discussion began when Milan Hauth reported that while local repositories can be accessed with or without the `.git` suffix (like `/path/to/repo` or `/path/to/repo.git`), dumb HTTP strictly requires the `.git` suffix and manual generation of `info/refs` via `git update-server-info`. This causes real problems for tools like httpdirfs that try to mount repositories over HTTP.

Technical experts including Brian M. Carlson and Jeff King explained why these limitations exist: HTTP lacks native atomic operations (without WebDAV) and doesn't provide machine-readable directory listings by default. These constraints make the current behavior intentional rather than a bug. Jeff King suggested a workaround using httpdirfs with Python's RangeHTTPServer, though with severe performance penalties.

Junio Hamano, the Git maintainer, firmly rejected any changes that would blur dumb HTTP's simple boundaries, like implementing directory scraping. Brian M. Carlson later reinforced this position with strong technical arguments against scraping HTTP directory listings, citing inconsistent server output and security risks. The only remaining proposal comes from Patrick Steinhardt, who suggested reftable's "tables.list" could replace `info/refs` in the future, though Junio noted this still wouldn't solve the fundamental need for file discovery.

The thread has reached consensus that dumb HTTP's limitations are intentional design choices, with no practical path to make it behave like local file access. The discussion remains focused on read operations, with Steinhardt's reftable proposal as the only potential future improvement still under consideration.
