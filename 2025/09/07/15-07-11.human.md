Maintainer response on dumb HTTP protocol limitations. Brian m. carlson explains why the current behavior requiring `update-server-info` for dumb HTTP access is necessary, contrasting with Milan Hauth's request for HTTP to match the file protocol's flexibility.

The key technical reason given is HTTP's lack of native atomic operations - the `info/refs` file serves as a lock mechanism during pushes to prevent data loss from competing updates. Without this file, there would be no way to coordinate concurrent operations. The response also notes HTTP lacks machine-readable directory listings without WebDAV, making the metadata file essential for fetches.

Carlson further points out that dumb HTTP won't work with the upcoming reftable backend (planned as default in Git 3.0), suggesting this protocol may be deprecated. The reply maintains the status quo position that the metadata generation requirement is fundamental to HTTP's constraints, not just an optimization as the original reporter suggested.

This appears to be a definitive maintainer stance on the issue, citing architectural constraints that make the requested behavior change impossible while maintaining data integrity. The response also hints at broader protocol evolution with reftable adoption potentially making this discussion moot in future versions.
