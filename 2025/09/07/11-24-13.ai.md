This is a bug report about Git's dumb HTTP protocol behavior. Milan Hauth reports that while local file access to Git repositories works with or without the `.git` suffix in the path, the same is not true for HTTP access. The key issue is that dumb HTTP requires running `git update-server-info` to create `info/refs`, which the reporter argues should not be necessary since the server could theoretically serve the raw Git objects directly.

The email demonstrates the problem by showing successful `ls-remote` operations against local paths (with and without `.git`) versus failing operations against a simple Python HTTP server serving the same repository. The workaround requires manual generation of server info files. The reporter argues this optimization should be optional, especially for low-latency local HTTP servers, and that the behavior should match file protocol's flexibility.

The report references two StackOverflow threads about `update-server-info` and private HTTP repositories, plus an issue with httpdirfs (a FUSE HTTP filesystem) failing to mount Git repos. The core argument is that dumb HTTP should "just work" like file protocol does, with optimizations being optional rather than mandatory. This appears to be a long-standing behavior difference that may affect users trying to serve repositories via simple HTTP servers.
