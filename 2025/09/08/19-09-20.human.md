This is a follow-up in the WebDAV PROPFIND feature discussion, where Milan Hauth continues advocating for WebDAV support in Git's HTTP transport. The email presents a concrete proposal for how Git could progressively try different HTTP methods (GET, OPTIONS, PROPFIND) when accessing repositories, rather than failing immediately if the first attempt doesn't work.

Milan outlines four fallback plans (A-D) that Git could attempt sequentially when accessing a repository over HTTP. The key addition is plans C and D which would use WebDAV's PROPFIND method to discover repository locations after traditional methods fail. This contrasts with Junio Hamano's earlier position that maintaining protocol simplicity is more important than WebDAV compatibility.

The email also references a separate but related thread about making Git work without `update-server-info`, suggesting Milan sees these as connected improvements to HTTP repository access. The tone remains technical rather than confrontational, but clearly disagrees with the maintainer's stance that WebDAV support would violate the "dumb HTTP" design principles.

This continues the fundamental disagreement in the thread: whether Git should adapt to common server configurations (like WebDAV-enabled nginx) even if it means adding protocol complexity, versus maintaining the current minimal HTTP transport design. The proposal is concrete enough that it could theoretically be implemented, but faces significant philosophical opposition from the maintainer.
