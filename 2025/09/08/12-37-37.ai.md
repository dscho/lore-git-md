This is part 3 of a 4-part series fixing batched reference update issues on case-insensitive filesystems, specifically addressing file/directory (F/D) conflicts in the files backend. The patch modifies how refname conflicts are handled when creating references in a single transaction, such as between 'refs/heads/foo' and 'refs/heads/Foo/bar'.

The key change is in `lock_raw_ref()` where refnames are now lowercased when checking for conflicts on case-insensitive filesystems, using a `strbuf` to temporarily store the lowercase version before adding it to the string list with `string_list_append_nodup()`. This maintains the separation between backend-specific case-sensitivity issues and the shared `refs_verify_refnames_available()` utility function. The patch also changes the string list initialization to `STRING_LIST_INIT_DUP` to properly handle memory management.

A new test case in t5510-fetch.sh verifies the F/D conflict detection by attempting to fetch references that would create such a conflict ('foo/bar' vs 'Foo') on a case-insensitive filesystem. The test confirms that the operation fails with a "refname conflict" error while still preserving successfully updated references (like 'main').

This builds on the thread's earlier work addressing case collisions and lock file handling, with the implementation following the approach validated by reviewers. The solution remains files-backend specific while maintaining cross-backend compatibility, though the long-term recommendation is still to use the reftable format for case-insensitive systems.
