This thread discusses an RFC patch series introducing atomic reference updates for `git replay`, primarily targeting server workflows like GitLab/Gitaly. The initial proposal added a `--update-refs` flag to enable direct, atomic ref updates (all succeed or none) rather than piping to `git update-ref`. 

After extensive discussion, key participants have converged on making atomic updates the default behavior, given `git replay`'s experimental status. Junio Hamano and Elijah Newren agreed this is justified despite some existing usage, with backward compatibility preserved via an `--output-commands` flag for the old pipe-based workflow. Christian Couder raised deployment concerns but acknowledged the technical merits, while Patrick Steinhardt proposed consolidating the interface into a single `--update-refs[=<mode>]` parameter.

The latest email from Siddharth Asthana simplifies the design further by dropping the redundant `--update` flag (individual ref updates) in favor of atomic-by-default behavior, addressing performance concerns Patrick raised earlier. A remaining `--allow-partial` flag would handle cases where some refs can fail independently. Siddharth also confirmed removing an unnecessary `result.clean` initialization Elijah flagged, as empty commit ranges are already handled correctly.

The discussion has progressed through technical reviews (Patrick), interface philosophy (Elijah), deployment considerations (Christian), and documentation refinements (Siddharth, Andrei Rybak). With maintainer alignment on the atomic-by-default approach and interface simplifications now proposed, the series appears ready for an updated version addressing these final refinements.
