This RFC thread explores adding atomic reference updates to `git replay` through a new `--update-refs` flag, primarily targeting server-side workflows like GitLab/Gitaly. The initial implementation by Siddharth Asthana enables direct ref updates without piping to `git update-ref`, using `ref_store_transaction_begin()` for atomic transactions (all-or-nothing updates). The series includes extensive test coverage and documentation, but faces design questions from reviewers.

Elijah Newren raised concerns about interface complexity, questioning the need for three update modes and unclear flag naming. Christian Couder earlier proposed alternative flag names (`--atomic-update`, `--batch-update`) and emphasized documentation needs. In the latest exchange, Couder responds to Newren's review, acknowledging that making atomic updates the default would have been ideal but noting `git replay`'s 18 months of real-world use (since v2.44.0) makes such changes potentially disruptive despite its experimental status. He also clarifies the server-side benefits: `git replay` already suits servers by operating in-memory without a worktree, and atomic transactions add reliability.

The discussion now centers on balancing ideal design with backward compatibility, as the command's existing usage constrains major interface changes. Key open questions remain about flag naming, update mode simplification, and clearly documenting the server workflow advantages. The thread has drawn technical feedback from Patrick Steinhardt, Kristoffer Haugsbakk, and others, showing active debate about optimizing this functionality for production use.
