This thread discusses an RFC patch series introducing atomic reference updates for `git replay`, primarily targeting server workflows like GitLab/Gitaly. The proposed `--update-refs` functionality would enable direct, atomic ref updates without piping to `git update-ref`.

The discussion has evolved through several phases: initial implementation by Siddharth Asthana, technical reviews from Patrick Steinhardt, interface design critiques by Elijah Newren, and practical deployment considerations from Christian Couder. Newren raised concerns about the complexity of having three update modes (`update_directly`, `update_refs_flag`, `batch_mode`) and unclear flag naming. Couder noted that while an ideal interface would make `--update-refs` the default, existing usage since v2.44.0 makes behavioral changes disruptive.

In the latest response, Patrick Steinhardt weighs in on the interface design, advocating for simplification. He agrees with removing the individual ref update path due to performance concerns and proposes consolidating the three flags into a single `--update-refs` parameter with optional modes (suggesting "allow-failures" as one possibility). This approach addresses earlier concerns about flag clarity while maintaining the core atomic update functionality.

Key open questions remain about final flag naming, default behavior philosophy given real-world usage, and resolution of Newren's interface simplification proposals versus deployment constraints. The discussion shows active debate between ideal design and practical adoption factors for this server-targeted feature.
