This thread discusses an RFC patch series introducing atomic reference updates for `git replay`, primarily targeting server workflows like GitLab/Gitaly. The proposed `--update-refs` functionality would enable direct, atomic ref updates without piping to `git update-ref`.

The discussion has seen active participation from key contributors. Christian Couder raised concerns about changing the default behavior, noting 18 months of existing usage since v2.44.0 makes behavioral changes disruptive, while highlighting the server-side benefits of in-memory operation and atomic transactions. Patrick Steinhardt proposed consolidating three flags into a single `--update-refs[=<mode>]` parameter for better interface design.

Elijah Newren's latest response argues that despite the command's availability, its prominent experimental markings (more visible than other commands') justify making `--update-refs` the default. He suggests major server-side users like GitLab and GitHub should be prepared for changes, proposing a config option for backward compatibility if needed. Newren also praised improvements in documenting the server-side benefits.

The thread reveals an ongoing tension between ideal interface design and real-world constraints, with technical discussions around flag consolidation, default behaviors, and documentation clarity. The implementation already includes ~600 lines of test coverage and uses the transaction API from `git update-ref`, targeting bare repositories. Key open questions remain about final flag naming, default behavior philosophy, and resolving Newren's interface simplification proposals against deployment realities.
