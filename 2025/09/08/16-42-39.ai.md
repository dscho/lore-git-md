This is the third patch in a bugfix series addressing color handling inconsistencies in Git's interactive patch mode (`-p`/`--patch`). The patch specifically fixes the fallback behavior for color configuration when `color.diff` or `color.interactive` are unset, ensuring proper respect for `color.ui` settings across all interactive commands.

The core issue stems from the 2021 Perl-to-C conversion, where the interactive mode's color handling lost its automatic fallback to `color.ui` when checking specific color settings. While `add -p` worked because it explicitly loaded color config, other commands like `checkout -p` would ignore `color.ui` settings. The fix centralizes the fallback logic in `add-interactive.c` by manually checking `color.ui` when primary color configs are unset, avoiding the need to modify each command's config callback.

Key technical changes include:
- New logic in `check_color_config()` that explicitly checks `color.ui` when primary color settings return unset (-1)
- Expanded test coverage in `t3701-add-interactive.sh` verifying the fallback works for all interactive commands (`add`, `checkout`, `commit`, `reset`, `restore`, `stash`)
- The solution maintains Git's design principle of plumbing commands avoiding porcelain config by only loading `color.ui` within the interactive code path

The patch builds on previous discussion and review feedback, with Jeff King explaining why alternative approaches (like modifying `want_color()` or individual command callbacks) would be problematic. The solution cleanly handles the regression while respecting Git's configuration boundaries. Test cases now verify that commands like `git -c color.ui=false checkout -p` properly disable color output.
