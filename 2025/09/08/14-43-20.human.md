This is a technical discussion about the future of Git's dumb HTTP protocol in relation to the reftable backend.

Junio Hamano responds to Patrick Steinhardt's proposal about using reftable's "tables.list" file to replace the current `info/refs` requirement for dumb HTTP access. While acknowledging the theoretical possibility, Hamano points out a key limitation: the "tables.list" file doesn't include information about pack files, which are still need to be discovered by clients. He emphasizes that the dumb HTTP protocol was specifically designed to work with extremely basic HTTP servers (without WebDAV support), requiring pre-generated metadata files to list all available resources.

The response includes a nostalgic footnote about Hamano's early experiences manually uploading repository files before having kernel.org access, illustrating the protocol's original constraints. This reinforces the maintainer position that the current dumb HTTP behavior is intentional rather than a limitation to be fixed. The discussion remains focused on read operations and the fundamental tradeoffs between protocol constraints and server simplicity.
