This is a technical discussion response in the ongoing debate about commit graph storage in the pluggable ODB effort. Patrick Steinhardt pushes back against Derrick Stolee and Junio Hamano's architectural concerns, defending his position that commit graphs should be tied to individual object sources rather than the repository-wide object_database.

Steinhardt makes several key arguments:
1. Commit graphs exist primarily as a performance optimization for Git's current storage format, not as a fundamental repository concept
2. Alternative storage backends (like databases) might provide equivalent functionality through different mechanisms
3. His refactoring doesn't actually enable multiple graphs (maintaining current "single graph" behavior) but prepares for backend-specific implementations
4. The change allows future flexibility where some backends might not use commit graphs at all

The response highlights the core tension in the pluggable ODB design - whether certain features are intrinsic to Git's object model (repository-wide) or implementation details of specific storage formats. Steinhardt positions commit graphs firmly in the latter category, suggesting they're an artifact of Git's current packfile-based storage rather than a conceptual requirement.

This email doesn't propose concrete code changes but provides important conceptual framing for the series. The discussion remains at an architectural crossroads, with Steinhardt maintaining his position against the repository-wide view advocated by Hamano and Stolee.
