This is a bugfix patch addressing case-insensitive filesystem issues in the refs/files-backend, specifically handling F/D conflicts during reference updates. The patch builds on previous work in the thread to properly detect conflicts between references that differ only in case (e.g., 'foo' vs 'Foo/bar') on case-insensitive filesystems.

The key change modifies `lock_raw_ref()` to lowercase reference names when checking for conflicts, allowing proper detection of directory/file conflicts during the locking phase rather than leaking these implementation details into the shared `refs_verify_refnames_available()` function. This addresses Junio Hamano's concern about how the generic code would detect conflicts with existing references.

The patch acknowledges an outstanding test case demonstrating a D/F conflict scenario (Foo/bar vs foo) that fails on macOS CI, which will be addressed in a subsequent version. The solution maintains the thread's consistent recommendation that reftable migration remains the long-term solution for case-insensitive environments.

Technical changes focus on refs/files-backend.c's transaction handling, with case-folding checks now properly integrated into the locking mechanism. The implementation follows Patrick Steinhardt's suggested optimizations for memory efficiency while preserving the separation of concerns between backend-specific and shared reference handling code.

This represents the second patch in a series addressing batched reference update issues on case-insensitive filesystems, with reviewers now aligned on the technical approach pending resolution of the final test case. The changes affect core reference operations like `git fetch`, `git receive-pack`, and `git update-ref --batch-updates`.
