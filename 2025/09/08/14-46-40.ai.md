This is a technical discussion in the ongoing debate about commit graph architecture in the pluggable ODB effort. Derrick Stolee responds to Patrick Steinhardt's position that commit graphs are storage-format-specific optimizations rather than fundamental repository components.

Stolee agrees in principle that alternative storage formats could exist, but argues that as long as commits maintain their current object format, the commit graph remains a valuable cache for speeding up `struct commit` population. He cites Azure DevOps' implementation as an example where commit graphs operate more efficiently by working directly with integer labels rather than full commit objects.

The key distinction Stolee makes is between the physical storage location of commit graphs (currently tied to object storage) and their logical role as a higher-level caching layer. He suggests the code interaction with commit graphs conceptually operates above the object store level, even if the current implementation shares storage infrastructure.

This reply reinforces the architectural divide in the thread - while Steinhardt sees commit graphs as implementation details of specific storage backends, Stolee maintains they serve a repository-wide optimization purpose that transcends any particular storage format. The discussion highlights the tension between physical implementation and logical abstraction in the pluggable ODB design.
