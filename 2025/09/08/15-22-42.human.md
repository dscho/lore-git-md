This is a discussion about the removal of git-new-workdir from Git's contrib/ directory, specifically addressing workflow impacts and potential workarounds.

Gabriel Scherer reports being affected by the removal of `git-new-workdir`, which was part of their regular workflow. While `git worktree` exists as a modern alternative, they highlight a key limitation: it prevents checking out the same branch in multiple worktrees, even temporarily. Kristoffer Haugsbakk suggests using `git worktree add --force` as a workaround, but Gabriel finds this insufficient since the restriction still applies during subsequent `git checkout` operations within the worktree.

The discussion reveals a genuine workflow gap between the old script and current worktree` functionality. While the original removal rationale (redundancy with `git worktree`) still holds, this exchange surfaces real user impact that wasn't fully considered during the removal process. Gabriel proposes improving the error message to suggest detached HEAD mode (`git checkout -d`) when encountering the branch conflict, which could help mitigate the issue.

This thread represents one of the final open questions in Patrick Steinhardt's `contrib/` cleanup series - whether the `git-new-workdir` removal needs reconsideration given these workflow impacts, or if better documentation of workarounds would suffice. The discussion remains constructive, focusing on practical solutions rather than disputing the removal decision itself.
