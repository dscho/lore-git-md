This is a technical discussion about Git's dumb HTTP protocol limitations, continuing the thread about repository path handling differences between local and HTTP access.

Jeff King responds to Milan Hauth's suggestion that dumb HTTP remotes should behave like file remotes, explaining why this isn't feasible due to fundamental protocol differences. He notes that while file remotes can run git-upload-pack locally, dumb HTTP has no server-side component and must simulate a filesystem, which performs poorly and lacks proper directory listing capabilities.

King provides a working example of using httpdirfs with a range-request-capable HTTP server as an alternative approach, though he notes it's painfully slow. He suggests that while Git could theoretically implement similar scraping logic as httpdirfs, the dumb HTTP code is poorly maintained and unlikely to attract development interest.

The response reinforces the technical constraints previously explained by Brian Carlson, while offering a workaround for users willing to accept performance tradeoffs. The tone suggests this is more of a dead-end discussion than an area for potential improvement, given the protocol's limitations and the project's apparent lack of interest in maintaining dumb HTTP functionality.
