This is a technical discussion about Rust/C type compatibility in the context of the ongoing Rust infrastructure series. Ezekiel Newren responds to Patrick Steinhardt's varint subsystem implementation (part of the Rust proof-of-concept patches) with concerns about using C types in Rust code.

Newren argues strongly against using C types (`c_int`, `c_uchar` etc.) in Rust, proposing instead that C code should use Rust primitive types when interfacing between the languages. He cites a detailed commit he previously wrote on the topic, noting that only `c_void` should be used sparingly on the Rust side. The concern stems from platform-specific variations in how Rust defines C types through `std::os::raw`, which may not perfectly match all C compilers across platforms.

The email includes concrete examples showing how Rust's definition of `c_long` changed between versions 1.63.0 and 1.89.0, particularly around WASM32 Linux ABI handling. This illustrates the potential for subtle incompatibilities when relying on Rust's C type definitions. The discussion appears technically well-reasoned and raises important considerations for the Rust integration effort, though it doesn't propose specific changes to the current patch.
