This is a technical discussion about Rust/C type interoperability in the ongoing Rust infrastructure series. Ezekiel Newren responds to Patrick Steinhardt's varint subsystem implementation (RFC v3 5/8) with concerns about using C types (`c_int`, `c_uchar`) in Rust code.

Newren strongly advocates for minimizing C type usage in Rust, suggesting Rust primitive types should be preferred in C code instead. He cites a previous commit where he detailed this philosophy, noting only `c_void` should be used sparingly on the Rust side. The core concern is that Rust's `std::os::raw` types (which inherit from `core::ffi`) make platform-specific assumptions that may not align with all C compilers' behavior.

The email provides concrete examples showing how Rust's definition of `c_long` changed between versions 1.63.0 and 1.89.0, particularly around WASM32 Linux ABI handling. This demonstrates the potential for subtle platform compatibility issues when relying on Rust's C type mappings. The implication is that such type definitions could introduce portability risks for Git across different platforms and Rust versions.

This feedback directly challenges a technical implementation choice in the Rust infrastructure work, raising important considerations about type safety and cross-platform consistency as Git adopts Rust. The discussion represents a deeper architectural question about the Rust/C boundary that could influence future interface design in the project.
