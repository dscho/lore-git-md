This is a design discussion about ref optimization architecture, continuing the thread about adding a `git refs optimize` subcommand. Junio Hamano weighs in with a clear preference for implementing optimization as a backend method in the refs API rather than as standalone code in `pack-refs.[ch]`.

Junio suggests refactoring the approach to:
1. Add a `refs_optimize()` method to the refs backend interface
2. Move files-specific logic into the files backend implementation
3. Potentially deprecate `refs_pack_refs()` in favor of this more general operation
4. Enhance the existing `git pack-refs` command to use this API

He notes this would allow backend-specific optimizations (like for reftable) while maintaining a single user-facing interface. While neutral on the command name itself (`pack-refs` vs `refs optimize`), he strongly advocates for the deeper architectural change to properly integrate with Git's refs backend system.

This email represents a significant maintainer-level design critique of the current approach, suggesting the series needs fundamental restructuring before proceeding. The key question now is whether the original author will pivot to this backend-focused design or attempt to justify the current shared-library approach.
