This is a technical discussion about path length validation in the submodule gitdir path encoding series. Adrian Ratiu responds to Jeff King's feedback on patch 7/10, which handles cases where encoded submodule names might exceed filesystem filename limits.

The core debate is around three approaches to handling path length limits:
1. Letting the filesystem fail naturally (Jeff's first suggestion)
2. Using a hardcoded conservative limit like 255 chars (Jeff's second suggestion)
3. Keeping the current `pathconf()`-based check (Adrian's original implementation)

Adrian expresses no strong preference but notes tradeoffs: the filesystem approach is simplest but may produce confusing errors, while the hardcoded limit would match Git's existing NAME_MAX fallback. The current `pathconf()` method provides clearer error messages and leaves the door open for future improvements (referenced as "the TODO" in the thread).

The discussion remains unresolved but low-stakes, as Adrian notes this could be deferred to a future iteration. This patch was deliberately split out to make the path length handling independent of the core encoding logic. The series remains production-ready regardless of which approach is chosen for this edge case.
