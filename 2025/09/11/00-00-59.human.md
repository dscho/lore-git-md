Security response regarding private branch proposal. Brian M. Carlson explains why Git doesn't support truly private branches as requested, citing fundamental security limitations in Git's design. The core issue is that Git's object model and protocols weren't designed to prevent data leakage - even with namespaces, a determined attacker could potentially access supposedly private objects if they can guess or discover object IDs. The response notes this would require extensive changes to Git's security model that nobody has volunteered to implement, with performance implications for features like partial clone.

Carlson strongly recommends against storing secrets in Git repositories at all, sharing personal experience about the operational headaches of secret rotation after accidental exposure. The reply suggests using dedicated secret stores as a security best practice rather than trying to make branches private. While technically detailed, the response doesn't address the feature development isolation use case from the original request, focusing solely on the security aspects of hiding sensitive files.
