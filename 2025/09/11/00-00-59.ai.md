Security-focused response to private branch proposal. Brian M. Carlson explains why Git cannot securely implement private branches as requested, citing fundamental protocol limitations. They reference `gitnamespaces(5)` to show that Git's design intentionally avoids pretending to provide read access control through namespaces, since determined attackers can discover and request arbitrary object IDs through various side channels (build logs, issue references, etc.). The response notes that true access control would require expensive reachability checks for every object access, harming performance of features like partial clone, plus major internal changes that nobody has volunteered to implement. Carlson strongly recommends against storing secrets in Git at all, advocating for dedicated secret stores instead, based on painful personal experience with secret rotation after accidental exposure. This authoritative response effectively closes the technical discussion by showing the proposal violates Git's security model, though it doesn't address the feature development isolation use case from the original request. The thread now lacks a clear path forward beyond the previously suggested submodule workaround or accepting that some workflows require separate repositories.
