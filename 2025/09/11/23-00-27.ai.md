This is a review response in the ongoing refactoring series for commit graph handling as part of the pluggable ODB effort. Taylor Blau raises two key concerns about Patrick Steinhardt's patch 6/6 which moves commit-graph storage from `struct object_database` to `struct odb_source`:

1. **Behavior change in `read_commit_graph_one()`**: The new version returns NULL on subsequent calls even if a graph was previously loaded, unlike the old `prepare_commit_graph()` which would return the cached graph. Taylor questions whether this might surprise callers.

2. **Alternate handling semantics**: The patch now potentially returns commit graphs from alternates, whereas previously it only returned the main object store's graph. Taylor is uncomfortable introducing this behavior change in the current series, suggesting it should be considered separately.

The review maintains the architectural tension noted in previous thread summaries - while the mechanical refactoring is progressing, there remain open questions about whether commit graphs should be treated as repository-wide caches (Junio/Derrick's view) or source-specific implementation details (Patrick's approach). Taylor's feedback focuses on preserving existing behavior during the transition rather than blocking the overall direction.

Key technical details affecting future discussion:
- Modified files: commit-graph.c, commit-graph.h, odb.c, odb.h, packfile.c
- New behavior patterns around `commit_graph_attempted` flag
- Potential alternate ODB graph loading semantics
- Maintains the series' pattern of moving graph pointers to odb_source while preserving functionality

This continues the pattern of the series where mechanical changes are mostly uncontroversial, but deeper design questions about graph ownership and cross-source behavior remain unresolved. The review doesn't block the patch but flags two specific behavior changes that might need reconsideration or separation from the core refactoring work.
