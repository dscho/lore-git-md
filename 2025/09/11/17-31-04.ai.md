This is a bugfix follow-up in the command deprecation series, specifically addressing recursion detection in alias shadowing of deprecated commands. Kristoffer Haugsbakk reports a regression where the system fails to detect recursive aliases involving deprecated commands (`whatchanged` and `pack-redundant`), unlike the working detection for regular aliases (`one` and `two`).

The issue manifests when deprecated commands form a mutual alias cycle (`whatchanged -> pack-redundant -> whatchanged`), causing infinite recursion instead of the expected fatal error. This occurs despite the same scenario being properly handled for non-deprecated aliases. The test case demonstrates both the working case (regular aliases) and broken case (deprecated command aliases).

The problem affects the alias handling logic in patch 2/7 of the series, which had previously been reviewed and considered complete after fixing a memory leak. This new discovery suggests the recursion detection needs adjustment specifically for the deprecated command path, though the email does not yet propose a solution.

Key technical details:
- The issue involves the interaction between `handle_alias()` and deprecated command handling
- Test case shows working recursion detection for regular aliases vs broken behavior for deprecated ones
- Both the original v4 implementation and Jeff King's suggested modification exhibit the same bug
- Files involved: alias.c` (primary), possibly `git.c` for command dispatch
- Test file: `t/t0014-alias.sh` (where the new test case would be added)

This represents the first post-v4 issue identified in the otherwise finalized deprecation series, requiring attention to the alias handling edge case before integration. The regression affects a core invariant (recursion safety) but appears limited to the deprecated command path.
