This is a discussion email in the ongoing thread about moving commit-graph storage from `struct object_database` to `struct odb_source` as part of the pluggable ODB effort. Taylor Blau responds to Patrick Steinhardt's defense of the design, focusing on conceptual disagreements about the commit-graph's role.

Taylor challenges Patrick's view that commit-graph functionality is purely an optimization tied to the object storage format. While acknowledging the caching aspects, Taylor argues that generation numbers and Bloom filters provide fundamentally new information that would be valuable regardless of storage backend efficiency. The email highlights a key philosophical divide in the thread - whether commit-graphs are implementation details of storage backends (Patrick's view) or repository-wide structured caches (Junio/Derrick's view).

Taylor notes an important behavior change in Patrick's approach: the patch would allow falling back to alternate ODB commit-graphs where previously only the main object store's graph was used. This continues the pattern where mechanical refactoring proceeds while deeper design questions about the commit-graph's conceptual model remain unresolved. The discussion remains technical and collegial, with both sides presenting reasoned arguments about the proper abstraction boundaries.
