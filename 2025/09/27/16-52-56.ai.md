This is a response to a user question about git-worktree behavior, not a patch or proposal. The email provides authoritative clarification from Junio C Hamano about the design rationale for worktree visibility.

Junio explains that worktree directories appear as untracked in the main repository because they are intentionally treated like any other directory containing a Git repository (similar to a nested repository from `git clone`). The behavior is by design - worktrees are not special-cased for ignoring, and doing so would be inconvenient for some workflows. 

The response suggests the user's expectation of automatic ignoring is misplaced, and instead recommends creating worktrees *outside* the main working tree directory if the untracked status is problematic. Junio provides concrete examples of his own workflow where worktrees are created in sibling directories (../git.maint, ../git.next) rather than within the main working tree.

Key technical points clarified:
- Worktree directories are treated identically to any directory containing a `.git` subdirectory
- The behavior is consistent with how nested clones appear in the parent repository
- Alternative workflow pattern shown using `--detach` and sibling directory locations

The response effectively closes the question by presenting the current behavior as intentional and offering a standard workaround, though it leaves open whether this design might ever be reconsidered in future Git versions.
