This thread examines how Git should handle the untracked status of worktree directories, sparked by a user's question about Git 2.51.0 behavior on Fedora. Junio Hamano established that worktree directories are intentionally treated like nested repositories (appearing as untracked in the main repository's status), which helps surface problematic configurations early. 

Michal Suchánek and Jason Cho have since explored edge cases, particularly around the asymmetry in how `.git` files are handled between current and sibling worktrees. Michal's latest contribution shifts the discussion from practical concerns to design philosophy, arguing that status operations could reasonably accommodate worktree awareness without significant performance impact, and questioning whether the current behavior reflects intentional design or implementation convenience. 

Key open questions remain about documentation gaps (particularly around the sibling-directory recommendation), how Git's approach compares to other VCS workflows, and whether the project wants to formalize worktrees as a special case in the untracked-file subsystem. The discussion now balances Junio's authoritative design explanation against emerging questions about conceptual purity versus pragmatic implementation.
