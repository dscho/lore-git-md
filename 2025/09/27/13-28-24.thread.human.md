The thread explores Git's worktree behavior, particularly whether worktree directories should appear as untracked in the main repository's status. Junio Hamano originally explained this as intentional design - treating worktree directories like nested repositories rather than special-casing them. The discussion has since evolved to examine documentation gaps, performance implications, and comparisons with other version control systems.

In the latest exchange, Junio clarifies that the worktree feature was designed with the assumption that worktrees would exist alongside (not inside) the main checkout. He acknowledges this assumption may need revisiting if users consistently find the current behavior confusing, and suggests documentation improvements could help. Michal Suchánek continues to push the discussion toward cross-VCS comparisons, noting that some systems commonly support multiple branch checkouts within a repository directory structure. 

The core tension now lies between Git's established design philosophy (worktrees as peer entities) and workflows imported from other systems. While Junio maintains that side-by-side checkouts represent Git way, he leaves room for reconsidering documentation or behavior if evidence shows widespread user confusion.
