This thread explores how Git handles worktree directories in the main repository, particularly whether they should appear as untracked files. The discussion began with a user question about Git 2.51.0 behavior on Fedora, prompting Junio Hamano to explain the intentional design: worktree directories are treated like nested repositories and appear as untracked in the main worktree's status. The conversation then uncovered an inconsistency - while the current worktree's `.git` file is hidden, sibling worktrees' `.git` files show as untracked.

Jason Cho's latest contribution strengthens the case by demonstrating a concrete problem with creating worktrees inside the main worktree directory. He shows how checking out a branch with a filename matching an in-repo worktree directory would fail, validating Junio's recommendation to place worktrees in sibling directories (like `../git.maint`) instead. This doesn't resolve the `.git` file asymmetry question, but provides practical justification for the current behavior - treating worktree directories as untracked helps users detect these configurations early.

The thread now has two clear takeaways: first, the community consensus strongly favors creating worktrees outside the main worktree directory to avoid path collisions. Second, while the technical inconsistency in `.git` file handling remains, its practical impact appears limited given the recommended workflow. No code changes have been proposed, but the discussion has clarified both the design rationale and potential pitfalls of alternative approaches.
