This thread examines how Git should handle worktree directories in status output, sparked by a user question about why these appear untracked in the main repository. Junio Hamano clarified that this is intentional - worktrees are designed as peer entities to the main checkout, not nested within it, and should ideally be placed in sibling directories. Michal Suchánek has questioned whether this behavior represents deliberate design or implementation convenience, noting inconsistencies in how `.git` files are handled between current and sibling worktrees, and comparing Git's approach to other VCS workflows.

The discussion has expanded to consider documentation gaps, performance implications, and philosophical questions about Git's abstraction design. Jason Cho validated the sibling-directory approach, while Michal highlighted the persistent risk of branch-switch collisions with nested worktrees. Ben Knoble has now introduced an important practical consideration: shell prompts frequently use Git status information, making any performance impact from worktree directory checks more noticeable to users. This adds weight to the evaluation of whether potential changes to status behavior would meaningfully affect real-world usage.

Key open questions remain about whether the current behavior should be preserved as intentional design (helping surface problematic configurations) or treated as an implementation artifact that could be improved. The thread continues to balance technical constraints, user expectations from other VCSes, and now concrete performance considerations like prompt responsiveness, while Junio maintains the original design philosophy that worktrees should conceptually be peers rather than nested entities.
