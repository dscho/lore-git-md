This thread has evolved from a user's question about worktree behavior in Git 2.51.0 to a broader discussion about worktree UX and documentation. The core issue revolves around how Git handles worktree directories in status output and the common pitfall of users accidentally creating nested worktrees inside their main worktree.

Junio Hamano, the Git maintainer, has consistently defended the current design where worktree directories appear as untracked in status output, citing performance considerations (especially for shell prompts) and the original peer-entity design philosophy. While acknowledging UX shortcomings, he maintains that the fundamental behavior shouldn't change. The discussion has now shifted toward improving documentation rather than modifying behavior.

Recent contributions have highlighted that:
1. Nested worktree usage is more common than previously thought (Eric Sunshine)
2. The bare repository + worktrees pattern naturally prevents nesting issues but needs better documentation (now agreed by Junio)
3. Shell prompt performance is a critical constraint (Ben Knoble)
4. There's a persistent mental model mismatch between worktrees and submodules for new users

Michal Suchánek's latest email pushes for more explicit documentation, suggesting adding warnings against in-tree worktrees directly in the `git worktree add` command description and better explaining the bare repository pattern. This reflects the thread's current consensus that documentation improvements are the most practical way forward, though some philosophical differences about usage patterns remain unresolved.

The discussion has effectively ruled out behavior changes to the status output or worktree creation command due to performance constraints and design principles, instead focusing on making the intended usage patterns clearer through documentation improvements.
