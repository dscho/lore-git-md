This thread explores the behavior and user experience of Git worktrees, particularly around how they appear in `git status` and where they're created. The discussion began with a user questioning why worktree directories show as untracked in the main repository's status. Junio Hamano explained this is intentional - worktrees are treated like nested repositories, not special-cased. The conversation has evolved to examine documentation gaps, performance implications for shell prompts, and comparisons to other version control systems.

A new dimension emerged when Sergey Organov pointed out that users often accidentally create worktrees inside their primary worktree directory rather than as siblings, leading to the status visibility issue. Junio acknowledged this as a known UX problem, sharing that he habitually uses "../" prefixes to avoid it. He suggested improving documentation and possibly adding safeguards when users attempt nested worktree creation. This shifts focus from debating the core behavior to preventing the problematic pattern through better user guidance. The thread now balances technical design philosophy with practical workflow improvements, with Junio's position remaining consistent while welcoming concrete UX enhancements.
