This thread has been exploring the behavior and user experience of Git worktrees, particularly around how they appear in status reports and the implications of creating nested worktrees. The discussion was sparked by a user question about Git 2.51.0 on Fedora and has evolved through multiple phases of technical analysis and design philosophy debate.

Junio Hamano, Git's maintainer, has consistently maintained the original design position that worktree directories should appear as untracked in the main repository's status, similar to nested clones. The discussion has revealed that while some users intentionally create nested worktrees without issue, others find this pattern confusing, especially when coming from a submodule mental model. Eric Sunshine provided evidence that nested worktree usage is more common than previously thought, leading to agreement that the documentation should better explain the recommended "bare repository + worktrees" pattern that inherently prevents nesting issues.

The latest contribution from Ben Knoble focuses on performance considerations, particularly how status operations impact shell prompts. He clarifies that while he supports Junio's design position, he wants to ensure that any future changes don't inadvertently make status operations more expensive, as this would affect a common workflow. This reinforces the thread's emerging consensus that documentation improvements - rather than behavior changes - are the right path forward, while acknowledging that different workflows (including some nested patterns) may have valid use cases.

The thread now appears to be converging on documenting best practices more clearly, including the sibling-directory approach and bare repository pattern, while maintaining the core worktree design principles. Performance considerations for common use cases like shell prompts remain an important factor in evaluating any potential changes.
