This thread has been exploring the nuances of Git worktree behavior and user experience, particularly around how worktrees interact with status reporting and where they should be created. The discussion began with user reports of worktree directories showing up as untracked in the main repository's status, which some found confusing or noisy.

Junio Hamano, Git's maintainer, has consistently maintained that worktrees are designed as peer entities to the main repository, not nested components. He's acknowledged the UX challenges but sees them as stemming from users creating worktrees in suboptimal locations rather than a flaw in the core design. Recent contributions from Eric Sunshine have provided evidence that nested worktree usage is more common and intentional than previously thought, though Junio suggests this might indicate most users simply avoid nesting worktrees in the first place.

The conversation has evolved to focus on documentation improvements, with agreement that patterns like using bare repositories with worktrees should be better documented. Junio notes this pattern naturally avoids the nesting issue since bare repos have no working directory to nest within. While some behavioral changes were initially proposed (like warnings for nested creation), the discussion now centers on clarifying the design philosophy and documenting established practices rather than changing core behavior.

Key participants have included Eric Sunshine providing empirical data on real-world usage, Jakub Jankiewicz offering a novice perspective, and Junio articulating the design rationale. The thread shows how Git's maintainers balance user experience concerns with preserving intentional design decisions, opting for documentation improvements when behavioral changes aren't aligned with the underlying model.
