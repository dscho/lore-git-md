This is a feature request proposing partial URL matching for Git credential configuration. The credential helper `git-credential-oauth` currently cannot distinguish between different path prefixes under the same host (like `example.com/org1` vs `example.com/org2`), as Git's credential matching requires exact path matches when paths are specified in the config.

The request suggests two possible syntax options for wildcard matching: an explicit wildcard (`credential.https://example.com/org1/*.key`) or an implicit wildcard (`credential.https://example.com/org1/.key`). The current behavior only matches exact paths or the bare domain, which limits credential configuration flexibility for users needing different credentials for different paths under the same domain.

The proposal comes from a real-world use case reported in the git-credential-oauth project (issue #83). This would require changes to Git's credential URL matching logic, which currently treats path components as exact matches only. The documentation explicitly states this limitation in the gitcredentials man page.

Key technical points for future reference:
- Current behavior: Paths in credential URLs must match exactly or be omitted entirely
- Proposed change: Allow wildcard matching for path prefixes
- Two syntax variants suggested for wildcard indication
- Affects credential helper configuration and URL matching logic
- Motivation comes from git-credential-oauth use cases
- Would require changes to credential.c matching logic and documentation updates

This appears to be a well-motivated feature request that could improve credential management for users with complex URL patterns, though the implementation would need to consider backward compatibility and security implications of wildcard matching.
