This is a response to a user question about git-worktree behavior, explaining why worktree directories aren't automatically ignored in the main repository's status.

Junio C Hamano clarifies that worktrees are intentionally treated like any other directory containing a Git repository - they appear as untracked because they are untracked content from the containing repository's perspective. The behavior is by design and consistent with how Git handles nested repositories in general.

The response provides practical advice: rather than expecting automatic ignoring, users should create worktrees outside their main working tree directory. Junio shares his own workflow of keeping worktrees in sibling directories (../git.next, ../git.maint etc.) as a cleaner alternative to nesting them inside the main worktree.

The explanation is direct and authoritative, coming from Git's maintainer, and effectively closes the question by stating this is working as intended rather than being a bug or oversight. The suggested workaround is simple and aligns with common Git workflows.
