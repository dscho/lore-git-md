This is a security-focused follow-up in the ongoing performance optimization thread comparing khash and commit-slab approaches, specifically addressing hash function vulnerabilities.

René Scharfe raises concrete security concerns about using `oidhash()` directly in hash table implementations, building on his earlier warnings. He cites the `lucky-commit` tool as evidence that attackers could feasibly generate commits with chosen hash prefixes, allowing them to create worst-case O(N) performance scenarios by forcing hash collisions. The example shows that even 32-bit prefixes (used by `oidhash()`) could be targeted, potentially degrading hash table operations to linear time across the entire repository history.

This email strengthens the security argument against direct `oidhash()` use that was previously discussed in the thread, providing a real-world tool demonstrating the attack feasibility. It reinforces the emerging consensus that security considerations must factor into data structure choices, alongside the performance characteristics that have dominated the discussion so far. The concern applies particularly to the `git describe` optimizations and any other cases where object hashes might be exposed to potentially malicious input.
