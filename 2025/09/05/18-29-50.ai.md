This is a design discussion in the ongoing thread about moving commit graph tracking from object_database to odb_source as part of the pluggable ODB effort. Derrick Stolee weighs in on Junio Hamano's earlier objections, providing additional technical perspective on the commit graph's role in the repository architecture.

Stolee observes that commit graphs behave as a "structured cache" that spans the entire repository rather than being tied to individual object stores, despite their physical storage location. He notes the current "first one wins" behavior when loading commit graphs from multiple sources, and points out that commit parsing and Bloom filter operations typically work at the repository level without regard to which object store contains the data.

While supporting the mechanical cleanups in patches 1-5, Stolee agrees with Hamano's architectural concerns about patch 6's core change. He suggests keeping the graph state at the object_database level while still allowing I/O operations to use odb_source for file location purposes. This maintains the repository-wide nature of commit graphs while accommodating the pluggable ODB infrastructure's needs.

The email reinforces the key architectural question about whether commit graphs should be repository-wide (current behavior) or source-specific (as proposed in the series). Stolee's perspective as a contributor deeply familiar with the commit graph implementation adds weight to Hamano's earlier objections, suggesting the series may need significant redesign around this fundamental point. The technical discussion continues to focus on balancing the graph's conceptual role with the physical storage requirements of the pluggable ODB system.
