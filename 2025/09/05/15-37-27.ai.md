This is a policy discussion in the ongoing Rust infrastructure RFC series, specifically addressing the transition timeline proposed by Phillip Wood. Junio Hamano responds to Wood's three-phase plan (6 months optional, then mandatory Rust, with 3 years of security updates for the last Rust-optional version).

Key technical context remains stable from previous discussion: the `ivec` interop layer, Rust module structure (`xprepare.rs`, `xtypes.rs`), and build system changes with `NO_RUST=1` escape hatch. The debate here focuses purely on transition mechanics.

Hamano agrees with the core approach but pushes back on specific timeframes:
- Accepts the 6-month optional period but questions calling it "short"
- Strongly objects to 3 years of security updates for Rust-optional versions, suggesting instead 18 months
- Proposes an alternative timeline: 3 years optional period followed by 18 months security updates
- Implicitly endorses the phased approach but wants more generous timelines for platform maintainers

The email reveals a key policy tension: balancing the project's desire to move forward with Rust against practical concerns for niche platforms. Hamano's position suggests he views the current proposal as too aggressive in deprecating non-Rust builds, particularly for commercial/legacy systems (NonStop, Cygwin) that were previously discussed in the thread.

This response will likely trigger further discussion about:
- Whether the 6-month optional period provides sufficient notice (Steinhardt had previously endorsed this)
- How to define "realistic" transition periods for different platform classes
- Whether security update commitments should scale with the optional period length
- The project's responsibility toward commercial/non-mainstream platforms

The technical implementation remains unaffected by this policy debate, with consensus already established on the Rust xdiff architecture and build system integration.
