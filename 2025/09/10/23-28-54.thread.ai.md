Brian M. They noted that true access control would require expensive reachability checks for every object access, harming performance of features like partial clone, plus major internal changes that nobody has volunteered to implement. Carlson strongly recommended against storing secrets in Git at all, advocating for dedicated secret stores instead.

Henrique Soares' reply reinforces the emerging consensus by pointing out that local branches are inherently private when not pushed to a remote, and suggests two existing solutions: keeping sensitive work local (the simplest approach) or using submodules for selective sharing of sensitive files like `.env`. This aligns with Carlson's technical explanation but focuses more on practical workflow solutions rather than protocol limitations. The thread now lacks a clear path forward beyond these workarounds or accepting that some workflows require separate repositories. Open questions remain about whether the feature development isolation use case from the original request can be addressed through existing mechanisms, and whether core Git changes would still be warranted versus relying on hosting provider capabilities.
