Feature suggestion for private branches in Git, with discussion shifting toward security limitations and practical alternatives. The original proposal suggested adding private branch functionality to hide sensitive files (like .env) or develop features privately before merging. Randall S. Becker (rsbecker@nexbridge.com) proposed a workaround using Git submodules combined with GitLab's visibility controls, which isolates private content in a separate repository while maintaining a public main project. Brian M. Carlson (brian m. carlson) authoritatively explained why Git cannot securely implement private branches as requested, citing fundamental protocol limitations and referencing `gitnamespaces(5)` to show Git's design intentionally avoids pretending to provide read access control through namespaces. They noted that true access control would require expensive reachability checks for every object access, harming performance of features like partial clone, plus major internal changes that nobody has volunteered to implement. Carlson strongly recommended against storing secrets in Git at all, advocating for dedicated secret stores instead.

Henrique Soares' reply reinforced the emerging consensus by pointing out that local branches are inherently private when not pushed to a remote, and suggested two existing solutions: keeping sensitive work local (the simplest approach) or using submodules for selective sharing of sensitive files like `.env`. Kristoffer Haugsbakk now contributes a third workflow alternative: maintaining a completely separate `.git-mine` repository alongside the main project's `.git` directory, allowing parallel working trees with non-overlapping files. This approach provides physical isolation without protocol changes, though it requires manual coordination between two independent repositories and loses change-tracking relationships compared to submodules.

The thread has converged on rejecting protocol-level solutions due to fundamental security and performance limitations in Git's design. All proposed alternatives (local branches, submodules, dual repositories) represent different tradeoffs between isolation and workflow convenience. No technical objections remain to the core security analysis from Carlson, and no new proposals for Git-level changes have emerged. The open question about feature development isolation appears answerable through existing mechanisms, with the choice between them depending on specific project needs rather than requiring core Git changes. The discussion now lacks unresolved technical questions, having shifted entirely to workflow recommendations building on Git's current capabilities.
