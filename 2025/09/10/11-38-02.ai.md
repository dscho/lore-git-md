This is a continuation of the architectural debate around commit graph handling in the pluggable ODB effort, specifically addressing the tension between repository-wide versus source-specific graph models.

Patrick Steinhardt responds to Derrick Stolee's position that commit graphs serve as repository-wide caches regardless of storage format. He clarifies that his proposal isn't about changing commit object types but about allowing different storage formats for metadata like generation numbers and bloom filters. Steinhardt provides concrete examples where alternative storage (cloud databases, SQLite) might handle this metadata more efficiently than the current commit-graph files.

The key technical proposal is to move graph-related decisions into object source backends via three function pointers:
1. Existence check for cached graph representations
2. Bloom filter/generation number loading
3. Commit loading via cached representation

Steinhardt argues this source-specific approach better accommodates diverse storage needs while maintaining abstraction. He acknowledges Stolee's alternative (repository-level graph handling with backend queries) could work but considers it potentially more complex. The email hints at an upcoming design document to formalize these ideas after completing two more patch series.

This response sharpens the technical contrast between the approaches while maintaining a constructive tone. It introduces concrete interface proposals that could inform future design discussions, though the fundamental architectural disagreement remains unresolved. The exchange exemplifies the careful balancing act in the ODB effort between abstraction purity and practical implementation concerns.
