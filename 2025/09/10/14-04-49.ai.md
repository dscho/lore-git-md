This is a review comment on the "split" subcommand implementation in Patrick Steinhardt's `git-history` RFC series (v3 patch 17/18). Phillip Wood suggests improvements to the commit message handling during the split operation.

Key technical points from Phillip's feedback:
- Current implementation only prompts for a new message for the first split commit, keeping the original message for the second
- Suggests prompting to edit both commit messages since either could contain most of the original changes
- Proposes implementing this in the sequencer to reuse existing commit message editing code
- Would make the split functionality available to `rebase -i` as well

The patch being reviewed adds substantial functionality:
- New `git history split` command that interactively splits a commit into two
- Uses `add-patch` interface to select hunks for the first commit
- Handles pathspec filtering, empty commit prevention, and hook execution
- Includes comprehensive tests covering various split scenarios

Phillip's suggestion touches on a key UX consideration - when splitting a change, either resulting commit might need message updates depending on how the changes are divided. His proposal would integrate better with existing Git infrastructure while providing more flexibility to users.

This continues the thread's pattern of constructive feedback on how to best integrate new history editing operations with Git's existing command architecture. The suggestion aligns with earlier discussions about command proliferation vs consolidation.
