This is a design discussion email in the ongoing RFC thread about the proposed `git-history` command, focusing on architectural considerations and potential integration with existing Git infrastructure.

Phillip Wood responds to the discussion between Patrick Steinhardt and Elijah Newren about the `git-history` proposal. He shares his experience with a similar `git-rewrite` wrapper he's been using, which provides functionality like amending, rewording, and dropping commits while rewriting all affected branches. Wood suggests several key architectural considerations:

1. **Integration Approach**: Questions whether to use the sequencer or extend `git-replay`, noting the current implementation's limitation of being based on cherry-picking rather than using the sequencer's todo list mechanism. He suggests adding a new sequencer entry point that accepts a todo list.

2. **Hook Behavior**: Proposes specific rules for when different hooks should run during history editing operations (commit-msg/prepare-commit-msg for reword, plus pre-commit for content changes).

3. **Future Features**: Mentions a useful feature from his wrapper that allows specifying edits via filename/line number pairs, which could be added to `git-history`.

4. **Branch Updates**: Suggests using the sequencer's update-ref mechanism to update all branches containing modified commits, which would require deeper sequencer integration.

Wood's feedback continues his pattern of advocating for better reuse of existing Git infrastructure rather than standalone implementations, as seen in his previous reviews of the `reword` subcommand. His comments align with Elijah Newren's earlier questions about command proliferation versus consolidation, while providing concrete technical suggestions about how integration might work.

The email doesn't propose specific code changes but rather frames architectural considerations that would affect the entire series, particularly around the sequencer integration and hook behavior. These points will likely influence future iterations of the RFC.
