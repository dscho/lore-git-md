Feature proposal for a `git history split` subcommand, part of Patrick Steinhardt's larger `git-history` RFC series (now at v3 with 31 patches). This patch implements an interactive way to split a commit into two by selecting which hunks should move to a new parent commit.

Phillip Wood provides constructive feedback on the implementation, suggesting two key improvements:
1. The current flow only prompts for a message for the new split-out commit, not allowing editing of the original commit's message. Phillip argues users may want to adjust both messages depending on how they're dividing the changes.
2. Implementing this in the sequencer would allow code reuse and make the functionality available via `rebase -i` as well.

The implementation shows thorough test coverage (468 lines of tests) for various scenarios:
- Handling different commit positions (tip, root, in-between)
- Pathspec filtering
- Hook execution
- Edge cases (empty commits, merge commits, dirty worktree)
- Interactive hunk selection

The command aims to simplify what's a complex manual process today (involving rebase -i, resets, and multiple commits). While the patch appears well-constructed, Phillip's feedback suggests opportunities to better integrate with existing Git infrastructure and improve the user experience around commit message editing.
