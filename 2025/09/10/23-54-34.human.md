This is a response in an ongoing discussion about private branches in Git. The original proposal suggested adding private branch functionality to handle sensitive files or in-progress features, though it lacked technical details. 

In this email, Randall Becker provides a practical workaround using Git submodules, suggesting to place private content in a separate submodule repository and control its visibility through GitLab's access controls. This addresses the .env file use case mentioned in the original proposal while working within Git's existing capabilities.

The response also gently chides the original poster for their informal language, reminding them of mailing list etiquette. The suggestion to use submodules is a pragmatic solution that doesn't require core Git changes, though it doesn't address the broader feature-branch visibility use case from the original proposal. The thread remains open for discussion of whether core Git changes might still be warranted.
