Feature implementation for `git-history reword` subcommand, part of the larger `git-history` RFC series (v3 patch 18/18). This patch adds commit message rewriting capability to the proposed history editing command suite, following the same pattern as interactive rebase's "reword" action.

Phillip Wood's review points out that the implementation duplicates existing sequencer functionality rather than reusing it. The current patch implements reword as a standalone operation with its own commit creation logic (handling author information, tree objects, and commit rewriting) when the sequencer already provides this capability. The implementation includes thorough test coverage (202 lines across 8 test cases) verifying behavior with merge commits, dirty worktrees, various commit positions (tip, middle, root), editor interaction, hook execution, and empty message handling.

Key technical details:
- Adds `reword` subcommand to `builtin/history.c` with `--message` option
- Implements new `cmd_history_reword()` function performing:
  - Commit lookup and validation
  - Message handling (provided or via editor)
  - New commit creation preserving original tree and parents
  - Commit chain rewriting
  - Hook execution (prepare-commit-msg, post-commit, post-rewrite)
- Adds test script `t/t3454-history-reword.sh` covering:
  - Merge commit rejection
  - Dirty worktree/index detection
  - Rewording at different commit positions
  - Editor interaction
  - Hook execution verification
  - Empty message prevention

The review suggests architectural reconsideration to leverage existing sequencer code rather than reimplementing similar functionality, which could both simplify this implementation and benefit other commands like `rebase -i`. This aligns with Phillip Wood's previous feedback pattern about better integrating new functionality with Git's existing infrastructure.
