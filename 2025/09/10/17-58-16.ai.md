Feature refinement for git replay's atomic ref updates.

This email from Siddharth Asthana responds to Elijah Newren's review of the atomic reference update functionality for `git replay`. The discussion focuses on simplifying the interface from three proposed modes (individual updates, atomic transactions, and partial-failure batches) down to a cleaner design. Key points:

Siddharth acknowledges the confusion caused by having both `--update` (individual ref updates) and `--update-refs` (atomic transactions), agreeing with Patrick Steinhardt's earlier performance concerns about the individual update approach. The proposed simplification would make atomic transactions the default behavior, with `--output-commands` preserving the old pipe-to-update-ref workflow and `--allow-partial` handling cases where some ref updates can fail independently.

The email also addresses a questionable initialization of `result.clean` that Elijah flagged - Siddharth confirms this was unnecessary and will remove it in v2 since empty commit ranges are already handled correctly by existing code. The discussion shows convergence toward a design where atomic updates become the primary mode, addressing earlier debates about default behavior while maintaining backward compatibility through clear opt-in flags.

Implementation details mentioned include the use of `ref_store_transaction_begin()` for atomicity and the removal of redundant `update_ref_direct()` code paths. The thread continues to refine the balance between ideal technical solutions (atomic by default) and practical deployment needs (keeping pipeline workflows possible via explicit flags). This email moves the discussion forward by synthesizing feedback into concrete interface simplifications for the next revision.
