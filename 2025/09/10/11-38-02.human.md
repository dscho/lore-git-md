This is a technical discussion in the ongoing debate about commit graph architecture for the pluggable ODB effort. Patrick Steinhardt responds to Derrick Stolee's arguments about commit graphs being repository-wide caches rather than storage-specific optimizations.

Steinhardt clarifies his position is not about changing commit object types, but about allowing different storage formats for metadata like generation numbers and bloom filters. He provides concrete examples where cloud-based object storage might benefit from storing this data alongside objects rather than in separate commit-graph files. The key proposal is to let each object source backend decide how to store and provide this metadata, with standardized function pointers for access (checking existence, loading filters/numbers, loading commits). This would abstract away whether the data comes from commit-graph files, database tables, or other formats.

Steinhardt acknowledges Stolee's repository-wide cache model could technically work but argues his source-specific approach better matches the pluggable ODB goals and would likely result in cleaner implementation. The email hints at an upcoming design document to formalize these ideas, suggesting this architectural discussion is still in flux. The tone remains constructive, with Steinhardt explicitly appreciating the technical debate while standing firm on the source-specific model's advantages.
