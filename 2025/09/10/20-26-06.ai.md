This is a documentation update for the atomic reference updates feature in `git replay`, part of the ongoing series to enable server-side workflows. The email focuses on resolving naming and interface design questions that emerged from earlier discussion.

Siddharth Asthana responds to Christian Couder's feedback about the `--update-refs` flag name potentially conflicting with `git rebase`'s similarly-named option. The key resolution is to adopt the simplified interface already endorsed by Junio Hamano and Elijah Newren: atomic updates become the default behavior, with `--output-commands` providing backward compatibility for pipeline users and `--allow-partial` handling non-atomic cases. This avoids the naming collision while preserving all functionality.

The discussion confirms removal of the redundant `--update` flag that was causing confusion, as its behavior can now be achieved through `--output-commands`. Documentation will clearly explain the performance and reliability differences between atomic updates (default) and command-output mode. The email also notes this design addresses Patrick Steinhardt's earlier performance concerns by using batched transactions.

Implementation-wise, this means `builtin/replay.c` will use `ref_store_transaction_begin()` by default, with the test suite in t3650/t3651 verifying the atomic behavior. The documentation updates will need to reflect that server-side users (particularly GitLab/Gitaly) should prefer the default atomic mode unless specifically needing command output for scripting.
