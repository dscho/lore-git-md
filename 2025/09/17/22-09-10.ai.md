This is a documentation patch in the ongoing Rust infrastructure series, specifically addressing the BreakingChanges announcement about Rust becoming mandatory in Git 3.0. SZEDER Gábor raises an important concern about SHA-1/SHA-256 interoperability in the context of platforms that won't have Rust support when Git 3.0 is released.

The original patch from Patrick Steinhardt outlines a phased approach to Rust adoption (optional in 2.52, default in 2.53, mandatory in 3.0) and proposes an LTS release for platforms that can't support Rust. However, it doesn't address how the SHA-256 transition - another major change planned for Git 3.0 - will interact with the Rust requirement, particularly for SHA-1/SHA-256 interoperability features.

SZEDER Gábor points out that if SHA-1/SHA-256 interop is only available via Rust code, this creates a functional gap for platforms stuck on the LTS release. The question implies this could affect repository migrations and compatibility between SHA-1 and SHA-256 repositories. The response suggests this interaction should be explicitly documented in the BreakingChanges announcement, with clear justification that the project has considered and accepted these limitations.

This email highlights an important cross-cutting concern between two major Git initiatives (Rust adoption and SHA-256 transition) that wasn't fully addressed in the original documentation. The issue touches on backward compatibility, platform support tradeoffs, and the practical implications of making Rust mandatory while simultaneously changing default hash algorithms. The concern is well-framed and technical, focusing on a concrete interoperability scenario rather than objecting to Rust adoption in principle.
