Refactoring patch for varint implementation as part of Rust integration preparation.

This patch standardizes integer widths in Git's varint encoding/decoding subsystem, replacing implicit types with explicit ones. Patrick Steinhardt changes the varint implementation to use `uint64_t` for values and `uint8_t` for length tracking, since varints are already limited to 16 bytes maximum. The changes affect both the core varint functions (`encode_varint`/`decode_varint`) and their callers in `dir.c` and `read-cache.c`.

The motivation is twofold: improving platform independence by removing implicit width assumptions, and preparing for Rust reimplementation where explicit types are preferred. Ezekiel Newren suggested this change, which appears to be part of the broader Rust integration effort (though this patch doesn't directly mention Rust beyond the commit message). The changes are behavior-preserving, just making the type contracts more precise.

Key technical details: `uintmax_t` becomes `uint64_t` for decoded values, `int` becomes `uint8_t` for encoded lengths, and call sites are updated accordingly. The patch touches varint's API surface (header changes) and several consumers that handle untracked cache and index entries. This appears to be a straightforward, mechanical change with no expected controversy, serving as groundwork for future Rust version of varint.c mentioned in the commit message.
