This is a follow-up discussion in the now-approved batched reference update series, addressing a final edge case regarding lock file handling on case-insensitive filesystems. The email clarifies the behavior when fetching both `refs/heads/foo` and `refs/heads/foo.Lock` references on case-insensitive systems. Karthik Nayak explains that with batched updates, the second reference wouldn't be created due to lock file collision detection, while without batching both would be created but subsequent updates to `foo` would fail. The discussion reveals this was always a latent issue in the files backend, though not severe enough to block merging the series. The exchange serves to document this remaining edge case for future consideration, particularly as the community moves toward the reftable backend which won't have these filesystem-specific issues. No code changes are proposed here - just technical clarification of the known limitation.
