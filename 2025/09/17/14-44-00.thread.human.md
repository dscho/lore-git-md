This thread began with Kevin Puetz reporting that `git fetch --dry-run --filter` was unexpectedly modifying `.git/config`, which violates the expected dry-run semantics. The discussion has evolved into a deeper technical exploration of how Git checks commit existence in partial clones, with Jeff King (Peff) identifying a client-side protocol bug in `--negotiate-only` behavior and analyzing several alternative approaches.

Junio C Hamano has now weighed in on Jeff King's suggestion to use tmp-objdir for true dry-run behavior. Junio notes that when dry-run was originally written, the quarantine mechanism (tmp-objdir) didn't exist, and questions whether strict dryness is actually preferable. He points out that the current behavior - where healthy objects are stored between dry-run and real operations - provides performance benefits by avoiding re-downloading already-verified objects in subsequent fetches. This introduces a key tradeoff between purity (true dry-run behavior) and practical optimization.

The core issue remains unresolved, but the discussion has significantly deepened our understanding of the technical constraints. We now have multiple potential solution paths with documented tradeoffs, including protocol fixes, server-side extensions, and workarounds using environment variables. Junio's perspective adds the important consideration that sometimes practical performance benefits may outweigh strict semantic purity, especially for consecutive operations. The Windows-specific context of the original report may also need consideration in any final approach.
