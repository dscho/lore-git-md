This is a discussion about the behavior of the proposed `git-history drop` command in Patrick Steinhardt's RFC series for new history editing functionality.

SZEDER Gábor raises a specific concern about the scope of automatic rebasing when using `git-history drop`. The command is planned to follow Jujutsu's behavior of not just dropping the target commit but also rebasing all its descendants - a potentially far-reaching operation. Gábor provides a concrete example with multiple branches to illustrate where this could become problematic, asking which commits would be rewritten and which branches repointed if commit B were dropped in the given topology.

The question highlights an important edge case in the proposed design. While Patrick has confirmed the intention to match Jujutsu's behavior, Gábor's example shows this could have surprising consequences in complex branch topologies, particularly when multiple branches share common ancestry. This suggests the need for either clear documentation of the scope of these operations or potentially more conservative default behavior with opt-in flags for broader rewrites.

The exchange is part of ongoing discussions about how to balance power and safety in the new history editing commands, with contributors carefully considering real-world usage scenarios. Gábor's example provides a valuable test case that may influence the final implementation details of the `drop` subcommand.
