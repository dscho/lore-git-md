Bug report about recursion depth limitation in `git subtree`. Arun Sharma reports hitting a maximum recursion depth (1000) when trying to push a subtree from the PostgreSQL repository, specifically when processing commits with `process_split_commit()` and `check_parents()` mutually calling each other. The issue occurs with a subtree containing 1685 commits from a parent repository with 52k commits.

The report notes that attempts to work around this via `ulimit -s` and `FUNCNEST=10000` were unsuccessful. The author asks whether non-recursive implementations exist or if alternative language implementations of `git-subtree` might avoid this issue. This appears to be a genuine limitation in the shell script implementation when handling deep commit histories, though the report doesn't include specific reproduction steps or a minimal test case.

The question about alternative implementations is particularly relevant given that `git subtree` is currently implemented as a shell script in `contrib/subtree/`, making it more susceptible to recursion depth limits than a C implementation would be. The bug appears to affect real-world usage with large repositories like PostgreSQL, though it's unclear how common this failure mode is in practice.
