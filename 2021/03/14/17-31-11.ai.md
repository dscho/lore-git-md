This is a follow-up in the ongoing thread about recursion depth limitations in `git subtree`. Arun Sharma provides the requested environment details to help investigate the issue: Ubuntu 20.04, Git 2.25.1, and Bash 5.0.16. He also offers a concrete reproduction case using the PostgreSQL repository, specifically splitting and merging the `src/interfaces/libpq` subtree.

The email confirms this is indeed a real-world use case hitting the shell recursion limit, not just a theoretical concern. The PostgreSQL repository is large enough (52k commits) to trigger the mutual recursion between `process_split_commit()` and `check_parents()` that was described in the initial report. The reproduction steps suggest this could be a common workflow pain point for projects maintaining subtrees of large upstream repositories.

While this doesn't advance a technical solution, it provides the missing context that brian m. carlson had requested. The thread now has all the key elements for someone familiar with `git subtree` to investigate further: clear reproduction steps, environment details, and confirmation this affects a major open source project's workflow. The ball is now in the court of contributors who work on subtree or shell-script-to-C conversions to propose architectural changes that could address the recursion limitation.
