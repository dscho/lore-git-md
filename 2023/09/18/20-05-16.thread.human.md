A regression in `git subtree split` has been reported by Colin Stagner, affecting Git 2.44 and later. The issue occurs when splitting subtrees that contain squashed subtree merges, causing parts of the history (particularly nested subtree content) to be incorrectly omitted from the split result. The problem manifests when using `git subtree add --squash` followed by `git subtree split`, where commits containing squashed merges are being filtered out due to missing "git-subtree-mainline:" markers.

The reporter has identified commit 98ba49ccc247 as the likely culprit, which was part of a larger subtree-related patch series. Testing confirms the behavior changed between v2.43 (working correctly) and v2.44 (showing the regression), with the newer version failing to include the contents of a `deeper/` directory in the split output. The report includes clear reproduction case and technical analysis pointing to the commit filtering logic in `should_ignore_subtree_split_commit()` as the source of the problem. This appears to be a legitimate regression affecting users who rely on splitting repositories containing squashed subtree merges.
