This is a follow-up in the `git branch --contains` performance thread, where Oswald Buddenhagen responds to Jeff King's explanation about why commit-graph optimizations are disabled when replace refs are present. 

Oswald acknowledges the challenges around warning users when optimizations are disabled, noting that automatic graph building during GC/fetch would make warnings pervasive in repos with replace refs. He suggests two potential solutions: allowing users to suppress the warning by manually disabling graph writing, or making it an advisory message that can be explicitly silenced. However, he points out the downside that users might miss future optimizations if they've silenced the warning and don't track changelogs.

The exchange continues the discussion about Git's design tradeoffs in this edge case, with Oswald offering practical suggestions while recognizing the inherent limitations. The core performance issue (30ms vs 1m40s) remains solved by disabling replace refs, but the thread surfaces ongoing questions about how Git might better handle such optimization-disabling scenarios in the future.
