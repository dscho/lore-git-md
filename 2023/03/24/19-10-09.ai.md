This is a technical analysis from Jeff King (Peff) in the ongoing discussion about optimizing `git branch --contains` performance. Peff digs into the implementation details, revealing that while commit-graph usage provides significant speedups (reducing runtime from 1m40s to 30ms in his test case), there may be further optimization opportunities in how the tag algorithm is applied.

Key technical findings:
1. The current implementation processes refs individually rather than using a single walk, even with commit-graph enabled
2. A proposed patch to enable the tag algorithm when generation numbers are available shows modest additional improvement (30ms -> 23ms)
3. Peff questions why the more efficient reach_filter() mechanism isn't being used for --contains operations

The email provides concrete performance measurements from linux.git and suggests the discussion should consider whether to:
- Adopt the tag algorithm more widely when generation numbers are available
- Explore using reach_filter() for --contains operations
- Better understand why the theoretical generation number optimizations aren't providing larger gains

This moves the conversation forward by identifying specific code paths that could be optimized, while validating that commit-graph usage does provide the bulk of the performance benefit. The analysis suggests the remaining optimizations may be marginal compared to ensuring commit-graph is properly utilized.
